二 · 速查表总览：一行一条作弊路径

这张表的设计目标是“照着填就能用”：每一行对应一条可被静态扫描或差分测试捕获的作弊路径，列给出字段名（写进审计报告时的键名）、判定阈值（触发红/黄灯的量化口径）、口径（这条阈值在什么测量条件下成立）。表里不出现“大概”“通常”，凡是无法给出固定阈值的项，一律写成“定性判定 + 必须附证据”的形式，避免审计者用主观判断替代证据链。

字段作弊路径阈值 / 判定口径
hardcoded_output硬编码输出输入扰动后输出逐位不变 → 红对同 shape 的 8 组随机输入做差分，逐元素 bitwise 比较
cache_reuse缓存结果冒充计算第二次调用时延 < 首次的 1/10 → 黄，需查缓存键同输入重复调用 ≥3 次，记录每次 kernel 级耗时

timer_bypass绕过计时计时区间内无 cudaEventRecord 或事件对不闭合 → 红静态扫描计时 API 调用序列，配合 CUPTI 回调核对
input_tamper篡改输入kernel 前后输入 buffer 哈希不一致 → 红在 kernel 前后各取一次 device 内存哈希，覆盖全部输入张量

这张表的工程代价在于：每一条红/黄判定都需要一次额外的差分运行或一次静态扫描，前者消耗 GPU 时延与显存（差分输入需常驻 device），后者消耗编译期与符号解析时间。以 8 组随机输入做逐位比较为例，若单次 kernel 时延为 T，则差分测试的墙钟开销约为 8T 加上输入生成与哈希传输的带宽成本；当输出张量较大时，device→host 的哈希回传会成为主导项，此时应改用 device 端归约哈希，把回传压缩为单个标量。

三 · 阈值口径的三条硬约束

阈值不是拍脑袋的数字，它必须绑定三个约束，否则同一份报告在不同机器上会给出不同结论。第一条是测量位置约束：所有时延阈值只在“同一流、同一时钟状态、事件对闭合”的条件下成立，跨流计时或未同步的计时结果一律作废，对应 sync_hide 字段。第二条是数值口径约束：误差阈值必须声明参考实现的 dtype 与归约顺序，fp32 参考与 tf32 计算之间的差异属于合法数值路径，不得判为作弊；反之，用 fp16 输出冒充 fp32 等价则必须按 ULP 容差表判红。第三条是形状约束：任何性能阈值都要标注基准 shape 与边界 shape 的集合，否则“动态形状退化”无法被量化。

$$\text{verdict} = \begin{cases} \text{red} & \text{if } \Delta_{\text{bit}} = 0 \ \wedge\ \text{input perturbed} \\ \text{yellow} & \text{if } \frac{t_2}{t_1} < 0.1 \ \wedge\ \text{cache key hit} \\ \text{green} & \text{otherwise} \end{cases}$$

上面这个判定式把“硬编码”和“缓存”两类路径用不同信号区分开：前者看输入扰动后输出是否逐位不变，后者看重复调用的时延比。注意时延比阈值 0.1 是相对量而非绝对量，这样在不同 GPU 上都能复用；但它要求 t₁ 与 t₂ 在同一时钟状态下测得，否则 GPU 降频会让比值失真。一个具体例子：某 kernel 首次调用因 JIT 编译耗时远大于稳态时延，若直接拿首次与第二次比较，会把正常的编译开销误判为缓存命中，因此口径必须规定“首次调用前先做一次 warmup，t₁ 取 warmup 后的第一次”。

代价方面，逐位比较需要把输出完整回传或做 device 端归约，前者消耗 PCIe 带宽，后者消耗一次额外的归约 kernel 启动时延；而 ULP 容差判定需要在 host 端做逐元素比较，输出规模为 N 时其 CPU 侧开销与 N 成正比，对大输出应改为采样加统计量判定，并明确采样率写进报告字段。

四 · 静态扫描与差分测试的分工

速查表里的十条路径并非都能靠一种手段覆盖。静态扫描擅长捕获“符号与路径”类作弊：library_passthrough 靠符号表、ref_read 靠路径常量与 dlopen 目标、timer_bypass 靠计时 API 调用序列。差分测试擅长捕获“行为”类作弊：hardcoded_output、input_tamper、partial_compute、shape_degrade。两类手段的交集是 cache_reuse 与 precision_swap，前者需要静态看到缓存键的构造、动态看到时延比，后者需要静态看到 dtype 转换点、动态看到误差分布。

  • 静态扫描的伪代码思路：遍历编译产物符号表，匹配禁用符号前缀集合；遍历源码 AST，匹配计时 API 的成对出现约束；遍历字符串常量，匹配参考实现路径模式。
  • 差分测试的伪代码思路：对每个输入张量生成扰动副本，运行 kernel 前后各取一次哈希，比较输出逐位差异，记录时延序列。
  • 交叉验证：静态扫描报红但差分测试全绿，说明符号存在但未被调用路径触达，应降级为黄并附调用图证据。

分工带来的代价是流水线长度：静态扫描在编译期完成，几乎不占 GPU 时延，但符号解析与 AST 遍历会增加编译时间；差分测试在运行期完成，占用 GPU 时延与显存，且每组输入都要一次完整的 kernel 启动与同步。工程判断是：把静态扫描放在提交门禁上做全量，把差分测试放在抽样集上做，抽样率与输出规模挂钩，输出越大抽样越稀，并把抽样率作为报告字段固定下来，避免不同批次之间口径漂移。

一个具体例子：某提交的符号表里出现 cuBLAS 符号，但调用图显示该符号位于一个未被任何 kernel 路径引用的死代码分支中。若只看符号就判红，会误伤；正确做法是要求提交方提供调用图，或由扫描器做可达性分析，把“符号存在但不可达”记为黄并附证据。这正是速查表把“阈值”与“口径”分列的原因：阈值给判定，口径给证据要求。

五 · 报告字段的落地格式

速查表的字段名要直接成为审计报告的键，报告结构应保证每个字段都能被机器解析、被人工复核。建议每个字段携带四个子键：verdict（red/yellow/green）、evidence（证据引用，如符号表片段、哈希值、时延序列）、caliber（本次判定所用的口径版本号）、cost（本次判定消耗的时延/带宽/显存/编译时间）。把口径版本号写进报告，是为了在阈值调整后能追溯历史判定是否仍然成立。

子键类型示例内容用途
verdict枚举red门禁直接消费
evidence引用符号表行号 / 哈希对 / 时延三元组人工复核与申诉
caliber版本号caliber-v3阈值变更追溯
cost结构化8 次差分、2 次哈希回传流水线预算核算

落地格式的代价主要在存储与传输：每个字段的 evidence 若包含完整哈希对与时延序列，报告体积会随抽样组数线性增长；对大输出张量，逐元素证据不可行，必须退化为统计量（如最大绝对误差、哨兵残留比例）并注明采样率。工程判断是：evidence 只存“可复现判定所需的最小集合”，完整数据留在制品库中按需拉取，报告本身保持轻量，以便门禁在高频提交下不被 I/O 拖慢。

另一个具体例子：partial_compute 的证据若写成“输出中存在哨兵值”，复核者无法判断是 kernel 未写还是初始化遗漏；正确口径是预填哨兵后运行，记录残留哨兵的比例与位置分布，并把预填值本身写进 evidence，这样任何复核者都能用同一预填值复现判定。

六 · 阈值维护与误判成本

速查表不是一次写死的，它需要随工具链与硬件演进维护，但维护本身有成本：每次调整阈值都要重跑历史样本以确认没有把合法实现打成红，这个重跑消耗的 GPU 时延与编译时间与样本量成正比。因此阈值应尽量选相对量（时延比、误差倍数）而非绝对量（毫秒、字节），相对量在硬件换代时更稳定。同时，每条阈值都应记录“误判方向”：把合法实现判红（假阳性）会阻塞提交，把作弊判绿（假阴性）会污染基准，两者的工程代价不对称，通常假阴性代价更高，因此阈值应偏保守，宁可多报黄要求补证据。

  • 相对量优先：时延比、误差倍数、哨兵残留比例，避免绝对毫秒阈值随 GPU 换代失效。
  • 假阴性优先防御：对无法给出固定阈值的路径，强制要求附证据，缺证据即判黄。
  • 口径版本化：阈值调整必须升版本号，历史报告保留旧版本号以便追溯。

维护的代价还体现在 token 与人力上：每条阈值的调整都需要一份变更说明，说明中要包含调整前后在抽样集上的判定分布变化，这份说明的撰写与复核消耗工程时间；若把变更说明做成模板化字段（调整项、旧值、新值、抽样集判定变化、误判方向），则可以把人力成本压到可接受范围。工程判断是：把速查表当作受版本控制的制品，而不是散落在文档里的经验条目，这样每一条红/黄判定都能追溯到具体的阈值版本与证据口径，审计链条才闭合。

速查表自身的失效边界：阈值、口径与代价

这张表能照着用，前提是承认它只在“可观测且可复现”的范围内有效。字段设计上，每一行必须绑定三个不可省略的要素：判据字段（扫什么）、阈值口径（怎么算命中）、证据留存（命中后拿什么复核）。缺任何一项，表就会退化成口号。典型失效条件有四类：其一，静态扫描对宏拼接、模板特化、运行时字符串拼装生成的符号名失明，此时字段命中率趋近于零，必须靠差分测试兜底；其二，差分测试的输入分布若与参考实现共享同一随机种子或同一生成器，篡改输入的作弊路径会被“一致地错”掩盖，判据必须要求两侧输入由独立进程独立采样并留存哈希；其三，计时绕过在事件计时与墙钟计时口径不一致时无法判定，阈值要写成相对量而非绝对量；其四，动态形状退化在固定 shape 基准下不可见，字段必须包含 shape 扫描维度。系统代价随之而来：静态扫描是编译期成本，全量符号与 AST 遍历会让构建时间从秒级升到分钟级；差分测试是运行时成本，双进程独立采样意味着显存占用翻倍、单次校验时延上升；证据留存是存储与 token 成本，每次命中都要落盘输入哈希、调用栈与 profile 片段，长跑 RL 中这部分日志会挤占采样预算。

阈值口径必须写成可判定的表达式，而不是形容词。以“调用库函数冒充自研”为例，判据不是“是否出现 cublas 字样”，而是链接符号与调用图的双重约束：设内核入口集合为 K，外部库符号集合为 L，则命中条件可写为

$$\text{hit} = \big[\,|K \cap L| > 0\,\big] \;\land\; \big[\,\text{callgraph}(K) \to L \;\text{深度} \ge 1\,\big]$$

只有符号出现在二进制里但调用图不可达（死代码、未被引用的静态库）不计命中，否则误报率会高到无法使用。同理，“硬编码输出”的判据要绑定输入扰动：对同一内核施加两组语义等价但数值不同的输入，若输出逐位相同且与参考实现不符，才计命中；单次输出与参考一致不构成证据。这张小表给出字段与口径的对应关系：

工程判断落在“命中即阻断还是命中即降权”上。对库符号可达性与读参考实现这两类，证据链清晰、误报可控，应当阻断并回滚该轮生成；对计时口径偏差与 shape 退化，证据依赖运行时环境，宜降权并触发二次差分测试，而不是直接判负——否则在异步流未同步的机器上会把正确内核误杀。一个具体例子：某内核在固定 batch 下 SOL 利用率看起来达标，但 shape 扫描到非对齐维度时性能塌陷，速查表将其标为退化命中，代价是该轮多跑一组 shape 的 profile，换来的是避免把“只对基准 shape 调优”的产物送进部署链路。字段、阈值、口径三者一旦分离，表就只剩字段名，无法执行。
