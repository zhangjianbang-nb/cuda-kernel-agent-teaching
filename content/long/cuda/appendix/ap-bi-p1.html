一 · 条目是什么：一次 kernel 生成实验的可追溯单元

《BI 与可观测性检查》不是一张“看板好不好看”的审美清单，它的检查对象是条目：一次 kernel 生成实验在实验追踪系统中留下的、可被独立检索与复现的最小记录单元。一个条目必须同时绑定四类信息才成立：任务标识（来自 KernelBench 系基准的题号与输入形状）、生成产物（CUDA C++ / Triton / CuTe / PTX 源码及其 commit）、运行环境快照（驱动版本、CUDA 版本、库版本、GPU 型号）、以及结果证据（正确性判定、时延/带宽测量、NCU/SASS profile 摘要）。缺任何一类，条目就退化为“一段聊天记录”，无法进入回归与 RL 奖励计算。

条目的边界由“可重放”定义，而不是由“跑过”定义。工程上常用的判定是：给定条目中记录的 commit 与环境快照，在一台同型号 GPU 上重新执行，能否得到同一正确性结论、以及落在容差内的性能读数。这个判定可以写成一个布尔函数：

$$\text{Valid}(e) = \big[\text{commit}(e) \neq \bot\big] \wedge \big[\text{env}(e) \neq \bot\big] \wedge \big[\text{oracle}(e) = \text{pass}\big] \wedge \big[\text{replay}(e) \in \text{tol}\big]$$

代价在于，环境快照的完整度直接换算成存储与检索成本：每个条目若附带完整 NCU 报告与 SASS dump，单条体积可达数十 MB 量级，十万级条目就是 TB 级归档；若只存指标摘要，重放时就必须重新采集，带来分钟级的验证时延。因此条目设计的第一处工程判断是证据分层：摘要常驻、原始 profile 冷存、按需回捞。

具体例子：同一道 KernelBench 题被 agent 用 Triton 生成两版，两版源码仅差一个 BLOCK_SIZE 常量。若条目只记录最终时延而不记录 commit 与常量取值，回归告警触发时无法判断是哪一版退化；若记录完整，则可以直接定位到常量变更这一行，并把该条目作为失败样本归档进入下一轮 RL 的负例池。

二 · 分类维度：按证据类型、按生命周期、按可信等级

条目分类不能只按“成功/失败”二分，那会丢掉最有价值的中间态。工程上可用的分类至少有三个正交维度。

维度一：证据类型。按条目携带的证据种类划分——纯正确性条目（只含 oracle 判定）、性能条目（含时延/带宽与 roofline 位置）、profile 条目（含 NCU 指标与 SASS 反汇编片段）、端到端条目（含生产链路收益）。这一维度决定了条目能被哪些下游消费：RL 可验证奖励只吃正确性加性能，roofline/SOL 分析只吃 profile 条目，生产端到端收益评估只吃端到端条目。跨维度复用会引入口径污染，例如把纯正确性条目的时延当作性能证据，会把测量噪声当成优化信号。

维度二：生命周期状态。条目在回归流水线中的位置：候选（刚生成、未验证）、已验证（正确性通过且环境快照完整）、已归档（失败样本，带失败模式标签）、已基线化（被选为回归对照）。状态迁移必须由检查器自动写入，不允许人工改标，否则回归告警的基线会被悄悄挪动。

维度三：可信等级。按证据强度分级：L0 仅有 agent 自述；L1 有本地正确性 oracle 通过；L2 有固定环境快照下的可重放验证；L3 有形式验证或独立实现交叉校验。等级不是标签装饰，它决定条目能否进入奖励计算——把 L0 条目混入奖励池，等价于把未验证的自我声明当成监督信号。

维度取值决定的下游行为主要代价
证据类型正确性 / 性能 / profile / 端到端可被哪些分析器消费跨类型复用导致口径污染
生命周期候选 / 已验证 / 已归档 / 已基线化是否进入回归对照集人工改标会漂移基线
可信等级L0–L3是否进入 RL 奖励池高等级验证的时延与算力开销

具体例子：一条 L2 性能条目在回归中时延上升，但它的 profile 证据缺失，无法判断是带宽打满还是 occupancy 下降。此时正确动作是把条目降级为“性能条目（无 profile）”，触发补采而非直接告警——补采一次 NCU 采集的代价是数十秒到分钟级，远低于误告警导致的一次错误回滚。

三 · 与相邻概念的区别：条目不是日志、不是指标、不是基准题

条目最容易与三类相邻概念混淆，而混淆直接导致检查清单失效。

与日志的区别。日志是时间序列上的事件流，天然不可寻址；条目是带主键的记录，可按 commit、题号、环境哈希检索。日志回答“发生了什么”，条目回答“哪一次实验、在什么环境下、得到了什么证据”。把日志当条目用，重放时只能靠时间戳猜环境，环境快照实际缺失。

与指标的区别。指标是看板上的聚合量（吞吐、命中率、告警数），条目是聚合量的下钻单元。看板告警说“某题时延中位数上升”，条目负责回答“是哪几个 commit、哪几个环境组合导致的”。指标口径与统计规范解决的是聚合怎么算，条目解决的是聚合背后能不能落到具体实验——两者是不同层，不能互相替代。

与基准题的区别。KernelBench 系基准的题是任务定义，条目是任务的一次执行。一道题可以对应成百上千条目；题号稳定，条目主键随 commit 与环境变化。把题号当条目主键，会让同一题的多版生成互相覆盖，回归对照集失去意义。

还有一层区别值得单列：条目与失败样本不是包含关系而是标记关系。失败样本是条目的一个子集加失败模式标签，标签体系由典型失败模式库维护；条目本身不因失败而消失，它保留完整证据供事后归因。删除失败条目是最常见的可观测性破坏行为，因为它同时删掉了负例池与回归基线。

具体例子：某次回归告警显示 Triton 版本 kernel 的时延整体上移。若系统只有指标没有条目，排查只能靠重跑全部实验；若有条目，可直接按环境快照中的库版本字段过滤，把范围缩到一次库升级前后的两组条目，比对它们的 NCU 摘要即可定位是 occupancy 还是访存模式变化。这里付出的代价是条目存储的索引开销，换来的是排查时延从小时级降到分钟级。

四 · 分类的判定机制：环境哈希与证据指纹

分类要可自动执行，就必须有确定性的判定机制。两个核心构件是环境哈希与证据指纹。

环境哈希把驱动版本、CUDA 版本、库版本、GPU 型号与关键编译选项拼成一个规范化字符串再取哈希，作为条目的环境主键。规范化必须固定字段顺序、统一版本号格式、剔除无关字段（如主机名、时间戳），否则同一环境会散成多个哈希，条目无法按环境聚合。伪代码思路如下：

$$\text{envHash} = H\big(\text{sort}(\text{driver}, \text{cuda}, \text{libs}, \text{gpu}, \text{flags})\big)$$

证据指纹则对条目携带的证据做内容哈希：正确性 oracle 的输入输出摘要、性能测量的统计量、profile 的指标集合。指纹的作用是检测“同一条目被悄悄改写”——若指纹变化而 commit 未变，说明证据被替换，条目应降级重验。

代价分析：环境哈希的计算与比对是常数级开销，可忽略；真正的成本在环境快照的采集与固化。容器化环境可以把快照固化成镜像层，代价是镜像体积与拉取时延；非容器环境只能记录版本字符串，重放时存在版本漂移风险，此时条目可信等级上限被压到 L1。证据指纹的代价是每次证据更新都要重算哈希并写回，带来写放大；若条目量大，指纹存储本身会成为索引负担，需要按生命周期状态分层保留。

具体例子：agent 在同一 commit 上先后两次运行，第一次因 GPU 被其他进程占用导致时延偏高。若条目记录了环境哈希与证据指纹，第二次运行的指纹与第一次不同但 commit 相同，检查器可判定为“同 commit 多证据”，保留两条并以较优环境的那条作为性能证据，另一条标记为受干扰样本归档——这比直接取平均更诚实，因为平均会把干扰噪声固化进基线。

五 · 分类维度之间的耦合：为什么不能只做单维标签

三个维度并不独立，耦合点在于“可信等级决定证据类型的可用性”。一条 L0 条目即使携带了性能读数，也不能作为性能证据使用，因为读数没有可重放环境背书；一条 L3 条目即使只有正确性证据，也可以在形式验证层面支撑奖励计算。若系统只做单维标签（例如只标“通过/失败”），就会出现高可信条目与低可信条目混在同一聚合里，看板指标被稀释，回归告警的灵敏度下降。

工程上的处理方式是把分类写成判定表而非自由标签：证据类型由条目实际携带的字段集合推导，生命周期由检查器状态机写入，可信等级由环境快照完整度与验证方式共同决定。判定表的每一行对应一种下游消费许可，任何不在表内的组合一律拒绝进入奖励池与回归基线。

代价体现在检查器本身的复杂度与运行时间：判定表越细，单条目检查的字段读取越多，批量检查的时延线性上升；但相比误把低可信条目当基线导致的错误回滚，这个开销是值得的。另一个代价是存储：高可信等级条目需要保留完整环境快照与原始 profile，冷热分层策略必须按等级而非按时间划分。

具体例子：一条被标为“已验证”的条目，其环境快照只记录了 CUDA 版本而缺驱动版本。判定表会把它从 L2 降到 L1，并禁止其进入回归对照集；若系统只做单维“已验证”标签，这条目会被误选为基线，后续所有对比都建立在漂移的环境上。这里没有编造任何数字，判断依据是快照字段的缺失本身。

六 · 条目定义落到检查清单上的形态

把上述定义翻译成检查项，每条检查都对应一个可判定的字段或状态迁移，而不是一句“是否齐备”的模糊问句。实验追踪检查对应条目主键与 commit 绑定；版本固定检查对应环境哈希字段完整且规范化；指标看板检查对应条目证据类型与看板聚合口径的映射关系；失败样本归档检查对应生命周期状态迁移与失败模式标签；回归告警检查对应已基线化条目的证据指纹稳定性。

这五项检查的共同前提是条目本身成立。若条目缺环境快照，版本固定检查无从谈起；若条目缺 commit，实验追踪检查退化为文件存在性检查；若条目缺证据指纹，回归告警只能依赖时延数值的抖动，无法区分真实退化与证据被替换。因此检查清单的执行顺序应当是先验条目完整性，再验各专项——顺序颠倒会让专项检查在残缺条目上产出虚假的“通过”。

具体例子：一次发布前的可观测性审计中，检查器发现某批条目的环境哈希字段为空。按顺序执行，这批条目先被判为不完整并阻断后续专项检查；若跳过完整性直接跑版本固定检查，检查器会因为“版本字段存在”而放行，实际这些字段从未参与哈希，无法保证同环境聚合。阻断的代价是发布延迟，收益是避免把不可追溯的实验写进基线。

条目定义的最终落点是主键设计：(题号, commit, envHash, 证据指纹) 四元组作为唯一键，任何一项变化都产生新条目而非覆盖旧条目。这个设计让条目天然只增不改，回归对照集可以按时间切片重建，失败样本归档不会因重跑而丢失。代价是存储单调增长，必须配合冷热分层与按等级保留策略；收益是每一次 kernel 生成都可追溯到具体 commit 与环境快照，这正是本检查条目存在的理由。

可追溯性断链的三种失效面与代价

把“可追溯”当成布尔量是这一节要拆掉的第一层误解。条目真正要求的是四元组 (commit, env_snapshot, sample_id, metric_series) 在时间轴上可反向寻址：任一失败样本能定位到具体 commit 与环境快照，任一指标劣化能定位到引入它的那次生成。断链发生在三个面上——环境漂移（驱动/CUDA/库版本未固定，同一 commit 在不同机器上复现出不同数值）、样本蒸发（失败样本只留在日志里未归档，回归告警触发时已无原始输入可重跑）、指标脱钩（看板曲线与 commit 无关联键，只能靠人工回忆对齐）。三者的共同代价不是“不方便”，而是让下游的正确性 oracle 失去判据：无法区分“kernel 写错了”与“环境变了”。

一个可操作的判据是追溯覆盖率，定义为可完整寻址的样本占全部生成样本的比例：

$$C_{\text{trace}} = \frac{|\{s : \text{commit}(s) \wedge \text{env}(s) \wedge \text{metric}(s) \neq \varnothing\}|}{|S|}$$

该比值低于阈值时，回归告警的信噪比会塌陷——告警数量不降反升，因为每次环境变动都被误判为代码回归。工程上更贵的是重跑成本：缺失环境快照意味着必须重建容器镜像并重放整条生成链，单次重跑的时间开销远超一次 NCU profile 采集；而缺失失败样本归档则直接让“失败样本进训练集”这条链路断掉，等于把已经付出的生成 token 全部浪费。

失效面典型症状系统代价
环境漂移同 commit 数值不一致镜像重建 + 全链重放
样本蒸发告警时无输入可重跑生成 token 与验证算力沉没
指标脱钩曲线无法归因到 commit人工对齐，告警信噪比下降

边界条件很明确：当生成吞吐远高于归档吞吐时，C_trace 必然被采样率压下来，此时正确做法是分层归档——只对触发过告警或进入 RL 训练集的样本做全量快照，其余仅保留 commit 与指标键。这与“全量留痕”是两种不同的工程判断，前者牺牲部分可追溯性换取归档带宽，后者则可能让存储与写入时延成为整条流水线的瓶颈。
