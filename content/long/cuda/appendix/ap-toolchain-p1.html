一 · 工具链条目的准确定义：四个可被独立替换的层

“工具链选型”在 kernel agent 语境里常被误当成“选个语言”。准确的定义是：一条从 agent 产出的源文本到 GPU 可执行机器码的转换链，由四个可独立替换的层构成——源语言层（CUDA C++、Triton DSL、CuTe/CUTLASS 模板库）、编译器层（nvcc、triton 编译器、NVRTC、ptxas）、中间表示层（PTX 虚拟 ISA、Triton IR/LLVM IR、CuTe 的 layout 代数）、运行时装载层（cubin 静态链接、cuModuleLoad 动态加载、torch 扩展 JIT）。选型条目比较的不是“语言好坏”，而是这四层组合后暴露给 agent 的接口面：agent 能写什么、编译器能校验什么、profile 能看到什么、部署能替换什么。

把条目定义为四层组合，直接决定了对照表的行该怎么切。若只按语言切，CUDA C++ 与 NVRTC 会被混为一行，但它们共享源语言却分属不同编译器层与装载层——NVRTC 把编译推迟到运行时，换来的是编译时延从构建期转移到推理期，代价是失去 nvcc 的离线优化与链接期检查。因此本对照表的每一行是一个层组合，而非一个名字。

一个具体机制上的差别：nvcc 走的是“预处理→cicc→PTX→ptxas→cubin→fatbin 链接”的完整流水，编译单元边界由 .cu 文件决定；NVRTC 接收的是内存中的源码字符串加编译选项，直接产出 PTX 或 cubin，没有文件系统参与。这个差别对 agent 的意义是：NVRTC 允许 agent 在单次会话内做“生成—编译—报错—改写”的紧循环，而 nvcc 路径要求 agent 先把源码落盘再调用外部构建系统，循环的每次迭代都带一次进程启动与文件 I/O 开销。

$$\text{迭代成本}_{\text{agent}} = t_{\text{gen}} + t_{\text{compile}} + t_{\text{load}} + t_{\text{verify}}$$

四项里只有 $t_{\text{compile}}$ 与 $t_{\text{load}}$ 受工具链选型直接支配。Triton 的编译时延随 kernel 规模与 autotune 配置数增长，autotune 把 $t_{\text{compile}}$ 乘以候选配置数；NVRTC 把 $t_{\text{load}}$ 变成 cuModuleLoad 的一次性开销；CuTe 的模板实例化把成本压进 $t_{\text{compile}}$ 的 C++ 前端阶段。选型表若不标注这四项各自被哪一层放大，就无法解释为什么同一个 kernel 在不同工具链下的 agent 多轮收敛轮数不同。

二 · 分类维度：表达力、编译时延、可移植性、调试可见性、性能上限

五个维度不是并列的评分项，而是有依赖方向的：表达力决定 agent 能描述多大的搜索空间；性能上限是该空间内最优解的天花板；编译时延决定 agent 在固定 token/时延预算内能试探多少次；调试可见性决定失败时 agent 能否从反馈中定位原因；可移植性决定同一份产物能否跨架构复用而不重新进入生成循环。前两者是“能不能”，后三者是“值不值”。

表达力的准确口径是可表达的程序集合，而非语法糖数量。CUDA C++ 可表达任意线程级控制流、共享内存手工布局、warp 级原语与内联 PTX，其集合接近硬件可编程面；Triton 以 tile 为粒度，把 block 内线程调度与共享内存分配交给编译器，可表达集合被限制在“规则 tile 运算 + 少量归约/扫描”内；CuTe 用 layout 代数表达任意 tiling 与 swizzle，但要求程序员以类型系统的方式陈述，表达力高而书写成本高；PTX 内联是唯一能直接指定指令选择与寄存器约束的层，表达力最高但完全丧失跨架构可移植性。

代价必须落在具体量上。以调试可见性为例：nvcc 路径下 agent 可从 cuobjdump/nvdisasm 拿到 SASS 并与源码行对应，一次失败定位的反馈 token 量是“若干行 SASS + 行号映射”；Triton 路径下 agent 看到的是 TTIR/TTGIR 层，SASS 映射弱，定位一个 bank conflict 需要额外跑 NCU 拿 shared 访存指标，反馈链路多一跳，单轮时延增加一次 profile 采集。可移植性的代价则是重编译：同一份 CUDA C++ 源码换架构要重跑 nvcc，$t_{\text{compile}}$ 重新计入 agent 循环；PTX 内联换架构则直接失效，必须回到生成阶段。

三 · 与相邻概念的区别：工具链 ≠ 基准 ≠ 指标 ≠ 验证器

工具链条目最容易被相邻条目吞掉的是“性能上限”这一维。基准条目回答“这个 kernel 在给定问题上算得快不快”，工具链条目回答“这条链在结构上允不允许更快”。前者是测量，后者是可达性论证。一个 Triton kernel 在 KernelBench 上得分低，可能是 agent 没写好，也可能是 tile 抽象根本表达不了该访存模式——前者归失败模式库，后者归本对照表。混为一谈会让 agent 在不可表达的搜索空间里空转。

与指标口径条目的区别在于归因粒度。指标条目定义 SOL、roofline 距离、带宽利用率怎么算；工具链条目解释为什么某条链在这些指标上有系统性偏差。例如 Triton 的 autotune 会在测量阶段引入配置搜索，若指标口径不剥离搜索开销，就会把编译时延记成 kernel 时延；NVRTC 的运行期编译同理，首次调用含 $t_{\text{compile}}$，稳态不含。工具链选型必须声明“哪一段计入端到端”，否则跨链比较不成立。

与正确性验证器清单的区别是责任边界。验证器判定数值是否落在容差内；工具链决定这个判定能在哪一层执行。PTX 内联改写了指令选择，验证器只能在输出张量上做黑盒比对，无法证明寄存器约束没被违反；CuTe 的 layout 代数若在类型层写错，错误可能在编译期就被类型系统拦下，也可能静默产生错误索引直到数值比对才暴露。因此对照表要标注每条链的错误可拦截层：编译期类型检查、ptxas 校验、运行期数值 oracle 三层各自能拦住什么。

一个具体例子：agent 生成一个 warp 级 reduce 的 kernel。CUDA C++ 路径下，__shfl_down_sync 的 mask 写错属于运行期数值错误，验证器可拦；Triton 路径下没有 warp 原语暴露，agent 只能写 tl.sum，编译器生成的归约树不可见，错误只可能来自 tile 形状不匹配，在 IR 下降期报错；PTX 内联路径下 shfl.sync 的成员 mask 若与活跃线程不符，ptxas 不校验语义，验证器成为唯一防线，且失败表现为间歇性数值偏差而非确定性报错——这类失败对 agent 的反馈信号最不友好，因为不可复现。

四 · 选型决策表的构造：以 agent 循环为坐标系

决策表不能按“推荐场景”罗列，那会退化成经验清单。可构造的口径是：把 agent 的一次任务分解为探索轮数 $N$、每轮编译成本 $c$、单次验证成本 $v$、部署后稳态收益 $g$，则总成本与收益的比较给出选型边界。探索阶段总成本近似 $N(c+v)$，部署阶段收益是 $g$ 的累积。当 $N$ 大而 $g$ 小（一次性 kernel、研究性任务），低 $c$ 的链占优；当 $g$ 大而 $N$ 有限（生产端到端收益显著），高表达力、高上限的链占优，即使 $c$ 更高。

$$\text{选型判据}:\quad N\,(c+v) \;<\; G \cdot g \;\;\Rightarrow\;\;\text{选高上限链}$$

其中 $G$ 是部署期调用量或收益折算周期。这个不等式解释了为什么 Triton 在 agent 快速迭代场景流行：$c$ 低、$v$ 中等，$N$ 可以开得很大；而 CuTe 与 PTX 内联在 $N$ 受限、$g$ 明确的场景才划算，因为它们的 $c$ 高（模板实例化或手写指令），必须用部署收益摊薄。

决策表还需一列标注反馈信号质量，它不进公式但决定 $N$ 的有效性。编译报错可读性、SASS 可获取性、NCU 指标可关联性共同决定 agent 每轮能否从失败中学到东西。若反馈信号只给出“数值不对”，$N$ 轮里有效探索的比例下降，等效于把 $N$ 打折。PTX 内联的反馈信号最弱（语义错误静默），Triton 的 IR 报错最结构化，nvcc 的 SASS 反馈最贴近硬件但需要 agent 具备读汇编的能力——这一项是 agent 能力与工具链的匹配问题，不是工具链的绝对优劣。

具体例子：一个 attention 变体 kernel，若目标是单次论文实验，$N$ 可能开到几十轮，Triton 的低 $c$ 让每轮迭代廉价，即使最终性能上限低于手写；若目标是推理服务端到端吞吐，$g$ 按调用量累积，CuTe 的 layout 代数能把 swizzle 与 tiling 精确表达，$c$ 的高模板实例化成本被部署收益覆盖。两条链的选择不是“哪个更好”，而是不等式两侧的量级比较。

五 · 条目边界的工程判断：何时必须跨链

单条链覆盖不了全部需求时，工程上的做法是分层混用而非整体切换。典型组合是 Triton 做探索期原型、CuTe 做性能关键路径、PTX 内联做单点指令替换。混用的代价出现在接口处：Triton 产物是编译后的 cubin，无法与 CuTe 的 C++ 模板在同一编译单元内联；PTX 内联只能在 CUDA C++ 源内生效，无法注入 Triton 生成的 IR。因此跨链混用要求明确边界契约——数据布局、同步语义、错误传播在哪一层对齐。

边界契约的一个具体机制是布局约定。Triton 的 tile 输出布局由编译器决定，若下游 CuTe kernel 期望特定 swizzle 的共享内存布局，两者必须在全局内存层面约定 stride 与对齐，否则跨链拼接处产生额外转置或 bank conflict，把单链的性能上限优势吃掉。这类代价不出现在任何单链的 profile 里，只在端到端测量中暴露，因此工具链条目必须声明“混用时的额外带宽/时延开销由谁承担”。

另一个判断是可移植性预算。若产物需要跨多代架构部署，PTX 内联的架构绑定使其不可作为长期路径，只能作为当前代的单点优化；CUDA C++ 与 Triton 的源码级可移植性允许一次生成多处编译，代价是每处重新计入 $t_{\text{compile}}$。CuTe 的架构特化模板在跨代时可能需要重写 layout，其可移植性介于两者之间。选型表应把“跨代重写成本”单列，而不是笼统写“可移植”。

最后一个工程判断是验证责任的下沉。表达力越高的链，编译器能拦的错误越少，验证器承担的越多。PTX 内联与 CuTe 手工 layout 要求验证器覆盖索引正确性、同步正确性与数值容差三层；Triton 的编译器承担了线程调度与共享内存分配的正确性，验证器可聚焦数值。这个责任分配直接决定 agent 循环里 $v$ 的大小，也决定失败模式库中哪些模式属于该链的固有风险。选型不是选最快的链，是选验证成本与部署收益匹配的链。

选型边界的判定：表达力、编译时延与可移植性的三角约束

把四种工具链放进同一个坐标系，真正的分界线不是“抽象层次高低”，而是编译期确定性与运行时确定性的归属。nvcc 把 tile 尺寸、线程映射、寄存器分配全部交给编译器在构建期固化；Triton 把 block 形状交给 JIT，在首次调用时按实际 shape 特化；CuTe/CUTLASS 把布局代数（layout algebra）在模板层展开，编译期即完成 swizzle 与 tiled copy 的实例化；PTX 内联与 NVRTC 则把决定权推到运行期——前者在 C++ 源码里嵌入汇编级指令，后者把字符串编译成 cubin。这条分界线决定了一个 kernel 在 shape 变化时是“重新编译”还是“重新调度”。失效条件很明确：当 workload 的 shape 分布高度离散（动态 batch、变长序列），nvcc 与 CuTe 的静态实例化会退化为模板爆炸或 kernel 数量膨胀；当 shape 稳定但需要极致指令级调度，Triton 的自动调度器无法表达手工的 register reuse 与 async pipeline 深度，性能上限被锁死。

用编译代价换性能上限的权衡可以写成一个粗略的判据：设 $T_{\text{build}}$ 为构建期编译时延，$T_{\text{jit}}$ 为首次调用 JIT 时延，$N$ 为运行期不同 shape 的配置数，则总时延开销近似为 $T_{\text{total}} \approx T_{\text{build}} + N \cdot T_{\text{jit}} + T_{\text{exec}}$。nvcc 与 CuTe 的 $N$ 被压到 1（或少量特化），代价是 $T_{\text{build}}$ 随模板实例化线性上升；Triton 与 NVRTC 的 $T_{\text{build}}$ 接近零，但每个新 shape 都付出一次 $T_{\text{jit}}$，在服务端首请求尾延迟上直接可见。调试可见性同样被这条线切开：nvcc 与 PTX 内联可以用 cuda-gdb 单步到 SASS 级，CuTe 的布局错误在编译期以模板报错暴露（可读性差但定位早），Triton 的 IR 层错误往往要落到生成的 PTX 才能定位，NVRTC 的运行时编译失败则只剩一个错误码字符串。

工具链决定权归属失效条件主要系统代价
CUDA C++/nvcc构建期固化shape 离散导致 kernel 膨胀构建时延、二进制体积
Triton首次调用特化需手工指令调度时上限受限JIT 时延、IR 调试成本
CuTe/CUTLASS模板层展开布局组合爆炸、编译报错晦涩编译时延、模板实例化显存
PTX 内联 / NVRTC运行期决定无编译期校验，错误后置JIT 时延、调试可见性缺失

一个具体例子能说明边界的锋利：同一段 GEMM，若 M/N/K 在部署中被固定为单一配置，CuTe 的 tiled copy 与 swizzle 能在编译期完全展开，寄存器压力与 shared memory bank 冲突在构建期就被消除，运行期只剩 launch；一旦 M 变成动态值，同一份 CuTe 代码要么退化为通用布局、要么为每个 M 实例化一份 kernel，前者损失性能上限，后者让编译时延与二进制体积同时膨胀。此时 Triton 的 autotune 反而更合适——它把配置搜索推到首次调用，用一次 JIT 时延换掉模板爆炸。而如果这段 GEMM 需要嵌入自定义的 `mma` 指令序列或非标准 swizzle，Triton 的调度器无法表达，只能落到 PTX 内联，代价是失去编译期正确性校验，任何寄存器约束写错都要到运行期才以 illegal memory access 或错误结果的形式暴露。选型因此不是“哪个更强”，而是判断该 workload 的 shape 方差、性能上限需求与调试预算三者中哪一个先触底。
