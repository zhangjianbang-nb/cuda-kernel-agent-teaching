一 · 阈值的来源：先分清“物理下限”与“工程余量”

工程阈值不是拍脑袋的数字，它有两个来源：一是由硬件参数与算法结构决定的物理下限，二是为吸收测量噪声、调度抖动、编译差异而留出的工程余量。深读论文时，凡是作者给出“达到 X% 峰值”“加速 Y 倍”这类结论，第一步不是记数字，而是判断这个数字相对哪条下限。以 roofline 为例，给定运算强度 I（FLOP/Byte）、峰值算力 P、峰值带宽 B，可达性能上限为：

$$P_{\text{roof}}(I)=\min(P,\; I\cdot B)$$

于是“达到峰值百分比”这一指标本身是可被操纵的：把 I 算小（少计中间张量的读写），roofline 拐点左移，同样的 kernel 显得更接近上限。因此读论文时必须追问：I 的分母里算了哪些字节？是否包含被融合掉的中间结果？这决定了阈值是物理下限还是作者自定的基线。工程余量的典型形态是“留 10%–20% 余量再判定达标”，但余量该留多少取决于测量方差，而方差必须实测——同一 kernel 连续跑多次取分布的离散度，而不是引用别人的经验值。代价在这里体现为时间：一次完整的方差标定需要重复运行数十次并采集 NCU 指标，单次 profile 的采集开销会让端到端时延膨胀数倍，因此阈值标定通常放在离线阶段，不进入在线回归。

具体例子：一个逐元素加法 kernel 的运算强度极低，roofline 上限由带宽决定；此时若作者报告“达到 80% 峰值算力”，这个数字没有意义，因为该 kernel 根本不在算力受限区。正确的读法是把它换算成“达到带宽上限的百分比”，并检查是否计入了读+写两侧字节。凡是论文只给单一百分比而不给受限类型的，视为不可复现的结论。

二 · 正确性阈值：容差、ulp 与 oracle 的强度分级

正确性阈值是 kernel agent 评测里最容易被稀释的一环。浮点比较的容差通常写成相对误差与绝对误差的组合：

$$\lvert a-b\rvert \le \mathrm{atol} + \mathrm{rtol}\cdot\lvert b\rvert$$

问题在于 atol 与 rtol 的取值直接决定了多少“错误 kernel”能通过。对 fp32 归约类算子，累加顺序改变会带来与元素数量相关的误差增长，容差若按单元素量级设定，长序列归约会系统性失败；反之若放宽容差到掩盖真实 bug，则正确性 oracle 失效。工程上更稳的做法是分级：先用比特级一致（bitwise）判定纯搬运、索引类 kernel；再用 ulp 距离判定数学函数与低精度算子；最后才用组合容差判定归约与矩阵乘。ulp 距离的定义是两浮点数在有序整数表示下的差值，它对接近零的值比相对误差更稳健。

代价体现在验证吞吐上：bitwise 判定最快，一次比较即可；ulp 判定需要把浮点映射到有序整数再求差，成本略高；组合容差需要逐元素计算并聚合最大值，且要处理 NaN/Inf 分支，单次验证的时延可达 bitwise 的数倍。若对每个候选 kernel 都跑最严格的一级，多轮采样的验证预算会被正确性检查吃掉，留给性能测量的轮次减少。具体例子：一个 softmax kernel 在分母归约上用了不同的分块顺序，输出与参考的差异集中在极小概率项上，相对误差爆表但绝对误差在 1e-7 量级；若 oracle 只做相对误差判定，该 kernel 被判错，而它实际是可接受的——这说明容差策略必须与算子数值特性绑定，而不是全局一个常数。

没有数字时怎么写清测量方法：固定随机种子生成输入，覆盖极值、零、次正规数与不同量级混合分布；对每个候选 kernel 记录最大绝对误差、最大 ulp 距离与失败元素比例三个量，而不是只报“通过/不通过”。这三个量的采集本身有成本——需要把输出张量搬回主机并做全量比较，搬运带宽与比较时延会主导小规模用例的验证时间。

三 · 性能阈值：加速比基线、测量重复数与噪声地板

“加速比”这个数字的分子是候选 kernel 时延，分母是基线时延，两者都必须声明测量协议。基线可以是框架原生实现、可以是朴素 CUDA 实现、也可以是编译器自动生成的版本，不同基线之间的差距足以让同一个 kernel 从“加速 3 倍”变成“持平”。读论文时要找的是：基线是否经过调优？是否包含 launch 开销？是否在同一 stream 上测？

测量重复数是另一个隐性阈值。单次计时受 GPU 时钟波动、L2 残留状态、其他进程干扰影响，工程上常用“重复 N 次取中位数”并报告四分位距。噪声地板的估计方法是：对同一 kernel 在完全相同的输入下重复测量，取时延分布的相对标准差；若候选与基线的差距小于该标准差的若干倍，则判定为“无显著差异”。代价是测量时间随 N 线性增长，且每次重复都要重置缓存状态以避免 L2 命中带来的系统性偏低——重置本身引入额外 kernel 与同步开销。

具体例子：一个 Triton 实现与 CUDA 实现在小规模输入上时延接近，但 Triton 的编译时间被排除在计时之外；若把首次编译的时延计入端到端，结论反转。因此性能阈值必须区分“稳态时延”与“含编译的首次时延”，前者用于 kernel 质量比较，后者用于生产部署判断。论文若只报稳态数字而不提编译开销，读者应自行补测：记录从源码到可执行 kernel 的墙钟时间，并注明是否命中编译缓存。

还有一个常被忽略的阈值是占用率与寄存器压力的耦合：当编译器为提升 ILP 而增加寄存器使用时，占用率下降可能抵消指令级收益。判定这类权衡不能只看时延，要同时采集占用率与寄存器数，并检查是否发生了本地内存溢出——溢出的代价是显存带宽被 spill 流量占用，表现为时延对输入规模异常敏感。

四 · 编译与工具链阈值：编译时间、缓存命中与版本敏感性

Kernel agent 的迭代循环里，编译时间是一个硬阈值：若单次编译超过交互预算，多轮搜索的轮数就被压缩。测量方法是记录从提交源码到拿到可加载模块的墙钟时间，并区分冷编译与缓存命中两种情况。缓存键通常包含源码哈希、编译选项与目标架构，任一变化都会导致未命中；因此“编译时间”这个数字必须绑定缓存状态才有意义。

版本敏感性是另一类阈值：同一份 Triton 源码在不同版本下可能生成不同的 PTX，性能差异可达一个量级；CUDA 工具链的架构支持矩阵也决定了某些指令能否使用。读论文时若作者未标注工具链版本与目标架构，其性能数字不可复现。工程判断是：把工具链版本作为评测元数据强制记录，任何跨版本比较都视为无效，除非在同一版本下重测基线。

代价方面，编译时间与搜索空间成正比：候选数量增加，总编译时间线性上升，且失败编译（语法错误、资源超限）也消耗时间。具体例子：一个 agent 在每轮生成多个候选并全部编译，若其中多数因寄存器超限而编译失败，有效候选率低，编译预算被浪费；改进方式是在生成阶段就做静态资源估算，把明显超限的候选过滤掉，代价是过滤规则本身可能误杀可通过编译器优化的写法。

五 · Profile 驱动优化的判定阈值：从指标到动作的映射

NCU 采集到的指标本身不是结论，需要映射为优化动作，而映射的触发条件就是阈值。典型映射包括：当内存吞吐接近峰值带宽而算力利用率低时，判定为带宽受限，动作是减少字节或提升复用；当 warp 停滞原因中长延迟指令占比高时，判定为延迟受限，动作是增加并行度或预取；当占用率低且寄存器数高时，判定为资源受限，动作是拆分 kernel 或降低寄存器压力。每个映射都需要一个判定门槛，例如“带宽利用率超过某比例才认定为带宽受限”，这个比例没有普适值，必须结合该架构的实测可达带宽（而非规格书峰值）来定。

测量方法上，NCU 的采集本身会扰动被测量对象：指标越多，重放次数越多，单次采集的时延膨胀越明显。因此阈值标定应在关闭非必要指标的条件下进行，只采集判定所需的最小指标集。代价是信息不完整可能导致误判，需要在离线阶段用全指标采集建立对照，再确定最小集。

具体例子：一个矩阵乘 kernel 的算力利用率低于预期，NCU 显示共享内存 bank 冲突计数偏高；若阈值设定为“冲突计数超过某绝对值即触发重排”，在小规模输入上会误触发，因为绝对计数随问题规模变化。正确做法是用冲突率（冲突次数/访问次数）作为判定量，它与规模无关，更适合作为阈值。这也说明阈值的单位选择比数值本身更重要：绝对计数适合容量判断，比率适合效率判断。

六 · 没有数字时：把“怎么测”写成可执行协议

论文索引里大量条目只给出定性结论，此时深读的价值在于把测量协议补全，而不是替作者编数字。一个可执行协议至少包含四件事：测量对象（哪个 kernel、哪个输入规模、哪个精度）、测量工具与采集粒度（计时方式、是否含同步、是否含编译）、重复与聚合方式（次数、取中位数还是最小值、是否报告离散度）、以及判定规则（与哪条基线比、差距多大算显著）。这四项缺一，结论就不可复现。

协议里还要写明失败处理：编译失败、运行超时、结果不一致的候选如何计入统计。若把失败候选直接丢弃，成功率被高估；若计入但按零性能处理，平均时延被扭曲。工程上常用“有效候选率”与“通过候选的性能分布”两个量分开报告，前者反映 agent 的生成质量，后者反映优化上限。代价是统计工作量增加，需要为每个候选保留完整记录而非只留最优。

具体例子：某条目声称某脚手架在多轮迭代后稳定产出可用 kernel，但未说明每轮的候选数量与失败率。深读时应补测：固定任务集，记录每轮生成数、编译成功数、正确性通过数、性能达标数四个计数，形成漏斗。漏斗的每一层收窄幅度就是该脚手架的工程阈值所在——若正确性通过率高但性能达标率低，瓶颈在优化策略而非生成能力。这个漏斗的采集成本主要是验证与计时的重复开销，属于离线标定，不应混入在线评测的时延统计。

最终落在工程判断上：阈值不是论文里的装饰数字，而是把“结论”翻译成“可复现动作”的接口。凡是给出数字的条目，追问它的分母、基线、重复数与工具链版本；凡是没给数字的条目，按上述四项补出协议再判断其贡献点是否成立。索引的可用性取决于这一层翻译是否被写下来，而不是取决于条目数量。

阈值不是常数：从论文索引里读出的“可复现边界”

索引里标注“可复现”的条目，往往隐含一组未写进正文的工程阈值：编译超时、单 kernel 迭代预算、正确性容差、profile 采样粒度。这些数字在论文中通常只出现在附录或脚注，而它们恰恰决定了复现是“跑通”还是“跑出可信结论”。以 KernelBench 系基准为例，正确性 oracle 的容差若按 $$|y_{\text{ref}}-y_{\text{test}}| \le \tau \cdot \max(1,|y_{\text{ref}}|)$$ 设定，τ 取紧会误杀合法的重排归约（浮点结合律不同），取松则放过真实的数值 bug；索引条目若只标“通过”，必须回查 τ 与输入分布，否则复现出的通过率不可比。代价是显性的：τ 收紧一档，agent 多轮 RL 中因“假失败”产生的负奖励会污染策略，token 消耗上升而有效信号下降。

编译与执行侧的经验数字同样需要测量而非引用。Triton 与 CuTe 的 autotune 空间在索引条目里常被记为“已调优”，但实际边界是编译时间与显存占用的乘积约束：候选配置数 N 与单次编译时延 t_c 决定 agent 单轮可探索的上限，$$N \le \frac{T_{\text{budget}}}{t_c + t_{\text{bench}}}$$，其中 t_bench 含 NCU 采集开销。采样粒度越细（如逐指令 SASS 计数），t_bench 越大，N 被压缩，agent 退化为贪心单点优化。索引中标注“profile 驱动”的条目，应同时记录采集模式与重复次数，否则 roofline 上的 SOL 百分比无法跨条目比较。

阈值类别失效条件系统代价
正确性容差 τ归约/原子操作重排假失败→RL 负奖励污染
autotune 候选数 N编译时延超预算探索空间坍缩为单点
profile 采样粒度采集开销淹没 kernel 时延SOL 估计偏差、不可比

因此索引的可用性判断应落在“阈值是否被显式记录并可重测”上：形式验证条目若只给“验证通过”，需追问不变量强度与超时设置；RL 训练条目若只给“收敛”，需追问每轮 kernel 编译失败率的上限。没有数字时，工程上唯一诚实的做法是把测量协议写进条目——输入形状集合、τ、N、采集模式、重复次数——让下一位读者能在自己的机器上重跑出同一组边界，而不是继承一个无法追溯的经验值。
