一 · 条目是什么：一份可被审计的评测契约

《评测协议规范》里的“条目”不是一条 benchmark 用例，也不是一份跑分记录，而是一份可被第三方复现与审计的评测契约。它把“某个 kernel 在某个任务上是否合格”这一判断，拆解为六个必须显式写死的字段：输入分布、容差标准、计时方法、硬件隔离、随机种子、结果上报格式。任何一个字段缺省，条目就退化为不可复现的传闻，而不是工程资产。判断一个条目是否成立，只需问一句：把这份条目交给一台陌生机器上的陌生工程师，他能否在不询问作者的前提下得到同一判定结论？能，则是条目；不能，则只是日志。

契约性带来一个直接的结构性要求：评测脚本与训练侧必须隔离。这里的“隔离”不是物理分机那么简单，而是指评测脚本不得读取训练侧的缓存、不得复用训练侧的随机数状态、不得依赖训练过程中残留的环境变量或编译产物。原因是 agent 在训练回路里会针对反馈信号做局部拟合，一旦评测脚本与训练脚本共享状态，反馈信号就被污染，条目测到的是“模型对旧脚本的记忆”而非 kernel 本身的性质。代价是实打实的：隔离意味着每次评测都要重新初始化上下文、重新编译、重新预热，单条目端到端时延上升，编译时间（尤其 Triton 与 CuTe 模板实例化）成为不可忽略的开销项；在批量评测时这部分开销会以 token 与 wall-clock 双重形式计入预算。

同时，条目必须留存原始日志以备审计。原始日志指未经聚合、未经重采样的逐次计时样本、逐元素误差向量摘要、编译命令行与编译器版本、驱动与固件标识。聚合后的中位数与 P90 只能作为上报格式的一部分，不能替代原始日志。审计场景下，重跑一次条目并与原始日志比对，是唯一能区分“结果漂移”与“上报错误”的手段。代价是存储与带宽：逐次样本的体量远大于聚合指标，长跑评测的日志落盘会成为 I/O 瓶颈，需要在条目里规定采样率与截断策略，而不是事后补救。

$$\text{条目} = \langle \mathcal{D}_{\text{in}},\ \tau,\ \mathcal{M}_{\text{time}},\ \mathcal{H},\ s,\ \mathcal{F}_{\text{report}} \rangle$$

这个六元组是本规范的最小完备集。缺 $\mathcal{H}$（硬件隔离）则跨机器比较失效；缺 $s$（随机种子）则输入分布不可重建；缺 $\mathcal{F}_{\text{report}}$ 则审计无从对齐。举例：一个 reduction kernel 条目若只写了“输入为随机浮点张量”，没有写分布的形状约束与种子，那么两次评测的输入不同，误差比较就退化为噪声比较，容差 $\tau$ 再严格也无意义。

二 · 分类维度一：按判定对象分——数值正确性、性能、鲁棒性

条目按“判定什么”可分为三类，三类的容差语义完全不同，混用是本规范要防的头号错误。

  • 数值正确性条目：判定对象是输出与参考实现的偏差。容差 $\tau$ 是误差界，通常写成逐元素相对误差与范数误差的组合。这类条目的核心机制是 oracle 的选择：参考实现可以是 CPU 高精度版本、可以是同语义的库调用、也可以是形式化规约。选择不同 oracle，$\tau$ 的量级不同，且必须与 oracle 的精度假设绑定写明。
  • 性能条目：判定对象是计时统计量，容差是“相对基线的加速比下界”或“相对 roofline 的 SOL 占比下界”。这类条目的容差不是误差而是阈值，且必须与计时方法 $\mathcal{M}_{\text{time}}$ 绑定——用 CUDA event 计时与用 wall-clock 计时得到的分布形状不同，阈值不可跨方法复用。
  • 鲁棒性条目：判定对象是边界条件下的行为，如非对齐尺寸、零长度输入、极端指数范围、并发流下的资源竞争。这类条目往往没有单一数值容差，而是“不得崩溃、不得产生 NaN、不得越界写”的布尔判定，配合一个宽松的数值容差作为兜底。

三类条目的代价结构不同。正确性条目的主要代价是 oracle 的计算时间与显存——高精度参考实现常比被测 kernel 慢一到两个数量级，若在 GPU 上跑参考实现还会挤占被测 kernel 的显存预算；性能条目的主要代价是计时噪声，需要足够多的重复样本来压低方差，重复次数直接乘以单次时延；鲁棒性条目的主要代价是构造边界输入的工程量与编译时间，因为边界形状常触发不同的模板实例化路径。举例：一个 softmax 条目若把正确性容差写成绝对误差 $10^{-6}$，在长序列、大 logits 的情形下必然误判，因为参考实现自身的累加顺序差异就会超过该界；正确做法是把容差写成与序列长度相关的相对界，并在条目里注明 oracle 的累加策略。

维度判定对象容差语义主要代价
正确性输出偏差误差界oracle 时间与显存
性能计时统计量阈值下界重复采样时延
鲁棒性边界行为布尔 + 兜底界构造与编译开销

三 · 分类维度二：按输入分布的可控性分——固定、参数化、生成式

输入分布 $\mathcal{D}_{\text{in}}$ 是条目里最容易被敷衍的字段，也是分类的第二根轴。按可控性分三档，每档对应不同的种子策略与复现成本。

固定输入：输入张量的具体数值被固化（哈希或直接存储），种子 $s$ 仅用于校验。优点是复现零歧义，审计时可直接比对输入哈希；缺点是覆盖面窄，agent 容易对固定输入过拟合，且存储体量随条目数线性增长。适用于回归测试与小规模正确性条目。

参数化输入：输入由一组形状与分布参数（维度、dtype、均值方差、稀疏度）加种子 $s$ 唯一确定。这是本规范推荐的默认档。机制上，条目记录参数元组与种子，评测脚本用确定性 PRNG 重建输入；审计时重放同一元组即得同一输入。代价是 PRNG 实现的跨平台一致性——不同库的同一算法在浮点生成路径上可能有末位差异，因此条目必须指定 PRNG 算法与生成顺序，而不能只写“随机”。

生成式输入：输入由外部数据源或模型生成，条目只记录数据源标识与采样规则。这类条目复现成本最高，因为数据源本身可能漂移；规范要求此类条目额外留存输入摘要（如分桶统计量与哈希），否则审计无法区分“kernel 退化”与“输入漂移”。代价是存储与带宽，摘要本身也要占空间。

$$\text{复现成本} \propto \frac{1}{\text{输入可控性}} + \text{摘要存储}$$

举例：一个 attention 条目若只写“随机生成 Q/K/V”，未指定 head 维度与序列长度的联合分布，则不同实现采到的形状分布不同，性能条目的加速比不可比。正确写法是把形状分布写成离散枚举加权重，并把种子绑定到枚举顺序，使重建完全确定。

四 · 分类维度三：按硬件隔离强度分——同机、独占、跨机

硬件隔离 $\mathcal{H}$ 决定条目结论的可迁移范围，按强度分三档。这一维度常被误认为只是“有没有独占 GPU”，实际上它同时约束计时方法与性能阈值的可比性。

  • 同机共享：评测与训练或其他负载共享同一 GPU。条目必须声明并发负载的存在与类型，计时方法必须能剥离干扰（如用 CUDA event 而非 wall-clock，并规定最小空闲窗口）。代价是计时方差大，性能阈值必须放宽，且结论不可跨机器迁移。
  • 独占单机：整卡独占，无其他进程。这是性能条目的基准档。机制上要求固定时钟策略（是否锁频）、固定驱动与固件版本、固定内存分配器行为。代价是吞吐利用率下降——独占意味着评测期间算力不能复用，批量评测的 wall-clock 成本按条目数线性叠加。
  • 跨机可比：在多台同规格机器上重复，条目结论要求机器间离散度落在给定界内。这一档的代价最高，因为需要额外的机器间校准条目（同一参考 kernel 在各机器上的计时分布），校准条目本身的时延与日志体量都要计入预算。

隔离强度与容差 $\tau$ 必须联动：同机共享档下的性能条目若沿用独占档的严格阈值，会把噪声误判为退化；反之独占档下放宽阈值则丧失灵敏度。举例：一个 GEMM 条目在共享档下测得加速比波动跨越阈值，若条目未声明并发负载，审计者会误以为 kernel 不稳定，实际是隔离字段缺省导致的归因错误。

五 · 与相邻概念的区别：条目、用例、基准、指标口径

四个概念常被混用，边界必须划清，否则规范无法落地。

条目 vs 用例：用例是“一个输入 + 一个期望输出”的具体实例；条目是生成用例的规则集加判定规则。一个条目可以派生出成百上千个用例（不同形状、不同种子），但条目本身只有一份。区别的工程意义在于：修条目要重跑全部派生用例，修单个用例只影响该实例。条目是版本化的对象，用例是条目的运行时产物。

条目 vs 基准：基准是条目的集合加聚合规则（如何从多条目的判定汇总出一个分数）。条目回答“这一个 kernel 在这一个任务上是否合格”，基准回答“这一批 kernel 在这一族任务上的整体水平”。基准速查属于另一份材料，此处只需记住：条目的容差与计时方法不可被基准的聚合规则覆盖，聚合只能在条目判定之上做统计，不能反向修改条目字段。

条目 vs 指标口径：指标口径规定“加速比怎么算、SOL 怎么算、方差怎么报”，是跨条目共享的计算约定；条目规定“这一个任务的输入、容差、隔离、种子”。口径是横向的，条目是纵向的。二者耦合点在于 $\mathcal{F}_{\text{report}}$：条目必须引用某一版口径，口径升版时条目要显式声明沿用旧版还是迁移，否则历史结果不可比。指标口径的细节由专门材料展开，这里只强调条目必须钉住口径版本号。

条目 vs 防作弊检查：防作弊是条目之上的附加约束层，检查 agent 是否通过缓存结果、特化输入、绕过计时等方式伪造合格。条目本身不承担防作弊职责，但条目字段的设计要为防作弊留接口——例如固定输入档必须存哈希以便检测输入替换，性能条目必须留存原始计时样本以便检测计时裁剪。二者是正交的：一个条目可以完全合规却在防作弊检查中失败，说明条目字段不足以约束行为，需要回填字段而非修改检查。

概念回答的问题版本化对象与其他概念的关系
条目单任务是否合格六元组派生用例、引用口径
用例单实例的输入输出否（运行时产物）由条目生成
基准一族任务的整体水平条目集合 + 聚合规则建立在条目判定之上
指标口径指标怎么算计算约定被条目引用并钉版本

六 · 字段完备性的判定：缺哪个字段会坏哪件事

条目分类的最终目的是做字段完备性检查。工程上不必追求“字段越多越好”，而要建立字段缺失与失效模式的一一映射，使审计者能快速定位条目缺陷。

  • 缺输入分布：正确性条目退化为噪声比较，性能条目的加速比不可跨实现比较。
  • 缺容差标准：判定无界，任何输出都可被判合格或不合格，条目失去判别力。
  • 缺计时方法：性能条目的阈值不可解释，CUDA event 与 wall-clock 的分布差异会被误读为 kernel 差异。
  • 缺硬件隔离：结论不可迁移，跨机器比较与共享档下的性能判定均失效。
  • 缺随机种子：参数化与生成式输入不可重建，审计无法重放。
  • 缺上报格式：聚合指标与原始日志无法对齐，漂移与上报错误不可区分。

完备性检查的代价是条目编写与维护的人力，以及每次字段变更触发的重跑成本。一个实用判据是：若某字段的缺失只影响“读起来是否舒服”而不影响“重跑是否得到同一判定”，则该字段不是必需字段，应移出六元组以免条目膨胀。举例：条目里写“编译器优化等级”看似细节，但它直接影响计时与数值（如 fast-math 改变累加顺序），因此属于计时方法与容差标准的绑定字段，不能省略；而“作者备注”不影响判定，不应进入六元组。

最终落在一条工程判断上：条目的分类维度不是标签，而是失效模式的索引。按判定对象分类，决定容差语义；按输入可控性分类，决定复现成本；按隔离强度分类，决定结论迁移范围。三者交叉即得条目的适用边界，审计者据此判断一条评测结论能否被采信，而不必重跑全部用例。这也是评测脚本与训练侧隔离、原始日志留存这两条硬性要求的结构性理由：它们把条目从“一次运行的记录”提升为“可被反复质询的契约”。
