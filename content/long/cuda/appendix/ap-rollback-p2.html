一 · 表的结构：三列定死，不留解释空间

这张速查表只回答一件事：当线上 kernel 的某个观测字段越过某条线时，值班的人该做什么。因此每一行必须是三元组——字段（从哪个信号里读）、阈值（越线的判定口径，含窗口与比较符）、口径（谁来算、按什么聚合、误报如何豁免）。三列缺一列，这张表就不能照着执行：只给字段不给阈值，等于把判断推回给人；只给阈值不给口径，同一份数据两个人算出两个结论；只给口径不给字段，则无从采集。

字段一律取自已有监控面，不新增埋点。可用的字段集合是封闭的：请求级错误率、端到端时延的 P50/P99、kernel 自身的执行时延分布、数值输出与参考实现的最大相对偏差、显存峰值占用、编译与首次调用耗时、灰度批次的样本量。阈值写成“比较符 + 数值 + 窗口”的三段式，例如“> 基线 × k，连续 N 个采样窗口”，其中 k 与 N 是配置项而非硬编码，因为不同 kernel 的噪声底不同。口径列必须写明聚合方式（按请求还是按 batch、是否剔除冷启动首调用）与豁免条件（如编译期抖动不计入时延判定）。

$$\text{trigger} = \mathbb{1}\left[\ \text{agg}_{w}\big(m(\text{field})\big) \gtrless \theta\ \right]\ \wedge\ \mathbb{1}\left[\ \text{samples} \ge n_{\min}\ \right]$$

这个判据里的 n_min 是防误报的关键：小样本窗口下错误率的方差极大，样本不足时即便越线也只记录不触发。代价是检出延迟——样本量门槛越高，从真实劣化发生到触发回滚之间的时延越长，这段时延内错误请求仍在被服务。因此 n_min 的选择本身就是一次“误报率 vs 检出时延”的权衡，必须写进表里而不是留给实现者拍脑袋。

二 · 错误率与精度漂移：两条不同的线

错误率字段的判定对象是“请求是否失败”，包括 kernel 抛错、超时、返回非法值。它的口径要区分硬失败与软失败：硬失败是异常与超时，直接计入；软失败是输出通过形状检查但数值不可用，需要下游校验器判定后才计入。两者混在一个比率里会让阈值失去意义，因为软失败的检出本身有延迟。表里应写成两行，各自独立的阈值与窗口。

精度漂移是另一条线，判定对象是“输出与参考实现的偏差”。它不是错误率的子集：一个 kernel 可以 100% 成功返回、零异常，但数值偏差缓慢爬升。口径必须钉死三件事——参考实现是谁（离线参考还是同批次 CPU 路径）、偏差用什么范数（最大相对偏差还是按元素 L2）、采样比例（全量比对还是抽样）。抽样比例直接决定这条线的成本：全量比对意味着每个请求都要跑一遍参考路径，时延翻倍；抽样比对则可能漏掉只在特定输入形态下出现的漂移。

字段阈值形态口径要点代价
硬失败率> 基线 + 绝对增量，连续窗口按请求计，剔除冷启动首调用检出快，误报低
软失败率> 绝对上限，连续窗口依赖下游校验器，按 batch 聚合检出延迟 = 校验器时延
最大相对偏差> 容差，单批次即触发指定参考路径与范数，抽样比例固定全量比对使时延翻倍
偏差爬升斜率窗口间增量 > 上限按同输入形态分组统计需保留历史窗口，显存/存储开销

具体例子：某归约类 kernel 上线后硬失败率为零，但最大相对偏差在长序列输入上从量级 1e-6 缓慢升至 1e-4 量级，短序列不变。若表里只设了“单批次偏差 > 容差”这一行，则永远不触发，因为单批次偏差始终在容差内；必须补上“按输入形态分组的偏差爬升斜率”这一行，才能把这类随规模放大的漂移抓住。这条线的代价是分组统计需要保留历史窗口，存储与聚合开销随分组数线性增长。

三 · 时延抖动：区分 kernel 自身与端到端

时延字段必须拆成两层。端到端 P99 反映用户感受，但它的噪声来源多（排队、批处理、下游），单独用它触发回滚会频繁误杀。kernel 自身的执行时延分布才是归因层：只有当 kernel 自身时延的某个分位数显著劣化、且端到端同向变化时，才判定为 kernel 侧问题。表里两行并列，口径写明“先看 kernel 层，再看端到端层，两层同向才触发”。

抖动的判定不能用均值。均值对长尾不敏感，而 GPU kernel 的劣化往往表现为尾部拉长——少数请求因 occupancy 下降或寄存器溢出而变慢。因此阈值应落在高分位数上，且窗口内要求“连续多个窗口越线”而非单点越线，以过滤掉编译期抖动、上下文切换等一次性事件。冷启动首调用的编译耗时必须显式剔除，否则每次灰度新批次都会误触发。

$$\text{jitter} = \frac{P99_{\text{win}} - P99_{\text{base}}}{P99_{\text{base}}},\qquad \text{trigger} = \text{jitter} \gt \delta \ \wedge\ \text{consec} \ge c$$

代价在这里体现为检出延迟与误报的乘积：窗口越长、连续窗口数 c 越大，误报越少但检出越慢。一个可执行的折中是让 kernel 层用短窗口高灵敏、端到端层用长窗口做确认，两层的时间常数不同。具体例子：某矩阵乘 kernel 因 tile 配置变更导致尾部时延上升，kernel 层 P99 在短窗口内即越线，而端到端 P99 因批处理吸收尚未变化；此时表应允许“kernel 层单独越线即进入观察态并自动回退灰度比例”，而不必等到端到端确认，代价是可能为一次不影响用户的劣化多付一次回退操作。

四 · 资源与编译字段：显存峰值与首次调用

显存峰值占用是回滚的硬约束而非性能指标：一旦峰值越过设备可用上限，后续请求直接 OOM，错误率会瞬间跳变。因此它的阈值形态不同于其他字段——不是“相对基线增量”，而是“绝对上限减去安全余量”，且判定窗口为单批次即触发，不要求连续窗口。口径要写明峰值如何采样（按分配器峰值还是按设备查询）以及是否包含框架自身的常驻占用。

编译与首次调用耗时属于“上线即一次性”的字段，它的作用是防止灰度批次被冷启动拖垮。阈值形态是“首次调用耗时 > 上限则本批次不计入时延统计”，本质是豁免规则而非回滚触发。把它误写成回滚触发会导致每次新批次都回滚一次，形成抖动循环。代价是编译时间本身占用灰度窗口：编译越慢，可用于观测稳态时延的窗口越短，样本量门槛 n_min 越难满足。

字段阈值形态口径要点代价
显存峰值> 上限 − 余量，单批次触发按分配器峰值采样，含常驻占用余量过小则频繁误触发
首次调用耗时> 上限则豁免本批次剔除出时延统计，不触发回滚压缩稳态观测窗口
稳态样本量< n_min 则判定无效按有效请求计，剔除豁免批次样本不足时检出延迟拉长

具体例子：某融合 kernel 在较大 batch 下显存峰值逼近上限，表里若只写“相对基线增量”则会漏判——因为基线本身也高，增量很小但绝对峰值已越线。改为绝对上限判定后，该批次在单窗口内即触发回退，代价是安全余量被吃掉一部分可用显存，等效于降低了可支持的最大 batch。

五 · 灰度比例与切换步骤：表驱动的执行序列

速查表的最后一组字段是灰度比例与切换动作，它们把“越线”翻译成“做什么”。灰度比例不是连续可调的旋钮，而是离散档位，每档对应一个观测窗口与样本量门槛。表里应写成“档位 → 观测窗口 → 晋升条件 → 回退动作”的映射，晋升条件即前述各字段全部未越线且样本量达标。回退动作分两级：降档（回到上一灰度比例）与全量回退（切回参考实现）。降档用于观察态，全量回退用于确认态。

切换步骤必须写成有序动作而非原则：停止新批次进入、等待在途请求排空或超时、切换路由到参考实现、校验参考路径自身健康、恢复流量。其中“校验参考路径自身健康”常被省略，但它决定了回退是否真的有效——若参考实现同样劣化，回退只是把故障换了个位置。代价是排空等待引入的时延：在途请求越多，排空越慢，这段窗口内新旧两条路径并存，显存占用是两者之和，可能触发前述显存峰值字段的二次越线。

$$\text{rollback cost} = t_{\text{drain}} + t_{\text{switch}} + t_{\text{verify}},\qquad \text{mem}_{\text{peak}} \approx \text{mem}_{\text{new}} + \text{mem}_{\text{ref}}$$

具体例子：某 kernel 在第二档灰度时精度漂移越线，执行降档后漂移消失，说明劣化与并发度相关而非实现本身。此时表应允许“降档后观察一个窗口再决定是否全量回退”，而不是直接全量回退；代价是多消耗一个窗口的观测时间，收益是避免把一次可修复的配置问题升级为版本回退。

六 · 复盘归档：字段回填与阈值校准

每次触发都必须回填一条归档记录，字段固定为：触发字段、越线时的窗口聚合值、当时的灰度档位、样本量、执行的动作序列、动作耗时、以及回退后同一字段的恢复值。这条记录的作用不是写报告，而是校准阈值——若某字段在多次触发中恢复值都远低于阈值，说明阈值过紧；若多次触发后恢复值仍贴近阈值，说明基线本身在漂移，需要重设基线而非调阈值。

归档口径要写明“恢复值”的采样时点：回退完成后固定延迟再采样，避免把排空期的混合流量计入。代价是归档存储随触发次数线性增长，且恢复值采样本身占用一次额外的观测窗口。具体例子：某错误率字段在三个月内触发多次，归档显示恢复值始终接近基线而阈值仅略高于基线，说明阈值与噪声底之间的距离不足，校准动作是把阈值改为“基线 + 噪声底估计的若干倍”而非固定绝对增量，这一改动直接降低后续误报率，代价是真实劣化的检出灵敏度同步下降，需要在归档里同时记录漏报样本以监控这一侧的影响。

速查表里最容易写错的三列：口径、观测窗与回退代价

速查表的价值不在阈值本身，而在每个阈值后面那列“口径”。同一张表里，错误率必须写清分母是“本 kernel 的 launch 次数”还是“端到端请求数”——前者在融合 kernel 里会被一次 launch 覆盖数千元素，分母小、方差大，单点抖动就会击穿阈值；后者则被上游排队稀释，故障被平均掉。延迟抖动同理：用 P99 还是 P99.9、观测窗是 1 分钟还是 15 分钟，决定了同一份遥测数据是“告警”还是“静默”。精度漂移必须绑定 oracle：是逐元素 allclose 的容差，还是下游任务指标的相对变化。表里若只写“错误率 < 0.5%”而不写分母与窗口，回滚决策就退化成值班人的主观判断。

失效条件要单独成列，而不是塞进备注。灰度比例与观测窗存在耦合：灰度 1% 时，单位时间内的样本量按比例缩小，达到统计显著所需的窗口被拉长，公式上可写成 n ≈ (z²·p(1−p))/δ²，其中 p 为基线错误率、δ 为可容忍偏差；样本不足时阈值形同虚设，此时应改用“绝对错误计数 ≥ k”这类计数型判据而非比率型。另一个失效条件是回退路径本身的代价：切回参考实现意味着重新加载权重/重新编译、丢失已预热的 L2 与常量缓存，端到端时延在切换瞬间出现尖峰，若灰度层没有预留双跑容量，回退动作本身就会触发二次告警。

字段口径要求失效条件系统代价
错误率分母=launch 次数，窗口≥样本量下限灰度 <1% 时比率不可判计数型判据需额外埋点
延迟抖动P99 相对基线增幅，固定窗口上游排队掩盖尾部双跑预留显存与 SM 占用
精度漂移绑定 oracle 与容差oracle 自身版本漂移离线校验的编译与 token 开销

具体例子：某融合 attention kernel 在灰度 2% 时，错误率分母取端到端请求数，单批 512 请求里 3 次失败被稀释为 0.6%，未触发阈值；但按 launch 口径该窗口内失败率已远超基线。把分母改回 launch 次数并加“绝对计数 ≥ 3”的辅助判据后，回滚在下一观测窗内被触发。代价是埋点从请求级下沉到 kernel 级，遥测写入量上升，且回退时双跑容量需按峰值 SM 占用的一个比例预留——这部分显存预算必须写进速查表，否则回滚清单在容量紧张时无法执行。
