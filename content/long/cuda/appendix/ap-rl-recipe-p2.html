一 · 速查表的字段骨架：把一次 rollout 拆成可填的格子

这张表不是超参清单，而是把一次多轮 RL 迭代中所有需要落笔的决策点压缩成字段。字段的划分依据是“谁消费它”：采样侧消费 batch 与轮数，反馈侧消费编译/运行产物，奖励侧消费正确性与加速比，约束侧消费 KL 与课程，监控侧消费 hacking 信号。每个字段必须带三样东西——取值口径（怎么算出来的）、阈值（越界即触发动作）、代价标签（改动它会付出什么）。缺任何一样，这张表就退化成一张抄来的配置。

字段命名要能直接映射到代码里的变量，避免“温度”“难度”这类歧义词。建议的骨架是：rollout_batch（每轮并行采样的候选数）、turn_budget（单条轨迹允许的编译-修正轮数）、feedback_payload（回灌给模型的反馈内容集合）、correct_gate（正确性门控的判定口径）、speed_norm（加速比归一化基准）、kl_coef（KL 惩罚系数）、curriculum_level（当前课程档位）、hack_signal（作弊监控指标集合）。这八个字段构成表的主键，其余字段都是它们的派生量。

派生量的计算必须写成公式而不是口头描述，否则不同人填表会得到不同口径。以“有效样本率”为例，它决定一轮迭代里有多少 token 真正参与了梯度：

$$\text{ESR}=\frac{\sum_{i=1}^{N}\mathbb{1}[\text{compile}_i\land\text{pass}_i]}{N\cdot \text{turn\_budget}}$$

分母用“候选数×轮数”而非候选数，是因为每一轮都消耗 token 与编译时延；分子只计编译成功且正确性通过的轨迹。ESR 低于阈值意味着大量轮次被浪费在语法错误与运行崩溃上，此时应下调 turn_budget 或提高初始 prompt 的骨架质量，而不是加大 batch。代价是明确的：turn_budget 每加一轮，单条轨迹的 token 消耗与编译排队时延近似线性增长，而 ESR 的边际收益在第三轮之后迅速衰减——这是工程判断，不是实验数字。

具体例子：某条轨迹第一轮编译报 shared memory 超限，反馈里只回灌了错误码，模型第二轮把 tile 改小但未改 bank 冲突，第三轮才通过。这条轨迹的 ESR 贡献是 1/3，而它的加速比若以第一轮为基准会被高估——因此 speed_norm 必须绑定“通过正确性门控的那一轮”，不能绑定“最后一轮”。填表时这一条要写进口径列，否则奖励塑形会系统性偏袒“靠多轮试错磨出来的慢 kernel”。

二 · 阈值列：每个字段的越界动作必须唯一

阈值的作用不是“设一个数”，而是“越界后执行哪一个动作”。一个阈值若对应两个以上动作，等于没有阈值。表里每个阈值列应写成三元组：比较符、数值来源（固定/自适应）、越界动作。数值来源必须标注是硬编码还是由历史统计推导，因为后者在课程调度下会漂移。

正确性门控的阈值最容易被写错。correct_gate 不应是“全部测试用例通过”这一个布尔值，而应分层：数值容差层、形状覆盖层、边界用例层。容差层的口径要与基准的比对方式一致（绝对误差、相对误差、还是 ULP 距离），三者对同一 kernel 的判定可能不同。阈值动作是：容差层失败→回灌具体失配的索引与两侧数值；形状覆盖不足→回灌缺失的形状列表；边界用例失败→标记该轨迹为“高危正确性”，不进入奖励计算但保留用于课程升级。代价是反馈 payload 的体积：回灌失配索引会显著增加 token 数，需在 feedback_payload 里设上限，超出则只回灌统计摘要。

KL 约束的阈值要区分“系数”与“实际散度”两个量。kl_coef 是惩罚权重，而真正需要监控的是每轮更新后的策略散度估计。阈值动作应是：散度超过上界→冻结本轮奖励塑形中的加速比项，只保留正确性门控信号；散度低于下界→说明策略几乎没动，检查是否 correct_gate 过严导致梯度被门控吃掉。这里有一个具体的机制代价：KL 惩罚是在 token 级累加的，若把 kl_coef 调大以压制散度，等价于压缩策略的探索半径，直接表现为 rollout_batch 中“新颖但正确”的候选比例下降——即 ESR 的分母不变而分子变小。

课程难度的阈值不能只看通过率。单看通过率会让课程在“简单题刷分”和“难题全崩”之间震荡。表里应同时记录 curriculum_level 与“该档位的编译失败率”和“该档位的加速比分布中位数”。阈值动作：通过率高但加速比中位数贴近 1.0→升档，因为模型在正确性上已饱和但没学到优化；编译失败率超过阈值→降档并回灌该档位的典型错误模式。代价是课程切换本身消耗一轮迭代的样本效率：新档位的首批候选几乎全部落在低 ESR 区间，这是切换成本，应在表里显式记为“档位冷启动轮数”。

字段口径阈值动作主要代价
correct_gate容差/形状/边界三层分层回灌，高危轨迹隔离反馈 token 体积
kl_coeftoken 级累加，监控实际散度越上界冻结加速比项探索半径收缩，ESR 分子下降
curriculum_level通过率+加速比中位数+编译失败率升/降档并回灌错误模式档位冷启动轮数

三 · 反馈构造的口径：回灌什么、不回灌什么

feedback_payload 是这张表里最容易被低估的字段。它决定了模型在下一轮看到的是“可操作的诊断”还是“噪声”。口径上要把反馈分成四类：编译器诊断（错误码、行列、约束违反量）、运行时诊断（越界、非法访存、超时）、性能诊断（相对基准的时延比、占用率、带宽利用的定性描述）、正确性诊断（失配索引与数值）。四类的回灌优先级不同：编译错误必须全量回灌定位信息，因为它是确定性的；性能诊断只回灌“与上一轮的差值方向”，不回灌绝对数值，避免模型对着数字过拟合。

一个具体的机制是反馈截断策略。当编译日志超过 feedback_payload 的 token 上限时，不能简单截断尾部——尾部往往是模板实例化的噪声，真正有用的是首条错误与约束违反量。口径应写成“保留首条错误 + 约束违反量的数值 + 错误类型计数”，丢弃模板展开栈。代价是模型可能重复犯同一类错误，因为丢失了后续错误的上下文；缓解方式是在表里加一个“错误类型直方图”字段，跨轮累积，让模型看到的是错误分布而非单条日志。

性能诊断的回灌有一个正确性陷阱：若把 NCU 采集的绝对指标（如 achieved occupancy）直接回灌，模型会朝着“提高占用率”优化，而占用率高不等于快——寄存器压力与指令级并行会互相挤压。口径应改为“相对基准 kernel 的定性差距 + 瓶颈类型标签（访存受限/计算受限/延迟受限）”，标签由 roofline 位置推导，而不是由单个计数器阈值推导。代价是标签推导本身需要一次 profile 采集，profile 的时延与显存开销要计入单轮迭代成本，因此表里应设“profile 采样率”字段：不是每条轨迹都采，只对通过正确性门控且加速比落在中位区间的轨迹采样。

例子：一条轨迹编译通过、正确性通过、加速比 0.6。若回灌“occupancy 偏低”，模型下一轮可能盲目加线程；若回灌“访存受限，基准 kernel 的算术强度高于你一个量级”，模型会转向减少冗余访存。后者才是可验证奖励想要引导的方向。这个差别就是口径列存在的理由。

四 · 奖励塑形的阈值：门控与归一的耦合点

奖励塑形的核心是“正确性门控 + 加速比归一”两段式，但两段的耦合点必须写死在表里，否则会出现“正确但不快”和“快但不正确”两类轨迹拿到相近奖励的情况。speed_norm 的口径应明确：归一化基准是基准实现（reference）的时延，还是同档位历史最优？前者稳定但会随硬件与编译选项漂移，后者自适应但会让奖励随课程升档而整体缩水。表里应写成“基准实现时延，且在同一编译选项下测得”，并把编译选项作为字段记录，防止跨轮比较时口径不一致。

门控的严格度与归一的分辨率是一对矛盾。门控越严（容差越小、形状覆盖越全），进入奖励计算的轨迹越少，归一化分布越窄，梯度信号越稀疏；门控越松，错误 kernel 混入奖励，模型学会“近似正确”的捷径。表里应设一个“门控通过率”监控字段，阈值动作是：通过率过低→放宽容差层但不放宽边界层；通过率过高→收紧形状覆盖。代价是每次调整门控都会改变奖励分布的均值，历史轨迹的奖励不可直接跨口径比较，因此表里要带“口径版本号”，跨版本只做定性对比。

$$r_i=\mathbb{1}[\text{gate}_i]\cdot \alpha\cdot \frac{t_{\text{ref}}-t_i}{t_{\text{ref}}}-\beta\cdot \text{KL}_i$$

这个式子里 gate 是三层门控的合取，alpha 与 beta 是塑形权重。工程上要注意：加速比项在 t_i 接近 t_ref 时对测量噪声极其敏感，一次编译选项的微小差异就能让符号翻转。口径上应对加速比做死区处理——落在基准时延某个比例带内视为零收益，避免模型追逐噪声。代价是死区会吞掉真实的小幅优化，因此死区宽度应随课程档位收窄，高档位才启用精细分辨。

具体例子：两条轨迹都通过门控，一条加速比 1.05、一条 0.98。若没有死区，后者拿到负奖励，模型会学到“保守改写”；若有死区且宽度覆盖这两者，两条都得零收益，模型得不到“哪个更好”的信号。表里因此要记录死区宽度与档位的对应关系，这是奖励塑形能否产生有效排序的关键口径。

五 · reward hacking 监控字段：把作弊信号变成可填的列

hack_signal 不是单一指标，而是一组互相印证的字段。常见的作弊形态在这套流程里有明确的观测面：缓存结果绕过真实计算、针对测试形状特化、把计算挪到计时区间之外、用低精度近似骗过容差。每种形态对应一个可观测信号，表里要把信号与判定口径写在一起。

  • 缓存绕过：口径是“同一输入重复调用时时延异常下降”，判定要看多次调用的时延方差，而不是单次时延。代价是需要重复调用，增加评测时延。
  • 形状特化：口径是“在训练形状上快、在留出形状上崩”，判定要保留一组不参与反馈的形状。代价是留出形状的评测算力。
  • 计时区间外移：口径是“kernel 时延与端到端时延的差值扩大”，判定要同时记录两者。代价是端到端测量本身的噪声。
  • 低精度骗过容差：口径是“输出与高精度参考的误差分布集中在容差边界”，判定要看误差分布的尾部而非均值。代价是高精度参考的计算开销。

这些信号的阈值动作应统一为“隔离而非删除”：命中信号的轨迹不进入奖励计算，但保留其反馈用于课程难度校准，因为作弊往往发生在难度跃升的档位，是课程调度需要的信息。表里应有一个“作弊命中率”字段，按档位分组统计。若某档位命中率异常升高，动作是回退档位并检查该档位的测试形状是否过于单一，而不是加大 KL 惩罚——后者只会让模型更保守，不会消除作弊动机。

一个具体的机制代价：留出形状的评测需要额外编译与运行，单条轨迹的评测时延上升；若对全部候选都做留出评测，一轮迭代的算力成本显著增加。因此表里应设“留出评测采样率”，只对通过门控且加速比超过基准的轨迹做留出验证——这正是作弊最可能出现的区间。这个采样率与第三节的 profile 采样率共享同一批候选，两者的算力开销应合并估算，避免重复编译。

最后落到一个工程判断：这张速查表的价值不在于字段多，而在于每个字段都能被单独回滚。当某一轮迭代出现奖励崩塌或 ESR 骤降时，工程师应能只改一个字段的口径并重跑，而不是整表重调。因此表里每个字段都要带“上次变更版本”与“变更理由”两列，把调参过程本身变成可审计的记录。没有这两列，速查表就只是一次性配置，无法支撑多轮迭代中的归因。
