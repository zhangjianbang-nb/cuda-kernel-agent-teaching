一 · 阈值的来源：把“经验数字”还原成可测的量

工程阈值不是拍脑袋的常数，而是某个代价函数在特定硬件与工作负载下的拐点。选型时真正要问的不是“编译要多久”，而是“编译时延相对于什么代价变得不可忽略”。把这句话写成式子，阈值就有了出处。设单次迭代的端到端时间为 Titer = Tcompile + Texec + Tverify，其中 Tcompile 是 kernel 构建（nvcc 编译、Triton JIT、NVRTC 运行时编译、CuTe 模板实例化）的耗时，Texec 是 kernel 在目标形状上的执行时间，Tverify 是正确性 oracle 与基准计时的开销。定义编译占比：

$$\rho = \frac{T_{\text{compile}}}{T_{\text{compile}} + T_{\text{exec}} + T_{\text{verify}}}$$

当 ρ 超过某个比例，agent 的多轮搜索就被构建开销主导，采样效率崩塌。这个比例就是“编译时延阈值”的真实定义，它随 Texec 变化：同一个 nvcc 编译时间，对毫秒级的小 kernel 是灾难，对秒级的大算子可以忽略。因此任何写进选型表的数字都必须附带测量条件（形状、batch、硬件、编译 flag），否则不可复用。测量方法上，Tcompile 要用冷缓存测（清空 Triton 的 JIT 缓存目录、禁用 ccache、nvcc 加 -lineinfo 前后各测一次以分离调试信息开销），Texec 用 CUDA event 包裹多次迭代取中位数而非均值，Tverify 单独计时以确认它没有偷偷主导预算。代价在于：冷缓存测量本身耗时且不可并行，一轮完整标定可能占用数十分钟的机器时间，这笔开销要计入工具链评估的固定成本，而不是摊到每个 kernel 上。

具体例子：一个逐元素 ReLU 类 kernel 在中等张量上执行时间是微秒量级，此时 nvcc 的数秒级编译会让 ρ 接近 1，agent 每提一个候选就要等编译，多轮 RL 的吞吐被彻底压死；同一套工具链换到带规约与多级 tile 的注意力类 kernel，执行时间抬升两个数量级，ρ 掉到可接受区间，nvcc 的表达力优势才开始兑现。结论不是“nvcc 慢”，而是“nvcc 的编译代价必须与目标 kernel 的执行时间同尺度比较”。

二 · 编译时延的分层测量：模板实例化是隐藏项

把 Tcompile 当成单一数字是选型中最常见的错误。它至少由三段构成：前端解析与语义检查、模板实例化与代码生成、以及设备端编译与链接。CuTe/CUTLASS 的代价几乎全部落在第二段——每个 tile 形状、每个 layout 组合都是一次新的模板实例化，实例化数量随配置空间组合爆炸。测量方法是对同一份源码做消融：固定一个配置编译一次记录基线，再逐步增加配置维度（dtype、tile 尺寸、stage 数），观察编译时间随配置数的增长斜率。若斜率近似线性，说明实例化是主项；若出现阶跃，说明撞上了某个昂贵的特化路径。nvcc 侧可以用 --ptxas-options=-v 观察寄存器与占用率，但它不直接给出时间分解，需要靠分段编译（先 -c 出 cubin 再链接）来切分。

伪代码思路如下，用于把编译时间归因到配置维度：

  • 对每个配置维度 d，构造只在该维度上变化的两个变体，分别冷编译并计时；
  • 计算 ΔTd = T(variantd+1) − T(variantd)，按 ΔTd 降序排列；
  • 对排名第一的维度做二分裁剪，找到“编译时间可接受”的最大配置数，这个数就是该工具链在此项目上的配置预算。

代价是显存的间接影响：模板实例化膨胀会推高 host 侧内存与编译进程的峰值占用，在容器内存限额下可能触发 OOM kill，表现为“编译随机失败”，这类失败在 agent 日志里极易被误判为代码错误。具体例子：一个 CuTe 实现的多 stage GEMM，若把 stage 数与 tile 尺寸都做成模板参数并在一个翻译单元里全量实例化，编译时间与内存占用都会随组合数上升；把配置裁剪到实际搜索会用到的少数几组，编译预算立刻回到可控范围。工程判断是：CuTe 的选型前提不是“能不能写”，而是“配置空间是否已被搜索策略约束住”。

三 · 执行侧阈值：占用率、寄存器与共享内存的硬边界

执行侧的“经验数字”大多可以还原成资源约束的等式。以占用率为例，活跃 warp 数受寄存器、共享内存、block 数三重上限约束，实际占用率是三者最小值的函数：

$$\text{occupancy} = \frac{\min\left(\left\lfloor \frac{R_{\text{reg}}}{r \cdot 32} \right\rfloor,\ \left\lfloor \frac{S_{\text{smem}}}{s} \right\rfloor,\ \left\lfloor \frac{W_{\text{max}}}{w} \right\rfloor\right) \cdot w}{W_{\text{max}}}$$

其中 r 是每线程寄存器数，s 是每 block 共享内存字节数，w 是每 block 的 warp 数，Rreg、Ssmem、Wmax 是每 SM 的对应上限。这个式子说明：占用率阈值不是“越高越好”的教条，而是延迟隐藏需求与资源竞争之间的平衡点。测量方法是双管齐下——用 --ptxas-options=-v 拿到静态寄存器与共享内存用量，再用 NCU 的占用率与 stall 采样确认实际达到的水平；两者不一致时，通常是动态共享内存或 launch bounds 未声明导致编译器保守估计。

代价体现在两个方向：寄存器压力过高会把 occupancy 压到阈值以下，长延迟指令（全局访存、特殊函数）无法被足够多的 warp 掩盖；反过来，为了抬高 occupancy 强行压低寄存器，会引入溢出到 local memory 的 spill，把片上带宽换成片外流量，性能反而下降。因此“寄存器阈值”应当表述为“在不发生 spill 的前提下允许的最大寄存器数”，测量方法是扫描 __launch_bounds__ 的 maxreg 参数，同时记录 spill 字节数与实测吞吐，找到 spill 首次非零的拐点。具体例子：一个带复杂索引计算的归约 kernel，索引逻辑吃掉大量寄存器，若不加约束，编译器为降占用率而 spill，NCU 上表现为 local memory 流量上升、L1 命中结构改变；把索引计算改为在编译期常量化的模板参数后，寄存器需求下降，spill 消失，占用率与吞吐同时改善。

四 · 正确性 oracle 的阈值：容差、ulp 与可复现性

正确性验证的“经验数字”是容差。它不能凭感觉给，而要从数值路径推导。对浮点累加，误差随累加长度增长，粗略的量级关系是相对误差与 √n 或 n 成正比（取决于累加顺序与是否使用补偿求和），因此容差应写成：

$$\text{tol}_{\text{rel}} = c \cdot \epsilon_{\text{mach}} \cdot f(n)$$

其中 εmach 是该 dtype 的机器精度，f(n) 反映累加结构（顺序累加取 n，树形归约取 log n 或 √n 量级），c 是安全系数。测量方法不是猜 c，而是做参考实现的误差分布统计：用高精度参考（CPU double 或 Kahan 补偿求和）对同一批输入算出误差直方图，取高分位数作为容差，而不是取最大值——最大值往往由个别病态输入主导，会把容差撑得失去判别力。代价是：容差过松会放过真实的精度退化（例如把 fp32 累加悄悄换成 fp16 中间量），容差过紧会把合法的指令重排与 FMA 融合判为错误，导致 agent 在正确解上反复“修复”，浪费采样预算。

可复现性是另一类阈值。GPU kernel 的确定性取决于归约顺序、原子操作与并行调度，非确定性 kernel 在两次运行间给出不同结果，会让基于逐位比较的 oracle 失效。测量方法是同一输入连续运行多次，统计输出差异的分布：若差异为零则逐位可复现，若差异在容差内则统计可复现，若超出容差则存在真实竞态。具体例子：一个使用 atomicAdd 做跨 block 归约的 kernel，逐位比较必然失败，但统计误差远小于容差；若 agent 的验证器只做逐位比较，它会把这个正确实现判错并反复重写，形成典型的假阴性循环。工程判断是：oracle 的严格程度必须与 kernel 的并行归约结构匹配，逐位比较只适用于规约顺序被完全固定的实现。

五 · 基准计时的阈值：预热、方差与最小可分辨差异

性能对比的“经验数字”是最小可分辨差异。任何两次测量的差值都必须与测量噪声比较，否则“优化”只是抖动。设同一配置重复测量得到时间样本，其标准差为 σ，则两次独立测量的差值在噪声内的概率很高，可分辨阈值约为：

$$\Delta_{\min} \approx z \cdot \sigma \sqrt{2}$$

z 取对应置信水平的系数。测量方法是：固定输入与配置，做足够多次重复（含预热以排除首次 launch 的上下文建立、JIT、cache 冷启动），报告标准差与分位数而非单点。预热次数本身是个阈值——太少则首轮开销污染样本，太多则测量时间膨胀；判断方法是画出时间随迭代序号的变化曲线，找到曲线进入平台的第一个点。代价是测量预算：每个候选 kernel 都要付出预热加重复的机时，在 agent 搜索中这会与候选数量相乘，成为吞吐瓶颈；因此实践中常对候选做粗筛（少量重复、宽容差），只对入围者做精细测量。

具体例子：两个 Triton 与 CUDA C++ 实现在同一形状上相差很小的百分比，若单次测量标准差与之同量级，这个差异不可信；把重复次数提高到噪声被压到差异之下，结论才成立。另一个陷阱是 autotune：Triton 的 autotune 在首次调用时穷举配置，这段开销若被计入 Texec，会把 Triton 的实测时间严重高估；测量时必须把 autotune 缓存预热到稳定态，或显式区分“首次调用”与“稳态调用”两个口径。工程判断是：跨工具链比较性能时，先对齐测量口径（是否含 autotune、是否含 JIT、预热策略），再谈数字，否则比较的是两套不同的计时定义。

六 · 把阈值落进选型决策：条件化的判断而非固定数字

把上述阈值组织成决策逻辑时，关键是把每个阈值写成“当 X 超过 Y 时选 Z”的条件句，并注明 Y 的测量条件。可以用一张条件表承载，而不是一张填满绝对数字的表：

判据测量量倾向代价面
ρ 编译占比高Tcompile 冷缓存 / Texec 稳态Triton 或 NVRTC 快速迭代表达力上限、运行时编译的首次延迟

这张表的价值在于每一行都能被独立测量，而不是依赖某个“公认数字”。PTX 内联与 NVRTC 的位置也由此确定：PTX 内联用于在高层实现中精确控制某几条指令（例如特定的舍入模式或访存指令），其代价是牺牲可移植性并对编译器优化形成屏障，测量方法是比较内联前后 SASS 的指令序列与实测吞吐；NVRTC 用于把编译推迟到运行时以换取部署灵活性，代价是首次调用的编译延迟进入关键路径，测量方法是记录首次与稳态调用的时间差，并确认这个差值是否落在服务延迟预算内。具体例子：一个需要在不同 GPU 架构上分发的推理服务，若把架构相关的特化交给 NVRTC 在首次请求时编译，首请求延迟会显著高于稳态；把编译移到预热阶段或离线缓存，代价转移到部署流程而非请求路径。工程判断落在“编译发生在哪个时间尺度上”——与 kernel 执行同尺度的编译是负担，与部署同尺度的编译是可接受的固定成本。

阈值不是拍脑袋：四类边界条件的测量口径

选型表里的每个数字都该有测量口径，否则它只是别人的机器上的偶然值。本方案要盯住四类边界：编译时延、迭代轮次预算、调试可见性折损、性能上限差距。编译时延用「冷启动一次编译 + 增量重编译」两段测，nvcc 走完整 fatbin 路径，Triton 走 JIT 缓存命中与未命中两条分支，NVRTC 单独记运行时编译开销，CuTe/CUTLASS 因模板实例化深度大，需按实例化组合数而非单文件计。判据是：若单次编译时延超过一次 agent 迭代预算的固定比例，模板重方案在 RL 多轮里就会被编译时间吞掉样本吞吐。

$$T_{\text{iter}} = T_{\text{gen}} + T_{\text{compile}} + T_{\text{run}} + T_{\text{verify}},\quad \rho = \frac{T_{\text{compile}}}{T_{\text{iter}}}$$

ρ 是选型的第一个硬阈值：ρ 高意味着反馈回路被编译器占据，此时应优先 Triton 或 NVRTC 缩短回路，把 CuTe 留给收敛后的最后一跳。第二个阈值是调试可见性折损：PTX 内联与 NVRTC 把错误从编译期推到运行期，正确性 oracle 必须能捕获非法访存与竞态，否则错误样本会污染奖励信号。第三个是性能上限差距，用同一 kernel 在 CUDA C++ 与 Triton 下的 SOL 利用率之比衡量，差距大到无法用调参弥补时，才值得付出模板与手写 PTX 的工程代价。

边界测量方法失效条件
编译时延 ρ冷/热两段计时，按实例化组合数归一ρ 超迭代预算比例，多轮 RL 吞吐塌陷
正确性折损注入越界/竞态用例，统计 oracle 捕获率运行期错误未被捕获，奖励被污染
性能上限同 kernel 跨方案 SOL 利用率对比差距无法靠调参弥补才升级方案

具体例子：一个归约 kernel 在 Triton 下热编译近乎瞬时，但 SOL 利用率停在较低档；换 CuTe 后利用率抬升，代价是实例化组合带来的编译时延使 ρ 明显上升。工程判断是分阶段选型——探索期用低 ρ 方案换迭代次数，收敛期用高上限方案换最后几个百分点，中间以 oracle 捕获率作为切换闸门。
