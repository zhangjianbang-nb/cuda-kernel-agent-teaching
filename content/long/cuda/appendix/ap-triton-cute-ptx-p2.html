一 · 速查表的字段设计：三层各自回答什么问题

这张表不是“语言特性罗列”，而是按“agent 在生成 kernel 时必须做出的决策”来排字段。每一行对应一个 Triton / CuTe / PTX 三层都绕不开的问题：这段代码由谁决定线程映射、由谁决定数据布局、由谁决定指令选择。字段分四组：抽象边界（谁写循环、谁写 tile）、布局控制粒度（能否显式指定 swizzle、能否固定寄存器分配）、warp specialization 支持（能否把 producer/consumer 拆到不同 warp group）、可观测产物（生成什么层级的中间表示与最终 SASS 差异）。每组字段都配一个“口径”列，说明该字段在评测时怎么量、量到什么粒度算数。字段值只做定性分级（原生支持 / 需手动展开 / 不可控），不写具体吞吐数字，因为同一 GEMM 在不同 shape 下的比值不稳定，写死数字会误导选型。

表的用法是“先查口径列，再查字段列”。agent 生成候选 kernel 后，第一步不是看它写得多漂亮，而是按口径列确认：这个候选的线程映射是编译器定的还是人定的？如果是编译器定的，那么性能方差就落在 autotune 的搜索空间上，而不是落在源码上；如果是人定的，那么正确性 oracle 必须覆盖手写索引的边界。这个判断决定了后续验证预算怎么分配——编译器定映射的候选可以用少量 shape 抽样验证，人定映射的候选必须做全边界扫描。

字段TritonCuTePTX口径（怎么量）
线程/block 映射由 compiler 从 tile 形状推导由 layout 代数显式构造由程序员逐条写死看 IR 中 thread id 是否出现在源码可见位置
布局控制粒度block 级，swizzle 不可见元素级，可写 swizzle 函数寄存器级，可指定 bank 分布改一个 layout 参数后 SASS 的 LDS 指令数是否变化
warp specialization无原生表达可用 layout 与 pipeline 组合表达用 bar.sync / mbarrier 手工划分是否存在独立的 producer warp group 分支

代价维度必须写进表的使用说明里：Triton 的抽象换来的是编译时间短、候选吞吐高，代价是布局不可控导致某些 shape 下 SASS 出现冗余 LDS；CuTe 的布局代数换来的是对 tile 的精确控制，代价是模板实例化带来的编译时间膨胀和错误信息可读性差；PTX 换来的是指令级确定性，代价是源码长度与维护成本，以及一旦写错 bank conflict 就只能靠 NCU 反推。这三条代价在 agent 场景下权重不同：多轮 RL 里候选吞吐是瓶颈，编译时间直接决定每轮能采多少样本，所以 Triton 候选适合做广搜，CuTe/PTX 候选适合做精修。

二 · 阈值：什么条件下必须下沉到下一层

“何时下沉到 PTX”不能靠感觉，要给可判定的阈值。阈值分三类：性能阈值、正确性阈值、表达力阈值。性能阈值看的是“同一 GEMM 在 Triton 下的 SOL 利用率与 NCU 报出的瓶颈段是否错位”——如果 NCU 显示 tensor pipe 利用率已接近饱和而 Triton 版本仍明显落后于手写版本，说明瓶颈不在算法而在指令选择或布局，此时下沉到 CuTe 改 layout 或到 PTX 改指令序列才有收益；如果 NCU 显示瓶颈在 DRAM 带宽且已接近 roofline，下沉没有意义，应该回到 tile 尺寸与流水深度。正确性阈值看的是“手写索引的边界覆盖是否可穷举”：Triton 候选的索引由编译器生成，边界错误通常表现为整块 tile 越界，可用少量 shape 抽样捕获；PTX 候选的索引由人写，越界可能只发生在某一列，必须做逐元素 oracle 比对。表达力阈值看的是“目标指令是否在 Triton 后端的 pattern 集合里”：wgmma、ldmatrix 的特定变体、异步拷贝的 commit/wait 组合，若后端不匹配，源码怎么写都生成不出来，此时唯一路径是下沉。

$$\text{下沉判据} = \big[\text{SOL}_{\text{upper}} - \text{SOL}_{\text{cur}} > \delta\big] \land \big[\text{bottleneck}_{\text{NCU}} \in \{\text{tensor},\ \text{issue}\}\big]$$

这个判据的工程含义是：只有当“上层已达到的 SOL 与理论上层可达的 SOL 之差超过阈值 δ”且“NCU 指认的瓶颈落在指令发射或 tensor pipe 而非带宽”时，下沉才被允许。δ 不写死数值，因为它随 shape 与 dtype 变化；口径是“用同一 shape 下已知最优实现作为 upper 参照”，而不是用文献数字。代价是每次下沉判断都要跑一次 NCU，这在多轮 RL 里是昂贵操作：一次 NCU profile 的时延远高于一次正确性比对，且会占用 GPU 导致采样吞吐下降。因此实践上把下沉判断放在候选筛选之后、精修之前，只对进入 top-k 的候选做 NCU，避免对全量候选做 profile。

具体例子：同一 softmax，Triton 版本在行宽不是 2 的幂时，编译器会生成带 mask 的冗余加载，SASS 中 LDS 条数多于手写版本；此时若 NCU 显示瓶颈在 issue 而非 DRAM，按判据应下沉到 CuTe 重写 layout 使行宽对齐，而不是直接跳到 PTX。反过来，若 NCU 显示 DRAM 已饱和，则 Triton 版本的冗余加载不是瓶颈，下沉只会增加编译时间而不改变 SOL，判据会拒绝这次下沉。

三 · warp specialization 的字段口径与代价

三层对 warp specialization 的支持差异，是速查表里最容易被误读的字段。Triton 没有原生的 producer/consumer warp group 表达，它的 pipeline 是编译器插入的，agent 无法指定“哪几个 warp 负责搬运、哪几个负责计算”；CuTe 可以用 layout 与 pipeline 组合表达分工，但需要手动把 copy 与 mma 的 atom 分配到不同 warp；PTX 则用 mbarrier 与 bar.sync 手工划分，控制最细也最易错。口径列写的是“是否存在独立的 producer warp group 分支”，这是一个可在 IR 或源码层面静态判定的条件，不需要跑 GPU。这个口径的意义在于：它把“是否支持 warp specialization”从模糊的“支持/不支持”变成可检查的结构条件，agent 可以用它做候选过滤。

代价体现在编译时间与正确性风险两侧。CuTe 表达 warp specialization 时，模板实例化数量随 warp group 数与 tile 形状组合增长，编译时间显著上升；在 RL 采样循环里，这意味着单位时间能评估的候选数下降。PTX 手工划分的代价是正确性风险：mbarrier 的 arrive/wait 配对写错不会导致编译失败，只会导致运行时的间歇性错误结果，必须靠重复执行与逐元素 oracle 才能捕获。因此速查表在这一字段旁标注“验证预算”：Triton 候选按低预算抽样验证，CuTe 候选按中预算做 layout 组合覆盖，PTX 候选按高预算做重复执行加全边界扫描。

具体例子：同一 GEMM，Triton 版本把流水深度作为 autotune 参数暴露，agent 只需搜索该参数；CuTe 版本需要把 copy atom 与 mma atom 分别绑定到不同 warp group，源码里出现显式的 role 分支；PTX 版本则要写 mbarrier 初始化、producer 的 arrive、consumer 的 wait 三段，任何一段的相位写错都会让结果在特定迭代次数后错位。三者的 SASS 差异体现在：Triton 生成的是编译器调度的流水，CuTe 生成的是按 layout 展开的固定分工，PTX 生成的是逐条可控的同步序列。

四 · 生成 SASS 差异的观测口径

速查表最后一组字段是“可观测中间层”，它决定 agent 能否在不跑 GPU 的情况下读到映射决策。Triton 的 TTIR/TTGIR 能看到 tile 形状与 layout 属性，但看不到最终的寄存器分配；CuTe 的 layout 类型在编译期就是源码的一部分，模板实例化后的类型名直接编码了 stride 与 swizzle；PTX 文本本身就是最细的观测层，SASS 只是它的下游。口径是“能否在不跑 GPU 的情况下读到映射决策”，这个口径把“可观测性”变成编译期可判定条件，而不是靠 profile 反推。

代价是观测层越深，读取成本越高。TTIR 是文本，解析成本低，适合 agent 做批量候选的静态筛选；CuTe 的 layout 类型需要编译器错误信息或模板调试工具才能读出，读取成本中等；PTX 文本可读但冗长，逐条比对指令序列的 token 成本高。在 agent 的上下文预算下，这意味着：广搜阶段只读 TTIR 做过滤，精修阶段才读 PTX 做指令级比对，中间层用 CuTe 的 layout 类型做过渡。这个分层读取策略直接对应速查表的字段顺序。

具体例子：同一 softmax，Triton 的 TTGIR 里能看到 block 级 layout 与 mask 的存在，但看不到 LDS 的具体条数；要确认冗余加载，必须下沉到 PTX 或直接看 SASS。CuTe 版本在源码里就把行内元素的 stride 写成编译期常量，冗余与否在类型层面即可判定，无需生成 SASS。PTX 版本则要逐条数 ldmatrix 与 lds 的出现次数，口径是“目标指令出现条数”，这是一个可自动化的静态计数，适合 agent 做候选排序。

五 · 速查表在 agent 循环中的插入位置

这张表不是给人读一次的文档，而是 agent 循环里的一个判定节点。它插入在“候选生成”之后、“正确性验证”之前：agent 先用字段列给候选打三层标签（Triton / CuTe / PTX），再用口径列决定该候选走哪条验证路径，最后用阈值列决定是否触发下沉。这个顺序的代价是：打标签本身需要读源码或 IR，消耗 token；但相比对全量候选跑 NCU，静态打标签的成本低一个量级。因此速查表的价值在于把“昂贵的 profile 判断”替换为“廉价的静态判断”，只在阈值触发时才付出 profile 成本。

具体例子：一轮 RL 采样出若干 GEMM 候选，agent 先按字段列识别出其中大部分是 Triton 候选，按口径列确认其线程映射由编译器推导，于是分配低验证预算；少数 CuTe 候选因源码中出现显式 layout 函数而被标为中预算；若某个候选的 TTIR 显示 tensor pipe 已饱和但 SOL 仍低于同 shape 的 upper 参照，阈值判据触发，agent 才对该候选跑 NCU 并决定是否下沉到 PTX 重写指令序列。整个循环里，速查表承担的是“分流”而非“评价”，评价仍由正确性 oracle 与 SOL 口径完成。

速查表：三层的失效边界与系统代价

这张表不是“选型推荐”，而是“失效判据”。每一行给出一个可观测字段、触发下沉的阈值口径、以及该层失效时的具体代价。字段必须能在编译产物或 profile 里直接读到，不能靠主观感受。以同一 GEMM/softmax 为例：Triton 层读 ttgir 里的 #blocked/#shared 布局属性与 num_warps；CuTe 层读 Layout 的 stride 与 MMA atom 的 Shape_MNK；PTX 层读 .reg 声明数、bar.sync 计数与 ldmatrix/stmatrix 的 .trans 修饰。阈值口径统一为“相对 roofline 的达成率”与“静态资源占用”两个维度，避免用绝对时延做跨层比较。

层观测字段下沉阈值口径失效代价
Tritonblocked 布局的 sizePerThread 与 shared 的 swizzle 位宽目标 MMA 的 fragment 布局无法由编译器自动推导，出现冗余 convert_layout共享内存往返与 bank conflict，带宽利用率跌破 roofline 拐点
CuTeMMA atom 的 K 维与 copy atom 的向量宽度不整除warp specialization 的生产者/消费者 tile 形状无法用单个 Layout 表达寄存器压力上升，occupancy 下降，编译期模板实例化时间膨胀
PTX.reg 数量、bar.sync 屏障粒度、cp.async 的 commit group需要手写 ldmatrix.trans 或非对称 barrier 才能匹配硬件 swizzleSASS 调度窗口受限，指令级并行被屏障切断，维护成本陡增

失效条件的判据可以写成一个比值：设目标 MMA 要求的 fragment 布局为 L_mma，编译器实际给出的布局为 L_gen，当 L_gen 到 L_mma 的转换需要跨越 shared memory 时，代价近似为

$$C_{conv} \approx \frac{2 \cdot |Tile| \cdot b}{B_{smem}} + N_{conflict} \cdot T_{cycle}$$
其中 |Tile| 是 tile 元素数、b 是元素字节、B_{smem} 是共享内存带宽、N_{conflict} 是 bank conflict 次数。这个式子说明：布局不匹配的代价不是“慢一点”，而是把一次寄存器级重排变成两次共享内存往返，直接吃掉 roofline 上本已紧张的带宽预算。softmax 场景同理，行内归约若被迫走 shared memory 做跨 warp 交换，时延由 log2(num_warps) 次屏障主导，而非算术本身。

具体例子：一个以 m16n8k16 为 MMA atom 的 GEMM，若 Triton 自动推导出的 blocked 布局 sizePerThread 与 atom 的 fragment 排布在 K 维上错位，ttgir 里会出现额外的 convert_layout，此时应下沉到 CuTe 用显式 Layout 把 copy atom 的向量宽度对齐到 atom 的 K 维；若连 CuTe 的单个 Layout 都无法同时表达生产者与消费者的 tile 形状（典型是 warp specialization 下 producer 用 cp.async 大 tile、consumer 用 MMA 小 tile），才需要 PTX 手写 bar.sync 的非对称屏障与 ldmatrix.trans。反向判据同样重要：若 L_gen 已等于 L_mma、convert_layout 计数为零、且 .reg 数量未触及 occupancy 拐点，则下沉只增加编译时间与 token 消耗，不带来任何 SASS 差异——此时应停在原层。

系统代价必须按层记账：Triton 层的代价主要在编译期布局搜索与可能的冗余转换；CuTe 层的代价是模板实例化带来的编译时间与寄存器压力，warp specialization 支持更细但要求 tile 形状在编译期完全确定；PTX 层的代价是正确性 oracle 的负担——手写屏障与 ldmatrix 修饰一旦与硬件 swizzle 不符，错误是静默的数据错位而非崩溃，必须靠逐元素比对或形式化检查兜底。因此速查表的用法是：先用字段定位失效点，再用公式估算转换代价，只有当估算代价超过该层可接受的带宽/时延预算时才下沉一层，且每次下沉都要把正确性 oracle 的粒度同步收紧一级。
