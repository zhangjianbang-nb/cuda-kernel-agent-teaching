一 · 条目是什么：失败模式的可判定定义

在《典型失败模式库》里，一个“条目”不是一段经验描述，而是一个可判定的四元组：触发条件（trigger）、可观测症状（symptom）、根因结构（root cause）、判定证据（evidence）。缺任何一项都不入库。判定证据是条目成立的门槛——它必须是一条能在不依赖人类直觉的前提下复现的观测，例如编译器退出码非零并给出特定诊断串、NCU 上某个 stall 原因占比异常、SASS 中某类指令计数为零、两次运行输出张量逐元素不一致。没有 evidence 字段的条目，本质上只是“传闻”，不能进入 agent 的检索与自检回路。

形式化地，把一次 kernel 生成-运行过程记为一个轨迹 τ，条目 E 定义为一个谓词：

$$E(\tau)=\mathrm{trig}(\tau)\wedge\mathrm{symp}(\tau)\wedge\mathrm{root}(\tau)\wedge\mathrm{evid}(\tau)$$

其中 trig 是静态可判定的（看源码、看编译命令、看 shape 与 dtype），symp 是运行时或编译时可采集的，root 是需要推理的结构性解释，evid 是可归档的证据指针。四者合取为真才判定“命中”。这个定义直接决定了库的工程形态：条目可以被写成断言，被 agent 在生成后自检阶段调用，也可以被评测流水线在回归阶段批量扫描。

代价必须写进条目本身。以“寄存器溢出”条目为例，它的 evidence 是编译产物中 local memory 相关统计非零、SASS 中出现 local load/store；它的代价字段记录的是溢出导致的额外显存流量与访存时延，以及由此带来的 occupancy 变化。条目如果不带代价字段，agent 就无法在“修掉它”与“接受它”之间做取舍——而真实工程里，很多失败模式的最优处置是接受并补偿，不是消灭。一个具体例子：某归约 kernel 在展开因子调大后出现溢出，症状是时延上升而非报错；若条目只写“溢出不好”，agent 会盲目回退展开因子，丢掉并行度收益；若条目写明“溢出把寄存器压力转成 local memory 流量，需与展开收益对比”，agent 才会去做两侧权衡。

二 · 分类维度：按可观测层而非按现象命名

失败模式最常见的错误分类法是按“现象”命名——报错、算错、慢。这种分类不可用，因为同一现象对应多个根因，同一根因在不同上下文呈现不同现象。本库采用按可观测层分类，四个维度正交组合：

  • 发生阶段：编译期 / 加载期 / 运行期 / 评测期。阶段决定 evidence 的采集点，编译期条目只需编译器输出，运行期条目必须挂 profiler。
  • 可观测通道：编译器诊断、运行时异常、数值比对、性能计数器、SASS 静态检查。通道决定条目能否被自动化，纯靠“看代码觉得不对”的条目一律降级为候选。
  • 确定性：必现 / 条件必现（依赖 shape、dtype、驱动版本）/ 概率性。概率性条目必须附带复现配方（重复次数、并发度、seed 策略），否则无法作为回归用例。
  • 影响面：正确性 / 性能 / 可移植性 / 可评测性。第四类最容易被忽略——评测环境漂移不改变 kernel 本身，却让所有对比数字失效。

四个维度构成一个坐标，条目在坐标上的位置决定了它的处置策略。举例：静默数值错误落在“运行期 × 数值比对 × 条件必现 × 正确性”，处置必须是 oracle 加严而非重跑；bank conflict落在“运行期 × 性能计数器 × 必现 × 性能”，处置是改数据布局而非改算法；autotune 过拟合落在“评测期 × 性能计数器 × 概率性 × 可评测性”，处置是换评测协议而非改 kernel。把三者混为一谈，会让 agent 在错误层级上做修改——用改算法的方式去修 bank conflict，或用重跑的方式去修数值错误，都是典型的处置错位。

维度组合还给出一个容量约束：库的条目数不应随现象数线性膨胀，而应随“可观测通道 × 根因结构”的组合增长。同一根因在不同阶段被观测到，应合并为一条并标注多通道 evidence，否则检索时会命中一堆同义条目，稀释 agent 的注意力预算——这是 token 成本层面的直接代价。

三 · 与相邻概念的三条边界

失败模式库与四个相邻概念经常被混淆，边界必须写清楚，否则库会退化成杂物间。

与“bug 清单”的区别：bug 清单是“发生过的事故记录”，条目是“可判定的谓词”。事故记录回答“上次谁踩了什么”，条目回答“给定这段代码和这份 profile，是否命中”。前者靠人读，后者靠程序判。因此条目必须写成可执行断言的形式，事故记录只能作为条目的 evidence 样例附在末尾。

与“反模式”的区别：反模式是编码风格层面的负面惯例（如无条件展开、滥用同步），它不保证导致失败；条目必须带触发条件与证据，命中即失败或即性能退化。反模式可以是一篇文档，条目必须是一条断言。二者关系是：反模式是条目的候选来源，条目是反模式的实证化。一个反模式若长期找不到可观测证据，就不应升级为条目。

与“正确性 oracle”的区别：oracle 是判定对错的基准（参考实现、区间容差、形式化规约），条目是“对错判定失败时，失败的结构性解释”。oracle 回答“是否错”，条目回答“为什么错、错在哪一层、怎么定位”。静默数值错误条目必须引用某个具体 oracle 的失效模式（例如容差过松掩盖了累加顺序差异），但条目本身不是 oracle。把两者混同，会导致 agent 在数值错误上反复加严容差而不去查根因——容差收紧只是让错误从静默变显式，不解决累加结构问题。

三条边界共同指向一个工程判断：条目是诊断资产，不是知识资产。它的价值在于被调用时能立刻缩小搜索空间，而不在于读起来有启发。因此条目的写作规范应偏向“字段完整、断言可执行、代价明确”，而非叙述流畅。

四 · 症状到根因的映射不是一对一

库的核心数据结构不是条目列表，而是症状-根因二分图。左侧是症状节点（编译失败、输出不一致、时延异常、occupancy 低、计数器异常），右侧是根因节点（类型不匹配、同步缺失、访存布局、寄存器压力、调度配置、评测协议缺陷）。一条边代表一个条目。图的度数分布决定了诊断难度：高度数症状（如“时延异常”）对应多条边，必须靠二级证据区分；低度数症状（如“编译期诊断串匹配”）几乎可直接定位。

诊断过程即图上的受限搜索：给定观测到的症状集合 S，候选根因是 S 的邻域交集。交集为空说明库有缺口，应记为“未归类失败”并进入候选队列；交集过大说明 evidence 粒度不够，需要补采集通道。这个机制的直接代价是采集成本：每增加一个通道（例如从只看退出码，到同时看 NCU 的 stall 分解），单次评测的时延与数据量都上升，且 profiler 本身会扰动被测 kernel 的时序。因此通道选择必须按症状度数分配——高度数症状才值得挂重通道。

一个具体例子：观测到“输出不一致”与“时延随并发度变化”两个症状同时出现，二分图上二者的邻域交集指向“同步缺失 / race condition”，而非“数值精度”。若只采集数值通道，agent 会去调容差；若同时采集并发度扫描通道，就能把候选收敛到同步类根因。这里 evidence 的增量成本是一次并发度扫描的运行时间，换来的收益是避免在错误根因上做无效修改——修改次数本身就是 token 与算力成本。

二分图还要求条目之间显式声明互斥与蕴含：寄存器溢出与 occupancy 塌陷常同时出现但前者可蕴含后者（溢出抬高寄存器占用从而压低 occupancy），此时不应作为两条独立根因重复计费；bank conflict 与访存布局错误是同一根因的两种观测，应合并。不做这层约简，agent 会在同一次失败上重复“修复”两个同源问题，产生虚假的改进信号。

五 · 条目字段规范与一个完整样例

每个条目固定八个字段，缺一不可：id、stage（阶段）、channel（观测通道）、determinism（确定性等级）、trigger（触发条件，写成可判定的谓词）、symptom（症状，附采集命令的语义描述而非具体命令）、root（根因结构，一段可推理的因果链）、cost（代价：时延 / 带宽 / 显存 / 编译时间 / token 中的一项或多项）、evidence（证据样例指针）。此外允许一个可选字段 dispose（推荐处置：修复 / 补偿 / 接受 / 换协议）。

以“评测环境漂移”条目为例，演示字段如何咬合：

字段内容
stage评测期
channel性能计数器 + 重复测量
determinism概率性，需固定复现配方
trigger同一 kernel 与同一输入，跨两次评测的指标差异超出测量噪声带
symptom排名翻转、加速比符号改变、方差显著大于基线方差
root时钟/功耗状态、并发负载、编译缓存命中与否、驱动或工具链版本差异，导致被测对象的实际执行配置与基线不一致
cost评测时延翻倍（需重复测量取稳健统计）、算力占用上升；若不做，则所有对比结论失效
evidence同配置重复运行的指标分布，与跨配置运行的分布对比
dispose换协议：固定测量配方、报告分布而非单点

这个条目的关键在于 trigger 写成了可判定谓词——“差异超出噪声带”，而不是“感觉不稳定”。噪声带本身由重复测量估计，这就把条目与统计规范绑定：条目不自带统计方法，只引用它。代价字段明确写出“不做则结论失效”，这是可评测性类条目的典型代价形态——它不消耗 kernel 的算力，却消耗整个评测流水线的可信度。

再看“编译失败”条目的字段咬合：trigger 是编译器退出码非零；symptom 是诊断串中的特定类别（类型不匹配、未定义符号、资源超限）；root 分为语法层与语义层，语义层最常见的是 dtype 与 shape 假设未在模板实例化时成立；cost 是编译时间与 agent 重试轮次的 token 消耗；evidence 是诊断串原文与最小复现代码。这里 dispose 通常是“修复”，但资源超限类编译失败（如静态共享内存超限）的 dispose 可能是“补偿”——改配置而非改代码。

六 · 分类的工程后果：检索、计费与缺口管理

分类维度不是学术装饰，它直接决定三件事的运行成本。第一是检索：agent 在自检阶段按症状集合查二分图，返回候选根因列表；列表长度即上下文注入量，直接对应 token 成本。维度设计得越正交，同一症状下的候选越少，注入越省。若分类按现象命名，检索会返回大量同义条目，token 成本上升而信息量不增。

第二是计费：多轮 RL 的可验证奖励需要区分“修对了”与“碰巧过了”。条目提供的是失败归因标签，奖励函数可以据此给“命中条目并被正确处置”更高权重，给“未归类失败但通过了”更低权重。没有条目分类，奖励只能看最终对错，无法惩罚“靠运气绕过失败模式”的轨迹。这里的代价是标注成本：每条轨迹都要跑一遍条目扫描，扫描本身消耗评测时延。

第三是缺口管理：二分图上邻域为空的症状集合就是库的缺口清单。缺口应按出现频次排序，高频缺口优先补条目，低频缺口允许长期存在。这个机制把“库的完备性”从主观判断变成可度量对象——缺口数量与命中率共同构成库的健康指标。一个具体工程判断：当某类症状反复出现却始终无法归入任何条目时，应优先怀疑 evidence 通道缺失，而非根因未知；补一个采集通道往往比补十条猜测性条目更有效。

最后落在条目与 agent 回路的接口上：条目在生成后自检、编译失败重试、评测回归三个环节被调用，每次调用返回的是“候选根因 + 推荐处置 + 代价估计”三元组，而非一段文字解释。这个接口形态决定了条目必须机器可读、字段完整、代价可比较——叙述性内容只能作为 evidence 的附注，不能作为条目的主体。库的演进方向因此不是“写得更全”，而是“断言更准、通道更省、缺口更少”。
