一 · 速查表的分层结构：字段、阈值、口径三段式

速查表不是指标清单的平铺，而是按“填什么—卡在哪—怎么算”三段切分。第一段是字段（field）：评测脚本必须落盘的键，缺一即视为报告不合规；第二段是阈值（threshold）：每个字段对应的通过/拒绝边界，边界必须写成可比较的表达式而非形容词；第三段是口径（caliber）：当同一字段存在多种测量方式时，指定唯一合法口径，其余口径只能作为诊断信息附注。三段之间是强约束关系：字段决定阈值的作用域，口径决定阈值能否被复现。工程上最常见的失效不是阈值定错，而是口径漂移——同一个 `latency_ms` 字段，一侧用 CUDA event 包住单次 launch，另一侧用 wall clock 包住含 host 同步的整段，两者相差一个数量级，阈值再合理也失去意义。因此速查表的每一行都应写成三元组 `(field, predicate, caliber)`，例如 `(p99_latency_ms, <= budget*1.05, cuda_event_around_kernel_only)`。这种三元组可以直接编译成评测脚本里的断言，也可以编译成审计时的 grep 模式，是速查表能“照着用”的前提。

$$\text{pass}(r)=\bigwedge_{i}\ \text{caliber}_i(r)\ \wedge\ \text{pred}_i(\text{field}_i(r))$$

代价在于：三元组越完整，评测脚本的维护成本越高。每增加一个字段，就要在训练侧与评测侧各写一次采集逻辑，并保证两侧不共享可变状态。以一次典型的多轮 RL 评测为例，若速查表含 18 个字段，单次评测的日志落盘量会从几十 KB 增长到数百 KB 量级，跨千次 rollout 后原始日志的存储与审计检索时延成为实际瓶颈；这不是正确性问题，而是评测吞吐的成本问题，需要在速查表里显式标注哪些字段是“必留原始”、哪些只需“留聚合”。

二 · 输入分布字段：形状、 dtype、稀疏度与种子

输入分布是速查表里最容易被写成“随机张量”四个字而实际不可复现的部分。合法字段至少包含：`shape`（含 batch 与 seq 维的完整元组）、`dtype`（含是否混合精度及累加类型）、`layout`（行主/列主、是否转置视图）、`sparsity`（若适用，给出非零比例与分布族）、`seed`（整数，且必须与 shape 绑定成 `(seed, shape)` 对）。阈值方面，形状不允许“同量级替代”：`(B,S,H)` 中任一维变化都会改变 tile 划分与 occupancy，因此速查表要求形状精确匹配，只允许在显式声明的 `shape_family` 内做等价类归并，且归并规则要写进表里。种子字段的阈值是“必须显式给定且非空”，禁止用时间戳或进程 ID 派生。口径上，随机数生成器族（如 Philox 与 MT 系列）必须固定，因为不同 RNG 的位序不同，同一 seed 产生的张量不同，正确性 oracle 的比对会整体漂移。

一个具体例子：某 kernel 在 `float32` 输入下通过，但评测侧用 `bfloat16` 生成输入而训练侧用 `float32`，累加误差被放大到容差之外，表现为“同一 kernel 两次评测结论相反”。这不是 kernel 的问题，而是速查表缺少 `dtype` 与 `accum_dtype` 的绑定字段。代价是显存的：混合精度输入使中间缓冲减半，但若速查表要求保留 fp32 参考输出用于比对，参考缓冲会额外占用一份全精度显存，在长序列场景下这部分开销不可忽略，需要在表里标注“参考输出可流式比对以省显存，但会引入同步点，增加端到端时延”。

三 · 容差与正确性阈值：绝对、相对与 ULP 三档

容差字段必须写成三档并存，而不是单一 `rtol`：`atol`（绝对误差）、`rtol`（相对误差）、`ulp_budget`（以 ULP 计的最大偏差）。判定式为逐元素 `|a-b| <= atol + rtol*|b|`，并对 NaN/Inf 单独设 `nan_policy`（拒绝或按位比对）。阈值的关键在于“按输出分布分段”：归约类输出（如 softmax 分母、layernorm 方差）在数值接近零时相对误差爆炸，必须回退到 `atol` 主导；而累加链长的输出应以 `ulp_budget` 为主，因为相对误差会随累加长度线性增长。速查表要求每个输出张量标注其“数值敏感类”（归约/逐元素/矩阵乘），并据此选择主导档位，禁止全表统一用 `rtol=1e-3` 糊过去。

$$\text{ok}_j=\bigl(|a_j-b_j|\le \text{atol}+\text{rtol}\,|b_j|\bigr)\ \vee\ \bigl(\text{ulp}(a_j,b_j)\le U\bigr)$$

口径上，参考实现必须与候选实现吃同一份输入位模式，且参考实现本身要在表里注明其累加顺序（是否用 Kahan 补偿、是否分块归约），因为参考的累加顺序决定了“真值”的偏差方向。代价是正确性验证的时延：逐元素三档判定在千万级元素上做全量比对，单次比对耗时可达毫秒量级，若每个 rollout 都全量比对，评测吞吐被比对本身吃掉；因此速查表允许“分层抽样比对 + 全量仅在失败时触发”，但必须写明抽样比例与触发条件，否则审计时无法复现结论。一个具体例子：矩阵乘输出在 `K` 维较大时，`ulp_budget` 设为个位数会误杀合法的分块归约实现，正确做法是把预算与 `K` 绑定成 `U(K)` 的表达式写进表里。

四 · 计时方法与硬件隔离字段

计时字段必须区分三种口径并各自独立成键：`kernel_time`（仅设备侧 kernel 执行，用 CUDA event 包夹，排除 launch 开销）、`launch_overhead`（host 侧提交到设备开始执行的时间）、`e2e_time`（含 host 同步与数据传输的端到端）。阈值上，`kernel_time` 用于与 roofline/SOL 对比，`e2e_time` 用于生产收益判断，两者不可互相替代。速查表要求每个计时字段标注 `warmup_iters`、`measure_iters` 与统计量（中位数或 p99），并规定 warmup 必须覆盖首次 kernel 加载与 JIT 编译，否则首个测量值被编译时间污染。硬件隔离字段包括 `device_id`、`clock_policy`（是否锁频）、`power_cap`、`mps_partition`（是否独占），阈值是“必须显式声明且评测期间不可变”，口径上要求评测进程与训练进程不共享同一 GPU 上下文。

代价体现在时延与显存两侧：锁频会降低峰值频率，使 `kernel_time` 系统性偏高，但换来跨次评测的可比性；不锁频则测量方差增大，p99 阈值需要放宽，放宽又削弱了阈值的判别力。独占分区（MPS）能消除邻居干扰，但分区后可用 SM 数减少，occupancy 上限下降，测得的 `kernel_time` 不能直接外推到整卡。一个具体例子：同一 kernel 在共享卡上测得 p99 抖动明显大于独占卡，若速查表未记录 `mps_partition` 字段，两次评测的差异会被误判为 kernel 回归。因此表里应把“隔离级别”作为一等字段，并规定跨隔离级别的结果不可直接比较，只能各自对照各自的基线。

五 · 结果上报格式与审计留痕字段

上报格式字段规定落盘结构与最小键集：`run_id`、`commit`（kernel 源码版本）、`config_hash`（编译 flags 与宏的哈希）、`seed_shape_pairs`、`metrics`（上述计时与正确性字段的聚合）、`raw_log_ref`（原始日志路径或内容寻址引用）。阈值是“键集完整 + 哈希可复算”：`config_hash` 必须能由落盘的编译参数独立重算，任何未纳入哈希的编译开关都视为口径漏洞。口径上要求评测脚本与训练侧隔离——评测进程不 import 训练侧任何可变模块，输入由评测侧独立生成或由只读快照提供，禁止训练侧在评测时注入缓存或预热状态。审计留痕的最小要求是原始日志不可被评测脚本自身覆写，且保留至少一次失败运行的完整日志，因为失败样本才是定位口径漂移的证据。

代价是存储与检索：保留原始日志使单次评测的落盘量上升，跨大规模 rollout 后审计检索需要索引结构，检索时延从秒级上升到需要批处理扫描；若改为只留聚合，则失败无法回溯，速查表的可信度归零。一个具体例子：某次评测报告 `kernel_time` 显著优于基线，审计发现 `config_hash` 未包含 `-use_fast_math`，该 flag 改变了除法的舍入行为，正确性档位被绕过；若速查表把编译 flags 纳入哈希并规定“哈希不一致即拒绝比较”，这类结论在落盘时就会被拦下，而不是在事后审计中才暴露。

六 · 阈值的可判别性与口径漂移的检测位

速查表最后要回答一个工程判断：给定阈值，它能否区分“真实回归”与“测量噪声”。做法是把每个阈值写成“基线 + 噪声带”的形式，噪声带由同一配置下的重复测量离散度决定，并在表里标注该离散度是单次评测内测得还是跨次测得。若阈值落在噪声带内，则该字段不具备判别力，必须降级为诊断字段而非通过条件。口径漂移的检测位应显式写进表：对每个计时字段保留一个“哨兵 kernel”（固定的小规模、计算量稳定的参考 kernel），其测量值随评测批次一同上报，哨兵值漂移超过噪声带即判定口径变化，整批结果作废重测。哨兵的代价是每次评测多一次固定开销的 launch 与测量，但换来的是跨批次可比性；没有哨兵，阈值只能在同一批次内比较，跨批次结论不可信。

具体机制上，哨兵 kernel 应选计算密度高、受显存带宽影响小的形态，使其对锁频与分区变化敏感、对输入规模不敏感，从而把“硬件状态变化”与“被测 kernel 变化”解耦。公式上可把判别条件写成哨兵偏差与噪声带的比较：

$$\text{drift}=\frac{|\,\text{sentinel}_{\text{batch}}-\text{sentinel}_{\text{ref}}\,|}{\sigma_{\text{ref}}}>\tau\ \Rightarrow\ \text{invalidate batch}$$

代价是评测轮次的实际时延增加，且哨兵本身若被训练侧缓存或预热，会失去检测能力，因此哨兵必须由评测侧独立启动、不共享上下文。一个具体例子：跨两次评测同一 kernel 的 `kernel_time` 相差数个百分点，若哨兵同步漂移同向，则判定为硬件状态变化而非 kernel 回归；若哨兵稳定而被测值漂移，才进入 kernel 层面的排查。速查表把这一判断写成一行可执行规则，比任何事后解释都更能约束评测结论的可信度。

速查表自身的失效边界：字段冻结、阈值漂移与口径污染

速查表要能“照着用”，前提是每个字段都有唯一写入方。工程上把表拆成三层：冻结层（输入分布标识、随机种子、硬件隔离档位、容差公式版本）只允许评测侧写入，训练侧只读；协商层（计时重复次数、warmup 轮数、显存上限）由两侧共同签署后落盘；观测层（原始日志路径、NCU 采集开关、上报字段顺序）由脚本自动填充，禁止人工编辑。失效条件很具体：一旦训练侧能改冻结层任一字段，容差就会被“调宽”到刚好通过，正确性 oracle 退化为自证。代价是每次评测多一次字段哈希校验与只读挂载，单次评测的固定开销落在毫秒级到秒级，相对于 kernel 编译时间可忽略，但相对于微秒级 kernel 的计时窗口不可忽略——因此校验必须放在计时区间之外，否则会把隔离成本算进 kernel 时延。

阈值漂移的根源是把“容差”当成一个数而不是一个函数。速查表应给出容差的形式而非定值：对浮点输出，逐元素判据写成相对与绝对混合的形式，其中相对项按输出量级缩放，绝对项兜住接近零的分量。

$$\text{pass}_i=\bigl|y_i-\hat y_i\bigr|\le \tau_{\text{abs}}+\tau_{\text{rel}}\cdot\max\bigl(|y_i|,|\hat y_i|\bigr),\qquad \text{pass}=\bigwedge_i \text{pass}_i$$

表里冻结的是 $\tau_{\text{abs}}$、$\tau_{\text{rel}}$ 与归约方式（逐元素全通过，还是允许按元素比例放行），而不是某个“通过率”。若把归约方式写成“误差均值小于阈值”，大误差会被大量小误差稀释，一个数值上完全错误的 kernel 也能过线；这是口径污染最典型的形态。代价体现在误放行上：一次误放行会让后续多轮 RL 把错误实现当作正样本，污染的是训练信号而非单次评测，修复成本远高于重跑。

计时口径的失效条件是“把不同隔离档位的结果混进同一张表”。硬件隔离档位必须与计时方法绑定：独占卡、MIG 切片、共享卡三种档位下，同一 kernel 的时延分布不同，速查表要显式标注每个档位允许的重复次数与统计量（最小值、中位数或分位数），并禁止跨档位比较。系统代价是重复次数乘以单次计时窗口：重复越多，方差越小，但评测墙钟时间线性增长；对编译时间长的 Triton/CuTe 变体，编译开销往往压过计时开销，此时应把编译时间单列上报字段，而不是折进 kernel 时延。具体例子：同一 reduction kernel 在独占档位取最小值、在共享档位取中位数，两者不可直接相减得出“隔离损失”，只能各自与同档位基线比。
