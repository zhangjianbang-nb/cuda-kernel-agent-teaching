一 · 回滚条目是什么：一次可执行的决策单元

在《回滚与降级清单》里，“条目”不是一句提醒，也不是一条监控告警，而是一个可执行的决策单元：它把“什么信号出现”“在哪个观测窗口内出现”“触发后切到哪个实现”“切换以什么粒度和顺序进行”“事后归档哪些证据”绑定成一条能被机器或值班工程师无歧义执行的记录。判断一段文字是不是条目，用一条操作性测试：把它交给一个不了解上下文的人，他能否在不追问的情况下完成触发判定与切换动作。做不到，它只是备注。

一个条目至少含五个字段：触发信号（指标 + 比较关系 + 阈值 + 观测窗口）、作用域（哪套 kernel、哪个 shape 区间、哪个部署环境）、回退目标（参考实现或上一稳定版本的精确标识）、切换协议（灰度比例、步进、观察期、自动或人工）、归档物（触发时刻的 profile、输入分布摘要、版本三元组）。其中“回退目标”必须是可寻址的实体，例如“仓库中 tag 为 ref-baseline 的朴素实现，编译选项固定为 -O3、无 fast-math”，而不是“退回原来的写法”。后者在事故现场无法执行，因为“原来的写法”在两周内已经被改过三次。

触发信号的形式化写法建议统一为四元组判定：

$$\text{trigger} = \big[\, m(t) \;\bowtie\; \theta \ \text{ for } \ t \in [t_0, t_0+W] \,\big] \wedge \text{scope}(s)$$

其中 $m$ 是度量，$\bowtie$ 是比较关系，$\theta$ 是阈值，$W$ 是观测窗口，$\text{scope}(s)$ 限定生效范围。四元组缺一不可：只写“错误率超过阈值”而没有窗口，单次抖动就会引发误回滚；只写窗口而没有作用域，一个 shape 分桶的精度漂移会误伤全部流量。代价在这里已经出现：窗口 $W$ 越长，误报越少但发现延迟越大，事故暴露面随时延线性增长；$W$ 越短，误报率上升，每次误回滚都要付出一次全量切换的时延代价与缓存/显存重分配开销。这是条目设计里第一个必须显式取舍的量。

具体例子：某 fused softmax kernel 上线后，条目写作“在 batch≥64 且 seq_len∈[512,2048] 的分桶内，连续 3 个统计周期（每周期 60 秒）的数值误差超阈值样本比例 > 0.5%，则将该分桶流量 100% 切回 ref-baseline 的逐元素实现”。这条记录可执行：分桶明确、窗口明确、目标明确。对照一条不可执行的写法：“精度有问题就回滚”——它既没有分桶也没有窗口，值班人无法判断“有问题”的边界。

二 · 三类触发指标：错误率、延迟抖动、精度漂移

条目按触发信号分为三类，三类的物理成因、观测手段与代价结构完全不同，混在一起写会导致阈值口径互相污染。

错误率类：包括 kernel 启动失败、非法内存访问、断言失败、结果与 oracle 比对不通过的样本占比。它的观测成本最低（多数可在宿主侧统计），但发现能力受限于 oracle 的覆盖面——oracle 没覆盖的输入分布，错误率恒为零，条目形同虚设。代价特征是“漏报代价高、误报代价低”，因此阈值应偏保守（宁可多切），窗口可短。

延迟抖动类：不是均值超标，而是分位数或方差在窗口内异常。成因通常是 occupancy 被寄存器压力压垮、shared memory bank 冲突随 shape 变化放大、或 L2 命中率因并发流量变化而塌陷。这类条目必须绑定 shape 分桶，因为抖动几乎总是分布相关的：同一 kernel 在小 shape 上稳定，在大 shape 上因寄存器溢出到 local memory 而出现长尾。观测依赖 NCU 的逐 kernel 指标与端到端分位数两条线并行，前者定位成因，后者判定是否触发。代价是采样开销：逐 kernel profile 会引入可观测的时延放大，因此条目要写明“仅在灰度桶开启细粒度采样，全量桶只统计端到端分位数”。

精度漂移类：输出与高精度参考（fp64 或 CPU 参考实现）之间的误差统计量随流量缓慢偏移，而非突变。典型成因是 fast-math 与 FMA 重排改变了累加顺序、Tensor Core 路径在不同 shape 下切换、或 reduction 的分块大小随 occupancy 自适应而变化。漂移类条目的难点在于“慢”：单次观测无法判定，必须用滑动窗口的统计量。判定式可写成对误差分布的偏移检测：

$$\text{drift} = \frac{\big|\,\mathbb{E}_W[e] - \mathbb{E}_{W_{\text{ref}}}[e]\,\big|}{\sigma_{W_{\text{ref}}}(e)} > \kappa$$

即以参考窗口的误差标准差为单位度量均值偏移。$\kappa$ 取值直接决定误报率，而每次误报的代价是一次回滚切换加上重新灰度的观察期——这段时间里新实现的收益归零，且团队注意力被占用。具体例子：某 reduction kernel 在 fp16 累加路径上，随着输入动态范围扩大，误差均值相对参考窗口偏移超过 3 倍标准差，条目触发，切回 fp32 累加参考实现；归档物中必须包含触发时刻的输入动态范围直方图，否则复盘无法区分“输入变了”与“kernel 变了”。

类别观测位置必须绑定的维度主要代价
错误率宿主侧 + oracle 比对输入分布覆盖漏报（oracle 盲区）
延迟抖动端到端分位数 + NCU 逐 kernelshape 分桶采样时延放大
精度漂移离线比对 + 在线抽样滑动窗口与参考窗口误报导致收益归零

三 · 分类维度之二：切换协议与灰度粒度

第二个分类维度是“怎么切”，它决定条目的执行代价与事故半径。按切换协议可分四档，档位之间不是精度差异，而是爆炸半径差异。

  • 硬切：一次性把目标作用域全部指向回退实现。执行最简单，但切换瞬间所有在途请求都要经历一次实现替换，若回退实现本身在目标 shape 上更慢，延迟会立刻抬升。适用于错误率类且作用域已被分桶收窄的情形。
  • 按比例灰度：以请求哈希或用户 ID 取模，把 $p$ 比例流量导向回退实现，按步进 $p \to p+\Delta$ 推进，每步有观察期。代价是双实现并存期间的显存占用翻倍（两套权重/中间缓冲同时驻留）与调度分支开销；收益是任何一步异常都可停在当前比例而不扩大。
  • 按分桶切：以 shape 分桶为单位整桶切换。粒度天然对齐抖动与漂移的成因，代价是分桶边界的选择本身需要证据——边界划错会把健康流量卷进回退。
  • 影子比对：不回退线上流量，而是把抽样请求同时送进两套实现，只比对输出与耗时，达到阈值才升级为真实切换。代价是额外算力与显存，收益是把“回滚”变成“先验证再回滚”，是精度漂移类条目的首选协议。

灰度比例与观察期的组合需要一条可计算的约束：设单步观察期内期望捕获的异常样本数为 $n = p \cdot r \cdot T$（$r$ 为请求速率，$T$ 为观察期），则 $n$ 必须大于判定所需的最小样本量，否则该步的判定没有统计意义。这条约束把“灰度 1% 观察 5 分钟”这类拍脑袋配置直接判为无效：样本不足时，条目要么延长观察期（拖慢回滚），要么提高起始比例（扩大爆炸半径），二者必选其一，必须写进条目而不是留给现场决定。

具体例子：某 attention kernel 的精度漂移条目采用影子比对协议，抽样比例 2%，观察期覆盖一个完整流量周期，比对统计量达标后才允许进入按比例灰度；归档物记录每一步的比例、观察期与实际样本数。这样复盘时能回答“是判定错了还是样本不够”，而不是只看到一条“已回滚”。

四 · 与相邻概念的边界：回滚、降级、熔断、禁用

四个词在事故现场经常被混用，但它们的决策对象不同，混用会导致条目写错字段。

回滚的对象是实现版本：把流量从新实现移回已知稳定的旧实现或参考实现，目标是恢复正确性与性能基线。它要求回退目标可寻址、可编译、可复现，因此条目必须携带版本三元组（代码 tag、编译选项、依赖库版本）。

降级的对象是功能档位：不换实现，而是降低精度、缩小 tile、关闭融合、跳过某些可选计算，用质量换稳定。降级的代价是精度或功能损失被显式接受，因此条目要写明降级后的精度下界与可接受的业务影响，而不是“先降级再说”。降级不要求回退目标存在，但要求降级路径本身经过验证——未验证的降级路径等于把事故换了个形态。

熔断的对象是调用链：在检测到下游持续失败时快速失败并短路，避免请求堆积放大故障。熔断通常不改变实现，只改变是否发起调用，因此它属于流量治理而非 kernel 版本治理；把熔断写进本清单会造成字段错配（没有回退目标、没有灰度比例）。

禁用的对象是特性开关：直接关闭某条优化路径（例如关闭某个 CuTe 布局的特化分支），回落到通用路径。它与回滚的差别在于作用域是特性而非版本，与降级的差别在于不承诺质量下界。

边界判定的操作性规则：条目若含“回退到某个可寻址实现”，归回滚；若含“降低某档质量并接受下界”，归降级；若既无回退目标也无质量下界，只是“停止调用”，那不是本清单的条目。这条规则的价值在于防止条目在复盘时无法归因：一次“回滚”若实际执行的是降级，复盘会误判根因为版本问题，而真实根因是精度预算不足。

具体例子：某 GEMM kernel 在特定 N 值上出现延迟抖动，团队先执行降级（缩小 tile 至不触发寄存器溢出的档位），抖动消失但吞吐下降；条目归档中同时记录降级档位与吞吐损失，并注明“未回滚，因为回退实现在该 N 上更慢”。这条记录让后续判断“是否值得为这个 N 单独做特化”有了依据，而不是把降级误记成回滚。

五 · 作用域与归档：条目的两个隐性字段

作用域字段决定条目的爆炸半径，归档字段决定条目能否被改进。二者常被省略，但省略后的条目在第二次触发时几乎必然失效。

作用域要写到“可独立切换的最小单元”。对 kernel 而言，最小单元通常不是整个算子，而是 shape 分桶 × 精度路径 × 部署环境的组合。写成“整个模型回滚”会把无关算子卷进来，代价是全量切换的时延与显存重分配；写成“所有 shape 回滚”会让健康流量承担回退实现的性能损失。作用域过窄的代价则是覆盖率不足：分桶边界之外的真实流量不受保护，事故仍会发生，只是不在条目的观测范围内。

归档字段至少包含：触发时刻的度量快照（含窗口与样本数）、触发时的输入分布摘要、两套实现的版本三元组、切换协议执行记录（每步比例与观察期）、以及回退实现的实测性能与精度。归档的目的不是留痕，而是让下一次条目修订有数据可依：阈值定得过高还是过低、窗口是否够长、分桶边界是否合理，全部只能从归档里反推。缺少归档的条目在第二次触发时只能重复同样的猜测。

代价在这里体现为存储与流程成本：每次触发都产生一份 profile 与分布摘要，若条目频繁误报，归档量会线性增长并挤占复盘带宽。因此条目应写明归档的保留策略与采样率——例如“仅保留触发前后各一个窗口的聚合统计，逐 kernel profile 按 1% 抽样保留”。这是条目设计里最容易被忽略、却在长期运行中最先暴露的成本项。

具体例子：一条延迟抖动条目在三个月内触发两次，归档显示两次的输入分布摘要几乎相同、而回退实现的实测延迟在第二次已高于新实现。复盘据此把条目从“回滚”改为“影子比对 + 降级”，并收窄分桶边界。若没有归档，这次修订无从发生，条目会继续执行一次收益为负的回滚。

六 · 条目与失败模式库、防作弊清单的分工

本清单与相邻清单的边界必须一次划清，否则同一现象会在三处被重复描述，而每处都写不深。

失败模式库回答“这类 bug 长什么样、如何从现象反推成因”，它的条目是诊断知识，不含阈值与切换动作。防作弊清单回答“评测时哪些行为会让数字失真”，它的对象是测量过程而非线上流量。本清单回答“线上信号达到什么条件时执行哪个动作”，对象是部署后的决策。三者的交集只应出现在引用关系上：本清单的条目可以引用失败模式库中的成因编号，用于归档归因；可以引用防作弊清单中的口径规范，用于保证阈值定义与评测口径一致。但条目本身不重复诊断步骤，也不重复口径定义。

分工的操作性检验：若一段文字在事故现场能直接执行，它属于本清单；若它需要工程师先做一轮分析才能得出结论，它属于失败模式库；若它约束的是离线测量而非线上流量，它属于防作弊清单。用这条检验可以快速判定一条新写的记录该放哪里，避免清单膨胀成什么都装的口袋。

具体例子：某条目写“触发后按失败模式库中‘寄存器溢出导致长尾’的成因编号归档，并按防作弊清单的误差口径重算漂移统计量”。这句话只做引用，不复述成因细节与口径细节，因此条目保持短小可执行，而深度留在各自模块。这也是本清单能维持“一条目一动作”的前提：深度靠引用，执行靠条目本身。
