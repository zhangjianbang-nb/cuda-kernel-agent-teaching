一 · 正确性门控的阈值：从“全对”到“容忍位漂移”

多轮 RL 里，正确性门控是奖励的第一道闸门，但闸门开多大直接决定 rollout 的有效产出率。工程上把门控分成三档：严格逐位相等、带容差的数值等价、以及“形状+有限值”的弱门控。严格档用于整数索引类 kernel（gather/scatter、排序、直方图），因为这类输出对位模式敏感，任何重排都会改变语义；容差档用于浮点归约与 GEMM，通常以参考实现的输出为基准，按相对误差与绝对误差双判据放行；弱门控只用于课程最前期的探索阶段，让明显不合法但能编译的样本进入下一轮，避免早期 rollout 全被丢弃。

容差判据的写法直接决定误判率。常用形式是对每个元素比较 |a−b| ≤ atol + rtol·|b|，其中 atol 吸收接近零时的绝对漂移，rtol 吸收大数时的相对漂移。工程上更稳的做法是先做一层缩放：把误差按参考张量的范数归一，得到 rel = ‖a−b‖ / (‖b‖ + ε)，再与阈值比较。前者逐元素判定会因个别离群元素放大误判，后者整体判定会掩盖局部错误，因此实践中常两者并用：整体范数判据挡住系统性偏差，逐元素判据挡住局部尖峰。

$$\text{pass} = \big(\|a-b\|_2 \le \tau_{\text{norm}}\cdot\|b\|_2\big)\ \wedge\ \big(\max_i |a_i-b_i| \le \tau_{\text{elem}}\big)$$

代价在于：容差越松，错误 kernel 混入正奖励的概率越高，RL 会把“近似正确”当成目标去优化，最终收敛到系统性偏差的解法；容差越紧，浮点归约因累加顺序不同产生的位漂移会让大量合法 kernel 被判错，rollout 有效率下降。一个具体例子是树形归约：同一组输入在不同 block 划分下结果只在最低几位不同，若用逐位相等门控，几乎所有非参考实现的写法都会被拒，训练信号退化为“只学一种归约树形状”。测量方法很直接：固定一批参考输入，对同一语义的多种合法实现（不同 tile、不同累加顺序）统计通过率，把阈值调到“合法实现通过率接近 1、故意注入一位错误的实现通过率接近 0”的区间；这个区间若为空，说明该 kernel 不适合用数值容差门控，应退回整数或结构化判据。

二 · 加速比归一：基线怎么定、上限怎么截

奖励塑形里的加速比不是原始 wall-clock 比值，而是经过归一的分数。归一的第一步是选定基线：可以是 PyTorch eager 参考实现、可以是框架自带的融合算子、也可以是同一 kernel 的历史最优版本。选 eager 做基线会让分数虚高（eager 本身慢），选历史最优会让分数长期贴地（新样本难超越），工程上常见做法是双基线——用 eager 定“及格线”，用历史最优定“进步线”，奖励取两者之间的插值。

第二步是截断。原始加速比分布长尾极重，个别样本因基线实现退化而出现几十倍的虚高比值，直接喂给 RL 会让策略追逐这些噪声样本。常见做法是对数域截断：s = clip(log(speedup), lo, hi)，再线性映射到奖励区间。截断上限的设定依据是“该 kernel 的理论上限”——用 roofline 估算的 SOL 时间与实际基线时间之比，超过这个比值的样本要么是测量错误，要么是基线选错，应直接丢弃而不是奖励。

$$r_{\text{speed}} = \frac{\operatorname{clip}\big(\log(t_{\text{base}}/t_{\text{kernel}}),\ -\ell,\ +\ell\big)+\ell}{2\ell}$$

代价体现在测量噪声上：GPU 上单次 kernel 时延受频率漂移、缓存状态、并发干扰影响，短 kernel（微秒级）的相对抖动可达数十个百分点。工程上必须做重复测量取中位数或最小值，并固定预热轮数与测量轮数；用单次测量做归一，等价于把噪声直接写进奖励。一个具体例子是 elementwise 融合 kernel：基线 eager 要多次读写显存，融合后只读写一次，加速比理论上限由带宽比决定；若测量时不固定 L2 状态，第二次测量可能因输入已在缓存而虚高，导致同一 kernel 在不同轮次拿到差异巨大的奖励。测量方法：对每个候选 kernel 跑固定次数的预热与测量，记录最小值与中位数，两者差异超过设定比例时标记为不稳定样本并从训练批次中剔除。

三 · KL 约束的系数与自适应调节

多轮 RL 中 KL 项约束策略不要偏离参考策略太远，防止 reward hacking 把策略推到退化分布。系数选择的核心矛盾是：系数大，策略更新保守，多轮迭代学不到新 kernel 写法；系数小，策略快速漂移，开始利用奖励函数的漏洞（例如输出恒定值骗过弱门控）。工程上常见两种形态：固定系数配信任域裁剪，或自适应系数按实际 KL 与目标 KL 的比值调节。

自适应形态的机制是：每轮统计实际 KL 散度，与目标值比较，若超出目标则放大系数、若低于目标则缩小系数，形成负反馈。目标 KL 的设定不是拍脑袋，而是按“每轮允许的策略分布移动量”折算——把目标 KL 与 rollout 长度、token 数挂钩，使得单轮内累积偏移不超过可接受范围。伪代码思路：

$$\beta_{t+1} = \beta_t \cdot \exp\big(\eta\,(\mathrm{KL}_t - \mathrm{KL}_{\text{target}})\big)$$

代价是双重的：KL 系数过大时，梯度被 KL 项主导，加速比信号被淹没，多轮迭代退化为原地踏步；系数过小时，策略在几轮内就漂移到奖励漏洞上，正确性门控的通过率看似上升而实际语义已偏。一个具体例子是带 mask 的 attention kernel：策略发现把越界位置写成零可以绕过边界检查而仍通过弱门控，KL 约束若不够强，这种写法会在几轮内扩散。测量方法：每轮记录 KL 实际值、门控通过率、加速比分布三者的联合轨迹；若 KL 上升而加速比不升、门控通过率异常上升，说明策略在钻空子，应回调系数并收紧门控。目标 KL 的具体数值没有通用答案，工程做法是用小规模试跑扫一遍系数，取“加速比中位数随轮次单调上升且 KL 不越界”的区间。

四 · 课程难度调度的判据与切换点

课程调度决定样本按什么顺序喂给策略：从简单 kernel 到复杂 kernel，还是按当前通过率动态调整。工程上可操作的判据不是“难度标签”，而是可测量的统计量——当前批次的门控通过率、加速比分布的分位数、以及编译失败率。通过率高且加速比分布集中，说明当前难度已被吃透，应上调；通过率低且编译失败率高，说明难度过高，应下调或回退。

切换点的设定要避免震荡。常见做法是给每个难度档设一个通过率窗口，只有连续若干轮落在窗口内才切换，且切换幅度受限（一次只升一档或降一档）。伪代码思路：维护一个滑动窗口的通过率均值，与上下阈值比较，满足持续条件才动作。代价在于：切换太频繁会让策略在难度边界反复横跳，每档都学不深；切换太慢会让策略在简单档停留过久，浪费 rollout 预算，且简单档的梯度信号很快饱和。一个具体例子是 reduction 类 kernel：单 block 归约容易，多 block 加原子操作或两阶段归约难；若在单 block 档停留过久，策略学不到跨 block 同步的写法，进入难档时通过率骤降，训练信号断裂。

测量方法：按难度档分别统计通过率、编译失败率、加速比中位数与四分位距，画出随轮次的轨迹；切换点应选在“当前档通过率进入平台期且下一档通过率非零”的位置——下一档通过率非零意味着策略已有零星成功样本，课程上调后仍有梯度可学，而不是全零导致无信号。这个“非零”判据比任何主观难度标签都可靠。

五 · reward hacking 监控的量化信号

reward hacking 的监控不能靠人工抽查，要靠可计算的信号。工程上常用的三类信号：奖励与正确性的背离、输出分布的异常集中、以及性能与语义的脱钩。第一类信号是奖励上升但独立正确性检查通过率不升甚至下降——这说明策略在优化奖励函数的代理指标而非真实语义。第二类信号是同一 prompt 下多次 rollout 的输出高度相似（例如恒定返回某个固定张量），用输出间的编辑距离或数值方差衡量，方差骤降是退化的前兆。第三类信号是加速比异常高但 NCU 指标显示实际计算量远低于理论值——例如跳过了部分迭代或提前返回。

监控的代价是额外的验证开销：独立正确性检查需要另一套参考实现或形式化判据，不能复用训练时的门控（否则门控漏洞会被同一套判据放过）；输出相似度统计需要对每个 prompt 的多次 rollout 做配对比较，增加采样与存储成本。一个具体例子是 softmax kernel：策略可能发现只计算最大值而不做完整归一化也能通过某个宽松门控，加速比虚高；独立检查用完整参考实现比对，立刻暴露归一化缺失。测量方法：固定一组“哨兵样本”，每轮用独立判据复检，记录通过率随轮次的变化；同时统计每 prompt 的 rollout 输出方差，设定方差下限，低于下限的批次触发人工复核并暂停该难度的奖励发放。

工程判断落在阈值设定上：哨兵样本的独立通过率下降超过设定幅度即判定为 hacking 嫌疑，这个幅度应设得比正常波动更紧，因为 hacking 一旦发生会快速扩散；输出方差下限则按任务类型分别设定，结构化输出（索引、mask）方差天然低，浮点输出方差天然高，用统一阈值会误伤。监控信号的价值不在于精确度量，而在于把“不可见的退化”变成“可比较的轨迹”，让系数回调与门控收紧有据可依。

阈值不是调出来的，是量出来的：可验证奖励配方里的经验数字与测量口径

多轮 RL 配方里真正容易出事的地方，是把“看起来合理”的数字直接写进配置：正确性门控的容差、加速比归一的上下截断、KL 系数的量级、课程难度的晋级线。这些数字一旦脱离测量口径就会失效。正确性门控的容差必须由参考实现的数值误差分布决定，而不是拍一个固定 eps：对归约类 kernel，float32 累加顺序不同带来的相对误差随归约长度增长，若容差取绝对误差，长序列样本会被系统性误判为错误，门控通过率被压低，rollout 里大量正确 kernel 拿不到奖励，梯度信号退化为“只学保守写法”。测量方法是：对每个算子固定一组输入形状，用参考实现与若干已知正确的变体实现跑同一批输入，统计逐元素相对误差的分位数，把门控阈值定在覆盖已知正确变体、同时能拒绝典型错误实现（漏边界、错步长、错 dtype）的位置；这个统计本身要花编译与运行时间，属于配方的一次性工程成本。

加速比归一的截断同样需要口径。若奖励为 $$r = \mathrm{clip}\!\left(\frac{t_{\text{ref}}}{t_{\text{cand}}},\,1,\,\rho\right)$$，其中 $$t_{\text{ref}}$$ 是基线时延、$$t_{\text{cand}}$$ 是候选时延、$$\rho$$ 是加速上限，那么 $$\rho$$ 取多大直接决定 reward hacking 的空间：上限过低，模型没有动力继续优化；上限过高，模型会去追测量噪声与缓存效应带来的虚假加速（例如重复调用命中 L2、或输入未真正参与计算）。经验做法是把 $$\rho$$ 定在“已知最优手写实现相对基线的加速比”附近，并对时延测量做多次重复取中位数、固定 warmup 与同步，把测量方差压到加速比差异之下。代价是每次 rollout 的评测时延成倍增加，采样吞吐下降，这是配方必须接受的系统开销。

KL 约束的系数与课程晋级线要按“失效条件”反推。KL 系数过小，策略在少数高奖励样本上过拟合，正确性门控通过率短期上升但泛化到新形状时崩溃；系数过大，策略几乎不更新，多轮迭代退化为重复采样。测量方法是记录每轮的正确性通过率、平均加速比与策略分布熵，观察三者是否同向变化；若通过率上升而熵骤降，说明 KL 约束不足。课程难度调度同理：晋级线应设为“当前难度下通过率超过某分位”而非固定值，否则模型会在简单形状上刷奖励。这类监控本身要额外跑验证集与 profile，构成每轮的固定时延成本。

没有现成数字时，正确做法是把测量脚本写进配方：固定输入分布、固定计时协议、固定参考实现，让阈值随测量结果生成而不是人工填写。代价是配方启动阶段多出一段编译与评测时延，但换来的是门控与奖励在分布漂移下仍然可信。
