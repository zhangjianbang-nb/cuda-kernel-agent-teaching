二 · 表头字段：一行一条 rollout 记录的最小闭包

速查表的第一层不是数字，而是字段定义。算力与成本估算表的最小可计算单元是「一条 rollout 记录」，它必须同时闭包三件事：这次 rollout 在什么硬件上、花了多少机时、产出了多少可用信号。字段缺失任何一项，后面的单价乘法和吞吐外推都会失真。建议固定为九列：gpu_model、usd_per_hour、compile_s、run_s、ncu_mult、profile_s、tokens_in、tokens_out、verdict。前两列是价格口径，中间四列是时间口径，后三列是信号口径。

时间口径的关键在于把「编译」和「运行」拆开。编译时间对 CUDA C++ 与 CuTe 是重尾分布，模板实例化与 nvcc 的 ptxas 阶段会随 kernel 复杂度非线性增长；Triton 的 JIT 首次编译同样不可忽略，但缓存命中后趋近于零。运行时间则是 kernel 本体加 launch 开销。把两者合并成一个 kernel_s 字段，会让「编译贵但跑得快」和「编译便宜但跑得慢」两类样本在预算表里无法区分，而这两类在优化决策上完全相反。

profile 开销不能用一个固定常数糊过去，必须显式建模为倍数。ncu 在采集完整指标集时会对 kernel 做 replay，同一 kernel 被反复执行以分轮收集不同 counter 组，实际耗时是裸跑的若干倍。速查表用 ncu_mult 表示这个倍数，profile_s = run_s × ncu_mult。这个字段的意义在于：它让「是否开 profile」变成一个可算的预算开关，而不是默认全开。

$$\text{cost}_{\text{rollout}} = \frac{\text{usd\_per\_hour}}{3600}\left(\text{compile\_s} + \text{run\_s} + \text{run\_s}\times\text{ncu\_mult}\cdot\mathbb{1}_{\text{prof}}\right) + \text{token\_cost}$$

这里的 token_cost 是 LLM 侧的输入输出 token 按模型单价折算的钱，与 GPU 机时是两条独立成本线。工程上常见的错误是把 token 成本摊进 GPU 单价里，导致换模型时整张表失效。举个具体例子：一个 CuTe 的 GEMM kernel，编译 40 秒、裸跑 3 秒、开 NCU 后 3×4=12 秒，若单价按小时计，则单次 rollout 的 GPU 成本主要被编译吃掉——这时优化方向是编译缓存与模板裁剪，而不是 kernel 本身。字段拆开才能看见这个结论。

三 · 阈值列：把连续量切成决策档位

速查表要「可直接照着用」，就必须给每个字段配阈值，把连续测量切成离散档位。阈值的作用不是评价好坏，而是决定下一步动作：继续采样、开 profile、放弃该样本、还是升级到形式验证。建议每个时间字段配两档阈值：warn 与 abort。超过 warn 记一次告警但仍计入统计，超过 abort 直接终止该 rollout 并记为无效样本，避免长尾样本拖垮整批吞吐。

字段口径warn 触发动作abort 触发动作
compile_s冷编译，不含缓存命中标记「编译主导」，检查模板实例化数量终止，记 compile_timeout
run_skernel 本体 + launch，不含同步等待标记「运行主导」，进入 roofline 粗判终止，记 run_timeout
ncu_multprofile 耗时 / 裸跑耗时缩减 metric 集，只采关键 counter关闭 profile，仅保留计时
tokens_out单次 rollout 生成 token 数检查是否陷入重复生成截断，记 token_overflow
verdict正确性 oracle 结论—fail 样本不进性能统计

阈值的口径必须写死，否则同一张表在不同机器上不可比。compile_s 明确为冷编译，意味着每次测量前清空 Triton 缓存与 nvcc 的中间产物目录；若允许缓存命中，编译时间会塌缩到接近零，阈值失去意义。run_s 明确不含同步等待，意味着计时区间只包住 launch 到 kernel 结束，不含 cudaDeviceSynchronize 之外的 host 侧开销。这两个口径不写清，跨型号对比就是自欺。

代价体现在统计功效上：abort 阈值设得越紧，无效样本越多，单批有效样本数下降，均值的置信区间变宽。设得越松，长尾样本吃掉机时，单位预算产出的有效 rollout 数下降。这是一个吞吐与统计稳定性之间的直接权衡，没有免费档位。具体例子：若 compile_s 的 abort 阈值卡在某个值，一个模板爆炸的 CuTe 样本会被直接丢弃，省下机时，但也丢失了「这类写法编译代价高」这一条对 agent 有用的负反馈——所以 abort 样本仍应记录字段值，只是不进性能均值。

四 · 单价与吞吐：每小时单价如何转成每有效样本成本

条目给定的核心字段是「按 GPU 型号给出每小时单价」。速查表里这一列不能只写单价，必须与吞吐绑定才有决策价值。定义单位预算的有效样本产出率为：

$$\text{valid\_per\_usd} = \frac{3600}{\text{usd\_per\_hour}}\cdot\frac{1}{\mathbb{E}[\text{sec\_per\_valid\_rollout}]}$$

分母的期望秒数要按有效样本重算，而不是按全部 rollout 平均。因为 fail 样本、abort 样本、token 溢出样本都消耗了机时却不产出可用信号，把它们计入分母会系统性高估产出率。速查表因此需要两个派生列：sec_per_rollout（全部样本平均）与 sec_per_valid（仅 verdict 通过且未 abort 的样本平均）。两者之比就是「有效率」，它本身也是一个应该被监控的阈值字段。

不同 GPU 型号的单价差异会直接改变策略选择。高价型号的单位机时贵，但单次 rollout 的编译与运行秒数可能更短，尤其在 kernel 规模较大、寄存器压力高、需要更多 SM 并行的场景下。速查表不预设哪类型号更划算，而是把 usd_per_hour、compile_s、run_s 三列并排放，让读者自己算 valid_per_usd。工程判断落在：当编译时间占比高时，换更贵的卡几乎不改善成本，因为编译是 CPU 侧与 ptxas 的工作，GPU 单价被浪费；当运行时间占比高且 kernel 受算力限制时，换卡才可能摊薄单位成本。

具体例子：某型号单价高、但运行秒数短，若 compile_s 占单次总秒数的一半以上，则该型号的 valid_per_usd 反而低于便宜型号。这类结论只能从拆开的字段里读出来，合并成「单次 rollout 秒数」就看不见了。代价是表格列数增加、维护成本上升，但这是让预算规划可复算的必要开销。

五 · token 成本列：与机时正交的第二条成本线

条目明确要求「全流程 token 成本」。速查表必须把 token 拆成 tokens_in 与 tokens_out 两列，因为输入侧包含 prompt、执行反馈、NCU 摘要、编译错误日志，输出侧包含 kernel 代码与解释文本，两者的单价通常不同，且随多轮交互累积。全流程意味着不是单轮：一次 rollout 可能包含生成、编译失败、读错误、重写、再编译、跑 profile、再改，每一轮都追加 token。

$$\text{token\_cost} = \sum_{t=1}^{T}\left(\text{in}_t\cdot p_{\text{in}} + \text{out}_t\cdot p_{\text{out}}\right)$$

速查表里应有一个 rounds 列记录交互轮数，因为 token 成本随轮数近似线性增长，而机时成本随轮数增长得更快（每轮都要重新编译与运行）。这两条成本线的相对斜率决定了优化重点：若 token 成本主导，应压缩反馈文本、只回传结构化错误码与关键 NCU counter，而不是整段日志；若机时成本主导，应压缩编译与 profile 开销。把两者混成一个「总成本」列会掩盖这个判断。

代价是反馈压缩会损失信息。把编译错误日志截断成错误码，agent 可能无法定位模板参数不匹配的具体位置，导致多跑一轮，反而增加总 token 与机时。速查表因此需要一个 feedback_bytes 字段配合阈值：超过阈值时触发摘要而非截断，摘要本身也消耗 token，但比整段日志便宜。具体例子：一个 Triton kernel 因 tl.load 的 mask 形状不匹配报错，完整日志可能很长，摘要成「mask 维度与 pointer 维度不一致」只需少量 token，agent 据此改写通常一轮收敛；而只给错误码则可能两三轮才收敛。这个权衡必须写进表里，而不是留给读者临场猜。

六 · 口径锁定：跨型号、跨批次可比的前提

速查表最后要锁死三类口径，否则不同人填的表无法合并。第一是计时口径：compile_s 为冷编译、run_s 不含 host 同步、profile_s 含 replay。第二是样本口径：哪些样本计入 sec_per_valid，哪些只记录不入均值，abort 与 fail 的区分标准。第三是价格口径：usd_per_hour 是挂牌价还是含抢占/闲置折算的实际价，是否含存储与网络。这三类口径应在表头注释里以固定枚举值出现，而不是自由文本。

一个常被忽略的口径是 NCU 的 metric 集。ncu_mult 高度依赖采集的 counter 组数：只采 sm__cycles_elapsed 与 dram__bytes 这类少量 counter 时倍数低，采完整 SpeedOfLight 与内存层级细分时倍数高。速查表应把 ncu_metric_set 作为 ncu_mult 的伴随字段，否则同一个倍数在不同 metric 集下不可比。这直接关系到 profile 预算：全量 profile 的机时开销可能数倍于裸跑，而它换来的 roofline 定位精度是否值得，取决于当前是「不知道瓶颈在哪」还是「已知瓶颈、只需验证」。

具体机制上，建议把速查表做成两张联动表：一张是「字段—阈值—口径」定义表（本部分给出的结构），另一张是「型号—单价—秒数—倍数」的实测填充表。前者稳定、版本化管理；后者随机器与驱动更新而变，每次变更需重测冷编译与 profile 倍数，因为编译器版本与 NCU 版本都会改变这两个量。工程判断落在：定义表是契约，填充表是快照，混在一起修改会让历史预算无法复算。跨批次比较时，只允许在定义表版本一致的前提下进行，否则 valid_per_usd 的差异里混入了口径漂移，无法归因到 kernel 或 agent 策略本身。

速查表的失效边界：单价、秒数与倍率在什么条件下不再可乘

这张表最容易被误用的地方，是把“每小时单价 × 单次 rollout 秒数 × 次数”当成线性预算公式。它只在三个口径同时成立时才可乘：单价对应的是同一张卡的同一计费粒度（按秒计费还是按小时向上取整），rollout 秒数里已经含了编译，且 NCU profile 开销倍数只作用于被采样的那部分 rollout。任一条件破裂，乘积就要改写。设单卡小时价为 $$P$$，单次 rollout 的编译加运行时间为 $$t_c+t_r$$，采样比例为 $$s$$，profile 开销倍数为 $$k$$，则一轮 $$N$$ 次 rollout 的真实卡时是 $$T=N\big[(t_c+t_r)+s(k-1)(t_c+t_r)\big]$$，成本为 $$P\cdot T/3600$$。注意 $$k$$ 乘的是整段 rollout 而不是仅 kernel 执行段——NCU 会重放 kernel、串行化、关闭部分并发，编译阶段不受影响但运行阶段被整体拉长，把 $$k$$ 只贴到 kernel 时间上会系统性低估。举例：某型号单价按小时计、rollout 为编译加运行若干秒、每若干次采样一次 profile，若把 $$k$$ 误当成只作用于 kernel 的百分之几，预算会明显偏低；反之若把 $$s$$ 当成 1，又会把 profile 开销放大到全量，得出“profile 不可用”的错误结论。

速查表的第二类失效来自 token 成本与卡时成本的耦合方式。全流程 token 成本由生成、修复、验证三段构成，其中修复轮的 token 数取决于编译错误与正确性失败的反馈长度，而反馈长度又取决于是否把 NCU 指标、SASS 片段、diff 一起塞进上下文。表里给的 token 数是“一次通过”的口径，多轮 RL 场景下必须按轮数展开：若首轮通过率为 $$p$$，最多 $$R$$ 轮，期望 token 近似为 $$\frac{1-(1-p)^R}{p}\cdot L$$（$$L$$ 为单轮 token），这个式子对 $$p$$ 极敏感——$$p$$ 从高位掉到中位，期望轮数接近翻倍，而卡时只按实际执行的轮数计。于是“token 预算够、卡时预算不够”和反过来的两种失衡都会出现，速查表必须把两者分开列，不能合并成一个“单次成本”。代价面同样要写清：把 NCU 指标塞进上下文提升修复率，是以每轮 token 变长为代价换取 $$p$$ 上升，净收益取决于 $$p$$ 的提升是否跑赢 $$L$$ 的增长。

第三类边界是“按 GPU 型号给单价”这件事本身的粒度问题。同一型号在不同集群、不同计费模式（独占、抢占、spot）下单价差异远大于型号间差异，而 rollout 秒数对显存带宽、SM 数量、L2 大小敏感，对主频不敏感；因此表里按型号分行只在“同型号同计费模式”内可横向比较。跨型号比较必须换成单位有效工作量成本，即每完成一次正确且达到目标加速比的 rollout 的成本，而不是每次 rollout 的成本。失效条件是正确性 oracle 的通过门槛变化：门槛提高会同时压低通过率、拉高期望轮数、拉长 profile 采样需求，三项同向恶化，此时旧表的每一格都偏低。工程判断上，速查表应标注“适用门槛”与“采样比例”两列，缺这两列的表格只能用于量级估算，不能用于承诺交付预算。

最后一条边界是时间口径的可加性：编译时间与运行时间的比例在不同 kernel 上差异极大，小 kernel 编译占主导、大 kernel 运行占主导，把两者合并成一个秒数会让“优化编译”和“优化运行”的收益无法归因。速查表若要支撑吞吐规划，至少要把编译秒数与运行秒数分列，并注明 profile 采样是否触发重编译。否则在编译占主导的样本上，任何针对运行时的优化都测不出收益，预算表会把钱花错地方。
