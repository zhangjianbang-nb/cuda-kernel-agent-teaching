一 · 速查表的结构：字段、阈值、口径三分法

这张表不是“工具介绍”，而是把选型决策压缩成可执行的判据。每一行代表一个候选工具，每一列代表一个必须回答的问题。字段分三类：能力字段（表达力、可移植性、调试可见性）、代价字段（编译时延、显存/带宽开销、token 成本）、判据字段（阈值与口径）。阈值不是拍脑袋的门槛，而是“超过它就换工具”的临界点；口径则是“这个数字怎么量”的定义，避免两个团队拿不同测量方式互相说服。

速查表的使用方式是自上而下过滤：先用表达力字段排除根本写不出来的工具，再用编译时延与调试可见性排除迭代成本过高的工具，最后用性能上限与可移植性在剩下的候选里做取舍。任何一格填“定性”而非数字，都意味着该字段在当前工程阶段不可测量，必须标注为待定而不是默认通过。

$$\text{选型得分} = w_e E + w_p P + w_d D - w_c C - w_t T$$

其中 E 为表达力、P 为性能上限、D 为调试可见性，C 为编译时延、T 为 token/人力成本。权重由项目阶段决定：探索期 w_c 高，收敛期 w_p 高。这个公式的用途不是算出一个绝对分数，而是强迫团队把权重写下来——权重分歧往往就是选型分歧的真正来源。

具体例子：一个 agent 在生成 flash-attention 变体时，若候选 Triton 版本编译时延低于阈值但表达力不足以写出 warp 级流水，则 E 项直接判零，无需进入加权计算。这一步省掉的是后续数轮无效 RL 采样的 token 开销。

二 · 表达力与性能上限：阈值怎么定

表达力的判据是“目标 kernel 是否需要工具无法表达的控制”。CUDA C++/nvcc 的表达力上限是完整的线程/共享内存/同步原语；Triton 以块级抽象为边界，warp 级调度与显式 barrier 不在其语言模型内；CuTe/CUTLASS 以 layout 与 tiled copy 的组合表达数据搬运，能覆盖多数 GEMM 类结构但对非规则访存需要绕行；PTX 内联与 NVRTC 则把控制权交回给写作者，代价是可移植性与调试可见性。

性能上限的阈值应写成“相对 roofline 的达成率”，而不是绝对 TFLOPS。口径：以目标 shape 下的 SOL 时间为分母，实测时间为分子，达成率低于某阈值即判定该工具在此 shape 上不适用。这个口径的好处是与硬件代际解耦，换卡后阈值仍然有效。

工具表达力边界性能上限判据主要代价
CUDA C++/nvcc全控制流与同步原语可达 SOL 高位，受寄存器压力约束编译时延随模板膨胀上升
Triton块级，无显式 warp 调度规则访存下接近 SOL，非规则访存掉档编译时延低，调试可见性弱
CuTe/CUTLASSlayout 组合表达搬运GEMM 类可达高位，非规则需手写模板实例化编译时延高
PTX 内联/NVRTC指令级，需自行保证正确性上限最高，但依赖写作者水平可移植性差，调试几乎不可见

具体例子：同一 reduction kernel，Triton 在规则 stride 下达成率高，但换成跨步访存后带宽利用率下降，此时应判定表达力不足而非调参不足——继续在该工具内调参只会消耗采样 token 而不改变上限。

三 · 编译时延与迭代成本：agent 循环里的硬约束

对 agent 而言，编译时延不是“等待时间”，而是“每轮反馈的固定税”。多轮 RL 的采样预算按轮计，编译时延直接决定单位 token 能换来多少次执行反馈。阈值应设为“单次编译时延占单轮预算的比例”，超过该比例则工具在 agent 循环中不可用，无论其性能上限多高。

口径：编译时延取冷编译的墙钟时间，不含缓存命中；缓存命中率单独作为字段记录，因为模板重实例化会让冷编译时延剧烈波动。CUDA C++ 的模板膨胀与 CuTe 的实例化是主要来源；Triton 的编译时延低但每次 shape 变化都可能触发重编译；NVRTC 把编译搬到运行时，把时延从构建期转移到执行期。

$$\text{有效采样率} = \frac{1}{t_{\text{gen}} + t_{\text{compile}} + t_{\text{exec}} + t_{\text{verify}}}$$

分母中任何一项变大都会稀释采样率。工程判断：当 t_compile 超过 t_exec 一个量级时，应优先考虑把该工具移出内循环，只在收敛阶段做最终验证。

具体例子：agent 对同一 GEMM 反复改 tile 参数，若每次改动都触发 CuTe 模板全量实例化，则单轮预算被编译吃光，正确性 oracle 的调用次数骤减，RL 信号稀疏到无法学习。此时正确做法是把参数搜索放在编译时延低的工具里做粗筛，再用高表达力工具做终选。

四 · 调试可见性与正确性代价

调试可见性的判据是“出错时能否定位到源码行与指令”。CUDA C++ 有完整的符号与行号映射；Triton 的中间表示与生成代码之间存在映射断点，越界与竞态往往表现为数值错误而非崩溃；PTX 内联的错误定位到指令级，几乎无法回溯到高层意图。可见性低的工具，其正确性验证成本必须计入选型，而不是事后补救。

口径：正确性代价用“定位一次失败所需的平均验证轮数”衡量，而非“是否通过”。这个口径承认可见性差的工具可以通过更强的 oracle 补偿，但补偿本身消耗预算。形式验证与差分测试在此扮演的角色是降低对可见性的依赖，但不能消除。

  • 可见性高：错误可映射到源码行，单轮定位。
  • 可见性中：需对照生成代码与 IR，多轮定位。
  • 可见性低：只能靠输入扰动与不变量断言缩小范围。

具体例子：Triton 生成的 kernel 在边界 tile 上出现静默错误，由于无法直接读到生成的 PTX，验证器只能靠构造边界 shape 的差分测试来暴露问题；这比在 CUDA C++ 里加一行 assert 昂贵得多，代价应体现在选型表的正确性列。

五 · 可移植性与部署口径

可移植性的判据不是“能否编译”，而是“换架构后是否需要重写”。CUDA C++ 与 Triton 在架构迁移上主要面临性能调优而非语义重写；PTX 内联则把架构细节写死，迁移即重写；CuTe 的 layout 抽象在一定程度上吸收架构差异，但 tile 选择仍需按架构重调。口径：以“迁移后达到原达成率所需的人工/采样轮数”计量。

部署端还要区分编译期与运行期：NVRTC 把编译放到部署机上，首帧时延与显存占用都会上升，适合 shape 动态但调用频次低的场景；AOT 编译则把成本前置到构建流水线。这个取舍在端到端收益核算里必须单列，不能混进 kernel 本身的性能数字。

字段口径阈值用法
编译时延冷编译墙钟，不含缓存占单轮预算比例超限即出内循环
性能上限相对 SOL 达成率低于阈值判表达力不足
调试可见性定位失败所需验证轮数轮数超限则需加强 oracle
可移植性迁移后恢复达成率所需轮数轮数超限则锁定架构

具体例子：同一 agent 产出的 kernel 在训练集群与推理集群之间迁移，若使用 PTX 内联写死指令，迁移成本等于重写；若使用 Triton，迁移成本主要是重调 tile 与 num_warps，采样轮数可控。选型表应把这一列填成轮数区间而非“好/差”。

六 · 速查表落地：字段填写的纪律

这张表最容易失效的方式是字段被填成形容词。纪律有三条：第一，每个数字必须带口径注释，否则跨团队比较无效；第二，阈值必须写成可判定的不等式，而不是“较高/较低”；第三，任何一格填“待测”都必须附带测量计划，否则该工具默认不进入候选集。

判据字段的优先级应随项目阶段调整：探索期把编译时延与 token 成本放在前列，收敛期把性能上限与可移植性放在前列。这个优先级本身应写进表头，让读表的人知道当前权重，而不是让每个读者自行猜测。

具体机制上，建议把表做成“每行一个工具、每列一个判据”的矩阵，并在矩阵下方附一行“当前项目权重”。当权重变化时，只改这一行而不改矩阵，选型结论随之更新。这样做的代价是维护成本，收益是避免每次讨论都从头复述定义。

工程判断落在最后一条：当两个工具在加权得分上接近时，选编译时延更低且调试可见性更高的那个，因为 agent 循环的迭代次数是稀缺资源，而性能上限的差距往往可以通过后续手工优化弥补。这条判断不依赖任何实验数字，只依赖对预算结构的认识。

速查表：字段、阈值与口径的落地边界

这张表不是“哪个工具更好”的排名，而是把选型判断压缩成可核对的字段：每个字段都要能在构建日志、profile 报告或正确性回归里找到对应证据，否则该行结论视为未验证。字段口径统一为四列——表达力（能否直接写出目标数据流与同步语义）、编译时延（从源码变更到可执行 kernel 的墙钟时间，含模板实例化与 PTX 汇编）、可移植性（跨 SM 架构与驱动版本的可运行范围）、调试可见性（能否在 SASS/PTX 层定位问题，以及错误信息是否指向源码行）。阈值不设“大概”，只设可观测的判定点：编译时延以交互式迭代能否在一轮对话内完成为界；可移植性以是否依赖特定架构指令或 CUTLASS 版本为界；调试可见性以是否能拿到寄存器级与指令级证据为界。任何一行若三项以上落在“不可观测”，就应降级为实验性方案，不得进入生产路径。

失效条件集中在两类边界。其一是模板与内联的膨胀边界：CuTe/CUTLASS 的表达力来自类型级布局代数，代价是每个 tile 形状组合都会实例化一份新 kernel，编译时延随组合数近似线性增长；当布局参数进入运行时分支而非编译期常量时，表达力优势立刻退化为调度开销。其二是 PTX 内联与 NVRTC 的版本边界：内联 PTX 绕过 nvcc 的部分优化与寄存器分配，性能上限取决于手写指令序列与目标 SM 的匹配度，一旦架构换代，指令可用性与调度规则变化会让原本的最优序列失效；NVRTC 把编译搬到运行时，换来的是部署侧无需预编译全部变体，但首次调用时延与 JIT 缓存管理成为新的系统代价。判定公式可写成：若 编译时延 × 迭代轮次 > 单轮对话预算，则模板重型方案不适合作为 agent 的首选探索工具；若 运行时 JIT 时延 > 服务冷启动容忍度，则 NVRTC 只能用于离线变体生成而非在线路径。

系统代价必须按资源口径记账，不能只记“快”。显存侧，CuTe 的静态布局与流水线 stage 数直接决定 shared memory 占用，stage 增加会挤压 occupancy；带宽侧，Triton 的自动调度在归约与转置类形状上可能引入额外搬运，需以 NCU 的 dram 吞吐与 L2 命中率核对；编译时间侧，nvcc 的模板深度与 PTX 内联的汇编往返都会拉长构建，agent 多轮尝试时这部分时延会累积成 token 预算外的隐性成本；调试侧，PTX 内联的错误往往表现为非法指令或静默数值偏差，缺少源码行映射，定位代价高于 Triton 的 IR 级报错。一个具体例子：同一 GEMM 变体在 Triton 下改 tile 只需改常量并重编译，在 CUTLASS 下改 tile 形状会触发新的模板实例化，构建时间从秒级进入分钟级，而运行期收益需用 SOL 口径的 roofline 距离来证明是否值得这笔编译开销。

字段判定口径失效信号主要代价
表达力目标数据流能否在源码层直接表达布局参数落入运行时分支调度开销、寄存器压力
编译时延单次变更到可执行 kernel 的墙钟模板组合爆炸、汇编往返多轮迭代的隐性时延
可移植性跨 SM 与驱动版本可运行依赖特定指令或库版本变体维护与回归成本
调试可见性能否取得 SASS/PTX 级证据无源码行映射、静默偏差定位时延、正确性风险

速查表之外的三个边界条件

速查表能回答“默认选谁”，但回答不了“什么时候这张表失效”。第一个失效条件是编译时延进入迭代回路：nvcc 对模板密集的 kernel 做全量编译，单次改动触发的重编译会打断 agent 的多轮采样节奏，此时应把 PTX 内联或 NVRTC 的运行时编译作为探索期通道，代价是丢失编译期常量折叠与部分寄存器分配优化，性能上限被压低。第二个失效条件是跨架构可移植性要求：Triton 的块级抽象把布局与流水交给编译器，代价是当目标形状或 dtype 落在其 lowering 覆盖之外时，会静默退化为低效路径，正确性仍在但 SOL 利用率骤降；CuTe/CUTLASS 则以显式 layout 与 tiled copy 换确定性，代价是模板实例化带来的编译时间与二进制膨胀。

第三个边界是调试可见性。PTX 内联与 NVRTC 让源码与 SASS 之间多了一层运行时拼装，NCU 采集到的指令地址难以反查源码行，正确性 oracle 失败时定位成本上升。可用一个粗粒度判据约束选型：设探索期单次编译时延为 $$T_c$$，单轮 agent 采样预算为 $$B$$，当 $$T_c \cdot N_{\text{iter}} > B$$ 时，编译期开销已吞掉采样预算，应切换到运行时编译通道，把省下的时延换成更多候选 kernel 的验证次数。

失效信号处置主要代价
重编译打断多轮采样NVRTC / PTX 内联丢失编译期优化，性能上限下降
形状/dtype 超出 Triton loweringCuTe/CUTLASS 显式 layout编译时间与二进制体积上升
SASS 无法反查源码回退 nvcc 保留 lineinfo编译时延回升

具体例子：一个以固定 tile 形状做 GEMM 的候选，在 Triton 下写法最短、验证最快，但若目标 dtype 组合触发退化，profile 显示带宽利用率远低于 roofline 预期，此时速查表的“默认 Triton”判断必须让位于 CuTe 的显式布局控制——选型表的每一行都应附带一个可观测的失效信号，而不是只给推荐项。
