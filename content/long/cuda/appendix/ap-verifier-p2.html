二 · 速查表：字段、阈值、口径

本表面向“拿到一个 kernel 就能立刻填”的场景：每一行给出一个检查项、它必须记录的字段、判定阈值（或阈值形态）、口径（即这个阈值在什么语义下成立），以及漏检时最典型的代价。表内不解释基础定义，只给可执行参数。所有阈值分三类写法：绝对阈值（如 0 ulp）、相对阈值（随 dtype/规模缩放）、形态阈值（不是数值，而是“必须覆盖哪些集合”）。填表时字段一律落盘为结构化记录，避免只留一句“已通过”。

检查项必填字段阈值 / 判定形态口径漏检代价
数值容差比对dtype、累加 dtype、参考实现版本、atol、rtol、比较算子（绝对/相对/混合）、ulp 距离相对阈值：rtol 随 dtype 位宽收缩；fp32 累加链上 atol 需按归约长度缩放；混合判据 |a−b| ≤ atol + rtol·|b|逐元素、在参考值非零处生效；归约类 kernel 需按分段长度给出分段阈值把“数值漂移”误判为“算法错误”，或反之放过真实偏差

三 · 阈值怎么定：从 dtype 与归约长度推

容差不是拍脑袋常数。对归约类 kernel，误差随累加长度增长，阈值必须写成规模的函数，否则长序列上必然误报。一个可落地的口径是：设单次运算的相对误差上界为 ε（由 dtype 位宽决定），归约长度为 n，则最坏情况相对误差按 n·ε 量级增长，实践中取

$$\mathrm{rtol}(n) = c \cdot \sqrt{n}\cdot \varepsilon,\qquad \mathrm{atol}(n) = \varepsilon \cdot \max_i |b_i|$$

其中 c 是由累加策略（串行、树形、分块）决定的常数，树形归约的 c 明显小于串行。字段里必须同时记录 n 与累加策略，否则同一 rtol 在不同实现间不可比。对 fp16 输入、fp32 累加的混合精度 kernel，阈值应基于累加 dtype 而非输入 dtype 推导，输入 dtype 只影响单次乘法的舍入。代价侧：把 rtol 收得过紧会让正确实现被判错，触发无意义的返工轮次；放得过松则让真实偏差通过，两者都消耗评测预算。具体例子：长度恰为 tile 整数倍加一的 tail 用例，若阈值按满 tile 长度推导，tail 段的短归约会被过松阈值掩盖，因此分段阈值必须按实际参与归约的元素数计算，而不是按分配到的 buffer 长度。

四 · 输入覆盖的形态阈值与代价

随机与边界输入的价值不在数量，而在“是否触发了不同的代码路径”。字段设计上，每个用例应携带一个路径标签（如 vectorized 主循环、tail 分支、广播分支、掩码分支），通过率按路径聚合而非按用例总数聚合。形态阈值可写成：每条路径至少被一个用例命中，且 tail 路径必须由“长度 mod tile ≠ 0”的用例命中。伪代码思路：

$$\text{coverage} = \frac{|\{\text{paths hit}\}|}{|\{\text{paths in kernel}\}|},\quad \text{gate}: \text{coverage}=1 \ \wedge\ \text{tail hit}$$

代价体现在 token 与编译时间两侧：为覆盖非连续 stride，需要构造额外的 stride 元组并可能触发不同的模板实例化，编译时间上升；为覆盖重尾分布，需要生成大幅值输入，可能触发溢出路径从而暴露真实的 NaN 处理缺陷。具体例子：一个按 128 元素 tile 向量化的 kernel，若用例集只有 256、512 这类整数倍长度，vectorized 主循环覆盖率满分而 tail 分支覆盖率为零，此时通过率再高也不构成正确性证据。因此速查表把“tail 命中”列为独立布尔字段，而不是混在“边界输入”里一句话带过。

五 · NaN/Inf 与位模式口径

NaN 的比较必须绕开数值相等语义。字段里记录“期望语义”三选一：传播（NaN 进则 NaN 出）、屏蔽（NaN 视为 0）、饱和（Inf 截断到有限最大值）。判定时对 NaN 位置使用位模式比较，对 Inf 使用符号位加指数位比较，其余位置走容差判据。混合判据需改写为分段形式：

$$\text{pass}_i = \begin{cases} \text{bits}(a_i)=\text{bits}(b_i), & b_i \text{ is NaN/Inf}\\ |a_i-b_i|\le \mathrm{atol}+\mathrm{rtol}|b_i|, & \text{otherwise}\end{cases}$$

口径上有一条容易踩的坑：参考实现若默认把 NaN 传播，而被测 kernel 按算子契约应屏蔽，则差分 oracle 会稳定报错，此时错的是 oracle 的语义假设而非 kernel。因此 oracle 字段必须显式声明语义，并与 kernel 契约对齐后才允许作为判据。代价：NaN 用例通常只占极小比例，但一旦漏检，下游梯度或统计量被污染且难以回溯到具体 kernel；反之若对 NaN 位置也套用容差判据，比较结果恒为假，会把正确实现误判为失败，浪费整轮返工。

六 · 确定性、SMT 与差分 oracle 的适用边界

确定性复跑的阈值是 0 位差，但它的口径必须绑定配置：固定 grid/block、固定归约树、禁用非确定性原子路径。字段中记录“确定性声明范围”，换配置即失效。代价是复跑本身消耗额外时延，尤其在长序列归约上翻倍；因此工程上常把确定性检查放在小规模用例上做位级比对，大规模只做容差比对，两者结论分开记录，不得互相替代。

SMT 验证的字段核心是“已验证输入域”。对定点或小位宽整数 kernel，可对输入域做全枚举或符号执行，结论是域内无违反；对浮点 kernel，需以位级编码或定点抽象建模，抽象误差单独记账，域外输入一律标为未验证。伪代码思路：先固定循环展开上界 k，把数组读写编码为带界约束的选址表达式，再对断言“输出等于规格”求反求解；不可满足即域内通过。代价是求解时间随展开深度与位宽指数上升，超时预算必须写进字段，超时的用例记为“未验证”而非“通过”。具体例子：一个 8 位量化的逐元素 kernel 可在全输入域上完成 SMT 验证，而同一结构的 fp32 kernel 只能验证若干代表性位模式组合，两者结论强度不同，速查表用“域”字段把这一差别显式化。

差分 oracle 的适用边界在于“不同源”。字段要求记录参考实现的来源与调用路径，并先对 oracle 自身跑一遍自检用例；若 oracle 与被测 kernel 共享同一份模板或同一段归约代码，差分恒通过而无信息量。代价是维护两套实现的编译与运行开销，且 oracle 版本漂移会引入假阳性。工程判断上，差分 oracle 适合覆盖形状与 stride 组合的广度，SMT 适合覆盖小域内的深度，确定性复跑适合捕捉并发与归约顺序问题；三者字段与口径不可互换，速查表把它们并列而非合并，正是为了让每条结论的适用范围在记录层面就锁死。

速查表的失效边界：容差口径、输入覆盖与代价三角

速查表最容易出问题的地方不是字段缺失，而是字段被当成绝对判据。数值容差比对的核心是三元组（rtol, atol, 比较域），三者必须同时记录，缺一即不可复现。常见失效是只记 rtol 而忽略 atol：当参考值接近零时相对误差爆炸，任何 rtol 都判失败；反之只记 atol 则在量级大的张量上放过系统性偏差。工程上应把判据写成逐元素形式 $$|a_i-b_i| \le \mathrm{atol} + \mathrm{rtol}\cdot|b_i|$$ 并在表中固定“以谁为基准”（通常是 CPU 高精度参考或 float64 上采样结果），否则交换 a、b 会得到不同结论。代价侧要写清：容差放宽一档，漏检率上升但复跑成本不变；容差收紧则误报率上升，每次误报都要人工或差分 oracle 复核，直接吃掉 token 预算与验证时延。一个具体例子：归约类 kernel 的输出在尾部有少量元素因累加顺序不同而产生 1 ulp 级差异，若 atol 设为 0，速查表会把完全正确的实现判为失败，迫使 agent 反复“修复”一个不存在的 bug。

随机与边界输入这一栏必须区分“覆盖形状”和“覆盖数值分布”两件事。形状与 stride 覆盖要显式枚举：非连续 stride、广播维度、长度为 1 的退化维、非 2 的幂尺寸、跨页边界的尾块；这些是越界写与掩码错误的唯一暴露途径，随机连续张量几乎必然漏检。数值分布则要单独列 NaN/Inf 处理口径：是“传播一致”（输入含 NaN 则输出必须含 NaN 于对应位置）还是“拒绝”（断言输入有限），两种口径下的 oracle 完全不同，混用会让差分 oracle 把正确实现判错。代价在于输入枚举是组合爆炸：形状维度的笛卡尔积乘以 dtype 乘以分布，单次验证的 kernel 启动次数随时延线性增长，GPU 侧空闲等待与主机侧同步开销会主导小 kernel 的验证时间。表中应给出“必测最小集”而非全集，例如固定三档尺寸加两类 stride 变体，把剩余预算留给确定性复跑。

确定性复跑与形式化 SMT 验证在速查表里属于不同信任层级，不能共用一栏阈值。确定性复跑的口径是“同输入、同配置、多次启动输出逐位一致”，它捕捉的是原子操作顺序、非确定归约、未初始化显存读取；其失效条件是硬件与驱动层的非确定性来源（如某些原子实现、动态并行调度）使复跑本身不稳定，此时应把该 kernel 标记为“不可复跑验证”，转而依赖差分 oracle。SMT 验证的边界更硬：它只对可编码为位向量或线性算术的小规模片段有效，遇到浮点超越函数、循环上界依赖运行时的 kernel 直接不可判定，表中应写明“适用规模上限”与“编码失败即降级”的处置，而不是给一个通过率。代价上，SMT 编码与求解时间随展开深度快速增长，一个中等规模的向量化 kernel 编码可能耗时数分钟到数十分钟，远超一次 GPU 复跑；因此速查表应把 SMT 放在“发布前一次性门禁”而非“每轮 RL 奖励”路径上，避免把求解时延计入 agent 的每步反馈。

字段口径失效条件主要代价
rtol/atol逐元素、固定基准侧参考值近零误报→复核 token
形状/stride 集最小必测集随机连续张量启动次数×时延
NaN/Inf传播或拒绝，二选一口径混用差分 oracle 误判
确定性复跑逐位一致，N 次硬件非确定源复跑显存与时间
SMT规模上限+降级浮点/动态上界求解分钟级

差分 oracle 是速查表里唯一同时承担“漏检兜底”和“误报仲裁”的角色，其口径必须写清参照实现的来源与版本，否则同一 kernel 在不同参照下结论相反。它的失效条件是参照本身有 bug 或与目标实现的语义约定不同（如归约的累加精度、舍入模式），此时差分只能证明“两者不同”，不能证明“谁错”。工程判断是：把差分 oracle 放在容差比对失败之后触发，而不是替代容差比对；触发后记录两侧中间张量摘要，用少量 token 定位首个偏离元素，避免全量 dump 撑爆显存与上下文。速查表最终要表达的边界是——每个字段都对应一种可被绕过的漏检路径，阈值不是精度承诺，而是“在该口径下我愿意接受的复核成本”。
