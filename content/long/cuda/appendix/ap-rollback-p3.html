一 · 阈值的三层来源：契约、硬件与统计噪声

工程阈值的第一个来源是契约层：kernel 对外承诺的语义与精度。回滚判定必须先区分“契约违反”与“性能不达标”。契约违反是硬阈值，例如输出与参考实现逐元素比对超出容差、NaN/Inf 出现、越界写、非确定性导致的不可复现差异。这类阈值不设“百分比容忍”，一旦触发即回滚，因为下游可能已经把错误结果写进了持久化状态。契约层的阈值由正确性 oracle 给出，具体比对方法与容差口径属于正确性验证器清单的范畴，此处只强调：回滚清单里的契约阈值必须是可执行的布尔判定，而不是“精度看起来还行”的主观描述。

第二个来源是硬件层：roofline 给出的理论上限。任何延迟阈值若不锚定在 SOL 上，就只是拍脑袋。设某 kernel 的算术强度为 $I$（FLOP/Byte），机器峰值算力 $P_{\text{peak}}$、峰值带宽 $B_{\text{peak}}$，则理论最短时间为

$$T_{\text{SOL}} = \max\left(\frac{W}{P_{\text{peak}}},\ \frac{Q}{B_{\text{peak}}}\right)$$

其中 $W$ 为总浮点工作量、$Q$ 为总访存量。工程上把回滚的延迟阈值设为 $T_{\text{SOL}} \times k$，$k$ 是“可接受的低效倍数”。$k$ 的取值不是常数，它取决于该 kernel 在端到端链路中的占比：占比越高，$k$ 越紧。这个 $k$ 必须写进清单并附上测量方法，否则灰度期间两拨人对“慢”的判断会不一致。

第三个来源是统计噪声：延迟抖动阈值必须相对于测量本身的方差来设定。单次 kernel 计时在 GPU 上受时钟波动、L2 残留、并发流干扰影响，重复测量的分位数才有意义。设 $n$ 次采样的第 $p$ 分位数为 $L_p$，则抖动阈值可写成 $L_{99}/L_{50} \le r$，$r$ 为清单登记的比值上限。$r$ 的合理性依赖于采样次数 $n$：$n$ 太小时 $L_{99}$ 本身不可信，此时应改用 $L_{95}$ 或增大 $n$。清单里应同时登记 $n$、分位口径与预热策略，这三项缺一不可，否则阈值不可复现。

二 · 常见阈值的量纲与判定形式

回滚清单里的阈值必须带量纲和判定形式，否则无法自动化。下表给出四类阈值的判定形式与代价来源，数字列留空处表示“由测量确定”，不填占位数字。

类别判定形式量纲主要代价
错误率失败样本数 / 总样本数 > $\epsilon$比例验证 token 与重跑时延
延迟抖动$L_{99}/L_{50} > r$ 或 $L_{99} > L_{\text{base}} \times m$比值采样次数 × 单次计时
精度漂移与参考实现的相对误差 > $\delta$，或分布 KL > $\kappa$无量纲参考实现常驻显存
资源越界峰值显存 > 预算，或占用 SM 数 > 上限字节 / 计数并发度下降

错误率阈值 $\epsilon$ 的关键在于分母的定义。分母是“本次灰度窗口内经过该 kernel 的全部调用”，还是“抽样验证的调用数”，两者语义完全不同：前者是生产事故率，后者是验证覆盖率。清单必须写明分母，并写明抽样率。抽样率过低时，$\epsilon$ 的置信区间宽到无法支撑回滚决策；此时正确做法不是放宽 $\epsilon$，而是提高抽样率或延长观察窗口，代价是验证 token 与端到端时延的增加。

精度漂移的判定比错误率更微妙。逐元素容差只能抓住“明显错”，抓不住“系统性偏移”。后者需要用分布级指标：对同一批输入，比较优化实现与参考实现的输出统计量（均值、方差、分位点）或散度。设参考输出分布 $P$、优化输出分布 $Q$，用

$$D_{\mathrm{KL}}(P \,\|\, Q) = \sum_{x} P(x)\log\frac{P(x)}{Q(x)}$$

作为漂移度量。代价是：为算这个量，参考实现必须在灰度期间保持可调用状态，意味着额外显存与额外算力；若参考实现本身是慢路径，这笔开销会直接体现在灰度窗口的成本里。工程判断是：只在灰度期开启分布级比对，全量上线后降级为抽样逐元素比对。

三 · 经验数字怎么来：测量协议而非拍脑袋

“经验数字”在工程书里最容易被写成玄学。这里给出可执行的测量协议，任何团队照做都能得到自己的数字，而不是抄别人的。

  • 基线采集：在目标硬件、目标驱动、目标并发度下，对参考实现与候选实现各跑 $n$ 轮，记录每轮的 $L_{50}$、$L_{95}$、$L_{99}$ 与峰值显存。轮与轮之间必须插入冷却或固定预热，否则第一轮受时钟爬升影响会污染分位数。
  • 方差归因：把总方差拆成三份——测量噪声（同一实现重复跑的离散度）、实现差异（候选与参考的均值差）、负载差异（不同输入形状带来的离散度）。只有当“实现差异”显著大于“测量噪声”时，延迟阈值的收紧才有意义。
  • 阈值反推：先定可接受的误回滚率（把好实现误判为坏的概率）与漏回滚率（把坏实现放过），再据此选分位数与倍数。误回滚率高会让灰度反复中断，代价是发布周期；漏回滚率高会让错误进入生产，代价是正确性。
  • 登记：把 $n$、预热策略、分位口径、硬件型号、驱动版本一并写进清单条目。缺任何一项，该阈值在另一台机器上就不可复现。

一个具体例子：某归约 kernel 的候选实现比参考实现快，但 $L_{99}$ 明显更高。若只看均值就放行，长尾请求会被拖慢；若只看 $L_{99}$ 就回滚，则放弃了均值收益。正确做法是把判定写成“均值改善且 $L_{99}/L_{50}$ 不超过登记比值”，两个条件同时满足才放行。这里的比值不是猜的，是按上述协议在目标硬件上测出来的。

编译时间也是需要登记的经验数字。Triton 与 CuTe 的编译/实例化开销会进入灰度窗口的端到端时延，尤其是首次调用触发 JIT 时。清单应记录“冷启动编译耗时”与“热路径耗时”两个数，并把冷启动排除在延迟阈值之外单独判定——否则每次灰度第一批请求都会误触发抖动告警。

四 · 没有数字时：把“怎么测”写进清单

很多 kernel 在首次上线时没有任何历史数据，此时清单不能留空，而要写测量处方。处方至少包含四项：测什么、在哪测、测多少、判定谁。

测什么：明确是端到端时延还是 kernel 自身时延。前者包含 launch 开销、数据搬运与同步，后者只含 device 侧执行。两者阈值不可混用，因为 launch 开销在小 kernel 上占比可能极高。用 CUDA event 夹住 kernel 区间得到的是后者；用请求到达至响应返回的时间戳得到的是前者。

在哪测：必须写明是否在与生产同构的硬件与并发度下测。单流空载测出的延迟不能直接用于多流并发场景，因为 L2 与带宽被其他流挤占。处方里应写明并发流数、是否开启 MPS、是否与其他 kernel 共存。

测多少：给出最小采样数 $n_{\min}$ 与预热轮数。$n_{\min}$ 的选取原则是让目标分位数有足够样本支撑——要估 $L_{99}$，样本量需远大于 100 的量级才不至于让单个异常值主导分位数；具体数值由团队按误回滚率反推并登记。

判定谁：写明阈值由哪个角色或哪条自动化流水线裁决，以及裁决失败后的动作是“回滚”“降级到参考实现”还是“仅告警”。这三者的区别在于是否改变线上行为，清单必须无歧义。

处方还应包含一个伪代码级的测量循环思路，便于工程落地：

  • 固定输入形状集合，覆盖典型与极端两种；
  • 预热 $w$ 轮丢弃，再采样 $n$ 轮；
  • 每轮记录起止 event、峰值显存、是否出现 NaN；
  • 对 $n$ 个样本排序取分位数，与登记阈值比对；
  • 任一硬阈值触发即短路，不再继续采样以省 token 与时延。

代价在于：这套循环本身消耗 GPU 时间与验证 token，尤其在 $n$ 较大时。工程折中是分层采样——硬阈值（NaN、越界）用全量或高抽样率，软阈值（抖动、漂移）用低抽样率加长窗口。

五 · 阈值与灰度比例、回滚动作的耦合

阈值不是孤立的数字，它和灰度比例共同决定回滚的“触发速度”。设灰度比例为 $g$，单位时间调用量为 $\lambda$，则观察窗口 $T$ 内经过候选实现的调用数为 $g\lambda T$。要让错误率阈值 $\epsilon$ 的判定有统计意义，需满足 $g\lambda T \cdot \epsilon \gg 1$，即窗口内预期失败数不能是个位数。这个不等式直接约束了灰度策略：$g$ 太小则必须拉长 $T$，而长窗口意味着错误结果在线上停留更久。

因此清单应把“灰度比例—观察窗口—阈值”三者作为一组登记，而不是分别登记。一个具体例子：某 kernel 的错误率阈值定得很低，但灰度比例也定得很低，结果窗口内一次失败都没有，判定为“通过”；实际上是因为样本量不足而无法证伪。正确做法是把“样本量不足”本身作为一种判定结果，动作是“延长窗口或提高灰度比例”，而不是“放行”。

回滚动作的粒度同样要登记。回退到参考实现的切换步骤属于本条目定义部分的内容，此处只讨论阈值侧的耦合：切换本身有代价——参考实现可能更慢、更耗显存，切换瞬间会有请求重试与缓存失效。清单应写明“阈值触发后多久内完成切换”以及“切换期间是否降级服务”。这个时限是工程判断，取决于参考实现的冷启动开销与流量峰值。

事后复盘归档流程要求把每次阈值触发的原始测量数据（分位数、样本量、硬件状态）一并存档。没有原始数据的复盘只能得出“当时觉得慢”的结论，无法校准下一次的阈值。归档的代价是存储与脱敏工作量，但它是阈值从“经验数字”变成“可复现数字”的唯一路径。

六 · 阈值的漂移与再校准

阈值会漂移，原因有三：硬件更换、驱动与编译器版本变化、负载结构变化。清单若把阈值写成永久常量，第一次硬件升级就会让所有判定失效。工程做法是给每个阈值登记“适用条件”与“再校准触发条件”。

再校准的触发条件应写成可观测事件，例如：驱动大版本变更、集群换卡、端到端链路中该 kernel 占比变化超过登记幅度、连续多个窗口误回滚率偏高。触发后不是直接改数字，而是重跑第三节的测量协议，用新数据反推阈值，并把旧阈值与新阈值一并归档，形成可追溯的校准历史。

再校准本身有成本：需要占用灰度窗口、消耗验证 token、推迟发布。因此清单应区分“必须再校准”与“可沿用”的情形。硬件与驱动变更属于必须；负载结构的小幅变化可沿用，但要在复盘里标注“阈值未校准，判定置信度下降”。

最后落到一个具体机制上：把阈值条目写成结构化记录，字段包括指标名、判定表达式、量纲、适用硬件与软件版本、测量协议编号、上次校准时间、触发后的动作。判定表达式必须是机器可求值的，例如“$L_{99}/L_{50} > r$ 且样本量 $\ge n_{\min}$”，而不是自然语言描述。这样灰度流水线可以直接消费清单，回滚决策不依赖人读文档。代价是清单维护成本上升，收益是阈值从“文档里的数字”变成“流水线里的判据”——这正是回滚清单能可信执行的前提。

阈值不是拍脑袋：从抖动分布反推回滚门限

回滚阈值最容易犯的错，是拿单次 benchmark 的均值当基线。正确做法是先测抖动分布：同一 kernel 在目标卡上连续跑 N 次（N 取到足以覆盖一次完整调度周期），记录每次的 p50/p99 延迟与显存峰值，得到均值 μ 与标准差 σ。回滚门限应设为 μ+kσ 而非 μ 的固定百分比，k 由业务能容忍的误报率决定——k 太小会把正常抖动判成故障，k 太大则漏掉真实退化。经验上 k 取 3 对应约千分之三的单侧误报，但这只是起点，必须用你自己的抖动直方图校准。

$$\text{rollback if } \; p99_{\text{new}} > \mu_{\text{ref}} + k\sigma_{\text{ref}} \;\; \text{or} \;\; \frac{|acc_{\text{new}}-acc_{\text{ref}}|}{\max(acc_{\text{ref}},\epsilon)} > \delta$$

精度漂移的门限 δ 不能设成 0：浮点重排、TF32 降精度、不同 reduction 顺序都会带来末位差异，δ 应取参考实现自身在多次运行间的最大相对偏差再留一档余量。测法是对同一输入集跑参考实现两遍，取两次输出的相对误差上界作为 δ 的下限。代价在于：这个测量本身要占一次完整的正确性回归时间，且输入集若覆盖不到长尾 shape，δ 会被低估，导致上线后在小 batch 上误触发回滚。

指标测量方法失效条件
错误率灰度流量上按请求计数，分母含被降级请求降级路径吞掉异常，错误率被稀释
延迟抖动连续 N 次 p99，对比 μ+kσN 不足一个调度周期，σ 偏小
精度漂移参考实现双跑取相对误差上界输入集缺长尾 shape

灰度比例与阈值要联动：5% 流量下错误率的置信区间很宽，此时应只看硬失败（崩溃、NaN、超时）而不看软指标，等比例升到 20% 以上再启用 δ 判定。切换回参考实现的动作必须可幂等重放——把 kernel 选择做成配置项而非编译期分支，回滚就是改一个 flag 并等一个调度周期生效，代价是一次重编译或一次配置热加载的时延，而不是重新部署整个服务。
