一 · 阈值从哪里来：把规格表变成判据

规格速查表给的是分母：SM 数、显存带宽、L2 容量、tensor core 代际、NVLink 拓扑、功耗墙。工程阈值是把分母变成分子式的判据——同一个 kernel 在 A100 上“够快”的判据，搬到 H100 上会变，因为分母变了。所以本部分不列“通用阈值表”，而是给出“阈值 = f(规格)”的构造方法，以及在没有现成数字时如何测出这个 f。

第一个构造原则是把绝对时间换成 roofline 占比。设 kernel 的实际耗时 T，理论下界 T_min = max(FLOPs / Peak_FLOPS, Bytes / BW)，则 SOL 利用率 U = T_min / T。判据写成 U 的门槛，而不是“多少微秒”。这样跨卡迁移时门槛不变，只是 T_min 变了。代价是：U 对 Peak_FLOPS 的取法极度敏感——用 tensor core 峰值还是 CUDA core 峰值，用稠密还是稀疏峰值，结果差一个量级。工程上必须固定口径并在报告里写明，否则同一 kernel 在两个 agent 手里会得出相反的“是否达标”结论。

$$U=\frac{T_{\min}}{T},\qquad T_{\min}=\max\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{BW}\right)$$

第二个构造原则是把“带宽”拆成三层：HBM 带宽、L2 带宽、SM 内共享内存/寄存器带宽。一个 kernel 的实测有效带宽若显著低于 HBM 峰值，先判断它是被 L2 命中率拖累还是被 occupancy 拖累。经验判据：当 working set 小于 L2 容量时，有效带宽可以超过 HBM 峰值（因为命中 L2），此时用 HBM 峰值做分母会低估 SOL，必须换 L2 带宽做分母。L2 容量是速查表里的固定值，working set 是 kernel 的属性，两者比较就得到一个布尔判据：working set < L2 容量 ⇒ 用 L2 带宽口径。这个判据不需要任何实验数字，只需要规格表加一次 working set 估算。

具体例子：一个 reduction kernel 在 A100 上处理 4 MB 输入。4 MB 远小于 A100 的 L2 容量（速查表值），因此它大概率 L2 resident，用 HBM 峰值当分母会把 U 算低。正确做法是用 L2 带宽口径重算 T_min，再看 U 是否过门槛。代价是：L2 带宽口径本身难以精确测量，通常要用微基准（streaming 小数组、固定 stride）标定，标定本身要花编译与运行时间。

二 · 常见阈值的四个族：占用率、分块、对齐、同步

工程阈值可以归成四族，每族都有一个“低于它就换策略”的拐点。这些拐点不是拍脑袋，而是由硬件结构决定的。

  • 占用率族：寄存器用量决定每 SM 能驻留多少 warp。判据是“寄存器/线程 × 线程/block × block/SM ≤ 寄存器文件容量”。当寄存器用量跨过某个档位，occupancy 会阶梯式下跌，延迟隐藏能力随之下降。代价是：为了压寄存器而牺牲 ILP，可能让单 warp 的指令级并行变差，净效果未必为正。测法：用编译器的 register 报告加一次 occupancy 计算，不需要跑 kernel。
  • 分块族：shared memory 分块大小决定 tile 内的数据复用次数。判据是“tile 面积 / tile 周长”这个复用比，越大越省 HBM 流量，但 shared memory 占用上升会压低 occupancy。拐点出现在 shared memory 用量逼近每 SM 容量时。代价是：分块过大导致 occupancy 跌破隐藏延迟所需的下限，带宽反而下降。
  • 对齐族：全局访存的合并度取决于地址对齐与 stride。判据是“一个 warp 的 32 个 lane 访问是否落在少数 128B 段内”。不对齐或 stride 非 1 时，一次逻辑访存拆成多次物理事务，有效带宽按拆分倍数下降。代价是：为了对齐而做的 padding 会增加显存占用与索引计算。测法：构造 stride 扫描微基准，看有效带宽随 stride 的阶梯下降位置。
  • 同步族：block 内 __syncthreads 的次数与 block 间同步（grid sync、atomic 计数）的次数。判据是“同步次数 × 每次同步的延迟”是否已占 T 的可观比例。代价是：减少同步往往要求重排数据布局，可能引入额外拷贝。

具体例子：一个 GEMM 变体在 shared memory 用量上逼近每 SM 容量，occupancy 掉到很低，此时即便算术强度很高，延迟隐藏不足会让 U 明显低于 roofline 预测。工程判断是：宁可缩小 tile、牺牲一点复用比，把 occupancy 拉回隐藏延迟所需的下限之上。这个判断的依据是规格表里的 shared memory 容量与寄存器文件容量，不需要实测。

三 · 没有数字时怎么测：三类微基准与它们的代价

规格表给不出的量——有效带宽、L2 命中率、同步延迟、tensor core 实际吞吐——只能测。测法分三类，各有明确的代价。

第一类：带宽阶梯扫描。固定总字节数，扫 stride 与对齐偏移，记录有效带宽。输出是一条阶梯曲线，拐点即对齐族阈值。代价是：每次扫描要编译多个变体，编译时间随变体数线性增长；若用模板参数化 stride，编译时间会成为主要开销。工程上把扫描限制在少数几个 stride 上，用运行时参数而非编译期常量，换取编译时间。

第二类：占用率扫描。固定 kernel 逻辑，用编译期参数控制寄存器用量与 shared memory 用量，扫出一组 occupancy 点，记录每个点的 T。输出是 T-occupancy 曲线，拐点即占用率族阈值。代价是：寄存器用量难以精确控制，编译器会做寄存器分配优化，导致“想压到 N 个寄存器”未必成功；需要读编译器的 register 报告来校验，否则扫描点不可信。

第三类：同步延迟标定。构造只含同步、不含计算的 kernel，测每次同步的墙钟时间。代价是：这类 kernel 的 T 极小，计时噪声占比高，需要大量重复取中位数；而重复次数本身消耗运行时间。工程判断是：同步延迟只在同步次数达到可观量级时才值得标定，否则直接用“同步次数 × 保守上界”做粗略估算即可。

$$\hat{B}_{\text{eff}}=\frac{\text{Bytes}}{\bar{T}},\qquad \text{拐点}=\arg\min_{s}\ \frac{\hat{B}_{\text{eff}}(s)}{\hat{B}_{\text{eff}}(s-1)}$$

具体例子：要判断一个 transpose kernel 是否被 stride 拖累，做法是固定矩阵尺寸、扫 stride 从 1 到若干值，记录有效带宽。若在某个 stride 处有效带宽出现明显台阶，说明该 stride 跨过了对齐边界。代价是：transpose 的 working set 若大于 L2 容量，扫描结果会混入 HBM 效应，必须把矩阵尺寸压到 L2 容量以下才能隔离出对齐效应——这又要求先知道 L2 容量，回到规格表。

四 · 测量方法本身的偏差：计时、预热、频率

阈值不可信，往往不是判据错，而是测量方法带偏。三个偏差源必须显式处理。

计时偏差：单次 kernel 的墙钟时间包含 launch 开销。当 T 与 launch 开销同量级时，测出的“kernel 时间”其实是“launch + kernel”。判据是：若 T 小于 launch 开销的若干倍，必须用批量提交或 CUDA graph 摊薄 launch，否则阈值被系统性高估。代价是：CUDA graph 会固定住 kernel 参数与内存地址，灵活性下降，调试变难。

预热偏差：首次运行包含 JIT 编译、页表建立、cache 冷启动。判据是：至少丢弃前若干次迭代，取稳定段的中位数。代价是：预热迭代本身消耗运行时间，在 agent 多轮搜索中会累积成可观的 token 与算力开销。

频率偏差：功耗墙与温度决定实际运行频率，而规格表给的是峰值频率。判据是：若 kernel 是长时间高占用，实际频率会低于峰值，用峰值算出的 T_min 偏乐观，U 被低估。代价是：要拿到实际频率需要额外采样，采样本身有开销；工程上更常见的做法是用“峰值频率算出的 U”作为上界，接受它偏保守。

具体例子：一个短小 kernel 在 agent 搜索中被反复评测，若每次只跑一次，launch 开销占比高，agent 会误判该 kernel“慢”而放弃优化方向。正确做法是固定批量提交次数，把 launch 摊薄后再比较。代价是批量提交让单次评测的显存占用上升，可能触发 OOM，需要在批量大小与显存之间取平衡。

五 · 把阈值写进 agent 的判据：可验证奖励的门槛设计

agent 生成 kernel 后需要一个“是否值得继续优化”的判据。这个判据必须是可计算的、跨卡可迁移的、且对测量偏差鲁棒的。做法是把阈值写成三元组：(口径, 门槛, 置信规则)。

判据族口径门槛形式置信规则
占用率寄存器/线程、shared memory/SMoccupancy ≥ 隐藏延迟所需下限编译器报告校验，不实测
带宽working set 与 L2 容量比较后选 HBM 或 L2 口径U ≥ 门槛预热后取中位数，批量摊薄 launch
对齐warp 内 lane 的 128B 段数段数 ≤ 少数几段stride 扫描定位台阶
同步同步次数 × 单次延迟同步开销占 T 的比例 ≤ 阈值同步-only kernel 标定或保守上界

可验证奖励的设计要点是：门槛必须能从规格表加一次测量推出，而不是从“别人跑过的数字”抄来。抄来的数字在换卡后失效，agent 会朝着错误方向优化。代价是：每次换卡都要重新标定，标定成本进入 agent 的搜索预算；若标定太贵，agent 会退化成用固定门槛，跨卡迁移时判据失真。

具体例子：agent 在 A100 上把一个 kernel 优化到 U 过门槛，换到 H100 后同一门槛下 U 下降，agent 若不知道分母变了，会误以为 kernel 退化而回滚优化。正确做法是把门槛写成“相对该卡 T_min 的占比”，并在换卡时重算 T_min。代价是重算 T_min 需要重新读规格表并可能重新标定有效带宽，这是一次性的固定开销。

六 · 工程判断：阈值是分母的函数，不是常数

把本部分收束到一个可操作的判断上：任何写进 agent 判据的阈值，都必须带上它的分母来源。写成“U ≥ x”而不写“x 对应的 Peak_FLOPS 与 BW 取自哪张表、哪一代 tensor core”，这个阈值就是不可复现的。工程上更稳的做法是把阈值写成“相对量 + 口径声明”，让判据随规格表自动缩放。

具体机制是：把规格表做成 agent 可读的结构化输入，阈值计算函数从该输入取分母，agent 每次评测都重新计算 T_min 与 U，而不是缓存一个常数门槛。代价是每次评测多一次查表与算术，几乎可忽略；收益是跨卡、跨代际的判据一致性。若规格表缺项（例如某卡的 L2 带宽未给出），判据必须显式降级为“用 HBM 口径 + 保守上界”，并在报告里标注降级，而不是静默用错分母。

最后一个具体判断：当 working set 与 L2 容量同量级时，口径选择本身成为不确定性来源，此时阈值应放宽而不是收紧——因为分母的不确定性已经大于 kernel 优化带来的差异。工程上宁可接受一个宽松但可复现的判据，也不要一个精确但依赖未标定量的判据。

阈值不是规格书上的常数，而是分母与测量口径的函数

把「SM 数 × 每 SM 峰值 FMA」当作算力分母、把「显存带宽 × 有效利用率」当作带宽分母，这两个分母一旦写死，所有经验阈值都会随之漂移。真正稳定的做法是把阈值表达成无量纲比值：算术强度 $$I = \frac{2FLOP}{Bytes}$$ 与机器平衡点 $$I^* = \frac{\text{PeakFLOPS}}{\text{PeakBW}}$$ 的比 $$r = I / I^*$$。当 r 远小于 1 时，任何「优化计算」的动作都注定被带宽吃掉；当 r 远大于 1 时，L2 容量与占用率成为新的约束。A100 与 H100 的 I* 相差近一个量级，因此同一份 kernel 在两张卡上会落在 roofline 的不同侧翼——这不是 kernel 变了，是分母变了。所以速查表里每一个「经验阈值」都必须标注它是在哪一代 SM、哪一档显存带宽、哪一版 tensor core 代际下测得的，否则跨代复用就是错误外推。

测量方法上，分母不能取自厂商标称峰值，而应取自同一张卡上的实测微基准：用纯 streaming copy 测可持续带宽（而非理论 HBM 带宽），用大 K 的 GEMM 或纯 FMA 循环测可持续 FLOPS，两者相除得到该卡的实测 I*。这一步的代价是可观的：微基准本身要占满 SM 与显存控制器，单次测量在秒级到分钟级，且必须与目标 kernel 在同一功耗墙、同一时钟策略下运行，否则 boost 时钟漂移会让 I* 偏移。消费卡尤其如此，其功耗墙与热设计使持续 FLOPS 显著低于短时峰值，用标称值算出的 r 会系统性偏乐观。一个具体例子：同一 conv 实现在数据中心卡上 r≈0.2 属于带宽受限，换到功耗墙更紧的消费卡上实测 FLOPS 下降后 r 可能升到 0.5 以上，此时继续做计算侧优化收益骤减，应转向减少中间张量驻留与提升 L2 命中。

L2 容量是另一类容易被误用的阈值。把「工作集小于 L2 就免费」当作判据是失效的，因为 L2 是跨 SM 共享且被所有并发 block 竞争的资源；有效容量取决于占用率、访问模式与替换策略。可操作的判据是：用 NCU 采集 L2 hit rate 与 L2 到 HBM 的实际流量，若 hit rate 随 block 数上升而塌陷，说明工作集已越过有效阈值，此时增大 tile 只会加剧抖动。下表给出阈值失效的典型条件与应改测的量。

阈值类型失效条件应改测的量
算术强度分界跨 SM 代际或功耗墙变化实测可持续 FLOPS 与带宽之比
L2 工作集并发 block 增多、访问模式冲突L2 hit rate 与 HBM 实际流量
占用率下限寄存器压力或 shared memory 超限achieved occupancy 与 stall 原因分布

最后是编译与验证侧的阈值代价。多轮 agent 优化里，「编译时间」本身就是一条硬阈值：Triton 与 CuTe 模板实例化的编译时延随 tile 参数组合爆炸增长，若每轮候选都要全量编译，token 预算会被编译等待挤占；可行做法是先用低成本静态检查（寄存器估算、shared memory 上限、tile 整除性）剪枝，再对少量候选做真实编译与 NCU profile。正确性 oracle 同理：形式验证或差分测试的覆盖度提升会带来时延与显存开销，阈值应设为「能区分候选优劣的最小验证强度」，而不是追求全量证明。工程判断落在这一点上——阈值的作用是剪枝候选空间，而不是给出绝对性能承诺；一旦分母口径改变，阈值必须重测，而不是沿用。
