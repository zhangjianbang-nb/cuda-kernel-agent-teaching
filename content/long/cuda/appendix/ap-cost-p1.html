一 · 条目是什么：一行成本记录的最小完备集

《算力与成本估算表》的每一行不是“一张卡多少钱”，而是一条可复算的成本记录：给定 GPU 型号、给定一次 kernel agent rollout 的工作负载，回答“这一次迭代烧掉多少机时、多少秒、多少 token”。一条条目必须同时携带四类字段才成立：单价字段（该型号每小时计价，含按需/预留/竞价的口径标记）、时间字段（单次 rollout 的编译秒数与运行秒数，二者分开记，因为它们的伸缩规律完全不同）、观测字段（NCU profile 开销倍数，即开 profile 后 wall time 相对不开的放大系数）、以及 token 字段（全流程 token 成本，覆盖生成、反思、工具返回文本的输入输出总量）。缺任一类的行只能叫“价格表”，不能叫成本估算表。

把四类字段合成一个可比较的标量，是本表的核心运算。设型号 $g$ 的时价为 $p_g$（元/小时），单次 rollout 的编译时间为 $t^{c}$、运行时间为 $t^{r}$（秒），profile 开销倍数为 $\kappa \in [1, \infty)$（仅在被采样的 rollout 上生效），采样率为 $\sigma$，token 单价为 $q$（元/token），单次 rollout 的 token 量为 $n$。则单次 rollout 的期望成本为：

$$C_{\text{rollout}} = \frac{p_g}{3600}\left(t^{c} + t^{r}\right)\left(1 + \sigma(\kappa - 1)\right) + q\,n$$

这个式子的结构本身就是分类依据：前项是机时成本，随 $t^c$、$t^r$、$\kappa$、$\sigma$ 线性增长；后项是 token 成本，与 GPU 型号无关但与轮数强相关。两条成本通道的比值决定了这条条目属于“算力主导型”还是“token 主导型”，这是本表最有用的一次二分。

具体例子：某条目记录型号 A、$p_g$ 按小时计、$t^{c}$ 明显大于 $t^{r}$（编译主导，典型于模板展开重的 CuTe 或 PTX 手写路径），$\kappa$ 取中等值、$\sigma$ 取低采样率。此时机时项被 $t^{c}$ 拉高，而 token 项相对稳定；若把该条目误记为“运行时间为主”，预算会被系统性低估，因为编译秒数在多轮 rollout 中是每轮都付的固定税，不是一次性开销。

二 · 分类维度一：按成本通道分（机时 / token / 观测）

第一个分类维度是成本落在哪条通道上，这决定了优化的抓手在哪。机时通道由 $p_g \cdot (t^c+t^r)$ 构成，抓手是并行度、批大小、编译缓存；token 通道由 $q\cdot n$ 构成，抓手是上下文裁剪、工具返回文本的压缩、反思轮数；观测通道由 $\sigma(\kappa-1)$ 构成，抓手是采样率与 profile 粒度。三者不是并列的，而是有耦合：开 NCU 会拉长 wall time（进机时通道），同时 profile 文本回灌进上下文（进 token 通道），所以一条条目若标为“观测主导”，它的成本对 $\sigma$ 的敏感度是双通道叠加的。

判别一条条目属于哪一类，用通道占比而非绝对数值：

$$\rho_{\text{obs}} = \frac{\sigma(\kappa-1)}{1 + \sigma(\kappa-1)},\quad \rho_{\text{tok}} = \frac{q n}{C_{\text{rollout}}}$$

$\rho_{\text{obs}}$ 只依赖 $\sigma$ 与 $\kappa$，与型号无关，因此它是跨型号可比的纯观测税；$\rho_{\text{tok}}$ 则随 $p_g$ 上升而下降——同一份 token 量在贵卡上显得便宜，在便宜卡上显得昂贵。这解释了一个常见误判：把 token 成本按“每条目固定”摊到所有型号上，会在低价型号上严重低估 token 占比。

代价面：机时主导型条目的瓶颈是排队与显存占用，优化它要付调度复杂度；token 主导型条目的瓶颈是上下文长度，压缩上下文会牺牲诊断信息，直接反映为正确性 oracle 的通过率下降；观测主导型条目每提高一档 $\kappa$ 就多付一份 wall time，且 NCU 的 replay 次数越多，$\kappa$ 越大，采样率必须相应下调才能守住预算。具体例子：一条以 Triton 生成的条目，$t^r$ 短、$t^c$ 中等、$\kappa$ 偏高，若把 $\sigma$ 从低档提到中档，$\rho_{\text{obs}}$ 会明显上升，此时正确做法是只对失败 rollout 开 profile（选择性采样），而不是全量降 $\kappa$。

三 · 分类维度二：按时间结构分（编译主导 / 运行主导 / 混合）

第二个维度看 $t^c$ 与 $t^r$ 的比例。编译主导型条目的特征是 $t^c \gg t^r$：一次 rollout 里绝大部分秒数花在 nvcc/ptxas 与模板实例化上，运行只是几毫秒的 kernel。这类条目的成本几乎与输入规模无关，只与代码形态有关——CuTe 的深层模板、PTX 内联汇编的手写约束、以及大量 unroll 都会推高 $t^c$。运行主导型则相反，$t^r$ 随问题规模（batch、序列长度、矩阵维度）增长，成本对输入分布敏感。混合型两者同量级，最容易被误分类，因为改动一个 tile 参数就可能让比例翻转。

分类的操作化判据是编译摊销比：设同一 kernel 在预算周期内被 rollout $R$ 次，若编译产物可缓存复用，则有效编译成本为 $t^c / R$；若每轮都重新生成代码（agent 改写源码），则 $R=1$，全额支付。写成：

$$t^{c}_{\text{eff}} = \frac{t^{c}}{R},\qquad R = \begin{cases} R_{\text{cache}} & \text{代码未变}\\ 1 & \text{每轮重生成}\end{cases}$$

这条判据把“编译主导”从静态属性变成可调属性：缓存命中率决定了条目在预算表里的真实位置。代价是缓存本身要占显存与磁盘，且缓存键必须包含编译 flags、架构号与源码哈希，键设计不当会让命中率虚高而正确性 oracle 失效——这是正确性代价而非性能代价，必须单列。具体例子：一条 CuTe 条目在开启编译缓存后 $t^c_{\text{eff}}$ 降到可忽略，条目从“编译主导”迁移到“运行主导”，预算表若不同步更新分类标签，后续吞吐规划会按错误的瓶颈做并行度设计。

性能代价方面，编译主导型条目对并行度的响应很差：加机器不能缩短单次编译，只能提高并发编译数，而并发编译吃 CPU 与内存带宽，会挤压同机的运行任务。因此这类条目在表里应标注“CPU 侧瓶颈”，与纯 GPU 瓶颈条目分开排班。

四 · 分类维度三：按 profile 开销形态分（常数税 / 规模相关税）

第三个维度是 $\kappa$ 的形状。NCU 的开销不是单一倍数，而取决于采集的指标集与 replay 策略：只采少量计数器时 $\kappa$ 接近常数；采全套指标、需要多次 replay 以分轮收集时，$\kappa$ 随 kernel 数与 replay 轮数增长，表现为规模相关税。表中必须区分这两种形态，否则 $\sigma(\kappa-1)$ 这一项在长 kernel 上会被低估。

把 $\kappa$ 拆成两部分：固定启动开销 $\kappa_0$（profile 会话建立、注入）与每 replay 轮成本 $\kappa_1 \cdot m$，$m$ 为 replay 轮数。则：

$$\kappa = \kappa_0 + \kappa_1 m,\qquad \frac{\partial C}{\partial m} = \frac{p_g}{3600}\,\sigma\,\kappa_1\,(t^c+t^r)$$

偏导说明：replay 轮数每加一轮，成本按 wall time 比例增加，且这个增量与 $t^r$ 成正比——所以长 kernel 的 profile 税天然更贵。这给出一条工程判断：对运行主导型条目，profile 应只覆盖代表性 shape，不做全 shape 扫描；对编译主导型条目，profile 税相对便宜（因为 $t^r$ 小），可以放宽采样。

代价面：降低 $m$ 会丢失分轮指标（如内存事务与 warp stall 的分解），使诊断从“定位到具体 stall 原因”退化为“知道有 stall”，直接拉低多轮 RL 中反思信号的质量，表现为 token 花在无效反思上——这是 token 代价换性能代价的典型交换。具体例子：一条运行主导条目在 $m$ 从高档降到低档后，$\kappa$ 明显下降、机时项回落，但 agent 拿到的 profile 文本不再区分 L2 命中与 DRAM 带宽瓶颈，后续改写方向错误，rollout 轮数上升，token 项反超机时项，条目分类从“机时主导”漂移到“token 主导”。

五 · 与相邻概念的区别：价格表、基准分数、roofline 上界

本表最常被混淆的三个邻居是：GPU 价格表、KernelBench 系基准的分数、以及 roofline/SOL 上界。区别在于回答的问题不同。价格表回答“这台机器一小时多少钱”，是条目的输入字段而非条目本身；它不含 $t^c$、$t^r$、$\kappa$、$n$，因此无法支撑吞吐规划。基准分数回答“这个 kernel 相对参考实现快多少”，是分子侧的效率度量，不含分母侧的成本；一个高分 kernel 若编译时间极长或需要全量 profile 才能收敛，其成本条目可能很差。roofline/SOL 回答“理论上还能快多少”，是上界而非实测，用来判断优化空间，不能直接乘单价得到预算。

三者的换算关系可以写成一个桥接式，用来把基准分数翻译成成本敏感度：设基线运行时间为 $t^r_0$、候选为 $t^r_1$，加速比 $s = t^r_0/t^r_1$，则单次 rollout 的机时节省为：

$$\Delta C = \frac{p_g}{3600}\left(t^{r}_0 - t^{r}_1\right)\left(1+\sigma(\kappa-1)\right) - \Delta q\,n$$

注意第二项是负号：更快的 kernel 往往需要更多轮生成与验证才找得到，token 成本上升会吃掉机时节省。这条式子解释了为什么“基准分数更高”不等于“成本条目更优”——只有当 $\Delta C > 0$ 时，加速才在预算意义上成立。这也是本表与基准速查表必须并列使用、不可互相替代的原因。

具体例子：一条 Triton 条目相对基线有可观加速，但生成该 Triton 代码所需的反思轮数明显多于直接写 CUDA 的路径，$\Delta q\,n$ 为正且不小；在低价型号上 $p_g$ 小，机时节省被 token 增量抵消，条目在成本表里反而劣于基线。工程判断是：低价型号上优先选生成成本低的路径，高价型号上才值得为加速付 token。

六 · 条目的粒度与合并规则

最后一个分类问题是粒度：一条条目对应“一个型号 × 一个工作负载 × 一种实现路径”，还是对应“一个型号 × 全部工作负载”。粒度太细会让表膨胀到无法排班，太粗则掩盖编译主导与运行主导的差异。合并规则应满足：同一 $(g, \text{path})$ 下，若各工作负载的 $t^c$ 方差小、$t^r$ 方差大，则按 $t^r$ 分桶合并（因为运行时间是规模函数）；若 $t^c$ 方差大，则不可合并，因为编译成本由代码形态决定，跨形态平均会失真。

合并后的条目成本用加权和而非算术平均，权重为该桶在预算周期内的 rollout 次数 $w_i$：

$$C_{\text{entry}} = \sum_i w_i C_{\text{rollout},i}\Big/ \sum_i w_i$$

代价面：合并降低表规模与排班复杂度，但会引入聚合误差；误差主要来自 $\kappa$ 的非线性（不同桶的 replay 轮数不同）与 token 量的长尾（少数失败 rollout 消耗大量反思 token）。因此合并时必须保留一个长尾标记字段，否则均值会被长尾拉偏而无人察觉。具体例子：某型号下多数 rollout 的 token 量集中，少数失败 rollout 因反复 profile 与反思消耗数倍 token；若只记均值，预算会系统性偏紧，实际执行时超支集中在失败样本上，而这正是最需要预算弹性的地方。

落到工程判断上：条目的准确定义应锁定为“可复算的四字段记录 + 一个分类标签（成本通道、时间结构、profile 形态）+ 一个粒度键（型号、路径、桶）”。分类标签不是装饰，它决定后续优化动作的方向；粒度键不是索引，它决定预算误差的上界。任何缺少分类标签的行，在吞吐规划阶段都必须重新归类，而重新归类的成本往往高于当初就记对的成本。

成本条目的边界：什么算进“每小时单价”，什么不算

《算力与成本估算表》里的“每小时单价”不是云厂商账单上的实例挂牌价，而是**可归因到 kernel 生成任务的那部分 GPU 时间价格**。这个定义决定了条目的失效条件：一旦任务的实际占用模式偏离“独占整卡、按小时连续计费”，单价就必须重算。典型偏离有三类。其一是分时复用：当多个 rollout 共享一张卡、以 MPS 或时间片方式并发时，单条 rollout 的有效单价应按占用份额摊薄，但摊薄系数不是线性的——SM 争用会让单次编译+运行的墙钟时间膨胀，摊薄后的单价反而可能高于独占价。其二是抢占式实例：单价低，但被回收导致 rollout 中断、编译产物与 profile 数据丢失，重跑成本要计入。其三是存储与网络：编译缓存、NCU 报告、SASS dump 的落盘与跨节点传输不在 GPU 单价内，却是全流程 token 成本之外的第二类隐性开销。因此条目必须显式声明计价口径（独占/共享、是否含中断重跑、是否含存储），否则跨型号比较会失真。

分类维度上，本表按三个正交轴切分条目：**GPU 型号**（决定单价与峰值算力）、**rollout 阶段构成**（编译、运行、profile 三段各自的秒数）、**profile 强度**（NCU 开销倍数）。三段秒数不能简单相加成“单次 rollout 秒数”就完事，因为编译段与运行段对单价的敏感度不同：编译是纯 CPU 前端加少量驱动交互，运行才是 GPU 计费主体。设单次 rollout 的编译秒数为 t_c、运行秒数为 t_r、NCU profile 开销倍数为 k（仅在开启 profile 的轮次生效），则单次 rollout 的 GPU 计费秒数近似为

$$T_{\text{bill}} = t_r \cdot \bigl(1 + k \cdot \mathbb{1}_{\text{profile}}\bigr) + \epsilon \cdot t_c$$

其中 \epsilon 是编译段折算到 GPU 计费的系数，通常远小于 1，因为编译期 GPU 大多空闲。这个式子的工程含义是：**profile 轮次的单价不能与普通轮次混算**，否则吞吐规划会系统性低估。举例来说，若某型号单价为每小时 P，单次 rollout 运行 30 秒、编译 20 秒，普通轮次计费秒数约 30 秒出头；一旦该轮开启 NCU，开销倍数 k 使运行段膨胀数倍，单次计费秒数可能逼近两分钟，同样的预算能跑的 rollout 数直接腰斩。表里必须把 profile 轮次单列一行，或给出“profile 轮次占比”这一参数，让读者自行加权。

与相邻概念的区别要划清三条线。第一，**与吞吐指标的区别**：条目给的是“每秒多少钱”，不是“每秒多少 token”或“每秒多少有效 kernel”；后者要除以全流程 token 成本与成功率，属于下游派生量，不在本表定义内。第二，**与硬件参数表的区别**：本表不列 SM 数、显存带宽、TFLOPS，这些是 roofline/SOL 分析的输入，不是成本条目的字段；型号只作为单价与 profile 开销倍数的索引键。第三，**与训练成本表的区别**：训练侧按 step 与全局 batch 计费，rollout 侧按“编译+运行+profile”三段计费，两者的时间粒度与可中断性完全不同，不能共用一张单价表。失效条件也由此明确：当 rollout 的编译段占比高到 \epsilon \cdot t_c 不可忽略（例如 Triton 首次编译、CuTe 模板实例化爆炸），或 profile 轮次占比超过预算假设时，条目必须回填实测秒数重算，而不是沿用标称单价外推。
