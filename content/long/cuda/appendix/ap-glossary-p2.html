二 · 速查表的结构：字段、单位与口径三列并行

术语表速查表不是词典，而是工程决策表。它必须让读者在拿到一条 profile 或一份评测报告时，能在三十秒内判断：这个数字属于哪一类量、它的单位是什么、它能不能与另一条数字直接比较。因此速查表的最小结构是三列并行：字段（field）、度量单位（unit）、口径（convention）。字段是术语的规范名，单位决定量纲，口径决定可比性边界。三者缺一，数字就会在跨章引用中失真。

以 SOL（Speed of Light）为例。字段写作 sol_ratio，单位是无量纲比值，口径必须写明分母取的是哪一条 roofline 上界：是 HBM 带宽上界、还是 SM 峰值算力上界、还是特定指令吞吐上界。同一个 kernel 在带宽受限与算力受限两种口径下，sol_ratio 可以相差数倍，若不标注口径，两个数字并列就是错误的。公式上，口径的定义可以写成：

$$\text{sol\_ratio} = \frac{T_{\text{measured}}}{T_{\text{roofline}}(b, f)}$$

其中 b 是所选带宽上界，f 是所选算力上界，T 是实测时延。口径列要回答的正是 b 与 f 的取值来源。代价在于：口径越精细，速查表越难维护；每新增一条 roofline 上界，就要为所有相关字段补一次分母说明，这是一次性的人力成本，但换来的是跨章数字的可比性。

具体例子：某 agent 生成的两个 Triton kernel，报告里都写 sol_ratio = 0.62。查速查表发现，第一个的分母是 HBM 带宽上界，第二个的分母是 SM 算力上界。前者说明它已接近内存带宽极限，优化方向是减少访存；后者说明它离算力峰值还有距离，优化方向是提高指令级并行。若不查口径列，这两个 0.62 会被误读为同等优化空间。

三 · 阈值列：把定性判断压成可执行的门限

速查表若只有字段与口径，仍然停留在描述层。工程上真正被反复查询的是阈值：什么数值算通过、什么数值触发告警、什么数值必须回退。阈值列的作用是把“看起来还行”压成一个 agent 可以自动判定的布尔条件。阈值必须与口径绑定，否则阈值本身没有意义——sol_ratio > 0.5 这个门限只在分母口径固定的前提下才成立。

以正确性 oracle 为例，速查表应给出 max_abs_err 与 max_rel_err 两个字段，单位分别是输出张量的绝对量纲与无量纲比值，口径写明参考实现是 FP32 还是 FP64、是否允许 NaN 传播。阈值则写成与数据类型挂钩的分段门限：FP16 输出与 FP32 参考比对时，相对误差门限要放宽到与半精度舍入同量级；FP32 输出与 FP64 参考比对时，门限收紧到单精度累积误差量级。伪代码上，判定逻辑是：

  • 若 max_rel_err > threshold(dtype)，标记为不正确，进入失败模式库；
  • 若 max_rel_err 落在门限的 0.5 倍到 1 倍之间，标记为边界通过，要求补充随机种子复测；
  • 若参考实现含归约操作，额外检查 max_abs_err 是否随规模增长而漂移，漂移即视为口径不匹配而非 kernel 错误。

代价在于：阈值收紧会提高假阴性率，把正确 kernel 判为失败，浪费多轮 RL 的采样预算；阈值放宽会提高假阳性率，让错误 kernel 进入部署候选。每一次阈值调整都要在验证器清单里留下口径变更记录，否则同一批次内的通过率不可比。具体例子：一个 agent 在归约 kernel 上连续三轮被判失败，查速查表发现阈值是按逐元素口径设定的，而归约的累积误差随 N 增长，属于口径错配；改为按规模分段的阈值后，同一 kernel 稳定通过。

四 · 执行反馈字段：时延、带宽、占用率的口径分离

执行反馈是 agent 多轮迭代的主要信号来源，速查表必须把反馈拆成互不混淆的字段。时延字段 latency_ms 的单位是毫秒，口径必须写明是否含 kernel launch 开销、是否取多次运行的中位数、是否剔除首次运行的冷启动。带宽字段 achieved_bw 的单位是 GB/s，口径写明是按有效字节数还是按理论传输字节数计算——后者在存在冗余访存时会高估效率。占用率字段 occupancy 是无量纲比值，口径写明分母是理论最大活跃 warp 数还是 SM 支持的最大线程数。

这三个字段的分离不是形式主义。一个 kernel 可能时延很低但带宽利用率也低，说明它受限于指令延迟而非访存；也可能占用率很高但时延不降，说明瓶颈在依赖链而非并行度。公式上，有效带宽的定义要显式区分：

$$\text{achieved\_bw} = \frac{B_{\text{useful}}}{t_{\text{kernel}}}$$

其中 B_useful 只计真正被消费的字节，冗余加载与写回不计入。口径列要说明 B_useful 的统计来源：是由 kernel 的访存模式静态推算，还是由 profiler 的扇区计数换算。两者在存在合并访存失败时会给出不同结果，速查表必须指定其一，否则同一 kernel 的两次报告无法比较。

代价在于：把 launch 开销纳入时延口径会让小 kernel 的时延被系统性高估，从而扭曲 roofline 比值；剔除冷启动则要求至少多跑一次预热，增加了评测的 wall-clock 时间。具体例子：一个逐元素加法 kernel 在两种口径下分别报告 0.03 ms 与 0.011 ms，差异全部来自 launch 开销；若速查表不标注口径，agent 会把优化方向错误地指向 kernel 内部而非批处理合并。

五 · 可验证奖励字段：奖励口径与作弊面

多轮 RL 的可验证奖励依赖速查表给出统一的奖励字段定义。字段 reward 是无量纲标量，口径必须写明它由哪些子项加权而成：正确性通过与否、SOL 比值、时延改进幅度、编译是否成功。权重本身不进速查表，进表的是子项的口径——例如“时延改进”是相对基线 kernel 还是相对上一轮 agent 自身输出。这两者差异极大：相对基线会奖励保守的微调，相对自身会奖励激进的重写，后者更容易触发正确性回退。

速查表还必须为奖励字段标注作弊面。可验证奖励的可信度取决于它是否可被无意义地刷高。典型作弊面包括：输出与参考实现完全相同的恒等 kernel、利用缓存命中伪造低时延、在 benchmark 规模上特化而在其他规模上崩溃。速查表对应给出三个检查字段：identity_check（输出是否逐位等于输入）、cache_warm（是否在预热后测量）、scale_sweep（是否在至少两个规模上复测）。每个字段的取值是布尔或枚举，口径写明判定方法。

代价在于：每增加一个作弊检查字段，评测流水线的运行时间就增加一份；scale_sweep 在大规模输入上尤其昂贵，可能使单轮评测的显存占用翻倍。工程判断是：把 identity_check 与 cache_warm 设为必检，scale_sweep 设为抽样检，抽样比例写进速查表的口径列，而不是留给实现者临场决定。具体例子：某轮 agent 输出一个在固定规模上时延极低的 kernel，scale_sweep 在另一规模上暴露其访存越界，奖励被回退，避免了错误 kernel 进入部署候选。

六 · 跨工具链字段的对齐：CUDA C++、Triton、CuTe、PTX

同一术语在不同工具链下的口径并不自动一致，速查表要为跨工具链引用提供对齐列。以“占用率”为例，CUDA C++ 侧通常按每 SM 活跃 warp 数报告，Triton 侧由编译器自动决定 num_warps 与 num_stages，其占用率口径取决于编译产物而非源码；CuTe 的 tile 划分会改变每线程工作量，进而改变占用率的分子；PTX 层则只能看到寄存器与共享内存的静态占用，看不到动态调度后的实际活跃度。速查表必须为每个工具链标注该字段的观测层级。

对齐列的价值在于防止跨章比较。一个 Triton kernel 报告的 occupancy = 0.75 与一个手写 CUDA kernel 报告的 occupancy = 0.75，若观测层级不同，就不能得出“两者并行度相当”的结论。速查表应给出层级枚举：源码级、编译产物级、运行时级、指令级。公式上，运行时占用率可以写成：

$$\text{occupancy}_{\text{rt}} = \frac{W_{\text{active}}}{W_{\text{max}}}$$

其中 W_active 是采样时刻实际驻留的 warp 数，W_max 是硬件上限。源码级口径则用编译期常量估算，不含运行时波动。代价在于：运行时级口径需要 profiler 介入，带来额外的采样开销与结果抖动；编译产物级口径不需要运行，但会高估实际占用率。具体例子：一个 CuTe kernel 在源码级估算占用率为 1.0，运行时采样只有 0.6，差异来自 tile 划分导致的寄存器压力；速查表若只标源码级，agent 会误判其已饱和而停止优化。

速查表的维护成本集中在对齐列：每接入一条新工具链，就要为所有跨链字段补一次层级标注。工程判断是，把对齐列做成必填项而非可选项，并在字段名中嵌入层级后缀（如 occupancy_rt、occupancy_src），使口径在字段名层面就不可混淆。这样做的直接收益是：跨章引用时不需要回查上下文，字段名本身即携带可比性信息。

速查表的失效边界：字段口径漂移、阈值不可移植与系统代价

速查表最容易失效的地方不是条目缺失，而是字段口径在跨章、跨工具链时发生漂移。同一列“加速比”在 KernelBench 口径下是相对 PyTorch eager 参考实现的端到端时延比，在 NCU 口径下却常被读成 kernel 自身 duration 之比；两者分母不同，数值不可互换。工程上要求速查表每一行都绑定三件事：度量对象（kernel-only 还是含 launch/同步的端到端）、计时口径（CUDA event 还是 wall clock、是否含 warmup 与 L2 flush）、基线版本（eager、compile 还是手写库调用）。缺任一项，该行只能作定性参考。一个具体机制是把口径写成可执行断言：评测脚本在产出指标前先校验 baseline_id 与 timer_mode 字段非空且与配置一致，否则拒绝写入结果表——这把“口径”从文档约定变成流水线闸门，代价是每次评测多一次配置解析与校验，属于微秒级开销，但能挡住整批结果作废的风险。

阈值列不可移植，是速查表第二个系统性弱点。SOL（speed of light）利用率的分母依赖 roofline 模型选定的峰值：以 HBM 带宽为屋顶时，算力受限 kernel 的 SOL 会被高估；以 SM 峰值 FMA 为屋顶时，带宽受限 kernel 的 SOL 会被低估。因此“SOL ≥ 某阈值即视为达标”这类写法必须附带屋顶选取规则，否则同一 kernel 在不同机器、不同屋顶下给出相反结论。可用的判据是算术强度 $$I = \frac{FLOPs}{Bytes}$$ 与机器平衡点 $$I^* = \frac{Peak_{FLOP/s}}{Peak_{B/s}}$$ 的比较：$$I < I^*$$ 时屋顶应取带宽，反之取算力，速查表的阈值行应显式记录所选屋顶及 $$I^*$$ 的取值来源。正确性 oracle 的阈值同理：浮点比对容差若写成固定绝对值，在归约类 kernel 上会随规模放大而误判，须改为相对误差加尺度因子，并注明是否允许 NaN/Inf 传播。代价体现在验证时延上：逐元素容差检查是 O(n) 访存，对大规模输出会引入与 kernel 同量级的带宽消耗，通常需抽样或分块比对来摊薄。

第三类失效来自“可验证奖励”字段被误当作性能字段使用。速查表中奖励口径应区分通过/不通过的二值信号与带连续惩罚的 shaping 项：前者对正确性 oracle 的漏判零容忍，后者对性能退化敏感但对数值噪声鲁棒。把二者混进同一列，会让多轮优化把“通过率提升”误读为“kernel 变快”。一个具体例子是归约 kernel 在边界 tile 上因容差放宽而通过，但实际吞吐因额外分支下降——若速查表只记录通过标志而不记录时延与分支发散度，该退化在表中不可见。系统代价方面，速查表本身若要求每次评测都填满全部字段（含 NCU 计数器、SASS 指令混合、编译时间），单次评测的采集开销会从秒级升到分钟级，且 NCU 复跑会串行化吞吐；工程判断是分层填表：正确性与时延为必填，profile 类字段按需触发，编译时间仅在 Triton/CuTe 变体对比时记录。

速查表的边界：字段口径与失效条件

速查表的价值不在于“能查”，而在于“查到的字段在什么条件下失效”。表中每个字段都应携带三件事：度量单位、采集口径、失效判据。以 SOL（Speed of Light）为例，字段值必须绑定 roofline 的分母选择——是 HBM 带宽上限还是 SM 峰值算力，二者不可混用；一旦 kernel 的实际瓶颈落在 L2 或指令发射而非 HBM，SOL 百分比会系统性偏高，此时该字段应标记为“不可解释”而非“达标”。同理，正确性 oracle 字段要区分“逐元素容差比对”与“形式化等价”，前者在浮点归约顺序变化时容差阈值需随规模放大，否则会把合法重排判为错误。

可验证奖励字段的系统代价最容易被低估：若奖励由实测时延计算，则每次 rollout 都要真实执行 kernel，单条样本的墙钟时延与显存占用直接进入 RL 采样吞吐，采样成本随时延抖动而放大；若改用静态指令计数或 profile 近似，则奖励与真实收益脱钩，agent 会优化到代理指标上。折中做法是把奖励拆成“正确性硬门控 + 性能软分”，硬门控用 oracle 布尔值，软分用可复算的归一化指标，代价是每次评估多一次 oracle 执行。

$$ r = \mathbb{1}[\text{oracle}=1]\cdot \frac{t_{\text{ref}}}{t_{\text{cand}}+\epsilon} $$

该式的边界在于 ε 的选取：ε 过小则极快但错误的候选获得虚高奖励，ε 过大则抹平真实差异；同时 t_ref 必须来自同一硬件、同一输入分布，跨设备复用参考时延会让奖励失去可比性。因此速查表中“参考时延”字段必须附带设备与输入形状指纹，缺失指纹即视为失效字段，不得进入跨批次聚合。
