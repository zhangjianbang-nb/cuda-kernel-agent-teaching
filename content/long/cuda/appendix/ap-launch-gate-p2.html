二 · 门禁字段的命名与取值口径

速查表的第一层不是阈值，而是字段。字段名一旦含糊，阈值就会在评审会上被反复重新解释，最后变成“看情况”。上线门禁的每个字段必须是机器可读的、单一来源的、带单位的，并且与证据文件一一对应。建议把字段分成四类：判定类（布尔）、度量类（数值+单位）、证据类（路径/哈希）、责任类（人名/角色）。判定类字段只允许 true/false/unknown 三值，禁止“基本通过”这种中间态；度量类字段必须写明口径，例如 p99_latency_ms 与 median_latency_ms 是两个字段而不是一个；证据类字段记录产物哈希而非“已上传”；责任类字段记录的是签字人而非“团队”。

口径的核心是“谁来测、在哪测、测几次”。同一个 kernel 在冷启动与热缓存下的时延可以差出一个数量级，因此每个度量字段都要附带三个限定词：输入分布（shape 与 dtype 的组合）、测量模式（是否 warmup、是否包含 launch 开销）、统计量（中位数、p90、p99 还是最小值）。速查表中把这些限定词压缩成后缀，例如 lat_p99_warm_ms 表示热缓存下 p99 时延，单位毫秒。后缀不是装饰，它是防止跨条目比较时口径漂移的唯一手段。代价是字段数量膨胀：一个 kernel 若有 3 种典型 shape、2 种测量模式、3 个统计量，度量字段就会有 18 个，评审表格随之变长。工程上的折中是只对“放行必须看”的组合建字段，其余留在证据文件里供追溯。

$$\text{gate} = \bigwedge_{i \in \mathcal{F}} \bigl( \text{value}_i \neq \text{unknown} \bigr) \wedge \bigwedge_{j \in \mathcal{T}} \bigl( \text{metric}_j \le \tau_j \bigr)$$

上式是门禁的合取结构：所有必填字段必须有值，所有阈值字段必须不超限。注意它没有加权求和，因为上线门禁是可验证奖励式的硬约束，不是打分排序。任何一项 unknown 都等价于不通过，这条规则把“证据缺失”从软性问题变成硬性阻断。代价是流程刚性：一次 NCU 采集失败就会卡住整条流水线，因此证据采集环节需要独立的重试与缓存机制，而不是让门禁逻辑去容忍缺失。

三 · 阈值分档：绝对阈值、相对阈值与回归阈值

阈值不是一组固定数字，而是三种性质不同的约束。绝对阈值针对物理上限，例如显存占用不得超过设备可用显存的某个比例、单次 kernel 时延不得超过业务 SLA 的预算切片；相对阈值针对基线对比，例如相对 PyTorch eager 实现的加速比不得低于某值、相对手写 CUDA 参考实现不得慢于某倍；回归阈值针对历史版本，例如相对上一放行版本的中位数时延劣化不得超过某个百分比。三者混用是门禁失效的常见原因：用相对阈值去卡一个本来就慢的基线，会让劣化版本轻松通过。

速查表应当为每个度量字段标注阈值类型，并给出“锚点”。绝对阈值的锚点是硬件或 SLA；相对阈值的锚点必须写明基线版本号与基线测量口径，否则加速比可以在换基线后凭空变好；回归阈值的锚点是上一次放行时留存的证据哈希，比对时必须用同一套测量脚本。代价体现在存储与复现：每个放行版本都要留存基线证据，仓库体积随时间增长；同时回归比对要求测量环境稳定，否则噪声会吞掉真实的劣化信号。

字段阈值类型锚点口径要点
correctness_all_pass判定验证器清单全部用例通过，含边界 shape
speedup_vs_eager相对指定基线版本同 shape、同 dtype、同 warmup
lat_p99_warm_ms绝对SLA 预算切片热缓存、含 launch 开销
mem_peak_ratio绝对设备可用显存峰值而非均值
regress_median_pct回归上一放行证据哈希同一测量脚本

举例：某融合算子在小 shape 上加速比很高，但在长序列 shape 上相对 eager 只有微弱优势。如果速查表只登记一个 speedup_vs_eager 字段并取最优 shape，门禁就会放过一个在真实负载上收益可疑的实现。正确做法是按 shape 分档登记字段，或规定加速比必须取“最差典型 shape”的值。这个选择直接改变放行结论，属于口径决策而非实现细节。

四 · 正确性与数值稳定性的字段化

正确性字段不能只有一个布尔值。至少拆成三层：逐元素数值比对（容差与 dtype 相关）、结构化输出比对（形状、步幅、边界填充）、以及退化输入行为（空张量、单元素、非连续布局）。每层对应独立的证据文件。数值稳定性单独成字段，因为它在浮点累加、归约与低精度路径上会独立失效：一个 kernel 在 fp32 上逐元素全绿，在 bf16 下可能因累加顺序不同而在长归约上超出容差。速查表应登记 tol_atol、tol_rtol 与所测 dtype 组合，而不是笼统写“通过比对”。

代价在于验证时间与 token 消耗：每增加一个 dtype 组合与一个边界用例，验证器就要多跑一次前向并多存一份证据；若验证由 agent 自动生成用例，还会增加生成与筛选的 token 开销。工程判断是：把 dtype 组合限制在“生产实际会走的路径”上，其余组合登记为“不适用”而非“未测”，并在速查表中显式区分这两种状态，避免把未覆盖误读为通过。

具体机制上，数值比对应采用“参考实现 + 双阈值”策略：绝对容差兜住接近零的元素，相对容差兜住大数值元素，二者取或。伪代码思路是：对每个输出元素计算 |a-b| 与 |a-b|/max(|b|, eps)，任一落入对应阈值即视为该元素通过，再统计失败元素比例并要求为零（或对归约类算子允许极小比例但需单独签字）。这个“允许比例”本身就是一个字段，必须显式登记，否则它会以口头约定的形式藏在评审记录里。

五 · 作弊告警与证据留存的字段

防作弊检查的输出必须是结构化告警，而不是一句“未发现异常”。速查表登记三类字段：静态可疑模式命中数（例如绕过计算直接返回缓存结果、对输入做特判分支）、动态行为异常（例如实际未启动预期数量的线程块、kernel 内提前返回）、以及基准贴合度异常（例如对基准 shape 硬编码 tile 尺寸而在其他 shape 上崩溃）。每类告警都要带证据定位：源码行号、profile 中的 launch 配置、或基准用例 ID。告警字段的取值是计数加严重级别，而不是布尔，因为“命中一条低危模式”与“命中高危硬编码”处置不同。

证据留存字段要记录三样东西：产物哈希、采集环境指纹（驱动与工具链版本）、以及采集时间戳。没有环境指纹的证据在跨机器复现时会失去可比性；没有哈希的证据无法证明评审时看到的就是放行时的产物。代价是存储与流程开销：每次放行都要打包证据，打包本身要时间，且环境指纹会暴露工具链漂移，导致原本能过的条目因环境变化被重新审视。这是有意为之的摩擦，它把“环境悄悄变了”从隐性风险变成显性阻断。

具体例子：某 kernel 在基准 shape 上命中硬编码分支，profile 显示实际线程块数远少于理论值，但时延表现优异。若速查表只有“性能达标”与“正确性全绿”两个字段，该实现会被放行；加入“动态行为异常计数”字段后，profile 证据直接把它拦下。这里的性能代价是零（拦下即不部署），但流程代价是一次返工与重新采集证据的时间。

六 · 回滚预案与责任签字的字段化

回滚预案不是文档附件，而是可执行的字段集合：回滚目标版本号、回滚触发条件（哪个度量字段越过哪条红线）、回滚验证方式（回滚后跑哪套冒烟用例）、以及回滚耗时预算。触发条件必须与前面的度量字段同名同口径，否则回滚判断会和放行判断打架。回滚验证方式要登记用例集 ID，而不是“人工确认”。耗时预算字段的存在是为了防止“能回滚但回滚要停机很久”这种伪预案。

责任签字字段按门禁类别拆分：正确性签字人、性能签字人、防作弊签字人、回滚预案签字人。签字人必须是具体角色而非团队名，且签字动作要与证据哈希绑定——签字意味着“我确认这份哈希对应的产物满足该字段”。代价是人力时延：四个签字人串行会拉长放行周期，并行则要求评审者能独立读懂证据。工程判断是把签字拆到“字段组”粒度而非“人”粒度，让同一角色可覆盖多个相邻字段组，同时保留字段级的责任追溯。

最后落在机制上：速查表的每一行都应能回答三个问题——这个字段的值从哪个证据文件来、谁对它签字、它越线时触发什么动作。三个问题答不全的行不应出现在表里，因为它在评审时一定会被重新解释，而重新解释就是门禁失效的起点。

速查表自身的失效边界：阈值口径漂移与证据链断裂

这张表之所以能“照着用”，前提是每一行的字段都绑定了一个不可再解释的判定口径，而不是一个可协商的目标值。工程上最常见的失效不是阈值定错，而是口径漂移：同一字段在不同提交里被不同的人用不同的测量方式填进来，表还在，判据已经失效。典型场景是性能阈值一栏——若“达到基线 X%”没有锁定测量脚本、输入形状集合、warmup 次数与计时方式（CUDA event 还是 wall clock、是否含首次 kernel launch 的 module load），那么两次全绿之间可能差出一整个数量级的噪声。正确性字段同理：全绿必须绑定固定的随机种子集合、容差（atol/rtol）与比较算子（是否对 NaN/Inf 做显式断言），否则“全绿”只是“没崩”。因此速查表的每一行都应携带一个口径指纹，形如

$$\text{gate}_i = \big(f_i,\ \theta_i,\ \pi_i,\ \text{owner}_i,\ \text{evidence}_i\big)$$

其中 $\pi_i$ 是口径指纹（脚本哈希 + 输入集哈希 + 容差参数），$\text{evidence}_i$ 是留存证据的定位符。判定函数为 $\prod_i \mathbb{1}[\text{measured}_i(f_i,\pi_i)\ \text{满足}\ \theta_i]$，任一 $\pi_i$ 与登记值不符即视为该门禁未通过，而不是“结果接近所以放行”。这一条的系统代价是每次提交都要重跑口径校验，编译与 profile 时间被计入 CI 关键路径；对 NCU 采集类门禁，单次采集的时延与显存占用会显著拉长流水线，因此通常把口径指纹校验做成缓存命中即跳过、未命中才重采的二分策略。

第二类失效来自证据链断裂：表要求“证据留存”，但留存的是结论而非可复现的输入。一个具体例子是显存门禁——报告写“峰值显存达标”，却没有记录测量时的 batch 配置、是否开启 activation 重算、allocator 的 reserved 与 allocated 两个口径取的是哪一个。当后续换卡或换驱动后 reserved 口径跳变，历史证据无法回溯判定当时是否真的达标，回滚预案也就失去了触发依据。可操作的约束是：证据必须是“重放即得同一判定”的最小闭包，包含命令、环境指纹（驱动/CUDA/编译器版本）、输入张量的形状与 dtype 清单，以及原始 profile 产物的哈希。代价是存储与检索开销，尤其 SASS 与 NCU 报告体积可观，需要按门禁粒度做保留期分级，而不是全量长期保存。

第三类边界是门禁之间的耦合：作弊告警与性能阈值共享同一份 profile 证据时，若扫描规则版本升级而阈值口径未同步，会出现“性能达标但告警命中”或反之的矛盾结论，此时表不能各自独立判定，必须先对齐 $\pi_i$ 再取合取。回滚预案一栏的失效最隐蔽——它常被填成“已准备”，但触发条件未量化、责任人未具名，等于把判定权交回给人。可执行的写法是把触发条件写成可观测表达式（如连续 N 次门禁失败或某字段超阈），并把责任人与证据定位符一并登记，使回滚本身也成为可审计的门禁项，而不是发布后的事后补救。
