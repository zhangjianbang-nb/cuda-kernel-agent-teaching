一 · 速查表的骨架：一行一个基准，列是口径而非指标

速查表的价值不在“列了多少个基准”，而在每一列都对应一个可执行动作：拿到一个模型产出的 kernel，先查哪一列决定它该进哪个评测入口，再查哪一列决定它的分数能不能被采信。因此表结构应固定为八列：基准名、任务层级、算子集合来源、规模档位、参考实现来源、评分脚本入口、防作弊约束、已知饱和项。前六列是“怎么跑”，后两列是“跑出来的数算不算”。把这两类信息混在一张表里是常见错误：防作弊约束不是元数据，它直接改变分母——一个被判定为调用库函数的提交，其正确性通过率不进分子，也不进分母，而是单独计入拒绝率。

口径上要区分三种“通过”：编译通过、数值通过、性能达标。速查表里每个基准必须标注它的主评分是三者中的哪一个组合。KernelBench 系的主口径是“数值通过 + 相对参考实现的加速比”，TritonBench 与 CUDA-L1 的入口脚本各自定义了不同的聚合方式，因此跨基准比较加速比是无效操作，表里必须显式写出“不可跨基准比较加速比”这一约束，否则读者会把 L1 的小算子加速比与 L3 的整模型加速比放在同一张柱状图上。

$$\text{score}=\mathbb{1}[\text{correct}]\cdot\frac{t_{\text{ref}}}{t_{\text{sub}}},\quad \text{denom}=\sum_{i}\mathbb{1}[\text{admissible}_i]$$

这个式子的工程含义是：分母只统计“可采信”的提交。一个提交若触发防作弊约束（例如直接 import torch 的算子实现、缓存输出、按输入形状硬编码分支），它既不得分也不稀释他人分数。代价体现在时延上：每个提交都要跑一次静态检查加一次动态探针，单次探针的额外开销在毫秒量级，但对几千个提交的批量评测，这部分时延会挤占 GPU 排队时间，需要在调度上把静态检查放到 CPU 侧先行过滤。

具体例子：某提交在 L1 的 elementwise 算子上报出加速比，但其源码里出现 torch.nn.functional 调用路径，静态检查命中后该行被标为 inadmissible，分数记零而非记一。速查表若没有“防作弊约束”这一列，读者会误以为这是一个有效正样本并拿去喂 RL。

二 · 层级与规模档位：L1/L2/L3 的分档决定分母形状

KernelBench 的 L1/L2/L3 不是难度标签，而是三种不同的分母形状。L1 是单算子、单 kernel 粒度，分母是算子数；L2 是融合模式（若干算子串成一个小图），分母是融合模式数；L3 是端到端模型片段，分母是模型数。速查表必须写出每一档的“规模档位”字段，即该档内输入张量的形状分布是固定集合还是按参考实现采样。这一字段直接决定正确性 oracle 的构造方式：固定形状集合可以用逐元素全等比较，采样形状则需要容差与随机种子绑定。

机制上，规模档位影响的是编译时间与显存两项代价。L1 单算子编译时间短，可对每个提交做多形状重编译验证；L3 端到端片段往往包含多个 kernel 与 host 侧逻辑，单次编译加运行的时间被拉长，此时评测预算必须按“每模型固定 trial 数”而非“每形状固定 trial 数”来分配。显存方面，L3 的激活值驻留使峰值显存成为硬约束，速查表应标注该档是否要求提交在给定显存上限内完成，超出即判失败而不是降速通过。

层级分母单位规模档位字段主要代价饱和风险
L1单算子形状集合固定/采样编译时间（每形状重编译）高：小算子易被库函数覆盖
L2融合模式图内算子数与连接方式中间张量显存中：融合收益上限明确
L3模型片段端到端输入分布峰值显存 + host 逻辑时延低：但方差大

具体例子：L2 的一个融合模式把逐元素加与归约串在一起，提交若只优化了归约而保留两次全局读写，数值通过但加速比接近一；速查表在“已知饱和项”列标注该模式已被参考实现逼近带宽上限，读者据此不再把该类样本当作有效训练信号。代价是：这类样本若仍进入 RL 批次，会以接近零的奖励方差占用 token 预算。

三 · 参考实现来源与评分脚本入口：口径的物理落点

“参考实现来源”这一列不是出处标注，而是正确性 oracle 的物理落点。速查表要写清三件事：参考实现是框架算子、手写 CUDA 还是编译期生成的 IR；参考实现是否与提交共享同一输入生成器；评分脚本入口是单文件还是需要环境变量注入。三者任一不匹配，数值通过率就不可比。工程上最常见的失配是输入生成器不一致——参考实现用固定种子生成，提交侧却按自己的分布采样，于是“通过”只证明了两个不同问题上的巧合。

评分脚本入口的字段要精确到调用形式，例如“以模块方式导入并调用 run()，返回 (correct, time_ms, meta) 三元组”。这个三元组的 meta 字段承载防作弊判定结果与编译日志摘要，是后续 profile 关联的锚点。代价在于：入口若要求每次评测重启进程以隔离 CUDA context，单次评测的启动时延会显著上升；批量评测时必须做进程池复用，否则时延开销会淹没真实 kernel 时间。

$$\text{admissible}=\text{static\_ok}\land\text{no\_cache}\land\text{shape\_general}\land\text{no\_lib\_call}$$

这四个合取项对应速查表“防作弊约束”列的四条子项，缺一不可。静态检查看源码符号，缓存检查看多次调用间输出是否随输入变化，形状泛化检查用扰动形状重跑，库调用检查看动态链接与调用栈。每条检查都有误杀代价：形状泛化检查对确实只支持固定形状的合法提交会误判，因此速查表要标注该基准是否允许“声明支持形状集”并据此豁免。

具体例子：TritonBench 的入口脚本对 Triton 提交要求提供 autotune 配置的显式声明，若提交在运行时静默 autotune 到与参考实现相同的配置，性能数字虽高但可复现性差；速查表在约束列写明“autotune 配置须随提交固化”，并把可复现性作为采信前提。代价是固化配置牺牲了运行时自适应带来的少量时延收益。

四 · 已知饱和项：为什么速查表必须带“负样本”列

饱和项是速查表里最容易被忽略、却最影响评测可信度的一列。一个算子或融合模式若已被参考实现逼近 roofline 上限，那么任何提交的加速比都挤在噪声带内，其奖励信号不可用于 RL。速查表标注饱和项的作用是把这个样本从“有效训练信号”降级为“回归测试用例”——它仍能检出正确性回归，但不再提供梯度。

机制上，判定饱和需要两个量：参考实现的 SOL 利用率与提交相对参考实现的时延分布方差。前者接近上限、后者方差大于均值时，该样本应标饱和。速查表不写具体阈值数字，只写判定口径：以 roofline 模型给出的带宽或算力上限为分母，参考实现利用率高于某档即视为饱和候选，再由方差确认。代价是：为算方差需要对同一提交多次重跑，评测时延按 trial 数线性增长，因此饱和判定应放在离线批处理而非在线评分路径上。

  • 饱和样本仍进正确性回归集，不进奖励聚合。
  • 饱和判定结果写入 meta，供后续 profile 关联。
  • 同一算子在不同规模档位下饱和状态不同，标注须带档位。

具体例子：L1 的逐元素算子在大形状下已被参考实现打到带宽上限，提交即便用了向量化加载也只带来噪声级差异；速查表在该行“已知饱和项”列写明“大形状档饱和，小形状档未饱和”，读者据此只取小形状档样本。代价是可用样本数下降，需要从其他层级补足批次。

五 · 字段间的耦合：阈值不是孤立数字

速查表若把每列当作独立字段填写，会漏掉字段间的耦合，导致口径自相矛盾。三组关键耦合是：规模档位与容差、参考实现来源与形状泛化豁免、评分入口与进程隔离。规模档位越小，浮点累加顺序差异越显著，容差必须随档位收紧或放宽；参考实现若本身是框架算子，其内部可能已做形状特化，此时对提交的形状泛化要求应放宽到与参考实现同等；评分入口若不做进程隔离，缓存检查会因 CUDA context 残留而误判。

$$\text{tol}=f(\text{reduction\_depth},\text{dtype}),\quad \text{trials}=\lceil \sigma^2/\delta^2\rceil$$

第一式说明容差是归约深度与数据类型的函数，速查表不应写死一个全局容差数字，而应写“容差随档位由评分脚本按此式生成”。第二式说明 trial 数由方差与目标置信区间宽度决定，这直接对应评测时延预算：方差大的 L3 样本需要更多 trial，单样本时延上升，批量评测的 GPU 排队时间随之上升。工程判断是：把 trial 预算按层级分配，L1 少 trial 多形状，L3 多 trial 少形状。

具体例子：某提交在 L3 上数值通过但加速比在多次 trial 间跳动，速查表若未标注该档的 trial 口径，读者会取单次最优值上报，造成选择性偏差。正确做法是按评分入口返回的 meta 取聚合统计量，并把方差一并记录。代价是记录方差增加了存储与后处理开销，但这是可采信评测的必要成本。

最后落在工程判断上：速查表的每一行都应能被一个脚本直接消费——字段名即变量名，阈值即脚本参数，口径即断言条件。当一行无法被脚本消费时，说明该行的口径尚未收敛，应退回定义阶段而不是靠人工解读补齐。防作弊约束列与饱和项列尤其如此：它们不是给人看的备注，而是评分脚本里必须求值的布尔量与降级标记。

速查表的失效边界：字段口径漂移、阈值饱和与防作弊代价

这张表能照着用，前提是承认它是一张“带失效条件”的表。字段层面最易踩的坑是口径漂移：L1/L2/L3 的“规模档位”在条目里是算子集合与规模档位的并列描述，但评分脚本入口与参考实现来源并非同一套——同一算子在不同基准里可能挂着不同来源的参考实现，于是“正确性通过”与“性能达标”两个字段的判定基准并不同源。工程上必须把表拆成两列语义：参考实现来源决定正确性 oracle 的容差形态（逐元素比对还是归约后比对），评分脚本入口决定计时口径（是否含 warmup、是否固定迭代数）。把两者混为一列，就会在跨基准比对时把“口径差异”误读为“实现差异”。

$$\text{可比性} = \frac{\text{同源参考} \times \text{同口径计时}}{\text{跨源参考} + \text{混合口径}} \le 1$$

阈值侧的失效条件是饱和项。条目明确标注各基准存在已知饱和项：当某算子的参考实现已接近硬件上限，评分脚本给出的加速比字段会长期贴在饱和区，此时该字段不再区分“好实现”与“更好实现”，只区分“是否退化”。速查表若把饱和项与未饱和项混排在同一阈值列，读者会拿一个已饱和算子的阈值去卡一个仍有优化空间的算子，得到错误的“已达标”判断。代价是显性的：饱和项上的多轮优化会消耗编译时间与 token 预算却换不来评分提升，而真正未饱和的算子被挤占迭代轮次。具体例子是归约类算子——其参考实现往往已用足带宽，加速比字段饱和，而同一档位下的逐元素算子仍有明显余量，两者必须分列标注。

防作弊约束的系统代价落在验证链上。条目要求标注各基准的防作弊约束，这意味着评分脚本入口不只是计时器，还承担输入扰动、调用序列检查与结果复算。每加一层约束，单次评测的时延与显存占用上升，且复算步骤会额外占用带宽；对大规模档位，复算本身可能成为瓶颈，使“评测吞吐”而非“kernel 吞吐”成为限制项。工程判断是：把防作弊约束按算子档位分级启用，L1 小规模档位全量启用，L3 大规模档位只保留调用序列检查与抽样复算，用抽样率换取评测吞吐，同时在表中显式记录抽样率字段，避免读者把抽样复算的通过率当成全量正确性。

规模档位饱和项与未饱和项混排编译时间与 token 空耗
