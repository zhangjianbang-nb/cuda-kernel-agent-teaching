一 · 阈值不是拍脑袋：从测量口径反推可接受线

工程阈值的合法性来自它背后的测量口径，而不是来自某个流传的数字。同一句“加速比 1.2 倍才算通过”，在分母取 eager 单次冷启动、还是取 warmup 后中位数、还是取 torch.compile 产物时，含义完全不同。因此本节的写法是：先固定分子分母，再谈阈值；口径未定就先把口径测出来，而不是先定阈值再凑数据。

一个可操作的机制是把阈值写成“口径函数”而非常数。设被测 kernel 的时延样本为 t_1..t_n，基线为 b_1..b_m，则加速比 S = median(b) / median(t)。阈值应表述为“在 warmup=W、重复 n 次、取中位数、基线为同 shape 的 eager 实现”这一组约束下的 S ≥ s_0。任何一项约束变化，阈值必须重测，不能平移。

$$S=\frac{\operatorname{median}(b_{1..m})}{\operatorname{median}(t_{1..n})},\qquad \text{CI}_{95\%}(S)\ \text{由 bootstrap 重采样给出}$$

代价在这里体现得很直接：把重复次数从 n 提到 4n，测量时延线性增长，而置信区间宽度按 1/\sqrt{n} 收缩；如果 kernel 单次运行只有几十微秒，那么测量开销会迅速超过 kernel 本身，评测流水线的墙钟时间成为瓶颈。具体例子：一个 elementwise 融合 kernel 单次 30 微秒，取 n=200 做中位数，单次评测约 6 毫秒，尚可接受；若为了压 CI 取 n=5000，单次评测 150 毫秒，在几百个候选上跑多轮 RL，评测成本就会盖过生成成本。此时正确做法是固定 n 并报告 CI 宽度，而不是无限加采样。

二 · 经验数字的三种来源与各自的失效边界

工程上流通的“经验数字”只有三类合法来源：硬件规格推导、实测标定、以及基准分布统计。三者失效边界不同，混用是口径事故的主要来源。

  • 硬件规格推导：由峰值带宽、峰值算力、SM 数量推出 roofline 上界，得到 SOL 利用率的分母。它给的是上界，不是可达值；把上界当阈值会把正常 kernel 判成不合格。
  • 实测标定：在同一张卡、同一驱动、同一编译选项下测出的微基准，例如纯拷贝带宽、纯 FMA 吞吐。它给的是“这台机器此刻的可达天花板”，跨卡、跨驱动即失效。
  • 基准分布统计：在 KernelBench 系任务集上统计某类算子的加速比分布，取分位数作为门槛。它给的是“同类任务的相对位置”，任务分布一变即失效。

机制上，把三者串成一条链：规格推导给分母，实测标定给可达系数 \eta，基准分布给分位门槛 q。SOL 利用率定义为 U = \text{achieved} / \text{peak}，而工程上真正可比的是 U/\eta，即“相对可达天花板的比例”。代价是标定本身要花编译与测量时间：每次换驱动或换编译 flag，\eta 都要重测，否则阈值漂移。具体例子：某 reduction kernel 达到峰值带宽的 62%，看似平庸；但该卡实测拷贝带宽只有峰值的 78%，则相对可达比例为 0.62/0.78≈0.79，属于正常区间。若直接用 0.62 对 0.9 的门槛，会误杀。

三 · 编译与 autotune 时间：必须计入分母的那部分

kernel agent 的产物往往带 autotune，而 autotune 的搜索时间经常被悄悄排除在加速比之外，造成“离线调好、线上吃亏”的口径偏差。规范做法是把编译时间 T_c 与 autotune 时间 T_a 显式列为独立指标，并规定它们是否进入端到端时延的分母。

两种口径必须同时报告：稳态口径（排除 T_c+T_a，只测热态单次）与冷启动口径（T_{e2e} = T_c + T_a + N\cdot t_{hot}，N 为批内调用次数）。前者用于比较 kernel 质量，后者用于判断生产可用性。阈值也应分设：稳态看加速比，冷启动看“摊销调用次数” N^* = (T_c+T_a)/(t_{base}-t_{hot})，即多少次调用才能把编译开销赚回来。

$$N^{*}=\frac{T_{c}+T_{a}}{t_{\text{base}}-t_{\text{hot}}}$$

代价是编译时间在 Triton/CuTe 路径上波动极大，且与候选数量成正比；autotune 的配置空间每扩大一倍，T_a 近似线性增长，而收益往往只在少数 shape 上体现。具体例子：一个 matmul kernel 稳态比基线快 15%，但 autotune 花掉数秒编译；若线上每次请求只调用一次，N^* 远大于 1，冷启动口径下它是净亏的。此时工程判断是缓存 autotune 结果并按 shape 分桶，而不是把 T_a 从统计里删掉。

四 · 显存与带宽阈值：用占用率而非绝对字节

显存占用的阈值不应写成“不超过 X GB”，而应写成相对可用显存的占用率，并区分峰值与稳态。机制上，峰值占用由 workspace、autotune 候选缓冲、以及框架侧缓存共同决定，其中 autotune 候选缓冲是最容易被忽略的一项：搜索期间同时驻留多份输出缓冲，峰值可能是稳态的数倍。

规范要求同时记录 M_{peak}、M_{steady} 与 M_{budget}（可用显存减去框架保留），阈值表述为 M_{peak}/M_{budget} \le r。带宽侧则用有效带宽 B_{eff} = \text{bytes moved} / t 与实测可达带宽之比，而不是与峰值带宽之比。代价是显存峰值测量需要插桩或分配器钩子，插桩本身改变时序，因此显存与时间必须分两轮测，不能在同一轮里既测峰值又测时延。

具体例子：一个 attention kernel 稳态占用很小，但 autotune 阶段因并行候选导致峰值翻数倍，在长序列 shape 上触发 OOM；若只看稳态占用，这个失败在评测中不可见。工程判断是把“autotune 峰值占用”作为独立门槛，超限则强制串行搜索，用编译时间换显存峰值。

五 · 没有数字时怎么写清测量方法

当任务缺少可引用的经验数字时，规范要求写出可复现的测量协议，而不是留空或写“视情况而定”。协议至少包含五项：warmup 次数与判定收敛的方法、重复次数与采样方式、统计量（中位数还是均值）、离散度指标（CI 或 IQR）、以及基线实现的确切来源。

  • warmup：以连续若干次时延的相对变化低于某比例作为收敛判据，而不是固定次数；固定次数在冷缓存与频率爬升场景下不可靠。
  • 重复：同一 shape 内重复，跨 shape 不混采样；混合采样会让中位数失去意义。
  • 统计量：时延分布右偏，用中位数；吞吐用总字节除以总时间，不用逐次平均。
  • 离散度：报告 bootstrap CI 或四分位距，并注明重采样次数。
  • 基线：注明是 eager、torch.compile 还是手写参考，以及是否含其自身的编译时间。

代价是这套协议让单次评测的墙钟时间与 token 消耗都上升：多轮 RL 中每个候选都要跑完整协议，评测吞吐下降，反过来限制了每轮候选数。具体例子：某任务无历史分布可依，作者按上述协议测出基线中位数与 CI，并把阈值设为“中位数优于基线且 CI 不重叠”，这是一个不依赖任何外部数字、可被复算的门槛。工程判断是：宁可阈值保守、协议透明，也不要用一个来源不明的数字充当门槛，因为后者在换卡、换驱动后无法归因。

阈值不是常数：工程经验数字的边界、失效条件与系统代价

把“加速比 ≥ 1.0”“SOL 利用率 ≥ 60%”“显存占用 ≤ 80%”这类数字写进规范时，最容易犯的错误是把它们当成物理常数。这些阈值本质上是带条件的判据：它们只在特定的测量口径、特定的输入分布、特定的硬件与软件栈下成立。一旦口径漂移，同一个 kernel 可以从“通过”翻转为“不通过”，而 kernel 本身一行代码都没改。因此规范里每个经验数字都必须绑定三件事：分子分母定义、测量协议（warmup、重复次数、统计量）、以及失效时的降级判定路径。缺任何一项，阈值就退化为不可复现的口号。

以 SOL 利用率为例，其口径必须显式写成受限资源上的比值，而不是笼统的“峰值占比”。对访存受限 kernel，分母应取该卡在目标频率下的可持续带宽而非理论峰值带宽：

$$\mathrm{SOL}=\frac{\text{实测有效字节数}/\text{中位耗时}}{\min(\text{可持续带宽},\ \text{可持续算力}/\text{算术强度})}$$

这里“有效字节数”必须按算法语义计数（例如 GEMM 只计读入的 A、B 与写出的 C，不计被 cache 吸收的重复访问），否则分母被人为压低、SOL 虚高。代价在于：可持续带宽本身依赖 occupancy 与访问模式，单靠一个标称值会在小尺寸问题上高估上限，导致一个实际已接近最优的 kernel 被判为“未达标”。工程判断是——对小尺寸输入，SOL 判据应切换为“相对同口径 baseline 的加速比”，因为此时启动开销与尾部效应主导，SOL 的分母失去意义。

加速比与 pass@k 的阈值同样有边界。加速比的分母必须是同 warmup、同重复次数、同统计量测出的 baseline 中位耗时；若 baseline 用了更短的 warmup，其耗时被首次调用开销污染，加速比会被系统性高估。pass@k 的失效条件更隐蔽：当 k 增大而候选生成高度同质（同一模板微调），pass@k 的边际增益迅速饱和，此时用大 k 的阈值做筛选等于用 token 预算换一个几乎不变的通过率。测量方法上，应固定采样温度与候选去重策略，并报告 k 对应的候选池实际多样性（如去重后唯一 kernel 数），否则 pass@k 只是重复计数的产物。

显存与编译/autotune 时间是两类最容易被阈值误伤的代价项。显存判据若只看稳态占用，会漏掉 autotune 阶段多个配置同时驻留造成的峰值；正确做法是记录整个搜索过程的峰值分配，并把“候选并行度”作为可调旋钮——降低并行度能压峰值，代价是搜索墙钟时间线性上升。编译与 autotune 预算则是端到端收益的隐形杀手：一个 kernel 的稳态加速比为 1.3，但若 autotune 花掉的墙钟超过被优化算子在真实负载中的总运行时间，端到端就是负收益。规范应要求同时报告“稳态加速比”与“含编译摊销的端到端加速比”，后者以真实调用次数为分母摊销，而不是以单次调用计。没有实测数字时，写清测量方法即可：固定输入集、固定 warmup 与重复次数、取中位数并给出置信区间，把 autotune 墙钟单独计时并注明是否计入端到端。

阈值不是常数：把经验数字钉在分母口径上

工程阈值失效的第一种方式，是分母被悄悄换掉。同一个“加速比 1.3×”在两种口径下含义完全不同：分母取 baseline 的单次 kernel 耗时，还是取包含 launch、同步与 Python 侧调度的端到端耗时。前者衡量 kernel 本身，后者衡量用户感知。当 baseline 的 kernel 只占端到端 40% 时，kernel 侧 2× 的加速在端到端只剩约 1.25×，于是“加速比阈值 1.3”在 kernel 口径下通过、在产品口径下不通过。规范的做法是把阈值写成三元组（指标、分母定义、测量域），并强制在报告里同时给出两个域的数字。代价是每次评测要多跑一遍端到端路径，端到端测量本身含同步开销，重复次数需比 kernel 侧多，token 与 wall-clock 成本随之上升；收益是阈值不再随实现细节漂移。

第二种失效来自 warmup 与统计量的耦合。GPU 首次 launch 含上下文初始化、JIT 与 cache 冷启动，若把首次样本计入均值，小规模 kernel 的均值会被抬高一个量级。规范应固定：warmup 至少覆盖一次完整 autotune 与一次显存分配峰值，正式样本取中位数而非均值，并给出置信区间。对 n 次重复的中位数，可用分位数自助法（bootstrap）估计区间，重采样次数 B 取数百量级即可稳定：

$$\hat{\theta}^{*}_{(1-\alpha)} = \text{quantile}_{1-\alpha}\{\text{median}(x^{(b)})\}_{b=1}^{B}$$

这里 x^(b) 是从 n 个样本中有放回抽样的重采样。若区间半宽超过中位数的 5%，说明样本不足或存在双峰（例如 autotune 选中了不同 config），此时不应直接与阈值比较，而应先定位双峰来源。代价是 bootstrap 在 CPU 侧引入额外计算，n 与 B 同时增大时统计耗时不可忽略；对编译与 autotune 时间这类一次性成本，重复次数应显著低于稳态 kernel 时间，否则测量本身污染被测对象。

第三种失效是 SOL 利用率的分母选错 roofline 拐点。以 HBM 带宽为上限的 memory-bound kernel，其 SOL 分母应是“字节数 / 峰值带宽”，而非峰值 FLOPS；若误用算力上限，利用率会被系统性高估。判断 bound 类型应先用算术强度 I = FLOPs / Bytes 与机器平衡点比较，再选分母。显存占用阈值同理：峰值显存必须在 autotune 全部候选 config 跑过之后取 max，而不是取最终选中 config 的稳态值，否则会漏掉候选阶段的瞬时峰值，导致部署时 OOM。编译时间阈值则要区分冷编译与缓存命中，前者含 PTX→SASS 与链接，后者接近零，混在一起统计会让阈值失去意义。
