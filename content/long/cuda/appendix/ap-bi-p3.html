一 · 阈值的来源：从 roofline 反推，而不是拍脑袋

工程阈值的第一个原则是：凡是能由 roofline 推出的数字，就不要凭经验给。给定 kernel 的算术强度 I（FLOP/Byte）、机器的峰值算力 P 与峰值带宽 B，roofline 上界为 min(P, I·B)，实测有效吞吐 T 相对该上界的比值就是 SOL 利用率。阈值应当直接定义在这个比值上，而不是定义在「TFLOPS 大于某个数」这种脱离形状的绝对量上——同一个 kernel 在 batch=1 与 batch=64 下的绝对吞吐差一个数量级，但 SOL 利用率是可比的。

$$ \text{SOL} = \frac{T}{\min(P,\; I \cdot B)}, \qquad I = \frac{\text{FLOPs}}{\text{Bytes}_{\text{HBM}}+\text{Bytes}_{\text{L2}}\cdot \alpha} $$

分母里的 α 是 L2 命中折算系数，因为 L2 带宽远高于 HBM，把 L2 流量按 HBM 计会低估上界。工程上更稳的做法是分别算两个上界：纯 HBM 版（保守，作为告警下限）与含 L2 折算版（乐观，作为目标线），把两者之间的区间作为「可接受带」。这样阈值自带物理含义，换了 GPU 只需换 P、B 两个常数，不必重新调参。

代价在于测量本身：SOL 需要可信的 FLOPs 与 Bytes 计数。FLOPs 可由形状静态推导，Bytes 必须来自 NCU 的 dram__bytes 与 lts__t_bytes 计数器，而 NCU 采集本身会让 kernel 降频、拉长时延（单次 profile 的墙钟开销通常是 kernel 本身时延的数十倍到上百倍量级，取决于采集的 section 数量）。因此 SOL 阈值只能用于离线回归，不能挂在在线热路径上。具体例子：一个 GEMM 形状 M=N=4096, K=4096，静态 FLOPs 为 2MNK，Bytes 约为 (MK+KN+MN)·4，算术强度落在数十 FLOP/Byte 量级，属于 compute-bound 侧；此时若实测 SOL 只有三成，问题几乎一定在流水线（tile 太小、bank conflict、寄存器压力导致 occupancy 塌陷），而不是带宽。

二 · 正确性阈值的分层：位精确、容差、统计等价

正确性阈值不能只有一个「allclose 通过」。工程上分三层，每层有各自的判定口径与代价。第一层是位精确（bit-exact），只适用于整数 kernel、索引类 kernel、以及确定性归约的固定顺序实现；它的代价是几乎完全禁止编译器重排与融合，任何 -use_fast_math 或 FMA 收缩都会破坏它。第二层是逐元素容差，形如 |a-b| ≤ atol + rtol·|b|，这是绝大多数浮点 kernel 的默认口径。第三层是统计等价：当 kernel 内部改变了归约顺序（split-K、树形归约、warp shuffle），逐元素比较会因浮点非结合性而失效，必须改用分布层面的判据。

$$ \frac{\lVert a-b \rVert_2}{\lVert b \rVert_2} \le \varepsilon_{\text{rel}}, \qquad \max_i \frac{|a_i-b_i|}{\max_j |b_j|} \le \varepsilon_{\infty} $$

相对 L2 误差与「以最大元素归一化的最大绝对误差」是两个互补口径：前者对整体漂移敏感，后者对局部尖点敏感。实践中常见的问题是只测前者，于是某个被放大的离群元素被总量掩盖。第三层的代价是它无法定位错误位置——统计等价通过但单点错了的情况是存在的，尤其在 softmax、layernorm 这类含减均值的算子里，均值偏移会被后续归一化吃掉一部分误差。因此统计等价必须配合「关键中间量抽查」：在 kernel 内部保留少量探针输出（如行最大值、行和），对这些探针做逐元素比较。

具体例子：一个 split-K 的 GEMM，K 方向切成 8 段并行累加，累加顺序不确定。此时逐元素 allclose 在 atol 取极小值时必然随机失败，正确做法是把 ε_rel 定在与「单精度累加 4096 项的最坏舍入界」同量级，并把参考实现也改成高精度累加（fp64 或 Kahan 补偿），使误差来源单一化。若参考实现本身用 fp32 顺序累加，则比较的是两个都有误差的量，阈值失去意义。

三 · 性能阈值的三个时间尺度：冷启、稳态、回归

同一个 kernel 的时延在三个尺度上含义完全不同，阈值必须分开定。冷启时延包含模块加载、JIT 编译、首次 cuModuleLoad 与上下文初始化；稳态时延是预热若干次后的中位数；回归时延是相对基线 commit 的比值。把三者混成一个「平均时延」是观测性检查里最常见的口径错误。

  • 冷启：对 Triton 而言包含 AST 解析、IR 下降、PTX 生成、cubin 编译与加载，量级可达数百毫秒到数秒，且与 kernel 复杂度强相关；对 CUDA C++ 则是 nvcc 编译时间加模块加载。阈值应设为「冷启时延 ≤ k × 稳态时延」这种相对形式，避免绝对毫秒数随机器漂移。
  • 稳态：必须用中位数而非均值，因为 GPU 上的时钟抖动、其他进程抢占、ECC 扫描都会产生长尾。采样次数要足以让中位数的置信区间收敛，通常需要几十到上百次迭代，具体次数由测得的方差决定，而不是固定值。
  • 回归：用比值而非差值。差值在快 kernel 上会被噪声淹没，比值在小基数上会被放大。回归阈值应同时约束「比值上界」与「绝对增量下界」——只有两者同时越界才告警，否则小 kernel 的 5% 抖动会天天触发。

测量方法上，稳态时延必须用 CUDA event 包夹在流内，不能用 host 侧 wall clock，否则会把异步提交的开销算进去。代价是 event 本身有固定开销（量级在微秒级），对亚微秒 kernel 会显著污染测量，此时应改为「N 次连续发射的总时间除以 N」的批量测法，用摊销把 event 开销压下去。具体例子：一个 elementwise kernel 稳态时延在个位数微秒，单次 event 包夹测出的数字会被 event 开销抬高数成；改成发射 1000 次再除，测量误差立刻降到可接受范围，代价是单次测量占用 GPU 时间变长，回归流水线的墙钟时间随之上升。

四 · 显存与占用率的经验带：不是越高越好

显存阈值分两类：峰值占用与碎片化。峰值占用应在 kernel 启动前后用 cudaMemGetInfo 采样，并留出安全余量——余量的大小由「同一进程内其他 kernel 的并发峰值」决定，而不是拍一个百分比。碎片化的判据是「最大可分配块 / 总空闲显存」，这个比值低说明空闲显存虽多但被切碎，后续大块分配会失败。这个指标在长跑推理服务里比峰值占用更能预测 OOM。

占用率（occupancy）是另一个容易被误用的阈值。occupancy 高不等于快：一个寄存器压力极大的 kernel 强行压低寄存器数以提升 occupancy，反而会因为 spill 到 local memory 而变慢。经验带应当写成「occupancy 不低于某个下限，且 spill 字节数为零」的合取条件。下限的取法是从 roofline 反推：若 kernel 是 latency-bound（算术强度低、访存为主），需要足够多的 warp 来隐藏访存延迟，下限就高；若是 compute-bound 且指令级并行充分，下限可以低。代价是 occupancy 与 spill 都是编译期属性，改动一个 __launch_bounds__ 就要重新编译，编译时间成本在 Triton 上尤其明显（每次 autotune 配置变更都触发一次完整编译）。

具体例子：一个 reduction kernel 在 block=1024 时 occupancy 受限，降到 block=256 后 occupancy 翻倍但时延反而变差，原因是跨 block 的原子累加次数增加、L2 流量上升。这说明 occupancy 阈值必须与「每字节有效工作量的访存次数」联合看，单看 occupancy 会给出错误结论。

五 · 可追溯性阈值：环境快照的完备性判据

可观测性检查里最容易被忽略的一类阈值是「追溯完备性」：一次 kernel 生成记录必须能唯一还原出当时的执行环境。判据可以写成一组必填字段的合取，任缺一项即视为不可追溯。字段包括：源码 commit、kernel 源码哈希、驱动版本、CUDA runtime 版本、cuBLAS/cuDNN/Triton 等库版本、GPU 型号与 SM 数、编译选项（含 -arch 与 fast-math 开关）、以及测量时的时钟与功耗状态。

$$ \text{Traceable}(r) = \bigwedge_{f \in F} \text{present}(r.f) \;\wedge\; \text{hash}(r.\text{src}) = r.\text{src\_hash} $$

这里的代价是存储与写入开销：每次生成都落一份完整环境快照，会让实验追踪的体积随轮数线性增长；工程上通常做「环境指纹去重」——把上述字段规范化后算一个指纹哈希，相同指纹只存一份，记录里只存指纹。代价是查询时要多一次 join，且指纹算法一旦变更就要重算历史数据。另一个代价是时钟与功耗状态的采集需要额外调用（NVML），在高频生成循环里会成为瓶颈，因此这类字段适合按「每 N 次采样一次」的节奏写入，而不是每次全量采集。

具体例子：同一个 kernel 源码在两个不同驱动版本下 SOL 利用率相差明显，若记录里没有驱动版本字段，回归告警会被误判为代码退化，排查方向完全错位。把驱动版本纳入指纹后，这类告警会被自动归因到「环境变更」而非「代码变更」，这是可追溯性阈值真正的工程价值——它不是合规动作，而是把回归告警的信噪比抬上去的手段。

六 · 失败样本归档的阈值：什么值得留，留多久

失败样本归档不能全留，也不能只留计数。判据应基于「可复现性」与「信息增益」两个维度。可复现性指该失败能否在固定环境下稳定重现；信息增益指该失败是否揭示了此前未覆盖的失败模式。工程阈值可以写成：稳定复现的失败必须留完整输入、完整环境指纹与最小复现脚本；不稳定复现的失败只留输入形状、随机种子与统计摘要；重复命中同一失败模式指纹的样本只保留首个与最近一个，中间样本折叠为计数。

  • 留完整的代价是存储：一个含大张量输入的失败样本可能占用与模型激活同量级的显存镜像，落盘后体积可观，因此归档前应做输入张量的最小化——把触发失败的最小形状与最小数值范围找出来，这本身需要额外的搜索时间。
  • 折叠的代价是丢失演化信息：同一失败模式在不同 commit 上的表现可能变化，只留首末两个样本会掩盖中间态。折中做法是保留「失败模式指纹 + commit + 关键指标」的轻量三元组，重样本按需重建。
  • 回归告警的阈值要与归档联动：当某失败模式指纹在近期窗口内重新出现，才触发高优先级告警；否则仅记录。这样避免了「历史失败反复告警」的疲劳。

具体例子：一个 kernel 在特定 M 不是 tile 整数倍时越界写，属于稳定复现类失败，必须留最小复现脚本与完整环境指纹；而一个因时钟抖动导致的偶发超时，属于不稳定复现类，只需记录形状、种子与超时分布摘要。把这两类混在同一归档策略里，会导致存储被偶发样本撑爆，同时真正需要复现的越界样本因为脚本缺失而无法重放。

阈值不是拍脑袋：可追溯性检查的量化口径与失效边界

可追溯性检查最容易退化成“看板上有图就算通过”。工程上应把它拆成四个可测布尔量：追踪记录是否携带 commit SHA、环境快照是否固定驱动/CUDA/库三件套、失败样本是否带复现命令归档、回归告警是否绑定到具体 kernel 变体。阈值的作用不是判断“好不好”，而是判断“能不能在事故后 30 分钟内重建现场”。一个可操作的判据是覆盖率公式：trace_coverage = 带完整环境指纹的 kernel 记录数 / 总 kernel 记录数，分母取最近一个回归窗口内的全部生成产物，分子要求 commit、驱动版本、CUDA 版本、关键库版本四项同时非空。低于 1.0 时不谈性能收益，先补记录；因为任何一次 NCU profile 与 SASS 对照，一旦缺少环境指纹就无法归因到具体 commit，优化结论直接作废。

经验数字要按“代价”而非“偏好”设定。追踪写入本身有 token 与时延代价：每条记录多存一份环境快照，在批量生成场景下会放大归档体积与检索延迟；失败样本归档若保留完整输入张量与中间 buffer，显存与磁盘占用随失败率线性上升。因此阈值应写成预算约束：归档保留率、快照字段数、告警静默窗口三者互相挤压。一个具体例子是回归告警：若把告警绑定到 kernel 变体而非 commit，同一变体在不同驱动下复现失败会被误判为“已修复”，此时应把告警键改为 (commit, driver, cuda, lib) 四元组，代价是告警条数上升、去重逻辑变复杂，收益是失败样本可被精确重放。

没有数字时写清怎么测，而不是留空。测量方法应固定为：在同一回归窗口内抽取全部失败样本，逐条执行“仅凭归档记录重建环境”的脚本，记录重建成功数与耗时；重建失败即视为可追溯性缺口，按缺口类型（缺 commit、缺驱动、缺库版本、缺复现命令）分类计数。该测量不依赖硬件参数，只依赖归档完整性，因此可在 CI 中作为门禁运行。失效条件是明显的：当生成流水线绕过追踪中间层直接写盘，或环境快照取自宿主而非容器，覆盖率会虚高而重建仍失败——这时阈值必须下调为“重建成功率”，而不是“字段非空率”。
