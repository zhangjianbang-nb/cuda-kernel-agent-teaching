一 · 基准条目的准确定义：一个 kernel 任务由什么构成

在 KernelBench 系基准里，“条目”（entry）不是一句“写个 softmax”的口头需求，而是一个可被判定的五元组：算子语义、输入规格、参考实现、评分脚本、约束声明。缺少任何一项，条目就无法进入自动评测闭环——没有输入规格就无法构造测试张量，没有参考实现就没有正确性 oracle，没有评分脚本就没有可比的时延口径，没有约束声明就无法区分“优化”与“作弊”。工程上把这五项写进同一份结构化描述（通常是一个 Python 模块加一份 YAML/JSON 元数据），评测器只读这份描述，不读 agent 的自然语言解释。

算子语义必须是可执行的，而非自然语言描述。KernelBench 的条目普遍以 PyTorch 参考实现作为语义载体：给定 `Model` 类的 `forward`，其数值输出即为语义定义。这带来一个关键性质——语义是“参考实现所算出的东西”，而不是“数学上应该算出的东西”。当参考实现本身在边界条件上有特定行为（例如对空张量返回空、对 NaN 传播的取舍），条目就把这些行为一并纳入定义。agent 若写出数学等价但边界行为不同的 kernel，会在正确性检查里被判失败。这是条目定义层面最容易被忽视的陷阱。

输入规格包含形状、dtype、布局与取值分布。形状决定 tile 划分与 occupancy 上限，dtype 决定是否能用 tensor core 或需要 fp32 累加，布局（contiguous / strided / channels-last）决定访存合并模式，取值分布决定是否需要处理极值、denormal 与溢出。评分脚本入口则是条目与评测框架的契约：它声明用哪些形状做正确性比对、用哪些形状做性能计时、计时采用什么同步方式与重复次数、是否剔除首次调用的编译/加载开销。同一个算子在不同评分脚本下会得到不同的“最优”实现，因此条目必须把评分脚本视为定义的一部分，而不是外挂的度量。

约束声明是条目定义中最具基准特色的一项。它明确写出：允许调用哪些库（如是否允许 cuBLAS/cuDNN/Triton 内建）、是否允许在 kernel 内做近似、是否允许改变输出 dtype、是否允许跨调用缓存。KernelBench L1/L2/L3 的分层本身就编码了一部分约束强度：层级越高，算子组合越复杂，对“自己写 kernel”的要求越强，对直接调库的容忍度越低。约束声明不是文档装饰，它被评分脚本以静态检查或运行时拦截的方式执行。

$$\text{entry} = \langle \mathcal{S},\ \mathcal{I},\ \mathcal{R},\ \mathcal{E},\ \mathcal{C} \rangle$$

其中 𝒮 为语义（参考实现）、ℐ 为输入规格集合、ℛ 为参考输出 oracle、ℰ 为评分脚本、𝒞 为约束集合。判定一个提交是否合格，等价于判定它是否同时满足 ℛ 的数值容差与 𝒞 的约束，并在 ℰ 下产生可比的时延。这个五元组视图的直接工程代价是：条目作者必须为每个算子维护一份参考实现与一份评分脚本，二者任一变更都会使历史分数不可比；因此基准版本必须与条目集合绑定发布，跨版本比较分数是无效操作。

二 · 分类维度之一：按算子结构与组合深度分层

KernelBench 的 L1/L2/L3 分层是组合深度维度，而不是难度维度的同义词。L1 是单算子条目：一个数学操作对应一个 kernel，例如逐元素激活、归约、矩阵乘、卷积、归一化。L2 是融合条目：两到数个算子被要求在同一个 kernel 或同一组 kernel 内完成，典型如 matmul + bias + 激活、layernorm + 残差、softmax 前后处理。L3 是架构级条目：完整的前向块，例如一个 transformer block 的注意力加 FFN 组合，条目要求端到端可运行且数值对齐。

分层带来的机制差异在于中间张量的归属。L1 条目中，输入输出由评分脚本分配，中间量几乎不存在；L2 条目中，融合是否成立取决于中间量能否留在寄存器或共享内存里而不落回 global memory；L3 条目中，中间量的生命周期跨越多个子计算，agent 必须决定哪些中间量物化、哪些重算。这直接决定了优化空间的上界：L1 的瓶颈通常是单 kernel 的访存或计算密度，L2 的瓶颈是融合边界的带宽节省，L3 的瓶颈是调度与并行分解。

组合深度还决定了正确性检查的复杂度。L1 的 oracle 是单次调用比对；L2 需要比对融合后输出与逐算子串联输出，且要处理融合引入的数值顺序差异（例如归约顺序改变导致的 fp32 舍入差异）；L3 需要比对整块输出，容差通常更宽，但失败定位更难——一个数值偏差可能来自注意力 softmax 的缩放、FFN 的激活近似或残差累加顺序。工程上，L3 条目的调试成本显著高于 L1，因为错误信号被多层复合放大或掩盖。

层级条目形态中间量归属主要优化杠杆正确性代价
L1单算子基本不存在访存合并、tile 尺寸、向量化单次比对，容差紧
L2算子融合寄存器/共享内存内消化融合边界、消除中间写回归约顺序差异，需放宽容差
L3架构块跨子计算生命周期并行分解、流水、重算 vs 物化误差复合，失败定位困难

一个具体例子：L1 的逐元素 ReLU 条目，评分脚本给出固定形状的输入，agent 只需保证每个元素独立计算正确并做到访存合并；而 L2 的 “matmul + bias + GELU” 条目，若 agent 把 GELU 放在第二个 kernel 里，虽然数值正确，但中间 matmul 结果要写回 global memory 再读回，带宽代价直接体现在时延上，评分脚本不会因“数值对”而给高分。这就是分层维度把“融合”变成可度量项的方式。

三 · 分类维度之二：按规模档位与形状族划分

同一算子在不同规模下是不同的优化问题。条目必须声明规模档位（size tier），否则分数不可比。规模档位通常按问题维度划分：小规模（单 block 可覆盖、受启动开销支配）、中规模（多 block、occupancy 与 tile 效率主导）、大规模（受显存带宽或 HBM 容量支配、可能需要分块或流式处理）。KernelBench 条目在评分脚本里为每个算子指定一组形状，正确性用一组、性能用另一组，二者可以不同——正确性形状偏向覆盖边界，性能形状偏向代表真实负载。

形状族的划分比单一形状更重要。矩阵乘类条目会区分方阵、瘦长矩阵（大 M 小 N）、批处理（batched）、转置布局；卷积类条目会区分小卷积核大通道、大卷积核小通道、depthwise、分组卷积。这些形状族在硬件上的 roofline 位置不同：方阵 matmul 偏计算密集，瘦长 matmul 偏访存密集，depthwise 卷积的算术强度极低。agent 若只针对一个形状调 tile，换到同条目的另一形状就可能退化。因此条目定义里必须写明“性能分数取形状族上的何种聚合”（例如取几何平均或取最差形状），这个聚合口径属于评分脚本，也属于条目定义。

$$\text{score} = \operatorname{agg}_{s \in \mathcal{T}} \frac{t_{\text{ref}}(s)}{t_{\text{sub}}(s)}$$

其中 𝒯 为性能形状集合，t_ref 为参考实现（通常是 PyTorch 或库调用）在相同形状与相同计时口径下的时延，t_sub 为提交实现时延。聚合函数的选择直接改变优化目标：取算术平均会奖励在多数形状上均衡的实现，取最小值会奖励单点极致优化而容忍其他形状退化。条目若不声明聚合口径，agent 就无法判断该追求均衡还是追求峰值，评测结果也无法复现。

规模档位的工程代价体现在编译与启动开销上。小规模条目里，kernel 启动延迟与模块加载时间可能占据时延的主要部分，此时“减少一个 kernel”比“提高计算效率”更有效；大规模条目里，寄存器压力与共享内存容量成为硬约束，tile 过大会导致 occupancy 下降甚至编译失败。一个具体例子：归约类条目在小规模下用单 block 完成即可，跨 block 同步的代价反而更高；在大规模下必须做多级归约，中间结果的显存往返成为主要带宽开销。条目把这两种规模放进同一算子集合，就是在测试 agent 是否能识别规模拐点并切换策略。

四 · 分类维度之三：按参考实现来源与评分口径划分

参考实现的来源决定了条目的“基线”含义。KernelBench 系条目的参考实现主要有三类来源：PyTorch 原生算子组合（eager 模式）、PyTorch 编译路径（如 torch.compile 产物）、以及厂商库调用（cuBLAS/cuDNN）。三者作为分母得到的加速比含义完全不同：对 eager 的加速比包含大量框架开销与未融合的中间写回，容易显得很高；对库调用的加速比则是在已经高度优化的基线上争夺剩余空间，难度大得多。条目必须标注参考实现来源，否则“3 倍加速”这类表述没有意义。

评分口径还包括计时方式与容差设定。计时是否包含 host-device 同步、是否使用 CUDA event、是否做 warmup、是否剔除首次编译，都会改变分母与分子。正确性容差则决定 agent 能否使用低精度近似：容差紧的条目禁止用 tf32 或 fp16 累加替代 fp32，容差宽的条目则允许一定程度的近似以换取吞吐。TritonBench 一类条目在参考实现上偏向以 Triton 写成的基线，其评分口径与 KernelBench 的 PyTorch 基线不可直接比较；CUDA-L1 一类条目则以 CUDA C++ 参考实现为基线，强调手写 kernel 与库的对照。跨基准比较分数是无效的，因为分母不同。

参考来源分母含义加速比易得程度典型约束
PyTorch eager含框架开销与中间写回较易，融合即得分禁止直接调库替代
torch.compile 产物已融合的编译基线中等，需超过编译器禁止复用编译缓存
厂商库调用高度优化基线难，剩余空间小禁止包装库调用冒充自写

一个具体例子：同一个 layernorm 条目，若分母是 eager 实现（多次 kernel 启动加中间写回），一个正确融合的单 kernel 就能取得明显加速；若分母是 cuDNN 或高度优化的库实现，融合带来的收益已被基线吃掉，agent 只能在访存向量化与 occupancy 上调优，加速比会小一个量级。条目若不写明分母来源，两次评测的分数差异会被误读为 agent 能力差异。

五 · 与相邻概念的区别：基准条目不是算子库条目、不是模型、不是性能测试

首先区分“基准条目”与“算子库条目”。算子库（如 PyTorch ATen、cuDNN、Triton 标准库）的条目以接口契约为核心：给定 dtype、布局、广播规则，返回语义正确的张量，性能是次要属性。基准条目则以可判定性为核心：它必须能在无人干预下判定正确与否、给出可比时延、并执行约束检查。算子库条目允许实现自由选择算法与精度策略，基准条目则用容差与约束把这种自由裁剪到可比较的范围内。把基准条目当成“再写一个算子库函数”来理解，会低估约束声明的作用。

其次区分“基准条目”与“模型”。模型条目（如端到端推理负载）的评分是任务级指标（吞吐、延迟分位数、精度），其内部由大量算子组成，单个算子的优劣被上层调度稀释。KernelBench 的 L3 条目虽然形态接近模型块，但它仍然是算子级条目：评分脚本直接调用该块的 forward，不经过完整模型的调度、批处理与内存管理。因此 L3 的分数不能直接换算为端到端收益；端到端收益需要另行测量，且受框架开销、kernel 启动次数、显存分配策略影响。把 L3 分数当作产品收益的代理，是常见的口径错误。

第三区分“基准条目”与“性能测试（benchmark harness）”。性能测试是一套测量方法：warmup、重复、同步、统计量选择。基准条目是被测量的对象。同一个条目可以被不同的 harness 测量，得到不同的数值；harness 的变更不影响条目语义，但影响可比性。条目定义里绑定评分脚本，正是为了把 harness 固定下来。这也解释了为什么防作弊检查必须与条目绑定：约束声明是条目的一部分，脱离条目的通用检查清单只能覆盖共性作弊，覆盖不了条目特有的约束（例如某条目禁止使用特定指令或特定库函数）。

第四区分“基准条目”与“正确性 oracle”。oracle 是判定正确性的参照物，条目是包含 oracle 的完整任务描述。一个条目可以有多个 oracle（例如同时比对参考实现输出与高精度计算结果），但 oracle 本身不构成条目。形式验证类工作会把 oracle 从“数值比对”升级为“性质证明”，此时条目定义需要额外声明被验证的性质集合；这类条目与纯数值比对条目在评分口径上不可混用。

一个具体例子：某条目要求实现一个带掩码的注意力打分。若把它理解为算子库条目，实现者会关注接口是否支持任意掩码形状；若把它理解为基准条目，实现者必须关注评分脚本用哪些掩码形状做正确性检查、容差是否允许在 softmax 里用近似指数、约束是否禁止调用库的 attention 实现。两者的优化方向与失败模式完全不同。

六 · 条目集合的饱和项与防作弊约束如何进入定义

条目集合不是越大越好。已知饱和项（saturated entries）指的是那些已经被现有实现逼近理论上界、继续投入优化收益极小的条目。饱和项留在集合里会稀释分数：agent 在这些条目上无论怎么努力都只能得到接近 1 的加速比，拉低聚合均值，却不能区分能力差异。因此条目说明必须标注哪些条目已饱和，评分时可以选择剔除或降权。饱和判定依据是 roofline 位置：当提交实现的时延已经贴近该形状下的带宽或算力上界，剩余空间不足以支撑有意义的比较。

防作弊约束进入条目定义的方式有两种：静态检查与运行时拦截。静态检查扫描提交代码的调用图，禁止出现被禁库函数或预编译产物；运行时拦截在评分脚本里替换或钩住特定 API，检测是否发生了被禁调用、是否跨调用缓存了结果、是否读取了评分脚本的输入文件。约束的强度与条目的开放度成反比：L1 条目通常禁止直接调库，L3 条目可能允许调用部分基础算子但禁止整体复用现成实现。约束越强，条目越能测出“自己写 kernel”的能力，但也越容易因误判而拒绝合法优化。

$$\text{valid}(s) = \text{correct}(s) \wedge \text{constraint}(s) \wedge \text{fresh}(s)$$

其中 fresh 表示每次评测使用新进程与新输入，禁止跨调用缓存。这个合取式的工程代价是：约束检查本身消耗评测时间，且静态检查可能产生假阳性（例如合法的内联汇编被误判为库调用），需要人工复核通道。另一个代价是条目作者必须为每个条目维护约束规则，规则与算子语义耦合，算子变更时规则也要同步更新。

一个具体例子：某逐元素条目禁止调用任何库的激活函数。agent 若用 Triton 写一个融合了激活与量化的 kernel，静态检查通过；若它用 PyTorch 的 `torch.nn.functional.gelu` 包一层再返回，静态检查会命中禁用符号而拒绝。反过来，若条目允许调用库但禁止缓存，agent 若在模块加载时预计算并缓存输出，运行时拦截会发现输入指纹不匹配而判失败。这两类约束都不是通用检查清单能覆盖的，它们必须写进条目定义，与评分脚本一起版本化。

饱和项与约束共同决定了条目集合的“有效分辨率”：一个条目若既饱和又约束宽松，它对区分 agent 能力几乎没有贡献；一个条目若约束过严导致合法实现频繁被拒，它引入的是噪声而非信号。条目维护者的实际工作因此不是不断增加条目，而是定期重测饱和项、校准约束规则的假阳性率、并在评分脚本变更时重新基线化历史分数。这套维护动作本身就是基准可信度的一部分，也是把“条目定义”从一次性文档变成持续工程对象的原因。
