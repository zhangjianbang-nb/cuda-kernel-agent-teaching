一 · 阈值的来源：从 roofline 反推，而不是拍脑袋

门禁清单上的每个数字都必须能回答“它从哪来”。工程上唯一站得住的来源是 roofline 反推：先确定该 kernel 在目标硬件上的理论上界，再把门禁阈值表达为该上界的百分比，而不是一个孤立的毫秒数或 GB/s 数。这样阈值随硬件代际、随 shape 变化自动平移，不会出现“上一代卡上定死的 0.8 ms 到了新卡上变成送分题”的情况。

$$T_{\text{gate}} = \alpha \cdot \max\left(\frac{F}{P_{\text{peak}}},\ \frac{B}{BW_{\text{peak}}}\right) + T_{\text{launch}}$$

其中 F 是实际浮点运算量，B 是实际搬运字节数，α 是放行系数，T_launch 是固定开销项。α 的取值本身就是一条工程判断：对纯访存型 kernel（elementwise、layernorm、reduce），α 通常要求更紧，因为这类 kernel 没有算法优化空间，达不到带宽上界的高比例就说明访存模式有问题（未合并、stride 访问、bank conflict）；对计算密集型（GEMM、attention），α 可以放宽，因为 tiling、split-K、epilogue 融合的收益空间大，且实测峰值本身受 occupancy 与寄存器压力限制。

代价在这里体现得很直接：α 定得过紧，门禁会把大量“其实已经可用”的 kernel 判为不合格，agent 的多轮迭代被无效地消耗在追逐不可达的上界上，token 预算与编译时间被浪费；α 定得过松，放行的 kernel 在生产流量下暴露为瓶颈，回滚成本远高于门禁成本。一个具体例子：对带宽受限的 copy-scale kernel，若实测只到峰值的 40%，几乎必然指向向量化宽度不足或未用 128-bit 访问，此时应把门禁卡在“达到峰值带宽的某个高比例”并要求 NCU 的 sectors/request 指标佐证，而不是接受一个“比 baseline 快”的模糊结论。

测量方法上，roofline 的上界不能靠厂商 spec 直接代入：实际可持续带宽要用一次大 size 的纯 copy 或 triad 微基准在同一张卡、同一时钟状态下测出来，作为分母。这一步的测量成本很低（秒级），但决定了后面所有阈值是否可信。

二 · 正确性门禁的阈值：容差、覆盖与随机种子

正确性门禁不是“全绿”两个字，而是一组可复现的参数：参考实现的选取、比较的范数口径、容差量级、输入分布与种子集合、以及边界 shape 的覆盖清单。阈值设计上，浮点比较应区分绝对与相对误差，常用组合是逐元素检查 |a−b| ≤ atol + rtol·|b|，并对 reduce 类 kernel 额外看整体范数误差，因为逐元素容差会掩盖累积误差在长归约上的放大。

  • 参考实现必须是高精度路径（fp64 或经确认的库实现），不能拿另一个低精度 kernel 当 oracle，否则两个实现共享同一类舍入偏差，门禁形同虚设。
  • 种子集合要固定并留存，随机输入必须覆盖极端幅值（接近零、接近溢出边界），否则 NaN/Inf 传播路径测不出来。
  • shape 覆盖要包含非对齐尺寸、质数长度、单元素、空张量语义，这些是 tiling 与边界分支最容易出错的地方。

代价：容差放宽会直接放过数值不稳定实现，尤其在 fp16/bf16 累加场景下，误差随归约长度增长，短序列测过关、长序列在生产上漂移；容差收紧则会让合法的低精度快速路径被误杀，agent 被迫回退到慢实现，性能门禁与正确性门禁互相拉扯。工程判断是把容差与数据类型、归约长度绑定成一张表，而不是全局一个常数。

测量方法：正确性门禁的通过证据应包含失败用例的最小复现输入（shape、seed、dtype、误差值），而不只是布尔结果。没有最小复现，后续 agent 的修复轮次只能靠猜，token 消耗成倍上升。

三 · 性能门禁的测量协议：预热、同步与计时口径

性能数字的可信度几乎完全由测量协议决定。门禁必须规定：预热迭代次数（触发时钟爬升、JIT 缓存命中、内存池预热）、计时是否包含 host-device 同步、是否使用 CUDA event 而非 wall clock、是否剔除首次调用的模块加载与 kernel 编译时间、以及重复测量的统计口径（取中位数还是最小值，方差超过多少判为不稳定）。

$$t_{\text{kernel}} = \frac{1}{N}\sum_{i=1}^{N}\big(t^{\text{end}}_i - t^{\text{start}}_i\big),\quad \text{reject if } \frac{\sigma}{\mu} > \beta$$

把 event 包在单次 launch 两侧，能把 launch 开销与 kernel 执行时间分开；若门禁关心端到端收益，则要另设一个包含 Python 侧调度、内存分配、同步的端到端计时项，两者不可混用。一个具体例子：某 agent 提交的 kernel 单次 event 计时优于 baseline，但端到端反而更慢，原因是它在每次调用里做了一次隐式的 device 侧分配与 host 同步；若门禁只测 kernel 时间，这个退化会被完全掩盖。

代价：预热不足会让首批测量被时钟与缓存效应污染，产生虚假的“快”；过度预热则拉长每次门禁的时延，在 agent 高频迭代场景下累积成可观的墙钟成本。同步点插入过多同样会破坏流水，使测量值偏离真实吞吐。工程上通常把预热次数与测量次数写成门禁配置的一部分并留存，使不同轮次、不同 agent 提交之间的数字可比。

测量方法：对不稳定结果（方差超阈值）应判为“测量无效”而非“性能不达标”，两者的处置路径不同——前者重测，后者回炉优化。这条区分能显著减少 agent 在噪声上浪费的迭代。

四 · 显存与占用率门禁：峰值、碎片与余量

显存门禁不能只看“能跑起来”，要规定峰值显存相对可用显存的余量比例，并把余量的用途写清：为同卡上并发的其他任务、为框架的缓存池、为后续算子留出空间。峰值测量应在最坏 shape 下进行，且要区分框架分配器的保留量与真实驻留量，否则会出现“账面上还有空间、实际分配失败”的情况。

  • 临时缓冲区（workspace）必须计入峰值，split-K、reduce 中间结果、attention 的 softmax 统计量都是常见来源。
  • 碎片化风险高的实现（反复申请释放不同尺寸块）要额外做长跑循环测试，观察保留量是否单调上升。
  • 占用率门禁应与寄存器用量、共享内存用量绑定检查，因为高占用率若以溢出到本地内存为代价，性能反而下降。

代价：余量定得大，等于人为压低可用并发度，端到端吞吐受损；余量定得小，生产上遇到更大 batch 或更长序列时直接 OOM，回滚预案被触发。一个具体例子：某 fused kernel 在小 shape 下显存余量充足，但 workspace 随序列长度线性增长，门禁若只测固定 shape，就会在长序列流量下失效。因此显存门禁必须声明其测试 shape 集合，并把 shape 与余量的关系作为证据留存。

测量方法：峰值显存应通过框架的统计接口或 device 侧查询在 kernel 执行前后取样，并在多次迭代中取最大值；仅看单次调用的瞬时值会低估峰值。

五 · 没有数字时怎么测：把门禁写成可执行的测量规程

当某个维度缺乏公认阈值时，门禁条目不应写成“性能良好”这类无法证伪的表述，而应写成一条测量规程：测什么、怎么测、记录什么、由谁判定。可执行的写法是把阈值替换为“相对基线”的比较规则，例如要求候选实现在同一测量协议下不劣于基线，且劣化幅度在预先声明的容差内；或者要求给出 roofline 百分比并附 NCU 佐证指标，由责任人按证据判定。

$$\text{pass} \iff \big(\text{correctness}=\text{true}\big)\ \wedge\ \big(\text{perf}_{\text{cand}} \le \text{perf}_{\text{base}}\cdot(1+\delta)\big)\ \wedge\ \big(\text{evidence}\ \text{complete}\big)$$

这条合取式的第三项常被忽略：证据完整性本身就是门禁的一部分。缺 NCU 报告、缺最小复现、缺测量配置的记录，即使前两项通过也不应放行，因为无法在回归时复现判定。责任人字段要落到具体角色而非“团队”，证据留存要规定存放位置与保留期限，使回滚时能追溯到当时的判定依据。

代价：把门禁写成规程会增加每次提交的固定开销——多一次 profile 采集、多一份记录，单轮时延上升；但相比放行后在线上定位一个数值漂移或性能退化，这个成本低一个量级。一个具体例子：对数值稳定性缺乏硬阈值时，规程可要求“在声明的最长归约长度与最宽动态范围输入下，误差不超过参考实现与候选实现之间的声明容差，并附失败样例”，把模糊判断转成可复核的证据链。

工程判断落在最后一步：门禁清单的每一条都应能被一个脚本自动判定，凡是需要人主观裁量的条目，要么改写成可测量的比较规则，要么明确标注为人工复核项并指定复核人。自动判定项与人工项的比例，本身就是这套门禁成熟度的直接读数。

阈值不是拍脑袋：从测量口径到失效边界的工程化落地

门禁阈值的第一条纪律是“口径先于数字”：同一个 kernel 在冷启动、热缓存、不同 shape 分布下测出的时延可以差出量级，若门禁不锁定测量口径，阈值本身就没有意义。工程上把口径拆成三件事：计时方式（CUDA event 环绕 vs. 主机侧 wall clock）、预热与重复次数（是否丢弃首轮 JIT/autotune 开销）、输入分布（固定 shape 还是按线上流量采样）。对 Triton 尤其要区分首次编译与后续命中缓存的执行，否则编译时间会被误记进 kernel 时延，导致门禁对“编译期成本”完全失明。正确性 oracle 的阈值同样需要口径：浮点比对必须声明容差基准（atol/rtol 与参考实现的精度路径），否则“全绿”只是比对脚本的产物。责任人应把口径写进证据留存物——一份可复跑的测量脚本加一份原始输出，而不是一句“已达标”。

经验数字的用法是“分档而非单点”。以 roofline 为锚，把 kernel 归入访存受限或计算受限两档，再分别设阈值：访存受限看有效带宽占 SOL 的比例，计算受限看有效 FLOPs 占 SOL 的比例，二者都用 achieved / SOL 归一化，避免被绝对时延掩盖。一个可操作的判据是：当实测达到 SOL 的比例低于该档位的经验下限时，先怀疑测量口径（L2 残留、时钟未锁频）而非直接判负；高于上限时则要反向核查是否发生了缓存作弊或输入退化。显存门禁不能只看峰值 allocated，还要看 reserved 与碎片化余量，因为 autotune 的候选配置会在搜索期短暂抬高峰值，若阈值卡在稳态峰值上，autotune 一开就会误报。数值稳定性阈值应绑定具体算子语义：归约类看相对误差随规模的增长斜率，而非单点误差。

$$\text{gate} = \big[\text{correctness all-pass}\big] \wedge \big[\text{perf} \ge \tau_{\text{tier}}\big] \wedge \big[\text{peakMem} \le M_{\text{budget}} - M_{\text{autotune}}\big] \wedge \big[\text{no cheat signal}\big]$$

失效条件必须写进门禁而不是留给评审口头判断。典型三类：其一，shape 越界——阈值只在被采样的 shape 集合上成立，线上出现更长序列或更大 batch 时，分块策略与占用率同时劣化，此时门禁应要求“外推区间”的抽样证据，而非默认线性外推；其二，并发污染——单流测量达标不代表多流并发下仍达标，带宽争用会让访存受限 kernel 的有效带宽显著下滑，门禁需声明测量时的流数与是否独占设备；其三，编译时间预算——autotune 与 CuTe 模板实例化会把编译时间推高，若门禁只测稳态时延，上线后首次请求的尾时延会被漏掉。系统代价上，把门禁做严的代价是测量成本本身：多档 shape × 多流 × 多次重复的采样会让单次门禁耗时上升，责任人需在“证据充分性”与“流水线节拍”之间显式取舍，并把取舍写进证据留存要求，而不是让阈值随人漂移。

阈值不是常数：门禁数字的失效边界与测量代价

工程阈值必须绑定测量口径，否则同一个 kernel 在两种口径下会得到相反的放行结论。以性能门禁为例，若以相对加速比 $$S = T_{\text{ref}} / T_{\text{cand}}$$ 作为判据，则 $$T$$ 的取法（是否含首次启动的 JIT 编译、是否含 host 侧拷贝、是否取多次迭代的中位数还是最小值）会直接改变 $$S$$ 的分母与分子。门禁清单里写的“≥1.2×”若不注明“同进程、预热后、CUDA event 计时、取 50 次中位数、排除首次编译”，这条阈值在 CI 上就不可复现。失效条件是明确的：当候选 kernel 的绝对时延进入微秒量级，launch 开销与计时噪声占比上升，相对加速比的方差会吞掉阈值余量，此时应改用绝对时延上限或 SOL 利用率作为门禁量。

正确性门禁的容差同样是经验数字，其边界由数值稳定性决定。逐元素算子用 $$|a-b| \le \text{atol} + \text{rtol}\cdot|b|$$ 尚可，但归约类算子（softmax、layernorm、sum）的误差随归约长度增长，固定 atol 会在长序列上误报。可行做法是把容差写成与规模相关的形式，或对归约结果额外比对统计量（均值、方差、最大值位置）。代价是显存：保存参考输出与中间张量做逐元素比对，在 LLM 推理形状下往往需要与激活同量级的显存，若门禁跑在全尺寸输入上，这部分开销可能超过被测 kernel 本身。工程折中是分层测量：小形状做严格逐元素比对，全尺寸只做统计量与抽样比对。

测量方法本身要写进门禁证据，而不是只写结论。建议每个门禁项固定记录三元组（测量脚本版本、输入形状与 dtype、重复次数与聚合方式），并把原始计时序列与 NCU 采集的指标一并留存，使阈值可被复核而非仅被引用。下表给出三类门禁量的口径与主要代价：

最后一条边界是阈值的时间有效性：硬件、驱动、编译器和形状分布任一变化都会让经验数字漂移，因此门禁阈值应带版本标签并在环境升级时重测基线，而不是把数字当作跨环境常量继承。责任人要签的是“口径 + 数字 + 环境版本”这一整条证据链，缺任一项即视为未就绪。
