一 · 条目是什么：从“论文”到“可复现条目”的升格

《核心论文索引》里的“条目”不是文献条目，而是一个可被 agent 消费的最小可复现单元。一条条目由四段构成：标识段（论文/仓库的稳定定位符，如 arXiv ID 或 repo commit）、贡献段（该工作相对既有基线新增的机制，一句话可判定的差异）、证据段（支撑贡献的评测配置与产物：基准子集、正确性 oracle、profile 采集口径）、复现段（复现所需的最小环境与已知阻塞点）。四段缺一，条目就退化为“引用”，无法进入索引主表。这个定义直接决定了索引的用途：它不是给人读的综述目录，而是给检索与调度层用的结构化记录——agent 在选脚手架、选验证器、选 RL 奖励形态时，按字段过滤而不是按标题猜测。

把“论文”升格为“条目”的代价是可复现性标注的维护成本。一条条目若标注为“可复现”，意味着证据段中的基准子集、oracle 与 profile 口径三者齐备且版本锁定；标注为“部分可复现”则要求明确指出缺失的是哪一段。这里的工程判断是：宁可标“部分”，也不要靠推断补全。因为下游 agent 会拿这个标注做预算决策——把一条“部分可复现”的条目当作“可复现”去跑，浪费的是整轮 GPU 时延与 token，而不是一次检索。

$$\text{条目} = \langle \text{ID},\ \text{贡献差分},\ \text{证据三元组},\ \text{复现阻塞点}\rangle,\quad \text{证据三元组}=(\text{bench},\ \text{oracle},\ \text{profile})$$

具体例子：一条关于“profile 驱动自动调优”的条目，其贡献段必须写成“以 NCU 采集的 stall 归因为反馈信号，替代以端到端时延为奖励的搜索”，而不是“提出了一种调优方法”。前者可判定，后者不可判定；判定性决定了这条条目能否被 agent 用作负样本对照。

二 · 五条线：分类的第一维是“产出物形态”

索引按五条线分栏：基准、agent 脚手架、RL 训练、形式验证、profile 驱动优化。这条分类轴不是按学科，而是按条目产出物的形态——即该工作最终交付给流水线的是什么。基准线交付的是“任务与评分口径”；脚手架线交付的是“生成—执行—修复的控制流”；RL 训练线交付的是“策略更新所依赖的奖励与轨迹结构”；形式验证线交付的是“正确性判定的更强 oracle”；profile 驱动优化线交付的是“以硬件计数器为信号的搜索策略”。形态决定了条目在流水线中的插入位置，也决定了它的失败模式归属。

线产出物形态接入点主要代价维度
基准任务集 + 评分口径评测层评测时延、口径漂移
脚手架控制流与工具契约生成层token 消耗、轮次上限
RL 训练奖励函数与轨迹结构训练层采样吞吐、显存驻留
形式验证更强正确性 oracle验证层验证时延、可判定子集覆盖率

用形态而非主题分类，好处是同一篇论文可以被拆进多条线而不重复：一篇既提基准又提 RL 奖励的工作，在基准线记其评分口径，在 RL 线记其奖励形态，两条条目共享同一 ID 但证据段不同。代价是索引的维护者必须做拆分判断，拆分粒度过细会让条目数膨胀、检索命中率下降；过粗则丢失接入点信息。工程上的折中是：一条条目只记一个接入点，跨线的部分用 ID 交叉引用，不在条目内复述。

三 · 第二维：可复现性状态的分级与判定

可复现性状态不是二值，索引采用三级：锁定可复现（环境、基准子集、oracle、profile 口径四者版本齐备，且有独立复跑记录）、条件可复现（缺一项但缺失项有明确替代路径，例如 oracle 可用等价判定替代）、不可复现（关键产物未公开或依赖闭源服务）。分级判定必须落到字段上，不允许用“作者声称”作为依据。判定伪代码的思路是逐项比对而非整体印象：

$$\text{state}=\begin{cases}\text{locked} & \forall f\in\{\text{env},\text{bench},\text{oracle},\text{profile}\}:\ \text{pinned}(f)\\\text{conditional} & \exists f:\ \neg\text{pinned}(f)\ \land\ \text{hasAlt}(f)\\\text{unrepro} & \exists f:\ \neg\text{pinned}(f)\ \land\ \neg\text{hasAlt}(f)\end{cases}$$

这里的关键机制是 hasAlt 的判定：替代路径必须本身是索引内的另一条条目，否则“有替代”就是空话。例如某条目的正确性 oracle 依赖一个未公开的参考实现，若索引中存在一条形式验证条目能对该 kernel 子集给出等价判定，则 hasAlt 成立，状态降为条件可复现；若不存在，则为不可复现。这条规则把可复现性从单条目属性变成了索引内的图属性，代价是每次新增条目都可能改变既有条目的状态，需要增量重算，而不是一次性标注。

性能代价体现在检索侧：条件可复现条目在被 agent 选中后，需要额外一轮“替代路径确认”，这一轮消耗的是检索 token 与时延；若索引不标注分级，这一轮会被隐式地并入执行阶段，表现为莫名其妙的失败重试。具体例子：一条 RL 训练条目若其奖励函数依赖未公开的评分脚本，标注为不可复现后，agent 会直接跳过它去选同线的条件可复现条目，省下的是整条轨迹的采样开销，而不是一次查询。

四 · 与相邻概念的区别：条目、术语、速查表、失败库

索引条目最容易与四类相邻产物混淆，区别在于回答的问题不同。术语表回答“这个词指什么”，是定义层；速查表回答“这个指标的正常范围与采集口径”，是度量层；失败模式库回答“这种症状对应哪些成因”，是诊断层；索引条目回答“这项工作交付了什么、能否复现、接入流水线哪一层”，是来源层。四者可以互相引用，但不能互相替代：把索引条目写成术语解释，会让检索层失去接入点信息；把失败模式塞进条目，会让条目变成诊断手册的副本。

  • 与术语表的边界：条目中出现的新概念，只在贡献段用一句话点明其差分，定义本身指向术语表，不在条目内展开。
  • 与速查表的边界：条目证据段只记“采集了哪些计数器、口径是什么”，具体阈值与解读指向 NCU 关键指标速查。
  • 与失败库的边界：条目复现段只记“已知阻塞点是什么”，该阻塞点在更大范围内的成因归类指向失败模式库。
  • 与基准速查的边界：基准线条目记“该工作对基准的改动与评分口径变更”，基准本身的构成指向 KernelBench 系基准速查。

这个边界的工程价值在于控制单条目的信息熵：一条条目若把定义、阈值、诊断全部内联，其长度会膨胀到无法被检索层有效截断，导致关键字段（ID、状态、接入点）被挤出上下文窗口。代价是读者需要在多个产物间跳转，收益是每条产物都能被独立版本化与独立更新——术语表更新不会污染索引条目的证据段。

五 · 分类维度之间的正交性与冲突处理

五条线（形态）与三级状态（可复现性）是正交的：任一形态都可以处于任一状态。但正交不等于无冲突。典型冲突是“形态归属争议”：一篇工作既交付了基准又交付了以该基准为奖励的 RL 配方，按“一条条目一个接入点”的规则应拆为两条，但两条共享同一证据段，若证据段中的基准子集后来被修订，两条条目需同步失效。索引的处理机制是证据段引用而非复制：证据段以引用形式指向一个独立的证据记录，条目只持有引用与状态判定结果；证据记录变更时，所有引用它的条目状态自动重算。这避免了复制带来的漂移，代价是索引需要维护一张证据记录表，检索时需要一次间接寻址。

$$\text{stale}(e)=\bigvee_{r\in\text{refs}(e)}\text{rev}(r)\neq\text{rev}_{\text{entry}}(r)$$

另一个冲突是“状态与形态的耦合误判”：形式验证线的条目常被误标为锁定可复现，理由是“验证器是开源的”；但形式验证条目的证据段包含“可判定子集覆盖率”，这个覆盖率本身依赖被验证 kernel 的形态，换一个 kernel 子集覆盖率就变，因此其状态应随子集标注为条件可复现。误判的代价是 agent 把形式验证当作万能 oracle 接入，结果在覆盖率之外的 kernel 上得到“验证通过”的空洞结论——这不是时延代价，而是正确性代价，且是静默的。

具体例子：一条 profile 驱动优化条目，其证据段引用了一个 NCU 采集配置记录；当该记录的口径从“单次采集”改为“多次采集取中位”时，引用它的条目状态从锁定降为条件，因为复跑抖动不再被口径吸收。检索层据此把该条目从“可直接复用”移到“需确认”队列，避免 agent 在抖动未量化的情况下把 profile 信号当作稳定奖励。

六 · 条目的最小字段集与拒绝规则

索引对条目设最小字段集，缺字段即拒绝入库，而不是降级入库。最小集为：稳定 ID、形态归属（五选一）、接入点、贡献差分（可判定句式）、证据三元组引用、状态判定结果、复现阻塞点（允许为空但必须显式声明为空）。拒绝规则的作用是防止“看起来像条目”的伪条目稀释索引：一篇只有摘要级描述的论文，无法写出可判定的贡献差分，应被拒绝而非以“不可复现”状态入库——因为“不可复现”仍暗示存在可判定的贡献，而摘要级描述连贡献差分都无法判定。

拒绝规则的性能含义在检索侧：伪条目会以高相似度命中查询，挤占真正的可复现条目，导致 agent 在无效条目上消耗检索轮次与上下文预算。把拒绝前置到入库阶段，代价是入库时的人工或半自动判定成本，收益是检索侧的命中精度。工程判断是：入库严格、检索宽松——入库时宁缺毋滥，检索时允许跨线召回再由状态字段过滤。

最后一个机制性判断落在“贡献差分”的句式约束上：差分必须写成“以 X 替代 Y”或“在 Z 条件下新增 W”，因为这两种句式天然携带对照基线，可被自动解析为负样本对。写成“提出了……”的条目无法解析出对照，检索层无法用它构造 A/B 对照，只能作为孤立正样本，价值减半。这条约束不涉及任何实验数字，只涉及条目文本的可解析性，但它决定了索引能否被下游 RL 流水线直接消费为偏好对来源。

索引条目的边界：五条线不是并列抽屉，而是可判定的归属规则

把一篇论文或仓库挂到五条线中的某一条，判据不是它“讲了什么”，而是它把不可验证的哪一段变成了可验证的。基准线交付的是任务与 oracle 的绑定关系；脚手架线交付的是从任务到候选 kernel 的搜索与反馈回路；RL 训练线交付的是可批量采样的奖励信号及其方差控制；形式验证线交付的是对正确性命题的机器可检证明或反例；profile 驱动优化线交付的是从 NCU/SASS 观测到改写决策的映射。一条条目若同时触及两条线，按“它使哪一段首次可判定”归主类，其余记为交叉标记，而不是重复计数。这条规则直接决定索引的失效条件：当某条目的 oracle 只覆盖形状与 dtype 而放过数值容差，它作为基准条目是成立的，但一旦被当作正确性 oracle 复用，就在容差边界上失效——此时应降级为“基准·弱 oracle”并指向形式验证线的条目。

分类维度取三个正交轴：可复现性状态（代码与权重是否可获取、评测脚本是否固定）、反馈信号类型（编译通过/数值比对/性能计数/证明义务）、以及被优化的对象（kernel 本体、搜索策略、还是奖励模型）。三者组合出的条目空间远大于五条线，索引只收录每格中贡献点可被一句话判定的代表项。系统代价体现在索引维护上：一条目若其反馈信号依赖特定 GPU 架构的计数器，跨代复现即需重跑基线，单次全量校验的编译与 profile 开销按任务数线性增长，token 消耗主要花在把 NCU 报告转成可比较的标量上，而非生成 kernel 本身。

$$\text{归属}(e)=\arg\max_{l\in L}\ \mathbb{1}\big[\text{首次可判定段}(e)=l\big],\quad \text{交叉}(e)=\{l:\text{触及}(e,l)\}\setminus\{\text{归属}(e)\}$$

与相邻概念的区别要落在可操作层面：基准条目区别于“数据集条目”，前者必须自带判定函数，后者只提供输入；RL 训练条目区别于“微调配方条目”，前者必须给出奖励的可验证构造，后者只给损失与数据配比；形式验证条目区别于“单元测试条目”，前者失败时产出反例路径而非仅布尔失败。具体例子：一个仓库若只发布 kernel 实现与自测脚本、不发布任务生成器与容差设定，它在索引中记为“脚手架·实现参考”，可复现性状态标为部分，且不得被引用为基准条目——因为它的判定函数不可迁移，复用者拿到的只是代码而非可判定的正确性边界。
