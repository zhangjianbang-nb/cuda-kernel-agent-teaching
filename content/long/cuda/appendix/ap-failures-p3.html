一 · 阈值的来源：从“症状”反推可测边界

工程阈值不是拍脑袋的常数，而是把失败模式翻译成可观测量之后，再反向标定出的判据。以寄存器溢出为例，症状是 kernel 编译通过、数值正确，但吞吐比预期低一截。根因是编译器把局部数组或大结构体放进 local memory，每次访问走 L1/L2 而非寄存器堆。可测的量是 ptxas 输出里的 registers、spill stores、spill loads 三个字段。判据不是“寄存器数超过 255 就溢出”——那是硬上限，不是工程阈值；真正的工程判据是 spill 字节数与 kernel 总访存字节数的比值。设单线程 spill 流量为 $$S_{spill}$$ 字节、线程数为 $$T$$、有效数据搬运量为 $$B_{eff}$$，则溢出开销占比

$$\rho_{spill} = \frac{S_{spill}\cdot T}{B_{eff}}$$

当 $$\rho_{spill}$$ 超过某个量级时，spill 流量已经能和真实数据流量竞争 L1 带宽，此时优化寄存器压力（改 tile 尺寸、拆循环、用 shared memory 暂存）的收益会盖过其他调参。这个量级必须在你自己的硬件上用微基准测出来：写一个只做 spill 的合成 kernel，逐步加大局部数组，记录 spill loads/stores 与实测带宽的对应关系，得到“每字节 spill 折算多少有效带宽损失”的换算系数。没有这个系数，任何“寄存器太多”的判断都是定性的。代价方面：spill 本身增加的是 L1 往返时延与指令数，编译期 ptxas 还会因寄存器分配搜索变慢，autotune 的候选空间被无效配置稀释。

具体例子：一个 reduction kernel 把每线程累加数组写成 float acc[32] 且下标由运行时变量决定，ptxas 必然将其放入 local memory。症状是 NCU 里 local memory 的 sectors 计数不为零、L1 命中率虚高（因为访问都落在 local 段）。定位手段是看 SASS 中是否出现 LDL/STL 指令；修复是把下标改为编译期可展开的常量或改用 warp shuffle。这里的工程判断是：只要 SASS 里出现 LDL/STL，就不必再讨论 occupancy，先解决溢出。

二 · 数值错误的阈值：容差、ULP 与“静默”的边界

静默数值错误最难设阈值，因为它不崩溃、不报错，只在特定输入分布下偏离参考值。工程上把判据分成三层：绝对容差、相对容差、ULP 距离。对 float32 的归约类算子，绝对容差要随累加长度缩放，因为浮点加法不满足结合律，误差随 $$\sqrt{n}$$ 或 $$n$$ 增长取决于求和策略。设参考实现用双精度、被测实现用单精度顺序累加，则最坏误差上界近似为

$$\epsilon_{abs} \approx n \cdot u \cdot \sum_i |x_i|,\quad u = 2^{-24}$$

其中 $$u$$ 是 float32 的单位舍入误差。这意味着你不能对所有归约用同一个固定容差：长度 1024 和长度 65536 的归约，允许的绝对误差差两个数量级。工程做法是按 $$n$$ 分档设容差，并把“参考实现”固定为双精度累加，避免参考本身带误差。代价是：容差放宽会漏掉真实的精度退化（例如把 __fmaf 误写成普通乘加导致精度下降），容差收紧会把合法的并行重排判为失败。测量方法是构造三类输入——全正数、正负交替、量级悬殊——分别看误差分布，因为量级悬殊输入会暴露“大数吃小数”的抵消问题。

具体例子：softmax 的 exp 在输入含大负数时下溢为 0，若参考实现先减最大值再 exp，被测实现忘了减最大值，则输出在数值上仍是合法概率分布但完全错误。这种错误用相对容差在输出层看不出来（输出都接近均匀），必须在中间张量上比对。工程判断：对含 exp/log 的算子，验证器必须比对减最大值之后的中间量，否则容差再严也抓不到。ULP 距离的用法是给每个元素算 |a-b| / ulp(b)，统计超过若干 ULP 的元素比例，比例阈值比单元素阈值稳健，因为它容忍个别边界元素的正常舍入。

三 · 并发与内存序：race 的可观测代理指标

race condition 的阈值不能靠“跑多少次不出错”来定，因为竞态窗口可能极窄。工程上改用可观测代理：一是用 compute-sanitizer --tool racecheck 做确定性检测，代价是运行时膨胀一到两个数量级、且只覆盖 shared memory 访问；二是构造“放大窗口”的输入，例如让所有线程在同一时刻写同一地址、或在写后立即读，把窗口从纳秒级拉到可观测级。判据是：在放大输入下重复运行 $$N$$ 次，若出现一次不一致即判定存在 race，不设“失败率低于多少算通过”的阈值——因为 race 的触发概率与调度、occupancy、时钟频率都相关，任何概率阈值都会被环境漂移击穿。

bank conflict 则是可量化的：shared memory 的 32 个 bank，若一个 warp 内多个线程访问同一 bank 的不同地址，则请求被串行化。设一个 warp 的访问被分成 $$k$$ 个冲突批次，则该次 shared 访问的代价是单批次的 $$k$$ 倍。工程判据不是“冲突数为零”，而是看 NCU 的 shared load/store wavefronts 与 ideal 的比值；比值接近 1 表示无冲突，明显大于 1 则需要改数据布局（padding、swizzle）。代价是 padding 会增加 shared memory 占用，可能把 occupancy 从一档压到下一档，所以 bank conflict 修复必须和 occupancy 一起评估，不能单独看冲突指标。测量方法是写一个只做 shared 读写、地址由 threadIdx 线性变换的微基准，扫描 stride 从 1 到 32，记录 wavefronts 曲线，得到该硬件的冲突代价表。

具体例子：一个 32×32 tile 的转置，若按行写入 shared、按列读出，读侧 stride 为 32，恰好所有线程落在同一 bank，冲突批次为 32。修复是加一列 padding 使 stride 变为 33。这里的工程判断是：padding 的收益要用 wavefronts 比值量化，而不是凭“应该会快”下结论；若 padding 导致 shared 占用跨过 occupancy 档位边界，净收益可能为负。

四 · occupancy 塌陷：不是越高越好，而是够用即可

occupancy 塌陷的症状是延迟隐藏不足：长延迟指令（global load、特殊函数）之后没有足够 warp 可切换。可测量的是 active warps per SM 与理论最大值的比值，以及 stall 原因分布中 “long scoreboard” 的占比。工程判据不是“occupancy 必须高于某百分比”，而是看 stall 是否集中在内存延迟上：若 long scoreboard 占比高且 occupancy 低，则提升 occupancy 有收益；若 stall 主要在 execution dependency 或 barrier，则提升 occupancy 无用。设每 SM 理论最大 warp 数为 $$W_{max}$$，实际驻留 $$W_{act}$$，则

$$O = \frac{W_{act}}{W_{max}}$$

但 $$O$$ 只是上限约束的结果，受寄存器、shared memory、block 数三者共同限制。测量方法是先用 cudaOccupancyMaxActiveBlocksPerMultiprocessor 算出理论值，再用 NCU 的 achieved occupancy 对比，差值大说明有运行时因素（如 tail effect、block 调度不均）。代价是：为了提 occupancy 而压低寄存器数，往往引入 spill，反而增加内存流量；为了提 occupancy 而减小 block 尺寸，会增加调度开销与同步次数。所以工程判断是“先看 stall 归因，再决定是否动 occupancy”，而不是把 occupancy 当独立目标优化。

具体例子：一个 GEMM kernel 用大 tile 导致每 block 寄存器需求高，occupancy 只有理论值的四分之一，但 NCU 显示 stall 主要在 “wait” 而非 long scoreboard，说明瓶颈是计算流水而非延迟隐藏，此时强行降 tile 提 occupancy 会减少数据复用、增加 global 流量，净效果为负。这个例子说明 occupancy 阈值必须和 roofline 位置联合判断。

五 · autotune 过拟合与评测漂移：阈值要带置信区间

autotune 过拟合的症状是：搜索阶段选出的最优配置，在换一批输入尺寸或换一台机器后不再是最好，甚至退化。根因是搜索时的测量噪声被当成真实差异。工程判据是“最优配置与次优配置的差距是否超过测量噪声”。设同一配置重复测量 $$m$$ 次的时延标准差为 $$\sigma$$，两个配置均值差为 $$\Delta$$，则只有当

$$\Delta > z\cdot\frac{\sigma}{\sqrt{m}}$$

时才能认为差异显著，$$z$$ 取对应置信水平的系数。工程做法是：对 top-k 候选各重复测量若干次，取中位数而非均值（抗离群），并用置信区间判断是否真的需要换配置。代价是搜索时间随 $$m$$ 线性增长，而 autotune 本身占用编译与运行预算；在 token 预算受限的 agent 场景里，重复测量会挤占探索其他配置的机会。测量方法是固定输入集、固定时钟（锁频）、固定后台负载，记录同一配置跨多次运行的时延分布，得到该环境的噪声底。

评测环境漂移的症状是同一 kernel 在不同时间跑出不同结论。根因包括 GPU 时钟降频、MIG 切分、其他进程占用、驱动版本差异。工程判据是：把“参考实现”和“被测实现”放在同一进程、同一时段交替测量，用比值而非绝对值做判据，因为比值能抵消共模漂移。代价是交替测量增加总时长，且比值仍受各自噪声影响，需要重复取中位数。具体例子：某次评测中被测 kernel 比参考快，但换时段复测发现两者都变慢且差距消失，说明原结论来自时钟状态差异而非 kernel 本身。工程判断：任何跨机器、跨时段的性能结论，必须报告测量条件与噪声底，否则不可复现。

六 · 没有数字时怎么测：微基准与归因表

当某个失败模式没有现成阈值时，标准动作是构造微基准，把该模式隔离成单一变量。步骤是：先写一个只包含该模式的最小 kernel（例如只做 shared 冲突访问、只做 spill、只做长依赖链），扫描关键参数（stride、数组大小、block 尺寸），记录一个可观测量（wavefronts、spill 字节、stall 占比、时延），画出曲线找到拐点。拐点就是该硬件的经验阈值。代价是微基准的结论不能直接外推到真实 kernel，因为真实 kernel 多个模式叠加；所以微基准只用于给出量级和方向，最终判据仍要在真实 kernel 上用 NCU 归因确认。

归因表的做法是：把 NCU 的 stall 原因、内存层级流量、指令 mix 三项并列，对每个候选失败模式标注“若为此模式，应观察到什么”。例如怀疑 bank conflict，则期望 shared wavefronts 偏高而 global 流量正常；怀疑 occupancy 塌陷，则期望 long scoreboard 高且 active warps 低；怀疑 spill，则期望 local 流量非零且 L1 命中结构异常。三者互斥性越强，归因越可信。工程判断是：先用归因表缩小范围，再用微基准标定阈值，最后回到真实 kernel 验证修复收益——这个顺序避免在错误的方向上做精细调参。

具体例子：一个 kernel 时延比预期高，归因表显示 global 流量与理论值一致、shared wavefronts 正常、local 流量为零，但 execution dependency stall 占比高，指向指令级依赖链过长而非内存问题。此时正确的动作是改算法减少串行依赖（如用树形归约替代线性累加），而不是调 tile 尺寸或加 occupancy。这个判断只能来自归因表，不能来自任何单一阈值。

阈值不是常数，是随形状与编译选项漂移的判据

失败模式库里最容易被误用的是把经验数字当成全局常数。以寄存器溢出为例，__launch_bounds__ 里写死的 maxThreadsPerBlock 与 minBlocksPerMultiprocessor 会直接改变 ptxas 的寄存器预算：同一个 kernel 在 minBlocks=1 时可能拿到 128 个寄存器而不 spill，改成 minBlocks=4 后预算被压到 64，编译器开始把活跃值搬进 local memory，症状是静默的性能塌陷而非编译报错。判断是否真的溢出，不能只看编译日志里有没有 “spill stores”，要看 ptxas -v 输出的 spill 字节数与实际 occupancy 的乘积：若 spill 字节数 × 每 SM 常驻 warp 数 超过了 L1 可承载的 local 流量，收益就被抵消。代价是可测量的——每次改 launch_bounds 都要重新跑一遍编译与 profile，编译时间从秒级升到十几秒量级，autotune 搜索空间随之膨胀。

occupancy 塌陷的阈值同样依赖测量方法。用 cudaOccupancyMaxActiveBlocksPerMultiprocessor 得到的是理论上限，而 NCU 的 sm__warps_active.avg.pct_of_peak_sustained_active 给出的是真实驻留比例，两者在存在动态 shared memory 或 __syncthreads 密集的 kernel 上会显著分叉。经验判据应写成比值而非绝对值：

$$\text{occupancy\_gap} = \frac{\text{theoretical\_warps} - \text{achieved\_warps}}{\text{theoretical\_warps}}$$

当 gap 超过某个由实测标定的比例时，优先怀疑 launch 配置与 shared memory carveout 设置不匹配，而不是盲目调大 block size。这个比值本身没有普适常数，必须针对每个 kernel 家族用一次 NCU 采样标定，标定成本是一次完整 profile 的时延（毫秒到秒级），换来的是后续 autotune 不必在错误维度上浪费 token 与编译预算。

症状优先测的量失效条件
静默数值错误与 fp64 参考的逐元素最大相对误差参考实现本身用了同一 fast-math 路径
bank conflictNCU 的 shared load/store wavefronts 比值访问模式随 tile 边界变化，单点采样不具代表性
autotune 过拟合跨形状的配置命中率评测形状集合与线上分布不一致

评测环境漂移的边界在于：同一份 kernel 在固定 clock 与放开 clock 下测得的时延差可以吞掉一个优化档位的收益，因此任何阈值比较都必须在同一 clock 策略、同一 MPS 配置下成对采样，否则测到的是环境噪声而不是 kernel 差异。race condition 没有可用的数值阈值，只能靠 compute-sanitizer 的 racecheck 做存在性判定，代价是运行时间放大一个数量级以上，因此它属于发布前的一次性门禁，而不是每轮 RL 反馈里的常规项。

阈值不是常数：从寄存器溢出到 occupancy 塌陷的判定链

寄存器溢出（spill）的判定不能只看编译器报出的 spill stores/loads 计数，因为局部数组被提升到 local memory 与真正的寄存器压力溢出在 SASS 上表现不同：前者是显式 LDL/STL，后者由 ptxas 在 -v 输出里给出 registers 与 spill 两栏。工程上可用的判定是“每线程寄存器数 × 线程数 ≤ 每 SM 寄存器文件容量”这条硬约束的余量，写成

$$R_{\text{avail}}=\left\lfloor \frac{65536}{B \cdot \lceil T/32 \rceil}\right\rfloor,\quad \text{spill risk}=R_{\text{used}}>R_{\text{avail}}$$
其中 $B$ 为每 block 线程数、$T$ 为每 SM 常驻线程数。一旦 $R_{\text{used}}$ 越过该线，ptxas 会强制降级，代价是 local memory 往返时延与 L1 带宽占用，在带宽受限 kernel 上直接体现为吞吐下降；而在计算受限 kernel 上，spill 的代价可能被指令级并行掩盖，因此“看到 spill 就判失败”是错的，必须结合 NCU 的 l1tex__t_sectors_pipe_lsu_mem_local_op_ld 与 smsp__inst_executed 比值判断。

occupancy 塌陷的阈值同样依赖架构而非固定百分比。以共享内存为例，每 SM 的可用容量与每 block 的静态+动态共享内存共同决定常驻 block 数

$$\text{blocks/SM}=\min\left(\left\lfloor\frac{S_{\text{smem}}}{S_{\text{blk}}}\right\rfloor,\left\lfloor\frac{R_{\text{sm}}}{R_{\text{blk}}}\right\rfloor,\left\lfloor\frac{W_{\text{max}}}{W_{\text{blk}}}\right\rfloor\right)$$
任一维度先饱和即成为瓶颈。典型失效条件是 autotune 在 tile 尺寸上过拟合：搜索把 BLOCK_M×BLOCK_N 推到共享内存刚好放下的边界，本地单卡测得最优，换到共享内存更小或 L2 更小的 SKU 上常驻 block 数从 2 掉到 1，occupancy 减半而 kernel 仍报告“编译成功”。定位手段是把 tile 尺寸、共享内存字节数、常驻 block 数三元组写进 autotune 的候选记录，并在评测环境漂移检测中对这三元组做快照比对，而不是只比对最终时延。

症状可测的量判定边界
寄存器溢出ptxas registers/spill、local ld/st 扇区数$R_{\text{used}}>R_{\text{avail}}$ 且 local 访存占比不可忽略
occupancy 塌陷常驻 block 数、smem 占用、achieved_occupancy任一资源维度先饱和，且 tile 参数处于容量边界

测量方法上，阈值必须由测量而非经验常数给出：先用 cudaOccupancyMaxActiveBlocksPerMultiprocessor 拿到理论常驻数，再用 NCU 的 launch__occupancy_limit_* 系列指标确认实际限制来源，两者不一致说明存在运行时动态共享内存或驱动侧限制未被建模。代价方面，每次 autotune 候选都需一次编译与一次 profiling，编译时间与 token 消耗随候选数线性增长，因此候选集应按“资源维度边界”剪枝而非盲目扩大网格；对无法测量的量（如跨 SKU 的 L2 行为），应在评测记录中显式标注为未测，而不是用默认阈值填充。
