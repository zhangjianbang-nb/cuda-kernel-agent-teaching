一 · 阈值的三种来源：规格、测量、回归

工程阈值不是拍脑袋的常数，它必须能回答“这个数字从哪来、失效时谁负责”。在 kernel agent 的语境里，阈值只有三种合法来源。第一种是规格给定：硬件规格书里的峰值带宽、SM 数量、寄存器文件大小、共享内存上限，这类数字由厂商定义，agent 只能引用不能发明，用错规格就是口径错误。第二种是测量得到：在目标卡上跑微基准（microbenchmark）测出的有效带宽、L2 命中率、启动开销，这类数字带测量条件，脱离条件即失效。第三种是回归拟合：从历史 kernel 的 profile 数据里拟合出的经验系数，例如某类算子在特定 tile 尺寸下的占用率拐点，这类数字最脆弱，必须绑定数据集版本与采集脚本。

三者的工程差别体现在失效模式上。规格阈值失效是“换卡即错”，测量阈值失效是“换负载即错”，回归阈值失效是“换数据分布即错”。因此术语表里每个阈值条目都应携带三个字段：来源类别、绑定条件、复核周期。缺少任一字段的阈值，在评审时按未定义处理，不允许进入 agent 的奖励函数或门禁判断。

$$\text{threshold} = \langle \text{source},\ \text{condition},\ \text{recheck}\rangle,\quad \text{valid} \iff \text{condition holds}$$

代价在这里是维护成本而非运行时开销：每增加一个回归阈值，就多一条需要随驱动、编译器、硬件版本复核的条目。一个中等规模的 kernel agent 评测集若把阈值条目控制在数十条量级，复核工作量尚可人力承担；一旦膨胀到数百条，就必须脚本化重测，否则阈值会静默腐化。具体例子：某团队把“共享内存占用不超过 48KB”写成硬阈值，换到共享内存更大的架构后该阈值不再约束性能，却仍在门禁里拦截合法 kernel，这就是规格阈值未绑定条件的典型代价。

二 · 没有数字时怎么写：可复现的测量协议

术语表最容易被诟病的地方是“写不出数字就写‘视情况而定’”。正确做法是把“视情况”拆成一份可执行的测量协议，让读者自己产出数字。协议至少包含四要素：被测对象、测量工具、采样口径、判据。被测对象要精确到 kernel 变体与输入形状；测量工具要指明是墙钟计时、CUDA event、还是 NCU 的硬件计数器；采样口径要说明预热次数、重复次数、取中位数还是最小值；判据要说明阈值是绝对量还是相对基线的比值。

一个可用的伪代码骨架如下，重点在于把“测什么”与“怎么判”分离：

  • 预热 N 次丢弃，消除首次启动的上下文建立开销；
  • 重复 M 次取中位数，同时记录最小值用于识别抖动；
  • 用 CUDA event 包裹 kernel 本体，排除 host 端同步与内存分配；
  • 同一输入形状下与参考实现对比，得到相对比值而非绝对时延；
  • 把采集脚本、驱动版本、编译器版本写入结果元数据。

这套协议的代价是测量时延与 token 预算：每次完整测量要跑预热加重复，单点耗时远高于一次推理调用；若 agent 在多轮优化中每轮都触发完整测量，token 与算力开销会线性叠加。工程折中是分层测量：粗筛用单次 event 计时，精筛才跑完整协议。具体例子：判断一个归约 kernel 是否达到带宽上限，粗筛只看 event 计时是否接近理论下界，精筛才用 NCU 读 DRAM 吞吐计数器，两者结论不一致时以精筛为准并回写粗筛的校准系数。

三 · 正确性 oracle 的阈值：容差不是越小越好

正确性验证的阈值是术语表里歧义最重的一类。浮点比较的容差（tolerance）必须区分绝对容差与相对容差，且要与累加顺序、数据类型绑定。对 fp32 归约，相对容差取机器 epsilon 的若干倍是常见做法；对 fp16 或 bf16 的矩阵乘，容差要随 K 维长度增长，因为累加误差随归约深度累积。把容差写成单一常数而不说明数据类型与归约深度，等于把 oracle 变成随机门。

$$\text{err} = \frac{\lVert y_{\text{kernel}} - y_{\text{ref}}\rVert}{\lVert y_{\text{ref}}\rVert},\quad \text{pass} \iff \text{err} \le \tau(d,\,K)$$

这里 τ 是数据类型 d 与归约深度 K 的函数，而不是常数。代价体现在假阴性与假阳性两侧：容差过紧会把合法的重排实现判错，浪费 agent 的优化轮次；容差过松会放过真实错误，污染可验证奖励。具体例子：一个用不同累加树实现的 softmax 归约，数值上与参考实现有微小差异，若容差按单次加法设定则必然误判，按归约深度缩放后才能通过。术语表应要求每个 oracle 条目写明容差函数的形式与标定方法，标定方法本身也要可复现：用参考实现在不同输入规模下自比较，观察误差分布的上分位，再留出安全裕度。

另一类正确性阈值是结构性判据，例如输出张量的形状、步长、是否原地修改输入。这类判据没有容差概念，只有布尔通过与否，但同样需要写明检查时机：是在 kernel 启动前校验参数，还是启动后比对输出。前者代价低但漏检运行时越界，后者代价高但能捕获真实内存错误，工程上通常两者并用，把前者作为快速门禁、后者作为精筛。

四 · 性能阈值的口径：SOL 百分比与相对加速比

性能阈值最常被误用的是“加速比”与“SOL 百分比”混用。加速比是相对基线的比值，基线一变结论就变；SOL（speed-of-light）百分比是相对硬件理论上限的比值，上限由 roofline 模型给出。两者不可互换：一个 kernel 相对慢基线有数倍加速，可能 SOL 只有很低；反之一个高度优化的 kernel 相对强基线加速有限，SOL 却已接近上限。术语表必须为每个性能阈值标注口径，并注明基线的选取规则。

$$\text{SOL} = \min\!\left(\frac{\text{achieved}}{\text{peak}_{\text{compute}}},\ \frac{\text{achieved}}{\text{peak}_{\text{bandwidth}}}\right)$$

roofline 的上限本身依赖算术强度，而算术强度依赖输入形状，所以 SOL 阈值必须绑定形状。代价在于基线维护：每换一个基线实现，所有相对加速比阈值都要重算；而 SOL 阈值虽不依赖基线，却依赖峰值规格的准确性，规格写错会系统性高估或低估。具体例子：判断一个 GEMM kernel 是否“够好”，用相对加速比会随 cuBLAS 版本漂移，用 SOL 百分比则稳定得多，但必须说明峰值算力取的是稠密还是稀疏口径。工程判断是：门禁用 SOL，汇报用加速比，两者都写清口径与绑定条件。

还有一类性能阈值是启动开销占比，对小 kernel 尤其关键。当 kernel 执行时间与启动开销同量级时，优化计算本身收益有限，阈值应转向“单次启动的固定开销是否可摊薄”。这类阈值的测量必须用 event 计时而非墙钟，且要区分冷启动与热启动，否则测到的是上下文建立而非 kernel 本体。

五 · 编译与工具链相关的经验数字

编译时间与寄存器压力是两类常被忽略的工程阈值。编译时间阈值用于约束 agent 的搜索空间：若每次变体编译耗时过长，多轮优化的总时延不可接受，agent 会倾向于保守变体而非激进探索。寄存器压力阈值用于判断占用率是否被寄存器文件卡住，它由每线程寄存器用量与每 SM 寄存器总量共同决定，超过拐点后占用率骤降。这两类阈值都不是“越小越好”，而是要与目标负载匹配。

  • 编译时间：区分单文件编译与全链接，前者影响搜索迭代速度，后者影响部署节奏；
  • 寄存器用量：用编译器资源报告读取，而非从源码估算；
  • 占用率拐点：由每 SM 的 warp 上限与寄存器、共享内存共同约束，取三者最小值；
  • 缓存配置：共享内存与 L1 的划分比例影响有效带宽，需按负载实测而非按默认值假设。

代价是编译时间与搜索广度的权衡：放宽编译时间阈值能覆盖更多模板实例与更大 tile，但每轮迭代的等待变长，同等 token 预算下能试的变体数下降。具体例子：一个使用大量模板展开的 kernel 变体，编译时间显著长于简化变体，若阈值设得过紧，agent 会系统性偏向未展开的实现，错过展开带来的性能收益。工程判断是把编译时间阈值设为“单轮预算的函数”而非固定常数，并记录每次编译的实际耗时用于校准。

六 · 阈值治理：版本化、灰区与回写

阈值一旦进入 agent 的奖励函数或门禁，就成为系统行为的一部分，必须像代码一样治理。治理的最小要求是版本化：每个阈值条目带版本号，变更需记录原因与影响面。其次是灰区设计：在通过阈值与失败阈值之间留出缓冲带，灰区内的结果不直接判负，而是触发补充测量或人工复核，避免阈值抖动导致 agent 行为震荡。第三是回写：测量得到的新数据要能反向修正阈值，形成闭环，否则阈值会随硬件与负载演进而腐化。

灰区的代价是判定时延：灰区内的样本需要额外测量或复核，单样本处理时间上升；但相比误判导致的优化轮次浪费，这个代价通常可接受。具体例子：某 kernel 的 SOL 百分比落在阈值附近反复抖动，若直接二值判定，agent 会在两个变体间来回切换；引入灰区后，系统对灰区样本追加一次高精度测量，用两次测量的中位数判定，抖动被吸收。回写机制则要求每次复核结论都写入阈值条目的修订记录，使下一个使用者能看到该阈值的置信度而非只看数值。

最终落在一条工程判断上：术语表里的每个数字都应能追溯到一次可复现的测量或一条明确的规格，无法追溯的数字应降级为“待测项”而非阈值。阈值治理的成本是持续的复核工作量，收益是 agent 行为在不同硬件、不同负载、不同工具链版本下保持可解释——这正是 kernel agent 可信评测的前提。

阈值不是常数：把“经验数字”写成可复测的判据

术语表里最容易腐坏的一类条目，是把“经验数字”写成孤立常数，例如“加速比大于某值才算收益”“误差小于某值才算正确”。这类写法在跨章引用时必然产生歧义，因为同一个数字在不同 dtype、不同 shape、不同 GPU 上对应完全不同的物理量。工程上应把阈值改写成三元组：判据 + 测量口径 + 失效条件。以 roofline 的 SOL 利用率为例，其定义是实测吞吐与同一 kernel 在该硬件上可达上界的比值，上界由访存带宽或峰值算力中较小者决定：

$$\mathrm{SOL}=\frac{T_{\text{measured}}}{\min\left(T_{\text{mem}},\,T_{\text{compute}}\right)},\qquad T_{\text{mem}}=\frac{\text{BytesMoved}}{BW_{\text{eff}}}$$

这里 BW_eff 必须是实测有效带宽而非规格书峰值，否则 SOL 会被系统性高估，导致 agent 把一次“带宽没打满”的优化误判为已达标。同理，正确性 oracle 的容差阈值不能只写一个绝对误差，而应写成相对误差与 ULP 的组合判据，并对归约类 kernel 额外声明累加顺序敏感性——因为浮点加法不满足结合律，换一种 tile 划分就会改变末位结果。这类阈值的代价是测量开销：每换一个 shape 就要重测一次上界，profile 采集本身会引入时延扰动，NCU 逐段 replay 还会放大总执行时间，因此阈值表应标注“在何种采集模式下测得”，否则复现时数字对不上。

测量方法上，建议把每个经验数字绑定到一条可执行的最小复现路径，而不是绑定到某次实验的结论。下表给出术语表中应强制填写的字段，缺任一项即视为口径不完整：

字段填写要求缺失后果
判据形式比值 / 绝对量 / ULP / 位级一致跨 dtype 不可比
测量口径warmup 次数、计时方式、是否含 launch 开销时延被高估或低估
失效条件shape 区间、dtype、是否含 mask/边界阈值被外推到不适用域
采集代价profile 模式、额外显存、编译时间复测成本被低估

失效条件的写法要具体到机制层面。例如“小 shape 下加速比阈值失效”，应展开为：当问题规模小到 launch 开销与 kernel 主体时延同量级时，任何指令级优化都被固定开销淹没，此时加速比的分母主要是驱动与调度成本，阈值应改为“端到端时延是否低于单次 launch 的若干倍”这类结构性判据。再如 Triton 与手写 CUDA 的对比阈值，必须声明是否计入编译时间与 autotune 搜索开销——agent 在多轮生成中反复触发编译，编译时间会直接吃掉 token 预算与墙钟预算，这项代价在只比较稳态 kernel 时延的表格里是看不见的。因此术语表的每个数字都应附带一句“该数字在什么条件下不再成立”，把边界写进定义本身，而不是留给读者去猜。
