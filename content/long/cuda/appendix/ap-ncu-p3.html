一 · 阈值的来源：从“可测基线”而不是“经验常数”出发

工程阈值不是拍脑袋的常数，而是从同一 kernel 的可测基线上推出来的。做法是：固定输入形状、固定编译选项、固定 profiler 采样区间，先跑出一个“干净基线”，再逐项改动一个变量，记录指标漂移。阈值 = 基线值 ± 允许漂移。没有这条基线，任何“占用率应大于 X%”的说法都是空话。具体机制上，NCU 的 --set full 会采集 SM 占用率、achieved occupancy、DRAM/L2 吞吐、warp stall 原因、tensor core 利用率、指令发射率等指标；但同一份报告里的数字受采样频率与 kernel 时长影响，短 kernel（微秒级）在 replay 模式下会被多次重放，指标是重放平均，不是单次真实值。因此测量方法的第一条纪律是：记录 kernel 的实际时长与 replay 次数，短于采样窗口的 kernel 要么合并多次调用再测，要么用 --replay-mode application 减少重放扰动。

代价在这里体现得很直接：--set full 的采集开销会让 kernel 时延膨胀一个量级以上，编译时间不变但端到端测量时间变长；如果用 --set roofline 或只开 --metrics 指定少量指标，开销显著下降，但丢失 stall 归因。工程判断是：调阈值阶段用窄指标集反复测，定阈值之后再用全量集做一次确认。一个具体例子：某 GEMM kernel 在 --set full 下报告 achieved occupancy 为 62%，但把 --metrics sm__warps_active.avg.pct_of_peak_sustained_active 单独采集时得到 58%，差异来自重放期间 L2 状态被扰动。阈值应取窄指标集的值，因为那才是生产路径上会出现的状态。

$$\text{threshold} = \text{baseline}(m) \pm k \cdot \sigma_{\text{replay}}(m)$$

其中 m 是指标，σ 是同一配置下多次采集的标准差，k 取 2 到 3。σ 本身就是要测的量：同一 kernel 连跑五次 NCU，看指标波动幅度。波动大的指标（如 L2 命中率，受 cache 预热影响）不适合做硬阈值，只适合做趋势判读。

二 · 占用率与延迟隐藏：阈值取决于 stall 结构而非固定百分比

SM 占用率（sm__warps_active.avg.pct_of_peak_sustained_active）和 achieved occupancy 常被当作“越高越好”，这是误读。占用率的工程意义只有一个：它是否足以隐藏该 kernel 的主导 stall。判读方法是先看 warp stall 原因分布，再看占用率。若主导 stall 是 stall_long_scoreboard（等全局内存），提高占用率有用；若主导 stall 是 stall_mio_throttle 或 stall_short_scoreboard（共享内存/特殊功能单元争用），提高占用率反而加剧争用，指标会变差。因此阈值不是“占用率 ≥ 50%”，而是“占用率提升后主导 stall 的占比下降”。

具体机制：NCU 的 warp state 统计把每个 warp 的周期归入若干 stall 类别，占比最高的那一类就是瓶颈信号。测量方法：用 --metrics smsp__average_warps_issue_stalled_*_per_issue_active.ratio 系列拿到各类 stall 的每发射周期平均 warp 数，比值最大的即主导项。代价：这套指标按 SMSP 细分，采集粒度细、开销中等；若只关心全局，用 --section WarpStateStats 一次拿全。一个具体例子：一个 elementwise kernel 占用率只有 25%，但 stall 分布里 stall_long_scoreboard 占七成，说明是访存延迟主导，此时把占用率提到 50% 能直接改善；而一个共享内存密集的 kernel 占用率 75%、stall_mio_throttle 占六成，再提占用率只会更糟，正确动作是减少 bank conflict 或改数据布局。

延迟隐藏的量化判据可以用 Little 定律形式表达：在给定占用率下，可隐藏的访存延迟上限约等于“每 SM 常驻 warp 数 × 每 warp 可并发指令数 ÷ 访存指令占比”。这不是精确公式，而是判读方向：占用率翻倍而 stall 占比不变，说明瓶颈不在延迟隐藏，继续调占用率是无效工程动作。

三 · 吞吐类指标：DRAM/L2 与 roofline 的距离怎么量

DRAM 吞吐（dram__throughput.avg.pct_of_peak_sustained_elapsed）和 L2 吞吐（lts__throughput.avg.pct_of_peak_sustained_elapsed）的阈值判读依赖 roofline 位置。方法：先用 --set roofline 或 --section SpeedOfLight 拿到 SM 与 Memory 两条 pipe 的利用率百分比，取较高者作为“当前受限维度”。若 Memory pipe 显著高于 SM pipe，则 kernel 是带宽受限，此时 DRAM 吞吐接近峰值百分比就是合理阈值；若 SM pipe 更高，DRAM 吞吐低是正常现象，不该拿它当瓶颈指标。具体机制：SpeedOfLight 段落把计算吞吐与内存吞吐各自归一化到峰值，两个百分比的大小关系直接给出受限类型，不需要自己算算术强度。

测量方法的坑在于“峰值”口径。DRAM 吞吐百分比的分母是理论峰值带宽，实际可达带宽受 ECC、刷新、访问模式影响，通常低于理论值；因此 80% 的 DRAM 吞吐在工程上已接近饱和，继续优化访存模式收益有限，应转向减少访存量（融合、复用、更低精度）。代价维度：DRAM 吞吐提升往往以显存占用或额外拷贝为代价，例如为了合并访问引入的 staging buffer 会多吃显存；L2 吞吐提升可能靠提高命中率，代价是更大的 tile 占用共享内存，压缩占用率。一个具体例子：一个 reduction kernel 的 DRAM 吞吐 78%、SM 吞吐 12%，判定为带宽受限；把两趟 reduction 改成一趟、用 warp shuffle 减少中间写回，DRAM 吞吐降到 55% 但总时延下降，说明原来的 78% 是“无效饱和”——吞吐高但做的功有冗余。

$$\text{arithmetic intensity} = \frac{\text{FLOPs}}{\text{Bytes moved}},\quad \text{bound} = \arg\max(\text{SM\%, Mem\%})$$

算术强度与 roofline 拐点的比较决定阈值该看哪条 pipe；这个量可以从 NCU 的 FLOP 计数与 DRAM 字节数直接算出，不需要额外建模。

四 · tensor core 利用率与指令发射率：分母口径决定阈值可信度

tensor core 利用率（sm__pipe_tensor_op_hmma_cycles_active.avg.pct_of_peak_sustained_active 一类指标）的阈值判读有两个前提：kernel 确实用了 tensor core 指令，且分母口径与指令形状匹配。若 kernel 走的是 FP32 FMA 路径，这个指标恒为零，拿它当瓶颈指标毫无意义。测量方法：先确认 SASS 里存在 HMMA/IMMA 指令（用 --section InstructionStats 或导出 SASS），再看 pipe 活跃周期占比。代价：tensor core 利用率高的 kernel 往往对数据布局敏感，为了喂满 pipe 需要 ldmatrix 与 swizzle，编译时间与寄存器压力上升；利用率从 40% 提到 70% 可能伴随占用率下降，两者要一起看。

指令发射率（smsp__inst_executed.avg.per_cycle_active 或 issue slot 利用率）的阈值更微妙：发射率接近每周期 1 条是 SMSP 的上限，但达到上限不等于高效——可能是在发射大量低价值指令（地址计算、谓词设置）。判读方法是把发射率与 stall 占比、每指令完成的工作量一起看。具体机制：smsp__issue_active.avg.pct_of_peak_sustained_active 给出 issue slot 占用百分比，配合 smsp__inst_executed.sum 可算每周期发射数。一个具体例子：某卷积 kernel 发射率 92%、tensor core 利用率 35%，看似发射很忙，但 SASS 显示大量指令用于 im2col 地址计算；把地址计算提到循环外、改用更规整的 tile 遍历后，发射率降到 70%、tensor core 利用率升到 60%、总时延下降。这说明发射率阈值不该单独设，应设为“发射率 × 每指令有效工作量”的联合判据。

代价维度：提高 tensor core 利用率通常要求更大的 tile，寄存器与共享内存占用上升，占用率下降；这是一对需要同时观测的指标，阈值应写成二元组而非单值。

五 · 没有数字时怎么测：最小可复现测量协议

当手头没有可信阈值时，不要引用二手经验值，而是跑一个最小协议。步骤如下：第一，固定输入形状与数据分布，记录随机种子；第二，用 --metrics 指定一组窄指标（占用率、主导 stall、DRAM 吞吐、tensor pipe 利用率、发射率），避免全量采集的重放扰动；第三，同一配置连跑至少五次，记录均值与标准差；第四，只改一个变量（tile 大小、线程数、向量化宽度），重复测量，画出指标随变量的单调区间；第五，把“指标开始变差或不再改善”的拐点作为该变量的工程阈值。这套协议的代价是测量时间：每个配置五次采集，若 kernel 本身毫秒级，单配置总耗时在秒级到十秒级，几十个配置就是分钟级，可接受；若 kernel 微秒级，需在应用层循环调用以拉长采样窗口，代价是引入调用开销，需在报告中注明。

具体机制上，窄指标集的选择原则是“每个受限维度一个代表指标”：SM 受限看发射率与 stall，内存受限看 DRAM/L2 吞吐，tensor 受限看 tensor pipe 利用率，占用率作为横切指标始终保留。这样五个指标足以覆盖判读，采集开销远低于 --set full。一个具体例子：调一个 layernorm kernel 的 block 大小，从 128 到 1024 扫一遍，记录 achieved occupancy 与 DRAM 吞吐；发现 256 之后占用率不再上升而 DRAM 吞吐持平，拐点在 256，阈值就定为“block ≥ 256 无收益”，而不是引用某个外部数字。

测量协议里必须写清的三件事：replay 次数、采样窗口是否覆盖完整 kernel、以及是否开启了 cache 预热。缺任何一项，指标都不可比。工程判断落在最后一句：阈值是测量协议的产物，换协议就要重测，跨 kernel 复用阈值只在受限类型相同时才成立。

阈值不是判据，是分诊顺序：占用率、吞吐与 stall 的联合判读

把 NCU 指标当阈值表用，最常见的失效方式是拿单指标卡线：看到 achieved occupancy 低于某个数就断定“占用率不足”，或看到 DRAM 吞吐不到峰值就断定“带宽没打满”。这两类判读在真实 kernel 上都会给出错误处方。原因是 SM 占用率与 achieved occupancy 描述的是“有多少 warp 槽位被填上”，而 DRAM/L2 吞吐描述的是“这些 warp 实际换回了多少字节”，二者之间没有单调关系：一个 occupancy 很高的 kernel 完全可能因为 warp 在同一 barrier 上串行而把 DRAM 吞吐压到很低；反过来，一个 occupancy 只有个位数的 persistent kernel 可以把 HBM 打到接近 SOL。工程上正确的用法是把阈值当作分诊顺序而非判决：先看 warp stall 原因分布决定“这个 kernel 是在等什么”，再用吞吐指标确认“等的东西是否真的是瓶颈资源”，最后才用 occupancy 判断“有没有足够的并发来掩盖这个等待”。

分诊的第一步是 stall 分布。NCU 的 warp stall 采样把每个 warp 的停顿周期归到若干原因上（long scoreboard 对应等待全局/本地内存返回，short scoreboard 对应 shared memory 与部分 MIO 依赖，barrier 对应 __syncthreads 与协作组同步，MIO throttle 对应特殊功能单元与 shared 指令队列拥塞，LG throttle 对应 LSU 发射队列满，not selected 表示 warp 就绪但调度器选了别人，imc/imc 分支与指令取指相关）。判读的关键不是某一个原因的绝对值，而是“主导原因是否与吞吐指标一致”。若 long scoreboard 占主导且 DRAM 吞吐接近 SOL，说明访存延迟已被充分掩盖，问题不在占用率；若 long scoreboard 占主导但 DRAM 吞吐远低于 SOL，则要么访问模式导致事务碎片化（例如 stride 访问把 128B 事务拆成多段），要么 L2 命中率异常，此时提高 occupancy 只是增加同时排队的请求数，未必提升有效带宽。一个具体的边界例子是带 `__syncthreads()` 的分块归约：当块大小使每个 SM 只能驻留一个 block 时，barrier stall 会随块内 warp 数线性上升，此时把 block 缩小以提高驻留块数能直接削掉 barrier 停顿，但如果缩小后每块的 shared memory 分块变小、全局读取的事务数增加，DRAM 侧的有效吞吐反而下降——这就是阈值判读必须带上的系统代价。

第二步是吞吐指标的口径。NCU 报出的 DRAM throughput 与 L2 throughput 都是“相对峰值的百分比”，分母取决于所测 GPU 的时钟与位宽配置，因此跨器件比较百分比没有意义，只能在同一器件同一时钟状态下比较同一 kernel 的不同版本。更稳的做法是同时看绝对字节速率与事务效率：有效带宽可写成

$$B_{\text{eff}} = \frac{\text{DRAM bytes read+write}}{\text{kernel duration}} \le B_{\text{peak}},\qquad \eta_{\text{tx}} = \frac{\text{sectors requested}}{\text{sectors required}}$$

其中 $\eta_{\text{tx}}$ 越接近 1 表示每次请求都落在真正需要的 sector 上；当它明显大于 1 时，说明存在 over-fetch（例如按 4B 步长读取却每次拉回 32B sector），此时即便 DRAM 百分比看起来“打满了”，实际有效载荷仍低于峰值，处方应是改访问布局而不是加并发。tensor core 利用率同理：它衡量的是 tensor pipe 处于活跃的周期占比，一个用 tensor core 做小尺寸 MMA 的 kernel 可以报出很高的利用率却仍被 long scoreboard 拖住，因为 MMA 指令之间在等操作数。指令发射率（issue slot 利用率）则用于区分“发射受限”与“等待受限”：发射率高而 stall 以 not selected 为主，说明调度器有富余 warp 可挑，瓶颈在指令吞吐；发射率低而 stall 集中在单一 scoreboard 原因，说明瓶颈是延迟而非发射。

第三步才是 occupancy，并且必须区分“理论占用率”和“achieved occupancy”。理论占用率由寄存器数、shared memory、block 大小与每 SM 的槽位上限共同决定，是可静态计算的；achieved occupancy 是采样期内活跃 warp 的平均占比，它会因为尾部效应、负载不均衡、以及 block 结束时的排空而低于理论值。判读规则是：只有当 stall 的主导原因属于“可被更多并发掩盖”的类型（long scoreboard、short scoreboard 的延迟类），且理论占用率明显低于可达到的上限时，提高 occupancy 才是有效处方；若主导原因是 barrier、MIO throttle 或 LG throttle，提高 occupancy 往往加重队列拥塞。测量方法上，不要依赖单次 profile 的瞬时值：用 NCU 的 `--set full` 或按 section 采集时，注意 replay 模式会多次重放 kernel，对含原子操作或非确定性输入的 kernel，重放会改变结果分布，此时应改用 `--replay-mode application` 或缩小采集 section 集合以降低重放次数；对 achieved occupancy 这类采样型指标，至少取多次采集的稳定区间再下判断。经验数字只应作为“先查哪里”的排序依据——例如 stall 分布中某一原因占比显著高于其余原因时优先查该路径，occupancy 与理论上限差距明显时优先查寄存器压力与 shared memory 配置——而不应作为通过/不通过的硬门槛。
