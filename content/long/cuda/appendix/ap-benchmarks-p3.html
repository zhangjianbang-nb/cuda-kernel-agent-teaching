一 · 阈值不是常数，是绑定测量条件的判据

在 KernelBench 系基准的工程实践中，一个数字脱离测量条件就没有意义。同一个“加速比 1.5×”在 L1 单算子、L2 融合算子、L3 端到端三层上的可信度完全不同：L1 的基线是参考实现单次调用，L2 的基线包含中间张量物化开销，L3 的基线则是完整模型前向。因此本部分讨论的所有阈值都写成三元组形式——(指标, 测量协议, 判据)，缺一项即视为不可用。工程上最常见的错误是把 L1 上测得的加速比直接搬到 L2 的评分脚本里做门限，结果是在融合场景下基线本身被高估，agent 生成的 kernel 看似“达标”实则没有收益。

测量协议至少需要固定四件事：输入形状与 dtype、warmup 与重复次数、计时边界（是否含 kernel launch、是否含 host-device 同步）、以及基线实现的选择（PyTorch eager、torch.compile、还是基准自带的参考 CUDA 实现）。以 L1 的 elementwise 类算子为例，计时边界若只包住 kernel 调用而不含 cudaDeviceSynchronize，测得的时延会被 launch 异步性吞掉，小 shape 下误差可达数量级；正确做法是在计时循环外做同步，循环内用 CUDA event 打点，并对每个 shape 取中位数而非均值，因为首次调用含上下文初始化与 JIT 开销。

$$\text{speedup} = \frac{\text{median}(T_{\text{baseline}})}{\text{median}(T_{\text{candidate}})},\quad \text{valid iff } \text{rel\_err} \le \tau_{\text{acc}} \ \wedge\ \text{cv} \le \tau_{\text{cv}}$$

其中 cv 是重复测量的变异系数，用来判定测量本身是否稳定。若 cv 超过阈值，加速比数值不可采信，应先排查时钟降频、共享 GPU 争用或 shape 过小导致的计时噪声。这一步的代价是测量时间：每个候选 kernel 在每个 shape 上做 5 次 warmup 加 20 次重复，单点约几十毫秒到数百毫秒；一个 L1 任务集合若含数十个算子、每个算子若干 shape，全量扫描的墙钟时间会显著超过单次编译时间，因此实践中常采用分层抽样——先在小 shape 上筛掉明显错误的候选，再对通过者做全 shape 精测。

二 · 正确性阈值的分层设定

正确性 oracle 的容差不是全局统一的，它随算子数值性质分层。逐元素算子（add、relu、sigmoid）在 fp32 下相对误差阈值可以收紧到 1e-5 量级；归约类算子（sum、softmax、layernorm）因累加顺序改变会放大误差，阈值需放宽到 1e-4 至 1e-3；矩阵乘类在 fp16 输入、fp32 累加下，与参考实现的差异主要来自分块顺序，通常用相对误差加绝对误差的混合判据。基准的评分脚本入口通常把容差写成配置项而非硬编码，agent 在生成 kernel 时应读取该配置而不是自行假设。

一个具体机制是“双阈值判定”：先做全元素逐点比较，统计超出容差的元素比例；若比例为零则通过，若比例极小但不为零，则检查这些元素是否落在参考实现本身数值不稳的区域（如 softmax 的极小概率项）。后者的代价是需要额外保存参考输出与中间量，显存占用翻倍；在 L2 融合算子中，中间量本身已被消除，无法逐层比对，只能做端到端输出比对，此时容差必须按融合链路的误差累积上界设定，否则会把正确的融合实现误判为错误。

  • 逐元素类：相对误差阈值紧，绝对误差阈值按 dtype 的机器 epsilon 量级设定。
  • 归约类：阈值放宽一个数量级，并对全零、全同值、含 NaN/Inf 的输入单独建用例。
  • 矩阵乘类：混合判据，且需覆盖非对齐 shape（如 M=1 的 GEMV 退化情形）。
  • 融合类：只做端到端比对，容差按链路长度累积，并显式记录每一跳的 dtype 转换。

正确性验证的时间代价常被低估：一个含 NaN 检测的逐点比较在千万级元素上需要一次全量 device-to-host 拷贝加 CPU 侧遍历，单次耗时可达数十毫秒，若对每个候选都执行，验证开销会超过 kernel 本身的执行时间。工程折中是先用 kernel 内的 reduce 做快速差异范数，只在范数超限时才回落到逐点比对。

三 · 性能判据：从加速比到 roofline 占比

加速比是相对量，容易被基线选择操纵；roofline 占比是绝对量，更难伪造但需要硬件峰值数据。工程上推荐的判据是二者并用：加速比用于筛选“比基线快”，roofline 占比用于判定“是否接近该算子的物理上限”。对一个 memory-bound 算子，roofline 判据是实测带宽除以峰值带宽；对 compute-bound 算子则是实测 FLOPs 除以峰值算力。基准中 L1 的多数算子属于前者，因此带宽利用率是主判据，算力利用率仅在 matmul、conv 类上作为主判据。

$$\eta_{\text{bw}} = \frac{B_{\text{eff}}}{B_{\text{peak}}},\quad B_{\text{eff}} = \frac{\text{bytes moved}}{T_{\text{kernel}}}$$

这里 bytes moved 必须按算法实际搬运量计算，而非按张量大小乘以元素宽度简单估算——融合算子消除中间张量后，搬运量下降，η 上升，这正是 L2 相对 L1 的收益来源。一个具体例子：两个逐元素算子串联，非融合实现搬运量为 4 倍张量字节（读入、写出、再读入、再写出），融合后降为 2 倍，理论带宽利用率上限不变但有效吞吐翻倍，因此融合版的加速比上限约为 2×，任何显著超过该值的测量都应怀疑计时边界或基线实现有问题。

测量 roofline 占比的代价在于需要一次独立的峰值带宽标定，通常在目标 GPU 上跑一个纯拷贝 kernel 取实测峰值，而非查表。标定本身耗时短，但结果随 GPU 时钟状态漂移，需在每次评测会话开始时重做。另一个代价是 NCU profile 的采集开销：逐 kernel 采集 stall 原因与内存事务统计会使 kernel 执行变慢数倍，因此只对通过加速比筛选的候选做 profile，且采样比例控制在能覆盖主要 warp 的最小集合。

四 · 编译时间与 token 预算的硬约束

agent 生成 kernel 的迭代循环里，编译时间是隐性成本。CUDA C++ 路径下单次 nvcc 编译含模板实例化，复杂 kernel 可达数秒到数十秒；Triton 路径的 JIT 编译在首次调用时触发，后续命中缓存，但缓存键包含 shape 与 dtype，shape 变化即重新编译。CuTe 模板元编程的编译时间更长，且错误信息冗长，agent 读取编译日志消耗的 token 显著高于 Triton。这些成本必须计入迭代预算，否则 agent 会在编译阶段耗尽轮次。

工程阈值建议按路径分层：Triton 单次编译控制在秒级以内，允许每个任务多轮试错；CUDA C++ 单次编译若超过十秒量级，应限制每任务的编译次数，并把编译失败视为高代价事件，优先通过静态检查（类型、共享内存上限、寄存器压力预估）在提交编译前拦截。一个具体机制是编译缓存键的规范化：把 shape 归一化为若干档位（小、中、大），同一档位内复用编译产物，代价是档位边界处的性能损失，收益是编译次数下降一个量级。

路径编译触发时机主要成本控制手段

token 预算的代价体现在日志回读：编译错误日志长度与模板嵌套深度正相关，agent 每轮回读全部日志会挤占生成预算。工程做法是只回读首条错误及其上下文若干行，其余截断，并在 prompt 中显式告知截断规则，避免 agent 反复请求完整日志。

五 · 饱和项与防作弊阈值的联动

基准中存在已知饱和项：某些算子在参考实现已经接近 roofline 上限，加速比空间极小，此时任何声称大幅加速的结果都应触发防作弊检查。饱和项的判定方法是先测参考实现在目标硬件上的 roofline 占比，若已超过高位阈值（如带宽利用率接近峰值），则该算子从“加速比排序”中剔除，改为“正确性加不退化”判据。这一步的代价是需要对参考实现本身做 profile，而非只测候选。

防作弊阈值与性能阈值必须联动设定：若候选 kernel 的加速比超过饱和项的理论上限，直接判定为测量异常或实现作弊（如跳过部分计算、缓存结果、利用输入分布特性）。一个具体机制是输入扰动检查——对同一 shape 用多组随机输入重测，若加速比随输入分布剧烈波动，说明实现依赖了特定数据模式而非通用计算。该检查的代价是测量次数成倍增加，因此只对排名靠前的候选执行。

  • 饱和项先标定参考实现的 roofline 占比，再决定是否纳入加速比排序。
  • 超过理论上限的加速比一律进入人工复核队列，不直接计入评分。
  • 输入扰动检查覆盖至少三组分布，波动超阈值即标记。
  • 融合算子的理论上限按搬运量比值推导，而非经验估计。

工程判断落在具体机制上：把“阈值”实现为评分脚本中的结构化配置——每个算子条目携带容差、roofline 上限、饱和标记与测量协议版本号，agent 在生成阶段读取同一份配置作为自检依据，评测阶段用同一份配置判定。配置版本号保证跨会话可比，任何阈值调整都必须伴随版本号递增，否则历史结果不可复现。

阈值不是常数，是随基准档位漂移的判据

在 KernelBench 系基准里，“通过”与“加速”从来不是单一数字，而是由评分脚本入口处的比较逻辑决定的判据组合。L1 的算子集合以单算子为主，参考实现来源多为 PyTorch 原生算子，评分脚本通常以固定随机种子生成输入、跑若干次取中位数，再与参考实现做逐元素容差比较；L2 引入融合与多算子链路，规模档位上升后，单次运行的时延被放大，评分脚本对“加速比”的分母更敏感——参考实现的基线若被固定在未融合版本，任何融合都会显得收益巨大，反之若基线已是最优实现，阈值就必须收紧。L3 更接近端到端形状，评分脚本入口往往要求同时满足正确性 oracle 与性能门槛，二者缺一即判负。这里的工程判断是：阈值必须与档位绑定记录，跨档位复用同一组容差和加速比门槛，会把 L1 的宽松判据带进 L3，产生系统性虚高。

正确性容差的测量方法必须写死在评分脚本里，而不是留给 agent 自报。常见做法是对每个输出张量计算相对误差与绝对误差的联合判据：

$$\text{pass} = \bigl(\lVert y_{\text{cand}} - y_{\text{ref}} \rVert_\infty \le \tau_{\text{abs}}\bigr) \lor \Bigl(\frac{\lVert y_{\text{cand}} - y_{\text{ref}} \rVert_2}{\lVert y_{\text{ref}} \rVert_2 + \epsilon} \le \tau_{\text{rel}}\Bigr)$$

其中 $\tau_{\text{abs}}$ 与 $\tau_{\text{rel}}$ 随数据类型漂移：fp32 路径可用较紧的相对容差，fp16/bf16 路径必须放宽，否则归约类算子（softmax、layernorm）在长序列上会因累加顺序差异被判错。代价是显存的：为了做逐元素比较，评分脚本需要在 GPU 上同时驻留候选输出与参考输出，L2/L3 的大形状下这份额外显存可能超过 kernel 本身的占用，导致测量本身改变被测对象的驻留行为。具体例子：一个融合的 layernorm 候选在 L2 档位上因累加顺序与参考实现不同，$\lVert \cdot \rVert_\infty$ 超出 fp16 的绝对容差，但相对误差在阈值内；若评分脚本只查绝对误差，正确实现被误杀，agent 会退回未融合版本，加速比归零。

性能门槛的测量方法要区分“单次时延”与“稳态吞吐”。KernelBench 系评分脚本普遍采用预热若干次后取多次运行的中位数，以压制首次启动的上下文初始化与 JIT 开销；但 Triton 路径的编译时间不可忽略，首次调用触发编译，若预热次数不足，中位数会被编译时延污染。工程上应把编译时间单独记账，不混入 kernel 时延，否则 agent 会学到“避免重编译”而非“写更快的 kernel”。CUDA-L1 一类任务在评分脚本入口处对防作弊有约束：禁止调用参考实现本身、禁止缓存跨轮结果、禁止在计时区间外做预计算。这些约束的代价是评分脚本必须做静态与动态双重检查，静态查源码里的禁用符号，动态查计时区间的调用图，检查本身增加评分时延，但不检查则加速比可被“把计算挪到计时外”轻易伪造。饱和项的处理同理：当某算子集合在参考实现下已接近硬件上限，继续压加速比门槛只会筛出噪声，评分脚本应对这类条目改用绝对时延上限或直接标注饱和、不计入排名。

判据测量位置失效条件系统代价
