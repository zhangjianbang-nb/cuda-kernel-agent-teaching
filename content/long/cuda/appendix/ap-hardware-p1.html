一 · 条目是什么：硬件分母的可引用快照

《GPU 硬件规格速查》里的每一条目，是一台具体 GPU 型号在某一固定口径下的一组标量：SM 数量、显存带宽、L2 容量、tensor core 代际、NVLink 拓扑形态、功耗墙。它的用途不是介绍硬件，而是充当 roofline 与 SOL 计算的分母来源——当 agent 声称某个 kernel 达到 70% 峰值算力或 55% 带宽利用率时，这些百分比的分母必须能追溯到条目里的一个数，而不是随手估的。条目因此是“可引用快照”而非“产品参数页”：快照意味着它有版本、有口径、有失效条件。

定义上要卡住三点。第一，条目只收录对 kernel 生成与评测有决策价值的量。SM 数决定并行度上限与占用率计算；显存带宽决定带宽受限 kernel 的 roofline 斜率；L2 容量决定分块（tiling）策略的可行性边界；tensor core 代际决定一条 MMA 指令的形状与吞吐档位；NVLink 拓扑决定多卡切分与集合通信的代价；功耗墙决定持续负载下的降频风险。第二，每个量必须带口径标签：显存带宽是理论峰值还是可持续值，SM 数是物理 SM 还是可调度 SM，功耗墙是板卡 TDP 还是可持续功耗。第三，条目必须与一个“分母引用协议”绑定——评测脚本从条目取数，而不是从注释或自然语言描述里取数。

$$\text{SOL}_{\text{mem}} = \frac{B_{\text{eff}}}{B_{\text{peak}}},\qquad \text{SOL}_{\text{comp}} = \frac{F_{\text{eff}}}{F_{\text{peak}}}$$

公式里 $B_{\text{peak}}$ 与 $F_{\text{peak}}$ 正是条目提供的两个分母；$B_{\text{eff}}$ 由 NCU 的 dram 吞吐读出，$F_{\text{eff}}$ 由指令计数与时钟推算。分母错一位，SOL 结论就整体偏移，而 agent 的多轮 RL 会把这个偏移当成真实梯度信号学进去——这是条目必须精确到口径的直接代价。具体例子：一个以流式拷贝为主的 kernel，若条目给的带宽是理论峰值而实测只能达到其一部分，agent 会持续收到“未达标”的惩罚信号，进而把优化预算浪费在无法突破的物理上限上；正确做法是条目同时给出理论峰值与可持续带宽两个字段，并规定 SOL 计算用后者。

代价方面，条目维护本身有成本：每新增一个型号、每换一次驱动或固件口径，都要重新核对字段并触发下游基准的重算，否则历史 SOL 曲线不可比。这类维护开销是 token 与工程时间，不是显存或时延，但它决定了整套评测的可信度基线。

二 · 分类维度：按“影响哪一类决策”切分，而非按产品线

条目的分类不能照抄厂商的产品分层（数据中心/消费/工作站），因为那对 kernel agent 没有决策含义。可用的分类维度是“这个字段影响哪一类生成与优化决策”，由此得到四个正交维度。

  • 并行度维度：SM 数、每 SM 的 warp 槽位、寄存器文件与共享内存容量。它决定占用率、grid 划分与尾效应，是 occupancy 调优与 persistent kernel 设计的输入。
  • 带宽维度：显存带宽、L2 容量与 L2 带宽、显存容量。它决定 roofline 的拐点位置、分块尺寸上限、以及是否值得做 shared memory 暂存。
  • 算力维度：tensor core 代际、支持的 MMA 形状与数据类型、FP32/FP64 单元配比。它决定一条 Triton 或 CuTe 的 MMA 原语能否在该卡上编译通过并达到预期档位。
  • 拓扑与功耗维度：NVLink 拓扑形态（是否全互联、是否有 NVSwitch）、PCIe 代际、功耗墙。它决定多卡切分策略、通信隐藏窗口、以及长时 benchmark 是否需要插入降频保护。

这四个维度不是并列的标签，而是有依赖顺序：先由算力维度确定 kernel 的指令级形态，再由带宽维度确定 roofline 上限，再由并行度维度确定能否填满该上限，最后由拓扑与功耗维度确定多卡与持续负载下的修正。分类的价值在于让 agent 在检索条目时按决策类型取字段，而不是把整张表塞进上下文——后者浪费 token 且稀释注意力。

维度代表字段影响的决策取数错误时的代价
并行度SM 数、寄存器/共享内存grid 划分、occupancy、persistent 设计尾效应误判，占用率调优方向反了
带宽显存带宽、L2 容量分块尺寸、暂存策略、roofline 拐点分块超出 L2，带宽利用率虚高
算力tensor core 代际、MMA 形状原语选型、数据类型、编译可行性生成不可编译或不达档位的 kernel
拓扑功耗NVLink 形态、功耗墙多卡切分、通信隐藏、降频保护通信代价低估，长跑数据不可比

具体例子：一个 agent 要在多卡上生成 all-reduce 融合的 kernel，它需要拓扑维度回答“是否全互联”，需要带宽维度回答“单卡带宽与链路带宽之比”，两者共同决定切分粒度；若只取 SM 数就动手，生成的切分在非全互联拓扑上会因跨节点跳数而崩溃。这里的代价是通信时延与显存占用同时上升，且正确性 oracle 不会报错——性能塌陷是静默的。

三 · 与相邻概念的区别：规格条目不是 profile，不是基准，不是成本表

最容易混淆的是把硬件规格条目当成 NCU 指标快照。区别在方向：条目是分母，是静态的、与具体 kernel 无关的上界；NCU 指标是分子，是动态的、与具体 kernel 与输入形状绑定的实测值。SOL 计算是把两者相除的动作，条目本身不含任何实测。混用会导致一个典型错误：把某次 profile 里读到的 dram 吞吐当作该卡的带宽字段写回条目，于是分母被一次偶然测量污染，后续所有 SOL 都失去可比性。

与 KernelBench 系基准的区别在粒度：基准条目描述的是“任务 + 输入分布 + 正确性判据 + 计时协议”的组合，回答“这个 kernel 该得多少分”；硬件条目描述的是“这台机器能给多少上限”，回答“这个分数离物理极限多远”。两者通过分母引用协议连接：基准的评分脚本从硬件条目取 $B_{\text{peak}}$ 与 $F_{\text{peak}}$，但基准本身不定义这些数。若基准自带硬编码的峰值，硬件条目就形同虚设，跨型号对比也不再成立。

与算力与成本估算表的区别在单位：成本表以美元、小时、token 为单位，回答“跑这次搜索要花多少”；硬件条目以 SM、字节每秒、字节、代际、拓扑、瓦特为单位，回答“物理上能到哪”。二者共享型号键，但字段集合不相交，混表会让 agent 把功耗墙当成预算约束去优化，方向完全错位。

与 Triton/CuTe/PTX 对照的区别在层次：那份对照回答“同一语义在三种表达层里怎么写、编译代价差多少”；硬件条目回答“写出来的东西在哪种硅上跑、上限是多少”。一个 CuTe 的 MMA 原语能否落地，取决于条目里 tensor core 代际字段；但条目不告诉你原语怎么写。指路即可，不展开。

具体机制上，区分靠字段级 schema：每个条目字段带 kind 标记（peak / sustained / topology / generation），SOL 计算只允许引用 kind=peak 或显式声明为分母的字段；profile 读数一律标 kind=measured，禁止回写。这条 schema 规则的正确性代价是：任何一次人工“修正”条目都会破坏历史可比性，需要版本号与重算触发。性能代价则是评测流水线多一次查表与校验，时延可忽略，但换来的是分母不被污染。

四 · 条目的失效条件与代际字段的语义

条目不是永久真理，它有三个失效源。其一是口径变更：驱动、固件或时钟策略调整会改变可持续带宽与可持续功耗，理论峰值不变但分母的可用版本变了。其二是负载形态：功耗墙字段在短时 burst 与长时持续负载下含义不同，若 benchmark 时长跨过降频拐点，用 TDP 当分母会系统性高估 SOL。其三是拓扑装配：同一型号在不同整机配置下 NVLink 形态可能不同（是否经 NVSwitch、链路是否被分区），条目必须以“型号 + 拓扑形态”为键，而不是只以型号为键。

$$\text{SOL}_{\text{adj}} = \frac{B_{\text{eff}}}{B_{\text{peak}}\cdot \eta_{\text{clock}}},\qquad \eta_{\text{clock}} = \frac{f_{\text{sustained}}}{f_{\text{boost}}}$$

$\eta_{\text{clock}}$ 是持续负载下的时钟折损因子，它把功耗墙字段转成一个可乘的分母修正。这个因子的取值必须来自条目而非现场猜测，否则不同批次的长跑数据不可比。代价是：引入修正后，短跑 kernel 的 SOL 会被低估，因此条目需要同时标注适用负载时长区间，评测脚本按时长选择是否施加修正。

代际字段的语义要单独卡住。tensor core 代际不是一个营销数字，而是一组可查询的能力：支持的 MMA 形状、支持的数据类型组合、每条指令的吞吐档位、以及是否支持稀疏变体。条目里存的是“代际标识 + 能力位图”，agent 在生成 Triton 或 CuTe 代码前先查位图，避免生成该代际不支持的形状——这类错误在编译期暴露，代价是编译时间与一轮无效生成；若在运行期才暴露，代价是正确性 oracle 失败与多轮 RL 的无效样本。

具体例子：某型号的条目若只写“第 N 代 tensor core”而不写能力位图，agent 可能生成一个依赖新形状的原语，在旧代际上编译失败，浪费一整轮搜索预算；反之若位图齐全，agent 会在生成前就选退化的形状，牺牲部分算力换取可编译性。这里的工程判断是：能力位图的维护成本高于代际数字，但它把失败从运行期前移到生成期，是值得的。

五 · 条目与分母引用协议的绑定方式

条目要真正起作用，必须与一个引用协议绑定，否则它只是文档。协议包含三步：查表、校验、冻结。查表按“型号 + 拓扑形态 + 口径版本”三元键取字段；校验检查所需字段的 kind 是否允许作为分母，以及负载时长是否落在条目声明的适用区间内；冻结把本次评测用到的分母快照写入结果元数据，使历史分数可复算。

  • 查表失败（型号缺失或拓扑形态未覆盖）时，评测必须报“分母不可用”并中止，而不是回退到默认值——默认值是分母污染的主要来源。
  • 校验失败（kind 不符或时长越界）时，允许降级为定性结论，但不允许输出百分比 SOL。
  • 冻结是写入而非读取：结果元数据里存的是分母的副本与版本号，不是指针，避免条目后续修订改变历史含义。

这套协议的性能代价体现在流水线时延上：每次评测多一次三元键查表与一次元数据写入，量级可忽略；真正的代价在存储与 token——冻结副本使每次评测结果体积增大，若把分母快照塞进 agent 上下文则挤占预算，因此协议规定快照只进结果元数据、不进 prompt，agent 侧只接收“分母已冻结”的布尔标志与必要的两个标量。

正确性代价则体现在可复算性上：没有冻结，条目一旦修订，历史 SOL 曲线会出现无法解释的跳变，多轮 RL 会把跳变误读为策略改进。具体例子：某次条目把可持续带宽字段从理论峰值改为实测可持续值，若未冻结，之前所有以理论峰值为分母的分数会突然“变好”，agent 学到的是一段虚假的奖励上升；冻结后，新旧分数各自带着自己的分母版本，比较时才需要显式换算。

六 · 字段粒度与 agent 检索的取舍

最后一个定义问题是粒度：条目该存多细？存太粗（只有型号与几个标量）则无法支撑分块与占用率决策；存太细（每 SM 的每个子单元、每条指令的吞吐）则条目体积膨胀，检索时挤占上下文，且维护成本随驱动版本线性上升。可操作的判据是“一个字段是否改变某类生成决策的离散选择”：SM 数改变 grid 划分的档位，L2 容量改变分块是否可行的布尔判断，tensor core 能力位图改变原语形状的枚举——这些值得存；而连续可调的微架构细节不值得，因为它们不改变离散选择，只改变常数因子。

检索侧的取舍同样具体：agent 不应把整张表读入，而应按决策类型取字段子集。生成阶段取算力与并行度维度，验证阶段取带宽维度算 SOL，多卡阶段取拓扑维度。每次取字段都带 kind 与版本，使 agent 的推理链里出现的是“分母来自条目版本 X”而非裸数字。代价是 prompt 结构变复杂、token 消耗上升；收益是分母可追溯，错误可归因到具体字段而非笼统的“模型不行”。

工程判断落在一条规则上：条目字段的增删必须由“是否改变离散决策”裁决，并由分母引用协议的校验步骤强制——新增字段若不被任何决策引用，就不进条目；被引用的字段若缺 kind 标记，评测直接拒绝启动。这条规则把条目从“参数汇总”变成“可执行的分母契约”，也是本部分与后续 profile、基准、成本条目能够拼接而不互相污染的前提。
