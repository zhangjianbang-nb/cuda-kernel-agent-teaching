一 · 指标条目的定义边界：一个指标条目到底规定了什么

在《指标口径与统计规范》里，“条目”不是指标名字本身，而是一份可执行的口径契约。一个合格条目必须同时固定五件事：测量对象（被测的 kernel 变体、输入形状分布、dtype、是否含 host 侧调度）、分子与分母的定义、采样协议（warmup 次数、重复次数、聚合方式）、噪声处理（中位数、分位数、置信区间算法）、以及失效判定（何时该次测量作废）。缺任何一项，条目就退化成“一个数字”，无法跨机器、跨实现、跨轮次比较。

把条目写成契约的直接收益是可复算。评测流水线读入条目，输出的是（值，区间，样本数，作废原因）四元组，而不是标量。代价是评测时延：每个条目要求的最小重复次数乘以单次测量时延，直接决定一轮 agent 迭代的墙钟时间；条目越严（重复越多、区间越窄），单轮反馈越慢，多轮 RL 的样本吞吐越低。这是口径严谨性与迭代吞吐之间的硬 trade-off，必须在条目层显式声明而不是在流水线里隐式默认。

具体机制上，条目用一个结构化记录表达，伪代码思路如下：

$$ \text{entry} = \langle \text{target},\ \text{num},\ \text{den},\ \text{warmup},\ \text{reps},\ \text{agg},\ \text{CI},\ \text{invalid}\rangle $$

其中 agg 取中位数或截尾均值，CI 指定自助法或 t 区间，invalid 是布尔谓词（如输出校验失败、出现 NaN、显存峰值超阈值）。举例：一个“加速比”条目若只写“baseline 时间 / 本实现时间”，而不规定 baseline 是否也走同一 warmup 与同一输入分布，则 agent 可以通过给 baseline 传入更冷的缓存来虚增比值——这正是条目必须把分母口径写死的原因。

二 · 分类维度一：按分子分母的物理量纲分类

条目按量纲分为四族，每族的分子分母口径差异是结构性的，不能互相换算。

  • 时间族：延迟（单次调用墙钟）、吞吐（单位时间处理的元素或 token 数）、编译时间、autotune 搜索时间。分子是时间或工作量，分母是次数、元素数或候选配置数。
  • 比率族：加速比、SOL 利用率、pass@k。分子分母都是同量纲的量，比值无量纲，但对分母的选取极度敏感。
  • 资源族：显存占用（峰值/稳态）、带宽占用。分子是字节数，分母是容量或理论峰值。
  • 正确性族：通过率、误差界内的匹配率。分子是通过的用例数，分母是用例总数，且用例集的构造规则本身属于条目的一部分。

量纲分类的工程意义在于：跨族聚合是无效的。把时间族的“延迟下降 20%”与比率族的“加速比 1.2”放进同一个排行榜加权，等于把不同分母混在一起。代价体现在报告层：每个族需要独立的聚合器与独立的置信区间算法（时间族适合对数域中位数，比率族适合对分子分母分别重采样再取比值），实现复杂度上升，但避免了“平均的加速比”这种无意义统计量。

具体例子：SOL 利用率的分子是实测有效吞吐（字节/秒或 FLOP/秒），分母是该 kernel 在目标硬件上的 roofline 上限（由带宽或算力决定，取两者较小者）。若条目未声明分母用的是理论峰值还是实测可达峰值（如用一次纯拷贝 kernel 标定的带宽），同一实现会得到两个差异显著的数字，且都无法与另一条目的数字比较。这就是为什么 SOL 条目必须把分母的标定方法写进契约。

三 · 分类维度二：按测量协议分类——冷、热与稳态

同一物理量在不同协议下是不同的条目。冷启动测量包含首次调用的上下文初始化、JIT 编译、cuModuleLoad 等一次性开销；热测量在 warmup 之后进行，反映稳态；稳态测量进一步要求输入数据驻留在预期层级（如 L2 命中率稳定）。三者不可互换，条目必须标注协议标签。

warmup 的作用不是“让数字好看”，而是把一次性开销从稳态估计中剔除。其代价是显式的时间预算：warmup 次数乘以单次时延计入评测总时延，对于毫秒级 kernel，warmup 占比可能超过测量本身。因此条目要规定 warmup 的终止判据——固定次数，还是连续若干次的中位数漂移小于阈值——后者自适应但引入额外方差，前者可复算但可能不足。

重复次数与聚合方式耦合。设单次测量值为 \(x_i\)，条目若规定取中位数，则估计量为：

$$ \hat{x} = \mathrm{median}\{x_1,\dots,x_n\},\quad \mathrm{CI}_{1-\alpha} = \left[\hat{x}_{(l)},\ \hat{x}_{(u)}\right] $$

其中区间端点由自助法重采样或按次序统计量取分位得到。中位数对长尾（如偶发的调度抖动、显存回收）稳健，代价是它不反映最坏情况；若条目关心尾延迟（如在线推理的 P99），就必须另设分位数条目，而不能用中位数条目代替。具体例子：一个 agent 生成的 Triton kernel 在 100 次重复中有 3 次因 autotune 缓存未命中而慢一个数量级，中位数条目会给出漂亮的稳态数字，而 P99 条目会暴露这一抖动——两个条目服务于不同的工程判断，不能合并。

四 · 与相邻概念的区别：条目、基准、检查器、配方

条目与相邻概念最容易混淆，区别在于职责边界。基准（如 KernelBench 系）定义任务集与评分维度，是“考什么”；条目定义单个维度的分子分母与统计协议，是“怎么算”；检查器（正确性验证器）判定单次运行是否有效，是“算不算数”；配方（多轮 RL 的可验证奖励）把条目输出映射为训练信号，是“怎么用”。四者串成一条链：基准选任务，条目定口径，检查器过滤无效样本，配方消费（值，区间）而非裸标量。

概念职责失效时的后果
基准任务集与评分维度任务分布偏移，跨基准不可比
条目分子分母、采样、聚合、区间数字可复算性丧失，跨机器漂移
检查器单次运行的有效性判定错误实现被计入通过率
配方条目输出到奖励的映射奖励被噪声主导，策略学不到信号

关键区别在“区间”这一项：只有条目产出置信区间，基准与检查器都不产出。配方若只消费点估计，会把测量噪声当成真实改进，导致策略对微小差异过拟合；若消费区间，则可对区间重叠的候选视为不可区分，从而抑制噪声驱动的更新。代价是配方侧需要额外的比较逻辑与样本预算——要缩小区间就得增加重复次数，直接推高单轮评测时延。

具体例子：一个实现把延迟从 1.00 降到 0.98（相对量），若条目规定的重复次数不足以让区间区分这两个值，配方应判定为“不可区分”而非“改进 2%”。这一判断的正确性完全依赖条目把区间算法写死；若条目只给中位数，配方无从判断，只能盲信点估计。

五 · 条目内部的分子分母陷阱：三个必须写死的细节

第一，分母是否包含框架开销。吞吐条目的分母若是“端到端墙钟”，则包含 host 侧调度、数据传输、同步；若是“kernel 内计时”，则仅含设备执行。两者差异可达数量级，条目必须声明计时边界（如用 CUDA event 包裹的范围）。代价是：端到端口径更贴近生产收益，但对 agent 不可控的框架噪声更敏感，方差更大，需要更多重复次数才能得到同宽区间。

第二，加速比的分母基线是否同协议。基线必须与本实现共享同一 warmup、同一输入分布、同一计时边界；否则比值失去意义。工程上常犯的错误是基线用库函数的最佳配置、本实现用默认配置，条目若不禁止这种不对称，加速比条目就变成配置比较而非实现比较。

第三，显存占用的分子是峰值还是稳态。峰值由分配器的高水位决定，受 autotune 期间临时缓冲影响；稳态反映常驻占用。条目必须指定采样点（如每次迭代后的分配器统计），并声明是否计入缓存池。代价是：峰值口径对 autotune 策略敏感，agent 可能通过减少候选配置来压低峰值，牺牲性能换显存——条目应把性能与显存拆成两个条目，避免单条目内的隐性权衡。

具体例子：编译与 autotune 时间条目，其分子是“从源码到可执行配置就绪”的墙钟，分母是候选配置数或编译单元数。若条目未声明是否计入 Triton 的磁盘缓存命中，同一 agent 在冷缓存与热缓存下会得到完全不同的数字，且热缓存数字无法反映首次部署成本——这正是条目要把缓存状态写进契约的原因。

六 · 分类维度三：按可比性范围分层

条目还应标注可比性范围，决定它能跨什么边界比较。三层：同机同栈可比（同一 GPU、同一驱动、同一编译器版本）、同机跨栈可比（同 GPU，不同 Triton/CuTe/PTX 路径）、跨机可比（不同 GPU 型号）。跨机可比要求条目把分母归一化到硬件上限（如 SOL 利用率），而绝对时延条目天然只在同机层可比。

分层的代价是条目数量膨胀：每个物理量乘以协议标签乘以可比层，形成条目矩阵。工程判断是只对进入排行榜与训练奖励的维度做全矩阵，其余维度保留单层条目以控制评测时延。具体机制上，条目记录里加一个 scope 字段，聚合器按 scope 分组，禁止跨组求均值。

具体例子：一个 SOL 利用率条目声明 scope 为跨机可比，则其分母必须用目标硬件的 roofline 上限而非实测拷贝带宽，否则不同型号的 GPU 之间数字不可比；而一个绝对延迟条目声明 scope 为同机同栈，则允许分母为实测基线，因为它只用于同机内的实现排序。两者服务于不同决策：前者回答“离硬件极限多远”，后者回答“比同机基线快多少”。把这两个问题混进一个条目，就会得到既不能跨机比较、又不能精确排序的中间态数字。

口径边界：当分母不再是"同一件事"

条目定义最容易失效的地方不在分子，而在分母是否与分子共享同一份工作量。以加速比为例，若基线取 PyTorch eager 的单次前向时延，而被测 kernel 的时延里已经扣掉了 autotune 与编译开销，那么分子分母描述的就不是同一条执行路径：前者包含框架调度与算子派发，后者只剩余 kernel 本体。工程上必须显式规定"计时窗口"的起止边界——是从 host 侧发起调用到同步返回，还是从第一个 kernel launch 到最后一个 kernel 结束——并规定基线是否走同一条 warmup 序列。一旦两边窗口不对齐，加速比会系统性偏向被测实现，且偏差随 kernel 数量增加而放大，因为每次 launch 的固定开销在分母里被重复计入、在分子里被摊薄。

把口径写成可判定的形式，比写成文字描述更可靠。设被测实现单次迭代时延为 timpl，基线为 tbase，则加速比 S = tbase / timpl；若两边各自重复 n 次并取中位数，则 S = median(tbase(1..n)) / median(timpl(1..n))。注意中位数之比不等于逐次比值的中位数，后者在抖动大时会给出偏乐观的结果，因此规范应锁定"先各自聚合、再相除"的顺序。同理，SOL 利用率的分母是 roofline 上该问题规模对应的理论下界（受限于带宽或算力中较紧的一项），而不是"某个已知最快实现"的实测值——后者会把实现质量混入物理上限，使利用率失去跨实现可比性。

失效条件集中在三类场景。其一是极小规模问题：当工作量低到 launch 开销与同步开销占主导时，任何以时延为分子的指标都在测量调度而非计算，此时应改用吞吐口径（单位时间处理的元素数或 token 数）并显式标注 batch 规模。其二是动态 shape 与数据依赖分支：若 warmup 阶段未覆盖实际运行时的 shape 分布，autotune 选出的配置在正式计时中触发重编译，编译时间会以尖峰形式污染中位数附近的样本，规范应要求把编译与 autotune 时间单列为一个独立条目而非并入时延。其三是显存占用：峰值显存与常驻显存是两个分母不同的量，前者决定能否跑通、后者决定能否并发，混用会让"显存优化"的结论无法复现。系统代价方面，为压低方差而增加重复次数会线性拉长评测墙钟时间，在 agent 多轮迭代场景下直接转化为 token 与算力预算的消耗；置信区间的计算本身也要求样本独立，若重复之间共享缓存状态，区间会被低估。
