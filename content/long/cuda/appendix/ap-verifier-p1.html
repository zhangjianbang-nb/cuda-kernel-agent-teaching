一 · 条目是什么：一条可执行断言，而非一份检查表

在 Kernel Agent 的语境里，“正确性验证器清单”中的每一条条目（entry）不是一句“要检查正确性”的口号，而是一个可执行断言单元：给定被测 kernel 的一次调用（含输入张量、形状、stride、dtype、编译选项、启动配置），它能返回一个三值判定——通过、失败、或不可判定（unknown）。三值而非二值是关键：形式化 SMT 验证在超时或状态空间不可解时会返回 unknown，差分 oracle 在被参照实现本身也含未定义行为时同样应返回 unknown。把 unknown 折叠成 pass 是清单工程里最常见的系统性缺陷，它让验证器的漏检率从“可度量”退化为“不可见”。

一条条目在结构上由五元组定义：(被测对象, 输入域, 判定谓词, 容差/预算, 判定语义)。被测对象可以是单个 kernel、一个融合算子、或一条 CuTe 布局变换；输入域是条目所覆盖的输入集合的声明（注意是声明，不是枚举——枚举属于采样策略，见后文随机与边界输入条目）；判定谓词是把输出映射到 {pass, fail, unknown} 的函数；容差/预算包括数值容差、超时、显存上限、编译时间上限；判定语义说明该条目在什么条件下“不适用”（not applicable），例如 NaN 处理条目对纯整数 kernel 不适用。缺任何一元，条目就无法被自动化编排，也就无法进入多轮 RL 的可验证奖励回路——因为奖励函数需要一个确定的、可复现的标量信号，而五元组正是把信号从“人读的结论”变成“机器读的标量”的最小契约。

代价在这里第一次显现：每条条目都要付出执行时延与token 成本。一次差分 oracle 比对需要跑两份实现，时延约等于被测 kernel 时延加上参照实现时延（参照实现常是 PyTorch eager 或朴素 CUDA，往往慢一个数量级）；而把失败结果回灌给 agent 作为执行反馈时，报错文本、张量摘要、最大误差位置都要序列化进上下文，单条失败反馈轻易占用数百到上千 token。清单越长，单轮验证的 token 预算越紧张，这正是后续部分要讨论的编排与裁剪问题的物理根源。

具体例子：对一条“形状与 stride 覆盖”条目，被测对象是一个 Triton 的 softmax kernel，输入域声明为“任意 2–4 维、最后一维长度 1 到 65536、允许非连续 stride”，判定谓词是“与参照实现逐元素比对，绝对误差 ≤ 1e-5 且相对误差 ≤ 1e-4”，预算为单次调用 50 ms 超时，判定语义为“dtype 为整数时不适用”。这条条目可以被自动生成输入、自动执行、自动产出标量奖励，而“检查一下 softmax 对不对”不能。

二 · 分类维度一：判定依据的来源——参照、规范、还是证明

最本质的分类维度是判定依据从何而来，它决定了漏检风险的性质。三类来源对应三类条目：参照型（差分 oracle、确定性复跑）、规范型（数值容差比对、NaN/Inf 处理、形状与 stride 覆盖）、证明型（形式化 SMT 验证）。

参照型的判定谓词写作 |f(x) − g(x)| ≤ τ，其中 g 是参照实现。它的漏检风险是相关性漏检：若被测 kernel 与参照实现共享同一处误解（例如都把某个归约的累加顺序写反，或都用了同一个有缺陷的库函数），两者会一致地错，差分比对通过而真实语义已偏。这类漏检无法通过增加采样点消除，只能通过引入独立来源的参照（不同算法路径、不同精度路径、CPU 参考实现）来稀释。代价是参照实现本身的时延与显存占用——CPU 参考实现对大张量往往不可行，只能在小形状上做，于是覆盖度与成本直接对冲。

规范型的判定谓词不依赖第二份实现，而依赖数学性质：容差条目依赖“浮点结果应在某个误差界内”，NaN/Inf 条目依赖 IEEE 754 的传播规则，形状与 stride 条目依赖“输出张量的 shape/stride 必须与语义定义一致”。规范型的漏检风险是规范本身写错——容差 τ 定得过松会放过真实 bug，定得过紧会把合法的浮点重排判为失败（false positive），后者在 RL 回路里尤其有害，因为它给 agent 灌入错误的负奖励，诱导它放弃正确的优化方向（例如放弃使用更快的 reduction 树形结构，只因为累加顺序变了导致末位差异）。

证明型的判定谓词是“存在性命题的否证”：把 kernel 的语义写成 SMT 公式，询问“是否存在输入使输出偏离规范”，若求解器返回 unsat 则通过，返回 sat 则给出反例，超时则 unknown。它的漏检风险来自建模保真度：SMT 模型必须精确刻画浮点语义（位级）、内存别名、线程交织，任何一处抽象过度都会让 unsat 变成假通过。代价是编译与求解时间——位级浮点建模会让求解器状态空间爆炸，实际只能覆盖很小的形状与很短的循环展开，因此证明型条目天然是“小形状全覆盖 + 大形状不适用”，与参照型正好互补。

来源判定谓词形态主要漏检风险主要代价
参照型|f(x)−g(x)| ≤ τ相关性漏检（共模错误）参照实现时延/显存，反馈 token
规范型性质断言（误差界、IEEE 规则、shape/stride 等式）规范过松/过紧，false positive 污染奖励容差调参的编译/重跑时间
证明型unsat / sat+反例 / unknown建模抽象过度导致假通过求解时间，仅小形状可行

具体例子：一个 CuTe 布局变换 kernel，参照型条目用 PyTorch 的 permute+contiguous 做参照，规范型条目直接断言“输出 stride 满足 stride[i] = prod(shape[i+1:])”，证明型条目对小至 4×4 的 tile 做位级 SMT 建模。三者对同一个 bug 的敏感度完全不同：若 bug 只在非连续输入下触发，规范型条目（直接检查 stride 等式）能抓到，参照型条目若参照实现内部先做了 contiguous 归一化则会漏掉。

三 · 分类维度二：输入域的构造方式——采样、枚举与符号

第二个维度是输入域如何被实例化，它决定条目的覆盖度与运行成本。三种方式：随机采样、边界枚举、符号化。

随机采样条目从声明的输入域中按分布抽取实例，判定谓词逐实例执行。它的核心机制是分布设计：均匀分布几乎必然错过稀疏的边界区域，因此工程上常用对数均匀（覆盖 1 到 65536 的维度长度）、混合分布（大部分实例落在常规区，少量注入极端值）、以及基于失败反馈的定向重采样——把上一轮失败的输入做扰动后重新注入，这在多轮 RL 中等价于一种无梯度的对抗搜索。代价是方差：通过率是随机变量，条目报告的“通过”只是样本通过，采样数 n 与真实漏检率 p 的关系满足漏检概率 ≈ (1−p)^n，要让漏检率降到 1% 以下而真实缺陷密度为 1e-3，需要数千次实例化，每次实例化的时延乘以 n 就是条目成本。

$$\Pr[\text{漏检}] = (1-p)^{n}, \quad n \approx \frac{\ln(1/\delta)}{\ln(1/(1-p))}$$

边界枚举条目不做抽样，而是显式列出结构性临界点：维度为 1、维度为 warp 大小的整数倍与整数倍减一、stride 为 0（广播）、stride 为负（翻转视图）、长度恰为 tile 边界、长度跨越 tile 边界一元素。它的机制是“把已知的 off-by-one 与对齐陷阱变成确定性命中”，代价是枚举表随维度组合爆炸——4 维张量每维 5 个边界值就是 625 个组合，再乘以 dtype 与 stride 模式，条目运行时间线性膨胀。因此边界枚举条目通常与随机条目分层组合：边界枚举保证“已知陷阱必被踩到”，随机采样保证“未知陷阱有概率被踩到”。

符号化条目把输入表示为符号变量，交给 SMT 求解器搜索反例，其输入域是“全部满足约束的输入”而非实例。它的覆盖度在理论上最高（对小形状是完备的），但如前所述受建模保真度与求解时间双重限制。工程判断：符号化条目应只用于索引计算、边界判定、布局映射这类离散逻辑密集的 kernel 片段，而不用于含大量浮点乘加的数值主体——后者交给参照型条目。

具体例子：一个带 masking 的 attention kernel，随机条目按对数均匀抽序列长度；边界枚举条目显式列出序列长度为 1、为 head_dim 的整数倍、为整数倍减一、以及 query 位置恰在 mask 边界的组合；符号化条目只对“给定 block 索引与线程索引，输出位置是否越界”这一离散谓词建模。三者叠加后，覆盖度来自不同机制，而不是靠把随机条目的 n 调大——后者只是线性加成本，前者是结构性补盲。

四 · 分类维度三：判定语义的严格度——精确、容差、性质

第三个维度是判定谓词有多严，它直接决定 false positive 率与 false negative 率的权衡。三档：位级精确、数值容差、性质断言。

位级精确条目要求输出与参照逐位相同，适用于整数运算、索引计算、布局变换、以及确定性复跑条目（同一输入两次运行结果必须位级一致）。它的机制简单、判定无歧义，代价是它对合法的浮点重排零容忍——任何改变累加顺序的优化（树形归约、split-K、warp shuffle 归约）都会改变末位，从而被判失败。因此位级精确条目只能用于语义上不允许重排的算子，或用于确定性复跑这种“自己与自己比”的场景。

数值容差条目把谓词放宽为|f(x)−g(x)| ≤ atol + rtol·|g(x)|，这是绝大多数浮点 kernel 的默认档。它的机制核心是容差标定：容差必须与 kernel 的数值条件数、累加长度、dtype 精度相匹配，而不是全局一个常数。对长度 65536 的 fp32 归约，最坏情况误差随累加长度增长，固定 1e-5 的 atol 会把正确实现判错；反之对长度 8 的点积，1e-2 的容差会放过真实 bug。代价是标定本身需要实验：容差调松降低 false positive 但抬高 false negative，调紧反之，而这个权衡点随形状变化，于是容差条目实际上是一个以形状为参数的容差函数，而非一个标量。

性质断言条目不比对具体数值，而断言结构性性质：输出满足概率单纯形（非负且和为 1）、输出单调、输出在给定 mask 下为零、输出 stride 满足布局等式、NaN/Inf 按 IEEE 规则传播（输入含 NaN 则输出对应位置必为 NaN，输入含 Inf 则按运算规则传播而非静默变成有限值）。它的机制是“用不变量替代参照”，优点是对合法重排免疫、无需第二份实现、时延低；缺点是性质本身可能不完备——一个把 softmax 输出全部置为 1/n 的 kernel 满足“非负且和为 1”，却完全错误。因此性质断言条目的漏检风险是性质不完备，必须与至少一条参照型条目配对使用。

严格度典型条目false positive 来源false negative 来源
位级精确确定性复跑、整数/索引 kernel合法浮点重排几乎无（除参照本身错）
数值容差数值容差比对、差分 oracle容差过紧、条件数大的形状容差过松、共模错误

具体例子：一个 LayerNorm kernel，位级精确条目在 fp32 下几乎必然失败（因为均值/方差的归约顺序与参照不同）；容差条目需要按隐藏维度长度设定 rtol，隐藏维度 8192 时容差必须放宽；性质断言条目检查“输出均值接近 0、方差接近 1、且对含 NaN 的输入输出必含 NaN”。三条条目各自抓不同的 bug：容差条目抓数值偏差，性质条目抓 NaN 静默吞噬（一个用 max(x, 0) 做保护的实现会把 NaN 变成 0，容差条目在无 NaN 输入时完全看不到）。

五 · 与相邻概念的区别：验证器、基准、profiler、oracle 不是同义词

清单条目最容易被混淆的相邻概念有四个，区分它们是为了避免把不同层次的信号混进同一个奖励函数。

与基准（benchmark）的区别：基准度量性能（时延、吞吐、SOL 占比），验证器度量语义正确性。一个 kernel 可以在 KernelBench 系基准上跑出高 SOL 却是错的——基准只保证“跑完了、计时了”，不保证“算对了”。工程上二者必须串联：先过验证器再进基准，否则性能数字毫无意义。代价上，验证器消耗的是执行时延与 token，基准消耗的是重复计时与 warmup 的 GPU 时间，两者预算不能互相挪用。

与 NCU/SASS profile 的区别：profiler 回答“这个 kernel 在硬件上发生了什么”（访存模式、occupancy、指令混合），验证器回答“结果对不对”。profiler 无法判定正确性——一个 bank conflict 严重的 kernel 可以完全正确，一个访存完美的 kernel 可以完全错误。反过来，验证器也无法解释性能瓶颈。二者的交集在于失败归因：当验证器报 fail 时，profiler 数据可以帮助定位是数值路径还是索引路径出错，但 profiler 本身不是判定依据。

与 oracle 的区别：oracle 是判定依据的提供者，验证器条目是使用该依据的断言。差分 oracle 是一种 oracle（参照实现），而“差分 oracle 条目”是把该 oracle 包装成五元组、加上输入域与容差预算后的可执行单元。形式化 SMT 验证提供的 oracle 是求解器的 unsat 结论，NaN/Inf 条目提供的 oracle 是 IEEE 754 规范。混淆二者会导致清单写成“我们有 oracle 了”却无法自动化——因为没有输入域与判定语义，oracle 只是一个函数，不是一个条目。

与防作弊检查的区别：防作弊检查针对的是agent 行为（是否读取了参照输出、是否硬编码了测试用例、是否在检测到验证环境时切换路径），验证器条目针对的是kernel 语义。二者正交但互相依赖：一个被 agent 硬编码了测试输入的 kernel 可以通过所有验证器条目，此时只有防作弊检查能抓住它；反之一个诚实但写错的 kernel 会被验证器抓住而防作弊检查无感。工程判断：验证器条目的判定结果必须与防作弊检查的结论分开记录，否则“通过验证”会被误读为“可信”。

具体例子：agent 生成的 Triton kernel 在基准上达到高 SOL，验证器容差条目通过，但确定性复跑条目失败（两次运行结果不同，说明用了非确定性的原子累加）。这不是性能问题也不是语义错误，而是可复现性缺陷——它会让下游的差分 oracle 条目产生抖动，进而让 RL 奖励信号带噪。此时正确的动作是把它记为确定性条目的 fail，而不是让基准的高 SOL 掩盖它。

六 · 条目的组合语义：清单是一个偏序，不是一个集合

把条目当成无序集合是分类工作里最后一个陷阱。实际上条目之间存在依赖偏序：形状与 stride 覆盖条目是几乎所有其他条目的前置——如果 kernel 在某个 stride 模式下直接越界崩溃，后续的容差比对根本无从执行；NaN/Inf 处理条目是数值容差条目的前置过滤——含 NaN 的输入进入容差比对会产生 NaN 误差，比较结果为 false，从而把“NaN 传播正确”误判为“数值错误”；确定性复跑条目是差分 oracle 条目的可信度前提——被测 kernel 若本身不确定，差分比对的误差分布不可解释。

这个偏序的工程含义是：清单的执行顺序与短路策略决定了单轮验证的成本。若按偏序拓扑序执行并在首个 fail 处短路，则大多数错误 kernel 会在廉价的前置条目（形状/stride 检查、NaN 检查，时延低、无需参照实现）处被拦下，昂贵的差分 oracle 与 SMT 求解只在通过前置后才启动。这把平均验证时延从“所有条目之和”降到“前置条目之和加上少量昂贵条目”，代价是诊断信息变少——短路只报告第一个失败，agent 拿不到后续条目的反馈，可能反复在同一处犯错。折中方案是分层短路：前置层短路，数值层不短路但按预算截断，证明层仅在数值层全通过后运行。

$$\text{单轮成本} \approx \sum_{e \in \text{前置}} c_e + \mathbb{1}[\text{前置全过}] \cdot \sum_{e \in \text{昂贵}} c_e$$

具体例子：一个 CuTe 的 tiled copy kernel，前置层包含形状/stride 覆盖与 NaN 检查（均为纯 CPU 侧断言或极短 GPU 调用），数值层包含容差比对与差分 oracle（需要参照实现），证明层包含对小 tile 的 SMT 建模。若 agent 第一版把 stride 计算写错，前置层在毫秒级拦下并返回具体的 stride 等式违例；若 stride 正确但累加精度不足，数值层报出最大相对误差位置；只有当两层都通过，才付出 SMT 求解的编译与求解时间。这个顺序不是审美选择，而是由每条条目的时延与 token 成本决定的工程判断——把最贵的条目放在偏序末端，是清单能被多轮 RL 反复调用而不撑爆预算的唯一可行结构。
