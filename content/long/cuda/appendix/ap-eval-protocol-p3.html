一 · 阈值从哪来：从规格反推，而不是拍脑袋

工程阈值的合法来源只有三条：硬件规格反推、测量噪声反推、以及业务收益反推。任何写进评测脚本的常数都必须能追溯到其中一条，否则它就是不可审计的魔法数字。以带宽类阈值为例，一个 kernel 的实测有效带宽必须与 roofline 上界比较，而不是与“某个常见值”比较。上界由规格决定：

$$B_{\text{eff}} = \frac{\text{BytesMoved}}{\text{KernelTime}},\qquad \text{SOL}_{\text{bw}} = \frac{B_{\text{eff}}}{B_{\text{peak}}\cdot \eta_{\text{reach}}}$$

其中 η_reach 是可达成系数，它不是硬件常数，而是同一张卡上由厂商库或手写最优 kernel 实测出的经验上限。工程做法是：在隔离机器上先跑一组“参照 kernel”（纯拷贝、纯 reduce、纯 GEMM），把它们的 SOL 记录下来作为该机器的标尺，再把待测 kernel 的 SOL 与之比较。这样阈值随机器漂移而自动校准，而不是把某个固定百分比写死。代价是每次换机器要重跑参照集，参照集本身耗时在秒级到十秒级，相对于整轮评测可忽略；但若参照 kernel 编译时间被计入，会污染计时，因此参照集必须预编译并缓存二进制。

正确性阈值的来源则是数值分析而非经验。对 fp32 累加，相对误差上界随累加长度增长，典型形式为 ε·√n（随机舍入假设）或 ε·n（最坏情况），其中 ε 是机器 epsilon。工程上取 k·ε·√n 作为容差，k 取 2–8 之间的小整数，并在评测脚本中把 n、ε、k 三个量显式打印进日志，否则事后无法判断一次失败是 kernel 错还是容差定错。对 fp16/bf16 的混合精度 kernel，容差必须按输出 dtype 而非输入 dtype 定，因为舍入发生在写回阶段。代价是容差放宽会漏掉真实 bug：一个把 reduce 顺序写反的 kernel 在宽松容差下可能通过，因此容差必须与“参照实现 + 高精度累加”的差分测试配合使用，而不是单独作为唯一 oracle。

二 · 计时方法：把噪声压到阈值以下

计时噪声决定了阈值能定多紧。GPU kernel 计时的最小可信粒度受三个因素支配：启动开销（微秒级）、时钟抖动（受功耗与温度影响）、以及事件记录精度。工程上不用单次计时，而用“预热 + 多次重复 + 取分位数”的组合。伪代码思路：

  • 预热 W 次（W 取到让 L2 状态与时钟稳定，通常数十次），丢弃全部预热样本；
  • 连续记录 R 次单次耗时，R 取到使中位数的标准误小于目标分辨率的若干分之一；
  • 上报中位数与 p90，同时上报 R 与离散度（如 IQR/中位数），离散度超过设定比例则判定该次测量无效并重测；
  • 用 CUDA event 包裹 kernel 而非包裹整个 host 调用，避免把 Python/框架开销算进 kernel 时间。

代价在于评测总时延：R 与 W 的乘积直接乘以单次 kernel 时间。对毫秒级 kernel，R 取百次量级即可；对微秒级小 kernel，启动开销占比高，必须用“批量提交 + 单次同步”的方式摊薄，否则测到的是启动开销而非 kernel。这里有一个必须写进协议的判断：当 kernel 时间与启动开销同量级时，报“端到端吞吐”而不是“单 kernel 时延”，并明确说明吞吐是在多大批次下测得的。另一个代价是显存：重复计时期间若每轮都分配输出缓冲，分配器抖动会进入计时；协议要求缓冲区在计时循环外一次性分配并复用。

具体例子：一个 elementwise 加法的 kernel，单次耗时在微秒量级，若用逐次同步的方式测，测得值会被 host 侧同步开销主导，导致 SOL 被严重低估，进而让一个本已接近带宽上限的 kernel 被判为“未达标”。正确做法是把 N 次调用背靠背提交，只在首尾各放一个 event，用总时间除以 N，并同时报告 N 与总时间，使审计者能复算。

三 · 硬件隔离与漂移：阈值必须带机器指纹

同一份阈值在不同机器上不可比，因此协议要求每条评测记录携带机器指纹：GPU 型号、驱动版本、时钟策略（是否锁频）、以及同机参照 kernel 的 SOL。锁频是压噪声最有效的手段，代价是吞吐下降且不能反映真实部署形态；因此协议区分两种模式——“诊断模式”（锁频、独占、关闭其他进程）用于判定正确性与算法优劣，“部署模式”（不锁频、共享）用于收益评估。两种模式的阈值不同，且必须在结果中标注模式，禁止跨模式比较。

漂移的检测机制是插入“哨兵测量”：在评测序列的首、中、尾各跑一次同一参照 kernel，若三次结果的离散度超过设定比例，则整批结果标记为受污染并作废。代价是每批多出若干次参照运行的时间，以及可能的整批重跑；但相比把热降频导致的性能下滑误判为 kernel 退化，这个代价是必要的。另一个隐性代价是显存隔离：若同机有其他进程占用显存，分配器行为改变会间接影响 kernel 的占用率与性能，因此协议要求记录评测开始与结束时的显存占用快照，作为隔离是否成立的证据。

具体例子：一个 reduce kernel 在锁频诊断模式下 SOL 稳定，但在部署模式下因同机推理进程抢占 SM 而出现长尾，p90 显著劣于中位数。若协议只看中位数，会得出“该 kernel 可用于生产”的结论；而带上 p90 与哨兵离散度后，结论变为“该 kernel 在共享环境下不具备稳定收益”，这正是阈值需要分位数而非单点值的原因。

四 · 输入分布与随机种子：阈值的前提条件

性能阈值对输入分布敏感：稀疏度、数值范围、对齐方式都会改变分支走向与访存模式。协议因此要求把输入分布写成可复现的生成器规格，而不是“随机张量”。规格至少包含：形状集合（含非对齐形状）、dtype、数值分布（均匀/正态/含极值）、稀疏模式、以及生成所用的随机种子。种子必须与结果一同上报，使审计者能逐位复现输入。代价是评测规模膨胀：形状集合每增加一维组合，评测次数线性增长，总时延随之上升；因此协议要求区分“主形状”（必测、全量计时）与“边界形状”（只测正确性、不做性能判定），把性能阈值限定在主形状上。

正确性阈值同样依赖输入。含极值的输入会放大累加误差，若只用均匀分布测容差，会系统性低估最坏误差。工程做法是在正确性测试集中显式加入“病态输入”（大动态范围、接近溢出的中间值），并对其单独设定更宽的容差，同时在日志中标注该组使用了放宽容差，防止审计者误以为所有组同标准。代价是病态输入可能触发参照实现自身的数值问题，因此参照实现必须用高精度累加（如 fp64 或 Kahan 补偿），其自身开销不计入被测 kernel 的计时。

具体例子：一个 softmax kernel 在均匀分布输入下误差远小于容差，但在含大幅值差的输入下出现指数溢出路径，误差跳变。若协议未规定病态输入组，该 bug 在评测中不可见；而一旦加入该组，容差判定会立刻失败，且失败可归因到具体的输入规格行，而不是笼统的“精度不达标”。

五 · 编译时间与 token 成本：被低估的阈值维度

生成式 kernel 的评测不能只测运行时间。编译时间与生成 token 数是两个必须进入阈值的维度，因为它们直接决定 agent 循环的可行性与成本。编译时间阈值的作用是筛掉“能跑但编译极慢”的候选：模板展开、CuTe 布局推导、PTX 内联汇编的复杂度都会把编译时间推到分钟级，而多轮 RL 中每次采样都要编译，编译时间乘以轮数就是墙钟成本。协议要求记录单次编译的墙钟时间，并对超过设定上限的候选直接判负，而不是等它跑完再评估。代价是可能误杀“编译慢但运行快”的 kernel，因此上限应按“编译时间 / 预期运行时间”的比值设定，而非绝对秒数。

token 成本阈值用于约束生成侧：一个 kernel 的源码长度与生成它消耗的 token 数决定了单次采样的成本。协议要求上报源码行数、token 数、以及“首次通过率”与“多轮修复后通过率”的对比。若一个候选需要多轮修复才通过，其累计 token 成本远高于一次通过者，即使最终性能相同，工程判断也应偏向一次通过者。代价是统计口径：token 计数依赖分词器版本，必须与机器指纹一同记录，否则跨版本不可比。

具体例子：两个候选运行时间相同，一个源码短、一次编译通过，另一个依赖大量模板、编译耗时显著更长且需两轮修复。若协议只按运行时间排序，二者并列；加入编译时间与 token 成本后，前者在“单位成本收益”上明确占优。这正是阈值维度必须多于一个的原因——单维排序会把工程上不可接受的候选排到前面。

六 · 没有数字时怎么测：可复现的测量规程

当某个维度缺少现成经验数字时，协议不允许留空或写“视情况而定”，而要求写出一段可执行的测量规程，使任何审计者能在自己的机器上复现出该数字。规程的最小结构是：被测对象、测量装置、控制变量、上报字段、以及判定规则。以“编译时间”为例，规程应规定：在同一容器镜像内、冷缓存条件下、以固定并发度执行编译命令，记录从进程启动到产物可加载的墙钟时间，重复若干次取中位数，并上报镜像摘要与并发度。这样即使没有先验数字，也能在任意机器上生成可比数据。

规程还必须规定“测量失败”的处理：若某维度无法稳定测量（离散度过大），协议要求上报该事实并标记该维度为“不可判定”，而不是用单次样本填充。代价是评测报告出现空缺字段，但这比填入不可信数字更符合审计要求。判定规则要写成可执行的条件，例如“若离散度超过设定比例，则重测；重测仍超限，则标记不可判定并附原始日志”。

具体例子：某新架构上尚无参照 kernel 的 SOL 经验值。按规程，先在该机器上跑一组纯拷贝与纯 reduce 作为参照，记录其 SOL 与离散度，把参照结果作为该机器的标尺写入评测记录，再以标尺为分母计算待测 kernel 的 SOL。整个过程不依赖任何外部数字，产出的是“本机标尺 + 相对值”，且原始日志留存可审计。这条规程的价值在于：它把“没有数字”转化为“有测量方法”，使阈值体系在未知硬件上仍然闭合，而不是退化为不可比较的定性描述。

阈值不是拍脑袋：从测量口径反推工程数字

工程阈值的合法性来自测量口径，而不是来自社区口口相传的“经验值”。同一 kernel 在 warmup 次数、L2 是否被前一次调用污染、是否开启持久化 clock、是否绑定 NUMA 节点这四种组合下，测得的时延可以相差一个量级，因此任何阈值都必须连同“怎么测”一起登记。建议把阈值写成三元组：判据、测量协议、失效动作。例如正确性判据取 max_abs_err ≤ atol + rtol·|ref|，测量协议固定为“同一随机种子下连续 N 次调用取中位数、丢弃首次调用、计时区间只包住 kernel launch 到 stream 同步”，失效动作是“标记为不可信而非直接判错”。这条三元组要随原始日志一起留存，审计时能复现出同一个数字，否则阈值只是噪声。

$$\text{score} = \frac{t_{\text{ref}}}{t_{\text{cand}}},\quad t = \operatorname{median}\{t_i\}_{i=2}^{N},\ \text{warmup}=1$$

边界条件比阈值本身更值得写清。加速比判据在 t_ref 本身接近 launch 开销时失效：当参考实现是逐元素小 kernel，候选实现即使算法更优也无法体现，此时应改用带宽利用率或 SOL 占比作为主判据，把时延比降为辅助信号。容差判据在归约类算子上失效：浮点求和顺序改变会放大误差，固定 atol 会让合法实现被判错，应改为按输出量级缩放的相对误差并配合 Kahan 参考实现。系统代价同样要计入：为压低方差而把 warmup 拉到数十次，会让单次评测的 GPU 占用时间成倍上升；为隔离硬件而独占整卡，会让吞吐型评测的排队时延成为瓶颈；加密锁频换取可复现性，则牺牲了真实 Boost 行为下的性能画像。

判据测量口径失效条件代价
时延比中位数、单 stream 同步参考实现受 launch 开销支配warmup 拉长评测墙钟
数值容差固定种子、缩放相对误差归约顺序敏感算子需维护高精度参考实现
带宽/SOLNCU 单次采集、锁频算子受延迟而非带宽限制profile 采集拖慢吞吐

没有可信数字时，正确做法是把“怎么测”写成可执行协议而不是留空：声明输入分布的形状族与边界形状、声明种子派生规则（如 seed = hash(task_id, trial)）、声明硬件隔离粒度（整卡独占还是 MIG 切片）、声明结果上报字段（中位数、四分位距、最小最大值、失败样本计数）。评测脚本与训练侧必须物理隔离，训练进程不得读取评测侧的阈值文件或历史日志，否则阈值会被间接拟合进策略。原始日志按 trial 落盘并带哈希，任何一次阈值调整都要留下变更记录——阈值漂移本身就是评测可信度下降的信号。
