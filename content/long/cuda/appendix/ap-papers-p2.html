一 · 速查表的字段骨架与取值口径

速查表的第一性问题不是“列哪些论文”，而是“一行要能承载哪些决策信息”。本表固定六个字段：线（基准 / 脚手架 / RL / 形式验证 / profile 驱动）、标识（论文短名或仓库名）、贡献点（一句话，动词开头）、可复现性状态（三档枚举）、依赖面（跑通它需要的最小外部条件）、读它的目的（你要从它身上拿走什么）。字段少而硬，是为了让读者在三十秒内判断“这一行是否值得深读”。

可复现性状态采用三档枚举，禁止模糊表述：A 表示仓库含可执行脚本与固定输入、结果可在无私有数据条件下重跑；B 表示代码开放但缺关键配置（数据切分、超参、硬件约束）或仅覆盖部分实验；C 表示仅论文描述、无公开实现或实现与论文口径不一致。这个三档不是质量评级，而是“你能否把它当作对照基线”的判据——C 档条目只能用于读机制，不能用于复现对比。

依赖面字段要写“最小可跑条件”，而不是“推荐配置”。例如一条 profile 驱动优化的条目，其依赖面应写成“单卡 + NCU 可用 + 一个可编译的 baseline kernel”，而不是罗列集群规模。这样做的代价是字段信息量被压缩，读者需要自己补全扩展条件；收益是避免把硬件参数堆砌成伪精确的准入线。

$$\text{可复现性} = f(\text{脚本完备度},\ \text{输入固定度},\ \text{硬件可达度})$$

具体例子：某条 RL 训练线条目，贡献点写“以执行反馈构造可验证奖励并做多轮采样”，可复现性标 B，依赖面写“单卡推理 + 一个正确性 oracle + 固定题集”，读它的目的写“拿走奖励构造的判据设计”。四字段合起来，读者立刻知道它不能直接当基线，但奖励设计可迁移。

二 · 阈值：什么条件下一条目进入“必读”与“可跳过”

速查表若只列条目而无阈值，等于把筛选成本转嫁给读者。本表为每行附一个入表阈值与一个降级阈值。入表阈值回答“它凭什么占一行”：要么提出了新的可验证性机制（如把正确性判定从数值比对推进到区间/符号约束），要么给出了可复用的执行反馈信号定义，要么把某一类 kernel 的优化路径讲到了可迁移的粒度。降级阈值回答“什么情况下可以不读”：贡献点与已有条目重复且可复现性更低、或依赖面超出你当前工具链一个数量级。

阈值必须可判定，不能写成“重要”“经典”。可判定的写法是绑定到具体机制：例如“该条目是否定义了独立于参考实现的正确性判据”是一个二元问题；“该条目是否报告了端到端收益而非仅 kernel 级加速”也是二元问题。用二元判据堆出阈值，代价是丢失细腻度，收益是两个人对同一行会给出同样的取舍。

判据入表（必读）降级（可跳过）
正确性机制给出独立于参考实现的判据仅数值 allclose 比对
反馈信号定义可自动提取的执行反馈仅人工评分
优化粒度路径可迁移到其他 kernel单例调参记录
可复现性A 或 B 且依赖面匹配C 档且无脚本

具体例子：一条形式验证线条目若只报告“在某 kernel 上验证通过”，而降级判据问的是“验证条件是否覆盖了边界形状与非法输入”，则该条目落在降级侧——它证明了一个点，没有给出可复用的约束模板。反之，若它给出了从 kernel 语义到约束的翻译规则，即便只在单例上跑通，也进入必读侧。

三 · 口径：跨条目的可比性如何被保证

速查表最容易失效的地方是口径漂移：同一列“加速比”在不同条目里分别指 kernel 级、算子级、端到端，读者横向比较就得出错误结论。本表的处理是把口径写进字段值本身，而不是另设一列注释。写法是“指标名@层级@基线”，例如“时延@kernel@朴素实现”与“时延@端到端@框架默认”是两个不可混用的值。任何未标注层级的数字一律视为不可比，不进入速查表。

正确性口径同理。数值比对要标注容差来源（绝对、相对、ULP），否则不同条目之间的“通过”不可加总。形式验证条目要标注约束覆盖的是形状域还是数值域——这两者的验证强度差一个量级，混在一列里会让读者误以为覆盖度相同。代价是每个字段值变长、表格变密；收益是横向扫读时不会产生虚假的可比性。

$$\text{可比性} = \mathbb{1}[\text{层级一致}] \cdot \mathbb{1}[\text{基线一致}] \cdot \mathbb{1}[\text{容差口径一致}]$$

具体例子：两条 profile 驱动优化条目都写“提升明显”，一条的基线是未融合的多 kernel 串联，另一条是已融合的单 kernel。若不标注基线，读者会认为后者弱；标注后可见前者优化的是融合机会，后者优化的是访存模式，二者不可比但各自可迁移。速查表的价值正在于把“不可比”显式化，而不是制造一张看似整齐的排行榜。

四 · 五条线的字段差异与填表规则

五条线的字段骨架相同，但字段值的填法不同，这是速查表能“直接照着用”的前提。基准线条目的贡献点必须写明“测什么能力、用什么判据”，依赖面写“题集规模与 oracle 类型”；脚手架线条目写“agent 与工具链的接口形态”，依赖面写“编译/执行/反馈回路是否闭环”；RL 线条目写“奖励信号来源与采样轮次结构”，依赖面写“推理吞吐与 oracle 时延”；形式验证线条目写“约束语言与覆盖域”，依赖面写“求解器与规模上限”；profile 驱动线条目写“从指标到改动的映射规则”，依赖面写“NCU 可采集的指标集”。

填表规则的核心是“贡献点必须是机制而非结果”。写“在某 kernel 上取得加速”是结果，不可迁移；写“用寄存器分块把全局访存转为共享访存”是机制，可迁移。这条规则让速查表从论文清单变成设计模式索引。代价是每条贡献点需要读者自己提炼，编写成本高；收益是同一行可以被不同 kernel 复用。

  • 基准线：贡献点写判据与能力覆盖，不写排名。
  • 脚手架线：贡献点写接口与反馈闭环形态，不写通过率。
  • RL 线：贡献点写奖励构造与轮次结构，不写收敛曲线。
  • 形式验证线：贡献点写约束翻译规则与覆盖域，不写验证个数。
  • profile 线：贡献点写指标到改动的映射，不写加速倍数。

具体例子：一条脚手架线条目，贡献点写“把编译错误、运行时错误与数值偏差三类反馈统一为结构化信号回灌给生成器”，依赖面写“编译器 + 执行沙箱 + oracle”。读者拿走的是反馈分类法，而不是某个通过率数字——后者换个题集就失效，前者可以搬到自己 agent 的回路里。

五 · 使用流程：从速查表到深读决策

速查表的使用不是“读一遍”，而是一个三步筛选流程。第一步按线定位：你的当前问题是正确性不可信、优化无方向、还是评测口径混乱，分别对应形式验证线、profile 驱动线、基准线。第二步按可复现性状态过滤：要做对照基线只取 A 档，要读机制可取 B 档，C 档仅作背景。第三步按依赖面匹配：若条目的最小可跑条件超出你当前工具链一个量级，标记为“暂存”而非“跳过”，因为工具链会演进。

这个流程的代价是每次使用都要重新走一遍三步，不能一次性背下来；收益是避免把速查表当成静态书单。工程判断在于：速查表的价值随你的工具链状态变化，同一行在不同阶段应给出不同取舍。因此表本身不设“推荐度”列——推荐度是读者状态与条目依赖面的函数，写死在表里必然过期。

$$\text{取舍} = g(\text{当前问题线},\ \text{工具链可达度},\ \text{可复现性档位})$$

具体例子：你正在搭一个多轮 RL 回路，第一步定位到 RL 线，第二步只取 A/B 档，第三步发现某条目的依赖面要求“低时延 oracle”，而你的 oracle 是离线批处理——该条目暂存，转而读另一条把奖励构造与 oracle 时延解耦的条目。三步走完，深读对象从十几条收敛到两三条，且每条都有明确的“拿走什么”。

六 · 维护规则：条目增删与口径变更的触发条件

速查表若不定维护规则，半年后就会混入不可比的值。触发增删的条件写死为三类：新条目出现时，必须同时满足入表阈值且可复现性不低于同线中位数，否则只进附录不进正表；已有条目可复现性降档时（仓库失效、脚本失配），状态字段立即改为 C 并保留一行说明，不删除——删除会丢失“曾经可复现”的信息；口径变更时（例如某线社区统一了加速比层级），整列重写而非逐行打补丁，因为混用新旧口径比全旧口径更危险。

维护的代价是每次变更都要重扫全表，不能增量修改；收益是表内始终只含同一口径的值。工程判断在于：速查表的可信度来自“拒绝收录”而非“收录得多”。一条依赖面写得含糊、可复现性无法判定的条目，收进来会污染整列的可比性，其代价远大于漏掉它的收益。

具体例子：某 profile 驱动线条目原标 B，其仓库后来删除了 NCU 采集脚本，仅剩 kernel 源码。按规则状态改 C、保留说明“采集脚本缺失，指标映射规则仍可读”。读者据此知道机制可读、基线不可复现，不会误把它当对照。这条规则让速查表在条目老化时仍然可用，而不是变成一张需要整体废弃的过期清单。

速查表自身的失效边界：字段口径漂移、阈值不可移植与维护成本

速查表最容易失效的地方不在条目缺失，而在字段口径漂移。同一列“加速比”在 KernelBench 系基准里可能指相对 PyTorch eager 的端到端时延比，也可能指相对 torch.compile 的 kernel 级比值；同一列“正确性”可能是 allclose 容差、可能是随机输入抽样、也可能是形式验证通过的约束子集。若不在表头固化口径，跨条目横向比较就会把不同分母的数值并排放。工程做法是给每个字段加一个口径标签，形如 speedup@eager-e2e、correct@atol1e-2-rand5，并在表尾单列“口径变更记录”，任何一次口径调整都追加一行而不是原地改写，否则历史复现结果无法对齐。代价是表宽增加、维护者每次录入需多填两三个标签，但这是唯一能让速查表在多人协作下不退化的机制。

阈值不可移植是第二类失效。表中“通过”往往写成某个固定容差或某个固定加速下限，但同一 kernel 在 FP32 与 TF32、在不同 SM 架构、在不同输入形状分布下，误差与性能都会移动。把阈值当成常量抄进 agent 的奖励函数，等价于把评测分布钉死在一个点上。更稳的写法是把阈值表达为相对量：以参考实现的实测误差分布为基线，判定条件写成 err_candidate ≤ k · err_ref，其中 k 由任务方给定而非表里写死；性能侧同理，用 t_candidate ≤ t_ref / (1+δ) 表达，δ 是任务声明的收益门槛。这样速查表给出的是判定形式而非魔数，agent 换硬件、换精度时只需替换基线测量，不必改表。代价是每次评测多一次基线测量与一次分布估计，时延与 token 开销都上升，但换来的是阈值在跨设备复现时不至于整体失效。

第三类是系统代价被表掩盖。速查表按“基准、agent 脚手架、RL 训练、形式验证、profile 驱动优化”五条线并列，读者容易把五列当成同质信息，实际上它们的复现成本差一个量级以上：基准条目通常只需一次编译加一次运行；RL 训练条目要拉起 rollout 集群与奖励服务，单条复现的显存占用与 wall-clock 是基准条目的数十倍；形式验证条目要跑约束求解，编译时间与求解时间可能压过 kernel 本身的运行时间；profile 驱动条目要采集 NCU 指标与 SASS，采集本身会改变 kernel 时序。若表中不标注“复现代价档位”，读者会按基准条目的节奏去排 RL 条目的复现计划。建议在表中加一列粗粒度档位（如“单机分钟级 / 多机小时级 / 需专用采集环境”），并附一行说明：档位只描述复现所需资源形态，不描述论文质量。

最后一条边界是表与 agent 的接口。速查表若被 agent 直接读取作为检索上下文，字段名与口径标签必须机器可解析，否则 agent 会把“通过”当成布尔真值而忽略其条件。可行的接口约定是：每个条目输出一个结构化记录，含 metric、denominator、tolerance、repro_level 四个必填键，缺键即视为不可用于奖励计算。这条约定把速查表从人读文档变成可校验的数据契约，代价是录入工作量上升、旧条目需一次性补齐，收益是 agent 的多轮优化不会因口径歧义而奖励错误行为。
