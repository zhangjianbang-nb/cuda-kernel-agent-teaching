一 · 术语表条目的定义粒度：从“词条”到“可判定谓词”

术语表不是词典。词典给的是语义等价物，术语表给的是可判定的谓词——读到某个术语时，读者应当能据此判断“眼前这个对象是不是它”。因此本书每个条目都写成三元组：判定条件（什么算）、度量单位（怎么量）、常见误用（什么不算）。判定条件必须可操作，不能写成“一种用于加速的技术”这类同义反复。例如“kernel”条目的判定条件不是“跑在 GPU 上的函数”，而是“以 grid/block 两级并行映射到硬件执行单元、由同一份代码对多个数据元素施加同一算子、且其性能由访存与计算的重叠关系决定的一段设备端代码”。这三条同时成立才算，缺一条就要归到别的条目去。

把定义写成谓词，直接决定了术语表能否被 agent 消费。生成侧 agent 在检索术语时，实际做的是把候选 kernel 的特征向量与条目谓词做匹配；如果谓词是模糊的自然语言，匹配就只能靠嵌入相似度，误差不可控。写成谓词后，匹配退化为布尔判定，可审计、可回归测试。代价是条目维护成本：每新增一个术语，作者必须同时给出反例集，否则谓词无法被证伪。工程上这笔开销值得付，因为术语歧义在跨章引用时会以指数方式放大——同一个“正确性”在第 3 章指数值等价、在第 7 章指 bit-exact，读者会在两处得到互斥结论。

度量单位是第二个必须钉死的维度。术语表里凡涉及性能的条目，一律标注单位与口径：时延用微秒（μs）还是毫秒、带宽用 GB/s 还是 GiB/s、显存占用是峰值还是稳态、编译时间是冷启动还是增量。单位不统一时，跨条目比较会系统性偏移。一个具体例子：某条目写“该 kernel 延迟 0.4”，读者无法判断这是 0.4 ms 还是 0.4 μs，两者相差三个数量级，足以让 roofline 判定从“访存受限”翻转为“计算受限”。因此本书约定，所有时延条目默认 μs、所有带宽条目默认 GB/s 并显式注明是否含 ECC 开销，凡未标注者视为条目缺陷。

$$\text{entry} = \langle \text{predicate}(x),\ \text{unit},\ \text{anti-example set} \rangle,\quad \text{valid}(x) = \bigwedge_{i} p_i(x)$$

这个合取式的工程含义是：任一子谓词失败，条目即不适用，agent 应转向相邻条目而不是强行套用。误用的主要来源正是“部分匹配即套用”——只满足“跑在 GPU 上”就称其为 kernel，会把 host 端调度的 wrapper 也算进来，导致后续 profile 归因错位。

二 · 分类维度：按“被度量对象”而非按“技术栈”切分

术语表最容易犯的分类错误是按技术栈切：CUDA 条目、Triton 条目、PTX 条目。这种切法在检索时几乎无用，因为读者的问题从来不是“Triton 里叫什么”，而是“我要判断这个东西的吞吐是否达标”。本书采用的主维度是被度量对象，共四类：产物类（artifact）、过程类（process）、判据类（criterion）、代价类（cost）。产物类是静态存在物——kernel 源码、编译后的 cubin、生成的 Triton IR；过程类是动态行为——生成、编译、profile、回放；判据类是判定规则——正确性 oracle、SOL 达标线、防作弊检查；代价类是资源消耗——时延、带宽、显存、编译时间、token 数。

四类之间是引用关系而非包含关系：判据类条目引用产物类条目作为输入，代价类条目引用过程类条目作为测量上下文。这个结构让术语表可以被组织成有向图，agent 沿边检索时不会把“度量”和“被度量”混为一谈。典型混淆是把“SOL”当成产物——SOL 是判据，它的输入是实测时延与硬件峰值，输出是达标与否的布尔值加一个比值；把 SOL 写成“一种优化后的 kernel”会让下游的奖励函数设计出错，因为奖励应当作用于产物，而 SOL 只是给产物打分的尺子。

维度判定依据典型条目误用后果
产物类可静态检视、可版本化kernel 源码、cubin、IR把过程日志当产物存档
过程类有起止时间、可重放生成轮次、profile 采集把一次采样当稳态性能
判据类输出布尔或比值正确性 oracle、SOL 线判据被当作优化目标本身
代价类有单位、可累加时延、显存、token单位混用导致跨条目比较失真

次级维度是抽象层级：源码级、编译器 IR 级、机器码级、硬件计数器级。同一术语在不同层级有不同定义，术语表必须标注层级，否则跨层引用会失配。例如“占用率”在源码级指每 SM 的活跃 warp 数上限估算，在硬件计数器级指实测的 warp issue 比例，两者数值可以相差很大。一个具体例子：某 kernel 源码级估算占用率 75%，但 NCU 实测 issue 活跃度只有 40%，原因是长延迟访存导致 warp 频繁 stall；若术语表不标层级，读者会误以为估算错误，实际是两个不同量。

三 · 与相邻概念的边界：五组必须切开的分野

术语表的价值一半在定义，一半在划界。以下五组是本书反复出现、且在其他条目中不会被展开的边界判定，本部分只给判据，不复述它们各自的主题内容。

  • kernel 与 operator：operator 是数学语义单元（如 softmax），kernel 是其一种设备端实现。一个 operator 可对应多个 kernel（融合前/融合后），因此“kernel 数量”不是“operator 数量”的度量。判据：若一段代码可被替换为另一段实现而数学语义不变，它是 kernel；若替换会改变语义，它是 operator。
  • 正确性 oracle 与数值容差：oracle 是判定程序，容差是 oracle 的一个参数。把容差当成 oracle 会让“通过”失去意义——放宽容差总能通过。判据：oracle 必须独立于被测实现（不同算法路径或高精度参考），容差只是其阈值设定。
  • 执行反馈与 profile：执行反馈是“跑通了没有、结果对不对、耗时多少”的粗粒度信号，profile 是计数器级的细粒度归因。判据：反馈可在无特权环境下获得，profile 通常需要性能计数器权限。
  • 可验证奖励与损失函数：奖励是标量、由判据产生、用于策略更新；损失是训练目标的一部分。判据：奖励必须能被独立重算，损失不必。
  • roofline 与 SOL：roofline 是上界模型（给出可达性能的天花板曲线），SOL 是实测值与该上界的比值。判据：roofline 不含实测输入，SOL 必须含实测时延。

这五组边界的共同代价是判定成本：每次划界都要跑一次对照实验或做一次静态检查，单条成本不高，但术语表条目数上百时，全量回归的编译与采集时间会累积到小时级。工程判断是：只对高频引用条目做全量回归，低频条目用抽样加人工复核。一个具体例子：把“执行反馈”误当“profile”会让 agent 在多轮优化中把粗粒度时延波动当作计数器信号，进而做出错误的瓶颈归因，浪费的是一整轮生成预算（token 与编译时间双重开销）。

四 · 条目间的引用闭包与歧义检测

术语表不是扁平列表，条目之间有引用：判据类引用产物类，代价类引用过程类。把这些引用写成有向边后，可以计算引用闭包——读到某条目时，读者必须同时理解的条目集合。闭包过大会导致单条目的阅读成本失控，闭包过小则会出现悬空引用。本书的工程约束是：任一 entry 的直接出边不超过 5 条，闭包深度不超过 2 层；超出则拆条目或提升为独立小节。

$$\text{closure}(e) = \{e\} \cup \bigcup_{d \le 2} \text{reach}(e, d),\quad |\text{closure}(e)| \le 12$$

歧义检测利用同一批谓词做反向检查：若两个条目的谓词在某测试集上同时为真，说明边界重叠，必须补反例或合并。这个检查可以自动化——把条目谓词编译成断言，对一组已知样本（真实 kernel、wrapper、日志、判据脚本）跑一遍，输出冲突矩阵。代价是维护样本集：样本要覆盖各抽象层级，且随工具链演进需要更新，否则断言会随版本漂移而失效。一个具体例子：某样本是一个 Triton 生成的 kernel 与其手写 CUDA 版本，两者数学语义相同但产物类条目谓词都判真，这不是歧义而是正确的多实现；真正需要报警的是同一个样本同时被判为“产物”和“过程”，那说明谓词写错了。

引用闭包还决定了术语表的检索顺序。agent 在生成前检索术语时，应先取判据类（知道要满足什么），再取产物类（知道产出什么），最后取代价类（知道预算多少）。顺序颠倒会让 agent 先锁定实现再找判据，容易产生“先写后凑”的作弊路径。这条顺序规则本身也是条目，其度量单位是检索步数，误用是把顺序当成硬约束导致检索僵化。

五 · 条目版本化与跨章一致性

术语表随工具链演进而变：PTX ISA 版本、Triton 语义、NCU 计数器命名都会漂移。若条目不带版本，跨章引用会在不同时间点给出不同结论。本书的做法是给每个条目附适用域：工具链版本区间、硬件架构区间、抽象层级。适用域之外，条目降级为“参考”而非“判据”。这不是形式主义——生成侧 agent 若把过期条目当判据，会产出在目标架构上不可编译或性能反转的 kernel。

跨章一致性的检查手段是术语指纹：对每个条目抽取其谓词中的关键量（单位、层级、判据类型），组成一个短向量，跨章比对同名条目的指纹是否一致。不一致即报警。代价是每次修订要重算指纹并人工确认差异，单次成本以分钟计，但能拦住“同一术语在两章定义不同”这类最难排查的错误。一个具体例子：第 2 章把“编译时间”定义为冷启动全量编译，第 9 章定义为增量编译，指纹中的“冷/热”标记不同，报警后统一为冷启动并注明增量另立条目。

版本化还带来一个工程判断：术语表应当只增不改语义，只改适用域。语义变更意味着下游所有引用失效，代价是全书回归；适用域收窄只是降级，代价可控。因此当工具链行为变化时，优先新增条目而非改写旧条目，旧条目保留并标注失效区间。这条规则让术语表成为可追溯的账本，而不是一份随版本重写的文档。

最后落到具体机制上：本部分给出的三元组结构、四类维度、五组边界、闭包约束与指纹检查，共同构成术语表的可执行骨架——每一条都能被写成断言并对样本集运行。读者在后续部分读到具体条目时，应当先看它的谓词与单位，再看它的反例集，最后看它的适用域；三者齐备才算一条合格条目，缺一者按缺陷登记，而不是按“写得不够清楚”放过。

术语边界的判定：从“可测”到“可判”

术语表条目最容易失效的地方不在定义本身，而在“度量单位”与“判定主体”被悄悄换掉。以 roofline/SOL 为例，条目把 SOL 定义为“给定 kernel 在目标硬件上可达的性能上界”，度量单位是时间或吞吐；但工程中常把它误用成“优化目标值”，于是当实测达到 SOL 的某个比例时就被判为“已优化”。失效条件很具体：SOL 依赖访存层次、数据类型与并行度假设，一旦 kernel 的实际数据布局偏离该假设（如非合并访问、bank conflict 密集），SOL 上界本身就不再紧，此时“接近 SOL”既不能证明实现正确，也不能证明还有优化空间。系统代价在于每次重算 SOL 都要跑一次分析模型或 profiler 采样，属于离线成本，不进入在线时延，但会拉长 agent 的每轮反馈周期。

正确性 oracle 的条目则必须区分“判定强度”与“判定代价”。oracle 的度量单位是布尔通过率而非误差幅度，常见误用是把“与参考实现数值接近”当成 oracle，忽略了参考实现本身可能对特定形状不合法。设输入域为 D，oracle 判定为 O(x)=1 当且仅当输出满足逐元素容差与形状约束，则覆盖率可写为：

$$\mathrm{Cov}=\frac{|\{x\in D: O(x)=1\}|}{|D|}$$

覆盖率低意味着 oracle 只对窄形状有效，agent 会在未被覆盖的区域获得虚假的正奖励。代价是构造高覆盖 oracle 需要枚举边界形状与极端数值，编译与执行时间随用例数线性增长，且容差阈值过松会放过真实错误、过紧会误杀合法实现。

条目判定主体典型失效系统代价
roofline/SOL分析模型布局偏离假设离线重算，拉长反馈周期
正确性 oracle参考实现+容差覆盖窄、容差失配用例数线性增长

因此条目分类维度应落在“判定主体是谁”与“代价发生在哪一层”，而非按工具名罗列。可验证奖励的条目必须显式声明其奖励函数是否与 oracle 同源：若奖励直接取自 oracle 的布尔输出，则奖励信号与正确性判定共享同一失效面，agent 的搜索会集中在 oracle 覆盖的窄域内；若奖励来自 profiler 指标，则需声明采样噪声与测量抖动如何折算为奖励方差。跨章歧义的根源正是这三类条目共用“正确”“快”这类词却指向不同判定主体。
