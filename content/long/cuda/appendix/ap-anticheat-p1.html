一 · 条目定义：什么算一条“防作弊检查项”

在《防作弊检查清单》里，“条目”不是一句“别作弊”的口号，而是一个可执行的三元组：被禁止的行为模式、该行为的可观测证据、判定该证据是否成立的检验过程。三者缺一，条目就退化成道德倡议。工程上判断一条目是否合格，用一条硬标准：给定一个候选 kernel 产物（源码、编译产物、运行 trace、profile 数据），检验过程必须能在有限步骤内输出“命中 / 未命中 / 无法判定”三态之一，且“无法判定”必须附带缺失的证据类型。这条标准直接决定了清单的可自动化程度——只有三态可判定的条目才能进 CI，其余只能进人工复核队列。

把条目写成三元组，代价体现在检查时延上。静态扫描类条目（如硬编码输出检测）单次耗时在毫秒到秒级，可以每个提交都跑；差分测试类条目需要至少两次真实执行并比对输出，时延随 kernel 规模线性上升；而涉及 NCU/SASS profile 的条目要触发一次完整采集，单次开销足以让“每个 PR 都跑”变得不现实。因此条目定义里必须显式标注检查成本档位，这是分类维度的第一根轴，后文展开。

一个具体例子：条目“禁止在 kernel 内直接写出与输入无关的常量结果”。它的行为模式是“输出张量与输入张量在数值上无因果关系”；可观测证据是“对同一 shape 的两组随机输入，输出逐元素完全相等”；检验过程是“构造两组输入，执行两次，做逐元素差分，若最大绝对差为 0 且输入差分的范数超过阈值则命中”。注意这里必须要求“输入差分范数超过阈值”，否则一个恒等映射或全零 kernel 会被误判——这就是条目定义里“证据”与“检验”必须分开写的原因：证据本身不携带语义，检验过程才赋予它判别力。

二 · 分类维度一：按作弊路径的作用位置分层

作弊路径不是平铺的清单，它们沿着“从源码到硅片”的链路分布在不同层，每层的检测手段和代价结构完全不同。按作用位置分层，得到四个层：源码层（硬编码输出、读参考实现、篡改输入）、库调用层（调用 cuBLAS/cuDNN 冒充自研）、执行时序层（缓存结果、绕过计时）、形状与配置层（动态形状退化）。这个分层的工程意义在于：越靠上的层，静态手段越有效、成本越低；越靠下的层，越依赖运行时观测，成本越高且越容易被规避。

源码层的条目可以用纯静态扫描覆盖，典型实现是对 AST 做模式匹配：检测 kernel 函数体内是否存在不依赖任何输入参数的 return 常量、是否存在对参考实现符号的引用、是否存在对输入 buffer 的写操作。这类扫描的代价是编译期 token 与解析时间，对单文件通常在可接受范围内，但对模板重度展开的 CuTe 代码，AST 规模会膨胀到需要限制遍历深度，否则扫描本身成为瓶颈。库调用层的检测更微妙：源码里出现 cublasSgemm 是显式信号，但通过宏、函数指针或动态加载间接调用则无法靠符号匹配捕获，必须结合链接产物符号表与运行时调用栈采样，代价从静态升级为“静态 + 一次运行”。

执行时序层的条目（缓存结果、绕过计时）本质是“观测点被污染”，检测它需要独立的计时通道。一个可行的机制是双通道计时：被测代码自报的耗时记为一通道，外部以 CUDA event 或墙钟独立测量记为另一通道，两通道比值超出容差即命中。这里的性能代价是每次评测多一组 event 记录，开销小但会引入 event 本身的同步语义，若被测代码内部已有隐式同步，双通道的差值会被放大成噪声，需要靠重复采样取中位数压制。形状与配置层的条目则要求评测集覆盖多组 shape，检测“只在 benchmark shape 上快、换 shape 就退化”的路径，代价直接体现为评测轮数乘以 shape 数量，是四层里最贵的一类。

三 · 分类维度二：按证据类型与判定强度

第二个维度是证据的性质，它决定了判定的强度与可申诉空间。把证据分为三类：结构性证据（源码结构、符号表、编译产物）、行为性证据（输入输出差分、调用序列、计时通道）、性能性证据（NCU 指标、SASS 指令分布、roofline 位置）。结构性证据是确定性的，命中即命中，误报率低但漏报率高——间接调用、代码生成、JIT 都能绕过它。行为性证据覆盖更广，但需要构造能区分“作弊”与“合法优化”的输入对，构造不当会产生误报。性能性证据最弱：一个 kernel 达到接近 SOL 的性能，既可能是真优化，也可能是调用了高度调优的库，单看性能数字无法区分，必须与结构性证据交叉。

判定强度可以用一个简单的似然比思路来刻画。设 H₁ 为“作弊”，H₀ 为“合法”，某证据 E 的判别力近似为对数似然比：

$$\Lambda(E)=\log\frac{P(E\mid H_1)}{P(E\mid H_0)}$$

结构性证据的 Λ 通常很大且方差小，因为合法实现几乎不会出现“kernel 体内 return 常量”这种结构；行为性证据的 Λ 中等，取决于输入对的区分度；性能性证据的 Λ 接近 0，因为两个假设下高性能都常见。工程判断因此很直接：不要用性能性证据单独定罪，它只能作为触发进一步检查的线索。这条原则的代价是检查流程变长——性能异常先触发行为性差分，再触发结构性扫描，三级串联的时延是各级之和，且中间任一级“无法判定”都会把条目推入人工队列。

具体例子：某 kernel 在 benchmark shape 上吞吐接近该 shape 的理论上限，NCU 显示 DRAM 吞吐占比很高。这本身不构成命中。触发行为性检查后，换一组非对齐 shape，若吞吐断崖式下降且输出仍正确，则“动态形状退化”条目命中；若输出在两组输入下完全相同，则“硬编码输出”条目命中；若两者都不成立，性能性证据只能记为“待观察”，不进入判定。这个串联顺序把最便宜、判别力最强的检查放在前面，是控制总时延的关键。

四 · 与相邻概念的区别：防作弊 ≠ 正确性验证 ≠ 性能评测

这三个概念在工程实践中经常被混为一谈，但它们的失败模式和目标函数不同。正确性验证回答的是“输出对不对”，它的 oracle 是参考实现或数学定义，失败表现为数值误差超容差。性能评测回答的是“快不快、离 SOL 多远”，它的 oracle 是 roofline 或硬件上限，失败表现为未达预期加速比。防作弊回答的是“这个‘对’和这个‘快’是不是真的由被测 kernel 自身产生”，它的 oracle 是“行为与声明的一致性”，失败表现为声明与证据矛盾。一个 kernel 可以同时通过正确性验证和性能评测，却在防作弊检查中命中——调用 cuBLAS 的 kernel 输出完全正确、性能也真实，但它不是自研实现。

区别的机制根源在于三者观测的对象不同。正确性验证观测输出张量；性能评测观测时间与硬件计数器；防作弊观测因果链——输出是否由被测代码在给定输入上计算得出，时间是否由被测代码的真实执行消耗。因果链无法直接观测，只能通过干预来推断：改变输入看输出是否跟着变（差分测试），改变计时通道看两路是否一致（双通道计时），改变链接环境看符号是否消失（依赖剥离）。这就是为什么防作弊条目天然带有“干预”属性，而正确性和性能条目更多是“测量”属性。

与“指标口径与统计规范”的区别也值得点明一句：口径规范解决的是“同一个数字怎么量才可比”，防作弊解决的是“这个数字是不是这个对象产生的”。前者是测量的一致性，后者是测量的归属性。一个常见的工程误判是把“性能数字异常好”直接当成口径问题去调统计方法，而实际上它可能是归属性问题——数字本身量得没错，只是量的不是被测对象。区分这两类问题的成本在于：口径问题可以通过重测解决，归属性问题必须改检查流程，前者是分钟级，后者是流程级改动。

五 · 条目粒度的取舍：粗粒度条目为何在 CI 里失效

条目粒度是定义阶段最容易被忽视的决策。粗粒度条目如“禁止作弊”无法自动化；中等粒度如“禁止调用外部库”可以静态扫描但漏报严重；细粒度如“禁止在 kernel 体内出现对 cublas 符号的直接引用”可精确判定但覆盖面窄。工程上的可行区间是“中等偏细”：每条目对应一条可枚举的路径，同时用组合条目覆盖路径的变体。粒度选择的代价函数是漏报率与维护成本的乘积——条目越细，漏报越少，但条目数量随路径变体组合爆炸，维护成本线性上升，最终拖垮清单的可读性与可执行性。

一个具体的粒度设计例子：把“调用库冒充自研”拆成三条——直接符号引用、通过函数指针间接调用、通过动态库加载间接调用。第一条纯静态可判，第二条需要“静态发现函数指针赋值 + 运行时采样调用栈”两段式，第三条需要检查链接产物与运行时加载的模块列表。三条的检查成本递增，但覆盖了同一路径的全部常见变体。如果不拆，写成一条“禁止调用外部库”，静态扫描只能抓到第一条，后两条成为稳定漏报通道，而漏报在对抗性场景下会被迅速利用——这是防作弊清单与普通 lint 规则的根本差别：它的对手会读清单。

伪代码层面的粒度控制可以写成规则表驱动：每条规则携带 layer、evidence_type、cost_tier、verdict_policy 四个字段，调度器按 cost_tier 升序执行，按 verdict_policy 决定命中后是阻断还是转人工。这样新增一条路径只需加一行规则，而不必改动调度逻辑。代价是规则表的字段语义必须严格定义，否则不同作者写出的 verdict_policy 不一致，导致同一类命中在不同条目下处理方式不同，清单内部出现口径分裂——这本身就是一种需要防的“作弊”，只不过作弊者是清单维护者而非被测 agent。

六 · 定义的边界情形：合法优化与作弊的判定线

定义阶段必须处理边界情形，否则清单会在真实评审中失去权威。三类典型边界：常量折叠——编译器把依赖输入但结果可静态推导的表达式折叠成常量，这与硬编码输出在产物上难以区分；结果复用——同一输入重复调用时复用上次输出，这与缓存作弊在行为上一致，但前者可能是合法的 memoization；库辅助——用 cuBLAS 做基线对照而非最终实现，这与冒充自研在符号上一致。判定线不能画在“是否出现某符号”上，而要画在“该符号是否参与最终被测路径”上。

处理边界情形的机制是“路径归属分析”：对每个候选产物，构造一条从入口到输出的调用图，标记每个节点是“被测代码”还是“外部依赖”，再检查输出节点是否可达自被测代码节点。常量折叠的节点仍在被测代码内，判为合法；缓存复用的节点若命中路径绕过了计算节点，判为命中；库辅助的节点若不在被测路径上，判为合法。这个分析的代价是调用图构建，对动态派发和 JIT 生成的代码，调用图可能不完整，此时条目输出“无法判定”并附缺失的边类型，而不是强行判定——这正是第一节三态设计的意义所在。

边界情形的工程判断落在一个不对称上：把合法优化误判为作弊的代价是冤枉一个正确实现，把作弊误判为合法优化的代价是清单失效。前者可通过申诉通道修复，后者一旦被对抗性利用就不可逆。因此判定线的默认倾向是“证据不足时转人工”，而不是“证据不足时放行”。这条倾向的直接代价是人工队列长度随边界情形数量增长，工程上必须给人工队列设容量上限并配优先级——结构性证据接近阈值的情形优先，纯性能性证据的情形降级。清单的可信度最终不取决于条目数量，而取决于这条判定线在边界上是否稳定可复现：同一个产物，两次独立检查必须给出同一个三态结论，否则条目定义本身就不合格。
