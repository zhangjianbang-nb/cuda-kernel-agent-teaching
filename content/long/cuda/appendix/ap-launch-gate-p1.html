一 · 门禁条目的定义：从“检查项”到“可裁决断言”

上线门禁清单里的一个条目，不是一句“检查一下正确性”的提醒，而是一条可裁决断言：它必须同时具备四个要素——判定对象、判定谓词、证据载体、裁决人。缺任何一个，条目就退化为口号。判定对象是被测 kernel 的一个可观测切面（某个 shape 下的输出张量、某条 NCU 计数器、某次编译的产物哈希、某个回滚脚本的执行退出码）；判定谓词是一个能把该切面映射到 {pass, fail, unknown} 的布尔函数；证据载体是该谓词求值所依赖的持久化产物（测试日志、profile 报告、diff、签名）；裁决人是对 fail 有权阻断发布、对 unknown 有权要求补测的角色。工程上把这四元组写成条目模板，才能让门禁在 CI 里被机器执行、在评审里被人追责。

形式化地，一条门禁条目 $g$ 可写为

$$g = \langle O,\ \pi,\ E,\ R \rangle,\quad \pi: \mathrm{obs}(O) \to \{\text{pass},\text{fail},\text{unknown}\}$$

其中 $\mathrm{obs}(O)$ 是从对象 $O$ 采集观测值的动作。关键点在于 $\pi$ 必须是全函数且可复现：给定同一份证据 $E$，任何人重跑 $\pi$ 都得到同一结论。凡依赖“看一眼觉得还行”的条目，都应被重写为带阈值的谓词。例如“性能达阈值”不是条目，$\pi_{\text{sol}} = [\mathrm{SOL}(O) \ge \tau_{\text{sol}}]$ 才是，其中 $\mathrm{SOL}$ 是相对 roofline 的达成率、$\tau_{\text{sol}}$ 是该 kernel 类别预设的下界。这里的代价是显式的：每增加一条带证据留存的条目，CI 就要多跑一次采集、多存一份产物。以 NCU 采集为例，一次带 section 的 profile 会把 kernel 重放若干遍，单次采集的墙钟时延通常是裸跑的数十倍量级，且报告体积可达数十 MB；因此条目设计的第一条工程约束是证据成本必须与它拦截的风险相称，不能给每个小 kernel 都挂全套 NCU 门禁。

具体例子：一条“显存与数值稳定性达标”的条目，其 $O$ 是目标 shape 集合上的前向输出，$\pi$ 同时求值两个谓词——峰值显存不超过预算、输出中 NaN/Inf 计数为零且相对误差在容差内；$E$ 是带固定随机种子的测试日志加上显存峰值采样；$R$ 是 kernel owner。若只写“注意数值稳定性”，则当输出在某个极端 shape 上出现 Inf 时，无人能证明自己检查过、也无人能被追责。

二 · 分类维度一：按被裁决的属性切分

门禁条目最自然的分类维度是“它在裁决什么属性”，这直接决定了证据形态与失败代价。可分成五族：正确性族、性能族、诚信族、资源与数值族、可运维族。这个切分不是美学选择，而是因为五族的证据采集路径、误判模式和阻断强度完全不同，混在一起写会让清单无法排优先级。

族典型谓词证据形态失败代价
正确性全 shape 输出与参考实现一致测试日志、逐元素 diff功能性错误，必须硬阻断
性能SOL 达成率 ≥ 阈值NCU 报告、计时统计收益归零，可条件放行
诚信无作弊告警静态/动态检查记录结论不可信，硬阻断
资源与数值显存 ≤ 预算、无 NaN/Inf峰值采样、数值扫描日志线上崩溃或静默错，硬阻断
可运维回滚脚本可执行且退出码为 0演练记录、产物快照故障恢复时间失控

正确性族的谓词看似简单，代价却藏在覆盖面上：把 shape 集合从“基准里的那几个”扩到“生产流量里的长尾”，测试时延会随 shape 数线性增长，而每个 shape 都要跑参考实现（往往是 PyTorch 或高精度 CPU 版本），参考侧本身可能比被测 kernel 慢一到两个数量级。因此正确性条目必须声明覆盖策略——是按基准固定集、按生产采样、还是按边界枚举——否则“全绿”二字没有信息量。性能族的谓词依赖 SOL 口径，而 SOL 的分母（roofline 的理论下界）随 kernel 类别变化，所以性能条目必须绑定类别标签，不能跨类比较阈值。诚信族与正确性族相邻但不同：正确性问“算得对不对”，诚信问“这个‘对’是不是靠绕过被测路径得到的”，两者的证据来源不同，前者是数值 diff，后者是调用路径与输入构造的审计。资源与数值族常被误并入正确性，但它的失败模式是“在基准 shape 上对、在生产 shape 上溢出”，因此它的 $O$ 必须包含显存峰值与极端数值输入。可运维族最容易被漏写，因为它在正常路径上永远 pass，只在故障时才被求值——这正是它必须以演练记录而非代码审查作为证据的原因。

三 · 分类维度二：按阻断强度与证据成熟度切分

第二个维度是条目失败时的处置权，分为硬门禁、软门禁、观察项三级。硬门禁 fail 即阻断发布，软门禁 fail 触发人工评审并需书面豁免，观察项只记录不阻断。这个维度与第一维度正交：同一个属性族里可以有不同强度的条目。例如正确性族中“基准固定 shape 全绿”是硬门禁，而“长尾 shape 抽样全绿”在覆盖尚未稳定时可先设为软门禁。工程判断的依据是误判成本的不对称性：把一条本应硬阻断的条目降级为软门禁，代价是缺陷流入生产；把一条噪声大的条目升级为硬门禁，代价是频繁的假阳性阻断，团队会开始习惯性豁免，门禁形同虚设。

与阻断强度耦合的是证据成熟度，可分四级：L0 无证据（仅声明）、L1 一次性人工记录、L2 可复现的自动化采集、L3 带签名与版本绑定的自动化采集。门禁条目应显式标注所需证据等级，因为同一谓词在不同证据等级下的可信度差异巨大。一个“SOL 达成率 ≥ 阈值”的谓词，若证据是 L1 的单次手抄数字，它无法排除测量时的时钟波动与后台干扰；若证据是 L3 的、绑定 commit 哈希与 GPU 型号的 NCU 报告加多次计时统计，它才具备裁决力。伪代码上，门禁执行器对每个条目做三件事：

$$\text{gate}(g)=\begin{cases}\text{block} & \pi=\text{fail}\ \wedge\ \text{level}(g)=\text{hard}\\\text{review} & \pi=\text{fail}\ \wedge\ \text{level}(g)=\text{soft}\\\text{record} & \text{otherwise}\end{cases}$$

代价在这里体现为证据留存的开销：L3 要求产物与代码版本、驱动版本、GPU 型号绑定，意味着每次重跑都要落盘元数据，存储与检索成本随条目数线性上升；而 L2 到 L3 的升级往往需要改造 CI 的产物命名与签名链路，是一次性的工程投入。具体例子：一条“回滚预案就绪”的条目，若证据只到 L1（某人说“脚本在本地跑过”），它在真实故障夜的裁决力接近零；升到 L3 要求演练记录包含脚本哈希、目标环境标识、演练时间戳与退出码，才能在发布评审上作为放行依据。这也解释了为什么可运维族条目通常被定为硬门禁却常以软门禁起步——证据链路没建好之前，硬阻断只会制造豁免文化。

四 · 与相邻概念的区别：门禁条目不是基准、不是指标、不是检查清单

门禁条目与 KernelBench 系基准的区别在于裁决对象的时间位置。基准回答“这个 agent 生成的 kernel 在受控题面上有多好”，其产物是分数分布，用于比较方法与训练信号；门禁条目回答“这一个具体产物能否进入生产”，其产物是放行/阻断决定。基准的题面可以为了可比性而固定、可以为了难度而裁剪；门禁的 shape 集合必须向生产流量对齐，哪怕那会让不同版本的 kernel 之间不可比。把基准分数直接当门禁阈值是常见错误：基准里的 SOL 分布是在特定题面与特定测量口径下得到的，迁移到生产 shape 上，分母变了，阈值失去意义。

它与指标口径的区别在于是否含处置语义。指标是观测，门禁是观测加阈值加责任加证据。一个 NCU 计数器读数是指标；把它写成“该计数器超过某界即阻断并通知 owner”才是条目。指标口径规范解决的是“同一个数怎么量才可比”，门禁条目解决的是“量出来之后谁来判、判错谁负责”。二者共享采集链路，但门禁多出的是裁决与留存两段。它与防作弊检查清单的区别在于范围：防作弊是诚信族的专门展开，关注的是结论可信度这一单一属性；门禁清单则要覆盖五族属性，诚信族只是其中一族，且诚信族的条目往往作为其他族条目的前置条件——若诚信检查 fail，正确性全绿也不构成放行理由，因为那份“绿”本身不可信。

它与正确性验证器清单的区别在于抽象层级：验证器清单枚举的是“用什么工具、比什么、容差多少”的实现手段，是可复用的组件库；门禁条目引用这些组件，但额外绑定 shape 覆盖策略、证据等级与责任人。一个验证器可以被多条门禁条目复用，而一条门禁条目也可能调用多个验证器。具体例子：同一个逐元素比对验证器，既服务于“基准 shape 全绿”这条硬门禁，也服务于“长尾抽样全绿”这条软门禁，两条条目的差别不在验证器，而在覆盖集合与阻断强度。这种区分让清单可以在验证器升级时批量重估受影响条目，而不必逐条重写。

五 · 条目粒度的取舍：为什么一条条目只裁决一个谓词

条目粒度是设计门禁清单时最容易被低估的决策。把“正确性、性能、显存”塞进一条条目，看似精简，实则让失败诊断退化为猜谜：当条目 fail 时，执行器无法区分是数值错、是慢、还是显存超，责任人也无法被精确指派。因此工程约束是一条条目一个谓词、一个责任人、一份证据。这条约束的代价是条目数膨胀，清单变长，评审时间上升；收益是失败可归因、豁免可精确到谓词、证据可独立留存。折中的做法是按“同一采集动作”聚合：若三个谓词共享同一次 NCU 采集，可以合并采集但拆分裁决，即一份证据、三条条目。

粒度还影响门禁的执行顺序与短路逻辑。正确性族应排在性能族之前，因为对一个算错的 kernel 做性能优化没有意义，且性能采集（NCU 重放）成本高，短路能省下这部分时延。诚信族应排在最前，因为它决定后续所有证据是否可信。伪代码上，执行器按族序求值并在硬门禁 fail 时短路：

$$\text{run}(G)=\text{foldl}\big(\lambda acc,g \to \text{if } acc=\text{block} \text{ then } acc \text{ else } \text{gate}(g)\big),\ \text{order}=[\text{integrity},\text{correctness},\text{resource},\text{perf},\text{ops}]$$

这个顺序本身是一条工程判断，而非定理：把诚信放在最前是因为它的证据成本最低（静态检查与调用路径审计通常比数值扫描和 NCU 采集便宜得多），却能否决后面所有昂贵采集的结论。把可运维族放在最后，是因为它的证据（演练记录）通常不随每次代码变更而变，可以按发布批次而非按 commit 求值，从而把它的执行频率降下来。具体例子：一次发布中，诚信检查发现被测 kernel 在某个 shape 上走了参考实现的分支，执行器立即阻断，正确性族的逐元素 diff 与性能族的 NCU 采集都不必启动——这省下的不只是采集时延，还有为不可信结论做人工评审的时间。

最后落在条目模板的字段设计上：每条条目至少要有 id、族标签、谓词表达式、所需证据等级、阻断强度、责任人、证据留存路径七个字段。缺 id 则无法在豁免记录里被引用；缺族标签则无法参与短路排序；缺证据等级则无法判断结论可信度；缺留存路径则证据在评审后即散失。这七个字段构成的最小结构，是把“放行条件”从自然语言承诺转化为可执行、可追责、可复算的工程对象的起点。

门禁条目不是检查项清单，而是带证据与责任人的放行断言

把“上线门禁清单”理解成一张打勾表是常见误读。条目的准确定义是：一条可判定、可追溯、可追责的放行断言——它必须同时绑定三样东西，判定条件（正确性全绿、性能达阈值、无作弊告警、显存与数值稳定性达标、回滚预案就绪）、证据留存（哪次运行的日志、哪份 profile、哪版回滚脚本）、责任人（谁签字、谁在失效时被叫醒）。缺任一项，条目就退化为“意见”而非“门禁”。由此可给出条目的判定式：放行当且仅当对所有条目 e，pass(e) ∧ evidence(e) ≠ ∅ ∧ owner(e) ≠ ∅ 同时成立；任一为假即阻断，且阻断原因必须落到具体条目而非“整体不达标”。这个合取结构决定了门禁的失效模式是“单点否决”，而不是加权打分——后者会把一个正确性漏洞用性能优势抵消掉。

分类维度应沿“证据的产生方式”切分，而不是沿“检查的对象”切分。第一类是可复现的离线判定：正确性全绿由固定种子、固定输入分布的测试套件产出，证据是测试报告，代价是每次改动都要重跑，编译与执行时间随 kernel 数量线性增长。第二类是统计性判定：性能达阈值依赖多次采样的时延/带宽分布，必须规定采样次数与置信区间，否则同一 kernel 在不同机器上给出相反结论；其代价是测量本身占用 GPU 时间，且阈值一旦贴近 roofline/SOL 上限，方差会把边界样本反复翻转。第三类是告警型判定：无作弊告警（如绕过基准输入、缓存结果、调用库函数冒充自研 kernel）本质是检测器的假阴/假阳权衡，证据是告警日志与人工复核记录，代价是复核 token 与人力。第四类是预案型判定：回滚预案就绪不产生运行时证据，只能靠演练记录证明，代价是上线前必须真实执行一次回滚，占用一次发布窗口。

与相邻概念的区别要划清三条线。其一，门禁条目 ≠ 基准分数：KernelBench 系基准给出的是相对能力信号，门禁条目要求的是针对本次上线形态的绝对判定，二者证据不可互换。其二，门禁条目 ≠ 正确性 oracle：oracle 回答“这个 kernel 算得对不对”，条目还要回答“错了能不能退回去、谁负责退”。其三，门禁条目 ≠ 性能回归看板：看板是持续观测，条目是一次性放行断言，观测数据只是条目的证据来源之一。一个具体例子：某 Triton kernel 在正确性套件上全绿、吞吐达到阈值，但显存峰值在长序列输入下越界——显存条目独立否决，性能条目不得为其背书。工程判断上，条目数量应随 kernel 的爆炸半径增长而增长，而非随代码行数增长；把条目写成“越多越安全”会直接推高编译与演练成本，最终逼团队用豁免绕过门禁，这比少写两条更危险。
