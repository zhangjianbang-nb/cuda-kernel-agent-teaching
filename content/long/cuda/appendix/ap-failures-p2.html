二 · 速查表的结构：一行一个失败模式，五列定死口径

这张表不是给读者“看一眼有印象”的，而是给 agent 在诊断循环里直接查表用的：给定一条失败信号，能立刻定位到失败模式、判定阈值、复现口径和必须付出的代价。所以表的列必须定死，不能随条目变化。本表固定五列：模式 / 首要信号 / 判定阈值（口径） / 最小复现手段 / 代价量级。前三列解决“是不是这个病”，后两列解决“怎么确认、确认要花多少”。任何一行若缺了阈值口径或代价量级，就不该进表——因为 agent 无法据此做二值判断，只能靠语言模型的模糊直觉，而这正是失败模式库要消灭的东西。

阈值列的口径统一约定为三种量纲之一：相对量（相对基线或相对理论峰值的比值）、绝对量（计数、字节、周期）、结构性布尔（存在/不存在某个可观测事实，例如 SASS 中是否出现某条指令、编译日志中是否出现某个 warning 类别）。结构性布尔是最可靠的一类，因为它不依赖测量噪声；相对量次之；绝对量最容易被环境漂移污染，所以凡是用绝对量的行，必须在“最小复现手段”列同时写明固定环境的动作。

$$\text{判定} = \begin{cases}\text{命中} & \text{若 } \frac{m}{m_{\text{ref}}} > \tau \ \text{或布尔条件成立}\\ \text{存疑} & \text{若 } \tau/2 < \frac{m}{m_{\text{ref}}} \le \tau\\ \text{排除} & \text{否则}\end{cases}$$

三态判定是这张表的隐含契约：agent 拿到“存疑”时不允许直接改代码，必须先跑“最小复现手段”列指定的动作把三态收敛成二态。这条规则的成本是每轮诊断多一次测量往返（典型为一次 kernel 重跑加一次 profile 采集），换来的收益是避免在错误根因上做无效编辑——无效编辑在 agent 循环里是 token 与编译时间的主要浪费源。

下表按“症状可观测性从强到弱”排序：编译期失败最容易被抓到，静默数值错误最难。排序本身有工程含义——越靠后的行，越依赖“最小复现手段”列里的人工构造输入，而不是靠现成 benchmark 跑一遍就能暴露。

读表时要注意两件事。第一，“首要信号”列故意只给一个信号，因为多信号并列会让 agent 在冲突时无法决策；次要信号放在“最小复现手段”列的动作里间接体现。第二，阈值列全部写成符号 τ，不写数值——这是刻意的：τ 的取值必须由项目自己的基线分布定，写死数值会让表在不同硬件、不同编译器版本上失效，而失效的速查表比没有速查表更危险，因为它给了虚假的确定性。

四 · 阈值怎么定：从基线分布反推，而不是拍脑袋

τ 不能凭空给。正确做法是先在“已知正确且已知性能达标”的配置集合上采一批测量，得到该指标的分布，再把 τ 放在分布的尾部之外。以静默数值错误为例：设参考实现与候选实现在一批输入上的逐元素相对误差为 ei，取分位数 q99(e) 作为 τnum 的下界候选，再乘以一个安全系数。这个做法有一个必须写进表的口径约束：误差必须在与参考实现相同的累加顺序下比较，否则比较的是算法差异而不是实现缺陷。归约类 kernel 的浮点累加顺序不同会带来合法误差，把这种误差判成“静默数值错误”是这张表最常见的误报来源。

$$\tau_{\text{num}} = \alpha \cdot q_{99}\!\left(\{e_i\}\right), \quad \alpha \ge 1$$

对 occupancy 塌陷，阈值 τocc 的定法不同：理论上限由寄存器数、shared memory 用量、block 上限三者取最小推出，实测驻留由 profile 给出。这里的口径陷阱是“理论上限”必须用实际编译产物的资源占用算，而不是用源码里写的 launch bounds 算——编译器可能因为 spill 或指令调度改变实际寄存器数，源码意图与产物事实之间的差就是塌陷的来源之一。代价上，这条判定需要一次完整编译加一次 profile，属于表中较贵的一行；因此工程上通常把它放在“已确认性能不达标”之后才跑，而不是每轮都跑。

对评测环境漂移，τdrift 的口径必须绑定“同一二进制、同一输入、同一并发度”，任何一项变化都不算漂移而算配置变更。具体例子：同一 kernel 在两个会话里测得的时延差异若超过 τdrift，先查时钟频率锁定与后台占用，再查输入是否被缓存预热影响——后者是 agent 评测里最隐蔽的漂移源，因为第一次运行包含冷启动，第二次不含。代价是重复采集带来的时延翻倍，收益是把“性能提升”与“测量噪声”分开。

五 · 最小复现手段：把“存疑”压成二值的固定动作

每一行的“最小复现手段”列都必须是一个可脚本化、无人类判断的动作序列，否则 agent 无法执行。以 race condition 为例，动作序列固定为：固定输入 → 连续运行 N 次 → 对每次输出做哈希 → 统计哈希集合基数。基数大于 1 即命中。这个动作的代价是 N 次重跑时延，且 N 必须足够大才能让低概率竞态暴露；工程判断是：若 N 次内未命中但代码中存在无同步的跨线程写，仍应标“存疑”并进入同步点二分，而不是直接排除。二分定位的代价是每插入一个同步点就多一次编译加运行，属于表中较贵的手段，所以只在“存疑”态使用。

对 bank conflict，最小复现手段是 A/B 改写而不是直接读 profile 数字：把访问 stride 从原值改为一个已知无冲突的值，重编译，比较两次 profile 的 wavefront 数。这样做的原因是 profile 的绝对 wavefront 数受编译器向量化影响，单看绝对值无法判断“是否可改进”；A/B 差分把编译器差异消掉了。代价是两次编译加两次 profile，收益是判定不依赖对硬件的先验假设。

对 autotune 过拟合，最小复现手段的核心是形状切分：把形状集合分成搜索集与留出集，在搜索集上选优，在留出集上复测。判定用相对量 τgen。这里的口径陷阱是留出集必须与搜索集在形状分布上同源但不相交，否则测的是外推能力而不是过拟合。代价是搜索空间大小乘以单次编译运行时间——这是表中最贵的一行，因此工程上通常只在“搜索集收益显著但线上收益不显著”时才触发。

六 · 表的使用纪律：三态、单信号、代价前置

这张表要能用，必须配三条纪律。第一，三态纪律：agent 只允许在“命中”态改代码，“存疑”态必须先执行最小复现手段，“排除”态必须记录排除理由，防止同一失败模式在后续轮次被重复排查。第二，单信号纪律：判定只用“首要信号”列，不得临时引入表外信号，否则不同轮次的判定不可比，评测口径被悄悄改写。第三，代价前置纪律：在跑任何一行之前先读“代价量级”列，若该行代价高于当前轮次的预算，就降级为记录而不判定——这条纪律直接对应 agent 循环里的 token 与编译时间预算，避免为了确认一个低优先级失败模式而耗尽整轮预算。

具体到工程判断：编译失败与寄存器溢出两行的代价最低（纯编译期，无运行时成本），应当每轮无条件跑；静默数值错误与 race condition 需要构造输入与重复运行，按需跑；bank conflict、occupancy 塌陷、autotune 过拟合、环境漂移四行需要 profile 或多配置扫描，只在性能类问题被提出后跑。这个分层不是偏好，而是由每行的代价量级直接推出的调度策略——速查表的价值一半在判定，一半在告诉你什么时候不该去判定。

速查表的失效边界：阈值不是判据，口径才是

速查表最容易出问题的地方，是把“症状字段”当成“判决字段”。表里每一行真正可用的只有三列：观测字段、触发阈值、口径说明。观测字段必须来自可复现的采集通道——编译日志的 error code、运行期的 cudaGetLastError 与 compute-sanitizer 报告、NCU 的 stall reason 分布、SASS 中 LDG/STS 的指令计数、autotune 的候选配置与实测时延序列。阈值一列只写“超过即进入该分支”，不写“等于即判定”，因为寄存器溢出、occupancy 塌陷这类量的边界是连续的：regs per thread 越过编译器设定的 spill 门槛时，症状不是二值的，而是 spill 字节数随时延一起爬升。口径一列必须写明测量对象与排除项，例如“bank conflict 计数取 shared load 的 wavefronts 与 ideal wavefronts 之比，排除 broadcast 访问”“occupancy 取 active warps 上限而非 achieved occupancy”，否则同一张表在两个团队手里会给出相反的结论。

一个具体机制可以写成判定式的形式化：设观测向量 o 含编译状态、sanitizer 命中数、stall 占比、spill 字节、autotune 时延方差，判定函数 D(o) 输出失败类别。速查表的作用不是替代 D，而是给出 D 在各分量上的分段线性近似：

$$D(o)=\arg\max_{c}\ \sum_{i} w_{i,c}\,\mathbb{1}\!\left[o_i \gtrless \tau_{i,c}\right],\quad \sum_i w_{i,c}=1$$

权重 w 与阈值 τ 的标定代价是真实的：每增加一个类别，就要在基准集上重跑一轮采集，NCU 单 kernel 的 profile 开销会让端到端评测时间成倍上升；若把 sanitizer 常开，race condition 的检出率上升但吞吐降到不可用于 autotune 的程度。因此表里必须标注“仅在验证阶段启用”的字段，把代价显式化。

失效条件集中在三类。其一是环境漂移：同一 kernel 在评测机 A 上 occupancy 达标、在 B 上塌陷，根因往往是 SM 版本与编译器版本不同导致寄存器分配变化，此时阈值应绑定到 (arch, nvcc 版本, 编译 flag) 三元组，而不是全局常数。其二是 autotune 过拟合：候选配置在固定 shape 上时延最优，换 shape 后排名翻转，速查表若只看“最优时延”字段就会漏判，必须并列记录候选集的时延方差与最差候选，方差越过阈值即标为过拟合嫌疑。其三是静默数值错误：编译通过、sanitizer 无命中、时延正常，但输出与 oracle 在特定边界元素上不符，这类失败不落在任何性能字段上，只能靠正确性 oracle 的差分字段捕获，表里应单列“oracle 不一致元素数”并规定其阈值为零容忍。
