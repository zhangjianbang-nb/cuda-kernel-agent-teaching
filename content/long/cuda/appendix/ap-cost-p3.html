一 · 阈值不是拍脑袋：三类可复现的测量口径

工程阈值的可信度取决于它能否被同一台机器、同一份代码、同一个输入在隔天复现。算力成本表里出现的每一个数字，都必须标注它属于哪一类口径，否则跨团队对齐时必然失真。实践中把阈值来源分成三类：硬约束型（由硬件规格与编译产物决定，如 SM 占用、共享内存上限、寄存器溢出点）、统计型（由多次采样得到的分布决定，如 rollout 时延的 P50/P95、NCU 采集开销的倍数）、预算型（由业务侧给定的成本上限反推，如每千次验证允许的 GPU 分钟数）。三类的测量方法完全不同：硬约束型靠编译期静态分析与一次最小复现，统计型靠固定采样次数与分位数报告，预算型靠把成本拆成可加项再逐项测量。

测量口径必须写成可执行的形式，而不是描述性文字。以「单次 rollout 的编译+运行秒数」为例，它的可复现定义是：给定 kernel 源码、固定的编译 flag 集合、固定的输入 shape 与 dtype，从进程启动到 kernel 结果写回主机内存的墙钟时间，重复 N 次后取分位数，并单独记录首次编译（冷启动）与缓存命中（热启动）两条曲线。冷热分离是必须的，因为 Triton 的 JIT 缓存与 CUDA 的 cubin 缓存会把首次编译的秒级开销摊薄到后续调用中，混在一起统计会让预算低估编译成本。代价在于：冷启动测量每次都要清理缓存目录，单条样本的准备时间从毫秒级升到秒级，采样吞吐下降一个量级；因此工程上通常只对候选集中的前若干名做冷启动测量，其余用热启动加固定补偿项。

一个具体例子：某条目要给出「A100 上单次 rollout 的编译+运行秒数」，正确做法是分别记录 t_compile（nvcc/ptxas 或 Triton JIT 的墙钟）与 t_run（kernel 执行加同步），再报告 t_total = t_compile + t_run 的 P50 与 P95，并注明编译缓存是否命中。若只报一个混合数字，读者无法判断优化编译时间是否值得——而这恰恰是 agent 多轮迭代中最常见的成本项。

二 · 编译开销阈值：什么情况下值得为编译时间买单

编译时间在 agent 循环里是纯开销，但它换来的运行时收益必须超过一个盈亏平衡点才值得。设候选 kernel 的编译耗时为 t_c，相对基线 kernel 的单次运行加速比为 s（s > 1 表示更快），基线单次运行时间为 t_b，则该候选在 n 次调用下的净收益为：

$$\Delta(n) = n \cdot t_b \left(1 - \frac{1}{s}\right) - t_c$$

令 Δ(n) = 0 得到盈亏平衡调用次数 n* = t_c / (t_b (1 - 1/s))。这个式子给出了一条工程判据：当预期调用次数低于 n* 时，编译更慢但更快的 kernel 在总成本上是亏的。agent 场景下 n 往往很小（一次验证只跑几次），所以 n* 常常落在个位数到几十之间，这意味着「编译时间超过运行时间一个量级」的候选在单次评测里几乎不可能回本，除非它被纳入生产部署路径。

由此衍生出两条经验阈值，都以定性方式表述而不编造具体秒数：其一，若某候选的编译耗时显著超过其单次运行耗时（例如超过一个数量级），则在单轮评测预算中应将其标记为「仅生产候选」，不参与多轮 rollout 的反复编译；其二，若编译耗时的方差很大（同一源码多次编译时间差异明显），说明编译路径中存在非确定性因素（模板展开、缓存状态、并行编译调度），此时应固定编译环境并把方差作为单独指标上报，而不是取均值掩盖。

测量方法上，编译时间必须与运行时间分开计时，且要区分「首次编译」与「增量编译」。CuTe 与模板重度使用的 CUDA C++ 代码，编译时间对模板实例化数量近似线性增长，因此可以用「每增加一个 shape 特化所带来的编译秒数增量」作为该 kernel 的编译成本斜率，写进成本表。代价是：为测斜率需要构造多个特化版本并逐一编译，测量本身的编译开销可能超过被测对象，因此只在候选进入决赛圈时做。一个具体例子：同一 kernel 对 4 个 dtype 各做一次特化，若编译总时间随特化数线性上升，则报告斜率而非单点值，读者据此判断新增一个 dtype 支持的边际成本。

三 · NCU profile 开销倍数：采样密度与预算的换算

NCU 采集不是免费的。它的开销来自两方面：一是 replay（同一 kernel 被多次重放以采集不同计数器组），二是采集本身的驱动侧停顿。开销倍数定义为 k = t_profile / t_run，即带 profile 的墙钟时间除以裸跑时间。这个倍数随采集的 metric 集合、是否开启 source-level 关联、是否采集 SASS 而变，因此成本表里必须写成「在某一采集配置下的倍数」，而不能给一个无量纲的通用值。

预算换算的机制是：若一次 agent rollout 需要做 m 次 profile，每次 profile 的裸跑时间为 t_run，则 profile 部分的总开销为 m · k · t_run，它直接叠加在 rollout 的编译+运行秒数上。于是单次 rollout 的有效成本为：

$$t_{\text{eff}} = t_{\text{compile}} + t_{\text{run}} + m \cdot k \cdot t_{\text{run}}$$

工程判据：当 m · k 与 1 同量级时，profile 开销已经与裸跑相当，此时应限制 profile 的触发条件（例如只在正确性通过后、只在候选排名前若干时采集），而不是对每个候选都全量采集。若 k 本身很大（采集了重量级 metric 组），则即使 m = 1 也会显著改变预算，成本表应把这类配置单列一行。

测量方法：固定同一 kernel、同一输入，先测裸跑 t_run（含同步），再在同一进程外启动 NCU 采集同一 kernel 测 t_profile，两者相除得 k。必须注意 t_run 要包含 kernel 启动与同步的完整墙钟，否则分母偏小会把 k 高估。代价是：NCU 采集会改变 GPU 的时钟行为与缓存状态，测得的 t_profile 不能反过来当作性能数字使用，只能用于开销换算；因此成本表里 profile 开销与 kernel 性能必须分列，禁止用 profile 期间的耗时去推断 SOL。一个具体例子：某候选在正确性 oracle 通过后触发一次 NCU 采集，若 k 约为数倍，则该候选的单次验证预算应把 profile 开销按倍数计入，而不是按裸跑时间计。

四 · Token 成本：把 GPU 分钟折算成可比的预算单位

全流程 token 成本是 agent 侧的成本，与 GPU 侧成本通过「每 token 对应的 GPU 秒数」耦合。设一次 rollout 消耗的 token 数为 T，其中生成侧 token 为 T_gen、提示与工具返回侧 token 为 T_ctx，单 token 的生成时延为 τ（由模型与批大小决定），则 LLM 侧墙钟约为 T_gen · τ（上下文处理另计）。把它与 GPU 侧 t_eff 相加，得到单次 rollout 的总墙钟，再乘以 GPU 每小时单价与并发度约束，才能得到「每次 rollout 的货币成本」。

这里的工程阈值是：token 成本与 GPU 成本谁占主导。当 T_gen · τ 显著大于 t_eff 时，优化 kernel 本身对总成本的影响被 LLM 时延掩盖，此时应优先压缩上下文（减少工具返回的冗余、截断 profile 文本）而不是继续调 kernel；反之当 t_eff 占主导时，编译与 profile 开销才是预算瓶颈。这个判断必须基于测量而非直觉，测量方法是分别记录 LLM 调用墙钟与 GPU 调用墙钟，按 rollout 聚合后比较占比。

代价在于：token 计数与 GPU 秒数的对齐需要插桩，插桩本身引入日志开销与时钟不同步误差；若 LLM 侧是流式返回，墙钟的起止点定义会显著影响结果，成本表必须写明「从请求发出到最后一个 token 落地」这一口径。一个具体例子：某条目的全流程 token 成本若主要来自把 NCU 的文本输出回灌进上下文，则压缩 profile 文本（只保留关键 metric 行）比换更快的 GPU 更能降本——这正是把 token 成本单列的意义。

五 · 每小时单价的边界条件：并发、占用与计费粒度

按 GPU 型号给出的每小时单价，只有在明确并发模型后才有意义。单卡单价 p（货币/小时）对应的有效吞吐取决于同时驻留的 rollout 数 c 与每个 rollout 占用的资源比例 r（如显存占比、SM 占用）。若 c · r ≤ 1，则单卡可承载 c 个并发 rollout，每个 rollout 的 GPU 成本为 p · t_eff / (3600 · c)；若 c · r > 1，则发生资源争抢，t_eff 本身会因争抢而上升，此时不能再用单卡单价线性折算，必须实测争抢后的 t_eff。

工程判据：当 kernel 的显存占用接近单卡容量、或 SM 占用率高到无法与编译进程共存时，并发度实际上被压到 1，此时单价折算退化为串行模型，成本表应显式标注「该条目按串行计」。编译进程与运行进程争抢 CPU 与内存带宽也是常见边界：nvcc 并行编译会占用大量主机内存，若与多个 rollout 同机运行，会推高 t_compile 的方差。测量方法是固定并发度 c 扫描，记录 t_eff 随 c 的变化曲线，找到 t_eff 开始明显上升的拐点，把拐点之前的 c 作为该条目的推荐并发。

代价是：并发扫描需要成倍的时间预算，且拐点位置依赖具体 kernel 的显存与计算特征，不能跨条目复用。因此成本表的做法是给出「单并发基准值 + 并发拐点的定性描述」，而不是给一个通用并发数。一个具体例子：某 kernel 显存占用使其只能单卡单实例运行，则其每小时单价折算必须按 c = 1 计，任何按多并发摊薄的估算都是错的；反之若某 kernel 显存很小、可与编译进程共存，则并发拐点由主机内存而非显存决定，测量时应把主机内存水位一并记录。

六 · 没有数字时怎么写：可执行的测量协议

成本表最容易被质疑的地方是「这一格为什么是空的」。正确做法不是填一个估计值，而是填一段可执行的测量协议，让读者能自己补上这个数字。协议至少包含五项：被测对象的最小复现（源码、flag、输入 shape/dtype）、计时起止点的精确定义、采样次数与分位数口径、需要同时记录的伴随量（编译缓存状态、并发度、显存水位、主机内存水位）、以及已知的干扰因素（NCU replay、时钟波动、编译并行度）。

以「单次 rollout 的编译+运行秒数」这一格为例，协议写成伪代码式的步骤即可：清理编译缓存 → 记录进程启动时刻 → 编译 → 记录编译结束时刻 → 运行并同步 → 记录结束时刻 → 重复 N 次 → 报告 t_compile、t_run 的 P50/P95 与缓存命中标记。这样即便当前没有数字，读者也能在自有机器上产出可比数据，且口径与表内其他条目一致。协议里必须写明 N 的选取依据：N 太小则分位数不可信，N 太大则测量成本超过被测对象；工程上通常以「P95 的置信区间宽度小于条目所需精度」为停止条件，而不是固定 N。

代价是：写协议比填数字更费篇幅，且协议本身需要维护——当工具链版本变化时，协议中的 flag 与计时点可能失效。因此成本表应把协议与数字分列，数字标注其对应的工具链版本与测量日期，协议标注其适用的版本范围。一个具体例子：某条目在 Triton 与 CUDA C++ 两条路径上的编译开销差异很大，若只给一个混合数字会误导选型，此时正确做法是分两行给出各自的协议与（若有）数字，并注明 Triton 的 JIT 缓存行为与 CUDA 的 cubin 缓存行为不同，二者的冷启动口径不可直接相减。

最终落在工程判断上：成本表里的每一个阈值都应当能追溯到一次可复现的测量或一条可执行的协议，二者缺一即视为不可信条目；当数字与协议冲突时，以协议为准并重新测量，而不是修改协议去迎合数字。

阈值不是拍脑袋：从单价、秒数与 profile 倍数反推预算边界

本表最容易失效的地方，是把“每小时单价”当成唯一成本项。实际预算是三段时间的乘积：单次 rollout 的编译秒数、运行秒数，以及 NCU profile 开启后的开销倍数。设单卡时价为 P（元/卡·小时）、单次 rollout 编译 t_c 秒、运行 t_r 秒、profile 开销倍数 k（未开为 1），则一次带 profile 的 rollout 成本为 P·(t_c + k·t_r)/3600。当 k·t_r 远大于 t_c 时，profile 就是预算主项；反之编译占主导，说明该方案应优先做编译缓存而不是加卡。工程阈值由此确定：若 t_c/(t_c + k·t_r) 超过一半，先治编译；否则先治 profile 采样密度。

失效条件集中在三处。其一，token 成本与 rollout 次数线性挂钩，但编译产物可跨 rollout 复用，一旦复用率下降（每次改动 kernel 签名或模板参数），token 预算会被重复编译吞掉。其二，NCU 倍数 k 在 kernel 极短（微秒级）时急剧放大，因为固定采集开销摊不开，此时应改用采样式计数而非全量 profile。其三，单价 P 的抢占式与按需式差异会直接改变“多轮 RL 是否划算”的判断，表里必须标注计费模式，否则吞吐规划失真。

观测量测法代价
t_c同一源码重复编译取中位数编译时间本身
t_rCUDA event 计时，排除首次冷启动显存驻留
k同 kernel 开/关 NCU 各跑一轮profile 时延

具体例子：某 kernel 编译 40 秒、运行 2 秒，开 NCU 后运行段放大到 30 秒，则 k=15，带 profile 单次成本约为纯运行的十余倍，此时把 profile 从“每次 rollout”降为“每 N 次抽样一次”，是唯一能同时保住正确性 oracle 覆盖与 token 预算的做法；N 的取值由可接受的漏检率决定，而非由单价决定。
