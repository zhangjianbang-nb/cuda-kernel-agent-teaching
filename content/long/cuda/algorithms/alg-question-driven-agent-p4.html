一 · 负载选型：哪些模型/算子/shape/硬件才配得上诊断式优化

诊断式优化的前提是“瓶颈可被单变量微实验分离”。这条前提直接决定了负载的准入条件。若一个 kernel 的耗时被 host 侧同步、launch 开销或 Python 调度主导，那么改 tile、改 swizzle 带来的信号会被这些噪声淹没，微实验回答不了任何问题。因此负载选型的第一条判据是：目标 kernel 的 device 时间必须占据端到端时延的主导份额，且其内部存在至少两个可竞争的瓶颈候选（例如 memory-bound 与 occupancy-limited 并存）。第二条判据是 shape 必须落在“有结构”的区间：过小的 shape 让 kernel 处于 launch-bound，过大的 shape 让 L2 行为退化为流式，二者都会使 bank conflict、pipeline 深度这类微架构问题失去可观测性。第三条判据是算子族要选那些瓶颈根因离散可枚举的——GEMM、attention、layernorm、softmax、reduce、conv 的瓶颈候选集是有限且已知的，而一个融合了十余个算子的 megakernel 其瓶颈是复合的，单变量实验无法归因。

硬件侧的选择同样不是“越新越好”。诊断式优化依赖 NCU 指标的可读性与 SASS 的可解释性：需要目标架构上 stall reason 分类足够细、shared memory 与 register 的计数器可用、warp scheduler 行为可观测。若硬件代际过旧，部分 stall 原因被合并统计，agent 提出的“是否 bank conflict 导致 stall”这类问题就无法被指标直接回答，只能退化为间接推断。反过来，若硬件过新而工具链的指标语义尚未稳定，profile 回灌的数值可能与 SASS 实际行为错位，微实验的“是/否”结论会失真。选型的工程判断是：选一代工具链成熟、指标语义稳定的架构作为诊断基准，把新架构作为迁移验证目标而非诊断目标。

一个具体例子：把一个 batch 很小、序列很短的 attention 放进诊断流程，agent 提出的“是否 shared memory bank conflict”问题会得到“否”，但这不是因为不存在 conflict，而是因为该 shape 下 kernel 根本没跑满 SM，stall 主要来自尾部 wave 的调度空洞。微实验改 swizzle 后指标无变化，agent 据此错误地关闭了 bank conflict 假设，实际是负载选错了。代价是：一轮提问加微实验的编译与运行开销（每次微实验都要重新编译并跑正确性与计时），在预算紧张时这笔开销换不回信息量，属于纯亏损。

二 · 基线锚定：诊断的对象是“相对谁的差距”

诊断式优化的每一次 accept/reject 都建立在 $$\Delta_{\text{opt}}=\frac{T_{\text{after}}-T_{\text{before}}}{T_{\text{before}}},\quad \text{accept if }\ \Delta_{\text{opt}}<-\epsilon\ \land\ \text{correct}$$ 之上。这里 T_before 不是任意一个历史版本，而是本轮微实验的对照基线。基线选错，Δ 的符号与量级都会误导后续提问。基线必须满足三个条件：与实验组只差一个变量、在同一测量协议下采集、其正确性已被独立 oracle 确认。工程上常见的错误是把“上一轮已接受的版本”直接当基线，而上一轮可能同时改了两个变量，导致本轮 Δ 无法归因到当前假设。

基线还承担“锚定绝对性能”的职责。诊断流程内部用相对 Δ 做接受判定，但对外必须有一个绝对锚：一个已知实现（库实现、手写参考、或编译基线）在同一 shape 与硬件上的耗时。没有绝对锚，agent 可以在一个本就离 SOL 很远的实现上反复取得微小 Δ，把“局部最优”误判为“瓶颈已消除”。绝对锚的作用是给诊断设一个终止条件：当相对锚的差距落入噪声带，继续提问的边际信息量低于微实验成本，流程应停止而非继续榨取 Δ。

测量协议本身是基线的一部分。计时必须固定 warmup 次数、重复次数、是否开 L2 flush、是否锁频。诊断式优化对测量噪声尤其敏感，因为单变量微实验的效应量往往小于 1%，若测量抖动与之同量级，Δ 的符号会随机翻转，agent 会把噪声当成证据写进问题库。代价体现在 token 与编译时间上：为压低噪声需要更多重复与更严格的 flush，单次微实验的墙钟时间上升；而 agent 每轮要读回指标并生成问题，token 消耗随实验次数线性增长。一个具体做法是把微实验的对照跑成 A/B/A 三段（基线—实验—基线复测），用两次基线的离散度估计噪声带，只有 Δ 显著超出噪声带才进入 accept 判定。

三 · 输入分布：shape 采样与数据值分布是两件事

诊断式优化对输入分布的要求比普通 benchmark 更严，因为它要回答的是“在这个具体配置下瓶颈是什么”。shape 分布决定了瓶颈的类型，数据值分布决定了瓶颈是否被触发。二者必须分开设定。shape 侧要覆盖三类点：典型点（生产流量中最常见的 M/N/K 组合）、边界点（使 tile 整除性失效、使 wave 量化出现尾部的尺寸）、退化点（极小或极大，用于检验假设是否仍然成立）。数据值侧要覆盖：全零/常量（暴露分支与规约的退化路径）、大幅值（暴露溢出与精度路径）、随机（暴露 bank 访问模式的真实分布）、以及结构化稀疏或对角占优（暴露特定访存模式）。

一个具体机制：bank conflict 类假设只有在 shared memory 访问地址呈现特定步长时才会显形。若输入数据全为常量，编译器可能把某些访存折叠掉，微实验改 padding 后指标纹丝不动，agent 得到“否”的结论，而真实负载下 conflict 确实存在。这就是数据值分布设置不当导致的假阴性。正确做法是让每个微实验的输入同时包含一个“能触发该假设”的值分布，并在问题记录中显式标注本次实验用的是哪一档输入，避免结论跨分布误用。

代价有两面。计算侧：为覆盖 shape 与值分布的笛卡尔积，微实验次数上升，编译与运行时间成倍增加；若每个点都跑完整正确性校验，token 与墙钟成本进一步放大。正确性侧：某些值分布会触发参考实现的慢路径或数值不稳定，使 oracle 本身成为瓶颈，甚至让“正确”判定依赖于容差设定。工程判断是分层采样：先用少量典型点做假设筛选，只在假设被初步证实后才在边界点与退化点上做确认实验，把昂贵的全分布验证留到 accept 之后。

四 · 指标计算：从原始计数到可回答问题的量

NCU 给出的原始计数不能直接喂给 agent 做判断，必须折算成与假设一一对应的量。诊断式优化的指标设计原则是：每个可证伪问题都应对应一个可计算的判别量，且该量的变化方向在假设成立时是确定的。例如“是否 shared memory bank conflict 导致 stall”对应的是 shared memory 访问的 conflict 次数与 wavefront 数之比；“是否 occupancy 受限”对应的是 achieved occupancy 与 theoretical occupancy 的差；“是否 pipeline 深度不足”对应的是 memory pipe 的 stall 占比与 L2 命中率的同时变化。把这些量写成判别式，agent 才能在实验后给出“是/否/部分”而非模糊描述。

指标计算必须处理归一化与可比性。绝对计数随 shape 变化，跨实验不可比；应折算为每指令、每字节或每 cycle 的比率。同时要区分“症状指标”与“根因指标”：stall 占比是症状，bank conflict 计数是根因；前者用于发现问题，后者用于确认假设。若只用症状指标，agent 会在多个 stall 原因之间反复横跳，无法收敛。一个具体例子：某 reduce kernel 的 stall 占比高，agent 先假设是 memory latency，微实验加深 pipeline 后 stall 占比下降但总时延未降，说明症状缓解而根因未除；随后用根因指标（shared memory conflict 计数）确认真正瓶颈在规约阶段的 bank 冲突，改 padding 后时延才出现显著 Δ。

代价在于指标采集本身。逐实验开启全套 NCU 采集会带来可观的 replay 开销与 kernel 重放次数，单次微实验的墙钟时间可能数倍于纯计时；若指标维度过多，agent 读回的 token 量也随之膨胀，挤占问题生成与代码修改的上下文预算。工程折中是分两级采集：筛选阶段只采少量根因指标，确认阶段才开全套；并把指标折算成判别式后再回灌，减少原始计数的 token 占用。

五 · 负载不对时会发生什么：三类失效模式

第一类是信号淹没。负载被 launch 开销或 host 同步主导时，单变量微实验的效应量低于测量噪声，Δ 符号随机，agent 的问题库被噪声污染。表现为多轮迭代后性能停滞且诊断轨迹自相矛盾——同一假设在不同轮次得到相反结论。这类失效的代价是整条诊断轨迹不可用于 SFT，因为其中的“证据”是伪证据。

第二类是假设不可达。负载的瓶颈根因不在 agent 可提问的候选集内（例如瓶颈在 host 侧数据准备、在框架的 layout 转换、在 kernel 间的同步），agent 会持续提出微架构层面的问题并全部得到“否”，然后转向盲目改代码。这正好回到问题定义中的失效路径：缺乏对瓶颈的显式提问与假设检验，修改与真实瓶颈不匹配。代价是轮次预算被耗尽而性能无改善，且问题库被写入一批无效假设，污染后续任务的先验。

第三类是基线漂移导致的假接受。当基线本身在同一轮内被隐式改变（例如编译选项、shape、输入分布未锁定），Δ 反映的是基线变化而非优化效果，agent 会接受一个实际无收益甚至有害的修改。这类失效最危险，因为它会累积：连续几次假接受后，绝对性能相对锚点反而倒退，而诊断流程仍报告“瓶颈逐步消除”。防御手段是把基线锁定写进实验协议，任何基线变更都必须作为独立变量重新走一遍假设-实验闭环，而不是混入当前轮次。

一个具体例子：某 GEMM 诊断任务中，agent 在未锁定输入分布的情况下比较两次实验，第二次因随机数据恰好落在更友好的 bank 访问模式上而取得 Δ，被判定为 swizzle 修改有效；后续在结构化数据上复测时收益消失。代价是若干轮编译与验证时间被浪费，且该错误结论进入了问题库，使后续同类任务优先尝试无效的 swizzle 方向。

六 · 配方固化：把负载与评测写成可复用的实验合约

要让诊断式优化在多任务间可迁移，负载与评测配方必须固化为机器可读的合约，而不是散落在 prompt 里的自然语言描述。合约至少包含：shape 采样清单及其分层标签、数据值分布档位、基线定义（含编译选项与测量协议）、指标判别式及其阈值、噪声带估计方法、以及每个假设与判别量的映射表。agent 在提问时从映射表中取判别量，在实验后按合约计算 Δ 并对照噪声带，接受判定完全由合约给出而非模型自述。

合约化的直接收益是消除“负载不对”的三类失效：信号淹没被噪声带条款拦截，假设不可达被映射表的完备性检查暴露（若某假设在映射表中无对应判别量，说明该负载不支持此假设），基线漂移被基线锁定条款阻止。代价是前期工程投入：为每个算子族编写合约需要人工确定判别式与阈值，且合约随硬件代际需要维护。另一个代价是灵活性下降——合约过严会把有意义的探索性实验判为无效，过松则退化为无约束搜索。

工程判断落在合约的粒度上：按算子族而非按单个 shape 编写合约，shape 清单作为合约的参数而非合约本身；判别式写成比率形式以跨 shape 可比；阈值用噪声带的倍数表达而非绝对数值，使合约在硬件迁移时只需重估噪声带。这样一份合约可以同时服务诊断式优化的提问阶段与接受阶段，把“负载是否合适”从事后诊断变成事前准入，避免 agent 在一个注定无法归因的负载上消耗轮次预算。

配方错位：诊断闭环在错误负载上的四种失效

假设—实验闭环的成立前提是：NCU/SASS 指标确实刻画了目标负载的真实瓶颈。一旦评测配方与部署负载错位，agent 会围绕一个不存在的瓶颈提出可证伪问题，微实验回答得再干净，结论也只对错误负载有效。最典型的失效是 shape 与输入分布错位：微实验常用固定 tile、固定 dtype、固定 batch 做单变量对照，而生产端是动态 shape、长尾分布、稀疏或极端值输入。此时 bank conflict 假设在评测 shape 上被证实，换到真实 shape 却因 occupancy 与寄存器压力变化而不再成立，优化动作被写进 kernel 后反而拉低端到端吞吐。代价直接体现在轮次预算上：每轮多出的提问与 1–3 个微实验都要编译、跑正确性、采集指标，轮次成本上升，预算紧张时不如直接搜索；而配方错位让这些开销全部沉没。

基线选择是第二个边界。若基线取的是未调优的朴素实现，$$\Delta_{\text{opt}}=\frac{T_{\text{after}}-T_{\text{before}}}{T_{\text{before}}}$$ 很容易通过，agent 会把“打败弱基线”误判为瓶颈消除，停止提问；若基线取的是厂商库或高度调优版本，$$\Delta_{\text{opt}}<-\epsilon\ \land\ \text{correct}$$ 的接受条件又过于苛刻，多轮迭代边际收益迅速归零，诊断轨迹退化为无效改动序列。正确做法是让基线、评测 shape 与部署 shape 同源，并在问题库里显式记录“该结论仅在何种 shape/硬件下成立”，否则跨配方复用结论就是隐性错误。

错位维度表现系统代价
shape/分布微实验结论不可迁移轮次预算沉没、编译时间浪费
基线强度假阳性收敛或过早停滞token 与迭代次数上升
指标口径只看 kernel 时延不看端到端带宽/显存收益被 launch 开销抵消

指标口径错位同样致命：微实验以单 kernel 时延为回答依据，而生产收益取决于端到端时延、显存峰值与带宽占用。改 swizzle 降低 stall 却抬高 shared memory 用量、压低 occupancy，单 kernel 变快而端到端因并发度下降变慢；加 padding 消除 bank conflict 却增加拷贝带宽。问题质量还依赖模型对 GPU 微架构的理解，问题提错会把闭环引向错误优化方向，此时单变量微实验越严谨，错误结论越可信。工程判断是：配方先于闭环——shape、基线、指标三者与部署对齐之前，不应启动假设—实验循环。
