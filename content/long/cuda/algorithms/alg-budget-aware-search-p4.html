一 · 负载画像：先决定“值不值得搜”，再决定“怎么搜”

预算感知搜索的第一道成本不在 GPU，而在判断。一个候选池里往往混着三类负载：结构性可优化（访存模式有明显冗余、tile 与 shape 不匹配、occupancy 被人为压低）、已接近硬件上限（再搜也只能在噪声内浮动）、本质不适合该硬件（算子形态与 SM 资源、寄存器预算、共享内存容量冲突）。把后两类送进细粒度 NCU/SASS 调优循环，是把最贵的预算烧在最不可能产生增益的地方。因此负载筛选要先于候选生成：对每个待搜算子，用一次廉价试跑估计其 SOL 距离，若实测时延已贴近该 shape 下的 roofline 上界（归一评分口径见 Roofline/SOL 归一评分一节），则该算子应被标记为“低搜索价值”，只保留极少数候选做验证性编译，而不是按默认配额铺开。

适合进入 coarse-to-fine 的负载有共同特征：存在多个可参数化的自由度（tile 尺寸、线程块形状、数据布局、流水深度、向量化宽度），且这些自由度对性能的影响是非单调、跨 shape 变化的。典型的如 GEMM 类（M/N/K 三维自由度与 split-K 策略耦合）、归约与 softmax 类（行长度与 warp 内归约粒度耦合）、卷积（implicit GEMM 的 tile 与 padding 交互）、attention（序列长度分块与 head 维度）。反之，逐元素算子（elementwise）的自由度基本只剩向量化宽度与 grid 映射，粗筛一次即可定论，不值得分配多轮预算。

硬件侧要区分“先验可迁移”与“先验不可迁移”。同一架构代际内（SM 数量、共享内存容量、寄存器文件规模相近），静态特征打分器的先验基本可用；跨代际时，占用率估计与 tile 可行性判断会系统性偏移——一个在较小 SM 上最优的 tile，在大 SM 上可能因 wave quantization 反而劣化。这里的代价是明确的：先验失准会让粗筛错误淘汰好候选，而这类错误在后续轮次中不可恢复，因为候选已被移出预算池。工程上的对冲手段是给粗筛保留一个“幸存者配额”：无论打分多低，每轮强制保留少量候选进入快速编译阶段，用真实测量而非静态估计做二次裁决。

二 · 基线选择：锚点错了，整条搜索曲线都错

基线不是“随便找个能跑的版本”，它决定了搜索的收益度量与终止条件。工程上应区分三层锚点：参考实现锚点（框架自带 kernel 或朴素 CUDA 实现，用于确认正确性与量级）、编译基线锚点（编译器自动调优产物，如带 autotune 的库调用，用于衡量“搜索是否真的超过了编译器”）、硬件上界锚点（roofline 或 SOL 估计，用于判断剩余空间）。三层缺一不可：只有参考实现会让搜索误以为小幅改进即为成功；只有硬件上界则无法判断候选是否已越过编译器这条现实基线。TF32/编译基线锚定的具体口径不在本节展开，此处只强调基线必须与候选在同一输入分布、同一计时方法、同一预热策略下测量，否则差值里混入了测量偏差。

基线选择的常见错误是把“最快的历史 kernel”当基线。这会让搜索目标变成“打败自己上一轮的产物”，收益曲线迅速扁平化，且一旦某轮出现测量噪声导致的虚假最优，后续所有候选都被迫与一个不可复现的锚点比较。正确做法是固定一个可复现的外部锚点作为分母，把搜索产物相对该锚点的加速比作为主指标，同时记录相对上一轮最优的自增益作为收敛信号。

代价体现在预算分配上：基线测量本身要占用 GPU 时间。若对每个 shape 都跑完整基线，粗筛阶段的时间开销会挤压细粒度调优的预算。折中方案是基线只测一次并缓存，且缓存键必须包含 shape、dtype、硬件标识与驱动/编译版本——任一变化都使缓存失效。这个缓存失效判断本身是廉价的，但它避免了用过期基线做出错误的“已超越编译器”判断。

三 · 输入分布：shape 采样决定了搜索在优化谁

kernel 性能对 shape 极度敏感，而 agentic 搜索的候选评价又必须落到具体 shape 上。若输入分布设置不当，搜索会收敛到“在采样到的 shape 上最快”的 kernel，而非“在目标工作负载上最快”的 kernel。这与隐藏 shape 分布抽样的防过拟合目的不同：本节关心的是训练/搜索阶段可见的 shape 集合是否覆盖了真实部署的形态。工程做法是把 shape 分成三档：核心档（部署中出现频率最高的几个 shape，占评价权重主体）、边界档（极端小 shape 与极端大 shape，用于暴露 occupancy 骤降、grid 不足、寄存器溢出等问题）、扰动档（在核心档附近做非对齐长度、奇偶维度扰动，检验候选对非整除 tile 的处理）。

分布设定的一个具体机制是按权重采样而非均匀采样。设核心档 shape 集合为 $S_c$，边界档为 $S_b$，则单轮评价的期望时延可写为加权和，权重反映部署频率。均匀采样会让一个罕见的大 shape 主导评分，把预算推向只在该 shape 上有效的候选。更严重的是，均匀采样下粗筛的小 shape 试跑与大 shape 细调之间存在系统性偏差：小 shape 上 occupancy 充足、访存延迟被隐藏，候选看起来都不错；切到大 shape 才暴露共享内存 bank 冲突或寄存器压力导致的占用率坍塌。这正是粗筛漏检的根源，代价是好候选在粗筛被误杀，或劣质候选在细调阶段才被发现，浪费整轮 NCU 采集。

因此粗筛阶段的小规模试跑必须至少包含一个边界档 shape 的快速测量，哪怕只测单次时延、不做完整 profile。这个额外测量的成本是几次 kernel launch 的时间，相对于一次完整 NCU 采集可以忽略，但它把“大 shape 才暴露的瓶颈”提前到了淘汰决策之前。输入分布的另一个维度是数据值分布：对于含分支或数据依赖的 kernel（如稀疏操作、条件归约），全零或全随机的输入可能走到与真实数据不同的执行路径，导致测得的时延不代表部署表现。此时应在评价配方中固定一组覆盖典型值域的输入张量，并在正确性校验中复用同一组，避免性能与正确性用不同数据各测一套。

四 · 指标计算：单点时延不够，要看分布与稳定性

把“一次测量”当指标是预算感知搜索里最隐蔽的浪费来源。GPU 时延测量受时钟频率波动、缓存状态、并发干扰影响，单次采样方差足以让两个真实差距很小的候选排序颠倒，进而让 bandit 后验被噪声污染。评价配方应规定：每个候选在每个 shape 上做预热若干次后取多次测量的中位数或截尾均值，并同时记录离散度。离散度本身是有用信号——一个方差极大的候选往往意味着其对缓存状态或调度敏感，在部署中不可靠，即便中位数好看也应降权。

指标体系的层次应与搜索阶段匹配。粗筛阶段只需一个廉价标量：小 shape 单次时延或相对基线的粗加速比，用于排序与淘汰。细调阶段则需要可归因的指标组合：实测时延、达到的 SOL 比例、占用率、以及从 NCU 回灌的关键 stall 原因分布（回灌机制见 NCU 指标回灌一节）。这里的代价是采集开销：完整 NCU 采集一次可能比 kernel 本身执行慢一个数量级以上，因此细调阶段的 profile 必须按预算配额触发，而不是每个候选每轮都采。合理的做法是只在候选进入预算分配的前若干名、且其潜力后验发生显著更新时才触发完整采集。

指标计算还要防止“指标替代目标”。例如用指令数或 occupancy 作为代理指标排序，会奖励那些降低了指令数但引入了额外同步或访存的候选。代理指标只应参与粗筛打分，最终排序必须回到实测时延与 SOL 比例。一个具体例子：某候选通过增大 tile 降低了总指令数，静态打分上升，但共享内存占用翻倍导致同时驻留的 block 数下降，实测时延反而变差——若细调阶段仍以指令数为主指标，这个候选会被错误地继续加预算。

五 · 负载错配的三种典型失效与预算后果

失效一：shape 覆盖不足导致过拟合。搜索在少数几个对齐良好的 shape 上找到高度特化的 tile 配置，一旦部署 shape 出现非整除维度，该配置退化到需要大量边界判断，时延反超基线。预算后果是：前期投入的细调轮次全部作废，且由于候选已被标记为“最优”，后续轮次不再探索其他方向，搜索提前收敛到错误解。对冲手段是在评价配方中强制保留边界档与扰动档的权重下限，使任何候选都必须在这两档上通过最低性能门槛才能进入细调。

失效二：基线不可比导致收益虚高。候选与基线在不同预热策略或不同计时口径下测量，报告出可观的加速比，但复测时消失。这类错误不会立刻暴露，却会污染 bandit 后验，让预算持续流向一个实际无增益的方向。代价是整条搜索轨迹的可信度崩塌——一旦发现某轮收益是测量假象，此前所有基于该后验的预算分配决策都需要重新审视。

失效三：硬件先验迁移失败导致过早淘汰。跨架构时静态打分器沿用旧先验，把在新硬件上本应占优的候选（例如因共享内存容量更大而可行的更大 tile）判为低潜力并提前终止。由于粗筛淘汰是不可逆的，这类失效的代价是搜索空间被系统性裁剪，且不会在指标上留下明显异常——搜索照常收敛，只是收敛到了一个次优解。检测手段是对比“粗筛淘汰的候选”与“幸存候选”在少量 shape 上的实测分布，若被淘汰组中存在实测优于幸存组中位数的个体，说明先验失准，需要放宽幸存者配额。

这三种失效的共同点是：它们都不表现为“搜索跑不动”，而表现为“搜索跑得很顺但结果不对”。预算感知机制本身无法识别这类错误，因为它的输入（潜力后验）已经被错误的评价配方污染。因此评价配方的校验必须独立于搜索循环，作为离线审计环节存在——这与变异测试审计 checker 的思路一致，只是审计对象从正确性 checker 换成了性能评价配方。

六 · 配方参数化：把评价配方当作可搜索对象的一部分

评价配方不应是写死的常量集合，而应作为搜索配置的一部分被显式参数化并记录：shape 采样权重、每档测量次数、预热次数、计时口径（是否含 launch 开销）、基线缓存键、profile 触发阈值。这些参数一旦变动，历史后验的可比性就被破坏，因此每次配方变更都应使相关候选的后验重置或降权。工程上把这组参数连同候选池、预算分配记录一起写入证据链，使得任何一次“某候选被选中”的决策都可回溯到当时的配方状态。

参数化带来的直接代价是配置空间膨胀：配方参数本身也有取值选择，若不加约束，调配方会变成另一场搜索。约束方式是分层固定——核心档 shape 集合与计时口径在项目级固定，不随单次搜索变动；每档测量次数与 profile 触发阈值可在小范围内按算子类型调整。这样既保留了针对不同算子形态的适配空间，又避免了配方漂移导致的后验不可比。

一个具体的工程判断落在预算分配的入口处：粗筛打分器的输出必须与评价配方的置信度联合使用。若某候选的粗筛测量只覆盖了核心档且样本数少，其打分应被折扣后再参与预算分配，而不是直接作为潜力估计。这与前文的分配公式在结构上一致——潜力估计的可信度应体现在分配权重里，而非仅在事后筛选。负载与评测配方的设计，本质上是在决定“哪些证据值得被相信”，而预算感知搜索的每一步分配，都是在这个信任结构上做的一次下注。
