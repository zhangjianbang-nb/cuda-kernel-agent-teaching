一 · 负载画像：什么样的模型/算子/shape 才值得上这道门

Batch 不变性门不是通用正确性检查，它只在“同一逻辑输入、不同物理批次”这一维度上做文章。因此负载筛选的第一条判据是：kernel 的语义是否与 batch 维度解耦。注意力里的 softmax、LayerNorm/RMSNorm 的归约、MoE 的 token 路由打分、采样 logits 的 top-k、以及任何带 split-K 或动态 tile 划分的 GEMM，都属于“逻辑上每个 token 独立、物理上却被 batch 改变归约树”的高危族。反过来，逐元素算子（elementwise、简单激活）天然满足不变性，把它塞进门控只会白烧两次 launch 的时延。

第二条判据是 shape 的“归约轴长度”与“批次轴长度”之比。设归约轴为 K、批次轴为 B，当 K 大到需要 split-K（例如 K 跨多个 CTA 分段累加再合并），归约顺序随 B 变化而重排的概率显著上升；当 K 很小而 B 很大，kernel 更可能走“每 token 一个 warp”的路径，不变性反而稳定。所以负载配方应优先覆盖 K 处于 split-K 阈值附近的 shape——这是门控最可能抓到东西的区间，也是单 batch 测试最瞎的区间。

第三条是硬件。不同 SM 数量、不同 shared memory 容量会改变 tile 选择与 occupancy 驱动的启发式，同一份 kernel 在 A 卡上 batch 不变、在 B 卡上因 tile 变小而引入新的分段归约，是很常见的。因此配方里硬件维度不能只写“一块 GPU”，而要标注 SM 数与 L2 规模这两个直接决定 tile/split 决策的量。至于模型层面，decoder-only LLM 的 prefill（大 B、长序列）与 decode（B 抖动、K 固定）应分开建负载：decode 阶段 batch 是连续变化的，恰恰是训练/推理可复现性最脆弱的地方。

代价在这里体现为覆盖面与成本的权衡：每增加一个 shape 组合，门控就要多跑一次 batch=B 的前向。若一个算子族铺 20 个 shape、每个 shape 两次运行，按单次 kernel 数十微秒计，单轮门控的额外时延在毫秒量级——相对一次 RL 迭代的采样开销可以忽略，但相对“只跑一次单 batch 正确性”则是翻倍。这就是为什么必须先做负载筛选，而不是无差别全量门控。

二 · 基线选择：单 batch 参考、fp64 oracle 与“同 kernel 自比”的分工

门控里的“基线”有三个候选，职责必须分清。第一类是 batch=1 的同 kernel 输出，它只回答“同一实现是否随 B 漂移”，不回答“实现是否正确”，因此不能替代正确性 oracle。第二类是 fp64（或高精度）参考实现，它回答数值正确性，但对归约顺序不敏感——fp64 累加几乎消除了重排带来的舍入差，所以拿它当不变性基线会系统性放过真实漂移。第三类是 同 kernel、同 B、不同调度配置（例如强制关闭 split-K）的输出，用于定位漂移来源，属于诊断基线而非门控基线。

正确的配方是：正确性用 fp64 参考（其 checker 与变异审计在别处展开，此处只作指路），不变性用 batch=1 的同 kernel 自比。两者串联，先过正确性再算 ΔBI，避免把一个本来就错的 kernel 判成“不变性失败”而污染诊断信息。基线锚定还要固定编译选项与数学库路径：TF32 开关、fast-math、cuBLAS 版本切换都会同时改变 batch=1 与 batch=B 的结果，若两端锚定不一致，测出的 diff 是编译差异而非调度差异。

$$\Delta_{\text{BI}}=\max_i\left|y_i^{(B=1)}-y_i^{(B)}\right|,\quad \text{Invariant}=\mathbb{1}\left[\Delta_{\text{BI}}\le \tau_{\text{BI}}\right],\quad R_{\text{final}}=R\cdot\text{Invariant}$$

阈值 τBI 的设定必须与数据精度挂钩：fp16 输出的 ulp 量级远大于 fp32，用同一个绝对阈值会要么误杀 fp16 的合法重排、要么放过 fp32 的真实漂移。工程做法是按 dtype 给相对阈值，并对 max-abs 与相对误差同时设限——只卡绝对差会在输出幅值大的 token 上失效。这里的具体代价是：阈值越紧，误杀率越高，被误杀的 kernel 奖励归零，等于把一次本可收敛的优化轮次直接扔掉；阈值越松，门控退化为装饰。一个可操作的折中是先用诊断基线（关闭 split-K 的版本）测出该算子族的“合法重排噪声地板”，再把 τBI 定在地板之上一个可解释的倍数。

三 · 输入分布：逻辑等价构造与 padding 的副作用

构造逻辑等价输入是这道门最容易做错的一步。做法是：取同一段真实序列，一份单独放在 batch=1 的槽位 0，另一份放在 batch=B 的某个槽位，其余 B−1 个槽位用 padding 填充。关键约束是 padding 不能参与归约统计——若 kernel 对 padding 位置也做 softmax 分母累加或 LayerNorm 均值，batch=B 的统计量就被污染，测出的 diff 是输入构造错误而非 kernel 漂移。因此配方要求：padding 值、attention mask、以及 kernel 对 mask 的处理路径三者一致，且目标 token 的输出提取位置必须由逻辑索引而非物理偏移定位。

输入分布的第二个维度是数值动态范围。全 1 或全 0 的合成输入会让归约树的重排差异退化到零，门控形同虚设；而极端长尾分布（少量超大值 + 大量接近零）会把 max-abs diff 放大到由单个元素主导，掩盖整体漂移。配方应至少覆盖三档：真实语料采样、对数均匀随机、以及带离群值的混合分布。每档都要记录目标位置的输出向量长度，因为逐元素比对的计算量与输出维度成正比——一个 hidden 维度 8192 的 norm 输出，比对本身是 8192 次减法加归约，相对两次 kernel 运行的时延仍可忽略，但对超长序列的 logits（词表数万）则不可忽视，此时应改为按 top-k 索引比对而非全量逐元素。

padding 带来的另一项代价在时延维度上：batch=B 的实际计算量因 padding 而膨胀，两次运行的时延不可直接比较，这一点决定了门控只能用于正确性判定，不能顺手拿来做性能评分。若把门控时延当性能信号回灌给搜索，会系统性奖励“padding 处理得快”而非“真实负载快”，这是配方必须显式禁止的用法。具体例子：一个 B=8 的门控运行，其中 7 个槽位是 padding，kernel 的有效吞吐只有真实 batch=8 的八分之一，任何基于这次运行的 SOL 归一都会失真。

四 · 指标计算：max-abs、相对误差与诊断定位的联合判读

指标不是单一标量。ΔBI 给出最坏元素，但工程上还需要三个辅助量：漂移元素的占比（多少 token 受影响）、漂移是否集中在特定 tile 边界（用逻辑索引模 tile 宽度做分组统计）、以及漂移随 B 的单调性（B=2、4、8 逐级测，看 diff 是否随分段数跳变）。这三者联合起来才能把“归约顺序重排”与“split-K 分段数变化”区分开：前者通常表现为弥散的小幅漂移，后者表现为在分段边界处跳变的中等漂移。

伪代码思路如下：对每个候选 B，运行 kernel 两次（B=1 与 B），提取逻辑索引集合 S 上的输出，计算逐元素差，再按 tile 宽度分组求组内 max；若某组的 max 显著高于其他组，标记该组对应的 tile 边界为疑似来源，并把该诊断信息写入回归集条目。诊断信息的价值在于：下一轮搜索若在同一 tile 配置上再次触发，可以直接跳过而非重跑两次 kernel，节省的是每轮的固定门控开销。

指标回答的问题典型代价
max-abs diff最坏元素漂移多大与输出维度成正比的比对时延
漂移元素占比影响面是局部还是全局额外一次归约统计
tile 分组 max是否集中在分段边界需要知道 tile 宽度，跨实现不可移植
B 逐级扫描漂移是否随分段数跳变门控运行次数从 2 次涨到 log B 次

指标计算的正确性代价在于分组统计依赖 tile 宽度这一实现细节：不同 kernel 的 tile 划分不同，同一套分组逻辑无法跨实现复用，若强行复用会把“分组不匹配”误报成“边界漂移”。因此配方建议把 tile 分组做成可选诊断层，门控主判据仍只用 ΔBI 与相对误差，保证主判据的实现无关性。

五 · 负载不对时会发生什么：误杀、漏杀与奖励污染

负载配方错了，后果分三类。第一类是误杀：把本身允许非确定性的算子（atomicAdd 归约、基于原子累加的分段合并）纳入门控，它们在不同 B 下本就产生合法漂移，门控判失败、奖励乘零，搜索被迫绕开这些算子族，等于人为缩窄了可优化空间。缓解手段是按算子类型维护豁免名单，名单本身要进版本控制并随 kernel 族扩展而审计，否则豁免会变成后门。

第二类是漏杀：shape 选得太温和，K 远离 split-K 阈值、B 只取 2 和 4，kernel 恰好走同一条调度路径，门控通过，但部署到真实 decode 的连续 batch 变化下立刻漂移。这类漏杀的代价不在单轮，而在回归集：没有失败样本入库，后续轮次的搜索不会学到“这个 tile 配置危险”，同一个错误会被反复引入。因此配方要求 shape 覆盖必须包含至少一个“临界 K”与一个“大 B”组合，宁可多花一次运行。

第三类是奖励污染：把 padding 膨胀后的时延或吞吐混入评分，或把不变性判定与性能评分耦合在同一标量里，会让搜索学到与部署收益无关的策略。公式 Rfinal=R·Invariant 的乘法结构本身是对的——不变性是硬门——但前提是 R 必须来自真实负载的性能测量，而非门控运行。具体例子：某轮搜索产出一个在 B=1 上极快、在 B=8 上因 tile 退化而慢的 kernel，若 R 取自门控的 B=8 padding 运行，该 kernel 会因“计算量小”而获得虚高奖励，同时不变性门又可能因 padding 污染而误判，两个错误叠加，搜索方向彻底偏航。

三类后果的共同根源是：门控的负载配方与部署负载分布不一致。工程判断上，配方的第一优先级不是“覆盖尽可能多的 shape”，而是“覆盖部署时 batch 真实会取到的值域与临界归约长度”，其余组合作为诊断层按需开启。这决定了门控的固定成本：主判据两次运行、诊断层按需展开，单轮开销可控，而漏杀带来的回归集缺失是不可逆的。

负载选型与评测配方：门控在哪些负载上成立、在哪里失效

Batch 不变性门的判定对象是“同一逻辑输入在不同 batch 维度下的逐元素输出”，因此负载选型的第一条硬约束是：算子必须存在一个可被单独定位的逻辑位置，且该位置的输出不依赖 batch 内其他样本的语义。注意力、LayerNorm/RMSNorm、softmax、reduce 类算子天然满足；而依赖跨样本统计量的算子（如 batch 维上的归约、跨样本的排序或 top-k）在定义上就与不变性冲突，不应纳入门控负载。第二类约束来自 shape：门控要求 batch=B 的输入由 batch=1 的同一序列加 padding 构成，若 kernel 对 padding 位置做了 mask 之外的优化（例如按有效长度动态切 tile、按 batch 内最大长度选 tile 尺寸），则 B=1 与 B 的实际 tile 划分本就不同，比对结果反映的是调度差异而非数值缺陷，需要把这类 shape 敏感性单独标注。硬件侧，split-K 与动态 tile 的触发条件与 SM 数量、每 SM 的寄存器预算强相关，同一 kernel 在小卡上不分裂、在大卡上分裂，因此门控必须在目标部署硬件上跑，跨卡复用的通过记录不可信。

基线选择决定门控的判别力。正确做法是以 batch=1 的 kernel 输出为基线，而不是以 PyTorch eager 或某个参考实现为基线——后者会把框架自身的归约顺序差异混入 $\Delta_{\text{BI}}$，使门控失去针对性。输入分布上，需要覆盖三类：短序列（触发小 tile、单次归约）、长序列（触发 split-K 与多级归约）、以及 padding 比例极端的构造（B 远大于 1 但有效位置极少），因为 padding 会改变实际计算量，使 batch=B 的时延不可直接与 B=1 比较，只能用于正确性门控而不能用于性能收益核算。指标计算即

$$\Delta_{\text{BI}}=\max_i\left|y_i^{(B=1)}-y_i^{(B)}\right|,\quad \text{Invariant}=\mathbb{1}\left[\Delta_{\text{BI}}\le \tau_{\text{BI}}\right],\quad R_{\text{final}}=R\cdot\text{Invariant}$$
其中 $\tau_{\text{BI}}$ 需按数据类型与累加精度设定：fp32 累加下取相对误差量级，fp16/bf16 累加则必须放宽并同时记录相对误差，否则门控会把正常的低精度舍入差异判成缺陷。比对只取目标位置，padding 位置的输出不参与，避免 mask 实现差异污染判定。

负载不对时的失效形态有三种，代价各不相同。其一是误杀：对本身允许非确定性的算子（atomicAdd 归约、跨 block 的原子累加）施加门控，$\text{Invariant}$ 恒为 0，$R_{\text{final}}$ 被乘零，整轮 RL 奖励信号被抹平，策略会把“正确但非确定”的优化路径全部判负——这需要按算子类型维护豁免名单，把 atomic 类归约排除在门控之外或改用确定性变体。其二是漏杀：若只测短序列与小 batch，split-K 与动态 tile 根本不被触发，门控通过但部署后在长序列上出现 batch 相关漂移，回归集里没有对应样本，后续轮次会反复复发。其三是成本错配：门控本身是两次运行加一次逐元素比对，单次开销低，可嵌入每轮奖励计算；但若把门控扩展到全 shape 网格，运行次数随 shape 数线性增长，编译与运行时间会成为 RL 迭代的瓶颈，此时应按算子类型抽样而非穷举。工程判断上，门控的负载配方应写成“算子白名单 + shape 抽样表 + 硬件绑定 + 豁免名单”四元组，任何一项缺失都会让 $\text{Invariant}$ 的语义漂移。

负载特征门控适用性主要代价
注意力/归一化/softmax，短序列适用，触发单次归约两次运行 + 比对，开销低
长序列，触发 split-K适用，正是捕获目标B 侧 padding 改变计算量，时延不可比
atomicAdd 归约不适用，需豁免误杀导致奖励乘零
跨样本统计量算子定义冲突，排除判定无意义
