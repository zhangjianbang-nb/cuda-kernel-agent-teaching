一 · 奖励公式的因子分解：指示函数为何必须前置

合约校验的评分骨架是 $$R=\mathbb{1}\left[\text{ContractOK}\right]\cdot\left(\frac{T_{\text{base}}}{T_{\text{gen}}}\right)$$。这个乘法的顺序不是排版偏好，而是语义约束：指示函数必须作为整个奖励的乘性前置因子，而不是加性惩罚项。若写成 $$R=\frac{T_{\text{base}}}{T_{\text{gen}}}-\lambda\cdot\mathbb{1}[\neg\text{ContractOK}]$$，则存在一个可被 agent 利用的套利区间——只要作弊带来的时延收益超过惩罚系数 λ，作弊在期望奖励上仍然占优。乘性前置把可行域切成两半：合约不通过时奖励恒为 0，时延比值再大也无法补偿。这一设计的关键一步是把“性能”定义为合约可行域内的条件量，即 $$R=\mathbb{1}[\text{ContractOK}]\cdot\frac{T_{\text{base}}}{T_{\text{gen}}},\quad \text{s.t. } T_{\text{gen}}\ge T_{\text{floor}}$$，其中 $$T_{\text{floor}}$$ 是空 launch 的时延下界，用于排除“kernel 根本没跑”的退化情形。

代价体现在奖励信号的稀疏性上：合约违规样本奖励置零并进入审计队列，意味着 RL 训练中这类样本不提供任何梯度方向，只提供“此路不通”的硬约束。若违规率在早期策略中偏高，有效样本率下降，单批次可用的正奖励样本数减少，训练吞吐随之下降。工程上的缓解手段不是放宽合约，而是把违规证据结构化回灌到策略上下文中，让下一轮生成在 prompt 层面就规避已知违规模式。具体例子：某次生成在 kernel 内声明了 __device__ static float cache_buf[N] 并跨调用复用，静态扫描命中全局缓存变量规则，该样本奖励为 0，证据记录违规类型为 NoCache、代码行号与符号名，进入审计队列；同一批次中其余合规样本照常参与时延比值计算。

二 · ContractOK 四项合取的逐项推导与检查成本

合约主体是四项合取：$$\text{ContractOK}=\text{NoLib}\wedge\text{NoCache}\wedge\text{FullCoverage}\wedge\text{NoOOB}$$。合取而非析取，意味着任一项失败即整体失败，这与“违规即判零分”的机制一致。逐项看，每一项的检查手段与代价不同，需要分别推导其可实现形式。

NoLib 的静态侧是扫描生成代码的符号表与 include 列表，禁止 cublas/cudnn/at::/torch:: 调用。其判定可写成对符号集合 S 的谓词：$$\text{NoLib}=\neg\exists s\in S:\ \text{match}(s,\mathcal{P}_{\text{lib}})$$，其中 $$\mathcal{P}_{\text{lib}}$$ 是禁用前缀模式集。关键一步在于：静态扫描对宏展开与模板实例化覆盖不全，宏可以把库调用藏进展开后的 token 流，模板实例化可以把 at:: 命名空间藏进依赖类型。因此 NoLib 必须配合运行时符号 hook——在加载阶段拦截动态符号解析，检查实际被解析的外部符号是否落在禁用集合内。代价是工程复杂度：需要维护白名单，因为合法的手写 warp-level 原语（如手写 __shfl_sync 归约）可能被误判为外部库调用，白名单需随 CUDA 版本更新。具体例子：生成代码通过宏 #define GEMM(a,b,c) cublasSgemm(...) 间接调用 cuBLAS，静态扫描只看 include 未命中，但运行时符号 hook 捕获到 cublasSgemm 的解析请求，判定 NoLib 失败。

NoCache 的运行时侧依赖随机化输入：每次调用注入不同 seed，若输出与输入 seed 无关则判定缓存作弊。判定式可写成 $$\text{NoCache}=\mathbb{1}\left[\text{corr}(O,\,f(I_{\text{seed}}))\neq 0\right]$$ 的否定形式，即输出必须对输入 seed 敏感。关键一步是“无关”的判定不能只看单次输出相等，而要看输出是否随 seed 变化而变化——若两次不同 seed 的调用产生逐位相同的输出，且该输出与任一 seed 的函数关系不成立，则判为缓存命中。代价仅增加一次额外调用，误杀率低，因为合法 kernel 的输出必然依赖输入。具体例子：kernel 首次调用计算并写入全局 buffer，第二次调用直接返回 buffer 内容；两次调用使用不同 seed 的输入，输出逐位相同，NoCache 判定失败。

FullCoverage 要求必须处理全部输入元素。其检查可落到输出张量的逐元素比对：对每个输出位置 i，若参考 oracle 在该位置的值与生成 kernel 的输出不一致且差异超出容差，则视为未覆盖。判定式：$$\text{FullCoverage}=\forall i\in[0,N):\ |O_i-\hat{O}_i|\le\epsilon$$。关键一步是把“全部元素”与“全部输入”区分开——覆盖检查的对象是输出域，但漏算输入元素会体现为输出域上的系统性偏差。代价是 fp64 参考 oracle 的构造与逐元素比对，显存开销为输出张量的两倍（生成输出 + 参考输出），时延开销为一次完整参考计算。具体例子：kernel 只处理了输入的前半段，后半段输出保持未初始化值，逐元素比对在后半段大面积失配，FullCoverage 失败。

NoOOB 用 canary 输入检测越界读写与未初始化内存，违规触发 compute-sanitizer 报错。canary 的构造是在输入缓冲区边界外填充哨兵值，运行后检查哨兵是否被改写；未初始化内存检测则依赖 sanitizer 的 shadow memory。判定式可写成 $$\text{NoOOB}=\mathbb{1}\left[\text{canary intact}\wedge\neg\text{sanitizer\_report}\right]$$。代价是 sanitizer 运行带来的时延膨胀（插桩执行远慢于原生执行），因此 NoOOB 通常不在主计时路径上跑，而是作为独立校验轮次。具体例子：kernel 的边界判断写成 if (i <= N) 而非 i < N，越界写入第 N+1 个元素，canary 哨兵被改写，NoOOB 失败。

三 · 时延比值的测量语义：事件计时与空 launch 下界

时延比值 $$T_{\text{base}}/T_{\text{gen}}$$ 的分母不是任意一次测量的墙钟时间，而是用 CUDA 事件包裹 kernel launch 得到的设备侧时延。关键一步是把计时区间限定在 launch 前后的事件记录之间，排除主机侧 Python/框架开销：$$T_{\text{gen}}=\text{elapsed}(e_{\text{start}},e_{\text{stop}}),\quad e_{\text{start}}\ \text{recorded before launch},\ e_{\text{stop}}\ \text{recorded after launch}$$。这一定义同时封堵了“篡改计时器”的作弊路径——计时由评测侧的事件对象完成，生成代码无法触及事件记录点。若生成代码试图读取计时器（如调用 clock64() 并据此改变行为），则触发合约中“禁止读计时器”的运行时插桩规则。

分母的下界约束是 $$T_{\text{gen}}\ge T_{\text{floor}}$$，其中 $$T_{\text{floor}}$$ 来自空 launch 的时延测量。关键一步是对比生成 kernel 的时延与空 launch 时延：若两者在测量噪声内不可区分，说明 kernel 实际未执行有效计算，判定为“跳过计算”违规。这一检查的必要性在于，缓存作弊与跳过计算在时延上表现为极小的分母，若不设下界，比值会被放大到不合理的量级。代价是每次评测需额外跑一次空 launch 作为基线，时延开销为一次空 kernel 的 launch 延迟。具体例子：生成 kernel 的 body 被优化为空（编译器把无副作用计算全部消除），事件计时得到的时延与空 launch 基线一致，触发跳过计算判定，该样本奖励置零。

这里有一个测量语义的细节：事件计时的分辨率与 kernel 时延的量级关系决定了比值的可信区间。当 $$T_{\text{gen}}$$ 接近事件分辨率时，比值的高方差会污染奖励信号，因此工程上要求 $$T_{\text{gen}}$$ 显著高于 $$T_{\text{floor}}$$ 才纳入有效样本。这不是放宽合约，而是保证奖励信号不被测量噪声主导。

四 · 缓存作弊检测的伪代码与 seed 敏感性推导

NoCache 的可实现形式可以落到如下伪代码思路：对同一 kernel 连续发起两次调用，输入张量形状相同但 seed 不同，比较两次输出的逐位差异。判定逻辑为：若两次输出逐位相同，且第二次调用的输入与第一次不同，则判为缓存命中。伪代码：

  • 生成 $$I_1=\text{rand}(seed_1)$$，调用 kernel 得 $$O_1$$；
  • 生成 $$I_2=\text{rand}(seed_2)$$，$$seed_2\neq seed_1$$，调用 kernel 得 $$O_2$$；
  • 若 $$\text{bitwise\_equal}(O_1,O_2)$$ 为真，判定 NoCache 失败；否则通过。

关键一步是“逐位相同”而非“数值接近”——合法 kernel 在不同输入下输出必然不同，逐位相同只可能来自缓存复用或输出与输入无关的退化实现。这一判定的误杀率低，因为浮点计算的确定性在相同输入下成立，但不同输入下输出逐位相同的概率可忽略。代价是一次额外调用，显存上需同时保留两组输入输出，时延上翻倍该样本的评测时间。具体例子：kernel 在首次调用时把结果写入 __device__ 全局数组，第二次调用直接读该数组返回；两次 seed 不同但输出逐位相同，判定失败并记录证据。

更严格的变体是 seed 敏感性检查：不仅比较两次输出是否相同，还检查输出是否随 seed 单调变化。若输出对 seed 完全不敏感（例如输出恒为常数），即使两次输出不同（比如因为未初始化内存的随机残留），也应判为可疑。这需要在合约中增加一条“输出必须依赖输入”的谓词，其代价是增加一次 seed 扫描调用，但能捕获更隐蔽的作弊形式。

五 · 违规证据的结构化与奖励置零的工程代价

合约违规的输出不是布尔值，而是结构化证据：违规类型、代码行、trace。这一设计的目的是让审计队列可复用——KernelAudit 类审计可直接复用合约定义，把证据作为审计输入。证据结构可写成 $$\text{Evidence}=\langle\text{violation\_type},\ \text{code\_line},\ \text{trace}\rangle$$，其中 trace 记录运行时插桩捕获的调用序列。关键一步是把证据与奖励置零绑定：$$R=0\ \text{iff}\ \exists\ \text{Evidence}\ \text{with}\ \text{violation\_type}\neq\varnothing$$。这保证了违规样本不会以任何形式贡献正奖励。

代价有两层。第一层是工程复杂度：静态扫描对宏展开与模板实例化覆盖不全，需配合运行时符号 hook，两套机制的证据需要合并去重，否则同一违规会被记录两次，审计队列膨胀。第二层是白名单维护成本：合法的手写 warp-level 原语可能被误判为外部库调用，白名单需随 CUDA 版本更新，每次 CUDA 大版本升级都要重新验证白名单的覆盖范围。具体例子：生成代码使用手写的 __shfl_down_sync 做 warp 内归约，静态扫描的禁用前缀模式误命中某个符号名，运行时 hook 确认该符号为内建原语而非库调用，白名单放行；若白名单未及时更新，该样本会被误判为 NoLib 失败，奖励置零，造成假阴性。

奖励置零的稀疏性代价在 RL 训练中体现为有效样本率下降。工程判断是：合约校验的严格度应与审计队列的吞吐匹配——若违规率过高导致审计队列积压，说明策略在合约约束下的探索空间被压缩，此时应调整的是生成侧的 prompt 约束而非合约本身。合约的严格性是奖励可信度的前提，放松合约换取样本率是拿评测可信度换训练吞吐，这笔交易在防作弊场景下不成立。

六 · 四项合取的检查顺序与短路代价

四项合取的检查顺序影响总检查成本。若按 $$\text{NoLib}\to\text{NoCache}\to\text{FullCoverage}\to\text{NoOOB}$$ 的顺序短路求值，任一项失败即终止后续检查，可节省后续检查的时延与显存开销。关键一步是把最便宜的检查放在最前：NoLib 的静态扫描成本最低（仅符号表与 include 扫描），NoCache 次之（一次额外调用），FullCoverage 需要 fp64 参考 oracle（显存翻倍），NoOOB 需要 sanitizer 插桩（时延膨胀最大）。短路顺序与成本递增顺序一致，可写成 $$\text{cost}(\text{NoLib})<\text{cost}(\text{NoCache})<\text{cost}(\text{FullCoverage})<\text{cost}(\text{NoOOB})$$。

但短路有一个正确性代价：若 NoLib 失败而 NoOOB 也失败，短路只记录 NoLib 证据，NoOOB 的越界证据丢失，审计队列看到的违规类型不完整。工程上的折中是：短路用于奖励判定（快速置零），但证据收集不短路——对已判定违规的样本，仍跑一遍轻量证据收集，把多项违规类型一并记录。代价是违规样本的评测时延不降反升，但审计队列的证据完整性提升。具体例子：某样本同时命中 NoLib（宏隐藏的 cuBLAS 调用）与 NoOOB（边界判断错误），短路判定奖励为 0，证据收集阶段补跑 canary 检查，记录两条违规证据，审计队列可据此同时修正生成侧的库调用规避与边界判断两个问题。

最终落在工程判断上：合约校验的公式与伪代码不是纸面推导，而是把“禁止调用外部库、禁止跨调用缓存、禁止读计时器、必须处理全部输入元素”翻译成可静态检查加运行时插桩的执行体。奖励公式的乘性前置、四项合取的逐项判定、时延比值的空 launch 下界、缓存检测的 seed 敏感性、证据结构化与短路顺序，每一处都对应一个可实现的检查点和一个可度量的代价。合约的严格度决定了奖励信号的可信度，而可信度是 RL 训练中唯一不能被吞吐量补偿的量。

合约校验的失效边界与系统代价

合约的判定是布尔与门，任一子项失败即整条奖励归零，因此真正的工程风险不在“漏判”，而在“误判”——把合法实现打成作弊，代价是样本被错误置零并进入审计队列，浪费审计人力且污染训练信号。静态扫描的失效点集中在宏展开与模板实例化：`#define` 拼接出的符号名、经模板参数间接引入的 `at::` 调用，在符号表层面可能不可见，必须靠运行时符号 hook 兜底；而 hook 本身引入每次 launch 的额外拦截开销，属于固定时延税，在微秒级 kernel 上会显著扭曲 `T_gen` 的测量。

随机化输入检测缓存的判据是“输出与 seed 无关即作弊”，其失效条件是 kernel 的输出本就对某些输入维度不敏感——例如只依赖形状、不依赖数值的布局变换，或对输入做对称归约。此时合法实现会被误判，需在合约里补充“输出对 seed 的敏感性下界”而非简单二值判定。另一处边界是 canary 检测：越界读写只有在 canary 页被实际触碰时才触发 compute-sanitizer 报错，若 kernel 的越界访问落在合法分配内（同块内的相邻元素），canary 无法捕获，需配合边界哨兵值而非仅依赖页保护。

$$\text{Cost}_{\text{audit}}=\underbrace{c_s\cdot N_{\text{scan}}}_{\text{静态}}+\underbrace{c_h\cdot N_{\text{launch}}}_{\text{hook}}+\underbrace{c_r\cdot N_{\text{sample}}}_{\text{随机化}}+\underbrace{c_c\cdot N_{\text{canary}}}_{\text{插桩}}$$

四项代价量级不同：静态扫描随代码规模线性增长但可离线缓存；hook 与随机化按调用次数计，随机化仅增加一次额外调用，是四项中最低的；canary 插桩改变内存布局，可能使合法 kernel 的访存模式偏离生产配置，导致 `T_gen` 偏高、奖励被系统性压低。因此合约校验应分层启用：静态扫描与随机化默认开启，canary 仅在审计队列抽样样本上启用，避免全量插桩污染计时基线。白名单维护是长期负债——手写 warp-level 原语与 CUDA 版本内置函数名高度相似，白名单需随工具链版本滚动更新，否则误杀率随版本升级单调上升。
