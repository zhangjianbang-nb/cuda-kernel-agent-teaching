一 · 事故现场：当 speedup 把两个不可比的世界拉到同一张表上

一支团队在 KernelBench 系评测里跑出了一批“漂亮”结果：某个融合 layernorm+matmul 的 kernel 相对 PyTorch 基线报出 3.1×，另一个纯 elementwise 的 kernel 报出 1.4×。评审按 speedup 排序，把 3.1× 的那个选为“本周最佳”，随后把它合入推理路径。上线后整条链路的端到端时延几乎没动，反而在长序列 batch 上出现了抖动。复盘时发现两件事：第一，那个 3.1× 的基线本身是一个写得极差的参考实现，基线弱，speedup 自然虚高；第二，那个 1.4× 的 kernel 其实已经贴着显存带宽上限跑，根本没有继续优化的空间，而 3.1× 的 kernel 距离其计算上限还差一大截。问题不在于哪个 kernel“更好”，而在于 speedup 这个标量把“基线强弱”和“硬件上限远近”两件事混成了一件，导致跨 kernel、跨 GPU 的分数根本不可比。

这就是 Roofline/SOL 归一评分要解决的具体问题：把实测时延折算到硬件的理论上限，得到一个与基线无关的效率分数。原始 speedup 的定义是 T_base / T_gen，它的分母是另一个实现，而不是物理定律；换一个基线，同一个 kernel 的分数可以任意漂移。SOL 归一评分换掉了分母：用该 shape 在该 GPU 上的理论最短时延 T_SOL 做分子，以 T_SOL/T_gen 作为利用率。这样一来，分数衡量的是“离硬件上限多远”，而不是“比某个参考实现快多少”。

二 · 机制：算术强度与 roofline 拐点如何给出理论下界

核心公式只有两行，但每一行的每个量都有工程含义：

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$

先算 kernel 的算术强度 I = FLOP / Bytes，即每搬运一个字节能完成多少次浮点运算。再查 GPU 规格得到按 dtype 区分的峰值算力 P_peak（fp32/tf32/fp16 各不相同）与峰值带宽 B_peak，二者之比就是 roofline 的拐点 I*。当 I < I* 时，kernel 是 memory-bound，理论下界由 Bytes/B_peak 决定；当 I > I* 时是 compute-bound，下界由 FLOP/P_peak 决定。T_SOL 取两者中的较大者——注意是较大者，因为两条上限中更紧的那条才是真正的瓶颈。最后用实测 T_gen 去除，得到 u。u 越接近 1，说明这个 kernel 越贴近硬件能给的最快速度。

伪代码层面的流程是四步：静态分析或 profiler 统计 FLOP 与 DRAM 字节数 → 计算 I 并与 I* 比较 → 计算 T_SOL → 实测 T_gen 并求 u，同时按 I 与 I* 的关系标注瓶颈类型。瓶颈标注是这套方法对 agent 最有价值的部分：它把“该优化计算还是该优化访存”变成一个确定性的信号，而不是让 agent 在裸 speedup 上盲猜。一个 u=0.35 且标注为 memory-bound 的 kernel，优化方向是减少 DRAM 往返、提高复用；一个 u=0.35 且标注为 compute-bound 的 kernel，方向则是提高指令级并行、减少 warp stall。同样的 0.35，反馈信号完全不同。

代价同样明确。第一，FLOP/Bytes 统计依赖 profiler 或人工建模，融合 kernel 的字节数极易低估——因为缓存复用让实际 DRAM 流量远小于按张量尺寸朴素累加的结果，Bytes 被低估会直接压低 T_SOL，使 u 虚高。第二，P_peak 是稀疏/稠密混合的理论值，实际可达上限约 70–85%，因此 u 的绝对值必须按经验系数校正，否则一个“u=0.9”的样本可能只是理论峰值本身不可达造成的假象。这两条代价决定了 SOL 分数不能裸用，必须配合异常复核。

三 · 适用边界：它解决什么，明确不解决什么

这套方法解决的问题可以精确列举：其一，消除基线依赖，让同一 kernel 在不同参考实现下得到同一个分数；其二，跨 GPU 型号可比，因为 T_SOL 随硬件规格变化，u 是归一化后的无量纲量；其三，给出“离硬件上限多远”的绝对判断，SOL-ExecBench 类评测可以直接把它作为主指标；其四，提供瓶颈类型标注，让优化反馈有方向。

它明确不解决的问题同样要写清楚，否则会被误用。第一，它不判断正确性——u 再高，kernel 算错了也是零分，正确性 oracle 与合约校验是另一条独立防线。第二，它不解决基线锚定问题：如果基线本身是 TF32 编译产物还是 fp32 手写实现，T_SOL 的计算不受影响，但“这个 kernel 值不值得替换基线”的商业判断仍需要基线锚定，那是另一套机制。第三，它不处理隐藏 shape 分布：单个 shape 的 u 不能代表整个分布，抽样策略是独立问题。第四，它对 u>1 的样本没有解释力——u>1 意味着实测快于理论下界，只可能来自测量误差或缓存复用导致的 Bytes 低估，这类样本必须复核剔除，而不能当作“超越硬件”的喜报。第五，它不替代 SASS/warp stall 级别的微观剖析：u 告诉你离上限多远，但不告诉你为什么没到。

一个具体例子能说明边界的实际形状。考虑一个 batch=1、hidden=4096 的 matmul：FLOP 约为 2×4096×4096×4096 量级，Bytes 约为权重与激活的字节和。若权重被完整缓存复用，朴素按张量尺寸累加的 Bytes 会显著高于真实 DRAM 流量，于是 I 被低估、T_SOL 被低估、u 虚高。此时正确的做法是用 profiler 的 DRAM 计数器取真实字节数，而不是用张量尺寸估算。反过来，若 profiler 不可用只能静态建模，就必须对融合 kernel 的字节数打一个保守折扣，并在报告里标注该折扣，否则 u 的绝对值不可信。

四 · 代价的量化视角：时延、带宽、显存与编译时间如何进入分数

SOL 分数的四个代价维度要分开看。时延维度：T_gen 是实测墙钟时间，包含 launch 开销与尾部效应，小 shape 上 launch 开销占比高会让 u 天然偏低，这不是 kernel 写得差，而是测量口径问题。带宽维度：Bytes/B_peak 这一项对 memory-bound kernel 是决定性的，任何对 Bytes 的低估都会等比例放大 u。显存维度：显存占用不直接进入 u 公式，但它决定了能否用更大的 tile 提高复用，从而间接改变 I 与瓶颈类型。编译时间维度：T_SOL 与编译无关，但 agent 多轮搜索时每次编译都消耗 token 与时间预算，u 的提升必须与搜索成本一起核算——一个把 u 从 0.4 提到 0.5 但编译时间翻倍的方案，在端到端收益上未必划算。

把这四个维度放进一个判断框架：先看 u 的绝对值是否落在经验可达区间（考虑 70–85% 的峰值可达系数），再看瓶颈标注是否与优化方向一致，最后看提升 u 的边际成本。一个 u=0.75 的 compute-bound kernel，剩余 25% 的空间可能来自理论峰值不可达，继续投入的回报极低；一个 u=0.3 的 memory-bound kernel，空间来自真实的 DRAM 往返浪费，投入回报高。SOL 分数在这里的作用不是排名，而是把“还有多少真实空间”和“空间在哪条上限上”同时说清楚。

场景u 的表现可信度判断工程动作
小 shape、launch 开销占比高天然偏低口径问题，非 kernel 问题改用大 shape 或扣除 launch 开销
融合 kernel、Bytes 朴素累加虚高，可能 u>1不可信用 DRAM 计数器取真实字节
compute-bound、u 接近 0.8接近经验可达上限可信但空间有限停止投入或转向算法变换
memory-bound、u 约 0.3远离上限可信且空间大提高复用、减少往返

五 · 为什么评测翻车往往不是 kernel 写错，而是分数口径错

回到开头的事故。3.1× 的 kernel 之所以被误选，不是因为它的 u 低，而是因为评审根本没有算 u。如果当时算了 u，会发现它的 u 可能只有 0.2 出头，说明它离计算上限极远，3.1× 全部来自弱基线；而 1.4× 的那个 kernel 若 u 已接近 0.8 且标注 memory-bound，则说明它已无空间，1.4× 是真实的天花板。两个 kernel 的正确排序与 speedup 排序恰好相反。这就是 SOL 归一评分的核心工程价值：它把“相对基线快多少”这个受基线污染的指标，替换成“相对物理上限还有多少”这个与基线无关的指标，从而让跨 kernel、跨 GPU 的选择变得可辩护。

但口径正确不等于可以直接用。u>1 的异常必须复核：测量误差（计时器精度、异步未同步）与缓存复用（Bytes 低估）是两类主要来源，前者靠重复测量与同步点排除，后者靠 profiler 的 DRAM 计数器校正。u 的绝对值必须按 70–85% 的峰值可达系数做经验校正，否则会把“理论峰值不可达”误判为“kernel 低效”。这两条复核规则应当写进评测合约，而不是留给评审临场判断——合约化的复核规则才是这套方法可信的前提，否则它只是换了一个更精致的、同样会被误读的标量。

最后落到一个具体机制上：SOL 分数的可信度取决于 Bytes 的测量口径。对任何含融合或缓存的 kernel，静态张量尺寸累加只能作为上界估计，真实 DRAM 字节必须来自 profiler 计数器；若 profiler 不可用，则必须在报告里显式标注“Bytes 为静态估计，u 为乐观上界”，并把该样本排除在跨 kernel 排名之外。这个判断不是保守，而是这套方法在工程上可用的最低条件——一个不标注口径的 u 值，和裸 speedup 一样不可比。

SOL 归一化解决的是“跨基线不可比”，不是“绝对性能真相”

先看一次典型的评测翻车：某轮 agent 生成的 kernel 在 A100 上对基线拿到 1.8× speedup，被判定为“显著改进”并进入下一轮训练；同一份 kernel 换到 H100 上对另一份基线只有 0.6×，于是被标为回退。两次判定都“正确”，但结论互相矛盾——因为 speedup 的分母是基线，基线本身强弱不同、实现质量不同、甚至同一 shape 下基线版本不同，分数就不可比。更隐蔽的失效是：基线本身离硬件上限很远时，1.8× 只说明“比烂基线好”，不说明这个 kernel 有多接近硬件能力。SOL 归一化把分母从“别人写的 kernel”换成“这块 GPU 在该 shape 下的理论最短时延”，于是分数变成与基线无关的效率量。它解决的问题只有一个：让不同 kernel、不同 GPU 型号、不同轮次的效率分数落在同一把尺子上，并顺带告诉 agent 瓶颈在计算还是访存。

机制上，先由静态分析或 profiler 统计 kernel 的 FLOP 数与 DRAM 字节数，得到算术强度 I=FLOP/Bytes；再查 GPU 规格拿到按 dtype 区分的 Peak_FLOPS（fp32/tf32/fp16 各自不同）与 Peak_BW，构造 roofline 拐点 I*=P_peak/B_peak；理论下界与利用率分别为

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$

I 与 I* 的关系决定标注 compute-bound 还是 memory-bound，这个标注直接改变 agent 的下一步动作：compute-bound 该去看寄存器压力、指令混合与 occupancy，memory-bound 该去看合并访存、bank conflict 与 L2 复用。相比裸 speedup 只给一个标量方向不明，瓶颈标注是带方向的反馈信号。但代价立刻出现：FLOP/Bytes 依赖 profiler 计数或人工建模，融合 kernel 的 DRAM 字节数极易低估——中间结果被缓存复用、没有真正落到 DRAM，分母 Bytes 偏小则 T_SOL 偏小、u 虚高；反过来，若把 cache 命中流量也算进 Bytes，u 又被压低。两种误差方向相反，且都随融合程度放大。

第二个代价在 Peak_FLOPS 的语义：规格表上的峰值是稀疏/稠密混合的理论值，实际可达上限按经验只有约 70–85%，因此 u 的绝对值必须按经验系数校正后才能当“离上限多远”读；未校正时 u=0.9 可能已经是实测极限，而 u=0.5 未必真有 2× 空间。第三个代价是复核成本：u>1 的样本必然来自测量误差或缓存复用，必须逐条复核并剔除，否则这些“超过理论上限”的样本会污染 RL 的可验证奖励，让 agent 学会刷分而非优化。工程判断是：SOL 分数适合做跨基线、跨型号的相对排序与瓶颈路由，不适合单独作为“绝对性能达标”的判据；把它和原始时延、基线 speedup、u>1 剔除规则一起放进评测管线，才是它适用的边界。

SOL 归一能回答什么，不能回答什么

一次评测翻车的典型形态是这样的：agent 在 KernelBench 式任务上把某个 elementwise 或 reduction kernel 的时延压到基线的若干倍，speedup 数字漂亮，于是被判定为“优化成功”。但换一个 shape、换一块 GPU、换一个基线实现（比如基线本身已经接近硬件上限），同一个 kernel 的 speedup 立刻塌回 1 附近——分数衡量的是“基线有多弱”，而不是“离硬件上限有多远”。这正是 SOL 归一要解决的具体问题：把实测时延折算成与基线无关的效率量。

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$
分子只依赖 shape、dtype 与 GPU 规格，分母是实测值，因此分数跨 GPU 型号可比，也能直接告诉 agent“还差多远”。

但它的适用边界同样硬。第一，FLOP 与 DRAM 字节数依赖 profiler 计数或人工建模，融合 kernel 尤其容易低估字节数——中间结果被缓存复用、没有真正落到 DRAM，于是 Bytes 偏小、T_SOL 偏小、u 被系统性压低（或按错误方向虚高），这类样本必须复核剔除。第二，Peak_FLOPS 是稀疏/稠密混合的理论峰值，实际可达上限只有约 70–85%，u 的绝对值需要经验系数校正，否则会把一个已经很好的 kernel 判成“还有三成空间”。第三，u>1 的异常几乎总意味着测量误差或缓存复用未被计入，不能当作“超越硬件”的喜报。

情形SOL 归一的判断代价来源
基线极弱、speedup 虚高可纠正，u 反映真实效率需 profiler 统计 FLOP/Bytes
融合 kernel 字节低估失效，u 不可信缓存复用建模成本、复核时延
接近峰值的成熟 kernel可给出剩余空间，但需系数校正Peak 理论值与可达值之差
纯访存瓶颈小 shape可标注 memory-bound，方向明确启动开销未计入 T_SOL

它明确不解决的问题包括：启动开销与 kernel launch 延迟占主导的小 shape（T_SOL 里没有这一项，u 会被压得很低却无从优化）、多 kernel 流水与端到端收益（SOL 是单 kernel 量）、以及正确性——u 再高也不能替代 oracle。工程判断是：把 SOL 当作方向性反馈信号与跨机型可比刻度，而不是绝对真理；对 u>1 与融合 kernel 强制走复核路径，对 compute-bound / memory-bound 的标注则直接决定 agent 下一轮该动计算还是动访存。
