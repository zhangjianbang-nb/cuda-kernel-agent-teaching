一 · 负载画像：先决定“合成什么”，再决定“合成多少”

合成算子数据扩增的负载配方不是“多造点算子”这么简单。它要回答三个耦合问题：合成分布 psynth 覆盖哪些算子族与参数轴、这些实例的参考时延由什么基线给出、以及训练时如何按难度分层采样。三者中任一错位，扩增出来的数据在真实框架调用上就会失真。本片段只讨论负载与评测配方这一层：适合什么模型/算子/shape/硬件，基线怎么选，输入分布怎么设，指标怎么算，以及负载配方不对时会发生什么。

先把负载写成可采样的参数元组。一个算子实例不只是算子名，而是（算子族，shape，dtype，layout/stride，融合模式，边界条件，硬件目标）的联合取值。逐元素类沿元素数与向量化宽度展开；归约类沿归约轴长度与输出规模展开；矩阵乘沿 M/N/K 与 batch 维展开；卷积沿 N/C/H/W、kernel、stride、dilation、padding 展开；attention 沿序列长度、头数、head_dim、因果掩码展开。融合组合是笛卡尔积上的稀疏子集——不是所有算子都能融合，融合模式本身要作为离散参数采样，而不是事后拼接。

负载画像的第一条工程判断是：算子族的采样权重不应正比于真实基准里的出现频次，而应正比于“频次 × 当前策略在该族上的失败率”。热门算子（GEMM、attention）在真实基准里占比高，但模型往往已经在其上收敛；冷门算子（带 stride 的归约、非对齐边界的卷积、混合 dtype 的逐元素链）出现频次低却失败率高。若按频次采样，训练分布继续偏斜，扩增的边际收益趋近于零。这条权重规则本身就是一个可调超参，需要与难度分层一起调，而不是拍脑袋定。

硬件目标决定负载的“有效形状带”。同一算子在不同 SM 架构上的瓶颈不同：寄存器压力、shared memory 容量、warp 调度粒度、L2 切片都会改变最优 tile。合成负载若只在单一硬件上标注参考时延，模型学到的可能是该硬件的特化解，而不是算子本身的结构性优化。工程上可行的做法是把硬件目标作为负载的一个维度，但控制其基数——例如两到三档代表不同 SM 代际与显存带宽档位的目标，而不是穷举。每增加一档硬件，参考时延的标注成本与评测时间线性增长，这是负载配方里最容易被低估的代价。

一个具体例子：归约算子族。若只采样“长度是 2 的幂、连续布局、fp32”的实例，模型会学到以向量化加载加 warp shuffle 为主干的模板；一旦真实调用出现长度 1000 左右、带 stride、fp16 累加的情形，模板的尾部处理与精度路径全部失效。负载配方必须显式包含非 2 的幂长度、非连续 stride、混合精度累加这三条轴，并且让它们占有可观的采样比例，否则扩增只是在强化已有偏置。

二 · 基线选择：参考时延的锚必须与训练目标同构

合成样本的监督信号里，参考时延 Tref 由基线给出。基线选错，整批数据的标签就是错的，而且错得系统性——不是噪声，是偏置。基线选择的核心原则是与训练目标同构：如果训练目标是“在真实框架调用中超过框架默认实现”，基线就应是该框架在该 shape/dtype 下的实际调用路径（含其内部的启发式选择、kernel 融合与调度），而不是一个理想化的 cuBLAS 峰值或手写最优 kernel。

这里有三个层次的基线，代价与用途各不相同。第一层是框架默认路径（PyTorch eager 调用、cuBLAS/cuDNN 库调用），它最贴近真实端到端，但标注成本高：每个实例都要真实跑一遍，且受框架版本、库版本、启发式缓存影响，可复现性差。第二层是库级基线（直接调 cuBLAS/cuDNN 的对应 routine），剥离了框架调度开销，标注更快、更稳定，但与真实调用存在系统性差距。第三层是解析/roofline 基线，只给理论上界，标注几乎零成本，但不能作为“可超越”的目标，只能作为归一化参照。

工程上常见的错误是用第三层当监督标签。roofline 上界不是任何真实 kernel 的时延，用它做 Tref 会让“超越基线”的判定失去意义：模型学到的不是“比框架快”，而是“比理论慢多少”。正确做法是把 roofline 只用于归一化评分与瓶颈归因（这部分属于 SOL 归一评分的主题，此处只作指路），监督标签必须来自第一层或第二层。

$$\text{gap}_i=\frac{T_{\text{base},i}-T_{\text{cand},i}}{T_{\text{base},i}},\qquad \text{label}_i=\mathbb{1}\{\text{gap}_i>\tau\}$$

上式是基线锚定下的样本标签构造：Tbase,i 为基线时延，Tcand,i 为候选 kernel 时延，τ 为判定阈值。阈值 τ 不能设为零：测量噪声、时钟抖动、缓存状态会让同一 kernel 的时延波动，零阈值会把噪声当成信号。阈值应随基线层次调整——第一层基线噪声大，τ 要留出余量；第二层基线稳定，τ 可以收紧。代价是：τ 越松，正样本越多但信噪比越低；τ 越紧，样本越干净但正样本稀疏，RL 的奖励信号变稀。

一个具体例子：attention 算子。框架默认路径可能在小序列长度下走融合 kernel，在大序列长度下切到另一条路径，两条路径的时延曲线不连续。若基线只取其中一条，合成样本在跨越该断点时会得到错误的“可超越”标签。负载配方必须让 shape 采样覆盖这些断点附近，并对基线做路径一致性检查——同一 shape 重复标注，时延方差超过阈值就标记为不可靠样本，从训练集中剔除。这是基线选择带来的直接标注代价。

三 · 输入分布：数值域、边界与布局的三重设定

输入分布不只指 shape 分布，还包括数值域、边界条件与内存布局。三者各自影响正确性 oracle 与性能标签，且相互耦合。数值域决定参考实现的精度路径：fp32 与 fp16 的累加顺序、fp64 参考 oracle 的比对容差、以及是否触发溢出/下溢/非规格化数。边界条件决定 kernel 的尾部处理与谓词分支：非对齐长度、零长度、单元素、极窄维度、极宽维度。内存布局决定访存模式：连续、带 stride、转置、广播、切片视图。

数值域的采样要避免“全在舒适区”。若输入全取标准正态、量级适中，kernel 的数值稳定性问题不会被暴露，参考 oracle 也不会与候选实现产生分歧。合成负载应显式注入极端量级、接近溢出阈值的累加、混合精度下的舍入敏感实例。代价是：这些实例的参考实现更容易出现数值分歧，需要更严格的容差设计与 fp64 参考比对，标注与审计成本上升。这部分与 Fuzz+fp64 参考 oracle 的主题相邻，此处只强调负载侧的采样比例必须显式设定，而不是默认均匀。

边界条件的采样有一个易被忽略的陷阱：零长度与单元素实例的时延不可比。这些实例的时延由启动开销主导，而非 kernel 主体，把它们混入性能标签会污染 gap 的分布。正确做法是把边界实例单独分层：它们用于正确性验证与鲁棒性训练，但不参与“超越基线”的性能标签构造，或至少赋予独立的阈值。

布局采样要覆盖真实框架调用的常见视图：非连续 tensor、转置后的矩阵乘、带 padding 的卷积输入、广播后的逐元素运算。这些视图在框架内部会触发不同的 kernel 选择与内存重排，合成负载若只采样连续布局，模型学到的访存优化在真实视图上会退化。代价是：非连续布局的参考实现构造更复杂，需要显式 materialize 或使用框架的视图语义，标注流水线的实现成本上升。

一个具体例子：逐元素融合链（如 add + mul + relu 的融合）。数值域上若只采样小量级正数，relu 的负半轴分支与饱和行为不会被触发；布局上若只采样连续，广播与非对齐切片的谓词分支不会被覆盖。负载配方应把“负值比例”“接近饱和的比例”“非对齐偏移”作为显式参数轴，并让它们在训练集中占有固定配额。这不是为了增加数据量，而是为了让 oracle 与性能标签在真实调用分布上不失真。

四 · 指标计算：正确性、性能与泛化三本账要分开记

合成负载的评测指标必须分账。把正确性与性能混成一个标量奖励，会让模型在“快但错”与“慢但对”之间做无意义的权衡，也会掩盖负载配方本身的缺陷。三本账分别是：正确性通过率、性能超越率（相对基线）、以及合成-真实分布差距。前两者在合成集上算，第三者在真实基准上算，三者共同决定这批合成数据是否值得继续扩增。

正确性通过率要按算子族与难度分层统计，而不是只报一个总数。总数会被热门算子主导，冷门算子的失败被平均掉。分层统计能直接暴露负载配方里哪条轴采样不足：若某算子族的通过率显著低于其他族，要么是该族本身更难，要么是参考 oracle 在该族上有 bug，要么是采样比例失衡导致训练不足。这三种原因的区分需要变异测试审计（该主题另有片段，此处只作指路）。

性能超越率的计算依赖基线锚定，前面已给出 gap 与标签构造。这里要补充的是测量协议：同一实例的候选 kernel 与基线必须在同一硬件状态、同一缓存预热策略、同一迭代次数下测量，且要区分冷启动与稳态。合成负载规模大，逐实例做完整稳态测量代价高；折中方案是对每个算子族抽样做稳态测量，其余实例用较短迭代估计，并把估计方差作为权重传入训练。代价是：短迭代估计的噪声会进入奖励信号，需要与 τ 阈值配合抑制。

合成-真实分布差距的度量不能只看平均性能差。更有信息量的是按算子族与 shape 带的差距分解：合成集上表现好、真实基准上表现差的族，就是分布错位的证据。工程上可以用真实基准的算子族分布作为参照，计算合成分布与真实分布在参数轴上的覆盖差异，再与性能差距做相关性分析。这一步的代价是需要真实基准的标注，且真实基准本身算子数量有限、分布偏斜——这正是扩增要解决的问题，也是评测无法完全摆脱的约束。

五 · 负载配方失配的三种典型失效

第一种失效是形状带错位。合成负载的 shape 采样集中在“好算”的区域——2 的幂、对齐、中等规模——因为这些实例的参考实现容易写、基线容易跑。真实框架调用的 shape 分布却长尾且不规则。结果是模型在合成集上性能超越率很高，在真实调用上骤降。这种失效不会在合成评测里暴露，只能靠真实基准的泛化监控发现。代价是：发现得晚，前期训练算力与标注成本已经沉没。

第二种失效是基线层次错位。用库级基线或 roofline 基线标注，训练出的策略在真实框架调用上不占优，因为框架的调度开销、kernel 选择启发式、内存分配策略都不在基线的考量内。模型学到的是“在理想调用路径下更快”，而不是“在真实调用路径下更快”。这种失效的隐蔽性更强：合成集上的 gap 分布看起来很健康，但标签与真实目标不同构。

第三种失效是数值域与边界采样不足。合成负载的输入全在数值舒适区，候选 kernel 的正确性在合成集上全通过，但真实调用中的极端量级、非规格化数、非对齐边界触发精度分歧或谓词分支错误。这类失效直接表现为正确性事故，而不是性能退化，代价更高。它同时污染 oracle：若参考实现在这些边界上本身有 bug，合成标签会把错误行为当成正确目标来训练。

三种失效的共同点是：它们都不是“数据量不够”，而是“分布不对”。增加合成实例数量不能修复分布错位，只会放大偏置。工程判断是：在扩增规模之前，先用小批量合成负载做真实基准的泛化探针，确认合成-真实差距在可接受范围内，再放大规模。探针的成本远低于大规模标注后再发现失效的成本。

一个具体例子：卷积算子族。若合成负载只采样方形 kernel、stride 1、same padding、连续布局，模型会学到以规则 tile 为主的模板；真实调用中的非方形 kernel、dilation、非对称 padding、NHWC 布局会触发完全不同的访存与边界处理。负载配方必须把这些轴作为显式参数，并让真实基准的泛化监控按这些轴分解差距，才能定位是哪条轴采样不足。

六 · 配方与训练循环的耦合：分层采样与难度调度

负载配方不是静态数据集，它与训练循环耦合。合成实例按难度分层采样，难度可以由基线 gap 的分布、算子族的失败率、或 shape 的极端程度定义。训练早期应偏向中等难度与高失败率族，让策略快速获得可用的结构先验；训练后期应偏向高难度与长尾族，逼近真实调用的分布边界。这种调度本身是一个超参，需要与 RL 的奖励尺度、SFT 的样本混合比例一起调。

分层采样的代价是训练 token 预算的重新分配。高难度实例的候选 kernel 更长、推理轮数更多、执行反馈更复杂，单样本消耗的 token 显著高于简单实例。若难度调度过激进，训练吞吐下降，单位算力获得的泛化收益可能反而降低。工程上要监控“每 token 的性能超越率增量”，而不是只看总超越率。这个指标能把负载配方的收益与训练成本放在同一尺度上比较。

配方与训练循环耦合的另一个点是合成数据的混入比例。纯合成训练会在真实端到端场景失效，这是已知代价；但混入比例过高会稀释真实数据的信号，过低则扩增无效。可行的做法是按算子族分别设定混入比例：真实基准覆盖充分的族少混，覆盖不足的族长混。这要求对真实基准的族分布有持续监控，监控成本是配方维护的固定开销。

最后落到一个具体机制上：把负载配方写成可版本化的配置文件——算子族权重、shape 轴采样范围、dtype 与布局配额、基线层次、阈值 τ、难度调度曲线、混入比例——每次训练运行绑定一个配方版本，评测结果按版本归档。这样当合成-真实差距扩大时，可以定位到是哪次配方变更引入的，而不是在无版本的数据集上做无法复现的归因。配方的版本化是扩增可信度的基础设施，其代价是配置管理与归档存储，但远低于失效后重新标注的成本。
