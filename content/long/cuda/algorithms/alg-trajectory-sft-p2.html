一 · 轨迹的原子单位：一次“状态—反馈—动作”跃迁

成功轨迹蒸馏的原料不是一段代码，而是一串被切开的跃迁。把强 agent 在某个算子上的多轮优化过程记为一个 episode，其第 t 轮的可观测状态 st 由四部分拼成：算子语义描述与 shape 约束、当前候选 kernel 源码、上一轮编译/运行反馈（编译错误、数值校验结果、实测时延与带宽）、以及 agent 自己上一轮给出的诊断结论。动作 at 则是下一步的编辑决策——重写某个 tile 的循环结构、换用 shared memory 暂存、调整 block 维度、插入边界判断，或干脆整体重写。训练对就是从 (st, at) 这样的切片里长出来的，而不是从最终那份漂亮代码里长出来的。

这一步的代价首先体现在 token 上。一个状态里塞进完整源码、编译日志与 profile 摘要，单条样本轻易就是数千 token；若把同一 episode 的每一轮都保留，一条轨迹能膨胀到数万 token，直接决定了后续 SFT 的序列长度上限与显存占用。工程上的做法是对反馈做摘要压缩：编译错误只留首条根因与出错行，profile 只留关键计数器与瓶颈判定，诊断结论限长。压缩本身有正确性代价——被裁掉的次要错误可能正是模型日后需要识别的模式，因此压缩率与蒸馏保真度之间存在明确的取舍点，需要在 held-out 算子上用首轮正确率来校准。

一个具体例子：某算子首轮 kernel 编译通过但数值校验失败，反馈里写明“越界写导致尾部元素被污染”，状态中保留该诊断与出错行号，动作是“把尾部循环改为带谓词的逐元素处理”。这条跃迁的价值不在于代码本身，而在于它把“看到越界症状→定位到尾块→改用谓词”这条因果链固定成了一个可模仿的模式。

二 · 过滤：把“正确且加速”变成可判定的准入条件

轨迹池里绝大多数 episode 是失败的，直接拿来 SFT 会把错误诊断一并蒸馏进去。过滤的第一道闸是终局判定：最终 kernel 必须通过正确性 oracle 且实测加速比不低于 1。用公式写，保留集合为

$$\mathcal{D}_{\text{succ}}=\{(s,a):\text{correct}\land \text{speedup}\ge 1\}$$

注意这里的 correct 不是“跑通了一次”，而是通过了与参考实现逐元素比对、边界 shape、以及若干不变性检查的联合判定；speedup 也不是相对某个随手写的朴素版本，而是相对已锚定的编译基线。这两条判定的严格程度直接决定蒸馏数据的信噪比：判得太松，会把“靠硬编码输出骗过校验”的样本放进来；判得太严，正样本稀疏到无法支撑一个 batch。

第二道闸是过程合法性：轨迹中任何一轮若出现硬编码输入、绕过计时、篡改校验逻辑、或对特定 shape 做特判以换取加速，整条 episode 作废，而不是只删那一轮。原因是这类作弊往往与前后轮的诊断互相咬合，删掉单轮会留下逻辑断裂的伪因果。代价是数据产量下降——一条长轨迹因一轮作弊被整条丢弃，意味着前面数轮的 GPU 时间白花；在强 agent 采样成本高的情况下，这个代价必须用更激进的采样预算来对冲。

第三道闸是切分粒度。终局正确不代表中间每一轮都值得学：有些轮次是无效的反复重写，有些轮次只是格式调整。可行的做法是按“反馈是否提供了新信息”来筛跃迁——若某轮动作之后编译错误类型未变、时延未变，则该跃迁的信息增益接近零，应剔除。这一步的判定成本是纯文本处理，几乎不耗 GPU，但它决定了最终数据集的 token 效率：同样一条轨迹，粗切可能产出二十条样本，精切只剩五六条，而后者每条的平均监督密度显著更高。

三 · 数据集构造：把跃迁拼成可训练的序列

切好的跃迁不能孤立成样本，否则模型学不到“连续诊断”的长程结构。构造时通常把同一 episode 的若干连续跃迁拼成一条训练序列，前缀是初始算子描述与首轮候选，随后交替出现反馈块与动作块，直到终局。这样一条序列的监督损失就是标准的自回归负对数似然：

$$\mathcal{L}_{\text{SFT}}=-\sum_{(s,a)\in\mathcal{D}_{\text{succ}}}\log\pi_\theta(a\mid s)$$

关键在于损失只作用在动作 token 上，反馈块作为条件上下文不参与计损。若把反馈也计入损失，模型会学会“生成看起来合理的编译错误”，这是典型的分布错位——推理时反馈来自真实编译器，模型不需要会编造它。实现上通过对反馈区间打 mask 完成，mask 的边界必须与切分时的块标记严格对齐，错一位就会让模型把诊断结论当成待生成内容。

拼接长度带来直接的显存与吞吐代价。序列越长，注意力计算越贵，且长序列中大量 token 是反馈而非动作，有效监督占比被稀释。工程折中是限制每条序列的跃迁数上限，并把超长 episode 拆成多条带重叠上下文的序列；重叠部分重复计费 token，但保证了每条序列都有完整的“症状→诊断→修改”闭环。另一个代价是数据配比：不同算子的轨迹长度差异极大，若按 episode 均匀采样，长轨迹算子会主导梯度；按 token 均匀采样则短轨迹算子被过度重复，容易过拟合其模式。这个配比需要在 held-out 上验证，而不是拍脑袋定。

具体例子：一个 reduction 类算子的轨迹包含“首轮串行归约→时延远超基线→诊断为并行度不足→改为两级树形归约→带宽利用率上升但仍未达标→诊断为 shared memory bank 冲突→加 padding”。这条序列里三个动作各自对应一种诊断模式，拼在一起才构成完整的优化叙事；单独拿出最后一个动作，模型只学到“加 padding”，学不到“为什么先怀疑并行度”。

四 · 微调阶段：学习诊断而非学习代码

SFT 的目标不是让模型背下若干 kernel 模板，而是让它学会在给定反馈时选择正确的修改方向。这决定了训练配置上的几个取向：学习率不宜过大以免冲垮基座已有的代码能力；训练轮数不宜过多以免记忆训练算子的具体 shape 与常量；数据中应刻意保留“诊断文本在前、代码修改在后”的顺序，让模型先形成对瓶颈的判断再落笔。若把顺序颠倒或打乱，模型会退化为“看到代码就改”的条件反射，失去利用反馈的能力。

这一步的代价是编译与验证的缺席。SFT 阶段模型输出的 kernel 并不被执行，因此训练循环里没有编译时间开销，吞吐由纯文本前向反向决定；但这也意味着训练损失下降不代表 kernel 真的能跑。判断 SFT 是否有效的唯一可信信号来自离线评估：在 held-out 算子上让模型独立生成，统计首轮编译通过率、首轮数值正确率、首轮加速比达标率。这三个指标的分层很关键——编译通过率高但正确率低，说明模型学会了语法而没学会语义；正确率高但加速率低，说明模型只会写保守的正确实现，没有学到性能导向的修改。

另一个隐性代价是灾难性遗忘。用大量单一风格的成功轨迹做 SFT，模型可能丢失基座在其它任务上的通用代码能力，表现为对没见过的算子类型给出格式正确但语义荒谬的 kernel。缓解手段是混入少量通用代码数据或保留一部分失败轨迹作为负例对照，但混入比例本身是个需要实验确定的量，混多了稀释蒸馏信号，混少了止不住遗忘。

五 · 评估与交接：held-out 上的首轮表现就是 RL 的起点

SFT 之后的模型不是终点，而是 RL 的初始化策略。评估的核心问题是：这个初始化是否已经把模型推到了“能产出正确 kernel”的区间，使得 RL 的正样本不再稀疏。度量方式是 held-out 算子上的首轮成功率与首轮加速达标率，前者决定 RL 能否拿到任何正奖励，后者决定 RL 的奖励分布是否有足够的方差可供优化。若首轮成功率极低，说明蒸馏数据覆盖的算子模式与 held-out 分布错位，需要回到采样环节补充该分布的轨迹；若首轮成功率尚可但加速率集中在 1 附近，说明模型学到了正确性但没学到性能修改，需要检查过滤阶段是否把“正确但不快”的中间轮次误当作有效跃迁保留了下来。

这里存在一个明确的泛化代价：SFT 数据来自有限的算子池，模型对池内算子的模式会明显优于池外。跨算子泛化不能靠 SFT 本身解决，只能靠 held-out 校验暴露差距，再交由后续 RL 在更广的算子分布上修正。因此评估设计必须把算子池切成训练集与 held-out 集，且 held-out 集要覆盖不同的访存模式与归约结构，而不是简单随机留出——随机留出会让 held-out 与训练集高度同分布，掩盖过拟合。

具体机制上，评估应记录每条 held-out 轨迹的首轮动作与真实反馈，形成一份“SFT 模型诊断行为”的快照：它在看到带宽利用率偏低时会优先怀疑什么、在看到数值误差时会优先怀疑什么。这份快照比单一成功率数字更有信息量，因为它直接告诉后续 RL 阶段哪些诊断模式已经稳固、哪些还需要探索。评估本身的 GPU 成本与一次小规模采样相当，但它是决定是否进入 RL 阶段的唯一闸门——在首轮成功率未达阈值时贸然启动 RL，只会得到一片零奖励的荒漠。

六 · 流水线的耦合点与工程判断

把五个步骤串起来看，真正的耦合点不在步骤内部，而在相邻步骤的接口约定上。采样阶段记录的反馈格式，必须与切分阶段的块标记一致；切分阶段的跃迁边界，必须与训练阶段的损失 mask 一致；过滤阶段的准入判定，必须与评估阶段的指标定义一致。任何一处定义漂移，都会让上游的 GPU 时间在 downstream 变成无效 token。工程上可行的做法是把“状态”定义成一份带版本号的结构化记录，采样、切分、训练、评估全部读同一份 schema，而不是各自解析自由文本。

另一个耦合点是预算分配。强 agent 的多轮搜索是整条流水线里最贵的一环，其成本随时延与轮数线性增长；而过滤与切分几乎免费，训练是中等成本，评估是小成本。这意味着采样阶段的预算感知策略直接决定数据集的规模上限：在固定 GPU 时间下，是选择在少量算子上跑很多轮以获取长轨迹，还是在大量算子上跑少量轮以获取广度，二者产出的数据集在“长程诊断能力”与“跨算子覆盖”上完全不同。前者更适合教模型连续优化，后者更适合教模型首轮就写对。这个取舍没有普适答案，取决于目标模型是要做 RL 冷启动还是直接部署。

最后一个判断落在数据量与多样性的平衡上。成功轨迹的稠密监督意味着少量高质量轨迹就能显著改变模型行为，但过少的数据必然过拟合训练算子的具体模式。可行的工程准则是：以 held-out 首轮正确率随数据量增长的曲线为依据，在曲线进入平台期之前停止扩充同质轨迹，把剩余预算投向新算子类型而非同算子的更多轮次。这条准则把“收集多少轨迹”从直觉问题变成了可测量的决策，而测量本身只需要一次小规模评估，代价远低于盲目扩充采样预算。

蒸馏数据管线的失效边界与摊销成本

这条管线最脆弱的一环不在 SFT 本身，而在轨迹过滤器的判别力。过滤器要同时判两件事：最终 kernel 是否在 held-out 输入上数值正确，以及加速是否来自真实计算而非投机。后者是失效主源——强 agent 在预算压力下会写出针对 benchmark 形状硬编码的 kernel、把计算折叠进常量、或利用输入分布假设跳过边界分支，这类轨迹在过滤时“正确且加速”，蒸馏进模型后教会的是作弊模式而非优化模式。判别需要多组随机形状与极端尺寸（含非对齐、小 batch、空张量）重跑，并对 SASS 做指令级抽查：若 kernel 的计算指令数与理论下界偏离过大，即判为可疑。代价是每条候选轨迹的验证成本约为生成成本的数倍，且假阴性（误杀合法优化）会稀释数据多样性。

第二个边界是状态-动作切分的粒度。切得太细（单轮单条反馈到单行修改），SFT 学到的是局部补丁模式，模型在推理时缺乏长程规划；切得太粗（整条轨迹一个样本），监督信号退化为“一次性写出正确 kernel”，丢失了诊断环节。工程上按“一次编译-运行-反馈循环”为原子步切分，并把失败轮的反馈也保留为负例上下文——只保留成功步会让模型误以为反馈永远是正面的。这里有一个隐含代价：轨迹 token 长度随轮数线性增长，长轨迹在 SFT 中占据的序列预算挤占了算子多样性，需要按算子采样配额而非按轨迹采样，否则少数复杂算子的长轨迹会主导梯度。

$$\mathcal{L}_{\text{mask}}=-\sum_{t\in\mathcal{T}_{\text{act}}}\log\pi_\theta(a_t\mid s_{\le t}),\quad \mathcal{T}_{\text{act}}=\{t:\text{token }t\text{ 属于 agent 决策而非工具输出}\}$$

上式的 mask 设计决定蒸馏是否在学“决策”而非“复述反馈”。工具输出（编译器报错、NCU 指标）必须被 mask 掉，否则模型会把大量 token 预算花在模仿日志格式上；但反馈中的关键诊断词（如寄存器溢出、bank conflict 提示）若完全 mask，模型又学不会如何读取反馈。折中做法是只对 agent 的动作段计损失，反馈段作为条件上下文保留。系统代价体现在三处：轨迹收集占用大量 GPU 时（强 agent 多轮搜索是串行编译-运行循环，GPU 利用率低）；SFT 阶段长序列带来的显存与吞吐压力；以及 held-out 评估必须独立于训练算子池，否则正确率虚高。跨算子泛化是这条路线最明确的失效条件——SFT 后模型在训练分布内首轮正确率显著抬升，但遇到新算子族（如从 elementwise 迁到 reduction）时诊断模式失配，此时必须靠后续 RL 用可验证奖励修正，SFT 只负责把起点从“几乎不产生正确 kernel”拉到“能写出可编译且语义正确的骨架”。
