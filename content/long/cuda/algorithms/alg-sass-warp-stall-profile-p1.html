一 · 事故现场：源码级反馈把 agent 引向了错误的优化方向

某团队在 KernelBench 风格的多轮优化闭环里，让 agent 对一个融合 GEMM+激活的 kernel 做自动调优。源码里循环体写得干净，agent 的静态分析给出判断：计算密集、访存规整，于是它把全部预算压在提高 occupancy 上——缩小 tile、降低每线程寄存器用量、增加 block 数。三轮之后，端到端时延不降反升。评测端只看到“正确性通过、时延变差”，于是判定该变异被 revert。真正的病灶在别处：编译器把内层循环展开了 8 条 FFMA，寄存器需求被推高，溢出到 local memory，每次迭代多出若干 STL/LDL 往返；同时因为寄存器占用抬升，occupancy 被压下来，warp 调度器没有足够的常驻 warp 去填 long scoreboard 的等待窗口。这些事实在源码层面完全不可见——源码里既没有 local spill，也没有 stall 类型，只有一段看起来无害的 for 循环。agent 基于源码做的“降寄存器”动作，恰好和编译器已经做的展开决策打架，越调越差。

这个事故的教训不是“agent 不够聪明”，而是反馈通道的信息带宽不够。源码级反馈把编译器优化后的真实指令序列抽象掉了，把 warp 调度与 stall 归因也抽象掉了。agent 面对的是一个被抹平了执行语义的中间表示，它无法回答三个关键问题：低效是寄存器压力导致的 occupancy 下降，还是 shared memory bank conflict，还是纯指令依赖链太长？这三个问题的动作空间完全不同——前者要调 tile 与寄存器预算，中者要改 swizzle 或 padding，后者要重排指令或引入 ILP。给不出区分，agent 就只能盲试，而盲试在昂贵的剖析预算下很快耗尽轮次。

因此本方法要解决的具体问题是：把“哪条 SASS 指令、哪类 stall、占多少周期”这一层证据，变成 agent 下一轮 prompt 里可消费的结构化反馈块，让动作选择从猜测变成归因驱动。它不解决的问题同样要划清：它不做正确性判定（正确性由独立 oracle 承担），不做跨架构的性能外推（不同代 SASS 差异大，反馈不可跨代复用），也不替代端到端收益核算——单 kernel 的 stall 占比下降不等于线上时延下降，后者还受 launch 开销、流水重叠与批不变性约束。

二 · 为什么源码级与 profile 汇总级反馈都不够

常见的替代方案有两类，各自在信息粒度上断了一截。第一类是纯源码静态分析：agent 读 CUDA C++ 或 Triton IR，推断访存模式与计算强度。它便宜、无需重放，但推断的是“程序员意图”而非“硬件现实”。编译器会做循环展开、指令重排、寄存器分配、谓词化，这些变换改变了指令混合比例与寄存器占用，而源码里没有任何痕迹。上面的事故就是典型：源码看不出 8 条 FFMA 的展开，也看不出 spill。

第二类是 NCU 的高层汇总指标，例如 occupancy、DRAM 吞吐占比、SM 利用率。这类指标能告诉你“这个 kernel 利用率不高”，但不能告诉你“为什么不高”。一个 SM 利用率 40% 的 kernel，可能是因为 barrier 同步过密导致 warp 集体空转，也可能是因为 long scoreboard 等待全局访存返回，两者的修复动作相反：前者要减少同步、拆分阶段，后者要预取、增大并行度、改善访存局部性。汇总指标把这两类 stall 混在一个标量里，agent 拿到后只能做无差别尝试。

本方法补的正是这一段：以 PC 为聚合粒度，把 stall 周期按类型拆开，再对齐回具体的 SASS 指令行。这样反馈块里出现的是“PC=0x… 处的 LDG 指令贡献了 long scoreboard 的主要周期占比”，而不是“occupancy 偏低”。归因一旦落到指令与 stall 类型，动作空间就收敛了。

$$\text{StallShare}_k=\frac{\sum_{pc}\text{cycles}_k(pc)}{\sum_{pc}\sum_{k'}\text{cycles}_{k'}(pc)}$$

这个占比公式是反馈块的核心量化项：对每一类 stall $k$（long scoreboard、MIO throttle、barrier、not selected 等），把它在所有 PC 上贡献的周期求和，再除以全部类型在所有 PC 上的周期总和。得到的是一个可比较的分布，而不是绝对周期数——绝对周期数受 kernel 规模与采样窗口影响，跨 kernel 不可比，占比则可以进入 prompt 作为排序依据。代价是：占比丢失了绝对量级信息，一个总周期很短的 kernel 也可能出现某类 stall 占比很高，此时应结合指令计数判断是否值得优化。

三 · 机制拆解：从 cubin 到可回灌的反馈块

整条链路的第一步是反汇编。用 cuobjdump -sass 对编译产物 cubin 做反汇编，得到该 kernel 的 SASS 指令序列，同时提取每线程寄存器数这一元数据。这一步不依赖源码，也不依赖编译器中间表示，拿到的是最终会跑在硬件上的指令。寄存器数在这里不是附带信息，而是判断 occupancy 上限的关键输入：

$$\text{RegPressure}=\frac{\text{regs per thread}\times\text{threads per block}}{\text{regs per SM}}$$

这个比值直接决定一个 SM 上能常驻多少个 block。当它逼近 1 时，寄存器成为 occupancy 的硬约束，任何“增加并行 warp 数”的建议都不可执行，必须先降寄存器或改 tile。反馈块里带上这个比值，agent 才不会提出与硬件约束冲突的动作。

第二步是采集 stall 采样。用 ncu 的 smsp__pcsamp 做 warp stall 采样，同时采集指令计数，按 PC 聚合 stall 周期。PC 采样意味着每条指令地址上累计了多少个等待周期是可查的，这比按 kernel 汇总的 stall 统计细一整个量级。采样需要 ncu 重放 kernel，这是本方法最直接的代价：单 kernel 剖析成本高，重放会放大实际执行时间，且采样窗口与重放次数影响统计稳定性。在轮次预算紧张的闭环里，不能对每一轮变异都做全量剖析，通常只在候选变异通过正确性门之后、进入性能比较之前做一次定向剖析。

第三步是把 stall 热点映射回 SASS 行并标注类型。具体做法是：按 PC 排序 stall 周期，取头部热点，在反汇编清单里定位对应指令，标注其 stall 类型。四类标注对应四类动作：long scoreboard 高，指向全局访存延迟未被覆盖，动作是预取、增大并行、改善访存局部性；MIO throttle 高，指向 shared memory 或特殊功能单元的队列拥塞，动作是改 bank 访问模式或减少 MIO 指令密度；barrier 高，指向同步等待，动作是减少同步点或拆分阶段；not selected 高，指向 warp 数量足够但调度器选不过来，通常说明 occupancy 已不是瓶颈，应从指令混合入手。

第四步是统计指令混合比例。把 LDG、FFMA、BAR 等指令在热点区间内的占比算出来，与 stall 分布交叉验证。一个 FFMA 占比高但 long scoreboard 也高的片段，说明计算被访存拖住，属于典型的访存受限而非计算受限；一个 BAR 占比不高但 barrier stall 占比高的片段，说明同步代价不在指令数量而在等待时长，问题出在阶段划分不均。交叉验证能防止单一指标误导。

第五步是生成反馈块。格式是“热点 SASS 片段 + stall 类型 + 建议动作”，注入下一轮 prompt。片段只截取热点附近的若干条指令，避免把整份反汇编塞进上下文——这是 token 代价的控制点。一份完整 SASS 清单可能有数百到上千条指令，全量注入会挤占 prompt 预算并稀释注意力；截取头部热点区间，配合占比数字，信息密度更高。伪代码思路如下：

  • 反汇编 cubin，得到指令列表与每线程寄存器数；
  • ncu 采样，按 PC 聚合各类 stall 周期；
  • 按 StallShare 排序，取累计占比超过阈值的 PC 集合；
  • 对每个 PC 定位 SASS 指令，标注 stall 类型与指令类别；
  • 计算该区间的指令混合比例与 RegPressure；
  • 拼装反馈块：区间指令、占比、类型、约束、候选动作。

这套机制的价值在一个具体例子上最清楚：编译器把循环展开成 8 条 FFMA，寄存器需求上升导致溢出到 local，SASS 里出现 STL/LDL，stall 采样在 LDL 上显示 long scoreboard 占比突出。源码级反馈完全看不到这条链路，而 SASS 级反馈能直接指出“展开导致 spill，spill 导致访存等待”。对应的动作也就明确了：限制展开因子、重排计算顺序降低活跃寄存器数，或者接受 spill 但用预取掩盖延迟。这是源码级分析给不出的判断。

四 · 适用边界：什么时候不该用这套反馈

第一类边界是映射精度。SASS 与源码行号的映射不精确，模板实例化与内联会把多条源码语句折叠进同一段指令，也会把一条语句摊到多个 PC。反馈块因此可能指向错误位置：agent 被告知热点在某段 SASS，回头改源码时改错了行。工程上的缓解是让反馈块以 SASS 片段本身为主语，描述“这段指令序列的行为”，而不是断言“源码第 N 行有问题”；动作建议也停留在指令级（限制展开、调整访存宽度、改同步结构），不直接给源码行号。这降低了误导概率，但也意味着 agent 需要自己完成从指令模式到源码改动的映射，增加了推理负担。

第二类边界是剖析成本。PC 采样依赖 ncu 重放，单 kernel 剖析的时延代价与重放次数成正比。在一个每轮都要评估数十个变异的搜索里，全量剖析不可行。适用场景是：变异数量已被正确性门与合约校验筛过一轮，剩下少量候选需要精细归因；或者某一类变异反复失败，需要一次性深挖原因。把剖析当作每轮标配，会把闭环吞吐拖垮。

第三类边界是跨代复用。不同架构的 SASS 指令集、寄存器文件规模、调度器行为都不同，一份在某代上得到的 stall 分布与指令混合，不能直接搬到另一代作为动作依据。反馈块必须与架构绑定，缓存与复用要按架构分键。这也意味着本方法不适合做“一次剖析、长期指导”的静态知识库，它本质上是每轮闭环里的即时证据。

第四类边界是归因的完备性。stall 采样给的是等待周期归因，不是根因证明。long scoreboard 高可能是因为访存延迟，也可能是因为依赖链把访存结果的使用推后，采样本身不区分这两者。反馈块给出的是“哪类等待占主导”，动作建议是概率性的方向，不是确定性修复。agent 仍需通过变异与重测来验证动作是否有效——这正是闭环存在的理由，也是本方法不能替代搜索的原因。

场景适用性原因
候选变异已通过正确性门，需精细归因适用剖析成本可摊薄到少量候选上
每轮对数十个变异全量剖析不适用ncu 重放时延拖垮闭环吞吐
跨架构复用历史反馈不适用SASS 差异大，占比不可迁移
需要确定性根因证明不适用采样给等待归因，不给因果证明
源码行级精确定位不适用模板与内联破坏行号映射

把边界说清楚之后，本方法的定位就明确了：它是闭环里的归因证据供给器，服务于动作选择，不服务于正确性判定，不服务于跨代知识沉淀。它把“为什么慢”从不可见变成可排序、可对齐、可注入的反馈块，代价是剖析时延、token 占用与映射误差。工程判断的关键在于：只在归因收益大于剖析成本的那一小段闭环里启用它，并且让反馈块以指令为主语、以占比为量化、以约束为边界，避免把不确定的映射当成确定的事实喂给 agent。

热点对齐的失效面与剖析开销的账

这套方法真正解决的问题只有一个：把“这个 kernel 慢”从源码层的猜测，变成 SASS 层可定位的归因。源码级反馈看不到编译器优化后的真实指令序列——循环被展开成几条 FFMA、寄存器是否溢出到 local、访存是否被重排，这些在 CUDA C++ 里全被抽象掉；warp 调度与 stall 原因同样被抽象掉，agent 拿到“耗时 1.8 ms”这种数字，无法判断瓶颈是寄存器压力、bank conflict 还是指令依赖。线上事故的典型形态是：某算子评测通过、正确性无误，但端到端吞吐只有预期的几分之一，agent 连续几轮改 tile 大小与线程数都无收益，因为真正的病灶是编译器把展开后的中间结果压进了 local memory，源码里根本没有对应行可改。它不解决的问题同样明确：不给出算法级重构建议，不替代 roofline 判断该不该换数据布局，也不对正确性负责——SASS 反馈只解释“为什么慢”，不解释“为什么错”。

失效条件集中在映射与采样两端。SASS 与源码行号映射不精确，模板实例化与强制内联会把多条源码语句折叠进同一段指令，反馈块可能指向错误位置，agent 据此改错地方，反而引入新的寄存器压力。PC 采样依赖 ncu 重放，单 kernel 剖析成本高：重放会串行化、锁定时钟、多次 pass 采集，一个 kernel 的剖析时延常常远超它本身的执行时延，在 agent 多轮迭代里这笔开销按轮数线性累加，token 预算与墙钟时间同时被吃掉。不同架构 SASS 差异大，反馈不可跨代复用，同一段“热点 SASS + stall 类型”在换代后可能完全失效。判断是否受寄存器限制时，可用 $$\text{RegPressure}=\frac{\text{regs per thread}\times\text{threads per block}}{\text{regs per SM}}$$ 快速估算 occupancy 上限，但该比值只说明“可能受限”，不说明 stall 是否真由它引起，必须与 stall 占比交叉验证。

因此适用边界可以压成一张小表：

场景适用性代价
单 kernel 微基准、架构固定高，热点可稳定对齐ncu 重放时延
模板/内联密集的融合算子低，行号映射易错位错误反馈引发无效迭代
跨代复用反馈块不可用SASS 差异导致归因失真
正确性排查不适用需另设 oracle

工程判断落在采样粒度上：与其对每个候选 kernel 全量剖析，不如只在 agent 连续两轮无收益时触发一次 PC 采样，并把反馈块限制在“热点 SASS 片段 + stall 类型 + 建议动作”三要素内，避免把不可靠的行号映射当作精确坐标使用。stall 占比公式 $$\text{StallShare}_k=\frac{\sum_{pc}\text{cycles}_k(pc)}{\sum_{pc}\sum_{k'}\text{cycles}_{k'}(pc)}$$ 给出的是相对归因，当某类 stall 占比高但绝对周期数低时，说明该 kernel 本身已接近饱和，此时继续按 stall 类型调优的边际收益低于换并行策略——这正是该方法不该被当作通用加速器的边界所在。
