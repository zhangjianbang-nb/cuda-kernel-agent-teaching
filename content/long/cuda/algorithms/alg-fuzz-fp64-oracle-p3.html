一 · 相对误差项：分母为什么是 max(|y|, ε)，以及它的失效边界

评分公式的第一项是逐元素相对误差再取最大值：

$$\text{err}=\max_i\frac{|y_{\text{gen},i}-y_{\text{fp64},i}|}{\max(|y_{\text{fp64},i}|,\epsilon)}$$

推导的关键一步不在分子，而在分母的钳位。若直接用 |y_fp64,i| 作分母，当参考值恰好为 0（ReLU 负半轴、mask 后的零填充、稀疏输出的大片零区）时，比值发散；而 kernel 在这些位置只要产生一个非零值，误差就是无穷大，checker 会给出与“算法错误”无关的失败。引入 ε 后，分母被抬到 ε 之上，误差项在零附近退化为绝对误差除以 ε，等价于把“零附近的容差”从相对尺度切换成绝对尺度。工程上 ε 的取值必须与 dtype 的表示范围挂钩：fp32 下取 1e-6 量级可让零附近的绝对容差与 fp32 的最小正规数同量级，fp16 下则要抬到 1e-3 量级，否则 fp16 的次正规区会被误判。

这个设计的代价是它掩盖了一类真实缺陷：当参考输出整体量级极小（例如 softmax 尾部、归一化后的残差），分母被 ε 主导，误差项变成绝对误差，此时一个绝对量很小但在该量级上完全错误的输出可以蒙混过关。对策是把评分拆成两段——对 |y_fp64,i| ≥ ε 的元素走相对误差，对 < ε 的元素单独统计绝对误差并设更紧的绝对阈值，而不是让一个钳位同时承担两种语义。另一个代价是 max 聚合的脆弱性：单个离群元素即可决定整张量通过与否，因此最小复现输入必须保留该元素的索引与输入切片，否则 agent 拿到的“失败”信号无法定位到具体分支。

具体例子：一个 fp16 的 LayerNorm kernel，参考输出在均值附近有大量 1e-4 量级的元素。若 ε 取 1e-6，这些元素的分母仍是自身量级，相对误差判定有效；若 ε 取 1e-2，它们全部落入绝对误差区，一个把结果整体偏移 5e-3 的实现会被判通过——而这在 fp16 下已经是数个 ULP 的偏差。阈值不是越松越安全，ε 的选择直接决定 checker 的判别力。

二 · ULP 距离项：为什么相对误差不够，双阈值如何互补

第二项是 ULP 距离的分位数约束：

$$\text{pass}=\mathbb{1}[\text{err}\le\tau_{\text{dtype}}\wedge \text{ULP}_{95}\le \upsilon]$$

相对误差衡量的是数值偏离的幅度，ULP 距离衡量的是“在目标 dtype 的浮点网格上偏离了几格”。两者不可互相替代：一个在 1e-8 量级上偏离 1e-9 的输出，相对误差是 10%，但 ULP 距离可能只有 1–2 格，属于正常的舍入差异；反过来，一个在 1e6 量级上偏离 1e3 的输出，相对误差仅 0.1%，却跨过了大量 ULP。前者会被相对误差误杀，后者会被相对误差放过。双阈值的作用是让“幅度正确”与“网格位置正确”同时成立才判通过。

ULP 距离的计算需要一步关键推导：把两个浮点数映射到它们的有序整数表示上再作差。对同号正数，直接取位模式的整数解释相减即可；对跨零、跨符号的情况，必须先做单调映射（负数取反其位模式的无符号解释，再整体平移），否则 -0.0 与 +0.0、或相邻的负数和正数之间会出现巨大的伪距离。这一步在实现上是一个分支密集的整数变换，代价是每个元素多出若干次整数运算与一次符号判断，在亿级元素上会显著抬高 checker 自身的时延——这也是为什么 ULP 项通常只在相对误差已通过的元素上计算，作为二次筛选而非全量首筛。

取 95 分位而非最大值，是有意的鲁棒化：最大值会被单个边界元素（例如恰好落在舍入中点附近的元素）绑架，而分位数描述的是“绝大多数元素的网格偏离程度”。代价是它放过了尾部 5% 的元素，因此必须与第一项的 max 相对误差配合——max 项负责抓住最坏幅度，分位项负责抓住整体网格质量，任一超限即失败。具体例子：一个 fp32 的归约 kernel，绝大多数输出与 fp64 参考相差 1 ULP，但有一个元素因累加顺序不同差了 30 ULP。max 相对误差可能仍在 1e-5 内通过，而 ULP_95 若被这个尾部元素拉高则失败；反之若把 ULP 项改成 max，则任何一次合法的重排都会导致误判。阈值 υ 需按 dtype 校准：fp32 常取个位数 ULP，fp16 因尾数只有 10 位，容忍度要相应放宽到十位数量级。

三 · dtype 阈值 τ 的校准：从表示精度反推容差

τ_dtype 不是拍脑袋的常数，而是从 dtype 的机器 epsilon 与运算链长度反推出来的。一次长度为 K 的累加，最坏情况的相对误差上界近似为 K·u（u 为该 dtype 的单位舍入误差），但实际实现中误差按随机游走增长，约为 √K·u。因此 τ 的设定应满足：τ ≥ c·√K·u，c 为安全系数，同时 τ 要远小于“算法错误”所能造成的偏差量级，否则阈值失去判别力。

给定事实中 fp32 取 1e-5、fp16 取 1e-2，正对应这一推导：fp32 的 u 约为 6e-8，√K·u 在 K 为数百到数千时落在 1e-6 到 1e-5 区间，1e-5 是合理上界；fp16 的 u 约为 5e-4，同样量级的 K 给出 1e-2 附近的上界。这也解释了为什么阈值必须按 dtype 分开：用 fp32 的 1e-5 去卡 fp16 输出，任何合法的 fp16 kernel 都会失败；用 fp16 的 1e-2 去卡 fp32，则会把大量算法错误放行。

代价在于 τ 与 K 的耦合：同一个 dtype 下，K=16 的逐元素算子和 K=8192 的归约不应共享同一阈值。工程实现上应把 τ 参数化为 (dtype, 归约深度的估计值) 的函数，或在测试用例元数据里显式标注期望的累加规模。具体例子：一个 fp32 的 softmax，先在指数上做 max 减法再做分母归约，若分母归约用顺序累加，K 等于列长，误差随列长增长；此时若沿用固定 1e-5，长列用例会稳定失败而短列用例稳定通过，agent 会把“通过短列、失败长列”误读为 shape 相关的 bug，而真实原因是阈值未随 K 校准。

四 · 参考实现的时延与显存代价：fp64 oracle 成为瓶颈的结构性原因

fp64 参考在 GPU 上的吞吐约为 fp32 的 1/32–1/64，这一比例直接来自硬件：消费级与多数数据中心 GPU 的 fp64 单元数量是 fp32 的 1/32 或 1/64，双精度指令的发射速率与寄存器压力也更高。于是评测流水线的时延结构变成：被测 kernel 的时延可能只有几十微秒，而参考计算在同一 shape 上要花毫秒级，参考成为端到端评测的绝对瓶颈。

推导的关键一步是把评测总时延写成两项之和：T_eval = T_gen + T_ref + T_cmp，其中 T_ref 在 fp64 下近似为 T_fp32 × (32~64)。当 T_gen 与 T_cmp 都是访存受限的轻量操作时，T_eval 由 T_ref 主导，且随 shape 线性放大——这意味着大 shape 用例的评测成本不是“稍慢”，而是“慢一到两个数量级”。显存侧的代价同样结构性：fp64 参考输出占用的字节数是 fp32 的两倍，若同时保留被测输出、参考输出、以及用于最小复现的输入切片，峰值显存约为 2×N×8 字节加上输入，在长序列或大 batch 下会触发换页或强制分块。

可行的缓解不是降低参考精度（那会破坏 oracle 的意义），而是改变参考的执行位置与粒度：把参考放到 CPU 上以多线程 fp64 计算，避开 GPU 的 fp64 吞吐瓶颈，代价是主机与设备间的传输时延与 CPU 侧的并行度上限；或对参考做分块流式计算，用时间换显存峰值。具体例子：一个 batch 很大的 fp16 矩阵乘，被测 kernel 在 GPU 上微秒级完成，而 fp64 参考若在 GPU 上跑，单次评测的时延被拉到毫秒级，一轮多候选搜索的评测预算会被参考计算吃光；把参考改为 CPU fp64 分块计算后，GPU 侧只承担被测 kernel 与比对，评测吞吐才回到可用区间。

五 · NaN/Inf 传播语义：单独通道与“全 NaN 通过”漏洞的封堵

NaN/Inf 输入不能走主评分通道，因为相对误差与 ULP 距离在 NaN 上都没有定义：NaN 与任何数比较都为假，Inf 减 Inf 得 NaN，分母含 Inf 时比值退化。若把 NaN 元素直接纳入 max 聚合，一个输出全 NaN 的 kernel 会因为“比较结果恒为假”而被判通过——这就是“全 NaN 通过”漏洞的机制根源。

封堵方式是把 NaN/Inf 的检查拆成独立的语义通道：对每个含 NaN/Inf 的输入位置，检查输出是否按 IEEE 规则传播——NaN 输入应产生 NaN 输出，+Inf 参与加法应产生 +Inf 或按运算定义的结果，且 NaN 的 payload 与符号不被静默改写。实现上这是一组逐元素的谓词判定，而不是数值比较：用 isnan/isinf 提取掩码，再比对掩码是否一致，最后对掩码内的元素检查符号位。代价是这条通道无法用向量化的数值比较完成，需要额外的掩码生成与归约，在混合分布输入上会增加可观的比对时延；同时不同框架对 NaN 传播的约定并不一致（例如某些归约在遇到 NaN 时是否短路），因此 checker 与参考必须显式约定同一套语义，否则两者互相矛盾，agent 收到的失败信号是 checker 的约定差异而非 kernel 的缺陷。

具体例子：一个 fp32 的 exp kernel，输入含 +Inf 时应输出 +Inf，含 -Inf 时应输出 0，含 NaN 时应输出 NaN。若 agent 的实现用 saturating 转换把 +Inf 截断成有限大值，主通道因输入含 Inf 而无法给出有意义的相对误差，只有语义通道能捕获这一错误；反之若 checker 未约定 -Inf 的期望输出，一个正确返回 0 的实现可能被误判。最小复现输入在这一通道上尤其重要：必须保存触发传播差异的那个具体输入值及其 dtype 位模式，否则 agent 无法区分“传播规则不同”与“数值算错”。

六 · 从公式到可实现伪代码：聚合顺序、短路与最小复现的落点

把四项（相对误差、ULP、dtype 阈值、NaN 通道）落成可实现流程，关键决策是聚合顺序与短路位置。推荐的顺序是：先做 NaN/Inf 掩码通道（廉价且能立即排除整类失败），再做相对误差的全量归约（访存受限，可与 ULP 计算融合在同一遍扫描里），最后仅对通过相对误差的元素计算 ULP 距离并取分位。短路点设在 NaN 通道与相对误差之间：一旦掩码不一致或 max 相对误差超 τ，立即失败并记录最小复现，不再付出 ULP 计算的整数运算代价。

伪代码思路如下（以文字描述控制流）：对输入按 dtype 采样生成 fuzz 张量，同时产出 NaN/Inf 掩码；调用 fp64 参考得到 y_ref，并在参考侧记录其与更高精度实现的一致性作为 oracle 自检；调用被测 kernel 得到 y_gen；第一步比对两个掩码，不一致则失败；第二步在掩码外的元素上逐元素计算 |y_gen−y_ref|/max(|y_ref|,ε) 并归约取 max，超 τ 则失败；第三步在已通过的元素上计算有序整数表示的差得到 ULP 距离，取 95 分位与 υ 比较；任一步失败时，保存该步中误差最大的元素的索引、输入切片与 dtype 位模式作为最小复现。整个流程中，参考计算与比对是两次独立的全量扫描，融合它们能把比对从两遍访存降到一遍，代价是寄存器压力上升、占用率下降，需要在编译期按 shape 选择是否融合。

代价核算落在三处：fp64 参考的时延（毫秒级，主导 T_eval）、ULP 整数变换的额外算力（每元素若干整数指令，亿级元素上不可忽略）、以及最小复现切片的显存驻留（按元素索引切片而非整张量拷贝，可把驻留压到常数级）。具体例子：一个含 NaN 的混合分布 fuzz 用例，若把 NaN 通道放在最后，checker 会先花掉整轮相对误差与 ULP 的计算预算，最后才发现掩码不一致；把掩码比对前置后，这类用例在第一步即短路，评测预算被释放给真正需要数值比对的候选。聚合顺序不是实现细节，它直接决定单位评测预算能筛掉多少无效候选。

双阈值判定的边界：何时 fuzz 加 fp64 反而失效

公式里的合取式 $$\text{pass}=\mathbb{1}[\text{err}\le\tau_{\text{dtype}}\wedge \text{ULP}_{95}\le \upsilon]$$ 把相对误差与 ULP 距离并联，代价是判定面变成二维：任一维越界即失败。相对误差分母取 $$\max(|y_{\text{fp64},i}|,\epsilon)$$ 的关键一步是防止参考值接近零时比值爆炸，但 $$\epsilon$$ 一旦取小，近零元素的 err 会被放大到远超 $$\tau_{\text{dtype}}$$，把纯舍入差异误判为算法错误；取大则掩盖真实的绝对偏差。工程判断是让 $$\epsilon$$ 与 dtype 的最小正规数挂钩而非拍脑袋常数，并对 $$|y_{\text{fp64},i}|<\epsilon$$ 的元素改走绝对误差分支，否则近零区永远是最小复现输入的高发地。

失效条件集中在三处。其一，fp64 参考自身不绝对：CPU 双精度与 GPU 双精度在 FMA 收缩、归约顺序上不同，大 shape 归约的参考值本身带 $$\mathcal{O}(\sqrt{n})$$ 量级的累积误差，此时 $$\text{ULP}_{95}$$ 的基准被污染，阈值 $$\upsilon$$ 失去意义，必须先记录参考实现与更高精度（如 Kahan 补偿求和或分段归约）的一致性再放行。其二，NaN/Inf 传播语义跨框架不一致，若 checker 只统计有限元素的 err，全 NaN 输出会因无有效样本而“通过”，必须对含 NaN/Inf 的输入单独断言传播规则而非并入主阈值。其三，随机 fuzz 的分布若不含极端指数与非 2 的幂长度，agent 仍可在常规区间内拟合，fuzz 的覆盖度直接决定硬编码防御是否成立。

系统代价落在评测吞吐上：fp64 参考在 GPU 上吞吐约为 fp32 的 1/32–1/64，大 shape 下参考计算成为评测瓶颈，单次 pass/fail 的时延由参考核而非被测核主导，token 预算被参考重算挤占。可实现的折中是分层判定：先用 fp32 参考做快速筛除明显错误，仅对接近阈值的样本升级到 fp64 复核，把 fp64 调用次数压到候选集规模；同时缓存最小复现输入及其 fp64 期望值，避免同一失败样本在多轮 RL 中被反复重算。
