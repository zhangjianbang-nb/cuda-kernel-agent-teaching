一 · 生成步：从契约到首版 kernel 的输入面

仅目标驱动基线的第一步不是“写代码”，而是把可验证目标压缩成一份 agent 可消费的契约。输入面只有四类字段：算子语义（数学定义与边界条件）、输入输出契约（dtype、layout、stride 假设、shape 符号化方式）、目标硬件（SM 架构、显存容量、可用共享内存上限）、性能目标（以参考 kernel 的 SOL 百分比表达，而非绝对毫秒）。这四类字段构成一个封闭的约束系统，agent 在首轮必须从中推导出线程块维度、每线程工作量、访存向量化宽度与是否需要共享内存暂存，而不是从任何提示清单里摘取“用 float4”“做 swizzle”之类的结论。

生成步的输出是一份可编译的源文件加一份自检脚本。自检脚本由 agent 自己写，用于在提交给外部 oracle 之前先跑一遍形状与 dtype 的冒烟测试。这里的关键机制是“契约先行、代码后置”：agent 必须先声明它打算如何满足契约（例如声明按 128 位向量化读取、声明对非对齐尾部的处理策略），再落笔写 kernel。这个声明动作本身是可审计的，因为它把 agent 的假设外化成了文本，后续轮次的失败可以回溯到哪一条假设被证伪。

代价出现在两个地方。其一是 token：契约解析与假设声明在首轮就消耗可观上下文，且随着 shape 符号化维度增加而线性增长；其二是编译时间，首版 kernel 往往带有未使用的模板分支和保守的边界检查，nvcc 的模板实例化与寄存器分配会拉长单次编译时延。一个具体例子：对一个归约类算子，agent 若在契约中读到“输入长度可为任意正整数”，首版常写出带完整尾部掩码的通用版本，编译产物寄存器压力偏高，首轮运行即触发占用率下降——这不是正确性问题，而是生成步把通用性写进了不该通用的位置，代价在后续 profile 步才被暴露。

二 · 编译步：工具原语的最小暴露面与失败分类

工具集只暴露三个原语：编译、运行、NCU 采集。编译原语不接受任何编译选项注入，agent 只能通过修改源码本身（如 __launch_bounds__、模板参数、循环展开pragma）来影响编译结果。这一约束是刻意的：若允许 agent 传 -O3 或 --use_fast_math 之类的旗标，优化收益就混入了工具配置而非模型决策，基线不再纯净。编译原语的输出被结构化为三类：成功并返回 cubin 元信息（寄存器数、共享内存静态占用、是否发生 spills）、编译错误（带行号与诊断码）、编译超时。

失败分类是这一步的核心机制。编译错误不能只回灌原始 stderr，否则 agent 会在模板报错的长串实例化栈里迷失。基线实现的做法是把诊断码映射为有限类别：类型不匹配、未定义符号、资源超限、语法错误，每类附一行定位信息。这样 agent 在下一轮的动作空间被压缩为“改哪一类”，而不是“读一整屏报错”。资源超限这一类尤其重要，因为它直接对应寄存器溢出与共享内存越界，是后续性能问题的前置信号。

$$\text{compile\_cost}_t = \text{tokens}_{\text{diag}} + \lambda \cdot \text{wall}_{\text{nvcc}}$$

这里的代价是明确的：每次编译都消耗一次工具调用预算与一段诊断 token，且编译时延随源码复杂度上升。一个具体例子是模板化的分块矩阵乘：agent 若把 tile 尺寸写成模板参数并在首轮实例化多个候选，单次编译会因多实例而显著变慢，而它真正需要的只是其中一个实例的寄存器报告。工程判断是：编译原语应支持“只编译当前候选”，把多候选探索留给轮次而非单次编译，否则编译时间会成为轮次预算的主要吞噬者。

三 · 运行步：正确性判定与性能采样的分离

运行原语做两件事，且必须分离：正确性判定与性能采样。正确性判定由一个外部 oracle 完成（其构造方式属另一条目的主题，此处只指路），agent 拿到的是布尔结果加最大绝对误差与相对误差的摘要，而非逐元素 diff。性能采样则在正确性通过后才执行，返回的是该次运行的 SOL 比值与耗时分布的分位数。分离的意义在于：错误答案的高性能毫无价值，若把两者混在一次调用里，agent 可能学会用“跑得快但错”的候选骗取正反馈。

运行步的输出还包括一个隐式信号：启动配置是否合法。网格维度超出硬件限制、共享内存请求超过上限、动态共享内存未声明，这些都会在运行时以明确错误码返回，agent 据此调整 launch 参数。这一步的代价是时延与显存：每次运行都要重新分配输入输出缓冲，对显存受限的目标硬件，agent 若申请了过大的临时缓冲，运行会直接失败而非降级，这个失败信号必须被回灌为“显存预算”约束，而不是被当作正确性错误。

具体例子：一个 softmax 类算子，agent 首版用单块完成整行归约，正确性通过但 SOL 远低于阈值；运行步返回的分位数显示耗时方差极大，提示 occupancy 不足。agent 在下一轮改为多块分段归约加二次归约，运行步的正确性摘要显示误差仍在容差内，SOL 上升。整个过程没有人工提示介入，agent 仅凭“正确性布尔 + SOL 比值 + 耗时方差”三个信号完成了诊断。代价是这一轮多消耗了一次运行与一次编译的 token 与时延。

四 · Profile 步：NCU 采集作为假设证伪器

NCU 采集原语只在 agent 主动请求时触发，且返回的是受限指标集：achieved occupancy、DRAM 吞吐占峰值比、L2 命中率、warp stall 的主要分布、每周期指令数。这个受限集是刻意的，因为完整 NCU 报告体量巨大，直接回灌会淹没上下文，而受限集恰好覆盖“是否受限于访存、是否受限于占用率、是否有长延迟 stall”三类主要假设。agent 在这一步的动作是：先提出一个关于瓶颈的假设（例如“当前受限于全局访存带宽”），再请求 profile 验证，若指标与假设矛盾则修正假设。

这一步的机制价值在于把“猜”变成“证伪”。没有 profile 时，agent 只能靠 SOL 比值单调地试错，收敛慢且容易陷入局部改动；有了受限指标，agent 可以在两三轮内定位到是占用率不足还是访存模式低效。代价是采集本身的时延：NCU 需要重放 kernel 并多次采样以保证指标稳定，单次采集的墙钟时间显著高于普通运行，且会占用工具调用预算。工程判断是：profile 不应每轮都采，而应在 SOL 停滞或假设冲突时触发，否则采集开销会挤占本可用于代码迭代的轮次。

具体例子：一个逐元素算子，agent 假设受限于 DRAM 带宽并请求 profile，返回的 L2 命中率异常高、DRAM 吞吐占比低，证伪了假设，真实瓶颈是每线程工作量太少导致的启动开销占比过高。agent 随即改为每线程处理多个元素并向量化，SOL 提升。这一轮没有产生新的正确性风险，代价是一次 NCU 采集的时延与一段指标解读 token。

五 · 轮次记录：能力基线的计量口径

每一轮结束后记录三元组：轮次序号、该轮消耗的 token、该轮结束时的 SOL 与正确性状态。最终能力基线按开头给出的公式计量：分子是“正确且 SOL 达到阈值”的样本计数，分母是任务总数 N；成本是每任务 token 的均值。这个口径的关键在于阈值 θ 是事先固定的，不能事后按 agent 表现调整，否则基线会向有利方向漂移。轮次记录还保留“首次达到阈值所用轮次”这一辅助量，用于区分“最终能达标但很慢”与“快速达标”两类能力形态。

$$\text{capability}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\left[\text{correct}_i\land \text{SOL}_i\ge \theta\right],\quad \text{cost}=\frac{1}{N}\sum_i \text{tokens}_i$$

代价体现在 token 与轮次的乘积上：无提示时收敛慢，轮次多，每轮都伴随编译、运行、可能的 profile，token 成本按轮次线性累加。一个具体例子是同一算子在有提示脚手架下两三轮达标，而在仅目标驱动下需要更多轮次反复证伪假设，最终 SOL 可能刚好越过阈值也可能停在阈值之下——后者计入能力分母的失败侧，这正是基线偏低这一代价的计量体现，而非异常。

记录口径还必须防一类污染：agent 若在某轮偶然通过阈值后继续改动代码导致回退，最终状态应以“是否曾达标”还是“最终是否达标”计？基线取后者，因为生产部署看的是交付态而非历史峰值。这一选择抬高了难度，也让轨迹数据更贴近真实能力边界：能稳定收敛到阈值以上的模型，才在能力计量上得分。

六 · 对比步：脚手架增益的归因切分

最后一步是把仅目标驱动基线与带提示脚手架放在同一批任务、同一阈值 θ、同一 oracle 下对比，量化脚手架增益。归因切分的方式是：固定模型与工具集，只改变是否注入提示与模板，观察能力值与成本的差值。若脚手架带来的能力提升主要来自少数几类算子的模板复用，则增益是工程性的；若提升分布在多数算子上且伴随轮次下降，则提示确实补足了模型的先验缺口。这一判断不能靠单次对比得出，需要按算子族分层看差值。

这一步的代价是实验规模：对比需要两套完整轨迹，token 与工具调用翻倍，且要保证两套轨迹的 oracle 与阈值完全一致，否则差值无意义。具体例子：对矩阵乘类算子，带提示脚手架可能直接给出分块与向量化的起始模板，首轮即接近阈值；仅目标驱动基线则要从契约推导 tile 尺寸，轮次更多。两者能力值之差就是脚手架在该算子族上的增益，而这个差值是否可迁移到其他算子族，取决于提示是否过拟合了基准的 shape 分布——这正是隐藏 shape 抽样那条目要处理的问题，此处只作为对比步的边界条件指出。

工程判断落在最后：仅目标驱动基线的价值不在于它跑得快或省 token，而在于它给出的能力值是“可归因于模型”的下界。任何后续的脚手架、SFT 数据、RL 奖励设计，都应以这个下界为参照来判断增益是否真实。若某脚手架的能力值显著高于基线但成本也显著更高，则需要进一步切分是轮次换来的还是提示换来的——这一步的计量口径决定了整套评测的可信度，而不是某一个 kernel 的快慢。

目标驱动基线的失效边界与系统代价

这套“只给目标、不给提示”的流程在纸面上干净，落到工程里却有一条明确的失效线：当算子语义本身无法用输入输出契约完整表达时，agent 会退化成盲目搜索。典型例子是带状态或带副作用的算子，例如需要跨调用保持累加器的扫描类 kernel，契约里只写形状与 dtype，模型无法从一次编译-运行循环中判断状态语义是否正确，只能反复试错。此时正确性 oracle 的判定必须足够强，否则 $$\text{capability}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\left[\text{correct}_i\land \text{SOL}_i\ge \theta\right]$$ 里的指示函数会把“碰巧通过弱测试”的实现计入能力，基线被系统性高估。代价是测试生成环节的 token 与编译时间：每轮多写一个边界用例，就多一次编译与运行，而这类用例恰恰是最难自动生成的。

第二个失效条件是工具原语的粒度。只暴露编译、运行、NCU 采集三个原语，意味着 agent 拿不到源码级定位信息，profile 输出是一堆指标而非“哪一行 stall”。模型必须自己把指标映射回代码结构，这一步的先验知识差异极大：熟悉 roofline 的模型能从 SOL 与带宽利用率反推是访存合并问题还是占用率问题，不熟悉的模型只会反复调 block size。系统代价体现在轮次上——无提示时收敛轮次显著多于带提示脚手架，token 成本按 $$\text{cost}=\frac{1}{N}\sum_i \text{tokens}_i$$ 线性累积，且每轮都伴随一次真实编译与 GPU 运行，wall-clock 时延不可忽略。下表给出三类算子在该流程下的典型代价结构差异（定性）：

算子类型主要失效点代价重心
逐元素/归约几乎不失效，SOL 易达阈值轮次少，token 低
矩阵乘/卷积tiling 先验缺失导致长时间停在低 SOLNCU 采集次数多，编译时间长
扫描/带状态契约不足以判定正确性测试生成 token 高，误判风险大

第三层代价是基线本身的偏低偏差。剥离人工提示后性能上限受模型先验知识限制，达到的 SOL 往往低于带专家提示的脚手架，这不是缺陷而是度量目标：它给出的是“原生能力下界”。工程判断在于，这条基线不能直接用于生产部署选型，只能用于两件事——量化脚手架增益（同一模型跑两遍，差值即提示工程贡献），以及为 SFT/RL 提供贴近真实能力边界的轨迹。若把该基线的 SOL 当作部署预期，会把脚手架带来的收益误记为模型能力，进而在换模型时出现性能回退。
