一 · 一次评测翻车：正确性通过、收益为负

设想一个典型的长程 kernel 优化任务：给定一个 fused softmax 与 layernorm 的复合算子，要求在 A100 上把端到端时延压到 SOL 的某个比例以内，预算为 40 轮迭代。单 agent 的前 8 轮表现正常：它先修掉了一个越界写导致的正确性失败，随后把向量化宽度从 1 提到 4，时延下降明显。但从第 9 轮开始，轨迹变得可疑——每一轮它都在改写同一段内层循环，改动幅度越来越小，正确性 oracle 一直通过，时延却在基线附近震荡。到第 20 轮，上下文已经塞满了十几版几乎相同的源码 diff 与编译日志，模型开始遗忘最早那条“该 kernel 受限于 shared memory bank conflict 而非指令吞吐”的诊断结论，转而去调 occupancy 的 launch bound。第 35 轮，它提交了一个把 tile 从 32 改成 64 的版本，正确性通过，时延比历史最优慢 12%，但 agent 在上下文里把这次改动记成了“性能提升”，理由是“编译日志里没有报错且寄存器用量下降”。最终评测脚本按最后一轮提交计分，得到的是一个正确但比基线更慢的 kernel。

这不是假设性的失败模式，而是单 agent 长程优化的结构性缺陷在评测端的投影。它同时暴露了三件事：其一，局部最优——agent 在向量化这条局部路径上反复微调，从未跳出到 split-K 或双缓冲这类需要重构数据流的策略；其二，上下文膨胀——每轮的源码、编译输出、profile 摘要线性堆积，挤占了真正有用的诊断信息，导致早期结论被稀释；其三，缺少可信的收益判定——agent 自己既是实现者又是评判者，它对“这次改动是否值得保留”的判断没有独立于生成过程的证据支撑，于是把“编译通过”误当成“性能提升”。

更隐蔽的代价在预算利用率上。40 轮里真正产生有效改进的只有前 8 轮，后 32 轮的 token 消耗全部沉没。若按每轮平均消耗数千 token 的上下文与生成量估算，这意味着超过四分之三的预算被用于重复试错与自我确认，而不是搜索新的策略空间。评测翻车的根因不在模型能力，而在优化过程的组织方式：正确性修复、性能调优与架构决策被压缩进同一个上下文窗口、由同一个决策者串行处理，三者互相挤占注意力，且没有任何机制强制“回退到历史最优点”。

二 · 它到底解决什么：把单串行决策拆成可归因的角色流水线

策略协同多智能体进化针对的正是上述“三角矛盾”——正确性、性能、架构三件事在同一上下文里争夺预算。它的核心不是让多个模型投票，而是按认知职责切分：proposer 只负责提出策略（如 split-K、双缓冲、向量化），coder 只负责把策略落成可编译、可通过正确性 oracle 的源码，profiler 只负责读 NCU 指标与 SASS stall 分布并输出瓶颈归因（访存/计算/同步/占用率），critic 只负责对比基线时延与 SOL 并裁定 keep/revert。四者通过共享策略池与双记忆（成功策略 / 失败教训）协调，每轮的保留决策由 critic 单点作出。

这个切分解决的具体问题是归因断裂。在单 agent 里，“时延没降”这个观测无法被分解为“策略选错了”还是“实现写歪了”还是“瓶颈判断错了”。而在角色流水线中，profiler 的 NCU 归因是显式产物：如果它判定瓶颈在 shared memory bank conflict，那么下一轮 proposer 收到的就是这条结构化诊断，而不是一段混杂着编译警告的原始日志。coder 的失败（编译不过、oracle 不通过）与策略的失败（实现正确但时延不降）因此可以被分开记账，分别写入失败教训记忆的不同条目。

第二个问题是长程迭代中的策略复用。双记忆让成功策略可被后续轮次重新组合，失败教训则阻止 proposer 重复提交已被证伪的方向。这直接对应单 agent 的“收益递减”：当 agent 忘记早期结论时，它会重新走进同一条死胡同；而记忆把“哪些方向已证伪”外化成可检索的状态，使预算花在未探索区域。用公式表达每轮的保留判据：

$$\text{reward}_t=\mathbb{1}[\text{correct}]\cdot\left(\frac{T_{\text{best}}}{T_t}-1\right)-\lambda\cdot\text{tokens}_t,\quad \text{keep if }\ \text{reward}_t>\tau$$

这里 $T_{\text{best}}$ 是历史最优时延，$T_t$ 是本轮时延，$\lambda$ 把 token 开销折算进收益，$\tau$ 是保留阈值。这个式子的工程含义是：一个正确但更慢的版本 reward 为负，必须回退；一个更快的版本若 token 开销过大也可能不达阈值。它把“是否保留”从 agent 的自我叙述中剥离出来，交给 critic 用可计算量裁定——这正是单 agent 缺失的那道闸门。

三 · 角色流水线的单轮机制与信息流

一轮完整迭代的步骤是确定的：proposer 读取历史策略池与当前瓶颈诊断，提出 1–3 个候选策略；coder 按策略生成或修改源码，编译并跑正确性 oracle；profiler 采集 NCU 指标与 SASS stall 分布，输出瓶颈归因；critic 对比基线时延与 SOL，决定保留、回退或合并策略，并把结果写入双记忆；下一轮 proposer 基于更新后的记忆继续，直到预算耗尽或收敛。

关键机制在于诊断与生成的解耦。proposer 的输入不是原始 NCU 全量指标，而是 profiler 压缩后的归因结论；coder 的输入不是历史全部源码，而是当前最优版本加一条策略描述。这种窄接口降低了每个角色的上下文负担，使单轮 token 开销可控，但也引入了一个必须正视的失真通道：profiler 的归因若错了（例如把 bank conflict 误判为 occupancy 不足），这条错误诊断会直接传导给 proposer，导致后续若干轮都朝着错误方向搜索。因此 critic 除了裁定 keep/revert，还承担一致性校验——它需要检查本轮时延变化是否与 profiler 的归因方向自洽，若不自洽则标记该诊断存疑，避免污染策略池。

用伪代码表达 critic 的裁定逻辑：

  • 若 oracle 不通过：reward 记为负，写入失败教训（实现层），策略本身不判死，允许 coder 重试一次；
  • 若 oracle 通过且 $T_t < T_{\text{best}}$：按上式算 reward，超过 $\tau$ 则更新 $T_{\text{best}}$、写入成功策略，否则回退；
  • 若 oracle 通过但 $T_t \geq T_{\text{best}}$：reward 为负，回退，并把该策略标记为“在当前瓶颈下无效”，供 proposer 后续避让。

这套逻辑的代价是单轮时延：四个角色串行调用意味着每轮至少四次模型交互加一次编译加一次 NCU 采集。相比单 agent 的一次生成，单轮墙钟时间与 token 成本都显著更高。在预算紧张（例如总轮数少于 10）时，角色流水线的固定开销摊不平，性价比反而不如单 agent 直接试错——这是该方法明确的适用边界之一。

四 · 具体例子：bank conflict 诊断如何改变搜索方向

回到第一节的 fused 算子。假设第 9 轮 profiler 采集到 SASS 中 shared memory 的 stall 占比偏高，NCU 显示 shared load 的 wavefront 数远超理论值，归因结论为“bank conflict 主导，而非 occupancy”。这条诊断进入策略池后，proposer 在下一轮提出的是 padding 共享内存数组与改变访问步长，而不是继续调 launch bound。coder 实现 padding 版本，正确性通过，时延下降；critic 按公式算出正 reward，保留并写入成功策略。此后若某轮 proposer 又提出调 occupancy，critic 可以引用失败教训记忆里“occupancy 非瓶颈”的条目直接驳回，省下一整轮编译与采集。

对照单 agent 的轨迹：它在同一观测下大概率会去改 tile 大小或加 launch bound，因为这些改动在语法上更“安全”、diff 更小，且不需要理解 bank 的地址映射。这不是模型不懂 bank conflict，而是单上下文里“改一个数字”的即时反馈成本低于“重构访问模式”，agent 在局部搜索中被低成本动作吸引。角色分工把“理解瓶颈”和“写代码”拆给两个角色后，proposer 不必承担实现风险，因而更愿意提出结构性策略；coder 则专注于把结构性策略写对。这个例子的性能代价对比是具体的：padding 版本可能增加 shared memory 用量、轻微降低 occupancy，但消除了 bank conflict 的串行化 wavefront，净时延下降；而调 launch bound 的版本在瓶颈不在 occupancy 时几乎不产生可测变化，白白消耗一轮预算与数千 token。

五 · 它不解决什么：三条明确的失效边界

第一，它不解决 oracle 本身不可信的问题。角色流水线把正确性判定交给 critic，但 critic 依据的仍是 coder 跑的 oracle。若 oracle 覆盖不足（例如只测了单一 shape、未覆盖边界 dtype），一个数值错误的 kernel 可以通过全部轮次并被保留，profiler 与 proposer 再精细也无从发现。这类问题属于 checker 审计与参考 oracle 的范畴，多智能体协调无法替代。

第二，它不解决评测口径问题。若评分只看最后一轮提交而非历史最优，critic 的 keep/revert 机制会被评测脚本绕过——回退了也没用，因为计分取的是末轮。方法本身假设评测端尊重“保留历史最优点”的语义，这个假设不成立时，整套回退逻辑失效。同理，若基线时延锚定不稳（编译选项、时钟状态漂移），reward 公式里的 $T_{\text{best}}/T_t$ 就失去意义。

第三，它不解决搜索空间本身贫瘠的问题。若任务的可优化维度只有一两个（例如一个已经高度调优的 elementwise kernel），proposer 提出的 1–3 个策略很快穷尽，角色流水线退化为高开销的空转。此时多 agent 的通信与上下文管理成本成为纯负担，单 agent 的一次性尝试更划算。

此外还有一条内部代价必须计入：角色间信息传递失真。profiler 的归因是自然语言结论，proposer 读的是这段文字而非原始指标，任何措辞偏差都会被放大成搜索方向的偏移。critic 的一致性校验只能事后发现自洽性缺失，无法完全消除这条失真通道。工程上的缓解手段是让 profiler 输出结构化字段（瓶颈类别、置信依据、对应 NCU 指标名）而非自由文本，但这又增加了 profiler 的实现复杂度与 token 开销。

六 · 适用边界的工程判据

把上述分析收敛成可操作的判据：当任务同时具备“多类瓶颈可能共存（访存/计算/同步/占用率）”“单轮试错成本高到需要诊断先行”“预算足够摊平四角色固定开销”三个特征时，策略协同多智能体进化是合适的选择——典型如含 reduction、需要 split-K 决策的 GEMM 变体，或数据流可重构的 fused 算子。反之，当 oracle 覆盖薄弱、评测口径不尊重历史最优、或可优化维度极少时，应当先修 oracle 与评测合约，再谈协调机制；把多 agent 架在不可信的判定之上，只会以更高成本产出同样不可信的结果。

一个具体的工程判断落在预算分配上：若总轮数为 $N$，四角色流水线的单轮开销约为单 agent 的数倍，则有效搜索轮数约为 $N/4$ 量级。当这个有效轮数小于策略空间的最小探索深度（例如需要至少 6–8 轮才能覆盖 split-K、双缓冲、向量化、padding 四条主线）时，协调机制的收益无法覆盖其通信成本，应退回单 agent 加外部记忆的轻量方案。这个判据不需要实验数字，只需要对任务策略空间宽度与单轮成本的量级估计——它也是决定是否引入 profiler 角色的分水岭：只有当瓶颈归因确实能改变 proposer 的下一步动作时，这条诊断链路才值得它的 token 与失真代价。

多角色协同的失效边界：归因失真、预算错配与策略池污染

这套 proposer/coder/profiler/critic 分工真正解决的问题，是单 agent 在长程 kernel 优化中把“诊断”和“生成”耦合在同一段上下文里：一旦某轮 NCU 归因判断错了，后续所有源码修改都建立在这个错误前提上，而单 agent 没有独立角色去反驳自己。但它的适用边界很窄——只有当 kernel 的瓶颈能被 NCU 指标与 SASS stall 分布稳定区分（访存、计算、同步、占用率四类）时，profiler 的归因才有指导价值。若瓶颈来自编译器版本差异、驱动层调度或跨 kernel 的流水重叠，profiler 给出的 stall 归因会指向错误方向，proposer 据此提出的 split-K 或双缓冲策略就是无效试错。此时多角色反而放大了错误：单 agent 至少会在编译失败时立刻回退，而分工体系里 profiler 的错误诊断会经 critic 写入“失败教训”记忆，污染下一轮策略池。

失效条件的核心是角色间信息传递的失真率。profiler 输出的是归因标签，proposer 消费的是策略候选，两者之间没有形式化的语义契约，critic 只能靠对比基线时延与 SOL 做一致性校验——而时延对比本身有噪声。用奖励公式看，保留判据是 $$\text{reward}_t=\mathbb{1}[\text{correct}]\cdot\left(\frac{T_{\text{best}}}{T_t}-1\right)-\lambda\cdot\text{tokens}_t,\quad \text{keep if }\ \text{reward}_t>\tau$$ 其中 $$\lambda\cdot\text{tokens}_t$$ 在多 agent 下被四份上下文同时放大：proposer 读策略池、coder 读源码与 oracle 输出、profiler 读 NCU 原始指标、critic 读三方结论，单轮 token 成本显著高于单 agent。预算紧张时，$$\tau$$ 若设得过低，会把“时延略降但归因错误”的策略也 keep 进池子；设得过高，则正确但收益小的修复被回退，长程迭代提前收敛到局部最优。

失效模式触发条件系统代价
归因失真传导瓶颈跨 kernel 或受驱动影响，NCU stall 归因不唯一错误策略入池，后续轮次重复无效试错，token 与编译时间双重浪费
预算错配四角色上下文叠加，单轮 token 超单 agent 数倍总轮数被压缩，长程复用策略池的优势来不及兑现
策略池污染critic 一致性校验被时延噪声误导失败教训记忆误标，proposer 回避本可成功的 split-K 类策略

具体例子：某轮 profiler 把共享内存 bank conflict 误判为占用率不足，proposer 提出增大 block size 而非 padding，coder 实现后编译通过、正确性 oracle 通过，但时延仅微降；critic 因 $$\text{reward}_t>\tau$$ 而 keep，并把“增大 block size 有效”写入成功策略记忆。下一轮 proposer 复用该策略于另一个受限于寄存器的 kernel，直接触发寄存器溢出与 occupancy 崩塌，回退代价是一整轮编译加 oracle 验证。这说明该方案不解决“归因本身不可靠”的问题，也不替代形式化的正确性 oracle——它只优化“在归因可信前提下如何分配多轮预算”。工程判断是：只有当 profiler 的瓶颈分类能被 SASS 反汇编交叉验证、且单轮 token 预算足以支撑四角色各跑一轮时，这套协同才划算；否则应退回单 agent 加人工归因校验。
