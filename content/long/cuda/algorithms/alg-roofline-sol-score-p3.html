一 · 从 T_SOL 到 u_SOL：一次除法背后的两次取 max

评分公式本身只有一行，但它的推导链条上有两个容易踩空的地方。先把公式摆出来：

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$

第一个 max 是物理上的：一个 kernel 在给定硬件上不可能比“算完所有浮点运算所需时间”和“搬完所有 DRAM 字节所需时间”中较慢的那个更快，因为计算与访存是串联的流水阶段，不是可叠加的并行资源。第二个隐含的 max 出现在分子内部的两次除法之间——它们必须使用同一 dtype 口径的 P_peak。若 FLOP 统计的是 fp16 乘加而 P_peak 取的是 fp32 峰值，分子会被系统性高估，u 随之下跌，agent 收到的反馈会指向“计算太慢”，而真实瓶颈可能是访存。推导的关键一步不是公式变形，而是**口径对齐**：FLOP 的计数规则（是否把 FMA 记为 2 次、是否计入 bias/激活的逐元素运算）必须与 P_peak 的 dtype 语义一一对应。

把 u 改写成算术强度的函数，可以看到评分对 I 的分段敏感性。令 I=FLOP/Bytes，则 T_SOL = FLOP/P_peak · max(1, I*/I)，于是

$$u_{\text{SOL}}=\frac{\text{FLOP}}{P_{\text{peak}}\cdot T_{\text{gen}}}\cdot\max\left(1,\frac{I^{*}}{I}\right)$$

当 I≫I* 时 u 退化为纯计算效率 FLOP/(P_peak·T_gen)，Bytes 完全不出现在分数里；当 I≪I* 时 u 退化为纯带宽效率 Bytes/(B_peak·T_gen)，FLOP 被彻底忽略。这意味着同一个 kernel 在两种 shape 下可能落在完全不同的评分分支上，而 agent 若只看 u 的标量值，无法分辨自己是在被计算项还是访存项扣分。代价就出在这里：u 是一个把两条上限压成一维的标量，它丢掉了瓶颈类型这一维信息，必须靠 I 与 I* 的比较额外回传，否则反馈信号的梯度方向是模糊的。

具体例子：一个 elementwise 的 GELU 融合 kernel，FLOP 按每元素若干次超越函数近似计，Bytes 按读 4B 写 4B 计，I 落在个位数 FLOP/Byte 量级，远低于现代 GPU 的 I*（数十 FLOP/Byte），因此 T_SOL 由 Bytes/B_peak 决定。此时即便把超越函数换成多项式近似、砍掉一半 FLOP，u 也几乎不动——正确的优化方向是合并访存、提高向量化宽度、减少冗余读写。评分公式在这里给出的不是“你差多少”，而是“你差在哪条线上”，前提是调用方把 I 与 I* 一并记录。

二 · 时延项的实测口径：T_gen 到底测什么

T_gen 是分母，也是整个评分里唯一带测量噪声的量。它的口径必须写死三件事：测的是 kernel 本体还是含 launch 的端到端、是否包含 host-device 同步、是否取多次迭代的中位数或最小值。三者任一漂移，u 就会在样本间不可比。工程上推荐的口径是：CUDA event 包裹单次 kernel launch，warmup 若干次后取多次迭代的**中位数**，并显式排除首次 launch 的上下文初始化开销。取中位数而非最小值，是因为最小值会被缓存热态与频率boost 抬高的偶然样本污染，使 u 虚高；取中位数则对调度抖动稳健，代价是每次评分需要多跑若干次迭代，评测吞吐下降，长 kernel 上这一开销可观。

时延口径还有一个隐蔽代价：**同步点位置**。若在计时区间内插入 cudaDeviceSynchronize，测得的 T_gen 会包含 host 侧调度延迟，在短 kernel（微秒级）上这部分占比可能超过 kernel 本体，u 被系统性压低。反之若完全异步、只靠 event 记录，则必须保证 event 落在同一 stream 上且中间无其他工作插入，否则测到的是排队时间而非执行时间。这两种错误方向相反，前者让 agent 误以为还有优化空间，后者让 agent 误以为已接近上限而停止搜索——后者对 RL 训练更有害，因为它直接掐断了探索。

具体例子：一个 reduction kernel 在较小 shape 上执行时间进入个位数微秒区间，launch 开销与 event 开销同量级。此时若不做 warmup、不取中位数，T_gen 的样本间方差会吞掉真实的优化收益；agent 在两次迭代间做了 5% 的访存改进，评分却因噪声反向波动，keep-revert 搜索会把正确改动 revert 掉。解决办法是把评分样本的最小执行时间下限设为一个阈值，低于阈值的 shape 改用批量重复执行摊薄开销，代价是单样本评分时间上升。

三 · 显存与字节项：Bytes 的建模误差如何单向抬高 u

Bytes 是分子里最容易低估的量。理想模型按“读入张量元素数 × dtype 宽度 + 写出张量元素数 × dtype 宽度”计，但真实 kernel 存在三类额外流量：融合前的中间结果若未驻留寄存器或 shared memory 而落回 DRAM、tiling 带来的 halo 重叠读、以及原子操作与规约的多次往返。反过来，也存在**高估**的方向：若中间张量在 L2 中被复用，profiler 统计的 DRAM 字节数会低于朴素模型。两个方向中，低估更危险，因为它直接压低 T_SOL、抬高 u，让一个实际很差的 kernel 看起来接近上限。

把误差写成可校正的形式。设朴素模型字节为 B_model，真实 DRAM 字节为 B_true，则 u 的偏差为

$$\frac{u_{\text{model}}}{u_{\text{true}}}=\frac{\max\left(\text{FLOP}/P_{\text{peak}},\,B_{\text{model}}/B_{\text{peak}}\right)}{\max\left(\text{FLOP}/P_{\text{peak}},\,B_{\text{true}}/B_{\text{peak}}\right)}$$

在 memory-bound 分支上该比值退化为 B_model/B_true。若 B_model 因忽略 halo 重叠而比 B_true 小一个固定比例，u 就被同比例放大，且这个放大是**单向的、不可通过重复测量消除的**。因此工程上要求 Bytes 必须来自 profiler 的 DRAM 读写计数器，而非人工建模，人工建模只作为 profiler 不可用时的降级路径，并在评分元数据里标注来源，供下游区分可信样本与近似样本。

代价体现在评测流水线的时间预算上：profiler 采集（尤其 NCU 的 DRAM 计数器）会使 kernel 执行变慢数倍到数十倍，且需要串行化以避免计数器争用。对大批量 shape 抽样评测，这意味着 Bytes 采集必须与 T_gen 采集分离——前者用少量代表样本做校准，后者用全量样本做计时。校准样本的选择本身是个工程判断：应覆盖 compute-bound 与 memory-bound 两侧，否则校准出的 B_model/B_true 比值只在单一分支上有效。

具体例子：一个分块矩阵乘的融合 epilogue，朴素模型只计 A、B、C 三个张量的字节，忽略了分块边界处 A 行块被相邻输出块重复读取的 halo 流量。在块尺寸较小、L2 无法容纳整行块时，真实 DRAM 读放大约一到两倍，u_model 相应虚高。agent 若据此认为已接近带宽上限而停止优化块尺寸，就错过了把块调大以减少 halo 的真实收益。这正是 Bytes 建模误差从“评分不准”传导为“搜索方向错误”的路径。

四 · 误差项与经验系数：u 的绝对值为何需要校正

P_peak 是规格书上的理论峰值，真实可达上限低于它，原因包括频率未跑满、指令发射受限于 warp 调度、以及稀疏与稠密混合负载下的单元利用率差异。可用事实给出的经验区间是实际可达上限约为理论值的 70–85%。这意味着即便一个 kernel 已经榨干硬件，u 也只会落在 0.7–0.85 区间，而非接近 1。若评分不做校正，所有样本的 u 被统一压在一个偏低的带上，样本间的**相对**排序不受影响，但绝对阈值判定（例如“u>0.9 视为达标”）会永远无法触发。

校正方式有两种，代价不同。第一种是乘一个固定经验系数 α（落在上述区间内），把 u 折算为 u/α，使满分对应可达上限；代价是 α 随 dtype、随 kernel 的指令混合比变化，单一 α 会在 compute-bound 与 memory-bound 样本上引入系统性偏差。第二种是**按分支分别校正**：compute-bound 分支用实测的峰值达成率（通过一个已知最优的参考 kernel 标定），memory-bound 分支用实测的 stream 带宽达成率标定。后者更准，代价是需要维护一组标定 kernel，且标定本身要随驱动、频率策略变化而重跑，评测流水线多出一段固定开销。

误差项还应包含统计误差。u 是 T_SOL 与 T_gen 的比值，两者各自的相对误差会传播：

$$\frac{\delta u}{u}\approx\sqrt{\left(\frac{\delta T_{\text{SOL}}}{T_{\text{SOL}}}\right)^2+\left(\frac{\delta T_{\text{gen}}}{T_{\text{gen}}}\right)^2}$$

T_SOL 的误差来自 FLOP/Bytes 统计与 P_peak 口径，T_gen 的误差来自计时噪声。前者是系统性的、不随重复测量减小；后者是随机的、可通过增加迭代次数压低。因此评分报告里应把两者分开标注：系统误差决定 u 的可信区间宽度，随机误差决定样本间比较的分辨率。当两个候选 kernel 的 u 差值落在系统误差带内时，排序结论不可信，应触发复核而非直接采纳。

具体例子：两个实现同一算子的 kernel，u 分别为 0.62 与 0.65，而 Bytes 建模的系统误差带为 ±8%。此时 0.03 的差值远小于误差带，keep-revert 搜索若据此选择前者，等于在噪声上做决策。正确做法是把两者都送入 profiler 复核 Bytes 与瓶颈类型，确认差异是否来自真实的访存改进，再决定保留哪一个。这一步的代价是每个候选多一次 profile 采集，但它把“基于噪声的 revert”这一最昂贵的错误挡在门外。

五 · 奖励公式：从 u 到可训练信号的三次变换

u 本身不适合直接作为 RL 奖励，原因有三：它有物理上界（校正后约等于 1），导致梯度在接近上限时饱和；它在样本间方差不均（短 kernel 的 u 噪声大）；它对“是否更快”这一二值事实不敏感（u 从 0.60 到 0.61 与从 0.90 到 0.91 在奖励上应否等价，取决于任务）。因此奖励公式通常在 u 之上做三次变换：截断、归一化、与正确性门控相乘。

第一步截断：把 u 限制在 [0,1] 区间（校正后），对 u>1 的异常样本不奖励而是标记复核。第二步归一化：以同一 shape 上参考实现的 u_ref 为锚，奖励取 (u−u_ref)/max(u_ref, ε)，把“相对参考实现的效率增益”作为信号，消除 shape 间难度差异。第三步门控：乘以一个正确性指示量，只有通过 oracle 校验的实现才获得正奖励，错误实现获得固定惩罚而非零奖励——零奖励会让 agent 学到“不提交”也是安全策略。

具体例子：同一 shape 下参考实现 u_ref=0.55，生成实现 u=0.70，正确性通过，则奖励为 (0.70−0.55)/0.55≈0.27，裁剪后进入训练。若生成实现 u=0.58 但正确性失败，奖励为负的固定惩罚，agent 学到“快但错”不如“慢但对”。若 u=1.2 触发异常标记，该样本被剔除而非获得最高奖励——这一步至关重要，否则 agent 会学会利用测量漏洞（例如故意让 kernel 异步返回）来刷高 u。异常剔除的代价是有效样本率下降，在测量噪声大的短 kernel 上尤为明显，需要靠批量重复计时来把异常率压到可接受水平。

六 · 可实现性检查：公式落地时的四个接口约定

把上述公式变成可运行代码，需要四个接口约定，缺一个就会在批量评测中产生不可比的 u。约定一：**dtype 与 FLOP 计数规则**随样本元数据一起传递，P_peak 的选取由 dtype 字段查表决定，禁止在评分函数内部隐式推断。约定二：**Bytes 来源标记**（profiler / 人工模型 / 缓存），评分函数据此决定是否对 u 施加误差带，人工模型来源的样本在排序比较时降权。约定三：**T_gen 的计时口径**（迭代次数、warmup 次数、取中位数还是最小值）写入配置，评分函数只读配置不读全局默认值。约定四：**异常判据的阈值**（u>1 的容差、系统误差带宽度）作为显式参数，而非硬编码常数。

这四个约定的共同代价是配置复杂度：每个样本携带的元数据字段增加，评测流水线的序列化与校验开销上升，且任一字段缺失都会使该样本不可比而必须丢弃。收益是评分结果可审计——当一条 u 值被质疑时，可以沿四个字段回溯到具体的 dtype 口径、字节来源、计时口径与误差带，判断它是真实效率还是建模产物。对 agent 训练而言，可审计性直接决定了错误信号能否被定位并修正，而不是让 agent 在一个系统性偏移的奖励面上做无意义的搜索。

具体例子：一个样本的 u=0.88，看似接近校正后的上限，但元数据显示 Bytes 来源为人工模型、T_gen 取的是最小值。两个字段都指向 u 被高估的方向：人工模型可能漏计 halo 流量，最小值可能采到缓存热态样本。评分函数应把该样本标记为“近似可信”，在与 profiler 来源样本比较时降权，并触发一次复核采集。若复核后 u 降至 0.71，则此前基于 0.88 做出的“已接近上限、停止优化”判断被推翻——这正是接口约定存在的意义：它不阻止误差发生，但阻止误差无声地进入训练信号。

最后一个工程判断落在评分函数的返回值形态上。只返回标量 u 是不够的，应返回一个结构：u、瓶颈类型（由 I 与 I* 比较得出）、误差带宽度、可信度标记。下游的奖励计算、keep-revert 决策、以及人工复核都消费这个结构而非单个数字。标量 u 适合做看板展示，结构化的评分结果才适合做训练信号——因为 agent 需要知道的不只是“差多少”，还有“差在哪条线上、这个差值是否可信”。
