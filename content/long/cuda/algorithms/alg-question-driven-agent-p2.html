一 · 从指标到可证伪问题：诊断环的入口

问题驱动诊断式优化的第一步不是改代码，而是把 NCU/SASS 指标翻译成一句能被实验判定的命题。agent 拿到的原始输入通常是一组结构化计数器：smsp__warp_issue_stalled_* 的 stall 分布、l1tex__data_bank_conflicts、sm__throughput 与 dram__throughput 的比值、以及 SASS 里每个基本块的指令混合。这些数字本身不构成结论，它们只是证据的原料。机制上，agent 需要先做一次「指标归因」：把 stall 占比最高的若干项与代码结构对齐，例如 stall_long_scoreboard 高指向全局访存延迟未被覆盖，stall_short_scoreboard 高指向 shared memory 或常量访存，stall_mio_throttle 高指向 MIO 队列拥塞（shared/LDS 指令密度过大）。归因完成后，agent 生成 1–3 个关于瓶颈根因的可证伪问题，每个问题必须满足两个条件：能用一次单变量实验回答「是/否/部分」，且答案会改变下一步动作。

一个合格的提问形如：「是否 shared memory bank conflict 导致 stall_short_scoreboard 占比偏高？」这个问题的可证伪性来自它绑定了一个可观测判据——若在 tile 的列维加 padding 后该 stall 项显著下降，则答案为是；若不变，则为否。不合格的提问是「如何让 kernel 更快」，因为它不约束变量、不给出判据，实验设计无从下手。提问环节的代价是 token 与推理时延：agent 需要读取指标摘要、对齐源码行号、写出问题与判据，通常消耗数百到上千 token 的上下文，并且这一步不产生任何性能收益，纯粹是诊断投资。代价的回报体现在后续轮次：一个定位准确的问题可以把「试五种 tile 尺寸」压缩成「一次 padding 实验」。

输入是 profile 摘要加源码片段，输出是问题列表及其判据。这里的关键工程判断是问题数量的上限：1–3 个问题对应 1–3 个微实验，若一轮内问题过多，实验预算被摊薄，单变量控制也会失效。问题库在这一步被查询——历史上同类 kernel、同类 stall 模式对应的已验证问题会被优先复用，减少重复提问的 token 开销。

二 · 最小微实验的设计：单变量与可观测判据

每个问题对应一个微实验，微实验的设计原则是「只变一个变量」。具体到 GPU kernel，可变的单变量包括：tile 尺寸（如从 64×64 改到 64×32）、shared memory 的 swizzle 模式、padding 宽度、pipeline 深度（双缓冲改三缓冲）、线程块内 warp 的映射方式、以及访存指令的向量宽度。选择哪一个变量由问题决定：bank conflict 问题对应 padding 或 swizzle；延迟覆盖不足对应 pipeline 深度；寄存器压力导致 occupancy 受限则对应 tile 缩小。实验的输入是原始 kernel 加一个受控的变异参数，输出是该变异下的指标快照与耗时。

微实验的代价必须被显式记账。编译时间是最容易被忽略的一项：一次 CUDA C++ 重编译在中等规模 kernel 上是秒级，但如果 agent 每轮做三到五个变异，编译开销会累积成可观的墙钟时间；Triton 的 JIT 编译同样有首次编译成本，autotune 式的多配置编译会把这一成本放大。运行代价包括正确性校验（与参考实现比对）与性能测量（多次迭代取中位数以压制噪声）。显存代价在 tile 放大类实验中会显现：更大的 tile 意味着更大的 shared memory 占用，可能把 occupancy 从多个 block 压到单个 block，这个副作用本身会污染实验结论，因此微实验必须记录 occupancy 作为协变量。

$$\Delta_{\text{opt}}=\frac{T_{\text{after}}-T_{\text{before}}}{T_{\text{before}}},\quad \text{accept if }\ \Delta_{\text{opt}}<-\epsilon\ \land\ \text{correct}$$

上式是微实验的判定式：只有相对改善超过阈值 ε 且正确性通过，变异才被接受。ε 的设定直接决定假阳性率——测量噪声在短 kernel 上可以轻易达到几个百分点，若 ε 过小，agent 会把噪声当成信号，把无效变异写进代码库。工程上常用的做法是把 ε 绑定到测量方差：先对基线做多次重复测量估计方差，再令 ε 为方差的若干倍。这个判定式与后续的保留/回退逻辑共用，但本步只负责产出「这个变异是否回答了问题」的证据，不负责决定是否合入。

一个具体例子：问题是「bank conflict 是否为 stall_short_scoreboard 的主因」。微实验保持 tile 尺寸、线程数、数据布局不变，仅把 shared memory 数组的列维从 32 改为 33（padding 一格）。若该 stall 项占比下降且总耗时改善超过 ε，答案为是，证据是「padding 后 conflict 计数下降、stall 项下降、耗时下降」三者同向；若 conflict 计数下降但耗时不变，答案为「部分」——说明 conflict 不是关键路径上的瓶颈，agent 应转向下一个问题而不是继续在 shared memory 上做文章。这种「指标改善但端到端不变」的情形正是单变量实验的价值所在：它阻止了 agent 把局部指标当成优化目标。

三 · 证据采集与答案判定：三态结论的记账

实验运行后，agent 采集指标并回答问题是/否/部分。三态而非二态是这一步的核心设计：GPU 瓶颈常常是多因耦合，一个变量改动后目标指标下降但另一指标上升，或者目标指标下降而端到端耗时不变，这些都属于「部分」。判定规则需要在实验设计时就写死，避免事后解释。典型判据组合是：目标 stall 项或冲突计数的相对变化、端到端耗时的相对变化、以及正确性是否通过。三者同向且超过阈值判「是」；目标指标变化显著但端到端不变判「部分」；目标指标不变判「否」。

证据的记录格式决定了这条轨迹能否被复用。每条证据至少包含：问题文本、变异描述（哪个变量、从什么改到什么）、基线指标、变异后指标、判定结论、以及一条「若答案为否则下一步转向何处」的备注。这条备注是防止 agent 在错误方向上反复试探的关键——当答案为否时，agent 不应重试同类变异，而应依据备注切换到下一个候选根因。证据的存储代价是上下文长度：每轮三态结论加指标快照会占用可观的 token，若全部塞进下一轮 prompt，上下文会迅速膨胀。工程做法是对证据做摘要压缩，只保留判定结论与关键指标差值，原始快照落盘供人工审计。

这一步的性能代价是测量本身：为了压制噪声，每个变异配置需要多次迭代与多次重复，短 kernel 上测量开销可能超过 kernel 本身的执行时间。正确性代价则体现在 fp64 参考或高精度比对的运行成本上——微实验虽然只变一个变量，但每个变异都必须过正确性门，否则一个「更快但算错」的变异会被误判为有效。一个具体例子：pipeline 深度从 2 改到 3 后耗时下降，但正确性比对在边界 shape 上失败，判定应为「否」并记录「深度增加引入的同步缺失导致越界」，这条证据直接进入问题库，下一轮同类 kernel 会先检查同步而非先调深度。

四 · 从答案到动作：修改、编译、验证的串联

拿到「是」或「部分」的答案后，agent 才进入修改环节。动作的选择由答案直接约束：bank conflict 为「是」则动作是 padding 或 swizzle 落地到正式代码；延迟覆盖不足为「是」则动作是调整 pipeline 或预取；occupancy 受限为「是」则动作是缩小 tile 或削减寄存器。这一步的输入是证据加当前 kernel 源码，输出是候选修改。修改必须与微实验的变异保持语义一致——微实验验证的是「padding 有效」，正式修改就应是同一 padding 策略的系统化应用，而不是另起炉灶换一种布局，否则实验证据与最终代码之间出现断裂，诊断环失去意义。

修改后的串联验证包含三段：编译、正确性、性能。编译失败是最廉价的失败，agent 应在此处快速回退而不是试图修补编译错误——修补会引入未经验证的第二个变量，破坏单变量原则。正确性验证使用与微实验相同的 oracle，但覆盖面更广：微实验可能只跑一个代表性 shape，正式修改则要过完整的 shape 集合与边界条件。性能验证使用判定式，只有 Δ 超过 ε 才保留。这三段的代价依次递增：编译是秒级，正确性验证是秒到分钟级（取决于 shape 集合大小与参考实现的精度），性能验证则需要重复测量。工程判断是把最便宜的检查放在最前面，让失败尽早暴露。

一个具体例子：微实验回答「swizzle 能降低 conflict」为是，正式修改把 swizzle 应用到所有 shared memory 访问点。编译通过，但正确性在非方阵 tile 上失败——原因是 swizzle 的索引映射假设了方阵。此时 agent 的正确动作不是回退整个 swizzle，而是把修改收窄到方阵分支，并在问题库中记录「swizzle 的适用条件包含方阵假设」。这条记录让下一轮的问题从「swizzle 是否有效」升级为「非方阵下何种布局等价有效」，问题质量随轮次提升。

五 · 保留、更新问题库与预算终止

有效修改被保留，无效修改被回退，问题库被更新。保留的判据就是判定式，但保留动作本身有代价：每次保留意味着代码库的一次变更，若多轮修改叠加，代码会逐渐偏离原始结构，后续诊断的归因难度上升。工程上常见的约束是限制单轮保留的修改数量，并在保留时记录该修改解决了哪个问题，使代码变更与问题一一对应。问题库的更新包含两类条目：被证实的问题（附判据与有效动作）与被证伪的问题（附反例与转向建议）。前者加速后续同类 kernel 的诊断，后者防止 agent 重走死路。

终止条件有两个：瓶颈消除或预算耗尽。瓶颈消除的判据不是「没有更多问题可问」，而是「当前 profile 下已无超过阈值的 stall 项或吞吐差距」——这需要一次收尾 profile 来确认，其代价是一次完整的 NCU 采集。预算耗尽的判据是轮次上限、token 上限或墙钟上限中的任一个先到。预算紧张时，诊断环的性价比下降：每轮多出的提问与微实验开销在轮次少时无法摊薄，此时直接搜索（变异+判定式，不提问）反而更划算。这是一个明确的工程取舍，而不是诊断环的缺陷——诊断环的收益随轮次增加而累积，因为它把每一轮的证据沉淀进问题库，使后续轮次的提问更准、实验更少。

问题质量的依赖是这套机制的结构性风险：问题提错会把 agent 引向错误优化方向，且错误方向上的实验同样消耗预算。缓解手段是问题库的复用与判据的严格化——判据越具体，错误问题越容易在实验阶段被证伪而不是被误信。一个具体例子：agent 提问「是否 L2 命中率低导致延迟」，但该 kernel 的数据集远小于 L2，问题本身不成立；微实验中改预取策略后 L2 命中率不变、耗时不变，判定为否，问题库记录「该 shape 下 L2 非瓶颈」，下一轮不再重复此问。这次证伪消耗了一轮预算，但换来了问题库的一条负知识。

这张表的意义在于把每一步的代价显式化：诊断环不是免费的，它用 token、编译时间和测量开销换取定位精度。工程判断落在预算分配上——当轮次预算充足且瓶颈耦合复杂时，诊断环的边际收益稳定；当预算只够一两轮时，直接搜索的单轮产出更高。诊断环的适用边界由此确定：它服务于多轮迭代场景，其价值随问题库的积累而增长，而不是在单轮内兑现。

假设闭环的边界：何时值得问，何时该直接改

这套“先提问、再微实验”的流程并非无条件占优。它的收益来自把一次昂贵的修改替换成一次廉价的判别：当候选优化动作的验证成本远高于单变量微实验时，闭环才划算。设一次完整修改-编译-正确性-性能验证的代价为 Cmod（含编译时间、正确性 oracle 调用、基准计时与 token 消耗），一次微实验的代价为 Cexp，则只有当命中真实瓶颈的先验概率 p 满足 p·Cmod > Cexp 时，提问才在期望上省时。反过来，若 kernel 处于明显的粗粒度瓶颈（如全局访存完全未合并、occupancy 被寄存器压力压到极低），NCU 指标已经给出近乎确定的结论，此时再设计微实验只是把确定性判断重新包装成一次实验，纯属增加轮次成本。

$$\mathbb{E}[\text{save}] = p\cdot C_{\text{mod}} - C_{\text{exp}},\quad \text{probe only if } \mathbb{E}[\text{save}]>0$$

失效条件集中在两处。其一是问题质量：agent 若把“stall 高”直接翻译成“bank conflict”，而真实根因是长依赖链导致的 latency 未隐藏，那么后续所有单变量实验都在错误的假设空间里搜索，微实验会给出“否”的答案却无法排除其他候选，轮次被消耗在否定错误假设上，边际收益趋零。其二是单变量约束本身：改 tile 形状往往同时改变 shared memory 占用、合并访问模式与寄存器压力，所谓“只变一个变量”在 CUDA 上常常是近似而非严格成立，实验结论因此带有混淆项，需要靠重复实验或对照实验来剥离。

情形推荐动作主要代价

系统代价还体现在诊断轨迹的存储与筛选上：每轮的问题、实验配置、指标快照与结论构成一条结构化记录，用于 SFT 时必须过滤掉“问题提错但实验偶然通过”的样本，否则会把错误归因模式固化进模型。工程判断是：把闭环当作预算受限的自适应策略，在轮次预算充足且瓶颈归因不确定时启用，在指标已给出强信号或预算紧张时降级为直接修改，并用 Δopt 的接受准则守住正确性底线。
