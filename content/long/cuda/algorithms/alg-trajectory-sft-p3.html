一 · 损失函数的分母：为什么只对成功集合求和

先把给定公式摊开看结构：

$$\mathcal{L}_{\text{SFT}}=-\sum_{(s,a)\in\mathcal{D}_{\text{succ}}}\log\pi_\theta(a\mid s),\quad \mathcal{D}_{\text{succ}}=\{(s,a):\text{correct}\land \text{speedup}\ge 1\}$$

这个式子里真正承载工程判断的不是负对数似然本身，而是集合 \(\mathcal{D}_{\text{succ}}\) 的定义。它是一个合取条件：正确 与 加速不低于 1 同时成立。把这两项写成指示函数，等价于

$$\mathcal{D}_{\text{succ}}=\{(s,a):\mathbb{1}[\text{pass}(a)]\cdot\mathbb{1}[\text{speedup}(a)\ge 1]=1\}$$

关键一步在于：这个指示函数是不可导的硬门，它作用在数据构造阶段而非损失内部。也就是说，梯度不会因为一个样本“差一点就加速”而获得任何部分信用——要么整条轨迹进集合，要么整条被丢弃。这与 RL 里用软奖励 shaping 的做法形成对照：SFT 把筛选责任前置到数据管线，损失本身退化为最朴素的 token 级交叉熵。代价是数据利用率：一条轨迹若最终正确但 speedup 停在 0.98，它贡献的稠密监督被整体归零，收集成本（强 agent 多轮 GPU 时间）无法回收。收益是训练稳定性：损失面上不存在“奖励 hacking 梯度”，模型无法通过输出讨喜但错误的 kernel 来降低 loss。

另一个容易忽略的点是求和范围。公式对所有 \((s,a)\) 对等权求和，意味着一条轨迹里每个“状态+反馈 → 下一步动作”的训练对权重相同。但一条成功轨迹中，前几轮的诊断动作往往比末尾的微调动作信息量更大——末尾动作常常只是把已经正确的代码做常量折叠。等权求和的直接后果是：模型在长轨迹尾部学到的“确认式修改”被过度强化，而真正稀缺的“从错误反馈中定位瓶颈”被稀释。工程上可行的补偿不是改损失形式，而是在切分阶段对训练对做重采样（例如对含编译错误、含 NCU 反压的中间状态多切几份），这仍落在 \(\mathcal{D}_{\text{succ}}\) 内部，不破坏公式的硬门语义。

具体例子：某算子轨迹共 6 轮，前 3 轮在修 shared memory 越界与 bank conflict，第 4 轮通过正确性，第 5、6 轮把 tile 从 32 调到 64 拿到 1.3×。按公式，6 轮全部进集合、等权；但若按信息量重采样，前 3 轮每轮切 3 份、后 3 轮各切 1 份，则同一轨迹贡献 12 个训练对而非 6 个。代价是单条轨迹的 token 预算翻倍，需在数据配比时用算子池的难度分层来抵消。

二 · 时延项：speedup 的测量口径决定了门的松紧

\(\text{speedup}\ge 1\) 看似简单，但它隐含一个测量口径问题：分子分母各自测什么。写成比值形式，

$$\text{speedup}=\frac{T_{\text{ref}}}{T_{\text{cand}}},\quad T=\text{median}\big(\text{kernel time per launch}\big)$$

推导的关键一步是把 \(T\) 定义为单次 launch 的 kernel 时间中位数，而不是端到端 wall time，也不是包含 host 侧 launch 开销的迭代时间。理由：SFT 要蒸馏的是 kernel 内部的诊断与改写能力，若把 host 开销混进分母，一个正确但 launch 配置保守的 kernel 会因为 Python 侧同步而显得“没加速”，从而被硬门误杀。用中位数而非均值，是为了让第一次 launch 的冷启动（含 JIT、L2 未预热）不污染统计。

这个口径带来两个可计算的代价。其一，测量本身消耗 GPU 时间：每条候选 kernel 需要 warmup 若干次加多次计时，若算子池规模为 \(N\)、每条轨迹平均 \(R\) 轮、每轮 \(K\) 次计时，则计时总次数约为 \(N\cdot R\cdot K\)，这是数据生产成本里被低估的一块。其二，中位数对长尾不敏感：若候选 kernel 存在偶发的严重 stall（例如某个 warp 在边界 tile 上退化），中位数仍可能显示加速，硬门放行，但 SFT 数据里就混入了“平均快、尾部慢”的样本，模型学到的是不稳健的优化模式。缓解手段是在门内追加一个离散度约束（如要求 p90 与中位数之比不超过某阈值），但这会把公式里的单标量门变成二维门，需要在数据管线里显式实现，而不是塞进损失。

具体例子：一个 reduction kernel 参考实现 \(T_{\text{ref}}\) 取中位数，候选版本把 block 从 256 改到 1024，中位数时间下降，speedup 记为 1.15 通过硬门；但该候选在最后一个不满 tile 上触发 warp 发散，p90 时间反而高于参考。若只看中位数，这条轨迹进 SFT 集合，模型会把“盲目增大 block”当作有效诊断动作学到。加入 p90 约束后该轨迹被剔除，代价是合格轨迹数量下降，需扩大算子池来补足数据量。

三 · 显存与误差项：正确性判定的两个隐藏维度

公式里 \(\text{correct}\) 是一个布尔量，但它背后至少有两层可推导的判据：数值误差界与显存占用。先看误差。对浮点 kernel，逐元素比较通常写成

$$\text{pass}=\bigwedge_i\Big(|y_i-\hat{y}_i|\le \tau_a+\tau_r\cdot|y_i|\Big)$$

即绝对容差与相对容差取和。关键一步在于 \(\tau_r\) 必须按算子类型分层：归约类算子（sum、softmax 分母）的误差随累加长度增长，若用逐元素同一条相对容差，长归约会在合法实现上误判失败，把正确轨迹挡在门外。代价是分层容差表本身成为数据管线的一部分，需要与 fp64 参考 oracle 的构造口径对齐——否则 SFT 集合里会混入“因为容差过松而侥幸通过”的样本，模型学到的是数值上不可靠的写法。

显存维度更隐蔽。一个 kernel 可以正确且加速，但通过临时缓冲区把峰值显存抬高到超出预算，这种样本若进 SFT，模型会学到“用空间换时间”的激进模式，在部署端触发 OOM。把显存写成约束：

$$\text{mem}_{\text{peak}}=\max_t\big(\text{alloc}(t)\big)\le M_{\text{budget}}$$

其中 \(t\) 遍历 launch 生命周期内的分配事件。推导的关键一步是 \(\text{mem}_{\text{peak}}\) 必须按生命周期峰值而非总分配量计——总分配量会把复用同一缓冲区的实现误判为高占用。实现上这要求轨迹记录里保留每次分配的时序，而不是只留一个汇总数。代价是记录粒度变细，轨迹存储体积上升；收益是硬门能挡住“以显存换加速”的轨迹，避免 SFT 把部署端风险蒸馏进模型。

具体例子：某 attention 变体把 K/V 全量驻留 shared memory 换取 1.2× 加速，逐元素误差在分层容差内通过，但峰值显存因多开一块 staging buffer 超出预算。若硬门只查 correct 与 speedup，该轨迹进集合；加入显存约束后剔除，模型转而学到分块加载的模式。代价是合格轨迹减少，需在算子池里补充显存受限的变体来维持数据量。

四 · 奖励与过滤的合取结构：把硬门写成可执行伪代码

把上面三项合起来，过滤逻辑不是单一评分而是合取门。可实现的伪代码思路如下（伪代码，非可运行代码）：

  • 对每条轨迹 \(t\)：解析最终 kernel 源码与每轮反馈记录；
  • 若源码含硬编码输出、按 shape 分支的特判、或对参考实现的直接调用 → 标记 cheat，整条丢弃；
  • 跑正确性：与 fp64 参考逐元素比，按算子类型取分层 \((\tau_a,\tau_r)\)，全元素通过才置 correct；
  • 跑计时：warmup 后取 kernel 时间中位数，算 speedup，并要求 p90/median 不超过离散度阈值；
  • 查显存：按分配时序算生命周期峰值，与预算比；
  • 四项全真才把该轨迹切分为 \((s,a)\) 对写入 \(\mathcal{D}_{\text{succ}}\)；任一项假则整条丢弃，不做部分保留。

这个结构的工程含义是：过滤是全或无的，而不是加权求和后取阈值。合取门的好处是每一项都可独立审计、独立变异测试；坏处是合格率是各项通过率的乘积，任一项过严都会让数据量指数级萎缩。设四项通过率分别为 \(p_1..p_4\)，则合格率约为 \(\prod p_i\)——这就是为什么轨迹收集必须依赖强 agent 的大预算：单条轨迹成本高，而合取门又砍掉大部分产出，只有靠算子池宽度与轮数来摊薄。

具体例子：某批 4 条轨迹，正确性通过 3 条、计时通过 2 条、显存通过 3 条、无作弊 4 条，合取后只剩 1 条进入 SFT 集合。若把门改成加权评分（例如正确 0.4、加速 0.3、显存 0.2、洁净 0.1，总分过线即收），可能收进 2–3 条，但其中会混入显存超标的样本。选择合取还是加权，取决于部署端对 OOM 的容忍度——这是工程判断，不是公式推导能给出的。

五 · 切分与 token 预算：从轨迹到训练对的推导

过滤之后是切分。一条轨迹是 \((c_0,f_0,d_0,c_1,f_1,d_1,\dots,c_T)\) 的序列，其中 \(c\) 是代码、\(f\) 是执行反馈、\(d\) 是决策。切分的目标是构造 \((s,a)\) 对，使 \(s\) 包含“当前代码 + 反馈”，\(a\) 是“下一步修改”。写成

$$s_i=(c_i,f_i),\quad a_i=\Delta(c_i\to c_{i+1}),\quad |\mathcal{D}_{\text{succ}}|=\sum_{t}\sum_{i=0}^{T-1}1$$

关键一步是把动作定义为差分 \(\Delta\) 而非完整重写。理由：若 \(a_i\) 是整段新代码，模型学到的是“每次从头写”，而这恰是 SFT 要纠正的盲目重写行为；差分形式迫使模型在反馈条件下做局部诊断。代价是差分需要规范化（空白、变量重命名），否则同一语义修改会产生多个 token 序列，稀释监督密度；规范化本身要写进数据管线，且规范化过强会抹掉有信息量的重命名（例如把 `acc` 改成 `partial_sum` 反映累加语义）。

token 预算可以直接推导：设每条轨迹平均 \(T\) 轮、每轮状态含代码 \(L_c\) token 与反馈 \(L_f\) token、动作 \(L_a\) token，则单条轨迹贡献约 \(T\cdot(L_c+L_f+L_a)\) token。若算子池 \(N\) 个、合格率 \(\prod p_i\)，总 token 量约为 \(N\cdot\prod p_i\cdot T\cdot(L_c+L_f+L_a)\)。这个式子说明：提高合格率（放宽门）与提高轮数（加深轨迹）在 token 预算上是可互换的，但两者对模型的影响不同——放宽门引入噪声样本，加深轮数引入更长的上下文依赖。工程上通常优先加深轮数，因为长程诊断正是 RL 冷启动最缺的能力。

具体例子：某轨迹 5 轮，每轮代码 400 token、反馈 150 token、差分动作 80 token，单条贡献约 3150 token；若合格率乘积为 0.25、算子池 200 个，总量约 15.7 万 token 量级。这个量级对 SFT 而言偏小，说明要么扩大算子池，要么对高信息量轮次做重采样——后者正是第一节里提到的等权求和补偿手段。

六 · 过拟合项的量化视角：held-out 上的泛化缺口

代价里写明“SFT 易过拟合训练算子的模式”。把它写成可观测的量：设训练算子集上的首轮正确率为 \(A_{\text{train}}\)，held-out 算子集上为 \(A_{\text{held}}\)，则泛化缺口

$$\text{gap}=A_{\text{train}}-A_{\text{held}}$$

推导的关键一步是：这个 gap 不是模型能力的度量，而是数据分布覆盖度的度量。若轨迹收集只在少数算子族上做深，模型学到的是这些族的诊断模板（例如“看到 bank conflict 就换 padding”），在 held-out 上模板失效，gap 拉大。因此 gap 的合理解释必须与控制变量绑定：同一基座、同一 SFT 步数、同一 held-out 划分，否则 gap 里混入了训练步数与数据量的差异。

工程上，gap 的用途不是事后报告，而是数据管线的反馈信号：若 gap 超过阈值，说明算子池的族覆盖不足，应补充 held-out 邻近族的轨迹，而不是简单增加同族轨迹数量——后者只会让 \(A_{\text{train}}\) 更高、gap 更大。代价是补充邻近族轨迹需要重新跑强 agent，GPU 时间成本与首轮收集同量级；收益是 SFT 后的模型作为 RL 初始化时，首轮加速的方差更小，RL 冷启动更稳。

具体例子：训练集集中在 GEMM 与 reduction 两族，held-out 含 scan 与 sort。SFT 后 GEMM 首轮正确率高，scan 上模型仍倾向于套用 reduction 的 tile 模板，gap 明显。此时正确动作不是加大 GEMM 轨迹量，而是补 scan 族的成功轨迹——scan 的跨步依赖与 reduction 的树形归约在诊断模式上不同，正是 gap 的来源。这一步做完后，\(\mathcal{D}_{\text{succ}}\) 的构成变了，但损失公式不变，说明公式的稳定性来自硬门语义而非数据分布假设。

成功轨迹蒸馏的边界：过滤口径、分布偏移与生产代价

该目标函数看似只做一件事——在成功集合上最大化对数似然，但它的全部效力都压在集合定义的两个合取项上。第一项 correct 由正确性 oracle 判定，第二项 speedup≥1 则把“能跑对但更慢”的轨迹一并排除。这意味着过滤阈值本身就是超参：若把加速门槛抬到 1.2 或 1.5，数据量骤减而信号更纯；若放宽到 1.0，则混入大量“刚好不退化”的样本，模型学到的是保守改写而非真正优化。更隐蔽的失效条件是作弊轨迹——硬编码输出、绕过边界检查、针对测试形状特化——它们同样满足 correct∧speedup≥1，却把“利用反馈”蒸馏成了“利用评测漏洞”。因此过滤必须包含反作弊检查（形状扰动重测、输入随机化、源码模式扫描），否则 SFT 阶段就把奖励黑客行为固化进策略，后续 RL 再难纠正。

轨迹切分决定了监督的粒度。把一条长程轨迹拆成 (状态+反馈 → 下一步动作) 的训练对，等价于对每个决策点做行为克隆；其代价是误差沿轨迹累积：若单步动作匹配率为 p，长度 L 的轨迹端到端成功率为 p^L，长轨迹的尾部步骤在数据中占比高但可学习性差。工程上常对轨迹做加权或截断，只保留“诊断→修改→验证通过”的关键跳转，牺牲稠密性换取信噪比。另一项系统代价是分布偏移：SFT 数据全部来自强 agent 的成功路径，模型学到的是“在已接近正确的代码上做局部修补”，而 RL 初始阶段面对的往往是错误百出的自采样 kernel，状态分布不匹配会让蒸馏出的诊断模式失效。held-out 算子上的正确率与首轮加速正是用来度量这一偏移的探针，而非训练指标。

生产成本落在采集侧而非训练侧。每条轨迹需要强 agent 多轮迭代、每轮编译与执行验证，GPU 时间随算子池规模与预算线性增长；一条含十余轮修改的轨迹，其验证开销远高于单次前向。相比之下 SFT 本身只是常规监督微调，成本可控。真正的工程判断是：把预算花在“扩大算子多样性”还是“加深单算子优化轮数”上——前者缓解过拟合训练算子模式的风险，后者提升轨迹的诊断深度。跨算子泛化无法靠 SFT 单独保证，必须由 held-out 校验与后续 RL 修正兜底。
