一 · 候选池生成与静态打分：把 GPU 时间挡在门外

预算感知搜索的第一步不是编译，而是造池子。一次 kernel 任务进来，agent 先按策略族展开候选：同一算子可以派生 tile 尺寸不同的版本、向量化宽度不同的版本、共享内存分块策略不同的版本、寄存器压力取向不同的版本。池子的宽度由剩余预算和任务难度共同决定——预算紧时池子窄而深，预算松时池子宽而浅。这一步的输入是算子语义描述、shape 分布摘要（前文已讲抽样，此处只当作已就绪的输入张量）、以及历史成功率先验；输出是一组待打分的候选描述符，每个描述符携带静态特征向量 φ_i。

静态特征的选择直接决定粗筛的信噪比。可用的是三类：访存模式（是否合并访问、是否有 bank conflict 风险、全局访存与共享访存的字节比）、tile 尺寸与线程块形状（能否被 shape 整除、边界判断的额外分支数）、占用率估计（由寄存器用量与共享内存用量反推每 SM 可驻留的 block 数）。这三类特征全部来自源码文本与编译前的资源估算，不消耗 GPU 时间，只消耗 token——agent 要为每个候选写一段描述并抽取特征，这是本步骤的主要成本项。

打分公式就是预算分配公式的分子部分：

$$\text{alloc}_i=B\cdot\frac{\hat{p}_i^{\alpha}}{\sum_j \hat{p}_j^{\alpha}},\quad \hat{p}_i=\sigma\left(w^\top\phi_i+\beta\cdot\text{UCB}_i\right)$$

其中 φ_i 是静态特征，w 是历史拟合出的权重，UCB_i 是未验证候选的探索奖励，α 控制预算集中的锐度。注意这个式子在粗筛阶段只用来排序，不直接分配预算——因为此时 p̂_i 的证据只有静态特征，方差极大。真正分配发生在细筛之后。排序后取 top-k 进入下一阶段，k 的取值是预算与池宽的折中：k 太小则漏掉静态特征不显眼但实际优秀的候选，k 太大则把 GPU 时间浪费在注定被淘汰的候选上。工程上的判断是让 k 随剩余预算线性增长，而不是固定常数。

代价在这里体现为漏检风险：静态特征无法表达运行期才暴露的问题，例如某个 tile 尺寸在小 shape 下占用率正常、在大 shape 下因寄存器溢出导致 occupancy 骤降。这类候选会在静态打分中被高估，占掉本该给真正高潜力候选的 top-k 名额。缓解手段是强制保留一定比例的“特征不典型”候选进入下一阶段，用少量 GPU 时间买保险。

二 · 快速编译与小规模试跑：第一次花 GPU 钱

top-k 候选进入第二阶段，动作序列固定为：编译、小规模正确性检查、单次时延测量。三件事共用一次 GPU 上下文，目的是用最小的墙钟时间把明显劣质者剔除。输入是候选源码与一组缩小后的 shape（通常取原 shape 的若干分之一，保持维度结构不变）；输出是每个候选的三元组（编译是否成功、正确性是否通过、时延读数）以及一份被淘汰名单。

编译本身就有成本，且这个成本常被低估。Triton 候选的编译时延随 kernel 复杂度上升，CuTe 模板实例化的编译时间可以到秒级甚至更长，CUDA C++ 在开启高优化等级时同样不便宜。更关键的是编译失败率：agent 生成的候选里有相当比例无法通过编译，这些候选如果直接进入 NCU 剖析阶段，会白白占用 GPU 队列。因此把编译放在最前面，让失败在零 GPU 执行成本处终止，是这一步的核心价值。伪代码层面：

  • 对每个候选 i：调用编译器，捕获返回码与诊断信息；失败则记 i 为 dead，跳过后续。
  • 编译成功者加载到 GPU，跑缩小 shape，与参考实现比对（参考 oracle 的构造见另一条目，此处只调用）。
  • 正确性通过者做一次时延测量，取单次或少数几次的中位数，避免冷启动噪声。
  • 按实测时延与静态打分的偏离程度更新 p̂_i 的后验，偏离大者标记为“静态特征失准”，供后续轮次修正 w。

代价有两层。第一层是时延测量的可信度：小 shape 下的时延与大 shape 下的时延不是单调关系，某个候选在小 shape 上快，可能只是因为 launch 开销占比高、计算量没压满，换到大 shape 反而因占用率不足而落后。第二层是正确性检查的覆盖面：小规模试跑只覆盖了少数 shape，边界条件、极端维度、非对齐指针这些错误可能漏网，留到细粒度阶段才爆出来，那时已经烧掉了更多预算。工程上的做法是把小规模试跑的 shape 选得“刁钻”而非“好跑”——刻意包含非 2 的幂、非对齐、单元素维度，让正确性检查在廉价阶段就尽量多抓错误。

一个具体例子：某归约算子的候选池里有 12 个候选，其中 3 个编译失败（模板参数不匹配），2 个在小 shape 上正确性失败（边界处理漏了尾块），剩余 7 个进入时延测量，其中 2 个时延明显落后被淘汰，5 个存活。整个阶段消耗的 GPU 时间只有数次 kernel 执行，token 成本主要是编译诊断信息的解析。

三 · 预算按潜力比例分配：从均摊到集中

存活候选进入第三阶段，此时才真正执行分配公式。输入是存活候选的后验 p̂_i（已由静态打分与小规模实测共同更新）、剩余预算 B、以及每个候选完成一轮细粒度调优所需的估计成本 c_i；输出是每个候选分到的预算 alloc_i。这一步的机制要点是：分配不是一次性的，而是每轮重算。因为每轮细粒度调优都会产生新证据，后验随之变化，预算流向随之改变。

公式里的 α 是调度锐度的旋钮。α 接近 1 时预算近似按潜力线性分配，探索性强但集中度低；α 取大值时预算向头部候选急剧倾斜， exploitation 强但容易在错误方向上押注过重。工程上 α 应随搜索轮次递增：早期证据少、后验方差大，α 取小值保留探索；后期证据充分，α 取大值把预算压到最有希望的候选上。这与 bandit 的经典取舍一致，但这里的“臂”是候选 kernel 而非超参数，拉一次臂的代价是一次 NCU 剖析会话。

分配的执行方式是配额制：每个候选拿到 alloc_i 后，换算成可执行的细粒度调优轮数 n_i = alloc_i / c_i。c_i 的估计来自候选的复杂度——需要采集的 NCU 指标数量、SASS 反汇编的规模、预期的变异次数。复杂度高的候选 c_i 大，即使潜力高也只能拿到较少轮数，这是预算约束下的必然妥协。若某个候选的 n_i 向下取整为 0，它实际上被冻结，等下一轮后验更新后可能重新获得预算。

代价在这里是过早淘汰的风险。后验 p̂_i 依赖历史先验 w，而 w 是在特定算子族、特定架构上拟合的。跨算子迁移时，某个在新算子上真正优秀的策略可能因为静态特征与历史成功模式不符而被压低 p̂_i，连续几轮拿不到预算，最终被终止。这种错误是不可逆的——一旦候选被标记终止，它的证据链就断了，后续无法翻案。缓解手段是给每个候选保留一个极小的“复活预算”，在终止后仍允许一次低成本复测，代价是总预算的几个百分点。

四 · NCU/SASS 细粒度调优循环：昂贵证据的采集

拿到配额的候选进入细粒度循环。每一轮的动作是：跑一次 NCU 剖析采集指定指标集、反汇编关键 warp 的 SASS、由 agent 依据指标与 SASS 提出一处变异、编译变异体、验证正确性、测量时延。输入是候选当前版本与上一轮的 profile 证据；输出是变异后的新版本、新的 profile 证据、以及时延是否改善的判定。

这一轮的代价结构与其他步骤完全不同。NCU 剖析本身有显著的时延开销——采集的指标越多、采样粒度越细，kernel 重放次数越多，单次剖析的墙钟时间可以是裸跑的若干倍。SASS 反汇编不花 GPU 时间但花 token：一段关键循环的 SASS 可能有几十条指令，agent 要读懂它并定位瓶颈，token 消耗与 SASS 长度成正比。变异后的编译又要花编译时间。因此一轮细粒度调优的总成本是“剖析时延 + 编译时延 + token”的叠加，这也是为什么预算必须集中——均摊给所有候选时，每个候选连一轮都跑不完。

循环内的判定逻辑是 keep-revert：变异后时延改善则保留，否则回退到上一版本。这个判定看似简单，实则有个陷阱：单次时延测量有噪声，尤其在 kernel 执行时间短、launch 开销占比高时，噪声可能淹没真实改善。工程上的做法是要求改善幅度超过一个与测量噪声估计相关的阈值才保留，否则视为无改善。这个阈值本身要花预算去标定——用同一版本重复测量若干次估计方差，这笔开销计入 c_i。

一个具体例子：某矩阵乘候选在细粒度阶段第一轮 NCU 显示共享内存 bank conflict 偏高，agent 读 SASS 后确认是 swizzle 模式缺失，提出加入 padding 的变异。变异体编译后时延改善，保留。第二轮 NCU 显示 occupancy 受寄存器用量限制，agent 提出减小 tile 尺寸的变异，但时延反而变差，回退。两轮消耗的剖析时延与编译时延加起来，已经超过粗筛阶段全部候选的总开销——这正是预算必须向高潜力候选集中的经验依据。

五 · 后验更新与提前终止：让证据改变预算流向

每轮细粒度调优结束，agent 用新证据更新 p̂_i。更新的输入是新旧时延对比、NCU 指标的变化方向、以及变异是否被保留；输出是新的后验与新的 UCB 项。机制上这是一个轻量的贝叶斯更新：保留的变异提升 p̂_i，回退的变异降低 p̂_i，连续多轮回退则 p̂_i 加速衰减。UCB 项随该候选被访问的次数增加而减小，访问越多的候选探索奖励越低，预算自然流向访问不足的候选。

提前终止的判据是组合式的：p̂_i 低于当前存活候选的中位数、连续若干轮回退、或剩余配额不足以完成一轮完整调优。三者任一满足即终止该候选，把它的剩余配额回收进公共池，由下一轮分配重新分给其他候选。这个回收机制是预算感知的关键——没有回收，提前终止只是省下了未来预算，对当前轮次无益；有了回收，终止动作立即转化为对其他候选的加注。

代价是终止判据的误杀率。连续回退可能只是变异方向选错，而非候选本身无潜力；agent 的变异提议质量不稳定时，好候选可能因为连续几次糟糕变异而被误判终止。工程上的缓解是区分“候选无潜力”与“变异无效果”：若回退的变异彼此差异很大（说明探索了多个方向都失败），终止判据可信；若回退的变异高度相似（说明 agent 在原地打转），应换变异策略而非终止候选。这个区分需要 agent 记录变异的历史，token 成本不高但逻辑复杂度不低。

六 · 预算耗尽时的输出：证据链而非裸 kernel

预算耗尽或所有候选终止时，搜索输出最优合法 kernel 及其 profile 证据链。输入是各候选的最终版本、时延读数、NCU 指标快照、SASS 片段、以及每次变异的保留/回退记录；输出是一个结构化产物，包含 kernel 源码、正确性验证记录、时延与 roofline 归一评分（归一方法见另一条目）、以及支撑“为什么这个版本最优”的证据链。

证据链的工程价值在于可审计。下游部署方要判断这个 kernel 是否可信，不能只看时延数字——数字可能来自有利的 shape、可能来自测量噪声、可能来自未被发现的正确性漏洞。证据链把每一步的判定依据摊开：哪一轮的哪个指标驱动了哪次变异，哪次变异被保留及其改善幅度，哪些候选被终止及终止理由。这让复核者能定位薄弱环节，而不是全盘接受或全盘否定。

这一步的成本是 token 而非 GPU 时间：整理证据链要回读整个搜索过程的日志，日志长度与搜索轮数成正比，长搜索的日志可能超出上下文窗口，需要分段摘要。摘要本身有信息损失风险——关键证据可能在摘要中被压掉。工程上的做法是在搜索过程中就结构化记录证据（每轮一条定长记录），而非事后从自由文本日志里抽取，把整理成本前移并摊薄。

最终产物的合法性由两道门保证：正确性 oracle 的通过记录、以及合约校验的通过记录（两者机制见对应条目）。预算感知搜索不改变这两道门的标准，只决定在有限预算下能对多少候选执行它们。因此输出时必须明确标注：哪些候选过了门、哪些没过、哪些根本没跑到门——最后这类是预算约束的直接产物，也是搜索可信度的边界所在。
