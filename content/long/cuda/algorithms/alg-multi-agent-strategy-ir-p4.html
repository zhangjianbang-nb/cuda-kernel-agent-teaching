一 · 负载选择：让 IR 的四个字段都有落点

策略 IR 写成 $$\text{IR}=\langle \text{Bound},\ \mathcal{A}_{\text{cand}},\ \mathcal{C}_{\text{res}},\ \text{reward}\rangle$$ 之后，负载（workload）的第一职责不是“跑得动”，而是让这四个字段都能被真实数据填满。若某个字段在负载上恒为空，多 agent 协同就退化为单 agent 加一层无意义的序列化开销。因此选负载时按字段反查：Bound 字段要求负载存在明确的瓶颈归属，即同一算子在不同 shape 下能在 memory-bound 与 compute-bound 之间迁移，分析 agent 才有分类可写；$\mathcal{A}_{\text{cand}}$ 要求负载存在至少两条互斥的优化路径（例如 tile 放大换复用 vs. tile 缩小换占用率），否则候选动作列表退化为单元素；$\mathcal{C}_{\text{res}}$ 要求负载对寄存器、共享内存、线程块尺寸有真实约束，约束不是装饰；reward 要求负载的计时方差可控，使执行 agent 回写的数值能被调度器比较。

按此标准，适合的算子族是“结构简单、参数空间有张力”的一类：GEMM 及其变体（含 batched、split-K）、softmax/层归一化、attention 的 fused 版本、reduce 与 scan、卷积的 implicit GEMM 形式、量化/反量化的逐元素链。不适合的是两类极端：一是参数空间近乎退化的算子（纯 copy、纯 cast），IR 的候选动作列表写不出差异；二是控制流密集、shape 高度不规则的算子（稀疏 gather、动态长度的 ragged 序列），其瓶颈归属随输入剧烈跳变，分析 agent 的 profile 读数无法稳定映射到 Bound 分类，评审 agent 也无法机械校验“动作是否实现”，因为同一动作在不同分支上语义不同。

shape 的选取要覆盖三种 regime：小 shape（launch 与尾效主导）、中 shape（roofline 拐点附近）、大 shape（纯带宽或纯算力饱和）。每个 regime 至少两个点，且必须包含一个“非 2 的幂”的维度，用来暴露 tile 边界处理与 padding 带来的额外访存。硬件侧则要求负载能同时给出可测的带宽与算力两个维度的占用信号，使 Bound 分类不依赖猜测。具体例子：一个 batch=1、序列长度 2048、head dim 64 的 attention 负载，在中端卡上落在 memory-bound，而在大卡上同一 shape 可能被算力吞掉——这种跨硬件的 Bound 迁移正是 IR 需要表达的，也是评测配方必须记录的。

代价在这里体现为编译时间与显存：覆盖三 regime × 两硬件 × 两 dtype 的负载矩阵，若每个点都触发一次完整编译，编码 agent 的 Triton/CUDA 编译开销会随配置数线性增长；显存则限制了大 shape 的上限，迫使在“够大以饱和”与“够小以可跑”之间取舍。工程判断是：负载矩阵按 Bound 迁移点稀疏采样，而非网格穷举。

二 · 基线怎么选：锚点必须与 IR 的 Bound 同源

基线的作用是给 reward 一个可比的零点。多 agent 场景下基线选错，会直接污染调度器的决策：评审 agent 按 IR 校验通过、执行 agent 回写了一个“看起来提升”的 reward，但提升来自基线本身选弱了，而非策略动作有效。因此基线选取的第一原则是“与 Bound 同源”——若 IR 声明该负载为 memory-bound，基线必须是同精度、同数据布局下接近带宽上限的实现（框架自带 kernel 或手写最优 copy 式实现），而不是一个明显低效的参考实现；若声明为 compute-bound，基线应接近该硬件的算力上限实现。用弱基线做锚点，等于把 reward 的定义域整体平移，冲突检测 $$\text{Conflict}=\mathbb{1}\left[\exists a\in\mathcal{A}:\ \text{Code}(a)\not\equiv\text{IR}(a)\right]$$ 也无法发现这种系统性偏差，因为代码确实实现了 IR 声明的动作，只是动作的价值被虚高了。

第二原则是基线必须与候选代码走同一条计时路径：同一 warmup 次数、同一同步方式、同一计时工具、同一输入分布。若基线用框架的融合实现而候选用分离实现，计时差异里混入了 launch 次数差异，reward 不可比。第三原则是基线要能被多个编码 agent 复用：同一 IR 下 Triton、CUDA、CuTe 三条实现路径应共享同一基线数值，否则跨后端比较失去意义。

代价是基线的构建与维护成本：一个真正贴近上限的基线往往需要单独调优，其编译与验证开销计入评测配方但不计入候选的 reward；同时强基线会压缩 reward 的提升空间，使小幅度优化在噪声内不可分辨，这反过来要求计时重复次数增加，进而拉长单轮时延。具体例子：对一个 memory-bound 的 softmax，若基线取框架默认实现（含多次 kernel launch 与中间张量落盘），候选的单 kernel 融合实现会得到虚高的加速比；换成手写的单遍带宽饱和实现后，同一候选的 reward 回落到真实区间，调度器才不会把“融合”误判为持续有效的动作而反复重试。

三 · 输入分布：正确性 oracle 与计时方差的双重约束

输入分布同时服务两个目的：让正确性检查覆盖数值边界，让计时反映真实数据路径。两者对分布的要求并不一致，必须分开设定再合并成一套采样方案。正确性侧要求分布包含极端值：接近 dtype 上限/下限的量级、正负混合导致的抵消、denormal 与零、以及会让归约顺序产生差异的长尾。计时侧要求分布不触发数据相关的慢路径（例如全零输入可能让某些实现跳过计算，或让分支预测进入最热路径），否则 reward 失真。

工程做法是把输入分布参数化为一个显式的采样规格，写进 IR 的约束字段旁：dtype、量级范围、稀疏度、是否含 NaN/Inf 的禁用标记、随机种子。种子必须固定并可复现，否则执行 agent 回写的 reward 在下一轮无法复算，调度器比较的是不同分布下的数值。正确性 oracle 用高精度参考（fp64 或分段高精度累加）在同一批输入上计算，容差按 dtype 与归约长度设定，而非全局一个常数。

代价体现在 token 与显存两处：分布规格越细，分析 agent 与评审 agent 需要读写的上下文越长，多 agent 串行调用下 token 消耗被放大；大 shape 加多组极端值输入会推高显存峰值，迫使减小 batch 或分块验证，而分块又会改变归约顺序，反过来影响容差设定。具体例子：对一个 fp16 的 reduce-sum，若输入分布全为同量级正值，任何归约顺序都给出相同结果，正确性检查形同虚设；加入跨 4 个数量级的混合分布后，顺序敏感的实现在 fp16 累加下会暴露误差，此时评审 agent 才能依据 IR 中“使用分段累加”的动作声明去校验代码是否真的实现了该动作，而不是只看输出是否落在容差内。

另一个易被忽略的点是分布与 Bound 分类的耦合：某些分布会让实际访存模式偏离理论 roofline（例如稀疏输入使有效带宽下降），若分析 agent 用理论带宽做 Bound 判断，会得出与 profile 矛盾的结论，进而在 IR 中写下错误的候选动作。因此分布规格必须与 profile 采集时的输入一致，NCU 读数才有意义。

四 · 指标怎么算：从单次计时到可比较的 reward

指标计算的核心是把“一次计时”变成“一个可被调度器比较的标量”，同时保留足够信息供评审 agent 判断该数值是否可信。最小配方是：固定 warmup 与重复次数，取中位数而非均值以抵抗离群，同时记录分位数（如 P90）作为方差信号；将候选时间与基线时间做比值得到加速比，再按 IR 声明的 Bound 归一——memory-bound 负载按有效带宽占理论上限的比例归一，compute-bound 按算力占比归一。归一化的意义在于让不同负载、不同硬件上的 reward 落在同一量纲，使调度器可以跨任务比较，而不必为每个负载维护独立的阈值。

伪代码思路：对每个配置，先跑基线得 $t_{\text{base}}$，再跑候选得 $t_{\text{cand}}$，计算 $r = t_{\text{base}}/t_{\text{cand}}$；若 $r$ 的置信区间跨越 1，则标记为“不可分辨”，不写入 reward 的提升字段，只写入“无结论”。这一条对多 agent 尤其重要：执行 agent 回写的 reward 若只是一个点估计，调度器会把噪声当成信号，反复把资源投给一个实际无收益的动作，形成搜索震荡。

正确性指标不能只用“通过/不通过”。应记录最大相对误差、误差分布的分位数、以及失败样本的输入特征（量级、位置），使评审 agent 能把失败归因到 IR 中的具体动作（例如“tile 边界未处理”对应 $\mathcal{A}_{\text{cand}}$ 中的某一条），而不是笼统打回。代价是每次评测需要额外的参考计算与统计开销，且分位数统计要求重复次数足够，直接拉长单轮时延；在多 agent 串行结构下，这一时延被放大 2–4 倍。

具体例子：一个 compute-bound 的 GEMM 负载，候选实现通过增大 tile 提升了算力占比，但寄存器压力上升导致占用率下降，在小 shape 上反而变慢。若指标只取大 shape 的加速比，reward 为正，调度器会保留该动作；若指标按 shape regime 分别归一并记录方差，评审 agent 能看到小 shape 上的负收益，从而在 IR 中把该动作标注为“条件有效”，限定其适用 shape 范围。这正是 IR 相对单 agent 的价值：指标的结构化回写让“何时有效”成为可追溯的约束，而非隐含在代码里。

五 · 负载不对时会发生什么：三类可观测的失效

第一类是 Bound 误分类导致的动作错配。负载的 shape 落在 roofline 拐点附近，profile 读数在两次采集间摇摆，分析 agent 交替写出 memory-bound 与 compute-bound 的 IR，编码 agent 随之生成互相矛盾的实现（一个优化复用、一个优化占用率），评审 agent 各自按自己的 IR 校验通过，冲突检测却检测不到——因为每个 agent 内部的 Code 与 IR 是一致的，冲突发生在 IR 之间而非 IR 与代码之间。结果是多 agent 重复分析、给出矛盾建议，正是无共享表示时的典型失效，只不过这里共享表示存在却未被负载稳定锚定。代价是 token 与编译时间的双重浪费，且调度器在两组 reward 间来回切换，无法收敛。

第二类是基线漂移导致的 reward 虚高。基线随框架版本或硬件状态变化而变动，而 IR 中记录的基线数值未同步更新，执行 agent 回写的加速比建立在过期锚点上。评审 agent 无法从代码层面发现这一点，因为它校验的是动作实现而非数值来源。失效表现为：某动作在多个负载上持续显示正收益，但端到端收益不出现。工程判断是把基线数值作为 IR 的一部分显式版本化，基线变更触发 reward 重算，而非沿用历史值。

第三类是输入分布与计时路径不一致导致的方差爆炸。正确性用极端值分布、计时用均匀分布，两者混在同一 reward 里，导致同一配置的重复测量结果离散度大，置信区间跨越 1 的比例升高，大量配置被标记为“不可分辨”。此时调度器失去有效信号，退化为随机探索，多 agent 的串行开销却照付。代价直接体现为单轮时延与 token 消耗：3–5 倍于单 agent 的 token 用量换来的是一批无结论的评测。

三类失效的共同点是：它们都不表现为代码错误，而表现为 IR 字段与负载事实之间的失配。因此评测配方的工程判断应落在“负载—基线—分布—指标”四者的一致性校验上，把一致性本身作为评审 agent 的一项机械检查，而不是寄望于 reward 数值自动暴露问题。

六 · 配方与 IR schema 的耦合边界

评测配方不是外挂在 IR 之外的脚本，它的每个参数都应能在 IR schema 中找到对应字段，否则 schema 不覆盖的评测维度就无法被多 agent 表达，扩展成本随之上升。具体映射：负载矩阵对应 Bound 字段的取值域；基线版本对应 reward 字段的锚点；输入分布规格对应 $\mathcal{C}_{\text{res}}$ 之外的“数据约束”扩展位；指标归一方式对应 reward 的量纲声明。当配方新增一个维度（例如新增一种 dtype 的容差策略），若 schema 无对应字段，分析 agent 写不出、评审 agent 校验不了，只能由人工在配方脚本里硬编码，这恰好是 IR 设计需要随任务演进的那部分成本。

边界处的工程判断是：配方维度只在能被至少两个 agent 机械读取时才纳入 IR。例如“计时重复次数”若只被执行 agent 使用，就不必进 IR，作为配方常量即可；而“基线版本”同时被执行 agent（取锚点）与评审 agent（校验数值来源）使用，就必须进 IR。按此标准裁剪，可以避免 schema 膨胀，同时保证跨后端复用——同一 IR 下 Triton/CUDA/CuTe 三条路径共享同一负载、同一基线、同一分布规格，reward 才具备跨后端可比性。

代价是配方变更的传播成本：一旦基线或分布规格进入 IR，任何变更都要触发所有引用该 IR 的编码 agent 重新生成与重测，单轮时延与 token 消耗随引用数上升。因此配方应尽量稳定，把易变的探索性参数留在配方脚本层，只把影响 reward 可比性的参数固化进 IR。具体例子：把一个 attention 负载的基线从框架实现换成手写带宽饱和实现，若基线版本已在 IR 中，则所有历史 reward 自动失效并触发重算，调度器的历史决策依据被清空；若基线只在脚本层，则新旧 reward 混用而无人察觉。两害相权，宁可承担重算成本，也不接受不可比的 reward 进入调度。
