一 · 负载画像：先决定“测什么形状”，再决定“测什么算子”

Fuzz+fp64 oracle 的评测配方不是从算子名开始的，而是从负载画像开始的。同一个算子在不同 shape 下会呈现完全不同的失败模式：归约类算子在非 2 的幂长度上暴露尾部余数处理错误，逐元素算子在极端指数输入上暴露饱和与舍入分支，矩阵类算子在 K 维非对齐时暴露 tile 边界与 padding 语义。因此配方第一步是把“算子 × shape 族 × dtype × 硬件档位”写成一张可枚举的矩阵，而不是一个固定用例列表。shape 族至少覆盖四类：2 的幂（用于对齐路径）、非 2 的幂（用于尾部余数）、小于一个 warp/tile 的极小 shape（用于启动与掩码边界）、以及跨过 L2/显存容量拐点的大 shape（用于分块与流水线切换）。每一类都要标注它想触发哪条代码路径，否则随机采样只是在浪费 fp64 参考的算力。

适合进这套配方的模型/算子有三条判据。第一，输出可被 fp64 在可接受成本内重算——逐元素、归约、softmax、layernorm、卷积、GEMM 的主干都满足，而带数据依赖迭代（如某些稀疏求解）或非确定性并发的算子需要额外约束。第二，存在明确的 dtype 阈值语义，使“算法错”与“舍入差”可分离。第三，shape 空间有工程意义的边界，能被 fuzz 生成器结构化覆盖。反过来，那些输出本身依赖随机种子、或参考实现必须调用被测 kernel 自身才能定义的算子，不适合作为主负载，只能作为辅助负载。

硬件档位决定参考实现的放置策略。fp64 参考在 GPU 上吞吐约为 fp32 的 1/32–1/64，这个比例直接决定了大 shape 下参考计算会不会成为评测瓶颈。工程判断是：小 shape 用 GPU fp64 参考换取低时延，大 shape 改用 CPU fp64 参考或分块流式比对，把参考成本摊到与生成成本同一量级。代价是 CPU 参考引入主机—设备同步与传输时延，单次评测的墙钟时间上升；收益是避免了“参考比被测慢两个数量级”导致的评测吞吐塌陷。这条取舍必须写进配方，而不是留给运行时临时决定。

二 · 基线选择：三条基线各管一件事

基线不是“随便找个能跑的版本”，而是各自承担一个诊断职责。第一条是朴素正确基线：语义最直白、无向量化无分块的实现，用来回答“算法对不对”。它通常就是 fp64 参考的 fp32 降级版或逐元素循环版，性能很差但语义清晰。第二条是框架/库基线：cuBLAS、cuDNN、PyTorch 原生算子，用来回答“离生产可用有多远”，它的作用是给出性能下界参照，而不是正确性参照。第三条是编译基线锚定：同一份源码在固定编译选项下的产物，用来隔离“编译器优化引入的数值漂移”与“源码本身的算法错误”——这条基线在别处已展开，此处只作为配方中的固定项登记，不重复其机制。

三条基线的选择规则要写成可执行判据：朴素基线必须与被测 kernel 共享同一输入分布与同一 fp64 参考，否则误差归因失效；库基线只用于性能比值，不参与 pass/fail 判定，避免把库自身的数值策略当成正确性标准；编译基线必须固定 flags 与架构目标，任何一次评测中变更编译选项都要作废重跑。代价是三条基线使单次评测的计算量约为单条基线的三倍，编译基线的编译时间也计入评测预算；收益是任何一个失败都能被归因到“算法 / 性能 / 编译”三者之一，而不是笼统的“没过”。

具体例子：一个 layernorm kernel 在非 2 的幂 hidden size 上失败。朴素基线同样失败，说明是算法层的尾部处理错误；若朴素基线通过而被测失败，则嫌疑落在向量化路径的掩码或对齐假设上；若库基线性能是被测的若干倍而正确性都通过，则问题降级为性能问题而非正确性问题。这个三分法让配方输出的不只是一个布尔值，而是一条可执行的修复线索。

三 · 输入分布：结构化 fuzz 而非均匀乱撒

输入分布的设计目标是“用最少的样本覆盖最多的分支”，因此它是分层采样而不是单一分布。按 dtype 采样：正态分布覆盖常规数值区间，均匀分布覆盖平坦动态范围，极端指数分布把值推到接近 dtype 上下界的位置以触发饱和与次正规数路径，混合分布按比例掺入 NaN/Inf 以检查传播语义。长度维度单独采样，强制包含非 2 的幂与尾部余数，例如把长度取为“2 的幂 ± 小偏移”和“tile 尺寸的整数倍 + 余数”。

判定公式沿用双阈值结构：

$$\text{err}=\max_i\frac{|y_{\text{gen},i}-y_{\text{fp64},i}|}{\max(|y_{\text{fp64},i}|,\epsilon)},\quad \text{pass}=\mathbb{1}[\text{err}\le\tau_{\text{dtype}}\wedge \text{ULP}_{95}\le \upsilon]$$

其中相对误差阈值按 dtype 校准（fp32 取 1e-5 量级、fp16 取 1e-2 量级），ULP95 作为第二道闸门防止“相对误差小但尾部若干元素严重偏离”被平均值掩盖。两个条件必须同时满足，这直接决定了误判率：只用相对误差会在接近零的输出上因分母保护而放过错误，只用 ULP 会在量级差异大的张量上对高幅值元素过于宽松。

NaN/Inf 必须单独成组检查传播语义，而不是混进主误差统计。原因是 NaN 参与 max 运算会污染整个误差向量，使“全 NaN 通过”成为漏洞：若 checker 只判断 err ≤ τ 而 NaN 比较恒为假或恒为真，实现可以选择性输出 NaN 绕过判定。配方要求对 NaN/Inf 输入单独断言“输出是否为 NaN/Inf、位置是否与参考一致”，并显式约定传播规则（是否按 IEEE 规则传播、是否允许框架特定的抑制行为），否则 checker 与参考会互相矛盾。代价是 NaN/Inf 组需要独立的比对逻辑与额外的参考调用，评测样本数上升；收益是堵住了一类最容易在 agent 搜索中被利用的作弊面。

四 · 指标计算：把“通过”拆成可归因的量

指标层不能只输出 pass/fail，而要输出可归因的三元组：最大相对误差及其位置、ULP95 及其分布、以及失败时的最小复现输入。最大相对误差定位到具体下标，配合最小复现输入（对输入做增量削减直到错误刚好消失）可直接指向错误分支。ULP 分布用分位数而非均值，因为均值会被大量正确元素稀释，掩盖尾部系统性偏移。工程上还应记录参考实现自身与更高精度的一致性，作为 oracle 可信度的自检项——若参考本身在极端指数上与更高精度不一致，则该样本的判定应被标记为“oracle 不确定”而非直接判失败。

性能指标与正确性指标必须分开计算再合成。正确性用上述双阈值，性能用与库基线的比值或与 roofline/SOL 的归一化比值（归一化评分机制在别处展开，此处只登记其为配方中的固定输出项）。合成的原则是：正确性不通过时性能数字不参与任何排序，避免 agent 用“快但错”的实现占据搜索前沿。代价是每次评测要跑两遍（正确性样本 + 性能样本），样本预算翻倍；收益是搜索信号不会被错误实现污染。

具体例子：一个 softmax kernel 在含 Inf 的输入上输出全 NaN。主误差统计因 NaN 污染而失效，但 NaN/Inf 专项组立刻报出“参考输出为有限值而生成输出为 NaN”，最小复现输入被削减到单个含 Inf 的元素。这条线索直接指向 exp 溢出后的减法顺序错误，而不是笼统的“数值不稳定”。

五 · 负载不对时会发生什么：四类典型失效

第一类，shape 覆盖不足导致假通过。若配方只采样 2 的幂长度，尾部余数分支从未被执行，一个在非对齐长度上越界的 kernel 会稳定通过。代价是这类漏洞在部署到真实负载时才暴露，且往往表现为偶发错误而非稳定崩溃，排查成本远高于评测阶段补一组 shape。工程判断是：shape 族的最小覆盖必须包含“非 2 的幂”和“小于一个 tile”两类，缺一不可。

第二类，输入分布过窄导致阈值失真。若只用正态分布，极端指数路径不被触发，fp32 阈值 1e-5 在常规区间上显得宽松，实现可以用低精度近似算法蒙混过关。代价是评测通过但生产端在长尾输入上精度不达标；收益侧的教训是分布必须分层，且每层都要标注它想触发的分支。

第三类，参考成本失控导致评测吞吐塌陷。大 shape 下 GPU fp64 参考吞吐为 fp32 的 1/32–1/64，若配方不加区分地对所有 shape 使用 GPU 参考，单次评测的墙钟时间被参考计算主导，多轮 RL 的采样效率骤降。代价直接体现为 token 预算内可评估的候选数减少，搜索广度受损。对策是按 shape 规模切换参考放置策略，并把参考耗时计入单次评测预算上限。

第四类，NaN/Inf 语义未约定导致 checker 自相矛盾。不同框架对 NaN 传播与 Inf 抑制的处理不一致，若配方不显式约定，checker 可能把参考的抑制行为判为错误，或把生成的抑制行为判为通过。代价是误判率上升且失败不可复现。工程判断是：传播语义必须写进配方契约，与 dtype 阈值并列，作为评测前的前置条件而非事后解释。

失效类型触发条件代价配方对策
假通过shape 只覆盖 2 的幂部署期偶发错误强制非 2 的幂与极小 shape
阈值失真输入分布单一长尾精度不达标分层采样并标注分支意图

六 · 配方落地：把负载写成可复现的清单

落地形态是一份结构化清单，而不是一段脚本。清单条目包含：算子标识、shape 族枚举、dtype、输入分布分层比例、参考放置策略（CPU/GPU/分块）、阈值（τdtype 与 υ）、NaN/Inf 专项开关、基线集合、以及单次评测的预算上限（参考耗时 + 生成耗时 + 编译耗时）。每个条目都要能被独立重放，最小复现输入随失败记录一起持久化，供后续搜索轮次直接复用。

预算上限是这份清单里最容易被忽视但最影响搜索效率的字段。fp64 参考的吞吐劣势意味着评测预算必须显式分配给参考计算，否则大 shape 样本会挤占小 shape 样本的评估机会，导致搜索前沿偏向“容易测”的负载而非“容易错”的负载。工程判断是：按“单位参考成本能覆盖的分支数”给样本排序，优先评估那些能触发未覆盖分支的 shape，而不是均匀抽样。代价是需要维护分支覆盖的记账，收益是把有限的评测预算花在信息量最高的样本上。

最后一个具体机制：清单与搜索循环的接口只暴露“通过/失败 + 归因标签 + 最小复现输入”，不暴露完整误差向量。原因是完整误差向量会成为 agent 过拟合的信号源，使其针对具体下标做局部修补而非修正算法。归因标签（算法 / 性能 / 编译 / oracle 不确定）足以驱动 keep-revert 决策，而最小复现输入足以定位分支。这条接口约束的代价是调试信息被压缩，收益是搜索信号保持稀疏且难以被针对性利用。

配方边界：fp64 参考在哪些负载上会失真

这套 oracle 的判定力高度依赖负载形态。它适合逐元素与归约类算子（激活、layernorm、softmax、reduce、简单 GEMM 的数值校验），shape 需覆盖非 2 的幂长度与尾部余数，以便暴露越界与掩码错误；硬件上要求 fp64 吞吐不为零且与 fp32 比例稳定，消费级 GeForce 的 fp64 单元被大幅削减，参考路径本身会成为噪声源。若把负载换成大规模 GEMM 或 attention，参考实现的算力开销会直接压过被测 kernel：fp64 参考在 GPU 上吞吐约为 fp32 的 1/32–1/64，当被测 kernel 已接近 SOL 时，评测时延由参考侧主导，fuzz 轮数被迫压缩，覆盖率反而下降。此时应改用 CPU 双精度参考或分块抽样比对，把 fp64 计算限制在被测输出的子集上，代价是抽样漏检——错误若只出现在未抽样分块，checker 给出假通过。

输入分布决定阈值是否可校准。按 dtype 采样正态、均匀、极端指数与含 NaN/Inf 的混合分布时，极端指数样本会让相对误差公式的分母剧烈变化：

$$\text{err}=\max_i\frac{|y_{\text{gen},i}-y_{\text{fp64},i}|}{\max(|y_{\text{fp64},i}|,\epsilon)},\quad \text{pass}=\mathbb{1}[\text{err}\le\tau_{\text{dtype}}\wedge \text{ULP}_{95}\le \upsilon]$$

当 $|y_{\text{fp64},i}|$ 接近 $\epsilon$ 时，分母被钳位，微小绝对偏差被放大为巨量相对误差，fp32 的 $\tau=10^{-5}$ 阈值在近零输出上频繁误杀正确实现；反之若样本全为大幅值，ULP 距离被稀释，真实精度退化被掩盖。工程上应把近零、次正规数与极端指数单独成组统计，而不是混入全局 max。NaN/Inf 传播语义在不同框架间不一致，必须显式约定（是否按 IEEE 规则传播、是否允许 quiet NaN 载荷差异），否则 checker 与参考互相矛盾；更危险的是“全 NaN 通过”漏洞——若比对逻辑对 NaN 做跳过处理，一个恒输出 NaN 的 kernel 会拿到满分。最小复现输入的保存同样有代价：每个失败用例需回放 fp64 参考并序列化输入张量，显存与磁盘开销随失败样本数线性增长，在长尾错误密集的负载上会拖慢整轮评测的吞吐。

负载特征判定可信度主要代价
逐元素/归约，含非 2 的幂长度高，能暴露掩码与边界错误参考算力约为 fp32 的 1/32–1/64
近零与极端指数混合分布中，需分组阈值相对误差分母钳位导致误杀
大规模 GEMM/attention低，参考成为瓶颈fuzz 轮数压缩，覆盖率下降
含 NaN/Inf 且语义未约定不可信全 NaN 假通过

基线选择上，fp64 参考只回答“数值是否偏离高精度真值”，不回答“是否达到硬件上限”；后者需另配 roofline/SOL 基线，二者混用会让 agent 把优化目标误读为压低误差而非提升吞吐。负载不对时的典型后果是：agent 学会针对固定 shape 与固定分布做特化硬编码，随机 fuzz 一旦换成非对齐长度即崩；或反过来，评测因参考开销过大而退化为少量固定用例，硬编码重新生效。判断配方是否成立的工程信号很直接——若失败样本的最小复现输入集中在同一 shape 尾部或同一指数区间，说明 fuzz 分布已覆盖到真实缺陷；若失败全部落在近零组且 ULP 距离很小，则应先怀疑阈值校准而非 kernel 逻辑。
