一 · 从 prompt 到候选池：G 路采样的物理成本

TRLOO 的流动起点不是数学，而是一次真实的批量采样。给定一个 kernel 任务 prompt（例如“对给定 shape 的 softmax 做融合实现”），策略模型在同一上下文下独立采样 G 条候选代码。这一步的输入是 prompt token 序列与采样温度、top-p 等解码参数，输出是 G 份互不相同的 CUDA C++/Triton 源码文本。关键机制在于：这 G 条样本必须共享同一 prompt、同一参考实现、同一测试 harness，否则“组内”的语义不成立，留一法 baseline 就失去可比性。工程上这意味着采样阶段就要把 prompt id、采样种子、解码参数一起写进候选记录，作为后续所有步骤的主键。

代价首先体现在 token 上：G 条候选意味着 G 倍解码开销，且 kernel 代码通常比自然语言答案长，单条动辄数百到上千 token，G 取 8 或 16 时单 prompt 的解码成本已经不可忽略。其次是显存：并发生成需要 KV cache 按 G 路复制或分页管理，长上下文 kernel prompt 下 KV 占用随 G 线性上升。再往后是编译，G 份源码要各自走一遍 nvcc/Triton 编译，编译时间与 G 成正比，且失败样本同样消耗编译时间——这一点常被低估，因为编译失败往往发生在模板实例化或 PTX 生成阶段，耗时并不比成功编译短多少。用公式刻画组内奖励集合就是后续所有计算的原料：

$$R=\{r_1,\dots,r_G\},\quad r_i=f_{\text{compile}}\circ f_{\text{verify}}\circ f_{\text{bench}}(\tau_i)$$

一个具体例子：某 prompt 下 G=8，其中 3 条编译失败、2 条编译通过但正确性校验不达标、3 条通过并测速。这 8 条全部要进入候选池并各自携带奖励，因为留一法要求“其余 G-1 条”的均值，任何一条被提前丢弃都会改变 baseline 的分母，进而破坏无偏性。

二 · 编译与验证：把源码变成可判定的奖励

第二步对每条候选依次执行编译、正确性验证、测速三段流水，输出是一个标量奖励 r_i 及其附属诊断（编译日志、错误类型、相对误差、时延）。机制上，这三段是有序且短路的：编译失败直接给最低奖励并跳过后续，正确性失败给次低奖励并跳过测速，只有全通过的样本才进入性能打分。短路设计的意义在于控制成本——测速是最贵的一段，不能让错误样本浪费 GPU 时间；但它也带来一个副作用：奖励分布被人为压成离散台阶，组内若多数样本落在同一台阶，方差会被系统性低估。

正确性验证本身有代价。以 fp64 参考实现做 oracle 比对时，参考路径要在 CPU 或高精度 GPU 上跑一遍，其耗时可能超过候选 kernel 本身的测速时间，尤其对小 shape 任务，固定开销占主导。测速段则要跑多轮 warmup 与重复计时以压制噪声，单条样本的测速 wall time 是候选 kernel 时延的数十倍到上百倍。把这些折算成组级成本，可以看到一个直接的线性关系：编译与测速的 GPU 时间随 G 线性增长，而正确性 oracle 的固定开销按组摊薄、不随 G 变化。伪代码层面的调度思路是：

  • 对 G 条候选并行发起编译，收集 (成功/失败, 日志)；
  • 仅对编译成功者并行跑正确性校验，记录最大相对误差；
  • 仅对校验通过者串行或分批测速，得到时延并折算为奖励；
  • 把每条候选的奖励与诊断写入组记录，供 baseline 计算使用。

具体例子：一个 reduction kernel 的候选在 fp64 oracle 下最大相对误差 1e-6 量级通过，但测速时因未做向量化而时延偏高，奖励落在中档；另一条候选编译通过、误差超标，奖励被压到次低档。两条样本的奖励差就构成了后续优势信号的来源，而它们的诊断字段（误差值、时延）是排查“奖励是否可信”的第一手材料。

三 · 留一法 baseline：无偏性的代数来源

第三步是 TRLOO 的核心计算。对第 i 条样本，baseline 取同组其余 G-1 条奖励的均值，优势为：

$$A_i=r_i-\frac{1}{G-1}\sum_{j\ne i}r_j$$

这一步的输入是完整的组奖励向量 R，输出是 G 维优势向量 A。机制上，它与“用组内均值做 baseline”只差一个分母，但性质完全不同：组内均值 baseline 对每个样本都包含它自己，导致优势与奖励自身相关，期望不为零，产生系统性偏差；留一法把自身排除，使 baseline 与 r_i 独立，从而 A_i 的期望等于真实优势。这个无偏性是纯代数的，不依赖任何近似，也不需要额外价值网络——这正是它适配 kernel 生成多样本采样的原因：同一 prompt 的 G 条候选天然构成可比组，组内比较即可，无需训练 critic。

代价在于方差与组大小的权衡。留一法 baseline 的方差随 G 增大而下降，因为均值估计用了更多样本；但 G 增大直接推高采样、编译、测速的线性成本。更隐蔽的代价是同质性：若组内 G 条候选全部编译失败或全部通过且时延接近，则 r_i 与 baseline_{-i} 几乎相等，A_i 趋近零，梯度信号被稀释。此时增大 G 并不能救场，因为新增样本大概率落在同一台阶上。工程判断是监控组内奖励的离散度，当离散度低于阈值时，与其加大 G，不如调整采样温度或 prompt 难度，让候选真正分化。一个具体例子：某简单 elementwise 任务下 8 条候选全部通过且时延差异在噪声范围内，优势向量几乎全零，这一组的策略梯度贡献接近于零，训练信号实际来自其他更难分化的 prompt。

四 · 标准化与裁剪：把优势变成可用的梯度权重

第四步对优势向量做标准化与裁剪，输出是用于加权的最终系数。标准化通常是在组内做零均值单位方差变换，裁剪则把极端值压到固定区间，防止单条异常样本主导更新。机制上，标准化改变了优势的尺度但不改变其符号排序，裁剪则直接牺牲部分信息换取稳定性。代价是双重的：标准化在组内方差极小时会放大噪声，把本已趋近零的优势重新拉成大幅值，反而制造虚假信号；裁剪则把真实的高优势样本截断，降低了有效学习率。这两者与第三步的同质性问题是耦合的——方差小的组经过标准化后，噪声被放大成看似显著的梯度。

伪代码思路是：先计算组内均值与标准差，做 (A_i - mean)/std，再 clamp 到 [-c, c]。具体例子：某组 8 条候选奖励为 {0,0,0,0,0,0,0,1}（七条失败一条成功），原始优势中成功样本约为 +0.875、失败样本约为 -0.125，标准化后成功样本被拉到接近 +2.6 量级，若裁剪阈值设为 2.0 则被截断。这条样本的梯度贡献被压掉一截，但换来的是更新步长可控。反过来，若八条全部为 1，标准化会因 std 趋零而产生数值爆炸，工程上必须加 epsilon 或直接跳过该组更新。

五 · 策略梯度更新与 KL 约束：优势如何落到参数上

第五步用优势加权策略梯度更新参数，并施加 KL 约束。输入是优势向量、G 条轨迹的 log 概率、以及参考策略；输出是参数增量。公式为：

$$\nabla_\theta J=\mathbb{E}\left[\frac{1}{G}\sum_{i=1}^{G}A_i\nabla_\theta\log\pi_\theta(\tau_i)\right]$$

机制上，每条候选的梯度按其优势加权求和，组内平均后回传。KL 约束的作用是限制新旧策略的偏离，防止一次高优势样本把策略拽离太远、破坏后续采样的多样性。代价体现在 token 与计算上：log 概率的计算要对每条候选的完整 token 序列做前向，G 条即 G 倍前向开销；KL 项需要参考策略的 log 概率，若参考策略是冻结副本则额外占一份显存。更关键的代价是梯度信噪比：当组内优势趋零时，加权梯度的期望虽无偏但方差相对更大，单步更新的有效信息量下降，表现为训练曲线在简单任务上停滞。

具体例子：某组中一条候选时延显著低于其余，优势为正且未被裁剪，其梯度项在组内求和时权重最大，参数更新主要沿这条候选的 token 方向；其余七条优势为负，提供反向拉力。KL 约束在此处的作用是防止这次更新把策略推得太远，使得下一轮采样仍能覆盖原有候选空间。若去掉 KL，高优势样本可能被过度强化，下一轮 G 条候选趋于同质，组内方差进一步塌缩，形成正反馈式的多样性丧失。

六 · 组级监控与 G 的动态调整：成本与信号的闭环

第六步是贯穿整组的监控与调度。输入是每组的奖励方差、优势分布、编译失败率、同质化程度；输出是下一轮 G 的取值与采样参数调整。机制上，这是一个以成本为约束的反馈环：G 太小则 baseline 方差大、优势噪声高；G 太大则编译测速成本线性膨胀而信号增益递减。监控指标中最直接的是组内奖励标准差与“全同组”比例——后者指奖励完全一致、优势全零的组占比，它直接度量了学习信号的浪费程度。

代价在这里表现为调度决策的滞后性：G 的调整要等若干组统计积累后才能生效，期间已消耗的 GPU 时间无法回收。另一个代价是监控本身的开销——记录每组诊断、聚合统计需要额外的存储与计算，虽不占 GPU 主路径，但在大规模并发下不可忽略。工程判断是：把 G 的下限锁在能保证 baseline 方差可接受的最小值，把上限锁在单组编译测速预算内，中间按全同组比例动态伸缩。具体例子：连续若干组全同组比例偏高时，系统下调 G 并提高采样温度，让候选分化；反之当组内方差过大、优势噪声明显时，上调 G 以压低 baseline 方差。这一闭环把“采样多少条”从超参数变成了随任务难度自适应的工作点，而它的每一次调整都以真实的编译与测速账单为代价。

留一法在流水线中的边界：何时失效、代价落在哪一层

把留一法嵌进 kernel 生成流水线，真正决定它可用性的不是公式本身，而是每一步的失败传播方式。采样 G 个候选后，每个候选要依次经过编译、正确性验证、测速三段，任一段失败即被赋予低奖励。这里的关键边界是：编译失败与数值错误在奖励空间里被压成同一个标量，留一法只看到标量差异，看不到失败类型。若同组 G−1 个对照样本全部编译失败而第 i 个样本编译成功但数值错误，baseline_{-i} 落在失败簇的低位，A_i 仍为正，策略梯度会把“能编译但算错”的 kernel 往上推。这是留一法在 kernel 场景下最典型的失效条件——奖励是单峰标量，而 kernel 的质量是多维的（编译性、正确性、时延、占用率），组内比较无法区分维度间的取舍。

第二个失效条件是组内同质化。当 prompt 过难，G 个候选全部编译失败，或过易全部通过验证且时延接近，组内奖励方差趋近零，A_i 同步趋零，该 prompt 对梯度的贡献被自动抹掉。这看似是安全特性，实则是采样预算的浪费：G 次编译与测速的 GPU 时间换来了零信息。监控组内奖励方差并动态调整 G 的机制正是为此存在，但调整本身有滞后——方差要在整组跑完编译测速后才能算出，而 G 的变更影响下一轮，中间存在一个 batch 的延迟。对长时延 kernel（单次测速需多次 warmup 与重复），这个延迟意味着数分钟的 GPU 空转。

$$\mathrm{Var}(A_i)=\mathrm{Var}(r_i)+\frac{1}{(G-1)^2}\sum_{j\ne i}\mathrm{Var}(r_j)-\frac{2}{G-1}\sum_{j\ne i}\mathrm{Cov}(r_i,r_j)$$

上式给出留一法方差的结构性代价：G 增大时第二项按 (G−1)^{-2} 收缩，但第一项 Var(r_i) 不随 G 变化，它来自单次编译测速本身的噪声——GPU 时钟抖动、共享显存争用、测速重复次数不足。这意味着把 G 从 4 提到 16 只能压低对照项，无法压低样本自身噪声；当测速噪声主导时，增大 G 的边际收益迅速衰减，而 GPU 成本线性上升。工程判断是：先保证单样本测速的重复次数与隔离度，再考虑加 G，否则是在为无法消除的噪声付采样费。

裁剪与标准化是另一处代价落点。留一法给出的 A_i 在组内均值附近对称分布，标准化除以组内标准差后，若组内仅有一个成功样本，其余全失败，该样本的标准化优势会被放大到极端值，裁剪阈值成为唯一的安全阀。阈值设得宽，梯度步长被单个异常样本主导；设得窄，真实的小幅改进被截断。这与 KL 约束形成耦合：KL 项压制的是策略整体漂移，裁剪压制的是单样本冲击，两者都在补偿留一法在稀疏成功组上的方差放大，而不是消除它。真正的消除手段是提高 G 或引入失败类型的分层奖励，前者付 GPU 成本，后者付奖励工程成本——留一法本身不解决这个问题，它只是把这个选择暴露在流水线的第三步上。
