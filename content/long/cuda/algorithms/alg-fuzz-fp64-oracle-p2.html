一 · 采样器：把 dtype 语义翻译成分布参数

fuzz 生成器不是“随机数发生器”，而是 dtype 语义到采样分布的编译器。它按 dtype 决定四类子分布的比例：正态（覆盖典型数值域）、均匀（覆盖量级跨度）、极端指数（逼近该 dtype 的最大/最小正规数与次正规数边界）、以及含 NaN/Inf 的混合分布。长度维度独立采样，强制包含非 2 的幂长度与尾部余数（如 1023、1025、4097），因为向量化 kernel 的尾块分支是最常见的错误藏身处。采样器输出一个结构体：输入张量、dtype 标签、shape、以及该样本所属的“覆盖桶”标识（如 extreme-exp / nan-prop / tail-remainder），后者用于后续失败归因。

代价在这里第一次显形：极端指数采样会让大量元素落在 fp16 的上溢区，若参考实现不做中间提升，参考自身就溢出。因此采样器必须与参考实现的精度策略联合设计——采样器记录“本样本预期是否触发上溢/下溢”，作为判定阶段区分“算法错”与“表示域限制”的元数据。一个具体例子：fp16 输入采样到 65504 附近的正态尾部，kernel 用 fp16 累加会溢出为 Inf，而 fp64 参考给出有限值，此时 checker 若只看相对误差会误判；正确做法是采样器把该样本标记为 overflow-prone，判定阶段改用“是否按 IEEE 规则饱和/溢出”的语义检查。

二 · fp64 参考：自身一致性先于比对

参考实现必须在被信任之前自证。流程是：先用 CPU 双精度（或 GPU 双精度）算出期望输出，再用一条更高精度的路径（如分段补偿求和、或 CPU 上的 long double / 任意精度库）复算同一批样本，记录两者的一致性残差。只有当参考自身残差远小于判定阈值时，该参考才被允许作为 oracle。这一步的输入是采样器产出的样本集，输出是“参考可信”标记与参考残差分布，代价是参考计算本身——GPU 上 fp64 吞吐约为 fp32 的 1/32–1/64，大 shape 下参考计算直接成为评测瓶颈。

工程上的折中是分层参考：小 shape 与边界样本走 CPU 高精度路径（慢但绝对可信），大 shape 走 GPU fp64 路径（快但需自证），两者在重叠样本上交叉校验。伪代码思路是：

$$\text{ref}(x)=\begin{cases}\text{cpu\_hp}(x), & |x|\le N_{\text{small}}\\ \text{gpu\_fp64}(x), & \text{otherwise}\end{cases},\quad \text{trust}=\mathbb{1}[\max|\text{cpu\_hp}-\text{gpu\_fp64}|_{\text{overlap}}<\delta_{\text{ref}}]$$

若 trust 为假，整个评测轮次作废而非降级使用——这是“可信评测”与“能跑就行”的分界线。代价是交叉校验样本的额外一次 fp64 计算，时延上等价于把参考成本乘以一个略大于 1 的系数，但换来的是判定结论的可辩护性。

三 · 比对：双阈值与 ULP 距离的联合判定

比对阶段输入是 kernel 输出与 fp64 参考，输出是逐元素的相对误差与 ULP 距离，再聚合为两个标量：最大相对误差与 ULP 的 95 分位。判定用双阈值，任一超标即失败：

$$\text{err}=\max_i\frac{|y_{\text{gen},i}-y_{\text{fp64},i}|}{\max(|y_{\text{fp64},i}|,\epsilon)},\quad \text{pass}=\mathbb{1}[\text{err}\le\tau_{\text{dtype}}\wedge \text{ULP}_{95}\le \upsilon]$$

阈值按 dtype 校准：fp32 相对误差取 1e-5 量级，fp16 取 1e-2 量级；ULP 阈值则约束“相对误差合格但逐元素抖动过大”的情形——例如归约类 kernel 在相对误差上过关，却在个别元素上偏离几十个 ULP，说明累加顺序不稳定，这在生产端会表现为 batch 间结果不可复现。双阈值的代价是判定逻辑更复杂、需要为每个 dtype 维护一对阈值，收益是把“算法错误”“精度差异”“数值不稳定”三类失败分开归因。具体例子：一个 softmax kernel 的 fp32 输出相对误差 3e-6 通过，但 ULP95 超出阈值，定位到 exp 近似实现的分段边界不连续，而非算法结构错误。

四 · 最小复现：失败样本的收缩与保存

判定失败后不直接丢弃样本，而是执行收缩：在保持失败的前提下，逐步减小输入长度、缩小数值范围、剔除无关元素，直到得到最小复现输入。收缩的输入是失败样本与失败判据，输出是一个小尺寸、可复现的输入张量加一份失败签名（err、ULP95、覆盖桶、dtype）。代价是收缩过程需要反复重跑 kernel 与参考，最坏情况下是 O(log n) 轮二分式缩减，每轮都要一次 fp64 参考计算；对大 shape 失败样本，收缩的时延可能超过原始评测本身。

收缩的工程价值在于把失败从“统计现象”变成“可调试对象”：最小复现输入可以直接喂给后续的 SASS/warp stall 剖析或二进制插桩 tracing，而不必在百万元素里猜错误分支。伪代码思路是：对长度做二分，对数值域做区间收缩，每步验证失败判据仍成立才接受收缩；若某步收缩后失败消失，则回退并记录该维度为“敏感维度”，这本身是归因信息。一个具体例子：一个 reduce kernel 在长度 4097 上失败，收缩到长度 33（一个 warp 加一个尾元素）后仍失败，直接指向尾块处理而非主循环。

五 · NaN/Inf 传播：单独语义通道

含 NaN/Inf 的样本不能走相对误差通道——任何与 NaN 的比较都为假，会导致“全 NaN 输出通过”的漏洞。因此判定流程为 NaN/Inf 输入单开一条语义通道：检查输出是否按 IEEE 规则传播（NaN 输入产生 NaN 输出、Inf 参与运算按规则产生 Inf 或 NaN、Inf−Inf 产生 NaN），并检查非 NaN 元素未被污染。输入是标记为 nan-prop 的样本，输出是逐元素的传播语义布尔向量，代价是这条通道无法用向量化比较指令批量完成，需逐元素或按位模式检查，吞吐低于常规比对。

跨框架不一致是这里的真实风险：不同框架对 NaN 的符号位、对 Inf 的饱和策略约定不同，若 checker 与参考实现各自隐含一套约定，二者会互相矛盾。工程判断是显式约定并写进合约：传播语义以 IEEE 754 为准，任何偏离必须在 kernel 合约里声明并由 checker 读取该声明，而不是让 checker 猜。一个具体例子：fp16 kernel 在 Inf 输入上返回饱和最大值而非 Inf，若合约声明“饱和语义”，checker 走饱和通道；若未声明，则判失败——这条判定不依赖数值大小，只依赖合约与实现的匹配。

六 · 单轮流动的成本账与瓶颈定位

把上述步骤串成一次完整流动，成本结构如下表（定性量级，非实测数字）：

步骤输入输出主要代价
采样dtype、shape 约束样本集 + 覆盖桶标记可忽略的 CPU 时延
参考计算样本集fp64 期望输出 + 可信标记GPU fp64 吞吐为 fp32 的 1/32–1/64，大 shape 下成为瓶颈
kernel 执行样本集生成输出kernel 自身时延，通常远小于参考

瓶颈定位的判断规则很直接：当参考计算时延超过 kernel 执行时延一个量级以上，评测的有效吞吐由参考决定，此时增大 batch 或并行样本数不会改善吞吐，只会加深 fp64 资源争用。工程上的应对是分层参考（第二节）与样本预算控制——把大 shape 样本数压到足以覆盖覆盖桶的最小集合，把预算让给边界样本。代价是覆盖率的统计置信度下降，收益是评测轮次能在可接受时延内完成。这条权衡必须显式记录在评测报告里，否则“通过率”会被误读为对全体 shape 分布的保证。

当 fuzz 与 fp64 参考自身成为瓶颈：边界、失效条件与系统代价

把随机 fuzz 与 fp64 参考串成一条流水线之后，真正决定这套 oracle 可用性的不是判定公式本身，而是每一步在什么条件下会失效。第一个失效点是 fuzz 生成器的分布覆盖与“可复现性”之间的张力：为了让硬编码失效，输入必须随机；但一旦判定失败，必须能保存最小复现输入，否则 agent 无法定位错误分支。工程上的做法是给生成器一个显式种子并记录采样路径（dtype、分布族、长度、特殊值注入位置），失败时把种子与最小化后的张量一起落盘。这里有一个常被忽略的代价：最小化（delta debugging）本身要在 fp64 参考上反复重算，若原始 shape 较大，缩减过程会把参考计算的次数放大数倍，评测时延从“一次前向”变成“几十次前向”。因此缩减必须设上限——按元素数或按重算次数截断，宁可保存一个未完全最小化的用例，也不能让单条失败样本拖垮整批评测的吞吐。

$$\text{cost}_{\text{eval}} = N_{\text{fuzz}}\cdot\left(t_{\text{gen}} + t_{\text{ref}}(S) + t_{\text{gen-kernel}}(S)\right) + N_{\text{fail}}\cdot k_{\text{shrink}}\cdot t_{\text{ref}}(S)$$

第二个失效点在于 fp64 参考的“参考资格”并非天然成立。fp64 实现自身也可能有错——归约顺序、累加器精度、超越函数的实现路径都会引入偏差，尤其在 CPU 与 GPU 双精度实现之间，数学库不同会导致末位差异。因此参考实现必须做自洽性检查：用更高精度（如 CPU 上的 double-double 或分段补偿求和）对同一输入抽样复核，记录参考与更高精度之间的一致性。若参考自身在某个输入区域就与更高精度不一致，该区域的判定结果不可信，checker 应把这段输入标记为“参考不确定”而非直接判 agent 失败。这一步的代价是参考路径要跑两遍甚至三遍，在 GPU 上双精度吞吐本就只有 fp32 的 1/32–1/64，再叠加复核，大 shape 下参考计算会直接成为整条评测链的瓶颈，agent 的生成时延反而被淹没。

步骤失效条件系统代价
fuzz 采样分布未覆盖非对齐长度/尾部余数漏检分支，误判率上升
fp64 参考参考自身与更高精度不一致参考重算 2–3 次，吞吐降至 fp32 的 1/32–1/64
双阈值判定阈值未按 dtype 校准fp16 用 fp32 阈值会把舍入误判为算法错误
NaN/Inf 检查框架间传播语义不一致checker 与参考互相矛盾，出现“全 NaN 通过”

第三个失效点最隐蔽：NaN/Inf 的传播语义。判定公式里的相对误差在遇到 NaN 时会退化为 NaN 比较，任何 `err ≤ τ` 都为假，于是“全 NaN 输出”在朴素实现下反而可能被某些宽松 checker 放过；而不同框架对 NaN 载荷、Inf 符号、0×Inf 的处理并不一致。工程上必须把特殊值检查从主判定中拆出来，单独约定：输入含 NaN 时输出是否必须为 NaN、Inf 的符号是否保持、有限输入是否允许产生 Inf。这条约定要写进 checker 而非依赖参考实现的默认行为，否则参考与 checker 会各说各话。代价是特殊值用例要单独跑一条判定分支，且每个 dtype 都要维护一份传播语义表，维护成本随支持的 dtype 数量线性增长。

最后一个边界是阈值 τ 与 ULP 双阈值的联合判定本身。公式要求相对误差与 ULP95 同时达标，这在数值接近零时会出现分歧：相对误差被 ε 截断后变得宽松，而 ULP 距离在次正规数附近急剧放大。fp32 用 1e-5、fp16 用 1e-2 的相对误差阈值是按 dtype 校准的，但 ULP 阈值 υ 若沿用同一套数值，会在极端指数输入上把正确的次正规数实现判为失败。可行的工程判断是：对极端指数与次正规区域单独放宽 υ 或改用绝对误差兜底，并把这类输入的判定结果标注为“精度敏感区”，让 agent 的优化反馈不被这类假失败污染——否则多轮 RL 的奖励信号会被系统性噪声拉偏，agent 学到的是规避次正规数而非真正修正算法。

阈值校准与 fuzz 覆盖之间的张力

这套 oracle 的失效点不在公式本身，而在两个可调量的耦合：fuzz 采样分布与 dtype 阈值 τ。若 fuzz 只按正态采样，输入落在极端指数区的概率极低，此时 τ 可以设得很紧（fp32 取 1e-5），误判率低但漏检率高——kernel 在次正规数或大指数差场景下的算法错误不会被触发。反过来，把极端指数、非对齐长度、NaN/Inf 混入采样后，同一 kernel 在同一 τ 下会因累加顺序差异产生更大的相对误差，τ 若不随采样分布放宽，就会把正确的 fp32 实现判为失败。判定式 $$\text{err}=\max_i\frac{|y_{\text{gen},i}-y_{\text{fp64},i}|}{\max(|y_{\text{fp64},i}|,\epsilon)},\quad \text{pass}=\mathbb{1}[\text{err}\le\tau_{\text{dtype}}\wedge \text{ULP}_{95}\le \upsilon]$$ 里 ε 的选取直接决定近零元素的判定行为：ε 过大则近零误差被稀释、掩盖符号错误；ε 过小则 fp32 在 1e-38 量级的舍入被放大成“失败”。工程上必须让 ε 与 τ 随 dtype 与采样档位联合标定，而不是全局常量。

第二个边界是 fp64 参考自身的可信度。参考实现若用 CPU 双精度逐元素循环，其与 GPU 双精度在归约顺序上的差异会引入与 kernel 同量级的误差，此时“参考”不再是 ground truth，而是另一个近似。缓解手段是对参考做自洽检查：同一输入用两种归约顺序（顺序累加与分块树形归约）各算一次，若两者相对差超过参考容差，则该用例作废而非判 kernel 失败。这一步的代价是参考计算量翻倍，在 GPU 上 fp64 吞吐约为 fp32 的 1/32–1/64，大 shape 下评测时延被参考端主导，单次验证的墙钟时间可能数倍于 kernel 本身。

第三个失效条件是 NaN/Inf 传播语义的框架分歧。IEEE 规则下 NaN 参与任何运算应传播为 NaN，但部分融合算子（如带 fast-math 的归约、饱和转换）会把 NaN 折叠成有限值或零。若 checker 只做数值比对而不单独走传播分支，会出现两种反向漏洞：全 NaN 输出因相对误差公式中 NaN 比较恒假而被判通过，或合法传播被误判失败。因此 NaN/Inf 用例必须走独立的布尔断言（逐元素 isnan/isinf 与符号位比对），不进入 τ 判定。下表给出三类输入的判定路径与主要代价。

输入档位判定路径主要代价
常规有限值相对误差 + ULP95 双阈值fp64 参考吞吐瓶颈
极端指数/次正规相对误差，ε 需按量级放宽τ 标定成本、误判风险
NaN/Inf 混合独立传播断言，绕过 τ需显式约定语义，跨框架不一致

最小复现输入的保存同样有系统代价：为定位错误分支需保留触发失败的完整张量，大 shape 下单个用例可达数百 MB 级显存与磁盘占用，若每轮 RL 都对失败用例做收缩（delta debugging），收缩过程本身要反复调用参考实现，把评测吞吐进一步压低。可行的工程判断是把收缩限制在标量或小切片上，用索引而非全张量回放，把“可复现”与“可存储”解耦。
