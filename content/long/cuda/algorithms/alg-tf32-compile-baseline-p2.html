一 · 步骤零：把基线锁进 manifest，而不是锁进代码

锚定基线的第一步不是写测量脚本，而是把“环境”本身变成一份可审计的产物。机制上，容器镜像的 CUDA、cuBLAS、cuDNN、PyTorch 版本号与 GPU 型号（含 SM 数量与显存容量）一并写入 manifest，评测进程启动时读取 manifest 并与运行时实际探测值逐项比对，任一不匹配即拒绝出分。这一步的输入是镜像标签与设备查询结果，输出是一份带哈希的基线指纹；代价是每次换机器都要重新生成指纹，且镜像体积与拉取时间随 CUDA 工具链膨胀，单次冷启动的容器准备时延远高于 kernel 本身的计时窗口。具体例子：同一份生成 kernel 在 A 机器上以 cuBLAS 某版本为分母得到加速，换到驱动与 cuBLAS 小版本不同的 B 机器，分母自身漂移，若不做指纹校验，两次评测的 speedup 会被误当作同一口径下的可比数字。工程判断是：manifest 校验失败时的正确行为是报错退出而非“尽力而为地测”，因为分母不可信时分子再准也没有意义。

与 manifest 配套的是开关锁定：torch.backends.cuda.matmul.allow_tf32、cudnn.benchmark、torch.compile 的模式选择必须在进程内显式赋值，而不是依赖默认值——默认值随 PyTorch 版本演进而变，这正是“虚高或虚低”的根源之一。锁定动作的输出是一组确定的布尔状态，代价是零运行时开销但引入了配置漂移风险：任何第三方库在 import 时改写这些全局开关，都会让后续测量静默失效，因此需要在每次计时前重读并断言。

二 · 四条参考路径的展开与各自代价

对每个 shape，参考侧要跑四条路径：eager fp32、eager tf32、torch.compile（max-autotune 档）、cuBLAS 直调。它们的输入是同一份按固定分布生成的张量（分布抽样本身是另一条目的主题，此处只强调同一 shape 必须复用同一份输入缓冲，避免分配抖动进入计时），输出是四条时延样本与四条对 fp64 参考的数值误差。四条的代价结构并不相同：eager fp32 走的是未融合的逐算子路径，显存峰值高、kernel 发射次数多，计时窗口里包含大量小 kernel 的启动开销；eager tf32 把矩阵乘的输入截断到 10 位尾数，吞吐上升但误差项随之放大；torch.compile 的代价不在稳态时延而在编译时间与 autotune 搜索——max-autotune 会对候选实现做实测挑选，首次调用可能耗时到秒级甚至更长，这段时间必须排除在计时之外，却又不能排除在“基线是否可用”的判断之外；cuBLAS 直调绕开框架调度，代价是需要自行管理 handle、workspace 与 stream，且其启发式选择在不同 shape 上可能退化。

计时协议是每条路径 warmup 20 次、计时 100 次取中位数。中位数而非均值的选择是为了抵抗偶发的时钟降频与调度抖动；代价是 100 次采样带来的统计噪声仍存在，尤其在小 shape 上单次时延落在微秒量级时，计时器分辨率与事件开销占比上升，需要用 CUDA event 而非主机侧时钟。四条路径合计约 4×100 次计时，这是单 shape 基线成本的量级来源；对含数十个 shape 的评测集，基线阶段本身就构成可观的时间预算，因此基线结果应按（shape, manifest 指纹）做缓存，命中即复用。

三 · 分母的合成规则与“精度换速度”的判定

四条路径测完之后，分母取四者最快时延：

$$S_{\text{eff}}=\frac{\min\{T_{\text{eager}},T_{\text{tf32}},T_{\text{compile}},T_{\text{cublas}}\}}{T_{\text{gen}}},\quad \text{valid}=\mathbb{1}\left[\max_i|y_{\text{gen},i}-y_{\text{fp64},i}|\le \tau\right]$$

这个 min 的语义是“该 shape 上现有最强参考实现的速度”，而不是“PyTorch 默认路径的速度”。取 min 的代价是分母对 cuBLAS 的退化极其敏感：若某 shape 上 cuBLAS 启发式选错 tile 或切分，分母被拉低，生成 kernel 的相对成绩被抬高——这正是把 cuBLAS 弱项误当生成 kernel 强项的风险面。反过来，若生成 kernel 只与未编译的 eager 比较，分母偏高，加速比虚高，KernelBench 类评测中常见的 2–5× 口径差异即由此产生。因此分母合成之后必须回看四条路径的离散程度：四条时延若彼此相差数倍，说明该 shape 对实现选择高度敏感，此时单一分母的说服力下降，应在结果里保留四条原始时延而非只报一个 speedup。

有效性判定与 speedup 是两条独立轴。生成 kernel 时延优于分母但 max_i|y_gen,i − y_fp64,i| 超过阈值 τ 时，标记为“精度换速度”，不计入有效加速。这里的代价是 τ 的选取本身需要与 dtype 口径对齐：tf32 路径的误差天然大于 fp32，若 τ 按 fp32 收紧，则 tf32 基线自身就会被判无效，分母集合被削掉一条；若 τ 放宽到 tf32 量级，则生成 kernel 可以靠降精度轻易通过。工程上可行的做法是让 τ 随参考路径的 dtype 分档，并要求生成 kernel 声明其数值口径，使 speedup 与 valid 在同一口径下比较。具体例子：一个把累加器降到 fp16 的生成 kernel 在时延上压过四条基线，但逐元素误差超出 fp32 档阈值，此时它得到的是“精度换速度”标签而非有效加速，避免评测集被降精度策略刷分。

四 · 缓存污染：autotune 与测量顺序的相互作用

torch.compile 的 autotune 结果会写入进程内缓存，同一 shape 第二次调用直接命中缓存，时延显著低于首次。若基线测量与生成 kernel 测量共享进程且顺序不当，分母会被缓存“喂快”，生成 kernel 的相对成绩被压低；反之若先测生成 kernel 再测基线，基线未命中缓存而偏慢，成绩被抬高。机制上的对策是每个 shape 测量前清空编译缓存（或使用独立进程/独立 cache 目录），使四条参考路径每次都从冷态开始；代价是清缓存后首次调用重新触发编译与 autotune，单 shape 的准备时间上升，且冷态时延本身包含编译开销，必须用 warmup 20 次把它挤出计时窗口。这里的工程判断是：warmup 次数不是拍脑袋定的，而是要让 autotune 的候选搜索在 warmup 阶段完成收敛，20 次是给定事实中的协议值，若某 shape 的候选实现多、搜索空间大，20 次未必够，需要在结果里记录 warmup 后时延的方差以判断是否已进入稳态。

测量顺序还应固定为“先基线后生成”，并对生成 kernel 同样执行清缓存与 warmup，使两侧的冷热状态对称。代价是对称化带来的总测量时长翻倍；收益是消除了顺序偏置这一系统性误差源。具体例子：同一生成 kernel 在“基线先测且不清缓存”的流程下得到的 speedup，与“每 shape 清缓存”的流程下得到的值不同，前者不可复现，后者才是可写进评测报告的口径。

五 · 单 shape 流水线的输入输出契约

把上述动作串成一次可重放的流动：输入是（shape 描述、输入分布种子、manifest 指纹、τ 分档）；第一段产出四条参考时延与四条对 fp64 的误差、四条显存峰值；第二段做基线自检——任一路径显存溢出或数值误差超出其 dtype 档位，则该路径从分母集合中剔除并记录剔除原因，防止“基线本身已降精度”被当作正常分母；第三段合成 min 分母并计算 S_eff 与 valid；第四段输出一条结构化记录：四条原始时延、分母、分子、speedup、置信区间、valid 标志、精度换速度标记、剔除原因列表。置信区间来自 100 次采样的中位数附近的分位数估计，其代价是采样数不足时区间偏宽，小 shape 上尤其明显，因此记录里应同时保留采样数与区间宽度，供下游判断该 shape 的成绩是否稳定。

这条流水线的显存代价常被忽略：四条参考路径各自持有输入、输出与 workspace，cuBLAS 直调的 workspace 随 shape 增长，torch.compile 的候选实现可能额外分配临时缓冲。若在同一进程内顺序执行且不释放，显存峰值会叠加，导致后续路径触发分配器回退甚至 OOM，使基线时延被分配行为污染。对策是每条路径测量后同步并释放中间张量，记录单路径显存峰值而非进程峰值。具体例子：一个大 shape 上 cuBLAS workspace 与 compile 候选缓冲叠加后逼近显存上限，若不隔离，最后测的那条路径时延异常偏高，分母被错误地排除掉最快的一条。

六 · 分母的可复现性与跨机重跑的成本结构

基线受 GPU 型号与驱动影响，跨机器复现必须重跑全部参考路径，不能搬运分母数字。机制上，manifest 指纹作为缓存键的一部分，指纹不同即缓存失效，强制重跑；代价是每台新机器上的基线阶段都要付出 4×100 次计时加清缓存与 warmup 的时间，对多机评测集群这是显著的前置开销。降低这部分成本的可行手段是把基线结果按（shape, 指纹）持久化并在集群内共享，但共享的前提是指纹严格一致——驱动小版本差异即视为不同指纹，宁可重跑也不混用。工程判断落在“分母是测量产物而非常量”这一认识上：任何把分母写死成表格的评测流程，都会在换机器后悄悄失去可比性，而 manifest 校验加缓存失效机制是把这种漂移显式化的最低成本手段。

最后一步是把分母的元信息随成绩一起落盘：四条原始时延、剔除记录、τ 分档、采样数与区间宽度。这些字段不参与 speedup 计算，却决定了成绩能否被审计。代价是记录体积与序列化开销上升，收益是当某条成绩被质疑时，可以回溯到是分母被 cuBLAS 退化拉低、还是生成 kernel 走了精度换速度路径——在没有这些字段的情况下，两者在最终数字上不可区分。

锚定基线的失效边界：什么时候“四路取最优”反而会骗人

这套四路锚定（eager fp32、eager tf32、compile max-autotune、cuBLAS 直调）的可靠性建立在一个隐含前提上：四条参考路径本身都是“干净”的——没有溢出、没有静默降精度、没有缓存污染。一旦这个前提破了，分母就不再是可信的地板，而是被压低的假地板，speedup 会被系统性放大。最典型的破法是 torch.compile 的 autotune 缓存：同一 shape 第二次进入时，编译路径直接命中已缓存的 kernel 选择，跳过了 autotune 的搜索与计时开销，于是它的中位时延比首次测量低一截。若不清缓存就连续跑多个生成 kernel 的对比，compile 基线会越跑越快，分母持续缩水。工程上的硬约束是每个 shape 测量前显式清空 inductor 缓存目录并重置 dynamo 状态，代价是每个 shape 多付一次完整 autotune 的编译时间——在 max-autotune 模式下这是分钟级而非毫秒级，对上百个 shape 的评测集来说，编译时间会成为总墙钟时间的主项，而不是 kernel 执行本身。

第二个失效条件是数值口径的静默漂移。cuBLAS 直调路径在特定 shape 上会因启发式选择而退化（例如窄 K、非对齐 stride 时切到低效 tile），此时它的时延明显高于 eager，四路取最优会自动把 cuBLAS 排除——这本来是优点，但也意味着基线集合对 shape 分布高度敏感：换一批 shape，最优路径的归属就变了，跨 shape 聚合的几何平均 speedup 不再是同一把尺子量出来的。更危险的是 tf32 路径：它天然带约 10 bit 尾数精度，若阈值 τ 设得宽松，tf32 基线可能以更低时延胜出，而生成 kernel 用 fp32 累加跑出更慢但更准的结果，被判为“无加速”。此时 $$S_{\text{eff}}=\frac{\min\{T_{\text{eager}},T_{\text{tf32}},T_{\text{compile}},T_{\text{cublas}}\}}{T_{\text{gen}}}$$ 的分子被 tf32 拉低，而 $$\text{valid}=\mathbb{1}\left[\max_i|y_{\text{gen},i}-y_{\text{fp64},i}|\le \tau\right]$$ 只校验生成侧、不校验基线侧，于是出现“基线不合法却当了分母”的漏洞。修补办法是把 valid 判据同时施加到四条参考路径上：任何一条对 fp64 参考超阈值的路径，先从 min 集合里剔除再取最优，代价是每个 shape 多四次 fp64 参考计算与误差统计，显存峰值也要额外记录一份。

第三类边界是硬件与驱动的不可迁移性。基线时延绑定 GPU 型号、驱动版本与 cuBLAS/cuDNN 版本，manifest 锁死容器镜像只能保证同一台机器内自洽；跨机器复现必须重跑全部参考路径，单 shape 成本约 4×100 次计时加 4×20 次 warmup，再叠加 compile 的 autotune 编译。以一张表概括各步骤的输入、输出与主要代价：

步骤输入输出主要代价
镜像锁定CUDA/cuBLAS/cuDNN/PyTorch 版本、GPU 型号manifest跨机需整体重跑，无法增量复用
四路参考测量shape、输入分布、清空后的 compile 缓存四条中位时延 + 误差 + 显存峰值4×120 次迭代/ shape，compile 编译时间占主导

生成侧判定生成 kernel 时延与误差speedup、置信区间、精度换速度标记误差超阈值则不计入有效加速，样本被浪费

还有一个容易被忽略的系统代价：置信区间的宽度直接受基线抖动支配。若某条参考路径（尤其 cuBLAS 在小 shape 上）时延方差大，取 min 会让分母偏向低分位数，speedup 的区间估计随之偏窄，看起来“显著”实则只是采样运气。稳健做法是对每条路径取中位数而非最小值再取四者最优，或在 min 之外同时报告四分位区间；代价是每个 shape 的计时次数从 100 提到更多以稳定分位数，评测总时长线性上升。工程判断上，这套锚定适合 shape 集合固定、机器同构、且愿意为编译时间买单的离线评测；一旦进入在线或多机横向对比，必须把“基线重测”当作一等公民的成本项计入预算，否则分母的漂移会吞掉生成 kernel 真实的那部分收益。
