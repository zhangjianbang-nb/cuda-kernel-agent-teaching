一 · 从一次评测翻车说起：自由文本生成的预算黑洞

设想一个典型的 kernel 生成评测回合：给定一个 fused softmax 或 layernorm 的算子描述与目标 GPU，agent 在 40 轮预算内迭代产出 CUDA C++。前 12 轮里，有 9 轮产出的代码根本过不了 nvcc——不是缺少 __syncthreads()，就是共享内存声明与 tile 尺寸不匹配，或者把 blockDim.x 与模板参数混用导致越界。剩下 3 轮能编译的，其中 2 轮在 fp32 参考对比下数值偏差超出容差，只有 1 轮真正跑进了性能测量环节。于是 40 轮预算里真正用于"性能探索"的不到四分之一，其余全部消耗在修语法、补同步、对齐边界上。这不是模型的推理能力问题，而是搜索空间的形状问题：自由文本是一个几乎无结构的空间，语法正确性构成一道稀疏的、离散的墙，agent 的每一次采样都要先撞墙再谈优化。

更隐蔽的翻车发生在评测口径上。当生成物是整段源码时，"哪一处改动带来了加速"无法归因：一次 1.3 倍的提速可能同时混入了 tile 从 32 改到 64、去掉了冗余的边界分支、以及把两次全局读合并成一次。keep-revert 搜索在这样的空间里只能做整段代码的保留或回退，无法做字段级消融，于是搜索退化为随机游走。评测分数看似在涨，但涨的原因不可解释，也无法迁移到下一个 shape。

这两类失败指向同一个工程判断：在让 LLM 写 kernel 之前，先把"写什么"从"怎么写"里剥离出来。策略 IR 与 DSL 约束生成做的就是这件事——LLM 不再输出源码，而是输出一份带类型与取值域约束的设计决策记录，由确定性 lowering 器翻译成 CUDA/Triton。语法墙被前移到 schema 校验，编译失败在 lowering 之前就被挡掉；决策字段可枚举，反馈能精确落到"哪个字段、哪类错误"，搜索也才有字段级消融的可能。

二 · 这个方法解决的具体问题：把程序合成约束成决策序列

问题的形式化可以写成一个受约束的优化：

$$\text{score}(d)=\mathbb{1}[\text{compile}(d)]\cdot\mathbb{1}[\text{correct}(d)]\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)},\quad d\in\mathcal{D}_{\text{DSL}},\ \text{s.t.}\ R(d)\le R_{\max},\ S(d)\le S_{\max}$$

这里 \(d\) 是 DSL 决策向量而非源码字符串，\(\mathcal{D}_{\text{DSL}}\) 是由 schema 定义的笛卡尔积（带合法取值域），\(R(d)\) 是寄存器占用，\(S(d)\) 是共享内存字节数，\(R_{\max}, S_{\max}\) 是硬件上限。注意 score 里的两个指示函数：编译与正确性是硬门，性能是软比。这个式子的关键不在评分本身（评分口径由 Roofline/SOL 归一那一部分处理），而在于可行域是被 schema 显式刻画的——\(d\) 的每一维都有类型和取值域，非法组合在解析阶段即被拒绝，而不是等到 nvcc 报错。

具体机制上，DSL schema 至少覆盖六类字段：tile 尺寸（如 BM、BN、BK）、线程映射（每个 tile 由多少 warp 沿哪个维度切分）、访存模式（向量化宽度、是否走 ldmatrix、全局读的合并策略）、流水线级数（cp.async 的 stage 数）、共享内存布局（swizzle 方式、padding）、边界处理策略（predicated 还是 padded）。每一项带合法取值域与类型约束，例如 BK 必须是 2 的幂且 BM*BK*4 ≤ S_max，流水线级数与共享内存总量之间存在线性约束。LLM 读取问题描述与硬件约束后输出这组决策，解析器做 schema 合法性校验与资源上限核算，确定性 lowering 再把它翻译成源码并注入边界检查与同步原语。

这样做的直接收益是编译失败率的结构性下降：语法错误被挡在 lowering 之前，因为 lowering 器产出的代码模板本身是经过验证的，变化的只是模板参数与分支选择。每轮预算更多落在性能探索而非修语法上。代价同样明确：DSL 的表达力上限就是性能上限。如果 schema 里没有"warp-specialized 流水线"这一维，那么 agent 无论多聪明都生成不出 producer-consumer 分离的 kernel；DSL 未覆盖的非常规优化（非均匀 tile、跨 block 的 persistent 调度、寄存器重用的手工编排）全部落在可行域之外。这是一个用表达力换可控性的交易，必须被显式承认而不是假装不存在。

一个具体的例子：在 GEMM 类算子上，schema 若只允许 BM∈{64,128}、BN∈{64,128}、BK∈{16,32}、stage∈{2,3,4}，决策空间是 2×2×2×3=24 个组合（再乘上 swizzle 与边界策略的少数选项）。这个空间小到可以穷举，也小到 beam search 在几轮内就能覆盖大部分；但正因为它小，任何需要 BM=256 或 stage=5 才能榨出的那部分性能就永远拿不到。工程判断因此变成：schema 的维度设计要与目标算子的性能瓶颈对齐——瓶颈在共享内存带宽就把 swizzle 与 BK 做成高分辨率维度，瓶颈在 occupancy 就把寄存器预算与 stage 做成约束耦合项。

三 · 它不解决什么：表达力边界之外的三个盲区

第一，它不解决算法层面的重构。DSL 描述的是"给定算子如何映射到硬件"，不是"这个算子该不该换一种数学等价形式"。FlashAttention 式的分块重写、把两次归约合并成一次、用结合律重排求和顺序以改善数值稳定性——这些属于算法选择，落在 schema 之外。若问题的最优解需要换算法，DSL 约束生成只能在给定的算法骨架内做局部最优，天花板由骨架决定。

第二，它不解决lowering 器自身的正确性。DSL 把语法错误挡在门外，但 lowering 器是一个需要维护的编译器：它注入的同步原语是否正确、边界检查是否覆盖所有 predicated 路径、swizzle 索引计算是否与声明的布局一致，这些正确性负担从 LLM 转移到了 lowering 器作者身上。一个 lowering bug 会以"所有使用该字段取值的决策都错"的形式系统性污染评测——比 LLM 的随机语法错误更危险，因为它看起来像是性能问题而非正确性问题。这也是为什么正确性 oracle 与变异测试审计必须独立于 DSL 层存在（那两部分各有专文）。

第三，它不解决跨架构的可移植性。DSL 字段的合法取值域往往与具体架构特性绑定：某个 stage 数在一种 SM 上合法，在另一种上因共享内存容量不足而非法；某个向量化宽度依赖特定的对齐要求。DSL 扩展与 CUDA 版本、架构特性的同步是持续的工程成本，schema 一旦冻结就会迅速过时。这不是一次性的建模工作，而是需要跟着硬件演进的维护负担。

代价可以用一个具体的量级感来说明：假设 lowering 器对每个 DSL 决策生成约数百行的模板实例化代码，编译一次需要数秒到数十秒（模板展开与寄存器分配是主要成本）。若 beam search 每轮评估 8 个候选，40 轮就是 320 次编译，编译时间本身可能超过性能测量时间。这意味着 DSL 层的搜索必须做编译缓存与决策去重——相同决策向量不重复编译，相邻决策共享模板实例——否则预算会被编译时间吃掉。这是自由文本生成不会遇到、而 DSL 约束生成必须正面处理的开销。

四 · 适用边界的判据：什么时候该上 DSL，什么时候不该

给出三条可操作的判据。其一，算子族是否具有稳定的结构骨架。GEMM、卷积、归约、softmax、attention 这类算子的并行结构高度模式化，tile/thread/block/流水线的决策维度可以被枚举，DSL 收益最大。反之，图级别的融合算子、依赖运行时数据分布的稀疏算子、控制流随输入变化的算子，其结构骨架不稳定，schema 要么退化成"允许任意代码"（失去约束意义），要么覆盖不全（失去表达力）。

其二，性能瓶颈是否落在 DSL 覆盖的维度上。若 profile 显示瓶颈是共享内存 bank conflict 或流水线气泡，而 schema 恰好有 swizzle 与 stage 维度，那么 DSL 搜索能直接命中。若瓶颈是 warp stall 中的长延迟依赖链（需要指令级重排）或 L2 命中率（需要跨 block 的调度策略），而 schema 没有对应维度，则 DSL 搜索会在一个错误的方向上做精细调优，产出"合法、正确、但不快"的配置。判据是：先做一次 NCU 剖析定位瓶颈类别，再检查 schema 是否有对应字段；没有就先扩 schema，而不是先跑搜索。

其三，评测预算中编译时间占比是否可接受。若单次编译时间远大于单次性能测量时间，DSL 搜索的吞吐会被编译主导，此时应优先做决策空间剪枝与编译缓存，或缩小 schema 维度，而不是加大 beam 宽度。

场景DSL 约束生成是否适用关键理由
规则 GEMM/卷积/attention 骨架适用结构模式化，决策维度可枚举，瓶颈可映射到字段
需要算法级重写（如分块重排）不适用算法选择在 schema 之外，天花板由骨架决定
稀疏/数据依赖控制流算子边界模糊骨架不稳定，schema 易退化为无约束或覆盖不全
瓶颈在指令级重排或跨 block 调度需先扩 schema现有维度无法命中瓶颈，搜索方向错误
编译时间主导预算需先剪枝/缓存吞吐被编译吃掉，beam 加宽无益

一个边界案例值得单独说：某次评测中，agent 在 DSL 空间内把某个 layernorm 变体的 tile 从 128 调到 256、stage 从 2 调到 3，性能提升有限且稳定；但当把同一算子交给自由文本生成时，模型偶然写出了一次把两次归约合并、并用 warp shuffle 替代共享内存的版本，性能显著更好。这不是说自由文本更好，而是说明该算子的性能瓶颈恰好落在 DSL 未覆盖的算法重构维度上。正确的工程反应不是放弃 DSL，而是把"归约合并策略"与"warp shuffle 使用"提升为 schema 的新字段，让这次偶然发现变成可复现、可消融的决策维度。这正是 DSL 扩展的典型触发条件：当自由文本在 schema 外反复命中同一类优化时，该类优化就该被 schema 化。

五 · 与评测可信度的耦合：为什么 schema 决定了反馈的粒度

DSL 约束生成的一个常被低估的价值在于它改变了反馈信号的结构。自由文本生成下，编译错误是一条指向某行代码的报错，agent 需要自己推断"是 tile 太大还是同步缺失"；正确性失败是一个数值误差，agent 需要自己定位是哪一段访存越界。反馈是非结构化的，修错过程本身消耗轮次。而在 DSL 下，解析器可以输出"字段 BK 取值 64 违反共享内存上限 \(S_{\max}\)"或"字段 stage=4 与 BM=128 的组合导致寄存器溢出"，反馈精确落到字段级。这让多轮 RL 的信用分配（credit assignment）从"整段代码"缩小到"单个决策维度"，梯度信号的方差随之下降。

但这里有一个必须警惕的耦合：schema 的粒度决定了评测能分辨的最小改进。若 schema 把"访存模式"做成一个粗粒度的枚举（如"向量化/非向量化"二选一），那么评测无法分辨"向量化宽度 4"与"向量化宽度 8"的差异，即使后者在特定 shape 上更快。评测的分辨率被 schema 的分辨率封顶。这与隐藏 shape 分布抽样那部分形成互补：抽样决定评测覆盖哪些输入，schema 决定评测能看见哪些实现差异，两者共同定义了"可信评测"的边界。一个在粗粒度 schema 上得分很高的 agent，可能只是擅长在少数几个粗粒度决策上做对，而非真正理解硬件。

代价体现在 token 预算上：DSL 决策向量的序列化长度通常远小于整段源码，单轮生成的 token 消耗下降，这意味着同样的预算可以支撑更多轮搜索或更宽的 beam。但反过来，schema 的文档（每个字段的语义、取值域、约束耦合）需要被注入 prompt，这部分是固定开销，且随 schema 维度增长而线性增长。当 schema 扩展到几十个字段时，prompt 中的 schema 描述可能占据相当比例的上下文，挤压问题描述与硬件约束的空间。这是一个需要在 schema 设计阶段就权衡的工程问题：字段不是越多越好，而是要与瓶颈对齐、与 prompt 预算匹配。

最后落到一个具体的工程判断上：DSL 约束生成不是"让 LLM 少犯错"的补丁，而是把 kernel 生成问题重新定义为在受约束的决策空间上做搜索。它的适用边界由三件事共同划定——算子骨架的稳定性、瓶颈与 schema 维度的对齐度、以及 lowering 器与 schema 的维护成本。越过这条边界，它产出的是合法、正确但不快的配置；在这条边界之内，它把编译失败率压下去、把反馈粒度做细、把搜索从随机游走变成字段级消融。判断一个 kernel 生成任务该不该上 DSL，本质上是在问：这个任务的性能上限，是否可以被一组可枚举的设计决策所刻画。
