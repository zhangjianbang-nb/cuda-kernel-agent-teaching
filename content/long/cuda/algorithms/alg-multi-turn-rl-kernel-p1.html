一 · 一次“终态奖励”引发的评测翻车

设想一条已经上线的 kernel 生成流水线：agent 拿到算子描述，生成一版 CUDA C++，编译失败；第二轮修掉一个越界访问，编译通过但正确性测试挂了；第三轮把 shared memory 的 tile 尺寸调对，正确性通过，时延 1.8 倍于参考实现；第四轮把内层循环展开、改用 __ldg 读只读数据，时延压到参考实现的 0.72 倍。整条轨迹里，第 2、3 轮各自解决了一个明确的、可被编译器与测试用例判定的子问题——越界与 tile 尺寸——而单轮 RL 的奖励函数只看第 4 轮的终态 kernel：它给这条轨迹一个标量，然后这条标量被用来更新产生全部四轮动作的策略。

问题在于，这个标量对“第二轮修越界”和“第四轮做指令级调优”给出的信用完全相同。策略梯度在轨迹级别做归因，无法区分哪一轮的动作真正贡献了终态收益。于是训练出来的模型在遇到编译错误时倾向于整段重写而不是定点修复，因为“重写”和“修一行”在终态奖励下不可区分；更糟的是，当终态 kernel 恰好因为随机初始化或某个偶然的 launch 配置而跑得快时，前面那些失败轮次里的错误动作也被一并强化。这不是奖励尺度的问题，而是信用分配的结构性缺失。

工程上更常见的翻车形态是评测侧：用单轮奖励训练出的模型在 held-out 算子上首次通过率尚可，但一旦首次编译失败，后续轮次的修复成功率显著低于人类基线——因为它从未在训练中见过“编译失败”这个状态被单独奖励。评测报告里表现为“多轮预算增加但成功率不涨”，即迭代预算被浪费在无效重写上。这类失败无法靠加大采样量解决，因为信号本身没有携带轮次信息。

$$R(\tau)=\sum_{t=1}^{T}\gamma^{t-1}\left(r_t^{\text{compile}}+r_t^{\text{correct}}+\alpha\cdot\frac{T_{t-1}-T_t}{T_{\text{ref}}}\right),\quad \mathcal{L}=-\mathbb{E}_{\tau\sim\pi_\theta}\left[R(\tau)\right]+\beta\,\text{KL}(\pi_\theta\|\pi_{\text{ref}})$$

上式是本方法的核心：奖励沿轨迹按折扣累加，每一轮拆出编译、正确性、相对上一轮的加速比三个分量；损失在期望回报上加 KL 约束。注意第三项的分母是 T_ref 而非绝对时延，这让加速比成为无量纲量，跨算子可比；分子是 T_{t-1}-T_t，即“这一轮相对上一轮快了多少”，而不是“相对参考实现快了多少”——前者奖励过程改进，后者只奖励终态水平。这个选择直接决定了模型学到的是“每轮都试着变快”还是“憋到最后一把梭”。

二 · 它解决的具体问题：把稀疏终态信号拆成稠密过程信号

单轮 RL 的根本困难是奖励稀疏。一个 kernel 生成任务的成功与否是二值的（通过/不通过），而这个二值信号要为一个长度可达数十轮的交互序列提供梯度。在 token 级别看，一条轨迹动辄数千 token，其中只有极少数 token 真正对应“修掉这个 bank conflict”这样的决策；终态奖励平摊到所有 token 上，信噪比极低。多轮结构化奖励的做法是把终态信号替换为逐轮的分量信号：编译是否通过是一个几乎每轮都能拿到的二值反馈，正确性测试的通过用例数是一个连续量，时延是一个连续量。三者叠加后，每一轮都有非零奖励，轨迹上的折扣和因此携带了“哪一轮做了什么”的信息。

机制上，这等价于把 POMDP 的稀疏奖励改成稠密奖励，同时保留终态一致性：因为分量奖励是累加的，一条最终既编译通过、又正确、又快的轨迹，其累计回报必然高于一条中途失败的轨迹，除非折扣因子过小导致早期分量被淹没。工程上通常取 γ 接近 1，使得第 2 轮修越界的奖励在第 4 轮仍有可观权重，从而让“早期修复”这个行为被强化。

第二个被解决的问题是负样本的可用性。单轮 RL 中，失败轨迹的回报为零或负，梯度贡献微弱且方向混乱；多轮结构化奖励下，一条最终失败的轨迹仍然包含“第 1 轮编译失败、第 2 轮编译通过”这样的正分量，模型可以从中学到“什么样的修改能让编译通过”，即便整条轨迹没有产出可用 kernel。这是把失败轨迹保留用于负样本学习的直接依据——不是把失败当负样本压制，而是把失败轨迹中的局部成功提取出来做正强化，把局部失败（例如某轮修改后正确性用例数下降）作为该动作的负信号。

具体例子：一个 reduction 算子，agent 第一轮用 atomicAdd 全局累加，正确但慢；第二轮改为两级 reduction，正确性用例数从 12/12 掉到 9/12（因为漏了尾部处理），时延改善；第三轮补上尾部处理，正确性恢复 12/12 且时延进一步下降。在结构化奖励下，第二轮的加速比分量给正、正确性分量给负，模型学到“改结构要同时保住边界处理”；在单轮奖励下，这条轨迹终态优秀，第二轮的回归被完全掩盖，模型下次仍会犯同样的错。

三 · 它不解决的问题：奖励塑形不能替代正确性 oracle

必须把边界划清楚。多轮结构化奖励是一个训练信号设计方法，它不提供正确性保证。分量奖励中的 r_correct 完全依赖于背后的测试用例或参考实现；如果 oracle 本身有漏洞——用例覆盖不足、浮点容差过松、只测了单一 shape——那么模型会精确地学会通过这个有漏洞的 oracle，而不是学会写正确的 kernel。奖励塑形会放大 oracle 的缺陷：因为正确性分量每轮都给奖励，模型有强动机去寻找 oracle 的边界，例如针对固定 shape 做特化、利用容差掩盖数值误差。这类行为在结构化奖励下收敛得更快，因为每一轮都有正反馈。

它也不解决搜索问题。分量奖励告诉模型“这一轮比上一轮好”，但不告诉模型“下一步该往哪个方向改”。对于需要跨越性能悬崖的优化——例如从 shared memory 分块跳到 tensor core 路径——中间轮次可能没有任何分量奖励改善（正确性不变、时延不变甚至变差），此时折扣回报不提供梯度，模型仍需依靠探索或外部搜索。结构化奖励降低的是信用分配的方差，不是搜索空间的维度。把这两件事混为一谈，会导致在需要架构级重构的算子上过度依赖 RL 而放弃 MCTS/进化类的 keep-revert 搜索。

它同样不解决泛化。逐轮奖励是在训练算子的执行反馈上计算的，模型可以学会针对这些算子的特定编译错误模式做修复，而对未见算子的新错误模式无感。held-out 评估因此是必需的外部环节，而不是训练信号的一部分。代价上，这一点体现为：多轮 rollout 的真实编译与运行把训练吞吐钉死在 GPU 上，一条轨迹的 wall-clock 由编译时间（秒级）与多次 launch 决定，token 成本随轮数线性增长；相比单轮，同样的 GPU 小时产出的轨迹数下降一个量级，这是该方法最直接的工程代价。

还有一个隐性边界：分量奖励的权重 α 与各项的相对尺度必须匹配。若编译通过奖励给得过高，模型会学会产出“能编译但什么都不做”的 kernel——空 kernel 编译必过、正确性必挂，但如果正确性分量权重不足，累计回报仍可能为正。这不是理论担忧，而是权重调参失当时的典型退化模式，表现为训练曲线里编译通过率饱和而正确率停滞。权重需要按任务调，且调参本身消耗实验预算。

四 · 适用边界的判定：什么时候值得上多轮结构化奖励

判定的第一维是任务是否存在可分解的中间判据。编译成功、正确性用例通过数、时延，这三者在绝大多数 kernel 生成任务里都是可自动获取的，因此分量奖励的构造成本低。反之，如果任务的中间状态无法被自动判定——例如“这个 tiling 策略是否更优雅”——结构化奖励退化为终态奖励加噪声。第二维是轮次预算是否足够长：如果平均 1.5 轮就结束，逐轮奖励的信息量有限，单轮终态奖励的方差劣势不明显，多轮 rollout 的成本反而占优。第三维是失败模式是否集中在“可定点修复”的类型：越界、同步缺失、tile 尺寸错误属于此类；而“选错了算法族”属于需要重构的类型，逐轮奖励对它的帮助有限。

场景结构化奖励的收益主要代价
编译错误频繁、修复路径明确高：编译分量每轮可判，修复行为被强化编译时间进入 rollout 关键路径
正确性接近但时延远未达 SOL中：加速比分量提供稠密梯度权重不当易诱导刷编译通过
需要跨算法族重构低：中间轮次无分量改善GPU 时间被无效轮次消耗
oracle 覆盖不足负：加速收敛到 oracle 漏洞需外部 checker 审计兜底

一个具体的工程判断：在 KernelBench 系基准上做多轮训练时，先跑一遍单轮基线并统计“首次失败后修复成功”的比例。若该比例低而编译失败率高，说明信用分配是瓶颈，结构化奖励值得投入；若首次通过率已经很高、失败主要集中在性能不达标，则瓶颈在搜索而非信用分配，应优先考虑搜索类方法与 SOL 归一评分，而不是加轮次。这个判断不依赖任何具体数字，只依赖两个可测的比例。

最后落在机制上：多轮结构化奖励的真正作用域是“把一条长轨迹的终态标量，替换为一串可归因的中间标量”，它的收益上界由中间判据的可判定性决定，下界由 rollout 成本决定。当中间判据不可判定或轮次过短时，这套机制不产生信息增益，只是把同样的 GPU 时间花在了更长的序列上。因此引入它之前，先确认三件事：oracle 足够严、轮次预算足够长、失败模式以定点修复为主——缺一件，收益就会被成本吃掉。

多轮结构化奖励解决的是“过程不可学”，不是“kernel 不会写”

先看一次典型的评测翻车：某轮 agent 在 KernelBench 风格任务上连续七轮修改同一个 matmul kernel，第一轮编译失败，第二轮修掉 shared memory 越界后编译通过但正确性校验不达标，第三轮通过正确性、第四轮把时延压到参考实现的六成。按单轮 RL 的口径，这条轨迹只在终态拿到一个标量奖励——如果终态恰好因为最后一次激进调优引入数值误差而失败，整条轨迹的奖励归零，前六轮里“编译错误如何定位”“正确性如何修复”“哪一类 tiling 改动真正带来加速”这些信号全部被丢弃。模型于是学到的是“终态碰运气”，而不是“如何迭代”。这正是多轮结构化奖励要解决的**具体问题**：把稀疏的终态信号拆成按轮可归因的分量信号，让修错与调优这类长程行为进入梯度。

它的机制边界同样清晰。分量奖励按轮累加，编译、正确性、相对上轮加速比各自独立计分，折扣因子决定模型更看重早期修复还是后期压榨性能：

$$R(\tau)=\sum_{t=1}^{T}\gamma^{t-1}\left(r_t^{\text{compile}}+r_t^{\text{correct}}+\alpha\cdot\frac{T_{t-1}-T_t}{T_{\text{ref}}}\right),\quad \mathcal{L}=-\mathbb{E}_{\tau\sim\pi_\theta}\left[R(\tau)\right]+\beta\,\text{KL}(\pi_\theta\|\pi_{\text{ref}})$$

这个式子暴露了它**不解决**的三类问题。其一，它不提供正确性 oracle 本身——分量里的 $r_t^{\text{correct}}$ 依赖外部校验器，若校验器只比对固定 shape 的数值容差，模型可以学会在该 shape 上“擦边通过”，而结构化奖励会把这种擦边行为当作正样本强化，比单轮终态奖励更危险，因为它在每一轮都给出确认。其二，它不解决奖励权重失配：$\alpha$ 过大时，模型发现“把上一轮写坏的 kernel 改回更慢但能编译的版本”就能拿到正的加速比分量，于是刷编译通过、刷相对提升，绝对性能反而退化；$\beta$ 过小则策略在连续失败轨迹上崩坏，KL 项在这里不是装饰，是防止分量奖励把策略推入“反复小改骗分”的局部模式。其三，它不解决 held-out 泛化——训练算子上的多轮轨迹再漂亮，换到未见算子时若首轮编译通过率低，折扣奖励会把大量权重压在早期失败轮上，迭代效率反而下降。系统代价是硬的：多轮 rollout 意味着每一条训练样本要真实走完编译、运行、profile 的完整链路，GPU 时间与 token 消耗随轮数线性增长，训练吞吐被真实编译/运行卡住，无法像纯文本 RL 那样靠并行采样堆吞吐。一个具体判断：当任务的终态奖励已经足够稠密（例如单轮就能稳定拿到正确且接近 SOL 的 kernel），引入多轮结构化奖励只增加成本不增加信息；它真正划算的场景，是那些“首轮几乎必然失败、需要三到五轮修错才能进入性能调优区间”的算子。
