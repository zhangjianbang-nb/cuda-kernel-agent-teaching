一 · 一次“翻车”的评测：当奖励比噪声还小

设想一个已经跑通的 kernel 生成流水线：策略网络针对一组 KernelBench 风格的算子生成 Triton 或 CUDA C++ 候选，评测器在固定 GPU 上跑 warmup 后计时，把 T_ref / T_cand 作为加速比直接写进奖励。某次迭代里，同一份候选代码在两次评测中分别得到 1.06× 与 0.94×，策略据此判定“这一版更好”并沿该方向更新；下一轮又因为同样的波动被反向更新。表面上看是策略在相近 kernel 之间来回震荡，实质是奖励信号的信噪比不足：单次计时的方差与真实改进幅度处于同一量级，RL 无法区分“策略变好了”和“机器今天更吵了”。

这类翻车的代价不是一次错误的梯度，而是整条流水线的可信度崩塌。工程上可观测到的现象是：奖励曲线在若干候选之间高频抖动、KL 与熵指标异常、keep-revert 搜索反复回滚同一批候选、最终产出的 kernel 在离线复测中并不比基线快。更隐蔽的代价是 token 与 GPU 时间的浪费——每一轮多候选评测都要真实执行，抖动导致的无效迭代直接折算成吞吐损失。抗噪鲁棒奖励塑形要解决的正是这个具体问题：把“测量得到的加速比”改造成“对测量噪声不敏感的奖励”，让策略只在有统计证据时才获得正反馈。

二 · 噪声从哪里来：三类不可忽略的扰动源

GPU 时延测量的扰动至少有三类，且它们的量级往往被低估。第一类是频率抖动：功耗与温度墙触发的动态调频使同一 kernel 的 SM 时钟在运行期间漂移，指令吞吐随之变化。第二类是噪声邻居：共享同一物理 GPU 的其他进程（其他评测任务、驱动后台、MIG 切分下的邻租户）争抢 L2 与内存带宽，使带宽敏感型 kernel 的时延出现系统性偏移。第三类是缓存状态：L2 是否被前一个候选“预热”、输入张量是否驻留、warmup 是否充分，都会改变首次迭代与稳态迭代的差异。这三类扰动都不服从简单的独立同分布假设，单次采样无法把它们平均掉。

把这三类扰动合并成一个可操作的模型：观测时延 T_i = T* + ε_i，其中 T* 是“干净”时延，ε_i 是零均值但重尾的扰动。若用单次观测构造加速比 T_ref / T_cand，则相对误差近似为 (ε_ref - ε_cand) / T*。当真实改进只有几个百分点而扰动幅度与之相当，奖励的符号就由噪声决定。这不是调参能解决的问题，必须在奖励构造层面引入稳健统计。

$$\tilde{T}=\text{median}(T_1,\dots,T_k),\quad \text{LB}=\tilde{T}-z\cdot\frac{\text{MAD}}{\sqrt{k}},\quad r=\mathbb{1}[\text{correct}]\cdot\max\left(0,\frac{T_{\text{ref}}}{\text{LB}}-1\right)$$

上式给出本方法的核心结构：用中位数 T̃ 抵抗重尾异常值，用中位数绝对偏差 MAD 估计离散度，再以 z·MAD/√k 构造置信下界 LB。奖励只取 LB 相对参考时延的加速，且被 max(0, ·) 截断为单边——低于门槛的候选得到零而非负值。注意 √k 项：重复测量次数直接决定下界的收紧速度，这是精度与吞吐之间的显式旋钮。

三 · 机制拆解：稳健统计量 + 置信下界门槛

第一步是采样。每个候选 kernel 在 warmup 之后重复运行 k 次，记录完整时延分布而非单一均值。warmup 的作用是排除首次加载、JIT 编译、缓存冷启动带来的系统性偏高；重复运行则给后续稳健统计提供样本。工程上 k 的取值受每轮 GPU 时间预算约束：k 翻倍意味着评测吞吐减半，因此 k 通常取小个位数到十余次，靠 MAD 与下界公式在小样本下仍保持稳健。

第二步是估计。中位数对重尾扰动不敏感——即使个别迭代被邻居进程拖慢数倍，中位数仍锚定在分布中心；MAD 则给出不依赖方差假设的离散度度量，避免标准差被异常值放大。二者组合得到 T̃ 与 LB，LB 的含义是“以给定置信水平，真实时延不高于此值”，因此 T_ref / LB 是保守的加速比估计：它系统性地低估真实加速，从而过滤掉噪声驱动的虚假提升。

第三步是奖励整形。只有 LB 超过阈值（例如相对参考有明确加速）才给正奖励，否则给零或惩罚。这里的阈值本身是一个工程判断：阈值过高会漏掉小幅但真实的改进，阈值过低则重新引入噪声敏感性。配合 reward normalization 与 clipping，把奖励幅度压到稳定区间，防止个别高方差样本主导梯度。第四步是环境校准：锁频、隔离评测进程、固定缓存预热流程，并持续监控奖励方差是否收敛——方差未收敛说明测量环境本身在漂移，此时任何奖励整形都只是掩盖问题。

用伪代码表达评测循环的关键片段：对候选 c，采样 {T_i}，计算 T̃、MAD、LB；若 LB < T_ref / (1+τ) 则 r = 0，否则 r = T_ref / LB - 1；最后对 r 做归一化与截断后送入 RL。整条链路里没有任何一步依赖“平均加速比”这一脆弱量。

四 · 代价：吞吐、漏检与收敛速度的三重权衡

稳健奖励不是免费的。最直接的代价是 GPU 时间：k 次重复测量使每轮评测的 GPU 占用成倍增加，训练吞吐相应下降。在候选数量大、单候选 kernel 时延短的场景下，评测开销可能超过策略前向本身，成为流水线瓶颈。缓解手段是把 k 与候选的重要性挂钩——对进入决赛圈的少数候选做高 k 精测，对初筛候选做低 k 粗测，但这要求评测调度器具备分级能力。

第二个代价是漏检：过于保守的下界会漏掉小幅但真实的提升。当真实加速只有百分之几而 MAD 较大时，LB 可能仍低于门槛，策略得不到任何正反馈，收敛速度变慢。这是偏差-方差权衡在奖励层面的体现：下界越保守，假阳性越少，假阴性越多。工程上需要根据任务对“错过改进”和“奖励噪声”的相对容忍度来选 z 与阈值，而不是套用固定常数。

第三个代价是正确性维度的耦合。奖励公式里的 𝟙[correct] 意味着正确性判定必须先于奖励计算，且判定本身不能有噪声。若正确性 oracle 依赖浮点比较而容差设置不当，一个数值上等价但实现不同的候选可能被判错，稳健奖励再精细也无意义。因此本方法假设正确性判定是确定性的、可复现的——这一假设的边界正是下一节要划清的内容。

五 · 适用边界：它解决什么，不解决什么

本方法解决的问题可以精确界定：在测量噪声与真实改进同量级时，把奖励从“单次观测的加速比”改造为“有统计证据的保守加速估计”，从而抑制策略在相近 kernel 间的震荡，使 RL 更倾向真实提升。它适用于候选之间性能差异小、评测环境存在频率抖动与邻居干扰、且正确性判定已经可靠的场景——典型如 KernelBench 系基准上的多轮 RL 迭代。

它不解决的问题同样需要明确。第一，它不修正系统性偏差：若评测环境整体偏慢（例如未锁频、邻居长期占用带宽），中位数只会稳健地估计这个偏慢的分布，不会还原干净时延；这需要环境校准而非统计整形。第二，它不替代正确性 oracle：奖励中的正确性指示符依赖外部判定，稳健统计对错误判定无能为力。第三，它不解决奖励黑客问题：若策略找到在测量协议下“看起来快”但实际无益的实现（例如利用缓存预热差异），置信下界只能降低其被奖励的概率，不能从合约层面禁止——那属于防作弊合约校验的职责。第四，它不适用于真实改进幅度远大于噪声的场景：此时单次测量已足够，重复测量纯属浪费吞吐。

一个具体例子可以说明边界的实操含义：某候选在 k=7 次测量中位数为 1.03× 参考，但 MAD 较大导致 LB 仅 0.98×，奖励为零。若离线复测确认该候选确实稳定快 3%，则说明 k 太小或环境噪声太大，应提高 k 或先做环境隔离，而不是放宽阈值——放宽阈值会把同一批噪声样本重新变成正奖励。反之，若某候选 LB 为 1.10× 但离线复测只有 1.01×，则应检查是否存在缓存状态不对称导致的系统性偏差，这已超出奖励整形的能力范围。

六 · 工程判断：先校准环境，再整形奖励

把本方法落地时，顺序比参数更重要。先做环境校准——锁频、隔离评测进程、固定 warmup 与缓存预热流程——再谈稳健统计。原因是：稳健统计量只能压缩随机扰动的影响，无法消除系统性偏移；在未校准的环境里提高 k 只会更精确地估计一个错误的分布。校准之后，用奖励方差是否随训练收敛作为健康指标：方差持续不降说明噪声源未被控制，此时应回退到环境排查而非继续调 z 与阈值。

参数选择上，k 由每轮 GPU 预算反推，z 由对假阴性的容忍度决定，阈值 τ 应与任务中有意义的改进幅度对齐——若业务只关心 5% 以上的加速，阈值就设在 5% 附近，让小幅改进自然落入零奖励区，避免策略为无意义的边际提升消耗迭代。最后，稳健奖励必须与正确性判定、合约校验串联成一条完整的可信链路：任何一环的噪声或漏洞都会让上游的统计努力失效。这条链路的下一环如何构造，属于本模块后续部分的范围。

什么时候这套奖励会反噬：失效条件与系统代价

这套奖励塑形要解决的，是一个很具体的故障模式：策略在若干性能几乎相同的 kernel 变体之间来回跳，不是因为它发现了更好的实现，而是因为测量本身在抖。典型翻车场景是评测端的“假晋升”：某轮采样出的候选 kernel 恰好赶在 GPU 频率爬升、噪声邻居退出或 L2 缓存被前一个候选预热的状态下运行，单次计时得到明显更低的时延，原始加速比被算成一次真实提升，策略于是把权重推向这个变体；下一轮复测时频率回落、缓存冷启，同一份代码的时延回到基线，奖励骤降。策略在“好—坏—好—坏”的奖励序列上反复更新，梯度方向被测量噪声而非代码质量主导，训练曲线呈锯齿状，最终收敛到一个既非最快也非最稳的中间态。这里的关键判断是：噪声不是随机均匀的，而是与执行顺序、频率状态、缓存驻留强相关的系统性偏差，因此不能靠“多训几轮自然平均掉”来解决，必须在奖励函数内部就把它压住。

边界由此划得很清楚。它不解决正确性判定问题——奖励里的 𝟙[correct] 只是一个门控开关，正确性 oracle 本身的漏判、误判（例如容差过松放过数值错误、容差过紧误杀合法重排）会直接以乘零的方式污染奖励，而稳健统计对此无能为力；它也不解决“真实但微小”的提升识别问题，恰恰相反，置信下界越保守，这类提升越容易被判为零奖励。它更不解决策略探索不足、奖励归一化与裁剪的超参失配、以及 reward hacking（例如候选 kernel 通过跳过必要同步或减少实际工作量来压低时延，却仍通过宽松的正确性检查）——这些属于奖励设计与验证环节的问题，不属于测量稳健性范畴。适用前提可以归纳为三条：同一候选可被重复执行且结果确定、测量环境的系统性偏差在 k 次重复内可被统计量吸收、以及单轮 GPU 时间预算允许 k 倍放大。任一条不成立，这套方法就退化为昂贵的安慰剂。

机制上，稳健统计量承担的是“把分布的中心从受污染的单点估计里拉出来”的职责：

$$\tilde{T}=\text{median}(T_1,\dots,T_k),\quad \text{LB}=\tilde{T}-z\cdot\frac{\text{MAD}}{\sqrt{k}},\quad r=\mathbb{1}[\text{correct}]\cdot\max\left(0,\frac{T_{\text{ref}}}{\text{LB}}-1\right)$$

中位数对异常值的崩溃点为 50%，MAD 取代标准差避免方差被离群样本放大，除以 √k 则把“重复次数”换算成置信区间的收缩率——这意味着 k 从 3 增到 12 只能把区间宽度压到一半，收益是次线性的。真正决定行为的是 z：z 取大，漏检真实小提升；z 取小，噪声重新渗入奖励。工程上应把 z 与“可接受的最小真实加速”绑定，而不是当成调参旋钮随手拧。

失效条件表现代价落点
k 过小、warmup 不足中位数仍被冷启/频率爬升污染奖励方差高，策略震荡
z 过大小幅真实提升被判零奖励收敛变慢，样本效率下降
环境未锁频/未隔离MAD 估计本身漂移，LB 不可比跨轮奖励不可加，归一化失效
正确性 oracle 宽松低工作量 kernel 获正奖励reward hacking，端到端收益为负

系统代价必须提前计入预算：每轮 k 次重复（含 warmup）把单候选的 GPU 占用时间成倍放大，在候选吞吐受限的 RL 循环里直接表现为训练吞吐下降与 wall-clock 拉长；k 次计时还意味着 k 份显存驻留与更长的编译—启动链路，若候选 kernel 编译时间本就占大头，重复测量的边际成本会被进一步放大。更隐蔽的代价是“保守性税”：置信下界门槛使一部分真实但幅度接近噪声底的小优化拿不到任何梯度信号，策略倾向于只在能拉开明显差距的方向上探索，收敛速度变慢，且容易在平台期停滞。校准动作（锁频、隔离、定期复测基线 T_ref）本身也要占工程预算，并且一旦环境漂移而校准未跟上，历史奖励与当前奖励就失去可比性，reward normalization 的滑动统计会失真。判断这套方法是否值得上，看的不是“它让曲线更好看”，而是“测量噪声导致的假晋升次数是否已经高到污染策略更新”——若假晋升罕见，直接付 k 倍 GPU 时间去换一个更稳的奖励，性价比并不成立。
