一 · 负载选择：先判瓶颈类型，再决定要不要进 SOL 评分

SOL 归一评分不是对所有 kernel 都成立的度量。它的前提是：该 kernel 的 FLOP 数与 DRAM 字节数能被稳定统计，且其理论下界 T_SOL 由 roofline 拐点 I*=P_peak/B_peak 唯一决定。因此负载筛选的第一步不是看 kernel 多热门，而是看它落在 roofline 的哪一段。若算术强度 I 远低于 I*，T_SOL 完全由 Bytes/B_peak 决定，此时评分实际衡量的是“访存效率”，任何减少冗余读写、提升合并访问的改动都会直接抬分；若 I 远高于 I*，T_SOL 由 FLOP/P_peak 决定，评分衡量的是“计算吞吐利用率”，此时指令级并行、寄存器压力、warp 调度才是主战场。两类负载的优化动作完全不同，混在同一张 SOL 排行榜里会让 agent 学到互相冲突的策略。

具体机制上，选负载时先做一次静态或 profiler 统计：用 NCU 的 dram__bytes 与 sm__inst_executed 折算 FLOP，算出 I，再与目标 GPU 的 I* 比较。以 fp16 稠密 GEMM 为例，其 I 随 M/N/K 增长而上升，小 shape（如 M=N=K=256）的 I 可能落在拐点附近，此时 T_SOL 对 FLOP 与 Bytes 两项都敏感，测量噪声会同时污染两个上限，评分方差大；而大 shape（M=N=K=4096）的 I 显著高于 I*，评分稳定但优化空间集中在 tensor core 利用率上。工程判断是：优先选 I 明显偏离 I* 的负载，让评分信号单峰、可归因；拐点附近的负载要么固定 shape 做专项，要么直接排除出通用评分集。

代价方面，负载筛选本身要花编译与 profile 时间：每个候选 kernel 至少跑一次 NCU 采集 dram__bytes 与指令计数，融合 kernel 还要人工拆分字节归属，单次采集在秒级到十秒级。若评分集含数十个负载，筛选阶段的编译加 profile 开销会显著拖慢 agent 的每轮迭代，因此实践中常把筛选结果缓存成“负载—瓶颈类型—I 区间”的静态表，只在硬件或 dtype 变更时重算。

二 · 硬件锚定：Peak_FLOPS 按 dtype 分档，Peak_BW 按实测校正

SOL 公式里的 P_peak 与 B_peak 不是厂商标称值的直接抄写。P_peak 必须按 dtype 分档：fp32 走 CUDA core 峰值，tf32 与 fp16 走 tensor core 峰值，三者相差数倍，混用会让 u 出现系统性偏差。更关键的是，厂商标称的 tensor core 峰值通常是稀疏与稠密混合的理论上限，稠密路径实际可达约 70–85%，因此直接用标称值算 T_SOL 会把 u 系统性压低，让一个已经很好的 kernel 看起来“离上限很远”。工程做法是引入经验校正系数：以稠密 microbenchmark（纯 tensor core 循环、无访存）实测可持续 FLOPS，作为 P_peak 的有效值，再代入公式。

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$

B_peak 同理：标称 HBM 带宽是理论引脚速率，实际可持续带宽受刷新、bank 冲突、ECC 影响，通常低于标称。用标称 B_peak 会让 memory-bound 负载的 u 虚低。校正方式是跑一个纯流式拷贝 microbenchmark（大数组 read+write），取实测 GB/s 作为 B_peak。注意校正系数与 dtype、shape 无关，只与硬件和访问模式有关，因此可以一次测好、全局复用。

硬件锚定的代价是：校正 microbenchmark 本身要占评测机时，且不同 GPU 型号需分别测；若评分集跨多型号，锚定表会膨胀。另一个隐性代价是校正系数漂移——同一型号在不同功耗墙、不同散热条件下可持续 FLOPS 不同，若 agent 的评分跨机器聚合，必须把锚定值与实测环境绑定，否则 u 的跨机可比性被破坏，而这正是 SOL 评分相对裸 speedup 的核心优势。

三 · 基线选择：SOL 评分不需要强基线，但需要“同 shape 同 dtype 同语义”的对照

SOL 评分的卖点是与基线无关，但这不意味着基线可以随便选。u=T_SOL/T_gen 里 T_gen 是 agent 生成 kernel 的实测时延，T_SOL 是硬件下界，两者都不含基线。基线的作用退化为两点：其一，提供正确性对照（同语义输出比对），其二，提供“人类可达水平”的参考线，用于判断 agent 产出是否值得进入评分。若基线选了一个语义不等价的实现（如把 fp32 累加换成 fp16 累加），正确性门会先把它拦掉；若基线选了一个未优化的朴素实现，参考线过低，agent 只要写出能跑的 kernel 就能拿高分，评分失去区分度。

具体做法是：基线固定为“同 shape、同 dtype、同语义、由成熟库或人工调优实现”的版本，其 u 作为参考锚点而非评分分母。例如一个 fp16 GEMM 负载，基线取调优后的库实现，其 u 落在校正后的 0.7–0.85 区间；agent 产出若 u 低于基线，说明还有优化空间，反馈信号应指向瓶颈类型（compute-bound 则查 tensor core 利用率，memory-bound 则查合并访问与 L2 命中）。基线不参与 u 的计算，但参与“是否值得继续优化”的判定。

代价在于：为每个负载维护一个调优基线需要额外工程投入，且基线本身随库版本、硬件代际变化，需定期重测。若基线过期，参考线失真，agent 会在已经接近上限的负载上反复空转，浪费编译与 profile 机时。工程判断是：基线只做参考线，不做分母，且参考线按瓶颈类型分档维护，避免用单一阈值卡所有负载。

四 · 输入分布：shape 抽样要覆盖拐点两侧，dtype 与布局必须与评分口径一致

输入分布直接决定 I 的分布，进而决定 u 的分布。若评分集只抽大 shape，所有负载都落在 compute-bound 段，agent 学不到访存优化；若只抽小 shape，所有负载都落在 memory-bound 段，agent 学不到计算优化。正确做法是按 I 分层抽样：显式构造一批 I 明显低于 I*、一批明显高于 I*、少量落在拐点附近的 shape，按层加权聚合 u。这样聚合分数既反映两类瓶颈的优化能力，又不会让拐点附近的噪声主导总分。

dtype 与布局必须与评分口径严格一致。fp16 与 bf16 的 P_peak 不同，NHWC 与 NCHW 的 Bytes 统计不同，转置与非转置的合并访问效率不同。若输入分布里混入不同布局，Bytes 统计会失真，u 不可比。具体例子：一个卷积负载，若输入按 NCHW 抽样但 kernel 按 NHWC 优化，实际 DRAM 字节数因跨步访问而膨胀，T_SOL 被低估，u 虚高，agent 会误以为访存已优化到位。因此抽样时必须固定布局，并在负载元数据里标注，评分时按布局分组聚合。

代价是：分层抽样使评分集规模膨胀，每层至少若干 shape 才能稳定估计层内均值，编译与 profile 次数随之上升。另一个代价是 token 开销——若 agent 以自然语言描述 shape 分布，长列表会挤占上下文；实践中常把分布压缩成“层—shape 区间—权重”的紧凑表，只传区间与权重，不传逐个 shape。

五 · 指标聚合：u 的绝对值要校正，u>1 必须复核剔除

单负载 u 算完后，聚合方式决定总分含义。算术平均会让大 shape（u 稳定但优化空间小）主导总分，几何平均则对小 u 更敏感、更能反映“短板”。工程上常按瓶颈类型分组后组内几何平均、组间按权重线性组合，使 compute-bound 与 memory-bound 两类能力都有独立读数。无论哪种聚合，u 的绝对值都必须经过校正：用第一节的 P_peak 有效值与 B_peak 实测值代入，否则 u 的绝对水平不可解释。

u>1 是必须处理的异常。它只有两个来源：测量误差（计时器分辨率、事件重叠）或缓存复用（Bytes 统计未计入 L2 命中导致的 DRAM 字节低估）。前者可通过多次采样取中位数、剔除离群点缓解；后者需要 profiler 的 dram__bytes 而非理论 Bytes 来算 T_SOL，或对融合 kernel 人工拆分字节归属。处理原则是：u>1 的样本不进聚合，单独标记为“不可信”，并回灌给 agent 作为“字节统计口径需修正”的信号，而不是当作高分奖励。若不剔除，agent 会学到“少报 Bytes”这一作弊路径，评分体系失效。

代价是：复核 u>1 需要额外一次 NCU 采集与人工判断，单样本成本在秒级；若异常样本比例高，评分集有效规模缩水，总分方差上升。工程判断是：把 u>1 比例作为评分体系健康度的监控指标，比例持续偏高说明 Bytes 统计口径或计时方法有系统性问题，应先修口径再谈优化。

六 · 负载不对时会发生什么：评分信号反转与策略退化

负载与评分配方错配的后果不是“分数偏低”，而是“信号反转”。典型场景一：把 memory-bound 负载放进 compute-bound 评分组，agent 按计算优化方向（提高 tensor core 占用、增加指令级并行）改动，实际瓶颈在 DRAM，u 不升反降，agent 从反馈里学到“计算优化无效”的错误结论。典型场景二：shape 全落在拐点附近，T_SOL 对 FLOP 与 Bytes 两项都敏感，测量噪声使 u 的方差大于真实优化带来的增益，agent 无法从多轮迭代中分辨有效改动，搜索退化为随机游走。

典型场景三：基线选得过弱，参考线过低，agent 产出朴素 kernel 即达参考线，后续优化轮次全部空转，RL 的可验证奖励失去梯度。典型场景四：dtype 或布局混用，Bytes 统计失真，u 虚高，agent 误判“已接近上限”而停止优化，实际离硬件上限仍远。这四种错配的共同代价是编译与 profile 机时的浪费——每轮迭代都要编译、跑 NCU、算 u，错配让这些机时产出无效梯度；在 token 层面，agent 会把错误结论写进策略 IR，污染后续搜索。

工程判断落在配方校验上：负载进评分集前，先验证其 I 与 I* 的关系稳定、dtype 与布局固定、基线参考线合理、u>1 比例可控；四项任一不满足，该负载只做专项评测，不进通用 SOL 聚合。评分配方的正确性优先于评分集的规模，宁可少几个负载，也不要让错配负载污染 agent 的策略学习信号。

负载配方错配时，SOL 分数会奖励错误的优化方向

SOL 归一评分的可信度几乎完全由负载配方决定，而配方里最容易被忽视的是 shape 与硬件拐点的匹配关系。若评测集里的 shape 全部落在算术强度 I 远高于拐点 I* 的区间，那么所有样本都是 compute-bound，此时 SOL 利用率只反映 tensor core 的占用率，访存优化带来的收益被完全掩盖；反过来，若 shape 全部落在 I ≪ I* 的区间，分数就退化成带宽利用率的度量，agent 会学到“少读一次 DRAM 就是胜利”，却在真正的计算密集算子上毫无建树。更隐蔽的失效是 shape 过小：当 FLOP 与 Bytes 都小到 kernel launch 开销与固定开销可比时，T_gen 被启动延迟主导，T_SOL 却按峰值算力折算，u 会被系统性压低，且压低幅度与 kernel 质量无关。因此配方必须显式覆盖拐点两侧，并给出每个 shape 的 I 与 I* 的比值分布，让评分者能看出分数是在哪条上限上取得的。

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$

基线选择是第二个失效源。SOL 分数本身与基线无关，但“是否值得部署”的判断仍要落在与基线（cuBLAS、cuDNN、厂商 kernel 或手写参考实现）的对比上；若基线选得过弱，u 很高却毫无工程意义，若基线选得过强（例如已高度调优的库 kernel），则 u 的提升空间被压缩，agent 的奖励信号变得稀疏。工程上应把基线固定为同 dtype、同 shape、同硬件下的库实现，并把 u 与相对基线的 speedup 并列报告：前者衡量离硬件上限的距离，后者衡量相对可部署替代品的增益，两者背离时优先相信 u 的瓶颈标注而非 speedup。输入分布同样要固定：dtype（fp32/tf32/fp16 对应不同 P_peak）、布局（行主序/转置/分块）、是否存在广播与掩码、batch 维是否对齐，任何一项变化都会改变 Bytes 统计与缓存复用行为，从而改变 u 的绝对值。

指标计算环节的代价集中在 FLOP/Bytes 的统计上。静态分析对融合 kernel 极易低估 DRAM 字节数——中间结果被寄存器或 shared memory 复用后并不落回 DRAM，但静态模型仍按“读入+写出”累加，导致 Bytes 虚高、T_SOL 偏大、u 虚高；profiler 统计（如 NCU 的 dram__bytes）能给出实测字节，但采样本身引入额外时延与显存开销，且对短 kernel 的测量噪声显著。另一项系统性偏差来自 P_peak：规格书上的峰值是稀疏与稠密混合的理论值，实际可达上限通常只有七成到八成五，因此 u 的绝对值必须按经验系数校正后再跨 GPU 比较，否则同一 kernel 在不同代际硬件上的分数会被峰值定义的差异污染。对 u > 1 的样本必须复核：要么是测量误差，要么是缓存复用让实际 Bytes 远小于模型值，这类样本应剔除而非计入均值。

具体到一个融合的 LayerNorm+GELU：静态模型按“读 x、写 y”计 Bytes，但若中间激活驻留寄存器，实际 DRAM 流量只有一次读一次写，模型值与实测值接近；若 kernel 被拆成两段且中间结果落回 DRAM，静态模型仍按单次读写计，Bytes 被低估一半，u 虚高近一倍，agent 会误以为已接近上限而停止优化。此时正确做法是用 profiler 的 dram 字节替换模型值重算 T_SOL，并把该样本的瓶颈标注从 memory-bound 改为按实测 I 重新判定。配方设计的工程判断是：先按 I 与 I* 的比值把评测集分层，每层至少保留一个可部署基线，再用 profiler 字节校正静态模型，最后对 u 做峰值可达系数的区间报告而非单点值——分数只有带上瓶颈类型与校正区间，才是 agent 能用来决定“优化计算还是优化访存”的信号。
