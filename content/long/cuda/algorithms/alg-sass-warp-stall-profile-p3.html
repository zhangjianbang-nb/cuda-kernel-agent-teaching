一 · StallShare 的分母为什么必须按 PC 聚合，而不是按 warp 平均

给定公式 $$\text{StallShare}_k=\frac{\sum_{pc}\text{cycles}_k(pc)}{\sum_{pc}\sum_{k'}\text{cycles}_{k'}(pc)}$$ 的第一眼直觉是“某类 stall 占总 stall 的比例”，但工程实现里真正决定这个数是否可用的，是求和下标 pc 的位置。ncu 的 smsp__pcsamp 采样输出是 (SMSP, warp, PC, stall reason) 的四元组流，如果先对 warp 求平均再按 stall 类型汇总，得到的是“每个 warp 平均被该类 stall 卡了多少周期”，它会被高占用但短命的 warp 稀释；而按 PC 聚合再求和，得到的是“整个 kernel 在这条指令上总共浪费了多少周期”，这才是 agent 能拿去对齐 SASS 行的量。

推导的关键一步是把采样计数换成周期期望。设采样周期为 T_s，某 PC 上被观测到 stall reason 为 k 的样本数为 n_k(pc)，则 cycles_k(pc) ≈ n_k(pc) · T_s · (active_warps/SMSP)。分母对所有 k' 求和时，T_s 与 warp 缩放因子同时出现在分子分母，因此 StallShare_k 对采样率不敏感——这是它能跨 kernel、跨架构比较的根本原因。代价是：当某个 PC 的样本数低于阈值（工程上常取几十个样本量级），比例的方差会大到不可用，必须做 PC 级置信区间裁剪，否则反馈块会把噪声当成热点。

具体例子：一个 GEMM 的 inner loop 被展开成 8 条 FFMA，若 long scoreboard 的样本集中在第 3 条 FFMA 的 PC 上，按 PC 聚合会得到一条尖锐的峰，agent 据此判断“LDG 的结果在第三次消费时才到位”，动作是提前发起预取或增大 tile 并行度；若按 warp 平均，这个峰会摊平到 8 条指令上，反馈块只能给出“整体访存偏慢”这种无法落地的结论。

二 · RegPressure 的推导：从每线程寄存器到 occupancy 上限

公式 $$\text{RegPressure}=\frac{\text{regs per thread}\times\text{threads per block}}{\text{regs per SM}}$$ 描述的是“一个 block 的寄存器需求占满整个 SM 寄存器文件的比例”。它的推导起点是硬件约束：SM 的寄存器文件按 warp 粒度分配，分配单位是 256 个寄存器（即每 warp 8 个分配槽），因此实际占用是 ceil(regs_per_thread × 32 / 256) × 256 每 warp。把 block 内 warp 数乘上去，再除以 SM 总寄存器数，就得到 RegPressure。关键一步在于取整发生在 warp 级而不是线程级——这意味着 regs_per_thread = 33 与 = 40 在分配上等价，都是每 warp 两个 256 槽。agent 若只看源码里的变量数去推寄存器，会系统性低估压力。

由此可导出 occupancy 上限：max_blocks_per_SM = floor(1 / RegPressure)（再与 warp 数上限、shared memory 上限取 min）。当 RegPressure 越过 0.5 时，SM 上最多只能驻留一个 block，warp 级并行度骤降，long scoreboard 与 not selected 的占比会同时上升——前者因为缺少其他 warp 掩盖访存时延，后者因为调度器在少量 warp 间反复挑选。这就是为什么 stall 剖析必须和寄存器统计一起回灌：单看 stall 类型会误判为“访存问题”，实际根因是编译器为了展开循环把寄存器用超了。

代价体现在编译时间与指令质量的双向权衡上。__launch_bounds__ 或 -maxrregcount 压低寄存器数会迫使编译器插入 spill，把值写回 local memory，引入额外的 LDL/STL 指令与 long scoreboard 停顿；反之放开寄存器限制能消除 spill，但 RegPressure 升高直接砍掉 occupancy。工程判断是：当 StallShare(long scoreboard) 高且 RegPressure > 0.5，优先尝试降低每线程寄存器而不是加预取——因为后者在低 occupancy 下根本没有足够 warp 去隐藏时延。

四 · 误差项：PC 采样重放与 SASS 行映射的不确定性

stall 剖析的误差有两个独立来源，必须分开建模。其一是采样误差：smsp__pcsamp 是硬件周期采样，样本数 n 服从近似泊松分布，比例估计的标准差约为 sqrt(p(1-p)/n)。当 StallShare 接近 0 或 1 时方差小，接近 0.5 时方差最大。这决定了反馈块里比例的呈现方式：不应给出小数点后多位的精确值，而应给出量级与排序，避免 agent 对噪声做过度反应。

其二是映射误差：cuobjdump -sass 给出的指令序列与源码行号的对应在模板实例化与内联展开后极不可靠，编译器可能把多个源码语句合并到一个基本块，也可能把一个循环体拆到多个段。工程上可行的做法是不依赖行号，而依赖 PC 偏移与基本块边界：把 stall 热点映射到“包含该 PC 的基本块起始偏移 + 块内序号”，再在反馈块里附上该基本块的 SASS 原文。这样 agent 拿到的是确定性的指令上下文，而不是可能指错的源码行。代价是反馈块里没有源码语义，agent 需要自己从 SASS 反推意图，对模型的指令理解能力要求更高。

还有一个跨代误差：不同架构的 SASS 指令集与 stall reason 分类不同，同一份反馈块不能跨代复用。若把 A 架构上学到的“long scoreboard 高就加预取”直接搬到 B 架构，可能因为 B 架构的访存流水更深而完全无效。工程判断是：反馈块必须携带架构标识，且动作建议只在同代内做 keep-revert 式的搜索验证，跨代时降级为“现象描述”而非“动作指令”。

五 · 奖励公式的可实现形式：把 stall 剖析折进标量

若把 stall 剖析作为 RL 或搜索的奖励项，需要一个把多维观测压成标量的公式。一个可实现的构造是：R = R_correct · (1 + α · ΔSpeedup) − β · Penalty_stall，其中 Penalty_stall 取 StallShare 的熵或最大项占比。用熵 H = −Σ_k p_k log p_k 的好处是它对“stall 集中在单一原因”敏感：当 kernel 被单一瓶颈卡死时熵低，说明优化方向明确，应给予正向信号；当 stall 均匀分布在多种原因上时熵高，说明瓶颈弥散，此时任何单点优化收益都有限，应压低奖励避免 agent 在无效方向上反复试探。

推导的关键一步是把 ΔSpeedup 与 StallShare 的变化解耦。ΔSpeedup 由端到端时延测得，受 launch 开销、内存分配等 kernel 外因素污染；StallShare 的变化只反映 kernel 内部执行效率。两者做乘积而非加和，是因为只有当正确性通过（R_correct = 1）且内部效率真实改善时，端到端收益才可信。代价是奖励信号的方差：StallShare 的采样噪声会通过熵项放大到奖励上，导致同一份 kernel 多次评测得到不同奖励，破坏 keep-revert 搜索的可比性。缓解手段是对 StallShare 做多次采样取中位数，或在奖励里加入对采样样本数的置信折扣。

具体例子：一次循环展开变体的 ΔSpeedup 为正但 StallShare(long scoreboard) 从主导变为与 MIO throttle 并列，熵升高，奖励被压低，搜索不会把这个变体当作稳定改进保留——这正好对应“展开消除了部分访存停顿但引入了 shared memory 压力”的真实情形，避免了仅看时延就误判为全面胜利。

六 · 伪代码落地：从采样流到反馈块的完整管线

把上述公式串成一条可实现的管线，核心循环如下：读入 cuobjdump -sass 的输出，解析出指令序列、每指令 PC 偏移与寄存器数；读入 ncu 的 smsp__pcsamp 原始采样，按 (PC, stall reason) 做计数聚合，得到 cycles_k(pc) 表；对每个 PC 计算 StallShare_k(pc) 并按全局 StallShare_k 排序取热点；对每个热点定位所属基本块，抽取指令窗口，计算 LDG 到消费指令的距离 d 与窗口内指令混合；用第三节的规则链产出 (stall 类型, 判定, 建议动作) 三元组；最后按 token 预算裁剪热点数量，拼成反馈块注入下一轮 prompt。

管线里有两个必须显式处理的工程点。第一，RegPressure 的计算要在反汇编阶段完成，因为寄存器数只在 cubin 里可靠，源码里的变量数不可信；把 RegPressure 与 StallShare 一起写进反馈块头部，agent 才能在读热点之前就知道 occupancy 是否已被寄存器锁死。第二，反馈块要携带“本次剖析的采样样本数”，让下游的奖励计算知道该比例的置信度，避免把低样本热点当成确定结论。

代价集中在剖析时延上：ncu 的 PC 采样需要重放 kernel，单 kernel 剖析成本远高于一次普通计时运行，若搜索每轮都做完整剖析，端到端吞吐会被剖析本身拖垮。工程判断是分层剖析：搜索前期只做计时与正确性筛选，进入 keep-revert 的精细阶段才对候选做 SASS+stall 剖析，且只剖析排名靠前的热点 PC 而非全量。这个分层策略让 stall 剖析的 token 与时延代价落在真正需要它的决策点上，而不是平摊到每一次候选生成。

采样口径的边界：PC 聚合 stall 在什么条件下失效

把 $$\text{StallShare}_k=\frac{\sum_{pc}\text{cycles}_k(pc)}{\sum_{pc}\sum_{k'}\text{cycles}_{k'}(pc)}$$ 当作反馈信号，前提是分母在采样窗口内稳定且各 PC 的样本量足以支撑比例估计。ncu 的 smsp__pcsamp 是低频采样，热点 PC 的样本数随 kernel 时长线性增长，而冷 PC 往往只有个位数样本——此时 StallShare 的置信区间宽到无法区分 long scoreboard 与 MIO throttle。更隐蔽的失效来自 PC 聚合本身：一条 SASS 指令在循环体内被反复执行，其 stall 周期被累加到同一 PC 上，比例反映的是“该 PC 贡献的等待总量”，不是“该指令单次执行的等待代价”。若热点 PC 恰好是展开循环中的一条 FFMA，占比高可能只说明它执行次数多，而非它本身是瓶颈。工程上必须同时看每 PC 的 stall 周期与执行计数之比，把“总量占比”与“单次代价”分开，否则反馈块会把 agent 引向错误指令。

寄存器压力项 $$\text{RegPressure}=\frac{\text{regs per thread}\times\text{threads per block}}{\text{regs per SM}}$$ 的边界更硬：它只在同一 SM 上以 block 为粒度成立，跨 block 的占用由调度器按 warp 分配，公式给出的是单 block 的静态占位，不是实际 occupancy。当编译器把循环展开成多条 FFMA 并触发寄存器溢出到 local 时，regs per thread 上升会直接压低 RegPressure 允许的并发 block 数，但真正代价是 local memory 的额外 LDG/STG 流量——这部分不会体现在 RegPressure 数值里，只会以 long scoreboard 占比的形式出现在 stall 采样中。因此两个公式必须联读：RegPressure 越过阈值解释“为什么 occupancy 掉了”，long scoreboard 高解释“掉了之后代价落在哪”。单独任一项都不足以支撑动作建议。

反馈块的可实现形态应是一个结构化记录而非自然语言段落，伪代码思路如下：对每个热点 PC，取 (sass_line, stall_type, cycles, exec_count, regs_at_pc)，按 cycles/exec_count 排序取前 N 条，再按 stall_type 聚合出占比；若某类型占比超过其余类型之和且对应 SASS 片段含 local 访存，则建议动作标为“降展开/减寄存器”；若 barrier 类占比主导且片段含 BAR.SYNC，则标为“减少同步粒度”。这里的关键一步是 exec_count 归一化——没有它，展开循环的任意一条指令都会伪装成热点。代价是每次剖析需 ncu 重放 kernel，单 kernel 剖析成本随采样精度上升，且不同架构的 SASS 指令名与 stall 分类不通用，同一反馈块跨代复用会指向不存在的指令。

还有一个系统代价常被忽略：SASS 与源码行号的映射在模板实例化与内联展开后不精确，热点片段可能落在与源码语义无关的地址上，agent 据此修改源码会改错位置。可行的缓解是把反馈块锚定在 SASS 片段本身（指令序列 + 寄存器数 + stall 类型），让 agent 在“指令形态”层面推理而非回跳源码行；代价是 prompt 中携带的 SASS 文本占用 token，且需要 agent 具备读 SASS 的能力。这条路径的边界很清楚：当 kernel 短、展开浅、架构单一时，PC 聚合与 RegPressure 联读足以支撑动作；当模板深度大、跨代部署、或采样预算不足以覆盖冷 PC 时，反馈块应降级为“类型占比 + 建议动作”的粗粒度信号，放弃逐 PC 定位，避免把噪声当成诊断结论。
