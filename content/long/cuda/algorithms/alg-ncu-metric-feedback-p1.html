一 · 一次“时延没降”的评测翻车

设想一个已经跑通的 kernel 优化闭环：agent 拿到一个 Triton 或 CUDA C++ 的初始实现，评测器只回传一个数字——端到端时延。第一轮 agent 尝试把 tile 从 64 调到 128，时延没动；第二轮它加了 shared memory 缓存，时延反而涨了 3%；第三轮它把循环展开、把计算挪到寄存器，时延仍然贴着基线。四轮之后 agent 的搜索轨迹呈现出典型的“盲目抖动”：每一轮都在改代码，但没有任何一轮的改动与真实瓶颈对齐。评测器给出的唯一信号是“没变好”，而 agent 无法从这个信号里推断出“为什么没变好”。

这不是 agent 能力不足，而是反馈通道的信息带宽太窄。端到端时延是一个标量，它把访存受限、计算受限、延迟受限、occupancy 不足、同步开销、指令发射瓶颈全部折叠成一个数。当这个数不动时，agent 面对的是一个欠定问题：有几十种可能的改动方向，每一种都能在别的 kernel 上奏效，但没有一种能被当前信号证实或证伪。更糟的是，时延对某些改动天然不敏感——例如在一个已经 DRAM 饱和的 kernel 上继续加计算并行度，SM 利用率上升但 DRAM 吞吐不变，端到端时延几乎不动，agent 却会误以为“加计算没用”，从而放弃一个本来正确的方向。

线上事故的版本更尖锐：某个推理服务把 attention 的 softmax kernel 换成了 agent 生成的融合版本，离线 benchmark 上时延持平，上线后 P99 时延恶化。事后 profile 发现新 kernel 的 achieved occupancy 从 62% 掉到 31%，原因是寄存器压力导致每个 SM 只能驻留更少的 warp，长尾请求在低 occupancy 下被放大。离线评测只看均值时延，掩盖了 occupancy 的退化；而 agent 在生成阶段从未见过 occupancy 这个量，自然也不会把它当作约束。这个案例说明：缺少硬件计数器回灌的评测，不仅让优化变慢，还会让“通过评测”的 kernel 在生产负载下失效。

二 · 这个方法解决的具体问题：把标量时延展开成结构化瓶颈

NCU 指标回灌要解决的核心问题是：让 agent 在每一轮都能知道当前 kernel 卡在哪个硬件维度上，而不是只知道“快或慢”。具体做法是用 Nsight Compute 采集一组关键指标，按 roofline 模型把 kernel 归类到 memory-bound、compute-bound 或 latency-bound，再把分类结果与 stall 原因压缩成一段可读的反馈文本，拼进下一轮 prompt。这样 agent 看到的不是“时延 1.83ms”，而是“DRAM 吞吐已达峰值带宽的 87%，SM 利用率 41%，achieved occupancy 55%，Top stall 为 long scoreboard——这是 memory-bound，应减少访存或提高 L2 复用，而不是增加计算”。

分类规则本身是一个分段函数，把连续指标离散成三个桶：

$$\text{Bound}=\begin{cases}\text{memory}, & \frac{\text{DRAM}_{\text{throughput}}}{B_{\text{peak}}}>0.8\\ \text{compute}, & \frac{\text{SM}_{\text{util}}}{1}>0.8\\ \text{latency}, & \text{otherwise}\end{cases},\quad \text{Feedback}=f(\text{Bound},\text{Top-3 stalls})$$

这个函数的工程意义在于它强制 agent 面对一个排他性的判断：一个 kernel 在同一时刻主要受一种资源约束。若 DRAM 吞吐超过峰值带宽的 80%，继续优化计算指令是浪费预算；若 SM 利用率超过 80%，继续减少访存也不会带来收益；两者都不满足时，问题通常落在延迟隐藏上——occupancy 不足、依赖链过长、同步过密。反馈函数 f 把 Bound 与 Top-3 stall 原因（如 long scoreboard、barrier、MIO throttle）组合成一段不超过 200 token 的文本，既保留数值又给出动作建议。

以一个具体的 reduction kernel 为例：agent 第一版用 256 线程、每线程处理 4 个元素，时延 0.94ms。NCU 采集显示 DRAM 吞吐为峰值带宽的 91%，SM 利用率 38%，L2 命中率 22%，Top stall 是 long scoreboard。回灌文本告诉 agent 这是 memory-bound，且 L2 命中率低说明访存模式缺乏复用。agent 下一轮把每个线程处理的元素数提高到 8 并改用向量化加载，DRAM 吞吐占比降到 74%，时延降到 0.61ms。如果没有回灌，agent 很可能去调 block size 或加 unroll，这些动作在 memory-bound 下对 DRAM 吞吐没有影响，只会消耗搜索预算。

三 · 它不解决什么：边界必须写清楚

第一，NCU 回灌不解决正确性问题。它描述的是“这个 kernel 在硬件上如何运行”，不是“这个 kernel 算得对不对”。一个数值错误的 kernel 同样可以被分类为 compute-bound 并给出漂亮的 stall 分布。正确性必须由独立的 oracle 承担——fp64 参考实现、变异测试、合约校验各有其位，回灌不能替代它们，也不能因为“profile 看起来很健康”就跳过正确性门。

第二，它不解决跨 shape 的泛化问题。一次 profile 只对应一组具体的 grid/block 配置和输入尺寸。agent 可能针对被 profile 的那个 shape 把 kernel 调到 memory-bound 的最优点，换一个 batch size 或序列长度后分类完全改变。回灌文本必须带上被采集的 shape 与 launch 配置，否则 agent 会把一次局部观测当成全局结论。这也是为什么隐藏 shape 抽样必须与回灌并行存在：回灌告诉 agent“在这个点上瓶颈是什么”，抽样告诉评测者“这个点在分布里代表什么”。

第三，它不解决测量本身的偏差。NCU 采集会串行化并重放 kernel，单次 profile 的耗时是裸跑的 10–100 倍。这个代价决定了它不能每轮全量跑：一个 20 轮的搜索若每轮都做 full-set profile，profile 开销会主导整个训练/搜索时延，把 RL 的吞吐压到不可用。工程上的折中是分层采集——只在关键轮次或时延出现异常时跑 full set，其余轮次跑一个 10–20 个指标的自定义 metric 集。但即便如此，回灌得到的时延数字也不是生产时延，agent 不能把 profile 里的 duration 当作优化目标本身。

第四，它不解决指标解读的可靠性。分类规则是经验性的阈值判断，错误分类会直接把 agent 引向错误方向。典型误判是把高 L2 命中率当成 compute-bound 的证据：L2 命中率高只说明访存被缓存吸收，不代表 SM 已经饱和；若此时 DRAM 吞吐占比其实不高、SM 利用率也不高，真实瓶颈可能是 latency-bound，而 agent 会去加计算。另一个误判来自 occupancy：achieved occupancy 低既可能是寄存器压力，也可能是 grid 太小、尾效应，回灌文本若只给数值不给上下文，agent 容易把“提高 occupancy”当成万能动作。

四 · 为什么必须回灌而不是让 agent 自己猜

有人会问：agent 既然能读代码，能不能自己推断瓶颈？在某些简单 kernel 上可以，但在融合算子、非常规访存模式、Tensor Core 路径上，静态代码阅读与真实硬件行为之间的差距很大。一个看似“计算密集”的 GEMM 可能因为 shared memory bank conflict 或 swizzle 不当而实际卡在 MIO throttle 上；一个看似“访存密集”的 layernorm 可能因为 occupancy 足够高而已经接近 DRAM 峰值。agent 的代码理解是符号性的，硬件计数器是物理性的，两者之间的映射需要实测。

更重要的是，回灌把“时延没降”这个负信号转化成了可操作的正信号。没有回灌时，agent 的搜索是“改代码—看时延—再改”的盲循环，每一轮的失败不携带方向信息。有回灌时，失败携带的是“DRAM 已饱和，应减少访存而非加计算”这样的约束，agent 的下一轮动作空间被收窄。这个转化对 RL 尤其关键：端到端时延的奖励是稀疏的，几十轮里可能只有一两次改进；而 Bound 分类与 stall 分布可以作为中间信号做 reward shaping，让策略在没拿到最终收益时也能学到“往哪个方向走”。

代价是反馈块本身的 token 开销与噪声。一个 200 token 的反馈块拼进 prompt，意味着每轮上下文多出几百 token 的预算；若反馈块里塞进过多指标，agent 的注意力会被稀释，反而忽略关键结论。工程上的做法是固定模板：先给 Bound 结论，再给三个支撑数值，最后给一条动作建议，其余指标留在结构化日志里供离线分析。这样既控制了 token，也保证了 agent 每轮看到的是同一套语义框架，便于跨轮比较。

五 · 适用边界的工程判断

把适用边界写成一张判断表，比写一段原则更有用：

场景回灌是否适用理由与替代手段
单 kernel 时延停滞，需定位瓶颈适用Bound 分类直接收窄动作空间；配合 Top-3 stall 定位具体原因
正确性存疑不适用回灌不判对错；须由 fp64 oracle、变异测试、合约校验承担
跨 shape 泛化仅作局部证据一次 profile 只对应一个 launch 配置；须与隐藏 shape 抽样并用
高频搜索轮次分层使用full-set profile 耗时 10–100×，只在关键轮次跑；其余用 10–20 指标子集
生产端到端收益评估不适用profile 时延非生产时延；端到端收益须由服务级压测承担

这张表的核心判断是：回灌是一个诊断工具，不是评测工具，也不是正确性工具。它的价值在于把“时延没降”这个标量失败展开成“卡在哪个硬件维度”的结构化约束，从而让 agent 的下一轮改动有方向。它的成本在于 profile 的重放开销与分类规则的误判风险，因此必须分层采集、带上下文、与正确性门和 shape 抽样并行。一个工程上可接受的配置是：每 N 轮做一次 full-set profile，其余轮次只采集 DRAM 吞吐占比、SM 利用率、achieved occupancy、L2 命中率与 Top-3 stall 这五个量，足以支撑 Bound 分类与动作建议，同时把 profile 开销控制在搜索总时延的可接受比例内。

最后落到一个具体机制上：反馈块的模板应当把 Bound 结论放在最前，因为 agent 的注意力对开头最敏感；数值放在结论之后作为证据，动作建议放在最后作为可执行项。若某一轮的分类落在阈值边缘（例如 DRAM 吞吐占比 79%、SM 利用率 78%），模板应显式标注“边界情况”，提示 agent 同时考虑两种瓶颈，而不是强行归入一类。这个细节决定了回灌在真实搜索中的可信度——错误分类比没有分类更危险，因为它会让 agent 带着错误的确定性去改代码。

当端到端时延成为唯一的信号：NCU 回灌要救的是哪一类翻车

先说一个评测翻车的典型形态。agent 生成了一版 kernel，端到端时延比上一轮慢了，或者干脆没动。它手上唯一的观测就是这一个标量，于是它开始“猜”：把 tile 调大一点、把 shared memory 用多一点、把循环展开、加一个 double buffer。这些动作在语义上互不相同，但在时延这个单点上完全不可分辨——它们都表现为“没变好”或“变差了一点”。更糟的是，有些改动会让时延略微下降而正确性边缘化，agent 于是沿着错误方向继续走，把预算烧在一条注定到不了 roofline 的路径上。这类翻车不是 agent 的推理能力问题，而是观测通道的问题：端到端时延是一个把 memory-bound、compute-bound、latency-bound 三种完全不同的物理状态压成一个数的投影，投影不可逆，agent 拿不到逆变换所需的自由度。

NCU 指标回灌要解决的正是这个“投影不可逆”。它不解决 kernel 的正确性——正确性由 oracle 与形式验证那条线负责，回灌块里出现的数值不能替代对拍；它也不解决搜索空间本身的大小，agent 仍然要在 tile、swizzle、同步粒度之间做选择，回灌只是把选择的依据从盲猜换成有物理含义的分档。它的适用边界很硬：只有当 kernel 已经能跑通、且性能确实受硬件资源约束时，指标才有解读价值；一个被寄存器溢出打穿 occupancy 的 kernel、一个访存完全非合并的 kernel，其 stall 结构会被更底层的问题主导，此时按 roofline 分类得到的标签会把 agent 引向错误的优化层级。换句话说，回灌是“在正确的实现之上做资源调度”的工具，不是“把错误实现修对”的工具。

$$\text{Bound}=\begin{cases}\text{memory}, & \frac{\text{DRAM}_{\text{throughput}}}{B_{\text{peak}}}>0.8\\ \text{compute}, & \frac{\text{SM}_{\text{util}}}{1}>0.8\\ \text{latency}, & \text{otherwise}\end{cases},\quad \text{Feedback}=f(\text{Bound},\text{Top-3 stalls})$$

这个分档公式本身就是失效条件的来源。两个阈值是经验规则，不是物理定律：DRAM 吞吐占峰值带宽的比例超过 0.8 判 memory-bound，SM 利用率超过 0.8 判 compute-bound，其余归为 latency-bound。问题在于指标之间的耦合会被规则误读。一个 L2 命中率很高的 kernel，DRAM 吞吐可能并不高，SM 利用率却因为等待 L2 返回而虚高，规则可能把它推进 compute-bound 档，agent 于是去加计算密度，而真实瓶颈是 L2 带宽或 scoreboard 停顿。反过来，一个 occupancy 很低但每线程 ILP 很高的 kernel，SM 利用率看起来不低，实际却是 latency-bound，正确动作是提高并行度而不是削减指令。所以回灌块里必须同时带上原始数值与派生量，让 agent 能看到“分类标签”与“支撑标签的数字”之间的张力，而不是只吃一个结论。

失效形态回灌给出的错误信号系统代价
L2 命中率高、DRAM 未饱和误判 compute-bound，诱导加计算多轮无效搜索，token 与 profile 预算双耗
寄存器溢出压低 occupancystall 归因被底层问题淹没分类标签失真，agent 在错误层级调参
kernel 极短、启动开销占比高指标被固定开销稀释profile 重放成本高于收益

代价的另一面是采集本身。NCU 要把 kernel 串行化并重放，单次 profile 的耗时是裸跑的 10–100 倍，这意味着它不能每轮全量跑。工程上的折中是分层触发：只在候选 kernel 通过正确性门槛后、且相邻两轮时延变化落在噪声带内时才采一次，采集 10–20 个关键指标（DRAM 吞吐、SM 利用率、achieved occupancy、L2 命中率、Top-3 stall 原因），派生量在本地算完再压缩成不超过 200 token 的反馈块拼进下一轮 prompt。200 token 的预算约束很实际：它逼着压缩环节丢掉大部分计数器，只保留能改变 agent 动作的那几个数。一个具体例子是 long scoreboard 占主导时，反馈块应当写成“DRAM 吞吐已接近峰值带宽、long scoreboard 为 Top-1 stall，应减少访存而非增加计算”，而不是罗列二十个计数器——后者会挤占 prompt 里本就紧张的上下文，还会让 agent 在无关指标上做文章。回灌的价值不在于指标多，而在于每个被保留的数字都能对应一个可执行的优化动作。
