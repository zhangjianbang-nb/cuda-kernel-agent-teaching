一 · 从 kernel 文本到 FLOP/Bytes 二元组

流动的第一步不是测时延，而是把一段 kernel 源码（CUDA C++、Triton 或 CuTe）折算成两个标量：总浮点运算数 FLOP 与总 DRAM 字节数 Bytes。这一步的输入是 kernel 源码加上该次调用的 shape 与 dtype 绑定，输出是二元组 (FLOP, Bytes)，代价是解析时间与人工建模误差。对 Triton 而言，静态分析可行度较高：循环边界、块大小、累加器 dtype 在 IR 层面可见，`tl.dot` 的维度直接给出乘加次数，一次 dot 计 2·M·N·K 次浮点运算。对 CUDA C++ 则更依赖 profiler：用 NCU 采集 `sm__sass_thread_inst_executed_op_fadd/fmul/ffma` 一类指令计数，按指令语义折算 FLOP；字节数取 `dram__bytes_read.sum` 与 `dram__bytes_write.sum`。伪代码思路如下：

$$\text{FLOP}=\sum_{\text{dot}}2MNK+\sum_{\text{elem}}c\cdot n,\qquad \text{Bytes}=4\cdot(\text{读元素数}+\text{写元素数})$$

这里的代价必须被显式承认：融合 kernel 的 Bytes 极易低估。一个把 LayerNorm 与残差相加融进同一 kernel 的实现，中间张量从不落回 DRAM，profiler 只报告首尾两次读写，于是 Bytes 远小于“按算子逐个计”的朴素模型，u 随之虚高。反过来，若用朴素模型而非 profiler，又会把缓存复用算成 DRAM 流量，把 u 压低。工程判断是：以 profiler 的 DRAM 计数为准，但在融合边界处人工核对，凡出现“中间张量本应落盘却被融合掉”的位置，在报告里标注建模口径。具体例子：一个 fp16 的 GEMM，M=N=K=4096，FLOP≈1.37e11，若 A/B/C 各读写一次，Bytes≈1.0e8，I≈1370 FLOP/Byte，远超任何现代 GPU 的拐点，属典型 compute-bound；而同一 shape 若被拆成“GEMM + 逐元素缩放”两个 kernel，第二个 kernel 的 I 只有个位数，瓶颈标注立刻翻转。

二 · 拐点 I* 与 T_SOL 的构造

第二步把二元组与机器规格对接。输入是 (FLOP, Bytes)、dtype 与目标 GPU 的 Peak_FLOPS、Peak_BW；输出是拐点 I*、理论最短时延 T_SOL 与瓶颈标签；代价是查表与 dtype 选择带来的口径分歧。核心公式即本模块的骨架：

$$u_{\text{SOL}}=\frac{T_{\text{SOL}}}{T_{\text{gen}}}=\frac{\max\left(\frac{\text{FLOP}}{P_{\text{peak}}},\frac{\text{Bytes}}{B_{\text{peak}}}\right)}{T_{\text{gen}}},\quad I^{*}=\frac{P_{\text{peak}}}{B_{\text{peak}}}$$

Peak_FLOPS 必须按 dtype 分列：fp32、tf32、fp16 三档的峰值差异是数量级级别的，用错一档会让 T_SOL 偏差数倍。TF32 的峰值锚定问题在别处已展开，此处只需记住：dtype 选择直接决定分母。构造 T_SOL 时取两条上限的较大者——若 FLOP/Peak_FLOPS > Bytes/Peak_BW，则 kernel 受计算限制，T_SOL 由算力项给出；反之由带宽项给出。比较 I 与 I* 即得瓶颈标签：I > I* 标 compute-bound，I < I* 标 memory-bound。这个标签是给 agent 的方向性反馈：compute-bound 的优化方向是减少冗余计算、提高 tensor core 占用、改善指令级并行；memory-bound 的方向是合并访存、提升有效带宽、减少中间落盘。代价在于 Peak_FLOPS 是稀疏/稠密混合的理论值，实际可达上限约 70–85%，因此 u 的绝对值需按经验系数校正，否则一个“已达 0.9”的 kernel 可能实际上已经贴着硬件极限，而 agent 仍被驱动去追不存在的余量。具体例子：某 GPU 的 fp16 峰值与带宽之比给出 I* 在数十 FLOP/Byte 量级，一个 I≈8 的 elementwise kernel 必被标为 memory-bound，此时把 T_SOL 算成 Bytes/Peak_BW，任何试图减少 FLOP 的优化都不会改善 u——这正是标签的价值。

三 · 实测 T_gen 与 u 的计算、异常复核

第三步是实测。输入是编译好的 kernel、shape 绑定与计时协议；输出是 T_gen 与 u=T_SOL/T_gen；代价是计时噪声、缓存热态与 launch 开销。计时必须固定 warmup 次数、固定迭代数、取中位数而非均值以抵抗长尾，且必须把 host 侧 launch 与同步开销计入或明确排除——两者口径不同会让 u 在小 kernel 上漂移明显。对 u>1 的样本必须复核，因为理论上界被突破只有两种解释：测量误差（计时器分辨率不足、异步未同步、编译器把整个循环优化掉）或缓存复用（Bytes 被高估，实际 DRAM 流量小于模型）。复核手段是回灌 NCU 的 DRAM 计数与 SM 活跃周期，若 profiler 报告的字节数显著低于模型值，则以 profiler 为准重算 T_SOL；若计时明显偏小，则检查是否漏了同步。这一步的代价是复核本身要跑一遍 profiler，单样本开销从毫秒级计时升到秒级采集，在大规模采样时需按比例抽样复核而非全量。具体例子：一个 K 很小的 GEMM，权重常驻 L2，模型按 DRAM 计 Bytes 得出 T_SOL 偏大，实测 T_gen 小于 T_SOL，u>1；复核发现 `dram__bytes_read` 远低于模型，说明权重被缓存复用，应把该样本标为“缓存敏感”并从 SOL 均值中剔除或单独统计，否则整批样本的 u 分布被少数异常值拉偏。

四 · 瓶颈标签回灌到生成与优化回路

第四步是把标签变成动作。输入是 (u, 瓶颈类型, 复核结论)；输出是下一轮生成/优化的约束或提示；代价是 token 与编译时间。这一步的关键机制是：SOL 分数本身只是标量，真正驱动 agent 的是“差在哪条上限上”。若标 compute-bound 且 u 偏低，反馈应指向 tensor core 利用率、warp 级并行度、寄存器压力导致的占用率下降；若标 memory-bound 且 u 偏低，反馈应指向访存合并、bank 冲突、L2 命中率。把这两类信号写进 prompt 或作为 RL 的可验证奖励分量，比裸 speedup 更有方向性——裸 speedup 只告诉 agent“比基线快或慢”，不告诉它“离硬件上限多远、该往哪个方向走”。代价体现在 token 预算：每条反馈附带瓶颈标签与 u 值，prompt 长度增加，多轮迭代时累积的上下文成本可观；同时每次重编译与重测引入秒级时延，若每轮都做全量 profiler 复核，回路吞吐会被采集开销主导。工程折中是：首轮做完整 profiler 统计与复核，后续轮次只做计时与轻量指令计数，仅在 u 异常跳变时触发重采集。具体例子：一个 memory-bound 的 reduction kernel，u 停在低位，agent 若只看到 speedup 可能反复调 block size；一旦反馈里写明“I 远小于 I*，瓶颈在带宽”，搜索空间立刻收缩到访存模式与向量化宽度上。

五 · 跨 GPU 可比性与分数口径的落地

第五步是把单样本 u 聚合成可比分数。输入是同一批 shape 上每个 kernel 的 u 与瓶颈标签；输出是按瓶颈类型分层的 SOL 利用率分布，以及跨 GPU 型号可比的效率分；代价是聚合口径与硬件差异带来的系统性偏差。由于 u 的分母是 T_SOL，而 T_SOL 由目标 GPU 的峰值决定，同一个 kernel 在不同 GPU 上得到不同的 u，这正是“与基线无关、跨型号可比较”的来源：它衡量的是“在该硬件上离理论上限多远”，而非“比某个手写基线快多少”。聚合时必须按瓶颈类型分层——把 compute-bound 与 memory-bound 的 u 混在一起求均值，会让均值失去物理含义，因为两类样本的可达上限经验系数不同（前者受 tensor core 稀疏/稠密混合影响，后者受有效带宽与缓存命中影响）。代价在于：跨型号比较要求每个型号都维护一份峰值表与经验校正系数，表错一档则整批分数偏移；同时 shape 分布若在不同型号间不一致，分层均值也不可直接对比。具体例子：同一组 GEMM shape 在两种 GPU 上跑，A 型号 I* 较低、B 型号 I* 较高，同一 kernel 在 A 上被标 memory-bound、在 B 上被标 compute-bound，若不分层就合并统计，会得出“B 型号效率更低”的错误结论，而实际上两个标签指向的是不同的优化路径。SOL-ExecBench 类评测正是靠这套口径直接给出“离硬件上限多远”，把绝对时延的不可比性消解掉。

六 · 单步代价的预算表与工程取舍

把五步的代价摊开，才能判断这条流水线在什么规模下可行。下表按步骤列出输入、输出与主要代价，均为定性量级而非编造数字：

步骤输入输出主要代价
FLOP/Bytes 统计源码 + shape/dtype(FLOP, Bytes)解析时间；融合 kernel 字节低估
拐点与 T_SOL二元组 + 峰值表I*、T_SOL、瓶颈标签dtype 口径错配；峰值表维护
实测与复核编译产物 + 计时协议T_gen、u、复核结论计时噪声；profiler 采集秒级开销

聚合与可比分层 u 分布跨型号效率分分层口径；峰值表与校正系数

预算表揭示的工程判断是：采集开销（profiler）与 token 开销（反馈文本）是两条主要成本线，而它们恰好都可以通过“首轮全量、后续轻量、异常触发”的策略压缩。真正不可压缩的是峰值表与经验校正系数的维护——它是 u 绝对值可信度的根基，一旦 Peak_FLOPS 用了稀疏值而 kernel 是稠密实现，u 会被系统性低估，agent 收到的“还有余量”信号就是假的。因此在部署这条流水线时，宁可把校正系数写成显式配置项并在报告中标注，也不要把理论峰值当作可达上限直接除。落到具体机制上：每次生成/优化/验证的流动都应携带一个三元组 (u, I/I* 标签, 复核状态)，聚合时按标签分层、按复核状态过滤，这样 SOL 分数才既是与基线无关的效率度量，又是 agent 可执行的方向信号。

当“理论下界”本身不可信：SOL 归一评分的边界与系统代价

把 SOL 归一评分拆成流动步骤看，它的脆弱点不在最后那一步除法，而在前面两个“看起来只是统计”的环节：FLOP/Bytes 的计量与 Peak 值的取用。步骤链条是——静态分析或 profiler 采集 kernel 的 FLOP 数与 DRAM 字节数，算出算术强度 I；查 GPU 规格按 dtype（fp32/tf32/fp16）取 Peak_FLOPS 与 Peak_BW，构造拐点 I*=P_peak/B_peak；代入 T_SOL=max(FLOP/P_peak, Bytes/B_peak) 得到该 shape 的理论下界；实测 T_gen 后取 u=T_SOL/T_gen，并按 I 与 I* 的大小关系标注 compute-bound 或 memory-bound；最后对 u>1 的样本做复核剔除。每一步的输入输出都清晰，代价却极不对称：前两步是离线或半离线的一次性开销（编译期建模或一次 profiler run），第四步的 T_gen 需要稳定计时（多次 warmup、锁频、排除时钟抖动），而第五步的复核是唯一带“判定”性质的动作，也是整套评分可信度的闸门。

失效条件集中在两处。其一是融合 kernel 的字节数低估：一个把 elementwise、reduction 与 layout 变换揉在一起的 kernel，profiler 报出的 DRAM 字节往往只覆盖了跨 kernel 边界的真实流量，而中间结果的缓存复用被算作“没发生”，于是 Bytes 偏小、I 偏大、T_SOL 偏小，最终 u 虚高——分数好看，却指向一个不存在的硬件上限。其二是 Peak_FLOPS 的口径问题：规格表上的峰值是稀疏/稠密混合、理想频率与理想占用率下的理论值，真实可达上限通常只有其七到八成，于是 u 的绝对值被系统性压低，跨 dtype 比较时更明显（tf32 与 fp16 的峰值倍率不同，同一 kernel 换 dtype 后 u 会跳变，但这不是 kernel 变好了）。这两种误差方向相反，叠加后 u 的绝对值既不能当“离上限多远”的绝对刻度，也不能当跨 dtype 的公平尺。

$$\hat{u}=\frac{T_{\text{SOL}}\cdot \alpha}{T_{\text{gen}}},\quad \alpha\in[0.7,0.85]\ \text{（经验可达系数，按 dtype 与稀疏性分档）}$$

系统代价要按步骤记账。静态建模的代价是人工：手写 FLOP/Bytes 模型对每个 shape 都要重推一遍，遇到动态 shape 或数据依赖的分支就退化为 profiler 依赖；profiler 路线的代价是采集时延与显存——一次 NCU 采集会让 kernel 串行化、关闭部分并发，采集窗口内的实测时延不可用于 T_gen，必须分两次跑（一次干净计时、一次带采集计量），这使单样本的评测成本翻倍。T_gen 的计时本身也有代价：为压住方差需要固定频率、多次重复取中位数，单 kernel 的评测时延从毫秒级抬到秒级，在批量评测里直接转化为吞吐下降。复核 u>1 的样本则是 token 与算力双重开销：要么重跑 profiler 确认字节数，要么人工审查融合边界，agent 侧还要为“异常样本”多消耗一轮推理。一个具体例子：某融合 layernorm+matmul 的 kernel，profiler 报 Bytes 只计了输入输出，中间激活全在 L2 复用，I 被高估近一个量级，u 算出大于 1；复核时把中间激活按“若不复用则需写回 DRAM”的口径补进 Bytes，u 立刻回落到合理区间——这一步不改 kernel，只改分母的建模口径，却决定了这个样本能否进入训练信号。

因此这套评分的正确用法不是把 u 当绝对效率，而是把 u 当“同 dtype、同建模口径下的相对排序信号”，并把瓶颈标注当作方向提示：I 远小于 I* 时 agent 应转向访存合并与分块，I 远大于 I* 时才值得动计算路径。工程判断落在复核策略上——与其追求 u 的绝对精度，不如把“Bytes 建模口径”写进评测契约（明确中间激活是否计入、缓存复用如何折算），并对 u 超过经验可达系数上限的样本一律标记为待复核而非直接剔除，因为那类样本恰恰可能是缓存复用做得最好的 kernel，误删等于把最有价值的反馈信号扔掉。
