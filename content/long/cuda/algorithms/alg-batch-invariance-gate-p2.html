一 · 门控的输入构造：从逻辑等价到物理等价

Batch 不变性门的第一个动作不是跑 kernel，而是构造一对“逻辑等价、物理不等价”的输入。所谓逻辑等价，是指两次运行中被关注的 token 序列完全相同；所谓物理不等价，是指这两次运行落在不同的 launch 配置上——一次是 batch=1，一次是 batch=B，其余 batch 位置用 padding 填满。这一步的输入是原始样本（一条序列、一个目标 token 位置索引、一个 B 值），输出是两份 device 侧张量以及一份“目标位置映射表”：在 batch=1 布局下目标 token 的扁平下标，与在 batch=B 布局下同一逻辑 token 的扁平下标。

构造的关键在于 padding 的填充方式必须与 kernel 的真实语义一致。若 kernel 内部按行做归约，padding 行应填零；若 kernel 做的是 softmax 类归一化，padding 行填零会引入额外的分母贡献，此时必须用 mask 语义对齐，否则门控比对的是两个语义不同的函数，diff 里混进了构造误差。这一步的代价是显存：batch=B 的输入张量是 batch=1 的 B 倍，对长序列 attention 类 kernel，B 取 8 或 16 时单次门控的峰值显存可达数百 MB 量级，在 RL 每轮都跑门控的场景下这是需要计入预算的固定开销。构造阶段本身没有 kernel 编译成本，但它决定了后续比对是否可信——padding 语义错一次，整条门控链路的结论就全部作废。

一个具体例子：某 fused layernorm kernel 在 batch=1 时走单行特化路径，在 batch=B 时按 4 行一组做向量化归约。构造输入时若把 padding 行填成 NaN 而非零，向量化路径的组内归约会被 NaN 污染，diff 立刻爆表，但根因是构造错误而非 kernel 缺陷。因此构造阶段必须附带一条自检：用 padding 行全零的输入跑一遍 batch=B，确认非目标位置的输出不参与比对，且目标位置输出与“仅该行有效”的参考实现一致。

二 · 两次运行与目标位置提取

第二步是执行。输入是两份已构造好的张量与目标位置映射表，输出是两组目标位置的输出向量 $y^{(B=1)}$ 与 $y^{(B)}$，形状均为目标 token 数 × 输出维度。执行顺序有讲究：先跑 batch=1 再跑 batch=B，还是反过来，会影响 GPU 上的缓存与时钟状态，但对正确性门控无实质影响；真正需要固定的是两次运行必须使用同一份编译产物、同一组 launch 参数（除 batch 维度外）、同一 stream 配置，否则 diff 里会混进编译差异与调度差异。

提取目标位置是这一步最容易被低估的成本。对 batch=1，目标位置就是序列内偏移；对 batch=B，需要按映射表做一次 gather。若输出张量是 $[B, S, H]$ 布局，gather 的索引计算是 $b \cdot S \cdot H + s \cdot H + h$，一次 gather 的带宽代价与目标 token 数 × 输出维度成正比。对 hidden 维度 4096、目标 token 数 512 的配置，单次 gather 搬运约 8 MB 量级的数据，相对 kernel 本身的运行时间可以忽略，但它引入了额外的 kernel launch 与同步点，在门控被嵌入每轮 RL 奖励计算时，这些同步点会打断训练主循环的流水，形成可观测的时延毛刺。

运行阶段还有一个隐性代价：batch=B 的实际计算量大于 batch=1，两次运行的时延不可直接比较。这一点在门控设计里必须显式承认——门控只回答“输出是否一致”，不回答“哪个更快”。把两次运行的时延比值当作性能信号是错误用法，因为 padding 改变了有效工作量，比值里既有 kernel 本身的缩放行为，也有 padding 带来的空洞计算。工程上的处理是把时延字段标记为“仅诊断”，不进入奖励函数。

三 · 逐元素比对与 $\Delta_{\text{BI}}$ 的计算

第三步是数值比对，这是门控的核心判据。输入是两组目标位置输出，输出是标量 $\Delta_{\text{BI}}$ 与布尔判定。公式为：

$$\Delta_{\text{BI}}=\max_i\left|y_i^{(B=1)}-y_i^{(B)}\right|,\quad \text{Invariant}=\mathbb{1}\left[\Delta_{\text{BI}}\le \tau_{\text{BI}}\right],\quad R_{\text{final}}=R\cdot\text{Invariant}$$

实现上，$\max_i$ 的归约应在 device 侧完成，避免把两组输出拷回 host 再做比对——后者对 512 token × 4096 hidden 的配置意味着约 16 MB 的 D2H 传输，在 PCIe 链路上是毫秒级开销，足以让门控成为每轮 RL 的瓶颈。device 侧实现是一个 elementwise 差值 kernel 加一次 max 归约，或者用两段式：先写差值到临时缓冲，再用一个 block 级归约出标量。临时缓冲的显存是目标输出规模的两倍（两组输出加差值），这是比对阶段的主要显存代价。

容差 $\tau_{\text{BI}}$ 的选择直接决定误杀率与漏检率的平衡。对 fp32 累加的归约，split-K 改变归约树深度会带来与累加项数对数相关的舍入差异；对 fp16 输出，同样的归约顺序变化可能被输出量化吞掉，也可能恰好跨过舍入边界放大成可见 diff。工程做法是按输出 dtype 与算子类别设阈值：fp32 输出用相对误差与绝对误差的联合判据，fp16/bf16 输出则必须把阈值放宽到量化步长的量级，否则门控会把所有合法的低精度 kernel 全部判死。这一步的代价是判定逻辑本身的复杂度——阈值表需要随算子类型维护，且每次新增算子都要重新标定，标定成本落在工程侧而非运行时。

一个具体例子：某 reduction kernel 在 batch=1 时用单 block 顺序累加，batch=B 时按 8 个 split 并行累加再合并。对 4096 个 fp32 元素的求和，两种归约树的舍入差异在 $10^{-6}$ 相对量级，若 $\tau_{\text{BI}}$ 设在 $10^{-7}$，该 kernel 会被稳定误杀；把阈值调到 $10^{-5}$ 后通过，但此时真正会改变结果的 bug（例如漏加一个 tile）产生的 diff 通常在 $10^{-2}$ 以上，仍能被捕获。阈值标定的本质是在“合法舍入噪声”与“结构性错误”之间找一条分界线。

四 · 差异归因：从标量 diff 到可行动诊断

当 $\Delta_{\text{BI}}$ 超阈值时，门控不能只输出一个失败布尔值，否则下游的修复环节无从下手。第四步是归因，输入是超阈的 diff 与两次运行的中间状态，输出是诊断信息：差异集中在哪些 token、哪些输出通道、diff 的分布形态（稀疏尖峰还是全局抬升）。归因的机制是把目标位置的 diff 向量按 token 与通道两个维度做聚合，观察 diff 的空间结构。

结构本身携带根因信息。若 diff 只在少数 token 上出现尖峰，且这些 token 恰好落在 tile 边界（例如序列长度不是 tile size 整数倍时的尾部 token），则根因指向 tile 划分在 batch=1 与 batch=B 下不一致。若 diff 在全部 token 上呈均匀的小幅抬升，根因更可能是归约顺序变化带来的系统性舍入偏移，属于可容忍噪声而非结构性缺陷。若 diff 集中在特定输出通道，则指向该通道对应的权重加载路径或向量化宽度在两种 batch 下走了不同分支。

归因阶段还可以借助一次额外的对照运行：把 batch=B 的输入改成“目标行有效、其余行全零但保留 batch 维度”，若此时 diff 消失，说明差异来自 padding 行对归约的污染（例如未做 mask 的跨行归约），而非目标行自身的计算路径变化。这次对照运行的代价是一次额外的 kernel 执行与比对，约等于门控主流程成本的一半，但它把“是否 mask 缺失”这一类高频根因从猜测变成可判定。诊断信息的输出应结构化：失败类型标签、diff 统计量、受影响 token 的索引集合，直接写入回归集条目，供后续轮次复现。

五 · 门控判定与奖励乘零的传导

第五步是把布尔判定传导到奖励。输入是 $\text{Invariant}$ 与单 batch 正确性通过后得到的原始奖励 $R$，输出是 $R_{\text{final}}=R\cdot\text{Invariant}$。这一步在计算上近乎零成本，但它的工程含义是：batch 不变性失败即判定不可部署，无论单 batch 正确性多好、性能多高，该候选 kernel 的奖励直接归零。乘零而非扣分的设计是为了让搜索过程无法用“高性能但破坏可复现性”的候选换取部分收益——一旦允许部分奖励，RL 会学会在不变性上做权衡，而可复现性在训练/推理链路里不是可权衡项。

乘零的传导路径需要与回归集联动。失败条目连同诊断信息写入回归集后，后续轮次生成的候选若在同一算子、同一失败模式上复发，回归集应能在门控之前就给出预警，避免重复消耗两次运行的成本。回归集的存储代价是每条失败记录携带一份最小复现输入（目标序列、B 值、阈值），规模远小于完整张量，但条目数量随轮次线性增长，需要按算子与失败类型做去重聚合。

一个具体例子：某 split-K matmul kernel 在 batch=1 时 K 维不切分，batch=B 时切 4 段并行累加，单 batch 正确性检查全部通过，性能也优于基线，但门控在 512 个目标 token 上测到 $\Delta_{\text{BI}}$ 超过 fp32 阈值，判定失败，奖励乘零。诊断信息显示 diff 集中在 K 维尾部 tile 对应的输出通道，根因是 split-K 的段边界在两种 batch 下落在不同位置。该条目进入回归集后，下一轮生成若再次提出同类 split-K 方案，门控前的静态检查即可拦截。

六 · 豁免名单与门控的边界维护

门控的最后一个机制步骤不是计算，而是维护。对本身允许非确定性的算子——典型如使用 atomicAdd 做归约的 kernel——两次运行的输出差异来自硬件原子操作的顺序不确定性，与 batch 无关，门控会稳定误杀。处理方式是按算子类型维护豁免名单：名单内的算子跳过 batch 不变性门控，或把判据从逐元素一致降级为统计一致（例如均值与方差的容差比对）。

豁免名单的代价是它削弱了门控的覆盖。名单每增加一个算子，就有一类“性能优化引入的非确定性”逃出门控视野，而这类错误恰恰是门控最初要捕获的目标。工程上的折中是要求豁免申请附带证据：该算子的非确定性在 batch=1 内部重复运行时同样出现，且量级与 batch 无关，以此证明差异来源是原子序而非 tile 划分。这条证据本身需要额外的重复运行成本，通常取 3 到 5 次重复即可给出稳定的 diff 分布。

边界维护还包括阈值的版本化。阈值随 dtype、算子类别、甚至 GPU 架构变化——不同架构的 FMA 顺序与舍入模式可能不同，同一 kernel 在两种架构上的合法舍入噪声量级不一致。把阈值写死在门控代码里会在跨架构部署时产生系统性误判，正确做法是把阈值作为配置项与算子元数据绑定，随编译产物一起版本化。这一步没有运行时开销，但它决定了门控在异构集群上的可信度：一个在 A 架构上标定的阈值搬到 B 架构上，要么漏检结构性错误，要么误杀合法 kernel，两种失效都不会在单次运行中暴露，只会在回归集的长期统计里显形。

门控的失效面：何时该信、何时该豁免

这条门控的判定力来自一个隐含前提：同一逻辑输入在不同 batch 布局下应当走同一条数值路径。一旦算子本身就把非确定性写进了语义，前提即告失效。典型是 atomicAdd 归约、跨 block 的浮点累加、以及依赖调度顺序的稀疏聚合——它们的输出在 batch=1 与 batch=B 下本就允许不同，ΔBI 超阈值是正常现象而非缺陷。此时若不设豁免，门控会把正确实现判成不可部署，奖励被乘 0，RL 信号被污染成“越保守越安全”的错误梯度。工程上的做法是按算子类型维护豁免名单，并在名单条目上标注豁免理由与复核周期；名单本身要有版本，因为一旦上游把 atomicAdd 换成确定性归约，旧豁免就成了漏检口子。

第二个失效面在输入构造。batch=B 那一侧必须用 padding 填满其余位置，padding 会改变实际计算量：tile 划分、split-K 的切分数、shared memory 占用都随有效 batch 变化，于是两次运行的时延不可直接比较，ΔBI 只配做正确性门控，不能拿来当性能证据。更隐蔽的是 padding 值本身：若 padding 位置参与归约（例如未加 mask 的 softmax 分母），目标位置输出会被污染，ΔBI 放大却与 batch 不变性无关，诊断信息会指向错误的根因。构造逻辑等价输入时必须显式验证 padding 不进入目标位置的计算图，这一步的代价是一次额外的单 batch 对照运行。

$$\Delta_{\text{BI}}=\max_i\left|y_i^{(B=1)}-y_i^{(B)}\right|,\quad \text{Invariant}=\mathbb{1}\left[\Delta_{\text{BI}}\le \tau_{\text{BI}}\right],\quad R_{\text{final}}=R\cdot\text{Invariant}$$

阈值 τBI 的选取是第三个代价点。取绝对容差时，量级差异大的输出通道会被小通道主导，max abs diff 掩盖真实偏差；取相对误差时，接近零的输出让分母爆炸。可行的折中是逐元素混合判据，并对每个输出张量单独设阈值，代价是阈值表随模型演进而漂移，需要回归集持续校准。定位环节同样有成本：diff 超阈值后要区分归约顺序、split-K、tile 边界三类来源，最直接的办法是把 batch=B 的运行强制退化为单 tile 单 split 再比对，这相当于多跑一次 kernel，门控从“两次运行 + 一次比对”涨到三次，在每轮 RL 奖励计算里嵌入时，这部分时延会直接摊到 rollout 预算上。

因此这条门控的工程判断是：它适合作为“性能优化引入的非确定性”的廉价筛子，不适合作为通用正确性 oracle。部署判定应当把 Invariant 与算子豁免标记做合取，而不是让 Invariant 单独决定 Rfinal；对豁免算子改用统计式判据（多次运行取分布而非逐元素比对），代价是采样次数上升、门控时延不再恒定。回归集记录的是失败样本的输入构造与根因标签，而非仅记录 ΔBI 数值——后者在阈值调整后即失去意义，前者才能在后续轮次复现同一失效路径。
