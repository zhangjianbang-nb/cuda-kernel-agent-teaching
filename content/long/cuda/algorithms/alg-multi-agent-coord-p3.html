一 · 奖励函数的逐项拆解与推导起点

给定公式为 $$\text{reward}_t=\mathbb{1}[\text{correct}]\cdot\left(\frac{T_{\text{best}}}{T_t}-1\right)-\lambda\cdot\text{tokens}_t,\quad \text{keep if }\ \text{reward}_t>\tau$$ 它不是拍脑袋的加权和，而是从“相对加速比”这一物理量出发的。推导的关键一步在于：把绝对时延 $$T_t$$ 转成无量纲的比值 $$T_{\text{best}}/T_t$$，再减 1 得到“相对当前最优基线的净增益”。减 1 这一步不可省：若只写 $$T_{\text{best}}/T_t$$，一个与基线持平的候选会拿到 1.0 的正奖励，keep 判据就失去区分度；减 1 后持平者奖励为 0，劣于基线者为负，语义才与“是否值得保留”对齐。指示函数 $$\mathbb{1}[\text{correct}]$$ 是硬门控而非软惩罚：正确性不通过时整项归零，避免“用错误换速度”的梯度污染策略池。第二项 $$-\lambda\cdot\text{tokens}_t$$ 把多角色通信成本显式计入，使 token 预算成为可调旋钮而非事后账单。

逐项看代价。第一项的数值范围受 $$T_{\text{best}}/T_t$$ 支配：当候选比最优基线慢一倍，该项约为 −0.5；快一倍则约为 +1.0，量级不对称，意味着“退步的惩罚”弱于“进步的奖励”，这是有意的——长程搜索中允许一次探路性退步，但 keep 阈值 $$\tau$$ 会拦住它。第二项的量级取决于单轮 token 消耗与 $$\lambda$$ 的标定：若一轮四角色往返消耗数千 token 而时延增益只有百分之几，则 $$\lambda$$ 过小会让奖励被“聊胜于无”的微小加速主导，过大则让所有候选都跌破 $$\tau$$、搜索提前停滞。具体例子：某轮 coder 提交的向量化版本正确但只快 3%，而 profiler 与 critic 的往返 token 折算后惩罚相当于 5% 的时延增益，则奖励为负，critic 应 revert——这正是公式想要的行为，把“沟通成本高于收益”的轮次自动淘汰。

keep 判据 $$\text{reward}_t>\tau$$ 的工程含义是：$$\tau$$ 不是零而是略大于零的正数，用来吸收测量噪声与计时抖动。若 $$\tau=0$$，任何在噪声范围内的“微弱更快”都会被写入成功记忆，策略池被伪增益污染，后续 proposer 会反复复用无效策略。代价是：$$\tau$$ 设得过高会让真实但幅度小的优化（如占用率微调带来的个位数百分比提升）永远进不了池子，长程迭代的收益曲线被压平。因此 $$\tau$$ 必须与基线计时的方差同量级标定，而不是凭经验取一个固定小数。

二 · 时延项的可加性与 Amdahl 式归因

公式里的 $$T_t$$ 是端到端 kernel 时延，但 critic 要判断“这一轮该保留哪条策略”，就必须把总时延拆到可归因的分量上，否则奖励只是一个黑箱标量，无法指导下一轮 proposer。推导的关键一步是把 $$T_t$$ 写成各阶段时延的加性分解：$$T_t=\sum_{s}T_s^{(t)}$$，其中 $$s$$ 遍历访存、计算、同步、启动开销等阶段。于是相对增益可写成 $$\frac{T_{\text{best}}}{T_t}-1=\frac{\sum_s T_s^{\text{best}}-\sum_s T_s^{(t)}}{\sum_s T_s^{(t)}}$$，分子按阶段可拆，critic 便能回答“这 3% 的增益来自哪个阶段”。这一步把标量奖励变成向量归因，是 profiler 输出能真正回灌到 proposer 的数学前提。

Amdahl 式的约束在此显形：若某阶段占总时延的比例为 $$p$$，该阶段被优化到接近零，总时延最多降到 $$(1-p)T_t$$，对应相对增益上限 $$\frac{p}{1-p}$$。具体例子：profiler 归因显示同步阶段占 40%，则即便把同步完全消除，总增益上限约为 0.67；若 proposer 提出的是针对占 5% 的计算阶段的向量化，理论上限仅约 0.05，低于 $$\tau$$ 时就不该浪费一轮预算。这条推导让 critic 能在编译与跑测之前就用归因比例否掉低上限策略，节省的是实打实的编译时间与 GPU 占用。

代价在于分解本身不免费：要拿到分阶段时延，需要 profiler 采集 NCU 指标并按 stall 分布做归因，这引入额外的采集开销与上下文 token；若归因粒度太细，token 成本上升而边际信息递减。工程判断是：分解粒度对齐 proposer 能提出的策略类别（访存、计算、同步、占用率四类即可），不要细到单条指令，否则奖励公式的第二项会吃掉第一项的收益。

三 · 显存与占用率的约束项如何进入判据

奖励公式没有显式显存项，但显存是 keep/revert 的硬约束，必须作为前置过滤而非软惩罚。推导的关键一步：把显存占用写成 $$M_t=M_{\text{static}}+M_{\text{dyn}}(B,S)$$，其中 $$B$$ 为批大小、$$S$$ 为问题规模；候选策略若引入双缓冲或 split-K 的部分和缓冲，会抬高 $$M_{\text{dyn}}$$。占用率则近似随每 SM 可用寄存器与共享内存反比变化：$$\text{occupancy}\approx\frac{\text{regs per SM}}{\text{regs per thread}\times\text{threads per block}}$$ 的受限项取寄存器与共享内存两者中更紧的一个。这两条式子说明：显存与占用率不是独立维度，而是通过“每线程资源”耦合在一起的。

因此 critic 的判据应是两级：先做可行性门 $$M_t\le M_{\text{cap}}$$ 且占用率不低于某下限，不满足则直接 revert，不进入奖励比较；满足后再用奖励公式排序。具体例子：coder 为实现双缓冲把共享内存翻倍，占用率从可容纳多块降到仅一块，虽然单块内访存延迟被掩盖，但 SM 上并行块数下降导致总体吞吐不升反降——此时奖励公式可能给出接近零的增益，而占用率门会先把它拦下，避免把“局部更快、全局更慢”的实现写进成功记忆。

代价是显存约束会压缩搜索空间：split-K 这类策略在减小单块工作量的同时增加部分和缓冲，规模稍大就越过 $$M_{\text{cap}}$$，proposer 若不了解这条边界会反复提出不可行策略，浪费编译与跑测预算。可行的工程做法是把 $$M_{\text{cap}}$$ 与占用率下限写进 proposer 的上下文，让它在提策略阶段就自我过滤，而不是等 critic 事后否决。

四 · 误差项与正确性 oracle 的耦合

指示函数 $$\mathbb{1}[\text{correct}]$$ 看似二值，实则背后是一个带容差的误差判据。推导的关键一步是把“正确”定义为逐元素相对误差不超过容差：$$\text{correct}=\bigwedge_{i}\frac{|y_i-\hat{y}_i|}{\max(|y_i|,\epsilon)}\le\delta$$，其中 $$\hat{y}_i$$ 为候选输出、$$y_i$$ 为 fp64 参考、$$\epsilon$$ 防止除零。这个定义把正确性从“是否跑通”提升为“数值是否在容差内”，因为 kernel 优化（重排归约顺序、改用 TF32、向量化）恰恰最容易在数值上产生微小漂移。

耦合点在于：$$\delta$$ 的选择直接改变奖励公式的可行域。若 $$\delta$$ 过松，一个数值已劣化但仍在容差内的候选会被判 correct 并拿到加速奖励，策略池里就混入了“以精度换速度”的实现；若过紧，合法的重排归约因浮点非结合性被误判为错误，proposer 会收到错误的失败教训，双记忆被污染。具体例子：把归约从顺序累加改为树形归约，数学上等价但浮点结果有末位差异，若 $$\delta$$ 卡在机器精度量级，该候选会被判错，critic 写入“树形归约不可用”的错误教训，后续轮次被永久屏蔽——这是误差项与记忆机制耦合失配的典型代价。

代价还体现在 oracle 本身的成本：fp64 参考实现要跑一遍完整规模，加上容差逐元素比较，单轮验证的时延可能超过候选 kernel 本身；若每轮都对全量元素做比较，验证开销会稀释奖励公式里时延项的区分度。工程判断是把 oracle 的比较做成抽样加边界覆盖：主体用抽样元素，边界与极值元素全查，既控制验证时延，又不放过系统性偏差。

五 · token 惩罚项与预算约束的推导

第二项 $$-\lambda\cdot\text{tokens}_t$$ 的推导关键一步是把 token 消耗折算成“等效时延增益”：设单位 token 的机会成本为 $$c$$，则惩罚项等价于从相对增益中扣除 $$\lambda\cdot\text{tokens}_t$$。要让这一项与第一项同量纲，$$\lambda$$ 必须满足：一轮典型通信的 token 成本所对应的惩罚，应约等于一次“可接受的微小加速”的增益量级。换句话说，$$\lambda$$ 的标定不是调参，而是把“沟通开销”翻译成“性能等价物”的汇率。

四角色分工天然抬高 $$\text{tokens}_t$$：proposer 读策略池与诊断、coder 生成源码、profiler 输出归因、critic 做一致性校验，每一跳都是上下文传递。推导上可以把总 token 写成各角色输入输出之和 $$\text{tokens}_t=\sum_{r}\text{tok}_r^{\text{in}}+\text{tok}_r^{\text{out}}$$，其中 profiler 的 NCU 归因文本与 critic 的校验说明是主要膨胀源。具体例子：若 profiler 每轮把完整 stall 分布原文塞进上下文，token 成本随轮次线性增长，而奖励公式的惩罚项随之线性上升，最终所有候选都跌破 $$\tau$$，搜索在预算耗尽前就停滞——这不是策略不好，而是上下文管理没有做压缩。

代价与工程判断：token 惩罚项的存在使“多轮”本身成为有成本的决策，而非免费迭代。可行的缓解是把 profiler 输出压缩成结构化的瓶颈标签（访存/计算/同步/占用率四类加比例），而非原始指标全文；把 critic 的校验结论写成短标签而非长篇论证。这样 $$\text{tokens}_t$$ 的增速被压到亚线性，奖励公式的第一项才有机会主导 keep 决策。反过来，若把 $$\lambda$$ 设为零，公式退化为纯加速比排序，多角色通信的膨胀将无人约束，长程迭代的预算利用率下降——这正是单 agent 上下文膨胀问题在多 agent 架构里的镜像。

六 · 从公式到可实现伪代码

把上述推导落到可实现层面，critic 的单轮决策可写成如下伪代码思路（非 $$\text{pre}$$ 块，按行叙述）：输入为候选 kernel 的时延 $$T_t$$、当前最优 $$T_{\text{best}}$$、正确性布尔、本轮 token 数、显存与占用率实测值。第一步做可行性门：若 $$M_t>M_{\text{cap}}$$ 或占用率低于下限，直接返回 revert 并写入失败教训，不计算奖励。第二步做正确性门：若 $$\mathbb{1}[\text{correct}]=0$$，奖励归零，同样 revert，但失败教训要记录具体的误差模式（哪类元素超容差），供 proposer 下轮避开。第三步计算 $$\text{reward}_t=\frac{T_{\text{best}}}{T_t}-1-\lambda\cdot\text{tokens}_t$$。第四步比较 $$\text{reward}_t>\tau$$，成立则 keep 并把 $$T_{\text{best}}\leftarrow T_t$$、策略写入成功记忆；否则 revert 并把归因标签写入失败教训。

这段伪代码的关键设计在于顺序：可行性门与正确性门都在奖励计算之前，避免“先算奖励再否决”造成的无效计算与日志噪声；$$T_{\text{best}}$$ 的更新只在 keep 分支发生，保证基线单调不升，从而使后续轮次的相对增益始终以真实最优为参照，而不是被一次伪增益拉低的基线。具体例子：某轮候选正确且快 8%，但显存超限，伪代码在第一步就 revert，$$T_{\text{best}}$$ 不变；下一轮 proposer 从失败教训里读到“显存超限”标签，改提分块更小的策略，而不是重复同一方向。

代价层面，这段伪代码每轮要跑一次正确性 oracle、一次 NCU 采集、一次显存与占用率读取，加上四角色上下文往返，单轮固定开销明显高于单 agent 的一次生成加一次跑测；在预算紧张时，固定开销占比上升，奖励公式的 token 惩罚项会把多轮收益压到阈值以下。工程判断是：把可行性门与正确性门做成轻量前置检查（编译期静态估计显存、抽样正确性），把昂贵的 NCU 采集留给已通过前置门的候选，从而在不改变公式语义的前提下降低单轮成本。公式本身不区分“检查顺序”，但实现顺序决定了预算利用率。

奖励门槛与角色失真的边界条件

该奖励式在工程上真正的难点不在correct项，而在比值项的分母：$$T_t$$是第 t 轮实测时延，含编译与 oracle 校验的墙钟开销。当 kernel 规模小、单次编译占主导时，$$T_{\text{best}}/T_t$$的方差被编译抖动放大，reward 的符号可能只反映编译器噪声而非策略优劣。此时 keep 判据$$\text{reward}_t>\tau$$会退化为对$$\lambda\cdot\text{tokens}_t$$的惩罚项做筛选——token 越省越易 keep，与优化目标背离。失效条件是明确的：编译时间与 kernel 执行时间同量级时，该式不可用于跨轮比较，必须改用纯 kernel 时延（剔除编译）或固定编译缓存后再测。

第二处边界是 profiler 归因失真沿角色链的传导。proposer 只读诊断文本，若 profiler 把占用率不足误判为访存瓶颈，proposer 会提出 split-K 类策略，coder 实现后 critic 只能看到时延未改善，却无法回溯是归因错了。双记忆此时写入的是“split-K 无效”这一错误教训，后续轮次被永久污染。代价是可量化的：一次错误归因至少浪费一轮完整预算（proposer 提案 + coder 编译 + profiler 采集 + critic 判定），且失败教训条目会挤占策略池的检索带宽，使真正有效的候选被稀释。

系统代价还体现在 critic 的一致性校验成本上。critic 若要对 profiler 归因做交叉验证，需重跑 NCU 或比对 SASS stall 分布与提案假设是否吻合，这等于把单轮 token 开销再抬高一档；若省略校验，则上述污染路径无阻断。工程判断是：$$\tau$$不应设为常数，而应按$$T_{\text{best}}$$的相对改善幅度设阈值，并要求 profiler 输出归因时附带其依据的具体指标名与采样区间，使 critic 能以低成本做“归因—指标”一致性检查，而非重跑采集。
