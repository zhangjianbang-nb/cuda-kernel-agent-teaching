一 · 评分公式的逐项拆解：从指示函数到比值项

评分公式 $$\text{score}(d)=\mathbb{1}[\text{compile}(d)]\cdot\mathbb{1}[\text{correct}(d)]\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)}$$ 看起来只有三项，但每一项背后都对应一条独立的验证流水线，且三项之间不是并列关系而是短路关系。两个指示函数是布尔闸门：$$\mathbb{1}[\text{compile}(d)]$$ 为 0 时，整个 score 直接归零，后续的正确性 oracle 与性能测量根本不应被触发——这一点在工程实现上必须显式落实，否则会出现“编译失败的配置仍然占用了正确性测试的 GPU 时间”的预算泄漏。同理 $$\mathbb{1}[\text{correct}(d)]$$ 为 0 时，性能测量也不应执行，因为一个数值错误的 kernel 的时延毫无意义，把它计入分母只会污染搜索信号。

比值项 $$\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)}$$ 的分子是参考实现的时延，分母是候选 DSL 决策 lowering 后 kernel 的实测时延。这里的关键推导一步在于：这个比值不是“加速比”意义上的无界量，而是被约束条件 $$R(d)\le R_{\max},\ S(d)\le S_{\max}$$ 夹住的。资源约束 R 与 S 分别对应寄存器用量与共享内存用量（或占用率下界），它们不是评分项而是可行性域的定义：任何违反约束的决策 d 在进入评分之前就应被剪枝，而不是靠 score 里再乘一个惩罚因子。原因在于惩罚因子会让搜索算法误以为“稍微超一点资源”是一个可探索的连续方向，而实际上寄存器溢出到 local memory 或共享内存超限导致的 occupancy 崩塌是非连续的性能悬崖。

具体例子：一个 tile 尺寸为 128×128、流水线级数为 3 的 DSL 决策，其共享内存需求可由 $$S(d)=2\cdot B_{\text{tile}}\cdot\text{sizeof}(\text{elem})\cdot L_{\text{pipe}}$$ 估算（双缓冲乘以流水线级数），若 elem 为 fp16、tile 为 128×128，则单级缓冲约 32KB，三级流水线双缓冲即 192KB，直接越过多数架构的共享内存上限——这一判断在 schema 校验阶段用算术即可完成，无需编译。代价是：把资源约束前移到解析器意味着 DSL schema 必须携带硬件常量表，schema 与架构特性同步的维护成本就是这套方案为“编译失败率下降”支付的对价。

二 · 时延项的测量口径与归一化推导

分母 $$T_{\text{kernel}}(d)$$ 的测量口径决定了整个评分的可信度。工程上必须区分三种时延：wall-clock 端到端时延（含 launch 开销与 host 侧同步）、device 侧 kernel 执行时延（CUDA event 夹逼）、以及稳态迭代下的平均时延（warmup 后多次取中位数）。评分公式里的 $$T_{\text{kernel}}$$ 应取第三种，因为前两种会被 launch 开销与首次编译/上下文初始化污染，而 DSL 决策之间的差异往往在微秒级，launch 开销足以淹没信号。推导的关键一步是把测量误差写成 $$\epsilon_T=\frac{\sigma_T}{\sqrt{n}}$$，其中 $$\sigma_T$$ 是单次测量的标准差、n 是重复次数；要让两个 DSL 决策的 score 差异可分辨，必须满足 $$\Delta T > 2\epsilon_T$$，否则 beam search 会在噪声上做选择。

伪代码落到可实现层面，测量函数应写成如下结构（以文字描述其控制流）：先做 k 次 warmup 丢弃，再采集 n 次 event 夹逼的时延样本，剔除首尾各一定比例的离群值后取中位数，同时返回样本标准差供上层判断该测量是否可信。若标准差超过中位数的某个比例阈值，则该测量标记为“不可信”，在搜索中不作为 keep 的依据。代价是：n 次重复测量把单次评估的 GPU 时间放大了 n 倍，在 beam width 为 b 的搜索中，每轮评估成本约为 $$b\cdot n\cdot T_{\text{kernel}}$$ 加上正确性 oracle 的开销；这是用测量预算换搜索信号质量的直接交易。

具体例子：两个 DSL 决策仅在流水线级数上不同（2 级 vs 3 级），实测中位数相差 3%，但样本标准差达到中位数的 5%，此时按上述判据该差异不可信，搜索应保持两者而非淘汰较慢者——这避免了把“流水线级数从 2 提到 3”这一正确方向因为一次噪声测量而 revert 掉。归一化方面，分子 $$T_{\text{ref}}$$ 必须与候选 kernel 在同一测量口径下取得，否则比值项会系统性偏置；参考实现的时延应缓存复用而非每次重测，缓存带来的风险是硬件状态漂移，因此需要在搜索会话开始时重测一次并记录。

三 · 显存与资源约束的推导：从字段到可行域

约束 $$R(d)\le R_{\max},\ S(d)\le S_{\max}$$ 中的 R 与 S 不是独立常量，而是 DSL 字段的函数。以线程映射字段为例，每线程寄存器用量可近似为 $$R(d)\approx R_{\text{base}}+c_1\cdot U_{\text{unroll}}+c_2\cdot\frac{W_{\text{tile}}}{T_{\text{thread}}}$$，其中 unroll 因子与每线程处理的 tile 宽度直接由 DSL 决策给出，base 与系数需由 lowering 器在编译后从 ptxas 输出回读校准。这一步推导的意义在于：schema 校验阶段只能用近似式做粗筛，真正的资源判定必须等编译完成后的寄存器报告，因此“解析器校验资源上限”与“编译后资源复核”是两道闸门，前者挡掉明显越界的决策以节省编译预算，后者捕获近似式失准的情况。

共享内存约束 S(d) 的推导更直接：$$S(d)=\sum_{i\in\text{buffers}}\text{size}_i(d)\cdot\text{depth}_i(d)$$，其中每个 buffer 的尺寸由 tile 尺寸与元素类型决定，depth 由流水线级数与双缓冲策略决定。关键一步是把 S(d) 写成对 DSL 字段的可微/可枚举函数，使得搜索可以在字段维度上做局部调整（例如把流水线级数从 3 降到 2 以腾出共享内存），而不是把整个决策丢弃。代价是：共享内存的精确用量还受对齐与 padding 影响，近似式会低估，因此 S_max 应留出安全裕度，裕度太大会浪费可用的 occupancy，太小则会在编译后复核阶段频繁 reject，浪费编译时间。

具体例子：一个决策把 tile 从 64×64 提到 128×64、流水线从 2 提到 3，按近似式共享内存从约 32KB 涨到约 96KB，若目标架构上限为 100KB 则勉强通过粗筛，但编译后因对齐 padding 实际达到 104KB 被复核拒绝。这次拒绝的代价是一次完整的编译时间（秒级到十秒级），而如果 schema 校验阶段把 padding 系数纳入估算，这次编译本可避免。这说明资源近似式的精度直接换算成编译预算的浪费率。

四 · 误差项与正确性 oracle 的判据推导

正确性指示函数 $$\mathbb{1}[\text{correct}(d)]$$ 内部并不是单一布尔量，而是一组数值判据的合取。对浮点 kernel，判据通常写成 $$\max_i\frac{|y_i-\hat{y}_i|}{\max(|y_i|,\epsilon)}\le \tau_{\text{rel}}\ \wedge\ \max_i|y_i-\hat{y}_i|\le \tau_{\text{abs}}$$，即相对误差与绝对误差的双阈值。推导的关键一步在于理解为什么需要双阈值：纯相对误差判据在参考值接近零时会爆炸（分母趋零），纯绝对误差判据在大幅值输出上过于宽松。双阈值取交集意味着任一元素违反任一阈值即判错，这是保守判据，代价是可能把数值上可接受的实现误判为错误，从而在搜索中错误地 revert 掉一个性能更优的决策。

对归约类 kernel，误差判据还需考虑累加顺序带来的差异：不同 tile 划分与线程映射会改变浮点加法的结合顺序，误差随归约规模增长。此时判据应写成 $$\text{err}(d)\le \tau_{\text{rel}}\cdot\sqrt{N_{\text{reduce}}}$$ 形式的规模相关阈值，其中 $$N_{\text{reduce}}$$ 是归约元素数，这一形式来自浮点误差随累加步数增长的经典界。伪代码层面，oracle 应先在 fp64 参考实现上算出基准值，再对候选 kernel 输出逐元素比较，并同时返回最大相对误差、最大绝对误差与违反阈值的元素计数——后两项是回灌给 DSL 层的结构化反馈，用于判断错误是集中在边界 tile（边界处理策略字段的问题）还是全局性（累加或布局字段的问题）。

具体例子：一个决策把边界处理策略从“谓词掩码”改为“padding 填充”，数值上等价但引入了额外的无效元素参与归约，导致最大相对误差从 1e-5 量级升到接近阈值。oracle 返回的违反元素计数若集中在最后一列 tile，则反馈精确指向边界处理字段，搜索可以只在该字段上做局部回退，而不必丢弃整个决策。代价是：fp64 参考 oracle 的运行时间通常是候选 kernel 的数倍，且需要额外的显存存放 fp64 基准输出，在 beam 宽度大时这部分开销不可忽略，因此实践中常对参考值做缓存，仅当输入 shape 变化时重算。

五 · 奖励塑形与搜索信号的推导：从 score 到 keep-revert 判据

搜索层拿到的奖励不应直接是 score 的原始值，因为 score 的分布高度偏斜：绝大多数编译失败或正确性失败的决策 score 为 0，少数成功者的 score 在 1 附近波动。直接把 0/1 混合的奖励喂给 beam search 会导致有效样本极少。推导的关键一步是构造分层奖励 $$r(d)=\alpha\cdot\mathbb{1}[\text{compile}]+\beta\cdot\mathbb{1}[\text{correct}]+\gamma\cdot\mathbb{1}[\text{correct}]\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)}$$，其中 $$\alpha<\beta<\gamma$$ 保证“能编译”优于“不能编译”、“正确”优于“仅能编译”、“快”优于“仅正确”，同时让编译失败与正确性失败之间仍有可区分的梯度信号。这一塑形的代价是引入了超参数 α、β、γ，它们需要与搜索的 keep 阈值联合校准，否则会出现“为了拿到 compile 奖励而生成大量平凡但正确的慢 kernel”的退化行为。

keep-revert 判据可写成：若 $$r(d_{\text{new}})>r(d_{\text{cur}})+\delta$$ 且新决策的测量被标记为可信，则 keep；否则 revert 到当前最优。阈值 δ 的作用是抑制在噪声上的抖动，其取值应与第二节的测量误差界挂钩，即 $$\delta\ge\gamma\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}}\cdot\frac{2\epsilon_T}{T_{\text{kernel}}}$$ 的量级。伪代码层面，搜索循环应维护一个按字段分组的统计：每个 DSL 字段被修改后带来的奖励变化均值与方差，用于在 beam 扩展时优先变异高方差字段（探索）或高均值字段（利用）。

具体例子：一个 beam 中有 8 个决策，其中 5 个编译失败、2 个正确但慢、1 个正确且快。若奖励是原始 score，则 5 个零奖励样本不提供任何方向信息；分层奖励下，这 5 个样本至少能按“编译失败发生在哪个字段”聚类，反馈给下一轮的 schema 约束收紧（例如某字段的取值域与另一字段的组合被证明高频失败，可在解析器中加交叉约束）。代价是：分层奖励让搜索更倾向于先解决编译问题再优化性能，收敛到高性能 kernel 所需的轮次可能增加，这是用轮次预算换每轮有效信息的交易。

六 · 公式与 lowering 的耦合：确定性翻译如何反哺评分

评分公式里的每一项都依赖 lowering 器的确定性：同一个 DSL 决策必须每次 lowering 出语义等价、性能可复现的源码，否则 $$T_{\text{kernel}}(d)$$ 就成了随机变量，score 的比较失去意义。推导的关键一步是把 lowering 的输出写成 $$\text{src}=\text{Lower}(d;\ \text{arch},\text{version})$$，其中 arch 与 version 是显式参数而非环境隐式状态；任何影响生成代码的编译器版本、架构特性开关都必须进入这个参数元组，并被记录在评估日志中。这样做的直接后果是：跨会话的 score 比较只有在参数元组一致时才合法，否则必须重测参考实现的 $$T_{\text{ref}}$$。

lowering 注入的边界检查与同步原语本身有时延代价，这部分代价必须计入 $$T_{\text{kernel}}(d)$$ 而非被剥离，否则评分会系统性高估那些依赖大量边界检查的保守决策。伪代码层面，lowering 器应在生成的源码中保留可追溯的注释标记（哪个 DSL 字段生成了哪段代码），使得编译错误与 NCU 指标能回灌到字段级；这一追溯能力是 DSL 方案相对自由文本生成的核心优势，其代价是 lowering 器需要维护字段到代码模板的映射表，DSL 每扩展一个字段就要同步扩展映射与测试。

具体例子：一个决策的流水线级数字段从 2 改为 3，lowering 器生成的代码中多出一组双缓冲的同步原语与共享内存声明，编译后寄存器用量上升、occupancy 下降，实测时延反而变慢。若评分只看 $$T_{\text{kernel}}$$ 的比值，该决策会被 revert；但由于 lowering 保留了字段级追溯，反馈可以精确写成“流水线级数 3 在该 tile 尺寸下导致 occupancy 跌破阈值”，搜索据此把该字段与 tile 尺寸的交叉约束加入 schema，而不是简单地把流水线级数锁死在 2。这一机制把一次失败的评估转化为 schema 约束的永久性改进，代价是 schema 会随搜索轮次单调膨胀，约束之间的交互需要定期审计以避免过度剪枝掉本可探索的合法区域。

当评分公式撞上 DSL 表达力天花板

评分式 $$\text{score}(d)=\mathbb{1}[\text{compile}(d)]\cdot\mathbb{1}[\text{correct}(d)]\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)}$$ 在 DSL 层有一个隐蔽的失效模式：两个指示函数把“不可编译”与“不正确”压成同一个 0，而 DSL 决策 $$d\in\mathcal{D}_{\text{DSL}}$$ 中真正导致失败的是某个字段的取值，比如 tile 尺寸与共享内存布局的组合超出 $$S(d)\le S_{\max}$$。若反馈只回灌“编译失败”，beam search 会在同一字段的相邻取值上反复撞墙；只有把指示函数拆成字段级掩码 $$\mathbb{1}[\text{compile}(d)]=\prod_{f\in d}\mathbb{1}[\text{field\_ok}(f)]$$，搜索才有梯度方向。代价是解析器要为每个字段维护独立的合法性判定，schema 每扩一维，校验路径与 lowering 分支同步增长，编译期成本从“一次 lowering”变成“逐字段预检 + 一次 lowering”。

边界条件更硬：DSL 未覆盖的非常规优化（warp-specialized 流水线、异步拷贝的细粒度重叠）无法被表达，评分式的分子 $$T_{\text{ref}}$$ 再高也换不来这类 kernel 的时延。此时 score 的上界被 $$\mathcal{D}_{\text{DSL}}$$ 的势封死，beam 宽度再大也只是在低维子空间里打转——这是表达力上限即性能上限的直接后果，而非搜索预算不足。

伪代码上，keep-revert 的判定应写成“合法且加速才保留”，否则回退到上一合法配置，避免无效迭代吃满轮次：

  • 解析 $$d$$ → 字段掩码；任一字段非法则记录字段名并丢弃，不进 lowering。
  • lowering 后编译、oracle 校验、计时；三项任一失败则把结构化错误写回该字段的候选表。
  • 仅当 $$\text{score}(d)>\text{score}(d_{\text{best}})$$ 且资源约束满足时替换 best。

系统代价落在两处：lowering 器需与 CUDA 版本、架构特性同步维护，DSL 每加一个字段就多一条 lowering 路径与一组边界检查注入点；同时字段级反馈让每轮 token 消耗从“整段源码”降到“字段名 + 错误类”，但解析器预检本身引入固定时延，在轮次预算紧张时这部分时延不可忽略。具体例子：共享内存布局字段若只允许两种取值，而目标 kernel 的最优解需要三缓冲布局，则该字段的合法域直接截断了 score 的上界——此时应扩 DSL 而非加 beam 宽度。
