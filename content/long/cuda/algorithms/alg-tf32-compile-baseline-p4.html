一 · 负载画像：先决定“考什么”，再决定“怎么考”

锚定基线的评测配方不是先写计时脚本，而是先给负载画像。TF32/编译基线锚定的负载画像要回答四个问题：模型族、算子族、shape 族、硬件族。这四者共同决定四条参考路径（eager fp32、eager tf32、torch.compile、cuBLAS 直调）中哪一条会成为分母，以及生成 kernel 的加速比是否具有可比性。负载画像错了，后面的计时再干净也是无效测量。

模型族的选择标准是“是否落在 cuBLAS/cuDNN 的启发式甜区”。Transformer 的 QKV 投影、MLP 上投影、注意力打分属于大 M/N/K 的规整 GEMM，cuBLAS 通常已接近 SOL，此时分母很强，生成 kernel 的加速空间被压缩，评测的鉴别力集中在“能否不退化”而非“能否超越”。相反，小 batch 解码阶段的 GEMV、带不规则 mask 的 attention、grouped GEMM（MoE 路由）、以及 stride 非连续的 layout 变换，属于 cuBLAS 启发式容易退化的区域，分母偏弱，加速比容易被放大——这正是需要四条基线交叉验证的地方。负载画像必须显式标注每个算子属于“甜区”还是“退化区”，否则同一份生成 kernel 在两个区里的 speedup 不可比。

算子族的粒度要细到“是否融合”。一个 LayerNorm+残差+cast 的融合算子，在 eager 下是三次 kernel launch 加两次中间张量往返 HBM，在 torch.compile 下可能被融合成一次，在 cuBLAS 直调下根本不存在对应入口。若评测只拿 eager 当分母，生成 kernel 的“融合收益”会被误记为“算法收益”。因此算子画像要记录：该算子在 eager 下的 launch 次数、中间张量字节数、是否被 torch.compile 融合。这个记录直接决定分母该取哪条路径。

shape 族的设定要覆盖三类：典型 shape（来自真实模型配置）、边界 shape（K 为奇数、M=1、N 极小）、以及退化 shape（K 不能被 8 整除导致 TF32 无法整块对齐）。典型 shape 决定评测的代表性，边界与退化 shape 决定评测的鲁棒性。只测典型 shape 的配方会系统性高估生成 kernel 的泛化能力，因为 LLM 生成的 tiling 往往对 K 的对齐性极度敏感。硬件族则锁定 GPU 型号与 SM 数量，因为 cuBLAS 的 kernel 选择表按架构分档，同一 shape 在两种架构上可能落到完全不同的实现。

代价在这里已经出现：负载画像越细，需要跑的参考路径组合越多。若画像含 4 个模型族 × 6 个算子 × 5 个 shape × 2 种硬件，参考路径测量点就是 240 组，每组四条路径各 120 次计时（20 warmup + 100 计时），单这一项就是数万次 kernel 调用。这是配方设计时必须先算的预算，而不是事后补测。

二 · 基线选择：四条路径的最优值做分母，而不是“默认路径”

分母的定义是配方里最容易被做错的一步。默认做法是拿 PyTorch 默认前向当分母，但默认前向的数值口径与编译状态是不透明的：allow_tf32 可能为真也可能为假，cudnn.benchmark 可能已开启启发式搜索，torch.compile 可能根本没启用。用这种分母算出的 speedup 既可能虚高（对比了未编译的 eager）也可能虚低（对比了已融合的 compile）。锚定配方要求对每个 shape 分别测四条参考路径，取最快时延作为分母：

$$S_{\text{eff}}=\frac{\min\{T_{\text{eager}},T_{\text{tf32}},T_{\text{compile}},T_{\text{cublas}}\}}{T_{\text{gen}}},\quad \text{valid}=\mathbb{1}\left[\max_i|y_{\text{gen},i}-y_{\text{fp64},i}|\le \tau\right]$$

这个 min 的语义是“生成 kernel 必须打赢该 shape 上最强的已知实现”，而不是打赢一个弱参照。取 min 而非取某一条固定路径，是为了让分母随 shape 自适应：大规整 GEMM 上 cuBLAS 往往最快，融合算子链上 torch.compile 往往最快，小 shape 上 eager 的低 launch 开销可能反而最快。四条路径各有所长，min 把它们压成一个下界。

基线选择还必须带数值口径校验。四条路径里，eager tf32 与 cuBLAS 直调若启用了 TF32，其输出相对 fp64 参考本身就有误差；若生成 kernel 用 fp32 累加打赢了 TF32 基线，speedup 里混入了精度差异，属于不公平比较。因此配方要求：每条参考路径都要对 fp64 参考测一次误差，确认基线未溢出、未意外降精度；若基线本身是 TF32 口径，则生成 kernel 也必须在同等数值口径下计时，或把基线换成 fp32 口径重测。valid 指示函数与 S_eff 必须成对报告，只报 S_eff 不报 valid 的评测等于放弃正确性约束。

具体例子：某 shape 上 eager fp32 时延为基准 1.0，eager tf32 因 TensorCore 路径降到 0.55，torch.compile 因融合降到 0.48，cuBLAS 直调 0.52。若配方只拿 eager fp32 当分母，生成 kernel 只要达到 0.9 就能报出约 1.1× 的“加速”；但按 min 分母 0.48 计，同一个 kernel 实际是 0.9/0.48≈1.9 倍的减速。这就是口径差异被压平前后的量级差别，也是 KernelBench 类评测中常见的虚高来源。反过来，若某 shape 上 cuBLAS 启发式退化到 1.8，而生成 kernel 做到 1.0，min 分母取 0.48（来自 compile）而非 1.8，加速比不会被 cuBLAS 的弱项污染。

代价：四条路径的测量成本是单路径的四倍，且 cuBLAS 直调需要绕过 PyTorch 的 dispatch 层，写独立的调用封装；数值口径校验又要为每条路径额外跑一次 fp64 对比。这些成本换来的是分母的可解释性——每个 speedup 都能追溯到“打赢了哪条路径”。

三 · 输入分布：数值范围、对齐性与 batch 不变性

输入分布决定两件事：数值误差是否触发 valid 失败，以及生成 kernel 的 tiling 是否落在对齐路径上。配方要求输入分布固定并写入 manifest，至少锁定四个维度：数值范围（是否含大幅值导致 fp32 累加溢出）、稀疏/稠密结构（是否有大量零或结构化 mask）、内存布局（行主序/列主序/带 padding 的 stride）、以及对齐性（K 是否为 8 的倍数、指针是否 16 字节对齐）。

数值范围直接关联 TF32 的尾数截断。TF32 保留 10 位尾数，相对 fp32 的 23 位尾数，在累加链较长时误差会累积。若输入分布取标准正态，误差通常在阈值内；若取大幅值加小幅值混合（例如 attention logits 经过 exp 前的量级差异），TF32 基线的误差可能已经接近阈值，此时生成 kernel 若再用 TF32 就会双双越界，valid 全为假，speedup 失去意义。因此配方要求输入分布与阈值 τ 联合标定：τ 要设在“基线自身误差的若干倍”之上，而不是拍一个固定小数。

对齐性是最容易被忽略的一项。cuBLAS 在 K 为 8 倍数时走 TensorCore 整块路径，K 为奇数时退回 SIMT 路径，两条路径的时延可能相差一个量级。若 shape 族里混入奇数 K 而不标注，分母会突然变大，生成 kernel 的相对表现被系统性高估。配方要求每个 shape 标注对齐状态，并把对齐与非对齐 shape 分开统计 speedup，不混在一个平均值里。

batch 不变性在这里的作用是约束输入分布的可复现性：同一 shape 在不同 batch 组织下（例如把 batch 维折叠进 M 或保持独立）应产生一致的数值口径与计时口径。若生成 kernel 对 batch 折叠敏感，说明其 tiling 依赖了具体的 stride 假设，这种敏感性必须在配方里被显式测出，而不是被平均掉。

代价：固定输入分布意味着放弃“随机输入下的统计平均”，每个 shape 只测一组确定性输入，测量方差变小但覆盖面变窄；要补覆盖面就得增加 shape 数，计时成本线性上升。数值范围的标定又需要先跑基线对 fp64 的误差分布，这是一次额外的全量参考测量。

四 · 指标计算：中位数、置信区间与“精度换速度”的隔离

计时口径的细节决定 speedup 是否可复现。配方规定每条路径 warmup 20 次、计时 100 次取中位数。warmup 的作用是让 GPU 时钟爬升到稳态、让 torch.compile 的 autotune 完成、让 cuBLAS 的启发式选择落定；取中位数而非均值是为了抵抗偶发的调度抖动与 GC 干扰。100 次的样本量足以给出中位数的置信区间，配方要求同时报告区间宽度，区间过宽（说明测量不稳）的 shape 要标记为低置信，不参与汇总排名。

指标不止 speedup 一个。配方要求每个 shape 同时记录：生成 kernel 的时延中位数与区间、显存峰值、编译时间（对 torch.compile 路径与 Triton 路径）、以及相对 fp64 的最大绝对误差。显存峰值用于排除“用更大 workspace 换速度”的隐性代价；编译时间用于暴露“autotune 很久但稳态很快”的路径——这类路径在单次评测里占优，在生产端到端里可能因编译开销被抵消。误差则直接喂给 valid 指示函数。

“精度换速度”的隔离是配方里最关键的判定逻辑：若生成 kernel 时延优于 min 分母，但误差超阈值 τ，则标记为“精度换速度”，不计入有效加速。这条规则防止生成 kernel 通过降精度（例如把 fp32 累加换成 fp16 累加、或跳过某些归约步骤）来骗取 speedup。实现上，valid 与 S_eff 必须联合报告：有效加速 = S_eff × valid，无效的 speedup 只作为诊断信息保留。

具体例子：某归约算子上，生成 kernel 用 fp16 中间累加把时延压到 min 分母的 0.7，S_eff≈1.4，但对 fp64 参考的最大误差超出 τ，valid=0，有效加速记为 0。配方不会把这个 1.4 计入排名，但会把它写进诊断日志，提示“该 kernel 的 tiling 思路可用，但累加精度需改回 fp32”。这正是把速度与正确性解耦报告的价值：既不埋没可复用的结构创新，也不让不合规的速度污染排名。

代价：100 次计时 × 四条路径 × 每个 shape，加上 fp64 参考对比与显存采样，单 shape 的测量开销约为单路径单次计时的数百倍；置信区间与编译时间的记录又要求评测框架在计时之外维护额外的采样通道，框架复杂度上升。

五 · 缓存污染与跨机复现：配方里的两个隐性陷阱

torch.compile 的 autotune 缓存是配方里最隐蔽的污染源。同一 shape 第一次编译时，autotune 会枚举多个候选实现并计时选优，这个过程的耗时被计入编译时间；但缓存一旦落盘，后续测量直接命中缓存，基线时延偏低，分母被系统性压低，生成 kernel 的 speedup 被系统性高估。配方要求每个 shape 测量前清空 autotune 缓存，或使用独立的缓存目录隔离，确保分母是在“冷编译”口径下测得的。若配方要报告稳态性能而非冷启动性能，则必须显式声明“缓存已预热”，并把编译时间单独列出，不能把两者混为一个数。

跨机复现是第二个陷阱。基线时延受 GPU 型号、驱动版本、cuBLAS/cuDNN 版本共同影响，同一 shape 在不同机器上可能落到不同的 cuBLAS kernel。配方要求把 CUDA/cuBLAS/cuDNN/PyTorch 版本与 GPU 型号写入 manifest，禁止运行时升级；跨机器复现时，全部参考路径必须在新机器上重跑，不能沿用旧机器的分母。这一点与容器镜像固定是同一件事的两面：镜像锁定软件栈，manifest 锁定硬件栈，两者合起来才构成可复现的分母。

具体例子：某 shape 在机器 A 上 cuBLAS 选中了 split-K 实现，时延 0.52；在机器 B 上因 SM 数量不同选中了非 split-K 实现，时延 0.71。若配方沿用机器 A 的分母去评机器 B 上生成的 kernel，speedup 会被高估约 1.37 倍。重跑全部参考路径后，分母回到 0.71，speedup 回到真实水平。这个例子的教训是：分母不是常数，是硬件与软件栈的函数。

代价：每 shape 清缓存意味着 autotune 开销在每次测量中重复支付，单 shape 的基线测量时间显著上升；跨机重跑全部参考路径则把复现成本从“跑生成 kernel”扩大到“跑生成 kernel 加四条基线”，在机器数量多时是线性放大的开销。

六 · 负载不对时的失效模式：三种可诊断的偏差

负载画像与配方不匹配时，评测不会报错，只会安静地给出错误结论。配方要求把三类失效模式写成可诊断的检查项，而不是靠事后人工怀疑。

第一类是“分母过弱导致的虚高”。当 shape 族集中在 cuBLAS 退化区（小 batch GEMV、非对齐 K、grouped GEMM），min 分母被 eager 或退化的 cuBLAS 占据，生成 kernel 只要不退化就能报出可观 speedup。诊断方法是检查每个 shape 的 min 分母来自哪条路径：若大量 shape 的分母来自 eager 而非 cuBLAS/compile，说明负载落在甜区之外，speedup 的可迁移性存疑，应补充甜区 shape 再汇总。

第二类是“分母过强导致的虚低”。当 shape 族全是大规整 GEMM，cuBLAS 已接近 SOL，生成 kernel 的加速空间被物理上限封死，speedup 普遍接近 1 甚至小于 1。这不代表生成 kernel 差，而是负载没有给融合与调度留出空间。诊断方法是看生成 kernel 的时延是否已接近 roofline 预测的 SOL：若已接近，则虚低是负载选择的结果，应补充融合算子与退化 shape 来恢复鉴别力。

第三类是“口径漂移导致的不可比”。当输入分布的数值范围、对齐性、或基线数值口径（TF32 vs fp32）在不同 shape 间不一致时，speedup 之间不可比，汇总平均值没有意义。诊断方法是把每个 shape 的口径标签（数值范围档、对齐状态、基线精度口径）与 speedup 一起输出，任何标签不一致的 shape 不得进入同一张排名表。

具体例子：某配方在 12 个 shape 上汇总平均 speedup 为 1.6，拆开看发现 9 个 shape 的分母来自 eager（甜区外），3 个来自 cuBLAS（甜区内）。甜区内的 3 个 shape 平均 speedup 仅 1.02，甜区外的 9 个平均 1.8。汇总值 1.6 既不描述甜区内的真实水平，也不描述甜区外的可迁移性，它是一个被负载构成稀释掉的数。配方要求按分母来源分层报告，正是为了避免这种稀释。

这三类失效模式的共同代价是：诊断本身需要额外的元数据采集（分母来源、口径标签、SOL 接近度），评测框架要为每个 shape 维护一张元数据表，并在汇总时执行分层规则。不做这层元数据，配方就只能给出一个无法解释的平均数；做了这层元数据，配方给出的是一张可追溯到具体负载与具体基线的分层表，这才是锚定基线在工程上真正的产出形态。
