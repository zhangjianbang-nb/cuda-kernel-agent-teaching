一 · 负载选择：先定“能测出能力差”的算子族

仅目标驱动基线的负载选择不是“找一个 kernel 跑通就行”，而是要让负载本身具备能力分辨力：在无提示条件下，不同模型、不同轮次之间必须产生可观测的 SOL 与正确性差异。若负载过于平凡（逐元素加法、简单 copy），几乎所有模型一轮就能摸到带宽上限，capability 恒为 1，基线失去区分度；若负载过于依赖冷门硬件特性（如特定架构的 TMA 描述符细节、非公开的 swizzle 约束），模型先验知识几乎为零，收敛完全靠随机试探，测到的是“猜中率”而非优化能力。可用的负载区间是：语义清晰、契约可形式化、性能上界可由 roofline 界定，但达到上界需要至少一次非平凡的结构决策——分块尺寸、共享内存布局、寄存器压力与 occupancy 的权衡、warp 级归约方式。

按算子族划分，适合纳入基线负载的是三类。第一类是带宽受限的归约/归一化族（row-wise softmax、layernorm、RMSNorm、reduce-sum），其 SOL 由全局内存流量决定，模型必须自己决定是否做向量化加载、是否用两级归约、block 内是否走 shared memory；这类负载的失败模式典型且可诊断，适合观察 agent 是否主动 profile。第二类是计算受限的 GEMM 变体（不同 M/N/K 比例、batch 维、转置组合），它迫使模型面对 tile 选择与流水线深度的组合空间，是区分“会写 CUDA”与“会调 CUDA”的关键负载。第三类是融合算子（如 bias+GELU、residual+norm），其收益来自减少中间张量的往返流量，模型需要自行判断融合边界，这类负载最能暴露“只改局部、不做全局流量分析”的弱点。

不适合的负载要明确排除：依赖库调用即可完成的算子（直接调 cuBLAS 就达标，测的是“知道调库”而非 kernel 能力）；形状极端到只有一种合法切分方式的算子（决策空间退化为 1）；以及正确性契约本身模糊的算子（如带随机性的 dropout，oracle 成本高于性能收益）。负载清单应写成“算子语义 + 契约 + 参考实现 + 目标阈值”的四元组，其中参考实现只用于计算 SOL 分母与正确性比对，不得暴露给 agent，否则等于变相注入提示。

二 · Shape 与输入分布：固定集合会过拟合，必须分层

shape 设定直接决定基线是否可复现、是否可比较。单一固定 shape 的问题是模型可以把 tile 尺寸硬编码到刚好匹配该 shape，一轮达标却在邻近 shape 上崩溃；这与“提示过拟合基准”是同一类病，只是过拟合发生在数据侧。因此基线负载的 shape 应组织为分层集合：一个公开的标称 shape（agent 可见，用于开发与自测），加一组隐藏的邻近 shape（同量级但边界不同，如 K 不是 tile 整数倍、M 很小 N 很大、含奇数尾块），再加一组跨量级 shape（用于检验泛化而非调优）。评分只在隐藏集合上计算，标称 shape 仅用于让 agent 有可编译可运行的对象。

输入分布的设定要区分“数值分布”与“结构分布”。数值分布影响正确性 oracle 的严格度：全零、全一、均匀随机、大幅值混合、含 NaN/Inf 的边界输入，分别检验不同的数值路径。对归约类算子，大幅值混合输入会放大累加顺序带来的误差，此时 fp64 参考与容差设定必须与之匹配（容差机制本身由 oracle 片段承担，此处只强调：输入分布是容差的前置条件，分布换了容差不变就是错的）。结构分布影响性能：稀疏/密集、对齐/非对齐、连续/带 stride 的视图，会改变向量化加载是否可行。基线应至少包含一组非对齐输入，因为对齐假设是模型最容易硬编码且最不容易自查的隐含前提。

代价在这里是可量化的：隐藏 shape 集合每扩大一倍，评测的编译与运行次数翻倍，单模型评测的墙钟时间与 GPU 占用线性上升；若隐藏集合含跨量级 shape，编译时间（尤其模板实例化与 CuTe 布局推导）会成为主要开销而非 kernel 执行本身。工程判断是：隐藏集合控制在个位数到十余个 shape，按“邻近边界”优先而非“数量优先”选取，把预算花在能暴露硬编码的 shape 上，而不是均匀撒点。

三 · 基线锚定：参考 kernel 与阈值的选取决定 capability 的含义

仅目标驱动基线给 agent 的目标是“达到参考 kernel 的 x%”，这个 x 不是随便定的常数，而是基线锚定的产物。锚定分两层：性能锚与正确性锚。性能锚取同一硬件上成熟实现（厂商库或人工调优 kernel）的实测 SOL 作为分母，阈值 x 应设在“明显高于朴素实现、明显低于成熟实现”的区间——太低则朴素实现即可达标，负载失去优化意义；太高则只有复现专家技巧才能达标，而基线恰恰禁止注入技巧，结果是全员失败、方差为零。正确性锚则是参考实现与 fp64 参考的比对容差，它必须独立于性能锚设定，不能因为性能阈值高就放松正确性。

阈值的选取还要与评分公式对齐。capability 定义为达标率：

$$\text{capability}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\left[\text{correct}_i\land \text{SOL}_i\ge \theta\right],\quad \text{cost}=\frac{1}{N}\sum_i \text{tokens}_i$$

其中 θ 是归一化后的 SOL 阈值，N 是负载实例数（算子 × shape 的组合）。这个定义是硬阈值：SOL 差一点与差很多在 capability 上等价，因此 θ 的位置必须落在能力分布的分界处，否则大量实例挤在阈值两侧会造成评分对微小噪声敏感。工程上应先用少量模型跑一轮，观察 SOL 的分布形态，再把 θ 放在分布的低密度区；这一步本身不引入提示，只是校准评测配方。代价是：θ 校准需要额外评测轮次与 GPU 时间，且校准集与最终评测集必须分离，否则 θ 又被过拟合。

具体例子：对一个 row-wise softmax 负载，朴素实现每行一个线程串行归约，成熟实现做两级归约加向量化加载。若把 θ 设在朴素实现的 SOL 附近，任何会写 block 归约的模型都达标，capability 饱和；若设在成熟实现的 95% 以上，则要求模型自行发现向量化宽度与 block 尺寸的匹配关系，这在无提示条件下是真实的能力门槛。基线应选后者，并接受由此带来的低达标率——低达标率正是“原生能力”的诚实读数。

四 · 指标计算：SOL 归一、token 成本与轮次的联合口径

指标口径必须一次定死，否则不同模型、不同批次的基线不可比。三个量：SOL、token、轮次。SOL 的计算需要固定分母来源（同一硬件、同一参考实现、同一测量方法），并且要明确测的是端到端 kernel 时间还是含 launch 开销的时间；对短小 kernel，launch 开销占比高，若口径不统一，模型可以通过减少 launch 次数“刷”指标而非真正优化。token 成本按公式中的 cost 累计，覆盖 agent 的全部交互（读文档、写测试、改代码、看 profile 输出），而不只是生成的代码 token；这一点决定了基线能否反映“自主诊断”的真实开销。轮次则记录从首次提交到达标（或预算耗尽）的迭代数，它是收敛速度的直接度量。

三者的联合口径要防止指标互相掩盖。一个模型可能用极少 token、极少轮次达标，也可能用大量 profile 轮次换来高 SOL；单看 capability 无法区分。基线报告应给出 (capability, cost, 轮次分布) 三元组，并在负载层面记录“未达标实例的 SOL 分布”，因为失败实例的 SOL 高低反映了模型是“方向错”还是“差最后一脚”，这对后续用轨迹做 SFT/RL 的数据筛选至关重要。伪代码层面的记录结构应类似：每个实例一行，字段为算子、shape、是否 correct、SOL 归一值、累计 token、轮次、终止原因（达标/预算耗尽/编译失败/超时）。终止原因必须单列，编译失败与性能不达标是两种完全不同的能力缺陷。

代价在于测量本身：NCU 采集会显著拖慢执行并改变缓存行为，若每个实例都做全量 profile，评测墙钟时间会成倍上升；若只在达标实例上采集，又丢失了失败实例的诊断信息。折中做法是对失败实例做轻量采集（仅关键计数器），对达标实例做一次完整采集用于归档。另一个代价是 token 计量依赖 agent 脚手架的上报，若脚手架本身有重试或截断逻辑，token 会被低估，基线必须固定脚手架版本并把计量点放在工具调用边界。

五 · 负载不对时的失效形态：从“虚高”到“全员零分”

负载与配方设定错误时，基线的失效不是随机噪声，而是有固定形态的。第一种是饱和型虚高：负载太简单或 θ 太低，capability 接近 1，模型间无差异，基线看似“模型都很强”，实则测的是“会写能跑的 CUDA”。第二种是地板型零分：θ 过高或负载依赖未公开的硬件细节，所有模型 capability 为 0，方差为零，基线无法排序，也无法提供有意义的失败轨迹。第三种最隐蔽，是shape 过拟合型虚高：标称 shape 上达标率很高，隐藏邻近 shape 上骤降，合并统计后 capability 中等，看起来“还行”，实际是模型把 tile 尺寸硬编码到了标称 shape 的整除关系上。第四种是口径漂移型不可比：SOL 分母换了参考实现、token 计量点变了、或 NCU 采集策略在批次间不一致，导致同一模型两次评测的 cost 与 SOL 不可比。

识别这些形态需要固定的诊断量：达标实例的 SOL 与 θ 的间距分布（判断是否饱和）、未达标实例的终止原因构成（判断是否地板）、标称与隐藏 shape 的达标率差（判断是否过拟合）、以及同一模型重复评测的方差（判断口径是否稳定）。这些量不进入 capability 公式，但必须随基线一起报告，否则读者无法判断一个 capability 数字是否可信。工程判断是：capability 是结果，诊断量是可信度，只报结果不报诊断量的基线不具备比较价值。

具体代价举例：若隐藏 shape 集合设计不当，含大量非整除尾块，模型在标称 shape 上达标后直接在这些 shape 上编译失败或越界，评测表现为大量“编译失败”终止原因，capability 被拉低，但这反映的是负载边界设定过苛而非模型能力不足。修正方式是让隐藏集合的边界难度分层，并在报告中分列“整除 shape 达标率”与“非整除 shape 达标率”，把结构泛化能力单独呈现，而不是混进一个标量。

六 · 硬件维度与配方固化：同一基线跨卡不可直接比

硬件选择是配方的一部分，不是背景参数。同一负载在不同卡上的 roofline 位置不同：带宽受限算子在带宽比高的卡上更容易触顶，计算受限算子在算力比高的卡上对 tile 与流水线更敏感。因此 θ 的绝对值不能跨卡复用，SOL 归一必须绑定“卡 + 参考实现 + 测量方法”三元组。基线配方应显式记录：目标架构、可用 SM 数与每 SM 资源上限、内存带宽与容量、是否允许使用该架构特有的指令或描述符。禁止事项也要写清：是否允许调库、是否允许内联 PTX、是否允许使用框架提供的融合模板——这些边界直接改变能力门槛，且必须在所有模型间一致。

配方固化的另一层是工具集边界。仅目标驱动基线只暴露编译、运行、NCU 采集三个原语，这意味着 agent 拿不到“优化技巧清单”，但也拿不到“上一次成功配置”的记忆。若评测框架在会话间保留了历史 kernel 或缓存，模型可能间接获得提示，基线就被污染。固化配方要求每次评测从干净工作目录开始，工具输出只含原始编译日志与计数器，不含人工解读。代价是：干净环境使编译时间重复付出，模板重的负载（CuTe 布局）编译开销可能超过 kernel 执行时间，评测吞吐下降；但这部分开销必须计入 cost 的墙钟侧，不能隐去。

最后的工程判断落在“负载—阈值—口径”三者的耦合上：负载决定能力门槛的形状，阈值决定门槛的位置，口径决定读数是否可比。三者任一漂移，capability 这个标量就失去意义。因此基线发布时应把三者作为不可分割的配方单元冻结，任何一次负载增删、θ 调整或计量点变更都必须视为新基线版本，旧版本的 capability 数字不得与新版本并列比较。这不是保守，而是让“纯模型能力”这个读数在跨模型、跨批次比较中保持可解释性的最低条件。
