一 · 变异体生成：从参考 kernel 到可判定输入

变异审计的第一步不是跑 checker，而是把参考实现变成一组“已知必然错误”的输入。参考 kernel 在这里充当种子，变异算子在其语义结构上做定向扰动，产出变异体集合 M。工程上可落地的算子分四族：边界条件翻转（把 i < N 改成 i <= N、把尾块处理分支删掉）、累加顺序打乱（把串行归约改成树形归约或反之，改变浮点结合律下的结果）、dtype 截断（中间累加从 fp32 降到 fp16 或 tf32，制造精度损失）、索引偏移 ±1（把 tile 起始偏移或 shared memory 写回下标整体平移）。每族对应一类真实工程 bug，而不是随机字节翻转——随机翻转大多触发编译失败或段错误，对 checker 的语义检错能力没有区分度。

每个变异体的输入是一个三元组：变异后的 kernel 源码、它应当产出的错误输出（由变异体自身运行得到）、以及参考输出。判定“这个变异体是否应当被 kill”不依赖人工标注，而依赖构造时的语义约定：只要变异改变了数学语义，其输出就应当偏离参考输出超过 checker 的容差。这里有一个容易被忽略的代价：变异体构造需要领域知识，且构造过程本身要保证变异体可编译、可运行、不越界访问。一个索引偏移变异若把访存推出分配边界，会触发非法访存而非产生错误数值，这类变异体必须被剔除，否则 kill rate 会被污染成“因崩溃而被判错”，虚高。

$$\mathcal{M}=\{m_1,\dots,m_n\},\quad m_i=(\text{src}_i,\ \text{out}_i^{\text{mut}},\ \text{out}^{\text{ref}})$$

具体例子：一个 softmax 参考 kernel，把行内最大值减去的步骤删掉（数值稳定性变异），在输入含较大正值时输出会溢出成 inf；把 exp 的累加从 fp32 改成 fp16（dtype 截断变异），在长行上相对误差抬升。前者是覆盖型漏洞——checker 若只比对 top-1 索引就完全漏检；后者是容差型漏洞——checker 若容差设成 1e-2 就会放过。两类变异体必须同时存在于集合中，否则分组报告无法区分“容差太松”与“覆盖不足”。

二 · 逐变异体执行 checker：一次判定的完整流动

对每个变异体，流程是：编译变异体 → 在固定输入上运行得到 out_i^mut → 把 out_i^mut 与 out^ref 一起喂给被测 checker → 记录 checker 返回的布尔判定。这里 checker 是被审计对象，不是工具；它的输入是两份输出张量（或输出加中间量），输出是 Pass/Fail。判定的语义必须是“这个变异体是否被识别为错误”，即 Checker(m)=Fail 记为一次 kill。

这一步的代价结构值得拆开看。编译代价：每个变异体一次 nvcc 编译，若变异体数量在 50–200，编译时间随集合线性增长，且 CUDA 编译单次常在数秒到数十秒量级，整轮审计的墙钟时间会被编译主导而非执行主导。执行代价：每个变异体要在与参考相同的输入分布上跑一遍，若输入含隐藏 shape 抽样，则执行次数还要乘以抽样数。判定代价：checker 本身的比对是 O(输出元素数) 的带宽受限操作，对大输出张量（如 attention 的完整 score 矩阵）会成为显存带宽瓶颈。三项相加，审计成本随变异体数量线性增长，这是该方法无法绕开的固有开销。

伪代码思路：

  • 对 m in M：编译 m.src，失败则标记 invalid 并从分母剔除；
  • 运行 m 得到 out_mut，若运行崩溃或产出 NaN 且参考无 NaN，仍按语义约定计入应 kill；
  • 调用 checker(out_mut, out_ref)，记录返回值与耗时；
  • 按变异族聚合，得到每族的 kill 计数与漏检计数。

具体例子：一个 reduction kernel 的变异体把 block 内归约的 shared memory 同步去掉，产生竞态，输出在不同运行间抖动。checker 若只跑一次比对，可能因抖动偶然落在容差内而漏检；这类变异体的判定需要多次运行取最坏偏离，代价是执行次数翻倍。这说明“每个变异体跑一遍 checker”在竞态类变异上并不充分，需要在流程里显式加入重复采样。

三 · KillRate 聚合与分组报告：把标量拆成诊断向量

聚合公式给出一个标量，但标量本身不指导修补。真正有用的是按变异族分组后的 kill rate 向量，它把“checker 不行”翻译成“checker 在哪一类语义扰动上不行”。

$$\text{KillRate}=\frac{|\{m\in\mathcal{M}:\text{Checker}(m)=\text{Fail}\}|}{|\mathcal{M}|},\quad \text{CheckerOK}=\mathbb{1}[\text{KillRate}\ge\kappa]$$

分组口径与变异算子族一一对应：边界族、归约顺序族、dtype 族、索引族。若边界族 kill rate 高而归约顺序族低，说明 checker 的容差对浮点结合律差异过于宽松，修补方向是收紧相对误差阈值或引入逐元素比对而非仅比对归约标量。若 dtype 族低而边界族高，说明 checker 只覆盖了数值范围而没覆盖精度，修补方向是增加对低位宽输出的敏感度，例如在容差里引入与 dtype 位宽挂钩的缩放。若索引族低，通常意味着 checker 只比对部分输出（如只比对首行或采样点），修补方向是扩大比对覆盖到全张量或按结构化采样覆盖边界 tile。

这里有一个统计代价：分组后每族的样本数变小，kill rate 的估计方差上升。50–200 个变异体分到四族，每族十余到五十个，单族 kill rate 的置信区间不可忽略。工程判断是阈值 κ 应作用于总体 kill rate，而分组向量用于诊断而非独立门控；否则会出现某族因样本太少而误判。另一个代价是人工复核：对漏检变异体逐个复核需要工程师阅读变异 diff 与输出偏离，复核成本与漏检数成正比，漏检越多修补工作量越大，这是审计流程里唯一不可自动化的环节。

具体例子：某 checker 总体 kill rate 达标，但分组显示 dtype 族漏检集中在中位数以上的长行归约上。复核发现 checker 的容差按绝对误差设定，长行累加使绝对误差随长度增长而超出阈值，于是 fp16 截断变异被放过。修补是把容差改为相对误差加长度缩放因子，重跑该族变异体后 kill rate 抬升。这个例子说明标量达标不等于 checker 可信，分组向量才是修补的入口。

四 · 漏检复核与 checker 修补：闭环的收敛条件

复核的目标不是逐个人工判定“这个变异体该不该 kill”，而是把漏检归因到 checker 的具体缺陷类型，再落到可执行的修补动作。归因分三类：容差过松（数值偏离在容差内）、覆盖不足（checker 根本没看这部分输出）、判定逻辑错误（checker 的比较方向或聚合方式写错，例如把 allclose 写成 anyclose）。三类对应三种修补：调容差、扩覆盖、改判定。修补后必须重跑全量变异体集合，而不是只跑漏检的那几个——容差收紧可能让原本通过的变异体变成误杀（把正确 kernel 判错），这是修补的副作用代价。

误杀代价在审计里常被低估。checker 收紧后，参考实现自身在浮点非确定性下可能落在新容差之外，导致正确 kernel 被 kill，进而污染 RL 奖励管线——正确解拿不到奖励。因此修补的收敛条件是双向的：kill rate 上升的同时，参考实现与已知正确变体（如等价重写、不同 tile 划分但数学等价）必须全部 Pass。这要求变异体集合里除了“应 kill”的错误变异，还要有一小组“应 pass”的等价变体作为阴性对照，否则单边收紧容差会一路把 kill rate 推到 100% 却让 checker 失去可用性。

伪代码思路：

  • 对漏检集合 L 中每个 m，记录偏离张量的最大相对误差、偏离位置分布、checker 实际比对的元素子集；
  • 若偏离在容差内 → 调容差；若偏离位置不在比对子集 → 扩覆盖；若比对逻辑与预期不符 → 改判定；
  • 重跑 M 全量加阴性对照集，要求 kill rate 与对照 pass rate 同时达标；
  • 未达标则回到归因，迭代。

具体例子：一个 matmul checker 只比对输出矩阵的对角块，索引偏移变异把非对角块写错却漏检。复核发现偏离集中在非对角块，归因为覆盖不足，修补是把比对扩展到全矩阵并按 tile 采样保证边界 tile 被覆盖。重跑后索引族 kill rate 抬升，但阴性对照里一个不同 tile 划分的等价实现因浮点累加顺序差异出现微小偏离，需要同时把容差从绝对误差改为带 K 维缩放的相对误差，才让对照通过。这一步的代价是容差公式变复杂，checker 自身的实现风险上升，需要再对 checker 做一次自检。

五 · 进入奖励管线的门控：阈值、成本与失效模式

只有 kill rate ≥ 阈值（如 95%）的 checker 才允许进入 RL 奖励管线。门控的意义在于：奖励信号的可信度直接决定策略优化的方向，一个漏检率高的 checker 会把错误 kernel 判为正确并给出正奖励，策略会收敛到“骗过 checker”而非“算对”。门控把这一风险量化为一个可审计的数字，而不是靠人工信任。

门控的代价是评测预算。每个候选 checker 版本都要跑全量变异体集合，50–200 个变异体乘以编译、执行、比对三项成本，单轮审计的 token 与墙钟开销在奖励管线里是固定税。工程判断是把审计放在 checker 变更时触发而非每次奖励计算时触发：checker 一旦通过门控就冻结，变异体集合随新发现的漏洞模式增量扩充，扩充后重跑全量。这样审计成本与 checker 变更频率成正比，而非与训练步数成正比。

失效模式有三类需要显式防范。其一，变异体集合覆盖不全导致 kill rate 虚高——checker 在集合内表现完美，集合外一触即溃；对策是持续扩充变异算子库，并把线上发现的漏检案例回流成新变异体。其二，变异体本身构造错误，把正确行为标成应 kill，导致 checker 被误判为不合格而反复修补；对策是每个变异体构造后先人工确认其语义确实偏离。其三，阈值 κ 的设定与任务容差耦合——对低精度 kernel 任务，95% 的 kill rate 可能过严，因为部分变异体的偏离本就落在任务允许误差内；此时应按任务精度档位分设阈值，而非全局一刀切。

具体例子：某团队在奖励管线里用一个只比对输出均值的 checker，变异体集合里恰好没有“均值不变但分布错误”的变异（如把方差压小的归约变异），kill rate 达标并放行。训练中策略学会了输出正确均值但错误分布的 kernel，端到端精度下降。回流后新增分布敏感变异体，checker 的 kill rate 在该族上暴露短板，门控才真正拦住。这说明门控的可信度上限由变异体集合的覆盖面决定，阈值只是把这一上限显式化。

变异体预算与“虚高 kill rate”的边界

这一步的输入是参考 kernel 与其测试输入，输出是一张按变异类型分组的 kill 表；代价是 checker 执行次数等于变异体数量，评测时延随 |M| 线性增长。变异算子库覆盖不全时，kill rate 会被系统性抬高：若某类错误（例如跨 tile 边界的漏算）根本没有对应变异体，checker 对该类缺陷的漏检不会出现在分母里，于是 CheckerOK 判真而实际检错能力不足。因此阈值 κ 必须与变异算子库的覆盖面一起审计，而不是单独看一个标量。

$$\text{KillRate}=\frac{|\{m\in\mathcal{M}: \text{Checker}(m)=\text{Fail}\}|}{|\mathcal{M}|},\quad \text{CheckerOK}=\mathbb{1}[\text{KillRate}\ge \kappa]$$

失效条件集中在两处。其一是变异体与参考实现语义等价：例如把归约顺序打乱但 checker 用高精度累加比对，此时变异体本不该被 kill，却拉低了 kill rate，造成误判——需要人工复核把这类变异体从分母剔除。其二是变异体过于“显眼”：索引偏移 ±1 往往直接触发越界或大规模数值偏差，checker 轻易捕获，而真正危险的精度截断型变异体（fp32 累加改 fp16 中间量）在小规模输入下误差落在容差内，属于典型漏检，必须单独构造接近容差边缘的输入才能暴露。

变异类型典型漏检原因修补方向
边界条件翻转测试输入未覆盖尾块补非整除尺寸用例
归约顺序打乱容差过松收紧相对误差
dtype 截断只比对部分输出全量比对 + 边界值

工程判断上，变异体数量通常取 50–200 个，超过这个量级后边际信息量下降而 checker 调用成本线性上升；更划算的做法是按变异类型分层抽样，保证每类至少若干个体，并把 kill rate 的分组报告作为进入 RL 奖励管线的硬门槛，而非只报一个总数。
