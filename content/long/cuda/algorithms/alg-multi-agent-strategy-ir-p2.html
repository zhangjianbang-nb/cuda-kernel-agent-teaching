一 · 分析步：从 profile 与源码到策略 IR 的落笔

流动的第一步不是生成代码，而是把“为什么改”写成可被下游机械读取的结构。分析 agent 的输入是两样东西：一份该 kernel 的 profile 切片（NCU 的 SOL 分项、occupancy 受限原因、warp stall 分布）与源码本身（含 launch 配置、tile 尺寸、循环结构）。它的输出是一条策略 IR，字段至少包含瓶颈分类、候选动作列表、约束三元组。瓶颈分类不是自由文本，而是枚举：memory-bound / compute-bound / latency-bound / occupancy-limited，四者互斥优先。候选动作列表是有序集合，每个动作带一个可执行语义标签，例如“把 A 的 tile 从 64×64 提到 128×64”“把 B 的加载改成 cp.async 双缓冲”“把归约从 shared 改成 warp shuffle”。约束是硬边界：寄存器上限、共享内存上限、目标占用率下限。

这一步的代价结构很特殊：它几乎不花 GPU 时间，但花的是“读”的 token 与人工 schema 设计成本。分析 agent 必须把 profile 的数值翻译成动作，而翻译规则不在模型权重里，在 IR schema 里。schema 不覆盖的动作无法表达——这是本步最大的正确性代价：一个真实存在的优化（比如把 bank conflict 用 padding 消掉）如果 schema 里没有对应标签，分析 agent 只能要么硬塞进最近的标签造成语义漂移，要么放弃该动作，导致后续所有 agent 都在一个被裁剪过的动作空间里搜索。

$$\text{IR}=\langle \text{Bound},\ \mathcal{A}_{\text{cand}},\ \mathcal{C}_{\text{res}},\ \text{reward}\rangle,\quad \text{Conflict}=\mathbb{1}\left[\exists a\in\mathcal{A}:\ \text{Code}(a)\not\equiv\text{IR}(a)\right]$$

公式里的 Conflict 指示函数是整条流水线的健康指标，而分析步是它第一次可能被点亮的地方：若分析 agent 写入的动作在约束下不可实现（例如 tile 提到 128×64 会突破共享内存上限），编码 agent 要么违反约束、要么静默降级，两者都会在评审步暴露为 Code(a) 与 IR(a) 不等价。具体例子：一个 reduction kernel 的 profile 显示 shared memory 带宽打满、寄存器余量充足，分析 agent 写“改用 warp shuffle 归约”并附约束“共享内存 ≤ 32KB”。若它同时保留了旧的 shared 缓冲声明，编码 agent 会照抄声明，评审 agent 就会在“动作声明为消除 shared 使用”与“代码仍分配 shared”之间打出 Conflict=1。这一步的工程判断是：分析 agent 的输出必须自带可证伪性，动作标签要能映射到代码里的可观测差异（分配、指令、launch 参数），否则评审步无从机械校验。

二 · 编码步：IR 动作到代码参数的逐条投影

编码 agent 的输入是整条 IR，输出是一份 Triton 或 CUDA 源文件加 launch 配置。它的核心纪律是“逐条投影”：IR 里每个动作必须落到代码里一个具体、可定位的参数或语句。动作“tile 128×64”对应 BLOCK_M/BLOCK_N 常量；动作“cp.async 双缓冲”对应一个 stage 数与 async copy 调用；动作“warp shuffle 归约”对应去掉 shared 数组、换成 __shfl_down_sync。投影不是自由创作，编码 agent 不允许引入 IR 未声明的结构性改动——这是策略与代码解耦的代价：表达力被 IR 锁死，任何 IR 外的优化都必须先回到分析步补写动作。

本步的代价是编译时间与 token。Triton 路径下，一次编译要经历 TTIR→TTGIR→LLVM IR 多级下降，BLOCK 常量变化会触发整条下降链重跑；CUDA 路径下 nvcc 的模板实例化随 tile 与 stage 数组合爆炸。多 agent 串行意味着编码步不能与分析步并行（它必须读 IR），单轮延迟因此叠加。token 消耗集中在“把 IR 翻译成代码”的长上下文：IR 本身短，但编码 agent 需要携带源码骨架、约束与历史 diff，三者叠加使单次调用显著重于单 agent 的直接生成。

具体例子：IR 声明三个动作——tile 128×64、双缓冲 stage=3、寄存器上限 128。编码 agent 生成 Triton kernel 时把 num_stages 设为 3，但 Triton 的自动流水在 stage 增大时会提高寄存器压力，可能越过 128 上限。此时编码 agent 面临选择：违反约束交代码，或在代码里加 maxnreg 限制导致 spill。前者在评审步被约束校验打回，后者在执行步表现为 local memory 流量上升、时延变差，reward 字段记下负值。这就是“动作—参数—代价”三者在编码步的耦合：一个 IR 动作的代价不是它在纸面上的语义，而是它在目标后端上引发的资源再分配。工程上，编码 agent 应把每个动作的投影写成带注释的映射表（动作标签→行号/参数名），供评审 agent 直接比对，而不是让评审去猜。

三 · 评审步：按 IR 做机械等价性检查

评审 agent 的输入是 IR 与编码 agent 交出的代码，输出是二值判定加差异标注。它不做性能判断，只做“代码是否实现了 IR 声明的动作”的等价性检查。检查分三层：结构层（launch 配置、tile 常量、stage 数是否与 IR 数值一致）、语句层（IR 声明的指令类别是否出现在代码中，如 async copy、shuffle、padding 声明）、约束层（静态可估的寄存器/共享内存是否越过 IR 上限）。三层全过则放行到执行步；任一层不过则打回，并把差异写成结构化 diff 附在 IR 上，供下一轮分析 agent 读取。

这一步是把“语义漂移”变成可计算量的关键。多 agent 无共享表示时的典型失败是：分析 agent 说“减少 shared 使用”，编码 agent 理解成“减少 shared 声明但保留读写”，评审 agent 若只读自然语言就会放过，最终执行步性能不升反降，而没人知道是哪一环错了。IR 把动作标签化后，评审可以问一个确定性问题：代码里是否还存在对 shared 数组的写？若 IR 动作为“消除 shared 归约”，答案必须是“否”。这就是 Conflict 指示函数的落地：它不比较自然语言，比较的是代码可观测特征与 IR 声明。

代价在于评审的覆盖边界。静态检查能覆盖 tile、stage、指令类别与声明式约束，但覆盖不了“动作是否被正确实现”的语义层——例如 IR 说“双缓冲”，代码里确实有两个 buffer，但同步点放错导致数据竞争。这类缺陷静态评审抓不到，只能落到执行步的正确性 oracle。评审步的另一个代价是延迟：它必须等编码步完成才能启动，串行链上再添一环。具体例子：IR 动作“把 B 的加载改成 cp.async 双缓冲”，编码 agent 写了 cp.async 但只开了一个 stage，评审的结构层立刻发现 stage 数与 IR 不符，打回并标注“声明 stage=2，实现 stage=1”。这个 diff 比任何自然语言反馈都更可执行，下一轮编码 agent 直接按 diff 修，不需要重新推理意图。

四 · 执行步：正确性与计时写回 reward

执行 agent 的输入是评审放行的代码与 IR 里声明的约束，输出是两项事实：正确性判定与计时结果，二者写回 IR 的 reward 字段。正确性判定不是自造 oracle，而是调用既有的参考实现比对（fp64 参考、隐藏 shape 抽样、batch 不变性门等由其他环节提供，这里只负责触发与收集）。计时则要固定测量协议：warmup 次数、重复次数、是否含 launch 开销、是否用 CUDA event 而非 wall clock。reward 字段不是单一标量，而是带结构的记录：时延、相对基线的比值、是否触发约束违反（如 spill 导致的 local memory 流量）、正确性通过与否。

本步的代价最直接：GPU 时间与显存。一次正确性比对要跑参考实现与候选实现两遍，隐藏 shape 抽样若覆盖多个尺寸则成倍放大；计时需要重复执行以压掉噪声，warmup 本身也占卡时。多 agent 串行下，执行步是唯一真正占 GPU 的环节，其余三步都在等它。token 代价反而低——执行 agent 的输出是数值，不是长文本。具体例子：编码 agent 按 IR 把 tile 提到 128×64 并开 stage=3，执行步测得的时延比基线好，但正确性比对在一个非对齐的隐藏 shape 上失败，reward 记录为“时延改善、正确性未过”。这条记录回到调度器，调度器不会因为时延改善就保留该轮，而是把正确性失败作为硬门，让下一轮分析 agent 在 IR 里补写“非对齐 shape 的边界处理”动作。reward 的结构化设计正是为了让调度器能区分“快但错”与“慢但对”，而不是被单一标量误导。

五 · 调度步：按 reward 与 Conflict 决定主导权

调度器的输入是整条 IR 的当前状态：reward 记录、Conflict 标志、以及历史轮次的 diff 栈。它的输出是下一轮由哪个 agent 主导。规则可以写成优先级判定：若 Conflict=1，主导权交给分析 agent（因为冲突根源在 IR 与代码的语义断层，需要重写动作或补 schema）；若 Conflict=0 且正确性未过，主导权交给分析 agent 补边界动作；若 Conflict=0、正确性过、时延未达目标，主导权交给编码 agent 在现有 IR 内换后端或调参数（同一 IR 可被 Triton/CUDA/CuTe 不同编码 agent 复用，这是解耦的直接收益）；若时延达标且正确，则该 IR 归档为可复用策略。

这一步的代价是调度决策本身的延迟与“主导权抖动”。多 agent 串行链上，调度器每轮都要等执行步的 reward 才能决策，单轮延迟因此是四步之和；若调度规则过于敏感（例如时延噪声导致来回切换主导 agent），会出现同一 IR 被反复重写、token 消耗按轮数线性放大的情况。工程判断是给调度器加滞回：reward 的时延项需超过测量噪声带宽才触发主导权变更，Conflict 则作为零容忍硬信号立即触发。

具体例子：一轮中编码 agent 用 Triton 实现 IR，执行步正确性过、时延距目标差一档，Conflict=0。调度器不回到分析步重写动作，而是把主导权交给 CUDA 编码 agent，让它读同一条 IR 换后端实现——IR 里的 tile、stage、约束不变，只是投影方式变了。这正是策略与代码解耦的价值：一次分析投入被多个编码后端摊销。反之，若该轮 Conflict=1（代码未实现声明的 shuffle 归约），调度器立刻回到分析步，因为此时换后端没有意义，语义断层必须先修。调度器的全部智能就体现在这两类信号的区分上：Conflict 是语义问题，reward 差距是投影问题。

六 · 单轮流动的代价账与 schema 演进压力

把五步串起来看，单轮的总代价可以拆成三本账。第一本是时延账：分析、编码、评审、执行四步严格串行，执行步占 GPU、其余三步占调用延迟，多 agent 串行使单轮延迟相对单 agent 直接生成显著拉长（给定事实为 2–4×）。第二本是 token 账：分析 agent 读 profile 与源码、编码 agent 读 IR 加源码骨架加历史 diff、评审 agent 读 IR 加代码、调度器读全量状态，四者叠加约为单 agent 的 3–5 倍。第三本是正确性账：Conflict 指示函数在评审步点亮，但它的根源往往在分析步的 schema 覆盖不足——一个无法表达的动作被硬塞进邻近标签，编码 agent 照做，评审按错标签校验，整条链在错误的语义上自洽地跑完，直到执行步的正确性 oracle 才暴露。这类失败的修复成本最高，因为它要求回到 schema 层补字段，而不是改一轮代码。

schema 演进因此成为这条流水线的长期税负。每遇到一个 schema 不覆盖的动作，就要人工设计新字段、新标签、新校验规则，并保证旧 IR 仍可被新评审 agent 读取。扩展成本高的直接后果是动作空间被人为收窄，分析 agent 倾向于只在已知标签里选，创新动作被系统性排除。缓解手段是把动作标签设计成“可组合”而非“枚举穷举”：一个动作由（作用对象、变换类型、参数）三元组构成，评审只需校验三元组在代码中的投影，而不需要为每个具体优化单独建标签。这样新优化可以用已有变换类型表达，schema 扩展从“加标签”降为“加变换类型”，频率大幅下降。

具体到工程判断：这条五步流的瓶颈不在 GPU，而在分析步的翻译质量与评审步的校验覆盖。执行步的 reward 只能告诉你结果对不对、快不快，不能告诉你哪一步错了；Conflict 标志能定位到“代码与 IR 不等价”，但定位不到“IR 本身是否合理”。因此可信的多 agent 协同要求 IR 自带可追溯链：每个动作标签记录它由哪条 profile 证据触发、被哪个编码 agent 以何种参数投影、被评审以哪条规则校验、执行步回报了什么代价。缺了这条链，多 agent 只是在共享一个格式，而不是共享一个可验证的表示。最后一段落在这里：调度器决定主导权的那一刻，它读的不是 reward 标量，而是这条链上最近一次 Conflict 的位置——冲突在评审层，回分析步；冲突在执行层且正确性过，换编码后端；两者皆无而时延未达，才在 IR 内调参。这条判定顺序本身就是策略 IR 作为共享黑板的全部意义。

共享黑板的失效边界：schema 覆盖度与串行代价

结构化策略 IR 的效力完全取决于 schema 的表达力。IR 四元组中 $\mathcal{A}_{\text{cand}}$ 是候选动作的封闭枚举，任何不在枚举内的优化（例如非常规的 warp 特化、异步流水重排、手写 PTX 内联汇编）都无法被分析 agent 写入、也无法被评审 agent 机械校验。此时冲突检测公式 $\text{Conflict}=\mathbb{1}[\exists a\in\mathcal{A}:\ \text{Code}(a)\not\equiv\text{IR}(a)]$ 退化为恒假——编码 agent 实现了 IR 之外的动作，评审 agent 却因 IR 中没有对应声明而无从比对，语义漂移重新出现，只是从“多 agent 之间”转移到了“IR 与代码之间”。工程判断是：schema 必须携带一个显式的 `unmodeled` 逃逸字段，允许编码 agent 声明“此处实现了 IR 未覆盖的动作”，并由调度器强制转人工评审，否则黑板会静默丢失信息。

第二个边界是约束字段的静态性。IR 中的寄存器上限、共享内存上限在分析阶段一次性写入，但真实 kernel 的占用率是编译期由 ptxas 决定的，编码 agent 按 IR 约束写出的 tile 参数可能在编译后被寄存器压力推翻，触发 spill。此时评审 agent 看到的代码“符合 IR”，执行 agent 却拿到劣化的时延，reward 字段回填的负反馈会被错误归因到策略而非约束本身。代价体现在迭代效率上：一次错误归因至少浪费一轮完整的分析—编码—评审—执行链路。

系统代价的主项是串行化。四个角色按 IR 流动依次调用，单轮端到端延迟相对单 agent 增加 2–4×，token 消耗约为单 agent 的 3–5 倍；若一轮内发生打回，评审与编码之间的往返还会再叠加一次。因此调度器不能对每个 kernel 都走全链路，应按 IR 的 reward 方差决定是否跳过分析 agent、直接复用上一轮 IR 做增量编码——把串行开销压到只在策略真正变化时才支付。

失效条件表现代价
动作不在 schema 枚举内冲突检测恒假，评审空转语义漂移回流，需人工兜底
约束与编译期占用率冲突代码合规但 spill一轮链路误归因
全链路逐 kernel 触发延迟 2–4×、token 3–5×吞吐下降，调度需按 reward 方差裁剪
