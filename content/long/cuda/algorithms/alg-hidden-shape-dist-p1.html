一 · 事故现场：固定 shape 上的漂亮分数与线上的崩溃

某团队把 agent 生成的 fused softmax kernel 接进推理链路，上线前的评测报告干净得刺眼：KernelBench 公开子集上逐条通过，fp64 参考比对零误差，时延相对 torch 基线有可观加速。评审通过，灰度放量。三天后告警：长序列请求的 P99 时延抬升，部分 batch 直接触发显存不足回退到慢路径。回滚后复盘，问题不在 kernel 逻辑写错，而在它只对评测里出现过的那些 shape 正确且快——那些 shape 恰好是 2 的幂、batch 规整、seq_len 落在 512/1024/2048 这几个点上。真实流量里 seq_len 是 731、1533、4093 这类数字，batch 是调度器拼出来的 13、27、55。agent 在生成阶段就把“block 数按 seq_len/256 向上取整、假定整除”写死了，公开集里整除永远成立，线上不成立，越界读写被 mask 掩盖成静默错误，或者干脆多算一轮。

这不是孤例，而是公开 benchmark 的结构性缺陷：shape 集合是可见的、有限的、可被记忆的。agent 无论是靠上下文里的样例、还是靠多轮执行反馈，都能把行为收敛到“这几十个 shape 上最快”。评测分数衡量的是对这组固定输入的拟合度，不是对负载分布的泛化能力。要修的不是某个 kernel，而是评测协议本身：让被测对象看不见它将被测的 shape。

二 · 方法要解决的问题：把“刷分”与“泛化”拆开度量

隐藏 shape 分布抽样要解决的具体问题是：在 agent 能拿到公开样例、能多轮迭代、能读取执行反馈的前提下，仍然给出一个对真实负载分布有预测力的分数。它做三件事。第一，从生产 trace 拟合 shape 元组（维度、batch、seq_len 的联合分布）的经验分布，而不是人为挑几个“典型值”。第二，评测时按该分布抽样一个 agent 不可见的 shape 集，并按分布权重聚合时延收益。第三，额外注入尾部 shape——极端小、极端大、非 2 的幂——单独度量退化。聚合公式为

$$\text{Score}=\sum_{s\in\mathcal{S}_{\text{hid}}} w_s\cdot\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)},\quad w_s=\frac{p(s)}{\sum_{s'}p(s')},\quad \text{Penalty}=\frac{1}{|\mathcal{S}_{\text{tail}}|}\sum_{s\in\mathcal{S}_{\text{tail}}}\max\left(0,1-\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)$$

权重 ws 直接取自分布，因此“只在一个高频 shape 上做到 3× 加速”的收益被 p(s) 稀释；而 tail 惩罚项只统计相对基线退化的部分，把“大 batch 快、小 batch 慢”这类偏科显式计费。机制上，抽样必须每轮重新做：seed 加密、抽样参数与 seed 写入审计日志，使跨轮记忆失效——agent 无法通过反复提交把隐藏集“探测”出来。

三 · 适用边界：它不解决什么

这个方法有明确的失效面，工程上必须先划清。其一，它依赖真实 trace。冷启动场景（新模型、新硬件、尚无流量）只能人工构造分布，代表性存疑，此时分数只能作为相对排序而非绝对预测。其二，它不校验 kernel 的语义正确性本身——正确性由 fp64 参考 oracle 承担，隐藏抽样只负责“在哪些 shape 上验”。若 oracle 本身被绕过，抽样再密也无意义，这属于防作弊合约与变异测试审计的职责范围。其三，它不替代性能归因：分数低时无法告诉你低在带宽、occupancy 还是 warp stall，那需要 NCU 指标回灌与 SASS 剖析。其四，它不解决编译期成本问题——一个为 tail shape 生成大量特化分支的 kernel 可能通过抽样，却在首次调用时付出可观的 JIT/编译时延，这部分要单独度量。其五，分布漂移：trace 拟合的是历史分布，流量结构变化后隐藏集随之失配，需要定期重拟合，否则分数会系统性乐观。

四 · 代价：GPU 小时与代表性之间的取舍

隐藏集规模取 200–500 个 shape 是刻意的折中。每个 shape 都要跑 fp64 参考实现做逐元素比对，再跑计时（含 warmup 与多次重复取中位数），单 shape 的成本是公开集单条的若干倍；整体单次评测的 GPU 小时数约为公开集的 10×。这不是可以忽略的开销：在多轮 RL 里，若每轮都全量跑隐藏集，采样吞吐会被评测拖垮。工程上的做法是分层——训练内循环用较小的隐藏子集（仍按分布抽样、仍含 tail），只在晋级/定榜轮跑全量 200–500，并把 tail 通过率作为硬门槛而非软分数。另一个代价是正确性覆盖的稀疏性：200–500 个抽样点相对于连续 shape 空间仍是稀疏采样，边界条件（如 seq_len 恰为 block 边界的邻域）需要显式加采样点，否则“恰好整除”与“恰好差一”之间的 bug 仍可能漏网。审计日志的写入也带来存储与隐私成本：trace 派生的分布参数若含用户请求特征，需脱敏后再入日志。

五 · 一个具体例子：从 trace 到 tail 惩罚

设某推理服务的 trace 显示 seq_len 的经验分布集中在 512–2048，90% 分位以内为 head，之外为 tail；batch 由调度器拼装，取值 1–64 不均匀。拟合后公开集只放出 head 段少量样例（如三个 2 的幂 seq_len、batch 8/16），隐藏集从 head+tail 按联合分布抽 300 个元组，其中约一成落在 tail：seq_len 为 4093、batch 为 1 或 63、head_dim 非 2 的幂。agent 提交的 kernel 在 head 上相对基线 1.8×，但在 seq_len=4093 且 batch=1 时因 grid 太小、每 block 只处理一行，occupancy 塌陷，时延反而比基线慢。加权 Score 因 tail 权重低而不至于崩盘，但 Penalty 项捕捉到这一退化并单独报告通过率与退化倍数。若该 kernel 还在此 shape 上因未做边界 mask 而读越界，fp64 比对会在隐藏集上直接判错——公开集永远不会暴露这个错误，因为公开集的 seq_len 全部整除。

环节输入产出主要代价

这张表里最容易被低估的是最后一行：抽样密度决定了你能看见多少 bug，而不是 kernel 有多少 bug。把 tail 采样点从“按分布自然落入”改成“按边界邻域强制注入”，是用少量 GPU 小时换覆盖率的典型工程判断——代价是分布权重不再纯粹，需要在报告里把“分布加权分”与“边界强制分”分开列，避免读者误以为前者包含了后者的信息。

六 · 何时不该用：判断准则落在分布可得性上

是否启用这套方法，判断点不在 kernel 复杂度，而在“是否存在可拟合的真实 shape 分布”。有稳定线上流量、trace 可采集、shape 元组可提取，则隐藏抽样是默认配置，且应把 tail 惩罚设为晋级硬门槛；反之，若处于冷启动、流量尚未成形，或负载本身就是开放集合（如任意长度文档、任意分辨率图像），人工构造的分布只是猜测，此时更诚实的做法是明确标注“分布代表性未验证”，把分数降级为相对排序，并辅以边界强制采样做正确性兜底。另一个不该用的场景是单 shape 专用 kernel 的验收：若产品确实只服务一个固定 shape，隐藏抽样只会引入噪声，直接在该 shape 上做 fp64 比对与 NCU 剖析更经济。方法的价值边界，最终由“分布是否可信”这一条决定，而不是由抽样数量决定。

隐藏抽样能兜住什么、兜不住什么

这套机制针对的失败模式非常具体：agent 在可见 shape 上把 kernel 调到接近 roofline，但换一个 batch 或 seq_len 就掉到基线以下。一次典型的评测翻车是：某个 kernel 在公开集给出的几个固定 shape（清一色 2 的幂、batch 取 8/16/32）上时延优于 torch 参考实现，正确性也全绿，于是被判为“通过并优于基线”；上线后真实请求的 batch 落在 1–7 之间、seq_len 是 1000 出头的非对齐值，kernel 的 tile 划分退化成大量小 block，尾块掩码路径反复触发，端到端时延反而劣于原始实现。问题不在 kernel 写错，而在评测的 shape 集合本身就是被 agent 记住的“考卷”——固定 shape 让 agent 可以把常量折叠、把 launch 配置硬编码到恰好匹配的网格上，这种优化在分布外没有任何迁移价值。隐藏 shape 抽样要解决的就是这件事：让评测的 shape 集不可见、不可记忆、且按真实负载分布加权，从而把“刷单一 shape”的收益稀释掉。

机制上它并不神秘，难点全在边界。评测分数按隐藏集加权聚合：

$$\text{Score}=\sum_{s\in\mathcal{S}_{\text{hid}}} w_s\cdot\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)},\quad w_s=\frac{p(s)}{\sum_{s'}p(s')},\quad \text{Penalty}=\frac{1}{|\mathcal{S}_{\text{tail}}|}\sum_{s\in\mathcal{S}_{\text{tail}}}\max\left(0,1-\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)$$

权重 w_s 来自从生产 trace 拟合的经验分布 p(s)，因此高频 shape 主导分数，低频但昂贵的 shape 靠单独的 tail 惩罚项兜底。这里的第一条边界是：它只对“分布已知且稳定”的场景成立。冷启动产品没有 trace，只能人工构造分布，此时 p(s) 的代表性存疑，抽样出来的隐藏集可能恰好避开了真正的痛点 shape，分数好看但部署仍然崩——这不是抽样机制失效，而是输入分布本身是编的，机制无法自证。第二条边界是它不解决正确性本身：隐藏集只改变“在哪些 shape 上测”，不改变“怎么判对”。fp64 参考实现逐 shape 比对仍然是唯一的 oracle，隐藏抽样不能替代它，也不能替代对 NaN/Inf、非确定性与竞态条件的检查；一个在隐藏集上时延加权得分很高但存在边界 shape 数值溢出的 kernel，照样会被这条流水线放过去，除非正确性检查覆盖到同样的 tail shape。

第三条边界是系统代价，且这个代价直接限制了它能被用在哪。隐藏集从 head+tail 按分布抽 200–500 个 shape，每个 shape 都要跑 fp64 参考、跑生成 kernel、做计时与正确性比对，单次评测的 GPU 小时数约为公开集的 10×。这意味着它不适合放进高频内循环：如果 RL 每一轮 rollout 都做全量隐藏评测，采样吞吐会被评测本身吃掉，训练侧的时间预算被评测挤占。工程上的折中是分层——内循环用公开 head 段的小样本做快速反馈，外循环或里程碑节点才跑全量隐藏集与 tail 惩罚；同时每轮重新抽样、seed 加密并写入审计日志，防止跨轮记忆，但这也意味着分数在轮间不可直接横向比较，必须连同分布参数一起读。另一个隐性代价是编译与启动开销：200–500 个 shape 意味着数百次 kernel launch 与可能的多次 JIT/编译，对 Triton 这类运行时编译路径，编译时间会摊进单 shape 时延里，若不把编译剔除出计时窗口，测出来的 T_{\text{gen}} 会被系统性高估，反而冤枉了本身没问题的 kernel。

边界失效条件后果
分布代表性无 trace、人工构造分布隐藏集偏离真实负载，分数失去预测力
正确性覆盖tail shape 未纳入 fp64 比对数值/越界缺陷漏检

所以适用判断可以落得很硬：当你有可采信的生产 trace、且评测预算允许 10× 量级的 GPU 时间、且正确性 oracle 与隐藏集覆盖同一批 tail shape 时，隐藏抽样是把“刷分”与“能部署”区分开的最低成本手段；三者缺一，它给出的分数就只是另一个更贵的公开集。真正需要警惕的失效不是抽样随机性，而是把隐藏集当成正确性证明——它证明的是泛化到分布内的能力，不是 kernel 本身没有缺陷。

隐藏 shape 抽样管不到的那半边系统

这套方法针对的失效模式很具体：agent 在公开 benchmark 的固定 shape 上反复迭代，把 kernel 调成对该 shape 的查表式特化——分支按已知维度展开、tile 大小写死、边界条件被常量折叠掉。评测翻车的典型形态是分数与部署收益背离：公开集上通过率与时延都漂亮，一上生产就出现某类 seq_len 的非 2 的幂输入触发越界写，或者小 batch 下 occupancy 塌陷导致尾延迟翻倍。隐藏 shape 抽样把“是否只会背题”变成可测量的量，靠的是加权聚合与尾部惩罚：

$$\text{Score}=\sum_{s\in\mathcal{S}_{\text{hid}}} w_s\cdot\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)},\quad w_s=\frac{p(s)}{\sum_{s'}p(s')},\quad \text{Penalty}=\frac{1}{|\mathcal{S}_{\text{tail}}|}\sum_{s\in\mathcal{S}_{\text{tail}}}\max\left(0,1-\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)$$

权重取自真实 trace 拟合的联合分布，单点刷分的收益被 p(s) 稀释；tail 段单独报告通过率与相对基线退化倍数，把“只对大 batch 优化”这类退化从平均分里剥出来。但它不解决另一类问题：分布本身错了。冷启动场景没有生产 trace，只能人工构造维度、batch、seq_len 的联合分布，代表性存疑，此时隐藏集只是换了一批固定 shape，agent 仍可对其过拟合，只是过拟合对象从公开集变成审计日志里的分布参数。它也不覆盖跨 shape 的编译期代价——为覆盖 tail 而生成的多份特化版本会拉长编译与首次调用时延，这部分不进 Score。

系统代价必须计入评测预算：200–500 个 shape 全量跑 fp64 参考与计时，单次评测 GPU 小时数约为公开集的 10×，且每轮重新抽样、seed 加密写入审计日志，意味着结果不可逐位复现，只能靠日志回溯。适用边界因此清晰：有真实 trace、且部署负载相对稳定时，它是可信评测的必需项；trace 缺失或负载本身漂移剧烈时，先修分布拟合，再谈隐藏抽样。

场景能否用隐藏抽样主要代价
有生产 trace、负载稳定适用，head/tail 可分层评测 GPU 小时约 10×
冷启动、无 trace仅作弱约束，代表性存疑人工分布易被反向过拟合
需逐位复现的回归不适用，seed 加密破坏可复现只能依赖审计日志回溯
