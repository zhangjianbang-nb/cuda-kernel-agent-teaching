一 · 从 IR 元组到可计算标量：reward 的分解与逐项语义

策略 IR 的元组形式 $$\text{IR}=\langle \text{Bound},\ \mathcal{A}_{\text{cand}},\ \mathcal{C}_{\text{res}},\ \text{reward}\rangle$$ 中，前三项是声明性的，只有 reward 是可比较的标量，调度器与评审 agent 的所有决策最终都压在它上面。因此推导的第一步是把 reward 拆成可独立计算、可独立归因的分量，而不是让执行 agent 直接写一个“总分”。工程上采用的分量形式是：正确性门 $$g_{\text{corr}}\in\{0,1\}$$、归一化性能分 $$s_{\text{perf}}$$、资源约束罚项 $$p_{\text{res}}$$、冲突罚项 $$p_{\text{conf}}$$，合成

$$\text{reward}=g_{\text{corr}}\cdot\left(s_{\text{perf}}-p_{\text{res}}\right)-p_{\text{conf}}$$

关键一步在于把 $$g_{\text{corr}}$$ 放在乘法位而不是加法位：正确性不是可以“用性能换”的项，任何未通过 oracle 的实现必须让 reward 直接归零，否则多轮搜索会系统性地偏向快但错的候选。这与前文提到的 fp64 参考 oracle 是同一套判据，此处只借用其输出，不重复其构造。第二关键一步是 $$p_{\text{res}}$$ 用“超出量”而非“是否超出”来度量：若 IR 声明寄存器上限 $$R_{\max}$$、共享内存上限 $$S_{\max}$$，实测为 $$R, S$$，则

$$p_{\text{res}}=\lambda_R\cdot\max\left(0,\frac{R-R_{\max}}{R_{\max}}\right)+\lambda_S\cdot\max\left(0,\frac{S-S_{\max}}{S_{\max}}\right)$$

这样轻微越界只扣少量分，评审 agent 仍可保留该候选作为下一轮的变异起点；而硬性越界（例如超出硬件共享内存物理上限导致编译失败）会通过 $$g_{\text{corr}}=0$$ 或编译失败直接出局。举例：某候选把 tile 从 64 提到 128，性能分上升，但寄存器从 40 涨到 72、越过 IR 声明的 64 上限，$$p_{\text{res}}$$ 给出一个小正值，reward 略降——调度器据此判断“方向对、约束错”，下一轮让分析 agent 改 IR 的 $$R_{\max}$$ 或让编码 agent 加 $$\text{maxreg}$$ 提示，而不是直接丢弃该方向。代价方面，分量式 reward 要求执行 agent 每轮多采集寄存器与共享内存实测值（编译日志或 cubin 解析），单轮多出一次编译产物读取，属于毫秒级开销，但换来的是可归因性：reward 变化能定位到具体分量，避免“总分掉了但不知道为什么”。

二 · 归一化性能分的推导：为什么必须除以基线而不是除以峰值

性能分 $$s_{\text{perf}}$$ 的推导起点是“同一 IR 下的候选要能跨硬件、跨 shape 比较”。设候选实测时延 $$t_c$$、基线时延 $$t_b$$（同一 shape、同一 dtype、同一编译基线锚定条件），最朴素的加速比是 $$t_b/t_c$$，但它有两个病：一是无上界，一个异常快的候选会把 reward 尺度拉爆，压制其他维度的信号；二是当 $$t_c\to 0$$ 时数值不稳定。因此取对数压缩并截断：

$$s_{\text{perf}}=\text{clip}\left(\frac{\log\left(t_b/t_c\right)}{\log\left(t_b/t_{\text{SOL}}\right)},\ -1,\ 1\right)$$

分母 $$\log\left(t_b/t_{\text{SOL}}\right)$$ 是“基线到 SOL 还有多少可压缩空间”的对数度量，分子是“候选实际压缩了多少”。这个构造的含义是：$$s_{\text{perf}}=1$$ 表示候选已把基线到 SOL 的差距全部吃掉（即达到 SOL），$$s_{\text{perf}}=0$$ 表示与基线持平，负值表示退步。关键一步是把 SOL 放进分母而不是让候选直接对 SOL 归一：直接对 SOL 归一会让“基线本身离 SOL 很远”的任务上，任何微小改进都被稀释成接近零的分数，多轮搜索失去梯度；而除以“可压缩空间”相当于把每个任务的分数轴重新标定到 [−1,1]，使不同任务的 reward 可比。这与前文 Roofline/SOL 归一评分是同一族思路，此处只推导其对数形式带来的性质，不重复 SOL 的测量方法。代价是分母依赖 $$t_{\text{SOL}}$$ 的估计质量：若 SOL 估计偏乐观（把不可能达到的下界当目标），分母偏大，所有候选的 $$s_{\text{perf}}$$ 被系统性压低，调度器会误以为“这个 IR 方向没前途”而提前收敛。工程上的缓解是把 SOL 估计的不确定度写进 IR 的 Bound 字段，让评审 agent 在 $$s_{\text{perf}}$$ 接近 1 但未达 1 时优先怀疑 SOL 估计而非候选质量。具体例子：某 reduction kernel 基线 100 单位时间、SOL 估计 25 单位，候选做到 50，则分子 $$\log 2$$、分母 $$\log 4$$，$$s_{\text{perf}}=0.5$$；若 SOL 估计实际应为 40，则分母 $$\log 2.5$$，同一候选得分升到约 0.76——分数对 SOL 估计的敏感度是这一项的主要误差来源。

三 · 时延与显存的形式化：串行多 agent 的轮次成本

多 agent 串行调用的单轮时延可以直接写成各阶段时延之和加上调度开销：

$$T_{\text{round}}=\sum_{i\in\{\text{ana},\text{code},\text{rev},\text{exec}\}}T_i+T_{\text{sched}}+T_{\text{io}}$$

其中 $$T_{\text{exec}}$$ 又分解为编译时间与运行时间：$$T_{\text{exec}}=T_{\text{compile}}+n_{\text{rep}}\cdot t_{\text{kernel}}$$，$$n_{\text{rep}}$$ 是计时重复次数（取中位数以抗噪）。关键一步是认识到 $$T_{\text{compile}}$$ 在 Triton/CUDA 路径上往往是 $$T_{\text{round}}$$ 的主导项而非 kernel 本身：一个 kernel 跑几十微秒，但 Triton 的 JIT 编译或 nvcc 的模板实例化可能耗到秒级，因此“多跑几次取中位数”对总时延的边际成本远低于“多编译一次”。这直接决定了调度策略：评审 agent 打回重写比执行 agent 多测几遍更贵。给定事实中多 agent 串行使单轮延迟增加 2–4×、token 消耗约为单 agent 的 3–5 倍，这两个倍数应理解为相对单 agent 单轮的量级，其来源正是上式中的四个 $$T_i$$ 串行叠加与四份上下文各自携带 IR、源码、profile 片段。显存侧则要区分“峰值”与“驻留”：候选 kernel 的峰值显存 $$M_{\text{peak}}$$ 由 IR 声明的 tile 与共享内存上限约束，

$$M_{\text{peak}}\approx M_{\text{in}}+M_{\text{out}}+S_{\text{tile}}\cdot n_{\text{stage}}\cdot B_{\text{elem}}$$

其中 $$S_{\text{tile}}$$ 是单 stage 的 tile 元素数、$$n_{\text{stage}}$$ 是流水级数、$$B_{\text{elem}}$$ 是元素字节数。关键一步是把 $$n_{\text{stage}}$$ 作为可被 IR 显式声明的动作参数：编码 agent 若擅自加深流水线以提性能，$$M_{\text{peak}}$$ 线性上升，可能越过 IR 的 $$S_{\max}$$，触发上一节的 $$p_{\text{res}}$$。具体例子：一个 GEMM 候选把 $$n_{\text{stage}}$$ 从 2 提到 4，共享内存翻倍，若 IR 声明上限恰好卡在 2 级的水位，则该候选性能可能更好但 reward 被罚项拉低——这正是评审 agent 需要机械比对“代码里的 stage 数是否等于 IR 声明的 stage 数”的原因，而不是只看 reward 高低。

四 · 误差项：计时噪声、SOL 估计误差与冲突罚项的传播

reward 的可信度取决于各分量的误差如何传播到最终标量。对 $$s_{\text{perf}}$$ 做一阶误差传播，设 $$t_c$$ 的相对误差为 $$\varepsilon_c$$、$$t_b$$ 为 $$\varepsilon_b$$、$$t_{\text{SOL}}$$ 为 $$\varepsilon_s$$，则

$$\delta s_{\text{perf}}\approx\frac{1}{\log\left(t_b/t_{\text{SOL}}\right)}\sqrt{\varepsilon_c^2+\varepsilon_b^2+\left(\frac{\varepsilon_s}{\log\left(t_b/t_{\text{SOL}}\right)}\right)^2}$$

关键一步是第三项：SOL 估计误差被分母的对数再除一次，意味着当可压缩空间很小时（$$\log(t_b/t_{\text{SOL}})$$ 接近 0），SOL 误差被放大到主导地位。这解释了为什么在“基线已接近 SOL”的任务上，reward 的排序不可信，调度器应降低对该任务 reward 的权重或直接跳过该 IR 方向。计时噪声 $$\varepsilon_c$$ 的抑制靠重复取中位数而非均值（长尾来自其他进程与频率抖动），代价是 $$n_{\text{rep}}$$ 倍运行时间，但如上节所述，相对编译时间这是廉价的。冲突罚项 $$p_{\text{conf}}$$ 则来自元组定义中的冲突指示：

$$\text{Conflict}=\mathbb{1}\left[\exists a\in\mathcal{A}:\ \text{Code}(a)\not\equiv\text{IR}(a)\right],\quad p_{\text{conf}}=\mu\cdot\text{Conflict}$$

这里的 $$\not\equiv$$ 不是文本比对，而是“IR 声明的动作 $$a$$ 在代码中是否存在对应实现”的机械校验：例如 IR 声明“使用 cp.async 双缓冲”，代码里必须能找到对应的异步拷贝与等待指令序列，否则该动作未实现。关键一步是把冲突检测放在 reward 之外单独成项，而不是折进 $$s_{\text{perf}}$$：因为一个未实现声明动作的候选可能碰巧很快（例如靠编译器自动向量化），若只看得分就会奖励“说一套做一套”，多轮后 IR 与代码彻底脱钩。具体例子：编码 agent 在 IR 声明“tile=128、stage=3”的情况下生成了 tile=64、stage=2 的代码，性能尚可，但 $$\text{Conflict}=1$$，reward 被扣 $$\mu$$，评审 agent 打回并标注差异字段——这正是 IR 作为共享黑板减少语义漂移的落点。代价是冲突校验需要解析代码结构（Triton 的 AST 或 CUDA 的参数/指令模式），每次评审多一次静态分析，属于 token 与 CPU 时间的小额开销，但比让错误候选进入下一轮搜索便宜得多。

五 · 伪代码：把上述公式落到可实现的控制流

下面给出调度器单轮的伪代码思路，所有公式在此处只以符号出现，具体实现对应上文各节。核心是：先算分量、再合成、再按归因决定主导 agent。

  • 读入当前 IR，取 $$\mathcal{A}_{\text{cand}}$$ 与 $$\mathcal{C}_{\text{res}}$$；
  • 对每个候选 $$a$$：调执行 agent 得 $$g_{\text{corr}}, t_c, R, S$$；调评审 agent 得 $$\text{Conflict}(a)$$；
  • 按第一、二、三节公式算 $$s_{\text{perf}}, p_{\text{res}}, p_{\text{conf}}$$，合成 reward 写回 IR；
  • 若 $$g_{\text{corr}}=0$$ 的候选占比高，下一轮主导 agent 设为分析 agent（IR 本身有问题）；
  • 若 $$\text{Conflict}=1$$ 占比高，主导设为评审 agent（编码漂移）；
  • 若 $$p_{\text{res}}$$ 集中为负贡献，主导设为分析 agent 改约束；
  • 否则按 reward 排序保留 top-k，主导设为编码 agent 做变异。

关键一步是“按归因选主导 agent”这一步：它不是按 reward 绝对值排序，而是按哪个分量在拖后腿来路由。这避免了“reward 低就换编码 agent”的盲目性——若低分来自 IR 的约束声明错误，换编码 agent 只会重复撞墙。代价是这套路由需要每轮统计分量分布，调度器本身要维护少量聚合状态（各分量的均值与越界计数），属于常数级开销；真正的成本仍在串行调用上，2–4× 时延与 3–5× token 是这一架构的固定税，伪代码无法消除，只能通过“减少无效轮次”来摊薄。具体例子：一轮中三个候选全部 $$g_{\text{corr}}=0$$，按 reward 排序会全部丢弃并让编码 agent 重写；而按归因路由会让分析 agent 先检查 IR 的 Bound 是否把 tile 上限写得过紧导致所有候选都编译失败——后者一轮就能纠偏，前者可能空转数轮。

六 · 公式体系的工程判断：哪些项该进 IR，哪些该留在执行侧

把上述公式全部塞进 IR schema 是错误的方向：IR 是 agent 间的共享表示，应只承载“可被机械校验的声明”，而公式中的测量量与误差量属于执行侧产物。判断标准是：一个字段若评审 agent 能仅凭代码与 IR 做等价性检查，就进 IR；若它依赖运行时测量或外部估计，就留在执行 agent 的回报里，由调度器合成。按此标准，$$\mathcal{A}_{\text{cand}}$$ 与 $$\mathcal{C}_{\text{res}}$$ 进 IR（可校验），$$t_c, R, S, \text{Conflict}$$ 是回报（可测量/可静态分析但不由 IR 声明），$$s_{\text{perf}}$$ 与 reward 是合成结果写回 IR 的 reward 字段。这一划分直接决定了 schema 的扩展成本：新增一个优化动作（例如 TMA 描述符预取）需要同时扩展 $$\mathcal{A}_{\text{cand}}$$ 的枚举与评审 agent 的校验规则，而新增一个性能分量只需改调度器的合成函数，不动 IR。关键一步是把 $$\text{Conflict}$$ 的判定规则也视为 schema 的一部分并版本化：当 IR 增加新动作而评审 agent 的校验规则未同步时，$$\text{Conflict}$$ 会系统性误报，reward 被无谓扣分，多轮搜索提前收敛到保守候选。代价是 schema 版本化带来迁移成本，旧 IR 在新评审规则下可能被判冲突，需要保留按版本分派的校验器。具体工程判断：在 IR 中为每个动作附带一个“可观测签名”（该动作在代码中应产生的指令或参数模式），评审 agent 按签名做模式匹配而非语义理解，这样冲突检测是确定性的、可复现的，代价是签名覆盖不到的动作无法表达——这正是给定事实中“schema 不覆盖的动作无法表达、扩展成本高”的具体机制落点，也是这套公式体系在长尾优化动作上必须接受的表达力上限。

IR 协同的失效边界：冲突检测、串行时延与 schema 税

这套 IR 协同的可靠性完全押在 Conflict 这个指示函数上，而它的判定条件其实很苛刻：Code(a) ≢ IR(a) 要求评审 agent 能把“IR 里声明的动作”与“代码里的具体参数”做逐项对齐。失效点在于，IR 的 Bound 与 𝒜cand 是离散标签（瓶颈类型、目标 tile、寄存器上限），而代码是连续实现——编码 agent 完全可以在不违反任何 IR 字段的前提下，写出一个把 tile 设成 IR 值、却用错流水线阶段或漏掉边界谓词的 kernel。此时 Conflict=0，评审放行，错误被推到执行 agent 才暴露，一轮串行调用白跑。更隐蔽的是 𝒞res 约束的松弛：寄存器上限写成常量，编码 agent 用 __launch_bounds__ 压住占用率却牺牲了 ILP，IR 无法表达这种权衡，冲突检测对“合法但劣化”的实现完全失明。因此 Conflict 只能抓语义漂移，抓不住性能漂移，评审 agent 必须额外挂一个基于 profile 的回归门，否则 IR 的机械校验会给出虚假安全感。

串行代价可以直接写成一轮协同的时延分解：Tround = Tana + Tcode + Trev + Texec + Tsched，其中前三项是纯 LLM 调用，后两项含真实 GPU 执行与调度判定。给定事实里单轮延迟增加 2–4×、token 约为单 agent 的 3–5 倍，意味着当 Texec 本身只占单 agent 时延的一小部分时，LLM 侧的串行放大才是主项——分析 agent 读 profile 与源码的上下文最长，往往是 Tana 主导。工程上的边界条件是：只有当 Texec / Tround 足够大（即 kernel 真实运行时间足以摊薄 LLM 开销），多 agent 的协同才有净收益；对微秒级小 kernel，串行开销直接吃掉优化收益。调度器按 reward 与冲突决定下一轮主导者，本质是在用 token 换搜索方向的可追溯性，这笔账只有在候选动作空间大、单 agent 容易上下文过载时才划算。

schema 税是这套方案最硬的边界。IR 四元组 ⟨Bound, 𝒜cand, 𝒞res, reward⟩ 每扩一个字段，分析 agent 的 prompt、编码 agent 的映射规则、评审 agent 的校验逻辑要同步改三处，且旧 IR 需要迁移。schema 不覆盖的动作无法表达，等于把优化搜索空间人为截断——CuTe 的 layout 变换、PTX 级的手工 swizzle 这类动作若不在 𝒜cand 枚举内，编码 agent 即使写出正确代码也会被评审判为“未实现声明动作”而打回，形成假阴性。下表给出三类典型失效与对应代价：

失效模式触发条件系统代价
冲突漏检代码满足 IR 字段但实现劣化一轮串行时延 + 执行侧 profile 回归才发现
schema 截断动作不在 𝒜cand 枚举内评审假阴性打回，token 浪费在无效重试
串行放大Texec 远小于 LLM 调用时延2–4× 单轮延迟、3–5× token，净收益为负

落到可实现层面，调度器应把冲突检测从布尔量升级为带差异标注的三态：Conflict ∈ {pass, soft-miss, hard-miss}，soft-miss 指 IR 字段满足但 profile 未达预期，交由分析 agent 修 IR 而非打回编码 agent；hard-miss 才触发重写。同时给 𝒜cand 留一个 escape 通道，允许编码 agent 提交 IR 未声明的动作并附理由，由评审 agent 反向补写 IR——这把 schema 扩展从人工设计变成协同过程中的增量沉淀，代价是每轮多一次 IR 回写与版本对齐，换来的是搜索空间不被 schema 提前锁死。
