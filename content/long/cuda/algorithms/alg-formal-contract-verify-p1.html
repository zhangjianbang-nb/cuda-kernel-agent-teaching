一 · 一次“全绿”评测如何放过了一个越界写

设想一个在 KernelBench 风格流水线上被反复调优的 reduction kernel：输入 shape 由隐藏分布抽样给出，fuzz 参考 oracle 用 fp64 累加做对照，变异测试审计过 checker，batch 不变性门也通过。所有信号都是绿的，agent 于是把它推进到部署候选。问题出在边界 tile：当最后一维不是 tile 宽度的整数倍时，掩码分支写的是 if (idx < n)，但同一个 warp 里另一条路径按 idx < n - k 计算偏移，两者在 n 恰好落在 tile 尾部若干元素时产生分歧，越界写落在相邻 buffer 的头部。fuzz 抽了几千组 shape，没有一组踩中这个窗口——因为触发条件不是“某个 shape”，而是“某个 shape 与某个 lane 编号、某个 tile 内偏移的联合取值”。抽样对联合稀疏事件的覆盖是测度问题，不是样本量问题。

这类事故的工程本质是：fuzz 给出的是“未发现错误”，而安全关键 kernel 需要的是“不存在错误”。前者是存在性否证，后者是全称命题。把两者混为一谈，就会让评测流水线在统计上看起来收敛、在语义上完全开放。形式化合约验证要解决的正是这个缺口——它不提升平均性能，也不替代 profile，它只回答一个问题：对前置条件定义的所有合法输入，后置条件是否恒成立。写成一行就是本系列反复出现的判据：

$$\text{Proved}=\forall \mathbf{x}\in\mathcal{D}_{\text{pre}}:\ \text{Post}(\text{Kernel}(\mathbf{x}),\mathbf{x})\ \wedge\ \text{NoOOB}(\mathbf{x}),\quad \text{Cost}=|\text{BMC depth}|\times|\text{SMT queries}|$$

注意这个式子里没有“概率”“置信度”这类词。要么全域成立，要么给出一个具体反例，要么落在有界展开之外的“未证明”区间。第三种状态是本方法最容易被误读的部分，也是适用边界的核心。

二 · 合约是什么：把 PyTorch 语义钉成前置与后置

合约不是注释，是可被判定的二元组。前置条件 Pre(x) 从 kernel 签名与它所替代的 PyTorch 语义中提取：shape 约束（哪些维度必须相等、哪些允许广播）、dtype、对齐要求、stride 连续性、归约轴的长度范围。后置条件 Post(y, x) 则是输出等式与结构不变式的合取：逐元素输出等于参考语义、归约结果的结合律容许误差、写指针始终落在 [base, base+len) 内、共享内存索引不越过 tile 边界。

关键在于“提取”这一步的工程形态。对 Triton 或 CUDA C++，索引表达式是符号化的：pid * BLOCK + arange(0, BLOCK) 这类构造可以直接翻译成整数线性表达式加分段掩码；对 CuTe 的 layout 代数，tile 与 stride 的组合本身就是可判定的映射，翻译成本更低。真正昂贵的是控制流：循环边界依赖运行时 shape 时，符号执行会分叉，路径数随分支嵌套指数增长。工程上的通行做法是把循环做有界展开（BMC），深度取典型 tile 大小——例如把 128×128 tile 的外层循环展开到覆盖一个完整 tile 迭代，把“更大 shape 由同一 tile 逻辑重复”作为归纳假设显式记录在合约里，而不是隐式假定。

代价在这里第一次显形。状态空间随展开深度与位宽增长，128×128 tile 的 BMC 落在分钟级到小时级；这意味着它无法塞进每轮 RL 的 rollout 循环——agent 一轮迭代的预算通常是秒级到十秒级，而一次完整证明可能吃掉整条训练队列的时间片。于是合约验证在流水线中的位置不是“每步都跑”，而是“候选晋级前的闸门”或“离线批处理审计”。把它放进内循环是设计错误，不是工具缺陷。

三 · 机制：符号索引、SMT 查询与反例回灌

具体执行路径可以拆成四步，每步都有明确的失败产物。第一步，把 kernel 的读写范围与索引边界编码为符号表达式，线程号、block 号、循环变量全部作为自由整数变量；掩码条件成为布尔约束。第二步，把后置条件取反，与前置条件、路径条件一起交给 SMT 求解器：若 Pre ∧ ¬Post 可满足，模型即为反例；若不可满足，该有界深度内命题成立。第三步，对归约类 kernel 额外编码结合律与顺序无关性——这不是数值等式，而是“任意重排下结果落在容许误差带内”的结构性质，通常用整数索引层面的置换约束近似，浮点部分留给 fuzz。第四步，验证失败时输出反例的具体 shape 与输入值，直接回灌给 agent 作为修复信号。

反例的精确性是本方法相对 fuzz 的最大工程红利。fuzz 报“某组随机输入崩了”，agent 需要从崩溃现场反推触发条件，往往要再跑几十轮才能定位；SMT 模型给出的是一组满足所有路径约束的具体赋值——哪个 lane、哪个 tile 偏移、哪个 n 值——agent 拿到的是构造性证据，修复时无需再猜。这与变异测试审计 checker 的思路互补：后者检验 oracle 本身是否足够敏感，前者检验 kernel 是否在所有合法输入上满足 oracle。两者都不解决“oracle 语义写错”的问题，那是另一层合约。

代价的第二面是浮点。SMT 对 IEEE-754 的建模成本高：舍入模式、非规格化数、NaN 传播都要显式编码，查询规模迅速膨胀。工程上的现实取舍是分层——整数索引、边界、结构性质走 SMT 做确定性证明；数值正确性仍依赖 fp64 参考 oracle 的 fuzz 与误差带判定。宣称“形式化验证了数值正确性”在多数流水线里是不成立的，合约里必须把这一层显式标注为“未覆盖”，否则报告的可信度会被高估。

四 · 不解决什么：三类边界要写进报告而不是藏在脚注

第一类边界是有界性。BMC 只覆盖展开深度内的路径，超出部分标记为“未证明”。这不是失败，是状态；但报告必须把它与“已证明”分开统计，并与 fuzz 结果合并成置信度画像。把“未证明”混进“通过”的流水线，等于把全称命题偷偷降级成存在性否证，前面的事故就会重演。

第二类边界是语义来源。合约的后置条件来自 PyTorch 语义的人工或半自动提取，如果提取本身错了——比如把归约轴的容许误差带设得过宽，或漏掉某个 dtype 的舍入差异——验证会证明一个错误的命题。形式化方法保证的是“相对于合约成立”，不保证“合约忠实于意图”。这与防作弊合约校验是不同层次的问题：后者防的是被测对象绕过评测，前者防的是评测规格本身写歪。

第三类边界是性能。合约验证不回答 kernel 快不快、是否接近 roofline、NCU 上 stall 分布如何。它甚至可能因为要求更严格的边界检查而让 kernel 变慢——一个为通过 NoOOB 而加的全量掩码，可能引入额外的谓词指令与寄存器压力。工程判断是：把验证通过的结构性质当作性能优化的安全网，而不是把验证当作性能门槛。先证明索引安全，再在安全的前提下做向量化与去掩码，顺序不能反。

还有一个常被忽略的代价维度：token。反例回灌给 agent 时，符号模型需要被序列化成 agent 可读的形式——shape、lane 编号、偏移、约束摘要。这份序列化文本比一段自然语言报错长得多，在长上下文 agent 里会挤占修复推理的预算。工程上通常只回灌最小反例与违反的子句，而非完整模型。

五 · 一个可操作的判据：什么时候值得上合约

把适用边界压成一条工程判据：当错误的触发条件是“输入空间中的稀疏联合事件”、且错误的后果是内存安全或静默数值污染时，合约验证的边际收益最高；当错误主要表现为性能退化、或触发条件在随机抽样下稠密时，fuzz 加 profile 的性价比更高。前者对应越界写、共享内存索引溢出、归约顺序依赖；后者对应 tile 配置选错、occupancy 不足、bank conflict。

具体到流水线编排，一个可行的分层是：agent 生成候选后先跑轻量合约——只编码索引边界与 shape 前置，展开深度取最小 tile，秒级出结果，失败即回灌反例；候选晋级到部署闸门时再跑完整合约，覆盖典型 tile 大小与归约结构性质，分钟级到小时级，通过者标记“有界证明”，未覆盖路径与 fuzz 结果合并成最终置信度。这个分层让合约验证既不拖垮 RL 内循环，又在关键节点提供确定性保证。KernelBench-Verified 类工作可以直接复用这套分层，把“已证明/未证明/反例”三态作为一等公民写进评测 schema，而不是压成一个布尔通过位。

最后落在机制上：合约验证的输出不是一个分数，而是一份带反例与未证明区间的证明义务清单。agent 的修复信号来自反例的具体赋值，评测的可信度来自“未证明”被显式计数。把这两件事做对，比把 BMC 深度推到多大更能决定这套方法在生产端是否站得住。

边界不在“能不能证”，而在“证到哪一层就停”

一次线上事故的形态往往比基准翻车更难堪：某个归约 kernel 在离线 fuzz 中跑过数万组随机 shape 与随机初值，覆盖率报告漂亮，随后在生产流量里遇到一个 tile 边界恰好落在尾块、且输入含 NaN 的 batch，索引越界读到了相邻缓冲区，输出静默错位。fuzz 的失效不是随机性不够，而是它只抽样：它证明的是“这些输入没问题”，而不是“所有合法输入都没问题”。对安全关键 kernel，需要的命题是 $$\text{Proved}=\forall \mathbf{x}\in\mathcal{D}_{\text{pre}}:\ \text{Post}(\text{Kernel}(\mathbf{x}),\mathbf{x})\ \wedge\ \text{NoOOB}(\mathbf{x}),\quad \text{Cost}=|\text{BMC depth}|\times|\text{SMT queries}|$$ 即在前置条件刻画的合法输入域上，后置条件与无越界同时成立。合约/形式化验证解决的正是这个全称量化问题：把 kernel 签名与 PyTorch 语义里隐含的 shape 约束、dtype、对齐写成前置条件，把输出等式与读写范围写成后置条件，再对符号输入做有界验证。它不解决的问题同样明确——它不替你判断前置条件写得对不对，也不覆盖超出展开深度的路径，更不自动给出浮点数值等价的证明。

机制上，验证器把循环与索引翻译成符号表达式，用 SMT 求解器询问“是否存在违反后置条件的输入”；对循环做 BMC 有界展开，深度按典型 tile 大小设定。失败时返回的反例是精确的：具体 shape 与具体输入值，而不是“某处可能越界”的告警。这一点对 agent 修复闭环的价值高于证明本身——agent 无需再猜触发条件，直接把反例当作新的测试用例回灌。代价则集中在状态空间：大 tile（如 128×128）的 BMC 会从分钟级滑向小时级，这个时延无法塞进每轮 RL 循环的反馈预算里；同时浮点语义在 SMT 中建模成本高，多数验证只能覆盖整数索引与结构性质，数值正确性仍要退回 fuzz。于是工程判断变成分层：结构性质（越界、别名、归约结合律）走确定性证明，数值误差走抽样与统计置信，两者合并报告，通过但超出有界范围的路径显式标记为“未证明”，而不是被静默计入“已验证”。

适用边界的判据可以落到一句话：当错误是“结构性的、可由索引与读写范围刻画的”，合约验证给出的是确定性结论；当错误是“数值性的、依赖浮点舍入与累加顺序的”，它只能让位。一个具体例子是带 mask 的 softmax 行归约：前置条件写成“最后一维长度任意、mask 为布尔、行内至少一个有效元素”，后置条件写成“输出每行和为 1（在容差内）且所有读写落在 [0, numel) 内”。索引与 mask 分支可被 BMC 在 tile 深度内穷尽，越界与除零能被反例钉死；而“和为 1”的浮点容差本身是合约的一部分，写宽了证明变弱，写窄了求解器在浮点建模上直接放弃。这正是该方法不解决的第二件事：它把“什么算正确”的负担交还给写合约的人，合约写错，证明的是错的命题。对 KernelBench-Verified 类工作，可复用的是这套前置/后置模板与反例回灌接口；不可复用的是“验证通过即部署”的假设——未证明路径必须与 fuzz 置信度并列呈现，否则评测翻车只是从随机漏检换成了有界漏检。
