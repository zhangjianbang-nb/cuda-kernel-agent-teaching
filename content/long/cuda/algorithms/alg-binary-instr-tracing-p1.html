一 · 一次“时延变好了”的评测翻车

设想一个典型的 kernel 自动优化流水线：agent 在第 t 轮把某个 reduction kernel 的内层循环展开因子从 4 改成 8，本地跑三次取中位数，时延从 41.2 µs 降到 38.7 µs，判定为改进并 keep；第 t+1 轮在此基础上继续调 shared memory padding，又降了 1.1 µs。到第 t+3 轮，整条链路的端到端时延反而比基线高，回滚到第 t 轮的 checkpoint 后仍然高。工程师打开仓库，看到的是三份互不相干的证据：一份 git diff 显示改了展开因子，一份 ncu 报告显示 DRAM throughput 下降了若干个百分点，一份 benchmark 日志显示中位数时延。没有任何一份材料能把“第 t 轮那次展开”与“第 t+3 轮观察到的 DRAM 吞吐下降”连起来——因为第 t 轮的 ncu 快照是在另一台机器、另一个 shape 上采的，而第 t+1 轮的 padding 修改改变了 bank 冲突模式，两者叠加后的效应从未被单独测量过。

这类翻车不是测量精度问题，而是证据链断裂问题。agent 的优化过程天然产生四类异构证据：源码/prompt 轮次（文本）、编译产物 SASS（二进制）、profile 计数器（结构化数值）、端到端时延（标量）。它们由不同工具在不同时刻产生，缺少共同的版本坐标。于是“哪次修改导致哪个指标变化”这个问题在事后无法回答，keep/revert 只能依赖单点时延这一最脆弱、噪声最大的信号。二进制插桩 tracing 要解决的正是这个：给每一次 kernel launch 打上版本标签，把上述四类证据对齐到同一条时间轴上，使因果链可回溯、可审计。

二 · 它解决的具体问题：把“修改→指标”变成可计算的 delta

插桩 tracing 的核心产物是一条按版本对齐的差分记录。给定第 t 轮修改，trace 层计算

$$\Delta_{\text{trace}}^{(t)}=\left(T^{(t)}-T^{(t-1)},\ \text{SASS}^{(t)}\oplus\text{SASS}^{(t-1)},\ \text{metrics}^{(t)}-\text{metrics}^{(t-1)}\right),\quad \text{Keep}=\mathbb{1}\left[\Delta T<0\wedge\text{Correct}\right]$$

三元组的每一维都指向同一版本坐标：时延差回答“快了多少”，SASS 异或回答“机器码层面到底改了什么”（展开因子变化会直接体现为指令条数与寄存器压力的变化，padding 变化会体现为地址计算指令的重排），计数器差值回答“硬件资源利用往哪个方向移动”。三者同源，才能把“展开因子 4→8 使寄存器压力上升、occupancy 下降、DRAM 吞吐被拖累”这条链讲清楚，而不是让工程师在两个工具之间做没有根据的联想。

具体机制上，trace 的采集分三层。第一层是编译期锚点：kernel 编译完成后立即计算 cubin 哈希，连同 launch 参数（grid/block 维度、shape、dtype）写入一条 launch 记录。第二层是运行期拦截：通过 CUPTI 的 launch 回调（或 LD_PRELOAD 拦截 cudaLaunchKernel 系列符号）捕获每次 launch 的起止时间戳与 stream ID，得到逐次 launch 的时延样本而非聚合中位数。第三层是低频计数器快照：以采样方式关联 ncu 采集的计数器，只对代表性 launch 打点，避免全量采集的爆炸性开销。三层记录以 cubin 哈希为主键合并，再按 git diff 或 prompt 轮次切分，得到每个版本的 trace 段。

这套机制的直接收益是 keep/revert 判据从“单点时延”升级为“trace delta”。单点时延的问题在于噪声：同一 kernel 连续三次测量的离散度足以吞掉 1–2 µs 级别的真实改进，agent 会把噪声当成信号反复回滚，浪费轮次。而 trace delta 同时要求时延下降与正确性通过，并且 SASS 差分提供了“这次修改确实改变了机器码”的旁证——如果 SASS 哈希没变而时延变了，那基本可以判定是测量噪声而非优化生效，这一条判据在纯时延评分体系里是无法表达的。

一个具体例子：某 agent 对 layernorm 的 fused kernel 做了两处修改——把 rsqrt 换成近似指令、把两趟读改成单趟。trace 显示 SASS 差分中近似指令确实替换成功，但计数器快照显示 L2 命中率下降、时延 delta 为正。若只看时延，agent 会回滚整个修改，连带丢掉单趟读这个真正有效的部分；有了 SASS 与计数器的对齐，可以定位到退化来自近似指令引入的额外校正路径，从而只回滚该处。这就是“可审计因果链”相对“标量评分”的实质差别。

三 · 它不解决的问题：trace 不是正确性 oracle，也不是评分基准

边界必须说清楚，否则 trace 会被误用成万能证据。第一，插桩 tracing 不判定正确性。它记录 launch 参数与 SASS 哈希，能证明“这次 launch 用的是哪个版本的二进制、跑的是什么 shape”，但不能证明输出张量对不对。正确性判定依赖独立的 oracle——fp64 参考实现、变异测试审计过的 checker、合约校验，这些是别的机制的主题，trace 只负责把正确性判定的结果与版本坐标绑定，使“某版本通过/未通过”成为可追溯的事实而非口头结论。

第二，trace 模式下测得的时延不能直接作为评分依据。CUPTI 回调本身引入 5–20% 的时延开销，回调越密集、launch 越频繁，开销越显著。这意味着 trace 段内的 T 值是“带观测者效应的时延”，用于比较版本间的相对趋势尚可，用于对外报告绝对性能则失真。工程上的做法是双轨：trace 模式跑相对 delta 做 keep/revert 决策，评分模式关掉回调、用干净环境重测绝对时延。两套数据不能混用，混用就是把观测开销记到被观测对象头上。

第三，trace 不解释性能根因。计数器快照是低频采样的，能给出方向性证据（吞吐降了、occupancy 变了），但不足以做 warp stall 级别的归因；那需要 SASS 级剖析与专门的反汇编分析。trace 的定位是“把证据串起来”，不是“把证据解释透”。把 trace 当成性能分析工具会导致对采样数据的过度解读——低频快照上的一个百分点波动，可能只是采样相位与 wave 边界的巧合。

第四，trace 的存储与解析成本随轮次线性增长。每一轮修改都产生新的 cubin 哈希、新的 launch 参数集合、新的计数器快照，长跑 agent 的 trace 文件会迅速膨胀，解析与对齐的 CPU 时间也会成为流水线瓶颈。必须配合采样策略（只对代表性 shape 与代表性 launch 打点）与压缩（哈希去重、计数器增量编码），否则 tracing 本身会成为吞吐瓶颈，反过来污染时延测量。

四 · 适用边界的判据：什么时候值得插桩

判断是否引入 tracing，可以看三个条件是否同时成立。其一，优化轮次足够多，单点时延噪声已经影响 keep/revert 决策——如果只做三五轮手工调优，人工比对 git diff 与 ncu 报告的成本低于搭一套 trace 基础设施。其二，修改的效应存在跨轮叠加，需要事后回溯定位——展开因子与 padding 这类互相作用的参数是典型场景，单点评估无法分离各自贡献。其三，存在审计需求，即“为什么保留这一版”需要向他人或向未来的自己给出证据链，而不只是“跑得快”。

反例同样清晰。对于一次性、单参数的调优（比如只调 block size），trace 的三层采集带来的复杂度远超收益；对于正确性尚未稳定的早期探索阶段，trace 记录的是一堆错误版本的时延，价值有限，应先解决 oracle 问题；对于端到端收益评估，trace 的观测开销使其不适合作为最终数字来源，应让位于干净环境下的基准测量。换言之，tracing 是“过程证据”工具，不是“结果评分”工具，它的价值在轮次间、在版本间、在因果链上，而不在单点绝对值上。

还有一个容易被忽略的边界：trace 的对齐精度取决于版本切分的粒度。若 agent 在一轮 prompt 内做了多处修改而只提交一次，trace 只能给出这一整轮的聚合 delta，无法分离单处修改的贡献。此时要么要求 agent 按修改单元提交（增加轮次与 token 成本），要么接受粗粒度归因。这是 tracing 与 agent 策略 IR 协同的交界处——trace 的可用性上限由上游修改的原子性决定，插桩层无法凭空恢复未记录的信息。

五 · 一个可落地的采集伪代码与它的代价账

把机制写成流程，大致是四步。编译后取 cubin 哈希并登记 launch 参数模板；运行期在 launch 回调里记录 (hash, grid, block, shape, dtype, t_start, t_end, stream_id)；对标记为采样的 launch 关联计数器快照；按版本切分并计算 delta。伪代码层面，回调里只做时间戳与元数据写入，计数器采集走异步旁路，避免在热路径上做重活——这是控制那 5–20% 开销的关键：回调本身的固定开销无法消除，但可以把可变开销（序列化、落盘）挪出热路径，用环形缓冲区批量刷写。

代价账要算清楚三笔。时延账：5–20% 的观测开销意味着 trace 段的 T 值系统性偏高，且开销比例随 launch 频率变化，高频小 kernel 的相对开销更大，因此跨 kernel 比较 trace 时延时必须警惕这一偏差。存储账：trace 文件随轮次线性增长，一个长跑 agent 的 trace 若不做哈希去重与计数器增量编码，解析时间会从秒级升到分钟级，直接拖慢 keep/revert 循环的周转。token 账：trace 摘要若回灌给 agent 作为决策上下文，需要压缩成结构化短文本（版本号、delta 符号、SASS 变更类别），否则原始 trace 的体积会挤占上下文预算，反而降低 agent 的推理质量。

具体例子：一个对 attention kernel 做多轮调优的 agent，每轮提交一次修改，trace 层对每个版本记录 3 个代表性 shape 的 launch 时延与一次计数器快照。第 7 轮时延 delta 为负但 SASS 差分显示寄存器数上升，trace 摘要提示“时延改善伴随资源压力上升”，agent 据此在第 8 轮避免继续堆展开因子，转而调整 tile 形状。若没有 SASS 与计数器的对齐，第 7 轮的时延改善会被当作纯收益接受，第 8 轮很可能在资源压力上撞墙。这个例子的价值不在于数字，而在于展示 trace 三元组如何把“看起来变好”拆解成“哪一部分真的好、哪一部分埋了隐患”。

最终落到工程判断上：二进制插桩 tracing 的定位是 agent 优化循环的“黑匣子”，它把分散在编译、运行、剖析三个环节的证据压到同一条版本轴上，使 keep/revert 从赌单点噪声变成读差分证据。它的适用边界由轮次密度、修改耦合度与审计需求三者共同划定；越过边界——把它当正确性 oracle、当评分基准、当根因分析工具——得到的不是更强的证据，而是被观测者效应与采样偏差污染的错误结论。是否引入它，取决于你的流水线是否已经出现“说不清哪次修改导致哪个指标变化”的病症，而不是取决于 tracing 本身有多时髦。

插桩追踪解决的是“因果链断裂”，不是“性能本身”

二进制插桩 tracing 要解决的具体问题，是 agent 多轮优化过程中证据链的断裂：源码 diff 在一个地方、SASS 在另一个地方、NCU 计数器在第三个地方、端到端时延又在评测脚本的日志里，四者之间没有共同的版本坐标。于是当某一轮 kernel 变慢或正确性翻转时，工程上无法回答“是哪一次修改、改动了哪条指令、导致哪个指标变化”。它不解决的问题同样明确：它不替你判断一个 kernel 是否接近 roofline，不替代 NCU 的深度瓶颈分析，也不负责生成候选修改——它只是把每次 launch 的参数、cubin 哈希、起止时间戳、流 ID 与可选的低频计数器快照钉在同一版本号上，让后续的 keep/revert 有据可依。一个典型翻车场景是：agent 连续三轮分别改了 tile 大小、向量化宽度与 shared memory 布局，评测端只看到最终时延退化，回滚时把三轮改动一起丢弃，连带扔掉了其中真正有效的那一轮——没有 trace，就无法把退化归因到具体那一轮。

其机制核心是把“修改—指标”的对应关系写成可比较的差分向量，并按版本对齐后做决策：

$$\Delta_{\text{trace}}^{(t)}=\left(T^{(t)}-T^{(t-1)},\ \text{SASS}^{(t)}\oplus\text{SASS}^{(t-1)},\ \text{metrics}^{(t)}-\text{metrics}^{(t-1)}\right),\quad \text{Keep}=\mathbb{1}\left[\Delta T<0\wedge\text{Correct}\right]$$

注意 Keep 判据用的是差分 ΔT 而非单点时延，这正是它相对“跑一次看快慢”的价值：单次测量噪声足以让一次真实改善被误判为退化而回滚。但边界也在这里——若某一轮只改了 host 侧 launch 配置而 SASS 哈希不变，SASS 差分项为零，trace 只能告诉你“配置变了、时延变了”，无法解释指令级原因，此时必须回到 NCU 做定点分析。适用边界可归纳为一张小表：

场景tracing 是否适用原因
多轮 agent 修改需归因适用版本对齐后可算每轮 delta
单点绝对性能评分不适用插桩开销污染时延
指令级瓶颈定位不适用需 NCU 全量计数器
正确性翻转审计适用参数与哈希可回溯

系统代价必须提前计入预算。CUPTI 回调或 LD_PRELOAD 拦截 launch 会引入可观测的时延开销（量级在个位数到两成之间），因此 trace 模式下测得的时延只能用于相对比较与趋势判断，不能直接作为评分依据——评分应走无插桩的干净通道，trace 只做旁路记录。trace 文件随轮次线性增长，若不采样与压缩，存储与解析成本会反过来拖慢 agent 循环；工程上的做法是对计数器快照做低频采样、对 SASS 差分只存哈希与变更段、对时延保留分位数而非全量样本。一个具体例子：某轮 agent 把 block 从 128 改到 256，trace 显示 cubin 哈希变化、时延差分转负、正确性通过，Keep 置 1；下一轮改 shared memory padding，哈希再变但时延差分转正，trace 直接给出反例记录，回滚只撤这一轮，前一轮收益得以保留——这正是插桩 tracing 在边界内最实际的产出。
