一 · 决策字段的 schema 化：把“写代码”拆成可校验的槽位

策略 IR 的第一步不是让模型产出任何字符级的 CUDA，而是先固定一张 schema 表。这张表把一次 kernel 设计拆成若干互不重叠的决策字段：tile 尺寸（M/N/K 三维）、线程映射（每个 warp 负责哪一维、每线程算几个输出）、访存模式（向量化宽度、是否走 shared memory 中转、是否用 ldmatrix 类指令）、流水线级数（double/triple buffer 的 stage 数）、共享内存布局（padding、swizzle、bank 对齐）、边界处理策略（predicate、tail 分支、pad-to-tile）。每个字段带类型与合法取值域，例如 tile 尺寸限定为 2 的幂且乘积不超过共享内存预算，流水线级数限定为 1–4，线程映射必须满足线程总数等于 block 维度乘积。

这一步的输出是一份结构化的决策向量 d，而不是源码。它的代价体现在表达力上：schema 一旦定死，凡是字段取值域之外的配置都无法被表达，DSL 的表达力上限就是后续性能的上限。具体例子：若 schema 的流水线字段只允许“统一 stage 数”，那么 warp-specialized 的异构流水线（生产者 warp 与消费者 warp 走不同深度）就落在域外，模型再聪明也生成不出来。工程判断是：字段粒度要按“能否被 lowering 器确定性翻译”来切，而不是按“能否被人类描述”来切。

二 · 约束求解与资源上限校验：在 lowering 之前拦掉不可行配置

LLM 读入问题描述（shape、dtype、算子语义）与硬件约束（SM 数量、每 SM 寄存器文件、共享内存容量、目标占用率），输出决策向量。解析器随即做两层校验：第一层是 schema 合法性（类型、取值域、字段间一致性，如线程映射与 tile 尺寸必须整除匹配）；第二层是资源可行性，用静态估算把决策映射到寄存器与共享内存占用，并检查是否越过上限。可行性约束可写成：

$$\text{smem}(d)=\sum_{i}\text{buf}_i(d)\cdot\text{stage}(d)\le S_{\max},\quad \text{regs}(d)\le R_{\max},\quad \text{occupancy}(d)\ge O_{\min}$$

不满足的决策不进入 lowering，直接以“字段级拒绝”的形式回灌：不是“这段代码编译不过”，而是“pipeline_stages=4 使 smem 估算超限，请降到 2 或缩小 tile_K”。这一步的代价是校验本身的时延——静态估算通常远低于一次真实编译，但它必须足够保守，否则会把可行配置误判为不可行，白白砍掉搜索空间。具体例子：一个 fp16 GEMM 在 tile 128×128、stage=3 时共享内存估算已逼近上限，解析器在 lowering 前就拒绝 stage=4，省下一次注定失败的 nvcc 调用（数十秒级编译时间）与一次无效 oracle 运行。

三 · 确定性 lowering：从决策向量到可编译源码的唯一映射

lowering 器接收合法决策向量，按固定模板翻译为 CUDA C++ 或 Triton 源码，并注入两类此前不在 DSL 字段里的东西：边界检查（对非整除 shape 的 predicate 与 tail 处理）与同步原语（shared memory 写后读的 __syncthreads()、流水线 stage 间的 barrier 位置）。关键性质是确定性：同一决策向量必须产出逐字节一致的源码，否则反馈无法归因到字段，beam search 的比较也失去意义。

伪代码思路：

  • 按字段顺序展开模板：tile → 线程映射 → 访存 → 流水线 → 同步插入点；
  • 每个字段对应一个代码片段生成函数，片段之间只通过显式声明的接口（buffer 名、索引变量）耦合；
  • 同步原语的插入由流水线级数与共享内存布局共同决定，作为 lowering 的派生量而非独立字段，避免模型在字段层面写出死锁配置。

代价有两块：一是 lowering 器本身的维护成本，DSL 每扩一个字段、每跟进一代架构特性（新的异步拷贝指令、新的 shared memory 布局约束），模板与派生逻辑都要同步改；二是确定性带来的表达力刚性——模板无法覆盖的代码组织方式（例如手工展开的极端特化）被排除在外。具体例子：边界处理字段取“pad-to-tile”时，lowering 会在加载侧插入越界掩码并在写回侧裁剪，这段代码不由模型书写，因此模型无法在此处引入越界读写，正确性风险被前移到字段选择本身。

四 · 编译、oracle 与测量：把三类失败折叠成结构化反馈

lowering 产物进入三段式验证：编译（nvcc/triton 编译成功与否）、正确性 oracle（与参考实现比对，含数值容差判定）、性能测量（计时并折算为相对参考的加速比）。三者的结果被折叠回 DSL 层，形成“字段—错误类”的映射，而不是一整段报错文本。评分形式为：

$$\text{score}(d)=\mathbb{1}[\text{compile}(d)]\cdot\mathbb{1}[\text{correct}(d)]\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)},\quad d\in\mathcal{D}_{\text{DSL}},\ \text{s.t.}\ R(d)\le R_{\max},\ S(d)\le S_{\max}$$

反馈的结构化程度决定了下一轮的有效性。编译失败要定位到“哪个字段生成的片段触发了哪类错误”（例如向量化宽度与对齐假设冲突导致的非法访存）；正确性失败要区分“数值误差超容差”与“边界 shape 下结果错位”，前者往往指向流水线同步或累加精度，后者指向边界处理字段；性能不达标则要标注是带宽受限还是延迟受限，从而提示应调 tile 还是调 stage。代价是每轮的固定开销：一次编译加一次 oracle 加多次计时，在预算有限的轮次里，这部分开销占比不小，因此解析器前置校验的价值就在于把注定失败的配置挡在这笔开销之外。具体例子：某轮决策在非整除 K 上正确性失败，反馈精确落到“边界处理=predicate 但 tail 分支缺失”，下一轮只改这一个字段即可，而不必重写整段 kernel。

五 · DSL 空间上的 beam / keep-revert 搜索：把预算花在可行邻域

有了字段级反馈，搜索就可以在决策向量空间上做，而不是在源码文本上做。beam search 维护若干合法且得分较高的决策，每轮对得分最高的若干配置做单字段或双字段变异（调 tile、调 stage、换访存模式），keep-revert 则对变异结果做接受/回退判定：得分提升且仍满足资源约束则保留，否则回退到父配置。由于字段可枚举，变异算子可以按字段类型定制——连续型字段（tile 尺寸）做邻域步进，枚举型字段（访存模式、边界策略）做离散切换。

这一步的代价是搜索宽度与每轮验证开销的乘积：beam 宽度为 b、每轮变异 m 个候选，则每轮要跑 b·m 次编译加 oracle 加计时。在编译时间以十秒计的现实下，宽度不能开大，因此字段级反馈的精度直接决定收敛速度——反馈越准，单字段变异越可能命中改进方向，所需宽度越小。具体例子：某配置在带宽受限诊断下，beam 保留它并只变异“向量化宽度”与“shared memory 中转”两个字段，其余字段冻结，从而把每轮候选数压到个位数，避免在无关维度上浪费编译预算。

六 · 表达力与工程成本的边界判断

这条流水线的收益与代价在同一处交汇：DSL 覆盖的字段越宽，可生成的优化越多，但 lowering 模板、资源估算、反馈归因三者的维护面同步扩大，且每一处扩展都要保证确定性 lowering 仍然成立。工程判断应落在“高频、可模板化、可静态估算”的优化上——tile、线程映射、流水线、布局、边界这几类字段覆盖了多数稠密算子性能差异的主因，而非常规优化（warp-specialized 流水线、跨 block 协作）落在域外，其性能上限由 DSL 表达力封顶，这是必须显式承认的代价而非可绕过的缺陷。

另一个边界是反馈的归因粒度：当一次失败同时牵涉多个字段（例如 tile 与 stage 共同导致共享内存超限），结构化反馈必须给出“主责字段”或“最小修改集”，否则 keep-revert 会在多个字段间来回震荡。可行的做法是在解析器阶段就做约束传播，把超限归因到最后一个使约束越界的字段，并在反馈中附带可行的取值建议。代价是解析器逻辑变复杂，但换来的是每轮变异的方向性，减少无效编译轮次。具体例子：stage=4 与 tile_K=64 的组合超限时，反馈指向“缩小 tile_K 可保留 stage=4”，模型据此做单字段调整，而不是同时改两个字段导致正确性回归。

约束边界：DSL 合成在哪些输入上失效，以及每一步的隐性账单

把策略 IR 的流动拆成五步之后，真正决定这套方案能否上生产的问题不是“能不能跑通”，而是“在哪一步先崩”。第一步定义 schema 时，失效条件已经埋下：合法取值域是离散枚举的，tile 尺寸、线程映射、流水线级数、共享内存布局、边界策略各自有类型与上限，但字段之间并非正交。例如 tile 尺寸与共享内存布局耦合，流水线级数与寄存器压力耦合，边界处理策略又与访存模式耦合。解析器只做逐字段校验时，会放过“每个字段都合法、组合起来却超资源”的决策，这类配置在 lowering 之后才由编译器以寄存器溢出或共享内存超限的形式暴露，反馈被迫退化为整段代码级错误，字段级定位能力在此失效。系统代价是可计算的：设字段数为 $n$、第 $i$ 个字段取值域大小为 $|D_i|$，名义搜索空间为 $\prod_i |D_i|$，但受约束 $R(d)\le R_{\max}$、$S(d)\le S_{\max}$ 裁剪后实际可行域远小于此；解析器若不做组合级校验，beam 搜索会把预算浪费在不可行配置上，每一轮都付出一次 lowering 加一次编译的固定开销，而这次开销不产生任何性能信息。一个具体例子：流水线级数取到上限、共享内存布局取到最大分块，两个字段单独看都在域内，组合后共享内存占用越过架构上限，编译阶段直接失败，本轮 token 与编译时间全部沉没。

第二步 LLM 输出 DSL 决策，这一步的代价不在正确性而在 token 预算的分配结构。问题描述与硬件约束作为输入，输出是结构化字段而非源码，单轮输出 token 显著低于直接生成 CUDA C++，这是该方案的核心收益之一；但收益被搜索轮数吃掉一部分。beam 宽度为 $k$、轮数为 $T$ 时，总输出 token 约为 $k\cdot T$ 乘以单次决策长度，而直接生成源码的方案单轮 token 高、轮数少。两者的总预算可比，差别在于前者每轮都能拿到字段级反馈、后者每轮都在修语法。失效条件是问题描述本身超出 DSL 表达能力：当算子需要 DSL 未建模的非常规结构（warp-specialized 流水线是典型），LLM 只能在现有字段里做次优组合，此时 token 花得再多也触不到性能上限，搜索在可行域内部收敛到一个“合法但不快”的配置。这不是 LLM 的能力问题，是 schema 表达力的硬边界，且该边界不会因增加轮数而移动。

第三步确定性 lowering 是整个方案的正确性锚点，也是维护成本的主要来源。lowering 把字段翻译为 CUDA C++ 或 Triton 源码，并注入边界检查与同步原语；注入逻辑必须与字段语义严格对应，否则会出现“DSL 决策合法、生成代码语义错误”的静默失败，这类错误绕过了 schema 校验，只能由正确性 oracle 兜住。代价体现在编译时间上：每次 lowering 产出的源码都要走完整编译流程，编译时间与源码规模、模板实例化深度正相关，在 beam 搜索中这是每轮乘以 $k$ 的固定支出。更隐蔽的代价是版本同步：DSL 扩展与 CUDA 版本、架构特性同步有工程成本，新架构的共享内存容量或新的同步原语若未及时进入 schema，lowering 器要么生成过时写法、要么在字段域外拒绝合法决策。一个具体例子：边界处理策略字段新增一种“尾部对齐”取值，lowering 器需要同时更新代码生成模板与资源估算逻辑，两处不一致时，解析器按旧估算放行、编译器按新代码拒绝，反馈信号自相矛盾。

第四步编译、正确性 oracle 与性能测量构成反馈回路，其代价是测量噪声与 oracle 覆盖率的乘积。性能测量本身有方差，单次时延不足以支撑 keep-revert 决策，需要重复采样；正确性 oracle 若只覆盖典型形状，边界策略字段的错误会在非典型形状上漏检。评分函数把三者压成一个标量：

$$\text{score}(d)=\mathbb{1}[\text{compile}(d)]\cdot\mathbb{1}[\text{correct}(d)]\cdot\frac{T_{\text{ref}}}{T_{\text{kernel}}(d)},\quad d\in\mathcal{D}_{\text{DSL}},\ \text{s.t.}\ R(d)\le R_{\max},\ S(d)\le S_{\max}$$

该式的结构决定了失效模式：任一指示函数为零，整条决策的分数归零，性能信息被完全丢弃。这意味着编译失败与正确性失败在搜索中不可区分，beam 无法从“差一点编译通过”的配置里学到任何东西，只能整体丢弃。代价是每轮预算中失败样本的信息量为零，而失败样本在早期轮次占比不低。改进方向是把指示函数换成结构化惩罚，把失败原因编码进反馈，但这会引入新的评分权重调参成本。第五步 beam/keep-revert 搜索在 DSL 决策空间上运行，保留合法且加速的配置进入下一轮；其系统代价是状态管理——每个保留配置需要记录字段取值、lowering 产物、编译产物与测量结果，显存与磁盘占用随 beam 宽度与轮数线性增长，在长轮次任务中成为实际瓶颈。一个具体例子：beam 宽度为若干、轮数为若干时，保留配置的编译产物累积占用可观，若不做淘汰策略，搜索后期的 I/O 开销会侵蚀性能探索的时间预算。

步骤主要失效条件系统代价
schema 定义字段耦合导致组合超资源可行域裁剪前的无效 lowering 与编译
LLM 决策问题超出 DSL 表达力token 预算乘以 beam 宽度与轮数
lowering注入逻辑与字段语义不一致每轮编译时间、版本同步工程成本

beam 搜索保留配置状态膨胀编译产物存储、I/O 挤占探索预算

工程判断落在 schema 的组合校验粒度上：逐字段校验便宜但放过耦合错误，组合级校验能提前拦截却需要维护字段间的约束矩阵，且约束矩阵随 DSL 扩展而增长。可行的折中是只对高耦合字段对做显式约束，其余交给 lowering 后的编译器兜底，代价是这部分失败仍以整段代码级反馈出现。DSL 表达力上限则是不可折中的硬边界，它决定了这套方案在非常规优化上的天花板，扩展 schema 的每一次动作都要同时支付 lowering 器与约束矩阵的维护成本。
