一 · 负载选型：从 DSL 表达力反推可评测的算子族

策略 IR 的负载选型不是“挑几个热门算子跑一跑”，而是从 DSL schema 的字段集合反推哪些算子能被这套 IR 完整描述、哪些只能被部分描述、哪些必须排除在评测集之外。判断依据是 lowering 路径的覆盖度：一个算子若其最优实现所需的决策（tile 形状、线程映射、流水线级数、共享内存布局、边界策略）全部落在 DSL 合法取值域内，它就是“可完整表达”的负载；若其最优实现依赖 DSL 未建模的机制（warp specialization、异步 barrier 分段、张量核心的非常规 fragment 布局），它属于“表达力外”负载，放进评测集只会让分数反映 DSL 的短板而非 agent 的能力。

具体机制上，把候选算子按决策维度做覆盖矩阵：行是算子族（elementwise、reduction、GEMM 变体、attention 类、归一化、扫描/前缀和、卷积），列是 DSL 字段。每个单元格标注“最优实现是否必须使用该字段的某个取值”。GEMM 类负载强依赖 tile 与共享内存布局字段，reduction 强依赖线程映射与流水线级数，扫描类则对流水线级数极敏感而对 tile 不敏感。覆盖矩阵中若某算子族有超过一个字段落在“必须但 DSL 无法表达”，该族整体移出主评测集，只作为表达力扩展的压力测试用例保留。

代价体现在两个方向。把表达力外负载放进主集，会让 score 的分子端被系统性压低，agent 在 DSL 层无论怎么搜都撞不到天花板，搜索预算被浪费在无解区域；把表达力内负载做得太窄（只留 elementwise 与简单 reduction），则 DSL 的 tile/流水线字段几乎不被激活，beam search 退化为对少数几个字段的枚举，评测失去区分度。工程判断是：主评测集应让每个 DSL 字段至少在一个算子族上成为性能主导因素，同时每个算子族的最优实现不触碰 DSL 之外的机制。

一个具体例子：把 softmax 行归约放进主集时，若 DSL 只有“tile 尺寸 + 线程映射 + 边界策略”而无“两趟归约 vs 在线单趟归约”这一流水线语义字段，则 agent 只能生成两趟版本，其带宽利用率被在线版本压制，score 反映的是 DSL 缺字段而非策略差。此时正确做法是把“归约趟数”提升为 DSL 字段，或把 softmax 移出主集。

二 · Shape 与输入分布的配方：让分数对分布偏移敏感

shape 配方决定 score 的方差来源。若评测集只用一组“好看”的 shape（如 4096×4096 的方阵），agent 会收敛到对该 shape 过拟合的 tile 选择，换一个非整除 shape 就退化。配方应包含三类：整除友好型（维度是 tile 的整数倍）、边界压力型（维度比 tile 整数倍多一个尾块，或远小于 tile）、极端长宽比型（如 M=1 的 GEMV、K 极大的瘦长矩阵）。三类各自占比要能让“边界处理策略”字段成为区分度来源——边界压力型 shape 上，不做尾块特化的 kernel 与做了尾块特化的 kernel 时延差距会被放大到 score 可见的量级。

输入分布的设置针对正确性 oracle 与数值稳定性。浮点负载的输入若全为小量级正数，累加顺序差异不会暴露；若混入大幅值异号元素，归约的数值误差才会显现。配方上给每个负载配一组“数值对抗”输入：大幅值异号、含次正规数、含 NaN/Inf 的边界样本（用于检验 kernel 是否按合约传播而非静默吞掉）。这些输入不进入性能计时，只进入正确性判定，避免污染时延测量。

$$\text{cov}(d)=\frac{|\{s\in\mathcal{S}_{\text{edge}}: T_{\text{kernel}}(d,s)\le \alpha\cdot T_{\text{ref}}(s)\}|}{|\mathcal{S}_{\text{edge}}|},\quad \alpha>1$$

上式给出一个可操作的配方指标：边界 shape 集合上的达标覆盖率。它把“只在友好 shape 上快”的策略显式惩罚——score 只看单一 shape 时，cov 高的策略与 cov 低的策略可能同分，把 cov 作为门或加权项才能区分。代价是评测时延：每个负载要跑三类 shape 各若干组，测量次数上升，单轮评测的墙钟时间增加；若把 cov 做成硬门（cov 低于阈值直接判不通过），则 agent 在早期轮次会因边界处理未收敛而大量被拒，搜索效率下降。折中是先做软加权，待边界策略字段稳定后再收紧为门。

一个具体例子：M=1 的 GEMV 负载上，tile 沿 N 方向切分、线程映射为“每线程一列”的策略在 N 整除时表现正常，但 N 非整除时尾块线程空转，cov 指标会把这类策略与做了尾块掩码的策略区分开。若配方里没有 M=1 这一档，两者分数相同，agent 学不到尾块掩码的价值。

三 · 基线与指标口径：T_ref 的选择决定 score 的语义

score 公式中 T_ref 不是“随便找个能跑的版本”，它的选择直接定义“加速”的参照系。可选基线有三类：框架内建算子（cuBLAS/cuDNN/ATen 原生调用）、手写但未经调优的朴素 kernel（naive tiled）、以及同一 DSL 下由人工编写的参考决策（reference DSL config）。三者的语义不同：对框架基线取比值，衡量的是“agent 能否打败成熟库”，门槛高、方差大，且库版本变动会让历史分数不可比；对朴素 kernel 取比值，衡量的是“agent 能否发现基本优化”，门槛低但区分度集中在早期轮次；对 reference DSL config 取比值，衡量的是“agent 在 DSL 空间内的搜索质量”，与 DSL 表达力上限对齐，最适合作为主指标。

指标口径要固定三件事：计时边界（是否含 kernel launch 开销、是否含 host-device 同步）、预热与重复次数（冷启动首轮是否计入）、以及统计量（中位数还是最小值）。计时边界不一致会让两个策略的分数差被 launch 开销淹没——小 shape 上 launch 开销占比高，含 launch 的计时会把 kernel 内部的 tile 优化差异压平。口径应在评测配方里写死并随负载一起版本化，任何口径变更都视为评测集换代。

基线类型score 语义主要代价适用阶段
框架内建算子相对成熟库的加速比库版本漂移导致跨期不可比；小 shape 上 launch 开销主导终局验收
朴素 tiled kernel相对未调优实现的基本优化增益门槛低，后期饱和无区分度早期冷启动
reference DSL configDSL 空间内的搜索质量参考配置本身需人工调优，维护成本主指标

一个具体例子：某 reduction 负载在极小 shape 上，框架基线的 launch 开销占端到端时延大头，agent 生成的 kernel 即便内部归约树更优，含 launch 计时下比值仍接近 1；改用 reference DSL config 且计时排除 launch 后，归约树差异才在 score 上显现。这说明基线类型与计时边界必须成对选择，不能各自独立设定。

四 · 硬件档位与配方绑定：同一 DSL 在不同架构上的有效域

DSL 字段的合法取值域隐含了硬件假设。共享内存布局字段的取值域若按某代架构的容量上限设定，换到共享内存更小的架构上，同一组决策会触发资源上限约束 R(d)≤R_max 而被拒，agent 收到的反馈是“字段非法”而非“该字段在此硬件上不可行”，两者对搜索的引导方向完全不同。配方必须把硬件档位与 DSL 约束绑定：每个档位声明自己的寄存器/共享内存/占用率上限，DSL 解析器按档位裁剪合法域，反馈里带上档位标识。

机制上，把硬件档位做成评测配方的一个维度，而非全局常量。同一负载在档位 A 上的最优 tile 在档位 B 上可能因占用率骤降而变差，score 必须在档位内归一（T_ref 取该档位下的参考实现），跨档位不做直接比较。代价是评测矩阵膨胀：负载数 × shape 类 × 档位数，测量次数成倍上升；若档位间差异只体现在容量上限，可只保留两个档位（宽松/紧张）以控制成本。

一个具体例子：流水线级数字段在共享内存宽松的档位上可取较大值以隐藏访存延迟，在紧张档位上该取值导致共享内存超限，lowering 前即被拒。若配方不区分档位，agent 会把“大级数”学成通用策略，换档位后整批决策失效，搜索需从头再来。绑定档位后，反馈精确到“该档位下流水线级数上限为 k”，agent 可在档位内快速收敛。

五 · 负载不对时的失效模式：分数失真与搜索误导

负载配方错误不会报错，只会让 score 悄悄失去意义。典型失效有三类。其一是天花板错位：评测集里混入 DSL 表达力外负载，agent 的最优可达 score 远低于 1，beam search 在这些负载上反复 keep-revert 却无法提升，预算被无效消耗；表现为整体收敛曲线提前平坦但平坦值偏低。其二是区分度塌缩：所有负载的最优实现都只依赖同一个 DSL 字段（如 tile 尺寸），其余字段从不成为性能主导，搜索退化为单字段枚举，agent 学不到多字段协同；表现为不同策略的 score 方差极小。其三是基线漂移：T_ref 取自会随环境变化的框架库，同一策略在不同时间评测得到不同分数，历史 keep-revert 决策失去可比性。

检测这三类失效需要配方自带诊断量：每个负载记录“参考 DSL config 的 score”（应接近 1，偏离则说明基线或口径有问题）、记录各 DSL 字段在最优策略中的激活频次（某字段长期零激活说明该字段在配方中无区分度）、记录 score 的跨策略方差（方差过低说明区分度塌缩）。这些诊断量不进入 score，只作为配方健康度指标随评测一起输出。

代价是配方维护成本：诊断量要求对每个负载额外跑参考配置与若干探针策略，单轮评测的测量次数上升，且配方每次调整都要重跑诊断基线。工程判断是：诊断量的成本远低于“用失真分数训练多轮 RL”的代价——后者会让策略收敛到配方漏洞而非真实优化能力，且漏洞在部署端才暴露。

一个具体例子：某配方中所有负载的 shape 都是 tile 整数倍，边界处理策略字段从未被激活，agent 生成的 kernel 在评测集上 score 接近 1，部署到真实非整除 shape 上因缺少尾块掩码而正确性失败。诊断量中“边界策略字段激活频次为零”本可提前暴露该配方缺陷，但若配方不带诊断，这一失效要到生产端才被发现。

负载配方决定 DSL 搜索的收益边界

策略 IR 的搜索效率建立在“合法配置空间可枚举”之上，而这一前提只在特定负载形态下成立。DSL 字段（tile 尺寸、线程映射、流水线级数、共享内存布局）本质上是为规则分块计算设计的，因此负载必须是计算密集、访存模式规整、shape 可静态推导的算子：GEMM、卷积、attention 的 fused kernel、layernorm/softmax 这类 reduction 都在射程内。反过来，动态 shape（变长序列、稀疏索引 gather）、数据依赖的控制流、跨 kernel 的全局同步，会让 DSL 的静态约束失效——lowering 器无法在编译期确定 tile 与边界策略，只能退化到保守配置，score 公式里的 $T_{\text{ref}}/T_{\text{kernel}}(d)$ 被压到接近 1，搜索退化成空转。评测配方必须与 DSL schema 对齐：若 schema 只覆盖两级流水线，就不要把需要三级流水线才能打满带宽的负载放进 $\mathcal{D}_{\text{DSL}}$，否则失败会被误记为“LLM 决策能力不足”而非“表达力缺口”。

基线选择直接决定 score 的语义。用朴素 PyTorch 实现做 $T_{\text{ref}}$ 会让几乎所有合法 DSL 配置都显得“加速”，掩盖 lowering 注入边界检查与同步原语带来的固定开销；用厂商库（cuBLAS/cuDNN）做基线则把目标变成“逼近手写最优”，此时 DSL 未覆盖的 warp-specialized 流水线就成为硬上限。工程上应双基线并行记录：库基线用于判断方案是否值得部署，朴素基线用于判断 DSL 决策是否真的在起作用。输入分布同样要写进配方——固定单一 shape 会让 beam search 过拟合到某个 tile 组合，切换到邻近 shape 时占用率骤降；正确性 oracle 需覆盖边界 shape（非 2 的幂、尾块不满、batch=1），否则 lowering 注入的边界检查可能从未被执行路径触发。指标计算上，score 的指示函数乘积意味着一次编译失败即归零，因此配方应把编译失败率与数值误差分开统计，避免把 lowering 缺陷记到 LLM 头上。

负载配错时的系统代价是可观测的：编译预算被无效 lowering 占满、beam 宽度被合法但无加速的配置挤占、token 消耗在重复生成同一批被 schema 拒绝的决策上。一个具体例子是 attention 的变长 decode：DSL 若只允许静态 tile，LLM 会反复尝试用固定 block 覆盖动态序列长度，解析器每次都因资源上限 $R(d)\le R_{\max}$ 或 $S(d)\le S_{\max}$ 拒绝，反馈虽精确到字段却无法收敛，整轮预算耗尽而 score 恒为零。判断标准应前置到配方设计：先用少量 shape 做 DSL 覆盖率探针，确认合法配置中存在能超过库基线的候选，再投入多轮搜索；否则应扩展 schema 或更换负载，而不是加大搜索轮次。
