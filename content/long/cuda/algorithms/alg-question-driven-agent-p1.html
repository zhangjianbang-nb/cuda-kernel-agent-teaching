一 · 一次“指标正确、结论错误”的翻车

设想一个典型的评测翻车场景。某轮 kernel 优化任务里，agent 拿到 NCU 报告：目标 kernel 的 SM 占用率不高，warp stall 里 long_scoreboard 占比突出，L2 命中率偏低。agent 据此判断“访存延迟是瓶颈”，于是把 tile 从 128×128 改成 64×256，想提高并发访存请求数。编译通过、正确性通过，性能却几乎不动，甚至略有回退。下一轮它继续沿这条线走：加 __ldg、改 unroll 因子、换 shared memory 布局，每一轮都有“合理”的指标依据，但每一轮都在同一个错误前提上做局部修补。若干轮后预算耗尽，性能曲线在某个平台期上反复横跳。

问题不在 agent 不会写 CUDA，而在它跳过了“提问”这一步：从“看到 long_scoreboard 高”直接跳到“改 tile 形状”，中间没有把“高 stall 是否真的由全局访存延迟造成”变成一个可证伪的命题。真实根因可能是 shared memory bank conflict 导致的串行化，也可能是 occupancy 被寄存器压力压死导致延迟无法被隐藏，还可能是这个 kernel 本来就是带宽受限、任何延迟优化都无效。这三种根因对应三种完全不同的动作，而指标表象是同一个。没有显式的假设与检验，agent 的修改与真实瓶颈不匹配，多轮迭代的边际收益迅速衰减——这正是问题驱动诊断式优化要解决的具体问题。

把这件事形式化，一次修改是否被接受，取决于两个条件的合取：

$$\Delta_{\text{opt}}=\frac{T_{\text{after}}-T_{\text{before}}}{T_{\text{before}}},\quad \text{accept if }\ \Delta_{\text{opt}}<-\epsilon\ \land\ \text{correct}$$

注意这个判据只回答“这次改动是否值得保留”，它不回答“为什么值得保留”。前者是搜索问题，后者是诊断问题。翻车案例的症结是：agent 把搜索当成了诊断，用接受判据代替了因果判断。当 Δ_opt 落在噪声区间内（|Δ_opt| 小于 ε），agent 既不能确认改动有效，也无法解释为什么无效，于是只能盲目再试一次。多轮之后，轨迹里全是“试了、没动、再试”，没有任何一条可复用的因果证据。

二 · 它解决的是“因果归属”，不是“搜索效率”

问题驱动诊断式优化的核心机制是：强制 agent 在每次修改前先提出可证伪的问题，设计微实验回答，再据答案决定动作。它把优化过程从“指标→改代码”的两段式，改成“指标→问题→微实验→结论→改代码”的闭环。这个闭环解决的是因果归属问题：给定一个观测到的现象（stall 高、带宽利用率低、occupancy 上不去），到底是哪个微架构机制在起作用。

具体步骤是一条固定流水线。第一，读取 NCU/SASS 指标，agent 生成 1–3 个关于瓶颈根因的可证伪问题，例如“是否 shared memory bank conflict 导致 stall”“是否寄存器压力把 occupancy 压到无法隐藏延迟”“是否这个 kernel 已触及 HBM 带宽上限”。第二，为每个问题设计最小微实验，只变一个变量：改 tile、改 swizzle、加 padding、换 pipeline 深度。第三，运行实验并采集指标，回答该问题（是/否/部分），记录证据。第四，基于答案选择优化动作并修改 kernel，编译、正确性、性能三重验证。第五，保留有效修改，更新问题库，进入下一轮直到瓶颈消除或预算耗尽。

关键在“可证伪”。一个合格的问题必须能通过一次单变量实验给出是/否的答案。以 bank conflict 为例，微实验可以是：在 shared memory 数组每行末尾加一个 padding 元素，使列访问错开 bank。若 stall 显著下降、性能改善，则“bank conflict 是根因”被证实；若指标纹丝不动，则被证伪，agent 应转向下一个假设而不是继续调 tile。这个实验的成本是一次编译加一次短跑，代价是轮次预算，收益是把一个模糊的“stall 高”拆成一个确定的机制判断。

与之对照，直接搜索（无提问、只按接受判据保留改动）在预算充足、瓶颈单一时更省轮次；但一旦瓶颈是多因耦合、指标表象与根因脱钩，直接搜索就会陷入前面描述的停滞。诊断式优化的代价明确：每轮多出提问与微实验开销，轮次成本上升，预算紧张时不如直接搜索。它的适用边界由此划出——它买的是“每轮改动的证据强度”，不是“每轮改动的数量”。

三 · 微实验的设计约束：单变量与最小可观测

微实验的伪代码骨架可以写成如下形式，重点在于“只变一个变量”和“先声明预期再执行”：

  • 读指标 M，从候选根因集合 H = {h1, h2, h3} 中选 1–3 个，对每个 hi 写出命题 Pi 与预期观测 Ei（若 hi 成立，指标 m 应如何变化）。
  • 对每个 Pi 构造变体 Vi：仅改动与 hi 对应的那一个旋钮（padding / swizzle / tile / pipeline 深度），其余保持基线。
  • 编译 Vi，跑正确性 oracle，再跑性能与指标采集；把实测 m 与预期 Ei 比对，输出 是/否/部分 并附证据（指标差值、SASS 差异）。
  • 若 是：把 hi 写入结论，据此选优化动作；若 否：把 hi 移出候选，进入下一假设；若 部分：缩小问题范围再提一个更细的子问题。

这套约束有明确的工程代价。单变量意味着每个假设要独占一次编译与一次跑分，编译时间与测量时延随假设数线性增长；若一个 kernel 编译需数十秒、跑分需数秒，三个假设就是数分钟的额外开销，在有限轮次预算里这是实打实的挤占。更隐蔽的代价是“最小可观测”：微实验的扰动必须大到能被指标分辨，又不能大到改变瓶颈本身。padding 加一个元素可能不足以错开 bank，加一整行又可能改变 shared memory 占用进而影响 occupancy，把单变量实验变成双变量。设计者必须在“扰动足够可见”和“扰动不引入新变量”之间取一个窄窗口，这个窗口依赖对具体 kernel 的访存模式的理解，而不是通用规则。

一个具体例子：某 reduction kernel 的 long_scoreboard 高，agent 提出两个假设——全局访存延迟未被隐藏，或 shared memory 写回存在 conflict。对第一个假设，微实验是把每线程处理的元素数翻倍（提高 ILP），预期 stall 下降；对第二个假设，微实验是给 shared 数组加 padding，预期 stall 下降。两个实验各只动一个旋钮，跑完后若只有 padding 版本改善，则根因锁定在 conflict，后续动作应是重排写回索引而非加大 ILP。若两个都无改善，则第三个假设——带宽已饱和——应被提出，此时任何延迟侧优化都无效，正确动作是减少总访存量而非调延迟。

四 · 它不解决什么：问题质量的上限与预算的下限

这个方法有两条硬边界，越过边界它就不比直接搜索更好。

第一条是问题质量依赖模型对 GPU 微架构的理解。问题提错会把优化引向错误方向，而且错误的问题往往能自洽地“被证实”——因为微实验的预期本身写错了。例如 agent 误以为某 kernel 是 compute-bound，提出“减少指令数能提速”，微实验删掉一段边界检查后性能略升，它便认定 compute 是瓶颈；但真实情况是删边界检查减少了分支发散，收益来自控制流而非算术吞吐。这种“证实的假阳性”比直接搜索更危险，因为它产出了一条看似有证据、实则归因错误的轨迹，若被用作 SFT 数据会污染训练信号。因此问题库需要与 SASS/warp stall 的细粒度剖析对齐，让每个问题都能落到具体指令与 stall 类型上，而不是停在“compute-bound / memory-bound”这种粗粒度标签。

第二条是预算。每轮多出提问与微实验开销，轮次成本上升。当总预算只够少数几轮时，把一轮拆成“提问+实验+修改”三段，实际可用于探索的修改次数被压缩，此时直接搜索的期望收益更高。诊断式优化的经济性只在“多轮、瓶颈耦合、指标表象与根因脱钩”这三个条件同时成立时才占优；缺一个条件，它的额外开销就换不回相应的证据强度。

还有一层不解决的东西：它不替代正确性 oracle。微实验的结论只回答“瓶颈在哪”，不回答“改动后是否仍正确”。任何被接受的修改仍须过正确性校验与合约校验，诊断闭环与正确性闭环是两条并行流水线，不能互相顶替。把“实验显示性能改善”当成“可以合并”的信号，是把因果判断误当成验收判断，这是另一类翻车。

五 · 适用边界的判定：三个可操作信号

把适用边界落成可判定的信号，工程上可以看三件事。

信号指向诊断式优化指向直接搜索
多轮后 Δ_opt 落入噪声区间且轨迹重复是：说明缺因果归属，需提问拆解否：说明只是搜索步长问题
指标表象与候选根因一对多（同一 stall 对应多种机制）是：单变量微实验可分辨否：随机改动难以收敛
轮次预算 vs 单次编译+跑分成本预算充裕时成立预算紧张时优先

第一行对应翻车案例的典型形态：性能曲线平台化、改动方向在几个旋钮间来回。此时继续加大搜索强度只会增加无效改动，正确动作是停下来提问。第二行是诊断式优化的主战场：当 long_scoreboard 高既可能是全局延迟也可能是 conflict 串行化时，只有单变量实验能把一对多拆成一對一。第三行是纯经济性判断：若单次编译加跑分耗时接近一轮预算的可观比例，提问开销就会挤掉探索空间。

反过来，若瓶颈单一且指标与根因一一对应（例如一个纯 elementwise kernel，带宽利用率已接近上限），提问环节就是纯开销，直接搜索或干脆判定“已触及带宽上限、停止优化”更合理。诊断式优化的价值随“指标—根因映射的模糊度”上升，随“预算/单轮成本比”下降，这两个量共同决定它是否值得启用。

最后落在机制上：这个方法的工程判断点不在“要不要提问”，而在“问题是否可被一次单变量实验证伪”。一个不可证伪的问题（“这个 kernel 是不是不够快”）不产生信息，只消耗轮次；一个可证伪但预期写错的问题会产生假阳性证据，污染问题库与后续轨迹。因此启用它的前置条件是问题库与 NCU/SASS 指标层级对齐、微实验旋钮与假设一一对应、以及一条独立的正确性流水线兜底。三者缺一，诊断闭环就会退化成“带解释的盲目搜索”，开销照付，证据不增。

诊断式优化的适用边界：它救不了什么，又会付出什么

这套方法的前提是：瓶颈的根因可以被表达成一个可证伪的命题，并且存在一个只改一个变量就能观测到差异的微实验。一旦这个前提不成立，闭环就退化成昂贵的空转。典型失效有三类。其一是根因不可分离：当 occupancy、寄存器压力、访存合并与指令级并行同时耦合时，单变量微实验无法把信号从噪声里剥离——改 tile 会同时改变 L2 命中率与 warp 数，改 padding 会同时改变 bank 分布与共享内存占用，实验结论因此不可归因。其二是问题库先验错误：agent 若把 NCU 的 stall 归因于 bank conflict，而真实原因是长依赖链导致的 scoreboard stall，那么后续所有微实验都在为一个不存在的假设收集证据，多轮迭代的边际收益迅速归零。其三是预算约束下的机会成本：每轮多出的提问、微实验编译与正确性验证，直接抬高单轮时延与 token 消耗；当 kernel 的搜索空间本身很窄、直接枚举几种 tile 配置就能命中时，诊断开销反而拖慢收敛。

判断是否该用，可以看一个简单的接受准则。设一次候选修改前后的实测时延为 $$\Delta_{\text{opt}}=\frac{T_{\text{after}}-T_{\text{before}}}{T_{\text{before}}},\quad \text{accept if }\ \Delta_{\text{opt}}<-\epsilon\ \land\ \text{correct}$$ 诊断式方法的代价在于它把“产生一个候选修改”的成本从一次编译抬高到一次编译加一次微实验加一次证据记录。若 $$\epsilon$$ 本身小于测量噪声（例如 kernel 时延抖动与 GPU 时钟波动同量级），那么微实验回答的“是/否”并不比随机猜测更可靠，此时应退回直接搜索而非继续提问。反过来，当单次编译时间很长（大 kernel、CuTe 模板实例化、PTX 级手写）时，盲目试错的代价高于诊断，闭环才有正收益。

系统代价需要按维度记账，而不是笼统地说“变慢”。下表给出四类开销的来源与它们真正侵蚀的资源：

开销项来源被侵蚀的资源何时可忽略
提问生成读取 NCU/SASS 指标后由 agent 产出 1–3 个可证伪问题token 预算、上下文长度指标维度少、问题模板稳定时
微实验编译改 tile / swizzle / padding / pipeline 深度各编译一次墙钟时间、编译缓存kernel 小、编译在秒级时

一个具体例子能说明边界在哪里。假设某 fused kernel 的 NCU 显示长板 stall 占比高，agent 提出“是否 shared memory bank conflict 导致 stall”，微实验只加 padding 改 bank 分布，结果时延无变化——这正确否定了该假设，但也暴露出方法的天花板：它只能否定被提出的假设，无法发现没人想到的根因。若真实瓶颈是 global memory 的访问粒度与 L2 sector 利用率，那么 padding 实验的“否”会被误读为“共享内存无关”，进而把优化方向引向错误的指令重排。此时正确的动作不是继续加实验，而是先扩展问题库的候选集，或直接退化为对访存模式的粗粒度扫描。诊断式优化的价值不在于它总能找到答案，而在于它把“改代码”之前的那一步显式化，并让每一次无效改动都留下可复核的否定证据；代价则是它要求问题质量与测量信噪比同时达标，缺一不可。
