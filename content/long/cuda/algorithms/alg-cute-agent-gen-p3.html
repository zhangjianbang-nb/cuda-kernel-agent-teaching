一 · SOL 评分公式的逐项拆解与归一化推导

评分公式 $$\text{SOL}=\max\left(\frac{F}{F_{\text{peak}}},\frac{B}{B_{\text{peak}}}\right),\quad \text{score}=\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}\cdot\mathbb{1}[\text{correct}]$$ 的核心是把“绝对性能”压成“相对峰值利用率”，再在生成 kernel 与参考 kernel 之间做比值。逐项看：\(F\) 是实测浮点吞吐（FLOP/s），\(F_{\text{peak}}\) 是该架构在该 dtype 下的理论峰值；\(B\) 是实测有效带宽（Byte/s），\(B_{\text{peak}}\) 是 HBM 理论带宽。取 max 而非 min 的原因在于：一个 kernel 若受限于计算，则带宽项必然远低于 1，取 max 让评分反映“最紧的那条 roofline 约束被满足到什么程度”，而不是被非瓶颈资源拖低。这一步推导的关键在于 roofline 模型本身：设算术强度 \(I=F/B\)（FLOP/Byte），则 kernel 的理论最短时间 \(T_{\min}=\max(F/F_{\text{peak}},\,B/B_{\text{peak}})^{-1}\)，于是 SOL 恰好是 \(T_{\min}/T_{\text{actual}}\) 的倒数形式——SOL 高即实际时间逼近 roofline 下界。

分母 \(\text{SOL}_{\text{ref}}\) 用参考实现（如 CUTLASS 手写 kernel 或 cuBLAS）的 SOL 做归一，是为了消除“不同 shape 天然可达上限不同”的偏差：小 shape 的 GEMM 因 launch 开销和尾部效应本就难以接近峰值，直接拿绝对 SOL 评分会系统性惩罚小 shape 的生成结果。归一后 score=1 意味着生成 kernel 与参考持平，>1 意味着超越。指示函数 \(\mathbb{1}[\text{correct}]\) 是硬门：正确性 oracle 不通过则 score 归零，防止“快但错”的 kernel 拿到高分。代价层面，这个公式对测量噪声敏感——\(F\) 与 \(B\) 由 NCU 采集，单次采样抖动会直接进入分子；工程上需多次采样取中位数，这带来额外 profiling 时延（每次 NCU 采集本身有秒级开销），在搜索轮数多时累积可观。具体例子：一个 sm90 上的 fp16 GEMM，若生成 kernel 的 tensor core 利用率只有参考的六成，则 \(\text{SOL}_{\text{gen}}/\text{SOL}_{\text{ref}}\approx0.6\)，即便正确性通过，score 也只有 0.6，搜索器应据此把该 layout 组合标记为 revert。

二 · 时延与编译开销的预算公式

CuTe 布局搜索的总预算不是单轮生成时间，而是“生成 + 模板实例化编译 + 运行 + profile”的串行叠加。设搜索轮数为 \(N\)，第 \(i\) 轮的 LLM 生成 token 数为 \(t_i\)、编译耗时为 \(c_i\)、运行与 profile 耗时为 \(r_i\)，则总墙钟时间 $$T_{\text{total}}=\sum_{i=1}^{N}\left(\alpha\, t_i + c_i + r_i\right)$$ 其中 \(\alpha\) 是每 token 的解码时延系数。推导的关键一步是把 \(c_i\) 从常数视为变量：CuTe 模板实例化的编译时间随 layout 组合的嵌套深度增长，一个多层 tiled_copy 加 swizzle 的实例化可能触发大量模板展开，编译时间在预算中占比可能超过生成开销——这正是该路线在预算敏感场景不划算的根源。因此搜索器需要把“编译失败”也计入成本：失败轮次 \(c_i\) 照付但无产出，等价于负收益。

伪代码层面，预算控制应写成显式的早停条件：维护累计耗时 T_used，每轮开始前检查 T_used + c_est > T_budget 则停止；c_est 用上一轮同类 layout 的编译耗时做估计。另一个可实现的优化是把编译缓存的键设为 layout 参数的规范化元组（MMA atom、tile shape、swizzle 模式、stage 数），命中缓存则跳过实例化，把 \(c_i\) 压到近零。代价是缓存本身占显存/磁盘，且键的规范化若漏掉某个隐含参数（如 shared memory 对齐）会导致错误命中，必须靠正确性 oracle 兜底。具体例子：某轮 LLM 生成了一个 stage=4 的 pipeline layout，编译耗时显著高于 stage=2 的同类组合，若预算只剩两轮，搜索器应优先尝试 stage=2 的变体而非继续深挖 stage=4，因为后者的边际编译成本已经吃掉可能的性能收益。

三 · 显存与共享内存约束的可行性判定

CuTe layout 搜索中大量组合在编译期就被显存约束淘汰，提前判定能省下整轮编译。共享内存占用由 tile shape 与 pipeline stage 共同决定：设单 stage 的 A、B 分块字节数为 \(S_A\)、\(S_B\)，stage 数为 \(k\)，双缓冲系数为 2，则 $$M_{\text{smem}}=2k\,(S_A+S_B)+M_{\text{extra}}$$ 其中 \(M_{\text{extra}}\) 是 MMA atom 的寄存器溢出与 epilogue 缓冲。可行性条件是 \(M_{\text{smem}}\le M_{\text{smem,max}}\)（该架构每 SM 的共享内存上限）。推导的关键一步是把 \(S_A\)、\(S_B\) 写成 tile shape 与 dtype 宽度的乘积：\(S_A = T_M \times T_K \times \text{sizeof(dtype)}\)，于是 tile shape 的枚举空间被这条不等式直接切掉一大块——例如在共享内存上限固定的架构上，\(T_M\) 与 \(T_K\) 同时取大值会立刻越界，搜索器应在枚举阶段就过滤，而不是交给编译器报错。

全局显存侧则约束输出 tile 与 workspace：attention 类算子的中间 softmax 统计量、split-K 的归约缓冲都会占显存，split-K 因子 \(s\) 增大时 workspace 线性增长，且归约步骤引入额外时延。伪代码上，可行性判定函数应在 LLM 生成之前运行：输入 shape、dtype、架构，输出合法 (tile, stage, split-K) 三元组集合，LLM 只在该集合内组合。代价是判定函数本身要做架构参数查表，若表过期（新架构 smem 上限变化）会误杀合法组合；工程上把上限做成可配置常量而非硬编码。具体例子：一个 \(T_M=128, T_K=64\) 的 fp16 tile 在 stage=3 时，仅 A、B 双缓冲就逼近共享内存上限，此时 epilogue 缓冲若再占用一块就会编译期静态断言失败——这正是 CuTe 类型系统把显存错误变成编译期错误的体现，回灌给 LLM 的错误信息应明确指出是哪一项越界。

四 · 正确性误差界与 oracle 判定公式

正确性 oracle 用 fp64 参考实现做基准，判定公式为逐元素相对误差与绝对误差的混合界：$$\text{err}=\max_{i}\frac{|y_i-\hat{y}_i|}{\max(|y_i|,\epsilon)},\quad \text{pass}=\text{err}\le \tau_{\text{dtype}}$$ 其中 \(y_i\) 是 fp64 参考值，\(\hat{y}_i\) 是生成 kernel 的输出，\(\epsilon\) 是防止除零的小量，\(\tau_{\text{dtype}}\) 随 dtype 变化（fp16 的累积误差天然大于 fp32）。推导的关键一步是认识到 GEMM 的误差随归约长度 \(K\) 增长：fp16 输入的 tensor core 累加在 fp32 中进行，但输入量化误差按 \(\sqrt{K}\) 量级累积，因此 \(\tau\) 不能取固定常数，而应随 \(K\) 缩放，否则长 \(K\) 的合法 kernel 会被误判为错。这一步直接决定 oracle 的假阴性率。

代价在于 fp64 参考实现本身的运行开销：fp64 在消费级/部分数据中心 GPU 上吞吐远低于 fp16，参考计算可能比被测 kernel 慢一个数量级以上，成为正确性验证的时延瓶颈。工程上可用分块抽样：只对部分输出 tile 做 fp64 比对，其余用低精度参考加误差传播上界兜底，但这引入漏检风险——一个只在未抽样 tile 上出错的 layout 会蒙混过关。伪代码上，oracle 应返回结构化结果而非布尔值：{pass, max_err, err_tile_idx}，err_tile_idx 回灌给 LLM 时能指向具体是哪个 tile 的 layout 映射错了（如 swizzle 方向反了导致行列互换），比一句“不正确”信息量大得多。具体例子：某生成 kernel 编译通过、性能接近参考，但 oracle 报出某几个 tile 的误差远超界，追查发现是 tiled_copy 的 thread-value layout 与 shared memory layout 的复合顺序写反，这类“编译通过但语义错”的 layout 正是 CuTe 路线必须靠强 oracle 兜底的典型场景。

五 · 奖励函数与搜索信号的构造

把 score 直接当奖励有两个缺陷：一是正确性硬门让搜索在早期几乎全是零奖励，梯度信号稀疏；二是编译失败轮次无任何信号。因此奖励应做分层构造：$$R=\mathbb{1}[\text{compile}]\cdot\left(w_c\,\mathbb{1}[\text{correct}]\cdot\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}+w_p\,\text{prog}\right)-w_f\,\mathbb{1}[\text{fail}]$$ 其中 \(\text{prog}\) 是过程信号（如 NCU 采集到的 tensor core 利用率相对上一轮的提升、bank conflict 数量的下降），\(w_c, w_p, w_f\) 是权重。推导的关键一步是把“编译通过”作为乘性门而非加性项：编译失败时整轮奖励为零甚至为负，避免搜索器奖励“生成了语法正确但无法实例化”的代码。过程信号 \(\text{prog}\) 的存在让搜索在尚未达到正确性时也能获得方向性反馈——例如某轮 layout 虽然数值错，但 NCU 显示 bank conflict 显著下降，说明 swizzle 方向选对了，只是映射细节有误，这一信号应被保留。

代价是权重调参本身消耗预算：\(w_p\) 过大时搜索器可能追逐 profile 指标而忽略正确性，\(w_f\) 过大时则过度保守、不敢尝试高风险 layout。伪代码上，奖励计算应在每轮结束时立即执行并把结果连同结构化错误一起写入搜索日志，供 keep-revert 决策使用。具体例子：一轮生成把 swizzle 从无改为 128B swizzle，编译通过、NCU 显示共享内存 bank conflict 从高位降到接近零，但 oracle 报错——此时奖励应为负（正确性门未过），但过程信号记录下“swizzle 方向正确”，下一轮 LLM 修正映射细节时保留该 swizzle 选择，收敛显著加快。这正是把 profile 指标回灌为过程奖励、而非仅作最终评分的工程价值。

六 · 从公式到可实现伪代码的落地

把上述公式串成一轮可执行的搜索循环，伪代码骨架如下（文字描述，不写代码块）：初始化合法组合集合 \(\mathcal{C}\) 由可行性判定函数给出；对每轮，从 \(\mathcal{C}\) 采样一个 layout 参数元组，查编译缓存，未命中则调 LLM 生成 CuTe 骨架并实例化编译；编译失败则把静态断言错误文本回灌、记 \(R=-w_f\)、continue；编译成功则跑 fp64 oracle 与 NCU profile，按上节公式算 \(R\)，若 \(R\) 优于当前最优则 keep 并更新最优参数，否则 revert；累计 \(T_{\text{used}}\)，超预算则跳出。关键实现点是错误回灌的格式化：CuTe 的静态断言输出冗长，需截取到“哪个 layout 的哪个维度不匹配”这一层再喂给 LLM，否则 token 消耗爆炸——这一步的 token 代价直接进入第一节的 \(t_i\) 项。

另一个落地细节是 keep-revert 的判据不能只看 \(R\) 的瞬时值：由于 NCU 采样抖动，单轮 \(R\) 的方差可能吞掉真实提升，工程上应对同一参数重复采样取中位数再比较，或引入滑动窗口。代价是重复采样让每轮 \(r_i\) 翻倍，与编译开销叠加后预算更紧。具体例子：某轮把 tile shape 从 \(128\times128\) 改为 \(128\times256\)，编译时间因模板嵌套加深而上升，NCU 首次采样显示利用率提升但第二次采样回落，若不做重复采样就会误 keep 一个实际无收益的 layout，后续轮次围绕它做变异全部浪费——这解释了为什么奖励公式必须与测量协议绑定，而不能孤立地看公式本身。

评分公式的失效边界：当 SOL 比值失去分辨力

本部分给出的 $$\text{SOL}=\max\left(\frac{F}{F_{\text{peak}}},\frac{B}{B_{\text{peak}}}\right),\quad \text{score}=\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}\cdot\mathbb{1}[\text{correct}]$$ 在布局搜索里承担的是「排序信号」而非「绝对性能」的角色，这一点决定了它的适用边界。取 max 而非加权和的动机很直接：一个 kernel 的时延由计算与访存两条路径中较慢者决定，若 F/F_peak 已经接近 1，则继续压 B/B_peak 不会带来端到端收益，max 自动把优化压力导向真正的瓶颈侧。但 max 的代价是**梯度消失**：当两个比值都远低于峰值（例如小 shape 下 launch 开销与尾部 wave 主导），SOL 对布局参数几乎不敏感，keep-revert 搜索会退化为随机游走。此时应改用 NCU 的细分指标（tensor core 利用率、shared memory bank conflict 次数、DRAM 吞吐占峰值比）作为中间奖励，把 SOL 只留作最终验收。score 中的指示函数同样有陷阱：正确性 oracle 用 fp64 参考实现，对 fp16/bf16 累加路径必须给定容差，容差过紧会把合法的重排累加判错，过松则放过「编译通过但语义错」的 swizzle 置换——后者恰恰是 LLM 写 CuTe 时最常见的失效模式。

推导的关键一步在于把 SOL 从「整 kernel 时间」拆到「单次 tile 迭代的稳态段」。设总时延 T = T_launch + T_prologue + N_iter·T_iter + T_epilogue，SOL 只在 N_iter·T_iter 主导时才可信。对 GEMM，T_iter 的下界由 MMA atom 的指令吞吐与 tiled_copy 的 shared→register 搬运共同决定，前者给出 F 侧上限，后者给出 B 侧上限；布局搜索真正能动的是后者——swizzle 决定 shared memory 的 bank 分布，tile shape 决定每 stage 的字节数与 pipeline 深度。因此搜索变量应被约束为 (tile_m, tile_n, tile_k, swizzle_bits, stages) 这五元组，而 MMA atom 与 dtype 由目标架构（sm80 的 mma.sync 与 sm90 的 wgmma/tma 路径不同）先行锁定。伪代码层面，keep-revert 循环应写成：对候选参数实例化 CuTe 模板 → 编译（静态断言失败则把错误文本回灌 LLM 修正 layout 参数）→ 跑 fp64 oracle → NCU 采集 → 计算 score → 仅在 score 提升时保留。注意编译失败与运行错误必须走不同回灌通道，否则 LLM 会把类型错误当成语义错误去改 tile shape。

系统代价集中在编译预算上，这是本方案最硬的边界。CuTe 的 Layout/Tensor/MMA 是重度模板元编程，每个候选参数组合都是一次完整实例化，编译时间随 tiled_mma 与 tiled_copy 的嵌套层数增长，单轮搜索的编译开销可以超过 LLM 生成开销本身——预算敏感场景下，枚举宽度必须按「编译次数 × 单次编译时延」反推，而不是按参数量自由展开。可行的缓解是把搜索分层：先用低成本代理（仅编译不含 MMA 的 layout 静态检查，或复用已实例化的相邻参数做增量编译）粗筛掉明显非法的 swizzle 组合，再对少量候选做全量实例化与 NCU profile。另一项代价是正确性兜底的显存与时间：fp64 参考实现对小 shape 尚可，对大 GEMM 需分块比对，oracle 本身会占用可观显存并拉长单轮验证时延。工程判断是：当目标 shape 的 N_iter 不足以让稳态段主导时（小 batch、decode 阶段 attention），SOL 比值与布局参数的相关性弱到不足以驱动搜索，此时应把预算转向 launch 配置与 epilogue 融合，而不是继续在 swizzle 空间里做 keep-revert。

失效条件表现应对
小 shape，launch/尾部 wave 主导SOL 对布局不敏感，搜索随机游走改用 NCU 细分指标作中间奖励
oracle 容差失配合法重排被判错，或语义错 swizzle 被放过按 dtype 定容差，加置换不变性检查

搜索预算的硬边界：编译时延、语义错与 SOL 分母的失效

这套流程的收敛速度不由 LLM 的 token 生成决定，而由 CuTe 模板实例化的编译时延决定。每个候选 layout 组合（MMA atom × swizzle × tile shape × pipeline stage）都触发一次完整的模板展开与 ptxas 编译，编译开销与候选数线性相乘，而 NCU profile 又必须在编译成功之后才能启动，于是单轮迭代的时延被拉长为「生成 + 编译 + 运行 + 采集」四段串联。当候选空间按 tile shape 与 swizzle 的笛卡尔积展开时，keep-revert 搜索的有效吞吐被编译墙直接截断：预算敏感的场景里，把搜索限制在少数几个已知合法的 atom 组合上，比扩大枚举宽度更划算，因为多出来的候选大概率在编译期就被静态断言拒绝，白白消耗了时延。

更隐蔽的失效条件是「编译通过但语义错」。CuTe 的类型系统只能保证 layout 的代数结构自洽——stride、cosize、swizzle 位运算合法——却无法保证该 layout 与目标算子的数据搬运语义一致。一个把 shared memory 的 swizzle 施加在错误维度上的 tiled_copy，能顺利实例化、能跑出非零结果，却在 fp64 oracle 下暴露出转置或越界读。此时评分公式的指示函数成为唯一闸门：

$$\text{score}=\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}\cdot\mathbb{1}[\text{correct}]$$

指示函数取零意味着前面所有 NCU 采集到的 tensor core 利用率与 DRAM 吞吐全部作废——错误 kernel 的 SOL 再高也不进入分子。这要求 oracle 必须前置到 profile 之前，且覆盖边界 shape（非对齐 M/N/K、奇数列），否则搜索会被「高分错误解」污染。代价体现在显存与带宽上：fp64 参考实现本身占用数倍于 fp16 工作集的显存，大 shape 下 oracle 的一次性开销可能超过单次 kernel 运行，必须分块比对以压低峰值占用。

分母 SOL_ref 的可靠性同样构成边界。若参考实现本身未达峰值，比值会被系统性放大，搜索会奖励「相对参考更快但绝对远离 roofline」的解。工程判断是：把 SOL 公式拆成访存与计算两支取 max，

$$\text{SOL}=\max\left(\frac{F}{F_{\text{peak}}},\frac{B}{B_{\text{peak}}}\right)$$

当算子处于 memory-bound 区间时，分子由 B/B_peak 主导，此时 tensor core 利用率指标对搜索几乎无梯度，NCU 驱动的 keep-revert 会退化为随机游走；只有确认算子落在 compute-bound 侧，布局搜索的收益才与编译代价相称。
