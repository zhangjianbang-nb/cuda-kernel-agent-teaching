一 · 步骤零：确定采集范围与重放预算

把 NCU 指标回灌拆成可执行流水线，第一步不是跑 ncu，而是决定“这一次到底采什么”。ncu --set full 会展开成数百个 metric、多趟 replay，单次 profile 的耗时是裸跑的 10–100×，因此它天然不能挂在每一轮优化循环上。工程上要把采集分成两档：快档用自定义 metric 集（10–20 个关键指标，通常 1–3 趟 replay），用于每轮迭代；慢档用 --set full 或 sectional 采集，只在候选 kernel 通过正确性门之后、准备晋级时跑一次。快档的输入是“编译产物 + 一组固定 shape 的 launch 配置”，输出是原始 metric 的 CSV/JSON；代价是每次迭代额外付出一次串行化重放的墙钟时间，且 replay 会改变 cache 预热状态，使被测 kernel 的 L2 命中率偏离真实端到端场景。具体例子：一个 4096×4096 的 GEMM，裸跑约几十微秒量级，而快档 profile 因为要 replay 数次并做 clock lock，实际耗时被放大到毫秒级——这决定了你一轮 agent 迭代里只能负担一次快档采集，不能对每个候选变体都跑。

这一步的工程判断是：把 profile 预算当成和 token 预算同级的稀缺资源来分配。常见做法是每轮只 profile 当前最优候选与一个新变异体，其余变体靠静态分析或轻量计时筛掉。若把快档采集铺到所有候选上，重放开销会直接吃掉搜索吞吐，agent 的迭代次数下降，反而降低最终质量。

二 · 步骤一：原始计数器采集与派生量计算

采集阶段只负责把硬件计数器读出来，不做判断。典型指标集包括 DRAM 吞吐、SM 利用率、achieved occupancy、L2 命中率、以及若干 stall 原因计数（long scoreboard、barrier、short scoreboard、MIO throttle 等）。这里有一个容易踩的坑：NCU 报的 occupancy 是 achieved occupancy（实际驻留 warp 数占理论上限的比例），它和“理论 occupancy”不是一回事；用理论值做瓶颈判断会把寄存器压力导致的低驻留误读成调度问题。派生量在这一步算出来，而不是留给 agent 心算：

$$\text{Bound}=\begin{cases}\text{memory}, & \frac{\text{DRAM}_{\text{throughput}}}{B_{\text{peak}}}>0.8\\ \text{compute}, & \frac{\text{SM}_{\text{util}}}{1}>0.8\\ \text{latency}, & \text{otherwise}\end{cases},\quad \text{Feedback}=f(\text{Bound},\text{Top-3 stalls})$$

注意这个分类是三选一的粗粒度判决，阈值 0.8 是经验约定而非物理常数。它的代价在于：当 DRAM 吞吐占比落在 0.6–0.8 的灰区、SM 利用率也接近 0.8 时，判决对测量噪声极其敏感，同一 kernel 两次 profile 可能落到不同分支。因此派生量计算要带上原始数值一起回灌，让 agent 看到“DRAM 0.72 / SM 0.55”这样的组合，而不是只看到 “memory-bound” 这个标签。具体例子：一个 elementwise 归一化 kernel，DRAM 吞吐占比 0.78、SM 利用率 0.3，按规则判 memory-bound；但如果它的 L2 命中率很高、实际 DRAM 流量被压缩，agent 若只读标签就会去减少访存，而真正的收益点可能是提高 ILP 掩盖 long scoreboard 延迟。

三 · 步骤二：Top-3 stall 归因与反馈块压缩

分类给出方向，stall 给出抓手。NCU 的 warp stall 采样按“每个 warp 在每个 issue slot 上因何未能发射”计数，把计数排序取前三，就得到这一轮最该处理的三个阻塞源。压缩成反馈块时要做两件事：保留数值（占比、绝对计数、对应 metric 名），给出可操作映射（long scoreboard → 提高访存并行度或预取；barrier → 减少同步点或改成分段同步；MIO throttle → 降低共享内存/特殊函数吞吐压力）。反馈块硬约束在 ≤200 token，因为它是拼进下一轮 prompt 的，token 开销直接换算成上下文预算与推理成本。一个可用的模板是：

  • 判决行：bound=memory, DRAM%=0.83, SM%=0.41, occ=0.62, L2hit=0.71
  • stall 行：top1=long_scoreboard(38%), top2=barrier(21%), top3=mio_throttle(9%)
  • 动作提示：DRAM 已饱和 → 优先减少全局访存与提升复用，而非增加计算

这一步的代价是双重的：一是压缩本身有信息损失，Top-3 之外的 stall（比如占比 8% 的 dispatch stall）被丢弃，可能恰好是某个变体的关键；二是“动作提示”由规则生成，规则错了就把 agent 引到错误方向。具体例子：一个 reduction kernel 的 top1 是 barrier（占比高），规则提示“减少同步点”，但真正原因是 block 内归约树深度太大导致每轮都要全 block 同步——此时正确动作是改成分层归约（warp 内 shuffle + 跨 warp 共享内存），而不是简单删同步。所以反馈块里的动作提示应写成“方向 + 可选动作集”，把最终选择权留给 agent 的策略层。

四 · 步骤三：回灌注入与 agent 动作选择

反馈块拼接到下一轮 prompt 的位置很关键。放在 system prompt 尾部会被后续长上下文稀释；放在“当前候选 kernel 源码 + 上一轮时延”之后、紧邻“请给出下一版”之前，注意力权重最高。注入格式建议是结构化键值而非散文，因为 agent 在生成 CUDA 代码时对键值对的遵循率高于对自然语言描述的遵循率。回灌之后，agent 的动作空间应当被反馈收窄：memory-bound 判决下，优先动作是增大 tile 提升复用、改 swizzle 改善合并访存、把中间结果留在 shared memory；compute-bound 判决下，优先动作是减少冗余计算、用更快的数学指令、提高 ILP；latency-bound 判决下，优先动作是提高 occupancy（降寄存器压力）、增加独立访存流、软件流水。这一步的输入是反馈块 + 上一版源码 + 时延，输出是下一版源码或参数变更；代价是 prompt token 增长（每轮多 200 token 量级）以及“反馈误导”带来的无效变异——agent 可能忠实执行了错误提示，生成一个方向对但收益为负的版本，浪费一轮编译与验证。

具体例子：CudaForge 类硬件反馈回路里，agent 收到 “DRAM 已饱和，应减少访存而非加计算” 后，把原来每线程读 4 个元素的向量化改成读 8 个并复用寄存器，DRAM 流量下降、时延改善；反过来，若反馈误判为 compute-bound，agent 会去加 FMA 而实际瓶颈在 long scoreboard，结果是时延不变甚至变差。这说明回灌的价值不在“给了信息”，而在“信息与真实瓶颈一致”。

五 · 步骤四：验证门与反馈可信度校准

回灌循环必须有一个验证门把“指标改善”与“端到端收益”对齐。做法是：agent 产出新版本后，先跑正确性 oracle（与 fp64 参考比对或合约校验，这部分机制见同模块其他条目），再跑裸计时得到端到端时延，最后才决定是否值得再花一次 profile 预算。这里的关键判断是指标改善不等于收益：DRAM 吞吐占比从 0.83 降到 0.70 可能只是把访存挪到了 L2，端到端时延未必下降；SM 利用率上升也可能是无效计算增多。因此验证门要同时看三个量：正确性通过、端到端时延不劣化、profile 判决方向与预期动作一致。代价是每轮多一次裸跑与一次正确性检查的墙钟开销，以及“指标与收益背离”时的判定成本——需要人工或规则决定是回退还是继续。

反馈可信度还需要校准：同一 kernel 在不同 clock 状态、不同 replay 次数下，DRAM 吞吐占比会有几个百分点的漂移。工程上常用做法是对快档采集做 2–3 次重复取中位数，并把“判决边界附近的样本”标记为不确定，让 agent 在灰区同时尝试两个方向而不是押注单一判决。具体例子：一个 transpose kernel 的 DRAM 占比在两次 profile 中分别是 0.79 和 0.82，跨越了 0.8 阈值，若只按单次结果回灌，agent 会在“减少访存”和“提高 occupancy”之间来回震荡；标记为不确定后，agent 可以生成两个变体并行验证，用端到端时延做最终裁决。

六 · 步骤五：反馈作为 reward shaping 的中间信号

把结构化反馈接进 RL 或多轮搜索时，它不只是 prompt 内容，还可以作为稠密奖励的中间信号，缓解“只有最终时延”的稀疏奖励问题。可行形式是：以判决方向与动作的一致性给部分分，以指标改善幅度给塑形项，最终奖励仍以端到端时延与正确性为准。这样做的代价是奖励黑客风险——agent 可能学会“让 DRAM 占比下降”而不真正提速，例如把访存改成低效但流量小的模式。因此塑形项必须与验证门绑定：只有正确性通过且端到端不劣化的变异才计入塑形。具体例子：一个 softmax kernel，agent 通过减少中间张量写回把 DRAM 流量降下来，指标好看但引入了额外同步，端到端反而变慢；若塑形只看 DRAM 占比就会奖励这个错误方向，绑定端到端门后该变异被拒绝，反馈信号回到正确轨道。

整条流水线的工程判断可以归结为一句：profile 预算是稀缺资源，反馈块是压缩后的有损信道，验证门是唯一可信的裁决者。每一步的输入输出与代价必须显式记账——采集的 replay 放大、压缩的 token 与信息损失、回灌的 prompt 成本、验证的墙钟开销、塑形的黑客风险——否则 agent 会在“指标变好”的幻觉里空转。落地时把快档采集限制在每轮一次、把反馈块控制在 200 token 内、把判决灰区标为不确定、把塑形项挂在端到端门上，这四条约束共同决定了 NCU 回灌能否真正转化为 kernel 质量的提升，而不是一堆好看的计数器读数。

反馈回灌的失效边界与系统代价

把 NCU 指标回灌进 prompt 的链路并非无条件成立，它的第一个失效点在于分类器本身的判别力。公式里的阈值判据 $$\text{Bound}=\begin{cases}\text{memory}, & \frac{\text{DRAM}_{\text{throughput}}}{B_{\text{peak}}}>0.8\\ \text{compute}, & \frac{\text{SM}_{\text{util}}}{1}>0.8\\ \text{latency}, & \text{otherwise}\end{cases}$$ 在两种情形下会给出误导性标签：一是 kernel 规模过小、单次发射的 wave 数不足，DRAM 吞吐与 SM 利用率都停在低位，分类器落入 latency-bound 分支，agent 于是被引导去调 occupancy 或减少同步，而真实瓶颈可能是 launch 开销或尾效应；二是高 L2 命中率把实际 DRAM 流量压低，DRAM 吞吐比例看起来不高，但 SM 利用率也未过线，同样被判 latency-bound，此时正确的动作是改数据布局或增大 tile 以提高算术强度，而不是加并行度。分类结果一旦错位，反馈块里附带的 Top-3 stall 原因反而会强化错误方向——例如 long scoreboard 在 memory-bound 与 latency-bound 下都常见，但对应的优化动作完全不同。工程上的处理是给分类器加一层置信检查：当两个比例都落在中间带（既未过 0.8 也未低于某个下限）时，反馈块显式标注“分类不确定”，并把原始指标数值直接抛出，让 agent 自行判断而非接受单一标签。

第二个边界是反馈块的压缩损失。把分类结果与 Top-3 stall 压缩到 ≤200 token，意味着大量计数器被丢弃，只保留派生量与三个 stall 名。这个预算在单轮内够用，但在多轮优化中会丢失跨轮可比性：agent 看到的是本轮绝对值，而不是相对上一轮的增量，于是无法判断“增大 tile 后 DRAM 比例从高位回落”究竟是访存减少还是 occupancy 下降导致的假象。可行的补救是把反馈块做成两段式——固定段放本轮分类与 Top-3，可变段放与上一轮同名指标的差值，差值段占用 token 更少但信息增益更高。代价是 prompt 长度随轮次线性增长，若不做截断，长会话的上下文预算会被反馈块吃掉，挤压真正需要保留的代码与错误信息。

系统代价的核心在采集侧。ncu 采集会使 kernel 串行化并重放，单次 profile 耗时是裸跑的 10–100×，这一量级决定了它不能每轮全量执行。若一次优化循环含 k 轮候选生成，全量 profile 的墙钟成本约为 k 倍裸跑时延乘以放大系数，在候选数量稍大时就吞掉整个预算。因此工程上必须做采样策略：只在候选通过正确性 oracle 之后触发 profile，且对同一 kernel 的多次变体只 profile 代表性子集；对疑似 memory-bound 的候选优先跑精简 metric 集（DRAM 吞吐、L2 命中率、occupancy），对疑似 compute-bound 的候选才上 --set full 拿 stall 明细。另一项代价是重放对测量本身的污染：串行化改变了并发环境，L2 状态与时钟频率都可能偏离真实负载，派生量的绝对值因此带有系统性偏差，跨 kernel 比较时只能看比例趋势而不能看绝对阈值。这也解释了为什么反馈块里应保留原始计数器而非只给标签——标签是规则产物，计数器才是可复核的证据。

具体到一次流动，输入是候选 kernel 与上一轮反馈块，输出是分类标签、Top-3 stall 与派生量三元组，中间代价是 profile 的串行重放。以“增大 tile 后时延未降”为例：若反馈块显示 DRAM 吞吐已过 0.8，agent 应转向减少访存而非继续加计算，此时若分类器因 L2 命中率偏高而误判为 compute-bound，agent 会去调 SM 侧参数，一轮预算白白消耗。因此回灌链路的价值不在指标本身，而在分类器与压缩策略能否在 token 预算、采集成本与判别可靠性三者间取得平衡；任何一环失配，反馈就从“把时延没降转化为可执行动作”退化为“把 agent 引向错误方向的高置信噪声”。

回灌链路的边界：分类器先于 agent 失效

这条链路真正的脆弱点不在 ncu 采集，而在 Bound 分类器本身是一个只有三档的硬阈值判别器。它把连续的 roofline 位置压成 memory/compute/latency 三个离散标签，任何落在阈值附近的 kernel 都会被随机地推过边界：DRAM 吞吐 79% 与 81% 的两个 kernel 可能得到完全相反的优化指令，而它们的真实瓶颈结构几乎相同。更糟的是，分类只看两个维度，achieved occupancy 与 L2 hit rate 只作为附属数值进入反馈块，不参与判决。于是一个 occupancy 仅 12%、DRAM 吞吐 82% 的 kernel 会被判为 memory-bound，agent 收到“减少访存”的指令，而真正该做的是提高并行度把延迟藏住——增大 tile 反而进一步压低 occupancy。反馈块越简洁，这种误判的传播就越不可逆：agent 在下一轮把 token 预算全部押在错误方向上。

$$\text{Bound}=\begin{cases}\text{memory}, & \frac{\text{DRAM}_{\text{throughput}}}{B_{\text{peak}}}>0.8\\ \text{compute}, & \frac{\text{SM}_{\text{util}}}{1}>0.8\\ \text{latency}, & \text{otherwise}\end{cases},\quad \text{Feedback}=f(\text{Bound},\text{Top-3 stalls})$$

失效条件可以列成一张短表。第一类是双饱和：DRAM 与 SM 同时越过 0.8，两个分支都成立，判决顺序决定结果，而顺序是人为写死的，与 kernel 实际的可优化空间无关。第二类是stall 归因漂移：Top-3 stall 取自单一 replay pass，long scoreboard 占比高既可能是访存延迟也可能是依赖链过长，反馈块把它写成自然语言后，agent 无法区分这两种语义，只能按字面选择“减少访存”或“拆依赖”，选错一次就浪费一整轮生成。第三类是小 kernel 的采样失真：ncu 需要重放并串行化，单次 profile 耗时是裸跑的 10–100×，对于微秒级 kernel，重放期间缓存状态已被前一次 pass 污染，L2 hit rate 与 DRAM 吞吐都不再代表真实负载，此时任何分类都建立在噪声上。

失效模式触发条件系统代价
双饱和判决歧义DRAM 与 SM 利用率同时 >0.8优化方向二选一，错选即整轮 token 作废
stall 语义丢失Top-3 压缩为自然语言agent 按字面动作，需额外一轮验证纠偏
重放污染kernel 时延远小于单次 replay 开销profile 耗时 10–100×，指标不可信

因此回灌不能每轮全量跑，工程上的折中是分层触发：只在候选 kernel 通过正确性 oracle 之后才付 profile 代价，且对同一 kernel 的多次变体复用一次采集结果，把 ncu 开销摊到整条搜索分支上。反馈块的 ≤200 token 预算也应留出一部分给“不确定”标记——当 DRAM 比例落在 0.7–0.9 区间或 stall 归因置信度低时，反馈块显式写出“分类存疑，建议先做 occupancy 探查”，而不是硬给一个标签。这一步的代价是反馈块变长、prompt 预算被挤占，但它换来的是 agent 不会把一次错误分类当成确定事实继续放大；相比之下，把误判当成 reward shaping 的中间信号危害更大，因为错误标签会被写进奖励函数，后续所有轮次都在为错误方向加分。
