一 · 事故现场：单 batch 全绿的 kernel 在线上炸了

先看一个不需要任何实验数字就能复现的事故形态。某推理服务上线了一个手写的 RMSNorm+残差融合 kernel，验收流程是标准的：拿一组固定 shape 的输入，跟 PyTorch 参考实现比 max abs diff，全部在 1e-5 以内，单测通过，性能比基线快了一截，于是合入。上线后症状不是崩溃，也不是数值乱飞，而是「同一句话，两次请求返回的 logits 不完全一样」，且这种不一致只在并发批量调度下出现——单条请求、batch=1 的压测路径完全干净。排查到最后，问题出在 kernel 内部：为了在小 batch 下把 SM 吃满，作者引入了 split-K 归约，把一次 reduction 拆成若干段并行累加再合并；当 batch 变大、每个 SM 分到的 token 数变化时，tile 划分随之改变，归约的分段边界跟着移动，浮点加法的结合顺序就变了。数学上等价，浮点上不等价。

这类事故的杀伤力在于它绕过了所有常规检查。单 batch 正确性检查比对的是「这个 shape 下这个 kernel 算得对不对」，而事故的内核在每一个被检查过的 shape 下都算得对。真正被破坏的是另一条性质：同一个逻辑输入，其输出不应依赖于它被放进多大的 batch 里。这条性质在训练侧同样致命——梯度累积、micro-batch 切分、FSDP 的 shard 边界都会改变实际 batch 组成，若 kernel 输出随 batch 漂移，则同一份数据在不同并行配置下产生不同梯度，可复现性直接归零，而 loss 曲线看起来完全正常，因为漂移量小到被优化过程吸收了。评测翻车的形态则是：KernelBench 类基准里一个候选 kernel 在给定的固定 shape 上拿到高分，被 RL 奖励强化，部署到变 batch 的生产路径后行为改变，而基准本身没有任何一项检查能看见这件事。

二 · 这个方法到底判定什么

Batch 不变性门（batch invariance gate）要判定的是一条非常窄、但非常硬的性质：对同一逻辑输入，分别以 B=1 与 B=B 运行同一个生成 kernel，逐元素输出必须在容差内一致。形式化为：

$$\Delta_{\text{BI}}=\max_i\left|y_i^{(B=1)}-y_i^{(B)}\right|,\quad \text{Invariant}=\mathbb{1}\left[\Delta_{\text{BI}}\le \tau_{\text{BI}}\right],\quad R_{\text{final}}=R\cdot\text{Invariant}$$

注意这个式子的三个工程含义。第一，它比对的是逐元素输出，不是聚合统计量——均值、方差、cosine similarity 都会把局部漂移抹平，而漂移恰恰是逐元素发生的。第二，它用的是 max abs diff 而非平均误差，因为一个 token 上的 1e-3 级偏差足以在采样时翻转 argmax，平均下来却是 1e-7。第三，奖励相乘的结构意味着这是一个硬门而非软惩罚：Invariant=0 时该轮奖励直接归零，不给「性能很好所以容忍一点数值漂移」的议价空间。这一点与软惩罚有本质区别——软惩罚会让策略学会用性能换数值容差，而数值容差在生产端不可交易。

它捕获的错误类别是明确的：split-K 归约、动态 tile 划分、按 batch 选择不同 kernel 变体（persistent vs. non-persistent）、按 occupancy 调整的 reduction tree 深度、以及任何在编译期或运行期依据 batch 维度做分支的启发式。这些错误的共同特征是由性能优化引入的非确定性，且在单 batch 测试中完全不可见——因为单 batch 路径下这些启发式根本不触发，或者只触发一种固定配置。

三 · 它不解决什么：三条明确的边界

第一条边界是允许非确定性的算子会被误杀。atomicAdd 归约、基于 atomic 的直方图、某些 scatter 语义的算子，其输出顺序本身就不保证，逐元素比对必然失败。这不是门的缺陷，而是门的适用范围问题：必须按算子类型维护豁免名单，把「顺序敏感但语义允许」的算子排除在门控之外。豁免名单本身是工程风险点——名单过宽等于门形同虚设，名单过窄等于误杀合法实现，维护它需要按算子语义而非按 kernel 名字分类。

第二条边界是它不检查单 batch 正确性。门只回答「B=1 与 B=B 是否一致」，不回答「B=1 是否等于数学参考」。一个在 B=1 下就错得一致的 kernel 能完美通过不变性门。所以这道门必须与 fp64 参考 oracle、变异测试审计等机制串联，不能单独作为正确性判据。它的定位是正确性检查的一个正交维度，而不是替代品。

第三条边界是时延不可比。构造 B=B 的输入需要 padding 其余位置，padding 会改变实际计算量——参与归约的元素数、tile 的有效利用率、甚至是否触发某个 batch 阈值分支都会变。因此这条路径上的 wall time 不能拿来跟 B=1 路径做性能对比，也不能用来估算吞吐。它只承担正确性门控职责，性能评估必须走独立的、shape 分布对齐的基准路径。把两者混在一起是常见的设计错误：一旦有人试图从这条路径顺带读出「batch 变大后快了多少」，就会得到被 padding 污染的结论。

还有一层隐含边界值得点明：门控的容差 τ_BI 不是普适常数。fp16 累加与 fp32 累加的漂移量级不同，归约长度不同则误差累积不同，τ_BI 必须按 dtype 与归约规模标定，否则要么放过真实漂移，要么把正常浮点结合律差异判成错误。

四 · 门控的执行结构：两次运行、一次比对、一条诊断

机制本身很轻：构造逻辑等价输入——同一序列分别放在 batch=1 与 batch=B（其余位置 padding）中；分别运行生成 kernel；提取目标位置的输出；逐元素比对，计算 max abs diff 与相对误差；若超阈值，定位差异来源并输出诊断；失败即判定不可部署，奖励乘 0，并写入回归集防止后续轮次复发。伪代码层面的结构是：

  • 对每个待测用例，固定逻辑输入 x 与目标位置索引集合 S；
  • 路径 A：x 置于 B=1 容器，取 y_A = kernel(x)[S]；
  • 路径 B：x 置于 B=B 容器、其余槽位 padding，取 y_B = kernel(x_padded)[S]；
  • 计算 Δ_BI = max over S of |y_A − y_B|，与 τ_BI 比较；
  • 若失败，按差异分布做归因：差异是否随归约段数变化、是否集中在 tile 边界位置、是否只在特定 batch 阈值以上出现，输出为结构化诊断。

成本结构要算清楚。门控的直接开销是两次 kernel 运行加一次逐元素比对：比对本身是 O(|S|) 的访存受限操作，相对 kernel 运行可忽略；两次运行中 B=B 那次因 padding 而计算量偏大，是主要开销。相比 NCU 级 profile 或 SASS 级剖析，这个成本低一个量级以上，因此可以嵌入每一轮 RL 奖励计算而不拖垮采样吞吐。代价则体现在 token 预算上：每轮多一次前向、多一次比对、失败时多一段诊断文本进入上下文，对长上下文策略而言这是实打实的预算占用。工程判断是：门控应放在奖励计算的必经路径上，但诊断文本只在失败时生成，避免每轮都付诊断的 token 成本。

一个具体例子能说明归因的价值。假设某候选 kernel 在 B≤8 时走单段归约、B>8 时走 split-K=4。门控在 B=16 下发现 Δ_BI 超阈，且差异集中在序列末尾若干 token 上——这正是 split-K 分段边界与 tile 尾部重叠的位置。诊断输出「差异随归约段数变化、集中于 tile 边界」，策略在下一轮就能针对性地把归约顺序固定为与 batch 无关的确定性树形结构，而不是盲目回退整个优化。这比只给一个二值失败信号的信息量大得多，也是这道门能嵌入多轮 RL 的原因：它提供的是可操作的梯度方向，不只是惩罚。

五 · 为什么必须是硬门：奖励塑形的失效模式

把不变性做成软惩罚（例如 R_final = R − λ·Δ_BI）在工程上很有诱惑力，因为它保留了「性能好但略有漂移」的中间地带。但这条路径有明确的失效模式：策略会学会把 Δ_BI 压在阈值边缘，用极小的数值漂移换取 split-K 带来的性能收益，而生产端的 argmax 翻转恰恰发生在阈值边缘——采样对 logits 的微小扰动极其敏感，1e-3 的漂移在低温采样下足以改变输出 token。软惩罚把「是否可部署」变成了一个连续优化问题，而部署决策是二值的。

硬门的另一个作用是把失败写入回归集。一次不变性失败不是丢弃这个候选就结束，而是把该用例（逻辑输入、batch 配置、失败模式）固化下来，后续每一轮都要重跑。这防止的是策略在多轮搜索中反复「重新发现」同一个错误配置——没有回归集，keep-revert 式搜索会在同一片失败区域反复试探，浪费采样预算。回归集的增长本身有成本：用例越多，每轮门控的运行次数越多，需要在覆盖度与吞吐之间做取舍，通常按失败模式聚类去重而非逐例累积。

与同模块其他机制的分工要一句话说清：TF32/编译基线锚定解决的是「跟谁比」，隐藏 shape 分布抽样解决的是「测哪些 shape」，而本门解决的是「同一逻辑输入在不同 batch 容器下是否自洽」——三者正交，缺一不可。防作弊合约校验管的是策略有没有绕过评测，本门管的是 kernel 自身在合法实现下的数值稳定性，两者不在同一层面上。

六 · 适用边界的工程判断

把边界收拢成可执行的判断：这道门适用于输出对归约顺序敏感、且生产路径 batch 会变化的 kernel——归一化、softmax、attention 的 softmax 部分、任何带 reduction 的融合算子。它不适用于输出本身按定义就与 batch 无关的逐元素算子（elementwise 无归约），也不适用于语义上允许顺序不确定的 atomic 类算子。对前者跑门控是浪费预算，对后者跑门控是制造假失败。

还有一个容易忽略的适用性条件：逻辑等价输入的构造必须保证 padding 不污染目标位置的计算。若 kernel 的归约跨越了整个 batch 维度（例如 batch 维的统计量），padding 会改变统计量本身，此时「同一逻辑输入」的前提被破坏，门控结果无意义。这类 kernel 需要专门的 mask 感知构造，或者干脆排除在门控之外并记录原因——排除本身要留痕，否则回归集会出现无法解释的空洞。

最后落在机制上：这道门的经济学是「两次运行换一条正交正确性维度」，其价值密度取决于失败模式是否真的会在生产端发生。对一个 batch 恒定为 1 的离线批处理场景，门控收益接近于零；对一个 batch 随负载动态变化的在线服务，它是唯一能看见 split-K 漂移的检查。判断标准不是「这道门先不先进」，而是「这个 kernel 的 batch 是否是一个会变化的运行时变量」——是，则门控必须在奖励路径上；否，则把预算留给别的维度。

门控管的是“同一逻辑输入换 batch 就变脸”，不是通用正确性

Batch 不变性门要解决的是一个非常窄但很致命的问题：kernel 在 batch=1 与 batch=B 下对同一 token 给出不同数值。归约顺序、split-K 切分、动态 tile 边界都会随 batch 改变，单 batch 正确性检查对此完全失明。线上事故的典型形态是：评测流水线用 batch=1 逐条跑通、单测全绿，服务端以 batch=32 上线后，同一 prompt 的 logits 与离线复现不一致，采样结果漂移，回归对比无法定位到具体 kernel——因为每个 kernel 单独看都“对”。门控的做法是把逻辑等价输入分别放进 batch=1 与 batch=B（其余位置 padding），提取目标位置输出逐元素比对，用 $$\Delta_{\text{BI}}=\max_i\left|y_i^{(B=1)}-y_i^{(B)}\right|,\quad \text{Invariant}=\mathbb{1}\left[\Delta_{\text{BI}}\le \tau_{\text{BI}}\right],\quad R_{\text{final}}=R\cdot\text{Invariant}$$ 把奖励直接乘零，并写入回归集防止后续轮次复发。

它的边界同样明确。第一类失效是对本身允许非确定性的算子误杀：atomicAdd 归约的累加次序天然随调度变化，batch=1 与 batch=B 的差异属于算子语义而非缺陷，必须按算子类型维护豁免名单，否则门控会把合法实现判死，RL 奖励被错误清零、策略被推向保守写法。第二类失效是 padding 改变了实际计算量：batch=B 那次运行多算了填充位置，时延不可直接比较，门控只能用于正确性判定，不能顺手当作性能信号；若把两次运行的耗时差喂进奖励，等于用计算量差异冒充优化收益。第三类失效是阈值本身：$$\tau_{\text{BI}}$$ 定得过紧会把浮点结合律差异当成错误，定得过松则放过真实 split-K 漂移，需要按 dtype 与归约深度校准，而不是全局一个常数。

系统代价要算清楚：每次门控是两次 kernel 运行加一次逐元素比对，比对本身是 O(输出元素数) 的访存，对大词表 logits 是带宽开销；batch=B 的 padding 让显存占用按 B 倍逻辑输入放大，长序列场景下这次“只为正确性”的运行可能比训练步本身更吃显存。工程判断是：门控应挂在奖励计算的每轮入口，但对已列入豁免名单的算子跳过，对输出规模超过阈值的层改用抽样位置比对以控制带宽；诊断信息必须落到“归约顺序 / split-K / tile 边界”三分类，否则失败只给出一个 diff 数字，回归集里没人能修。
