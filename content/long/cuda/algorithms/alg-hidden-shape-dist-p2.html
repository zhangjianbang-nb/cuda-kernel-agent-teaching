一 · 从 trace 到 shape 元组：抽样的输入与第一道代价

隐藏 shape 分布抽样的第一步不是抽样，而是把生产负载的调用记录压成可计算的 shape 元组。输入是一条真实负载 trace：每次 kernel launch 的维度、batch、seq_len、dtype、stride 布局，以及调用频次。输出是一张经验分布表，键为归一化后的 shape 元组（例如 (M,N,K) 或 (batch, heads, seq_len, head_dim)），值为该元组在 trace 窗口内的出现概率。这一步的机制核心是“去重 + 归一化”：同一逻辑 shape 因 stride 或对齐差异产生的变体要合并，否则分布会被长尾噪声污染；而 dtype 与布局必须保留为元组的附加维度，因为同一个 (4096,4096,4096) 在 fp16 与 fp32 下的最优 kernel 完全不同。

代价出现在两个地方。其一是 trace 采集本身：生产 trace 往往需要插桩或采样，采样率过低会漏掉低频但关键的 shape，采样率过高则带来可观的运行时开销与存储带宽压力。其二是拟合：对高维联合分布做经验估计，样本量不足时尾部概率估计方差极大，而尾部恰恰是本方法最关心的部分。一个具体例子是 transformer 推理服务：prefill 阶段的 seq_len 分布与 decode 阶段的 seq_len=1 分布混在同一条 trace 里，若不按阶段切分，拟合出的边缘分布会把两类完全不同的 kernel 行为平均掉，隐藏集抽样就会失真。工程判断是：trace 窗口必须覆盖至少一个完整的流量周期，且按调用阶段分桶后再拟合，否则后续所有加权聚合都建立在错误的 p(s) 上。

二 · head/tail 切分：分位阈值决定了惩罚项的作用面

拟合出经验分布后，按累积概率做 head/tail 切分。给定分布 p(s)，将 shape 按概率降序排列，取累积概率达到阈值（如 90%）的最小前缀为 head 段，其余为 tail 段。输出是两个互不相交的集合 S_head 与 S_tail，以及各自的权重。这一步的机制看似简单，但阈值的选择直接决定了泛化惩罚项的敏感度：阈值越高，tail 段越小、越极端，惩罚项越尖锐但统计噪声越大；阈值越低，tail 段混入中等频率 shape，惩罚项被稀释，难以捕获“只对大 batch 优化”的退化。

代价是代表性。tail 段的 shape 在真实 trace 中出现频次低，经验估计的置信区间宽，若 trace 窗口不够长，某些 tail shape 可能只出现个位数次，其 p(s) 估计几乎不可信。更麻烦的是非 2 的幂 shape：它们在生产中常因 padding 被抹平，trace 里根本看不到，只能人工注入。一个具体例子是 batch=17 或 seq_len=1000 这类 shape，真实服务里往往被 pad 到 32 或 1024，trace 记录的是 pad 后的值，隐藏集若只按 trace 抽样就永远测不到这些边界。因此 tail 段必须显式包含人工构造的极端小/大与非 2 的幂 shape，这部分不来自分布拟合，而来自工程枚举。代价是这部分 shape 的权重无法用 p(s) 校准，只能等权处理，与加权聚合的口径不一致，需要在审计日志里标注来源。

三 · 隐藏集抽样：seed、规模与跨轮不可记忆性

抽样步骤的输入是 head/tail 两段及其权重，输出是一个规模 200–500 的隐藏 shape 集 S_hid。机制是按 p(s) 从 head 段抽样、按注入规则从 tail 段抽样，两者按预定比例混合，抽样 seed 加密保存。规模下限 200 是为了让加权聚合的方差可控，上限 500 是为了控制单次评测的 GPU 小时数。seed 加密的目的不是保密 shape 本身，而是防止 agent 通过反复提交探测出隐藏集内容——若 seed 可预测，agent 可以在多轮之间拟合出隐藏集的 shape 列表并针对性过拟合，这正是本方法要防的行为。

代价是每轮重抽带来的评测不稳定。同一份 kernel 在两轮不同 seed 下的得分会有波动，波动幅度取决于分布尾部的厚度与抽样规模。规模越大波动越小，但 GPU 小时数线性上升。一个具体例子：若 head 段有 50 个高频 shape、tail 段有 30 个注入 shape，200 个样本的抽样中某些 tail shape 可能一轮出现、一轮不出现，导致惩罚项在两轮间跳变。工程上的处理是把 tail 段设为必抽（分层抽样），head 段按权重随机抽，这样惩罚项的方差被压住，代价是 head 段的抽样不再是纯 i.i.d.，加权聚合的无偏性需要按分层权重修正。这一步的另一个代价是审计：seed 与分布参数写入日志后，日志本身成为跨轮记忆的载体，若日志对 agent 可见，加密 seed 形同虚设。

四 · 批量执行：正确性与时延的双轨测量

agent 提交 kernel 后，评测在 S_hid 上批量执行，每条 shape 跑两轨：正确性轨用 fp64 参考实现比对，时延轨用基线 kernel 与生成 kernel 的实测时间比。输出是每条 shape 的通过标志与 T_base(s)/T_gen(s) 比值。机制上，两轨必须分离测量：正确性比对引入 fp64 参考的额外计算与内存流量，若与时延测量混在同一轮，缓存状态与时钟频率会被污染。批量执行的顺序也应固定或随机化，避免 shape 排序带来的热缓存偏差。

代价在这里最集中。200–500 个 shape 全量跑 fp64 参考与计时，单次评测 GPU 小时数约为公开集的 10×，这是本方法最直接的工程成本。fp64 参考在消费级 GPU 上吞吐极低，若参考实现本身是逐元素朴素写法，正确性轨的耗时可能远超时延轨。一个具体例子是归约类 kernel：fp64 参考的串行归约在 500 个 shape 上跑一遍，其耗时足以让单次评测从分钟级升到小时级。缓解手段是参考实现也做并行化与缓存复用，但这又引入“参考实现是否可信”的新问题，需要独立的变异测试审计（见 checker 审计条目）。另一项代价是显存：批量执行若并行多个 shape，峰值显存按最大 shape 的中间张量估算，tail 段的大 shape 往往就是显存瓶颈，迫使执行退化为串行，进一步拉长评测时延。

五 · 加权聚合与惩罚项：分数如何被分布塑形

聚合步骤把逐 shape 的比值压成两个数：加权得分与尾部惩罚。加权得分按分布权重求和：

$$\text{Score}=\sum_{s\in\mathcal{S}_{\text{hid}}} w_s\cdot\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)},\quad w_s=\frac{p(s)}{\sum_{s'}p(s')}$$

惩罚项只在 tail 段上计算退化幅度：

$$\text{Penalty}=\frac{1}{|\mathcal{S}_{\text{tail}}|}\sum_{s\in\mathcal{S}_{\text{tail}}}\max\left(0,1-\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)$$

机制上，加权得分使刷单一高频 shape 的收益被 w_s 稀释：即便 agent 在某个 head shape 上把时延压到基线的数倍，它在总分里的贡献上限就是该 shape 的权重。惩罚项则单独捕获 tail 段的退化，max(0,·) 只惩罚比基线慢的情形，比基线快不产生负惩罚，避免 agent 用极端优化换取惩罚项的抵消。两个数分开报告而非合成单一标量，是为了让工程判断保留可解释性：一个高分低惩罚的 kernel 是可信的，一个高分高惩罚的 kernel 说明它在大 shape 上崩了。

代价是权重口径的一致性。head 段权重来自 p(s)，tail 段注入 shape 的权重无法校准，惩罚项用等权平均，两者口径不同，直接相加会引入偏差。另一个代价是 T_base(s) 的测量本身：基线 kernel 在同一 shape 上的时延也有方差，若基线测量不固定（例如每轮重测），比值噪声会叠加到得分上。一个具体例子是 tail 段的小 shape：基线 kernel 在小 shape 上受 launch 开销主导，T_base 只有微秒级，测量噪声占比高，惩罚项容易因噪声误判退化。工程处理是对小 shape 做多次重复取中位数，代价是评测时间进一步上升。

六 · 重抽样与审计日志：跨轮记忆的封堵点

每轮评测重新抽样，是封堵跨轮记忆的机制核心。输入是上一轮的 seed 与分布参数，输出是新一轮的 S_hid 与新的审计记录。机制上，重抽样必须同时改变 seed 与抽样规模或分层比例，否则 agent 可以通过多轮提交做统计推断，逐步逼近隐藏集的 shape 集合。审计日志记录 seed、分布参数、head/tail 切分阈值、注入 shape 列表与来源标注，其作用是让评测可复现、可追责，同时作为“分布是否漂移”的证据链。

代价是复现性与稳定性的张力。重抽样使同一 kernel 的跨轮得分不可直接比较，若用得分做 RL 奖励，奖励信号的方差会传导到策略更新，需要额外的基线归一化（见 Roofline/SOL 归一评分条目）。审计日志的写入本身也有代价：若日志包含完整 shape 列表，其体积随抽样规模线性增长，且日志若对 agent 可见就成为泄漏源。一个具体例子是冷启动场景：没有真实 trace 时只能人工构造分布，此时审计日志里的“分布参数”是人为设定的，代表性存疑，重抽样只是在一个人为分布内抖动，无法检验真实负载偏移。工程判断是：冷启动阶段的隐藏集评测只能作为相对排序，不能作为绝对泛化结论；一旦拿到真实 trace，必须重新拟合并重跑基线，否则历史得分不可比。这一步落在具体机制上——重抽样的价值不在于换一批 shape，而在于让“分布”本身成为每轮评测的显式输入，从而使 agent 的优化目标被迫跟随分布而非跟随固定 shape 列表。

抽样边界：从 trace 拟合到隐藏集落地的失效面

隐藏 shape 抽样并不是一个“评测时随机换几个尺寸”的轻量动作，它的每一步都绑定真实 trace 与算力预算。第一步是从生产 trace 提取 shape 元组，输入是带时间戳的请求日志（维度、batch、seq_len 三元组），输出是去重后的 shape 频次表；代价在于 trace 本身可能缺失冷启动阶段的长尾请求，或只覆盖单一业务线，导致拟合出的经验分布对目标负载代表性不足。第二步按分位数切 head/tail（如 90%/10%），公开集只放 head 段少量样例，隐藏集从 head+tail 按分布抽 200–500 个 shape 并加密 seed——这一步的代价是抽样本身不耗 GPU，但加密 seed 与分布参数必须写入审计日志，否则跨轮重抽样失去可追溯性。第三步在 agent 提交 kernel 后批量跑 fp64 参考正确性与计时，按 shape 加权聚合：

$$\text{Score}=\sum_{s\in\mathcal{S}_{\text{hid}}} w_s\cdot\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)},\quad w_s=\frac{p(s)}{\sum_{s'}p(s')}$$

加权聚合使刷单一 shape 的收益被稀释，但代价是 200–500 个 shape 全量跑 fp64 参考与计时，单次评测 GPU 小时数约为公开集的 10×，且 fp64 参考路径在消费级卡上可能不可用，只能退化为 fp32 参考并接受精度噪声。第四步对 tail shape 单独报告通过率与相对基线退化倍数，作为泛化惩罚项：

$$\text{Penalty}=\frac{1}{|\mathcal{S}_{\text{tail}}|}\sum_{s\in\mathcal{S}_{\text{tail}}}\max\left(0,1-\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)$$

该惩罚项能捕获“只对大 batch 优化”的退化，但它的失效条件很具体：若 tail 段只含极端小 shape，惩罚项对“只对小 shape 优化”的 kernel 同样失灵，因为分母被小 shape 主导；若 tail 中非 2 的幂 shape 占比过高，而真实负载中非 2 的幂请求本就稀少，惩罚项会把部署中无关紧要的退化放大成主要扣分项。更隐蔽的失效来自每轮重新抽样：重抽样防止跨轮记忆，但若分布参数本身随轮次漂移（trace 更新），前后两轮的 Score 不可直接比较，审计日志必须同时记录分布参数版本，否则跨轮对比会引入不可归因的方差。冷启动场景只能人工构造分布，代表性存疑，此时隐藏集与公开集的分布差异不再是“不可见”，而是“人为设定”，agent 若通过公开集反推人工分布的构造规则，抽样防线即告失效。

工程判断落在抽样预算与失效面的权衡上：200–500 个 shape 的隐藏集在单卡上跑 fp64 参考与计时，若每个 shape 含 warmup 与多次迭代，单轮评测的墙钟时间足以让多轮 RL 的采样吞吐下降一个量级，因此隐藏集规模应按 tail 段占比动态收缩——tail 越稀薄，越需要更多 head 抽样来稳定加权 Score，而 tail 惩罚项只需覆盖极端小/大与非 2 的幂的少量代表点即可暴露退化方向。抽样 seed 加密只防跨轮记忆，不防 agent 在单轮内对隐藏集做在线探测：若评测接口允许 agent 提交后读取逐 shape 时延，agent 可在同一轮内迭代 kernel 逼近隐藏集分布，此时加密 seed 形同虚设，必须把逐 shape 结果延迟到整轮结束后才释放。

抽样器自身的失效面：trace 偏差、尾部稀疏与重抽样开销

这套机制的边界不在 kernel 端，而在分布端。隐藏集完全由生产 trace 拟合出的经验分布驱动，一旦 trace 本身有偏——采集窗口过短、只覆盖某一类模型或某一档 GPU、batch 由调度器人为截断——抽样出的 head/tail 划分就只是对偏差的放大。冷启动场景没有 trace 可拟合，只能人工构造维度与 seq_len 的联合分布，此时 90%/10% 分位切点缺乏统计支撑，tail 段可能只落到个位数 shape，惩罚项 $$\text{Penalty}=\frac{1}{|\mathcal{S}_{\text{tail}}|}\sum_{s\in\mathcal{S}_{\text{tail}}}\max\left(0,1-\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)$$ 的分母过小，单个 shape 的计时抖动就能把整项拉偏，泛化信号退化为噪声。更隐蔽的失效是分布漂移：trace 拟合完成后负载形态改变（seq_len 增长、出现新的非 2 的幂维度），隐藏集仍按旧分布抽样，agent 在旧分布上表现良好却在真实新负载上崩溃，而评测系统不会报错——它只是抽样了一个过时的世界。

重抽样带来的是可复现性与成本的直接冲突。每轮评测重新抽样以防止跨轮记忆，意味着同一份提交在不同轮次拿到的隐藏集不同，分数不可逐轮直接比较；seed 与分布参数写入审计日志只能事后归因，无法在评测时消除方差。加权聚合 $$\text{Score}=\sum_{s\in\mathcal{S}_{\text{hid}}} w_s\cdot\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)},\quad w_s=\frac{p(s)}{\sum_{s'}p(s')}$$ 中权重来自拟合分布，若抽样实现用均匀采样再赋权，低概率的 tail shape 会以极小权重进入总分，惩罚项与总分之间出现口径不一致：总分几乎不感知 tail 退化，惩罚项却单独放大它。工程上必须固定“抽样即赋权”的实现，否则两套口径会让 agent 学会只优化总分而忽略惩罚。

系统代价集中在评测吞吐。200–500 个 shape 全量跑 fp64 参考与计时，单次评测 GPU 小时数约为公开集的 10×，且 fp64 参考在消费级卡上本身受限，正确性 oracle 的算力开销会挤压时延测量窗口，需要把参考计算与计时跑分离到不同 stream 或不同卡上。抽样 200–500 个 shape 还意味着编译缓存命中率下降：每个 shape 可能触发不同的特化分支与 launch 配置，编译时间随 shape 多样性上升，agent 若在提交前针对公开 head 样例做过 autotune，隐藏集上的首次调用会落入未调优路径，测得的 $$T_{\text{gen}}(s)$$ 混合了冷启动开销与稳态性能。判断标准很直接：当 trace 覆盖不足一个完整负载周期、或 tail 段 shape 数低于可统计阈值时，这套抽样只能作为筛选器而非评分器；此时应退回固定隐藏集加人工 tail 注入，把重抽样频率降到跨版本而非跨轮。
