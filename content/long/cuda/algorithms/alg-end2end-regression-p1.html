一 · 一次“微基准满分、线上翻车”的事故解剖

某推理服务团队在算子库中合入了一个由 agent 生成的 LayerNorm+残差融合 kernel。候选 kernel 在 KernelBench 风格的微基准上取得明显加速：单独计时该算子，时延从基线实现下降到不足原来的三分之二，正确性检查在固定 shape 下通过，评审据此放行。上线后端到端 P99 时延不降反升，吞吐持平略降，显存峰值还上涨了一截。回滚后逐层排查，原因并不神秘：候选 kernel 为了减少寄存器压力把中间结果写回一块独立 scratch 缓冲区，而真实模型里前后算子原本共享同一块 workspace，插入候选后多出一次额外的分配与一次跨 kernel 的读写往返；同时该 kernel 的 launch 配置在真实并发下网格规模偏小，SM 占用不足，微基准的单流环境掩盖了这一点。更麻烦的是，融合改变了累加顺序，在长序列尾部的极小值上出现与 fp64 参考的偏差，微基准的固定输入没有覆盖到。

这个案例精确划出了本方法要解决的问题边界：微基准时延是部署收益的有偏估计量。偏差来自三个方向——launch 与调度开销在端到端里被摊到整个算子链上、内存布局与 workspace 复用关系在孤立计时中不可见、融合机会的得失只在前后算子上下文中才成立。因此需要一道以真实模型为被测对象的回归门，把“候选 kernel 插回真实 trace 后是否真的更快且仍然正确”作为合入的充分条件，而不是把微基准分数当作代理指标。

$$\text{gain}_{\text{e2e}}=\frac{T_{\text{base}}^{\text{e2e}}-T_{\text{gen}}^{\text{e2e}}}{T_{\text{base}}^{\text{e2e}}},\quad \text{merge if }\ \text{gain}_{\text{e2e}}\ge \theta\ \land\ \text{maxerr}\le\epsilon$$

上式是本门的最小判定式。注意它的两个合取项地位对等：性能收益不达阈值要回退，数值误差越界同样要回退，且误差判定不因收益巨大而放宽。事故中的候选恰好是“收益为正、误差越界”的组合，若门只卡性能，它会被放行；若门只卡正确性，它会被当作有效优化合入而拖累线上。这正是把两个条件写成合取而非加权打分的原因。

二 · 它不解决的问题：三类被明确排除的失效模式

适用边界的第一层是“不解决什么”。端到端回归门是一个部署价值的否决器，不是优化器，也不是正确性的充分证明。它无法替代其他环节，具体排除三类问题。

  • 微基准本身的测量造假。若候选 kernel 在微基准阶段就通过缓存输入、跳过边界分支、针对固定 shape 特化等手段虚报时延，端到端门只能观察到“插回后没有收益”并回退，却无法指出造假发生在哪一层。识别这类行为属于防作弊合约校验与变异测试审计的职责，本门只承担最后一道否决。
  • 真实 trace 未覆盖的路径。端到端 benchmark 的覆盖面由 trace 决定。若线上存在低频但关键的 shape（长尾 batch、极端序列长度、稀疏输入），而 trace 抽样未命中，门会给出“无回归”的结论，这个结论只在被抽中的分布上成立。隐藏 shape 分布抽样解决的是覆盖面问题，本门解决的是“在被覆盖的分布上是否值得合入”。
  • 正确性的形式化保证。门内的数值一致性检查是采样式的：在给定输入集合上与参考实现比对 maxerr。它不能证明对所有输入正确，浮点结合律改变、非规格化数、NaN/Inf 传播路径都可能逃逸采样。合约与形式化验证、fp64 参考 oracle 承担的是更强的正确性论证，本门只做部署前的最后一道采样闸。

代价在这里第一次显形：门的判定强度受限于 trace 与输入集的质量，而构建高质量 trace 与输入集的成本落在人身上。一个覆盖不足的 trace 会让门变成橡皮图章，其误放行代价是线上事故；一个过度保守的输入集会让门频繁误拒，其代价是优化产能被浪费。工程上必须显式记录 trace 的来源、采样策略与覆盖的算子集合，否则门的结论无法被审计。

三 · 机制：把候选插回真实调用上下文

门的核心动作不是“再跑一次 benchmark”，而是重建候选 kernel 的真实调用上下文。从真实推理或训练 trace 中提取热点算子时，必须连同其调用上下文一起提取：输入 shape、stride 与内存布局、前后算子的身份、workspace 的分配与复用关系、流与并发配置。只提取算子名与 shape 是不够的——事故案例中正是 workspace 复用关系决定了候选的额外开销。

替换阶段要求接口与内存布局严格一致：候选 kernel 的入参顺序、对齐假设、输出 stride、对 workspace 的读写约定必须与基线实现等价，否则测得的差异混杂了适配层开销而非 kernel 本身。实践中这一步常需要一层薄适配，适配层本身的时延必须计入端到端总账，不能从测量中剔除。

测量阶段有三条硬性要求。其一，warmup 必须充分，把首次 launch 的模块加载、JIT 编译、页表建立排除在计时窗口外，否则候选若引入新的编译单元会因冷启动被误判。其二，多 batch 与真实并发必须纳入，单流单请求的测量会系统性低估 launch 开销占比、高估小算子的收益。其三，重复多次并报告分布的尾部而非均值，系统噪声在共享 GPU 上足以吞掉小算子的真实收益。

伪代码层面的门控流程可写成：对每个候选 k，先在基线模型 M 上取端到端基线 T_base（同一 trace、同一并发、同一 warmup 协议），再把 k 插入 M 得到 M_k，测 T_gen 与显存峰值，同时在与 trace 同分布的输入集上跑数值一致性得到 maxerr，最后按判定式决定合入或回退，并把回退原因（收益不足、误差越界、显存上涨、噪声不可分辨）写入策略池供后续搜索复用。

性能代价在此处集中体现：端到端 benchmark 的单次成本远高于微基准。它需要加载完整模型权重、回放真实 trace、维持并发压测，单轮耗时通常是算子级计时的数量级以上；而为了压住系统噪声又必须重复多轮，于是每个候选的验证预算被显著抬高。这直接限制了单位时间内可验证的候选数量，也是后续部分要讨论的吞吐与预算分配问题的起点。

四 · Amdahl 稀释：小算子优化为何被门误拒

端到端收益被 Amdahl 定律结构性稀释。设被优化算子在端到端总时延中占比为 p，该算子自身时延下降比例为 s，则端到端收益上界为：

$$\text{gain}_{\text{e2e}}\le p\cdot s$$

举例说明量级关系：若某算子占总时延的比例很小，即便该算子被加速到接近零时延，端到端收益也被 p 封顶。当阈值 θ 设在个位数百分比时，占比低于 θ 的算子无论怎么优化都无法过门——这不是候选质量差，而是门的结构性盲区。事故的反面同样成立：一个占比可观、微基准加速温和的算子，可能因为消除了跨算子的一次同步而带来超出 p·s 的端到端收益，此时微基准排序会把它排在后面。

这个盲区带来的代价是误拒：有价值的局部优化因低于阈值被回退，优化产能被浪费，且策略池会积累“该算子族不可优化”的错误先验，污染后续搜索的决策。工程上的应对不是简单调低 θ——θ 调低会让噪声级别的伪收益混入生产。可行做法是对占比接近 θ 的算子采用更长的重复测量以压低置信区间宽度，或对同一算子族的多个候选做批量端到端测量以摊薄固定成本；这些都属于测量预算的分配问题，而非判定式本身的修改。需要强调的是，任何放宽都必须以误差条件不放宽为前提。

五 · 与相邻环节的接缝：门只做否决，不做归因

把本门放进整条流水线看，它的输入来自热点算子提取与 trace 抽样，输出是合入/回退的二元决定加一条失败原因记录。它与相邻环节的接缝必须清晰，否则会出现职责重叠或真空。

相邻环节它回答的问题本门不替代它的原因
Roofline/SOL 归一评分候选离硬件上界还有多远SOL 高不代表端到端有收益，占比与开销结构决定实际价值
NCU 指标回灌 / SASS 剖析瓶颈在哪个微架构单元剖析解释“为什么慢”，门只回答“插回后是否值得合入”
防作弊合约校验候选是否遵守测量合约门观察到异常收益缺失但无法定位造假
Batch 不变性门不同 batch 下行为是否一致不变性通过不蕴含端到端收益为正

接缝处的典型失效是把门的回退原因当作根因。门记录的是“收益 0.4%、低于阈值”，这不是根因；根因可能是 launch 开销占比过高、可能是 workspace 冲突、也可能是测量噪声未收敛。策略池若直接把“收益不足”当作该候选的负标签，会错误地惩罚一个结构上正确的 kernel。因此回退记录必须携带测量上下文：基线时延、重复次数、置信区间、占比估计、误差值，供后续环节做归因。这也是本门与 MCTS/进化 keep-revert 搜索对接时的接口要求——搜索侧需要的是可归因的失败信号，而非二元标签。

代价再次出现：携带完整上下文的回退记录会显著增加存储与检索开销，尤其当候选数量大、每轮端到端测量产生多条时序与显存轨迹时。工程判断是只保留聚合统计量与少量代表性轨迹，原始轨迹按采样率留存，避免策略池被原始数据淹没而失去检索价值。

六 · 适用边界的工程判据

落到可执行的判据上，本门适用于满足以下条件的场景：候选 kernel 将被插入一个可完整加载并回放的真实模型；存在可复现的 trace 能覆盖该算子在生产中的主要调用上下文；端到端测量能在可接受的重复次数内把噪声压到低于 θ 的量级；正确性检查有可用的参考实现且输入集与 trace 同分布。四条中任一不满足，门的结论就应标注为“在该条件下成立”，而不是无条件放行。

反向判据同样明确：当被优化算子在端到端中占比远低于 θ、且没有证据表明它能消除跨算子开销时，不应把端到端门作为主要判据，否则只会得到一串无信息量的回退；当 trace 覆盖不足时，门的“无回归”结论不具备外推效力，必须与隐藏 shape 分布抽样联合使用；当候选改动涉及数值路径（融合、重排、降精度）时，采样式误差检查不足以支撑合入，需引入更强的正确性论证再进门。

最后一点落在判定式的阈值语义上。θ 与 ε 不是调参旋钮，而是部署契约的编码：θ 编码了“多小的收益不值得承担合入风险与维护成本”，ε 编码了“多大的数值偏差在该模型的下游任务中不可接受”。这两个数应由模型所有者而非 kernel 作者设定，并在每次模型或下游任务变更时复核。门的作用是把这两个契约值变成不可绕过的合入条件——候选可以来自任意搜索策略、任意语言与任意优化手法，但只有在真实调用上下文里同时满足收益与误差两条约束，才被允许进入生产。

回归门卡不住的那部分：边界、失效条件与系统代价

端到端回归门的判定逻辑本身很短：

$$\text{gain}_{\text{e2e}}=\frac{T_{\text{base}}^{\text{e2e}}-T_{\text{gen}}^{\text{e2e}}}{T_{\text{base}}^{\text{e2e}}},\quad \text{merge if }\ \text{gain}_{\text{e2e}}\ge \theta\ \land\ \text{maxerr}\le\epsilon$$
但它能给出的结论严格受限于“被测量的那一次替换”。典型翻车不是微基准造假，而是替换位置错了：候选 kernel 在 trace 里命中的是 decode 阶段的小 batch 调用，而端到端 benchmark 用 prefill 主导的负载跑，于是 kernel 侧时延降了，端到端却因 launch 开销与布局转换被吃掉，甚至变慢；反过来，某次融合改动只在长序列下才显出收益，短序列基准上被阈值误拒。回归门解决的是“部署收益是否真实存在”，不解决“这个 kernel 在别的 shape、别的并发、别的驱动版本下是否仍成立”，也不解决收益归因——它只回答合入与否，不回答为什么。

失效条件集中在三处。其一，Amdahl 稀释：单算子占端到端比例低于阈值量级时，任何真实收益都会落到 θ 之下，门会把有效优化判成噪声，这是阈值设计的结构性误拒，不是 kernel 的问题。其二，噪声吞掉信号：端到端 benchmark 受调度抖动、显存分配器状态、并发争用影响，重复次数不足时 gaine2e 的置信区间可能跨过 θ，门在临界点反复翻转。其三，正确性判据的盲区：maxerr≤ε 是逐元素数值检查，对布局错位、越界写、非确定性归约顺序引入的间歇性错误不敏感，尤其当替换改变了内存布局而接口层做了隐式拷贝时，数值一致但语义已偏。

边界类型门能拦住门拦不住
收益真实性微基准加速、端到端无收益收益归属哪个算子、是否可复用
正确性稳定的数值偏差布局/越界/竞态类间歇错误
泛化被测负载内的回归未见 shape、并发、驱动版本下的退化

系统代价必须提前计入预算：搭建真实模型与 trace 的工程量、每次判定需多次重复跑端到端 benchmark 的机时、以及为保持接口与内存布局一致而引入的适配层——后者本身可能带来一次额外拷贝，把候选 kernel 的收益在门内就抵消掉。工程判断是：把回归门当作合入前的最后一道闸，而不是优化搜索的反馈信号；阈值 θ 应按算子占端到端比例分层设定，对低于稀释下限的候选改用“微基准收益 + 调用上下文匹配”作为替代判据，并把每次回退的失败原因写入策略池，供后续生成阶段规避同类替换位置。
