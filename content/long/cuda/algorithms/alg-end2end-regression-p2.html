一 · 从 trace 到算子切片：热点提取的输入与代价

端到端回归门的第一步不是写 kernel，而是把“要优化什么”从真实负载里切出来。输入是一份真实推理或训练 trace（PyTorch profiler、Nsight Systems、或框架自带的 op-level 计时），输出是一组热点算子记录，每条记录至少携带：算子类型与调用栈、输入输出的 shape 与 stride、dtype、前后相邻算子、调用频次、以及该算子在整条 trace 中的累计时延占比。这一步的工程判断在于“上下文”必须一起切出来——只留 shape 不留前后算子，后面替换时就会丢掉融合机会与布局约束，候选 kernel 即便单点更快，插回去也可能因为多一次 layout 转换而净亏。

具体机制上，热点提取按累计时延排序取头部，但排序键不能只用 kernel 自身时延。一个被调用上千次的小算子，其单次 launch 开销在端到端里被放大；一个只调用几次的大 GEMM，其占比高但替换收益上限被 Amdahl 定律锁死。因此切片阶段就要记录调用频次与单次时延两个维度，供后续判断“值不值得进候选池”。伪代码思路是：对 trace 中每个 op 聚合 (op_type, shape, stride, dtype) 四元组为 key，累计时延与次数，再按累计时延降序取前 K 个，同时保留每个 key 的一条代表性调用上下文（前驱、后继、是否在融合块内）。

代价在这里已经出现：trace 采集本身有开销，全量 profiler 会引入可观测的减速与显存膨胀，长 trace 的存储与解析时间随调用次数线性增长；若为了降开销做采样，又会漏掉低频但高占比的算子。另一个代价是 token 层面的——把上下文序列化进 agent 的提示里，shape/stride/前后算子描述会占用可观的上下文预算，K 取得太大直接挤掉后续优化轮的推理空间。一个具体例子：某模型中一个 elementwise 加法在微基准里被优化到接近带宽上限，但它在 trace 中紧邻一个 transpose，切片时若没记录后继算子，替换后插入的 layout 转换就把收益吃光——这正是上下文必须随切片一起流动的原因。

二 · 替换与接口对齐：布局一致性的隐性成本

第二步把候选 kernel 插回模型对应位置。输入是候选 kernel 的源码/编译产物加上第一步的上下文记录，输出是一个可运行的替换版本：接口签名一致、输入输出 stride 与 dtype 一致、stream 与同步语义一致。这里的核心机制是“接口契约”而非“数值契约”——候选 kernel 必须接受与原算子相同的张量视图，不能要求调用方先做一次 contiguous 或 permute，否则这次转换的时延要记在候选账上。工程上通常用一个薄 wrapper 承担对齐：wrapper 检查 stride，必要时做显式拷贝并计时，把拷贝开销并入候选的端到端账本，而不是藏在模型代码里。

代价体现在两个方向。其一是显存：wrapper 为对齐做的临时缓冲会抬高峰值显存，在 batch 大、并发高的真实服务里，峰值显存上升可能直接压低可服务的并发数，端到端吞吐反而下降。其二是编译与加载时间：候选 kernel 若用 Triton 或 CuTe 模板，首次调用触发 JIT 编译，这段编译时间必须计入冷启动预算；若在 benchmark 的 warmup 阶段被掩盖，就会在真实部署的首请求上暴露。一个具体例子：候选 kernel 假设输入是行主序连续，而模型中该张量来自一次 slice，stride 非连续；wrapper 选择先 contiguous 再调用，端到端账本里就多了一次全量拷贝的带宽代价，收益公式里的 T_gen 必须包含它，否则回归门会被虚假收益骗过。

接口对齐还牵涉同步语义：原算子可能在默认 stream 上异步执行，候选若引入额外的事件或跨 stream 依赖，会改变重叠行为。这一步的输出应当是一份“可插拔清单”：替换点、wrapper 行为、额外拷贝与同步的显式记账，供第三步直接消费。

三 · 端到端 benchmark：warmup、多 batch 与噪声预算

第三步跑端到端 benchmark。输入是替换后的完整模型、真实并发配置与请求分布，输出是一组端到端指标：时延（均值与尾部分位）、吞吐、峰值显存。机制上有三件事必须做对。第一是 warmup：JIT 编译、cuBLAS/cuDNN 算法选择、显存池预热都要在计时窗口之外完成，否则首请求的冷启动会污染均值。第二是多 batch 与真实并发：只在单一 batch 上测会掩盖 launch 开销与占用率变化，回归门要求至少覆盖服务实际会遇到的 batch 区间，并在并发下测吞吐而非单请求时延。第三是重复测量与噪声预算：端到端受系统噪声影响，单次测量不足以判定收益是否超过阈值，需要多次重复取统计量，并把测量方差纳入判定。

收益公式在这里落地：

$$\text{gain}_{\text{e2e}}=\frac{T_{\text{base}}^{\text{e2e}}-T_{\text{gen}}^{\text{e2e}}}{T_{\text{base}}^{\text{e2e}}},\quad \text{merge if }\ \text{gain}_{\text{e2e}}\ge \theta\ \land\ \text{maxerr}\le\epsilon$$

其中 T_base 与 T_gen 必须是同一配置、同一 warmup 策略、同一并发下的测量，否则分子里的差值混入了配置差异。代价是明确的：端到端 benchmark 需要真实模型与真实 trace，搭建成本高；每次候选评估都要跑完整模型，单轮评估的机时远高于微基准；噪声要求多次重复，进一步放大机时。Amdahl 定律在这里起稀释作用——若目标算子只占端到端时延的一小部分，即便它被优化到接近零，gain_e2e 也低于阈值 θ，候选会被判为“不值得合入”。这不是误判，而是回归门的设计意图：部署价值按端到端计，不按微基准计。

一个具体例子：某候选在微基准上把目标算子时延压到原来的三分之一，但该算子只占端到端的一小段，替换后 gain_e2e 落在阈值之下；同时 wrapper 引入的拷贝让峰值显存上升，吞吐在多并发下不升反降。回归门据此拒绝合入，并把“占比不足 + 显存上升”写入失败原因。这一步的输出因此不只是通过/拒绝，还包括收益、显存、吞吐三组数值与测量方差，供第四步判定。

四 · 数值一致性与回归判定：正确性与性能同闸

第四步在跑性能的同时跑数值一致性检查，输出是 maxerr 与判定结论。机制上，一致性检查必须用与原算子相同的输入分布与 dtype 路径，比较对象是基线模型的输出而非孤立张量——孤立张量的比对会漏掉后续算子对误差的放大或掩盖。误差阈值 ε 按 dtype 与算子语义设定：归约类算子对累加顺序敏感，融合类算子改变了中间精度，阈值要相应放宽但不能放宽到掩盖真实错误。判定是合取：gain_e2e ≥ θ 且 maxerr ≤ ε 才允许合入，任一不满足即回退。

代价在于一致性检查本身要跑一遍完整前向（训练场景还要跑反向），机时与端到端 benchmark 同量级；若为了省机时只抽查部分 batch，误差可能落在未抽查的分布上。另一个代价是 ε 的设定需要工程判断：设得过紧，合法的融合优化会被误拒；设得过松，隐性错误流入生产。一个具体例子：候选把两个相邻的归约融合成一个，减少了中间张量的显存往返，端到端有收益，但融合改变了累加顺序，maxerr 略高于原算子的逐位一致；此时判定取决于 ε 是否按“融合后允许的误差预算”设定，而不是按“逐位一致”设定。这一步的输出必须把 maxerr 与 gain_e2e 一起记录，因为后续策略池要用这对数值判断失败原因是性能不足还是正确性越界。

五 · 回退与失败原因入池：策略池的输入格式

第五步处理未通过的候选：回退到基线，并把失败原因结构化写入策略池。输入是第四步的判定记录（收益、maxerr、显存、吞吐、测量方差）加上候选的生成来源（哪种模板、哪种调度、哪种融合尝试），输出是一条可供后续搜索消费的失败样本。机制上，失败原因要分维度标注而不是一句“未通过”：是 gain_e2e 低于 θ（占比不足或被 Amdahl 稀释）、是 maxerr 超 ε（正确性越界）、是显存上升压低并发、还是测量方差过大导致判定不可靠。这四个维度对应四种不同的后续动作：占比不足的算子应从候选池降权，正确性越界的融合模式应标记为高风险，显存上升的要检查 wrapper 的临时缓冲，方差过大的要增加重复次数而非改 kernel。

代价在这里是策略池的膨胀与 token 成本：每条失败样本都要序列化进后续 agent 的上下文，样本越多，单轮推理可用的上下文越少；若不压缩，策略池会挤占优化轮的预算。工程上通常按“失败维度 + 算子类别”聚合，只保留代表性样本与统计计数，而不是逐条保留。一个具体例子：同一融合模式在三个不同 shape 上都因 maxerr 越界被拒，策略池应记录“该融合模式在归约类算子上误差越界”这一条聚合结论，而不是三条重复样本；后续生成阶段据此避开该模式，节省的是生成与评估两头的机时。

回退本身也要计时：回退动作若涉及重新加载基线 kernel 或重建显存池，这段恢复时间属于工程代价，不能假设回退是零成本。回归门的输出因此是一条带账本的判定：合入则记录收益与误差，回退则记录失败维度与恢复开销，两者都进入策略池供下一轮流动使用。

六 · 流动的整体账本：每步代价的叠加方式

把五步串起来看，端到端回归门的代价不是单点开销而是叠加账本：trace 采集的减速与存储、上下文序列化的 token、wrapper 的拷贝带宽与临时显存、JIT 编译的冷启动、端到端 benchmark 的机时与重复次数、一致性检查的完整前向、策略池的上下文占用。这些代价中任何一项被漏记，都会让 gain_e2e 偏高或让判定不可靠。工程判断在于：账本必须在替换阶段就建立，wrapper 的拷贝与同步要显式计入 T_gen，JIT 编译要放在 warmup 之外单独计量，重复次数要按测量方差动态调整而不是固定值。

流动的方向性也值得注意：第一步切出的上下文决定了第二步能否对齐、第三步能否复现真实并发、第四步的 ε 能否按算子语义设定。上下文切错，后面每一步都在补偿而非优化。一个具体例子：切片时漏记了目标算子处于一个融合块内，替换后 wrapper 把融合块拆开，端到端多出一次中间张量的显存往返；此时第三步测出的 gain_e2e 为负，第四步判定回退，第五步把“融合块被拆开”写入策略池——这条失败原因本可以在第一步就避免，代价是整轮评估的机时。因此回归门的流动不是线性流水线，而是带反馈的循环：策略池的失败维度回流到切片与生成阶段，改变下一轮候选的分布。

最终落在具体机制上：端到端回归门的可信度取决于账本的完整性，而账本的完整性取决于每一步是否把自身代价显式输出给下一步。收益公式只是判定的表层，真正决定门是否可信的是 T_gen 里有没有混入未记账的拷贝、maxerr 的 ε 是否按算子语义而非逐位一致设定、以及失败原因是否以可聚合的维度入池。这三件事做对，回归门才不是一次性的通过/拒绝，而是可持续流动的工程判据。

回归门在真实 trace 上的失效边界与摊销代价

这套流程的脆弱点不在测量本身，而在“插回真实模型”这一步的语义保真度。候选 kernel 必须保持接口与内存布局一致，但真实 trace 里热点算子的调用上下文往往带有隐式契约：stride 约定、对齐假设、原地写回、与前后的融合边界。一旦替换后布局被迫插入一次 transpose 或 contiguous 拷贝，端到端收益就被这笔额外带宽吃掉。设候选 kernel 微基准时延 Tk、基线 Tkbase，插入的布局转换代价 Tlayout，则实际可观测收益为 (Tkbase−Tk−Tlayout)/Te2ebase；当 Tlayout 与微基准节省量同量级时，回归门必然拒绝一个在孤立环境里确实更快的 kernel——这是门本身的假阴性，而非候选的质量问题。

另一类失效来自 Amdahl 稀释与噪声的叠加。端到端收益被非热点部分摊薄，小算子优化极易落在阈值 θ 之下；而端到端 benchmark 又受并发、频率漂移、内存分配抖动影响，单次测量方差可能大于待判定收益本身。工程上必须把判定改成重复测量下的区间比较，而不是点估计：

$$\text{gain}_{\text{e2e}}=\frac{T_{\text{base}}^{\text{e2e}}-T_{\text{gen}}^{\text{e2e}}}{T_{\text{base}}^{\text{e2e}}},\quad \text{merge if }\ \text{gain}_{\text{e2e}}\ge \theta\ \land\ \text{maxerr}\le\epsilon$$

其中 θ 需按测量噪声下限设定，ε 则要覆盖不同 batch 与并发下的数值漂移，否则门会在“误拒有效优化”和“放行隐性错误”之间反复摇摆。

步骤输入输出主要代价
trace 热点提取真实推理/训练 trace算子+调用上下文trace 采集开销、存储
候选替换候选 kernel、接口契约可运行模型布局转换、编译时间
端到端 benchmark多 batch、真实并发时延/吞吐/显存重复运行墙钟、噪声
收益与一致性判定基线指标、maxerr合入/回退+失败原因误拒率、策略池污染

系统代价还体现在反馈闭环的吞吐上：每次候选都要跑完整端到端 benchmark 加数值一致性检查，单轮墙钟远高于微基准，直接压低单位时间内可评估的候选数，进而拖慢多轮优化的采样效率。因此回归门适合作为合入前的最后一道闸，而不是搜索循环里的高频打分器；把端到端测量放在候选已通过微基准与正确性初筛之后，才能让这道门的成本落在它真正该拦的那一小批候选上。
