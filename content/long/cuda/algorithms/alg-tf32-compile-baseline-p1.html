一 · 一次“虚高 3 倍”的评测翻车

先把事故讲清楚，因为它决定了这套方法的存在理由。某次 KernelBench 风格的内部评测里，一个 agent 生成的 fused LayerNorm+GELU kernel 在报告里拿到了 3.1× 的加速比，团队据此把它合入推理路径。上线后端到端收益接近零，甚至在小 batch 上略慢。复盘发现：分母用的是 torch.nn.functional 的 eager 路径，而该路径在评测容器里既没有开 TF32，也没有走 torch.compile 的融合；更糟的是，被测 shape 恰好落在 cuDNN 启发式选择的一个退化配置上，eager 参考本身就跑得异常慢。分子是精心调过 tile 的 kernel，分母是一条“没人会在生产里用的路径”，3.1× 里至少 2× 来自口径差，而不是 kernel 本身。

这类翻车不是偶发。LLM 生成的 kernel 天然会与“PyTorch 默认路径”比较，而“默认”是一个随环境漂移的量：allow_tf32 的开关状态、cudnn.benchmark 是否开启、是否经过 torch.compile 的算子融合、cuBLAS/cuDNN 的具体版本，任何一项变动都会让分母上下浮动数倍。于是加速比这个数字同时承载了“kernel 有多好”和“基线有多差”两个信号，二者不可分离。TF32/编译基线锚定要解决的，正是把后者钉死，让前者可读。

必须同时说清它不解决什么。它不判断生成 kernel 的正确性是否充分——那是 fp64 参考 oracle 与变异测试审计的职责；它不覆盖隐藏 shape 分布的抽样偏差；它也不替代 roofline/SOL 归一化去回答“这个 kernel 离硬件极限还有多远”。锚定只做一件事：给定一个 shape、一个输入分布、一套冻结的软件栈，定义一条可复现、可比较、且不会被“弱基线”污染的分母。

二 · 分母的定义：四路参考与取最优

机制上，锚定把分母从一个标量变成一个集合，再取集合的最小值。评测前锁定 torch.backends.cuda.matmul.allow_tf32、cudnn.benchmark、torch.compile 模式与 cuBLAS 版本，对同一输入分布分别测 eager fp32、eager tf32、torch.compile(max-autotune)、cuBLAS 直调四条参考路径，以四者最快时延作为分母。写成公式即：

$$S_{\text{eff}}=\frac{\min\{T_{\text{eager}},T_{\text{tf32}},T_{\text{compile}},T_{\text{cublas}}\}}{T_{\text{gen}}},\quad \text{valid}=\mathbb{1}\left[\max_i|y_{\text{gen},i}-y_{\text{fp64},i}|\le \tau\right]$$

这个 min 是关键设计，不是随手取快。取最优意味着分母代表“在这台机器、这套软件栈上，现有最强参考实现能做到什么”，于是 S_eff 回答的是“生成 kernel 是否击败了所有已知的成熟路径”，而不是“是否击败了一条被刻意留弱的路径”。同时 valid 项把精度绑进同一个数：只有误差在阈值 τ 内的加速才计入有效加速，否则标记为“精度换速度”，不进排行榜。这条约束直接堵住了用 TF32 甚至更低精度换时延、再拿去和 fp32 基线比的套利路径。

代价立刻显现。单 shape 的基线测量成本约为 4 条路径 × 100 次计时，加上各 20 次 warmup，即每 shape 至少 480 次 kernel 执行，相对只测一条 eager 基线是四倍量级的评测开销。更隐蔽的代价是 torch.compile 的 autotune 缓存：一旦某个 shape 触发过 autotune，后续测量会命中缓存，基线时延偏低，S_eff 被系统性压低。因此必须每 shape 清缓存后重测，这一步的编译时间本身就要计入评测墙钟。举例：一个 4096×4096 的 GEMM，若不清缓存，第二次测得的 compile 基线可能明显快于首次冷启动，导致同一 kernel 在两次评测中得到不同的 S_eff——这不是 kernel 变了，是分母变了。

三 · 容器与 manifest：让分母可复现

锚定的第二个机制是环境冻结。把 CUDA、cuBLAS、cuDNN、PyTorch 版本与 GPU 型号写入 manifest，容器镜像固定，禁止运行时升级。原因很直接：cuBLAS 在特定 shape 上的启发式选择随版本变化，同一个 GEMM 在不同 cuBLAS 版本下可能相差一个可观的倍数；驱动与 GPU 型号则决定 SM 数量、L2 容量与时钟行为。分母一旦跨机器漂移，S_eff 就失去了跨实验的可比性。

伪代码层面的评测循环大致是：对每个 shape，先 torch.cuda.empty_cache() 并清 compile 缓存，再依次跑四条参考路径，各 warmup 20 次、计时 100 次取中位数，同时记录每条参考路径相对 fp64 参考的最大误差与显存峰值，确认基线本身没有溢出、没有悄悄降精度；随后测生成 kernel 的时延与误差；最后输出 S_eff 与置信区间。这里“取中位数而非均值”是对 GPU 时延长尾的防御，而“记录基线自身误差”是对基线可信度的自检——如果 eager tf32 基线的误差已经逼近 τ，那么用它做分母去要求生成 kernel 满足更严的误差，就是不合理的。

代价是跨机器复现必须重跑全部参考路径，无法把分母当作常量搬运。这在多卡、多代 GPU 的评测集群里意味着每个新机器都要付一遍四路测量的成本。工程上的折中是：把 manifest 与基线时延一起存档，同一 manifest 内复用，跨 manifest 一律重测，绝不做“按比例换算”。因为换算假设了不同机器上四条路径的相对排序不变，而 cuBLAS 的退化恰恰会打破这个假设。

四 · 四路基线暴露的“弱项陷阱”

四条基线不只是为了取最小值，它同时是一张诊断表。单看 eager 与生成 kernel 的比值，你无法区分“生成 kernel 很强”和“eager 很弱”；四条路径并列后，若 cuBLAS 直调显著快于 eager，说明差距主要来自框架开销而非算法；若 torch.compile 明显快于 eager，说明融合机会被生成 kernel 重复实现了；若四条路径中某一条在特定 shape 上异常慢，那正是 cuBLAS 或 cuDNN 启发式的退化点。

后者是锚定最重要的副产品：它防止把 cuBLAS 的弱项当成生成 kernel 的强项。举例，某个非规则 batch 的 GEMM，cuBLAS 因 tile 选择不佳而退化，生成 kernel 只要击败这条退化路径就能拿到漂亮的 S_eff，但换到规则 shape 上优势立刻消失。锚定通过取四路最优，把这种“只在弱项上赢”的情况压回真实水平；同时把退化点本身记录下来，作为后续优化与回归的靶子。代价是评测报告变厚：每个 shape 要存四条时延、四条误差、四条显存峰值，存储与解析成本上升，且需要人工或自动规则去判定“某条基线退化”是否属于环境问题而非 kernel 问题。

五 · 适用边界：什么时候锚定是错的工具

锚定有明确的失效区。第一，当被测对象不是单算子而是端到端图时，四路参考无法覆盖图级别的调度、内存复用与算子间融合，此时分母应换成端到端基线，锚定退化为“固定编译开关”的弱版本。第二，当生成 kernel 使用了参考路径不具备的数值格式（如 fp8 或分块量化）时，valid 项的 τ 必须按格式重设，否则锚定会把合法的精度取舍误判为作弊；这不是锚定能自动决定的，需要评测者给出格式相关的误差预算。第三，当硬件或驱动频繁变动、无法冻结 manifest 时，跨实验的 S_eff 不可比，锚定只剩单次实验内的相对排序价值。

还有一个边界是成本结构上的：四路基线在小 shape 上会被启动开销主导，warmup 20 次、计时 100 次的中位数仍可能被 kernel launch 与 Python 调度噪声污染，此时 min 取到的是噪声的最小值而非真实最优。工程判断是：对极小 shape 改用 CUDA Graph 或事件计时并单独标注，不与大 shape 的 S_eff 混排。这类判断无法由公式给出，只能由评测设计者在 manifest 里显式声明。

把这些边界合起来看，锚定的定位就清楚了：它是评测口径的地基，不是评测的全部。它把“分母是什么”这件事从隐式默认变成显式契约，从而让 S_eff 这个数字在跨 agent、跨轮次、跨机器时具备可解释性；而正确性是否充分、shape 分布是否代表性、kernel 离 SOL 多远，仍要由各自的方法回答。一个只报告加速比而不报告分母构成的评测，在锚定视角下是不可审计的——这正是本方法要挡住的那类翻车。

锚定基线能救什么、救不了什么：一次“虚高 4 倍”的评测翻车

某次内部评测里，一个生成 kernel 在 matmul 形状上报告了数倍于 PyTorch 的加速比，团队据此把它推入候选池。复现时把分母换成 cuBLAS 直调并锁死 TF32 开关，加速比立刻塌回接近 1×——原来分母走的是未编译的 eager 路径，且 allow_tf32 在不同进程里取值不一致，生成 kernel 恰好跑在 fp32 高精度档、基线跑在 TF32 低精度档，比较的是两条不同数值口径的曲线。这类翻车不是“生成得不好”，而是分母不可信：基线本身既没有被固定精度语义，也没有被固定编译状态，更没有验证它自己是否数值正确。锚定基线要解决的就是这个具体问题——把分母从“随手一跑的 PyTorch”变成“口径可审计、可复现、数值自证的四条参考路径取最优”。它不解决的问题同样明确：它不提升生成 kernel 的绝对性能，不替代正确性 oracle，也不解决跨 GPU 架构的可移植性；它只是把“加速比”这个标量的可信度抬到工程可用的下限。

机制上，锚定发生在计时之前而非之后：容器镜像把 CUDA/cuBLAS/cuDNN/PyTorch 版本与 GPU 型号写进 manifest 并禁止运行时升级；对每个 shape 分别跑 eager fp32、eager tf32、torch.compile(max-autotune)、cuBLAS 直调四条参考路径，各 warmup 20 次、计时 100 次取中位数；同时记录每条参考路径相对 fp64 参考的数值误差与显存峰值，确认基线自身没有溢出、没有悄悄降精度。最终分母是四条基线的最快时延，分子是生成 kernel 的时延，输出 speedup 与置信区间。有效加速的判定写成：

$$S_{\text{eff}}=\frac{\min\{T_{\text{eager}},T_{\text{tf32}},T_{\text{compile}},T_{\text{cublas}}\}}{T_{\text{gen}}},\quad \text{valid}=\mathbb{1}\left[\max_i|y_{\text{gen},i}-y_{\text{fp64},i}|\le \tau\right]$$

这个式子的两个部分承担不同职责：Seff 用 min 而非单一路径，是为了让分母站在“PyTorch 生态在该 shape 上能达到的最好水平”上，从而暴露 cuBLAS 在特定形状上的退化，避免把 cuBLAS 的弱项误读为生成 kernel 的强项；valid 项则把“精度换速度”从加速比里剥离——若生成 kernel 快于基线但误差超阈值 τ，标记为“精度换速度”，不计入有效加速。代价随之而来：四条路径 × 100 次计时意味着单 shape 约 4 倍于单基线测量的计时成本，warmup 与中位数统计进一步拉长评测墙钟；torch.compile 的 autotune 缓存会污染后续测量，必须每 shape 清缓存，否则基线时延偏低、分母被系统性低估，加速比反而虚高。跨机器复现时，基线受 GPU 型号与驱动影响，换卡必须重跑全部参考路径，manifest 里任何一项版本漂移都会让历史 speedup 失去可比性。

适用边界可以用一张小表划清。锚定基线在“同一容器、同一 GPU、同一输入分布、生成 kernel 与基线共享数值语义”的前提下成立；一旦输入分布改变（例如稀疏度、batch 形状跨过 cuBLAS 启发式切换点）、或生成 kernel 使用与基线不同的累加顺序与精度档，分母就不再是同一问题的分母。它也无法判定生成 kernel 在边界 shape（极小 M、极大 K、非对齐 stride）上的正确性——那属于正确性 oracle 与形式验证的职责，锚定只保证“比较是公平的”，不保证“被比较者是对的”。工程判断上，把锚定当作评测流水线的准入闸门而非评分器：先让基线自证（误差、显存、版本 manifest 全部通过），再谈 speedup；任何跳过基线自证直接报加速比的数字，都应视为不可采信。

锚定基线解决的是口径问题，不是 kernel 质量问题

这套锚定方法要治的是评测分母的漂移，而不是生成 kernel 本身的优劣。它把 allow_tf32、cudnn.benchmark、torch.compile 模式与 cuBLAS 版本在评测前钉死，用 eager fp32、eager tf32、compile、cuBLAS 直调四条参考路径的最快时延做分母，再以 fp64 参考判定数值有效性：

$$S_{\text{eff}}=\frac{\min\{T_{\text{eager}},T_{\text{tf32}},T_{\text{compile}},T_{\text{cublas}}\}}{T_{\text{gen}}},\quad \text{valid}=\mathbb{1}\left[\max_i|y_{\text{gen},i}-y_{\text{fp64},i}|\le \tau\right]$$
典型翻车是生成 kernel 与未编译的 eager PyTorch 比较拿到虚高加速比，或反过来撞上已开 TF32 的默认路径被判为“变慢”，KernelBench 类评测中 2–5× 的口径差异正是这样被压平的。它不解决的是：生成 kernel 在真实端到端负载中的收益、跨 GPU 架构的可移植性、以及基线自身已经退化时的绝对性能判断。

失效条件集中在三处。其一，基线受 GPU 型号与驱动影响，换机器必须重跑全部参考路径，manifest 里锁定的镜像一旦漂移，分母即失效。其二，torch.compile 的 autotune 缓存会污染后续测量，必须每 shape 清缓存，否则基线时延偏低、加速比被系统性低估。其三，若四条基线中最快那条本身已越过误差阈值（例如 TF32 路径在长 K 归约上超 τ），分母就不可信，此时应退回 fp32 基线而非取 min。

边界情形后果处置
基线溢出/降精度分母偏小，加速比虚高剔除该路径，重测显存峰值
compile 缓存残留分母偏小，虚高每 shape 清缓存后重跑
生成 kernel 快但超 τ“精度换速度”标记不计入有效加速

系统代价是可量化的：单 shape 需四条路径各 warmup 20 次、计时 100 次取中位数，约 4×100 次计时开销，再叠加每条路径对 fp64 参考的误差核算与显存峰值采样；跨机器复现则要把这份成本整体重付一遍。工程判断因此很直接：锚定基线适合做“同机、同镜像、同 shape”下的相对排序与回归门禁，不适合当作跨集群的绝对性能榜单；当分母的四条路径彼此离散度已经接近生成 kernel 与基线的差距时，这套口径失去分辨力，应改用固定 cuBLAS 直调单路径并显式声明精度档位。
