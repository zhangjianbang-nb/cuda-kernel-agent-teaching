一 · 负载适配的判据：什么样的模型/算子/shape 值得进轨迹池

轨迹蒸馏的负载不是“随便找一批 kernel 跑强 agent”，而是先回答一个筛选问题：这条轨迹能否提供可迁移的诊断-修改模式。判据落在三个维度上。其一是模型侧：基座必须已经具备基本的 CUDA/Triton 语法生成能力与对编译错误的阅读能力，否则轨迹里大量 token 消耗在“语法纠错”而非“性能诊断”上，蒸馏出的模式停留在表层修补。其二是算子侧：优先选那些存在明确性能上界、且优化空间可由反馈信号定位的算子——规约、转置、softmax、layernorm、GEMM 分块变体这类有清晰 roofline 参照的负载，其“诊断到修改”的因果链短，轨迹的监督信号稠密；反之，访存模式高度依赖外部库实现细节的算子，轨迹中的修改往往不可归因。其三是 shape 侧：shape 必须能触发不同的 kernel 配置分支（如 tile 大小、grid 维度、是否走 split-K），否则轨迹退化为对单一配置的重复微调。

一个具体的筛选机制是给算子池打“可诊断性分”：对每个算子，先用弱基线跑一遍，记录编译失败率、首轮正确率与 profile 中可读的瓶颈指标数量；只有瓶颈指标能被 NCU 明确归因（如 shared memory bank conflict、低 occupancy、长依赖链）的算子才进入轨迹池。伪代码思路如下：

$$\text{pool}=\{o:\ \text{compile\_fail}(o)<\tau_c\ \land\ \text{first\_correct}(o)>\tau_a\ \land\ \text{bottleneck\_attributable}(o)\}$$

代价在数据生产端：每个算子要跑多轮优化，GPU 时间按“轮数 × 每轮编译+profile+benchmark”累积；把不可诊断算子剔出池子会缩小数据规模，但换来的是每条轨迹的 token 效率——同样一次 SFT，训练对中“诊断到修改”的比例更高，单位 token 的监督价值更大。举例：一个纯 elementwise 的向量加法算子，其瓶颈几乎总是带宽，诊断空间只剩向量化与合并访存两条，轨迹多样性低，进池收益有限；而一个 reduction 算子在不同 shape 下会在“原子操作争用”“两级规约”“warp shuffle”之间切换策略，轨迹能覆盖多种诊断路径，属于高价值负载。

二 · 基线锚定：速度阈值与正确性参照怎么选

轨迹过滤公式里的 speedup ≥ 1 看似简单，但基线选错会让整个数据集偏向“无意义的重写”。基线必须是同一硬件、同一输入分布下、由成熟实现（如 cuBLAS/cuDNN 或手写参考 kernel）测得的时延，而不是模型自己上一轮的输出——否则会出现“自我加速”的假阳性：模型把上一轮慢实现当基线，改出一个仍然慢于库实现的 kernel 却被判为成功。正确性参照同理，必须独立于被测 kernel，用高精度参考（fp64 或库实现）在相同输入上比对，容差按算子数值特性设定。

过滤条件的完整形式应写成三元组：正确性、相对基线的加速比、以及“非退化”约束（输出 shape/dtype 与语义一致、无硬编码分支）。用公式表达为：

$$\mathcal{D}_{\text{succ}}=\{(s,a):\ \text{pass}(a;\ \text{ref}) \ \land\ \frac{t_{\text{base}}}{t_a}\ge 1 \ \land\ \neg\text{cheat}(a)\}$$

代价体现在两个方向。基线过强（如直接对标高度调优的库 kernel）会让绝大多数轨迹被过滤掉，正样本稀疏，SFT 数据量不足；基线过弱（如朴素 triple-loop 实现）则让 speedup ≥ 1 轻易满足，轨迹里充斥“从极慢到稍慢”的修改，模型学到的是低水平的性能直觉。工程判断是：基线取“同硬件上库实现时延的固定倍数区间”作为软门槛，同时保留绝对时延作为辅助排序，让轨迹池既有足够样本又有区分度。具体例子：对一个 fp16 GEMM，若基线取 cuBLAS，则只有真正接近库性能的分块策略能过线；若基线取朴素实现，则任何带 shared memory 的版本都过线，轨迹的修改模式会退化为“加 shared memory”这一条。

三 · 输入分布设定：shape 抽样与数值边界

输入分布决定轨迹覆盖的配置空间。轨迹池里的 shape 不能只取“好跑”的方阵或 2 的幂，否则模型学到的 tile 选择在非对齐 shape 上直接失效。设定输入分布时要同时覆盖三类维度：规模维度（小 shape 触发低 occupancy 路径、大 shape 触发分块与流水）、对齐维度（能否被向量宽度整除、是否触发边界检查分支）、数值维度（极值、denormal、NaN/Inf 是否出现在测试输入中，影响正确性 oracle 的严格度）。

一个可操作的机制是分层抽样：每个算子维护一个 shape 族，按“对齐/非对齐 × 规模档位”交叉生成，轨迹收集时记录每条轨迹实际命中的 shape 桶，SFT 数据集按桶配比采样，避免大 shape 轨迹淹没小 shape 轨迹。伪代码思路：

$$\text{bucket}(o)=\{\text{align}\in\{0,1\}\}\times\{\text{size}\in\{\text{small},\text{mid},\text{large}\}\},\quad \text{sample}\propto \frac{1}{|\text{bucket}|}$$

代价是评测时延与显存：非对齐 shape 与大 shape 组合会让 benchmark 时间上升，边界检查分支引入的 divergence 让 profile 噪声变大，需要更多重复测量才能稳定判定加速比。具体例子：一个 layernorm 算子，在 hidden size 为 2 的幂时走向量化路径，在非 2 的幂时走标量回退路径；如果轨迹池只收 2 的幂 shape，模型 SFT 后遇到非对齐输入会写出越界访存或错误的分块，正确率在 held-out 上塌陷，而训练集指标看不出问题。

四 · 指标计算：正确率、首轮加速与轨迹质量

评测配方要区分三类指标，且各自的计算口径必须固定，否则跨批次比较失真。第一类是正确率：按算子、按 shape 桶统计通过参考 oracle 的比例，分母是该桶的全部尝试次数而非仅成功轨迹。第二类是首轮加速：模型在无反馈条件下第一次生成的 kernel 相对基线的加速比分布，取中位数与过线率两个统计量，因为均值会被少数极端快样本拉偏。第三类是轨迹质量：成功轨迹中“诊断步骤被后续修改实际采用”的比例，用于衡量蒸馏信号是否稠密。

指标聚合公式可写成按桶加权的形式，避免大 shape 主导整体分数：

$$\text{Score}=\sum_{b} w_b\cdot\frac{1}{N_b}\sum_{i\in b}\mathbb{1}[\text{correct}_i\land \text{speedup}_i\ge 1],\quad \sum_b w_b=1$$

代价在评测吞吐：每个 shape 桶都要跑参考实现与候选实现，profile 与 benchmark 的重复次数随桶数线性增长；若桶划分过细，评测时间成为瓶颈，且小桶样本量不足导致方差大。工程上通常把桶数控制在个位数到十余个，并对小桶设最小采样数。具体例子：评估 SFT 后模型的首轮加速时，若只报告全体均值，一个在 large 桶上偶然命中的高速 kernel 会掩盖 small 桶上普遍的失败；按桶报告过线率后，能直接看出模型在低 occupancy 路径上的诊断能力缺失，这正是后续 RL 需要补的方向。

五 · 负载不对时的失效形态

负载与评测配方错配不会报错，只会让 SFT 指标好看而下游失效。典型形态有三种。其一是算子池偏置：池中全是访存密集型算子，轨迹里的修改集中在合并访存与向量化，模型对计算密集型算子的分块与流水毫无概念，held-out 上正确率尚可但加速比普遍低于 1。其二是 shape 泄漏：训练 shape 与评测 shape 同分布，模型记住了特定 tile 配置，换 shape 后写出越界或错误规约，正确性 oracle 直接判失败。其三是基线漂移：轨迹收集时的基线实现与评测时的基线不一致（如驱动版本、库版本变化），导致 speedup ≥ 1 的判定在评测端系统性偏移，数据集标签与真实性能脱钩。

检测这些失效的机制是 held-out 交叉校验：在轨迹池之外保留一组算子与 shape，评测时同时报告训练桶与 held-out 桶的过线率差值；差值超过阈值即判定负载偏置。伪代码思路：

$$\text{bias}=\left|\text{pass}_{\text{train}}-\text{pass}_{\text{heldout}}\right|,\quad \text{bias}>\delta\Rightarrow \text{rebuild pool}$$

代价是数据重建成本：重新收集轨迹意味着再跑一轮强 agent 的多轮优化，GPU 时间与 token 消耗都不可忽略；但不重建的代价更大——SFT 把模型拉到“在训练分布上能写正确 kernel”的假起点，RL 冷启动时在真实分布上仍然正样本稀疏，蒸馏的收益被抵消。具体例子：若轨迹池只收方阵 GEMM，模型 SFT 后在 batched 非方阵 GEMM 上首轮正确率明显下降，而训练集指标平稳；此时应把非方阵与 batch 维度加入池子并重跑收集，而不是加大 SFT 轮数。

六 · 配方落地的工程判断

把上述四件事（负载筛选、基线锚定、输入分布、指标口径）固化成一份可复现的配方文件，是轨迹蒸馏能被信任的前提。配方文件应记录：算子池清单与可诊断性打分、基线实现及其版本、shape 桶划分与每桶最小采样数、正确性 oracle 的容差与数值边界、指标聚合权重。每次重新收集轨迹或重新评测，都以该文件为唯一事实源，任何字段变更都要触发 held-out 复验。

一个具体的落地约束是预算感知：轨迹收集的 GPU 时间按“算子数 × 轮数 × 每轮 profile 开销”估算，配方里应给出单算子预算上限，超预算的算子降级为少轮次或移出池子。这与 SFT 的训练 token 预算形成对冲——收集端多花 GPU 时间换来更稠密的监督，训练端就能用更少 token 达到同等首轮正确率。工程判断落在取舍上：当 held-out 过线率与训练桶过线率的差值持续偏大时，优先修负载与输入分布，而不是调 SFT 的超参；因为负载错配是数据层面的系统性偏差，超参调整无法补偿。

负载选错时，蒸馏先坏在哪一环

成功轨迹蒸馏的收益高度依赖负载与基座模型的匹配度，这一点在配方设计阶段就必须显式建模，而不是等 SFT 跑完再看 held-out。轨迹里的每个训练对是“状态+反馈 → 下一步动作”，状态由算子语义、shape、当前代码与上一轮反馈共同构成；若基座模型在训练负载上本就极少产出可编译代码，则轨迹中的诊断动作对它而言是纯噪声——它学不到“为什么这行会越界”，只能记住“看到这类报错就贴这段补丁”。更隐蔽的失效是负载过窄：算子池若集中在 elementwise 与 reduction，轨迹里大量出现的是向量化与 shared memory 归约模式，模型会把“加 `__syncthreads()` 再重写循环”当成通用解法，迁到 GEMM 或 attention 类算子上时首轮正确率反而低于未微调基座。因此算子池必须按访存模式、并行维度、是否含规约与是否需 tiling 分层抽样，且每层保留足量 held-out 算子只做评估、不进 SFT。

基线选择直接决定过滤阈值是否合理。若基线取 PyTorch eager 而非框架内已融合的算子实现，则大量轨迹的“加速”只是消除了框架开销，蒸馏进去的是“绕开框架”而非“写对 kernel”；这类轨迹在真实部署中相对融合基线并不加速，却占满了 $\mathcal{D}_{\text{succ}}$。过滤条件应写成相对“同语义最强可用基线”的加速比，并对每个算子记录基线来源与测量协议；同时把正确性 oracle 前置为硬门槛——数值容差、边界 shape、非连续 stride、空 tensor 与极大/极小规模都要覆盖，否则一条硬编码输出或对特定 shape 特判的轨迹会污染整个训练对集合。代价是明确的：每算子多基线测量与多 shape 正确性校验会把数据生产阶段的 GPU 时间成倍放大，而轨迹收集本身已依赖强 agent 多轮搜索，这部分开销无法用采样并行完全摊薄。

输入分布设定是第二个易被低估的边界。轨迹中的反馈（编译错误、越界、数值偏差、profile 热点）与 shape 强相关：小 shape 下 kernel 启动开销主导，轨迹学到的“减 launch 次数、合并循环”在大 shape 上会牺牲占用率；大 shape 下 tiling 与寄存器压力成为主矛盾，轨迹里的分块参数在小 shape 上又造成浪费。合理做法是每个算子采样一组对数分布的 shape，并在训练对里保留 shape 作为状态的一部分，让模型学会条件化而非记住单一配置。指标上不能只报最终正确率，应同时记录首轮编译通过率、首轮正确率、首轮相对基线加速比与达到正确所需轮数；后者直接对应 RL 初始化质量——若 SFT 后模型仍需多轮才正确，说明蒸馏的是“修补”而非“一次写对”，RL 阶段的正样本仍稀疏。

硬件维度同样会改变负载的有效性。不同架构的 shared memory 容量、warp 调度与访存粒度不同，同一轨迹里的分块尺寸与同步点在另一代卡上可能直接触发资源超限或性能倒退；把跨架构轨迹混入同一 SFT 集，等于让模型在状态里看不到硬件标识却要输出架构相关决策。工程判断是：轨迹收集与 SFT 数据构造按目标硬件分桶，跨桶只做评估不做混合训练；held-out 同时按算子与硬件切分，任一维度掉点即回退到更窄的负载并补采轨迹，而不是靠加大 SFT 轮数掩盖。表里给出负载失配时的典型症状与对应代价，便于在配方阶段定位。
