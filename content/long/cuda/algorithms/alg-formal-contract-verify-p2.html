一 · 从签名与语义提取合约：前置条件的机械生成

合约验证的第一步不是求解，而是把 kernel 的接口契约从“人读的注释”变成“机器可判定的谓词”。输入是 kernel 的 CUDA C++ 签名、launch 配置（grid/block/tile）、以及它在 PyTorch 侧的等价语义描述（例如“对最后一维做 softmax”“沿 dim=1 求和”）。输出是一组前置条件 Pre 与后置条件 Post 的合取式，前者约束合法输入空间，后者约束输出关系。这一步的代价主要落在 token 与人工审阅上：agent 需要读取签名、推断 stride 与对齐假设，把 PyTorch 语义中隐含的广播、padding、mask 规则显式化；一个中等复杂度的融合 kernel 往往要生成数十条原子谓词，每条都要与参考实现交叉核对，否则后续 SMT 求解会在错误的前提上给出“证明通过”的假阳性。

具体机制上，前置条件按三类拆分：shape 约束（如 N % tile == 0 或允许尾块）、dtype 与对齐（指针 16 字节对齐、元素宽度决定向量化可行性）、以及索引域（线程索引映射到全局坐标的合法区间）。后置条件则写成输出张量与输入张量的逐元素等式，外加一条独立的结构性谓词 NoOOB，它不依赖数值语义，只断言所有访存地址落在分配区间内。把 NoOOB 单独抽出是关键工程判断：它让索引正确性与数值正确性解耦，前者可交给 SMT 确定性判定，后者留给 fuzz 抽样。

代价的具体形态是“谓词爆炸”：每增加一个可选的尾块处理分支，前置条件就要多一组析取项，SMT 求解的分支数随之上升。举例来说，一个带 mask 的 attention kernel，其前置条件需同时表达“序列长度可被 tile 整除”与“不可整除时最后一列 mask 为真”两条路径，agent 若把两者写成同一条含糊的约束，求解器会在边界上给出反例，而这个反例往往只是合约写错而非 kernel 写错——这类“合约 bug”在回灌修复信号前必须先被过滤，否则会把 agent 引向错误方向。

二 · 循环与索引翻译为符号表达式

拿到合约后，第二步是把 kernel 的循环体与索引算术翻译成符号表达式，供求解器消费。输入是 kernel 源码的控制流（for 循环、if 分支、warp 级 shuffle、共享内存读写），输出是一组以符号输入 x 为自由变量的路径约束与状态转移。这一步的机制核心是“索引算术的位向量建模”：线程索引 threadIdx.x、块索引 blockIdx.x、以及由它们派生的 row = blockIdx.y * TILE + threadIdx.y 全部映射为固定位宽的位向量，乘法与取模按机器语义精确建模，避免整数溢出被忽略而漏掉真实越界。

公式层面，这一步产出的是路径条件集合，每条路径对应一个 pc_i(x) 与一个地址表达式 addr_i(x)，后续 BMC 要证明的就是：对任意满足 Pre 的 x，存在某条路径使 addr_i(x) 越界或使输出等式不成立。代价在这里第一次显性化——位向量乘法的求解复杂度随位宽与嵌套深度快速增长，一个 128×128 tile 的二维索引展开会产生大量非线性项，SMT 求解器对这类项的处理从秒级滑向分钟级。工程上的缓解手段是把 tile 维度符号化但把 tile 大小固定为常量，让乘法退化为常量移位，代价是失去“任意 tile 大小均正确”的普适性，只证明了当前配置下的正确性。

具体例子：一个二维卷积 kernel 的索引表达式包含 ih = oh * stride - pad + kh，其中 kh 是循环变量。翻译时若把 kh 当作无界整数，求解器会立刻找到 ih < 0 的反例；正确做法是把 kh 的循环边界 [0, KH) 作为路径约束的一部分加入，使反例只在真实可达的索引域内产生。这一步的疏漏是 BMC 假反例的主要来源，也是 agent 修复信号噪声的主要来源。

三 · BMC 有界展开：深度即代价

第三步是对展开后的路径做有界模型检验。输入是上一步的符号表达式与一个展开深度 k，输出是三种判定之一：在深度 k 内找到违反 Post 的反例、在深度 k 内未找到反例（记为“有界通过”）、或求解超时。机制上，BMC 把循环展开为 k 份拷贝，把“存在反例”编码为一条合取式交给 SMT 求解器判定可满足性；可满足即反例，不可满足即在深度 k 内无违反。

$$\text{Proved}=\forall \mathbf{x}\in\mathcal{D}_{\text{pre}}:\ \text{Post}(\text{Kernel}(\mathbf{x}),\mathbf{x})\ \wedge\ \text{NoOOB}(\mathbf{x}),\quad \text{Cost}=|\text{BMC depth}|\times|\text{SMT queries}|$$

这条公式把代价结构说透了：总代价是展开深度与查询数的乘积，两者都随 tile 规模线性或超线性增长。深度 k 的选择不是任意的，它必须覆盖典型 tile 大小对应的循环次数——一个 128×128 tile 在 16×16 线程块下每个线程要迭代 64 次，若 k 取小于 64，则循环尾部的越界路径根本不在验证范围内，此时“有界通过”是空洞的。代价的具体量级：大 tile 的 BMC 落在分钟级到小时级，这个时延意味着它无法嵌入每轮 RL 的奖励计算回路，只能作为离线门禁或阶段性审计。

具体例子：一个归约 kernel 在展开深度不足时，前 k 次迭代的索引都被证明在界内，但第 k+1 次迭代的跨步写入恰好越过共享内存边界。BMC 报告“有界通过”，而实际运行在特定 shape 下触发越界。这正是“有界通过 ≠ 证明”的工程含义：报告必须携带深度参数，下游消费者据此判断置信度，而不是把有界通过当成无条件正确。

四 · 反例提取与回灌：精确触发条件的价值

第四步只在验证失败时发生，但它是整条流水线对 agent 最有价值的一环。输入是求解器返回的可满足赋值，输出是一个具体的、可执行的输入配置：shape、dtype、以及逐元素的输入值（或至少是触发越界的那几个关键索引处的值）。机制上，SMT 模型给出的赋值是符号变量的具体实例，工程上需要把它“物化”为可被 PyTorch 或 CUDA runtime 直接消费的张量——这包括把符号 shape 还原为具体维度、把符号索引值映射回张量坐标、以及补齐未被约束的自由变量（通常填零或填随机种子固定的值）。

这一步的性能代价是“物化开销”，通常远小于求解本身，但有一个隐性成本：反例可能依赖未指定的自由变量，若物化时随意填充，复现时可能触发不同的路径。稳妥做法是把所有自由变量一并纳入模型赋值，保证反例是自洽的完整输入。正确性代价则体现在反例的“最小性”上——求解器给出的往往不是最小反例，agent 拿到一个 128×128 全张量的反例后难以定位根因，工程上常追加一步收缩：固定部分维度、二分缩小触发集合，把反例压到能触发错误的最小 shape。这一步的额外 SMT 查询会推高总代价，但换来的是修复信号的信噪比。

具体例子：一个 softmax kernel 在 N 不能被 tile 整除时，尾部线程读取了未初始化的共享内存槽位。SMT 返回的反例精确指出 N = tile + 1 且最后一个 block 的 threadIdx.x = 0 越界。agent 无需猜测触发条件，直接把尾块分支的 mask 补上。对比之下，fuzz 要撞到这个边界需要构造恰好落在 tile 边界外的长度，抽样命中率低且不可解释——反例的确定性正是合约验证相对抽样的核心增量。

五 · 未证明路径的标记与置信度合并

第五步处理“既没证明也没反驳”的剩余空间。输入是 BMC 的深度参数、超时查询列表、以及 fuzz 的抽样覆盖统计，输出是一份分层的置信度报告：哪些性质是确定性证明的、哪些是有界通过的、哪些是完全未覆盖的。机制上，每条性质被打上三态标签，并与 fuzz 的通过率做合取式合并——只有“证明通过 ∧ fuzz 未发现反例”才进入高置信度桶；“有界通过 ∧ fuzz 通过”进入中置信度桶并标注深度；超时或未展开的路径进入“未证明”桶，明确列为残余风险。

代价在这里体现为报告体积与人工审阅时间：一个包含数十条性质的 kernel，三态标签与深度参数的组合会让报告膨胀，工程上需要用结构化 schema 约束字段，避免自由文本描述淹没关键信息。另一个代价是“置信度不可传递”：有界通过的性质不能与其他性质组合成更强的结论，因为组合证明需要每条性质都无界成立，而有界通过只保证深度内成立。这一点在多 kernel 流水线的端到端验证中尤其致命——单 kernel 的有界通过无法支撑整条流水线的正确性声明。

具体例子：一个 fused kernel 的索引性质被证明无越界，但其归约顺序的结合律性质因浮点建模成本高而只做了整数索引层面的有界验证，数值结合律留给 fuzz。报告中这两条性质分属不同置信度桶，下游若把“无越界已证明”误读为“整个 kernel 已验证”，就会高估安全性。工程判断是：把 NoOOB 的证明与数值正确性的抽样明确分列，让消费者看到证明的边界在哪里。

六 · 浮点语义的建模成本与验证边界

整条流水线有一个绕不开的边界：浮点。SMT 对 IEEE-754 的建模需要精确表达舍入模式、非规格化数、NaN 传播，其求解复杂度远高于整数位向量，工程上多数验证器只对整数索引与结构性质做完整建模，浮点数值等式则退化为“在给定舍入假设下的近似约束”或干脆交给 fuzz。这一步的输入是 kernel 中的浮点运算序列，输出是“可建模部分”与“不可建模部分”的切分；代价是切分本身需要人工判断哪些浮点性质值得投入建模成本——归约结合律在整数上可证，在浮点上只能验证“在特定求和顺序下与参考实现的误差界”，而这个误差界又依赖输入分布。

机制上的折中是：把浮点运算抽象为不满足结合律的符号算子，只验证“不引入额外舍入”这类结构性质，数值正确性完全交给 fp64 参考 oracle 的抽样比对。这样做的正确性代价是明确的——验证覆盖的是“算法结构正确”，不是“数值结果正确”，两者在报告中必须分开陈述。性能代价则是双轨制的：结构性质走 SMT，分钟级；数值性质走 fuzz，秒级但只给抽样置信度。具体例子：一个 layernorm kernel 的均值归约，SMT 能证明其索引不越界、累加器初始化正确，但无法证明浮点求和顺序与 PyTorch 逐位一致；后者只能靠 fuzz 在若干 shape 上比对误差。工程判断落在“证明什么、抽样什么”的切分线上，而不是追求全证明——全证明的建模成本会把 BMC 推到小时级以上，彻底脱离可用的验证节奏。

有界证明的边界：未证明路径、浮点缺口与 RL 循环的时间预算

这套流程的失效点不在“证明失败”，而在“证明通过”的语义被悄悄放大。BMC 只对展开深度内的路径给出确定性结论：设循环展开上界为 d、tile 维度为 T，则被覆盖的输入集合是 $$\mathcal{D}_{\text{proved}}(d)=\{\mathbf{x}\in\mathcal{D}_{\text{pre}}\mid \text{loop trips}(\mathbf{x})\le d\}$$，而 $$\text{Proved}=\forall \mathbf{x}\in\mathcal{D}_{\text{pre}}:\ \text{Post}(\text{Kernel}(\mathbf{x}),\mathbf{x})\ \wedge\ \text{NoOOB}(\mathbf{x}),\quad \text{Cost}=|\text{BMC depth}|\times|\text{SMT queries}|$$ 里的全称量词实际只落在 $$\mathcal{D}_{\text{proved}}$$ 上。深度按“典型 tile 大小”选取时，边界 tile（尾块、非对齐 shape、动态 grid 的最后一轮）恰恰落在证明域之外，却被报告为“已验证”。工程上必须把通过结果拆成三态：证明、反例、未证明，并把未证明路径的输入集合显式回灌给 agent 与 fuzz 调度器，否则置信度是虚高的。

第二个缺口是浮点。SMT 对 IEEE-754 的建模需要位级编码加法、乘加与舍入模式，归约结合律一旦写成合约，求解器要在交换律与浮点非结合性之间做位爆破，查询规模随元素数超线性增长。因此多数合约只覆盖整数索引、读写范围与结构性质（NoOOB、shape 一致性、dtype 对齐），数值等式退化为“在给定舍入假设下的近似约束”，最终数值正确性仍由 fuzz 承担。这意味着验证通过并不蕴含“归约结果与 PyTorch 逐位一致”，agent 若把证明当作数值 oracle 使用，会在容差边界上产生系统性误判。

系统代价体现在流水线位置而非单次求解。一次 BMC 在大 tile 上处于分钟级到小时级，而 RL 每轮需要的是秒级奖励信号，验证因此不能放在内循环，只能作为离线闸门或按采样触发的深度检查。可行的折中是分层调度：每轮 RL 只跑索引与边界性质的浅层查询（深度取小、查询数少），把全深度 BMC 留给候选提交前的准入检查，并把反例缓存为回归用例，避免同一 shape 重复求解。反例本身是精确的 shape 与输入值，agent 修复时无需再猜触发条件，这是该方案相对 fuzz 的核心收益；但缓存命中率低时，重复求解的编译与求解时间会挤占生成预算。
