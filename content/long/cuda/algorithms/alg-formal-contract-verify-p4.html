一 · 负载选择的判据：从合约可证性反推 kernel 形态

负载与评测配方不是先挑 benchmark 再跑，而是从“这个 kernel 的合约能否被有界验证覆盖”反推。给定 Proved = ∀x∈D_pre: Post(Kernel(x),x) ∧ NoOOB(x)，一个负载是否值得进入形式化验证流水线，取决于三件事：前置域 D_pre 能否被有限条 shape/dtype/对齐约束枚举完；后置条件能否写成不依赖浮点语义的等式或不等式；索引表达式在符号化后是否仍落在 SMT 可判定的整数线性算术片段内。凡是索引含数据依赖的间接寻址（gather/scatter、稀疏路由、动态 top-k），符号表达式会退化为带未解释函数的数组理论，求解代价急剧上升，这类算子应被划到 fuzz+fp64 oracle 一侧，而不是硬塞进 BMC。

适合的形态有三类。第一类是纯仿射索引的 elementwise 与 tile 级 GEMM：索引是 blockIdx/threadIdx 的线性组合，边界条件可写成 0 ≤ i < N 的合取，BMC 深度只需覆盖一个 tile 的展开。第二类是固定归约树的 reduction（行/列 sum、softmax 的分母），结合律与累加顺序可作为合约的一部分显式声明，验证器只需检查“任意置换下结果等价”这一结构性质，而不必建模 float 舍入。第三类是 layout 变换（transpose、swizzle、CuTe 的 tiled copy），其正确性完全由索引映射的双射性刻画，是形式验证性价比最高的负载。反过来，含原子操作、跨 block 通信、动态并行度的 kernel，其状态空间随 grid 规模组合爆炸，BMC 深度一旦超过单 block 的循环上界就无法收敛。

代价在这里是具体的：一个 128×128 tile 的 GEMM，把内层 K 循环完全展开后，符号状态数随 tile 面积平方增长，单次 BMC 查询在分钟级到小时级，这意味着它无法进入每轮 RL 的 rollout 循环——RL 一轮要采样成百上千个候选，验证只能作为离线门禁或最终验收，而不是即时奖励信号。工程判断是：把负载切成“每轮 RL 用 fuzz 快速筛、周期性用 BMC 复核”的两档，而不是对所有负载统一要求证明。

二 · 基线锚定：编译基线与数学基线的双重选择

基线选择的核心不是“跟谁比快”，而是“跟谁比才不冤枉候选”。形式化验证场景下基线承担两个不同职责：数学基线（fp64 参考实现）负责正确性 oracle，编译基线（torch.compile / cuBLAS / Triton 自动调优产物）负责性能锚定。二者不可混用：用编译基线做正确性比对会把编译器自身的近似（TF32、fast-math、融合重排）当成 ground truth，从而放过候选 kernel 的真实数值偏差；用 fp64 基线做性能比对则毫无意义，因为它的 roofline 位置与候选完全不同。

具体机制上，正确性基线应写成与 kernel 同语义但不同实现的 fp64 版本，并在合约里显式声明容差合约：|out_fp32 - out_fp64| ≤ atol + rtol·|out_fp64|，其中 atol/rtol 由 dtype 与归约长度决定，而不是拍脑袋常数。性能基线则要固定编译基线的版本、后端与调优状态，否则同一 shape 下 cuBLAS 的 heuristic 选择会随版本漂移，导致候选的相对分数不可复现。这里与前文“TF32/编译基线锚定”的分工是：那部分讲如何锁定基线数值口径，本部分只讲基线在负载配方中的角色分配。

代价体现在 token 与时延两侧：跑一次 fp64 参考 oracle 对大 shape 意味着数倍于 fp32 的显存与带宽占用，若在 RL 每步都调用，单次 rollout 的墙钟时间被 oracle 拖长；而编译基线若每次评测都重新 autotune，编译时间本身会淹没候选 kernel 的执行时间，使“性能提升”变成“编译缓存命中率”的假象。工程做法是把 fp64 oracle 结果按 (shape, dtype, 输入种子) 缓存，编译基线产物按版本号固化，二者都作为评测配方的静态资产而非每轮现算。

三 · 输入分布设计：让反例可复现、让覆盖可度量

输入分布不是“随机就行”，它同时决定 fuzz 的覆盖率和 BMC 反例的可解释性。设计原则是分层：结构层固定 shape/dtype/stride/对齐，数值层控制取值范围与特殊值密度，扰动层注入 NaN/Inf/denormal/极值以触发边界路径。结构层必须与 D_pre 完全一致，否则 BMC 证明的是另一个 kernel；数值层则要保证 fp64 oracle 与候选在同一输入上可比，特殊值密度过高会让容差合约失效（NaN 传播使不等式无意义），过低则漏掉溢出与下溢路径。

一个可操作的配方是：对每个负载维护一张输入分布表，按 (shape 类别 × dtype × 特殊值比例) 三维取样，shape 类别覆盖 tile 整除、非整除、单元素、超大 N 四档；特殊值比例设 0、低密度、高密度三档。BMC 的反例输入直接取自这张表的结构层，因为反例必须是合法前置域内的具体 shape 与索引值，验证器输出的反例若落在 D_pre 之外则说明前置条件写错了，这本身就是合约 bug 的信号。伪代码思路：

$$\text{Cover}_{\text{fuzz}}=\frac{|\{\text{branch}\in\text{CFG}:\ \exists x\in\text{Sample},\ \text{exec}(x)\ \text{hits}\ \text{branch}\}|}{|\text{CFG}|}$$

覆盖率作为输入分布是否合格的度量，比“跑了多少条样本”更有信息量。代价是采样成本：要覆盖非整除 tile 与极值路径，样本数需按分支数而非 shape 数增长，单轮 fuzz 的 kernel 启动次数与时延随之上升；若把特殊值密度调高以省样本，又会引入大量被容差合约判为失败但实为数值噪声的假阳性，反过来污染 agent 的修复信号。

四 · 指标计算：把正确性、性能、可证性拆成三条独立轴

指标不能压成一个标量。形式化验证负载至少要报三组数：正确性轴（fuzz 通过率、fp64 最大相对误差、BMC 证明/反例/未证明三态计数）、性能轴（相对编译基线的加速比、SOL 利用率、绝对时延）、可证性轴（被证明的路径占比、BMC 展开深度、单次查询耗时）。三轴独立报告的理由是它们互相不可折算：一个 kernel 可能 fuzz 全过但 BMC 给出反例（说明 fuzz 漏了边界），也可能 BMC 全证但性能低于基线（说明索引化简牺牲了访存合并）。

可证性轴的计数口径必须写死：Proved 只统计在给定 BMC 深度内无违反的路径，超出深度的路径记为“未证明”而非“通过”，并与 fuzz 结果合并成置信度区间，而不是二值判定。性能轴的加速比要以固化编译基线为分母，且同一 shape 下取多次测量的中位数以抵抗频率抖动。代价在于：三轴全量报告使单次评测的 token 消耗与墙钟时间成倍增加，尤其 BMC 查询本身是分钟级，若每个候选都跑全量三轴，评测吞吐会被可证性轴拖垮。工程折中是分级报告——RL 内循环只报正确性轴与性能轴，可证性轴按批次抽样复核。

轴指标失败时的信号主要代价
正确性fuzz 通过率、fp64 最大相对误差容差合约被突破，回灌具体输入fp64 oracle 的显存与带宽
性能相对编译基线加速比、SOL 利用率索引化简牺牲合并访存基线 autotune 的编译时间
可证性Proved/反例/未证明计数、BMC 深度前置条件写错或索引非线性分钟级到小时级单次查询

五 · 负载不对时的失效模式：三种可诊断的崩塌

负载配方错误不会表现为“分数偏低”，而会表现为三种可诊断的崩塌。第一种是前置域过宽：D_pre 里混入了 kernel 实际不支持的 shape（如非对齐 stride），BMC 立刻给出反例，但反例是合约 bug 而非 kernel bug，agent 会去修一个不存在的越界，浪费整轮 rollout。第二种是输入分布与合约容差不匹配：特殊值密度过高使 fp64 oracle 自身溢出，容差不等式两边都是 Inf，比较结果无意义，fuzz 通过率虚高。第三种是基线漂移：编译基线版本或 autotune 状态未固化，同一候选在不同轮次得到相反的性能结论，RL 的奖励信号变成噪声，搜索退化为随机游走。

诊断手段是把失效模式映射回配方字段：反例落在 D_pre 外 → 查前置条件提取；fuzz 通过率异常高且误差分布集中在极值 → 查特殊值密度与容差合约；性能结论不可复现 → 查基线固化。每种失效都有明确代价：第一种浪费的是 agent 的修复 token 与 BMC 查询时间；第二种浪费的是 oracle 的显存并污染正确性轴；第三种直接摧毁 RL 的信用分配，使多轮迭代的 keep-revert 判据失效。具体例子：一个 softmax kernel 的负载若把 N 设为非 2 的幂且未在 D_pre 中声明该约束，BMC 会在归约树的非整除分支上给出反例，而这个分支在真实调用中根本不会出现——修复信号指向了错误的代码路径。

六 · 配方固化：把负载写成可版本化的合约资产

负载配方的最终形态是一份可版本化的合约资产，包含：D_pre 的结构约束清单、输入分布表、fp64 oracle 的容差参数、编译基线的版本与调优快照、BMC 展开深度与查询预算。这份资产与 kernel 源码分离，使得同一份配方可以跨候选复用，也使“负载变了”与“kernel 退化了”在评测日志里可区分。机制上，配方以结构化文件落盘，评测器读取后生成 fuzz 采样计划与 BMC 查询脚本，二者共享同一份 D_pre，避免 fuzz 与验证在不同前置域上各说各话。

代价是配方维护本身成为工程负担：每新增一个负载就要标定容差参数与 BMC 深度，标定不充分会让可证性轴长期停在“未证明”。工程判断是优先把配方固化在索引仿射、归约结构固定的算子上，对数据依赖寻址的算子只保留 fuzz 档并显式标注“无形式化覆盖”，而不是用浅层 BMC 制造虚假的证明感。配方固化的收益在跨轮次可比性：当 agent 的候选在多轮 RL 中演化时，只有配方不变，性能与可证性轴的差分才归因于 kernel 本身。

负载配方与验证边界：合约方案适合什么、在哪儿失效

合约验证的负载配方不是“随便挑几个 KernelBench 题跑通”，而是要让前置条件 \(\mathcal{D}_{\text{pre}}\) 的符号化规模与 BMC 深度落在可解区间。选型的第一条判据是索引结构：一维连续索引、固定 stride 的 gather/scatter、tile 内二维仿射索引，翻译成符号表达式后约束数量随 tile 边长线性增长，SMT 求解器能在可接受时间内给出 sat/unsat；一旦索引依赖运行期数据（如 sorted 后的 segment offset、动态稀疏行指针），符号表达式退化为带数组理论的间接寻址，求解成本急剧上升，此时应把该段降级为 fuzz 覆盖、只对边界检查做局部合约。第二条判据是归约结合律的可表达性：把“输出等于按某种顺序累加”写成后置条件时，整数归约可直接编码为求和等式，浮点归约只能退化为“结果落在区间内”的弱断言，因此负载应优先选整数索引类与结构类 kernel（copy、transpose、padding、边界 clamp、index 计算），把数值等价留给 fuzz 与对拍。

基线与输入分布的设定直接决定反例是否有意义。基线不是“PyTorch 参考实现跑一遍”，而是把 PyTorch 语义提取出的前置条件当作合约的一部分：shape 约束、dtype、对齐、stride 连续性都要显式写进 \(\mathcal{D}_{\text{pre}}\)，否则求解器会在合法但 PyTorch 根本不产生的输入上找到“反例”，agent 拿着这种反例去修 kernel 只会引入无谓分支。输入分布应覆盖三类：边界 shape（tile 边长不整除、单元素、零维退化）、对齐与非对齐指针、以及会触发循环尾部分支的余数输入；符号执行对每一类做有界展开，深度取典型 tile 大小即可，不必追求全尺寸。指标上区分三个量：证明覆盖率（被 unsat 覆盖的路径占符号路径的比例）、反例有效率（反例能在真实 GPU 上复现越界或错误输出的比例）、以及单题验证时延。三者要一起报，只报“验证通过率”会把大量标记为“未证明”的路径洗成通过。

$$\text{Proved}=\forall \mathbf{x}\in\mathcal{D}_{\text{pre}}:\ \text{Post}(\text{Kernel}(\mathbf{x}),\mathbf{x})\ \wedge\ \text{NoOOB}(\mathbf{x}),\quad \text{Cost}=|\text{BMC depth}|\times|\text{SMT queries}|$$

负载不对时的失效形态很具体。若把 128×128 大 tile 的二维索引直接丢进 BMC，展开深度与状态空间相乘，单题验证从秒级滑向分钟级到小时级，这个时延无法进入每轮 RL 循环——agent 每提一个候选就要等一次求解，采样吞吐被验证器卡死，RL 的有效样本率反而下降。若输入分布只取整除 shape，尾部分支永远不被符号化，验证报告显示“全部 proved”，但真实负载里非整除 shape 一跑就越界，这正是 fuzz 抽样漏掉、合约本应补上的那类错误，配方错了就等于把验证器的价值清零。若把浮点数值正确性也塞进 SMT，建模成本高且多数求解器对浮点理论支持有限，结果是验证时间暴涨却只证了索引与结构性质，数值错误仍要靠 fuzz 兜底；正确做法是明确分工——合约证结构，fuzz 证数值，报告里把“未证明”路径与 fuzz 结果合并成置信度，而不是让 agent 误以为整数索引 proved 就等于 kernel 正确。反例回灌同样有代价：反例是精确的 shape 与输入值，agent 修复无需再猜触发条件，但如果反例落在 \(\mathcal{D}_{\text{pre}}\) 之外的非法输入上，修复信号就是噪声，因此前置条件的收紧本身要作为配方的一部分被评审。

负载特征合约可证部分主要代价
一维连续 / 固定 stride 索引越界、索引仿射性求解快，深度随 tile 线性
二维 tile、非整除 shape尾部分支边界BMC 深度×查询数，分钟级起
