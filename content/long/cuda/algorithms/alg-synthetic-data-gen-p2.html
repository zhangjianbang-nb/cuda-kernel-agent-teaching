一 · 算子语法定义：把“算子”拆成可采样的参数空间

合成数据扩增的第一步不是生成，而是定义生成什么。这里的“算子语法”是一套受约束的参数化描述，它决定了一个合成实例能被程序化地实例化、能被参考实现覆盖、能被基线跑通。语法的最小单元是四类算子族：逐元素（elementwise）、归约（reduction）、矩阵乘（matmul）、卷积（conv），attention 作为矩阵乘与归约、softmax 的融合组合单独成族。每个族带一组参数：shape（各维尺寸）、dtype（fp32/fp16/bf16/int8 等）、stride（是否连续、是否转置视图）、边界条件（空张量、单元素维、非对齐长度、越界掩码）。

语法的输出是一个算子实例描述符，形如 (op_family, shape, dtype, stride, boundary_flag, fusion_pattern)。它是后续三步的唯一输入，也是整个流水线的契约：参考实现、基线时延、训练样本都由它派生。代价在这里第一次出现——语法空间越大，覆盖率越高，但每个实例都要付出一次参考实现编写与基线测量的成本。若把融合模式也纳入语法（如 matmul+bias+activation），实例数量按融合深度指数增长，采样预算必须做分层截断，否则生成器会把算力耗在重复的融合组合上。

具体机制上，语法用一组产生式规则约束合法性：逐元素族要求输出 shape 与输入一致；归约族要求指定归约轴且输出 shape 为去掉该轴后的形状；矩阵乘族要求 (M,K)×(K,N) 的 K 维对齐约束；卷积族要求通道数与 kernel size 的组合满足下采样整除关系。这些约束不是装饰，它们决定了参考实现能否被自动生成——不合法的实例在语法层就被拒绝，避免污染下游。

$$\mathcal{G}=\{g_\theta \mid \theta\in\Theta_{\text{op}}\times\Theta_{\text{shape}}\times\Theta_{\text{dtype}}\times\Theta_{\text{stride}}\}$$

这里 Θ 是各维参数域，g_θ 是参数化生成函数。一个具体例子：归约族取 shape=(4096, 8192)、dtype=bf16、stride=非连续（列主序视图）、boundary_flag=非对齐尾块，生成器据此产出一个“沿第二轴求和、输入为非连续视图”的实例。这个实例的参考实现必须处理 stride 跳读，基线时延也必须在该布局下测量，否则训练样本的标签与真实调用不符。语法层的代价是设计时延：每增加一个算子族或一种融合模式，都要同步扩展参考实现模板与基线适配层，这部分工程量不随采样规模摊薄。

二 · 程序化采样与参考实现生成：oracle 的构造与污染风险

采样阶段把语法实例化为具体张量与代码。输入是算子描述符，输出是三元组 (x_i, ref_i, T_ref,i) 中的前两项：输入张量与 fp64/PyTorch 参考输出。采样策略决定分布形状——按算子族分层、按 shape 量级分桶、按 dtype 覆盖，避免采样器退化为只产出热门配置。分层采样的直接代价是样本不均衡：冷门算子族（如带掩码的归约、非对齐卷积）生成慢、参考实现复杂，单位时间产出低，若不加权，训练集仍会被 GEMM/attention 主导，扩增的意义被稀释。

参考实现的生成有两条路径。其一是模板化：为每个算子族预写 PyTorch 参考函数，参数从描述符注入；其二是符号化：用 fp64 逐元素展开的朴素实现作为黄金参考，牺牲速度换正确性。两条路径的共同风险是 oracle 污染——参考实现若有 bug（如归约轴错、stride 处理错、dtype 提升规则错），错误标签会随合成数据进入训练集，模型学到的是错误行为而非正确行为。这正是变异测试审计要解决的问题，本片段只指出其位置：审计发生在参考实现生成之后、样本入库之前，是流水线中的一道闸门。

代价的量化维度是生成吞吐与显存：fp64 参考实现的内存占用约为 fp32 的两倍、bf16 的四倍，大 shape 实例（如 8192×8192 的 fp64 中间结果）会直接触发显存上限，采样器必须按可用显存做 shape 截断或分块计算。一个具体例子：对 shape=(1, 65536) 的 softmax 归约，fp64 参考实现需物化 65536 个双精度元素，若采样器同时并发生成数十个实例，显存峰值迅速堆高，生成吞吐被迫下降。工程判断是：参考实现按 dtype 分级——fp32 及以上走 fp64 黄金路径，低精度走“fp32 计算 + 误差界”路径，用误差界替代逐位比对。

$$\text{ref}_i=\text{Ref}(x_i;\ \text{op},\text{shape},\text{dtype},\text{stride}),\quad \|\text{ref}_i-\text{ref}^{\text{fp64}}_i\|_\infty\le \epsilon(\text{dtype})$$

这条误差界是低精度参考实现的正确性契约：ε 由 dtype 的尾数位宽决定，超出即判定参考实现失效，实例被丢弃而非入库。丢弃率本身是采样器的健康指标——丢弃率异常升高意味着语法层与参考实现层脱节。

三 · 基线时延测量：标签的构造与测量噪声

第三步对每个合成实例跑基线（PyTorch/cuBLAS/cuDNN），得到参考时延 T_ref,i，与输入、参考输出一起构成完整训练样本。输入是算子描述符与张量，输出是标量时延标签。这一步的机制核心是测量协议：warmup 次数、重复次数、同步方式、是否固定时钟频率、是否隔离其他负载。协议不稳定，标签就是噪声，而噪声标签会直接毒化 RL 的奖励信号——模型优化的是测量抖动而非真实性能。

代价在这里体现为墙钟时间与 GPU 占用：每个实例的基线测量需要数十到数百次迭代取中位数，单实例耗时从毫秒到秒级不等；若合成集规模为万级，基线测量本身就是一个可观的 GPU 预算项，且与训练任务争抢同一批卡。工程上的折中是分层测量：热门族与边界实例做全协议测量，长尾族做短协议测量并标注置信度，训练时按置信度加权。另一个代价是基线选择的偏差：PyTorch 的算子实现随版本变化，cuBLAS 的启发式选择随 shape 变化，同一描述符在不同环境下测出的 T_ref 可能差异显著，标签必须绑定测量环境元数据，否则跨环境复用会引入系统性偏差。

具体例子：对 shape=(4096, 4096)、dtype=fp16 的矩阵乘，cuBLAS 可能选择 split-K 策略，其时延对 K 维分块敏感；若测量协议未固定 workspace 大小与 stream 优先级，同一实例两次测量可给出不同标签。这类抖动在 RL 训练中表现为奖励方差，模型会在同一实例上反复试探而学不到稳定策略。因此基线测量必须与“防作弊合约校验”解耦——后者管的是模型输出是否真跑了 kernel，前者管的是标签本身是否可信，两者是流水线上不同的闸门。

$$T_{\text{ref},i}=\operatorname{median}\{t_1,\dots,t_n\},\quad \text{s.t.}\ \text{warmup}\ge w,\ \text{sync}=\text{True}$$

中位数而非均值的选择是为了抵抗调度抖动造成的长尾；w 的取值需覆盖 JIT 编译与缓存预热，否则首个迭代的编译开销会污染标签。这一步的输出不是单一数字，而是带元数据的标签记录：环境版本、协议参数、置信度。

四 · 混入训练集与难度分层：分布加权的机制

第四步把合成样本混入 SFT/RL 训练集，并按难度分层采样。输入是带标签的合成样本池与真实基准样本池，输出是训练批次流。机制核心是难度分层：难度不由 shape 大小单一决定，而由“基线时延相对 SOL 的差距”“参考实现的边界复杂度”“dtype 混合程度”共同刻画。分层的目的不是让训练变简单，而是让采样概率与模型当前能力匹配——过难的实例给出稀疏奖励，过易的实例不产生梯度信号。

代价是token 预算与采样偏差：每个训练样本在 SFT 中消耗的 token 数与其代码长度成正比，融合模式越深、边界条件越多，样本越长，单位 token 的信息密度反而可能下降。RL 中每个样本的多轮交互成本更高，若分层不当，大量 token 花在模型已掌握的实例上。工程判断是：合成样本与真实样本按固定比例混合，比例本身是一个超参，纯合成训练会在真实端到端场景失效，这一点在“问题与适用边界”中已界定，此处只强调混合比例需随训练阶段调整——早期偏合成以扩覆盖，后期偏真实以校准分布。

具体例子：一个带掩码的 attention 融合实例，其代码长度是纯 GEMM 实例的数倍，若按均匀采样，token 预算会被长样本吞噬而短样本覆盖不足。分层采样器应对每个难度桶设 token 配额上限，桶内按实例数均分，保证长尾算子族不被长样本挤出批次。另一个机制是合成-真实分布差距监控：在训练过程中周期性在真实基准上评估，若真实性能不升反降，说明合成分布偏移过大，需回调混合比例。这一步的代价是评估本身的时延——真实基准评估不能太频繁，否则挤占训练算力。

$$p_{\text{sample}}(i)\propto \frac{w_{\text{diff}(i)}}{1+\text{tok}(i)/\bar{\text{tok}}},\quad \sum_i p_{\text{sample}}(i)=1$$

权重 w 按难度桶设定，分母对长样本做惩罚，避免 token 预算被少数实例垄断。这个采样分布与开头的训练集公式共同定义了扩增后的数据分布：D_train = D_real ∪ {合成三元组}，其中合成部分的采样概率由上式调制。

五 · 真实基准评估与分布差距回灌：闭环的最后一步

第五步在真实基准（KernelBench 系与真实框架算子）上评估泛化，监控合成-真实分布差距。输入是训练后的模型与真实基准任务集，输出是跨算子泛化指标与差距诊断。机制核心是差距归因：把真实基准上的失败样本按算子族、shape 量级、dtype 归类，与合成集的覆盖情况对照，找出“合成集有覆盖但模型仍失败”与“合成集未覆盖”两类缺口。前者指向训练信号问题（难度分层或奖励设计），后者指向语法层覆盖不足，需回到第一步扩展参数域。

代价是评估时延与回灌延迟：真实基准评估需要跑完整 kernel 并测量时延，单轮评估的墙钟时间远高于合成样本的生成时间；若评估频率过高，训练吞吐被拖垮，若过低，分布差距发现滞后，错误方向上的训练持续消耗算力。工程折中是按训练步数设评估窗口，窗口内的合成采样比例保持稳定，窗口结束时做一次真实评估并据结果调整下一窗口的混合比例。这与“NCU 指标回灌”是不同层面的闭环：后者回灌的是单 kernel 的微观指标，前者回灌的是分布层面的宏观信号。

具体例子：真实框架调用中出现“非连续输入上的 layer norm + 残差融合”，合成语法若只覆盖连续布局的逐元素与归约，模型在该融合上性能骤降；差距归因会把该失败标记为“语法覆盖缺口”，触发语法层增加 stride 参数域的融合组合。另一个例子是 dtype 混合：真实调用中 fp16 输入配 fp32 累加是常见模式，若合成集只生成单一 dtype，模型在混合精度路径上的寄存器压力估计失准，表现为时延标签与实测偏离。这一步的输出是下一轮扩增的输入——语法扩展清单与采样权重调整建议。

$$\Delta_{\text{gap}}=\mathbb{E}_{x\sim p_{\text{real}}}\big[\text{speedup}_{\text{model}}(x)\big]-\mathbb{E}_{x\sim p_{\text{synth}}}\big[\text{speedup}_{\text{model}}(x)\big]$$

差距 Δ 为负且显著时，说明合成分布高估了模型能力，需收紧合成采样或增加真实样本权重；为正则说明合成集偏保守，可扩大语法域。这个量不是一次性指标，而是每个评估窗口的回灌信号，驱动下一轮采样的参数调整。

六 · 单步代价的账本：流水线预算如何分配

把五步的代价放在一张账本上，才能判断扩增流水线的瓶颈在哪。语法定义是一次性设计成本，随算子族与融合模式数量线性增长；采样与参考实现生成的代价是显存与吞吐，受 fp64 黄金路径的显存上限约束；基线测量的代价是 GPU 墙钟时间，与实例数成正比且与训练争抢算力；混入训练的代价是 token 预算，受样本长度与分层配额调制；真实评估的代价是低频但高延迟的墙钟开销。五者中，基线测量与参考实现生成是可变成本的主体，语法定义是固定成本，真实评估是周期性固定开销。

步骤输入输出主要代价
语法定义算子族与参数域描述符产生式设计时延，随融合深度增长
采样与参考实现描述符(x, ref) 二元组显存峰值、生成吞吐、oracle 污染风险
基线测量描述符与张量T_ref 标签GPU 墙钟、测量噪声、环境绑定
混入训练样本池训练批次流token 预算、采样偏差
真实评估模型与真实基准差距诊断评估时延、回灌滞后

账本给出的工程判断是：扩增规模的上限不由采样器决定，而由基线测量的 GPU 预算与参考实现的显存上限共同决定。若把预算全投在采样数量上，基线测量会成为瓶颈，标签质量下降；若把预算全投在参考实现的正确性上，样本吞吐不足，训练集覆盖上不去。合理的分配是按算子族分层设预算：热门族少量高质量样本，长尾族大量中等质量样本，用置信度加权弥补标签噪声。一个具体机制是给每个样本打“可信度分”，由参考实现的误差界、基线测量的协议完整度、变异测试审计结果共同决定，训练时按可信度加权损失，低可信度样本不参与奖励计算。

最后落在具体机制上：流水线的每一步都产出带元数据的记录，描述符、参考实现版本、测量协议、可信度分、评估窗口编号，这些元数据是回灌信号的载体。没有元数据，差距归因无法定位到具体步骤，扩增就退化为盲目堆量；有了元数据，每一步的代价与产出都可追溯，语法扩展与采样权重调整才有依据。合成算子数据扩增的可信度不来自样本数量，而来自这条可追溯的账本。
