一 · 时延项的推导：从单次 launch 到可比较的 ΔT

trace 里最容易被误读的就是 T。它不是一个标量，而是一条按 launch 序号排列的时间戳序列。设第 i 次 launch 的起止时间戳为 t_s(i)、t_e(i)，流 ID 为 s(i)，则单次时延 d(i)=t_e(i)-t_s(i)。但 agent 关心的不是某一次，而是同一 kernel 在给定 shape/dtype 下的稳态时延。于是定义版本 t 的聚合时延为对同构 launch 集合 I_t 的稳健统计量：

$$T^{(t)}=\operatorname{median}_{i\in I_t}\big(d(i)\big),\qquad \sigma^{(t)}=\operatorname{MAD}_{i\in I_t}\big(d(i)\big)$$

取中位数而非均值，是因为 CUPTI 回调路径上偶发的调度抖动会污染尾部；MAD（中位绝对偏差）比标准差更能抵抗离群点。关键的一步推导在这里：keep 判据写的是 ΔT<0，但 ΔT 是两个带噪统计量之差，其噪声量级约为 sqrt(σ²_t+σ²_{t-1})/sqrt(n)（n 为每版采样次数）。若不设门限，任何小于该量级的改善都可能是噪声。因此工程上把判据细化为带死区的形式：

$$\text{Keep}=\mathbb{1}\Big[\big(T^{(t)}-T^{(t-1)}\big)<-\kappa\cdot\frac{\sqrt{(\sigma^{(t)})^2+(\sigma^{(t-1)})^2}}{\sqrt{n}}\ \wedge\ \text{Correct}\Big]$$

κ 取 1 到 2 之间，本质是把“改善必须超过噪声带宽”写进决策。代价是：死区会吞掉真实的小幅改善，尤其在 kernel 本身已接近 roofline 时，剩余优化空间本就落在噪声量级内，trace 无法分辨。具体例子：一个 reduction kernel 在 n=64 次采样下中位时延从 41.2 µs 降到 40.9 µs，MAD 均为 0.6 µs，则噪声带宽约 0.6·sqrt(2)/8≈0.106 µs，κ=1 时 0.3 µs 的改善勉强过线；若 κ=2 则被判为不显著而回滚——这是可接受的保守，因为回滚成本远低于把噪声当收益固化进版本链。

二 · SASS 差分的代数：⊕ 不是集合对称差，而是对齐后的指令级 diff

公式里的 SASS^{(t)}⊕SASS^{(t-1)} 常被简化为“哈希是否相等”，但哈希相等只能证明没变，证明不了“变了哪里”。真正的 ⊕ 需要先把两版 cubin 反汇编成指令序列，做基本块级对齐，再在块内做指令级最长公共子序列。设版本 t 的指令序列为 A=[a_1..a_m]，前一版为 B=[b_1..b_l]，则 diff 结果为三元组 (added, removed, shifted)，其中 shifted 指操作数或寄存器分配变化但 opcode 不变的指令。这一步的推导要点是：寄存器重编号会让朴素 diff 产生大量伪“删除+新增”，必须先做寄存器归一化（按 def-use 链重命名）再比对，否则 diff 的信噪比极低。

伪代码落到可实现层面，核心循环如下（文字描述，不写代码块）：对每个基本块，先比较指令条数与 opcode 多重集；若不等，标记结构性变化；若相等，进入操作数比对，把物理寄存器映射到归一化编号后逐位比较，仅当 opcode 或归一化操作数变化才计入 removed/added。产出是一个按基本块聚合的变更向量，可直接作为 trace 的一列。

代价在编译时间与存储：反汇编加对齐的耗时随 kernel 规模增长，一个大 kernel 的 cubin 可达数百 KB 指令，单次 diff 在工具链上要几十到上百毫秒；trace 若每轮都存完整 SASS 文本，文件体积按轮次线性膨胀。工程折中是只存归一化后的指令哈希序列（每指令 8 字节），完整反汇编按需重放。具体例子：agent 把 shared memory 的 bank 冲突通过 padding 消除，SASS 上表现为若干 LDS 指令的地址计算变化而 opcode 不变——若只比哈希，会看到“变了”但说不出所以然；对齐 diff 则精确指出是 3 条地址指令的 shifted，与 NCU 上 shared 冲突计数器下降形成互证。

三 · metrics 差分的采样语义：低频快照如何与高频 launch 对齐

metrics^{(t)}-metrics^{(t-1)} 看似简单，实则受采样频率约束。NCU 采集是低频的（每次采集要暂停/重放 kernel，开销远大于 CUPTI 回调），因此 trace 中 metrics 只覆盖部分 launch。设版本 t 共 N_t 次 launch，其中被 NCU 采样的子集为 M_t，|M_t|≪N_t。推导的关键一步是把 metrics 视为对 M_t 的条件期望，而非对全体 launch 的估计：

$$\Delta m^{(t)}=\frac{1}{|M_t|}\sum_{j\in M_t}m_j-\frac{1}{|M_{t-1}|}\sum_{j\in M_{t-1}}m_j,\qquad \text{Var}(\Delta m)\approx\frac{\sigma_m^2}{|M_t|}+\frac{\sigma_m^2}{|M_{t-1}|}$$

由于 |M_t| 小，Δm 的方差显著大于 ΔT，这意味着 metrics 更适合做“方向性证据”而非“判决证据”。工程判断：keep/revert 的硬判据只用 ΔT 与 Correct，metrics 用于解释与归因，以及在 ΔT 落在死区内时提供第二意见。具体例子：某 kernel 的 ΔT 为 −0.05 µs（死区内），但 NCU 快照显示 sm__throughput 上升、dram__bytes 下降，说明改动确实减少了访存但被其他瓶颈掩盖；此时记录 metrics delta 作为“潜在收益”标注，留待后续与其他改动叠加时复核，而不是直接 keep。

代价是采样本身扭曲被测对象：NCU 重放会改变 cache 状态与时钟行为，采样到的 metrics 不能与 trace 中同时延混用。因此 trace 文件必须给每条 metrics 记录打上 replay=true 标记，评分管线在计算 T 时剔除这些 launch。

四 · 正确性项 Correct 的布尔化：从 oracle 到可组合的判定

公式里 Correct 是一个布尔量，但它的来源是浮点比对，天然带容差。设参考输出为 y*，被测输出为 y，逐元素判定为 |y_i-y*_i|≤atol+rtol·|y*_i|，全体元素通过才算该 launch 正确。推导的关键一步是把“逐 launch 正确”聚合为“版本正确”：

$$\text{Correct}^{(t)}=\bigwedge_{i\in I_t}\text{Pass}(y_i,y^*_i)\ \wedge\ \text{ShapeOK}\ \wedge\ \text{DtypeOK}$$

取合取而非多数投票，是因为 kernel 的正确性是全称命题：一个 shape 错了就是错了，不能用其他 shape 的正确率抵消。这与评分公式中 Correct 作为 keep 的必要条件一致——它是一票否决项。代价在于：严格合取会让偶发的非确定性失败（如 atomic 顺序导致的末位差异）直接触发回滚，误杀率上升。工程折中是引入重试语义：对失败 launch 重跑至多 r 次，仅当全部重试均失败才判 Correct=false，并在 trace 中记录重试次数作为非确定性信号。

具体例子：一个 softmax kernel 在 dtype=fp16 下，某个 batch 的极值元素因归约顺序不同产生 1 ulp 差异，恰好越过 rtol。若不重试，agent 会把一次正确的优化回滚；若重试两次均通过，则判定为数值非确定性而非逻辑错误，keep 并标注该 shape 的容差敏感。这里 oracle 的构造与变异测试审计属于其他片段的主题，本片段只强调：Correct 进入公式前必须完成布尔化与重试语义的定义，否则 keep/revert 的因果链在第一步就断了。

五 · trace 文件增长与压缩：线性膨胀下的解析成本模型

每轮 trace 记录包含 launch 参数、SASS 哈希序列、时间戳、可选 metrics 快照。设单条记录平均 b 字节，版本 t 有 N_t 次 launch，则总存储为 Σ_t N_t·b，随轮次线性增长。解析成本同样线性：每次 keep/revert 决策要读取当前版与前一版的全部记录做对齐。推导的关键一步是把“对齐”建模为按 (kernel_id, shape, dtype, stream) 四元组的分组连接，其代价为 O(N_t+N_{t-1}) 的哈希连接，而非朴素的两两比较。

压缩策略有三层，各有代价：其一，对时间戳做差分编码，只存 Δd，压缩率取决于抖动幅度；其二，对 SASS 只存归一化哈希序列，完整反汇编按需重放，牺牲的是离线审计时的可读性；其三，对 metrics 做低频采样并只保留变化超过阈值的计数器，牺牲的是归因的完整性。具体例子：一个训练循环里 agent 跑了 200 轮修改，每轮 50 次 launch，若每条记录 2 KB，则 trace 总量约 20 MB——尚可接受；但若把完整 SASS 文本（每版数十 KB）也塞进去，则膨胀到数百 MB，解析一次决策要秒级。工程判断是：trace 的存储预算应与评分管线的时延预算挂钩，单次决策的解析时间必须远小于被测 kernel 的编译时间，否则 trace 本身成为瓶颈。

六 · keep/revert 的组合判据与反例记录

把四项合起来，keep 是一个合取式：时延显著改善、正确、且 delta 可归因。但工程上还要处理“改善但不可归因”的情形——例如 ΔT<0 显著，但 SASS diff 为空、metrics 无变化，说明改善来自测量环境漂移而非代码。此时应判为“不可信改善”，回滚并记录环境快照。推导的关键一步是把归因写成条件概率式的启发：

$$\text{Attributable}=\mathbb{1}\big[\|\text{SASS}^{(t)}\oplus\text{SASS}^{(t-1)}\|>0\ \vee\ \|\Delta m^{(t)}\|>\tau_m\big]$$

即 SASS 有实质变更，或 metrics 变化超过阈值 τ_m，二者至少其一。keep 最终为 ΔT 显著 ∧ Correct ∧ Attributable。代价是：Attributable 会拒绝那些“编译器自动优化生效但源码未变”的改善——例如换了一个编译 flag 导致 SASS 变化，这其实是合法的，但 diff 非空所以能通过；真正被拒的是纯环境漂移，这正是我们想要的。

反例记录是 revert 的副产品：每次回滚要把 Δ_trace 三元组、失败原因（时延退化 / 正确性失败 / 不可归因）、以及触发判据的具体数值写入反例库，供后续轮次的 prompt 或搜索策略引用。具体例子：agent 尝试把 __syncthreads() 换成 warp 级同步，SASS 上 BAR.SYNC 消失、WARPSYNC 出现，时延下降但某个跨 warp 依赖的 shape 出现错误——Correct=false 触发回滚，反例记录下“该 shape 下 warp 级同步不充分”，下一轮 agent 若再提同类改动，检索到反例即可跳过。这条反例的存储成本极低（一条记录几百字节），但它把一次昂贵的错误试验转化为后续搜索的先验，是 trace 体系里性价比最高的部分。

插桩 trace 的三重失效边界：观测失真、对齐错位与存储膨胀

把 $$\Delta_{\text{trace}}^{(t)}=\left(T^{(t)}-T^{(t-1)},\ \text{SASS}^{(t)}\oplus\text{SASS}^{(t-1)},\ \text{metrics}^{(t)}-\text{metrics}^{(t-1)}\right),\quad \text{Keep}=\mathbb{1}\left[\Delta T<0\wedge\text{Correct}\right]$$ 当成评分器之前，必须先承认它是一个带偏观测器：$$T^{(t)}$$ 是在 CUPTI 回调或 LD_PRELOAD 拦截路径下测得的墙钟，其中包含回调进入/退出的固定开销与流同步抖动，因此 trace 模式下的时延只能用于相对比较，不能直接喂给 KernelBench 式的绝对评分。工程上应把 trace 时延记为 $$\tilde T^{(t)}$$，与干净跑（无插桩）的 $$T^{(t)}_{\text{clean}}$$ 分离，keep/revert 判定用 $$\Delta\tilde T$$ 的符号，最终上报用干净跑的绝对值；否则一次“优化”只要把 launch 次数从 3 次降到 2 次，回调开销的摊薄就会伪造出时延改善。具体例子：一个融合 kernel 把两次小 launch 合并为一次，回调总开销从两次降到一次，$$\tilde T$$ 下降而真实计算时间未变，若直接用 $$\tilde T$$ 做 keep，就会把一个中性改动误判为优化并写进反例库。

第二个边界是版本对齐：$$\text{SASS}^{(t)}\oplus\text{SASS}^{(t-1)}$$ 的异或只在两次编译产物的指令序列可比时才有意义。编译器版本、$$-\text{use\_fast\_math}$$、寄存器上限、甚至 $$\text{grid}$$ 常量折叠都会改变 SASS，使异或结果非空却与源码改动无关；反过来，源码改了但 SASS 恰好等价（例如换写法但生成同一指令流），异或为空却掩盖了真实修改。对齐必须锚定在“代码版本”而非“SASS 差异”上：用 git diff 或 prompt 轮次 ID 作为主键，SASS 哈希只作辅助校验。伪代码落到可实现层面：$$\text{trace}[i]=\{\text{ver},\ \text{cubin\_hash},\ \text{launch}(grid,block,shape,dtype),\ t_{\text{start}},t_{\text{end}},\ \text{stream\_id},\ \text{ncu\_snap}\}$$，按 $$\text{ver}$$ 分组后对相邻组求 delta；若 $$\text{cubin\_hash}$$ 相同而 $$\text{ver}$$ 不同，标记为“等价重编译”，delta 归零而不触发 keep。代价是每轮多一次 cubin 哈希计算与一次 trace 落盘，编译时间与 I/O 各增一小段，换来的是因果链不被编译器噪声污染。

第三个边界是存储与解析成本随轮次线性增长：每轮 trace 含 launch 参数、时间戳、流 ID 与可选 ncu 快照，ncu 快照本身是低频采样但单条记录体积远大于时延记录。若不做采样与压缩，trace 文件在几十轮后就会让解析脚本的读取时间超过单次 kernel 的编译时间，审计反而变慢。可行做法是分层：时延与哈希每轮全量保留（体积小），ncu 计数器按固定间隔抽样（例如每 N 轮一次或仅在 $$\Delta\tilde T<0$$ 的候选轮触发），并对时间戳做差分编码。表格对比三种记录策略的系统代价：

策略时延开销存储增长失效条件
全量 CUPTI 回调5–20%线性，含全部 launch高频小 kernel 下回调占比过高，$$\Delta\tilde T$$ 失真
仅哈希+时间戳低线性但小无法解释指标变化的微观原因
哈希+抽样 ncu中亚线性抽样轮错过关键退化，需配合候选轮触发

还有一个容易被忽略的失效条件：$$\text{Keep}=\mathbb{1}[\Delta T<0\wedge\text{Correct}]$$ 中的 $$\text{Correct}$$ 若只来自单次随机输入，trace 的 keep 决策就把正确性 oracle 的方差引入了优化循环。正确做法是把正确性判定与 trace delta 解耦：trace 只负责“哪次修改动了哪个指标”，正确性由独立的差分测试或形式化检查给出布尔值，两者在决策层合取。这样即便 trace 因回调开销把一次真实优化误判为退化，也不会连带把正确性结论污染；反过来，正确性失败时 trace 仍保留完整的 SASS 与 launch 参数，可直接作为反例样本回灌给 agent 的下一轮 prompt。工程判断落在采样粒度上：trace 的价值在于可回溯，不在于全量，把 ncu 快照压到候选轮、把时延记录压到差分编码，才能让这条证据链在几十轮优化中保持可读、可审计、可复现。

插桩 trace 的失效边界：何时 delta 不可信、何时开销吃掉收益

这套 trace 的核心假设是：同一 kernel 在两次 launch 之间，只有被修改的代码维度发生变化，其余条件（shape、dtype、stream、clock）保持一致。一旦该假设被打破，$\Delta_{\text{trace}}^{(t)}$ 中的时延差就混入了非代码因素，Keep 判据 $\mathbb{1}[\Delta T<0\wedge\text{Correct}]$ 会把测量噪声误判为优化收益。典型失效场景有三类：一是 shape 或 dtype 在轮次间漂移，导致 grid/block 配置被动变化，此时应把 launch 参数作为 trace 的联合主键，delta 只在同主键分组内比较；二是 GPU clock 与功耗状态波动，短 kernel 的时延差可能小于 clock 抖动幅度，需以多次重复的中位数或最小值作为 $T^{(t)}$，并对 $\Delta T$ 设一个与 kernel 时长成比例的死区阈值；三是 CUPTI 回调本身引入的 5–20% 时延开销，在 trace 模式下测得的 $T^{(t)}$ 系统性偏高且偏高幅度随回调密度变化，因此 trace 时延只能用于相对比较，绝对评分必须走无插桩的独立测量通道。

另一个边界是 SASS 哈希的粒度。$\text{SASS}^{(t)}\oplus\text{SASS}^{(t-1)}$ 用整段二进制异或只能回答“变了没有”，无法回答“变了哪条指令、影响了哪个计数器”。当编译器因无关的源码改动（如注释、变量重命名）重排指令或改变寄存器分配时，哈希会翻转而实际语义未变，此时 delta 非零但指标不变，agent 容易把编译噪声当成优化信号。可行的折中是按基本块或按指令类别做分段哈希，并只在 metrics 出现显著变化时才触发 SASS 级 diff，把昂贵的反汇编对齐留给少数可疑轮次。代价是分段哈希使 trace 写入量上升，需配合采样与压缩，否则 trace 文件随轮次线性增长会拖垮解析侧。

失效条件delta 表现工程处置

clock 抖动$\Delta T$ 符号随机翻转重复采样取最小值 + 死区阈值

伪代码层面，判据应写成带守卫的形式而非裸比较：if same_launch_key(t,t-1) and repeats_enough(t) and abs(dT) > deadzone(T): keep = (dT < 0 and correct)，否则标记该轮 delta 为“不可判定”并保留原版本，把不可判定轮次单独计数作为 trace 质量的元指标。这一守卫的直接代价是有效决策轮次减少——噪声大的短 kernel 可能连续多轮被判为不可判定，agent 的搜索效率下降；但相比误回滚一个真实优化，或误保留一个退化版本，这个代价是可控的。当不可判定比例持续偏高时，说明该 kernel 的时长已接近测量分辨率下限，此时应转向基于计数器（如指令数、访存事务数）的代理指标做 keep/revert，而非继续依赖墙钟时延。
