一 · 负载画像：什么模型/算子/shape 才配得上布局搜索

CuTe 布局搜索的收益不是均匀分布的。它只在“布局自由度真正影响性能”的负载上成立：计算密度高、tensor core 是主路径、且 tile 形状与 swizzle 组合空间足够大。具体判据是三条同时满足——算子主体是 GEMM 或 attention 的 QK^T/PV 矩阵乘、dtype 落在 fp16/bf16/tf32 的 MMA 路径上、目标架构有明确的 MMA atom 族（sm80 的 mma.sync 与 sm90 的 wgmma 语义差异极大，atom 枚举空间完全不同）。反例同样清晰：elementwise、reduction、layernorm 这类带宽受限算子，布局只影响合并访存与向量化宽度，搜索空间退化成几个固定选项，CuTe 模板实例化的编译开销直接吃掉全部收益。conv 处于中间地带，只有 implicit GEMM 形式、且 channel 对齐到 MMA atom 的 K 维时才有搜索价值。

shape 维度上要区分“结构 shape”与“数值 shape”。结构 shape 决定 atom 枚举的合法性：M/N 是否能被 tile 整除、K 是否是 atom K 的整数倍、batch/head 维是否进入 grid。数值 shape 只影响 occupancy 与 wave 量化。布局搜索的负载配方应固定结构 shape 的一小组代表值（覆盖整除、非整除、极端窄高/宽扁三种形态），而把数值 shape 交给隐藏分布抽样去压力测试——后者是别的片段的主题，此处只强调：布局搜索的评测集必须显式标注哪些 shape 是“布局敏感”的，否则搜索会在无关维度上空转。

硬件侧的关键判据是共享内存容量与 swizzle 模式的耦合。sm90 的 228KB smem 上限允许更深的 pipeline stage，stage 数本身是搜索参数，但它与 swizzle 的 bank 分布强耦合：stage 增加会改变 smem layout 的 stride，进而改变 bank conflict 图谱。因此负载配方必须把“目标架构 + smem 预算 + stage 上界”作为一个三元组固定下来，否则同一份 CuTe 代码在不同预算下最优布局不同，评测结果不可比。代价是显存的静态占用：stage 越多，每 CTA 的 smem 驻留越大，occupancy 下降，这条 trade-off 必须在配方里显式记录，而不是让搜索隐式承担。

一个具体例子：bf16 GEMM，M=N=4096、K=4096，sm90，smem 预算 200KB。合法 atom 组合里 wgmma 的 N 维候选是 8/16/32/64/128/256，tile shape 候选从 64×64 到 128×256，stage 候选 2–5，swizzle 候选 32B/64B/128B。这个组合空间是几千量级，恰好落在“可枚举但不可暴力编译”的区间——这正是布局搜索的甜点区。若把 K 换成 64（窄 K），atom K 维只剩一个合法值，搜索退化为 tile shape 的单维扫描，收益骤降。

二 · 基线选择：锚点错了，SOL 比值全是噪声

基线不是“随便找个能跑的版本”。在 CuTe 布局搜索的评测里，基线承担两个不同职能：性能锚点与语义锚点。性能锚点必须是同一硬件、同一 dtype、同一结构 shape 下的强基线——通常是 CUTLASS 官方 profiler 的对应配置，或手写 CuTe 的已知良好实现。语义锚点则是 fp64 参考实现，只用于正确性判定，不参与性能比值。把两者混为一谈是配方设计中最常见的错误：用朴素 triple-loop 当性能基线会让 SOL 比值虚高，用 fp64 参考当性能基线则让比值恒小于 1、失去区分度。

基线锚定的具体机制是“同编译单元、同 launch 配置”。CuTe 的性能对 launch bound、cluster 维度、grid swizzle 极其敏感，基线若用不同 launch 配置，比较的是两套调度而非两套布局。配方要求基线与生成 kernel 共享同一份 launch 参数生成逻辑，只允许 layout/tile/stage 三个维度不同。这样 SOL 比值的分子分母才落在同一坐标系里：

$$\text{SOL}=\max\left(\frac{F}{F_{\text{peak}}},\frac{B}{B_{\text{peak}}}\right),\quad \text{score}=\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}\cdot\mathbb{1}[\text{correct}]$$

公式里 F 与 B 分别取自 NCU 的 sm__pipe_tensor_op_hmma_cycles_active 折算的 FLOPs 与 dram__bytes 折算的带宽，F_peak/B_peak 用目标架构的规格值。注意 score 的分母是 SOL_ref 而非 1，这意味着基线本身若不达峰值，score 会系统性偏高——这是可接受的，因为比值衡量的是“相对改进”，但配方必须同时报告 SOL_ref 的绝对值，否则无法判断基线是否已经接近 roofline、搜索空间是否还有余量。

代价体现在编译时间上：强基线通常也是 CuTe 模板实例化产物，与生成 kernel 共享头文件但实例化不同参数，每轮评测要编译两份。若基线用 CUTLASS profiler 二进制则省去编译，但 launch 配置对齐就退化为运行时参数匹配，容易漏掉 cluster 维度这类编译期常量。工程判断是：基线编译一次、缓存复用，生成侧每轮编译，把编译预算集中花在搜索上。一个具体例子：sm90 bf16 4096³ GEMM，基线取 CUTLASS 3.x 的 128×128×64 stage-3 配置，其 SOL_ref 已接近 tensor core 峰值；此时 score 的天花板很低，搜索的价值在于把 bank conflict 与 stage 调优的残差榨出来，而不是追求数量级提升——配方必须让评测者预期到这个量级。

三 · 输入分布：数值域决定 oracle 强度，也决定性能可复现性

输入分布的设计要同时服务正确性与性能两个目标，而这两者对分布的要求并不一致。正确性 oracle 需要能暴露数值问题的分布：fp16 累加溢出、bf16 尾数截断、tf32 的 10 位尾数在 K 维累加中的误差放大。性能侧则需要能避免非规格化数（denormal）拖慢流水、避免全零输入让分支预测与压缩路径失真。配方做法是分层：正确性层用宽动态范围随机（含大指数差、含符号交替、含接近 fp16 上限的值），性能层用零均值单位方差随机，两层分开跑、分开记账。

具体机制上，输入生成要绑定 dtype 的语义边界。fp16 的上限是 65504，K 维累加若用 fp16 累加器（而非 fp32）会在 K 较大时溢出，这个溢出只在特定分布下触发——因此正确性层的分布必须包含“单元素接近上限、K 维部分和跨过上限”的构造样本，而不是纯随机撞运气。bf16 的问题在尾数：8 位尾数意味着两个相差 2^-8 相对量级的数相加会丢低位，分布要包含这种量级差。tf32 的误差在 K 维累加中随 sqrt(K) 增长，分布要覆盖 K 的多个量级。

性能可复现性的代价是显存与生成时间。宽动态范围分布若用 fp64 生成再降精度，生成开销与显存占用都是单位方差随机的数倍；配方通常把正确性样本集控制在几十个固定种子，性能样本集用流式生成避免全量驻留。另一个代价是 token：若输入分布描述要进 LLM 的 prompt（让模型知道数值域），描述本身占 token，且过于详细的分布描述会挤占布局参数的推理空间。工程判断是把分布规格做成结构化短码（dtype、范围、特殊构造标记），而非自然语言长描述。

一个具体例子：attention 的 QK^T 在 fp16 下，softmax 前的 logits 若分布方差过大，exp 会溢出；正确性层必须包含“行最大值远大于其余元素”的构造，检验 kernel 是否做了 max-subtraction。性能层则用标准正态，因为真实推理负载的 logits 分布接近此形态。两层用同一 kernel、不同输入，score 只在性能层计算，正确性层只输出布尔门。

四 · 指标计算：从 NCU 计数器到可比较的标量

指标计算的第一个陷阱是“计数器语义与算子语义的错配”。NCU 给的 tensor core 活跃周期数不等于有效 FLOPs：wgmma 的某些指令在 K 维不足时会有空转周期，活跃周期数会把空转计入。配方要求用指令级计数器（smsp__inst_executed_pipe_tensor 折算的实际 MMA 指令数 × 每指令 FLOPs）而非周期数来算 F，周期数只用于诊断 stall。同理，DRAM 吞吐要用 dram__bytes_read/write 的实际字节数除以 kernel 时长，而非用理论带宽乘占用率。

第二个陷阱是测量时长的选择。CuTe kernel 的首次 launch 含 JIT/模块加载开销，稳态性能要取多次 launch 的中位数或最小值。配方固定“预热 N 次、采样 M 次、取最小值”的流程，N 与 M 由 kernel 时长决定而非拍脑袋：短 kernel 需要更多采样抵消计时噪声，长 kernel 采样少但单次成本高。代价是评测墙钟时间，尤其当搜索每轮都要 profile 时，profile 开销可能超过编译开销——这是布局搜索预算模型里必须计入的一项。

第三个陷阱是 SOL 的 max 语义。公式取 F/F_peak 与 B/B_peak 的较大者，意味着 kernel 只要在一个维度接近峰值，SOL 就高，另一个维度的低效被掩盖。这对布局搜索是危险的：bank conflict 严重的 kernel 可能因计算密集而 SOL 仍高，搜索会误判布局已优。配方要求同时记录两个分量与它们的比值，当 F/F_peak 与 B/B_peak 差距小于某阈值时标记为“平衡区”，此时布局调优的边际收益最大；差距大时标记为“单侧受限”，搜索应转向受限侧对应的参数（带宽受限查 swizzle 与向量化，计算受限查 atom 与 stage）。

一个具体例子：sm80 fp16 GEMM，NCU 显示 tensor core 利用率 62%、DRAM 吞吐 41%。SOL 取 0.62，score 看似不错，但两个分量差距 21 个百分点，落在平衡区边缘——配方会提示搜索继续，重点查 smem bank conflict（swizzle 候选）与 stage 数。若利用率 85%、吞吐 30%，则判定计算受限已接近饱和，搜索应停止 tile 扩张、转向减少冗余搬运。这个判定逻辑本身就是指标计算的一部分，而非事后分析。

五 · 负载不对时会发生什么：三类失效模式

第一类失效是“搜索空间退化”。当结构 shape 使 atom 枚举只剩一个合法组合（窄 K、非对齐 N、dtype 不在 MMA 路径），布局搜索退化为单点验证，LLM 的生成能力无处施展，而 CuTe 模板实例化的编译开销照付。表现是每轮搜索编译时间恒定、score 方差极小、keep-revert 从不触发 revert。配方检测信号是“合法组合数低于阈值”时直接跳过搜索、回退到固定模板。代价是评测吞吐：这类负载若混入评测集，会拉长整体墙钟而不贡献区分度。

第二类失效是“基线失配导致的伪改进”。基线用了不同 launch 配置或不同 stage 数，生成 kernel 的 score 提升实际来自调度差异而非布局。表现是 score 提升但 NCU 的 bank conflict 计数未降、tensor core 利用率未升。配方要求每次 score 提升都附带至少一个 NCU 计数器的同向变化作为佐证，否则标记为可疑。代价是 profile 次数翻倍，但这是防伪改进的必要开销。一个具体例子：生成 kernel 把 stage 从 3 提到 4，score 升了，但基线是 stage-3——这个提升是 pipeline 深度带来的，与 swizzle 无关，若配方不记录 stage 差异，就会把功劳记在布局搜索头上。

第三类失效是“正确性门过松导致的语义错布局”。CuTe 的类型系统保证 layout 合法，但不保证语义正确：一个编译通过的 tiled_copy 可能把 A 的 tile 映射到了错误的 smem 偏移，在特定 shape 下恰好数值正确（如对称矩阵、全一输入），在隐藏分布下崩。表现是正确性层全过、性能层 score 高，但换一批输入就错。配方要求正确性层必须包含非对称、非均匀、含特殊值的构造样本，且 oracle 用 fp64 参考而非同精度对比——后者会把系统性误差当成正确。代价是 oracle 的 fp64 计算本身耗时，对 attention 这类 O(N²) 算子尤为明显，配方通常用小 shape 的正确性样本控制这个开销。

三类失效的共同根源是负载配方与搜索目标没有对齐：搜索优化的是 score，而 score 只在配方定义的坐标系里有意义。配方不对时，搜索会收敛到一个在该坐标系里高分、在真实负载上无收益甚至错误的 kernel。工程判断是：负载配方的设计成本应计入搜索总预算，且配方的变更必须触发搜索结果的重新验证，不能沿用旧 score。

六 · 配方的工程化：把负载规格变成可执行合约

负载配方最终要落成机器可读的合约，而不是文档里的一段描述。合约的最小字段集是：算子类型、结构 shape 列表、dtype、目标架构、smem 预算、stage 上界、基线标识（含 launch 配置哈希）、输入分布短码、指标计算口径（F 与 B 的计数器来源）、正确性样本集标识。每个字段都要能被评测流水线直接消费，而不是靠人解读。这样做的代价是前期建模成本：每个算子族要写一份合约模板，且模板变更要版本化，否则历史 score 不可比。

合约的可执行性体现在两个环节。其一是搜索前的合法性预检：合约里的结构 shape 与 atom 枚举逻辑要能算出合法组合数，低于阈值直接拒绝进入搜索，避免第一类失效。其二是评测后的归因检查：score 提升必须附带合约指定的 NCU 计数器同向变化，否则拒绝计入 keep。这两个环节把“负载不对”从运行时的隐性失效变成搜索前的显性拒绝与搜索后的显性过滤。

代价的量化维度是编译时间与 profile 时间之和占搜索总墙钟的比例。当这个比例超过生成时间时，配方应收缩搜索空间（减少 atom 候选、固定部分 stage）而非扩大评测集。这是布局搜索与一般 kernel 生成的预算模型差异：后者的瓶颈在 token 与生成，前者的瓶颈在编译与 profile。一个具体例子：sm90 attention 的 QK^T，合约固定 head_dim=128、seq 长度取 512/2048/8192 三档、smem 预算 200KB、stage 上界 4，基线为 CUTLASS fmha 对应配置。搜索前预检发现 seq=512 档的合法 atom 组合数不足，直接跳过该档、只搜后两档，把编译预算集中在有区分度的负载上。

最终落在具体机制上：负载配方的核心不是“选一个好负载”，而是把负载规格、基线锚定、分布分层、指标口径四者绑成一个可执行合约，让搜索的每一次 keep-revert 都在合约定义的坐标系里发生。合约不对，搜索的收敛方向就是错的；合约对了，CuTe 的类型系统与 NCU 的计数器才能形成闭环——前者把布局错误挡在编译期，后者把性能归因落到具体参数上。
