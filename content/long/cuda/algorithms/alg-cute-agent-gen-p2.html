一 · 从算子描述到合法 atom 集合：搜索空间的第一道收敛

一次 CuTe kernel 生成的起点不是代码，而是一份被结构化过的算子描述：M/N/K、dtype（fp16/bf16/fp8/tf32）、目标架构（sm80 还是 sm90）、A/B 的 layout 约定（row-major 还是 col-major、是否转置）、batch 维与 epilogue 需求。这份描述的作用是把 CuTe 的抽象层“钉死”在一个有限枚举域内——因为 CuTe 的 Layout、Tensor、MMA atom 都是类型级对象，一旦 dtype 与架构确定，可用的 MMA atom 集合就是可枚举的，而不是开放的。以 sm90 上的 fp16 GEMM 为例，候选 atom 来自该架构支持的 MMA 形状族（如不同 M×N×K 组合的 tcgen05 或 wgmma 变体），再叠加 A/B 在 shared memory 中的 major 模式，构成一个离散的候选表。这一步的输出不是代码，而是一张候选参数表：每个条目包含 MMA atom 标识、tile shape（CTA tile 与 warp tile）、shared memory layout 的 major/swizzle 模式、pipeline stage 数。代价在这一步是 token 与上下文预算：候选表本身要序列化进 prompt，条目越多，LLM 的骨架生成越容易被稀释；工程上通常按“架构支持 × dtype 合法 × tile 能整除问题 shape”三层过滤，把表压到几十条量级，否则后续每一条都要付出编译代价。一个具体例子：K=4096 的 fp16 GEMM，若 tile K 取 64 且 pipeline stage 取 4，则单 CTA 的 shared memory 需求随 stage 线性增长，过滤阶段就要把超出 shared memory 容量的组合剔除，避免把注定编译失败的组合送进下一环。

二 · 骨架生成：LLM 只填“组合位”，不发明语义

第二步是让 LLM 产出 CuTe 代码骨架。关键约束是：骨架的语法结构与类型关系由模板固定，LLM 的产出被限制在若干“组合位”上——选择哪个 MMA atom、tiled_mma 如何切分、tiled_copy 的源/目标 layout 与线程映射、shared memory layout 的 swizzle 函数、以及 pipeline 的 stage 数与 producer/consumer 角色划分。这种受限生成把 LLM 的自由度从“写一个 kernel”降为“在一张合法表里选一行并正确接线”，从而把语义错误的概率压到主要由“接线错误”构成，而非“从零发明 layout”。伪代码层面的流程是：读候选表 → 选 atom → 构造 Layout 与 Swizzle → 组装 tiled_mma/tiled_copy → 生成 gemm 主循环与 epilogue。这一步的代价是生成 token 与时延：骨架长度随 pipeline 复杂度上升，stage 越多、copy 路径越多，token 消耗越大；同时 LLM 对 CuTe 语义理解不足时会产出“语法合法但 layout 语义错位”的代码，例如把 copy 的线程映射与 MMA 的 fragment layout 对齐关系搞反，这类错误不会在编译期暴露，只能靠后续 oracle 兜底。具体例子：在 sm80 上为 row-major A、col-major B 生成骨架时，若 LLM 把 A 的 shared memory major 选成与 ldmatrix 期望的转置模式不一致，编译能过，但数值结果错位——这正是“编译通过但语义错”的典型形态。

三 · 模板实例化与编译：类型系统把错误前移，但时间账单很重

第三步是 CuTe 模板实例化加编译。CuTe 的类型系统在这里承担了“静态断言”的角色：layout 的 rank、shape 与 stride 的一致性、atom 与 tile 的整除关系、swizzle 位宽与元素大小的匹配，都会在实例化阶段变成编译期错误。失败时，编译器吐出的静态断言信息被回灌给 LLM，作为下一轮修正 layout 参数的输入——这是一个以编译错误为奖励信号的局部修复循环，而不是重新生成整段代码。这一步的代价是本部分最需要正视的一项：CuTe/CUTLASS 的模板实例化编译时间长，每轮搜索的编译开销可能超过生成开销。当搜索需要在几十个候选上做 keep-revert 时，编译时间会主导整个预算；预算敏感场景下，把编译并行化、缓存已通过的实例化、或对候选做粗筛（先用小规模 shape 编译验证类型合法性）是必要的工程手段。具体例子：同一份骨架在只改 swizzle 模式时，实例化出的类型不同，编译单元无法复用，意味着每次 keep-revert 都要重新付出一次完整实例化成本；因此搜索策略上应优先在“编译代价低、语义影响大”的参数（如 tile shape）上做粗搜索，再在 swizzle 这类细粒度参数上做局部精修。

四 · 正确性 oracle 与 NCU profile：两把尺子量同一份产物

第四步是双轨验证。正确性侧用 fp64 参考实现做 oracle，逐元素比对生成 kernel 的输出，容忍度按 dtype 设定；这一步的代价是参考实现的运行时间与显存——fp64 参考在大 shape 上本身就很重，通常需要抽样或分块比对来控制开销。性能侧用 NCU profile 采集三类指标：tensor core 利用率、shared memory bank conflict 计数、DRAM 吞吐。这三类指标正好对应 CuTe 布局搜索的三个失效模式：MMA atom 选得不对或 tile 太小导致 tensor core 空转；swizzle 没配好导致 bank conflict 抬高 shared memory 访问时延；copy 路径与全局内存访问模式不匹配导致 DRAM 吞吐上不去。评分沿用

$$\text{SOL}=\max\left(\frac{F}{F_{\text{peak}}},\frac{B}{B_{\text{peak}}}\right),\quad \text{score}=\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}\cdot\mathbb{1}[\text{correct}]$$
其中正确性指示函数是一票否决：任何数值偏差都让该候选的分数归零，无论 SOL 多高。具体例子：一个候选在 NCU 上显示 tensor core 利用率尚可但 bank conflict 计数偏高，说明瓶颈在 shared memory layout 的 swizzle 选择上，而不是 MMA atom 本身——这条 profile 信息直接指向下一轮该改哪个参数，而不是盲目重生成。

五 · keep-revert 布局搜索：用 profile 定向，而非随机游走

第五步是以 SOL 利用率为目标对 layout/tile 参数做 keep-revert 搜索。与通用的进化式搜索不同，这里的变异被 NCU 指标定向：bank conflict 高则改 swizzle 模式或 shared memory major；tensor core 利用率低则改 MMA atom 或增大 warp tile；DRAM 吞吐不足则改 copy 的向量化宽度与全局访问的合并模式。每次变异后重新走“实例化—编译—oracle—profile”四环，通过则保留，失败或分数下降则回退到上一状态。这一步的代价是搜索轮数乘以单轮成本，而单轮成本由编译时间主导（见第三节），因此轮数预算必须与编译预算一起规划；一个常见工程判断是：当单轮编译时间已经接近或超过生成时间时，应减少候选宽度、提高每次变异的针对性，而不是扩大搜索面。具体例子：在 sm90 的 attention kernel 上，若 profile 显示 shared memory bank conflict 集中在 K/V 的加载路径，搜索就应把变异限制在 K/V 的 swizzle 与 copy atom 上，保持 Q 侧与 MMA atom 不动，这样每轮只改一个类型维度，编译产物可部分复用，轮数虽少但每轮信息量高。

六 · 输出与代价核算：一次流动的账本

最后一步输出最优 CuTe kernel，同时输出一份可复核的参数记录：选中的 atom、tile shape、swizzle、stage 数，以及对应的 SOL 分数与 NCU 指标快照。这份记录的价值在于让“为什么这个 layout 赢了”可被审计，而不是只留下一个二进制。把整条流动的代价摊开看，可以列成一张账：

步骤输入输出主要代价
算子解析与 atom 枚举shape/dtype/架构候选参数表token 与上下文预算
骨架生成候选表CuTe 代码骨架生成 token 与时延
实例化与编译骨架可执行产物或静态断言错误编译时间（常为主导项）
oracle + NCU产物正确性判定与三类指标fp64 参考运行时间与显存
keep-revert 搜索指标 + 分数下一轮变异方向轮数 × 单轮编译成本
输出最优候选kernel + 参数记录记录序列化的少量 token

这张账本给出的工程判断是明确的：CuTe 模板化生成的优势在于把 layout 错误前移成编译期错误、把搜索空间压成可枚举的离散表，从而让 LLM 不必发明语义；但它的代价结构是“编译时间换搜索确定性”，一旦编译开销超过生成开销，搜索的性价比就取决于变异是否被 NCU 指标定向。换句话说，这条流动的可信度不来自 LLM 写得多好，而来自每一步都有类型系统、fp64 oracle 与 profile 指标三者在同一份产物上给出可复核的判定——缺任何一环，编译通过的 layout 就可能是一个语义错位的陷阱。

编译墙与语义空转：CuTe 布局搜索的两类失效边界

把 layout、swizzle、tile shape、pipeline stage 摊成可搜索参数后，这套流程的真实瓶颈并不在 LLM 的采样，而在两个非对称的失效面。第一个是编译墙：CuTe 的 Layout/Tensor/MMA 全靠模板元编程实例化，一个 GEMM 骨架里 tiled_mma、tiled_copy、shared memory layout 与 swizzle 的每一次参数改动都会触发整条模板链重新实例化，编译器要为每个 atom 组合做类型推导、静态断言求值与 PTX 生成。搜索循环里 keep-revert 每试一个候选就要付一次这样的编译账单，而 LLM 生成代码骨架的 token 开销相比之下是常数级的小头。当候选空间按 tile shape × swizzle 模式 × stage 数组合展开时，编译时间随候选数线性累加，预算敏感的场景里“每轮搜索编译开销超过生成开销”不是偶发，而是默认状态。工程上的边界判断很直接：若单次实例化编译时延已经接近甚至超过一次 NCU profile 的采集周期，那么搜索的吞吐就由编译器而非 GPU 决定，此时应把候选裁剪到模板已预实例化的子集，或改用运行期参数化的 layout（牺牲部分编译期检查换搜索带宽）。

第二个失效面是语义空转：CuTe 类型系统能把 layout 的形状/步长不匹配变成编译期静态断言错误，但类型正确不等于语义正确。一个 tiled_copy 的 atom 排列在类型上自洽、能通过编译，却可能把线程到数据的映射写成与 MMA atom 的 fragment 布局错位的版本——编译通过，数值全错。这类错误不会在实例化阶段暴露，只能靠 fp64 参考的正确性 oracle 兜底。于是流程的正确性代价被转移到 oracle 环节：每个候选都必须跑一次全量比对，而不能只靠编译成功就进入 profile。评分式 $$\text{score}=\frac{\text{SOL}_{\text{gen}}}{\text{SOL}_{\text{ref}}}\cdot\mathbb{1}[\text{correct}]$$ 里的指示函数正是这道闸门——它把“编译通过但语义错”的候选直接归零，避免错误 layout 污染 keep-revert 的收益估计。代价是 oracle 的运行时延（fp64 参考本身可能比待测 kernel 慢一个量级）叠加到每个候选上，与编译墙一起构成搜索预算的双重开销。

两类失效的耦合点在于反馈信号的质量。编译失败时回灌给 LLM 的是 CuTe 静态断言文本，这类错误信息往往指向模板深处的类型不匹配，LLM 若对 CuTe 语义理解不足，容易做出“改一个参数让断言消失”的局部修补，而非修正真正的 layout 逻辑，形成反复编译、反复失败的循环——每一轮都在付编译代价却不缩小候选空间。NCU 侧的信号同样有边界：tensor core 利用率、共享内存 bank conflict、DRAM 吞吐能定位“哪里慢”，但无法区分“慢是因为 swizzle 选错”还是“慢是因为 tile shape 与 shape 不整除导致的尾块浪费”，后者需要解析阶段就拿到的 shape/dtype/架构信息参与归因。因此 keep-revert 的判据不能只看 SOL 标量，要把 NCU 指标拆成可归因的分量，否则搜索会在平台期反复回退同一族候选。

失效面触发条件主要代价兜底手段
编译墙候选组合多、模板链深每候选一次全量实例化编译时延预实例化子集、运行期参数化
语义空转类型自洽但 fragment 映射错位每候选一次 fp64 oracle 比对指示函数归零、强制 oracle 闸门
反馈失真断言文本指向模板深处无效编译轮次累积错误归类后再回灌

具体到一个 sm90 上的 GEMM：解析阶段拿到 M/N/K 与 dtype 后枚举合法 MMA atom，LLM 选出 tiled_mma 与对应 tiled_copy，shared memory layout 的 swizzle 模式作为搜索变量。若某个 swizzle 候选编译通过但 bank conflict 计数偏高，NCU 能直接指出冲突来源，keep-revert 据此回退；但若该候选同时存在 fragment 错位，SOL 会因为数值错误而虚高或虚低，此时只有 oracle 的指示函数能把它拦下。系统代价的分配由此清晰：编译墙吃掉搜索的墙钟时间，oracle 吃掉正确性预算，NCU 采集吃掉每候选的 GPU 占用，三者叠加决定了这套方案在给定预算下能覆盖的候选规模上限。超出该上限时，正确的工程动作是缩小搜索维度（先固定 stage 数只搜 swizzle），而不是加大 LLM 采样量——后者只会把更多候选推进编译墙。

模板实例化即验证：编译墙、语义空洞与搜索预算的边界

这条流水线的关键假设是“编译通过≈布局合法”。CuTe 的静态断言确实能把 stride 不整除、swizzle 位宽与元素宽度冲突、tiled_copy 的 thread-value 布局与 MMA atom 形状不匹配这类错误挡在运行前，但它只验证类型层面的一致性，不验证语义。一个把 A 矩阵的 (M,K) 布局写成 (K,M) 转置视图、却仍满足所有整除约束的 CuTe 代码可以干净编译，随后在 fp64 oracle 上给出错误结果——此时回灌给 LLM 的不是静态断言文本，而是数值 diff，修正信号的信噪比远低于编译错误。因此 oracle 必须前置为硬门禁：任何进入 NCU profile 的候选都必须先过正确性，否则 NCU 采集到的 tensor core 利用率只是“一个错误 kernel 跑得多快”。

第二个边界是编译墙。CuTe/CUTLASS 的模板实例化在 tile shape、stage 数、swizzle 组合上呈组合爆炸，单次实例化的编译时间随模板深度非线性上升，而 keep-revert 搜索每轮都要重新实例化。设候选数为 N、单次编译时间为 tc、单次 profile 时间为 tp、LLM 生成时间为 tg，则一轮搜索的墙钟代价近似为

$$T_{\text{round}} \approx t_g + N\cdot(t_c + t_p),\quad \text{当 } N t_c \gg t_g \text{ 时搜索被编译支配}$$

这意味着“多枚举几个 swizzle”在预算敏感场景下不是免费的：编译开销会挤占本可用于更多 LLM 采样或更长 profile 的预算。工程判断是先把候选集按解析阶段得到的 shape/dtype/arch 剪枝到合法 atom 的笛卡尔积子集，再用便宜的静态指标（共享内存占用、每 SM 的 CTA 数、寄存器压力上界）预筛，只对预筛幸存者付编译费。

失效模式观测信号系统代价
编译通过但布局语义错fp64 oracle diff 超阈值浪费一轮 profile 与 NCU 采集
swizzle 与元素宽度冲突静态断言文本一次编译 + 一次 LLM 修正往返
bank conflict 未消除NCU 共享内存冲突计数高多轮 keep-revert，编译时间累加
tile 过大导致 occupancy 塌陷tensor core 利用率低但 DRAM 吞吐正常需回退 tile shape 并重新实例化

第三个边界是 SOL 目标本身的误导性。评分 score = SOLgen/SOLref · 𝟙[correct] 中，SOL 取 max(F/Fpeak, B/Bpeak)，当 kernel 受 DRAM 带宽约束时，提高 tensor core 利用率对 SOL 毫无贡献，搜索会朝错误方向做 keep-revert。具体例子：一个 sm90 上的 attention 变体在某个 tile shape 下 DRAM 吞吐已接近峰值而 MMA 利用率仅过半，此时继续缩小 tile 以提升 occupancy 只会增加冗余加载、拉低 SOL；正确动作是判定该候选已处带宽屋顶，停止在该维度搜索，把预算转向减少 K/V 重读的 pipeline stage 调整。NCU 指标必须与 roofline 判定联合使用，否则“指标驱动搜索”会退化为对单一指标的过拟合。
