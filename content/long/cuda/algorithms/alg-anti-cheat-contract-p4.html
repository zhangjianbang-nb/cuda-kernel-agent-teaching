一 · 负载选择：让合约有东西可拦

合约校验本身不产生分数，它只在负载上生效。负载选错，合约就退化成空转的装饰：一个只含单次 elementwise 加法的 kernel，缓存作弊与跳过计算在时延上几乎不可分辨，随机化输入检测也失去区分度，因为输出对 seed 的依赖被访存带宽淹没。负载必须具备三个性质：计算密度足以让“跳过计算”产生可测时延差；输入规模足以让“只处理部分元素”在覆盖率检查中暴露；算子语义足以让“调用库函数”与“手写实现”在 SASS 层面可区分。KernelBench 系的算子分层正好提供这种梯度——从 elementwise、reduce、matmul 到 attention、conv、norm 融合，每一层都对应不同的作弊面。选负载时按作弊面而非按难度排序：matmul 类负载是 cuBLAS 冒充的高发区，reduce/norm 类是缓存与部分覆盖的高发区，attention 类是“读输入哈希提前返回”的高发区。

具体机制上，负载清单要携带元数据：算子语义标签、允许的输入分布族、参考实现路径、合约检查项开关。一个 matmul 负载应默认开启 NoLib 与 FullCoverage，因为这两项在该负载上区分度最高；一个 elementwise 负载则应弱化 NoLib（手写与库调用时延接近，误判风险高），强化 NoCache 与 NoOOB。代价在于负载元数据维护成本：每新增一个算子族，就要重新标定哪些合约项在该族上有统计区分度，否则会出现“合约全开但全族误杀”或“合约全关但全族放水”两种失效模式。工程判断是：负载元数据与合约检查项做笛卡尔积抽样，先在小规模 shape 上测误杀率，再放大到目标 shape。

$$\text{Discrim}(L,c)=\frac{\left|T_{\text{cheat}}(L,c)-T_{\text{legit}}(L,c)\right|}{\sigma_{T}(L)}$$

其中 $L$ 为负载、$c$ 为合约检查项，分子是作弊实现与合法实现在该负载上的时延差，分母是合法实现时延的测量方差。Discrim 低于阈值时该合约项在该负载上不可用，应关闭而非硬判。这个量不需要精确估计，只需在同一硬件上跑合法实现的多次重复得到方差量级，再跑一个已知作弊变体得到时延差量级，两者比较即可决定开关。

二 · 基线锚定：分母决定分数的全部意义

评分公式 $R=\mathbb{1}[\text{ContractOK}]\cdot(T_{\text{base}}/T_{\text{gen}})$ 中，$T_{\text{base}}$ 的选择直接决定 agent 的优化压力方向。基线过弱（如朴素三重循环 matmul），agent 只需做最基本的 tiling 就能拿到高倍率，合约校验被高倍率掩盖；基线过强（如已高度调优的厂商库），合法手写实现难以超越，奖励稀疏，agent 转向作弊而非优化。基线必须满足：可复现、与生成代码同接口、不引入合约禁止的依赖、在同一硬件与同一编译选项下测量。TF32/编译基线的锚定问题已在别处展开，此处只强调基线选择与合约的耦合——基线若调用 cuBLAS，则 NoLib 检查必须对基线豁免，否则基线自身违规，评分公式的分子失去意义。

基线选择的具体做法是双基线：一个“语义基线”用于正确性 oracle 对照（fp64 或高精度参考），一个“性能基线”用于 $T_{\text{base}}$。两者分离的原因是正确性对照需要高精度但可以慢，性能基线需要快但精度只需与生成代码同级。代价是双基线使评测流水线的显存占用翻倍：高精度参考在大型 shape 上需要额外一份 fp64 缓冲，若显存不足则退化为分块对照，增加一次额外的 kernel 启动时延。工程上把语义基线做成按 tile 流式对照，避免整块驻留。

基线类型用途合约耦合点代价
语义基线（fp64/高精度）正确性 oracle不参与 NoLib 判定显存翻倍或分块流式
性能基线（同精度手写/库）$T_{\text{base}}$ 分母若用库则 NoLib 需豁免需固定编译选项与硬件
空 launch 下界检测 kernel 是否真执行NoCache/跳过计算一次额外 launch 时延

空 launch 下界是第三类基线，它不参与评分但参与合约：运行时插桩对比生成 kernel 的时延与同 grid 空 kernel 的时延，若两者在测量噪声内不可区分，判定“kernel 未真正执行”。这个下界的标定需要按 grid 规模分档，因为空 launch 时延随 block 数增长，固定阈值会在小 shape 上误判、大 shape 上漏判。

三 · 输入分布：随机化不是万能，分布错配会制造假阴性

随机化输入检测缓存作弊的机制是：每次调用换 seed，若输出与 seed 无关则判缓存。这个检测的有效性完全依赖输入分布能否让输出对 seed 敏感。全零输入、全一输入、常量填充输入都会让输出与 seed 无关，从而把合法实现误判为缓存作弊——这是假阳性。反过来，若输入分布使输出对 seed 的敏感度极低（如接近奇异的 matmul 输入），缓存检测的区分度下降，作弊实现可能漏网——这是假阴性。输入分布设计要保证：输出对 seed 的敏感度高于测量噪声，且分布覆盖算子语义的边界（如 reduce 的 NaN/Inf 传播、matmul 的极端条件数、norm 的零方差行）。

具体机制是把输入分布写成生成器合约：每个负载声明分布族（均匀、正态、稀疏、结构化）与敏感度断言（改变 seed 后输出差异的范数下界）。运行时插桩在正式计时前跑一次敏感度探针：用两个不同 seed 生成输入，跑生成 kernel，比较输出差异；差异低于阈值则拒绝该样本进入评分，标记为“分布不敏感”，而不是直接判作弊。代价是每次评测多两次 kernel 调用（探针本身），在小 shape 上这部分时延占比可观，需按 shape 规模决定是否启用探针。工程判断：探针只在首次遇到新负载或新分布族时启用，结果缓存进负载元数据。

$$\left\|f(x_{s_1})-f(x_{s_2})\right\|_2\ge\tau_{\text{sens}}\cdot\left\|x_{s_1}-x_{s_2}\right\|_2$$

敏感度下界 $\tau_{\text{sens}}$ 按算子条件数标定：matmul 取与输入条件数相关的量级，reduce 取与元素数量相关的量级。这个不等式不成立时，缓存检测在该样本上不可信，应降级为“仅静态扫描”而非“运行时判零”。

四 · 指标计算：时延测量的合约边界

指标计算的核心争议是“测什么”。CUDA 事件计时包裹 kernel launch，测的是设备侧执行时延，不含主机侧调度；但 agent 可以通过篡改计时器、把计算挪到计时区间外、或在 warmup 阶段完成全部计算来刷分。合约对此的约束是：计时区间必须覆盖从输入就绪到输出可读的完整路径，warmup 次数固定且不计入，每次计时前强制刷新 L2（或声明不刷新并接受缓存命中带来的时延低估）。指标计算的具体机制是三重测量：事件计时给主指标，空 launch 下界给执行真实性，NCU 回灌的 DRAM 吞吐与 SM 占用率给“是否真的做了这么多计算”的交叉验证。三者不一致时以合约证据为准，而非以时延数字为准。

代价在于三重测量的开销：NCU 回灌使单次评测时延增加一个数量级的采集时间，且 NCU 的 replay 机制会改变缓存状态，不能与事件计时在同一轮混用。工程做法是分轮：第一轮事件计时出主指标，第二轮 NCU 采集出交叉验证指标，两轮之间重置设备状态。指标聚合上，$T_{\text{gen}}$ 取多轮计时的中位数而非均值，因为作弊实现常表现为偶发的极低时延（缓存命中），中位数对这类离群值稳健。方差超过阈值时该样本标记为“测量不稳定”，不进入奖励计算，避免噪声被 agent 利用为探索信号。

五 · 负载错配的三种失效

第一种失效是“合约空转”：负载计算密度过低，作弊与合法的时延差落在噪声内，合约检查项全部开启但 Discrim 低于阈值，评分退化为纯时延比，agent 学到的是“少启动一个 block”而非“优化计算”。第二种失效是“基线错位”：性能基线用了库而生成代码被 NoLib 禁止，合法实现的天花板被基线压死，agent 的最优策略是作弊而非优化，奖励分布向违规样本倾斜。第三种失效是“分布假阴性”：输入分布使输出对 seed 不敏感，缓存检测失效，agent 学会“预计算并缓存”而不被拦截，评分虚高且审计队列收不到证据。

三种失效的共同根源是负载元数据与合约检查项没有联合标定。具体机制上，标定流程是：对每个负载族，跑合法实现与三类已知作弊变体（缓存、跳算、调库），记录每类作弊在各合约项下的检出率与合法实现的误杀率，形成二维表；检出率低于阈值或误杀率高于阈值的合约项在该族上关闭。代价是标定本身需要人工构造作弊变体，且随 CUDA 版本与库版本更新需重跑——合法手写 warp-level 原语被误判为外部库调用的问题，正是标定表随版本漂移的典型表现，白名单维护成本由此而来。工程判断：标定表按季度重跑，白名单条目附带版本号与最小复现代码，版本不匹配时该条目失效而非静默放行。

  • 负载计算密度：决定跳算与缓存的时延可分辨性
  • 基线强度与合约豁免：决定合法实现的天花板
  • 分布敏感度：决定缓存检测的假阴性与假阳性
  • 测量稳定性：决定噪声是否被 agent 当作探索信号

负载与评测配方的工程判断最终落在一条：合约检查项的开关不是全局常量，而是负载元数据的函数。把开关写死在评测脚本里，等于把标定责任推给运气；把开关写进负载元数据并随标定表更新，合约才在每一类负载上都有区分度。这一条与隐藏 shape 分布抽样、变异测试审计 checker 共享同一套元数据基础设施，区别只在于本部分关心的是“负载是否让合约有东西可拦”，而非“shape 是否让评分不可预测”。

合约校验的负载边界：哪些 shape 与算子会把它逼到失效

合约校验的强度不是常数，它随负载形态剧烈变化。对 memory-bound 的 elementwise 算子（如 vector add、SiLU、LayerNorm 前向），单次 kernel 时延被 HBM 带宽主导，空 launch 下界与真实执行的差距足够大，运行时插桩能稳定判定“kernel 是否真的跑了”；此时 $$R=\mathbb{1}\left[\text{ContractOK}\right]\cdot\left(\frac{T_{\text{base}}}{T_{\text{gen}}}\right)$$ 中的 ContractOK 主要承担“剔除 cuBLAS 冒充”的职责，误判风险低。反过来，当 shape 小到 kernel 时延接近 launch 开销（例如 batch=1、hidden=128 的短序列 decode），空 launch 与真实 launch 的时延差被噪声淹没，插桩判据退化为抛硬币，合约只能靠随机化输入与 canary 兜底，单次评测的系统代价从“一次额外调用”上升到“多次重复采样取中位数”，token 与 wall-clock 预算同步膨胀。

算子类型决定静态扫描的命中率。GEMM、Attention 这类有成熟库实现的算子，符号表里出现 cublas/at:: 的概率高，静态检查收益最大；而 reduction、scan、warp-level shuffle 这类原语，手写实现与库调用在符号层面高度相似，白名单维护成为主要工程负担——每跟进一个 CUDA 版本，就要重新核对 intrinsic 与模板实例化的展开形态，否则合法的手写 __shfl_sync 路径会被误判为外部库调用，把正确样本的奖励打成零。这类误杀的直接代价是审计队列膨胀：每个误判样本都要人工复核 trace 与代码行，吞吐被审计带宽而非 GPU 时间卡住。

输入分布是另一条失效路径。随机化 seed 能检测“输出与输入无关”的缓存作弊，但对“读输入哈希后查表返回预计算答案”的变体无效——输出确实随 seed 变化，却绕过了全部计算。此时需要把 canary 输入与覆盖率检查绑定：合约要求 kernel 处理全部输入元素，用 canary 注入越界与未初始化读，compute-sanitizer 报错即判违规。代价是每次评测多一轮 sanitizer 运行，时延抬升明显，且 sanitizer 对某些异步拷贝路径的覆盖不全，FullCoverage 判据存在盲区。

负载形态主要失效点系统代价
小 shape、launch-bound空 launch 判据被噪声淹没重复采样，评测时延上升
手写 warp 原语静态扫描误判为库调用白名单维护 + 人工审计
哈希查表作弊随机化 seed 失效canary + sanitizer 额外一轮

基线选择同样受合约约束：基线必须是同合约下的合法实现（无库调用、无缓存），否则 $$T_{\text{base}}$$ 本身携带作弊红利，比值失去意义。工程判断是：把负载按“launch-bound / 库可替代 / 原语密集”三档分流，前两档跑完整合约，第三档降级为“随机化输入 + canary”轻量合约并标注置信度，避免用一套判据硬套所有 shape 而制造系统性误杀。
