一 · 一次“脚手架虚高”引发的评测翻车

设想一个典型的生产接入评审：某团队用带完整优化提示的 agent 脚手架在 KernelBench 系基准上跑出一组漂亮数字，声称模型能在若干算子上达到参考 kernel 的较高 SOL 比例，于是决定把这条链路直接接到线上算子生成流水线。上线后第一周，一个 batch 维度和 hidden size 都落在训练分布之外的推理请求触发了新生成的 kernel，正确性 oracle 通过，但端到端时延反而比手写实现差，NCU 显示 occupancy 被寄存器压力压死。回滚之后复盘发现：基准上的高分并非来自模型对 GPU 执行模型的理解，而是来自脚手架里那份“优化技巧清单”——清单恰好覆盖了基准里反复出现的几类算子形态，模型只是把提示里的模板套上去。一旦形态漂移，模板失效，模型自身的诊断能力从未被真正测量过。

这个事故的核心不是模型不行，而是度量对象错了。带提示脚手架下的分数是“模型能力 + 脚手架工程”的复合量，二者不可分离。更糟的是，提示本身是人工针对基准写的，存在对基准分布的过拟合：清单里每一条“记得用 shared memory 做 tiling”“优先向量化 load”都是从基准的典型形态反推出来的，模型在评测中表现出的“优化直觉”其实是提示的回声。工程上要回答的问题因此变得具体：当我们说某个模型“会写 GPU kernel”时，这个判断有多少来自模型权重里的先验，有多少来自我们塞进 context 的专家规则？如果无法拆分，任何关于模型选型、RL 训练收益、脚手架投入产出比的决策都建立在流沙上。

二 · 这个方法要解决的问题：把“能力”从“工程”里剥出来

仅目标驱动基线（goal-only baseline）的做法是把输入压到最小：只给 agent 算子语义、输入输出契约、目标硬件与性能目标（例如达到参考 kernel 的某个百分比 SOL），工具面只暴露编译、运行、NCU 采集三个原语，不提供任何优化提示、代码模板或专家规则。agent 自主决定是否读文档、是否先写测试、是否 profile，每一轮自行提出假设、改代码、验证。评测指标是两个量的组合：

$$\text{capability}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\left[\text{correct}_i\land \text{SOL}_i\ge \theta\right],\quad \text{cost}=\frac{1}{N}\sum_i \text{tokens}_i$$

第一个量是“在正确性成立且 SOL 达到阈值 θ 的算子上占比”，第二个量是达到该状态所消耗的平均 token。二者必须同时报告：只报 capability 会掩盖“靠堆轮次堆出来”的路径，只报 cost 则无法区分“便宜但没达标”和“便宜且达标”。这个定义的关键在于 θ 和正确性 oracle 都是外部给定的、可验证的，不由 agent 自述；SOL 归一化与 oracle 的具体构造属于其他片段的主题，此处只强调它们是硬约束而非软信号。

机制上，goal-only 基线做的事情是切断“提示→行为”的因果链。带提示脚手架里，模型输出与提示条目之间存在强相关，评测无法归因；去掉提示后，模型若仍能在多轮内收敛到 θ 以上，那么收敛路径上的每一次 profile 读取、每一次寄存器压力诊断、每一次 tile 尺寸调整都只能归因于模型自身的先验与探索策略。这正是“纯模型能力”的操作化定义：不是模型知道多少优化名词，而是它在只有可验证目标和最小工具面时，能否自主构造出“假设—修改—测量”的闭环。

三 · 它明确不解决的问题

适用边界必须先划清楚，否则这个基线会被误用。第一，它不解决生产部署方案的问题。无提示条件下收敛慢、轮次多、token 成本高，这是方法的固有代价而非缺陷：agent 需要自己发现“这个算子受限于 global memory 带宽”还是“受限于指令发射”，需要自己决定先做 profile 还是先改 tile，这些探索在带提示脚手架里被清单直接跳过。把 goal-only 轨迹直接拿去上线，等于用最高的 token 成本换一个偏低的质量上限。

第二，它不提供性能上限的估计。模型的先验知识边界决定了它能想到的优化空间：如果模型权重里没有某种 warp 级协作模式的概念，它在无提示条件下大概率不会自发构造出来。因此 goal-only 的 SOL 分布系统性低于带专家提示的脚手架，这个“偏低”是测量结果的一部分，不是需要修复的 bug。用 goal-only 分数去论证“模型不行”是错的，正确用法是把它当作下界锚点，与带提示脚手架的上界一起构成区间。

第三，它不替代防作弊与正确性审计。goal-only 只保证“目标可验证”，不保证 agent 没有通过退化实现骗过 oracle，也不保证 SOL 计算没有被输入分布的选择性采样污染。防作弊合约校验、变异测试审计 checker、fuzz 加 fp64 参考 oracle 是并行存在的独立防线，goal-only 基线假定这些防线已经就位，否则 capability 指标本身不可信。第四，它不解决隐藏 shape 分布的抽样问题：goal-only 的输入契约里 shape 是给定的，若评测集本身对分布覆盖不足，基线分数同样会虚高，这属于抽样环节的职责。

四 · 一个具体例子：从“套模板”到“自己诊断”

取一个 reduction 类算子：输入是二维张量，沿第二维求 softmax 后再做加权求和，目标硬件给定时延阈值 θ 对应参考 kernel 的某个 SOL 比例。带提示脚手架的轨迹通常是：提示里有“先做 row-wise 分块、用 shared memory 存中间结果、注意 bank conflict”，模型照着写出一个能跑的版本，profile 一次，看到带宽利用率尚可就收工。整条轨迹的 token 消耗集中在代码生成，诊断环节被提示短路。

goal-only 轨迹则不同。第一轮模型可能写出一个每线程处理一行的朴素版本，编译通过、正确性通过，但 NCU 显示 global memory 吞吐远低于峰值，warp stall 集中在 long scoreboard。第二轮它需要自己从 stall 类型推断出“访存不合并或数据复用不足”，于是尝试把一行切成多段由多个 warp 协作，引入 shared memory 做部分和。第三轮可能发现 shared memory 的 bank conflict 让收益打折，再调整 padding。每一轮都是一次假设、一次代码修改、一次 profile 验证，token 消耗分布在读 NCU 指标、写测试、改代码三处。最终它可能收敛到 θ 以上，也可能停在 θ 以下——停在下面的情况同样有价值：轨迹显示它在某个 stall 类型上反复打转，说明模型先验在这一类执行模型细节上存在盲区，这正是 SFT/RL 数据应该补的地方。

代价在这里是具体的：goal-only 的轮次通常是带提示脚手架的数倍，token 成本相应放大；编译与 NCU 采集本身也消耗 wall-clock，若算子编译时间长，多轮探索的时延代价会传导到评测吞吐。收益则是轨迹的可归因性：每一条 stall 指标到代码修改的映射都由模型自己建立，这条轨迹拿去训练时，模型学到的是“从测量到假设”的映射，而不是“从提示到模板”的映射。

五 · 适用边界的工程判据

判断一个场景是否该用 goal-only 基线，可以看三个条件是否同时成立。其一，评测目的是归因而非选型：你要回答“模型原生能力如何”，而不是“这条流水线能不能上线”。其二，正确性与性能目标可以被外部硬性验证，且验证成本低于 agent 探索成本——否则 oracle 本身成为瓶颈。其三，你接受分数偏低且方差偏大：无提示条件下不同算子上的收敛难度差异会被放大，capability 的均值需要配合逐算子分布一起看，单看均值会掩盖“简单算子全过、困难算子全挂”的双峰形态。

反过来，以下场景不应使用：需要快速产出可部署 kernel 的生产任务；需要评估脚手架工程投入产出比的任务（那应该做带提示与不带提示的对照实验，而不是只跑 goal-only）；以及正确性 oracle 尚未通过变异测试审计的阶段——此时 goal-only 的低分可能来自 oracle 误判而非模型能力，归因链条断裂。工程上更稳妥的做法是把 goal-only 作为固定锚点纳入常规评测矩阵：每次模型或脚手架变更，都同时跑 goal-only 与带提示两条线，用两者差值量化脚手架增益，用 goal-only 绝对值追踪模型原生能力的漂移。这个矩阵的维护成本主要是 token 与编译时延，但换来的是任何一次“基准高分”都能被拆解成可解释的两部分。

最后落到机制上：goal-only 基线的价值不在于它给出一个数字，而在于它把评测的因果结构固定下来——目标可验证、工具面最小、提示为零。只要这三条不被破坏，任何后续的轨迹分析、RL 奖励构造、SFT 数据筛选才有共同的参照系；一旦为了“让分数好看”偷偷加回一条提示，基线就退化成又一个过拟合基准的脚手架，事故会以另一种形态重演。

目标驱动基线的失效边界与系统代价

目标驱动基线最容易在“目标本身可被廉价满足”的算子上翻车。考虑一个逐元素缩放算子，语义与契约都极简，性能目标设为达到参考 kernel 的某个百分比。由于该算子天然带宽受限，模型只要写出一份合并访存、向量化加载的朴素实现，就能在少数几轮内撞上目标线，SOL 指标看起来漂亮，但这条轨迹几乎不含任何调度决策、不含 shared memory 分块、不含流水线重叠——它验证的是“模型会不会写正确的 CUDA”，而不是“模型会不会优化”。若把这类轨迹直接混入 SFT/RL 数据，等于用低信息量样本稀释了真正有价值的诊断行为。反过来，在需要多维分块、寄存器压力权衡、bank conflict 规避的算子上，无提示 agent 常在错误假设上反复打转：它可能连续多轮修改 tile 尺寸而不去读 NCU 的 occupancy 与 stall 原因，轮次与 token 消耗线性上升，最终 SOL 却停在阈值之下。这就是基线的第一个边界——它衡量的是“模型先验与目标难度的匹配度”，而不是一个与任务无关的恒定能力值。用公式表述，基线的读数同时被能力与任务难度调制：

$$\text{capability}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\left[\text{correct}_i\land \text{SOL}_i\ge \theta\right],\quad \text{cost}=\frac{1}{N}\sum_i \text{tokens}_i$$

其中 θ 的设定直接决定基线的判别力。θ 过低，几乎所有正确实现都通过，capability 饱和、方差塌缩，无法区分模型；θ 过高，则连具备正确优化直觉的模型也被判失败，基线退化为噪声。工程上必须把 θ 锚定在参考 kernel 的实际 SOL 上，并意识到这个锚点本身带有硬件与编译器版本的耦合——换一张卡、换一版 nvcc，参考 kernel 的 SOL 就变，历史基线的可比性随之断裂。这是第二个边界：基线不是绝对刻度，而是相对当前工具链的相对刻度，跨版本比较必须重跑参考实现而非复用旧阈值。

系统代价方面，无提示意味着搜索空间完全由模型自行剪枝，收敛轮次与 token 成本显著高于带提示脚手架，且方差大——同一模型在同一算子上的多次运行可能给出差异明显的轮次分布。这对评测预算提出硬约束：若每个算子允许的轮次上限设得过紧，失败样本里混杂着“能力不足”与“预算不足”两种原因，capability 被系统性低估；设得过松，token 成本又吞掉整个评测吞吐。可行的折中是记录每条轨迹的轮次-token-SOL 三元组而非只记最终布尔值，把“在预算内未达标”与“达标但代价高”分开统计。第三个边界在于工具集的最小性本身是双刃的：只暴露编译、运行、NCU 采集三个原语，迫使模型自主诊断，但也剥夺了它获取文档、检索相似 kernel 的通道，于是基线实际测量的是“模型参数内化的优化知识 + 从 profile 反推假设的能力”的联合体，而非纯粹的代码生成能力。当模型在 NCU 指标解读上系统性偏弱时，基线会把它误判为优化能力不足。

失效条件表现对基线的污染
目标可被朴素实现满足少轮次即达标，轨迹无优化决策capability 虚高，数据信息量低
θ 锚点随工具链漂移跨版本 SOL 不可比历史基线失去参照
轮次预算过紧失败样本原因不可分capability 被低估
profile 解读能力缺失反复盲改 tile 尺寸能力与诊断力混淆

因此这套基线适合回答“在剥离全部人工策略注入后，模型能否仅凭可验证目标与最小工具闭环自主到达性能阈值”，适合作为脚手架增益的对照分母、作为轨迹数据的质量筛；它不适合作为生产部署方案的直接候选——无提示路径的 token 成本与轮次时延在端到端收益核算里通常不划算，也不适合用来给“模型是否懂某个具体优化技巧”下结论，因为技巧是否被使用是轨迹分析的事，不是基线布尔值能承载的。真正需要盯住的是：当某模型在带提示脚手架上得分远高于本基线时，差额里有多少来自可复用的诊断行为、多少来自提示对基准分布的过拟合——这个分解才是选择继续投入脚手架工程还是投入模型后训练的依据。
