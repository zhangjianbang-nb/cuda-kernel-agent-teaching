一 · 轨迹展开：一次 kernel 任务如何被拆成可计分的轮次

多轮 RL 的结构化奖励不是给一段静态代码打分，而是给一条被切开的轨迹打分。切法决定了信号密度，也决定了训练吞吐。工程上把一次 kernel 任务展开为固定上限 T 轮的序列：第 t 轮 agent 接收的输入是状态 st，包含原始算子规格（形状、dtype、语义参考实现）、上一轮的代码文本、上一轮的编译诊断、上一轮的正确性判定与实测时延、以及当前轮的预算提示（剩余轮数、是否已接近 SOL 阈值）。动作 at 是这一轮产出的完整 kernel 源码（CUDA C++ 或 Triton），不是 diff 片段——因为编译器诊断与 SASS 层面的一致性要求整文件可复现，diff 会让状态表示与最终产物脱节。

每一轮的执行流水线是固定的四段：编译 → 正确性 oracle → 计时 → 归一化。编译段产出二元结果与结构化诊断（错误码、出错行、寄存器溢出提示）；正确性段调用前文已述的 oracle 体系，产出通过/失败与最大相对误差；计时段在固定输入上做多次重复取中位数，产出 Tt；归一化段把 Tt 与 Tref 相除，得到可跨算子比较的比值。四段全部落盘为一条记录，构成轨迹的一个时间步。关键设计点是：**失败轮次同样产出完整记录**，编译失败时正确性与时延字段置为无效但保留占位，这样后续的负样本学习才有结构可依，而不是把失败轨迹整条丢弃。

代价在这里第一次显形。单轮 RL 一次 rollout 只需一次编译加一次计时；多轮 rollout 的 GPU 时间与 token 成本随 T 线性放大，且训练吞吐被真实编译/运行硬性卡住——编译是 CPU 侧串行瓶颈，计时是 GPU 侧独占瓶颈，两者都无法像纯文本 RL 那样靠增大 batch 摊薄。一个具体例子：一个 reduction 类算子，agent 首轮写出越界访存，编译通过但正确性失败；第二轮修边界，正确性通过但时延是参考实现的数倍；第三轮引入向量化加载与 warp 级归约，时延逼近阈值。三轮里只有第三轮在单轮 RL 下会得到正奖励，前两轮的修错行为完全不可学——这正是切轮次的意义。

二 · 分量奖励的逐轮计算：三个信号源与一个折扣结构

每轮记录落地后，奖励函数按分量拆解。编译分量 rcompilet 是二值的，但工程上常做成阶梯：语法/类型错误为零，编译通过但带警告（如寄存器压力告警）给部分分，干净通过给满分。正确性分量 rcorrectt 同样分层：完全失败为零，数值接近但超出容差给部分分，通过给满分；这里的容差必须与 oracle 的判定口径严格一致，否则 agent 会学到“贴着容差边缘”的脆弱解。性能分量不是绝对时延，而是相对上一轮的加速比，这是整个奖励结构里最容易写错的一项。

$$R(\tau)=\sum_{t=1}^{T}\gamma^{t-1}\left(r_t^{\text{compile}}+r_t^{\text{correct}}+\alpha\cdot\frac{T_{t-1}-T_t}{T_{\text{ref}}}\right),\quad \mathcal{L}=-\mathbb{E}_{\tau\sim\pi_\theta}\left[R(\tau)\right]+\beta\,\text{KL}(\pi_\theta\|\pi_{\text{ref}})$$

公式里三个细节值得逐条拆。其一，性能项用的是 Tt−1 − Tt，即本轮相对上轮的增量，而不是相对 Tref 的绝对位置；这意味着“从很慢改到中等”与“从中等改到很快”在增量上可能等价，奖励鼓励的是持续改进的斜率而非一次性撞线。其二，分母是 Tref 而非 Tt−1，避免了在接近最优时增量被小数除爆、产生数值上极端的奖励尖峰。其三，α 是性能项相对正确性项的权重，它直接决定策略是“先修对再调优”还是“为了提速牺牲正确性”。权重不当会诱导模型刷编译通过而忽略性能——这是已知的失败模式，表现为轨迹前几轮奖励爬升很快、后几轮停滞在低性能平台。

折扣因子 γ 的作用是把远期性能收益折算到当下。γ 接近 1 时，末轮的 SOL 达标能反向激励前几轮的铺垫动作（比如提前做 shared memory 布局）；γ 偏小时，策略退化为贪心，只优化眼前一轮的增量，长程优化行为学不到。代价是 γ 与 α 联合构成一个二维调参面，且这两个参数与算子类型强相关：访存密集型算子对 α 更敏感，因为其性能增量对布局改动响应剧烈；计算密集型算子则对正确性容差更敏感。一个具体例子：同一个 GEMM 任务，α 取大值时 agent 倾向在第二轮就上 tensor core 路径但跳过边界校验，正确性分量骤降；α 取小值时 agent 反复微调 tile 尺寸却不敢换算法，轨迹在中等性能处收敛。

三 · 轨迹入模：状态表示、动作空间与折扣回报的组装

一条轨迹 τ 由 T 个 (st, at, rt) 三元组构成，送入策略优化时要做两件事：状态压缩与回报组装。状态压缩的难点在于代码文本随轮次增长，直接拼接会迅速吃满上下文窗口，token 成本随 T 平方级膨胀。工程做法是保留最近一轮完整代码加历史轮的诊断摘要（错误码、时延比值、是否通过），把“代码演化史”压成“诊断演化史”。代价是策略失去了对早期代码细节的精确记忆，但换来了 T 可以开到更大而不爆 token 预算。

动作空间是完整源码，采样时用温度控制探索幅度：高温倾向于结构性改动（换算法、换数据布局），低温倾向于参数微调（tile 尺寸、unroll 因子）。多轮场景下温度应随轮次衰减，前几轮鼓励大胆重构，后几轮收敛到精调——这与单轮 RL 固定温度的做法不同，因为多轮里“探索”的语义是跨轮次的，而非单次采样的。

回报组装按公式逐轮累加折扣奖励，得到整条轨迹的标量 R(τ)，再对轨迹做策略梯度。这里有一个容易被忽略的工程点：**失败轨迹的回报不是零**。一条三轮全编译失败的轨迹，其 R(τ) 可能因首轮的编译阶梯分而为正的小值，也可能因全零而为零；但无论正负，它都作为负样本参与梯度，教策略避开导致连续失败的动作区域。若把失败轨迹过滤掉，策略只会看到成功路径，遇到编译错误时缺乏修复行为的先验。代价是失败轨迹拉低了 batch 的平均回报，方差变大，需要更大的 batch 才能稳定梯度——这是用吞吐换行为覆盖度的典型权衡。

KL 项 β·KL(πθ‖πref) 的作用在多轮里被放大：因为一条轨迹有 T 个动作，KL 惩罚在整条轨迹上累积，若不加约束，策略会在某一轮突然偏离参考策略并在后续轮次沿偏离方向滚雪球。实践中 KL 系数需要随轮次位置调整——早期轮次的偏离代价更高，因为早期动作决定了后续所有轮次的状态分布。一个具体例子：agent 在首轮把 kernel 改成完全不同的并行划分，后续两轮都在这个错误划分上修补，KL 约束若只作用于末轮则无法阻止这种“根节点错误”。

四 · 裁剪与稳定性：多轮场景下策略崩坏的两种典型形态

多轮 RL 的策略崩坏与单轮不同，它有两种形态。第一种是**轮次坍缩**：策略学会在首轮就输出一个“安全但平庸”的 kernel（能编译、能通过正确性、性能中等），因为这样能稳定拿到编译与正确性分量，而性能分量的增量在后续轮次难以保证。结果是 T 轮全部产出近似相同的代码，轨迹退化为单轮。第二种是**奖励刷取**：策略发现某类动作能稳定触发编译阶梯分或正确性部分分，于是反复在该动作附近采样，性能分量被系统性忽略。

裁剪机制针对的是第一种形态。PPO 式的比率裁剪限制单轮策略更新幅度，但在多轮里裁剪要作用于每个时间步的比率，而非整条轨迹的乘积比率。若用整条轨迹的乘积比率裁剪，早期轮次的小幅偏离会被后续轮次的比率放大，裁剪阈值失去意义。工程实现上对每个 t 计算比率 ρt = πθ(at|st)/πold(at|st)，逐项裁剪后加权求和。代价是每个时间步都要保存旧策略的对数概率，显存占用随 T 线性增长；在长轨迹（T 较大）时这是显存的主要开销之一，往往比模型参数本身更早触顶。

针对第二种形态，靠的是奖励结构的自适应调整而非裁剪。当检测到某分量奖励在连续多轮中饱和（比如编译分量连续满分而性能分量零增量），对该分量的权重做衰减，把梯度压力转移到未饱和的分量上。这不是公式里的固定项，而是训练循环里的调度逻辑。一个具体例子：一个 softmax 类算子，agent 连续三轮编译干净通过、正确性通过，但时延始终停在参考实现的数倍，性能分量零增量；此时若不调权重，策略会认为“当前动作已是最优”，停止探索向量化或 warp 级归约；调权重后性能项的梯度占比上升，迫使策略在后续轮次尝试结构性改动。

五 · 泛化评估的插入点：held-out 算子与轨迹级过拟合

多轮 RL 的过拟合形态与单轮不同：单轮过拟合表现为对训练算子的终态 kernel 记忆，多轮过拟合表现为对训练算子的**迭代路径**记忆——策略学会了“对这类形状先做 A 再做 B 再做 C”的固定套路，遇到形状分布外的算子时，套路的第一步就失效，后续轮次全在错误路径上修补。因此 held-out 评估不能只看终态性能，还要看迭代效率：在 held-out 算子上达到同等性能所需的轮次数。

评估插入点在训练循环里是周期性的，但评估本身要跑完整的多轮 rollout，成本与训练 rollout 同量级。工程上通常用较小的 held-out 集合加较短的 T 上限来做快速评估，只在关键节点跑完整 T。代价是评估吞吐直接挤占训练吞吐，且 held-out 算子的编译/计时同样受真实硬件限制，无法并行化到与训练完全重叠。一个具体例子：训练集覆盖多种形状的 layernorm，held-out 放一个形状分布外的 group norm；若策略学到的是“按行归约”的固定套路，在 group norm 上首轮就会因归约维度错误而编译失败，迭代效率评估立刻暴露过拟合，而终态性能评估可能因后续轮次的盲目修补而给出误导性的中等分数。

这里有一个工程判断：held-out 评估的频率应与 α、γ 的调参节奏绑定。每次调整奖励权重后必须重跑 held-out，因为权重变化会改变策略的迭代路径偏好，旧的泛化结论不再成立。把评估当作调参的伴随动作而非独立阶段，是多轮 RL 工程流水线里容易被省略但代价高昂的一环。

六 · 单轮成本核算：每一步的时延、带宽、显存与 token 账

把一次多轮 rollout 的成本拆到步骤级别，才能判断训练吞吐的瓶颈在哪。编译步骤是 CPU 侧串行，单次编译的时延由源码规模与模板实例化深度决定，CUDA C++ 的重模板 kernel 编译时延可达秒级，Triton 的 JIT 相对轻但仍有固定开销；这一步不占 GPU，却卡住整条流水线的推进节奏。正确性步骤占 GPU 但访存量小，主要成本是 oracle 的参考实现执行与误差比对。计时步骤是 GPU 独占且需要多次重复取中位数，单轮计时占用的 GPU 时间与 kernel 本身的时延成正比，对慢 kernel 而言这一项会显著拉长 rollout。归一化步骤是纯 CPU 的算术，成本可忽略。

token 账集中在状态压缩上：每轮输入的状态包含代码文本与诊断摘要，输出是完整源码。若不做压缩，第 t 轮的输入 token 数随 t 线性增长，整条轨迹的 token 总量随 T 平方增长；压缩后近似线性。显存账集中在旧策略对数概率的保存上，逐时间步保存使显存随 T 线性增长，这是长轨迹训练的主要显存压力来源。带宽账在计时步骤：多次重复计时意味着同一份输入被反复读入，对访存密集型 kernel 而言，计时过程本身的带宽占用与 kernel 运行带宽同量级，若与训练的其他 GPU 任务共享设备，计时精度会被干扰。

一个具体例子可以把这个账算清：一个 T=4 的轨迹，编译四次（其中两次失败，失败编译的时延通常短于成功编译，因为模板实例化在中途终止）、正确性执行两次（失败轮次跳过）、计时两次（仅正确性通过的轮次计时）、状态压缩四次。整条轨迹的 GPU 时间主要由两次计时构成，CPU 时间主要由四次编译构成，两者无法重叠——因为下一轮的输入依赖上一轮的编译与计时结果。这种严格串行的依赖链是多轮 RL 训练吞吐的根本约束，也是为什么多轮 rollout 的 GPU 时间与 token 成本远高于单轮：不是单步更贵，而是步与步之间没有并行空间。
