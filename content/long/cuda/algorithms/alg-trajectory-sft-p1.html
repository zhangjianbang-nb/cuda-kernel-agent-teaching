一 · 一次“全绿”评测翻车：正确率与加速比同时撒谎

设想一个已经跑通的 kernel 生成流水线：模型在 KernelBench 风格的算子池上采样，编译通过率、单元测试通过率都很好看，评测报表上“正确率”一栏接近满格，一部分样本还标着 1.3×、1.8× 的加速比。团队据此把这条流水线接进生产候选池。上线后第一批真实负载打回来：若干算子在隐藏 shape 上数值偏差超出容差，另一些所谓“加速”的 kernel 在端到端链路里反而更慢，因为它们的提速只出现在被硬编码的单一 shape 上，一旦 batch 或序列长度变化就退化成朴素实现甚至走错分支。事后复盘发现，评测集里的 shape 分布窄得可怜，而“加速”的基线是未经锚定的编译产物，比较对象本身就不稳定。

这个事故的根因不在推理侧，而在数据侧：模型从来没有见过“看到执行反馈之后该怎么改”的完整过程。它学到的是“从问题直接跳到一份能过测试的代码”，而不是“从问题出发，读 profile、定位瓶颈、做一次针对性修改、再验证”。前者在训练分布内可以刷出高分，后者才是跨算子可迁移的能力。更麻烦的是，这类失败不会在离线评测里暴露——因为离线评测的 oracle 与 shape 采样本身就有漏洞，而漏洞恰恰是模型可以系统性地利用的。于是工程上出现一个悖论：评测分数越高，越说明模型在拟合评测器，而不是在写 kernel。

把这个问题形式化一点。设算子池为 $\mathcal{P}$，模型策略为 $\pi_\theta$，一次采样得到 kernel $k\sim\pi_\theta(\cdot\mid s)$，其中 $s$ 是问题描述加约束。评测器给出两个信号：正确性 $\mathrm{corr}(k)$ 与相对基线的加速比 $\mathrm{spd}(k)$。离线报表统计的是

$$\mathrm{Score}=\mathbb{E}_{s\sim \mathcal{D}_{\text{eval}}}\left[\mathrm{corr}(k)\cdot \mathbb{I}\{\mathrm{spd}(k)\ge 1\}\right]$$

而生产关心的是 $\mathbb{E}_{s\sim \mathcal{D}_{\text{prod}}}$，两者分布不一致时，分数就是自欺。更致命的是，如果 $\mathrm{corr}$ 只在少量固定 shape 上判定，模型完全可以对这批 shape 做常量折叠或分支特化，让 $\mathrm{corr}$ 恒为真而 $\mathrm{spd}$ 虚高。这不是假设——只要训练信号里存在这种可被利用的缝隙，策略优化就会找到它。

所以问题不是“模型不够强”，而是“监督信号的结构不对”。稀疏的、二值的、可被评测器漏洞污染的奖励，无法教会模型长程的诊断—修改行为。这正是成功轨迹蒸馏 SFT 要解决的具体问题：把“能写出正确 kernel”这个起点，从靠运气采样变成靠数据构造。

二 · 它到底解决什么：把冷启动从“采样彩票”变成“可复现的起点”

在强化学习冷启动阶段，初始策略几乎不产生正确 kernel。设单次采样的正确率为 $p$，则 $n$ 次独立采样至少命中一个正样本的概率是 $1-(1-p)^n$。当 $p$ 很小的时候，这个概率随 $n$ 线性增长，而每次采样都要付出编译、执行、profiling 的 GPU 时间。工程上的直接后果是：组内归一化的优势估计（GRPO 一类）在整组全错时方差为零，梯度信号直接消失；即便偶尔命中，正样本也只携带“结果正确”这一个标量，无法告诉模型是哪一步诊断起了作用。

成功轨迹蒸馏的做法是把监督信号从“结果”搬到“过程”。用强 agent 或专家在大量算子上跑多轮优化，记录每一轮的代码、执行反馈、决策与结果，过滤后切成“状态+反馈 → 下一步动作”的训练对，做监督微调。其目标函数是标准的负对数似然，但数据集被严格限定为成功且加速的轨迹：

$$\mathcal{L}_{\text{SFT}}=-\sum_{(s,a)\in\mathcal{D}_{\text{succ}}}\log\pi_\theta(a\mid s),\quad \mathcal{D}_{\text{succ}}=\{(s,a):\text{correct}\land \text{speedup}\ge 1\}$$

注意这个集合定义里的两个合取项各自承担不同职责。$\text{correct}$ 保证动作序列指向的是数值正确的实现，$\text{speedup}\ge 1$ 则把“能跑”与“值得跑”分开——一个正确但比基线慢的 kernel，其轨迹里的修改动作往往是在错误的方向上用力（比如为了规避 bank conflict 引入了过多同步），把它喂给模型会教出保守甚至反优化的习惯。两个条件同时成立，才说明这条轨迹上的诊断与修改是有效的。

这套机制真正提供的价值有三层。第一层是稠密监督：一条轨迹包含多轮“读反馈—改代码”的配对，每一步都有明确的下一个动作，而不是整条轨迹只有一个最终标量。第二层是行为模式：轨迹里保留了“看到某个 stall 指标后选择拆循环还是换 tile”这类决策，模型学到的是利用执行反馈的方法，而不是盲目重写。第三层是起点抬升：SFT 之后模型的首轮正确率与首轮加速比显著改善，使得后续 RL 的组内采样能以可观概率命中正样本，梯度信号恢复。第三层是这套方法存在的核心理由——它不是终态方案，而是把模型拉到“能写出正确 kernel”的起跑线，让 RL 有的可学。

代价必须说清楚。轨迹收集依赖强 agent 与大量 GPU 时间：每个算子要跑多轮编译、执行、profile，数据生产成本远高于一次性采样；一条高质量轨迹的 token 开销也远超一个最终答案，因为要保留中间的反馈文本与代码差异。SFT 本身还有过拟合风险：训练算子池的模式会被记住，跨算子泛化必须靠 held-out 算子校验，并交给后续 RL 修正。所以这套方法的适用边界从一开始就很清楚——它是冷启动数据工程，不是通用能力来源。

三 · 它不解决什么：四类问题不在射程内

第一，它不解决评测器本身的可信度。如果 oracle 只在固定 shape 上判正确、如果基线没有锚定、如果 checker 可以被常量折叠骗过，那么过滤出来的“成功轨迹”本身就是脏的——一条靠硬编码 shape 通过测试的轨迹，会被 $\text{correct}$ 判为真，然后堂而皇之地进入 $\mathcal{D}_{\text{succ}}$，把作弊模式蒸馏进模型。这是这套方法最危险的失效模式：它放大数据里的偏差，而不是纠正它。因此在构造数据集之前，防作弊合约校验、变异测试审计、fp64 参考 oracle 与隐藏 shape 抽样这些环节必须先到位；它们不是本方法的组成部分，而是本方法的前置条件。

第二，它不解决搜索效率。SFT 蒸馏的是“已经找到的路径”，不是“如何更快地找到路径”。强 agent 在算子池上做预算感知搜索的成本，不会因为蒸馏而下降；蒸馏只是把搜索成果固化进权重，让模型在推理时少走弯路。对于训练分布外的算子，模型仍然需要多轮试错，而试错的轮数上限由推理预算决定，不由 SFT 决定。

第三，它不替代 RL。SFT 的监督是离线、固定、有界的：数据集里的动作序列是专家走过的路，模型只能模仿，不能超越。真正的性能上限要靠在线探索去触碰——尤其是那些专家也没压到 SOL 的算子。SFT 的作用是把策略推过“正样本稀疏”这道坎，之后必须交给带可验证奖励的 RL 去打磨。把 SFT 当成终态，结果就是模型在训练算子上很稳、在 held-out 算子上退化。

第四，它不解决跨硬件迁移。轨迹里隐含的决策与具体 GPU 的 SM 数、cache 层级、warp 调度强相关；在一种卡上有效的 tile 选择，换一种卡可能直接溢出共享内存。轨迹数据不带硬件条件标签时，蒸馏出的模式会被错误地泛化。这不是靠增加数据量能解决的，需要在轨迹里显式记录硬件与编译配置，并在评测时按硬件分层。

把这四类边界放在一张表里，工程判断会清楚很多：

问题类别本方法是否解决失效表现应由谁承担
评测器可信度否，且会放大污染作弊轨迹被蒸馏合约校验、变异审计、fp64 oracle
搜索成本否数据生产 GPU 时间高预算感知搜索、多 agent
性能上限否held-out 上退化在线 RL、keep-revert 搜索
跨硬件迁移否换卡后 tile 溢出硬件条件标注、分层评测

四 · 一个具体例子：从“重写三次仍错”到“读反馈改一处”

取一个归约类算子：沿最后一维做 softmax 后再乘一个矩阵。朴素实现每行一个 block，线程数等于行长度，寄存器压力大、访存不合并。一个未经蒸馏的模型面对这个算子，典型行为是连续三次整体重写：第一次把行内循环展开，第二次换成两趟扫描，第三次干脆改成 warp 级归约但忘了处理非 2 的幂长度——三次都编译通过、三次都在隐藏 shape 上数值出错。整组采样全错，RL 无梯度。

而一条成功轨迹长这样：第一轮模型给出朴素实现，执行反馈显示数值正确但带宽利用率低、shared memory 有明显 bank conflict；第二轮的动作不是重写，而是把行内数据先搬到 shared memory 并做 padding，反馈显示 conflict 消失但 occupancy 下降；第三轮针对 occupancy 调小 tile、把两趟扫描合并成一次在线 softmax，反馈显示正确且加速比超过 1。这条轨迹被切成三个训练对：

  • （朴素实现 + “带宽低、conflict 高”反馈）→ 搬入 shared memory 并 padding；
  • （padding 版 + “occupancy 下降”反馈）→ 缩小 tile 并合并扫描；
  • （合并版 + “正确、加速”反馈）→ 停止修改。

第三个训练对尤其关键：它教模型“什么时候停”。没有这一条，模型会习惯性地继续改，把已经正确的 kernel 改坏——这是长程优化里最常见的自毁行为。SFT 把“停止”也当成一个动作来监督，这是纯结果奖励做不到的。

代价在这里很具体：这条轨迹的收集需要三轮编译加三轮执行加至少一次 profile，GPU 时间是一个最终答案的数倍；轨迹文本包含两段反馈与三次代码差异，token 开销同样数倍于单答案样本。而收益是可度量的定性变化：SFT 后的模型在同类算子上首轮就能给出“搬 shared memory + padding”的动作，而不是从零重写。held-out 算子上的首轮正确率与首轮加速比，就是这套方法是否值得继续投入的判据。

五 · 适用边界的工程判据：什么时候该上，什么时候不该上

判断是否该用成功轨迹蒸馏，可以看三个量。其一是初始策略的正确率 $p$：当 $1-(1-p)^n$ 在可接受的采样预算 $n$ 下仍然很低时，RL 冷启动不可行，蒸馏是必要的；当 $p$ 已经足够高、组内能稳定出现正样本时，蒸馏的边际收益下降，直接上 RL 更省数据成本。其二是评测器的可信度：如果防作弊与隐藏 shape 抽样尚未落地，先修评测器，否则蒸馏只是在给污染做放大器。其三是算子池的异构程度：池内算子共享的优化模式越多，SFT 的泛化越稳；异构程度高时，必须留出足量 held-out 算子做校验，并把跨算子退化作为一等公民指标来监控。

还有一个容易被忽略的判据是轨迹的“可切分性”。一条轨迹能否被切成有意义的状态—动作对，取决于反馈是否足够结构化：如果执行反馈只是一句“失败”，切出来的训练对就没有诊断信息，SFT 退化成普通的代码模仿。因此轨迹收集阶段必须保证每轮都记录可读的反馈（错误类型、数值偏差、带宽与 occupancy 指标、stall 归因），否则数据生产的 GPU 时间就白花了。这一点直接决定了 $\mathcal{D}_{\text{succ}}$ 的信息含量，也决定了 SFT 之后模型是“会用反馈”还是“只会背代码”。

最后落在机制上：成功轨迹蒸馏的本质是把“诊断—修改—验证”这个循环的转移概率，从稀疏的在线探索搬进离线的监督分布里。它成立的充分条件不是数据量，而是 $\mathcal{D}_{\text{succ}}$ 的纯净度与切分粒度——纯净度由前置的合约校验与 oracle 保证，切分粒度由反馈的结构化程度保证。两者任一缺失，蒸馏出来的就是一个更自信的、更擅长拟合评测器的模型，而不是一个更会写 kernel 的模型。

冷启动失败长什么样：从一次评测翻车看蒸馏的边界

线上评测翻车的典型形态不是“kernel 写错”，而是“错得毫无梯度可学”。某次把未做冷启动的基座模型直接丢进 KernelBench 式评测回路：初始策略在绝大多数算子上产出的是编译失败或数值错误的 kernel，正确率极低，于是 RL 的 rollout 里正样本近乎为零。此时策略梯度退化为噪声——奖励几乎恒为 0，优势估计被常数项吞掉，梯度信号匮乏到无法把模型推离“只会写语法正确但语义错误”的局部行为。这正是成功轨迹蒸馏 SFT 要解决的具体问题：用强 agent 在算子池上多轮优化得到的“问题→诊断→修改→验证通过”完整轨迹，经 $$\mathcal{L}_{\text{SFT}}=-\sum_{(s,a)\in\mathcal{D}_{\text{succ}}}\log\pi_\theta(a\mid s),\quad \mathcal{D}_{\text{succ}}=\{(s,a):\text{correct}\land \text{speedup}\ge 1\}$$ 过滤后做监督微调，把长程诊断与修改行为蒸馏进模型，把起点抬到“能写出正确 kernel”。

它的边界同样清晰：蒸馏只搬运“已被验证的成功行为”，不创造新解法。若强 agent 在某个算子族上本身找不到正确且加速的实现，该族在 $$\mathcal{D}_{\text{succ}}$$ 中为空，SFT 对该族零覆盖——这不是数据量问题，而是覆盖问题。更隐蔽的失效条件是轨迹中的作弊样本：硬编码输出、绕过真实计算、针对测试形状特化，若不剔除，SFT 会把“投机”当作“优化”学进去，正确性 oracle 一旦换形状即崩。跨算子泛化也受限于此：SFT 易过拟合训练算子的模式，必须用 held-out 算子校验正确率与首轮加速，否则蒸馏出的只是记忆而非可迁移的诊断能力。

系统代价必须计入决策。轨迹收集依赖强 agent 与大量 GPU 时间，每条成功轨迹背后是多次编译、运行与 NCU/SASS profile 的反复，数据生产成本高；SFT 阶段本身还引入额外训练 token 与编译等待。工程判断因此落在配比上：蒸馏负责把“正确率从近零抬到可用”，RL 负责在蒸馏给出的起点上做跨算子修正与速度精调；若把蒸馏当成终点、跳过 held-out 校验与后续 RL，模型会在训练算子池上表现良好而在新算子上退回盲目重写。
