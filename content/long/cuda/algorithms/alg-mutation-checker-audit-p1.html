一 · 事故复盘：一个“通过”的错误 kernel 如何污染整条奖励管线

先看一个不涉及任何虚构数字的典型翻车链路。某团队用 KernelBench 风格的算子集做多轮 RL：策略网络采样出 Triton kernel，评测端用参考实现的输出做逐元素比对，容差取 atol=1e-2, rtol=1e-2，并且只比对输出的前若干行以控制显存。某一轮采样出的 kernel 在 reduction 维度上漏掉了最后一个 tile 的尾块——当形状不能被 tile 整除时，尾块元素直接保留为未初始化值。这个 kernel 在绝大多数“整齐”形状上完全正确，在少数非整齐形状上错得很离谱，但由于比对只覆盖前若干行、且这些行恰好落在被正确处理的区间内，checker 判定通过。于是这个 kernel 拿到了与正确 kernel 相同量级的奖励，被 keep 进策略池，后续若干轮采样持续围绕它做变异，把“漏尾块”这一缺陷固化成策略的默认写法。等到人工抽查发现时，已经积累了一批在真实形状上不可用的候选。

这条链路的要害不在 kernel 写错——采样出错是 RL 的常态，正是要靠奖励信号把它筛掉。要害在于 checker 本身被当成了不可质疑的 oracle。奖励管线里每一个环节都被审计过：TF32/编译基线锚定保证计时可比，隐藏 shape 分布抽样保证泛化不被过拟合，防作弊合约校验拦截硬编码输出，Fuzz+fp64 参考 oracle 处理数值路径。唯独“checker 能不能抓住错误”这件事，长期停留在“我们相信它是对的”这一层。变异测试审计要解决的正是这个具体问题：把 checker 从假设正确变成可度量，用一组人为构造的、已知错误的 kernel 去攻击 checker，统计它抓到了多少。

需要立刻划清的边界是：这个方法不验证参考实现本身的正确性（那是 fp64 oracle 与形式化验证的职责），不度量 kernel 的性能或 roofline 位置（那是 SOL 归一评分的职责），不检测策略是否在作弊（那是合约校验的职责）。它只回答一个问题：给定一个 checker，当被测 kernel 确实错了，checker 判 Fail 的概率有多大，以及漏掉的是哪一类错。

二 · 形式化：kill rate 作为 checker 的可度量属性

把 checker 记作一个从 kernel 输出到 {Pass, Fail} 的判定函数。变异测试的做法是构造变异体集合 $$\mathcal{M}$$，其中每个 $$m$$ 是由参考实现经一次受控扰动得到的、语义上确定错误的 kernel。对每个变异体跑一遍 checker，记录判定结果，得到：

$$\text{KillRate}=\frac{|\{m\in\mathcal{M}: \text{Checker}(m)=\text{Fail}\}|}{|\mathcal{M}|},\quad \text{CheckerOK}=\mathbb{1}[\text{KillRate}\ge \kappa]$$

这里的 $$\kappa$$ 是准入阈值，事实给出的工程口径是 95%。这个式子的结构值得注意：它是一个比率而不是布尔量，因此天然支持分组报告。把 $$\mathcal{M}$$ 按变异算子类型划分——边界条件翻转、累加顺序打乱、dtype 截断、索引偏移 ±1——对每个子集分别算 kill rate，就能区分“checker 整体还行但某一类错全漏”和“checker 整体均匀地弱”。前者是覆盖问题（比对范围没到边界），后者是容差问题（阈值太松）。这个区分直接决定修补方向：覆盖问题要扩比对范围或加形状采样，容差问题要收紧 atol/rtol 或换用相对误差范数。

公式里隐含一个代价：$$\mathcal{M}$$ 的规模决定统计分辨率。若只有 20 个变异体，一个漏检就让 kill rate 掉 5 个百分点，阈值 95% 意味着一个都不能漏，这在统计上过于苛刻且对变异体构造质量极度敏感。事实给出的常用规模是 50–200 个变异体，此时单次漏检的影响落在 0.5%–2% 区间，阈值判定才有意义。代价是评测成本随 $$|\mathcal{M}|$$ 线性增长：每个变异体都要完整跑一遍 checker，包括 kernel 编译、启动、输出搬运与比对。若 checker 单次运行含编译在内是秒级，200 个变异体就是分钟级的固定开销，且这笔开销要在每次 checker 修改后重跑——它不是一次性投入，而是随 checker 演化的持续税。

三 · 变异算子库：从参考 kernel 生成“确定错误”的样本

变异体的构造质量决定 kill rate 的可信度。核心要求是每个变异体语义上确定错误，不能出现“改了但恰好等价”的变异——等价变异体会被 checker 正确判 Pass，却计入分母拉低 kill rate，造成虚警。事实给出的四类算子各有明确的错误语义：

  • 边界条件翻转：把 i < N 改成 i <= N 或把尾块处理分支删掉，制造越界读或漏算尾部元素。这类错误在整齐形状上不可见，专门攻击 checker 的形状覆盖。
  • 累加顺序打乱：在 reduction 中交换两个部分和的累加次序，或把树形归约改成线性归约。浮点加法不满足结合律，结果在最低有效位上不同；若 checker 容差过松，这类变异体全部存活。
  • dtype 截断：把中间累加器从 fp32 降到 fp16 或 bf16，制造精度损失。这类变异体专门探测 checker 是否真的在做数值比对，而不是只看形状和 dtype。
  • 索引偏移 ±1：把全局索引加一或减一，制造整体错位。这是最容易被抓住的一类，通常 kill rate 接近满分，因此它在分组报告里的价值是作为对照组——如果连索引偏移都抓不住，说明 checker 的比对逻辑本身有结构性缺陷，而非容差问题。

构造这些变异体需要领域知识：要知道参考 kernel 的哪些行是边界处理、哪些是归约核心、哪些是类型转换点。自动化的通用变异器（随机改一个运算符）会产生大量等价变异体和编译失败的变异体，前者污染分母，后者浪费评测预算。因此变异算子库必须按算子族定制并持续扩充——这是该方法最重的人力成本，也是 kill rate 虚高的主要来源：若算子库只覆盖索引偏移这类“好抓”的错误，kill rate 会漂亮但毫无信息量。

四 · 一个具体例子：尾块漏算为何能穿过三道防线

回到第一节的事故，把 checker 的三道典型防线逐一拆开看，就能看清 kill rate 分组报告的实际用法。假设参考 kernel 是一个行归约，输入形状 [M, N]，N 不保证是 tile 的整数倍。

第一道防线是容差。checker 用 atol=1e-2 比对。对于 fp32 归约，正常实现的相对误差在 1e-6 量级，1e-2 的绝对容差意味着只要输出量级不超过 1e2，任何精度类错误都不会被抓住。用 dtype 截断变异体去测，kill rate 会很低——这不是因为 checker 逻辑错，而是容差比错误信号的量级大了四个数量级。修补方向明确：收紧容差或改用相对误差。

第二道防线是比对范围。checker 只比对前若干行以省显存。尾块漏算影响的是 N 方向上的最后一段列，若比对按行切片且切片恰好避开了受影响的列区间，变异体存活。用边界翻转变异体去测，kill rate 低，且分组报告显示“边界类全漏、索引类全抓”，直接指向覆盖问题而非容差问题。

第三道防线是形状采样。若 checker 只在整齐形状上跑，尾块路径根本不被执行，任何针对尾块的变异体都无法被触发——此时变异体本身跑出来的输出与参考一致（因为参考在该形状下也没走尾块路径），变异体退化为等价变异体。这是最隐蔽的一种失效：kill rate 被等价变异体拉低，看起来像 checker 弱，实际是变异体构造没对准形状分布。这正是隐藏 shape 分布抽样要解决的问题，变异测试必须与它联动——变异体的输入形状要覆盖非整齐维度，否则测的是空气。

三件事叠加，一个在真实形状上不可用的 kernel 就穿过了全部防线。分组 kill rate 报告的价值在于：它不会只给一个“checker 得分 0.6”的笼统结论，而是给出“边界类 0.2、精度类 0.3、索引类 1.0”的剖面，让工程师一眼看出该修容差还是该修覆盖。

五 · 适用边界：什么时候这个方法不适用，以及它的失效模式

变异测试审计的适用前提是：存在一个可执行的参考实现，且变异体能够被确定地判定为错误。这排除了两类场景。其一，参考实现本身可疑——若参考实现有 bug，由它派生的变异体可能“错得和参考一样”，checker 判 Pass 反而是正确的，kill rate 失去意义。这类场景要先走 fp64 参考 oracle 或形式化验证把参考钉死，变异测试才有地基。其二，输出语义无法逐元素比对的任务——例如输出是排序后的集合、或是经过不可微后处理的统计量，此时“确定错误”难以构造，变异体与等价变异的界限模糊。

该方法自身的失效模式有三条，工程上必须显式管理。第一，算子库覆盖不全导致 kill rate 虚高：只测好抓的错误，分数漂亮但预测不了真实采样分布里的错误类型。缓解手段是让变异算子库跟随线上翻车案例扩充——每抓到一个穿过的错误 kernel，就把它抽象成一个新变异算子加进库，这条反馈回路比任何静态阈值都重要。第二，等价变异体污染分母：需要人工复核低 kill rate 的变异体，区分“checker 漏检”与“变异体其实等价”，后者应从集合中剔除而非计入漏检。第三，阈值 $$\kappa$$ 的刚性：95% 是一个工程口径而非普适常数，对数值敏感型算子（长链归约、低精度累加）可能需要更严，对离散输出型算子可以放宽；把 $$\kappa$$ 写死成全局常量会让审计失去分辨力。

还有一条成本边界值得单独指出：变异测试度量的是 checker 的检错能力，不是 checker 的误杀率。一个把容差收到极紧的 checker 可以让 kill rate 逼近 1.0，代价是把正确 kernel 也大量判 Fail，直接摧毁 RL 奖励信号的可用性。因此 kill rate 必须与正确 kernel 的通过率配对报告——只报 kill rate 的审计是半张报表，会诱导工程师把 checker 越调越紧直到奖励管线失效。这个配对约束是本方法进入奖励管线的前置条件：只有 kill rate ≥ 阈值且参考实现在同一 checker 下稳定 Pass 的 checker，才允许被挂到 RL 奖励计算上。

六 · 为什么必须前置：审计发生在奖励管线之前而非之后

把变异测试放在奖励管线的哪个位置，决定了它的工程价值。若放在管线之后、作为离线质量报告，它只能事后解释“为什么这一轮训崩了”，无法阻止污染。正确的位置是前置门禁：checker 每次修改（调容差、改比对范围、加形状采样）都必须重跑变异审计，kill rate 达标才允许上线。这条规则把 checker 的演化纳入了与 kernel 相同的可验证框架——checker 也是一个需要被测试的软件制品，只不过它的测试用例是变异体而非普通输入。

前置带来的直接代价是评测预算的重新分配。事实给出的 50–200 个变异体、每个跑一遍 checker 的线性成本，意味着每次 checker 变更都要付出分钟级的固定开销，且这笔开销发生在任何 RL 训练开始之前。工程判断是：这笔钱必须花，因为它的替代方案是让一个有漏洞的 checker 在数百轮训练中持续发放错误奖励，后者的代价是整批候选 kernel 的报废与策略的固化污染，量级远高于分钟级审计。真正需要优化的是变异体的执行效率——变异体与参考实现共享编译产物、批量提交、复用输入缓冲，把单变异体成本压到编译一次、启动多次的量级，而不是削减变异体数量。削减数量会直接损失统计分辨率与分组报告的粒度，是把审计做成形式主义的典型做法。

最后落在机制上：变异审计的输出不是一个通过/不通过的布尔值，而是一份按变异类型分组的 kill rate 剖面加一份人工复核记录。这份剖面进入 checker 的版本管理，与 checker 代码同仓同审。当某个算子族的边界类 kill rate 低于阈值时，门禁拒绝该 checker 版本进入奖励管线，工程师必须补充覆盖或收紧容差后重跑。这条闭环让“checker 是否可信”从口头承诺变成可 diff、可回滚、可追责的工程制品。

当 checker 自己就是被测对象：kill rate 能兜住什么、兜不住什么

这个方法要回答的问题很窄：benchmark 的正确性 checker 本身有多大检错能力。线上翻车往往不是 kernel 写错，而是 checker 放过了错的 kernel——容差设得过松，把 fp16 截断误差和真正的累加错误一起吞掉；只比对输出的前若干行或某个切片，漏掉边界列；只覆盖规整形状，对非对齐尾块视而不见。这类漏洞在奖励管线里的后果是灾难性的：错误 kernel 拿到正奖励，RL 把“骗过 checker”学成策略，训练越久偏移越远。于是有了可度量的口径：

$$\text{KillRate}=\frac{|\{m\in\mathcal{M}: \text{Checker}(m)=\text{Fail}\}|}{|\mathcal{M}|},\quad \text{CheckerOK}=\mathbb{1}[\text{KillRate}\ge \kappa]$$

机制上是从参考 kernel 生成变异体集合：边界条件翻转、累加顺序打乱、dtype 截断、索引偏移 ±1，逐个喂给 checker 并记录是否被判定为错误，再按变异类型分组报告漏检类别。分组是关键——若索引偏移类全部漏检，说明覆盖范围有洞；若 dtype 截断类全部漏检，说明容差过松。修补方向由此确定，而不是凭感觉调 tolerance。只有 kill rate 达到阈值（如 95%）的 checker 才允许进入奖励管线，这一步把“假设 checker 正确”换成了“checker 必须自证”。

边界同样清晰。变异体构造依赖领域知识，算子库覆盖不全时 kill rate 会虚高——没注入的缺陷类型自然杀不掉也测不出，指标看起来漂亮但毫无意义，因此变异算子库需要持续扩充，这本身是一项长期维护成本。评测成本随变异体数量线性增长，通常需 50–200 个变异体，每个都要跑一遍 checker，在长输出、多形状的 kernel 上单轮审计的时延与显存占用不可忽略；若 checker 自身含参考实现比对，等于把参考 kernel 再执行一遍。它也不解决 checker 与参考实现同源同错的问题：变异体由参考实现派生，参考实现若在某条路径上本就写错，变异体与 checker 会一起错、一起放过，kill rate 对此完全失明，需要独立的正确性 oracle 或形式化手段兜底。工程判断是：kill rate 是奖励管线的准入门槛而非正确性证明，阈值卡在 95% 意味着仍有约 5% 的变异体漏检，这部分必须靠人工复核漏检样本、按类型补算子来收敛，而不是靠调高 κ 掩盖。
