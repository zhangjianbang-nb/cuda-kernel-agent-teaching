一 · 一次评测翻车：线性重试把预算烧在了退化分支上

设想一个典型的评测现场：团队拿 KernelBench 风格的任务集跑一个单轮 kernel 生成 agent，基线是朴素实现，目标是拿到可部署的加速版。单轮成功率低，于是最自然的工程反应是“多试几次”——同一个 prompt 采样 N 次，取计时最快的那个。这个策略在评测里表现为一条漂亮的曲线：采样数从 4 涨到 32，pass@k 单调上升。但把它放到真实预算约束下，问题立刻暴露：线性重试没有记忆。第 7 次采样和第 23 次采样之间没有任何信息传递，agent 不知道哪些修改方向已经被证明会退化，也不知道哪些参数组合曾经接近过正确性门。

更糟的是 reward 的分布形状。用 $$R_i=\frac{T_{\text{base}}}{T_{\text{gen}}}\cdot\mathbb{1}[\text{Correct}]$$ 做单点奖励时，绝大多数采样落在 $$\mathbb{1}[\text{Correct}]=0$$ 上，reward 恒为零，梯度信号消失；少数正确样本里，speedup 的方差又极大——同一个 tile 配置在不同 shape 上可能差出数倍。线性重试在这种稀疏且高方差的奖励面上等价于盲采样，采样数翻倍只带来边际收益递减，而每一次采样都要付出完整的正确性门加计时成本。评测翻车的具体形态是：预算耗尽时最优 kernel 仍停留在“能跑但不快”的朴素实现附近，而中间那些“差一点就对”的修改路径全部被丢弃，没有任何机制把它们捡回来。

这就是 keep-revert 搜索要解决的第一个具体问题：把无记忆的重复采样，换成有记忆的树状搜索。每次 kernel 修改是一个树节点，keep/revert 是边的剪枝决策，搜索过程本身携带“哪些动作曾经有效、哪些曾经退化”的先验。它不解决的是：如果正确性 oracle 本身不可信，或者 reward 归一化被作弊合约污染，树搜索只会更快地收敛到一个错误的最优点——这两件事分别由合约校验与变异测试审计、Roofline/SOL 归一评分承担，本方法假定它们已经就位。

二 · 设计空间的结构性盲区：为什么“多试”不等于“搜到”

kernel 的设计空间不是一维的。tile 大小、split-K 切分、向量化宽度、unroll 因子、shared memory swizzle、流水级数，这些维度彼此耦合：把 tile 从 64 提到 128 可能让 shared memory 占用翻倍从而限制 occupancy，而同时把 split-K 从 1 提到 4 又能把 occupancy 拉回来。线性重试在这种耦合面上做的是独立采样，命中“两个维度同时调对”的概率是各自命中率的乘积，随维度数指数衰减。

树搜索的价值在于它把这个乘积结构展开成一条路径。根节点是参考实现或朴素 kernel，每个子节点是一次具体修改动作，从根到叶的一条路径就是一组协同的配置。UCT 选择公式 $$\text{UCT}(s,a)=Q(s,a)+c\sqrt{\frac{\ln N(s)}{N(s,a)}}$$ 中，第一项 $$Q(s,a)=\frac{1}{N(s,a)}\sum_{i}R_i$$ 是利用项，把预算压向历史上 reward 高的分支；第二项是探索项，随父节点访问数增长而对未访问子节点加权。这个结构让“先调 tile 再调 split-K”成为一条可回溯的路径，而不是两次独立掷骰。

但这里必须说清适用边界：动作空间是人工设计的。未纳入动作空间的修改——最典型的是 CuTe layout 层面的重排、以及 PTX 内联汇编级别的指令选择——根本无法被搜索到。这不是调参问题，是结构性盲区：搜索算法再聪明，也只能在给定的动作集合内做组合。工程判断是，动作空间的设计粒度决定了这个方法的天花板，粒度太粗（只允许“调 tile”）会漏掉跨层协同，粒度太细（允许任意代码改写）会让单节点成本失控并且正确性门通过率骤降。一个可操作的折中是分层动作空间：粗粒度动作负责结构性决策（是否 split-K、是否向量化），细粒度动作只在粗粒度分支被 keep 之后展开。

三 · 单节点成本：为什么必须剪枝而不是穷举

每个树节点都要完整跑一遍正确性门与计时。给定事实给出的量级是单节点约 1–5 GPU 分钟，预算 100 节点即 2–8 GPU 小时。这个成本结构直接决定了算法形态：任何“先把整棵树展开再评估”的方案在预算上不可行，搜索必须是增量的、按需展开的。

keep/revert 剪枝的经济学就在这里。设一个分支在深度 d 处被判定退化，若不剪枝，该分支下所有潜在子节点（假设分支因子为 b）都要各自付出 1–5 GPU 分钟；剪枝后只付出了一个节点的成本就把它整条子树排除。更关键的是 revert 不只是丢弃，它还要降低该动作的先验——这样同一父节点下的其他子节点在后续 UCT 计算中获得相对更高的探索权重，预算被重新导向未被证伪的方向。这是一个带反馈的剪枝，而不是静态的黑名单。

代价的另一面是搜索成本的可控性依赖预算截断而非收敛判据。达到轮次或 GPU 小时上限就输出最优路径上的 kernel 与修改序列，这意味着结果质量与预算强相关，且不同任务的最优预算不可预知。工程上必须把预算当作一等公民来设计：节点成本高的任务（大 shape、需要多轮编译）应配更小的分支因子和更激进的剪枝阈值，否则预算会在前几个分支上耗尽，树还没长出形状。

四 · 一个具体例子：split-K 分支上的 keep 与 revert

取一个 reduction 类 kernel：朴素实现单 block 串行归约，正确但远低于带宽上限。根节点即此实现。动作空间包含 tile 大小、unroll、split-K、swizzle、向量宽度五类。第一轮 UCT 因所有子节点访问数为零而近似均匀探索，agent 生成“split-K=4”子节点：正确性门通过，计时显示 speedup 明显改善，reward 归一化后回传，该节点 $$N(s,a)$$ 加一、$$Q(s,a)$$ 抬升。keep。

第二轮利用项把预算压向这个分支，agent 在其下尝试“split-K=4 且 tile=128”。这次正确性门通过但计时退化——shared memory 占用上升压低了 occupancy，split-K 带来的并行度被抵消。revert 到父节点，同时降低“增大 tile”这一动作在该父节点下的先验。第三轮探索项把预算导向同父节点下未被访问的“向量宽度=4”子节点，命中改善，keep 并继续扩展。最终输出的最优路径是“split-K=4 → 向量宽度=4”，中间那条 tile 分支只花了一个节点的成本就被排除。

这个例子里可以读出方法的能力边界：它找到的是一组在动作空间内可表达的协同配置。如果真正的瓶颈在于该 reduction 需要 CuTe 层面的 layout 重排才能把访存模式对齐到 128B 事务，那么无论树搜索多充分都碰不到——因为“重排 layout”不在动作集合里。此时正确做法不是加大预算，而是扩充动作空间并接受单节点成本上升，或者承认该方法不适用、转用其他手段。这是本方法最重要的一条工程判断：搜索算法的收益上限由动作空间决定，预算只决定你多接近这个上限。

五 · 它不解决什么：三类必须挡在门外的失败模式

第一类，正确性 oracle 不可信。树搜索的 keep 决策建立在正确性门之上，若门本身漏判（例如只比对少量随机输入、未覆盖边界 shape），搜索会稳定地 keep 住一个数值错误的 kernel，并且因为 reward 高而反复扩展它。这类失败比线性重试更危险，因为树搜索的“记忆”会把错误固化成一个被反复利用的分支。防线在 Fuzz 加 fp64 参考 oracle 与变异测试审计 checker，本方法只负责在门可信的前提下做搜索。

第二类，reward 归一化被污染。若计时基线被锚定在编译产物而非参考实现上，或者归一化口径随节点漂移，$$R_i$$ 就失去可比性，UCT 的 $$Q(s,a)$$ 变成噪声的平均。TF32/编译基线锚定与 Roofline/SOL 归一评分是这条防线的位置，本方法假定 reward 在整棵树内同口径。

第三类，shape 分布偏移。树搜索在一个固定的评测 shape 集合上做 keep/revert，若真实部署的 shape 分布与评测集不同，被 keep 的配置可能在新 shape 上退化。隐藏 shape 分布抽样与 Batch 不变性门处理这个问题；本方法能做的是把 shape 作为节点上下文的一部分记录，使同一配置在不同 shape 下的 reward 不被混算，但它不负责生成有代表性的 shape 分布。

这三类失败模式的共同结构是：它们都发生在搜索循环之外，却决定了搜索循环的输出是否可信。把 keep-revert 搜索当成一个独立组件来部署，而不先确认这三道门在位，是工程上最常见的误用。

六 · 适用边界的正面刻画：什么时候值得上树

反过来刻画适用条件更有利于工程决策。第一，任务存在可分解的修改路径：从朴素实现到目标实现之间，存在一串每次只改一两个维度的中间态，且每个中间态都能通过正确性门。若最优实现相对于朴素实现是“整体重写”而非“逐步演进”，树搜索的路径结构就失去意义。第二，单节点成本与预算匹配：1–5 GPU 分钟乘以预期节点数必须落在可接受预算内，否则应先用更便宜的静态分析缩小动作空间。第三，动作空间能覆盖主要瓶颈维度：先用 NCU 指标回灌与 SASS/warp stall 剖析定位瓶颈属于哪一类（访存、occupancy、指令吞吐），再据此设计动作空间，而不是拍脑袋列一张参数表。

在这些条件满足时，给定事实给出的收益量级是：在 KernelOPT/EvoEngineer 类任务中，同预算下树搜索的最终 speedup 比线性重试高 1.2–1.8×。这个区间的下沿对应动作空间较粗、单节点成本较高的场景，上沿对应动作空间与瓶颈维度对齐良好的场景。收益来源不是搜索算法本身的魔力，而是 keep/revert 把预算从退化分支上挪走、把“差一点就对”的中间态保留为可继续扩展的节点——这正是线性重试结构上做不到的事。

最后落到一个机制判断上：keep-revert 搜索的正确用法是把它当作预算分配器而非答案生成器。它不产生新的 kernel 设计，只决定在给定的动作集合里，哪些修改值得继续投入 GPU 分钟。因此动作空间的设计、正确性门的强度、reward 口径的统一，这三件事的工程优先级都高于调 UCT 的探索常数 $$c$$。把这三件事做对之后，树搜索的边际收益才开始显现；做不对，树搜索只是把线性重试的错误更快地固化下来。

搜索能覆盖什么，不能覆盖什么：一次评测翻车划出的边界

线上事故的形态往往不是“kernel 算错”，而是“评测说它变快了”。某次推理服务的 prefill kernel 在评测流水线上拿到稳定的加速比，合入后线上吞吐反而下降：评测脚本用固定 shape 与固定 warmup 计时，而 agent 提交的修改把 tile 从 128 降到 64 并加了 split-K，恰好在该 shape 上把 occupancy 顶满；线上真实 batch 分布更宽，split-K 的 reduction 额外读写把 L2 压穿，端到端时延被拖长。这个案例暴露的不是 agent 不会写 kernel，而是搜索目标函数与部署目标之间的错位——而 keep-revert 树搜索恰恰是把这种错位放大而非消除的机制，因为它会沿着被错误 reward 认可的分支持续扩展。

该方法的适用边界由此可以写清楚：它解决的是“在离散、可组合、可快速验证的修改空间里，用有限预算做有记忆的全局搜索”这一问题。把每次修改视为树节点，用 $$\text{UCT}(s,a)=Q(s,a)+c\sqrt{\frac{\ln N(s)}{N(s,a)}}$$ 在“利用高 reward 分支”与“探索未访问修改”之间分配预算，reward 取 $$R_i=\frac{T_{\text{base}}}{T_{\text{gen}}}\cdot\mathbb{1}[\text{Correct}]$$，keep/revert 则是对退化边的剪枝。它不解决的是：reward 本身不可信时的目标错配、动作空间之外的设计（未纳入动作表的 CuTe layout 或自定义 swizzle 根本无法被访问）、以及跨 shape 的泛化——树搜索只在被计时的那些 shape 上做选择，没有任何机制强制它对新 shape 保持稳健。

系统代价决定了边界的实际位置。每个节点都要完整跑正确性门与计时，单节点成本约 1–5 GPU 分钟，100 节点预算即 2–8 GPU 小时；这意味着搜索深度天然被预算截断，长链条修改（例如先改 layout 再改 pipeline 阶段数）在浅预算下几乎不可能被组合出来。更隐蔽的代价是动作空间的人工设计成本：动作表越窄，搜索越省，但结构性盲区越大；动作表越宽，单节点验证成本与组合爆炸同时上升。工程判断是：只有当 reward 与线上目标同构（同一 shape 分布、同一计时口径、同一正确性 oracle），且关键设计维度已进入动作表时，keep-revert 搜索才值得投入；否则它会把预算精确地花在一个错误的局部最优上。
