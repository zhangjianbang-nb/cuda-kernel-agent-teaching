一 · 负载画像：什么样的模型/算子/shape 才配得上端到端门

端到端回归门不是对所有候选 kernel 一视同仁的关卡，它必须先回答“这条负载值不值得进这个门”。判断依据不是 kernel 写得多漂亮，而是该算子在真实 trace 里的三个量：调用频次、单次时延占端到端时延的比例、以及它与前后算子的耦合度。频次高、占比大、耦合松的算子，端到端收益最容易穿透 Amdahl 稀释；反之，单次只占端到端千分之几、又被前后算子强制同步的算子，微基准再快也几乎不可能跨过阈值。

具体机制上，负载画像从真实推理/训练 trace 中提取热点算子及其调用上下文：shape、layout、dtype、前后算子是谁、是否处在融合链的中间。这里的关键判据是“可替换性”——候选 kernel 能否在保持接口与内存布局一致的前提下插回原位。若前后算子依赖特定的 stride 或对齐假设，替换就会引入隐式 layout 转换，端到端反而变慢。一个典型例子是 attention 前的 transpose+contiguous：单独看这个 copy kernel 很慢，但把它“优化掉”意味着下游 kernel 要接受非连续输入，端到端时延可能不降反升。因此负载筛选阶段就要把这类“看似热点、实则被布局绑定”的算子标记为不适合单独替换。

shape 维度上，端到端门偏好的是在真实分布下有稳定调用形态的算子：decode 阶段的 batch×1 小 shape、prefill 阶段的长序列、以及训练里的固定 micro-batch。隐藏 shape 抽样解决的是“候选是否泛化”，而负载画像解决的是“这个 shape 在端到端里是否真的被反复走到”。代价在于：为覆盖真实并发与多 batch，端到端 benchmark 的搭建成本高，需要真实模型、真实 trace 和可复现的输入管线；同时系统噪声要求多次重复取中位数，单次测量不可信。

$$\text{share}_o=\frac{\sum_{i\in\text{trace}} t_o^{(i)}}{T_{\text{e2e}}},\quad \text{gate-ready if }\ \text{share}_o\ge s_0\ \land\ \text{calls}_o\ge n_0$$

这条判据的作用是把“微基准加速但端到端无收益”的候选提前挡在门外，而不是等跑完端到端才发现收益被稀释。代价是阈值 s0、n0 设得过高会误拒真正有价值的融合型优化——融合往往把多个小算子的 share 合并后才够格，单算子视角会低估它。

二 · 基线选择：锚定谁，决定门是宽还是严

端到端门的基线不是“未优化的 PyTorch 原始实现”这么简单。基线选择直接决定阈值 θ 的物理含义：若基线是框架默认 kernel（含 cuBLAS/cuDNN 高度调优的实现），那么候选必须打败的是工业级库，门槛天然高；若基线是上一次合入的版本，门就变成增量回归检测，衡量的是“这一版相对上一版是否退步”。两种基线回答不同问题，混用会让收益符号失去意义。

工程上通常需要三层基线并存：库基线（判断候选是否具备替代库的资格）、版本基线（判断本次改动是否引入回归）、以及同候选的 CPU/参考实现（仅用于正确性，不参与性能比较）。版本基线必须与候选在同一硬件、同一驱动、同一 warmup 策略下测量，否则端到端时延的系统性偏移会被误读为 kernel 收益。一个具体例子：某候选在库基线下 gain 为正，但在版本基线下为负，说明上一版已经通过融合拿到了更大收益，此时候选应回退而不是合入——这正是回归门把“绝对加速”和“相对回归”分开的价值。

基线锚定的代价是测量预算：三层基线意味着端到端 benchmark 要跑三遍以上，加上多 batch、真实并发与重复取中位数，单轮门的墙钟时间显著上升。若把基线缓存为固定快照，又会因硬件/驱动漂移而失效，需要定期重锚。指标计算上，端到端收益用下式，且必须与正确性检查同轮完成，避免“性能过了、数值错了”的候选溜进生产。

$$\text{gain}_{\text{e2e}}=\frac{T_{\text{base}}^{\text{e2e}}-T_{\text{gen}}^{\text{e2e}}}{T_{\text{base}}^{\text{e2e}}},\quad \text{merge if }\ \text{gain}_{\text{e2e}}\ge \theta\ \land\ \text{maxerr}\le\epsilon$$

θ 的取值必须与基线层级绑定：库基线对应较高的 θ，版本基线对应接近零甚至略负的 θ（允许噪声内的持平）。把两套 θ 混用，等于让门在“打败库”和“不退步”之间反复横跳，候选的合入决策失去可复现性。

三 · 输入分布：真实 trace 采样而非均匀随机

端到端门的输入分布必须来自真实 trace 的采样，而不是均匀随机张量。原因在于 kernel 的端到端行为对输入分布高度敏感：稀疏激活、变长序列、batch 内 padding 比例、以及数值范围都会改变分支走向、访存模式和实际占用。均匀随机输入会让候选落在一条“平均路径”上，掩盖真实负载里最慢的那条分支。一个具体例子是变长 attention：均匀随机长度采样出的平均序列长度，与真实 trace 里长尾分布的中位数差异巨大，前者测出的端到端时延系统性偏乐观。

机制上，输入分布设定要固定三件事：shape 采样分布（从 trace 统计出的频次加权）、数值分布（真实激活的统计特性，含极端值）、以及调用序列（前后算子与并发模式）。这三者共同构成“评测配方”，配方一旦固定就应版本化，任何候选都在同一配方下比较，否则跨候选的 gain 不可比。代价是配方构建需要 trace 解析与统计管线，且配方越贴近真实，benchmark 的方差越大——长尾 shape 会拉高单次测量的抖动，必须靠重复次数与中位数压制。

正确性侧的输入分布同样不能省：maxerr 检查必须在真实数值分布上做，而不是全 1 或全 0 的玩具张量。玩具张量会让数值误差被结构性掩盖，例如归约顺序改变在均匀输入下误差极小，在长尾激活下却可能放大。因此输入分布与正确性 oracle 是同一份配方的一体两面，配方不对，性能与正确性两侧同时失真。

四 · 指标计算：时延、吞吐、显存三线并行

端到端门的指标不是单一数字，而是时延、吞吐、显存三条线同时记录，任何一条劣化都构成回归。时延取端到端墙钟时间的中位数（含 warmup 后的稳态），吞吐取单位时间完成的请求数，显存取峰值分配与峰值驻留。三者之间存在结构性权衡：候选通过增大 workspace 换取更少的分支与更好的合并访存，时延降了但显存升了；在显存受限的部署形态下，这种候选即使 gain 为正也应被门拦下，因为它在真实并发下会触发 OOM 或迫使 batch 缩小，端到端吞吐反而下降。

指标计算的伪代码思路是：先跑 warmup 丢弃首轮编译与缓存效应，再跑 N 轮取中位数与分位数，同时记录每轮的显存峰值；正确性检查在同一批输入上跑参考实现对比 maxerr。这里的关键是 warmup 必须覆盖候选的首次 launch 与可能的 JIT/编译开销——Triton 候选的首次编译时间若不计入 warmup，会被误算进稳态时延，导致 gain 被系统性低估；反之若把编译时间算进端到端，又会误杀本身运行时很快的候选。代价是编译时间这一项在小算子场景下可能超过 kernel 本身的时延，门必须明确“稳态时延”与“含编译首启时延”是两个指标，分别对应不同部署形态。

噪声控制是指标计算里最容易被忽视的代价：端到端 benchmark 受系统噪声影响，单次测量不可信，必须多次重复取中位数，并对 gain 给出置信区间而非点估计。若 gain 的点估计刚过 θ 而区间跨过 θ，门应判为不确定并回退，而不是赌一把合入。一个具体例子是 decode 阶段的小 kernel：其端到端时延被 launch 开销主导，重复测量的方差可能大于候选本身的收益，此时候选应被判为“不可测”，转入策略池等待更大粒度的融合机会。

五 · 负载不对时会发生什么：三类典型失真

第一类是 Amdahl 稀释导致的误拒。小算子优化在微基准上加速显著，但端到端占比低，gain 低于 θ 被回退。这不是门的缺陷，而是负载画像阶段 share 判据没提前拦截的结果——正确的做法是在画像阶段就把这类算子标记为“需与相邻算子合并评估”，而不是让它在端到端门里反复被拒、消耗测量预算。误拒的代价是策略池里堆积大量“微基准赢家、端到端输家”的候选，搜索方向被误导。

第二类是布局不匹配导致的假加速。候选在独立 benchmark 里用连续输入跑得很快，插回模型后前后算子产出非连续张量，隐式 copy 把收益吃掉甚至反转。这类失真的根源是评测配方没有固定 layout 上下文，只测了 kernel 本身。防它的机制是在配方里显式记录输入 stride 与对齐，候选替换时必须声明其 layout 假设，门在插入前做一次 layout 兼容性检查，不兼容直接判失败并记录原因。

第三类是基线漂移导致的假回归。硬件频率、驱动版本、后台负载变化会让版本基线的端到端时延整体偏移，候选的 gain 符号随之翻转。这类失真的代价最隐蔽：它让门在“合入”与“回退”之间产生不可复现的抖动，同一候选在不同时间跑出相反结论。对策是把基线测量与候选测量交错进行（A/B 交错而非先后串行），并在同一时段内完成对比，把系统性漂移抵消掉。

  • 误拒：share 判据前置，避免小算子反复消耗端到端预算。
  • 假加速：配方固定 layout 上下文，插入前做兼容性检查。
  • 假回归：基线与候选交错测量，抵消系统性漂移。

六 · 配方版本化与失败原因回灌

评测配方本身必须版本化，与候选、基线、硬件指纹一起构成一次门判定的完整记录。没有版本化的配方，gain 的跨轮比较失去意义：上一轮用均匀随机输入测出的正收益，这一轮换成 trace 采样后可能变成负的，而门无法区分这是候选退步还是配方变更。版本化的最小粒度是“shape 采样分布 + 数值分布 + 调用序列 + warmup 策略 + 重复次数”五元组，任一项变更即视为新配方，旧的门判定不可直接复用。

失败原因回灌是配方闭环的另一半：每次回退都要把失败类型（Amdahl 稀释、layout 不兼容、基线漂移、正确性 maxerr 超限、显存超限）结构化写入策略池，供后续搜索阶段读取。这样端到端门不只是合入闸机，还是搜索的负样本来源——被拒的候选携带“为什么被拒”的标签，下一轮生成可以据此避开同类形态。代价是策略池需要维护失败标签的语义一致性，标签定义漂移会让回灌数据失去训练价值。

工程判断上，端到端门的配方应偏向“窄而深”而非“宽而浅”：宁可覆盖少量真实高频负载并把每条负载的 layout、数值、并发都钉死，也不要用大量合成 shape 铺开覆盖面。因为端到端收益的本质是部署收益，部署收益只在真实负载上成立；合成 shape 上的端到端数字再漂亮，也无法回答“这条 kernel 插进生产模型会不会变慢”。配方越窄，单条负载的测量预算越充足，重复次数与交错测量才跑得动，gain 的置信区间才收得紧。

端到端门的适用边界：负载配方决定它是否可信

端到端回归门的判别力完全由负载配方决定，配方错了，门就变成噪声放大器。适配面是“热点算子占据可观端到端占比”的模型：Transformer 的 attention、norm、elementwise 融合链，以及训练侧的反向 reduce、优化器 step 这类在真实 trace 中反复出现且 shape 稳定的算子。不适配的是端到端占比被 Amdahl 定律压到阈值以下的场景——小算子即便微基准翻倍，$$\text{gain}_{\text{e2e}}=\frac{T_{\text{base}}^{\text{e2e}}-T_{\text{gen}}^{\text{e2e}}}{T_{\text{base}}^{\text{e2e}}}$$仍可能低于 θ 而被误拒；此时应改用“算子占比 × 微基准收益”的预估门，或把多个同链算子打包成一次替换再测。硬件侧要求基线 kernel 与候选 kernel 在同一 SM 架构、同一显存带宽档位下比较，跨代对比会把架构红利误记为生成收益。

基线选择与输入分布是配方里最容易出错的两处。基线必须是真实模型当前部署的那份实现（含框架自带 kernel、已有手写 kernel），而非朴素 PyTorch 参考实现，否则门会把“框架开销”算成生成收益。输入分布要覆盖真实 trace 的 shape 直方图：长尾小 batch、变长序列、非对齐 hidden 维、非连续 layout 都要进配方，因为候选 kernel 常在对齐 shape 上快、在尾部长尾上因 launch 开销与分支发散而慢。配方应固定 warmup 次数、多 batch 档位与并发度，并对每个档位重复采样取分位数而非均值，抑制系统噪声。

负载不对时的失效形态是可枚举的。其一，只测单 batch 单 shape，候选 kernel 的 launch 开销被摊薄，端到端收益虚高；其二，输入 layout 与模型实际不符（如把非连续张量先 contiguous 再喂），测出的时延不含布局转换代价，合入后真实链路反而变慢；其三，基线用了未融合的参考实现，融合机会被重复计入收益。下表给出配方要素与失效后果的对应：

配方要素错误设定失效后果
batch/shape仅单档对齐 shapelaunch 开销被低估，收益虚高
layout预先 contiguous漏算布局转换，合入后端到端变慢
基线朴素参考实现框架开销误记为生成收益
采样单次均值噪声淹没小于 θ 的真实收益

系统代价落在搭建与运行两侧：真实模型与 trace 的采集、候选 kernel 的接口对齐与插桩、多档位多轮重复 benchmark，都是持续的工程开销；端到端跑一次远贵于微基准，配方越全，回归门单次判定时延与显存占用越高，还会挤占 GPU 资源影响并发测试的稳定性。因此配方应按算子占比分层：高占比算子走全档位端到端门，低占比算子走预估门加抽样端到端抽检，把 $$\text{merge if }\ \text{gain}_{\text{e2e}}\ge \theta\ \land\ \text{maxerr}\le\epsilon$$ 的判定成本压在收益最可能兑现的那部分负载上。
