一 · 事故现场：三份互相矛盾的“优化建议”

设想一次典型的评测翻车：一个 7B 级别的 agent 在 KernelBench 风格的题上被要求优化一个 LayerNorm+残差融合 kernel。单 agent 模式下，它读 profile、读源码、写代码、自己调参，四件事挤在一个上下文里。第一轮它判断瓶颈在访存，于是把 tile 调大；第二轮它又觉得瓶颈在寄存器压力，把 tile 调小；第三轮它干脆同时改了 tile、改了向量化宽度、加了 __launch_bounds__，代码跑出来的正确性没问题，但延迟比基线还差。评测脚本只看到“正确但更慢”，于是记为失败——但失败的原因不是它不会写 CUDA，而是它从未把“为什么这么改”写下来，导致每一轮的判断都无法被下一轮继承，也无法被任何人审计。

把同样的任务拆成三个 agent，问题不会自动消失，只会换个形态。分析 agent 说“瓶颈是 L2 带宽，应该做 tile 分块并提高每线程的复用”；编码 agent 理解成“把 block 从 256 改成 512”；评审 agent 拿不到分析 agent 的原始结论，只能看代码，于是它评审的是“代码是否像一段合理的 CUDA”，而不是“代码是否实现了被声明的优化动作”。三个 agent 各自都做了合理的事，合起来却是一次语义漂移：意图在传递过程中丢失，且丢失不可见。这就是本方法要解决的具体问题——不是“单 agent 不够聪明”，而是多 agent 之间缺少一个可被机械校验的共享表示。

代价是可直接度量的：多 agent 串行调用使单轮延迟增加 2–4×，token 消耗约为单 agent 的 3–5 倍。也就是说，如果没有共享表示，多 agent 不仅没换来更好的 kernel，还额外付出了 3–5 倍的 token 和 2–4 倍的墙钟时间，去生产三份互相矛盾的结论。这个代价本身就是引入策略 IR 的直接动机：既然协同的成本已经付出，就必须让协同的产物可追溯、可校验。

二 · 形式化：IR 是什么，冲突是什么

策略 IR 被定义为一个四元组：

$$\text{IR}=\langle \text{Bound},\ \mathcal{A}_{\text{cand}},\ \mathcal{C}_{\text{res}},\ \text{reward}\rangle,\quad \text{Conflict}=\mathbb{1}\left[\exists a\in\mathcal{A}:\ \text{Code}(a)\not\equiv\text{IR}(a)\right]$$

四个字段各有明确职责。Bound 是瓶颈分类（访存受限、计算受限、延迟受限、同步受限等），它决定了后续动作的搜索方向；𝒜_cand 是候选优化动作列表，每个动作是一个有名字、有参数的离散对象，例如“沿 K 维做 32 宽的 tile 分块”“对输出做 4 元素向量化写”“把中间结果放进共享内存并加一次 __syncthreads”；𝒞_res 是资源约束，典型的是寄存器上限与共享内存上限，它把动作限制在硬件可承受的范围内；reward 是执行 agent 回填的实测结果，包含正确性判定与计时。

冲突指示函数 Conflict 是本方法的核心可计算量：对候选动作集合中的每一个动作 a，比较代码中实际实现的行为 Code(a) 与 IR 中声明的行为 IR(a)，只要存在一处不等价，冲突即为 1。注意这里的“等价”不是指代码文本相同，而是指参数级的行为对应——IR 声明“tile 宽 32”，代码里就必须能找到对应维度的 32；IR 声明“共享内存不超过 48KB”，代码的静态共享内存声明就必须落在约束内。这使得评审 agent 的工作从“读代码判断好坏”退化为“逐条比对声明与实现”，是一个可以写成检查表的机械过程。

这个形式化带来的直接收益是可审计性：任何一次打回都附带具体差异标注（哪个动作未实现、哪个参数越界），而不是一句“这段代码不够好”。代价则体现在 schema 的设计成本上——Bound 的枚举、𝒜_cand 的动作词汇表、𝒞_res 的约束表达，都需要人工设计并随任务演进；schema 不覆盖的动作根本无法表达，于是新优化手法要么被强行塞进旧动作，要么被静默丢弃。这是本方法最真实的边界：IR 的表达力上限就是多 agent 协同的上限。

三 · 机制：黑板式协同的四个角色

IR 在系统中扮演共享黑板的角色，四个角色围绕它形成单向可追溯的链路。分析 agent 读 profile 与源码，写出 Bound、𝒜_cand、𝒞_res；编码 agent 只读 IR，按 𝒜_cand 中的每个动作生成对应的 Triton/CUDA/CuTe 代码，IR 中的每个动作必须映射到代码中的具体参数；评审 agent 按 IR 逐条校验代码是否实现了声明的动作，未实现则打回并标注差异；执行 agent 跑正确性 oracle 与计时，把结果写回 reward 字段。调度器读 reward 与冲突检测结果，决定下一轮由哪个角色主导——冲突为 1 时优先回给编码 agent 修实现，reward 无改善时回给分析 agent 换 Bound 或换动作。

伪代码层面的调度逻辑可以写成：

  • 若 Conflict == 1：本轮不计 reward，把差异标注附在 IR 上打回编码 agent，禁止分析 agent 改 Bound（防止用换方向掩盖实现错误）。
  • 若 Conflict == 0 且 reward 改善：接受该 IR 为新基线，允许分析 agent 在同一 Bound 下追加动作。
  • 若 Conflict == 0 且 reward 未改善：判定该 Bound 下的动作空间已耗尽，交回分析 agent 重做瓶颈分类。

这套规则的关键在于把“策略错误”和“实现错误”分开处置。单 agent 无法做这个区分，因为它既是被审判者又是审判者；多 agent 若无 IR，评审 agent 也没有比对基准，只能凭感觉。IR 让这个区分变成一个布尔量。

性能代价在这里具体化为两处。其一是串行链路：分析→编码→评审→执行四段依次进行，单轮延迟增加 2–4×，且评审与执行无法与编码重叠（评审必须等代码落地）。其二是 token：分析 agent 要读 profile 与源码、编码 agent 要读完整 IR 并生成代码、评审 agent 要读 IR 与代码做逐条比对，三段上下文叠加使 token 消耗达到单 agent 的 3–5 倍。一个具体例子：对前述 LayerNorm 融合 kernel，单 agent 一轮约消耗一份源码加一份 profile 的上下文；IR 模式下，分析 agent 产出含 3 个候选动作与 2 条资源约束的 IR，编码 agent 需读这份 IR 加源码，评审 agent 需读 IR 加生成代码，三段上下文互不共享前缀，缓存命中率下降，实际计费 token 显著上升。

四 · 解耦红利：同一 IR 喂不同后端

策略与代码解耦后，同一个 IR 可以被不同编码 agent 复用。这是本方法区别于“把 prompt 拆细”的地方：拆 prompt 只是把一段话分成几段，IR 则是把意图固化成结构化对象，使得 Triton 编码 agent、CUDA 编码 agent、CuTe 编码 agent 可以读同一份 𝒜_cand 与 𝒞_res，各自生成符合自身抽象层次的实现。Astra、cuPilot 这类框架可以直接接入：它们需要的正是一个“声明式中间层”，把上层的优化决策与下层的代码生成分开。

复用带来的收益是可比较性。当同一 IR 被三个后端分别实现时，评审 agent 对三份代码做的是同一套比对，执行 agent 回填的是同一 reward 字段，于是“Triton 实现是否比 CUDA 实现更接近 IR 声明”成为一个可回答的问题，而不是靠人读代码猜。代价是 IR 必须对后端保持中立：𝒜_cand 里的动作不能写成“插入 __syncthreads”这种 CUDA 专有表述，否则 Triton 后端无法映射；但写得太抽象（如“提高数据复用”）又无法被机械校验。这个张力是 schema 设计的核心难点，也是扩展成本高的根源。

一个具体例子：IR 声明“对 K 维做 32 宽分块，每线程复用 4 个元素，共享内存不超过 48KB”。CUDA 后端把它映射为 block 内 32 线程沿 K 维、每线程 4 次加载加一次同步；Triton 后端把它映射为 BLOCK_K=32 加循环内累加。评审 agent 对两者做的是同一检查：K 维分块宽度是否为 32、每线程元素数是否为 4、共享内存声明是否越界。若 Triton 实现里 BLOCK_K 被写成 64，冲突指示函数直接置 1，打回并标注“K 维分块宽度声明 32、实现 64”。这个标注不需要评审 agent 理解 Triton 语义，只需要它读参数。

五 · 不解决什么：三条明确的边界

第一条边界是 schema 覆盖不到的动作。IR 只能表达 𝒜_cand 词汇表里已有的动作。若某个 kernel 的最优解依赖于一个尚未被纳入词汇表的手法——比如某种特定的 warp 级 reduce 重排、某种非标准的 bank 冲突规避布局——分析 agent 无法把它写进 IR，编码 agent 也就不会去实现它。系统不会报错，只会安静地收敛到一个“IR 可表达范围内的较优解”。这是比崩溃更危险的失败模式：它看起来在工作，只是永远够不到那部分性能。扩展成本高正体现在这里：每纳入一个新动作，都要同步更新分析 agent 的产出格式、编码 agent 的映射规则、评审 agent 的比对逻辑，三处一致才算真正支持。

第二条边界是正确性本身。IR 的冲突检测只保证“代码实现了声明的动作”，不保证“实现是对的”。一个 tile 分块动作被正确实现，但边界处理写错，冲突仍为 0，错误由执行 agent 的正确性 oracle 捕获——而 oracle 的强度是另一条独立防线（fp64 参考、变异测试审计等）。IR 不能替代 oracle，它只保证意图与实现的一致性，不保证实现与数学定义的一致性。把这两件事混为一谈，会让评审 agent 误以为自己承担了正确性职责。

第三条边界是搜索效率。IR 让协同可追溯，但不让搜索变快。调度器按 reward 与冲突决定主导角色，本质仍是一个串行的提议-校验循环，单轮延迟 2–4× 的代价不会因为 IR 而消失。IR 换来的不是更少的轮数，而是每一轮的结论都可被继承、可被审计。若任务本身只需要一两轮微调，IR 的 schema 设计与多 agent 编排开销很可能超过收益；这类任务应当留在单 agent 路径上。

一个具体例子说明第一条边界的代价：某 kernel 的瓶颈被分析 agent 正确判为延迟受限，但最优手法是重排 warp 内归约顺序以减少 stall，而 𝒜_cand 里只有“增加 ILP”“改用共享内存归约”两个动作。系统会在两个动作间反复试探，reward 停在某个平台期，调度器判定“动作空间耗尽”并回给分析 agent 重做瓶颈分类——分析 agent 再次给出同样的 Bound，循环往复。整个循环的 token 消耗是单 agent 的 3–5 倍，产出的却是一个被 schema 天花板卡住的解。这不是调度器的错，是表达力的边界。

六 · 工程判断：什么时候值得上 IR

判断标准可以落在一个比值上：IR 的固定成本（schema 设计、四个角色的编排、每轮 2–4× 延迟与 3–5× token）对比它换来的收益（语义漂移消除、冲突可机械检测、同一 IR 跨后端复用）。收益在两种情形下明显占优。其一是任务需要多轮迭代且每轮的优化意图必须被继承——此时没有 IR，上一轮的判断在下一轮就蒸发了，多 agent 只是在重复分析。其二是同一策略需要在多个后端上落地并比较——此时 IR 是唯一能让比较成立的中立层。

反过来，两种情形应当明确不上 IR。任务只需单轮生成、无调优需求时，多 agent 编排的固定成本无法摊薄；任务的优化手法超出 𝒜_cand 词汇表且短期内不打算扩展 schema 时，IR 只会把系统锁在一个安静的天花板下。后一种情形尤其需要警惕：它不会以失败的形式暴露，只会以“reward 曲线提前走平”的形式暴露，而走平的原因可能被误判为模型能力不足。

落到具体机制上，一个可操作的工程判断是：先测量冲突率，再决定是否扩 schema。在已有任务集上跑一轮，统计 Conflict 为 1 的比例。若冲突率低而 reward 走平，问题在表达力而非协同，应当扩 𝒜_cand；若冲突率高，问题在实现与声明的对齐，应当加强评审 agent 的比对粒度而不是加动作。这个测量本身只需要 IR 已经存在——也就是说，IR 的第一份价值不是提升性能，而是把“协同失败发生在哪一层”变成一个可观测的量。这正是它相对于“把 prompt 拆细”的根本区别：拆 prompt 只改变信息流向，IR 让信息流向的正确性可被计数。

策略 IR 的适用边界：它挡得住语义漂移，挡不住 schema 之外的世界

这套协同机制真正解决的问题只有一个：多 agent 在没有共享表示时产生的语义漂移。典型翻车场景是评测侧的“假通过”——分析 agent 判定瓶颈在共享内存 bank conflict，建议把 tile 从 32×32 改成 64×16 并加 padding；编码 agent 只落实了 tile 尺寸、漏掉 padding；评审 agent 因为没有可对照的中间表示，只能凭代码“看起来合理”放行；执行 agent 跑出的正确性用例恰好不触发冲突路径，计时还略有改善，于是这一轮被记为成功并进入 reward。三轮之后策略库被污染，后续所有基于该 reward 的调度都在放大一个从未被实现的优化动作。冲突检测式把这类事故变成可判定的：

$$\text{IR}=\langle \text{Bound},\ \mathcal{A}_{\text{cand}},\ \mathcal{C}_{\text{res}},\ \text{reward}\rangle,\quad \text{Conflict}=\mathbb{1}\left[\exists a\in\mathcal{A}:\ \text{Code}(a)\not\equiv\text{IR}(a)\right]$$

它的边界由 schema 画定。IR 只能表达 Bound、候选动作集、资源约束与 reward 四类字段，凡是无法归入这四类的意图——比如“这条 kernel 应该改写成 persistent 形式以复用 warp”“这个算子应当整体换算法而非调 tile”——都落在表达范围之外。这类动作要么被分析 agent 硬塞进候选动作列表而丢失语义，要么被静默丢弃，评审 agent 也就无从校验。扩展 schema 是人工成本：每新增一类动作，要同时改分析端的输出约束、编码端的参数映射表、评审端的等价性判定规则，三处不同步就会引入新的漏检。因此该方案适用于动作空间可枚举、约束可量化的调优型任务（tile 尺寸、流水深度、向量化宽度、寄存器/共享内存上限），不适用于算法级重构与跨算子融合这类动作空间开放的场景。

系统代价同样构成适用边界。多 agent 串行调用使单轮延迟增加 2–4×，token 消耗约为单 agent 的 3–5 倍；当任务本身只需一次轻量调参时，IR 的构造、校验与回写开销超过收益。更隐蔽的代价在调度侧：调度器依据 reward 与冲突标志决定下一轮主导 agent，一旦 reward 字段被错误写入（例如计时噪声导致的假提升），冲突检测只能发现“代码未实现 IR”，发现不了“IR 本身选错了动作”。所以这套机制的可信度上限等于分析 agent 的瓶颈判定质量，IR 只是把判定结果显式化并使其可追溯，并不替代判定本身。
