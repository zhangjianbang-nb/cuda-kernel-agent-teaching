一 · 从瓶颈诊断到策略候选：proposer 的输入契约

在四角色流水线里，proposer 不是自由发挥的“点子生成器”，它的输出质量被输入契约严格约束。一次调用的输入由三部分组成：历史策略池（成功策略条目 + 失败教训条目）、当前瓶颈诊断（profiler 上一轮输出的归因结论，含 NCU 指标切片与 SASS stall 分布摘要）、以及当前 kernel 的结构摘要（grid/block 维度、每线程工作量、共享内存用量、寄存器压力）。输出是 1–3 个候选策略，每个策略必须携带三样东西：一句可执行的动作描述（如“沿 K 维做 split-K，配 atomic 累加”）、预期改善的瓶颈类别（访存/计算/同步/占用率之一）、以及该策略与历史失败条目的冲突检查结果。

这个契约的关键在于“策略必须可被 coder 无歧义地翻译成代码”。因此 proposer 的输出粒度被刻意限制在结构性变换层面——split-K、双缓冲、向量化宽度、warp 级归约方式、occupancy 目标——而不是“让它更快”这类无法落地的意图。冲突检查是廉价但有效的过滤：若候选策略与失败教训条目语义相近（同一瓶颈类别、同一变换、同一失败归因），proposer 必须显式说明为何本次条件不同，否则该候选被 critic 直接丢弃。

代价在这里首次显形：proposer 单次调用的 token 开销由策略池长度主导。策略池随轮次线性增长，若不做摘要压缩，第 N 轮的上下文成本近似为 O(N) 条目的拼接，长程迭代中 token 预算被历史文本吃掉的比例会持续上升。工程上的做法是给策略池设容量上限并对条目做结构化摘要（瓶颈类别 + 变换 + 结果三元组），把每条压缩到固定长度，使 proposer 的输入成本与轮次解耦。一个具体例子：当 profiler 归因为“全局访存受限、L2 命中率低、stall 集中在 long scoreboard”时，proposer 提出的候选应是提高数据复用（分块 + 共享内存暂存）或改变访问粒度（向量化到 128 位），而不是盲目加大 occupancy——后者与归因不匹配，冲突检查阶段即被拦下。

二 · 策略到源码：coder 的编译-验证闭环

coder 接收单个策略（通常一次只处理一个候选，以保证归因清晰），执行四步：定位修改点、生成或改写源码、编译、跑正确性 oracle。定位修改点依赖 kernel 结构摘要与策略动作描述的匹配——例如策略说“沿 K 维 split-K”，coder 需要找到归约循环的边界并插入跨 block 的累加路径。生成阶段不是从零写 kernel，而是在现有源码上做局部变换，这大幅降低了语法错误率，但也带来一个隐性风险：局部变换可能破坏原有的边界条件处理（如 tail 元素的掩码），因此正确性 oracle 必须在每次编译后无条件执行，而不是等 critic 阶段才跑。

编译与 oracle 的代价是这条流水线里最硬的墙。编译时间随 kernel 复杂度与模板实例化数量上升，CuTe/模板化写法尤其明显；oracle 的执行成本取决于测试用例规模——若 oracle 覆盖多组 shape 与边界条件，单次验证的 GPU 时间可能远超一次 kernel 实际运行。伪代码层面的调度逻辑是：

$$\text{for each } s \in \text{candidates}: \quad \text{src} \leftarrow \text{patch}(s); \quad \text{bin} \leftarrow \text{compile}(\text{src}); \quad \text{ok} \leftarrow \text{oracle}(\text{bin})$$

只有 ok 为真才进入 profiler 阶段，否则该候选连同编译错误或数值失配信息写回失败教训条目。这里有一个必须明确的工程判断：编译失败与数值失配应被区分记录，因为前者是 coder 的翻译缺陷（策略本身可能有效），后者是策略与当前实现的语义冲突。混为一谈会让 proposer 在下一轮错误地放弃有效策略。代价的另一个面是 token：coder 的输出是完整源码补丁，源码长度直接决定输出 token 量，长 kernel 的单轮成本可达数千 token；若一轮提出 3 个候选，成本近似三倍。因此预算紧张时应把候选数压到 1，用轮次换宽度。

三 · 指标采集与瓶颈归因：profiler 的降维职责

profiler 的输入是编译通过的二进制与一组固定 shape 的负载，输出是一份归因结论而非原始指标堆砌。采集内容包括 NCU 的吞吐类指标（DRAM 带宽利用率、SM 计算利用率、L2 命中率）、占用率相关指标（活跃 warp 数、寄存器与共享内存限制）、以及 SASS 层面的 stall 分布（long scoreboard、short scoreboard、barrier、MIO throttle 等）。归因的本质是降维：把几十个计数器压缩成一个主瓶颈类别加一两个次瓶颈，因为 proposer 只能消费有限宽度的诊断信息。

归因逻辑可以用一个加权的判据表达，其核心是比较各类资源利用率与理论上限的差距：

$$\text{bottleneck} = \arg\max_{c}\ \left( U_c^{\text{peak}} - U_c^{\text{measured}} \right) \cdot w_c$$

其中 c 遍历访存、计算、同步、占用率四类，w_c 是经验权重，用于抑制那些“差距大但不可改善”的类别（例如受算法固有访存比限制的带宽缺口）。这个公式不是精确科学，它的作用是给归因一个可复现的排序依据，避免 profiler 输出随机的、前后不一致的结论——一致性正是 critic 后续校验的对象。

代价有两层。第一层是采集本身：NCU 的细粒度采集需要多次重放 kernel，单次 profiling 的墙钟时间可达 kernel 实际运行的数十倍，若每轮对 3 个候选都做全量采集，预算会被测量吃掉。工程折中是先做一轮粗采集（少量关键指标、单次重放）筛掉明显无改善的候选，再对幸存者做细采集。第二层是归因失真：stall 分布是统计性的，采样窗口短时噪声大，profiler 可能把“barrier 等待”误判为同步瓶颈，而真实原因是 occupancy 过低导致 warp 不足以掩盖延迟。这类误判会通过诊断直接污染 proposer 的下一轮策略选择，因此 profiler 的输出必须附带置信说明（采样覆盖度、指标间是否自洽），供 critic 校验。

四 · 收益判定与记忆写入：critic 的裁决与代价核算

critic 接收三样输入：候选 kernel 的实测时延 T_t、当前基线最优时延 T_best、以及 profiler 的归因结论与置信说明。它的裁决依据是给定的奖励式：

$$\text{reward}_t=\mathbb{1}[\text{correct}]\cdot\left(\frac{T_{\text{best}}}{T_t}-1\right)-\lambda\cdot\text{tokens}_t,\quad \text{keep if }\ \text{reward}_t>\tau$$

这个式子的结构值得拆开看：正确性是乘性门，一旦 oracle 失败奖励直接归零，杜绝“用错误换速度”；速度项是相对基线的比值减一，因此只有当 T_t 严格小于 T_best 时才为正，持平即零收益；token 惩罚是线性的，直接对应多 agent 通信与上下文管理的开销。阈值 τ 的作用是设置保留门槛——微小提速不足以抵消 token 成本时不应保留，否则策略池会被噪声条目污染。

裁决有三种结果：保留（写入成功策略条目，更新 T_best）、回退（写入失败教训条目，注明失败归因）、合并（当候选策略与已有成功策略正交且可叠加时，标记为待组合，留待下一轮 proposer 提出组合策略）。合并这一支是双记忆机制的价值所在：单 agent 往往在获得一次提速后就停止探索正交方向，而策略池允许把“split-K 提升并行度”与“向量化降低访存指令数”两条独立收益叠加，其组合收益需要新一轮实测确认，不能假设线性相加。

代价核算在 critic 这里最集中。token 开销来自四角色的往返：proposer 的输入输出、coder 的源码补丁、profiler 的归因文本、critic 的裁决记录，单轮总量显著高于单 agent 的一次生成。这意味着在预算固定的条件下，多 agent 的轮次上限低于单 agent，其性价比只在“单 agent 已陷入局部最优、盲目试错成本高于协调成本”的场景成立。另一个代价是一致性校验的开销：critic 需要检查 profiler 归因与实测指标是否自洽（例如归因为访存受限但 DRAM 利用率并未接近峰值），这项检查本身消耗推理 token，却是阻断错误归因传导的必要环节。一个具体例子：某候选实测时延略优于基线但 token 消耗使 reward 落在 τ 之下，critic 判回退，并把“该变换在此 shape 下收益不足”写入失败教训，避免下一轮 proposer 重复提出。

五 · 记忆更新与下一轮起点：闭环的流动结构

一轮结束后，双记忆的写入是分流的结构化操作，而非简单追加。成功策略条目记录：瓶颈类别、变换动作、实测时延与基线比值、适用 shape 特征。失败教训条目记录：尝试的变换、失败类型（编译失败/数值失配/收益不足/归因不符）、以及失败时的瓶颈诊断快照。两条记忆的检索方式不同——proposer 读成功条目是为了找可复用的正交策略，读失败条目是为了做冲突检查；critic 读两者是为了判断新候选是否在重复已知失败。

下一轮 proposer 的输入因此是“更新后的策略池 + 上一轮 critic 的裁决摘要 + 当前 T_best 与 SOL 差距”。终止条件有两个：预算耗尽（token 或轮次上限）或收敛（连续若干轮无候选通过 τ 门槛，且策略池中无待合并条目）。收敛判定必须包含“待合并条目为空”这一条，否则会在仍有正交收益未探索时提前停止。

这条流动结构的性能代价体现在端到端时延上：一轮完整循环包含至少一次编译、一次 oracle、一次粗采集、一次细采集与四次模型调用，墙钟时间以分钟计，远高于单 agent 的单次生成。因此在生产端到端收益的语境下，多 agent 的适用判断不是“是否更快收敛”，而是“收敛后的 kernel 相对基线的提速是否足以摊薄协调开销”。当基线已接近 SOL、剩余提升空间小于 token 成本对应的阈值时，这条流水线的性价比为负，应退回单 agent 或直接人工调优。闭环的真正工程价值在于把“诊断—生成—验证”三段解耦后，每一段的失败都能被结构化记录并阻断重复，从而在长程预算下把试错从随机游走变成有记忆的搜索。

四角色流水线的边界条件：归因失真、预算坍缩与回退抖动

这套四角色流水线的有效性建立在一条隐含假设上：profiler 给出的瓶颈归因是可信的，且 proposer 能把它翻译成可执行的策略。一旦这条链路断裂，系统不是退化成一个慢一点的单 agent，而是退化成一个被错误诊断持续误导的多 agent——因为双记忆会把错误归因当成“教训”固化下来。典型失效场景是 profiler 把 L2 命中率下降归因为“访存瓶颈”，而真实原因是 occupancy 被寄存器压力压到很低、导致延迟隐藏失败；proposer 于是连续提出向量化与 split-K 类策略，coder 每轮编译通过、正确性 oracle 通过，但时延不动，critic 连续 revert，预算在无效轮次里烧光。这里的代价不是时延而是预算坍缩：单轮 token 成本高于单 agent，而有效轮次占比趋近于零。工程上的判据是给 profiler 的输出加一道可证伪约束——归因必须附带至少一个可观测的反事实指标（例如“若为访存瓶颈，则增大 split-K 后 DRAM 吞吐应上升”），critic 在 keep 之前校验该指标方向是否与归因一致，不一致则标记归因为“未定”，禁止写入成功策略池。

回退抖动是第二个边界。critic 的判定公式为

$$\text{reward}_t=\mathbb{1}[\text{correct}]\cdot\left(\frac{T_{\text{best}}}{T_t}-1\right)-\lambda\cdot\text{tokens}_t,\quad \text{keep if }\ \text{reward}_t>\tau$$

注意 $T_{\text{best}}$ 是历史最优而非上一轮，这使 reward 对“微小改进”极其敏感：当 $T_t$ 与 $T_{\text{best}}$ 接近时，比值项趋近于零，而 $\lambda\cdot\text{tokens}_t$ 是正的固定开销，于是任何一轮只要没有实质突破就必然落在 $\tau$ 之下被 revert。问题在于 $\tau$ 与 $\lambda$ 的标定依赖任务规模：小 kernel 上 tokens 开销占比高，$\tau$ 稍大便会让所有中间改进被丢弃，proposer 反复提出同一族策略，形成 keep/revert 抖动；大 kernel 上则相反，$\tau$ 过小会保留噪声级别的时延波动，污染 $T_{\text{best}}$。可操作的边界是让 $\tau$ 随 $T_{\text{best}}$ 的量级缩放，并把 tokens 惩罚改为按“本轮是否产生新诊断信息”折扣，而不是按绝对 token 数线性扣——否则 profiler 越啰嗦、诊断越详细，反而越容易被判为不划算。

第三个边界来自角色间信息传递的带宽本身。proposer 读的是策略池摘要与瓶颈诊断，coder 读的是策略文本，profiler 读的是 NCU 指标与 SASS stall 分布——每一跳都是一次有损压缩。SASS stall 分布维度高，若压缩成一句“同步开销大”，proposer 就无法区分是 barrier 密度问题还是 warp 调度问题，只能提出泛化的“减少同步”策略，coder 落地时往往改错位置。这里的代价是编译时间与验证轮次：每次 coder 修改都要走编译加正确性 oracle，编译失败或 oracle 不过的轮次同样消耗预算却不产生 reward。工程判断是让 profiler 输出结构化归因（瓶颈类别、证据指标、置信度、建议验证动作），critic 只在置信度高于阈值时才允许该归因进入下一轮 proposer 的输入，低置信度归因转为“待验证假设”，由 coder 用最小改动做探针实验而非直接重构 kernel。这样把一次高风险的错误传导拆成若干次低成本的探针，代价是轮次变多，但每轮的编译与验证开销可控。
