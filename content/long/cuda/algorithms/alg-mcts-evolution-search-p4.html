一 · 负载画像：什么样的 kernel 才值得进树

MCTS/进化 keep-revert 搜索的每一分预算都花在“跑完整正确性门 + 计时”上，因此负载选择的第一原则不是“难”，而是“单节点评估便宜且 reward 有梯度”。适合进树的负载具备三个特征：参考实现存在且可被 fp64 或高精度 oracle 校验；存在多个正交的设计自由度（tile、split-K、向量宽度、流水深度、swizzle），使得动作空间天然分层；性能对形状敏感，同一 kernel 在不同 shape 上 SOL 差异显著，从而让搜索有东西可找。反例是那些只有单一自由度的算子——例如纯 elementwise 的 SiLU，tile 大小是唯一变量，树在第一层就退化成线性扫描，UCT 的探索项失去意义。

按算子族给出优先级：GEMM 及其变体（含 batched、grouped、split-K）是首选，因为 tile×split-K×swizzle×向量化构成四维以上动作空间，且 roofline 上界清晰；attention（prefill/decode 分离）次之，decode 阶段的 KV cache 布局与 split-K 组合能产生明显分叉；reduction/normalization（softmax、layernorm、RMSNorm）适合作为中等难度负载，动作空间集中在向量宽度与 warp 内归约策略；卷积（implicit GEMM）动作空间大但正确性门成本高，适合预算充足时使用。不建议把 memory-bound 的纯拷贝类算子放进树——它们的 SOL 已经接近 1，reward 归一化后几乎无区分度，等于用 1–5 GPU 分钟/节点去买噪声。

硬件维度上，负载要与目标卡的 roofline 拐点匹配。在算力/带宽比高的卡上，GEMM 的 tile 搜索收益大；在带宽相对充裕的卡上，split-K 与流水深度的收益更明显。同一棵树不应跨架构复用：在 A 卡上收敛出的 tile=128×128 分支，迁到 B 卡上可能直接退化，而 keep/revert 会把这类退化当作“该动作先验低”记录下来，污染后续搜索。工程上应把架构标识写进根节点元数据，让不同架构各自建树。

形状（shape）维度的负载设计要避免“单点过拟合”。若只用 M=N=K=4096 一个方阵，搜索会收敛到对该点最优但在瘦长矩阵上崩溃的 tile。做法是给每个节点定义一组 shape 采样（例如方阵、瘦长、batch 小、K 极大四类），节点 reward 取这组 shape 上的几何平均或最差值，而不是单点最好值。代价是单节点计时从一次变成四次，单节点成本从 1 GPU 分钟量级升到数分钟，预算 100 节点时 GPU 小时数相应翻倍——这是用评估成本换泛化性的典型交易。

二 · 基线锚定：分母选错，整棵树都歪

reward 公式里的 $T_{\text{base}}$ 是搜索的坐标系原点，基线选错会让 UCT 的 Q 值整体偏移，甚至让“退化”与“改善”的判定反转。基线必须满足：与候选 kernel 走同一条计时路径（同一 warmup 次数、同一 CUDA event 包裹方式、同一 L2 flush 策略）；在同一输入分布上测量；且是“可被超越但不荒谬”的实现——用 cuBLAS 作基线会让手写 kernel 长期处于 Q<1 的负 reward 区，树会倾向于 revert 到根节点，搜索停滞；用朴素 triple-loop 作基线则让几乎所有子节点都“改善”，keep 分支爆炸，预算被低质量分支吃掉。

工程上推荐双基线：一个“强基线”用于归一化（cuBLAS/cuDNN 或厂商库），一个“弱基线”（朴素实现或上一轮搜索的最优）用于判定 keep/revert 的阈值。归一化用强基线保证跨任务可比，剪枝阈值用弱基线保证搜索有前进动力。二者混用会让 reward 的语义漂移：同一节点在不同轮次得到不同 Q，UCT 的选择统计被污染。

$$R_i=\frac{T_{\text{base}}}{T_{\text{gen}}}\cdot\mathbb{1}[\text{Correct}],\quad \text{keep if } R_i>1+\epsilon,\ \text{revert if } R_i<1-\epsilon$$

这里的 $\epsilon$ 是计时噪声带。GPU 计时在短 kernel 上抖动可达百分之几，若 $\epsilon$ 取 0，keep/revert 会被噪声驱动，树在等价分支间来回跳。取 $\epsilon$ 应基于重复计时的方差估计（例如同一 kernel 连测 30 次取中位数与四分位距），把 $\epsilon$ 设在噪声上界之上。代价是：$\epsilon$ 越大，真正的小幅改善被漏掉，搜索粒度变粗；$\epsilon$ 越小，误 keep 的分支越多，预算浪费在伪改善上。这是一个显式的偏差-预算权衡，应在建树前固定并写入元数据，而不是每轮动态调整。

具体例子：对一个 K 极大的 GEMM，split-K 从 1 改到 4 通常带来明显加速，但从 4 改到 8 的收益可能落在噪声带内。若 $\epsilon$ 设得过小，树会把 8 当作改善并继续在其上扩展，实际收益为零却消耗了后续节点的预算；若 $\epsilon$ 设得过大，4 也被判为 revert，搜索错过真实收益。基线锚定的质量直接决定这条边界画在哪里。

三 · 输入分布：正确性门与计时必须同分布

输入分布的设计要同时服务两件事：正确性 oracle 要能暴露数值问题，计时要有代表性。二者若不同分布，会出现“正确性门在随机均匀分布上通过、计时在极端值分布上崩溃”的裂缝。推荐三层分布：第一层是标准随机（均匀或正态，量级与真实负载匹配），用于常规正确性校验与计时；第二层是数值压力层（大幅值、小幅值、混合量级、含零与次正规数），专用于 fp64 参考比对，暴露累加顺序与精度损失；第三层是形状压力层（非对齐维度、奇数 K、batch=1），暴露 tile 边界与 tail 处理缺陷。

计时必须用第一层分布，且固定随机种子。若计时输入每节点重抽，节点间的时间差里混入了输入差异，keep/revert 判定失真。正确性门则应覆盖三层，但只在第一层上做计时——这是一个刻意的成本分配：正确性门可以便宜地跑多次（小 shape、fp64 比对），计时必须贵而稳（大 shape、多次重复取中位数）。单节点成本里，正确性门通常占小头，计时占大头，因此把分布压力放在便宜的一侧是划算的。

一个常被忽略的代价：fp64 参考 oracle 在 GPU 上的显存占用。对 K 极大的 GEMM，fp64 中间结果可能是 fp32 的数倍，若显存不足会触发换页或 OOM，使正确性门本身成为瓶颈。工程做法是把参考计算分块或在 CPU 上做，代价是正确性门时延上升，单节点成本从 1 GPU 分钟量级推向更高。这笔开销必须计入预算模型，否则“100 节点 2–8 GPU 小时”的估算会在数值压力层上被打破。

四 · 指标计算：几何平均、最差值与 SOL 归一

单节点 reward 不能只用一次计时的比值。推荐把节点指标定义为多 shape、多重复下的聚合量：对每个 shape 取重复计时的中位数 $T_{\text{gen}}$，再对 shape 集合取几何平均的加速比。几何平均对退化 shape 的惩罚比算术平均更重，能阻止“一个 shape 极快、其余全崩”的分支被 keep。若负载对最差 shape 敏感（例如服务端尾延迟），则直接用最小值（最差加速比）作为节点 reward，代价是搜索更保守，改善分支更难被保留。

$$R_{\text{node}}=\exp\left(\frac{1}{|S|}\sum_{s\in S}\ln\frac{T_{\text{base}}(s)}{T_{\text{gen}}(s)}\right)\cdot\mathbb{1}[\forall s:\text{Correct}(s)]$$

正确性项用全称量词而非存在量词：任一 shape 不正确，整节点 reward 归零。这比“平均正确率”更严格，也更符合 kernel 部署的现实——一个在奇数 K 上越界的 kernel 不能因为方阵正确就被保留。代价是正确性门的成本随 shape 集合线性增长，且严格门会让早期搜索的 keep 率偏低，树的前几层几乎全是 revert，预算消耗在“证明不行”上。缓解办法是把形状压力层放在浅层节点做快速筛除，深层节点才跑全量。

SOL 归一（roofline 上界）用于跨算子比较节点质量，但不应替代 $T_{\text{base}}/T_{\text{gen}}$ 作为 UCT 的 Q。原因：SOL 是理论上界，手写 kernel 与上界的差距里混入了编译器与库实现的差距，用它做 reward 会让搜索追逐“接近上界”而非“超越基线”，而后者才是部署收益。工程上把 SOL 作为诊断指标回灌（记录在节点元数据里），用于判断某分支是“已接近硬件极限、继续扩展无意义”还是“离上界远、还有空间”，从而指导动作空间的选择，而不是直接进 Q 值。

五 · 负载不对时会发生什么

第一类失效是 reward 无梯度：负载的 SOL 已接近 1（纯带宽算子），或基线过强（厂商库已最优），导致几乎所有子节点 $R_i\le 1$。树的行为退化为“不断 revert 到根”，UCT 的探索项把预算撒向随机动作，最终输出与根节点等价。表现为搜索跑满预算但最优路径长度为 1，GPU 小时全部沉没。诊断信号是 keep 率在浅层就趋近于零。

第二类失效是动作空间与负载不匹配：负载的性能瓶颈在 layout（如 CuTe 的 tiled copy 布局），而动作空间只含 tile 与 unroll。此时树在错误的维度上搜索，所有分支的 reward 差异都落在噪声带内，keep/revert 由噪声驱动，最优路径是随机游走的结果。这正是“未纳入的动作无法被搜索到”的结构性盲区的具体形态——不是搜索算法不行，是负载的收益维度不在动作空间里。诊断信号是节点间 reward 方差接近计时噪声方差。

第三类失效是形状过拟合：单 shape 负载上收敛出的分支在隐藏 shape 分布上崩溃。由于 reward 只在训练 shape 上计算，树会自信地 keep 一个脆弱的 tile 配置，部署时正确性门或性能门在真实分布上失败。代价不是搜索预算，而是部署后的回滚成本。缓解是把 shape 采样做成节点评估的一部分（见第一节），代价是单节点成本上升。

第四类失效是正确性门与计时分布错位：计时用对齐的大 shape，正确性门也用同一分布，tail 处理缺陷（非对齐维度、奇数 K）从未被触发。树保留了一个在训练分布上正确且快的 kernel，但在真实输入上越界写。这类失效最危险，因为搜索过程的所有指标都“绿”，失败发生在部署端。工程判断是：正确性门的分布必须严格宽于计时分布，且宽出的部分要覆盖已知的边界条件类别，而不是随机撒点。

第五类失效是预算模型失真：负载的单节点成本被低估（fp64 oracle 显存换页、shape 集合过大、重复计时次数过多），导致“100 节点 2–8 GPU 小时”的规划在实际执行中翻数倍，搜索在中途被截断，输出的是未收敛路径上的中间节点。工程上应在建树前用小样本实测单节点成本，把实测值写进预算，而不是用经验值外推。

六 · 配方固化：把负载与评测写成可复现的合约

负载与评测配方必须固化成机器可读的合约，随树一起版本化。合约字段包括：算子标识与语义描述、基线实现与其版本、shape 集合及采样权重、输入分布三层定义与随机种子、计时协议（warmup 次数、重复次数、聚合方式、L2 flush 策略）、正确性门（oracle 精度、容差、覆盖的 shape 子集）、reward 聚合公式与 $\epsilon$、单节点成本实测值。任何一个字段变更都必须触发树的重建或至少标记节点元数据，否则跨轮次的 Q 值不可比。

合约固化的直接收益是 keep/revert 判定的可审计性：当某个分支被 revert，可以回溯到是哪个 shape、哪个分布层、哪个容差导致的，而不是面对一个黑箱 reward。代价是前期工程投入——写合约、实测单节点成本、标定 $\epsilon$ 都要花时间，且合约越细，负载迁移到新算子时的复用成本越高。工程判断是：合约的粒度应停在“影响 keep/revert 判定”的字段上，不影响判定的字段（如日志格式）不进合约。

一个具体的工程取舍：是否把 SOL 上界写进合约作为硬门（超过上界的计时视为测量错误并丢弃）。写进去能防住计时抖动导致的伪加速，代价是某些真实的上界突破（例如利用稀疏性或数据相关的快速路径）会被误杀。对以稠密 GEMM 为主的负载，硬门利大于弊；对含数据依赖分支的负载，硬门会系统性排除有效分支，此时应改为软告警并人工复核。

最终落在一点上：MCTS/进化 keep-revert 的搜索质量上限由负载与评测配方决定，而不是由 UCT 常数或种群大小决定。一个 reward 有梯度、基线锚定正确、分布分层、合约固化的负载，能让树在几十个节点内收敛到有意义的路径；一个 reward 无梯度或动作空间错位的负载，任何搜索参数调优都只是在噪声里打转。建树前先问“这个负载的收益维度是否在动作空间里、reward 是否有区分度”，比建树后调参更有价值。

搜索预算与负载错配：树搜索在哪些 shape 上会亏

keep-revert 搜索的收益不是免费的：每个候选节点都要跑一次完整正确性门加计时，单节点成本约 1–5 GPU 分钟，100 节点即 2–8 GPU 小时。这意味着负载选择的第一原则是“基线离 roofline 有可被动作空间闭合的差距”。若参考实现已经接近 SOL（例如大 batch、规则 shape 上的纯 GEMM），动作空间里的 tile/unroll/split-K 组合只能挤出个位数百分比，而 reward 归一化后分支间差异被噪声淹没——计时抖动与 L2 状态残留足以让 UCT 把预算花在等价节点上。反过来，split-K 归约、不规则 reduction、小 shape 下的 launch 开销占比高，才是树搜索能兑现 1.2–1.8× 的区间。判断依据不是“算子难不难”，而是基线相对 SOL 的余量是否大于单节点计时噪声。

输入分布必须与正确性 oracle 绑定设计。若只测单一 shape，搜索会过拟合到该 tile 配置；若分布过宽，正确性门在每个节点上都要跑全部用例，单节点成本从 1 GPU 分钟抬到 5 GPU 分钟，同预算下可探索节点数直接缩水数倍。工程做法是分层：门禁用少量边界用例（含非对齐长度、零长度、极端 stride）保证不崩，计时用主 shape 加权，reward 按 $$R_i=\frac{T_{\text{base}}}{T_{\text{gen}}}\cdot\mathbb{1}[\text{Correct}]$$ 只在通过门禁后计入，避免“快但错”的分支污染 Q 值。基线则必须固定为同一硬件、同一编译选项下的参考实现，且基线计时与候选计时交替采样，否则时钟漂移会把 keep/revert 判反。

失效条件集中在两类。其一是动作空间盲区：未纳入的动作（如 CuTe layout、PTX 级 swizzle）无法被搜索到，树再深也到不了那片区域，表现为搜索曲线早早平台化而 SOL 仍有余量——此时加预算无用，只能改动作空间。其二是负载本身不适合多轮：单轮生成成功率高的简单算子，线性重试已够，树搜索的探索开销反而拖长端到端时延；而 shape 极小的负载，单节点计时被 launch 开销主导，reward 信号几乎全是噪声，keep/revert 退化为随机游走。系统代价还体现在编译时间上：每个子节点都要编译，模板实例化重的 kernel 编译时间可与计时同量级，预算应按“编译+正确性+计时”三项合计，而非只算 GPU 计时。

负载特征树搜索期望主要代价
基线远离 SOL、分支差异大正收益，剪枝有效节点数×单节点成本
基线近 SOL、规则大 shape收益被噪声吞没预算空转
极小 shape、launch 主导reward 失真计时不可信
动作空间未覆盖关键变换平台化，加预算无效结构性盲区
