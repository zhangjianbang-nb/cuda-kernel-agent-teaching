一 · 一次评测翻车：为什么基准分数会骗人

先看一个在 agent kernel 训练里反复出现的翻车形态。训练集里只有 KernelBench 那批公开算子，且分布高度偏斜：GEMM、softmax、layernorm、attention 这几类占了绝大多数样本，冷门算子——带 stride 的转置卷积、非连续输入的 reduce、混合 dtype 的 elementwise 融合、带 mask 的变长 attention——几乎不出现。RL 阶段用执行反馈做奖励，模型很快学会在这些热门算子上把 tile 大小、shared memory 用量、warp 分工调到极熟，KernelBench 上的通过率和加速比都好看。然后把它接到真实框架里，调用一个 `conv_transpose2d` 加 bias 加激活的融合算子，输入是非连续 view，dtype 是 fp16 而权重是 fp32，模型生成的 kernel 直接越界读或者给出错误结果。

这不是模型“变笨”，而是训练分布与评测分布同时窄化。KernelBench 系基准本身算子数量有限，且其采样并不代表真实框架调用分布；当训练集和测试集共享同一批热门算子时，分数衡量的是记忆而非泛化。更隐蔽的是，agent 在优化循环里会针对固定 shape 做常量折叠、把边界条件写死，执行反馈全绿，但换一个 batch size 或换一个 stride 就崩。这类失败在评测里表现为“通过率虚高、端到端收益为零”，在线上表现为“离线 benchmark 加速 1.4x，上线后延迟不降反升”。

合成算子数据扩增要解决的正是这个具体问题：把训练分布从“少数热门算子 + 少数固定 shape”扩展为“算子语法空间上的参数化采样”，让 agent 在训练时就见到长尾 shape、dtype 组合、融合模式和边界条件，从而在未见过的真实算子上仍能生成正确且高效的 kernel。它不解决的是：真实框架调用分布的精确建模、算子语义本身的歧义、以及硬件层面的微架构调优（后者要靠 NCU/SASS 回灌那条线）。合成数据是分布扩增，不是分布替代。

二 · 扩增的对象是语法空间，不是样本数量

关键机制是把“算子”从一组固定实例提升为一个可参数化的语法。语法层定义算子族：逐元素、归约、矩阵乘、卷积、attention，以及它们的融合组合；每个族带一组参数：shape、dtype、stride/layout、边界条件（尾块、非整除、mask、空 tensor）、融合模式（prologue/epilogue 的元素级操作链）。采样器在这个语法上做程序化抽样，而不是对已有 kernel 做文本变异。

训练集因此写成：

$$\mathcal{D}_{\text{train}}=\mathcal{D}_{\text{real}}\cup\{(x_i,y_i,\text{ref}_i,T_{\text{ref},i})\}_{i=1}^{M},\quad x_i\sim p_{\text{synth}}(\cdot\mid\text{op},\text{shape},\text{dtype})$$

其中每个合成样本是四元组：输入描述 x、期望输出 y、参考实现 ref、参考时延 T_ref。注意这里扩增的是“语法空间上的覆盖”，不是把同一个 GEMM 复制一万遍。一个 4096×4096 的 GEMM 变体和一个 17×33 的尾块 GEMM 在语法上同族，但对 agent 的挑战完全不同：后者要求正确处理非整除 tile、边界 predicate、以及极小的 occupancy。只堆同分布样本，扩增的是 token 消耗而不是泛化。

代价立刻出现。合成样本需要自动生成参考实现作为 oracle，参考实现本身是代码，代码会错。一个 fp64 参考实现里把 reduce 的初值写成 0 而非 −inf，会让所有带负输入的 max-reduce 样本标注错误，agent 学到的是错误语义，且这个污染会通过 SFT 固化进权重。这就是为什么合成管线必须配变异测试审计 checker——往参考实现里注入已知 bug，看 oracle 是否能抓住；抓不住就说明标注不可信。这条审计不是可选项，它是合成数据能否进入训练集的门槛。

三 · 标注成本与编译时延：扩增的真实账单

合成数据的卖点是标注成本低：参考实现由生成器自动产出，参考时延由 PyTorch/cuBLAS 基线跑出来，不需要人工写 kernel 或人工标答案。但“低”是相对的，账单落在三处。

  • 编译与执行时延：每个合成样本要跑一次参考实现拿 T_ref，还要跑一次基线拿对照。若一个样本的参考实现是 PyTorch 组合算子，单次前向在 GPU 上是毫秒级，但 M 个样本串行跑就是分钟到小时级；若参考实现走 fp64，吞吐再降一个量级。这是数据生成阶段的固定成本，与训练 token 成本分开计。
  • 显存：fp64 参考实现意味着中间张量按双精度存，一个大 shape 的 reduce 或 attention 样本，fp64 中间缓冲可能是 fp32 的数倍，采样器必须按显存预算裁剪 shape 上界，否则生成进程 OOM。
  • oracle 可信度成本：每个算子族都要有对应的变异测试集，注入边界 bug（off-by-one、stride 忽略、mask 反向、dtype 截断）验证 checker 能捕获。审计覆盖不足的族，其合成样本不能进训练集，这直接削减了有效 M。

具体例子：一个融合算子族“matmul + bias + GELU”，采样器给出 shape (M,K,N) 从 {1, 17, 128, 4096} 的笛卡尔积里抽，dtype 在 fp16/fp32/bf16 间抽，stride 在连续与非连续间抽。仅这一个族就能产出数百个语法上不同、语义上同源的样本。但其中非连续 stride 的样本，参考实现必须显式做 `.contiguous()` 或按 stride 索引，否则 PyTorch 的广播语义会让 ref 与 kernel 的期望不一致——这类样本正是最容易污染 oracle 的地方，也是审计必须优先覆盖的地方。

四 · 分层混入：合成与真实的配比是工程判断

生成完不等于能用。把合成数据直接倒进 SFT/RL 训练集，会让模型偏向合成分布里的“干净”形态：整除 shape、连续 layout、单一 dtype。真实框架调用恰恰相反——非整除、非连续、混合精度、带 mask 是常态。因此混入要按难度分层采样，而不是均匀采样。

分层维度至少三条：算子族稀有度（热门族降采样、冷门族升采样）、shape 难度（尾块、极小、极大分桶）、语义复杂度（单算子 vs 融合链）。RL 阶段尤其要注意，奖励来自执行反馈，合成样本若过于简单会让策略退化为“套模板”，若过难则奖励稀疏、方差大。一个可操作的伪代码思路是：

  • 对每个算子族维护一个采样权重 w_f，初始按真实基准中的出现频率反比设定；
  • 每轮训练后统计该族在真实基准上的通过率，通过率高的族降权，低的族升权；
  • 难度桶内按固定配额采样，保证每个桶都有代表样本进入 batch。

代价是 token 预算的重新分配：冷门族升采样意味着同样 token 数下热门族的曝光减少，短期内在 KernelBench 热门子集上的分数会下降。这是预期行为，不是回归。工程判断在于：如果评测只看热门子集，合成数据看起来“有害”；如果评测看真实框架算子集，合成数据才显出收益。这也是为什么合成-真实分布差距必须被监控，而不是假设它不存在。

五 · 边界条件：合成数据失效的三种典型场景

合成扩增有明确的适用边界，越过边界就是负收益。

第一，真实调用分布不可参数化时。真实框架里的算子往往由多个原语组合而成，融合模式取决于图优化器的决策，而不是语法层能枚举的固定链。合成器能覆盖“matmul+激活”，但覆盖不了“某个框架在特定后端上把三个算子融成一个带动态 shape 的 kernel”。这类样本只能从真实 trace 里采，合成器无能为力。

第二，参考实现语义与框架语义不一致时。PyTorch 的某些算子在不同 dtype 下有隐式提升规则，fp16 输入可能被提升到 fp32 计算再降回；合成器的参考实现若按数学定义写，就会与框架实际行为不符，oracle 标出的“正确答案”在真实调用里是错的。这类不一致必须靠对拍真实框架输出来发现，单靠合成器自洽无法暴露。

第三，性能参考时延不可比时。T_ref 来自 PyTorch/cuBLAS 基线，但真实场景的基线可能是融合后的框架 kernel，二者时延不可直接比较。用合成 T_ref 做奖励，agent 会优化到“打败 PyTorch 单算子”，而不是“打败框架融合算子”，端到端收益落空。这要求评估阶段必须回到真实框架调用上做收益核算，合成数据只负责训练分布，不负责收益证明。

一个具体判断：当某算子族的真实调用中，融合模式由框架图优化器动态决定的比例超过语法层可枚举范围时，该族的合成样本应只用于正确性训练（教 agent 处理边界），不用于性能奖励训练。把两类目标混在一个奖励里，会让 agent 学到“在合成基线上刷分”的错误策略。

六 · 与验证闭环的接口：合成数据不是孤岛

合成数据扩增的可信度最终取决于它与验证环节的接口。参考实现是 oracle，但 oracle 本身要被审计；合成样本进入训练集前要过合约校验（dtype/shape/stride 的合法性、输出范围、NaN/Inf 行为）；训练后的 agent 要在真实基准上评估泛化，并监控合成-真实差距。这三道关卡缺一不可。

接口设计上，每个合成样本应携带来源标签：算子族、采样参数、参考实现版本、审计状态。这样当真实评测出现回归时，可以反查是哪个族的合成样本导致了过拟合或语义污染，而不是面对一个黑箱训练集束手无策。变异测试审计的结果也应作为样本元数据保留——未通过审计的族，其样本在混入时被过滤，而不是被“大概没问题”地放行。

代价是管线复杂度：生成、审计、混入、评估四个阶段各自有失败模式，且失败会跨阶段传播。一个审计漏掉的参考实现 bug，会在训练后表现为真实算子上的系统性错误，而这时已经烧掉了整轮训练 token。工程上的应对是把审计前移：在样本进入训练集之前就做变异测试，而不是训练完再查。这与防作弊合约校验、变异测试审计 checker 是同一套思路的不同落点——合成数据扩增负责把分布铺开，验证闭环负责保证铺开的每一块都可信。

最终落在一条工程判断上：合成算子数据扩增的收益不在 M 的大小，而在语法空间覆盖的宽度与 oracle 的可信度。M 再大，若采样集中在整除 shape 与连续 layout，agent 学到的仍是窄分布；oracle 再自动，若没有变异测试兜底，污染会静默进入权重。把这两件事做对，扩增才是泛化的来源；做错，它只是把过拟合换了一个更贵的形状。

合成扩增的边界：它补的是长尾覆盖，不是真实调用分布

一次典型的评测翻车是这样的：某轮 RL 训练后，模型在 KernelBench 的 GEMM 与 attention 子集上通过率与加速比都很体面，但把同一批策略接到真实推理框架里，遇到 非连续 stride 的归约 + 广播融合、fp32 累加配 bf16 输入、极小 shape 的 batch=1 卷积 这类调用时，生成的 kernel 要么编译失败，要么正确性 oracle 直接报错，要么性能退化到不如 PyTorch 基线。根因不是策略退化，而是训练分布偏斜：真实基准里热门算子占绝大多数，模型把容量花在了少数模板上。合成扩增要解决的正是这个“覆盖”问题——用程序化生成器在算子语法（逐元素、归约、矩阵乘、卷积、attention 及其融合组合）上参数化 shape/dtype/stride/边界条件，采样出大量变体，并自动生成 PyTorch/fp64 参考实现作为 oracle、跑基线得到参考时延，从而把训练集从

$$\mathcal{D}_{\text{train}}=\mathcal{D}_{\text{real}}\cup\{(x_i,y_i,\text{ref}_i,T_{\text{ref},i})\}_{i=1}^{M},\quad x_i\sim p_{\text{synth}}(\cdot\mid\text{op},\text{shape},\text{dtype})$$
中的第二项撑大。它不解决的是：真实框架调用分布的建模、端到端调度与内存复用、以及“合成分布本身是否可信”这一层。

失效条件集中在两处。其一是分布错位：合成采样按算子语法均匀或分层展开，而真实框架调用由上层图优化与算子融合决定，长尾 shape 往往来自动态 batch、变长序列、稀疏边界，合成器若只按静态网格采样，训出的策略在真实端到端场景里会失效——这不是泛化不足，而是训练目标与部署目标不是同一个分布。其二是 oracle 污染：参考实现由生成器自动产出，一旦某个融合模式的 fp64 参考写错（例如归约轴顺序、边界 padding 语义），错误标注会以高置信度进入 RL 的可验证奖励，模型会被奖励去复现错误行为。工程上必须对合成 oracle 做变异测试审计：人为注入 stride/边界/精度变异，检查参考实现与基线是否同步报错，未通过审计的算子族整族剔除。代价是明确的：合成样本的生成与基线计时本身消耗 GPU 时延（每个实例至少一次基线前向），oracle 审计又要额外跑变异批次，整体数据构建成本随算子族数量线性上升；而混入比例过高时，真实基准上的通过率反而会因分布漂移下降。

场景合成扩增是否适用主要代价
冷门 dtype/stride 组合的正确性覆盖适用，长尾样本廉价基线计时 GPU 时延、oracle 审计成本
动态 shape 下的真实框架端到端不适用，需真实 trace 补样合成-真实分布差距无法靠扩增消除
融合模式探索有条件适用，需语法层可表达语法未覆盖的融合仍为盲区

判断标准应落在“合成-真实分布差距”的监控上，而不是合成样本量。把合成数据按难度分层混入 SFT/RL 时，必须同时在真实基准与真实框架算子上留出评估集，观察两侧通过率与加速比的剪刀差；一旦真实侧不升反降，说明扩增已越过边界，应回退混入比例并补真实 trace。合成扩增是覆盖工具，不是分布对齐工具——把它当成后者用，就是那次翻车的复现路径。
