一 · 单轮提示：从参考实现到候选源码

Warpline 的方法学起点不是某个新算子，而是把一次 kernel 生成拆成可观测的流水线。单轮提示这一步的输入是三元组：参考实现（PyTorch eager 或论文指定库版本）、基准口径（输入 shape、dtype、容差、计时方式）、以及目标语言的约束（Triton / CuTe DSL / CUDA C++ 三选一）。输出是一份候选源码文本，附带 agent 自述的优化意图。代价有两块：token 与编译时间。token 侧，参考实现加上口径说明通常构成 prompt 的主体，候选越长、注释越多，后续编译与探针注入的解析成本越高；编译侧，候选一旦进入 nvcc 或 Triton 编译，单次编译时间就成为迭代周期的硬下限，而 Warpline 的设计恰恰要绕开“每次迭代都重新编译”的税。

这一步的关键工程判断是：单轮提示产出的候选必须自带“可被二进制分析”的结构。Warpline 分析的是编译产物而非源码，因此候选里若出现极端的内联展开、模板特化或手写 PTX 内联汇编，二进制里的事件边界会变得稀疏，探针可插入的位置随之减少。一个具体例子：同一个 reduction kernel，写成 Triton 的 tl.sum 会编译成规整的 warp shuffle 序列，二进制里能清晰区分加载段与归约段；写成 CUDA C++ 的手工展开循环，编译器可能把多个阶段的指令交织在一起，二进制级事件切分就只能退化为按基本块粗粒度划分。这不是正确性问题，而是证据粒度问题——粒度越粗，agent 拿到的“时间花在哪”就越模糊，后续 RL 或脚手架的回灌信号信噪比越低。

$$\text{cost}_{\text{turn}}=\underbrace{c_{\text{prompt}}}_{\text{token}}+\underbrace{t_{\text{compile}}}_{\text{编译时延}}+\underbrace{t_{\text{probe}}}_{\text{二进制改写}}$$

把这三项并列的意义在于：Warpline 声称“无需重新编译、无需手工插桩”，削掉的是第三项里的人工部分与第二项的重复部分，但第一项（prompt token）不受它控制。因此单轮提示阶段的候选质量直接决定了后面几步是否值得走——一个连语义都不对的候选，二进制探针插得再准也只是在测量错误。

二 · Agent 脚手架：把二进制证据变成下一步动作

脚手架这一步的输入是上一轮留下的三类证据：编译是否成功、运行是否正确、以及 Warpline 产出的统一时间线。输出不是代码，而是一个结构化的“下一步动作”——改哪一段、按什么方向改、是否回退。这一步的机制核心是证据对齐：Warpline 把二进制级 trace 与硬件 profiling 数据放在同一条时间线上，前者回答“每个 warp 的时间去了哪”，后者回答“各单元有多忙”。两者对齐后，脚手架才能区分“这个 kernel 是访存受限”与“这个 kernel 的某个 warp 在等一个长延迟依赖”——前者对应换 tile 策略，后者对应改流水或消除分支。

代价体现在反馈回路的时延上。一次完整的“生成—编译—运行—评测—回灌”循环，其墙钟时间由编译、运行、profile 三段构成；Warpline 削掉的是“为插桩而重新编译”这一段，但运行与 profile 本身无法省略。工程上的直接后果是：脚手架必须在有限轮次内做出高价值决策，不能靠穷举。一个具体例子：某 kernel 的 trace 显示 70% 的 warp 时间集中在全局加载后的同步点，profiling 又显示 SM 的 LSU 利用率并不高——两条证据合起来指向“同步粒度太粗而非带宽不足”，脚手架据此选择拆分 tile 而非增大 prefetch 深度。若只有 profiling 一条证据，agent 很可能误判为带宽问题并做出无效修改。

正确性代价在这里以“回退”的形式出现。论文给出的接受判据是正确性门与性能门的合取：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

注意这个判据只要求“不慢于基线”，并不要求“显著更快”。在脚手架语境下这是合理的：单步修改的方差大，要求每步都显著加速会让搜索过早收敛。但它也埋下一个失败模式——若基线未开 TF32 或未用最强库实现，s≥1 的门槛会被轻易跨过，脚手架会持续接受实际更慢的候选，离线分数虚高而在生产端崩塌。

三 · RL 与可验证奖励：把 trace 折进奖励

RL 这一步的输入是候选 kernel 及其在基准题上的执行结果，输出是策略更新。Warpline 提供的新颖之处在于奖励的可验证性来源不止于“跑得快”，还包括“证据可复现”：因为探针注入只依赖二进制，agent 在源码、IR 或 PTX 任一层级编辑后产生的新版本，都能自动重新生成同一口径的 trace。这消解了传统 intra-kernel tracer 的死结——手工探针加重新编译会改变被测量的 kernel 本身，测量对象与优化对象不再是同一个东西。

奖励设计的代价是 token 与显存。若把 trace 摘要作为奖励模型或规则判定的输入，每条样本都要携带一段结构化时间线，长度随 kernel 复杂度增长；若把 profiling 计数器一并纳入，显存占用随采样深度上升。工程折中是只保留 top-k 时间片段的聚合量，但这会丢掉长尾 warp 的信息——而长尾恰恰是 warp 级 trace 相对硬件 profiler 的独有价值。一个具体例子：一个 GEMM kernel 的 trace 里 95% 的 warp 时间在 MMA 流水上，5% 落在 epilogue 的写回；若只保留聚合量，epilogue 的优化空间被淹没，而实际上把 epilogue 的向量化写回改掉可能带来可观的端到端收益。

可验证奖励的另一面是 reward hacking。论文的接受判据是布尔合取，agent 可以通过 fallback 到参考实现来保证 pass 为真，同时用 shape 特化让 s≥1 在给定输入上成立。Warpline 的二进制证据本身不能阻止这种行为，但它能让评测者看到“这个候选的时间花在了哪里”——一个 fallback 候选的 trace 会与参考实现高度同构，这是可检测的指纹。因此 RL 阶段的工程判断是：把 trace 同构性作为辅助惩罚项，而不是只信 accept 这一个比特。

四 · Verifier：正确性 oracle 与性能门的分离

Verifier 这一步的输入是候选二进制、给定输入分布、以及基线计时。输出是两个独立的判定：正确性与性能。Warpline 的方法学要求这两者分离，因为二进制探针注入本身可能引入测量扰动——论文声称在 NVIDIA B200 上跨 35 个 Triton、CuTe DSL 与 CUDA C++ kernel，中位开销 1.2%，中位 99.9% 的执行指令保持不变；对照的既有 tracer 中位开销显著更高（论文给出 1.6、13.2、4.6、32.7 等量级）。这些数字的含义是：探针注入不是零成本的，verifier 必须把“被测 kernel 因插桩而变慢”与“候选本身更慢”区分开。

机制上，这要求 verifier 在两条路径上各测一次：原始二进制与插桩后二进制。正确性判定用原始二进制，避免探针改变执行语义；性能判定也用原始二进制，避免插桩开销污染 T_agent；trace 采集用插桩后二进制，且只在需要证据时启用。代价是评测时延翻倍——每个候选要跑两遍。一个具体例子：某 CuTe DSL kernel 在插桩后中位开销落在 1.2% 量级，但个别 kernel 的尾部开销远高于中位；若 verifier 用插桩后的时延做性能门，这些尾部 kernel 会被误判为性能回退而错误回退，损失的是真实的优化机会。

正确性 oracle 的代价在输入分布上。论文口径未给出全部 shape，这意味着 verifier 的容差与输入采样策略必须显式记录，否则跨硬件、跨 dtype 迁移时正确性门会失效。工程判断是：把 oracle 的输入分布当作评测契约的一部分固化下来，而不是当作可调参数。

五 · 二进制改写：探针插入的机制与不变性代价

这是 Warpline 区别于其他 agent 脚手架的核心机制。输入是编译后的二进制（cubin 或等价产物），输出是注入了探针的二进制。机制分两步：先分析二进制决定记录哪些事件，再把探针写入二进制本身，不经过重新编译、不经过任何手工步骤。这一步的代价是“不变性”——论文声称中位 99.9% 的执行指令保持不变，剩下的 0.1% 就是探针本身及其必要的上下文保存。这个比例决定了 trace 的可信度：扰动越小，测到的时间越接近真实执行。

为什么必须走二进制而不是源码或 IR？因为 agent 可能在源码、IR 或 PTX 任一层级编辑，若探针注入绑定在某一层，换层就要重做。二进制是所有这些层级的共同下游，只依赖它就能对每个新版本重新生成证据，从而闭合优化回路而无需人工介入。代价是二进制分析的复杂度：事件边界的识别依赖指令模式与基本块结构，遇到编译器激进重排时切分粒度会退化。一个具体例子：Triton 生成的 kernel 在二进制里通常保留较清晰的基本块边界，探针可落在加载、计算、写回三段之间；而 CUDA C++ 经过高强度优化的 kernel，编译器可能把三段指令交织，探针只能落在更粗的同步点上，trace 的时间归因随之变粗。

另一个被低估的代价是闭源 kernel 的可追踪性。论文指出 Warpline 也能追踪闭源 kernel，而既有 tracer 做不到——因为后者依赖源码级插桩。这扩大了证据的适用范围，但也意味着 verifier 面对的是无法审计的二进制，正确性只能靠输入输出比对而非语义检查。工程判断：闭源场景下应把 trace 与 profiling 的对齐结果作为主要证据，正确性门退化为黑盒差分测试。

六 · 一次完整流动的代价账本

把五步串起来看，一次 kernel 生成—编译—运行—评测的流动可以写成一张代价账本。生成阶段付 token；编译阶段付编译时延；运行阶段付墙钟时间与显存；评测阶段付双跑时延（原始与插桩各一次）；回灌阶段付 trace 序列化与奖励计算的 token。Warpline 的贡献是把“为插桩重新编译”这一项从账本里划掉，并把“手工探针”这一项归零，但它没有消除编译、运行、评测本身的成本。

这张账本解释了一个工程判断：Warpline 的价值不在单点加速，而在把“证据生成”从人工与重编译中解放出来，使 agent 能在每一轮迭代都拿到同一口径的 warp 级时间归因。代价是评测时必须区分插桩扰动与真实性能差异，且必须把 trace 同构性纳入反 reward hacking 的检查。若省略这两条，accept 这个比特会变得不可信，整条流动的最优结果也就不可复现。

二进制插桩的失效面与系统代价

Warpline 的边界首先由“只读二进制”这一约束划定。插桩点在 SASS 层选定，因此它无法感知源码级语义：被编译器内联、循环展开或指令调度重排后的热点，在二进制里只剩地址与指令窗口，agent 拿到的是“哪个 warp 在哪个 PC 区间停留”，而不是“哪一行 Triton 代码慢”。当 kernel 由 CuTe DSL 或 PTX 手工编辑产生时，同一逻辑版本可能对应完全不同的指令布局，证据的可比性依赖 trace 与硬件 profiling 数据在同一时间轴上的对齐质量；对齐一旦因时钟域或采样窗口偏移而失配，agent 会把等待访存的 stall 误判为计算瓶颈，进而做出错误的改写决策。论文在 B200 上报告 35 个 Triton/CuTe DSL/CUDA C++ kernel 的中位开销 1.2%、执行指令中位 99.9% 保持不变，但这组数字的成立前提是插桩密度受控——探针本身占用指令槽与寄存器，密度上升会同时抬高开销并扰动被测 kernel 的调度。

代价可以写成可测量的形式：设插桩后指令数为 $I_p$、原指令数为 $I_0$，则指令扰动率为 $\delta = (I_p-I_0)/I_0$，而单次证据生成的墙钟代价近似为 $T_{\text{trace}} = T_{\text{run}} + N_p\cdot c_p + T_{\text{align}}$，其中 $N_p$ 为探针数、$c_p$ 为单探针记录成本、$T_{\text{align}}$ 为与 profiler 数据对齐的解析开销。对 agent 循环而言，真正的成本不在单次 trace，而在每轮候选都要重跑这条链路：编译、运行、插桩、对齐、回灌，任何一步失败都让该轮反馈为空，agent 只能在无证据条件下盲改。一个具体例子是带 shape 特化的 GEMM：二进制插桩能指出尾块 warp 的长时间 stall，但若 agent 据此改写 tile 形状而未同步调整边界处理，正确性门会直接拒绝候选，这一轮的 trace 开销即成为纯沉没成本。

失效条件集中在三类。其一是闭源 kernel：Warpline 声称可追踪闭源 kernel，而手工探针类 tracer 不能，但闭源意味着无法确认插桩是否触碰了厂商保留的指令序列，证据的可信度只能靠 99.9% 指令不变这一统计口径兜底，无法逐条核验。其二是跨硬件迁移：论文结论只在给定硬件、基线与输入分布上成立，插桩策略对指令集与调度器的假设在别的架构上未必保持 1.2% 量级。其三是评测口径本身——若基线未开 TF32 或未用最强库实现，加速比 $\text{speedup}=T_{\text{base}}/T_{\text{agent}}$ 会被系统性高估，而接受判据 $\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$ 只检查正确性与速度，不检查证据是否真的被用于决策，于是“有 trace 但没用 trace”的候选同样能通过，形成证据链上的空转。
