一 · 一次 kernel 生成—编译—运行—评测的流动拆解

把“方法”拆成流动，而不是拆成模块清单，是因为这条流水线上每一步的失败代价完全不同：生成阶段的失败是 token 代价，编译阶段的失败是编译时间代价，运行阶段的失败是显存与时延代价，评测阶段的失败则是“判决错误”代价——它不会立刻报错，而是把一个错误结论写进排行榜和 RL 奖励。本部分按这四步走，每一步给出输入、输出、代价，并把论文的变异分析机制嵌进评测步，说明它为什么必须放在最后一步而不是最前一步。

第一步，生成。输入是题目描述、参考实现签名、以及（在 agent 脚手架下）上一轮的编译诊断与 profile 摘要；输出是一段 CUDA C++ 源码文本。单轮提示的代价最直接：一次前向的 token 数，加上把题目与参考实现塞进上下文的 token 数；在 188 道 KernelBench 题目的规模上，这是可枚举的、可预算的。agent 脚手架的代价结构不同：它把一次生成拆成多轮，每轮都要重新读入上下文，token 代价随轮数线性增长，而收益是编译错误可以被局部修复而不是整段重写。RL 路线的代价又不同：采样 N 个候选意味着 N 次生成，奖励信号来自后续步骤，因此生成步的代价被放大 N 倍，且必须等整条流水线跑完才能回传。verifier 路线的生成步最便宜——它不生成 kernel，只生成测试协议（输入分布、容差、检查逻辑），但它决定了后面所有候选的判决口径。

一个具体例子：对一道 reduction 类题目，单轮提示可能直接给出一个用共享内存做树形归约的 kernel；agent 脚手架则可能先给出一个能编译但越界的版本，编译器报出静态数组越界后，第二轮只改索引表达式；RL 采样则会产生若干在数值上略有差异的候选，其中一部分的差异恰好落在容差盲带内——这正是评测步要处理的问题。三种路线在生成步的输入输出形式相同，但代价的量纲不同：token、轮数×token、N×token。

$$\text{cost}_{\text{gen}}=\underbrace{c_{\text{ctx}}}_{\text{上下文读入}}+\underbrace{R\cdot c_{\text{turn}}}_{\text{多轮重读}}+\underbrace{N\cdot c_{\text{sample}}}_{\text{RL 采样}}$$

这个式子只是把三种路线的代价并列，不是要相加；实际工程里选一种。它的用处是提醒：当评测步的判决不可信时，前面三步的代价全部作废，而 RL 路线作废得最贵，因为它已经为 N 个候选付了钱。

二 · 编译步：可编译性是变异分析的第一道闸门

编译步的输入是源码文本与目标架构的编译选项，输出是二进制或编译诊断。代价是编译时间，在 CUDA 上单次编译从数秒到数十秒不等，取决于模板实例化深度与是否启用 CuTe/PTX 内联。这一步在方法上的意义被论文的变异规则直接利用：注入的故障必须是“可编译的”。论文的确定性规则向 188 道 KernelBench 题目的已验证 CUDA 实现注入 10,303 个可编译故障，其中 7,384 个带有独立的 kill witness。这个“可编译”约束不是修辞——如果注入的故障让代码编译不过，那么任何测试协议都能“杀死”它，测出来的检出率就是编译器的功劳，而不是 oracle 的功劳。因此变异分析把编译步当作过滤器：只有通过编译的变异体才进入候选池，才配得上被计入分母。

代价在这里体现为一个具体的工程取舍：10,303 个变异体意味着上万次编译。若每个变异体单独编译，编译时间就是这条流水线的主导成本；工程上通常把同一题目的多个变异体合并到一个翻译单元或用增量编译摊薄。但合并会带来另一个代价：一个变异体的编译错误可能污染同批次其他变异体的诊断，破坏“每个变异体独立可编译”的前提。所以变异分析在实现上必须保证变异体之间的编译隔离，这与 agent 脚手架里“多轮修复共享一个编译上下文”的做法正好相反。

一个具体例子：把一处 += 改成 = 的累加变异，在 reduction kernel 里仍然能编译通过，但语义上丢掉了部分和；这类变异体是“可编译且语义错误”的理想样本。相反，把共享内存数组维度改成负数会直接编译失败，这类变异体在进入分母前就被剔除。论文的 10,303 与 7,384 之间的差额，正是这条闸门筛掉的部分——有 witness 的变异体才是可信的分母。

三 · 运行步：输入分布与容差共同定义“被执行到的语义”

运行步的输入是二进制、输入张量、以及测试协议规定的容差；输出是候选输出与参考输出的逐元素比较结果。代价是显存占用与 kernel 时延，以及为覆盖输入分布而重复运行的次数。这一步是论文诊断的核心现场：官方检查用少量随机输入加一个宽松浮点容差判正确，于是“被执行到的语义”只是全部语义的一个子集。变异分析要测的，正是这个子集相对于全部可编译故障的覆盖率。

论文给出的关键数字把这一步的失效结构说清楚了：官方检查漏掉六分之一的带 witness 故障，即 16.9%，而且是确定性地漏；漏检按故障族偏斜，算术类故障逃逸 8.7%，精度类故障逃逸 78.6%。这个偏斜不是随机噪声，它由容差盲带解释——盲带随归约规模增长。归约越长，合法浮点方差越大，容差必须放宽，盲带就越宽，精度类变异体越容易整段落在盲带里不被发现。同时论文测量了输入激进程度的上限，这个上限由合法浮点方差设定：输入再激进，参考实现自身的数值抖动就会让比较失去意义。

$$\text{blind band}\ \propto\ \sqrt{n}\cdot\varepsilon_{\text{fp}},\qquad \text{escape}=\mathbb{1}\big[\,|y_{\text{mut}}-y_{\text{ref}}|<\tau\,\big]$$

第一式是定性比例：盲带随归约长度 n 的平方根与浮点精度 ε 增长；第二式是逃逸判据，变异体输出与参考输出之差落在容差 τ 内即判为未被杀死。两式合起来说明：精度类故障的逃逸率 78.6% 不是测试写得差，而是容差与归约规模的结构性后果。一个具体例子：在长归约上把 float 累加换成半精度中间量，误差随 n 累积，但仍在为合法方差设定的 τ 之内，官方检查判它正确；变异分析因为有独立 witness，能确定地把它标为漏检。

运行步的代价还体现在输入数量上。论文报告，在 kill matrix 上优化测试套件，每道题两个输入即可达到 98.0% 检出率，留出集上 94.8%。这意味着运行步的成本可以从“若干随机输入”压缩到“两个精心选择的输入”，但这两个输入的选择依赖 kill matrix——也就是依赖先跑过大量变异体。于是运行步出现一个先有鸡还是先有蛋的代价：为了省运行成本而优化输入，必须先付一遍全量变异体的运行成本。

四 · 评测步：把 oracle 本身当作被测对象

评测步的输入是运行步的比较结果与测试协议，输出是一个判决：候选正确或错误。传统流水线里这一步是终点；在论文的方法里，这一步是起点，因为被测对象不是 kernel 而是 oracle。机制是把 7,384 个带 witness 的变异体当作已知错误的探针，让测试协议去判，统计它判错的比例。分数定义为被杀死变异体的比例：

$$\text{adequacy}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\big[\text{protocol kills mutant}_i\big],\qquad N=7{,}384$$

这个定义把“测试够不够好”变成一个可比较的数，而不是靠手工加输入分布、加 fuzzing、收紧容差来猜。代价是评测步从 O(候选数) 变成 O(候选数 × 变异体数)：每换一次测试协议，都要把 7,384 个变异体重跑一遍。这是变异分析最实在的工程成本，也是它只能离线做、不能塞进每轮 RL 奖励的原因。RL 奖励需要低时延回传，而 adequacy 的计算需要上万次运行；两者在预算上不兼容。工程判断因此是：变异分析用于校准 oracle，校准后的 oracle 才用于 RL 奖励。

论文还用这个评测步审计了最强的现有补丁：KernelBench-Verified 的增益可拆成 +4.0 分来自隐藏输入、+4.5 分来自更紧的容差。这个拆分只有把 oracle 当被测对象才做得出来——手工补丁通常把两项混在一起报告，无法判断哪一项在起作用。另一个具体结果是：跨 48 个整体架构，盲区随规模增长，集中在深层同构流水线；有两道题被证明不可裁判，因为它们的官方参考实现在基准自己的容差下就违反了 fp 一致性。这是评测步最尖锐的代价形态：不是 oracle 漏检，而是 oracle 的参考本身就不可信，任何测试协议在这两道题上都没有意义。

五 · 反馈回灌：从 kill matrix 到测试生成器

反馈步的输入是评测步产出的 kill matrix（变异体 × 测试协议的杀死矩阵），输出是下一轮的测试协议或候选筛选信号。代价是 token 与编译时间：如果反馈用于 agent 脚手架，每一轮都要把 profile 与诊断重新塞进上下文；如果用于 RL，奖励必须等 adequacy 或至少等一次正确性门跑完。论文在这里给出一条与直觉相反的经验：故障分类学教给测试生成器的信息，比原始故障本身更多。也就是说，把 7,384 个变异体按族（算术、精度、索引、同步等）归类后再喂给生成器，比直接给一堆变异样本更有效。

机制上可以这样理解：原始故障是点，分类学是结构。生成器从点里学不到“哪一类故障在什么归约规模下会逃逸”，从结构里能学到。这与容差盲带的公式直接对应——精度类故障的逃逸率 78.6% 是一个族级统计量，生成器据此可以专门构造长归约加半精度中间量的测试，而不是随机撒输入。代价是分类学本身要人工或半自动维护，且族边界在不同架构上会漂移；论文报告盲区随规模增长、集中在深层同构流水线，说明族级结论不能无条件跨架构搬运。

一个具体例子：在 agent 脚手架里，若反馈只回灌“编译失败/运行超时”，agent 会学会写更保守的 kernel；若反馈回灌“你的候选在精度族变异体上未被区分”，agent 才会去动数值路径。前者降低编译代价但牺牲性能上限，后者增加运行与评测代价但提高正确性可信度。这是反馈设计里最直接的成本交换。

六 · 流水线的可信边界：哪些步可以省，哪些不能

把四步的代价并列后，工程判断变得具体。生成步可以省 token（单轮提示）、可以省轮数（不做 agent）、可以省采样（不做 RL），这些节省只影响性能上限，不影响判决可信度。编译步可以省时间（合并翻译单元、增量编译），但必须保住变异体之间的编译隔离，否则 adequacy 的分母被污染。运行步可以省输入数（两个输入到 98.0%），但省输入的前提是已经付过全量 kill matrix 的成本。评测步不能省，因为它是唯一把 oracle 当被测对象的步骤；一旦省掉，前面三步的判决就回到“少量随机输入加宽松容差”的旧口径，而论文已经确定性地证明这个口径漏掉 16.9% 的带 witness 故障。

这条边界的实际含义是：变异分析不是流水线里的一个可选插件，而是流水线的校准层。它离线运行、成本高、产出是一个经过审计的测试协议；这个协议再被部署到在线流水线里，承担 RL 奖励与排行榜判决。论文把全部变异体与 kill matrix 以 KernelBench-M 的形式发布，正是为了让这个校准层可复现——没有这份数据，任何声称“我的 oracle 够好”的说法都无法被第三方用同一批探针检验。最后落在具体机制上：可信的 kernel 评测不是把容差调紧，而是先有一批带独立 witness 的已知错误探针，再用探针的杀死率给 oracle 打分；这个打分动作本身，就是方法与旧方案的分界线。

变异分析作为评测器：边界条件与系统代价

把变异分析当作 oracle 的“充分性度量”，其核心机制是确定性规则注入可编译故障，再以测试协议能否杀死这些故障来打分。这里的关键边界在于：分数只度量“被见证的故障”是否被检出，而不是度量真实错误空间。论文中 10,303 个注入故障里只有 7,384 个带有独立 kill witness，意味着约三成故障连“应当被杀死”的判据都不成立，这部分不计入分母。因此，一个协议拿到高分，只说明它覆盖了可被独立见证的那一子集，对无见证故障的盲区完全不可见。工程上必须把“见证覆盖率”与“检出率”分开报告，否则高分会掩盖注入规则本身的偏差。

失效条件集中在两类。第一类是精度类故障：官方检查漏掉 78.6% 的精度故障，而算术故障只漏 8.7%，说明容差盲带随归约规模增长，测试协议若只加输入分布而不收紧容差，对精度变异几乎无效。第二类是参考实现自身不可裁判：48 个整体架构中有两个问题的官方参考在 fp 口径下违反基准自己的容差，这类题目的任何变异分数都无意义。系统代价方面，一次完整评分要对每个候选 kernel 跑全部注入故障的编译—运行—比对，编译时间随故障数线性增长，10,303 个故障乘以 188 题意味着数万次 nvcc 调用；显存与运行时间则取决于测试输入数与归约规模，输入越激进，合法浮点方差越大，反而压缩了可用的容差窗口。

$$\text{detect}=\frac{|\{f\in F_{\text{wit}}\ :\ \text{protocol kills }f\}|}{|F_{\text{wit}}|},\qquad \text{coverage}=\frac{|F_{\text{wit}}|}{|F_{\text{inj}}|}$$

两个指标必须并列：论文的 98.0%（两输入/题）与 94.8%（held-out）都是 detect 口径，coverage 由 7,384/10,303 固定。工程判断是：把变异分数当作回归门禁时，应固定在同一批见证故障上比较，避免因注入规则变动导致分母漂移；同时把精度类故障单列一张子表，因为它们在官方口径下的逃逸率比算术类高一个量级，混合平均会稀释这一信号。
