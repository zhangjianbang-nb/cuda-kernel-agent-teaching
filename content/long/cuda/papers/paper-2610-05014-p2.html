一 · 迁移分数的口径本身就是一道窄门

MetaKernelBench 的评测口径可以拆成两层：单次尝试的加速比，以及跨 DSL 的成对提升。前者是 $$s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$ 的比值，后者要求同一道题在 CuTe DSL 与 TIRx 两个变体上分别做 solo 尝试与 skill-conditioned 尝试，并在匹配的单次预算下比较。最终聚合形式是 $$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau]$$，即阈值计数而非连续均值。这两层口径决定了它的适用边界：它测的是“同一问题、换一种 DSL 表达、经验能否复用”，而不是“经验能否跨问题复用”。一旦把结论外推到跨算子族、跨硬件、跨 dtype，口径就不再成立。阈值 τ 的选择还带来一个隐性代价：计数指标对分布尾部不敏感，一个把多数题推到 τ 附近、少数题崩掉的策略，与一个稳定中等提升的策略可能得到相同的 score，但生产端到端收益完全不同。用连续均值或分位数报告会损失与论文口径的可比性，这是使用该基准时必须自己补的一层。

具体机制上，成对设计把“模型能力”与“迁移增益”做了差分：solo 尝试给出该模型在该变体上的基线水平，skill-conditioned 尝试只多了一个自然语言 skill 作为输入，其余预算匹配。于是提升量 Δ 归因于 skill，而不是更多的采样次数或更长的上下文。代价是评测成本翻倍：每道题至少四次尝试（两个变体 × solo/skill），74 道题、六个模型、两个方向，尝试次数是 74×2×2×6 量级。若每次尝试都要编译、跑正确性门、测时延，编译时间与 GPU 占用会成为评测管线的主要开销，尤其在 CuTe DSL 侧模板实例化与 TIRx 侧编译路径差异明显时，单次尝试的墙钟时间不可忽略。这也是为什么论文强调“匹配的单次预算”——不匹配预算的对比会把“多试几次”误读为“迁移有效”。

二 · 负迁移：-19% 不是噪声，是失效模式的指纹

论文给出的成对提升区间是 -19% 到 +29%，跨六个模型、两个方向。负值的存在说明 skill 不是单调有益的正则项。从机制上看，负迁移至少有三条通路。第一条是 DSL 语义错配：CuTe DSL 的 layout/tile 抽象与 TIRx 的调度原语并不一一对应，源侧总结出的“把 tile 设成某个形状再沿某个轴切分”在目标 DSL 里可能对应一个完全不同的融合边界，skill 被照搬后触发额外的中间物化或同步。第二条是失败经验的有害蒸馏：论文明确 skill 的转移“whether or not the source attempt passes verification”，即源尝试未通过正确性门时其经验照样被传递。一个基于错误实现总结出的“这条融合链应该这样切”会把错误的结构性假设注入目标尝试，模型在目标 DSL 里会花预算去修复一个本不该存在的形状约束。第三条是预算挤占：skill 作为唯一额外输入占用了上下文，模型用于阅读目标 DSL 参考实现与错误信息的 token 变少，在长上下文模型上表现为对编译错误的响应变迟钝。

这三条通路的代价不同。语义错配的代价是时延与带宽：错误的 tile 选择导致 shared memory 占用上升或 global memory 访问模式劣化，加速比跌破 1；失败蒸馏的代价是正确性：目标尝试可能编译通过但在边界 shape 上给出错误结果，若评测只做单点输入检查就会漏过；预算挤占的代价是 token 与轮次：在匹配预算下，模型少读一轮错误信息就少一次修正机会。工程判断上，负迁移的检测不能只看均值，要看配对分布的左尾——哪些题、哪些模型方向出现负值，以及这些题的源尝试是否通过了验证。如果负值集中在源尝试失败的题上，说明蒸馏环节缺少“经验可信度”的门控；如果负值集中在某一 DSL 方向，说明 skill 的表达形式偏向源 DSL 的词汇，需要做 DSL 中立的抽象层。

三 · 与相邻工作的差别：它测的是“经验资产”，不是“单次实现”

与 KernelBench 系基准的差别在于评测对象。KernelBench 一类基准对每次尝试的实现打正确性与速度分，题目是独立的，尝试之间不共享状态；MetaKernelBench 的题目成对出现，且 skill 是跨尝试唯一的额外输入，评测对象从“这一次写得好不好”变成“上一次学到的东西这一次值多少钱”。与 Kevin、CUDA-L1、CUDA-L2、Dr. Kernel 这类多轮 RL 工作的差别在于优化目标：那些工作优化的是策略在单题上的收敛速度与最终性能，奖励来自编译、正确性与时延；MetaKernelBench 不训练策略，它用一个固定的成对协议去度量策略产出的经验是否可迁移，奖励信号是差分后的提升量。与 Astra、CudaForge、cuPilot 这类多 agent 框架的差别在于评测粒度：那些框架报告的是端到端任务完成率与加速比，MetaKernelBench 把“知识库/蒸馏技能”这一中间产物单独拎出来做受控变量。与 Geak 这类 Triton agent 评测的差别在于 DSL 对的构造：Geak 在单一 DSL 上评 agent 能力，MetaKernelBench 用“只差 DSL”的成对变体把语言表达差异隔离成自变量。

这个差别带来一个具体的工程代价：MetaKernelBench 不能替代 KernelBench 式的绝对性能排名。它的 score 是阈值计数，且成对设计让每道题的绝对加速比被差分抵消，一个在 CuTe 与 TIRx 上都只有 1.05× 但 skill 稳定带来 +10% 的模型，与一个在 CuTe 上 1.5×、TIRx 上 0.9× 且 skill 无增益的模型，在迁移分数上可能前者更高。若团队的目标是选一个能直接产出生产级 kernel 的模型，迁移分数不是决策依据；若目标是判断“把历史尝试沉淀成知识库是否值得投入工程成本”，迁移分数才是。另一个差别是验证强度：相邻工作多在单题上做正确性门加性能门，MetaKernelBench 的成对协议要求两个变体都过门才计入有效配对，配对缺失会改变分母 N，报告时必须说明配对完成率，否则 score 不可比。

四 · 适用边界：硬件、dtype、输入分布三条线

论文的结论只在给定硬件、基线与输入分布上成立，这是最硬的边界。硬件线上，CuTe DSL 的 tile 抽象与具体 SM 的 shared memory 容量、warp 调度粒度绑定，skill 里若含“这个 tile 在该卡上刚好放得下”的经验，换一张 shared memory 更小的卡就会从正迁移翻成负迁移；TIRx 侧的调度原语同样对 SM 数量与寄存器压力敏感。dtype 线上，融合子图的数值路径（累加精度、是否用 TF32、归约顺序）会改变正确性门的判定，源尝试在 fp16 上通过验证的经验迁移到 bf16 目标时，可能触发不同的舍入行为，正确性门若只做容差比较而不做逐元素分布检查，会放过系统性偏差。输入分布线上，74 道题是六个族的融合子图，shape 未在摘要中给出全部口径，若评测输入是固定 shape，skill 可能学到的是“这个 shape 下这样切”，而非“这类融合结构这样切”，生产端遇到动态 shape 时迁移收益归零甚至为负。

具体代价可以这样估：跨硬件迁移时，一个依赖 shared memory 容量的 tile 选择在目标卡上要么编译失败（静态断言），要么退化为多次 global memory 往返，带宽代价直接体现在时延上；跨 dtype 迁移时，正确性门的容差若按源 dtype 设定，目标 dtype 的误差分布不同，门限过松会让错误实现通过，门限过紧会把正确实现误杀，两者都污染配对统计。工程上使用该基准前应先做一次“边界自检”：把题目按是否含动态 shape、是否跨 dtype 归约、是否依赖特定 SM 容量分组，分别报告迁移提升，而不是只报一个总区间。论文的 -19% 到 +29% 是跨六模型两方向的聚合区间，聚合掩盖了分组差异，直接拿这个区间做决策会高估或低估特定场景的收益。

五 · 什么情况下不该用它

第一，不该用它做单模型的绝对性能选型。score 是阈值计数且成对差分，绝对加速比被抵消，无法回答“哪个模型写出的 kernel 最快”。第二，不该用它验证跨算子族的经验复用。题目成对且只差 DSL，跨族迁移（例如从 attention 融合到 norm 融合）不在评测范围内，用它推断“知识库能覆盖新算子”是外推。第三，不该用它做生产端到端收益的代理。离线配对提升与端到端时延之间隔着框架调度、内存分配、图捕获等环节，+29% 的配对提升在端到端上可能被 launch 开销与数据搬运吃掉；论文口径是单 kernel 时延，不是端到端。第四，不该在未控制基线强度时引用其加速比。若基线未开 TF32 或未用最强库实现，solo 尝试的 T_base 偏大，s_i 被高估，迁移提升的差分虽部分抵消了基线偏差，但阈值计数对基线漂移敏感。第五，不该把它当作正确性 oracle 的替代。skill 转移不依赖源尝试通过验证，这意味着基准本身容忍“从错误中学习”的路径，但生产部署需要独立的形式化或差分测试门，不能把基准的正确性门当作部署门。

还有一个更细的边界：当模型的 solo 能力已经接近该 DSL 的手写上限时，skill 的可提升空间被压缩，配对提升趋近于零甚至为负（预算挤占效应占主导）。此时用该基准判断“知识库无用”是错的，正确判断是“该模型在该 DSL 上已无迁移余量”。区分这两种情况需要看 solo 尝试的绝对加速比分布：若 solo 已普遍高于某个水平，迁移分数的低值不应被解读为经验无价值。反过来，若 solo 普遍低于 1，说明模型尚未掌握该 DSL 的基本写法，此时 skill 的正迁移可能只是“教会了基本结构”，而非“复用了领域经验”，这种提升在生产上不可持续，因为下一次遇到新结构仍然要从头学。

六 · 失效模式的工程检测顺序

把上述边界落成一条可执行的检测链：先查配对完成率与源尝试验证状态，把 skill 按“源通过/源失败”分组，分别看提升分布；再查 DSL 方向不对称性，若某一方向系统性负迁移，优先怀疑 skill 的词汇偏向源 DSL；再查题目族分组，把含动态 shape 与跨 dtype 归约的题单列，看提升是否集中在固定 shape 的题上；最后查预算敏感性，把单次预算减半重跑，若提升消失则说明增益来自更多试错而非经验复用。每一步的代价都可控：分组重跑只增加统计开销，预算减半重跑增加一次完整评测的墙钟时间，但能排除“多试几次”的混淆。一个具体的例子是：某模型在 CuTe→TIRx 方向提升 +20%，但源失败组的提升为 -15%，源通过组为 +25%，说明蒸馏环节缺少可信度门控，工程上应在 skill 生成前加一道“源尝试必须过正确性门”的过滤，代价是损失一部分从失败中学习的样本，收益是消除负迁移的左尾。

最终落在机制上：MetaKernelBench 的价值不在于给出一个可排名的分数，而在于把“经验资产”变成可受控测量的变量——成对变体隔离 DSL，匹配预算隔离试错次数，skill 作为唯一额外输入隔离知识注入。使用它的正确姿势是把它当作一个差分实验平台：任何关于知识库、蒸馏技能、跨 DSL 迁移的工程假设，都应该在这个平台上以配对提升的分布形态来验证，而不是以一个聚合区间来背书。当配对提升的方差大于均值、或负值集中在可解释的失效通路上时，基准给出的是诊断信号而非结论；把诊断信号误读为结论，是这个基准最容易被误用的地方。

迁移增益的符号不定：什么时候这份“经验”反而是负资产

MetaKernelBench 的配对口径把迁移效应压成一个可正可负的标量：同一模型、同一目标变体、匹配的 per-attempt 预算，唯一变量是“是否携带来自另一门 DSL 的自然语言 skill”。摘要给出的跨六个模型、双向配对提升区间是 −19% 到 +29%——这个区间本身就是边界声明：迁移不是单调增益，存在系统性的负迁移。机制上，负迁移来自 skill 的抽象层级错配：源尝试蒸馏出的是 CuTe 的 tile/layout 级表述（如某个 fused subgraph 的 tiling 与 pipeline 切分），搬到 TIRx 侧时，若目标 DSL 的调度原语不提供对应的表达，模型会把自然语言指令硬翻译成不存在的构造，产生编译失败或退化实现；而 skill 在源尝试未通过验证时同样被传递，等于把一次失败尝试的错误直觉制度化。代价体现在 token 与编译时间上：skill 作为唯一额外输入占用上下文，条件尝试的有效搜索预算被压缩，编译—运行—profile 的反馈轮次减少，正确性门与性能门更容易在早期被触发回退。

$$\Delta_i=\frac{T_{\text{solo},i}-T_{\text{skill},i}}{T_{\text{solo},i}},\qquad \text{lift}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\Delta_i>0]\cdot\Delta_i$$

适用边界由题目构造方式直接划定：74 道题是六个 family 的 fused subgraph，每道题以 CuTe DSL 与 TIRx 变体成对出现，二者“只差 DSL”。这意味着基准测的是同一算法结构下的语言层迁移，而非跨算子族、跨 dtype、跨硬件、跨框架的迁移。一旦目标问题的数学结构或访存模式偏离源 family，skill 中隐含的 roofline 判断（compute-bound 还是 memory-bound、是否值得做 split-K）就不再成立，迁移分数不能外推。跨硬件尤其危险：摘要未给出跨架构验证，而 tile 尺寸与 shared memory 预算的结论高度依赖 SM 结构与带宽比，把 A 卡上的经验搬到 B 卡属于未被该基准覆盖的推断。
