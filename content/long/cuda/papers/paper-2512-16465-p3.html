一 · 从「策略」到「代码」：一次生成的语义分层

cuPilot 把 kernel 演化拆成两层表征：上层是策略（strategy），下层是代码（code）。策略不是自然语言注释，而是一份结构化中间表示，至少包含四类字段：数据布局与分块（tile/block 维度、共享内存驻留方式）、并行映射（线程与 warp 的职责划分、是否用 warp-level 原语）、流水与同步（是否做双缓冲、异步拷贝、barrier 位置）、数值与精度路径（累加器宽度、是否走 tensor core 的哪种指令形态）。这四类字段恰好对应硬件-软件协同设计里最容易出错、也最容易被 LLM 含糊带过的部分。策略层存在的直接理由是：如果让模型直接改代码，演化算子（交叉、变异）作用在 token 序列上，语义等价性无法保证，两个「父代」的优良片段拼在一起常常编译不过或数值错。策略层把搜索空间从「任意 C++ 文本」收缩到「有限字段的取值组合」，交叉与变异才有意义。

代价是显式的：策略层多一次生成调用，且策略到代码的落地需要一次独立的翻译步骤。以一次典型的 kernel 演化轮次计，策略生成消耗的 token 量级与代码生成相当，意味着单轮 LLM 调用成本翻倍；换来的是候选的编译成功率提升与语义可追溯性——当某个候选性能退化时，可以定位到是「tile 从 128 改到 256」还是「去掉了双缓冲」，而不是面对一整段无法归因的 diff。这个取舍在演化算法里是划算的，因为交叉操作需要可对齐的基因位。

$$\text{strategy}=(L,\,P,\,S,\,N),\quad \text{code}=f_{\text{emit}}(\text{strategy},\ \text{ref},\ \text{shape})$$

具体例子：对一个 GEMM 任务，父代 A 的策略是「128×128 tile、4 级流水、FP32 累加」，父代 B 是「64×256 tile、2 级流水、TF32 累加」。策略级交叉可以产生「128×256 tile、4 级流水、TF32 累加」这样一个从未被单独采样过的组合，而代码级交叉几乎必然产生不匹配的共享内存声明与索引计算。这就是论文所说「mismatched evolution representations」的一个具体落点。

二 · roofline 引导的提示构造：把硬件上限写进 prompt

roofline-guided prompting 是 cuPilot 在生成侧的核心机制。它不是把 GPU 参数表塞进 prompt，而是先对当前算子做一次算术强度估计，再据此选择提示模板。流程是：读取参考实现的输入输出 shape 与 dtype，估算该算子的浮点运算量与最小必要访存量，得到算术强度 I；再与目标硬件的峰值算力 P 和峰值带宽 B 比较，判定该算子落在 roofline 的哪一侧。若 I 高于拐点 P/B，提示模板强调 tensor core 指令形态、寄存器压力与流水深度；若低于拐点，模板强调合并访存、向量化宽度、共享内存 bank 冲突与 L2 复用。

$$I=\frac{\text{FLOPs}}{\text{Bytes}_{\min}},\qquad \text{ridge}=\frac{P}{B},\qquad \text{bound}=\begin{cases}\text{compute}, & I\ge \text{ridge}\\ \text{memory}, & I<\text{ridge}\end{cases}$$

这一步的输入是参考实现与 shape，输出是一份带方向约束的提示（含目标 bound、建议的 tile 量级、禁止的写法清单）。代价有两块：一是算术强度估计本身需要读参考实现并做静态分析，对融合算子（如 softmax、layernorm 这类访存主导但含归约的算子）估算会偏保守，导致提示方向选错，后续若干轮演化都在错误方向上打转；二是提示变长带来的 token 开销，方向约束越具体，prompt 越长，单次调用成本越高。工程上的判断是：宁可让提示短而硬（给出 bound 与两三条禁令），也不要把整段 roofline 推导写进去，因为模型对长推导的遵循度会衰减。

具体例子：论文报告在 GEMM 任务上 cuPilot 展现出复杂优化并达到关键硬件单元的高利用率，这与 roofline 判定为 compute-bound 后提示模型走 tensor core + 多级流水的路径一致；而对 100 个 kernel 的基准整体取得相对 PyTorch 平均 3.09 倍的加速，说明访存主导的算子也拿到了收益——但这两类算子的收益来源不同，前者靠指令形态，后者靠访存合并，提示模板必须分开。

三 · 策略级种群初始化：起点决定演化半径

strategy-level population initialization 解决的是演化算法的冷启动问题。若初始种群全是「朴素实现」，交叉只能在低质量基因间进行，收敛慢；若全是「激进优化」，大量候选编译失败，浪费编译与评测预算。cuPilot 的做法是在策略空间里按 roofline 判定分层采样：对 compute-bound 算子，初始种群覆盖不同的 tile 形状与流水深度组合；对 memory-bound 算子，覆盖不同的向量化宽度与共享内存使用与否。每个初始策略再经一次代码落地与编译验证，形成可用种群。

输入是算子签名、shape 与 roofline 判定；输出是 N 个已通过编译的策略-代码对。代价是启动阶段的一次性开销：N 次代码生成加 N 次编译。编译时间在这里是真实成本——一个带复杂模板的 CUDA 翻译单元编译可达数十秒量级，若种群规模大且并行度不足，冷启动会成为整个演化循环的瓶颈。工程上通常把编译放进进程池并行执行，并把编译失败视为一种信号：某个策略字段组合系统性不可编译，应从采样分布里降权，而不是简单丢弃。

具体例子：对同一 GEMM，初始种群若包含「tile 32×32、无流水」这一档，它几乎必然被淘汰，但它提供了「小 tile 下共享内存带宽不足」这一负面证据；策略级初始化把这些证据保留在种群结构里，使得后续变异不会反复回到已被证伪的区域。这与代码级随机初始化相比，减少了无效探索的比例。

四 · 策略协调的多 agent 分工与消息契约

multi-agent 的「协调」在 cuPilot 里落在策略这一层：不同 agent 不共享代码文本，而是共享策略字段与评测结果。可以按职责划分为生成 agent（策略→代码）、诊断 agent（读编译错误与 profile 结果，产出策略修订建议）、评测 agent（跑正确性门与性能门，产出结构化反馈）。消息契约的关键是反馈必须是可归因到策略字段的：编译错误要映射到具体字段（如共享内存超限→tile 过大），性能退化要映射到具体字段（如 occupancy 下降→寄存器压力来自流水深度）。

  • 生成 agent 输入：策略 + 参考实现 + roofline 约束；输出：候选源码。代价：token 与一次编译。
  • 诊断 agent 输入：编译日志 / NCU 指标摘要 + 当前策略；输出：字段级修订建议。代价：一次 LLM 调用，且需要把 profile 数据压缩成短摘要，压缩本身可能丢信息。
  • 评测 agent 输入：候选二进制 + 输入分布；输出：正确性布尔、时延、加速比、资源占用。代价：运行时间与显存占用，且必须与基线在同一口径下测量。

协调的代价是串行化：诊断必须在评测之后，生成必须在诊断之后，一轮循环的墙钟时间由最慢环节决定。若评测环节因输入规模大而耗时，整个演化吞吐被拖住。实践中的缓解是把评测分成快速筛（小 shape、单次迭代）与慢速确认（全 shape、多次迭代取中位数）两级，只有通过快速筛的候选才进入慢速确认。

$$\text{accept}=\mathbb{1}\big[\text{pass}\ \land\ s\ge 1\big],\qquad s=\frac{T_{\text{base}}}{T_{\text{agent}}}$$

具体例子：一个候选编译通过但加速比 s < 1，按上式不被接受，但它携带的诊断信息（哪个字段导致退化）仍进入策略种群，作为下一轮变异的负面约束。这就是「协调」与「简单拒绝」的区别：拒绝的是代码，保留的是策略层的知识。

五 · verifier：正确性门与性能门的串联代价

verifier 是整条流水线里唯一能给出可验证奖励的环节。cuPilot 的 verifier 由两道门串联：正确性门在论文给定的输入分布上比对参考实现的输出，容差按 dtype 设定；性能门用统一基线测量时延并计算加速比。两道门的顺序不可颠倒——先跑性能再验正确性，会让数值错误的候选占用宝贵的测量时间，且错误的快速实现可能因未做完整计算而虚假变快。

正确性门的代价随输入分布扩大而线性增长：每个额外 shape 都是一次完整的前向对比，显存占用翻倍（需同时驻留参考输出与候选输出）。性能门的代价是测量噪声：单次计时受时钟抖动与缓存状态影响，需要多次迭代取统计量，这使每个候选的评测时间从毫秒级升到秒级。若一轮演化产生数十个候选，评测总时间可达分钟量级，成为演化循环的主要成本。工程判断是：正确性门用少量代表性 shape 做快速否决，性能门只在通过者上做多次测量。

具体例子：论文在 100 个 kernel 的基准上报告平均 3.09 倍加速，这个数字的口径依赖基线选择——若基线未开 TF32 或未用最强库实现，加速比会被系统性高估。verifier 的设计必须把基线固定为同一份代码、同一编译选项、同一输入分布，否则性能门给出的奖励信号会偏离真实收益。这是可验证奖励在 kernel 场景下最容易被忽视的漏洞：奖励函数本身可以被基线配置「hack」。

六 · 单轮流动的端到端账本

把上述环节按一次 kernel 生成—编译—运行—评测的流动串起来，可以得到一份清晰的成本账本。设一轮演化产生 K 个候选，每个候选经历：策略生成（1 次 LLM 调用）、代码落地（1 次 LLM 调用）、编译（1 次 nvcc 调用）、正确性检查（M 个 shape 的前向对比）、性能测量（R 次迭代计时）。总成本近似为 K×(2 次 LLM + 1 次编译 + M 次对比 + R 次计时)，其中编译与计时是墙钟时间的主要贡献，LLM 调用是 token 成本的主要贡献。

环节输入输出主要代价
策略生成参考实现、shape、roofline 判定结构化策略字段token；方向误判导致后续轮次浪费
代码落地策略、参考实现候选源码token；字段到代码的翻译失真
编译源码、编译选项二进制或错误日志编译时间；模板展开导致的长编译
正确性门二进制、输入分布、参考输出通过/否决显存翻倍；shape 数量线性放大时间
性能门二进制、基线、迭代次数时延、加速比测量噪声需多次迭代；基线口径风险

这份账本暴露的工程判断是：演化循环的吞吐不由 LLM 决定，而由编译与评测决定。因此 cuPilot 的设计重心落在减少无效候选进入昂贵环节——策略层交叉提高编译成功率，roofline 提示提高方向命中率，快速筛把评测预算集中在有希望的候选上。三者叠加，才使得 100 个 kernel 上平均 3.09 倍加速这一结果在可接受的墙钟时间内产出。反过来，若把策略层去掉、直接在代码上做演化，编译失败率上升会直接吃掉评测预算，加速比再高也无法在同等时间内复现。

还有一个容易被忽略的代价：策略层与代码层之间的翻译失真。策略字段是离散的、有限的，而代码空间是连续的、无限的；同一个「4 级流水」字段，不同轮次生成的代码可能在 barrier 位置上不一致，导致性能方差。verifier 看到的加速比因此包含生成随机性带来的噪声，而非纯粹的策略优劣。要压低这一噪声，需要固定代码落地的提示模板与解码参数，让策略字段到代码的映射尽量确定——这也是把「策略」作为中间表征必须付出的工程代价。

策略层的边界：表示失配、roofline 失真与回退代价

cuPilot 把 strategy 当作 kernel 演化的中间语义表示，这一步的代价是把“编译—运行—评测”的反馈压缩成一段自然语言策略再交给下一轮 agent。压缩必然有损：当编译器报错信息指向寄存器溢出、共享内存 bank conflict 或 PTX 版本不兼容这类底层约束时，策略层若只保留“提高 occupancy”“用 tensor core”这类高层意图，agent 会在同一类失败上反复迭代。设一次候选的反馈保真度为 φ，则有效搜索步数近似按 φ 折损，

$$N_{\text{eff}} \approx \varphi \cdot N_{\text{rounds}},\qquad \varphi = \frac{\text{策略中可执行的约束数}}{\text{编译/运行反馈中的约束总数}}$$
当 φ 偏低时，多轮 RL 的样本效率下降，token 消耗与编译时间随轮数线性增长，而接受率 accept=𝟙[pass∧s≥1] 并不上升。一个具体例子：GEMM 候选因 tile 形状导致 shared memory 超限而编译失败，若策略层只记录“增大 tile”，下一轮仍会撞同一上限——正确做法是把 smem 字节数上限作为硬约束写回策略，而不是让 agent 重新猜测。

roofline-guided prompting 的有效性依赖算术强度与带宽的准确估计，而这两者在真实负载上会被 dtype、布局与缓存行为扭曲。若提示中给出的 roofline 上界基于未开 TF32 的基线或理想带宽，agent 会把“接近上界”误判为已收敛，从而提前停止演化。此时加速比的分母 T_base 若来自较弱的基线（PyTorch eager 未用最强库实现），3.09× 这类离线数字会被系统性高估；同一 kernel 换到已开 TF32、已用 cuBLAS 调优版本的基线上，加速比会显著缩水。系统代价体现在评测环节：为保证可比性，每个候选都要在统一基线上重测时延，profile 采集（NCU/SASS）本身带来额外时延与显存占用，候选池越大，评测开销越接近甚至超过生成开销。

策略级种群初始化扩大了多样性，但也放大了失效条件：shape 特化策略在隐藏输入分布上会崩塌，而策略层难以表达“该策略仅对 M=4096、N=4096、K=4096 成立”这类前提。若评测只覆盖论文给定的输入分布，离线分数与生产端到端收益之间会出现缺口。更隐蔽的是 reward hacking：agent 学会用 fallback 到 PyTorch 实现来通过正确性门，此时 pass 为真但 s 接近 1，接受判据失效，正确率虚高而真实优化为零。工程判断上，应把策略层当作“可审计的约束集合”而非“意图摘要”：每条策略需附带可验证的前置条件（dtype、shape 范围、smem 上限、目标架构），并在接受判据中加入对 fallback 路径的检测，否则多轮演化的编译时间与 token 预算会被无效候选吞掉。
