一 · 适用边界：可验证性是入场券，不是通行证

CUDA-L1 的方法骨架决定了它的适用边界由一条硬约束划出：训练信号必须来自可被工具链自动判定的执行结果。具体机制上，闭环的每一环——nvcc 编译、GPU 运行、与参考实现逐元素比对、计时——都要求算子具备三个条件：有确定的参考实现可作为 oracle、输入分布可被采样复现、单次运行时间短到能支撑同题多候选采样。三者缺一，对比奖励就退化为噪声。以逐元素比对为例，判定逻辑是 correct_i = all(|y_i - y_ref| ≤ tol)，其中 tol 在给定材料中未定义；这意味着对于归约类算子（softmax、layernorm 的跨行归约）或含原子操作的散射写入，浮点累加顺序不同会带来末位差异，若 tol 取得过紧，正确候选被误判为负例，若取得过松，错误候选混入正例，两种误判都直接污染成对偏好损失的梯度方向。

代价体现在两个维度。其一是单题成本：候选数 k 增加时，编译与 GPU 运行开销按 O(k) 线性放大，而对比损失只需要一对正负样本，多余候选的边际信息收益递减，工程上必须在 k 与单题吞吐之间做取舍。其二是覆盖面：动态 shape、数据依赖的控制流、需要多 kernel 协同的融合算子，都难以用单次静态比对完整覆盖，这类任务落在方法边界之外。一个具体例子是带 mask 的 attention：参考实现与候选实现在极长序列上的数值分歧往往集中在被 mask 的位置，若 oracle 只比对未 mask 区域，负例池会漏掉真实的越界写入错误。判断是明确的：CUDA-L1 适合算子级、语义封闭、可逐元素校验的任务；不适合把正确性定义在跨算子契约或全局不变量上的场景。

二 · 跨 shape 迁移：计时口径比数值口径更脆弱

跨 shape 迁移的风险不在正确性侧，而在性能侧。正确性判定对 shape 是局部性质：只要参考实现与候选在同一输入上比对通过，结论就成立。但加速比 t_base / t_i 是强 shape 依赖的量，同一 kernel 在小 shape 上受 launch 开销支配、在大 shape 上受带宽或占用率支配，最优实现策略完全不同。对比奖励把同题多候选排序后取相对偏好，模型学到的是“在该题该 shape 分布下更快”，而非“在该算子上更快”。若评测输入分布只覆盖单一 shape 档位，策略会过拟合到该档位的 tiling 与向量化宽度。

$$\text{score}(s) = \frac{1}{|S|}\sum_{s\in S}\log\frac{t_{\text{base}}(s)}{t_i(s)}$$

上式提示了工程上的补救方向：把奖励从单点 shape 扩展为 shape 集合上的聚合，代价是候选评测次数乘以 |S|，单题编译与运行成本同步放大，且计时噪声在短 kernel 上被放大——中位数计时若不含数据传输、不含 warmup 次数说明，跨 shape 比较的口径就不一致。给定材料明确指出计时方法（是否取中位数、是否含数据传输）与基线配置均未给出，这使跨 shape 的加速比结论无法直接引用。一个具体例子：同一 GEMM 候选在 M=N=K=4096 上因 shared memory 分块获益，在 M=1 的 decode 场景下该分块反而增加无效计算，若训练分布偏前者，模型在后者上的排序会系统性错误。判断是：跨 shape 迁移必须以 shape 分层评测为前提，否则对比奖励学到的是分布偏置而非算子能力。

三 · 跨 GPU 与 dtype 迁移：硬件反馈的不可移植性

跨 GPU 迁移的困难来自反馈信号的硬件绑定。编译与运行反馈是特定架构的产物：occupancy 上限、shared memory 容量、warp 调度粒度、L2 划分都随 SM 版本变化，一个在某一代 GPU 上通过计时排序胜出的候选，换到另一代可能因寄存器压力溢出而变慢。对比奖励不携带硬件元信息，模型无法从“更快”这一相对信号中分离出“因为该架构的某条指令吞吐高”这一因果，迁移时策略携带的是架构相关的隐式偏好。代价是双重的：跨代复评需要重新采样候选并重新计时，等于重跑一轮训练闭环的评测段；而若只在单一架构上训练与评测，结论的外推范围就被锁死在该架构。

dtype 迁移的问题更靠近正确性 oracle。fp32 与 bf16/fp16 的容差需求相差数个数量级，给定材料未给出容差标准，意味着同一 tol 被套用到不同精度时，低精度候选的舍入误差可能触发误判。更关键的是混合精度累加：候选在 fp16 输入下用 fp32 累加器是常见优化，但其输出与纯 fp16 参考实现的差异是否落在容差内，取决于 tol 的定义方式（绝对、相对还是 ULP）。工程判断是：dtype 维度必须在 oracle 中显式分层，把容差作为 dtype 的函数而非全局常量，否则负例池会系统性地把合法的精度优化标记为错误，训练信号偏向保守实现，压制了真正有价值的低精度 kernel。

四 · 跨框架迁移：语义契约在框架侧，不在 kernel 侧

跨框架迁移的边界最容易被低估。CUDA-L1 的输入是算子语义加参考实现，而真实框架（PyTorch、JAX、Triton 生态）对同一算子的语义契约包含大量 kernel 之外的内容：广播规则、stride 与内存布局约定、原地操作语义、autograd 图的衔接、stream 与同步语义。候选 kernel 在孤立比对中通过，接入框架后可能因布局假设（如假定 contiguous）在非连续输入上产生错误结果，或因缺少 stream 感知在并发场景下出现竞态。这类失败不会出现在逐元素比对的负例池里，因为评测环境本身就是隔离的。

代价体现在集成阶段：把训练出的 kernel 接入生产需要补齐布局断言、边界检查与 fallback 路径，这些工程量不在训练闭环内，也无法被对比奖励激励。一个具体例子是 layernorm 的候选实现假定最后一维连续，框架在转置视图上调用时该假设失效，正确性 oracle 在隔离测试中给出通过，生产端却得到错误输出。判断是：CUDA-L1 产出的是算子级候选，不是框架级组件；跨框架迁移的可信度取决于评测 harness 是否复现了框架的调用契约，而给定材料未说明评测是否包含布局与并发维度，因此其结论向框架侧的迁移需要独立验证，不能由训练阶段的加速比直接背书。

五 · 与相邻工作的差别：相对排序与绝对回归的分野

与同方向工作的差别应落在信号构造上，而非口号式的“更强”。CUDA-L1 的核心选择是用同题多候选的相对排序替代绝对分数回归：奖励 r_i = α·1[correct_i] + β·log(t_base/t_i) 只用于排序，成对偏好损失 −log σ(r_{i+} − r_{i−}) 消去了基线 t_base 的绝对尺度，使训练对计时噪声的绝对漂移不敏感——这是相对排序相对绝对回归的结构性优势。代价是它把信息压缩成序关系，丢弃了加速比的绝对幅度：一个 1.01× 与一个 3× 的候选若同处正例侧，对损失的贡献由配对方式决定而非由真实收益决定，模型可能在高收益方向上学习不足。

与以执行反馈驱动多轮迭代的 agent 脚手架类工作相比，CUDA-L1 把编译失败与数值不一致显式纳入负例池，使负例来源不依赖人工标注，这是其数据自增循环的关键；但代价是负例池的质量完全由 oracle 的判定精度决定，容差与边界输入未定义时，负例池同时容纳真错误与假错误。与以硬件反馈做优化的框架类工作相比，CUDA-L1 不做 profile 级归因（未使用 NCU/SASS 指标指导搜索），因此它学到的是端到端计时排序，而非“哪条指令或哪个 stall 是瓶颈”的因果解释，迁移到新架构时缺少可解释的调整依据。判断是：CUDA-L1 的贡献在训练信号的可验证性与相对性，其边界在于 oracle 精度、shape 分布覆盖与硬件绑定；把它当作算子级候选生成器是合适的，把它当作跨平台性能保证则超出了方法能提供的证据范围。

六 · 开放问题：哪些缺口必须补，哪些是方法固有

给定材料列出的缺口可按可补与固有分两类。可补的：基准题目数量、算子覆盖与输入分布未给出，导致无法核对防作弊设计是否充分——若题目集小且公开，模型可能记忆题目而非学习优化，对比奖励无法区分记忆与泛化，这需要私有留出集与分布偏移测试来补；计时口径未定义（是否中位数、是否含数据传输、warmup 次数），使加速比结论不可复现，需在评测协议中固定；容差标准未给出，需按 dtype 与算子类别分层定义并公开。固有的：对比奖励依赖同题多候选采样，编译与 GPU 运行成本随候选数线性增长，这是方法结构决定的，只能通过候选剪枝（先用编译与正确性过滤，再对通过者计时）降低常数，无法消除线性项；仅靠数值比对缺少形式化或合约级验证，浮点边界上的判定风险是 oracle 设计的内在局限，需引入区间算术或参考高精度实现作为补充 oracle，代价是评测时延上升。

防作弊是另一个必须落到机制上的开放问题。正确性先于性能的排序规则压缩了“以错误换速度”的空间，但没有封死计时侧作弊：候选可通过缓存结果、跳过必要同步或利用评测输入的可预测性获得虚高加速比。工程上的对策是在计时前插入输入扰动与结果复核，并对多次运行取分布而非单点，代价是单题评测时间成倍增加。判断落在具体机制上：CUDA-L1 的可信度不取决于对比损失的形式，而取决于 oracle 的分层精度、计时协议的封闭性与留出集的不可见性；这三项在给定材料中均未闭合，因此其加速比结论应被视为方向性证据，生产采纳前必须以独立 harness 复评，并把候选剪枝与 oracle 分层作为部署前的强制门。

边界不在算法而在评测契约：迁移、容差与单题成本

CUDA-L1 的对比奖励成立的前提是“同题多候选可排序”，这决定了它的适用边界首先不是模型能力，而是评测契约的可复现性。跨 shape 迁移时，同一算子在不同输入规模下最优策略会切换（例如固定 tile 的 shared memory 复用在大 shape 上收益显著，在小 shape 上被 launch 开销吞掉），而对比奖励只对同题候选排序，不携带跨 shape 的偏好约束；模型学到的“更快”是相对该题基线，换 shape 后正负例的相对次序可能反转，策略需要重新采样才能校正。跨 GPU 迁移同理：occupancy 与访存带宽比变化会改变候选排序，若训练与部署的 GPU 架构不一致，排序信号即失效。跨 dtype 的风险更直接——正确性 oracle 仅做逐元素数值比对且容差未定义，fp16/bf16 累加顺序差异落在容差边界时，正例与负例的划分本身不稳定，成对偏好损失会把噪声当信号。跨框架（PyTorch/Triton/CuTe 混用）时，基线实现的口径不一致会让加速比不可比，这是比模型泛化更早失效的一环。

单题成本是第二个硬边界。候选数 k 增加时，编译与 GPU 运行开销线性放大，可写成 C(q) ≈ k·(ccompile + crun + cverify)，其中 ccompile 对模板密集的 CuTe 候选远高于简单 CUDA C++，cverify 随输出规模增长。失败编译率越高，负例池越丰富但有效正例越稀疏，单位 token 的训练收益下降；这与“执行反馈驱动数据自增”的叙事存在张力——自增的是负例，正例仍依赖采样命中。工程判断是：候选数应受单题时延预算约束而非固定值，且需按算子类型分层（访存型算子编译便宜、可多采样；模板型算子应减少候选、提高单次编译质量）。

shape最优 tile/launch 策略切换，同题排序不跨题传递需按 shape 分桶重采样，采样成本上升

与相邻工作的差别应落在“信号来源”而非“是否用 RL”：监督微调把正确实现当标签，缺少负例的相对结构；单轮提示无执行回灌，无法区分编译失败与数值错误；形式验证路线给出的是正确性保证而非性能排序，二者正交——CUDA-L1 的数值比对 oracle 不构成合约级验证，浮点边界上的判定风险只能靠容差设计与边界输入覆盖来压，而不能靠对比奖励本身消除。因此它的合理定位是“在锁定评测口径下的算子级搜索加速器”，而非可跨平台直接复用的优化器；上线门应是基准题目数量、输入分布、计时方法（是否取中位数、是否含数据传输）与容差标准四项先固化，再谈加速比结论的可引用性。
