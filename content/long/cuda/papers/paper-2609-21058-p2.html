一 · 基准的边界：KernelBench level 1 与 DLRM-Bench 的两种口径

这篇论文的评测面由两块拼成，二者口径不同，混读会把结论读歪。第一块是 KernelBench level 1，56 道题，覆盖逐元素、归约、矩阵乘、卷积等单算子；第二块是论文自建的 DLRM-Bench，12 道推荐系统 kernel 题，沿用 KernelBench 的题面格式（参考实现 + 输入生成 + 正确性检查），但算子分布偏向 embedding 查表、特征交叉、MLP 这类推荐模型主干。两块基准的差别不在难度，而在“问题是否属于真实模型的关键路径”：KernelBench level 1 是合成算子集合，DLRM-Bench 是从一个具体模型里剥出来的热点。

56 这个数字本身携带口径信息。论文报出的“独立验证的加速”是 22/56，而“正确”是 91.1%（即 56 题中约 51 题通过正确性门）。两个分母相同、分子不同，说明存在一条严格的分界线：正确不等于快，快必须经过独立复测。这条分界线的工程含义是，任何只报“正确率”的评测都在掩盖性能失败；任何只报“加速比”的评测都在掩盖编译失败与数值错误。DLRM-Bench 的 12 题则报出 41.7% 的胜率与 1.552x 的中位加速，胜率的分母是 12，样本量小，单题翻转就能让胜率跳动 8 个百分点以上，因此这个数字只适合做方向性判断，不适合做模型间排序。

两块基准共享同一套题面格式，这带来一个隐性代价：题面格式决定了输入生成方式，而输入生成方式决定了 shape 分布。KernelBench 格式的题面通常给一组固定 shape 或一个 shape 采样区间，候选 kernel 若针对该区间做了特化（比如把 block size 写死成 128、把 tile 形状对齐到某个 M/N/K），离线分数会好看，但这属于对评测口径的拟合而非对算子本身的优化。论文用“独立验证”这一步来压制这种拟合：候选必须在评测方控制的输入上重新跑正确性与时延，而不是在生成方自报的数字上签字。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

上式是这类基准通用的 fast-p 形式：$N$ 是题数，$s_i$ 是第 $i$ 题相对基线的加速比，$\tau$ 是判定阈值。它把连续的速度压成一个伯努利计数，好处是抗离群值，坏处是丢掉幅度信息——一道 10x 的题和一道刚过阈值的题贡献相同。论文同时报中位数（1.235x、1.552x）来补回幅度，但中位数对分母敏感：若某题基线实现本身很弱，$s_i$ 会被系统性抬高。这就是为什么“基线选择”比“指标选择”更能决定结论。

二 · 基线与 dtype：加速比的分母才是真正的争议点

论文的基线口径是 PyTorch eager、torch.compile 与论文指定的库实现三者并列。这三者的性能差距在不同算子上可以差出一个数量级：逐元素算子上 eager 与 compile 接近，卷积与 GEMM 上 compile 可能显著落后于 cuBLAS/cuDNN。若候选 kernel 只与 eager 比，得到的加速比里混进了“编译器没优化好”的成分，而不是“LLM 写出了更好的 kernel”。因此可核查的口径必须写明每题用的是哪条基线、是否取了三条基线中的最快者。论文报出的 1.235x 中位加速，只有在基线取最强实现时才有工程意义；若基线取 eager，这个数字会被高估，且高估幅度随算子类型漂移。

dtype 是第二个不可比源。GPU 上 fp32 与 tf32 的吞吐差距来自 Tensor Core 的输入精度截断，bf16/fp16 又在此基础上翻倍。若基线以 fp32 运行而候选 kernel 内部把输入降为 tf32 做乘加，加速比里就混进了精度让渡——数值上可能仍通过正确性检查（因为检查容差通常按 fp32 设定得较松），但这不是同精度比较。论文摘要未给出逐题的 dtype 清单，这构成本部分最需要标注的不可核查项：读者无法从摘要判断 22 个加速里有几个是跨 dtype 比较的产物。工程上可核查的做法是要求候选与基线在同一 dtype、同一 TF32 开关状态下测量，并在题面里显式记录该开关。

计时口径的代价常被低估。一次 kernel 时延测量若不做显式同步，CUDA 的异步发射会让 host 端计时器读到的是入队时间而非执行时间；若不做预热，首次调用包含 JIT 编译、上下文初始化与 cache 冷启动，能把一个微秒级 kernel 测成毫秒级。论文的“独立验证”若要可信，必须规定预热轮数、重复次数与取中位还是取最小。这些细节在摘要层面缺失，意味着 1.235x 这个数字的可复现性依赖于论文正文的测量协议，而非摘要本身。

三 · 隐藏 shape 与分布：离线分数在生产上崩塌的机制

LLM 生成 kernel 的一个结构性弱点是它看得见题面里的 shape。KernelBench 格式的题面通常把输入维度写在参考实现里，模型据此可以推出 M/N/K、batch、通道数，进而把 tile 大小、unroll 因子、shared memory 用量全部写死。这在离线评测里是合法优化，在生产里是定时炸弹：真实模型的 shape 随 batch、序列长度、并发数变化，写死的 tile 在非对齐 shape 上会退化成边界分支密集的低效路径，甚至因 shared memory 超限而无法启动。

论文对此的处理方式是“独立验证”——评测方用自己的输入分布重跑，而不是沿用生成时的输入。这个机制的正确性代价是：候选 kernel 在评测输入上可能直接编译失败或越界，从而把“正确率”从生成方的自报值拉低。91.1% 这个正确率若是在评测方控制的输入上得到的，其可信度显著高于生成方自报；但摘要未说明评测输入是否覆盖了非对齐 shape、极端 batch、空张量等边界。工程判断上，一个可信的 shape 口径应至少包含三档：对齐 shape（性能上限）、非对齐 shape（边界分支代价）、动态 shape（是否支持符号化维度）。缺第三档，就无法区分“特化 kernel”与“通用 kernel”。

分布问题不止于 shape。数值分布决定归约类 kernel 的累加顺序是否影响结果、决定 softmax 类 kernel 是否遇到全 -inf 行、决定 embedding 查表是否命中越界索引。正确性 oracle 若只比对固定随机种子下的输出，候选 kernel 可能在该种子下恰好通过而在其他分布下溢出。论文的“独立验证”若只换 shape 不换数值分布，仍留有缺口。可核查的口径要求记录：随机种子、数值范围、是否含特殊值（NaN/Inf/零行）、容差（绝对/相对/混合）以及比较的元素级最大误差。

这里有一个具体的代价链条：一个针对 4096×4096×4096 特化的 GEMM kernel，在 4096×4096×17 上因 K 维不整除而走边界分支，有效算力可能跌到峰值的零头；而基线 cuBLAS 的 split-K 与 stream-K 调度对非整除 K 有专门处理。离线基准若只测前者，会把这个退化完全隐藏。DLRM-Bench 的 41.7% 胜率之所以值得单独看，正因为推荐系统的 embedding 维度与 batch 分布比 Transformer 更不规则，特化 kernel 更容易在这里暴露。

四 · roofline 与 addressable fraction：把 kernel 加速翻译成端到端收益

论文最有工程价值的一步是把“kernel 快了多少”换算成“模型 wall clock 快了多少”。这个换算的核心量是 addressable fraction：真实模型运行时间里，由 LLM 可生成、可替换的 kernel 所占据的比例。论文在三个域、七个负载上测得该比例落在 8.9% 到 58.2% 之间。这个区间的两端对应两种截然不同的工程现实：低端意味着即便把可寻址部分优化到无穷快，端到端收益也被 Amdahl 定律压死；高端意味着单个热点 kernel 就是收益的全部来源。

$$T_{\text{e2e}}' = T_{\text{e2e}} - f\cdot T_{\text{e2e}}\left(1-\frac{1}{s}\right),\qquad \text{speedup}_{\text{e2e}}=\frac{1}{1-f+f/s}$$

式中 $f$ 是 addressable fraction，$s$ 是该部分内部的加速比。取 $f=0.582$、$s=1.552$（DLRM-Bench 的中位加速），端到端加速约为 $1/(1-0.582+0.582/1.552)\approx1.24$，与论文“投影 8.63% 端到端”的方向一致但幅度不同——说明论文的投影用的是更保守的 $f$ 或更低的 $s$，或两者叠加了非理想重叠。反过来，Transformer 上 80–86% 的时间花在 cuBLAS GEMM 与 FlashAttention 上，这两者已是高度优化的库实现，LLM 生成的 kernel 很难在其中再挤出空间，因此论文把 Transformer 的端到端改善上界压在约 1%，并指出该比例随模型规模增大而缩小——模型越大，GEMM 与注意力占比越高，可寻址的边角算子占比越低。

这个换算暴露了基准分数与生产收益之间的系统性错位。KernelBench level 1 的 22 个加速、1.235x 中位，若映射到 $f$ 很小的负载上，端到端收益接近于零；而 DLRM-Bench 的 1.552x 中位之所以能投影出 8.63%，是因为推荐模型的 $f$ 高达 58.2% 且集中在一个 embedding kernel 上。也就是说，同样质量的 kernel，落在不同 $f$ 的负载上，工程价值差一个数量级。任何只报 kernel 级加速比而不报 $f$ 的评测，都无法回答“这值不值得部署”。

roofline 在这里的作用是给 $s$ 设上限。一个 kernel 的加速比不可能超过其算术强度所对应的屋顶线：若候选 kernel 仍受内存带宽约束，$s$ 的上界就是带宽比；若它把计算从 SIMT 搬到 Tensor Core，$s$ 的上界才可能翻倍。论文未在摘要中给出逐题的 roofline 定位，这意味着 1.235x 这个中位数无法判断是“接近屋顶线的合理优化”还是“离屋顶线很远、仍有空间”。可核查的口径应记录每题的 SOL（speed-of-light）占比，把加速比归一化为“离屋顶线还有多远”。

五 · 五个模型配置与 30.4%：开源权重模型的评测口径差异

论文评测五个模型配置，前沿模型正确率 91.1%、22 个独立验证加速；开源权重模型最好的一档只到 30.4% 正确、3 个验证加速、卷积题全灭。这两组数字放在一起时，最容易被误读的是“30.4% 与 91.1% 是同一把尺子量的”。实际上，五个配置若共享同一题面、同一基线、同一输入分布，则可比；若其中某些配置用了不同的采样温度、不同的重试次数、不同的候选筛选策略，则正确率的差异里混进了推理预算的差异。论文摘要未给出每配置的采样参数与重试预算，这是本部分必须标注的第二个不可核查项。

“卷积题全灭”这一条尤其值得从口径角度读。卷积在 KernelBench level 1 里是难度高地：它同时要求 im2col 或直接卷积的循环组织、边界处理、通道对齐，以及对 cuDNN 隐式 GEMM 的竞争。开源模型在此全灭，可能反映的是能力差距，也可能反映的是题面未给足提示（比如未说明 layout 是 NCHW 还是 NHWC）、或正确性容差对卷积累加顺序过于敏感。前沿模型的三个卷积加速之所以被单独点出，正因为它们是“在最强基线 cuDNN 之上仍然更快”的少数样本——这类样本的说服力远高于逐元素算子上的加速，因为逐元素算子的基线本就接近带宽上限，加速空间有限。

评测五个配置的 token 代价是另一个隐性口径。若每个配置在每题上生成多个候选并做筛选，总 token 消耗随候选数线性增长，而正确率的提升可能只来自其中一两个候选。论文若报的是“最佳候选”的正确率而非“首次生成”的正确率，则 91.1% 与 30.4% 都是选择后的数字，比较的是搜索预算而非单次生成能力。工程判断上，可信的口径应同时报首次通过率与 k 次采样通过率，并把 token 消耗作为分母的一部分——否则“哪个模型更强”会退化成“哪个模型被允许试更多次”。

编译时间是这类评测里最容易被忽略的代价项。Triton 与 CuTe 候选的编译在首次调用时发生，一个复杂 kernel 的编译可以耗时数秒到数十秒，远超其执行时间。若计时口径把编译计入，微秒级 kernel 的加速比会被编译开销吞掉；若不计入，则掩盖了部署时的冷启动成本。论文的“独立验证”若要可复现，必须明确编译是否在计时之外、是否复用编译缓存、是否对每个候选单独编译。这三条不写清，1.235x 就无法被第三方复算。

六 · 可核查的测量口径清单：把摘要级结论变成可复算的实验

把上述缺口收拢成一份可执行的口径清单，是本部分对读者最直接的交付。清单的每一项都对应一个会让数字失真的机制，且每一项都能在论文正文或复现实验里被显式记录。以下六条按对结论的影响排序：

  • 基线锁定：每题记录所用基线实现（eager / compile / 指定库）及其版本，并声明是否取三者最快。加速比的分母必须是最强基线，否则 $s_i$ 系统性偏高。
  • dtype 与 TF32 开关：候选与基线必须同 dtype；若基线关闭 TF32 而候选内部使用 TF32，该题不计入加速统计，或单独标注为“精度让渡加速”。
  • 输入控制权：正确性与时延的输入由评测方生成，至少覆盖对齐、非对齐、动态三档 shape，并记录随机种子、数值范围与特殊值注入。
  • 计时协议：预热轮数、重复次数、同步方式、取中位还是取最小、编译是否计入，四项全部写明。缺任一项，时延数字不可跨论文比较。
  • 正确性 oracle：容差类型（绝对/相对/混合）、元素级最大误差、是否逐元素比对还是仅比对统计量。卷积与归约类必须记录累加顺序敏感性。
  • 搜索预算：每题的候选数、采样温度、重试次数、token 消耗，以及报的是首次通过率还是 k 次通过率。跨模型比较必须对齐预算。

这六条之外还有一条元规则：任何跨论文的加速比比较，必须先确认两篇论文的 $f$ 是否同量级。KernelBench level 1 的 1.235x 与 DLRM-Bench 的 1.552x 不可直接比较，因为前者是合成算子集合、后者是真实模型热点；前者映射到端到端可能接近零收益，后者映射出 8.63%。同理，Transformer 上“约 1% 端到端上界”这个结论不能搬到推荐系统上，因为两者的 $f$ 相差近一个数量级。跨硬件、跨 dtype、跨框架的迁移在摘要层面完全未验证，任何引用这些数字的工程决策都应把“仅在论文给定硬件与基线上成立”作为前置条件写进文档。

最后落到一个具体机制上：论文用“独立验证”把生成方的自报数字与评测方的复测数字分开，这个分离本身就是口径的核心。生成方报 91.1% 正确，评测方只认 22/56 的加速，两者之间的差额就是“正确但不够快”与“快但不可复现”的集合。工程上真正要部署的不是 91.1%，而是那 22 个在评测方输入上、对最强基线、同 dtype、显式同步计时后仍然更快的样本——而这 22 个样本能否转化为端到端收益，取决于它们落在 $f$ 的哪一端。把 $f$、$s$、基线、dtype、输入控制权、搜索预算六项写进实验记录，摘要级的结论才能变成可复算的工程判断。
