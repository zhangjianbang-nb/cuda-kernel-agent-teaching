一 · 基准缺位下的口径重建

AutoKernel 的摘要级材料没有给出基准数据集名称、题目数量与输入分布，这意味着任何“加速比”都缺少分母的定义域。工程上可核查的评测必须先固定三件事：算子集合（哪些 op、哪些 shape 组合）、参考实现（谁是对照组）、测量边界（计时从哪到哪）。缺一不可。论文未给出这三项，因此本部分不引用任何加速比数字，只讨论口径本身应当如何构造，以及缺失口径会带来哪些不可比的后果。一个具体机制是：把每个任务实例化为三元组 (op, shape, dtype)，评测集就是这三元组的笛卡尔采样；若论文未声明采样分布，读者无法判断候选内核是在“易 shape”上刷分还是在真实分布上泛化。代价是显性的——评测集越宽，单轮编译运行耗时与 token 成本越高，搜索轮数上限被迫压缩，收敛质量下降。

$$\text{Speedup}(k)=\frac{T_{\text{ref}}(s,d)}{T_{\text{cand}}(k,s,d)},\quad \text{Geomean}=\exp\!\Big(\frac{1}{N}\sum_{i=1}^{N}\ln \text{Speedup}_i\Big)$$

几何平均而非算术平均是内核基准的默认口径，因为加速比是比值量，算术平均会被个别超高加速比任务拉偏。举例：若十个任务中有九个加速比为 1.0、一个为 10.0，算术平均给出 1.9，几何平均只给出约 1.26——后者才反映“典型任务上的收益”。论文未说明使用哪种聚合，这是第一个不可比点。

二 · 基线的调优程度决定加速比的含义

材料明确未给出对比基线及其调优程度。这在工程上是致命的口径缺口：与 PyTorch eager 实现比、与未调优的朴素 CUDA 比、与 cuBLAS/CUTLASS 调优实现比，三种基线得到的“加速比”语义完全不同。前两者度量的是“智能体能否写出比框架默认路径更快的代码”，后者度量的是“智能体能否超过厂商手调库”——后者难度高一个量级，且 cuBLAS 在特定 shape 上已接近 roofline，任何正加速比都极为罕见。一个具体机制是把基线分档：

  • L0 参考实现：PyTorch/Triton 直译，语义正确但未优化；
  • L1 框架默认：框架调度到的库函数路径；
  • L2 厂商调优：cuBLAS/cuDNN/CUTLASS 手调 kernel。
论文未声明候选内核与哪一档比较，读者无法判断加速比是“相对朴素实现”还是“相对工业库”。代价在于：若基线是 L0，加速比可以很大但工程价值有限；若基线是 L2，加速比接近 1 已属不易，但论文若不给基线档位，两种情形在表格里长得一模一样。

另一个不可比点是基线的调优投入。同一 shape 下，cuBLAS 可能已做过 autotuning 选择最优 tile 配置，而参考实现可能是固定 tile 的朴素版本。若论文未说明基线是否经过 autotuning、是否使用相同 dtype 与相同内存布局，加速比的分母就带有隐藏的不公平。工程判断是：任何内核基准报告加速比时，必须同时报告基线档位、基线是否 autotuned、以及候选与基线是否在同一 dtype/布局下测量。

三 · 硬件与 dtype：不可比的两个隐藏维度

材料未给出目标 GPU 型号与显存配置。这不是细节缺失，而是口径缺失：同一内核在 H100 与 A100 上的 roofline 位置不同，在消费级卡与数据中心卡上的 SM 数量、L2 容量、HBM 带宽差异会直接改变最优 tile 尺寸与占用率。一个具体机制是 roofline 定位：对每个任务计算算术强度 I = FLOPs / Bytes，与目标硬件的 峰值算力 / 峰值带宽 比，判断任务是 compute-bound 还是 memory-bound。若论文未给硬件，读者无法复算 I 与拐点，也无法判断候选内核是“接近 SOL”还是“离 SOL 很远”。代价是：memory-bound 任务上，加速比的上限由带宽比决定，若硬件带宽未声明，加速比数字无法跨平台迁移。

$$\text{SOL}=\min\!\Big(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\Big),\quad \text{Efficiency}=\frac{T_{\text{SOL}}}{T_{\text{measured}}}$$

dtype 同理。fp32、tf32、fp16、bf16 在 tensor core 上的峰值算力差数倍，且数值容差要求不同。材料未说明评测使用的 dtype，也未说明正确性比对的容差设置。一个具体例子：同一 reduction kernel 在 fp32 下要求逐元素相对误差在 1e-5 量级，在 bf16 下容差可放宽到 1e-2 量级；若论文用 bf16 测量性能却用 fp32 判定正确性，或反之，正确性通过率与加速比就分属两个不同的数值世界。代价是：容差过松会放过数值错误的内核（正确性 oracle 失效），容差过紧会误杀合法优化（如用 tf32 近似 fp32 的合法路径）。

四 · faster rate 与 fast_p：通过率类指标的口径陷阱

除加速比外，内核基准常用“faster rate”（候选快于基线的任务占比）与“fast_p”（加速比超过阈值 p 的任务占比）来刻画分布。这两个指标对阈值 p 极其敏感，且对任务采样分布敏感。一个具体机制：给定 N 个任务，faster rate 是 #{i: Speedup_i > 1} / N，fast_p 是 #{i: Speedup_i > p} / N。若评测集里混入大量 memory-bound 小 shape（加速比天花板低），faster rate 会被系统性压低；反之若全是 compute-bound 大 shape，faster rate 会被抬高。材料未给出任务分布，因此这两个指标即便给出也无法解释。代价是：通过率类指标不携带“快多少”的信息，一个 1.01× 的加速与一个 5× 的加速在 faster rate 里权重相同，工程上应同时报告 geomean 与分位数。

另一个陷阱是正确性通过率与性能通过率的耦合。AutoKernel 的选优规则是在正确候选中取性能最优者，这意味着性能指标只在正确性过滤后的子集上计算。若论文只报告“最优内核的加速比”而不报告“有多少候选因正确性被淘汰”，读者无法判断搜索效率：一个智能体可能生成一百版内核、九十九版数值错误、一版侥幸正确且快，最终加速比很好看但搜索成本极高。代价体现在 token 与编译时间上——每轮编译运行都消耗算力与时间，淘汰率高的搜索在工程上不可部署。

五 · 隐藏 shape 与分布：泛化口径的构造

材料未说明是否使用隐藏 shape 或隐藏输入分布。这是评测可信度的核心：若智能体在搜索阶段能看到全部评测 shape，它可能针对这些 shape 做特化（硬编码 tile 尺寸、硬编码边界处理），在评测集上表现好但在未见 shape 上崩溃。工程上可核查的做法是划分 search set 与 held-out set：搜索阶段只暴露 search set 的 shape，最终报告 held-out set 上的加速比与正确性。一个具体机制是 shape 采样策略：从真实负载的 shape 分布中采样，而非均匀采样小 shape；并保证 held-out set 覆盖边界情形（非 2 的幂、极小、极大、非连续布局）。代价是：held-out 评测增加编译运行次数，且若 held-out 上性能显著下降，说明搜索过拟合，这本身就是有价值的负面结果。

输入分布同理。对 reduction、softmax 类算子，输入值的分布（是否含 NaN/Inf、是否极端动态范围）会影响数值稳定性与分支行为。材料未说明输入生成方式，因此正确性判定的覆盖面无法核对。一个具体例子：若输入全为正态分布的小值，一个在极端值上溢出的 kernel 可能通过正确性检查；若输入包含 1e30 量级的值，同一 kernel 会失败。工程判断是：正确性 oracle 必须声明输入分布、容差、以及是否覆盖 NaN/Inf 与边界 shape，否则“正确”二字不可信。

最后落在工程判断上：AutoKernel 的贡献在于把内核优化组织为迭代搜索闭环，但闭环的“奖励信号”是否可信，完全取决于上述口径是否被声明。一个未声明基线档位、未声明 held-out 划分、未声明计时边界的加速比，在工程上不能作为部署依据；可核查的做法是把口径字段作为评测报告的一等公民，与加速比数字同表呈现，任何缺失字段都标记为“不可比”。这也是后续复现工作必须先补齐的测量基础设施。

测量口径的不可核查性与失效边界

AutoKernel 的评测叙事有一个结构性弱点：整条闭环的每一环都依赖执行层给出可比较的标量，而论文材料对如何产生这些标量几乎全部留白。选优规则本身是干净的——

$$\text{best} = \arg\max_{k \in \{k_1,\dots,k_n\}} \text{Perf}(k) \quad \text{s.t.} \quad \text{Correct}(k)=\text{true}$$
但它把两个最脆弱的量（Perf 与 Correct）当作黑箱输入。一旦 Correct 的判定缺少容差声明与边界 shape 覆盖，argmax 就会在一个被污染的候选集上运行：一个在尾块、非对齐 stride 或极小 M 上越界写入的内核，只要主 shape 输出在默认容差内，就能通过检查并参与性能排序。此时搜索循环的“奖励信号”实际是被污染的，智能体后续轮次的改写方向也随之偏移——错误不会被单轮暴露，而是被历史记录固化，形成路径依赖。

性能口径的失效更隐蔽。若计时包含编译、内核启动与主机—设备数据传输，则加速比的分母被系统性抬高；若重复次数不足、未做 warmup 与时钟锁定，则小 shape 上的测量方差会直接决定候选排序。对迭代搜索而言这不是精度问题而是搜索动力学问题：噪声大的 Perf 会让智能体把随机波动误读为“分块/向量化有效”，从而在无效方向上消耗轮次。代价可以量化——设单轮编译加运行耗时为 tr、轮数上限为 N、每轮智能体上下文 token 为 T，则一次搜索的墙钟成本约为 N·tr 加上 N·T 的推理开销；若因口径噪声多耗 30% 轮次，这部分成本不产生任何真实加速，纯属测量误差的乘数。下表把材料中缺失的口径项与其对结论的影响对齐：

口径项材料状态缺失导致的失效
基准算子/shape/分布未给出无法判断负载代表性，泛化结论不可外推
基线及其调优程度未给出加速比参照系不明，可能对比未调优的朴素实现
正确性容差与边界覆盖未说明数值误差内核可通过检查并进入选优

由此可给出该方案的可信边界：它作为“执行反馈驱动的搜索脚手架”在机制上是自洽的，但作为“性能主张”目前不可核查。工程上可接受的补救不是补数字，而是补口径契约——固定 dtype 与硬件、声明容差与边界 shape 集合、把编译与数据传输移出计时窗口、对每个候选记录重复次数与方差，并要求最终报告同时给出正确性回归通过率与 roofline 下的 SOL 占比，否则 faster rate 与 geomean 只是同一批未定义量的函数。隐藏 shape 与输入分布的处理同理：若搜索期可见的 shape 与评测期不同，智能体学到的分块参数会过拟合到可见分布，此时应把 shape 采样策略本身写进口径，而不是留作隐含假设。

口径缺失下的可比性边界：AutoKernel 评测数字为何不能横向引用

AutoKernel 的选优规则本身是干净的：$$\text{best} = \arg\max_{k \in \{k_1,\dots,k_n\}} \text{Perf}(k)\ \ \text{s.t.}\ \ \text{Correct}(k)=\text{true}$$但这条公式只约束“在自家候选集内取最优”，并不约束 Perf 与 Correct 的测量口径。论文为摘要级材料，未给出基准数据集名称、题目数量与输入分布，也未给出对比基线及其调优程度，因此任何跨论文的 faster rate、geomean speedup 或 fast_p 都无法与本方案对齐：分子是自家搜索出的内核，分母是未知调优程度的基线，比值不可比。更隐蔽的是隐藏 shape 与输入分布的处理——材料未说明是否划分 held-out shape、是否在评测时重采样输入，若搜索阶段可见的 shape 与报告阶段一致，则迭代搜索存在对评测集过拟合的通道，加速比会被系统性高估。

正确性与性能两侧的口径缺口各自对应一类失效。正确性侧，判定依赖与参考实现比对，但容差设置、边界 shape 覆盖与防作弊措施均未说明；对 reduction、softmax 一类含浮点累加的算子，过宽容差会放过数值错误内核，过严则误杀合法重排实现，而缺少边界覆盖时越界写可能在小 shape 上不触发。性能侧，计时方式、重复次数与是否排除编译及数据传输开销未给出；若把主机到设备拷贝计入分母而不计入分子，或未做 warmup 与多次取中位数，roofline 上的 SOL 占比就失去意义。这些不是精度问题，而是口径问题：同一内核在不同口径下可以呈现相反结论。

系统代价同样落在口径之外。搜索轮数、token 成本与单次编译运行耗时均未给出，而迭代闭环的成本结构是“每轮一次编译 + 一次运行 + 一次模型调用”，轮数上限与收敛判据未说明意味着无法估算最坏情况开销；对编译时间敏感的模板重载或 CuTe 布局展开，单轮编译可能主导总时延。工程判断上，引用该方案时应只把它当作“闭环框架存在性”的证据，而非性能证据；可核查的测量口径须自行补齐：固定 dtype 与 shape 集合、声明容差与边界用例、报告计时是否含拷贝与编译、给出基线的调优来源，并在同一口径下重跑候选与基线。
