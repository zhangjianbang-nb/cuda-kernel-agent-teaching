一 · 基准的构成与可比性边界

CudaForge 的评测负载是算子级 kernel 任务：每条任务包含任务语义描述、一份参考实现、以及一组输入 shape 分布。这个三元组决定了后面所有指标的分母，也决定了哪些数字能横向比较。参考实现是正确性 oracle 的来源，同时也是性能基线的候选之一；shape 分布则决定工作负载落在 roofline 的哪一段。摘要级材料没有给出算子清单、任务条数与 shape 的具体取值，因此任何跨框架的加速比对照都必须先声明这一缺口，否则就是把不同分母上的比值放在一起。

可比性至少受四个变量支配：硬件型号、dtype、基线定义、计时口径。硬件决定峰值带宽与算力，dtype 决定字节数与指令吞吐（fp32 与 bf16 的 roofline 拐点相差一倍以上），基线决定 speedup 的分子分母，计时口径决定测量的是 kernel 本体还是含启动开销的端到端。CudaForge 材料中这四项均未给出具体设置，这意味着它报告的任何一个加速比都只能在“同一硬件、同一 dtype、同一基线、同一计时方式”的自洽实验内成立，不能直接与 KernelBench 系或其他 agent 框架的数字并置。工程上正确的做法是把这四项写成测量口径的一部分随结果一起发布，而不是留给读者猜。

单轮提示直接生成的 kernel 作为对照基线，其意义在于隔离“多轮闭环”这一变量的贡献。但这条基线本身有方差：同一提示在不同采样温度下产出的 kernel 性能分布很宽，若只取一次采样作分母，speedup 会被偶然性放大或缩小。因此基线应当以多次采样的统计量（中位数或最优值，并注明取法）定义，否则 faster rate 这类比例指标会失去解释力。

$$\text{speedup}(k)=\frac{T_{\text{base}}}{T_{k}},\qquad \text{faster}(k)=\mathbb{1}\big[T_{k}<T_{\text{base}}\big]$$

代价在于：把基线定义得越弱（未调优 CUDA 实现），speedup 越好看但信息量越低；定义得越强（厂商库或手调 kernel），通过率越低但结论越可信。CudaForge 同时列出这两类基线是合理的，问题只在于数值未披露，读者无法判断 faster rate 是在哪条分母上算出来的。

二 · 指标族：faster rate、speedup、geomean 与 fast_p

四个指标回答四个不同问题。faster rate 是比例指标，回答“有多少任务被加速”，对离群值不敏感，适合刻画覆盖率；speedup 是逐任务比值，回答“单个任务快多少”，但算术平均会被个别超大加速比拉偏；geomean 对逐任务 speedup 取几何平均，抑制长尾、保持比值尺度上的对称性，是跨任务汇总的默认选择；fast_p 则是分位数口径，回答“有多少任务达到参考实现 p 倍的性能”，把“通过”从布尔判断变成阈值判断。四者混用时最常见的错误是用算术平均 speedup 汇报总体收益，同时用 faster rate 汇报覆盖率，两个数字来自不同聚合方式，读者会误以为它们描述同一分布。

$$\text{geomean}=\exp\!\Big(\frac{1}{N}\sum_{i=1}^{N}\ln \frac{T_{\text{base},i}}{T_{i}}\Big),\qquad \text{fast\_}p=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\Big[\frac{T_{\text{base},i}}{T_{i}}\ge p\Big]$$

正确性门控与指标聚合的耦合是这里的关键机制。CudaForge 只让通过参考输出比对的 kernel 进入排序，因此分母 N 是“正确 kernel 数”而非“任务总数”。若一个框架正确率低，它的 geomean 只覆盖了容易的子集，与高正确率框架的 geomean 不可比。汇报时必须同时给出正确率与参与聚合的任务数，否则 geomean 会被幸存者偏差污染。这是把 score(k)=1[correct]·T_ref/T_k 从单候选打分提升到集合聚合时必须显式处理的代价。

具体例子：假设十个任务，某框架在其中六个上正确且都比基线快，另外四个编译失败。它的 faster rate 若以十个任务为分母是 0.6，若以六个正确任务为分母是 1.0；geomean 只在六个任务上计算。两个口径都能自洽，但含义完全不同，跨论文对照时必须统一到“任务总数为分母”的口径，并把正确率单列。fast_p 的阈值 p 同样要写明，p=1.0 与 p=1.2 的通过率差异足以改变结论方向。

三 · roofline 与 SOL：把 speedup 换算成可达上限的比例

speedup 是相对量，roofline 给出绝对上限。对每个 kernel，按其算术强度（FLOP/Byte）定位在 roofline 折线上的理论最短时间，再与实际耗时相比得到 SOL（speed-of-light）利用率。这个比例的价值在于：一个 speedup=3 的 kernel 可能只达到 20% SOL，说明优化空间仍大；另一个 speedup=1.1 的 kernel 可能已达 85% SOL，说明基线本身接近硬件极限，继续压榨的边际收益低。仅看 speedup 无法区分这两种情形，而这正是 agent 迭代该不该继续的直接判据。

$$T_{\text{SOL}}=\max\!\Big(\frac{\text{FLOP}}{\text{PeakFLOPS}},\ \frac{\text{Bytes}}{\text{PeakBW}}\Big),\qquad \text{SOL util}=\frac{T_{\text{SOL}}}{T_{k}}$$

机制上，roofline 需要每个任务的 FLOP 与访存字节数估计，这来自参考实现的语义而非被测 kernel 的实现——否则一个偷工减料的 kernel 会把自己的 roofline 也拉低。代价是：roofline 只覆盖计算与带宽两个维度，对延迟受限的小 shape、对占用率受限的 kernel、对依赖 launch 开销的微型任务给不出紧上界，此时 SOL util 会系统性偏低，不能作为“还有多少优化空间”的证据。shape 分布在这里直接起作用：同一算子在小 shape 下是延迟受限、在大 shape 下是带宽受限，把两者混进一个 geomean 会掩盖瓶颈类别的差异，因此按 shape 分桶汇报 SOL util 比单一汇总更有诊断价值。

具体例子：一个逐元素算子在大 shape 下字节数主导，SOL 由峰值带宽决定，此时 speedup 与 SOL util 大致同向；同一算子在小 shape 下 launch 延迟主导，T_SOL 远小于实际耗时，SOL util 可能只有个位数百分比，但这不代表 kernel 写得差。CudaForge 的硬件反馈若把这类任务误判为“带宽未打满”，反馈摘要就会引导模型做无效的访存改写——这正是反馈映射缺少形式化保证时的典型失效。

四 · 隐藏 shape 与分布：评测协议里的防过拟合设计

若 shape 在提示中完全可见，agent 可以针对具体尺寸做特化（硬编码 tile、展开循环、选择特定 block 大小），在可见 shape 上表现优异但在未见 shape 上崩溃或退化。隐藏 shape 的做法是把 shape 分成可见集与保留集：可见集进入提示供生成与调优，保留集只在最终评测时使用，且不进入任何一轮反馈。这样测的是 kernel 的参数化程度而非记忆能力。

实现上，隐藏集必须与可见集同分布采样还是跨分布采样，决定了结论的强度。同分布隐藏集检验的是“是否过拟合到具体数值”；跨分布隐藏集（不同 batch、不同 head 数、非对齐长度）检验的是“是否正确处理边界与对齐”。后者更有工程意义，因为生产负载的 shape 分布会漂移。代价是跨分布隐藏集上的正确率通常更低，且失败模式更多样（越界、对齐假设破裂、warp 分支发散），需要正确性校验器覆盖非对齐与极端小 shape 的用例，否则隐藏集上的性能数字建立在未验证的正确性之上。

具体例子：一个矩阵乘 kernel 在可见的 4096×4096 上通过并加速，但在隐藏的 4097×4097（非 2 的幂、非 tile 整数倍）上因缺少边界谓词而越界写。这类失败在只报告可见集结果的评测中完全不可见。因此测量口径必须写明：隐藏集的 shape 采样规则、是否含非对齐尺寸、每个任务在隐藏集上跑几次、以哪次为准（首次运行含预热还是取稳态中位数）。CudaForge 材料未给出这些细节，复现时应自行补齐并把补齐后的口径随结果发布。

把上述讨论收敛成一份可执行的记录模板，是让 CudaForge 类结果可复核的最低要求。下表列出每一项应记录的内容及其对结论的影响方向。

这张表里最容易被忽略的是计时口径中的“是否含多轮迭代开销”。CudaForge 的搜索成本随轮数线性增长，若最终汇报的只是最优 kernel 的单次耗时，读者会误以为框架的收益是纯性能收益；实际端到端收益应扣除生成、编译、profile 与反馈组装的墙钟时间与 token 成本。工程判断上，一个 speedup 只有在“单任务搜索开销 < 该任务在生产中重复执行的累计节省”时才值得部署，而这个不等式两边都依赖上表的记录项。

具体机制上，建议把每轮迭代记录为一条结构化条目：轮次、编译状态、正确性判定、耗时、profile 摘要、反馈文本哈希。反馈文本哈希的作用是让“同一反馈是否导致同一修改”可被检验，从而在复现时区分模型方差与反馈质量差异。代价是记录粒度变细后存储与复核成本上升，但这部分成本远低于因口径缺失导致整批结果不可用的代价。

六 · 不可比数字的识别与处理

三类数字在 CudaForge 语境下必须标记为不可比。第一类是跨硬件的 speedup：同一 kernel 在不同带宽的 GPU 上 speedup 不同，因为分母基线也随之变化，把两个硬件的 speedup 并列会掩盖绝对性能差异。第二类是跨基线的 faster rate：以未调优实现为分母的通过率天然高于以厂商库为分母的通过率，两者不是同一难度。第三类是跨正确率口径的 geomean：正确率不同的框架，其 geomean 覆盖的任务子集不同，数值高低可能只反映子集难度而非优化能力。

处理方式不是回避这些数字，而是把它们降级为“同口径内可读、跨口径仅作定性参考”。具体做法：在汇报表里为每个数字标注其口径标签（硬件、dtype、基线、聚合分母），跨框架对照时只比较标签完全一致的行；标签不一致的行只用于说明机制差异，不用于排序。这与正确性门控是同一逻辑的两个层面——门控保证单个候选可信，口径标签保证候选集合之间的比较可信。

最后落在工程判断上：CudaForge 的评测可信度不取决于它报告了多大的加速比，而取决于它是否把“哪些数字在什么条件下成立”写清楚。一个只给出 speedup 而不给出基线采样规则、计时口径与隐藏 shape 协议的评测，即便数字亮眼也无法支撑部署决策；反之，一个给出完整口径表、哪怕加速比温和的评测，其结论可以被复算、被质疑、被增量修正。测量口径本身就是可验证性的一部分，缺了它，硬件反馈闭环再完整，也只是在一个不可复核的坐标系里做搜索。

口径缺口下的可比性边界与复现测量方案

本方案在评测口径上存在结构性缺口：摘要级材料未给出基准规模、基线数值、硬件型号、dtype 与计数器口径，因此任何跨方案比较都必须先降级为“机制可比、数字不可比”。可比性的最低条件是五项对齐——参考实现的语义与容差、输入 shape 与分布、GPU 型号与时钟状态、dtype 与累加精度、计时边界（是否含 kernel launch 与同步）。缺任一项，$$\text{score}(k)=\mathbb{1}[\text{correct}(k)]\cdot T_{\text{ref}}/T_k$$ 中的 $T_{\text{ref}}$ 与 $T_k$ 就落在不同测量域，比值失去意义。一个具体失效例子：参考实现用 FP32 累加而候选 kernel 走 TF32 张量核，数值校验在宽松容差下通过，$T_k$ 却因精度降级而虚高，score 被系统性高估；此时正确性门控形同虚设，必须把 dtype 与容差写进口径表而非留给实现者默认。

隐藏 shape 与分布的处理是本方案最易被误读的边界。框架按模板把 shape 拼进提示，模型在可见 shape 上迭代收敛后，隐藏 shape 上的性能与正确性并无保证——搜索式优化天然过拟合提示中出现的维度组合。工程上的补救不是扩大提示，而是在校验器侧保留一组不下发提示的 shape 做门控，并要求候选在这些 shape 上同样通过正确性比对；代价是每轮多跑若干次前向，时延与显存占用随隐藏集规模线性增长，且隐藏集一旦泄漏进反馈摘要，其门控意义即刻消失。分布同理：非连续 stride、边界维度、极端 batch 若不在隐藏集中，反馈摘要指出的“瓶颈类别”可能只对训练 shape 成立。

可核查的测量口径应固化为下表，并在复现时逐项标注“已给出/未给出”，未给出项一律不得进入定量结论。

口径项本方案状态复现要求
基准与算子清单未给出规模列出算子、shape 集与隐藏集划分
基线未调优 CUDA 与单轮生成，设置未给出固定编译选项与同一参考实现
硬件与 dtype型号、精度未给出记录 GPU、时钟、dtype 与容差
指标faster rate/speedup/geomean 口径未给出声明计时边界与聚合方式
成本轮数与 token 未给出实测单任务迭代成本与收益比

指标聚合本身也是边界：faster rate 对“快于基线的候选占比”敏感，少数极端加速样本会拉高 geomean 而掩盖多数任务无收益的事实，因此须同时报告逐任务 speedup 分布与失败率，而非只给一个 geomean。roofline 口径更需谨慎——未给出计数器口径时，带宽利用率与 SOL 只能定性描述瓶颈类别，不能当作定量上限。系统代价方面，迭代成本随轮数线性增长，编译沙箱与 profile 采集链路是固定开销，反馈摘要失真会引入无效修改并放大 token 消耗；生产部署前必须以单任务实测成本对照端到端收益，否则搜索开销可能吞掉性能收益。
