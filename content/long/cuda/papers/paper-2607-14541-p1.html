一 · 从一张生产 trace 上的“热核清单”说起

设想一个已经跑在整集群上的推理服务：卡型是算力受限、显存宽裕的那一类，服务分 prefill 与 decode 两个阶段交替运行。运维侧能拿到的唯一可靠事实是 GPU 时间账本——哪些 kernel 吃掉了卡时。把这张账本按应用卡时加权、按服务阶段拆开，会得到一份极不均匀的清单：少数十几个算子占据了绝大部分 GPU 时间，其余长尾算子单个占比小到可以忽略。论文正是从这样一份全集群生产推理 trace 中采样出 30 个算子、440 个 shape，构成 Atrex-Bench，并为每题附上由 GPU 时间份额导出的重要性权重与逐题 roofline 上限。这个构造方式本身就是对旧方案的一次判决：过去用来衡量 kernel 生成能力的题面，来源是合成或人工策展的，与真实部署负载之间存在系统性偏移。

偏移的代价不是抽象的。一个在合成题面上刷到高分的候选 kernel，落到生产 trace 的热核上，可能连基线都跑不过；反过来，一个在合成题面上平平的候选，恰好在某个高权重算子上拿到了可观的加速，对端到端时延的贡献却可能超过前者十倍。旧方案的评测口径没有权重概念，把 440 个 shape 一视同仁地平均，等于默认“长尾算子与热核同等重要”——这与卡时账本直接冲突。论文给出的聚合口径把这件事写死：分数不是简单平均加速比，而是按重要性加权的、带阈值的通过率。这一点在后续评测部分会展开，此处只需记住：旧口径的失效首先发生在“题目从哪来”和“每题值多少”这两个环节，而不是发生在模型能力上。

二 · 三条旧路径各自的工程账

在 LLM 介入之前，把一个算子做成生产可用的 GPU 实现，主流只有三条路，每条都有明确的成本结构。

手写 CUDA C++。这是性能上限最高的一条路，也是开发周期最长的一条。一个中等复杂度的融合算子，从读懂 PyTorch 参考实现的语义、确定数值容差、设计 tile 与共享内存布局，到写出第一版能编译的 kernel，再到用 NCU 抓取 stall 原因、调 occupancy、处理 bank conflict 与尾块，工程上是以人周计的。它的痛点不在“写不出来”，而在“写出来之后还要证明它对”。正确性 oracle 往往只能靠与 eager 实现逐元素比对，浮点结合律差异、denormal 处理、边界 shape 都会制造假阴性；而一旦为了性能做了 shape 特化，正确性覆盖面就随特化分支数量线性膨胀。可维护性是第三条账单：手写 kernel 的模板参数、launch 配置、架构分支（sm 版本差异）散落在代码里，换一代卡就要重审一遍。

Triton。它把 tile 级编程抽象出来，用 Python DSL 描述块级计算，编译器负责布局与流水。开发周期比手写 CUDA 短一个量级，代价是性能上限被编译器策略封顶：当算子需要非常规的 shared memory 复用、跨 warp 的细粒度同步、或者需要手工控制 async copy 的流水深度时，Triton 的表达力不够，只能退回 CUDA 或接受次优。另一个隐性代价是编译时间——Triton 的 JIT 与 autotune 在 shape 空间上做搜索，首次遇到新 shape 时的编译与调优开销会直接体现在服务的长尾时延上，这在生产上是必须被预算掉的成本。

库调用。cuBLAS、cuDNN、CUTLASS 这类库把常见算子做到了接近 roofline，工程上最省事：一次调用，正确性由厂商背书。痛点是覆盖率与适配性——库只覆盖它认为值得覆盖的形态。生产 trace 里的算子往往是“两个标准算子粘在一起再加一个逐元素变换”的融合体，库没有对应入口；即便有，shape 分布一旦偏离库的调优假设（比如极瘦长的 GEMM、非 2 的幂的归约长度），库实现就会掉到 roofline 之下。更麻烦的是，库的版本升级会悄悄改变数值行为与性能曲线，端到端回归因此变成一项常态工作。

路径开发周期量级性能上限正确性负担可维护性
手写 CUDA C++人周最高，可贴 roofline自建 oracle，特化分支膨胀架构分支多，换卡重审
Triton人天受编译器策略封顶语义较清晰，边界仍需覆盖较好，但 autotune 缓存需管理
库调用人时常见形态接近 roofline，偏态形态掉队厂商背书版本升级引入隐性回归

三条路共同的缺口是：它们都无法以“天”为单位，为一个由生产 trace 定义的、形态各异的算子集合，批量产出接近 roofline 的实现。而这个集合的规模是 30 个算子、440 个 shape——按手写路径的节奏，这是一个以人年计的工程。

三 · 性能上限为什么不是“再调调参”就能突破

把性能问题说清楚，需要一个可计算的判据。roofline 模型给出单个 kernel 在给定硬件上的时间下界：

$$T_{\text{roof}}=\max\left(\frac{\text{FLOPs}}{\text{PeakFLOPS}},\ \frac{\text{Bytes}}{\text{PeakBW}}\right)$$

论文为每题附上一个 per-problem roofline ceiling，正是用这个量作为分母来衡量候选实现离硬件极限有多远。注意这个式子的结构：它取计算时间与访存时间的较大者，意味着一个 kernel 只要有一侧贴住上限、另一侧没有成为瓶颈，就已经是“roofline 最优”的。工程上真正难的是判断当前实现卡在哪一侧——这需要 profile 而不是猜测。算力受限、显存宽裕的卡型上，很多生产算子的算术强度落在斜线段，也就是访存受限区；此时优化方向是减少冗余搬运、提高有效带宽利用率，而不是堆 ILP。反过来，一旦误判，把工夫花在指令级并行上，收益会接近于零。

旧路径在这个判据下的表现可以定性描述：库实现对常见形态能贴住 ceiling，对偏态形态则因 tile 划分与流水深度不适配而明显偏离；Triton 在访存受限的简单算子上通常接近 ceiling，但在需要精细控制共享内存与流水阶段的算子上会被编译器策略拖住；手写 CUDA 能达到 ceiling，但达到它所需的人力不可扩展。这就是“非改不可”的技术根源：不是现有工具不好，而是它们的产出速率与生产 trace 所要求的覆盖面之间存在数量级差距。而这个差距恰好是 LLM 编码 agent 有机会填补的——前提是评测口径必须先修好。

四 · 正确性单独作为能力证据为什么会失真

论文摘要里有一句判断值得逐字读：correctness alone overstates capability, since much of the apparent pass rate comes from…（后续部分会给出完整机制）。这句话指向的工程现实是，一个 agent 可以通过“不真正实现 kernel”而通过正确性检查。最典型的形态是 fallback：候选代码在无法生成有效 kernel 时，退回调用 PyTorch eager 或某个库函数。语义上完全正确，数值上逐位可比，正确性门轻松通过；但性能上它只是基线本身，加速比约等于 1，对 roofline 的逼近度为零。如果评测只看正确率，这类候选与真正写出高效 kernel 的候选无法区分。

论文给出的受控案例研究从反面印证了这一点：agent 能把 zero-FlyDSL fallbacks 转成真实 kernel，并且这些 kernel 匹配或超过手工调优的生产基线。也就是说，fallback 不是不可避免的技术天花板，而是搜索过程在某个上下文里停滞时的逃逸行为。把 fallback 计入通过率，等于把“放弃”记成了“成功”。这直接决定了评测必须双门：正确性门之外还要有性能门，且性能门的参照系是 roofline ceiling 而不是基线。用公式表达，单题得分应当是相对基线的加速比，而聚合分数是带阈值的加权通过率：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个式子里有两个容易被忽视的工程参数。其一是基线 $T_{\text{base},i}$ 的选择：若基线没有开启 TF32、没有使用最强的库实现，$s_i$ 会被系统性高估，候选看起来“超过了库”，实则只是超过了弱基线。其二是阈值 $\tau$：定得太低，fallback 与微小改进都能通过；定得太高，则大量真实但幅度有限的优化被抹掉。论文的加权结构把这个式子从“平均加速比”改造成“按 GPU 时间份额加权的通过率”，使得一个在高权重热核上刚好过阈值的候选，其贡献远大于在长尾算子上大幅加速的候选——这与卡时账本的逻辑一致。

五 · 可维护性与评测可信度的双重账单

旧路径的可维护性成本，在 LLM 介入后不是消失了，而是转移了形态。手写 kernel 的维护负担是“人读懂代码”；agent 生成的 kernel 的维护负担是“人判断这段代码为什么快、在什么输入下会崩”。后者更难，因为生成过程留下的搜索轨迹（试了哪些 tile、哪些流水深度、哪些被回退的候选）通常不在产物里。一个没有 profile 依据的加速，换一个 shape 就可能变成退化；一个靠 shape 特化硬编码分支堆出来的加速，在隐藏输入分布上会直接崩塌。论文的应对是把 profile 反馈纳入 agent 的迭代回路——Atrex-Kernel-Agent 的核心是 iterative measure-revise search，加上 optimization dropout 来跳出停滞的搜索上下文，再加一层包含 298 个参考 kernel 文件与 244 条优化知识的 GPU 优化知识库。这三件东西的共同作用是让“为什么快”变成可追溯的：测量给出证据，dropout 防止在局部最优里空转，知识库提供可复用的优化模式而不是每次从零试错。

评测可信度的账单则体现在复现成本上。要让 440 个 shape 上的分数可信，必须固定：输入分布、基线实现与其编译选项、正确性容差、时延测量方法（是否含 launch 开销、是否 warmup、是否取中位数）。任何一项漂移都会让跨论文比较失效。论文把题目来源钉死在生产 trace 上，实际上是把“输入分布”这一项从可自由选择的变量变成了基准的一部分——这是它相对合成基准最实质的改进，也是它必须自带重要性权重的原因：一旦题目来自真实分布，题目之间的价值差异就不再可忽略。

还有一个具体的工程代价必须计入：编译时间。440 个 shape 乘以多个候选，如果每个候选都要走一次完整编译加 profile，评测本身就是一个不小的集群作业。agent 侧的搜索若不做剪枝，token 消耗与编译排队会成为吞吐瓶颈；这也是为什么 measure-revise 回路需要 dropout 机制——它省的不只是搜索步数，还有每一步背后的编译与测量开销。

六 · 旧方案失效的边界在哪里

把旧方案的痛点收敛成一句工程判断：它们失效的边界不在“能不能写出一个正确的 kernel”，而在“能不能在一个由生产 trace 定义的、带权重的算子集合上，以可接受的成本批量逼近 roofline，并且让每个结果都可被 profile 证据支撑”。手写 CUDA 能逼近 roofline 但成本不可扩展；Triton 成本可扩展但上限被封；库调用成本最低但覆盖面与偏态形态适配不足。三者叠加，恰好留下一个空位：需要一个能以 profile 为反馈、以知识库为复用、以 dropout 为逃逸机制的优化 agent，并且需要一个把题目来源、权重与 roofline ceiling 都钉死的基准来诚实地衡量它。

论文摘要给出的第一个测量结果把这个空位量化了：六个前沿编码 agent 在 Atrex-Bench 上评测，最好的 vanilla 模型在生产算子上只达到约 10% 的硬件 roofline。这个数字的含义不是“模型不行”，而是“旧评测口径下的高分不能迁移到生产口径”。10% 与 roofline 之间的差距，正是旧方案（包括以合成题面训练的 agent）没有覆盖到的部分：真实算子的形态、真实的访存/计算配比、真实的重要性分布。要让这个差距被可靠地缩小，第一步不是换模型，而是承认题目必须来自 trace、分数必须带权重、正确性必须与性能门联立——这正是本部分之后要逐层拆开的内容。

手写、库调用与 Triton 三条路径在真实推理流量下的失效边界

先看一个具体现场：某推理服务在 compute-limited、memory-rich 的 GPU 上跑满集群，30 个算子、440 个 shape 的负载画像被直接采样出来。工程团队面对的第一个问题不是“能不能写快”，而是“该写哪一个”。手写 CUDA 的路径把决策权交给最熟悉 SASS 的人，代价是开发周期以人周计、每个 shape 都要单独调 tile 与 bank 冲突，且一旦 dtype 或 head dim 变化，寄存器压力与 occupancy 的平衡点就整体漂移；库调用（cuBLAS/cuDNN/FlashAttention 一类）把正确性和可维护性外包出去，但库的启发式按通用 shape 分布调优，落到长尾 shape 上要么走 fallback 路径、要么直接拒绝，性能上限被库的 dispatch 表锁死；Triton 把 tile 级抽象交给编译器，开发周期压缩到人天，可一旦 kernel 进入访存受限区，编译器生成的 pipeline 与 swizzle 往往达不到手写水平，且 autotune 的搜索空间在编译期展开，config 数量乘以 shape 数量直接推高编译时间与缓存占用。

这三条路径共同的系统代价可以写成一个粗略的分解：端到端时延 $$T_{\text{e2e}}=\sum_{i} w_i\cdot T_i,\quad T_i=\max(T_{\text{mem},i},T_{\text{compute},i})+\tau_{\text{launch},i}$$ 其中 $$w_i$$ 是该算子在全集群 GPU 时间中的份额（按 application card-hours 加权、并按 serving phase 分开计算）。旧做法的根本缺陷在于优化目标错位：工程师按“最难的算子”或“最热的单点”分配人力，而真实收益由 $$w_i$$ 与 roofline 余量的乘积决定。一个占 GPU 时间极小、却已被手写到接近 roofline 的算子，继续投入的边际收益趋近于零；反过来，一个看似平凡、却因 fallback 而只跑到 roofline 一小部分的算子，才是分数的主要来源。没有 per-problem roofline ceiling 这把尺子，团队无法判断“已经够快”与“还差得远”的边界在哪里。

正确性与可维护性的代价同样具体。手写 kernel 的正确性 oracle 依赖逐元素对拍，隐藏输入分布（非常规 stride、非对齐尾块、动态 shape）会让离线通过的实现在生产上静默出错；库调用把这一风险转移给供应商，但版本升级会改变数值路径，回归测试必须覆盖 dtype 与算法选择的组合。更隐蔽的是评测口径本身：基线若未开 TF32、未使用最强库实现，加速比会被系统性高估；shape 特化与 fallback 分支会让正确率虚高——候选在无法编译或无法匹配时退回参考实现，pass rate 看起来漂亮，实际能力被夸大。论文给出的观察正是这一点的量化版本：六个前沿 coding agent 中最好的 vanilla 模型在 Atrex-Bench 的生产算子上只达到约 10% 的硬件 roofline，而“仅看正确性”会高估能力，因为相当一部分表面通过率来自 fallback。

路径开发周期量级性能上限主要失效条件
手写 CUDA人周，按 shape 递增可逼近 rooflinedtype/shape 漂移后 occupancy 失衡；人力无法覆盖长尾
库调用人天受 dispatch 表约束长尾 shape 走 fallback；版本升级改变数值路径
Triton人天访存受限区常低于手写autotune 空间×shape 数推高编译时间；pipeline 不足

于是“非改不可”的判断落在工程而非情绪上：当负载画像显示收益集中在少数高 $$w_i$$ 且 roofline 余量大的算子上，而人力与库 dispatch 都无法系统性地覆盖这批算子时，继续在旧路径上加人只是把成本线性放大。真正需要的是一个能读取 profile、按重要性加权排序、并在编译—正确性—时延反馈闭环里迭代的机制；这也是后续把 trace-driven 基准与优化 agent 放在同一口径下讨论的前提。旧方案并未“错误”，它只是在生产流量面前暴露了边界：优化目标与真实 GPU 时间份额脱钩，正确性口径与能力脱钩，而这两处脱钩都无法靠单点手写或换一个库版本来修补。
