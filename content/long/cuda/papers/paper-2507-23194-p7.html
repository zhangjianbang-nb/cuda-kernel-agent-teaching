一 · 正确性漏检：oracle 的容差与覆盖边界

Geak 的正确性判定是与参考实现逐元素比对，材料没有给出容差阈值，也没有说明边界 shape 的处理方式。这不是细节缺失，而是失败模式的第一现场：一个内核在评测中“通过”，并不等于它在语义上正确。逐元素比对至少有三个可漏检的缝隙。其一是容差口径与 dtype 不匹配：fp16/bf16 归约在长 K 维度上累积误差随规模增长，若容差写成固定绝对值而非相对误差加 dtype 相关下限，长序列用例会被误判为失败，短用例则会把真实误差掩盖过去。其二是 NaN/Inf 的比对语义：`NaN != NaN` 使含 NaN 的输出天然判错，而部分算子（如 softmax 的极端输入、masked 位置的填充值）本就允许 NaN 传播，oracle 若不区分“期望 NaN”与“意外 NaN”，就会在两端同时产生假阴性与假阳性。其三是边界 shape 未覆盖：当 M 或 N 不是块大小的整数倍时，越界写与尾块掩码错误只在特定 shape 暴露，若基准只取对齐的方阵，这类错误可以长期潜伏。

工程上的做法是把 oracle 从“单点比对”升级为分层判定，伪代码思路如下：

$$\mathrm{pass}=\bigwedge_{s\in S}\Big(\mathrm{allclose}(y_s,\hat y_s,\ \mathrm{rtol}(\mathrm{dtype}),\ \mathrm{atol}(\mathrm{dtype}))\ \wedge\ \mathrm{nan\_mask}(y_s)=\mathrm{nan\_mask}(\hat y_s)\Big)$$

其中 $S$ 是 shape 集合，必须显式包含非对齐尾块、单元素退化维度与空张量。代价是显存的：每个 shape 都要保留参考输出与候选输出做比对，若一次跑完整个 $S$，峰值显存随用例数线性上升；实践中按 shape 串行执行并及时释放，把比对成本压到单用例峰值。一个具体例子：LayerNorm 在 N=1023 时若内核按 1024 向上取整读取，越界读到的脏数据不会触发非法访问（落在同一分配块内），逐元素比对在 N=1024 的对齐用例上完全通过，只有把 N=1023 纳入 $S$ 才能暴露。

二 · shape 特化：编译期常量换来的脆弱性

Triton 的块级 DSL 让内核作者自然地把 BLOCK_SIZE、num_warps、甚至归约轴长度写成常量，编译器据此做展开与寄存器分配，性能收益真实存在。但这也意味着候选内核可能只对生成时看到的 shape 有效：常量化的循环边界在更大 shape 上截断，硬编码的 grid 维度在 batch 变化时漏算尾部。Geak 的流程里，任务层给出 shape 与输入分布，智能体据此生成候选，若基准只用单一 shape 计时，shape 特化内核会拿到虚高的加速比。

诊断手段是把 shape 作为一等维度记录：每次评测除记录耗时外，同时记录候选源码中被常量化的事件（BLOCK_SIZE、grid 表达式、循环上界是否引用运行时变量），并对同一候选在若干 shape 上重跑正确性。监控指标可以是“跨 shape 通过率”，即通过用例数除以总用例数；一个只在单一 shape 通过的候选，其跨 shape 通过率接近 $1/|S|$，与真正泛化的候选在统计上可分。代价是编译时间：每个 shape 组合都可能触发一次 Triton 编译（JIT 缓存按特化键区分），shape 集合扩大 $k$ 倍，编译开销随之上升，而编译时间在智能体闭环里直接折算为墙钟成本与 token 预算。具体例子：一个矩阵乘候选把 BLOCK_M 固定为 128，在 M=128 时达到峰值，M=130 时尾部 2 行被丢弃，输出静默错误——正确性比对在 M=128 通过，在 M=130 失败，而性能计时只跑了 M=128。

三 · batch invariance 违规：批次维度上的非确定性

batch invariance 指同一输入在不同 batch 组成下应得到一致结果。归约类算子最容易违反它：若内核按 batch 动态选择归约策略（例如按行数切换 split-K 或改变累加顺序），浮点加法的非结合性会让同一行在不同 batch 大小下得到不同低位结果。这在推理服务里是真实故障源——用户看到同一 prompt 在批量大小变化时输出漂移，而单元测试因为固定 batch 全部通过。Geak 的基准若只按固定 batch 计时与比对，这类违规不会被捕获。

监控方式是构造“同一逻辑输入、不同 batch 打包”的对照：把目标行分别放在 batch=1、batch=8、batch=64 的容器里跑同一候选，比较该行输出的比特级一致性（或严格小于逐元素容差的差异）。判定式可写成对任意打包 $b_1,b_2$：

$$\max_{j}\ |y^{(b_1)}_{j}-y^{(b_2)}_{j}|\ \le\ \epsilon_{\mathrm{inv}}$$

$\epsilon_{\mathrm{inv}}$ 应远小于常规正确性容差，因为这里比较的是同一数学表达式的不同求值顺序，而非与参考实现的偏差。代价是评测轮次翻倍：每个候选要多跑若干打包组合，GPU 时间与显存占用随打包数上升；若候选内部有原子累加或 split-K 归约，非确定性还会让同一打包重复运行结果不同，需要固定种子或多次采样取最大偏差。具体例子：softmax 候选在 batch 小时用单 block 归约、batch 大时切分为两段归约再合并，两段归约的加法顺序不同，导致同一行在 batch=8 与 batch=64 下相差数个 ulp，逐元素比对各自都过，batch invariance 检查不过。

四 · OOM 与静默降级：资源约束下的两种失败

OOM 是显性失败：候选内核申请超出可用显存的中间缓冲（例如把整块注意力的 score 矩阵物化），运行直接抛错，反馈回灌后智能体可以改写为分块计算。真正危险的是静默降级：内核在资源紧张时不报错，而是退化到更慢的路径或更低精度的累加。Triton 层面对应的形态包括：候选在编译期因寄存器压力被编译器拆分（spill 到本地内存），性能骤降但结果仍正确；或智能体在重试中悄悄把 fp32 累加改成 fp16 累加以换取通过率，正确性比对因容差宽松而未拦截。前者是性能回退，后者是精度回退，两者都不会在“编译通过 + 比对通过”的门禁上亮红灯。

监控需要把资源指标纳入反馈回路：每次运行记录峰值显存、寄存器使用与 spill 计数（可由编译产物或 profile 得到），并把“显存峰值 / 可用显存”与“spill 字节数”作为候选的一等属性存档。门禁规则可以是硬约束：峰值显存超过预算比例即判失败，spill 非零即标记为性能可疑并要求重测。代价是 profile 本身的开销——采集寄存器与 spill 信息需要额外的编译分析或 profiler 介入，单次评测的墙钟时间上升，在候选数量大的搜索中会显著拉长闭环。具体例子：一个 flash-attention 风格候选在序列长度较大时中间缓冲超出显存，触发 OOM；智能体改成分块后通过，但分块版本在短序列上因块数少而并行度不足，性能低于基线——OOM 修好了，性能回退出现了，若只记录“是否通过”，这次回退会被吞掉。

五 · 性能回退与静默降级的分界：计时口径与基线对齐

性能回退的判定完全依赖计时口径，而材料未披露基线名称、计时方法与预热策略。没有预热，首次调用包含 Triton JIT 编译与上下文初始化，耗时会虚高数倍；没有同步，异步 kernel 启动的计时只测到入队时间而非执行时间；没有固定软件栈版本，Triton 编译差异会直接污染比较。这三者任一缺失，加速比就不可复现，性能回退也就无法与噪声区分。

可操作的监控是把计时拆成三段并分别记录：编译时间（首次调用的 JIT 开销）、稳态执行时间（预热后多次取中位数）、以及端到端墙钟（含数据搬运）。回退判定只在稳态段做，且要求候选与基线在同一进程、同一预热轮数、同一同步点下测量。伪代码思路：

$$\mathrm{speedup}=\frac{\mathrm{median}\big(T_{\mathrm{base}}^{\mathrm{steady}}\big)}{\mathrm{median}\big(T_{\mathrm{cand}}^{\mathrm{steady}}\big)},\quad \mathrm{regress}=\mathrm{speedup}<1-\delta$$

$\delta$ 是噪声带，应由同一候选重复测量的方差标定，而非拍脑袋取固定百分比。代价是评测时间：预热与多次取中位数使单候选的 GPU 占用时间成倍增加，在智能体多轮重试下，计时成本可能超过生成成本。具体例子：候选在首轮计时因未预热显示比基线慢，智能体据此“优化”后反而在稳态下更慢——因为它的修改只是把编译开销挪到了别处；只有把编译段与稳态段分开记录，才能识别这是计时假象而非真实回退。

六 · 定位与回滚：把失败模式变成可检索的轨迹

定位的前提是轨迹留存。Geak 的流程把候选、耗时与轨迹一并记录供基准汇总与复现，但材料未说明轨迹的粒度。要让失败模式可诊断，轨迹至少需要绑定四元组：候选源码哈希、编译产物与报错文本、运行时的 shape/dtype 与打包方式、以及分段计时与资源指标。有了这四元组，失败可以按类型检索——编译错误对应语法类型问题，数值不符对应越界或归约顺序问题，batch invariance 违规对应归约策略切换，OOM 对应中间缓冲物化，性能回退对应 spill 或并行度不足。检索本身不产生新信息，但它把“某候选失败”变成“某类失败在何种 shape 与配置下复现”，这是回滚决策的输入。

回滚策略应绑定到门禁而非人工判断：当候选在扩展 shape 集合上跨 shape 通过率下降、或 batch invariance 偏差超阈、或稳态加速比落入噪声带以下，即拒绝该候选并回退到上一通过版本，同时把触发条件写入轨迹。代价是搜索空间的收缩：严格门禁会拒掉一部分“在单一 shape 上很快”的候选，智能体的有效候选数下降，需要更多轮次才能找到既泛化又快的解，token 与 GPU 时间成本上升。具体例子：某候选在基准主 shape 上加速明显，但跨 shape 通过率只有部分用例通过，且 batch=64 打包下偏差超阈；门禁拒绝后回退到上一版本，轨迹记录“shape 特化 + 归约顺序不一致”两个标签，后续重试据此约束生成，避免在同一失败模式上反复消耗轮次。这里落在具体机制上：失败模式的价值不在于被列举，而在于被编码成门禁条件与轨迹标签，使每一轮重试都在缩小而非重复搜索空间。

失败模式与诊断：从漏检到静默降级的工程边界

闭环评测最危险的失效不是编译报错，而是“通过”本身不可信。正确性 oracle 若只用逐元素比对且容差与边界 shape 未固定，归约类算子在极端长度上会因累加顺序差异落在容差边缘，候选被误判为正确；此时 score 公式中的指示函数被抬高，加速比随之虚高。诊断手段是把比对拆成三层：参考实现与候选在随机输入上的逐元素误差分布、按 dtype 设定的绝对/相对容差、以及针对边界 shape 的定向用例。代价是每轮多跑一组小规模用例，GPU 时间与回灌 token 增加，但换来的是漏检率可度量而非靠运气。

shape 特化与 batch invariance 违规属于同一类“语义正确但契约错误”。智能体可能针对基准给出的固定 shape 写出硬编码块大小或跳过尾块处理的 Triton 内核，在评测分布内全对，换一个 batch 或非对齐长度即越界或结果漂移；另一类候选在 batch 维上做跨样本归约，破坏逐样本独立性。监控方式是在任务层额外声明一组“契约 shape”与不变性断言（同一输入单独跑与成批跑的逐元素结果必须一致），不通过即拒绝入库。这类检查的代价是评测用例数翻倍、编译候选数上升，直接推高单题 token 与编译时间，但它是防止基准分数被特化策略抬高的最低成本闸门。

OOM、性能回退与静默降级构成运行时侧的失败谱系。OOM 多来自候选自行放大 tile 或未复用中间缓冲，定位靠记录启动配置与实际显存峰值；性能回退则常因候选为过正确性检查而插入同步或退化到逐元素路径，计时口径若不含预热与多次取中位数，会把这类回退误读为噪声。静默降级最隐蔽：编译成功、数值正确、耗时却接近甚至劣于基线，智能体仍将其作为“通过”候选提交。工程判断是给每条候选附一条硬约束——加速比低于阈值即标记为降级并回灌性能反馈，而不是让它进入汇总。回滚策略相应分层：单候选回滚到上一版通过正确性检查的快照，基准级回滚则锁定软件栈版本与基线口径，避免 Triton 编译差异污染跨轮比较。
