一 · 失效模式：当 MAP-Elites 的“行为维度”变成过拟合通道

KernelFoundry 的核心是 MAP-Elites 质量多样性搜索，它把候选 kernel 投射到一组“kernel-specific behavioral dimensions”上，在每个网格单元保留最优个体以维持探索。这套机制在离线基准上有效，但它同时制造了一类结构性失效：行为维度一旦与评测输入分布耦合，搜索就会沿着“在该分布上表现好”的方向漂移，而不是沿着“在该硬件上真正高效”的方向漂移。具体机制是，行为维度通常由 profile 派生量（占用率、每线程指令数、共享内存使用量、访存模式分类）构成，这些量对 shape 高度敏感。当基准题固定 shape、固定 dtype、固定 layout 时，MAP-Elites 会把“恰好匹配该 shape 的 tile 尺寸与展开因子”固化为精英个体，搜索收敛到一组 shape 特化 kernel。

代价体现在迁移上：这类特化 kernel 在隐藏输入分布上会同时损失正确性裕度与性能。正确性方面，边界 shape（非整除、极小 M/N/K、非连续 stride）会触发越界或未定义行为，而离线正确性门只覆盖给定输入；性能方面，tile 尺寸与寄存器压力是按特定 shape 调优的，换 shape 后占用率骤降，时延回退到基线以下。用论文自身的评分口径看，

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个指标对“多数题勉强过线、少数题崩塌”的分布不敏感——它只数过线题数，不惩罚单题上的严重回退。一个在 KernelBench 上拿到 2.3 平均加速比的候选集，完全可能包含若干在隐藏 shape 上慢于 PyTorch eager 的个体，而 score 仍然好看。工程判断是：把 score 换成带最差题惩罚的聚合（如几何平均或分位数下界），并在精英保留时加入跨 shape 的稳健性过滤，否则 MAP-Elites 的多样性只是“过拟合方式的多样性”。

二 · 适用边界：SYCL 跨平台叙事与硬件绑定的张力

论文的一个显著主张是用 SYCL 生成跨平台 GPU kernel，并在 KernelBench 上报告 SYCL 的平均加速比 2.3，同时生成 CUDA kernel 与先前工作对比。这里存在一个必须讲清的边界：跨平台编程模型不等于跨平台性能可迁移。SYCL 的抽象层把 work-group、sub-group、local memory 暴露给程序员，但不同厂商后端对这些概念的映射差异巨大——sub-group 宽度、local memory 容量、寄存器文件组织、warp/wavefront 调度策略都不同。KernelFoundry 的搜索是在“远程访问的多样硬件”上分布式执行的，这意味着精英个体是在某一块具体设备上被选出的；当同一份 SYCL 源码部署到另一块设备时，行为维度的取值会整体偏移，MAP-Elites 网格的语义随之失效。

具体机制上，行为维度若包含“sub-group 内活跃 lane 比例”或“local memory 占用字节数”，这两个量在 NVIDIA 与 AMD 后端上的默认值不同，同一 kernel 会落入不同网格单元，精英选择不再可比。代价是编译时间与 token 预算的双重浪费：为一块设备演化出的 prompt 与 kernel 组合，在另一块设备上需要重新演化，而 meta-prompt evolution 共同演化的 prompt 本身也带有硬件偏向。论文的分布式框架“remote access to diverse hardware”缓解了测量问题，但没有解决精英个体的可移植性问题。

因此适用边界应表述为：KernelFoundry 适用于“目标硬件固定、输入分布已知且稳定”的离线优化场景；一旦目标硬件集合是开放的，或输入分布由上游动态决定，它的搜索收益会被重新演化成本抵消。一个具体例子是推理服务中的 GEMM：prefill 阶段 shape 随 batch 与序列长度连续变化，decode 阶段则是极小 M 的 GEMV 形态，两段的最优 tile 完全不同，单一精英个体无法同时覆盖，必须按形态分桶演化，而这已经超出论文所述的单次搜索流程。

三 · 与相邻工作的差别：演化搜索 vs 反馈回路 vs 对比式 RL

把 KernelFoundry 放进相邻工作谱系里，差别不在“是否用 LLM”，而在“搜索信号的结构”。标准 prompting 加反馈回路（CUDA-LLM、CudaForge 一类）把编译错误、运行结果、profile 数值作为下一轮 prompt 的输入，本质是单链贪心：每轮只保留一个候选，反馈只告诉模型“上一个好不好”。KernelFoundry 的 MAP-Elites 保留的是种群，反馈告诉模型“这一类行为特征的个体好不好”，搜索信号带有分箱结构，因而能跳出单链的局部最优。对比式 RL（CUDA-L1、CUDA-L2 一类）则把奖励做成可验证的加速比，用策略梯度更新生成分布；它的信号是标量奖励，没有行为维度的显式建模，探索依赖采样噪声。

方法族搜索信号探索机制主要代价
prompt+反馈回路单候选的编译/运行/profile 结果无，链式贪心易陷入首个可行解，token 消耗线性于轮数
对比式 RL标量加速比奖励策略采样噪声奖励稀疏，需大量采样；reward hacking 风险
KernelFoundry分箱后的精英质量 + prompt 共演化MAP-Elites 网格填充每代需编译并测量整个种群，编译时间与设备占用高

关键差别在 meta-prompt evolution：prompt 与 kernel 共同演化，意味着搜索空间包含“如何描述任务”这一层。这带来一个相邻工作没有的失效面——prompt 可能演化出对评测器有利但对任务无意义的措辞，例如引导模型生成在基准 shape 上恰好对齐的代码。这与 reward hacking 同源，但发生在文本层而非代码层，更难用正确性门拦截。工程上应对它需要把 prompt 变异限制在结构化模板内，并对 prompt 做与 kernel 同等强度的回归测试。

四 · 正确性 oracle 的薄弱面：fallback 与“虚高正确率”

论文的流程是编译、在给定输入上做正确性检查、测量时延、按反馈保留或回退。这条链路里最脆弱的一环是正确性 oracle 的覆盖面。当候选 kernel 在基准输入上通过检查，它就被标记为正确；但基准输入通常是若干固定 shape 的随机张量，不覆盖 NaN/Inf 传播、非对齐指针、别名（aliasing）、并发写竞争、以及累加顺序导致的浮点差异。一个具体机制是 reduction 类 kernel 的原子加：候选可能用非确定性顺序累加，在基准容差内通过，但在要求位级可复现的生产管线里不可接受。

更隐蔽的是 fallback 路径。若框架在候选失败时回退到 PyTorch 参考实现并仍计入时延统计，正确率会被系统性抬高：失败候选的时延被参考实现的时延替代，score 里的 s_i 变成基线对基线的比值，恒为 1 附近，从而“过线”。论文摘要未给出 fallback 的处理细节，这本身就是需要核验的点。代价是可信度：一个报告 2.3 平均加速比的系统，若其正确性门只覆盖固定输入且允许静默回退，则加速比的分母里混入了未被优化的路径。

工程判断是三重加固：其一，正确性 oracle 必须包含形状扰动与边界用例（0 长度、非整除、stride 非连续），并对浮点结果做相对误差与位级双口径；其二，fallback 必须显式记录并在评分中标注，禁止静默替换；其三，对每个精英个体保留其通过的输入集合，部署前在真实输入分布上重跑，任何未覆盖形态一律视为未验证。这三条不增加搜索成本，只增加验证成本，而验证成本远低于生产事故。

五 · 什么情况下不该用它

第一类不该用的场景是延迟敏感的一次性任务。KernelFoundry 的每一代都需要编译并测量整个种群，分布式远程硬件访问进一步引入排队与传输开销；对于只跑一次、或对编译时间有硬上限（如 CI 中的分钟级预算）的任务，演化搜索的固定开销超过其收益。相比之下，单链反馈回路在少量轮次内就能给出可用候选，代价是解的质量上限更低。判断标准是：优化收益是否值得多花一个数量级的编译与测量时间。

第二类是不具备可靠 profile 与稳定测量环境的场景。MAP-Elites 的行为维度依赖 profile 输出，若设备被共享、时钟被降频、测量噪声与候选间差异同量级，分箱结果就是噪声的分箱，精英选择退化为随机。此时搜索不会收敛，只会消耗 token 与设备时间。论文的分布式框架假设硬件可远程访问且测量可复现，这一假设在多数共享集群上不成立。

第三类是正确性规格本身模糊或不可判定的任务。若算子语义依赖未文档化的库行为（如特定 cuBLAS 版本的累加顺序、特定 dtype 的舍入模式），正确性 oracle 无法给出确定判据，演化搜索会朝着“匹配参考实现偶然行为”的方向过拟合，产出的 kernel 在库版本升级后失效。这类任务应先固化语义规格，再谈优化。

第四类是目标硬件尚未确定或频繁变更的部署。如前所述，精英个体与 prompt 都带硬件偏向，跨设备迁移需要重新演化；若部署目标在演化期间变化，整个搜索预算作废。此时更合适的是硬件无关的算法级优化（分块策略、数据布局），把硬件特化留给部署期的最后一次编译。

最后需要指出，论文的结论只在给定硬件、基线与输入分布上成立，且数字为论文声称、未独立复现；跨硬件、跨 dtype、跨框架的迁移未验证。把 KernelFoundry 当作“默认开启”的优化器是工程上的误判——它是一台需要明确输入边界、明确验证口径、明确硬件目标才能启动的搜索机器，边界之外的收益不可信。

进化搜索的失效面：行为维度、代理指标与跨硬件迁移

KernelFoundry 的 MAP-Elites 骨架把「行为维度」当作网格坐标，把「适应度」当作格子内的保留依据。这一设计在搜索早期极其有效，但它的失效模式几乎全部来自这两者的错配。行为维度是人工指定的 kernel 特征（分块大小、线程映射、共享内存用量一类），一旦维度选得与真实性能瓶颈正交，网格就会被大量「行为上不同、性能上等价」的个体填满，探索预算被均匀地摊薄到无意义的格子里。更糟的是，行为维度是离散化的，边界附近的个体被强行归入相邻格子，导致真正处于性能拐点的候选被丢弃。代价是可测量的：网格规模随维度数指数增长，每个格子至少需要一次编译加一次计时才能被占据，编译时间与远端硬件排队时延直接线性叠加到总预算上；在分布式框架下，一次跨机器 benchmark 的往返时延往往比 kernel 本身的时延高两三个数量级，网格越细，无效往返越多。工程判断是：行为维度数应控制在 2–3 个，且每个维度必须能通过一次廉价的静态分析（寄存器用量、occupancy 上限）预估，而不是靠编译后实测。

适应度函数是第二个失效点。论文口径下的分数是阈值化的加速比计数：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个式子的分母是基线时延，因此基线的选择直接决定搜索方向。若基线未开启 TF32、未链接最强库实现，或基线本身是一个未经调优的朴素版本，那么 $T_{\text{base}}$ 被系统性高估，所有候选的 $s_i$ 同步膨胀，阈值 $\tau$ 变得毫无区分度——搜索会收敛到「比弱基线快」而非「接近硬件上限」的个体。阈值化的另一面是梯度消失：一旦某候选跨过 $\tau$，继续优化的收益在分数上不可见，进化压力消失，后续变异退化为随机游走。这与 roofline/SOL 口径的连续指标形成鲜明对比，后者能把 60% SOL 与 75% SOL 区分开，而阈值计数不能。代价体现在 token 上：为了恢复区分度，必须扩大种群规模或增加代数，prompt 与 profile 回灌的 token 消耗随之上升，而收益被阈值截断。

第三类失效来自 shape 特化与输入分布漂移。进化框架天然倾向于生成对评测输入过拟合的 kernel：分块尺寸、向量化宽度、甚至分支结构都可能被调到恰好匹配基准 shape 的因子。离线分数因此虚高，而生产端一旦遇到非对齐维度、动态 batch 或不同 dtype，性能会断崖式下跌，正确性门也可能因边界处理缺失而失败。这类过拟合在 MAP-Elites 下被放大，因为行为维度奖励「与众不同」，而「与众不同」常常等价于「对该 shape 特别定制」。迁移到相邻硬件时问题更严重：SYCL 跨平台生成意味着同一份候选要在不同厂商的硬件上编译运行，而行为维度与适应度都是在特定硬件上测得的；subgroup 大小、共享内存带宽、warp 调度策略的差异会让网格坐标失去物理含义，历史最优个体在新硬件上可能连正确性都过不了。论文的分布式远端访问缓解了「测不到」的问题，但没有解决「测了不可迁移」的问题——跨硬件、跨 dtype、跨框架的迁移在摘要级口径下未被验证。

还有一类代价常被忽略：reward hacking 与回退路径。当正确性门只覆盖有限输入，候选可以通过特判、跳过边界或依赖未定义行为来「通过」检查，同时在计时上取巧（例如把计算挪到异步流之外、复用上一次结果）。这类个体在进化中具有选择优势，因为它们的时延极低。防御手段是把正确性 oracle 做成随机化输入加参考实现逐元素比对，并把计时绑定到同步后的端到端区间；代价是每次评估的时延与显存占用上升，评估吞吐下降，搜索代数被迫压缩。与相邻工作的差别正在此处：标准 prompt-feedback 循环只把 profile 当作反馈信号，缺少行为维度的多样性维持，容易早熟收敛；而 KernelFoundry 用质量多样性换取了探索广度，代价是网格维护、跨机往返与过拟合风险。判断是否该用它的分界线很清晰：当任务处于硬件上限附近、基线已是最强实现、输入分布稳定且单一硬件时，进化搜索的边际收益低于其编译与往返开销，此时应退回单点 profile 驱动的定向优化；反之，当设计空间离散、行为维度可静态预估、且允许跨硬件批量 benchmark 时，它才是合适的工具。
