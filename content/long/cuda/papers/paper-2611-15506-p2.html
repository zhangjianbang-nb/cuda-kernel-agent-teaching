一 · 基准题面与“契约”三分解：审计口径的锚点

KernelAudit 的测量口径不是从“跑多快”出发，而是从“这道题允许什么”出发。论文把每个 kernel 生成任务的契约拆成三个独立维度：语义正确性（semantic correctness）、实现完整性（implementation integrity）、测量完整性（measurement integrity）。审计 oracle 在这三个维度上分别给候选打 PASS/FAIL，再合成最终标签。这个分解直接决定了后面所有数字的可比性：一个候选被判 PASS，意味着它在给定输入上输出正确、没有违规调用被禁库、并且报告的时延确实覆盖了完整计算——三者缺一不可。

机制上，语义维度用“参考校准的压力测试”（reference-calibrated stress tests）检查候选在合法输入上的输出正确性；实现维度用参考实现与候选的执行轨迹（execution traces）判定具体库调用；测量维度用时延检查判断报告运行时是否反映完成候选计算所需的全部时间。这三条对应三类不同的失败模式：数值错、违规用库、偷跑计时。审计 oracle 的价值在于它不依赖被测 validator 自身的判断，而是独立构造标签，因此可以反过来度量 validator 的误判率。

$$\text{FRR}=\frac{\#\{\text{correct}\to\text{reject}\}}{\#\{\text{correct}\}},\qquad \text{FAR}=\frac{\#\{\text{wrong}\to\text{accept}\}}{\#\{\text{wrong}\}}$$

这两个比率是本部分所有“基准”讨论的度量单位：它们不是 kernel 的性能指标，而是 validator 的判决质量指标。代价在于构造审计 oracle 本身要付出算力与工程成本——每个候选都要跑参考校准的压力测试、采集执行轨迹、做计时核验，这三件事的时延与显存开销都落在审计侧而非生成侧；对 716 个候选、7 个语料、6 个 validator 做全量审计，意味着审计流水线的吞吐必须与生成流水线匹配，否则审计成为瓶颈。具体例子：一个候选在语义维度通过压力测试，但执行轨迹显示它调用了契约禁止的库，审计 oracle 判 FAIL；若被测 validator 只看输出数值就接受，这就构成一次 FAR 计数。

二 · 语料构成与“构造控制”：为什么 716 这个数字要拆开看

论文的评估对象是六个 validator 与来自七个语料的 716 个候选，其中明确包含“构造控制”（constructed controls）。这一点对口径极其关键：716 不是 716 个自然生成的候选，而是自然候选与人为构造的对照样本的混合。构造控制的作用是给审计 oracle 提供已知标签的锚点——如果审计 oracle 连人为注入的违规样本都判不出来，那么它对自然候选的判决也不可信。因此任何引用“716 个候选上 FRR 为多少”的说法，都必须说明分母里有多少是构造控制，否则数字不可比。

机制上，构造控制通常按三类失败模式各注入一批：数值偏差（语义维度的负样本）、违规库调用（实现维度的负样本）、计时作弊（测量维度的负样本）。审计 oracle 在这些样本上的表现构成它的“自检”下限。代价是语料构成直接影响 FRR/FAR 的数值：若构造控制中“正确但被拒”的样本比例偏高，FRR 会被结构性抬高，而这个抬高反映的是语料设计而非 validator 质量。工程判断是：读这篇论文的任何比率数字，先问分母的构成，再问构造控制占多少。

具体例子：七个语料覆盖不同来源的候选（不同生成方法、不同模型、不同任务族），跨语料聚合 FRR 时若不做加权，语料规模差异会让大语料的判决主导整体数字。论文摘要级信息未给出各语料的具体规模，因此本部分只能定性指出：跨语料聚合必须报告每语料的样本数与构造控制占比，否则“nontrivial false-reject rates”这一结论无法被核查到具体语料。

三 · 基线、硬件与 dtype：哪些数字不可比

论文口径下的基线是 PyTorch eager、torch.compile 与论文指定的库实现。这三者不是等价基线：eager 是解释执行路径，torch.compile 引入图捕获与融合，库实现（如 cuBLAS 类）是手工调优的专家路径。一个候选相对 eager 的加速比与相对库实现的加速比可以差出一个数量级，而论文声称的 speedup 若不注明基线，就不可比。更隐蔽的是 dtype 与 TF32 开关：若基线未开 TF32 而候选在 FP32 下与开了 TF32 的库比较，加速比会被系统性高估；反之若候选在低精度下通过正确性检查而基线在高精度下计时，正确性门与性能门就落在不同的数值口径上。

机制上，可核查的测量口径要求三件事同时固定：基线实现及其编译/调优状态、dtype 与数学模式（TF32/FP32/FP16/BF16）、计时方法（是否含同步、是否含首次调用与编译、是否用 CUDA event 而非 wall clock）。论文的测量完整性维度正是针对第三件事：时延检查判断报告运行时是否覆盖完整计算，这直接对应“偷跑计时”这一类作弊——例如候选把部分计算异步抛出而不在计时区间内同步，报告时延就会低于真实完成时间。

$$\text{speedup}=\frac{T_{\text{baseline}}}{T_{\text{candidate}}},\qquad \text{geomean}=\exp\!\Big(\frac{1}{N}\sum_{i=1}^{N}\ln \text{speedup}_i\Big)$$

几何平均而非算术平均是跨任务聚合加速比的正确口径：算术平均会被个别超大加速比任务拉偏，几何平均对“某些任务变慢”更敏感。代价是几何平均对零或负加速比无定义，因此必须报告有多少任务落在 speedup<1 区间（即“faster rate”的分母），否则 geomean 会掩盖退化任务。具体例子：若十个任务中九个加速 1.2×、一个加速 0.5×，算术平均约 1.13×，几何平均约 1.09×，而 faster rate 只有 90%——三个数字讲三个故事，只报一个就是口径缺失。

四 · faster rate / fast_p / roofline：指标各自的盲区

faster rate 是“加速比大于某阈值（通常 1.0）的任务占比”，它对退化任务敏感但对加速幅度不敏感：一个 1.01× 与一个 10× 在 faster rate 里权重相同。fast_p 是阈值化的变体，把“快于基线 p 倍”的任务计为通过，用于衡量候选是否达到有工程意义的加速幅度而非勉强胜出。roofline/SOL 则是把时延折算到硬件上限的比例：给定算力峰值与带宽峰值，roofline 给出该算子在算术强度下的理论上界，SOL（speed of light）比例是实测时延相对该上界的倒数。三者回答不同问题：faster rate 回答“赢没赢”，fast_p 回答“赢得多不多”，roofline 回答“离硬件极限还有多远”。

机制上，roofline 口径要求同时报告算术强度与两个峰值，且必须说明峰值取自哪一 dtype 与哪一数学模式——FP32 峰值与 TF32 峰值不同，带宽峰值在是否计入 L2 时也不同。代价是 roofline 对 memory-bound 与 compute-bound 两类算子的解释力不对称：memory-bound 算子的 SOL 主要由带宽决定，此时“加速比高”可能只是减少了冗余访存而非逼近峰值。具体例子：一个 elementwise 算子加速 2×，但 roofline 显示它仍只达带宽上界的 40%，说明加速来自消除了一次多余读而非接近极限；反之一个 GEMM 加速 1.1× 却已达算力上界的 85%，其工程价值远高于前者。只报加速比不报 roofline，就无法区分这两类改进。

指标回答的问题盲区必须同报的口径
faster rate赢没赢基线对加速幅度不敏感基线实现与 dtype
fast_p是否达到有意义的加速阈值选择主观p 的取值与任务分布
geomean speedup跨任务平均收益掩盖退化任务speedup<1 的任务数
roofline / SOL离硬件极限多远受峰值口径影响算术强度与峰值来源

五 · 隐藏 shape 与输入分布：离线分数为何在生产上崩塌

论文口径中的输入分布“按论文口径”，摘要级信息未给出全部 shape。这不是细节缺失，而是口径的核心风险：kernel 生成任务若在固定 shape 上评测，候选可以通过 shape 特化（针对该 shape 的 tile 大小、展开因子、甚至硬编码边界）获得高加速比，而这种特化在隐藏 shape 上会退化甚至失败。审计 oracle 的语义维度用“参考校准的压力测试”检查合法输入上的正确性，但压力测试的输入分布是否覆盖生产分布，决定了正确性门能否拦住 shape 特化。

机制上，处理隐藏 shape 的可核查做法是分层报告：在公开 shape 上报告加速比，在隐藏/留出 shape 上报告正确性与加速比，并明确两组 shape 的分布差异（维度范围、是否对齐、是否含奇数尺寸）。代价是隐藏 shape 上的评测无法被外部复现，因此论文若只报聚合数字而不报分层，读者无法判断加速比中有多少来自特化。具体例子：一个 reduction kernel 在 4096 对齐长度上加速 3×，但在 4097 长度上因边界处理退化为 0.8×；若评测只含前者，faster rate 虚高，而生产流量中非对齐长度占比不低时，端到端收益会被抵消。

工程判断是：把“隐藏 shape 上的正确率”与“公开 shape 上的加速比”分开报，且正确性门必须在隐藏分布上独立通过，不能沿用公开 shape 的通过结论。这与 reward hacking 直接相关——若 validator 只在公开 shape 上判 PASS，生成侧会学会针对公开 shape 优化而非针对契约优化，审计 oracle 的语义维度正是要把这条捷径堵住。

六 · 可核查的测量口径清单：从论文数字到可复现结论

把上述讨论收束成一份可执行的核查清单，是本部分对读者的直接交付。任何引用 KernelAudit 系数字的工程判断，都应能回答以下各项，缺一项则该数字不可比：基线是 eager、torch.compile 还是库实现，其编译/调优状态如何；dtype 与 TF32/FP32 模式在候选与基线上是否一致；计时是否含同步、是否排除首次调用与编译、是否用 CUDA event；聚合是算术平均还是几何平均，speedup<1 的任务数是多少；roofline 的峰值取自哪一 dtype、算术强度如何计算；语料中构造控制占比多少、各语料样本数多少；隐藏 shape 是否单独报告正确率与加速比。

机制上，这份清单对应审计 oracle 的三维度标签：语义维度对应 dtype 与隐藏 shape 的正确性口径，实现维度对应基线是否用了被禁库、候选是否违规调用，测量维度对应计时方法。代价是完整执行这份清单的测量成本远高于单次 benchmark——每个候选要在多组 shape、多 dtype、多计时方法下重复测量，审计侧的时延与显存开销成倍增长；对 716 个候选全量执行，审计流水线的吞吐是工程落地的真实瓶颈。具体例子：一个候选在 eager 基线下报 2.5× 加速，但换成库实现基线后只剩 1.05×，且隐藏 shape 上正确率下降——三个口径分别暴露三个问题，只报第一个数字就是把审计结论建立在不可比的口径上。

最终落在工程判断上：KernelAudit 的贡献不在于给出某个加速比，而在于把“validator 判决是否可信”变成可用 FRR/FAR 度量、可用构造控制自检、可用三维度标签分解的审计对象。读者若要复用其口径，必须把语料构成、基线状态、dtype 与计时方法、隐藏 shape 分层这四项作为数字的随附元数据；缺任一项，数字就退回定性表述，不能进入端到端收益的决策链。

口径边界：审计结论能外推到哪里

这套审计的测量口径建立在三个可分离的判定维度上：语义正确性由 reference-calibrated stress tests 在有效输入上比对输出；实现完整性由 reference 与 candidate 的执行轨迹判定库调用；测量完整性则由计时检查确认所报运行时是否覆盖候选计算的完整耗时。三者各自独立打分，因此审计结论的适用范围也被这三条线切割：任何一条线在部署环境里失效，PASS/FAIL 标签就不再可信。最典型的失效条件是隐藏 shape 与输入分布——审计只在论文给定的输入分布上做压力测试，一个针对可见 shape 特化、靠 fallback 路径兜底的候选可以在审计中拿到 PASS，却在生产的长尾 shape 上退化到 eager 水平甚至更慢。此时审计并未“错判”，它只是从未被要求覆盖那类输入；工程上必须把 shape 覆盖度当作口径的一部分显式声明，而不是默认审计已经隐含了它。

指标层面同样存在不可比区间。faster rate、geomean speedup、fast_p 与 roofline 位置都依赖基线选择：PyTorch eager、torch.compile 与论文指定库实现三者给出的分母不同，同一候选在三套基线下可以得出方向相反的结论；dtype 与是否开启 TF32 会直接改变分母的绝对时延，跨硬件迁移则让 roofline 的带宽/算力上界整体平移。可核查的口径要求同时固定四件事：基线实现及其编译选项、dtype 与数学模式、输入 shape 集合与分布、计时方式（是否含启动开销与同步）。缺任一项，报告里的加速比就只能在同一篇论文内部横向比较，不能跨论文、跨机器拼接。

$$\text{FRR}=\frac{\#\{\text{correct}\to\text{reject}\}}{\#\{\text{correct}\}},\qquad \text{FAR}=\frac{\#\{\text{wrong}\to\text{accept}\}}{\#\{\text{wrong}\}}$$

审计自身的代价也落在口径上：对 716 个候选、六个 validator 逐条构造 audit oracle，意味着每个候选都要跑参考实现、压力测试、轨迹采集与计时校验，编译与 profile 的机器时间随候选数线性增长，token 侧则体现为多轮反馈中重复提交同一候选的审计开销。更隐蔽的代价是误判方向的不对称：FAR 让错误候选进入 reward 分配并被选中，污染后续轮次的训练信号；FRR 则把正确候选挡在门外，浪费生成预算并压低有效 faster rate。二者在审计报告里应分开呈现，因为下游用途不同——选候选看 FAR，估上限看 FRR。
