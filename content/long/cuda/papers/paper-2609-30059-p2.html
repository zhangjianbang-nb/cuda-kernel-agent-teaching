一 · 评测对象：250 题的三层结构与“dispatch 可见”的边界

KernelOPT 的评测负载是 KernelBench 全量 250 题，在 NVIDIA H200 上跑完：Level1 是 100 道单算子题，Level2 是 100 道复合算子题，Level3 是 50 个完整模型架构。这个分层不是装饰，它直接决定指标该怎么读。Level1 的候选 kernel 是孤立函数，输入张量由题面固定，测量时延就是一次 kernel launch 的时延；Level2 的候选要在一段由多个算子拼成的数据流里被调用，测出来的时间包含中间张量的分配与相邻算子的间隙；Level3 的候选嵌在 nn.Module 里，测的是整模型前向。三层对应三种不同的“加速比分母”，把 Level1 的 speedup 与 Level3 的 speedup 放进同一张表求 geomean，是把三种不同的物理量平均，数值上没有意义。论文摘要里那句“把孤立 kernel 的改进翻译成模型级收益仍然困难”，在口径上就体现为这个分层：Level1 的高分不保证 Level3 有收益，因为 Level3 的瓶颈往往在 dispatch 开销、算子间同步与显存往返，而不在被替换的那一个 kernel 内部。

“dispatch-aware”这个定语在测量上有一个具体含义：系统读的是编译器产物里的 Triton kernel 与外部库调用，也就是说它优化的是 Inductor 生成的图在运行时实际 dispatch 到的那一段。于是评测口径必须回答一个问题——基线是什么。论文给出的基线是 PyTorch eager、torch.compile 与论文指定的库实现。这三者的时延量级完全不同：eager 是逐算子 Python 侧调度，torch.compile 走 Inductor 融合，库实现（如 cuBLAS/cuDNN 路径）是厂商手写 kernel。若加速比的分母取 eager，一个中等质量的 Triton 候选就能拿到数倍数字；若分母取 torch.compile 的融合产物，同样的候选可能只快一点点甚至更慢。因此任何跨论文比较都必须先对齐分母，否则“快 N 倍”只是分母选择的产物。本片段只讨论口径，具体的搜索机制留给后续部分。

二 · 指标族：faster rate、speedup、geomean、fast-p 与 roofline 各自回答什么

论文的评分公式是阈值化的通过率：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这里 $s_i$ 是第 $i$ 题相对基线的加速比，$\tau$ 是判定阈值。这个形式在口径上等价于 fast-p：它统计的是“有多少题达到了至少 $\tau$ 倍”的比例，而不是平均加速比。两者的差别在长尾上非常尖锐。假设 250 题里有 200 题拿到 1.0 倍、50 题拿到 10 倍，fast-p（$\tau{=}1.0$）是 0.2，而算术平均 speedup 是 2.8。fast-p 对“多数题没有收益”这件事是诚实的，算术平均则被少数大赢家拉高。工程上判断一个 agent 是否可用，看的是 fast-p 与通过题目的分布，而不是一个被长尾污染的均值。

geomean 是另一个口径：$\exp(\frac{1}{N}\sum_i \ln s_i)$。它对加速与减速对称，一题 2 倍与一题 0.5 倍在几何平均里互相抵消，这在比较不同 agent 的稳定性时比算术平均更合适。但 geomean 有一个代价：它要求每一题都有可测的 $s_i$，任何编译失败或正确性不通过的题都必须以某个约定值参与（通常是 0 或 1），这个约定会直接改变 geomean 的量级。论文的四段验证里，正确性门在性能门之前，意味着不通过正确性的候选不进入性能统计，这避免了把“快但错”的候选算进 geomean，但也意味着分母 $N$ 是“通过正确性的题数”而非 250——报告时必须写清 $N$ 的实际取值。

roofline 是第四类口径，它不比较基线，而比较物理上限。对一道题，先算它的算术强度 $I = \text{FLOPs}/\text{Bytes}$，再取 $\min(\text{峰值算力}, I \times \text{峰值带宽})$ 作为可达性能上界，候选的实际吞吐除以上界就是 SOL（speed of light）占比。roofline 的价值在于它把“比基线快”与“离硬件极限近”分开：一个候选可以比 eager 快 5 倍却只有 15% SOL，说明真正的空间还在别处。代价是 roofline 需要精确的 FLOPs 与字节计数，而 Level2/Level3 的复合算子与整模型很难给出无争议的计数，因此 roofline 在 Level1 上最可信，在 Level3 上通常只作定性参考。论文的指标口径里同时出现正确率、加速比与资源占用，资源占用这一项在工程上应理解为显存峰值与占用率，它们与 roofline 一起构成“快得合理”的证据链。

三 · 哪些数字不可比：分母、dtype、硬件与测量方式的四重错位

第一重错位是分母。同一道 Level1 题，分母取 eager 与取 torch.compile 的加速比可以差一个量级；分母取厂商库实现时，一个 Triton 候选在矩阵乘类题目上几乎不可能赢，而在逐元素类题目上又容易赢。跨论文比较时，若 A 论文用 eager、B 论文用最强库，B 的 fast-p 天然更低，这不是方法优劣而是口径差异。第二重错位是 dtype。论文的验证包含多 seed 数值比较与 float64 回退的模型级检查，这说明数值口径是被认真对待的；但加速比本身对 dtype 极度敏感——fp32 与 bf16/fp16 的峰值算力差数倍，若基线未开 TF32 而候选在 bf16 下测，加速比会被系统性高估。摘要没有给出全部 dtype 配置，因此任何跨论文的 dtype 对照都不可靠，只能在同一篇论文内部比较。

第三重错位是硬件。全部 250 题在 H200 上评测，这意味着所有数字都绑定在 H200 的 SM 数量、HBM 带宽与 L2 容量上。一个在 H200 上通过 roofline 判定为带宽受限的候选，换到带宽更低的卡上可能变成算力受限，最优 tile 尺寸随之改变；换到 SM 更少的卡上，占用率与 wave 量化效应会让原本 1.03 倍的收益消失。论文的局限一节明确写了跨硬件、跨 dtype、跨框架迁移未验证，这是口径上的诚实，也意味着 H200 上的 fast-p 不能当作通用能力指标。第四重错位是测量方式：一次 kernel launch 的时延要用 CUDA event 在流内计时并做多次重复取中位数或最小值，若用 wall-clock 包住 Python 调用，测到的是 Python 开销加 launch 开销；Level3 的整模型测量还要决定是否包含首次编译与 warmup，是否清空 L2，是否固定 clock。这些细节在摘要层面不可见，因此“论文声称的加速比”与“可复现的加速比”之间始终存在一段需要自行补齐的口径。

错位维度典型表现对指标的影响
基线分母eager vs torch.compile vs 厂商库加速比量级差一个数量级，fast-p 不可横向比
dtype / TF32基线 fp32 未开 TF32，候选 bf16加速比系统性高估

四 · 隐藏 shape 与输入分布：离线分数在生产上崩塌的机制

论文摘要没有给出全部 shape，只说输入分布按论文口径。这在口径上留下一个必须自行处理的空洞：候选 kernel 是否针对题面给定的固定 shape 做了特化。特化的收益是实打实的——把 tile 尺寸、循环展开因子、shared memory 布局按某一组 $(M,N,K)$ 硬编码，可以省掉运行时的分支与边界判断，在 Level1 上轻松拿到超过 1.03 倍的收益。代价是泛化：生产端的 shape 是动态的，batch 大小随请求变化，序列长度随输入变化，一旦实际 shape 偏离特化点，边界处理缺失会导致越界或错误结果，或者退化到一条未被优化的 fallback 路径，时延反而高于基线。这就是“shape 特化让离线分数在生产上崩塌”的具体机制，它不是概率事件，而是特化本身的定义决定的。

处理这个空洞的口径有三条。其一，在评测集内做 shape 划分：用一组 shape 调优、另一组未见过的 shape 测性能，报告两组之间的加速比衰减。其二，对候选做 shape 扫描，记录 $s_i$ 随 shape 变化的曲线，把“在多少比例的 shape 上仍满足 $\tau$”作为第二个 fast-p。其三，把动态 shape 下的正确性纳入正确性门：论文的四段验证包含执行检查与多 seed 数值比较，若在多个 shape 上跑多 seed 并与 float64 参考比对，特化导致的边界错误会被捕获。这三条都增加测量成本：shape 扫描把每题的测量次数从常数变成与 shape 网格大小成正比，编译时间也随候选数量线性增长；在 agent 搜索场景下，这意味着反馈回路的时延上升，进而影响搜索轮数。工程判断是：宁可牺牲一部分离线 fast-p，也要保留一组隐藏 shape 的测试集，否则优化的是题面而不是算子。

五 · 四段验证与性能门：正确性 oracle 如何改变分母

论文的四段验证是执行检查、多 seed 数值比较、带 float64 回退的模型级检查，以及端到端性能门（$\gamma{=}1.03$）。这四段在口径上构成一条漏斗：候选先要能编译并跑通，再要在多个随机种子下与参考数值一致，再要在整模型层面与 float64 参考对齐，最后才进入性能比较，且只有相对基线达到 1.03 倍才被接受。这个 $\gamma$ 是一个工程上的噪声阈值——它承认测量本身有抖动，小于 3% 的差异不足以判定为真实收益。代价是灵敏度：真实的 2% 改进会被门挡掉，若某题的收益本来就只在个位数百分比，这道题在 fast-p 里恒为 0。因此 $\gamma$ 的选择直接决定 fast-p 的上限，报告时必须写明 $\gamma$，否则不同论文的 fast-p 不可比。

float64 回退这一步值得单独说，因为它是正确性 oracle 的口径核心。低精度 kernel 的数值误差在单算子层面可能落在容差内，但在整模型层面会被放大：一次 softmax 或归一化的偏差经过多层传播后改变输出分布。用 float64 参考做模型级比对，等于把“数值上是否等价于一个可信实现”作为硬门，而不是用低精度基线互比。这提高了正确性判定的可信度，代价是参考实现的构建成本与比对时的显存占用——float64 张量在 H200 上占用是 fp32 的两倍，对 Level3 的大模型意味着必须分块比对或只在选定层上比对。另一个代价是 fallback 路径本身可能被 reward hacking：若 agent 学会在数值不稳时退回一个慢但正确的实现，正确率会虚高而性能收益归零。口径上应对此的辦法是分别报告“通过正确性门的题数”与“同时通过性能门的题数”，两个数字的差值就是 fallback 与无效优化的规模。

六 · 可核查的测量口径清单

把上述讨论收敛成一份可执行的测量口径，读者在复现或对比时应逐项对齐。基线：明确是 eager、torch.compile 还是厂商库，三者分别报告，不混用分母。dtype：写明基线是否开启 TF32，候选与基线是否同 dtype，跨 dtype 的比较一律标注为不可比。硬件：记录 GPU 型号与 clock 设置，H200 之外的迁移需重新测 roofline。计时：用流内 CUDA event，固定 warmup 次数，报告重复次数与取值方式（中位数或最小值），Level3 需说明是否包含首次编译。shape：区分调优集与隐藏集，报告隐藏集上的 fast-p 衰减。指标：同时给出 fast-p（写明 $\tau$）、geomean（写明 $N$ 的实际取值与失败题的约定值）、以及 Level1 上的 SOL 占比。验证：写明四段验证各自的通过数，特别是正确性门与性能门（$\gamma{=}1.03$）的差值。最后，任何跨论文的数字对照都必须先确认这七项中有几项对齐，未对齐的项应视为不可比而非优劣证据。

这套口径的直接后果是：KernelOPT 在 250 题上的结果不能被简化为一个“快了多少倍”的数字，而应被读成三层结构下、以 torch.compile 或库实现为分母、在 H200 上、经过四段验证过滤后的通过率。工程上真正要抄的不是那个数字，而是这条漏斗的形状——正确性门在前、性能门带噪声阈值、模型级用 float64 兜底——因为正是这条漏斗决定了 agent 的搜索反馈是否可信，也决定了离线 fast-p 与生产收益之间那段距离能否被量化。

口径边界：250 题与 γ=1.03 门控在什么条件下失效

KernelOPT 的评测面是 KernelBench 全量 250 题（Level1 单算子 100、Level2 复合算子 100、Level3 模型架构 50），硬件为 NVIDIA H200，基线取 PyTorch eager、torch.compile 与论文指定库实现，指标以加速比与 fast-p 型通过率为主，公式为 $$s_i=T_{\text{base},i}/T_{\text{cand},i},\quad \text{score}=\frac{1}{N}\sum_i\mathbb{1}[s_i\ge\tau]$$ 其中 τ 的取值直接决定分数含义：τ=1.0 是“不慢于基线”，τ 取论文端到端门控的 γ=1.03 则是“至少快 3%”。同一批候选在两种 τ 下可以给出差异极大的通过率，因此报告 fast-p 时必须同时给出 τ、基线版本与 dtype 口径，否则数字不可比。Level3 的模型级检查还叠加了 float64 fallback 与端到端性能门控，这意味着一个在 Level1 上加速明显的 kernel，若在模型装配后触发 fallback 或未过 γ 门，最终不计入收益。

失效条件集中在三处。其一，基线强度：若 torch.compile 未开启与论文一致的编译模式、库实现未取最强后端、或未统一 TF32 开关，分母被抬高，加速比系统性虚高；跨 dtype（fp32/fp16/bf16）比较时，roofline 位置本身改变，同一 kernel 的 SOL 利用率不可直接横比。其二，shape 特化：dispatch-aware 搜索会针对编译器产物中的具体调用点做合成，隐藏 shape 或输入分布一旦偏离离线题面，特化分支退化为通用路径，离线分数在生产上崩塌，而论文口径并未覆盖跨分布迁移。其三，正确性口径：多 seed 数值比较与 float64 fallback 能压住大部分数值漂移，但 fallback 路径本身会掩盖候选在边界输入上的错误，使正确率虚高；reward hacking 则表现为候选针对测量方式而非真实负载优化。

口径项可核查要求不可比场景
基线eager / torch.compile / 指定库三档分别报告仅报最弱基线
dtypefp32、fp16、bf16 分列，TF32 开关写明混 dtype 取 geomean
shape题面 shape 与隐藏分布分开标注特化 kernel 冒充通用
门控γ=1.03 与 τ=1.0 两套分数并列只报宽松 τ

系统代价同样落在口径上：250 题全量跑四阶段验证（执行检查、多 seed 数值比较、模型级 float64 回退、端到端性能门控）意味着每题至少一次编译加多次计时，编译时间与 GPU 占用是搜索预算的硬约束；把 γ 门控放到模型级又要求装配完整模型，单题评测时延远高于孤立 kernel 计时。工程判断是：把 Level1 的 fast-p 当作搜索能力的上界指标，把 Level3 过 γ 门的比例当作可部署收益的下界指标，两者之间的落差就是 dispatch 与装配开销的真实代价，任何只报单一分数的评测都不可采信。
