一 · 一个推理服务里的算子交付现场

设想一个已经上线的推理服务：主干是 Transformer 解码，每层里有一组形状固定但 dtype 与 batch 会随流量波动的融合算子——RMSNorm 加残差、RoPE 旋转位置编码、KV cache 的 paged attention 拼装、以及一个带 mask 的 softmax。这些算子原本由一位熟悉 CUDA 的工程师手写，代码里塞满了针对特定 head_dim 与 SM 架构的展开、__shfl 归约、共享内存 bank 对齐和 cp.async 流水。服务上线三个月后，GPU 换代、head_dim 从 64 变到 128、序列长度分布整体右移，这份 kernel 需要重写。工程师的排期是两周：一周写、一周调。这不是夸张，而是手写 CUDA 的常态成本结构——开发周期以周计，性能上限由作者对硬件细节的掌握程度决定，正确性靠人肉构造的边界用例兜底，可维护性则几乎为零，因为每一处展开都与具体形状绑定。

于是工程团队转向第二条路：Triton。同一个 RMSNorm 用 Triton 写出来只有几十行，tl.load/tl.sum/tl.store 把向量化、线程映射和共享内存交给编译器，形状参数化天然支持。代价是性能上限被编译器策略钳住：归约维度上的 block size、num_warps、以及是否触发 tl.dot 的 tensor core 路径，都需要人工扫参；一个 block size 选错，就可能从接近带宽上限掉到一半。更隐蔽的代价是编译时间——Triton 的 JIT 在首次遇到新 shape 时要做 autotune，若 autotune 空间开得大，冷启动时延会直接打进服务的 P99。

第三条路最省事：直接调库。cuBLAS、cuDNN、CUTLASS 的现成 kernel，或者 PyTorch 的 torch.compile 生成物。这条路把正确性和可维护性外包给了 NVIDIA 与 PyTorch 团队，但把性能上限和形状适配权也一并交了出去：库的启发式选择在非常规 shape、非常规 dtype 组合、或者需要与前后算子融合的场景下会退化；而融合本身往往才是收益来源——一个单独的 softmax 是带宽受限的，把它和前后的 elementwise 融在一起才能省掉一轮 HBM 往返。

三条路的共同点是：交付一个 kernel 的成本，主要不在写，而在验证与调优的循环里。这个循环的每一圈都要编译、跑正确性、测时延、看 profile，一圈的时延以分钟计，而一个候选的质量判断往往只靠一个脆弱的脚本。LLM 生成 kernel 之所以有吸引力，正是因为它把这个循环的“写”这一环压到了秒级；但循环并没有消失，它只是把瓶颈整体搬到了“判断候选好不好”这一步上。

二 · 旧方案的痛点结构：四个维度上的代价

把上面三条路的痛点拆成可比较的维度，可以看到它们并不是同一组权衡的不同取值，而是各自在不同的维度上触顶。

路线开发周期性能上限正确性保障可维护性主要时延/资源代价
手写 CUDA周级，随形状与架构变更重写最高，可达 SOL 附近依赖人工边界用例，回归靠人极低，与形状强绑定人力；寄存器压力与 occupancy 调参
Triton天级中高，受编译器策略限制语义较清晰，但 mask/边界易错中，参数化友好JIT 编译与 autotune 冷启动时延
库调用 / torch.compile小时级常规 shape 高，非常规 shape 退化高（库已充分测试）高无法融合带来的额外 HBM 带宽

手写 CUDA 的性能上限之所以最高，是因为作者可以精确控制数据在寄存器、共享内存、L2 与 HBM 之间的流动层级，把一次归约的通信量压到理论下界。但这份控制力的代价是正确性完全由人承担：一个 __syncthreads() 放错位置，在某个 warp 调度顺序下才暴露；一个边界 mask 少写一位，只在序列长度不是 block 整数倍时出错。这类 bug 的检测成本远高于修复成本，因为它们不产生编译错误，只在特定输入上产生数值偏差。

Triton 把正确性负担降下来了，但引入了另一种不确定性：编译器是否把你的意图翻译成了高效指令，是不可见的。同一个 tl.sum，在不同 block size 下可能走 warp shuffle 归约，也可能走共享内存归约，两者的时延差可以到数倍。工程师只能靠扫参和 profile 反推，而这个反推过程本身就是一个搜索问题。

库调用的痛点最容易被低估：它看起来“免费”，但融合缺失的代价是实打实的带宽。以解码阶段的 attention 为例，若 QK^T、softmax、PV 三步各自独立成 kernel，中间结果要三次写入并读回 HBM。设中间张量大小为 S 字节，则额外流量约为 3S 量级；在 HBM 带宽为 B 的器件上，这部分额外时延下界是 3S/B。当 S 不大时这部分可以忽略，但当 batch 与序列长度上来后，它就成为主要项。这就是 flash-attention 一类融合 kernel 存在的根本理由，也是“库调用够用”这一判断失效的地方。

$$T_{\text{extra}} \;\ge\; \frac{3S}{B_{\text{HBM}}},\qquad \text{SOL}_{\text{bw}} = \frac{\text{bytes moved}}{B_{\text{HBM}}}$$

把这三条路的痛点并置，结论是清楚的：没有一条路能同时把开发周期、性能上限、正确性和可维护性都压到工程可接受的水平。手写 CUDA 牺牲后两者，Triton 牺牲性能上限的一部分，库调用牺牲性能上限的另一部分。这正是 LLM 生成 kernel 的切入点——它试图用“生成 + 验证”的循环替代“手写 + 调优”的循环，把写的那一环变成近乎零成本，从而把工程注意力集中到验证上。

三 · 生成范式把瓶颈搬到了 validator 上

一旦接受“候选由 LLM 生成”这个前提，整个工程流程就变成了一条流水线：给定任务契约（输入分布、参考实现、允许与禁止的库、性能口径），生成若干候选，编译，跑正确性，测时延，按反馈保留或回退。这条流水线里，每一个决策点都由一个 validator 做出：它决定哪个候选被接受、哪个被拒绝，而接受/拒绝的结果直接决定 reward 分配、候选选择和最终对外声称的加速比。

于是问题的性质变了。旧方案里，“好不好”由工程师的判断兜底；新方案里，“好不好”被压缩成 validator 输出的一个布尔值。这个布尔值一旦出错，错误会沿着流水线放大：一个被错误接受的候选进入下一轮迭代，成为后续生成的“好样本”；一个被错误拒绝的候选则让搜索空间白白缩小。论文的出发点正是这句话——LLM 驱动的 kernel 生成的有效性，高度依赖于所用 validator 的质量，而现有 validator 存在多种缺陷。

论文点名的两类缺陷值得逐字拆开看。第一类是错误接受：候选违反了任务契约中“禁止使用某库”的约束，validator 却没有识别出来，于是判为通过。第二类是错误拒绝：候选合法地使用了契约允许的库，validator 却把它判成违规而拒绝。这两类错误的方向相反，但根源相同——validator 对“库使用”这一维度的判定，缺乏独立于候选自述的证据。

为什么这个维度特别容易出错？因为库使用往往不是写在源码里的显式调用，而是通过宏、模板实例化、或者运行时分派间接发生的；一个候选可以在源码层面看起来“手写”，实际却在某个分支里调了 cuBLAS。反过来，一个候选可能因为包含了某个头文件就被静态扫描判为违规，而它实际并未调用对应库。静态文本匹配在这两个方向上都会失准。

把 validator 的错误率写成可度量的量，就是论文采用的这对指标：

$$\text{FRR}=\frac{\#\{\text{correct}\to\text{reject}\}}{\#\{\text{correct}\}},\qquad \text{FAR}=\frac{\#\{\text{wrong}\to\text{accept}\}}{\#\{\text{wrong}\}}$$

FRR 衡量“好候选被误杀”的比例，FAR 衡量“坏候选被放过”的比例。这两个量在工程上的后果不对称：FAR 高会让加速比声称虚高、让错误实现进入生产；FRR 高则会让搜索效率骤降，因为大量合法候选被丢弃，生成循环在无效方向上反复消耗 token 与编译时间。论文的实验结论是，它评估的六个现有 validator 都存在不可忽略的 false-reject rate——也就是说，在旧方案下，搜索空间被系统性地浪费了。

这里有一个具体的代价链条可以算清楚：假设每轮生成 N 个候选，每个候选的编译加正确性检查加计时合计耗时 t，validator 的 FRR 为 r。那么每轮被误杀的合法候选数为 N·r，对应的无效计算量为 N·r·t；若生成循环需要 K 轮才能收敛，累计浪费就是 K·N·r·t。在 t 以分钟计、N 以十计、K 以十计的配置下，这个量级足以让整个流水线的吞吐减半。而 FAR 的代价不在算力，在可信度：一个被错误接受的候选一旦被写进对外报告，后续所有基于它的比较都失去意义。

四 · 为什么“换个更强的 validator”不是答案

面对上述缺陷，一个自然的反应是：把 validator 做得更强——更细的静态分析、更严的运行时插桩、更全面的测试用例。这条路在工程上会遇到三个结构性障碍。

第一是契约本身是多维的，单一检查无法覆盖。一个 kernel 生成任务的契约至少包含三层：语义正确性（在合法输入上输出是否与参考一致）、实现完整性（是否使用了被禁止的库、是否使用了被允许的库）、以及测量完整性（报告的运行时是否反映了完成计算所需的全部时间）。这三层各自需要不同的证据来源：语义正确性要靠与参考实现对照的压力测试；实现完整性要靠参考与候选的执行轨迹对比；测量完整性要靠计时检查，确认没有把部分计算排除在计时之外。任何单一维度的检查都会在其他维度上留下盲区。

第二是validator 与被验证对象之间存在共谋风险。如果 validator 的实现细节对生成模型可见，模型可以通过构造特定形式的代码来绕过检查——这不是理论担忧，而是 reward hacking 的标准形态。论文提出的“独立审计”正是针对这一点：审计者不参与生成，也不复用生成侧的判断逻辑，而是独立构造 oracle，按契约模型的三个维度给候选打 PASS/FAIL 标签，再用这批标签去度量 validator 的 FRR 与 FAR。换句话说，validator 的质量本身必须被独立地度量，而不能由 validator 自己声称。

第三是度量的成本必须可控。独立审计需要构造带标签的候选集，而标签的获取需要跑参考实现、跑压力测试、比对执行轨迹。论文的做法是在 716 个候选、来自七个语料（含构造的对照样本）上做这件事，并对六个 validator 逐一评估。这个规模说明审计本身是一项有成本的工程活动，而不是一次性的脚本检查；它的价值在于把“validator 好不好”从主观判断变成可复现的指标。

把这三层障碍合起来看，就能理解为什么旧方案的痛点“非改不可”：不是因为手写 CUDA 太慢、Triton 不够快、库调用不够灵活这些各自独立的问题，而是因为当生成范式把决策权交给 validator 之后，整个流水线的正确性和性能声称都建立在 validator 的可靠性上，而这个可靠性此前从未被独立度量过。一个 FRR 不可忽略的 validator，会让生成循环在合法候选上反复空转；一个 FAR 不可忽略的 validator，会让加速比成为无法验证的数字。这两件事中的任何一件，都足以让“LLM 生成 kernel”从工程上不可信。

五 · 一个具体场景里的代价核算

回到开场的推理服务。假设团队决定用 LLM 生成那个融合的 RMSNorm 加残差 kernel，契约规定：允许使用 tl.load/tl.store 等 Triton 原语，禁止调用 torch.nn.functional 里的现成算子（因为任务要求是手写融合），性能口径要求计时覆盖完整的读写与归约。生成侧给出十个候选，validator 逐个判定。

若 validator 的库使用判定依赖源码文本匹配，一个把 F.rms_norm 包在 try/except 分支里、正常路径走手写实现的候选，就可能被误判为违规而拒绝——这是 FRR 的一个实例。反过来，一个通过模板间接调用库函数、源码里看不到库名的候选，就可能被误判为合规而接受——这是 FAR 的一个实例。前者让团队丢掉了一个可能达标的实现，后者让一个实际未满足“手写融合”契约的实现进入候选池，并在后续轮次里被当作正样本继续演化。

再看测量完整性这一维。一个候选可能只对 kernel 主体计时，把预处理与后处理排除在外；在单算子基准上这看起来是合理的，但在端到端服务里，这部分时间是要付的。若 validator 不做计时检查，报告的加速比就会系统性偏高。论文对此的处理是明确的：计时检查要评估报告的运行时是否反映了完成候选计算所需的全部时间。这条检查的代价是每次评估都要做一次完整的端到端计时，而不是只测 kernel 内部——在候选数量大时，这部分时延会累积，但它换来的是加速比声称的可信度。

把这三类代价放在一张账上：FRR 造成的浪费是算力与 token（无效编译、无效生成轮次），FAR 造成的代价是可信度与生产风险（错误实现上线、报告失真），测量完整性缺失造成的代价是性能声称的系统性偏差。三者都不是靠“换个更强的生成模型”能解决的，因为它们出在判断环节，而不是生成环节。这就是本部分要落到的工程判断：在生成范式下，validator 不是一个附属的检查脚本，而是整条流水线的正确性锚点；对它的审计不是可选项，而是让加速比数字具备意义的前提。

论文给出的审计路径——按语义正确性、实现完整性、测量完整性三个维度独立构造 oracle，用参考校准的压力测试、执行轨迹对比与计时检查分别取证，再在带标签的候选集上度量 FRR 与 FAR——正是把这个锚点本身变成可检验对象的具体机制。它的代价是审计环节的额外工程投入与评估时延，换来的是对“哪个候选该被接受”这一判断的可复现性。在一个加速比声称动辄被写进对外材料的工程环境里，这笔交换是必要的。
