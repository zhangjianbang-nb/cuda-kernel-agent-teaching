一 · 从一次线上推理的算子替换说起

设想一个已经跑在 GPU 上的推理服务：模型结构固定，batch 与序列长度按业务流量波动，服务端每毫秒都在算一笔账。此时性能团队发现某个归一化加激活的融合算子占了端到端时延的可观比例，想换掉它。工程上可选的路只有三条：调用 cuBLAS/cuDNN 之类的库算子、手写 CUDA C++、或用 Triton 写块级 DSL。三条路各自对应一种成本结构，而 Geak 这篇工作要处理的，正是这三条路都绕不开的那段“从需求到可上线内核”的空白。

库调用的痛点是覆盖面。库算子经过高度调优，单点性能通常不是问题，但一旦算子的 shape、dtype 组合或融合模式落在库的覆盖范围之外，工程队就只能退回手写。手写 CUDA 的痛点是周期：一个中等复杂度的融合算子，从确定分块策略、处理边界、写 shared memory 流水，到调 bank conflict 与寄存器压力，再到跨架构回归，往往以人周计。Triton 把这段周期压缩到人天量级，块级抽象让工程师不必直接面对线程束与共享内存布局，但它并没有消除“写出来是否正确、是否够快”的验证负担。三条路共同的问题是：**性能上限由最熟悉硬件的那个人决定，而正确性由最熟悉算子语义的那个人决定，这两拨人往往不是同一拨。**

二 · 旧方案的真实成本：周期、上限、正确性、可维护性

把旧方案的成本拆开看，会发现它们不是四个独立问题，而是互相牵制的一个环。开发周期短意味着抽象层次高，抽象层次高意味着对硬件细节的控制弱，控制弱意味着性能上限受限；而为了逼近上限去手写底层，正确性与可维护性又同时恶化。这个环在 Triton 出现后并没有被打破，只是环的半径变小了。

具体到机制层面。手写 CUDA 时，工程师要显式决定 tile 尺寸、线程块映射、数据在 shared memory 中的排布与流水级数。一个典型的 GEMM 类内核，tile 从 128×128 改到 128×256，寄存器溢出与 occupancy 的平衡点就变了，需要重新测。这类决策没有解析解，只能靠 profile 迭代。Triton 把这层决策部分交给编译器：工程师写 `tl.load`、`tl.dot` 与块级循环，编译器负责 lowering 到 PTX 并做调度。代价是工程师失去了对指令级调度的直接控制，遇到编译器调度不理想的场景，只能靠改块形状或加约束去“引导”编译器，而这种引导本身又是一轮试错。

正确性成本同样被低估。GPU 内核的正确性不是“跑通一次”就算数，它要求在一组覆盖边界 shape、极端 dtype、非对齐指针与退化归约的输入上都与参考实现逐元素一致。手写内核里，越界读写往往不立刻报错，而是污染相邻内存后在别处表现为数值漂移；归约树在非 2 的幂长度上容易漏掉尾部元素。这些缺陷在单元测试里未必暴露，却会在长尾流量上以静默错误的形式出现。可维护性则是另一笔账：一个为特定 shape 手工调优的内核，换一代硬件或换一版编译器就可能退化，而当初写下它的工程师未必还在。

$$\mathrm{cost}_{\text{old}} = \underbrace{C_{\text{dev}}}_{\text{人周}}\cdot N_{\text{shape}} + \underbrace{C_{\text{verify}}}_{\text{边界覆盖}} + \underbrace{C_{\text{maint}}}_{\text{跨代回归}}$$

这个式子说明的是：旧方案的成本随 shape 数量线性增长，因为每个新 shape 都可能需要重新调 tile、重新验证。而推理服务的 shape 分布恰恰是长尾的，头部几个 shape 撑起大部分流量，尾部几十个 shape 各自只占极小比例却必须正确。工程队通常只为头部 shape 做手工调优，尾部 shape 退回库算子或通用实现，于是性能曲线在尾部塌陷。这不是懒惰，而是成本结构决定的理性选择。

三 · 为什么“再招一个人”不是答案

面对上述成本，最直接的旧思路是扩充人手。但这条路在工程上很快撞墙，原因有三。其一，能同时读懂算子语义、硬件微架构与编译器行为的工程师是稀缺资源，招聘周期与培养周期都远长于业务迭代周期。其二，人手增加带来的是并行度而非复用度：每个工程师调出来的 tile 策略与验证脚本都带个人印记，难以沉淀为组织资产。其三，也是最关键的，人工调优的搜索空间是低效的——工程师凭经验剪枝，跳过大量看似无望的配置，而这些被跳过的配置里恰恰可能藏着反直觉的更优解。

于是行业自然转向“让机器去搜”。这条线索在 Geak 之前已有大量工作，本套书其他部分会分别讨论 KernelBench 如何定义“写得对且写得快”的评测口径、CUDA-LLM 如何让模型直接产出 CUDA、以及若干多轮 RL 与多智能体框架如何组织搜索。这些工作共享一个前提：把内核生成视为一个**带执行反馈的搜索问题**，而不是一次性的文本生成。Geak 的位置正在于此——它不主张新的训练配方，而是主张把 Triton 内核生成组织成可复现的智能体流程，并配一套评测基准，让不同工作的结果能横向比较。这个主张看似温和，实则直指旧方案最深的痛点：**没有统一口径，就没有可信的进步度量。**

这里有一个具体的代价必须点明。若各家用各自的基线、各自的输入分布、各自的计时方法报加速比，那么“我的智能体比你的快 1.3 倍”这句话在工程上毫无意义——基线可能是一个未调优的朴素实现，计时可能没有预热、没有排除首次编译，输入可能只覆盖了 friendly shape。工程队拿这样的数字去做上线决策，风险等同于拍脑袋。统一口径的成本是真实的：固定 Triton 与 CUDA 版本、固定硬件平台、明确预热策略与计时边界、明确正确性容差。这些约束会压低绝对数字，却让数字变得可用。

四 · Triton 作为落点的两面性

Geak 选择 Triton 而非 CUDA C++ 作为生成目标，这个选择本身携带工程判断。Triton 的块级 DSL 把内核写成对 tile 的操作，语法面窄、语义清晰，对生成模型而言搜索空间显著小于 CUDA——模型不必在线程束映射、shared memory swizzle 这些低层细节上浪费 token，而可以把预算花在块形状、循环结构与边界处理上。代价是性能天花板：Triton 编译器对某些指令级优化不开放，遇到需要精细控制流水或使用特定 PTX 指令的场景，Triton 表达不出来，只能退回 CUDA 或 CuTe。这一点在本套书讨论 CuTe 与 PTX 的部分会展开，此处只需记住：**Triton 降低了生成门槛，同时给性能上限设了一道编译器决定的闸门。**

另一面是编译时间。Triton 的 JIT 编译在候选数量多时成为实打实的成本：每一轮候选都要走一遍 lowering 与 PTX 生成，编译失败的候选同样消耗时间。智能体闭环里，编译是必经关卡，编译报错文本回灌给下一轮是主要反馈信号之一。若一轮生成产出数十个候选，编译开销会与 GPU 运行开销同量级，甚至更高——尤其当候选大多语法或类型错误、根本到不了运行阶段时。这意味着闭环的吞吐受编译环节制约，重试轮数上限与候选筛选策略直接决定 token 成本与墙钟时间。材料未披露这些上限，因此工程代价无法从摘要估算，这一点在评估任何“多轮闭环”方案时都应作为必查项。

正确性 oracle 的严格程度也随 Triton 而变化。Triton 内核与参考实现的逐元素比对需要容差阈值，而阈值的选择直接影响通过率：过松则放过数值缺陷，过紧则把合法的浮点重排判为错误。归约类算子在非 2 的幂长度上，不同的累加顺序会产生可观测的浮点差异，这不是 bug 而是浮点非结合性的必然结果。因此 oracle 的设计必须区分“语义错误”与“合法数值偏差”，而这个区分在材料中未被说明。工程上，这意味着任何引用 Geak 通过率数字的结论，都必须先确认其容差口径。

五 · 旧方案在评测维度上的失明

旧方案还有一个不易察觉的缺陷：它无法回答“这个内核在别的 shape 上会怎样”。手工调优的产物是一个针对特定配置的快照，工程师知道它在自己测过的 shape 上快，但不知道它在相邻 shape 上的行为曲线。库算子则相反，覆盖面广但单点未必最优。两者都缺少一个统一的、可复现的评测面，让不同实现放在同一组输入分布下比较。

Geak 配套的基准试图补上这一面。其评分形式把正确性与加速比绑在一起：

$$\mathrm{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\mathrm{correct}_i]\cdot\frac{T_{\mathrm{base},i}}{T_{\mathrm{cand},i}}$$

这个式子的工程含义比表面更深。指示函数意味着一个错误候选的贡献是零而非负值——它不会拉低平均分，只会浪费一次机会。这在评测上是宽容的，但在工程上是危险的：一个在 90% 的 shape 上正确、在 10% 的边界 shape 上静默错误的内核，其分数可能接近满分，而它在生产环境里会以长尾错误的形式造成事故。因此基准的题目设计必须刻意覆盖边界 shape 与异常输入，否则分数会系统性高估可用性。材料未给出题目数量与输入分布覆盖范围，这正是评估该基准可信度的关键缺口。

加速比的分母是基线耗时，分子是候选耗时，两者必须同口径测量。预热策略、是否包含首次编译、是否同步、是否用 CUDA event 还是墙钟，每一项都会改变比值。旧方案里各团队自报的数字之所以不可比，正是因为这些细节从未被统一。Geak 的价值主张之一就是把它们固定下来，但固定的具体内容在摘要级材料中缺席。工程判断上，这意味着：**在全文核对基线名称与计时方法之前，任何加速比都应视为待验证。**

六 · 非改不可的那条线

把上述痛点收拢，会看到一条清晰的线：旧方案的问题不在于某个环节不够好，而在于环节之间没有闭环。工程师写完内核，验证靠人眼与零散脚本，性能靠手工 profile，反馈靠记忆与笔记。这条链路上每一次失败的信息都在传递中衰减，而衰减的代价由下一个 shape、下一代硬件、下一位接手的人承担。智能体闭环的意义不是取代工程师，而是把这条链路上的反馈变成机器可读、可回灌、可留存的信号——编译报错文本、逐元素比对的差异位置、计时得到的加速比，三者构成下一轮修改的输入。

具体机制上，一次闭环的形态是：给定算子语义、shape 与 dtype 分布，生成首版 Triton 候选；编译器拦截语法与类型错误并把报错回灌；通过编译后在 GPU 上运行，与参考实现逐元素比对，数值超差则定位越界或归约错误再改；通过正确性后按统一口径计时并与基线比较；最终把正确候选、耗时与轨迹一并留存。这条链上每一步都有明确的失败模式：编译错误对应语法类型问题，数值不符对应越界与归约问题，性能不达标对应块形状与调度问题。失败模式可分类，意味着反馈可结构化，这正是旧方案做不到的。

代价同样明确。多轮重试意味着 token 成本随轮数线性增长，而材料未给出轮数上限；候选筛选意味着并非所有候选都值得跑完整个闭环，筛选策略未披露则无法估算算力开销；轨迹留存意味着存储与复现成本，但这也是唯一能让失败模式统计与回归复现成为可能的手段。工程上真正需要盯住的判断是：闭环的吞吐是否被编译环节卡住、正确性 oracle 的容差是否足以区分语义错误与浮点重排、以及基准是否具备防作弊机制——缺少最后一项时，针对基准过拟合或缓存结果的策略会系统性抬高分数，而这类分数一旦进入上线决策，代价由生产环境承担。
