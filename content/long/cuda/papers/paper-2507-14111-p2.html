一 · 论文的评测口径：从摘要能核到哪一层

CUDA-L1 的公开材料停在摘要级，因此本部分要做的不是复述它的结论，而是把“一个加速比数字要成立，必须同时钉死哪些变量”逐条拆开。给定事实里明确写出的口径只有三条：任务是 CUDA 算子级、每题附参考实现与输入分布、性能以“相对基线实现的加速比”表示。其余全部缺失——基准题目数量、算子覆盖、基线是谁、硬件型号、dtype、计时是否取中位数、是否含 H2D/D2H 拷贝、正确性容差。这意味着任何引用其加速比的行为都必须先声明“口径未定义”，否则就是把一个不可比的数当成可比结论。

把这件事形式化：一个被报告的加速比 $S$ 实际上是七元组的函数

$$S = f(\text{bench},\ \text{baseline},\ \text{HW},\ \text{dtype},\ \text{timer},\ \text{tolerance},\ \text{shape})$$

七个自变量里任意一个变动，$S$ 就换了一个含义。CUDA-L1 的材料只固定了“baseline 存在”这一点，其余六个自由度全部开放。工程判断因此很直接：它的加速比只能作为“同口径内部的相对排序信号”使用，不能跨论文、跨硬件、跨 dtype 横向比较。这不是苛责，而是 kernel 评测的常态——同一段 kernel 在含拷贝与不含拷贝两种计时下，加速比可以差出一个量级，因为小算子的端到端时间被传输主导。

一个具体例子：假设某算子的基线实现是朴素的三重循环 GEMM，候选是分块共享内存版本。若计时只包 kernel launch 到结束，分块版的收益被完整计入；若计时把输入张量的拷贝也算进去，而输入规模又小到拷贝占主导，那么再好的 kernel 也会被稀释成接近 1 的加速比。CUDA-L1 未说明属于哪一种，所以它的 $S$ 在“端到端收益”这个生产口径下不可直接采信。代价是明确的：口径不明导致复现实验必须自带全套测量脚手架，单题复现的工程投入远超读一篇摘要的收益。

二 · 基线与硬件的不可比性：谁在当分母

“相对基线实现的加速比”这句话里，分母的身份决定了这个指标的全部意义。kernel 优化领域至少有四类基线：朴素参考实现（naive）、框架内置实现（如 PyTorch eager）、厂商库（cuBLAS/cuDNN）、以及同题的历史最优候选。四者难度差一个数量级以上。以朴素实现为分母，一个中等质量的分块 kernel 就能拿到数倍加速；以 cuBLAS 为分母，能拿到 1.2 倍已属不易——CUDA-L2 那条线正是以“超越 cuBLAS”为卖点，说明这个分母才是硬骨头。CUDA-L1 未给出基线配置，于是它的加速比无法判断落在哪一档。

硬件同理。同一 kernel 在消费级卡与数据中心卡上的相对加速比不同，因为分母实现（尤其是厂商库）在不同架构上的优化成熟度不同：库在主力架构上被高度调优，在边缘架构上留有余量，于是“相对库的加速比”会随架构漂移。dtype 亦然：fp32 与 bf16/tf32 下的算术强度、寄存器压力、tensor core 可用性完全不同，一个在 fp32 下有效的分块策略在 bf16 下可能因 MMA 指令形状不匹配而失效。给定材料对硬件与 dtype 均无说明，因此 CUDA-L1 的加速比连“同架构内可比”都无法保证。

工程上可执行的替代做法是：复现时把分母显式化为三个并列基线（naive / framework / vendor library），分别报告 $S_{\text{naive}}$、$S_{\text{fw}}$、$S_{\text{lib}}$，并注明硬件型号与 dtype。这样即使原论文口径缺失，读者也能把结论映射到自己的分母上。代价是评测成本三倍化——每个候选要在三种基线下计时，且厂商库基线需要额外的 API 调用与 warmup 管理。对于以多候选采样为核心的对比 RL 流程，这个成本会直接乘到候选数上。

口径维度CUDA-L1 给定材料不可比风险复现时的最小补救
基线未给出naive 与 cuBLAS 分母差一个量级以上并列报告三种分母
硬件未给出库优化成熟度随架构漂移注明型号与 SM 架构
dtype未给出fp32/bf16 的最优策略不同固定 dtype 并声明
计时未给出含/不含拷贝差一个量级声明是否含传输、是否取中位数
容差未给出浮点边界误判正负例给出 atol/rtol 与判定规则

三 · 指标族：faster rate、geomean、fast_p 与 roofline 各自回答什么

kernel 基准的指标不是可互换的。faster rate 是“候选快于基线的题目占比”，它回答覆盖率，但对幅度不敏感：一个快 1.01 倍和一个快 10 倍在 faster rate 里权重相同。geomean 加速比是各题加速比取几何平均，回答整体水平，且对个别极端值不敏感——这正是它被广泛采用的原因，因为算术平均会被单题百倍加速拉爆。fast_p 是“加速比超过阈值 p 的题目占比”，回答“有多少题真正跨过了有工程意义的门槛”，例如 fast_2 表示至少快一倍。三者回答三个不同问题，任何单一指标都会被针对性优化。

roofline 是另一层：它不问“比基线快多少”，而问“离硬件上限还有多远”。以算术强度 $I$（FLOP/Byte）为横轴，性能上界为

$$\text{Attainable} = \min(\text{Peak}_{\text{compute}},\ I \times \text{BW}_{\text{mem}})$$

把候选的实测吞吐除以该上界，得到 SOL（speed-of-light）占比。这个口径的价值在于它把“分母是谁”这个模糊问题替换成“硬件物理上限”，跨实现可比性最强；代价是需要精确统计每个 kernel 的实际访存量与 FLOP 数，而这在融合算子或含规约的 kernel 上极难准确计数，通常要靠 NCU 的计数器而非源码推导。CUDA-L1 的材料未提及 roofline，因此其加速比无法换算成 SOL，也就无法判断“快”是靠近上限还是仅仅赢了弱基线。

指标选择的性能代价是测量开销本身：geomean 要求每题多次计时取中位数，fast_p 要求阈值判定前先保证计时稳定，roofline 要求 NCU 级别的计数器采集（会引入 replay 开销，单 kernel 采集时间可达毫秒到秒级）。在对比 RL 的训练闭环里，如果每轮对每个候选都跑 NCU，采样成本会压垮训练吞吐；因此工程上常见的折中是训练期只用 wall-clock 加速比做奖励，评测期才对入选候选补 roofline 分析。CUDA-L1 未说明它属于哪种，这直接决定了它的奖励信号是否带有测量噪声。

一个具体例子：某题候选 A 比基线快 1.05 倍但 SOL 仅 12%，候选 B 快 0.98 倍但 SOL 达 65%。在 faster rate 口径下 A 是正例、B 是负例；在 roofline 视角下 B 才是真正接近硬件的实现，A 只是赢了弱基线。对比奖励若只按加速比排序，就会系统性地奖励“挑软柿子”而非“逼近上限”，这是奖励作弊的一种温和形式，且不会被正确性 oracle 拦住。

四 · 隐藏 shape 与输入分布：泛化口径的缺口

给定材料说“每题附参考实现与输入分布”，但没有说评测时 shape 是固定的还是隐藏的。这两者对应完全不同的能力主张。固定 shape 下，模型可以针对该 shape 做常量折叠、硬编码 tile 尺寸、甚至把边界条件在编译期消掉，得到的 kernel 在该 shape 上极快但在其他 shape 上崩溃或退化。隐藏 shape 下，候选必须在运行时读取维度并走通用路径，性能上限更低但泛化性真实。CUDA-L1 未声明属于哪一种，因此其加速比无法区分“学会了优化”与“学会了拟合评测 shape”。

输入分布同理。数值比对 oracle 的判定依赖输入取值：全零输入、单位阵、随机均匀、以及含 NaN/Inf 的边界输入，会触发不同的数值路径。若评测只用随机均匀分布，一个在极端值上溢出但常规输入正确的 kernel 会被判为正例。给定材料明确说容差标准未给出，这意味着连“多大误差算通过”都未定义，浮点边界上的判定风险无法量化。

可核查的测量口径应当写成如下伪代码思路：对每题维护一个 shape 集合 $\mathcal{S}$ 与分布集合 $\mathcal{D}$，候选必须在所有 $(\text{shape}, \text{dist})$ 组合上通过正确性，性能取各组合加速比的 geomean，并单独报告最差组合的加速比。

$$S_{\text{robust}} = \left(\prod_{s \in \mathcal{S}} \prod_{d \in \mathcal{D}} S_{s,d}\right)^{1/(|\mathcal{S}||\mathcal{D}|)},\quad S_{\text{worst}} = \min_{s,d} S_{s,d}$$

代价是评测组合数相乘：若 5 个 shape × 3 个分布 = 15 次运行，每次含编译与计时，单题成本上升一个量级。对于以多候选采样为训练信号的流程，这意味着训练期的评测必须抽样而非全组合，否则候选数 × 组合数的乘积会不可承受。CUDA-L1 未给出 shape 与分布的处理方式，因此其加速比在“生产端到端收益”这个主张上缺少泛化证据——一个只在评测 shape 上快的 kernel 部署到真实负载上可能直接退化。

五 · 正确性 oracle 的口径：容差、判定顺序与作弊空间

给定材料明确：正确性判定先于性能比较，未通过者直接进入负例池。这个顺序设计本身是对奖励作弊的结构性防御——它堵死了“用错误输出换加速比”这条最廉价的作弊路径，例如跳过部分计算、用低精度近似替代、或直接返回缓存结果。但防御的强度取决于 oracle 的严格度，而容差标准未给出，于是防御在浮点边界上是漏的。

逐元素比对的判定可写成：对参考输出 $y$ 与候选输出 $\hat{y}$，通过条件为

$$|\hat{y}_j - y_j| \le \text{atol} + \text{rtol} \cdot |y_j|,\quad \forall j$$

atol 与 rtol 的取值直接决定正负例边界。rtol 过松，一个用 fp16 累加替代 fp32 累加的 kernel 会被判通过，而它在长规约上误差随规模增长；rtol 过紧，合法的重排累加（改变求和顺序）会因浮点非结合性被判失败，从而把正确优化错杀成负例。两种错误都会污染对比奖励：前者放进假正例，后者放进假负例，而成对偏好损失对两者都敏感。

更根本的缺口是缺少形式化或合约级验证。数值比对只能覆盖被采样的输入点，无法证明对所有输入正确。一个在评测输入上通过、但在某个未采样边界上越界写显存的 kernel，会被判为正例并进入训练信号，而它的错误在部署时才暴露。工程上的补救是加一层合约检查：在候选运行前后校验输出张量的形状、stride、以及（在可用时）用 compute-sanitizer 跑一遍内存越界检测。代价是每次候选运行多一遍 sanitizer 开销，单次可达数十倍于正常执行时间，因此只能对入选候选抽样执行，不能进训练内环。

一个具体例子：某归约 kernel 用树形归约替代顺序累加，在 1024 元素上误差在 rtol=1e-5 内通过，但在 1e6 元素上误差累积超出容差。若评测 shape 只覆盖小规模，这个候选会被判正例并强化；若容差按元素数缩放（如 rtol 随 $\log n$ 放宽），则判定更贴近数值实际。CUDA-L1 未给出容差规则，因此无法判断它的正例池里是否混入了这类规模敏感的候选。

六 · 可核查口径清单：把不可比变成可复现

综合以上，CUDA-L1 的评测口径缺失集中在六处：基准规模与算子覆盖、基线身份、硬件与 dtype、计时方法、正确性容差、shape 与分布处理。这六处不是细节，而是决定加速比含义的自由度。工程上可执行的核查清单应当逐条落到可观测的量上，而不是停留在“论文没说”。

  • 基准：题目数、算子类别（elementwise / reduction / matmul / attention 等）、每题是否附多组 shape；缺此项则 faster rate 的分母未知。
  • 基线：明确是 naive、framework 还是 vendor library，并给出该基线的实现来源与版本；缺此项则加速比不可跨论文比较。
  • 硬件与 dtype：GPU 型号、SM 架构、fp32/bf16/tf32 的选择；缺此项则无法判断库基线在该架构上的成熟度。
  • 计时：是否含 H2D/D2H、是否 CUDA graph 捕获、warmup 次数、取中位数还是最小值、是否剔除首次 launch 的上下文开销；缺此项则小算子加速比可差一个量级。
  • 正确性：atol/rtol 数值、是否随规模缩放、是否跑 sanitizer、是否覆盖边界输入；缺此项则正负例边界不可复现。
  • shape 与分布：固定还是隐藏、评测集与训练集是否重叠；缺此项则无法区分优化能力与 shape 拟合。

把这些条目写成机器可读的评测配置，是对比 RL 流程能被第三方复现的前提。具体机制上，评测器应当在每次运行输出一个结构化记录：题目 ID、shape、dtype、基线名、候选耗时中位数、基线耗时中位数、容差判定结果、是否含拷贝。对比奖励模块只读这些字段，而不读原始 wall-clock，这样奖励信号与口径绑定，口径一变奖励含义即变，避免“训练时用一套口径、报告时用另一套”的隐性漂移。

代价落在采样预算上：结构化记录要求每题至少跑基线一次并缓存，候选每次计时需 warmup 与多次重复，单候选的测量时间从一次 launch 膨胀到数十次 launch 加同步。若每轮采样 $k$ 个候选、共 $n$ 题，测量开销约为 $O(kn)$ 次计时序列，且编译开销与 $k$ 线性相关——这正是给定材料指出的主要工程代价。工程判断因此是：训练内环用最简口径（单 shape、单分布、wall-clock 中位数、固定容差）保吞吐，评测外环用完整清单（多 shape、多分布、roofline、sanitizer 抽样）保可信度，两者之间用同一份结构化记录格式衔接，使内环的正例在外环可被重新判定而不必重跑全部候选。
