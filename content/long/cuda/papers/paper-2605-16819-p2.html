一 · 负载层：算子—形状对如何被切成 in/out 两组

AgentKernelArena 的负载层不是一张算子清单，而是一个二维采样空间：算子（op）与形状（shape）的笛卡尔积被划成 Din 与 Dout 两个不相交子集。分布内集合承载"公开用例"，分布外集合承载"未见形状、未见算子组合"。这个切分方式决定了后续所有指标的含义：加速比在两组上分别统计，差值即泛化差距。材料没有给出算子集合规模、形状采样规则与 out 集合的构造方式，因此这里只能给出可核查的口径骨架，不能给出具体用例数。

关键机制是"同一算子、不同形状"与"同一形状、不同算子"两种迁移必须被分开考察。若 Dout 只换形状不换算子，测的是形状泛化；若只换算子不换形状，测的是算子泛化；两者混在一个集合里求平均，会把两种失败模式糊成一个数。工程上应把 out 集合再分成 out-shape 与 out-op 两个子桶，分别报告加速比，否则泛化差距无法归因。伪代码层面，采样器应保证每个算子至少在 in 与 out 中各出现一次，避免某算子只在 out 出现导致基线缺失：

$$\mathcal{D}_{\mathrm{out}}=\mathcal{D}_{\mathrm{out}}^{\mathrm{shape}}\cup\mathcal{D}_{\mathrm{out}}^{\mathrm{op}},\quad \mathcal{D}_{\mathrm{out}}^{\mathrm{shape}}\cap\mathcal{D}_{\mathrm{out}}^{\mathrm{op}}=\varnothing$$

代价在于：out 集合越大，评测的编译—运行总时延线性增长，且每个 out 用例都要配参考实现作为 oracle，显存与主机内存开销随用例数上升。一个具体例子：某 reduction 算子在 in 集合用 4096×1024 的规整形状，在 out-shape 集合用 1023×777 这种非 2 的幂、非对齐形状，智能体若把 block size 与向量化宽度硬编码为 2 的幂，编译能过、正确性也能过，但计时会暴露访存合并退化——这正是 out-shape 桶要抓的失败模式。

二 · 基线口径：分母是谁，决定了加速比能不能横向比

论文的加速比定义为 tbase/tagent，分母是"参考实现或朴素实现"。材料未给出基线名称与实现细节，这是本基准最大的不可比来源。工程上必须区分三类分母：框架自带 kernel（如 PyTorch eager 调用）、朴素手写实现（naive CUDA/Triton）、以及厂商库（cuBLAS/cuDNN）。三者数值差异可达数倍，同一智能体换分母就能从"加速 1.2×"变成"减速 0.6×"。

可核查的口径要求基线在评测协议中锁定版本与编译 flag，并在轨迹记录中写入基线标识字段。基线计时的采样方式必须与 agent kernel 完全一致：同一硬件、同一 dtype、同一 warmup 次数、同一中位数口径。否则分子分母的噪声不同源，加速比分布会偏。一个具体例子：某 matmul 用例若基线取 cuBLAS 的 TF32 路径，而 agent kernel 用 FP32 累加，两者精度档不同，加速比虽高但正确性 oracle 的容差必须按 dtype 分别设定，不能共用一套阈值。

代价体现在正确性校验侧：基线越强，oracle 的数值容差越难放宽，agent kernel 因累加顺序不同产生的舍入误差会被误判为失败，从而把本可计入计时的样本踢出统计。这直接改变通过率与加速比均值。

三 · 硬件与 dtype：固定硬件是可比性的前提，也是泛化的边界

材料明确"评测需在固定硬件上取多次运行中位数以控制噪声"，但未给出 GPU 型号与数量。这意味着任何跨论文的加速比对比都不可直接引用——同一 kernel 在 H100 与 A100 上的 roofline 拐点不同，分块策略的最优点也不同。硬件固定带来两个后果：其一，排行榜分数只在同一硬件代际内可比；其二，智能体学到的优化模板（如 shared memory 容量假设、SM 数量假设）会绑定到该硬件，迁移到不同配置时泛化差距会被放大，而这一维度恰恰是论文声称要考察的"不同硬件配置上的迁移表现"，材料却未给出跨硬件评测的具体配置。

dtype 口径同样未在材料中锁定。FP32/FP16/BF16/TF32 的选择直接改变算术强度与 roofline 位置：同一算子从 FP32 换到 BF16，计算峰值翻倍而带宽不变，kernel 从 compute-bound 滑向 memory-bound，智能体的优化方向应随之改变。可核查的协议应把 dtype 写入每个用例的 schema，并与正确性容差绑定：

$$\mathrm{atol},\mathrm{rtol}=f(\mathrm{dtype}),\quad \text{且}\ \mathrm{roofline}\ \text{按 dtype 的峰值重算}$$

代价是评测矩阵膨胀：算子 × 形状 × dtype × 硬件四维组合，每个组合都要独立编译与计时，编译时间与显存占用成倍上升。一个具体例子：LayerNorm 在 FP32 下是带宽受限，智能体优化向量化加载即可；换到 BF16 后若仍按 FP32 的向量宽度分块，寄存器压力与指令数变化会让计时结果偏离 roofline 预测，泛化差距里就混入了 dtype 不匹配的噪声。

四 · 指标族：faster rate、speedup、geomean、fast_p 与 roofline 的分工

材料只确认了"分布内与分布外分别统计加速比并计算差值"与"计时取中位数"，未给出 faster rate、geomean、fast_p 的具体定义与阈值。这里给出工程上可核查的分工，不引入材料外的数字。faster rate 是计数型指标：加速比大于 1 的用例占比，它对长尾失败不敏感，适合看"能不能赢基线"；geomean 是乘性平均，抑制单个超大加速比拉高均值，适合看整体水平；fast_p 是阈值型指标：加速比超过 p 的用例占比，p 的取值必须在协议中固定，否则跨论文不可比。

三者的统计代价不同：faster rate 只需通过率与加速比符号，计算成本最低；geomean 要求每个用例都有有效计时，编译失败与正确性失败必须被显式剔除而非记为零，否则 geomean 会被零值拖垮；fast_p 对阈值敏感，阈值漂移会直接改变排名。roofline 则提供上界参照：把 agent kernel 的实测时间与按峰值算力/带宽推算的理论下界比较，得到 SOL（speed of light）占比，用来判断加速比是"接近硬件极限"还是"基线本身太弱"。

$$\mathrm{geomean}=\exp\!\Big(\frac{1}{N}\sum_{i=1}^{N}\ln \frac{t^{\mathrm{base}}_i}{t^{\mathrm{agent}}_i}\Big),\quad \mathrm{SOL}_i=\frac{t^{\mathrm{ideal}}_i}{t^{\mathrm{agent}}_i}$$

一个具体例子：某智能体在 10 个用例中 6 个加速 1.05×、4 个减速 0.5×，faster rate 为 0.6 看似及格，但 geomean 会被 0.5× 的用例压到 1 以下，两个指标给出相反结论——这正是必须同时报告计数型与乘性指标的原因。代价是报告复杂度上升，读者需要理解指标间的张力，而不是只看一个排行榜数字。

五 · 哪些数字不可比：失败样本、噪声与隐藏 shape

材料明确"编译失败与正确性失败单独计入、不进入计时阶段"。这条规则保护了加速比均值不被失败样本污染，但也制造了不可比：若智能体 A 在 100 个用例中 40 个编译失败、60 个平均加速 1.5×，智能体 B 全部通过、平均加速 1.2×，只报加速比会得出 A 更优的错误结论。可核查的口径必须同时报告通过率与加速比，并把失败类型分桶（编译失败、超时、正确性失败、计时异常）。

噪声是第二类不可比来源。中位数计时能抵抗离群值，但材料未给出运行次数与 warmup 策略。GPU 时钟漂移、L2 缓存残留、同一 MIG 切片上的邻居干扰都会让同一 kernel 的计时在多次运行间波动。协议应固定 warmup 次数、重复次数与是否锁频，并在轨迹中记录每次运行的原始计时而非只记中位数，便于事后审计方差。

隐藏 shape 的处理是第三类。论文声称考察"未见形状"，但材料未说明 out 形状的构造方式。若 out 形状只是 in 形状的等比缩放，智能体的模板仍能命中；若 out 形状在维度数、对齐性、动态性（如变长序列）上与 in 有结构性差异，才是真正的分布外。防作弊的关键是保留一个不公开的隐藏测试集，智能体在评测时不可见，只在最终计分时使用——否则泛化差距本身会成为新的过拟合目标，智能体反向优化 out 集合。代价是隐藏集使评测不可完全复现，只能在协议中承诺隐藏集的构造规则与抽样种子，让第三方能重建同分布的不同实例。

一个具体例子：softmax 算子在 in 集合用固定 seq_len=512，out 集合若只是把 seq_len 改成 1024，智能体按 512 调好的 block 配置仍近似最优；若 out 集合引入 batch 内变长序列与 mask，智能体必须处理动态边界，这才是形状泛化的真实考验。材料未给出这类构造细节，因此引用其泛化差距数值时必须标注"out 集合构造未知"这一前提。

泛化差距指标的三重失效边界与测量代价

泛化差距公式本身是两组平均加速比之差，但它的统计性质远比差值看起来脆弱。设分布内用例数为 n_in、分布外为 n_out，若 n_out 很小，则 \mathcal{D}_{out} 上单条用例的计时抖动会以 1/n_out 的权重直接进入 Gap，而中位数计时只压制单次运行的噪声，压不住用例抽样方差。更关键的是失败样本被排除在计时之外：若某智能体在分布外形状上编译失败率高，它的 Gap 只由少数成功用例构成，分母被悄悄缩小，Gap 反而可能显得更小。因此报告 Gap 时必须同时给出两组通过率与有效样本数，否则该指标在失败率非零时不可解释。工程代价上，分布外集合每扩一条用例就多一轮编译—正确性—计时流水线，编译时间与正确性 oracle 的运行时间随 n_out 线性增长，这是复现成本的主要来源。

第二个失效条件是分布外集合一旦公开即成为新的过拟合目标。Gap 作为排行榜指标被优化时，智能体会把分布外形状的维度、边界条件记进模板，Gap 收窄并不代表迁移能力提升。可核查的口径是把分布外集合再切成公开验证集与隐藏测试集，只公开前者用于迭代反馈，后者仅在最终计分时运行一次；代价是隐藏集无法回灌反馈，智能体在隐藏集上的表现只能事后观测，评测方需承担一次不可复现的最终运行成本。第三个边界是硬件绑定：Gap 的分子分母都依赖同一基线的计时，换 GPU 型号或驱动版本后基线绝对时间改变，两组加速比的差不再可比，跨硬件只能比较同一硬件内的 Gap 排序，不能比较 Gap 数值本身。

测量口径上还需固定三件事才能让数字可核查：计时运行次数与聚合方式（材料只说明取中位数，未给次数）、编译预算轮数与是否计入超时、以及 profile 信号是否开启。开启 NCU/SASS 回灌会显著拉长每轮迭代的墙钟时间并引入采集开销，同一智能体在开与关 profile 下的加速比不可混入同一张表。下表给出可直接写进评测协议的字段与不可比情形：

口径字段必须锁定不可比情形
硬件与驱动GPU 型号、驱动、编译 flag跨型号比较 Gap 数值
计时运行次数、中位数、是否含预热次数不同则加速比抖动不可分离
失败计入编译/正确性失败单列并报通过率仅报成功用例加速比

具体例子：某智能体在分布内固定形状上把分块调到最优，加速比高；换到维度更大、边界非对齐的分布外形状时，其硬编码的分块假设导致越界，正确性 oracle 判失败，该用例不进入计时，Gap 由剩余成功用例算出，看起来迁移良好。若评测协议同时报告分布外通过率，这一假象立刻暴露——这正是把通过率与 Gap 并列作为准入双阈值的工程理由，也是该基准在缺少负载规模与预算数字时最需要补齐的口径。
