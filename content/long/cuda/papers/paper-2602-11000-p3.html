一 · 单轮提示：一次前向的输入、输出与三项代价

把整条流水线拆到最细的粒度，第一段是单轮提示（single-attempt）。输入是三元组：算子语义描述（reference 实现的签名与语义）、形状/ dtype 约束、以及一个模板化的 Triton 骨架提示。输出是一段可编译的 Triton 源码，长度通常在数百 token 量级。论文报告的单轮口径正是这一段：微调后的 GPT-5 把 kernel 正确率从 43.7% 提到 77.0%（+33.3 个百分点），把「优于 TorchInductor」的比例从 14.8% 提到 21.8%（+7 个百分点）。这两个数字必须分开读——正确率是编译+运行+数值比对的门，加速比门是第二个门，二者不是同一次判定。

单轮提示的代价结构是三项叠加：prompt token（含参考实现与约束）、completion token（源码）、以及最容易被忽略的编译时间。Triton 的 JIT 首次编译一个 kernel 需要走 MLIR 到 PTX 再到 cubin 的完整链路，单 kernel 首次编译在秒量级，这意味着在 RL 采样阶段，编译开销可能超过生成开销。工程判断：批采样时必须做编译缓存（按源码哈希去重），否则同一份候选被反复编译会直接吃掉 rollout 吞吐。一个具体例子：同一算子族下模型常生成结构相同的 kernel，仅常量不同，缓存命中率可观，这是把单轮采样成本压下来的第一个杠杆。

单轮提示的失败模式是「看起来对」：语法合法、能编译、但在边界 shape 上越界或漏掉 mask。论文把 SFT 排除在外的理由正是这一点——高质量标注数据稀缺，且编译器偏好（compiler biases）会让模型学到「能过编译但不对」的分布。因此单轮提示只作为流水线的入口，不作为可信度的来源。

二 · Agent 脚手架：把一次生成变成一条可回灌的回路

脚手架层把单轮提示包成一个循环：生成 → 编译 → 运行 → 评测 → 反馈改写。输入是问题描述加历史轨迹（上一轮的源码、编译错误、运行时报错、profile 摘要），输出是下一轮候选。论文给出的整机结果落在这里：接入完整 coding agent 后，在扩展的 KernelBench 套件上解出 97.4% 的问题，并在 72.9% 的问题上超过 TorchInductor，几何平均加速比为 2.12。注意这三个数字的口径不同——97.4% 是「解出」（通过正确性门），72.9% 是「胜过基线」，2.12 是只在胜出的子集上取的几何平均。把它们混成一个「平均加速 2.12 倍、正确率 97.4%」的说法是口径错误。

脚手架的核心机制是反馈的类型化。编译错误是确定性的、可定位到行；运行时报错（越界、非法内存访问）需要 CUDA 的异步错误捕获，必须在每次 launch 后同步并检查；数值不匹配需要定位到具体元素索引；性能不达标需要 profile 归因（是带宽受限还是占用率不足）。四类反馈进入下一轮 prompt 的方式不同：编译错误整段回灌，数值错误只回灌失配摘要（避免 prompt 膨胀），profile 只回灌 top 归因。这里有一个明确的代价：每轮回灌的 token 数随轨迹长度线性增长，若不截断，十轮之后 prompt 本身就会挤占生成预算。

$$\text{cost}_{\text{rollout}}=\sum_{i=1}^{N}\big(T^{\text{in}}_{i}+T^{\text{out}}_{i}\big)\cdot c_{\text{token}}+\sum_{i=1}^{N}t^{\text{compile}}_{i}+t^{\text{run}}_{i}$$

这个式子说明为什么「多轮」不是免费的：轮数 N 增大时，token 成本线性涨，而编译与运行成本取决于候选是否命中缓存、输入规模是否可控。工程上要把 N 卡在「反馈还能带来新增信息」的边界上，超过这个边界，多轮只是在重复同一种失败。

三 · RL 环节：奖励如何从一次评测流回策略

RL 段把上述回路变成训练信号。论文的奖励形式是稀疏的、门控的：

$$R=\sum_{t=0}^{T}\gamma^{t}r_{t},\qquad r_t=\Delta\text{speed}_t\cdot\mathbb{1}[\text{pass}_t]$$

逐项读：$\mathbb{1}[\text{pass}_t]$ 是正确性门，未通过则该步奖励为零——这直接切断了「快但错」的候选获得正梯度的路径；$\Delta\text{speed}_t$ 是相对统一基线的加速增量，只在通过正确性门后计入；$\gamma$ 是折扣因子，把多轮改写中的早期贡献衰减。这个设计的代价是奖励稀疏：绝大多数采样在第一步就拿到零奖励，梯度方差大，需要较大的 batch 才能稳定。另一个代价是 $\Delta\text{speed}$ 的测量噪声——时延测量本身有抖动，若不做多次重复取中位数，噪声会直接进入奖励。

论文明确说 RL 相比 SFT 是「数据高效且自适应」的替代，但前提是「能访问相关工具、谨慎选择训练问题、有稳健的评测环境」。这三条对应三个工程约束：工具即编译器与 profiler 必须在回路里；训练问题要覆盖足够多的算子族，否则策略会过拟合到少数形状；评测环境要隔离——同一张卡上并行跑多个候选会互相干扰时延测量，必须串行化或做资源分区。一个具体例子：若把两个候选同时 launch 在同一 SM 上，二者的时延都被污染，$\Delta\text{speed}$ 变成噪声，奖励信号失效。这是「稳健评测环境」在工程上的真实含义。

四 · Verifier：正确性 oracle 的分层与它的漏网方式

verifier 不是单一函数，而是分层门。第一层是编译门：源码能否被 Triton 前端接受并生成 cubin。第二层是运行门：在给定输入上不触发非法访存、不超时。第三层是数值门：与参考实现逐元素比对，需按 dtype 设定容差（fp32 与 fp16 的容差不同，归约类算子的累加顺序会引入差异）。第四层是性能门：时延相对基线有增益。四层串联，任一层失败即回退。

verifier 的代价在覆盖度与成本之间。逐元素比对需要把输出搬回主机或做设备端归约，前者引入 D2H 带宽开销，后者需要额外的归约 kernel；对于大 shape，D2H 拷贝可能比被测 kernel 本身还慢。工程做法是设备端先做差分归约，只把 max abs diff 与失配计数搬回，把带宽代价压到常数级。但这一做法有漏网方式：若参考实现本身在某个 shape 上走了不同的算法路径（例如 TorchInductor 的融合决策随 shape 变化），逐元素比对会把「算法差异」误判为「数值错误」，产生假阴性。

更深的漏网来自 shape 特化。候选 kernel 可以针对评测输入硬编码 tile 大小与边界，在给定 shape 上通过全部门，但在隐藏输入分布上崩塌。论文的结论明确限定在「论文给定的硬件、基线与输入分布」上，跨硬件、跨 dtype、跨框架的迁移未验证。因此 verifier 必须包含至少一组未参与生成的 shape 做留出检查，否则正确率数字只反映记忆而非泛化。

五 · 一次完整流动的端到端账本

把四段串起来，一次 kernel 生成—编译—运行—评测的流动可以记成一张账：

步骤输入输出主要代价
单轮提示语义描述、shape/dtype 约束、骨架Triton 源码prompt+completion token
编译源码cubin 或编译错误首次编译秒级，缓存可摊薄
运行cubin、输入张量输出张量或运行时错误显存占用、launch 同步
正确性门输出、参考输出pass/fail、失配摘要D2H 带宽或设备端归约
性能门时延采样、基线$\Delta$speed重复测量、串行化
反馈改写四类反馈下一轮 prompt轨迹 token 线性增长

账本里最贵的一行往往不是生成而是评测：正确性门的 D2H 与性能门的重复测量都是常数级但不可省略的开销。在 RL 采样规模上，这两项决定了每小时能产出多少条有效奖励信号。工程判断：把正确性门做成设备端归约、把性能门做成固定次数的中位数采样，是把 rollout 吞吐从「受限于评测」拉回「受限于生成」的关键。

另一个账本项是回退成本。反馈改写若失败，需要回退到上一版候选并保留其源码与评测记录，否则重跑会重复付出编译与测量成本。这要求脚手架维护一个候选池而非单条轨迹——候选池的显存与磁盘占用是隐性代价，但比重复编译便宜。

六 · 机制层面的三个工程判断

第一，单轮与 agent 的口径必须分开报告。43.7%→77.0% 是单轮正确率，97.4% 是 agent 解出率，72.9% 与 2.12 是 agent 相对 TorchInductor 的胜率与几何平均。把单轮数字当作系统能力会低估脚手架，把 agent 数字当作模型能力会高估策略——两者之间的差额正是脚手架与多轮反馈的贡献，而这个差额没有被单独消融（论文摘要未给出完整消融）。

第二，奖励门控的严格性直接决定 reward hacking 的空间。$\mathbb{1}[\text{pass}_t]$ 把正确性设为硬门，但「pass」的定义若只覆盖评测 shape，特化候选就能通过。防御手段不是加严容差，而是加留出 shape 与随机化输入。代价是每次评测的输入生成与比对成本上升，且留出 shape 上的性能可能远低于评测 shape，导致 $\Delta\text{speed}$ 的分布偏移。

第三，编译缓存与候选池是这套流水线的两个隐形基础设施。没有前者，RL 采样被编译时间卡住；没有后者，回退与重跑被重复测量卡住。二者的代价都是存储与哈希管理，收益是把端到端吞吐从评测受限转为生成受限。论文的 2.12 几何平均加速比是在统一基线下测的，若基线未开 TF32 或未用最强库实现，这个数字会被系统性高估——这是读这类结果时必须先问的口径问题。

奖励门控下的失效边界与系统代价

把一次 kernel 生成—编译—运行—评测拆成流动步骤后，真正决定这套方案边界的不是生成能力，而是每一步的门控条件与代价结构。奖励函数 $$R=\sum_{t=0}^{T}\gamma^{t}r_{t},\qquad r_t=\Delta\text{speed}_t\cdot\mathbb{1}[\text{pass}_t]$$ 的关键在于指示函数：正确性门一旦为假，整条轨迹的时延收益被清零，策略只能从编译失败或数值不符的信号里学“别犯错”，而学不到“怎么更快”。这带来第一个失效条件：当题目本身的通过率很低时（单轮尝试下正确率从 43.7% 提升到 77.0%，意味着仍有相当比例的样本落在门外），大量 rollout 的梯度信号被指示函数吞掉，token 预算消耗在无效探索上，训练吞吐被正确性门而非性能信号主导。第二个失效条件是 Δspeed 的测量口径：若基线未开 TF32、未用最强库实现，Δspeed 会被系统性高估，策略学到的是“相对弱基线更快”而非“真正更快”，这类奖励黑客在离线基准上不可见，只在换基线后暴露。

系统代价分布在四个环节，且互相挤占。生成环节的代价是 token：agent 脚手架的多轮改写把单题消耗从单次补全抬到数十次交互，上下文里塞入编译日志与 profile 片段后，单步推理时延随序列长度线性上升。编译环节的代价是墙钟时间：Triton 的 JIT 编译与 autotune 在候选数量上做乘法，一个候选若触发多组 config 搜索，编译时间可达运行时间的数倍，使得“多生成几个候选再筛”的策略在吞吐上不可行。运行与评测环节的代价是显存与设备占用：正确性检查需要按论文口径的输入分布逐一比对，参考实现与候选同时驻留显存，大 shape 下会触发 OOM 而被迫缩小 batch，进而改变时延测量的可比性。下表把四步的输入、输出与主要代价并置：

步骤输入输出主要代价
生成题目描述、参考实现、历史反馈候选 kernel 源码token 数与多轮上下文长度
编译源码、目标架构、config 空间可执行体或编译错误JIT 与 autotune 墙钟时间
运行可执行体、输入分布输出张量、时延样本显存驻留与测量噪声
评测输出、基线时延、正确性门奖励标量、保留/回退决策基线可比性与回退策略偏差

第三个失效条件来自 shape 特化。策略在固定输入分布上被奖励塑形，容易收敛到对特定 shape 硬编码的 tile 尺寸与分支，离线分数因此虚高；一旦生产端输入分布漂移，这类候选的正确性门仍能通过（数值对），但 Δspeed 反转为负，而奖励函数里没有“跨 shape 泛化”这一项，模型无从得知。第四个失效条件是回退机制：agent 脚手架在候选失败时回退到库实现，使最终正确率被回退路径抬高——97.4% 的求解率与 72.9% 的超越比例之间的差额，正是回退与部分通过共同贡献的，评测时必须把“回退次数”作为独立指标记录，否则正确率无法归因到模型本身。工程判断上，这套方案的可信度取决于把指示函数从“单点通过”改为“分布内多点通过 + 基线口径锁定”，代价是每题的评测成本按输入点数量线性增长，与生成端的 token 预算形成直接竞争。
