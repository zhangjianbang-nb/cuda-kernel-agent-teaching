一 · 任务分级与输入分布：口径的第一层约束

KernelBench 的评测口径从任务定义层就开始收紧。任务按难度分四级递进：单算子、算子序列、端到端模型片段、组合负载。级别越高，组合复杂度越大，可观察到的通过率随级别上升而衰减——这是分级设计的目的，而不是副作用。关键机制在于：每一级任务都显式规定输入 shape 与数据类型分布，候选内核与 PyTorch 参考实现必须使用完全相同的输入张量。这意味着加速比的分母和分子共享同一输入分布，正确性判定也在同一分布上完成。若把不同方法在各自挑选的 shape 上报出的加速比放在一起比较，口径立刻失效。

输入分布的处理有一个工程上的取舍。基准固定 shape 与 dtype 分布，换来的是可复现性；代价是对真实负载长尾覆盖有限。一个在基准规定 shape 上通过数值比对并跑出加速比的内核，迁移到真实模型中遇到非对齐维度、混合 dtype 或动态 shape 时，通过率与加速比都可能显著变化。因此测量口径必须写明：加速比只在基准规定的输入分布下有效，跨分布外推需要重新校准，不能直接把基准数字当作生产收益。

形式化地，一道任务可记为四元组：

$$\mathcal{T}_i=\langle \text{spec}_i,\ \mathcal{D}_i,\ y_i^{\text{ref}},\ T_i^{\text{ref}}\rangle$$

其中 $\text{spec}_i$ 是算子语义说明，$\mathcal{D}_i$ 是规定的输入 shape 与 dtype 分布，$y_i^{\text{ref}}$ 与 $T_i^{\text{ref}}$ 分别是参考实现在该分布上的输出与耗时。候选内核只在 $\mathcal{D}_i$ 上被评测，任何偏离 $\mathcal{D}_i$ 的输入都不进入统计。这条约束看似简单，却是后续所有指标可比性的前提。

具体例子：一道单算子任务规定输入为某一固定 batch 与通道组合的浮点张量，候选内核若针对该 shape 做了硬编码的 tile 划分，在基准上可能通过并跑出加速比；但同一内核换一个通道数就会因越界或数值偏差被判语义错误。基准不惩罚这种特化，因为它只承诺在 $\mathcal{D}_i$ 上度量——这正是口径需要被明确写出的原因。

二 · 双角色基线：oracle 与分母是同一个东西

KernelBench 把 PyTorch 参考实现同时用作语义 oracle 和性能基线。这个设计选择带来一个直接后果：正确性判定与加速比计算在同一输入、同一实现上闭环。候选内核的输出与 $y_i^{\text{ref}}$ 做逐元素容差比对，通过者才进入计时；计时结果与 $T_i^{\text{ref}}$ 相除得到加速比。两个角色共用一份代码，消除了“oracle 用一套实现、基线用另一套实现”导致的系统性偏差。

代价同样明确。PyTorch 是唯一基线，意味着加速比数字只反映相对框架基线的收益，不反映相对手写 CUDA 库或厂商内核的上限。一个跑出加速比的内核，可能仍远低于 cuBLAS 或 cuDNN 在同类算子上的水平；基准没有给出这个上限对比，因此加速比不能被解读为接近硬件 roofline。评测报告若只报加速比而不说明基线性质，会高估方法成熟度。

正确性判定的机制是逐元素容差：

$$\text{Pass}_i=\mathbb{1}\left[\lVert y^{\text{kernel}}-y^{\text{ref}}\rVert_{\infty}\le \varepsilon\right],\qquad \text{Speedup}_i=\frac{T_i^{\text{ref}}}{T_i^{\text{kernel}}}\ \text{仅当}\ \text{Pass}_i=1$$

这里 $\varepsilon$ 的取值材料未给出，重复测量次数也未给出。这两项缺失直接影响跨设备复现：容差偏松会让数值不稳定的内核混入性能统计，容差偏紧会压低通过率；重复次数不足则中位数计时受噪声支配。工程上引用该基准时必须自行约定这两项，并在报告中写明，否则不同实验室的通过率不可比。

具体例子：一个内核在浮点累加顺序上与参考实现不同，逐元素误差在容差内则判通过并计时；若容差被收紧，同一内核可能被判语义错误，从性能统计中消失。加速比分布因此对容差敏感——这是口径中必须显式声明的隐藏参数。

三 · 指标族：faster rate、speedup、geomean、fast_p 与 roofline 的分工

单一加速比中位数不足以刻画一个方法。评测口径需要一组互补指标，各自回答不同问题。下表给出各指标的定义与它掩盖的东西：

指标定义回答的问题盲区
编译成功率编译通过样本数 / 总样本数生成代码是否可落地不反映语义与性能
正确率数值比对通过样本数 / 编译通过样本数语义是否等价不反映快慢
faster rate加速比 > 1 的样本占比（在通过样本内）有多少任务真的赢了基线不反映赢多少
speedup 中位数通过样本加速比的中位数典型收益掩盖长尾与失败样本
geomean speedup$\exp(\frac{1}{N}\sum \ln s_i)$跨任务的平均收益对失败样本的处理需约定
fast_p加速比超过阈值 $p$ 的样本占比高收益任务的密度阈值选择主观
roofline / SOL实测吞吐与硬件上限之比离硬件极限多远需要 NCU/SASS 级 profile

几何平均的定义值得单独写出，因为它是跨任务汇总最常用的口径：

$$\text{Geomean}=\exp\!\left(\frac{1}{N}\sum_{i=1}^{N}\ln s_i\right),\qquad s_i=\frac{T_i^{\text{ref}}}{T_i^{\text{kernel}}}$$

几何平均对加速比取对数后求均值，避免了算术平均被个别超大加速比拉偏的问题；但它对 $s_i<1$ 的样本同样敏感，且失败样本如何处理（剔除、计为 1、计为 0）会显著改变结果。口径必须写明这一点：只对通过数值比对的样本计时，未通过者不进入性能统计——这意味着 geomean 的分母 $N$ 是通过样本数而非总题数，跨方法比较时若通过率不同，geomean 的可比性被削弱。正确做法是同时报告通过率与 geomean，让读者看到“在多少任务上平均赢了多少”。

faster rate 与 fast_p 是分布视角的补充。faster rate 只问“是否超过基线”，对超过多少不敏感；fast_p 设定阈值 $p$，问“有多少任务达到显著加速”。两者都不替代 speedup 分布本身。roofline/SOL 则是另一层：它把实测吞吐与硬件上限对比，回答“离极限多远”，但这需要 NCU/SASS 级 profile，材料未说明基准是否集成该工具。没有 roofline，加速比只能说明相对 PyTorch 的收益，不能说明内核本身的效率上限。

具体例子：两个方法在通过样本上 geomean 相同，但一个 faster rate 高、speedup 分布集中在 1.1 附近，另一个 faster rate 低、少数任务加速比很大。前者是“普遍小赢”，后者是“少数大赢”，单看 geomean 无法区分。口径要求同时给出 faster rate 与分布，正是为了区分这两种能力形态。

四 · 哪些数字不可比：口径失配的四种典型情形

跨方法比较加速比时，以下四种失配会让数字失去意义。第一，基线不同：以 PyTorch 为分母的加速比不能与以手写 CUDA 库为分母的加速比直接比较，后者分母更小，同样的内核会得到更低的加速比。第二，硬件不同：计时与编译环境绑定单一指定 GPU，跨设备比较需谨慎，不同架构的访存带宽与 SM 数量会改变同一内核的相对收益。第三，输入分布不同：基准固定 shape 与 dtype，方法若在自选 shape 上报数，分母与分子的输入不一致。第四，失败样本处理不同：把编译失败计为加速比 0 与把失败样本剔除，会得到不同的 geomean 与 faster rate。

这四种失配的共同根源是：加速比是一个比值，比值的可比性依赖分子分母在同一口径下测量。KernelBench 的设计把口径写进任务定义层——固定输入、固定基线、固定硬件、失败单列——正是为了让比值可比。任何偏离这套口径的报告，都需要显式声明偏离项，否则数字不可比。

具体例子：方法 A 报告 geomean 加速比，但只在通过样本上计算且未报通过率；方法 B 报告 geomean 并把编译失败计为 1。两者数字相近，但 A 的分母是通过样本（可能很少），B 的分母是全部样本。读者无法判断哪个方法更强，因为失败样本的处理口径不同。可核查的测量口径要求：报告 geomean 时必须同时给出通过率与失败样本处理规则。

另一个不可比点是计时方法。材料说明计时取重复测量中位数，但未给出重复次数与是否做 warmup。中位数对噪声稳健，但若重复次数不足，中位数本身波动大；若未做 warmup，首次运行的编译与缓存开销会污染计时。跨实验室复现时，这两项必须自行约定并写明，否则同一内核在不同环境下的加速比不可比。

五 · 隐藏 shape 与分布的处理：可复现性与覆盖度的权衡

基准对输入 shape 与 dtype 分布的处理是“显式规定、完全共享”。候选内核与参考实现使用完全相同的输入张量，这意味着不存在隐藏 shape——所有输入都在任务定义层写明。这个选择换来可复现性：任何人在同一 GPU 与编译环境下重跑，得到相同的输入分布与相同的基线耗时。代价是覆盖度：真实负载的长尾 shape、动态维度、混合精度组合未必被基准覆盖。

工程上，这意味着基准通过率不能直接外推为生产通过率。一个在基准规定分布上通过的内核，迁移到真实模型时可能因 shape 不对齐而性能骤降，或因 dtype 组合未覆盖而数值偏差。评测报告应把“基准分布内”与“分布外”分开陈述，前者是可复现的口径，后者需要重新校准。材料未给出分布的具体取值，引用时须标注数字缺失而非推测。

具体例子：一道算子序列任务规定固定的中间张量 shape，候选内核可以针对该 shape 做融合与 tile 划分；在基准上通过并跑出加速比。但真实模型中该序列的中间 shape 随 batch 变化，融合策略失效，加速比可能转为负值。基准不承诺分布外行为，这正是口径需要写明“仅在规定分布内有效”的原因。

可核查的测量口径应包含以下字段，缺一不可：任务级别与题量、输入 shape 与 dtype 分布、基线实现与版本、GPU 型号与编译选项、数值容差 $\varepsilon$、重复测量次数与 warmup 策略、失败样本处理规则、以及是否使用 NCU/SASS profile。材料为摘要级，未给出具体题量、各模型通过率、加速比中位数与分级统计；引用时必须标注这些数字缺失，而不是用定性表述填补。

六 · 失败模式的三分法与报告义务

KernelBench 把编译成功率单列，使编译失败、语义错误与性能不达标成为三类可分别统计的失败模式。这个三分法的工程价值在于：它迫使评测报告说明失败来源，而不是只报加速比。一个方法加速比高但编译成功率低，说明它生成的代码脆弱；一个方法编译成功率高但正确率低，说明它语义把握不足；一个方法两者都高但 faster rate 低，说明它写得出对的内核但优化不足。三种失败模式对应三种不同的改进方向。

报告义务由此而来：评测报告应同时给出三类失败模式的分布，以及通过样本内的加速比分布。只报加速比会掩盖失败来源，使读者误以为方法成熟度高于实际。材料未给出消融实验，可预期的消融维度包括难度级别、是否提供执行反馈、单轮与多轮生成、以及不同数值容差对通过率的影响，但具体结果未给出——这意味着失败模式分布的具体数字也缺失，引用时同样须标注。

具体例子：一个方法在单算子级别编译成功率高、正确率高，但在端到端模型片段级别编译失败率上升，原因可能是宿主调用封装与多算子组合的接口不匹配。若报告只给总体加速比，这个级别间的衰减被平均掉；若报告按级别给出三类失败模式分布，衰减立刻可见。分级统计与失败模式三分法是同一套口径的两个面。

最终，可核查的测量口径落在一个判断上：加速比是比值，比值的可信度取决于分子分母是否在同一输入、同一基线、同一硬件、同一失败处理规则下测量。KernelBench 把这四条写进任务定义层与评测执行层，使跨方法比较有了共同锚点；但容差、重复次数、题量与分级统计的缺失，要求引用者在报告里补齐这些字段，否则数字不可复现。评测的可信度不来自加速比的大小，而来自口径的完整声明。
