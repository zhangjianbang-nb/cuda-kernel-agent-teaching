一 · 反馈回灌的三层接口：编译、运行、profile

KernelBench 的评测执行层在概念上只做四件事——编译、运行、数值比对、计时，但它天然暴露了三类可被回灌给生成端的信号，且这三类信号的抽象层级依次升高。第一层是编译器的诊断输出：nvcc 或 Triton 编译器返回的错误码、出错文件与行号、模板实例化失败链、未定义符号、寄存器溢出警告。第二层是运行期错误：非法内存访问、越界写、未初始化共享内存读取、warp 内分支发散导致的同步死锁，通常以 CUDA runtime 的 error code 与 kernel launch 失败形式出现。第三层是硬件计数器：NCU 采集的 SM 占用率、DRAM 吞吐、L2 命中率、warp stall 原因分布，以及 SASS 反汇编里可见的指令混合与寄存器压力。三层信号的信息量、获取延迟与可解析性差异极大，回灌策略必须按层区分，而不是把一段 stderr 文本原样塞回 prompt。

一个可操作的接口设计是让评测器为每个候选产出一个结构化反馈记录，而不是自由文本。伪代码思路如下：

$$\text{fb}=\{\,\text{stage}\in\{\text{compile},\text{run},\text{correct},\text{perf}\},\ \text{code},\ \text{loc},\ \text{metric},\ \text{diag}\,\}$$

其中 stage 决定这条反馈该被路由到哪一类修复动作：compile 阶段失败应触发语法与类型修复，run 阶段失败触发内存与同步修复，correct 阶段失败触发语义与数值精度修复，只有 perf 阶段才值得引入 profile。把四类失败混为一谈，模型会把一个越界写误判成“性能不够”而去改 tile 大小，这是反馈粒度错配的典型代价。

代价方面，编译反馈最便宜：一次 nvcc 调用在秒级返回，token 开销仅是错误信息本身，通常几十到几百 token。运行反馈稍贵：需要真实分配显存、启动 kernel、捕获 error code，一次非法访问可能触发上下文失效，需要重建 CUDA context 才能继续评测后续候选，这会让单次评测的墙钟时间从毫秒级跳到秒级。profile 反馈最贵：NCU 以 replay 方式多次重放同一 kernel 以采集不同计数器组，单次采集可能把被测 kernel 的实际执行放大数倍到数十倍，且输出是结构化但体量庞大的报告，直接塞进上下文会挤占生成预算。因此工程上常见的做法是分层触发：编译失败只回灌编译器诊断；编译通过但运行失败只回灌 error code 与出错 API；运行成功但数值不符只回灌最大误差位置与参考值；只有前三关全过，才值得花 NCU 的钱。

二 · 编译与运行错误的可修复性分级

编译错误并非同质。按可修复性可以粗分三档：词法/语法错误（缺分号、括号不匹配、类型名拼错）几乎总能被模型在单轮内修好，因为错误信息直接指向位置；模板与 API 误用（把 cudaMalloc 的参数顺序写反、忘记 cudaMemcpy 的方向参数、Triton 里 tl.load 的 mask 形状不匹配）需要模型理解宿主与设备代码的边界，修复轮数上升；架构约束类错误（共享内存超限、寄存器数超过 block 上限、使用了目标架构不支持的指令）则要求模型改变算法结构而非改一行代码，单轮修复成功率显著下降。KernelBench 把编译成功率单列为指标，正是为了让这三档的分布可见——只报加速比会把“根本没编译过”的样本从视野里抹掉。

运行错误的信息量比编译错误低，因为 CUDA 的 error code 往往只给出“invalid memory access”而不给具体地址与指令。工程上可以做的增强是在候选代码外包一层检查：在 kernel launch 后同步并检查返回值，在调试模式下用 compute-sanitizer 定位越界。但 sanitizer 的代价是执行时间放大一个数量级以上，且对大规模 shape 可能直接超时，因此只适合在候选反复失败时按需开启，而不是每轮都跑。一个具体例子：某候选在单算子任务上编译通过，运行时报 misaligned address，若只回灌 error code，模型倾向于盲目加 __align__；若回灌 sanitizer 给出的“第 37 行、线程 (x,y) 访问偏移 4 字节处”这一粒度，模型能直接定位到向量化加载的指针对齐假设错误。这说明运行期反馈的价值不在“有没有错”，而在“错在哪一行、哪个线程”。

正确性反馈同样需要粒度设计。KernelBench 用逐元素容差判定，超出容差即判语义错误。若只回灌一个布尔值，模型无从判断是整体符号错、边界条件错还是浮点累加顺序导致的精度漂移。回灌最大绝对误差、出错元素索引、该位置参考实现与候选的数值，能让模型区分“逻辑错”与“精度错”——前者要改算法，后者可能要改累加策略或数据类型。代价是这部分反馈要携带张量切片，token 开销随诊断元素数线性增长，通常只回灌前若干个最大误差点即可。

三 · NCU 与 SASS：把 stall 归因变成可执行的修改建议

当候选已经编译、运行、数值正确，剩下的问题才是“为什么不够快”。此时裸 speedup 只告诉模型“慢了 1.8 倍”，不告诉它慢在哪。NCU 的 warp stall 采样把每个 warp 的等待原因分类：stall_long_scoreboard（等待全局内存返回）、stall_short_scoreboard（等待共享内存或 MIO）、stall_barrier（等待 __syncthreads）、stall_math_pipe_throttle（数学流水线饱和）、stall_not_selected（warp 就绪但调度器选了别人）。这些分类直接映射到不同的优化动作：long scoreboard 高说明访存延迟未被隐藏，应提高 occupancy 或做预取；barrier 高说明同步过密，应减少 block 内同步点或改用 warp 级原语；math pipe throttle 高说明计算密集，应检查是否有冗余指令或可向量化的运算。

把 stall 分布转成 prompt 里的可执行线索，需要一个归因公式的思路。设某 kernel 的总 stall 采样数为 S，第 i 类 stall 计数为 si，则占比 pi=si/S。工程上不直接回灌全部 pi，而是取 top-2 并附上对应的 SASS 片段。SASS 层面的信息补充了 NCU 看不到的细节：例如 LDG.E.128 与 LDG.E.32 的混用说明向量化不彻底，IMAD 密集而 FFMA 稀疏说明整数索引计算占比过高，寄存器数（通过 nvcc --ptxas-options=-v 或 cuobjdump 获得）偏高则解释 occupancy 为何上不去。一个具体例子：某矩阵乘候选的 NCU 显示 long scoreboard 占主导，SASS 显示每次 LDG 后紧跟一次 BAR.SYNC，说明加载与计算没有重叠；把这条组合反馈回灌后，模型把双缓冲引入共享内存流水，stall 结构随之改变。若只给 speedup，模型只能靠猜。

代价必须算清楚。NCU 的 replay 机制意味着采集 N 组计数器就要重放 N 次 kernel，对短 kernel 的放大倍数尤其夸张；对端到端模型片段这类长负载，一次完整 profile 可能耗时数十秒到分钟级，远超编译与运行的成本。SASS 反汇编本身便宜，但输出体量大，一个中等 kernel 的反汇编可达数百行，全量塞入上下文会挤占本已紧张的生成 token 预算。因此 profile 反馈应被当作“昂贵但高信息密度”的资源，按候选的失败模式选择性投放：数值已对但加速比低于基线的候选才值得 profile，且只回灌 top stall 类别与关键 SASS 行，而不是整份报告。

四 · roofline 诊断：把“慢”翻译成“离上限多远”

speedup 是相对量，roofline 是绝对量。给定 kernel 的浮点运算量 F（FLOP）与访存量 B（Byte），算术强度 I=F/B；硬件峰值算力 P、峰值带宽 W，则 roofline 上界为：

$$\text{Attainable}=\min\left(P,\ I\cdot W\right),\qquad \text{SOL}=\frac{\text{Achieved}}{\text{Attainable}}$$

SOL（speed-of-light）百分比把“加速比 1.2 倍”翻译成“达到硬件上界的 34%”，后者才是可跨任务比较的诊断量。KernelBench 以 PyTorch 为唯一基线，加速比只反映相对框架的收益，不能直接解读为接近硬件上限；roofline 恰好补上这一维。对 memory-bound 的算子（如 elementwise、归一化），I 低，上界由 I·W 决定，SOL 低说明带宽没打满，应查合并访问与 L2 命中；对 compute-bound 的算子（如大矩阵乘），上界由 P 决定，SOL 低说明流水线利用率不足，应查 occupancy 与指令混合。

把 roofline 回灌给模型的关键是给出“当前瓶颈侧”而非一个百分比。若实测带宽已接近 W 而算力远低于 P，反馈应明确写“memory-bound，带宽利用率高，继续优化访存收益有限，应减少总访存量或提升数据复用”；反之则写“compute-bound，算力利用率低，应检查是否有可融合的冗余计算”。这种方向性反馈比“SOL=34%”更能约束模型的搜索空间。代价在于 roofline 需要准确的 F 与 B 估计：F 可从算子语义推算，B 需按实际访问模式统计，若模型改写了算法（比如引入分块复用），B 会随之变化，静态估计可能失真。因此 roofline 反馈适合作为粗粒度方向指引，而非精确判据。

五 · 为什么硬件反馈优于裸 speedup

裸 speedup 是一个标量，它把“编译失败”“语义错误”“性能不达标”压缩成一个数字或一个缺失值，信息在压缩中丢失。更关键的是，speedup 对修改方向不敏感：两个截然不同的候选可能给出相同的加速比，模型无法从中学到哪条修改路径有效。硬件反馈则提供了因果链——stall 类别指向等待源，SASS 指向指令选择，roofline 指向瓶颈侧，三者共同构成“症状—病因—处方”的结构。KernelBench 把编译成功率、正确率、加速比三元组分开报告，本质上就是在评测层面承认这三类信号不可互相替代；把这一原则延伸到反馈回灌，就是按失败阶段路由不同粒度的诊断。

信息量与延迟之间存在明确的权衡。编译反馈延迟最低、信息最局部，适合高频多轮迭代；profile 反馈延迟最高、信息最全局，适合低频定向诊断。一个工程上合理的调度是：前若干轮只回灌编译与正确性反馈，快速把候选推到“能跑对”的状态；当候选稳定通过后，再按加速比与基线的差距决定是否触发 profile，且每次 profile 只回灌一个瓶颈维度的摘要。这样做的代价是总评测时间上升——profile 的 replay 开销与结构化报告的解析开销都要计入——但换来的是每一轮反馈都携带可执行的方向，而不是让模型在盲目试错中消耗生成预算。一个具体判断：若某候选连续多轮加速比停滞而编译与正确性均通过，继续回灌 speedup 已无信息增量，此时应切换到 stall 与 roofline 诊断；反之若候选仍在编译失败，投入 NCU 是纯粹的浪费。

反馈回灌的边界：硬件信号何时失效、代价几何

把 NCU 指标回灌给 agent 时，第一个失效条件是归因错位：warp stall 的长周期计数（如 long scoreboard 占比高）既可能来自全局内存访问模式差，也可能只是 occupancy 不足导致延迟无法被其他 warp 掩盖，而后者往往由寄存器压力或共享内存用量引起——这三类根因对应完全不同的改写动作（向量化/合并访存、调低寄存器、改 tile 尺寸）。若反馈只给 stall 名称而不给 occupancy、寄存器数与访存事务数，agent 极易把“延迟隐藏不足”误判为“带宽不够”，从而做出无效甚至有害的改写。第二个失效条件是采样噪声：单次 NCU 采集会串行化并重放 kernel，其测得的周期数不能直接当作计时口径；若把 profile 耗时与 speedup 计时混用，加速比会系统性偏移。因此回灌必须区分“诊断信号”与“性能信号”，前者用于定位，后者只认基准规定的重复测量中位数。

粒度与延迟构成直接的系统代价。以每轮一次完整 NCU 采集计，单 kernel 的 replay 开销通常是毫秒到数十毫秒量级，叠加编译（CUDA C++ 的 nvcc 编译在模板与 CuTe 场景下可达秒级）后，一轮“生成—编译—运行—比对—profile”闭环的墙钟时间远高于纯文本生成的 token 成本；多轮 RL 中若每步都挂 profile，采样吞吐会被 profile 主导。可行的折中是分层回灌：编译失败只回灌错误类型与首条诊断行（信息量高、成本近零）；语义错误回灌最大绝对误差与出错索引；仅对已通过正确性且加速比低于基线的样本触发 NCU，且只取 3–5 个标量（occupancy、DRAM 吞吐占 SOL 比例、主导 stall、每 warp 访存事务数）。用公式表达筛选条件：

$$\text{profile}(k)\ \text{触发} \iff \text{Pass}(k)\land \frac{T_{\text{pytorch}}}{T_k}<\tau,\qquad \text{回灌向量}=\langle \text{occ},\ \text{DRAM}_{\text{SOL}},\ \text{stall}_{\text{top}},\ \text{tx/warp}\rangle$$

下表对比三类反馈在信息量与代价上的取舍，可见硬件反馈并非越细越好：

反馈类型信息量单轮代价典型失效
编译错误文本高（定位到行）近零模板报错冗长，截断后丢失根因
数值误差摘要中（定位到元素）一次比对容差固定时，fp16 累加误差被误判为语义错
NCU/SASS 标量中高（定位到瓶颈类）replay 串行化stall 归因错位、采样不代表计时

具体例子：一道 reduction 类单算子任务，候选内核通过数值比对但加速比低于基线。裸 speedup 反馈只告诉 agent“慢了”，它可能盲目加大 block 尺寸；而回灌 occupancy 偏低加主导 stall 为 long scoreboard、tx/warp 偏高这三个标量，可直接指向“每线程跨步访存未合并”，改写方向收敛到合并访存与向量化加载。反过来，若该样本本就受限于 kernel 启动开销（小 shape 下端到端片段常见），profile 显示 DRAM 吞吐远低于 SOL 且 stall 以 barrier 为主，此时任何访存改写都无效，正确动作是融合相邻算子或减少启动次数——这正是硬件反馈优于裸 speedup 的地方：它把“慢”拆成可判定的瓶颈类别，使 agent 的搜索空间从盲目调参收缩到有依据的少数改写。代价是这套回灌依赖固定的 GPU 与编译选项，跨设备迁移时 stall 分布与 SOL 比例都会漂移，回灌阈值需重新校准而非直接复用。
