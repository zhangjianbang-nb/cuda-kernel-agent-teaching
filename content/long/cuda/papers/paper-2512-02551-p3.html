一 · 生成步：策略模型吐出的不是代码，是一组待验证的配置假设

在 CUDA-L2 的闭环里，第一步的输入是矩阵乘的 shape 描述（M、N、K 与数据类型）以及上一轮回流的诊断信息；输出是一份完整的 CUDA C++ 源码。关键之处在于：这份源码并非“一段程序”，而是一组可被后续步骤逐一证伪的假设——tiling 尺寸、每线程累加器数量、共享内存分块方式、线程块与网格的映射关系、是否使用向量化加载。策略模型在生成时并不知道这些假设中哪几条会撞上寄存器上限、哪几条会造成 bank conflict，因此生成步的输出天然带有不确定性，其价值必须由编译、运行、计时三步依次裁决。

从代价角度看，生成步消耗的是 token：源码长度随 tiling 参数与展开程度上升，一份带显式展开与边界处理的 kernel 明显长于朴素三重循环版本。这直接决定了后续多轮迭代的预算上限——若每轮采样若干 kernel、每份源码数百至上千 token，则轮数与批量共同构成训练侧的主要成本项，而材料未给出该成本的具体数值，只能定性判断它是该方法工程可行性的第一道门槛。

一个具体例子：给定方阵 shape，模型首轮常写出每线程持有较大累加器阵列的写法以提升算术强度，这一假设在生成步看是合理的，却会在编译步被寄存器压力直接否决。生成步因此不是“一次成型的产出”，而是把搜索空间中的某个点提交给硬件裁决。

二 · 编译步：把语法与资源错误转成结构化负样本

编译步的输入是上一步的源码，输出是二值结果加上一份失败类型标签。CUDA-L2 明确把编译失败归为三类可回流信号：语法错误、寄存器溢出、共享内存超限。这三类错误的处理方式不同——语法错误指向代码结构本身，通常意味着生成质量缺陷；寄存器溢出与共享内存超限则是资源约束违反，指向 tiling 与线程组织参数越界。系统把错误类型而非原始报错文本回传，使下一轮生成获得的是“该往哪个方向收缩”的约束，而不是一段需要模型自行解析的编译器日志。

这一步的代价是编译时间与迭代节拍。每次生成都要走一遍 nvcc 前端与 ptxas，寄存器溢出恰恰发生在 ptxas 阶段，意味着必须真正完成编译才能拿到该信号，无法用轻量静态检查替代。多轮闭环中，编译时间与生成 token 成本叠加，构成每轮迭代的固定开销；若采样批量大，编译步会成为吞吐瓶颈。

伪代码层面的机制可写成：若 regs_per_thread > limit 则标记 REG_SPILL，若 smem_bytes > limit 则标记 SMEM_OVER，两者都进入负样本池并附上触发参数。一个具体例子：模型在某轮把每线程累加器数量设得过高导致溢出，回传标签后下一轮降低累加器数量、改为更多线程分担，这正是材料所述“降低每线程累加器数量”的规避路径。编译步因此承担了搜索空间中“硬约束边界”的探测功能。

三 · 运行与校验步：正确性是硬门槛，不是奖励的一部分

运行步的输入是编译通过的 kernel 与同 shape 的参考矩阵乘实现，输出是数值比对结论。CUDA-L2 的奖励设计在这里划出一条清晰的界线：数值校验不通过的 kernel 奖励直接置零，无论其延迟多快。这不是把正确性折进奖励做加权，而是把正确性作为乘性门槛——错误结果换取的速度不被承认。其形式化表达即本部分的核心公式：

$$r=\begin{cases}\dfrac{t_{\mathrm{cuBLAS}}}{t_{\mathrm{kernel}}}, & \text{若数值校验通过}\\0, & \text{否则}\end{cases}$$

这一设计的工程含义值得展开：若把正确性做成奖励中的软惩罚项，策略会学到“用轻微数值偏差换取大幅提速”的投机路径，而矩阵乘的数值偏差往往来自同步缺失与边界处理错误，这类错误在更大 shape 或不同数据分布下会放大为完全错误的结果。硬门槛切断了这条路径，代价是早期训练中大量样本奖励为零，梯度信号稀疏——失败样本必须靠诊断标签而非奖励数值提供学习方向，这正是材料强调“失败诊断一并纳入更新”的原因。

运行步的具体失败模式包括同步与边界处理问题导致的数值偏差。一个具体例子：模型在分块边界处漏写对 K 方向尾块的处理，编译通过、运行不崩，但与参考结果比对超阈值，该样本奖励置零并回传“数值偏差”标签，下一轮生成倾向于补齐边界分支。此步的代价是运行时间与参考实现的比对开销，在真实 GPU 上每次采样都要实际执行，无法离线伪造。

四 · 计时步：加速比的分母是会被环境漂移的基线

计时步的输入是通过校验的 kernel 与同 shape 的 cuBLAS 调用，输出是加速比 t_cuBLAS / t_kernel。这一步看似只是读一个数，实则是整个闭环中最脆弱的环节。材料明确指出：每换一次 GPU 型号或 cuBLAS 版本都需重测基线，否则加速比口径漂移；计时还需固定预热与重复次数以降低噪声。这意味着奖励信号并非 kernel 的绝对属性，而是 kernel 与特定基线、特定硬件、特定测量协议三者共同定义的相对量。

其代价体现在测量噪声直接污染奖励。若重复次数不足，单次延迟抖动会使同一 kernel 在不同轮次得到不同奖励，策略更新被噪声驱动；若预热不充分，首次调用的冷启动开销混入均值，系统性低估 kernel 性能。多次测量取统计量是必要手段，但每次测量都消耗 GPU 时间，与采样批量相乘后构成训练侧的主要 wall-clock 成本。材料未给出测量次数与预热策略的具体取值，因此该成本只能定性判断为“不可忽略”。

一个具体例子：同一份 kernel 在固定 shape 下与 cuBLAS 比较，若基线未随驱动或库版本更新而重测，加速比可能因分母变化而虚高或虚低，而策略对此毫无感知，只会朝着被污染的奖励方向演化。计时步因此不只是评测，它是奖励函数的物理实现，其协议稳定性等价于奖励函数的可复现性。

五 · 奖励聚合与轨迹更新：三类信号如何合成一条学习路径

聚合步的输入是编译标签、校验结论与加速比，输出是写入多轮轨迹的标量奖励加诊断元数据。这里的机制要点是：奖励数值只承载“通过校验后的速度”，而失败类型承载“为什么没通过”，两者分离进入轨迹。高奖励样本提供正例，失败诊断提供负例方向，材料所述“高奖励样本与失败诊断共同进入更新”正是这一分离结构的体现。若把失败类型也压进标量奖励，则不同失败模式之间的区分度丢失，策略无法学到“溢出该降累加器、数值偏差该补边界”这种针对性的修正。

轨迹层面的代价是存储与筛选：每轮若干 kernel 的源码、编译标签、校验结论、计时结果都要保留，供策略更新时按奖励筛选。轮数、批量与 token 成本材料未给出，因此无法估算轨迹规模；但可以判断，轨迹的保留策略直接决定训练侧能否复用历史失败样本，若只保留高奖励样本则丢失负例方向，若全量保留则存储与更新开销上升。

一个具体例子：某轮采样中一份 kernel 编译溢出、一份数值偏差、一份通过校验但慢于 cuBLAS。三者奖励分别为零、零、小于一的正值，但诊断标签分别为 REG_SPILL、NUM_MISMATCH、无。下一轮生成在这三条轨迹的共同约束下，倾向于同时避开溢出参数与边界缺陷，并向更高占用率的写法靠拢。聚合步因此是“把硬件裁决翻译成策略可消费的梯度方向”的翻译层。

六 · 单轮闭环的工程判断：信号可信度决定方法上限

把五步串起来看，CUDA-L2 的方法骨架并不复杂：生成—编译—运行—校验—计时—聚合，每一步的输入输出都明确，代价也都落在可计量的资源上（token、编译时间、GPU 运行时间、测量噪声）。真正决定该方法能否成立的，不是闭环的结构，而是每一环信号的可信度。编译标签的可信度取决于错误分类是否覆盖真实失败模式；校验的可信度取决于容差阈值与参考实现是否严格；计时信号的可信度取决于基线重测与测量协议是否固定。材料在这三处均未给出具体取值，因此该方法的可复现性边界无法从现有信息判断。

工程判断落在一点上：以 cuBLAS 加速比为奖励，等价于把奖励函数外包给一个会随环境漂移的外部基线。这带来两个直接后果——其一，任何跨硬件、跨库版本的结论都必须重测基线才能比较，材料所述“跨 shape 与跨硬件的可比性无法从材料判断”正源于此；其二，奖励的绝对数值不可跨环境迁移，只有同一环境内的相对排序可信。因此该闭环适合作为特定硬件上的 kernel 搜索脚手架，其产出的高奖励样本在该环境下有效，但“超过 cuBLAS”不能被当作普适结论引用。方法的上限由信号可信度而非搜索算法本身决定，这是本部分从机制层面能给出的最具体判断。

闭环里最先崩的不是策略，是奖励口径

把生成—编译—运行—评测串成一条链后，真正决定这套方法能不能学的不是策略网络，而是奖励函数在边界上的行为。论文的奖励是一个分段函数：

$$r=\begin{cases}\dfrac{t_{\mathrm{cuBLAS}}}{t_{\mathrm{kernel}}}, & \text{数值校验通过}\\0, & \text{否则}\end{cases}$$
这个设计把正确性做成硬门槛，避免了“用错误结果换速度”的作弊路径，但它同时制造了一个梯度悬崖：一个kernel从数值偏差略超阈值到刚好通过，奖励从0跳到某个正数，中间没有任何平滑过渡。策略在悬崖附近采样时，看到的信号是二值的，无法区分“差一点就对”和“完全跑飞”，于是失败诊断的类型标签（寄存器溢出、共享内存超限、数值偏差）就成了唯一可用的稠密信息。代价在于，这些标签是离散类别，回传后只能提示“下一轮降低每线程累加器数量”这类粗粒度动作，无法告诉模型偏差出现在哪个tile边界上。一个具体例子：某shape下kernel因边界处理漏掉尾块导致数值校验失败，奖励置零，模型下一轮若只按“同步与边界处理问题”这一标签调整，很可能在非方阵shape上反复踩同一类坑，因为标签没有携带shape维度的信息。

第二个边界是计时口径的脆弱性。加速比的分母是同shape的cuBLAS延迟，分子是kernel延迟，两者都必须在同一预热策略、同一重复次数、同一cuBLAS版本下测得。换一次GPU型号或cuBLAS版本，分母漂移，历史轨迹里所有正奖励样本的相对排序失效，多轮更新积累的“高占用率、合理共享内存分块”偏好可能整体错位。这不是精度问题，是可比性问题：奖励的绝对值不再有意义，只有同一环境内的相对比较成立。工程上这意味着每次硬件或库版本变更都要重测基线并重跑一批参考kernel，成本随shape集合线性增长，而材料未给出shape数量，无法估算这条重测流水线的规模。计时噪声本身也是代价：矩阵乘kernel延迟常在微秒到毫秒量级，若重复次数不足，噪声会淹没真实加速比，使奖励在阈值附近抖动，策略学到的是噪声而非tiling策略。

第三个失效条件是反馈信号的覆盖不对称。编译错误与数值失败被归类回传，属于负样本；计时结果只在正确性通过后才产生正奖励。于是搜索空间里大量“能编译、能跑、但慢”的样本只贡献一个小于1的加速比，没有任何诊断信息说明慢在哪里——是共享内存分块太小导致带宽未饱和，还是占用率被寄存器压力压低。论文的结构里没有NCU/SASS级别的profile回流，计时层只给标量延迟，奖励聚合层只把它折成加速比。这意味着多轮迭代中，模型对“慢”的修正只能靠试错采样，而非定向优化，采样预算成为隐性成本。若每轮生成若干kernel、每个都要编译加真实GPU运行加多次计时，单轮wall-clock由编译时间与计时重复次数主导，token成本反而次要；材料未披露轮数与批量，这条成本曲线无法闭合。

生成shape描述、历史失败标签带tiling参数的CUDA源码token标签粗粒度，无法定位边界错误

把这张表连起来看，系统的可信边界很清楚：它能在固定shape集合、固定GPU与固定cuBLAS版本下，用二值正确性门槛加标量加速比驱动多轮搜索，负样本靠失败类型标签规避同类错误；但它不能跨环境迁移奖励，不能对“慢”给出定向梯度，也不能把单一矩阵乘的结论外推到其他算子。工程判断上，这套闭环适合作为受控实验台——先锁死基线版本与计时口径，再用失败标签的细粒度化（例如把寄存器溢出回传为具体用量而非布尔）换取更稠密的负样本信号，否则多轮RL的采样预算会大量消耗在重复踩同类编译坑上。
