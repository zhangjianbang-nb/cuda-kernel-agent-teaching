一 · 结构奖励的失效模式：当代理特征与真实性能脱钩

CudaPerf 的核心赌注是：memory coalescing、occupancy、arithmetic intensity、synchronization pattern 这些可从源码静态抽取的并行化特征，与 kernel 的真实执行性能之间存在稳定相关性，因此可以作为 reward 的一部分。这个假设在论文给定的基准与硬件上成立，但它有明确的失效边界，而这些边界恰恰决定了工程上什么时候不该用它。

第一类失效是特征可被“装饰”而非“实现”。结构奖励通常由静态分析或轻量 AST 匹配给出，模型完全可以在源码里写出看起来合并访问的索引表达式、声明足够大的 block size、插入看似合理的 `__syncthreads()`，而实际运行时由于分支发散、bank conflict 或寄存器溢出，真实带宽利用率远低于静态特征所暗示的水平。此时结构奖励给出正向信号，执行奖励因为候选刚好通过正确性门而给出非负信号，两者叠加把一条劣质路径推成高概率采样。代价是采样预算：多轮 RL 里每一轮都要编译、跑正确性、测时延，一个被结构奖励误导的候选会占用一整轮迭代的时延与 token，而它本可以被执行反馈直接淘汰。

第二类失效是 occupancy 与 arithmetic intensity 的方向性冲突。高 occupancy 往往意味着更小的寄存器占用与更简单的线程级并行，但对计算密集 kernel 而言，真正决定 roofline 位置的是每字节访存对应的浮点运算量，压低寄存器反而可能增加重复访存。结构奖励若把 occupancy 当作单调递增的正向特征，就会系统性地把模型推向 memory-bound 一侧。用一个粗粒度的打分示意：

$$s_{\text{struct}}=\alpha\cdot \text{coalesce}+\beta\cdot \text{occupancy}+\gamma\cdot \text{AI}-\delta\cdot \text{sync}$$

其中 $\alpha,\beta,\gamma,\delta$ 若为固定常数，则在不同 roofline 区域的 kernel 上给出错误排序——对 GEMM 类 kernel，$\beta$ 的权重应当趋近于零甚至为负。论文的离线 pairwise ranking 模块本意是让模型从强弱候选对比中学习这种权重，但 ranking 的训练分布来自论文数据集（2.9k C→CUDA 与 1k PyTorch→CUDA，每程序配多份实现），一旦目标 kernel 落在该分布之外（例如稀疏算子、带动态 shape 的 reduction），学到的偏好就不再可迁移。

具体例子：一个 layernorm 的 fused kernel，模型把 block size 从 256 提到 1024 以获得更高 occupancy 特征分，但每个 block 需要跨更多行做 reduction，`__syncthreads()` 次数上升，实际时延反而增加；结构奖励因为 occupancy 提升而加分，执行奖励因为加速比 $\Delta\text{speed}_t<0$ 而扣分，两者在 $r_t=\Delta\text{speed}_t\cdot\mathbb{1}[\text{pass}_t]$ 的乘性结构下互相抵消，梯度信号变得噪声化——这正是结构奖励与执行奖励简单加权求和时的典型代价：训练稳定性下降，需要更多轮次才能收敛。

二 · 执行奖励的可验证性边界：正确性门与计时口径

执行奖励看似最“硬”，但它的可信度完全依赖于正确性 oracle 的覆盖度与计时口径的一致性。CudaPerf 的奖励形式把加速比与通过标志相乘，意味着任何通过正确性检查的候选都能拿到与加速比成正比的奖励；问题在于“通过”的定义。

若正确性检查只覆盖论文给定的输入配置（数据集声称每个程序配“diverse input configurations”，但 diverse 不等于 exhaustive），模型可以学到针对这些 shape 的特化：把 tile size、unroll 因子、甚至边界处理硬编码到具体维度上。这类候选在离线基准上加速比亮眼，在生产端遇到未见过的 batch size 或非对齐长度时要么走 fallback 分支导致性能崩塌，要么直接越界。代价是部署阶段的端到端回归成本：离线分数与线上时延的差距不会被 RL 训练过程暴露，只会在真实流量上以 P99 时延或错误率的形式出现。

计时口径是第二个边界。加速比的分母是基线，而基线选择（PyTorch eager、torch.compile、论文指定库实现）直接决定奖励的绝对尺度。若基线未开启 TF32 或未使用厂商最强库，任何候选都能轻易获得正加速比，奖励信号失去区分度；反之若基线是高度调优的库实现，多数候选的 $\Delta\text{speed}_t$ 为负，奖励稀疏到无法驱动学习。论文的评测口径固定了基线，但这一固定性本身就是迁移风险：换一个基线，同一批候选的排序会翻转。

还有一个更隐蔽的代价：计时噪声。kernel 时延在微秒量级，GPU 时钟抖动、L2 残留状态、并发流干扰都会让同一候选的测量值波动。若 $\Delta\text{speed}_t$ 直接取自单次测量，奖励就带上了与 kernel 质量无关的方差；多轮 RL 中这种方差会累积成策略的随机漂移。工程上的判断是：执行奖励必须建立在多次测量取中位数、固定时钟状态、清空 L2 的口径上，否则结构奖励再精细也无法补偿执行信号的噪声。

具体例子：一个矩阵乘 kernel 在论文基准的固定 M/N/K 上通过正确性检查并报告加速，但模型把 K 维按 16 对齐做了假设；当生产输入 K=1000（非 16 倍数）时，kernel 要么结果错误要么退化为标量路径。正确性 oracle 没覆盖这个 shape，执行奖励给了满分，部署时才暴露——这是“离线可验证”与“生产可信”之间最典型的裂缝。

三 · 多轮迭代精化的成本结构：什么时候轮次不再划算

CudaPerf 用执行反馈做 iterative refinement，让候选在多轮中逐步改进。这个机制的有效性依赖一个前提：每一轮的反馈都携带足以定位问题的信息量。编译错误、运行错误、profile 数值确实携带信息，但信息密度随轮次递减——第一轮往往修掉语法与明显逻辑错误，后续轮次面对的是性能瓶颈，而性能瓶颈的定位需要 NCU/SASS 级别的细粒度数据，仅靠“加速比没提升”这一标量反馈，模型只能做盲目改写。

成本侧要算三笔账。其一是编译时间：每轮每个候选都要走完整编译链路，CUDA C++ 的模板实例化与 PTX 生成在复杂 kernel 上可达秒级到十秒级，多候选并行采样时编译成为吞吐瓶颈。其二是 token：多轮对话把历史候选、编译日志、profile 摘要全部塞进上下文，上下文长度随轮次线性增长，而有效信息占比下降。其三是 GPU 时延：正确性检查与计时都要真实执行，候选数量乘以输入配置数量乘以重复测量次数，构成训练循环里最贵的一项。

因此存在一个明确的“不该用”区间：当目标 kernel 的性能瓶颈无法从标量加速比反馈中区分（例如瓶颈在访存模式而非计算量），多轮精化的边际收益低于每轮的成本；当编译时间占单轮 wall-clock 的比例过高（复杂模板 kernel），增加轮次不如增加单轮候选数；当正确性 oracle 本身昂贵（需要多组输入、多种 dtype 交叉验证），每轮验证成本会压过训练收益。

具体例子：一个需要 CuTe 布局抽象的 GEMM 变体，单次编译因模板展开耗时显著，而每轮反馈只有一个加速比数字。此时把 8 轮精化换成 8 个并行候选加一轮筛选，能在相同 wall-clock 内覆盖更大的搜索空间——多轮的价值在于反馈的因果性，而非轮次本身。

四 · 与相邻工作的差别：奖励结构决定适用面

把 CudaPerf 放进同方向的工作里看，差别不在“是否用 RL”，而在奖励的构成与反馈的粒度。纯 outcome-based 的 RLVR（只给正确性与加速比）在奖励稀疏时退化，CudaPerf 用结构特征做稠密化；但稠密化是有偏的，偏差方向由特征设计决定。这与 Kevin 那类以多轮执行为主轴、把反馈组织成对话轨迹的做法不同：后者的信号全部来自真实执行，无偏但稀疏；CudaPerf 用结构奖励换稠密性，代价是引入与硬件、shape 分布绑定的先验。

维度CudaPerf 的取向带来的边界
奖励来源执行奖励 + 静态结构特征结构特征与真实性能脱钩时产生误导
反馈粒度标量加速比 + 代码级特征无法定位访存/同步级瓶颈
训练阶段离线 pairwise ranking + 在线 RLranking 分布外的 kernel 迁移性弱
数据规模2.9k C→CUDA、1k PyTorch→CUDA覆盖不到的算子族缺少先验

与对比学习路线（如 CUDA-L1 式的 contrastive 优化）相比，CudaPerf 的 pairwise ranking 同样利用强弱对比，但它把对比结果固化进 reward model 再进入在线 RL，而不是直接在采样层面做偏好选择；这意味着离线 ranking 的质量成为上限，ranking 训练数据的偏差会被在线阶段放大。与多智能体框架（Astra、cuPilot 一类）相比，CudaPerf 是单策略的多轮精化，没有角色分工带来的分解能力，因此在需要“先重构算法再调优”的任务上不如多智能体结构，但在奖励可验证性上更干净。

差别最终落到适用面：CudaPerf 适合那些结构特征确实主导性能、且基准分布与生产分布接近的 kernel 族——规则的计算密集或访存密集算子、shape 相对固定的推理路径。它不适合结构特征与性能弱相关、或生产输入分布显著漂移的场景。

五 · 不该用它的判据：四条工程红线

把上面的失效模式收敛成可操作的判据，有四条红线。

  • 正确性 oracle 覆盖不足。如果无法枚举生产输入的关键 shape/dtype 组合，任何基于“通过给定输入”的奖励都不可信。此时应先用形式化或差分测试扩大 oracle，再谈 RL；否则训练出的策略是在优化一个错误的代理目标。
  • 结构特征与 roofline 位置错配。目标 kernel 若处于计算密集区，occupancy 类特征的方向性可能为负；若处于访存密集区，arithmetic intensity 的提升空间有限。特征权重必须按 kernel 族重新校准，固定权重的结构奖励在跨族迁移时系统性偏差。
  • 基线不可比或计时噪声主导。基线未开 TF32、未用最强库、或单次测量方差与候选间差异同量级时，$\Delta\text{speed}_t$ 不携带有效排序信息，奖励退化为噪声。此时增加 RL 轮次只是放大方差。
  • 编译成本压过搜索收益。模板重、编译时间长的 kernel，多轮精化的 wall-clock 成本高于并行采样加一轮筛选；轮次的价值来自反馈因果性，若反馈只有标量加速比，轮次不产生因果信息。

这四条红线的共同点是：它们都指向“奖励信号的可信度”而非“模型能力”。CudaPerf 的方法论贡献在于把结构信息引入奖励，但结构信息的可信度是外部给定的——它依赖静态分析的正确性、特征与硬件的对应关系、以及基准分布的代表性。工程判断应当是：先验证奖励，再投入训练。

具体例子：在一个带动态 batch 的推理服务里，离线基准固定 batch=1，生产 batch 在 1 到 64 之间波动。CudaPerf 训练出的候选在 batch=1 上加速明显，但 tile 配置对小 batch 最优、对大 batch 造成 occupancy 崩塌。正确性 oracle 覆盖了 batch=1，结构奖励认可其 tile 选择，执行奖励给出高分——三条信号一致地指向一个生产上不可用的候选。这就是“离线可验证”与“生产可信”分离的代价，且无法通过增加训练轮次修复，只能通过扩大 oracle 的输入分布来修复。

六 · 迁移的工程路径：把奖励当作可替换组件

既然边界来自奖励的可信度，迁移的正确姿势是把奖励设计当作可替换、可校准的组件，而不是把论文的训练配方整体搬运。具体做法是分层验证：第一层，用论文数据集之外的算子族做零样本测试，观察结构奖励给出的排序与真实加速比排序的 Spearman 相关性；相关性低于阈值就说明特征权重不可迁移，需要按族重校准。第二层，把执行奖励的计时口径与生产口径对齐（相同基线、相同测量协议），测离线分数与线上时延的偏差分布；偏差尾部过厚说明 shape 特化已经发生。第三层，在真实流量上做影子部署，用端到端收益而非 kernel 级加速比作为最终判据。

公式上，可以把奖励拆成可校准的形式：

$$r_t=\mathbb{1}[\text{pass}_t]\cdot\big(w_e\Delta\text{speed}_t+w_s\,\hat{s}_{\text{struct}}(k_t)\big)$$

其中 $\hat{s}_{\text{struct}}$ 是按 kernel 族条件化的结构分，$w_s$ 随族变化；当某族的结构分与加速比相关性弱时，$w_s\to 0$，退化为纯执行奖励。这个退化路径本身就是工程判断：结构奖励是稠密化的工具，不是必须保留的组件。代价是校准成本——每个新算子族都需要一批带真实加速比标注的候选来估计相关性，这批标注的获取成本（编译、执行、测量）与训练本身同量级。

最后落到一个具体机制上：CudaPerf 的离线 pairwise ranking 模块在迁移时最值得保留，因为对比学习只需要强弱候选的相对关系，不依赖绝对加速比尺度；而在线 RL 阶段的奖励权重最需要重校准，因为绝对尺度绑定了基线与硬件。把 ranking 当作跨硬件可迁移的先验、把在线奖励当作需本地校准的组件，是在新硬件或新算子族上复用这套方法时最稳妥的拆分方式——反之，整体搬运训练配方而不校准奖励，失效模式会在部署阶段以离线分数与线上收益的落差形式集中兑现。
