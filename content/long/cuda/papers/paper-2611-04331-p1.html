一 · 一个 nightly 回归里的真实算子：为什么“能跑”不等于“知道时间去哪了”

设想一个在线推理服务，主干是 transformer decoder，每层里有一组融合算子：RMSNorm、RoPE、KV-cache 写入、attention 的 softmax 与 GEMM 拼接、以及最后的 MLP。工程团队已经把这些算子从 PyTorch eager 迁到 Triton 实现，并在 CI 里挂了一条 nightly 回归：每次提交都跑一遍固定 shape 的微基准，记录端到端时延与单算子加速比。某天回归报告显示 attention 融合算子比上周慢了 8%，但没有人能说清慢在哪。硬件 profiler 给出的是一张“单元占用图”：SM 的 issue slot 利用率、LSU 吞吐、DRAM 带宽占比、Tensor Core 活跃周期。图上每一格都很忙，却没有任何一格告诉你“第 37 号 warp 在等待第 12 号 warp 写完 shared memory 屏障”，也没有一格告诉你“这段 40 条指令的循环体因为寄存器 bank conflict 被拆成了两轮发射”。工程师只能靠猜：是不是 shared memory 的 swizzle 写错了？是不是 `__syncthreads()` 放早了？猜错一次，就是一次重新编译、一次重新跑基准、一次重新 review。这就是论文摘要第一句话所指的现场：LLM agents are becoming GPU kernel engineers, but they still tune kernels without seeing where the time goes.

把这条链路拆开看，痛点是叠加的。开发周期上，一个中等复杂度的融合算子从 Triton 草稿到可合入，通常要经历“写—编译—跑正确性—跑性能—读 profile—改”的循环，每轮循环的固定成本是编译时间与基准排队时间，而真正有价值的诊断信息在每轮里只增加一点点。性能上限上，手写 CUDA 的调优空间最大，但门槛也最高；Triton 把门槛降下来了，代价是编译器替你做了大量决策（layout、pipeline、寄存器分配），你能改的旋钮变少，遇到编译器“自作主张”的低效路径时缺少下手的抓手；库调用（cuBLAS、cuDNN、CUTLASS 实例）在标准 shape 上极强，但一旦 shape 特化、dtype 混合、或者需要与前后算子融合，库的边界就成了性能边界。正确性上，融合算子把多个数学步骤塞进一个 kernel，边界条件（mask、越界、NaN 传播、累加顺序）成倍增加，而微基准的输入分布往往比生产窄。可维护性上，一个为了 3% 加速而手写的 PTX 内联片段，半年后没人敢动。

二 · 旧方案的三条路，各自卡在哪一步

第一条路是手写 CUDA C++。它给你对线程块、warp、shared memory、寄存器、指令级并行的完全控制，也给你完整的调优自由度。代价是：正确性由你负责，性能由你负责，可移植性也由你负责。一个典型的坑是寄存器压力——你为了让循环体全展开而提高了 ILP，编译器却因为寄存器上限开始 spill，性能反而下降；你在源码层面看不到 spill，只能从 profiler 的 local memory 流量里反推。第二条路是 Triton。它用 tile 级抽象换取了可读性与可移植性，编译器负责 layout 转换与流水线。问题是当 kernel 变慢时，你面对的是一个多层 IR 栈：Triton IR、TTGIR、LLVM IR、PTX、SASS。你能改的是源码，而决定性能的往往是下面几层。第三条路是库调用与模板实例化（cuBLAS / CUTLASS）。它们在标准 GEMM 上接近 roofline，但融合能力有限；一旦你要把 epilogue 融进去，就得自己写 CuTe 或 CUTLASS 的定制 kernel，复杂度立刻回到第一条路。

三条路的共同缺口不在“写”，而在“看”。论文对这一缺口的表述非常精确：Hardware profilers report how busy each unit was, not where each warp's time went; intra-kernel tracers can show it, but only with hand-placed probes and a recompilation that alters the very kernel being measured. 这句话包含两个独立的断言。其一，硬件 profiler 的观测粒度是“单元级聚合”，它能告诉你 Tensor Core 的利用率是 62%，但不能告诉你某个 warp 在某个屏障上停了多久。其二，能给出 warp 级时间去向的工具（intra-kernel tracer，例如在源码里插入 `clock64()` 打点）需要手工放探针，并且必须重新编译——而重新编译会改变寄存器分配、指令调度、甚至内联决策，于是你测的已经不是你要测的那个 kernel。这是一个观测者效应：探针本身成了被测对象的一部分。

把这两点合起来，就得到一个工程上的死结。想让 agent 自动优化 kernel，就必须给它“时间去哪了”的证据；想拿到这个证据，就必须改 kernel；改了 kernel，证据就失真；失真之后，agent 基于错误证据做出的修改，可能只是在补偿探针带来的扰动。这不是精度问题，是因果问题。

三 · 反馈回路的成本结构：为什么“多跑几轮”救不了

在 agent 化的 kernel 优化里，一轮完整的反馈回路大致是：读取参考实现与基准口径 → 生成候选 → 编译 → 在给定输入上做正确性检查 → 用统一基线测时延与加速比 → 按反馈保留或回退。这条回路的吞吐由最慢的一环决定，而通常最慢的一环是“编译 + 基准测量”，不是“生成”。生成一个候选的 token 成本是可控的；编译一个 CUDA 文件的墙钟时间、以及为了统计稳定而重复测量若干次的基准时间，才是回路的主要开销。如果每一轮还要额外插入手工探针、再编译一次、再跑一次，回路成本直接翻倍，而且两次测量的对象不是同一个二进制。

更麻烦的是信号的维度不匹配。agent 拿到的是一个标量奖励：加速比。论文给出的口径是

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

其中 $T_{\text{base}}$ 是统一基线的时延，$T_{\text{agent}}$ 是候选的时延，$\text{pass}$ 是正确性门。这个奖励函数只告诉 agent“变快了还是变慢了”，不告诉它“哪一段变慢了”。在一个有几十个基本块、上百条指令的 kernel 里，标量奖励对应的搜索空间是巨大的；agent 只能做黑盒试探，而黑盒试探在编译成本高的场景下等价于随机游走。这就是为什么单纯增加轮数收益递减：每一轮买到的新信息量太少。要打破这个瓶颈，必须让每一轮的反馈从标量变成“带位置的结构化证据”——也就是把时间归因到具体的指令区间、具体的 warp、具体的屏障。

代价也要说清楚。把反馈从标量升级为结构化 trace，意味着每轮要产出并传输一份时间线数据：trace 的长度与 kernel 的执行时长、探针密度成正比，落盘与解析都要花时间与显存/主机内存。如果探针密度过高，被插桩的二进制指令数上升，测量本身的开销就会污染结果；如果密度过低，归因分辨率不够，agent 仍然只能猜。这个密度—分辨率—开销的三角权衡，是后面所有设计决策的根源。

四 · 一个具体的失败案例：融合 attention 里的屏障错位

回到开场的那个融合 attention 算子。假设 Triton 版本在某个 shape 上比上周慢了 8%。工程师的第一反应是看 profiler：DRAM 带宽占比不高，Tensor Core 利用率中等，SM issue 利用率偏高。这三个数字互相矛盾——如果 issue 利用率高而带宽不高，说明 SM 在空转等数据；但等的是什么数据，profiler 不说。工程师怀疑是 softmax 与 GEMM 之间的 shared memory 复用出了问题，于是手动在 Triton 源码里插入打点（Triton 没有原生的 warp 级打点，只能用 `tl.debug_barrier()` 加时间戳的土办法），重新编译，发现某段循环体占了 40% 的时间。于是他改写了 swizzle，重新编译，性能没变。再改，还是没变。三轮之后他开始怀疑测量本身：探针插入改变了编译器对循环的展开决策，他测到的 40% 是探针版本的 40%，不是原版的 40%。

这个案例的教训不是“工程师不够聪明”，而是“工具给错了粒度”。他需要的是：在不改源码、不重新编译的前提下，知道原版二进制里哪一段指令区间消耗了最多周期，以及这段区间与硬件 profiler 的单元占用数据如何对齐。论文的切入点正是这里：Warpline analyzes the binary to decide which events to record and inserts probes into the binary itself without recompilation or any manual step. 注意这句话里的两个动作：分析二进制来决定记录哪些事件（而不是让人来选探针位置），以及把探针插入二进制本身（而不是插入源码再编译）。前者把“探针放哪”从人工判断变成静态分析问题；后者把“观测者效应”从“重新编译改变 kernel”降级为“二进制改写只增加少量指令”。论文在 B200 上给出的口径是：跨 Triton、CuTe DSL、CUDA C++ 三种来源的 35 个 kernel，中位开销 1.2%，执行指令的中位 99.9% 保持不变。这两个数字合起来说明一件事：被测量的 kernel 基本还是原来那个 kernel。

五 · 为什么“二进制级”是这条路的必要条件，而不是优化项

要理解为什么必须下沉到二进制，得看 agent 的编辑层级。论文明确指出，agent 可能在三个层级上改 kernel：源码（CUDA C++ / Triton）、IR、PTX。如果证据生成依赖源码级探针，那么 agent 每换一个编辑层级，探针方案就得重做一遍；更糟的是，如果 agent 直接改 PTX，源码级探针根本无处安放。而二进制是所有这些层级的共同下游：无论 agent 在源头怎么改，最终都要落到一个可执行的 cubin 上。论文的表述是：Because it needs only the binary, it can regenerate this evidence for every new version of the kernel at whatever level the agent edits it (source, IR, or PTX), closing the optimization loop without human intervention. 这句话的工程含义是：证据生成被解耦成了“对任意二进制都成立的通用步骤”，而不是“针对某种源码形态的定制步骤”。

这个解耦带来两个直接收益。第一，回路可以无人化：agent 生成新版本 → 编译出二进制 → Warpline 在二进制上插桩 → 跑一次拿到 trace → 与硬件 profiler 数据在统一时间线上对齐 → 反馈给 agent。整个链条里没有“人手放探针”这一步，也就没有“人忘了放探针”或“人放错位置”的失败模式。第二，覆盖范围扩大：论文提到 Warpline 还能追踪闭源 kernel，而依赖源码探针的 tracer 做不到——因为没有源码可插。对于一个要评估“库调用 vs 自写 kernel”的 agent 来说，这个能力是必需的：你得能看见 cuBLAS 内部的时间去向，才能判断自写版本是否真的赢在关键路径上。

代价同样存在。二进制改写要处理重定位、指令长度变化、分支偏移修正；插入的探针会占用寄存器和指令槽，论文给出的 1.2% 中位开销就是这个代价的量化。更隐蔽的代价是：二进制级分析看到的是编译器优化后的形态，源码里的意图（比如“这个循环我想让它全展开”）在 SASS 里已经不可见，agent 拿到的证据是“机器实际做了什么”，而不是“人想让它做什么”。这在诊断上是优点，在归因上是难点——agent 必须学会把 SASS 级的时间去向映射回它自己能改的源码/IR/PTX 决策。

六 · 旧 tracer 的开销锚点与“统一时间线”的必要性

论文给出的对比锚点值得单独拎出来看：现有 tracer 的中位开销显著高于 Warpline，摘要级给出的数字序列里包含 1.6、13.2、4.6、32.7 这些量级（具体归属以论文正文为准，此处只作为“旧方案开销不可忽略”的定性证据）。这些数字的工程含义不是“旧工具差”，而是“旧工具的开销足以改变结论”。当一个 tracer 带来十几个百分点的开销时，agent 在插桩版本上测到的加速比，与在干净版本上测到的加速比，可能给出相反的 accept 判断——按上面的公式，$s\ge 1$ 的门槛会被系统性偏移。这就是为什么“低开销”不是锦上添花，而是让反馈回路成立的前提条件。

第二个必要条件是统一时间线。硬件 profiler 给的是单元级聚合数据，Warpline 给的是 warp 级事件序列；两者如果各自独立呈现，agent 得到的是两份无法互相印证的材料。论文的做法是 aligns the trace with hardware profiling data on one unified timeline：把“某段指令区间在什么时候执行、由哪些 warp 执行”与“同一时刻各硬件单元有多忙”放在同一条时间轴上。这样 agent 才能做真正的因果判断，例如“这段指令区间执行期间 Tensor Core 空闲、LSU 饱和，说明瓶颈在数据搬运而不是计算”，而不是从两张图里各自猜一个结论再拼起来。对齐本身有成本：两份数据的时间基准不同（profiler 的采样周期 vs 探针的时间戳），对齐需要插值或匹配，匹配误差会直接变成归因误差。这是后面部分要展开的机制，此处只需记住：统一时间线是“证据可信”的一部分，不是可视化装饰。

把这一部分的判断收束到一句工程结论上：在 agent 化 kernel 优化的回路里，真正的瓶颈不是生成候选的 token 成本，而是“每轮能买到多少可信的、带位置的时间归因”。手写 CUDA、Triton、库调用三条路都把这件事留给了人，而人做这件事的成本（手工探针 + 重新编译 + 观测者效应）恰好是回路无法自动化的原因。Warpline 的二进制级插桩把这一步的成本压到中位 1.2% 开销、99.9% 指令不变，从而让“生成—编译—测量—归因—改写”这条链条第一次可以在无人介入的情况下闭合。
