一 · 一次迭代的状态机：从任务描述到轨迹记录

AgentKernelArena 的方法论核心不是某个模型，而是一条把「任务描述 → 源码 → 二进制 → 计时数字 → 下一轮提示」串起来的固定流水线。负载层采样出一个算子与形状组合，连同参考实现、允许的 DSL 与编译预算，打包成一条任务描述；这条描述是智能体脚手架唯一的外部输入。脚手架把它渲染成提示，模型输出源码或补丁，执行层接管编译、正确性校验与计时，最后把结果写进一条固定 schema 的轨迹记录，并决定是否回灌给智能体进入下一轮。整条链路的状态转移可以写成：

$$s_{k+1}=F\big(s_k,\ \mathrm{feedback}(s_k)\big),\quad \mathrm{feedback}\in\{\varnothing,\ \text{compile\_err},\ \text{oracle\_fail},\ \text{timing},\ \text{profile}\}$$

这里 $s_k$ 是第 $k$ 轮的源码与元数据，$F$ 是脚手架（提示模板 + 上下文裁剪策略），feedback 是执行层能回灌的四类信号。注意 $F$ 不是模型本身——模型只是 $F$ 内部的一次调用，脚手架决定了历史保留多少轮、错误信息截断到多少字符、profile 摘要压缩成几行。这个区分很重要：同一个模型换一套脚手架，轨迹长度和最终加速比都会变，所以论文要求所有智能体共享同一脚手架接口，否则跨系统比较失去意义。代价体现在 token 上：每一轮回灌都要把上一轮的源码、错误文本和计时数字重新塞进上下文，轮数越多上下文越长，而编译预算轮数在协议里是固定的，因此单次任务的 token 成本近似正比于预算轮数与每轮反馈长度的乘积。一个具体例子：首版 kernel 编译失败，回灌的是编译器报出的行号与符号冲突信息；智能体据此改掉共享内存声明后编译通过，但正确性 oracle 在边界形状上报越界，回灌的是失败用例的索引与期望/实际输出片段——这两类反馈的文本形态完全不同，脚手架必须为它们分别设计模板，否则模型会把编译错误当成数值错误来修。

二 · 单轮提示与脚手架的分工：谁承担迭代

论文把智能体层抽象成统一接口，接口之下允许两种极端形态。单轮提示是最薄的一层：任务描述进、一次生成出，没有回灌，智能体拿到的是零反馈的盲写。它的代价结构非常干净——token 成本最低、时延最短，但把全部风险压在首版生成上，编译失败即整条用例归零。脚手架形态则把迭代责任从模型转移到外层循环：模型每次只负责一次修改，脚手架负责决定喂什么、喂多少、什么时候停。这两种形态在同一口径下跑，恰好暴露了「迭代能力」与「单次生成能力」的差别，这也是论文把编译失败与正确性失败单独计入、不进入计时阶段的原因——如果失败样本被静默丢弃，单轮提示的高失败率会被加速比均值掩盖。伪代码层面，脚手架的主循环大致是：

$$\textbf{for } k \leftarrow 1 \textbf{ to } B:\ \ c_k \leftarrow \mathrm{compile}(s_k);\ \ \textbf{if } \neg c_k.\mathrm{ok} \textbf{ then } s_{k+1}\leftarrow F(s_k, c_k.\mathrm{err});\ \textbf{continue}$$

其中 $B$ 是编译预算轮数。这个循环的工程判断点在于：编译失败的分支不消耗计时资源，但消耗轮数与 token，所以一个反复编译不过的智能体会在预算耗尽前把上下文塞满错误日志，反而降低后续修复概率。一个具体例子是 Triton 路径上的典型失败——block size 写成非 2 的幂导致编译期断言失败，回灌文本很短，模型容易一次修对；而 CUDA 路径上模板实例化失败的报错动辄数百行，脚手架若不截断，单轮 token 就会吃掉预算的显著比例。这就是为什么论文强调脚手架接口统一：截断策略本身就是一个隐性的性能变量。

三 · 正确性 oracle 与计时的耦合：失败样本如何不污染加速比

执行层在编译通过后先跑正确性 oracle，再进入计时。这个顺序不是随意的：如果把计时放在正确性之前，一个输出全零但跑得极快的 kernel 会拿到虚高的加速比。oracle 以参考实现为基准，对每个用例比对输出；论文明确把正确性失败单独计入、不进入计时阶段，于是加速比统计的分母只包含「编译通过且正确」的样本。这带来一个统计口径上的代价：通过率与加速比必须同时报告，否则高失败率下的均值会失真——假设十个用例里三个编译失败、两个正确性失败，剩下五个的平均加速比再漂亮，也不能代表智能体的真实能力。计时本身采用多次运行取中位数，中位数而非均值的选择是为了抵抗首次运行时的冷启动与偶发调度抖动；但材料未给出运行次数与硬件型号，因此计时噪声的置信区间无法量化，这是复现时首先要补齐的口径。一个具体例子：某 kernel 在分布内形状上正确性通过、计时显示加速比低于基线，若开启 profile，回灌的热点信息指向全局内存访问未合并，智能体据此调整分块与访存模式后再次计时——这一轮修改的收益必须与上一轮的错误修复区分开记录，否则轨迹里无法判断哪类反馈真正驱动了性能提升。耦合的另一个代价是时间：每个用例都要跑正确性加多次计时，单用例墙钟时间远高于一次编译，预算轮数乘以用例数就是评测的总时延下限。

四 · profile 信号作为可选反馈：信息量与开销的权衡

脚手架接口把 NCU/SASS profile 列为可选项，这个「可选」二字承载了方法上的关键分歧。开启 profile 时，智能体拿到的不只是「快或慢」，而是热点函数、访存模式、occupancy 之类的结构化摘要；关闭时，它只能从计时数字反推瓶颈。前者信息量大，但采集本身有开销——NCU 需要串行化、多次 replay 才能拿到稳定计数，单用例的 profile 时间可能超过计时本身，且摘要压缩进提示要占 token。后者零开销，但把诊断责任完全推给模型对数字的猜测。从消融角度看，是否回灌 profile 是一个天然的可消融维度，论文材料未给出该消融的数值，但机制上的判断是清楚的：profile 对「已经正确但不够快」的用例价值最大，对编译失败与正确性失败几乎无用，因此合理的脚手架应当按反馈类型分流，只在计时阶段之后才附上 profile 摘要。一个具体例子：计时显示加速比低于基线且差距不大时，profile 摘要指出 shared memory bank conflict，智能体改 padding 后收益明显；而若差距极大，profile 往往指向算法层面的问题（如未做 tiling），此时模型需要的是重构而非微调，profile 的细粒度信息反而可能诱导局部修补。这里的性能代价是双重的：profile 采集拉长单轮时延，摘要占用 token 预算，两者都直接压缩可用的迭代轮数。

五 · 分布内与分布外的同一流程：泛化差距如何在机制上产生

同一智能体、同一脚手架、同一执行层，先在分布内形状上跑完整流程，再在分布外形状上重跑一遍，最后把两组加速比相减得到泛化差距。机制上值得注意的是：两次运行之间智能体不携带任何跨任务的持久状态（材料未给出跨任务记忆的设计），因此分布外的表现完全取决于模型把分布内学到的修改策略迁移到新形状的能力。这就把「记住模板」与「真正会优化」在流程层面分开了——前者在分布内形状上加速比高、在分布外骤降，后者两组接近。公式上，差距是两组平均加速比之差：

$$\mathrm{Gap}=\frac{1}{|\mathcal{D}_{\mathrm{in}}|}\sum_{i\in\mathcal{D}_{\mathrm{in}}}\frac{t^{\mathrm{base}}_i}{t^{\mathrm{agent}}_i}-\frac{1}{|\mathcal{D}_{\mathrm{out}}|}\sum_{j\in\mathcal{D}_{\mathrm{out}}}\frac{t^{\mathrm{base}}_j}{t^{\mathrm{agent}}_j}$$

这个定义的工程脆弱点在于分母：$|\mathcal{D}_{\mathrm{out}}|$ 的构造方式决定了差距的可比性。如果分布外形状只是把分布内形状的某一维放大，那么一个对形状参数做自适应分块的智能体很容易迁移，差距被系统性低估；如果分布外引入了分布内从未出现的算子组合，差距又会混入「任务难度差」而非纯粹的迁移能力差。论文材料未给出构造细节，这是复现时最需要补齐的一环。代价方面，分布外集合意味着双倍的用例数与双倍的评测时延，且分布外用例的通过率通常更低，失败样本单独计入后，两组加速比的分母规模可能不对称，直接相减的统计意义需要谨慎对待。一个具体例子：分布内是方阵乘方阵，分布外是长宽比悬殊的矩阵乘，前者上调好的分块参数在后者上导致 occupancy 骤降，加速比从高于基线掉到低于基线，差距因此为正且数值可观——这正是该指标想要捕捉的信号。

六 · 轨迹记录与防作弊：固定 schema 的工程约束

三层之间通过固定 schema 的轨迹记录连接，这条记录同时是评测产物和防作弊基础设施。每一轮都要落盘：轮次索引、源码哈希、编译状态、正确性结果、计时中位数、是否附 profile、消耗的 token 与墙钟时间。固定 schema 的直接收益是不同智能体可以在同一口径下逐轮对齐比较——不是比最终加速比，而是比「第几轮修好编译」「第几轮通过正确性」「第几轮开始产生正加速」。代价是记录本身的存储与序列化开销，以及 schema 变更带来的兼容成本；更隐蔽的代价是它约束了脚手架的灵活性，任何自定义的反馈格式都必须映射回 schema 字段，否则跨系统比较失效。防作弊的关键在于隐藏测试集：泛化差距一旦被当作优化目标，智能体就可能反向过拟合分布外集合，因此分布外用例的可见性必须受控，轨迹记录里不应泄露分布外形状的具体参数。一个具体例子：若脚手架把分布外用例的完整形状写进任务描述，模型可以直接针对该形状硬编码分块大小，此时差距指标归零但迁移能力并未提升——这正是论文强调统一接口与固定 schema 的深层原因，它让「看到了什么」成为可审计的事实，而不是各系统自说自话的配置。工程判断落在这里：评测协议必须同时锁定硬件、驱动、编译 flag 与预算轮数，任何一项松动都会让轨迹记录失去横向可比性，而材料未给出这些锁定值，意味着直接引用其结论前必须先补齐这套口径。

泛化差距作为目标函数时的失效边界与流水线代价

泛化差距公式本身是一个无界差分，$$\mathrm{Gap}=\frac{1}{|\mathcal{D}_{\mathrm{in}}|}\sum_{i\in\mathcal{D}_{\mathrm{in}}}\frac{t^{\mathrm{base}}_i}{t^{\mathrm{agent}}_i}-\frac{1}{|\mathcal{D}_{\mathrm{out}}|}\sum_{j\in\mathcal{D}_{\mathrm{out}}}\frac{t^{\mathrm{base}}_j}{t^{\mathrm{agent}}_j}$$其统计性质取决于两组集合的基数与形状分布是否可比。若 $\mathcal{D}_{\mathrm{out}}$ 只含少量形状，单个用例的计时抖动会以 $1/|\mathcal{D}_{\mathrm{out}}|$ 的权重放大到指标上，中位数计时只能压住单点噪声，压不住集合过小带来的方差。更关键的是，一旦把 Gap 写进智能体的优化目标而非仅作报告项，分布外集合就从"考卷"变成"训练信号"，智能体可以通过反复试探该集合的计时反馈反向拟合它——这与固定形状过拟合是同一失效机制，只是换了个集合。因此工程上必须把 $\mathcal{D}_{\mathrm{out}}$ 拆成可见的反馈子集与不可见的隐藏子集，前者进脚手架回灌，后者只进最终计分。

流水线各步的代价并不对称。编译步的代价是墙钟时间与失败率：编译失败与超时按失败计入、不进入计时，这一步的预算是硬约束，轮数耗尽即终止，因此编译预算直接决定智能体可探索的修改次数上限；正确性 oracle 步的代价是参考实现的执行开销与边界用例覆盖度，越界类失败往往只在特定形状触发，回灌失败用例是让智能体定位问题的唯一通道；计时步的代价是多次运行取中位数所需的设备占用，若同时报告通过率则还需额外统计。三者叠加，单用例的评测成本随迭代轮数线性增长，而 profile 信号（NCU/SASS）的采集开销显著高于纯计时，开启 profile 等于用设备时间换反馈信息量——这是一次明确的预算再分配，而非免费增强。

失效条件集中在两处。其一是失败率失真：编译失败与正确性失败不计入计时，若某智能体大量提交不可编译或不正确的 kernel，其进入计时的样本是被筛选过的子集，加速比均值会系统性偏高，必须与通过率并列报告才能读出真实能力。其二是轨迹可比性依赖固定 schema：不同智能体在同一口径下可比的前提是工具链版本、驱动、硬件与计时次数全部锁定，任何一项漂移都会让两组加速比之差混入环境噪声而非泛化信号。具体到一个边界形状用例：智能体首版 kernel 在分布内形状通过，切到分布外维度时越界，oracle 回灌失败用例后其加入边界判断并通过，但计时显示加速比低于基线——这说明"能跑对"与"能跑快"在分布外是两件事，泛化差距捕捉的正是后者，而前者只能靠通过率兜底。
