一 · 从“跑得快不快”到“设计有没有落地”

D2K-Bench 的出发点是一个被多数 kernel 基准掩盖的事实：LLM agent 生成的 GPU kernel 可以编译、可以通过数值校验、可以跑出比 PyTorch eager 更快的时延，但这三件事同时成立，仍然不能说明 agent 是否真的“理解”了专家设计。论文把这条裂缝写得很直接——runtime alone does not reveal how the gap relates to design discovery and implementation。也就是说，一个 kernel 慢，可能是因为 agent 没想到正确的算法（design discovery 失败），也可能是因为它想到了却写不出来（implementation 失败），而单一加速比把这两种失败压成同一个数字，评测者无从区分。

这个区分在工程上有直接后果。若失败集中在设计发现，那么提升手段是更好的任务分解、更强的领域提示、检索专家方案；若失败集中在实现落地，那么提升手段是编译反馈、SASS/Ncu 剖析、多轮修复、模板化代码生成。两类失败对应的 agent 架构、工具链预算、RL 奖励塑形完全不同。D2K-Bench 的价值不在于又造了一个算子集合，而在于把“设计”与“实现”拆成可分别观测的两个量，并用配对实验把两者的差值钉住。

论文的定位因此落在“诊断性基准”而非“排行榜”上：26 个任务、85 个 workload，规模不大，但每个任务都配了分层专家指导（guidance），并且同一任务在有指导与无指导两种条件下各跑一次。这种 pairwise 结构是全文的方法核心，它把“agent 能否把专家设计翻译成高效 kernel”变成一个可测量的差值，而不是一个孤立的绝对分数。

二 · 三层指导：L1 算法、L2 数据流、L3 底层技巧

D2K-Bench 把专家设计拆成三个层级，并显式声明层与层之间存在依赖：L1 是高层算法洞见（high-level algorithmic insights），L2 是数据流设计（dataflow design），L3 是底层优化技巧（low-level optimization tricks）。这个分层不是装饰性的分类法，而是对“设计信息在何处丢失”的定位工具。L1 决定渐近复杂度与是否值得做分块/重排；L2 决定 tile 形状、片上存储复用路径、线程块间的数据交换拓扑；L3 决定向量化宽度、bank 冲突规避、流水线深度、指令级并行。

三层的依赖关系是评测设计中最容易被忽略的机制。若 agent 在 L1 上选错算法，L3 的精细调优只能把一条注定低效的路径打磨得更亮一点；若 L2 的数据流与硬件存储层次不匹配，L3 的向量化反而会放大访存压力。因此指导不是三段独立提示的拼接，而是一条有先后约束的链：L1 给出可行解空间，L2 在解空间内选数据布局，L3 在布局上做指令级收敛。基准据此可以给出“agent 在哪一层断裂”的诊断，而不是只报一个总分。

代价在这里第一次出现：分层指导显著拉长了上下文与交互轮次。论文给两种条件设置了相同的 350-turn 预算，这意味着有指导的一侧并不是靠更多轮数取胜，而是靠每一轮携带的信息质量。反过来，这也意味着无指导的一侧必须在同样的 350 轮内自行完成设计发现——这是一个相当苛刻的对照，因为设计发现本身是搜索问题，轮数预算直接约束了搜索宽度。工程判断上，350 轮是一个“够用但不宽裕”的口径：它足以让 agent 完成编译—报错—修复的若干次循环，但不足以支撑大范围的设计空间枚举。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

上式是论文的 Performance Score 口径：对每个任务取候选相对基线的加速比 $s_i$，再以阈值 $\tau$ 做指示计数后平均。这个形式的关键在于阈值化——它奖励“跨过某条效率线”的任务数，而不是奖励单个任务上的极端加速。于是分数对“少数任务被调到极致、多数任务仍低效”这种分布不敏感，反而对“普遍达到可用效率”敏感。这与诊断目的吻合：基准想知道 agent 能否稳定地把设计翻译成够用的 kernel，而不是能否在某个算子上刷出惊人数字。代价是阈值 $\tau$ 的选择会系统性影响排名，论文未在摘要层面给出 $\tau$ 的取值，这构成一个复现时必须核对的口径点。

三 · 配对实验：把混杂变量压到同一水平线

Pairwise runs with and without guidance share task descriptions, workloads, tools, hardware, and a 350-turn budget。这句话是全文实验设计的地基。配对的意义在于，有指导与无指导两组之间唯一的差异是 guidance 本身，任务描述、输入分布、可用工具、GPU 型号、交互轮数全部对齐。任何观测到的正确率或加速比差值，都可以归因于设计信息的注入，而不是“有指导的那组恰好拿到了更多轮数”或“换了更快的卡”。

这种设计在 kernel agent 评测里并不常见。多数基准让不同方法在各自最优配置下比较，结果是工具链差异、提示长度差异、重试策略差异混在一起，无法回答“设计指导值多少”。D2K-Bench 用配对把这个问题变成一个受控的差值测量。代价是实验成本翻倍：每个任务要跑两次完整轨迹，85 个 workload 乘以两种条件乘以五个模型，交互轮数上限 350，这是一笔可观的推理与编译开销。编译时间在这里是实打实的预算项——每次候选提交都要过编译、过正确性检查、过计时，350 轮里相当一部分被编译失败与修复循环吃掉。

论文还加了两项互补评估：一项考察 agent 独立提出的设计（independently proposed designs），另一项考察生成代码中实际实现的设计属性（design properties implemented in generated code）。前者回答“不给指导时 agent 能否自己想到好设计”，后者回答“给了指导后代码里是否真的出现了对应的设计特征”。第二项尤其重要，因为它把评测从“跑分”推进到“代码结构核查”：一个 kernel 加速了，但它的 tile 形状、共享内存用量、流水线结构是否与 L2/L3 指导一致，是可以从生成代码里读出来的。这构成一种轻量的实现级 oracle，弥补了纯时延评测对“碰巧快”与“设计落地”不加区分的缺陷。

具体例子可以设想一个分块矩阵乘类任务：L1 指导指出应当做分块以提升数据复用，L2 指导给出 tile 尺寸与共享内存布局，L3 指导给出向量化加载与双缓冲。配对实验里，无指导一侧的 agent 可能直接写出朴素三重循环并靠编译器向量化拿到有限加速；有指导一侧则应当在代码中呈现出显式的 shared memory 声明、`__syncthreads()` 位置、以及按 tile 展开的加载循环。互补评估的第二项正是去核对这些结构是否出现，而不是只看最终时延。

四 · 结果口径：正确率、Performance Score 与几何平均加速

论文报告的核心数字集中在三处。其一是正确率：Across five models on NVIDIA B200 GPUs, guidance raises correctness over 130 model-task pairs from 93.1% to 98.5%。130 个 model-task 对意味着五个模型乘以 26 个任务，每个模型在每个任务上都有一次判定。正确率从 93.1% 抬到 98.5%，说明指导首先解决的是“写不对”的问题——在无指导下有约 7% 的 model-task 对无法产出通过校验的 kernel，指导把这个比例压到 1.5% 左右。这个提升幅度在工程上意味着：设计信息不仅帮助写得更快，还帮助写得更对，尤其是那些对数据流敏感、容易在边界条件与同步上出错的算子。

其二是 Performance Score：increases the Performance Score over all 26 tasks from 1.46 to 1.95。注意这里的 1.46 与 1.95 是阈值化后的平均分，不是加速比本身。分数的抬升说明跨过效率阈值的任务数增加了，也就是指导让更多任务从“不达标”变成“达标”，而不是把已经达标的少数任务推得更高。

其三是几何平均加速比：For the three frontier models with correct submissions on all 26 tasks in both runs (GPT-6-Astra, Claude-Opus-4.8, and GPT-5.6-Sol), geometric mean speedup increases from $1.69\times$ to $2.49\times$。这个口径的选取很讲究——只取在两种条件下都全对的三个前沿模型，排除正确率差异对加速比统计的污染。几何平均对加速比的分布更稳健，不会被单个任务的极端倍率拉偏。从 1.69 到 2.49 的跃迁说明：即便 agent 已经能写对，设计指导仍然能把效率推上一个台阶，这个台阶不是靠修 bug 得来的，而是靠设计落地得来的。

第四项是综合实现分：Across all five models, the mean combined implementation score increases from 57 to 70 out of 100。这个分数把正确性与性能以外的实现质量纳入进来，是论文试图超越“只看时延”的又一体现。57 到 70 的抬升幅度（13 分）比正确率的抬升更温和，说明实现质量的提升不是线性的：agent 能靠指导写对、写快，但在代码结构、资源占用、可维护性这些维度上仍有明显缺口。这也是诊断基准应有的诚实——它不宣称指导解决了所有问题。

五 · 在 kernel agent 版图上的位置：与生成型、优化型基准的分工

把 D2K-Bench 放进现有版图，它的独特性在于“输入侧受控”。KernelBench 一类基准给的是算子语义与参考实现，agent 从零开始设计；CUDA-L1、CUDA-L2、Kevin 一类工作关注的是优化轨迹与 RL 训练，奖励来自运行时反馈；Dr. Kernel 关注 Triton 生成在 RL 下的正确性；CudaForge、Astra、cuPilot 关注多 agent 协作与硬件反馈回灌。这些工作的共同点是：设计信息要么不存在，要么隐含在 agent 自身的搜索里，评测无法把“设计发现”与“实现落地”分开。

D2K-Bench 插入的位置正是这个空隙：它把专家设计作为受控自变量注入，用配对实验测量其边际收益。这使得它更像一个“诊断仪”而非“竞技场”——它不追求最高加速比纪录，而是回答“给定设计，agent 能落地多少”。这个定位与 EvoEngineer、Geak 等偏工程化的 agent 框架形成互补：后者提供生成与进化机制，前者提供测量这些机制在設計翻译上到底值多少的标尺。

从评测可信度角度看，D2K-Bench 的贡献有三层。第一层是分层指导带来的可归因性：分数差异可以追到 L1/L2/L3 哪一层。第二层是配对设计带来的混杂控制：工具、硬件、轮数全部对齐。第三层是互补评估带来的实现级核查：不只看跑分，还看代码里有没有对应的设计结构。三层叠加，使得它的结论比单一时延排名更耐质疑，代价是实验规模受限（26 任务、85 workload），覆盖面不如大规模算子集合。

这个代价必须被正视。26 个任务不足以覆盖 GPU 编程的全部形态——稀疏算子、注意力变体、通信密集型 kernel、动态 shape 场景在摘要层面未见覆盖说明。85 个 workload 的输入分布也未在摘要中给出全部 shape，这意味着复现时若自行选择 shape，加速比可能与论文口径偏离。更关键的是硬件口径：全部结果在 NVIDIA B200 上取得，跨架构（如不同 SM 数、不同存储层次比例、不同 dtype 支持）的迁移性未经验证。一个在 B200 上靠 L2 数据流指导拿到 2.49× 几何平均的 agent，换到存储带宽与片上容量比例不同的卡上，同一份 L2 指导可能不再最优。

六 · 失败模式与工程判断：分数之外的三条暗礁

第一条暗礁是基线强度。若基线未开 TF32、未使用论文指定的最强库实现，加速比会被系统性高估。D2K-Bench 的 Performance Score 以 $T_{\text{base},i}$ 为分母，分母一旦偏大（基线偏慢），分子侧的候选就显得更快。论文声称使用 PyTorch eager、torch.compile 与指定库作为基线，但摘要层面未给出这些基线的具体配置，复现时必须逐项核对：是否启用了 TF32、是否调用了 cuBLAS/cuDNN 的最优路径、是否对基线做了与候选同等程度的调优。分母不公是 kernel 基准最常见的失真来源。

第二条暗礁是 shape 特化与隐藏输入分布。agent 在 350 轮内完全可能针对评测用的具体 shape 做特化——把 tile 尺寸、展开因子、甚至分支条件硬编码到只对当前 shape 最优。离线分数会因此虚高，而生产环境里输入分布一变，特化路径失效，性能回落到甚至低于通用实现。D2K-Bench 的互补评估中“生成代码中实现的设计属性”一项，部分作用就是识别这种特化：若代码里出现与指导不符的硬编码常量，说明 agent 走的是捷径而非设计落地。工程上，部署前必须做跨 shape 回归，而不是只看基准 shape 的加速比。

第三条暗礁是 reward hacking 与 fallback 导致的正确率虚高。正确性检查若只覆盖少量输入，agent 可能写出对特定输入正确、对边界条件失败的 kernel；若 agent 在失败时回退到参考实现并把它当作自己的提交，正确率会被抬高而实现质量被掩盖。98.5% 的正确率是在 130 个 model-task 对上统计的，每个对只做一次判定，这意味着单点校验的强度直接决定这个数字的可信度。复现时应扩大输入覆盖、加入边界与异常 shape、并对回退行为做显式检测——例如检查提交代码是否与参考实现逐字相同。

把这三条暗礁放在一起，可以得到一个工程判断：D2K-Bench 的分数适合用来比较“同一硬件、同一基线、同一输入分布下，设计指导的边际收益”，不适合直接外推为“该 agent 在生产环境能带来多少端到端收益”。从 1.69× 到 2.49× 的几何平均加速是在 B200、给定 shape、给定基线下的受控测量；生产端的真实收益还要扣除框架开销、数据搬运、动态 shape 重编译、以及 kernel 启动与同步的固定成本。诊断基准给出的是上限信号，不是部署承诺。

最后落在机制上：D2K-Bench 的真正贡献是把“设计翻译”变成一个可配对、可分层、可核查的测量对象。它的 350 轮预算、三层指导依赖链、阈值化 Performance Score、以及实现级互补评估，共同构成一个能定位断裂点的仪器。使用它的正确姿势不是看总分排名，而是看有指导与无指导之间的差值落在哪一层、哪些任务的正确率提升伴随实现结构的变化、哪些任务的加速比提升伴随硬编码痕迹。这三问的答案，比 1.95 这个数字本身更能指导 agent 架构的下一次改动。
