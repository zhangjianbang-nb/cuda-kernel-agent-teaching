一 · 从一次线上回归说起：固定形状的胜利与真实流量的溃败

设想一个典型的推理服务：某个 Transformer 变体在 decode 阶段有一个融合算子，负责 LayerNorm、残差加与一次小规模的矩阵乘。团队里的性能工程师花了三周，用 CUDA C++ 手写出一个针对 batch=1、序列长度 2048、hidden=4096 这一组形状高度特化的 kernel，把三个原本独立的 kernel 合并成一个，中间结果留在寄存器与 shared memory 里，省掉了两次 global memory 往返。在压测环境里，这个手写 kernel 相对框架自带的朴素实现拿到了可观的加速比，于是被合入主干。上线两周后，流量结构变了：序列长度分布向短请求偏移，batch 因为连续批处理而动态变化，同一个 kernel 在 seq=137、batch=3 这类形状上开始频繁触发尾块分支，寄存器压力导致 occupancy 掉到很低，端到端时延反而比库调用更差。这不是虚构的极端案例，而是 GPU kernel 工程长期存在的结构性矛盾：**优化的收益与优化的适用范围几乎总是同向收缩**。

这个矛盾在工程上表现为一个尖锐的问题：当性能工程师针对一组已知形状把 kernel 打磨到极致时，他实际上是在用「形状特化」换取「指令级与访存级的效率」。特化的代价是泛化能力的丧失，而真实部署环境的形状分布是漂移的、长尾的、不可完全枚举的。手写 CUDA 的这条路径，其痛点不在于工程师不够强，而在于人力所能覆盖的形状空间与真实流量所呈现的形状空间之间存在数量级差距。这正是 AgentKernelArena 这类工作出现的问题现场：不是「LLM 能不能写 kernel」这个孤立问题，而是「在形状分布持续漂移的生产环境里，谁来持续产出既正确又足够快、还能迁移到未见形状的 kernel」。

二 · 三条旧路径的各自天花板：手写、Triton、库调用

在 LLM 智能体介入之前，GPU kernel 工程的主流做法可以粗分为三条路径，每条路径都有自己的性能上限与工程代价，且这些代价的性质互不相同。

手写 CUDA C++ 的性能上限最高，工程师可以直接控制线程块划分、shared memory 布局、warp 级原语、异步拷贝与流水线深度，理论上可以逼近硬件的 roofline 拐点。代价是开发周期以周计，且每一行代码都携带正确性风险：越界访存、竞态、同步缺失、bank conflict 引发的隐性性能塌陷，都需要借助 compute-sanitizer、NCU 逐层排查。更麻烦的是可维护性——一个为特定形状调优的 kernel，其分块参数、寄存器预算、展开因子全部是硬编码的经验值，当上游模型结构或形状分布变化时，这些常量失去意义，维护者往往只能重写而非修改。性能上限高，但**有效性能上限只在它被调优的那个形状邻域内成立**。

Triton 把开发周期压缩了一个量级：用块级编程模型（block-level programming）替代线程级手工编排，编译器负责 layout 推导、向量化与 shared memory 分配，工程师只需描述 tile 的形状与循环结构。这让「一天内写出一个可用的 fused kernel」成为常态，也让自动调优（autotune）可以把 tile size、num_warps、num_stages 作为搜索维度。代价是性能上限被 DSL 的表达能力所约束：某些需要精细控制寄存器分配、warp 间通信或非规则访存的算子，Triton 生成的代码会留下可观测的差距；autotune 本身也有编译时间与首次运行延迟的成本，配置空间一大，编译预算就成了瓶颈。Triton 的性价比很高，但它把「形状特化」从手写常量变成了 autotune 的配置选择，**特化的本质没有消失，只是被自动化了**。

库调用（cuBLAS、cuDNN、CUTLASS 实例化的 GEMM）是三者中最稳健的：正确性由厂商保证，维护成本接近于零，且在标准形状上性能极强。代价是灵活性：库的启发式调度在非标准形状、融合机会、特殊数据类型上会退化为保守选择；跨算子的融合（比如 GEMM 后接激活再接归一化）需要工程师自己拆成多次库调用，中间结果被迫落回 global memory，带宽开销无法避免。库调用的性能上限是「厂商已经枚举过的形状与融合模式」的上限，**任何库没有覆盖的组合，其性能就退回朴素实现**。

三条路径的共同点是：它们都把「优化」这件事绑定在一个人力可及的搜索范围上——工程师的经验、autotune 的配置网格、厂商的枚举清单。当形状分布是静态的、可枚举的，这个绑定是合理的；当形状分布是动态的、长尾的，这个绑定就成为瓶颈。这不是工具不够好，而是**搜索的执行者（人）与搜索的空间（形状 × 融合模式 × 硬件配置）之间的规模失配**。

三 · 为什么「非改不可」：四个痛点的耦合

把痛点拆开看，会发现它们不是并列的四个问题，而是相互耦合、彼此放大的。

开发周期是最直观的：一个融合算子从需求到合入，手写路径以周计，Triton 路径以天计。但开发周期的真正代价不在首次开发，而在**每次形状分布漂移后的重新调优**。生产环境的形状分布不是一次性给定的，它随流量结构、上游模型版本、批处理策略持续变化。这意味着调优不是一次性投入，而是一个持续发生的成本项，其频率与形状漂移的频率成正比。人力无法跟上这个频率，于是实际工程中大量算子停留在「能用但非最优」的状态。

性能上限的问题在于它是局部的。一个手写 kernel 在目标形状上可能逼近 roofline，但在相邻形状上可能因为尾块利用率下降、occupancy 塌陷而大幅退化。用 roofline 的语言说，kernel 的实际吞吐取决于它在给定形状下能达到的 arithmetic intensity 与 memory bandwidth 的匹配程度；形状一变，这个匹配关系就变，而硬编码的分块参数不会随之调整。性能上限的「上限」二字必须加上定语：**在调优形状邻域内的上限**。

正确性是最容易被低估的一项。手写 CUDA 的正确性验证依赖参考实现逐元素比对，而边界形状（非对齐维度、极小 batch、极端序列长度）恰恰是最容易出错、也最容易被测试集遗漏的地方。更隐蔽的是，一个在测试形状上通过比对的 kernel，可能在未见形状上触发越界——因为测试集本身就是形状特化的。这与评测基准的问题是同一个问题的两面：**形状特化的测试集只能验证形状特化的正确性**。

可维护性则是前三个痛点的复利。硬编码常量的 kernel 难以被他人修改，修改者需要重建原作者的全部调优上下文；autotune 的配置在硬件换代后需要重新搜索；库调用的融合缺失需要工程师手工拼接。可维护性差的直接后果是：团队倾向于「不动能跑的代码」，于是性能优化停滞，技术债累积。

$$\mathrm{Cost}_{\mathrm{total}} = \underbrace{C_{\mathrm{dev}}}_{\text{首次开发}} + \underbrace{f_{\mathrm{drift}} \cdot C_{\mathrm{retune}}}_{\text{形状漂移引发的重调优}} + \underbrace{C_{\mathrm{verify}} \cdot p_{\mathrm{edge}}}_{\text{边界形状的正确性验证}}$$

这个式子想说明的是：当形状漂移频率 $f_{\mathrm{drift}}$ 上升时，第二项会主导总成本，而人力路径的 $C_{\mathrm{retune}}$ 是刚性的、不可压缩的。这正是「非改不可」的工程判断依据——不是手写 CUDA 不好，而是**人力调优的边际成本无法随形状空间的扩张而下降**。要打破这个刚性，需要把调优的执行者从人换成能大规模并行搜索、并能从执行反馈中迭代的东西。这就是 LLM 智能体介入的动机，也是 AgentKernelArena 把「泛化」作为一等评测维度的现实基础：如果智能体只是在固定形状上刷出高加速比，它不过是把手写工程师的形状特化行为自动化了一遍，痛点一个都没解决。

四 · 固定形状基准的隐性代价：排行榜分数与部署收益的脱钩

在智能体介入之后，旧的评测方式暴露了新的问题。KernelBench 系的基准以少量固定算子、固定形状计分，智能体在这些公开用例上迭代多轮，很容易收敛到「针对这组形状的模板」。这在机制上是可以理解的：智能体的搜索过程由执行反馈驱动，而反馈信号只来自固定形状的计时，于是搜索自然收敛到该形状的最优解。问题在于，这个最优解在未见形状上的表现完全没有被计分。

AgentKernelArena 的核心度量是把这件事显式化：分别统计分布内与分布外的平均加速比，取差值作为泛化差距。

$$\mathrm{Gap}=\frac{1}{|\mathcal{D}_{\mathrm{in}}|}\sum_{i\in\mathcal{D}_{\mathrm{in}}}\frac{t^{\mathrm{base}}_i}{t^{\mathrm{agent}}_i}-\frac{1}{|\mathcal{D}_{\mathrm{out}}|}\sum_{j\in\mathcal{D}_{\mathrm{out}}}\frac{t^{\mathrm{base}}_j}{t^{\mathrm{agent}}_j}$$

这个式子的工程含义比它的数学形式更重要。第一项是智能体在「它被允许看到的形状」上的加速比，第二项是它在「它没见过的形状」上的加速比。如果智能体真正学会了优化（理解了分块、访存、occupancy 的一般原理），两项应当接近，Gap 小；如果智能体只是记住了模板（把公开用例的形状常量硬编码进 kernel），第一项会显著高于第二项，Gap 大。**Gap 把「记住」与「会」这两种在单一分数下无法区分的能力分开了**。

这里有一个必须点明的代价：分布外集合的构造本身是一项工程。如果分布外形状与分布内形状差异过小，Gap 无法区分模板记忆与真实泛化；如果差异过大（比如维度数量级跳变），智能体的失败可能源于任务本身超出了合理迁移范围，而非过拟合。更棘手的是，一旦 Gap 成为排行榜的优化目标，智能体可能反向过拟合分布外集合——这与机器学习里「在测试集上调参」是同一个陷阱。因此分布外集合必须保留隐藏部分，且构造方式不能公开到可以被智能体针对性搜索的程度。这是评测设计者要承担的额外工程成本，也是旧基准没有暴露、新基准必须面对的问题。

执行层的口径同样值得注意：编译失败与正确性失败单独计入、不进入计时阶段。这个设计的理由是避免失败样本污染加速比统计——一个编译不过的 kernel 没有计时，若把它当作零加速比计入均值，均值会失真。但代价是：如果智能体的失败率很高，只报告通过样本的加速比会高估其真实能力。因此完整的评测报告必须同时给出通过率与加速比，**单看加速比均值是有偏的**。这与泛化差距是同一类问题：单一聚合指标总会掩盖分布的形状。

五 · 一次多轮迭代的完整轨迹：反馈回灌如何改变搜索方向

要理解旧方案为什么在「持续调优」这件事上失效，看一次 AgentKernelArena 脚手架下的完整迭代轨迹最直观。负载层给出某算子在分布内形状上的任务描述，连同参考实现与约束（编译预算、允许的工具链）。智能体生成首版 kernel 源码。

第一轮：执行层编译失败，回灌编译错误。智能体修正语法与类型问题，编译通过。第二轮：正确性 oracle 发现边界形状越界——参考实现逐元素比对在某个非对齐维度上失败，回灌失败用例的具体形状。智能体加入边界判断与 mask，正确性通过。第三轮：计时显示加速比低于基线，若开启 profile，回灌热点信息（访存瓶颈、occupancy 限制），智能体调整分块大小与访存模式。预算耗尽后记录该用例结果。随后同一智能体在分布外形状上跑同样流程，最终报告同时给出两组加速比与泛化差距。

这条轨迹揭示了旧方案与智能体方案在机制上的根本差异：旧方案的调优是**一次性的人力决策**，工程师在写代码前就决定了分块参数与优化策略，之后的反馈只有「跑得快不快」这一条粗粒度信号；智能体方案的调优是**多轮的执行反馈闭环**，每一轮都有结构化的失败信号（编译错误、正确性失败用例、计时、profile 热点）回灌，搜索方向被这些信号逐步修正。这个闭环的代价是编译预算：每一轮都要编译、运行、计时，编译时间与运行时间直接构成评测的时间成本；如果 profile 信号开启，NCU 采集本身也有开销，且采集的指标粒度会影响反馈的信息量。

这里有一个工程判断值得单独拎出来：**反馈信号的质量决定了搜索的上限**。只回灌「加速比低于基线」这一条标量信号，智能体只能盲目尝试分块参数；回灌「该 kernel 的 global memory 吞吐已接近峰值带宽、但 shared memory 利用率低」这样的 profile 摘要，智能体才能定向地调整数据复用策略。这与旧方案里工程师依赖 NCU 逐层排查是同一个道理，只是执行者从人换成了模型，反馈的带宽成了新的瓶颈。AgentKernelArena 把 profile 信号列为可选，正是承认了这条信号链的成本——采集开销、指标选择、摘要方式都会影响评测的可比性。

另一个容易被忽略的代价是轨迹记录本身。三层之间通过固定 schema 的轨迹记录连接，保证不同智能体在同一口径下可比。这意味着每一次编译、每一次正确性校验、每一次计时都要被结构化地落盘，评测的存储与复现成本随用例数与轮数线性增长。这是旧基准（单轮、单形状、只记最终分数）没有的成本项，也是「可信评测」必须支付的代价。

六 · 旧方案失效的根因：优化对象与评测对象的不一致

把上面几条线索收拢，旧方案失效的根因可以归结为一句话：**优化的对象是「一组固定形状上的 kernel」，而部署需要的对象是「一个形状分布上的 kernel 生成能力」**。手写 CUDA 优化的是一个具体 kernel 实例，Triton autotune 优化的是一个配置网格，库调用优化的是一个枚举清单，固定形状基准优化的是一个公开用例集合——四者的优化对象都是「点」，而生产环境需要的是「面」。

AgentKernelArena 的问题现场正是这个「点与面」的错配。它不否认固定形状上的加速比是有意义的信号，但它指出这个信号不足以预测部署收益：一个在公开形状上刷出高分的智能体，可能在未见形状上退化到不如朴素实现，而排行榜无法区分这两种智能体。泛化差距公式与分布内/分布外双口径，就是把「面」上的表现纳入计分的机制。这个机制的有效性依赖分布外集合的构造质量，其工程代价（隐藏测试集、构造难度分级、失败率与加速比同时报告）是旧基准没有承担的。

对工程读者而言，这一部分留下的判断是具体的：当你评估一个 kernel 优化智能体时，先问它的评测口径是否区分了分布内与分布外，再问失败样本是否被单独计入，最后问 profile 反馈的信号带宽是否足以支撑定向搜索。三个问题里任何一个缺失，排行榜分数与真实部署收益之间就会存在无法量化的缺口——而这个缺口，恰恰是旧方案在真实流量面前反复暴露的那个缺口。
