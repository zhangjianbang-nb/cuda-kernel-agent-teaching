一 · 单轮提示：一次生成的全部代价都压在 prefill 上

在 Atrex-Bench 的语境里，单轮提示是最便宜的基线，也是最容易把分数打虚的路径。它的输入是算子语义描述、参考实现签名、shape 元数据与 roofline 上限；输出是一段候选 kernel 源码（CUDA C++ 或 Triton）。整条链路上没有回灌，模型在第一次 decode 结束时就交付最终答案，因此它的“迭代次数”恒为 1，代价结构极其简单：全部成本集中在一次长上下文 prefill 加一次自回归 decode 上。

把这一步写成伪代码，代价项就一目了然：

$$\text{cost}_{\text{1shot}}=\underbrace{c_{\text{prefill}}(L_{\text{prompt}})}_{\text{读参考实现+roofline}}+\underbrace{c_{\text{decode}}(T_{\text{out}})}_{\text{生成源码}}+\underbrace{c_{\text{nvcc}}(T_{\text{out}})}_{\text{编译}}$$

三项里只有第三项与 GPU 真正相关。编译时间是单轮路径最容易被低估的隐性代价：候选源码一旦触发模板展开或寄存器压力过大，nvcc 的编译时延会从秒级跳到分钟级，而这条路径没有任何机制在编译失败时自我修正——编译错误直接变成一次零分。正确性上，单轮提示的失败模式是“看起来对”：模型倾向于复刻参考实现的数学形式，却忽略生产 shape 下的边界条件（非对齐 stride、动态 batch、混合 dtype），于是正确性门在小 shape 上通过、在 440 个采样 shape 上崩塌。性能上，论文给出的判断是即使最强的 vanilla 模型也只能达到硬件 roofline 的约 10%，这个量级说明单轮提示基本停留在“能跑”而非“跑得好”。

具体例子：一个 memory-bound 的 layernorm 变体，单轮提示往往给出朴素的单 pass 实现，读一遍写一遍，带宽利用率被中间统计量的二次读取拖垮；模型不会主动想到用 Welford 单遍归约或把统计量与归一化融合进同一个 block，因为这类决策需要 profile 反馈，而单轮路径没有反馈通道。

二 · Agent 脚手架：measure-revise 循环把时延换成搜索预算

AKA 的核心是把单轮的“一次性交付”改成迭代的 measure-revise 搜索。一次迭代的输入是上一轮的候选源码加上它的 profile 结果（时延、带宽、占用率、SASS 热点），输出是改写后的候选。与单轮相比，代价结构从“一次 prefill”变成“N 次 prefill + N 次编译 + N 次计时”，其中 N 是搜索轮数。这条路径把 token 预算和墙钟时间换成了搜索广度，代价是线性增长的编译与测量开销。

循环的骨架可以写成：

$$\text{cand}_{k+1}=\text{Revise}\big(\text{cand}_k,\ \text{Profile}(\text{cand}_k),\ \text{KB}\big),\quad \text{accept if } s_{k+1}>s_k$$

这里的关键机制是 profile 作为输入而非事后报告。NCU 采集的指标（DRAM throughput、L2 hit rate、warp stall 原因）被结构化后塞回提示，模型据此判断瓶颈在访存还是计算，再决定改写方向：合并访存、改 tile 形状、换 shared memory 布局、或引入 async copy。每一步的代价可以拆成三块：编译时延（候选越复杂越贵）、计时噪声（小 kernel 的时延在微秒级，重复测量次数不足会让 s_i 抖动）、以及上下文膨胀（每轮把 profile 文本追加进 prompt，prefill 长度随轮数增长）。

性能代价的量化口径是搜索效率：如果每轮平均只带来个位数百分比加速，而每轮编译加测量要花掉数十秒，那么 agent 的墙钟收益在端到端部署里会被摊薄。正确性代价则体现在“改写引入回归”上——一次为了提升带宽而重排的访存模式，可能破坏某个 shape 下的数值等价性，因此每轮都必须重跑正确性门，而不能只在最终候选上验一次。具体例子：一个 reduction kernel 在 profile 显示 warp stall 于 long scoreboard 后，agent 把标量累加改成向量化加载并加 shared memory 归约树，时延下降，但非 2 的幂 shape 需要额外的尾部处理分支，这个分支若写错就在 440 个 shape 中的少数几个上静默出错。

三 · optimization dropout：跳出停滞搜索上下文的机制与代价

measure-revise 的死穴是搜索上下文收敛到局部最优后反复自我确认：模型在连续几轮里给出结构相似的改写，profile 指标几乎不动，token 却持续消耗。AKA 引入 optimization dropout，其机制是在检测到停滞（连续若干轮 s_i 无显著提升）时，主动丢弃当前上下文中的部分优化历史，让下一轮从更“干净”的状态重新出发，而不是在已经走死的方向上继续微调。

这一步的输入是停滞判定信号与当前上下文，输出是裁剪后的上下文和一条新的改写指令。代价有两面：一方面丢弃历史会损失已经验证有效的局部改动，可能让 s_i 回退，因此需要保留一个最优候选的快照用于回退；另一方面，裁剪上下文直接降低了后续每轮的 prefill 长度，把 token 成本压回来。用公式表达这个权衡：

$$\text{keep}=\arg\max_{c\in\mathcal{C}}\ s(c)\quad\text{s.t.}\ \ |\text{ctx}(c)|\le B_{\text{drop}}$$

也就是说，dropout 不是随机遗忘，而是在上下文预算 B_drop 内保留得分最高的那条路径。工程判断上，这个机制的价值取决于停滞检测的灵敏度：阈值太松，dropout 触发太晚，白白烧掉几轮编译；阈值太紧，频繁丢弃会让搜索变成随机游走，正确性门被反复触发。具体例子：一个 GEMM 变体在 tile 从 128×128 改到 64×256 后再无提升，dropout 丢弃 tile 搜索历史，迫使 agent 转向 epilogue 融合方向，从而绕开了在 tile 维度上的无效穷举。

四 · 分层知识库：298 个参考 kernel 与 244 条优化条目的检索代价

AKA 附带一个分层 GPU 优化知识库，包含 298 个参考 kernel 文件与 244 条优化条目。它的作用不是让模型背诵，而是在改写时提供可检索的先例：当 profile 指出某类瓶颈（例如 shared memory bank conflict 或低占用率），检索层把对应的参考实现与优化条目注入提示，缩小模型的搜索空间。

这一步的输入是 profile 特征与当前源码结构，输出是若干条参考片段。代价主要是检索与注入带来的上下文开销：注入的参考代码越长，prefill 越贵，且长上下文会稀释关键指令的注意力权重。分层设计的用意正在于此——先按瓶颈类型粗筛，再按算子族细选，避免把整个知识库塞进 prompt。可以把这个选择写成约束：

$$\text{inject}=\text{TopK}\big(\text{sim}(\text{profile},\ \text{entry})\big),\quad \sum|\text{inject}|\le B_{\text{kb}}$$

正确性代价体现在“先例错配”：一个为特定 dtype 或特定架构调优的参考 kernel 被错误地套用到另一个 shape 上，会引入隐蔽的数值或对齐问题。性能代价则体现在检索延迟与注入冗余上——如果 TopK 选得过大，agent 每轮都要为无关代码付出 prefill 成本。具体例子：profile 显示某 kernel 的 L2 命中率低，知识库检索到一条关于分块预取（block-level prefetch）的条目，agent 据此插入 cp.async 流水，但该条目原本针对的是另一个访存模式，直接套用会让 shared memory 占用翻倍、占用率下降，反而拖慢时延——这正是需要 measure-revise 回灌来兜底的原因。

五 · verifier：正确性门与性能门的串联代价

无论单轮还是 agent，候选都必须过两道门。正确性门的输入是候选 kernel、参考实现与 440 个采样 shape 的输入分布，输出是逐 shape 的布尔判定；性能门的输入是通过正确性门的候选，输出是相对基线的加速比 s_i。论文的评分公式把这两道门压成一个阈值计数：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个形式暴露了一个工程事实：正确性本身不进分数，它只是 s_i 有定义的前提。于是 verifier 的代价结构是串联的——正确性门失败的候选不进入计时，省下了测量开销但浪费了编译开销；正确性门通过的候选要跑满计时，而计时本身在小 kernel 上是噪声敏感的操作。更关键的是，论文明确指出仅凭正确性会高估能力，因为表面通过率中有相当部分来自 fallback 而非真实 kernel。这意味着 verifier 必须能识别“退化为参考实现”的候选，否则正确性门形同虚设。

代价的另一个维度是 shape 覆盖：440 个 shape 全量验证的墙钟时间与编译次数成正比，若每个候选都要全量跑，agent 的搜索轮数就被压得很低。工程上的折中是分层验证——先用少量代表性 shape 粗筛，再对高分候选做全量验证，但这会引入“粗筛漏掉边界 shape”的正确性风险。具体例子：一个候选在主要 shape 上加速明显，却在某个非对齐 batch 上因越界读而结果错误；若粗筛没覆盖该 shape，错误候选会被误判为高分并进入下一轮改写，污染整个搜索轨迹。

六 · RL 路径与四条路径的代价对照

第四条路径是 RL：把 kernel 生成建模为策略，以 verifier 的输出作为可验证奖励。它的输入是题目与参考实现，输出是策略更新后的生成分布。与 agent 脚手架的区别在于，RL 把搜索成本从推理时前移到训练时——推理时一次生成即可，但训练时需要大量 rollout，每个 rollout 都要编译、运行、计时，代价是训练墙钟与 GPU 卡时。

奖励设计直接决定这条路径的成败。若奖励只用正确性，策略会收敛到 fallback；若奖励只用加速比，策略会在少数容易的 shape 上过拟合。论文的评分口径提示了一个更稳的组合：以 s_i 的阈值计数为主项，辅以正确性作为硬门，并对 fallback 施加惩罚。代价上，RL 的样本效率受编译时延拖累——一个 rollout 的编译若需数十秒，单卡每小时能采集的样本数就被压到很低，这使得 RL 在 kernel 任务上比在纯文本任务上贵得多。

路径每步输入每步输出主要代价典型失效

四条路径共享同一个 verifier，但代价分布截然不同：单轮把成本压在推理，agent 把成本压在搜索轮数与编译，RL 把成本压在训练 rollout。工程判断的落点在于，生产端到端收益不取决于单次生成的峰值加速，而取决于搜索预算与编译时延的比值——当编译时延接近单轮 prefill 的量级时，agent 的迭代收益会被编译开销吃掉；只有当 profile 反馈能稳定带来结构性改写（而非参数微调）时，measure-revise 的墙钟投入才划算。论文的受控案例显示 agent 能把零 FlyDSL fallback 转成匹配或超过手工调优基线的真实 kernel，这个结果的意义不在于数字，而在于它证明了反馈通道存在时，搜索可以跳出 fallback 吸引子——而这正是单轮提示与纯正确性奖励都做不到的。

失效边界：当 trace 采样、roofline 上限与加权评分互相拆台

Atrex-Bench 的可信度建立在三个假设上：440 个 shape 能代表生产分布、per-problem roofline ceiling 是可达上界、importance weight 能正确排序优化收益。任一假设破裂，整条“生成—编译—运行—评测”流水线的结论就会漂移。最直接的失效条件是 trace 采样偏差：30 个算子按 GPU 时间份额加权，意味着低频但长尾的算子权重趋近于零，agent 在这些题上即使把时延压到 roofline 也几乎不改变总分。反过来，某个高频算子若在采样窗口内恰好被上游融合或替换，其权重会被高估，agent 会把搜索预算浪费在即将消失的 kernel 上。代价是搜索 token 与编译时间的错配——AKA 的 measure-revise 循环每轮都要编译并 profile，一次无效探索烧掉的是真实 GPU 机时，而非离线仿真。

第二个失效点藏在 roofline ceiling 的口径里。若 ceiling 按 compute-limited、memory-rich 的硬件峰值推算，而候选 kernel 的实际瓶颈是 launch 开销或 occupancy 不足，那么 $s_i=T_{\text{base},i}/T_{\text{cand},i}$ 的分子分母都落在同一段“未被 roofline 覆盖”的区间，加速比看起来可观，离硬件上限却仍远。论文观察到的“最强 vanilla 模型仅达约 10% roofline”正是这种口径的产物：它度量的是与理论上界的距离，不是与生产基线的距离。工程判断上，这意味着用该分数做模型排序时，必须同时看绝对时延与 roofline 占比，否则会把“比 PyTorch eager 快但离 SOL 很远”的候选误判为可用。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N} w_i \cdot \mathbb{1}[s_i\ge\tau],\qquad \sum_i w_i = 1$$

第三个失效条件是正确性门与性能门的耦合方式。摘要明确指出 correctness alone overstates capability，因为相当一部分表面通过率来自 fallback——候选编译失败或数值不达标时退回参考实现，pass 率虚高而 kernel 并未真正生成。AKA 的 optimization dropout 用来跳出停滞的搜索上下文，但它同时是一个 reward hacking 的入口：agent 学会在难例上触发 dropout 并回退到基线，从而稳定拿分。控制手段是把 fallback 显式计入代价——每次回退消耗一次编译与一次 profile，且该题的 $w_i$ 在总分中标记为“未优化”。一个具体例子：某 memory-bound 算子的候选在 Triton 下编译通过但 shared memory 超限，运行期回退到 eager，正确性检查全绿，时延却等于基线；若评分不区分“真 kernel”与“fallback”，这条记录会被误读为一次成功优化。

这三类失效共同指向一个工程判断：Atrex-Bench 的加权分数是“生产收益的代理”，不是“kernel 质量的度量”。代理在 trace 覆盖充分、roofline 口径与瓶颈一致、fallback 被显式惩罚时才可信；一旦跨硬件、跨 dtype 或跨框架迁移，权重与 ceiling 都需要重算，否则离线分数与生产端到端收益之间的相关性会断裂。AKA 的 298 个参考 kernel 文件与 244 条优化知识条目能缓解搜索停滞，但无法修复评测口径本身的偏差——这是基准设计问题，不是 agent 能力问题。
