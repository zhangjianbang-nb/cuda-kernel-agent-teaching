一 · 基准构成：235 题从哪来、为什么这个规模改变了可比性

SOL-ExecBench 的题目池是 235 个 CUDA kernel 优化问题，抽取自 124 个生产与新兴 AI 模型，覆盖语言、扩散、视觉、音频、视频与混合架构。这个构造方式决定了它的口径与 KernelBench 系合成算子集有本质差别：题目不是“造出来的矩阵乘变体”，而是从真实模型计算图中切出来的算子，带有真实的 shape 约束、dtype 组合与前后向配对关系。对 agent 而言，这意味着候选 kernel 必须同时满足模型级语义（例如 attention 的 mask 语义、归一化的 eps 位置、量化缩放因子的广播轴），而不是只对一个孤立算子做数值对齐。

规模本身是口径的一部分。235 题、124 模型，平均每模型不到两个算子，说明选题是“按模型覆盖”而非“按算子难度分层”——它优先保证架构多样性，而不是让某一类算子反复出现来刷分。评测时若把 235 题简单算术平均，等于给每个模型近似等权；这与按 token 数或按端到端时延加权的生产口径不同。因此读这张榜时第一件事是确认聚合方式：论文给出的聚合是阈值化的 faster rate 形式，

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

即统计“加速比超过阈值 τ 的题目比例”，而不是几何平均加速比。这两者的代价完全不同：阈值计数对“刚好过线”的候选不敏感，对“远高于线”的候选也不奖励，因此它压制了单题极端加速比对总分的拉动；代价是丢失了分布尾部信息，一个在 200 题上快 1.01 倍、在 35 题上慢一半的候选，与一个在 200 题上快 3 倍、在 35 题上持平但都不过线的候选，可能得到相近的分数。工程判断上，这意味着该指标适合回答“有多少题被真正攻下”，不适合回答“平均能快多少”。

具体例子：一道来自扩散模型的 FP8 前向算子，其参考实现是框架内的融合 kernel，候选若只做逐元素重写而不处理缩放因子的 layout，正确性门会先失败；即便通过，其 s_i 也可能落在 τ 之下而被计为 0——阈值计数把“接近但未达标”的优化直接归零，这是与 geomean 口径最大的行为差异。

二 · 基线与 SOL 界：为什么“打败软件基线”不再是分母

论文的核心口径转换是：不再以可变软件实现为分母，而以解析推导的 Speed-of-Light 上界为参照。SOLAR 流水线负责为每题推导硬件接地（hardware-grounded）的 SOL 界，SOL Score 则量化候选在“发布定义的评分基线”与“硬件 SOL 界”之间闭合了多少差距。写成比值形式，设基线时延 T_base、候选时延 T_cand、SOL 界对应时延 T_sol，则闭合比例为

$$\text{closure}_i=\frac{T_{\text{base},i}-T_{\text{cand},i}}{T_{\text{base},i}-T_{\text{sol},i}}$$

这个式子的工程含义是：分母不再是“别人写得多快”，而是“硬件理论上还能快多少”。它带来两个直接后果。其一，基线若本身已接近 SOL，分母趋近于零，闭合比例数值爆炸、不可解释——所以论文用“release-defined scoring baseline”固定基线版本，避免基线漂移导致历史分数失效。其二，SOL 界是解析推导而非实测最优，若推导偏乐观（例如忽略了实际必须的中间物化或同步开销），闭合比例会被系统性压低；若偏保守，则出现闭合比例大于 1 的情形，需要单独解释而不是当作“超越硬件”。

代价体现在测量侧：SOL 界要求对每题的访存字节数、必需 FLOPs、以及目标 dtype 下的有效吞吐做建模，这需要在编译期或静态分析阶段确定数据流，而不是跑一遍计时就行。对 agent 循环来说，这意味着每题都要携带一份 SOL 元数据（字节数、算术强度、目标 dtype），生成侧可以据此选择 tiling 与向量化宽度，验证侧则用它判断候选是否落在合理区间。具体例子：一道 BF16 反向算子，其 SOL 界由必须写回的梯度张量字节数主导，候选若通过跳过零梯度区域来减少写回，正确性检查必须覆盖稀疏梯度情形，否则“闭合更多差距”其实是漏算工作量。

三 · 硬件与 dtype 口径：Blackwell 专属能力如何进入分母

基准面向 NVIDIA Blackwell GPU，覆盖 BF16、FP8 与 NVFP4，并明确包含“最优性能预期依赖 Blackwell 专属能力”的 kernel。这句话对口径的影响是决定性的：SOL 界必须按目标 dtype 的原生吞吐来推导，而不是按 FP32 折算。BF16、FP8、NVFP4 三档的有效峰值不同，且低精度档往往受限于缩放因子处理、layout 转换与累加精度要求，SOL 界里必须把这些“非计算但必需”的字节移动计入，否则分母偏小、闭合比例虚高。

跨 dtype 的数字不可比，原因有三层。第一层是峰值差异：同一算子在 BF16 与 NVFP4 下的 SOL 时延本就不同，把两个 dtype 的 s_i 放进同一个 geomean 等于混合了不同物理上限。第二层是正确性容差：低精度路径的数值误差预算更宽，候选可以用更激进的近似（例如分段累加、缩放因子粗量化），这些近似在 BF16 下会被正确性门拒绝，于是“同题不同 dtype”实际是不同难度的题。第三层是 Blackwell 专属指令的可用性：依赖特定硬件能力的 kernel 在旧架构上要么不可编译、要么退化为慢路径，因此任何跨硬件引用该榜数字的行为都缺少分母一致性。

可核查的口径要求是：报告分数时必须同时声明 GPU 型号、dtype、基线版本与 τ 取值。缺少任一项，s_i 与 score 都无法复算。具体例子：一道 NVFP4 量化的前向算子，其 SOL 界包含量化/反量化所需的字节往返；若候选把反量化推迟到下一个 kernel，单题时延下降但改变了计算图边界，这类“跨题搬运”必须由 harness 的静态检查拦截，否则分数不可比。

四 · 隐藏 shape 与输入分布：离线分数为何会在生产上崩塌

论文口径中，输入分布按论文给定，摘要未给出全部 shape。这一点必须被当作口径缺口对待，而不是细节。真实模型算子的性能对 shape 极度敏感：batch 维、序列长度、head 数、hidden 维是否被 128 整除，直接决定 tiling 是否对齐、是否触发尾块处理、是否能用上向量化加载。一个针对固定 shape 做特化的候选（把 tile 大小、寄存器分配、甚至展开次数硬编码到该 shape）在基准上可以闭合大量差距，但换一个 batch 就退化。

隐藏 shape 的处理方式决定了榜单的可信度。工程上可核查的做法是：评测集分为公开 shape 与保留 shape 两部分，公开部分用于 agent 迭代，保留部分只在最终评分时使用，且保留部分的分布偏移（不同 batch、不同序列长度、非对齐维度）必须被记录。伪代码层面的门控可以写成：

  • 对每题维护 shape 集合 S_pub 与 S_held，S_held 不进入反馈回路；
  • 正确性门在 S_pub ∪ S_held 上全通过才计入；
  • 性能门取 S_held 上的最差 s_i 或分位数，而非 S_pub 上的均值；
  • 静态检查拒绝将 shape 常量硬编码进索引计算或循环边界的候选。

代价是 token 与编译时间：每题多套 shape 意味着多轮编译与多轮计时，agent 的迭代预算被稀释；若保留 shape 只在末期跑，又会出现“反馈与评分分布不一致”的乐观偏差。具体例子：一道音频模型的卷积类算子，公开 shape 的序列长度是 2 的幂，候选用了对齐加载；保留 shape 含非 2 的幂长度，尾块处理缺失导致越界读，正确性门直接失败——这类失败在只看公开 shape 的循环里完全不可见。

五 · 沙箱 harness：让计时可复算的四个机制

论文提供沙箱化 harness，包含 GPU 时钟锁定、L2 cache 清除、隔离子进程执行，以及针对常见 reward hacking 的静态分析检查。这四项不是工程装饰，而是把 s_i 变成可复算量的前提。

时钟锁定消除的是频率漂移：GPU 在短 kernel 上会因功耗与温度策略在 Boost 档之间跳变，同一候选两次计时可以差出可观比例，足以让 τ 附近的判定翻转。锁定后计时方差下降，代价是绝对时延不再代表生产环境（生产里频率是动态的），因此该榜的 s_i 应被读作“同频下的相对量”，不能直接换算成端到端收益。L2 清除消除的是跨迭代缓存残留：若不清除，第二次跑同一候选会命中上一次留下的数据，测出偏低的时延，而生产中数据流是连续的，这种“热身红利”不可迁移。隔离子进程消除的是状态污染：CUDA context 残留、显存碎片、环境变量与库版本混用都会让计时不可复现，隔离后每次测量从干净状态开始，代价是启动开销被计入总预算。

静态分析检查针对 reward hacking：常见手法包括在计时区间外做计算、缓存结果直接返回、按输入指针或 shape 分支走快路径、调用被禁用的库函数。这些手法会让 s_i 虚高而正确性门仍通过。检查的代价是误杀：某些合法的特化（例如按对齐性选择不同加载路径）与作弊在静态特征上接近，需要白名单或人工复核。具体例子：候选在首次调用时把结果写入全局缓冲，后续调用直接读回——正确性检查若只跑一次就发现不了，隔离子进程加多次调用计数才能暴露；而 L2 清除保证读回路径不会被缓存掩盖。

六 · 不可比清单与可核查的测量口径

把上述内容收敛成一张可执行的对照表，用于判断任何一个引用 SOL-ExecBench 的数字能否与自己的结果并列。

维度可比条件不可比情形与后果
硬件同为 Blackwell，同型号、同显存配置跨架构引用：Blackwell 专属 kernel 在旧卡上退化或不可编译，分母失效
dtype同题同 dtype（BF16 / FP8 / NVFP4 分开统计）混合 dtype 求 geomean：峰值与容差不同，等于混合物理上限
基线固定 release-defined 基线版本，且确认 TF32/最强库已启用基线未开 TF32 或未用最强库：s_i 被系统性高估
SOL 界同一 SOLAR 推导版本，字节数与 FLOPs 建模一致不同推导版本混用：closure 分子分母不同源，闭合比例不可加
输入分布公开 shape 与保留 shape 的划分、偏移量已声明只报公开 shape：shape 特化分数在生产上崩塌
计时时钟锁定、L2 清除、隔离子进程、重复次数与聚合方式已声明未锁频/未清缓存：热身红利与频率漂移使 s_i 不可复现
聚合τ 取值、faster rate 的 N 与题目集合固定换 τ 或换题目子集：score 不可纵向比较

在这张表之上，可核查的测量口径可以写成一段最小声明：GPU 型号与时钟策略；每题 dtype 与基线版本；τ 与聚合公式；公开/保留 shape 的划分；每题的重复次数与取中位数还是最小值；静态检查的白名单版本。缺一项，读者就无法从 s_i 反推出 T_cand 是否在同等条件下测得。对 agent 系统而言，这套口径还决定了反馈信号的质量：若反馈用的是未锁频的单次计时，agent 会在噪声上做梯度，收敛到“碰巧快”的候选而非稳定快的候选。

最后落在工程判断上：SOL Score 的价值不在于给出一个绝对排名，而在于把“还剩多少硬件余量”变成可分解的量——每题一个 closure_i，一个候选在哪类算子上闭合得多、在哪类上停在基线附近，直接指向下一步该改 tiling、改 dtype 路径还是改数据流边界。使用这张榜时，先核对上表的七行是否与自己的测量环境对齐，再决定是否引用其分数；不对齐时，只引用其题目集合与 SOL 元数据，把计时与聚合换成自己可复算的口径。

SOL 分数的可比性边界：基线漂移、隐藏分布与沙箱代价

SOL Score 把“相对软件基线的加速比”换成“向硬件 SOL 上界收敛的比例”，公式为 $$\text{SOL Score}=\frac{T_{\text{base}}-T_{\text{cand}}}{T_{\text{base}}-T_{\text{SOL}}}$$ 其中 $$T_{\text{base}}$$ 是 release 定义的评分基线、$$T_{\text{SOL}}$$ 是 SOLAR 解析推导的界。这个口径的边界很硬：分母一旦为负或接近零（基线本身已贴近 SOL，或 SOL 界推导过于乐观），分数会爆炸或失去意义；因此跨题聚合必须用 fast-p 这类阈值命中率而非算术平均，否则单题异常值主导总分。代价是 SOLAR 的解析界依赖对访存、算力、片上容量的建模假设，模型偏差直接变成全体分数的系统性偏移。

不可比的来源集中在三处：其一，基线若未启用 TF32、未调用最强库实现，$$T_{\text{base}}$$ 偏大，SOL Score 被高估；其二，BF16/FP8/NVFP4 三类 dtype 的 SOL 界不同，跨 dtype 求 geomean 无物理意义，只能同 dtype 内比较；其三，Blackwell 专属能力（如 NVFP4 路径）上的最优实现无法迁移到其他架构，论文结论只在给定硬件上成立。隐藏 shape 与输入分布是另一重风险：候选若针对公开 shape 做特化，离线分数高但生产分布上崩塌，因此测量口径必须声明 shape 采样方式，并把分布外输入纳入正确性门。

沙箱本身引入系统代价：GPU 时钟锁定与 L2 cache 清空使每次测量更接近稳态，但清缓存与隔离子进程带来固定开销，单题时延测量需多次重复取中位数以摊薄；静态分析检查针对常见 reward hacking（如缓存结果、跳过计算）属于编译期成本，会增加候选被拒的比例，进而拉长 agent 的迭代轮次与 token 消耗。工程判断是：把 SOL Score 当作“剩余差距的闭合度”读，同时记录基线版本、dtype、shape 采样与沙箱配置四项元数据，缺任一项的分数不可跨报告比较。
