一 · 从“装备”到“提问”：一次 kernel 生成的四段流动

KernelSeek 的方法骨架并不复杂，复杂的是它把“结构自由度”这个抽象权衡落成了四段可观测的流动：生成 → 编译 → 运行/评测 → 反馈改写。每一段都有明确的输入、输出与代价，而论文的核心主张——用“在正确时刻问出的一个短问题”替代“往 agent 身上堆工具”——正是嵌在这四段之间的接缝上。要读懂它，必须先把这四段拆开，看每一步到底消耗什么、产出什么、在哪里失血。

第一段是生成。输入是参考实现（一个已经能跑、但不够快的 CUDA kernel）与任务描述；输出是一个候选 kernel 的源码文本。这里的关键约束是论文明确写下的“no operator-specific knowledge and no faster implementation to imitate”：agent 拿到的是一个通用编码 agent 的身份，而不是一个被喂了 FlashAttention 论文、CUTLASS 模板或已知最优解的先验库。代价在这一段主要是 token：候选源码的长度、以及 agent 为决定“改哪里”所消耗的推理 token。生成段的质量决定后续三段的全部上限——一个语义上就错的候选，编译段会直接把它烧掉。

第二段是编译。输入是候选源码，输出是二进制或编译错误。这一段是纯机械的、可判定的，也是整条流水线里最便宜也最无情的一环：语法错、寄存器溢出、不支持的 PTX 指令、shared memory 超限，全部在这里暴露。代价是编译时间与失败率。论文没有给出编译耗时的数字，但工程上可以定性判断：一个 agent 若在生成段频繁产出不可编译的候选，编译段就会变成一道高墙，把“试错预算”大量消耗在零信息量的失败上。这正是 open-ended agent “pay for the freedom in trials” 的第一笔账。

第三段是运行与评测。输入是可执行候选与论文给定的输入分布；输出是正确性判定与时延测量。正确性门是硬的：候选必须在给定输入上逐元素/逐场景通过，才进入性能比较。性能门则用统一基线折算加速比：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这个公式看似平凡，但它把“接受”定义成一个合取条件：正确性与加速比必须同时成立，任何一项不达标都退回。代价在这一段是 GPU 时间与显存占用——每次评测都要真实跑一遍 kernel，输入分布越宽，评测越贵。论文的 182 个场景（每架构）正是这一代价的直接来源：正确性不是抽查一个 shape，而是在一整批场景上全过。

第四段是反馈改写。输入是前三段累积的信号（编译错误、正确性失败、时延数字、以及 agent 自己提出的问题）；输出是下一轮候选。这一段是 KernelSeek 与 scripted/open-ended 两类方案的分水岭：scripted agent 在这里查表（优化菜单、固定角色），open-ended agent 在这里做种群变异，而 KernelSeek 在这里插入一个“短问题”——把“剩余差距在哪里”变成一个显式的假设，再据此决定下一步改什么。代价是推理 token 与轮次：问题本身很短，但它触发的是有方向的编辑，而不是盲目的重复编辑。

二 · 单轮提示与 agent 脚手架：谁在决定“下一步做什么”

把四段流动落到实现上，第一个分岔是单轮提示与agent 脚手架的区别。单轮提示的输入是一段拼好的 prompt（参考 kernel + 任务 + 少量指令），输出是一次生成；它没有“下一步”的概念，四段流动被压成一次前向。代价极低（一次生成、一次编译、一次评测），但信息回流为零：编译错误或时延数字不会影响这一次生成，因为生成已经结束。它的适用面正是 scripted agent 的适用面——当配方（recipe）恰好覆盖当前任务时，单轮提示能以极少的采样换来可用的候选；一旦任务落在配方之外，它就“stall where it does not”。

agent 脚手架则把四段流动变成循环：生成段的输出进入编译段，编译/运行/评测的信号回灌到下一轮的生成段。脚手架的输入不再是一段静态 prompt，而是一个状态：当前最优候选、历史失败原因、已尝试的编辑方向。输出是下一轮的动作（改哪一行、换哪种 tiling、是否回退）。代价从“一次生成”升级为“N 次生成 + N 次编译 + N 次评测”，并且多出一层状态管理的开销——历史越长，prompt 越长，token 越贵。论文对 prevailing style 的批评正落在这里：工具丰富的自主 agent 把 profiler 解析、反汇编、文档检索、经验库全部塞进脚手架，状态越来越重，但“方向”并没有因此变清晰。

一个具体的对照是论文给出的同任务对照：在相同任务、评测器、硬件与周次下，一个按流行风格搭建的工具丰富自主 agent 在 133 个模型驱动步骤后停在 0.50x FlashAttention-3，而 KernelSeek 达到 1.13x。133 步是一个可观测的代价锚点：每一步都要生成、编译、评测，累计的 GPU 时间与 token 是实打实的。0.50x 意味着这个 agent 不仅没加速，反而比基线慢一倍——它消耗了大量 trial，却没有把 trial 转化成方向。这不是“工具不够多”的问题，而是“工具没有回答一个具体问题”的问题。

脚手架的设计因此有一个反直觉的判断：减少装备、增加提问。装备（profiler 输出、反汇编、检索）增加的是信息量，但信息量不等于方向；提问增加的是假设的质量，而假设直接决定下一轮编辑的命中率。代价的转移也很清楚：装备的代价是每次都要解析、检索、拼接，token 与延迟线性增长；提问的代价是一次短推理，但它的收益是非线性的——一个正确的问题可能让后续若干轮编辑都落在有效方向上。

三 · RL 与 verifier：可验证奖励如何嵌进四段流动

论文的方法里，RL 与 verifier 不是独立模块，而是嵌在第三、四段之间的判定器。verifier 的输入是候选 kernel 与输入分布，输出是一个布尔（正确性）加一个标量（加速比）；两者合成上一节的 accept 指示函数。这个 verifier 的性质决定了 RL 信号的性质：它是可验证的（编译通过、逐场景正确、时延可测），因此奖励不是模型自评，而是外部世界给的硬判决。代价是 verifier 必须真实执行——每个候选都要编译、跑满场景、测时延，这就是“thousands of evaluations”账单的来源。

把 verifier 放进 RL 回路，奖励可以写成对 accept 的聚合，例如在一批候选上取接受率或取最优加速比：

$$R=\mathbb{E}_{\text{task}}\left[\max_{k\in\text{batch}}\ \mathbb{1}[\text{pass}_k\land s_k\ge 1]\cdot s_k\right]$$

这个式子的工程含义比它的数学形式更重要：它奖励的是“在预算内找到至少一个既正确又加速的候选”，而不是“平均而言改得不错”。这直接对应 open-ended agent 的失败模式——wrong candidates 大量存在，若奖励按平均算，错误候选会把信号稀释；若奖励按最优算，则一次命中就能拉动整批。代价是方差：最优奖励的方差大，需要更多 batch 才能稳定，而每个 batch 的每个元素都要付编译 + 评测的钱。

verifier 的另一个代价是它可能被绕过。论文的失败模式清单里明确写了 reward hacking / fallback 会让正确率虚高：如果 verifier 只检查少数场景，或者候选在失败时悄悄回退到基线实现，accept 就会假阳性。这不是 verifier 本身的缺陷，而是 verifier 与输入分布之间的缝隙——182 个场景的全覆盖正是为了堵这个缝，但覆盖越全，评测越贵。工程判断在这里是：verifier 的严格度与评测成本是一条曲线上的两端，KernelSeek 选择的是“全场景正确性 + 统一基线时延”，用评测成本换可信度。

一个具体例子能把 RL 信号的方向性讲清楚。假设 agent 在某一轮提出的问题是“这个 kernel 的瓶颈是 shared memory 带宽还是 occupancy”。若问题问对了，下一轮编辑会集中在 tile 大小或寄存器压力上；若问错了，编辑会落在无关的指令调度上，编译通过、正确性通过、但加速比不动——accept 为假，奖励为零，但这一轮消耗的编译与评测成本已经付出。RL 在这里学到的不是“哪种编辑有效”，而是“哪种提问能引出有效编辑”，这正是论文“supplies direction without narrowing what the agent may do next”的操作化含义。

四 · 每一步的输入输出与代价账本

把四段流动的输入、输出、代价摊成一张表，能看清 KernelSeek 的钱花在哪里、省在哪里。下表按步骤列出，代价列只写定性或论文给出的锚点，不补数字。

步骤输入输出主要代价
生成参考 kernel、任务描述、当前状态（含上一轮问题）候选源码文本推理 token；候选长度
编译候选源码二进制或编译错误编译时间；不可编译候选的零信息失败
运行/评测可执行候选、输入分布（182 场景/架构）正确性布尔、时延、加速比GPU 时间；显存；场景覆盖带来的评测成本
反馈改写编译/正确性/时延信号、agent 提出的问题下一轮编辑方向或回退决定短问题推理 token；轮次；状态拼接的 prompt 长度

这张表暴露的第一个不对称是：编译段与评测段的代价是硬的、可预测的，生成段与反馈段的代价是软的、随状态膨胀的。scripted agent 把软代价压到最低（固定动作，不需要长状态），代价是配方外失效；open-ended agent 把软代价放到最大（种群、历史、工具输出全进 prompt），代价是 133 步仍停在 0.50x。KernelSeek 的取舍是在软代价里加一个短问题，而不是加一堆工具——问题的 token 成本远低于解析 profiler 输出或反汇编，但它提供的是方向而非信息量。

第二个不对称是评测段的成本随场景数线性增长，而正确性的可信度也随场景数线性增长。182 个场景每架构是一个明确的覆盖口径，它把“在给定输入分布上正确”变成可验证的命题，但也意味着每个候选都要跑满这批场景。若一个 agent 在 133 步里每步都产出一个候选，评测成本就是 133 × 182 次运行量级——这正是“thousands of evaluations”的算术来源。KernelSeek 能用更少的方向性编辑达到 1.13x，等价于把同样的评测预算花在更少、更准的候选上。

第三个不对称是反馈段的问题质量与后续轮次的命中率之间的非线性关系。一个短问题若问在“剩余差距在哪里”，它就把后续编辑的搜索空间从“所有可能的改动”收缩到“与假设相关的改动”，但不收缩 agent 能做什么（论文强调 without narrowing what the agent may do next）。代价是问题可能问错，收益是问题问对时后续若干轮都省下盲试。工程上这意味着反馈段的设计目标不是“信息更多”，而是“假设更准”。

五 · 从 0.50x 到 1.13x：方向性在流动中的位置

论文给出的最强对照是同一任务、同一评测器、同一硬件、同一周次下的 0.50x 与 1.13x。把这两个数字放回四段流动，可以看到方向性到底改变了哪一段。0.50x 的 agent 在 133 步里持续生成、编译、评测，但它的反馈段没有产生假设——它有的是工具输出（profiler、反汇编、检索），缺的是“剩余差距在哪里”的判断。于是每一轮编辑都是对当前候选的局部扰动，扰动累积却不对准瓶颈，最终时延反而高于基线。1.13x 的 KernelSeek 在同样的流动里插入问题，把反馈段从“信息回灌”变成“假设生成”，后续编辑因此落在有效方向上。

这里有一个容易被误读的点：1.13x 不是“更多 trial 的产物”，恰恰相反，它是“更少无效 trial 的产物”。open-ended agent 的自由度换来的是 trial 的数量，而 trial 的代价是编译 + 评测的硬成本；KernelSeek 的自由度没有减少（它仍然可以改任何东西），但它把 trial 的选择交给了问题。用公式语言说，若把每一步的编辑看作从动作空间 A 中采样，无方向的采样在 A 上近似均匀，命中有效方向的概率低；有问题引导的采样在 A 的一个子集上集中，命中率提高，而 A 本身不变。代价是问题可能把子集选错，收益是子集选对时收敛快。

论文还给出了跨架构的延伸：KernelSeek 产出了面向 Hopper 与 Blackwell 的、无依赖的 FlashAttention 前向 kernel——单 CUDA 文件，不含 CUTLASS、CuTe、cuBLAS、cuDNN，在每个架构的 182 个场景上全部正确，并达到 1.16x FlashAttention-3（数字锚点中另有 1.46 出现，按论文口径属另一测量）。这条事实的方法论含义是：无 operator-specific knowledge 的 agent 仍能产出跨架构可用的 kernel，说明“方向”不是靠预置的算子知识给的，而是靠流动中的问题给的。代价是跨架构意味着每架构都要跑满 182 场景，评测成本翻倍；收益是产出的 kernel 不依赖库，部署面更宽。

六 · 机制落点：问题作为流动中的控制信号

把整条流动收束到一个机制判断上：KernelSeek 把“问题”当作四段流动之间的控制信号，而不是当作 prompt 里的一段文本。控制信号的性质是它改变下一段的行为：编译段的错误告诉 agent“哪里不能编译”，评测段的加速比告诉 agent“改得够不够快”，而问题告诉 agent“下一步该验证哪个假设”。三者串起来，才构成一个有方向的闭环。缺少问题这一环，前两个信号只能做局部修正，无法回答“剩余差距在哪里”，这正是 0.50x 的 agent 在 133 步后仍无进展的机制解释。

这个机制的代价结构也很清楚：问题的推理成本低，但它依赖前三段提供的信号质量；若编译段频繁产出不可编译候选，或评测段的场景覆盖不足，问题就建立在噪声上，方向会偏。因此 KernelSeek 的方法不是“用问题替代工具”，而是“用问题把工具的输出组织成假设”——工具仍然在流动里（编译、运行、评测都是工具），但它们服务于一个假设，而不是堆在状态里等 agent 自己消化。工程判断落在这一点：在 kernel 优化这种搜索空间巨大、单次评测昂贵的场景里，把预算花在提高每次 trial 的方向性上，比花在增加 trial 的数量或装备的丰富度上回报更高；而方向性的最小载体，是一个在正确时刻问出的短问题。
