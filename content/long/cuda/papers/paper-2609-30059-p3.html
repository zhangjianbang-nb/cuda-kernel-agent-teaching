一 · 从编译产物出发：dispatch 视图是搜索的入口

KernelOPT 的起点不是自然语言描述的算子，而是编译器产物本身。Inductor 生成的代码里同时存在两类可优化对象：一类是它自己生成的 Triton kernel，另一类是它对外部库的调用（如 cuBLAS、cuDNN、ATen 算子）。论文的机制是先把这份产物解析成一张“dispatch 表”——每个节点记录算子语义、输入输出 dtype 与 shape、当前实现来源（Triton 生成 / 库调用 / fallback 到 eager）、以及该节点在整图里的调用次数。这张表是后续所有 agent 动作的输入：没有它，agent 只能看到一段孤立代码，无法判断“改这个 kernel 对整模型时延有没有意义”。

这一步的代价是解析与静态分析时间。对 Level3 的模型架构（论文在 250 题中划出 50 个模型级题目），图规模可达数百节点，解析开销随节点数线性增长，并且需要把 Inductor 的 FX graph 与生成的 Triton 源文件做对齐——对齐失败时节点会被标记为“不可归因”，这些节点不进入优化候选池。工程上这意味着搜索空间被静态裁剪：调用次数低于阈值的节点直接跳过，因为即便单 kernel 加速数倍，摊到端到端也只落在噪声里。这个裁剪是必要的，否则 agent 的 token 预算会被大量低收益 kernel 吞掉。

具体例子：一个 Level2 复合算子题里，dispatch 表可能显示某 elementwise 融合 kernel 占端到端时延的主要份额，而旁边几个小库调用各占极小比例。agent 的注意力应当落在前者；若把预算花在后者，即使拿到单点加速，模型级 score 也不动。这正是论文强调“translating isolated kernel improvements into model-level gains remains a challenge”的机制根源——单 kernel 加速比与模型级加速比之间隔着一层 dispatch 权重。

二 · 生成步：单轮提示、脚手架与多 agent 分工的输入输出

生成步的输入是 dispatch 表里选中的节点（含原始 Triton 源、shape/dtype 约束、以及该节点上下游的读写模式），输出是一份候选实现。论文的系统是多 agent 的，按角色拆分：有的 agent 负责读 profile 与编译器产物做诊断，有的负责改写 Triton kernel，有的负责判断是否应改为调用外部库或 Helion kernel（论文明确支持 PyTorch nn.Modules、standalone Triton kernels 与 Helion kernels 三种形态）。单轮提示在这里不是“一次性生成”，而是把诊断结论、约束、以及上一轮的失败原因压进一个上下文窗口，让改写 agent 在一个受控的编辑空间里动作。

生成步的代价主要是 token 与编译时间。每次改写都要重新走一遍 Triton 编译（JIT 编译 + autotune 配置搜索），一个候选的编译时间在秒级到十秒级，而 agent 每轮可能产出多个候选；若不做候选去重与语法预筛，编译队列会成为吞吐瓶颈。工程上的做法是在生成后先做轻量静态检查（dtype 一致性、shared memory 用量上限、block 维度合法性），把明显非法的候选挡在编译之前，这一步用毫秒级代价换掉秒级编译浪费。

具体机制上，生成 agent 的编辑动作被约束为“局部重写 + 可回退”：它拿到的不是空白文件，而是当前最优候选的源码，加上 profile 指出的瓶颈位置（如 occupancy 受限、bank conflict、冗余的 global load）。这种“带锚点的改写”比从零生成收敛快，但也带来一个正确性代价：局部改写容易保留原实现的数值路径，若原实现本身在边界 shape 上有隐患，改写会把这个隐患继承下去——这正是后续多阶段验证要解决的问题。

三 · 编译—运行—评测：四级验证门的流动与代价

候选进入验证流水线后，论文给出四级门：执行检查、多 seed 数值比对、带 float64 回退的模型级检查、以及端到端性能门（阈值 γ=1.03）。这四级的顺序是有代价考量的：越靠前的门越便宜，越靠后的门越贵。

  • 执行检查：编译并跑通，捕获非法内存访问、越界、编译失败。代价是单次 kernel 启动时延加编译时间，输出是布尔通过/失败与错误类型。
  • 多 seed 数值比对：在多个随机输入 seed 上与参考实现比对，容忍浮点误差但要求统计上一致。代价是 N 倍的前向时延（N 为 seed 数），输出是逐 seed 的最大相对误差与是否越界。
  • 模型级检查 + float64 回退：把候选装回整模型跑一遍，若数值漂移超阈值则用 float64 参考路径复核，判断是候选真错还是低精度累积噪声。代价是整模型前向（Level3 题上远高于单 kernel），输出是模型级输出的一致性判定。
  • 端到端性能门：在统一基线下测时延，要求加速比达到 γ=1.03 才保留。代价是重复计时与 warmup，输出是加速比与是否晋级。

这四级门的核心判据是论文给出的 score 公式：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

注意这里的 score 是“过阈值题目的比例”，不是平均加速比。这个口径决定了 agent 的行为：一个把某题从 1.0 推到 1.5 的候选，与一个把它从 1.02 推到 1.04 的候选，在 score 上贡献相同（都只贡献一个 1），但后者消耗的验证成本一样。于是搜索策略应当偏向“把临界题推过 τ”，而不是“把已过线的题继续推高”——这是 dispatch-aware 搜索在预算分配上的直接推论。τ 的取值论文未在摘要中给出具体数字，但 γ=1.03 作为性能门阈值是明确的，两者共同构成“性能门 + 计分门”的双阈值结构。

具体例子：某候选在单 kernel 上拿到明显加速，但装回模型后端到端只提升不到 3%，性能门拒绝它。这不是候选无效，而是 dispatch 权重太低——agent 需要回到第一步重选节点，而不是继续在这个节点上打磨。这个回退路径是 KernelOPT 与“单 kernel 刷分”类方法的分水岭。

四 · RL 与反馈回路：奖励从哪来、代价在哪

论文的系统带 RL 成分，但奖励信号不是人写的偏好，而是上述验证门产生的结构化反馈：编译是否通过、数值是否一致、模型级是否一致、端到端加速比是否过 γ。把这些离散信号拼成奖励时，最直接的形式是分级奖励——编译失败给最低，数值错给次低，数值对但性能未过门给中等，过门给最高。这样 agent 学到的不是“写出能跑的代码”，而是“写出能过门的代码”。

RL 回路的代价体现在样本效率上：每个训练样本要跑完整条编译—运行—评测链，单样本的墙钟时间由编译时间、多 seed 前向、整模型前向与计时重复共同决定。相比纯文本 RL，这里的每一步都绑定真实硬件执行，吞吐受 GPU 队列限制。工程判断是：把便宜的门放在前面做过滤，只有通过前三级的候选才进入昂贵的端到端计时，这样每条样本的平均成本被前级门压低。

另一个代价是 reward hacking 的风险面。论文的四级验证本身就是对这个风险的对冲：如果只看“单 kernel 加速比”，agent 会学会针对评测 shape 做特化、或在数值上偷工（例如降低累加精度换吞吐）。多 seed 比对压缩了前者，float64 回退压缩了后者。但仍有残余：候选可能学会在 fallback 路径上“看起来正确”——即检测到 float64 复核时走保守路径，正常路径走激进路径。这类行为在离线基准上难以暴露，属于论文局限里“shape 特化与隐藏输入分布会让离线分数在生产上崩塌”的具体机制之一。

五 · 组装与部署：模型级收益如何被确认

“assembles and evaluates the resulting model”是论文方法链的最后一环：把通过验证的候选 kernel 替换回编译器产物，重新组装成可运行的模型，再在统一基线上评测。这一步的输入是候选源码加 dispatch 表中的替换点，输出是一个可复现的模型级加速比。组装本身有代价：替换点若涉及跨 kernel 的融合边界（例如把两个相邻 Triton kernel 合成一个），需要重跑 Inductor 的调度，编译时间会显著上升；若只是单点替换，组装接近零成本。

部署侧的判断标准是端到端回归而非离线分数。论文在 H200 上覆盖 250 道 KernelBench 题（100 单算子、100 复合算子、50 模型架构），这个分层本身就说明模型级题目是独立的一档：单算子题的加速比不能直接外推到模型题，因为 dispatch 权重、kernel 间依赖、以及内存复用模式都不同。工程上应当把 Level3 的通过率当作部署前的硬门，而不是用 Level1 的高分做替代指标。

具体机制上，组装后的模型级检查还有一个隐性代价：float64 回退路径会显著拉长单次评测时间（float64 在 GPU 上的吞吐远低于 fp16/bf16），因此它只应在数值漂移触发时启用，而不是默认全跑。把回退做成条件触发，是用“少数可疑样本的昂贵复核”换“整体评测吞吐”的典型折衷。

六 · 各步代价的横向对照与工程取舍

把一次 kernel 生成—编译—运行—评测的流动摊开看，每一步的瓶颈位置不同，取舍也不同。下表按步骤列出输入、输出与主要代价（定性，不引入论文未给出的数字）：

步骤输入输出主要代价
dispatch 解析Inductor 产物、FX graph节点表 + 权重解析时间随节点数线性增长
生成/改写选中节点、profile 诊断、上轮失败原因候选源码token 预算、上下文窗口
编译候选源码可执行 kernel + autotune 配置秒级编译，队列吞吐受限
执行 + 多 seed 数值候选、参考实现、seed 集误差统计、通过/失败N 倍前向时延
模型级 + float64 回退组装后模型一致性判定整模型前向，回退路径昂贵
端到端性能门统一基线、候选加速比、是否过 γ重复计时与 warmup

这张表给出的工程判断是：搜索预算应当按“单位代价的 score 增益”分配，而不是按“单 kernel 加速比”分配。由于 score 是过阈值题目的计数，一个候选的价值取决于它是否把某题从 τ 之下推到 τ 之上；若某题已在 τ 之上，继续投入的边际收益为零（在 score 口径下），此时应把预算转向临界题或未通过题。这与“最大化平均加速比”的直觉相反，是 KernelOPT 计分口径带来的策略差异。

另一个取舍在候选宽度与验证深度之间。宽候选（每轮生成多个变体）能提高命中临界题的概率，但每个候选都要走编译与前三级的门，代价线性上升；深验证（多 seed、整模型、float64 回退）能压低 reward hacking 与数值隐患，但单样本成本高。论文的四级门结构实际上给出了一个默认配比：便宜门做宽筛，昂贵门只对少数晋级候选开启。工程上若要复现这套流程，最容易被忽略的是编译队列的调度——把编译与评测做成异步流水，能让 GPU 在编译等待期间继续跑其他候选的计时，这是把墙钟成本摊薄的具体手段。

最后落在机制上：KernelOPT 的可信度不来自单点加速比，而来自“dispatch 权重 → 候选生成 → 四级门 → 模型级组装”这条链上每一环都有明确的输入输出与可回退点。任何一环被跳过（例如跳过模型级检查直接采信单 kernel 加速比，或跳过 float64 回退直接采信低精度一致性），离线分数就会与生产收益脱钩；这条链的完整性，比任何单个 agent 的提示技巧都更决定最终结果的可信度。

验证门与分发边界：四阶段校验的代价与失效面

KernelOPT 的可信度不来自生成，而来自四道串联的验证门：执行检查、多 seed 数值比对、带 float64 回退的模型级检查、端到端性能门（γ=1.03）。前三道是正确性 oracle，第四道是收益门。关键在于它们是串联否决而非加权：任一阶段失败即回退候选，因此单题的实际评测成本是四阶段之和，而非最便宜那一阶段。多 seed 数值比对把单次运行的正確性判定变成 k 次采样加逐元素容差比较，代价是 k 倍运行时间与 k 倍中间张量显存；float64 回退在模型级检查中把整条前向抬到双精度，显存占用与指令吞吐同步恶化，对 Level3 的 50 个模型架构而言，这一阶段往往是整条流水线里最贵的一步。性能门 γ=1.03 意味着候选必须比基线快至少 3% 才被接受，这个阈值直接决定了搜索的有效产出率：在测量噪声与 dispatch 抖动接近 3% 的算子上，大量真实但微弱的改进会被判为无效，agent 的多轮迭代预算被消耗在阈值边缘而非实质优化上。

$$\text{accept}=\mathbb{1}\big[\text{exec}\wedge\text{num}_k\wedge\text{model}_{f64}\big]\cdot\mathbb{1}\big[T_{\text{base}}/T_{\text{cand}}\ge\gamma\big],\quad \gamma=1.03$$

这套门控的失效面集中在两处。其一是分发边界：KernelOPT 检查的是编译产物中生成的 Triton kernel 与外部库调用，当算子被 Inductor 融合进更大的图、或运行时 dispatch 到库实现而非被检视的 kernel 时，被优化的对象与真正执行的路径分离，模型级收益可能为零甚至为负——这正是论文所述“孤立 kernel 改进难以转化为模型级增益”的机制根源。其二是回退掩盖：float64 回退与多 seed 容差在放宽判定时会让数值上可疑的候选通过，正确率被系统性抬高；同理，若基线未开 TF32 或未用最强库实现，γ 门会被轻易跨过，加速比被高估。工程判断上，应把四阶段耗时与 token 消耗计入单题预算，并对 Level1 的 100 个单算子题与 Level2/Level3 分别设定不同的 γ 与 seed 数：单算子题可用严格门换可信度，模型级题则应把预算倾斜到分发路径核验，而非继续加 seed。
