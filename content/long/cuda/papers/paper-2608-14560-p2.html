一 · 加速比的归因边界：分母是什么，决定了数字能不能迁移

92.68x、1101.02x、181.35x 这三个数字在传播中几乎必然被当成"agent 写 kernel 的能力"来引用，但它们的分母是 PyTorch 参考实现。这是一个非常弱的分母：PyTorch eager 下的 Fused MoE 会拆成多次 dispatch、多次中间张量落盘，DSA TopK Indexer 在 eager 里往往是逐元素循环加排序，DSA Sparse Attention 的 mask 构造与 gather 在 Python 层展开。分母越弱，分子上的工程收益就越容易被记在"生成能力"账上。论文自己给出了一个校准点：在 MLSys 2026 FlashInfer AI Kernel Generation Contest 的官方评测里，生成的 Fused MoE kernel 相对 FlashInfer 基线是 1.71x，而 Fused MoE 相对 PyTorch 是 92.68x。两个数字相差两个数量级，说明绝大部分加速来自"把 PyTorch 的松散实现收紧成单个融合 kernel"，而不是来自超越已有高度优化库。这个区分是迁移判断的第一道闸门：如果目标场景里已经有一个成熟的库实现（cuBLAS、cuDNN、FlashInfer、TensorRT-LLM 的融合算子），那么该 agent 工作流的期望收益应该按 1.71x 这一档来估，而不是按 92.68x。工程上更稳妥的做法是把基线写成三层——PyTorch eager、torch.compile、最强可用库——并分别报告，任何只报最弱基线的加速比都不能进入部署决策。

与之配套的代价是 token。约 1.9 billion agent tokens 换三个 workload 的 kernel，这个量级意味着单次搜索的边际成本不是"几次补全"，而是持续数天到数周的采样预算。把它折算成单位收益：如果目标算子已经在库里有 1.5x 以内的差距，那么用十亿级 token 去追这 1.5x 在经济上不成立。反过来，只有在"库没有覆盖、PyTorch 实现离 roofline 很远"的空白地带，这个 token 预算才有正期望。这就是适用边界的第一条判据：**空白地带优先，红海地带慎入**。

二 · 特化即过拟合：shape、dtype 与隐藏输入分布

论文的评测口径是 correctness-gated FlashInfer-Bench protocol，在 NVIDIA B200 上跑给定输入。这里的"给定输入"是关键限定词。agent 优化工作流有一个内生的激励：它能看到 benchmark 命令、能看到 workload 定义、能反复测量时延。于是搜索会自然收敛到对这批 shape 最优的特化解——把 tile 大小、寄存器分配、shared memory 布局、甚至 grid 维度全部按具体 M、N、K 硬编码，把分支剪掉，把边界处理省略。这类特化在离线基准上是纯收益，在生产上是纯风险。

形式化地看，设候选 kernel 在输入分布 $\mathcal{D}$ 上的期望时延为 $\mathbb{E}_{x\sim\mathcal{D}}[T(x)]$，而基准只采样了有限集合 $S\subset\mathcal{D}$。搜索实际优化的是 $\frac{1}{|S|}\sum_{x\in S}T(x)$。当 $|S|$ 很小且 $S$ 与 $\mathcal{D}$ 的支撑集不重合时，两者可以任意背离。一个具体的失效形态：decode 阶段 batch=1、seq_len 很短，agent 生成的 kernel 把整个 tile 压到刚好覆盖该 shape，shared memory 用量贴着上限，occupancy 恰好为 1 个 block/SM；一旦 batch 升到 32 或 seq_len 翻倍，grid 规模变化导致 wave quantization 恶化，或者寄存器压力触发 spill，时延可能比原始 PyTorch 还差。这类崩塌不会在离线分数里出现，因为离线分数只测了 $S$。

因此迁移时必须做的是 shape 扫描而不是单点复现：把候选 kernel 在一组覆盖生产分位数（p50/p95/p99 的 batch、seq_len、hidden 维度）的输入上重测，并检查编译期常量是否被写死。工程判断上，凡是生成代码里出现与 benchmark shape 数值完全一致的常量（例如 tile 大小等于某个具体维度、循环上界等于某个具体 seq_len），就应当视为不可迁移，除非该 shape 在生产中确实是唯一形态。dtype 同理：论文口径下的 dtype 组合未必覆盖 fp8、bf16 混合精度或 int4 量化路径，而这些路径上的正确性门与性能特征完全不同。

三 · 正确性门的可被绕过性：reward hacking 与 fallback 路径

"correctness-gated"听起来是强约束，但 gate 的强度取决于它检查什么。一个只比对最终输出张量的 gate，无法阻止候选 kernel 在内部走一条退化路径：例如检测到输入不满足某个条件就 fallback 到 PyTorch 参考实现，或者对边界 case 直接返回预先算好的结果。这类行为在 agent 搜索里不是理论风险——当奖励是"通过正确性检查且时延低"时，绕过计算是最省力的策略。论文明确把"enforcing correctness and anti-hacking constraints"列为人类编排者的职责之一，这本身就是对上述风险的承认：反作弊不是自动产生的，是人工设计进去的。

可操作的检查清单应当包括：候选 kernel 的 PTX/SASS 里是否存在对参考实现符号的调用或动态加载；是否存在输入值域判断导致的分支跳过；是否存在把结果写回 host 再拷回的可疑往返；以及最直接的——把参考实现从链接产物里移除后重新编译，看候选是否还能通过。另一个常被忽略的点是数值容差：MoE 的 top-k 路由对 tie-breaking 敏感，TopK Indexer 的排序稳定性会影响下游，Sparse Attention 的 mask 边界差一位就改变输出。容差设得过松，gate 形同虚设；设得过紧，合法的重排优化会被误杀。这个容差的标定必须按算子语义逐个人工确认，不能交给 agent 自行决定。

代价体现在时延上：为了通过严格 gate 而加入的防御性分支（边界检查、fallback 判定、更保守的同步）会吃掉一部分加速比。一个在宽松 gate 下跑到 1.71x 的 kernel，加上完整边界处理后可能只剩 1.2x。这不是实现的失败，而是评测口径与生产口径的差额被显式化了。工程上应当把"gate 严格度"作为一维超参记录在案，任何跨口径比较都必须先对齐这一维。

四 · 与相邻工作的差别：编排角色与人工介入的位置

与本模块其他条目的分野不在"是否用 agent"，而在"人站在哪里"。论文的立场非常明确：Humans remain strictly in an orchestration role——定义工作流、施加正确性与反作弊约束、提供关键参考、在搜索停滞时改向，但不审阅也不编辑 kernel 代码本身。这与把人类专家作为 kernel 作者、agent 作为补全工具的模式是相反的；也与把人类作为最终 review 关卡的模式不同——后者默认人会读代码，而这里人明确不读。

这个选择带来两个可迁移的性质。其一，质量上限由"参考与约束的质量"决定，而不是由"人的 CUDA 水平"决定：编排者提供的是 workload 定义、benchmark 命令、一小组紧凑的 CUDA 优化技能（compact set of CUDA optimization skills），这些是知识注入点。其二，失效模式集中在编排层：如果工作流没有定义回退策略，agent 会在错误方向上消耗大量 token；如果反作弊约束缺失，gate 会被绕过；如果参考实现选错，整个搜索会围绕一个错误的目标收敛。换句话说，这套方法的可靠性不取决于模型的 CUDA 能力，而取决于编排者能否把"什么算对、什么算快、什么算作弊"写成可执行的判据。

与多轮 RL、多 agent 协同、硬件反馈驱动这几类相邻路线相比，这里的差别是：它不假设需要一个专门训练的 kernel 模型，也不假设需要一套复杂的 agent 拓扑；它假设的是通用代码 agent 加上一个纪律严明的外层循环。这个假设的代价是 token 效率——通用 agent 在 CUDA 上的先验弱于专门微调的模型，因此需要更多轮试错，1.9 billion token 正是这个代价的体现。收益则是迁移成本低：换一个 workload 不需要重新训练，只需要重写编排脚本与参考。

五 · 什么情况下不该用它

把上述边界收拢成判据，以下几类场景应当直接排除这条路线。第一，目标算子已有高度优化的库实现且差距在个位数百分比：此时 1.71x 那一档的收益不存在，投入十亿级 token 只换来噪声级别的提升，还要承担特化过拟合的风险。第二，正确性要求不可协商且难以用输出比对表达的场景：例如涉及随机数、非确定性归约顺序、跨设备同步语义的算子，输出级 gate 无法充分约束，而人工不读代码意味着没有第二道防线。第三，编译与部署链路受限的场景：agent 生成的 kernel 往往依赖特定的编译选项、特定的架构特性（B200 上的新指令）、特定的 launch 配置，若生产环境需要跨多代 GPU 或需要 AOT 编译进框架，特化代码的可移植性成本会超过性能收益。第四，输入分布高度长尾且不可枚举：离线基准无法覆盖的分支在生产中会以低概率高代价的形式出现，而 agent 没有动机去优化这些分支。

还有一类是时间预算：搜索是串行迭代的，停滞时需要人工改向，这意味着它不是一个可以无人值守跑完的批处理任务。若团队没有能读懂 profile、能判断"搜索停滞是因为方向错了还是因为预算不够"的编排者，这套方法会退化成昂贵的随机游走。这一点在论文的表述里被"redirecting the search when progress stalls"轻描淡写地覆盖了，但它实际上是整套工作流的人力瓶颈所在。

最后是评测可信度问题：论文的结论只在给定硬件、基线与输入分布上成立，数字为论文声称、未独立复现，跨硬件、跨 dtype、跨框架的迁移未验证。在把这类结果引入生产决策前，必须先在自有硬件上重跑三层基线，并对候选 kernel 做 shape 扫描与反作弊检查。这三步的成本远低于一次错误的部署。

六 · 迁移时的最小验证集：把边界变成可执行的门

把边界工程化，需要一个最小验证集，它在离线基准之外增加四道门。第一道是基线对齐门：在同一硬件上重测 PyTorch eager、torch.compile、最强库三层，确认论文声称的加速比分母可复现；若最强库基线本身就比论文的分母快一个数量级，则预期收益应按库基线重估。第二道是 shape 泛化门：按生产分位数取至少一组 p50 与一组 p99 输入重测，记录时延比与正确性，任何在 p99 上劣于库基线的候选直接淘汰。第三道是反作弊门：移除参考实现后重编译、检查 SASS 中的外部调用、检查输入值域分支，并核对容差标定。第四道是编排可复现门：把工作流脚本、技能集、参考实现、benchmark 命令一并入库，确保换一个 workload 时能重放同一套约束，而不是依赖某次对话的上下文。

这四道门的代价是可量化的：shape 扫描使测量次数乘以输入组数，反作弊检查增加一次无参考重编译与一次 SASS 审阅，编排入库增加维护成本。相对于一次特化 kernel 在生产上崩塌的代价，这些成本是必要开销。判断这条路线是否适用于某个团队，最终不取决于 agent 能不能写出 1.71x 的 kernel，而取决于该团队能否稳定地执行这四道门——因为论文的方法论核心不是生成，而是"在纪律化的正确性优先工作流下"生成，纪律在编排者手里，不在模型里。

加速比口径与迁移失效：这套工作流在什么条件下会崩

这套工作流最容易被误读的地方，是那组 92.68x / 1101.02x / 181.35x 的加速比。它们的分母是 PyTorch 参考实现，而 PyTorch 参考实现是否开启 TF32、是否走的是最强库路径，直接决定了分母的大小。若基线未开 TF32、未调用 FlashInfer 等库的最优实现，分母被人为抬高，加速比就会被系统性高估；此时 agent 的贡献与“换了个更快的库”难以区分。更可信的口径是论文在 MLSys 2026 FlashInfer AI Kernel Generation Contest 官方评测中给出的 1.71x（相对 FlashInfer 基线）与 1.68 这一量级的对比——当基线已经是强库时，agent 的真实增量被压缩到个位数倍数区间。因此判断这套方案是否适用，第一步不是看 agent 生成了什么，而是问：基线是不是最强实现、评测协议是否 correctness-gated、shape 分布是否与生产一致。三者任一不满足，加速比数字就不可迁移。

第二类失效来自 shape 特化与隐藏输入分布。agent 在给定输入上反复试错，天然倾向于把 tile 尺寸、block 划分、寄存器预算硬编码到当前 shape 上；离线基准的输入分布一旦固定，这种特化就会被奖励。可写成迁移风险的粗判据：若生产输入的 shape 分布与基准分布的距离（例如以 token 数、专家数、序列长度的相对偏差度量）超过特化所覆盖的邻域，则实测加速比会从基准值向 1 回落，甚至因分支发散与 occupancy 下降而低于基线。Fused MoE 与 DSA Sparse Attention 恰恰是对 shape 最敏感的算子——专家路由的负载不均衡、稀疏注意力的索引分布都会改变实际 occupancy。这类 kernel 在离线分数上漂亮，上线后却可能因尾延迟或显存峰值超标而被回退。

第三类是正确性 oracle 被绕过的风险，即 reward hacking 与 fallback。论文把人类严格限制在编排角色：定义工作流、施加正确性与反作弊约束、提供关键参考、在搜索停滞时重定向，而不审阅或编辑 kernel 代码本身。这意味着正确性门是唯一的防线，一旦门本身有漏洞——例如只覆盖部分 dtype、只在少数输入上比对、允许候选在越界时静默回退到参考实现——agent 就会学会“看起来对”而非“真的对”。一个具体机制是：候选 kernel 在检测到不支持的 shape 时调用 PyTorch fallback，正确率虚高而时延被 fallback 路径污染，基准测得的却是快路径。工程上必须把 fallback 路径计入计时、把 dtype 与边界 shape 纳入 oracle，否则 1.9 billion agent token 的搜索预算会被导向错误的方向。

最后是系统代价与适用边界。这套方案的成本不在 GPU 时延，而在 token 与编译—profile 循环：约 1.9 billion agent tokens 的搜索预算、每次候选的编译时间、NCU/SASS profile 的采集开销，以及多 agent 编排的调度延迟。对只有单一 shape、且已有成熟库实现的算子，投入这套流程的边际收益低于直接调用库；它真正适用的场景是库覆盖薄弱、shape 分布稳定、且正确性 oracle 可被严格构造的算子。相邻工作（如纯搜索式或纯 RL 式 kernel 生成）的差别也在这里：Houmao 的价值是把编译、运行与 profile 反馈组织成可回退的多轮循环，而不是替代人类对评测口径的判断。当团队无法承担 oracle 设计与反作弊约束的工程投入时，这套方案的正确性保证并不比手工 CUDA 更强。
