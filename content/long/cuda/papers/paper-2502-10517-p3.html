一 · 单轮提示：一次前向的输入契约与生成代价

在 KernelBench 的评测闭环里，单轮提示是最小可观测单元：模型只看到一段语义说明与规定的输入 shape、数据类型分布，一次前向吐出一段可编译的 CUDA 内核加宿主调用封装。它的输入契约非常硬——任务定义层已经把算子语义、张量形状、dtype 写死，模型没有澄清机会，也没有执行反馈可看。输出则是一个候选实现，评测器只把它当作字节流接收，不关心模型在生成时是否附带了推理过程。

这一步的代价主要落在 token 上。生成一段带宿主封装的 CUDA 内核，长度远超同语义的 Python 函数：kernel 声明、线程/块索引计算、边界判断、共享内存声明、host 侧 cudaMalloc/cudaMemcpy/launch 配置都要写出来。token 预算直接决定候选能否一次写全，截断会表现为语法不完整，在下一步被记为编译失败而非语义错误。这是单轮提示的结构性弱点：它把「想清楚」和「写完整」压进同一次自回归，中间没有任何纠错窗口。

具体例子：一道单算子任务要求对给定 shape 的矩阵做逐元素变换，模型需自行决定 grid/block 维度、是否用向量化加载、边界线程如何处理。它生成的代码若把 block 维度写成固定 256 而 shape 不能被整除，越界写会污染相邻显存，数值比对随即失败——这类错误在单轮里无法被模型自己发现，只能由评测器在运行时暴露。

$$\text{Cost}_{\text{single}}=\underbrace{L_{\text{prompt}}}_{\text{语义+shape}}+\underbrace{L_{\text{gen}}}_{\text{kernel+host}},\qquad \text{Pass}=\text{Compile}\land\text{Numeric}\land\text{Speedup}$$

工程判断上，单轮提示是整条流水线的下限基线：它度量的是模型在零反馈条件下的先验能力。任何 agent 脚手架、多轮优化的增益，都必须相对这个下限报告，否则无法区分「方法有效」与「多给了 token 和轮数」。

二 · 编译：把自然语言产物变成可执行二进制

编译是第一个硬门。评测执行层在固定 GPU 与编译选项下调用 nvcc，把候选源码连同宿主封装编译成可执行体。输入是上一步的字节流，输出只有两种：成功产出的二进制，或一条带错误类型的失败记录。KernelBench 把编译成功率单列为指标，正是为了让这条门独立于语义与性能被统计——编译失败、语义错误、性能不达标是三类可分别归因的失败模式，混在一起报加速比会掩盖失败来源。

这一步的代价是编译时间与工程约束。nvcc 对模板实例化、寄存器压力、内联展开的处理会让编译时延从秒级到数十秒级不等，而候选代码若带模板化的 tile 参数或大量 unroll，编译时间会显著膨胀。更隐蔽的代价是「可编译性」与「可优化性」的张力：为了压寄存器占用而写的复杂分支，可能触发编译器的保守调度；为了追求向量化而写的对齐假设，可能在编译期通过、运行期因未对齐访问而崩溃。编译成功不等于语义正确，这一步只筛掉语法与类型层面的错误。

具体例子：模型生成的内核在 host 侧漏写 cudaDeviceSynchronize，编译毫无问题，但计时环节会把异步 launch 的返回时间当作 kernel 耗时，得到虚高的加速比。这类错误编译期不可见，只有计时口径的严格性才能拦住——这也是为什么评测必须把「编译成功」与「计时可信」分开对待。

工程上应把编译错误类型结构化记录（未定义符号、类型不匹配、资源超限、ptxas 报错），因为不同错误对应不同的修复策略：符号缺失是接口问题，资源超限是并行划分问题，ptxas 报错往往指向寄存器或共享内存压力。把这些混成一句「编译失败」，后续 agent 的修复信号就被稀释了。

三 · 运行与数值比对：语义 oracle 的判定边界

编译通过后进入运行阶段。评测器用与 PyTorch 参考实现完全相同的输入张量驱动候选内核，再把输出与参考输出做逐元素比对。这里的关键机制是「同一输入分布」：语义 oracle 与性能基线同为 PyTorch 参考实现，候选与基线共享同一批随机张量，保证正确性判定与加速比计算在同一输入下进行，避免「用一套输入判对错、用另一套输入测速度」的口径漂移。

判定用逐元素容差：超出容差即判语义错误，样本不进入性能统计。容差取值材料未给出，但它的工程含义很明确——容差过松会放过累积误差，容差过紧会把合法的浮点重排判为错误。归约类算子（求和、softmax）对累加顺序敏感，不同线程块划分会产生不同的舍入路径，逐元素比对在数学等价但数值不同的实现上会误判。这是 KernelBench 口径的一个已知张力：它用逐元素容差换取判定简单，代价是对重排容忍度低。

$$\text{Pass}=\mathbb{1}\left[\lVert y_{\text{kernel}}-y_{\text{pytorch}}\rVert_{\infty}\le\varepsilon\right]$$

具体例子：一道算子序列任务里，前一个算子的输出作为后一个的输入，误差会沿链路累积。单算子级别能通过的容差，在序列级别可能因累积而越界，这解释了通过率随难度级别上升而衰减的一部分原因——不是模型不会写单个算子，而是误差传播在组合负载下被放大。

代价上，数值比对本身是显存带宽密集的操作：要把两个同 shape 的输出读出来做逐元素差，对大张量而言这次比对的耗时可与 kernel 本身同量级。评测器若把比对时间计入候选耗时，会系统性压低加速比；若不计入，则需明确口径。材料未给出这一细节，跨实现比较时必须自行约定。

四 · 计时与加速比：连续信号的口径陷阱

只有通过数值比对的样本才进入计时。评测器用同一输入重复测量取中位数，与 PyTorch 基线耗时相除得到加速比。中位数而非均值，是为了抵抗首次 launch 的冷启动与偶发调度抖动；重复测量次数材料未给出，但次数不足会让中位数本身不稳定，尤其在 kernel 耗时接近计时分辨率时。

这一步的代价是时延测量的系统性偏差。GPU kernel 计时对以下因素极度敏感：是否包含 host-device 同步、是否复用已分配的显存、是否预热过 L2、时钟是否处于 boost 状态。一个在计时上「作弊」的实现——比如把内存分配挪到计时窗口外——会得到好看的加速比却不反映真实端到端收益。KernelBench 以 PyTorch 为唯一基线，意味着加速比只反映相对框架基线的收益，不能直接解读为接近硬件上限；缺少手写 CUDA 库或厂商内核的上限对比，会高估方法成熟度。

$$\text{Speedup}=\frac{T_{\text{pytorch}}}{T_{\text{kernel}}},\qquad T=\text{median}\left(t_1,\dots,t_n\right)$$

具体例子：一个逐元素算子在小 shape 上，PyTorch 基线的 launch 开销占比很高，候选内核即便计算部分更快，加速比也可能被 launch 开销吃掉；换到大 shape，计算占比上升，同一份代码的加速比数字会明显不同。这说明加速比是 shape 的函数，脱离输入分布谈加速比没有意义——而 KernelBench 恰恰把 shape 固定在任务定义层，迁移到真实负载时数字需重新校准而非直接外推。

工程判断：计时环节应把「正确性已通过」作为前置条件严格执行，未通过者不计入性能汇总，否则失败样本的异常耗时（比如越界写导致的非法访问被驱动吞掉后返回）会污染加速比分布。这是「先判对、再测快」的解耦原则在流水线上的落地。

五 · 反馈信号的分层：二元门与连续奖励

把四步串起来看，KernelBench 的评测闭环天然产出分层信号：编译是二元门，数值比对是二元门，加速比是连续量。这三层信号的信息密度不同，对下游优化的价值也不同。编译失败只告诉模型「语法/接口错了」，语义失败告诉它「算错了但能跑」，加速比则告诉它「对了但不够快」。把三层压成一个标量奖励，会让模型在「修语法」和「调性能」之间失去方向感。

材料确认的可优化环节是推理期的生成—编译—运行—评测闭环：模型单次或多次生成候选，编译与数值比对提供二元反馈，加速比提供连续信号，但具体轮数、奖励设计与 token 成本未给出。这意味着 KernelBench 本身是评测基准而非训练方法，它提供的是信号接口，不是信号消费策略。agent 脚手架与 RL 方法是在这个接口之上做文章：脚手架把二元反馈回灌进下一轮提示，RL 把连续加速比变成策略梯度。

具体例子：同一道任务，单轮提示下模型可能生成一个能编译但越界的 kernel，得到「编译成功、语义失败」的记录；若把这条记录连同错误类型回灌，下一轮模型有机会修正边界判断。这个回灌动作本身有 token 代价——错误信息、原代码、修复指令都要占上下文，轮数越多上下文越长，单位样本的 token 成本随轮数线性上升。这是多轮方法必须面对的账：增益是否覆盖 token 膨胀。

代价上，反馈分层的另一个隐性成本是评测吞吐。每个候选都要走编译—运行—比对—计时四段，编译时间与 GPU 占用是串行的，批量评测的吞吐受最慢一段制约。若把多轮生成放进同一评测循环，单样本的 wall-clock 成本会成倍增长，这在规模化 RL 采样时是硬约束。

六 · 流水线视角下的失败归因与工程取舍

按流动拆完四步，可以看到 KernelBench 的方法论核心不是某个模型技巧，而是把「能写对」与「写得快」拆成可分别统计的口径，并让每一步的输入输出边界清晰。编译成功率、数值比对正确率、相对加速比三元组进入汇总，使跨方法比较有了共同锚点。这个设计的工程价值在于失败归因：当一份报告只给加速比中位数时，读者无法判断方法是「普遍能编译但普遍算错」还是「少数算对但很快」，而三元组把这两种情况区分开。

取舍也很明确。以 PyTorch 为唯一基线，换来的是语义 oracle 与性能基线同源、口径统一，代价是缺少硬件上限参照；逐元素容差换来判定简单，代价是对重排类实现容忍度低；固定 shape 与 dtype 换来可复现，代价是长尾负载覆盖不足。这些取舍不是缺陷，而是基准设计者为「可比较」付出的代价，使用者需在引用数字时标注这些边界。

具体例子：一道端到端模型片段任务，模型生成的 kernel 在单算子级别能通过，但组合后中间张量的 dtype 提升（比如 fp16 累加到 fp32）未被正确处理，数值比对在链路末端越界。这类失败在单算子级别不可见，只有分级任务才能暴露——这正是难度分级作为消融维度的意义：通过率随级别上升的衰减，本身就是组合复杂度对生成质量的度量。

工程判断落在最后一步的口径纪律上：计时只对通过数值比对的样本执行，未通过者不进入性能统计；编译失败单列；容差与重复次数在跨设备复现时自行约定并显式记录。这三条纪律决定了加速比数字是否可信。KernelBench 没有给出容差取值与重复测量次数，这不是遗漏而是把口径责任交给使用者——任何引用其加速比的工作，都必须自己补齐这两项约定，否则数字不可复现。

评测口径的边界：三类失败模式与不可外推的加速比

KernelBench 的评测执行层把一次候选内核的判定拆成三段互斥的出口：编译失败、数值比对失败、通过后计时。这个设计的关键在于「单列编译成功率」——若把编译失败并入正确率，语义错误与语法/工具链错误会被混为一谈，报告里只剩一个下降的正确率数字，无法判断模型是写错了算子逻辑还是写不出可编译的宿主封装。代价是评测器必须维护错误分类：编译阶段要捕获编译器诊断并按错误类型归档，运行阶段要区分数值超差与运行时崩溃（如非法访存、越界），后者在 GPU 上往往表现为异步错误，需要同步点与错误码检查才能定位。工程上这意味着每个候选样本的评测时延不只是「编译 + 运行 + 计时」，还包含错误归因的固定开销；对批量评测，编译时间在候选数量大时成为吞吐瓶颈，尤其当候选普遍编译失败时，评测器仍在为每个失败样本付出一次完整编译尝试。

正确性与加速比的耦合点只有一个：只有通过逐元素容差判定的样本才进入计时。这避免了失败样本的异常耗时污染加速比分布，但也带来一个统计口径上的代价——加速比的分母是「通过者集合」，而非「全部候选」，因此两个方法若通过率差异很大，其加速比中位数并不可直接比较。更严格地说，设候选集合为 $$\text{Speedup}=\frac{T_{\text{pytorch}}}{T_{\text{kernel}}},\qquad \text{Pass}=\mathbb{1}\left[\lVert y_{\text{kernel}}-y_{\text{pytorch}}\rVert_{\infty}\le \varepsilon\right]$$，报告应给出三元组（编译成功、Pass、Speedup）的联合分布而非各自的边际；只报 Speedup 的条件中位数会系统性高估方法成熟度，因为被淘汰的失败样本恰好是难度最高、最可能暴露语义缺陷的那部分。容差 ε 本身是未给定的自由参数：ε 放宽会提升通过率并把更多近似实现纳入计时，ε 收紧则可能把合法的浮点重排（如归约顺序不同导致的末位差异）判为语义错误，这一取舍在材料中未给出取值，跨设备复现时必须自行约定并随报告披露。

失效条件集中在两处。其一是基线唯一性：PyTorch 参考实现同时充当语义 oracle 与性能基线，加速比只反映相对框架基线的收益，缺少手写 CUDA 库或厂商内核的上限对照，因此一个高加速比数字不能被解读为接近硬件 roofline——它可能只是击败了未充分调优的框架实现。其二是输入分布固定：每题规定 shape 与数据类型分布，候选与基线共享同一批输入张量，这保证了可比性，却把长尾负载排除在外；迁移到真实负载时，通过率与加速比都可能显著变化，需重新校准而非直接外推。以一道算子序列任务为例：模型生成的融合内核在基准给定的小 shape 上通过比对并获得加速，但同一内核在更大 batch 或非对齐维度上可能触发越界或性能反转，而基准不会暴露这一点。难度分级的价值正在于此——通过率随级别上升的衰减本身就是一个失效信号，提示组合复杂度增加时编译与语义失败的比例如何迁移，但材料未给出分级统计数字，引用时只能定性描述衰减趋势。

系统代价还体现在计时口径上：重复测量取中位数抑制了抖动，但计时仅覆盖内核执行，不含宿主封装与数据传输的完整链路，因此加速比是内核级而非端到端级；对端到端模型片段任务，这一口径会高估实际部署收益。评测器固定单一 GPU 与编译选项，使跨设备比较失去意义，任何跨硬件引用都需重新建立基线。这些边界不构成缺陷，而是口径的显式约定：KernelBench 把「能编译」「算得对」「跑得快」拆成可分别统计的三类失败模式，其工程判断是——报告失败模式分布比报告单一加速比更能约束方法声称的能力边界。
