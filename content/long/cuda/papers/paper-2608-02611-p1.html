一 · 从一条线上推理路径说起：三个算子、两次同步、一次降级

设想一个已经上线的推理服务：输入经过一次 LayerNorm，接一个 fused 的 GELU 与残差相加，再走一次 attention 的 softmax 归一化。这三段在 PyTorch eager 下是三个独立 kernel，中间结果全部落回 HBM，每段之间有一次隐式的 kernel launch 与流同步。工程师打开 profiler，看到的是这样一幅图景：LayerNorm 的读写带宽接近峰值但利用率只有一半，因为它是 memory-bound 的归约，读一遍写一遍，中间还多了一次对 mean/variance 的二次遍历；GELU 与残差是两个 elementwise kernel，各自把 4 字节的中间张量搬进搬出；softmax 在 attention 里被单独切出来，多了一次 max 归约和一次 sum 归约的往返。三段加起来，端到端时延里有相当比例不是花在算术上，而是花在搬运和启动开销上。

这就是 GPU kernel 工程要解决的现场：算子边界是框架按语义切出来的，不是按硬件访存层次切出来的。手写 CUDA 的第一反应是把三段融成一个 kernel，用 shared memory 缓存行内归约结果，让 GELU 的输入直接来自 LayerNorm 的寄存器输出。这个想法在纸面上十分钟就能画出来，落到工程上却是一整条链路：要处理不同 hidden size 的尾块、要保证归约的数值稳定性与 PyTorch 参考实现逐位可比、要在 Hopper 与 Ampere 上分别验证 warp shuffle 的路径、要写一套覆盖边界 shape 的测试、还要在后续框架升级时保持 ABI 兼容。这条链路的成本，才是“手写 CUDA”真正的门槛，而不是那几十行算术。

于是绝大多数团队退回到库调用：cuBLAS、cuDNN、CUTLASS 模板、或者直接用 Triton 写一个够用的版本。库调用的好处是正确性和可维护性有兜底，代价是性能上限被库的通用性锁死——库要为所有 shape、所有 dtype、所有架构负责，它不能假设你的 hidden size 恰好是 4096、不能假设你的 batch 永远小于 8、更不能假设你的输入分布是固定的。当服务已经定型、shape 分布收敛之后，这份通用性就变成了纯粹的浪费。这就是本文要处理的问题现场：不是“能不能写 kernel”，而是“在给定预算下，能不能稳定地找到比库更好、且不比库更不可信的那个 kernel”。

二 · 旧方案的三条路径与各自的硬约束

把论文之前的做法摊开，大致是三条路径，每条都有明确的硬约束，且约束之间互相牵制。

路径一：手写 CUDA C++。控制力最强，能直接操作 shared memory 布局、warp 级原语、异步拷贝与 TMA，也能针对特定架构写死 pipeline 深度。代价是开发周期以人周计，且正确性验证的成本随 shape 覆盖度线性上升。一个 fused LayerNorm+GELU 的 kernel，算术部分可能只占全部工作量的三成，剩下七成是边界处理、数值对齐、多架构分支和回归测试。更麻烦的是可维护性：一旦上游框架换了归约顺序，逐位对齐的假设就崩了，而这类问题往往在灰度发布后才暴露。

路径二：Triton。用块级编程模型换掉了大部分显式线程管理，开发者写的是 tile 上的操作，编译器负责布局与流水。这让开发周期从人周压到人天，也让自动调优（autotune）成为默认选项。但 Triton 的性能上限受限于它愿意暴露的抽象层级：对 shared memory 的精细复用、对异步流水的手动编排、对特定指令（如 wgmma、tcgen05）的直接调用，都需要绕过或等待编译器支持。此外 autotune 本身有成本：每个候选配置都要编译、要跑 benchmark，配置空间一大，编译时间和测量噪声同时上升。

路径三：库调用。零开发成本、正确性由厂商背书、跨架构可移植。代价是性能上限被通用性锁死，且库的黑盒性质让“为什么慢”难以诊断——你拿到的是一个已经调好的 kernel，能改的只有调用参数（比如 workspace 大小、算法选择），而这些参数往往又依赖 shape 才能选对。

三条路径的共同点是：性能、正确性、开发成本三者不可同时最优。手写拿性能但付开发与维护；Triton 拿开发效率但让出部分性能上限；库拿正确性与可移植但让出性能。这个三角约束是本文的出发点：如果有一个 agent 能在给定预算下自动在这三者之间做取舍，并且把“可信”作为一等约束而不是事后补丁，那么三角的一角就可以被放松。

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

上式是论文口径下最基本的两个量：加速比以基线时延为分子，接受判据要求候选既通过正确性检查、又不慢于基线。注意 accept 里的 s≥1 是一个硬门——它把“正确但更慢”的候选直接判死，这一点在旧方案里通常被忽略：手写工程师会保留一个正确但没跑赢库的版本作为退路，而自动搜索如果也保留这类候选，就会污染后续的选择压力。

三 · 为什么非改不可：四个痛点在同一处汇合

痛点一：开发周期与搜索空间的错配。手写路径下，一个工程师一周能试的变体数量是个位数；而 kernel 的优化空间（tile 大小、流水深度、线程映射、归约策略、向量化宽度）是组合爆炸的。人力的串行探索与空间的并行规模根本不匹配，导致大量次优解从未被访问。Triton 把单次尝试的成本降下来，但 autotune 的配置空间仍然是盲搜，且每次尝试都要付编译与测量成本。

痛点二：性能上限被“通用性税”锁死。库的实现要为最坏情况留余量：动态 shape、任意 stride、混合 dtype。当服务的 shape 分布收敛后，这些余量全是浪费。一个具体的例子：attention 的 softmax 在库实现里通常要为任意序列长度准备分块策略，而如果服务里序列长度集中在某个区间，就可以把分块写死、把 max 与 sum 的两次归约合并成一次在线归约，省掉一次完整的中间张量往返。这类收益在库路径下拿不到，在手写路径下拿得到但要付开发成本。

痛点三：正确性不是二值，而是分布。“通过单元测试”与“在生产输入分布上正确”是两件事。手写 kernel 常见的失败是尾块越界、归约顺序改变导致的浮点差异、以及特定 dtype 下的溢出。库路径把这些风险转移给厂商，但一旦你要在库之上做融合或改写，风险又回到自己身上。论文摘要里那句“generated variants can violate correctness constraints”指向的正是这一点：自动生成的变体天然倾向于走捷径，而捷径往往在边界上失效。

痛点四：测量噪声让搜索提前停滞。GPU 时延测量本身有方差：时钟频率漂移、L2 状态、同卡其他进程的干扰、以及 kernel launch 的抖动。当候选之间的真实差异小于测量噪声时，搜索就会在早期把真正有潜力的方向误判为失败。“search often stalls early”在工程上的含义是：不是没有好候选，而是好候选被噪声淹没，选择压力失效。这一点的代价是 token 与算力预算的双重浪费——agent 反复在同一个局部最优附近打转，每一轮都付出生成与评估成本。

四个痛点在同一处汇合：搜索的每一轮都要付生成成本、编译成本、测量成本，而这三者的预算有限。旧方案没有预算概念，要么全量高保真评估（贵到不可行），要么全量低保真评估（噪声大到不可信）。论文的切入点正是把这个预算显式化：先用低成本评估筛掉大量明显不合格的候选，只把高保真预算留给有希望的幸存者。这就是“coarse-to-fine, budget-aware”的字面含义，也是它区别于此前那些“生成即评估”的 agent 脚手架的地方。

四 · 一个具体场景的代价核算：融合 softmax 的三种做法

把上面的抽象落到一个可核算的例子上。取 attention 里的 softmax 归一化，输入是一个 [B, H, S, S] 的分数张量，需要在最后一维上做 max、减、exp、sum、除。三种做法：

  • 库路径：调用框架的 softmax，内部通常是两到三个 kernel（找 max、算 exp 与 sum、归一化），中间张量落回 HBM。开发成本为零，正确性有兜底，但每个中间张量都是一次完整的读写往返。
  • Triton 单 kernel：把整行载入 shared memory 或寄存器，在线归约一次算出 max 与 sum，再写回。开发成本是人天级，性能取决于行宽是否能放进片上存储；行宽超过阈值就要分块，分块又引入跨块的二次归约。
  • 手写 CUDA：在 Triton 的基础上手动编排异步拷贝与流水，把 exp 的计算与下一块的载入重叠。开发成本是人周级，性能上限最高，但每个架构都要单独验证。

代价核算的关键不是绝对时延，而是每次尝试的边际成本。库路径的边际成本是零（改调用参数即可），Triton 的边际成本是一次编译加一次测量，手写的边际成本是一次完整的开发加验证循环。自动搜索要在这条成本曲线上工作，就必须回答：给定总预算 B（以编译次数、测量次数、token 数计），如何在候选空间上分配？论文的答案是分层：低保真层用便宜的评估（比如短输入、少迭代、单次测量）做粗筛，高保真层用完整输入与多次测量做精评。这个分层本身不新鲜，新鲜的是它把“预算”作为搜索的一等公民，而不是事后调参。

这里有一个容易被忽略的正确性代价：低保真评估用的输入分布如果与生产分布不同，粗筛就会系统性地偏向那些在短输入上快、在长输入上崩的候选。论文摘要没有展开输入分布的细节，但“policy-gated evaluation”这个措辞暗示了评估是被策略门控的——不是所有候选都走同一条评估路径，门控决定了谁进入高保真层。门控设计得不好，就会出现“粗筛通过、精评失败”的浪费，或者更糟，“粗筛误杀、真候选从未被看见”。

五 · 旧方案的隐性成本：可维护性与诊断的黑洞

前面四个痛点里，可维护性最容易被低估。手写 kernel 的可维护性成本不在写的时候，而在改的时候：上游框架升级、新架构上线、dtype 策略调整，每一次都要重新验证。一个 fused kernel 如果有 5 个 shape 分支、3 个架构分支、2 个 dtype 分支，组合起来就是 30 条路径，每条都要有测试覆盖。这个成本是随分支数组合增长的，而优化恰恰倾向于增加分支——每一个针对特定 shape 的写死都增加一条路径。

Triton 缓解了一部分：块级抽象让分支变少，autotune 把配置选择交给编译器。但 autotune 引入了新的隐性成本——编译时间。配置空间大的 kernel，首次运行要编译几十个变体，这在服务冷启动时是实打实的时延。更麻烦的是诊断：当 autotune 选中的配置在某个 shape 上表现异常，你很难从 Triton 的抽象层回溯到具体的指令序列，因为中间隔着一层编译器。

库路径的诊断黑洞最深：你拿到的是一个黑盒，能观测的只有端到端时延和 NCU 的粗粒度计数器。想知道“为什么这个 shape 上慢”，只能靠猜和试。这正是论文引入“profiler-informed diagnosis”的动机——把 NCU/SASS 层面的反馈回灌给 agent，让诊断从猜测变成有依据的改写。旧方案里，profile 是人的工具；在新方案里，profile 是搜索循环的一部分。这个转变的代价是每次 profile 都要付采集开销（NCU 的 replay 会让 kernel 跑多遍），所以 profile 不能对每个候选都做，只能对幸存者做——这又回到了预算分配的问题上。

把这些成本放在一起看，旧方案的根本问题不是某一条路径不够好，而是没有一条路径能同时满足“快、对、可维护、可诊断”。手写牺牲后两者，Triton 牺牲性能上限与诊断深度，库牺牲性能上限与诊断能力。论文要做的不是发明第四条路径，而是用一个 agent 把三条路径的取舍自动化：在预算约束下，决定什么时候该手写、什么时候该用 Triton、什么时候该退回库，以及什么时候该停下来。

六 · 从“能不能写”到“值不值得信”：问题的重新定义

把问题现场收束到一个判断上：GPU kernel 工程的瓶颈已经从“能不能写出一个正确的 kernel”转移到“能不能在有限预算下可信地找到一个值得部署的 kernel”。前者是能力问题，后者是决策问题。能力问题随着 LLM 代码生成与 Triton 的普及正在快速缓解；决策问题反而因为候选数量爆炸而变得更难——候选越多，噪声越大，选择压力越容易失效。

这就是为什么论文的摘要把三件事并列：正确性约束被违反、测量噪声、搜索早期停滞。三者不是独立的工程麻烦，而是同一个决策问题的三个面：没有正确性门，候选空间里混入不可部署的解；没有噪声处理，选择压力被方差淹没；没有预算分层，搜索在早期就把资源烧光。论文给出的 0.88x–6.72x 相对 PyTorch 的加速比、最高 1.4x 相对此前最优 kernel agent 的加速比、以及最高 48% 的优化时间下降，正是这三个面被同时处理后在同一批 Triton 任务上的合成结果。注意 0.88x 这个下界：它说明并非所有任务都能赢，agent 在某些任务上仍然慢于基线——这恰恰印证了 accept 判据的必要性，也说明“可信”不是“总是更快”，而是“不快的时候能被识别出来并回退”。

旧方案在这个判断上的失位是结构性的：手写工程师的决策依据是经验，库的决策依据是厂商调优，Triton autotune 的决策依据是局部 benchmark。三者都没有一个显式的、可核算的预算模型，也就无法回答“再试一个候选值不值”。论文把预算显式化之后，搜索的每一步都有了成本标签，决策从“试了再说”变成“在预算内选最优动作”。这个转变的具体机制——粗筛与精评的分层、策略门控、profile 回灌——是后续部分要展开的内容；本部分要留下的判断是：在预算不可核算的旧方案里，性能上限、正确性与开发成本之间的三角约束无法被放松，而一旦预算成为一等公民，这个三角就有了被系统性取舍的可能。
