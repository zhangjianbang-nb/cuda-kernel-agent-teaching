一 · 反馈回灌的三层结构与粒度选择

CUDA-L1 的执行反馈不是单一标量，而是沿工具链分三层产生，每层的信息量与回灌成本不同。第一层是编译期：nvcc 返回的错误码、出错行号、诊断文本（未声明标识符、类型不匹配、共享内存越界声明、非法内建函数调用）是确定性的、可复现的，回灌代价仅为一次编译时延。第二层是运行期：kernel 启动失败、非法访存、断言触发、输出与参考实现逐元素比对不一致，这类信号需要一次 GPU 执行与一次比对，代价是启动开销加比对带宽。第三层是性能期：通过正确性校验后计时，得到相对基线的加速比，代价是多次重复计时取中位数以压制噪声。

粒度选择直接决定训练信号的可用性。把三层压缩成一个布尔“通过/失败”，模型无法区分“语法错误”与“数值偏差”，负例池里的样本失去可学习的结构；反之把 NCU 的逐指令指标全量回灌，token 预算被指标文本吞掉，且大部分指标与当前候选的失败原因无关。CUDA-L1 在给定材料中的做法是把编译错误结构化回灌提示、把正确性失败与更慢实现一并投入负例池，性能层只保留相对基线的加速比标量——即“错误给结构、性能给标量”的非对称粒度。这个选择的工程理由是：编译错误的因果链短且确定，值得用文本承载；性能差异的因果链长且混杂，标量足以驱动对比排序，细节留给离线 profile 分析而非在线回灌。

代价可以量化。设单题采样 k 个候选，编译时延 tc、单次运行加比对时延 tr、计时重复 m 次，则单题反馈成本约为 k·(tc + tr + m·tr)，随候选数线性增长——这正是该方法被点明的主要工程代价。若再把 NCU 采集塞进在线循环，每次 profile 会引入远超单次执行的采集开销与指标落盘时延，闭环轮次会被拖垮。因此在线闭环只做轻量判定，重 profile 属于离线诊断。

二 · 编译错误的结构化回灌：从文本到可学习信号

编译失败在朴素实现里只被记为一个负例标签，模型学到的信息是“这个候选不行”，但不知道自己错在哪个语法构造。CUDA-L1 把 nvcc 的失败信息作为结构化反馈回灌提示，使负例携带错误类型。可行的结构化方式是抽取错误码、源行号、符号名与诊断类别，拼成定长字段而非整段 stderr：

$$\text{fb}_{\text{compile}} = \langle \text{err\_code},\ \text{line},\ \text{symbol},\ \text{category}\rangle$$

类别至少应区分语法/类型错误、资源声明错误（共享内存、寄存器声明越界）、API 误用（同步、索引、内建函数签名）与警告升级。这样负例池可按类别分层采样，对比对时让模型在同一类别内比较“错得不一样”的候选，学习信号从“全错”细化为“错法不同”。

具体例子：一个候选在归约 kernel 中把 __shfl_down_sync 的掩码参数写成常量而非活动掩码，nvcc 可能通过编译但在特定 warp 布局下产生未定义行为；另一个候选把共享内存数组声明为动态大小却未在启动配置中传入字节数，编译期直接报错。前者落入运行期正确性层，后者落入编译层，若二者被压成同一个负例标签，模型无法区分“声明错误”与“语义错误”这两种修复路径。结构化回灌让前者获得“检查掩码语义”的提示方向，后者获得“检查启动配置”的方向。

代价在于 token：每条结构化反馈约占几十个 token，k 个候选全失败时单题反馈文本量随 k 增长；若把完整 stderr 回灌，模板展开与头文件路径会把单条反馈推到数百 token，挤占上下文。工程判断是只回灌首条根因错误而非级联错误链，因为级联错误多为同一根因的重复展开，信息冗余度高。

三 · 运行期正确性反馈：oracle 的判定边界

正确性判定先于性能比较，这是 CUDA-L1 抑制奖励作弊的核心次序：候选必须与参考实现逐元素比对通过才进入计时，未通过者直接进负例池。这个次序的代价是吞吐——错误候选也消耗一次完整 GPU 执行与一次比对，比对本身要读回输出张量，带宽开销与输出规模成正比。对于输出为大规模矩阵的算子，比对读回的字节数可能超过 kernel 自身写出的字节数，形成“验证比计算贵”的倒挂。

更细的工程问题在容差。给定材料明确指出正确性 oracle 仅为数值比对、容差标准未给出、缺少形式化或合约级验证。浮点归约、原子累加、快速数学函数近似都会引入与运算顺序相关的误差，固定绝对容差会在量级差异大的输入上误判：小量级输出上绝对容差过松会放过错误实现，大量级输出上过紧会把正确实现打成负例。可行做法是相对与绝对混合判据：

$$\text{pass} = \forall j:\ |y_j - \hat{y}_j| \le \tau_{\text{abs}} + \tau_{\text{rel}}\cdot|\hat{y}_j|$$

并把边界输入（极大、极小、含 NaN/Inf 的输入分布）纳入判定集，否则负例池会被浮点边界噪声污染，对比损失学到的是噪声排序而非真实优劣。具体例子：一个用 __fmaf_rn 重排累加顺序的候选在常规输入上与参考实现差异在 1e-6 量级，但在累加项量级相差 1e6 的输入上相对误差放大；若容差只按绝对阈值设定，该候选被误判为负例，模型会回避融合乘加这类本应鼓励的优化。

信息量层面，运行期反馈应携带失败位置而非仅布尔值：首个不匹配的下标、该位置的期望值与实际值、不匹配元素计数。这让负例从“数值不对”细化为“在某段索引区间偏差”，为后续对比采样提供方向。代价是回灌 token 与比对时的额外索引扫描时延。

四 · NCU/SASS 与 warp stall：离线诊断如何转成在线信号

NCU 提供的是因果证据而非奖励：SM 占用率、achieved occupancy、warp stall 原因分布（长记分牌等待、屏障、指令取指、执行依赖）、L1/L2 命中率、DRAM 吞吐、每周期指令数。SASS 层则给出指令混合、寄存器压力、分支与谓词化程度。这些指标回答“为什么慢”，而对比奖励只回答“谁更慢”。CUDA-L1 的在线闭环在给定材料中并未把 NCU 纳入回灌，这符合成本判断：NCU 采集是串行化、重放式的，单次 profile 的时延可达正常执行的数十倍，且指标落盘产生额外 I/O，若每轮对 k 个候选全量采集，闭环周期被 profile 主导。

可行的转译路径是把 profile 结论压缩为离散诊断标签再回灌，而非原始计数器。例如：长记分牌 stall 占比高 → 标签“访存延迟未隐藏”，提示方向为增加并行度或预取；屏障 stall 高 → “同步过密”，提示减少 __syncthreads 或改用 warp 级同步；寄存器溢出导致本地内存流量上升 → “寄存器压力”，提示缩小 tile 或重排计算；DRAM 吞吐接近峰值而 SM 利用率低 → “带宽受限”，提示减少冗余读写。标签化把连续计数器变成有限符号集，token 成本可控，且与模型的代码修改动作可直接对应。

具体例子：一个分块矩阵乘候选的 NCU 显示 DRAM 吞吐已接近平台峰值、SM 活跃周期占比低、长记分牌 stall 占主导，诊断标签为“带宽受限且延迟未隐藏”。对应的修改动作是把共享内存分块加大以减少全局读、或引入双缓冲预取；若只看加速比标量，模型只知道“比基线慢”，无法定向到这三类动作中的哪一个。这就是硬件反馈信息量优于裸 speedup 的直接体现：标量给排序，profile 给梯度方向。

代价必须计入：SASS 反汇编与 NCU 指标解析本身消耗工程实现复杂度与离线算力；标签化规则若过粗会把不同根因合并，过细则标签空间爆炸、回灌 token 上升。工程折中是每个算子族维护一小组合并标签（访存受限、计算受限、同步受限、占用率受限），并在离线阶段用 roofline 交叉验证标签正确性。

五 · roofline 诊断：把加速比放到可达上界下校准

裸加速比的问题在于它没有上界参照：一个候选比基线快 1.2 倍，可能已接近该算子的 roofline 上限，也可能离上限还有数倍空间。没有上界，对比奖励无法区分“接近最优”与“偶然更快”，也无法判断某轮迭代是否已进入平台期。roofline 给出的是算术强度与可达性能的映射：

$$P_{\text{roof}} = \min\left(P_{\text{peak}},\ I \cdot B_{\text{mem}}\right),\quad I = \frac{\text{FLOPs}}{\text{Bytes}}$$

把候选的实测吞吐与 Proof 比较得到“距上界比例”，这个比例可作为诊断标签而非奖励：比例低且算术强度落在带宽斜线上 → 访存受限；比例低且落在计算平台上 → 计算或占用率受限；比例接近 1 → 已接近该实现路径的上界，继续微调收益递减。这样加速比标量被放进一个有物理意义的坐标系，负例池中“更慢”的样本可按受限类型分层，对比采样时同层内比较才有意义。

具体例子：两个候选在同一算子上分别比基线快 1.1 倍与 1.3 倍，但前者算术强度低、落在带宽斜线且距上界仅 10%，后者算术强度高、距计算平台上界还有 3 倍空间。若只按加速比排序，前者被标为正例、后者被标为负例；按 roofline 校准后，后者的可改进空间更大，应作为优先探索方向而非简单负例。这说明对比奖励必须与 roofline 诊断联合使用，否则排序会把“已近最优”误当作“值得模仿”。

代价在于 roofline 需要准确的峰值参数与字节计数：字节数需按实际访存模式估算（含缓存复用折减），FLOPs 需按实现而非数学定义计数（融合乘加算两次浮点运算）。估算偏差会系统性偏移上界，导致诊断标签错位。工程上应把 roofline 作为离线校准工具，在线只回灌离散标签，避免把估算误差引入奖励。

六 · 为什么硬件反馈优于裸 speedup：信息量、延迟与作弊面

裸 speedup 作为唯一信号有三个结构性缺陷。其一，它是标量，同题候选排序只提供序关系，不提供“往哪个方向改”的信息，模型在负例上只能做无方向的重采样，样本效率低。其二，它可被作弊：不稳定的计时、缓存预热差异、跳过必要同步、减少输出写入都能抬高表观加速比，而正确性判定先于计时只能挡住“输出错误”，挡不住“计时口径被利用”。其三，它没有上界，无法判断收敛。

硬件反馈在这三点上分别补位。编译错误与运行错误提供方向性（错在哪一行、哪类构造）；NCU/SASS 标签提供受限类型（访存、计算、同步、占用率），把修改动作空间从全代码缩小到一类；roofline 提供上界校准，把“更快”转成“距可达上界更近”。信息量上的差别可用粗略的信道类比表述：标量反馈每轮传递约 log₂k 比特的序信息，而结构化反馈每轮传递的是类别加位置，量级上高出一个可分辨的层级——这不是精确的比特数结论，而是定性判断：结构化反馈让同一批候选产生更多可区分的负例类别。

延迟与成本是反面。硬件反馈的采集时延显著高于计时：编译诊断需一次完整编译，NCU 采集需重放与串行化，roofline 校准需离线峰值测量。因此在线闭环应保持“编译错误结构化 + 正确性布尔加位置 + 加速比标量”的轻量组合，把 NCU/SASS/roofline 放在离线诊断与课程设计环节，用标签化结果指导下一轮采样分布，而不是每轮全量采集。工程判断落在采样预算的分配上：把 k 个候选中的大部分用于轻量判定以维持闭环轮次，抽出少量候选做离线 profile 以更新诊断标签库，二者按轮次交替，才能在不被采集时延拖垮的前提下让反馈信息量持续增长。
