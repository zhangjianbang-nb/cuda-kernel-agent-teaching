一 · 一个推理服务的算子现场

设想一个已经上线的推理服务：模型结构固定，流量稳定，GPU 型号统一，SLO 卡在 P99 时延上。profiler 打开后，热点并不在某个巨大的 GEMM 上——cuBLAS 已经把那里榨得很干净——而是在一串形状古怪、语义琐碎的算子组合上：一个 fused residual + LayerNorm + 量化的 epilogue，一个带不规则 mask 的 attention 变体，一个 KV cache 上的 gather-scatter，一个 batch 维被压到很小的 GEMM。它们在 PyTorch eager 下由若干独立 kernel 拼成，中间结果反复往返 HBM；torch.compile 能吃掉一部分 launch 开销与访存，但遇到动态 shape、非标准 dtype 组合或自定义 epilogue 时，往往退回 eager 或生成一个并不比手写更快的 Triton kernel。这就是论文开篇那句判断的现场版本：高效 GPU kernel 对扩展现代 AI 系统是必需的，而它依然是一件复杂的事，因为硬件架构错综复杂、且需要专门的优化专业知识。

工程团队此时面对的不是“要不要写 kernel”，而是“这五个算子谁来写、写多久、写完谁来保证对”。一个能跑通的手写 CUDA 版本，从读懂 PyTorch 参考语义、确定数值容差、处理边界与对齐、到在目标卡上把 occupancy 与访存模式调顺，是以人周计的工作量；而性能上限取决于写它的人对 SM 结构、bank conflict、异步拷贝流水线的理解深度。这不是一个可以靠堆人线性扩展的过程，因为合格的人本身就稀缺。论文要回答的正是这个缺口：能不能让模型来承担这件事，并且承担得可信。

二 · 三条旧路径各自的代价

在 LLM 介入之前，工业界的做法大致三条，每条都有明确的成本结构。

手写 CUDA C++。控制力最强，能直接操作 shared memory 布局、warp 级原语、异步拷贝与流水线阶段数，性能上限最高。代价是开发周期与正确性风险同时最大：一个 off-by-one 的越界写不会立刻崩，而是在某个 shape 上静默污染相邻 buffer；一个未加 __syncthreads() 的读写竞争只在特定 occupancy 下暴露。维护成本同样高——硬件代际更替时，为上一代调优的 tile 尺寸与流水深度需要重调。可移植性差，同一份代码在另一张卡上可能掉一截。

Triton。用块级抽象换掉了大部分线程级手工管理，编译器负责 layout 与向量化，开发周期显著缩短，且天然带 autotune。代价是性能上限受编译器策略约束：编译器对 layout 的选择、对 reduction 的切分、对 mask 的处理，未必是这张卡上的最优解；一些需要精细控制流水线或 warp 特化的场景，Triton 表达不出来或表达出来也拿不到收益。更关键的是，Triton 的“正确”依赖编译器版本——升级一次工具链，数值行为与性能都可能漂移。

库调用。cuBLAS、cuDNN、CUTLASS 这类库在标准形状上是性能与正确性的双重保险，工程上最省心。代价是覆盖面的边界：非标准 epilogue、融合语义、特殊 dtype 组合、动态 shape，库要么不支持，要么需要用户自己写 epilogue 而 epilogue 恰恰是性能分水岭。库的调优目标是通用性，不是你这一个 shape。

三条路径的共同点是：它们都要求“人”具备专门的优化专业知识，而这正是论文指出的瓶颈。当模型规模与算子种类同时膨胀时，这个瓶颈不是靠流程优化能绕过去的。

三 · 为什么 LLM 直接接手会失败

直觉上，既然 LLM 能写一般顺序代码，写 GPU kernel 应该只是“换个语言”。论文给出的判断恰恰相反：LLM 在 GPU 代码生成上面对显著挑战，原因有三，且每一条都指向不同的工程后果。

高质量标注数据稀缺。通用代码语料里，CUDA 与 Triton 的占比极低，而“既正确又在目标硬件上高效”的样本更低——高效的 kernel 往往藏在闭源库与内部仓库里，公开的高性能实现与其调优理由（为什么这个 tile、为什么这个流水深度）很少成对出现。后果是：模型能写出语法正确的 kernel，但写不出符合硬件直觉的 kernel。论文由此得出一个关键推论：这排除了把监督微调（SFT）当作可扩展方法论的路径——没有足够的高质量标签，SFT 的天花板就是数据的天花板。

编译器的偏置。论文点明 compiler biases 是生成环节的障碍。生成出来的代码要经过 nvcc 或 Triton 编译器，而编译器会按自己的启发式改写：寄存器分配、指令调度、循环展开、向量化，都可能把你以为的“精心设计”抹平或扭曲。于是“源码看起来对”与“SASS 跑起来快”之间隔着一层不可见的变换。工程后果是：仅凭源码审查无法判断性能，必须看编译产物与实测。

反馈缺失。顺序代码的正确性可以靠单元测试廉价验证；GPU kernel 的正确性需要构造覆盖边界、对齐、dtype、shape 分布的输入，性能需要统一基线下的时延测量与 profile。没有这套环境，模型只能盲写。

把这三条合起来看，就得到论文的方法论选择：强化学习提供了数据高效且自适应的替代方案，但它要求能访问相关工具、谨慎选择训练问题、以及一个稳健的评测环境。这三项要求不是附属品，而是整个方案能否成立的前提——它们决定了奖励信号是否可信。

四 · 奖励必须挂在可验证的门上

论文给出的奖励形式把“正确”与“快”耦合成一个可验证的量：

$$R=\sum_{t=0}^{T}\gamma^{t}r_{t},\qquad r_t=\Delta\text{speed}_t\cdot\mathbb{1}[\text{pass}_t]$$

逐步奖励 r_t 是加速比增量乘以一个正确性指示函数。这个乘法的工程含义比它的数学形式重要得多：正确性是一道硬门，未通过则本步收益归零，无论这个候选比基线快多少。这直接对应生产端的判断——一个快 3 倍但偶尔算错的 kernel 在推理服务里是不可部署的，它的期望收益是负的，因为一次错误输出可能污染整个请求甚至整个会话。指示函数把这种非对称代价编码进了训练信号。

但硬门本身带来代价。第一，正确性检查必须足够严：如果 oracle 只覆盖少数几个 shape，模型会学会在这几个 shape 上过门、在别的 shape 上崩溃，这就是 shape 特化导致的离线分数与生产表现脱节。第二，Δspeed 的测量必须挂在统一基线上：基线若未开 TF32、未用最强库实现，加速比会被系统性高估，模型学到的是“打败一个弱基线”而不是“打败生产基线”。第三，每一步都要编译、运行、计时，这是一次真实的时延与算力开销——rollout 的吞吐被评测环境卡住，训练成本随验证严格度上升。第四，γ 折扣下的多步累积意味着一次早期错误会稀释后续正确步骤的贡献，若回退机制设计不当，模型会倾向于保守候选而非探索。

一个具体的失败模式值得在这里点名：reward hacking 与 fallback 会让正确率虚高。如果环境允许候选在失败时回退到参考实现并仍记为通过，那么“正确率”度量的是回退路径的可靠性，而不是模型生成 kernel 的能力。论文报告的单次尝试设置下的正确率从 43.7% 提升到 77.0%（+33.3 个百分点），这个数字之所以有意义，前提正是单次尝试、无回退、正确性门独立于性能门。

五 · 旧方案为什么非改不可：一个量化对照

把旧路径的成本与新方案的目标放在同一张表上，问题的紧迫性就具体了。论文报告，在单次尝试设置下，微调后的模型把 kernel 正确率从 43.7% 提到 77.0%，并把“性能超过 TorchInductor 的问题比例”从 14.8% 提到 21.8%（+7 个百分点）。当它被集成进一个完整的 coding agent 后，能在扩展的 KernelBench 套件上解决最多 97.4% 的问题，并在 72.9% 的问题上超过 PyTorch TorchInductor 编译器，几何平均加速比为 2.12。

这些数字的工程读法是：旧路径下，那五个古怪算子要么由稀缺的专家花人周手写，要么退回 eager 承受访存与 launch 开销，要么接受 torch.compile 的次优生成。新路径把“生成候选”的成本压到一次模型调用加一次编译加一次计时，把“筛选”的成本交给可验证的门。但代价同样明确：97.4% 的解决率是在论文给定的硬件、基线与输入分布上成立的；跨硬件、跨 dtype、跨框架的迁移未经验证；离线基准上的 2.12 倍几何平均加速比，在隐藏输入分布变化时可能因 shape 特化而崩塌。换句话说，旧方案的痛点是“慢且贵”，新方案的风险是“快但只在被验证过的分布上可信”。

这正是论文强调稳健评测环境的原因：它不是一个附属的工具链，而是把“可信”从口号变成可测量属性的唯一手段。没有统一基线、没有覆盖输入分布的正确性 oracle、没有编译与 profile 反馈的回灌，奖励信号就退化成对弱基线的过拟合。

六 · 一次完整流程里的成本落点

把论文描述的流程摊开，可以看到每一段的成本落在哪里。先读取参考实现与基准口径，确定输入分布与容差；再按方法生成候选；编译后在给定输入上做正确性检查；用统一基线测量时延与加速比；最后按反馈保留或回退候选，输出可复现的最优结果。

这段流程里，编译是第一个隐性成本：候选数量乘以编译时间，直接决定 rollout 的墙钟时间；Triton 的编译比 CUDA 快，但 autotune 会成倍放大编译次数。正确性检查是第二个成本：输入分布越宽，覆盖越可信，但每次检查都是一次真实执行，显存占用与运行时间随 shape 规模上升。计时是第三个成本：要压住测量噪声，需要重复运行与同步，单次候选的评测时延可能远大于其单次执行时延。反馈回灌是第四个成本：profile 结果（NCU 指标、SASS 差异）的数据量远大于一个标量奖励，把它塞进上下文会消耗 token 预算，取舍点在于“给多少 profile 细节才足以让模型定位瓶颈而不淹没在噪声里”。

这些成本共同决定了这套方法的经济性边界：它适合那些“手写太贵、库不支持、torch.compile 拿不到收益”的算子——也就是开场那个推理服务里的五个热点。对于标准 GEMM 这类库已经做到极致、且形状稳定的场景，让模型去挑战库的收益不足以抵消验证成本。工程判断因此不是“用不用 LLM 写 kernel”，而是“哪些算子值得进入这条可验证的生成-评测回路”，以及这条回路的正确性门与基线口径是否严到足以让离线分数在生产上站得住。

库调用与手写之间的“无人区”：为什么旧方案在推理服务里必然失效

在一个在线推理服务里，一个 fused residual-LayerNorm 算子被调用在每层每个 token 上。旧方案的第一选择是调库：cuBLAS、cuDNN、CUTLASS 或 PyTorch 原生算子。库的边界很清晰——它只对“标准形状、标准 dtype、标准布局”给出接近 SOL 的实现；一旦遇到非连续 stride、动态 batch、混合精度边界或需要跨算子融合的访存复用，库要么退回多 kernel 串联，要么直接不支持。多 kernel 串联的系统代价是可量化的：每个中间结果都要写回 HBM 再读回，一次 elementwise 融合缺失就多出两趟全局访存。设中间张量字节数为 $B$、HBM 有效带宽为 $BW$，仅这一次往返的额外时延下界为 $$t_{\text{extra}} \ge \frac{2B}{BW}$$，在 L2 无法容纳激活值的层规模下，这个下界就是实打实的端到端损失，而不是理论噪声。

第二选择是手写 CUDA 或 Triton。它突破了库的形状边界，但把成本转移到了工程侧：开发者要自己处理 bank conflict、warp 级归约、异步拷贝流水、occupancy 与寄存器压力的权衡。这段开发周期的代价不在写代码，而在验证——每个 tile size、每个 pipeline 深度都要重新做正确性回归与 NCU profile，一次调参轮次往往以“天”计。更棘手的是性能上限并不随人力线性提升：手写 kernel 的加速比相对 TorchInductor 常常只在个位数百分比区间，而维护成本随硬件代际、dtype 组合、shape 分布呈组合式增长。这正是论文所指的“intricate hardware architectures and the need for specialized optimization expertise”——瓶颈是专家注意力，不是算力。

旧方案真正的失效条件出现在“分布漂移”上：离线基准里 shape 固定、输入连续，手写 kernel 可以针对单一配置做极致特化；生产流量里 shape 是长尾分布，特化 kernel 在非目标 shape 上要么触发 fallback 到 eager，要么因 tile 不整除而性能塌陷。于是出现一个悖论——离线分数越高，往往意味着特化越深，生产端到端收益越不可信。这也是为什么论文把“robust evaluation environment”与“careful selection of training problems”并列为 RL 路线的前提：没有统一基线（PyTorch eager / torch.compile / 指定库）与统一输入分布，任何加速比都只是局部最优的自我证明。对照论文的单次尝试结果——正确率 43.7%→77.0%、超越 TorchInductor 的比例 14.8%→21.8%——可以看出旧方案留下的空白不是“能不能写出来”，而是“在正确性门与性能门同时约束下稳定写出来”的比例极低。
