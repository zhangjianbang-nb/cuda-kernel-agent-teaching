一 · 从「题面」到「可执行候选」：单轮提示的输入契约

SOL-ExecBench 的一次评测从一道题的题面对象开始，而不是从一段自然语言描述开始。题面对象至少携带四类字段：参考实现（release-defined 的 scoring baseline，即论文口径下的基线实现）、算子语义与数值容差、输入分布（shape/dtype/layout 的具体取值，BF16/FP8/NVFP4 三档）、以及该题在 SOLAR 中推导出的 SOL 界与对应硬件资源约束。单轮提示（single-shot prompting）把这一对象压成一段提示：语义描述 + 参考实现签名 + 输入清单 + 目标 dtype + 可用工具链（CUDA C++ / Triton / CuTe / PTX 由题目指定或由脚手架选择）。输出是一份候选源码文本，可能附带编译命令与自测脚本。

这一步的代价主要落在 token 上，而非算力上。参考实现越长、输入清单越细，提示越长；而 SOL 界本身不进提示——它是评测端的私有量，模型看不到 τ 与 s_i 的具体阈值，只能看到「请逼近硬件极限」的定性要求。这个信息不对称是刻意的：如果 SOL 界进入提示，模型会倾向于针对界做数值拟合而非真正写高效 kernel。工程上要付的代价是：题面序列化必须无损（dtype、stride、广播语义一个不能错），否则候选在第一步就注定失败，而失败原因会被误记成「模型不会写 kernel」。一个具体例子：某题要求 NVFP4 输入、FP32 累加、BF16 输出，若题面把累加精度写成 BF16，候选即便跑通也会在正确性门上被容差判死，这一轮生成的 token 全部沉没。

二 · 编译：把源码文本变成可加载模块的确定性关卡

候选源码进入编译阶段，输入是源码文本 + 题目指定的编译选项（架构目标 sm_100 级别的 Blackwell、优化级别、是否启用特定指令集），输出是共享对象或 cubin，以及一份编译日志。编译是整条流水线里唯一「确定性可复现」的关卡：同样的源码与选项，成败与警告集合稳定。因此它承担了第一道静态筛除——语法错误、未定义符号、不支持的 intrinsic、寄存器压力导致的编译失败都在这里被拦下，不消耗 GPU 时间。

代价有两块。其一是编译时延：CuTe/PTX 内联汇编与模板展开会显著拉长 nvcc 的编译时间，单题从数秒到数十秒不等，若 agent 脚手架在一轮里生成多个候选并全部编译，墙钟时间会成倍上升；其二是编译期的资源可见性——-Xptxas -v 给出的寄存器数、共享内存占用、spill 情况，是后续性能门的早期信号。一个具体机制：若候选的寄存器用量越过占用率拐点，编译器会插入 local memory spill，此时即便 kernel 逻辑正确，带宽也会被 spill 流量吃掉，SOL 得分被压到很低。工程判断是：把编译日志里的资源指标作为反馈的一部分回灌给下一轮，比等到运行期才发现 spill 便宜得多——前者只花编译时间，后者要花一次完整的 GPU 测量。

$$\text{occupancy}=\frac{\text{regs per thread}\times\text{threads per block}}{\text{regs per SM}}\ \text{与}\ \frac{\text{smem per block}}{\text{smem per SM}}\ \text{取紧者}$$

三 · 运行与正确性门：容差、隐藏输入与 fallback 的代价

编译通过后进入运行阶段。输入是模块 + 题目给定的输入分布实例，输出是候选在参考输入上的数值结果，以及一份与参考实现逐元素比对的正确性报告。正确性门不是单一阈值，而是按 dtype 分档的容差组合：BF16 允许较宽的相对误差，FP8 与 NVFP4 因为尾数位极少，必须同时约束相对误差与绝对误差，并对累加顺序敏感的场景放宽逐元素比较、改用统计量（如范数相对误差）。这一步的代价是显存与时间：FP8/NVFP4 的参考实现往往需要反量化到高精度再比对，中间张量的显存占用可能超过候选 kernel 本身的占用；若题目是反向传播（backward），还要额外保存前向的中间激活，显存峰值进一步抬升。

更关键的是隐藏输入分布。题面给出的输入清单是公开的，但评测端另有一组未公开的 shape/layout 组合，用来检测 shape 特化。一个具体失败模式：候选把 block 大小与 tile 形状硬编码成公开输入的最优解，在隐藏输入上要么越界、要么占用率崩掉，正确性门通过而性能门崩塌，或者反过来在边界 shape 上直接算错。论文提供的沙箱化 harness 用隔离子进程执行、GPU 时钟锁定与 L2 cache 清空来保证测量可复现，同时用静态分析检查常见 reward hacking 手法——例如检测候选是否偷偷调用基线库、是否在计时区间外做预计算、是否读取环境变量分支到「快路径」。这些检查本身有代价：静态分析对源码做模式匹配，会误伤合法的库调用（比如题目允许调用 cuBLAS 的题），需要按题配置白名单；隔离子进程带来进程启动与 CUDA context 初始化的固定开销，单题测量墙钟被拉长，但对消除跨题污染是必要的。

四 · 计时与 SOL 得分：把「快」换算成「离硬件极限多近」

性能门的输入是候选在锁定时钟、清空 L2 后的多次计时采样，输出是时延中位数与由 SOLAR 推导的 SOL 界之间的比值。论文的 SOL Score 定义为候选在「基线到硬件 SOL 界」这段区间里填补的比例，其单题得分沿用加速比形式 s_i = T_base,i / T_cand,i，再与阈值 τ 比较后聚合：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

注意这里的分子是 release-defined 的 scoring baseline 时延，而非候选相对某个可变软件实现的加速比——这正是 SOL-ExecBench 与以软件基线为参照的基准的分野。SOL 界由 SOLAR 解析推导：按算子的访存量与计算量，分别算出带宽受限与算力受限两条下界，取紧者，再叠加该 dtype 在 Blackwell 上的有效吞吐折减。这一步的代价是测量噪声：GPU 时钟锁定消除了频率漂移，但 L2 清空与冷启动使每次采样都带固定开销，采样次数不足时中位数会被离群值污染；采样过多则单题墙钟线性增长。工程判断是固定采样次数并取中位数，把噪声预算写进 harness 而不是留给评测者临场决定。

一个具体例子：某题在 BF16 下是带宽受限，SOLAR 推出的界对应「读一遍输入、写一遍输出」的最小访存量；候选若做了多余的中间物化（比如先写临时缓冲再读回），即便算术完全正确，s_i 也会明显低于 1，SOL Score 落在阈值之下。此时反馈信号不是「算错了」，而是「多了一次全局内存往返」——这正是 SOL 口径相对软件基线口径的诊断价值：它把性能差距归因到具体的资源维度上。

五 · agent 脚手架与 RL 回路：反馈如何变成下一轮的输入

把上述四步串成回路的是 agent 脚手架。它的输入是上一轮的完整轨迹：题面、候选源码、编译日志（含寄存器/spill 指标）、正确性报告、计时采样与 SOL 得分，以及（若启用）NCU/SASS profile 的摘要。输出是下一轮的动作：改写候选、调整编译选项、换工具链（例如从 CUDA C++ 退到 Triton 以降低模板复杂度）、或宣告放弃。脚手架的策略空间决定了回路的形状：单轮提示只走一次生成—编译—运行—评测；多轮 agent 允许在同一题上迭代若干次，每次迭代都要重新付编译与测量成本；RL 回路则把整条轨迹的终局得分当作可验证奖励，回灌到策略更新。

这里的核心机制是「反馈的选择性」。把全部日志原样塞回提示会迅速撑爆上下文：一次 NCU profile 的指标表加上 SASS 反汇编，token 量远超题面本身。可行的做法是抽取少量判别性信号——spill 字节数、实际占用率、访存吞吐占 SOL 界的比例、以及正确性门失败时的首个不匹配元素位置与误差量级——组成一段短反馈。代价是信息损失：抽取规则若偏向某一类指标，策略会被引导去优化那一类，而忽略未被抽取的瓶颈。RL 回路还额外付采样成本：每道题的多轮轨迹都要真实编译与真实计时，GPU 时间随轮数线性增长，而奖励是稀疏的（只有终局 SOL Score 过阈值才为正），这使得信用分配必须落在「哪一轮的哪个改动带来了得分跃迁」上。一个具体例子：某候选第一轮因 spill 得分低，第二轮仅把 tile 从 128 降到 64 就跨过阈值，若反馈里没有寄存器指标，模型无从知道该改什么，只能盲目重采样。

六 · verifier 的边界：正确性 oracle 能证明什么、不能证明什么

verifier 在流水线里出现两次：一次是运行期的正确性门（经验性 oracle，比对参考输出），一次是静态分析检查（规则性 oracle，拦截 reward hacking）。前者能证明「在这组输入上数值一致」，不能证明「在所有合法输入上一致」——隐藏输入分布正是为了压缩这个缺口，但它仍是抽样而非证明。后者能拦截已知的作弊模式，不能拦截未列入规则的取巧，例如利用计时区间的边界条件做惰性求值。要真正闭合正确性，需要形式化方法介入：对访存索引做符号验证、对归约顺序做浮点误差界推导，代价是每题都要写规约与不变量，工程成本远高于经验比对，因此只对少数高风险题启用。

更隐蔽的漏洞在性能侧：SOL 界本身是解析推导的产物，若 SOLAR 对某算子的访存建模偏保守（例如忽略了片上复用），界会偏松，候选轻易跨过阈值却并未真正逼近硬件极限；反之建模偏激进，界不可达，所有候选都被判失败。这不是 verifier 能修的，而是界推导的建模误差。工程判断是：把 SOL 界当作「可比口径」而非「物理真值」，跨题比较得分有意义，单题得分接近 1 时反而要回头核对 SOLAR 的建模假设。verifier 的代价最终落在可信度上——沙箱、时钟锁定、L2 清空、静态分析这一整套 harness 的复杂度，换来的是分数可复现；任何一处省略，都会让 SOL Score 在跨机器、跨批次比较时失去意义。

边界条件：SOL 口径下的失效模式与系统代价

SOL-ExecBench 的评测闭环把“相对软件基线的加速比”替换成“向硬件 SOL 上界的收敛度”，这一替换直接改变了 agent 优化器的激励结构，也引入了一类新的失效面。核心量是 SOL Score：给定 release 定义的 scoring baseline 时延 $T_{\text{base}}$ 与 SOLAR 解析推导的硬件下界 $T_{\text{SOL}}$，候选 kernel 的时延 $T_{\text{cand}}$ 所闭合的差距比例为

$$\text{SOL Score}_i=\frac{T_{\text{base},i}-T_{\text{cand},i}}{T_{\text{base},i}-T_{\text{SOL},i}},\qquad \text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\text{SOL Score}_i\ge\tau]$$

分母 $T_{\text{base}}-T_{\text{SOL}}$ 是这道题的全部可争夺空间，它由 SOLAR 的解析界决定，而不是由某个可被替换的库实现决定。这意味着一旦 SOLAR 对某算子的界推导偏松（例如对 NVFP4 下混合精度数据搬运与张量核吞吐的联合约束建模不足），分母被高估，候选 kernel 即使已经贴近真实硬件极限，SOL Score 仍被系统性压低；反之界偏紧则分母趋近于零，任何微小抖动都会让分数在 0 与 1 之间跳变，阈值 $\tau$ 附近的判定失去统计意义。这是该方案最本质的边界：分数可信度完全寄生在解析界的正确性上，而解析界对 Blackwell 专属能力（BF16/FP8/NVFP4 前向与反向、依赖新指令路径的 kernel）的刻画恰恰是最难验证的部分。

第二类失效来自测量侧。为支撑 agentic 优化器的鲁棒评测，论文提供沙箱化 harness，包含 GPU 锁频、L2 cache 清除、隔离子进程执行与针对常见 reward hacking 的静态分析检查。这些机制各自有代价：锁频消除了时延抖动但把 GPU 钉在固定频率点，跨 SKU 迁移时该频率点未必是生产频率，SOL 界与实测时延的相对关系会漂移；L2 清除保证冷缓存口径一致，却使每次测量多出一次显式的 cache flush 开销，单题测量时延被拉长，agent 多轮迭代的墙钟成本随之上升；隔离子进程让崩溃与非法内存访问不污染主进程，代价是每次候选评测都要付出进程启动与 CUDA context 初始化的固定开销，在 235 题 × 多轮候选的规模下这笔开销不可忽略。静态分析检查能拦住明显的作弊模式（例如绕过计时区、复用缓存结果），但对“shape 特化”这类合法却脆弱的优化无能为力。

第三类失效是泛化断层。SOL-ExecBench 的题面来自 124 个生产与新兴模型的真实算子，覆盖语言、扩散、视觉、音频、视频与混合架构，但评测只在论文给定的输入分布上进行。agent 完全可以在这一分布上把 kernel 写成对特定 shape、特定对齐、特定 dtype 组合的硬编码路径，SOL Score 逼近 1，而生产端换一个 batch 或换一个 head 维度就退化为 fallback。这类候选在离线基准上表现为高分，在端到端回归中却可能因额外的分支判断与寄存器压力反而慢于通用实现。工程判断上，SOL Score 必须与“输入分布外抽样”和“端到端时延回归”两项联合使用：前者检验 shape 鲁棒性，后者检验 kernel 在真实模型图中的收益是否被 launch 开销、访存模式变化与流水线气泡吞掉。单看 SOL Score 的排行榜，本质上是在奖励对固定分布的过拟合，这与该基准想要衡量的“贴近硬件高效执行”之间存在张力。
