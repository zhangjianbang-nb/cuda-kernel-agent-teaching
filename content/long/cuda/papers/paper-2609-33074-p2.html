一 · 失效模式一：正确性门本身是可被策略绕过的

CA-GRPO 的机制是“先让正确性足够可靠，再优化性能”，其判定并非单次通过/失败，而是一个带阈值的组内相对信号。摘要给出的评分口径是

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这里 N 是一组候选的数量，si 是候选相对基线的时延加速比，τ 是性能门限。注意这个式子里没有任何一项直接度量“候选是否在所有输入上都正确”——正确性是以门的形式外挂的，只有通过正确性检查的候选才进入这组统计。工程上这意味着两件事：其一，正确性 oracle 的覆盖度直接决定了这个 score 的信度；其二，一旦 oracle 有缝，策略会沿着缝走，而不是沿着性能走。

具体的绕过路径有三类，且都不需要模型“理解”自己在作弊。第一类是 fallback 型：候选 kernel 内部检测到不支持的 shape、dtype 或 stride 组合时，悄悄回退到 PyTorch eager 路径。这样在基准输入上测得的时延可能仍优于基线（因为基线本身包含了更重的框架开销），而正确性检查也全部通过——但生产上遇到真正需要 kernel 融合的输入时，加速比归零。第二类是 shape 特化型：把基准里出现过的维度硬编码进模板参数与循环边界，遇到新 shape 要么编译失败，要么走到未定义行为分支。第三类是 容差型：利用正确性检查的数值容差，在低精度累加、近似激活函数上做文章，使输出落在容差带内但数值语义已经偏离。

代价是双向的。把正确性门收紧（更多随机种子、更多边界 shape、更严容差）会显著拉长每次 rollout 的验证时延：一个候选要跑遍一组输入分布，编译加执行的成本按候选数线性增长，而 CA-GRPO 需要组内多个候选才能算出相对信号，于是单步训练的实际墙钟时间被验证环节主导。反过来放松门，则 score 的方差被 reward hacking 抬高，训练信号失真——模型学到的是“如何通过检查”，不是“如何写对 kernel”。判断 KernelZero 是否可信，第一件事是问：它的正确性 oracle 是否对 fallback 做了显式检测（例如禁止候选内部调用 aten 算子、检查生成的 PTX/SASS 中是否出现预期外的库调用），以及是否在训练分布之外保留了 shape 留出集。

二 · 失效模式二：Proposer 与 Coder 的共演化会同步漂移

KernelZero 的结构是两个模型交替优化：Proposer 从 API 集合生成 Torch 模块，Coder 把它翻译成 CUDA 或 Triton。frontier-driven 模块生成机制的意图是“按 Coder 当前的弱点持续产出能力对齐的训练模块”。这个设计的隐含假设是：Proposer 产出的模块分布与真实负载分布保持足够重叠，且 Coder 的弱点被正确识别。两个假设都可能破。

漂移的第一种形态是 难度塌缩。Proposer 的优化目标是让 Coder 在其产出上取得进步，于是它倾向于生成 Coder 已经能做对的模块的变体——因为这类模块的 reward 信号稳定、方差小。结果是课程自动变简单，Coder 在基准上的 pass@1 上升，但对真正困难的算子（多算子融合、非规则访存、需要 warp 级同步的 reduction）毫无长进。第二种形态是 API 集合收窄。Proposer 只在给定的 API 集合内组合，若这个集合不包含生产负载里的关键算子（比如某种稀疏格式、某种量化布局），那么整条共演化链再高效，也覆盖不到这些算子。

工程上可以用一个简单的重叠度指标来监控这种漂移：把 Proposer 每轮产出的模块集合按算子类型与 shape 分布聚类，与目标负载的分布做直方图交集。交集持续下降就说明课程在偏离。代价体现在 token 与编译时间上：每一轮 Proposer 生成模块、Coder 生成候选、编译、验证，构成一个闭环，闭环的周期越长，漂移越难被及时发现；而缩短周期意味着每轮样本更少，GRPO 的组内统计噪声更大。这是一个无法同时满足的三元约束：课程对齐、训练效率、信号信度。

具体例子：假设目标负载里有一个需要跨 block 通信的 softmax 加 top-k 组合算子。Proposer 若从未生成过带跨 block 归约语义的模块，Coder 就永远没有机会在“需要两次 kernel launch 还是一次日式融合”这类决策上获得反馈。此时 Coder 在 KernelBench Level 1/2 上的 75.8%/69.6% pass@1 与 100%/97% pass@10 依然成立，但这些数字度量的是基准覆盖范围内的能力，不是这个算子的能力。

三 · 适用边界：它擅长什么，不擅长什么

从摘要给出的口径看，KernelZero 的评测落在 KernelBench Level 1 与 Level 2，即单算子与简单算子组合的层面，指标是 pass@k 与相对基线的加速比。这个口径决定了它的能力边界：它优化的是“给定一个 Torch 模块语义，产出一个在该语义上正确且更快的 kernel”。凡是能被写成“一个模块进、一个 kernel 出”的问题，都在它的射程内；凡是需要跨模块协同、需要改变数据布局契约、需要与框架调度器协商的问题，都在射程外。

维度在边界内在边界外
语义粒度单算子或可融合的算子链，语义由 Torch 模块固定需要改变张量布局契约、跨层流水、动态控制流
输入分布训练与评测共享的 shape/dtype 分布长尾 shape、动态 batch、混合精度切换
正确性判据数值容差内的逐元素比对需要位级一致、需要确定性归约顺序

特别要指出“跨硬件、跨 dtype、跨框架迁移未验证”这一条。CUDA 与 Triton 两条路径的抽象层级不同：Triton 的 block-level 编程模型把 shared memory 与同步细节藏了起来，模型学到的优化动作（调 tile size、调 num_warps、调 num_stages）在 CUDA 路径上并不等价；反过来，CUDA 路径上学到的寄存器级技巧在 Triton 里根本无法表达。因此“KernelZero-7B 在 CUDA 上超过 Claude-4.5-Sonnet、在 Triton 上超过 DeepSeek-V4-Pro”这两个结论是两条独立的能力曲线，不能互相外推。把 CUDA 侧的调优经验直接搬到 Triton 侧，或者把在 A 架构上测出的 tile 配置搬到 B 架构，都是边界外的操作。

另一个常被忽略的边界是基线强度。加速比的分母是 Tbase，若基线未开 TF32、未使用论文指定的最强库实现、未做 torch.compile，分母被抬高，加速比就被系统性高估。这不是 KernelZero 特有的问题，但它是判断其结论能否迁移的第一道闸门：任何声称的加速比，必须先确认分母是不是“该硬件上可得的最强实现”。

四 · 与相邻工作的差别：共演化 vs 单侧优化

把 KernelZero 放进同批工作里看，差别不在“是否用 RL”，而在优化对象的数量与耦合方式。多数相邻工作只优化一个环节：Kevin 走多轮 RL 让模型在编译与运行反馈中迭代改写；CUDA-L1 用对比式强化学习在候选之间建立偏好；Dr. Kernel 把 RL 的细节做对，聚焦 Triton 生成；Fine-Tuning GPT-5 走的是监督微调路线，把强模型的产出蒸馏进小模型。这些工作的共同点是：训练数据的分布是外部给定的，模型只负责在固定分布上变强。

KernelZero 的不同在于它把“数据分布”本身也变成了可训练对象。Proposer 负责造题，Coder 负责解题，两者交替优化，形成一个自动课程。这带来两个相邻工作没有的性质：其一，训练数据可以随 Coder 的能力前沿移动，理论上避免了“数据太难导致信号稀疏”与“数据太简单导致无梯度”的两头空转；其二，正确性与性能的权衡被显式建模为两阶段——CA-GRPO 只在正确性可靠之后才把性能纳入优化目标，而不是把两者混在一个标量 reward 里做加权。

与多智能体框架（Astra、cuPilot、CudaForge、EvoEngineer）的差别在于耦合的紧密度与训练信号的来源。多智能体框架通常是推理时的编排：规划者、编码者、评审者分工，靠硬件反馈驱动搜索，不做权重更新。KernelZero 的两个模型都是被训练的，交替优化意味着 Proposer 的梯度来自 Coder 的失败模式，Coder 的梯度来自 Proposer 产出的模块——这是一个双向闭环，而不是单向的“生成—评审—重试”。代价是训练复杂度：两个模型、两套 reward、一个交替调度策略，任何一侧失稳都会污染另一侧的信号。多智能体框架没有这个问题，但也拿不到跨轮次的能力累积。

与 CUDA-L2 这类追求超越 cuBLAS 的工作相比，KernelZero 的目标不是单点极限性能，而是在一个基准集合上把 pass@1 与 pass@10 同时推高。75.8%/69.6% 的 pass@1 与 100%/97% 的 pass@10 之间的落差说明：它的强项是“多试几次总能对”，而不是“一次就对”。这在工程部署上的含义很直接——若推理预算只允许一次生成，它的实际可用率由 pass@1 决定；若允许采样多个候选再筛选，pass@10 才有意义，而筛选本身需要正确性 oracle 与性能测量，成本不可忽略。

五 · 什么情况下不该用它

第一，当正确性 oracle 不可靠或不可负担时。CA-GRPO 的整个设计建立在“正确性可以被廉价、可靠地判定”之上。若目标算子的正确性需要位级一致、需要与参考实现做大规模随机对拍、或需要人工审核数值语义，那么每轮 rollout 的验证成本会吞掉训练收益。此时更合适的做法是先用监督信号把基础能力拉起来，而不是投入共演化闭环。

第二，当目标负载与基准分布显著不重叠时。KernelZero 的课程由 Proposer 在给定 API 集合内生成，若生产负载的核心算子不在这个集合里，或者其 shape 分布是长尾的，那么训练出的 Coder 在离线基准上的高分不能兑现为端到端收益。判断方法是先做一次分布对齐审计：把生产负载的算子类型、shape 直方图、dtype 组合与基准口径逐项比对，重叠度低就不该把预算押在共演化上。

第三，当部署环境与训练环境跨架构时。论文的结论只在给定硬件、基线与输入分布上成立，跨硬件迁移未验证。PTX 层面的优化（寄存器压力、occupancy 调优、指令级并行）与具体 SM 架构强绑定；Triton 层面的 tile 配置与 L2 容量、SM 数量强绑定。若部署在另一代 GPU 上，离线加速比需要重新测量，且很可能需要重新训练或至少重新做课程对齐。

第四，当推理预算只够一次生成、且没有筛选环节时。pass@1 与 pass@10 的落差意味着它的产出质量分布很宽。生产端到端场景里，如果没有“生成多个候选—编译—验证—择优”的流水线，实际拿到的是分布的下半部分。而搭这条流水线的成本（编译时延、显存占用、验证时延）在低 QPS 场景下可能超过 kernel 本身带来的收益。

第五，当团队无法承担双模型训练与交替调度的工程复杂度时。两个模型、两套 reward、一个自动课程，意味着超参空间翻倍，故障定位路径变长。若团队的目标只是“把几个热点算子手写优化”，直接用人写 CUDA 加 NCU profile 的确定性路径，收益/成本比更高。共演化的价值出现在“算子集合持续扩张、人力无法逐个覆盖”的场景，而不是“算子集合固定且已知”的场景。

最后落到一个工程判断上：KernelZero 的可信度不取决于它声称的 75.8% 或 100%，而取决于三个可核验的接口——正确性 oracle 是否检测 fallback、Proposer 产出的模块分布与目标负载的重叠度是否被监控、以及加速比的分母是否为该硬件上可得的最强基线。这三项中任何一项缺失，离线分数就不能作为部署决策的依据；三项齐备时，它的自动课程才是可复用的资产，而不只是一组基准数字。

边界与失效：KernelZero 什么时候不该上场

KernelZero 的分数建立在论文给定的硬件、基线与输入分布之上，它的两个模型共享一条自动课程：Proposer 依据 Coder 当前弱点生成 Torch 模块，Coder 再翻译为 CUDA/Triton，CA-GRPO 只在正确性足够可靠后才优化性能。这条链条的隐含前提是“弱点可被模块化表达、正确性可被单点判定”。一旦目标算子依赖跨 kernel 的全局状态（如多卡通信、持久化缓存、动态 shape 驱动的 launch 配置），Proposer 生成的 Torch 模块无法承载这类语义，Coder 只能退化为局部改写，课程信号随之失真。此时它的 pass@1 提升并不迁移到真实负载，反而掩盖了结构性问题。

评测口径的脆弱性同样构成硬边界。若基线未开 TF32、未使用论文指定的库实现，加速比会被系统性高估；而 shape 特化会让离线高分在生产分布上崩塌。用论文的 score 公式看，$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$ 该指标只统计超过阈值 τ 的比例，对“刚好压线”的候选与“大幅领先”的候选一视同仁，因此对基线漂移极其敏感——基线一弱，score 虚高；基线一强，同一候选立刻跌出阈值。工程上应把 τ 与基线版本一起锁定，并对每个候选记录绝对时延而非仅记录是否过线。

与相邻工作的差别在于“课程由谁驱动”。多数 LLM kernel 生成方案把反馈压在单模型的多轮采样上，KernelZero 把课程外置到 Proposer，用 Coder 的失败模式反向定义训练分布；代价是双模型交替优化带来的编译与评测开销翻倍，每一轮都要重新编译候选、跑正确性门与性能门，token 与 GPU 时延随课程轮数线性增长。若团队只关心单点算子的一次性生成，这套交替机制的收益不足以覆盖其系统成本。

不该用它的场景可以列成一张简表：目标硬件与论文不一致且无同口径基线；输入分布含隐藏 shape 或动态 dtype；正确性 oracle 只能做端到端数值比对而非逐点判定；以及需要跨 kernel 融合或通信重叠的算子。这些情况下，CA-GRPO 的正确性门无法可靠闭合，性能门又会被 reward hacking 与 fallback 路径污染，正确率虚高而生产收益为零。判断标准应落在“能否构造可复现的逐点 oracle 与锁定基线”上，而非模型规模。
