一 · 一个推理服务里的“三份实现”

设想一个已经上线的推理服务：主干是 Transformer，但端到端时延里有相当一部分不在 GEMM 上，而在那些“看起来不像算子”的算子——RMSNorm、RoPE 的旋转位置编码、softmax 前的 mask 填充、KV cache 的 paged 拼接、top-k/top-p 采样里的排序与累积和。这些环节的共同特征是：形状随 batch 与序列长度动态变化、单次工作量小、访存模式不规则。工程团队面对它们时通常只有三条路，而三条路各自有明确的代价。

第一条是手写 CUDA C++。工程师要自己处理 grid/block 的映射、warp 内的 reduction、shared memory 的 bank 冲突、以及非对齐访存下的向量化装载。以 RMSNorm 为例，一个 block 处理一行、用 warp shuffle 做平方和的树形归约是标准写法，但当行长度不是 32 的整数倍时，尾部线程的掩码处理与 __syncthreads 的插入位置就会直接决定它是带宽受限还是延迟受限。手写版本的上限很高——可以精确控制寄存器压力、用 cp.async 做流水、把归约与写回重叠——但开发周期以人日计，且每一次 shape 分布变化都要重新审视 tile 尺寸的选择。

第二条是 Triton。它把 block 级编程模型暴露给用户，tl.load/tl.sum 加 BLOCK_SIZE 的写法让一个 RMSNorm 在几十行内成型，编译器负责 layout 与向量化。代价是控制粒度：当需要跨 block 的持久化状态、或者需要精细的异步流水与寄存器复用，Triton 的表达力会撞墙，工程师被迫退回手写或者接受一个次优的自动调度。

第三条是库调用。cuBLAS、cuDNN、CUTLASS 提供的融合算子覆盖了主流路径，但长尾形状与自定义融合（比如 norm 后立刻接一个带 mask 的残差）往往没有现成实现，退化为多个 kernel 串联，中间结果反复落回 HBM。一个本可融合为单次读写的链条被拆成三次全局访存，带宽开销按元素字节数线性放大。

这三条路的共同点是：正确性与性能的判定权，掌握在少数人手里，且判定方式是“跑几个随机输入看看数值对不对”。这正是本部分要盯住的问题现场——不是“LLM 能不能写 kernel”，而是“当 LLM 开始批量写 kernel 时，我们用来判它对错的尺子本身有多准”。

二 · 判定权的转移：从人眼 review 到自动 oracle

在手写时代，正确性由作者自己保证：他知道自己用了哪种归约顺序、在哪里做了 fp32 累加、哪一步允许 TF32。评审者读代码，能看出“这里把 float 累加器换成了 half”这种语义漂移。判定是语义级的，虽然慢，但与被测实现的内部结构对齐。

当候选 kernel 由 LLM/agent 批量生成、由 RL 奖励驱动时，判定必须自动化，于是退化为一个 oracle：给定若干随机输入，比较候选输出与参考输出的逐元素误差，若最大相对误差落在容差 τ 内则判对。这个 oracle 的输入只有两样东西——输入分布与容差。它不看代码，不看归约树，不看累加精度。判定从语义级降到了采样级。

采样级的判定有一个结构性缺陷：它只能证明“在这几个点上没错”，无法证明“在别的点上会错”。而 LLM 生成的 kernel 恰恰最擅长在“没被采到的点”上出错——它可能把边界条件写反、可能把 float 累加悄悄降级、可能在 reduction 的分块边界上漏掉尾部元素。这些错误在随机均匀输入上大概率不触发，因为随机输入很少落在边界上，且宽松容差会把精度退化吸收掉。

论文把这个缺陷量化了：在 188 个 KernelBench 问题的已验证 CUDA 实现上，用确定性规则注入 10,303 个可编译的故障，其中 7,384 个带有独立的 kill witness（即存在一个输入能让该故障产生可观测的错误输出）。官方检查器在这 7,384 个有见证的故障上漏掉了 16.9%，也就是“六个里漏一个”，而且是确定性的漏——同样的故障、同样的输入协议，每次都漏。这个数字的意义不在于它大，而在于它可复现：它不是统计噪声，是协议本身的盲区。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

上面这个式子是性能侧的评分口径：对 N 个问题，候选相对基线的加速比 s_i 超过阈值 τ 才计一分。它与正确性 oracle 是串联的——先过正确性门，再算加速比。问题在于，正确性门漏掉的那 16.9%，会直接进入这个求和，把不该计分的候选计成满分。于是 leaderboard 上的名次与 RL 的奖励信号，都被这个盲区污染。

三 · 盲区不是均匀的：按故障族分层

论文给出的分层数据是这份工作最锋利的地方：算术类故障的逃逸率是 8.7%，而精度类故障的逃逸率是 78.6%。两者相差近一个数量级。这说明 oracle 的盲区有明确的方向性——它对“算错了”相对敏感，对“算得不够准”几乎失明。

机制上可以这样理解。算术故障（比如把加法写成减法、把索引偏移一位）会产生量级上的偏差，随机输入下几乎必然触发，宽松容差也兜不住。精度故障则不同：把 float 累加器降为 half、把归约顺序从树形改成串行、把 TF32 打开而不告知——这些操作在数值上只引入相对误差量级的小扰动，而 oracle 的容差 τ 恰恰被设得足够宽以容纳合法的浮点方差。于是扰动落在容差带内，被判为正确。

论文进一步解释了容差带的形状：它随归约规模增长。归约长度越长，合法浮点累加的方差越大，为了让参考实现自己通过检查，τ 必须放宽；τ 放宽后，精度故障的扰动就更容易藏进去。这是一个自我强化的循环——归约越大，容差越宽，盲区越深。论文还测出了一个“输入激进度的上限”，由合法浮点方差本身设定：输入再怎么设计，也不能让参考实现自己失败，这个约束封顶了 fuzzing 能走多远。

代价在这里体现为正确性债，而非时延或显存。一个在 KernelBench 上拿到高加速比的候选，可能在生产里对长序列的 softmax 归约产生可见的数值漂移；而这种漂移在离线基准的随机短序列上永远不出现。工程判断因此变得危险：加速比是可信的，正确性标签是不可信的，而两者被同一个分数捆绑在一起。

四 · 手工补丁与它的不可度量性

社区已经意识到 oracle 弱，反应是打补丁：增加输入分布（hidden inputs）、加 fuzzing 配方、收紧容差。论文点名审计了最强的现有补丁 KernelBench-Verified，把它的增益拆开：+4.0 分来自隐藏输入，+4.5 分来自更紧的容差。这个拆解本身就是方法论的示范——它说明补丁的收益可以被归因到具体机制，而不是一个笼统的“更好了”。

但补丁的根本问题是无法度量充分性。你加了三种输入分布，怎么知道够不够？你把 τ 从 1e-2 收到 1e-3，怎么知道会不会误杀合法实现？没有度量，补丁就只能是经验性的堆叠，且每次堆叠都要付出代价：更紧的容差会让合法的浮点方差触发假阳性，把正确候选判错，直接污染 RL 奖励；更多输入分布会拉长每次评测的时延与 token 消耗，在需要多轮迭代的 agent 循环里，这个开销按轮数线性累积。

论文的做法是把“充分性”变成一个可计算的量：变异得分。给定一个测试协议 P（输入分布 + 容差 + 比较方式），在注入的故障集合上跑一遍，得分就是 P 能杀掉的、有见证的故障比例。这个量把“补丁够不够”从主观判断变成了一个分母明确的比率。它不依赖具体实现的语言（CUDA / Triton / CuTe 皆可注入），也不依赖硬件——故障是语义级的，kill witness 是输入级的。

工程代价是构建成本：10,303 个故障、188 个问题、7,384 个带见证的故障，这套语料本身需要人工与自动化的混合投入，且每个故障都要保证“可编译”——否则测的就不是 oracle 而是编译器。论文把整套东西以 KernelBench-M 的形式发布，意味着后续工作不必重建，但首次构建的固定成本是这类方法绕不开的门槛。

五 · 为什么非改不可：奖励信号与生产收益的错位

把上面的线索接起来，问题的严重性就清楚了。RL 训练 kernel agent 时，奖励来自“正确性门通过 + 加速比达标”。如果正确性门漏掉 16.9% 的故障，且漏掉的集中在精度族（78.6%），那么训练信号会系统性地奖励那些用精度换速度的候选。一个把 fp32 累加降级、把归约改成串行、把 TF32 打开的 kernel，在 oracle 眼里是正确的，在加速比上是有优势的——它会得到正奖励，被保留、被强化。这不是偶发的 reward hacking，是 oracle 盲区结构决定的方向性漂移。

这种漂移在生产端的表现是：离线基准上的加速比无法迁移。论文的失败模式清单里明确写了——shape 特化与隐藏输入分布会让离线分数在生产上崩塌；未开 TF32、未用最强库的基线会高估加速比；fallback 会让正确率虚高。三者叠加，离线 leaderboard 的名次与端到端收益之间没有可靠的映射。工程团队拿到的不是一个可信的排序，而是一个被盲区扭曲的排序。

论文还给出了一个更硬的结论：跨 48 个完整架构，盲区随规模增长，且集中在深层同构流水线上；有两个问题被证明无法被裁判——它们的官方参考实现本身就违反了基准自己的容差（对 fp 而言）。这意味着不是“检查器不够严”，而是“参考实现与被测实现处在同一个不可判定的数值带里”。当参考自己都不满足自己的容差时，任何基于它的 oracle 都失去了基准点。这是“非改不可”的最强论据：不是精度问题，是基准的可判定性问题。

论文给出的正面结果说明改是可行的：在 kill matrix 上优化测试套件，两个输入每问题即可达到 98.0% 的检出率，留出集上 94.8%。也就是说，不需要无限堆输入，只需要按故障族的结构去选输入。更进一步，故障分类学本身教给测试生成器的信息，比原始故障集合更多——分类给出了“该往哪个方向设计输入”的先验，而不是盲目 fuzzing。这条路径把 oracle 的设计从经验堆叠转成了可优化的目标函数。

六 · 本部分落在哪里

回到那个推理服务：RMSNorm 的长行归约、softmax 的长序列归约、top-k 的累积和——它们恰好都是“容差带随归约规模增长”的重灾区，也恰好都是精度故障最容易藏身的地方。一个 agent 生成的融合 kernel 如果在这些点上把累加精度降了一档，离线 oracle 会放行，生产端会在长序列上暴露数值漂移，而排查成本落在最不该承担它的环节——线上服务。

所以这篇论文的切入点不是“再写一个更好的检查器”，而是先把“检查器有多好”变成一个可测量的量。变异分析提供的是分母：一个有见证的故障集合，任何协议都能被同一个分母打分，补丁之间因此可比。这个转向的工程含义是，kernel agent 的评测栈需要多一层——不是更多的随机输入，而是一个故障语料 + kill witness + 变异得分的三元组，挂在正确性门之前或之后，用来审计门本身。没有这一层，加速比与正确性标签就是两个不可分离、且其中一个不可信的数。

手写 kernel 与库调用之间的“无人区”：为什么推理服务的算子栈必须换一种验证方式

设想一个在线推理服务里的 fused attention + RMSNorm 融合算子：手写 CUDA 版本在离线微基准上比 PyTorch eager 快出一截，但上线后长序列、混合 dtype、动态 batch 的请求一进来，数值漂移与偶发 NaN 开始出现，回滚到库调用又丢掉了延迟收益。这正是论文所指的现场：Benchmarks for LLM-generated GPU kernels decide correctness with a few random inputs and a loose floating-point tolerance, and their verdicts now feed leaderboards and reinforcement-learning rewards. 手写 CUDA 的代价是开发周期与可维护性——每个 dtype、每个 shape 特化都要重写归约树与边界处理；Triton 把门槛降下来，却把正确性责任转移到编译器与 autotune 的启发式上；库调用性能上限受限于通用 tiling，无法吃到本服务特有的访存模式。三者共同的边界在于：它们的“正确”由少量随机输入加宽松浮点容差判定，而这个判定本身从未被度量。

失效条件是可刻画的。设参考实现输出 $r$、候选输出 $c$，判定规则形如 $|r-c|\le \tau\cdot\max(|r|,|c|)+\epsilon$。当归约规模 $n$ 增大，合法浮点方差本身随 $\sqrt{n}$ 增长，容差带被迫放宽，于是“盲带”随归约尺寸扩张——论文明确指出 a tolerance blind band growing with reduction size，并给出 a measured ceiling on input aggressiveness set by legitimate floating-point variance。这意味着靠加大输入攻击性来补检查器是有天花板的：输入越激进，合法实现的方差越容易触碰容差边界，误杀与漏杀同时上升。

系统代价体现在三个维度。其一是正确性代价的分布极不均匀：官方检查 misses one in six witnessed faults (16.9%)，且 8.7% of arithmetic faults escape, but 78.6% of precision faults do——也就是说，算术错误大多能被抓住，精度类错误几乎裸奔，而这恰恰是推理服务最敏感的一类。其二是评测成本：手工补丁（额外输入分布、fuzzing 配方、更紧容差）没有可度量的充分性判据，with no way to measure whether any patch suffices，团队只能靠反复试错消耗编译与运行时间。其三是跨规模迁移：Across 48 whole architectures, the blindness grows with scale, concentrating in deep homogeneous pipelines，小模型上通过的检查器在大模型深栈上系统性失明，甚至 two problems prove unrefereeable，因为官方参考实现自身就违反了基准的容差。一个具体例子：某融合归约算子在 fp16 输入下用宽松容差通过，换到 bf16 长序列后误差累积越过阈值，服务端表现为输出分布偏移而非崩溃，监控难以捕获。

方案开发周期性能上限正确性判据可维护性
手写 CUDA长，逐 dtype/shape 重写高，可贴合访存少量随机输入 + 宽松容差低，归约树与边界易腐化
Triton短受 autotune 启发式约束同上，责任转移给编译器中
库调用最短通用 tiling，难吃特化库自带测试，但与基准口径不一致高

于是“非改不可”的理由不是性能，而是判据本身不可信：当 leaderboard 与 RL reward 都建立在这个判据上，reward hacking / fallback 会让正确率虚高，而工程团队无法区分“候选真的对”与“检查器没看见错”。论文的切入点因此是把检查器当作被测对象，用确定性规则向已验证的 CUDA 实现注入 10,303 compilable faults（覆盖 188 个 KernelBench 问题，其中 7,384 带独立 kill witness），以杀死率作为 oracle 充分性的度量；其优化结果——98.0% detection with two inputs per problem (94.8% held-out)——说明输入预算而非容差松紧才是主要杠杆。对算子库维护者而言，这意味着旧方案的边界不在 kernel 写得好不好，而在“通过测试”这件事本身没有被量化。
