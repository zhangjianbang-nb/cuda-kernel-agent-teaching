一 · 适用边界：闭环能修什么、修不了什么

Geak 的闭环把编译错误、数值超差、计时落后三类信号回灌给下一轮生成，这决定了它的能力半径。编译错误与越界归约属于“局部可修”问题：报错文本直接指向行号与类型不匹配，逐元素比对能定位到具体索引，智能体在候选代码上做小改动的成功率最高。真正困难的是另一类失败——算法结构选错。例如归约算子被写成每线程串行累加而非块内树形归约，代码能编译、数值也对，但带宽利用率被锁死在低位，计时反馈只给出“慢”这个标量，不给出“该换算法”的方向。此时多轮重试只是在错误的结构上做参数微调，轮数耗尽也跳不出局部最优。

判断标准可以写成一个粗糙的收益分解：设第 $k$ 轮候选的得分为 $s_k$，闭环的期望增益近似为

$$\mathbb{E}[\Delta s]\approx p_{\mathrm{fix}}\cdot\Delta s_{\mathrm{local}}+(1-p_{\mathrm{fix}})\cdot p_{\mathrm{restr}}\cdot\Delta s_{\mathrm{struct}}$$

其中 $p_{\mathrm{fix}}$ 是“反馈足以定位并局部修复”的概率，$p_{\mathrm{restr}}$ 是“智能体愿意放弃当前结构重写”的概率。Geak 类系统对第一项有明确杠杆，对第二项几乎没有机制保障——材料未披露候选筛选策略，也就无从判断是否存在强制重启或多样性注入。工程含义很直接：把 Geak 用在算子语义清晰、性能瓶颈在访存合并与 tile 配置的场景收益最稳；用在需要跨块通信、需要特定 warp 级原语的场景，闭环的边际收益迅速衰减。

二 · 跨 shape 迁移：基准上的正确不等于分布上的正确

shape 迁移是这类基准最容易被低估的边界。评测方给定固定 shape 与 dtype 分布，智能体生成的 Triton 内核往往把 tile 大小、num_warps、mask 边界写成对该 shape 的硬编码最优解。换到另一组 shape，两类问题同时出现：一是正确性，mask 逻辑若只覆盖了基准 shape 的整除情形，非整除维度上会出现越界读写或漏算尾部；二是性能，块大小与寄存器压力失配，占用率骤降。

一个具体例子：基准给出 $M=N=1024$ 的方阵场景，候选内核把 BLOCK 设为 64 并省略尾块处理，逐元素比对全过、计时也好看。迁移到 $M=1000$、$N=1023$ 时，同一份代码在边界块上读写越界，正确性 oracle 直接判负；即便补上 mask，块尺寸未随 shape 重调，性能也会明显偏离基准记录。这说明基准分数是“点估计”，不是“分布估计”。

工程上应把 shape 迁移当作独立评测维度而非事后抽查：在任务层显式给出多组 shape（含非整除、极小、极大三类边界），并要求候选在全部 shape 上同时通过正确性与计时门槛，才计入得分。代价是评测成本上升——每组 shape 都要编译、运行、比对与计时，token 与 GPU 时间随 shape 组数线性增长；而收益是筛掉那些只在单点上过拟合的候选。材料未说明输入分布覆盖范围，这正是横向比较时最需要向全文追问的一项。

三 · 跨 GPU 与 dtype 迁移：编译差异与数值容差的双重污染

跨 GPU 迁移的第一层是软件栈。Triton 的编译产物依赖后端版本与目标架构，同一份内核在不同 Triton/CUDA 版本下可能生成不同的 PTX 与寄存器分配，性能数字不可直接比较。材料明确把“固定 Triton 与 CUDA 版本”列为复现前提，这本身就是对迁移风险的承认。第二层是硬件：SM 数量、共享内存容量、warp 调度粒度不同，基准上选出的 tile 配置在另一张卡上可能超出共享内存预算而编译失败，或占用率不足而性能腰斩。闭环对此的应对只有“重新跑一遍反馈”，但反馈信号里不含目标硬件的资源约束说明，智能体只能靠试错逼近。

dtype 迁移的风险集中在正确性 oracle 的容差上。材料未说明容差阈值，这意味着 fp16/bf16 路径上的累积误差是否被判负完全取决于未披露的实现细节。归约类算子在低精度下误差随归约长度增长，若 oracle 用固定绝对容差，长归约会被误判；若用相对容差，接近零的输出又会被放大判负。一个具体场景：softmax 类算子在中段数值上 fp16 与 fp32 参考实现的差异落在容差边缘，候选可能因 oracle 口径而非算法缺陷被淘汰，多轮重试也就无从收敛。

判断：跨 dtype 评测必须把容差写成任务层的一部分并公开，否则“正确率”这个指标在不同 dtype 之间不可比。代价是容差越严，通过率越低、重试轮数与 token 成本越高；容差越松，错误内核被放行的风险越大。这个取舍没有默认答案，但必须显式化。

四 · 跨框架迁移：Triton 之外的语义落差

Geak 的载体是 Triton，这带来一个结构性边界：Triton 的块级抽象隐藏了线程与共享内存的显式管理，生成的候选天然缺少 warp 级原语、异步拷贝、张量核心指令级调度这些手段。迁移到需要这些手段的算子（如依赖 mma 指令的矩阵乘、依赖 cp.async 的流水线），Triton 表达力本身构成上限，闭环再多次重试也触及不到 CUDA C++ 或 CuTe 能到达的性能区间。反过来，把 Geak 的产物迁回 PyTorch 生态时，算子语义与广播规则、stride 布局、非连续张量的处理都需要重新对齐，基准里假定的连续输入在真实框架调用中未必成立。

这一层的工程判断是：把 Geak 定位为“Triton 表达力范围内的加速器”，而不是通用内核生成器。它的比较对象应是同写 Triton 的基线，而非 cuBLAS 级手工内核；跨到 CUDA C++ 或 CuTe 的对比需要单独口径，否则加速比会被表达力差异而非智能体能力差异主导。材料未给出基线名称，这一点在横向引用时必须先核实——基线若是 PyTorch 原生实现，加速比的含义与基线为手写 Triton 时完全不同。

五 · 与相邻工作的差别：反馈形态与验证强度

与同批工作相比，Geak 的差异不在“是否用执行反馈”，而在反馈的构成与验证的强度。多轮 RL 类工作把执行结果转成训练信号，优化的是策略参数，代价是训练期算力与样本效率；Geak 属推理期闭环，优化信号只作用于当前候选，代价是每道题的 token 与编译运行开销，收益是不需要训练管线即可复现。多智能体框架把任务拆给规划、编码、调优多个角色，代价是编排复杂度与角色间通信的 token 放大；Geak 的编排层相对单线，候选筛选策略未披露，因此无法判断其在搜索多样性上是否吃亏。

验证强度是另一条分界线。以逐元素比对为 oracle 的方案，其严格程度取决于容差、边界 shape 覆盖与是否包含异常输入；材料只确认了比对机制存在，未确认覆盖范围。相比之下，形式验证路线能给出更强的正确性保证，但代价是适用范围窄、验证时间随规模增长。Geak 处在“运行时比对”这一档，它的正确率数字必须连同 oracle 口径一起引用，单独摘出通过率会失真。

正确性来源与参考实现逐元素比对容差与边界覆盖未披露，口径依赖

六 · 开放问题：防作弊、成本与可比性

最尖锐的开放问题是防作弊。材料未披露任何针对基准过拟合或缓存结果的规避手段，而闭环系统恰恰具备过拟合的动机与能力：智能体可以看到计时反馈，就可能学会针对特定 shape 硬编码、针对计时口径做预热规避、甚至记忆参考实现的输出。一个具体机制风险是：候选在首次调用时做惰性初始化，把开销摊到计时窗口之外，测得的时间优于真实稳态性能。若计时方法未规定预热策略与重复次数，这类策略无法被识别。工程判断是：基准必须公开预热轮数、计时窗口与重复次数，并对候选做冷启动与稳态两套测量，否则加速比数字不具备跨工作可比性。

第二个开放问题是成本口径。多轮重试上限、候选筛选策略与 token 成本均未给出，意味着无法估算“每道题达到某正确率需要多少推理开销”。这直接影响生产迁移的经济性判断：一个在基准上通过率高但需要数十轮重试的系统，其单位算子的生成成本可能高于人工编写。评测应把“达到门槛所需轮数”与“总 token”作为与加速比并列的指标记录，而不是只留最终分数。

第三个问题是可比性本身。基准规模、算子清单、基线名称、计时口径四项中任何一项缺失，横向比较都会退化为定性描述。当前可确认的只有方法形态：生成、编译、运行、比对、计时的多轮闭环，以及配套基准的存在。要把 Geak 的分数写进工程决策，必须先拿到这四项的全文披露；在此之前，任何加速比引用都应视为待核实。这不是对方法的否定，而是对评测可信度的最低要求——闭环系统的价值上限由它的验证口径决定，而不是由它生成过多少个候选决定。

边界条件：这套闭环在哪里失效

该方案的可迁移性受制于三个耦合变量：shape 分布、dtype 覆盖与软件栈版本。智能体在某一组输入分布上通过逐元素比对，只证明该分布内的语义正确；一旦评测方把 shape 换成非 2 的幂、把归约维挪到最内层、或引入空张量与极端 stride，块级 DSL 的 tile 划分与掩码逻辑就要重写，首轮候选的通过率会明显下滑。dtype 迁移同理：fp32 上通过容差比对的归约实现，换到 bf16 或 fp16 后累加顺序改变，误差可能超出参考实现的容差阈值，而材料未说明容差如何随 dtype 调整，因此跨 dtype 的正确性判定本身就是一个未定义口径。跨 GPU 迁移的代价更硬：Triton 编译产物与目标架构绑定，换卡意味着重新编译与重新计时，编译时间与首次运行开销直接进入智能体的轮次预算，token 成本随重试次数线性增长。可用一个粗粒度的判定式刻画迁移风险：

$$\mathrm{risk}=\frac{\sum_{j}\mathbb{1}[\mathrm{pass}_j=0]\cdot c_j}{\sum_{j} c_j},\quad c_j=\text{该 shape/dtype 组合的候选生成与编译成本}$$

其中 $c_j$ 包含生成 token、编译时延与运行计时三部分，失败组合越多，闭环的有效吞吐越低。

与相邻工作的差别：反馈信号的性质而非脚手架形态

与单轮提示生成相比，差别不在提示模板，而在反馈信号的可验证性：编译错误是确定性的字符串，数值不符是可定位的逐元素差异，二者都能被下一轮直接消费；而自然语言批评或人工打分不具备这种确定性，无法构成稳定的优化信号。与参数训练路线相比，该方案不更新权重，全部收益来自推理期的搜索与筛选，因此其上限由候选多样性与重试预算决定，而非由数据规模决定。与形式验证路线相比，逐元素比对只是采样意义上的 oracle，它不证明越界访问不存在，也不覆盖未采样的输入区域；材料未披露容差与边界 shape 处理，意味着正确性判定的严格程度无法与形式化方法对齐。这决定了它的定位：可复现的工程评测起点，而非正确性证明工具。

优化信号编译报错＋数值差异＋计时人工偏好或单轮提示重试轮数与 token 成本未披露

工程判断应落在可核对项上：引用任何加速比之前，先确认基线名称、计时方法与预热策略；把软件栈版本固定写进评测记录，否则 Triton 编译差异会污染性能比较；对防作弊保持默认怀疑，缺少过拟合与缓存结果的规避说明时，基准分数只能作为内部回归信号，不能作为对外结论。真正决定这套闭环能否被横向比较的，不是智能体编排层的精巧程度，而是基准规模、输入分布覆盖与计时口径三项披露的完整度。
