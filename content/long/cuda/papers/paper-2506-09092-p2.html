一 · 失效模式：加速比的三种虚高来源

FSR 的评分口径是 $$s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$，加速比完全由分母基线决定。这意味着任何“基线选弱”的操作都会直接放大分数，而不需要候选 kernel 变强。工程上要盯住三类虚高：其一，基线未开 TF32 或未启用论文指定的库实现，PyTorch eager 的 fp32 matmul 与 cuBLAS 的 TF32 路径相差一个数量级，此时候选只要写出一个正常的 tiled GEMM 就能拿到漂亮比值；其二，基线没有做 shape 对齐，参考实现按通用 shape 写，候选按测试 shape 特化，比较的其实是“特化 vs 通用”而非“LLM vs 人”；其三，基线缺少 warmup 与同步，第一次调用包含上下文初始化与 lazy module 加载，计时被污染。这三种情况在离线复现里都极易发生，因为它们不需要改候选代码，只需要改测量脚本。判断方法很直接：把基线换成同硬件上最强的库实现（cuBLAS / CUTLASS / cuDNN 对应算子），重跑一遍 $$s_i$$，若加速比从数倍塌到 1 附近，说明原分数主要来自基线选择而非 kernel 质量。这一步的代价是一次基线重建的工程时间，换来的是一张不会被生产环境打脸的分数表。

具体例子：一个 LLM 生成的 fp32 GEMM 在 4096×4096 上对 PyTorch eager 报出数倍加速，但把基线换成开启 TF32 的 cuBLAS 后加速比收敛到 1 附近——候选真正做对的是“用了 shared memory tiling”，而这件事 cuBLAS 早就做了。这不是候选的错，是评测口径的错。FSR 论文摘要强调“measured by actual kernel execution latency on the target GPU”，但“actual latency”只有在基线同样 actual 时才有意义。

二 · 适用边界：shape 特化与输入分布的悬崖

FSR 的搜索-强化回路是在“论文给定的输入分布”上闭合的：候选被编译、在给定输入上做正确性检查、测时延、按反馈保留或回退。这个回路天然偏向对测试 shape 过拟合的候选——LLM 在反馈里看到的是固定 shape 的时延数字，它会学会写死 block 维度、写死 tile 大小、甚至写死循环边界。一旦生产输入分布漂移（batch 变化、序列长度非 2 的幂、dtype 从 fp16 换到 bf16），特化 kernel 要么走 fallback 分支退化成通用路径，要么直接越界或结果错误。工程判断是：把候选的“shape 泛化”当作独立门禁，而不是正确性门禁的附带项。做法是在正确性检查里加入至少一组非测试分布的 shape（奇数长度、极小 batch、极大 batch 各一），并要求候选在这些 shape 上仍然编译通过且数值在容差内；不满足就退回通用实现。代价是每轮多几次编译与运行，token 与 wall-clock 都会涨，但这是唯一能挡住“离线分数高、上线就崩”的机制。

另一个边界是 dtype 与架构。论文的结论只在给定硬件、给定 dtype 上成立，跨架构迁移未验证。LLM 生成的 CUDA 代码里若出现 __shfl_sync 的宽度假设、共享内存容量假设（如 48KB 静态分配）、或 warp 数假设，换到共享内存更小或 warp 调度不同的架构上就会编译失败或性能反转。这不是“模型不够强”，而是硬件特定代码的本质：它把架构参数编码进了源码。因此 FSR 类方法的合理定位是“在已知硬件画像下做离线优化”，而不是“一次生成、到处部署”。

三 · 与相邻工作的差别：反馈粒度决定迁移性

把 CUDA-LLM 放进同批工作里看，差别不在“是否用 RL”，而在反馈信号的结构。KernelBench 系工作提供的是基准与口径，回答“怎么量”；Kevin、CUDA-L1 这类多轮 RL 工作把执行反馈做成训练信号，回答“怎么在多轮里收敛”；CUDA-L2 把目标推到超越 cuBLAS 的 matmul；Dr. Kernel 把 RL 做在 Triton 生成上；CudaForge、Astra、cuPilot 把硬件反馈或多 agent 协调引入回路。CUDA-LLM 的 FSR 处在“特征搜索 + 强化”这一格：它把编译通过、功能正确、运行时性能三者联合优化，并用实际 kernel 执行时延作为最终度量。与纯 RL 方法相比，FSR 的搜索环节让候选空间先被特征约束收窄，再交给强化回路精修；与多 agent 框架相比，它没有把任务拆给多个角色，而是把反馈压进单一回路的打分函数。这个差别的工程后果是：FSR 的迁移性受限于它的打分函数——打分函数里没有的维度（跨 shape 泛化、跨 dtype、端到端收益），回路就不会去优化它。

四 · 什么情况下不该用它

第一，算子已经被厂商库覆盖且库实现接近 roofline。此时 LLM 生成的候选要赢过 cuBLAS/CUTLASS 的概率很低，而 FSR 回路每轮都要编译、跑正确性、测时延，编译时间与 token 消耗是实打实的成本；收益上限是“追平库”，风险下限是“引入一个未验证的特化分支”。判断标准是先用 roofline 估一下该算子的 SOL，若库实现已在 SOL 的较高比例上，直接放弃生成路线。第二，正确性 oracle 本身不可靠的场景。FSR 用“给定输入上的正确性检查”做门禁，若算子涉及归约顺序敏感的浮点累加、原子操作的竞态、或需要多随机种子才能暴露的边界，单次输入检查会放过错误候选；此时 reward hacking 的空间在于“候选在测试输入上对、在生产输入上错”，而回路没有机制发现它。这类场景应先建形式化或差分测试 oracle，再谈生成。第三，端到端收益不可归因的场景。若 kernel 只占端到端时延的小头，单 kernel 加速比再高也传导不到用户可见的收益；FSR 的度量是 kernel 级时延，不是端到端。第四，编译预算受限的在线场景。FSR 的搜索-强化回路需要多轮编译与执行，离线可行，在线服务里每次请求都跑一遍回路不现实。

代价核算要写清楚：每轮候选的编译时间（CUDA 编译是秒级到十秒级）、正确性检查的运行时间、profile 采集的开销、以及 LLM 侧每轮的 token 消耗。这些成本在离线批量优化里可以摊薄，在单算子一次性任务里往往超过收益。一个具体的工程判断：若该算子的库实现已接近 SOL、且端到端占比低于可感知阈值，FSR 类方法的期望收益为负——不是因为方法不好，而是因为它的成本结构不适合这个场景。

五 · 迁移到生产：把离线分数翻译成可回归的门禁

迁移的核心不是“把候选搬过去”，而是“把评测口径搬过去”。FSR 的回路在离线闭合，生产端要重建同样的闭合：统一基线（同硬件最强库实现）、统一输入分布（含生产真实 shape 采样）、统一计时口径（warmup、同步、多次取中位数）、统一正确性容差。然后把候选放进端到端回归：不是只看 kernel 时延，而是看整条链路在候选替换前后的时延差与数值差。若端到端收益不可见，候选就不该合入，哪怕离线加速比很高。这一步的机制是“收益归因”：用 profile 把端到端时延拆到 kernel 级，确认候选替换的那一段确实是瓶颈，且替换后瓶颈确实下移。代价是每次合入都要跑一遍端到端回归与 profile 采集，wall-clock 成本高于单 kernel 基准，但这是唯一能防止“离线赢、线上输”的工程手段。

另一个迁移动作是保留 fallback。候选 kernel 必须带一条经过验证的通用路径，在 shape 越界、dtype 不匹配、编译失败时回退；回退路径的正确性要独立验证，不能假设“库实现总是对的”。这与 FSR 回路里的“按反馈保留或回退候选”是同一机制在生产端的延伸：回退不是失败，是边界内的正常行为。工程上要把回退率当作监控指标——回退率突然升高，说明输入分布漂移或候选的假设被打破，此时应触发重新搜索而不是继续压测。

最后落在具体机制上：FSR 的评分函数 $$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau]$$ 是一个阈值计数，它奖励“过线”而不奖励“过线多少”，也不惩罚“在未测 shape 上崩”。生产端要做的第一件事，就是把这个计数口径扩成带泛化维度的门禁：阈值 $$\tau$$ 之外再加一组非测试 shape 的正确性与时延约束，把“离线过线”翻译成“回归过线”。这一步不改模型、不改回路，只改度量，却是决定这套方法能不能可信落地的分界线。

边界与迁移：FSR 在哪些条件下失效，以及何时不该启用它

FSR 的闭环是“生成—编译—正确性检查—实测时延—按反馈保留或回退”，这条链路成立的前提是候选能在目标 GPU 上真实跑起来并被统一基线测量。一旦这个前提被打破，整条链路退化为盲搜索：编译失败或运行即崩的候选无法产生有效时延样本，正确性门与性能门同时失效，模型只能靠语法层面的先验继续改写，反馈信号归零。更隐蔽的失效来自 reward hacking——候选在检查用的输入分布上通过正确性门、在计时用的 shape 上刷出高加速比，却在生产流量下崩掉；FSR 的 score 公式 $$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$ 只统计“超过阈值 τ 的题目比例”，对“超了多少”和“在哪些 shape 上超”都不敏感，因此少量极端特化就能把分数拉高而不暴露脆弱性。工程上应把 score 拆成“通过率 × 最小加速比 × 跨 shape 方差”三元组，并对每个候选记录其编译时间、显存占用与回退次数，作为与加速比并列的准入条件。

迁移边界比失效模式更难察觉。论文的结论只在给定硬件、基线与输入分布上成立，跨 GPU 架构迁移时，同一份 CUDA 代码的 occupancy、bank 冲突模式与指令吞吐都会变，FSR 在 A 卡上搜出的 tile 尺寸与 unroll 因子搬到 B 卡往往直接掉出阈值 τ；跨 dtype（fp32→fp16/bf16）迁移会改变数值容差，正确性门若沿用原阈值则误判率上升；跨框架迁移（PyTorch eager / torch.compile / 论文指定库）则改变了基线口径，加速比的分母不再可比。这三类迁移都不在 FSR 的反馈回路内——它只对“当前机器、当前基线、当前输入”做优化，没有任何机制把跨环境鲁棒性写进奖励。因此把 FSR 产物直接搬进生产端到端路径之前，必须在目标环境重跑一遍“编译—正确性—时延”三关，并把重跑结果与原分数并列存档，否则离线分数与线上收益之间的缺口无人能解释。

系统代价同样构成边界。FSR 的每一轮迭代都要真实编译并计时，编译时间与 kernel 执行时延共同决定单题搜索成本；对编译期长的模板重载或 CuTe 布局代码，单次编译可能远超 kernel 本身时延，使“多轮改写”的边际收益迅速衰减。显存方面，候选若申请超出设备容量的 shared memory 或寄存器溢出，会触发编译失败或运行时降级，反馈回路被迫回退，token 预算被消耗在无效候选上。一个具体例子：某归约算子在固定 shape 上被 FSR 搜出高加速比版本，但其 tile 尺寸硬编码为 2 的幂且未处理尾块，换到非对齐长度时正确性门直接失败——这不是模型的错，而是搜索目标函数没有覆盖“尾块处理”这一维度。判断是否该用 FSR 的工程准则因此很直接：若题目集合的 shape 分布稳定、基线口径固定、目标硬件单一，FSR 的闭环能兑现收益；若 shape 长尾、跨卡部署、基线随框架版本漂移，则应先用固定模板或手写 kernel 兜底，把 FSR 限制在离线探索阶段，不让其产物直接进入生产路径。

边界：当 FSR 的搜索空间撞上硬件墙

FSR 的反馈回路本质上是把「编译—正确性—时延」三态信号压进一个标量奖励，再用特征搜索把候选往高分区推。它的失效条件首先来自这个奖励的可分辨性：当候选 kernel 的时延差落在测量噪声内（例如小 shape 下 launch 开销主导、或 L2 命中导致重复测量方差极小），奖励梯度退化为随机游走，搜索会把 token 预算烧在无意义的语法变体上。此时系统代价不是显存而是编译时间与采样 token——每个候选都要走一次 nvcc/ptxas 全流程，一个 10 轮迭代、每轮 8 候选的回路意味着数十次编译，编译时间在 CI 里会直接压过 kernel 本身的毫秒级时延。可用的判据是信噪比门限：若同一候选重复测量的时延标准差与基线时延之比超过候选间加速比差距的一半，就该停止搜索而不是继续加轮次。

$$\text{SNR}_i=\frac{\lvert T_{\text{base},i}-T_{\text{cand},i}\rvert}{\sigma_{\text{meas},i}},\qquad \text{stop if } \mathrm{median}(\text{SNR}_i)<2$$

第二个失效面是shape 特化与隐藏输入分布。FSR 在论文给定的输入分布上做正确性检查与时延测量，模型很容易学到「针对这批 shape 展开循环、写死 tile 尺寸」的局部最优；一旦生产端 batch 或 seq_len 漂移，特化 kernel 的 occupancy 与访存合并模式同时劣化，离线加速比无法迁移。这不是模型的错，而是评测口径的边界：正确性 oracle 只在给定输入上成立，性能门只在给定基线上成立。工程上必须把「同 dtype、跨 shape 的回归集」作为迁移门，任何只在单一 shape 上胜出的候选都标记为不可部署。

第三类边界是与相邻工作的分工。FSR 属于「LLM 生成 + 执行反馈」这一族，与纯静态的检索式模板库、以及基于形式验证的等价性检查处在不同位置：前者靠真实时延信号做选择，代价是必须真跑；后者靠 SMT/符号执行保证语义等价，代价是表达力受限、难以覆盖并行归约与原子操作。FSR 不提供语义等价证明，它的正确性来自测试用例的覆盖度，因此当算子含非确定性归约顺序、或依赖未定义行为的 warp 级同步时，测试通过不等于语义正确。不该用它的场景由此清晰：需要可证明等价的内核、编译器后端已能自动调优且基线已接近 SOL 的算子、以及编译预算被严格限制的在线服务路径——在这些位置，FSR 的搜索开销换不来超过噪声的收益。
