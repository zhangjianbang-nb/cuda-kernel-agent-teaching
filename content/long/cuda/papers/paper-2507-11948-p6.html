一 · 一条轨迹的真实账本：token、GPU 时与编译墙钟

多轮 RL 生成内核的成本结构，和单轮代码补全完全不是一个量级。单轮补全的账本只有一项：输入提示 token 加输出代码 token。多轮轨迹的账本要按回合展开，每一回合同时消耗三类资源——模型侧的自回归 token、执行侧的 GPU 墙钟、以及编译侧的前端时间。把这三项写成一条轨迹的总代价，可以形式化为：

$$C(\tau)=\sum_{t=1}^{T}\Big(c_{\text{tok}}\cdot(n^{\text{in}}_t+n^{\text{out}}_t)+c_{\text{gpu}}\cdot \tau^{\text{run}}_t+c_{\text{cc}}\cdot \tau^{\text{compile}}_t\Big)$$

这里的关键不是公式本身，而是三项的相对量级。token 项随轮数线性增长，因为每轮都要把历史反馈重新拼进提示——编译错误文本、运行输出、性能读数，都是要重复付费的上下文。GPU 时项取决于内核的实际执行时长与重复测量次数，一个正确但慢的内核在性能采集阶段往往要跑多轮 warmup 与重复计时，这部分成本与内核质量无关，只与测量协议有关。编译项最容易被低估：CUDA C++ 的编译是重前端过程，模板实例化、内联展开、PTX 生成与 ptxas 后端各自耗时，一个中等复杂度的内核单次编译就可能达到秒级，而一条轨迹里编译次数等于轮数加上失败重试次数。

具体到一个例子：假设某任务首轮产出的内核编译失败，第二轮修正后编译通过但正确性判定不达标，第三轮修正正确、第四轮做性能优化，那么这条轨迹至少触发四次编译、两次运行判定、一次性能采集，token 侧则累积了四份逐渐变长的提示。若把轮数上限从 4 提到 8，token 成本大致翻倍，编译次数翻倍，而 GPU 时因为后期轮次的内核更接近正确、执行更充分，增长会超过线性。这就是规模化的第一个非线性来源。

二 · 编译时间：被忽视的吞吐瓶颈

在 RL 训练循环里，编译不是免费的旁路，而是采样吞吐的硬约束。设单条轨迹平均需要 Nc 次编译、每次编译耗时 tc，则单条轨迹的编译墙钟为 Nc·tc。当并行采样 B 条轨迹时，若编译资源池只有 K 个并发槽位，编译阶段的排队时间为：

$$\tau^{\text{queue}}\approx \frac{B\cdot N_c\cdot t_c}{K}-t_c$$

这个式子的工程含义很直接：编译并发度 K 不足时，GPU 会空转等待编译结果，采样吞吐被编译池卡死。实践中 K 受限于容器的 CPU 核数与内存——nvcc 与 ptxas 都是吃满单核的重进程，模板密集的内核还会把内存推到数 GB。一个中等规模的采样集群，若只给每个执行沙箱分配两三个核，编译排队就会成为主导时延。

缓存是这里最有效的杠杆，但缓存命中率有结构性上限。按源码哈希缓存编译产物，只能命中完全相同的源码；而多轮 RL 的轨迹里，模型每轮都在改代码，相邻轮次的源码几乎必然不同，缓存命中率接近于零。真正有效的是按“任务描述 + 轮次序号 + 反馈摘要”缓存执行结果，让重复采样同一任务的轨迹复用已测过的中间状态——但这要求反馈序列化格式稳定，否则哈希不稳定、缓存失效。代价是缓存层本身要维护一份结构化反馈存储，写入与查询都引入额外时延，且缓存一致性在并发改写时容易出错。定性地说，缓存能把重复任务的编译次数压下来，但对首次出现的任务无能为力，因此它改善的是平均吞吐而非最坏时延。

三 · GPU 时与并发：执行沙箱的隔离成本

执行层的并发不是把内核丢上 GPU 就完事。多轮 RL 要求每个回合的执行结果可归因到具体轨迹，这意味着沙箱必须隔离：独立进程、独立 CUDA context、独立显存配额。CUDA context 的创建本身有固定开销，且每个 context 占用一份显存用于模块加载与运行时状态；当并发沙箱数上升，显存被 context 与内核模块挤占，可用于实际内核执行的显存下降，大 shape 的任务开始出现分配失败。

更隐蔽的代价是计时污染。性能信号要被用作奖励，就必须稳定可复现；但并发执行时，多个内核争抢 SM 与内存带宽，单条轨迹测得的时延被邻居干扰，奖励信号带噪。工程上的常见做法是串行化性能采集阶段——正确性判定可以并发，性能测量必须独占。这直接把吞吐砍成两段：并发段快、独占段慢，整体墙钟由独占段主导。设并发度为 B、独占测量单次耗时 tm，则每批轨迹的性能采集墙钟约为 B·tm，与并发度无关地线性增长。这就是规模上去以后第一个先崩的地方：不是模型推理，不是编译，而是独占式性能测量的串行瓶颈。

具体例子：一批 64 条轨迹进入性能采集，每条需要三次重复计时取中位数，单次计时含 warmup 约几十毫秒量级，则这一批的采集墙钟就是秒级到十秒级，且无法通过加卡缓解——加卡只是增加了可并行的独占槽位，但每条轨迹的测量本身不可压缩。若再要求 NCU 级 profile 采集（本系列其他部分讨论的 SASS 级信号），单次采集开销会再上一个量级，因为 NCU 需要 replay kernel 并逐段收集计数器，吞吐下降是结构性的。

四 · 搜索轮数与规模：哪里先崩

把轮数上限 T 当作可调旋钮，会撞上三重约束。第一重是 token 预算：提示长度随轮数累积，历史反馈全部保留时，第 t 轮的输入 token 约为前 t−1 轮反馈之和，总 token 消耗对 T 呈二次增长。若做反馈摘要压缩，则压缩本身要花一次模型调用，且压缩会丢失编译错误的细节行号与类型信息，模型修正的准确率下降——这是用正确性换成本。

第二重是收益递减。多轮 RL 的奖励是轨迹级汇总，早期轮次贡献的是“从编译失败到编译通过”的跃迁，后期轮次贡献的是性能微调。当轮数从 4 提到 8，新增四轮大概率落在性能微调区间，单轮奖励增量变小，而每条轨迹的成本翻倍，单位成本的奖励增益下降。这在训练侧表现为梯度信噪比恶化：长轨迹的方差更大，优势估计更难，需要更大的 batch 才能稳定，而更大 batch 又加剧了第三节的独占测量瓶颈。

第三重是失败轨迹的沉没成本。编译始终失败或正确性始终不达标的轨迹，消耗了全部 T 轮的成本却只拿到接近零的奖励。若失败率在任务分布上不均匀——某些算子形态天然难编译——则采样预算被系统性浪费在难任务上。规模上去以后，第二个先崩的点就在这里：失败轨迹的占比随任务难度上升，而系统没有机制在早期识别并提前终止，导致 GPU 时与 token 双重浪费。提前终止需要可靠的早期信号（例如连续两轮编译错误类型相同即判定陷入循环），但这类判据本身要调，调错会误杀本可修正的轨迹。

五 · 中小团队的真实预算线

对一个没有大规模采样集群的团队，可行的配置不是把轮数和并发拉满，而是把资源集中在“编译通过率”这一段。理由是：多轮 RL 的奖励跃迁主要发生在编译失败到编译通过之间，这一段每单位 GPU 时的边际收益最高；而性能微调段需要独占测量与稳定计时，成本结构最重、收益最不确定。具体做法是分层预算：正确性判定阶段用高并发、短超时、按源码哈希缓存编译产物；性能采集阶段只对通过正确性判定的轨迹开放，且限制每任务只做一次采集，把独占测量的串行段压到最小。

缓存与并发在这里的取舍是明确的：编译缓存改善平均吞吐但要求反馈格式稳定，独占测量保证信号可信但牺牲吞吐，二者不可兼得。中小团队的工程判断应当是——先保证信号可信，再谈吞吐，因为带噪奖励驱动的策略更新会把模型推向投机行为（本系列奖励部分已讨论的奖励漏洞），而修复一个被污染的策略比放慢采样贵得多。至于轮数，四到六轮是成本与收益的平衡区间，超过这个区间需要先证明后期轮次的奖励增量确实存在，而这一点在摘要级材料里恰恰是未披露的，不能凭直觉外推。

最后落到一个具体机制上：把每条轨迹的成本记成三元组（token 数、编译次数、独占测量次数），在采样循环里实时累计，当某任务的累计成本超过预算阈值时强制终止并标记为“成本超限失败”。这个机制把规模化的失控点从“事后发现账单爆炸”变成“事前截断”，代价是部分本可修正的长轨迹被提前砍掉，正确性上表现为通过率略降——这是一笔用少量通过率换成本可控性的明确交易，也是中小团队在预算约束下唯一能落地的规模控制手段。

规模放大后的三处先崩点与预算口径

多轮闭环把单次推理变成“生成—编译—运行—再生成”的串行链，系统代价随轮数 T 线性放大，而编译与执行是墙钟时间的主要来源。一个可直接用于预算估算的粗粒度模型是：单条轨迹代价 ≈ T·(Lgen·ctok + tcompile + trun)，其中 ctok 为每 token 的推理成本，tcompile 与 trun 分别对应一次编译和一次执行。规模上去后最先崩的不是模型质量，而是执行层的并发吞吐：编译进程与 GPU 运行需要隔离沙箱，沙箱启动、依赖加载与超时控制都是固定开销，当并发轨迹数超过沙箱池容量时，排队时延会吞掉反馈带来的收敛收益。第二处是缓存命中率——同一任务描述的多轮前缀高度重叠，若不做前缀缓存与编译产物缓存，每轮都要重付一次完整编译成本；编译缓存失效（源码每轮必改）意味着只能缓存工具链与头文件层，收益有限。第三处是反馈序列化：把编译器报错与运行结果结构化拼回提示，token 长度随轮数累积增长，长轨迹的上下文成本会反过来挤压采样规模。

代价项随规模的变化失效条件
推理 token随 T 与历史反馈长度线性增长前缀缓存缺失时成本翻倍
GPU 时随并发轨迹数线性增长沙箱池饱和后排队主导墙钟
编译时间每轮一次，无法跨轮复用编译失败轨迹仍付全额编译成本

对中小团队，真实约束不是能否跑通一次多轮训练，而是能否承担“失败轨迹的沉没成本”。编译失败与正确性不达标的轨迹同样消耗 T 轮推理与 T 次编译，若失败比例高，有效样本产出率下降，等效于把 GPU 时与 token 预算按失败率打折。可验证奖励 R(τ)=Σ rt 只汇总结果，不区分“第几轮才通过”，因此早轮通过的长尾轨迹与末轮勉强通过的轨迹在预算上等价，但后者占用的执行资源远高于前者。工程上应把轮数上限与早停判定作为一等预算参数：早停阈值过松会放大无效轮次，过紧则截断本可修正的轨迹。材料未披露轮数上限、失败率与 token 成本，因此任何“规模上去收益递增”的外推都缺乏支撑；可确认的边界是，该方案的部署代价主要由执行沙箱并发度与反馈序列化长度决定，而非模型侧算力。
