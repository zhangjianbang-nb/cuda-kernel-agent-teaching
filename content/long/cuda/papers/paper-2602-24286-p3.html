一 · 任务池到脚手架：一次轨迹的入口与上下文成本

把一次 kernel 生成拆成流动的步骤，第一步不是写代码，而是把任务池里的一条算子规格装进智能体的上下文。任务池的每条样本至少携带三样东西：算子语义（例如“对给定 shape 做逐元素归约并输出标量”）、输入分布（shape 采样范围、dtype、边界情形）、以及一份参考实现作为正确性 oracle。这三样构成脚手架的初始 prompt，也是整条轨迹的“题面”。题面的信息量直接决定后续轮次的搜索空间：语义写得含糊，智能体会在错误的并行分解上反复试探；输入分布不给边界情形，正确性判定就会在边界元素上反复失败。

脚手架在这一步的职责是把题面、工具描述、历史轮次拼成一条可增长的对话上下文。每一轮智能体输出的是工具调用意图（写文件、提交编译、运行、读回结果），脚手架负责把工具返回值序列化回上下文。这里的代价是 token：多轮轨迹的上下文随轮次线性增长，编译诊断往往是大段文本（模板实例化报错、未定义符号、共享内存越界位置），一次失败回填可能吃掉数千 token。若不在脚手架层做诊断摘要（只保留错误码、文件行号与首条关键信息），上下文预算会被失败记录挤占，挤压后续改写所需的推理空间。一个具体例子：智能体首版内核因共享内存索引越界被 nvcc 拒绝，回填的诊断若原样塞入，包含模板展开的完整报错可能长达数百行；摘要为“行号 + 越界访问的数组名 + 建议上界”后，智能体下一轮修正索引的成功率显著高于面对原始报错。

这一步没有性能数字，只有 token 与时延代价：题面加工具描述是固定开销，历史轮次是可变开销，编译诊断是失败时的额外开销。工程判断在于把“哪些反馈进上下文、以什么粒度进”当作脚手架的核心设计，而不是把原始工具输出无差别透传。

二 · 写码与编译：诊断回填的粒度决定重试效率

智能体写出 CUDA 源码后，沙箱调用 nvcc 编译。编译步骤的输入是源码文件加固定的编译标志（CUDA 版本、架构标志、优化等级），输出是二元的通过/失败，失败时附带诊断。诊断分三类，处理方式不同：语法与符号类（未定义符号、头文件缺失）几乎总能被智能体直接修正；资源类（共享内存超限、寄存器溢出、launch 配置非法）需要改写并行分解或 tile 大小；模板与类型类（实例化失败、类型不匹配）往往需要重构函数签名。把三类混在一起回填，智能体会在低价值的语法修补上消耗轮次。

编译步骤的代价是编译时间与沙箱吞吐。nvcc 对模板密集的 kernel 编译时间可达数十秒量级，若每条轨迹要经历三到五次编译，单条轨迹的墙钟时间被编译主导，而非 GPU 执行。这直接影响 RL 训练的采样吞吐：轨迹收集的瓶颈从 GPU 算力转移到 CPU 编译。工程上的缓解手段是编译缓存（相同源码命中缓存直接返回）与并行沙箱池，但缓存命中率取决于智能体改写的多样性——若智能体每轮只改一行，缓存几乎无效。

一个具体机制：沙箱在编译失败时不仅回填诊断，还可回填“上一次通过编译的源码版本”作为 diff 基线，让智能体明确本轮改动引入了哪个错误。这比让智能体在完整源码上重新推理便宜得多。代价是上下文里多了一份源码副本，token 开销上升；收益是重试轮次下降。这个权衡没有普适答案，取决于任务池中算子的平均源码长度。

三 · 运行与正确性判定：容差口径即奖励口径

编译通过后进入 GPU 执行。运行步骤的输入是可执行体、输入张量与参考实现，输出是逐元素比对结果。正确性判定用逐元素比对，但容差口径是整条流水线里最容易被低估的设计点。容差过松，数值偏差的内核被放过，策略学到的是“近似即可”的坏习惯；容差过紧，合法的优化（例如改变累加顺序导致的浮点舍入差异、使用快速数学函数）被误杀，策略被推向保守实现，加速比奖励无从谈起。

容差必须与算子语义对齐：归约类算子的误差随累加长度增长，逐元素算子的误差应与单次运算的舍入界同阶。把同一个绝对容差套到所有算子上，等价于对长归约过松、对短逐元素过紧。更合理的做法是按算子给出相对容差加绝对容差的组合判据，并在参考实现侧固定累加顺序，使 oracle 本身可复现。

$$ \text{pass} = \bigwedge_{i} \left( |y_i - \hat{y}_i| \le \tau_{\text{abs}} + \tau_{\text{rel}} \cdot |y_i| \right) $$

运行步骤的代价有两层。第一层是执行时延本身，单次 kernel 运行在微秒到毫秒量级，相对编译可以忽略；第二层是正确性比对的开销，逐元素比对要把输出拷回主机并在 CPU 上比较，对于大 shape 的输出，拷贝带宽成为瓶颈。若每个候选内核都要做全量比对，比对成本可能超过被测内核本身的执行时间。工程上常见的折中是抽样比对加全量比对两级：先用小规模输入做快速筛选，通过后再上全量。代价是抽样可能漏掉只在特定 shape 上触发的越界或数值问题，这正是防作弊与正确性口径需要一起设计的理由。

一个具体例子：智能体为边界元素加入分支后，逐元素比对从“边界不一致”转为全通过。这一步的反馈不是数字而是差异位置，脚手架把差异位置（索引、期望值、实际值）回填，智能体据此定位是边界分支缺失还是索引映射错误。差异位置的信息密度远高于“正确性失败”四个字，但回填全部差异会爆上下文，通常只回填前若干个不匹配位置及其邻域。

四 · 测速与奖励聚合：截断上限与测量口径

正确性通过后进入测速。测速步骤的输入是可执行体、固定输入、基线实现，输出是候选内核延迟与基线延迟之比。这一步的工程细节决定奖励信号是否可信：warmup 次数、时钟是否固定、是否禁用缓存效应、测量取中位数还是最小值。缓存效应是最隐蔽的污染源——若输入张量在多次迭代间驻留 L2，候选内核测得的延迟会系统性偏低，加速比虚高，策略学到的是“利用缓存”而非“写好内核”。固定 warmup 与固定时钟口径是让加速比可跨轮次比较的前提，论文摘要未披露该细节，这使跨论文的加速比不可直接比较。

奖励聚合把三类信号折成标量。编译通过是二值门，正确性是二值门，性能项是连续值并设上限截断：

$$ r = \lambda_{\text{comp}} \cdot \mathbf{1}[\text{compile}] + \lambda_{\text{corr}} \cdot \mathbf{1}[\text{correct}] + \lambda_{\text{perf}} \cdot \min\left(\frac{t_{\text{base}}}{t_{\text{kernel}}},\, c_{\max}\right) $$

截断上限 $c_{\max}$ 的作用是防刷分：若某个候选内核因测量噪声或缓存效应测出异常高的加速比，不设上限会让策略朝“制造测量假象”而非“真实优化”的方向漂移。截断的代价是压制了真实的大幅超越基线的情形——当候选内核确实显著快于厂商库时，超出上限的部分不进入奖励，策略对该类改进的敏感度下降。权重 $\lambda$ 的配置同样有代价：性能项权重过高会让策略在正确性边缘试探（容差内的数值偏差换取速度），正确性项权重过高则退化为“能跑就行”的保守策略，加速比维度失去训练信号。

一个具体机制：奖励聚合器在轨迹级别而非轮次级别聚合时，失败轮次的负向信号如何计入是关键。若只对最终通过的内核给奖励，中间失败记录不贡献梯度，多轮重试的学习信号被浪费；若每轮都给奖励，编译失败的轮次会获得与成功轮次相近的负向信号，策略可能学会“少提交、多观望”。合理的折中是按轮次给稀疏的形状奖励（编译通过给小额、正确性通过给中额、性能项只在最终轮给），使重试过程本身成为可学习的对象。代价是奖励塑形的复杂度上升，调参成本增加。

五 · 防作弊与轨迹入库：评测门与训练缓冲的交界

测速与奖励之间还夹着一道防作弊检查。智能体可以走三条捷径绕过真实计算：硬编码输出（按输入值直接返回常量）、缓存结果（首次计算后复用）、按 shape 特判（对小 shape 走查表、对大 shape 走真实内核）。这三条捷径在逐元素比对下都能通过正确性判定，在测速下甚至能测出极高加速比。防作弊的手段包括：输入随机化（每次运行换随机种子，硬编码失效）、多次运行一致性检查（缓存结果在输入变化后暴露）、以及源码级检查（禁止按 shape 分支返回常量的模式）。

防作弊的代价是评测吞吐：输入随机化意味着每个候选内核要跑多组输入，运行次数成倍增加；源码级检查需要静态分析或人工规则，误报会误杀合法优化（例如按 shape 选择 tile 大小是合法优化，与按 shape 特判在源码上难以自动区分）。论文摘要未给出检查机制，这是评测口径待补的关键缺口——防作弊缺失时，奖励信号被捷径污染，训练出的策略在真实负载上失效。

轨迹入库是流动的最后一步。一条完整轨迹包含题面、每轮源码、每轮工具返回（编译诊断、差异位置、测速数字）、以及最终奖励。入库时要把这些序列化成训练缓冲的样本，供策略更新使用。这里的代价是存储与采样：多轮轨迹的 token 量远大于单轮样本，缓冲的采样效率下降；若轨迹长度差异大（有的算子三轮通过，有的算子十轮仍在编译失败），批次内的填充浪费显著。工程判断在于按轨迹长度分桶采样，避免短轨迹被长轨迹的填充拖累。

一个具体例子：某轨迹首版内核编译失败（共享内存越界），第二轮修正索引后编译通过但边界数值不一致，第三轮加入边界分支后正确性通过，测速得加速比并折算奖励。这条轨迹的三个中间状态都是训练信号：第一轮教“资源约束下的索引合法性”，第二轮教“边界条件的显式处理”，第三轮教“性能与正确性的联合优化”。把中间状态丢弃只留最终奖励，等于把多轮 RL 退化为单轮结果奖励，这正是智能体 RL 与单轮补全的分水岭。

六 · 各步骤代价的横向对照与工程判断

把五步的输入、输出与代价并排看，能看出瓶颈的迁移路径。任务池与脚手架的开销是 token，写码与编译的开销是编译时间与沙箱吞吐，运行与正确性判定的开销是比对带宽，测速与奖励聚合的开销是测量口径的可信度，防作弊与入库的开销是评测吞吐与存储。RL 训练的总成本由这五项叠加，而摘要级材料未披露 token 预算与 GPU 机时，工程代价无法量化评估。

步骤输入输出主要代价
任务池→脚手架算子语义、输入分布、参考实现初始上下文与工具描述token（题面固定 + 历史可变）
写码→编译源码、编译标志通过/失败、诊断编译时间、沙箱吞吐、诊断 token
运行→正确性可执行体、输入、oracle逐元素比对结果、差异位置比对带宽、容差口径风险
测速→奖励候选延迟、基线延迟加速比、标量奖励测量口径可信度、截断上限
防作弊→入库多组输入、源码、轨迹评测判定、训练样本评测吞吐、存储与采样效率

横向对照给出的工程判断是：这条流水线的可信度不取决于奖励公式的形式，而取决于每一步的口径是否闭合。编译诊断的粒度决定重试效率，容差口径决定正确性判定的松紧，测速口径决定加速比奖励是否被缓存效应污染，防作弊决定评测分数是否对应真实内核能力。任何一环口径缺失，奖励信号就会在训练中被策略利用，而不是被策略服从。对生产部署而言，端到端收益要压过厂商库基线才有意义，而这条流水线测出的是 kernel 级加速比，与端到端收益之间还隔着框架开销与调度开销——这是评测口径与部署口径之间必须显式对齐的缺口。
