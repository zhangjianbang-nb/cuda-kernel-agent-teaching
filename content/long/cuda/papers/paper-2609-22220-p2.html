一 · 基准题面与故障注入口径

这篇论文的测量对象不是 kernel 本身，而是“判定 kernel 对错的裁判”。它的基准题面直接复用 KernelBench 的 188 道题，但把每道题的“已验证 CUDA 实现”当作宿主，用确定性规则向其中注入可编译的故障，共得到 10,303 个变异体（mutant），其中 7,384 个配有独立的 kill witness——即存在一组输入，使变异体输出与参考实现的可接受区间明显偏离。这个设计决定了本部分所有口径问题的性质：分母不是 188，而是 10,303；一次“通过率”不是 kernel 的正确率，而是裁判对故障的检出率。

变异规则按家族划分，至少覆盖算术类与精度类。算术类故障改变运算结构（如把累加换成错误结合顺序、替换算子），精度类故障改变数值路径（如降低中间累加精度、改变舍入点）。这一分类直接支撑了后文最重要的偏斜结论：官方检查漏掉 16.9% 的已见证故障，但算术类只漏 8.7%，精度类漏掉 78.6%。也就是说，一个裁判的“总分”若只报一个数，会掩盖它在精度维度上近乎失明的状态。工程含义是：任何声称“检出率 90%+”的测试协议，必须同时给出按家族分解的漏检率，否则该数字不可核查。

变异体的可编译性是硬约束。不可编译的故障会在编译阶段被淘汰，不进入分母，因此 10,303 这个数字本身已经过滤掉了一类“显然能被编译器抓住”的错误。代价是：编译时间成为测量管线的一部分，每个变异体都要走一遍 nvcc 编译加一次运行，7,384 个带 witness 的变异体意味着至少 7,384 次编译—运行—比对循环。这是本论文测量成本的主要来源，也是为什么它选择确定性规则而非随机 fuzzing：确定性规则让每个变异体可复现、可归档，代价是覆盖面受规则设计者视野限制。

二 · 指标定义：faster rate、speedup、geomean 与 fast-p

性能侧的口径沿用 KernelBench 系基准的通行做法，但必须写清楚每个符号的分母。单题加速比定义为基线时延与候选时延之比：

$$s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}},\qquad \text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau]$$

这里 $T_{\text{base},i}$ 是第 $i$ 题在指定基线下的时延，$T_{\text{cand},i}$ 是候选 kernel 的时延，$\tau$ 是加速阈值。$\text{score}$ 就是常说的 fast-p（fast rate at threshold p），即“达到阈值 $\tau$ 的题目占比”。它与 faster rate 的区别在于后者通常只要求 $s_i>1$，阈值更松。geomean 则是 $\exp(\frac{1}{N}\sum_i \ln s_i)$，对 $s_i<1$ 的题目同样计入，因此对“少数题极慢”比算术平均更敏感。

三个指标回答不同问题，混用会制造不可比。faster rate 回答“有多少题比基线快”，geomean 回答“整体几何平均提速”，fast-p 回答“有多少题达到某个有意义的门槛”。一个 agent 可以靠大量题目刚好超过 1.0 抬高 faster rate，却在 geomean 上被少数严重退化的题目拉低；反过来，少数题巨大提速也能抬高 geomean 而不改善 fast-p。论文的裁判测量与这些性能指标正交：它测的是正确性门的漏检率，不是速度。把两者混在一张表里报“综合分”，等于用一个未定义权重的加权和掩盖两个独立维度。

具体例子：若某题基线为 PyTorch eager，候选 kernel 在 fp32 下达到 1.3 倍，但裁判因容差过松而放过了一个精度变异体，那么该题在 fast-p 上计为通过、在变异分析上计为漏检。这两个结论同时成立，且必须同时报告。任何只报其中一个的评测表，都无法回答“这个分数是否可信”。

三 · 基线、硬件与 dtype：哪些数字不可比

基线口径是本论文最容易被误读的地方。论文指定 PyTorch eager、torch.compile 与论文指定的库实现作为基线。三者不可互换：eager 通常是最慢的基线，用它算出的加速比系统性偏高；torch.compile 会引入自己的融合与代码生成，与手写 kernel 的比较更接近同代际；库实现（如 cuBLAS 类）则是强基线，用它算出的加速比最保守。同一候选 kernel 在这三种基线下可以给出三个差异显著的数字，而论文并未声称跨基线可换算。

dtype 口径同样关键。论文的故障家族里精度类占主导，说明测量大量涉及 fp32/fp16/bf16 之间的数值路径差异。若基线未开 TF32 或未使用最强库，加速比会被高估；若候选 kernel 在 fp16 下运行而基线在 fp32 下运行，加速比则混合了精度与实现两个变量，不可比。工程判断是：报告加速比时必须同时声明 (a) 基线实现及其版本策略、(b) 双方 dtype、(c) 是否启用 TF32/张量核心、(d) 测量的是端到端还是仅 kernel 时延。缺任一项，数字不可复现。

硬件口径的不可比性来自论文的一条结论：跨 48 个完整架构，盲区随规模增长，且集中在深层同构流水线上。这意味着同一裁判在不同 GPU 上的漏检率不同——规模越大、流水线越深，容差盲带越宽。因此“在 A 卡上检出率 98.0%”不能外推到 B 卡。论文还指出有两道题的官方参考实现在基准自身容差下就违反 fp 一致性，即“不可裁判”（unrefereeable）。这两题在任何硬件上都应被剔除或单独标注，否则会污染分母。

四 · 隐藏 shape 与输入分布：盲带的来源

论文的核心机制之一是“容差盲带随归约规模增长”。形式化地说，若参考实现与候选实现都做长度 $n$ 的浮点归约，合法浮点方差随 $n$ 增长，裁判必须放宽容差才能避免误杀正确实现；放宽的容差又同时放过了精度变异体。于是存在一个由合法方差设定的“输入激进度上限”：输入分布越极端（大动态范围、长归约、病态条件数），合法方差越大，容差必须越松，盲带越宽。论文明确测量了这个上限，而不是假设它可以无限收紧。

隐藏 shape 的处理因此不是“多给几个随机 shape”那么简单。KernelBench-Verified 这一最强补丁的增益被论文拆解为 +4.0 点来自隐藏输入、+4.5 点来自更紧容差——两项贡献量级相当，说明单靠隐藏输入不足以补上精度维度的洞。工程上，隐藏 shape 的正确用法是让 shape 覆盖归约长度与动态范围的边界，而不是均匀随机采样；均匀采样会系统性低估长归约题目的盲带。

代价方面：每个隐藏 shape 都要一次编译加一次运行，shape 集合扩大线性推高测量时延与显存占用；更紧的容差则推高误杀率，即正确实现被判错，这会把 agent 推向保守实现，间接压低加速比。具体例子：一道长归约题在 $n$ 很大时，fp32 累加的合法方差已接近裁判容差，此时再收紧容差会把正确 kernel 判为失败，而放宽则放过降低累加精度的变异体——这正是论文所说“由合法浮点方差设定的激进度天花板”。

五 · 可核查的测量口径清单

把上述约束落成一份可执行的测量协议，需要固定以下要素，缺一项则该次测量的分数不可与他人的分数并列：

  • 题集与分母：188 道 KernelBench 题，剔除论文标注的两道不可裁判题，并声明是否剔除；变异分母为 10,303，带 witness 子集为 7,384。
  • 裁判版本：官方检查、KernelBench-Verified 或自建协议，逐项声明输入分布、容差、dtype 处理。
  • 指标分解：总分必须附按故障家族的漏检率（算术类 8.7%、精度类 78.6% 是论文基线，不是通用常数）。
  • 性能口径：基线实现、双方 dtype、TF32 开关、时延是否含同步、fast-p 的 $\tau$ 取值。
  • 硬件档：架构与规模，因为盲区随规模增长。
  • 复现产物：变异体、witness、kill matrix 与测试协议脚本，论文以 KernelBench-M 数据集形式发布。

这套清单的直接用途是审计：给定一份声称“检出率 98.0%”的测试协议，核查者应要求其给出 held-out 数字（论文对应 94.8%），因为 98.0% 是在 kill matrix 上优化得到的，存在对变异体集合的过拟合；94.8% 才是未见故障上的泛化估计。两个数字并列才构成可核查的声明。同理，任何只报“官方检查漏检 16.9%”而不报家族分解的引用，都丢失了最有工程价值的信息——精度类漏检 78.6% 才是部署端真正的风险面。

最后落到一个具体机制上：论文的故障分类学（taxonomy）被证明比原始故障本身更能教会测试生成器。这意味着测量口径里应保留“按家族标注”的字段，而不只是二值的 kill/miss。一个测试协议若只记录“是否杀死”，就无法利用家族信息去定向补强精度维度；而精度维度恰恰是 78.6% 漏检所在。可核查的测量不是把分数算得更准，而是把分数的构成暴露到足以指导下一步补测的粒度。

口径边界：当“杀死率”被当成排行榜分数时会发生什么

本节的立场是：mutation adequacy 是一个对 oracle 的度量，不是一个对 kernel 的度量。把它误接到性能口径上，会立刻产生三类不可比。第一类是基线漂移：论文的加速比形式为 $$s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}},\qquad \text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau]$$，其中 $$T_{\text{base},i}$$ 取 PyTorch eager、torch.compile 还是论文指定库，直接决定 $$s_i$$ 的分子；若基线未开 TF32、未走最强库路径，加速比会被系统性高估，而这一高估与 oracle 的杀死率毫无关系。第二类是 dtype 与容差耦合：论文测得精度类故障的逃逸率高达 78.6%，算术类仅 8.7%，说明“容差盲带随归约规模增长”这一机制在 fp32 累加、fp16 输入、bf16 混合精度下宽度不同，跨 dtype 抄分数等于把盲带宽度当成常数。第三类是硬件口径：48 个整机架构上盲区随规模增长、集中于深层同构流水线，意味着同一份 kill matrix 在另一块卡上重算会得到不同的逃逸集合——论文自己也把“跨硬件、跨 dtype、跨框架迁移未验证”列为局限。

隐藏 shape 与输入分布是第二个失效面。KernelBench-Verified 的增益被论文拆成 $$+4.0$$ 点来自隐藏输入、$$+4.5$$ 点来自收紧容差，这个拆分本身就是口径警告：隐藏输入带来的分数提升并不等价于 oracle 变强，它可能只是把测试从“随机采样”挪到了“更贴近真实分布”。工程上必须把 shape 分成三层记账——基准公开 shape、隐藏 held-out shape、生产 trace shape——并分别报告杀死率与加速比；否则 shape 特化 kernel 在离线基准上拿到的 $$s_i$$ 会在生产上崩塌，而 oracle 依然判它“正确”。论文用 kill matrix 优化测试集，两个输入即可达到 98.0% 检出（held-out 94.8%），这恰恰说明“输入数量”不是充分统计量，输入分布才是；把 98.0% 当成“oracle 已足够”去放行任意 shape，是把 held-out 的 5.2 个百分点缺口藏进了生产。

第三个代价是测量本身的系统开销与不可裁决性。注入 10,303 个可编译故障、其中 7,384 个带独立 kill witness，意味着每条测试协议都要对每个 mutant 编译并执行一遍：编译时间随 mutant 数线性增长，显存与上下文切换成本叠加，token 侧则体现为把编译/运行反馈回灌给 agent 的轮次膨胀。更硬的边界是“不可裁决”：论文指出两个问题的官方参考实现自身就违反了基准的容差（对 fp 而言），这类题在任何口径下都无法给出可信判决，必须从分母中剔除而不是当作 0 分或 1 分。可核查的测量口径因此应写成四元组：(基线实现与编译标志, dtype 与容差 τ, shape 三层来源, mutant 集合版本)，并同时报告 faster rate、geomean speedup 与 fast_p 三个指标——单一 fast_p 在 $$\tau$$ 附近对基线噪声极度敏感，geomean 则掩盖长尾退化。最后一条工程判断：kill matrix 的故障分类学比原始故障本身更能教会测试生成器，因此把 taxonomy 作为口径的一部分发布（KernelBench-M 已随数据集释放），比发布一个聚合分数更能让下游复现与审计。

口径可比性的边界：哪些数字只能内部自洽

这套测量把「oracle 充分性」定义成可复现的分数，代价是它只在论文自己那套口径内成立。基准是 188 个 KernelBench 问题的已验证 CUDA 实现，故障注入后得到 10,303 个可编译故障，其中 7,384 个带独立 kill witness；分数按 witness 被检出的比例计，官方检查漏掉 16.9%。这个比例是「确定性」的：同一批故障、同一套参考实现、同一容差，重复跑必然得到同一结果。一旦换硬件或换基线，分母（witness 集合）不变，但分子会变——因为检出与否取决于参考实现与候选在同一 dtype、同一输入分布下的数值差，而 fp32 累加顺序、TF32 开关、库版本都会改变这个差。所以 16.9% 不能当作跨平台常数引用，只能当作「该口径下的充分性下界」。

不可比的另一层来自加速比口径。论文流程里时延用统一基线测，若基线未开 TF32 或未用最强库实现，候选的相对优势会被系统性放大；这与 oracle 分数无关，却常被并排引用。可核查的做法是把两类数字分开登记：正确性侧只报 witness 检出率与容差参数，性能侧只报同一基线、同一 dtype、同一 shape 下的比值，并注明基线是否启用 TF32 与库版本。混合汇报会让「检出率高」被误读为「kernel 更好」。

$$\text{detect}=\frac{|\{f\in W: \text{oracle}(f)=\text{fail}\}|}{|W|},\qquad W=\text{witnessed faults}$$

隐藏 shape 与分布是这套方案最脆的边界。论文用优化套件在 kill matrix 上达到 98.0% 检出（留出 94.8%），说明「两个输入」就足以覆盖多数故障族；但这也意味着分数对输入选择高度敏感：若隐藏分布落在容差盲带之外（盲带随归约规模增长），检出率会虚高；若落在盲带之内，则虚低。更硬的失效条件是「不可裁判」：48 个整体架构中有两个问题的官方参考实现自身就违反了基准容差（对 fp 比较），这类题目的任何分数都无意义，必须在口径里单列剔除，而不是计入平均。系统代价随之而来：每增加一个输入就多一次编译与运行，故障注入本身要保证可编译，10,303 个故障的编译时间与显存占用构成测量成本的主要部分；把套件压到每题两个输入，正是用覆盖率换测量吞吐的工程折中。
