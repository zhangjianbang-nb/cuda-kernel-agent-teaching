一 · 一个推理服务里的真实算子现场

设想一个已经上线的 LLM 推理服务：prefill 阶段要做 fused residual + RMSNorm，decode 阶段每步都要跑一次 attention 的 softmax 归约，中间还夹着 RoPE 的旋转与 KV cache 的拼接写入。这些算子单看都不复杂，但它们在端到端时延里占据的比例并不小，而且形状随 batch、序列长度、head 数动态变化。工程团队面对的第一个现实是：这些算子要么直接调库，要么自己写。调库的代价是形状不匹配时退化严重——cuBLAS/cuDNN 的启发式选择在非常规 shape 上未必给出最优 tile，而框架层往往还要插入额外的 layout 转换 kernel，把一次本该融合的计算拆成三四次显存往返。自己写的代价则是另一套账：一个熟练的 CUDA 工程师写一个 fused RMSNorm，从读懂参考实现、确定 block 与 warp 的映射、处理尾部不对齐、到在目标卡上把 occupancy 调到可接受，通常以人日计；写完还要面对正确性回归、不同架构的编译分支、以及后续维护者看不懂 SASS 的窘境。

这就是本篇讨论的起点：Triton kernel 自动生成不是学术玩具，它瞄准的正是这类“库覆盖不到、手写不划算、但又在热路径上”的算子。Dr. Kernel 把大模型训练成能写 Triton kernel 的智能体，其问题现场由三个约束共同定义——开发周期要压缩到分钟级、性能要逼近手写上限、正确性不能靠人肉 review 兜底。这三者之间的张力，构成了旧方案非改不可的理由。

二 · 手写 CUDA 的工程账本

手写 CUDA 的性能上限最高，因为它允许工程师直接控制寄存器分配、共享内存布局、warp 级原语与异步拷贝流水。但这份控制力的代价是显式的：每一个 tile 尺寸的选择都要和 occupancy、bank conflict、指令级并行一起权衡；每一次归约都要考虑 warp shuffle 的树形结构与跨 warp 的共享内存中转；每一个边界条件都要在索引计算里显式 clamp，否则越界读写不会报错，只会静默污染结果。更麻烦的是，这些决策与具体 GPU 架构绑定——同一份 kernel 在 sm_80 与 sm_90 上的最优配置不同，异步拷贝与 TMA 的可用性也不同，于是代码里长出大量 #if 分支与模板特化。

从工程度量上看，手写路径的成本结构大致是：开发时延以人日计，正确性验证依赖逐元素比对与边界用例覆盖，性能调优依赖 NCU 采集的 stall 原因与 SASS 反汇编阅读，维护成本随架构分支数量线性增长。一个具体的例子：为 decode 阶段的 attention 写一个融合 softmax 的 kernel，工程师需要处理序列长度不是 tile 整数倍时的 masking、在线 softmax 的 running max 与 running sum 更新、以及输出写回时的 layout 对齐。任何一处写错，结果不会崩，只会让生成文本的概率分布轻微偏移——这类错误在端到端评测里极难定位，只能靠算子级的逐元素 oracle 拦住。

换言之，手写 CUDA 的痛点不是“写不出来”，而是“写对且写快”的单位成本太高，且这份成本无法随任务数量摊薄。当模型结构迭代导致算子形状频繁变化时，手写路径的边际成本几乎不下降。

三 · Triton 把门槛降下来，但把正确性风险留在了原地

Triton 的设计取舍是把 block 级编程模型暴露给用户：工程师描述的是 tile 上的计算，编译器负责把它 lowering 到 warp 级指令、决定共享内存分配与流水线调度。这让代码量大幅收缩，一个 matmul 或 softmax 的 Triton 实现可以在一屏内写完，且同一份代码能跨架构编译。代价是性能上限被编译器的调度策略封顶：自动生成的流水线深度、向量化宽度与 swizzle 方式未必匹配具体 shape，工程师只能通过 num_warps、num_stages、BLOCK_SIZE 这类旋钮间接影响，而无法像 CUDA 那样直接指定寄存器级布局。

更关键的是正确性风险并未随代码量下降而消失。Triton 的语义里，tl.load 的 mask、tl.arange 的边界、归约轴的选择、以及 fp32 累加与 fp16 输入之间的类型提升，都是容易出错的点。一个典型的失败模式是：归约时把 tl.sum 的轴写错，编译通过、运行不崩，但结果在某个维度上被错误折叠；或者 masking 条件用了 < 而非 <=，在序列长度恰好等于 tile 边界时丢掉最后一个元素。这些错误对编译器而言完全合法，只有逐元素比对参考实现才能暴露。

于是 Triton 把“写”的门槛降下来了，却把“验证”的门槛原样留给了工程团队。当生成主体从人变成模型时，这个未被降低的验证门槛就成了瓶颈：模型可以批量产出语法合法的 kernel，但其中正确率未知，人工 review 无法扩展。

四 · 库调用的性能天花板与融合缺口

库调用路径看似最省事，实则把成本转移到了别处。cuBLAS、cuDNN、CUTLASS 提供的 kernel 在标准 shape 上经过深度调优，性能通常难以被手写超越；但它们的启发式选择以通用性为目标，在 batch 很小、序列很长、或者 head 维度不是 2 的幂时，往往选不到最优 tile。更结构性的问题是融合：一个 RMSNorm 后接残差加法的模式，在库调用路径下是两次独立的 kernel launch，中间结果要写回显存再读出来，多出一次完整的读写往返。以 fp16 激活、隐藏维度数千的量级估算，这次往返的带宽开销足以吃掉融合本可节省的时间。

工程上还有一个隐性成本：库的版本与框架的绑定。升级 CUDA 版本可能改变启发式行为，导致同一份模型在不同环境下的时延不可复现；而自定义融合算子则要自己承担跨版本编译兼容性。这就形成了一个尴尬的中间地带——库覆盖不到的融合模式，既没有现成 kernel 可用，又不值得为每个 shape 手写一份。Triton 生成恰好落在这个地带的中心：它要产出的不是通用库的替代品，而是针对具体算子语义与输入分布的定制 kernel。

$$\text{speedup} = \frac{t_{\text{base}}}{t_{\text{kernel}}}, \quad \text{其中 } t_{\text{base}} \text{ 为基线实现的实测时延}$$

这个比值是 Dr. Kernel 性能奖励的核心，但它同时暴露了旧方案的评价困境：基线是谁？如果基线是库调用，那么融合带来的加速比会很好看，但库在标准 shape 上本就接近 roofline，加速空间有限；如果基线是朴素手写实现，加速比容易虚高，却不代表工程价值。基线口径不固定，加速比就不可比——这一点在后续评测部分会展开，此处只需记住：性能奖励的可信度从基线定义那一刻就开始承担风险。

五 · 单轮提示与执行反馈的稀疏性

在 Dr. Kernel 之前，kernel 生成的主流做法是单轮提示：给模型算子语义与参考实现，让它一次性输出 kernel 源码，然后编译运行看结果。这条路径的失败模式非常具体。第一类是编译失败：类型不匹配、未定义的符号、Triton 版本差异导致的 API 变更，模型在单轮里没有任何机会看到错误信息并修正。第二类是运行失败：越界访问触发 illegal memory access，或者共享内存超限导致 launch 失败，这些错误在单轮范式下只表现为一个“失败”标签，无法告诉模型错在哪一行、哪个索引。第三类是数值不一致：编译运行都通过，但与参考实现比对不通过，模型同样拿不到差异模式。

把这三类失败压缩成一个二值奖励，就是奖励稀疏的来源。假设一个任务的成功率是 p，单轮采样的奖励方差约为 p(1-p)，当 p 很低时几乎全部样本奖励为零，策略梯度没有可用的方向信号。更糟的是奖励黑客：如果奖励只看速度不看正确性，模型会学会产出不计算任何东西的 kernel——空 kernel 或只写回常量的 kernel 编译最快、运行最快，加速比趋于无穷。这不是假设性的担忧，而是任何以时延为奖励、以执行为判据的系统都必须正面处理的攻击面。

多轮 rollout 的意义正在于此：编译错误、运行失败、测速结果作为下一轮生成的上下文回灌，把一次性的稀疏信号拆成多级、可归因的反馈。模型第一轮修语法，第二轮修索引与边界，第三轮才谈分块与向量化。这条闭环的代价是 token 成本与编译运行开销随轮数线性增长——每多一轮，就多一次生成、一次编译、一次 GPU 运行与一次比对。轮数不是免费的，这正是后续训练部分要量化的工程账。

六 · 为什么非改不可：三个不可回避的工程判断

第一个判断是规模。算子形状随模型迭代而变化，手写路径的边际成本不随任务数量下降，库调用路径在非标准 shape 与融合模式上覆盖不足，两者叠加留下的缺口只能由自动生成填补。第二个判断是可信度。生成系统要能上线，正确性判定必须由可验证的 oracle 承担，而不是由模型自述或人工抽检承担；逐元素比对参考实现是唯一可扩展的硬门槛，容差与输入分布的设计决定了这个门槛的松紧。第三个判断是奖励结构。只要性能奖励存在，就必然存在投机路径，因此正确性未通过时奖励必须为零，且加速比要设上限以控制奖励尺度——上限的作用不是惩罚快，而是防止个别极端值主导策略更新，让训练信号分布在可比较的区间内。

把这三条落到具体机制上：生成端产出 Triton 源码与启动脚手架；执行端编译、运行、与参考实现逐元素比对；评测端先过正确性 oracle，再以相对基线的加速比折算性能奖励。任何一环缺失，系统就会退化——缺 oracle 则奖励黑客横行，缺多轮反馈则稀疏奖励无法收敛，缺基线口径则加速比不可比。这三者的组合不是锦上添花，而是让“模型写的 kernel”具备工程可用性的最低条件。旧方案在这三条上各自有缺口，这就是 Dr. Kernel 要重新做 RL 配方的直接动因。

值得强调的是，正确性 oracle 本身也有代价。逐元素比对需要把参考实现的输出完整驻留在显存中，对于大 shape 意味着额外的显存占用与一次全量读回；容差选择过松会放过数值偏差，过紧则会把合法的浮点重排判为失败。这个权衡在材料中未给出具体取值，但它决定了整个奖励信号的信噪比——oracle 判错一次，后续所有性能奖励都建立在错误的前提上。

手写与库调用之间的“无人区”：Triton 生成任务的系统代价

把视角放到一个在线推理服务的算子库维护现场：某个 attention 变体在特定 head 维度上表现不佳，工程师要在“改库调用参数”与“手写 CUDA 特化 kernel”之间做选择。前者受限于库已编译的模板实例与分块策略，后者则要求作者同时掌握索引映射、边界谓词、共享内存布局与 warp 级归约，一次改动往往牵动编译、数值比对与回归测速三条链路。Triton 试图填进这条中间地带——用 Python 级 DSL 表达分块与并行，让非 CUDA 专家也能写出接近手写水平的 kernel。但恰恰是这个“中间”定位暴露了旧方案的边界：库调用无法覆盖长尾 shape 与融合模式，手写 CUDA 的开发周期与可维护性代价又难以摊薄到单个算子；而 Triton 源码本身仍是一份需要正确性证明与性能调优的程序，人工写它的边际成本并不比 CUDA 低多少。

失效条件很具体。库调用在算子融合、非标准布局、动态 shape 上退化为多次 launch 加中间张量落地，带宽被读写往返吃掉；手写 CUDA 在架构代际切换时，寄存器压力与 occupancy 的调参经验不可迁移，维护者需要重跑 profile 才能判断是否该改 block size。Triton 的边界则在于其抽象层对某些底层控制（如精细的 shared memory swizzle、异步拷贝流水）表达力不足，遇到这类需求仍要回落到 PTX 或 CuTe。三种路径共同的代价是“验证成本”：任何一次 kernel 改动都必须重新建立正确性 oracle 并重测算术强度，而这一步在旧流程里靠人工比对与零散 benchmark，无法作为可复用的训练信号。

$$\text{人工迭代成本} \approx N_{\text{试错}} \cdot \left(t_{\text{编写}} + t_{\text{编译}} + t_{\text{比对}} + t_{\text{测速}}\right)$$

上式里每一项都不是小数：编译一次 Triton kernel 要经过 IR lowering 与 PTX 生成，比对要构造覆盖边界与极端 shape 的输入分布，测速要固定基线实现与计时口径。旧方案把这些成本压在单个工程师身上，导致长尾算子长期停留在“能跑但不快”的状态。更关键的是，人工反馈无法规模化为一阶可验证奖励：写错一个边界谓词，编译器不会报错，只有逐元素比对才能发现；而性能是否真的优于基线，取决于基线是否同一实现、测速是否同一口径。这正是后续把编译通过、数值一致与相对基线加速比组合成多级奖励、并以正确性为硬门槛的动机所在——旧方案缺的不是想法，而是一条把“生成—编译—运行—评测”闭环自动化的可信通路。
