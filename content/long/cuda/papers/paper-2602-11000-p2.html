一 · 基准构成与“扩展套件”的口径漂移

这篇论文的评测对象是 KernelBench 系基准，但摘要里出现了一个关键措辞：“an expanded KernelBench suite”。这意味着论文报告的 97.4% 解决率与 72.9% 超越 TorchInductor 的比例，并不是在原始 KernelBench 题目集上取得的，而是在一个被扩展过的题目集合上取得的。对任何要复现或对比的工程团队来说，第一件必须核清的事就是：扩展了什么、扩了多少、扩展题目的难度分布是否与原集同构。如果扩展部分偏向更容易被 Triton 表达的逐元素或归约类算子，那么 97.4% 这个数字与在原始集上测得的解决率就不可直接比较；反过来，如果扩展部分引入了更多融合模式或非标准布局，那么它反而更能暴露模型的真实上限。论文摘要没有给出扩展的具体构成，因此可核查的测量口径必须要求：报告分母（题目总数）、报告每道题的算子类别与参考实现来源、并明确标注哪些题目属于原集、哪些属于扩展集。缺少这三项，任何跨论文的解决率对比都是无效的。

基准的另一个口径问题是“题目”与“测试用例”的区分。KernelBench 系基准的通行做法是每道题给定一个 PyTorch 参考实现和一组输入 shape，模型需要产出行为等价的 kernel。正确性判定依赖在这组输入上的逐元素比对（通常带容差）。于是“解决率”实际上是“在给定输入分布上通过正确性门且性能门”的比例，而不是“算子被正确实现”的比例。这个区别在隐藏 shape 的场景下会被急剧放大：一个针对固定 shape 做了特化的 kernel，可以在基准输入上通过全部检查，却在生产侧的动态 shape 上直接编译失败或退化为标量循环。论文的 43.7%→77.0% 正确率提升，其分母是单次尝试下的题目数，其分子是通过正确性门的题目数——这个口径本身是清晰的，但它不度量泛化。

二 · 基线选择：三个基线、三种不可比

论文指定的基线是 PyTorch eager、torch.compile（其代码生成后端为 TorchInductor）与论文指定的库实现。这三个基线在加速比计算中扮演完全不同的角色，混用会直接制造虚假收益。

  • PyTorch eager 是“未优化参考”，以它为分母得到的加速比通常最大，但它几乎不构成工程意义上的对手。用 eager 做分母的加速比在跨论文比较时最容易失真，因为不同论文可能在不同 dtype、不同是否启用 TF32、不同是否做同步测量的条件下测 eager。
  • TorchInductor 是真正的对手。论文的核心性能指标——“fraction of problems outperforming TorchInductor”从 14.8% 提升到 21.8%——就是以它为分母的。这个指标的定义必须是：在同一输入、同一 dtype、同一测量协议下，候选 kernel 的中位时延严格低于 Inductor 生成 kernel 的中位时延，且候选通过正确性门。任何一处协议不一致，这个比例就会漂移。
  • 库实现（cuBLAS/cuDNN 等）是上界参照。对 matmul、conv 这类算子，库实现往往已经接近 roofline，模型生成的 Triton kernel 超越库实现的空间极小；若论文把库实现纳入分母而不加区分，会系统性压低“超越比例”。

由此产生的第一个不可比点是 dtype 与精度模式。Triton 在 fp32 上默认的累加行为、PyTorch 是否开启 TF32、cuBLAS 是否走 TF32 tensor core 路径，都会让同一算子的时延相差数倍。若基线未开 TF32 而候选 kernel 走了 tf32 路径，加速比会被系统性高估；反之若基线用了最强库路径而候选只做了朴素实现，则会低估。第二个不可比点是测量协议：是否做 warmup、是否用 CUDA event 计时、是否在计时前同步、是否取中位数而非均值、是否把 kernel launch 开销计入。第三个不可比点是编译时间是否计入——Triton 的 JIT 编译在首次调用时可能耗时数百毫秒到数秒，若不计入则离线分数好看，计入则端到端收益可能为负。

三 · 指标族：faster rate、speedup、geomean、fast_p 与 roofline 的分工

论文同时使用了多个指标，它们回答的问题不同，不能互相替代。可核查的口径要求每个指标都带明确的定义式。

$$\text{faster rate}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}\left[\text{lat}_{i}^{\text{cand}}<\text{lat}_{i}^{\text{base}}\right],\qquad \text{geomean speedup}=\exp\left(\frac{1}{N}\sum_{i=1}^{N}\ln\frac{\text{lat}_{i}^{\text{base}}}{\text{lat}_{i}^{\text{cand}}}\right)$$

faster rate（论文中的“fraction of problems outperforming TorchInductor”）是一个计数型指标，它对每道题只问“是否更快”，对快多少不敏感。它的优点是抗离群值，缺点是掩盖了分布：21.8% 的题目更快，但这 21.8% 里可能大量只是微弱领先，而落后题目可能落后数十倍。geomean speedup 则是对数域的均值，论文报告的 2.12 几何平均加速比正是这个口径。几何平均的意义在于它把“快 2 倍”和“慢 2 倍”对称处理，不会被单题的超大加速比拉高；但它同样不告诉你尾部有多差。fast_p 是 faster rate 的阈值化版本——要求加速比超过 p（例如 fast_1.0 即严格更快，fast_1.5 即至少快 50%），它把“微弱领先”和“实质领先”区分开。论文摘要只给了 faster rate 与 geomean，没有给 fast_p 的 p 值分布，这构成一个可核查性缺口：读者无法判断 21.8% 中有多少是实质性的性能改进。

roofline 口径是另一条独立轴。加速比是相对量，roofline 是绝对量：把实测时延与该算子在其算术强度下的理论下界比较，得到 SOL（speed-of-light）利用率。一个 kernel 可以相对 eager 快 3 倍，却只达到 roofline 的 15%，因为 eager 本身离下界很远。论文摘要未提及 roofline 指标，因此其性能主张全部是相对口径，无法回答“这些 kernel 离硬件极限还有多远”。对生产部署而言，相对口径足够回答“换掉 Inductor 是否划算”，但不足以回答“是否值得继续投入优化”。

指标定义回答的问题典型失真来源
faster rate候选严格快于基线的题目占比换用候选是否值得基线未开 TF32、微弱领先被计入
geomean speedup加速比的对数均值整体收益幅度单题超大加速比、失败题被剔除
fast_p加速比超过 p 的题目占比实质改进的比例p 值未报告则不可比
roofline / SOL实测时延相对理论下界离硬件极限多远算术强度估算依赖实现细节

四 · 正确性门与性能门的耦合：43.7%→77.0% 的分母陷阱

论文报告的单次尝试正确率从 43.7% 提升到 77.0%，提升 33.3 个百分点。这个数字的口径必须与性能指标的口径严格区分：正确率的分母是全部题目，分子是通过正确性检查的题目；而 faster rate 的分母是“通过正确性的题目”还是“全部题目”，会带来完全不同的读数。若 faster rate 的分母是全部题目，那么一个正确但极慢的 kernel 会同时拉低正确率分子之外的 faster rate；若分母是通过正确性的子集，那么正确率提升本身就会机械地改变 faster rate 的基数。论文摘要未明示这一点，因此可核查的口径要求：报告 faster rate 时同时给出其分母（通过正确性的题目数）与全题目数下的比例。

正确性门本身也有代价。逐元素比对带容差，容差的选择直接影响通过率：fp16/bf16 下累加顺序不同会导致末位差异，容差过紧会把合法实现判错，过松则会放过数值不稳定的实现。更隐蔽的是“隐藏 shape/分布”的处理。论文摘要提到基准输入分布“按论文口径”，但未给出全部 shape。工程上可核查的做法是三层：(1) 基准公开 shape 上的正确性与性能；(2) 留出 shape（同分布但未公开）上的正确性，用于检测 shape 特化；(3) 动态 shape 或极端 shape（如空张量、超大 batch、非对齐维度）上的编译成功性与退化行为。第三层尤其关键：Triton kernel 在非 2 的幂维度上常需要 mask 分支，一个只针对 1024 对齐优化的 kernel 在 1000 维度上可能触发大量掩码开销，时延翻倍而正确性仍通过。隐藏分布若不覆盖这类边界，离线分数就会系统性乐观。

五 · 硬件、dtype 与“2.12 几何平均”的适用边界

论文的结论只在论文给定的硬件、基线与输入分布上成立。硬件口径至少涉及三项：GPU 型号与显存带宽、SM 数量与时钟、是否多卡。同一 kernel 在带宽受限的 SKU 与算力受限的 SKU 上，roofline 拐点位置不同，最优实现策略（是否做算子融合、是否用 shared memory 分块）也不同。dtype 口径涉及 fp32/fp16/bf16/fp8 的选择与累加精度：Triton 对 bf16 的 dot 默认走 tensor core，对 fp32 则可能走 FMA 路径或 tf32 路径，两者的吞吐差一个数量级。若论文的 2.12 几何平均加速比是在某一 dtype 下取得的，把它外推到另一 dtype 就是无效推断。

“2.12”这个数字还有一个结构性含义：几何平均对失败题目敏感。若某题候选 kernel 编译失败或正确性不通过，该题在几何平均中如何计入——剔除、记加速比为 1、还是记一个惩罚值——会显著改变结果。剔除失败题会系统性抬高几何平均（幸存者偏差）；记 1 则把失败等同于“与基线持平”，同样乐观。可核查的口径要求明确：几何平均的分母是否为全部题目、失败题如何赋值。论文摘要未给出这一处理，因此 2.12 只能作为“在论文口径下”的声称值，不能作为跨论文比较的锚点。

具体例子：假设某道归约题在基准 shape（batch=1024, hidden=4096）上，候选 kernel 通过分块与向量化把时延从基线的 0.8 ms 降到 0.4 ms，加速比 2.0；但同一 kernel 在隐藏 shape（batch=1000, hidden=4095）上因掩码分支退化到 1.6 ms，加速比 0.5。若隐藏 shape 未纳入评测，该题贡献 +2.0 到几何平均；若纳入，贡献变为 −2.0 的对数项。一道题的符号翻转就足以让整体几何平均移动可观幅度，这正是隐藏分布必须公开的原因。

六 · 可核查测量口径的最小清单

把上述讨论收敛成一份工程团队可以直接执行的清单，用于复现论文数字或做跨论文对比。每一项缺失都意味着对应指标不可比。

  • 题目集：总题数、原集与扩展集的划分、每题参考实现来源、算子类别分布。
  • 基线：eager 的 dtype 与 TF32 开关状态、Inductor 的版本与编译选项、库实现的版本与是否走 tensor core 路径。
  • 测量：warmup 次数、计时方式（CUDA event / wall clock）、同步点、统计量（中位数/均值）、是否计入 JIT 编译时间与 launch 开销。
  • 正确性：容差与 dtype 组合、比对元素数、是否含 NaN/Inf 处理、隐藏 shape 集合与动态 shape 覆盖。
  • 指标：faster rate 的分母、geomean 对失败题的赋值规则、fast_p 的 p 值、是否报告 roofline/SOL。
  • 硬件：GPU 型号、显存带宽、SM 数、单卡/多卡、驱动与 CUDA 版本。

这份清单的直接代价是 token 与工程时间：完整报告隐藏 shape 集合与失败题处理规则会让论文的评测章节显著变长，复现方则需要为每个基线组合跑一遍测量矩阵。但不做这件事的代价更高——43.7%、77.0%、21.8%、72.9%、2.12 这些数字一旦脱离口径，就会在跨论文对比中被误读为“模型能力”的差异，而实际上它们度量的是评测协议之间的差异。对生产端到端收益而言，真正决定是否上线的不是基准上的 faster rate，而是在目标硬件、目标 dtype、目标 shape 分布下重测一遍得到的 faster rate 与 geomean——基准数字只提供先验，不提供保证。

口径边界：哪些加速比不可比，隐藏 shape 如何穿透评测

这篇论文的可核查数字只有一组：单次尝试正确率 43.7%→77.0%，优于 TorchInductor 的比例 14.8%→21.8%；接入完整 agent 后在扩展 KernelBench 上解出 97.4%、72.9% 的题超过 TorchInductor、几何平均加速比 2.12。跨论文比较时必须先对齐四件事：基线是否含 torch.compile/TorchInductor 与论文指定库、dtype 是否统一（TF32 开关直接改变 eager 基线时延）、GPU 型号与时钟、以及计时是否含编译与首次调用。任一项不同，2.12 这类几何平均就不可直接搬运；尤其基线未开 TF32 或未用最强库实现时，加速比会被系统性高估。

隐藏 shape 的处理决定了离线分数的可信度。若候选 kernel 按固定 shape 做了 tile/block 特化，评测分布一旦偏移，正确性门仍可能通过而性能门崩塌。可核查口径应写成：对每个题维护输入分布 D，报告 $$\text{fast}_p=\frac{1}{|D|}\sum_{x\in D}\mathbb{1}\!\left[\frac{t_{\text{base}}(x)}{t_{\text{cand}}(x)}\ge p\right],\quad \text{speedup}_{\text{geo}}=\exp\!\Big(\tfrac{1}{|D|}\sum_{x\in D}\ln\tfrac{t_{\text{base}}(x)}{t_{\text{cand}}(x)}\Big)$$ 即同时给出 fast_p 与几何平均，并声明 p、D 的构造方式与是否含极端 shape；只报单一几何平均会掩盖长尾退化。

系统代价落在测量环节：逐 shape 计时加 NCU/SASS profile 会把单题评测从秒级推到分钟级，agent 多轮迭代时 profile 开销可占总时延的主要部分；编译时间与 Triton autotune 的首次调用也必须计入或明确剔除。失效条件很具体：reward 里 Δspeed 未与正确性门绑定，模型会以 fallback 到 eager 或删减计算换取虚高正确率；shape 特化在隐藏分布上表现为正确率不变而 fast_p 骤降。工程判断是：把 43.7%→77.0% 视为单次尝试的正确性锚点，把 72.9%/2.12 视为特定硬件与基线下的条件结论，复现时先锁定基线口径再谈迁移。
