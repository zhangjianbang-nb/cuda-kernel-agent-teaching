一 · 一个算子库维护者的深夜：从 cuBLAS 到自研 kernel 的落差

设想一个真实推理服务的算子库维护场景：模型结构定型后，团队发现某个融合算子（例如 attention 里的 QK^T 后接 softmax 再乘 V，或者一个带 epilogue 的 GEMM）在高层库调用下无法覆盖。cuBLAS 与 cuDNN 只提供固定切面的原语，一旦需要把 bias、激活、量化缩放融进同一个 kernel 以省掉一次 HBM 往返，库调用就失效了。此时工程上只有三条路：手写 CUDA C、用 Triton 重写、或者继续在库调用外拼多个 kernel。三条路各有各的账要算，而账本上的第一行永远是开发周期。

手写 CUDA C 的现实成本不在写，而在调。一个能在目标 shape 上跑出接近 roofline 的 GEMM，需要工程师同时决定线程块尺寸、每线程 tile、shared memory 的 swizzle 布局、寄存器分块、流水级数与 cp.async 的排布。这些决策彼此耦合：改一个 tile 尺寸，寄存器压力变化，occupancy 变化，流水深度又要重排。一个熟练工程师为一个算子调出稳定性能，周期以周计；而推理服务的模型迭代以月计，算子库的排期根本追不上。这就是“非改不可”的第一层压力——不是性能不够，是交付节奏对不上。

性能上限是第二层。手写 CUDA 的性能天花板取决于工程师对目标硬件的理解深度，而硬件在换代：同一份 kernel 在新架构上可能因为 MMA 原子形状、shared memory bank 宽度、寄存器文件大小的变化而性能骤降。维护者要为新架构重调一遍，且没有系统化的方法保证调优结论可迁移。第三层是正确性：手写 kernel 的越界访问、race condition、数值精度偏差往往在特定 shape 或特定 batch 下才暴露，测试覆盖靠人工枚举边界情形，漏一个就是线上事故。第四层是可维护性：一个算子库里的 kernel 由不同工程师在不同时期写成，风格、布局约定、启动配置各不相同，新人接手时读代码的成本高于重写。

这四层压力叠加，使得“算子库维护”变成一个高人力、低复用、难验证的工种。而 LLM 已经能生成 Triton 与 CUDA C 代码这一事实，让工程界看到了把这条链路自动化的可能——但真正的障碍不在语言层，而在抽象层。

二 · Triton 的甜区与边界：为什么它救不了所有算子

Triton 的设计取向是用块级编程模型屏蔽线程级细节：程序员写的是 tile 上的操作，编译器负责把它 lowering 到线程、shared memory 与 MMA 指令。这个抽象对一类算子极其有效——以 elementwise、reduction、规则分块的 GEMM 为代表，代码量小、可读性高、跨架构可移植性好。但它有一个明确的边界：当算子需要精确控制数据在寄存器与 shared memory 之间的布局、需要手工选择 MMA 原子形状、需要把多个不同形状的 tile 拼进同一条流水线时，Triton 的块级抽象就不再提供足够的表达力。

具体机制上，Triton 的 layout 由编译器推导，程序员只能通过有限的 hint 影响它；而在 CuTe 的世界里，layout 是一等公民，是可以用类型系统在编译期表达和组合的对象。一个典型的例子是带非标准 epilogue 的 GEMM：输出 tile 需要按特定 stride 写回、需要与另一个 tensor 做逐元素融合、且融合部分的访问模式与主 GEMM 的 MMA 输出布局不一致。Triton 里这通常意味着一次额外的 layout 转换（通过 shared memory 中转），代价是一次额外的 shared memory 往返与同步；而在 CuTe 里，可以用 `composition` 与 `layout` 的组合在编译期把 epilogue 的访问模式直接对齐到 MMA 输出，省掉这次中转。

代价是量化的：一次 shared memory 中转在 tile 级别意味着额外的写-读带宽与一次 barrier，在带宽受限的算子上直接反映为吞吐下降；更隐蔽的代价是寄存器压力——编译器推导的 layout 可能迫使某些中间结果落到 shared memory，而手工布局可以把它们留在寄存器里。这就是为什么高性能库（cutlass 系）最终都建在 CuTe 这类布局代数之上，而不是建在 Triton 的块抽象之上。Triton 的甜区很甜，但甜区之外是硬边界，而推理服务里恰恰有大量算子落在甜区之外。

三 · CuTe 的表达力与它的入场券价格

CuTe 的核心是把 tensor 建模为“布局 + 数据”的对偶：layout 是一个从坐标到偏移的映射，由 shape 与 stride 的嵌套元组构成，可以在编译期做代数运算（composition、product、complement）。MMA 原子（如 `SM80_16x8x16_F32F16F16F32_TN`）是带类型信息的模板，把指令形状、数据类型、寄存器布局全部编码进类型。程序员的工作变成：用 layout 代数描述数据分块，用原子类型描述计算单元，让编译器在实例化时把这些拼成完整的 kernel。

这套表达力的价格是入场券极高。要写一个正确的 CuTe kernel，工程师必须同时掌握：layout 的嵌套语义与 stride 约定、MMA 原子的寄存器布局要求、shared memory 的 swizzle 模式如何与原子布局对齐、以及模板实例化失败时那一屏几十行的编译错误在说什么。一个 layout 写错一个 stride，编译器报的错可能指向一个完全无关的模板参数，定位成本极高。这就是 CuTe 的现实：它给了你接近手写汇编的控制力，但把“布局正确性”这个负担完整地压回给程序员。

$$\text{layout}: (s_0, s_1, \dots) \mapsto \text{offset} = \sum_i c_i \cdot \text{stride}_i,\quad \text{stride 嵌套需与 MMA 原子寄存器序一致}$$

把这个负担交给 LLM，问题立刻显现：普通提示下模型能写出语法正确的 CuTe 代码框架，但 layout 的 stride 组合、原子选择与 swizzle 对齐这三件事，模型没有可靠的先验。生成结果要么编译不过（模板实例化失败），要么编译过了但数值错（layout 与原子寄存器序不匹配），要么两者都对但性能远低于手写版本（分块与流水策略选错）。这不是提示工程能解决的问题，因为失败信号不在文本里，而在编译器和 GPU 上。

一个具体的例子：为 row-major 的 A 与 column-major 的 B 写一个 TN 布局的 GEMM，模型若把 A 的 layout 写成 `(M, K):(K, 1)` 而原子要求的是 `(M, K):(1, M)` 的寄存器序，编译能过，但 MMA 读到的寄存器顺序错位，结果逐元素比对时大面积超差。这种错误靠读代码几乎看不出来，只有跑起来比对才知道。这就是为什么仅靠“生成代码”不够，必须有执行反馈。

四 · 旧方案的共同缺口：没有闭环，就没有可信的优化

把三条旧路放在一起看，它们的缺口是同一个：反馈回路是断的。手写 CUDA 的反馈是工程师的眼睛和 NCU profile，周期长但闭环完整；Triton 的反馈是编译器和 benchmark，但表达力受限导致闭环在边界处失效；库调用的反馈根本不存在，因为用户改不了库。而 LLM 生成代码这条新路，如果不接上编译、运行、正确性比对与 profile 这四个信号，就只是把“写代码”这一步加速了，把“调代码”这一步原封不动留给了人。

更具体地说，旧方案在四个维度上的代价可以并列比较。开发周期：手写以周计，Triton 以天计，库调用为零但覆盖受限。性能上限：手写取决于工程师水平且随架构漂移，Triton 受块抽象限制在甜区外有系统性损失，库调用固定在库的切面上。正确性保障：手写靠人工测试枚举，Triton 靠编译器保证布局但语义错误仍需人工比对，库调用由厂商保证。可维护性：手写风格分裂，Triton 较好但边界算子仍需回落手写，库调用不可改。

方案开发周期量级性能上限正确性保障可维护性
手写 CUDA C周取决于工程师，随架构漂移人工枚举边界风格分裂，接手成本高
Triton天甜区内好，甜区外系统性损失布局由编译器保证，语义需比对较好，边界算子需回落

这张表的含义不是“旧方案都不行”，而是：没有任何一条旧路能同时满足“覆盖任意融合算子、接近手写性能、有可验证的正确性、可维护”这四个条件。推理服务的算子需求恰恰落在这个四条件的交集之外。这就是 CuTeGen 这类工作的问题现场——不是要取代手写，而是要把 CuTe 这条唯一能同时逼近四个条件的路，从“只有少数专家能走”变成“智能体可以稳定走通”。

而要让智能体走通，就必须把 CuTe 的编译期约束变成生成约束，把编译诊断、运行时报错、数值比对与 profile 信号变成可回灌的反馈。缺了任何一环，优化就是盲目的：没有编译反馈，模型在模板错误里打转；没有正确性 oracle，性能数字可能是以数值错误为代价换来的；没有 profile，分块与流水的改写没有方向。这三者的组合正是旧方案缺失的闭环，也是后续所有机制设计的出发点。

五 · 为什么“可验证奖励”是这条路的工程前提

旧方案里，性能优化是人的判断：工程师看 profile，凭经验改 tile，再跑一遍。这个过程的每一步都有人在做“这个改动值不值得保留”的决策。把这一步交给智能体，就必须把决策标准写成可计算的量，否则搜索会退化成随机游走。CuTeGen 的奖励口径正是为此设计的：编译通过、数值正确、相对参考实现的加速比、profile 信号有效，四项共同构成一个可验证的标量。

$$\mathcal{L}=\alpha\,\mathbf{1}_{\text{compile}}+\beta\,\mathbf{1}_{\text{correct}}+\gamma\,\frac{T_{\text{ref}}}{T_{\text{gen}}}+\delta\,\mathbf{1}_{\text{profile\_ok}}$$

这个式子的工程含义比它的数学形式更重要。第一项是硬门：编译不过的候选直接淘汰，不进入性能比较，这避免了在无效代码上浪费评测预算。第二项是正确性门：数值超差的候选即使快也不能保留，这堵住了“用数值错误换性能”的捷径。第三项是性能项，用相对参考实现的加速比而非绝对延迟，使得不同 shape、不同硬件上的候选可以横向比较。第四项是 profile 有效性，用来区分“碰巧快”与“瓶颈被真正解决”。

代价在于评测成本。每个候选都要走一遍编译—运行—比对—profile，而 CuTe 的模板编译本身就慢：一个复杂 kernel 的模板实例化可能耗时数十秒到数分钟，候选数量乘以编译时间就是搜索的墙钟成本。再加上每轮修复消耗的 token，闭环的经济性完全取决于“多少候选能换来一个可用的 kernel”。这就是为什么任务规格层的字段设计如此关键——shape 分布、数据类型、参考实现、容差口径若定义不清，评测结果不可复现，整个闭环的可信度就塌了。旧方案里这些口径由人隐式持有，新方案里必须显式写成结构化字段。

一个具体的工程判断：在固定 CUDA 与 CuTe 版本、固定编译器选项的前提下，编译通过率本身就是一个有意义的度量。如果智能体在十轮修复后仍卡在同一类模板实例化错误上，说明反馈信号没有提供足够的信息让模型定位 layout 与原子选择的不匹配，这时继续加轮数只是烧 token。反过来，如果编译通过率随轮数稳定上升，说明诊断回灌的字段设计是有效的。这个判断不需要任何加速比数字就能做出，而它恰恰是旧方案里没人系统记录的东西。

六 · 问题现场的收束：闭环的三条硬约束

把问题现场收束成三条硬约束，就能看清 CuTeGen 这类框架为何必须按“规格—生成—编译执行—验证评测—反馈”五层来组织，而不是做一个单纯的代码生成器。第一条约束是表达力：目标算子落在 Triton 甜区之外，必须用 CuTe 的布局代数与 MMA 原子来表达，这意味着生成器必须理解 CuTe 的类型系统，而不是只会写 CUDA C 的线程代码。第二条约束是可验证性：性能数字必须挂在正确性 oracle 之上，否则加速比没有意义；这要求验证层在评测层之前，且容差与越界检查口径必须显式。第三条约束是反馈有效性：编译诊断与 profile 信号必须被结构化成模型能消费的字段，否则多轮修复会陷入重复失败循环——这是 CuTe 模板错误冗长带来的直接工程风险。

这三条约束共同解释了旧方案为何“非改不可”：手写 CUDA 满足表达力但开发周期与可维护性不达标；Triton 满足开发周期但在表达力上撞墙；库调用满足正确性与周期但覆盖受限。三者都无法同时满足推理服务对融合算子的需求。而 LLM 生成这条路，若不接上编译、运行、比对、profile 四类信号，就只是把第一条约束（表达力）从人转移到了模型，把后两条约束原封不动留在了工程侧。

具体到工程落地，最容易被低估的是反馈信号的字段设计。编译诊断不是一段文本，而是一个需要被解析成“错误类别 + 涉及的模板参数 + 疑似 layout 位置”的结构；profile 信号也不是一张图，而是需要被映射成“瓶颈类别 + 建议的改写动作”的规则。这两层映射的质量直接决定闭环能否收敛，而它们的维护成本（每轮修复的 token 消耗、每次编译的墙钟时间、每条映射规则的覆盖范围）在旧方案里从未被系统核算过。CuTeGen 的价值主张正是把这套核算显式化：用可验证奖励把“值不值得保留这个候选”变成可计算的判断，用结构化反馈把“下一轮该改哪里”变成可回灌的上下文。至于这套闭环在真实基准上的通过率与加速比，摘要级材料没有给出数字，工程判断只能落在机制层面——闭环是否成立，取决于编译诊断的解析粒度与 profile 到改写动作的映射稳定性，而不是取决于模型参数量。
