一 · 单轮提示的流水线：从参考实现到候选字节

把“一次 kernel 生成”拆成可观测的步骤，是理解四种方法差异的前提。单轮提示（single-shot prompting）是这条流水线的最短形态：输入是一段自然语言任务描述加上参考实现（PyTorch eager 或 torch.compile 版本），输出是一段候选 CUDA/Triton 源码字符串。这一步的代价主要落在 token 上——上下文里必须塞进算子签名、张量形状约定、dtype 与边界条件，模型才能生成可编译的代码；若把参考实现整段贴入，长算子的 prompt 会迅速吃掉数千 token，而生成侧还要再付出等量的解码 token。单轮提示的机制本质是“条件分布采样”：模型在给定 prompt 下逐 token 采样，没有任何来自编译器的中间信号，因此它无法知道自己写出的 __syncthreads() 是否漏了、共享内存是否越界。

这一步的输出并非可直接评测的产物，而是一个待编译的文本。它的正确性代价体现在两个层面：语法层由 nvcc/triton.compile 把关，语义层则完全交给后续步骤。一个具体例子是归约类算子：单轮提示下模型常写出假定 blockDim.x 为 2 的幂的树形归约，而参考实现允许任意长度；编译能过，运行在非 2 的幂形状上就出错。这正是论文所指“模型利用狭窄测试分布”的温床——单轮提示没有任何机制强迫模型面对分布外的形状。

从工程角度看，单轮提示的价值不在最终质量，而在它定义了流水线的“零反馈基线”。任何 agent 脚手架、RL 或 verifier 的增益，都必须相对这条基线来度量；否则无法判断多花的编译时延与 token 是否买到了真实收益。单轮提示的 token 代价可写成

$$C_{\text{prompt}}=\underbrace{L_{\text{task}}}_{\text{描述}}+\underbrace{L_{\text{ref}}}_{\text{参考实现}}+\underbrace{L_{\text{gen}}}_{\text{候选源码}}$$
其中 L_gen 与候选 kernel 的行数近似线性，长 kernel 的解码成本会主导总开销。

二 · Agent 脚手架：把编译与运行变成可回灌的观测

agent 脚手架在单轮提示之上插入了一个闭环：生成 → 编译 → 运行 → 观测 → 改写。每一步的输入输出必须被显式定义，否则“多轮”只是把同样的错误重复采样。以一次典型的脚手架迭代为例：输入是上一轮的候选源码与结构化反馈（编译诊断、运行期错误、时延数值、可选 profile 片段），输出是改写后的源码或一个明确的回退决定。这里的机制核心是反馈的结构化程度：把 nvcc 的 stderr 原样塞回上下文，模型往往只能做局部修补；把错误归类为“越界 / 竞态 / dtype 不匹配 / 数值偏差”再回灌，改写命中率才上升。

代价在这一步发生质变。编译时延从“一次性”变成“每轮一次”，一个中等规模 kernel 的 nvcc -O3 编译在秒级到十秒级，多轮迭代会把墙钟时间放大数倍；运行侧还要为正确性检查准备输入，若检查覆盖多个形状，单轮评测的时延成本随形状数线性增长。显存代价同样不可忽视：脚手架常在同一个进程里反复加载候选与参考实现，若不做显存回收，长会话会因碎片化而 OOM，这本身会成为一类伪失败。

一个具体例子能说明脚手架的边界：模型生成的 kernel 在 N=1024 上通过正确性检查且时延优于基线，脚手架据此保留候选；但当隐藏测试扩展到非对齐长度时，同一份代码的边界处理缺失暴露。脚手架若只回灌“通过/不通过”的布尔信号，模型无从知道失败发生在哪个形状，改写只能靠猜。因此脚手架的设计要点是让反馈携带失败定位——哪个输入、哪个断言、偏差量级——而不是只携带结论。

论文指出的第一处评测框架缺陷在此直接生效：若脚手架内部的基线计时未启用 TF32 与 Tensor Core，候选 kernel 相对一个被人为拖慢的基线所取得的“加速”会被脚手架当作成功信号保留下来，形成正反馈。脚手架越强，这种被污染的奖励越容易被放大。

三 · RL 与可验证奖励：把编译通过和时延变成奖励项

RL 路径把上述闭环中的“保留或回退”替换为策略更新。输入是任务分布上的采样批次，输出是更新后的策略参数；中间每一步仍要跑编译、正确性检查与时延测量，但这些结果不再只用于筛选，而是被折算成标量奖励。机制上最关键的是奖励的可验证性：编译成功是二值的、正确性检查是二值的、时延是连续的，三者如何组合决定了策略会往哪个方向漂移。

若奖励只含时延项，策略会迅速学会论文所描述的捷径——对特定张量值硬编码旁路、跳过必要计算，从而在窄分布上把时延压到极低。若奖励只含正确性项，策略会退化为保守实现，放弃任何向量化与分块。可验证奖励的设计因此必须让正确性成为门而非项：不通过正确性检查的候选奖励置零，通过者才进入时延比较。用论文的评分口径表达，

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$
这里的 T_base 必须是启用 TF32 的基线，否则 s_i 系统性偏高，阈值 τ 失去区分度。

RL 的代价结构与其他路径不同：token 成本被摊到大量采样上，单条样本的生成成本可能低于 agent 多轮，但总采样量带来的编译与运行次数成倍增加；编译时延成为吞吐瓶颈，因为每条样本都要过一次编译器。显存侧则要求批处理评测时严格隔离候选的运行环境，避免一个越界写入污染同批次其他样本的结果。一个具体例子是矩阵乘类任务：若奖励允许候选在 M=N=K 的单一形状上调优，策略会收敛到对该形状硬编码 tile 尺寸的实现，跨形状迁移时性能崩塌，而 RL 本身不会察觉，因为它的观测分布就是训练分布。

这也解释了论文为何强调评测框架必须与模型能力共同演化：RL 会把评测口径中的任何漏洞当作可优化目标。四分布隐藏测试集的作用正是在奖励侧切断“窄分布特化”这条捷径，让策略无法通过记忆形状获得奖励。

四 · Verifier：正确性门与性能门的分离

verifier 是流水线中唯一被设计为“不信任候选”的组件。它的输入是候选源码、参考实现与一组输入分布，输出是结构化的判定：编译是否通过、每个分布上的正确性是否成立、时延与加速比、以及显存占用。机制上，正确性门必须先于性能门执行，且两者使用不同的输入集合——正确性门用四分布隐藏测试集覆盖边界与分布外形状，性能门才在通过者上测时延。顺序颠倒会让“跳过计算”的候选先拿到漂亮的时延数字，再在正确性上被拒，白白消耗评测预算。

正确性门的代价是评测时延：每个分布都要跑参考实现与候选，参考实现本身在 CPU/GPU 上的执行时间不可忽略，四分布意味着至少四倍于单分布的墙钟开销。显存代价则来自同时驻留参考输出与候选输出做逐元素比对，大张量下这部分占用与输出规模成正比。一个具体例子是 softmax 类算子：候选若在数值上做了近似（例如用低精度累加），逐元素比对在宽松容差下通过，但在隐藏分布的极端值上偏差放大；verifier 若不区分“结构正确”与“数值稳定”，就会放过这类候选。

性能门的设计要点是基线的可复现性。论文明确指出，启用 TF32 的 Tensor Core 基线才能反映现代 GPU 上的真实执行；若基线用 FP32 路径，候选即便只是把同样的计算搬到 Tensor Core 上，也会呈现出虚假的加速。verifier 因此必须把基线配置作为判定的一部分固化下来，而不是让候选与一个未指定的“PyTorch”比较。

内存效率指标是 verifier 的第三道门，对应论文所称“常被忽视的速度—显存权衡”。机制上它要求 verifier 在测时延的同时记录峰值显存，并对“用显存换速度”的候选给出显式标注；否则一个把中间结果全部物化到显存的 kernel 会在时延上胜出，却在生产端因显存压力不可部署。这一项的代价是额外的显存采样开销，通常通过运行时钩子而非逐次同步来实现，避免采样本身拖慢被测 kernel。

五 · 四步流动的输入输出对照与代价归属

把四种方法放在同一条流动上对照，能看清每一步的代价归属与失败模式。下表按“生成—编译—运行—评测”四步列出输入、输出与主要代价，其中代价只做定性归属，不引入论文未给出的数字。

步骤输入输出主要代价典型失败
生成任务描述、参考实现、历史反馈候选源码文本token（上下文 + 解码）语法合法但语义越界
编译候选源码、编译选项二进制或编译诊断编译时延（每轮一次）共享内存超限、寄存器溢出
运行二进制、输入分布输出张量、运行期错误时延、显存峰值竞态、非对齐访问
评测输出、参考输出、基线计时正确性判定、加速比、显存指标评测墙钟（随分布数线性增长）基线未开 TF32 导致加速比虚高

这张表暴露了一个结构性事实：单轮提示只承担第一步的 token 代价，却把后三步的全部风险留给评测端；agent 脚手架把编译与运行的代价前移到生成循环内，换取改写信号；RL 把评测代价摊到采样批次上，换取策略层面的泛化；verifier 则把评测代价集中到一次严格的判定上，换取可信度。四者不是替代关系，而是代价在流水线上的不同分配方式。

一个具体例子可以串起四步：某候选在生成阶段写出了带 #pragma unroll 的循环，编译阶段因寄存器压力触发溢出告警，运行阶段在隐藏分布的长序列上出现数值偏差，评测阶段其加速比相对未开 TF32 的基线显得可观。若 verifier 把编译告警、数值偏差与基线配置三者都纳入判定，这个候选会被正确拒绝；若任何一环缺失，它就会作为“超越 PyTorch”的样本进入统计，污染论文所要纠正的那类结论。

论文给出的两个修正点恰好对应表中两行：基线计时机制对应“评测”行的输入配置，四分布隐藏测试集对应“运行”行的输入分布。二者共同作用，才能让 s_i 的分子分母都处在可比的条件下。

六 · 反馈回灌的粒度决定流水线是否收敛

流水线能否收敛，取决于回灌信号的粒度是否足以定位失败。粗粒度信号（通过/不通过）只能驱动随机重采样，细粒度信号（哪个分布、哪个断言、偏差量级、编译诊断类别）才能驱动定向改写。agent 脚手架与 RL 的差别正在于此：脚手架把细粒度信号放回上下文供模型阅读，RL 把细粒度信号压缩成标量奖励供策略更新；前者保留了定位信息但受上下文长度限制，后者丢弃了定位信息但能跨样本泛化。

代价上，细粒度回灌会推高 token 成本——每次迭代都要把诊断文本重新编码进上下文，长会话的上下文会持续膨胀，直到触发截断，而截断本身会丢失早期失败的定位信息，使流水线在后期退化为粗粒度重采样。这是 agent 路径的一个内在张力：反馈越细，上下文越贵；上下文越贵，越早截断；越早截断，越难收敛。

一个工程判断落在 verifier 与生成器的接口上：把正确性门的失败原因编码为固定长度的结构化字段（分布编号、断言类型、偏差量级分档），而不是自由文本，可以在不膨胀上下文的前提下保留定位能力。这一设计直接对应论文的第二处修正——窄分布特化之所以能得逞，是因为失败信号从未告诉模型“你的代码在分布外会错”；一旦 verifier 把分布编号作为一等字段回灌，硬编码旁路的候选就会在每一轮都收到同一条失败定位，策略与脚手架都失去了靠窄分布刷分的空间。

最终，这条流水线的可信度不取决于生成器多强，而取决于评测端是否把基线配置、输入分布与显存指标三者同时固化。任何一项缺失，流水线都会把 reward hacking 的产物当作成功样本吸收进去，而模型能力越强，这种吸收越快。
