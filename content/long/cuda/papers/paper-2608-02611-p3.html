一 · 单轮提示的边界：一次生成能承载多少信息

KernelBrain 的搜索起点不是脚手架，而是一条被刻意压窄的单轮提示通道。它把一次 kernel 生成拆成三段输入：算子语义（PyTorch 参考实现的签名与语义契约）、形状/ dtype/ 布局约束、以及一个可选的“上一次失败原因”摘要。输出是一段 Triton 源码文本，长度受 token 预算约束。这一步的代价几乎全部落在 token 上：提示里塞入完整参考实现、错误栈、profile 摘要，会迅速吃掉上下文窗口，而留给生成的空间越小，模型越倾向于退回模板化的 tile 配置。单轮提示的机制本质是“一次性条件采样”，它没有回退能力，因此正确性门在第一步就必须存在——否则后续所有预算都花在编译不通过的文本上。

这里的关键工程判断是：单轮提示不是用来产出最优 kernel 的，而是用来产出“可编译、可运行、语义等价”的种子。论文把低成本的筛选放在最前面，正是因为编译与一次正确性检查的单位成本远低于一次高保真 profile。用公式表达这一步的过滤效率：

$$\text{yield}_{\text{seed}}=\frac{N_{\text{compile}}\cdot N_{\text{pass}}}{N_{\text{sample}}},\qquad \text{cost}_{\text{seed}}=N_{\text{sample}}\cdot(c_{\text{tok}}+c_{\text{compile}}+c_{\text{run}})$$

其中 $c_{\text{tok}}$ 是生成 token 的时延成本，$c_{\text{compile}}$ 是 Triton 到 PTX/cubin 的编译时间，$c_{\text{run}}$ 是一次前向的显存与时间开销。具体例子：对一个归约类算子，若单轮提示只给出参考实现而不给形状，模型常写出假设 2 的幂长度的 kernel，编译通过但在奇数长度输入上越界——这类失败在正确性门上被廉价拦下，代价只是一次编译加一次运行，而不是一次完整的 NCU 采集。

二 · Agent 脚手架：把一次生成变成一条可回退的流水线

脚手架层把单轮提示包进一个循环：生成 → 编译 → 运行 → 评测 → 诊断 → 变异。每一轮的状态由候选池承载，池中每个条目至少带四元组（源码、编译状态、正确性判定、时延测量及其置信区间）。论文强调的“LLM-guided mutation”在这一层落地为：从池中挑选存活者，把它的源码、失败诊断或 profile 摘要拼成新的提示，再走一次单轮生成。变异不是随机扰动，而是有条件的方向性改写——诊断信息决定了改 tile 大小、改向量化宽度还是改归约树结构。

脚手架的代价是状态管理与调度开销：候选池越大，每轮的挑选与提示拼装越贵；而编译是串行瓶颈，Triton 编译一个中等复杂度 kernel 的时间在秒级，几十个候选就会把一轮搜索拖到分钟级。因此脚手架必须与预算分配耦合，否则“多生成几个试试”会直接吃光时间预算。伪代码思路如下：

  • 输入：参考实现、形状集合、总预算 $B$（以墙钟时间或 GPU 秒计）。
  • 初始化：单轮提示采样 $k_0$ 个种子，全部过编译门与正确性门。
  • 循环：对存活者按“低成本评测分数”排序，取前 $m$ 个进入高保真评测；其余仅保留源码与廉价分数。
  • 诊断：对高保真评测中未达标的候选，采集 profile 摘要回灌提示，生成下一代变异。
  • 终止：预算耗尽或连续若干代无存活者提升。

具体例子：一个矩阵乘类 kernel 在低精度下编译通过、正确性通过，但时延只与 PyTorch 持平；脚手架不会直接丢弃它，而是把它留在池中作为“基线存活者”，把高保真预算转给另一个 tile 更大、寄存器压力更高的变体。这里付出的代价是显存：大 tile 变体在编译期就可能因共享内存超限而失败，失败本身消耗编译时间但不消耗运行显存，属于廉价负样本。

三 · 预算感知：粗筛与高保真评测的分界怎么划

论文的核心机制是“低成本的筛很多、高保真的只给有希望的存活者”。这条分界线不是拍脑袋定的，而是由测量噪声与预算的比值决定。运行时测量有噪声，单次计时不足以区分 5% 的差异；要压噪声就得重复测量、取分位数或做配对比较，而重复次数直接乘以 GPU 秒。设单次测量方差为 $\sigma^2$，要分辨的相对差异为 $\delta$，所需重复次数近似为：

$$n\approx\frac{2\sigma^2}{\delta^2}\cdot z^2,\qquad \text{budget}_{\text{hi}}=n\cdot c_{\text{run}}+c_{\text{prof}}$$

粗筛阶段用单次或极少次测量加宽松阈值，只回答“是否值得再测”；高保真阶段才做重复测量与 profiler 采集。代价体现在两个方向：粗筛阈值太松，会把噪声当信号，让高保真预算被平庸候选吃掉；阈值太紧，则会误杀那些首次测量偏慢但结构上有潜力的变体。论文用“policy-gated evaluation”来表述这一层门控——不是所有候选都配得上 NCU。

具体例子：同一 kernel 连续两次计时相差 8%，粗筛若按单次结果排序，会把一个实际更快的变体排到后面；预算感知的做法是给存活者一次重测机会，只有重测后仍占优的才进入高保真队列。这一步的代价是时延：重测把粗筛阶段的墙钟时间拉长，但换来了高保真阶段候选质量的提升。论文声称优化时间最多降低 48%，这一数字对应的正是把高保真预算集中到少数存活者上所省下的 GPU 秒，而非生成环节的 token 节省。

四 · 策略门控与 verifier：正确性门和性能门是两道不同的闸

verifier 在 KernelBrain 里不是单一函数，而是两级闸门。第一级是正确性 oracle：在论文给定的输入分布上比对输出，容差按 dtype 设定；第二级是性能门：加速比 $s=T_{\text{base}}/T_{\text{agent}}$ 必须不小于 1 才被接受。论文给出的接受判据是：

$$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这个判据看似简单，工程上却有两个陷阱。其一是基线口径：若基线未开 TF32 或未用最强库实现，$T_{\text{base}}$ 被高估，$s$ 被系统性放大，离线分数好看但生产上崩塌。其二是 shape 特化：候选在给定形状上通过正确性与性能门，换一个隐藏输入分布就可能越界或退化。因此 verifier 的输入必须显式携带形状集合，输出必须区分“在该形状上通过”与“在形状集合上通过”。

策略门控的另一层含义是拒绝无意义的变异：当诊断显示候选的瓶颈在访存而非计算时，继续调 tile 大小是浪费预算，门控应把这类变异挡在生成之前。代价是 token：门控逻辑本身要写进提示或作为脚手架规则，规则越复杂，提示越长，单轮生成的可用上下文越少。具体例子：一个 softmax 类 kernel 首次测量显示带宽利用率已接近峰值，门控判定继续优化计算无收益，于是把预算转给另一个尚未被充分测量的候选，而不是在同一候选上反复变异。

五 · Profiler 诊断回灌：从 SASS/NCU 到下一次提示

“profiler-informed diagnosis”是这条流水线里信息密度最高的一步，也是最贵的一步。NCU 采集一次完整指标集的代价远高于一次计时：它需要重放 kernel、串行化采集、可能改变 occupancy。因此诊断只对高保真阶段的存活者做，且采集的指标集要按瓶颈假设裁剪——访存瓶颈看 DRAM throughput 与 L2 命中，计算瓶颈看 issue slot 与 pipe utilization，延迟瓶颈看 stall reason 分布。

诊断的输出不是原始计数器，而是一段可塞进提示的自然语言或结构化摘要，例如“共享内存 bank conflict 显著”“寄存器溢出导致 occupancy 下降”“全局访存未合并”。这段摘要进入下一轮变异的提示，构成闭环。代价有三项：采集时延、显存（重放需要保留输入输出缓冲）、以及提示 token（摘要越长，留给源码生成的空间越小）。具体例子：一个转置类 kernel 的 NCU 摘要显示写回未合并，脚手架据此把变异方向限定为“改变共享内存填充以消除 bank conflict”，而不是盲目调 block 大小；下一次生成因此有明确方向，单轮提示的命中率上升。

这里有一个容易被忽略的工程判断：profiler 摘要的可信度取决于采集时的时钟与功耗状态。若采集期间 GPU 降频，stall 分布会失真，回灌给模型的诊断就是错的，后续变异会朝错误方向收敛。因此诊断步骤必须与测量步骤共享同一套状态控制，否则“有反馈”反而比“无反馈”更糟。

六 · 一次完整流动的代价账本

把上述步骤串起来，一次 kernel 生成—编译—运行—评测的流动可以记成一张代价账本。每一步的输入、输出与主要成本如下表所示，表中不填具体数字，只标成本类型，因为论文摘要未展开各步骤的绝对开销。

这张账本解释了论文为何把“粗到细”作为组织原则：编译与正确性门是廉价且高淘汰率的闸，应放在最前；计时是中等成本但噪声大的环节，需要预算感知的重复策略；profiler 是最贵且信息最密的一环，只对少数存活者开放。论文报告的 0.88x–6.72x 对 PyTorch 的加速比与最高 1.4x 对现有 kernel agent 的加速比，是在这套预算分配下取得的；其中 0.88x 的存在说明并非所有任务都能赢过基线，接受判据 $s\ge 1$ 会把这些候选挡在最终输出之外，但它们在搜索过程中仍消耗了预算。

落到工程判断上：这条流水线的可靠性不取决于生成模型多强，而取决于三道闸的顺序与阈值是否与测量噪声匹配。正确性门若放在计时之后，噪声会污染淘汰决策；profiler 若对全部候选开放，预算会在第一轮就耗尽；变异若不带诊断，单轮提示的命中率会退化回随机采样。KernelBrain 的方法论价值在于把这些顺序与预算写成显式规则，而不是留给 agent 自行决定——这也是它能在 Triton kernel 生成任务上同时改善质量与搜索效率的机制来源。

预算闸门失效的三种边界与系统代价

这套方法的骨架是“低成本的粗筛 + 高保真的细评”，但真正决定成败的不是粗筛本身，而是门控策略：什么时候把一个候选从廉价通道提升到高保真通道，什么时候直接丢弃。论文把门控写成 policy-gated evaluation，本质是一个带预算约束的接受判定：

$$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1],\qquad s=\frac{T_{\text{base}}}{T_{\text{agent}}}$$
问题在于，粗筛阶段的 $T_{\text{agent}}$ 来自噪声较大的短时测量，而细评阶段的 $s$ 才是可信值。若粗筛的门槛设得偏松，大量注定失败的候选会消耗高保真预算，48% 的优化时间节省立刻被吃掉；若设得偏紧，真正有潜力的慢热候选在早期就被误杀，搜索提前停滞——这正是论文摘要里点名的 “search often stalls early”。这个权衡没有免费解：门控越保守，单位时间内的有效探索越少；门控越激进，单位候选的评测成本越高。工程上必须把门控阈值当作超参显式暴露，而不是藏在脚手架里。

第一个失效条件是正确性门与性能门的耦合顺序。若先测性能再验正确性，一个输出错误但跑得快的候选会拿到虚高的 $s$，进入细评后才发现 pass 为假，高保真预算被浪费在一次注定回退的评测上。反过来，若正确性检查本身很贵（大 shape、多 dtype、需要逐元素比对），粗筛阶段的成本结构就从“编译+短跑”变成“编译+全量比对”，粗筛失去廉价性。代价是显存的：正确性检查通常要同时驻留参考输出与候选输出，在长序列或大 batch 场景下，这份额外显存可能直接把候选挤下卡，让一次本可成功的编译运行变成 OOM 失败，被错误地计入“不可行”。

第二个失效条件是profiler 反馈的回灌延迟。profiler-informed diagnosis 的输入是 NCU/SASS 级指标，输出是下一轮变异的方向提示；但 profile 一次的开销远高于一次计时，且它给出的是“哪里慢”，不是“怎么改快”。当候选池很大时，只有幸存者才值得 profile，这意味着诊断信息天然滞后于搜索前沿：早期被丢弃的候选从未获得诊断，其失败原因不会被学习进变异策略。于是变异分布会向“已经能跑通的方向”收缩，探索多样性下降，搜索在局部最优附近反复打转。系统代价体现在 token 上：每一轮诊断提示都要占用上下文，多轮之后 prompt 膨胀，单次生成的边际成本上升，而有效信息密度下降。

第三个失效条件是基线口径与输入分布。0.88x–6.72x 的加速比是相对 PyTorch 基线测得的，若基线未开 TF32 或未使用最强库实现，这个区间会被系统性高估；而 shape 特化带来的收益在隐藏输入分布上极易崩塌——候选针对基准 shape 做了 tile 与展开，换一个 batch 或序列长度，occupancy 与访存模式同时劣化。这类失败不会在离线基准上暴露，只会在端到端回归里以“正确但更慢”的形式出现。因此部署前必须做跨 shape 的抽样回归，把 $s<1$ 的候选连同其特化假设一起回退，而不是只看基准上的最优值。
