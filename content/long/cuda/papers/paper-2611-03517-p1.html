一 · 现场：一条延迟预算被切碎的生产链路

设想一个在线推理服务，主干是 Transformer 解码，每步都要跑一次 attention。服务端的延迟预算被切成三段：请求排队、kernel 执行、结果回传。真正决定尾延迟的是中间那段——而这段里最贵的往往是 attention 的 fused kernel。工程团队手里有两条路：调库，或者自己写。调库意味着把 FlashAttention 的某个版本钉死在依赖里；自己写意味着有人要在 CUDA 里手推 online softmax 的分块递推、处理 head dim 不是 2 的幂、把 shared memory 的 bank conflict 压下去。两条路都不是“选一次就完事”，因为硬件在换代、shape 分布在漂移、框架版本在升级。

这就是这篇论文的现场。它不是从“LLM 能不能写 kernel”这个抽象问题出发的，而是从一个具体的工程僵局出发：一个已经存在的 CUDA kernel，能不能在没有算子专属知识、也没有更快的实现可以模仿的前提下，被做得更快。论文给出的答案实体叫 KernelSeek，一个 question-driven agent。要理解它为什么必须存在，得先看清它之前的两条主流路线各自卡在哪里。

先把评测口径摆出来，因为后面所有讨论都挂在它上面。论文沿用一套统一的任务—评测器—硬件—时间窗设定，加速比与接受判据写成：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这个式子里藏着两个门：正确性门 pass 与性能门 s≥1。任何一个候选只要有一项不过，就不算接受。注意它是“与”，不是“或”——这意味着一个跑得飞快但数值错的 kernel 和一个数值完美但比基线慢的 kernel 在账本上是同一类东西：废品。这个判据本身就是对旧方案的一记质问：手写路线长期在这两个门之间来回摇摆，而库调用路线干脆放弃了第二个门。

二 · 旧方案之一：手写 CUDA 的性能上限与开发周期

手写 CUDA 的痛点不是“写不出来”，而是“写出来之后不知道还差多少”。一个工程师把 attention 的前向写成单文件 CUDA，编译通过、数值对齐，然后开始调。调什么？register 压力、occupancy、shared memory 分块大小、warp 内 reduce 的 shuffle 模式、global memory 的 coalescing。每一项都对应一个可以测量的量，但把这些量映射到“下一行该改哪里”需要经验。经验的生产周期以周计。

更麻烦的是性能上限的判定。一个手写 kernel 跑出某个时延，工程师怎么知道这已经接近硬件极限？roofline 给了一个粗粒度答案：把算术强度与带宽/算力上限画在一张图上，看落在斜坡还是平台。但 roofline 只告诉你“理论上还能快多少”，不告诉你“这 30% 的差距具体藏在哪一段指令里”。要回答后者，得看 SASS、看 NCU 的 stall reason 分布、看 memory throughput 与 compute throughput 的比值。这些工具的输出是结构化但庞大的，人读一遍要几十分钟，而且读完之后往往还是不知道下一步动哪里。

正确性这一侧的代价同样实在。attention 的 online softmax 涉及 running max 与 running sum 的递推，分块边界处理错一位，结果就在长序列上缓慢漂移，短输入测不出来。工程上常见的做法是拿一批固定 shape 做回归，但生产流量的 shape 分布是长尾的。论文的评测口径里有一个具体数字可以说明这种覆盖有多难：它要求候选在每架构 182 个场景上全部正确。182 个场景意味着 dtype、head dim、序列长度、batch 组合的交叉，手写路线要为这个矩阵负责，靠人肉枚举是不现实的。

可维护性是最后一根稻草。一个为了某个 shape 特化过的 kernel，在下一版框架里可能因为 layout 变了而失效；一个用了 CUTLASS 模板的 kernel，在换硬件时要重新走一遍模板实例化的迷宫。论文明确把“无依赖”当成一个卖点：KernelSeek 产出的 FlashAttention 前向是单 CUDA 文件，不含 CUTLASS、CuTe、cuBLAS、cuDNN。这个约束不是洁癖，而是对可维护性代价的直接回应——依赖越少，换代时重新验证的面就越小。

三 · 旧方案之二：库调用与 Triton 的“够用即止”

库调用路线的逻辑是：把 kernel 的正确性和大部分性能外包给 cuBLAS/cuDNN/FlashAttention。这在多数场景下是理性的，但它有一个结构性缺陷——库针对的是“平均意义下的最优”，不是“你的 shape 分布下的最优”。当你的序列长度、head 数、batch 组合落在库的调优盲区里，你拿到的是一个正确但不满意的数。而你没有手段去改它，因为库是二进制。

Triton 处在一个中间位置。它把 block-level 的编程模型抬高了，写起来比 CUDA 快，自动处理一部分 layout 与向量化，代价是编译器对底层细节的掌控让渡给了 DSL。工程上的典型体验是：Triton 版本几十行就能跑对，但当你需要精确控制 shared memory 复用或者手写异步拷贝流水时，DSL 的表达力就成了天花板。这不是 Triton 的缺陷，是抽象层级的必然代价——你换来了开发速度，付出了对最后几个百分点的控制权。

把这两条路线放在论文的框架里看，它们其实共享同一个盲点：它们都不产生“关于差距的假设”。库调用不产生假设，因为它不让你改；Triton 让你改，但不告诉你改哪里值得。工程师于是陷入一种循环：改一版、测一版、看不出所以然、再改一版。这个循环的每一圈都要付出编译时间、GPU 占用、以及人的注意力。

论文对这两种旧方案的定性很直接：它们都“缺乏方向”——缺的是关于剩余差距在哪里的假设。这句话是整篇论文的支点，也是本部分要落下的判断：旧方案的问题不在于工具不够多，而在于工具不回答“下一步问什么”。

四 · 两条 agent 路线：结构—自由的 tradeoff

在 KernelSeek 之前，LLM agent 做 kernel 优化已经分化成两端，论文把它概括为 structure-freedom tradeoff。

一端是 scripted agent：用学到的策略、优化菜单或者固定角色，把模型在每一步做什么钉死。它的优点是 sample-efficient——在配方适用的地方，几步就能出结果，因为搜索空间被人工剪过了。代价是“配方不适用时就停摆”：菜单上没有的优化，agent 不会想到；固定角色分好的工，遇到跨阶段的耦合问题就卡住。这类方案的代表在别处已经展开，此处只指路：它们的共同结构是“把人的优化经验编码成步骤序列”。

另一端是 open-ended agent：让一个自导向的模型去变异一个 kernel 种群，用试验次数换自由度。论文对它的代价描述得很具体：成千上万次评测、反复编辑、以及大量错误候选。这不是修辞，是账本——每一次评测都要编译、要跑、要占 GPU；每一个错误候选都要被正确性门拦下。自由度是用 token 和 GPU 小时买的。

两端的共同反应更值得注意：面对硬目标，它们都选择“给 agent 装备更多”——解析过的 profiler 输出、反汇编分析、对文档与库的检索、经验教训的存储。这条路的逻辑是“信息越多，模型越聪明”。论文的反驳是：这些都不构成方向。更多的 profiler 字段不等于知道该看哪个字段；更多的检索结果不等于知道该问什么问题。装备是横向铺开的，方向是纵向的。

这里有一个可以用数字锚定的对照。论文报告，在相同任务、相同评测器、相同硬件、相同周内，一个按流行风格搭建的、工具丰富的自主 agent，在 133 个模型驱动的步骤之后停在 0.50x FlashAttention-3；而 KernelSeek 达到 1.13x。0.50x 意味着它不仅没超过基线，还慢了一倍——133 步的评测预算被花在了没有方向的变异上。这个对照不是要证明“工具无用”，而是要证明“工具多不等于方向对”。

五 · 为什么非改不可：三个代价的叠加

把旧方案的代价拆成三本账，可以看到它们为什么会在同一个项目里叠加。

开发周期账。手写路线的周期以人周计，agent 路线的周期以评测次数计。open-ended agent 的“成千上万次评测”听起来是自动化的胜利，但每一次评测都有编译时间与 GPU 占用。一个 kernel 编译几十秒、跑一遍几秒，一千次评测就是数小时的墙钟时间，还不算错误候选浪费掉的那部分。scripted agent 省评测，但省下来的是“配方内”的评测，配方外的探索直接归零。

性能上限账。库调用把上限锁在库的调优范围内；Triton 把上限锁在 DSL 的表达力内；手写 CUDA 的上限取决于工程师读 profile 的能力。三条路的上限都不是硬件的上限，而是“人/工具能看见多少”的上限。论文的 1.13x 与 1.16x 之所以有意义，是因为它们是在“没有更快实现可模仿”的条件下拿到的——上限是被假设驱动的搜索推上去的，不是被模仿推上去的。

正确性账。182 个场景的全覆盖要求，把“跑通一个 shape”和“可信”之间的距离量化了。手写路线靠人肉回归覆盖不了这个矩阵；agent 路线靠正确性门自动拦截，但门本身要设计得够严，否则 reward hacking 会让正确率虚高——这是论文在局限里点明的失败模式之一，也是所有 agent 方案共享的风险。一个只在固定输入上 pass 的候选，在隐藏输入分布上会崩，而离线分数看不出来。

三本账叠加的结论是：旧方案不是“不够好”，是“不可持续”。每一代硬件、每一次 shape 分布漂移，都要把这三本账重算一遍。这就是论文要回答的问题的工程根源——不是“能不能让 LLM 写 kernel”，而是“能不能让 kernel 优化的每一步都有方向，从而把评测预算花在刀刃上”。

六 · 一个具体的失败切片：133 步换来的 0.50x

把 0.50x 这个数字拆开看，能看清旧 agent 路线的失败机制。一个工具丰富的自主 agent，手里有 profiler 解析、有反汇编、有文档检索，理论上信息完备。它跑了 133 步，每一步都是一次“看反馈—改代码—再评测”的循环。结果停在 0.50x。

这个结果的解释不在“模型不够强”，而在“循环没有收敛方向”。133 步里，agent 大概率反复在几个局部改动之间震荡：调 block size、调 unroll、换一种 reduce 写法。每一次改动都有反馈，但反馈是标量——快了还是慢了——而不是“差距在哪”。没有假设，就没有“这个改动验证了哪个猜想”的记录，于是下一步的改动与前一步的改动之间没有累积关系。133 步是 133 个独立的试错，不是 133 次递进的逼近。

对照 KernelSeek 的 1.13x，差别不在步数多少，而在每一步是否携带一个关于“剩余差距在哪里”的假设。论文的核心主张正是这一句：两端都缺方向，而在正确的时刻问一个短问题就能提供方向，且不缩小 agent 下一步可以做什么。这句话的后半段是关键——“不缩小自由度”。它不是用菜单剪搜索空间，而是用一个问题把搜索空间照亮。这与 scripted agent 的“钉死步骤”是两种完全不同的约束方式：前者约束的是注意力，后者约束的是动作。

从工程判断上落一句：如果一个 agent 的评测预算是一千次，那么它真正稀缺的资源不是 GPU 时间，是“这一千次评测各自在验证什么”的可解释性。旧方案给不出这个可解释性，所以一千次评测退化成一千次抽样。KernelSeek 的切入点就是把这个可解释性补上——用问题，而不是用装备。

当“装备齐全”也救不了：工具富集型 agent 的失效边界

在一个线上推理服务里，attention 前向的时延被一个第三方库实现钉死：换 dtype、换 head_dim、换 batch 组合都会让库里的启发式选到次优 tile，工程师只能手写特化 kernel 或退回 PyTorch eager。这正是论文要处理的现场——不是“没有工具”，而是工具已经堆到极限。论文把既有做法归为两端：scripted agent 用学习策略、优化菜单或固定角色锁死每一步，配方适用处样本高效，一旦目标超出配方就停摆；open-ended agent 让模型自导变异 kernel 种群，用成千上万次评测、反复编辑和错误候选来支付自由度。两者的共同反应都是“给 agent 更多装备”：解析后的 profiler 输出、反汇编分析、文档与库检索、经验教训库。问题在于，装备增加并不改变搜索的方向性。

失效条件是结构性的。工具富集把每一步的上下文预算推高，profile 解析与反汇编回灌意味着每轮都要重新读入大段结构化文本，token 成本随步数线性叠加；open-ended 一侧则把代价压在评测侧，候选种群意味着编译与运行次数成倍增长，单次编译加正确性门加计时构成一个不可压缩的时延单元。更关键的是判定口径：$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$ 这个门只看“过没过 1x”，不看“离 roofline 还差多少、差在带宽还是占用率”。于是 agent 可以在一个已经接近 SOL 的 kernel 上反复微调拿到 1.02x 并宣告成功，也可以在一个远离 SOL 的 kernel 上卡在 0.9x 却不知道该动哪里——装备告诉它“现在多快”，没告诉它“剩下的差距在哪、下一步该问什么”。

系统代价可以直接对照。论文给出的同任务、同评测器、同硬件、同一周对照中，一个按主流风格搭建的工具富集自主 agent 在 133 个模型驱动步之后停在 0.50x FlashAttention-3；KernelSeek 达到 1.13x。前者并非缺工具，而是把 133 步花在了没有假设的试错上——每一步都重新解析 profile、重新检索、重新编辑，却没有一个“剩余差距在哪”的判断来裁剪动作空间。这就是本片段要强调的边界：装备解决的是“能不能看到信息”，方向解决的是“看完之后改什么”，而后者恰恰是工具富集无法用增加工具来弥补的；至于方向如何由一次短问题供给，属于后续小节的主题。
