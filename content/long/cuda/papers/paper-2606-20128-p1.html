一 · 一个上线前夜的推理服务：kernel 正确但服务不可信

设想一个典型的推理服务交付现场。模型结构已经冻结，端到端时延预算被切成三段：调度、数据搬运、算子计算。最后一段里有一个自定义融合算子——LayerNorm 加残差再加一次逐元素缩放，形状随 batch 变化，dtype 在 fp16 与 bf16 之间按请求切换。团队里没人愿意手写它：手写 CUDA 要处理向量化宽度、warp 内归约、shared memory 的 bank 冲突，还要为每一种 batch 边界写一个特化版本；用 Triton 写则要自己决定 block size、num_warps、累加精度，并在 autotune 的配置空间里做取舍；直接调库最省事，但融合本身就没有现成的库函数，拆成三个 kernel 意味着三次 global memory 往返。于是团队把这段交给一个 LLM agent，agent 在半天内产出了一个 Triton kernel，在离线基准上跑通了，加速比看起来可观，正确性检查也过了。

问题出在“过了”这两个字上。离线检查用的是基准里给定的那一个固定 shape、固定 dtype、固定容差，输入样本数在基准之间还各不相同。上线之后，请求的 shape 落在特化分支没有覆盖的尾部区间，dtype 切到 bf16，容差口径也随之改变。kernel 没有崩溃，它只是安静地算错了几个元素——而 allclose 式的检查在离线阶段从未见过这些输入。这就是这篇论文命名的“正确性幻觉”：评测口径给出的通过判定，与生产环境中的真实正确性之间，存在一条由固定 shape、固定 dtype、固定容差和少量样本共同挖出的沟。本部分要处理的不是这条沟怎么填，而是这条沟为什么在 2026 年之前一直存在——即 LLM 介入之前，GPU kernel 工程的主流做法是什么，它们的痛点如何累积到非改不可的地步。

二 · 三条旧路径的工程账本：手写 CUDA、Triton、库调用

旧方案不是一条路，而是三条代价结构完全不同的路。把它们的账本摊开，才能看清 LLM agent 被引入的真实动机：不是因为人写不出 kernel，而是因为三条路在“开发周期 × 性能上限 × 正确性 × 可维护性”这个四维空间里各自都有一个无法回避的短板。

手写 CUDA 的上限最高。工程师可以直接控制寄存器分配、用 __shfl_down_sync 做 warp 归约、用 cp.async 做流水、用 PTX 内联指令压榨指令级并行。但它的开发周期以人周计：一个融合算子从设计到通过数值验证，通常要经历“朴素版 → 分块版 → 向量化版 → 特化版”四轮迭代，每一轮都要重新做正确性验证。更贵的是可维护性：当模型结构改动、dtype 组合增加、目标 GPU 从 A100 换到 H100 时，手写 kernel 的特化假设（比如固定的 shared memory 容量、固定的 SM 数量假设）会逐条失效，维护成本随时间线性上升而非摊销。

Triton 把开发周期压下来了。工程师用 block 级抽象描述计算，编译器负责线程映射与内存合并，autotune 负责配置搜索。代价转移到了两个地方：其一是性能上限——Triton 的表达能力覆盖不了某些需要精细控制 shared memory 布局或异步流水深度的场景，生成的代码在访存密集型算子上常与手写版本有差距；其二是正确性口径的隐蔽性——Triton 的 tl.dot 在 fp16 输入下默认走 TF32 或 fp32 累加，累加精度的选择直接影响数值结果，而这个选择往往不在工程师的显式控制之下。一个在 fp32 累加下通过 allclose 的 kernel，切到 TF32 就可能越过容差边界。

库调用（cuBLAS、cuDNN、CUTLASS 实例）的开发周期最短，正确性由厂商背书，性能在标准形状上通常接近硬件上限。它的短板是覆盖面和形状敏感性：融合模式一旦偏离库的预设（比如上面那个 LayerNorm+残差+缩放的组合），就只能拆成多次库调用，每次调用之间的 global memory 往返把带宽吃掉；而在非标准 shape 上，库的启发式选择未必是最优的，工程师又无法介入。

路径开发周期性能上限正确性来源可维护性
手写 CUDA人周级，多轮迭代最高，可控制到指令级自建数值验证，责任在作者特化假设随硬件/模型漂移而失效
Triton人天级中高，受抽象层限制编译器语义 + 自建验证，累加精度隐式较好，但 autotune 配置与硬件绑定
库调用小时级标准形状接近上限，非标准形状退化厂商背书最好，但融合能力缺失

这张表的读法是：没有任何一条路径同时在前三列拿到高分。工程团队实际做的是按算子重要性做分配——核心热点算子手写，边缘算子调库，中间地带用 Triton 兜底。这种分配本身就是一种妥协的产物，而 LLM agent 的引入，本质上是要把这个分配问题从“人力预算约束下的手工调度”变成“可自动搜索的候选生成与验证问题”。

三 · 正确性为什么在旧方案里就已经是薄弱环节

值得强调的是：正确性幻觉不是 LLM 带来的新病，旧方案里它已经潜伏着，只是被人的经验掩盖了。手写 CUDA 的工程师知道自己在 fp16 归约时要提升累加精度，知道边界线程的 mask 要写对，这些知识以隐性形式存在于人身上；一旦这个人离开，知识就丢失。Triton 把一部分知识固化进编译器，但把另一部分（累加精度、容差选择）留给了调用者。库调用则把知识完全外包，代价是工程师失去了对数值路径的可见性。

真正的问题在于验证环节的口径。旧方案的验证通常是“拿几个代表性输入跑一遍 allclose”。这个做法在工程上合理，但它隐含了一个未经检验的假设：代表性输入覆盖了数值风险的分布。对于手写 kernel，工程师凭经验挑选输入，覆盖度取决于个人判断；对于 Triton kernel，autotune 会在多个配置上跑，但正确性检查往往只在最终选中的配置上做一次；对于库调用，验证几乎被跳过，因为“厂商的东西不会错”。

论文的做法正是把这个假设拿出来做实证检验。它构造了一个受控语料：24 个 Triton 与 CPU 替身 kernel，其中 15 个是正确对照，9 个是注入了有据可查的转录错误的 LLM 风格缺陷变体。然后用算子 schema 感知的种子化模糊测试，配 fp64 的 CPU 参考实现和按 (op, dtype) 分别设定的绝对容差，重新评测这批 kernel。结论是：种子化 oracle 标记出全部 9 个缺陷 kernel，同时让全部 15 个正确对照通过，在对照上没有精度损失。这个结果的含义不是“模糊测试好用”，而是“固定 shape、固定 dtype、固定容差、少量样本的旧口径，在原理上就无法区分正确与缺陷”——因为缺陷恰恰藏在口径没有覆盖的输入维度上。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个打分公式是旧基准的典型形态：N 个样本上的加速比超过阈值 τ 的比例。它的结构性问题一目了然——正确性被压缩成一个前置的布尔门，而门本身的判定依赖固定的输入集合；一旦门通过，后续所有优化压力都作用在 s_i 上，没有任何机制去惩罚“只在给定输入上正确”的候选。这就是 reward hacking 的结构性温床：候选 kernel 可以通过特化到基准 shape 来抬高 s_i，而正确性门对此无感。

四 · 可维护性与性能上限的耦合：为什么“够用”会失效

旧方案还有一个更隐蔽的痛点：可维护性与性能上限不是独立的两个维度，它们在特化这件事上耦合。手写 kernel 的性能来自特化——为特定 shape、特定 dtype、特定 GPU 写死分支。特化越深，性能越高，可维护性越差。Triton 的 autotune 试图用配置搜索替代人工特化，但搜索出的最优配置同样绑定在评测时的硬件与形状分布上；换一个 GPU 类，最优配置可能完全不同，而重新搜索需要时间，且搜索结果的可信度又回到那个老问题：在哪些输入上验证过？

论文把这个问题推到了跨硬件维度上做检验。它把语料扩展到 26 个算子（新增一对 flash-attention），在五类 GPU 上重跑同一套协议：RTX 3060、A10、L40S、A100 SXM4、H100 NVL。判定结果在五类 GPU 上完全一致：10 个幻觉全部被抓出，16 个对照全部干净。这个跨硬件一致性的意义在于，它说明正确性缺陷的检出不应依赖特定硬件的数值行为——一个在 A100 上因容差宽松而通过的缺陷 kernel，在 H100 上不会因为硬件更好就变成正确的。反过来，这也暴露了旧方案的一个假设错误：团队常以为“换个更强的卡，数值问题会缓解”，但容差口径不随硬件调整，缺陷的可见性也就不随硬件改善。

代价在这里体现为编译时间与验证时延。种子化模糊测试要为每个 (op, dtype) 组合生成多组输入，每组都要在 fp64 CPU 参考上算出基准值，再与 GPU 候选比对。这个流程的时延远高于“跑一个固定 shape 的 allclose”：CPU 参考实现本身是串行或低并行的，fp64 在消费级 GPU 上又被大幅削弱，所以参考计算必须落在 CPU 上。对于一个 flash-attention 算子，fp64 CPU 参考的耗时可能把单次验证从秒级推到分钟级。这就是旧方案不愿做严格验证的经济原因——不是不知道该怎么验，而是验证成本相对于开发成本太高，在人力预算下被理性地省略了。

五 · 非改不可的工程判断：三个不可逆的趋势

把旧方案的痛点归拢，可以看到三个不可逆的趋势，它们共同构成了“非改不可”的判断依据，而不是一句“LLM 很火所以要用”。

第一，算子融合的需求在增长，而库的覆盖面在相对收缩。模型结构越来越偏向自定义融合（归一化 + 残差 + 激活 + 缩放），库函数按单算子设计，融合只能靠手写或 Triton。这意味着旧方案里“调库兜底”的那条路在热点算子上越来越不可用，人力必须投入到手写或 Triton，开发周期压力上升。

第二，硬件与 dtype 组合在爆炸。五类 GPU、多种 dtype、多种容差口径的组合，使得“一次特化、长期使用”的假设失效。手写 kernel 的特化维护成本随组合数增长，而 Triton 的 autotune 配置空间同样随组合数增长。旧方案没有自动化的候选生成与验证闭环，组合爆炸直接转化为人力的线性投入。

第三，也是最关键的：正确性的判定口径本身成了瓶颈。当候选来源从“少数工程师的手写”变成“大量自动生成的候选”时，固定 shape、少量样本的 allclose 检查在统计上就不再够用——候选数量越多，越有可能出现恰好通过固定输入集合、但在其他输入上失效的样本。论文的 9 个缺陷变体正是这类样本的受控复现：它们不是随机噪声，而是有据可查的转录错误，恰恰是 LLM 生成 kernel 时最典型的失败形态（索引偏移、mask 边界写反、累加精度降级）。旧口径对这类缺陷的漏检不是偶然，是结构性的。

这三个趋势叠加，使得旧方案的账本从“可接受的妥协”变成“不可接受的负债”。工程判断因此不是“要不要引入 LLM”，而是“引入 LLM 之后，验证口径必须同步升级，否则自动生成的候选只会把正确性幻觉规模化”。论文的贡献正在于把这个判断做成可复现的实证：用受控语料证明旧口径漏检、新口径不漏检，并把结论推到跨硬件一致性上。

六 · 旧方案留下的接口：候选生成与验证必须解耦

从工程结构上看，旧方案留下的最重要的遗产不是某段代码，而是一个接口划分：候选生成（谁写出 kernel）与候选验证（怎么判定它正确且快）必须解耦。手写 CUDA 把两者绑在同一个工程师身上，验证质量取决于个人经验；Triton 把生成交给编译器、验证留给调用者，接口模糊；库调用把两者都外包，接口消失。LLM agent 的引入之所以可能，恰恰是因为它天然适合这个解耦——生成端可以是一个概率模型，验证端必须是一个确定性的、口径可审计的 oracle。

论文的种子化 oracle 就是这个验证端的具体形态：算子 schema 感知的输入生成、fp64 CPU 参考、按 (op, dtype) 的绝对容差。它的代价是验证时延与 CPU 参考的计算开销，收益是把正确性判定从“在给定输入上通过”变成“在 schema 覆盖的输入空间上通过”。这个转换的工程含义是：验证不再是一个前置布尔门，而是一个可以独立演进、独立审计的组件。当候选生成端从手写换到 Triton 换到 LLM agent 时，验证端不需要重写——这正是旧方案从未提供、而后续所有 agent 框架都默认依赖的接口。

落到具体机制上：一个融合算子的 schema 包含输入张量的秩、每个维度的取值范围、dtype 集合、以及该 dtype 下的绝对容差。种子化模糊测试按 schema 采样输入，fp64 CPU 参考按同一 schema 计算期望值，候选 kernel 的输出与之逐元素比对。这个流程对单个候选的验证成本是 CPU 参考的耗时乘以采样组数，对批量候选则是线性叠加——这就是为什么验证必须与生成解耦：生成端可以并行产出大量候选，验证端按自己的吞吐节奏筛选，两者的成本结构不同，绑在一起就会互相拖累。旧方案把两者绑在人身上，人成了瓶颈；新方案把两者拆开，瓶颈转移到验证吞吐上，而验证吞吐是可以通过工程手段（参考实现的向量化、采样策略的剪枝）优化的。这个瓶颈转移本身，就是这篇论文所处理的“正确性幻觉”问题的工程起点。
