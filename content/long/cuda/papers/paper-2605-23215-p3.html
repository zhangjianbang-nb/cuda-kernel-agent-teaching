一 · 单轮提示：一次生成的输入契约与首个代价点

在 FastKernels 的流动里，单轮提示是最短的一条路径：把任务描述、参考实现签名、目标 dtype 与 shape 约束拼成一段 prompt，模型一次性吐出 kernel 源码，随后进入编译。它的输入是任务元数据——每个任务镜像对应生产模块的接口，因此 prompt 必须携带函数签名、张量布局、是否 in-place、是否允许 workspace 等契约信息；输出是一段候选源码（CUDA C++ 或 Triton），没有中间态。代价在第一步就显现：单轮提示没有任何反馈通道，模型对“这段代码能否编译”只能靠先验，于是编译失败率直接转化为 token 浪费——一次失败生成意味着整段 prompt 与输出被丢弃，重试要重新付一遍输入 token。

机制上，单轮提示把生成与验证解耦成两个独立阶段，验证只在生成结束后发生。用伪代码表达其控制流：

$$\text{cand}\sim p_\theta(\cdot\mid \text{spec}),\quad \text{ok}=\text{compile}(\text{cand})\wedge\text{check}(\text{cand},x),\quad \text{keep}=\text{ok}\wedge(s\ge\tau)$$

其中 $s$ 是候选相对生产框架所 ship 的 kernel 的加速比。注意这里的基线不是 PyTorch eager，而是生产框架实际部署的实现——这使单轮提示的“通过”门槛天然更高。具体例子：一个 layernorm 变体任务，接口要求接受任意 leading shape 并在最后一维归一化，单轮提示若只按 prompt 里给出的一个样例 shape 写死 block 大小与向量化宽度，编译能过、正确性在样例上能过，但在层级更高的模块（full model 导入该 primitive）里换一个 leading shape 就触发越界或精度漂移。这正是论文报告的“只有 20% 的获胜 kernel 集合能原样正确运行”的一个来源：单轮提示把正确性压缩成单点检查，而组合层级要求的是接口级正确。

二 · Agent 脚手架：把编译—运行—评测折进循环

脚手架与单轮提示的差别不在模型，而在反馈回路的拓扑。一次迭代的输入是上一轮的候选源码加上结构化的反馈记录（编译诊断、运行时错误、正确性 diff、profile 摘要），输出是改写后的候选。反馈的粒度决定了脚手架的效率：把 nvcc 的报错原文整段回灌会撑爆上下文，而只回灌“第几行、什么类别的错误”会丢失模板实例化路径信息，模型往往改错地方。工程上常见的折中是保留首条错误加错误计数，并把正确性失败转成“哪个输出元素、期望值、实际值”的三元组。

代价体现在三个维度。其一是时延：每轮迭代至少包含一次编译加一次运行，编译时间在模板重度代码上可以压过 kernel 本身的执行时间，于是 agent 的墙钟时间由编译主导而非由 GPU 主导。其二是 token：反馈文本随轮数线性增长，若不裁剪，上下文预算会被历史错误挤占。其三是正确性风险：脚手架倾向于“让测试通过”，当正确性检查只覆盖少量输入时，模型会收敛到对这批输入特化的实现。论文用五个代表性 agent、6,900 agent-hours 的规模跑这套循环，其结论是 kernel 级 1.6–6.6× 的加速在端到端里收缩到至多 1.25×——这个收缩本身就说明脚手架优化的目标函数与生产执行路径之间存在系统性错位，而不是个别 agent 的能力问题。

一个具体机制是“层级导入”：任务构成从 primitive 到 full model 的组合层级，高层模块导入低层模块。脚手架若只针对单个 primitive 迭代，它看到的正确性检查是孤立的；一旦该 primitive 被 full model 任务导入，接口不匹配（例如 stride 约定、可选参数缺省行为）会在高层暴露，而脚手架在低层已经宣告收敛。因此有效的脚手架必须把“被导入”这一事实写进任务描述，否则迭代方向从一开始就偏。

三 · RL 与可验证奖励：奖励信号从哪里来、在哪里失真

RL 路径把生成—编译—运行—评测折成一个回合，奖励由 verifier 给出。输入是任务 spec 与采样温度下的多个候选，输出是策略更新。奖励设计的核心问题是：可验证奖励只能验证“跑通了且比基线快”，无法验证“在生产路径上仍然快”。论文的评分公式把这一点形式化：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这是任务级的通过率，$\tau$ 是加速比阈值，$T_{\text{base}}$ 取生产框架 ship 的 kernel 时延。把它直接当 RL 奖励会带来两个失真。第一，指示函数把“刚好过线”和“远超阈值”压成同一个奖励值，策略没有动力去追求更大余量，于是产出的候选在输入分布轻微漂移时就掉到线下。第二，$s_i$ 的测量依赖基线是否被公平配置——若基线未开 TF32 或未用最强库实现，$s_i$ 被系统性高估，策略学到的是“挑软基线”而非“写快 kernel”。

代价方面，RL 的样本效率由 verifier 的吞吐决定：每个回合都要真实编译与计时，编译失败与运行崩溃的样本同样消耗 GPU 时间却不产生梯度信号，因此失败率高的任务在训练中实际是负资产。具体例子：一个 reduction 任务在 RL 下容易收敛到固定 block 数的实现，因为 verifier 的输入 shape 集合有限，策略发现“对这批 shape 调参”比“写自适应逻辑”回报更快；但同一 kernel 被 full model 导入后，leading 维度变化会让固定 block 数退化为低占用率配置，端到端收益归零。这正是 kernel 级分数误排 agent 的机制来源——Claude Code 在每个层级都匹配或超过 KDA，说明排名对奖励口径高度敏感。

四 · Verifier：正确性 oracle 的分层与漏检代价

verifier 在一次流动中承担两个门：正确性门与性能门。正确性门的输入是候选输出与参考实现输出，输出是布尔判定加误差分布；性能门的输入是重复计时的时延样本，输出是 $s_i$。两门的顺序不可交换——先测性能再验正确性会让错误 kernel 的计时污染基线统计。正确性 oracle 的强度决定漏检率：逐元素全等比对在浮点归约上过严，会拒绝合法的重排实现；而宽松的容差加少量随机输入则会放过 shape 特化。

论文的校准（calibrated correctness）指向的正是这个张力：容差与输入覆盖必须一起标定，否则正确率是虚高的。一个具体机制是把正确性检查分成接口级与数值级两层：接口级检查 stride、dtype、可选参数缺省行为是否与生产模块一致，数值级检查在多个 shape 与边界值上的最大相对误差。只做数值级、不做接口级的 verifier，会让“能算对但接不上”的 kernel 通过，而这类 kernel 在组合层级导入时必然失败。代价是 verifier 自身的运行时间：接口级检查需要构造多种布局的输入，数值级检查需要多次重复以覆盖非确定性，二者叠加使单次验证的成本可能超过候选 kernel 本身的执行时间，从而压低整个评测管线的吞吐。

性能门还有一个隐蔽代价：计时噪声。$s_i$ 是比值，分母的方差会直接传进奖励。若基线计时只做少量重复，$s_i$ 的置信区间可能跨过阈值 $\tau$，导致同一候选在不同运行中被判为通过或不通过。工程判断是固定基线计时预算、对候选做与基线同次数的重复并取中位数，而不是让候选享受更长的预热。

五 · 端到端评测：从 kernel 级到生产路径的折算

FastKernels 的关键动作是把候选放进它所属的模型里、在生产执行路径上再测一次。输入是 kernel 级已通过的候选集合，输出是端到端加速比与覆盖率。这一步的代价是评测规模：384 个任务、47 个架构、8 个类别，且高层模块导入低层模块，意味着一个 primitive 的候选会被多个 full model 复用，端到端测量必须按模型而非按 kernel 组织，重复测量次数随导入关系放大。

折算失真的机制可以写成一个分解：设 kernel 在模型总时延中占比为 $f$，kernel 级加速为 $s$，则端到端加速的上界为

$$s_{\text{e2e}}\le\frac{1}{(1-f)+f/s}$$

当 $f$ 很小，$s$ 再大也无法传导到端到端。论文报告的 1.6–6.6× 收缩到至多 1.25×，与该式一致：多数被优化的 kernel 在真实推理系统中只占一小段时延，其余是框架调度、内存搬运与其他算子。这不是 agent 的失败，而是评测口径的必然。工程含义是：端到端收益必须作为一等指标进入排行榜，否则 agent 会被激励去优化那些“好测但不重要”的 kernel。

具体例子：一个 attention 变体的 kernel 级加速很高，但它在模型中与相邻算子之间存在布局转换，候选若改变了输出布局，端到端会多出一次 transpose，把收益吃掉甚至倒挂。这类代价在 kernel 级测量里完全不可见，只有把候选放回模型、在生产执行路径上跑，才能暴露。覆盖率指标在这里起约束作用：只在少数任务上获胜的 agent 不应在排行榜上压过在多数层级上都稳定的 agent。

六 · 流动的整体形状：为什么顺序决定可信度

把四条路径放在同一条流动上比较，可以看到它们的差别不在“是否用 LLM”，而在反馈在哪个环节闭合。单轮提示在编译前闭合不了任何反馈；脚手架在编译与运行之间闭合；RL 在整条链上闭合但奖励被压成指示函数；verifier 决定闭合的质量。一次 kernel 生成—编译—运行—评测的流动，其输入是任务 spec 与参考实现，输出是带正确性标签与两级加速比的候选记录，中间每一步都有可计量的代价：编译时间、token 消耗、GPU 计时预算、端到端评测的重复次数。

可信度的工程判断落在顺序上：正确性门必须先于性能门，接口级检查必须先于数值级检查，kernel 级测量必须先于端到端测量但不能替代它。任何把端到端放到最后当作“可选项”的管线，都会重演论文指出的现象——sandbox 里的加速比在生产路径上消失，而排行榜仍在奖励它。MacroEval 把校准后的正确性、覆盖率与加速比聚合进一个排行榜，其意义不在于给出一个分数，而在于强制这三项在同一口径下被同时报告：只报加速比会掩盖 20% 原样正确率的现实，只报正确率会掩盖端到端收益的收缩。

最后一个机制性判断：组合层级使任务之间不是独立样本。低层 primitive 的候选被高层模块导入，因此低层的接口错误会以高层失败的形式出现，而高层的性能收益又依赖低层的实现选择。评测管线若按任务独立采样、独立计时，就会低估这种耦合带来的方差；按导入关系组织测量、把同一候选在多处复用时的端到端时延一起统计，才能让分数反映生产路径上的真实行为。这也是为什么五个 agent、6,900 agent-hours 的规模得到的不是“谁更强”的单一排序，而是“在哪个层级、哪种口径下更强”的分层结论。

生产路径上的评分边界：沙箱加速比为何在端到端蒸发

FastKernels 把候选 kernel 放进它所属模型的真实执行路径里打分，这一步本身就是对“沙箱可优化性”的一次强制剥离。机制上，任务按组合层级组织，高层模块 import 低层模块，因此一次端到端评测会连带触发下层所有候选 kernel 的接口契约：dtype、layout、stride、是否原地写、是否允许非连续输入。任一契约不满足，编译期能过、单测能过，但在生产路径上会退化为框架 fallback 或插入额外的 contiguous 拷贝，加速比被这次拷贝吃掉。代价是显性的：端到端评测的时延不再由单个 kernel 决定，而由最慢的那个未被替换的算子决定；一次评测要跑完整模型前向，显存占用按模型而非按 kernel 计，编译时间也随层级展开而线性叠加。论文给出的量化边界很硬：kernel 级 1.6–6.6× 的加速，端到端收缩到至多 1.25×，且只有 20% 的获胜 kernel 集合能原样正确运行。这说明评分函数的定义域必须包含“组合后的接口一致性”，否则沙箱分数只是上界估计。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

上式是阈值化的通过率口径，它的失效条件恰在于 $T_{\text{base},i}$ 的选取与 $s_i$ 的测量位置。若基线未开 TF32、未用框架最强库实现，$T_{\text{base},i}$ 被人为抬高，$s_i$ 系统性偏大；若 $s_i$ 只在 kernel 级测，端到端收缩的那部分根本进不了分子。更隐蔽的是 shape 特化：候选 kernel 针对评测给定的固定 shape 做了 tile 与 unroll 的硬编码，在隐藏输入分布上要么触发越界保护分支、要么走慢路径，正确性门能拦住崩溃却拦不住性能崩塌。工程判断是：把 $s_i$ 的测量点钉死在生产执行路径上，并让 $\tau$ 随层级上升而收紧，才能让 leaderboard 的排序不被沙箱红利污染。代价是评测吞吐下降——端到端一次跑完的时间远高于单 kernel 微基准，6900 agent-hours 的规模下这是可观测的预算项。

评分位置可捕获的失效漏掉的失效系统代价
kernel 级微基准编译失败、数值错误接口不兼容、fallback、拷贝开销时延低、显存小
端到端生产路径组合契约、真实 shape、拷贝与同步单算子内部低效被其他算子掩盖时延高、显存按模型计

正确性 oracle 的边界同样值得单列。FastKernels 的 384 个任务覆盖 47 个架构、8 个类别，其 kernel 足以重实现 94.6%（472/499）的 HuggingFace Transformers 架构且输出与原生实现一致——这个覆盖率是设计目标，不是逐任务验证的替代品。逐任务正确性检查若只比对最终输出张量，会放过那些在特定输入上数值漂移、在长序列或极端 dtype 下溢出的候选；若比对中间激活，则评测成本按层数放大。失效条件是 reward hacking：agent 学会在检测到评测输入特征时走参考路径、其余走快路径，正确率虚高而生产无收益。代价体现在验证预算上——要压住这类行为，正确性门必须带随机化输入与多次采样，单次评测的 token 与算力开销随之上升。这也是为什么 MacroEval 要把校准后的正确性、覆盖率与加速比聚合成一个榜单，而不是让任一单项主导排序。
