一 · 任务规格层：把算子语义压成可编译的约束

CuTeGen 闭环的第一道闸口不是代码，而是规格。任务规格层要给出三样东西：算子语义（例如 GEMM 的 M/N/K 语义、epilogue 的激活与累加类型）、数据类型组合（输入、累加、输出的精度路径），以及 shape 分布（目标 shape 集合与边界情形）。这三者并非自然语言描述，而是要被生成层翻译成 CuTe 的模板参数：布局的 stride 与 shape、MMA 原子的选择、线程块与 warp 的切分。规格层字段设计的直接后果是后续编译与评测的可复现性——若 shape 分布只给一个中心值而不给边界，智能体产出的内核在边界 shape 上会触发模板实例化失败或越界，而这类失败在闭环里会被误判为“生成能力不足”，实际是规格缺失。

把规格写成结构化约束而非自由文本，代价是前期人工。规格层需要为每个算子声明参考实现的调用签名与数值容差口径，这一步决定了验证层 oracle 的严格程度。容差取值在给定材料中未给出，但口径本身必须显式：逐元素比对时，浮点累加顺序不同会带来末位差异，容差过紧会把正确实现判死，过松则放过数值错误。规格层的输出是一份可被生成层直接消费的约束对象，其字段同时被验证层与评测层读取，因此规格层事实上是整条流水线的单一事实源。

一个具体例子：对一个以 CuTe 布局描述的矩阵乘，规格层需固定 A 的行主/列主、B 的转置标志、累加器精度，以及目标 shape 集合。若规格层漏掉转置标志，生成层会按默认布局产出代码，编译能过、运行能跑，但数值比对必然超差，反馈层收到的信号是“数值错误位置集中在某一维”，智能体据此猜测布局方向，多轮修复的 token 消耗被浪费在规格本可一次性消除的歧义上。这就是规格层作为代价中心的含义：它省下的每一轮修复，都以规格编写时的一次显式声明为代价。

二 · 代码生成层：CuTe 模板范式下的首版产出

生成层的输入是规格约束对象，输出是 CuTe 内核源码加启动配置（线程块维度、每线程 tile、流水级数）。与生成 CUDA C 或 Triton 不同，CuTe 的生成约束来自其类型系统：布局是编译期常量，MMA 原子是模板类型，张量切分通过 make_tensor 与 local_partition 一类组合子表达。普通提示难以稳定命中这些范式，因为模型必须同时决定“用哪个原子”和“布局如何与原子对齐”，两者耦合在模板实例化里，错一处就编译失败。CuTeGen 的做法是把 CuTe 的布局与 MMA 原子范式作为生成约束注入提示，让智能体在模板骨架内填充参数，而不是从零发明结构。

首版产出的代价集中在编译时间与 token 两端。CuTe 模板实例化是重编译负担：一个含多层嵌套布局与 MMA 原子的内核，单次编译的墙钟时间远高于等价 CUDA C 内核，而闭环每轮都要编译若干候选，编译时间随候选数线性叠加。token 侧，生成层要输出完整内核源码与配置，首版提示的上下文包含规格、范式骨架与少量示例，输出长度由内核规模决定。生成层不负责正确性，它只负责产出“可进入编译”的候选；把正确性判断推给验证层，是为了让生成层的搜索空间不被过早剪枝。

伪代码思路可写成：给定规格 S 与范式骨架 K，生成层采样 c ∼ p(c | S, K, H)，其中 H 是历史反馈上下文（首轮为空）。候选 c 包含源码与启动配置两部分，二者必须一致——线程块维度与内核内的 tile 切分不匹配时，编译可能通过但运行会越界或结果错位。一个具体例子：智能体为某个 shape 选择 128 线程的块与每线程 8 元素的 tile，但源码里的布局 stride 按 4 元素切分写死，编译通过、运行越界，反馈层回灌的是运行时报错位置而非编译诊断，修复轮次因此增加。生成层的工程判断是：启动配置应与源码同源生成，而不是事后补填。

三 · 编译执行层：两类诊断信号的分流

编译执行层在 GPU 工具链上实例化模板并运行，捕获两类信号：编译诊断与运行时报错。编译失败时，回灌的是模板实例化错误——CuTe 的错误信息冗长，指向的是某个布局或原子类型不满足约束，而非直接指出应改哪一行。这类错误的可修复性取决于智能体能否把“类型不匹配”映射回“布局参数选错”，映射规则是闭环有效性的关键工程代价。运行失败时，回灌的是越界或数值异常的位置，信号更具体，但定位到源码行仍需符号化。

代价在这里最容易被低估：编译诊断的 token 长度。CuTe 模板报错常包含多层实例化栈，单条诊断的字符数可达数千，若原样塞回提示，上下文预算被迅速耗尽，且有效信息密度低。工程上的处理是结构化裁剪——提取错误类型、涉及的模板参数与首个失败点，丢弃中间实例化栈。这一步的取舍是：裁剪过狠会丢失修复线索，裁剪不足则 token 成本失控。运行时报错的代价则是 GPU 时间：每次运行都要占用设备，越界访问可能触发非法内存访问而使进程终止，闭环需捕获该终止并转为可读信号，否则一轮候选评估会中断整条流水线。

一个具体例子：智能体选择的 MMA 原子与目标架构的指令集不匹配，编译在模板实例化处失败，诊断指向原子类型约束。若反馈层原样回灌，智能体在下一轮可能重复同一原子选择，形成重复失败循环——这是材料中明确指出的失败模式。缓解手段是把“原子—架构”约束在规格层前置声明，让生成层在采样时就排除不匹配的原子，而不是等编译失败后再修。编译执行层的输出因此不只是“通过/失败”，还包括失败类别标签，供反馈层决定是走修复路径还是走重采样路径。

四 · 验证评测层：oracle 与 profile 的双口径

验证层以参考实现为 oracle 做逐元素比对，数值超差即判定失败。这个口径的严格程度由容差决定，而容差在材料中未给出具体取值，因此工程上必须把它作为显式配置项而非隐式默认。逐元素比对的计算代价与输出规模成正比：对一个大 shape 的输出，比对本身要读写全量结果，显存带宽成为验证的瓶颈之一，尤其当参考实现与生成实现的结果都需要驻留显存时。验证层的输出是布尔判定加错误位置分布，后者被反馈层用来缩小修复范围。

评测层在正确性通过后测量延迟与吞吐，并采集硬件 profile 信号定位瓶颈。这里的口径问题在于：延迟测量需固定硬件平台与工具链版本，CuTe 模板行为对编译器版本敏感，版本漂移会直接改变编译通过率与性能数字。profile 信号到代码改写的映射是闭环的另一处工程代价——信号告诉你“某个流水级利用率低”或“某类访存模式未合并”，但把它翻译成“改分块大小”还是“换布局”需要映射规则，规则不稳则智能体在错误方向上迭代。评测层的输出是延迟、吞吐与瓶颈标签，三者共同构成候选排序的依据。

$$\mathcal{L}=\alpha\,\mathbf{1}_{\text{compile}}+\beta\,\mathbf{1}_{\text{correct}}+\gamma\,\frac{T_{\text{ref}}}{T_{\text{gen}}}+\delta\,\mathbf{1}_{\text{profile\_ok}}$$

该奖励口径把编译通过、数值正确、相对参考实现的加速比与 profile 合规四项合成一个可验证标量。它的工程含义是：编译与正确性是硬门槛（指示函数），加速比是连续项，profile 合规则是对“快但低效”实现的额外约束。代价在于权重选择——\gamma 过大时，智能体倾向牺牲数值稳健性换速度；\beta 过大时，搜索停滞在保守实现上。一个具体例子：某候选编译通过、数值正确、加速比略高于参考，但 profile 显示访存未合并，\delta 项将其降权，促使下一轮改写访存布局而非接受该候选。评测层的口径因此不是单一速度排名，而是多维门槛下的筛选。

五 · 反馈优化层：候选搜索与轮次成本

反馈层把错误类别、性能瓶颈与搜索候选回送生成器，驱动下一轮修复或重采样。材料明确优化主要发生在推理期的智能体搜索与执行反馈回路，而非参数更新；是否存在 RL 或轨迹 SFT 未给出。这意味着闭环的经济性完全由推理成本决定：每轮的 token 消耗（提示上下文加生成输出）与编译时间（候选数乘以单次编译墙钟）构成主要开销。搜索轮数与候选数量在材料中未给出，因此工程上必须把这两个量作为可配置预算，并在上线门里核算每轮修复的 token 与编译时间。

候选搜索的组织方式影响收敛速度。逐一评测若干候选、保留正确且加速比最高者，是最直接的策略，但其代价是候选数乘以（编译加运行加比对）的时间。若候选间差异只在启动配置，可先做低成本筛选（编译通过性）再进入昂贵评测；若差异在布局结构，则必须完整评测才能区分。反馈层的映射规则决定修复方向：编译错误走“改布局或原子”路径，运行错误走“改切分或边界处理”路径，profile 瓶颈走“改分块或流水”路径。三条路径的 token 成本不同，编译诊断最长，profile 信号最短但最模糊。

一个具体例子：首版内核编译通过但数值超差，反馈层给出错误位置分布集中在输出某一维，智能体据此判断布局方向错误，改写 stride 后第二轮通过；随后 profile 显示某流水级空转，智能体改写流水级数，第三轮加速比提升。这条三轮路径的代价是三次编译、两次运行比对与一次 profile 采集，外加每轮的提示上下文膨胀——历史反馈若不裁剪，第三轮的上下文长度可能是首轮的数倍。反馈层的工程判断是：历史上下文需按信号类别做摘要压缩，保留失败类别与关键参数，丢弃冗长的原始诊断。

六 · 闭环的工程边界：可复现性与失败循环

整条流水线的可信度建立在固定环境上：CUDA 与 CuTe 版本、编译器选项、硬件平台都需锁定，否则模板行为漂移会让编译通过率与性能数字不可比。上线门应包含编译通过率、数值正确率与相对基线加速比三项阈值，基线需包含手写 CuTe 实现与高层库实现，以便计算相对加速比。材料未给出基准规模、基线与加速比数字，因此当前只能作为方法框架参考，引用时不得虚构这些量。

失败模式的工程含义值得单独指出。CuTe 模板编译错误冗长且与布局强相关，自动修复可能陷入重复失败循环——智能体在同一原子选择上反复失败，每轮都消耗编译时间与 token 而无进展。缓解手段是失败计数与路径切换：同一错误类别连续出现时，强制重采样而非继续修复。另一处边界是 batch invariance：材料指出框架未给出不同 batch 下数值一致性的验证，而性能收益可能以数值一致性为代价，生产上线需补充该口径的测试。维护成本则需记录每轮修复的 token 与编译时间，评估闭环经济性——若单次内核生成的闭环成本高于人工编写，框架的价值就只剩降低门槛而非提升效率。

闭环的最后一个机制细节是信号到动作的映射表。把编译诊断、运行报错、profile 瓶颈三类信号各自映射到有限的改写动作集合（改布局、改原子、改分块、改流水、改边界处理），智能体在动作空间内搜索而非自由改写源码，可显著降低无效轮次。代价是动作空间的设计需要领域知识，映射表覆盖不全时，智能体面对未见过的信号只能回退到自由改写，闭环退化为普通提示修复。这张映射表因此是 CuTeGen 方法层最具体的工程资产，也是其可维护性的核心负担。
