一 · 生成前的契约抽取：把“批不变”写成可检查的依赖约束

论文的核心主张是把 BI 从一句口号变成生成阶段就能检查的约束。做法不是让 agent 自由发挥，而是在生成之前先从参考实现与算子语义中抽出一份“契约”（contract）：哪些张量维度参与归约、哪些索引依赖 batch 维、哪些标量来自运行时 shape。契约的产物是一组静态依赖规则，形如“输出元素 y[i] 只能依赖 x[i] 与逐元素常量，禁止依赖 batch_size 或跨样本归约”。这一步的输入是参考实现、算子签名与评测口径；输出是结构化契约，供后续静态分析与运行时校验共用。

机制上，契约把 BI 表达为一条可判定的性质：对任意两个 batch 上下文 B₁、B₂，同一输入样本 x 的输出必须逐位相等。写成公式即

$$\forall x,\ \forall B_1,B_2:\ \text{bits}\big(f(x;B_1)\big)=\text{bits}\big(f(x;B_2)\big)$$

这条公式的工程含义是：它排除了任何“按 batch 规模选择不同归约树”“按 batch 规模切换 tile 大小导致累加顺序变化”“按 batch 规模决定是否走 fast path”的实现。契约抽取的代价主要落在 token 与编译时间上——需要把参考实现与规则模板喂给模型，并让模型输出结构化规则而非自由文本；规则一旦抽错，后续所有门都建立在错误前提上，这是本方法最贵的一处单点风险。具体例子：一个 softmax 类算子若在 batch=1 时走 warp-level 归约、在 batch≥8 时走 block-level 归约，浮点累加顺序改变，末位比特就会漂移；契约会直接禁止“归约策略随 batch 变化”这一类写法。

二 · 单轮提示与 agent 脚手架：候选进入流水线的入口

论文把工具设计成通用 kernel agent 的插件，因此入口不是单一形态。单轮提示路径下，输入是任务描述、参考实现、契约规则与输出格式约束，输出是一份候选 kernel 源码；代价是单次前向的 token 成本与一次编译，好处是流水线短、失败可快速丢弃。agent 脚手架路径下，输入多了历史反馈（编译错误、运行时错误、上一轮的 BI 判定），输出是改写后的候选；代价是每轮都要重新编译与重跑校验，token 与编译时间随轮数线性增长。

两条路径共享同一个关键设计：BI 检查被插在“性能基准测试之前”。论文明确写到把工具集成为优化循环中的 successive acceptance gates，在进入性能测量前就拒绝结构上有风险或动态上不不变的候选，并把反馈回灌给 agent。伪代码层面即

$$\text{cand}\rightarrow \text{compile}\rightarrow \text{static gate}\rightarrow \text{dynamic gate}\rightarrow \text{bench}\rightarrow \text{accept/reject}$$

这个顺序本身就是代价决策：把便宜的静态检查放在昂贵的动态校验之前，把动态校验放在更昂贵的基准测量之前，避免为一个注定违反 BI 的候选付出完整 profile 成本。具体例子：agent 提交一份把 batch 维折叠进 grid 的 reduction kernel，静态门发现输出索引依赖 blockIdx 与 batch 规模的乘积关系，直接拒绝并返回“索引依赖 batch 维”的反馈，agent 下一轮改为按样本独立映射，省掉一次完整基准测量。

三 · 静态依赖分析：编译期就能判死的结构风险

静态门的输入是候选源码（CUDA C++ / Triton / CuTe / PTX 层面的中间表示）与契约规则，输出是“结构风险”判定与定位信息。机制是沿着数据依赖图检查三类模式：归约维度是否跨越样本边界、索引表达式是否含 batch 规模变量、以及是否存在按运行时 shape 分支选择不同算术路径的控制流。前两类是纯结构问题，不需要执行即可判定；第三类需要把分支条件与 batch 变量做符号关联。

代价方面，静态分析本身很便宜（相对编译与运行），但它有假阴性与假阳性：过度保守会拒绝本可不变的候选，浪费 agent 轮次；过度宽松会放过动态不不变的实现，把成本推给后面的动态门。论文的 19/83 违规发现说明这类结构风险在已发布产物中真实存在，且不是罕见个例。具体例子：某 kernel 用 if (batch > 4) 选择 vectorized load 宽度，两种宽度的累加顺序不同；静态门通过符号关联把该分支标记为“算术路径随 batch 变化”，在编译前即拒绝。这里的工程判断是：静态门应偏向保守，因为漏放的代价是整条基准测量链路白跑，而误拒的代价只是一轮 agent 改写。

四 · 动态逐位一致性校验：跨 batch 上下文的实测门

动态门的输入是已编译候选、一组固定的输入样本与多个不同的 batch 上下文，输出是逐位一致性判定。机制是把同一批样本分别放进不同 batch 组合中运行，比较同一位置输出的比特模式，而不是比较浮点容差内的近似相等——因为 BI 的定义就是逐位可复现。这一步直接对应论文所说的 dynamic validation of bitwise consistency across batch contexts。

代价是本方法最重的一环：每个候选要在多个 batch 上下文下各跑一次，运行次数随上下文数量线性增长，显存占用也随最大 batch 上升；对 serving 场景的真实任务，这意味着校验成本可能接近甚至超过基准测量本身。因此上下文集合的选择是设计要点：太少会漏掉触发不同 fast path 的临界 batch，太多则拖垮吞吐。具体例子：一个 layernorm 变体在 batch=1 与 batch=16 下输出一致，但在 batch=3（非 2 的幂，触发不同 tile 划分）下末位不同；若上下文集合只取 1 和 16，动态门会误放。这说明动态门的有效性取决于上下文覆盖，而覆盖度直接换算成运行次数与显存代价。

五 · 性能门与接受判据：BI 通过之后才谈加速

通过两道 BI 门之后，候选才进入性能测量。输入是候选、统一基线（PyTorch eager、torch.compile 与论文指定库）与论文口径的输入分布；输出是时延、加速比与资源占用。接受判据沿用论文给出的形式：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这里的 pass 在本文语境下不只是数值正确，还包含 BI 通过；也就是说接受条件被收紧为“正确 ∧ 批不变 ∧ 不慢于基线”。代价体现在两方面：一是 BI 门会砍掉一部分本来更快的候选（例如依赖 batch 规模切换 fast path 的实现），因此最终几何平均加速比会低于纯性能优化的上限；二是性能测量本身需要稳定计时与足够重复，属于整条链路中第二贵的环节。论文报告的结果是 BI 通过率从 67.6% 提升到 91.9%，同时保留基线几何平均的 91.8%——这组数字正是“用一部分性能换可复现性”的定量表达。具体例子：一个按 batch 规模选择不同 tile 的 matmul 变体在基准上更快，但动态门判定其在临界 batch 下比特不一致，被拒绝；agent 收到反馈后改为固定 tile 划分，加速比略降但通过全部门。

六 · 反馈回灌与插件化：让原有优化能力不被替换

论文强调工具是 plug-in component，允许通用 kernel agent 复用其原有优化能力，只额外加上 BI 强制。这意味着反馈不是另起一套优化器，而是把门的判定结果翻译成 agent 能消费的信号：静态门返回结构风险的位置与规则编号，动态门返回不一致的 batch 上下文与输出位置，性能门返回加速比与基线差距。输入是门判定，输出是下一轮提示中的约束片段；代价是每轮都要重新走编译—校验—测量，轮数越多总 token 与编译时间越高。

机制上，反馈的设计要避免两类退化：一是把“拒绝”变成无信息，agent 只能随机重试；二是把“通过”变成过拟合，agent 学会只针对校验用的 batch 上下文做特化。后者的代价是隐藏输入分布上的 BI 回归，属于典型的 reward hacking 风险。工程判断是：反馈应携带规则编号而非仅布尔值，且动态门的上下文集合不应完全暴露给 agent，否则特化会绕过校验。具体例子：agent 连续两轮提交同一份依赖 batch 变量的索引写法，静态门每次返回同一规则编号，agent 在第三轮改为逐样本独立映射并通过——这正是反馈携带定位信息而非仅“失败”二字的价值所在。

契约静态分析挡不住的那些候选：边界、失效条件与系统代价

把 \tool 当作“插件式门禁”接入优化循环，意味着它并不替换 agent 的生成器，而是在候选 kernel 进入性能基准之前插两道闸：契约引导的静态依赖分析，以及跨 batch 上下文的逐位一致性动态验证。静态分析读取的是候选源码与算子契约（哪些张量维度是 batch 维、归约轴在哪、哪些缓冲被跨请求复用），据此判定结构性风险——例如归约顺序依赖 batch 内元素排布、以 batch size 为循环边界展开的累加、或在共享内存里做与 batch 布局耦合的树形归约。这类候选被直接拒绝，不进入计时环节。代价是编译期与 token 开销：静态分析需要在生成后、编译前插入一次额外的源码级检查，agent 每轮多一次往返；若候选被拒，回灌的反馈文本会挤占上下文预算，长会话中反馈累积会压缩后续生成的可用 token。动态验证则是更贵的一环：同一输入在不同 batch 上下文（不同邻居请求、不同 padding、不同 batch size）下重放，逐位比较输出，任一不一致即判失败。它的代价是显存与时间——需要构造多个 batch 上下文并保留中间输出做位级比较，对显存受限的算子，多上下文重放会把峰值占用推高；对长时延算子，验证次数乘以单次运行时间直接进入优化循环的墙钟时间。

失效条件集中在三处。其一，契约本身不完备：若算子契约没有显式声明 batch 维语义，静态分析只能退化为启发式，把“看起来像归约”的候选一律标风险，误杀本可不变的实现，导致 BI 通过率上升但加速比被无谓牺牲。其二，动态验证的上下文覆盖不足：只验证有限几种 batch 组合，无法排除在未覆盖的邻居请求组合下出现位级漂移，尤其当候选内部存在与 batch 内位置相关的分支（如按 lane 划分的 warp 级归约）时，验证通过并不等于不变性成立。其三，逐位一致性对某些算子过严：浮点归约在合法重排下本就不保证位级相同，若契约允许非确定性归约，硬性位级门禁会把正确但非逐位一致的候选判死，此时需要的是“跨上下文一致”而非“与参考逐位相同”的口径区分。论文报告的 19/83 违规说明这类风险在已发布产物中真实存在，但也提示门禁的假阳性与假阴性都会直接改变优化循环的走向。

$$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1],\qquad s=\frac{T_{\text{base}}}{T_{\text{agent}}}$$

把接受条件写成上式后，门禁的位置就决定了代价结构：若 BI 验证放在性能基准之后，非不变候选会先消耗一轮完整计时，浪费的时延等于被拒候选的基准运行时间；\tool 选择把它前置为 successive acceptance gates，用静态分析先砍结构性风险、再用动态验证砍行为不一致，最后才让幸存者进入基准。这样做的系统代价是“验证吞吐”成为瓶颈——每个候选都要付出多上下文重放的固定开销，优化循环的迭代数受限于验证而非生成。一个具体例子：某归约算子候选在 batch=1 时与参考逐位一致，但在 batch=8 且邻居请求改变 padding 后，因累加顺序随 batch 布局变化而出现末位差异；静态分析若能识别“归约轴与 batch 维耦合”即拒，省下一次基准计时；若识别不出，动态验证在两种上下文下比较即可捕获，代价是两次运行加一次位级比对。工程判断在于：门禁越靠前，省下的基准时间越多，但静态分析的误杀率越高；门禁越靠后，验证越贴近真实行为，但每个被拒候选都已付出计时成本。\tool 作为可插拔组件保留原 agent 优化能力的同时，把 BI 强制变成循环中的硬约束，其收益（BI 通过率从 67.6\% 提升到 91.9\% 而保留 91.8\% 的基线几何平均加速比）本质上是用验证开销换可复现性，这一交换在验证成本高于基准计时的算子上并不划算，是该方法最直接的适用边界。

门控插件的边界：静态契约与动态位级验证各自失效的地方

\tool 作为可插拔组件嵌入通用 kernel agent，其代价不在生成侧而在评测侧的流水线位置：它被实现为优化循环中的连续验收门（successive acceptance gates），在性能基准测试之前拒绝“结构上有风险”或“动态上非不变”的候选，并把反馈回灌给 agent。这意味着每次候选都要额外承担一次静态依赖分析（编译期，按 kernel 规模与依赖图深度增长，对小算子可忽略、对融合大 kernel 会拉长编译时间）与一次跨 batch 上下文的动态位级一致性验证（需构造多个 batch 组合各跑一遍，运行次数随上下文数线性增长，显存占用按最大 batch 计）。门控放在性能测量之前，省下了对不合格候选做基准测试的时延开销，但把成本前移到了正确性阶段；若 agent 每轮产出多个候选，验证调用次数即为候选数乘以上下文数，token 与 GPU 时间同时放大。

$$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1],\qquad s=\frac{T_{\text{base}}}{T_{\text{agent}}}$$

静态契约分析的能力边界在于它只能看见“契约里写明的”依赖：归约顺序、跨 batch 维的共享缓冲、原子累加、以 batch size 为参数的 tile 划分。若 kernel 通过间接方式引入 batch 相关性——例如以运行时 batch 大小选择不同的 tiling 策略、或在 epilogue 中按 batch 索引做条件分支——静态分析可能放行，此时唯一兜底是动态位级验证。反之，动态验证的失效条件是上下文覆盖不足：只测少数几个 batch 组合时，非不变性可能恰好落在未采样的组合上而被误判为通过。论文报告的 19/83 违规率说明这类缺陷在已发布产物中并不罕见，但该比例只在论文给定的硬件、基线与输入分布上成立；跨 dtype、跨框架的迁移未验证，门控的判定阈值也随之漂移。

门输入输出主要代价典型漏检
静态契约分析候选源码 + 契约声明结构风险标记编译期时延运行时按 batch 选策略
动态位级验证候选 + 多组 batch 上下文位级一致性判定运行次数 × 上下文数、显存未采样的 batch 组合
性能门通过前两门的候选加速比与保留/回退基准测量时延基线未开 TF32 导致高估

系统层面的工程判断是：门控的严格度与保留率之间存在直接张力——论文在三个 agent 框架上把 BI 通过率从 67.6% 提到 91.9%，同时保留基线几何平均加速的 91.8%，说明门控并非免费，它以约一成的性能收益换取不变性。更隐蔽的风险在反馈回路本身：agent 收到“非不变”反馈后可能改写为保守实现以通过门控，形成 reward hacking 式的正确率虚高；而回退机制若默认退回参考实现，则加速比与正确率同时被美化。因此门控必须与性能门解耦记录——分别统计通过率、保留加速比与被拒候选的分布，否则离线分数无法预测生产端到端收益。
