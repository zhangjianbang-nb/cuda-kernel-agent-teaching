一 · 生成步：提示形态决定搜索空间的形状

把一次 kernel 生成拆成流动的第一步，输入是「问题规格」：参考 PyTorch 实现、算子语义、输入 shape/dtype 分布、目标硬件与基线口径。输出是候选源码（CUDA C++ / Triton / CuTe / PTX 之一）。论文评测的五种模型配置在这一步的差别不在采样温度，而在提示形态：单轮提示把整个规格压进一个上下文窗口，模型一次性吐出完整 kernel；agent 脚手架则把规格切成可迭代的子目标，每一轮只改动一处（tiling、向量化宽度、shared memory 布局、流水级数），并把上一轮的编译错误与 profile 摘要作为下一轮输入。

单轮提示的代价结构很直接：token 预算一次性消耗在「读懂规格 + 写出正确代码」两件事上，模型没有机会看到自己的编译错误。对 KernelBench level 1 这类单算子题，这恰好够用——前沿模型在 91.1% 的题上产出了正确 kernel。但对卷积这类需要处理边界、padding、dtype 混合的题，单轮的成功率明显塌陷：开放权重模型最好的一档正确率只有 30.4%，且卷积题全灭。这不是采样次数的问题，而是单轮提示无法承载「先写一个能编译的朴素版本，再根据 NCU 反馈重排」这种多步结构。

agent 脚手架的输入多了两样东西：工具返回的结构化错误（编译器诊断、launch 失败原因、正确性断言的差异位置）和性能计数器摘要。输出不再是单个候选，而是一条候选轨迹。代价从 token 转移到时延：每一轮都要真实编译、真实运行，一轮的墙钟时间由 nvcc 编译（秒级到十几秒）加 kernel 执行（微秒到毫秒）构成，编译时间在迭代次数上被线性放大。这是脚手架相对单轮提示最容易被低估的开销——当候选需要几十轮才收敛时，编译时间会超过 GPU 时间一个量级以上。

RL 路线把这一步从「推理时搜索」搬到「训练时分布塑形」。输入是成批的题目与可验证奖励函数，输出是策略参数更新。它的代价不在单次生成，而在采样吞吐：每条轨迹都要跑完编译—运行—评测才能拿到奖励信号，因此 rollout 的瓶颈是编译与正确性检查，而不是自回归解码。论文没有给出 RL 配方的细节，但从「五种模型配置」的对比口径看，RL 与脚手架属于同一层的工程选择：都试图把「一次生成」变成「带反馈的多次生成」，区别只在于反馈被固化进权重还是留在上下文里。

二 · 编译步：把语法正确性从语义正确性里剥出来

编译步的输入是候选源码加编译选项（架构代号、优化级别、是否开 fast math、链接哪些库），输出是二进制或编译诊断。这一步在流水线里的作用是把失败分成两类：语法/类型/资源约束失败，与语义失败。前者由编译器直接判定，代价低、信号强；后者必须进入运行步才能暴露。

一个具体机制是资源约束检查。kernel 的寄存器用量、shared memory 用量、线程块尺寸在编译期就能算出上限，超出硬件限制的候选会在 launch 阶段直接失败。把这类检查前移到编译步，可以让 agent 在拿到 profile 之前就排除掉一整类无效候选，避免把 GPU 时间浪费在必然失败的配置上。伪代码思路是：

$$\text{accept}(k)=\mathbb{1}[\text{compiles}(k)]\cdot\mathbb{1}[\text{regs}(k)\le R_{\max}]\cdot\mathbb{1}[\text{smem}(k)\le S_{\max}]$$

代价体现在编译时间与缓存命中率上。同一份源码在不同架构代号下编译出的 SASS 不同，寄存器压力也不同；如果脚手架在每轮都换编译目标，编译缓存就无法复用，单轮时延会显著上升。工程上的做法是把编译目标固定成评测口径里的那一档，只在候选确实需要架构特化时才切换。

这一步的另一个代价是「编译通过但语义错误」的候选占比。论文的 91.1% 正确率是在编译通过之后才统计的，也就是说编译步本身不构成主要瓶颈；真正的漏斗在运行步。对开放权重模型，30.4% 的正确率意味着大量候选能编译、能 launch，但在给定输入上给出错误结果——这类失败无法靠编译器诊断捕获，只能靠正确性 oracle。

三 · 运行与正确性步：oracle 的粒度决定假阳性的形状

运行步的输入是二进制、输入张量、参考实现，输出是候选输出与参考输出的差异度量。正确性 oracle 的粒度是这一步的核心设计变量：逐元素全等、相对误差阈值、还是按 dtype 的 ULP 容差。粒度太松会把数值上等价但语义错误的 kernel 放行（例如把 reduction 的结合顺序改了却恰好落在容差内），粒度太紧会把合法的浮点重排判为失败。

论文口径下的正确性检查是在「给定输入分布」上做的。这是一个必须写清楚的限定：正确率 91.1% 与 30.4% 都是相对这批输入而言，不是对算子全部定义域的保证。一个在固定 shape 上正确的 kernel，换一个非对齐的尾维度就可能越界或读错 shared memory。工程上的代价是显存：为了做逐元素比对，参考输出与候选输出必须同时在显存里驻留，对大 tensor 这意味着正确性检查本身会推高峰值占用，甚至成为比 kernel 执行更大的开销。

形式验证在这里是另一种 oracle。它不跑输入，而是对 kernel 的索引表达式与访存模式做符号推理，证明「对任意合法 shape，输出等于参考语义」。代价是编译时间与可表达性：能自动证明的 kernel 通常是规则 tiling 的仿射索引，遇到数据依赖的分支或原子操作就退化。论文没有采用形式验证，但这条路线解释了为什么「正确率」这个数字必须绑定 oracle 类型才有意义——换一个更严的 oracle，91.1% 会下降，而下降的部分正是那些在固定输入上侥幸通过的候选。

一个具体例子是卷积。前沿模型在 56 道题里独立验证了 22 个加速，其中包含三个卷积；开放权重模型在卷积上零解。卷积的正确性检查要覆盖 padding 边界、stride 与 dilation 的组合、以及 channel 维度的非对齐尾块——这些恰好是固定输入分布最容易漏掉的部分。因此「三个卷积被验证」这句话的信息量，取决于验证时用的 shape 集合是否覆盖了边界情形。

四 · 性能评测步：加速比的分母与计时口径

性能步的输入是候选 kernel 与基线实现，输出是时延与加速比。论文给出的评分形式是阈值化的胜率：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个式子里有两个隐藏的自由度。第一是 $T_{\text{base}}$ 取什么：PyTorch eager、torch.compile、还是论文指定的库实现。基线越弱，$s_i$ 越容易越过阈值，加速比越好看。第二是计时口径：是否包含 kernel launch 开销、是否做 warmup、是否用 CUDA event 还是 wall clock、是否固定 clock 频率。对一个执行时间在微秒级的 elementwise kernel，launch 开销可以占到大半，计时口径的差异足以让同一个候选在「加速」与「减速」之间翻转。

论文报告的 1.235x 中位加速比与 22/56 的验证胜出数，是在它自己声明的基线与口径下成立的。这不是削弱结论，而是给结论划定适用范围：跨硬件、跨 dtype、跨框架迁移时，分母会变，胜率也会变。工程判断是，任何声称「超过 PyTorch」的 kernel 都必须附带基线版本、编译选项（尤其是 TF32 是否开启）与计时方法，否则加速比不可复现。

这一步的代价是测量噪声与 GPU 占用。为了得到稳定的时延，通常要重复多次取中位数或最小值，每次重复都占用 GPU；在共享集群上，这会与其它任务争抢 SM，导致测量值偏高。更隐蔽的代价是「shape 特化」：候选可以针对评测用的那一组 shape 做硬编码 tiling，在离线基准上拿到高加速比，但在生产输入分布上退化。论文的端到端分析正是为了暴露这一点——离线胜率与真实收益之间的落差，就是 shape 特化与基线选择共同造成的。

五 · 反馈回流步：保留、回退与奖励塑形

反馈步的输入是正确性判定与性能判定，输出是「保留候选」「回退到上一版」或「改写某一处」的动作。在 agent 脚手架里，这个动作由提示模板与启发式规则决定；在 RL 里，它被压缩成一个标量奖励。两种形态的代价不同：脚手架的回退是显式的，每一轮回退都消耗一次编译与一次运行；RL 的奖励塑形是隐式的，错误的正负号会污染整个策略分布。

一个具体机制是分层门控：先过正确性门，再过性能门。正确性门不通过的候选不进入计时，避免把 GPU 时间花在错误 kernel 上；性能门不通过的候选回退到上一版，避免在局部最优上反复震荡。伪代码思路是：

$$\text{keep}(k_t)=\mathbb{1}[\text{correct}(k_t)]\cdot\mathbb{1}[T(k_t)<T(k_{t-1})]$$

代价是「回退陷阱」：如果性能门的阈值设得太紧，脚手架会在两个几乎等价的候选之间来回跳，迭代次数上升而性能不升。更严重的代价是 reward hacking——当奖励只看加速比而不看正确性覆盖度时，策略会学会产出在评测 shape 上极快、在其它 shape 上错误的 kernel。论文的 41.7% 胜率与 1.552x 中位加速比是在 DLRM-Bench 的 12 道推荐系统题上测的，这个数字的可信度依赖于正确性门与性能门是串联而非并联的。

RL 路线在这一步的代价是 token 与 GPU 时间的乘积：每条 rollout 都要完整走一遍生成—编译—运行—评测，采样成本随题目数与轨迹数线性增长。这也是为什么 RL 配方必须把「可验证奖励」设计得尽量便宜——正确性检查能用小 shape 就不必用大 shape，能用抽样就不必做全量比对。论文没有展开 RL 细节，但从它把「独立验证的加速比」作为核心口径来看，奖励信号的可验证性是整条流水线的前置约束。

六 · 端到端折算步：从 kernel 胜率到墙钟占比

最后一步把离线胜率折算成真实负载的收益。输入是 profile 结果（每个 kernel 在总墙钟里的占比）与离线加速比，输出是可寻址比例与投影收益。论文的核心发现是：七个负载跨三个领域，可寻址比例落在 8.9% 到 58.2% 之间；在 transformer 上，80–86% 的运行时间花在 cuBLAS GEMM 与 FlashAttention 上，这把端到端改善的上界压在约 1%，且这个比例随模型规模缩小；在推荐系统上可寻址比例是 58.2%，集中在一个 embedding kernel 上。

折算的公式思路是加权：

$$\text{gain}_{\text{e2e}}=\sum_{k\in\text{kernels}} f_k\cdot\left(1-\frac{1}{s_k}\right)$$

其中 $f_k$ 是 kernel $k$ 在总墙钟里的占比，$s_k$ 是它的加速比。这个式子的含义很硬：即使某个 kernel 加速 1.552x，如果它只占 8.9% 的墙钟，端到端收益也只有百分之几。论文在 DLRM-Bench 上测到 41.7% 胜率、1.552x 中位加速比，据此投影出 8.63% 的端到端收益——这个数字之所以能到 8.63%，是因为推荐系统的可寻址比例高达 58.2%，而不是因为 kernel 本身更快。

这一步的代价是 profile 的侵入性。要拿到 $f_k$，必须对真实负载做逐 kernel 计时，这会引入 profiler 开销、改变 kernel 调度顺序、甚至抑制某些融合优化。更实际的代价是「可寻址比例」的定义依赖基线：如果基线里的 GEMM 已经用了 cuBLAS 的最强实现，那么任何自写 GEMM 的加速空间都被压得很窄；反过来，如果基线是未开 TF32 的 eager 实现，可寻址比例会被高估。论文把 transformer 的上界压在约 1%，正是承认了 cuBLAS 与 FlashAttention 已经占据了绝大部分墙钟——这不是 LLM 生成 kernel 的失败，而是「可寻址比例」这个口径本身的工程含义：生成式 kernel 的战场在 cuBLAS 覆盖不到的长尾算子上，而不在已经被高度优化的稠密算子上。

加速比门限与“可寻址份额”的耦合失效

这套流程的边界不在生成端，而在两个门限的乘法关系上。正确性门是布尔量，性能门却是阈值量：候选只有在 $$s_i=T_{\text{base},i}/T_{\text{cand},i}\ge\tau$$ 时才计入胜率，而论文口径下 frontier 模型在 KernelBench level 1 上正确率 91.1%、56 题中仅 22 题通过独立验证的加速、中位 1.235x——这意味着约七成“正确”的候选在性能门上被丢弃。更关键的是，胜率并不等于端到端收益：即使 DLRM-Bench 上取得 41.7% 胜率、中位 1.552x，投影到端到端也只有 8.63%，因为可寻址份额本身只有 58.2%（推荐系统，集中于单个 embedding kernel）；而 transformer 上 80–86% 时间被 cuBLAS GEMM 与 FlashAttention 占据，端到端上限被压到约 1%，且随模型规模收缩。失效条件因此很明确：当基线库已接近 SOL、或热点被不可替换的库调用锁死时，性能门通过率再高也无法转化为墙钟收益。

系统代价体现在评测管线的重复开销上。每轮候选都要走“编译—正确性检查—统一基线计时”三步，编译时间与计时抖动直接吃掉 token 预算：一个被性能门拒绝的候选，其编译与多轮计时成本与胜出候选相同，却贡献零收益。若把 $$\text{yield}=\frac{1}{N}\sum_i\mathbb{1}[c_i\wedge s_i\ge\tau]$$ 作为筛选效率指标（$$c_i$$ 为正确性），则 frontier 配置的 yield 受限于 22/56 这一上限，而 open-weights 最好仅 30.4% 正确、三个验证加速、卷积全灭——说明弱模型的瓶颈在正确性门而非性能门，继续加采样轮数只会放大编译开销。工程判断是：把 τ 与可寻址份额一起标定，对可寻址份额低于阈值的负载直接跳过 kernel 级优化，比在性能门上反复回退更省时延。
