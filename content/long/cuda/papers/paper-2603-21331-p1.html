一 · 从一次线上推理的深夜告警说起

设想一个已经上线的推理服务：模型结构固定，batch 与序列长度分布由业务流量决定，GPU 型号在采购时已经锁定。某天监控显示 P99 时延抬升，算子级 profile 指向一个融合后的 attention 变体——它不在 cuBLAS、cuDNN 或 CUTLASS 的现成覆盖里，是团队两年前为了绕开某个中间张量的显存往返而手写的 CUDA kernel。这段代码当初由一位熟悉 SM 占用率与 bank conflict 的工程师写成，注释里留着当时的调优笔记，但那位工程师已经转岗。现在要做的不是“重写整个模型”，而是让这个 kernel 在新 shape 分布下重新变快，同时不能改变数值语义。

这个场景把 GPU kernel 工程的四个痛点一次性摊开：开发周期以人月计，性能上限被写代码那一个人的知识边界封死，正确性依赖脆弱的经验判断，可维护性随着人员流动迅速衰减。AutoKernel 这类工作的位置，正是从这个现场出发：把“改写—编译—运行—比对—测量”这一圈原本由人完成的动作，交给一个带执行反馈的智能体循环。本部分只处理一件事——在这篇论文之前，主流做法是什么，它们各自在哪一步卡住，以至于非改不可。

二 · 三条旧路径：手写 CUDA、Triton、库调用

第一条路径是手写 CUDA C++。它的优势是控制力：线程块形状、共享内存布局、`__syncthreads()` 的位置、向量化宽度、寄存器压力，全部可调。代价是这些决策互相耦合。以矩阵乘的一个 tile 为例，块大小 BM×BN、每线程累加片段 TM×TN、共享内存 stage 数共同决定占用率与流水深度，改动一个参数就要重新验证数值边界与尾部处理。一个中等复杂度的融合算子，从初版到可上线，工程上通常要经历数十次编译—profile—改写循环，每次循环都要人读 NCU 指标、看 SASS 片段、判断瓶颈在访存还是计算。这条路径的性能上限很高，但上限由写代码者的经验决定，且不可复制。

第二条路径是 Triton。它把块级编程抽象出来，用 `tl.load`/`tl.dot` 描述 tile 级计算，编译器负责布局与流水。开发周期显著缩短，正确性也更容易保证，因为语言层面屏蔽了线程级索引。代价是性能上限受编译器调度能力约束：某些访存模式、特定的 swizzle 需求、非标准的归约结构，Triton 的自动布局未必给出最优解，工程师只能退回 CUDA 或接受次优。更关键的是，Triton 的调优空间是离散的元参数（`BLOCK_M`、`BLOCK_N`、`BLOCK_K`、`num_warps`、`num_stages`），自动搜索这些参数本身就是一个组合优化问题，而搜索的每一次试验都要付出编译与运行的实打实开销。

第三条路径是库调用。cuBLAS、cuDNN、CUTLASS 模板库覆盖了大量标准形态，性能经过厂商深度调优，正确性有保障，维护成本接近零。但库的覆盖是“标准形态”的覆盖：一旦算子需要融合（比如 attention 里 softmax 与 GEMM 的拼接）、需要非标准布局、需要特定 dtype 混合，库就退化为若干次独立调用，中间结果被迫写回显存再读回。以一次融合前的两算子链为例，中间张量大小为 M×N、元素为 2 字节，则多出的显存往返流量约为 2·M·N·2 字节（写一次、读一次），在带宽受限的算子上，这部分流量直接吃掉融合本可带来的收益。库调用的痛点不是性能绝对值低，而是“不可融合”带来的结构性损失。

路径开发周期性能上限正确性风险可维护性
手写 CUDA长，人月级高，受作者经验封顶边界与数值处理易错低，人员流动即失传

三条路径的共同结构是：性能提升依赖“人”在编译—运行—profile 闭环中做决策。这个闭环的每一圈都有真实代价——一次编译数十秒到数分钟，一次正确性比对要构造参考实现与容差，一次 NCU profile 要重放 kernel 并采集计数器。人做这个循环的速度，就是整个 kernel 工程的速度上限。

三 · 单轮代码生成的失效点：为什么提示一次不够

大模型进入这个领域后，最先被尝试的是单轮提示：给任务描述与参考实现，让模型直接输出一版 kernel。这条路在简单算子上能跑通，但在真实优化任务上系统性失效，原因可以拆成三层。

第一层是编译反馈不可省略。生成的 CUDA 代码经常在接口层出错：`__launch_bounds__` 与块大小不匹配、共享内存声明超过静态上限、模板参数与 launch 配置不一致。这些错误只有编译器能给出精确的行号与诊断，模型在无反馈条件下无法自查。第二层是正确性不可由“看起来对”替代。浮点归约的顺序改变会带来 ulp 级差异，边界 shape（非整除的尾块、长度为 1 的归约维）会触发越界或漏算。判定必须是与参考实现逐元素比对并设定容差，这个动作只能在运行后完成。第三层是性能反馈的维度远超代码文本。一个 kernel 慢，可能是因为寄存器溢出导致占用率下降，可能是因为共享内存 bank conflict，可能是因为全局访存没有合并。这些信息存在于 NCU 计数器与 SASS 里，不在源码里。模型读源码无法推断出“把 `num_stages` 从 2 提到 3 会让流水填满但共享内存翻倍从而压低占用率”这类结论。

把这三层合起来看，单轮生成的本质是“开环控制”：输出一版代码，没有测量，没有修正。而 kernel 优化的本质是闭环搜索——每一版候选都要经过编译、运行、比对、测量，反馈决定下一版往哪个方向改。AutoKernel 的核心思想正是把这个闭环显式化：智能体读取上一轮的编译结果、正确性判定与性能测量，再生成下一版。用公式表述最终选优规则：

$$\text{best} = \arg\max_{k \in \{k_1,\dots,k_n\}} \text{Perf}(k) \quad \text{s.t.} \quad \text{Correct}(k)=\text{true}$$

这个式子的工程含义是：搜索空间里的候选必须同时过正确性门与性能排序，二者缺一不可。单轮生成连“候选集合”都构不成，因为它没有经过 Correct 判定，也没有 Perf 测量。

四 · 闭环每一圈的代价：编译时间、token、显存与测量噪声

把闭环交给智能体，不等于闭环变便宜。每一圈都有四类实打实的开销，工程上必须逐项计入，否则“自主优化”会变成“自主烧钱”。

其一是编译时间。一次 nvcc 编译带模板展开的 kernel，耗时从数十秒到数分钟不等；Triton 的 JIT 首次编译同样要付出布局推导与 PTX 生成的时间。搜索若跑 n 轮，编译开销就是 n 次编译的累加，且编译失败轮次同样计入——失败也是反馈，也要花时间。其二是 token 成本。每一轮智能体都要读入历史尝试记录（源码、编译日志、性能数字），上下文随轮数增长，单轮 token 消耗随历史长度上升，总成本近似随轮数超线性增长。其三是显存与运行开销。正确性比对要同时驻留候选输出与参考输出，性能测量要重复运行以压低噪声，每次重复都占用 GPU 时间。其四是测量噪声。kernel 时延在微秒级时，计时方式、重复次数、是否排除数据传输与编译开销，直接决定 Perf 这个数字是否可信；若口径不严，搜索会朝着“测量偏差最大的方向”收敛，而不是朝着真实更快的方向。

举一个具体的代价结构：假设一个融合算子搜索跑 n=20 轮，其中若干轮编译失败、若干轮正确性不通过、剩余轮次进入性能测量。有效性能样本只占一部分，但编译与运行的 GPU 时间按全部轮次计。这意味着搜索的经济性不由“最好那一版有多快”决定，而由“多少轮被浪费在编译失败与正确性失败上”决定。工程判断因此落在两处：一是把编译错误与接口错误尽早拦截（在生成阶段就约束 launch 配置与共享内存上限），二是把正确性比对做成廉价的前置门，避免错误内核进入昂贵的性能测量阶段。

五 · 正确性 oracle 的脆弱性与防作弊缺口

旧方案里，正确性由人把关：写代码的人知道哪里可能溢出、哪里归约顺序变了、哪里尾块没处理。闭环搜索把这个把关交给自动比对，脆弱性立刻显现。比对依赖参考实现，而参考实现本身可能是库调用或朴素实现，两者的数值路径与候选 kernel 不同，逐元素严格相等几乎必然失败。因此必须设容差，容差的选取直接决定“什么算对”：容差过松，一个累积误差偏大的 kernel 会被判为正确并进入性能排序，最终上线后数值漂移；容差过紧，合法的重排归约被误杀，搜索空间被人为压缩。

更隐蔽的缺口在边界覆盖。参考比对通常跑一组固定 shape，若这组 shape 恰好都是整除的、对齐的、长度规整的，那么尾块处理、非对齐访存、长度为 1 的归约维这些最容易出错的路径根本没有被测试。一个在这些边界上越界的 kernel，可以在主 shape 上通过比对并拿到好看的性能数字。防作弊还有第三个维度：候选 kernel 是否可以“偷看”参考实现或测试输入，是否可以在测量时跳过实际计算，是否可以把结果缓存后直接返回。这些在材料中均未说明防护机制，属于评测可信度的已知缺口。

工程上的应对思路是把正确性门做成多层：先用小规模随机输入做快速筛查，再用覆盖边界 shape 的用例集做回归，最后对通过者做一次与参考实现的差异分布检查（不只看是否在容差内，还看误差是否随规模增长）。这套分层本身有成本——用例集越多，每轮比对越慢，搜索轮数被迫压缩。正确性与搜索广度之间的这个取舍，是闭环工程里无法回避的张力。

六 · 可维护性与性能上限：为什么旧方案非改不可

回到开场的那个深夜告警。手写 kernel 的可维护性问题不是“代码难读”，而是“调优知识不可迁移”：当初为什么选这个 tile 形状、为什么这个 stage 数，这些决策的依据留在某个人的头脑与零散的 profile 截图里，没有进入代码库。人员一走，下一次 shape 分布变化时，接手的人只能从头再做一遍编译—profile—改写循环。Triton 缓解了可读性，但没有解决“元参数需要随 shape 重搜”的问题；库调用缓解了维护，但把融合的结构性收益让渡了出去。

性能上限的问题同样结构性。手写 CUDA 的上限是作者的经验半径；Triton 的上限是编译器调度能力的半径；库的上限是厂商覆盖形态的半径。三者都不是“搜索出来的上限”，而是“被预先决定的上限”。当模型结构与流量分布持续漂移时，这个上限会不断被动下降，而重新触顶的成本是一次完整的人工调优周期。AutoKernel 的迭代搜索把这个触顶动作变成可重复执行的循环：每轮产出一个候选及其评测记录，历史记录供后续轮次参考，最终在正确候选中取性能最优者。它的价值不在于某一版 kernel 比手写更快，而在于把“重新触顶”从人月级动作变成可编排的搜索过程。

但必须把话说清楚：这篇论文是摘要级材料，未给出基准数据集名称与题目数量，未给出对比基线及其调优程度，未给出加速比、正确性通过率等具体数字，也未给出搜索轮数、token 成本与单次编译运行耗时。因此“非改不可”的论证在本部分落在机制层：单轮开环无法产生经过 Correct 判定与 Perf 测量的候选集合，而 kernel 优化的决策信息只存在于编译诊断、运行比对与硬件计数器中。闭环是信息上的必需，不是效率上的偏好。真正需要后续工作补齐的，是这套闭环在真实基准上的评测口径与搜索成本——在口径未定之前，任何“自主优化已超越手写”的读法都是把摘要当结论。
