一 · 生成端：从算子语义到可编译的 Triton 源码

Dr. Kernel 的一次 kernel 生成，起点不是“写个 kernel”这句空话，而是一份结构化的任务描述：算子语义（例如归约、逐元素、矩阵乘的变体）、输入张量的 shape 与 dtype、以及参考实现的调用约定。生成端要产出的不只是 Triton kernel 本体，还包括调用脚手架——host 侧的 launch 代码、grid 与 block 的配置、以及把 PyTorch 参考实现与 kernel 输出对齐的胶水。这一步的输入是任务描述加历史反馈（首轮为空），输出是一段可被 Triton 编译器接受的源码文本。

代价在这里第一次显形：token。生成端每轮要吐出的不是几十行而是上百行的 kernel 加脚手架，多轮 rollout 意味着同一任务被反复生成，token 消耗随轮数线性增长，而材料明确未给出轮数与 token 预算，这本身就是工程上必须自己标定的量。更隐蔽的代价是“生成即错误”的概率：Triton 的语义边界（block 内归约、mask 写法、`tl.load` 的边界条件）与 PyTorch 的语义并不一一对应，模型首轮写出的代码大概率在编译期就倒下。这正是多轮闭环存在的理由——单轮提示把这一次失败直接判死，而 Dr. Kernel 把它变成下一轮的输入。

一个具体例子：任务要求对长度为 N 的向量做带 mask 的归约。模型首轮可能写出固定 block size 而忽略 N 不是 block 整数倍的情形，源码语法完全合法，但语义上越界。这个错误不会在生成端被发现，它要等到执行端的逐元素比对才暴露。生成端的输出因此必须被视为“待验证的假设”，而不是“答案”。

二 · 编译端：语法、类型与 PTX 生成的三道坎

执行端接手的第一个动作是编译。Triton 编译器把 Python 风格的 kernel 源码降到 TTIR、TTGIR，再落到 PTX，最后由驱动编译成 SASS。这条链上任何一环失败，都会以异常文本的形式返回。Dr. Kernel 把编译错误原样回灌给模型，作为下一轮生成的上下文——这是闭环里最便宜的一环：编译失败通常在秒级返回，不需要占用 GPU 做数值比对，也不需要跑测速。

但“便宜”不等于“无害”。编译错误的文本往往指向语法或类型（例如 dtype 不匹配、`tl.constexpr` 参数缺失），模型据此修正后可能通过编译，却在语义上仍然错。于是出现一种典型的退化：多轮反馈若只回灌错误文本而无 profile 数据，优化轮次可能退化为语法修补——模型学会了让代码“能编译”，却没学会让它“算得对、跑得快”。这是 Dr. Kernel 奖励设计必须把正确性设为硬门槛的直接原因：编译通过只是入场券，不是得分项。

$$\text{compile}(k) \rightarrow \{\text{PTX} \mid \text{error text}\}$$

编译端的另一项代价是编译时间本身。Triton 的 JIT 编译对每个新的 shape 组合都要重新走一遍降级流程，多轮 rollout 中同一任务被反复编译，编译开销会与 GPU 运行开销叠加。材料未给出工具链版本与编译环境，这意味着复现者必须自己决定是否缓存编译产物、是否固定 shape 集合以摊薄编译成本。一个工程判断是：把编译失败与运行失败在反馈通道里分开标注，让模型能区分“语法错”与“语义错”，否则两类错误混在同一段文本里，修正方向会被稀释。

三 · 运行与正确性 oracle：逐元素比对作为硬门槛

编译通过后，kernel 在 GPU 上运行，输出与参考实现逐元素比对。这是 Dr. Kernel 整个奖励结构的地基：正确性 oracle 判定通过与否，未通过则奖励为零。公式上，奖励被写成两段式：

$$r = \begin{cases} 0, & \text{编译失败或正确性未通过} \\ 1 + \alpha \cdot \min\left(\frac{t_{\text{base}}}{t_{\text{kernel}}}, S_{\max}\right), & \text{正确性通过} \end{cases}$$

这个式子里有三个工程决策点。第一，编译失败与数值不一致是否同权为零——材料把两者并列，但口径上必须明确，否则“语法错”和“算错”在训练信号里不可区分，模型无法学到“先保证对”的优先级。第二，逐元素比对的容差未在材料中给出，而容差直接决定 oracle 的严格程度：容差过松，错误 kernel 可能蒙混过关，性能奖励被投机获取；容差过紧，浮点归约顺序差异会把正确 kernel 判死，奖励稀疏到无法训练。第三，参考实现的来源与输入分布未说明，而 oracle 的可信度完全取决于这两者——同一 kernel 在不同输入分布下可能通过比对也可能失败。

代价在这里是双向的：正确性比对本身要跑参考实现，等于每个候选 kernel 都附带一次基线执行，显存与算力开销翻倍；而 oracle 判死一个 kernel 的代价是整轮奖励归零，若首轮通过率极低，训练信号会大面积稀疏。一个具体例子：归约类算子在浮点累加顺序上与 PyTorch 不同，逐元素比对在严格容差下会报不一致，模型收到的反馈是“数值错”，但它真正需要修的是累加策略而非索引——反馈文本若不携带失败模式（最大绝对误差、出错位置的比例），修正就会盲目。

四 · 测速与性能奖励：加速比、上限与可比性

只有通过正确性检查的 kernel 才进入测速环节，得到相对基线的加速比，折算为性能奖励。奖励用 min(t_base / t_kernel, S_max) 截断，作用是控制奖励尺度，防止个别极端加速比主导策略更新。这是一个务实的设计：若不设上限，一个偶然跑出数倍加速的 kernel 会在策略梯度里占据过大权重，把模型推向复制该个例而非学习通用优化手法。

但加速比作为奖励有一个前置条件常被忽略：基线实现与测速口径必须固定。不同任务的基线不同（有的对 cuBLAS，有的对朴素 PyTorch 实现），若不固定，跨任务的奖励不可比，多任务混合训练时策略会被“基线弱”的任务带偏。材料明确基线配置与上限取值未给出，这意味着复现者必须自己锁定基线版本、测速的 warmup 次数与计时方式（是否含 launch 开销、是否用 CUDA event），否则奖励信号在任务间漂移。

代价方面，测速要求每个通过正确性的 kernel 都跑多次以取稳定时延，GPU 时间随轮数累积；而“加速比过低”的反馈若只给一个数字，模型不知道瓶颈在分块、向量化还是共享内存，后续轮次的优化尝试就变成盲试。这正是执行反馈需要携带 profile 数据的理由——材料未说明是否使用 NCU/SASS 级反馈，若只用端到端时延，优化轮次的信息量是单比特的。

五 · 多轮 rollout：反馈回灌与闭环的稳定性代价

把上述四步串起来的是多轮 rollout：每轮的编译错误、运行失败与测速结果作为下一轮生成的上下文，形成生成—编译—运行—评测的闭环。输入是任务描述加累积的反馈历史，输出是下一轮源码；循环若干轮后汇总奖励更新策略。这个结构替代了单轮提示的一次性反馈，把“一次判死”变成“迭代修正”。

闭环的稳定性代价体现在三处。其一是上下文长度：每轮反馈文本（编译错误栈、失败模式、时延数字）都要进 prompt，轮数增加时上下文膨胀，token 成本与注意力稀释同时上升，模型可能遗忘首轮的语义约束。其二是错误累积：若某一轮的回灌文本误导了模型（例如把浮点容差问题描述成索引错误），后续轮次会在错误方向上越走越远，而奖励归零只告诉它“错了”，不告诉它“错在哪”。其三是训练稳定性：材料强调奖励设计与多轮 rollout 的稳定性，但具体 RL 算法、轮数与 token 预算未给出——这意味着“多轮”本身是一个需要标定的超参，轮数太少反馈不充分，轮数太多则 token 与编译运行开销压垮吞吐。

一个具体例子：某任务首轮编译失败（dtype 不匹配），第二轮修正后编译通过但数值不一致（边界 mask 写错），第三轮修正 mask 后通过正确性但加速比低于基线，第四轮尝试分块优化。四轮里模型依次处理了语法、语义、性能三类问题，每一类的反馈通道不同，若混在一起回灌，模型可能在同一轮里同时改三处而引入新错误。工程上的判断是：反馈要按类别结构化，让模型知道当前轮次该修哪一类。

六 · 防作弊约束与评测端的未定项

Dr. Kernel 的防作弊约束落在奖励结构上而非事后过滤：正确性未通过奖励为零，性能奖励设上限，两者共同压制“只追速度牺牲正确”的投机。但材料同时暴露了评测端的未定项——正确性 oracle 的容差、输入分布与防作弊细节未说明，基准任务数量、基线配置与指标数值未给出。这些不是细节，而是决定整套方法能否被复核的口径：没有容差就无法判断 oracle 是严是松，没有输入分布就无法判断正确性通过率是否被特定 shape 美化，没有基线配置就无法判断加速比是否可比。

从工程落地角度看，这套机制的可信度取决于三个可验证点：编译失败与数值不一致是否在奖励里同权为零；加速比的基线与测速口径是否在任务间固定；多轮反馈是否携带足以定位瓶颈的信息（失败模式、profile 数据）而非仅错误文本。三者任一缺失，闭环就会退化为“语法修补 + 盲试优化”，而这正是单轮提示时代的老问题换了件外衣。材料未给出消融实验，多轮 rollout、正确性门槛与性能奖励各自贡献无法分离——这意味着即便最终指标优于基线，也无法归因到哪一个机制在起作用，工程上复制这套配方时只能整体照搬，无法按成本裁剪。

最后落在一个具体机制上：奖励公式里的 S_max 截断与正确性零奖励是同一枚硬币的两面——前者限制性能信号的动态范围，后者把性能信号的门槛设在“算对”之后。这两条约束共同决定了策略更新的方向：模型先学会通过 oracle，再学会在通过者中提速。若 oracle 的容差与输入分布不公开，这个方向就是不可审计的；若多轮反馈只回灌错误文本，这个方向就会被语法修补主导。Dr. Kernel 把配方“做对”的主张，最终要由这两处口径的公开程度来兑现。

硬门槛之外的失效面：oracle 口径、基线漂移与多轮成本

正确性 oracle 是这套方案唯一的硬闸门，但闸门本身没有在材料里给出容差与输入分布，这决定了它的边界。逐元素比对若采用严格相等，浮点归约顺序变化即判失败，会把大量语义正确、仅累加次序不同的 Triton kernel 挡在门外，奖励恒为零、策略得不到任何梯度；若容差放得过宽，则错误 kernel 可以靠数值噪声蒙混过关，性能奖励重新暴露给奖励黑客。工程上应把 oracle 拆成两级：编译通过与形状/类型合法为一票否决，数值比对按 dtype 设定相对与绝对容差的双阈值，并把容差作为任务元数据随 rollout 一起下发，否则同一批次内不同任务的奖励尺度不可比。代价是显性的：每个候选 kernel 都要跑一次参考实现与逐元素比对，比对本身是访存密集型操作，其带宽开销往往与被测 kernel 同量级，正确性判定因此成为 rollout 吞吐的主要瓶颈之一。

性能奖励写成 1 + α·min(t_base/t_kernel, S_max) 时，奖励的可比性完全依赖基线实现与测速口径的固定。若基线随任务变化而未归一，同一加速比在不同算子上代表的工程量不同，策略会偏向那些基线写得差的简单任务；若测速未固定 warmup、重复次数与计时边界（是否含启动开销、是否含首次 JIT 编译），则同一 kernel 的两次测量可以给出差异明显的比值，奖励噪声直接转化为策略梯度方差。设单轮测速的计时噪声为 σ，加速比估计的相对误差约为 σ/t_kernel，当 kernel 时延接近计时分辨率时该项误差会压过真实优化收益，此时 min 截断只能限制上界、无法抑制下界的抖动。一个具体例子：对小 shape 的 elementwise 算子，启动开销占主导，任何分块或向量化改动都淹没在噪声里，模型在后续轮次学到的不是优化策略而是对测量抖动的过拟合。

多轮 rollout 的成本结构也需要在方法层面交代清楚。每增加一轮，就多一次生成 token、一次 Triton 编译、一次 GPU 运行与一次比对；编译是 CPU 侧的重开销，且失败编译同样消耗时间却不产生任何有效奖励信号，形成纯损耗轮次。若把编译失败与数值不一致同权置零，模型无法区分“语法不会写”与“语义算错了”两类失败，反馈文本里缺少 profile 数据时，优化轮次容易退化为语法修补而非分块、向量化与共享内存的实质调整。可用一张小表刻画单轮各阶段的输入输出与代价：

阶段输入输出主要代价
生成算子语义、上一轮错误文本Triton 源码与启动配置token 预算随轮数线性增长
编译源码编译错误或可执行产物CPU 编译时延，失败轮次零收益
运行比对产物、参考实现、容差通过/失败与失败模式访存带宽，判定吞吐瓶颈
测速通过比对的 kernel相对基线加速比计时噪声，需固定口径

由此得到的工程判断是：这套配方的有效性不在奖励公式本身，而在三个未被材料量化的接口——oracle 容差、基线固定方式、每轮反馈的信息含量。三者任一缺失，多轮闭环就会退化成昂贵的单轮提示加语法重试；而轮数增加带来的 token 与编译开销是确定的，收益却取决于反馈是否携带足以指导优化的结构化信息。缺少消融意味着无法分离多轮 rollout、正确性门槛与性能奖励各自的贡献，部署方在复现时只能把这三者当作一个整体黑盒接受，维护成本与端到端收益因此无法在方法层面预先核算。
