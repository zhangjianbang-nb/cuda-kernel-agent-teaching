一 · 基准构成与任务粒度：评测集到底长什么样

讨论 Dr. Kernel 的评测可信度，第一件事不是看它报了多少 speedup，而是问：评测集由哪些算子任务构成、每个任务以什么粒度被定义。论文面向 Triton kernel 生成，任务单元是「算子语义 + 输入分布 + 参考实现」三元组，模型产出的是 Triton kernel 源码与启动脚手架。摘要级材料明确承认算子类型与 shape 分布未给出、任务规模未给出，这意味着任何「正确率」与「加速比」都缺少分母。对工程读者而言，分母比分子更重要：一个只在少量规整 shape 上通过的 kernel，与一个在边界 shape、非对齐长度、极端 dtype 上仍正确的 kernel，是两种完全不同的能力，而前者更容易被奖励黑客利用。

可核查的口径要求把任务集拆成三层：语义层（算子数学定义，如归约轴、广播规则、累加精度）、形状层（每类算子的 shape 采样分布，含对齐与非对齐两类）、参考层（参考实现来源，是 PyTorch eager、torch.compile 还是手写 CUDA 基线）。三层缺一层，复现就无从谈起。论文材料在这三层上均留白，因此本部分只能给出「应当如何测量」的框架，而不能替它补数字。

代价在这里是统计功效：若任务数不足，正确率的置信区间会宽到无法区分两个策略。设通过任务数为 k、总任务数为 n，通过率的标准误近似为 √(p(1−p)/n)；当 n 只有几十时，两个相差几个百分点的策略在统计上不可分。这就是为什么「基准规模未给出」不是格式瑕疵，而是结论不可复核的根因。

$$\text{SE}(\hat p)=\sqrt{\frac{\hat p\,(1-\hat p)}{n}},\qquad \hat p=\frac{k}{n}$$

具体例子：一个归约算子若只在对齐到 128 元素的长度上评测，向量化与合并访存几乎必然生效，加速比虚高；一旦加入长度 1000 这类非对齐 shape，掩码与尾块处理会把加速比拉回。评测集若不含后者，faster rate 就是被 shape 分布「喂」出来的。

二 · 基线选择：加速比的分母决定一切

Dr. Kernel 的性能奖励定义为相对基线的加速比 t_base / t_kernel 并设上限 S_max。这个定义在数学上干净，在工程上却把全部不确定性压进了 t_base。基线可以是 PyTorch eager 算子、torch.compile 产物、cuBLAS/cuDNN 库调用，也可以是 Triton 官方教程实现。四者测出的加速比可以相差数倍，且论文材料只写「单轮提示基线（具体配置未给出）」，没有说明性能奖励的分母究竟是哪一种。

可核查口径必须固定三件事：基线实现版本、基线是否经过 warmup 与 autotune、基线是否在同一 GPU 同一时钟状态下测。若基线是 eager 且未做 CUDA graph 捕获，小算子的启动开销会主导计时，此时 kernel 只要减少 launch 次数就能「赢」，而这与计算效率无关。若基线是 cuBLAS，则加速比衡量的是「模型能否逼近厂商库」，难度陡增，faster rate 会显著下降。两种基线对应的能力画像完全不同，混用则数字不可比。

基线类型加速比含义主要失真来源
PyTorch eager相对解释器调度开销launch 开销、算子融合缺失
torch.compile相对编译器生成 kernel编译缓存命中、图切分策略
cuBLAS/cuDNN相对厂商手调库库版本、启发式选择
Triton 教程实现相对同语言参考写法教程实现本身未调优

性能代价体现在奖励尺度上：S_max 截断使得极端加速比不再主导策略更新，但也意味着「超过上限的部分」在梯度里不可见。若上限设得过低，模型在已经远超基线的任务上失去继续优化的激励；设得过高，个别异常样本会拉偏整批更新的方差。论文未给出上限取值，这一项就无法复核。

三 · 指标族：faster rate、speedup、geomean 与 fast_p 各自测什么

kernel 生成文献常用的指标不是单一数字，而是一族互补统计量，每个回答不同问题。faster rate 回答「有多少比例的通过任务比基线快」，是计数型指标，对分布形状不敏感但丢弃了幅度信息。speedup 是单任务比值，geomean 把所有任务的比值取几何平均，抑制长尾极值，适合跨任务汇总。fast_p 则是分位数口径：在通过任务中，加速比超过阈值 p 的比例，衡量「有多少任务达到了某个工程可接受的门槛」。

$$\text{geomean}=\exp\!\left(\frac{1}{N}\sum_{i=1}^{N}\ln \frac{t_{\text{base},i}}{t_{\text{kernel},i}}\right),\qquad \text{fast}_p=\frac{\#\{i: s_i \ge p\}}{N}$$

这四者不可互换。geomean 对「一个任务 10 倍、九个任务 0.9 倍」给出接近 1 的汇总值，掩盖了分布的双峰；faster rate 会把那一个 10 倍与九个 0.9 倍记为 10% 通过率，同样丢失幅度。工程判断应同时报告 faster rate 与 geomean，并用 fast_p 给出门槛视角。论文材料只称「取得优于基线的正确率与加速比」，未说明用的是哪一个汇总口径，因此无法判断它是否用 geomean 掩盖了长尾。

正确性代价在这里以「分母收缩」的形式出现：只有通过 oracle 的 kernel 才进入性能统计，因此 faster rate 的分母是「正确 kernel 数」而非「任务数」。若两个策略的正确通过率不同，它们的 faster rate 建立在不同分母上，直接比较会系统性偏袒「写得少但写得稳」的策略。可核查口径应同时报告「正确率 × 条件加速比」的联合分布，而不是两个边缘指标。

具体例子：十个任务中八个正确，其中六个快于基线，则 faster rate 报 6/8=75%；若另一策略十个任务全正确但只有五个快于基线，报 50%。单看 faster rate 前者更优，但后者的绝对正确产出更多，端到端收益可能更高。这正是需要联合口径的原因。

四 · 硬件、dtype 与 roofline：性能数字的物理前提

加速比是相对量，但它的物理上限由硬件决定。同一 kernel 在 H100 与 A100 上的可达成带宽与算力不同，roofline 拐点位置不同，因此「加速比 2 倍」在不同 GPU 上意味着不同的实现质量。论文材料未给出硬件型号，也未说明测速时的时钟策略（是否锁频、是否受功耗墙影响），这使得任何跨论文比较都失效。工程上应把硬件型号、SM 数量、显存带宽、是否 MIG 切片作为口径的一部分固定下来。

dtype 同样改变分母。fp32 与 bf16 的算力差距可达数量级，若基线用 fp32 而生成 kernel 内部降精度到 bf16，加速比里混入了精度偷换，而正确性 oracle 若容差过松就检测不到。可核查口径要求：基线 dtype 与生成 kernel dtype 必须一致，或显式声明允许的精度降级及其容差。论文未给出容差，这一条无法复核。

$$\text{SOL}=\max\!\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right),\qquad \text{speedup}_{\text{roof}}=\frac{t_{\text{base}}}{\text{SOL}}$$

roofline 给出的是「理论上还能快多少」的标尺。若生成 kernel 的实测时间已接近 SOL，则剩余加速空间受物理限制，继续优化只增加编译与 token 成本而无收益；若远离 SOL，则说明瓶颈在访存模式或占用率，多轮反馈应转向分块与共享内存而非语法修补。论文未说明是否使用 NCU/SASS 级 profile，因此无法判断其反馈闭环是否具备这种「瓶颈定位」能力——若只回灌错误文本，优化轮次容易退化为语法修补，这是材料中已点明的失败模式。

性能代价以测量噪声形式出现：小算子的单次计时受启动开销与缓存状态影响，方差可能超过真实加速比。可核查口径应报告重复次数、warmup 轮数、是否取中位数而非均值。这些参数论文均未给出。

五 · 隐藏 shape 与分布：泛化口径如何被污染

「隐藏 shape」在 kernel 评测里有两层含义。第一层是训练时不可见、评测时出现的 shape，用于检验模型是否写出对长度、对齐、广播都正确的通用 kernel，而非记住某个具体尺寸。第二层是输入数值分布，例如是否含 NaN/Inf、是否极端量级、归约轴长度是否触发数值不稳定。Dr. Kernel 的奖励以正确性为硬门槛，但材料承认输入分布与参考实现来源未说明、容差未给出，因此「正确」二字的边界是模糊的。

隐藏 shape 的处理直接决定 faster rate 的可比性。若评测集与训练集共享同一 shape 采样器，模型可以通过记忆尺寸相关的分块参数获得虚高加速比；若评测集使用不同分布，则泛化能力才被真正测量。可核查口径应声明训练/评测 shape 是否同分布，并给出至少一个跨分布迁移的对照。

数值分布的影响同样具体：一个 softmax kernel 在输入含大幅值时若未做减最大值处理，会在 fp16 下溢出，而容差较松的 oracle 可能放过。正确性 oracle 的容差设计因此是评测可信度的核心，论文未给出细节，这是材料自陈的局限之一。工程判断是：容差应按 dtype 的机器精度与算子条件数设定，而非全局一个常数。

代价体现在评测成本上：隐藏 shape 越多，每个任务的编译与运行次数越多，评测端 GPU 时间线性增长；若多轮 rollout 每轮都对全部 shape 重测，token 与编译开销会迅速累积，而论文未量化这部分成本。

六 · 可核查的测量口径清单

把上述讨论收敛成一份可执行的测量口径，是本部分对工程读者的直接交付。任何声称在 Triton kernel 生成上取得加速比的工作，都应能回答下列问题；Dr. Kernel 的摘要级材料在多数条目上留白，这正是其数字不可复核的原因。

  • 任务集：算子清单、每类算子的 shape 采样分布、对齐与非对齐比例、任务总数 n。
  • 基线：实现来源与版本、是否 autotune、是否 CUDA graph、与生成 kernel 的 dtype 是否一致。
  • 硬件：GPU 型号、SM 数、显存带宽、是否锁频、是否独占。
  • 计时：warmup 轮数、重复次数、取中位数还是均值、是否含 launch 开销。
  • 正确性：参考实现来源、逐元素比对容差、NaN/Inf 处理、隐藏 shape 是否与训练同分布。
  • 指标：faster rate 的分母（正确 kernel 数还是任务数）、geomean 的截断方式、fast_p 的 p 取值、S_max 上限。
  • 成本：每任务平均 rollout 轮数、token 消耗、编译与运行 GPU 时间。

这份清单的价值在于把「加速比」从一个孤立数字还原为一组前提。工程判断落在一个具体机制上：性能奖励的分子是生成 kernel 的实测时间，分母是基线时间，而两者都必须在同一硬件、同一 dtype、同一计时口径下取得，否则奖励信号在策略更新中引入的是噪声而非梯度。Dr. Kernel 以正确性为硬门槛的设计在方向上正确，但门槛之外的测量口径若不被固定，多轮 RL 学到的可能只是对某个未声明基线的过拟合。

口径边界：加速比奖励在什么条件下失效

Dr. Kernel 的性能奖励建立在相对基线的加速比上，这一口径的隐含前提是：同一任务内基线实现与测速方式固定，且不同任务之间的奖励尺度可比。但材料明确未给出基线配置与上限取值，于是奖励函数中 min(t_base/t_kernel, S_max) 的两端都处于未定义状态。若基线是朴素 PyTorch 实现，加速比会系统性偏大；若基线是已调优的 Triton 参考实现，同一 kernel 的加速比可能落到 1 附近。截断上限 S_max 的作用是压制极端值主导策略更新，但它同时把“从 1.2 倍提升到 3 倍”和“从 3 倍提升到 10 倍”压缩成同一奖励，梯度信号在高端被削平。工程上可核查的做法是把基线版本、编译选项、warmup 次数与计时方法（CUDA event 还是 wall clock、是否含 launch 开销）一并写入任务元数据，否则跨任务的 geomean 与 fast_p 指标只是同一批不可比数字的再平均。

正确性 oracle 的容差是另一处口径缺口。逐元素比对在浮点归约类算子上对累加顺序敏感，容差取绝对误差还是相对误差、是否按 dtype 分档，直接决定哪些 kernel 被判通过。容差过松会让数值错误的 kernel 拿到性能奖励，构成奖励黑客的入口；容差过紧则把合法的重排优化判为失败，奖励稀疏问题加剧。一个可操作的折中是分层容差：fp32 用相对误差加少量绝对下限，fp16/bf16 按 ULP 缩放，并在任务描述中显式声明，使 oracle 判定可复现。代价是每个任务需要额外的参考实现校验与容差标定工作，属于评测端的一次性人力开销，而非训练时延。

隐藏 shape 与输入分布的处理决定了加速比能否外推。若训练任务只覆盖固定 shape，模型可能学到对该 shape 的分块参数硬编码，评测时换 shape 即失效。材料未说明 shape 分布与是否留有隐藏集，因此无法判断论文报告的加速比是分布内还是分布外结果。可核查的测量口径应至少包含：每个任务给出 shape 采样范围与分布类型（均匀、幂律、边界值），评测集与训练集在 shape 上做不相交划分，并分别报告分布内与分布外的 faster rate。多轮 rollout 的 token 成本随轮数线性增长，而编译与运行开销按任务数乘以轮数计，若隐藏集规模不足，统计功效无法支撑 fast_p 这类尾部指标。
