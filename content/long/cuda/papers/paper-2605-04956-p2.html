一 · 基准构成与分类口径：176 题、15 类，类别是评测的第一等公民

KernelBenchX 的基准体量是 176 个任务、15 个类别。这个数字本身不构成评测能力，真正决定口径的是它的组织方式：题目不是按算子名平铺，而是按任务结构分组成类，评测结果先按类别聚合，再跨类别汇总。论文的核心论点正是从这一组织方式里长出来的——类别对语义正确性的解释力接近方法设计的三倍（解释偏差 9.4% 对 3.3%）。这意味着任何一份只报告全局平均分的评测表，都在把类别间的巨大差异平均掉，从而掩盖了“能力在哪里断裂”这个论文真正要回答的问题。

对做评测的工程团队而言，这带来一个直接的接口要求：提交的结果必须携带类别标签，且类别划分要与论文一致，否则跨报告不可比。类别标签不是元数据装饰，它是统计单元。若把 15 类压成“算子类/非算子类”两档，9.4% 的解释偏差就会被稀释到无法复现，Fusion 类 72% 的全方法失败率也会被 Math 类的一致通过所掩盖。可核查的口径是：每个候选 kernel 记录 (task_id, category, dtype, shape_set, baseline_id) 五元组，缺一不可。

代价在这里体现为评测预算。按类别分层报告意味着每类都要有足够样本量才能给出稳定的类别级正确率，176 题摊到 15 类，部分类别样本偏少，类别级置信区间会变宽。这不是可以靠增加候选数量解决的——增加候选只降低方法侧方差，不降低类别侧方差。工程判断是：类别级结论只用于定性排序与失败模式定位，定量加速比仍以任务级配对比较为准。

一个具体例子：Fusion 类任务要求把多个算子融合进单个 Triton kernel，正确性检查必须覆盖融合后中间结果的数值一致性，而不只是最终输出。若 oracle 只比对最终张量，融合 kernel 丢掉一个中间归一化步骤仍可能通过检查，这类“假正确”会直接污染类别级正确率。因此 Fusion 类的正确性 oracle 必须逐中间量比对，或至少在参考实现里保留可观测的中间张量。

二 · 基线与 dtype：PyTorch eager、torch.compile 与库实现的三层参照

论文的基线口径是三层：PyTorch eager、torch.compile、以及论文指定的库实现。三层不是冗余，它们回答不同问题。eager 是“LLM 生成的 kernel 是否值得替换朴素 PyTorch”的下限参照；torch.compile 是“是否值得替换编译器自动融合”的中线参照；库实现（如 cuBLAS 级别的厂商 kernel）是“是否接近人类手写上限”的上限参照。加速比的分母取哪一层，直接决定报告里 46.6% 这个数字的含义——论文明确指出 46.6% 的正确 kernel 慢于 PyTorch eager 基线，即连下限都没跨过。

dtype 是第二个不可比的来源。Triton kernel 的数值行为对 dtype 极其敏感：fp32 累加与 tf32 累加在矩阵乘类任务上会给出不同的误差界，bf16 输入的归约顺序改变会放大舍入误差。若基线未开 TF32 而候选 kernel 走了 TF32 路径，加速比会被系统性高估；反之若候选 kernel 在 fp32 下严格累加而基线用了 TF32，候选会被不公平地判慢。可核查口径要求：基线与候选在同一 dtype、同一 TF32/FP32 累加策略下测量，并在结果里显式记录该策略。论文摘要未给出全部 dtype 配置，因此跨报告引用其加速比时必须标注“dtype 策略未核验”。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

上式是 fast-p 型指标的一般形式：τ 是加速比阈值，s_i 是任务 i 上基线时延与候选时延之比。这个指标只关心“是否跨过阈值”，不关心跨过多少，因此对长尾加速比不敏感——一个 1.01× 和一个 10× 在 τ=1.0 下贡献相同。代价是它无法区分“勉强通过”与“显著优于基线”，而后者恰恰是生产部署关心的。工程上应与 geomean 加速比配对使用：fast-p 衡量覆盖率，geomean 衡量典型收益，两者一起才能防止“大量微增益 + 少数巨大回退”被平均值掩盖。

具体例子：一个 Reduction 类任务，基线 eager 在 fp32 下做两遍归约，候选 Triton kernel 用单遍在线归约并把累加器降到 bf16。若测量时未固定累加精度，候选可能因更少的显存往返而显示 2× 以上加速，但正确性检查在长序列上会因 bf16 累加溢出而失败。此时正确性门先于性能门生效，加速比数字作废——这正是“正确性不蕴含效率”的反向约束：效率数字只有在正确性门通过后才有意义。

三 · 指标族：faster rate、speedup、geomean、fast-p 与 roofline 的分工

论文涉及的指标族可以按回答的问题分层。faster rate 回答“有多少比例的候选比基线快”，是覆盖率指标；speedup 是任务级配对比值，是效应量指标；geomean 是对数域平均，抗长尾；fast-p 是带阈值的覆盖率，用于设定工程门槛；roofline 回答“距离硬件上限还有多远”，是效率上界指标。这五个指标不能互相替代，混用会产生不可比的报告。

geomean 的选择有明确理由：加速比是比值，算术平均会被少数超大加速比主导，几何平均在对数域等权，符合“每个任务同等重要”的评测伦理。代价是 geomean 对慢于基线的任务惩罚偏软——一个 0.5× 的任务与一个 2× 的任务在 log 域对称，但工程上 0.5× 意味着部署回退，2× 只是收益。因此报告 geomean 时必须同时给出慢于基线的任务占比，论文给出的 46.6% 正是这个补充量。

roofline 指标的作用是把“快”与“接近硬件极限”分开。一个 kernel 相对 eager 有 3× 加速，但若其算术强度落在 memory-bound 区间而实测带宽只达到峰值的四成，它仍然远离 roofline，后续优化空间在访存而非计算。论文的跨硬件加速比方差达到 21.4×，这一数字本身就说明单硬件上的 speedup 不能外推：同一 kernel 在不同显存带宽与 SM 配置下，roofline 位置会移动，加速比随之漂移。可核查口径是：roofline 分析必须绑定具体硬件的峰值带宽与峰值算力，且报告实测值占峰值的比例，而非只报绝对时延。

指标回答的问题主要代价典型误用
faster rate多少任务跨过基线不区分增益幅度与 geomean 混报为“平均加速”
speedup单任务效应量受基线选择支配换基线后跨报告直接比较
geomean典型收益对回退惩罚偏软不附慢于基线的占比
fast-p工程门槛覆盖率阈值 τ 主观τ 不写明即引用
roofline距硬件上限需绑定硬件峰值跨硬件外推

具体例子：Math 类任务在五种方法下被一致解出，正确率高但加速比分布窄——这类任务的 roofline 往往落在 compute-bound 区，Triton 生成的 kernel 若未做指令级流水，实测算力占比低，speedup 停留在 1× 附近。此时 fast-p 在 τ=1.0 下接近全通过，但 geomean 接近 1，两个指标共同说明“能写对，但没写出效率”。这正是论文第二条发现的量化形态：迭代精修提升正确率而不提升性能。

四 · 哪些数字不可比：基线强度、shape 特化与跨硬件方差

不可比的第一个来源是基线强度。若某份报告用未开 TF32 的 eager 作分母，而另一份用 torch.compile 作分母，两者的 speedup 不在同一标尺上。论文明确把三层基线并列，意味着任何引用其加速比的下游工作都必须声明分母层级。更隐蔽的是库实现的选择：同一个矩阵乘，调用不同版本的厂商库会给出不同的分母时延，而论文未在摘要级给出库版本，因此跨报告引用库基线加速比属于不可核验区间。

第二个来源是 shape 特化。LLM 生成的 Triton kernel 常把 block size、num_warps、grid 形状硬编码到针对评测输入调优的值。这在固定 shape 上给出漂亮加速比，但一旦生产输入分布偏移——序列长度变化、batch 变小、维度不是 2 的幂——特化 kernel 会退化甚至编译失败。论文的隐藏 shape/分布处理正是针对这一点：评测输入分布按论文口径给定，候选不得窥探测试 shape。可核查口径要求报告区分“调优集 shape”与“留出集 shape”两组数字，只报前者等于报训练集精度。

第三个来源是跨硬件方差。论文给出的 21.4× 跨硬件加速比方差是一个量级声明：同一候选在不同 GPU 上的相对收益可以差出一个数量级以上。这不是测量噪声，而是 roofline 位置移动的结构性结果。因此“在某卡上 2×”不能写成“加速 2×”，必须写成“在硬件 H、基线 B、dtype D 下 2×”。工程判断是：跨硬件迁移结论只能定性，定量结论必须绑定硬件型号与显存配置。

具体例子：一个 Fusion 类候选在留出 shape 上因 block size 不整除而触发边界分支，实测时延翻倍，speedup 从 1.8× 跌到 0.9×。若报告只给调优集数字，这个回退完全不可见。代价是评测必须跑两组 shape，测量时延预算翻倍；收益是离线分数与生产表现之间的落差被提前暴露。

五 · 隐藏 shape 与分布：正确性 oracle 与性能门的分离

隐藏输入分布的处理不是“多跑几个 shape”，而是把正确性 oracle 与性能门拆成两道独立关卡。正确性 oracle 在留出分布上做逐元素或逐中间量比对，容差按 dtype 设定；性能门只在正确性通过的任务上测量时延。这个顺序不可颠倒：先测时延再补正确性，会让“快但错”的候选进入加速比统计，虚高正确率与虚高加速比同时发生。

论文第一条发现给出了这一设计的经验依据：72% 的 Fusion 任务在五种方法下全部失败，而 Math 类被一致解出。若 oracle 只做最终张量比对，Fusion 的失败率会被低估，因为部分错误融合在最终输出上数值接近；若 oracle 在隐藏分布上做中间量比对，失败率才真实。代价是 oracle 实现复杂度上升：参考实现必须暴露中间张量，或提供可分解的数值检查路径，这对基准维护者是持续成本。

隐藏分布还约束了 reward 设计。若评测反馈把“编译通过”当作奖励信号，候选会向可编译但语义错误的形态漂移；论文第二条发现里 GEAK 迭代的编译率从 52.3% 升到 68.8% 而平均加速比从 1.58× 降到 1.44×，正是这种漂移的量化形态——新救回的 kernel 持续弱于一直正确的 kernel（1.16× 对更高值）。这说明编译率与正确率、加速比必须作为三个独立指标报告，任何一个都不能替代另一个。

$$\text{pass}_i=\mathbb{1}\big[\lVert y_i-\hat y_i\rVert_\infty\le\epsilon(\text{dtype})\big]\ \wedge\ \mathbb{1}\big[\text{compile}_i\big]$$

上式的含义是：任务 i 通过，要求编译成功且隐藏分布上的最大逐元素误差在 dtype 相关容差内。性能门在此之后再测时延。代价是每个任务要跑留出 shape 的正确性检查，编译时间与运行时间都计入评测预算；对 176 题、多候选、多方法的组合，评测总时长会成为实际瓶颈，因此工程上常做分层抽样：全量跑正确性，性能只在通过子集上测。

具体例子：一个 Reduction 候选在调优 shape 上误差在容差内，但在留出分布的长序列上因累加顺序改变超出容差。正确性门拦下它，性能门不执行，加速比不进入统计。若没有隐藏分布，这个候选会以 1.5× 的假加速进入 geomean，污染整个类别结论。

六 · 可核查的测量口径清单：把报告写成可复现的实验记录

把上述约束落成一份可核查口径，需要每条结果携带足够的上下文，使第三方能在不读论文全文的情况下判断可比性。最小集合包括：硬件型号与显存配置、基线层级与库版本、dtype 与累加策略、调优集与留出集 shape 清单、正确性容差、时延测量方法（是否含编译、是否取中位数、warmup 次数）、以及类别标签。缺任一项，该数字只能作为定性参考。

时延测量本身有代价取舍。取中位数抗离群但丢失尾部信息；取最小值反映上限但易被缓存效应污染；含编译时间则反映端到端部署成本但放大 Triton 的 JIT 开销。论文口径未在摘要级给出测量细节，因此引用其 speedup 时应标注“测量方法未核验”。工程判断是：报告同时给冷启动（含编译）与稳态两组时延，前者对应生产首次调用，后者对应稳定吞吐。

跨报告可比性的最后一道闸是失败模式归档。论文点名的三类风险——基线未开 TF32 导致加速比高估、shape 特化在隐藏分布上崩塌、reward hacking 与 fallback 让正确率虚高——都应在结果表里以显式字段标注，而不是留在脚注。一个候选若在留出分布上回退到 eager 路径，它的“正确”是 fallback 的正确，不是 kernel 的正确，两者必须分开计数。

具体例子：某候选在 176 题中通过 120 题正确性门，其中 30 题实际走了 fallback 路径。若报告只写“正确率 68%”，读者无法区分真实 kernel 正确率与 fallback 掩盖率。可核查写法是拆成三行：编译成功率、真实 kernel 正确率、fallback 占比，再附类别分解。代价是报告字段变多、维护成本上升；收益是任何下游引用都能定位到具体机制，而不是引用一个被平均掉的全局数字。
