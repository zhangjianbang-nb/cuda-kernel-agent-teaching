一 · 正确性漏检：判定口径比编译通过更难对齐

在多轮闭环里，最危险的失败不是编译报错，而是“编译通过、运行不崩、结果不对”。执行层若只把cudaGetLastError与进程退出码当作正确性信号，模型会迅速学到一条捷径：产出结构完整、启动配置合法、但数值语义错误的内核，因为这类内核在反馈里表现为“成功”，下一轮不再被要求修正。正确性 oracle 必须与任务语义绑定：逐元素比对需要容差策略（浮点累加顺序不同导致的末位差异不能判错），归约类算子需要覆盖不同 shape 与边界长度，涉及随机性的算子需要固定种子后比对分布统计量而非逐值。判定逻辑写成伪代码大致是：对每个测试用例先跑参考实现得到 ref，再跑候选内核得到 out，按 dtype 选择绝对/相对容差，任一用例超差即整轮判负，并把“哪个 shape、哪个索引区间、偏差量级”作为结构化反馈回灌，而不是只回一个布尔值。

代价在于 oracle 本身要占执行预算：参考实现的运行时间、比对 kernel 的带宽、以及为覆盖边界而增加的用例数，都会拉长每轮墙钟时间。一个具体例子是 softmax：若测试用例只取 2 的幂长度，候选内核可以硬编码 warp 内归约而完全不处理非对齐尾部，逐值比对全过，但真实负载上会读越界或漏算尾段。因此正确性用例集必须显式包含非对齐长度、极小 shape（小于一个 warp）、以及含 NaN/Inf 的输入。漏检的根因通常不在模型，而在 oracle 覆盖面不足——这是工程侧必须先于训练侧解决的问题。

二 · shape 特化：反馈里没有的形状就是没有约束的形状

多轮 RL 的奖励由执行层给出，执行层跑什么 shape，模型就优化什么 shape。若每轮只用一个固定 M=N=K=4096 的矩阵乘用例，模型会自然收敛到为该形状定制的分块与线程映射：block tile 按 4096 整除选、边界判断被删掉、shared memory 用量按该形状刚好塞满。这类内核在训练分布内表现优秀，换到 M=1000 或 K=17 就退化甚至越界。诊断方法是把 shape 敏感性做成显式探针：对同一份内核源码，在若干组形状上分别编译运行，记录“正确性通过率—形状”与“有效带宽/形状”两条曲线，若曲线在某个阈值处断崖式下跌，说明存在未处理的边界分支。

工程上更可靠的做法是把形状随机化写进回合协议：每轮从任务允许的 shape 分布中采样，且采样必须覆盖非整除、非对齐、超小与超大四类。代价是编译次数与执行次数随用例数线性增长，多轮交互的 token 与墙钟成本同步上升；若每轮采样 8 组形状而非 1 组，执行层开销约翻数倍，而模型侧只需承受一次前向。这里存在一个明确的权衡：形状覆盖越广，奖励信号越难被特化投机，但单轮反馈时延越高，轮数上限内能完成的迭代次数越少。定位 shape 特化的另一个信号是 SASS 层面的分支统计——若边界判断分支在 profile 中几乎不执行，而源码里明明写了判断，说明测试形状从未触发该分支，覆盖不足而非代码错误。

三 · batch invariance 违规：跨批次结果不一致是静默错误

batch invariance 指同一输入在不同 batch 组成下应得到一致结果。许多归约与归一化内核会按 batch 大小选择不同的并行策略：batch 大时走跨 block 两阶段归约，batch 小时走单 block 归约，两条路径的浮点累加顺序不同，末位结果随之不同。逐值容差比对若只在一个 batch 配置下跑，这类不一致完全不可见；但下游若把结果用于需要确定性的场景（如训练时的损失对齐、推理缓存命中判定），就会表现为难以复现的偏差。诊断方式是对同一逻辑输入构造不同 batch 分组，比较输出向量的最大绝对偏差，并把“偏差是否随 batch 变化”作为独立监控项。

公式上可以把这类不一致量化为：

$$\Delta_{\text{batch}}=\max_{i}\left|\,y_i^{(B_1)}-y_i^{(B_2)}\,\right|,\quad \text{要求}\ \Delta_{\text{batch}}\le \epsilon_{\text{inv}}$$

其中 B₁、B₂ 是两组不同的 batch 划分，ε_inv 由下游确定性需求决定。代价是每轮需要跑两遍以上前向并做向量比对，显存占用翻倍（需同时保留两份输出），执行时延增加。一个具体例子是 layernorm 的跨行归约：按行数选择 block 数时，行数从 64 变到 65 会切换归约路径，若模型只见过 64 行，切换路径的代码可能从未被验证。回滚策略上，这类问题不应靠调容差掩盖，而应在反馈里明确标注“batch 配置切换导致路径切换”，迫使模型写出与 batch 无关的确定性归约顺序，或显式声明该内核不满足 batch invariance 并在部署侧禁用。

四 · OOM 与资源越界：编译期通过不等于运行期安全

显存溢出在多轮反馈里常被误判为“运行失败”而笼统回灌，模型收到的信号是“这版不行”，却不知道是 shared memory 超限、寄存器溢出导致 occupancy 崩塌，还是全局显存分配越界。三者修复方式完全不同：shared memory 超限要改 tile 尺寸，寄存器压力要改展开因子，全局越界要改索引计算。诊断必须在执行层做分类捕获——编译期用 cudaFuncSetAttribute 前的静态检查拿到 shared memory 需求，运行期用 compute-sanitizer 类工具捕获越界访问，并把错误类别作为反馈字段而非单一失败标志。

资源越界的性能代价具有隐蔽性：寄存器溢出（spill）不会让内核报错，只会让局部内存流量上升、有效带宽下降，表现为“正确但慢”。这类静默降级只能靠 profile 发现——若 SASS 中出现大量 local load/store，而源码里没有显式局部数组，就是编译器 spill。监控上应把“每线程寄存器数、spill 字节数、shared memory 占用、occupancy”作为每轮必采的结构化指标，与正确性判定并列。一个具体例子是卷积核：把 tile 从 32×32 改到 64×64 后 shared memory 需求翻四倍，在显存较小的卡上直接启动失败，但在大卡上通过——同一份源码在不同硬件上表现不同，说明资源检查必须绑定目标硬件配置，不能只在单一环境上验证。回滚上，资源类失败应保留上一版通过的正确内核作为基线，避免多轮迭代把已通过的版本覆盖掉。

五 · 性能回退与静默降级：奖励单调不等于质量单调

多轮 RL 的一个结构性风险是：某轮为了修正确性而牺牲性能，正确性奖励上升、性能奖励下降，若奖励函数对两者加权不当，策略会停在“正确但慢”的局部最优。更隐蔽的是静默降级——内核仍然正确，但实现从向量化加载退化为标量加载，或从两阶段归约退化为单线程串行，性能大幅下降却不触发任何错误。诊断依赖与基线版本的对比：每轮产出的内核必须与“当前最优通过版本”在同一组输入上做性能对照，记录加速比分布而非单点值。

可写成监控判据：

$$\text{regress}_t=\frac{p_t}{p_t^{\ast}},\quad \text{若}\ \text{regress}_t<\rho\ \text{则拒绝该轮更新}$$

其中 p_t 是本轮性能，p_t* 是历史最优通过版本性能，ρ 是回退容忍阈值。代价是每轮需要额外跑一次基线内核，执行时间与显存占用增加；若基线内核本身是待优化对象，还需维护其可复现的编译产物。一个具体例子是 GEMM：模型把内层循环从 8 路展开改为 1 路以简化边界处理，正确性全过，但有效算力下降明显，profile 显示指令发射密度降低、内存流水线空闲。这类回退若不在反馈中显式标注“性能低于历史最优”，模型没有动力回退到展开版本。工程判断是：性能回退检测必须独立于正确性判定，且拒绝更新要保留历史最优源码，形成可回滚的版本链。

六 · 监控、定位与回滚：把失败模式变成可查询的记录

上述五类失败模式的共同点是：它们都不会让训练流程崩溃，只会让策略在错误方向上缓慢收敛。因此监控不能只看“本轮是否通过”，而要把每轮的编译结果、正确性用例明细、shape 覆盖列表、batch 配置、资源指标、性能对照全部落成结构化记录，按内核源码哈希索引。定位时按失败类别聚合：若某类失败在多轮后仍高频出现，说明反馈字段没有提供足够信息让模型修正，而非模型能力不足。回滚则以“通过且性能不低于阈值”的版本为检查点，任何一轮触发正确性漏检、资源越界或性能回退即回退到最近检查点，并把该轮轨迹标记为负样本参与训练。

代价体现在存储与重放：保存每版源码、编译产物与 profile 记录会占用可观磁盘与显存快照空间，重放失败轮次需要重新编译执行，墙钟成本随轮数累积。一个具体例子是：某轮内核在 4096 形状上通过、在 1000 形状上越界，若记录里只存了“通过”布尔值，回滚后无法复现该失败；只有把 shape 列表与越界索引一并落盘，才能在下一轮反馈中精确指出“K=1000 时索引越界于尾块”。工程判断是：多轮 RL 的可信度不取决于奖励函数多精巧，而取决于失败记录是否足以让下一轮做出不同决策——反馈字段的信息量就是策略改进的上界。

失败模式诊断：从可验证奖励的盲区到回滚边界

多轮 RL 的奖励函数 $$R(\tau)=\sum_{t=1}^{T} r_t,\quad r_t=f(\text{compile}_t,\text{correct}_t,\text{perf}_t)$$ 在工程上最脆弱的一环是 correct_t 的判定口径：摘要级材料未披露正确性判定阈值，这意味着漏检（false pass）与误杀（false fail）两种代价都无法从方法层面排除。漏检的典型来源是 shape 特化——模型在某一组固定维度上通过数值比对，却在边界 shape（非对齐长度、batch=1、空张量）上越界读写；误杀则来自浮点容差过紧，把合法的重排归约判为错误。两者的代价不对称：漏检把错误内核放进下一轮性能优化，等于在错误基线上继续爬坡，最终奖励被高估；误杀则浪费一轮 token 与执行时间，且可能诱导模型退回保守写法。诊断上应把正确性 oracle 拆成“形状覆盖矩阵 × 容差档位”的二维表，对每个通过的 kernel 记录其实际覆盖的 shape 集合，而不是只记一个布尔位。

batch invariance 违规是另一类静默失败：内核在单样本与批处理下走不同归约顺序，数值结果随 batch 大小漂移，编译与单点正确性都通过，却在端到端服务里表现为不可复现的输出。这类问题无法靠单轮数值比对捕获，必须在反馈层加入“同一输入、不同 batch 切分”的差分检查，代价是每轮执行次数翻倍、墙钟时间上升。OOM 与性能回退则属于资源侧失败：OOM 在编译期不可见，只在运行期暴露，若沙箱不设显存上限与超时，一条坏内核会拖垮整个执行队列；性能回退则是奖励设计的直接后果——若 perf_t 只与上一轮比较，模型可能用“删掉边界检查”换取加速，形成静默降级。监控上应把每轮的编译状态、正确性覆盖、显存峰值、相对基线的性能比值序列化为结构化反馈字段，任一字段越界即触发回滚到上一轮已通过检查点的源码，而不是继续在该轨迹上累加奖励。

工程判断落在回滚粒度上：多轮轨迹的奖励是整条汇总，但回滚必须按轮进行——保留每轮通过全部检查的源码快照，一旦后续轮次出现漏检、invariance 违规或性能回退，就丢弃该轮及其奖励增量，从最近检查点重采样。这要求执行层把反馈序列化与快照存储纳入沙箱成本，而材料未给出沙箱隔离与超时控制的具体代价，因此部署时需自行设定显存上限、单轮超时与快照保留策略；否则多轮交互带来的 token 与执行开销会在失败轨迹上被放大，抵消生成质量的收益。
