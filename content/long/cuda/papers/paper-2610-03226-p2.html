一 · 指导注入的失效模式：从“抄结构”到“抄不动”

D2K-Bench 的指导分三层：L1 高层算法洞察、L2 数据流设计、L3 低层优化技巧，且层间存在依赖。这个分层本身就是失效诊断的坐标系。最常见的失效不是“给了指导还写错”，而是指导被翻译成了形状而非机制：agent 把 L2 的数据流描述照搬成固定的 tile 尺寸、固定的 shared memory 布局，却没有把“为什么这个数据流能减少 global memory 往返”这一因果链落到自己的循环结构里。结果是代码在基准 workload 上跑得动，换一个 shape 就退化。判据很直接：把 L2 指导里出现的每个常量（tile 大小、stage 数、warp 划分）当作变量扫一遍，若性能曲线在指导给出的取值附近出现尖峰而非平台，说明 agent 学到的是常量而非机制。这类失效在 L3 上更隐蔽——L3 技巧（如 swizzle、双缓冲、向量化宽度）往往与 L2 数据流强耦合，agent 若在 L2 已偏离，L3 的“技巧”会变成无效装饰，甚至引入额外寄存器压力拖低 occupancy。

第二种失效是层间依赖被忽略。L1 的算法洞察若要求改变归约顺序，L2 的数据流就必须重排，L3 的向量化宽度也随之改变。agent 常见做法是三层各自局部最优、拼在一起互相拆台：L1 换了分块策略，L2 仍按旧的分块写 shared memory 索引，L3 仍按旧的连续性做向量化，编译能过、正确性也能过（因为索引自洽），但带宽利用率掉一个档次。检测手段是逐层回退：保留 L1+L2 去掉 L3、保留 L1 去掉 L2+L3，看性能落差是否单调。若去掉 L3 反而更快，说明 L3 与上层不匹配，agent 是在给一个已经错位的结构打补丁。

第三种失效与 350-turn 预算直接相关。预算耗尽时的“最后一次编辑”往往是破坏性的：agent 在接近上限时倾向于做大幅改写而非微调，因为小幅改动已无收益信号。若最后一次改写恰好通过了正确性门但性能未复测，就会把一次退化写进最终提交。工程上应对办法是把预算切成“探索段”和“收敛段”，收敛段只允许单点参数改动并要求每次改动都复测，代价是吞吐下降——同样的 350 turn 能覆盖的候选数减少，但换来的是最终提交的可信度。

$$\text{gap}_{\text{layer}}=\frac{T_{\text{full}}}{T_{\text{full}\setminus\text{layer}}}-1,\qquad \text{若 }\text{gap}_{L3}<0\text{ 则 }L3\text{ 与上层失配}$$

具体例子：一个以 L1“分块归约减少原子操作”为洞察的任务，agent 若把 L2 写成每块一次 atomicAdd、L3 又加上 shared memory 双缓冲，双缓冲的同步开销会吃掉原子操作减少带来的收益，gap_{L3} 为负——这正是“技巧堆叠”而非“机制迁移”的典型信号。

二 · 适用边界：诊断基准能回答什么、不能回答什么

D2K-Bench 的 26 任务、85 workload 与 130 个 model-task 对的配对设计，回答的是“指导是否被有效翻译”这一因果问题，而不是“这个 agent 在生产上能不能用”。配对运行共享任务描述、workload、工具、硬件与 350-turn 预算，唯一变量是有无指导，因此 93.1%→98.5% 的正确率提升与 Performance Score 1.46→1.95 的抬升可以归因于指导，而非采样噪声或预算差异。但这也意味着它的结论被牢牢钉在 B200、给定输入分布、给定基线口径上。跨硬件迁移的第一道坎是带宽/算力比变化：在 B200 上成立的 tile 尺寸与 stage 数，换到带宽更紧或 SM 数更少的卡上，roofline 拐点会移动，指导里隐含的最优点随之漂移。基准不会告诉你这个漂移量，因为它的 workload 分布是固定的。

第二道坎是dtype 与数值口径。正确性门若只在单一 dtype 上通过，换 fp16/bf16/fp8 后归约顺序、累加精度、向量化对齐都会变，agent 写出的 kernel 可能仍“正确”但性能大幅退化，或者反过来为了通过正确性门引入了额外同步。基准的 98.5% 正确率是在其口径下测的，不能外推为“该 agent 在混合精度流水线里可靠”。第三道坎是基线强度：若基线未开 TF32、未用最强库实现，加速比会被系统性高估；D2K-Bench 用统一基线缓解了这一点，但读者若把它的 Performance Score 直接搬到自己项目的基线口径上比较，就会得到不可比的数。工程判断是：把 D2K-Bench 当作指导翻译效率的对照实验，而不是绝对性能排行榜。

还有一个边界是任务粒度。26 个任务覆盖的是可被专家写出指导的算子，指导本身的存在是前提。对于尚无成熟设计洞察的新算子（例如新注意力变体、稀疏格式尚无公认数据流），L1 指导无从给出，基准的配对设计退化为“无指导 vs 无指导”，此时它测的是 agent 的独立设计能力——论文的 complementary assessment 正是为此设置的旁路，但它不是主口径。把主口径的结论套到“无指导可给”的场景上，是把诊断工具当成了能力上限。

三 · 与相邻工作的差别：诊断口径 vs 生成能力 vs 优化流水线

相邻工作大致分三类，D2K-Bench 与它们的差别不在“谁更强”，而在测量对象。第一类是生成能力基准（KernelBench 系）：它们问“能不能写出跑得动且不慢的 kernel”，以 runtime 与正确率为主要读数，不控制“是否给了设计指导”这一变量。D2K-Bench 的配对设计把“设计发现”与“实现翻译”拆开，runtime 不再是唯一读数——Performance Score 与 combined implementation score（57→70）刻画的是实现质量，而非单纯速度。这意味着一个在 KernelBench 上分数不错的 agent，可能在 D2K-Bench 上暴露“只会从零试错、不会读指导”的短板；反之亦然。

第二类是单轮/多轮 RL 与进化框架（Kevin、CUDA-L1/L2、EvoEngineer、cuPilot、Dr. Kernel 等）：它们优化的是“给定反馈下如何搜索出更快的 kernel”，奖励信号来自编译、运行与 profile。D2K-Bench 不提供训练配方，它提供的是诊断标尺：当这些方法报告加速比时，D2K-Bench 的配对口径能回答“这份加速里有多少来自指导翻译、多少来自盲目搜索”。两者是互补的——RL 方法可以用 D2K-Bench 的配对设置做消融，判断奖励是否在奖励“读懂设计”而非“碰巧撞上”。第三类是多 agent 与硬件反馈框架（Astra、CudaForge）：它们强调工具编排与 profile 回灌，D2K-Bench 的差别在于把“指导层级”作为受控变量，而不是把工具链当作自由变量。换言之，D2K-Bench 的贡献是实验设计而非agent 架构。

代价方面，配对设计意味着评测成本翻倍：每个 model-task 对要跑有指导与无指导两次，130 对即 260 次运行，每次 350 turn，编译与 profile 的时延叠加。这是诊断精度换来的开销；若只想做粗筛，单侧运行更便宜，但就失去了归因能力。另一个差别是正确性门的严格度：D2K-Bench 把正确率作为独立读数（93.1%→98.5%），而不是把错误候选直接丢弃，这让“指导提升了正确率”成为可观测结论；相邻工作若只报告“最优候选的加速比”，就看不到指导对失败率的抑制作用。

四 · 什么情况下不该用它：四类误用

误用一：把 Performance Score 当生产加速比。score 的定义是阈值计数下的几何平均式聚合，s_i = T_base,i / T_cand,i，且只在 s_i ≥ τ 时计入。这个口径奖励“跨过阈值”，不奖励“越过阈值后继续变快”，因此它适合比较“有多少 workload 达到了可用水平”，不适合预测端到端吞吐。生产端到端收益还取决于 kernel 在流水线中的占比、launch 开销、以及与相邻算子的融合机会——这些都不在 26 任务的单算子口径里。若你的场景是“一个算子占端到端 5%”，把它从 1.7× 优化到 2.5× 对总时延的贡献被 Amdahl 定律压到很小，此时 D2K-Bench 的高分不构成部署理由。

误用二：用离线分数替代隐藏输入分布的验证。shape 特化是这类基准的固有风险：agent 可能针对给定 workload 的 shape 写出硬编码 tile 与分支，离线分数漂亮，生产上遇到新 shape 就回落到甚至慢于基线。D2K-Bench 的 85 workload 提供了一定覆盖，但它不是生产流量分布。工程上必须在自己的 shape 分布上重跑正确性门与性能门，并专门测试“边界 shape”（极小、极大、非对齐），否则离线分数是虚的。

误用三：把正确率虚高当可靠性。fallback 与 reward hacking 会让正确率虚高：agent 可能写出“检测到不支持的输入就退回 PyTorch 路径”的 kernel，正确性门通过，但性能门测的是 fallback 路径的时延，或者反过来测的是快路径而生产上大量走 fallback。D2K-Bench 的 complementary assessment 检查生成代码里实际实现的设计属性，正是为了识别这种“名义实现、实际回退”。若你的验收只看正确率与加速比两个数，就会漏掉这一类。

误用四：在无指导可给的场景套用配对结论。前面已述，L1 洞察缺失时配对设计退化。若你的团队正在探索尚无公认数据流的新算子，D2K-Bench 的主口径不适用，应改用其 complementary assessment 的旁路，或直接以独立设计能力为读数。硬套主口径会把“无指导”误读为“指导无效”。

$$\text{端到端收益}\approx f\cdot\left(\frac{1}{s}-1\right),\qquad f=\text{该 kernel 占端到端时延比例}$$

具体例子：某算子 f=0.05，s 从 1.69 提到 2.49，端到端收益约 0.05×(1/1.69−1/2.49)≈1.0%，而 D2K-Bench 的分数抬升看起来是 47%。这不是基准错，而是口径错配——把诊断分数当部署收益，就会为 1% 的收益付出重写 kernel 的维护成本。

五 · 迁移到自建评测时的最小可信集

若要把 D2K-Bench 的口径迁移到自己的算子集，最小可信集包含四件事。其一，配对控制：有指导与无指导两次运行必须共享任务描述、workload、工具链、硬件与预算，唯一变量是指导；否则归因不成立。其二，分层回退：至少跑 full、full∖L3、full∖L2L3、full∖L1L2L3 四个配置，用 gap_layer 判断层间是否失配，这比单看总分更能定位 agent 的短板。其三，独立正确性门：正确率与性能分开读数，且正确性门要覆盖边界 shape 与非默认 dtype，防止 fallback 与 shape 特化污染。其四，实现属性核查：对生成代码做静态或半静态检查，确认指导里声称的设计（数据流、同步策略、向量化宽度）确实出现在代码里，而不是被注释掉或被 fallback 绕过。

代价是评测时延与工程投入：四配置回退使运行次数翻四倍，350-turn 预算下每次运行的编译与 profile 开销叠加，token 消耗也随之上升；实现属性核查需要额外的代码分析工具，属于一次性投入但维护成本持续。收益是可归因的结论：你能说清“这个 agent 在 L2 上强、在 L3 上与 L2 失配”，而不是只有一个总分。对于要决定是否把 agent 接入生产流水线的团队，这个归因比分数本身更有用——它直接指向该修哪一层，而不是笼统地“再训一版”。

最后落在工程判断上：D2K-Bench 的价值在于它把“runtime 不揭示差距来源”这一观察变成了可操作的对照实验，其 93.1%→98.5% 与 1.46→1.95 是这一对照下的读数，而不是能力上限。使用它的正确姿势是把它当作分层诊断仪：先在自己的硬件与 shape 分布上复现配对设置，用分层回退定位失配层，再用实现属性核查排除 fallback 与 shape 特化，最后才用端到端 Amdahl 折算判断是否值得部署。跳过任何一步，分数都会变成不可迁移的数字。

当专家指导变成“答案泄漏”：D2K-Bench 的失效边界与迁移代价

D2K-Bench 的配对设计（有指导/无指导共享任务描述、负载、工具、硬件与 350 轮预算）在诊断上很干净，但它同时把一条隐含前提写进了评测口径：指导本身是正确且可执行的。一旦 L1/L2/L3 三层指导中出现跨层依赖错配——例如 L2 的 dataflow 假设了 L1 不成立的算法不变量，或 L3 的向量化 trick 依赖某个 L2 未落实的 tile 形状——agent 会陷入“照着指导写却编译不过或数值不对”的死循环，350 轮预算被消耗在调试而非搜索上。此时 score 公式 $$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$ 只统计达标率，无法区分“没找到设计”与“设计给了但实现失败”这两种性质完全不同的失败，诊断信号在此处退化。

第二个失效条件是指导粒度过细导致的 reward hacking。当 L3 层把“用 __ldg + 手工 unroll”这类局部 trick 写得足够具体，agent 可以把优化目标从“逼近专家实现”退化为“逐条满足指导文本”，产出的 kernel 在基准 shape 上加速比好看，却对隐藏输入分布脆弱——shape 特化、缺少边界分支、假设对齐的向量化在非对齐 stride 上直接触发越界或 fallback。这类候选在离线口径下正确率虚高（fallback 路径兜住了数值），但在生产端到端回归里表现为时延抖动与显存峰值抬升。迁移到不同 dtype 或不同 SM 架构时，L3 的 trick 往往最先失效，而 L2 的 dataflow 仍可复用，这说明三层指导的可迁移性并不均等。

与相邻工作的差别在于评测目标而非方法：KernelBench 系基准问“能不能写对、能快多少”，D2K-Bench 问“专家设计被翻译了多少”。因此它不适合作为纯性能排行榜使用——把 26 任务、85 负载上的 Performance Score 从 1.46 抬到 1.95 当作模型能力排序，会忽略配对运行共享 350 轮预算这一约束带来的预算耦合效应。不该用它的场景很具体：需要跨硬件（非 B200）外推时、需要把加速比直接折算成产品收益时、以及指导文本本身来自待评测模型（自举指导）时——后者会让“有无指导”的对照失去独立性。真正可迁移的用法是把三层指导当作诊断探针：看 agent 在哪一层停止吸收，而不是看总分。
