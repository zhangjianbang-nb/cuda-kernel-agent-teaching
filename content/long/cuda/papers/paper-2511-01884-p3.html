一 · 首轮提示的组装：任务语义、参考实现与 shape 分布如何编码

在 CudaForge 的流水线里，第一环不是模型调用，而是提示组装器把算子任务编码成一段可执行意图。输入有三块：算子语义描述（做什么运算、边界条件、数据类型）、参考实现（通常是 PyTorch 或朴素 CUDA 版本，作为正确性 oracle 的来源）、输入 shape 分布（若干组具体维度，用于覆盖不同并行度与访存模式）。输出是一段结构化提示，交给生成器产出首版 CUDA 源码。这里的机制要点是：参考实现与 shape 必须同时进入提示，因为后续校验器需要前者做逐元素比对，而性能评测需要后者确定 grid/block 规模与内存占用。

代价出现在 token 与信息保真度上。参考实现若以完整源码形式嵌入，提示长度随算子复杂度线性上升；shape 分布若枚举过多组，同样挤占上下文。工程上的折中是只嵌入参考实现的签名与关键循环骨架，shape 以列表形式给出而非展开成张量描述。这一步的失败模式是提示歧义：语义描述漏掉边界处理（如非对齐尾块），模型生成的 kernel 在多数 shape 上正确、在尾块 shape 上越界，直到校验器阶段才暴露，浪费一整轮编译与运行。

一个具体例子：矩阵乘类任务，提示中给出 M/N/K 的三组 shape（含一组非 2 的幂维度），参考实现为三重循环版本。模型据此选择 tile 划分，但首版往往忽略尾块谓词，导致非对齐 shape 上数值不符——这正是下一节校验器要捕获的信号。

二 · 生成器与编译沙箱：源码到可执行体的第一道门

生成器的输入是上一节的提示，输出是 CUDA 源码文本。源码进入编译沙箱，沙箱的职责被限定为三件事：编译、启动、捕获。编译阶段用 nvcc 编译，捕获编译器诊断原文（错误码、行号、类型不匹配、未定义符号）；启动阶段在真实 GPU 上以受控的超时与显存上限运行，捕获崩溃（非法访存、断言失败）与超时；两者都以结构化记录形式落盘，而不是丢弃。

这一步的代价是编译时间与沙箱隔离成本。每次迭代都要重新编译，编译时间随源码规模与模板实例化深度增长；若模型生成大量模板或展开循环，nvcc 前端时间会显著拉长单轮时延。沙箱隔离（容器、驱动版本固定）保证可复现，但也意味着每轮都要付出环境启动开销。失败模式在此处最密集：语法错误、类型不匹配、缺少头文件、共享内存超限、launch 配置越界。材料未给出各类失败占比，但机制上这些错误原文被原样回灌，模型在下一轮做的是局部修补而非重写。

伪代码思路可概括为：compile(src) → {ok, diagnostics}；if !ok: feedback ← diagnostics；else: run(src, shapes) → {outputs, crash, timeout}。关键设计是编译失败不进入运行阶段，避免把不可执行体送入 GPU 造成无意义等待。一个具体例子：模型生成使用 __syncthreads() 于分支内的 kernel，编译器不报错但运行期死锁触发超时，沙箱把超时事件与 launch 配置一并回灌，下一轮模型移除分支内同步。

三 · 正确性校验器：候选门控与差异定位

编译通过后，运行输出进入校验器。校验器的输入是候选 kernel 的实际输出与参考实现的期望输出，输出是布尔判定加差异摘要（失败用例索引、最大绝对误差、首个不匹配位置）。机制上它承担门控职责：只有判定为正确的候选才进入性能排序，错误实现不参与最优候选竞争。这是可信评测的核心——若跳过门控直接按耗时排序，一个数值错误但跑得快的 kernel 会被误选为最优，整条搜索轨迹被污染。

$$\text{score}(k)=\mathbb{1}\big[\text{correct}(k)\big]\cdot\frac{T_{\text{ref}}}{T_{k}}$$

公式把门控与性能合为一个标量：正确性指示函数为零时分数归零，正确时分数为参考耗时与候选耗时的比值。代价在于校验本身要跑参考实现，参考实现的耗时计入每轮开销；若参考实现是朴素版本，其运行时间可能远大于候选，成为单轮时延的主要成分。另一个代价是数值容差的选择：浮点累加顺序不同导致微小差异，容差过严会把正确 kernel 判错，过松会放过真实错误。材料未给出容差口径，复现时须自行固定。

具体例子：归约类算子，候选 kernel 用树形归约改变了浮点加法顺序，与参考的串行累加在低位有差异。校验器返回最大绝对误差与失败用例索引，反馈摘要指出“数值偏差集中在尾部元素”，模型据此判断是尾块处理缺失而非归约逻辑错误。

四 · 硬件 profile 采集：从耗时到瓶颈类别

正确性通过的候选进入 profile 采集器。输入是可执行 kernel 与 shape，输出是硬件计数器读数与耗时，再由反馈组装器压缩成瓶颈类别摘要。机制上采集器读取的是真实 GPU 上的计数器（访存吞吐、占用率、指令吞吐等口径材料未给出），耗时以事件计时或多次运行取中位数的方式获得。关键不是原始计数器数值本身，而是把数值映射成“访存受限 / 计算受限 / 占用率不足 / 同步开销”这类可操作的类别，再拼进下一轮提示。

代价有三层：采集本身引入额外运行，profile 工具通常带来测量开销，单轮时延因此高于纯运行；计数器口径与 kernel 的对应关系需要固定（哪个 metric 对应哪个瓶颈），口径漂移会让反馈失真；反馈摘要的压缩是有损的，把多维计数器压成一句话，可能丢掉定位瓶颈所需的关键维度。材料明确指出反馈摘要质量直接决定下一轮修改方向，失真会引入无效修改——这是整条流水线最脆弱的环节，因为它是唯一没有形式化保证的映射。

具体例子：某候选 kernel 耗时高于基线，采集显示占用率低而访存吞吐未饱和，摘要输出“并行度不足，建议增大 block 规模或减少寄存器压力”。模型下一轮改写 launch 配置与寄存器使用，而非盲目改访存模式。若无此摘要，模型只能凭猜测在访存与并行之间随机试探，搜索效率显著下降。

五 · 反馈组装与迭代排序：一轮闭环的完整代价账

反馈组装器把三类信号拼回提示：编译诊断原文、校验差异摘要、profile 瓶颈类别。输入是结构化记录，输出是下一轮提示的增量段落。机制上它按失败阶段分流：编译失败只回灌诊断，不附 profile；校验失败回灌差异位置与失败用例；校验通过才附 profile 摘要与耗时对比。分流的意义是避免把无关信号塞进提示稀释注意力——编译错误阶段给模型看计数器数值毫无用处。

每轮结果被记录并排序，排序键即上面的 score。轮数上限与温度是超参，失败样本进入下一轮修正而非丢弃，形成执行反馈驱动的搜索。代价账可以按轮拆开：单轮时延 = 提示组装 + 生成（token 成本）+ 编译（编译时间）+ 运行（含参考实现）+ 校验 + profile 采集 + 反馈组装。工程代价随迭代轮数线性增长，材料未给出轮数上限与 token 成本，因此生产部署前必须实测单任务成本与收益比，防止搜索开销吞掉性能收益。一个具体例子：某任务在第三轮才通过校验，前两轮的编译失败与数值不符各消耗一次生成与一次编译，若轮数上限设为五，最坏情况下五轮全失败则输出为空，此时框架的产出是迭代轨迹而非可用 kernel。

排序与保留最优的机制还有一个隐含代价：轨迹存储。迭代轨迹与最优候选一并输出，使每次修改可复核，也为后续轨迹 SFT 与失败模式分析提供数据形态，但轨迹规模材料未给出。若每轮都保存源码、诊断、计数器与提示增量，存储随轮数线性增长，长任务的轨迹体积不可忽略。

六 · 闭环的工程判断：反馈质量是上限，门控是底线

把这条流水线拆到底，可以看到两个决定成败的机制点。底线是正确性门控：它把错误实现挡在排序之外，使 score 公式的指示函数真正起作用，避免性能排序被污染。上限是硬件反馈到提示的映射：编译诊断是确定性的文本，校验差异是确定性的数值，唯独 profile 摘要是有损压缩，缺少形式化保证。反馈摘要失真时，模型收到的是错误的方向指引，后续轮次的修改围绕伪瓶颈展开，搜索在错误子空间里消耗轮数与 token。

工程判断因此落在两处。其一，反馈组装器应按阶段严格分流，编译失败不附 profile、校验失败不附性能对比，减少无关信号对注意力的稀释；其二，profile 摘要应保留可复核的原始计数器读数作为轨迹的一部分，使“摘要是否失真”在事后可被审计，而不是只留下自然语言结论。材料未给出计数器口径与摘要模板，复现时须把这两项固定为可版本化的配置，否则同一任务在不同配置下的轨迹不可比，可信评测无从谈起。迭代轮数上限则是成本与收益的旋钮：轮数增加线性放大 token 与 GPU 时延，而收益取决于反馈质量——反馈可靠时多轮有效，反馈失真时多轮只是放大无效修改。

闭环的边界：反馈失真、门控漏判与搜索成本

这套流水线最脆弱的一环不在生成器，而在“硬件反馈→提示”的翻译层。profile 采集器拿到的是计数器与耗时，反馈组装器要把它压缩成一段自然语言摘要，模型再据此决定改访存还是改并行。这里没有任何形式化保证：摘要若把“occupancy 偏低”误述为“带宽不足”，下一轮修改就会朝错误方向走，而 score 公式 $$\text{score}(k)=\mathbb{1}\big[\text{correct}(k)\big]\cdot\frac{T_{\text{ref}}}{T_{k}}$$ 只对最终候选打分，不会惩罚中间轮的无效探索。失效条件是明确的：当瓶颈类别与摘要措辞之间出现系统性偏差，搜索会收敛到“局部最优但方向错误”的 kernel，且迭代轨迹看起来完全合理——这正是可复核性无法替代反馈正确性的地方。工程上必须把原始计数器与摘要文本一并落盘，复现时先校验摘要与计数器的一致性，再谈性能结论。

正确性门控同样有漏判面。校验器比对参考输出，但算子级任务的输入 shape 分布若未覆盖边界（极小的 M、非对齐的 N、含 NaN 的输入），一个在采样 shape 上通过的 kernel 仍可能在真实负载上越界或数值漂移。门控只保证“通过采样用例的候选进入排序”，不保证候选在分布外正确。代价是双重的：放宽容差会让错误 kernel 污染排序，收紧容差会把合法但数值路径不同的实现（如不同累加顺序）误杀，二者都直接改变最优候选的选择。可操作的做法是把失败用例的差异位置结构化回灌，而不是只回灌“不匹配”三个字，让模型能定位是索引错误还是精度问题。

搜索成本随轮数线性增长，这是该方案最硬的系统代价。每一轮都包含一次编译、一次 GPU 启动、一次参考比对与一次 profile 采集；编译沙箱的隔离与驱动版本固定又增加了环境维护开销。token 成本同样线性：每轮提示都携带任务语义、参考实现、上一轮错误原文与指标摘要，上下文随轨迹累积而膨胀。材料未给出轮数上限与单任务 token 消耗，因此生产部署前必须实测“单任务搜索开销 / 端到端性能收益”的比值——若收益来自几微秒的 kernel 时延，而搜索本身消耗数分钟 GPU 时间与大量 token，则收益口径必须按批量摊薄后才成立。下表给出各步骤的输入输出与主要代价，用于判断哪一步该被裁剪。

步骤输入输出主要代价

由此得到一个工程判断：该框架的可信度不取决于生成器多强，而取决于反馈链路能否被独立审计。失败样本进入下一轮修正而非丢弃，这保留了修复成功率这一可观测指标，但材料未给出各类失败占比，因此无法判断搜索是在“修语法”还是在“真优化”上消耗轮数。若编译错误占比高，说明首轮提示的任务语义与类型约束不足，应优先改提示模板而非加轮数；若数值不符占比高，说明参考实现与 shape 覆盖不足，应优先扩用例。把轮数当作唯一旋钮是最容易做错的决定——它同时放大 token 成本与反馈失真累积，而 score 公式对此完全无感。
