一 · 从一次 MoE 训练算子的“卡住”说起

设想一个已经在生产里跑起来的 MoE 训练栈：专家路由后的分组 GEMM 与 all-to-all 前后衔接，端到端吞吐被一个 fused 的 expert kernel 拖住。团队手里有一份专家手调过的 Triton 实现，性能已经优于朴素 PyTorch，但距离硬件上限仍有明显缺口。此时工程上真正要回答的不是“能不能再快一点”，而是“下一个改动点在哪里、改完值不值得”。传统路径给出的是一个昂贵的二分：要么继续由熟悉 Hopper 的工程师读 SASS、跑 NCU、手工重排 WGMMA 的 tile 与流水，周期以人周计；要么退回库调用，接受 cuBLAS/cuDNN 在非标准 shape 与融合模式下的保守选择。论文给出的对照事实是：在 VeOmni 这批已被专家优化过的 MoE 训练 kernel 上，KernelPro 通过从零生成 raw-CUDA+CuTe 的 Hopper WGMMA kernel，取得了相对手调 Triton 的 1.23x 加速。这个数字的意义不在于“又一个加速比”，而在于它跨过了一条此前被认为必须由人类专家把守的边界——对手调实现的进一步压榨。

把场景抽象成工程约束，问题现场由四个量共同定义：开发周期（人周/次迭代）、性能上限（相对 roofline 的达成率）、正确性风险（数值与边界条件）、可维护性（谁能读懂、谁能改）。手写 CUDA 在前两项上有上限优势但周期与可维护性最差；Triton 在周期与可维护性上折中，却把一部分底层控制权让渡给了编译器；库调用周期最短、正确性最稳，但性能上限被通用性锁死。三者共同的结构性痛点是：反馈回路太长且太贵。一次“改 tile 形状 → 编译 → 跑 NCU → 读指标 → 判断瓶颈 → 再改”的循环，其成本主要不在编译，而在人类把原始硬件计数器翻译成下一步动作的认知开销。

二 · 三条旧路径各自的性能天花板在哪里

手写 CUDA 的上限由程序员对流水线与存储层级的掌控程度决定。以 Hopper 上的 GEMM 为例，能否把 WGMMA 的异步性与 TMA 的搬运重叠起来、能否让 shared memory 的 swizzle 与 bank 冲突规避同时成立、能否把 epilogue 的寄存器压力压到不溢出，决定了实际达成率。这些决策的搜索空间是组合爆炸的：tile 尺寸、stage 数、warp 分工、swizzle 模式、指令选择彼此耦合，且最优组合随 shape 与 dtype 漂移。工程师的经验本质上是一组启发式剪枝规则，把不可行的组合先排除掉。代价是这些规则难以言传、难以复用，且一旦硬件换代（如从 Ampere 到 Hopper）就要重建。

Triton 把上述决策部分交给编译器，程序员描述的是块级程序语义。这大幅压缩了开发周期，但也意味着当编译器做出的调度选择不理想时，程序员缺少直接干预的把手；能调的多是 BLOCK_SIZE、num_warps、num_stages 这类旋钮，调参空间被压扁。库调用则更极端：cuBLAS 在标准方阵上接近峰值，但在 fused、非连续、分组、动态 shape 的场景里往往退化为多次 kernel 启动或插入额外搬运，端到端收益被启动开销与中间张量的显存往返吃掉。

用 roofline 把三条路径的差距量化，性能上限可写成：

$$P_{\text{att}}(I)=\min\left(P_{\text{peak}},\;I\cdot B_{\text{eff}}\right),\qquad I=\frac{\text{FLOP}}{\text{Byte}}$$

其中 $I$ 是算子的算术强度，$B_{\text{eff}}$ 是有效带宽。三条路径的差别不在于 $P_{\text{peak}}$（同一块卡），而在于能否把 $B_{\text{eff}}$ 推到接近 HBM 峰值、以及能否让实际 $I$ 不因多余的中间读写而下降。库调用在融合缺失时会把本可留在寄存器/shared 的中间结果写回 HBM，直接压低有效 $I$；手写 kernel 能把 $B_{\text{eff}}$ 做高，但需要精确的搬运与重叠；Triton 介于两者之间，取决于编译器是否选中了合适的流水。这个公式也是后续判断“瓶颈到底在算力还是在带宽”的第一把尺子——它决定了优化动作的方向，而方向判断错误是旧流程里最贵的浪费。

三 · 正确性与可维护性：被加速比掩盖的两种成本

旧路径的第二个痛点是正确性。手写 kernel 的边界条件（尾块、非对齐、空 tensor、极端 shape）是 bug 的高发区，且这类 bug 往往在特定输入分布下才暴露，离线基准跑通不等于生产安全。Triton 把一部分边界处理交给编译器，风险转移到“编译器假设是否成立”；库调用正确性最稳，但融合改写后语义等价性需要重新验证。论文的评测口径把这一点明确为双门：正确性门 + 性能门，候选必须先过正确性检查再谈加速比。这条纪律直接对应一个已知的失败模式：若基线未开 TF32、未用最强库实现，加速比会被系统性高估；若允许候选对 shape 做特化而隐藏输入分布不同，离线分数在生产上会崩塌。换言之，加速比是一个条件数很高的指标，它的可信度取决于基线强度与输入分布的一致性。

可维护性是第三种成本，且最难量化。一个手写 CuTe kernel 的维护者需要同时理解 tile 布局、swizzle、WGMMA 描述符与流水阶段，人员流动即意味着知识流失。Triton 的可维护性更好，但当性能不达标时，团队往往被迫回退到手写，形成“Triton 原型 → CUDA 重写”的双份维护。库调用可维护性最好，代价是性能上限。三者的权衡不是静态的：随着模型结构迭代（新的融合模式、新的 dtype、新的并行切分），最优选择会漂移，而每次漂移都触发一轮昂贵的人工重写。

路径开发周期性能上限正确性风险可维护性典型失效点
手写 CUDA/CuTe长（人周级迭代）最高，可达 roofline 附近边界条件与数值细节最差，知识集中于个人换硬件代际需重建启发式

这张表的读法是：没有一行同时占优，因此工程实践长期在“快但脆”与“稳但慢”之间摆动。真正的破局点不是选一条路，而是把反馈回路的认知成本降下来，让“改—测—判断”这一步不再依赖稀缺的专家注意力。

四 · 为什么“让 LLM 直接写 kernel”不够：原始指标的翻译鸿沟

把 LLM 引入这条回路，最朴素的做法是给模型看源码和报错，让它改。这在语法与简单逻辑上有效，但在性能优化上迅速撞墙，原因是一个信息论层面的问题：NCU 给出的是一组原始计数器（occupancy、各类 stall 比例、L2 命中、DRAM 吞吐、指令发射数），而“下一步该改什么”是一个语义判断。从原始指标到动作之间存在一条翻译鸿沟，人类专家靠经验跨越它，LLM 直接面对数字时缺少这条桥。举例：当 DRAM 吞吐接近峰值而 SM 发射率低，专家会判断为“带宽受限，应减少中间搬运或提高复用”；当 occupancy 低且 stall 集中在 long scoreboard，专家会判断为“延迟隐藏不足，应增加并行或预取”。同样的数字组合在不同 kernel 语义下指向相反的动作，模型若只看数字，容易做出方向性错误的修改，浪费整轮编译与测量预算。

这条鸿沟的代价可以量化到预算层面。设一轮“生成—编译—测量”的成本为 $C$（编译时间 + 测量时延 + 显存占用导致的串行化），有效轮数为 $N$，则总优化预算为 $N\cdot C$。若方向判断错误率高，则有效探索轮数被浪费，$N$ 中真正推进性能的比例下降。论文的消融给出了这条鸿沟存在的直接证据：把原始指标替换为编码了专家启发式的 micro-profiling 工具后，优化质量显著提升（p < 0.0001 vs raw metrics）。这不是“多一点信息”的边际改善，而是信息形态的改变——从数值到可执行的自然语言指引。

这也解释了为什么单纯扩大模型或增加采样在性能优化任务上收益递减：瓶颈不在生成能力，而在反馈的语义密度。旧方案（手写、Triton、库调用）各自绕开了这个问题——手写靠人脑翻译，Triton 靠编译器隐式翻译，库调用干脆不翻译——但没有一条路径把翻译本身工程化、可插拔化。

五 · 旧流程的迭代经济学：一次改动的真实成本结构

把一次优化迭代拆开看，成本分布在四个环节：假设形成（人读 profile 想方向）、实现（写代码）、验证（编译 + 正确性）、测量（时延与资源）。手写路径里，假设形成与实现占大头；Triton 路径里实现被压缩，但假设形成仍贵；库调用几乎没有假设形成，因为可调空间小。LLM 介入后，实现成本显著下降，于是假设形成成为新的瓶颈——这正是论文把 micro-profiling 工具作为核心贡献的原因：它直接攻击的是回路中最贵的那一环。

迭代经济学还有一个容易被忽略的维度：搜索策略。贪心地“每次取当前最优改动”在耦合的调优空间里会陷入局部最优，因为单步最优的改动组合起来未必最优（例如先调 tile 再调 stage，与先调 stage 再调 tile 的落点不同）。论文的消融显示，用 MCTS 搜索替代贪心带来 26% 的几何平均提升（p = 0.004），而主动的工具编排带来 23% 的提升（p = 0.035）。这两个数字说明：在反馈语义化的前提下，如何组织探索本身就是一个独立的性能杠杆，而不是附属技巧。旧流程里这一层几乎不存在——人类工程师的探索顺序由直觉决定，无法系统化复用。

把这条经济学落到具体例子上：一个 fused MoE expert kernel 的调优，涉及分组 GEMM 的 tile、all-to-all 的切分粒度、以及 epilogue 的写回策略。三者耦合，贪心改 tile 可能让 all-to-all 的切分失配，端到端反而变慢；而 MCTS 能在树上保留“当前看起来不优但为后续改动铺路”的分支。代价是搜索轮数增加，即 $N\cdot C$ 上升，因此工具编排的价值在于用更少的轮数排除更多分支——主动调用合适的 micro-profiling 工具，等价于在树上提前剪枝。

六 · 能耗维度：旧方案没有覆盖的第四个约束

旧路径的隐含假设是“速度即目标”。但在真实推理服务与训练集群里，功耗墙与散热预算同样是硬约束：同一时延下更低的能耗意味着更高的机架密度与更低的运营成本。论文明确指出 KernelPro 是第一个在速度之外优化能效的 CUDA kernel coding agent，在匹配速度下测得 11.6% 的能耗下降。这个数字的工程含义是：优化目标从标量变成了向量——(时延, 能耗, 正确性, 可维护性)。旧方案里，手写工程师偶尔会顺手考虑能耗（例如减少无效搬运），但没有系统化的度量与反馈；Triton 与库调用则完全不暴露这一层。

能耗作为反馈信号的特殊性在于它与时延不完全同向。一个提高 occupancy 的改动可能缩短时延却提高功耗；一个减少搬运的改动可能同时改善两者。因此把能耗纳入回路要求反馈工具能区分“省时的省能”与“费时的省能”，这与前文提到的语义翻译是同一类问题：原始功耗计数器同样需要被翻译成动作。这也解释了为什么论文把 micro-profiling 工具设计为可插拔——能耗只是其中一个插件，瓶颈检测工具的集合可以随目标扩展，而不需要重写整个回路。

回到开场的 MoE 场景：团队面对的不再是一个“要不要重写 kernel”的二元决策，而是一条可复现的回路——读取参考实现与基准口径，生成候选，编译后做正确性检查，用统一基线测量时延与资源占用，按反馈保留或回退。这条回路把原本集中在少数专家身上的翻译工作，分散到了可插拔的工具与搜索策略上。旧方案并非被否定，而是被重新定位：手写 CUDA 提供上限参照，Triton 提供快速原型，库调用提供正确性基线，三者共同构成回路里的对照系，而回路本身才是新的工程对象。

手写与库调用在真实推理服务里的边界

把镜头放到一个在线推理服务的 MoE 层：专家权重按 token 路由动态聚合，batch 形状随流量抖动，dtype 在 BF16 与 FP8 之间切换。这里的 kernel 工程主流做法有三条路：库调用（cuBLAS、CUTLASS 现成模板）、手写 CUDA（含 CuTe 的 WGMMA 抽象）、以及 Triton 快速原型。库调用的边界最清楚：一旦算子融合模式超出库的 tile 与 epilogue 组合，就退化成多次 launch 加中间张量落显存，带宽被吃满而算力闲置。手写 CUDA 能突破这层，但开发周期以人周计，且正确性依赖工程师对 Hopper 异步流水、warpgroup 寄存器布局的心智模型；Triton 把周期压到人天，却在 WGMMA 这类需要显式描述 shared memory 布局与 mbarrier 的阶段触到表达力上限。论文正是从这个现场出发：VeOmni 上专家已调优的 Triton MoE kernel，被一个从零生成的 raw-CUDA+CuTe Hopper WGMMA kernel 以 1.23x 超过——说明“专家手调 Triton”本身就是一个会被跨越的性能上限，而非终点。

这三条路的共同代价可以用 roofline 一句话刻画：给定算术强度 I，可达性能被 P_att(I)=min(P_peak, I·B_eff) 封顶。库调用的问题不在 P_peak，而在融合不足导致有效带宽 B_eff 被中间张量的读写稀释；手写 CUDA 的问题不在公式，而在人力无法对每个 shape 重新推导 I 与 tile 的匹配；Triton 的问题在于编译器对 B_eff 的调度决策不透明，工程师只能靠试。三者叠加的系统代价是：开发周期（人周 vs 人天）、正确性风险（异步流水与边界条件）、可维护性（手写 kernel 与框架版本强耦合），以及最隐蔽的一项——性能上限被“专家已调优”这句话固化，团队失去继续下探的动力。

失效条件同样具体。库调用在 shape 特化场景失效：离线基准用固定 shape 测出的加速比，遇到生产端动态 batch 与路由稀疏度变化就会崩塌，因为 tile 配置与 occupancy 是按基准 shape 选的。手写 CUDA 在硬件代际切换时失效：Hopper 的 WGMMA 与 TMA 描述符写法无法平移到下一代，维护成本按代际重付。Triton 在需要精细控制寄存器压力与 pipeline stage 时失效，工程师被迫回退到 raw CUDA。更关键的是评测口径本身会骗人：基线若未开 TF32、未用最强库实现，加速比会被系统性高估；shape 特化与隐藏输入分布让离线分数在生产上失真；reward hacking 与 fallback 机制让正确率虚高。这正是 KernelPro 要替换旧方案的理由——不是旧方案不够快，而是它无法在“生成—profile—回退”的闭环里被可信地度量与迭代。
