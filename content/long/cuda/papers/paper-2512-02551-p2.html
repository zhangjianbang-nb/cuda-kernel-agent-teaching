一 · 基准的构造方式：单算子、同 shape 对照

该论文的评测负载被压缩到一件事：矩阵乘法。基准的构造逻辑不是“收集一批 kernel 任务”，而是“对每一个待测 shape，现场生成一个同 shape 的 cuBLAS 调用作为对照”。这意味着基准的原子单位是 (shape, dtype, 基线实现) 三元组，而不是一个静态数据集。评测时策略模型拿到的是矩阵乘任务描述，产出 CUDA 源码，编译运行后与同 shape 的 cuBLAS 结果比对数值、再比延迟。这个设计的直接后果是：基准本身没有固定规模——shape 集合未披露，因此“测试了多少个 shape”这一最基本的可复现信息是缺失的。读者在引用其结论时必须把“超过 cuBLAS”限定为“在其未公开的 shape 集合上、在其未公开的 GPU 上、相对其未公开版本的 cuBLAS”。

同 shape 对照有一个容易被忽略的机制细节：cuBLAS 对每个 shape 会走不同的内部启发式路径（不同 tile、不同 split-k、不同 stream-k 策略），因此基线延迟本身是 shape 的函数，且对 shape 的微小扰动敏感。把 kernel 延迟与同 shape 的 cuBLAS 延迟相除，形式上消掉了绝对硬件性能，但消不掉基线选择带来的偏差。若某 shape 恰好落在 cuBLAS 启发式的次优区间，加速比会被系统性高估；反之若落在 cuBLAS 的甜点区，加速比会被压低。论文未披露 shape 集合，也就无法判断其报告的加速比是分布在 cuBLAS 的强区还是弱区。

$$\text{speedup}(s)=\frac{t_{\mathrm{cuBLAS}}(s)}{t_{\mathrm{kernel}}(s)},\qquad s\in\mathcal{S}_{\text{undisclosed}}$$

代价在这里体现为测量成本：每个 shape 都要跑一遍 cuBLAS 基线，且基线必须与 kernel 在同一进程、同一时钟状态、同一显存压力下测量，否则分子分母不同源。工程上这意味着评测机不能同时跑其他负载，且每个 shape 的基线计时需要预热与重复。论文材料未给出预热次数与重复次数，这是口径上的第一个空洞。

二 · 指标族：faster rate、geomean、fast_p 与 roofline 各自回答什么

单看一个加速比数字没有意义，因为加速比的分布是重尾的：少数 shape 上大幅超过 cuBLAS 可以拉高算术平均，而多数 shape 上略慢会被掩盖。这类基准通常需要四个互补指标。faster rate 是加速比大于 1 的 shape 占比，回答“赢了多少个 shape”，对离群值不敏感但完全丢失赢的幅度。geomean 是对加速比取几何平均，回答“典型 shape 上的相对性能”，因为几何平均对乘性误差对称，一个 2× 和一个 0.5× 在几何平均下互相抵消，这比算术平均更符合“相对基线”的语义。fast_p 是加速比超过阈值 p 的 shape 占比（例如 p=1.1 表示至少快 10%），回答“有多少 shape 是显著赢而非噪声内打平”。roofline 则把绝对延迟换算成达到的浮点吞吐占硬件峰值的比例，回答“离硬件上限还有多远”，它与基线无关，因此是唯一能跨硬件比较的量。

指标回答的问题对离群值的敏感性可比性边界
faster rate赢的 shape 占比低（只计符号）依赖 shape 集合与基线版本
geomean speedup典型 shape 的相对性能中（乘性对称）依赖 shape 集合，跨硬件不可比
fast_p显著赢的 shape 占比低阈值 p 需固定，否则不可比
roofline 占比离硬件峰值多远高（受峰值假设影响）跨硬件可比，但需固定峰值口径

论文材料只给出“以相对 cuBLAS 的加速比为核心指标”，未说明是否报告 faster rate、geomean 或 fast_p，也未给出 roofline 数据。这带来一个具体的可比性陷阱：如果只报告“在部分 shape 上超过 cuBLAS”，那么这句话在 faster rate 口径下可能对应很小的占比，在 geomean 口径下可能小于 1。工程判断是：任何声称“超过 cuBLAS”的 kernel 生成工作，必须同时给出 faster rate 与 geomean，否则无法区分“广谱小幅落后但个别 shape 爆发”与“广谱稳定领先”。

以矩阵乘为例说明指标分歧：假设某方法在 8 个 shape 中 3 个达到 1.3×、5 个为 0.85×。faster rate 为 0.375，算术平均约 1.02（看似赢了），几何平均约 0.96（实际输了）。同一批数据在三个指标下给出三种结论，这正是口径必须预先声明的原因。

三 · 硬件、dtype 与基线版本：三个未披露变量如何摧毁可比性

加速比是一个无量纲量，但它只在“同一 GPU、同一 dtype、同一 cuBLAS 版本、同一计时方法”这四个条件同时固定时才可跨实现比较。论文材料明确说硬件为真实 GPU 但型号未给出，dtype 未给出，cuBLAS 版本未给出。这三个缺失不是形式上的不完整，而是实质性的不可比来源。

硬件维度：矩阵乘的性能由 SM 数量、每 SM 的寄存器文件与共享内存容量、HBM 带宽、L2 容量共同决定，而这些比例在不同代际 GPU 上并不一致。一个在共享内存充裕的卡上有效的双缓冲 tile 策略，换到共享内存紧张的卡上会直接触发共享内存超限失败（这正是论文记录的失败模式之一）。因此同一份源码在不同 GPU 上的加速比可以符号相反，跨硬件的加速比不可比是结构性的，不是测量噪声。

dtype 维度：fp32、tf32、fp16、bf16 在 cuBLAS 中走完全不同的内核路径，tensor core 的可用性、累加精度与吞吐差异巨大。生成 kernel 若用 fp32 累加而基线用 tf32，数值校验容差与性能对比同时失真。论文未披露 dtype，意味着无法判断其加速比是在 tensor core 路径上还是在 CUDA core 路径上取得的，而这两条路径的优化空间完全不同。

基线版本维度：cuBLAS 每次随 CUDA 工具链更新都会调整启发式与内核实现，同一 shape 的基线延迟会漂移。论文材料自己指出“每换一次 GPU 型号或 cuBLAS 版本都需重测基线，否则加速比口径漂移”。这句话应被当作该工作最重要的工程告诫：加速比不是源码的属性，而是 (源码, 基线版本, 硬件) 三元组的属性。

$$\text{speedup}\ \text{is comparable only under}\ \langle \text{GPU model},\ \text{dtype},\ \text{cuBLAS version},\ \text{timing protocol}\rangle\ \text{fixed}$$

代价是复现成本：要核查该论文的任何加速比数字，需要重建其未披露的四个条件，而其中任何一个未知都会使数字落在不同的可比类里。工程上可行的做法是把基线版本与 GPU 型号写入评测产物的元数据，使加速比携带其可比类标签，而不是作为一个裸数字流通。

四 · 隐藏 shape 与分布：为什么“部分 shape 超过”不能外推

论文材料承认“在部分 shape 上超过 cuBLAS”，但未给出 shape 集合、矩阵规模、是否覆盖非方阵、奇异 shape 与边界尺寸。这不是披露不足的细节问题，而是决定了结论的适用范围。矩阵乘的性能对 shape 极度敏感，原因在于 tiling 的整除性：一个 128×128 的 tile 在 M=N=K=4096 时完美整除，在 M=4097 时产生边界 tile，浪费近一整块 tile 的计算与访存。生成 kernel 若针对整除 shape 调优，会在非整除 shape 上出现明显回退，而 cuBLAS 的启发式通常对边界有专门处理。

隐藏 shape 分布的另一个后果是选择偏差：如果 shape 集合是作者挑选的、且偏向于 cuBLAS 表现平平的区间，那么 faster rate 会被系统性抬高。这在方法学上无法从摘要级材料中排除。可核查的口径要求 shape 集合预先声明并覆盖三类：整除友好的大方阵、非整除的奇异尺寸、以及 K 很小或很大的极端比例（后者决定是否走 split-k）。

分布维度还包括输入数值分布。正确性校验以参考矩阵乘结果比对为门槛，但容差阈值未给出。对于 fp16/bf16 累加，不同的累加顺序会产生不同的舍入误差，容差过松会让错误 kernel 通过校验并拿到加速比奖励，容差过紧会让合法但累加顺序不同的 kernel 被判失败。这是正确性 oracle 与性能奖励耦合处的口径漏洞：奖励函数把正确性当硬门槛，但门槛本身的阈值未披露，等于门槛的高度未知。

代价体现在失败样本的构成上：若容差设置不当，失败样本中会混入“数值合法但被判错”的假阴性，这些样本作为负样本回流会误导策略远离某些合法的累加策略。论文材料记录了数值偏差作为失败模式，但未区分真错误与容差误判。

五 · 可核查的测量口径：把计时协议写成可复现的契约

要让加速比可核查，计时协议必须固定到可以被第三方重放的程度。最小契约包含：预热次数（使 GPU 时钟与缓存进入稳态）、重复次数（取中位数而非均值以抗离群）、是否同步（kernel 异步启动，不同步会测到启动开销而非执行时间）、是否包含显存分配与拷贝、以及是否锁定时钟频率。论文材料只提到“计时层多次测量延迟”与“需固定预热与重复次数以降低噪声”，未给出具体数值。

一个可操作的伪代码口径如下，用于说明每个参数如何影响分子分母：

  • 对每个 shape s：先跑 W 次预热，丢弃；再跑 R 次，每次前后插入设备同步，取 R 次的中位数作为 t(s)。
  • cuBLAS 基线与生成 kernel 使用同一 W、R、同步方式与显存布局，交替测量以抵消时钟漂移。
  • 记录每次测量的方差；若方差超过中位数的某比例，标记该 shape 的加速比不可信。

这里每个选择都有代价。预热不足会让首个 kernel 承受时钟爬升与指令缓存冷启动，系统性高估基线或低估 kernel；同步方式不同会让两个数字一个含启动开销一个不含，加速比失真；交替测量增加评测时间但消除漂移。工程判断是：评测时间成本与口径可信度直接冲突，W 与 R 越大越可信但每个 shape 的评测成本线性增长，而多轮 RL 中每个 shape 要被评测多次，这个成本会被轮数放大。

另一个可核查项是失败样本的记录格式。论文把编译错误、数值失败与计时结果三类信号归类回传，这要求评测产物不仅记录奖励标量，还记录失败类型标签与对应的源码快照。否则第三方无法区分“加速比低是因为 kernel 慢”还是“因为编译失败被置零”。奖励公式里失败样本奖励为零，零奖励与低加速比在标量上不可区分，只有保留失败类型才能重建分布。

$$t(s)=\operatorname{median}\{\,t_1,\dots,t_R\,\},\quad \text{with } W \text{ warmups and device sync per iteration}$$

具体例子：某 shape 上 kernel 中位延迟为 0.42 ms、cuBLAS 为 0.50 ms，加速比 1.19；但若预热从 10 次降到 2 次，cuBLAS 因时钟未爬升测得 0.58 ms，加速比虚高到 1.38。同一份源码在两个预热口径下相差 16 个百分点，这说明口径本身就是结论的一部分。

六 · 哪些数字不可比，以及引用时的最小声明集

综合以上，该论文中不可比的数字有三类。第一类是跨硬件的加速比：未披露 GPU 型号，且加速比随 SM 比例、共享内存容量与带宽变化，跨代不可比。第二类是跨 cuBLAS 版本的加速比：基线随工具链更新漂移，未披露版本则无法定位可比类。第三类是跨 shape 集合的聚合指标：faster rate 与 geomean 都依赖 shape 分布，未披露集合则聚合值不可复现。相对地，roofline 占比是唯一在原则上可跨硬件比较的量，但论文未给出，且它依赖峰值吞吐的假设口径。

引用该工作时，最小声明集应包含五项：GPU 型号、dtype、cuBLAS 版本、shape 集合（至少给出规模区间与是否含非整除尺寸）、计时协议（预热次数、重复次数、同步方式、统计量）。缺任一项，加速比就应被标注为“条件未定”。论文材料在这五项上全部缺失，因此其“超过 cuBLAS”的结论只能作为存在性证据——存在某个未公开的配置使生成 kernel 快于同 shape 的 cuBLAS——而不能作为普适性能声明。

工程判断落在基线重测的触发条件上：每当 GPU 型号或 cuBLAS 版本变化，基线必须重测，且旧加速比数字应作废而非沿用。这一条应写进评测流水线的元数据校验里，使加速比携带其可比类标签。对于多轮 RL 训练，这意味着奖励函数在硬件或库版本变更后会发生尺度漂移，历史轨迹中的奖励不可直接与新轨迹混合更新——这是把性能信号作为奖励时最容易被忽略的口径耦合。

加速比口径的边界：什么情况下这个数字不成立

该方案的指标体系只有一个核心量：同 shape 下 \(t_{\mathrm{cuBLAS}}/t_{\mathrm{kernel}}\)，正确性作为硬门槛把失败样本奖励置零。这意味着所有对外宣称的“超过 cuBLAS”都必须绑定三元组（shape 集合、GPU 型号、cuBLAS 版本）才成立。材料未披露 shape 数量与硬件型号，因此该结论只能读作“在作者选定的一组方阵/稠密 GEMM 上、在某一代 GPU 与某一版 cuBLAS 上取得正加速比”，不能外推为跨 shape 或跨硬件的普适优势。工程上更危险的是基线漂移：cuBLAS 每次随 CUDA 工具链升级都会重调启发式与 kernel 选择，同一份生成 kernel 在旧版上跑出的 1.x 倍加速，换版本后可能直接落到 1 以下，而论文口径不提供任何版本锁定说明。

计时噪声是第二个失效条件。kernel 延迟之比的方差随 shape 缩小而放大——小规模 GEMM 的单次 launch 开销与 L2 残留状态占比高，若不固定预热次数与重复次数，加速比可在测量层面翻转。可核查的口径应写成：先跑若干次预热丢弃，再取重复测量的中位数而非均值（均值被偶发抢占污染），并同时报告 cuBLAS 与生成 kernel 的绝对延迟，使读者能自行复算比值。下表给出三类不可比情形与对应的核查动作：

不可比情形后果核查动作
cuBLAS 版本或 GPU 型号变更基线漂移，比值失真锁定版本号与型号，重测基线
未固定预热/重复次数小 shape 方差主导结论报中位数与绝对延迟
shape 集合未公开选择性报告无法排除公开全部 shape 与逐项比值

隐藏 shape 与输入分布的处理同样决定结论强度。材料只说明评测负载为矩阵乘、具体 shape 分布与数据类型未给出，也未说明是否覆盖非方阵、奇异尺寸与边界规模。生成 kernel 的 tiling 参数往往对 shape 敏感：为某一组方阵调出的分块在窄长矩阵上会因占用率骤降而失效，而 cuBLAS 内部按 shape 走不同启发式路径，两者对比在分布外 shape 上不具备对称性。因此可复现的测量口径必须把 shape 集合作为一等公民公开，逐 shape 报告比值并给出几何平均，而不是只报一个聚合加速比；同时应披露 dtype 与容差阈值，因为数值校验的阈值松紧直接决定哪些“快而错”的 kernel 被放行——奖励函数在正确性门槛处的这一刀，实际上定义了整个搜索空间的有效边界。
