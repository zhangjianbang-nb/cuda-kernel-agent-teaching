一 · 反馈不是标量：把一次运行拆成四层可回灌信号

EvoEngineer 的反馈回路之所以区别于“跑一遍拿个 speedup 就回去改”的朴素循环，在于它把单次执行拆成四个层级、四种语义、四种代价的信号，并按信息密度分层回灌。第一层是编译反馈：nvcc/ptxas 的报错行、寄存器溢出警告、共享内存超限、非法指令、未定义符号。这一层延迟最低（秒级），信息量最高，因为错误位置精确到行、原因精确到资源约束。第二层是运行反馈：非法内存访问、越界、race condition 触发的 CUDA error、kernel launch 失败、结果与参考实现逐元素比对失败。这一层延迟中等（秒到分钟），代价是必须构造合法输入并承担一次完整 launch。第三层是 profile 反馈：NCU 采集的 achieved occupancy、DRAM throughput、L2 hit rate、warp stall 原因分布（stall_long_scoreboard、stall_mio_throttle、stall_barrier、stall_wait 等）、SASS 层面的指令混合与 bank conflict 计数。这一层延迟最高（分钟级，NCU 重放需要多次 pass），但信息量指向“为什么慢”而非“慢不慢”。第四层是 roofline 诊断：把实测吞吐与硬件峰值、带宽上限对齐，判断候选落在 memory-bound 还是 compute-bound 区间。

四层信号的粒度差异直接决定回灌方式。编译错误适合逐条文本回灌，因为 LLM 对“第 87 行 shared memory 超出 48KB”这类结构化文本的修复能力远强于对一段性能数字的归因能力。运行错误需要附带最小复现输入与期望输出片段，否则模型只能盲猜。profile 信号必须做降维，NCU 原始输出动辄数百个 metric，直接塞进上下文会挤占 token 预算并稀释注意力；EvoEngineer 的做法是抽取与当前瓶颈相关的子集（occupancy、DRAM 利用率、top-3 stall 原因），形成一段可读的诊断摘要。roofline 信号则是一个二元判断加一个比值，用来决定下一轮优化方向是减少访存还是增加并行度。

$$\text{bound}=\begin{cases}\text{memory}, & \text{DRAM throughput} \ge \alpha\cdot B_{\text{peak}}\\ \text{compute}, & \text{SM throughput} \ge \alpha\cdot P_{\text{peak}}\\ \text{latency}, & \text{otherwise}\end{cases}$$

这里的 α 是判定阈值，取接近 1 的值表示“已接近该维度上限”。代价在于：NCU 重放会放大被测 kernel 的实际执行时间若干倍，对短 kernel（微秒级）尤其不划算，因此 profile 只应作用于已通过正确性门、且 speedup 已进入候选池的版本，而不是每个变异体都跑一遍。一个具体例子：某 reduction kernel 编译通过、结果正确、speedup 只有 1.1×，NCU 显示 DRAM throughput 已达峰值的九成而 SM throughput 不足三成，roofline 判定为 memory-bound，于是下一轮变异的方向被约束为“减少全局访存次数、改用向量化 load”，而不是继续调 block size——后者在 memory-bound 区间几乎不产生收益。

二 · 编译与运行错误的回灌：把“不可运行”变成“可修复”

通用 LLM 代码进化方法在 CUDA 上失效的第一个原因，论文点得很直接：general-purpose LLM code evolution methods cannot meet strict correctness requirements of CUDA kernel optimization。CUDA 的严格性体现在两个不对称：编译期的不对称（大量在 CPU 侧合法的写法在 GPU 侧非法，如跨 warp 的隐式同步假设、动态并行、寄存器数组索引）与运行期的不对称（错误往往不立即暴露，越界写可能静默污染相邻 buffer，race 可能只在特定调度下出现）。因此反馈设计的第一原则是：不能让“编译失败”和“结果错误”共用同一条回灌通道。

编译错误的回灌要做三件事：截取报错首行与关键行（nvcc 的报错常有模板展开的长尾，全量回灌浪费 token）、附上出错行号附近的源码窗口、标注该错误属于语法类还是资源类。资源类错误（寄存器数超限、shared memory 超限、launch bounds 不满足）的修复策略与语法类完全不同：前者需要重构数据布局或降低并行度，后者只需局部改写。把这两类混在一起回灌，模型倾向于做局部语法修补，而资源类问题需要的是结构性重写。

运行错误的回灌代价更高。一次非法访存需要构造能触发它的输入，而触发条件可能依赖 shape、对齐、边界值。EvoEngineer 的流程里，正确性检查在给定输入分布上执行，反馈包含“哪个输出元素不匹配、偏差量级、是否 NaN/Inf”。偏差量级本身是强信号：整块输出为 NaN 通常指向未初始化共享内存或除零；末位元素不匹配通常指向边界处理缺失；随机位置偶发不匹配指向 race。这三种模式对应三种截然不同的修复动作，而裸 speedup 完全不携带这些信息。

一个具体例子：某 softmax kernel 在多数 shape 上正确，但在非 2 的幂的列数上末列输出错误。若只回灌“正确性失败”，模型可能重写整个归约逻辑；若回灌“第 N-1 列至第 N 列不匹配、其余列逐位一致”，模型会直接定位到尾部处理的 mask 条件。后者的修复轮次显著少于前者，代价是反馈管线必须做逐元素比对并生成结构化差异，而不是一个布尔值。这就是粒度换轮次的典型权衡：更细的反馈需要更多离线计算与 token，但换来回灌轮次的下降。

三 · NCU 与 SASS：从“慢”到“为什么慢”的归因链

裸 speedup 是一个标量，它回答“这个候选比基线快多少”，但不回答“下一个变异应该改什么”。EvoEngineer 把 profile 信号接入进化循环，本质上是把优化从随机搜索变成有方向的局部搜索。NCU 提供的归因链是：occupancy 低 → 看 launch bounds 与寄存器压力；occupancy 高但吞吐低 → 看 stall 原因分布；stall_long_scoreboard 占主导 → 访存延迟未被隐藏，需要提高 ILP 或预取；stall_mio_throttle 占主导 → 共享内存/特殊功能单元吞吐打满，需要减少 bank conflict 或换指令；stall_barrier 占主导 → 同步开销过大，需要减少 __syncthreads 次数或改用 warp 级原语。

SASS 层面的信号补充了源码层面看不到的事实：编译器是否把循环展开、是否生成了 LDG.E.128 向量化访存、shared memory 访问是否存在 bank conflict、是否有冗余的 MOV 与谓词指令。这些信息对 LLM 的回灌价值在于，它把“源码意图”与“实际生成指令”之间的差距显式化。模型写了一个看似向量化的 load，但 SASS 显示是四次 32-bit LDG，说明对齐假设不成立或指针类型未加 __restrict__，这类归因是 speedup 数字永远无法提供的。

$$\text{speedup}_{\text{roof}}=\frac{T_{\text{baseline}}}{T_{\text{candidate}}},\qquad \text{gap}=1-\frac{\text{achieved}}{\min\left(P_{\text{peak}},\,I\cdot B_{\text{eff}}\right)}$$

roofline 诊断把 profile 数据折算成一个“距离上限还有多远”的比值。gap 大且判定为 memory-bound，说明访存效率是主矛盾；gap 大且判定为 compute-bound，说明指令吞吐或占用率是主矛盾；gap 小则说明该候选已接近该硬件的可实现上限，继续进化的边际收益低，应把预算转向其他算子。这个判断直接改变进化策略的资源分配：不是所有候选都值得多轮迭代。

代价必须说清楚。NCU 的采集是重放式的，需要多次 pass 才能收集完整 metric 集，单次 profile 的墙钟时间可达被测 kernel 执行时间的数十倍；对 91 个真实 CUDA kernel 的规模做全量 profile，profile 开销会成为整个流程的主导项。因此工程上的做法是分级采样：正确性门通过的候选才进 profile，profile 只采与当前判定瓶颈相关的 metric 子集，且对同一候选的多次变异复用上一次的瓶颈判定作为先验。另一个代价是 token：一段 NCU 摘要加 SASS 片段轻易占去数千 token，若每轮都全量回灌，上下文预算会被迅速耗尽，挤掉参考实现与历史变异记录。

四 · 反馈的延迟结构与“反馈预算”分配

四层信号的延迟量级差异构成一个天然的漏斗：编译（秒）→ 运行正确性（秒到分钟）→ profile（分钟级）→ roofline 归因（依赖 profile）。EvoEngineer 的进化循环若按最昂贵的信号驱动每一轮，吞吐会被 profile 拖垮；若只用最便宜的编译信号，则永远无法触及性能瓶颈。合理的分配是把反馈预算按漏斗分层：每个变异体必过编译门与正确性门，只有通过者才消耗 profile 预算，且 profile 预算按候选池的排名分配——speedup 排名靠前或瓶颈判定尚不明确的候选优先获得 profile 配额。

这个分配策略的信息论依据是：编译与运行错误的边际信息量最高（它们直接排除一整片搜索空间），profile 的边际信息量中等（它缩小方向但不排除具体写法），roofline 的边际信息量最低（它只给二元判定）。因此把便宜且高信息量的信号放在前面，是降低单位有效反馈成本的关键。代价是漏斗前端的失败率：若生成质量差，大量候选死在编译门，profile 预算根本用不出去，此时应把预算转投到“从编译错误中学习”的提示构造上，而不是强行 profile 一个不可运行的 kernel。

一个具体例子：某矩阵乘变体连续三轮编译失败，错误均为 shared memory 超限。若管线只回灌布尔失败，模型会在同一方向上反复尝试；若回灌“当前 tile 配置需要 X KB 共享内存、硬件上限 48KB、建议降低 tile 高度或改用分块流式加载”，模型在下一轮直接改变 tile 形状。这里的代价是反馈构造本身需要解析编译输出并做资源核算，属于离线工程量，但它把无效轮次从多次压到一次。

五 · 为什么硬件反馈优于裸 speedup：可归因性与可验证性

裸 speedup 的根本缺陷是它把多维性能空间压缩成一维标量，丢失了归因信息。两个候选可以有相同的 speedup，但一个是 memory-bound 且访存效率已接近上限，另一个是 compute-bound 且占用率严重不足；对前者继续调访存是浪费，对后者调访存则完全无效。硬件反馈保留了“哪个维度是主矛盾”的信息，使变异方向可归因。这与论文的形式化立场一致：把 CUDA kernel 优化定义为一个有明确目标、约束与评测指标的代码优化任务，而约束与指标不止于一个加速比数字。

第二个优势是可验证性。编译错误与正确性失败是硬约束，不可协商；profile 指标是可复现的物理量，同一 kernel 在同一硬件上的 occupancy 与 stall 分布稳定。相比之下，speedup 受基线选择、TF32 开关、库版本、输入分布影响极大——论文的局限里明确写了基线若未开 TF32 或未用最强库，加速比会被高估。硬件反馈把评价从“相对某个可能被削弱的基线”部分转移到“相对硬件物理上限”，后者不随基线漂移。这也是 roofline 诊断在进化循环中的真正作用：它提供一个不依赖基线的绝对参照。

第三个优势是反馈与修复动作之间的映射更短。stall 原因到源码改动的映射是具体的：long_scoreboard → 提高 ILP/预取；mio_throttle → 降 bank conflict；barrier → 减同步。speedup 到源码改动的映射则是发散的，模型只能凭先验猜测。映射越短，单位 token 的修复效率越高。代价是硬件反馈的采集成本与解析成本，以及它对硬件与工具链版本的依赖——跨硬件迁移时，同一 stall 分布的归因可能失效，这是 profile 驱动进化在可移植性上的固有开销。

论文报告的最高 2.72× 平均中位加速比、36.75× 最大加速比、以及在 50 个算子中 28 个（56.0%）取得超过 2× 加速，这些数字本身不区分反馈机制；但“在严格正确性约束下取得 principled balance between performance and correctness”这一表述指向的正是反馈分层的设计——正确性门在前，性能信号在后，profile 归因决定方向。若把 profile 层拿掉、只留 speedup，进化会退化为对基线的过拟合，shape 特化与隐藏输入分布会让离线分数在生产上崩塌，这是论文局限里点明的失败模式之一。

六 · 回灌格式与上下文预算的工程约束

反馈最终要以文本形式进入模型上下文，格式设计直接决定信息密度。EvoEngineer 的工程约束可以归纳为三条：结构化优先于自然语言（报错行号、metric 名、比值用固定字段承载，减少解析歧义）、差分优先于全量（只回灌与上一轮相比变化的信号，避免重复已知信息）、摘要优先于原始（NCU 数百 metric 抽成十行以内的诊断块）。这三条共同对抗的是上下文预算：一段全量 NCU 输出加 SASS 反汇编可以轻易超过模型的有效注意力范围，导致关键信号被稀释。

差分回灌尤其重要。进化循环中，相邻两轮候选往往只差一个 tile 参数或一个同步位置，此时回灌“occupancy 从 0.42 升到 0.51、stall_barrier 占比从 31% 降到 12%”比回灌两份完整 profile 更有信息量，token 成本却低一个量级。代价是管线必须维护上一轮的 profile 快照并做字段级 diff，这是一笔状态管理开销，但换来的是每轮反馈的 token 效率。

还有一个常被忽略的代价：反馈文本本身的生成时延。编译输出解析、逐元素比对、NCU metric 抽取、SASS 片段裁剪，每一步都是 CPU 侧处理，在候选数量大时其累计时延可能超过 GPU 侧测量时延。因此反馈管线的吞吐应与 kernel 测量吞吐匹配，否则 GPU 空转等反馈。工程判断是：把反馈处理做成流水线并与下一批候选的生成重叠，用候选池深度吸收反馈时延的抖动。最终落在具体机制上——EvoEngineer 的可信度不来自某个加速比数字，而来自“编译门 → 正确性门 → profile 归因 → roofline 判定”这条漏斗每一层都可复现、每一层的信号都能映射到具体的下一轮变异动作；反馈的粒度与延迟结构，就是这条漏斗的物理形态。
