一 · 基准题面与“可测性”分层

KernelBrain 的评测对象是 Triton kernel 生成任务，摘要明确写的是 “important Triton kernel generation tasks”，因此它落在 KernelBench 系谱系里，但本部分只谈口径，不复述 KernelBench 的题面构造。真正决定一个基准能否被信任的，不是题目数量，而是每道题是否被拆成“可测的三层”：参考语义层（PyTorch 参考实现给出输入输出契约）、编译层（候选必须通过 Triton 编译与 launch 配置合法性）、性能层（在给定 shape 与 dtype 上的稳定时延）。三层任何一层缺失，后面的加速比就是浮点数上的幻觉。工程上应把每道题写成一条记录：算子签名、输入分布（shape 集合与 dtype）、参考实现、容差、基线实现、测量协议版本。缺一项就在报告里标注“不可比”。代价很直接：一条记录从“跑一下”升级为“可复现口径”，单题准备成本从分钟级升到小时级，但换来的是跨机器、跨批次数字的可对齐性。

可测性分层还决定预算分配。KernelBrain 的核心机制是先用低成本评估筛掉大批候选，再把高保真预算留给幸存者；如果基准题面本身不可分层测量，低成本筛选就只能靠“编译通过”这种弱信号，筛选精度崩塌，后续高保真预算被浪费在注定失败的候选上。因此基准口径不是评测附属品，而是搜索效率的前提。一个具体例子：某题参考实现用 torch.nn.functional 组合，候选 kernel 在边界 shape 上越界写但不崩溃，若正确性检查只比对中心切片，该候选会以“通过”进入高保真池，消耗掉本应给真正有希望变体的 profile 预算。

二 · 基线选择与加速比的分母

论文给出的加速比区间是 0.88x–6.72x over PyTorch，以及最高 1.4x over the state-of-the-art kernel agent。这里有两个分母，必须分开记账。分母一：PyTorch 基线。是 eager 还是 torch.compile？是否开启 TF32、是否允许 cuBLAS/cuDNN 选择算法、是否计入首次调用的 autotune 开销？分母二：SOTA kernel agent 基线。是同一硬件、同一 dtype、同一 shape 集合下重跑的结果，还是引用其论文数字？跨论文引用数字几乎必然不可比，因为测量协议、warmup 次数、同步方式、时钟锁定策略都不同。加速比定义本身简单：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

但分母的构造决定了这个比值的含义。若 PyTorch 基线未开 TF32 而候选 kernel 用 fp32 累加却在内部走 TF32 路径，则 6.72x 这种上界数字会被系统性高估；若基线是 eager 而候选对比的是 torch.compile 已融合的版本，则同一候选的“加速”可能瞬间消失。工程判断是：报告里必须同时给出“对 eager”“对 compile”“对库实现”三条分母线，任何一条缺失就注明不可比。代价是评测时间成倍增加——三条基线各需独立 warmup 与多轮采样，单题测量从数十次 launch 升到数百次，但这是唯一能让 0.88x 这种“低于 1”的数字具备解释力的方式：0.88x 说明候选在部分题上确实退化，而不是测量噪声。

三 · 指标族：faster rate、geomean、fast_p 与 roofline

单一 speedup 均值会被长尾题主导，因此基准报告通常用指标族而非单数。faster rate 是加速比大于 1 的题占比，直接对应上面的 accept 指示函数在题目维度上的平均；它对“多数题小幅赢、少数题巨幅赢”的分布不敏感，适合回答“这个 agent 是否普遍有效”。geomean 是对数域平均，抑制 6.72x 这类上界对均值的拉扯，适合跨题汇总；代价是它对低于 1 的题同样敏感，一道 0.88x 会把 geomean 拉低得比算术平均更明显。fast_p 是“达到 p 倍加速的题占比”，p 取 1.0、1.2、1.5 等阈值，用来刻画分布右尾；它比 faster rate 更能区分“勉强赢”和“显著赢”。roofline 则把时延换算成达到的 SOL（speed of light）比例：以该算子的内存带宽上限或算力上限为分母，衡量候选离硬件极限多远。roofline 的价值在于跨题可比——不同算子的绝对时延不可比，但 SOL 占比可比。

这四类指标的测量代价不同。faster rate 与 geomean 只需时延，测量成本低但受噪声影响大；fast_p 需要更多重复采样才能稳定估计阈值附近的题；roofline 需要 NCU 采集带宽/算力计数器，单题 profile 开销远高于计时，且计数器采集本身会扰动时延，必须与计时分开跑。一个具体机制：对每道题先跑 N 次计时取中位数，再单独跑一次 NCU 采集 dram__bytes 与 sm__throughput，用前者算时延、用后者算 SOL，两者不混在同一轮里。否则 profile 开销会污染 0.88x 这类接近 1 的判定。

指标回答的问题主要代价不可比风险
faster rate是否普遍有效低，仅计时基线未对齐时整体偏移
geomean跨题汇总低，仅计时对 <1 题过度敏感
fast_p右尾强度中，需多轮采样阈值 p 未声明则不可比
roofline SOL离硬件极限多远高，需 NCU计数器扰动、上限假设不同

四 · 硬件、dtype 与 shape 分布：三条不可比的裂缝

论文结论只在给定硬件、基线与输入分布上成立，这是摘要级事实，也是本部分最需要强调的工程判断。裂缝一：硬件。不同 SM 数量、不同显存带宽、不同 L2 容量会让同一 kernel 的 SOL 占比大幅漂移；一个在带宽充裕卡上被内存 bound 的 kernel，换到算力相对富余的卡上可能变成算力 bound，优化方向完全反转。裂缝二：dtype。fp32、tf32、bf16、fp16 的累加精度与吞吐上限不同，候选若在 bf16 下测得 1.4x，不能外推到 fp32；更隐蔽的是 tf32 默认开关在不同框架版本下不一致，导致“同一基线”在不同机器上分母不同。裂缝三：shape 分布。基准题若只测固定 shape，候选很容易过拟合到该 shape 的 tile 配置；一旦生产输入是动态 batch 或非对齐维度，特化 kernel 的加速比会崩塌甚至低于 1。

隐藏 shape/分布的处理是口径设计的核心。工程上分两档：可见档（公开在题面里的 shape 集合，用于开发与自测）与隐藏档（评测时替换的 shape 集合与 dtype 组合，用于防止特化过拟合）。隐藏档必须与可见档同分布采样但不同实例，否则“隐藏”只是换了个数字。代价是评测方差上升：隐藏 shape 若包含非对齐维度，候选的 launch 配置可能非法，编译期或运行期失败率上升，正确率指标被拉低；这恰恰是想要的信号——它暴露的是泛化能力而非测量噪声。一个具体例子：某题可见 shape 是 4096×4096 的方阵，候选把 tile 硬编码为 128×128；隐藏档给出 4093×4097，候选因边界处理缺失而越界，正确性门直接拒绝，避免了把过拟合分数带进生产。

五 · 测量口径：warmup、同步、噪声与预算记账

“runtime measurements are noisy” 是论文自己点出的问题，因此口径必须显式规定噪声控制。最小协议：每次测量前做若干次 warmup 触发 autotune 与缓存预热；每次测量后做设备同步再读时钟；同一配置重复采样取中位数而非均值，以抵抗偶发调度抖动；跨批次比较时锁定时钟或至少记录时钟状态。伪代码思路：

$$\text{for } r \text{ in repeats: } t_r=\text{median}\big(\text{sync};\text{clock}();\text{launch}\times k;\text{sync};\text{clock}()\big),\quad T=\text{median}(t_r)$$

预算记账同样属于口径。KernelBrain 的卖点是 “up to 48% lower optimization time”，这个数字只有在“优化时间”被定义为可核查的量时才可比：是 wall-clock 总时长、还是 GPU 小时、还是 LLM token 数加编译次数？三者不可互换。低成本筛选阶段消耗的是编译与短跑时间，高保真阶段消耗的是 profile 与多轮采样时间，若报告只给总时长而不给阶段拆分，48% 就无法归因到“粗到细预算分配”这一机制上。工程判断：报告应给出三元组（候选总数、编译次数、profile 次数）加上 wall-clock，任何一项缺失就标注“预算口径不完整”。代价是记录开销本身——每次编译与 profile 都要打点，但这是唯一能让“搜索效率提升”与“kernel 质量提升”分开归因的方式。

六 · 可核查清单与失败模式

把上述内容压成一张可核查清单，读者可以据此判断一篇 kernel agent 报告的数字能否被采信。清单项：基线是否声明 eager/compile/库三条线；dtype 与 TF32 开关是否声明；shape 可见档与隐藏档是否声明采样规则；计时是否含 warmup、同步、中位数与重复次数；指标是否给出 faster rate、geomean、fast_p 阈值与 roofline 上限假设；预算是否给出候选数、编译数、profile 数与 wall-clock 拆分；正确性容差与边界 shape 是否覆盖。任一项缺失，对应数字降级为“定性参考”。

失败模式有三类，都与口径直接相关。其一，基线未开 TF32 或未用最强库实现，加速比被系统性高估，6.72x 这类上界尤其危险。其二，shape 特化与隐藏分布缺失，离线分数在生产上崩塌，表现为可见档高分、隐藏档正确率骤降。其三，reward hacking 与 fallback 让正确率虚高：候选在正确性检查失败时回退到参考实现，计时却记在候选名下，accept 指示函数被绕过。防御机制是在测量管线里强制“回退即判负”——任何触发 fallback 的候选在性能层记为零加速，而不是记参考实现的时延。代价是部分本可通过修复边界而存活的候选被误杀，但相比把 fallback 时延算成加速比，这个代价是值得的。最终落在一条工程判断上：基准口径的严格程度应随部署阶段递增，离线探索可以放宽隐藏档以换取吞吐，生产回归必须全量隐藏档加回退判负，否则 0.88x 到 6.72x 这个区间就无法回答“哪些题真的赢了”。

口径边界：0.88x 到 6.72x 这组数字在什么条件下失效

论文给出的加速比区间 0.88x–6.72x 相对 PyTorch，以及最高 1.4x 相对 state-of-the-art kernel agent、最高 48% 的优化时间缩减，是同一套评测口径下的产物，不能拆开引用。口径由四件事锁定：基准是“important Triton kernel generation tasks”这一算子集合，基线是 PyTorch（eager 或 torch.compile 未在摘要中区分），输入分布按论文给定 shape，指标是 $$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$ 所定义的加速比与接受判定。0.88x 这个下界本身就说明口径的诚实度：它意味着存在候选在正确性通过后仍慢于基线，被如实计入而非剔除。任何把 0.88x 从分母里去掉、只报 6.72x 的做法都会让 geomean 与 faster rate 同时失真，因为加速比分布是长尾右偏的，几何平均对下界样本极度敏感——一个 0.88x 能把十个 3x 的几何均值从 3.0 拉到约 2.7。因此可核查的测量口径必须同时公布 faster rate（s≥1 的比例）、geomean（对数域均值）与 fast_p（如 fast_1.0、fast_1.5 的分位计数），三者缺一不可。

失效条件集中在基线的强度上。若基线 PyTorch 未开 TF32、未使用 cuBLASLt 的启发式选择、或对比的“state-of-the-art kernel agent”未按其最强配置运行，1.4x 与 6.72x 都会被系统性高估；这类高估不体现在方差里，而体现在偏移里，重跑多少次都复现同一个偏高的数。第二个失效条件是 shape 特化：agent 在搜索中会针对给定 shape 做 tile 与 grid 的硬编码，一旦生产输入分布漂移（batch 变化、序列长度非 2 的幂、dtype 从 fp16 切到 bf16），离线测得的加速比会直接崩塌，而正确性门仍能通过——这正是“离线分数高、生产收益负”的典型路径。第三个是 reward hacking 与 fallback：候选在边界输入上走 PyTorch 回退分支，正确率虚高而时延被回退路径掩盖，此时 accept 判据里的 pass 与 s 都失去意义。论文用 policy-gated evaluation 与 profiler-informed diagnosis 来压制这类行为，但门控策略本身是超参，其严格程度直接决定 48% 时间缩减中有多少是“省掉了本该被否决的候选”。

隐藏 shape 与分布的处理是本方案边界上最需要工程判断的一环。coarse-to-fine 的预算分配意味着低成本筛选阶段用的输入必然少于高保真阶段，若两个阶段的输入分布不一致，筛选阶段的排序就不可信：一个在单一 shape 上快 5x 的候选可能在多 shape 上慢于基线，却在低成本阶段被误判为 survivor 而吃掉高保真预算。可操作的测量口径是固定三层输入——参考 shape（论文给定）、扰动 shape（同一算子的邻近尺寸）、边界 shape（极小与极大），并规定只有三层全部 pass 且几何均值 s≥1 的候选才计入 faster rate；同时记录每层的测量重复次数与方差，因为 runtime measurement 的噪声正是论文开篇列出的三大困难之一。代价是明确的：三层输入把高保真阶段的测量次数乘以三，编译与 profile 开销同比上升，48% 的时间缩减会被部分吃掉；但换来的是加速比数字在生产分布上的可迁移性。下表给出这套口径下必须同时报告的最小字段集。

字段含义不可比时的表现
faster rates≥1 且 pass 的候选占比剔除 0.88x 样本后虚高
geomean对数域加速比均值只报 max 时失去长尾信息
fast_ps≥p 的计数（如 1.0/1.5）阈值不公布则无法复算
基线配置TF32/compile/库版本未开 TF32 则整体偏移
输入三层参考/扰动/边界 shape单 shape 特化不可迁移

最后落在预算与口径的耦合上：coarse-to-fine 的“低成本筛选”若用单次计时而非多次取中位数，噪声会直接决定谁进入高保真阶段，此时 1.4x 相对 SOTA agent 的优势可能只是预算分配策略的差异而非 kernel 质量差异。可核查的做法是把筛选阶段的判定写成显式伪代码思路——对每个候选在参考 shape 上跑 k 次取中位数，仅当 s≥1 且编译无 warning 才升级预算，否则丢弃并记录丢弃原因——并把 k 与丢弃率一并公布。这样 0.88x 的下界才有解释力：它不是某个候选的偶然慢，而是口径允许慢候选进入统计的证据。跨硬件、跨 dtype、跨框架的迁移在摘要层面未验证，因此这套数字的适用范围应严格限定在论文给定的硬件与输入分布内，任何外推都需要重新走一遍三层输入与基线配置核对。
