一 · 现场：一个 nightly 算子库的困境

设想一个在产线推理服务里维护算子库的团队。模型结构每隔几周就换一版，attention 的 mask 形态、MoE 的 top-k 路由、归一化的融合方式都在变；算子库里那批手写 CUDA kernel 是两年前为旧 shape 调出来的，其中若干已经在新的 batch 分布下退化成带宽瓶颈。团队面对的第一个事实是：手写 CUDA 的调优周期与模型迭代周期不匹配。一个中等复杂度的融合算子，从读懂 NCU 报告里那一屏指标（DRAM throughput、L2 hit rate、issue slot 利用率、warp stall 原因分布），到定位是访存合并没做好还是 occupancy 被寄存器数压死，再到改写出一个真正更快的版本，往往要经历若干轮“改—编译—跑—profile”的往返。每一轮往返的成本不只是工程师的时间，还有排队占用的 GPU 机时。

第二个事实是性能上限被人的注意力预算锁死。同一个算子，专家能想到的候选策略空间很大：tile 尺寸、线程块映射、shared memory 的 swizzle 方式、是否用 cp.async 做流水、是否把 reduction 拆成两级、是否走 tensor core 的 MMA 布局。但一个人在一次迭代里通常只验证两三个方向，剩下的方向因为“没时间试”而被永久放弃。这不是知识问题，是搜索带宽问题。第三个事实是正确性：手写 kernel 的边界条件（尾部 tile、非对齐 shape、NaN/Inf 传播、不同 dtype 的舍入）极易出错，而这类错误在 nightly 回归里未必能被小规模用例捕获，一旦漏到线上就是数值漂移。第四个事实是可维护性：手写 kernel 与 Triton 实现混在一起，注释稀少，原作者离职后没人敢动，性能优化变成“只增不改”的考古工作。

这四条痛点指向同一个结构性缺陷：优化过程没有可执行的反馈闭环。工程师脑子里的“假设—验证”循环是隐式的、不可复现的；换一个人、换一天，同样的起点会走出完全不同的路径。这正是 CudaForge 这类工作要处理的现场。

二 · 旧方案一：手写 CUDA 的反馈断层

手写 CUDA 的痛点不在于“难写”，而在于反馈信号的获取成本高且不可结构化。工程师看到的是 NCU 的一屏计数器，要把它翻译成“下一步改什么”，中间依赖大量经验性推断：stall 里 long scoreboard 占比高，说明访存延迟没被掩盖，可能要加流水或提高 occupancy；但如果同时寄存器用量已经接近上限，提高 occupancy 又会 spill，于是陷入两难。这个推断链条没有任何机制保证收敛，也没有记录，下一次遇到同类瓶颈仍然从零开始。

从代价上看，一次完整的调优往返包含：改写源码（分钟级）、编译（秒级到分钟级，模板重的 kernel 编译时间会显著拉长）、启动与计时（毫秒级但需要独占 GPU 以避免干扰）、profile 采集（NCU 逐 kernel 采集会带来可观的减速，采集粒度越细代价越大）。把这些加总，一个算子验证十个候选策略的成本是小时量级，而其中大多数候选会被证明是退步。更麻烦的是计时口径：不同工程师用不同的 warmup 次数、不同的计时工具、不同的 clock 状态，得到的“加速比”彼此不可比，导致性能结论无法沉淀。

正确性维度上，手写路径的把关完全依赖测试用例的覆盖度。一个典型例子是 reduction kernel 在 shape 不能被 tile 整除时的尾部处理：如果测试集里恰好只有整齐的 shape，尾部逻辑的错误会长期潜伏。这类错误的代价不是崩溃，而是静默的数值偏差，排查成本远高于编译错误。

三 · 旧方案二：Triton 与库调用的天花板

Triton 把写 kernel 的门槛降下来了：用块级编程模型描述 tile 上的计算，编译器负责线程映射与部分流水优化，开发者不必手写 warp shuffle 或 shared memory 布局。对大量 elementwise、reduction、matmul 变体，Triton 能在很短时间里给出一个“还不错”的实现，开发周期从周级压到小时级。但它把优化空间的一部分交给了编译器，当瓶颈落在编译器没有覆盖的维度上时，语言层表达力就成为上限。例如需要精细控制 shared memory 的 bank 冲突规避、需要手工安排 async copy 的多级流水深度、需要针对特定架构的 MMA 指令布局做寄存器重排，这些在 Triton 里要么表达不出来，要么表达出来后被编译器改写回它自己的调度。

库调用（cuBLAS、cuDNN、CUTLASS 实例）是另一条路：性能基线高、正确性有保证、维护成本低。代价是适配性。库的启发式选择针对通用 shape 分布调优，遇到融合机会（比如 GEMM 后接 bias、激活、量化）时，要么拆成多个 kernel 导致额外的显存往返，要么只能用库提供的有限 epilogue。一个具体的账：两个 kernel 各自读写一遍中间结果，多出来的显存带宽开销在带宽受限的融合场景里可以直接吃掉融合带来的收益。库调用还带来版本耦合——升级库版本可能改变启发式选择，性能随之漂移，而这种漂移不在团队的代码 diff 里，难以归因。

把三条旧路径放在一张表里对照，痛点的分布就清楚了：

路径开发周期性能上限正确性风险可维护性
手写 CUDA周级，往返次数多高，但受人的搜索带宽限制边界条件易漏，静默数值偏差低，知识不可复现
Triton小时级中，受语言表达力与编译器调度限制较低，语义清晰中，源码可读
库调用分钟级基线高但融合受限高保证高，但版本漂移不可见

三条路径共同的缺口是同一个：没有一条路径把“编译结果、运行正确性、硬件计数器”变成可以自动回灌给优化主体的结构化信号。人做这件事靠经验，库不做这件事，Triton 的编译器只做一次性的静态决策。于是当 LLM 被引入来生成 kernel 时，它继承的正是这个缺口——单轮提示生成的 kernel 既不知道编译会不会过，也不知道跑起来对不对，更不知道自己慢在哪。

四 · LLM 单轮生成的失效模式

把 LLM 放进这个现场，第一版的做法自然是“给任务描述，让它写 kernel”。这条路径的失效模式可以被精确刻画，而不是笼统地说“效果不好”。第一类是编译失败：类型不匹配、shared memory 声明尺寸超过静态限制、缺少必要的同步、API 签名记错。编译器的报错原文其实包含极强的定位信息（行号、期望类型、模板实例化路径），但单轮生成拿不到它，于是同一个语法错误可以在不同候选里反复出现。第二类是数值不符：逻辑写对了但边界处理错了，或者 reduction 的累加顺序导致浮点结果超出容差。第三类是崩溃与超时：越界访存、非法内存访问、死锁（漏了 __syncthreads），这类失败在沙箱里表现为进程被杀或挂起，如果没有超时捕获机制，整个评测流水线会被一个候选拖死。

第四类也是最隐蔽的一类：能跑、能对、但慢。单轮生成没有任何机制告诉模型“你这个版本的 DRAM throughput 只有峰值的四成，瓶颈在访存而不是计算”，于是模型在下一轮（如果有下一轮）只能靠猜。这就是为什么“生成结果性能不稳定”不是随机性，而是缺乏定向反馈导致的搜索盲目性。

用可验证信号的语言来写，单轮生成的评分函数退化成一个几乎不可用的门：

$$\text{score}(k)=\mathbb{1}\big[\text{correct}(k)\big]\cdot\frac{T_{\text{ref}}}{T_{k}}$$

这个式子里，$\mathbb{1}[\text{correct}(k)]$ 是门控项，$T_{\text{ref}}/T_k$ 是相对参考实现的加速比。单轮场景下，门控项大量取零（不可编译或数值不符），而即便取一，$T_k$ 也没有被任何反馈引导过，分布极宽。更关键的是，这个 score 只在最终候选上计算一次，中间过程不产生任何可用于改进的信号——它是一次性打分，不是搜索。CudaForge 的核心改动正是把这个一次性打分拆成每轮都可计算的信号，并把编译错误、运行差异与 profile 指标拼回提示，使 $\text{score}$ 从“事后评判”变成“事前引导”。

代价方面，单轮生成的 token 成本低（一次前向），但有效产出率低：大量候选在编译阶段就被淘汰，等于把 token 花在了不可能通过的样本上。而多轮闭环虽然每轮都要付编译、运行、profile 的机时与 token，却能把失败样本转成下一轮的修正输入——失败不再被丢弃，而是被结构化记录后回灌。这个转换是否划算，取决于单任务的平均轮数与每轮反馈的质量，而这两者在摘要级材料里都没有给出数字，属于必须实测的口径。

五 · 为什么非改不可：三个不可回避的工程约束

第一个约束是可复现性。产线算子库的性能回归必须能归因：这次 nightly 变慢，是 shape 分布变了，是驱动/库版本变了，还是某个 kernel 被改坏了？手写路径下，性能结论散落在个人笔记与口头传承里，无法机器校验。要让“每次修改是否真正带来端到端收益”成为可判断的问题，优化过程本身必须被记录成轨迹——每一轮的源码、编译结果、正确性判定、profile 指标与耗时都要落盘。这正是 CudaForge 把迭代轨迹与最优候选一并输出的工程动机：轨迹不是为了展示，而是为了事后复核与失败模式分析。

第二个约束是正确性门控必须先于性能排序。如果先按耗时排序再补正确性检查，一个越界但跑得飞快的 kernel 会污染最优候选的选择，且这种污染在只看最终结果的评测里不可见。把 $\mathbb{1}[\text{correct}(k)]$ 放在乘号左边不是排版习惯，是评测可信度的结构保证。第三个约束是反馈质量决定优化上限。硬件计数器到自然语言摘要的映射没有形式化保证：如果摘要把“L2 命中率低”误述成“计算利用率不足”，模型下一轮就会去改计算路径，做无效修改。这意味着闭环系统的稳定性不取决于模型规模，而取决于反馈组装器这一层的保真度。

一个具体的工程判断可以这样落地：在接入任何闭环框架之前，先测三个量——单任务平均轮数、每轮 profile 采集的时延开销、以及失败样本的修复成功率。前两个决定搜索开销是否吞掉性能收益，第三个决定反馈是否真的被模型用上了。这三个量在摘要级材料里均未给出，因此在生产决策前必须以自己的负载实测，而不能把机制描述当作定量结论引用。

六 · 旧方案的共同缺口与本篇的落点

把三条旧路径与单轮 LLM 生成并置，缺口的形状是一致的：优化主体与执行环境之间没有一条结构化的、每轮可用的信道。手写路径靠人脑做这条信道，带宽低、不可复现；Triton 把信道交给编译器，只走一次；库调用干脆没有信道；单轮 LLM 生成则完全断开。CudaForge 要做的不是发明新的 kernel 写法，而是把这条信道工程化——生成器产出源码，沙箱负责编译与崩溃/超时捕获，校验器比对参考输出，profile 采集器读取计数器与耗时，反馈组装器把错误原文、指标与差异摘要拼回下一轮提示。这条流水线的每一段在旧方案里都单独存在过（编译器、测试、NCU），但从未被串成一个以“下一轮提示”为输出的闭环。

因此本篇的落点是一个明确的工程判断：kernel 优化的瓶颈已经从“会不会写 CUDA”转移到“能不能低成本地获得并利用执行反馈”。在这个判断下，评价一个 agent 框架的第一顺位指标不是它生成的 kernel 有多快，而是它的反馈链路是否保真、是否可复现、失败样本是否被结构化回收。后续对 CudaForge 各组件的拆解，都应围绕这条链路的质量来读，而不是围绕单次加速比来读。

闭环之外的代价：当反馈链路本身成为瓶颈

把编译错误、数值差异与 NCU 计数器拼回提示，看似只是“多跑几轮”，实际把 kernel 优化的成本结构改写了。手工调优时，专家的时间主要花在读 SASS 与设计实验上，机器时间几乎可忽略；而在 CudaForge 这类框架里，每一轮都要付出一次完整编译、一次 GPU 启动、一次参考输出比对与一次 profile 采集。设单轮固定开销为 $$C_{\text{round}}=t_{\text{compile}}+t_{\text{run}}+t_{\text{profile}}+t_{\text{prompt}}$$，则 N 轮搜索的总代价近似 $$C_{\text{total}}\approx N\cdot C_{\text{round}}+N\cdot L_{\text{tok}}\cdot p_{\text{tok}}$$，其中 $$L_{\text{tok}}$$ 为每轮提示与生成的 token 量。这个式子的含义很直接：迭代成本随轮数线性增长，而性能收益却是次线性的——多数候选在头几轮就逼近该任务的可达上限，后续轮次往往只在做边际修正。材料明确未给出轮数上限与 token 成本，因此生产部署前必须实测单任务成本与收益比，防止搜索开销吞掉性能收益。

更隐蔽的边界在于反馈摘要的保真度。硬件计数器到自然语言提示的映射没有形式化保证：把“L2 命中率偏低”翻译成“改写访存或并行策略”这一步，依赖的是模板与模型对指标语义的解读，而非可验证的因果链。一旦摘要失真——例如把 occupancy 受限误判为带宽受限——模型会沿错误方向改写，后续轮次在错误盆地内反复震荡，正确性门控仍能通过，性能却停滞。此时 $$\text{score}(k)=\mathbb{1}\big[\text{correct}(k)\big]\cdot\frac{T_{\text{ref}}}{T_{k}}$$ 只告诉你“没变快”，不告诉你“为什么没变快”，搜索退化为随机游走。这是该方案相对手写调优最本质的失效条件：专家能从 SASS 直接读出 stall 原因，而反馈组装器只能给出压缩后的指标摘要，信息在压缩中丢失。

系统代价还体现在可维护性上。编译沙箱需要隔离以保证可复现，容器与驱动版本、profile 工具口径都成为必须锁定的工程资产；换一张 GPU 或升级一次驱动，历史轨迹的可比性就被打破。下表对比三种旧做法在该维度上的暴露面：

做法主要代价失效条件
手写 CUDA专家工时，周期以人日计专家稀缺，跨架构迁移需重调
Triton / 库调用表达力受 DSL 约束，调参空间有限算子超出库覆盖或需非常规布局
单轮提示生成token 成本低但结果不可编译、性能不稳无执行反馈，错误无法自纠

具体到一个推理服务场景：某算子库中的 attention 变体在特定 shape 下未命中库内 fast path，工程师要么手写 kernel 并逐版读 NCU，要么退回通用实现接受性能损失。CudaForge 的闭环在此处确有价值——它能自动把“编译失败”“数值不符”“耗时高于基线”三类信号转成下一轮修正指令，失败样本不被丢弃而是进入修正。但价值兑现的前提是反馈链路本身可信：若 profile 采集口径不一致，或摘要把瓶颈类别标错，多轮迭代只是在放大噪声。因此判断该方案是否可用，不能只看它能否生成可编译 kernel，而要看它在固定轮数预算下，单位 token 与单位 GPU 秒换来的端到端加速是否稳定为正——这个口径材料未给出，必须自行实测。
