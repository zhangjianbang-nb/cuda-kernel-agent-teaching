一 · 基准构成：任务集合的形态决定口径上限

该论文的评测负载被描述为“GPU kernel 优化任务集合”，但摘要级材料没有给出算子清单、题目数量与 shape 分布。这一缺口不是形式上的信息缺失，而是直接决定测量口径能否成立的结构性问题。kernel 优化任务的评测可比性由三个维度共同锁定：算子语义（elementwise、reduction、matmul、attention 等）、shape 分布（是否覆盖小 batch、非对齐维度、极端长宽比）、以及 dtype 组合（fp32/fp16/bf16/fp8 的混合精度路径）。三者任一未披露，外部读者就无法判断某一加速比是在什么条件下取得的。

从机制上看，任务集合的构造方式会系统性影响智能体的搜索行为。若集合以访存密集型算子为主，DSL 中分块与向量化参数的变异收益会被放大，speed-of-light 归一化差距对带宽上限更敏感；若以计算密集型算子为主，则流水策略与寄存器压力成为主导变量。论文未披露算子类型配比，意味着无法判断其声称的效率提升是来自对某一类负载的适配，还是具有跨负载的普遍性。这一点在复现时尤为关键：同一套 DSL 模板在不同算子族上的表达力差异，会直接转化为通过率与迭代轮数的差异。

具体到一个可核查的例子：假设任务集合包含一个 reduction 算子，其 shape 为 (4096, 8192) fp16 输入、沿第二维求和。该算子的 speed-of-light 由显存带宽上限决定，实测耗时与理论上限的比值对分块大小高度敏感。若论文未说明此类 shape 是否在集合内、占比多少，则任何关于“效率提升”的定性声明都无法映射到可复现的实验条件。工程判断上，读者应把“任务集合未披露”视为口径不可核查的一级信号，而非等待全文补充的次要细节。

二 · 基线与对照方向：自由形式生成不是可复现的基线

摘要仅以“自由形式代码生成的智能体”作为对照方向，未给出具体系统名称与版本。这在评测口径上构成一个比缺少数字更严重的问题：基线不可复现，则加速比的分母不可复现。自由形式 CUDA 生成的智能体在提示模板、迭代轮数上限、编译失败重试策略、温度采样参数上的任一差异，都会显著改变其最终产出的 kernel 质量。把这些变量笼统地归为“自由形式方向”，等于把一个多维配置空间压缩成一个标签，使对照失去可核查性。

从测量机制看，基线对照需要锁定至少四项：初始提示的算子规格描述粒度、每轮反馈的信息量（是否包含编译错误、是否正确性失败原因、是否包含 profile 数据）、迭代预算（轮数或 token 上限）、以及候选保留策略。论文的 DSL 方法在反馈层引入了 speed-of-light 归一化差距，这本身就是对基线反馈信息量的改变；若基线未获得同等信息量的反馈，则两者的差异不能全部归因于 DSL 约束。这一混淆在消融缺失的情况下无法拆解，摘要也确认未给出消融细节。

代价层面，基线不可复现直接转化为复现成本：外部团队若要重建对照，需要自行实现一个自由形式生成智能体，并对其提示与预算做任意假设，所得加速比与论文声明不可直接比较。具体例子是编译失败率这一指标——自由形式生成在高自由度下编译失败率通常显著高于受约束表达，但若基线未报告该指标，则 DSL 在“减少无效编译”上的收益只能定性表述，无法折算为编译次数或时延节省。工程上应把基线版本号与配置快照列为引用该论文结果的前置条件。

三 · 硬件与 dtype：speed-of-light 分母的物理依赖

speed-of-light 归一化指标的分母不是常数，而是硬件模型参数的函数。摘要明确未说明硬件型号与 speed-of-light 估计所依赖的硬件参数，这意味着公式中的 T_speed of light 无法被独立重算。该分母至少依赖峰值浮点吞吐、显存带宽、以及目标架构的缓存层次与占用率上限。不同 GPU 世代的带宽与算力配比不同，同一 kernel 的 SOL ratio 在不同硬件上不可直接横向比较——这是论文自身局限声明中承认的一点。

$$\mathrm{SOL\ ratio}=\frac{T_{\mathrm{measured}}}{T_{\mathrm{speed\ of\ light}}},\qquad \mathrm{gap}=1-\frac{1}{\mathrm{SOL\ ratio}}$$

dtype 的影响同样落在分母上。fp16 与 bf16 的峰值吞吐通常高于 fp32，若任务集合混合多种 dtype 而 speed-of-light 估计未按 dtype 分别建模，则归一化差距会系统性偏向高吞吐 dtype 的算子。更细的机制是：混合精度路径下，累加器精度与输入精度的组合会改变实际可达吞吐，而硬件模型若只取峰值算力，会高估理论上限，使 gap 被人为放大，引导信号朝不可达方向收敛。论文未披露 dtype 组合，这一偏差无法被量化。

一个可核查的具体场景：在带宽受限的 elementwise 算子上，T_speed of light 由“数据量除以峰值带宽”给出；若硬件型号未披露，读者无法确认峰值带宽取的是理论值还是实测可持续带宽。后者通常低于理论值，取理论值会使 SOL ratio 偏小、gap 偏大，智能体收到的“还有很大优化空间”信号可能是虚假的。工程判断上，引用该论文的 SOL 数字时必须同时记录硬件型号、dtype 与带宽取值口径，三者缺一即不可比。

四 · 指标族：faster rate、speedup、geomean、fast_p 的口径差异

kernel 智能体评测常用的指标族包括 faster rate（通过正确性检查且快于基线的题目占比）、speedup（单题实测耗时相对基线的比值）、geomean（各题 speedup 的几何平均）、fast_p（speedup 超过阈值 p 的题目占比）。这四个指标回答的是不同问题，混用会产生误导。faster rate 是计数型指标，对极端加速比不敏感；geomean 压缩了长尾，但对单题退化惩罚温和；fast_p 直接刻画“有多少题达到了可用加速门槛”，对生产端到端收益的映射最直接。论文摘要未给出任何一项的具体数值，也未说明采用哪一族指标。

机制上，这些指标对搜索过程的激励方向不同。若智能体以 geomean 为目标，它倾向于在所有题目上做小幅改善，避免在单题上冒险；若以 fast_p 为目标，它会把预算集中在少数有希望突破阈值的题目上。论文的反馈信号是逐题的 SOL 归一化差距，这更接近逐题优化而非集合级指标优化，因此其声明的“效率提升”究竟对应哪一族指标的改善，需要全文核实。缺少这一映射，读者无法判断效率提升是“更多题目变快”还是“少数题目变得很快”。

代价层面，指标选择影响 token 与编译预算的分配。以 fast_p 为目标的搜索会在低潜力题目上提前终止，节省编译次数但放弃潜在的小幅收益；以 geomean 为目标的搜索则需要在每题上维持迭代，编译运行开销更高。具体例子：若任务集合有 N 题，每题平均迭代 r 轮、每轮一次编译加运行，则总编译次数约为 N×r；fast_p 策略可通过早停把 r 压到低于 geomean 策略的水平，但代价是放弃部分题目的改善。论文未披露 N 与 r，这一权衡无法定量。

五 · 隐藏 shape 与输入分布：正确性 oracle 的覆盖面

隐藏 shape 与输入分布的处理方式，决定正确性检查是“样例通过”还是“语义等价”。摘要提到正确性检查作为硬约束置于编译运行之后，失败候选记录失败模式后回退变异，但未说明检查所用的输入是固定样例还是随机生成、是否覆盖边界 shape。若检查仅用单一 shape 的固定输入，智能体可能产出对该 shape 过拟合的 kernel——例如硬编码分块尺寸恰好整除该维度——而在隐藏 shape 上失败或退化。

从机制上看，正确性 oracle 的覆盖面与 DSL 的表达约束相互作用。DSL 在生成阶段拒绝非法分块与线程映射组合，这过滤了结构性错误，但不能过滤数值错误，例如归约顺序改变导致的浮点舍入差异、或边界处理缺失导致的越界读写。后者只有在特定 shape 下才暴露。因此正确性检查的输入分布必须与评测 shape 分布一致，否则硬约束的门槛低于实际部署要求。论文未披露输入分布与数据规模，无法判断是否覆盖访存密集与计算密集两类负载，也无法判断是否包含非对齐维度。

代价层面，扩大正确性检查的 shape 覆盖会增加每题的运行次数与时延。若每题在 k 个 shape 上验证，则运行开销约为单 shape 的 k 倍，且边界 shape 往往触发更慢的路径。具体例子：一个 matmul kernel 在 M=1 的瘦长 shape 上与在方阵 shape 上的最优分块完全不同，若正确性检查只覆盖方阵，智能体可能产出在瘦长 shape 上正确但性能极差的候选，而该候选仍能通过硬约束进入保留集合。工程判断上，隐藏 shape 的处理应被视为正确性口径的一部分，而非评测细节。

六 · 可核查的测量口径清单

综合上述缺口，引用该论文结果时应建立一份可核查的测量口径清单，逐项标注“已披露/未披露”。清单至少包含：任务集合的算子清单与题目数量；每题的 shape 与 dtype；硬件型号及 speed-of-light 估计所用的峰值算力与带宽取值（理论值或实测可持续值）；基线系统的名称、版本与迭代预算；指标族（faster rate / speedup / geomean / fast_p）及阈值 p；正确性检查的输入分布与 shape 覆盖；迭代轮数上限与候选池规模；编译次数与 token 成本。摘要级材料对上述各项均未给出，因此当前状态是“口径不可核查”，任何引用都应限定为定性声明。

口径边界：SOL 归一化指标的失效条件与测量代价

本方案的反馈信号不是毫秒数，而是实测耗时与硬件上限的比值，因此所有“效率提升”的声明都继承了这个比值的分母误差。设硬件模型给出的理论上限为 $$T_{\mathrm{sol}}$$，实测为 $$T_{\mathrm{meas}}$$，则引导信号为 $$\mathrm{gap}=1-\frac{T_{\mathrm{sol}}}{T_{\mathrm{meas}}}$$。关键在于 $$T_{\mathrm{sol}}$$ 由带宽、峰值算力与访存粒度等硬件参数推算，一旦模型低估了实际可达上限（例如忽略了非理想合并访问或 occupancy 受限），gap 会被系统性放大，智能体便朝一个并不存在的目标变异，收敛方向被扭曲。这不是噪声，而是偏差：多轮迭代不会把它平均掉，反而会沿错误梯度累积。因此引用该方法的加速比时，必须先确认分母的推导口径，否则跨硬件、跨 dtype 的数字不可比。

第二个边界是 DSL 表达力与搜索空间的交换。DSL 在生成阶段拒绝非法分块与线程映射组合，把无效编译挡在编译环节之前，代价是模板之外的调度策略（如非常规流水、跨算子融合、特定架构的异步拷贝组合）根本无法被表达。于是“效率提升”可能同时包含两部分：真实搜索压缩，以及把难优化算子直接排除在候选之外。二者在汇总指标里混在一起，单看 faster rate 无法区分。工程上应把超出模板的算子单列，报告其覆盖率与拒绝率，而不是并入总通过率。

测量代价同样要计入。每轮变异都要展开源码、编译、运行并采集耗时，编译时间与运行时间共同构成单轮成本；若正确性检查置于运行之后作为硬约束，失败候选仍消耗一次完整编译加执行，只是不进入保留集合。候选池越大、迭代上限越高，这部分沉没成本越显著。可核查的口径应至少固定：硬件型号与 dtype、SOL 模型参数来源、每轮编译次数与总编译时间、正确性 oracle 的具体判据、以及聚合方式（geomean 还是 fast_p 阈值）。缺少任一项，跨系统的 speedup 对比就不成立。
