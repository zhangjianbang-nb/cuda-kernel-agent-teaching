一 · 反馈对齐失效：当"显式规划"变成负资产

这篇论文最锋利的一句结论是"explicit planning is beneficial only when feedback is aligned"。把这句话当作工程判据来读，它实际上给出一张失效地图：规划不是免费的，它把反馈信号压缩成计划文本，而压缩过程本身会丢信息、会放大噪声、会锁定错误假设。当反馈与规划目标不同构时，显式规划从增益项变成损耗项。

机制上可以这样刻画：设第 g 代规划器接收的反馈集合为 F_g = {compile, run, profile, correctness}，规划器输出计划 P_g，再由代码生成器映射到候选 kernel K_g。失效发生在两处映射的复合上——反馈到计划的映射 f: F_g → P_g 是有损的，计划到代码的映射 h: P_g → K_g 是多值的。若 f 把 profile 中的占用率信号误读为"需要更大 tile"，而真实瓶颈是寄存器溢出导致的 occupancy 上限，则 P_g 会把后续若干代都钉死在错误方向上。这就是论文所说的"iterative planning amplifies early perturbations"：一次误读不是一代的损失，而是被冻结进轨迹的偏置。

$$\text{gain}(P_g)=\mathbb{E}\big[\text{speedup}(K_g)\big]-\mathbb{E}\big[\text{speedup}(K_g^{\varnothing})\big],\qquad K_g=h(P_g),\;K_g^{\varnothing}=h(\varnothing)$$

当 gain(P_g) ≤ 0 时，规划层应当被旁路。工程代价是明确的：每一代规划都要消耗 token（计划文本通常比 diff 长数倍），并且引入一次额外的模型调用时延；在编译时间本就以分钟计的 CUDA 场景里，规划层把单代墙钟时间推高，而如果它带来的是负增益，这笔开销就是纯亏。具体例子：编译反馈报出 "too many resources requested for launch"，规划器若把它归因为"block 尺寸过大"并持续缩小 block，而真实原因是每线程寄存器数超标，则连续数代都在错误的参数轴上搜索，正确性门始终不过，加速比恒为 1。

二 · 轨迹冻结的适用边界：它测的是结构，不是绝对值

CUDAnalyst 的核心手段是 trajectory freezing 加 selective feedback injection：冻结轨迹，使各代之间的状态可复现，然后只注入单一反馈分量，观察规划决策的变化。这套方法的价值在于把"反馈效应"与"轨迹漂移"解耦，但它的适用边界也正来自这个设计——它回答的是受控轴上的结构性问题，不是任意部署环境下的性能预言。

冻结意味着采样的多样性被牺牲。真实自演化 agent 的轨迹是随机的：温度采样、并行候选、编译器版本差异都会让同一提示产生不同路径。冻结后测得的归因是条件于某条被选定的轨迹，若该轨迹本身不代表典型路径（例如恰好早期就撞上一个幸运的正确 kernel），则 coalitional-style attribution 会把功劳错记给某个反馈分量。代价体现在统计效率上：要覆盖轨迹空间，需要多次冻结—重放，每次重放都包含完整编译与计时，显存与机器时间按重放次数线性增长。

论文声称这些趋势"hold across reference backbones, representative workloads, and reference induction regimes"，但这句话的限定词同样重要——robust within the controlled axes studied。跨硬件、跨 dtype、跨框架的迁移未被验证。具体例子：在某一代 GPU 上，profile 反馈中"L2 命中率低"是有效信号，规划器学会"提高数据复用"；换到 L2 容量更大、带宽更紧的硬件上，同一信号可能指向完全不同的优化轴，冻结实验里学到的反馈—计划映射就不再成立。因此把 CUDAnalyst 当作跨平台调优器使用是越界；它应当被当作诊断仪，用于回答"在这个固定栈上，哪个反馈分量真正驱动了计划质量"。

三 · 与相邻工作的差别：归因层而非生成器

把这篇工作放进同批条目里看，差别不在它生成了什么，而在它测量了什么。KernelBench 系工作定义的是"能不能写对、写快"的评测口径；CUDA-LLM、Kevin、CUDA-L1、CUDA-L2、Dr. Kernel 走的是多轮 RL 与对比式优化，产出的是更强的策略；Geak、Astra、CudaForge、cuPilot、EvoEngineer 产出的是 agent 脚手架与进化循环；Fine-Tuning GPT-5 for GPU Kernel Generation 走的是监督微调路线。这些工作的共同点是：它们都改变生成端，然后用端到端加速比作为证据。

CUDAnalyst 恰恰指出端到端消融在这里不可靠——迭代规划放大早期扰动，反馈效应与轨迹漂移混在一起，于是"加了反馈所以变快"这类结论无法被端到端实验支撑。它的定位是分析层：不替换生成器，而是给生成器加一个可控的观测面。这带来一个直接的工程判断——如果你要的是更高的绝对加速比，应当去用那些 RL 或进化类工作；如果你要回答"我的 agent 里四个反馈通道各自贡献多少、它们之间是冗余还是互补"，CUDAnalyst 才是对的工具。混用会出错：拿归因层的结论去论证生成器的优越性，等于用显微镜的读数去评价望远镜的放大倍数。

还有一层差别在反馈的粒度。RL 类工作把反馈压成一个标量奖励，天然丢失了"哪一条反馈起了作用"的信息；CUDAnalyst 保留分量结构，用 coalitional-style 归因处理分量间的交互——即反馈之间不是可加的，两个反馈同时存在时的效应不等于各自效应之和。这个交互项正是"structured multi-feedback interactions"所指。代价是组合爆炸：n 个反馈分量的联盟空间是 2^n，即便用近似归因，注入实验的次数也随分量数快速增长，每次注入都要一次完整编译与计时。

四 · 不该用它的四种情形

第一种：生产端到端收益评估。论文的结论只在给定硬件、基线与输入分布上成立，且摘要级信息未给出全部 shape。离线基准上的加速比若来自 shape 特化，隐藏输入分布会让分数在生产上崩塌；此时用 CUDAnalyst 的受控结论去背书上线决策，是把诊断当保单。正确做法是先做端到端回归，再看归因。

第二种：基线未校准的场景。若基线没开 TF32、没用最强库实现，加速比会被系统性高估，而归因实验会把这个高估一并继承——因为归因比较的是"有反馈"与"无反馈"在同一基线下的差，基线本身错了，差的符号都可能翻转。这类错误的代价不是时延，而是错误的技术判断：你会把资源投向一个本不存在的瓶颈。

第三种：反馈通道本身不可靠。若正确性门形同虚设，agent 可以用 fallback 或 reward hacking 让正确率虚高，那么注入"正确性反馈"这一分量的实验测到的是作弊路径的收益，而非真实信号的价值。此时归因结果具有误导性，且误导方向恰好是"正确性反馈很有用"。

第四种：需要跨栈迁移的调优。跨硬件、跨 dtype、跨框架的迁移未验证，冻结轨迹上学到的反馈—计划映射是栈局部的。把它当作可移植的调优知识库使用，等于假设不同 GPU 的 roofline 拐点相同——这在带宽受限与计算受限两类负载之间显然不成立。

$$\text{accept}=\mathbb{1}\big[\text{pass}\land s\ge 1\big],\qquad s=\frac{T_{\text{base}}}{T_{\text{agent}}}$$

这个接受判据本身就是一道边界：它只要求不慢于基线，不要求归因正确。一个靠 fallback 保住 s=1 的 agent 可以通过接受门，却在归因实验里表现出"规划无效"——因为它的计划从未真正改变过 kernel。具体例子：某代编译失败后 agent 直接回退到基线实现，正确性通过、加速比为 1，接受门放行；在冻结重放中，这一代被记为"反馈注入无效应"，从而低估了编译反馈的真实价值。这是接受判据与归因目标之间的结构性错位。

五 · 把边界写进使用协议

工程上可行的做法是把 CUDAnalyst 定位成"上线前的因果体检"，而非"上线后的性能保证"。体检协议包含三步：先在目标栈上固定基线口径（TF32 开关、库版本、输入分布），再冻结若干条代表性轨迹做分量注入，最后只把归因结论用于资源分配决策——比如决定是否值得为 profile 反馈多付一轮编译时延，而不是决定最终 kernel 选型。

代价核算要显式化。设注入实验次数为 m，单次编译加计时的墙钟为 t_c，则归因总开销约为 m·t_c，与生成端的 token 开销是两笔独立预算。若 m·t_c 超过一轮完整自演化搜索的成本，归因本身就失去了经济性——这时应当退回到粗粒度的端到端对照，接受"不知道哪个分量起作用"的不确定性。这是一个明确的工程判断：归因的精度必须与决策的价值匹配，为一次参数微调做全联盟归因是浪费，为一次架构级反馈改造做单分量消融则不够。

最后落在机制上：CUDAnalyst 的可信度来自轨迹冻结带来的可复现性，而它的不可迁移性也来自同一处——冻结把随机性移出了实验，也就把"换一个栈会怎样"移出了结论。使用它时应当把每条归因结论都标注上它的冻结条件（硬件、dtype、基线、输入分布），并在条件变化时重新体检，而不是把结论当作跨栈常量搬运。

反馈归因结论的失效边界与迁移代价

CUDAnalyst 的结论建立在“轨迹冻结 + 选择性反馈注入”这一受控实验装置上，因此它的适用边界首先由冻结本身定义。冻结意味着在某一代把规划轨迹钉死，只改动被注入的反馈分量；这能剥离 trajectory-dependent drift，但也把“规划对历史反馈的累积依赖”从因果链里切掉了。一旦真实 agent 的规划是跨代累积的——第 k 代的计划依赖前 k−1 代全部编译、profile 与正确性信号——冻结实验测出的归因权重就不再等于在线系统中的边际收益。代价是可量化的：若冻结窗口长度为 G 代，则归因结论的有效半径大致受限于 G 内反馈通道未饱和的前提；当某一通道（例如 NCU 的访存指标）在 G 内已把候选推向局部最优，后续注入的同类反馈边际信息趋近于零，此时 coalitional-style 归因会把该通道权重估高，因为它把“已饱和的重复信号”误记为“持续有效的信号”。工程判断是：把冻结窗口与反馈通道的饱和检测绑定，饱和即终止该通道的注入，否则归因表只是历史噪声的平均。

第二个失效模式来自评测口径与生产分布的对齐。论文的 accept 判据是 $$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$，其中 s 为相对统一基线的加速比。这个判据在离线基准上是干净的，但它对基线选择极度敏感：若基线未开 TF32、未用论文指定的最强库实现，s 会被系统性高估，于是“反馈对齐时显式规划有益”这一结论在迁移到生产基线时可能反转——生产端往往已用 cuBLAS/CUTLASS 级别实现，s≥1 的门槛骤然变紧，原本被判为 accept 的候选大批落到 1 以下。更隐蔽的是 shape 特化：agent 在给定输入分布上把 tile 尺寸、shared memory 布局、寄存器压力调到该 shape 的甜点，离线加速比漂亮，但隐藏输入分布（不同 batch、不同 dtype、非对齐 stride）一到，occupancy 与 bank conflict 结构全变，性能崩塌而正确性门仍然通过。这类候选在 accept 判据下是“真阳性”，在生产回归里是“性能假阳性”。因此 CUDAnalyst 式归因只能回答“在论文给定硬件、基线与输入分布内，哪种反馈驱动了计划”，不能回答“该计划在跨 dtype、跨框架、跨硬件时是否仍成立”——后者需要独立的分布外回归集，而不是归因层。

第三类边界是反馈通道的异构性与注入成本。CUDAnalyst 的价值恰在于把编译错误、运行正确性、profile 指标分开注入，但这也意味着它的结论粒度是“通道级”而非“信号级”：编译反馈是一个近乎二值的门，profile 反馈是连续的高维向量（时延、带宽、occupancy、stall 原因），二者在 coalition 归因中被压成同一量纲的权重，实际上编译门的边际信息在候选首次通过后即归零，而 profile 信号的边际信息随代际递减但不会归零。把两者放进同一张归因表，会掩盖“编译门只在早期有效、profile 只在后期有效”的时序结构。系统代价方面，选择性反馈注入要求每一代都重新编译、重新跑正确性检查并采集 profile，单次注入的端到端时延由编译时间（模板实例化与 ptxas 优化占大头）、基准测量重复次数与 NCU 采集开销叠加；当候选数量为 N、注入通道为 C、代数为 G 时，归因实验的总测量次数是 N×C×G 量级，而在线 agent 只需 N×G。这个 C 倍放大就是归因的税，它换来的是可解释性，不是吞吐。若把 CUDAnalyst 直接塞进 RL 训练回路做每步奖励塑形，token 与 wall-clock 预算会被归因实验吃掉，训练吞吐反而下降。

与相邻工作的差别也决定了“不该用它”的场景。端到端消融（关掉某类反馈看最终加速比）回答的是“该反馈整体是否有用”，代价是早期扰动被迭代放大、反馈效应与轨迹漂移混淆；CUDAnalyst 用冻结换来了干净的代级归因，代价是失去跨代累积效应。因此当研究问题是“某条反馈在长程自演化中是否会被 agent 学会利用”时，冻结实验给不出答案，应回到带轨迹的在线消融并接受其噪声。另一类相邻工作是纯执行反馈驱动的搜索（编译-运行-回灌），它不区分反馈通道，也就不需要归因层；当团队的目标只是拿到一个能跑的更快 kernel、且候选空间已被强基线压缩到 s≥1 稀疏时，投入 C 倍测量做归因的回报低于直接把预算花在更多候选采样上。判断准则可以写成：当归因结论要用于“调整反馈配比”这一决策，且该决策的收益上界高于 C 倍测量成本时，CUDAnalyst 值得用；当结论只用于“报告哪种反馈更重要”而无下游配比动作，或硬件/基线/输入分布即将迁移时，它是过度工程。论文自身也把稳健性限定在“受控轴内”，跨硬件与跨 dtype 的迁移未被验证，这正是把它当生产默认脚手架之前必须先补的回归项。
