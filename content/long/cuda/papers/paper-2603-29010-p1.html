一 · 一个 nightly 回归里的真实算子

设想某推理服务团队的 nightly 回归：某个 attention 变体在长序列 shape 上比上周慢了 18%，值班工程师打开仓库，发现这个 kernel 是半年前一位同事手写的 CUDA C++，文件里塞满了 __launch_bounds__、手工展开的 cp.async 流水、以及三段针对不同 SM 架构的 #if 分支。他既不敢改，也说不清慢在哪里——因为这段代码没有留下任何关于「当初为什么选这个分块」的记录。这正是这篇论文要处理的现场：不是实验室里从零写一个 GEMM，而是工程团队面对一堆已经存在、性能上限不明、正确性靠人肉保证、维护成本随架构代际线性增长的 kernel 资产。

在这篇论文之前，GPU kernel 工程的主流做法大致三条路，每条路都有明确的工程代价。第一条是手写 CUDA C++：表达力最强，能精确控制寄存器分配、shared memory 布局、warp 级原语与流水深度，但开发周期以人周计，且性能高度依赖作者对目标架构的直觉。第二条是 Triton：用块级编程模型把 thread/warp 级细节交给编译器，开发周期压缩到人天量级，代价是调度自由度被编译器接管，遇到编译器不擅长的模式（非规则访存、跨块流水、特殊归约）时性能上限被锁死，且调优手段只剩少数几个 BLOCK_SIZE、num_warps、num_stages 旋钮。第三条是直接调库：cuBLAS、cuDNN、CUTLASS 提供接近硬件上限的实现，开发周期近乎为零，但一旦算子形状或语义偏离库的覆盖范围——融合算子、自定义 epilogue、非标准 layout——就无库可用，只能退回前两条路。

三条路的共同痛点是：性能上限不可知。工程师改完一个 kernel，测出 0.42 ms，然后呢？这个数字是好是坏？距离这块 GPU 在这组 shape 上理论能做到的极限还有多远？没有这个参照，优化就退化成盲目的试错：改一版、跑一遍、看数字变没变，变了就留下，没变就再改。这种工作方式的迭代成本极高——每次变异都要经历编辑、编译、启动、计时、比对正确性的完整循环，而单次循环给出的信息量只有一个标量耗时加一个通过/失败位。

二 · 反馈稀疏：智能体接手后痛点被放大

当 LLM 智能体被引入来做 kernel 生成与优化时，上面这套工作方式的缺陷被成倍放大。自由形式的 CUDA 源码是一个几乎无约束的搜索空间：任何一个字符的改动都可能产生语义合法但性能迥异的新候选，也可能产生编译不过的垃圾。智能体拿到的反馈却极其贫瘠——编译成功/失败、正确性通过/失败、一个粗粒度耗时。这三类信号无法告诉它瓶颈在访存还是计算、是 occupancy 不足还是 bank conflict、是流水深度不够还是寄存器溢出。

于是智能体的行为退化为大范围的随机变异：它会在一次迭代里同时改动分块大小、线程映射、展开因子和流水策略，然后从结果里无法归因到底是哪个改动起了作用。搜索空间随代码自由度爆炸，迭代轮数与 token 成本随之高企——每一轮都要把整段源码送进上下文，模型再吐出一整段新源码，编译与运行的开销叠加在 token 开销之上。更糟的是无效变异：大量候选在编译阶段就被拒绝，或在正确性检查上失败，这些轮次完全不产生任何性能信息，纯属浪费。

这里可以写出旧方案的信息效率问题。设单轮迭代的总代价为 C = C_token + C_compile + C_run + C_verify，其中 C_token 随源码长度线性增长，C_compile 与 C_run 是固定开销但每次都要付。若一轮中有效性能信号的概率为 p（即候选既编译通过又正确），则获得一次可用性能观测的期望代价是 C/p。自由形式代码生成下 p 被编译失败与数值错误压低，而每次观测携带的信息量又只有一个标量耗时，于是「单位信息量的代价」被两个因子同时放大。这就是论文动机的定量骨架：不是智能体不够聪明，而是反馈通道太窄、搜索空间太宽。

$$\text{cost per usable signal}=\frac{C_{\text{token}}+C_{\text{compile}}+C_{\text{run}}+C_{\text{verify}}}{p_{\text{valid}}},\qquad \text{info per signal}\approx 1\ \text{scalar}$$

具体例子：智能体想把一个 layernorm 融合 kernel 的耗时从 0.9 ms 压下去。它先试了把 BLOCK_SIZE 从 256 改到 512，编译通过、正确、耗时 0.88 ms；下一轮它同时改了 BLOCK_SIZE、把两次归约合并成一次、并换了向量化宽度，结果编译失败——这一轮的全部 token 与编译开销归零。它无法从失败信息里判断是哪个改动导致的，只能整体回退再试。三轮下来，它既不知道 0.88 ms 离硬件上限有多远，也不知道下一步该往访存还是往计算方向调。

三 · 正确性与可维护性：两条被低估的代价线

性能之外还有两条代价线。正确性方面，手写 CUDA 的数值错误往往只在特定 shape 或特定边界条件下暴露：越界读写可能不崩溃但污染相邻 buffer，warp 内归约的 mask 写错只在非 2 的幂线程数下出错，cp.async 的 commit/wait 配对错误在低 occupancy 时偶发。这些错误在开发期难以覆盖，在智能体生成的候选里出现频率更高，而旧方案的反馈只在运行期才发现它们——一次编译加一次运行的开销已经付完，才发现候选是废的。

可维护性方面，手写 kernel 与架构代际强绑定。一次 SM 架构升级可能让精心调过的分块与流水参数从最优变成次优，甚至让某些 PTX 内联汇编失效。团队要么为每个架构维护一份分支，要么在升级后重新做一遍人工调优。Triton 缓解了这一点（编译器负责适配），但把调优自由度让渡出去；库调用则把适配责任转移给库的维护方，代价是失去对非标准算子的控制。三条路在「架构迁移成本」这一维度上各有各的账，没有一条能同时给出表达力、性能上限可见性与迁移低成本。

把这几条代价线并排放，旧方案的结构性缺陷就清楚了：它们都缺少一个归一化的性能参照和一个受限的变异空间。前者决定智能体能否判断「还差多远」，后者决定每次变异是否落在有意义的方向上。论文的两个核心机制——用 DSL 约束 kernel 表达、用 speed-of-light 归一化差距作为反馈——正是分别对准这两个缺口。DSL 把分块、线程映射、流水策略这些调度参数显式化为有限且语义合法的组合，非法结构在生成阶段就被拒绝，不进入编译环节；speed-of-light 把实测耗时折算成距硬件上限的比值，让每轮反馈从「0.88 ms」变成「SOL ratio 0.62，gap 0.38」，智能体据此判断瓶颈方向而非盲目试错。

$$\mathrm{SOL\ ratio}=\frac{T_{\mathrm{measured}}}{T_{\mathrm{speed\ of\ light}}},\qquad \mathrm{gap}=1-\frac{1}{\mathrm{SOL\ ratio}}$$

代价也随之转移：DSL 的表达力上限成为可优化算子范围的硬边界，超出模板的调度策略无法表达；speed-of-light 估计依赖硬件模型参数，估计偏差会直接扭曲引导信号，把搜索引向错误方向。这两条局限在本部分只需标记，其机制细节与工程后果属于后续部分的范围。就问题现场而言，判断是明确的：旧方案的三条路各自能解决一部分问题，但没有一条能同时把「变异空间受限」「性能上限可见」「正确性前移」三件事做到，而这正是智能体规模化做 kernel 优化时必须先补上的基础设施。

四 · 为什么非改不可：规模化的临界点

如果只是偶尔写一两个 kernel，旧方案的痛点尚可忍受。真正让问题变得不可回避的是规模化：当一个团队需要覆盖数十个算子、每个算子若干 shape 变体、每个变体在数代 GPU 上都要有可用实现时，手写路线的人力成本线性爆炸，Triton 路线的性能上限损失在关键路径上被放大，库调用路线的覆盖缺口累积成必须自研的长尾清单。此时引入智能体做自动化生成是自然选择，但若智能体仍工作在自由形式代码加稀疏反馈的旧范式上，它只是把人力成本换成了 token 成本与编译运行成本，并没有解决信息效率问题。

论文的立场可以概括为一个工程判断：智能体的效率瓶颈不在生成能力，而在反馈设计。把优化目标从「能跑」改为「逼近硬件上限」，把变异空间从「任意源码」收窄到「语义合法的调度参数组合」，是把智能体从盲目搜索推向定向搜索的两个必要动作。摘要层面只声称效率提升，未给出加速比、通过率、迭代轮数或 token 成本等任何量化口径，因此这套机制的实际收益必须以具体基准与硬件口径验证——这一点在引用时不可含糊。但问题现场本身是清楚的：旧方案在开发周期、性能上限可见性、正确性前移与架构迁移成本四条线上同时吃紧，而智能体的引入若不伴随反馈通道的重构，只会把这些代价换算成另一种形式继续存在。

一个具体的工程判断落在编译次数上：在旧范式下，每次变异都要走完整的编译链路，而 DSL 前端在生成阶段就拒绝非法分块或线程映射组合，等于把一部分本会浪费在编译器里的迭代提前拦截。编译一次的成本在大型 kernel 上是秒级到十秒级，几十轮无效变异累积起来就是可观的墙钟时间；把非法候选挡在编译之前，是这套方法最直接可测的收益点之一，也是后续部分要展开的机制细节的入口。

从手写调度到受约束表达：自由形式 kernel 工程的失效边界

以一个线上推理服务的算子库为例：同一套 attention 变体要覆盖多种 head 维度与序列长度，手写 CUDA 的工程师按 shape 分支维护多份模板，每份模板的分块、线程映射与流水策略都是隐式写在源码里的常量。当新硬件上线或新 shape 进入流量，改动落在源码层面，等于重新做一次调度设计——编译、跑正确性、profile、再改，循环以人日计。库调用（cuBLAS/cuDNN 一类）把这段周期压缩成一次链接，代价是把调度决策权交给库作者：shape 落在库的启发式覆盖范围内则性能可接受，落在边缘（极小 batch、非对齐维度、非常规 dtype 组合）则只能接受库给出的次优调度，且无法从外部观测到它为何选了这个 tile。Triton 处在两者之间，用 tile 级抽象换取了可移植性，但 autotune 的搜索仍以实测耗时为目标函数，配置空间随 num_warps、num_stages、BLOCK 尺寸组合膨胀，单算子调优的编译与试跑次数在工程上不可忽略。

这三条路径的共同瓶颈不在“能不能写出来”，而在反馈的信息密度。自由形式 CUDA 源码的自由度包括循环结构、共享内存布局、同步位置、指令级选择，搜索空间随代码行数指数增长；而执行反馈通常只有通过/失败与一个粗粒度耗时数字。智能体面对“耗时 0.42 ms”无法判断瓶颈在访存带宽、占用率还是指令依赖链，只能做盲目变异，大量候选在编译阶段就被语法或资源约束拒绝，或在运行期才暴露数值错误。设候选空间为 $$|\mathcal{S}|=\prod_{i} |\theta_i|$$（各调度参数取值数之积），在无约束表达下 $$|\theta_i|$$ 本身不受语义合法性裁剪，无效组合占比高，编译与试跑开销按候选数线性放大；token 成本则随迭代轮数累积，因为每一轮都要把源码与反馈重新送入模型上下文。

正确性与可维护性构成第二重代价。自由形式代码的正确性检查只能放在编译运行之后，失败候选已经消耗了一次编译与一次 GPU 执行；数值错误（越界、竞态、精度退化）与编译错误混在同一失败信号里，智能体难以区分该修语法还是该改调度。可维护性上，同一算子的多份手写模板之间没有共享的中间表示，调度知识以注释和口口相传的形式存在，无法被工具链校验，也无法被智能体复用。这正是需要引入受限表达的原因：把分块、线程映射、流水策略显式化为 DSL 参数，让非法组合在生成阶段被拒绝，把正确性护栏前移；同时把反馈从绝对毫秒数换成相对硬件上限的归一化差距，使单轮反馈携带“瓶颈在哪、还差多远”的信息。这一转换的边界同样明确：DSL 模板覆盖不到的调度策略无法表达，speed-of-light 估计依赖硬件模型参数，估计偏差会直接扭曲引导方向；因此该方法的价值必须以具体基准与硬件口径验证，而不能把“效率提升”的声明直接当作已验证的加速比。
