一 · 基准题面：从“算子集合”到“可执行任务”的口径

《Ask, Don't Equip》的实验面并不以“多少个算子”作为卖点，摘要里给出的任务锚点是一个具体而窄的对象：把已有的 CUDA kernel 变快，且不依赖算子专属知识、也没有更快的实现可以模仿。KernelSeek 的评测落点是 FlashAttention 前向 kernel，在 Hopper 与 Blackwell 两代架构上各自产出无依赖的单文件 CUDA 实现（不引入 CUTLASS、CuTe、cuBLAS、cuDNN）。这意味着本部分的基准口径必须区分三层：题面层（“给定一个已有 kernel，让它更快”）、实现层（单文件、无第三方库依赖、可独立编译）、场景层（每架构 182 个测试场景）。三层中任何一层被替换，加速比就不再是同一个量。

题面层的机制是“起点固定”：agent 拿到的不是空白函数签名，而是一份已能正确运行的 CUDA kernel，任务是改写它。这与从零生成 kernel 的基准在测量语义上完全不同——后者的基线往往是 PyTorch eager，前者的基线是“给定的那份 kernel 自身”。因此当论文报告 KernelSeek 达到 1.13x 时，分母是那份既有 kernel 的时延，而不是某个库调用。工程上必须把这一点写进测量口径：$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}}$$ 中的 Tbase 必须明确标注是“给定 kernel 的原版”还是“库实现”，两者不可混用。论文摘要里同时出现了“1.13x”与“1.16x FlashAttention-3”两种表述，前者对应同任务同评测器下的既有 kernel 起点，后者对应与 FlashAttention-3 的比较；把它们放进同一张表而不标注分母，就是不可比的典型来源。

实现层的代价是编译时间与可移植性。单文件、无 CUTLASS/CuTe 依赖的约束，换来了“可直接丢进任何 CUDA 工具链编译”的便利，代价是放弃了库内已经调好的 tile 调度与流水线原语，agent 必须自己写出等价结构。这一约束对测量有直接影响：编译时间被计入候选筛选成本，而候选数量在开放式 agent 里是成千上万次评测量级（摘要明确指出开放式 agent 为自由度付出的代价是数千次评测、反复编辑与错误候选）。因此“每候选平均编译+运行秒数”是必须记录的二级指标，否则无法解释为什么某些 agent 在相同 wall-clock 预算下评测数更少。

场景层的 182 个场景是正确性口径的核心。论文声称 KernelSeek 产出的 kernel 在每架构全部 182 个场景上正确。这里的“场景”至少包含 shape、dtype、序列长度、head 配置等维度的组合，但摘要未给出具体分布。可核查的做法是把场景表当作一等公民：记录每个场景的输入张量形状、dtype、是否 causal、是否带 mask、batch 与 head 数，并逐场景记录通过/失败。只报“182/182 通过”而不公开场景表，等价于把正确性 oracle 变成一个黑箱，读者无法判断这 182 个场景是否覆盖了边界（如非 2 的幂序列长度、极短序列、head_dim 非 64/128 的情形）。

二 · 基线选择：三种分母与它们各自的偏差方向

论文给出的基线集合是 PyTorch eager、torch.compile 与论文指定的库实现。这三者在同一张加速比表里代表三种不同的分母语义，偏差方向也各不相同。eager 基线通常最慢，用它做分母会系统性高估加速比；torch.compile 基线取决于是否触发融合、是否走 inductor 的模板路径，方差大；库实现（此处的 FlashAttention-3）是最强基线，用它做分母得到的数字最小、也最保守。论文的 1.16x 是对 FlashAttention-3 的比值，属于最强基线口径，这一点必须在表格里显式标注，否则读者会误以为是对 eager 的比值。

更隐蔽的偏差来自数值精度开关。摘要未提及 TF32 是否开启。若基线侧未开 TF32 而 agent 侧开了，矩阵乘类 kernel 的加速比会被系统性放大；反之若基线开了而 agent 侧保持 FP32，则加速比被压低。可核查口径要求：两侧使用同一 dtype、同一 TF32/FP32 策略、同一 cuBLAS 数学模式，并在结果表里单列一栏“数值模式”。这不是苛求，而是因为 FlashAttention 类 kernel 的时延对 head_dim 与 dtype 极其敏感，任何一侧的精度降级都会让 1.16x 这个数字失去意义。

第三个偏差源是“同周同硬件”的时效性。论文明确说明对比是在“same task, evaluator, hardware, and week”下进行的：一个工具丰富的自主 agent 在 133 个模型驱动步骤后停在 0.50x FlashAttention-3，而 KernelSeek 达到 1.13x。这句话的信息量在于它把“周”写进了口径——库实现每周都在更新，跨周比较等于换了分母。工程上应把基线版本（commit、wheel 版本号）与测量日期一并记录，否则 0.50x 与 1.13x 的差距可能部分来自基线漂移而非 agent 能力。

代价层面：三种基线各自的测量成本不同。eager 基线几乎零准备成本但信息量低；torch.compile 需要预热与编译缓存，首次测量会被编译时间污染，必须做 warmup 后再计时；库实现需要固定版本并验证其自身在该 shape 上确实走的是预期 kernel（而非 fallback 到通用实现）。一个具体例子：若 FlashAttention-3 在某组 head_dim 上回退到非最优路径，则 agent 侧只要写出一条针对该 head_dim 的专用 kernel 就能轻松拿到大于 1 的比值，但这个比值不反映真实优化能力。因此基线侧必须做“基线自检”——确认基线在其声称的最优路径上运行。

三 · 指标族：faster rate、speedup、geomean 与 fast_p 的分工

论文摘要只给出 speedup 与 accept 两个形式化定义：$$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$ 其中 pass 是正确性门，s 是加速比。这个定义把正确性与性能合成一个布尔量，适合做“通过率”统计，但它丢掉了幅度信息：一个 1.001x 的候选与一个 1.5x 的候选在 accept 上等价。因此工程口径必须同时报告三个量：faster rate（s>1 的候选占比，即 accept 在全部候选上的均值）、speedup 的分布（中位数与 geomean）、以及 fast_p（s≥p 的候选占比，p 取 1.1、1.2 等阈值）。三者分工明确：faster rate 衡量“能不能赢”，geomean 衡量“平均赢多少”且对极端值稳健，fast_p 衡量“赢得够不够多”。

geomean 的选择有明确理由：加速比是比值，算术平均会被个别超大加速比拉偏，几何平均在对数尺度上对称，适合跨任务聚合。但 geomean 有一个陷阱——它要求每个任务都有有效加速比，任何任务上的失败（编译失败、正确性不通过）若被记为 0 或丢弃，都会让 geomean 失真。正确做法是把失败任务按惩罚值计入（例如记 s=0 或以基线时延计入），并在表里注明惩罚规则。论文的 accept 定义天然处理了这一点：不通过的候选不计入分子，但也不应被静默地从分母里删掉。

roofline/SOL 是第四类指标，它与 speedup 正交。speedup 是相对量，roofline 是绝对量：把实测时延换算成达到的带宽或算力，再与该硬件的峰值比较，得到 SOL（speed of light）百分比。相对量的危险在于“基线本身很慢”时，一个平庸的 kernel 也能拿到好看的 speedup；绝对量则能揭示剩余空间。工程上应把两者并列：一个 1.16x 的 kernel 若 SOL 只有峰值的 30%，说明还有结构性的优化余地，agent 的下一步假设应该指向那里，而不是继续在 1.16x 上做微调。这正是论文“缺的是方向、是一个关于剩余差距在哪里的假设”的论点在测量层面的对应物。

代价：指标越多，测量成本越高。SOL 需要带宽/算力峰值参数与逐 kernel 的字节数/FLOPs 计数，计数错误会让 SOL 失真；fast_p 需要足够多的候选样本才能稳定，候选数少时 fast_p 的置信区间很宽。一个具体例子：若某 agent 只产出 5 个候选，fast_1.2 的取值只能是 0、0.2、0.4……，这种粒度不足以支撑“该 agent 更擅长产出高倍率 kernel”的结论。

四 · 不可比清单：哪些数字不能放进同一张表

第一类不可比是分母不同。给定 kernel 起点（1.13x）与库基线（1.16x FlashAttention-3）是两种分母，不能合并成一个“KernelSeek 平均加速比”。第二类不可比是硬件代际不同。Hopper 与 Blackwell 的峰值带宽、SM 结构、异步拷贝原语都不同，同一 kernel 在两代上的 speedup 不可直接平均；论文分别报告两代架构的 182 场景正确性与 1.16x，这个分列做法应被保留，而不是压成一个数。第三类不可比是评测周不同，前文已述。第四类不可比是候选预算不同：133 个模型驱动步骤的自主 agent 与 KernelSeek 的步骤数若不等，则 0.50x 与 1.13x 的对比混合了“方法差异”与“预算差异”，必须同时报告步骤数与 wall-clock。

第五类不可比最容易被忽略：正确性口径不同。有的工作报告“编译通过即算通过”，有的报告“在少量随机输入上数值接近”，论文的口径是 182 个场景逐架构全通过。这三种口径下的通过率不可比。可核查的做法是把正确性 oracle 写成显式规则：容差（atol/rtol）、比较对象（参考实现的输出）、是否允许 NaN/Inf、是否检查非连续输入与广播。FlashAttention 类 kernel 还涉及 softmax 的数值稳定性，容差设得过松会让错误实现蒙混过关。

第六类不可比是“是否允许特化”。论文强调 KernelSeek 不依赖算子专属知识，但未说明候选是否被允许针对具体 shape 做特化。若允许，agent 可以为 182 个场景各写一条分支，正确率与加速比都会好看，但生产上遇到隐藏 shape 就会崩塌。因此口径里必须有一栏“shape 泛化策略”：是单一 kernel 覆盖全部场景，还是按 shape 分派。这一栏缺失时，1.16x 的含义是模糊的。

代价：把不可比清单写全，会让结果表变宽、变难读，也会暴露更多“论文没说的东西”。但这是可信评测的必要成本——一张只报一个数的表，读者无法判断这个数属于哪一类分母、哪一代硬件、哪一种正确性口径。

五 · 隐藏 shape 与分布：离线分数如何不在生产上崩塌

隐藏 shape 的处理是这类基准最脆弱的一环。论文摘要未给出全部 shape，只给出 182 个场景这一计数。工程上应把场景集划分为“公开集”与“隐藏集”：公开集用于 agent 迭代，隐藏集只在最终评测时使用，且隐藏集的分布要与生产流量对齐（序列长度分布、batch 分布、是否长尾）。若两者同分布，隐藏集只能检测过拟合；若两者不同分布（例如公开集全是 2 的幂序列长度，隐藏集含质数长度），隐藏集才能检测泛化。论文的 182 场景是否包含非 2 的幂长度，摘要未说明，这正是需要核查的点。

机制上，shape 特化的收益来自 tile 尺寸与序列长度的整除关系。当序列长度是 tile 的整数倍时，边界处理代码可以被编译期消除；非整除时则需要谓词化加载与尾块处理，时延上升。一个针对 2 的幂长度调优的 kernel 在质数长度上可能退化到比基线更慢。因此测量口径应包含“跨 shape 的 speedup 方差”，而不只是均值。方差大意味着特化，方差小意味着泛化。这个量与 fast_p 互补：fast_p 看阈值通过率，方差看稳定性。

分布偏移的代价是双重的：离线分数虚高，生产端回退。工程判断是——在离线基准里主动构造“分布外场景”子集（极短序列、极长序列、非整除长度、非连续输入），并单独报告该子集上的 faster rate。若某 agent 在公开集上 1.16x 而在分布外子集上低于 1.0x，则它的分数应被标注为“条件性加速”，不能作为部署依据。论文的 182 场景若已覆盖这些边界，应在表里注明覆盖了哪些维度；若未覆盖，读者应把 1.16x 理解为“在论文给定分布上的加速比”，这与论文自身的局限声明一致。

另一个隐藏变量是输入数据分布对性能的影响。对于注意力类 kernel，causal mask 的有无会改变有效计算量；若基线侧与 agent 侧对 mask 的处理方式不同（例如一侧跳过上三角、另一侧全算后屏蔽），时延差异会被误读为 kernel 质量差异。口径要求：mask 语义必须两侧一致，并在场景表里标注 causal/non-causal。

六 · 可核查的测量口径模板

把上述讨论收敛成一张可执行的记录表，是本部分要交付的工程物。每条记录至少包含：任务标识（起点 kernel 的哈希）、基线类型与版本（eager / torch.compile / 库 commit）、硬件型号与架构代际、dtype 与 TF32 策略、场景表（shape、causal、mask、batch、head 配置）、正确性 oracle（容差、参考实现、NaN 规则）、计时方法（warmup 次数、重复次数、取中位数还是最小值、是否用 CUDA event）、指标（faster rate、geomean speedup、fast_1.1/fast_1.2、SOL 百分比）、候选预算（模型步骤数、wall-clock、编译+运行总秒数）、以及 shape 泛化策略（单 kernel 还是分派）。这张表的作用不是让结果更好看，而是让任何一个数字都能被追溯到它的分母、硬件与正确性口径。

计时方法本身有代价与陷阱。用最小值计时会低估真实时延（忽略缓存抖动与调度噪声），用中位数则对长尾更稳健但需要更多重复。CUDA event 计时必须包裹足够多的迭代以摊薄 launch 开销，否则短 kernel 的时延被 launch 主导，加速比失真。一个具体例子：FlashAttention 在极短序列上的单次时延可能只有几微秒，若每次迭代都同步一次，同步开销会淹没 kernel 时间，此时应改为批量迭代后统一同步并除以迭代数。

最后落在工程判断上：论文给出的 0.50x 与 1.13x 是在“同任务、同评测器、同硬件、同周”下取得的，这个四同条件是这组数字唯一可比的前提。任何把这组数字搬到另一块 GPU、另一版库、另一套场景表上的引用，都必须重新建立分母与正确性口径，否则 1.13x 只是一个失去锚点的字符串。测量口径的价值正在于此——它把“论文声称”翻译成“可复现的条件”，而 KernelSeek 的 182 场景全通过、1.16x FlashAttention-3、以及 1.46 这一数字锚点，只有在口径完整时才能被读者独立核查。
