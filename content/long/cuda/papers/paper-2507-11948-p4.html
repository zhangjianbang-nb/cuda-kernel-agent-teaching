一 · 反馈回灌的三种通道：编译、运行、性能

在多轮闭环里，反馈不是一坨文本，而是按语义分成三条通道，每条通道的序列化格式、延迟与信息密度都不同。编译通道回传的是编译器诊断（错误码、出错行、模板实例化栈、寄存器溢出警告）；运行通道回传的是退出状态与正确性判定（段错误、越界、非法访存、与参考实现的逐元素比对结果）；性能通道回传的是计时与计数器（kernel 墙钟、带宽利用率、occupancy、warp stall 原因分布）。三者的关键差别在于：编译与运行反馈是离散且可判定的，性能反馈是连续且带噪声的。把三者塞进同一段自然语言提示，模型会倾向于抓住最显眼的那条（通常是编译报错），而忽略性能通道里的细粒度信号。因此工程上更稳的做法是给每条通道独立的字段槽位，并在提示模板里固定顺序，让模型每一轮都看到"编译状态—正确性状态—性能摘要"三段式结构，而不是一段自由文本。

一个具体的机制是：编译失败时只回灌诊断通道，不进入运行阶段，这样单轮延迟被压到编译时间量级；编译通过但运行错误时回灌运行通道并附带最小复现的输入 shape；只有正确性通过后才采集性能信号。这个门控顺序本身就是一种信息压缩——它把"当前该修什么"的优先级编码进了反馈的可见性。代价是：一旦正确性判定过于宽松（例如只比对少量随机样本），模型可能带着隐性错误进入性能优化阶段，后续所有性能反馈都建立在错误内核上，轨迹被污染。这就是正确性 oracle 必须比性能口径更严格的原因，也是本片段与形式验证条目分工的边界。

$$\text{feedback}_t=\big(\,\text{diag}_t,\ \text{verdict}_t,\ \text{prof}_t\,\big),\quad \text{prof}_t \text{ 仅在 } \text{verdict}_t=\text{pass} \text{ 时非空}$$

举例：一个 reduction 内核首轮编译报"共享内存数组大小必须是编译期常量"，第二轮模型改成动态共享内存但忘了同步，运行通道回传逐元素比对的最大绝对误差超阈值；第三轮修正同步后通过，性能通道才第一次给出该 kernel 的带宽利用率与 stall 分布。三轮里模型看到的字段数量不同，这正是门控设计的意图。

二 · NCU 与 SASS 级信号的降维：从计数器到可行动诊断

NCU 采集的原始指标动辄上百个，直接回灌既不现实也无益——模型的上下文预算有限，且大部分计数器与当前瓶颈无关。有效做法是先做roofline 定位：用实测的 FLOPs 与字节吞吐对照该 GPU 的峰值算力与峰值带宽，判断 kernel 落在计算受限区还是访存受限区，再只回灌与该区相关的少数几个指标。访存受限时看 DRAM 吞吐占比、L2 命中率、合并访存效率；计算受限时看指令发射率、pipe 利用率、是否存在长依赖链。这一步把"一百个计数器"压成"一个瓶颈判断加三个佐证指标"，信息密度反而上升。

SASS 级反馈的价值在于它绕过了源码层的抽象。模型写的 CUDA C++ 经过编译器优化后可能面目全非：循环被展开、寄存器被重排、分支被谓词化。当源码看起来合理但性能不佳时，回灌一段热点 SASS（例如发现某个内层循环里出现了大量 LDG 而非 LDG.128 向量化加载，或出现了本地内存 spill 的 LDL/STL）比回灌源码级建议更直接。但 SASS 回灌的代价很高：反汇编文本长、token 消耗大、且模型对 SASS 语法的先验弱，容易产生"看懂但改不对"的空转。工程折中是只回灌统计摘要——指令 mix 的占比、spill 的字节数、分支发散的比例——而不是整段反汇编。

信号层信息量token 代价可行动性
编译诊断高（定位到行）低直接
运行判定中（定位到语义）低直接
roofline 瓶颈判断高（定位到资源）中中
SASS 统计摘要中（定位到指令）中高中
原始计数器全量低（噪声淹没）极高弱

warp stall 的原因是这条链上最容易被误用的一环。NCU 给出的 stall 原因（如 long scoreboard、barrier、MIO throttle）描述的是"warp 为什么没发出下一条指令"，但它不直接告诉你该改什么。把 stall 原因原样回灌，模型常见的反应是盲目加 occupancy 或改 block size，而真正的病因可能是访存模式不合并导致的 long scoreboard。因此回灌时应把 stall 原因与访存效率指标捆绑呈现，让模型看到"stall 类型 + 对应资源指标"的配对，而不是孤立的 stall 排名。

三 · 反馈的粒度与延迟：为什么"每轮全量 profile"是陷阱

多轮 RL 的样本效率受两个成本支配：每轮的推理 token 与每轮的执行墙钟。全量 NCU 采集会让单轮墙钟膨胀一个数量级以上——NCU 需要串行化、重放 kernel、多次采样以降低噪声，这对一个需要跑几十轮的轨迹来说是致命的。更严重的是，全量 profile 的噪声会污染奖励：同一内核两次采集的带宽利用率可能因 GPU 频率波动而差异明显，若奖励直接取单次测量值，策略会学到"运气好"而非"写得好"。

可行的粒度策略是分层触发：前若干轮只回灌编译与正确性，让模型先把内核写对；正确性稳定后再引入轻量计时（多次运行取中位数）作为粗粒度性能信号；只有当粗粒度信号显示该内核已进入有竞争力的区间，才触发一次 NCU 采集做瓶颈归因。这样 profile 的次数被压到轨迹的少数几轮，token 与墙钟成本可控，同时保留了关键轮次的诊断深度。代价是：模型在早期轮次看不到瓶颈细节，只能靠粗粒度信号做方向性探索，收敛可能更慢——这是用样本效率换执行成本的典型权衡。

$$\text{cost}_{\text{turn}}=\underbrace{c_{\text{infer}}}_{\text{token}}+\underbrace{c_{\text{compile}}+c_{\text{run}}}_{\text{墙钟}}+\underbrace{\mathbb{1}[\text{trigger}]\,c_{\text{ncu}}}_{\text{重放与采样}}$$

举例：一个 matmul 内核在第 2 轮通过正确性，第 3 轮轻量计时显示其吞吐仅为参考实现的若干分之一（定性表述，材料未给出具体数字），触发 NCU 后发现 DRAM 吞吐占比高而计算 pipe 空闲，判定为访存受限；第 4 轮模型据此改用分块加载与寄存器复用，粗粒度计时改善后才再次触发 profile 确认瓶颈转移。整个轨迹只做了两次 NCU 采集，而非每轮一次。

四 · 为什么硬件反馈比裸 speedup 更有效

裸 speedup 是一个标量奖励，它只回答"快了多少"，不回答"为什么慢"。把它作为唯一反馈时，模型面对的是一个信用分配难题：一次改动同时改变了分块策略、访存模式与寄存器压力，speedup 上升或下降都无法归因到具体决策。更糟的是，speedup 对噪声敏感——计时抖动、GPU 频率、缓存预热状态都会影响测量，标量奖励把所有这些不确定性折叠成一个数，策略容易在噪声上过拟合。

硬件反馈提供了结构化的中间信号，把标量拆成可归因的维度：瓶颈落在哪类资源、哪类 stall 主导、访存是否合并。这让模型的多轮修正有了方向，而不是在参数空间里随机游走。从 RL 的角度看，这相当于在稀疏的终局奖励之外引入了密集的过程信号——不是改变奖励函数本身，而是改变模型在每一轮能观测到的状态。状态更丰富，策略在同一轨迹预算下能做出更少但更准的修改。

代价同样明确：硬件反馈的采集成本高、序列化后 token 占用大、且存在被模型误读的风险（把 stall 原因当成病因）。此外，若反馈字段设计不当，模型可能学会"迎合指标"而非真正优化——例如为了压低 stall 计数而插入无意义的计算来填充流水线。这要求性能口径必须与端到端计时绑定校验，单看某个计数器容易被投机。这一点与奖励设计中"可验证信号是否可被投机"的问题是同一枚硬币的两面。

五 · 回灌协议的设计约束：字段、顺序与截断

把上述通道落成工程，需要一份明确的回灌协议。三个约束值得写进设计文档。其一是字段稳定性：每一轮的反馈模板必须字段名与顺序固定，缺失字段用显式占位符（如"未采集"）而非省略，否则模型会把"字段消失"误读为"该项已通过"。其二是截断策略：编译诊断可能长达数百行模板实例化栈，必须截断到首个错误加少量上下文，并保留错误码；SASS 摘要按指令类别聚合而非逐条列出。其三是历史压缩：多轮轨迹里早期轮次的完整反馈不应无限累积进上下文，应只保留每轮的一行摘要（轮次、状态、关键指标），把详细反馈留给最近一轮。这直接决定 token 成本随轮数增长是线性还是有界。

一个具体的伪代码思路：环境侧维护一个反馈记录器，每轮结束时按固定 schema 写入 {turn, compile_status, error_digest, verdict, metric_summary, bottleneck_tag}，提示构造时取最近一轮的完整记录加此前各轮的一行摘要。这样即使轮数上限较高，上下文增长也被压住。代价是：早期轮次里模型曾经犯过的错误细节不再可见，存在重复犯错的风险——缓解办法是在摘要行里保留错误码或瓶颈标签，让模型至少知道"这条路走过且失败了"。

另一个常被忽视的约束是反馈与代码的对应关系。若一轮里模型产出了多个候选内核，反馈必须标注它对应哪一个候选，否则模型无法建立"这段代码→这个诊断"的映射。多候选采样会放大执行成本，但能提高单轮的探索效率；是否值得取决于编译与运行的墙钟相对于推理 token 的占比。材料未披露该工作的候选采样与反馈字段设计，因此这里的协议约束应视为工程上的一般性要求，而非对该论文实现的复述。

最后落在工程判断上：反馈回灌的瓶颈不在"能不能采集"，而在"采集什么、以什么粒度、在什么时机"。编译与运行通道应当每轮必到且低延迟；性能通道应当门控触发、分层降维、与端到端计时交叉校验。把 NCU 全量计数器每轮灌进提示，看似信息充分，实则同时抬高了 token 成本、墙钟成本与噪声污染，是这类闭环系统里最容易犯的过度设计。
