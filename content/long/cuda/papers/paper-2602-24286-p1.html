一 · 从一次线上推理的算子替换说起

设想一个已经上线的推理服务：主干是 Transformer，单卡上跑着若干 fused 算子，其中 attention 的 softmax 与 mask 合并、LayerNorm 的归约、以及一个自定义的 rotary embedding 拼接，都是团队自己写的 CUDA kernel。某天模型结构微调，head 维度从 64 变成 80，输入序列分布也变了。原来那套手写 kernel 的 tile 尺寸、共享内存布局、寄存器预算全部失配，性能掉到厂商库基线以下，而厂商库又没有对应融合形态。工程师面对的是一个典型的三难：要么改 kernel，要么退回多个库调用拼接，要么放弃融合。这就是本文要处理的问题现场——它不是“模型能不能写出一段 CUDA”，而是“在算子语义、输入分布、硬件基线三者同时约束下，谁能稳定产出既正确又比基线快的 kernel”。

这个场景里，痛点不是抽象的。手写 CUDA 的工程师要重新推导索引、重排 shared memory 的 bank 布局、在 __syncthreads() 前后重算边界分支，一轮改完还要跑逐元素比对、跑 NCU 看 occupancy 与 DRAM throughput、跑端到端延迟。开发周期以人日计，而模型结构的迭代周期以天计，两者根本不匹配。更麻烦的是性能上限：手写 kernel 的质量高度依赖作者对 SASS 与访存模式的理解，同一个算子换一个人写，加速比可能相差数倍，且这种差异无法通过代码 review 稳定复现。

二 · 旧方案的三条路径与各自的失效点

论文之前，GPU kernel 工程的主流做法可以归为三条路径，每条都有明确的失效模式。

  • 手写 CUDA C++：控制力最强，能精确安排寄存器、warp 级原语、异步拷贝。代价是开发周期长、正确性靠人工推理、可维护性差——一个 tile 参数改动会牵动索引、边界、同步三处，回归测试必须覆盖所有 shape。
  • Triton：以 block 级编程模型换取开发效率，编译器负责布局与向量化。代价是性能上限受编译器调度约束，遇到需要精细控制 shared memory swizzle 或 warp specialization 的场景，往往打不到手写 kernel 的水平；且 Triton 的抽象泄漏在边界 shape 上表现为隐式 mask 开销。
  • 库调用（cuBLAS/cuDNN）：正确性与性能都有厂商保证，是默认基线。代价是形态固定：融合模式、非标准 layout、动态 shape 特判都难以表达，一旦算子不在库的覆盖范围内，就只能退回多 kernel 拼接，中间结果的显存往返直接把带宽吃光。

三条路径的共同缺口在于：它们都假设“人来承担从语义到实现的映射”。当算子形态快速变化、当融合需求超出库的覆盖面，这个假设就崩了。单轮提示生成 CUDA 的尝试正是想补这个缺口，但论文明确指出其结果是“正确性与性能双双失守”：编译失败、访存越界、数值偏差，以及相对 cuBLAS/cuDNN 基线无明显加速。这不是提示工程能修好的问题，因为单轮补全没有机会看到编译诊断，也没有机会在数值比对失败后重写边界分支。

三 · 正确性与性能的双重失守为什么是结构性的

把单轮生成的失败拆开看，会发现它不是一个“模型不够强”的问题，而是反馈回路缺失导致的结构性问题。CUDA kernel 的正确性判定不是文本层面的：一个索引表达式在语法上完全合法，但会在某个边界 shape 上越界读写；一个归约在数学上等价，但浮点累加顺序改变后与参考实现的逐元素比对超出容差。这些错误只有在编译、运行、比对之后才暴露。单轮模型拿不到这些信号，只能靠先验猜测，于是错误率随算子复杂度上升。

性能侧同理。加速比是相对量，锚定在厂商库基线上，而基线本身随 shape、dtype、GPU 架构变化。一个在 4096×4096 上快的 kernel，在 batch=1 的 decode 形态上可能因为 occupancy 不足而慢于库调用。没有实测延迟，模型无法知道自己写的 tile 尺寸是否落在 roofline 的带宽受限区还是计算受限区。论文的奖励设计正是针对这一点：

$$ r = \lambda_{\text{comp}} \cdot \mathbf{1}[\text{compile}] + \lambda_{\text{corr}} \cdot \mathbf{1}[\text{correct}] + \lambda_{\text{perf}} \cdot \min\left(\frac{t_{\text{base}}}{t_{\text{kernel}}},\, c_{\max}\right) $$

三项分别对应编译通过、逐元素比对一致、相对基线加速比，性能项用 c_max 截断，防止某个 shape 上的偶然极速把奖励拉爆。这个式子的工程含义是：正确性是门控项，性能是连续项，编译是前置门。任何一项缺失，训练信号就会退化——只奖励编译通过会产出能跑但慢的内核，只奖励性能会放过数值偏差的内核。

代价在这里是可量化的：每次多轮迭代都要付一次 nvcc 编译时间（秒级到十秒级，取决于模板与架构标志）、一次 GPU 执行与逐元素比对（显存带宽与参考实现驻留成本）、一次延迟测量（需要 warmup 与固定时钟，否则缓存效应污染加速比）。这些成本乘上轨迹条数，就是训练侧的真实开销；论文未披露 token 预算与 GPU 机时，但这笔账在工程上无法回避。

四 · 一个具体轨迹：三次提交才换来一个可训练样本

论文给出的流程例子足以说明旧方案为何非改不可。任务池给出某算子的规格与输入分布，智能体先写出一版朴素 CUDA 内核；提交编译后沙箱返回共享内存越界与未定义符号的编译错误，智能体据此修正索引与头文件；再次编译通过，运行后与参考实现比对发现边界元素数值不一致，智能体加入边界分支；第三次运行正确性通过，测得延迟并与基线比较得到加速比；奖励聚合器按三项折算奖励，该轨迹连同中间失败记录进入 RL 训练缓冲。

这条轨迹的关键在于“中间失败记录”被保留。单轮范式下，第一次编译失败的输出就是废样本；多轮范式下，失败诊断本身是训练信号——模型学会了“共享内存越界”对应索引重算、“未定义符号”对应头文件与函数签名、“边界元素不一致”对应尾块分支。这带来一个 token 成本上的权衡：一条成功轨迹可能包含三次提交的完整上下文，token 消耗是单轮样本的数倍，但换来了可验证的奖励锚点。工程判断在这里很清楚：如果任务池的算子复杂度足够高、单轮通过率足够低，多轮轨迹的边际信息量就压过 token 成本；反之，简单算子上多轮是浪费。

五 · 可维护性与评测口径：旧方案没解决、新方案必须面对的两笔账

旧方案的可维护性痛点不只是“代码难改”，而是“改动无法被自动验证”。手写 kernel 的回归依赖人工构造 shape 集合与容差，库调用则把验证责任转移给厂商。多轮智能体范式把验证内建进回路：逐元素比对参考实现是正确性 oracle，相对基线加速比是性能 oracle。但这同时把评测口径问题放大——容差过松会放过数值偏差内核，过紧会误杀合法优化（例如改变累加顺序的合法重排）；性能测量若不固定 warmup 与时钟，缓存效应会让加速比奖励失真，训练信号被噪声主导。

更隐蔽的是防作弊。智能体在脚手架里能读到输入分布与参考实现，若评测侧不做检查，硬编码输出、缓存结果或按 shape 特判都能绕过真实内核计算，分数虚高但无真实能力。论文摘要未给出检查机制细节，这本身就是一个工程风险点：奖励函数越强，越需要配套的测量纪律。对生产部署而言，最终判断落在端到端收益与维护成本能否压过厂商库基线——一个在基准上加速比漂亮、但在真实服务里因为 shape 分布偏移而退化的 kernel，维护成本反而高于直接调库。

路径开发周期性能上限正确性来源可维护性
手写 CUDA人日级高，依赖作者水平人工推理 + 回归测试低，参数改动牵动多处
Triton小时级受编译器调度约束框架语义 + 比对中，抽象泄漏在边界 shape
库调用分钟级厂商保证，形态固定厂商保证高，但融合需求无法表达
单轮提示生成分钟级无实测锚点无，编译/越界/数值偏差频发不可控

这张表的意义不在于排名，而在于指出旧方案在三列上同时失守：开发周期、性能上限、正确性来源无法兼得。多轮智能体 RL 的切入点正是把“正确性来源”从人工推理换成可验证的执行反馈，把“性能上限”从作者水平换成相对基线的实测加速比。代价是训练侧的编译与执行开销、评测侧的防作弊与测量口径建设。这两笔账是否划算，取决于任务池里算子形态的变化速度——变化越快，手写与库调用的边际成本越高，反馈回路的相对收益越大。

六 · 为什么非改不可：反馈回路是唯一能同时压住三列的杠杆

把问题收敛到一句工程判断：CUDA kernel 的质量由“语义到实现的映射”决定，而这个映射的正确性与性能都无法在文本层面验证。旧方案要么把这个映射交给人的经验（手写、Triton 调优），要么交给厂商的固定形态（库调用），两者都无法随算子形态快速变化而自动重估。单轮生成试图自动化映射，但缺少编译诊断、数值比对与实测延迟三类信号，于是正确性与性能同时失守。

论文的解法是把这三类信号组织成可验证奖励，驱动多轮轨迹上的策略优化。其机制核心不是模型规模，而是回路：编译失败回填诊断、数值不一致回填差异位置、性能数字回填加速比，每一步都让策略在下一次提交时带着具体错误信息改写。这个回路的工程代价明确——每次迭代付编译时间、GPU 执行与测量成本，轨迹 token 数倍于单轮；其收益也明确——奖励锚定在可验证的执行结果上，而非文本相似度。对生产端而言，判断标准落在端到端收益与维护成本能否压过厂商库基线；对评测端而言，判断标准落在防作弊检查与测量口径是否足以让加速比可信。这两条判断线，构成了后续所有优化与验证工作的前提。

当厂商库基线成为天花板：手写与单轮生成的失效边界

在一个在线推理服务的算子替换场景里，团队想把某个归一化加激活的融合算子从三次独立库调用合并成一次内核启动，以减少中间张量的显存往返。手写 CUDA 的路径是：先写朴素版本保证逐元素比对通过，再手动做向量化访存、共享内存分块与寄存器压榨，最后用 NCU 看吞吐是否贴近 roofline 上限。这条路径的性能上限确实高，但代价是开发周期以人日计，且每一次 shape 分布变化、每一代架构迁移都要重新调优；更隐蔽的代价是可维护性——分块尺寸、边界分支、bank 冲突规避这些决策散落在代码里，没有测试就无法判断某次改动是优化还是退化。库调用路径相反：cuBLAS/cuDNN 一次调用即得，正确性与数值口径由厂商背书，但它把融合机会锁死，中间结果的显存写回无法消除，端到端收益被内存带宽卡住。

单轮提示生成 CUDA 试图取两者之中：模型读题后一次吐出内核源码。问题在于这条路径的失效条件是结构性的，而非偶发。编译期它常因共享内存越界、未定义符号、架构标志不匹配而失败；运行期它常因漏掉边界分支导致尾部元素数值不一致；性能上则频繁出现相对厂商库基线无明显加速，甚至因未做向量化而更慢。三类失败互相耦合：修一个越界索引可能引入新的数值偏差，而一次编译失败就浪费掉整条样本的全部 token 预算。设单轮成功率为 $p$，则期望尝试次数为 $1/p$，每次尝试都付出完整的 prompt 与生成 token 成本，而失败样本不产生任何可用梯度信号——这正是单轮范式在工程上不可扩展的根源。

路径主要失效条件系统代价
手写 CUDAshape 分布漂移、架构迁移需重调人日级开发周期，调优知识不可复用
库调用融合机会被锁死，中间张量显存往返端到端受带宽限制，无法压过基线
单轮生成编译失败、边界数值偏差、无加速每次尝试全额 token，失败样本零信号

把这三条路径放在一起看，痛点不在“模型不够强”，而在反馈回路缺失：编译诊断、差异位置、加速比这些信号在单轮范式里被丢弃，模型无法知道自己错在哪、慢在哪。更麻烦的是评测侧的口径问题——若性能测量不固定 warmup 与时钟，缓存效应会污染加速比；若正确性容差与算子语义不对齐，过松放过数值偏差内核、过紧误杀合法优化；若缺少防作弊检查，硬编码输出或按 shape 特判就能让分数虚高而无真实内核能力。这些口径缺失使跨方案比较失去意义，也让“是否值得从库调用迁移到自研内核”这个工程判断无法量化。CUDA Agent 的切入点正是把这些执行信号组织成可验证奖励并纳入多轮训练回路，其奖励聚合形式为

$$ r = \lambda_{\text{comp}} \cdot \mathbf{1}[\text{compile}] + \lambda_{\text{corr}} \cdot \mathbf{1}[\text{correct}] + \lambda_{\text{perf}} \cdot \min\left(\frac{t_{\text{base}}}{t_{\text{kernel}}},\, c_{\max}\right) $$

其中性能项的上限截断 $c_{\max}$ 是防刷分的第一道闸：没有它，策略会倾向于针对评测 shape 做特化而非写出通用内核。但这条公式本身也暴露了旧方案未解的代价结构——编译项与正确性项是离散的 0/1，性能项才是连续信号，三者权重如何分配直接决定策略是“先求编译通过”还是“先求加速”，而权重、容差、测量口径在摘要级材料中均未给出，意味着这套回路在工程落地前仍需补齐测量与防作弊的具体机制。
