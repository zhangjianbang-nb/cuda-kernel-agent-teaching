一 · 反馈通道的分层：从编译错误到硬件计数器

执行反馈在 Geak 这类脚手架里不是单一信号，而是一条分层通道。最底层是 Triton 编译器的报错文本——语法、类型、块大小不合法、`tl.load` 的 mask 维度不匹配，这类错误在 CPU 侧就能捕获，代价是一次编译尝试的时延，通常远低于一次 GPU kernel launch。往上一层是运行期错误：非法内存访问、共享内存超限、`cudaErrorIllegalAddress`，这类错误需要真正把 kernel 放到 GPU 上跑，代价是一次 launch 加一次同步，且往往污染上下文，需要重置设备或进程隔离。再往上是数值正确性：与参考实现逐元素比对，超差即判失败，代价是一次完整的输入输出搬运加比对 kernel。最上层才是性能反馈：计时、NCU 指标、SASS 反汇编、warp stall 采样。

这条通道的信息量与代价成正比，但并非线性。编译错误的信息量极高——报错文本直接指向代码行与类型约束，智能体几乎不需要推理就能定位；代价却最低。数值不符的信息量中等——只告诉你“第 i 个元素差了”，不告诉你为什么差，智能体得自己从归约顺序、越界、mask 逻辑里找原因；代价是一次完整运行。性能反馈的信息量最模糊——一个加速比数字不解释任何东西，必须配合 NCU 的 stall 原因分解才有诊断价值；代价是 profile 本身的开销，NCU 采集会把 kernel 重放多次，单次采集的墙钟时间可能是裸跑的数十倍。

工程上的关键判断是：不要把反馈压成一个标量。裸 speedup 作为唯一信号时，智能体只能做黑盒搜索——改一版、测一下、看数字涨没涨，涨了保留、跌了回退。这种搜索在搜索空间大、单次评估贵时收敛极慢，且容易卡在局部最优：一个因为寄存器溢出而变慢的版本和一个因为块大小不匹配而变慢的版本，在标量信号下看起来完全一样，但修复方向截然相反。

二 · 编译与运行错误的回灌粒度

编译错误回灌的粒度选择直接影响重试效率。最粗的做法是把整段 stderr 原样塞回提示，问题是 Triton 的报错常常带一大段 Python traceback，真正有用的只有最后几行——错误类型与出错的内核行号。把整段 traceback 灌进去，token 成本随嵌套深度膨胀，而有效信息占比极低。较细的做法是做一次结构化抽取：错误类别（语法/类型/shape 不匹配）、出错的文件行号、涉及的变量名，再映射回候选代码的对应片段。这样一轮反馈可能只有几十个 token，却足以让智能体做定点修改。

运行期错误的回灌更棘手，因为它发生在 GPU 上，宿主侧拿到的往往只是一个错误码。一个具体的机制是：在 launch 前对候选 kernel 做静态资源检查——用 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 或 Triton 编译产物里的 `shared`、`num_regs` 元数据，预判共享内存是否超限、寄存器数是否触发 spill。这类检查在编译后、launch 前完成，能把一部分运行期失败提前成编译期可诊断的问题，避免一次昂贵的设备上下文污染。

$$\mathrm{cost}_{\mathrm{fb}} = t_{\mathrm{compile}} + \mathbb{1}[\mathrm{compiled}]\cdot(t_{\mathrm{launch}} + t_{\mathrm{sync}} + t_{\mathrm{verify}}) + \mathbb{1}[\mathrm{correct}]\cdot t_{\mathrm{profile}}$$

这个代价分解说明为什么反馈要分层投放：编译失败时只付第一项，正确性失败时付到第三项，只有正确候选才值得付 profile 的代价。若不分层、每轮都对所有候选做完整 profile，token 与墙钟成本会被大量注定失败的候选吃掉。一个具体例子：某候选在 `tl.dot` 的累加器维度上写错，编译能过、运行能跑、数值全错；如果这一轮就触发 NCU 采集，采到的是一份“正确性都不过的 kernel 的性能画像”，纯属浪费。分层投放把 profile 留给通过正确性检查的候选，是成本控制的基本纪律。

三 · NCU 与 SASS：把 stall 原因翻译成修改动作

NCU 的价值不在于给出一个利用率百分比，而在于把“慢”拆成可归因的 stall 类别。对 Triton 生成的 kernel，最常见的几类 stall 有明确的对策映射：`stall_long_scoreboard` 指向全局内存依赖未就绪，通常意味着访存延迟未被足够多的在途请求掩盖，对策是提高 occupancy 或做软件预取；`stall_short_scoreboard` 指向共享内存或特殊功能单元依赖，常见于归约链路过长；`stall_wait` 指向指令发射等待，往往与寄存器压力或指令级并行不足相关；`stall_mio_throttle` 指向 MIO 队列拥塞，典型于大量 `tl.load` 未合并访存。

把这些 stall 类别回灌给智能体时，必须附带定位信息，否则智能体无法把“stall_long_scoreboard 占主导”翻译成“把 `BLOCK_K` 调大以增加在途加载”。可行的做法是把 NCU 的 source-level 视图（若编译时保留了行号信息）与 Triton 源码行对齐，给出“第 12 行的 `tl.load` 贡献了最多 long scoreboard stall”。SASS 层面则更进一步：反汇编能暴露 Triton 编译器生成的 `LDG` 是否被合并、是否有冗余的 `BAR.SYNC`、寄存器分配是否导致 `LDL/STL` 本地内存往返。一个具体的诊断路径是：NCU 报高 local memory 流量 → 查 SASS 发现 `LDL` 密集 → 判定寄存器 spill → 回灌“减少同时活跃的累加器张量或缩小块尺寸”。

代价方面，NCU 采集的时延是硬成本：一次完整指标采集要把 kernel 重放多遍以覆盖不同计数器组，墙钟时间远超裸跑；若对每个候选都采集，多轮闭环的墙钟会被 profile 主导。折中做法是只对“通过正确性且加速比落在某个区间”的候选做定向采集——太慢的候选没有诊断价值，太快的候选不需要诊断。SASS 反汇编则是静态的，代价是一次编译产物的读取，几乎可忽略，适合每轮都做轻量筛查。

四 · Roofline 诊断：把 kernel 放到正确的性能上界下

Roofline 的作用是给智能体一个“这个 kernel 最多能多快”的参照，避免它在已经接近硬件上界的候选上继续无效迭代，也避免它在远低于上界的候选上误以为已经优化到位。对 Triton kernel，算术强度 $I$ 可由 kernel 的浮点运算数与字节搬运量估算，性能上界为：

$$P_{\mathrm{bound}} = \min\left(P_{\mathrm{peak}},\ I \cdot B_{\mathrm{peak}}\right)$$

把实测性能与 $P_{\mathrm{bound}}$ 的比值作为反馈，比裸 speedup 更有信息量：一个相对基线加速 2 倍但只达到 roofline 上界 20% 的候选，说明还有大量空间；一个加速 1.1 倍但已达上界 85% 的候选，说明瓶颈在别处（可能是 launch 开销或固定开销占比）。诊断结论直接决定下一轮动作：前者应继续调块大小与访存模式，后者应检查是否被固定开销主导、是否值得融合。

roofline 诊断的工程代价在于算术强度估算本身依赖对 kernel 语义的理解——对归约类算子，实际搬运量取决于分块策略，静态估算会偏差。可行的折中是让 NCU 的 `dram__bytes` 与 `sm__sass_thread_inst_executed_op_fadd_pred_on` 等计数器提供实测分子分母，用实测值代入 roofline，而不是靠源码静态推算。这样每次诊断多付一次定向采集的代价，换来的是不会把智能体引向错误的优化方向。一个具体例子：某 Triton 矩阵乘候选的实测带宽已接近峰值带宽的九成，此时继续增大 `BLOCK_M` 只会加剧寄存器压力，正确动作是转向减少冗余加载或改用更优的分块，而不是盲目调大块尺寸。

五 · 为什么硬件反馈优于裸 speedup

裸 speedup 是一个差分信号，它只回答“比基线快还是慢”，不回答“为什么”和“还能多快”。在闭环里，这导致三个具体问题。其一，信号稀疏：多轮迭代中大多数候选的 speedup 差异落在计时噪声内，智能体无法从噪声中提取方向。其二，归因缺失：同一 speedup 下可能对应完全不同的瓶颈，回退策略无法区分“该调块大小”和“该改访存模式”。其三，上界未知：没有 roofline 参照，智能体不知道当前候选离硬件极限多远，容易过早停止或过度优化。

硬件反馈把这三个问题各自对应到具体机制：NCU 的 stall 分解提供归因，roofline 提供上界，SASS 提供代码级证据。信息量提升的代价是采集时延与 token 成本——一份结构化诊断报告可能包含 stall 类别、占比、对应源码行、roofline 比值，几十到上百个 token，远高于一个 speedup 数字。但在多轮闭环里，这笔 token 投入换来的收敛轮数下降通常更划算：一次精准诊断省下的可能是数轮盲试。

反馈类型信息量单次代价适用轮次
编译报错文本高（定位到行）低（CPU 侧）每轮
数值比对差异中（定位到元素）中（一次运行）编译通过后
裸 speedup低（标量）低（计时）仅作筛选
NCU stall 分解高（归因）高（重放采集）正确且值得优化的候选
SASS 反汇编中高（代码证据）低（静态读取）每轮轻量筛查
Roofline 比值高（上界参照）中（需实测计数器）性能候选诊断

这张表的工程含义是：反馈投放要按候选状态分级，而不是每轮对所有候选一视同仁。编译失败只付最低代价，正确性失败付中等代价，只有跨过正确性门槛的候选才进入高代价诊断。若把 NCU 采集前置到编译失败阶段，闭环的墙钟会被无意义的 profile 拖垮；若把 roofline 诊断省略、只留 speedup，智能体就退化成黑盒调参器。

六 · 回灌格式与闭环稳定性

反馈回灌的格式决定智能体能否稳定利用信息。一个可行的机制是把诊断结果组织成固定字段的结构化文本：失败类别、定位（源码行/变量）、证据（报错片段或计数器值）、建议动作空间（可选的修改方向列表）。固定字段的好处是智能体不必每轮重新解析自由文本，token 开销可预测，且便于在轨迹里做失败模式统计。代价是结构化本身要写解析器——从 Triton 报错里抽行号、从 NCU 报告里抽 stall 占比、从 SASS 里抽指令计数，这些解析逻辑的维护成本是脚手架的真实工程负担。

闭环稳定性还有一个容易被忽视的点：反馈的时效性。若诊断报告描述的是三轮前的候选，智能体已经改过代码，报告里的行号就对不上，回灌反而制造混乱。因此每份反馈必须绑定候选版本号，且只对当前版本有效。另一个稳定性问题是反馈的一致性：同一类失败在不同轮次应给出同构的描述，否则智能体会把同一问题当成新问题反复试错。这两点共同指向一个工程判断——反馈层不是被动地把原始输出转发给模型，而是一个需要版本管理、字段规范化与解析器维护的主动组件；它的质量直接决定多轮闭环是收敛还是空转。
