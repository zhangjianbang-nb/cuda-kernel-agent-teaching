一 · 回合协议：一次 kernel 生命周期的状态机

把多轮 RL 拆开看，本质是把一次 kernel 生成的生命周期建模成有限状态机，每个回合是一次状态转移。给定任务描述 d（算子语义、shape、dtype、目标 GPU 约束），策略在回合 t 观测到的是历史 h_t——它由前 t-1 轮的内核源码与结构化反馈拼接而成——输出动作 a_t，即一份完整的 CUDA 源码（注意是整份源码而非 diff，这一点决定了后续 token 成本的口径）。环境对 a_t 执行编译、运行、判定、采集性能，产出反馈 f_t，拼入 h_{t+1}。终止条件有两个：判定通过且性能达标，或达到轮数上限 T。整条轨迹 \tau=(h_1,a_1,f_1,\dots,a_T) 是训练层的输入单元。

这个状态机的关键设计点不在“多轮”本身，而在反馈 f_t 的字段设计。摘要级材料只确认反馈包含编译与运行结果，未披露字段。从工程角度，反馈至少要能区分三类失败：编译期错误（语法、类型、不支持的 intrinsic、架构不匹配）、运行期错误（非法访存、越界、未初始化、同步错误）、结果错误（数值偏差超阈值）。三者对模型的修正方向完全不同：编译错误需要语法级修补，运行错误需要内存与同步推理，结果错误需要算法级重写。若反馈只给一个布尔“失败”，模型在多轮中极易在同一处反复犯错——这正是多轮 RL 要解决的核心痛点，也是奖励设计必须区分的粒度。

代价在这里第一次显形：每一轮都是一次完整的编译加运行，编译时间在模板重度展开的 CUDA 代码上可达秒级到十秒级，运行时间取决于 shape 与迭代次数。轮数上限 T 直接线性放大墙钟时间与执行次数。若 T=8，单条轨迹的执行成本是单轮提示的八倍量级，而 token 成本还要叠加历史拼接带来的上下文增长——第 t 轮的输入长度约等于任务描述加上 t-1 份源码与反馈，是超线性增长。这就是多轮协议的第一个工程判断：反馈必须压缩成结构化短字段，而不是把原始编译器日志整段塞回提示。

二 · 生成层：按轮产出源码的输入输出与 token 账

生成层的输入是 h_t，输出是 a_t。首轮 h_1 只含任务描述，此时模型没有任何执行信号，行为等价于单轮代码补全——这正是旧方案失败率高的地方：没有反馈，模型只能靠先验猜 API 与并行策略。后续轮次的 h_t 含前轮源码与反馈，模型的任务从“从零写”变成“读反馈改代码”，这是能力要求截然不同的两种任务形态。多轮 RL 的训练价值就在于让策略学会后者，而不是把前者重复 T 遍。

token 账要算清楚。设任务描述长度为 L_d，单份源码长度为 L_s，单份反馈长度为 L_f，则第 t 轮输入长度近似为

$$L_t \approx L_d + (t-1)(L_s + L_f)$$

整条轨迹的生成 token 总量约为 \sum_t L_t + T\cdot L_s，随 T 呈二次增长。这是多轮 RL 相对单轮提示最直接的代价：即便每轮输出长度不变，输入侧的累积也让总 token 消耗按轮数平方级上升。工程上的缓解手段是只保留最近一轮的源码与反馈、或对历史做摘要压缩，但摘要本身会丢失编译错误的精确行号信息，形成“压缩换 token、精度换修正成功率”的权衡。材料未披露该工作是否做历史压缩，因此这一权衡只能作为设计维度记录，不能断言其取舍。

具体例子：一个 reduction 类 kernel 首轮常犯的错误是把 block 内归约写成跨 block 的全局累加，编译能过但结果错。若反馈只回传“结果不匹配”，模型下一轮很可能微调线程数而非改归约结构；若反馈回传“输出张量第 i 个元素期望值与实际值”，模型才有依据定位到累加范围。这说明反馈字段的语义密度直接决定多轮是否“持续改进而非重复犯错”。

三 · 执行层：编译、运行、判定、采集的四段流水

执行层是这套方法里工程分量最重的部分，它把一份字符串变成可验证信号。四段流水依次是：编译（nvcc 或等价工具链，产出二进制或报错）、运行（在目标 GPU 上启动 kernel，含输入准备与结果回读）、判定（与参考实现比对，产出正确性布尔与误差量）、采集（性能信号，如耗时或吞吐）。每段的输出都要序列化成下一轮提示可消费的字段。

编译段的代价不只是时间，还有环境一致性。CUDA 工具链版本、目标架构（sm 版本）、依赖头文件路径都会影响同一份源码的编译结果。若沙箱环境与训练环境不一致，模型学到的“编译通过”模式在部署时会失效。运行段的代价是显存与超时控制：错误的内核可能申请超大共享内存或陷入死循环，必须有显存上限与墙钟超时两道闸，否则一条坏轨迹能拖垮整个采样批次。判定段的代价是参考实现的准备——每个任务都需要一个可信的正确性 oracle，这本身是数据准备工作量。采集段的代价是测量噪声：单次运行的耗时受频率波动与缓存状态影响，需要多次迭代取统计量，进一步放大执行时间。

伪代码层面的执行层接口大致是：

$$\text{exec}(a_t)\rightarrow(\text{status},\text{err},\text{correct},\text{perf})$$

其中 \text{status} 区分编译失败与运行失败，\text{err} 是截断后的错误摘要，\text{correct} 是判定结果，\text{perf} 是性能信号。四元组直接决定奖励构成，也决定反馈字段。材料未披露该四元组的具体字段与判定阈值，因此这里的接口是方法定位下的合理抽象，而非原文实现。工程判断在于：\text{err} 必须截断，因为原始编译器日志可达数百行，整段回灌会让 token 账失控；截断策略（保留首个错误、保留错误码、保留行号）本身就是影响修正成功率的设计变量。

四 · 奖励构造：可验证信号如何汇总成轨迹回报

奖励是这套方法的训练核心。给定公式

$$R(\tau)=\sum_{t=1}^{T} r_t,\quad r_t=f(\text{compile}_t,\text{correct}_t,\text{perf}_t)$$

关键在 f 的形状。若 f 只奖励“编译通过”，策略会收敛到写出保守、简单、能编译但性能平庸的内核——这是可验证奖励最典型的投机路径。若 f 只奖励“正确”，策略会忽略性能，产出正确但远低于 roofline 的实现。若 f 把性能信号直接乘进去，则存在测量噪声被策略利用的风险：模型可能学到针对特定 shape 的过拟合写法，在评测分布外失效。合理的 f 应是分级结构：编译失败给负值或零，正确性未过给零，正确后按性能相对基线给连续奖励。这样每一类失败都有明确的梯度方向，且性能奖励只在正确性门之后生效。

轨迹回报的汇总方式也有讲究。逐轮求和 R(\tau)=\sum r_t 会让“早期失败、后期修好”的轨迹与“一直正确”的轨迹得到相近回报，弱化了“少犯错”的信号；若改为终局奖励加折扣，则前期轮次的探索得不到激励，策略会倾向于首轮就保守。材料未披露该工作采用哪种汇总，因此这里只能指出两种口径的后果差异：求和口径鼓励修正能力，终局口径鼓励首轮质量，二者对多轮训练的行为塑造完全不同。

代价层面，奖励计算本身几乎零成本（都是布尔与数值比较），真正的成本在轨迹采样：每条轨迹要跑 T 轮执行，采样批量乘以轮数就是总执行次数。若批量大、轮数高，执行层会成为训练吞吐的瓶颈，而不是 GPU 算力。这是把 RL 用在 kernel 生成上的结构性约束：训练瓶颈从模型前向转移到了沙箱执行。

五 · 训练层：轨迹如何进入策略更新

训练层接收的是整条轨迹及其回报，做策略梯度类更新。材料仅确认“多轮交互产生的轨迹与可验证信号参与奖励计算”，未给出 KL 约束、采样规模、优势估计方式。可确认的结构性事实是：轨迹是变长的（不同任务终止轮数不同），回报是稀疏的（多数轮次奖励为零，只有正确性通过后才出现性能奖励），这两个特性决定了训练实现上的两个难点。

变长轨迹要求按轨迹而非按轮做批处理，否则不同轨迹的轮数不对齐会造成填充浪费；稀疏回报要求优势估计能跨轮传播——某一轮的修正动作可能要到几轮后才体现为正确性通过，信用分配跨度大。这是多轮 RL 相对单轮 RL 的核心训练难点，也是“多轮是否真的优于单轮多次采样”这一问题的关键：若信用分配做不好，多轮轨迹的梯度信号会被稀释，效果退化为独立采样的集成。

具体例子：一条轨迹前两轮编译失败、第三轮编译通过但结果错、第四轮修正后正确且性能达标。按求和口径，前三轮的负奖励与第四轮的正奖励叠加；若折扣因子设置不当，第四轮的信号可能被前三轮的负值淹没，策略学不到“读编译错误改语法”这一子技能。这说明奖励汇总与折扣不是形式细节，而是决定多轮能否学到分阶段修正能力的设计变量。材料未披露这些超参，因此工程上只能把“信用分配跨度”作为该方法落地时必须自行校准的维度。

六 · 三层耦合的工程代价与判断

把生成层、执行层、训练层放在一起看，耦合点有三处，每处都带明确代价。第一处是反馈序列化格式：生成层消费的字段必须与执行层产出的字段严格对齐，格式变更会同时影响提示构造与奖励计算，属于跨层契约。第二处是沙箱隔离：执行层跑的是模型生成的任意代码，必须有资源上限与超时，否则一条恶意或错误的内核能拖垮采样；沙箱的启动开销（容器拉起、依赖挂载）会叠加到每轮执行时间上。第三处是正确性 oracle 与性能口径的一致性：判定用的参考实现与采集用的测量方法必须固定，否则同一份内核在不同轮次得到不同判定，奖励信号自相矛盾。

三层耦合下的端到端代价可以用一个粗略的资源账表达：单条轨迹的执行次数为 T，单次执行含编译、运行、判定、采集四段，墙钟时间为四段之和；token 消耗按第二节的二次增长；显存占用由运行段的内核决定，需设上限。这三项中，执行次数与 token 是随轮数线性或超线性增长的，而正确性收益是否随轮数饱和，材料未给出失败模式统计，无法判断。工程判断因此落在：多轮 RL 的可行性不取决于模型能力，而取决于执行层的吞吐与反馈字段的语义密度——前者决定训练能否跑起来，后者决定多轮是否真的在修正而非重复。

与单轮提示相比，这套方法把“一次通过率”的压力从模型先验转移到了反馈利用能力上。若反馈字段足够精确、奖励分级足够清晰，模型可以在多轮中完成从语法修补到算法重写的跨越；若反馈被压缩过度或奖励只覆盖编译与正确性，多轮就退化为带重试的单轮采样，token 与执行成本翻倍而质量不增。这是该方法在工程落地时最需要先验证的假设，也是摘要级材料无法回答、必须由全文补齐的部分。

闭环的边界：奖励可验证性、反馈可机读性与执行代价

该方案把「生成—编译—运行—再生成」串成闭环，其有效性的前提是三个环节同时成立：反馈必须可机读、奖励必须可验证、执行必须可承受。三者的失效条件并不对称。反馈层最脆弱的是编译器报错的结构化——若把原始 stderr 直接拼入下一轮提示，模型需要自行从数百行模板化文本中定位行号与错误类型，多轮之后上下文被报错噪声占满，修正信号被稀释。可验证奖励的边界更硬：$$R(\tau)=\sum_{t=1}^{T} r_t,\quad r_t=f(\text{compile}_t,\text{correct}_t,\text{perf}_t)$$ 中若 perf 项缺席或口径模糊，策略会收敛到「编译通过且数值正确但性能平庸」的保守内核——正确性 oracle 是二值的，性能却是连续的，二者拼接时前者会主导梯度。材料未披露正确性判定阈值与性能口径，因此无法判断该奖励是否存在被投机利用的漏洞，这是评估该方法可信度的第一道缺口。

执行代价是闭环的隐性税。每一轮都要真实编译并运行，单条轨迹的成本随轮数线性增长，而编译本身是秒级操作，远贵于一次前向推理；若任务涉及大 shape 或多组配置，运行时间进一步放大。与单轮提示相比，多轮交互同时增加推理 token 与执行次数，材料未给出 token 成本与墙钟时间，端到端收益无法量化。工程上还需维护执行沙箱、超时控制与反馈序列化，这些在材料中均无具体代价披露。一个具体的失效场景是：编译超时被当作编译失败回灌，模型收到的是与代码质量无关的信号，多轮后学会的是规避复杂模板而非修正逻辑。

环节失效条件代价形态
反馈回灌报错未结构化，噪声占满上下文token 膨胀，有效信号稀释
可验证奖励仅覆盖编译与正确性收敛到低性能保守内核
执行沙箱超时误判为编译失败墙钟时间与错误信号双损

因此判断该方案是否成立，不能只看「多轮是否比单轮通过率高」，而要看残留失败比例——材料未给出编译失败率、正确性不达标比例与多轮后仍失败的残留比例，稳定性边界不明。若残留比例高，说明反馈未被有效利用，多轮只是在重复犯错；若残留比例低但性能信号缺失，说明模型学会了通过而非优化。这两类失败在摘要级材料中无法区分，需以全文的失败模式统计与硬件环境补齐后才能评估其在不同 GPU 架构与算子形态下的泛化边界。
