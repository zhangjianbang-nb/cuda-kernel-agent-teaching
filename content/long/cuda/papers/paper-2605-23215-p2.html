一 · 基准的构成单位与可比性边界

FastKernels 的评测对象不是孤立的 kernel 文件，而是 384 个任务，取自 47 个代表性架构、归入 8 个类别。这个数字本身决定了口径的第一条约束：任务必须与生产模块的接口对齐，即候选 kernel 的签名、张量布局、dtype 与调用约定要与框架实际下发的形式一致。论文的表述是每个任务“mirrors the interface of the corresponding production module”，并且打分对象是“the kernels production frameworks ship”——也就是说基线不是随手写的 naive CUDA，而是生产框架真正出货的实现。这一条把很多旧基准的可比性直接切断：在 KernelBench 类设定里，基线常是 PyTorch eager 拼出来的参考路径，候选只要赢过它就能拿到漂亮加速比；而在 FastKernels 里，候选要面对的是已经经过厂商调优的库 kernel，赢的空间被结构性压缩。

任务的组合层级是第二个口径要素：从 primitives 到 full models，高层模块 import 低层模块。这意味着同一份候选代码会在多个层级被复用与计分，低层 primitive 的错误会沿 import 链向上传播，而高层模块的端到端时延又包含低层 kernel 的贡献。评测时必须区分“单 kernel 级得分”与“端到端得分”，否则会把层级复用带来的收益或损失重复计入。工程上可核查的做法是：为每个任务记录其依赖的下层任务 ID 集合，端到端测量时固定下层实现（用参考实现或已冻结的候选），只替换当前层，避免上下层同时变动导致归因不清。

覆盖度的口径也值得单列：论文声称这些 kernel 足以重实现 94.6%（472/499）的 HuggingFace Transformers 架构，且输出与原生实现匹配。这个数字是“覆盖”而非“性能”，它约束的是基准的代表性，不构成任何加速比承诺。把它误读为“在这些架构上都能加速”是常见的口径混淆。可核查的测量口径应把覆盖率作为独立字段记录：任务集覆盖了哪些架构、哪些架构只有部分模块被覆盖、未覆盖的 27 个架构属于哪类算子。

二 · 基线、硬件与 dtype：三处最易被高估的地方

基线口径的核心问题是“是否用了最强库、是否开了 TF32”。论文把基线定为生产框架出货的 kernel，这在原则上排除了弱基线，但工程上仍有三处漏洞。第一，库版本与调度策略：同一算子在不同 cuBLAS/cuDNN 版本、不同 heuristic 选择下时延差异显著，若基线跑在默认 heuristic 而候选针对特定 shape 手工调参，比较就不对等。第二，TF32/FP32 的开关：矩阵乘类任务若基线未开 TF32 而候选用了 TF32 tensor core，加速比会被系统性高估，且正确性检查若用宽松容差还会放过精度退化。第三，融合边界：生产框架常把多个算子融进一个 kernel（如 layernorm+residual），若基准任务只测其中一段，候选的“加速”可能只是把融合拆开后的局部收益。

硬件口径同理。论文未在摘要级给出具体 GPU 型号与数量，因此任何跨硬件的数字迁移都不可比：SM 数量、HBM 带宽、L2 容量决定了 roofline 的拐点位置，同一 kernel 在带宽受限与计算受限区间的最优策略不同。可核查的测量口径要求记录：GPU 型号、驱动与 CUDA 版本、时钟是否锁定、是否启用 MPS、单卡还是多卡、是否独占。缺少这些字段的加速比只能在同一实验室内自比，不能跨论文引用。

dtype 口径要写成显式矩阵而非单一数字。至少区分 FP32、TF32、FP16、BF16、FP8 五档，并记录每档下的正确性容差与是否允许降精度。一个常见的口径事故是：候选在 BF16 下赢了基线 FP32 的时延，被记成“加速”，但端到端模型若要求 FP32 数值稳定性，这个候选根本不可部署。可核查做法是为每个任务标注“允许的 dtype 集合”与“参考实现的 dtype”，候选若改变 dtype 必须在结果里单独标记，不得混入同一加速比统计。

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{cand}}},\qquad \text{仅当 } \text{dtype}_{\text{cand}}\subseteq\text{dtype}_{\text{allowed}} \text{ 且正确性门通过}$$

代价方面：锁定时钟与独占 GPU 会把吞吐测量变成时延测量，单次运行的代表性下降，需要多次重复取中位数并报告方差；开启 TF32 会让基线变快、压缩加速比空间，但换来的是与生产默认配置一致的可比性。这是一个明确的工程取舍，而不是“大概更准”。

三 · 指标族：faster rate、geomean、fast_p 与 roofline 的分工

论文给出的核心打分公式是阈值化的胜率：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这就是 fast_p 家族的写法：τ 是加速比阈值，分数是“达到阈值的任务占比”。它的优点是抗离群值——单个任务上 50× 的异常加速不会主导排名；缺点是丢失幅度信息，一个 1.01× 与一个 6× 在 τ=1.0 下同权。因此口径上必须同时报告 geomean（几何平均加速比），它对数域平均、对倍率对称，适合跨任务汇总；但 geomean 对“某些任务退化为 0.5×”非常敏感，会把整体拉低，需要与 fast_p 并读才能看出分布形状。论文摘要给出的 kernel 级加速比区间是 1.6×–6.6×，这是区间表述而非 geomean，引用时不得把它当作平均值。

roofline 口径是另一条独立轴：把候选的实测时延与理论下界比较，下界由该任务在目标硬件上的算术强度与带宽/峰值算力决定。roofline 的价值在于判断“这个加速比是否还有空间”，而不是替代 fast_p。一个候选在 fast_p 上赢了，但实测时延已贴近 roofline 拐点，说明该任务已接近饱和，进一步优化的边际收益低；反之若远离 roofline，说明基线或候选都没打满，加速比的可比性存疑。可核查的测量口径要求为每个任务记录算术强度、实测带宽利用率与 SM 占用率，这些字段来自 NCU/SASS profile，而不是从加速比反推。

指标回答的问题口径代价
fast_p（τ 阈值胜率）有多少任务达到目标加速丢失幅度，τ 选择影响排名
geomean speedup整体倍率水平对退化任务敏感，需报告最差任务
roofline 距离还剩多少优化空间需 profile 数据，测量开销与噪声
端到端时延生产路径上的真实收益受模型其余部分主导，归因困难

具体例子：某 attention 类任务在 kernel 级拿到 4× 加速，但端到端在完整模型里只体现为 1.1×，因为该 kernel 只占端到端时延的约四分之一，其余时间花在数据搬运与相邻算子上。这正是论文报告的 1.6×–6.6× 收缩到“at most 1.25× end to end”的机制来源——不是测量误差，而是 Amdahl 定律在真实执行路径上的体现。

四 · 哪些数字不可比：跨论文、跨硬件、跨 dtype 的硬边界

第一类不可比是跨基准的加速比。KernelBench 系基准的基线多为 eager 参考实现，FastKernels 的基线是生产库 kernel，两者分母不同，同一候选在两边的 speedup 数值不可直接比较，也不能用“在 A 上 5×、在 B 上 2×”推断基准更严。第二类是跨硬件的绝对时延：同一 kernel 在不同 GPU 上的时延不可比，只有同一硬件上的倍率才可比，且必须同驱动、同 CUDA 版本。第三类是跨 dtype 的倍率：BF16 对 FP32 的加速比混合了精度下降与实现优化两个因素，不能作为“kernel 质量”的证据。

第四类是层级不可比：primitive 级得分与 full model 级得分不可混入同一排行榜，因为前者只测单 kernel，后者包含调度、内存分配与相邻算子。论文的 MacroEval 把 calibrated correctness、coverage 与 speedup 聚合进排行榜，这里的“calibrated”是关键——正确性不是二值，而是按任务容差校准后的判定；若不同任务的容差尺度不一，聚合就会失真。可核查口径要求公开每个任务的容差定义（绝对误差、相对误差、还是 allclose 的 rtol/atol），以及校准方法。

第五类是 agent 预算不可比。论文用五个代表性 agent、共 6,900 agent-hours 做种子实验，这个预算规模决定了搜索深度；一个只跑几十轮的 agent 与一个跑数百小时的 agent 在同一 fast_p 上的差异，混合了预算与能力两个变量。引用排名时必须同时给出 agent-hours、token 消耗与重试次数，否则“Claude Code matches or beats KDA at every l…”这类结论无法归因。

代价层面：把上述字段全部记录会让每次评测的存储与后处理成本上升，profile 采集本身会引入数个百分点到数十个百分点的时延扰动（取决于采集粒度），因此性能数字应在关闭 profile 的独立运行中采集，profile 只用于解释而非计分。

五 · 隐藏 shape 与输入分布：离线分数为何在生产上崩塌

论文的问题陈述直指“synthetic inputs and weak baselines”，隐藏 shape 与输入分布是口径设计的核心。生产推理的 shape 不是固定的：batch 随请求波动、序列长度随 prompt 变化、KV cache 长度随时间增长。一个针对单一 shape 特化的候选（例如把 tile 大小写死为某个整除值）在基准上能赢，但在真实分布上会触发回退路径或边界分支，时延骤增。可核查的测量口径要求：为每个任务定义输入分布（shape 采样范围、dtype、稀疏度、数值范围），并区分“公开分布”与“隐藏分布”——候选在公开分布上调优，评分在隐藏分布上执行，两者不重叠。

处理隐藏分布的具体机制是分层采样：按 batch、序列长度、head 数等维度划分桶，每桶内独立采样若干实例，报告每桶的加速比与最差桶。这样做的代价是评测实例数成倍增长，测量时间与显存占用上升；若桶过细，每桶样本太少，方差主导结果。工程判断是桶数控制在个位数到十余个，且报告最差桶而非仅报平均，因为生产事故往往发生在最差桶。

另一个机制是分布漂移检测：同一候选在公开分布与隐藏分布上的 fast_p 差值若超过阈值，标记为“分布敏感”，不计入排行榜或单独列出。论文报告的“only 20% of winning kernel sets run correctly as-is”正是这类问题的量化表现——在基准上赢的 kernel 集合，放到真实模型里只有约五分之一能原样正确运行，其余需要修改接口、处理边界 shape 或修复数值问题。这个 20% 不是正确率指标，而是“可移植性”指标，口径上必须与正确性门分开记录。

具体例子：一个 layernorm 候选在隐藏维度为 2 的幂时达到高加速比，但生产模型里存在非 2 的幂的 hidden size，候选的向量化加载越界或走标量回退，正确性检查在公开分布上通过、在隐藏分布上失败。可核查做法是把“非 2 的幂 hidden size”作为独立桶强制纳入，并要求候选在该桶上通过正确性门才计入 fast_p。

六 · 可核查的测量口径清单与复现路径

把上述要素落成一份可执行的测量协议，至少包含以下字段，缺一即视为不可比：硬件（GPU 型号、数量、时钟状态、驱动/CUDA 版本）、基线（库版本、heuristic 设置、TF32 开关、融合边界）、dtype 矩阵（允许集合与参考 dtype）、输入分布（公开/隐藏划分、桶定义、每桶样本数）、计时方法（warmup 次数、重复次数、取中位数还是最小值、是否含 host-device 同步）、正确性门（容差定义、校准方法、是否允许 fallback）、profile 字段（算术强度、带宽利用率、占用率，仅用于解释）、agent 预算（agent-hours、token、重试）。

计时方法本身是口径事故高发区。CUDA event 计时必须包含必要的同步，否则会把异步下发的时间漏算；多次重复取中位数可抗离群，但会掩盖尾延迟，生产关注的是 p99 而非中位数，因此口径上应同时报告中位数与 p99。warmup 不足会让首次编译与 JIT 开销混入时延，尤其对 Triton 候选影响显著——Triton 的 autotune 在首次调用时枚举配置，编译时间可达数百毫秒到数秒，若不计入 warmup 就会被误记为运行时开销；反之若把 autotune 时间计入端到端，又会惩罚那些用编译时间换运行时性能的候选。工程判断是把编译/autotune 时间单列为“编译代价”字段，与运行时延分开报告。

复现路径上，论文给出代码仓库 github.com/Snowflake-AI-Research/fastkernels，可核查的做法是：先跑参考实现建立基线时延表，再在同一机器上跑候选，逐任务比对 fast_p 与 geomean，最后在完整模型上跑端到端回归。端到端回归必须使用与 kernel 级评测相同的输入分布，否则两层结果无法对齐。对于声称的 94.6% 覆盖率，应独立核对任务集与 HuggingFace 架构的映射表，确认“输出匹配”是在何种容差与何种 dtype 下判定的。

最后落在工程判断上：FastKernels 的口径价值不在于给出一个排行榜，而在于把“kernel 级赢”与“端到端赢”拆成两个必须同时满足的门。1.6×–6.6× 收缩到 1.25×、20% 可原样运行、kernel 级得分 mis-rank agent，这三个事实共同指向一个测量原则——任何只报 kernel 级加速比而不报端到端与可移植性的评测，其数字在生产语境下不可采信。可核查的替代做法是把端到端时延与“原样正确运行率”作为一等指标写入协议，kernel 级 fast_p 只作为诊断信号，用于定位哪个 primitive 还有空间，而不是作为部署决策的依据。
