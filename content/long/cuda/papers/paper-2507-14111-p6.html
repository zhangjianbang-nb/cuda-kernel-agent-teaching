一 · 单题成本的线性放大结构

CUDA-L1 的对比奖励要求同题多候选，这一条设计决定了整个系统的成本形状：单题开销不是常数，而是候选数的线性函数。设每题每轮采样 k 个候选，编译成功率 pc，则单题单轮的 GPU 执行次数期望为 k·pc，编译调用次数为 k。总成本可写成：

$$C_{\text{total}} = N_{\text{task}} \cdot R \cdot k \cdot \left( c_{\text{gen}} + c_{\text{compile}} + p_c \cdot (c_{\text{run}} + c_{\text{time}}) \right)$$

其中 cgen 是单候选的 token 成本，ccompile 是 nvcc 单次调用的墙钟时间，crun 是 GPU 执行时间，ctime 是计时重复取中位数的额外执行开销。注意 cgen 与 ccompile 对所有候选都要付，而 crun 只对编译通过的候选付——这意味着编译失败率越高，GPU 时反而越省，但 token 与编译时一点不少。工程上第一个要盯的比值就是 pc：它同时决定 GPU 利用率和负例池的填充速度。若 pc 偏低，系统会退化为“烧 token 换编译错误日志”，负例池里全是语法与类型错误，对比信号集中在低级错误上，对加速比排序几乎无贡献。具体例子：一个矩阵乘算子，k=8，若 6 个候选编译失败，则本轮只产生 2 次有效计时，成对偏好样本最多 2 对，而 token 与 nvcc 成本按 8 份计。

二 · token 与 GPU 时的错位账本

这两类资源的价格曲线完全不同，不能合并成一个“成本”概念。token 成本随候选数与轮数线性增长，且与生成长度正相关；CUDA 源码本身较长，一个带 tile、shared memory 与边界处理的 kernel 动辄数百行，生成 token 数远高于普通代码任务。GPU 时则由 k·pc 与计时重复次数决定，且计时为了抗噪通常要多次执行取中位数——给定材料明确计时方法未给出，但“多次计时取中位数”在流程描述中出现，意味着每个通过校验的候选至少被执行数遍。于是存在一个反直觉的账：减少候选数 k 能省 token 与编译时，却直接削弱对比奖励的质量，因为成对样本数按 k 的组合数下降；而成对偏好损失需要正负对，k=2 时最多 1 对，k=4 时理论上最多 6 对，实际受正确性过滤后更少。工程判断是：k 的下界由“每题每轮至少产生一对有效正负样本”决定，而不是由预算决定；若某题长期产不出正例（全部编译失败或全部更慢），该题应被降权或暂时移出采样池，否则它在消耗全额成本的同时只贡献负例，使偏好损失单向偏置。

三 · 编译时间是隐藏的串行瓶颈

nvcc 单次编译在带模板、CuTe 或大量 unroll 的 kernel 上会显著拉长，且编译是 CPU 侧的串行或半并行资源，与 GPU 执行不共享同一瓶颈。当 k 增大，编译队列先于 GPU 队列饱和：GPU 可能空闲等待编译产物，而 CPU 核心被 nvcc 占满。这是规模上去后最先崩的地方之一——不是显存，不是 GPU 算力，而是编译吞吐。缓解手段有三类，各有代价：其一，编译缓存，按源码哈希命中已编译的 cubin，命中率高时省掉重复编译，但缓存键必须包含编译选项与架构号，否则会拿到错误二进制，属于正确性风险而非性能优化；其二，并行编译池，把 k 个候选分发到多核，代价是内存占用与调度开销上升，且编译失败的结构化日志需要按候选归位，日志错配会污染负例池；其三，编译前置过滤，用轻量静态检查（括号匹配、明显类型错误）挡掉一部分必然失败的候选，省下 nvcc 调用，但过滤器本身可能误杀合法写法，需以“只挡确定性错误”为界。具体例子：同一算子 8 个候选串行编译，若单次编译墙钟是 GPU 执行的数倍，则整轮墙钟由编译主导，GPU 利用率被压到很低，此时增加 GPU 数量毫无收益。

四 · 搜索轮数与负例池的边际收益

多轮 RL 的轮数 R 不是越多越好。每轮更新后策略偏移，上一轮产生的负例池会逐渐与当前策略的采样分布失配——早期负例多是语法错误，后期负例多是“正确但不够快”的实现，两者对偏好损失的贡献不同。若负例池只增不减，训练信号会被历史低级错误稀释。工程上需要给负例池设淘汰或分层：按错误类型（编译失败 / 数值不一致 / 更慢）分层采样，保证每批对比对里三类都有代表，而不是让编译失败样本占满。代价是采样逻辑复杂度上升，且分层比例本身成为超参，调错会让模型偏向“先求编译通过”而牺牲优化激进性。另一个边际问题是轮数增加带来的缓存失效：若编译缓存按源码哈希，策略更新后源码分布变化，缓存命中率随轮数下降，编译成本回升。规模上去后第二个先崩的点就在这里——缓存命中率随训练推进单调下滑，而团队往往按早期命中率做预算，导致后期实际开销超出预估。

五 · 并发与正确性 oracle 的争用

并发执行候选会引入计时污染：多个 kernel 共享 GPU 时，计时结果互相干扰，加速比排序失真，进而把“被邻居拖慢的正确实现”误判为负例。这不是性能问题，是正确性判定问题——对比奖励的排序依赖计时，计时被污染则正负标签错位。因此计时阶段必须串行或至少独占 GPU，而编译与生成阶段可以并发。这形成流水线结构：生成与编译并行铺开，计时阶段收窄为单通道。代价是吞吐受计时通道限制，GPU 时利用率取决于计时通道的占空比。另一个争用点是参考实现的执行：每个候选都要与参考输出逐元素比对，参考实现若每次重跑，成本按候选数放大；若缓存参考输出，则需保证输入分布固定，否则缓存失效。具体例子：同一题 8 个候选并发编译、串行计时，若单次计时含多次重复执行，计时通道成为整轮墙钟的下界，此时提高并发度只缩短编译段，整体收益递减。给定材料未给出容差标准，浮点边界上的比对在并发与不同执行顺序下可能给出不一致判定，这是并发设计必须预留的稳定性余量。

六 · 中小团队的真实预算边界

把上述成本折算成可执行的预算判断，中小团队应优先核算三个量而非总算力：单题单轮的全额成本（token + 编译 + 计时）、有效正例产出率、缓存命中率随轮数的衰减曲线。第一个量决定能跑多少题，第二个量决定训练信号是否稠密，第三个量决定后期预算是否失控。可操作的门槛是：先在小规模算子集上测出 pc 与正例率，再反推 k 与 R 的上界，而不是先定 GPU 数量。若正例率极低，增加 k 只是放大负例，应改为提升提示中的编译约束或引入参考实现片段，把成本花在提高 pc 上。若缓存命中率衰减快，应把预算从“多轮”转向“少轮 + 更大 k”，用单轮内的宽采样换对比质量。给定材料未给出候选数、失败率与基准规模，因此任何预算表都只能以相对比例表达：token 成本与 k·R 成正比，GPU 时与 k·pc·R 成正比，编译墙钟在 k 超过并行编译核数后转为串行增长。工程判断落在一条上：对比奖励的质量由有效成对样本数决定，而有效成对样本数由正确性过滤后的候选分布决定——预算应优先买“过滤后仍有多样候选”，而不是买“更多轮”。

候选数放大后的成本结构与最先崩掉的环节

CUDA-L1 的单题成本不是一次前向加一次编译，而是“每轮 k 个候选 × 多轮 m 轮”的乘积。把单题训练开销写成 $$C_{\text{task}} \approx m \cdot k \cdot \left(c_{\text{gen}} + c_{\text{nvcc}} + c_{\text{run}} + c_{\text{verify}}\right)$$ 其中 nvcc 编译与 GPU 计时是主导项：编译一个中等复杂度的 CUDA 源文件在单核上要占用可观的 CPU 秒数，而计时阶段为保证中位数稳定往往要重复运行并做 warmup，GPU 时随候选数线性增长。生成侧反而是最便宜的——token 成本由输出源码长度决定，一个 kernel 几百到上千 token，相比编译与运行可以忽略。因此规模上去以后，第一个崩的通常不是显存也不是模型上下文，而是**编译吞吐**：当并发采样把 k 提到数十、并行题数上百时，nvcc 进程会把宿主机 CPU 打满，GPU 反而空转等编译。工程上的直接对策是把编译做成独立队列加结果缓存，以源码哈希（含编译选项与架构 sm 号）为键，命中则跳过 nvcc；同一算子在多轮之间重复生成的近似源码能吃到这部分缓存，但缓存命中率取决于采样温度，温度高则命中率低、成本回落有限。

第二个崩点是正确性 oracle 的判定成本与误判代价。逐元素比对本身是带宽受限的，输出张量大时比对耗时可以与 kernel 本身同量级；更麻烦的是容差未定义带来的边界风险：浮点累加顺序不同导致的末位差异，会让一个实际正确的 kernel 被判负例，进入负例池后污染对比信号。这类误判在成对偏好损失 $$\mathcal{L} = -\log \sigma\left(r_{i^{+}} - r_{i^{-}}\right)$$ 下的危害是双向的：既惩罚了正确实现，又让一个错误或更慢的实现被当作正例，梯度方向被系统性带偏。缓解手段是把比对分级——先用宽松容差筛掉明显错误，再对通过者在固定随机种子上做多次重复比对，只有稳定通过者才进入计时，代价是每题的 verify 调用次数翻倍。

第三个崩点是计时口径与并发争用。相对基线加速比依赖基线在同一硬件、同一时刻的测量；若训练集群上多个评测任务共享 GPU，SM 占用与 L2 争用会让计时抖动，中位数也压不住长尾。工程判断是给计时阶段独占 GPU 或至少做 SM 级隔离，并把基线时间在同一批次内重测而非复用历史值。下表给出各环节在规模上升时的增长方式与先崩顺序：

环节随规模的增长主要资源失效表现
候选生成线性于 m·ktoken / 显存上下文与吞吐，通常最后崩
nvcc 编译线性于 m·k，缓存可削减宿主机 CPU 核队列积压，GPU 空转
正确性比对线性于 m·k，随输出规模放大显存带宽容差误判污染负例池
计时线性于通过者数 × 重复次数GPU 独占时隙并发争用导致加速比不可比

对中小团队，现实预算应按“每题每轮可承受的编译次数”倒推 k，而不是先定 k 再算账：把编译队列的日吞吐除以题目数与轮数，得到可行的 k 上限，再决定是否用缓存与失败样本复用（编译失败的类型化错误可跨题复用为提示模板，减少重复试错）。若 k 被迫压到很小，对比奖励的同题候选不足，正负对退化，方法的核心优势随之消失——这是该方案在预算约束下最本质的边界，而非某个可以靠调参绕过的工程细节。
