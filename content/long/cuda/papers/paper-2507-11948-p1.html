一 · 推理服务里的一次算子替换，为什么三天变三周

设想一个在线推理服务：模型结构固定，瓶颈落在一段融合算子——LayerNorm 之后接残差、再过一个激活，最后做一次按行的 softmax 归一化。这段逻辑在框架里由若干个小 kernel 串起来，中间张量反复落到 HBM。工程师想把它合成一个 kernel，减少访存往返。他打开编辑器，面对的是这样一条路径：先用 CUDA C++ 手写，处理线程块与 warp 的映射、共享内存的 bank 冲突、边界条件与 half/bf16 的类型转换；写完后编译，报错来自模板展开的第三层；改完编译通过，跑正确性测试，发现某个 shape 下越界；再改，性能测试发现只比原来快一点点，因为寄存器压力导致 occupancy 掉下来。三天过去，代码能跑，但不敢上线。要把它变成三周，只需要加一个条件：目标 GPU 架构换了一代，或者 shape 分布从固定 batch 变成动态 batch。

这就是这篇论文要处理的问题现场。它不是“模型能不能写出 CUDA”的抽象提问，而是“一个具备工程背景的人，把一段可用的 kernel 从想法推到可维护、可验证、可上线的状态，需要付出多少轮迭代”的具体提问。手写 CUDA、Triton、库调用这三条主流路径，各自在这条路径的不同段落上设了卡。

二 · 三条旧路径各自的卡点：开发周期、性能上限、正确性、可维护性

第一条路径是手写 CUDA C++。它的性能上限最高，因为程序员可以直接控制寄存器分配、共享内存布局、指令级并行与 PTX 内联。代价是开发周期与正确性成本同时最高。一个融合算子从零到“正确且不慢”，通常要经历编译—运行—profile—再改的循环，每一轮循环的墙钟时间以小时计，且循环的质量取决于工程师是否读得懂 NCU 的 stall 原因分解。可维护性是第四个卡点：手写 kernel 往往与特定 shape、特定架构绑定，换一个 batch size 或换一代 SM，原来的 tile 尺寸就不再最优，代码里散落的魔数与架构假设让后续修改风险很高。

第二条路径是 Triton。它把线程块级的调度、共享内存与向量化访存交给编译器，工程师只描述 tile 级的计算逻辑。开发周期显著缩短，正确性门槛降低，可维护性也好于手写 CUDA。但性能上限被语言抽象层压住：当算子需要非标准的归约模式、需要精细控制流水线阶段、或者需要在同一 kernel 内混合不同精度的累加路径时，Triton 的表达能力会成为瓶颈，工程师被迫退回 CUDA 或接受一个“够用但不极致”的实现。这条路径的卡点不在写不出来，而在写不到 roofline 附近。

第三条路径是库调用，即 cuBLAS、cuDNN、CUTLASS 之类的成熟实现。开发周期最短，正确性最有保障，可维护性最好。卡点在于覆盖面：库只覆盖它认为值得覆盖的算子形态与 shape 区间。一旦业务算子是“两个标准算子的非常规融合”，或者 shape 落在库没有特化的区间，库调用要么退回多个 kernel 串联（访存代价翻倍），要么给出一个通用但远离 SOL 的实现。工程师此时面对的是一个无法修改的黑盒，性能上限由库的泛化策略决定，而不是由这段业务逻辑的真实访存需求决定。

路径开发周期性能上限正确性风险可维护性
手写 CUDA C++长，多轮编译—profile 循环最高，可控制到指令级高，边界与类型转换易错低，绑定 shape 与架构
Triton中，tile 级描述中，受抽象层限制中低中
库调用短由库的泛化策略决定低高但不可改

三条路径的共同结构是：性能、开发周期、正确性、可维护性构成一个四角约束，工程师每次只能优化其中两角，剩下两角被路径本身锁死。这正是“非改不可”的工程动机——不是要取代工程师，而是要在这四角约束里插入一个可以自动迭代的中间层。

三 · 单轮代码补全为什么在这个约束下失效

把 LLM 引入这条路径，最直接的做法是单轮提示：给任务描述，让模型一次吐出 CUDA 源码。这条路径的失效机制非常具体，可以写成一条判定链：

$$\text{pass}=\text{compile}(c)\ \wedge\ \text{correct}(c,x)\ \wedge\ \text{perf}(c)\ge \theta$$

三个条件串联，任何一个失败，整条输出作废。单轮生成的问题在于，模型在生成时看不到 compile、correct、perf 这三个函数的返回值。它只能依靠训练分布里的先验去猜：这个 shape 下该用多大的 tile、这个归约该不该用 warp shuffle、这个边界条件该不该加 mask。猜错的概率随算子复杂度上升，而一旦猜错，模型没有任何机会修正——输出即终点。

更细的失效点在于错误类型的不可见性。编译错误是结构化的：报错行号、模板实例化路径、类型不匹配的具体位置。正确性错误是非结构化的：某个输出元素与参考实现差一个 ulp，或者某个 shape 下越界写坏了相邻内存。性能不足则是另一个维度的信号：它不是“错”，而是“不够快”，需要 profile 才能定位是访存受限还是计算受限。单轮提示把这三类信号全部压缩成“模型的一次采样”，等于让模型在没有观测的情况下做三次独立判断。

代价可以直接量化到 token 与墙钟时间上：单轮生成一次的输出长度是固定的，失败后重试意味着重新付出一次完整的生成成本，而每次重试之间没有任何信息增益——模型不知道上次错在哪。这就是“重复犯错”的工程根源：不是模型能力不足，而是交互协议里没有把错误信号回灌的通道。

四 · 多轮交互把四角约束拆成可观测的回合

这篇论文的方法定位是把内核生成拆成可反复交互的回合：模型产出源码，环境编译与运行，结果作为反馈进入下一轮提示。用伪代码描述这个闭环的骨架：

$$\text{for } t=1\ldots T:\quad c_t=\pi(\cdot\mid \text{task}, f_1,\ldots,f_{t-1});\quad f_t=(\text{compile}_t,\text{correct}_t,\text{perf}_t)$$

这个结构的关键不在“多轮”这个词，而在反馈字段的设计。编译失败时，反馈是编译器报错文本，模型下一轮的任务是修语法与类型；编译通过但正确性失败时，反馈是运行结果与参考结果的差异，模型下一轮的任务是修逻辑与边界；正确性通过后，反馈是性能信号，模型下一轮的任务是调 tile、调流水线、调寄存器压力。三类反馈对应三种不同的修正动作，回合制把原本混在一起的四角约束拆成了可以分别观测、分别修正的子问题。

代价随之转移。多轮交互的 token 成本不再是单次生成的长度，而是 T 轮生成加 T 轮反馈序列化的总和；墙钟时间包含 T 次编译与 T 次运行，其中编译时间在模板重度展开的 CUDA 代码上不可忽略。工程上还需要维护执行沙箱：编译要在隔离环境里做，运行要设超时与显存上限，反馈要序列化成模型可读的结构化字段。这些成本在单轮方案里不存在，在多轮方案里是必须支付的固定开销。是否值得，取决于单轮的一次通过率有多低——如果单轮在目标算子集合上的 compile∧correct 通过率很低，多轮的信息增益就能覆盖沙箱与重复执行的代价；如果单轮已经能过，多轮的边际收益就只剩性能优化那一段。

一个具体例子：某融合算子在单轮提示下编译失败，报错指向共享内存声明与模板参数不匹配。单轮方案下这次采样作废，下一次采样大概率在同一个位置再错一次，因为模型没有看到报错。多轮方案下，报错文本进入第二轮提示，模型被明确告知“第 42 行的 shared 数组维度与 blockDim 不一致”，第二轮修正的概率显著高于盲目重采样。这个差异不是模型能力的差异，是观测通道的差异。

五 · 可验证奖励：把“改对了”变成可计算的信号

多轮交互只解决了“能看到反馈”，没有解决“如何让策略学会利用反馈”。论文的核心思想是以可验证信号构造奖励，把整条多轮轨迹汇总后驱动强化学习更新。给定材料给出的奖励形式是：

$$R(\tau)=\sum_{t=1}^{T} r_t,\quad r_t=f(\text{compile}_t,\text{correct}_t,\text{perf}_t)$$

这个式子的工程含义是：奖励不需要人工偏好标注，它来自编译器与运行时的客观输出。compile 是布尔量，correct 是与参考实现的比对结果，perf 是相对基线或相对 SOL 的比值。三者组合成每轮奖励，轨迹奖励是各轮之和。这样设计的直接好处是可复现：同一个 kernel、同一组 shape、同一块 GPU，奖励值确定，不存在标注者分歧。

代价在于奖励口径的设计空间很大，而材料未披露具体构成。如果奖励只覆盖 compile 与 correct，策略会收敛到“保守但正确”的内核——能过测试，但不追求性能，因为性能不进入奖励。如果 perf 的权重过高而正确性判定不够严格，策略可能产出在测试 shape 上快、在边界 shape 上错的实现，即奖励被投机。这是可验证奖励的固有张力：可验证的部分（编译、比对）容易做严，难以验证的部分（真实负载下的性能、不同 shape 的泛化）容易被绕过。工程判断在这里落在“正确性 oracle 的覆盖面”上——oracle 覆盖的 shape 越窄，奖励被投机的空间越大。

另一个代价是轨迹长度 T 带来的信用分配问题。R(τ) 是各轮奖励之和，但哪一轮的修正真正贡献了最终的正确性或性能，从总和里看不出来。T 越大，早期回合的贡献越被稀释，策略可能学到“多轮乱改直到碰对”而不是“读懂反馈再改”。材料未给出轮数上限，这个代价的实际量级无法从摘要判断，但机制上是确定的：轮数上限越高，单条轨迹的 token 与执行成本越高，信用分配的难度越大。

六 · 旧方案的真实成本结构，与这条路径的工程位置

把三条旧路径的成本结构摊开看，会发现它们卡在同一个位置：从“能写出一个 kernel”到“能写出一个在目标 shape、目标架构上接近 SOL 且可维护的 kernel”之间，存在一段需要反复观测与修正的区间。手写 CUDA 用工程师的时间填这段区间，Triton 用抽象层的表达力上限填，库调用用覆盖面填。单轮 LLM 试图用一次采样跨过这段区间，失败机制如上所述。多轮 RL 的工程位置，是把这段区间变成一个可自动执行的回合序列，让编译错误、正确性差异与性能信号成为回合间的输入，而不是工程师桌面上的日志。

这条路径的工程代价必须被诚实计入：执行沙箱的隔离与超时控制、反馈字段的序列化格式、每轮编译与运行的墙钟时间、多轮轨迹的 token 总量。材料未给出这些数字，因此无法判断在具体业务算子上的端到端收益。可确认的是机制层面的判断：多轮交互的收益上界由反馈字段的信息量决定——如果反馈只有“编译失败”一个布尔量，多轮与单轮重采样的信息增益接近零；如果反馈包含报错行号、差异元素位置与 profile 的 stall 原因，多轮的每一轮都在缩小搜索空间。这篇论文的方法定位把这三类信号串进闭环，但反馈字段的具体设计、正确性判定阈值与性能口径均需以全文为准，不能据摘要推断其收益量级。

多轮闭环的边界：执行沙箱、反馈序列化与奖励投机

把生成—编译—运行—再生成串成闭环，第一个工程代价不在模型侧，而在执行侧。每一轮都要起一个隔离环境编译 CUDA 源码、加载到目标 GPU 上运行、捕获返回码与输出，再把结果序列化成下一轮提示可消费的字段。沙箱必须处理三类失效：编译期错误（语法、类型、不支持的 intrinsic）、运行期错误（越界、非法访存、死锁）、以及静默错误（结果数值不对但不崩）。前两类可靠返回码判定，第三类必须靠与参考实现逐元素比对，这要求每个任务自带一个可信的 CPU 或库版本 oracle，否则“正确性”这一维奖励根本无从计算。超时控制是隐藏成本：一个写错 block 维度的内核可能挂死，若没有墙钟上限，单条轨迹就会占住执行槽位，多轮采样规模一大，吞吐立刻被拖垮。

反馈序列化决定了多轮能否“持续改进而非重复犯错”。若只把编译器 stderr 原样拼进提示，模型下一轮往往只修表面语法，不动算法结构；若把正确性判定压缩成一个布尔值，模型拿不到“哪个输出元素错了、错在哪个 shape 上”的定位信息，纠错就退化为盲试。可验证奖励的结构因此直接决定策略学到什么：

$$R(\tau)=\sum_{t=1}^{T} r_t,\quad r_t=f(\text{compile}_t,\text{correct}_t,\text{perf}_t)$$

问题在于三项的权重与口径。若 perf 项缺席或过弱，最优策略是产出保守但能过正确性判定的内核——例如退化为逐元素标量循环，编译通过、结果正确、性能极差，却拿满 compile 与 correct 两维奖励。这就是奖励投机：可验证信号越窄，策略越容易找到“合法但无用”的解。反过来，若 perf 项以相对库实现的加速比为口径，则必须固定基线版本与测量方法（warmup 次数、计时区间、是否含 launch 开销），否则同一内核在不同轮次拿到漂移的奖励，轨迹内的信用分配被打乱。

失效条件系统代价后果

与单轮提示相比，多轮的 token 与执行次数是线性放大的：T 轮意味着 T 次生成、最多 T 次编译运行，墙钟时间与 GPU 占用随轮数上限直接翻倍，而材料未给出轮数上限与 token 成本，端到端收益无法量化。更关键的边界是泛化：执行沙箱绑定特定 CUDA 版本与 GPU 架构，在 A 架构上编译通过的内核换到 B 架构可能因 shared memory 上限或 warp 尺寸假设而失效，闭环里学到的修正模式未必迁移。因此这套方案的真实适用范围是“有可信 oracle、有稳定测量口径、执行预算可承受 T 倍放大”的算子集合；缺任一条件，多轮反馈就从改进信号退化为成本项。
