一 · 一次真实的推理服务扩容决策

设想一个已经上线的推理服务：模型结构稳定，流量持续上涨，扩容评审会上有人提出把某个注意力前的投影算子换成自研 kernel，理由是“理论 FLOPs 利用率还有余量”。工程团队随即面对的不是一个算法问题，而是一条完整的证据链：这个 kernel 在目标 GPU 上是否数值正确、在真实 batch 与 shape 分布下是否真的比库函数快、换一个 cuBLAS 版本后结论是否还成立、谁来维护这份代码、下一次 GPU 型号切换时重测成本多大。这条链上任何一环断裂，替换决策就无法落地。CUDA-L2 这类工作之所以值得深读，恰恰因为它把这条链上的最后一环——以厂商库为基线的加速比——直接做成了学习目标。但在进入它的机制之前，必须先看清它所要替代的旧方案究竟卡在哪里。

矩阵乘法是这条链上最苛刻的试验场。cuBLAS 在主流 GPU 上对常见 shape 已经做了多年手工调优，涵盖分块尺寸、共享内存布局、寄存器级双缓冲、warp 级 tile 划分、以及针对不同 shape 的启发式选择。任何“通用代码生成”产出的 kernel，要在这块已经被反复压榨过的地面上取得优势，等于要在成熟算子库的最强项上做增量。这正是问题的现场：不是没有 kernel 能跑，而是能跑的 kernel 与库之间的差距，在正确性、tiling 质量与占用率三个维度上同时存在。

二 · 三条旧路径各自的成本结构

论文之前，GPU kernel 工程的主流做法可以粗分为三类，每一类的痛点性质不同，但都指向同一个结论：人工路径的迭代速度跟不上硬件与模型结构的演化速度。

第一类是手写 CUDA C++。它的性能上限最高，工程师可以直接控制寄存器分配、共享内存 bank 布局、`__syncthreads()` 的位置与 `cp.async` 的流水深度。代价是开发周期以人周计：一个矩阵乘 kernel 从朴素三重循环到接近 cuBLAS，通常要经历多轮 profile 驱动的改写，每一轮都依赖 NCU 计数器（occupancy、shared load/store 效率、warp stall 原因）来定位瓶颈。更麻烦的是正确性：边界处理、非对齐访存、fp16 累加溢出、以及不同 shape 下的尾块处理，都是容易出错且难以用单元测试穷尽的地方。可维护性则体现在人身上——写出这个 kernel 的工程师一旦离开，后续 GPU 架构换代时的重调优几乎等于重写。

第二类是 Triton。它用块级编程模型把 tiling、mask 与流水调度交给编译器，开发者只需描述 tile 的形状与累加逻辑，开发周期从人周压缩到人天甚至人时。代价是性能上限受编译器约束：自动生成的流水与寄存器分配未必贴合特定 GPU 的 SM 结构，在极端 shape 或需要精细控制共享内存 swizzle 的场景下，往往落后手写实现一截。同时 Triton 的表达能力边界意味着某些优化（比如非常规的 warp 特化、跨 tile 的软件流水）难以直接表达。

第三类是直接调用 cuBLAS 或 cuDNN 等厂商库。这是生产环境最常见的选择：零开发周期、正确性由厂商背书、版本升级即获得新架构优化。代价是性能上限被库的通用性锁死——库必须覆盖所有 shape，因此无法为某一个特定 shape 做极致特化；当模型结构中出现非标准 shape、融合机会（比如 matmul 后接 bias 与激活）或特殊数据类型时，库调用要么退化为多次 kernel 启动，要么干脆不覆盖。可维护性看似最好，实则把风险转移到了版本依赖上：库的行为随版本变化，性能回归与数值差异都可能在不经意间引入。

路径开发周期量级性能上限正确性风险来源维护负担

三类路径的共同结构是：性能、开发速度、正确性保证三者不可兼得。工程团队每次做算子决策，实际上是在这个三角里选一个角，然后承担另外两个角的代价。这个三角正是自动 kernel 生成想要打破的对象——如果模型能在真实 GPU 上快速试错，并以库为基线度量，那么“开发周期”这一角可以被压缩，而“性能上限”与“正确性”则通过执行反馈来守住。

三 · 通用代码生成模型的第一道墙：正确性

在大语言模型进入这个领域之后，最先暴露的问题不是慢，而是错。通用代码生成模型产出的矩阵乘 kernel，在结构上往往看似合理——有外层 tile 循环、有共享内存暂存、有 `__syncthreads()`——但在真实 GPU 上运行时，失败模式高度集中：寄存器溢出导致编译期报错或占用率骤降；共享内存申请超过 SM 上限导致 kernel 无法启动；边界处理缺失导致非方阵或非整除 shape 下越界读写；同步点位置错误导致共享内存读写竞争，数值结果随机偏差。

这些失败对单轮提示范式是致命的。单轮提示下，模型看不到自己产出的 kernel 在编译器和硬件上发生了什么，只能凭训练分布里的“常见写法”生成代码。一旦 shape 偏离训练分布中的典型方阵，错误率急剧上升。更关键的是，模型没有任何机制知道自己错在哪一类：是寄存器压力、是同步、还是尾块。没有分类的失败信号，下一轮生成只能靠随机扰动，收敛效率极低。

正确性作为硬门槛的意义在这里显现。若把速度纳入奖励而不先过数值校验，模型会迅速学会用错误结果换取低延迟——比如跳过部分累加、缩小 tile 覆盖范围、或在边界处直接返回未初始化值。这类“快而错”的解在搜索空间里比比皆是，且比正确解更容易被采样到。因此奖励必须写成硬门槛形式：

$$r=\begin{cases}\dfrac{t_{\mathrm{cuBLAS}}}{t_{\mathrm{kernel}}}, & \text{若数值校验通过}\\0, & \text{否则}\end{cases}$$

这个式子的工程含义是：正确性是乘性前置条件而非可加项。校验不通过的样本奖励归零，但其失败类型（编译错误、数值偏差、资源超限）仍被记录并回传，作为负样本诊断。代价是采样效率——大量轮次会消耗在失败样本上，token 与 GPU 机时被用于生成不可用的 kernel。这是自动生成路径相对于手写路径新增的一项成本，且在多轮训练中持续存在。

具体例子：某轮模型为一个非整除 shape 生成 kernel，tile 尺寸取 128×128，但 M 维度不是 128 的倍数，代码中缺少尾块 mask，运行层比对参考结果时发现最后几行数值偏差超阈值，奖励置零，失败类型标记为“边界处理缺失”。下一轮模型在同一 shape 上倾向于加入边界判断或改用更小的 tile，这正是失败诊断回流的价值所在——它把一次数值失败转化成了一条可操作的搜索方向。

四 · 第二道墙：以库为基线的度量口径

正确性之后是性能。这里的痛点不是“kernel 慢”，而是“慢多少、跟谁比、怎么比才算数”。手写工程师习惯用 SOL（speed of light）或 roofline 模型估算上限，但在生产决策中，真正有说服力的口径只有一个：同 shape、同数据类型、同 GPU、同 cuBLAS 版本下，kernel 延迟与库延迟之比。CUDA-L2 把这一口径直接写进奖励，等于把“是否值得替换库调用”这个工程问题翻译成了优化目标。

这个口径的代价是它对环境极度敏感。计时必须固定预热次数与重复次数以压低噪声；cuBLAS 基线必须用同 shape 重测，而不能引用别处的数字；GPU 型号或 cuBLAS 版本一变，基线漂移，此前所有加速比结论的可比性归零。这意味着每一次硬件或库升级，整套评测都要重跑。对训练侧而言，这意味着奖励信号的可复现性依赖于一套固定的测量协议，协议不稳，策略学到的就是噪声。

更微妙的是 shape 依赖。cuBLAS 对不同 shape 使用不同的内部启发式与 kernel 变体，某些 shape 上库已经接近硬件上限，另一些 shape 上库的选择并非最优。因此“超过 cuBLAS”这个结论必须绑定 shape 集合才有意义。论文材料只到摘要级，未披露 shape 数量与具体分布，这使得“超过”的强度无法从外部判断——它可能是在少数对库不利的 shape 上取得的，也可能覆盖了较广的分布。工程读者在引用时必须把这一点作为前提，而不能把它当作普适结论。

度量口径还带来一个隐性成本：为了让加速比可比，评测必须固定 shape 集合、基线版本与计时口径。这三者中任何一项变动，都会让历史轨迹中的奖励失去参照。多轮训练下，这意味着训练环境与评测环境必须严格一致，否则策略会在一个漂移的奖励地形上优化。这是自动生成路径相对于库调用路径新增的第二项工程负担。

五 · 第三道墙：反馈的组织方式决定搜索效率

即便正确性与度量口径都解决了，单轮或少轮反馈仍然不够。执行反馈包含三类性质完全不同的信号：编译错误（语法、寄存器溢出、共享内存超限）、运行时数值失败（同步错误、边界越界、精度偏差）、以及计时结果（延迟与加速比）。这三类信号若被压成一个标量奖励，模型无法区分“我编译不过”与“我编译过了但慢了 3 倍”这两种处境，而它们需要的修正动作完全不同。

CUDA-L2 的处理方式是把失败类型显式归类回传，与高奖励样本共同进入多轮轨迹。其闭环结构是：策略生成源码 → 编译层捕获资源与语法错误 → 运行层执行并与参考结果比对 → 计时层以 cuBLAS 为基线算加速比 → 奖励聚合层把正确性、加速比与失败类型编码为标量信号回传 → 训练侧按轮次筛选高奖励样本与诊断信息更新策略。这个结构的关键不在任何单一环节，而在于失败诊断不被丢弃：编译失败与数值失败作为负样本保留，使模型在后续轮次中规避同类写法。

代价体现在样本效率与工程复杂度上。多轮意味着每个 shape 要消耗多次生成、编译、运行与计时的完整循环，GPU 机时与 token 成本随轮数线性增长，而材料未给出轮数、批量与 token 成本，工程代价无法从外部估算。另一个代价是反馈延迟：编译与运行是串行环节，一轮的端到端时延由最慢的环节决定，若计时需要多次重复测量以压噪声，单轮时延进一步拉长。这与手写工程师用 NCU 做一次 profile 的时延量级不同——后者是人工介入的分钟级，前者是自动化但需要吞吐支撑的批量循环。

具体机制上，一个可操作的伪代码思路是：对每个 shape，采样若干 kernel，先过编译，编译失败则记录错误类别并跳过运行；编译通过则运行并做数值比对，失败则奖励置零并记录偏差类型；通过则多次计时取稳健统计量，与同 shape 的 cuBLAS 基线相除得到奖励。高奖励样本进入正样本池，失败样本按类别进入诊断池，两者共同构成下一轮策略更新的数据。这个流程的工程判断点在于：诊断池的容量与采样比例需要控制，否则失败样本会淹没正样本，使策略在“避免错误”上过拟合而牺牲性能探索。

六 · 为什么非改不可：三角约束下的工程判断

回到开场的扩容评审。若团队选择手写路径，得到的是最高性能上限与最长开发周期；若选择库调用，得到的是零开发周期与被通用性锁死的上限；若选择 Triton，得到的是折中的开发速度与受编译器约束的上限。三者都无法同时满足“快速迭代 + 逼近库性能 + 正确性可验证”这三个生产要求。模型驱动的自动生成之所以值得投入，是因为它有可能把开发周期这一角压缩到与 Triton 相当甚至更低，同时用执行反馈把正确性守住，并把性能上限的目标直接锚定在库基线上。

但这条路径新增的代价必须被正视：失败样本消耗的采样成本、计时协议漂移导致的可比性风险、以及多轮循环的 GPU 机时与 token 开销。这些代价不会因为“用上了强化学习”而消失，它们只是从人身上转移到了系统与算力上。工程判断的关键在于：当 shape 分布稳定、GPU 型号单一、且库在该 shape 上确有未压榨的余量时，自动生成的收益可能覆盖其成本；而当 shape 高度动态、硬件频繁换代时，基线重测与协议维护的成本会迅速侵蚀收益。

这也解释了为什么矩阵乘是一个合理的切口而非终点。它是库优化最成熟、度量口径最清晰、正确性校验最直接的算子，因而最适合检验“执行反馈驱动的搜索能否在成熟库面前取得优势”这一命题。若在这个最苛刻的试验场上，以 cuBLAS 加速比为奖励的多轮闭环能够稳定产出可比甚至更优的 kernel，那么硬件计时信号作为 kernel 生成核心优化目标的可行性就得到了初步验证。反之，若在矩阵乘上都无法稳定超过库，那么把方法扩展到卷积、归一化等更广算子族的路径就需要重新评估——因为那些算子的基线更弱、shape 更不规则、正确性 oracle 更难构造，搜索空间的噪声只会更大。论文材料仅到摘要级，加速比数值、shape 集合与训练成本均未披露，因此这一判断目前只能停留在机制层面：闭环结构成立，但闭环在真实工程约束下的效率与泛化边界，仍需后续证据填充。
