一 · 单轮提示：一次前向的输入、输出与代价

在 KernelBenchX 的流动里，单轮提示是最短的一条路径：把任务描述、参考实现的 PyTorch 语义、输入 shape/dtype 约定拼成一个 prompt，模型直接吐出 Triton kernel 源码，然后进入编译。它的输入是三段式——算子语义（例如 Fusion 类里多个逐元素算子的组合关系）、参考实现的签名与广播规则、以及评测口径要求的输出契约（返回张量还是原地写回）。输出是一段候选源码，通常带 @triton.jit 装饰器和手写的 grid lambda。

代价集中在两处。第一是编译时间：Triton 的 JIT 首次编译要经过 AST 解析、TTIR/TTGIR 变换、LLVM 后端与 PTX 生成，一个中等复杂度的 kernel 在冷启动下是秒级开销，而基准里 176 个任务、15 个类别、五个方法各跑一遍，编译预算本身就是可观的一项。第二是 token：单轮提示没有反馈回路，模型必须在一次生成里同时决定 tile 大小、num_warps、mask 策略与边界处理，任何一处判断失误都直接落到编译失败或语义错误上。KernelBenchX 报告 GEAK 迭代中编译率从 52.3% 升到 68.8%，这个起点数字说明：单轮提示下接近一半的候选连编译门都过不了，代价不是时延而是直接归零。

具体例子是 Fusion 类任务：把 bias-add、GELU、dropout 三个逐元素算子融成一个 kernel。单轮提示下模型常见的错误是把 dropout 的随机数生成放进 kernel 内部却没有对齐 PyTorch 的 RNG 语义，编译能过、运行不报错，但正确性检查在固定 seed 下立刻失败。这类失败不是性能问题，而是语义契约没被单轮提示完整承载——这正是 KernelBenchX 把「任务结构决定正确性多于方法设计」列为第一发现的经验基础：72% 的 Fusion 任务在五个方法下全部失败，单轮提示只是其中最先崩的一环。

二 · Agent 脚手架：把编译与运行反馈折进下一轮

脚手架在单轮之上加了一个循环：生成 → 编译 → 运行 → 正确性检查 → 把结果回灌进下一轮 prompt。输入因此从静态任务描述变成「任务描述 + 上一轮源码 + 编译器报错或运行时不匹配的具体信息」。输出是修正后的候选，以及一个保留/回退决策。机制上最关键的是反馈的粒度：把 PTX 汇编报错原文塞回去，还是把「第 3 个输出张量在 shape (128, 4096) 上与参考实现最大绝对误差 1e-2」这种结构化诊断塞回去，决定了模型能否定位问题。KernelBenchX 的五个代表方法在这一层的差异，正是它要比较的对象。

代价是轮数与编译预算的乘积。每一轮都要重新编译，而 Triton 的编译缓存只在源码哈希不变时命中；一旦模型改了 tile 常量，缓存失效，编译时间重新计入。更隐蔽的代价是「救回来的 kernel 更慢」：论文给出的数字是，随着 GEAK 迭代推进，编译率从 52.3% 升到 68.8%，但平均加速比从 1.58× 降到 1.44×，新救回的 kernel 稳定地弱于一直正确的那些（1.16× 对更高值）。这说明脚手架优化的是「能不能跑」，而不是「跑得多快」——迭代精修提升正确性但不提升性能，是论文的第二条发现。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个打分式在脚手架语境下的含义是：只有当候选的加速比超过阈值 τ 才计一分，而 s_i 的分母是统一基线（PyTorch eager、torch.compile 与论文指定库）的时延。脚手架如果只盯着编译通过与数值正确，就会把大量 s_i 略大于 1 甚至小于 1 的候选留在池子里；46.6% 的正确 kernel 比 eager 基线还慢，这个比例正是「正确不等于高效」的量化表达。一个具体例子是 Math 类任务：它们被五个方法一致解出，因为语义简单、边界少，脚手架只需一两轮就能收敛；但 Fusion 类即使迭代多轮，救回的候选也往往因为多算子融合后寄存器压力上升、occupancy 下降而落在基线之下。

三 · RL 训练回路：奖励从哪来、代价落在哪

RL 路径把「生成—编译—运行—评测」整体当作环境，策略网络是 LLM，动作是 token 序列，奖励由 verifier 给出。输入是任务池与参考实现；输出是一批带奖励信号的轨迹，用于策略更新。机制上有两个必须说清的点。其一是奖励的可验证性：KernelBenchX 的口径下奖励至少分两层——正确性门（与参考实现逐元素比对，含 dtype 与容差）与性能门（相对统一基线的加速比）。其二是奖励稀疏性：编译失败给零奖励，语义错误给零奖励，只有通过正确性门才拿到与 s_i 挂钩的连续奖励，这让梯度信号在早期极其稀疏，52.3% 的编译率意味着近一半采样拿不到任何有效梯度。

代价是采样吞吐。每条轨迹都要真实编译并跑在 GPU 上，编译时间与 kernel 执行时间共同构成每步的墙钟成本；相比纯文本 RL，这里的环境步是秒级而非毫秒级。另一个代价是 reward hacking 的空间：如果奖励只看「比 eager 快」，模型可以生成针对基准输入 shape 特化的 kernel，在隐藏输入分布上崩塌；如果奖励只看正确性，模型会退化成逐元素朴素实现，46.6% 慢于基线的现象就是这种退化的下游表现。跨硬件加速比方差达到 21.4×，意味着在单卡上训出的奖励信号换一张卡就可能完全失真——RL 回路必须把硬件标识当作环境状态的一部分，而不是隐含常量。

具体例子是 Math 类任务在 RL 下的行为：因为正确性容易达成，奖励几乎全部由性能项主导，策略会迅速收敛到少数几种 tile 配置；而 Fusion 类因为 72% 的全方法失败率，奖励长期为零，策略在这些任务上得不到有效更新，形成类别间的不均衡。这正是「类别解释了近三倍于方法的语义正确性方差（9.4% 对 3.3% explained deviance）」在训练侧的投影：方法设计的改进幅度，被任务结构的难度差异压过去了。

四 · Verifier：正确性 oracle 与性能门的串联

verifier 是整条流动的裁判，输入是候选源码、参考实现、输入分布与基线时延，输出是布尔正确性判定加一个加速比数值。机制上它必须做三件事：编译候选并捕获编译错误；在论文给定的输入分布上跑参考实现与候选，逐元素比对（含 NaN/Inf 语义、dtype 提升规则、非连续张量的 stride 处理）；用统一基线测时延，通常需要 warmup 与多次重复取中位数以压住测量噪声。任何一环缺失都会让分数虚高：基线若没开 TF32 或没用最强库实现，加速比会被系统性高估。

代价分三类。编译时间已在前两节计入；测量时延本身要占用 GPU 时间，且为了压噪声需要重复采样，176 个任务乘以五方法乘以多轮，累计的 GPU 小时不是小数；显存占用则是隐形成本——Fusion 类候选如果 tile 过大导致 shared memory 超限，编译期就报错，但如果只是接近上限，运行时 occupancy 下降，测出来的时延会显著劣化，而这类劣化在单次测量里容易被误读为「实现不好」而非「资源约束」。

具体例子是跨硬件方差：同一份正确 kernel 在不同 GPU 上的加速比可以差到 21.4×，verifier 若只在一张卡上给奖励，就等于把硬件特性编码进了评分。KernelBenchX 的口径要求基线、输入分布、硬件三者同时固定，任何一项漂移都会让 s_i 失去可比性。这也是为什么论文把「正确性不蕴含高效性」单列为第三条发现：verifier 的正确性门和性能门是串联的，通过前者不保证后者，46.6% 的正确 kernel 慢于 eager 就是串联结构下最常见的漏网形态。

五 · 四类方法在同一条流动上的位置差异

把单轮提示、agent 脚手架、RL、verifier 放在同一条「生成—编译—运行—评测」流动上看，它们的差别不在环节数量，而在反馈回路的闭合位置。单轮提示在生成后即断开，编译与运行结果不回灌；脚手架把编译与运行结果回灌到生成，回路闭合在「下一轮 prompt」；RL 把 verifier 的奖励回灌到策略参数，回路闭合在「梯度」；verifier 本身不生成，只做门控，是前三条路径共用的裁判。

这张表对应论文的核心比较框架：五个代表方法各自落在不同位置，而 KernelBenchX 的结论是位置差异带来的正确性方差（3.3%）小于任务类别带来的方差（9.4%）。换句话说，把方法从单轮换成脚手架或 RL，收益不如「这道题本身属于哪个类别」重要。一个具体判断是：在 Fusion 类上，无论换哪种方法，72% 的失败率都不动；在 Math 类上，单轮提示就能稳定解出。这意味着工程上选择方法之前，先做类别分层比调方法超参更划算。

六 · 流动上的工程判断：先分层，再闭合回路

把这条流动落到工程实践，第一步不是选方法，而是按类别给任务分层：Math 类可以用单轮提示加严格 verifier 快速过；Fusion 类必须上脚手架，且要把「救回的候选是否真的更快」作为独立门控，而不是只看编译率上升。第二步是闭合位置的选择：如果目标是正确率，脚手架的回灌粒度要细到具体张量索引与误差量级；如果目标是性能，RL 的奖励必须包含跨硬件归一化，否则 21.4× 的方差会把策略引向单卡特化。

第三步是 verifier 的成本核算：编译时间、测量重复次数、显存上限三者共同决定单任务的评测预算，而 176 个任务乘以五方法意味着预算要按类别分配——Fusion 类失败率高、迭代轮数多，编译预算应向其倾斜；Math 类收敛快，可以把预算省下来给性能测量做更多重复采样。最后一步是接受「正确不等于高效」作为流动的固有属性：46.6% 的正确 kernel 慢于 eager，这个数字不是 bug 而是串联门控的必然产物，工程上要做的不是消除它，而是在 verifier 里把性能门设为独立且不可跳过的第二道闸，让 s_i 的分母始终是统一基线，让 τ 始终显式。

一个具体机制上的收尾判断：KernelBenchX 把「类别」作为一等公民写进评测口径，本质上是承认生成—编译—运行—评测这条流动的瓶颈不在回路闭合的技术实现，而在任务结构本身的可解性分布。52.3% 到 68.8% 的编译率提升伴随 1.58× 到 1.44× 的加速比下降，说明回路越闭合、越容易把「能跑」误当成「跑得好」；因此任何闭合回路的设计都必须把性能门与正确性门做成并联而非串联，否则迭代只会把候选推向基线之下。

失效边界：类别方差、迭代陷阱与正确性—效率剪刀差

这套流程的边界首先由任务类别划定，而不是由方法设计划定。论文给出的方差分解是硬约束：类别对语义正确性的解释偏差为 9.4%，方法仅 3.3%，前者接近后者的三倍；同时 Fusion 类任务在五种方法上全部失败的比例高达 72%，而 Math 类任务被稳定解出。这意味着在同一套生成—编译—运行—评测流水线上，Fusion 的失败并非某个脚手架或某轮 RL 的偶发失效，而是结构性的：融合算子要求跨算子边界重排数据布局与归约顺序，候选一旦在 tile 划分或共享内存复用上选错，正确性门就直接拦下，后续时延测量根本不会发生。工程判断是：把预算按类别分配，Fusion 上应优先投入参考实现对齐与分步验证，而不是盲目增加采样轮数。

迭代精炼的代价可以用一条单调性陷阱刻画。论文报告 GEAK 迭代中编译率从 52.3% 升到 68.8%，而平均加速比从 1.58× 降到 1.44×；被“救回”的 kernel 稳定劣于持续正确的 kernel（1.16× 对更高值）。其机制在于反馈回灌的目标函数错位：编译失败与运行报错是可判定的强信号，模型会优先修复它们，于是把资源投向“能跑”而非“跑得快”，新救回的候选往往靠退化策略（更小 tile、更多同步、放弃向量化）换取可编译性。伪代码层面可写成保留规则 keep = (correct_new) and (speedup_new > speedup_best)，若省略后半句，迭代就变成正确率的单目标爬坡。系统代价是每轮编译与 profile 的时延开销被浪费在低质量候选上，token 预算随轮数线性膨胀而收益递减。

正确性不蕴含效率，这是评测口径最容易被误读的地方：46.6% 的正确 kernel 慢于 PyTorch eager 基线，跨硬件加速比方差达 21.4×。评分公式本身只做阈值计数，$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$ 其中 s_i 是相对统一基线的加速比、τ 是判定阈值，它把连续的性能差异压成二值，掩盖了 1.16× 与 1.44× 这类差距，也让“正确但慢”的候选在计数上不受惩罚。更隐蔽的失效来自基线口径：若基线未开 TF32 或未用最强库实现，T_base 被抬高，加速比被系统性高估；shape 特化与隐藏输入分布则让离线分数在生产上崩塌。因此这套方案的可信度上限取决于三件事同时成立——基线按论文口径固定、输入分布覆盖非特化 shape、正确性门之外再加性能门与跨硬件复测。
