一 · 评测口径的第一性约束：材料只到摘要级

本部分要处理的是一个不太讨喜但必须正面回答的问题：Kevin 这篇工作公开材料只到摘要级，那么“基准与口径”这一节能写什么、不能写什么。工程判断的第一步不是罗列指标，而是划出可核查与不可核查的边界。给定事实中明确写着：评测负载形态未给出（算子集合、shape 分布、题量规模），硬件环境未给出（目标 GPU 架构与显存配置），基线配置未给出（单轮提示或已有 agent 方案），输入分布未给出（任务描述来源与难度分层）。这意味着任何“Kevin 在 KernelBench 上达到 X 倍加速”式的陈述都属于编造。可核查的只有方法骨架：多轮交互、编译与运行反馈回灌、可验证奖励汇总轨迹。因此本节的写法是——把评测口径拆成若干必须显式声明的字段，逐个说明 Kevin 材料在这些字段上的状态，并给出当全文补齐时应当如何核对的口径模板。这不是回避，而是把“不可比”本身当作一个工程结论来交付。

一个可操作的口径清单至少包含七项：基准与题量、基线、硬件、dtype、指标定义、隐藏 shape/分布处理、正确性 oracle。任何一项缺失，跨论文的加速比数字就失去意义。以 dtype 为例，同一算子在 fp32 与 bf16 下的 roofline 拐点完全不同：fp32 的算力峰值通常远低于 bf16，内存带宽却相同，于是同一内核在 fp32 下可能被判为 compute-bound，在 bf16 下却是 memory-bound。若两篇论文各自不声明 dtype，把它们报告的 speedup 并列就是无效比较。Kevin 材料未披露 dtype，这一点必须在引用其任何性能结论时标注为“口径未知”。

$$\text{Speedup} = \frac{T_{\text{base}}}{T_{\text{kernel}}},\qquad \text{geomean} = \exp\!\Big(\frac{1}{N}\sum_{i=1}^{N}\ln \text{Speedup}_i\Big)$$

上式的两个细节决定可比性。其一，$T_{\text{base}}$ 是基线选择问题：对 matmul 用 cuBLAS 还是用朴素 tiled 内核，得到的 speedup 可以差一个数量级；对 elementwise 用 PyTorch eager 还是用融合后的 TorchInductor，结论同样翻转。其二，geomean 对“快得离谱的个别样本”不敏感、对“慢于基线的样本”惩罚温和，因此单看 geomean 会掩盖长尾失败；工程上必须同时报告 fast_p（例如 fast_1、fast_5，即加速比超过 1 倍或 5 倍的样本占比）与慢于基线的比例。Kevin 材料未给出任何通过率、加速比或性能数字，因此这三个量在本文中只能作为口径要求提出，不能作为结果引用。

二 · faster rate 与 fast_p：把“能跑”与“跑得快”分开计

内核生成的评测最容易犯的错误是把编译通过、正确性通过、性能超过基线三件事压成一个布尔量。多轮 RL 场景下这个错误代价更高：奖励若只覆盖编译与正确性，策略会收敛到“保守但低性能”的内核——这是给定事实中明确列出的失败模式之一。因此口径上应把三层判定拆开：编译成功率、正确性通过率、faster rate。faster rate 定义为在正确性通过的样本中，加速比严格大于 1 的占比；它与 fast_p 的区别在于阈值：fast_p 用固定倍数门槛（如 1×、2×、5×），faster rate 只用 1× 作为分界。两者都需要分母声明——分母是全部题量还是仅正确样本，会显著改变数值。工程上推荐双报：以全部题量为分母的“端到端 faster rate”反映真实收益，以正确样本为分母的“条件 faster rate”反映优化能力。

这里有一个具体的机制性代价。假设一个 100 题的小基准，模型编译成功 80 题、正确 60 题、其中 30 题快于基线。端到端 faster rate 是 30%，条件 faster rate 是 50%。若论文只报后者，读者会高估系统可用性；若只报前者，又看不出优化环节的瓶颈在正确性还是在性能。多轮 RL 的轨迹长度 $T$ 还会放大这个偏差：轮数上限越高，编译失败被修复的概率越大，端到端 faster rate 随 $T$ 单调上升，但每轮都消耗推理 token 与 GPU 执行时间。给定事实指出材料未给出 token 成本与墙钟时间，因此无法量化这条曲线的边际收益。可核查的口径要求是：报告 faster rate 时必须同时给出 $T$、每题平均轮数、以及每轮的平均 token 数，否则无法判断提升来自“更会改代码”还是“更多次尝试”。

表中最后一列的“缺失后果”不是修辞，而是可操作的审查项。以正确性 oracle 为例，若容差用相对误差 $10^{-2}$ 而非 $10^{-5}$，一个数值上不稳定的 reduction 内核也能通过，随后在性能上因为跳过了补偿求和而显得更快——这就是奖励投机的最小实例。给定事实明确写着“未披露正确性判定与性能口径，难以判断奖励是否可被投机利用”，因此任何引用 Kevin 性能结论的工程文档都应把 oracle 容差列为待核项。

三 · roofline 与 SOL：把 speedup 换算成“离上限多远”

speedup 是相对量，roofline 是绝对量。二者并用才能回答“这个内核还有多少空间”。roofline 的基本形式是：给定算术强度 $I$（FLOP/Byte），可达性能上界为算力峰值与带宽乘以 $I$ 的较小者。工程上更常用 SOL（speed of light）口径：以 NCU 采集的 DRAM 吞吐占峰值带宽的比例、SM 吞吐占峰值算力的比例，取两者较大者作为“已达上限的百分比”。一个内核若 SOL 只有 30%，即便 speedup 为 2×，也只说明基线更差，不说明内核接近硬件极限。

$$P_{\text{roof}}(I)=\min\big(P_{\text{peak}},\; B_{\text{peak}}\cdot I\big),\qquad \text{SOL}=\max\!\Big(\frac{\text{DRAM}_{\text{achieved}}}{B_{\text{peak}}},\;\frac{\text{SM}_{\text{achieved}}}{P_{\text{peak}}}\Big)$$

这个换算带来一个具体的评测代价：SOL 需要 NCU 级 profile，而 profile 本身会引入测量开销（多次 replay、时钟锁定、缓存刷新），单题采集时间远高于一次计时运行。给定事实指出材料未说明是否接入 NCU 或 SASS 级性能采集，因此 Kevin 的奖励是否包含 SOL 级信号无法确认。若奖励只用墙钟时间，模型可能学到“减少 launch 开销”而非“提升吞吐”的策略——在小 shape 上这确实有效，但在大 shape 上会失效。可核查的口径要求是：报告 speedup 时注明计时方式（CUDA event、wall clock、是否含数据传输与内核 launch），报告 SOL 时注明采集工具与 replay 次数。两者混用会让“快”这个字失去物理含义。

具体例子：一个 shape 为 4096×4096 的 fp16 matmul，算术强度约为 $2N^3/ (3N^2 \cdot 2\text{B})$ 量级，落在 compute-bound 区间；同一内核换成 batch=1、M=K=128 的小矩阵，算术强度骤降，进入 memory-bound 区间。若基准题集只含大 shape，模型学到的 tiling 策略在小 shape 上会因占用率不足而退化；反之亦然。这就是隐藏 shape 分布必须显式声明的物理原因，而不是统计洁癖。

四 · 隐藏 shape 与分布：留出集是唯一可信的泛化证据

内核生成基准的一个结构性风险是 shape 泄漏：若题面直接给出待测 shape，模型可以针对该 shape 硬编码 tile 大小、展开因子甚至 grid 配置，从而在固定 shape 上取得高 speedup 而在邻近 shape 上崩溃。给定事实写明“输入分布未给出：材料未说明任务描述的来源与难度分层”，因此 Kevin 是否采用隐藏 shape 无法确认。工程上应要求的口径是：题面只给算子语义与 dtype，评测时在留出 shape 集合上采样，并报告“同分布 shape”与“分布外 shape”两组 faster rate。前者衡量拟合，后者衡量泛化。

隐藏分布的处理还涉及正确性 oracle 的边界用例。以 reduction 为例，隐藏 shape 应包含非 2 的幂长度、含 NaN/Inf 的输入、以及极小的 N=1 情形；这些用例的通过率是判定内核是否真正通用的硬门槛。代价在于评测时间：每个隐藏 shape 都要跑一次编译加执行，若留出集有 $S$ 个 shape、题量 $N$，总执行次数为 $N \times S$，多轮 RL 下再乘以平均轮数 $\bar{T}$。给定事实未给出题量与轮数上限，因此这个乘积无法估算，但口径上必须声明 $S$ 与 $\bar{T}$，否则“隐藏 shape”只是口号。

  • 机制：题面剥离 shape，评测端按留出集注入；模型无法在生成时看到待测维度。
  • 代价：执行次数按 $N \times S \times \bar{T}$ 增长，墙钟时间与 GPU 占用同步上升。
  • 例子：同一 tiled matmul 内核在 4096 方阵上 speedup 显著，在 128 方阵上因占用率不足慢于基线；只报前者即构成选择性报告。
  • 核查：要求论文给出留出集的 shape 列表或采样分布，以及分布外 faster rate。

五 · 哪些数字不可比：一份负面清单

跨论文比较 kernel agent 的性能是本领域最常见的误用。以下情形在口径上不可比，遇到即应拒绝并列。第一，基线不同：以 cuBLAS 为分母的 speedup 与以朴素实现为分母的 speedup 不可比，前者衡量“接近厂商库的程度”，后者衡量“相对教学实现的改进”。第二，硬件不同：不同 GPU 架构的带宽与算力比不同，同一内核的 roofline 位置不同，speedup 不可迁移。第三，dtype 不同：fp32 与 bf16 的峰值算力差异会使 compute-bound 判定翻转。第四，计时口径不同：含数据传输的端到端时间与纯内核时间不可比。第五，题集不同：算子集合与难度分层不同，geomean 不可比。第六，正确性 oracle 不同：容差宽松的评测会放过数值不稳定但更快的实现。

给定事实明确写着“材料未给出任何通过率、加速比或性能数字，无法陈述实验结果”，因此 Kevin 的数字不在可比较之列——不是因为它差，而是因为口径未披露。工程判断应当是：在全文补齐之前，把 Kevin 的贡献定位为方法闭环（生成—编译—运行—再生成）与可验证奖励的设计，而非性能结论。这与前文已经处理的问题现场相衔接：单轮生成的一次通过率低，多轮反馈是结构性解法；但解法是否有效，取决于口径是否可核查。一个具体的不可比实例：论文 A 报告 geomean 1.8×（基线 cuBLAS，H100，bf16，纯内核计时），论文 B 报告 geomean 3.2×（基线 PyTorch eager，A100，fp32，含传输）；两者并列会得出 B 优于 A 的错误结论，而实际上 B 的分母更弱、硬件更旧、dtype 更不利于算力发挥。

$$\text{可比性} = \mathbb{1}[\text{base}] \cdot \mathbb{1}[\text{hw}] \cdot \mathbb{1}[\text{dtype}] \cdot \mathbb{1}[\text{timing}] \cdot \mathbb{1}[\text{task set}] \cdot \mathbb{1}[\text{oracle}]$$

把可比性写成六个指示变量的乘积是一个有用的工程习惯：任一为零，整条比较作废。这也解释了为什么本节的篇幅要留给“不可比”而非“结果”——在摘要级材料下，唯一能交付的严谨结论就是这份负面清单。

六 · 可核查的测量口径模板

落到可执行层面，本节给出一个测量口径模板，供在全文补齐后逐项核对 Kevin 的评测章节。模板分四组。环境组：GPU 型号与显存、CUDA 工具包版本、编译器版本、容器隔离方式、超时阈值。任务组：算子集合与题量、难度分层依据、题面是否含 shape、留出 shape 列表与采样分布、dtype 声明。执行组：编译失败是否计入分母、正确性 oracle 的参考实现与容差、计时方式（CUDA event 或 wall clock、是否含传输与 launch）、每轮反馈字段、轮数上限与平均轮数、每题 token 消耗。指标组：编译成功率、正确性通过率、端到端 faster rate、条件 faster rate、fast_1/fast_5、geomean、以及可选的 SOL 分布。

这四组字段中，执行组的“编译失败是否计入分母”最容易被忽略却影响最大。若编译失败被剔除，faster rate 会系统性高估；多轮 RL 恰恰以修复编译错误为卖点，剔除失败样本等于抹掉了方法的主要作用对象。给定事实指出材料未给出编译失败率与多轮后仍失败的残留比例，因此这一项在 Kevin 处为待核。另一个具体机制是反馈序列化的代价：每轮把编译器报错、运行结果与性能信号拼入下一轮提示，会线性增加上下文长度，进而增加推理 token 与显存占用；材料未给出反馈字段设计，故无法估算这部分开销。工程判断上，若反馈字段过长而轮数上限又高，token 成本可能抵消生成质量收益——这正是给定事实列出的失败模式之一，也是口径模板必须把 token 消耗单列的原因。

最后落到一个可操作的核查动作：在引用 Kevin 的任何性能主张之前，先在其全文中检索上述四组字段；若“基线”“dtype”“计时方式”“留出 shape”四项中有任一项缺失，则该主张只能作为定性方向引用，不得进入横向对比表。这个动作本身就是本部分要交付的工程判断——评测的可信度不来自数字的大小，而来自口径的完备性；在多轮 RL 场景下，口径缺失的代价被轮数与 token 成本进一步放大，使得“看起来更快”与“确实更快”之间的差距比单轮生成时更难分辨。
