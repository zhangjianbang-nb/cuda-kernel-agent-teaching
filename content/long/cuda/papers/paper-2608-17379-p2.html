一 · 失效模式：当"目标指令被执行"不等于"更快"

PTXBench 最值得工程团队警惕的一条结论，是它把"目标指令是否在运行时真正执行"与"性能是否具有竞争力"拆成了两个独立指标，而实测结果是二者并不绑定。论文明确写道：executing the target instructions does not necessarily translate into competitive performance。这不是一句修辞，而是一个可被观测的失效模式：候选 kernel 里确实出现了架构相关的 PTX 指令（比如面向 H100/B200 的特定 MMA 变体或异步拷贝路径），运行时检查通过，但端到端时延仍落后于 frontier library。原因在机制层面很清楚——单条指令的吞吐提升会被它周围的约束吃掉。一条高吞吐的 tensor core 指令要求操作数已经驻留在正确的寄存器布局与共享内存 bank 排布上，如果生成器为了"用上这条指令"而额外插入了 layout 转换、冗余的 shared memory staging 或同步屏障，那么节省下来的指令周期会被这些搬运开销抵消，甚至反向超出。

把这个失效模式写成可判定的形式，需要把"指令命中"与"性能命中"分开计分。设候选 $i$ 的目标指令命中为 $h_i\in\{0,1\}$，加速比为 $s_i=T_{\text{base},i}/T_{\text{cand},i}$，则论文给出的通过率口径是：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

工程上应当再补一个交叉表：$h_i=1$ 且 $s_i\ge\tau$ 的比例，与 $h_i=1$ 但 $s_i<\tau$ 的比例。后者就是"指令用对了但没变快"的样本量。这个量在 attention backward 上会显著放大，因为反向传播的算子链条更长、中间张量更多，任何一次多余的 materialization 都会把指令级收益吞掉。代价是显存的：为了维持目标指令所需的操作数布局，候选往往需要额外的 workspace 或更高的寄存器压力，occupancy 下降后时延反而变差。具体例子：一个 attention backward 候选把 softmax 梯度的重算路径写成两趟，第一趟用架构指令做矩阵乘、第二趟做归约，指令命中为真，但中间张量落回 global memory，带宽开销直接压过了计算节省。

二 · 难度断层：attention backward 是能力的分水岭

论文给出的第二个边界是难度分布的不均匀：success rates fall substantially on complex attention backward workloads。这句话的工程含义是，PTXBench 的分数不能当作一个标量能力值来用——GEMM 类负载与 attention 前向的通过率，与 attention backward 的通过率不在同一个量级上，把它们平均成一个数会系统性高估模型在真实训练栈里的可用性。机制上，backward 的难点不在单条指令，而在多算子协同：一个 fused backward 需要同时处理 $dQ$、$dK$、$dV$ 三条梯度路径，它们对 reduction 维度的选择不同，对 shared memory 的复用模式也不同，还要与 causal mask、softmax 的数值稳定性（减最大值、防溢出）耦合。生成器只要在其中一条路径上选错 reduction 轴，正确性检查就会失败，而这类错误不会因为"会写 PTX"而自动消失。

因此评测口径必须按负载族分层报告，而不是只报总分。可操作的做法是给每个族一个最低样本量与一个置信区间下界，只有当某族的下界超过阈值时才认为该族"可用"。代价是 token 与编译时间：attention backward 的候选通常更长、编译更慢，多轮修复时每一轮的编译—运行—profile 回灌都更贵，单条样本的评测成本远高于 GEMM。具体例子：同一模型在 GEMM 上能稳定产出通过正确性门的候选，但换到 attention backward，失败集中在梯度累加的精度与 mask 边界处理上——前者是 dtype 与累加顺序问题，后者是索引边界问题，两者都不是 PTX 指令选择能补救的。

三 · 迁移边界：H100/B200 上的结论不能外推

PTXBench 的评测面被明确限定在 H100 与 B200 两块 GPU、GEMM 与 attention 两类负载上。这构成一条硬边界：架构相关 PTX 的价值恰恰来自它对具体 SM 版本的依赖，因此跨架构迁移不是"打折"，而是"失效"。一条在 B200 上被证明能提升吞吐的指令序列，换到另一代 SM 上可能根本不被接受，或者被 ptxas 降级成等价但更慢的通用序列；更隐蔽的情况是它仍能编译、仍能执行，但操作数布局假设不再成立，性能回退。论文自身也把"跨硬件、跨 dtype、跨框架迁移未验证"列为局限。工程判断应当是：把 PTXBench 的分数视为"在该架构上、该负载族上、该基线口径下的条件能力"，而不是模型的通用 GPU 编程能力。

迁移风险的量化可以借助一个简单的敏感性比：设同一候选在架构 $A$ 与 $B$ 上的加速比为 $s_i^A$、$s_i^B$，则迁移损失为 $\Delta_i = s_i^A - s_i^B$，报告 $\max_i \Delta_i$ 比报告均值更有信息量，因为失效往往集中在少数"深度依赖特定指令"的样本上。代价体现在验证预算上：每换一代架构，正确性 oracle 与性能基线都要重建，profile 口径（NCU 的 metric 集、SASS 的反汇编对照）也要重跑，这部分成本不会被模型侧的微调摊薄。具体例子：一个依赖特定异步拷贝路径的候选，在新架构上编译通过、正确性通过，但因为该路径的延迟隐藏特性改变，原本被掩盖的 global memory 往返暴露出来，加速比从领先变为落后。

四 · 基线口径：加速比的分母决定结论的可信度

论文把 speedup over frontier libraries 作为核心指标之一，这使结论高度依赖分母的选取。可用事实里已经点明一条失败模式：基线若未开 TF32、未用最强库实现，加速比会被高估。机制上，GEMM 与 attention 的库实现会在 dtype 允许时走 TF32 或更高吞吐的 tensor core 路径，若基线停留在 FP32 的朴素路径，任何候选都能轻易"赢"，但这种赢在生产栈里不存在。因此读 PTXBench 的结果时，必须先确认三件事：基线是 PyTorch eager、torch.compile 还是论文指定的库实现；dtype 与是否启用 TF32；输入 shape 是否与生产分布一致。

与相邻工作的差别也在这里显出来。KernelBench 系基准把"能否写出高效 kernel"作为主问题，CUDA-L1/CUDA-L2 一类工作把对比强化学习与超越 cuBLAS 作为目标，Dr. Kernel 把 RL 的正确性做对作为重点，而 PTXBench 的独特角度是把"架构相关 PTX 的使用"本身变成可审计的对象——它不只问快不快，还问目标指令有没有真的跑起来。这个角度带来一个额外代价：审计需要运行时指令命中检查，这要求插桩或反汇编对照，单条样本的评测时延高于纯时延测量。具体例子：一个候选在未开 TF32 的基线下拿到漂亮加速比，但把基线换成开启 TF32 的库实现后加速比归零——这不是候选变差了，而是分母变了。

五 · 修复式训练的天花板：数据覆盖与教师质量

论文用监督微调适配 Qwen3.6-27B，并给出一个关键的定性判断：Repair-conditioned training improves several tasks, but generalization remains uneven; data coverage, balance, and the quality of the reasoning teacher matter in addition to dataset size。这句话划出了方法侧的边界：修复条件训练（把编译错误、正确性失败、性能不达标作为条件喂回）能提升若干任务，但不能保证跨任务族的一致泛化，且收益不随数据量单调增长——覆盖、平衡、教师推理质量三者与规模同等重要。

机制上，修复式样本的分布决定了模型学到的是"修这一类错"还是"学会诊断"。若训练集里 attention backward 的失败样本稀少，模型在该族上的修复能力就不会因为 GEMM 样本的堆积而提升；若教师给出的推理链只描述"改成这条指令"，而不描述"为什么当前布局不满足该指令的操作数约束"，模型学到的是模式匹配而非诊断能力，遇到新架构就会退化。代价是 token 与标注预算：高质量的推理教师样本比普通修复样本贵得多，而平衡采样又会稀释高频族的样本密度。具体例子：同一批修复数据在 GEMM 上带来稳定提升，但在 attention backward 上提升有限，原因不是数据量不足，而是该族的失败类型（精度、边界、多路径协同）在数据里没有被充分表征。这也解释了为什么"数据规模"不是唯一杠杆。

六 · 什么情况下不该用 PTXBench

把边界收拢成工程判断，有几类场景应当明确不用它，或者只把它当参考而非门禁。第一，目标是跨架构可移植的 kernel 生成：PTXBench 的分数建立在 H100/B200 的架构特性上，用它来挑选"通用最优"模型会引入架构偏置，此时应改用架构无关的基准或以 Triton 层为口径的评测。第二，目标是端到端训练栈收益：PTXBench 测的是单算子或算子族的加速比，shape 特化与隐藏输入分布会让离线分数在生产上崩塌，若没有端到端回归，单算子领先不能作为上线依据。第三，目标是正确性形式化保证：PTXBench 的正确性门是给定输入上的功能检查，不是形式验证，对数值边界、极端 shape、非对齐指针的覆盖有限，涉及金融或科学计算精度要求时应叠加形式化或区间分析。

第四，基线口径不可控的场景：若无法确认基线是否开启 TF32、是否使用最强库实现，加速比数字不可比，此时应先用统一基线重建分母再谈模型差异。第五，预算受限的快速筛选：PTXBench 的指令命中审计与 attention backward 样本的编译—profile 成本较高，若只是做粗筛，用更轻的 KernelBench 系基准先过滤，再用 PTXBench 做深度审计，是更合理的成本分配。最后一条工程判断落在机制上：PTXBench 的真正价值不是给出一个排名，而是把"指令命中—正确性—加速比"三者拆开，让每一次失败都能归因到具体环节；一旦把它的分数压缩成单一标量用于选型，这个归因能力就丢失了，而这恰恰是它在可信评测方向上不可替代的部分。

架构特定 PTX 的三重失效面：指令命中、加速幻觉与迁移断点

PTXBench 的评测口径里有一个容易被忽略的分离：它同时测“功能正确性”“选定的目标指令是否在运行时真的执行”和“相对前沿库的加速比”。这三者并不构成一条单调的因果链，恰恰是这条链的断裂处定义了该方案的适用边界。失效模式之一是指令命中但收益为零：模型生成的 kernel 里确实出现了目标架构的指令（例如面向 H100/B200 的特定 MMA 变体或异步拷贝路径），运行时校验通过，但端到端时延并未改善。原因在于指令级收益被周边的访存布局、寄存器压力或同步开销吃掉——一条指令被发射，不等于它处在 roofline 的拐点上。论文明确观察到“executing the target instructions does not necessarily translate into competitive performance”，这句话应当被读作一条工程判据：指令命中率是必要但不充分条件，不能作为优化成功的代理指标。评测时必须把“指令执行验证”与“加速比门”拆成两道独立的闸，否则会把大量命中却无收益的候选计入成功。

失效模式之二是复杂度断层，且断层位置高度可预测。论文报告 success rates 在复杂 attention backward 负载上大幅下降，而 GEMM 与 attention 前向相对可控。这提示能力边界不在“会不会写 PTX”，而在“能否在反向传播的多阶段数据流里维持正确的中间状态与同步语义”。反向算子通常包含多路归约、原子累加、跨 stage 的梯度拼接，任何一处 PTX 层的 fence 或 barrier 语义写错，都会在功能正确性上直接失败，而不是缓慢退化。因此把 PTXBench 的分数外推到生产时，第一件事是按算子族分层看：GEMM 类的高分不能为 attention backward 背书。系统代价在这里体现为验证成本的非对称性——反向算子的正确性 oracle 需要更细粒度的数值比对（多 dtype、多 shape、梯度累加顺序敏感），单个候选的验证时延与显存占用都高于前向，导致单位 token 的有效反馈密度下降，多轮搜索的迭代预算被快速消耗。

失效模式之三是基线口径与 shape 特化带来的加速幻觉。论文给出的评分形式为

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

其中 $T_{\text{base},i}$ 的取值直接决定 $s_i$ 的分母。若基线未开启 TF32、未使用论文指定的最强库实现，分母被系统性放大，加速比被高估；反之若候选针对基准 shape 做了硬编码特化，离线分数会漂亮，但隐藏输入分布一变就崩塌。这两类偏差在同一个 score 里不可区分，因此 PTXBench 的分数只在该论文给定的硬件（H100/B200）、基线与输入分布上成立，跨硬件、跨 dtype、跨框架的迁移未被验证。工程判断是：把 PTXBench 当作可审计的回归测试台而非性能排行榜——它的价值在于“能否稳定复现某条指令路径并给出可核验的正确性证据”，而不是“某模型是否比 cuBLAS 快”。

由此可以划出“不该用它”的几条线。其一，当目标是跨代际架构迁移时不该用它做主判据：PTXBench 绑定 H100/B200 的指令集与微架构特征，模型学到的可能是对特定 SM 版本的记忆而非可迁移的优化推理，论文自己也只做了 Qwen3.6-27B 的监督微调适配，且 repair-conditioned training 的泛化仍不均匀，数据覆盖、平衡与推理教师质量的影响不亚于数据规模。其二，当正确性 oracle 本身不可靠时不该用它：reward hacking 与 fallback 机制会让正确率虚高，若没有独立的数值容差与多输入采样，score 会被污染。其三，当团队需要的是端到端生产收益而非算子级峰值时，PTXBench 只能作为前置筛选——它不覆盖框架调度、显存分配与 kernel 间流水，算子级加速在真实负载里可能被 launch 开销与依赖串行吞掉。其四，当编译与验证预算紧张时，PTX 路线的单位候选成本显著高于 Triton 路线，若任务本身已被 torch.compile 覆盖到接近 roofline，投入 PTX 搜索的边际收益不足以抵消编译时延与多轮 profile 的 token 开销。这些边界不是对 PTXBench 的否定，而是把它定位为一个受控条件下的能力探针：它测的是模型在给定架构上能否稳定走通“生成—编译—指令验证—加速”这条链，而不是这条链在任意部署环境里的等价物。
