一 · 基准题集与三条实现路径的分层

Warpline 的评测负载是 35 个 kernel，横跨 Triton、CuTe DSL、CUDA C++ 三种实现路径。这个构成不是随手凑的样本量，而是刻意让「同一算子、三种语言层级」并存：Triton 走的是编译器自动调度，CuTe DSL 暴露 tile/layout 层，CUDA C++ 则允许手写 warp 级流水。对 agent 而言，这三条路径的可编辑面完全不同——Triton 改的是 block size 与 num_warps，CuTe 改的是 tiled copy 与 MMA atom 的组合，CUDA C++ 改的是寄存器分配与 `__syncthreads()` 的位置。Warpline 的证据链之所以要「只依赖 binary」，正是为了在这三种编辑面上给出同一口径的观测：无论 agent 改的是源码、IR 还是 PTX，最终都落到同一个 cubin 上，探针插入点由二进制分析决定，而不是由源语言语法决定。

这意味着基准的读法必须分层。把 35 个 kernel 的加速比直接取几何平均，会把「Triton 上 agent 只能调参」和「CUDA C++ 上 agent 能重写数据通路」这两类难度混为一谈。可核查的做法是按实现路径分桶报告：每个桶内给出该桶的基线（同语言的参考实现，而非跨语言最优实现），桶间不合并 geomean。论文摘要只给出 B200 上的总体开销数字，未给出分桶加速比，因此任何声称「Triton 桶加速 X 倍」的转述都属于越界。

另一个口径问题是基线选择。论文指定 PyTorch eager、torch.compile 与论文指定库实现三类基线。这里存在一个必须显式声明的开关：库实现是否启用 TF32、是否调用 cuBLAS 的 heuristic 模式、torch.compile 是否开了 max-autotune。若基线未开 TF32 而候选 kernel 用了 TF32 tensor core，加速比会被系统性高估——这不是 agent 的功劳，而是精度口径不一致。可核查的测量口径要求把 dtype 与 math mode 写进基线定义：fp32 严格模式、fp32 允许 TF32、bf16/fp16 三档必须分开报，跨档不可比。

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

上式的两个量必须绑定同一 dtype、同一 shape、同一 warmup 策略才有意义。$T_{\text{base}}$ 的测量若包含首次 JIT 编译或 cuBLAS heuristic 搜索，$T_{\text{agent}}$ 却已预热，则 speedup 里混进了编译时间差。代价就在这里：把编译时间计入时延会让 Triton 候选普遍吃亏（Triton 的 autotune 可能触发数十次编译），把它排除又会让「一次编译多次复用」的部署场景失真。工程判断是双列报告——稳态时延与首调用时延分开，前者用于 roofline 对比，后者用于端到端收益核算。

二 · 硬件锚点与 roofline 的可比边界

全部测量在 NVIDIA B200 上完成。这个锚点决定了 roofline 的上界：B200 的 HBM 带宽与 tensor core 峰值吞吐构成两个屋顶，任何 kernel 的 SOL（speed of light）分数都是相对这两个屋顶算的。问题在于，roofline 只对「计算密集或带宽密集二者居其一」的 kernel 有清晰含义；对于既受限于 shared memory 带宽、又受限于 occupancy 的 kernel（典型的 fused softmax、layernorm 类），算术强度落在屋顶交点附近，SOL 分数对 tile 大小极其敏感，跨 shape 不可比。

因此可核查的口径是把 SOL 分数与 shape 绑定报告，而不是给一个算子一个 SOL 数字。具体机制：对每个 (kernel, shape, dtype) 三元组，先算该 shape 下的最小必需访存量 $B_{\min}$ 与最小必需浮点运算量 $F_{\min}$，再算算术强度 $I=F_{\min}/B_{\min}$，与 B200 的屋顶交点强度 $I^*$ 比较，得出该点属于带宽界还是计算界。只有落在同一侧的样本，其 SOL 分数才可横向比较。

$$I=\frac{F_{\min}}{B_{\min}},\qquad \text{SOL}=\min\!\left(\frac{I}{I^*},\,1\right)\cdot\frac{T_{\text{ideal}}}{T_{\text{measured}}}$$

代价是测量成本：每个 shape 都要单独做 NCU 采集才能拿到实测带宽与吞吐，35 个 kernel 乘以多档 shape，profile 次数迅速膨胀。这正是 Warpline 要解决的痛点之一——硬件 profiler 报的是「每个单元多忙」，不是「每个 warp 的时间去哪了」，所以单靠 NCU 无法把 SOL 缺口归因到具体指令。Warpline 的二进制探针把 warp 级时间线对齐到同一时间轴，才让「SOL 差 30% 是因为某段 stall 在等 shared memory bank conflict」这类判断可落地。开销数字在这里是硬约束：中位 1.2% 的额外开销、中位 99.9% 的执行指令保持不变，意味着探针插入基本不扰动被测量的 kernel；对照的既有 tracer 中位开销显著更高，且需要手工放置探针并重新编译，而重编译本身会改变被测量的那个 kernel。

三 · 指标族：faster rate、geomean、fast_p 各自的失效面

KernelBench 系基准常用的指标族有四类，Warpline 的评测口径需要把它们分开定义，否则数字互相污染。faster rate 是「候选快于基线的样本占比」，它对离群值不敏感但对小样本抖动敏感；geomean 是加速比的几何平均，压缩了极端加速的影响但要求每个样本都有正的加速比定义；fast_p 是「加速比超过阈值 p 的样本占比」，直接对应部署决策；roofline/SOL 是绝对效率指标，与前三个相对指标不在一个坐标系。

指标定义失效面代价来源
faster rate占比 $\mathbb{1}[s>1]$1.01× 与 3× 同权，噪声可翻转需多次重复取中位，测量时延翻倍
geomean$\exp(\overline{\ln s})$一个 0.5× 的样本拖垮整体，掩盖长尾要求全样本可测，失败样本需单独计
fast_p占比 $\mathbb{1}[s\ge p]$阈值 p 的选择直接决定排名与部署收益挂钩，需端到端回归
SOL见上式跨 shape、跨算术强度侧不可比每点需 NCU 采集，profile 成本高

具体例子：若 agent 在 35 个 kernel 上产出 20 个 1.05× 与 5 个 2×，faster rate 为 25/35，geomean 被那 5 个 2× 拉高，fast_1.5 只有 5/35。三个数字讲的是三个不同的故事，任何一个单独引用都会误导。可核查口径要求同时报 faster rate、geomean 与至少一个 fast_p，并附失败样本数（编译失败、正确性不过、超时）作为分母修正。把失败样本从分母里剔除是常见的 reward hacking 通道：agent 学会只提交能编译的简单 shape，正确率虚高而覆盖率崩塌。

正确性门与性能门的绑定关系由 accept 式给出：pass 且 $s\ge 1$ 才算接受。这里的代价是正确性检查本身的时延——每个候选都要在给定输入上跑参考对比，若用 allclose 且容差按 dtype 设定，fp32 严格模式与 bf16 的容差不同，跨 dtype 混用会让「正确」的定义漂移。工程上必须把容差写进口径表，与 dtype 一一对应。

四 · 隐藏 shape 与输入分布：离线分数为何在生产上崩塌

基准题集给出的 shape 是可见的，生产负载的 shape 是隐藏的。agent 针对可见 shape 做特化——把 tile 大小、unroll 因子、甚至分支路径按具体维度硬编码——在离线基准上拿到高加速比，换一个 shape 就退化。这不是假设性风险，而是 shape 特化的结构性后果：一个为 $M=4096,N=4096,K=4096$ 调优的 GEMM，其 shared memory 分块在 $M=128$ 时 occupancy 会掉到个位数。

可核查的处理方式有三条，各有代价。其一，留出隐藏 shape 集：在题集内划分可见/隐藏两组，隐藏组只在最终评测时跑，agent 无法针对性调优。代价是隐藏组无法参与迭代反馈，agent 在隐藏组上的表现是零样本泛化，分数方差大。其二，shape 扰动：对每个可见 shape 施加维度抖动（如 $\pm 10\%$ 的 M/N/K），要求候选在扰动集上仍满足 $s\ge 1$。代价是评测样本数成倍增长，编译与测量时间线性膨胀。其三，分布声明：论文口径要求把输入分布写清楚——是均匀随机、还是带特定稀疏结构、还是真实负载采样。分布不同，同一个 kernel 的访存模式不同，带宽界与计算界的归属可能翻转。

$$s_{\text{robust}}=\min_{x\in\mathcal{D}_{\text{hidden}}} \frac{T_{\text{base}}(x)}{T_{\text{agent}}(x)}$$

用最坏情况加速比而非平均加速比作为接受准则，是把隐藏分布风险前置的手段。代价是它过于保守：一个在多数 shape 上 2×、在个别 shape 上 0.95× 的候选会被拒，而后者可能只是某个维度的边界效应。工程判断是分层接受——可见集用 geomean，隐藏集用 $s_{\text{robust}}\ge 1$ 作为硬门，两者都过才进部署候选池。

Warpline 在这个环节的角色是降低验证成本：因为它只需 binary 就能重建证据，agent 每改一版（无论改的是源码、IR 还是 PTX）都能自动拿到新的 warp 级时间线，无需人工放探针、无需重编译。这使得「在隐藏 shape 上重跑证据链」的边际成本降到接近零，从而让 shape 扰动策略在工程上可行——否则每扰动一次就要重新插桩重编译，验证预算根本撑不住。

五 · 数字锚点与不可比清单

论文给出的可引用数字集中在开销侧：B200 上 35 个 kernel，Warpline 的中位额外开销 1.2%，中位 99.9% 的执行指令保持不变；对照的既有 tracer 中位开销显著更高。另有 1.6、13.2、4.6、32.7 四个数字锚点，摘要级未给出其完整语境，转述时必须标注出处与量纲，不得把它们拼成一个「综合加速比」。这些数字回答的是「观测代价有多小」，不是「agent 优化效果有多好」——两者是不同的问题，混引即失真。

不可比清单需要显式列出。跨硬件不可比：B200 的屋顶参数与 A100/H100 不同，SOL 分数不能平移。跨 dtype 不可比：fp32 严格、fp32+TF32、bf16 三档的基线时延差数倍，speedup 不可混算。跨基线不可比：torch.compile 开不开 max-autotune、库实现用不用 heuristic，都会让 $T_{\text{base}}$ 漂移。跨 tracer 不可比：既有 tracer 需要手工探针加重编译，其开销数字与 Warpline 的 1.2% 不在同一测量协议下——前者测的是「插桩后的 kernel」，后者测的是「插桩后仍基本不变的 kernel」，被测量的对象本身就不同。

还有一个隐蔽的不可比点：Warpline 能追踪闭源 kernel，而既有 tracer 不能。这意味着 Warpline 的证据覆盖面包含库实现内部，而对照 tracer 的覆盖面只到用户代码边界。若用「证据覆盖率」做横向比较，必须声明分母是全部 kernel 还是仅开源 kernel，否则数字无意义。

六 · 可核查测量口径的最小清单

把上述讨论收敛成一份可复现的口径表，是这一部分要交付的工程物。最小清单包含：硬件型号与时钟状态（是否锁频）、dtype 与 math mode、基线三元组（eager / compile / 库）及其开关、warmup 与重复次数、时延统计量（中位还是均值）、shape 集划分（可见/隐藏/扰动）、正确性容差与 dtype 的对应、失败样本的计法、以及 tracer 开销的测量协议（是否重编译、探针是否手工放置）。任何一项缺失，报告的数字就不可复核。

具体机制上，时延测量必须区分稳态与首调用：稳态用 CUDA event 包裹多次迭代取中位，首调用单独计时以捕获 JIT 与 autotune 成本。正确性检查用参考实现逐元素对比，容差按 dtype 设定并在口径表里写死。tracer 开销的测量则要求同一 kernel 在「无探针」「Warpline 探针」「手工探针+重编译」三种状态下各测一遍，才能把 1.2% 与对照开销放在同一坐标系里。

代价核算：完整口径表跑一遍 35 个 kernel × 三档 dtype × 三档 shape 集 × 三种 tracer 状态，profile 与编译次数是组合爆炸的。工程上的折中是先用可见集筛掉明显失败的候选（编译不过、正确性不过），只对存活候选做全口径测量；这样把昂贵的 NCU 采集留给少数候选，而 Warpline 的零重编译特性让存活候选的证据重建几乎免费。最后落在一条判断上：评测口径的可信度不取决于指标多花哨，而取决于失败样本有没有被如实计入分母、基线开关有没有被写死、以及 tracer 开销与被测 kernel 是否在同一测量协议下——这三件事任何一件含糊，加速比就只是数字游戏。

二进制探针的边界：不可观测指令、开销口径与跨版本证据漂移

Warpline 的可行性边界由“二进制里还剩多少可插桩的自由度”决定。它在不重编译的前提下分析二进制、决定记录哪些事件并把探针写入二进制，因此在 B200 上对 Triton、CuTe DSL、CUDA C++ 共 35 个 kernel 取得中位 1.2% 开销、中位 99.9% 已执行指令保持不变；但这一口径本身是代价来源：被改写的那 0.1% 指令若落在内层循环的关键路径或访存指令上，单 warp 时间线的语义就会被探针自身扰动，agent 据此做出的“这里最慢”判断可能是插桩产物而非 kernel 性质。更硬的失效条件是闭源 kernel 与已剥离符号的 cubin：Warpline 能追踪闭源 kernel（现有 tracer 做不到），但事件选择依赖对二进制的静态分析，遇到内联展开后无稳定边界的 PTX 或经过 ptxas 重排的调度，探针只能落在粗粒度基本块上，时间归因分辨率随之退化。此时应把 trace 降级为“块级证据”，并在反馈里显式标注分辨率，避免 agent 把块级热点误读为指令级瓶颈。

测量口径必须把探针开销从加速比里剥出去，否则优化循环会奖励“更难被插桩”的写法。设基线时延 $$T_{\text{base}}$$ 与候选时延 $$T_{\text{agent}}$$，论文口径的接受判据是 $$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$；但带探针运行得到的 $$T_{\text{agent}}^{\text{probe}}$$ 含 1.2% 量级的中位开销，若直接用它与无探针基线相比，等于系统性惩罚被观测的候选。可核查做法是同一候选跑两遍：无探针版进性能门，带探针版只进证据链，两者共享同一输入与同一 warmup 次数。表中列出三类不可比情形。

情形为何不可比工程处置
基线未开 TF32 / 未用最强库分母被人为抬高，加速比虚高固定基线版本与编译开关，写入口径文件
shape 特化 + 隐藏输入分布离线分数在生产分布上崩塌报告多 shape 的 geomean 与最差 fast_p，而非单点最优
fallback 路径未计入正确率虚高、时延被低估把回退分支的执行时间计入 $$T_{\text{agent}}$$

跨版本证据漂移是这套方案特有的系统代价。Warpline 只需二进制即可为每个新版本重新生成证据，无论 agent 在源码、IR 还是 PTX 层编辑，这关闭了无人干预的优化环；但探针插入位置随二进制变化而变，两次迭代的 trace 若落在不同基本块上，agent 看到的“改善”可能只是观测点搬家。控制手段是把事件集合与探针锚点做成可复现的确定性映射，并在每轮反馈里附带锚点清单与指令改动比例（对照 99.9% 这一量级），使跨轮比较建立在同一观测面上。对隐藏 shape 与分布，论文摘要未给出全部 shape，因此离线分数只能在论文给定的硬件、基线与输入分布上成立；生产端应以端到端回归而非基准单点作为接受依据，并把 roofline 位置作为辅助判据——当候选已接近 SOL 时，继续压时延的收益会被探针开销与测量噪声吞掉。
