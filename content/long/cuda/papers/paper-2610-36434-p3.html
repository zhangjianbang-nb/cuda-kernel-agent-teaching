一 · 单轮提示：把“目标”压缩成一次可执行请求

JustGoal 的起点不是一套脚手架，而是一次单轮提示。输入只有两样东西：优化目标（例如“在给定 shape 上把该算子做到比基线更快，同时保持数值正确”）与约束（dtype、容差、允许使用的语言层、不得改变语义）。输出是一段完整的 kernel 源文件，外加一段自述的编译与测试计划。注意这里没有 kernel 知识库、没有历史候选池、没有预置 workflow——论文把“goal-only”定义为：通用 agent 只拿到目标与约束，评测回路由它自己搭。

这一步的代价主要落在 token 与上下文预算上。目标与约束本身很短，但 agent 为了自建评测回路，必须在同一轮里写出参考实现调用、输入生成、正确性断言和计时骨架，输出长度因此被拉长到数千 token 量级；相比“给一份模板再填空”的做法，单轮提示把设计负担全部压进了解码过程。具体机制上，提示里通常包含一个可执行契约：函数签名、输入张量的 shape/stride/dtype、允许的误差界、以及“不得调用被禁库”的硬约束。这个契约是后面所有门禁的锚点——没有它，正确性检查无从谈起。

一个具体例子：对一个归约类算子，单轮提示给出的约束是“输出与参考实现在 float32 下相对误差不超过给定容差、禁止使用框架内置的融合算子”。agent 于是必须自己决定线程块大小、是否用 warp shuffle、是否做两级归约，并在同一份输出里附带一段自测代码。若它选择直接调用库函数，编译能过、正确性能过，但违反约束，在评测阶段被直接判负——这正是 goal-only 基线要暴露的失败模式：约束必须可机械检查，否则“目标”会被最省力的路径劫持。

二 · 编译：把自然语言承诺变成可加载的二进制

第二步是编译。输入是上一步产出的源文件与编译命令（编译器、架构目标、优化级别），输出是二进制或编译错误。这一步的代价是编译时延与失败率：CUDA C++ 路径要走 nvcc 的前端与 ptxas，Triton 路径要走 JIT 与 LLVM 后端，CuTe 模板实例化会把编译时间推到分钟级。对 agent 而言，编译错误是最廉价也最高密度的反馈——它精确到行号与符号，不需要跑起来就能排除一整类候选。

机制上，编译阶段要做三件事：语法与类型检查、架构兼容性检查（目标 SM 是否支持所用指令，如特定精度的张量核心指令）、以及资源占用预估（寄存器数、共享内存量）。后者直接决定 occupancy，是后续性能门的第一道筛子。伪代码思路可以写成：

$$\text{compile}(s)\rightarrow \begin{cases}\text{bin}, & \text{if ok}\\ \text{err}(s), & \text{otherwise}\end{cases}\qquad \text{gate}_1=\mathbb{1}[\text{bin}\ \text{loadable}]$$

代价的具体形态：一次失败的编译可能只花几秒，但一次成功的模板重编译可能花掉数十秒到数分钟；若 agent 在同一轮里反复改写，编译时间会线性叠加，成为整条回路的主要时延来源之一。工程判断是：把编译失败当作免费信号，把编译成功当作付费信号——前者用来收缩搜索空间，后者才值得进入运行阶段。一个具体例子是 Triton 候选在 autotune 配置爆炸时编译时间远超运行时间，此时应优先裁剪配置空间而不是继续生成新候选。

三 · 运行与正确性门：先证明对，再谈快

第三步在给定输入上运行候选，输出是数值结果与运行状态（是否越界、是否超时、是否触发非法访存）。正确性门是硬门：任何数值不符的候选，其加速比一律不计。论文的接受判据写得很直白：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这里 pass 是正确性谓词，s 是加速比。注意这个判据把“正确”与“更快”绑成一个合取项，意味着一个 10 倍加速但错一个元素的候选得分为零。机制上，正确性检查要覆盖三类输入：随机稠密输入、边界 shape（如奇数长度、非对齐 stride）、以及退化输入（空张量、单元素）。代价是显存与时间：随机输入要占用与问题同规模的显存，边界用例要额外构造，若 agent 自建的评测回路只测一种 shape，就会出现“离线全过、生产崩塌”的典型失败。

一个具体例子：某候选在默认 shape 上通过，但在非 2 的幂长度上因归约树不完整而漏算尾部元素。这类错误在单 shape 测试里不可见，只有边界用例能捕获。工程上的代价判断是：正确性用例的构造成本远低于一次错误部署的代价，因此宁可让 agent 在回路里多跑几组 shape，也不要为了省几秒运行时间而削减用例。运行阶段还要记录资源占用（显存峰值、是否发生 spill），这些量不进入接受判据，但会进入后续 profile 的解释框架。

四 · 计时与统一基线：加速比的分母从哪来

第四步是计时。输入是候选与基线，输出是时延与加速比。基线由论文口径给定：PyTorch eager、torch.compile 与论文指定的库实现。这一步的代价是测量噪声与基线选择偏差：GPU 时延受时钟频率、缓存状态、并发流影响，单次测量不可信，通常要多次迭代取中位数并做 warmup。更关键的是分母——若基线未开 TF32、未用最强库实现，加速比会被系统性高估，这是论文自己点名的失败模式。

机制上，计时必须固定三件事：输入分布（shape、dtype、布局）、测量方法（事件计时而非墙钟）、以及是否包含数据传输。对 kernel 级基准，通常只计 kernel 执行时间，排除 host-device 拷贝；但生产端到端收益要看包含拷贝的总时延，两者不能混用。伪代码思路：先 warmup 若干次丢弃，再连续计时取分位数，最后用同一套 harness 跑基线与候选，保证分母与分子同源。一个具体例子：同一候选在“基线用 eager”时得到可观的加速比，换成“基线用库实现”后加速比收缩到接近 1——这正是论文在 B200 上报告 1.14x 到 2.34x 这类区间时必须要交代的口径问题。

这一步的性能代价是评测时间本身：每个候选要跑多轮计时，候选越多，评测开销越大。工程判断是把计时预算按候选的“存活概率”分配——通过正确性门的候选才值得做精细计时，未通过的只做一次快速探测。

五 · 反馈回灌：agent 如何用结果改写下一轮

第五步是把编译错误、正确性失败、计时结果回灌给 agent，形成下一轮候选。输入是结构化的反馈记录，输出是改写后的源文件或放弃信号。JustGoal 的特殊之处在于：这个回路是 agent 自己搭的，而不是外部框架预置的。也就是说，agent 要自己决定测什么、怎么测、以及从结果里读什么。代价是 token 与轮次：每一轮回灌都要把结果序列化进上下文，长错误日志会迅速吃满窗口；轮次越多，累计 token 成本越高。

机制上，有效的回灌要把非结构化输出压成可操作的信号：编译错误映射到具体行与符号，正确性失败映射到首个不符的索引与误差量级，计时结果映射到相对基线的比值与资源瓶颈。一个具体例子：候选因寄存器溢出导致 occupancy 过低，profile 显示 occupancy 受限，agent 据此把线程块调小或改用共享内存分块——这类改写只有在反馈里带上资源占用数字时才可能发生。若反馈只有“慢了”，agent 只能盲目重写，轮次成本被浪费。

这里的工程判断是：回灌的信息密度决定搜索效率。把一次运行的完整日志塞进上下文，代价是 token；把日志压成“失败类别 + 关键数值”，代价是可能丢失细节。论文的 goal-only 设定把这一权衡交给 agent 自己，因此它的表现同时也是对“通用模型能否自建有效反馈压缩”的一次检验。

六 · 验证门与同模型对照：为什么“专用机械”必须自证

最后一步是验证与对照。输入是候选的接受判据结果与同模型、同范围的对照实验，输出是“是否值得保留这套专用机械”的判断。论文给出的对照锚点是：在 Fable 5.1 上做单 shape 的同模型比较时，KDA-0.5 harness 达到 JustGoal 性能的 0.95x；而单机制消融显示领域知识与预置流程没有带来一致收益。这两个事实把问题从“专用脚手架是否有效”改写成“专用脚手架相对 goal-only 基线的增益是否稳定超过噪声”。

机制上，同模型对照要求三件事对齐：同一个基础模型、同一批 shape、同一套计时与正确性口径。任何一项不对齐，比较就失效——比如对照用了更多轮次、更大 token 预算，或换了更强的基线库，增益就会被归因错误。代价是实验成本：每个算子都要跑两套回路，评测时间翻倍；若还要做跨硬件、跨 dtype 的迁移验证，成本进一步上升。论文明确把结论限定在给定硬件、基线与输入分布上，跨硬件与跨框架迁移未验证，这是读者在使用其数字时必须带上的边界。

一个具体例子：某专用 agent 在单 shape 上比 goal-only 快，但把 shape 换成非对齐布局后优势消失，说明其增益来自对特定 shape 的过拟合而非通用机制。工程判断因此落在论文那句结论上：专用机械应当由相对同模型、同范围 goal-only 基线的清晰增益来证明其存在，并且在基础模型换代时重新评估——因为 goal-only 基线的能力随模型变强而抬升，昨天的增益今天可能归零。这也是 JustGoal 作为“基线”而非“系统”的真正用途：它给所有专用脚手架提供了一个必须跨过的、会随模型升级而移动的门槛。

目标即规格：单轮提示在什么条件下失效

JustGoal 的“单轮提示”并不是把优化目标丢给模型就结束，它实际承担的是规格生成：把“更快”翻译成可编译、可测的接口契约。输入只有优化目标与约束（算子语义、dtype、shape 范围、不得调用某库），输出是一份候选 kernel 源码加自检脚本。代价落在 token 与编译时间上：模型必须在一次上下文里同时完成算法选择、tiling 决策、边界处理与评测脚本编写，任何一处遗漏都会让后续编译阶段直接失败，而不是给出一个“慢但正确”的候选。失效条件很具体——当约束里缺少显式 shape 集合时，模型倾向按单一 shape 特化，离线测得的加速比在隐藏输入分布上崩塌；当约束未声明数值容差，正确性门只能退化为全等比较，fp16/bf16 累加顺序差异会把正确候选判死。因此单轮提示的边界不在“模型够不够强”，而在约束文本是否足以充当规格。

把一次生成—编译—运行—评测写成状态机，可以看到单轮提示只覆盖第一个转移：

$$\text{accept}=\mathbb{1}\big[\text{pass}\land \text{speedup}\ge 1\big],\qquad \text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}}$$

其中 pass 由正确性 oracle 给出，T 用统一基线测量。单轮提示的输出若未通过编译，代价是整轮 token 白费且无梯度信号；若通过编译但 pass 为假，代价是一次运行与一次回退；若 pass 为真而 speedup 小于 1，则候选被丢弃但保留了“该方向不可行”的信息。这三种代价的量级不同，而单轮提示无法区分它们——它没有把编译错误、运行错误、数值错误分流成不同的反馈通道，于是模型在下一轮只能看到“失败”这个笼统标签。

脚手架自建评测环的系统代价

JustGoal 的关键设计是让通用 agent 自建评测环，而不是继承领域知识库或预定义搜索工作流。输入是目标与约束，输出是一套“生成—编译—运行—打分”的脚本；代价是脚手架本身的正确性风险被转移给了模型：如果模型写出的计时脚本没有做 warmup、没有固定 clock、没有隔离多流，那么它测到的 T_agent 会系统性偏低，speedup 被高估。这类 reward hacking 不会触发正确性门，因为 kernel 本身是对的，错的是测量。工程判断上，自建评测环必须与候选 kernel 分开审计——评测脚本的 diff 要独立于 kernel 的 diff 被审阅，否则“加速”可能只是计时器变快了。

阶段输入输出主要代价
生成目标 + 约束文本候选源码 + 自检脚本token；上下文长度决定可表达的 tiling 复杂度
编译候选源码可执行体或错误编译时间；模板/PTX 展开失败即整轮作废
运行给定输入分布输出张量 + 时延显存峰值；shape 特化导致越界或 fallback
评测输出 + 基线时延pass、speedup基线口径不一致则分数不可比

表中“运行”一栏的显存代价常被低估：自建评测环若按最大 shape 分配输出缓冲，会在小 shape 上引入与 kernel 无关的分配开销，使 speedup 被压低；反之若按最小 shape 分配，大 shape 上会触发越界或静默截断。这两种偏差都不体现在正确性门上，只体现在分数里。论文在 B200 上报告 8/10 算子超过开源库、几何平均 1.14x 至 2.34x，这一口径成立的前提正是评测环与基线测量在同一脚本内闭合；一旦把评测环拆到外部框架，跨框架的同步与流语义差异会直接污染 T_base 与 T_agent 的比值。

同模型对照暴露的边界

论文给出的受控对照是判断这套方案边界的最硬证据：在 Fable 5.1、单 shape、同模型条件下，KDA-0.5 脚手架只达到 JustGoal 的 0.95x，而单机制消融显示领域知识与预定义流程没有带来一致收益。这说明专用机械的价值必须用同模型、同范围的 goal-only 基线来证明，否则加速比里混入了模型差异。对工程读者，这条结论的直接含义是：当基础模型换代时，任何领域知识库或搜索工作流的增益都要重新测量，因为“知识”可能只是弥补了旧模型的规格理解能力。失效条件因此写成一条判据——若某脚手架在 goal-only 基线上无法稳定超过 1.0x，它的编译时间、维护成本与 token 开销就是纯负债。

把这条判据落到一次具体流程上：读取参考实现与基准口径，生成候选，编译后做正确性检查，用统一基线测时延与加速比，按反馈保留或回退。回退的代价不是零——它消耗一轮 token 且不产生可复用产物；而保留一个仅在小 shape 上快的候选，会把 shape 特化风险带入生产。论文在 9 个有可比结果的算子上于 5 个超过公开专用 agent kernel，这一比例本身就是边界的刻度：goal-only 能赢的地方集中在规格清晰、评测环可自闭合的算子；一旦算子需要跨 kernel 融合或依赖库级调度，缺少领域知识的代价才会显现。最后落在工程机制上：JustGoal 的可信度不来自“通用 agent 更强”，而来自评测环与候选同源、基线口径闭合、同模型对照可复现这三条同时成立；任一条断裂，1.14x 至 2.34x 的区间就不再是可迁移的结论。
