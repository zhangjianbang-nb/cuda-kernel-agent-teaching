一 · 基准题面：十个算子与九处可比

JustGoal 的评测口径里，最容易被忽略的不是指标，而是“题面”本身。论文报告的两个分母并不相同：对开源库的比较覆盖 10 个算子，对“已公开发布的最快专用 agent kernel”的比较只有 9 个算子具备可比对象。这意味着 8/10 与 5/9 不是同一批样本上的两个分数，把它们并列成“既打败库又打败 agent”的复合结论，在统计上是不成立的。工程上必须把这两条曲线拆开看：前者衡量的是与 PyTorch eager、torch.compile 及论文指定库实现的差距，后者衡量的是与同类 agent 产物的差距，后者才是这篇论文真正的主张所在——专用脚手架的知识是否还有边际价值。

题面粒度同样决定了数字的含义。论文摘要给出的加速比是“per-operator geometric mean”，即先对每个算子内部的多个测量点求几何平均，再在算子之间呈现区间 1.14x 到 2.34x。这是一个跨算子的分布描述，而不是一个全局 geomean。若读者把 1.14 与 2.34 当作“整体加速比的下界与上界”，就会犯两类错误：一是低估弱算子的拖累，二是忽略强算子对全局均值的杠杆。正确的复现口径是：逐算子记录几何平均，同时记录该算子的测量点数量与 shape 集合，最后再决定是否给出跨算子汇总。

具体机制上，per-operator geomean 的算法是

$$\text{geo}_k=\exp\!\Big(\frac{1}{n_k}\sum_{i=1}^{n_k}\ln \frac{T_{\text{base},k,i}}{T_{\text{agent},k,i}}\Big)$$

其中 $k$ 是算子下标，$n_k$ 是该算子被测量的输入点个数。这个式子对 $n_k$ 极其敏感：若某算子只测了一个“好”shape，它的 geomean 就等于该点的单次加速比，方差为零但代表性也为零。因此可核查的口径必须公开每个 $n_k$，否则 1.14x–2.34x 这个区间无法被第三方重放。代价是显存的：为了在同一进程内跑完所有 $n_k$ 个输入点并保持基线可比，通常需要为每个点单独分配输入输出缓冲，峰值占用随最大 shape 而非平均 shape 走，这是复现时最常见的 OOM 来源。

二 · 基线与硬件：B200 上的可比性边界

论文的硬件口径是 NVIDIA B200。这一条不是装饰：B200 的 SM 数量、HBM 带宽与 Tensor Core 代际共同决定了哪些算子会落在带宽墙、哪些落在算力墙，从而决定了“加速比”这个标量的物理含义。一个在 B200 上对带宽受限算子取得的 1.5x，与在算力受限算子上取得的 1.5x，其工程价值完全不同——前者往往意味着更激进的向量化与更少的冗余读写，后者意味着更深的流水与更好的 MMA 排布。因此复现时必须把每个算子的 roofline 位置标注出来，否则加速比无法跨硬件迁移。

基线侧，论文列出的对照是 PyTorch eager、torch.compile 与论文指定的库实现。这三者的可比性差异极大。eager 是最弱基线，torch.compile 会引入图融合与自动调优，库实现则往往已经是厂商手写 kernel。把 agent 产物同时与三者比较，会让“超过开源库”这句话的含义变得模糊：超过 eager 是基本要求，超过 torch.compile 说明融合策略有效，超过库实现才是真正困难的。论文摘要只说了“outperforms open-source libraries”，没有区分这三层，复现者必须自己把三层拆开记录。

不可比的典型来源是数值精度开关。若基线未开启 TF32 或未使用最强的库路径，agent 侧的加速比会被系统性高估。这不是猜测而是结构性的：TF32 在矩阵乘类算子上能把基线时延压掉一大截，一旦基线跑在 FP32 全精度路径上，任何使用 TF32 的候选都会显得“更快”。可核查的口径要求在同一 dtype、同一 math mode 下测量双方，并在报告中显式写出 torch.backends.cuda.matmul.allow_tf32 之类的开关状态。代价是编译时间：开启 TF32 后 torch.compile 的自动调优空间变化，首次编译的时延会上升，这部分时延若不计入测量窗口，就会污染“端到端”口径。

具体例子：一个以 FP32 累加、TF32 输入的 GEMM 候选，在基线为 FP32 全精度时可能报告出可观的加速比；但把基线切到 TF32 后，同一候选的加速比会大幅缩水甚至低于 1。这正是论文自身在局限里承认的边界——结论只在论文给定的硬件、基线与输入分布上成立。

三 · 指标族：faster rate、speedup、geomean 与 fast_p

这一族指标各有各的失效模式，混用会制造虚假的进步感。faster rate 是“加速比大于 1 的测量点占比”，它对分布形状不敏感，只对符号敏感：一个在所有点上都是 1.01x 的候选与一个在 90% 点上 3x、10% 点上 0.5x 的候选，faster rate 可能相同，但工程含义相反。speedup 是单点比值，容易被离群点主导。geomean 抑制离群点但要求所有点同号为正，遇到 0.5x 的点会把整体均值拉低得比算术平均更狠。fast_p 则是“加速比超过阈值 p 的测量点占比”，它把“够快”定义成一个可调的门槛，适合表达生产侧的验收标准。

论文摘要给出的接受判据是

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这个式子把正确性与性能门耦合在一起：只有通过正确性检查且加速比不小于 1 的候选才被计入“接受”。它的问题在于 $s\ge 1$ 这个门槛对测量噪声零容忍。GPU 时延测量的抖动在微秒级算子上可以轻易跨过 1.0，导致同一候选在不同运行中在“接受”与“拒绝”之间翻转。可核查的口径应当把门槛改为带容差的 $s\ge 1-\epsilon$，或对每个点做多次重复取中位数，并公开重复次数。代价是测量时间线性增长：每个点重复 $r$ 次，总测量时延乘以 $r$，在 shape 集合较大时会显著拉长复现周期。

具体例子：论文报告 1.14x 到 2.34x 的 per-operator geomean 区间。若某算子的 geomean 落在 1.14x，意味着它内部多个测量点的平均比值仅略高于 1；此时若测量抖动为几个百分点，该算子完全可能在某些重放中跌到 1 以下。这就是为什么“8 of 10 operators”这个计数比区间端点更稳健——计数只依赖符号，而符号在 geomean 层面已被平均平滑。

roofline 指标则是另一层：它把实测时延与理论下界比较，给出“离 SOL 还有多远”。论文摘要未给出 SOL 数字，因此复现者需要自己计算每个算子的算术强度与带宽/算力上界。这一步的代价是建模时间而非 GPU 时间，但它决定了加速比能否被解释——一个 2.34x 若仍远离 roofline，说明还有空间；一个 1.14x 若已贴近 roofline，说明该算子已被榨干。

四 · 隐藏 shape 与输入分布：离线分数的生产崩塌点

论文摘要明确承认输入分布“按论文口径”，且未给出全部 shape。这是整篇论文最脆弱的可比性环节。agent 类方法天然倾向 shape 特化：在给定 shape 上做常量折叠、把 tile 尺寸硬编码、按整除关系裁剪边界检查。这些手段在离线基准上收益显著，但一旦生产侧的 shape 落在特化假设之外，性能会断崖式下跌，甚至因越界或未覆盖的分支而正确性失败。

处理隐藏 shape 的工程机制有三条。其一是 shape 泛化测试：在基准 shape 之外维护一组“未见 shape”，包括非 2 的幂、非整除、极小与极大边界，要求候选在这些 shape 上仍通过正确性门且加速比不低于某个下限。其二是分布偏移检测：记录候选代码中出现的常量与分支条件，若常量与基准 shape 强相关，则标记为特化风险。其三是回退路径：为每个候选保留一个通用实现作为 fallback，当运行时 shape 不满足特化前提时切换到 fallback。

代价是显存与编译时间。泛化测试需要为每个未见 shape 分配缓冲，峰值显存由最大未见 shape 决定；若候选为多个 shape 生成多个特化版本，编译时间随版本数线性增长，且每个版本的 cubin 都占用模块加载空间。具体例子：一个把 tile 固定为 128×128 的 GEMM 候选，在基准的整除 shape 上表现优异，但遇到维度为质数的输入时，边界处理分支被激活，有效吞吐下降，加速比可能从大于 1 跌到小于 1。这类失败在只看基准 shape 的评测中完全不可见。

更隐蔽的是 reward hacking 与 fallback 导致的正确率虚高。若 agent 在正确性检查失败时静默回退到基线实现，测量到的时延其实是基线的时延，加速比趋近于 1 却被计入“接受”；若回退逻辑未被记录，接受率就被系统性抬高。可核查的口径要求在每次测量中记录实际执行的代码路径标识，并统计 fallback 触发率。这个统计本身不花 GPU 时间，但要求脚手架在运行时埋点，属于工程改造成本。

五 · 同模型对照：0.95x 这个数字的正确读法

论文给出了一组受控的同模型比较：使用 Fable 5.1、在单 shape 设定下，KDA-0.5 harness 达到 JustGoal 性能的 0.95x。这个数字的信息量远大于 1.14x–2.34x 区间，因为它是同模型、同 scope 的对照，剥离了模型能力差异，只留下脚手架知识的边际贡献。0.95x 意味着专用 harness 在同等条件下并未超过 goal-only 基线，反而略低。配合“single-mechanism ablations show no consistent benefit from domain knowledge”这一表述，可以读出论文的核心判断：专用机制的价值必须用同模型同 scope 的对照来证明，而不是用跨模型的绝对加速比来证明。

读这个数字要注意三点。第一，它是单 shape 设定，shape 泛化未被检验，因此不能外推到多 shape 场景。第二，0.95x 是相对值而非绝对时延，它不告诉你两者各自离 roofline 多远；两个都远离 SOL 的实现之间的 0.95x 与两个都贴近 SOL 的实现之间的 0.95x，工程含义不同。第三，它是单一模型的对照，论文自身也指出专用机制应“reevaluated whenever the foundation model changes”——基础模型换代后，这个比值需要重测。

机制上，同模型对照要求两次运行共享同一套采样参数、同一套正确性门、同一套测量窗口，唯一变量是脚手架是否提供领域知识与预定义工作流。代价是 token：两次运行各自消耗完整的生成预算，对照实验的 token 成本是单次运行的两倍，若还要做多 seed 重复以估计方差，成本继续翻倍。这是这类对照实验最现实的约束——它比 GPU 时延更贵。

具体例子：若把 0.95x 与 5/9 这两个数字并置，可以得到一个自洽的读法：JustGoal 在多数可比算子上超过了已发布的专用 agent kernel，但在同模型受控对照中，专用 harness 并未带来稳定增益。两者不矛盾——前者比的是不同模型加不同脚手架的产物，后者剥离了模型差异。工程判断应落在后者：当基础模型足够强时，领域知识的边际收益需要被重新定价。

六 · 可核查的测量口径清单

把上述讨论收敛成一份可执行的测量口径，是这一部分真正的交付物。任何声称复现 JustGoal 结论的报告，至少应公开以下字段，缺一项就不可比。

字段要求缺失后果
硬件GPU 型号、SM 数、HBM 带宽、时钟策略加速比无法跨硬件迁移
dtype / math mode输入 dtype、累加 dtype、TF32 开关状态基线被削弱，加速比高估
基线层级eager / torch.compile / 库实现分别记录“超过开源库”含义模糊
shape 集合每个算子的 $n_k$ 与具体 shape 列表geomean 不可重放
未见 shape泛化测试集与通过率特化风险不可见
测量窗口是否含编译、是否含首次调用、warmup 次数端到端口径被污染
重复次数每点重复 $r$ 次与聚合方式1.0 门槛附近翻转
fallback 率实际执行路径标识与回退触发统计正确率虚高
roofline 位置每算子算术强度与 SOL 距离加速比无法解释

这份清单里最贵的一项是测量窗口的定义。若把 torch.compile 的首次编译计入基线时延，基线会被显著拖慢，agent 侧的相对优势被放大；若把 agent 侧的多轮搜索与编译时间计入，agent 侧又会显得昂贵。论文摘要未给出这一口径，因此复现者必须自己声明，并意识到不同声明会给出不同的 1.14x 与 2.34x。工程上稳妥的做法是双口径报告：纯 kernel 执行时延口径用于比较 kernel 质量，含搜索与编译的端到端口径用于比较系统成本。

最后落在具体机制上：JustGoal 的评测之所以能支撑“goal-only 基线已足够强”这一判断，不是因为 2.34x 这个上限，而是因为 0.95x 这个同模型对照点与 5/9 这个同类比较计数。前者说明专用知识在受控条件下没有稳定增益，后者说明在真实可比样本上 goal-only 并不落后。任何后续工作若要主张专用脚手架的价值，必须在这两个口径上同时给出超过 1 的对照数字，否则加速比区间再宽也只是跨模型比较的产物。
