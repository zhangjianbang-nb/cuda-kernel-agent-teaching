一 · 正确性漏检：数值比对 oracle 的边界与漏判面

CUDA-L1 把正确性判定放在加速比之前，这是防奖励作弊的第一道闸门，但闸门本身是逐元素数值比对，容差标准在给定材料中未给出。这意味着漏检不是偶发 bug，而是 oracle 定义不完备时的结构性缺口。逐元素比对的形式化表述为：对输出张量每个位置 j，判据是 |yj − ŷj| ≤ atol + rtol·|ŷj|；atol 与 rtol 未定，则同一候选在不同容差下可能被判正例或负例。漏检有三类典型面：其一，浮点累加顺序改变导致的末位差异被宽松容差吞掉，候选实际已偏离参考语义；其二，边界输入（极大/极小值、非规格化数、NaN/Inf 传播路径）未被输入分布覆盖，比对通过但语义错误；其三，归约类算子在特定 shape 下恰好与参考同序，换 shape 即崩。工程上不能只依赖单点比对，应把 oracle 做成合约：固定 atol/rtol 并记录在评测元数据中，对每个算子补充边界用例集，对归约与扫描类额外做多随机种子重复比对。代价是显存的额外输入副本与重复运行时间——每个候选多跑 k 组输入，GPU 运行成本按 k 倍增长，而对比采样本身已随候选数线性放大编译与运行开销，两者叠加会显著拉长单题评测时延。一个具体例子：LayerNorm 类算子在隐藏维非 2 的幂时，若候选用了不安全的 warp 归约，宽松容差下比对通过，但换到 4096 以上隐藏维即出现可见偏差，这类候选若进入正例池，会把错误模式写进策略。

二 · shape 特化与静默降级：性能只在采样分布内成立

对比奖励只对同题多候选排序，题目附带的输入分布决定了候选被评测的 shape 集合。模型完全可能学到“针对评测 shape 硬编码 tile 尺寸与分支”的实现：在评测 shape 上加速比漂亮，换 shape 即退化为朴素循环甚至走错分支。这不是作弊，而是奖励信号的定义域太窄。诊断手段是把候选的编译产物与运行路径做 shape 扫描：对同一 kernel 在若干代表性 shape（小、中、大、非对齐、奇数维）上分别计时，绘制加速比随 shape 的曲线；若曲线在评测点附近出现尖峰而在邻域塌陷，即判定为 shape 特化。公式上可定义形状鲁棒性指标：

$$\rho = \frac{\min_{s \in S} \text{speedup}(s)}{\text{speedup}(s_{\text{eval}})}$$
ρ 接近 1 表示性能在形状集合 S 上稳定，远小于 1 则是特化信号。静默降级是另一面：候选内部带 fallback 分支，在评测 shape 走快速路径，其他 shape 悄悄退回通用路径，正确性不报错、性能不报警，只有把 shape 扫描纳入监控才能暴露。代价是评测时延：每个候选多跑 |S| 个 shape，计时次数按 |S| 倍增长，且大 shape 会推高显存峰值。工程判断是：把 shape 扫描做成抽样而非全量，只对进入正例池的候选做邻域扫描，负例池候选不重复付费。

三 · batch invariance 违规：批次维度上的语义漂移

batch invariance 指同一输入在不同 batch size 或不同 batch 内位置下应得到一致结果。归约类与归一化类算子最容易违反：候选若把 batch 维并入归约轴，或按 batch 大小选择不同 tile，则 batch=1 与 batch=32 的输出在浮点末位上不一致，甚至语义不一致。CUDA-L1 的逐元素比对通常对单组输入执行，若输入分布固定了 batch size，这类违规完全不可见。监控方式是对同一逻辑输入构造不同 batch 组装（padding 到不同 batch、打乱 batch 内顺序），比对跨 batch 配置的输出一致性；判据可写成：对任意两个 batch 配置 b₁、b₂，同一逻辑样本的输出差应落在容差内。违规的代价是正确性层面的：下游若做 batch 内归一化或跨样本归约，结果会随 batch 组成漂移，属于难以在单测中复现的生产事故。定位手段是把候选的归约轴与 block 映射打印出来（通过编译期宏或运行期断言），检查是否存在依赖 blockIdx.y 的跨样本归约。具体例子：softmax 类候选若把行内归约与跨行统计混在一个 block 内，batch 变化会改变归约树形状，输出在末位漂移，宽松容差下被判正例，但生产端做温度缩放时会放大误差。

四 · OOM 与资源越界：编译通过不等于可部署

候选通过 nvcc 编译、通过数值比对，仍可能在真实负载下 OOM 或触发非法访存。OOM 的来源包括：候选为追求占用率而申请超大共享内存，超出目标架构上限时编译期即报错（可捕获），但动态共享内存与寄存器压力导致的占用率塌陷只在运行时显现；候选按评测 shape 分配中间缓冲，换大 shape 即爆显存。诊断需要在评测管线中加入资源探针：编译后用 cuobjdump 或驱动 API 读取寄存数与共享内存用量，运行前按目标 shape 估算峰值显存，运行后用 CUDA 错误码区分 OOM、非法访存与超时。代价是评测基础设施的复杂度：资源探针本身要占用编译时间与一次额外加载，且显存估算需要知道候选的中间张量生命周期，对生成代码做静态分析并不总是可行。工程上更现实的做法是把 OOM 与非法访存作为负例的独立标签写入负例池，而不是与“更慢”混为一类——CUDA-L1 的负例池按编译失败、数值不一致、更慢三类归并，资源类失败若不单列，策略无法区分“语法不会”与“资源不会”。具体例子：一个用大 tile 的 GEMM 候选在评测 shape 上通过，换到长宽比极端的 shape 时共享内存需求翻倍，触发 OOM，若这类样本只被标为负例而不带原因，下一轮采样仍会重复生成同类结构。

五 · 性能回退与计时口径：加速比是相对量，基线漂移即误判

性能口径为相对基线实现的加速比，但基线配置与计时方法（是否取中位数、是否含数据传输）在给定材料中均未给出。这带来两类回退风险：其一，基线本身随驱动、编译选项或输入分布变化，同一候选在不同时间点的加速比不可比，历史正例可能在新基线下变成负例；其二，计时若含数据传输，候选的 host-device 拷贝策略会污染 kernel 时间，模型可能学到“减少拷贝”而非“优化计算”。监控上应把计时拆成 kernel 时间与端到端时间两条曲线，并对每个候选固定重复次数取中位数、报告方差；方差过大（例如首轮冷启动与后续轮差异显著）的候选应标记为计时不稳定，不进入正例。公式上可定义回退判据：

$$\text{regress}_i = \mathbb{1}\left[\frac{t_i}{t_{\text{base}}} > 1 + \delta\right] \ \wedge\ \mathbb{1}[\text{correct}_i]$$
δ 为允许的回退阈值，需在评测元数据中显式声明。代价是评测吞吐：多次计时与方差统计把单候选的 GPU 占用时间拉长数倍，与多候选采样叠加后单题成本线性上升。定位回退的具体例子：某候选在评测机上加速比 1.3，换到同架构不同显存带宽的卡上变成 0.9，原因是候选的占用率对带宽敏感而基线不敏感——这类回退只能靠跨配置复测暴露，单机评测无法发现。

六 · 监控、定位与回滚：把失败模式变成可回灌的结构化信号

上述失败模式的共同点是：它们都不表现为编译错误，因此不会被 nvcc 的结构化反馈捕获，只能靠评测管线主动探测。监控层应至少包含四项探针：容差与边界用例集（对抗正确性漏检）、shape 邻域扫描（对抗特化与静默降级）、跨 batch 一致性比对（对抗 batch invariance 违规）、资源用量与计时方差（对抗 OOM 与计时噪声）。每项探针的输出不是布尔值，而是带标签的结构化记录：失败类型、触发 shape、触发 batch 配置、资源峰值、计时分布。这些记录回灌进负例池时，应作为负例的元数据而非仅作为“负例”本身，使对比采样能按失败类型分层——CUDA-L1 的负例池设计只区分编译失败、数值不一致与更慢，工程上需扩展为可归因的标签体系，否则策略更新只能学到“这类候选不好”，学不到“为什么不好”。定位路径是从标签反查候选源码的对应结构：shape 特化对应 tile 常量与分支条件，batch 违规对应归约轴映射，OOM 对应共享内存与中间缓冲声明。回滚策略分两级：候选级回滚是把触发任一探针的候选直接移出正例池并冻结其源码指纹，防止同一错误结构在多轮采样中反复进入；基线级回滚是当基线配置变更导致历史加速比不可比时，冻结旧正例的奖励权重，只在新基线下重新评测后再解冻。代价是评测基础设施的维护成本：四项探针使单候选的 GPU 时间与显存占用成倍增加，而对比采样本身已随候选数线性放大编译与运行开销，两者相乘决定了单题评测预算的上限。工程判断落在取舍上：探针不必对全部候选执行，只对通过编译与基础比对的候选做完整探针，失败候选仅记录编译错误类型；这样把昂贵的正确性与性能探针集中在少数有希望的候选上，使监控成本随正例候选数而非总候选数增长。

失效面：奖励闭环在哪些条件下会给出错误信号

CUDA-L1 的奖励建立在“同题多候选排序”上，因此它的第一个边界不在模型而在采样预算：候选数 k 增加时，编译与 GPU 运行开销近似线性放大，单题成本可写成 $$C_{\text{task}} \approx k\,(c_{\text{compile}} + c_{\text{run}} + c_{\text{verify}})$$ 其中编译失败候选仍要付出 nvcc 前端解析与错误结构化的代价。当 k 被压低以控制成本时，正负对数量下降，成对偏好损失的梯度方差上升，模型更容易把“偶然更快但语义等价性未覆盖”的实现推成正例——这是奖励信号稀疏与采样不足耦合出的静默降级，表现为训练曲线仍上升而线上正确性回退。

第二个失效面是正确性 oracle 的判定边界。逐元素数值比对在浮点累加顺序改变、规约树深度变化、TF32/FP16 混用时会落在容差边缘，容差未定义时同一候选可能在不同轮次被判为正例或负例，负例池被污染，对比损失学到的是噪声而非优化方向。更隐蔽的是 shape 特化：候选若把 block 维度、shared memory 布局或循环边界硬编码到某一输入形状，在小规模参考输入上通过比对并拿到高加速比，换到未覆盖形状即越界或结果错误。这类候选在训练分布内是正例，在生产输入上是 OOM 或非法访存的来源，而闭环本身不会自动发现，除非评测集显式包含形状扫描与边界输入。

第三类是 batch invariance 违规与性能回退。kernel 若按 batch 内元素重排归约顺序，单样本输出随 batch 组成变化，逐元素比对在固定 batch 下仍可通过，但服务端动态 batching 会暴露不一致；这类错误不触发编译失败也不触发数值比对失败，属于最贵的漏检。监控上应把“同候选在不同 batch 组合下的输出差异”作为独立门禁，而不是并入正确性 oracle。回滚策略则依赖候选来源可追溯：每个正例需记录算子、输入分布、计时口径与编译产物哈希，一旦线上出现回退，按哈希定位到具体候选并回退到上一稳定基线，同时把该候选从正例池移入负例池，避免下一轮对比采样再次采到它。工程判断是：对比奖励的收益上限由评测口径的严格度决定，口径不补齐时，加速比数字的说服力低于一次形状扫描的覆盖度。
