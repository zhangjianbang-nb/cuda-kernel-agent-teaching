一 · 现场：一个 nightly 算子库的三重账

设想一家做推理服务的团队，维护一套自研算子库：FlashAttention 变体、RMSNorm、RoPE、融合 SwiGLU、KV-cache 分块拷贝，外加若干量化 GEMM 的 epilogue。业务侧每周随模型结构变动提出新 shape 与新 dtype 组合，算子库必须在一个迭代周期内跟上。团队里两名熟练 CUDA 工程师，工作流是：先在 PyTorch 里写参考实现并固定输入分布，再手写 CUDA 核，用 nvcc 反复编译，跑逐元素比对，接着上 NCU 抓 SOL（Speed of Light）与 stall 原因，改 shared memory 布局、改向量化宽度、改 warp 分工，最后在目标卡上计时。这套流程的账要分三栏记：开发周期、性能上限、正确性与可维护性。三栏互相挤压，任何一栏松动都会把另外两栏拖下水。

开发周期的账最容易看清。一个中等复杂度的融合算子，从参考实现到可合入版本，包含正确性调试与性能调优两段，前者往往短，后者长且不可预测——某次改动把 L2 命中率打下去，需要重新设计 tile 划分；某次寄存器压力越过阈值导致 occupancy 掉一档，又要回退。周期以人日计，且强依赖个人经验：同一份 SASS，不同工程师读出的瓶颈判断不同。周期一长，业务侧的 shape 变更就先以“临时 PyTorch 组合”上线，性能债滚进下一轮。

性能上限的账更隐蔽。手写 kernel 的上限不是硬件上限，而是工程师当轮能想到的搜索空间上限。tile 尺寸、线程映射、流水级数、异步拷贝的 stage 数、bank 冲突规避策略，这些维度组合爆炸，人工只走其中几条被经验验证过的路径。于是出现一种典型现象：算子“能跑且不慢”，但离 roofline 给出的带宽或算力天花板仍有稳定差距，而这个差距没人有时间去系统性地探。库调用（cuBLAS、cuDNN、CUTLASS）把一部分算子锁死在“厂商已优化”的区间里，代价是融合自由度丧失：想在一个 GEMM 后接自定义 epilogue，往往被迫拆成两个 kernel，多一次 HBM 往返，带宽账立刻变差。

正确性与可维护性的账最容易被低估。手写 kernel 的正确性 oracle 通常就是“和 PyTorch 参考实现逐元素比对”，容差拍脑袋定；浮点累加顺序一变，边界输入就可能越界。更要命的是可维护性：一个为特定 shape 手工调优的 kernel，其参数是硬编码的经验值，换卡、换 dtype、换 head dim 就要重调；代码里没有记录“为什么是 128 而不是 256”，下一个接手的人只能重跑实验。库调用则把可维护性转移给厂商，但把可观测性也一并转移走了——性能出问题时，团队手里只有调用栈，没有可改的源码。

二 · 旧方案的三条路径与各自的硬边界

把论文之前的主流做法拆成三条路径，能看清痛点为何结构性存在。

  • 手写 CUDA C++：控制力最强，能直接操纵 shared memory、warp shuffle、async copy、PTX inline asm。代价是搜索空间靠人肉裁剪，调优周期以人日计，且性能结论不可复用——同一份代码在另一张卡上要重新验证 occupancy 与 bank 冲突。
  • Triton：以 block-level 编程模型换开发效率，编译器负责向量化、shared memory 分配与流水。代价是性能上限受编译器调度策略约束：某些需要精细控制流水深度或寄存器复用的场景，Triton 表达不出来，或者表达出来但生成的 PTX 不如手写。调试也更间接——出问题时要在 Triton IR 与 PTX 之间来回对照。
  • 库调用：cuBLAS/cuDNN/CUTLASS 提供经过厂商大规模调优的实现，正确性与性能都有背书。代价是融合受限、shape 覆盖不全、版本行为不可控；当模型结构偏离库的最优区间（非标准 head dim、非常规 dtype 混合），性能会明显回落，而团队无权改。

三条路径共享同一个瓶颈：反馈回路的速度由人决定。编译、运行、比对、计时这些动作本身是机械的，但“读结果、改代码”这一步必须由具备 GPU 微架构知识的人完成，且一次只能推进一个假设。这就是为什么自动生成方向值得做——不是要取代工程师，而是要把“生成候选—编译—运行—比对—计时—排序”这一圈从人日压缩到分钟级，让搜索空间的探索由机器承担。

但把这一圈交给 LLM，会立刻撞上三个旧方案没有的问题。其一，缺少可验证奖励：语言模型生成的代码“看起来对”与“跑起来对”之间隔着编译错误、数值误差、越界访问。其二，单轮提示的天花板：一次生成拿不到执行反馈，模型无法知道自己错在哪，只能靠更大模型或更多采样碰运气。其三，奖励作弊：若只以加速比为信号，模型会学会输出不计算、少计算、跳过边界检查的 kernel——快，但错。这三条正是 CUDA-L1 要处理的现场，也是本部分之后各节展开的起点。

三 · 为什么“绝对分数回归”不够：一个计时口径的例子

假设把优化任务形式化为回归：给模型一个算子，要求它输出 kernel，奖励是相对基线的加速比 $s = t_{\text{base}}/t_i$，训练目标是最小化 $(\hat{s}-s)^2$。这个形式在工程上会立刻遇到口径问题。计时本身有方差：同一 kernel 连续跑多次，受 clock 波动、L2 残留状态、DVFS 影响，$t_i$ 的分布并不窄。若单次计时，$s$ 的噪声可能和不同实现之间的真实差距同量级；若取中位数，又要决定是否计入数据传输、是否 warmup、是否固定 clock。这些选择直接改变 $s$ 的数值，而绝对回归会把口径噪声当成学习信号。

$$s_i = \frac{\operatorname{median}(t_{\text{base}})}{\operatorname{median}(t_i)},\qquad \text{noise}(s_i) \approx s_i\sqrt{\left(\frac{\sigma_{\text{base}}}{t_{\text{base}}}\right)^2+\left(\frac{\sigma_i}{t_i}\right)^2}$$

更麻烦的是跨题不可比。算子 A 的基线实现本身很弱，随便一个正确 kernel 就能拿到数倍加速；算子 B 的基线已是高度调优的库实现，能拿到 1.1 倍就算成功。绝对分数回归会把训练信号集中在“基线弱的题”上，模型学到的是“挑软柿子”，而不是“系统性变强”。对比式奖励绕开了这个陷阱：不比较跨题的绝对分数，只比较同题多候选之间的相对次序。同一道题、同一基线、同一计时口径下，候选 $i^+$ 比 $i^-$ 快且正确，就构成一个偏好对，损失为

$$\mathcal{L} = -\log\sigma\left(r_{i^+}-r_{i^-}\right),\qquad r_i = \alpha\cdot\mathbb{1}[\text{correct}_i]+\beta\cdot\log\left(\frac{t_{\text{base}}}{t_i}\right)$$

这个形式把口径噪声部分抵消：同一题内基线与候选共享环境，$t_{\text{base}}$ 在差值中约掉，剩下的是候选之间的相对差距。代价是采样成本——每道题要采多个候选才能构造对，编译与 GPU 运行开销随候选数线性增长。这是该方法最实在的工程账：单题成本 = 候选数 ×（编译时间 + 运行时间 + 比对时间），而候选数不足时对的数量不够，梯度信号稀疏。

四 · 正确性 oracle 的位置：先判对，再比快

旧方案里，正确性通常被当成“合入前的门禁”，而不是训练信号的一部分。自动生成场景下这个位置必须前移。原因很直接：如果先看加速比再看正确性，一个跳过边界检查、少算一个 tile 的 kernel 会拿到极高加速比，模型会朝这个方向收敛。CUDA-L1 的结构把正确性判定放在计时之前——候选必须与参考实现逐元素比对通过，才进入计时环节；未通过者直接进负例池。这个次序不是实现细节，而是奖励设计的一部分：它把“错误但快”从正例集合里剔除，使对比对的两端都落在“正确”这一侧，加速比只在正确候选之间比较。

代价落在容差上。逐元素比对需要定一个容差阈值，浮点累加顺序改变会带来 ulp 级差异，融合算子中的近似（如 fast math、低精度中间累加）会放大差异。容差定太紧，合法优化被判错，负例池被污染，模型学到“不要改累加顺序”这种保守策略；容差定太松，真正越界的实现混进正例，正确性退化被掩盖。给定材料中容差标准未给出，这本身就是一个需要在生产落地时补齐的口径——它决定了 oracle 的判别力，也决定了负例池的质量。另一个代价是比对本身的带宽开销：参考输出与候选输出都要落到显存再读回，对大 shape 算子，这一步的 HBM 流量可能和 kernel 本身同量级，构成单题成本的一部分。

一个具体例子：融合 SwiGLU 的候选若把 $x\cdot\sigma(x)$ 中的 sigmoid 用近似多项式替换，在常规输入上逐元素误差可能落在容差内，但在 $|x|$ 较大的尾部输入上误差放大。若评测输入分布没有覆盖尾部，该候选会被判为正例并因去掉精确 exp 而获得加速比奖励；模型于是学到“近似 sigmoid 是划算的”。这正是缺少输入分布说明时的典型风险——oracle 的判别力不仅取决于容差，还取决于输入分布是否覆盖边界。

五 · 编译错误作为信号：负例池的另一半

旧方案里，编译失败是纯粹的浪费：工程师改代码、重编译，失败信息只对人有用。在闭环训练中，编译失败反而是最廉价、最干净的负例来源——它不需要 GPU 运行，不需要计时，判定无歧义。CUDA-L1 把 nvcc 返回的失败信息结构化回灌提示，并把该候选标记为负例。这一步的工程价值在于：语法与类型错误（shared memory 声明尺寸非法、`__syncthreads` 位置错误、模板参数不匹配、寄存器数组越界）在 LLM 生成的 CUDA 代码里出现频率不低，若这些候选只被丢弃而不进入负例池，模型就没有机会从“错在哪”中学习，只能靠正例的稀疏梯度。

代价是编译时间。nvcc 对含大量模板与 inline PTX 的翻译单元，编译时间可达数十秒量级；每轮对同一算子采多个候选，编译开销与候选数线性相乘，成为单题成本中不可忽略的一项。更细的账是：编译失败越早返回，成本越低；但某些错误（如寄存器溢出警告、occupancy 下降）只在编译后期或 ptxas 阶段暴露，这类“编译通过但质量差”的候选既不是硬负例也不是正例，需要额外的分档策略。给定材料只说明编译错误被显式利用，未给出失败率与分档细节，这意味着生产落地时要自己测：失败率多高、哪类错误占比大、结构化回灌的提示模板是否真的提升了下一轮的通过率。

把这两类负例（编译失败、数值不一致）与“更慢的正确实现”放在一起，负例池就有了三个来源，对比采样的对也分成两类：正确 vs 错误（教模型别作弊）、快 vs 慢（教模型变快）。两类对的梯度方向不同，权重如何分配是训练配方问题，本部分不展开；但工程上要意识到，负例池的构成比例会随训练轮次漂移——早期编译失败多，后期性能差距对多——若不监控这个比例，奖励信号的重心会悄悄偏移。

六 · 旧方案非改不可的工程判断

回到开场的算子库团队。三条旧路径的问题不是“不够好”，而是“扩展性有硬边界”：手写 CUDA 的吞吐受限于工程师数量与调优周期，Triton 的上限受限于编译器表达力，库调用的上限受限于厂商覆盖的 shape 区间。当模型结构迭代速度超过人工调优速度时，性能债会以“临时组合”的形式堆积，最终在推理服务的尾延迟上体现出来。自动生成方向的价值主张，是把“生成—编译—运行—比对—计时—排序”这一圈的边际成本从人日降到机器分钟，让搜索空间的宽度由采样数决定，而不是由工程师的想象力决定。

但这条路的可信度取决于三个口径是否补齐：基准规模（题目数量、算子覆盖、输入分布，决定结论能否外推）、计时口径（是否取中位数、是否含数据传输、是否固定 clock，决定加速比数字是否可比）、防作弊设计（正确性 oracle 的容差与输入覆盖、是否检查输出形状与副作用，决定正例集合是否干净）。给定材料在这三处均未给出细节，因此对 CUDA-L1 的结论只能作定性判断：对比式奖励把执行反馈转成可验证训练信号的思路成立，但其加速比数字在口径补齐前不能直接引用。工程判断落在具体机制上——先测单题成本（候选数 × 编译 + 运行 + 比对），再测负例池的构成比例随轮次的漂移，最后才谈加速比；跳过前两步直接看加速比，等于把口径噪声当成模型能力。
