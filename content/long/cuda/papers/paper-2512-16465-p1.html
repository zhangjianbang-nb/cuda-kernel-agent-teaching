一 · 从一次线上推理的尾延迟说起

设想一个已经上线的推理服务：主干是 Transformer 解码，中间夹着若干自定义算子——fused layernorm、rotary embedding、KV cache 的 gather/scatter、以及一段 shape 随 batch 变化的 GEMM。服务跑在 A100/H100 集群上，SLO 卡在 P99 尾延迟。值班工程师打开 profile，发现某个融合算子在特定 batch 下占了整步时延的可观比例，而它调用的库实现要么没有覆盖这个 shape，要么内部做了保守的分块选择。此时团队面对的不是"要不要写 kernel"，而是"谁来写、多久写完、写完怎么证明它更快且没算错"。

这就是 cuPilot 这类工作的问题现场。论文摘要把痛点压成一句话：优化 CUDA kernel 是"challenging and labor-intensive"的任务，因为它同时要求软硬件协同设计（hardware-software co-design）的专业知识，以及高性能 kernel 库本身的专有性（proprietary nature）——厂商库不开源、不解释启发式，工程师只能黑盒调参。这两条约束叠加，使得"手写一个比库更快的算子"在多数团队里是一件投入产出比极差的事。

本部分只做一件事：把 cuPilot 之前的四条主流路径——手写 CUDA、Triton、库调用、以及早期的 LLM 单发式生成——各自的工程代价摊开，说明为什么"再优化一点"不够，必须换表示。评测口径与多轮进化的机制留给后续部分。

二 · 手写 CUDA：上限最高，周期最长

手写 CUDA C++ 是唯一能触及硬件全部能力的路径：warp 级 shuffle、shared memory 的 bank 排布、异步拷贝（cp.async / TMA）、tensor core 的 fragment 布局、寄存器压力与 occupancy 的取舍，全部由人决定。代价是这条路径的每一层都需要显式决策。一个中等复杂度的融合算子，从读懂参考实现、推导数据流、写出第一版能跑通的 kernel，到用 NCU 逐项消掉 stall（long scoreboard、MIO throttle、barrier），通常以人周计。论文用"labor-intensive"概括的正是这段周期。

更麻烦的是性能上限与正确性并不独立。为了压榨带宽，工程师会做向量化加载、改变数据布局、把中间结果留在寄存器里跨 tile 复用；每一步都在缩小正确性的验证面。一个典型的伪代码思路是：

$$\text{tile}(i)=\text{load}_{128\text{b}}(A[i{:}i{+}T]),\quad \text{acc}\mathrel{+}=\text{mma}(W_{\text{frag}},\text{tile}(i)),\quad \text{store}_{128\text{b}}(\text{acc})$$

这段结构看起来无害，但 load 的对齐假设、mma 的 fragment 顺序、以及 store 的边界处理，任何一处与 shape 不匹配都会静默产生错误结果——GPU 不会替你报错，只会给出一个数值上"看起来合理"的张量。正确性 oracle 因此成为必需品：必须有一份逐元素的参考实现（通常是 PyTorch eager）在给定输入分布上做全量比对，并且要覆盖非对齐尾块、空 tensor、极端 dtype。这部分验证代码本身的工程量，常常与 kernel 本体相当。

可维护性是第三条隐性成本。手写 kernel 与上层框架的耦合极深：dtype 一变、layout 一换、GPU 架构一升级（sm80 → sm90 的 TMA 与 WGMMA），原先的启发式全部失效，需要重写。团队里能读懂这段代码的人往往只有一个。于是现实中大量算子最终退回库调用，不是因为库更快，而是因为没人敢改。

具体例子：一个 batch=1 的 decode 阶段 fused attention，手写路径需要处理 KV 长度非 2 的幂、head_dim 非 64/128 的情况；工程师为这几个边界写的分支代码，会让主循环的寄存器分配变差，occupancy 下降，最终在常见 shape 上反而不如库。这就是"上限最高"与"实际更快"之间的鸿沟。

三 · Triton 与库调用：把决策权交出去

Triton 的设计取向是把 block 级编程模型暴露给用户，把线程级调度、shared memory 分配、向量化这些决策交给编译器。写一个 matmul 的 Triton kernel，用户只需描述 tile 形状与累加逻辑，编译器负责生成 PTX。这大幅压缩了开发周期：一个能跑通的 Triton 版本可以在小时级完成，而对应的 CUDA 版本要天级。

代价是性能上限被编译器封住。Triton 的抽象层次决定了它无法表达某些手写技巧——精细的 swizzle 布局、跨 warp 的寄存器复用、非规则的 pipeline 深度。当 kernel 是 memory-bound 时，Triton 通常能接近 roofline；当 kernel 是 compute-bound 且需要极致 instruction mix 时，Triton 生成的代码往往在关键硬件单元利用率上留有余量。论文在 GEMM 任务上强调 cuPilot"achieves high utilization of critical hardware units"，正是把这余量当作靶子。这里的性能代价可以定性表述为：Triton 把"调优空间"换成了"开发速度"，而这个交换在算子库级别的竞争中是亏的。

库调用（cuBLAS / cuDNN / CUTLASS 实例）是第四条路径，也是最常见的工程选择。它把正确性和可维护性外包给厂商，代价是专有性：库内部的启发式不公开，遇到未覆盖的 shape 就退回通用实现，性能断崖式下跌。论文摘要里的"proprietary nature of high-performance kernel libraries"直接指向这一点——工程师无法阅读、无法修改、无法针对自己的 shape 分布做特化。一个真实场景：某算子库对 M=1 的 skinny GEMM 走的是通用分块，而推理服务里 80% 的请求都是这个 shape；工程师明知有更优的 split-K 方案，但因为不能改库，只能在上层做算子融合绕开。

把三条路径放在一张表里，代价结构一目了然：

路径开发周期性能上限正确性风险可维护性
手写 CUDA人周级最高，可触硬件全能力高，静默错误面大差，架构升级即重写
Triton小时级中，受编译器抽象限制中，语义较窄较好
库调用分钟级随 shape 波动，未覆盖即断崖低最好，但不可改

这张表说明：没有一条路径同时满足"快、对、可改、便宜"。工程上只能在四者间做静态取舍，而取舍点一旦选定就无法随 shape 分布动态调整。这正是需要新表示的根本原因。

四 · 早期 LLM 单发式生成：为什么"能写"不等于"更快"

LLM 的出现提供了一个诱人的替代：让模型直接读参考实现、写出 CUDA 或 Triton kernel。这条路把开发周期从人周压到分钟级，token 成本远低于人力成本。但 cuPilot 摘要对它的判断很直接：现有方法"often fall short in performance due to their suboptimal agent designs and mismatched evolution representations"——性能不够，原因不在模型能力，而在 agent 设计与进化表示的错配。

拆开看，"错配"至少有两层。第一层是反馈回路太浅：单发式生成只做一次编译+一次正确性检查，通过就交付，不通过就重试。它没有把 NCU 的 stall 归因、SASS 的指令构成、roofline 的带宽/算力位置回灌给模型，因此模型无从知道"这一版离硬件上限还差在哪"。第二层是搜索表示太粗：以整段源码为进化单位，交叉与变异都在 token 层面发生，一个微小的布局改动会被无关的语法差异淹没，进化算法实际上在做随机游走。

正确性代价在这里被放大。LLM 生成的 kernel 常常在常见 shape 上通过检查，却在尾块、非对齐、极端 dtype 上失败；如果 oracle 只覆盖主路径，错误会被静默接受。论文给出的接受判据是显式的双门：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

其中 pass 是正确性门，s 是相对统一基线的加速比。这个判据本身简单，但它把"正确"与"更快"绑成一个不可分割的接受条件——任何只过一门的结果都不进入种群。代价是编译与测量开销：每个候选都要编译、在给定输入上跑正确性检查、再用统一基线测时延，单次迭代的时延成本远高于纯文本生成。当候选数量上升，这部分开销会成为吞吐瓶颈。

具体例子：一个 LLM 被要求优化 layernorm 的融合版本，它写出了正确的单 pass 实现，但因为把 reduction 放在了一个 block 内、没有做跨 block 的两阶段归约，在长序列上 occupancy 不足，加速比落在 1 以下。单发式流程会直接丢弃这个候选，而不会告诉模型"问题在于归约粒度"。这就是反馈深度不足的直接后果。

五 · 非改不可的三条硬约束

把上述痛点收敛，可以得到三条互相独立的硬约束，它们共同解释了为什么 cuPilot 要引入"strategy"作为中间语义表示，而不是继续在源码层面做进化。

第一条是表示与搜索的匹配。源码是实现的最终形态，不是设计的形态。一个 kernel 的性能由一组高层决策决定：分块尺寸、数据布局、流水线深度、归约策略、是否用 tensor core、是否做 split-K。这些决策的组合空间远小于 token 空间，且在语义上可比较、可交叉。以源码为进化单位，等于在一个高维、语法噪声大的空间里搜索一个低维的设计空间。cuPilot 的做法是把 strategy 抽出来作为进化的载体——摘要明确写"introduces strategy as an intermediate semantic representation for kernel evolution"，并配套"strategy-coordinated evolution algorithm"与"strategy-level population initialization"。这一步的代价是额外的抽象层：strategy 必须先被翻译成可编译的源码，翻译环节本身可能引入错误，因此正确性门必须放在翻译之后而非之前。

第二条是反馈必须带硬件语义。只说"慢了"不足以指导下一步。roofline 给出的是"这个 kernel 落在带宽墙还是算力墙、距离墙有多远"，这是可操作的归因。论文的"roofline-guided prompting"正是把这一层语义注入提示词。代价是 profile 开销：每次候选都要跑 NCU 或至少采集带宽/算力利用率，这部分时延与显存占用会计入迭代成本。对于小 kernel，profile 的开销可能超过 kernel 本身的执行时间，工程上需要用采样或多次重复摊薄。

第三条是正确性 oracle 必须与性能门同权。前面已经看到，GPU 的错误是静默的。若 oracle 只覆盖主路径，进化过程会系统性地偏向"在测试分布上快、在真实分布上错"的候选——这正是 reward hacking 的温床。cuPilot 的接受判据把 pass 放在合取的第一项，方向是对的；但工程判断在于 oracle 的覆盖面：输入分布若与论文口径不一致（shape、dtype、layout），离线加速比会系统性高估。论文声称在 100 个 kernel 的基准上相对 PyTorch 平均 3.09×，这个数字的成立前提是基线选择与输入分布；若基线未开 TF32、未用最强库实现，加速比会被高估，这是读这类结果时必须先核的口径问题。

三条约束合起来指向同一个结论：需要的不是"更强的模型"，而是"更合适的进化表示 + 更深的硬件反馈 + 更严的正确性门"。cuPilot 的 multi-agent 结构、strategy 表示与 roofline 提示，都是围绕这三条约束做的工程回应。至于 strategy 如何被协调、多个 agent 如何分工、种群如何初始化，属于后续部分的范围。

回到开场的推理服务：那个占尾延迟的融合算子，在旧路径下要么等人周级的手写，要么接受库的保守实现，要么赌一次 LLM 单发。三条路都不满足"快、对、可改、便宜"的同时成立。cuPilot 要证明的是，把设计决策抽成 strategy、让进化在 strategy 层发生、用 roofline 与正确性门双重筛选，可以在保持正确性的前提下把加速比稳定推到基线之上——而这条路径的第一个工程代价，就是每次迭代都要付出编译、profile 与全量比对的时延，这个代价必须被算进吞吐预算里，而不是当作免费的反馈。

库调用的天花板与手写内核的边际成本

在一个在线推理服务里，attention 的 decode 阶段是典型现场：batch 小、序列长、KV cache 带宽吃紧，cuBLAS 与 FlashAttention 的通用实现按固定 tile 与调度策略跑，落到具体 shape 上往往离 roofline 有一段距离。工程师的第一反应是换库或调参数，但库的启发式选择不对外暴露，且高性能 kernel 库的闭源属性使得“照着改一行”不可行——这正是论文开篇强调的硬件软件协同设计门槛与专有库壁垒。手写 CUDA 于是成为唯一出口：一个 fused kernel 要同时处理 shared memory 分块、warp 级归约、异步拷贝与寄存器压力，开发周期以人周计，且每次架构换代都要重做。

旧方案的系统代价可以用一条简单的账来刻画。设基线时延为 $$T_{\text{base}}$$，候选为 $$T_{\text{agent}}$$，收益 $$\text{speedup}=T_{\text{base}}/T_{\text{agent}}$$；但真正的工程判据是接受条件 $$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$，即正确性门与性能门同时通过。手写路径的失效条件很明确：一旦 shape 分布偏移（如 prefill 长序列混入 decode 批次），按单一 tile 特化的 kernel 会退化为带宽受限甚至触发寄存器溢出，加速比跌到 1 以下，而回退到库调用又意味着维护两套路径、双倍回归测试成本。Triton 降低了表达门槛，却把调度决策交给编译器，遇到需要精细控制 swizzle 或 TMA 的场景仍要落回 CUDA 或 CuTe。

可维护性是更隐蔽的代价。一个算子库场景里，同一 GEMM 变体要为不同 dtype、不同 SM 版本维护多份实现，编译时间随模板实例化膨胀，CI 里每次改动都要重跑全部 shape 的正确性与性能基线。论文给出的对照是：在 100 个 kernel 的基准上，cuPilot 生成的 kernel 相对 PyTorch 平均达到 3.09 倍加速，GEMM 任务上体现出对关键硬件单元的高利用率——这说明旧方案并非性能上限已到，而是搜索与表达的成本把工程师挡在了上限之前。换言之，非改不可的理由不是“LLM 更时髦”，而是人工枚举策略的空间太小、反馈回路太慢，无法覆盖 shape 特化与架构迁移带来的组合爆炸。
