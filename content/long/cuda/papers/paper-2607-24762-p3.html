一 · 一次迭代的流动：从模型到候选 kernel

Kernel Forge 的起点不是一条孤立的 kernel 签名，而是一个未经修改的 PyTorch 模型。harness 接收模型后做的第一件事是定位可优化单元：把模型按算子粒度切开，找出运行时间占比高、且存在手写空间的那一小撮 kernel——论文摘要点名的矩阵乘、卷积、归一化正是这类对象。这一步的输出不是代码，而是一份「待优化清单」：每个条目携带算子类型、张量 shape/dtype、在模型中的调用位置，以及一个可执行的参考实现（PyTorch eager 版本）。代价在这一步就已经埋下：切分与 trace 需要跑一遍前向，若模型含动态控制流或数据依赖的 shape，trace 会退化成多次采样，显存与时间开销随采样次数线性增长。工程上的判断是：清单粒度太粗会把整段子图塞给 LLM，候选代码无法独立编译；太细则丢失融合机会。Kernel Forge 选择的是「单算子为单元、但保留调用上下文」的折中，这也是它能做到「原地替换」的前提——候选 kernel 必须能塞回原模型同一个调用点，接口签名由 harness 自动生成而非让 LLM 猜。

清单确定后进入生成环节。论文的表述是 MCTS 探索多条优化路径，而非单条线性精修链。把这句话翻译成机制：每个待优化 kernel 对应一棵搜索树，根节点是参考实现，子节点是一次具体的改写动作（换 tile 尺寸、改向量化宽度、引入 shared memory 分块、换 reduction 策略等）。每次扩展由一个 LLM 调用产生候选源码，节点上记录该候选的编译状态、正确性判定与实测时延。选择策略在「已验证高收益」与「未探索分支」之间做权衡，这正是 MCTS 的 UCT 形式要解决的问题：

$$\text{UCT}(n)=\frac{Q(n)}{N(n)}+c\sqrt{\frac{\ln N(\text{parent})}{N(n)}}$$

其中 $Q/N$ 是该节点历史候选的平均收益（用加速比或时延归一化），第二项鼓励访问次数少的分支。$c$ 的取值直接决定 harness 的性格：偏小则快速收敛到局部最优，迭代预算被少数几个高收益分支吃掉；偏大则把 50 次迭代摊薄到大量低质量候选上，编译与测量开销翻倍。论文给出的预算是「每个 kernel 仅 50 次优化迭代」，在这个量级下 $c$ 不能取大，否则树还没展开预算就耗尽。这里的代价是token 与编译时间：每次扩展是一次完整的 LLM 生成（输入含参考实现、shape、上一轮反馈），输出是整段 CUDA 源码；随后是 nvcc 编译，单次编译在秒级，50 次迭代意味着单 kernel 的墙钟时间里有相当比例花在编译器上而非 GPU 上。具体例子：ResNet-50 的 adaptive_avgpool2d 被优化到 $1.52\times$，这个算子本身计算量极小、受限于 reduction 与访存，搜索树的有效分支大概率集中在并行归约的切分方式上，而不是 tile 尺寸——MCTS 的价值在于它能快速放弃那些编译通过但收益为零的分支。

二 · 编译与正确性门：候选进入测量前的两道闸

候选源码生成后并不直接上 GPU 计时。第一道闸是编译：harness 调用工具链（论文口径覆盖 CUDA / Triton / CuTe / PTX）把源码变成可加载的模块，编译失败即回灌错误信息给 LLM 作为下一轮扩展的输入。这一步的工程细节决定了 agent 能否自我修复：编译器报错文本（缺少头文件、非法 inline asm、寄存器溢出警告）必须原样进入提示，而不是被截断成「编译失败」四个字。第二道闸是正确性检查，在论文给定的输入分布上跑候选并与参考实现比对。这里有一个容易被忽略的设计点：正确性 oracle 的容差必须与 dtype 匹配——fp32 累加的 reduction 与 fp16 输入的卷积，逐元素全等的判据会把合法候选误杀，而放宽容差又会放过真实的数值错误。Kernel Forge 的正确性门是硬门：不通过则不进入计时环节，这避免了「快但错」的候选污染搜索树的收益估计。

两道闸的代价不对称。编译失败的成本是秒级编译时间加上一次 LLM 调用的 token；正确性失败的成本是一次前向执行加比对，通常远小于编译。真正昂贵的是假阴性：一个数值上合法但被容差误判的候选被丢弃，搜索树失去一条可能通向高收益的路径，而 harness 无法察觉这种损失。工程上的缓解手段是把正确性检查做成多档：先用宽松容差筛掉明显错误，再对通过者用严格容差复核，两档都过才计时。这个策略的代价是执行次数翻倍，但在 50 次迭代的预算下，多跑几次前向远比浪费一次 LLM 扩展便宜。具体例子：Stable Diffusion 3.5 的 group_norm 被优化到 $1.70\times$，归一化类算子的正确性对均值/方差的累加顺序敏感，若 oracle 只做全等比对，任何改变归约顺序的候选都会被判错，而改变归约顺序恰恰是这类算子提速的主要手段——这说明正确性门的容差设计直接决定了搜索空间的可达范围。

三 · 计时与评分：统一基线下的加速比口径

通过两道闸的候选进入测量。harness 用统一基线测时延，基线是 PyTorch eager、torch.compile 与论文指定库实现，候选与基线在同一输入、同一硬件（DGX Spark 的 GB10）上背靠背测量。评分公式在论文口径下是阈值化的通过率：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

$N$ 是评测用例数，$s_i$ 是第 $i$ 个用例上基线时延与候选时延之比，$\tau$ 是加速比阈值。这个公式的选择本身就是一个工程判断：它奖励「稳定超过阈值」而非「平均加速比高」，因为后者会被个别极端用例拉高，掩盖多数用例上的退步。代价是它对 $\tau$ 极度敏感——$\tau$ 定在略高于 1 的位置，则大量小幅提速的候选被判失败，搜索树的收益信号变得稀疏；$\tau$ 定得低，则退步候选也能拿到分数，reward hacking 的空间打开。计时环节本身的代价是测量噪声：单次 kernel 时延在微秒到毫秒量级，GPU 时钟波动、缓存状态、相邻 kernel 的干扰都会让 $s_i$ 抖动，harness 必须做多次重复取中位数或最小值，重复次数直接乘以墙钟时间。在 50 次迭代的预算下，每次迭代都做充分重复是不现实的，于是 harness 面临一个取舍：早期迭代用少量重复快速筛掉劣质候选，后期对少数优胜者做精细测量。这个两段式测量的代价是早期可能误杀一个噪声中看起来慢的候选，收益是把测量开销集中在真正要交付的那几个 kernel 上。

另一个口径问题是基线是否「开满」。论文的基线包含 torch.compile 与指定库，若基线未开 TF32 或未用最强库实现，加速比会被系统性高估。Kernel Forge 作为 harness 的价值之一是把基线固定下来，让不同候选之间的比较在同一把尺子上进行；但这也意味着它的绝对加速比数字只在论文给定的硬件与基线上成立，跨硬件、跨 dtype 迁移时口径会漂移。具体例子：论文报告在四个 PyTorch 模型上优化 14 个 kernel 使其超过 PyTorch eager，其中 LLM 负载的 kernel 若基线是 eager 而非融合后的库实现，$1.52\times$ 这类数字的含义是「比朴素实现快」，不是「比最优库快」——读这个数字时必须同时读它的基线定义。

四 · 反馈回灌：编译、运行与 profile 结果如何变成下一轮的输入

Kernel Forge 的反馈不是单一的「快/慢」布尔值，而是分层回灌：编译错误文本、正确性失败的具体用例与偏差量、计时得到的 $s_i$、以及 profile 层面的资源占用。每一层进入下一轮 LLM 提示的方式不同。编译错误适合原样拼接，因为编译器消息是结构化的、指向明确的；正确性失败需要附带输入 shape 与参考输出片段，否则 LLM 无法定位是索引越界还是数值精度问题；计时结果则要转成相对基线的比值而非绝对毫秒，因为绝对时延对 LLM 没有可操作的语义。profile 结果（占用率、访存吞吐、寄存器压力）是最高价值也最难回灌的一层：它告诉 agent「这个候选是 compute-bound 还是 memory-bound」，从而决定下一轮该改计算密度还是改访存模式。代价是 profile 工具本身的开销——NCU 级别的采集会让单次运行慢一个数量级，在 50 次迭代的预算里不可能每轮都做全量 profile，只能对通过正确性门且时延接近优胜者的候选做抽样采集。

反馈回灌的另一个机制是树上的状态复用。MCTS 的节点保存了候选源码与其测量结果，当搜索回溯到某个祖先节点再扩展新分支时，LLM 的提示里可以带上「这个父节点的候选已经达到 $s=1.3$，它的瓶颈是 shared memory bank conflict」这样的结构化摘要，而不是让模型从零重写。这降低了每轮扩展的 token 成本，但也引入一个风险：摘要本身是 LLM 生成的解释，可能把真实的瓶颈归错因，导致后续分支沿着错误方向展开。工程上的做法是让摘要只包含可测量的事实（占用率数值、编译警告、$s_i$），把因果解释留给下一轮 LLM 自己推断。具体例子：group_norm 的 $1.70\times$ 若来自把两次 pass 融合成一次，则 profile 上应看到访存量减半；若 harness 把这个事实作为反馈回灌，下一轮扩展就更可能尝试类似的融合动作而非继续调 tile 尺寸——反馈的粒度决定了搜索的效率。

五 · 验证与部署：从离线分数到端到端回归

搜索结束后，harness 输出的是每个 kernel 的最优候选及其测量记录。但「离线基准上快」不等于「生产上快」，Kernel Forge 的原地替换设计正是为了缩短这段距离：候选 kernel 的接口由 harness 生成，能直接塞回原模型的调用点，不需要开发者手工重写 glue code。验证环节因此分成两层。第一层是单 kernel 回归：把候选替换进模型，跑一遍前向，确认输出与原始模型在容差内一致，且端到端时延确实下降。第二层是端到端回归：模型整体的吞吐、显存占用、以及与相邻算子的交互是否退化——一个单 kernel 提速的候选可能因为改变了中间张量的布局，迫使下游算子插入额外的 transpose，端到端反而变慢。这一层的代价是显存：融合类候选往往需要额外的 workspace 或改变中间结果的驻留方式，在显存紧张的部署场景下，离线基准上不显眼的显存增量会成为拒绝理由。

部署判断的核心是「收益是否可归因」。论文报告的 14 个 kernel 超过 eager、以及 adaptive_avgpool2d 的 $1.52\times$、group_norm 的 $1.70\times$，都是单 kernel 层面的数字；要把它们转化成端到端收益，必须确认这些 kernel 在模型总时延中的占比，以及替换后没有引入新的同步点或布局转换。Kernel Forge 附带的可视化界面在这里起作用：它让工程师检查候选源码、调试失败、监控搜索进度，本质上是把「可信」这件事从分数延伸到可审计——一个加速比数字若不能对应到具体的候选源码与测量记录，就无法在部署评审中被接受。代价是人工审查的时间，这部分成本不随迭代次数下降，是 harness 无法自动化的残余。

最后落在工程判断上：Kernel Forge 的方法骨架是「参考实现 → MCTS 扩展 → 编译/正确性双门 → 统一基线计时 → 分层反馈回灌 → 原地替换回归」，每一步的代价都可以量化到 token、编译秒数、测量重复次数或显存增量。这套流动的可靠性不取决于 LLM 单次生成的质量，而取决于两道门与计时口径是否把错误候选挡在收益估计之外——正确性门的容差设计与计时基线的固定方式，比搜索策略本身更能决定最终交付的 kernel 是否可信。shape 特化与隐藏输入分布会让离线分数在生产上崩塌，这一点在部署评审时必须作为独立项核查，而不是寄希望于搜索过程自动覆盖。

边界：MCTS 分支预算、shape 特化与回退路径的三重代价

Kernel Forge 的搜索结构决定了它的失效面。MCTS 在“生成—编译—运行—评测”回路里为每个候选节点付出一次完整编译与一次计时，因此单 kernel 的迭代预算（论文口径为 50 次优化迭代）必须被分摊到多条路径上，而非线性精修链。设分支因子为 $$b$$、平均深度为 $$d$$，则节点数近似 $$N \approx b^{d}$$ 的截断版本；在固定迭代上限下，扩大 $$b$$ 意味着每条路径更浅，容易停在“编译通过但未触及内存层级”的局部最优，而收缩 $$b$$ 则退化为单链精修，正是论文明确要避开的形态。代价是双重的：编译时间随节点数线性增长（每个候选都要过一次 nvcc/triton 编译），而计时噪声在小 kernel 上会淹没真实差异，导致 UCT 选择被抖动误导。

更硬的边界在输入分布。harness 接受未修改的 PyTorch 模型原位替换，评测却在论文给定 shape 上做，候选极易滑向 shape 特化：把 tile 尺寸、并行度、甚至循环边界写死成编译期常量。这类 kernel 在离线基准上加速比漂亮，一旦生产侧 batch、序列长度或 dtype 漂移，就会触发重编译或直接落到慢路径。正确性门只校验给定输入上的数值一致，无法拦住“对别的 shape 语义仍对但性能崩塌”的情形；性能门又只认统一基线的时延比，于是特化成为被奖励的行为。工程上必须补一条分布外抽检：在非基准 shape 上重跑正确性与时延，把 $$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$ 的统计口径从单一 shape 扩到 shape 族，否则离线分数不可迁移。

第三重代价来自回退与 reward hacking。当候选编译失败或正确性不过，agent 会回退到 PyTorch eager 或 torch.compile 路径，此时端到端时延被基线主导，加速比被人为拉平甚至虚高；若评分只看“是否优于基线”而不惩罚回退率，搜索会学会频繁提交注定失败的候选以换取重试预算。可控的做法是把回退率与编译失败率作为硬约束写进接受条件，并限制单 kernel 的编译次数上限——这直接对应 token 与 wall-clock 预算：每次失败重试都消耗一轮 LLM 调用与一次编译，50 次迭代的预算在失败密集时会被迅速耗尽。论文在 DGX Spark GB10 上对四个模型、14 个 kernel 报告了 1.52×（adaptive_avgpool2d）与 1.70×（group_norm）量级的加速，但这些数字绑定在给定硬件、基线与输入分布上，跨 dtype 与跨框架迁移未验证，任何把该口径直接外推到生产 SLA 的判断都缺乏依据。
