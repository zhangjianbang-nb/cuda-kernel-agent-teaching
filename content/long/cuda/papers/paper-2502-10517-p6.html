一 · 把「一次评测」拆成可计费的五类资源

KernelBench 的评测闭环是编译—运行—数值比对—计时四段式，但落到工程预算上，这四段实际消耗的是五类互不相同的资源：模型侧 token、GPU 侧机时、搜索侧轮数、编译侧墙钟时间、以及缓存与并发带来的调度开销。它们不是可互相折算的同一种货币——token 花在生成候选上，GPU 时花在跑候选上，编译时间花在把候选变成可执行体上，而编译失败样本根本不进入 GPU 计时环节却照样烧掉编译时间与 token。把这几项混在一个「每题成本」里，就无法判断规模上去以后该先砍哪一刀。

设一道任务生成 $n$ 个候选，单候选平均生成 token 为 $L$、编译耗时 $t_c$、通过正确性检查的比例为 $p$、通过者单次计时耗时 $t_r$、重复测量次数 $k$，则单题期望成本可写成：

$$C_{\text{task}} \approx n\,(c_{\text{tok}}L + c_{\text{gpu}}t_c) + n\,p\,k\,c_{\text{gpu}}t_r$$

这个式子的关键不在数值而在结构：第一项随 $n$ 线性增长且对 $p$ 不敏感，第二项被 $p$ 直接缩放。当 $p$ 从高难度级别的任务上掉下来时，第二项缩水而第一项纹丝不动，于是「多采样」的边际收益迅速劣化——花在生成与编译上的钱买不到任何可计时的样本。这正是 KernelBench 把编译成功率单列为指标的直接工程后果：它让失败成本可见，而不是被加速比中位数掩盖。

具体例子：一道端到端模型片段级任务，若 $p$ 只有个位数百分比，则 $n=8$ 的采样预算里绝大多数候选只贡献了编译错误类型，计时环节几乎空转；此时把预算从「加采样」转向「加执行反馈轮次」更划算，因为反馈能提高 $p$ 而不是稀释它。代价是反馈轮次本身要重复编译与运行，$t_c$ 与 $t_r$ 被乘上轮数——这是下一节要算的账。

二 · 搜索轮数的成本曲线：反馈不是免费的

多轮生成—编译—运行—评测的闭环里，每一轮都要重新付出生成 token 与编译时间。设轮数为 $R$、第 $r$ 轮新增候选数为 $m_r$、该轮通过率为 $p_r$，则累计有效样本数为 $\sum_r m_r p_r$，而累计成本为 $\sum_r m_r(c_{\text{tok}}L + c_{\text{gpu}}t_c) + \sum_r m_r p_r k c_{\text{gpu}}t_r$。有效样本对成本的比值（可理解为「每个可计时样本的价格」）为：

$$\text{CostPerValid}=\frac{\sum_r m_r\,(c_{\text{tok}}L+c_{\text{gpu}}t_c)+k\,c_{\text{gpu}}\sum_r m_r p_r t_r}{\sum_r m_r p_r}$$

这个比值随 $R$ 的走向取决于 $p_r$ 是否随轮次上升。若执行反馈确实把语义错误逐轮压下去，$p_r$ 递增会让分母增长快于分子，单价下降；若反馈只是把编译错误换成另一种编译错误，$p_r$ 持平，则单价随 $R$ 单调上升，因为每轮都重复支付固定生成与编译开销。KernelBench 材料未给出具体轮数与奖励设计，因此无法断言哪条曲线成立——但工程判断是明确的：在没测出 $p_r$ 随轮次的变化之前，不要默认多轮一定摊薄单价。

一个具体机制上的代价点：编译是串行瓶颈。候选代码需要独立编译并带宿主调用封装，编译一个 CUDA 翻译单元的时间远大于一次小规模内核的计时时间，因此在 $p$ 低的级别上，编译墙钟会主导总时长。若把编译并发度设为 $J$，则编译阶段墙钟近似 $n t_c / J$，但并发编译会争抢 CPU 与内存带宽，$t_c$ 本身随 $J$ 上升而膨胀，存在一个使总墙钟最小的 $J$，且这个 $J$ 与 GPU 计时阶段的并发度不是同一个值。把编译并发与 GPU 并发混设成同一个数，是中小团队最常见的预算错配。

三 · 缓存的三层与各自的失效条件

规模上去以后，最先崩的通常不是 GPU，而是重复计算。可缓存的对象分三层，失效条件各不相同。第一层是生成缓存：相同任务描述与相同 shape 分布下，同一模型的候选可复用，失效条件是提示模板、模型版本或采样温度变化——这一层省的是 token，命中时 $c_{\text{tok}}L$ 归零。第二层是编译缓存：候选源码到可执行体的映射，失效条件是编译选项、CUDA 版本或 GPU 架构变化；这一层省的是 $t_c$，但缓存键必须包含编译选项，否则跨口径复用会污染加速比。第三层是计时缓存：通过正确性检查的候选在同一输入张量上的耗时，失效条件是 GPU 型号、时钟状态或并发负载变化——这一层最危险，因为计时对同卡并发极度敏感，缓存命中却跑在不同负载下会直接扭曲加速比。

代价在于缓存键的维度爆炸。一道任务的键至少包含任务 id、shape 与 dtype 分布、容差 $\varepsilon$、编译选项、GPU 标识；跨级别汇总时还要带上难度级别。键维度每加一维，命中率大致按该维取值数的倒数衰减。工程上的取舍是：生成缓存与编译缓存可以宽键共享，计时缓存必须窄键且绑定单卡独占运行，否则宁可重测。KernelBench 材料未给出容差取值与重复测量次数，这意味着计时缓存的键里 $\varepsilon$ 与 $k$ 两项在跨团队复现时无法对齐——这正是「跨设备复现需自行约定」的实质成本，不是一句注意事项，而是缓存不可共享。

四 · 规模上去以后，哪里先崩

按资源类型的增长阶排序，可以给出一个先崩顺序的判断框架，而不是笼统地说「规模大了会慢」。token 成本随 $nR$ 线性增长，无饱和；GPU 计时成本随 $n p k$ 增长，被 $p$ 压制；编译墙钟随 $nR$ 线性增长但被并发度 $J$ 摊薄，且 $t_c$ 随 $J$ 膨胀使其实际增长略超线性；缓存命中率随键维度指数衰减，是唯一会「突然」崩的一项——当任务集合从单算子扩到端到端模型片段，shape 分布与 dtype 组合迅速多样化，宽键缓存的命中率会阶跃式下降，于是原本被缓存吸收的 token 与编译开销一次性回灌到预算里。

具体例子：单算子级别任务 shape 分布集中，生成缓存命中率高，扩规模时成本近似线性、可预测；一旦跨到算子序列与端到端片段，组合复杂度上升使同一提示模板下的候选复用率下降，同时通过率 $p$ 随级别上升而衰减（这是 KernelBench 分级设计预期可观察的衰减），两项叠加使「每个可计时样本的价格」在级别切换处出现跳变。工程上应把级别切换当作预算重估点，而不是把单算子级别的单价线性外推到全部级别。

另一个先崩点是失败样本的存储与人工复核。编译失败与语义错误分别记录，意味着每个失败候选都要保留源码、错误类型与输入张量指纹；当 $nR$ 上万时，失败样本的数量远超通过样本（因为 $p$ 低），存储与检索成本由失败侧主导。这一项在单题预算里几乎不可见，在规模预算里却是常数级开销。

五 · 中小团队的真实预算怎么排

给定一个固定预算，正确的分配顺序不是「先加采样、再加轮数」，而是先用小预算测出三个量：各级别的通过率 $p$、编译时间 $t_c$ 与计时时间 $t_r$ 的比值、以及执行反馈对 $p$ 的边际提升。这三个量决定了上面成本公式里哪一项主导。若 $t_c \gg k t_r$，则瓶颈在编译，应优先提高编译并发与编译缓存命中，而不是加 GPU 并发；若 $p$ 极低且反馈无效，则加采样是纯烧钱，应转向缩小任务范围或换提示策略；若 $p$ 高而 $t_r$ 主导，则加重复测量次数 $k$ 会线性推高成本，此时应固定 $k$ 并把预算投向更高难度级别的覆盖。

一个可操作的排法：把预算切成三段——探测段（小 $n$、单轮，测 $p$ 与 $t_c/t_r$）、扩展段（按探测结果定 $n$ 与 $R$，编译与 GPU 并发分开设）、复核段（失败样本分类统计，不进入性能汇总）。三段的比例由探测结果决定而非拍脑袋。代价是探测段本身要花 token 与 GPU 时，且探测结论只对当前 GPU 与编译环境成立；换卡或换 CUDA 版本后 $t_c$ 与 $t_r$ 的比例变化，探测需重做。KernelBench 以 PyTorch 为唯一基线、计时口径与硬件绑定，这一绑定在预算层面意味着探测结论不可跨设备搬运。

最后落在工程判断上：KernelBench 材料为摘要级，未给出题量、通过率与加速比数字，因此任何「每题多少钱」的绝对值都无法从论文直接读出；能读出的只有成本结构——编译失败不进入计时却照样计费、通过率缩放计时项而不缩放生成项、缓存键维度决定命中率的阶跃点。中小团队的预算表应围绕这三个结构事实搭建，把「多采样」与「多轮反馈」当作需要先用探测段验证边际收益的选项，而不是默认开启的杠杆。

规模上去以后，先崩的是编译与计时预算，不是模型能力

把 KernelBench 从几十道题扩到全量分级任务、并让 agent 做多轮生成时，最先被吃掉的资源不是 GPU 算力而是编译与评测的墙钟时间。每一份候选内核都要走「编译—运行—数值比对—计时」四段式，编译失败样本虽不进入性能统计，却仍要付出一次完整编译尝试的代价；计时环节对通过样本重复测量取中位数，意味着每道题的有效 GPU 时随候选数线性增长。设单题候选数为 k、单次编译耗时为 c、单次计时重复数为 r、单次运行耗时为 t，则单题评测成本近似为

$$C_{\text{eval}} \approx k\,c + k\,p\,r\,t,\qquad p=\Pr[\text{编译成功}\wedge\text{语义正确}]$$

其中 p 是编译与数值比对双重通过的概率，级别越高、组合复杂度越大，p 衰减越明显，于是第二项被压缩而第一项照付——这正是「编译失败单列」这一口径的系统代价：它让失败可归因，但也让搜索轮数直接乘在编译时间上。一个具体例子：端到端模型片段题里，候选内核往往需要多个 kernel 加宿主封装，编译单元变多、编译时间上升，而一旦语义比对不过，全部计时预算作废，token 花在生成上、GPU 时花在编译上、两者都不产出加速比样本。

第二个先崩的是缓存与并发的一致性。评测要求候选与 PyTorch 基线使用完全相同的输入张量、固定 GPU 与编译选项，这天然限制了并行度：多进程并发跑同一批题会争抢同一块 GPU 的计时窗口，中位数计时被邻居干扰；若为提吞吐把不同题分散到多卡，则跨设备计时口径不再可比，加速比数字失去意义。工程上的折中是缓存编译产物与参考输出：把 PyTorch 参考实现的输出张量按 (任务, shape, dtype, 种子) 做键缓存，避免重复跑基线；把编译成功的候选二进制按源码哈希缓存，跳过重复编译。缓存命中率决定实际成本，而缓存失效的代价是显存——保存参考输出与中间张量在端到端片段级别会迅速吃掉显存预算，这也是中小团队最容易低估的一项。

规模维度先崩的位置代价形态
候选数 k 上升编译墙钟编译时间线性增长，GPU 空转
难度级别上升通过率 p 衰减计时预算浪费，样本稀疏
并发评测计时可比性中位数受干扰，跨卡不可比
参考输出缓存显存端到端片段张量驻留

对中小团队而言，真实预算应这样切：把 token 花在「能编译」这一关上——先用低成本静态检查或单轮生成过滤明显编译不过的候选，再对幸存者做数值比对，最后才对极少数通过者做重复计时；搜索轮数不宜盲目加大，因为每多一轮就多一次编译与一次可能作废的计时。判断规模是否已越界的信号很直接：当编译时间开始超过单次运行时间、当通过样本少到中位数计时失去统计意义、当参考输出缓存挤占显存导致批量缩小，就说明该收窄任务级别或降低候选数，而不是继续堆轮数。基准以 PyTorch 为唯一基线这一点在规模扩张时更需警惕：加速比只反映相对框架基线的收益，扩大规模并不会让它逼近硬件上限，缺手写库对比时高估方法成熟度的风险随样本量放大而放大。
