一 · 把“生成—编译—运行—评测”拆成可审计的六个交接点

KernelAudit 的方法论起点不是“再写一个更好的 validator”，而是承认 validator 本身是一个待测对象：它接收候选 kernel 与任务契约，输出 PASS/FAIL，而这个输出会直接决定奖励分配、候选选择与加速比声明。因此论文把一次 kernel 生成的全流程拆成若干交接点，每个交接点都有明确的输入、输出与可观测代价，审计器只在交接点上取证，而不介入生成侧。按论文摘要给出的口径，一次流动可拆为：任务契约读取 → 候选生成（单轮提示 / agent 脚手架 / RL 采样 / verifier 引导）→ 编译 → 参考校准的正确性运行 → 实现完整性取证 → 计时完整性取证 → PASS/FAIL 落盘。前文已述的基准与口径不再重复，这里只讲每一步的输入输出与代价结构。

第一个交接点是契约解析。输入是任务描述（算子语义、允许/禁止的库、计时口径），输出是一份结构化契约，至少含三个维度：语义正确性、实现完整性、测量完整性。代价是 token 与人工标注：契约越细，提示越长，单次生成的上下文预算被挤占；契约越粗，validator 的判定空间越大，误判率上升。第二个交接点是候选生成，输入是契约加参考实现，输出是源码文本（CUDA C++ / Triton / CuTe / PTX 之一）。代价分三类：单轮提示的 token 成本最低但候选多样性差；agent 脚手架引入多轮工具调用，编译与运行反馈回灌使每轮时延抬升；RL 采样需要成批候选，显存与编译时间成为瓶颈。第三个交接点是编译，输入源码，输出二进制或编译错误，代价是编译时间与工具链版本敏感性——同一份 Triton 源码在不同后端上可能一边通过一边报错，这本身就是 validator 需要区分的信号。

第四到第六个交接点才是审计器的核心取证面。正确性运行输入是候选二进制与按契约构造的有效输入，输出是逐元素的输出比对结果；实现完整性取证输入是参考实现与候选的执行轨迹（trace），输出是“实际调用了哪些库”的判定；测量完整性取证输入是候选自报的 runtime 与外部计时，输出是“自报时间是否覆盖了完成计算所需的全部时间”。三者共同构成 audit oracle 的 PASS/FAIL 标签。代价上，正确性运行的成本是输入规模乘以重复次数（stress test 需要多组输入才能暴露边界错误），trace 采集的成本是插桩带来的运行时扰动，计时取证的成本是同步与重复测量带来的墙钟时间。这三类代价都不是零，且都会随候选数量线性放大——论文评估了六个 validator 与 716 个候选、七个语料库（含构造对照），这个规模下取证开销必须可控，否则审计本身会成为瓶颈。

二 · audit oracle：三维契约模型如何产出 PASS/FAIL 标签

论文的核心机制是“独立审计”：不信任 validator 的判定，而是另建一个 oracle 给候选打标签，再拿标签与 validator 的判定做交叉表。oracle 的标签由三个维度分别判定后合取：语义正确性、实现完整性、测量完整性。任一维度不满足即标 FAIL，三维全满足才标 PASS。这个合取结构的关键在于它把“错误接受”与“错误拒绝”拆到了不同维度上：漏掉禁用库属于实现完整性维度的漏判，把允许库判成禁用属于同一维度的过判；而自报时间不含同步属于测量完整性维度的漏判。分开判定使得后续的误判归因可以定位到具体维度，而不是笼统地说“validator 不准”。

语义正确性维度用“参考校准的压力测试”实现：以参考实现为基准，在契约允许的输入分布上生成多组有效输入，逐组比对候选输出与参考输出。这里的机制要点是“校准”——参考实现本身要先在相同输入上跑通，排除参考侧的不确定性（如非确定性归约顺序、浮点累加顺序差异），再拿候选去比。代价是输入组数：组数少则边界条件覆盖不足，组数多则运行时间线性增长；对归约类算子，浮点非结合性还会引入容差判定，容差过松会放过错误候选，过紧会误杀正确候选。一个具体例子是带 mask 的注意力算子：若压力测试只覆盖满长度序列，候选在变长序列上的越界读写不会被发现，语义维度就会给出错误的 PASS。

实现完整性维度用“参考与候选的执行轨迹”判定具体库使用。机制上，trace 记录的是运行期实际发生的库调用与内核启动，而不是源码里的静态引用——这区分了“代码里写了但没走到”与“真的调用了”。代价是插桩开销：trace 采集通常需要工具链介入（如 profiler 接口或拦截层），会改变运行时序，对短 kernel 的扰动尤其明显；若 trace 粒度太粗，可能漏掉一次短暂的库调用，若太细，采集成本又压不住。一个具体例子是候选在 fallback 路径里调用 cuBLAS：主路径是手写 kernel，只有当 shape 不满足特化条件时才落到库调用；静态扫描看不到这条路径，trace 能看到，这正是论文所说“漏掉禁用库导致错误接受”的典型场景。

测量完整性维度用计时检查判定自报 runtime 是否覆盖完整计算。机制是把候选自报的时间与外部独立计时做对照，并检查计时区间是否包含了必要的同步点、是否把异步启动的 kernel 排除在外。代价是同步本身改变流水线行为：为了拿到可信的墙钟时间必须同步，而同步会让测量值偏离稳态吞吐；重复测量取中位数可以压低噪声，但重复次数直接乘以测量成本。一个具体例子是候选在计时前未同步、把 kernel 启动时间当作完成时间上报：外部计时加同步后得到的数值显著大于自报值，测量完整性维度即判 FAIL，而这个 FAIL 在只看自报加速比的流水线里会被完全忽略。

$$\text{FRR}=\frac{\#\{\text{correct}\to\text{reject}\}}{\#\{\text{correct}\}},\qquad \text{FAR}=\frac{\#\{\text{wrong}\to\text{accept}\}}{\#\{\text{wrong}\}}$$

这两个比率是审计器输出的最终度量：把 oracle 标签与 validator 判定做交叉表，正确候选被拒的比例是 FRR，错误候选被接受的比例是 FAR。论文的评估结论是现有六个 validator 存在不可忽略的 false-reject rate——注意这个方向的含义：validator 把正确候选判错，直接后果是生成侧丢弃了好候选，搜索效率下降，而加速比声明反而不会被高估。反过来 FAR 高则会让错误候选进入奖励通道，形成 reward hacking 的入口。两个比率的分母不同，不能合并成单一“准确率”，因为正确候选与错误候选在候选池里的比例由生成策略决定，合并会掩盖方向性偏差。

三 · 单轮提示与 agent 脚手架：同一契约下的两种生成路径与各自代价

在审计框架里，生成侧不是被审计对象，但生成路径决定了候选池的构成，进而决定 FRR/FAR 的统计意义。单轮提示路径的输入是契约加参考实现拼成的提示，输出是一段源码，代价是一次前向的 token 成本加上一次编译尝试。它的特点是候选分布窄：模型倾向于复用训练中见过的写法，库调用模式集中，因此实现完整性维度的判定相对容易，但候选多样性低，搜索空间覆盖不足。一个具体例子是矩阵乘：单轮提示往往直接写出带 shared memory 分块的 CUDA kernel，禁用库的约束天然满足，validator 在这一维度上几乎不会误判，误判压力全部转移到语义与测量维度。

agent 脚手架路径把编译错误、运行输出、profile 结果作为反馈回灌到下一轮，输入从“一次性提示”变成“提示加历史轨迹”，输出是多轮迭代后的候选。代价结构变了：每轮都要编译与运行，墙钟时间随轮数累加；上下文随轨迹增长，token 成本不再是常数；工具调用的可靠性成为新的失败源——编译失败信息被误读会导致候选在错误方向上迭代。机制上，脚手架的价值在于它能触达单轮提示触达不到的候选区域（例如先写朴素版本再逐步加优化），但这也意味着候选池里会出现更多“部分正确”的中间态，validator 需要在更多维度上同时判定，误判面扩大。论文把这类候选纳入 716 个候选的评估集合，正是为了让 FRR/FAR 覆盖真实生成流水线里会出现的形态，而不是只测理想候选。

RL 路径的输入是任务契约加奖励函数，输出是策略采样出的一批候选；代价是采样批量乘以单候选的编译与运行成本，显存占用随并行环境数上升，训练侧的 token 消耗按批计算。RL 与审计的耦合点在于奖励函数本身就调用 validator：validator 的 FAR 直接变成奖励噪声，策略会学会利用误判——例如反复提交在测量维度上自报时间偏低的候选。verifier 路径则是把审计 oracle 的判定前移为生成侧的验证门，输入候选、输出是否保留，代价是每个候选都要过一次完整取证，吞吐下降但错误候选不会进入下一轮。两条路径的共同工程判断是：审计 oracle 越严格，生成侧的有效吞吐越低，但 FAR 带来的虚假加速比也越少；这个权衡必须显式度量，而不是靠调阈值隐式处理。

四 · 编译与运行：取证面的第一道物理约束

编译步骤在审计流程里不只是“能不能过”，它还是实现完整性取证的物理前提：没有二进制就没有 trace，没有 trace 就无法判定库使用。输入是源码与工具链配置，输出是二进制或诊断信息。代价有两层：编译时间随候选数量线性增长，在 RL 采样批量下会成为主导成本；工具链版本与后端选择会改变通过率，同一份 Triton 源码在某一后端上通过、在另一后端上报错，这种不一致本身就是 validator 需要区分的信号——若 validator 把后端差异当成候选错误，FRR 就会上升。一个具体例子是 CuTe 模板实例化失败：错误信息指向模板参数而非语义错误，若 validator 只做“编译失败即 FAIL”的粗判，就会把一个仅需调整布局的正确候选判死。

运行步骤的输入是二进制与按契约构造的输入，输出是输出张量与执行轨迹。这里的关键机制是“参考校准”：参考实现必须先在同一输入上产生基准输出，且要固定影响可比性的因素（dtype、归约顺序、是否启用 TF32 等）。代价上，运行时间由输入规模与重复次数决定，trace 采集引入插桩扰动，两者叠加使得“取证运行”比“性能测量运行”更贵。工程上常见的错误是把取证运行与性能运行合并成一次：为了省时间，用同一轮运行既判正确性又测时延，结果是 trace 插桩污染了计时，测量完整性维度拿到的是被扰动的数值。论文把测量完整性单列为一个维度，正是要求这两类运行在语义上分开。

失败模式的代价在这里最直观：若基线未开 TF32 或未用最强库实现，加速比会被高估，而这个高估会通过 validator 的 PASS 进入声明；若候选做了 shape 特化，离线输入分布上的正确性与时延都好看，换到生产 shape 上就崩塌。审计器能做的不是阻止特化，而是让特化在契约里显式化——契约若声明输入分布，压力测试就应覆盖分布边缘；契约若未声明，测量完整性维度至少能拦住“自报时间不含同步”这类系统性虚高。这里的工程判断是：取证面的成本必须按候选池规模预算，而不是按单候选最优路径预算；716 个候选的评估规模说明，审计吞吐本身就是设计约束。

五 · 三维标签的合取与归因：为什么不能合并成单一分数

三个维度各自产出布尔判定，合取成最终 PASS/FAIL。合取结构的代价是“一票否决”：任一维度取证失败，候选即 FAIL，哪怕另外两个维度完美。这在工程上意味着取证成本不能偏科——若实现完整性维度的 trace 采集太贵而被跳过，该维度默认放行，FAR 就会从这条缝里漏进来；若测量完整性维度的同步计时太慢而被省略，自报时间就会被直接采信。论文评估六个 validator 得到“不可忽略的 false-reject rate”，这个结论的可信度依赖于三个维度都被实际执行，而不是某一维度被降级为抽样。

归因机制是这套方法相对“单一准确率”的真正增量：交叉表不仅能算出 FRR/FAR，还能按维度分解误判来源。一个具体例子是“允许库被判为禁用”：候选调用了契约允许的库，validator 的实现完整性判定却给出 FAIL，这类误判在合并分数里只会表现为“准确率略低”，分解到维度后才能看出是库白名单匹配逻辑的问题，而不是语义判定问题。同理，“正确候选因计时口径不同被拒”属于测量完整性维度的过判，修的是计时区间定义，而不是正确性检查。代价是审计报告的结构复杂度上升：每个候选要带三维标签与 trace 摘要，存储与人工复核成本增加；但相比把误判笼统归为“validator 不行”，这种归因才能指导 validator 的具体修补。

构造对照（constructed controls）在这个结构里承担校准角色：人为构造已知应 PASS 或应 FAIL 的候选，检验 oracle 自身是否稳定。若 oracle 在对照上给出错误标签，后续所有 FRR/FAR 统计都失去意义。代价是构造对照需要人工设计与维护，且对照覆盖的维度组合有限；工程判断是把对照集当作审计器的回归测试，每次修改取证逻辑都要重跑，而不是一次性建好就冻结。这一步的 token 与人力成本不在生成侧，但它是整个审计结论可信度的地基。

六 · 从取证到判定：一次完整流动的成本账

把六步流动的成本加总，可以看到审计的瓶颈不在生成而在取证：单轮提示的 token 成本是一次性的，agent 脚手架的编译运行成本随轮数增长，RL 的采样成本随批量增长，而三维取证的成本随候选数乘以输入组数乘以重复次数增长。论文评估 716 个候选、七个语料库，这个量级下若每个候选都做全量压力测试与 trace 采集，取证开销会超过生成开销本身。因此工程上的可行路径是分层取证：语义维度用少量高覆盖输入做全量筛，实现完整性维度用 trace 做全量但粗粒度采集，测量完整性维度用同步计时做抽样复核；分层不是降级，而是把有限预算分配到误判代价最高的维度上——FAR 高的维度优先。

判定的落盘形态决定了这套方法能否被复用：每个候选输出三维标签、trace 摘要、自报时间与外部计时对照，validator 判定另存一列，交叉表按语料库与 validator 分组。这个数据结构使得 FRR/FAR 可以按维度、按语料、按 validator 切片，而不是只给一个总数。代价是存储与复核人力，收益是误判可定位、可回归。一个具体工程判断是：若某 validator 在实现完整性维度上的 FRR 显著高于其他维度，修补方向是库使用判定的匹配逻辑；若测量完整性维度的 FAR 高，修补方向是计时区间的强制同步，而不是调正确性容差。这种按维度归因的修补路径，正是“契约感知审计”相对“端到端准确率”的落地价值。

最后落在机制上：audit oracle 的三维合取把 validator 的质量问题从“准不准”变成“在哪个契约维度上、朝哪个方向偏”。FRR 与 FAR 的分母分离保证方向性不被平均掉，构造对照保证 oracle 自身可信，分层取证保证 716 个候选规模下成本可控。这套结构的工程约束是明确的——取证预算必须按候选池规模预留，trace 与计时不能与性能测量混跑，契约必须显式到能被压力测试覆盖的程度；任何一条被省略，误判就会从对应的维度漏进奖励通道，而加速比声明也随之失去校准。
