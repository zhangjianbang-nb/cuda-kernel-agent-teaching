一 · 从一次线上推理的算子替换说起

设想一个已经上线的推理服务：模型里有一段 attention 前的归一化加残差，PyTorch 版本由三个算子拼成，每个算子各自一趟读写显存。端到端 P99 时延卡在预算边缘，工程团队决定把这三步融成一个自定义 kernel。任务被派给一位熟悉 CUDA 的工程师，接下来发生的事，恰好概括了这篇论文之前 GPU kernel 工程的全部痛点。

他先写 CUDA C++：手写 grid/block 维度、用 __shared__ 做块内归约、处理边界与对齐、为半精度和单精度各写一份模板。编译通过只是第一步，随后是数值比对——归约顺序改变会带来浮点误差，容差定得过紧会误判、过松会放过语义错误。再之后是调优：block size 从 128 试到 1024，向量化宽度从 4 试到 8，寄存器压力一上来 occupancy 就掉，NCU 里 stall 原因从 memory throttle 变成 barrier。一个看似简单的融合算子，从接需求到能进生产，周期以周计；而它换来的收益，可能只是端到端几个百分点的时延。这就是非改不可的现场：需求侧要求算子级定制越来越频繁，供给侧的手工产能与验证成本却几乎不变。

更麻烦的是，这条路径上的每一个环节都缺少统一口径。工程师说“快了 1.4 倍”，指的是相对哪个基线、在哪个 shape 上、用什么计时方式、容差多少——这些都没有共识。于是同一个优化，在不同团队的报告里可以是 1.1 倍也可以是 2 倍，而没人能判断差异来自实现质量还是口径差异。这正是 KernelBench 要解决的问题现场：不是没有人会写 kernel，而是写 kernel 这件事的产出无法被可信地度量。

二 · 三条旧路径各自的性能上限与代价

论文之前，主流做法可以归为三类，它们的痛点并不相同。

第一类是手写 CUDA C++。它给出的是性能上限：工程师可以精确控制共享内存布局、寄存器分配、warp 内 shuffle 归约、异步拷贝流水，理论上能逼近硬件的 roofline 拐点。代价是开发周期与可维护性。一个算子要为多种 dtype、多种 shape 分支、多种架构（sm 版本差异）分别调优，代码量迅速膨胀；一旦上游模型结构改动，这些手写分支就成为技术债。正确性上，浮点归约顺序、边界条件、未定义行为（如越界读被编译器优化掉）都是隐蔽的错误源，且缺乏系统性的 oracle 比对流程。

第二类是 Triton。它把 block 级编程抽象成 tile 上的向量运算，开发者写的是“一个 program 处理一块数据”的逻辑，编译器负责布局与流水。开发周期显著短于 CUDA，可维护性也好，但性能上限受制于编译器：自动生成的流水与布局在部分模式（如非规则访存、复杂归约、特殊数据复用）上打不到手写水平，遇到编译器不擅长的结构时，开发者能调的旋钮有限。正确性方面 Triton 的语义更接近张量运算，出错概率低，但一旦出错，调试信息（IR 层）对普通工程师并不友好。

第三类是直接调用库：cuBLAS、cuDNN、CUTLASS 模板库，或框架自带的融合算子。这是最省事的路径，正确性由厂商保证，性能在标准 shape 上通常很强。痛点在于覆盖面：库只覆盖它认为值得优化的形态，长尾 shape、特殊 dtype 组合、自定义算子语义都落在覆盖之外；而库的调用边界往往强制物化中间结果，无法做跨算子的融合，于是显存带宽被反复消耗。一个典型例子是“归一化 + 残差 + 量化”这种三段式，库能分别提供每一段，但融合起来的那一趟读写省不下来。

路径性能上限主要代价典型失效场景
手写 CUDA C++接近硬件 roofline开发周期以周计，多 dtype/shape 分支导致维护成本高上游结构改动后分支失配；浮点归约顺序引发数值偏差
Triton受编译器流水与布局能力约束调优旋钮有限，IR 层调试门槛高非规则访存、复杂归约打不到手写水平
库调用标准 shape 上很强覆盖面窄，调用边界强制物化中间结果长尾 shape、自定义语义、跨算子融合缺失

三条路径共享一个结构性缺陷：它们都没有把“写得对”和“写得快”拆成可分别统计的量。手写路径的正确性靠人工 review 与零散测试，Triton 路径靠框架层测试，库路径靠厂商背书；性能则各自用各自的基线报数。当有人提出“让 LLM 来写 kernel”时，第一个问题立刻暴露：拿什么证明它写的东西是对的、快的、且与别人的结果可比？没有这个口径，任何生成方法都无法被严肃评估。

三 · 开发周期里的隐性成本：验证与调优占了大头

把开发周期拆开看，编码本身往往不是最耗时的部分。以一个融合算子为例，粗略的阶段划分是：语义确认与参考实现、首版 kernel 编写、编译与数值调试、性能调优、回归与上线。其中后三段占据大部分工时，且高度依赖专家经验。

数值调试的成本来自浮点语义的微妙性。GPU 上的归约是树形的，不同 block 划分会改变求和顺序，进而改变舍入误差的累积路径。判定“算对了”需要定义容差：逐元素无穷范数误差小于阈值。写成公式即

$$\text{Pass}=\mathbb{1}\left[\lVert y_{\text{kernel}}-y_{\text{ref}}\rVert_{\infty}\le \varepsilon\right]$$

这个看似简单的判据在实践中极难拿捏。ε 取太紧，合法的重排会被判错；取太松，真实的语义 bug（如漏加一项、索引偏移）会被放过。更关键的是，容差必须与输入分布绑定：同一 kernel 在数值范围大的输入上误差被放大，在小范围输入上又显得很准。没有统一的输入生成与容差约定，正确性结论无法跨实现比较。

调优的成本则来自搜索空间的组合爆炸。block size、每线程元素数、向量化宽度、共享内存分块、流水深度，这些旋钮相互耦合，且最优点随 shape 与 dtype 漂移。工程师靠 NCU 采集 stall 原因、DRAM 吞吐、occupancy，再凭经验改一版、重测一轮。一轮编译加测量的时延在分钟量级，一天能试的次数有限。这就是为什么“性能上限”在纸面上很高，实际交付却常常只拿到其中一部分：不是不知道更好的写法，而是没有足够预算去找到并验证它。

可维护性是第三种隐性成本。手写 kernel 一旦为多个 shape 分支特化，就形成了一张难以测试覆盖的组合网；新架构上线时，旧分支的调优参数全部失效。团队于是倾向于“能不动就不动”，这反过来抑制了算子级优化的意愿。三者叠加，构成了 LLM 介入前的真实约束：不是缺想法，是缺一条把想法快速、可信地变成可比较结果的流水线。

四 · 为什么“能跑”与“跑得快”必须分开度量

在旧做法里，一个 kernel 的失败往往被笼统地记为“不行”。但失败其实有三种截然不同的来源，处理方式完全不同。

  • 编译失败：语法、类型、架构不匹配、宿主调用封装缺失。这类失败是二元的，且往往暴露生成侧对工具链约束的无知。
  • 语义错误：能编译能跑，但输出与参考实现超出容差。来源可能是索引、边界、归约逻辑、dtype 转换。
  • 性能不达标：正确但慢于基线，说明实现没有利用好访存或并行度。

把三者混在一起统计，会得到无信息量的结论。一个方法报“通过率 40%”，无法判断它是编译不过、算不对、还是算对了但没加速。更糟的是，若只报加速比而把失败样本剔除，分布会被系统性高估：快的样本被留下，慢的和错的被静默丢弃。因此评测口径必须把编译成功率单列，并且只对通过数值比对的样本计时，让加速比的定义域明确。

加速比本身的定义是

$$\text{Speedup}=\frac{T_{\text{pytorch}}}{T_{\text{kernel}}}$$

其中分母只对通过正确性检查的候选计算，未通过者不进入性能统计。这个约束看似技术细节，实则是评测可信度的基石：它把“正确性”设为“性能”的门槛，避免用错误但飞快的 kernel 拉高均值。同时它要求候选与基线使用完全相同的输入张量，否则计时比较失去意义——不同 shape 下的耗时不可比，这是旧做法里最常见的口径漏洞。

一个具体例子能说明分开度量的价值：某候选在单算子任务上编译成功、数值通过、加速比高于 1；换到算子序列任务，编译仍成功，但中间结果的 dtype 提升导致数值超出容差，于是被计为语义错误而非性能失败。若只看“是否加速”，这个样本会被误读为“该方法在序列任务上性能退化”，而真实原因是语义。三类失败模式分开统计，才能把改进方向指向正确的地方。

五 · 旧方案无法回答的问题：跨方法可比性

即便每个团队都认真做了正确性验证与性能测量，旧方案仍有一个无法自解的问题：结果之间不可比。原因有四层。

其一是基线不统一。有人相对 PyTorch eager 计时，有人相对 TorchScript，有人相对某个已融合的库调用。基线不同，加速比的含义就不同。其二是输入分布不统一。kernel 的性能强烈依赖 shape 与 dtype，若各自挑选有利的 shape，数字自然好看。其三是计时口径不统一。是否 warmup、是否同步、取均值还是中位数、是否包含宿主侧开销，都会显著改变结果。其四是容差与失败处理不统一。有人把编译失败算作零分，有人直接剔除，汇总方式不同导致通过率不可比。

这四层不统一，使得“LLM 能写高效 kernel”这类主张在论文之前无法被严肃检验。一个方法可以在自选任务、自选基线、自选 shape 上展示漂亮的加速比，而另一个方法在另一套设定下展示相反的结论，双方都无法证伪对方。这不是方法本身的问题，是度量基础设施缺失的问题。

从工程角度看，缺失的正是三样东西：一套按难度分级的任务集合，使能力可以被分层观察；一个同时充当语义 oracle 与性能基线的参考实现，使正确性与加速比在同一输入上计算；一套把编译、运行、比对、计时串起来并统一报告的评测执行流程。KernelBench 的核心贡献就是把这三样东西固定下来，让“能编译”“算得对”“跑得快”成为三个可分别统计的口径。这也解释了为什么它的定位是评测基准而非生成方法：在度量可信之前，任何优化主张都缺少落脚点。

代价同样明确。以 PyTorch 为唯一基线，意味着加速比只反映相对框架的收益，不能解读为接近硬件上限——手写库或厂商内核的上限没有被纳入对比，方法成熟度容易被高估。输入 shape 与 dtype 由基准规定，真实负载的长尾未必被覆盖，迁移时通过率与加速比需要重新校准。计时与硬件绑定，跨设备比较需额外约定。这些都是后续方法必须正视的边界，而不是可以被加速比数字掩盖的细节。

六 · 工程判断落在哪一层

把旧方案的痛点归拢，会发现它们并非彼此独立：开发周期长，是因为验证与调优缺少自动化反馈；性能上限拿不到，是因为搜索预算被编译与测量的时延吃掉；正确性难保证，是因为容差与输入分布没有统一约定；可维护性差，是因为每个 shape 分支都要独立调优与测试。四者共同指向同一个缺口——一条把“生成候选、编译、数值比对、计时、汇总”串成闭环且口径固定的流水线。

这条流水线的关键设计选择，是把正确性判定放在计时之前，并且把编译失败单列为一种结果而非异常。用伪代码表达其控制流：

  • 读取任务语义与规定的输入 shape、dtype 分布；
  • 生成候选 kernel 及宿主调用封装；
  • 在固定 GPU 与编译选项下编译，失败则记录错误类型并终止该样本；
  • 用与参考实现相同的输入张量运行，逐元素比对，超容差判语义错误并终止；
  • 通过者重复计时取中位数，除以 PyTorch 基线耗时得到加速比；
  • 样本以「编译成功、语义正确、加速比」三元组进入汇总。

这个控制流本身就是一种工程判断：它承认失败是常态且分类型，承认性能只在正确的前提下才有意义，承认单次测量的噪声需要用重复取中位数压制。它的代价是把评测变成一个有状态、有环境依赖的过程——编译时间、GPU 占用、容差取值都成为影响结果的因素，而这些在材料中并未完全固定，跨设备复现需要自行约定。这正是后续 agent 脚手架与执行反馈方法要在此起跑线上继续解决的问题：基准给出了口径，但没有给出如何高效地在这个口径下搜索。
