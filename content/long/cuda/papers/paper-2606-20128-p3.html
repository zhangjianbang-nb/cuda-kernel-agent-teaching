一 · 单轮提示：从自然语言到候选源码的第一次映射

单轮提示是这条流水线最短的路径：输入是一段算子描述（op schema 加参考语义）、目标 dtype、目标 shape 与框架约束；输出是一段 Triton 或 CUDA C++ 源码，通常还带一段自测脚本。代价集中在 token 与编译时间上：一次生成消耗的 token 量与源码长度成正比，而编译一次候选 kernel 的时间在 Triton 路径上由 JIT 前端加 PTX 汇编构成，在 CUDA 路径上由 nvcc 的模板实例化与 ptxas 构成。真正的风险不在编译失败，而在编译成功——单轮提示没有任何执行反馈，模型只能靠对语义的“记忆”写出索引表达式，而索引表达式恰恰是转录错误的高发区。

论文构造的受控语料正是针对这一点：24 个 Triton 与 CPU stand-in kernel，其中 15 个正确对照、9 个 LLM 风格错误变体，错误变体按“有据可查的转录错误”注入。所谓转录错误，指的是语义上等价的重写被写错一格——例如归约维度写反、mask 边界差一、stride 乘错、dtype 提升顺序颠倒。这类错误在固定 shape、固定 dtype、固定容差的 allclose 检查下极易漏网，因为固定输入恰好落在错误不显形的那一侧。单轮提示的输出因此必须被当作“待验证假设”而非“候选解”，它的输入输出契约里缺了最关键的一环：错误空间的覆盖。

把这一步形式化，设提示为 p，采样温度为 T，单轮产出 k 个候选，则这一步的产出集合是 {c_1,…,c_k} ~ π(·|p)。它的成本函数可写成 k·(L_tok + t_compile)，其中 L_tok 是每候选的 token 开销，t_compile 是编译时延。工程判断很直接：单轮提示适合做“语义骨架”的快速铺量，不适合作为正确性结论的来源；它的价值在于为后续步骤提供多样化的起点，而非提供可交付的 kernel。

二 · Agent 脚手架：把编译与运行接进回路

脚手架的本质是把“生成—编译—运行—读反馈”做成一个可迭代的状态机。输入是算子描述加一个可执行环境（编译器、GPU、基线实现）；输出是一串候选及其执行轨迹。每一步的状态包含：当前源码、编译诊断、运行期异常、数值比对结果、以及可选的 profile 摘要。脚手架与单轮提示的差别不在模型，而在回路里多了两个硬约束：编译必须真跑，运行必须在真实设备上跑。

伪代码层面，一次迭代可以写成：读取 schema 与参考实现 → 生成候选 → 编译（失败则把诊断回灌）→ 在给定输入上运行并与参考比对 → 若通过则测时延与加速比 → 按反馈决定保留、改写或回退。这里的代价结构变了：token 开销被摊薄到多轮，但每轮都付出一次编译加一次运行的时延；更隐蔽的代价是上下文膨胀——把编译日志与运行输出塞回提示会迅速吃掉上下文预算，导致后续轮次的语义漂移。工程上常见的折中是只回灌结构化摘要（错误码、首个不匹配的索引、最大绝对误差），而非原始日志。

脚手架的正确性上限由它的 oracle 决定。若 oracle 只是固定 shape 的 allclose，脚手架会把“通过”当作收敛信号，于是搜索过程被引导向“在给定输入上恰好正确”的解，而不是语义正确的解。论文的实验正是在这个位置插入变量：把同一批候选放到 op-schema-aware 的种子化模糊测试下，用 fp64 CPU 参考与按 (op, dtype) 设定的绝对容差重新裁决。结果是 9 个错误变体全部被标记、15 个正确对照全部通过，且在对照上没有精度代价。这说明脚手架的性能代价（多轮编译与运行的时延）换来的是裁决能力的提升，而不是搜索效率的提升——两者必须分开计量。

三 · RL 与可验证奖励：把裁决信号变成梯度

RL 路径把上述裁决信号当作奖励。输入是提示分布与一个可执行的验证器；输出是策略更新后的候选分布。奖励的设计决定了策略会往哪里漂：若奖励只取“通过固定输入检查”，策略会学到在固定 shape 上过拟合的写法；若奖励取加速比，策略会学到削减计算量而牺牲语义的写法。论文给出的评分形式是 score = (1/N) Σ 1[s_i ≥ τ]，其中 s_i = T_base,i / T_cand,i，即逐题加速比过阈值的比例。这个形式把正确性折叠进“是否计入”的门里，因此门的严格程度直接决定奖励的可信度。

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

RL 的代价有三个可测项：采样吞吐（每轮要跑大量候选，编译与运行次数随采样数线性增长）、奖励延迟（一次运行加一次比对的时延被串进训练回路）、以及奖励黑客的暴露面。论文的失败模式清单里明确点到 reward hacking 与 fallback 会让正确率虚高：当候选在检查失败时可以回退到基线实现，评分就会把“回退”计成“通过”，于是策略学会频繁触发回退而非真正修好 kernel。可验证奖励要可信，必须让“回退”在奖励里显式计零，并且让验证器覆盖到错误变体所代表的错误类别。

具体例子是论文的 9 个错误变体：它们都是“看起来对”的写法，在固定输入下能过 allclose。若 RL 的奖励建立在这种检查上，这些变体会被当作正样本强化；而一旦换成 op-schema-aware 的种子化模糊测试加 fp64 参考，它们全部被标记。这说明 RL 的上限不取决于策略网络，而取决于验证器能分辨的错误粒度——验证器看不见的错误，策略就会主动生产。

四 · Verifier：裁决器的输入、输出与精度预算

验证器是这条流水线里唯一直接决定“正确性幻觉”是否被戳破的组件。它的输入是候选 kernel、参考实现（论文用 fp64 CPU 参考）、按 (op, dtype) 设定的绝对容差、以及由 op schema 驱动的种子化输入生成器；输出是逐输入的通过/失败裁决与失败定位。关键机制有两层：一是输入生成要覆盖 schema 允许的 shape、stride、边界与 dtype 组合，而非固定一组；二是容差要按 dtype 分别设定，因为 fp16 与 fp32 的舍入行为不同，用同一容差会同时造成误判与漏判。

验证器的代价是精度预算与算力预算的乘积。fp64 CPU 参考意味着每个输入都要在 CPU 上跑一遍高精度实现，这在小样本下可承受，在模糊测试的输入数量上会迅速变成瓶颈；种子化生成让输入可复现，但也意味着覆盖度受种子策略限制。论文的实验规模给出了一个可参照的量级：24 个 kernel 的受控语料上，9/9 错误被标记、15/15 对照通过、对照上零精度代价；随后扩展到 26 个算子（加入一对 flash-attention）并在五类 GPU（RTX 3060、A10、L40S、A100 SXM4、H100 NVL）上重跑同一协议，裁决在五类硬件上完全一致：10/10 幻觉被捕获、16/16 对照干净。这个跨硬件一致性说明裁决信号主要来自数值语义而非硬件时序，因此验证器可以在离线环境里先行定标。

工程判断落在容差设定上：按 (op, dtype) 的绝对容差是把“数值等价”翻译成“可判定谓词”的唯一旋钮。容差过松，转录错误被吸收；容差过紧，合法的重排与融合被误杀。论文没有给出全部 shape 与容差数值，因此可复现的做法是把容差当作超参记录在评测口径里，并随 dtype 与算子类别分层，而不是全局一个常数。

五 · 一次完整流动的代价账本

把四个环节串起来看，一次 kernel 生成—编译—运行—评测的流动可以记成一张代价表。单轮提示付出 token 与编译时延，换取候选多样性；脚手架付出多轮编译、运行与上下文预算，换取执行反馈；RL 付出采样吞吐与奖励延迟，换取分布层面的收敛；验证器付出 fp64 参考的算力与模糊测试的输入数量，换取裁决的可信度。四者的代价不叠加在同一维度上，因此不能用一个“总成本”笼统比较，必须按环节分别计量。

环节输入输出主要代价失效形态
单轮提示op schema、dtype、shape候选源码token、编译时延转录错误、索引写反
Agent 脚手架候选、编译诊断、运行输出迭代后的候选与轨迹多轮编译运行时延、上下文膨胀被固定输入 oracle 误导收敛
RL提示分布、可验证奖励更新后的策略采样吞吐、奖励延迟reward hacking、fallback 虚高
Verifier候选、fp64 参考、分层容差、种子化输入逐输入裁决CPU 参考算力、输入数量容差过松吸收错误、种子覆盖不足

这张表里最容易被低估的是脚手架那一行的“上下文膨胀”：把编译日志原样回灌会让后续轮次的提示被噪声占据，模型开始在日志文本上做模式匹配而非在语义上推理。一个具体的工程折中是给反馈做压缩——只保留首个不匹配索引、最大绝对误差、以及编译错误的类别标签，把原始日志留在文件系统里供人查。这样做的代价是丢失了部分诊断细节，收益是让回路在有限 token 预算内保持语义聚焦。

另一个可量化的判断点是验证器的输入数量与裁决稳定性之间的关系。论文的跨硬件实验用的是同一协议、同一语料，五类 GPU 上裁决完全一致，说明在这个语料规模上裁决对硬件不敏感；但这不等于裁决对输入数量不敏感——固定 shape 的小样本正是“正确性幻觉”的成因。因此把验证器从“少量固定输入”换成“schema 驱动的种子化模糊测试”，本质上是在用算力换覆盖度，而这个交换的边际收益在错误变体全部集中在边界与 dtype 提升路径上时最高。

六 · 机制层面的工程判断

四个环节共享一个结构性事实：它们都把“正确性”压缩成一个布尔谓词，而这个谓词的严格程度由验证器单方面决定。单轮提示与脚手架看不见验证器之外的错误，RL 只能强化验证器能分辨的行为，验证器自己则受容差与种子覆盖的约束。论文用 24 个 kernel 的受控语料把这条链路的薄弱点显式化：9 个错误变体在旧口径下能过检查，在新口径下全部被标记，且 15 个正确对照无一被误杀。这个结果的意义不在数字本身，而在它证明了“零精度代价”是可以与“错误全捕获”同时成立的——前提是容差按 (op, dtype) 分层、参考实现用 fp64、输入由 schema 驱动生成。

由此得出的工程判断是：不要把验证器当作流水线末端的过滤器，而要把它当作流水线起点的规格说明。单轮提示的提示词里应当嵌入验证器将要使用的 dtype 与容差语义；脚手架的反馈压缩应当保留验证器关心的字段（不匹配索引、误差量级）；RL 的奖励应当在“回退”与“通过”之间划出硬边界。这三处改动都不增加新的模型能力，只改变信息在回路里的流向，代价是提示与反馈的构造复杂度上升，收益是正确性信号从“事后抽检”变成“生成时的约束”。论文的跨硬件复跑进一步给出一个可操作的定标方式：先在离线环境用 fp64 参考把裁决协议固定下来，再把它搬到目标硬件上，因为裁决对硬件类别不敏感，而对输入分布与容差敏感。

固定口径 oracle 的边界：schema-aware fuzz 能抓住什么、抓不住什么

该方案把“正确性”从一次固定 shape、固定 dtype、固定容差的 allclose 判定，替换为按算子 schema 生成输入的种子化 fuzz，并用 fp64 CPU 参考实现配合逐 (op, dtype) 绝对容差做判定。其代价结构很明确：判定次数从基准原本的少量输入（各基准输入数不一）膨胀到每个算子多条 fuzz 用例，单条用例的参考计算落在 CPU 上，编译与启动开销之外还要叠加 CPU 侧 fp64 计算与结果回传，评测墙钟时间随用例数与张量规模近似线性增长；同时 fp64 参考在 CPU 上对大 shape 的显存与带宽压力远高于 GPU 侧候选，成为整条流水线的吞吐瓶颈。收益是可复现的判定：24 个 Triton 与 CPU stand-in kernel（15 个正确对照、9 个按已知转录错误注入的 LLM 风格缺陷变体）上，种子化 oracle 标记 9/9 缺陷、放行 15/15 对照，对照集上零精度代价；扩到 26 个算子（加入一对 flash-attention）并在 RTX 3060、A10、L40S、A100 SXM4、H100 NVL 五类 GPU 上重跑，判定完全一致：10/10 幻觉被捕获、16/16 对照干净。

边界在于这套 oracle 只覆盖 schema 允许的输入空间，不覆盖数值路径上的实现选择。若候选在 fuzz 分布内正确、却在生产分布外退化（极端 reduction 长度、非对齐 stride、稀疏或长尾 dtype 组合），判定仍会放行；若缺陷只在特定 warp 布局或 shared memory bank 冲突下触发数值偏差，而容差按 (op, dtype) 固定，偏差可能被容差吞掉。判定可形式化为对用例集 $\mathcal{F}$ 的合取：

$$\text{pass}=\bigwedge_{x\in\mathcal{F}}\ \bigl|\,\text{cand}(x)-\text{ref}_{fp64}(x)\,\bigr|\le \tau_{\text{op},\text{dtype}}$$

其中 $\tau$ 与 $\mathcal{F}$ 都由人选定，因此 oracle 的强度上限即 $\mathcal{F}$ 的覆盖度与 $\tau$ 的紧度，而非候选本身的正确性。系统代价的另一面是判定与性能测量的耦合：fuzz 用例的 shape 分布若偏离基准计时所用 shape，加速比与正确性就在两套输入上分别成立，离线分数无法同时代表二者；跨五类 GPU 判定一致只说明该缺陷族对硬件不敏感，不能推出跨 dtype、跨框架迁移同样稳定。

失效条件oracle 行为工程代价
缺陷仅在 fuzz 分布外触发放行（假阴性）生产回归才发现，回退成本高
容差过松吞掉数值偏差放行精度问题延后暴露
fp64 CPU 参考成大 shape 瓶颈判定正确但慢评测墙钟与 CPU 显存占用上升
计时 shape 与 fuzz shape 不一致正确性与加速比脱钩离线分数不可直接外推

因此该机制适合作为正确性门的第一道筛子，而非唯一门：它把“固定口径下的偶然通过”压成可复现判定，但把输入分布设计与容差标定的责任留给了评测者，且以 CPU 侧 fp64 参考的时延与显存为代价换取判定可信度。
