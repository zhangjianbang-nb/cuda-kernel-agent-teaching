一 · 一个推理服务里的静默漂移

设想一个在线 LLM 推理服务：请求到达是泊松式的，调度器为了把 GPU 喂满，把同一时刻到达的请求拼成一个 batch 送进 kernel。同一个用户请求，第一次可能和另外 7 条请求同批执行，第二次重试时恰好只有它自己，batch size 从 8 变成 1。从服务视角看，输入 token 序列一字未改，输出 logits 理应逐位相同。但在实际系统里，这两次执行的结果并不必然一致——attention 的 softmax 归约顺序、layernorm 的均值方差计算、GEMM 的 split-K 累加树，都会随 batch 维度上并行划分方式的变化而变化。浮点加法不满足结合律，`(a+b)+c` 与 `a+(b+c)` 在 IEEE 754 下可以相差一个 ulp；当这个 ulp 落在 argmax 的边界上，贪心解码就会选出不同的 token，随后自回归地把整条序列推向另一条轨迹。这就是 batch invariance（BI）问题：kernel 对同一输入在不同 batch 上下文下给出不同的数值输出。

这个问题的工程杀伤力在于它不可见。正确性测试通常固定 shape、固定 batch，一次跑通即判定通过；性能测试只关心时延。两者都不会暴露「同一输入、不同批次、不同比特」这一维度。论文的切入点正是这里：它指出 LLM serving 系统动态组批，同一请求在不同 run 中与不同请求同批执行，若 kernel 缺乏 BI，变化的 batch 上下文会改变未变输入的数值输出，破坏可复现性。而现有的 kernel 生成 agent 只盯正确性与效率，系统性忽略了 BI。论文在 83 个可适用 batch 的已发布产物中确认了 19 个 BI 违规——这不是边角案例，而是接近四分之一的命中率。

要理解为什么这件事非改不可，得先看清这篇论文之前 GPU kernel 工程的主流做法及其代价结构。三条路径——手写 CUDA、Triton、直接调库——各自把痛点推到了不同位置，但没有一条把 BI 纳入验收口径。

二 · 手写 CUDA：性能上限最高，迭代成本也最高

手写 CUDA C++ 是性能天花板最高的路径。工程师可以直接控制 shared memory 的 bank 布局、warp 内的 shuffle 归约、寄存器压力与 occupancy 的权衡，甚至手写 PTX 内联汇编去卡住某条指令的发射。代价是开发周期以人周计：一个 fused attention 变体从设计到可上线，需要经历 tile 尺寸搜索、边界条件处理、数值稳定性验证、多架构（sm_80/sm_90）回归。更关键的是，手写代码的归约树是工程师在编码时静态决定的——他写下 `for (int offset = 16; offset > 0; offset >>= 1) val += __shfl_down_sync(...)` 的那一刻，就已经把「沿 batch 维如何切分」固化进了指令序列。若这个切分依赖 blockIdx 与 batch size 的映射关系，BI 就被无声地破坏。

性能上限的另一面是正确性维护成本。手写 kernel 的数值行为难以用单元测试覆盖：测试用例通常只覆盖少数几个 shape，而 BI 要求的是「对任意 batch 上下文组合，同一行输入的比特输出不变」。这是一个全称量化命题，枚举测试无法证伪，只能抽样。工程上常见的妥协是：只在固定 batch 下做 golden 对比，把跨 batch 的一致性交给「应该没问题」的直觉。论文确认的 19 个违规说明这种直觉不可靠。

可维护性同样被侵蚀。手写 kernel 与框架的融合逻辑（epilogue、mask、dtype 分派）耦合紧密，一次框架升级就可能要求重写。开发周期、性能上限、正确性、可维护性四者构成一个不可能三角：手写路径把前两项拉满，后两项靠人力硬扛。当模型结构与 serving 组批策略每月都在变，人力硬扛的边际成本迅速失控。

三 · Triton 与 DSL：把门槛降下来，把语义盲区留了下来

Triton 的出现改变了成本结构。工程师用块级抽象描述 kernel：`tl.load` 一个 tile、`tl.dot` 做矩阵乘、`tl.sum` 做归约，编译器负责布局推导、向量化与 shared memory 分配。开发周期从人周压到人天，性能在多数访存密集与中等规模 GEMM 上能逼近手写实现。代价是语义控制权部分让渡给编译器：归约的实现细节（是否用 warp shuffle、归约树的形状、是否跨 CTA 拆分）由编译器根据 tile 形状与 num_warps 决定，工程师看到的是 `tl.sum(x, axis=0)` 这样的声明式表达。

这恰恰是 BI 的高危区。归约轴的选择、tile 沿 batch 维的切分方式，会随输入 shape 变化而被编译器重新推导；同一个 Triton kernel 在 batch=1 与 batch=8 时可能生成不同的归约树，从而产生不同的舍入序列。工程师在源码层面看不到这个差异，只能通过跨 batch 的比特对比去观测。而 Triton 生态的测试惯例是「对 PyTorch 参考实现做 allclose 比较」，容差通常设在 1e-2 到 1e-3 量级——这个容差足以吞掉 BI 造成的 ulp 级偏差，却不足以阻止偏差在自回归解码中被放大。换言之，DSL 把开发成本降下来了，却把 BI 从「工程师可见的编码决策」变成了「编译器内部不可见的推导结果」，检测难度反而上升。

编译时间也是一项被低估的代价。Triton 的 autotune 会对每个候选配置做编译与实测，配置空间随 tile 尺寸、num_stages、num_warps 组合爆炸；在 CI 里对每个 shape 跑完整 autotune，编译与测量开销可以轻易超过 kernel 本身的运行时间。当 agent 被引入来做候选搜索时，这个开销会被放大数倍——每一轮生成的候选都要编译、都要 autotune，反馈回路的时延直接决定了搜索的迭代次数上限。

四 · 库调用：最省事，也最不可控

第三条路径是直接调 cuBLAS、cuDNN、FlashAttention 等成熟库。开发周期接近零，性能由厂商针对主流 shape 调优，正确性有厂商背书。代价是控制权完全外移：库内部是否 batch-invariant，取决于厂商的实现选择与版本。cuBLAS 的 GEMM 在不同 batch 下可能选择不同的 split-K 策略，FlashAttention 的变长序列路径会按实际 batch 内的序列长度分布选择不同 kernel 变体——这些选择对调用方不透明。工程师能做的只有「锁版本 + 固定 shape」，而 serving 系统的动态组批恰恰不允许固定 shape。

库路径的另一个代价是性能上限被锁死在通用实现上。厂商 kernel 要覆盖从 1 到数千的 batch、从 fp16 到 fp8 的 dtype、从短序列到长序列的分布，必然在某些细分场景留下空隙。这正是 kernel 生成 agent 的立足点：针对特定 shape 分布生成特化 kernel，换取超越通用库的时延。但特化本身与 BI 存在张力——特化意味着针对特定 batch 上下文做布局与归约决策，一旦该决策被固化，跨 batch 的一致性就失去保障。论文的 19/83 违规率，很大程度上就来自这种「为效率而特化、为特化而牺牲一致性」的取舍。

把三条路径放在一张表里，痛点分布就清楚了：

路径开发周期性能上限正确性风险BI 可见性主要代价
手写 CUDA人周级最高归约树静态固化，跨 batch 易漂移源码可见但需人工审计人力、多架构回归
Triton/DSL人天级接近手写编译器推导归约树，随 shape 变化源码不可见autotune 编译时间、容差掩盖

三条路径共享同一个盲点：验收口径里没有 BI 这一项。正确性门用固定 shape 的 allclose，性能门用加速比，两者都不问「同一输入换一个 batch 邻居，输出是否逐位相同」。论文的贡献正是把这个盲点变成显式的验收门。

五 · 验收口径的数学缺口

现有 agent 的优化回路可以写成这样一组判定：候选 kernel 先过正确性门，再过性能门，两门皆过则接受。用公式表达，即论文给出的接受判据：

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

其中 `pass` 是正确性检查的布尔结果，`s` 是相对基线的加速比。这个判据的缺口在于 `pass` 的定义域：它只在评测给定的输入分布上求值，而 BI 要求的是对 batch 上下文的全称量化。设输入为 `x`，batch 上下文为 `c`，BI 要求 `f(x, c₁) = f(x, c₂)` 逐位成立；而 `pass` 只检查了 `f(x, c₀)` 与参考实现的近似相等。两个命题之间隔着一整个 batch 维度。

这个缺口的工程后果是：agent 可以在完全合规的验收流程下，系统性地产出 BI 违规的 kernel。更糟的是，优化压力会主动把 agent 推向违规方向——为了压低时延，agent 倾向于做更激进的 shape 特化、更深的归约树拆分、更细的 tile 切分，而这些恰恰是破坏 BI 的手法。论文的 19 个确认违规不是 agent 的偶然失误，而是验收口径缺位下的理性产物。性能收益是显式的、可测量的，BI 损失是隐式的、不可见的，优化器自然向显式目标倾斜。

代价可以定性描述：一个 BI 违规的 kernel 在离线基准上可能拿到可观的加速比，但在生产 serving 里，它会让同一请求在重试、缓存命中、不同并发下产生不同输出，表现为「偶发的不一致回复」——这类故障难以归因到 kernel，因为单次执行的正确性检查永远通过。修复成本则落在排查上：需要在跨 batch 的比特级对比中定位漂移源，再回到归约树去改。这正是论文提出 contract-guided static dependency analysis 与 dynamic bitwise validation 的动机——把隐式的 BI 要求变成显式的、可自动执行的验收门。

六 · 为什么非改不可：组批策略与特化压力的合流

把问题放到 serving 的真实约束下，非改不可的理由就更硬。现代推理服务为了吞吐，普遍采用连续批处理（continuous batching）：每个 decode step 都重新组批，batch 的成员与大小逐 step 变化。这意味着「同一请求的 batch 上下文」不是稳定量，而是每个 step 都在变的随机量。一个缺乏 BI 的 kernel 在这样的系统里，等于把数值输出的稳定性交给了调度器的排队顺序。可复现性——这个在调试、审计、A/B 实验里被默认为前提的东西——被悄悄剥夺了。

与此同时，kernel 生成 agent 的引入放大了特化压力。agent 的搜索空间天然偏向「针对评测 shape 做极致优化」，而评测 shape 的 batch 维度往往是固定的几个值。agent 学到的策略是「在这个 batch 下最快」，而不是「在任何 batch 下都一致」。当这些产物被发布到动态组批的生产环境，特化假设立刻失效。论文在 83 个可适用 batch 的已发布产物里找到 19 个违规，说明这不是理论担忧，而是已经进入发布管线的现实缺陷。

因此，改造的方向不是放弃特化，而是在特化之上加一道一致性契约：候选 kernel 在进入性能基准之前，先过静态依赖分析与跨 batch 上下文的比特一致性动态验证；结构上有风险或动态上不一致的候选被直接拒绝，并把反馈回灌给 agent。论文把这个机制设计成通用 kernel agent 的插件式组件，复用原有优化能力，只增加 BI 强制。这解释了为什么验收门必须前置——若先测性能再查 BI，agent 已经为快而不一致的候选付出了编译与测量成本，反馈回路也被污染。前置的代价是每轮候选多一次跨 batch 的动态验证（若干次额外执行与比特比较），换来的是把 19/83 这类违规挡在基准之前；论文报告 BI 通过率从 67.6% 提升到 91.9%，同时保留 91.8% 的基线几何平均加速——一致性门不是免费的性能税，但它的成本被约束在可接受区间内。真正需要工程判断的是：这道门放在编译后、基准前的哪个位置，以及静态分析与动态验证的先后顺序如何影响反馈信息的质量。

动态批处理下的“静默数值漂移”：手写与库调用路线的边界

在一个连续批处理（continuous batching）的推理服务里，同一个请求的 prefill 或 decode 会被调度器塞进不同规模的 batch：这一轮与 7 个请求同批，下一轮可能只剩 2 个。手写 CUDA 与 Triton 的常规做法是按“当前 batch 大小”切分 tile、选择归约树形状与累加顺序，于是同一份输入在不同 batch 上下文下走出不同的浮点归约路径。设某归约链的浮点结果为 $y=\mathrm{fl}(\sum_{i} x_i)$，当分段长度 $B$ 改变时结合顺序改变，误差项 $\delta(B)$ 随之变化，最终位模式不再相等——这正是论文所指的 batch invariance（BI）缺失。其系统代价不是“算错了”，而是不可复现：同一 prompt 的 logits 位模式漂移，缓存命中、投机解码的接受率与回归测试的 golden 比对全部失效，而这类失效在单 batch 基准里完全不可见。

旧方案的三条路线各有明确的失效条件。库调用（cuBLAS/cuDNN/FlashAttention 类）把归约顺序交给启发式选择，batch 变化即换 kernel 变体，BI 由库的版本与 shape 决定，工程上不可控；手写 CUDA 能钉死归约树，但开发周期以人日计，且每换一个 dtype 或架构就要重做寄存器与共享内存的占用权衡；Triton 把周期压到小时级，代价是编译器对 tile 与 num_warps 的自动选择同样随 shape 变化，`tl.sum` 的归约顺序不由作者完全掌握。可维护性上，三者共同的债务是“正确性”只被定义为单上下文数值接近，而非跨上下文位一致。

路线BI 可控性主要代价
库调用低，随 shape 换变体版本锁定、不可解释的数值差异
手写 CUDA高，可钉死归约树开发周期长、跨架构重写

论文给出的量化现场是：83 个可批处理（batch-applicable）的已发布产物中有 19 个被确认违反 BI。这个比例说明问题不是个别实现疏忽，而是“正确性 + 效率”这一旧评价口径的结构性盲区——生成 agent 的接受判据 $\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$ 只校验单上下文通过与加速比，位一致性根本不在门内。于是优化循环会稳定地奖励那些靠 batch 特化换取速度的候选，把不可复现性当作免费收益收下，直到生产端到端回归才暴露。
