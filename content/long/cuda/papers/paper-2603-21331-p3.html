一 · 从任务描述到首版内核：决策层的输入装配

AutoKernel 的搜索循环不是从“写代码”开始，而是从“装配上下文”开始。决策层在每一轮拿到的输入由三部分拼成：任务描述（算子语义、输入输出张量形状与 dtype、参考实现或数学定义）、历史尝试记录（此前每一版内核的源码、编译输出、正确性判定、性能读数），以及本轮要遵守的约束（接口签名、可用编译选项）。这三部分不是等权拼接：任务描述是常量，历史记录是随轮次线性增长的变量，约束是短小的前缀。因此决策层真正的工程负担在于历史记录的管理——轮数越多，提示越长，token 成本按轮次累加而非按候选数累加。

首版内核的生成有一个隐含代价：在没有历史的情况下，智能体只能依赖任务描述中的语义线索，此时它倾向于选择“能跑通”的朴素实现而非“跑得快”的实现。这不是缺陷而是搜索的起点设计——先建立正确性基线，再在后续轮次中用性能反馈驱动改写。伪代码层面，决策层的单轮调用可写成：

$$\text{ctx}_t = \text{Concat}(\text{task},\ \text{hist}_{1:t-1},\ \text{constraints}),\quad k_t = \text{Agent}(\text{ctx}_t)$$

其中 $\text{hist}_{1:t-1}$ 是前 $t-1$ 轮的完整评测记录。这个设计的直接代价是上下文长度随 $t$ 增长，若不做截断或摘要，第 $n$ 轮的提示 token 量约为首轮的 $n$ 倍量级；对长搜索而言，token 成本会成为比编译时间更早触及的瓶颈。具体例子：一个矩阵乘类任务，首版内核可能直接三重循环实现，决策层此时只消费任务描述；到第 5 轮，提示中已包含 4 份源码与 4 组编译/性能记录，智能体需要在其中辨认“上一轮的分块尝试为何没有提升”，这一步的推理质量直接取决于历史记录的组织方式——是原样堆叠还是结构化摘要，决定了智能体能否从失败中提取可复用的改写方向。

二 · 编译步：错误信息作为一等反馈信号

执行层的第一步是编译。输入是决策层产出的候选内核源码与固定的编译配置（架构目标、优化等级、头文件与库依赖），输出是二值的编译结果加上诊断文本：成功则产出可加载的二进制，失败则产出编译器报错（语法错误、未定义符号、不支持的 intrinsic、寄存器或共享内存超限等）。这一步在整条流水线中时延最低但信息密度最高——一条编译错误往往能一次性排除一整类改写方向。

关键在于错误信息如何回传。若把原始编译器输出原样塞回提示，智能体需要自行从冗长的模板实例化报错中定位根因，这在 CUDA C++ 的模板重载场景下极易失焦；若做过度摘要，又可能丢掉“哪个参数类型不匹配”这类决定改写正确性的细节。工程上的折中是保留首条错误与出错行号、截断模板展开栈。代价方面：编译本身耗时通常在秒级，但若搜索循环中每轮都触发完整重编译，累计编译时间会与轮数成正比；对使用重量级模板库（如 CuTe 风格的类型级编程）的候选，单次编译可能显著拉长，此时“多轮搜索”的经济性会被编译时间侵蚀。

具体机制上，编译失败分支不进入运行与评测，因此它不消耗 GPU 时间，只消耗 token 与编译机时。这个分支的价值在于它是唯一能廉价纠错的分支：语法与接口问题在编译期暴露，避免了把错误内核送上 GPU 后才发现输出全错。一个典型例子是智能体在改写中引入了参考实现不支持的 dtype 特化，编译器在模板实例化处报错，回传后智能体在下一轮退回通用路径——这一轮的总代价是一次编译加一次模型调用，没有 GPU 运行开销。

三 · 运行与正确性判定：oracle 的构造与容差代价

编译通过后进入运行步。输入是可加载内核、输入张量与参考实现；输出是内核的实际输出以及一个正确性布尔判定。判定的机制是与参考实现逐元素比对，但比对的严格程度直接决定搜索的走向：容差过松会把数值误差大的内核判为正确，让搜索在错误的基础上继续优化性能；容差过紧会把合法的浮点重排（如改变累加顺序）判为错误，扼杀真正有价值的优化方向。浮点内核的累加顺序重排是性能优化的常见手段，而它必然带来与参考实现不同的舍入结果，因此容差设置实质上是“允许哪些优化”的策略声明。

$$\text{Correct}(k)=\bigwedge_{i}\ \bigl|\,\text{out}_k[i]-\text{ref}[i]\,\bigr| \le \tau_{\text{abs}} + \tau_{\text{rel}}\cdot\bigl|\text{ref}[i]\bigr|$$

这个逐元素判定的代价是显存与带宽：需要同时驻留内核输出与参考输出，比对本身是一次全量读，对大规模输出张量而言，比对带宽可能与被测内核的写出带宽同量级。若参考实现也在 GPU 上运行，还要计入参考实现的运行时间——它不计入被测内核的性能读数，但计入每轮的实际墙钟时间。边界覆盖是另一个代价点：仅比对主路径输出会漏掉边界 shape（非对齐尺寸、尾块、空张量）上的越界写，这类错误在性能读数上往往表现为“异常快”，因为内核跳过了部分工作。因此可信的正确性判定需要一组覆盖边界形态的输入，而非单一 shape。

具体例子：一个归约类内核在改写中把累加从顺序改为树形，数值结果在容差内一致，判定通过；但若同一改写顺带把尾块处理写错，主 shape 比对通过而边界 shape 比对失败，此时搜索必须依赖多 shape 覆盖才能拦住这个候选。这一步的工程判断是：正确性 oracle 的覆盖面就是搜索空间的护栏宽度，护栏越窄，搜索越容易漂向“快但错”的区域。

四 · 性能测量：口径决定搜索爬的是哪座山

正确性通过后才进入性能测量。输入是已判定正确的内核与计时配置，输出是本轮的性能读数，作为奖励信号回传给决策层。测量的口径包含三个必须显式声明的选择：计时方式（事件计时还是墙钟）、重复次数与统计量（单次、均值还是最小值）、以及是否排除编译与数据传输开销。这三者不声明，性能读数就不可比——不同轮次之间若口径漂移，智能体爬的是一座移动的山。

机制上，性能读数被用作搜索的奖励信号，其形式可写为对候选集的排序目标：

$$\text{best} = \arg\max_{k \in \{k_1,\dots,k_n\}} \text{Perf}(k) \quad \text{s.t.} \quad \text{Correct}(k)=\text{true}$$

这个目标函数看似简单，但它的代价在于：Perf 的测量噪声会直接注入搜索方向。GPU 内核的计时对时钟频率、缓存状态与并发负载敏感，单次测量方差可能与被优化量级相当；若不做多次重复取稳健统计，智能体可能把噪声误读为改进，进而在下一轮沿错误方向改写。另一个代价是测量本身的 GPU 时间：每轮一次测量意味着搜索的总 GPU 占用与轮数成正比，而正确性比对与性能测量往往需要多 shape、多重复，单轮 GPU 时间可能数倍于单次内核运行。

具体例子：智能体在某轮尝试了向量化访存改写，性能读数提升，但该提升若来自缓存预热而非真实带宽改善，下一轮基于此继续加深向量化就会偏离。工程上的对策是把测量配置固定为常量并写入历史记录，使每轮读数在同一口径下可比；同时把“是否排除数据传输”作为显式字段记录，避免把 host-device 拷贝时间混入内核时间导致加速比虚高。这一步的判断是：性能测量不是事后统计，而是搜索循环的一部分，它的口径设计等价于定义优化的目标函数。

五 · 反馈回传与历史组织：闭环的带宽瓶颈在上下文

一轮的终点是把编译结果、正确性判定与性能读数组织成反馈，回传给决策层，进入下一轮。输入是本轮的全部评测记录，输出是更新后的历史结构。这里的核心机制不是“把结果贴回去”，而是历史的结构化：编译失败、正确性失败、正确但性能未提升、正确且性能提升，这四类结果对下一轮改写的指导意义完全不同，若混为一谈地堆叠，智能体需要自行分类，推理负担与 token 成本同时上升。

代价分析上，反馈回传的瓶颈在上下文带宽而非 GPU：每轮新增的记录包含源码（数百到数千 token）、编译诊断、正确性差异摘要与性能读数，历史随轮数线性增长。若不设上限，长搜索的提示会触及上下文窗口，迫使截断——而截断哪一段历史是一个策略问题：丢掉早期的失败记录可能让智能体重蹈覆辙，丢掉近期的成功记录则丢失了当前的优化方向。一种工程折中是保留最近若干轮的完整记录加更早轮次的摘要（只保留“尝试了什么、结果类别、性能量级”），把 token 预算集中在近期。具体例子：第 8 轮的提示中，第 1–3 轮只以一行摘要出现（“朴素实现，正确，基线性能”），第 4–7 轮保留完整源码与读数，智能体据此能看出“分块尝试连续三轮未提升”这一模式，而不必重读早期源码。

另一个机制点是收敛判据与轮数上限。材料未给出具体设置，但从闭环结构可推出其工程形态：轮数上限是硬预算（token 与 GPU 时间的上界），收敛判据是软信号（连续若干轮无性能改进则停止）。两者共同决定搜索的经济性——上限过小则搜索未及有效区域，过大则边际收益递减而成本线性上升。最终选优在全部正确候选中取性能最优者，这意味着搜索过程中性能读数最好的那一轮未必是最后一轮，历史记录必须完整保留每个候选的读数才能正确选优。

六 · 单轮流水线的代价账本与工程判断

把上述步骤按一次生成—编译—运行—评测的流动摊开，每一步的输入、输出与代价可以并列成一张账本。这张账本的意义在于：搜索的总成本不是“轮数乘以单轮成本”这么简单，因为不同分支的单轮成本差异极大——编译失败分支只花编译机时与 token，正确性失败分支花 GPU 运行时间但不花性能测量时间，只有全通过的分支才支付完整的测量成本。

步骤输入输出主要代价
上下文装配任务描述、历史记录、约束本轮提示token 随轮数线性增长
内核生成本轮提示候选源码模型调用时延与 token
编译源码、编译配置二进制或诊断文本编译机时，模板重时显著拉长
运行与正确性二进制、输入、参考实现输出、正确性布尔值GPU 时间、比对显存与带宽
性能测量正确内核、计时配置性能读数GPU 时间、测量噪声注入
反馈回传本轮评测记录更新后的历史上下文窗口压力、截断策略

从这张账本可以读出该方法的工程判断：AutoKernel 的搜索成本主要由上下文长度与 GPU 测量时间两项主导，而非模型推理本身。编译失败分支是最廉价的信息来源，应当被充分利用——把编译诊断整理得越可读，智能体在廉价分支上纠错的效率越高，越少把错误候选送上 GPU。正确性 oracle 的覆盖面是搜索空间的护栏，护栏宽度决定搜索能否安全地探索数值重排类优化。性能测量的口径是目标函数的定义，口径不稳则搜索方向不稳。这三者共同构成闭环的可信度基础，而材料未给出它们的配置细节，因此该方法目前提供的是一套结构清晰的工程框架，其可信度取决于这些未公开的配置在真实基准上如何落地。
