一 · 剪枝门控的误判面：DCP 把谁砍错

DCP 的判据是“简单”与“灾难性”两类任务在多轮展开中的价值排序，它依赖 GRPO rollout 组内的相对表现来定档。失效的第一种形态是把慢热型任务误判为灾难性：某些 kernel 的首轮编译失败并非因为模型无能，而是因为题目本身要求跨多个抽象层（例如需要同时处理 tiling、bank conflict 与异步拷贝流水），首轮必然全错，第二轮引入 profile 反馈后才开始收敛。DCP 若在首轮就把这类题从多轮展开中切掉，等于剥夺了它唯一的成长路径。代价是可测量的：这类题在训练分布中的占比一旦超过阈值，多轮调试能力的梯度信号会整体塌陷，表现为 first-turn proficiency 上升而 multi-turn debugging resilience 下降——论文摘要恰恰把这两项并列作为卖点，说明它们之间存在张力。

第二种形态是把简单题误判为高价值。判据来自组内相对优势，若一个 rollout 组内所有样本都失败，相对排序退化为噪声，DCP 可能把“全员失败但方差大”的题保留下来，把“多数成功但方差小”的题砍掉。后者恰恰是稳定正梯度的来源。用公式表述这种退化：设组内通过率为 p，组内奖励标准差为 σ，DCP 保留判据近似为 σ·f(p) 的排序，当 p→0 时 σ 由个别偶然通过样本主导，排序不再反映题目难度。工程上的检查手段很直接：记录被剪枝题目的首轮通过率分布，若被剪枝集合的首轮通过率不是双峰而是单峰集中在 0 附近，说明门控在砍“难”而非砍“无价值”。

第三种形态与 Rank-Based Reward 耦合。成对锦标赛式的相对优势本身是尺度无关的，这解决了手工调参问题，但也意味着它无法区分“小幅领先”与“大幅领先”。在一个简单题上，两个候选都正确、时延差 3%，锦标赛给出的优势与一个复杂题上时延差 40% 的优势在数值上可能同量级。DCP 若用这种优势做价值估计，会把资源错配到边际收益极低的简单题上。论文声称该方法“inherently penalizes token inefficiency on simple prompts”，这一性质成立的前提是简单题上的 token 消耗确实更低；一旦模型学会在简单题上堆叠冗余解释性 token 换取锦标赛胜率，惩罚项就失效，这是典型的 reward hacking 通道。

二 · 编译时延作为反馈成本：多轮预算的硬边界

LEAP 的核心经济学是“把昂贵的编译与硬件探索集中到高价值任务”。这句话隐含一个前提：编译时延在题目间是可比的。真实情况是编译时延随模板复杂度、头文件深度、PTX 生成路径呈超线性增长。设单次编译时延为 ci，第 i 题的多轮展开轮数为 Ti，则总反馈成本为 Σ ci·Ti。DCP 优化的是 Ti 的分配，却没有对 ci 建模。后果是：一道编译耗时数倍于均值的题，即使被判为高价值，其单位反馈成本也远高于同档位的轻量题。若门控只看“难度”不看“编译成本”，资源会流向编译最慢的那批题。

$$\text{cost}_i = c_i \cdot T_i,\qquad \text{value}_i = \frac{\Delta\text{speed}_i \cdot \mathbb{1}[\text{pass}_i]}{\text{cost}_i}$$

正确的门控应当按单位成本价值排序，而非按难度排序。这在工程上意味着需要在 rollout 前做一次轻量编译探测，把 ci 纳入 gating 输入。代价是探测本身消耗编译配额，且探测结果受缓存状态影响不稳定。一个具体例子：同一份 CuTe 模板在不同 -arch 目标下编译时延差异显著，若训练集群混用多种架构，ci 的估计会跨节点漂移，门控决策随之抖动。这种抖动在单机复现时不可见，在多机训练时表现为剪枝率随节点分布波动。

另一个硬边界是反馈回灌的带宽。多轮环境反馈不仅是编译结果，还包括运行时时延、profile 计数器、错误日志。把这些文本回灌进上下文会挤占 token 预算。设每轮反馈注入 k 个 token，T 轮后上下文增长 k·T，在长上下文模型上这直接转化为显存与注意力计算开销。LEAP 的“lean”定位正是针对这一点，但剪枝只减少了轮数，没有减少单轮反馈的体量。若单轮反馈包含完整 NCU 段落，剪枝带来的节省会被反馈体量抵消。工程判断：剪枝与反馈压缩必须同时做，只做前者会在反馈密集的题目上失效。

三 · 迁移边界：跨硬件、跨 dtype、跨框架

论文的结论只在给定硬件、基线与输入分布上成立，这是摘要级信息里最需要被强调的一句。迁移失效有三个具体机制。其一是roofline 位置漂移：一道在给定 GPU 上处于 memory-bound 的题，换到高带宽比的硬件上会变成 compute-bound，此时“时延降低”对应的优化方向完全不同——前者奖励合并访存与向量化，后者奖励指令级并行与寄存器压力控制。LEAP 学到的策略是“在这类题上做这类改写”，硬件一换，策略的先验就错位。表现为加速比在离线基准上复现，在目标硬件上退化甚至为负。

其二是dtype 与数值容差。正确性门通常是“给定输入上的数值比对”，容差阈值决定了哪些候选能通过。fp32 下通过的低精度近似策略，在 fp16/bf16 输入分布上会因累积误差越过容差。更隐蔽的是，某些候选通过降低精度换取时延，在训练分布上恰好落在容差内，换一批输入就失败。这不是模型的错，是 oracle 的覆盖不足。代价是正确率虚高：离线正确率由容差与输入分布共同决定，两者任一变化都会让这个数字失去意义。

其三是框架抽象层的迁移。CUDA C++、Triton、CuTe、PTX 四层抽象对反馈的敏感度不同。Triton 的编译时延低、错误信息结构化程度高，多轮反馈的收益快；CuTe 模板错误信息冗长且指向性差，同样的轮数换来的有效信号更少；PTX 层则几乎没有可用的高层反馈，模型只能靠二进制通过与否学习，退化为信号稀疏的原始困境。LEAP 若在 Triton 上验证，其剪枝策略的收益不能直接搬到 CuTe 路径上——后者需要更长的展开轮数才能产生可辨识的梯度，而 DCP 恰恰在压缩轮数。

迁移维度失效机制可观测代价
跨硬件roofline 位置漂移，优化方向反转离线加速比复现，目标硬件退化
跨 dtype容差与输入分布共同决定通过率正确率虚高，换分布即崩
跨框架反馈信息量随抽象层升高而下降同等轮数下梯度信号不足

四 · 与相邻工作的差别：LEAP 不做什么

与多轮 RL 路线相比，LEAP 的差别不在“是否多轮”，而在轮数的分配权交给了一个动态门控。Kevin 一类的多轮框架把固定轮数预算平均分配给所有题，优点是实现简单、方差可控，缺点是编译成本在简单题上被浪费。LEAP 用 DCP 把这份预算重新分配，代价是引入了门控本身的误判风险与实现复杂度。判断标准很清晰：当题目难度分布接近均匀、编译时延方差小的时候，固定轮数与动态剪枝的收益差会收敛，此时剪枝带来的额外状态管理与调参成本不值得。

与对比式优化路线相比，LEAP 的 Rank-Based Reward 用组内锦标赛替代了显式的成对比较数据集。后者需要构造正负样本对，前者只需同一 prompt 下的多个 rollout。优点是无需额外数据工程，缺点是锦标赛结果的方差随组大小增大而下降——组太小则排序噪声大，组太大则单次 rollout 的显存与时间成本上升。这与 GRPO 的组大小选择是同一个约束，LEAP 没有绕开它，只是把约束从“奖励尺度”转移到了“排序可靠性”。

与硬件反馈 agent 路线相比，LEAP 的反馈来自编译、运行与 profile 的回灌，而不是多 agent 分工下的策略协调。后者在单题上能投入更多探索预算，前者在批量题目上更经济。两者的适用边界由题目数量决定：题目少而单题价值高时，多 agent 深挖更划算；题目多而单题边际收益低时，剪枝加批量 rollout 更划算。LEAP 的定位明确落在后者，这也意味着它在“少数极难题目”的场景下不是最优选择。

与形式验证路线相比，LEAP 的正确性 oracle 是执行反馈而非证明。这意味着它无法给出“这个 kernel 对所有合法输入都正确”的保证，只能给出“在这批输入上通过”。对于需要强正确性承诺的部署场景，LEAP 产出的候选必须再过一道形式化或差分测试门，这道门的成本不计入 LEAP 的训练经济学，却是生产落地的必要开销。

五 · 什么情况下不该用 LEAP

第一类不该用的场景是题目集合小且每道题都值得深挖。当题目数量在个位数量级、单题的性能收益足以覆盖数小时的编译与探索成本时，DCP 的剪枝没有可剪的对象，反而因为门控的误判风险损失了本应获得的探索轮数。此时固定轮数、加大组大小、人工介入反馈解读更直接。

第二类场景是编译时延不可预测或极高。若单次编译在分钟量级，多轮展开的总成本会主导整个训练预算，剪枝省下的轮数不足以抵消探测与门控的开销。更严重的是，高时延会放大门控抖动：一次偶然的编译超时会让题目被判为灾难性，而这个判断在后续轮次无法被纠正，因为题目已经被切出展开。工程上应当先做编译时延的分布测量，若长尾超过均值数倍，先解决编译缓存与增量编译，再谈剪枝。

第三类场景是正确性 oracle 覆盖不足。若输入分布只覆盖少数 shape，或容差设置宽松，LEAP 会在一个失真的奖励面上优化，剪枝只会加速收敛到这个失真面。此时增加轮数、增加剪枝都不会提升生产可用性，正确的动作是补 oracle：扩充输入分布、收紧容差、加入差分测试。这是数据工程问题，不是 RL 问题。

第四类场景是目标硬件与训练硬件不一致且无法在目标硬件上做反馈。LEAP 的全部信号来自执行反馈，若训练集群与部署硬件架构不同，反馈信号本身就是错的。此时要么在目标硬件上重建反馈回路，要么退回到以静态分析为主的优化路线，接受更低的自动化程度。用 LEAP 在这类场景上训练，得到的是一个在错误 roofline 上最优的策略。

第五类场景是需要可审计的优化理由。Rank-Based Reward 产生的是相对优势，不产生“为什么这个改写更快”的解释。在需要人工复核每一次性能改动的团队里，LEAP 的输出只能作为候选，复核成本不因自动化而降低。这与剪枝无关，是方法本身的属性：它优化的是结果分布，不是推理链。

六 · 工程判断：把剪枝当作预算调度器而非难度分类器

把 DCP 理解成“难度分类器”是误用的根源。它实际做的是在固定反馈预算下重分配展开轮数，其正确性判据应当是“单位成本的梯度产出”，而不是“题目是否困难”。按这个理解，门控输入至少应包含三项：首轮通过率的组内分布、编译时延的估计、以及该题在历史 rollout 中的梯度贡献。只给难度一项，门控就在做它没有信息去做的事。

$$\text{keep}_i = \mathbb{1}\left[\frac{\hat{g}_i}{\hat{c}_i} > \tau\right],\qquad \hat{g}_i = \text{Var}_{\text{group}}(r),\ \hat{c}_i = c_i + k\cdot T_i$$

这个判据的代价是它需要跨轮次的状态，而跨轮次状态在多机异步训练下难以保持一致。一个可行的折中是：门控只在每轮开始时基于上一轮的统计做一次批量决策，不追求逐样本精确，接受一定比例的误剪。误剪的代价可以用被剪题目的后续表现来度量——若被剪题目在离线评测中本可产出高加速比候选，说明剪枝率过高。这个度量需要保留一个不剪枝的对照组，成本是额外的编译配额，但它是唯一能校准门控的手段。

最后一条边界与部署相关：LEAP 的产出是候选 kernel，不是可直接上线的实现。论文的训练流程明确包含“按反馈保留或回退候选”，回退机制在生产端是必要的安全网，但它也会让离线正确率虚高——回退到基线实现总能通过正确性门，只是没有加速。评测时必须把回退率单独报告，否则“正确率”这个数字混合了模型产出与基线兜底，无法反映真实能力。这一点在跨硬件迁移时尤其致命：目标硬件上回退率上升会被误读为模型退化，实际是基线在该硬件上本就更快。
