一 · 任务层到首轮提示：语义、shape 与 dtype 如何被压进 token

Geak 的流程起点不在模型，而在任务层把算子规格转成一份可被智能体消费的提示。任务层必须给出三样东西：算子语义（例如归约轴、广播规则、边界行为）、输入 shape 与 dtype 分布、以及参考实现的调用约定。这三者共同决定首轮候选的搜索空间——语义描述含糊会让模型猜归约维度，shape 缺失会让模型硬编码 tile 大小，dtype 未声明则会让模型在 fp16 与 fp32 的累加精度上做出错误假设。

把规格压进提示的机制是模板化组装：语义段落 + shape 列表 + dtype 约束 + 参考实现签名，拼成一段固定结构的文本。代价体现在 token 上：shape 列表越长、语义描述越细，首轮提示越长，而多轮闭环中每一轮都要重发这份上下文，token 成本随轮数线性增长。工程判断是：shape 应以代表性集合而非全量枚举进入提示，否则提示长度会挤占模型用于生成代码的有效上下文。

具体例子：一个 softmax 算子，若提示只写“按最后一维归一化”，模型可能生成按行归约但未处理非连续 stride 的 Triton 内核；若提示附带“输入为 (B, S) 连续布局、dtype 为 fp16、累加用 fp32”，候选首轮就更可能写对 tl.sum 的轴与 tl.float32 的转换。这一步没有性能代价，但错误规格会以编译失败或数值超差的形式在后续步骤放大。

二 · 生成步：候选代码、启动配置与边界处理的三件套

智能体在首轮提示下产出的不是一段裸 kernel，而是一组三件套：Triton 内核函数体、启动配置（grid、block size、num_warps、num_stages）、以及边界处理（mask 与 tail 分支）。这三者任一缺失都会让后续步骤失败：没有启动配置则执行层无法确定 launch 维度；没有 mask 则在非整除 shape 上越界读写。

生成步的机制是模型在 Triton DSL 约束下做块级编程：用 tl.program_id 取块索引、用 tl.arange 构造块内偏移、用 tl.load/tl.store 带 mask 访问。伪代码思路可写成：对每个输出块，计算块起始偏移，构造块内索引向量，按 mask 加载输入，执行块内归约或矩阵乘，按 mask 写回。生成步的输出是一份待编译的候选，其代价是 token：候选越长（含边界分支与调试注释），单轮生成时延越高；多候选并行采样则成倍放大 token 消耗。

具体例子：矩阵乘内核若模型只写 BLOCK_M=128, BLOCK_N=128, BLOCK_K=32 而不写 K 维尾块的 mask，则在 K 非 32 整数倍时越界；若写了 mask 但把 num_stages 设得过高，则在共享内存受限的 GPU 上编译期即报资源超限。这两种失败分别落在编译步与运行步，构成后续反馈的输入。

三 · 编译步：报错文本作为第一类反馈信号

候选进入执行层后第一站是 Triton 编译器。编译步的输入是候选源码与启动配置，输出是编译产物或错误文本。Triton 的编译期检查覆盖语法、类型推断、块大小合法性与共享内存/寄存器资源约束；任一不满足即抛出异常，异常文本被捕获后原样回灌给智能体作为下一轮提示的一部分。

编译反馈的机制价值在于它是确定性信号：报错文本直接指向违规构造，模型据此修改的收敛速度远高于盲目重采样。代价是编译时间——Triton 的 JIT 编译对每个新 shape/配置组合都要走一遍 lowering 与 PTX 生成，多轮重试意味着多次编译，编译时间在闭环总时延中不可忽略。工程上应缓存已编译配置，避免同一候选重复编译。

具体例子：模型写出 tl.dot(a, b) 但 a 的块形状为 (128, 32)、b 为 (64, 32)，编译器报维度不匹配；回灌后模型把 b 的块改为 (32, 64) 或转置加载，第二轮即通过。另一类典型是 num_warps=16 超出硬件上限，报错文本直接给出合法范围，模型一轮即可修正。

四 · 运行与正确性比对：逐元素 oracle 与两类失败

编译通过后候选在 GPU 上运行，输出与参考实现逐元素比对。正确性 oracle 的机制是：对每个输出元素计算绝对误差或相对误差，与容差阈值比较，全部通过才判定正确。材料未披露容差阈值与边界 shape 的处理方式，这意味着 oracle 的严格程度是未知量——阈值过松会放过精度缺陷，过严会把合法浮点重排判为错误。

比对失败至少分两类，对应不同的修改路径。第一类是数值超差但形状正确，通常源于归约顺序、累加精度或除零保护缺失；第二类是越界或未定义行为，通常源于 mask 写错或 tail 分支缺失。前者的定位靠误差分布（哪个轴上的误差更大），后者的定位靠运行时报错或非法内存访问。代价是运行时间：每个候选都要跑一遍参考实现与候选实现，参考实现的耗时在大 shape 上不可忽略，且比对本身要占用显存容纳两份输出。

$$\mathrm{err}_i=\frac{|y_i-\hat{y}_i|}{\max(|y_i|,\epsilon)}\quad\text{，全部 } \mathrm{err}_i\le\tau \text{ 才判正确}$$

具体例子：layer norm 内核若在方差计算时漏掉 +eps，在输入接近常量时相对误差爆炸，逐元素比对会在这些位置集中报错，提示模型补上 eps；若归约用了 fp16 累加而参考用 fp32，误差随元素数增长，模型需把累加类型改为 fp32。这两类修改都不改变启动配置，只改内核体，因此编译时间代价小、运行比对代价不变。

五 · 计时与加速比：统一口径下的性能反馈

通过正确性检查的候选进入计时步。计时步的输入是正确候选与基线实现，输出是候选耗时、基线耗时与加速比。机制上要求统一口径：相同的预热次数、相同的同步方式、相同的测量重复数，否则加速比不可比。材料未披露基线名称、计时方法与预热策略，这是横向比较的主要风险点——不同预热策略会让首次运行的编译开销混入计时，导致加速比失真。

性能反馈回灌给智能体的形式是加速比数值与基线耗时，模型据此判断是否需要调整 block size、num_stages 或算法结构。代价有两层：计时本身要占用 GPU 时间，多候选逐一计时会拉长闭环；更重要的是，性能反馈的信号密度低于编译与正确性反馈——加速比只是一个标量，模型难以从中定位瓶颈在访存还是计算。工程判断是：若能在计时步附带 roofline 位置或 occupancy 估计，反馈的信息量会显著提升，但材料未说明 Geak 是否这样做。

$$\mathrm{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\mathrm{correct}_i]\cdot\frac{T_{\mathrm{base},i}}{T_{\mathrm{cand},i}}$$

具体例子：同一矩阵乘候选，若 block size 从 128 降到 64，占用率上升但每块计算量下降，计时可能显示加速比持平或略降；模型若只看标量加速比，无法判断是共享内存带宽受限还是寄存器压力过大，只能靠试错。这正是性能反馈需要更细粒度信号的动机。

六 · 多轮编排与候选筛选：闭环的收敛条件与工程代价

编排层把上述步骤串成闭环：生成→编译→运行→比对→计时→回灌，直到候选通过正确性并达到性能门槛，或达到轮数上限。编排层的机制包括候选筛选（在多候选间按编译通过率、正确率、加速比排序）与重试策略（失败信息如何拼进下一轮提示）。材料未给出轮数上限、候选筛选策略与 token 成本，因此闭环的收敛条件与工程代价无法从摘要估算。

闭环的代价结构可以定性拆解：每轮的成本 = 生成 token 成本 + 编译时间 + 运行与比对时间 + 计时时间。编译与运行时间随候选数与轮数线性增长，token 成本随提示长度与轮数线性增长。若候选筛选采用并行采样，token 成本成倍放大而编译/运行时间也成倍放大；若采用串行重试，则时延随轮数累加。工程判断是：闭环的收益来自失败信息的复用——一次编译错误回灌后，后续轮次应避免重复同类错误，否则多轮只是重复采样而非收敛。

具体例子：一个 reduce 算子的候选在第一轮因 mask 缺失越界，第二轮补上 mask 但 block size 过大导致共享内存超限，第三轮缩小 block size 后通过正确性但加速比低于基线。此时编排层需决定是继续调 block size 还是换算法结构；若轮数上限为三轮，则该候选被记录为“正确但未达标”，其轨迹进入基准汇总供失败模式统计。轨迹留存的价值在于：失败模式分布（编译错误占比、数值超差占比、性能不达标占比）本身就是评测口径的一部分，而材料未披露这部分数据，意味着当前只能确认闭环形态，无法量化其收敛效率。

闭环的另一处工程细节是反馈文本的组装：编译错误原文、数值误差摘要、加速比数值三者拼进下一轮提示时，提示长度会随轮数膨胀，挤占模型用于生成的有效上下文。若编排层对反馈做摘要压缩（只保留错误类型与关键行号），token 成本可控但信息有损；若原样回灌，信息完整但 token 成本随轮数上升。这一取舍在材料中未说明，属于复现时必须自行决定的工程参数。

闭环在何处断裂：编译门、数值门与计时门的失效边界

把一次 Triton 内核生成拆成“提示—生成—编译—运行—比对—计时”六段后，真正决定这套脚手架能不能用的不是生成质量，而是三道门各自的判据强度。编译门最廉价：编译器返回的报错文本是结构化程度最高的反馈，语法与类型错误能被精确定位到行，回灌后模型修改的收敛速度最快；代价是编译时间本身进入循环，Triton 的 JIT 与 autotune 会让同一份源码在不同 shape 下触发多次编译，若脚手架在每轮重试都重新编译全部候选，编译开销会随重试轮数线性叠加，成为 token 成本之外的第二类隐性开销。数值门则脆弱得多：逐元素比对依赖参考实现的语义等价，但归约顺序、累加精度与边界 shape 的处理会让“正确”变成一个带容差的判断，材料未给出容差阈值，这意味着同一份候选在不同 oracle 严格度下可能得到相反结论——容差放宽则越界与归约错误被吞掉，容差收紧则合法的浮点重排被误判为失败，两种偏差都会污染后续计时样本的合法性。

计时门的问题不在测量本身，而在可比性。加速比按 $$\mathrm{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\mathrm{correct}_i]\cdot\frac{T_{\mathrm{base},i}}{T_{\mathrm{cand},i}}$$ 汇总时，分子中的基线耗时若未固定预热策略与计时口径，分母的候选耗时即便测准也失去意义；更关键的是该式把正确性做成 0/1 乘子，一个通过比对但仅快 1% 的候选与一个快 10 倍但偶发数值超差的候选在期望上可能等价，这会诱导智能体把搜索预算投向“刚好过门”的候选而非真正稳健的实现。工程上可把门做成三级：编译门只回灌报错摘要以省 token；数值门记录最大绝对误差与首个失配索引，供下一轮定位越界或归约错误；计时门仅在正确性通过后执行，且必须与基线在同一软件栈版本、同一预热轮数下测量，否则 Triton 编译差异会直接污染比较。

失效条件可以归成一张小表，它同时是这套方案的边界清单。
门典型失败回灌信息系统代价
编译门语法/类型错误、不支持的块操作报错文本与行号每轮重编译，编译时间随重试累积

三类失败对应三种不同的修复路径，混为一谈会让智能体在错误方向上消耗轮数：编译错误应触发局部重写，数值错误应触发语义级重构，计时异常则应先怀疑测量而非代码。

还有一个常被忽略的边界是搜索本身的代价不可估。材料未给出重试上限、候选筛选策略与 token 成本，这意味着闭环的终止条件只能由外部设定；若以“连续若干轮无提升”为停止准则，则一个编译始终不过的候选会耗尽全部轮数预算，而一个首轮即通过且加速比尚可的候选可能被过早接受，错过更优解。具体例子：某归约算子的首版候选因未处理非 2 的幂 shape 而在数值门失败，回灌失配索引后模型改为掩码写法，第二轮通过但计时显示因多了一次条件判断而慢于基线；此时若脚手架只按加速比排序，会把这份正确但慢的候选丢弃，转而重试一个更快但边界未覆盖的版本——正确性与性能在同一个分数里被耦合，取舍必须显式化，例如先按正确性过滤再做性能排序，而不是让 0/1 乘子隐式决定。防作弊同样落在这一层：若候选可缓存结果或针对固定 shape 特化，计时门测到的加速比不再代表算子本身的收益，材料未披露此类机制，横向比较的可信度只能等全文核对。
