一 · 一次闭环的真实账单：token、GPU 时与编译时间

把 Geak 的执行反馈闭环拆到最细，一次「生成—编译—运行—比对—计时」的迭代要消耗三类资源，且它们的量级差异极大。第一类是 token：首轮提示包含算子语义、输入 shape、dtype 分布与接口约定，后续每轮还要把编译报错文本或数值比对差异回灌，因此上下文长度随轮数单调增长，而不是每轮重置。第二类是 GPU 时：候选内核要在真实设备上跑，正确性比对需要参考实现与候选各跑一遍，计时阶段还要重复多次以压低方差。第三类是编译时间：Triton 的 JIT 路径在首次遇到某个 shape 组合时要走完整的编译链路，这一步发生在 CPU 侧但阻塞整个闭环，且与 GPU 时不可重叠。

把这三者写成成本模型，设第 $r$ 轮上下文 token 数为 $C_r$、生成 token 数为 $G_r$、GPU 单次测量耗时为 $t_g$、计时重复次数为 $K$、编译耗时为 $t_c$，则单候选的总代价可近似为：

$$\mathrm{Cost}=\underbrace{\sum_{r=1}^{R}(C_r+G_r)\cdot p_{\mathrm{tok}}}_{\text{语言模型侧}}+\underbrace{R\cdot(t_c+K\cdot t_g)\cdot p_{\mathrm{gpu}}}_{\text{执行侧}}$$

关键在于两项的缩放方式不同。语言模型侧随轮数 $R$ 近似二次增长，因为 $C_r$ 本身在累积；执行侧随 $R$ 线性增长，但 $t_c$ 往往是单轮里最贵的一项。一个具体例子：某归约算子的候选在语法上通过了，但块大小与 shape 不匹配导致越界，编译阶段不报错、运行阶段才出现数值超差，于是这一轮既付了编译时间又付了 GPU 时，还额外付了一轮带错误上下文的 token。这类「编译通过但运行失败」的候选是最贵的失败模式，因为它把三类资源全部消耗一遍却不产生任何可用信号之外的进展。

工程判断上，闭环设计必须让便宜的信号先跑。编译错误在 CPU 侧就能捕获，应当在任何 GPU 资源被占用之前完成筛选；数值比对应当在计时之前完成，避免为错误候选付计时重复 $K$ 次的代价。把顺序倒过来——先计时再比对——会让每个错误候选都多付 $K$ 倍 GPU 时，在并发场景下直接拖垮吞吐。

二 · 搜索轮数与候选筛选：规模上去先崩的是上下文

规模扩大有两条正交的轴：单任务的搜索轮数 $R$，以及并发任务数 $M$。二者对系统的压力点完全不同。增大 $R$ 时，最先崩的不是 GPU 显存也不是编译队列，而是上下文预算：每一轮都要把历史报错、历史候选与比对差异带进提示，$C_r$ 的增长使得单次调用的 token 成本上升，同时长上下文下的指令遵循质量下降，模型开始重复已经失败的修改。这意味着轮数上限不是由「还能不能再试一次」决定，而是由「上下文还能不能承载有效信号」决定。

增大 $M$ 时，最先崩的是编译与执行层的排队。Triton 编译是 CPU 密集的，多个并发任务同时触发新 shape 的编译会争抢同一批 CPU 核，$t_c$ 被拉长；GPU 侧则出现显存碎片与占用冲突，尤其是当多个候选各自持有参考实现的中间张量时。设并发度为 $M$、单任务平均占用显存为 $m$、设备显存为 $V$，则可行并发度受限于：

$$M_{\max}\approx\left\lfloor \frac{V\cdot\eta}{m}\right\rfloor$$

其中 $\eta$ 是留给运行时与碎片的安全系数。这个式子说明并发不是免费的：把 $M$ 推到 $M_{\max}$ 附近时，任何一个候选的显存峰值抖动都会触发整体失败，而失败后重试又要重新付编译与 token 成本。

候选筛选是缓解这两条轴压力的核心手段。一个可操作的策略是分层筛选：第一层只做静态检查与编译，淘汰语法与类型错误；第二层做小 shape 的快速数值比对，淘汰明显的越界与归约错误；第三层才进入全 shape 比对与计时。具体例子：某矩阵乘候选在静态检查阶段就因为块维度声明与输入不匹配被淘汰，省下了后续全部 GPU 时；而另一个候选在小 shape 上数值正确、在大 shape 上因边界处理缺失而超差，第三层才暴露，这类候选的代价无法通过前置筛选消除，只能靠覆盖率更高的测试 shape 提前发现。筛选层的代价是额外的测试用例与运行时间，收益是避免为注定失败的候选付完整闭环成本。

三 · 编译时间与缓存：被低估的固定开销

Triton 的编译开销在单任务视角下像是常数，但在规模化视角下它是复现性与吞吐的共同瓶颈。编译结果与 shape、dtype、块配置、软件栈版本强绑定，任何一项变化都会触发重新编译。缓存能缓解重复编译，但缓存命中率取决于搜索策略是否在相同配置空间内反复试探。若智能体每轮都改动块大小，缓存几乎不命中，$t_c$ 全额付出；若智能体在固定配置下只改边界处理逻辑，缓存命中率高，执行侧成本显著下降。

缓存带来的正确性代价同样具体：缓存键若未包含软件栈版本，跨版本复用编译产物会引入难以定位的数值差异，表现为「同一份代码在不同机器上结果不同」。这在横向比较中尤其危险，因为性能数字与正确性判定会同时被污染。工程上应把 Triton 版本、CUDA 版本与编译选项纳入缓存键，代价是缓存条目膨胀与命中率下降，收益是结果可复现。

一个具体机制：把编译产物按「算子 + shape 签名 + dtype + 块配置」四元组索引，命中时直接跳过编译阶段进入运行。这样做的直接收益是把单轮执行侧成本从 $t_c+K\cdot t_g$ 降为 $K\cdot t_g$，在 $t_c$ 占主导的场景下相当于把闭环吞吐提升一个量级。代价是首次遇到新配置时仍要付全额 $t_c$，且缓存失效后的重编译会集中爆发，需要限流以免压垮 CPU 侧。

四 · 并发与隔离：共享设备下的相互污染

并发执行多个候选时，性能测量会被相互污染。计时阶段若与其他任务共享 GPU，测得的时间包含调度抖动与显存带宽竞争，加速比失去可比性。设候选真实耗时为 $t$、干扰导致的额外抖动为 $\delta$，则观测值为 $t+\delta$，而 $\delta$ 随并发度上升而非线性增长。这意味着并发度越高，单个候选的性能数字越不可信，而基准的可信度恰恰依赖这些数字。

隔离策略有三种取舍。独占设备最干净，代价是吞吐最低，适合最终验收阶段。时间片轮转能提高吞吐，代价是计时噪声，适合筛选阶段。按 SM 或显存配额分区介于两者之间，代价是需要运行时支持且分区边界难以精确控制。工程判断是：正确性比对可以并发，计时必须隔离。把这两类操作放在同一并发池里，等于用吞吐换掉了基准最核心的可比性。

具体例子：某候选在独占设备上测得加速比高于基线，但在并发池中因带宽竞争被压到基线以下，若直接采信并发池的数字，会误判该候选为失败并触发不必要的重试，额外付出 token 与编译成本。这类误判在规模上去后会被放大，因为并发池中的任务越多，单个任务的测量偏差越大。

五 · 中小团队的真实预算：把闭环跑在可承受的规模上

对没有大规模集群的团队，预算约束决定了闭环必须做减法。可承受的规模由三个上限共同决定：单任务轮数上限 $R_{\max}$、并发任务上限 $M_{\max}$、以及每日总 token 与 GPU 时预算。三者不是独立的，提高 $R_{\max}$ 会推高单任务成本从而压低可并发的任务数，反之亦然。一个实用的配置思路是固定总预算 $B$，在 $R$ 与 $M$ 之间做分配：

$$B\approx M\cdot\left[\sum_{r=1}^{R}(C_r+G_r)\cdot p_{\mathrm{tok}}+R\cdot(t_c+K\cdot t_g)\cdot p_{\mathrm{gpu}}\right]$$

在 $B$ 固定时，把 $R$ 压到较小值、把 $M$ 提上去，适合探索阶段，能快速覆盖更多算子并收集失败模式分布；把 $M$ 压到较小值、把 $R$ 提上去，适合打磨阶段，针对少数候选做深度修改。两种配置的代价不同：前者牺牲单候选的收敛深度，后者牺牲覆盖面与失败模式统计的样本量。

具体机制上，中小团队应优先做三件事。其一，把编译错误与静态检查前置，避免为语法错误付 GPU 时。其二，把正确性比对拆成小 shape 快筛与大 shape 复核两级，用小 shape 的廉价运行淘汰大部分错误候选。其三，把计时隔离到独占窗口，只在候选通过全部正确性检查后才进入，避免并发污染。这三件事都不需要额外硬件，只改变闭环内的顺序与并发策略，收益是把有限预算集中在真正有希望的候选上。

规模上去以后先崩的位置，取决于团队先触碰哪个上限。若先触碰上下文预算，表现为轮数增加但质量不升，token 成本线性上升而通过率停滞；若先触碰编译队列，表现为并发度提高但单任务时延暴涨，闭环吞吐不升反降；若先触碰显存，表现为并发任务随机失败并触发重试，成本被失败重试吞噬。识别当前瓶颈的方法是看单位预算产出的有效候选数：当该指标随规模上升而下降时，说明已经越过了某个上限，继续加规模只会放大代价而不增加产出。

规模上去以后，先崩的是编译与重试预算

把闭环按算子数 $K$、每算子平均重试轮数 $R$、每轮提示与回灌 token 数 $T$ 展开，token 成本近似为 $K\cdot R\cdot T$ 的线性放大，而 GPU 时则近似为 $K\cdot R\cdot (t_{\mathrm{compile}}+t_{\mathrm{run}})$。真正先失控的不是生成，而是 Triton 编译：每个候选都要走一次 JIT，编译时间与 kernel 复杂度、模板展开、autotune 配置数正相关，而失败候选同样消耗编译预算。工程上应把编译结果按 (源码哈希, Triton 版本, 目标架构) 做键级缓存，命中则跳过编译直接进运行阶段；否则同一算子在第 3、4 轮反复改一行注释都会重付一次编译代价。代价是缓存键一旦漏掉 dtype 或 shape 约束，就会把错误配置复用进正确性比对，制造假阳性。

并发是第二个断点。执行层要在同一批 GPU 上串行化编译、运行与计时，若把 $M$ 个候选并发压到 $G$ 张卡上，排队时延约为 $\lceil M/G\rceil$ 个时间片，而计时阶段必须独占设备才能保证口径稳定——并发跑计时会把预热与频率波动混进加速比。因此正确性比对可以并发，计时必须隔离，这使吞吐在计时环节被硬性削平。一个具体例子：某归约算子的候选在第 2 轮因越界触发数值不符，回灌后第 3 轮才通过，若编译缓存未命中，仅这一个算子就吃掉三次编译加两次运行，而有效信息只有一条错误文本。

规模变量放大对象先崩的位置
算子数 Ktoken、编译次数编译队列与缓存命中率
重试轮数 RGPU 时、回灌 token计时隔离导致的串行瓶颈
候选宽度运行与比对次数正确性 oracle 的比对带宽

中小团队的真实预算应按“每算子一次通过的正确性比对 + 一次隔离计时”为基线单元估算，把重试轮数上限设为硬约束而非软提示：轮数上限一旦放开，token 与 GPU 时按 $R$ 线性增长，而通过率通常呈递减收益。判断边界很直接——当编译缓存命中率低于运行次数的一半，或计时排队时延超过单次运行耗时，规模收益就已经为负，此时应缩算子集而非加轮数。
