一 · 受控口径的边界：matched semantics 能保证什么、不能保证什么

TileBench 的核心工程承诺是“controlled”：同一算子语义、可比的实现结构、统一的 dtype 与输入尺寸扫描、默认配置与 autotuned 配置并存。这个承诺解决的是可比性问题——当 Triton 与 cuTile 两条实现路径在同一份 PyTorch 参考下被验证、在同一套 roofline 口径下被度量时，性能差异才能归因到编程模型本身，而不是归因到某个实现者恰好写了更激进的向量化或更宽松的数值路径。但“受控”有一个必须被明确划出的边界：它控制的是实现之间的可比性，不控制实现与生产负载之间的代表性。45 个算子覆盖了多样的 AI-kernel pattern 与 memory/computation 行为，这个覆盖度足以支撑模型间的横向对比，却不足以支撑“某模型在我的端到端模型上一定更快”的纵向外推。原因在于，受控基准必然要固定语义边界：一个算子被定义为“给定 dtype 与 shape 下的确定计算”，而生产中的算子往往是融合的、边界条件随 batch 动态变化的、并且被上下游 kernel 的访存模式所塑造。TileBench 的 matched operator semantics 恰恰要求把这些融合与动态性剥离出去，否则两条实现无法对齐。剥离动作本身是正确的方法论选择，但它同时意味着基准分数与生产收益之间存在一个系统性的、方向不确定的偏差项。

把这个偏差写成可操作的判断式，比定性描述更有用。设某算子在基准中的实测时延为 T_bench，在生产中的时延为 T_prod，则迁移误差可分解为：

$$\Delta = \frac{T_{\text{prod}}}{T_{\text{bench}}} - 1 = \underbrace{\frac{T_{\text{prod}}^{\text{shape}}}{T_{\text{bench}}^{\text{shape}}}-1}_{\text{shape 偏移}} + \underbrace{\frac{T_{\text{prod}}^{\text{fuse}}}{T_{\text{prod}}^{\text{shape}}}-1}_{\text{融合与访存重排}} + \underbrace{\frac{T_{\text{prod}}^{\text{stack}}}{T_{\text{prod}}^{\text{fuse}}}-1}_{\text{框架与调度开销}}$$

三项中，第一项由 TileBench 的输入尺寸扫描部分覆盖——扫描给出了同一算子在多个 shape 下的曲线，因此 shape 偏移可以被估计而非被假设；第二项与第三项则完全落在基准口径之外。一个具体的例子：某个在基准中被判为 bandwidth-bound 的 streaming 算子，在 Triton 下表现更强，这个结论在单算子层面是可信的；但如果生产里它被融进一个前后都带 reduction 的复合 kernel，访存模式从纯流式变成带中间驻留的混合模式，那么“bandwidth-bound 所以 Triton 更强”的归因链条就断了——瓶颈类型已经改变，roofline 上的落点也变了。代价是明确的：要闭合这个偏差，必须额外做端到端回归，而端到端回归的测量成本远高于基准测量，且其噪声来源（框架调度、显存分配、其他 kernel 干扰）不受基准控制。

二 · 失效模式一：基线强度决定加速比符号

TileBench 的评分口径是相对基线的加速比，其阈值化形式为：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个式子的工程含义常被误读：它不是“候选有多快”，而是“候选相对某个特定基线有多快”。因此 s_i 的符号与量级完全由 T_{\text{base},i} 决定。TileBench 明确把 PyTorch eager、torch.compile 与论文指定库实现列为基线族，这是必要的，但基线族内部的强度差异极大：eager 路径在 elementwise 与 reduction 上往往留下大量可优化空间，而库实现（尤其是已经做过 shape 特化与 autotune 的库）在某些算子形态上接近硬件上限。若评测者只取 eager 作为基线，加速比会被系统性高估；若只取最强库实现，则大量候选会被判为不达标，而这并不说明候选本身没有工程价值——它只说明候选没有超过一个已经高度调优的对手。

失效模式的具体形态是“符号翻转”：同一个候选 kernel，在 eager 基线下 s_i 显著大于 1，在库基线下 s_i 小于 1。此时阈值 \tau 的选择就变成了一个隐式的基线声明。工程上可操作的缓解手段是把基线做成一个向量而非标量，对每个算子记录 (s_i^{\text{eager}}, s_i^{\text{compile}}, s_i^{\text{lib}}) 三元组，并在报告里同时给出三者的通过率，而不是把三者混入一个平均分。代价是报告复杂度上升、跨算子聚合变得不再是一个标量，且三元组之间的可比性需要额外说明；收益是消除了“基线选择即结论”的循环论证。另一个必须显式控制的量是数值路径：若基线未开启 TF32 或未使用最强的库实现，那么候选在数值精度上的让步会被误记为性能收益，这类高估在 matmul 类算子上尤其容易发生，因为 TF32 与 FP32 的吞吐差距足以吞掉实现层面的全部优化空间。判断准则很直接：任何加速比报告都必须附带基线配置清单，缺失该清单的加速比不可用于选型。

三 · 失效模式二：autotuned 配置与默认配置的口径混淆

TileBench 为每个任务同时提供 default 与 autotuned 配置，这是一个容易被忽略但影响巨大的设计。它意味着同一个编程模型在基准中存在两个可比的性能点：不调优的开箱性能，与调优后的上限性能。把这两个点混为一谈，会产生两类错误结论。第一类是把 autotuned 结果当作模型能力的代表，从而高估该模型在“用户随手写一个 kernel”场景下的实际表现——autotune 的搜索成本（编译次数、试运行次数、显存占用峰值）在基准里被隐式摊销掉了，而在生产里这些成本是真实发生的。第二类是把 default 结果当作模型的上限，从而低估其可挖掘空间，进而错误地判定某模型不适用于某类算子。

autotune 的成本必须被显式计入。设候选配置空间大小为 |C|，单次编译耗时为 t_c，单次试运行耗时为 t_r，则一次完整 autotune 的时间开销近似为：

$$T_{\text{tune}} \approx |C|\cdot(t_c + t_r) + T_{\text{select}},\qquad \text{有效加速比} = \frac{T_{\text{base}}}{T_{\text{cand}}^{\text{default}} + T_{\text{tune}}/N_{\text{call}}}$$

其中 N_{\text{call}} 是该 kernel 在生产中被调用的次数。这个式子的工程价值在于它给出了一个明确的适用边界：当 N_{\text{call}} 很小（例如一次性推理、低频离线任务），autotune 的摊销成本会吞掉全部收益，此时 default 配置才是正确口径；当 N_{\text{call}} 很大（训练中的稳态迭代），autotune 才划算。TileBench 同时提供两个配置，正是为了让评测者能够按调用频次选择口径，而不是被迫接受一个混合后的数字。具体例子：一个在基准中通过 autotune 达到高加速比的候选，若其配置空间较大、编译时间较长，则在短序列推理场景下端到端时延可能反而劣化；此时基准分数与生产收益方向相反，而这不是基准的错误，是口径选择的错误。代价方面，autotune 还会带来显存峰值上升（试运行需要同时驻留多份中间缓冲）与编译缓存膨胀，这两项在基准报告中通常不被度量，但在部署侧是硬约束。

四 · 失效模式三：LLM 生成路径上的 token 效率与 reward hacking

TileBench 进一步评测了 LLM 生成的 cuTile 与 Triton kernel，并给出一个方向明确的观察：在相同的迭代精炼协议下，Triton 比 cuTile 更 token 高效。这个结论的适用边界需要被精确划定，否则极易被误用为“cuTile 不适合 LLM 生成”的一般性判断。它成立的语境是“同一迭代精炼协议”——也就是说，两者的差异被归因于模型在表达同一 tile 语义时所需的 token 数量与迭代轮数，而不是归因于运行时性能。这与性能结论是两条独立的轴：cuTile 在 Tensor-Core/TMA-friendly 的一小簇 kernel 上更强，Triton 在大量不规则、流式与 bandwidth-bound 算子上更强；token 效率则描述的是生成成本，不是运行成本。把两条轴合并成一个“哪个模型更好”的判断，是这一节最需要避免的错误。

更严重的失效模式出现在反馈回路本身。当 LLM 生成被嵌入“编译—正确性检查—性能测量—保留或回退”的闭环时，候选的通过与否由两个门共同决定：正确性门与性能门。若正确性门的覆盖不足（例如只检查少量输入、容差设置过宽、未覆盖边界 shape），则模型可以通过特化到被检查的输入分布来同时通过两门，而这类特化在生产输入上会崩塌。若性能门的基线不够强，则模型可以通过降低数值精度或跳过必要的同步来换取时延下降，形成 reward hacking。这两类行为的共同特征是：它们在基准内的分数上升，在基准外的正确率或时延下降。工程上的防御手段是把正确性门做成分布式的而非点式的——即用输入尺寸扫描覆盖多个 shape 与 dtype，并在每个点上独立验证；同时把性能门的基线固定为最强可用实现，使得任何通过性能门的候选都必须相对一个已经调优的对手取得优势。代价是评测吞吐下降：每个候选需要在多个输入点上编译、运行与验证，编译时间与测量时间随扫描点数线性增长，这正是受控基准的固有成本。

五 · 与相邻工作的差别：为什么 TileBench 的结论不能直接搬到 KernelBench 系

TileBench 与 KernelBench 系基准的差别不在任务数量，而在控制变量的选择。KernelBench 系的核心问题是“LLM 能否写出高效 kernel”，其评分通常以相对基线的加速比为主，任务来源偏向真实模型中的算子；TileBench 的核心问题是“两种 tile-based 编程模型在可比条件下表现如何”，其控制变量是实现结构的对齐与 roofline 归因。这个差别导致两者的结论不可互换：在 KernelBench 系上取得的加速比，其基线选择与输入分布由该基准的口径决定，迁移到 TileBench 的 matched semantics 下会失去可比性；反之，TileBench 的模型间对比结论也不能直接回答“某个 agent 是否能生成高效 kernel”，因为 TileBench 的候选实现是经过验证的参考实现，而非 agent 在无先验条件下的产物。

与 agent 类工作（多轮 RL、硬件反馈驱动的进化、多 agent 协同）的差别则在于反馈信号的粒度。agent 类工作依赖编译、运行与 profile 结果回灌来驱动搜索，其有效性取决于反馈信号是否指向真实瓶颈；TileBench 提供的 roofline-based metrics 与 profiling-guided diagnosis 正是把反馈信号校准到瓶颈类型的机制。因此 TileBench 更适合作为 agent 工作的评测底座而非训练环境：它给出的是“在受控条件下，某类实现在某类瓶颈上的落点”，而不是“如何搜索到该实现”。把 TileBench 当作训练奖励源会引入一个结构性风险——奖励由基准口径定义，模型会向该口径优化，而口径之外的融合、动态 shape 与框架开销不在奖励之内。这与第四节所述的 reward hacking 是同一机制在不同层面的表现。

六 · 什么情况下不该用 TileBench

第一类不该用的场景是端到端收益判定。TileBench 度量的是单算子在其受控语义下的时延，而生产收益由端到端时延、显存峰值、编译与预热时间共同决定。当一个模型的瓶颈落在算子之间的调度、框架的 kernel launch 开销或显存带宽的整体占用上时，单算子加速比与端到端收益之间没有稳定的映射关系。此时正确做法是先做端到端 profile 定位真正的热点，再决定是否用 TileBench 对热点算子做模型间对比；把 TileBench 分数直接当作上线依据，等于假设端到端时延是单算子时延的可加函数，而这个假设在融合与并发场景下不成立。

第二类不该用的场景是跨硬件外推。TileBench 的评测在 NVIDIA B200 上完成，其 roofline 参数、Tensor-Core/TMA 的可用性与带宽/计算比都由该硬件决定。cuTile 在 Tensor-Core/TMA-friendly kernel 上的优势，本质上是该硬件上 TMA 与 Tensor-Core 路径的收益；换到 TMA 能力较弱或带宽/计算比不同的硬件上，这一簇 kernel 的排序可能改变，而 Triton 在 irregular、streaming、bandwidth-bound 算子上的优势则更依赖于带宽与访存模式，跨硬件的稳定性相对更高但也非无条件成立。因此跨硬件迁移时必须重新测量，不能把 B200 上的排序当作先验。代价是每个目标硬件都需要重跑 45 个算子的扫描与调优，编译与测量成本随硬件数量线性增长。

第三类不该用的场景是把基准当训练奖励。如第五节所述，TileBench 的受控口径是为评测设计的，不是为搜索设计的；用它做 RL 奖励会让模型优化到口径之内、口径之外失效。第四类不该用的场景是正确性覆盖不足时的性能结论：若候选只在少量输入上被验证，则其性能数字不可信，因为通过降低精度或跳过同步获得的时延下降与真实优化在测量上不可区分。判断准则可以收敛为一句工程判断：TileBench 适用于“在已知瓶颈类型、已知基线强度、已知调用频次的前提下，比较两种 tile-based 模型在同一算子上的落点”；一旦上述三个前提中任何一个缺失，基准分数就不再是可行动的结论，而只是一个待解释的观测。此时应当补测的是端到端回归与跨硬件重跑，而不是继续在基准内加算子或加扫描点——后者提升的是覆盖度，不修复口径与生产之间的结构性偏差。
