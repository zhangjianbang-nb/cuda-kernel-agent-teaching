一 · 一个推荐系统的深夜现场

设想一个已经上线的推荐推理服务：请求进来后先做 embedding lookup，把几十个稀疏特征映射成稠密向量，再走若干层 MLP 与特征交叉，最后打分排序。整条链路里，真正吃满 GPU 的往往不是那些被论文反复引用的 GEMM，而是那个又宽又稀疏的 embedding 表——查表、去重、分桶、拼接，形状随 batch 内用户行为长度剧烈抖动，几乎没有现成的 cuBLAS 调用可以套。团队里最资深的 kernel 工程师花两周写出一版手写 CUDA，把 gather 与 reduce 融合进一个 block，端到端拿到一点几个百分点的收益；三个月后特征维度改了，那版 kernel 的 tile 假设全部失效，只能回退到 PyTorch 的 index_select 加 cat，性能回到原点。这就是《How Much of a Real Workload Can LLM-Generated GPU Kernels Actually Reach?》要面对的问题现场：不是“LLM 能不能写出比 PyTorch 快的 kernel”，而是“写出来的那点加速，究竟能覆盖真实负载里多大一块墙钟时间”。论文给出的答案很克制——在七个跨三个领域的负载上，可寻址比例从 8.9% 到 58.2%；在推荐系统上这个数字是 58.2%，且集中在一个 embedding kernel 上。

这个现场揭示了旧方案的结构性困境：kernel 工程的收益上限不由 kernel 本身决定，而由它在整条时间线上的占比决定。手写 CUDA 能拿到的那 1.5x、2x，乘以一个很小的占比，才是用户能感知的端到端收益。论文在 transformer 类负载上把这个乘法定量得很清楚：80–86% 的运行时间被 cuBLAS GEMM 与 FlashAttention 占据，于是即便你把剩下那 14–20% 全部优化到零，端到端提升也被钉死在约 1%，而且随着模型规模增大，这个比例还会继续缩小。旧方案的所有痛点——开发周期、性能上限、正确性、可维护性——本质上都是在这个“占比约束”下被放大的。

二 · 手写 CUDA：周期、上限与不可维护性

手写 CUDA 是过去十年 GPU kernel 工程的主流做法，它的机制是工程师直接对线程层次结构、共享内存布局、寄存器压力与指令级并行做决策。一个典型的融合算子要处理：global memory 的合并访问、shared memory 的 bank conflict 规避、warp 内 reduce 的 shuffle 序列、以及边界条件的 predication。这套机制的代价首先是开发周期——一个中等复杂度的 kernel 从设计到通过数值校验通常以周计，而其中大部分时间花在调试 race condition 与数值偏差上，而不是花在性能调优上。其次是性能上限：手写 kernel 的最优 tile 尺寸与展开因子是针对某一组 shape 调出来的，一旦输入分布漂移（batch 变小、序列变长、稀疏度变化），原本的最优配置就退化成次优，而重新调参又是一轮完整周期。

正确性是第三个痛点，也是最隐蔽的。手写 kernel 的数值行为与参考实现之间的差异往往出现在归约顺序、累加精度与边界处理上。一个在 fp32 下通过校验的 kernel，换到 tf32 或 bf16 输入时可能因为累加器精度不足而在长归约上产生可观测误差。论文的评测口径把这一点制度化了：候选必须先编译、再在给定输入上做正确性检查，然后才进入时延测量。这个顺序不是形式主义——如果先测性能再补正确性，工程师会不自觉地用“差不多对”的候选去换加速比，而这正是离线分数与生产表现脱节的根源之一。

可维护性是第四重代价，且它与前三条互相放大。手写 kernel 是一份用线程索引写成的、几乎没有抽象层的代码，它的每一行都编码了某个 shape 假设。当上游模型结构变化时，这份代码不是“需要调整”，而是“需要重写”。在推荐系统场景里，特征 schema 的迭代频率远高于 transformer 的层结构迭代频率，这意味着手写 kernel 的摊销周期被压得很短，工程投入很难回收。论文在推荐系统上测到的 58.2% 可寻址比例，恰恰落在一个 schema 频繁变动的领域——这既是机会，也是旧方案最痛的地方：机会在于有大量时间可以被优化，痛在于手写方案跟不上变动节奏。

三 · Triton 与库调用：把上限交给别人

Triton 的出现把 kernel 开发的门槛降了一档：工程师用块级（block-level）的抽象描述计算，编译器负责线程映射、共享内存分配与流水线调度。它的机制优势在于把“怎么写对”从工程师手里接走了一部分，代价是把“能不能写到极限”交给了编译器。对于规整的、以 GEMM 与 elementwise 为主的负载，Triton 生成的代码可以接近库实现；但对于形状高度不规则、需要精细控制访存模式的算子（例如稀疏 embedding 的 gather-reduce 融合），Triton 的块级抽象会强制一种规整的切分，导致要么浪费线程，要么引入额外的中间缓冲。这个代价是带宽与显存：不合适的切分会让有效带宽利用率下降，中间缓冲则直接吃掉显存容量，在长序列或大 batch 下成为硬约束。

库调用是另一条路径：直接调 cuBLAS、cuDNN、FlashAttention 这类经过深度调优的实现。它的机制是把性能上限外包给库作者，代价是把灵活性归零。库函数只对它能识别的 shape 与数据类型走快速路径，一旦遇到非标准布局或融合需求，就要么退回慢路径，要么被迫拆成多个调用、付出额外的 kernel launch 与中间张量读写开销。论文的基线口径明确包含 PyTorch eager、torch.compile 与论文指定的库实现——这意味着任何声称的加速比都是相对这些已经很强的基线而言的，而不是相对一个朴素的 naive 实现。这一点在解读 22/56 的独立验证加速比与 1.235x 的中位数时必须记住：分母不是软柿子。

把三条路径放在一起看，旧方案的共同结构是：性能上限被“谁来做最后的调度决策”所决定，而开发周期被“这个决策需要多少人天”所决定。手写 CUDA 把决策权拿回来但付出人天，Triton 交出部分决策权换取人天，库调用交出全部决策权换取零人天但放弃上限。三者之间没有一条路径能同时满足“快、对、可维护、跟得上迭代”。这正是 LLM 生成 kernel 试图插入的空隙——它不是要取代库，而是要在库覆盖不到的那块不规则地形上，用可验证的自动生成替代手写。

四 · 正确性与性能的双门：为什么旧流程会虚高

旧方案在评测上的一个系统性偏差，是把“能跑”当成“对”，把“某组 shape 上快”当成“快”。论文的流程把这两件事拆成两道门：先编译，再在给定输入分布上做正确性检查，然后用统一基线测时延与加速比，最后按反馈保留或回退。这个顺序对应一个简单的判据：候选只有在正确性门通过后，其性能数字才被计入。用公式表达，单个问题的加速比定义为基线时延与候选时延之比，而整体分数是加速比超过阈值 τ 的问题占比：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

这个定义看似简单，但它把“正确性”与“加速”绑定在同一个指示函数里：一个数值错误的候选即使时延再低，也不贡献分数。旧流程的虚高恰恰来自绕过这道绑定——用 shape 特化把候选调到某个特定输入上极快，却在隐藏输入分布上崩塌；或者用 fallback 机制在检测到不利条件时悄悄退回基线实现，让正确率看起来很高而实际加速来自别处。论文摘要级的结论已经暴露了这种偏差的量级：前沿模型在 KernelBench level 1 上正确率达到 91.1%，但独立验证的加速比只出现在 56 个问题中的 22 个，中位数 1.235x；开放权重模型最好只到 30.4% 正确率、三个验证加速比、卷积全灭。正确率与加速比之间的这道鸿沟，就是旧评测口径没有分开的两件事。

代价在这里体现为 token 与编译时间：每一次候选生成、编译、正确性检查、时延测量都是一轮完整的反馈回路，而多轮搜索会把这条回路重复很多次。如果正确性门放在性能门之后，那么大量算力与 token 会被浪费在“快但错”的候选上；如果放在之前，则每一轮都要付出编译与数值校验的固定开销。论文选择先正确后性能，等于用编译时间换掉了无效的性能测量——这是一个工程判断，而不是一个评测细节。

五 · 可寻址比例：旧方案看不见的分母

旧方案最根本的盲点，是它从不问“这块 kernel 在真实负载里占多少时间”。手写工程师的 KPI 是单算子加速比，Triton 用户的 KPI 是能否写出可用的融合，库调用的 KPI 是命中快速路径的比例——三者都不对端到端墙钟负责。论文引入的“可寻址比例”（addressable fraction）正是把这个分母显式化：对一个真实模型做 profile，把运行时间按 kernel 归类，算出其中有多少落在“可以被生成式方法改写且值得改写”的那部分。七个负载、三个领域的结果是 8.9% 到 58.2% 的跨度，这个跨度本身就是对旧方案的一记提醒——同样一套 kernel 工程技术，在不同负载上的投资回报率相差数倍。

transformer 类负载把这个约束推到极端：80–86% 的时间在 cuBLAS GEMM 与 FlashAttention 上，这两块是库作者与硬件厂商投入最多的阵地，生成式方法很难在这里取得稳定优势，于是端到端提升被限制在约 1%，且随模型规模增大而继续缩小。推荐系统则相反：58.2% 的时间集中在一个 embedding kernel 上，这是一个形状不规则、库覆盖薄、手写成本高的位置，恰好是生成式方法的用武之地。论文为此构造了 DLRM-Bench，12 个 KernelBench 格式的推荐 kernel 问题，在上面测到 41.7% 的胜率与 1.552x 的中位加速比，并据此投影出 8.63% 的端到端收益。注意这里的逻辑链条：单算子中位 1.552x 乘以可寻址比例，才得到 8.63%——旧方案只报前者，不报后者，于是读者会误以为 1.552x 就是用户能拿到的收益。

这张表的意义不在于数字本身，而在于它把“值不值得做”变成一个可测量的问题。旧方案的工程判断依赖经验与直觉：资深工程师知道 embedding 值得写、GEMM 不值得写，但这种知识无法传递、无法量化、无法在模型结构变化时快速重估。可寻址比例把这个判断变成一次 profile 就能回答的问题，代价是一次完整的性能剖析——它会引入额外的测量开销与扰动，但在离线评估阶段这是可接受的。

六 · 为什么非改不可：迭代速度与验证成本的对撞

把旧方案的四重痛点放回推荐系统现场，会看到一个自我强化的循环：schema 迭代快 → 手写 kernel 摊销周期短 → 团队倾向于不写、退回库调用 → 库调用在不规则形状上效率低 → 端到端收益停滞 → 但没人有动力去写，因为写了也很快失效。打破这个循环需要的不是更强的工程师，而是更低的单次尝试成本与更可靠的验证。LLM 生成 kernel 的价值主张正在于此：把一次尝试的成本从“两周人天”压到“一次生成加一次编译加一次正确性检查”，使得在 schema 变动后快速重试成为经济上可行的选项。但这个主张只有在验证可信时才成立——如果正确性门形同虚设，快速重试只会快速产出虚高的数字。

论文的 91.1% 与 30.4% 之间的落差，说明这条路径目前是分层的：前沿模型能在 level 1 上产出大量正确候选，但独立验证的加速比只覆盖 56 个问题中的 22 个；开放权重模型连正确率都只有三成，卷积问题全灭。这意味着“非改不可”的紧迫性不是均匀分布的——在 embedding 这类库覆盖薄、形状不规则的位置，生成式方法已经有可测量的收益；在 GEMM 与注意力这类库投入密集的位置，它还没有证明自己能稳定超过基线。工程判断因此不是“全面替换手写”，而是“按可寻址比例分配尝试预算”：先 profile 找出占比高且库覆盖薄的那块，再在那里投入生成与验证的循环，其余部分继续用库。

这个判断的代价是明确的：profile 需要额外一轮测量，生成与验证需要编译时间与 token 预算，而收益被可寻址比例封顶。在 transformer 上，即便生成式方法把可寻址的那 14–20% 全部拿下，端到端也只有约 1%，这个投入产出比在多数团队里不成立；在推荐系统上，58.2% 的可寻址比例配上 1.552x 的中位单算子加速，投影出 8.63% 的端到端收益，这个数字才足以支撑一次工程改造。旧方案之所以非改不可，不是因为手写 CUDA 不好，而是因为它把工程注意力均匀地铺在所有 kernel 上，而真实负载的时间分布是极度不均匀的——不改，就意味着持续把人力投入到占比很小、上限很低的位置上。
