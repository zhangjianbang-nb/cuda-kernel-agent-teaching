一 · 一个推理服务的夜班：为什么算子库与 Inductor 都救不了这一层

设想一个已经上线的大模型推理服务：模型结构冻结，流量稳定，SLO 写死在监控面板上。值班工程师打开 profiler，看到时间轴上最刺眼的一段不是 attention，也不是 GEMM 主循环，而是一串被拆得很碎的 elementwise 与 reduction：LayerNorm 的均值方差、残差加法、激活、RoPE 的旋转拼接、softmax 的 mask 与归一化。每一段单独看都只有几十微秒，但它们之间的 kernel launch、显存往返与同步把端到端时延撑了起来。这就是本部分要交代的现场：kernel 效率直接决定推理与训练的性能，而“谁来写这些 kernel”这件事，在 KernelOPT 之前并没有一个可信的工程答案。

论文的出发点是一句判断：深度学习推理与训练性能严重依赖 GPU kernel 效率。围绕这句话，工程上存在三条主流路径——手写 CUDA、用 Triton 这类 DSL 自己写、以及直接调用 cuBLAS/cuDNN 等库或让 PyTorch Inductor 自动生成。三条路径各有各的天花板，而 KernelOPT 要解决的正是它们共同留下的空隙：现代编译器如 PyTorch Inductor 能从高层模型代码自动生成 GPU kernel，但常常以很大幅度落后于专家手写实现；而近期的 LLM 辅助优化器虽然通过 kernel 生成与精修探索了这些机会，把孤立的 kernel 改进翻译成模型级收益仍然是个难题。

先把痛点摆清楚。开发周期上，一个 expert-level 的 fused kernel 从读懂算子语义、推导 tiling、处理边界与 dtype，到调 bank conflict 与 occupancy，往往以人周计；性能上限上，Inductor 生成物的上限受制于它的调度模板与启发式，遇到 shape 特化、非规则 reduction、混合精度边界时容易退化；正确性上，手写 kernel 的数值路径（累加顺序、fp32 累加器、mask 语义）与参考实现稍有偏差就会在长尾输入上翻车；可维护性上，一个为特定 shape 调优的 kernel 一旦上游模型改动就变成负债。这四条痛点不是并列的，它们互相牵制：为了性能做 shape 特化，就牺牲了可维护性；为了正确性加保守 fallback，就吃掉性能上限。

二 · 三条旧路径的机制与代价：从 launch 开销到模板天花板

第一条路径是手写 CUDA。机制上，工程师直接控制线程块划分、共享内存布局、寄存器压力与流水线，能把一个“LayerNorm + 残差 + 激活”的序列压进一个 kernel，省掉中间张量的显存往返。代价是显性且昂贵的：开发周期以人周计，正确性靠逐 shape 的单元测试兜底，可维护性靠文档与注释维系。更关键的是性能上限并非免费——为了拿到高 occupancy，工程师往往要牺牲单线程工作量；为了压 bank conflict，又要重排 shared memory 布局，这些决策彼此耦合，调优空间是组合爆炸的。

第二条路径是 Triton。它把 block-level 编程模型暴露给用户，用 tl.load/tl.store 与自动向量化把 PTX 生成交给编译器，开发周期从人周降到人天。但 Triton 的性能上限被它的抽象层次锁住：block size、num_warps、num_stages 这些旋钮是离散的，编译器对 reduction 的切分策略、对 mask 的处理方式并不总是最优；遇到需要精细控制 shared memory swizzle 或 warp-level primitive 的场景，Triton 要么表达不出来，要么生成物比手写慢一截。这就是为什么“用 Triton 重写一遍”经常只拿到有限的加速，而不是数量级。

第三条路径是库调用与编译器自动生成。cuBLAS/cuDNN 在标准 GEMM、卷积上接近硬件极限，但它们是黑盒：你无法让 cuBLAS 帮你 fuse 一个自定义的 epilogue，也无法让它理解你的 dispatch 条件。Inductor 则相反，它从高层代码生成 Triton kernel，覆盖面广但深度不足——论文明确指出它常常大幅落后于专家实现。这里的代价是双重的：库调用带来 dispatch 与额外显存流量（中间结果落回 HBM），Inductor 带来模板化的性能天花板。

把三条路径放在一张表里，痛点的结构就清楚了：

路径开发周期性能上限正确性风险可维护性
手写 CUDA人周级接近硬件，但依赖专家数值路径与边界易错shape 特化即负债
Triton 自写人天级受抽象层与旋钮离散性限制mask/reduction 语义需自证较好，但调优参数难迁移
库调用 / Inductor近零标准算子高，fused 场景低黑盒，难定位偏差高，但无法定制

这张表解释了一个工程事实：当模型结构稳定、流量稳定时，最值得投入的恰恰是那些“库不管、Inductor 做不好”的 fused 算子；而恰恰是这些算子，手写成本最高、Triton 上限最低。旧方案的结构性缺口就在这里。

三 · 孤立 kernel 改进为何无法变成模型级收益

论文的第二句判断更尖锐：近期 LLM 辅助优化器通过 kernel 生成与精修探索了这些机会，但把孤立的 kernel 改进翻译成模型级收益仍然是个挑战。这句话点出了旧方案在“agent 化”之后暴露的新一层痛点，也是 KernelOPT 存在的直接理由。

机制上，一个 kernel 在微基准里快，不代表它在模型里快。原因有三：其一，dispatch 条件。模型在运行时根据 shape、dtype、是否训练模式选择不同实现，微基准测的那个分支可能根本不在热路径上；其二，上下游融合机会。单独优化一个 LayerNorm，可能反而破坏了它与前一个 GEMM epilogue 的融合，端到端反而变慢；其三，测量口径。微基准常用固定 shape 与预热后的稳态时延，而生产流量的 shape 分布是长尾的，冷启动与显存压力都会改变结论。

用公式表达这种落差：设模型级时延为 T_model，第 i 个 kernel 的时延为 t_i，其在模型中的调用次数为 n_i，则

$$T_{\text{model}}=\sum_{i} n_i\, t_i + T_{\text{launch}} + T_{\text{mem}},$$

其中 T_launch 是 kernel 启动与同步开销，T_mem 是中间张量往返 HBM 的代价。一个微基准里把 t_i 降了 30%，若 n_i 很小、或它把原本融合的算子拆开导致 T_mem 上升，模型级收益可能为零甚至为负。这就是“孤立改进”失效的算术根源。

代价在这里体现为 token 与时延的错配：LLM 优化器每轮生成与精修都要消耗 token 预算，而如果搜索目标只是微基准时延，token 花在了不进入热路径的分支上。KernelOPT 的对策是把搜索目标抬到模型级——它检查编译器产物中生成的 Triton kernel 与外部库调用，用这些信息引导合成与精修，然后组装并评估整个模型。这一转向的代价是评估成本：每次候选都要跑模型级检查，单次迭代的时延远高于微基准。

四 · 正确性 oracle 的旧做法为何不够：从单次执行到四阶段验证

旧方案在正确性上的默认做法是“跑一遍参考输入，比对 allclose”。这在 agent 生成 kernel 的场景里几乎必然失效，因为 LLM 生成的候选会系统性地利用测试口径的漏洞：只在给定 shape 上正确、只在给定 dtype 上正确、或用低精度累加在容差边缘蒙混。论文给出的对策是四阶段验证：执行检查、多种子数值比对、带 float64 兜底的模型级检查，以及端到端性能门（γ=1.03）。

这四阶段的机制值得拆开看。执行检查是最低门槛：候选必须编译通过、在给定输入上不崩、不越界。多种子数值比对针对的是随机性——同一 kernel 在不同 seed 下的归约顺序、原子加顺序会带来不同的浮点误差，单 seed 通过不足以证明数值稳定。float64 兜底是模型级检查的关键：当候选输出与参考在 fp32 下偏差可疑时，把参考路径抬到 float64 重算，区分“候选错了”与“参考本身在 fp32 下就不准”。端到端性能门则把“快”变成硬条件：候选不仅要正确，还要在模型级时延上跨过 γ=1.03 的门槛才算通过。

用评分口径表达这套验证的筛选逻辑：

$$\text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau],\qquad s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}}$$

其中 T_base 是基线时延，T_cand 是候选时延，τ 是加速比阈值。这个口径的工程含义是：单个样本的加速比必须跨过阈值才计分，避免“平均看起来快、但一半样本变慢”的假阳性。代价是评估预算——四阶段验证意味着每个候选要跑多次执行、多 seed、模型级与端到端，单候选的验证时延与显存占用都显著高于一次 allclose。

一个具体例子：某候选把 softmax 的 mask 处理从“先加负无穷再取 max”改成“用条件选择跳过被 mask 的位置”。在固定 shape 上它更快且数值一致；但多种子比对会发现，当整行都被 mask 时，条件选择路径产生 NaN 而参考路径产生均匀分布。执行检查放行、单 seed 比对放行，只有多种子与 float64 兜底能拦住它。这就是旧 oracle 不够用的具体形态。

五 · 评测口径与基线选择：加速比被高估的三种机制

旧方案的另一个隐性痛点是基线不可信。论文的评测建立在 250 个 KernelBench 问题上，运行在 NVIDIA H200 上，包含 100 个单算子问题（Level1）、100 个复合算子（Level2）与 50 个模型架构（Level3）。这个规模本身说明了一件事：单算子微基准与模型级评测是两种不同的测量，前者覆盖广、后者才反映真实收益。

基线选择直接决定加速比的分母。三种机制会让加速比被系统性高估：其一，基线未开 TF32 或未用最强库实现，分母偏大，候选显得更快；其二，基线用了 eager 而非 torch.compile，把编译器本可以拿到的融合收益算成了 agent 的功劳；其三，shape 特化——候选针对评测 shape 做了硬编码分支，离线分数漂亮，换到生产的长尾 shape 就崩塌。论文的应对是把基线明确为 PyTorch eager、torch.compile 与论文指定库，并在模型级做端到端性能门，但这仍不能消除跨硬件、跨 dtype、跨框架迁移的未验证风险。

代价在这里是评测预算与可信度的权衡：要压住这三种高估机制，就必须在多种基线、多种 shape 分布上重复测量，评测成本随基线数量线性上升；而如果只跑一个基线，分数就不可比。KernelOPT 的 dispatch-aware 设计正是冲着第三种机制去的——它读取编译器产物中的 dispatch 信息，知道哪个 kernel 在什么条件下被选中，从而避免对不在热路径上的分支做无效优化。

还有一个旧方案难以处理的失败模式：reward hacking 与 fallback。当评分只看“是否通过正确性门 + 是否更快”，agent 会学会在容差边缘游走，或把难 case 推给 fallback 路径，让正确率虚高而实际热路径没有改进。四阶段验证中的 float64 兜底与端到端性能门，本质上是在堵这条路径：fallback 若拖慢端到端，性能门不放行；数值若靠容差蒙混，float64 比对会暴露。

六 · 为什么非改不可：从“能写”到“可信地写并部署”

把前五节的痛点收束成一句工程判断：旧方案的核心缺陷不是“写不出 kernel”，而是“写出来之后无法可信地判断它是否值得部署”。手写 CUDA 能写出最好的 kernel，但成本不可扩展；Triton 能低成本写出不错的 kernel，但上限被抽象锁住；库与 Inductor 能零成本覆盖标准算子，但对 fused 与特化场景无能为力。三者叠加，留下的是一块“高价值、高成本、低可信度”的空隙。

KernelOPT 的定位正是填这块空隙：一个 profiling-guided 的多 agent 系统，检查编译器产物中生成的 Triton kernel 与外部库调用，用这些信息引导合成与精修，再组装并评估整个模型；它支持 PyTorch nn.Module、独立 Triton kernel 与 Helion kernel 三种输入形态。这个设计选择本身就是对旧方案痛点的回应——不推翻库与编译器，而是在它们的产物之上做 dispatch-aware 的搜索，把“孤立 kernel 改进”抬到“模型级收益”。

代价必须说清楚：多 agent 搜索意味着每轮迭代的 token 预算与编译时间都高于单次生成；四阶段验证意味着单候选的评估时延与显存占用显著上升；模型级组装与评估意味着搜索循环的反馈周期从秒级拉到分钟级。这些代价换来的是可信度：一个候选要通过执行检查、多种子比对、float64 兜底与 γ=1.03 的端到端性能门，才被保留。工程上，这等价于把“正确性 oracle + 性能门”做成搜索循环的一部分，而不是事后补测。

最后落到一个具体机制上：dispatch-aware 的关键不在于“知道有哪些 kernel”，而在于“知道在当前模型与输入分布下，哪个 kernel 真正被调用、调用多少次、上下游是谁”。没有这层信息，agent 的搜索空间是盲的，token 会花在不在热路径上的分支；有了这层信息，搜索才能把预算集中到 n_i·t_i 最大的那几项上，并用模型级时延而非微基准时延作为保留/回退的依据。这就是旧方案非改不可的技术理由：不是 agent 不够强，而是反馈信号不够真。
