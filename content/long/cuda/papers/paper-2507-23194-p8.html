一 · 从 kernel 加速比到端到端收益的映射

内核级加速比是必要条件，不是上线依据。生产端到端时延由数据搬运、框架调度、主机侧同步与内核执行共同构成，Amdahl 型分解给出上限：若目标内核在端到端时延中占比为 f，候选相对基线的加速比为 s，则端到端加速比不超过 1/((1−f)+f/s)。当 f=0.2、s=3 时端到端上限约 1.15；当 f=0.05 时即便 s=10 也只有约 1.04。这意味着在把 Geak 闭环产出的 Triton 候选推入生产前，第一件事是测出 f，而不是看基准里的 score。

$$\mathrm{Speedup_{e2e}}\le\frac{1}{(1-f)+f/s},\qquad f=\frac{T_{\mathrm{kernel,base}}}{T_{\mathrm{e2e,base}}}$$

具体机制上，f 的测量要贴着真实调用路径：把参考实现与候选分别放进同一段前向代码，用同一 batch、同一 dtype、同一 stream 配置，分别记录 CUDA event 包裹的端到端区间与内核自身区间。代价在于这一步需要生产侧的可观测性投入：若框架默认开启同步点或每层做 dtype 转换，内核计时会被主机侧空转稀释，profile 出来的 f 偏小，导致错误地放弃一个本可上线的候选。一个典型例子是 LayerNorm 类算子：基准里单算子加速 2 倍，但生产前向中该算子前后各有一次 layout 变换与一次 all-reduce，f 被压到 0.1 以下，端到端收益不足 5%，而引入 Triton 候选带来的额外编译与加载路径反而增加了首帧时延。

二 · fallback 与框架集成的工程形态

生产集成的核心不是“替换内核”，而是“可回退地替换内核”。可接受的形态是运行时分派：以算子语义、shape 区间、dtype 与硬件能力为键，命中已通过正确性门与性能门的候选则走 Triton 路径，否则回落到基线实现。分派表本身要有版本号，与候选的编译产物、Triton 版本、CUDA 版本绑定，避免 A/B 环境混用。伪代码思路如下：

  • 入口处读取 shape/dtype/设备能力，查分派表；未命中直接调用基线，零额外开销。
  • 命中后首次调用触发 Triton 编译与缓存加载，编译失败或超时则永久降级该键并记录事件。
  • 运行期以轻量校验（输出 dtype、shape、有限值检查）兜底，异常时切回基线并上报。
  • 分派表与候选产物随发布包分发，禁止运行时从网络拉取内核源码。

代价集中在三处：首次调用的编译时延（Triton JIT 在冷缓存下会阻塞首个 batch，需用预热或离线编译缓存消除）、分派查表的每调用开销（Python 侧字典查找在微秒级，对高频小算子不可忽略，应下沉到 C++ 侧或做静态绑定）、以及双路径并存的显存占用（候选与基线各自的 workspace 与中间缓冲不能同时驻留）。一个具体例子是把 Geak 产出的 reduction 候选接入推理框架：预热阶段对覆盖生产 shape 分布的若干档位做离线编译并落盘缓存，运行时只做键匹配与加载，首帧时延回到基线水平；而未做预热的接入方式在长尾 shape 上触发 JIT，表现为偶发的百毫秒级抖动。

三 · 维护成本：候选是资产还是负债

自动生成的 Triton 内核进入代码库后，维护成本按“每次工具链升级的回归面”计。Triton 的语义与 lowering 随版本演进，同一份候选在新版本上可能编译失败或数值漂移；CUDA 驱动与 GPU 架构变更会改变 occupancy 与访存行为，基准里的加速比不保证在新卡上复现。因此每个候选都需要绑定：语义说明、参考实现、正确性用例集（含边界 shape 与异常输入）、计时口径与基线版本、目标硬件清单。缺少任一项，候选就从资产变成不可验证的负债。

维护项触发条件代价形态
工具链回归Triton/CUDA 版本升级全量候选重编译与正确性重跑，CI 时长增长
硬件迁移换卡或扩卡型需在新卡重测 f 与加速比，部分候选失效需下线
shape 漂移业务输入分布变化分派表命中率下降，长尾触发 JIT 抖动
基线演进上游库更新更快实现原加速比被吃掉，候选需重评或删除

具体机制上，把候选纳入 CI 的正确性 oracle 应是“与参考实现逐元素比对 + 边界 shape 覆盖”，而不是只跑基准里的固定输入；计时则需固定预热次数与重复次数，否则回归信号被噪声淹没。代价是 CI 资源：每个候选在每个目标卡型上都要跑一遍编译与计时，候选数量增长会线性推高流水线时长与 GPU 机时占用。一个具体例子是归约类候选在换用不同 SM 数量的卡后，块大小与 warp 数不再匹配，正确性仍过但性能跌回基线以下，若没有硬件清单与重测流程，这类退化会在生产里静默存在。

四 · 跨硬件迁移的失效边界

Triton 的块级抽象让候选在源码层可移植，但性能可移植性依赖 autotune 配置与硬件特征。迁移时最先失效的是显式写死的 num_warps、BLOCK_SIZE 与流水级数：在小卡上块过大导致 occupancy 不足，在大卡上块过小导致访存合并度下降。其次是共享内存与寄存器预算，候选在一种架构上刚好不溢出，换架构后 spill 到本地内存，带宽骤降。再次是数值路径，不同架构的 FMA 与归约顺序差异会让原本贴着容差边界的候选越界。

工程判断上，跨硬件迁移应把 autotune 配置作为候选的一部分随硬件键分发，而不是在运行时盲目搜索；盲目搜索的代价是首次调用时对多组配置逐一编译与计时，在服务冷启动窗口内不可接受。一个具体例子是矩阵乘类候选：在基准卡上以较大 tile 取得加速，迁到显存带宽更低、SM 更少的卡上后 tile 导致 occupancy 掉到个位数，性能低于基线；若分派表按硬件能力设了阈值并在未命中时回落，则退化被限制在个别档位，而不是全局劣化。

五 · 什么情况下不值得上线

上线决策应由三个门共同决定，任一不过即不上：正确性门（参考比对通过且边界 shape 覆盖充分）、端到端门（按 f 折算后的端到端收益超过运维与回归成本）、可维护门（候选具备完整元数据、能在目标硬件清单上重测、有明确 fallback）。据此可列出典型的不值得上线情形：

  • f 过低：内核在端到端中占比小，折算后收益落在测量噪声内，替换只增加路径复杂度。
  • 基线已足够快：上游库更新后原加速比被吃掉，候选的边际收益不足以抵消回归成本。
  • shape 分布长尾：生产输入高度离散，分派表命中率低，JIT 抖动与缓存膨胀的代价超过命中部分的收益。
  • 硬件清单不稳定：目标卡型频繁变更或混布，候选无法在固定硬件上重测，性能承诺不可兑现。
  • 正确性 oracle 不严：容差与边界覆盖不足，候选在异常输入上静默出错的风险高于其性能收益。

代价的量化方式是把“上线收益”写成端到端时延节省乘以调用频次，再减去编译缓存维护、CI 重测机时与 fallback 路径的常驻开销；当净值为负或落在噪声区间，正确的工程动作是保留候选作为离线参考而不进入生产路径。一个具体例子是高频小算子：单次内核节省数微秒，但分派查表与轻量校验的每调用开销在同一量级，端到端净值接近零，且双路径并存增加了故障面，此时不上线是更稳的判断。真正值得上线的是 f 足够高、shape 分布集中、硬件清单稳定、且候选带有可复现元数据的那一类；Geak 闭环的价值在于把这类候选筛出来并留下可核对的轨迹，而不是把基准分数直接当作上线许可。

上线判据：从 kernel 加速比到端到端收益的折算与失效边界

kernel 级加速比与端到端收益之间不存在线性映射，中间隔着调用频次、数据搬运、框架调度与同步开销四道折损。设某算子单次调用在基线实现下耗时 T_base，候选内核耗时 T_cand，单次调用可省 Δ = T_base − T_cand；但候选往往需要额外的 layout 转换、临时缓冲区分配或 host 侧参数打包，记这部分固定开销为 C_glue，则端到端净收益为：

$$\mathrm{speedup_{e2e}}=\frac{T_{\mathrm{total}}}{T_{\mathrm{total}}-\sum_{k} n_k\left(\Delta_k-C_{\mathrm{glue},k}\right)}$$

其中 n_k 是该算子在一次端到端请求中的调用次数。这个式子的工程含义很直接：当 n_k 很小（例如 decode 阶段每层只调一次的小算子），C_glue 一旦与 Δ 同量级，净收益就被吃掉，甚至为负。更隐蔽的是同步代价——Triton 内核若引入额外的 cudaDeviceSynchronize 或隐式 stream 同步用于计时与校验，会把异步流水打断，端到端时延反而上升。判断是否值得上线，第一步不是看基准里的加速比，而是把 n_k、Δ_k 与 C_glue,k 三者实测出来，代入上式做一次折算；任何一项缺失，上线决策就缺少依据。

框架集成与 fallback 是第二道边界。生产路径不能假设候选内核永远正确：shape 越界、dtype 不在覆盖范围、驱动或 Triton 版本不匹配时，必须有确定性回退到参考实现的分支，且回退判定本身要廉价——若每次调用都做一次运行时 shape 检查与分支，这个判断开销可能超过内核节省的时间。合理的做法是把覆盖条件在编译期固化为特化分支，仅对不满足条件的输入走 fallback，并把 fallback 触发率作为上线后的观测指标；触发率偏高说明特化范围选错，等于用维护成本换了一个很少生效的快路径。维护成本还体现在软件栈耦合上：Triton 与 CUDA 版本差异会改变编译产物与性能，材料明确指出未固定软件栈版本时编译差异会污染性能比较，因此每次升级驱动或框架都要重跑正确性比对与计时，这笔回归成本必须计入上线预算，而非一次性投入。

跨硬件迁移会进一步压缩收益窗口。同一份 Triton 内核在不同 SM 数量、不同 shared memory 容量与不同 L2 结构上，块大小与流水深度的最优配置并不一致；基准里调好的 BLOCK_SIZE 与 num_warps 迁移到另一张卡上可能从加速变为退化。材料未披露基线名称、计时方法与预热策略，也未说明容差阈值与边界 shape 的处理方式，这意味着跨平台复用同一组性能数字本身就不成立，迁移时必须在新硬件上重做 autotune 与正确性校验。至于防作弊，材料同样未披露机制，无法判断基准分数是否被针对输入分布的过拟合策略抬高；上线前应自行构造分布外 shape 与极端 dtype 做抽检，而不是直接采信基准通过率。综合来看，不值得上线的情形可以归纳为三类：调用频次低到 n_k·Δ_k 无法覆盖 C_glue 与回归成本；fallback 触发率高、快路径实际很少命中；以及目标硬件与评测硬件不一致且缺少重测预算。反过来，只有当端到端折算为正、fallback 路径经过故障注入验证、且软件栈升级后的回归流程已经脚本化时，kernel 级加速才构成可交付的生产收益。
