一 · 正确性漏检：容差判定下的“假通过”与 shape 盲区

KernelBench 的语义判定只有一条硬规则：候选内核与 PyTorch 参考实现在完全相同的输入张量上逐元素比对，超出容差即判语义错误。这条规则在评测层是干净的，但在诊断层留下了两个必须正视的漏检通道。第一条是容差本身的松紧：逐元素无穷范数判定 ‖y_kernel − y_pytorch‖∞ ≤ ε 对归约类算子（softmax、layernorm、sum）天然宽容，因为参考实现自身在 float32 累加顺序上与候选不同，误差量级随归约长度增长；若 ε 取固定值而不随 dtype 与归约规模缩放，长归约上的错误累加可能被整体吞掉。诊断上应把比对拆成两层：先做 dtype 相关的相对误差 ‖y_k − y_p‖∞ / (‖y_p‖∞ + δ)，再对归约轴单独统计误差随长度的斜率，斜率异常抬升即为累加顺序错误的信号，而不是简单判过。

第二条漏检通道是 shape 覆盖。基准为每题规定输入 shape 与 dtype 分布，候选内核只需在这组 shape 上通过。生成模型极易写出硬编码块大小、假定整除、假定最后一维对齐的内核，在基准 shape 上数值完全正确，一旦维度不整除或 stride 非连续就静默越界或读错偏移。这类错误的代价不在评测时延，而在部署时的显存越界与结果污染。工程上的定位手段是给每个候选内核补一组扰动 shape：把基准 shape 的每个维度分别加减一个非对齐量（如 1、3、17），重跑同一比对；通过率在扰动集上骤降即判定为 shape 特化。这一步的额外成本是每个样本多出数倍的前向时延与显存峰值，但相比把特化内核放进生产，这个代价是必须付的。

$$\text{RelErr}=\frac{\lVert y_k-y_p\rVert_\infty}{\lVert y_p\rVert_\infty+\delta},\qquad \text{SpecFlag}=\mathbb{1}\left[\text{Pass}_{\text{perturbed}} \ll \text{Pass}_{\text{bench}}\right]$$

具体例子：一道 layernorm 任务，基准 shape 为 (B, H) 且 H 为 2 的幂。候选内核把 H 硬编码为编译期常量并假设线程块恰好覆盖一行，基准上逐元素误差在容差内。把 H 改为 1000 后，块内跨步读越界，输出尾部元素为未初始化显存值，无穷范数误差直接爆表——这就是 shape 特化在扰动集上暴露的典型形态。诊断报告应把“基准通过、扰动失败”单列为一类，与“基准即失败”区分开，因为前者是泛化缺陷，后者是能力缺陷。

二 · batch invariance 违规：批内耦合的隐蔽错误

batch invariance 指同一输入在不同 batch 组成下应得到逐位一致（或在容差内一致）的输出。许多生成内核为了压测时延，把归约维度与 batch 维度合并做跨样本归约，或把 batch 大小写进 kernel launch 配置做特化，导致单样本推理与批推理结果不一致。KernelBench 的评测口径以固定输入张量比对，天然无法捕捉这类违规：只要基准 batch 下数值正确，内核就判过。但生产端到端收益恰恰依赖批推理，批内耦合会在动态 batching 的服务里造成结果漂移，且漂移量随 batch 组成变化，难以用固定容差兜住。

监控机制是在正确性 oracle 之外加一条不变性检查：取同一批样本，分别以 batch=1、batch=基准值、以及随机打乱顺序的 batch 组成各跑一次，比对逐样本输出。判定式为 max_i ‖y_i^{(b1)} − y_i^{(bN)}‖∞ ≤ ε_inv，ε_inv 应比主容差更紧，因为同一输入在同一内核上不应有数值路径差异。代价是三次前向的时延与显存，且对动态 shape 内核需要额外的 launch 配置枚举。定位上，若不变性失败而主比对通过，几乎可以锁定为跨样本归约或 batch 维度上的编译期常量折叠；修复方向是强制归约轴只在本样本内闭合，并把 batch 作为运行时参数而非模板参数。

具体例子：一个 softmax 内核把行归约写成块内归约后接块间归约，块间归约的共享内存缓冲按最大 batch 分配但未按实际 batch 清零。batch=1 时残留值恰好为零，结果正确；batch 打乱后残留值非零，部分样本的输出被污染。这类错误在基准口径下完全不可见，只有不变性检查能把它拉出来。工程判断是：凡是涉及归约与共享内存的内核，不变性检查的优先级不低于主比对。

三 · OOM 与性能回退：资源口径下的两类退化

OOM 在 KernelBench 口径里不是编译失败也不是语义错误，它发生在运行阶段，表现为显存分配失败或内核 launch 失败。生成模型常写出按基准 shape 静态分配中间缓冲的内核，或把整个归约轴物化到显存再二次归约，基准 shape 下勉强装下，扰动 shape 或更大 batch 下直接 OOM。诊断上应把峰值显存作为与加速比并列的观测项：在计时前后采样 torch.cuda.max_memory_allocated，与 PyTorch 基线的峰值显存做比值。比值显著高于基线（例如中间缓冲物化导致数倍膨胀）即标记为显存回退，即便加速比为正也不能放行。代价是显存采样本身引入同步点，会轻微扰动计时，因此采样应与计时分开跑两轮。

性能回退的形态更隐蔽：候选内核在基准 shape 上加速比为正，但在扰动 shape 或不同 dtype 下跌到基线以下。根因通常是 launch 配置与 shape 绑定——块大小按基准维度整除选取，非整除时退化为大量尾块或串行循环。监控手段是记录每个样本在基准 shape 与扰动 shape 上的加速比向量，取最小值而非中位数作为放行依据；KernelBench 报告的是加速比分布，工程上应把分布的左尾当作风险指标。定位时把加速比与占用率、块数一起看：块数随 shape 剧烈跳变而加速比同步塌陷，即为 launch 配置特化。

四 · 静默降级：编译通过但语义漂移的中间态

静默降级指内核编译成功、基准比对通过，但实际执行路径与作者意图不符：编译器把越界访问优化掉、把未定义行为折叠成常量、或把 float32 累加自动降精度。这类问题在 KernelBench 的三类失败模式（编译失败、语义错误、性能不达标）里没有独立位置，因为它落在“语义正确”桶里。诊断手段是引入编译期告警与运行时哨兵：开启 -Xptxas -v 观察寄存器与溢出告警，对怀疑路径插入边界断言（在调试构建下启用，发布构建下关闭）。代价是调试构建的编译时间与运行时开销显著上升，因此只在候选进入放行评审前跑一次，而非每个样本都跑。

另一类静默降级来自数值路径：候选内核用 half 累加替代 float 累加以换取带宽，基准容差下通过，但在长归约或大动态范围输入上误差累积。定位方式是做 dtype 敏感性扫描：同一 shape 下把输入 dtype 从 float32 换成 float16 再换回，观察输出误差是否随 dtype 跳变；跳变即说明内核内部精度路径与声明不符。工程判断是：凡是加速比异常高且误差贴近容差边界的样本，优先怀疑精度降级而非真实优化，因为真实优化通常伴随误差量级不变。

具体例子：一个矩阵乘内核把共享内存 tile 的边界检查写成 if (row < M && col < N) 但编译器在 M、N 为编译期常量时把条件折叠，越界线程读到的是相邻 tile 的残留数据，基准 shape 下恰好落在有效区，扰动 shape 下读出垃圾值。这类错误既不触发编译失败也不触发主比对失败（基准 shape 下），只有扰动集与边界断言能捕获。

五 · 监控、定位与回滚：把失败模式接进流水线

监控层的设计原则是让每个失败模式有独立的计数器，而不是汇总成一个通过率。KernelBench 把编译成功率单列已经开了这个头，工程上应继续拆：编译失败按错误类型分桶（语法、类型、launch 配置、链接），语义失败按误差形态分桶（整体偏移、尾部越界、归约斜率异常），性能失败按加速比区间分桶。每个桶对应一条诊断脚本，桶的计数变化直接指向根因类别，避免“通过率下降”这种无信息量的告警。

定位层的核心是把候选内核的失败复现成最小用例：从基准 shape 出发做维度二分，找到第一个使比对失败的最小扰动，再对该用例做单步调试或打印中间缓冲。这一步的 token 成本不可忽视——若把诊断交给 LLM agent 做多轮迭代，每轮都要把错误信息、shape、误差向量喂回模型，长上下文下的诊断轮次会快速消耗预算；因此诊断应优先用确定性脚本完成最小用例缩减，只在脚本无法归因时才升级到模型推理。

回滚层的判断标准是放行门的多重化：编译成功、主比对通过、扰动集通过、不变性通过、峰值显存不超基线倍数、加速比左尾不低于 1，六项全过才进入候选池。任一项失败即回滚到上一版内核或 PyTorch 基线路径，并把失败样本连同其 shape 指纹写入回归集，防止同一特化模式在后续生成中重复出现。回滚的代价是候选池吞吐下降——严格门会拒掉一批基准上加速比为正的样本——但这是把“基准通过”与“可部署”分开的必要成本。KernelBench 的材料未给出容差取值与重复测量次数，工程落地时必须自行约定并把约定写进回归集元数据，否则跨设备复现时失败模式无法对齐。

失败模式与诊断：正确性漏检、shape 特化、batch invariance 违规、OOM、性能回退、静默降级

KernelBench 的逐元素容差判定在固定 shape 与固定输入张量下只覆盖一个点，边界在于它无法区分「语义正确但数值路径不同」与「真正算错」。典型失效条件是候选内核把归约顺序改成树形而非顺序累加，在 $\varepsilon$ 宽松时通过、在长尾 shape 上误差累积越界；诊断手段是同一语义在多个 shape 上重复比对，并把误差分布（最大绝对误差、超容差元素占比）而非单一 Pass 布尔值记入报告。代价是评测时延随 shape 数线性增长，且每个额外 shape 都要重新编译与计时，token 与编译时间双重上升。

shape 特化与 batch invariance 违规是同一枚硬币的两面：候选内核按基准规定的 shape 硬编码 tile 大小与线程映射，在基准内加速比漂亮，换一个 batch 或非对齐维度即触发越界访存或静默降级为标量路径。监控方式是在计时前插入 shape 扰动探针——对同一算子跑基准 shape 与一个邻近 shape，比较两次输出与两次加速比；若加速比骤降而输出仍通过，说明走了回退分支。系统代价是探针本身占用显存与一次额外编译，且扰动 shape 可能触发 OOM，需要在独立进程或显存配额下隔离运行，否则 OOM 会污染整批评测。

性能回退与静默降级的定位依赖三元组之外的第四列：编译选项与计时中位数之外的方差。仅报中位数会掩盖候选内核首次运行含 JIT 开销、后续稳定但整体慢于基线的情形；应同时记录重复测量的离散度，离散度大即提示存在未预热路径或动态分支。回滚策略上，正确性通过但加速比低于基线的样本不应直接丢弃，而应标记为「性能不达标」保留在分布中，否则汇总会系统性高估方法成熟度。下表给出三类失败模式的可观测信号与处置。

失败模式可观测信号处置
正确性漏检邻近 shape 误差越界多 shape 比对，记误差分布
shape 特化/静默降级加速比骤降而输出通过扰动探针，隔离进程
OOM/性能回退进程崩溃、计时方差大显存配额，保留不达标样本
