一 · 一个推理服务的现场：kernel 不是"能跑就行"

设想一个已经上线的多模态推理服务：语言模型主干、一个扩散头、一个视频编码前端，三者共享同一批 Blackwell GPU。运维侧看到的不是"某个 kernel 快了多少倍"，而是三段相互纠缠的账：主干每 token 的时延、扩散头每步的去噪时延、以及整机在 FP8 与 NVFP4 混部下的显存占用。工程师打开 profile，发现时间并没有均匀地摊在矩阵乘上——真正吃掉预算的是那些"看起来不起眼"的算子：RMSNorm 的融合残差、RoPE 的复数旋转、注意力里 softmax 与 mask 的合流、扩散采样中的 group norm 与 timestep embedding 拼接、视频前端的 3D 卷积与 layout 变换。这些算子单个只占几微秒，但在一层里被调用几十次，且每次都要在 HBM 上往返读写中间张量。

于是现场出现了一个典型的工程动作：把这些算子手写成融合 CUDA kernel。工程师会先量一个基线——PyTorch eager 下的算子链，再量 torch.compile 之后的版本，最后量手写融合版本。三次测量给出三个不同的数字，而"到底还能不能再快"这个问题，没有任何一个数字能回答。因为前两个数字衡量的是"比 PyTorch 快多少"，第三个数字衡量的是"比上一个手写版本快多少"，它们都是相对量，锚点会漂移：PyTorch 版本一升级，昨天的 1.8× 今天就变成 1.3×；换一个 shape，昨天的赢家今天就输给 cuBLAS。这就是 SOL-ExecBench 要处理的问题现场——不是"没有 kernel 可写"，而是"写完之后不知道离硬件极限还有多远"。

论文的出发点在摘要里写得很直白：随着 agentic AI 系统越来越能生成和优化 GPU kernel，进展被一类基准所约束——它们奖励的是相对软件基线的加速比，而不是与硬件高效执行的接近程度。这句话把痛点定位在评测口径上，而不是生成能力上。换句话说，2026 年的现场不是"LLM 写不出 kernel"，而是"写出来了，也跑快了，但没人能说这个快是不是到头了"。

二 · 旧方案的三条路径与各自的账

在 SOL-ExecBench 之前，GPU kernel 工程的主流做法可以粗分为三条路径，每条路径都有自己的成本结构。

路径一：手写 CUDA C++。这是性能上限最高的一条路，也是代价最重的一条。一个融合算子从设计到合入，要经历：确定 tile 形状与 shared memory 预算、处理 bank conflict、写 warp-level reduction、处理边界与 tail、在 BF16/FP8/NVFP4 之间做数值路径选择、再在 Blackwell 特有的能力（如更宽的 MMA 形状、新的量化格式）上做特化。这条路的开发周期以人周计，而且每一次硬件换代都要重做一遍。更麻烦的是正确性：手写 reduction 的累加顺序、FP8 的 scaling factor 放置、mask 的边界条件，任何一处错了都不会崩，只会让数值缓慢偏移，直到某个下游任务指标掉点才被发现。可维护性则是第三笔账——一个为特定 shape 特化的 kernel，在输入分布变化时往往直接退化成慢路径，而代码里没有任何东西告诉后来者"这个分支只在 seq_len 是 128 的倍数时有效"。

路径二：Triton。Triton 把 tile 级编程抽象出来，开发者写的是 block 语义而不是 thread 语义，编译器负责映射到 warp 与 shared memory。它显著压缩了开发周期，也让 autotune 成为标准动作。但代价转移到了别处：一是性能上限受编译器调度能力约束，某些需要精细控制寄存器压力或异步流水深度的场景，Triton 生成的代码达不到手写水平；二是编译时间与 autotune 搜索空间成为新的时延来源，一个带十几个 config 的 autotune 在冷启动时可能耗掉数秒到数十秒，这在离线基准里无所谓，在在线服务的扩容路径上却是实打实的成本；三是可解释性下降——当 kernel 慢了，开发者面对的是编译器生成的 IR，而不是自己写的循环。

路径三：库调用。cuBLAS、cuDNN、CUTLASS 以及各类 fused 库把"正确性"和"可维护性"两笔账基本抹平：调用方不写 kernel，只写 dispatch。代价是适配性——库为通用 shape 优化，遇到非标准 layout、非标准 dtype 组合、或者需要与前后算子融合的场景，往往只能拆成多次调用，中间张量落回 HBM。一个典型例子是"attention + 残差 + norm"的三合一：库能给你一个极快的 attention，但你仍然要为残差和 norm 各付一次全量读写。在 HBM 带宽成为瓶颈的 decode 阶段，这几次往返的代价可能超过 attention 本身。

三条路径的共同缺陷不在实现层面，而在度量层面：它们都只能回答"比谁快"，无法回答"离硬件极限多远"。而后者恰恰是判断"是否值得继续投入"的唯一依据。

三 · 相对加速比的三种失真

把"相对软件基线的加速比"当作目标函数，会在三个地方系统性失真，这三处失真正是旧方案非改不可的技术理由。

第一是基线可漂移。加速比的分母是一个可变实现：PyTorch eager、torch.compile、或者论文指定的某个库版本。分母一变，分子不变，分数就变。更隐蔽的是基线本身可能没开满硬件能力——若基线未启用 TF32、或未调用当前最强的库实现，那么一个平庸的候选 kernel 也能拿到漂亮的加速比。这不是候选变强了，是分母被做弱了。论文在失败模式里明确点到这一点：基线若未开 TF32、未用最强库，加速比会被高估。

第二是上限不可见。假设某个算子的理论下限是 40 微秒（由 HBM 带宽或 tensor core 吞吐决定），基线是 200 微秒，候选做到 80 微秒，加速比 2.5×，看起来很好。但真实剩余空间是 2×，而分数只反映了"打败基线"这一件事。当所有候选都超过基线之后，分数饱和，优化信号消失——agent 继续迭代，reward 却不再变化。这正是论文所说"奖励相对基线而非接近硬件高效执行"的直接后果：优化过程在到达某个平台后失去梯度。

第三是shape 特化与隐藏分布。相对加速比可以在单一 shape 上被刷到很高，因为候选可以针对该 shape 做常量折叠、展开、甚至硬编码 tile 尺寸。一旦生产输入分布偏移——batch 变小、seq_len 不是 2 的幂、dtype 从 BF16 切到 FP8——这些特化路径要么走 fallback，要么直接算错。论文把这类风险归入"shape 特化与隐藏输入分布会让离线分数在生产上崩塌"，并在评测侧用隔离子进程、L2 清空、GPU 锁频与静态分析检查来压制 reward hacking 与 fallback 造成的虚高正确率。

$$s_i=\frac{T_{\text{base},i}}{T_{\text{cand},i}},\qquad \text{score}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[s_i\ge\tau]$$

上式是旧口径的典型形态：分母是基线时延，阈值 τ 是一条人为设定的加速比门槛。它的信息量被压缩成一个布尔量——过线或不过线。一个 1.01× 和一个 10× 在计数上等价，一个"离 SOL 还差 5%"和一个"离 SOL 还差 80%"也等价。这种压缩对排行榜友好，对优化过程有害：它丢掉了"还剩多少空间"这个最有用的信号。

四 · 正确性与可维护性的隐藏成本

旧方案的另一个痛点不在性能侧，而在"可信"侧。手写 kernel 与生成 kernel 共享同一类失败模式，而这些失败模式在相对加速比的口径下几乎不可见。

考虑一个 FP8 的矩阵乘融合 kernel。候选实现为了提速，把 scaling factor 的乘法从 per-tensor 改成 per-block，数值上更精细，但如果 block 边界处理与参考实现不一致，输出会在某些通道上系统性偏移。这种偏移不会让 kernel 崩，也不会让单测失败（如果单测只比对随机输入的最大绝对误差），但会让下游的 attention 分数分布变形。论文的评测流程把"正确性门"放在性能门之前：编译候选、在给定输入分布上做正确性检查、再用统一基线测时延。这个顺序本身就是一个工程判断——正确性不是性能的附属品，而是前置条件。

可维护性的成本则体现在"知识不可迁移"。一个为 Blackwell 特化的 kernel，其有效性依赖于特定的 MMA 形状、特定的量化格式、特定的 shared memory 容量。当这些前提变化时，代码不会报错，只会变慢。旧方案没有任何机制把"这个 kernel 在什么条件下有效"编码进评测，于是每一代硬件都要重新做一遍经验积累。SOL-ExecBench 的做法是把评测锚定在由 SOLAR 管线解析推导出的 SOL 边界上——边界随硬件变化，但"距离边界的比例"这个量是跨实现可比的。这就把可维护性问题从"记住上一代的经验"转成"测量当前代的距离"。

还有一个常被忽略的成本：评测本身的可复现性。同一份候选 kernel，在不同机器状态（GPU 频率漂移、L2 残留、其他进程干扰）下测出的时延可以差出可观的比例，足以让一个本该过线的候选落到线下。论文为此提供了沙箱化 harness，包含 GPU 锁频、L2 清空、隔离子进程执行与静态分析检查。这些机制不是锦上添花，而是让"加速比"这个数字具备可比性的前提——没有它们，相对加速比连自己和自己比都不稳定。

五 · 为什么必须换锚点：从"打败谁"到"还剩多少"

把上述痛点归拢，会发现它们共享同一个根因：锚点选错了。以软件实现为锚，锚会动、锚可能弱、锚不告诉你上限。以硬件极限为锚，锚是静态的（对给定硬件与给定算子语义而言），锚不会因为 PyTorch 升级而漂移，锚天然给出"剩余空间"这个连续量。

这就是 SOL-ExecBench 的核心转向：它不比较候选与某个库实现，而是测量候选与解析推导出的 SOL 边界之间的距离。论文用 SOL Score 来量化这个距离——它衡量的是候选 kernel 在一个 release 定义的评分基线与硬件 SOL 边界之间，闭合了多大比例的空隙。这个定义的关键在于"比例"二字：它把绝对时延映射到一个归一化的区间上，使得不同算子、不同 dtype、不同 shape 的分数可以放在同一个尺度上比较，而不需要各自找一个基线。

这个转向对 agentic 优化有直接影响。在旧口径下，一旦候选超过基线，reward 就饱和，多轮迭代失去意义；在新口径下，只要还没到 SOL 边界，就还有可测量的改进空间，反馈信号在接近边界时才自然衰减。这解释了为什么论文要把"接近硬件高效执行"作为目标，而不是"超过软件基线"——前者是一个有梯度的问题，后者是一个会饱和的问题。

代价同样存在。SOL 边界是解析推导的，推导本身依赖对硬件参数的建模（带宽、吞吐、cache 层级），模型误差会直接进入分数。一个被低估的 SOL 边界会让所有候选看起来都"接近极限"，从而掩盖真实的优化空间；一个被高估的边界则会让所有候选都显得很差，优化信号失真。论文用 SOLAR 管线来做这件事，其准确性是整个基准可信度的地基——这也是为什么本系列后续部分要专门讨论 SOL 推导的口径与验证。

另一个代价是覆盖面。论文的基准包含 235 个 CUDA kernel 优化问题，抽取自 124 个生产与新兴 AI 模型，覆盖语言、扩散、视觉、音频、视频与混合架构，面向 NVIDIA Blackwell GPU，包含 BF16、FP8、NVFP4 的前向与反向负载，并包含那些最佳性能预期依赖 Blackwell 特有能力的 kernel。这个规模意味着评测成本不再是"跑几个算子"，而是一条完整的管线：读取参考实现与评测口径、生成候选、编译、正确性检查、统一基线测时延、按反馈保留或回退。每一步都有时延与算力开销，而 SOL 边界的解析推导本身也是一次性但不可忽略的工程投入。

六 · 一个具体算子的两本账

把上面的分析落到一个算子上：decode 阶段的 fused RMSNorm + 残差 + RoPE。这个算子链在 eager 下是三次 kernel 启动、三次全量读写中间张量。假设隐藏维度对应的张量大小为 M 字节，HBM 带宽为 B，那么仅数据往返一项的下界就是若干次 M/B 量级的时间；而算术部分（norm 的归约、RoPE 的旋转）在 tensor core 上几乎可以忽略。也就是说，这个算子的 SOL 边界主要由带宽决定，而不是由算力决定。

旧口径下，工程师会量 eager 版本、量 torch.compile 版本、再量手写融合版本，得到一个加速比。这个数字告诉他"融合有效"，但不告诉他"融合之后还剩多少带宽没用上"。如果手写版本因为 shared memory 布局不佳导致有效带宽只达到峰值的六成，加速比依然漂亮，但 SOL Score 会暴露这个缺口。新口径下，同样的工程动作得到的反馈是"距离带宽边界还差四成"，这个信号直接指向下一步该做什么——改 layout、改 vector 宽度、还是改 occupancy。

两本账的差别不在测量精度，而在决策价值。相对加速比回答的是"这次改动有没有用"，SOL 距离回答的是"下一次改动该往哪走"。对于一个要跑多轮 RL、要回灌 profile 反馈、要在正确性门与性能门之间做取舍的 agent 系统，后者才是可用的信号。论文把评测从"打败一个可变基线"重构为"闭合到硬件 SOL 的剩余空隙"，本质上是在为 agentic 优化提供一个不会饱和、不会漂移、且与硬件语义对齐的目标函数——而这个目标函数的可信度，取决于 SOLAR 推导的边界是否站得住，这正是后续部分要拆开看的地方。
