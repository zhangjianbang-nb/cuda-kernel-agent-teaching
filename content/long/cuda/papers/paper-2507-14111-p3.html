一 · 生成：从算子语义到候选源码

闭环的入口是一次受控采样。给定算子语义（如 softmax、layernorm、GEMM 分块）与参考实现签名，策略模型对同一题目采样 k 个候选 CUDA 源码，k 是该方法唯一显式可调的“宽度”旋钮，也是全部工程代价的乘数。每个候选的输入是算子描述、张量形状与 dtype、参考实现的函数签名，输出是一段自包含的 .cu 文本，通常包含 kernel 本体、launch 配置与 host 侧封装。采样阶段本身不产生正确性信息，只产生待验证的假设；因此候选之间必须保持足够的多样性，否则对比排序会退化为对同一错误的重复惩罚。

代价在这里第一次显形：token 消耗与 k 成正比，且候选越长（含完整 host 封装与模板展开）单题 token 成本越高。工程上更值得关注的是“有效候选率”——若 k 个候选中有大量在编译阶段即被淘汰，则采样预算被浪费在语法层面而非优化层面。这决定了后续负例池的构成比例，也决定了单题摊销成本能否被接受。一个具体例子：对同一 GEMM 题目采样 8 个候选，其中 3 个因共享内存声明与 block 维度不匹配而编译失败，这 3 个候选的 token 成本无法转化为任何性能信号，只能作为语法负例。

二 · 编译：nvcc 作为结构化反馈源

候选源码进入工具链，由 nvcc 编译。此步的输出不是二值的成功/失败，而是三态：成功产出可加载的 cubin；失败返回诊断信息；成功但带警告（如未使用变量、隐式类型收窄、寄存器压力提示）。CUDA-L1 的关键设计是把编译失败显式纳入训练信号，而非静默丢弃：失败候选被标记为负例，同时其诊断文本作为结构化反馈回灌到下一轮提示中，使模型从类型错误、维度不匹配、非法内存访问声明这类语法与语义边界上学习。

这一步的代价是编译时延。nvcc 对含模板与展开循环的 kernel 单次编译可达数秒量级，k 个候选串行编译会把单题墙钟时间推高一个量级；并行编译可缓解但受 CPU 核数与编译缓存命中率约束。更隐蔽的代价是“编译通过≠可运行”：编译成功只保证符号与类型合法，不保证 launch 配置在目标 GPU 上可执行（如超出 shared memory 上限、block 数超过网格限制），这类错误要到运行阶段才暴露，等于把一部分验证成本后移。伪代码层面的控制流是：for cand in candidates: status = nvcc(cand); if fail: neg_pool.append(cand, diag)，其中 diag 的截断长度直接影响回灌提示的 token 预算。

三 · 运行与正确性 oracle：先判对错，再谈快慢

编译通过的候选在 GPU 上执行，输出与参考实现逐元素比对。这一步的排序原则是该方法防作弊的核心：正确性判定严格先于性能比较，未通过数值比对的候选直接进入负例池，不参与计时，从而堵死“用错误输出换加速比”的捷径。比对使用逐元素数值比较，容差标准在给定材料中未给出，这意味着浮点归约顺序差异、rsqrt 近似、--use_fast_math 带来的误差都落在判定边界上，正负例的划分对容差取值敏感。

代价分两类。其一是运行成本：每个候选至少一次前向执行加一次参考执行，若输入分布含多组形状则成倍放大；k 个候选的 GPU 时间与候选数线性相关。其二是正确性判定的风险成本：容差过松会把有实质误差的实现判为正例，污染偏好对；容差过紧会把合法的浮点重排判为负例，浪费本可用的优化样本。一个具体例子：同一 reduction kernel 因改变累加顺序，在长向量上出现末位差异，若容差取绝对阈值而非相对阈值，该候选会被误判为负例，尽管其加速比显著。此处缺少形式化或合约级验证，只有数值 oracle，因此边界样本的判定只能靠容差策略兜底。

四 · 计时与对比奖励：相对排序替代绝对回归

通过校验的候选被多次计时取中位数，与基线实现比较得到加速比。计时口径（是否含数据传输、是否含 launch 开销、是否固定时钟）在给定材料中未给出，这是该方法最需要在评测侧补齐的细节：若计时含 H2D/D2H 拷贝，则计算密集 kernel 的加速比会被传输带宽稀释；若不含，则小算子的 launch 开销被忽略，排序偏向于减少 kernel 数量的实现而非真正提升吞吐的实现。

奖励构造把正确性指示与对数加速比加权组合，再在同一题目的候选集合内做相对排序，形成正负对：

$$r_i = \alpha \cdot \mathbb{1}[\text{correct}_i] + \beta \cdot \log\left(\frac{t_{\text{base}}}{t_i}\right),\quad \mathcal{L} = -\log \sigma\left(r_{i^{+}} - r_{i^{-}}\right)$$

关键在于损失只依赖 ri⁺ − ri⁻ 的差值，而非绝对分数。这带来两个工程后果：其一，绝对加速比标度的漂移（不同题目基线强弱不同）不影响梯度方向，模型学到的是“在同一题目内偏好更快的实现”；其二，若同一题目内所有候选都正确但加速比接近，差值趋近于零，梯度信号微弱，此时 k 的增大才有意义——它提高了采到显著更快候选的概率。代价是采样宽度与编译运行成本线性绑定，单题成本可写成 C(k) = k·(cgen + ccompile + crun + ctime)，其中 ctime 因多次计时取中位数而额外乘上一个重复因子。

五 · 负例池与多轮回灌：失败样本的二次利用

排序完成后，正例与负例并非一次性丢弃。编译失败、数值不一致、更慢的实现全部进入负例池，供后续轮次的对比采样复用。这一机制的价值在于把“失败”从噪声变成资产：同一题目的负例池随轮次增长，模型在后续采样时可以持续与历史失败样本构成偏好对，而不必每轮重新采齐全部负例。多轮闭环的控制流是：生成 → 编译 → 运行 → 排序 → 成对损失更新 → 下一轮重新生成，失败样本在池中累积。

代价是池的管理成本与陈旧性风险。负例池随轮次膨胀，若采样时对池做均匀抽样，早期因语法错误失败的候选会长期占据负例配额，压制后期更有信息量的“正确但更慢”负例；若按时间衰减加权，则需额外维护元数据。另一个代价是策略更新后的分布漂移：更新后的模型生成的候选分布已变，池中旧负例可能不再构成有效对比（例如旧负例的失败原因已被模型学会），继续使用会浪费梯度预算。工程判断上，负例池应按失败类型分层（编译失败 / 数值失败 / 性能落后）并限定每类配额，而非无差别累积。

六 · 单题成本核算与口径缺口

把五步串起来，单题一次迭代的成本结构可以逐项拆开：生成阶段 k 次自回归解码的 token 成本；编译阶段 k 次 nvcc 调用的 CPU 时延（并行度受核数约束）；运行阶段通过校验的候选各一次执行加参考执行；计时阶段通过校验的候选各 m 次重复取中位数。四项相加即为单题摊销成本，且随 k 线性增长。给定材料未给出候选数 k、编译失败率、计时重复次数 m 与基线配置，因此无法核算单位加速比所对应的实际算力开销——这是引用该方法结论时最需要警惕的口径缺口。

这张表暴露的工程判断是：该方法的可信度不取决于奖励公式的形式，而取决于计时口径与容差策略是否被显式固定。相对排序的设计确实降低了对绝对分数标定的依赖，但它把风险转移到了“同题候选集合是否足够多样”与“正确性边界是否被容差正确切分”这两处。若 k 过小，正负对差值集中在噪声区间，偏好损失退化为随机梯度；若容差未定义，浮点边界样本会以不可复现的方式改变正负例归属。因此生产化前的门禁应落在两处具体机制上：固定计时是否含数据传输与是否取中位数，并把容差写成按 dtype 与归约长度的显式规则，而非留给 oracle 隐式决定。

闭环的边界：对比奖励在什么条件下失效，以及它向系统索要的代价

对比式奖励的成立前提是“同一算子、同一输入分布下存在多个可比较的候选”。这个前提一旦松动，整套机制就从“排序”退化为“噪声”。失效的第一种形态是候选池塌缩：当模型对某算子反复生成语义等价、性能相近的实现时，正负对之间的 $r_{i^{+}}-r_{i^{-}}$ 趋近于零，成对偏好损失的梯度信号随之消失，多轮迭代退化为无效空转。第二种形态是负例污染：编译失败与数值不一致的候选被统一压进负例池，但二者携带的信息量并不对等——语法错误提供的是可结构化的修复线索，而浮点边界上的数值偏差提供的是“几乎正确”的误导信号。若容差标准未定义，一个仅在某几个边界元素上超出容差的实现会被判为负例，模型学到的不是“避免误差”，而是“远离该数值区间”，这与真实优化目标正交。第三种形态是计时口径漂移：加速比以相对基线为口径，但基线配置、是否取中位数、是否含数据传输在给定材料中均未给出，同一候选在不同口径下可能跨越正负例分界线，导致同一份执行反馈在不同轮次给出矛盾标签。

把奖励公式拆开看，代价结构就清楚了。

$$r_i = \alpha \cdot \mathbb{1}[\text{correct}_i] + \beta \cdot \log\left(\frac{t_{\text{base}}}{t_i}\right)$$
正确性指示项是硬门，加速比项是软信号。硬门先于软信号执行，意味着任何未通过逐元素比对的候选连进入计时环节的资格都没有——这挡住了“用错误输出换加速比”的作弊路径，但也意味着正确性 oracle 的判定精度直接决定负例池的质量。逐元素比对在浮点归约、原子操作、非确定性调度这几类算子上天然脆弱：同一 kernel 多次运行可能给出位级不同的结果，若 oracle 不做确定性约束，正确候选会被随机判负。这是正确性代价，不是性能代价，但它污染的是训练信号本身。软信号一侧，对数加速比把“快一倍”和“快十倍”压缩到同一量级，避免了绝对分数回归对极端加速比的过度敏感，代价是对小幅提速的区分度下降——在基线已经接近 roofline 的算子上，几个百分点的提升在 log 空间里几乎不可分辨，正负对排序会退化为随机。

工程代价的核心是候选数带来的线性放大。每轮对同一算子采样 $k$ 个候选，每个候选都要走一遍 nvcc 编译、GPU 运行、逐元素比对、多次计时取中位数。编译时间是固定开销且不可并行摊薄到单题之外，GPU 运行时间随候选数线性增长，计时取中位数意味着每个通过校验的候选至少占用数次 kernel 启动与同步。单题成本大致正比于 $k \cdot (t_{\text{compile}} + m \cdot t_{\text{run}})$，其中 $m$ 是计时重复次数。候选数增加提升对比信号的区分度，却同步放大编译失败率带来的浪费——失败候选同样消耗一次编译，却不产生任何计时信息。摘要未给出候选数与失败率，这意味着无法从材料判断该闭环在单题预算内能否收敛。更隐蔽的代价在负例池的存储与采样：失败样本持续进入池子供后续对比采样，池子随轮次增长，若采样策略不做配额控制，早期的高频错误类型会淹没后期的细微性能差异，使模型偏向“修复语法”而非“逼近 roofline”。

一个具体的失效场景足以说明边界在哪里。考虑一个归约类算子，基线实现已接近显存带宽上限。模型生成的候选在分块大小与线程映射上做微调，多数候选的计时差异落在测量噪声内，此时按加速比排序得到的正负对实际上是噪声排序；同时，若某个候选因浮点累加顺序不同而在个别元素上超出未定义的容差，它被判负，模型收到的信号是“该分块策略错误”，而真实原因是数值结合律。这一轮更新同时被噪声排序与误判负例污染，策略向错误方向偏移。要堵住这个口子，工程上需要三件事：计时口径固定为含数据传输的端到端中位数并公开声明；正确性 oracle 对非确定性算子引入确定性执行约束或统计容差；对比采样对负例按错误类型分层配额，避免单一错误类型主导梯度。这三项在给定材料中均未落地，因此该方法的加速比结论只能作为方向性证据，不能直接迁移到生产口径的收益核算。
