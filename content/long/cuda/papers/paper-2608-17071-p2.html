一 · 结论共享内存的语义压缩损失

KernelArc 的协调机制里最值得追问的一条是 conclusions-only shared memory：策略特化 agent 并行跑，彼此只交换“结论”而不交换轨迹。这条设计在候选预算固定时是合理的——它把跨 agent 的通信带宽从 O(轨迹长度) 压到 O(结论条数)，让 N 个 agent 的搜索空间近似线性叠加而不是平方级互相污染。但代价是语义压缩：一个 agent 放弃某条路线的原因（编译失败、寄存器溢出、bank conflict、共享内存不够、某个 tile 形状在 H100 上撞到 TMA 边界）在压缩成一句结论后，接收方无法区分“这条路走不通”和“这条路在我这个策略下走不通”。

形式化地，设 agent i 的局部状态为 s_i，共享结论为 c_i = compress(s_i)，则 agent j 的决策依据是 f(c_{-j}) 而非 f(s_{-j})。压缩算子丢掉的维度正是“失败归因”。当策略空间正交时（GEMM 的 tile 切分 vs. epilogue 融合 vs. 库配置表），这个损失小；当策略空间重叠时（两个 agent 都在试 grouped-query attention 的 KV 分块），结论共享会让双方同时收敛到同一个局部最优，plateau-triggered drafting 触发得越晚，浪费的候选预算越多。

工程上的判断很直接：如果你的 workload 族内策略维度高度重叠，conclusions-only 的收益会被重复探索吃掉；此时要么人为把 agent 的策略空间切开（按算子阶段而非按优化手法分工），要么接受“共享结论 + 独立验证”的双重开销。后者的代价是可测量的——每个候选都要过一次确定性 benchmark guard，guard 的时延乘以候选数就是纯开销，在 L1 级小算子上这笔开销可能超过 kernel 本身的执行时间。

二 · 确定性 benchmark guard 的失效边界

论文把 deterministic benchmark guard 作为正确性与性能的双重门：候选必须通过正确性检查，且加速比 s ≥ 1 才被接受，即

$$\text{speedup}=\frac{T_{\text{base}}}{T_{\text{agent}}},\qquad \text{accept}=\mathbb{1}[\text{pass}\land s\ge 1]$$

这个门在离线基准上是干净的，但它的“确定性”只在给定输入分布上成立。guard 的确定性来自固定 shape、固定 dtype、固定随机种子；一旦生产输入的 shape 分布漂移，guard 通过的实现可能在真实负载上退化。论文自己列出的产出里有一类特别危险：static cuBLASLt Expert-API configuration tables 与 shape-gated decoder-layer fusion。前者是把库配置表静态化，后者是按 shape 做门控融合——两者都是 shape 特化的极端形式。它们在 SOL-ExecBench 的类别代表 workload 上能拿分，是因为基准的 shape 集合是已知且有限的；换一组 shape，配置表命中率下降，门控分支走空，性能回落到甚至低于未特化版本。

这不是实现缺陷，是评测口径的必然产物。任何以“固定 shape 集合上的时延”为奖励的搜索，都会把预算倾斜到对该集合过拟合的方向。KernelArc 的多 agent 并行只是把这个倾向放大了：N 个 agent 各自找到一组 shape 特化解，结论共享后互相确认“这条路有效”，plateau 更晚触发，过拟合更深。判断标准是看产出里 shape 特化实现占比——如果 fused MoE backward 和 paged prefill attention 的胜出候选都带 shape 门控，那这套结果迁到变长序列或动态 batch 的生产环境时需要重新跑一遍搜索，而不是直接部署。

代价体现在两个方向：离线阶段，guard 的重复测量与编译时间随候选数线性增长；在线阶段，shape 未命中导致的回退分支增加一次分支判断与潜在的重配置开销。对延迟敏感的 decoder 层，这个分支本身就在关键路径上。

三 · 与相邻多 agent 工作的差别在哪

把 KernelArc 放进同批工作里，差别不在“多 agent”这个标签，而在协调原语的选择。Astra 与 cuPilot 同样做多 agent 协作，但它们的协调偏向策略层（分工、投票、策略协同）；KernelArc 的协调偏向状态层——conclusions-only shared memory 加 read-only cross-agent state，本质是把 agent 之间的耦合降到“只读广播”。这个选择带来两个可观测后果。

维度KernelArc 的取向迁移风险
协调原语只读结论广播 + plateau 触发起草策略重叠时重复探索，预算浪费
反馈粒度确定性 benchmark guard 的通过/拒绝粗粒度反馈无法定位失败归因
产出形态含静态配置表与 shape 门控的融合实现shape 漂移即退化
验证强度正确性门 + 性能门无形式化保证，边界输入未覆盖

与 CudaForge 那类以硬件反馈为核心的框架相比，KernelArc 的反馈回路更窄：它依赖 guard 的二元判定，而不是把 NCU/SASS profile 的细粒度指标回灌给 agent 做定向改写。窄反馈的优点是判定确定、不易被噪声误导；缺点是 agent 只知道“没过”，不知道“为什么没过”，于是只能靠并行试错覆盖搜索空间。这正是它需要多 agent 的结构性原因，也是它在候选预算紧张时效率不如定向反馈框架的原因。

与 Kevin、Dr. Kernel 这类多轮 RL 路线相比，KernelArc 不做策略梯度更新，全部收益来自推理时的搜索编排。这意味着它的上限受限于基座模型的一次性生成质量，且无法通过训练把“哪种失败该往哪个方向改”内化。代价是 token 消耗：N 个 agent 并行意味着 N 倍的生成 token，加上结论共享的读写与 guard 的重复编译，单题成本远高于单 agent 单轮。在 L1 级小算子上，这个成本结构很难摊薄。

四 · 正确性 oracle 的覆盖缺口

论文的验证口径是正确性门加性能门，没有形式化验证。对 GEMM、MoE backward 这类数值密集算子，正确性门通常是对比参考实现的输出容差；对 paged prefill attention 与 NVFP4 grouped-query attention，容差判定要处理量化误差与分页索引的边界。缺口在于：guard 只在给定输入上跑，而 kernel 的正确性域远大于输入集合。

具体机制上，paged attention 的分页表长度、block table 的空洞、序列长度不是 block 大小整数倍时的尾块处理，都是容易在固定输入下被掩盖的路径。NVFP4 的量化缩放因子在极端值分布下的溢出/下溢同理。这些路径在基准输入上不触发，guard 判 pass，实现进入产出列表，但在生产的长尾请求上出错。多 agent 并行在这里没有帮助——所有 agent 共享同一个 guard，也就共享同一个覆盖缺口。

工程判断：把 KernelArc 的产出直接当生产 kernel 用是不成立的，正确做法是把它的产出当作“高价值候选”，再叠一层性质测试或差分测试。代价是额外一轮验证时延与显存占用（差分测试要同时驻留参考实现与候选的中间张量）。对显存紧张的 fused MoE backward，这层验证本身可能 OOM，需要分块跑。

五 · 什么情况下不该用它

第一类不该用的场景是单算子、单 shape、且已有强库实现。KernelArc 的收益来自异构 workload 上的并行探索与结论复用；当 workload 只有一个算子、一个 shape，多 agent 的协调开销（结论共享、guard 重复、plateau 判定）没有可摊销的对象，而静态配置表这类产出对单一 shape 的增益又可以被手工调参复现。此时它的 token 成本与编译时间都花在协调上，不如单 agent 加定向 profile 反馈。

第二类是不接受 shape 特化的部署环境。如果服务端的输入 shape 分布开放（动态 batch、变长序列、多租户混合 dtype），shape-gated 融合与静态配置表的命中率不可控，离线 leaderboard 上的排名不能转化为端到端收益。论文的评测口径明确限定在 H100 与 B200 上的类别代表 workload，跨硬件、跨 dtype、跨框架的迁移未验证——这三条正是生产环境最常见的漂移维度。

第三类是需要形式化保证的场合。KernelArc 的 accept 判据是经验性的 pass 加 s ≥ 1，没有不变式证明，也没有对边界输入的系统覆盖。对正确性要求高于性能的场景（数值敏感的归约、金融或科学计算路径），这套门不足以支撑部署决策。

第四类是基线口径不可信的场景。论文自己点出的失效模式里最隐蔽的一条是基线未开 TF32 或未用最强库实现——此时 T_{\text{base}} 被高估，加速比被系统性放大，而 guard 只检查 s ≥ 1，不会发现基线本身偏弱。多 agent 的结论共享会把这个偏差放大成“多条路线都确认有效”的假象。使用前必须核对基线是否与生产环境的最强实现对齐，否则整套排名的意义仅限于该基线口径内部。

最后一条边界落在 reward hacking 与 fallback 上：当候选实现检测到基准输入特征后走快速路径、其余情况回退到慢路径，正确率与加速比会同时虚高，而 guard 的固定输入恰好落在快速路径上。这类实现能通过确定性门，却在生产上表现为性能抖动。识别方法是把 guard 的输入集合做扰动重测，看加速比方差；方差大的候选应视为未通过，无论它在原始口径上排名多高。这条判断比任何 leaderboard 名次都更能决定一次迁移是否成立。

结论共享与确定性守卫在什么条件下失效

KernelArc 的协调机制有三个可分离的部件：策略专化 agent 并行搜索、只写结论的共享内存、以及确定性 benchmark guard。这套设计成立的前提是"结论"本身可被压缩成少量离散事实——例如某个 tile 配置在该 shape 下胜出、某条融合路径被编译门否决。一旦任务的最优解依赖于连续参数空间中的细粒度调优（例如寄存器压力与 occupancy 的折中曲线在某个区间内非单调），结论共享就会丢失关键梯度信息：agent A 报告"配置 X 更快"，agent B 无法从中推断"X 附近还有更优邻域"，只能重新独立搜索。此时并行 agent 的探索预算被重复消耗，固定候选预算下的有效覆盖率下降。用候选预算 B 与去重后的独立探索点数 N 表示，有效利用率可写成

$$\eta=\frac{N}{B},\qquad \text{draft cost}\propto (1-\eta)\cdot B$$

当 η 接近 1 时共享内存几乎无增益，多 agent 退化为多个独立搜索进程的并集，token 与编译时间随 agent 数线性增长而加速比不增。具体例子：BF16 GEMM 的 tile 选择在 M×N×K 的边界 shape 上（如 K 不是 16 的倍数）会出现非单调的 shared memory bank 冲突行为，结论式共享无法表达"这个配置在 K=4096 时输、在 K=4097 时赢"的条件依赖，agent 之间只能反复提交互相矛盾的结论，plateau-triggered drafting 被过早触发，drafting 本身消耗的编译轮次反而挤占了有效搜索。

确定性守卫的代价与它挡不住的东西

确定性 benchmark guard 的作用是让同一候选在重复测量下给出可比时延，从而避免 agent 追逐测量噪声。它的实现代价是测量次数与同步开销：每个候选需要固定次数的重复与显式设备同步，单候选验证时延从"一次 kernel 启动"膨胀为"多次启动 + 同步 + 统计"。在候选吞吐量高的搜索阶段，这个开销会成为瓶颈——guard 越严格，单位时间内可评估的候选数越少，而 agent 并行的收益恰恰依赖于候选吞吐。更关键的是 guard 只保证测量可重复，不保证测量代表生产：它无法识别 shape 特化。论文所列实现中包含 shape-gated decoder-layer fusion 与 static cuBLASLt Expert-API 配置表，这两类产物的共同特征是"在给定输入分布上极快、在分布外退化"。离线基准的输入分布由论文口径给定，生产流量的 shape 长尾不在其中，guard 对二者一视同仁地给出确定性数字，于是离线分数与端到端收益之间出现系统性偏差。此时正确性门与性能门的联合判据

$$\text{accept}=\mathbb{1}[\text{pass}\land s\ge 1],\qquad s=\frac{T_{\text{base}}}{T_{\text{agent}}}$$

只回答了"在这个输入上是否更快"，没有回答"换一个输入是否仍然正确且不更慢"。shape-gated 分支若在未覆盖的 shape 上回退到慢路径，端到端时延可能因分支判断与额外 kernel 启动而净增，而离线 accept 仍为真。

不该用它的三类场景

第一类是基线口径不可信的场景。论文自己点明的失效模式是基线未开 TF32 或未使用最强库实现，此时加速比被高估，agent 的搜索方向被错误的梯度牵引——它会去优化一个本已被库实现覆盖的瓶颈。若部署方的生产基线是 cuBLASLt 最强配置而非 PyTorch eager，KernelArc 在离线基准上排名第一的结论不能直接迁移，因为排名比较的是论文指定的基线集合。第二类是正确性 oracle 薄弱或输入分布不可枚举的场景：agent 的搜索空间包含静态配置表与 shape-gated 分支，这类产物天然对隐藏输入敏感，reward hacking 与 fallback 路径会让离线正确率虚高，而形式验证或差分测试若只覆盖基准 shape，就无法证伪。第三类是编译预算受限的在线场景：多 agent 并行 + 结论共享 + drafting 的 token 与编译时间开销是叠加的，若单次优化窗口只允许个位数候选评估，plateau-triggered drafting 尚未触发就已超时，框架的协调机制全部落空，不如单 agent 加确定性 guard 直接跑。

与相邻工作的差别落在协调层而非搜索层

与单 agent 执行反馈类工作相比，KernelArc 的增量不在"用 profile 回灌改写候选"这一环——那是共享的基础设施——而在协调层：结论式共享内存把跨 agent 通信压缩为离散事实，plateau-triggered drafting 把"何时换策略"从固定轮次改为基于进展停滞的触发。与纯并行采样加投票的方案相比，它的差别是只读跨 agent 状态：agent 之间不互相修改对方的候选池，避免了一个 agent 的错误结论污染全局。这个设计的代价是收敛速度受限于结论的传播延迟——一个 agent 的新发现要等到其他 agent 下一次读取共享内存才生效，在候选评估时延长的任务上（如 fused mixture-of-experts backward 的编译与验证成本高），传播延迟占总搜索时间的比例上升。工程判断上，是否采用它取决于两个可测量量：单位候选的验证时延是否远小于单 agent 的完整搜索周期（决定并行是否有意义），以及任务的最优解是否可被离散结论充分描述（决定共享内存是否有效）。两者任一不成立时，协调层的复杂度就是净负担。
