一 · 一个推理服务现场的 kernel 账本

设想一个已经上线的 LLM 推理服务：模型结构固定，batch 与序列长度按线上流量分布波动，SLO 卡在 P99 时延上。工程师打开 profiler，发现注意力之外的“杂项算子”占掉了可观的 GPU 时间——RMSNorm、RoPE、SwiGLU 激活、KV cache 的 gather/scatter、采样阶段的 top-k。这些算子单个都不复杂，但数量多、shape 碎、访存密集，PyTorch eager 实现往往一个算子一次 launch，中间结果反复落 HBM。把它们逐个换成融合 kernel，端到端能挤出可观的时延余量；问题在于，谁来写这些 kernel，写完谁来保证它在所有线上 shape 上都对。

这就是《EvoEngineer》要回答的问题现场。论文开篇的判断很直接：CUDA kernel optimization has become a critical bottleneck for AI performance，训练与推理效率直接取决于高度优化的 GPU kernel。这句话在工程上可以翻译成一笔账：模型侧的算法改进已经进入平台期，而算子侧仍有大量未被榨干的带宽与指令级并行。账本的另一面是成本——手写一个融合 kernel 并把它调到超过库实现，需要熟悉架构的工程师投入数天到数周，还要覆盖正确性边界、多种 dtype、多种 shape。于是“用 LLM 自动做 kernel 优化”成为一个自然的诉求，但论文同时指出，这个领域此前是一个 fragmented ecosystem of isolated and incomparable approaches with unclear problem formulations：方法彼此孤立、不可比较、问题定义含糊。

二 · 旧方案的三条路径与各自的墙

在 EvoEngineer 之前，GPU kernel 工程的主流做法可以归为三类，每一类都撞在自己的墙上。

  • 手写 CUDA C++。控制力最强：shared memory 分块、寄存器复用、warp 级原语、异步拷贝、流水线双缓冲都能精确编排。代价是开发周期长且强依赖人。一个 fused RMSNorm+残差 kernel，工程师要先确定 tile 形状与线程映射，再处理尾块与对齐，再在 SASS 层面确认没有多余的 spill 与 bank conflict。任何一处疏漏都表现为“能跑但慢”，而定位它需要 NCU 的逐指标下钻。
  • Triton。用块级 DSL 把 tile 编程抽象出来，编译器负责线程映射与共享内存分配，开发效率显著高于 CUDA C++。但 Triton 的表达力有边界：非常规的数据布局变换、需要精细控制 warp 间协作的算子、以及依赖特定 PTX 指令的路径，往往要退回 CUDA 或内联汇编。性能上限因此不完全由算法决定，还由编译器能否识别出你的意图决定。
  • 直接调用库。cuBLAS、cuDNN、CUTLASS 提供的实现经过深度调优，在标准 shape 上通常就是天花板。但库的覆盖是“标准形态优先”：融合模式一旦偏离库的假设（比如非常规的 epilogue、非标准的 dtype 组合、动态 shape 的 tail 处理），要么退回多个算子串联，要么只能自己写。库调用还带来一个隐性成本——它把优化空间封在 API 边界内，工程师无法针对自己的流量分布做特化。

三条路径共享同一个结构性痛点：优化是人工的、串行的、不可复用的。一个人调好的 kernel 换一个 shape 分布就可能退化；一次调优的经验难以沉淀成可自动执行的策略。这就是“非改不可”的工程理由——不是 LLM 有趣，而是人工调优的边际成本已经高于它带来的边际收益。

三 · 性能上限不是一个数，而是一条 roofline

讨论“手写能不能更快”时，工程上需要一个可判定的上限，否则优化就变成无休止的试错。roofline 给出的是这条上限：对给定 kernel，其算术强度 I 定义为浮点运算量与访存字节数之比，可达性能被峰值算力与有效带宽共同钳制。

$$P_{\text{att}}(I)=\min\left(P_{\text{peak}},\;I\cdot B_{\text{eff}}\right),\qquad I=\frac{\text{FLOP}}{\text{Byte}}$$

这条公式的工程含义是：如果一个算子落在 memory-bound 一侧（I 小），那么无论怎么改指令序列，性能都被 I·B_eff 封死，唯一有效的优化是减少访存字节——也就是融合。RMSNorm、RoPE、SwiGLU 这类逐元素或轻归约算子正是典型：它们的算术强度低到几乎完全由 HBM 带宽决定，eager 模式下“读输入—写中间—读中间—写输出”的多趟往返把有效字节数放大数倍。融合 kernel 把中间结果留在寄存器或 shared memory，直接把 Byte 压下来，这才是加速的来源，而不是指令调度。

反过来，矩阵乘这类 compute-bound 算子落在 P_peak 一侧，优化空间在 tile 形状、流水线深度、Tensor Core 利用率上，手写要超过 cuBLAS 极其困难。这条分界线解释了为什么自动 kernel 优化的收益高度不均匀：融合类算子容易拿到大幅加速，而标准 GEMM 类算子几乎无空间。EvoEngineer 报告的 91 个真实 CUDA kernel 上 median speedup 2.72×、单算子最大 36.75×、50 个算子中 28 个（56.0%）超过 2×，这个分布形态与 roofline 的判断一致——高倍速来自访存路径的重构，而非算力的凭空增加。

代价也要记在账上：融合把多个算子的逻辑塞进一个 kernel，寄存器压力上升，occupancy 下降，尾块处理变复杂；一旦 tile 选错，融合 kernel 可能比两个独立 kernel 还慢。roofline 只给上限，不给实现路径，从上限到实际 kernel 之间的这段路，正是旧方案里最贵的人工部分。

四 · 正确性不是二值，而是必须被形式化的约束集

旧方案里最容易被低估的痛点是正确性。手写 kernel 的正确性靠人审和测试用例，而 LLM 生成的 kernel 把这个问题放大了一个量级：模型可以写出语法正确、在某个 shape 上数值吻合、却在另一个 shape 上越界或产生 NaN 的代码。论文对此的表述是 general-purpose LLM code evolution methods cannot meet strict correctness requirements of CUDA kernel optimization——通用代码演化方法满足不了 kernel 优化的严格正确性要求。

“严格”在 kernel 语境下有具体所指，至少包含四层：索引不越界（含尾块与负索引）、数值在给定 dtype 与容差下等价（浮点归约顺序改变会引入差异，必须定义容差口径）、同步与竞态正确（shared memory 的写后读屏障、warp 内 shuffle 的活跃掩码）、以及边界条件（空 tensor、单元素、非对齐指针）。任何一层缺失，性能数字都失去意义。

一个具体的失败模式：LLM 为 LayerNorm 生成一个按行分块的 kernel，在 hidden size 是 32 的倍数时用向量化加载，测试集恰好全是这种 shape，正确性检查全绿；上线后遇到 hidden size 不是 4 的倍数的模型变体，向量化路径读越界，输出错位。这类错误在离线基准上不可见，因为基准的输入分布是固定的。EvoEngineer 的做法是把 kernel 优化形式化为一个带明确 objective、constraints 与 evaluation metrics 的代码优化任务，正确性从“测试通过”上升为约束集中的硬门——候选必须先过正确性门，才进入性能比较。这个次序本身就是对旧方案的一次修正：人工调优时正确性由工程师的直觉兜底，自动化时必须把它写成可执行的判据。

正确性门的代价是吞吐：每个候选都要编译、在输入分布上跑一遍数值比对，一轮演化里几十个候选意味着几十次编译加运行。编译时间与验证时延构成搜索循环的主要开销，这也是为什么演化框架必须做候选剪枝，而不是无脑扩大采样。

五 · 可维护性与“不可比较”的生态

第三条痛点是可维护性，它在论文里以“fragmented ecosystem”的形式出现。旧方案产出的 kernel 是孤立的工件：一个人写的 CUDA 文件、一段 Triton 脚本、一次库调用配置。它们之间没有共同的评测口径——有人报相对 eager 的加速比，有人报相对 torch.compile，有人用不同 GPU、不同 dtype、不同 shape 集合。结果是一堆数字无法横向比较，也无法判断某个方法的能力边界在哪里。对工程团队而言，这意味着无法回答“我该用哪种方法”这个最实际的问题。

可维护性的另一面是演化后的代码由谁接手。LLM 生成的 kernel 往往带有针对特定 shape 的特化常量、手工展开的循环、以及为通过某个测试而加的边界分支。这些代码在原始输入分布上表现优异，但一旦 shape 变化就需要重新演化。论文强调 EvoEngineer 要在 performance 与 correctness 之间取得 principled balance，这个“principled”的工程解读是：优化策略必须可被指导、可被适配，而不是一次性过拟合到基准上。一个只对单一 shape 最优的 kernel，其维护成本最终会抵消它带来的加速。

这里有一个必须点明的评测陷阱：如果基线没有开启 TF32、没有使用最强的库实现，那么任何“超过 PyTorch”的加速比都会被系统性高估。EvoEngineer 的基线口径是 PyTorch eager、torch.compile 与论文指定的库实现，读者在解读 2.72× 与 36.75× 时必须把基线配置一并纳入判断。同理，shape 特化与隐藏输入分布会让离线分数在生产上崩塌，reward hacking 与 fallback 机制会让正确率虚高——这些都是旧方案遗留、新方案必须正面处理的问题。

六 · 为什么必须把优化写成可执行的循环

把三条痛点合起来看，旧方案的根本缺陷不是“写得不够快”，而是优化过程本身没有被形式化。人工调优的循环是：读参考实现 → 猜瓶颈 → 改代码 → 编译 → 测正确性 → 测性能 → 保留或回退。这个循环在工程师脑子里跑，每一步的判据是隐性的。EvoEngineer 的切入点是把这个循环显式化：先形式化为带 objective、constraints、metrics 的代码优化任务，再建立系统化的 LLM 代码演化框架，为设计与适配优化策略提供指导，最后落到一个 kernel 优化系统上，在 91 个真实 CUDA kernel 上做实验。

这个循环里每一步都有明确的工程代价。读取参考实现与基准口径决定了后续所有比较的可信度；生成候选消耗 token，候选越多搜索越广但编译验证的时延线性上升；编译后在给定输入上做正确性检查，是唯一能拦住越界与数值偏差的硬门；用统一基线测量时延与加速比，决定了反馈信号是否被基线配置污染；按反馈保留或回退候选，则决定了演化是单调改进还是会震荡。论文的贡献在于把这五步串成一个可复现的闭环，而不是提供一个孤立的代码生成器。

回到开场的推理服务：融合 RMSNorm+残差这类 memory-bound 算子，roofline 说收益来自减少 HBM 往返，正确性门要求覆盖非对齐与尾块，可维护性要求特化不锁死在单一 shape。EvoEngineer 的价值不在于它能让 LLM 写出某个 kernel，而在于它把“写—验—测—留”的判据固定下来，使得 91 个 kernel 上的 2.72× median 与 56.0% 的 2× 达成率成为可比较、可复现的量，而不是又一个孤立数字。旧方案缺的正是这个坐标系。

手写与库调用之间：被忽略的“最后一公里”与它的系统代价

在一个典型推理服务里，attention 的 decode 阶段与 prefill 阶段对 kernel 的要求截然相反：decode 是 batch 小、序列长、访存受限，prefill 是算力受限、并行度高。工程团队面对的现实是，PyTorch eager 提供的通用 kernel 在 decode 这种低算术强度区间离带宽上限很远，而 cuBLAS、CUTLASS 之类的库实现又只覆盖少数标准 shape 与 dtype 组合。于是团队被迫在两条路之间选择：要么接受库调用的性能天花板，要么手写 CUDA 针对具体 shape 特化。这条“最后一公里”的代价并不体现在单次 kernel 上，而体现在它把一个本可批量化的问题变成了逐算子、逐 shape 的人工工程。用 roofline 描述这种落差很直接：

$$P_{\text{att}}(I)=\min\left(P_{\text{peak}},\;I\cdot B_{\text{eff}}\right),\qquad I=\frac{\text{FLOP}}{\text{Byte}}$$
当 I 落在拐点左侧，性能完全由有效带宽 B_eff 决定，而通用实现的 B_eff 往往被冗余搬运、非合并访问和 occupancy 不足压低；手写特化能把 B_eff 推高，但每一次推高都要付出人力与验证成本。

手写路径的失效条件非常具体。第一是 shape 漂移：为 batch=1、head_dim=128 调优的 kernel，一旦服务端把 batch 提到 8 或切换到 GQA，寄存器压力、共享内存切分和 warp 映射全部失效，性能可能回落到不如库实现。第二是正确性边界：手写 kernel 需要自己处理边界 mask、非对齐指针、fp16/bf16 累加精度与 NaN 传播，任何一处疏漏都不会在编译期暴露，只会在特定输入上产生静默错误——这类错误在离线单元测试里通过率很高，却在长尾请求上偶发。第三是可维护性：一个算子库若有几十个特化 kernel，每个都绑定特定架构的指令选择与流水编排，升级 GPU 架构或 CUDA 版本时，回归验证的工作量随特化数量线性增长。表层的“性能上限”问题背后，其实是验证成本与特化数量之间的乘积关系。

路径典型边界主要代价
PyTorch eager低算术强度、非标准 dtype离带宽上限有距离，无法按 shape 调优
库调用（cuBLAS/CUTLASS）仅覆盖标准 shape 与布局命中率低时退回通用路径，性能不可控
手写 CUDA 特化绑定单一 shape 与架构开发周期长、正确性靠人工、特化数量带来回归成本

把这三条路径放在一起看，问题的性质就清楚了：它们共享同一个结构性缺陷——缺少一个统一的问题表述，使得“给定参考实现、约束与评测口径，自动搜索并验证一个更优 kernel”这件事无法被系统化。库调用把决策权交给供应商，手写把决策权交给工程师，两者都无法在保持严格正确性门的前提下批量探索候选。论文正是把这一缺口表述为“孤立且不可比的碎片化生态”与“通用 LLM 代码演化无法满足 CUDA kernel 的严格正确性要求”两个并列障碍，并用 91 个真实 kernel 上的实验给出 2.72× 的平均中位加速与最高 36.75× 的单算子加速作为这一表述的量化锚点。这里的工程判断是：真正的瓶颈不是“能不能写出一个快 kernel”，而是“能否在可复现的约束下，以可接受的编译与验证开销，持续产出既快又正确的候选”，而这恰恰是手写与库调用两条旧路径都不提供的。
