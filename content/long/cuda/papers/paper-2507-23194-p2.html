一 · 基准承载什么：算子语义、shape 与 dtype 分布的三元组

Geak 的评测基准不是一个“题目列表”，而是一组以算子为单位的三元组：语义说明、输入 shape、dtype 分布。这个结构决定了后面所有数字的可比性——同一个算子在不同 shape 下可能落在完全不同的 roofline 区间，同一个 dtype 会改变向量化宽度与寄存器压力，因此“某算子加速比 X 倍”这句话若不绑定 shape 与 dtype，等于没有信息量。基准层的职责是把这三元组固定下来，让智能体在首轮提示里就能拿到确定的输入契约，而不是让候选内核在评测时面对随机形状。

具体机制上，任务层向编排层交付的是一条结构化记录：算子名、数学语义（例如归约轴、广播规则、边界条件）、每个测试用例的 shape 元组与 dtype。执行层据此构造输入张量并调用参考实现。这里有一个容易被忽略的工程点：参考实现本身也是口径的一部分。若参考实现是 PyTorch 的朴素算子组合，基线耗时就包含了框架调度开销；若参考实现是 cuBLAS/cuDNN 调用的融合算子，基线就更接近硬件上限。论文材料未披露基线名称与版本，这意味着任何引用其加速比的行为都必须先确认基线到底是“框架级朴素实现”还是“厂商库实现”，两者相差的可能是一个数量级的调度开销。

$$\mathrm{speedup}_i=\frac{T_{\mathrm{base},i}}{T_{\mathrm{cand},i}},\qquad \mathrm{geomean}=\exp\!\Big(\frac{1}{N}\sum_{i=1}^{N}\ln \mathrm{speedup}_i\Big)$$

用几何平均而非算术平均，是因为加速比是比值量纲，算术平均会被个别超高倍数的用例主导。代价是：几何平均对“某个用例加速比小于 1”极其敏感——一个 0.5 倍的用例会把整体拉低得比算术平均更狠，这在工程上是合理的惩罚，但也意味着基准必须报告逐用例分布，否则读者无法判断几何平均是被少数失败用例拖累还是整体偏弱。token 成本上，逐用例报告意味着评测输出体积随 N 线性增长，若 N 达到数百，轨迹留存与汇总的存储开销不可忽略。

一个具体例子：同一归约算子在 shape 为 (1024, 4096) 的 fp32 输入下可能是带宽受限，在 (8, 4096) 下则可能是启动延迟受限。前者候选内核的优化重点是合并访存与向量化，后者则要减少 block 数与同步开销。若基准只报一个笼统的算子级加速比，这两种情况的优化信号会被混在一起，智能体收到的反馈也无法指向具体瓶颈。因此 Geak 基准的 shape 覆盖范围本身就是评测强度的一部分，而材料未给出覆盖范围，这正是当前口径不可核查的第一处缺口。

二 · 指标族：faster rate、fast_p 与 roofline 各自回答什么问题

单一加速比无法区分“稳定地略快”与“偶尔极快但多数更慢”。因此基准需要一组互补指标。faster rate 是候选相对基线更快的用例占比，回答的是“赢面有多大”；fast_p 是加速比超过阈值 p 的用例占比（例如 fast_1.0 即 faster rate，fast_2.0 表示至少两倍），回答的是“赢得多狠”；几何平均回答的是“整体期望倍数”。三者组合起来才能刻画分布形状：faster rate 高但几何平均低，说明多数用例只是微弱领先、少数用例严重落后；faster rate 低但几何平均高，说明少数用例大幅领先、多数用例小幅落后。

roofline 指标则把“快”换算成“离硬件上限多远”。对每个用例，按访存字节数与浮点运算数分别算出带宽上限时间与算力上限时间，取较小者作为该用例的理论下界，候选耗时与之相除得到 SOL（speed of light）利用率。这一步的工程价值在于：它把“加速比”从相对量变成绝对量，使得不同基线口径下的结果仍可横向比较——即便基线是朴素实现导致加速比虚高，SOL 利用率仍会暴露候选离硬件上限的真实距离。代价是 roofline 需要精确的字节数与 FLOP 计数，对融合算子或含数据依赖分支的算子，这两个量本身就需要建模假设，假设不同则 SOL 不可比。

指标回答的问题失效场景
faster rate赢面占比微小领先被计入，掩盖大幅落后
fast_p（如 fast_2.0）显著领先的占比阈值 p 选取主观，跨论文不可比
几何平均加速比整体期望倍数被单点失败用例主导
SOL 利用率离硬件上限的距离字节/FLOP 建模假设不一致

具体机制上，计时口径必须与指标绑定：若计时包含首次调用的编译与 autotune 开销，Triton 候选会被系统性惩罚，因为 Triton 的 JIT 编译与 autotune 在首调用时发生；若计时只取稳态循环的平均值，则隐藏了真实部署中的冷启动代价。论文材料未披露预热策略与计时方法，这是第二处不可核查缺口。工程判断上，可复现的口径应至少声明：预热次数、计时迭代数、是否同步、是否包含编译、是否取中位数或最小值。缺少任一项，跨工作的加速比就不能直接相减比较。

三 · 哪些数字不可比：基线、软件栈与防作弊三重污染

第一重污染来自基线。若 A 工作以 PyTorch 朴素实现为基线，B 工作以 cuBLAS 为基线，则 A 报告的 3 倍与 B 报告的 1.2 倍不可比——前者可能只是击败了框架调度开销，后者是在与厂商手写内核竞争。Geak 材料未给出基线名称与版本，因此其加速比只能作为“相对某未具名实现”的内部量，不能与其他基准的加速比并列。可核查的做法是要求基准同时报告候选的绝对耗时与 SOL 利用率，让读者自行换算。

第二重污染来自软件栈。Triton 的编译结果对版本高度敏感：block size 的默认启发式、autotune 的搜索空间、后端 lowering 的优化 pass 都会随版本变化，同一份内核代码在不同 Triton 版本下的耗时可能显著不同。CUDA 驱动与 GPU 架构同理。因此固定工具链版本不是形式要求，而是性能数字可比的前提。材料提到需固定 Triton 与 CUDA 版本，但未给出具体版本号，这使复现者无法确认自己是否处在同一编译条件下。编译时间本身也是一项代价：Triton 的 autotune 在候选配置多时会让首调用延迟达到秒级，若基准把编译计入端到端时延，这一项会主导小 shape 用例的结果。

第三重污染来自防作弊。基准一旦公开，候选就可能针对测试 shape 做特化：把 shape 硬编码进内核、预计算常量、或在检测到特定输入时走捷径。材料未披露防作弊机制，因此无法判断分数是否被过拟合策略抬高。可核查的防线包括：隐藏 shape（评测时才下发）、随机化输入分布、对同一算子用多组未见 shape 复测、以及对内核源码做静态检查以发现硬编码常量。隐藏 shape 的处理方式是本部分的核心工程问题——若基准在提示阶段就给出全部 shape，智能体可以逐 shape 定制；若评测时才给出，智能体必须生成对 shape 参数化的通用内核，这才检验真实的泛化能力。

一个具体例子：矩阵乘算子在固定 (M,N,K) 下，候选可以把 block 划分写死为最优配置；一旦评测换成相邻的 shape，写死的配置可能因 tile 不整除而触发边界分支，性能骤降。隐藏 shape 的代价是评测方差上升——同一候选在不同隐藏 shape 上的加速比分散度更大，几何平均的置信区间变宽，需要更多用例才能稳定排序。token 成本上，隐藏 shape 意味着智能体无法在提示中看到全部输入契约，首轮生成的通用性要求更高，多轮反馈中因 shape 不匹配导致的失败重试次数上升。

四 · 正确性 oracle 的严格度决定性能数字的含金量

性能指标只在正确性通过后才有意义，而正确性 oracle 的严格度直接决定了有多少候选能进入计时阶段。Geak 的正确性判定是与参考实现逐元素比对，材料未说明容差阈值。容差不是小事：fp32 归约在不同累加顺序下会产生末位差异，若容差设为严格相等，合法的并行归约会被误判为错误；若容差过松，候选可以用低精度近似（例如把 fp32 累加降为 fp16）换取速度而不被察觉。因此容差阈值必须与 dtype 绑定声明，例如 fp32 用相对误差加绝对误差的组合判据，fp16 用更宽的相对误差。

$$\mathrm{pass}_i=\mathbb{1}\Big[\max_{j}\big|y^{\mathrm{cand}}_j-y^{\mathrm{ref}}_j\big|\le \tau_{\mathrm{abs}}+\tau_{\mathrm{rel}}\cdot\big|y^{\mathrm{ref}}_j\big|\Big]$$

边界 shape 是 oracle 严格度的另一维度。空张量、单元素张量、非整除 tile 的尾块、含 NaN/Inf 的输入，都会触发候选内核的边界分支。若基准只测“整齐”shape，候选可以省略边界处理，代码更短、寄存器压力更小、性能更好，但这样的内核在真实部署中会越界或静默出错。因此边界用例的覆盖比例是评测强度的一部分，材料未给出覆盖范围，意味着无法判断通过正确性检查的候选是否真的处理了尾块。工程判断上，正确性 oracle 应把边界用例与常规用例分开报告，让读者看到候选在哪一类上失败。

代价方面，逐元素比对需要把参考输出与候选输出同时驻留显存，对大 shape 用例，这相当于把显存占用翻倍；若基准并发跑多个用例，显存压力会限制可测的最大 shape。时延上，比对本身是带宽受限操作，对超大输出可能比内核本身还慢，因此正确性检查的耗时需要与计时分离，不能混入加速比的分母。一个具体例子：一个输出为 (4096, 4096) fp32 的算子，输出张量占 64MB，两份比对即 128MB，加上输入与中间缓冲，单用例显存需求可能超过中端卡的容量，导致基准被迫缩小 shape 上限——这直接改变了 roofline 所处的区间。

五 · 可核查的测量口径清单

把上述缺口收敛成一份可执行的口径清单，是让 Geak 类基准从“演示”走向“可比较”的最小工程动作。清单应包含以下条目，每条都对应一个可被第三方复核的声明：算子语义与数学定义；每个用例的 shape 元组与 dtype；参考实现的名称与版本（或明确标注为朴素实现）；基线实现的名称与版本；Triton 与 CUDA 版本、GPU 型号与驱动版本；预热次数与计时迭代数；是否包含 JIT 编译与 autotune；同步方式与计时统计量（中位数/最小值/均值）；正确性容差的绝对与相对阈值；边界用例清单；隐藏 shape 的下发时机；防作弊检查项。

这份清单的信息密度决定了复现成本。缺少任一项，复现者就需要做假设，而假设的差异会直接体现在数字上。例如“是否包含 autotune”这一项，对 Triton 候选的影响可能是首调用延迟从毫秒级升到秒级；对稳态吞吐则几乎无影响。若论文只报稳态吞吐而不声明预热，读者会误以为端到端部署也是这个速度。因此口径声明不是附录里的形式主义，而是数字语义的一部分。

具体机制上，可核查的口径应把“测量”与“判定”分离：执行层先跑正确性比对，通过的候选进入计时队列；计时队列按固定预热与迭代执行，记录每次迭代的耗时分布而非单点值；汇总层从分布中取统计量并同时保留原始样本，供复核。这样做的代价是存储与汇总开销上升——每个用例保留全部迭代样本，数百用例乘以数十次迭代，轨迹体积可观。但对失败模式统计而言，这个代价是值得的：只有保留原始样本，才能区分“候选稳定地慢”与“候选偶发地被系统噪声拖慢”。

一个具体例子：某候选在 20 次迭代中 18 次耗时接近基线、2 次因显存回收或频率波动耗时翻倍。若只报平均值，该候选看起来略慢；若报中位数，则接近持平；若报最小值，则看起来更快。三种统计量给出三种结论，而只有保留原始样本才能让读者判断哪个统计量适合其部署场景。这正是口径必须显式声明统计量的原因。

六 · 隐藏 shape 与分布偏移下的评测设计

隐藏 shape 的处理有两种工程路线。第一种是“提示期给全集、评测期抽样”：智能体看到全部 shape 列表，但评测只随机抽取子集计时。这降低了过拟合单个 shape 的收益，但仍允许针对列表内的 shape 做特化。第二种是“提示期给分布、评测期给具体值”：智能体只知道 shape 的分布范围（例如 M,N,K 在某个区间内），评测时才下发具体元组。第二种更接近真实部署，但对智能体的泛化要求更高，首轮生成的失败率也更高，多轮重试的 token 成本随之上升。

分布偏移还有 dtype 维度。若提示期只给 fp32，评测期混入 fp16 或 bf16，候选的向量化宽度与累加精度假设都会失效。Triton 的块级 DSL 对 dtype 的处理依赖编译期常量，若候选把 dtype 写死，评测期换 dtype 会直接编译失败或走错路径。因此 dtype 分布的隐藏方式应与 shape 一致：提示期给分布范围，评测期给具体值，并在反馈中只回灌“该 dtype 下失败”而不泄露具体测试用例，避免智能体针对单个 dtype 打补丁。

代价上，隐藏分布会拉长收敛轮数。智能体在看不到具体输入的情况下生成的通用内核，往往需要更多轮编译错误与数值不符的反馈才能修正边界处理。材料未给出多轮重试上限与 token 成本，因此无法估算这一代价的量级。工程判断上，隐藏 shape 的收益（防过拟合）与代价（收敛变慢、方差变大）需要权衡：对以“展示能力”为目标的基准，可以给全集；对以“可信评测”为目标的基准，应隐藏具体值并报告逐用例分布，让读者看到候选在未见 shape 上的真实表现。

最终落在一条具体的工程判断上：Geak 类基准的可信度不取决于它报告了多大的加速比，而取决于它是否把基线、软件栈、计时口径、容差阈值与隐藏策略写成可被第三方逐条复核的声明。缺少这些声明时，加速比只是一个内部相对量，不能跨工作比较；补齐这些声明后，即便绝对数字不亮眼，评测结果也具备了被复现和被质疑的基础。基准的价值在于让失败可归因——是编译错误、数值超差、还是 shape 泛化不足——而不是让分数好看。
