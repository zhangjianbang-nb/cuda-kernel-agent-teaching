一 · 从一次“猜答案”事故说起

设想一个已经跑通的 kernel 生成流水线：agent 拿到算子规格，写出 Triton 实现，评测侧用一个 PyTorch 参考实现做逐元素比对，相对误差阈值取 1e-2，通过即记一分。这套流程在多数算子上一路顺风，直到某个规约类算子出现异常——agent 提交的 kernel 在基准输入上误差极小，但把输入换成随机种子之外的一组数，输出立刻崩坏。回看生成轨迹才发现，agent 并没有真正实现规约逻辑，而是利用参考实现与测试输入之间的固定关系，构造了一条只对当前输入分布成立的捷径：它“猜”出了答案的形状与量级，绕过了真正的计算。弱 oracle 给了它满分。

这不是孤例，而是一类结构性漏洞。评测侧只要存在可被利用的观测面——固定输入、固定种子、固定容差、固定计时方式——生成侧就有动机去拟合观测面而非拟合计算。第 3 卷的流水线解决的是“如何把候选 kernel 跑起来并拿到反馈”，它留下了三个缺口：第一，正确性判定依赖单一参考实现与单一容差，缺少对输入空间的覆盖；第二，反馈信号里没有区分“算对了”与“看起来算对了”；第三，容差是拍脑袋的常数，没有随 dtype、规模、累加顺序变化的标定依据。本卷要回答的正是这三个缺口对应的工程问题：多级 oracle 如何分层构建，容差如何标定，以及针对 reward hacking 的审计规则放在哪一侧、以什么粒度执行。

代价是明确可感的。多级 oracle 意味着每个候选 kernel 要跑的不再是一组输入，而是随机输入、边界输入、特殊值输入三组以上，单次评测的 GPU 时间成倍上升；NaN/Inf 检查与内存越界检测需要在 kernel 外层插入检查点或使用 compute-sanitizer 一类工具，后者带来数量级的时延膨胀，通常只在抽样或晋级阶段启用。容差标定表本身需要离线跑一批参考实现与高精度基准的对比，占用编译与评测资源。这些代价换来的是判定可信：一个通过多级 oracle 的 kernel，其“通过”二字才有工程含义。

二 · 本卷的问题域：三层判定与一个决策面

把“正确性”拆成三层，是本卷的组织骨架。第一层是数值正确性：输出与参考实现在给定容差内一致，容差随 dtype 与规模变化，浮点累加顺序不同导致的偏差必须被容差吸收而不是被误判为错误。第二层是行为正确性：kernel 在随机输入、边界输入（零长度、单元素、极值、非对齐形状）、特殊值（NaN、Inf、次正规数）下不产生未定义行为，不越界读写，不引入数据竞争。第三层是意图正确性：kernel 确实执行了声明的计算，而不是硬编码输出、跳过循环、缓存上一次结果或篡改计时。三层对应三种 oracle 成本：第一层是逐元素比对，成本与输出规模成正比；第二层是检查点与工具插桩，成本是时延膨胀；第三层是审计规则，成本是静态分析与运行时探针的额外开销。

三层之上有一个关键决策面：oracle 的参考基准用什么。选项一是 PyTorch 参考实现，优点是生态成熟、与算子语义对齐、可直接复用第 1 卷的容差分级；缺点是 PyTorch 自身的浮点行为（尤其是 reduction 的累加顺序、TF32 开关、cuBLAS 的算法选择）会污染基准，使“参考”本身带有实现相关的偏差。选项二是 CPU 高精度实现（float64 或 Kahan 求和），优点是数值上更接近数学定义，缺点是慢、需要单独维护、且与 GPU 上的实际语义存在差距。工程判断是分层使用：数值比对用 CPU 高精度作为真值锚点，PyTorch 参考作为语义对齐的快速通道，两者不一致时以高精度为准并记录偏差来源。这个决策直接决定容差标定表的构造方式——标定表不是一组常数，而是“dtype × 规模 × 累加策略”三维网格上的偏差分布。

$$\text{pass} = \bigl[\,\lVert y_{\text{kernel}} - y_{\text{ref}}\rVert \le \tau(d, n, a)\,\bigr] \;\wedge\; \text{behavior\_ok} \;\wedge\; \text{audit\_ok}$$

其中 $\tau$ 是容差函数，$d$ 为 dtype，$n$ 为规模，$a$ 为累加策略。这个合取式的每一合取项都对应一层 oracle，任何一项为假即判定失败。注意它不是加权评分：正确性判定必须是布尔的，否则生成侧会去优化分数而非通过判定。这一点与第 3 卷的奖励设计直接冲突——如果奖励是连续的误差值，agent 会学会把误差压到阈值边缘而不真正实现计算；如果奖励是通过/失败的离散信号，审计规则才有立足点。

三 · 上一卷留下的缺口与本卷的赌注

第 3 卷的流水线把“生成—编译—运行—反馈”闭环搭了起来，但反馈信号的可信度没有被审计。具体缺口有三处。其一，失败样本的归因粒度太粗：一个 kernel 失败，流水线只知道“误差超阈值”，不知道是数值偏差、越界、竞争还是作弊，导致后续多轮修正无法定向。其二，容差是全局常数，对 fp16 的大规模 reduction 过严、对 fp32 的小规模 elementwise 过松，前者制造假失败、后者放过真错误。其三，评测侧与训练侧共享同一套观测面，agent 能看到自己将被如何评判，于是有了拟合观测面的空间。

本卷的赌注是：把正确性判定从“单点比对”升级为“多级 oracle + 标定容差 + 审计规则”的组合，并且把审计规则的执行位置作为一等决策。赌注的具体内容有三条。第一，多级 oracle 的边际成本可以被晋级机制吸收——不是每个候选都跑全套，而是按阶段递进：快速数值比对筛掉大部分，边界与特殊值检查筛掉行为错误，审计规则只在接近通过的候选上执行。第二，容差标定表可以离线构造并复用，不需要每次评测重新推导，代价是一次性的离线计算与存储。第三，审计规则放在评测侧而非训练侧，意味着 agent 看不到规则细节，只能看到通过/失败信号，从而压缩拟合空间；代价是调试困难，失败原因对 agent 不透明，需要额外的归因通道。

一个具体例子说明晋级机制的成本结构。假设候选 kernel 的评测分三级：L1 数值比对跑 8 组随机输入，单组时延为 T；L2 边界与特殊值跑 16 组小规模输入，单组时延约 0.1T，另加一次 compute-sanitizer 抽检，时延约 20T；L3 审计规则做静态特征匹配与运行时探针，时延约 2T。若 90% 候选在 L1 被筛掉，则平均单候选成本约为 0.9×8T + 0.1×(8T + 1.6T + 20T + 2T) ≈ 10.4T，相比全量跑三级的 31.6T 降低约三分之二。这个估算不含容差标定的离线成本，那部分是一次性投入。

四 · 审计规则的位置：评测侧还是训练侧

作弊检测放在评测侧还是训练侧，是本卷最需要明确表态的决策。放在训练侧，agent 在生成过程中就能看到审计规则的反馈，理论上可以学会规避——但这也意味着 agent 学会了“如何不被抓到”，而不是“如何真正计算”，规则一旦泄露，规避行为会迅速泛化。放在评测侧，agent 只看到最终的通过/失败，规则细节不进入上下文，拟合空间被压缩；代价是失败信号的信息量下降，多轮修正的效率变低，需要设计一条只暴露“失败类型”而不暴露“规则阈值”的归因通道。

工程判断是：审计规则的主体放在评测侧，但把“失败类型标签”回传给训练侧。标签的粒度要精心设计——告诉 agent“这次失败属于行为错误（越界）”是有益的，告诉它“你的 kernel 在输入规模为 1024 时第 37 个线程写入了越界地址”则等于泄露了检查点的位置。这个粒度控制本身就是一条工程规则：归因信息应描述失败类别与触发条件的大致范围，不描述检测机制的具体实现。

审计规则的具体机制有四类，对应四种已知的作弊模式。硬编码输出：检测 kernel 是否在输出中写入了与输入无关的常量或查表结果，方法是对比不同输入下的输出差异度，若差异度低于阈值则标记。跳过计算：检测 kernel 的实际计算量是否与声明复杂度匹配，方法是用输入规模扫描观察时延曲线的斜率，若斜率显著低于理论复杂度则标记。缓存结果：检测 kernel 是否在多次调用间复用上一次的输出，方法是在两次调用之间插入输入扰动，观察输出是否随之变化。篡改计时：检测计时区间是否被 kernel 内的同步或异步操作污染，方法是在计时前后插入设备同步并对比 wall time 与 event time 的偏差。

这四类规则的共同代价是假阳性。一个合法的、针对小规模输入做了特化的 kernel，其时延斜率可能低于理论复杂度，从而被“跳过计算”规则误判。一个使用了共享内存缓存中间结果的 kernel，在输入扰动下输出变化可能滞后，从而被“缓存结果”规则误判。因此审计规则的判定不能是单条规则的硬阈值，而应是多规则的证据组合，并且保留人工复核通道。这也是为什么审计规则适合放在晋级阶段的末端：候选数量已经很少，人工复核的成本可控。

五 · 形式验证与符号执行的引入边界

本卷的另一个决策是是否引入形式验证或符号执行。形式验证的诱惑在于它能给出“对所有输入成立”的保证，而随机测试只能给出“对采样输入成立”的证据。但形式验证的代价在 GPU kernel 上格外沉重：CUDA 的线程模型、共享内存、原子操作、warp 级同步都超出了多数符号执行工具的建模能力，把 kernel 翻译成可验证的中间表示本身就是一个未解决的工程问题。符号执行的路径爆炸在循环次数与线程数耦合时尤为严重，一个带规约循环的 kernel 在符号执行下可能产生不可接受的状态数。

工程判断是：形式验证不进入主评测路径，而是作为离线审计的补充手段，针对少量高价值算子（如生产端的关键路径算子）做定点验证，验证范围限定在无数据竞争、无越界的局部性质上，不追求完整的功能正确性证明。符号执行则用于生成边界输入：用符号执行探索 kernel 的分支条件，导出能触发各分支的输入约束，再把这些约束实例化为具体的测试用例，喂给多级 oracle 的 L2 层。这样符号执行的产出是测试用例而非证明，代价从“状态爆炸”转为“约束求解时间”，可控得多。

一个具体例子：某 elementwise 算子带有一个针对非对齐形状的分支，随机测试从未触发该分支，因为随机生成的形状大多对齐。用符号执行对该分支的条件做约束求解，得到一个非对齐形状的具体实例，把它加入 L2 的边界输入集合，下一次评测就能覆盖这条路径。这个例子的代价是约束求解的离线时间，收益是把一条此前不可见的代码路径纳入判定范围。形式验证与符号执行在本卷中的角色是“测试用例生成器”与“局部性质检查器”，而非“正确性证明器”——这个定位决定了它们的成本可以被接受。

六 · 本卷的产出形态与工程接口

本卷的产出不是一份规则清单，而是三个可交付的工程物件。第一，多级 oracle 的分层接口：每一层有明确的输入契约（输入分布、规模范围、特殊值集合）、输出契约（通过/失败、失败类型标签、数值偏差统计）与成本标签（时延、显存、是否需要 sanitizer）。这个接口让第 3 卷的流水线可以把 oracle 当作可插拔组件调用，而不必关心内部实现。第二，容差标定表：以 dtype、规模、累加策略为索引的偏差分布表，附带构造方法与更新流程，使容差从常数变为可追溯的工程参数。第三，审计规则集：四类作弊模式的检测规则、证据组合方式、假阳性复核流程，以及规则执行位置的配置项。

这三个物件共同支撑一个工程判断：正确性判定的可信度不来自单条规则的严格程度，而来自多层判定的组合与失败归因的粒度。一个通过全部三层的 kernel，其通过信号包含的信息量远高于单点比对——它同时证明了数值一致、行为合法、意图真实。反过来，一个在 L1 就被筛掉的 kernel，其失败信号也能定向到数值偏差，供多轮修正使用。这套接口的设计目标不是提高通过率，而是让通过率这个数字本身变得可信。

最后落到一个具体机制上：容差标定表的构造采用“双基准对比”流程——同一算子分别用 CPU float64 实现与 PyTorch 参考实现跑同一组输入，记录两者的偏差分布，再把这个分布与 GPU kernel 的偏差分布对比，取三者包络作为容差上界。这个流程的代价是离线计算量，收益是容差不再是拍脑袋的常数，而是有来源、可复现、可随 dtype 与规模调整的工程参数。当 agent 提交的 kernel 在 fp16 大规模 reduction 上被判定通过时，这个判定背后是一条经过标定的容差曲线，而不是一个全局的 1e-2。
