一 · 从一次抖动说起：评测流水线要回答的到底是什么

设想一个已经跑起来的推理服务：一个 fused softmax-plus-topk 算子，输入形状 [B=64, S=2048, H=4096]，bf16，部署在单张 H100 上。agent 交上来两个候选 kernel：A 手写 CUDA，B 用 Triton 自动调优生成。第一次评测，A 的端到端时延比 B 低 4.1%；第二次评测，B 反超 2.7%；第三次两者持平。三次评测用的是同一份代码、同一张卡、同一批输入。工程团队面对的不是“哪个 kernel 更快”这个问题，而是“我凭什么相信任何一次测量”。这就是本卷的起点：评测流水线不是打分器，而是一台**可复现的测量仪器**，它的产出必须让“3% 的差异”这句话有意义。

把这个问题拆成可执行的形式，本卷要回答四件事。第一，**测量口径**：一次 kernel 调用的“耗时”到底指什么——是 CUDA event 夹住的 device 区间，还是 host 侧 wall clock 包住的 launch 加同步；warmup 多少次、重复多少次、取中位数还是分位数。第二，**环境口径**：容器化执行沙箱如何固定驱动、CUDA 版本、编译 flags，GPU 隔离与时钟锁定如何消除邻居干扰与频率漂移。第三，**统计口径**：在给定方差下，多少次重复才能把置信区间压到可判别 3% 差异的宽度，以及用什么检验判定“A 优于 B”而非“这次运气好”。第四，**失败口径**：编译错、运行错、超时、数值错、性能不达标这五类失败如何被分类、如何被计入排名，而不是被静默丢弃。

这四件事共同构成一个判据：给定 agent 提交的 kernel 与一组基准任务，流水线输出一个带不确定度带的分数，且这个分数在重跑时落在带内。没有这个判据，后面所有关于 RL 奖励、agent 排名、生产收益的讨论都悬空。

二 · 上一卷留下的缺口：任务与判据之间没有桥

第 2 卷给出了基准任务：KernelBench 系的算子集合、输入分布、参考实现与正确性容忍度。第 1 卷给出了判据：什么样的 kernel 算“对”，什么样的算“快”，roofline 与 SOL 如何给出理论上界。两者都是静态的——任务是一份清单，判据是一组定义。缺口在于：**从“任务 + 判据”到“一个可信的数字”之间，没有任何机制保证这条路径可重复**。

具体缺口有三处。其一，判据里的“快”是相对什么测的？roofline 给出的是带宽或算力上界，但实测时延受 launch 开销、L2 残留、时钟状态影响，同一个 kernel 在同一张卡上两次测量可以差出可观的百分比。其二，正确性判据是逐元素的容忍度，但 agent 生成的 kernel 可能在边界形状上越界读写而不被逐元素比较捕获——这类错误在单次运行里表现为“通过”，在压力运行里表现为非法访存。其三，任务清单默认每个任务有唯一参考实现，但 cuBLAS 兜底、不同精度路径、不同 tile 策略都会让“等价”变成需要定义的关系，而不是需要比较的数值。

这个缺口的代价是具体的：如果评测不可复现，那么 agent 的排名就是噪声的函数。一个在三次评测中两次胜出的 kernel，可能只是恰好赶上了时钟未降频的窗口。RL 训练里，这种噪声会被奖励函数放大——agent 学到的是“如何碰运气”，而不是“如何写出更好的 kernel”。本卷的赌注就是：**把测量仪器做对，比把搜索算法做复杂更能提升最终 kernel 的质量**。

三 · 本卷的赌注：口径统一优先于模型能力

赌注可以写成一个不等式。设真实性能差异为 Δ，测量噪声的标准差为 σ，重复次数为 n。可判别的差异下界近似为：

$$\Delta_{\min} \approx z_{1-\alpha/2}\cdot\frac{\sigma}{\sqrt{n}}$$

要让 Δ_min 小于 3%，要么压低 σ，要么增大 n。增大 n 的代价是线性的评测时延与 GPU 占用；压低 σ 的代价是一次性的工程投入——固定时钟、隔离 GPU、统一 warmup、统一计时原语。本卷选择后者：先把 σ 压到足够小，使得在可接受的 n 下 Δ_min 落在 3% 以内，而不是靠堆重复次数去平均掉本可消除的系统性噪声。

这个选择的工程含义是：流水线的复杂度从“统计补救”转移到“环境控制”。容器化执行沙箱固定镜像内的 CUDA toolkit 与编译器版本，避免同一份源码在不同 nvcc 下生成不同 SASS；GPU 隔离用 MIG 或独占分配消除邻居 kernel 对 L2 与 DRAM 带宽的争用；时钟锁定把 SM 频率钉在固定档位，消除因功耗墙触发的降频导致的时延漂移。每一项都对应一个可测量的方差来源，而不是笼统的“环境稳定”。

赌注的另一半是失败分类的严格性。一个编译失败的 kernel 与一个数值错误的 kernel 在排名上不应等价：前者是 agent 的语法或 API 使用问题，后者是语义问题，两者的修复路径不同，对 RL 奖励的塑造也不同。流水线必须把五类失败分别记录并计入分母，否则 agent 可以通过提交大量“能编译但跑不对”的 kernel 来刷高“通过率”这一指标。

代价在这里是明确的：容器化沙箱带来镜像构建与启动开销，GPU 隔离降低单卡可并发评测的任务数，时钟锁定牺牲了 boost 频率下的峰值性能观测。这些代价换来的是 σ 的下降，而 σ 的下降直接决定了 3% 这个门槛是否可达。

四 · 计时原语的选择：CUDA event 与 wall clock 的分工

计时口径的第一个决策是原语。CUDA event 记录的是 device 侧时间戳，夹在 kernel launch 前后，测的是 GPU 上实际执行区间；wall clock 包住的是 host 侧从发起 launch 到同步返回的整段，包含 launch 开销、驱动路径、可能的 host-device 同步抖动。对于单 kernel 微基准，event 给出的是干净的 device 时间；对于端到端服务片段，wall clock 才是用户感知的时延。

伪代码层面的口径定义如下：对每个候选 kernel，先跑 W 次 warmup 使时钟与缓存进入稳态，再跑 R 次测量，每次测量用一对 event 夹住连续 K 次 launch，取 K 次的平均作为该次测量的样本；最终对 R 个样本取中位数与 p90。warmup 的作用不是“让 GPU 热起来”这种模糊说法，而是让 L2 的残留数据、指令缓存、时钟档位进入可重复的状态；K 次连续 launch 摊薄单次 launch 的固定开销，使 event 区间主要反映稳态执行。

这里有一个必须写进口径的陷阱：event 夹住的区间如果包含 host 侧同步，测到的就不是纯 device 时间。正确做法是在 launch 流上记录起始 event，连续 launch K 次，再记录结束 event，最后统一 synchronize 并读取两个 event 的时间差。任何在循环内插入同步的实现都会把 host 抖动引入样本。

代价方面：event 方案要求 K 次连续 launch 共享同一份输入输出缓冲，这意味着测量的是稳态吞吐而非首次调用的冷启动时延；对于依赖一次性预处理的 kernel，冷启动时延被系统性低估。wall clock 方案则把 launch 开销计入，对短 kernel 尤为不利——一个执行 8 微秒的 kernel，launch 开销可能与之同量级，wall clock 会把差异放大成假象。因此口径必须声明：微基准用 event，端到端用 wall clock，两者不可混用于同一张排名表。

五 · 兜底与口径边界：cuBLAS、单卡与多卡

第二个决策是是否允许 cuBLAS 兜底。允许兜底的含义是：当 agent 生成的 kernel 在某个形状上失败或过慢时，流水线回退到库实现，服务仍能正确运行。这对生产端到端收益是必要的，但对评测是危险的——兜底会掩盖 agent kernel 在该形状上的缺陷，使排名表上的分数不再对应“agent 写的代码有多好”，而对应“agent 代码加兜底路径的混合体有多好”。

本卷的口径是分离两条路径：评测排名表只统计 agent kernel 自身的结果，兜底命中率作为单独的诊断指标记录。一个任务若在超过阈值比例的形状上触发兜底，该任务标记为“未覆盖”，不计入性能排名，但计入覆盖率统计。这样 agent 无法通过“写一个到处兜底的壳”来获得高性能分数，同时生产侧仍能拿到兜底带来的可用性。

单卡与多卡口径同理。单卡口径下，一个 kernel 的时延是确定的标量；多卡口径下，通信与切分策略进入测量，同一份 kernel 在不同并行度下的表现不可直接比较。流水线必须把并行度写进口径元数据，排名表按并行度分组，跨组比较视为无效。代价是多卡评测的 GPU 占用成倍增加，且通信抖动引入新的方差来源，需要单独的 warmup 与重复策略。

具体例子：一个 all-reduce 融合的 kernel 在单卡上测的是本地归约时延，在多卡上测的是归约加通信的端到端时延，两者相差一个通信项。若排名表不区分，单卡优化得好的 kernel 会在多卡组里被误判为差，反之亦然。口径元数据的作用就是让这种比较在结构上不可能发生。

六 · 把噪声压到 3%：方差来源的逐项拆解

要把 Δ_min 压到 3%，需要知道 σ 由什么构成。σ² 可分解为：时钟漂移方差、L2 与 DRAM 争用方差、launch 路径方差、输入数据分布方差、编译产物方差。每一项对应一个控制手段，且每一项的代价不同。

方差来源控制手段代价
时钟漂移锁定 SM 频率档位放弃 boost 峰值，观测值偏低
L2/DRAM 争用GPU 独占或 MIG 隔离单卡并发评测任务数下降
launch 路径K 次连续 launch 摊薄冷启动时延被低估
输入分布固定种子与形状集合覆盖率受限于所选形状
编译产物固定镜像内 nvcc 与 flags镜像构建与存储开销

逐项控制后，剩余 σ 主要来自测量本身的随机性，此时 n 的选择才有意义。以 3% 为目标，若控制后的 σ 相对于均值为 2%，则单次测量的标准误在 n=4 时约为 1%，双侧 95% 区间半宽约 2%，已可判别 3% 差异；若 σ 未控制而高达 8%，则 n 需增至数十次才能达到同样宽度，评测时延与 GPU 占用成倍上升。这就是“先控环境、再定重复”的顺序不可颠倒的原因。

显著性检验的用法也要写进口径：排名表不输出裸均值，而输出均值与置信区间；两个 kernel 的比较用配对检验，因为同一形状、同一输入下的两次测量共享环境，配对能消掉共同的环境偏移。代价是配对要求两个 kernel 在同一时间窗口内交替测量，增加了调度复杂度，但换来的是在相同 n 下更窄的判别区间。

失败分类在这一节收口：编译错与运行错在测量前即被拦截，不进入计时；超时按口径上限截断并单独计数；数值错由正确性 oracle 判定，与性能排名解耦；性能不达标是排名表的正常输出，不是失败。五类失败的计数共同构成一个任务的“有效样本率”，这个比率与性能分数一起进入 agent 的评估，防止用大量无效提交稀释分母。

当 3% 的差异被噪声吞掉：评测流水线的失效边界

以一个具体的服务场景开场：某团队用 agent 为一个 attention 变体生成 Triton kernel，候选实现相对基线的实测加速比落在 1.02–1.05 之间，而同一份代码在同型号卡上隔夜重跑，加速比会在 0.98 与 1.06 之间摆动。此时“是否采纳”这个决策的输入不是 kernel 本身，而是评测流水线的分辨率。本卷的赌注正在这里：把评测从“跑一次看数字”变成一条带沙箱、隔离、口径与统计判据的流水线，使 3% 的差异成为可判别量而非随机涨落。代价是明确的——容器化执行与 GPU 隔离带来启动时延，warmup 与重复采样吃掉吞吐，显著性检验要求更多重复次数，单次评测的 token 与机时成本随之上升；若把这些成本压到最低，判据就会退化为噪声。

失效条件可以写成一条不等式。设单次测量噪声标准差为 σ，重复 n 次取中位数，则均值标准误约为 σ/√n（中位数的渐近方差更大，量级同阶）；要判别相对差异 δ，需满足 δ·μ > k·σ/√n，k 为判据倍数。当 σ 主要来自时钟漂移与邻居负载而非 kernel 自身，增大 n 只压低随机分量，压不动系统性偏移——这正是必须做时钟锁定与 GPU 隔离的原因。反例：若允许 cuBLAS 兜底，候选实现可能在大 shape 上悄悄回落到库调用，测得的“加速”其实是调度路径差异；若计时混用 wall clock 与 CUDA event，启动开销与异步排队会污染小 kernel 的口径。这类失效不报错，只让排名漂移。

口径选择收益系统代价
CUDA event 计时剔除主机侧排队噪声需固定 stream 与同步点，漏掉首帧冷启动
禁用 cuBLAS 兜底测到真实自研路径部分 shape 直接编译失败或超时，失败率上升
单卡固定时钟方差可控、可复现失去多卡通信与真实频率 Boost 行为

因此本卷不把“跑通”当作评测终点，而把失败分类（编译错、运行错、超时、数值错、性能不达标）当作一等产出：只有把“测不准”与“算不对”分开记账，agent 的多轮优化才不会在噪声上过拟合。一个具体机制是把每次评测的元数据（时钟状态、warmup 次数、重复数、分位数口径、是否触发兜底）随结果一起落盘，使两次排名差异可归因到口径变更而非 kernel 变更。工程判断落在取舍上：当判别阈值从 3% 放宽到 10%，重复次数与机时成本下降，但小改进被系统性丢弃；收紧到 1%，则需接受更长的排队与更高的超时失败率——这条曲线本身就是本卷要交付的决策依据。
