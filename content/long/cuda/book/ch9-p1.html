一 · 开场：一个 1.8x 的 kernel，为什么只换来 4%

设想一个推理服务：某推荐模型的 embedding + 归一化 + 激活这一段，被 agent 生成并调优出一个融合 kernel。在隔离的微基准里，它相对 PyTorch 原生实现拿到 1.8x 的 kernel 级加速，NCU 上 SM 占用与访存效率都漂亮。团队按流程合入、打包、上线灰度。第二天看线上大盘：P99 端到端时延只降了 4%，吞吐几乎没动，单卡成本曲线看不出拐点。

这不是失败故事，而是本卷的起点。1.8x 与 4% 之间的落差，不是 kernel 写错了，而是三个口径同时错位：其一，被优化的那段在端到端时间里的占比本来就有限，Amdahl 的上限先把它压死；其二，融合 kernel 换掉了框架原本的算子序列，但引入了一次额外的布局转换与一次同步，把省下的时间又吐了回去；其三，微基准测的是稳态、独占、固定 shape，线上是变长 batch、动态 shape、与其他 kernel 争抢 SM 的混合负载。本卷要回答的，就是如何让“kernel 级收益”可信地翻译成“服务级收益”，以及在翻译不成立时，如何尽早发现而不是上线后才发现。

$$S_{e2e} = \frac{1}{(1-p) + p/S_{k}},\qquad p=\frac{T_{k}}{T_{e2e}}$$

这个式子没有任何新东西，但它是本卷所有决策的锚：当 p 只有 5% 量级时，哪怕 S_k 趋于无穷，端到端上限也只有约 1.05x。所以本卷的第一个工程动作不是“再优化 kernel”，而是先把 p 测准——按算子、按 shape 分桶、按真实请求分布加权，而不是拿一个平均占比糊过去。这个测量本身的代价是显存的：要拿到分桶时间占比，就得在服务进程内做细粒度计时或分段 profile，采样开销与额外显存驻留必须被预算进去，否则测量行为本身会污染被测对象。

二 · 上一卷留下的缺口：能力有了，判决没有

第 8 卷交付的是“模型能写出并调优出通过微基准的 kernel”，第 3 卷交付的是“评测口径与可信流水线”，第 1 卷交付的是“业务需求清单”。三者拼在一起，仍然缺一块：从“这个 kernel 在基准上更快且正确”到“这个服务该不该换、换多少、换错了怎么退”的判决链路。基准里的正确性是数值 oracle 意义上的正确性；生产里的正确性是“在业务精度容差内、在真实输入分布上、在框架调度约束下不破坏语义”。这两者之间隔着一层集成语义，而集成语义从来不在 kernel 作者的视野里。

具体机制上，缺口体现在三个接口上。第一是布局与生命周期接口：框架的张量有固定的 stride、内存池、流与事件语义，agent 产出的 kernel 往往假设连续布局、假设自己可以自由分配 workspace，一旦嵌入就要么触发隐式 copy，要么在错误的 stream 上同步。第二是精度接口：kernel 内部用 fp32 累加还是 tf32、是否重排归约顺序，都会改变末位比特，微基准里用 allclose 一挡就过，业务侧则可能在长尾样本上放大成排序或阈值判定的翻转。第三是调度接口：框架的图捕获、算子融合 pass、动态 shape 分支会与手写 kernel 争夺“谁来融合”的决定权，两个融合策略叠加时常出现负优化。

缺口的代价可以直接计量：一次布局转换在 HBM 上多走一遍读写，按带宽折算就是实打实的时延；一次跨 stream 同步会把异步流水打断，把本可重叠的访存与计算串行化；一次精度回退导致的业务指标抖动，则需要用更大的灰度样本量和更长的观察窗口才能判定，直接拉长了发布周期。这些都不是 kernel 内部能优化掉的，只能靠集成路径的设计来消除。

三 · 本卷的赌注：把“收益归因”当作一等工程物

本卷押的是一个判断：生产落地的瓶颈不在 kernel 生成，而在收益归因与集成路径的可测量性。换句话说，与其追求微基准上再高零点几倍的加速，不如先把“这 4% 是从哪来的、还能不能再多、多出来的部分值多少钱”变成可复现的工程产物。这个赌注的反面是常见的做法——拿微基准数字做发布决策，用“kernel 加速比”当 KPI，结果团队持续优化 p 很小的算子，投入产出比持续恶化。

归因的具体机制是分层拆解：把端到端时延拆成框架开销、数据搬运、kernel 执行、同步等待四类，再在 kernel 执行内部按算子分桶，每层都保留改动前后的对照。伪代码思路大致是：对同一批真实请求，分别在基线版本与候选版本上跑分段计时，按 (算子, shape 桶, batch 区间) 三维聚合，输出每桶的时间差与请求占比的乘积，得到加权收益；同时记录每桶的显存峰值与额外 copy 字节数，把“省下的计算”与“多花的搬运”放在同一张表里对冲。这套聚合的代价是采样本身：高频计时器会引入可观测的抖动，分段 profile 在长尾 shape 上采样率不足会给出噪声很大的桶估计，因此桶的划分粒度必须在统计功效与开销之间取平衡。

决策项判据失败代价
只换热点 kernel该算子 p 值与可消除的框架开销之和是否超过发布门槛集成面小但收益天花板低，反复投入难见成效
整算子融合融合后布局转换与同步是否被消除，而非被搬移负优化风险高，回滚粒度粗
精度容差业务侧指标在容差内的敏感度，而非 allclose 阈值长尾样本翻转，需更长观察窗口才能判定
灰度比例与回滚阈值按请求分桶的收益方差，而非全局均值均值掩盖长尾退化，回滚滞后

以开场的服务为例：归因表显示，那 4% 里有相当一部分来自被消除的一次布局转换，而融合 kernel 内部因为 workspace 分配引入的一次隐式同步又吃掉了一部分；真正来自计算加速的份额比预期小。这个结论直接改变了下一步动作——不是继续调这个 kernel 的 tile，而是去谈“能不能把上游的 layout 在框架侧就固定下来”。这就是归因作为一等工程物的价值：它把优化方向从 kernel 内部挪到了集成边界上。

四 · 候选筛选：先算上限，再谈实现

本卷产出的第一道工序是候选 kernel 筛选，它的核心不是“哪个 kernel 最快”，而是“哪个 kernel 值得被集成”。筛选的第一层是 Amdahl 上限：对每个候选算子，用真实请求分布加权算出 p，再乘以一个乐观的 S_k 上界，得到端到端收益的天花板；天花板低于发布门槛的直接出局，不进入集成。第二层是可消除开销清单：该算子周边是否存在可被融合消除的 copy、同步、临时分配，这些是融合类改动的真正收益来源。第三层是集成风险面：需要改框架代码的深度、是否需要图捕获兼容、是否需要新的精度路径。

这里有一个容易被忽略的代价项：编译与打包时间。候选 kernel 进入生产镜像意味着更长的构建链、更多的架构变体（不同 SM 版本、不同 shape 特化），每次框架升级都要重新验证。一个微基准上略快但需要大量 shape 特化的候选，其维护成本会以编译时间和回归矩阵规模的形式持续计费。因此筛选阶段就要把“特化数量”当作负向指标，而不是把“峰值加速”当作唯一正向指标。

具体例子：同一段归一化逻辑，候选 A 是单 kernel 融合但需要两次布局转换，候选 B 是保留框架算子但在中间张量上省掉一次物化。微基准上 A 更快，但按 p 加权并计入转换成本后，B 的端到端期望更高且集成面更浅。筛选的结论应当是 B 优先进入 A/B，而不是让 A 因为微基准数字好看而占用集成资源。

五 · 集成的三条硬边界：布局、精度、调度

与 PyTorch、TensorRT、vLLM 这类框架集成时，agent 产出的 kernel 必须接受三条硬边界，任何一条越界都会把微基准收益清零。布局边界：kernel 的输入 stride 假设必须与框架实际给出的张量一致，或者显式声明一次转换并由归因表计入成本；不能靠“运行时恰好连续”这种隐式契约。精度边界：累加精度、归约顺序、是否使用近似指令，都要在业务精度容差下做端到端验证，而不是在微基准里用固定随机种子过关。调度边界：kernel 必须在框架指定的 stream 上执行，workspace 必须来自框架内存池或显式预算，图捕获场景下不得有运行期动态分配。

这三条边界的验证成本不对称：布局问题通常在集成测试里立刻暴露，代价是返工；精度问题往往只在长尾样本上暴露，代价是灰度期的指标抖动与更长的观察窗口；调度问题最隐蔽，可能在低负载下完全正常，在高并发下才因 stream 争用或内存池碎片而退化。因此集成测试的设计应当按“暴露难度”分配样本量：调度类问题需要高并发压测，精度类问题需要覆盖长尾输入分布，布局类问题需要覆盖动态 shape 与非常规 stride。

$$\text{集成收益} = \sum_{b}\big(\Delta T_{k,b} - \Delta T_{copy,b} - \Delta T_{sync,b}\big)\cdot w_b$$

其中 b 是请求桶，w_b 是该桶的请求占比。这个式子的工程含义是：任何一个桶里搬运或同步的增量超过计算节省，该桶就是负收益，必须单独处理而不是被全局均值掩盖。开场的 4% 正是这个式子在全局加权后的结果，而分桶看时，某些桶甚至是负的——这正是后续灰度阈值要按桶设定的原因。

六 · 灰度与回滚：把判决做成可执行的阈值

灰度不是“先放 1% 看看”，而是把归因结论转成可执行的判决规则。机制上，灰度比例应当按请求桶的收益方差来定：收益稳定且为正的桶可以快速放量，收益方差大或存在负收益风险的桶需要更小的比例与更长的观察窗口。回滚阈值必须同时包含性能与正确性两类信号：端到端时延的分位数退化、吞吐下降、业务侧精度相关指标的漂移，任一越界即触发回滚。回滚粒度取决于集成方式——只换热点 kernel 可以按算子开关回滚，整算子融合则往往需要按版本回滚，这也是筛选阶段要把回滚粒度当作决策项的 reasons。

代价在这里体现为发布周期：更细的桶划分与更长的观察窗口意味着更慢的放量节奏，而更粗的划分则冒着均值掩盖退化的风险。一个可操作的折中是：先用小比例灰度收集分桶收益的方差估计，再据此重设放量节奏，把“观察”本身当作一次测量而不是一次等待。真实负载下的收益归因必须在这个阶段持续进行，因为线上请求分布会漂移，微基准里成立的 p 值在流量结构变化后不再成立。

回到开场那个服务：如果灰度阶段就按桶看归因，负收益桶会在小比例下先暴露，团队可以在放量前就决定“这个 shape 区间回退到框架原生路径”，而不是等到全量后才发现 4% 里有一部分是负贡献。这就是本卷要建立的工程判断——kernel 的加速比是输入，端到端的分桶净收益才是判决依据，而判决必须在上线前就以可执行阈值的形式存在。

当微基准的 1.8x 撞上端到端的 4%

先把这个场景钉死：一个推理服务里，注意力前的 LayerNorm+残差融合被候选 kernel 替换，微基准在目标卡型上跑出 1.8x 加速，团队按此预估容量收益并排期上线；灰度后按集群口径核算，端到端时延只降了 4%，吞吐几乎不动。这不是调优失败，而是本卷要处理的边界：微基准测的是 kernel 自身在理想 occupancy 与热 cache 下的执行时间，端到端测的是它在真实 batch 分布、框架调度、显存分配器与通信重叠之间的位置。两者之间的差距由 Amdahl 与“非 kernel 时间”共同决定：若该 kernel 占端到端 GPU 时间比例为 $$p$$，加速比为 $$s$$，则端到端理论上限为 $$T_{\text{e2e}} \ge T_{\text{base}}\left[(1-p) + p/s\right]$$。代入 $$p=0.05,\ s=1.8$$，上限约 3.8%——4% 不是异常，是公式的直接输出。失效条件因此很清晰：当 p 小到与测量噪声同量级时，任何 kernel 级加速都无法在端到端被可信归因。

由此得到本卷的第一个工程判断：候选 kernel 的筛选标准不能是微基准加速比，而应是“可归因收益上界”。筛选阶段就要拿到该 kernel 在真实 trace 中的时间占比（NCU 或框架 profiler 的 kernel 时间切片），并乘以一个保守的集成折损系数——融合 kernel 往往改变 launch 数量、寄存器压力与 occupancy，进而改变相邻 kernel 的调度间隙；把算子拆成多 kernel 的融合方案还会引入额外中间显存与同步点。代价是显性的：筛选阶段多花一轮 profile 采集与集成验证的编译/构建时间，换来的是避免把整卷的灰度预算押在一个 p 值不足的算子上。

第二个判断关于核算口径。单卡核算看的是 kernel 时间与单请求时延，集群核算看的是吞吐、尾延迟与资源碎片；同一份 1.8x 在单卡口径下亮眼，在集群口径下会被批处理填充率、KV cache 占用与负载不均衡稀释。本卷要求收益归因同时给出两个口径，并把回滚阈值绑定在集群口径的尾延迟上，而非均值。下表是本卷对三类候选的取舍边界：

候选类型微基准信号端到端风险核算口径
热点单 kernel 替换加速比高、p 小收益不可归因集群尾延迟
整算子融合launch 减少显存峰值与精度容差单卡时延+吞吐
精度降级路径带宽下降业务侧容差不可接受正确性 oracle 先行

第三个判断落在精度容差上：融合与降精度会改变数值路径，业务侧能否接受不由 kernel 作者决定，而由第 1 卷的业务需求清单与第 3 卷的评测口径共同裁定。工程上的做法是把容差写成可执行的回归断言——对固定输入集比对输出分布与下游指标，任何超阈即触发回滚，而不是等到灰度期间靠人工观察。这里的系统代价是回归测试的构建与运行时间，以及为保留可回滚路径而维持的双版本 kernel 编译产物与显存开销。
