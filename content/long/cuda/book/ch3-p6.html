一 · 从“跑分”到“时间去向”：反馈信号的分层

agent 拿到一个能跑通的 kernel 之后，最想知道的是“它慢在哪”。但“慢”不是一个标量，而是一组可被观测的分层信号：端到端时延、kernel 内部 stall 结构、指令级瓶颈、以及二进制层面的资源占用。可信评测流水线要做的，是把这些信号整理成 agent 能消费的、与判据口径一致的反馈，而不是把 ncu 的一屏文本原样丢进上下文。分层的第一原则是：每一层信号必须绑定一个明确的测量口径，否则 agent 会把不同口径的数字放在一起比较，得出错误结论。例如端到端 wall clock 包含了 launch 开销与 Python 侧调度，而 kernel 级 CUDA event 只覆盖 device 执行段；两者相差在短 kernel 上可以是一个数量级，agent 若拿 wall clock 去对齐 roofline 的理论下界，就会误判“离 SOL 很远”，进而做出无意义的优化。

因此反馈接口应当显式携带口径标签：scope=kernel 与 scope=e2e 分开上报，并附带 warmup 次数、重复次数、取中位数还是分位数。这与本卷前面确定的计时口径直接挂钩——如果流水线的排名口径是中位数 kernel 时间，那么 profile 反馈也必须以同一段重复采样的中位次为锚，否则 agent 优化的目标函数与评测的目标函数不一致。代价是采样开销：一次带 ncu 的 profile 会把 kernel 重放多次，单次采集的时延可达毫秒到秒级，且会串行化执行，无法与吞吐测试并行。工程上通常把 profile 放在“诊断回合”而非“排名回合”，用少量重放换取结构信息，再回到无插桩的快跑口径做验证。

二 · Roofline：把“离上限多远”变成可计算的标量

roofline 的价值不在于画图，而在于给 agent 一个可微的、可比较的差距度量。给定 kernel 的浮点运算量 $F$（FLOP）与访存量 $B$（Byte），算术强度 $I=F/B$，机器峰值算力 $P_{peak}$ 与峰值带宽 $BW_{peak}$，则可达性能上界为：

$$P_{max}=\min\left(P_{peak},\; I\cdot BW_{peak}\right),\qquad \text{SOL}=\frac{P_{achieved}}{P_{max}}$$

agent 需要的是三个数：$I$、当前落在斜线段还是平台段、以及 SOL 百分比。落在斜线段说明访存受限，优化方向是提高复用（分块、寄存器缓存、共享内存重排）；落在平台段说明算力受限，方向是减少指令数、提高 ILP 或换用更低精度的数据通路。这里的关键机制是：$F$ 与 $B$ 必须按“有效”口径统计——$B$ 应取实际发生的全局访存字节（含因合并失败而放大的事务），而不是按张量形状算出的理想字节。若用理想字节，一个合并效率只有一半的 kernel 会被算成访存受限且 SOL 虚高，agent 会误以为“已经接近上限”而停止优化。代价在于统计精度：精确的有效字节需要硬件计数器，而计数器采集本身要占用一次 profile 重放；用解析式估算则会在间接寻址、稀疏访问上失真。

具体例子：一个逐元素缩放 kernel，$I$ 极低（每元素一读一写、仅一次乘），必然落在斜线段，SOL 的上界就是带宽比。此时 agent 若去优化指令调度是徒劳的，正确动作是检查访存是否合并、是否可以用向量化加载把事务数压到理论值。反过来，一个矩阵乘的小尺寸 tile 版本，$I$ 随 tile 尺寸上升，agent 应判断当前 tile 是否已越过脊点（ridge point，$I=P_{peak}/BW_{peak}$）；未越过就继续增大 tile，越过后再转向指令级优化。roofline 给出的不是答案，而是“该往哪个方向花 token”的判据。

三 · Warp stall：把“等”拆成可归因的类别

roofline 只告诉你能不能更快，warp stall 告诉你是谁在拖。SASS 级 stall 原因通常分为若干类：等待内存依赖（long scoreboard）、等待共享内存/常量（short scoreboard）、等待数学流水线（math pipe throttle）、等待指令取指（no instruction）、以及 barrier 同步。agent 需要的是每类的占比与绝对周期数，而不是一个笼统的 “stall”。机制上，这些计数来自 SM 的 warp 调度器采样：每个周期记录每个 warp 未能发射的原因，按类别累加，再除以总周期得到占比。伪代码思路是：

  • 对目标 kernel 做一次定点重放，采集 smsp__warp_issue_stalled_*_per_warp_active.pct 一组计数器；
  • 按占比排序，取前两类作为归因候选；
  • 把“占比 × 该 kernel 的实测周期”换算成绝对损失周期，与理论下界的差值对照；
  • 只把前两类与绝对损失写进 agent 的反馈，其余丢弃，控制上下文长度。

代价是采样分辨率与重放成本：计数器按 SM 子集采样，短 kernel 可能采不到足够样本，占比噪声大；重放又必须锁定时钟，否则占比会随频率漂移。工程判断是：对执行周期低于某个阈值的 kernel，不采 stall 结构，改用指令级静态分析（SASS 反汇编 + 依赖链长度估算）替代，避免用噪声占比误导 agent。具体例子：一个 reduction kernel 若 long scoreboard 占比高，说明全局加载延迟未被隐藏，agent 应增加每线程的独立加载数或提前发起加载；若 barrier 占比高，说明块内同步过频，应改为 warp 级归约或两级归约。两类占比指向完全不同的改写，这正是分层反馈的意义。

四 · SASS：让 agent 看见编译器做了什么

源码到 SASS 之间存在大量编译器决策：循环展开、向量化、寄存器分配、谓词化、指令调度。agent 在 CUDA C++ 层面做的“优化”可能被编译器抵消，也可能被编译器悄悄完成。可信反馈必须把 SASS 的关键统计暴露出来：每线程寄存器数、溢出到本地内存的字节数、实际发射的指令条数、以及关键循环的展开因子。机制上，这些可从 cubin 反汇编与资源占用报告中提取，不需要运行；代价是编译时间与工具链耦合——不同 CUDA 版本的 SASS 编码与调度策略不同，跨版本比较指令条数没有意义，反馈里必须带上工具链版本标签。

最需要警惕的是寄存器溢出：源码层面看起来只是多用了几个局部变量，编译器却把寄存器压力推过阈值，产生 local memory 的 spill，直接打击带宽与延迟。agent 若只看源码，会认为“变量多一点无所谓”；看到 SASS 中的 LDL/STL 指令与 spill 字节数，才会转向减小活跃变量数或改用共享内存。另一个典型是向量化失效：源码写了 float4，但因指针对齐未保证，SASS 里仍是标量 LDG.E，事务数翻倍。反馈应把“期望的向量宽度”与“SASS 实际宽度”并列，让 agent 直接看到差距，而不是让它去猜。这里的性能代价是可量化的：spill 字节数乘以访问频次即近似为额外的本地内存流量，可与 roofline 的 $B$ 相加后重新计算 SOL，形成闭环。

五 · 二进制插桩：在不改源码的前提下取时间

当源码不可改、或需要按指令/按内存事务粒度归因时，二进制插桩是唯一手段。机制上分两类：静态改写 cubin，在目标指令前后插入读时钟的指令并把差值写入缓冲区；或动态借助调试/分析接口在指令边界暂停并采样。前者精度高、开销可控，但需要理解 SASS 编码与寄存器分配，插桩本身会改变寄存器压力与调度，可能引入观测者效应；后者侵入性小，但采样是统计性的，短 kernel 上样本不足。伪代码思路：选定插桩点集合（如每个基本块入口），分配一个全局计数器缓冲区，插入 S2R 读时钟、做差、原子累加到对应槽位，最后把槽位表回传。代价是三重的：插桩指令本身增加执行周期（每个插桩点几条指令，密集插桩可让时延翻倍）、原子累加引入串行化、缓冲区占用显存并可能触发额外的写事务。

因此插桩反馈必须自带“开销标定”：用同一 kernel 的未插桩版本做基线，报告插桩后的时延膨胀比例，并声明归因结论只在膨胀可接受的区间内可信。具体例子：一个多阶段 kernel（加载—计算—写回），agent 怀疑写回段是瓶颈。静态插桩在每个阶段边界读时钟，得到三段占比；若写回段占比高且该段内 STG 事务数远超理论值，则归因成立，agent 转向改善写合并或改用流式写。若膨胀比例过大导致占比失真，则应退回用 stall 类别与 roofline 联合推断，而不是相信插桩数字。这一条是可信评测的底线：任何 profile 信号都要附上它的获取代价，否则 agent 会把观测噪声当成物理事实。

六 · 反馈的压缩与可判别性

agent 的上下文预算有限，profile 反馈不能是原始计数器转储。压缩的原则是“只保留能改变决策的量”：roofline 的 $I$ 与 SOL、stall 前两类的绝对损失周期、SASS 的 spill 字节与向量宽度、插桩的阶段占比与膨胀比例。每个量都要带口径与获取代价标签，且与排名口径的中位次对齐。判别性要求来自本卷的方差控制目标：反馈中任何用于比较的数字，其噪声必须小于要判别的差异，否则 agent 会在噪声上做优化。机制上，对每个上报量给出重复采样的离散度（如四分位距），当离散度超过阈值时把该量标为“不可判别”，agent 应忽略它。代价是额外的重放次数与统计计算，但相比让 agent 在抖动信号上浪费多轮 token，这个代价是划算的。

具体工程判断：把 profile 反馈做成“诊断回合”的产物，与“排名回合”的快跑口径分离；诊断回合允许毫秒级重放与插桩，排名回合只跑无插桩的中位数计时。两者之间用同一份 kernel 二进制与同一时钟锁定状态衔接，确保 agent 在诊断中看到的瓶颈与排名中测到的时延是同一个物理对象。若诊断回合的膨胀比例超过可接受区间，则整份 profile 反馈降级为“方向性提示”，不参与定量比较。这条规则把“看见时间去哪了”约束在可信范围内：agent 得到的是可归因、可复算、带代价标签的信号，而不是一屏漂亮但不可判别的计数器。

当 profile 本身成为噪声源：硬件反馈链路的失效边界

把 NCU、SASS 反汇编、二进制插桩接进 agent 的反馈回路，前提是这些信号在重复采集下自身稳定。失效点恰恰在这里：NCU 默认的 replay 模式会把 kernel 重放多次以分趟采集不同硬件计数器，重放期间 L2 被预热、指令缓存状态改变，测出来的 stall 分布与真实单次执行不同；对短 kernel（执行时间与 replay 开销同量级）尤为严重。更隐蔽的是时钟：若未锁定 SM 时钟与显存时钟，两次 profile 的 smsp__warp_issue_stalled_long_scoreboard 占比差异可能主要来自频率漂移而非代码变化。工程判断是：profile 采集必须与计时口径分离——计时用 CUDA event 加固定 warmup 与分位数口径，profile 只在时钟锁定、缓存状态受控的专用通道里跑，且同一 kernel 至少两次采集比对 stall 直方图的一致性，不一致就标记该样本不可用于归因。

roofline 作为归因工具同样有边界。它给出的是渐近上界：算术强度 I = FLOPs / Bytes，可达性能 P ≤ min(P_peak, I · B_peak)。对访存不规则、依赖链长、occupancy 被寄存器压力压低的 kernel，roofline 预测的“应该达到”与实测的差距无法区分是带宽没打满还是延迟没藏住。此时需要 warp stall 分解来补：把 stall_long_scoreboard（等全局访存）、stall_wait（等固定延迟指令）、stall_barrier（同步）的占比与 occupancy 一起看，才能判断是提高并行度还是改数据布局。代价是 token 与采集时延：一次完整 NCU 采集加 SASS 反汇编的文本量可达数千行，直接塞进上下文会挤占推理预算，通常只回传按 stall 排序的 top-N 源码行与对应 SASS 片段的摘要。

二进制插桩（如按指令边界插入计数或时间戳）提供最细粒度的时间归属，但会改变被观测对象：插桩引入的额外指令改变指令缓存行为与调度，测得的是“插桩后的 kernel”。对寄存器紧张的内核，插桩还可能触发 spill，使原本的瓶颈消失或转移。因此插桩只适合做定性定位（哪一段循环是热点），不适合作为性能判据。系统代价上，插桩版本编译时间与二进制体积增长，且需与未插桩版本的正确性输出逐元素比对，否则优化方向可能建立在错误语义上。

反馈信号可信前提典型失效代价
NCU 计数器时钟锁定、replay 一致性校验短 kernel 重放污染缓存采集时延长，计数器分趟
roofline 上界算术强度可静态估算延迟受限时无法归因需配合 stall 分解
SASS 反汇编与 PTX/源码行映射可靠编译器重排致映射漂移上下文 token 占用高
二进制插桩插桩前后语义等价已验证spill 改变瓶颈位置编译时间与体积增长

具体例子：一个 reduction kernel 在 roofline 上被判为带宽受限，agent 据此改向量化宽度；但 NCU 显示 stall_barrier 占比高，真实瓶颈是块内同步与尾块负载不均，向量化改动只带来噪声级波动。这说明单一路径的硬件反馈会把 agent 引向错误的优化方向——流水线必须要求至少两条独立信号（roofline 预测 + stall 分解）交叉印证后才允许把该归因写入下一轮 prompt，否则只作为候选假设记录，避免把一次抖动固化成“事实”。
