一 · 开场：一个 3% 的算子，为什么值得单独一卷

设想一个已经上线的推理服务：模型结构稳定，batch 形状稳定，唯一不稳定的是每层之间那个融合算子——把 layernorm、残差、量化打包进一个 kernel。它占端到端时延的比例很小，小到性能团队排优先级时总是把它排在后面；但它又足够热，热到每省下一点，都会在整条链路上被放大成可观的容量。工程上真正棘手的不是“写一个能跑的 kernel”，而是“写一个比现在快、并且在各种边界形状上都对”的 kernel。前者一个熟练工程师半天能交差，后者要反复编译、反复跑、反复看 profile，往往耗掉数天。

这正是本卷的对象。第 3 卷把评测接口定死了：一个 kernel 提交进来，怎么喂输入、怎么计时、怎么判定通过。第 4 卷把 oracle 契约定死了：正确性由谁裁决、容差怎么给、形式审计在什么条件下介入。两卷合起来，回答了“如何可信地判断一个 kernel 好不好”。但它们都默认了一件事——那个被判断的 kernel 已经存在。谁把它写出来？谁在编译失败后改它？谁在第一次跑出错误结果后定位到是 shared memory 的边界条件写错了？本卷要回答的就是这个空缺：**从一份算子规格，到一个通过评测契约的 kernel，中间那段由 agent 承担的闭环如何搭起来。**

用一个更具体的场景锚定：任务是把一个 Triton 写的 softmax 换成 CuTe 版本，目标形状是隐藏维 4096、行数动态。第一次生成，agent 给出的 CuTe 代码在 tile 划分上把行维和列维搞反了，编译能过，跑出来数值全错。第二次，它拿到的是“输出与参考在第 0 维不匹配”这样一句反馈，改了三处无关的地方。第三次才在反馈里看到具体的行号与错误类别，才把 tile 形状改对。这三次尝试的差别不在模型能力，而在**反馈的结构**。本卷的赌注就压在这里。

二 · 上一卷留下的三个缺口

第 3 卷与第 4 卷交付的是“判定器”，不是“生产者”。把判定器直接接到一个只会一次性生成的模型上，会暴露三个结构性缺口，它们不是调参能补的。

第一个缺口是**编译错误的语义丢失**。nvcc 或 Triton 编译器吐出的报错是给人类看的：模板展开几百行、错误位置指向实例化点而非真实错误点、CuTe 的静态断言只给一句“static assertion failed”。一次性生成把这段文本原样塞回上下文，模型看到的是一团噪声。缺口在于：没有人把编译器输出解析成结构化字段——错误类别（类型不匹配 / 越界 / 对齐 / 资源超限）、真实源文件行号、涉及的模板参数。没有这个结构，修复就是盲改。

第二个缺口是**执行结果的回灌粒度**。第 3 卷的评测接口能告诉你“不通过”，但“不通过”对修复没有信息量。真正有用的是：哪个输出元素错了、错在哪个维度、误差是系统性偏移还是随机噪声、是否只在某个形状边界上错。粒度决定了修复的搜索空间大小。粒度到“通过/不通过”，搜索空间是整个 kernel；粒度到“第 17 行、行维 tile 上界少算 1”，搜索空间是几行。

第三个缺口是**轮次的经济学**。一次性生成没有预算概念。多轮修复必须回答：每任务最多几轮、每轮多少 token、什么时候停。停早了，一个只差一行的 kernel 被丢弃；停晚了，agent 在一个本质上写错的方案上反复打转，烧掉预算还污染上下文。第 4 卷的 oracle 能判定对错，但判定不了“再给一轮是否值得”。这个决策属于脚手架。

三个缺口指向同一个结论：判定器与生成器之间需要一层运行时。它不是 prompt 模板的集合，而是一个有状态机、有预算、有记忆的循环。

三 · 本卷的赌注：闭环的增益来自反馈结构，不来自模型规模

本卷押的是一个可以被证伪的判断：**在固定模型与固定 token 预算下，把“一次性生成”升级为“编译—执行—修复”闭环，带来的通过率增益主要来自反馈的结构化程度，而非轮数本身。** 换句话说，给同样的模型更多的轮数但喂噪声反馈，增益会迅速饱和；把反馈从自由文本改成带行号与错误类别的结构体，同样的轮数能多救回一批 kernel。

这个赌注有可操作的推论。若它成立，那么脚手架的工程重心应该放在反馈管道的设计上：编译器输出的解析器、执行结果的差分归因、失败模式的结构化归档。若它不成立——即增益主要来自轮数——那么重心应该放在预算调度上。两种设计的资源分配完全不同，这就是为什么必须先把这个判断摆出来。

代价也必须摆出来。结构化反馈不是免费的：解析编译器输出需要为每种编译器（nvcc、Triton 的 MLIR 报错、PTX 的 ptxas 报错）写适配层，这是一次性的工程成本，且随工具链版本漂移。执行结果的差分归因需要在评测侧多跑一次参考实现并做逐元素比对，这引入额外的时延与显存——参考实现本身可能就是一个大 kernel，在动态形状下要额外占一份 activation。上下文管理上，把历史尝试压缩成失败模式记忆，意味着每轮都要做一次摘要，摘要本身消耗 token，且摘要写坏了会把错误结论固化进后续轮次。这些都是闭环相对一次性生成多付的钱。

$$\text{net gain} = \underbrace{P_{\text{pass}}(F_{\text{struct}}, n) - P_{\text{pass}}(F_{\text{raw}}, n)}_{\text{结构增益}} - \underbrace{c_{\text{parse}} + c_{\text{diff}} + c_{\text{summ}}}_{\text{闭环开销}}$$

公式里 $$F_{\text{struct}}$$ 是结构化反馈，$$F_{\text{raw}}$$ 是原始文本反馈，$$n$$ 是轮数，$$P_{\text{pass}}$$ 是通过率。三项开销分别对应解析、差分与摘要。工程判断在于：结构增益随 $$n$$ 增长而收敛，开销随 $$n$$ 线性增长，因此存在一个最优轮数，超过它净增益转负。这正是本卷要给出的终止条件的理论依据，而不是拍一个“最多 5 轮”。

四 · 运行时架构的四个决策面

把闭环拆开，本卷要处理的是四个互相牵制的决策面。它们不是并列的模块，而是彼此约束的设计选择。

**决策一：单 agent 还是 planner-executor 分工。** 单 agent 的上下文里同时装着算子规格、历史尝试、编译器报错和 profile 摘要，简单但容易在长上下文里丢掉规格约束。planner-executor 把“决定改哪里”和“写出代码”分开：planner 只看结构化反馈与失败模式记忆，产出一句修改意图（“把行维 tile 的上界从常量改为动态计算”），executor 拿着意图与相关代码片段生成补丁。分工的代价是两次模型调用的 token 翻倍，收益是 planner 的上下文短、决策更稳。判断标准是任务复杂度：单 tile 的 elementwise 融合适合单 agent，多层流水或需要重写数据布局的适合分工。

**决策二：反馈粒度到行号还是到错误类别。** 行号精确但脆弱——agent 一旦重排代码，行号就失效，且编译器给的行号常常指向模板实例化点。错误类别鲁棒但搜索空间大。工程上的折中是两级：先用错误类别缩小到“对齐问题”或“边界问题”，再在该类别内给行号与涉及的变量名。这个折中的实现代价是解析器要维护一张“错误类别 → 常见修复模式”的表，这张表就是失败模式记忆的雏形。

**决策三：每任务最大轮数与 token 预算。** 承接第三节的公式，轮数上限应由结构增益的收敛点决定，而不是固定值。可操作的做法是：连续两轮反馈的结构化字段完全一致（同一行号、同一错误类别），判定为“打转”，提前终止。这个终止条件的代价是可能误杀一个即将突破的尝试——比如 agent 连续两轮都在同一个类别里试不同修法，第三轮才成功。缓解办法是给“打转”判定留一次豁免。

**决策四：是否允许检索历史成功 kernel。** 允许检索，等于把过去的成功案例当作 few-shot 注入，能显著缩短新任务的首次尝试路径；代价是检索到的 kernel 可能形状不匹配，诱导 agent 套用错误的 tile 配置，且检索本身消耗上下文预算。禁止检索则每个任务从零开始，上下文干净但重复踩坑。折中是检索只返回“结构摘要”（tile 形状、使用的指令、同步方式），不返回完整代码，让 agent 自己重建。

四个决策面共享一个约束：上下文预算。历史尝试压缩、失败模式记忆、检索结果、当前代码、结构化反馈，全部挤在同一个窗口里。压缩策略决定了哪些信息在第三轮之后还活着。一个具体的机制是“失败模式记忆”以键值对存储：键是（错误类别，涉及变量），值是上次尝试的修法与结果。每轮开始时只注入与当前错误类别匹配的条目，而不是全量历史。这把上下文占用从随轮数线性增长压成随类别数增长。

五 · 一个具体例子：从 softmax 到可部署 kernel 的修复轨迹

回到开场的 CuTe softmax。任务规格：隐藏维 4096，行数动态，要求数值与参考在 fp32 容差内一致，且端到端时延不劣于现有 Triton 版本。第 3 卷的接口负责计时与判定，第 4 卷的 oracle 负责容差裁决。脚手架要做的是中间那段。

第一轮：agent 生成 CuTe 代码，tile 形状取 (128, 256)，把行维映射到 tile 的行、隐藏维映射到列。编译通过。执行结果：输出与参考在第 0 维系统性偏移。差分归因给出结构化反馈：错误类别为“归约轴错误”，涉及变量 `tile_m`，行号指向 `copy` 的布局定义处。注意这里的关键——如果反馈只有“不通过”，第二轮无从下手；有了“归约轴错误 + tile_m”，搜索空间被压到布局定义的那几行。

第二轮：agent 依据反馈把 `tile_m` 与 `tile_n` 对调，但隐藏维 4096 不能被 256 整除的边界情形没处理，动态行数下最后一块 tile 越界。编译仍通过，执行在特定行数下报非法访存。反馈类别变为“边界越界”，行号指向 `predicate` 缺失处。这一轮的代价是评测侧多跑了一次参考比对，时延增加，但换来了精确的归因。

第三轮：agent 补上 predicate，通过。三轮的总 token 消耗与两轮相同量级，但如果没有第二轮的边界归因，第三轮会在错误的方向上继续改布局。这条轨迹说明：增益来自第二轮反馈把“边界”这个类别单独拎出来，而不是来自多给了一轮。

这里有一个容易被忽略的代价：动态行数意味着参考实现也要按动态形状跑，差分归因的显存占用随行数增长。若行数上限很大，参考比对本身可能成为评测侧的瓶颈。工程上的处理是把差分归因采样化——只比对前若干行与最后若干行，中间行按块抽样。这引入漏检风险：一个只在中间某行触发的边界错误可能被放过。抽样率与漏检率的权衡，是本卷在正确性代价一侧必须给出的口径。

六 · 与第 3、4 卷的接口，以及本卷不碰的东西

本卷的输入被严格限定为第 3 卷的评测接口与第 4 卷的 oracle 契约。这意味着脚手架的终止条件不能自造一套判定标准——它只能消费评测接口给出的通过/不通过与结构化差分，以及 oracle 给出的容差裁决。反过来，脚手架的输出也必须能被这两者直接消费：生成的 kernel 要符合接口的提交格式，修复过程中的中间尝试不应污染评测侧的基准状态。这个接口约束带来一个具体的工程后果：评测接口若只返回布尔值，脚手架的结构化反馈就得自己在评测侧之外重建，这会让差分归因的时延记在脚手架账上而非评测账上。接口设计决定了成本归属。

本卷不碰的东西同样明确。它不写训练配方——多轮 RL 与奖励塑形是另一卷的主题，这里只把“轮数与预算”当作运行时参数，不讨论如何用强化学习去学这个参数。它不写产品评测——端到端收益的度量属于落地那一卷，这里只到“kernel 通过契约且不劣于基线”为止。它不堆硬件参数——SM 数量、带宽这些量只在解释某个反馈类别的成因时出现，不作为设计变量。它也不重复 oracle 的形式审计细节，只在需要说明“为什么某个错误类别必须由 oracle 裁决而非脚手架猜测”时一句话指路。

真正落在本卷肩上的，是一个有状态的循环：解析编译器输出成结构体、把执行差分归因到行与变量、按失败模式记忆压缩历史、按结构增益的收敛点决定何时停。这四件事拼起来，就是“一次性生成”到“编译—执行—修复”闭环的那一步。修复轮次带来的第一波真实增益，就发生在这一步里——不是模型变强了，是它终于看得懂自己错在哪。
