一 · checker 漏检率：把「正确」拆成可测的统计量

生产端到端落地时，checker 不是布尔函数，而是一个有漏检率与误报率的分类器。把候选 kernel 输出记为 y，参考实现输出记为 y*，checker 判定为「通过」记作 P。真正需要审计的是两个条件概率：漏检率 P(P | y ≠ y*)，即错误输出被判通过的比例；误报率 P(¬P | y = y*)，即正确输出被判失败的比例。前者决定有多少错误 kernel 会流入集成与灰度，后者决定有多少正确 kernel 被无谓地打回重写、浪费编译与 token 预算。

工程上最常见的漏检来源是容差口径过宽。checker 用 allclose(atol, rtol) 逐元素比对，而参考实现本身在 fp32 下就有累加顺序差异；当 atol 被调到覆盖参考实现自身噪声时，一个把归约维度写错但数值量级相近的 kernel 同样能通过。审计做法是把 checker 当作被测对象：构造一批「已知错误」的变异体，统计它们被判通过的比例，得到漏检率的经验估计。这个估计必须按算子族分层——归约类、卷积类、attention 类的错误模式不同，单一全局漏检率会掩盖 attention 掩码写错这类高危漏检。

$$\hat{L} = \frac{1}{M}\sum_{i=1}^{M}\mathbf{1}\big[\text{checker}(K_i)=\text{pass}\ \big|\ K_i \in \text{Mutants}\big]$$

代价在采样成本上：变异体数量 M 越大，漏检率置信区间越窄，但每个变异体都要跑一次参考实现与一次候选 kernel，显存占用按 batch 线性增长，编译时间按变异体数量线性叠加。一个具体例子：某团队对 layernorm 的 checker 做审计，构造了 40 个变异体，其中 6 个是「减均值时漏掉一个元素」，全部被判通过——因为该错误只改变输出第 3 位有效数字，落在 rtol=1e-2 内。这 6 个变异体直接暴露了容差口径与业务精度要求脱节。

二 · 变异测试：用「故意写错」反推 oracle 的判别力

变异测试的核心不是覆盖率，而是判别力：对每个变异算子（把 += 改成 =、把边界条件 < 改成 <=、把 shared memory 的同步去掉、把 tile 大小改一位），checker 必须判失败。若某个变异体存活，说明 checker 对该类错误不敏感，需要补测试用例或收紧容差。变异算子要按 kernel 的语义结构设计，而不是随机翻转比特——随机比特翻转大多产生 NaN 或量级爆炸，checker 轻易捕获，对判别力没有信息量。

伪代码思路：对候选 kernel 的源码做 AST 级替换，生成变异体集合，逐个编译并在同一组输入上运行，记录 checker 判定。关键在于输入选择——必须包含能触发该变异语义的输入。例如「去掉同步」的变异体只在存在跨 warp 数据依赖的输入形状下才产生错误，若输入 batch 恰好让每个 warp 独立完成，变异体存活但并非 checker 失职。因此变异测试必须与输入生成联动，否则存活率被高估。

代价是编译时间：每个变异体都要走一次 nvcc 编译，一个中等规模 kernel 单次编译在秒级，几十个变异体就是分钟级；若变异体还要跑 NCU profile 定位差异，时延进一步放大。工程判断是变异测试只在 kernel 定稿前跑一轮全量，日常回归只跑存活过的变异体子集。

三 · fuzz：用输入分布逼出 oracle 的盲区

变异测试检验 checker 对「代码错误」的敏感度，fuzz 检验 checker 对「输入分布」的敏感度。GPU kernel 的错误高度依赖形状：非 2 的幂的 tile、尾块、空 tensor、单元素维度、stride 非连续、dtype 混合，都是漏检高发区。fuzz 的输入生成器要覆盖这些维度，而不是随机均匀采样数值——数值随机对结构性错误几乎没有区分力。

一个可操作的生成策略是按「形状空间」做组合覆盖：M、N、K 各取边界值（1、tile 大小减一、tile 大小、tile 大小加一、非对齐大值），stride 取连续与非连续两档，dtype 取 fp32/fp16/bf16 三档，再叠加空 tensor 与极值输入。组合数按乘法增长，必须做 pairwise 裁剪，否则显存与编译时间都撑不住。每个 fuzz 用例要同时跑参考实现与候选 kernel，参考实现本身在非连续 stride 下可能触发 PyTorch 的慢路径，时延远高于候选 kernel，导致 fuzz 吞吐被参考实现拖住。

$$\text{Cov}_{\text{shape}} = \frac{|\{s \in S_{\text{test}} : \text{checker exercised}\}|}{|S_{\text{boundary}}|}$$

具体例子：某 reduction kernel 在 N=1024 时通过全部测试，但 N=1025（尾块一个元素）时漏加最后一个元素，checker 因 rtol 宽松判通过。fuzz 生成器若只取 2 的幂形状，这个错误永远不会暴露。代价是显存：极值输入（如 1e38 量级）在 fp16 下溢出为 inf，参考实现与候选 kernel 的 inf 传播路径不同，需要单独口径处理，否则误报率飙升。

四 · 形式验证与合约验证：把「正确」从采样提升为证明

采样型 oracle 的漏检率永远非零，形式验证的价值在于对特定性质给出无遗漏的证明。对 GPU kernel 可行的形式化路径有三类：一是对索引映射做 SMT 求解，证明每个输出元素恰好被一个线程写一次、且读到的输入索引在界内；二是对定点/整数运算做等价性检查，证明候选 kernel 与参考实现在位级一致；三是对浮点运算做误差界推导，给出 |y - y*| ≤ ε 的可证上界，把容差从「试出来的」变成「推出来的」。

合约验证是轻量版：在 kernel 入口与出口插入断言，声明前置条件（形状、stride、dtype、对齐）与后置条件（输出范围、单调性、守恒量如 softmax 行和为 1）。这些断言在 debug 构建下开启，在 release 构建下编译掉，零运行时开销。合约的价值在于把「隐式假设」显式化：一个 kernel 假定输入已按 128 字节对齐，若集成层传入非对齐指针，合约在入口即失败，而不是在输出端产生难以归因的数值偏差。

代价是编译时间与工程投入：SMT 求解对含循环的索引映射需要展开或加不变式，展开深度受限于求解器状态空间，一个复杂 kernel 的证明脚本编写成本以人日计；浮点误差界推导需要逐算子传播舍入误差，链式归约的界会随 log N 增长，界过松则证明无意义。工程判断是形式验证只覆盖高危算子（attention 掩码、softmax 归一化、量化反量化），其余靠变异测试与 fuzz 兜底。

五 · 怎么证明「正确」：分层证据链与业务口径对齐

生产端到端落地时，「正确」不是单一结论，而是一条分层证据链：位级等价（整数/定点）、误差界内（浮点，有推导上界）、采样通过（fuzz 覆盖边界形状）、变异体全杀（判别力足够）、合约断言全过（前置条件成立）。每一层给出不同的置信度与不同的代价，集成决策要声明自己站在哪一层上。只声明「微基准通过」而不声明容差来源与形状覆盖，等于把漏检风险转嫁给灰度阶段。

证据链必须与业务精度口径对齐。业务侧能接受的误差往往不是逐元素 rtol，而是端到端指标（分类准确率、生成质量、排序一致性）。checker 的容差若按逐元素设定，可能与业务口径脱节：一个逐元素误差在容差内的 kernel，在端到端链路中经过多层复合后可能放大到业务不可接受。审计动作是把 checker 的判定与端到端 A/B 的结果做交叉表，统计「checker 通过但端到端指标下降」的比例，这个比例就是 oracle 与业务口径的错位量。

具体例子对应故事中的首个 kernel 上线：微基准加速 1.8x，checker 全部通过，但端到端仅 4% 收益。审计发现 checker 只验证了单算子数值，没有验证该算子在真实框架图里的输入分布——集成层传入的是非连续 stride 的中间张量，候选 kernel 走了慢路径，微基准的加速在生产形状下不成立。这不是数值错误，而是 oracle 的覆盖盲区：checker 没有把「真实调用形状」纳入测试集。修正动作是把集成层的实际形状采样进 fuzz 输入池，并在 checker 里加一条合约断言：输入 stride 必须连续，否则拒绝该候选。

代价核算要落到具体资源上：全量变异测试加 fuzz 加形式验证的审计流水线，单轮编译时间可达小时级，显存峰值由最大 fuzz 形状决定，token 成本来自 agent 根据审计失败反复重写 kernel 的轮次。工程判断是把审计分成两级——准入门槛跑变异体子集与真实形状 fuzz，上线前跑全量证据链；两级之间用灰度比例与回滚阈值衔接，而不是用「checker 通过」一句话放行。

Oracle 审计的边界：漏检率、变异测试与合约验证的系统代价

checker 的漏检率不是抽象指标，而是把“正确”折算成可接受风险的唯一杠杆。工程上应把 oracle 视为带假阴性的二值分类器：设真实错误集合为 E、checker 判错集合为 F，则漏检率漏检 = |E∩¬F|/|E|，误报率误报 = |F∩¬E|/|¬E|。漏检的代价是错误 kernel 进入灰度、污染下游指标；误报的代价是正确 kernel 被回滚、浪费一轮编译与 A/B 预算。二者不可同时压低，必须按业务侧精度容差设定一个显式的接受阈值——例如把漏检率压到 1e-3 量级，就意味着 oracle 必须覆盖绝大多数边界形状与数值区间，而覆盖度提升直接抬高单次验证的编译时间与 token 消耗。一个具体失效条件是：checker 只在固定 shape（如 4096×4096）上比对，而生产流量里 17×33 这类奇数尾块触发越界写，漏检率在该 shape 分布上接近 1，微基准却全绿。因此 oracle 审计的第一条工程判断是：checker 的输入分布必须与真实流量分布对齐，否则漏检率数字没有意义。

变异测试是把漏检率从“不可知”变成“可测”的手段：对参考实现注入受控变异（改 stride、错位偏移、去掉边界判断、把 fp32 累加换成 fp16、把 __syncthreads 挪位），构造一批已知必错的 kernel，跑 checker 看它能抓出多少。抓出比例即 checker 的敏感度，未抓出的变异体就是漏检的具体来源。代价在于变异体数量与验证时延成正比：每个变异体都要编译、加载、执行、比对，若一批 40 个变异体、单个编译 20 秒量级，一轮变异测试就吃掉十几分钟编译时间，且占用 GPU 做数值比对。更隐蔽的代价是变异体本身可能被编译器优化掉（例如死代码消除把错误偏移变成无害），导致“变异体未报错”被误读为 checker 漏检，实际是变异没生效——所以变异测试必须配一条自检：变异体在无 checker 的裸跑下应产生可观测的数值差异，否则该变异体作废。fuzz 则补上变异测试覆盖不到的随机路径：对 shape、dtype、stride、对齐、NaN/Inf 输入做随机采样，重点打边界（0 长度、1 元素、非 2 幂、跨页对齐）。fuzz 的系统代价是 GPU 时间与显存碎片：大量小 shape 反复分配释放，容易把显存池打散，后续大 kernel 的 A/B 基线被拖慢，因此 fuzz 应与生产 A/B 分卡或分时段执行。

形式验证与合约验证解决的是“采样采不到”的那类错误。合约验证的思路是在 kernel 入口与出口插入断言（前置条件：指针对齐、shape 一致、stride 合法；后置条件：输出在容差内、无越界写、无数据竞争），把断言编译进 debug 版本，用符号执行或 SMT 求解检查所有路径是否满足。对 CUDA 而言，线程索引与共享内存的约束可写成线性算术，SMT 能在小 shape 上给出“存在越界”的反例；但状态空间随 block/grid 维度指数增长，形式验证只能覆盖小规模配置，大规模配置仍需采样。代价是编译时间与工具链复杂度：带断言的 debug 版本编译更慢、寄存器压力更大，且符号执行对含原子操作与 warp shuffle 的 kernel 支持有限，往往退化为“合约可写、验证不可解”。因此工程判断是：合约验证用于锁定接口契约与明显越界，形式验证只用于最关键的少数 kernel（如 attention 的 softmax 归一化、归约的边界处理），其余靠变异测试与 fuzz 兜底。三者叠加后的总验证预算是可量化的：设单 kernel 编译 C、变异体数 M、fuzz 样本数 S、形式验证配置数 V，则单轮审计时延 ≈ C·(1+M) + S·t_exec + V·t_smt，其中 t_exec 是单样本执行加比对时间，t_smt 是单配置求解时间。这个预算必须与灰度窗口对齐——审计没跑完就放量，等于把漏检风险直接转嫁给线上。

回到“怎么证明正确”的工程落点：正确性证明不是一次性证书，而是随流量分布漂移的持续合约。生产端应把 checker 的漏检率、变异测试敏感度、fuzz 覆盖率作为发布门禁的三个数，任一不达标即阻断灰度；同时把 oracle 的输入分布版本与业务流量分布版本绑定，流量分布变了就重跑审计。一个具体例子是首个 kernel 上线时微基准 1.8x、端到端仅 4% 的教训：当时 checker 只验证了固定 shape 的数值正确性，没验证集成路径上的 dtype 转换与 layout 假设，结果 kernel 在真实负载的尾块上产生静默错误，收益归因被错误数据污染。修复方式不是加更多采样，而是把合约断言前置到框架集成层，让 layout 与 dtype 的不匹配在进入 kernel 前就报错——这比事后提高漏检率便宜得多。审计的最终产物是一张带失效条件的表：每个 checker 覆盖哪些 shape/dtype/边界、漏检率上界、对应编译与 GPU 时延预算、以及触发重审的流量分布变化阈值。
