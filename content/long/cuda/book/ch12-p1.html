一 · 开场：一次被回滚的融合算子发布

把镜头对准一个具体发布：团队为某个推理服务写了融合算子，把 LayerNorm、残差相加与一次矩阵乘前的量化打包进同一个 kernel，目标是省掉两次全局内存往返。单测通过，正确性对拍通过，微基准在目标卡上跑出明显优于基线的时延。上线三天后回滚。原因不在 kernel 本身，而在三处接口：第一，微基准用的是固定 shape 的合成张量，生产流量里存在一批极短序列，此时网格规模不足以填满 SM，融合带来的收益被启动开销吃掉；第二，评测流水线里的 oracle 只覆盖了 fp32 参考路径，量化分支的舍入行为在边界值上与参考实现不一致，而这条分支恰好被线上某类输入触发；第三，发布门禁只校验了单算子时延，没有校验端到端收益，融合算子把上游的写回延迟藏进了流水线，端到端反而变差。

这个例子把本卷要回答的问题压成一句话：当一支团队已经拥有前十一卷给出的方法、数据、成本与可靠性结论之后，如何把它们固化成一套可执行、可审计、可迭代的组织流程，使 kernel agent 的产出能稳定进入生产。注意这里的动词是“固化”而不是“掌握”。方法存在于某个工程师的 notebook 里、评测脚本存在于某个仓库的分支上、oracle 的变更记录存在于聊天记录中，这些都不构成体系。体系的标准是：换一个人、换一个季度、换一批算子，同样的流程仍然产出可比较的结果，并且失败可以被归因。

本卷的产出物是团队路线图，包含四件互相咬合的东西：能力矩阵、角色分工、季度里程碑与验收标准、治理规则。它们不是文档装饰，而是把前十一卷的口径变成组织约束的载体。能力矩阵回答“我们会在哪些维度上被考核”，角色分工回答“谁对哪个维度的数字负责”，里程碑回答“什么时间点必须达到什么验收线”，治理规则回答“什么变更必须经过谁的评审”。技术债清单与下一轮基准升级计划则是这套体系的输出，而不是输入。

二 · 上一卷留下的缺口：口径有了，但没有被组织持有

前十一卷各自给出了可用的结论：问题定义与口径确定了什么算一次有效评测；基准演化史说明了 KernelBench 系基准的版本漂移如何影响可比性；可信评测流水线给出了执行反馈与 NCU/SASS profile 的采集规范；Oracle 与形式审计给出了正确性判定的边界；Agent 脚手架、硬件反馈、多轮 RL 与奖励、数据与 SFT 基座分别覆盖了生成侧的训练与推理闭环；生产端到端落地、可靠性与 BI、成本与容量覆盖了上线侧。这些结论单独看都成立，合在一起却暴露三个缺口。

第一个缺口是口径的所有权。口径写在论文或内部文档里，但没有一个角色对“口径是否被遵守”负责。评测工程师可以按自己的理解放宽 tolerance，RL 工程师可以按自己的奖励函数改写正确性门槛，两边都不算违规，因为没有人被授权定义唯一口径。结果是跨季度的数字不可比，能力矩阵上的“提升”无法区分是模型变强还是口径变松。

第二个缺口是基准版本与 oracle 的耦合没有治理。基准升级会改变题目分布，oracle 变更会改变判定边界，两者任意一个变动都会让历史数字失效。前十一卷给出了变更的方法，但没有给出变更的审批路径：谁提议、谁评审、冻结期多长、旧数字如何标注。缺少这条路径时，团队会在“追新基准”和“保住历史可比性”之间反复摇摆，每次摇摆都消耗一批算力和人力。

第三个缺口是成本与可靠性结论没有落到排期上。成本与容量部分给出了单位产出的算力与 token 开销，可靠性与 BI 部分给出了故障归因的方法，但路线图按什么维度排期——按能力维度还是按业务场景——决定了这些结论是否被真正使用。按能力排期容易做出漂亮的矩阵，却说不清哪个业务场景受益；按业务场景排期容易交付，却难以复用评测资产。这个取舍本身就是本卷的关键决策之一。

$$\text{可比性} = f(\text{基准版本冻结},\ \text{oracle 变更评审},\ \text{口径单一所有权})$$

代价是明确的：冻结基准版本意味着放弃一部分新题目的信号，评审 oracle 变更意味着每次正确性边界调整都要付出评审时延，单一所有权意味着评测工程师的排期被口径维护占用。这三项代价换来的是一件事——能力矩阵上的每个数字都能被追溯到一次具体的评测运行与一个具体的 oracle 版本。没有这个追溯链，路线图就只是愿望清单。

三 · 本卷的赌注：把评测资产当作一等公民

本卷押的注是：在 kernel agent 的生产体系里，评测资产（基准版本、oracle、profile 采集规范、奖励函数）的边际价值高于模型侧的边际价值。这个判断有具体的机制支撑。生成侧的能力提升遵循递减曲线：脚手架与 RL 的改进在早期带来大幅通过率提升，之后每一点提升都需要成倍的采样与训练开销。而评测侧的改进是一次性的：一个被修正的 oracle 边界会同时改变所有历史运行的重判结果，一个被冻结的基准版本会让跨季度比较成为可能，一个被规范化的 NCU 采集流程会让每次失败都能落到具体的 stall 原因上。

用伪代码表达这个赌注在工程上的形态：

  • 评测运行先读基准版本号与 oracle 版本号，两者任一缺失则拒绝运行，而不是回退到默认值；
  • 运行结果写入带版本标签的记录，正确性判定与性能数字绑定同一份记录；
  • 任何 oracle 变更必须附带一组“边界样例”的重判报告，报告不通过则变更不生效；
  • 能力矩阵的每个单元格只接受带版本标签的记录作为输入，手工填写的数字不被接受。

代价落在时延与人力上。拒绝运行会让一次本可以出数的实验直接失败，团队需要为此准备回退路径；边界样例重判会拉长 oracle 变更的周期；版本标签让历史数据迁移变得繁琐。这些代价在早期看起来是负担，在跨季度比较成为刚需时会变成唯一的救命绳。具体例子：某季度团队想证明 RL 投入带来了通过率提升，如果两批运行使用了不同的 oracle 版本，提升就无法归因；有了版本标签，团队可以直接筛出同版本运行做对比，把“模型变强”与“判定变松”分开。

这个赌注也决定了本卷不做什么。本卷不重新推导基准的设计原则，不重新论证 RL 奖励的构造，不重新给出 profile 指标的物理含义——这些在前十一卷已经完成，本卷只在需要指路时用一句话带过。本卷的篇幅留给组织形态：能力矩阵的维度怎么切、角色边界怎么划、里程碑的验收标准怎么写、治理规则怎么在冲突时生效。

四 · 能力矩阵：七个维度与它们的验收口径

能力矩阵的七个维度是基准、评测、oracle、脚手架、RL、落地、运维。切分原则不是按技术栈，而是按责任边界：每个维度必须能指派一个唯一负责人，并且该负责人能对维度内的数字做出承诺。基准维度负责题目分布与版本冻结；评测维度负责运行采集与数字入库；oracle 维度负责正确性判定边界；脚手架维度负责生成侧的工具链与执行反馈回路；RL 维度负责奖励函数与训练投入配比；落地维度负责端到端收益与发布门禁；运维维度负责故障归因与容量。

维度核心产出验收口径主要代价
基准冻结版本与题目清单跨季度可比性可追溯放弃新题目信号的时延
评测带版本标签的运行记录拒绝无版本运行实验失败率上升
oracle边界样例重判报告变更评审通过率变更周期拉长
脚手架执行反馈回路失败可归因到 stall 原因profile 采集开销
RL奖励函数与配比同版本下的通过率对比采样算力与 token
落地端到端收益与门禁门禁拦截记录发布时延
运维故障归因与容量账本归因覆盖率值班人力

矩阵的读法不是打分，而是找缺口。一个维度如果连续两个季度没有验收记录，说明该维度的负责人没有被真正授权，或者验收口径不可执行。具体例子：脚手架维度的验收口径是“失败可归因到 stall 原因”，如果某季度的失败记录里大部分只写了“时延不达标”而没有 NCU 指标，那么这个维度就是空的，能力矩阵上的高分没有意义。矩阵的价值在于它把这种空转暴露出来，而不是掩盖它。

代价在这里体现为矩阵维护本身的开销：七个维度各有一份验收口径，每季度需要一次对齐会，每次对齐会需要拉齐版本标签与重判报告。这个开销相对于一次错误发布造成的回滚是小的，但相对于一个只做单算子优化的团队是大的——这也是为什么矩阵只在具备多角色协作的团队里成立。

五 · 角色分工与里程碑：谁承诺数字，谁承担回滚

角色分工的核心不是职责描述，而是承诺关系。kernel 工程师承诺单算子正确性与微基准时延，并对融合后的接口行为负责；评测工程师承诺运行记录的完整性与版本标签的正确性，并有权拒绝不合规的运行；RL 工程师承诺奖励函数与 oracle 口径一致，并对训练投入配比给出季度建议；平台运维承诺故障归因覆盖率与容量账本，并对发布门禁的执行负责。四个角色之间是承诺链而不是汇报链：评测工程师拒绝运行，RL 工程师的季度对比就缺数据，这个缺口会被记录为技术债，而不是被私下绕过。

里程碑按季度设置，每个里程碑必须带验收标准，验收标准必须是可判定的布尔条件，而不是程度副词。具体例子：某季度里程碑是“落地维度建立端到端收益门禁”，验收标准写成“连续若干次发布中，门禁对端到端收益为负的候选算子执行拦截，且拦截记录可追溯到具体的 profile 数据”。这样的标准可以被审计，也可以被失败。相比之下，“提升端到端收益”不是验收标准，因为它无法判定是否达成。

$$\text{里程碑达成} = \bigwedge_{d \in \text{维度}} \text{验收}_d(\text{版本标签一致})$$

代价是排期刚性。带布尔验收标准的里程碑不允许“基本完成”，这会让季度末的评审变得尖锐，也会让资源不足的维度直接暴露为未达成。缓解手段是把技术债清单作为正式产出：未达成的维度进入债清单，下一季度排期时优先偿还，而不是被悄悄降级为“持续改进”。技术债清单的条目必须写明缺口、影响的能力矩阵单元格、偿还所需的角色与预估开销，否则不予收录。

这里有一个具体的工程判断：RL 与 SFT 的投入配比不应由 RL 工程师单方面决定，而应由能力矩阵的缺口驱动。如果评测维度的版本标签覆盖率不足，那么增加 RL 采样只会产出更多不可比的数字，配比应当先向评测侧倾斜。这个判断把“投入配比”从技术偏好变成了组织约束，也是本卷把角色分工与能力矩阵绑在一起的原因。

六 · 治理规则：冻结、评审与门禁如何生效

治理规则有三条主线：基准版本冻结、oracle 变更评审、生产发布门禁。三条规则的共同机制是默认拒绝：没有版本标签的运行默认无效，没有重判报告的 oracle 变更默认不生效，没有端到端收益记录的发布默认被拦截。默认拒绝把举证责任放在变更提出方，而不是放在评审方，这在多角色团队里是唯一能长期执行的形态。

基准版本冻结的具体机制是冻结窗口加迁移路径：窗口内不接受新题目进入基准，窗口结束时统一升级并标注旧数字的失效范围。代价是新题目信号被延迟一个窗口，收益是跨季度比较成立。oracle 变更评审的具体机制是边界样例集：任何变更必须附带该集合上的重判结果，评审方只看重判报告与变更理由，不看实现细节。代价是变更周期从小时级拉长到天级，收益是正确性判定不会在无人察觉的情况下漂移。生产发布门禁的具体机制是端到端收益记录与 profile 证据绑定：候选算子必须同时给出微基准与端到端两组数字，任一为负则拦截。代价是发布时延增加，收益是开场那个回滚案例不会重演。

三条规则之间有一处冲突需要显式处理：基准升级会带来新题目，新题目可能暴露 oracle 的边界缺陷，而 oracle 变更又需要重判报告，重判报告依赖冻结的基准版本。处理方式是把升级与评审排成串行队列，而不是并行推进：先完成 oracle 评审，再执行基准升级，升级后的首批运行同时产出新题目的基线数字与旧题目的重判数字。这个串行化会让一个季度的前半段看起来进展缓慢，但它避免了“新基准配旧 oracle”这种既不可比也不正确的中间状态。

治理规则的最终检验标准不是文档是否齐全，而是冲突发生时规则是否被引用。具体例子：当 RL 工程师希望放宽奖励函数里的正确性门槛以提升通过率时，评测工程师应当引用 oracle 评审规则拒绝，而不是靠人际协商。规则被引用一次，它的存在就被确认一次；规则从未被引用，它就只是装饰。本卷把这一点作为路线图的收尾判断：一套路线图的成熟度，取决于它在压力下被引用而不是被绕过的次数。
