一 · 漏检率：把“正确”拆成可计数的错误面

checker 的漏检率不是一个标量，而是一组按错误类型分层的条件概率。工程上先把“正确”定义为输出张量在给定容差下的逐元素等价，再把它拆成若干可独立注入的错误面：索引越界、边界条件缺失、累加顺序改变导致的舍入漂移、dtype 提升链错误、非连续 stride 处理缺失、mask 语义错位、原子操作竞争。对每个错误面构造一个“变异体”，让变异体在真实输入分布上运行，观察 checker 是否判负。漏检率即 P(checker 判正 | 变异体存在)，按错误面分别统计，而不是取平均。

关键在于 checker 自身的判定逻辑必须与 kernel 的语义解耦。常见做法是双 oracle：一个基于 PyTorch eager 的参考实现（高精度、慢），一个基于解析解的闭式结果（仅适用于线性算子）。两者不一致时进入人工裁决队列，而不是让其中一个静默胜出。代价是每次评测的参考侧时延翻倍，对 KernelBench L1 这类小算子尚可接受，对 L3 的融合算子则会把单次评测从秒级推到十秒级，直接压缩多轮 RL 的采样吞吐。

具体例子：一个 softmax kernel 的变异体把减最大值那一步去掉，在输入幅值较小时数值仍然稳定，eager 参考实现因为内部做了 max 减法而给出不同结果，逐元素容差 1e-5 下两者都“通过”。这个变异体只有在输入含大幅值（如 1e4 量级）时才暴露。这说明漏检率必须绑定输入分布来报告：漏检率 = f(checker, 变异体集合, 输入分布)，三者缺一不可，单独报一个数字没有工程意义。

$$\text{miss rate}_{e} = \frac{\#\{\text{mutants of type } e \text{ judged pass}\}}{\#\{\text{mutants of type } e\}}$$

二 · 变异测试：用算子语义生成有杀伤力的变异体

随机比特翻转式的变异对 GPU kernel 几乎没有杀伤力，因为大多数位翻转会让 kernel 崩溃或输出明显错误，被 checker 轻易抓住。有效变异必须沿着算子语义走：把 __syncthreads() 删掉、把 tile 边界从 <= 改成 <、把 shared memory 的 bank 冲突规避写法退化为朴素写法、把 fp32 累加改成 fp16 累加、把 predicated load 的 mask 取反。这类变异体在多数输入上仍然产出“看起来合理”的结果，正是漏检的高发区。

变异体的生成应当由 kernel 的 AST 或 Triton 的 IR 驱动，而不是文本替换。对 CUDA C++ 走 Clang AST 匹配，对 Triton 走其 IR 的 pattern rewrite，对 CuTe 走 layout 与 tiler 的参数扰动。每条变异记录三个属性：语义类别、预期被哪类 checker 抓住、预期性能影响方向。性能影响方向很重要——一个只改累加精度的变异体不应改变 occupancy，若 profile 显示寄存器数突变，说明变异注入点选错了，需要回退重做。

代价在编译时间。一个中等规模 kernel 的变异体集合若取 30 条，每条都要走一遍 nvcc 编译加一次评测，编译时间从单次的数十秒膨胀到十几分钟。工程折衷是把变异测试放在基准版本升级前的离线审计里跑，而不是每次 agent 提交都跑；在线只跑一个约 5 条的高杀伤力子集，用编译缓存（ccache 或 Triton 的 kernel cache）把重复编译压掉。

具体例子：一个 reduction kernel 的变异体把 warp shuffle 的 mask 从 0xffffffff 改成 0x0000ffff，在 block size 恰为 32 的整数倍时结果正确，在尾块上错。checker 若只跑 2 的幂形状的输入，这条变异体永远漏检。这直接指向下一节的 fuzz 策略。

三 · Fuzz：形状空间与数值空间的联合采样

GPU kernel 的输入空间至少是三维的：形状（各维长度、是否连续、stride 布局）、数值分布（幅值范围、是否含 NaN/Inf、是否含重复索引）、以及执行配置（block/grid、是否走 tail path）。fuzz 的职责是在这三轴上采样出能触发边界路径的输入，而不是均匀随机。均匀随机会把绝大多数样本落在“中间形状”，而边界路径恰恰在极端形状上。

采样策略上，形状轴用边界偏置：每个维度以高概率取 1、取小于 tile 尺寸的值、取 tile 尺寸的整数倍、取整数倍加一、取质数长度。数值轴用分层采样：正常幅值、接近 dtype 上限的幅值、含 ±0 与次正规数、含 NaN/Inf 的隔离样本（这类样本单独判定，不与正常样本混在一个通过率里）。执行配置轴则强制覆盖 tail path：当形状不能被 tile 整除时，必须至少有一条样本落在尾块分支。

fuzz 的成本是评测时延的线性膨胀。一次评测若跑 50 条样本，单条样本的 kernel 启动加同步开销在微秒级，但参考实现的 eager 路径在毫秒级，总时延由参考侧主导。对 L3 融合算子，50 条样本的参考侧可能到数百毫秒，多轮 RL 里每个 rollout 都跑一遍会显著拖慢采样。折衷是分层：训练期用 8 条覆盖边界的固定样本集，审计期用 200 条随机加边界的样本集，两套样本集共享同一份种子记录以便复现。

具体例子：一个 batched matmul kernel 在 M=1 的退化形状上走了一条未优化的 fallback 分支，该分支没有做边界检查，越界读到了相邻 tensor 的内存。均匀随机采样几乎不会命中 M=1，边界偏置采样则必中。这类错误在数值上表现为偶发的微小偏差，逐元素容差下可能通过，只有配合越界检测（如 compute-sanitizer 的 memcheck）才能稳定判负——这说明 fuzz 必须与工具级 oracle 联动，不能只靠数值比对。

四 · 形式验证：把 tile 级不变量写成可判定的断言

对 GPU kernel 做端到端形式验证在当前工具链下不现实，但做 tile 级、循环级的不变量验证是可行的。思路是把 kernel 的每个 tile 计算抽象成一个带前置/后置条件的契约：前置条件约束输入 tile 的索引范围与 dtype，后置条件约束输出 tile 与参考语义的等价关系。然后用有界模型检验或 SMT 求解在小的 tile 尺寸（如 4×4）上穷举或符号执行，验证不变量在展开后的循环里成立。

可判定的部分集中在索引算术与 mask 逻辑：越界证明、对齐证明、mask 覆盖完整性。这三类恰好是漏检率最高的错误面，因此形式验证的投入产出比在索引层最高。累加顺序与浮点舍入不在可判定范围内，只能退回数值 oracle 加误差界分析。

代价是建模工作量与求解时间。把一个 128×128 tile 的 kernel 降到 4×4 做符号执行，循环展开后状态空间仍然随 tile 面积增长，SMT 求解可能在分钟级到小时级。工程上只对基准里高频出现的算子模板（elementwise、reduction、matmul 变体）建立契约库，新算子复用模板契约加参数实例化，而不是每个 kernel 从零建模。编译时间在这里转化为求解时间，属于离线审计成本。

具体例子：一个 transpose kernel 的 shared memory tile 是 32×33（加一列避免 bank 冲突），索引算术里写 smem[ty][tx] 与 smem[tx][ty] 的转置关系。形式化后置条件要求输出 out[i][j] == in[j][i]，在 4×4 实例上符号执行可以证明该等式对所有 tile 内索引成立，同时暴露当 tx 或 ty 达到 32 时的越界写。这类证明不依赖输入数值，因此对数值 fuzz 覆盖不到的路径是补集。

五 · 合约验证：运行时断言与影子执行

形式验证覆盖静态可判定的部分，合约验证覆盖动态的、依赖运行时配置的部分。做法是在 kernel 里插入轻量断言（索引范围、对齐、mask 一致性），在调试构建下开启，在性能构建下编译掉。断言的代价是寄存器压力与分支，一个每线程执行一次的边界断言可能让 occupancy 掉一档，因此只在审计构建里开。

影子执行是另一条路：把 kernel 的写操作同时记录到一份影子缓冲区，评测结束后用参考实现重放并比对影子缓冲区的最终状态，而不是只比对输出张量。这能抓住“输出正确但中间写越界”的情况——输出张量恰好正确，但越界写污染了相邻内存，在下一次调用时才爆发。影子缓冲区的显存开销与输出同量级，对 L3 大算子意味着数百 MB 的额外占用，评测机需要预留。

合约验证的判定逻辑要区分“违反合约”与“数值不等”。违反合约是硬失败，直接判负并记录违反点；数值不等则进入容差判定。两者混在一个通过率里会让 agent 学到“把断言关掉就能过”的错误策略，因此审计流水线必须把合约违反单独计数，并在基准变更记录里留痕。

具体例子：一个 layernorm kernel 在 N 不能被 warp 宽度整除时，用 predicated 写回，但 predicate 的条件写成了 tid < N 而非 tid < N && tid < blockDim.x，在 blockDim 大于 N 时越界写。输出张量本身正确（越界部分被后续覆盖或落在 padding 区），影子缓冲区则记录到越界地址，合约验证判负。这类错误在纯数值 oracle 下漏检率接近 1。

六 · 审计闭环：把漏检率变成基准版本升级的门槛

上述四类手段（变异测试、fuzz、形式验证、合约验证）不是并列选项，而是一条按成本递增的漏斗。在线评测跑数值 oracle 加 5 条高杀伤力变异体加 8 条边界样本；离线审计跑全量变异体、200 条 fuzz 样本、模板契约的形式验证与影子执行。漏斗的每一层都要记录该层抓住的变异体类别与数量，形成一张“哪层抓哪类错”的覆盖矩阵。

这张矩阵直接决定基准版本能否升级。规则是：若某个错误面在在线层与离线层的合计漏检率超过阈值，则该错误面必须补进在线层，或者该算子从基准中降级。这正是私有 held-out 集迁移的工程依据——公开集上的分数虚高被污染检测揭穿后，重建基准时不能只换数据，还要把 checker 的漏检率作为准入条件写进变更记录。一个算子进入私有 held-out 的前提是它在审计漏斗下漏检率可接受，否则它的历史分数不可比。

代价落在评测容量上。审计漏斗的离线部分对每个算子模板要跑变异体集合与形式验证，单模板的审计时间在小时级，基准里数十个算子模板意味着审计周期以天计。这要求审计与在线评测使用不同的机器池，且审计结果按算子模板缓存，模板不变则复用上次审计结论，只在模板参数或 checker 逻辑变更时失效。

工程判断落在具体机制上：把 checker 的漏检率当作基准的一等公民指标，与分数并列记录在版本谱系里；每次基准升级必须附带一张覆盖矩阵的增量，说明新增算子在各错误面上的漏检率与对应的审计层。没有这张矩阵的升级不予合入，因为无法证明新基准上的分数与旧基准可比——而这正是私有 held-out 迁移后最容易被忽略、也最容易让 agent 钻空子的地方。

私有 held-out 上的 Oracle 审计：漏检率、变异与合约边界

基准迁移到私有 held-out 之后，分数虚高被污染检测揭穿，随之而来的问题不再是“题目够不够难”，而是“判分器凭什么说它对”。KernelBench 系基准的 checker 通常是“参考实现 + 数值容差 + 形状/步长枚举”的组合，其失效模式有三类：容差过松导致错误 kernel 通过（漏检），容差过紧导致正确但重排归约顺序的 kernel 被误杀（误报），以及枚举覆盖不到的非连续 stride、广播、空张量边界。漏检率必须被显式度量，而不是假设为零。做法是对每个任务构造一组“已知错误”的变异体，统计 checker 判其为通过的比例，得到该任务的漏检率估计；再对参考实现本身做差分测试，确认 oracle 不是自洽的循环论证。

变异测试的机制是：对参考 kernel 施加语义保持或语义破坏的变换，前者应通过、后者应被拒。语义保持变异包括归约顺序置换、分块大小改变、fp32 累加改为成对求和；语义破坏变异包括去掉边界 mask、把 stride 写死为连续、把 softmax 的分母漏掉一项、把 atomicAdd 换成非原子写。判分矩阵如下：

变异类型期望若判错的代价
归约重排（语义保持）通过误报：扼杀合法优化，浪费 RL 采样 token
去 mask / 写死 stride拒绝漏检：错误 kernel 进入 held-out 分数，污染可比性
非原子并发写拒绝（概率性）漏检：需多次重复运行才能暴露

漏检率的统计代价直接体现在评测预算上：每个任务若需 m 个变异体、每个变异体重复 r 次以捕获非确定性错误，则单任务审计运行数为 m·r，相对单次正确性检查的开销倍数为 m·r；在 GPU 上这意味着评测 wall-clock 与显存占用成倍上升，且并发写类错误只有重复运行才以概率 p 暴露，漏检率下界约为 (1-p)^r。因此审计不能全量跑在每次 RL 迭代里，只能作为基准版本升级时的门禁。

$$\text{漏检率} \approx \frac{1}{N}\sum_{i=1}^{N}\frac{\#\{\text{被接受的破坏性变异体}_i\}}{m_i},\qquad P(\text{漏检并发写}) \approx (1-p)^{r}$$

形式验证与合约验证是另一条边界：对 Triton/CUDA 的完整功能正确性做 SMT 或精化证明，在含浮点、共享内存同步与 warp 级原语的 kernel 上不可扩展，编译/求解时间会从秒级膨胀到不可接受，因此工程上只对“索引算术与边界条件”这类整数片段写前置/后置合约（如 0 ≤ idx < N、block 覆盖完整、无越界写），把浮点语义留给数值 oracle。合约的代价是维护成本：kernel 模板一变，合约即失效，需要与基准变更记录同步版本化。一个具体例子是转置 kernel 的合约只声明读写索引映射与 tile 覆盖，而不声明浮点结果，从而在 tile 大小从 32 改到 64 时合约仍可复用，但去 mask 变异体仍会被索引合约拒绝——这正是漏检率与合约强度之间的可操作折中点。
