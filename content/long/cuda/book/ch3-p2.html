一 · 基准任务的三种口径：算子级、子图层、端到端

本卷承接第 2 卷的基准任务清单，但“任务”本身在评测时必须被固定到一种口径上，否则同一个 kernel 在三套口径下会得到三个互不相容的“快”。算子级口径把被测对象限定为单个 kernel launch：输入张量形状、dtype、layout、stride 全部写进任务描述，计时区间只覆盖从 launch 前到 launch 后的同步点，任何 host 侧的数据准备、随机初始化、结果校验都排除在计时窗口之外。子图层口径把若干相邻算子打包成一个可融合的单元（例如 matmul + bias + activation），允许 agent 输出融合 kernel 或 Triton 程序，此时“快”的基线不再是逐个算子的 cuBLAS 调用之和，而是框架 eager 模式下同一子图的实测时延。端到端口径则把整个模型前向（或一个训练 step）作为被测单元，agent 的产出必须嵌入真实调用链，收益要扣除布局转换、额外 kernel launch 与 Python 调度开销。

三种口径的差别不是精度问题，而是归因问题。算子级口径下，一个把 bias 融合进 matmul 的 kernel 会因为“任务描述里没有 bias”被判为越界；子图层口径下同样的融合是合法且被鼓励的；端到端口径下，融合带来的收益可能被上游一次不必要的 contiguous 拷贝吃掉。工程上必须为每个任务在元数据里显式标注 scope 字段，并规定基线只能在同一 scope 内取。一个具体机制是：任务包携带 baseline_ref，指向一个已冻结的基线实现（框架 eager 版本或参考 CUDA 实现），评测时先跑基线再跑候选，两者共享同一份输入生成器与同一份随机种子，从而把“输入分布差异”从时延差异里剔除。

$$\text{speedup} = \frac{T_{\text{baseline}}(s, d, h, \text{scope})}{T_{\text{candidate}}(s, d, h, \text{scope})}$$

公式里四个自变量必须同时锁定：形状 s、dtype d、硬件 h、口径 scope。少锁一个，speedup 就不可复核。代价在于：子图层与端到端口径需要维护真实调用链，容器镜像体积与启动时延上升，单次评测的 wall clock 从秒级涨到十秒级以上；算子级口径便宜但容易奖励“只优化被计时的那一段”的局部最优。例子：一个 agent 在算子级口径下把 LayerNorm 写成单 pass Welford，speedup 看起来可观；换到端到端口径，因为它在输出上多做了一次 dtype 转换，整网时延反而回退，这正是口径不一致导致的误判。

二 · 基线不是“跑一遍 cuBLAS”：兜底策略要写进口径

是否允许 cuBLAS/cuDNN 兜底，是本卷最容易被忽略却影响排名最大的决策。允许兜底时，agent 可以输出“检测到形状属于某类，直接调 cuBLAS”的分支，这类实现几乎不可能被手写 kernel 打败，评测就退化成“谁会调库”。禁止兜底时，任务变成纯手写实现，但基线的选取又必须公平：基线不能是“随手写的朴素 kernel”，否则 speedup 虚高。可复核的做法是把基线定义为“该硬件上框架 eager 路径的实际时延”，并在任务元数据里记录基线所用的库版本与算法选择（例如 cuBLAS 的 heuristic 模式），因为库版本变化会改变基线本身。

一个具体机制是双基线制：baseline_lib 记录库兜底时延，baseline_ref 记录参考手写实现时延，评测报告同时给出两个 speedup，排名用哪一个由任务族预先声明。这样既不让“调库”垄断排名，也不让朴素实现成为虚高分母。代价是评测工作量翻倍：每个任务要跑两条基线，且库基线在容器内必须固定版本，镜像锁定带来的存储与构建时间成本是实打实的。另一个代价是正确性侧：库兜底实现通常有更宽松的数值容差（例如 TF32 路径），若候选实现走 FP32 精确路径，正确性 oracle 的容差必须按 dtype 分别设定，否则会出现“更准的实现被判错”的荒谬结果。

例子：一个 matmul 任务，agent 输出 Triton 实现并在 allow_lib=False 下与参考手写 kernel 比较，speedup 稳定在可判别区间；同一实现在 allow_lib=True 下与 cuBLAS 比较则明显落后。若任务族未声明用哪条基线，两次评测的排名会互相矛盾——这正是“结果反复抖动导致误判”的一个非噪声来源：不是测量抖，是分母换了。

三 · 硬件与 dtype 的锁定：时钟、隔离与可复现的机器状态

“快”必须绑定到一台状态可复现的机器上。GPU 隔离要求每个评测容器独占指定 device，禁止同卡并发；时钟锁定要求关闭自动 boost 或把 SM 时钟、内存时钟固定在评测窗口内可接受的稳定档位，并在报告中记录锁定前后的时钟读数。不做这两件事，同一份 kernel 在两次评测间的时延差异可以轻易超过本卷要判别的 3% 阈值，而这个差异与 kernel 质量无关。容器化执行沙箱还要固定驱动版本、CUDA runtime 版本、编译器版本与编译 flag，因为 -O3 与 --use_fast_math 的开关会直接改变生成的 SASS。

dtype 口径同样要写死：输入 dtype、累加 dtype、输出 dtype 三者分开记录。混合精度任务里，TF32 与 FP32 的累加路径不同，roofline 上的可达算力也不同，若不区分，speedup 会把“降精度换速度”误记为“kernel 更优”。一个具体机制是任务元数据里的 dtype_triple 字段与 tol_policy 字段绑定：容差按 dtype 三元组查表，而不是全局一个常数。代价是显存：高精度累加与更大的中间缓冲会抬高峰值显存，某些形状下候选实现因显存不足而失败，这类失败必须归入“运行错”而非“性能不达标”，否则失败分类会污染性能统计。

例子：同一 LayerNorm kernel 在 FP16 输入、FP32 累加下通过容差，在 FP16 累加下时延更低但数值偏差超出该 dtype 的容差表，评测应判数值错。若容差不分 dtype，这个实现会被记为“更快且正确”，排名被系统性带偏。硬件侧的例子：锁定时钟后，一个 occupancy 偏低的 kernel 与高 occupancy kernel 的时延差才稳定可复现；不锁定时，boost 行为会让两者在多次重复间交错领先。

四 · 计时口径：CUDA event、wall clock 与统计量的选择

计时用 CUDA event 还是 wall clock，取决于口径。算子级与子图层口径用 CUDA event：在 stream 上记录起始与结束 event，同步后取差值，能把 host 侧调度与 Python 开销排除，代价是 event 本身有微小开销，对极短 kernel（微秒级）会引入可观测偏差，此时需要把多次 launch 打包进同一对 event 之间再除以次数。端到端口径必须用 wall clock，因为真实收益包含 host 调度与框架开销，用 event 会把这部分收益人为放大。两种计时器不能混用于同一张排名表。

统计量口径要写死 warmup 次数、重复次数与报告的分位数。中位数抗离群但掩盖尾部；P90/P99 反映真实服务体验但对短 benchmark 不稳定。可复核的做法是：固定 warmup 轮数（覆盖 JIT 编译、cache 预热、时钟爬升），固定重复次数，报告 median 与 P90 两个数，排名判定用 median，显著性检验用重复样本的分布。方差控制的手段包括：固定输入生成种子、禁用同卡并发、锁定时钟、对每次重复重新同步。显著性检验用配对比较：同一轮内基线与候选交替执行，消除机器状态漂移。

$$\text{reject } H_0 \iff \frac{\bar{d}}{s_d/\sqrt{n}} > t_{1-\alpha,\,n-1},\quad d_i = T^{\text{base}}_i - T^{\text{cand}}_i$$

代价是评测时延：warmup 加重复加配对，单任务耗时是“跑一次”的数倍到数十倍；容器启动与 JIT 编译时间也被计入总预算。例子：一个 Triton 任务首次 launch 触发编译，若 warmup 不足，编译时间混入 median，候选实现被误判为慢；把 warmup 固定为覆盖首次编译后，同一实现的 median 才落回可判别区间。另一个例子：短 kernel 用 event 计时且只跑少数几次，event 开销占比过高，配对检验的 n 不足导致无法拒绝原假设，正确实现被记为“无显著提升”。

五 · 把“快”翻译成可复核数字：报告结构与失败分类

可复核的数字不是单个 speedup，而是一条可重放的记录：任务 id、scope、dtype 三元组、硬件与时钟状态、基线引用、warmup/重复次数、计时器类型、median 与 P90、配对检验结果、失败分类。报告结构必须让第三方在不重跑的情况下判断这个数字是否可信——例如看到 timer=event 却 scope=e2e，就应直接判为口径违规。失败分类（编译错/运行错/超时/数值错/性能不达标）要与性能统计分离：编译错与运行错不计入时延分布，超时单独计数，数值错在通过正确性 oracle 之前不进入排名，性能不达标只是“未超过阈值”而非“错误”。混在一起会让“快”的分母被失败样本污染。

一个具体机制是阈值判定用相对差而非绝对差：只有当配对检验拒绝原假设且 median 相对差超过预设阈值（本卷要判别的是 3% 量级）时，才记为“性能达标”。这避免把噪声当提升。代价是 token 与算力：每个任务要产出完整报告字段，agent 侧的多轮迭代需要读取这些字段作为反馈，报告越长，喂回模型的上下文成本越高；因此报告要分层，机器可读的紧凑字段与人类可读的解释分开，喂回 agent 的只是紧凑字段。

例子：同一 agent 的两版实现，A 版在未锁时钟的机器上测得更快，B 版在锁定后测得略慢但方差更小；若报告缺 clock_state，两版无法放在同一张表上比较，排名只能靠“谁先跑”。把该字段补齐后，配对检验给出 A 版提升不显著、B 版显著，排名才稳定——这正是故事中“评测抖动导致误判”的工程解法：不是把噪声压到零，而是把口径写死到可复核。

六 · 口径的版本化与跨任务可比性

口径本身会演化：新增 dtype、新增子图层任务、基线库升级、时钟锁定策略调整。若不版本化，历史排名与新排名会被静默拼接，产生不可解释的跳变。可复核的做法是给整套口径打版本号，报告里记录 protocol_version，跨版本比较只在显式声明“口径等价”的子集内进行。一个具体机制是口径变更需要附带重跑基线：任何影响分母的变更（库版本、时钟策略、warmup 次数）都触发基线重测，否则旧基线数字与新候选数字不可同表。

代价是重跑成本：每次口径变更都要重跑全部任务的基线，容器构建与 GPU 机时是真实开销；因此口径变更应批量进行而非逐任务打补丁。另一个代价是可比性收缩：版本化后，跨版本排名不再连续，agent 的多轮 RL 若跨版本取奖励，奖励信号会出现台阶，需要在训练侧按版本分段归一。例子：把 warmup 从固定轮数改为“直到时延收敛”，短 kernel 的 median 下降而长 kernel 不变，若不做版本标注，同一 agent 在新旧口径下的分数差会被误读为能力变化。

落到工程判断上：本卷的“快”是一个四元组约束下的条件量，评测流水线的职责不是追求更小的噪声，而是让每个数字都带着自己的口径出生。当报告里 scope、timer、dtype_triple、clock_state、baseline_ref、protocol_version 六个字段齐备且互相自洽时，3% 的判别阈值才有意义；缺任何一个，speedup 就退回成一个不可复核的形容词。

口径的边界：哪些「快」能被这套流水线复核

这套流水线能复核的「快」，严格限定在同一容器镜像、同一 GPU 型号与时钟状态、同一 dtype 与同一输入形状分布下，同一实现相对同一基线的比值。它不能复核跨硬件代际的绝对性能，也不能复核依赖库版本漂移的收益：cuBLAS 兜底一旦被允许，被测 kernel 的耗时里就混入了厂商库的版本行为，基线本身随镜像更新而漂移，3% 的判别阈值立刻失效。因此口径必须写成三元组（基线实现，镜像摘要，时钟锁定策略），任何一项变更都要求重跑基线而非复用旧数字。失效条件还包括：输入形状落在被测 kernel 的 tail 分支上时，中位数掩盖了长尾；多卡口径下通信与计算重叠使单卡 event 计时不可加。

方差控制的代价是采样预算。要把噪声压到可判别 3% 差异，重复次数 n 与相对标准误的关系近似为

$$\text{RSE}\approx \frac{\sigma}{\mu\sqrt{n}},\quad n \gtrsim \left(\frac{\sigma}{0.03\,\mu}\right)^2$$

当 σ/μ 在百分之几量级时，n 需达到数百次量级，每次重复都含 warmup、同步与 event 记录开销，单任务评测时延随之上升；若改用 wall clock 以省去同步，则进程调度与 Python 侧开销进入样本，σ 变大，反而推高 n。工程判断是：对短 kernel 用 CUDA event 加固定 warmup 与分位数口径，对长 kernel 放宽 n 并接受更宽的判别阈值，把「性能不达标」与「数值错」分开计入失败分类，避免把统计不可判别误记为性能回归。

口径项可复核失效条件
CUDA event 中位数同镜像同卡相对基线tail 形状、异步未同步
cuBLAS 兜底仅同版本库内比较库升级、基线漂移
