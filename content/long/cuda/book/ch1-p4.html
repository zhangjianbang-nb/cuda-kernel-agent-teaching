一 · 漏检率：checker 的第一性指标

一个 checker 的价值不在它放过了多少正确 kernel，而在它放过了多少错误 kernel。把「正确」定义成 checker 返回 pass，就必须先量化这个定义本身的错误率。工程上把 checker 的失效拆成两类：假阴性（把正确 kernel 判错，误杀）与假阳性（把错误 kernel 判对，漏检）。前者损失的是 agent 的探索效率与训练信号质量，后者直接污染基准分数，是评测可信度的头号敌人。因此审计的第一步是给 checker 建立漏检率指标，而不是先谈覆盖率。

设待测 kernel 集合为 K，其中真实错误子集为 E（由独立 oracle 标注），checker 判错集合为 F。漏检率定义为 |E \ F| / |E|，误杀率为 |F \ E| / |K \ E|。这两个量必须分开报告：一个只会说 pass 的 checker 漏检率接近 1，误杀率为 0，看起来「从不冤枉好人」，实则毫无判别力。工程判断上，漏检率是硬约束（通常要求低于某个可接受阈值，且对数值敏感任务更严），误杀率是软约束，因为它只影响 agent 的搜索成本，可以通过多轮重试摊薄。

漏检率的代价直接体现在 token 与算力上。一个漏检率高的 checker 会让错误 kernel 进入性能排名，agent 在错误方向上继续优化，多轮 RL 的奖励被污染，训练 token 花在拟合噪声上。具体例子：elementwise 加法 kernel 中，若 checker 只比对 float32 输出的前若干元素，一个把尾部元素写错、但头部完全正确的 kernel 会被判 pass，而它在 reduction 融合场景下会静默产生错误结果。这类漏检在基准里表现为「分数虚高」，在端到端部署里表现为线上数值漂移。

二 · 变异测试：给 checker 造敌人

漏检率无法靠「多跑几个正确 kernel」测出来，必须主动构造错误 kernel。变异测试（mutation testing）就是系统化地生成「几乎正确但确实错误」的实现，用它们攻击 checker。对每个参考实现，施加一组变异算子：改边界索引（off-by-one）、换累加顺序、把 float32 累加改成 float16 中间累加、删掉同步屏障、把 shared memory 的 bank 冲突规避写错、把 mask 条件从 `<` 改成 `<=`、在 reduction 中漏掉最后一个 warp 的归约。每个变异体都是一个已知错误的 kernel，checker 若判其 pass，即记一次漏检。

变异得分（mutation score）定义为被 checker 杀死的变异体比例：

$$\text{MS} = \frac{|\{m \in M : \text{checker}(m) = \text{fail}\}|}{|M|}$$

其中 M 是变异体集合。MS 低于 1 意味着存在 checker 看不见的错误类别，这些类别就是审计报告里必须列出的「盲区清单」。变异测试的成本是编译时间与显存：每个变异体都要编译、加载、跑一遍，一个 attention kernel 的变异体集合若有几十个，编译与执行开销会显著拖慢评测流水线。工程上通常对变异体做分层采样：数值类变异全测，结构类变异按算子族抽样。

具体例子：对 softmax kernel 施加「减去最大值」这一步的变异——去掉 max 减法，直接在 exp 上累加。对于小数值输入，这个变异体与正确实现在 float32 下输出几乎一致，checker 若只用小数值测试用例就会漏检；只有喂入大幅值输入（导致 exp 溢出）才能杀死它。这说明变异测试必须与输入分布设计联动，否则 MS 虚高。

三 · Fuzz：把输入空间当作攻击面

变异测试攻击的是实现，fuzz 攻击的是输入。checker 的判别力依赖测试用例的覆盖，而 kernel 的错误往往只在特定输入形态下暴露：极端形状（1 元素、质数长度、非 2 的幂）、极端数值（次正规数、inf、nan、接近 dtype 上限）、非连续 stride、空 tensor、广播维度为 1。fuzz 的任务是生成这些形态并验证 checker 在它们上面仍能区分对错。

一个可操作的 fuzz 策略是「差分 fuzz」：同一输入分别喂给参考实现与待测 kernel，比较输出；同时把输入喂给一个已知错误的变异体，确认 checker 在同样输入下能判错。后者是关键——只做前者的 fuzz 只能发现待测 kernel 的错，不能发现 checker 的盲。伪代码思路：

  • 从形状分布中采样 (M, N, K, dtype, layout)，优先覆盖边界值；
  • 对每个样本，跑参考实现得 R，跑待测得 T，跑变异体得 M；
  • 若 checker(R, T) = pass 且 T 与 R 在独立高精度 oracle 下不等，记漏检；
  • 若 checker(R, M) = pass，记该变异类别在该输入形态下不可检。

fuzz 的代价是时延与显存：高精度 oracle（如 float64 参考或 CPU 端任意精度累加）本身可能比 GPU kernel 慢一个数量级，且大形状样本会挤占显存。工程上把 fuzz 分成离线审计与在线抽检两档：离线审计跑全量形态，产出盲区清单；在线抽检只跑高风险形态（nan/inf、非连续 stride），控制单次评测的时延预算。

具体例子：一个 reduction kernel 在 N 为 2 的幂时正确，在 N 为质数时因尾部处理错误而漏加元素。若 fuzz 的形状分布只采样 2 的幂，checker 永远不会遇到这个错误，漏检率被低估。把质数长度加入分布后，该错误立即暴露，且暴露的前提是 checker 的容差口径能区分「少加一个元素」带来的相对误差——这又把容差分级问题拉了回来。

四 · 形式验证与合约验证：把「正确」变成可证明命题

测试只能证伪不能证真，形式验证试图补上这一半。对 GPU kernel 做端到端形式验证的代价极高（状态空间含线程索引、共享内存、同步语义），工程上可行的路径是合约验证（contract verification）：为 kernel 写前置条件与后置条件，用符号执行或 SMT 求解在受限规模上证明后置条件成立。合约的形式是 Hoare 三元组 {P} kernel {Q}，P 约束输入（形状、dtype、stride 对齐、数值范围），Q 约束输出（逐元素等价于参考表达式、归约顺序无关的误差界）。

合约验证的现实边界在于规模：符号执行对线程数、循环次数敏感，通常只能在极小形状（如单 block、固定 tile）上完成证明，无法覆盖生产形状。因此它的定位不是替代测试，而是为关键算子族（matmul 的 tile 边界、attention 的 mask 逻辑）提供「局部正确性证书」，再把证书与大规模差分测试组合成证据链。代价是编译时间与工程人力：写合约、调求解器、维护证明脚本的开销远高于写测试，只有高价值、高复用、错误代价大的 kernel 值得投入。

具体例子：一个 fused elementwise-mul-add kernel 的合约可以写成「对任意 i，输出 out[i] 等于 a[i]*b[i]+c[i] 在指定舍入模式下的结果」。符号执行在固定向量宽度下可证明该等式，但它证明不了跨 block 的调度正确性——后者仍需差分测试。合约验证的产出是可审计的证明脚本，而不是一个 pass 标记；审计报告里应写明「已证明的范围」与「未覆盖的范围」，避免把局部证书误读为全局正确。

五 · 容差口径：正确性判据本身的审计对象

checker 的判别力不只取决于比对逻辑，还取决于容差。容差定得太松，漏检率上升；定得太紧，误杀率上升，agent 被大量假阴性信号拖垮。容差必须按 dtype 与累加顺序分级：float32 逐元素运算可用较小的相对误差界，float16 中间累加的 reduction 需要放宽，matmul 的 K 维累加顺序变化会带来与 K 成正比的误差增长。一个可操作的误差模型是

$$\varepsilon_{\text{rel}} \approx \kappa \cdot \sqrt{K} \cdot u$$

其中 u 是 dtype 的单位舍入误差，K 是累加长度，κ 是与归约树形状相关的常数。这个式子给出的是容差的下界估计，checker 的实际阈值应在此基础上留出余量，但余量本身要审计：余量过大等于主动引入漏检。

容差审计的方法是「双向注入」：向上注入一个刚好超出容差的正确实现（因合法归约顺序差异），确认 checker 不误杀；向下注入一个刚好落在容差内的错误实现（如漏加少量元素但相对误差仍小），确认 checker 能判错。两者之间的间隙就是 checker 的判别盲区宽度。代价是评测时延：双向注入需要构造大量边界样本，且每个样本都要跑高精度 oracle。工程判断上，这个间隙宽度应作为基准元数据的一部分公开，让下游使用者知道分数的置信边界。

具体例子：attention kernel 在 float16 下做 softmax，累加顺序变化导致的相对误差可能落在 1e-2 量级；若 checker 把容差定在 1e-3，大量合法实现被误杀，agent 的多轮 RL 信号变成「无论怎么改都不过」；若定在 1e-1，一个漏掉部分 mask 元素的错误实现可能蒙混过关。容差分级不是拍脑袋，而是由 dtype、累加长度、归约树形状共同决定的工程参数。

六 · 证据链：怎么证明「正确」

「正确」不是一个布尔值，而是一条证据链：变异测试给出盲区清单，fuzz 给出输入形态覆盖，形式/合约验证给出局部证明，容差审计给出判别间隙宽度，差分测试给出大规模经验证据。审计报告的结论应写成「在如下输入分布、如下容差口径、如下已证明范围内，checker 的漏检率不超过 X，误杀率不超过 Y，未覆盖的错误类别为 Z」，而不是一句「checker 已验证」。

这条证据链的工程代价要显式计入评测流水线：变异体编译时间、fuzz 的高精度 oracle 时延、合约证明的求解时间、容差边界样本的显存占用。一个可信的基准不是「跑得快」，而是「知道自己在哪些地方不可信」。具体到本卷的任务分类法，elementwise 与 reduction 的 checker 可以用差分测试加容差审计达到较高置信度，attention 与 fused 算子则必须叠加变异测试与局部合约证明，否则 mask 逻辑与边界处理的漏检无法被经验测试覆盖。

最终落到一个工程判断：checker 的审计成本应与任务的错误代价匹配。进入 agent 可解域的任务，若其错误在生产端表现为静默数值漂移而非崩溃，则漏检率的优先级高于误杀率，审计预算应压在变异测试与容差下界上；若错误表现为越界访问或崩溃，则差分测试的形状覆盖优先。把这条判断写进验收口径，比任何单点工具都更能决定基准分数的可信度。

Oracle 审计的失效面：漏检率、变异覆盖与验证成本

checker 本身是一个被测对象，它的漏检率决定了「正确」这个标签的可信度。工程上把 oracle 审计拆成三层：变异测试度量 checker 对错误实现的敏感度，fuzz 在输入域上探测容差边界，形式/合约验证在关键不变量上给出无采样证明。三层不是替代关系，而是覆盖不同的失效模式——变异测试抓「checker 太松」，fuzz 抓「输入分布外推失效」，形式验证抓「采样永远碰不到的反例」。一个可操作的漏检率估计是：给定一组人工注入的变异体 $M$（如漏掉同步、错用 `__syncthreads()` 位置、累加顺序翻转、边界条件 off-by-one、dtype 截断），checker 判为通过的比例

$$\text{FNR} = \frac{|\{m \in M : \text{checker}(m) = \text{pass}\}|}{|M|}$$

这个比值必须按任务分类法分桶统计，因为 elementwise 的变异体几乎全被逐元素比对抓住，而 reduction/attention 的变异体大量落在容差与累加顺序的灰色地带。代价是直接的：每增加一个变异体就要多编译、多跑一次基线比对，变异集规模随 kernel 变体数线性增长，在 CI 里表现为编译时间与 GPU 占用的成倍上升；若把变异测试放进 agent 的多轮 RL 回路，它还会挤占 rollout 预算，使每轮可用于探索的候选数下降。

容差口径是漏检率的主要杠杆，也是最容易自欺的地方。以相对误差与绝对误差混合判据为例，常见形式是

$$\text{pass} \iff |y - \hat{y}| \le \text{atol} + \text{rtol}\cdot|y|$$

对 fp16 累加、fp32 累加的 reduction，同一 rtol 下的实际严格程度差一个量级；若 checker 用固定 atol 而不按 dtype 与累加顺序分级，变异体「把 fp32 累加降为 fp16 累加」会稳定通过，这正是漏检率被低估的典型路径。反过来，把 rtol 收得过紧会让合法实现（不同 reduction 树形、不同 tile 顺序）被判错，false reject 会污染 agent 的奖励信号，使其学到「保守到不敢改」的策略。工程判断是：容差必须写成 (dtype, 累加顺序, 归约长度) 的函数，并在任务清单里显式登记，而不是留一个全局常数。

形式验证与合约验证的边界要提前说清。合约验证（如对 kernel 前置条件、共享内存越界、同步配对的断言）能在编译期或运行期以极低采样成本捕获结构性错误，代价是插桩带来的指令开销与寄存器压力，可能改变 occupancy 从而让性能基线失真——因此审计用的插桩版本与性能测量版本必须分离。真正需要 SMT/符号执行的无采样证明只对小块、无数据依赖的 kernel 可行，规模一大状态空间就爆炸，编译/求解时间不可控。fuzz 则相反：它便宜、可并行，但对「罕见但致命」的数值路径覆盖不足，且需要一套能生成合法输入形状与数值分布的生成器，生成器本身的偏差就是漏检率的隐藏来源。三者组合的工程口径是：变异测试定基线敏感度，fuzz 定输入域边界，合约验证守住不变量，形式验证只在不可解域边缘的关键 kernel 上做点状证明；任何一层缺失都要在验收粒度上降级声明，而不是默认「正确」。
