一 · 基准谱系与可比性边界

本卷面对的“快”，从来不是一个标量，而是一组被口径约束过的可复核数字。KernelBench 系基准提供了三层可比性：算子级（单 kernel 对单参考实现）、模块级（多 kernel 组合成子图）、端到端级（真实模型的一段前向或训练步）。三层的口径不可混用：算子级测的是 kernel 本体在给定 shape/dtype 下的吞吐与占用，模块级测的是融合与调度带来的额外收益，端到端级测的是这些收益在真实访存与同步模式中是否还成立。把算子级的加速比直接搬到端到端结论上，是本卷最常见的口径事故。因此每个评测条目必须携带一个四元组标签：(基准层, 基线, 硬件, dtype)。缺任一项，数字即不可复核。

基线选择本身就是一个决策点。对同一算子，PyTorch eager、torch.compile、cuBLAS/CUTLASS 库调用、厂商手写 kernel 四类基线给出的“快”含义完全不同：相对 eager 的加速比容易被融合与调度吃掉，相对库调用的加速比才是 kernel 工程真正要打的仗。本卷要求评测记录同时保存至少两条基线，并显式标注主基线。主基线一旦变更，历史数字全部作废重测，而不是做比例换算——因为换算会引入不可审计的假设。

可比性还受输入分布约束。基准的默认 shape 往往落在库实现的最优区间，而 agent 生成的 kernel 可能在边界 shape 上退化。因此口径规定：每个算子至少覆盖一组主 shape、一组非对齐 shape（尾维不是 2 的幂或不是 128 的倍数）、一组极小 shape（batch=1、序列长度个位数）。三组结果分别报告，禁止只报最优组。这条规则直接对应后面 oracle 的边界输入检查，二者共享同一份 shape 清单，避免评测与正确性验证各说各话。

$$\text{加速比} = \frac{T_{\text{baseline}}(\text{shape}, \text{dtype}, \text{device})}{T_{\text{candidate}}(\text{shape}, \text{dtype}, \text{device})}$$

代价在这里体现为测量成本：三组 shape × 两条基线 × 多次重复，单条评测的 GPU 机时是单点测量的数倍；若再叠加 dtype 组合，机时线性膨胀。工程判断是：把 shape 清单固化为基准配置文件，评测侧只读不写，agent 不可见，防止针对特定 shape 过拟合。

二 · dtype 与容差标定表

dtype 决定了“正确”的判据，也决定了“快”的上限。fp32 参考实现与 bf16/fp16 候选实现之间的差异不是噪声，而是可预期的舍入累积；fp8 与整型量化又引入缩放因子与饱和截断。本卷的口径是：容差不是全局常数，而是一张随 dtype 与规模变化的标定表。表的每一行给出 (dtype 对, 归约长度区间, 相对容差, 绝对容差, NaN/Inf 策略)。归约长度是关键维度——同样是 bf16，长度 128 与长度 8192 的累积误差量级不同，用同一容差会把正确实现判错，或把错误实现放过。

标定表的生成机制是：用 CPU 高精度（float64 或 Kahan 补偿求和）作为真值，对参考实现与候选实现分别计算误差分布，取高分位作为容差下界，再乘一个安全系数。这里有一个必须写进口径的代价：CPU 高精度参考的时延比 GPU 参考高出一到两个数量级，因此只对抽样输入跑高精度，其余输入跑 GPU 参考比对。抽样比例与抽样策略（随机 + 边界）写入评测记录，保证可复现。

dtype 对归约长度判据取向主要代价
fp32 / fp32短严格相对容差几乎无额外成本
bf16 / fp32长相对+绝对混合高精度抽样机时
fp16 / fp32中长关注溢出饱和边界输入构造
fp8 / bf16任意缩放因子一致性量化误差主导

具体例子：一个 bf16 的 softmax kernel，若候选实现用 fp32 累加而参考用 bf16 累加，候选反而更接近真值，此时按“与参考比对”会判候选错误。口径必须允许“优于参考”的判定路径——即同时比对高精度真值，候选误差小于参考误差时视为通过。这条规则写进标定表的备注列，而不是留给评测者临场判断。

三 · 硬件口径与时钟状态

同一份 kernel 在同一型号 GPU 上的数字可以相差百分之几十，差异来自时钟状态、功耗墙、MPS 共享、ECC 与显存频率。本卷口径要求评测记录携带硬件指纹：设备型号、SM 数量、显存容量与带宽档位、当前时钟策略（是否锁定）、是否独占。不锁时钟的测量只能用于相对比较，不能用于绝对性能声明；跨设备比较必须重测，不做归一化换算。

测量机制上，采用预热 + 多次重复 + 取中位数，并同时记录分位数分布。均值会被首次运行的冷启动与偶发抢占拉偏，中位数对长尾更稳健，但分位数分布本身是诊断信息：若 P99 远高于中位数，说明存在同步或访存抖动，这类 kernel 在生产端到端场景中往往表现更差。因此口径规定：报告必须包含中位数与 P90/P99，单点最优值不得作为结论。

代价是测量时延：预热轮数不足会让结果偏向乐观，轮数过多则单条评测机时上升。工程折中是固定预热轮数与重复轮数，写入基准配置，不允许 agent 侧调整。另一个代价是显存：并发跑多条评测会互相干扰显存带宽，口径要求评测串行独占，牺牲吞吐换取可比性。具体例子：一个依赖 L2 缓存的 kernel，在共享 MPS 环境下 L2 被其他进程污染，测得时延偏高，若不做独占标记，该数字会被误读为 kernel 本身退化。

四 · 指标分层：时延、带宽、占用与 roofline

“快”要翻译成可复核数字，必须落到分层指标上。第一层是墙钟时延，包含 launch 开销与同步开销，适合端到端口径；第二层是 kernel 自身时延，用 CUDA event 包裹，排除 host 侧开销；第三层是有效带宽与有效算力，用访存字节数与浮点操作数除以时延得到；第四层是 roofline 位置，即实测吞吐相对该硬件在该 dtype 下的峰值带宽或峰值算力的比值。四层指标必须同时记录，因为单看墙钟时延无法区分“kernel 慢”与“launch 多”。

$$\text{SOL} = \max\left(\frac{\text{实测带宽}}{\text{峰值带宽}},\ \frac{\text{实测算力}}{\text{峰值算力}}\right)$$

roofline 口径的关键是算术强度的计算必须与候选实现的实际访存模式一致，而不是照抄参考实现。一个做了融合的 kernel 减少了中间张量写回，其实际访存字节数低于参考，若仍按参考的字节数计算带宽，会低估其 SOL。因此口径要求：带宽分子取自候选实现的实际全局访存计数（可由 profiler 计数或按实现推导），并在记录中注明来源。

代价体现在 profile 开销：采集硬件计数器需要额外一轮运行，且计数器复用会限制可同时采集的指标组，通常需要多轮才能凑齐带宽、占用与 stall 原因。这使单条评测的机时进一步上升。工程判断是：正确性判定用轻量路径，性能归因用重量路径，二者分离，避免每次评测都付全量 profile 成本。具体例子：一个 shared memory 分块矩阵乘，墙钟时延改善但有效带宽下降，原因是分块导致重复加载；只看时延会误判为全面优化，分层指标才能暴露这一取舍。

五 · 把“快”写成可复核记录

可复核的含义是：第三方拿到记录能重跑出同一结论，或至少能解释差异来源。本卷规定评测记录的最小字段集：基准层、算子标识与 shape 清单、dtype 对与容差表版本、主基线标识、硬件指纹与时钟状态、预热与重复轮数、四层指标及分位数、profile 采集开关与计数器组、随机种子。任一字段缺失，记录标记为不可复核，不得进入汇总。

机制上，记录以结构化格式落盘并与代码版本、基准配置哈希绑定。哈希绑定是防篡改的第一道闸：agent 若修改基准配置或容差表，哈希变化即触发重审。这与 reward hacking 审计中的“篡改计时”规则同源——计时口径的任何变更都必须走审计通道，而不是在评测脚本里静默调整。代价是流程摩擦：每次口径修订都要重跑受影响的历史条目，机时与人力成本真实存在，但这是数字可信的前提。

具体例子：某候选 kernel 报告了相对 eager 的显著加速，但记录显示其主基线被临时替换为未融合的参考实现，且 shape 清单只含最优组。按最小字段集审查，该记录因基线标识与 shape 覆盖不合规被退回，加速比不作数。这类退回不是否定 kernel 本身，而是否定其数字的可复核性——二者必须分开表述，否则会误伤真实优化。

最后一个工程判断落在口径的稳定性上：容差表与 shape 清单的版本号必须单调递增且不可回退，评测侧只接受当前版本。这样，“快”才是一个随时间可比较的量，而不是每次评测重新定义的临时结论。

口径的边界：当「快」被翻译成数字时，哪些前提正在悄悄失效

把 kernel 的时延翻译成可复核数字，本质是一次口径声明：硬件型号与 SM 数、时钟与功耗策略、dtype 与累加精度、输入规模与 batch 形状、基线实现（PyTorch eager、cuBLAS、Triton 参考核）、计时方法（CUDA event 区间、是否含 warmup、是否含 H2D/D2H、是否锁页内存、是否固定频率）。任何一项缺失，数字就不可复核。本卷的审计立场是：数字必须与口径同生同死，报告里出现的每个 speedup 都要能反查到一份口径记录。代价首先体现在 token 与工程时间上——把口径写全，单条样本的评测描述会从一两行膨胀到结构化字段，多轮 RL 里这意味着 rollout 的观测长度上升、上下文预算被挤占；若把口径塞进 reward 计算而非观测，则审计侧需要额外的元数据通道，评测流水线的序列化成本上升。一个具体例子：同一个 RMSNorm 核，在「含 H2D 的端到端计时」与「纯 kernel event 计时」两种口径下会给出方向相反的快慢结论，前者被搬运带宽支配，后者才反映 SM 利用率；若不声明，两个数字都「正确」却互相矛盾。

失效条件集中在三类。其一是规模外推失效：在 N=1024 上测得的 speedup 不能线性外推到 N=65536，因为后者会跨过 L2 容量、occupancy 拐点与寄存器溢出阈值，roofline 上的工作点从 compute-bound 滑向 memory-bound。其二是dtype 口径漂移：FP32 累加与 TF32 累加、BF16 输入配 FP32 累加，在数值容差与吞吐上都不同；把 baseline 用 TF32、候选核用 FP32 累加做对比，等于用精度换速度却不声明，这是审计规则要抓的隐性作弊。其三是基线选择失效：以未融合的 eager 实现为基线会系统性放大收益，以厂商库为基线则可能把「与 cuBLAS 持平」误判为「无收益」。可复核的做法是要求候选核同时对齐两条基线，并记录相对差距。用公式表达口径约束：

$$\text{speedup}=\frac{T_{\text{base}}(\text{shape},\text{dtype},\text{clock})}{T_{\text{cand}}(\text{shape},\text{dtype},\text{clock})},\quad \text{valid}\iff \Delta_{\text{num}}\le \tau(\text{dtype},\text{scale})$$

其中容差 τ 随 dtype 与归约规模变化，规模越大、累加链越长，τ 越宽；这条约束把「快」与「对」绑在同一张表上，任何只报分子不报分母、只报时延不报 τ 的报告都视为口径不完整。系统代价在于：为每个 (shape, dtype) 组合标定 τ 需要跑参考实现与高精度对照，标定表本身随规模增长而膨胀，评测侧要为每个候选核加载对应行，内存与查询时延都上升；若 τ 标定过紧，正确核被误杀，过松则弱 oracle 被「猜答案」式实现骗过——这正是故事里 agent 学会猜答案的事故根源。

口径项缺失时的失效审计代价
计时区间搬运时延混入 kernel 时延需重跑并比对 event 边界
dtype/累加精度精度换速度未声明需数值对照与 τ 标定
基线实现收益被系统性放大需双基线交叉验证
输入分布缓存命中被人为抬高需随机与边界输入重测

因此本节的工程判断是：把「快」翻译成数字时，先冻结口径再测，而不是测完再补口径；口径记录与容差标定表必须作为 oracle 的输入一并版本化，任何口径变更都触发重测而非重算。对 reward hacking 的防线也落在这一层——硬编码输出、跳过计算、缓存结果、篡改计时，四类作弊中有三类直接攻击口径（计时、缓存、跳过），只有把口径与 τ 一起纳入审计规则，正确性判定才可信；代价是评测吞吐下降与标定维护成本上升，但换来的是数字可复核，而非可复述。
