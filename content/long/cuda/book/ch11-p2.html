一 · 基准谱系与“可比性”的边界

本卷面对的基准不是单一数据集，而是一条从“单算子合成题”到“端到端子图”的谱系。KernelBench 系基准的核心形态是：给定 PyTorch 参考实现与形状/精度约束，要求产出一个数值等价的 kernel，再以加速比与正确性共同判定。它的价值在于可自动生成、可自动校验、可批量规模化——这三点直接决定了评测成本模型的分母。但谱系上每往右移一格（从单算子到融合子图、从固定 shape 到动态 shape、从 fp32 到 bf16/fp8），可比性就衰减一格：跨条目比较加速比时，若不锁定 dtype、shape 分布与基线版本，数字之间没有偏序关系。

机制上，评测口径必须把“任务实例”定义成三元组 (op, shape-set, dtype) 加一个基线锚点。基线锚点有两种：eager 参考实现（PyTorch 原生算子组合）与厂商库基线（cuBLAS/cuDNN/CUTLASS 对应实现）。前者衡量“相对朴素实现的收益”，后者衡量“相对已优化实现的剩余空间”。二者给出的加速比可以差出一个量级，因此任何“快 N 倍”的陈述必须绑定锚点类型。本卷采用的口径是双锚点并列上报，而不是取其一。

$$\text{speedup}_{\text{eager}}=\frac{t_{\text{eager}}}{t_{\text{kernel}}},\qquad \text{speedup}_{\text{lib}}=\frac{t_{\text{lib}}}{t_{\text{kernel}}}$$

代价在于：双锚点意味着每个任务实例要跑三次计时（eager、lib、candidate），评测 GPU 分钟数近似翻倍。以单任务单次计时含 warmup 与多次重复为例，若单次测量窗口为秒级，则一个千级任务集的单轮评测就落在“数百 GPU 分钟”量级——这正是容量规划要吸收的成本项。具体例子：同一道 GEMM 题，在 eager 锚点下 candidate 可能呈现数倍加速，而在 cuBLAS 锚点下加速比收敛到 1 附近甚至低于 1；若报告只写前者，读者会误判 kernel 的真实工程价值。

二 · 硬件与 dtype：把“快”钉在具体硅片上

加速比是相对量，硬件是它的隐藏参数。同一 kernel 在 A100 与 H100 上的比值不同，原因不是 kernel 变好了，而是基线实现随架构换代而变（Tensor Core 代际、共享内存带宽、L2 容量、异步拷贝指令可用性）。因此评测口径必须记录：GPU 型号与数量、SM 频率策略（是否锁频）、显存带宽档位、驱动与 CUDA 版本、编译选项（-O3、--use_fast_math 与否）。缺少任一项，数字不可复核。

dtype 是第二个隐藏参数，且它同时影响正确性与性能两侧。fp32 累加与 bf16 累加的数值容差不同，fp8 还引入缩放因子（scale）语义；一个在 bf16 下通过容差校验的 kernel，换到 fp32 可能因累加顺序差异而越界。口径上应把 dtype 与容差绑定成一对：(dtype, atol, rtol)，并在报告中显式给出。性能侧，dtype 决定理论峰值——roofline 的上界随 dtype 变化，因此“达到峰值百分比”这类指标必须注明是按哪种精度的峰值算的。

口径字段缺失时的后果记录成本
GPU 型号/锁频跨节点数字不可比元数据，零 GPU 开销
dtype + 容差对正确性判定漂移需额外一轮参考值计算
基线锚点类型加速比失去偏序多一次计时
编译选项性能差异归因错误需缓存编译产物

代价具体落在编译时间与缓存上：为每个 (kernel, 编译选项) 组合保留编译产物，会推高评测节点的磁盘与冷启动时延；若每次评测都重编译，单任务编译开销可达秒级到数十秒，在千级任务集上叠加成可观的 GPU 空闲等待。工程判断是：编译产物按内容哈希缓存，缓存命中率作为评测吞吐的独立监控项。

三 · 指标分层：时延、吞吐与“有效加速”

“快”至少有三个互不等价的度量：单次调用时延（latency）、单位时间吞吐（throughput）、以及端到端收益（end-to-end gain）。kernel 级评测通常测时延，但生产侧关心的是吞吐与端到端。二者之间的换算不是常数：小 shape 下 launch 开销与 Python 侧调度占主导，时延的改善可能被吞掉；大 shape 下才逼近 roofline。因此口径必须声明测量的是哪一种，并给出 shape 分布。

机制上，时延测量要区分冷启动（含 JIT 编译、上下文初始化）与稳态（warmup 后多次重复取中位数或最小值）。稳态数字用于比较 kernel 质量，冷启动数字用于评估部署可行性——后者常被忽略，却直接决定生产替换是否可行。重复次数与统计量的选择本身是成本项：重复越多，置信区间越窄，GPU 分钟数线性上升。

$$\text{GPU minutes}=N_{\text{tasks}}\times R_{\text{reps}}\times\frac{t_{\text{warmup}}+t_{\text{measure}}}{60}$$

其中 Rreps 是为压低方差所需的重复轮数。置信度与成本在此直接对冲：把重复数翻倍，方差按平方根收敛，但评测集群占用翻倍。具体例子：同一 kernel 在两种 shape 下，小时延场景的测量噪声占比更高，需要更多重复才能把中位数稳定到可比较的程度；而大 shape 下单次测量已足够长，重复数可以减少。口径应允许按 shape 分档设定重复数，而不是全局统一。

“有效加速”是第三个层次：把 kernel 加速比折算到端到端时延上，必须乘以该 kernel 在整条计算图中的时间占比（Amdahl 口径）。一个 3 倍加速但只占端到端 5% 时间的 kernel，端到端收益不足 4%。本卷要求同时上报 kernel 级加速比与该 kernel 的时间占比，缺后者则无法进入单位收益成本的计算。

四 · 正确性 oracle 的口径成本

正确性判定不是免费的布尔值，它有自己的口径与成本。最基本的是数值比对：以参考实现输出为基准，按 (dtype, atol, rtol) 判定逐元素误差。参考输出本身要算一次，这构成额外的 GPU 时间；若参考实现是 eager 组合，它往往比 candidate 慢，于是 oracle 成本可能超过被测对象。

更强的 oracle 是性质检验：形状/步长一致性、边界条件（空 tensor、极端 shape）、确定性（同输入多次运行结果一致）、以及无越界写（可用计算卫生检查或工具化检测）。形式化审计属于另一条线（见对应片段），本段只强调其成本形态：形式验证的求解时间随 kernel 规模非线性增长，且对循环边界与别名分析的建模需要人工投入，难以批量规模化。因此可信评测流水线的默认口径是“数值比对 + 性质抽检”，形式审计作为高价值样本的加签环节。

代价的具体形态：容差放宽会提高通过率但削弱判别力，容差收紧会把合法实现误判为失败。二者都在消耗评测预算——前者浪费在无效候选上，后者浪费在复检上。工程判断是把容差与 dtype 绑定成版本化配置，任何容差变更都触发基线重算，避免历史数字与新数字混排。具体例子：同一 reduction kernel 因累加顺序不同，在 fp32 下误差在容差内，在 bf16 下越界；若口径未绑定 dtype，同一份报告会自相矛盾。

五 · 从“快”到可复核数字：报告结构与复现包

可复核的数字需要三件东西：原始测量、归约规则、环境指纹。原始测量指每次重复的计时样本（而非仅中位数），归约规则指取中位数/最小值/几何平均以及异常值剔除策略，环境指纹指上节列出的硬件与软件字段。三者齐备，第三方才能在不重跑的前提下判断数字是否可信；若要重跑，还需复现包：任务定义、参考实现、编译命令、随机种子、shape 列表。

机制上，报告应把每个任务实例组织成一条记录，字段包括：任务 ID、锚点类型、dtype 与容差、shape 集、稳态时延及其分散度、冷启动时延、正确性判定结果与失败原因分类、编译耗时、GPU 型号。归约到集合级别时，采用按任务等权的中位数而非按时间加权，避免大 shape 任务主导整体数字。同时上报通过率，因为加速比只在通过的样本上有意义——失败样本的“快”是伪快。

$$\text{score}=\text{median}_{i\in\text{passed}}\left(\text{speedup}_i\right)\quad\text{with}\quad \text{passrate}=\frac{|\text{passed}|}{N}$$

代价在于存储与传输：逐次样本加环境指纹使单条记录体积上升，千级任务集的报告从“一张表”变成“一个数据集”，需要对象存储与索引。另一个代价是复现包的维护成本——参考实现随框架版本漂移，旧复现包可能在新环境下产出不同基线，因此复现包必须钉住版本。具体例子：同一批复现包在驱动升级后重跑，eager 基线时延变化导致所有加速比整体平移，若报告未记录驱动版本，这种平移会被误读为 kernel 质量变化。

六 · 口径与容量的耦合点

口径选择直接改变容量需求，这是本卷把两者放在一起的原因。三个耦合点最显著：其一，双锚点使每任务计时次数翻倍；其二，按 shape 分档的重复数使测量窗口长度不均，调度上产生长尾任务，峰值排队被少数长任务拖住；其三，正确性 oracle 的参考计算与复检构成额外负载。三者叠加，使“评测吞吐”而非“单次评测速度”成为瓶颈——这与故事映射中评测集群排队拖慢迭代的观察一致。

工程判断因此落在口径的分层采样上：全量任务集跑单锚点、低重复的快速档，用于迭代期的高频反馈；高价值子集跑双锚点、高重复、加签 oracle 的严格档，用于发布前的置信判定。两档共享同一环境指纹与归约规则，保证数字可拼接。这样做的代价是两档之间的数字不能直接混排，需要在报告中标注档位；收益是把 GPU 分钟数从“全量严格”压到“分层加权”，同时保留严格档的可复核性。

具体机制上，快速档的通过率作为严格档的触发器：快速档失败的任务不进入严格档，从而把严格档预算集中在校验边界样本上。这一触发器本身需要口径支持——失败原因必须分类（数值越界、编译失败、超时、非法访存），否则无法区分“值得复检”与“确定无效”。分类字段的成本是每条记录多几个枚举值，收益是严格档的 GPU 分钟数按失败率成比例缩减。最终，可复核数字的产出速率由这套分层口径决定，而容量规划的参数（评测集群与训练集群配比、峰值排队策略）正是以该速率为输入反推出来的。

口径失配：当“快”无法折算成同一张账单

本卷所有成本数字都挂在一组口径上：基准版本、基线实现、硬件型号、dtype、指标定义。口径一变，数字就不可比，而工程上最常见的失效不是算错，是拿两个不同口径的数字相减。典型场景：kernel 在 fp16 下比基线快，但基线是 fp32 参考实现，端到端收益被 dtype 转换的额外 cast kernel 吃掉；或者基准测的是单算子时延，生产侧瓶颈却在算子间的显存往返。可复核的做法是把每次测量绑定成五元组 (benchmark_rev, baseline_impl, gpu_sku, dtype, metric)，任何一项缺失即视为不可复核，成本模型拒绝入库。代价是元数据存储与校验开销——每个评测任务多出一次基线重跑与口径比对，单任务 GPU 分钟数上升，但换来的是跨批次数字可相减。

指标口径本身也有边界。以 roofline 为参照的 SOL 利用率只在计算或带宽其一饱和时才有意义；当 kernel 处于低占用、访存不规则的状态，SOL 分母选错会让“提升”变成口径假象。折算公式必须显式写出分母来源：

$$\text{cost}_{1\%}=\frac{\Delta T_{\text{e2e}}\ \text{对应的卡时}}{\max(\text{speedup}_{\text{sol}},\ \epsilon)}\quad\text{s.t.}\ \text{dtype},\ \text{baseline},\ \text{gpu}\ \text{三者锁定}$$

分母被钳制在 ε 以上，是为了防止基线本身接近零时成本被除爆；这个钳制阈值是口径的一部分，必须与基准版本一同冻结。失效条件是基线实现被替换而未升版本号——此时历史成本曲线出现不可解释的跳变，容量规划会按错误斜率外推。

系统代价落在评测吞吐上。口径校验要求每个候选 kernel 与锁定基线在同卡同 dtype 下各跑一遍，重复次数由置信区间决定而非固定值；少重复省 GPU 分钟但放宽置信，多重复则直接推高排队长度。这正是故事中评测集群排队拖慢迭代的机制来源：瓶颈不在单次 kernel 执行，而在口径对齐所需的成对测量。一张小表足以说明取舍边界：

口径项锁定后的代价失锁后的后果
dtype额外 cast kernel 计入端到端收益被高估

工程判断因此落在“冻结口径、放开重复次数”：口径五元组随基准版本一起版本化，重复次数按置信需求动态调整，把成本弹性留给统计侧而非定义侧。这样容量规划拿到的斜率才是可外推的，评测集群与训练集群的配比也才有稳定输入。
