一 · 漏检率不是布尔量：checker 的统计口径

把“正确”当成一个布尔判定，是 oracle 审计里最先要拆掉的假设。任何 checker 都是有限样本上的判决函数，它真正可度量的量是漏检率（false accept rate）与误杀率（false reject rate）。前者决定 agent 能否靠“骗过测试”刷分，后者决定修复循环会不会被噪声带偏。工程上要把 checker 写成三元组：输入域采样器、参考实现、容差判据。漏检率定义为在真实错误集合 E 上判为通过的比例，误杀率是在正确集合 C 上判为失败的比例。二者不是对称代价：漏检会让 RL 奖励信号被污染，误杀会让 agent 在正确 kernel 上反复“修复”，直接烧掉轮数预算。

具体机制上，checker 的判据通常是“输出张量在给定 dtype 与容差下逐元素接近”。问题在于容差本身是一个可被利用的自由度：把 atol 放宽到 1e-2，绝大多数近似正确的 kernel 都能过，但真正写错索引的 kernel 也可能因为数值饱和而蒙混。审计要做的是把容差当作超参数扫描，观察通过率随容差变化的曲线斜率——斜率陡峭说明测试对数值误差敏感，斜率平坦说明测试几乎不区分对错。这条曲线本身就是漏检率的经验代理。

$$\text{FAR}=\frac{|\{e\in E:\ \text{checker}(e)=\text{pass}\}|}{|E|},\qquad \text{FRR}=\frac{|\{c\in C:\ \text{checker}(c)=\text{fail}\}|}{|C|}$$

代价落在时延与显存上：为了压低漏检率，checker 往往要跑多组随机种子、多种 shape、多种 dtype，每组都要分配输入输出缓冲区并做同步。一个任务若跑 8 组配置，单次判定时延是单组的数倍，而 agent 每轮修复都要重新判定，轮数预算被判定开销挤占。具体例子：一个 reduction kernel 在 N=1024 时正确、在 N=1023 时越界读，若采样器只取 2 的幂，漏检率接近 1，而修复循环永远不会触发——这正是“测试通过但 kernel 错”的典型形态。

二 · 变异测试：给 checker 注射已知错误

漏检率无法直接从真实错误集合估计，因为真实错误集合本身未知。变异测试提供了可操作的替代：对参考实现做受控变异，生成一批“必然错误”的 kernel，再看 checker 能否全部拒绝。变异算子要覆盖 GPU 特有的错误面：索引偏移一位、边界条件从 < 改成 <=、共享内存同步缺失、warp 内 shuffle 掩码写错、累加初值从 0 改成 1、把 fp32 累加降级为 fp16。每个变异体都是一条已知错误的探针，checker 对其判 pass 即记一次漏检。

变异测试的产出不是单一数字，而是“变异杀伤率”矩阵：行是变异算子，列是测试配置。矩阵里出现整列全 pass，说明该配置对该类错误完全无感；出现整行全 pass，说明该类错误是系统性盲区。工程判断由此变得具体：盲区集中在边界条件类变异上，就补非 2 的幂 shape 与非对齐指针；盲区集中在同步类变异上，就补多 block 竞争与 stream 并发场景。

  • 变异体生成要廉价：参考实现是 Python/PyTorch 时，变异在源码层做文本替换即可，不需要重新编译 CUDA。
  • 杀伤率的分母是变异体总数，分子是被拒绝数；分母太小会让指标失真，通常要覆盖每个算子至少十余个变异点。
  • 变异测试本身有编译时间代价：若变异体是 CUDA C++，每个变异体都要过一次 nvcc，编译时间随变异体数量线性增长，审计流水线要并行化。

具体例子：一个 softmax kernel 的参考实现被变异为“减去最大值”这一步被删除。数值上在输入幅度较小时仍然接近正确，checker 若只用小幅度输入就漏检；补一组大幅度输入后该变异体被稳定拒绝。这说明变异测试的价值不在于证明 checker 完备，而在于把“完备”这个不可判定的目标降解为一张可追踪的盲区清单。

三 · Fuzz：把输入域当作攻击面

变异测试攻击的是实现，fuzz 攻击的是输入域。对 kernel 而言，输入域包括 shape、stride、dtype、对齐、别名关系、并发 stream 数。fuzz 的目标是找到让 checker 与真实语义分歧的输入，而不是找到让 kernel 崩溃的输入——崩溃至少会被发现，分歧才是漏检。生成策略上，优先构造边界样本：长度为 0、长度为 1、长度为质数、非连续 stride、带偏移的视图、fp16 与 bf16 混合、NaN/Inf 注入。

一个可执行的伪代码思路是分层采样：第一层按 shape 维度做边界与随机混合，第二层按内存布局注入非连续与别名，第三层按数值分布注入极值与特殊值。每层采样后跑 checker 与高精度参考（如 fp64 参考或 CPU 参考），记录分歧样本。分歧样本要回流成回归用例，否则 fuzz 的产出是一次性的。

$$\text{coverage}=\frac{|\{\text{shape 桶被至少一个用例命中}\}|}{|\{\text{shape 桶}\}|}$$

代价在显存与时间：非连续 stride 与别名输入会让 kernel 的有效带宽下降，单次判定时延上升；NaN/Inf 注入会让某些 kernel 走慢路径。fuzz 的预算要按“每任务判定次数”计，而不是按墙钟时间计，否则慢任务会被系统性少测。具体例子：一个 transpose kernel 在方阵上正确，在 1×N 与 N×1 的退化情形下索引计算溢出，fuzz 的边界层若只覆盖方阵就完全测不到；把退化 shape 加入桶后，该 kernel 在修复循环里被稳定拦下。

四 · 形式验证与合约验证：把“正确”写成可判定的命题

fuzz 与变异都是经验手段，形式验证提供的是另一条路径：把 kernel 的语义写成前置条件、后置条件与循环不变式，交给 SMT 求解器或交互式证明器。对 GPU kernel，可行的切入点是合约验证而非全自动定理证明——在每个 kernel 入口写 assume（指针对齐、shape 范围、stride 关系），在出口写 assert（输出与参考的代数关系），中间用不变式刻画分块累加。工具链上，CUDA 侧可用带合约的 C++ 方言做静态检查，Triton 侧可把 block 级语义降到张量级公式再交给求解器。

合约验证的强项是覆盖所有输入而非采样输入，弱项是规模：一旦 kernel 里有数据相关的分支或原子操作，路径爆炸会让求解时间不可控。工程判断是分层使用：对索引计算、边界谓词、归约结合律这类“小命题”做全自动验证；对涉及浮点非结合性的部分，退回到“误差界证明 + 经验测试”的组合。浮点合约要写成区间形式而非等式，例如输出必须落在参考值的某个 ulp 区间内，这个区间由累加顺序与 dtype 决定。

手段覆盖对象主要代价适用命题
变异测试已知错误类编译时间随变异体线性增长checker 盲区清单
fuzz输入域边界判定时延与显存分歧样本发现
合约验证全输入空间求解时间、路径爆炸索引与边界谓词
形式证明代数语义人工建模成本归约结合律、分块等价

具体例子：一个分块矩阵乘 kernel 的合约写成“对任意合法 M/N/K 与对齐指针，输出等于参考在给定 ulp 区间内”。求解器能自动证掉索引不越界与 tile 覆盖完整这两条，但浮点累加顺序带来的误差界需要人工给出上界，再作为 assume 注入。这条分工让形式验证的产出是可复用的引理库，而不是一次性证明。

五 · 审计流水线怎么接进 agent 的修复循环

审计不是离线报告，它要变成 agent 运行时的一个反馈源。机制上，把 checker 的判定结果拆成结构化信号：通过/失败、失败类别（数值超差、越界、未同步、形状不符）、分歧样本的最小复现输入。这些信号进入上下文管理，作为“失败模式记忆”的一条记录，供后续轮次检索。修复预算的终止条件要同时看轮数与“判定置信度”：若某轮之后 checker 的漏检率估计仍高，就不能因为一次 pass 而终止，而要追加一轮变异/fuzz 复核。

代价体现在 token 与轮数上：每次复核都要把分歧样本、变异杀伤矩阵摘要塞进上下文，token 消耗随审计强度上升；而修复轮数预算是有限的，审计占用的轮次会挤压真正的代码修改轮次。工程判断是把审计分成两级：轻量级（固定种子 + 边界 shape）每轮必跑，重量级（变异 + fuzz + 合约）在 agent 声称“已修复”时触发一次。这样漏检率高的任务会在终止前被拦下，而不会在每轮都付出全量审计开销。

  • 失败类别要映射到修复动作：越界类触发边界谓词重写，未同步类触发同步点插入，数值超差类触发累加精度调整。
  • 分歧样本要作为回归用例固化，否则同一错误会在后续轮次以不同形态复现。
  • 变异杀伤矩阵的摘要要压缩成“盲区标签”而非原始矩阵，控制上下文长度。

具体例子：agent 生成一个 warp 级 reduction，checker 首轮通过，但重量级审计发现“同步缺失”变异体未被拒绝，于是触发追加复核，fuzz 构造出多 warp 竞争输入并暴露错误；修复循环据此插入 __syncthreads()，第二轮通过且变异杀伤率补齐。这条路径说明：审计的价值不在于给出一个“正确”的结论，而在于把“通过”这个信号的可信度量化，并让 agent 的终止条件依赖这个可信度而不是单次判定。

Oracle 审计的边界：checker 漏检、变异测试与形式验证的系统代价

checker 本身是一个被测对象，而不是公理。审计的核心是给 checker 定义漏检率：给定一批已知错误的 kernel 变体（变异体），checker 判为通过的比例即漏检率，记为 $$ \mathrm{FNR} = \frac{|\{m \in M : \mathrm{checker}(m) = \text{pass}\}|}{|M|} $$，其中 M 是变异体集合。变异测试的关键不是随机扰动，而是语义保持与语义破坏的成对构造：对每个正确 kernel 施加边界改写（去掉 mask、把 `__syncthreads()` 挪到循环外、把 `float` 累加改成 `half`、把 shared memory tile 尺寸减半、把归约的初值从 0 改成 1），每个变异体都携带一个“应当被哪个断言捕获”的标签。若某变异体逃逸，说明 oracle 的断言维度存在盲区，而不是 kernel 本身正确。代价在于变异体数量与编译时间成正比：每个变异体都要独立编译并执行，一轮审计的编译开销是单 kernel 的 |M| 倍，且变异体执行往往触发越界访问，需要隔离的进程与超时预算，否则一个非法访存就把整个审计进程拖垮。

fuzz 与变异测试互补：变异测试是白盒定向的，fuzz 是黑盒随机的，重点在输入域而非代码域。对 kernel 而言，输入域包括 shape、stride、dtype、对齐、空 tensor、极端值（NaN/Inf、denormal、int 溢出边界）以及非连续布局。fuzz 的有效性取决于能否生成“合法但刁钻”的输入，而不是随机字节——随机字节大多在参数校验阶段就被拒绝，覆盖率极低。工程上更划算的做法是把 fuzz 输入空间压缩成一组等价类代表：每个等价类取一个代表输入，配合变异体做笛卡尔积，形成 (变异体 × 输入类) 的审计矩阵。代价是显存与时间：大 shape 的 fuzz 用例会挤占 GPU，通常要把审计放在独立队列、限制单用例显存上限，并对超时用例单独记账，否则审计吞吐会被少数慢用例拖到不可用。

形式验证与合约验证是另一条路径，但它有明确的适用边界。合约验证的思路是给 kernel 写前置/后置条件（例如“输出形状等于输入形状”“归约结果与参考实现的相对误差小于阈值”“shared memory 访问下标恒小于 tile 尺寸”），再用符号执行或 SMT 求解检查这些条件在所有路径上成立。它对控制流与下标安全类性质有效，对浮点数值精度几乎无能为力——浮点舍入使 SMT 求解器难以给出有意义的证明，实践中只能退化为区间算术加采样。形式验证的系统代价是编译期与求解时间：一个带循环不变式的 kernel 合约，求解时间可能从秒级涨到分钟级，且对 CuTe/PTX 层的手写代码，建模成本远高于收益。因此工程判断是分层的：下标安全与形状契约走形式/合约验证，数值正确性走变异测试加高精度参考实现，性能回归走 profile 对比，三者不可互相替代。

审计手段捕获的错误类型主要代价失效条件
变异测试断言盲区、边界条件遗漏编译时间 ×|M|，需隔离执行变异体构造不覆盖真实失败模式
fuzz非法输入、极端值、布局假设显存占用、慢用例拖吞吐输入等价类划分失真
合约/形式验证下标越界、形状契约违反求解时间分钟级、建模成本浮点数值性质无法证明

把这三者接进 agent 闭环时，审计结果必须回灌成结构化反馈而非布尔值：逃逸的变异体 ID、触发的输入等价类、合约求解失败的路径条件，都要作为下一轮修复的上下文。代价体现在修复预算上：一次审计失败若只回灌“checker 未通过”，agent 会在同一错误类别上反复试探，浪费轮数与 token；回灌到具体变异体与输入类，才能把修复收敛到断言或边界处理上。这也解释了为什么脚手架从一次性生成升级为编译-执行-修复闭环后，第一波真实增益来自修复轮次——但增益的上限由 oracle 的漏检率决定，checker 漏掉的错误不会被修复，只会被“通过”。
