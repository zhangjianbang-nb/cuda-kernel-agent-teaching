一 · 口径表：把“快”拆成可复核的字段

本卷的奖励函数不是从“感觉快了”出发，而是从一张固定字段的口径表出发。每个候选 kernel 在进入 RL 管线之前，必须被压成一行结构化记录：算子族与形状签名、参考实现（baseline）标识、硬件型号与 SM 配置、dtype 与累加精度、计时口径（是否含 launch、是否含 H2D/D2H、warmup 与重复次数、取中位数还是最小值）、正确性判定结果、绝对时延、相对基线加速比、SOL 利用率、编译耗时、显存峰值。这张表的作用是让“快”成为一个可被第三方重跑复现的数字，而不是一段叙述。奖励设计里“绝对加速比还是相对基线”的决策，本质上就是这张表里 baseline 字段是否被钉死的问题：baseline 一旦随轮次漂移，加速比就失去可比性，多轮信用分配也随之失真。

机制上，口径表由评测流水线在每次 rollout 时填充，字段缺失即视为无效样本，不进入奖励计算。伪代码思路是：record = collect(kernel, shape, hw, dtype, timer_cfg); if not record.complete: drop; reward = gate(record.correct) * f(record.speedup, record.sol)。这里的代价是吞吐：一次完整口径采集包含 warmup、多轮重复计时与一次参考实现对照，单样本评测时延远高于“跑一次看数”；在课程学习的早期难度档上，这种开销会直接压低单位时间内的有效 rollout 数，进而拉长 RL 训练曲线的爬升段。具体例子：同一个 reduction 算子在固定形状下，若计时口径含 launch 开销，小规模 shape 的相对加速比会被系统性压低，于是奖励把模型推向“只在大 shape 上优化”的策略——这正是口径不一致导致的奖励偏移，而不是模型真的学会了取舍。

二 · 基线：分母的选择就是奖励函数的选择

基线不是“随便找个能跑的版本”，它必须与参考实现同语义、同 dtype、同形状签名，并且在同一硬件上以同一计时口径测量。工程上通常准备三层基线：框架原生实现（作为语义锚点）、手写 CUDA 参考实现（作为性能锚点）、以及当前策略已产出的最优 kernel（作为自我对照）。前两层固定不变，第三层随训练推进而更新，但只在“自我对照”这一列使用，绝不进入奖励的分母。若把第三层误用作分母，奖励会退化为“比上一轮自己快多少”，模型可以通过在早期故意产出慢 kernel 来抬高后续相对增益，这是典型的奖励 hacking 路径，需要在监控面板上以“分母漂移告警”形式拦截。

公式上，相对加速比定义为 $$ S = \frac{T_{\text{base}}}{T_{\text{cand}}} $$，其中 T 为同口径下的时延统计量。绝对加速比则把 T_{\text{base}} 替换为固定常数或硬件理论下界，二者在课程不同阶段的激励方向不同：绝对口径鼓励逼近硬件极限，相对口径鼓励稳定超越基线。代价在于方差：相对口径的分母若在小 shape 上本身噪声大，S 的置信区间会变宽，导致同一正确 kernel 在不同 rollout 中拿到差异明显的奖励，进而让 PPO/GRPO 的优势估计被噪声主导。具体例子：一个 elementwise 算子的框架原生基线在大 shape 上已接近带宽上限，此时相对加速比的天花板很低，奖励几乎不随优化努力变化；若改用 SOL 归一化口径，奖励重新获得区分度，但要求口径表里记录峰值带宽的测量方式，否则归一化本身又引入新的不可复核项。

三 · 硬件与 dtype：把不可比因素挡在奖励之外

硬件字段的作用不是堆参数，而是把“跨设备不可比”挡在奖励计算之外。同一算子族在不同 SM 配置、不同显存带宽的卡上，SOL 上限不同，绝对时延更不可比；因此奖励只在同一硬件分层内做横向比较，跨层样本只进入课程迁移统计，不进入同一批优势估计。dtype 字段同理：fp32 与 bf16 的正确性容差、累加精度要求不同，若允许模型在 bf16 下用更低精度换取速度而不改变门控阈值，正确性硬门控会被系统性绕过。工程判断是：dtype 与容差必须写进口径表并与 oracle 判定绑定，奖励函数只读取“已通过该 dtype 容差”的布尔量，不自行推断。

机制上，硬件分层用一张静态映射表实现：tier = hw_table[device_id]; reward = normalize_by_tier(speedup, tier.sol_ceiling)。代价是样本利用率：分层后每层内的有效样本数下降，课程学习在算子族迁移时需要更多轮次才能填满各层的难度档，表现为训练曲线在平台期停留更久。具体例子：把同一个 matmul 形状的 fp32 与 bf16 候选混在同一奖励批次里，bf16 候选因累加精度更低而普遍更快，奖励会奖励“换 dtype”而非“改 kernel”，多轮修复的成功率统计被污染——修复轮次带来的增益被 dtype 切换的增益掩盖，信用分配无法归因到具体某一轮的代码改动。

四 · 指标：加速比、SOL 与正确性门控的三层结构

指标不是单一标量，而是三层结构：正确性门控（布尔，硬性）、加速比连续奖励（相对或绝对）、SOL 归一化（把加速比映射到硬件上限的比例）。三层之间是串联关系而非加权求和：门控为假时后两层不计算，避免“快但错”的候选获得任何正奖励；SOL 归一化只在加速比超过基线一定幅度后启用，防止在易优化算子上奖励饱和。公式上可写成 $$ r = \mathbb{1}[\text{correct}] \cdot \big( \alpha \cdot \text{clip}(S) + \beta \cdot \text{SOL} \big) $$，其中 SOL = T_{\text{ideal}} / T_{\text{cand}}，T_{\text{ideal}} 由口径表记录的峰值带宽或峰值算力推出。正确性作为硬门控还是软惩罚的决策，就落在 \mathbb{1}[\text{correct}] 这一项上：软惩罚会让模型学会“用少量错误换大幅加速”的投机策略，硬门控则把这类样本直接归零，代价是早期正确率低时有效正奖励稀疏，训练信号变弱。

代价体现在 token 与编译时间两侧：SOL 归一化要求每次 rollout 都读取硬件峰值字段并做一次除法，计算开销可忽略，但口径表补全与 oracle 判定带来的额外评测时延会挤占 rollout 预算；硬门控使大量候选在正确性检查阶段被丢弃，单位 token 的有效训练信号下降。具体例子：一个 fused softmax 候选在某一轮修复后时延下降但数值容差边缘越界，硬门控将其归零，该轮在多轮信用分配中被记为“无增益”；若改用软惩罚，同一候选会拿到部分奖励，模型随后倾向于继续在容差边缘试探，监控面板上的正确性通过率会缓慢下滑而加速比曲线仍在上行——这正是需要被面板拦截的 hacking 形态。

五 · 把多轮增益翻译成可复核数字

多轮信用分配要回答“哪一轮修复带来增益”，前提是每一轮的数字都可复核。做法是在口径表上增加轮次字段：同一轨迹内，第 k 轮的候选与第 k-1 轮在同一口径下测量，增益定义为 $$ \Delta_k = r_k - r_{k-1} $$，并附带该轮改动是否触碰了 dtype、形状签名或 baseline 字段的标记。若标记为真，\Delta_k 不可直接归因于代码修复，必须单独计入“口径变更”桶。折扣因子如何设，取决于 \Delta_k 的噪声水平：噪声大时高折扣会让早期轮次的信号被淹没，噪声小时低折扣会让后期无效轮次获得过多信用。工程上以口径表记录的重复计时方差作为折扣因子的输入，而不是凭经验固定。

代价是评测预算的线性增长：每轮都做同口径复测意味着一条 n 轮轨迹的评测开销是单轮的 n 倍，在课程高难度档上这会显著拖慢单位时间内的轨迹产出，训练曲线的突破点被推迟。具体例子：某轨迹第 2 轮把 shared memory 分块改小后时延下降，第 3 轮仅调整了 launch 配置而时延持平，若不做逐轮同口径复测，两轮会被合并成一个“修复成功”的标签，信用分配无法区分真实增益来自哪一轮；逐轮复测后 \Delta_2 为正、\Delta_3 为零，折扣因子把信用集中到第 2 轮，后续课程在该算子族上复现这一改动模式，多轮修复的成功率统计才具备可解释性。

六 · 口径漂移的监控与工程判断

口径表本身会漂移：baseline 被替换、计时口径被修改、硬件分层表更新、dtype 容差被放宽。每一次漂移都会让历史奖励与新奖励不可比，若不加监控，RL 训练曲线上的“突破”可能只是口径变化造成的假象。监控面板应记录每次口径变更的时间戳与影响字段，并在变更前后各保留一批固定样本做对照复测，把差异写成可复核的数字而非叙述。机制上，对照样本集是静态的、不参与训练的，只用于口径审计；伪代码思路是 audit = eval(fixed_set, old_cfg) vs eval(fixed_set, new_cfg); if drift > threshold: flag。代价是固定样本集占用评测预算且不产生训练信号，属于纯开销，但它是把“快”翻译成可信数字的必要成本。

工程判断落在两处：其一，奖励函数只读取口径表中已冻结的字段，任何未冻结字段的变化都触发告警而非静默生效；其二，课程学习的难度递进以口径表字段为边界，算子族迁移时先验证新族在旧口径下可测，再放开奖励。具体例子：当硬件分层表新增一档设备时，若直接把新档样本混入旧批次，SOL 归一化的分母改变，同一 kernel 的奖励数值整体平移，训练曲线出现台阶式跳变；先跑固定样本对照、确认漂移幅度、再决定是否重标定历史奖励，才能让“多轮修复成功率显著上升”这一观察落在真实机制上，而不是口径变更的副产品。

口径漂移：当“快”被翻译成可复核数字时的边界

本卷把“快”落成可复核数字，靠的是一条固定链路：交互轨迹里的原始计时 → 评测分数 → oracle 判定 → 奖励。这条链路最脆的环节不是 GPU，而是口径本身。同一份 kernel 在“相对基线加速比”与“SOL 归一化”两种口径下会给出方向相反的排序：前者奖励“比参考实现快”，后者奖励“离硬件上限近”。若参考基线本身是社区里一份未调优的 PyTorch 实现，一个只做了合并访存的 Triton kernel 就能拿到漂亮加速比，却在 SOL 口径下暴露利用率不足；反之，一个贴着 roofline 的 CuTe kernel 若基线已被高手优化过，加速比会显得平庸。奖励设计因此必须显式声明分母：

$$ r_{\text{speed}}=\min\!\left(\frac{t_{\text{base}}}{t_{\text{cand}}}-1,\ \kappa\right),\qquad r_{\text{SOL}}=\frac{\text{achieved}}{\text{roofline}} $$
两者不可混用于同一批次，否则多轮信用分配会把“换了基线”误判成“某一轮修复带来了增益”。

失效条件集中在三类。其一，计时噪声吞掉真实增益：小 shape 下单次 launch 的时延被 CPU 侧开销与事件同步主导，加速比在 1.0 附近抖动，正确性门控通过但奖励信号近乎为零，多轮 RL 在这一区间学不到东西，只能靠课程学习把样本推向大 shape 或计算密集算子族。其二，dtype 与硬件绑定：fp32 与 bf16 的 roofline 不同，A100 与 H100 的 SOL 分母不同，跨硬件汇总分数会把“换了卡”读成“换了算法”；口径必须把 (dtype, 硬件, shape) 作为三元组钉死，任何一项变动都触发重测而非沿用旧分。其三，正确性作为硬门控时，一个数值上仅在极端输入越界的 kernel 会被整条奖励清零，多轮修复的信用无法回传到“几乎正确”的那一轮；软惩罚则相反，会让 reward hacking 沿着“牺牲边界正确性换速度”的斜坡滑下去。工程判断是：门控用 oracle 的严格判定，但把失败样本单独成桶、给部分信用，而不是直接丢弃。

系统代价必须计入口径。逐样本跑 NCU/SASS profile 能把 SOL 分母做实，但单次 profile 的采集开销远高于一次计时，若每个 rollout 都采，训练吞吐被 profile 拖垮；可行折中是分层采样——只在课程升级点与信用分配的关键轮次采 profile，其余轮次用计时加解析 roofline 估算。下表给出三种口径在可复核性与代价上的取舍。
口径可复核性主要代价典型失效
绝对时延低（受噪声与机器状态影响）需多次重复取中位数小 shape 抖动
相对基线加速比中（依赖基线版本）基线需固定并随卷存档基线过弱导致虚高

落到故事映射上：训练曲线从平台期突破，恰恰发生在把“相对基线加速比”换成“SOL 归一化 + 正确性分桶”之后——不是因为模型变强，而是因为奖励不再奖励“挑软基线”，多轮修复的成功率才在统计上显形。口径不是评测的附属品，它是奖励函数的第一性参数。
