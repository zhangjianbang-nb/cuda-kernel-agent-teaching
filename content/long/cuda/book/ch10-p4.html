一 · 漏检率不是标量：checker 的混淆矩阵与分层抽样

讨论“正确”之前，先把 checker 当成一个被测对象。给定一组输入，checker 输出 accept/reject，而真实语义给出 pass/fail，于是四格表成立：真阳（错误 kernel 被拒）、假阳（正确 kernel 被拒）、真阴、假阴。工程上真正致命的是假阴——错误 kernel 被判为正确，进入基准分数、进入 RL 奖励、最终进入生产。因此 Oracle 审计的第一指标是漏检率，而非通过率：

$$\mathrm{FNR}=\frac{\#\{\text{bad kernel accepted}\}}{\#\{\text{bad kernel total}\}},\qquad \mathrm{FPR}=\frac{\#\{\text{good kernel rejected}\}}{\#\{\text{good kernel total}\}}$$

这两个量必须分开报告，因为它们的代价结构完全不同。假阳浪费 agent 的 rollout token 与编译时间，属于算力损耗；假阴污染奖励信号，属于语义污染，且不可通过增加采样挽回。更麻烦的是漏检率不是全局标量：它对 kernel 类别、数据类型、规约规模高度敏感。一个用 torch.allclose(rtol=1e-2) 做 oracle 的流水线，在 elementwise 加法和 softmax 上漏检率可能极低，但在 layernorm 的方差倒数、attention 的 softmax 分母、以及任何涉及 atomicAdd 非确定性累加的 kernel 上，漏检率会显著抬升，因为误差被结构性地放大而非随机抖动。

因此审计流程要求分层抽样：按算子族（elementwise / reduction / matmul / normalization / attention）、按 dtype（fp32 / tf32 / bf16 / fp16 / fp8）、按形状（小 shape 触发 launch 开销与边界分支，大 shape 触发累加顺序差异）切分，每层单独估计 FNR，并给出置信区间。若某层样本量不足以估计，就明确标记为“未审计层”，而不是用全局均值掩盖。这里有一个具体机制值得写进审计规则：对每个 kernel 变体注入已知错误（见下一节），用注入错误的检出比例作为该层 FNR 的上界估计，因为注入错误的分布未必与 agent 真实犯错分布一致，这个估计只能当上界用。

代价方面，分层抽样的成本主要是评测机时与显存：每层要跑足够多的输入才能让 FNR 的置信区间收敛，而大 shape 的 attention kernel 单次前向就可能吃掉数十 GB 显存，导致审计吞吐被显存而非算力卡住。工程判断是：小 shape 层用高采样率换统计功效，大 shape 层用少量但精心构造的对抗输入（极端值、denormal、inf/nan 传播路径）换检出率，两者互补而非互相替代。

二 · 变异测试：用注入错误给 oracle 打分

漏检率无法直接测量，因为“坏 kernel 的全集”不可枚举。变异测试提供了可操作的替代：对参考实现做语义保持或语义破坏的变换，生成一组已知好/已知坏的变体，然后看 checker 是否给出预期判定。语义破坏变异（mutant）应当覆盖 agent 真实会犯的错误类型，而不是随机翻转比特。可用的变异算子包括：把 float 累加器降为 half；把 __syncthreads() 删除或移到错误位置；把边界判断的 < 写成 <=；把 atomicAdd 换成普通写；把 tile 的 stride 写错一位；把 exp 的输入少减一个 max。每个 mutant 对应一类失败模式，与第 3 卷的失败分类直接对齐。

伪代码思路如下：对参考 kernel K_ref 与候选 K_cand，构造变异集合 M = {m_1..m_n}，每个 m_i 作用于 K_ref 得到 K_ref^i，其输出与 K_ref 的差异由高精度参考（fp64 或 CPU 实现）确认；随后要求 checker 对 K_ref^i 判 reject。检出率 detect = |{i: checker rejects K_ref^i}| / n 就是 oracle 在该变异族上的灵敏度。关键在于 mutant 必须“真的错”：若某 mutant 在数值上等价（例如改变了一个不影响结果的循环顺序），它就不该计入分母，否则会人为压低检出率。这要求变异生成阶段本身有一个高精度 oracle 做筛选，形成两层 oracle：内层判 mutant 是否真错，外层判 checker 是否能抓到。

变异测试的代价是编译时间与 token：每个 mutant 都要编译并运行，n 个 mutant 意味着 n 次 nvcc 调用，在模板密集的 CuTe 代码上单次编译可达数十秒，n=50 时审计一轮就是分钟级；若把变异测试放进 agent 的每轮奖励计算，rollout 成本会成倍上升。工程判断是把变异测试放在离线审计与 CI 门禁，而不是在线奖励路径；在线只跑固定的一组“哨兵 mutant”（十来个高价值变异），用少量编译开销换取对 oracle 退化的持续告警。

一个具体例子：某团队发现基准分数在一周内平滑上升，但生产灰度出现数值异常。回查发现 checker 的 rtol 被一次“降低假阳”的调参从 1e-3 放宽到 1e-2，而变异测试中“累加器降精度”这一 mutant 恰好落在放宽后的容差内，检出率从高降到接近零。哨兵 mutant 若在 CI 中运行，这次退化会在合并前被拦住，而不是等到线上告警。

三 · Fuzz：把输入分布当作 oracle 的一部分

checker 的判定依赖输入，因此 oracle 审计必须同时审计输入分布。固定的一小撮基准 shape 会让 agent 过拟合到这些 shape 的边界条件，而真实负载的 shape 是长尾的。Fuzz 的目标不是随机乱撞，而是按失败模式定向生成：极端幅值（接近 dtype 上限、denormal、次正规数）、退化形状（维度为 1、非 2 的幂、奇数长度触发 tail 分支）、对齐异常（非 128 字节对齐的指针偏移）、以及并发敏感形状（多 block 规约、跨 SM 的 atomic 竞争窗口）。

一个可执行的机制是差分 fuzz：同一输入同时喂给候选 kernel 与高精度参考（fp64 CPU 实现或禁用 TF32 的库调用），比较误差分布而非单点误差。判定不应只看 max abs err，因为单个离群点会淹没整体；应同时看误差的分位数与相对误差的分布形状。对归约类 kernel，误差随规约长度增长的斜率本身就是信号：若斜率显著高于 fp32 累加的理论预期，说明实现用了低精度累加或错误的树形结构。公式上可写成对规约长度 n 拟合 err(n) ≈ c·n^α，α 的偏移比单点误差更能暴露结构性缺陷。

Fuzz 的代价是时延与显存：差分 fuzz 要跑两份实现，参考实现通常慢一个数量级以上，因此单轮 fuzz 的墙钟时间由参考侧主导；大 shape 下两份实现同时驻留显存，峰值显存翻倍，在单卡上会直接限制可 fuzz 的最大规模。工程折中是分层：小 shape 全量差分 fuzz，大 shape 只跑候选侧并用稀疏采样的高精度校验点（例如对输出做随机子集抽样再与参考比对），把显存压力降到可控范围，代价是漏检概率随抽样率上升，需要在审计报告里显式记录抽样率。

具体例子：一个 reduction kernel 在 n=1024 时误差正常，在 n=100003（非 2 的幂、触发 tail 处理）时出现明显偏差，原因是 tail 分支用了未初始化的累加器。固定 shape 的基准永远碰不到这个分支，而定向 fuzz 的退化形状生成器一次就能命中。这类缺陷在生产端的表现是“大多数请求正常、偶发请求数值异常”，正好对应可靠性体系里数值异常告警的典型形态。

四 · 形式验证与合约验证：把“正确”从采样变成蕴含

采样式 oracle 永远只能给出概率性结论。形式验证试图给出蕴含式结论：若前置条件成立，则后置条件成立。对 GPU kernel 而言，完整的功能正确性验证代价极高（循环不变式、共享内存别名、warp 级同步语义都要建模），因此工程上更现实的是合约验证：为 kernel 写一份轻量规约（contract），包括前置条件（指针对齐、shape 约束、dtype 假设）与后置条件（输出范围、单调性、与参考的代数关系），然后用符号执行或 SMT 在小规模参数上证明，或用运行时断言在真实输入上监控。

可落地的合约形式有三类。其一是代数合约：例如 softmax 的输出逐行和为 1、每个元素非负；layernorm 的输出均值接近 0、方差接近 1。这类合约不需要参考实现，能在没有高精度 oracle 的情况下独立抓错，代价是只能覆盖部分语义，一个把整行乘以常数的错误 kernel 仍能满足“和为 1”。其二是边界合约：对 inf/nan 输入的传播行为做断言，例如规定 nan 必须传播而非被 clamp 吞掉。其三是等价合约：证明两个实现（如 Triton 版与 CUDA 版）在给定前置条件下逐位或按容差等价，这在小 shape 上可由 SMT 完成，在大 shape 上退化为采样。

形式化的代价主要是人力与编译/求解时间：写一份有用的合约需要理解算子的数学性质，比写一个 allclose 贵一个量级；SMT 求解在含浮点运算的路径上容易爆炸，实际只能覆盖很小的参数域，因此形式验证的产出通常是“小规模上无缺陷”的强证据加上“大规模上由 fuzz 覆盖”的弱证据，两者拼接成审计结论。工程判断是：把合约验证集中在高价值、低维度的算子上（normalization、softmax、简单规约），对 matmul 这类维度爆炸的算子只做代数合约与边界合约，不做逐元素等价证明。

具体例子：一个 attention kernel 在 fp16 下对极大 logit 做 softmax 时溢出为 inf，随后 inf/inf 产生 nan。代数合约“每行和为 1 且无 nan”在运行时断言中立刻触发，无需参考实现即可定位；而基于 allclose 的 oracle 在参考实现同样溢出时会给出“一致”的判定，漏检。这说明合约验证的价值不在于替代采样 oracle，而在于覆盖采样 oracle 与参考实现共享的盲区。

五 · 审计结论怎么写：证据等级与可复现性

“证明正确”在工程上不是一个布尔值，而是一份证据组合。审计报告应当为每个算子族给出证据等级：L0 仅有固定 shape 的 allclose；L1 有分层抽样与变异测试检出率；L2 有定向 fuzz 覆盖退化形状与极端值；L3 有合约验证或小规模形式证明。等级不是越高越好，而是要与该算子在奖励路径与生产路径中的权重匹配：进入 RL 奖励的算子至少要 L2，进入灰度发布的算子要 L2 加运行时断言。

可复现性是审计结论成立的前提。每条证据必须绑定：输入生成器的种子与分布参数、checker 的容差与比较函数、参考实现的精度与编译选项（是否禁用 TF32、是否开启 fast math）、以及硬件与驱动版本。缺少任一项，漏检率的数字就无法被复算，也就无法在事故复盘中作为依据。这与可靠性体系里的版本与配置追踪是同一套机制：审计记录本身就是一种配置追踪，只不过追踪对象是 oracle 而非 kernel。

代价体现在流程时延上：完整跑一遍 L2 审计（分层抽样 + 变异测试 + 定向 fuzz）在单卡上通常是小时级，若算子族多则天级，这与 agent 快速迭代的节奏冲突。工程折中是增量审计：每次 kernel 变更只重跑受影响层与哨兵 mutant，全量审计按固定周期或按发布节点触发；同时把审计结果缓存为带哈希的证据包，变更未触及的层直接复用旧证据，代价是缓存失效判断本身需要正确，否则会复用过期的漏检率。

具体例子：一次精度事故复盘时，团队发现告警对应的 kernel 版本在基准上分数很高，但审计记录显示该算子族只有 L0 证据，且 checker 容差在两次提交之间被放宽而没有任何变异测试记录。归因树因此把根因定位到“oracle 退化”而非“kernel 实现错误”，这与第 3 卷的失败分类衔接：数值类失败的下游往往站着一个未被审计的 checker。修复动作不是改 kernel，而是把该算子族提升到 L2 并加运行时合约断言，同时把容差变更纳入 CI 门禁。

最终落在一条工程判断上：Oracle 审计的产出不是“这个 checker 是对的”，而是“在这个输入分布、这个变异族、这个证据等级下，漏检率的上界是多少，以及哪些层尚未被覆盖”。把这句话写进审计报告的固定字段，比任何一次全绿的通过率都更能支撑可靠性与 BI 的口径一致性——因为 BI 看板上的成功率与加速比分布，其分母正是 checker 判定的“正确”集合，而这个集合的边界由审计证据划定。

当 Oracle 自身成为故障源：审计的边界与代价

checker 的漏检率不是常数，它随输入分布漂移。审计的做法是给 oracle 本身建一条变异链：对参考实现注入受控缺陷（边界条件翻转、累加顺序打乱、fp32→tf32 降精度、mask 越界一位），统计每个变异体被 checker 判死的比例，得到 kill rate。漏检率可写为 $$P_{\text{miss}} = 1 - \frac{|M_{\text{killed}}|}{|M_{\text{total}}|}$$，其中变异体集合必须覆盖该 kernel 的失败分类（第 3 卷的编译/数值/性能/集成四类）。代价是编译与运行时间：每个变异体都要过一次完整构建加执行，变异体数量与 CI 时长线性相关，实践中常把变异测试限制在 nightly 而非每次提交。

fuzz 与形式验证补的是不同盲区。fuzz 用随机形状、随机 dtype、随机 stride 组合去撞越界与竞态，命中率高但不可证；形式验证（合约验证、SMT 对索引与同步的建模）能给出“对所有合法输入成立”的结论，但建模成本高，且一旦 kernel 用了动态并行或原子归约，抽象会失真——验证通过不等于硬件上通过。合约验证的边界在于前置条件：把“输入已对齐、无别名”写进合约，等于把风险推给调用方，而线上灰度数据里恰恰存在未对齐的 tensor。系统代价体现在验证时间与 token：一次完整形式验证可能耗分钟级，agent 多轮 RL 中若每轮都调用，采样吞吐被显著压低。

因此审计结论必须带范围标注，而不是一个布尔“正确”。看板上的口径应区分“checker 通过”“变异 kill rate 达标”“合约验证覆盖的形状集合”，三者不可互相替代。一次数值精度事故的复盘价值正在于此：告警触发后，归因树先问“是 kernel 错还是 oracle 错”，再问“oracle 的漏检是否落在未覆盖的变异类上”。若把审计开销压到零，代价就是漏检率不可知；若把审计做成全量形式验证，代价是迭代周期。工程判断是：按失败分类分配审计预算，数值类走变异加 fuzz，索引与同步类走合约验证，性能类只做回归比对。
