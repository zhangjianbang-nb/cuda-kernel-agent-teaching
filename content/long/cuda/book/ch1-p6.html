一 · 从“跑分”到“时间账本”：profile 是 agent 的观测接口

把硬件反馈接进 agent 回路，第一步不是选工具，而是定义观测对象。kernel 的墙钟时间是一个标量，对优化决策几乎无信息量；agent 需要的是可归因的时间账本：哪一段指令流在等、等什么、等了多久，以及这段等待是否属于可优化域。因此 profile 的输出必须结构化到“指令级或 warp 级事件 + 计数 + 采样位置”，而不是一张汇总表。工程上通常分三层：roofline 层给出理论上限与瓶颈类别（算力受限还是带宽受限），warp stall 层给出调度器视角的停滞原因分布，SASS 层给出具体指令与访存模式。三层之间是包含关系而非替代关系——roofline 判断“值不值得优化”，stall 判断“卡在哪类资源”，SASS 判断“改哪条指令”。

代价必须写进口径：NCU 采集 stall 采样会引入额外 replay，kernel 被多次重放，单次采集的时延可达原 kernel 的数倍到数十倍；采集的 metric 集合越大，重放次数越多。这直接约束 agent 的调用预算——如果每轮 RL 都做全量 NCU，采样开销会淹没训练吞吐。可行做法是分级采集：快速轮只取 roofline 所需的 DRAM 吞吐与 SM 利用率两个比率，深挖轮才开 stall 与 SASS 源关联。另一个代价是编译时间：要拿到带行号关联的 SASS，需要 `-lineinfo` 编译，这会增大二进制体积并轻微影响寄存器分配，agent 必须在“可观测性”和“最终发布二进制”之间区分两个构建产物。

具体例子：一个 elementwise 的 fp16 向量加，roofline 显示 DRAM 吞吐已接近峰值带宽的九成，SM 利用率却很低。此时 agent 若继续在指令调度上做文章就是方向错误——瓶颈在访存，正确动作是检查向量化宽度与合并访问，而不是减少指令数。这个判断只靠墙钟时间做不出来，靠 stall 分布也只能看到“等内存”，必须叠加 roofline 的带宽上限才有决策意义。

二 · roofline 作为可解域的前置筛子

roofline 在 agent 流水线里的位置很特殊：它不是优化手段，而是准入判据。给定目标 GPU 型号与软件栈版本，agent 可以先算出任务的算术强度，再对照峰值算力与峰值带宽，得到该任务的理论最优时间下界。若现有手写实现已经贴近下界，这个任务就不该进入 agent 可解域——不是 agent 不行，而是没有优化空间，强行让 agent 去“优化”只会产出噪声奖励。这与任务分类法的口径直接咬合：elementwise 与 reduction 大多落在带宽受限区，matmul 与 attention 落在算力受限区，fused 任务则要看融合后算术强度的迁移方向。

机制上，agent 侧应实现一个轻量 roofline 估算器：输入 shape、dtype、算子语义，输出 FLOPs 与最少字节数，再乘以目标 GPU 的峰值参数。注意字节数要按“必须发生的访存”计，而非按实现细节计——中间结果若能留在片上就不计入 DRAM 流量。这个估算器本身有误差来源：峰值算力对不同精度不同（fp16 与 fp32 的峰值差异显著），峰值带宽受 ECC 与访问模式影响，因此估算结果应作为区间而非点值使用，agent 的判据是“实现落在下界的多少倍以内”，而不是“是否等于下界”。

代价体现在误判成本上：把本已接近 SOL 的任务放进可解域，agent 会消耗大量采样预算去追逐不存在的收益，最终以“无显著加速”收场，污染多轮 RL 的奖励分布；反过来把有空间的任务筛掉，则损失真实收益。因此筛子要保守——宁可放进少量无空间任务，也不要漏掉高空间任务，因为前者的代价是算力预算，后者是机会成本。具体例子：一个 batch 很小的 layernorm，算术强度低，roofline 判定为带宽受限，且现有实现已用上向量化访存，agent 应直接标记为“无可解空间”，把预算让给同批中算术强度更高的 fused 算子。

三 · warp stall 分布：把“等”拆成可行动的原因

stall 采样的价值在于它把“慢”分解成调度器可观测的原因：等内存依赖、等指令发射、等屏障、等数学流水线、等分支解析等。agent 拿到的是每个 stall 原因的采样计数占比，而不是绝对时间。这里有一个必须写进口径的陷阱：采样计数占比不等于时间占比，因为不同 stall 原因下 warp 被换出的行为不同；但作为相对排序信号，它足以指导 agent 选择下一步动作。工程上应把 stall 分布与 roofline 联合解读：带宽受限任务里“等内存”占主导是预期内的，此时要看的是访存效率而非消除等待；算力受限任务里若“等数学流水线”占比高，说明指令级并行不足或存在长依赖链。

伪代码思路：agent 的动作选择可以写成一个规则表，输入是（roofline 判定类别，top-2 stall 原因，occupancy 水平），输出是候选变换集合。例如判定为算力受限且 top stall 为数学流水线等待，候选动作包括增加独立累加链、调整 tile 尺寸以提高 ILP；判定为带宽受限且 top stall 为内存依赖，候选动作包括改变数据布局、提升向量化宽度、检查是否发生分区冲突。规则表不是硬编码优化，而是把 profile 信号映射为搜索方向，具体变换仍由 agent 生成并验证。

代价在于采样分辨率与扰动：stall 采样是统计性的，短 kernel 上采样点不足，分布不稳定，agent 可能被噪声误导；长 kernel 上采样开销又推高单轮时延。折中做法是对 kernel 做多次重放取聚合，或在 kernel 内部用二进制插桩打点，以低开销获得确定性计数。具体例子：一个 reduction kernel 的 stall 分布显示屏障等待占比异常高，agent 据此判断块内归约的同步粒度过细，改为两级归约并增大每线程处理元素数，屏障次数下降，stall 分布随之迁移——这个迁移本身可以作为“优化是否生效”的辅助信号，而不必等最终时延。

四 · SASS：从源码意图到真实指令流

源码层面的优化意图经常在编译后失真：编译器会重排、合并、展开，寄存器压力导致溢出，向量化被拆解。agent 若只看 CUDA C++ 或 Triton 源码，就无法解释 profile 里观察到的现象。SASS 层的作用是提供“真实执行了什么”的证据链：指令序列、寄存器使用、访存指令宽度、谓词与分支结构。把 SASS 与源码行号关联（依赖 `-lineinfo`），agent 才能定位到具体语句对应的指令块，进而判断某段 stall 是否由该语句引起。

机制上，agent 需要的不是完整 SASS 反汇编文本，而是结构化摘要：每个基本块的指令数、访存指令占比、寄存器峰值、是否存在本地内存溢出（local memory 访问意味着寄存器溢出到栈，是明确的性能损失信号）。这些摘要可以由工具链解析生成，作为 profile 的附加上下文注入 agent。注意 token 代价：完整 SASS 文本对长 kernel 可达数千行，直接塞进上下文会挤占推理预算；摘要化是必须的工程约束，只保留与 stall 热点关联的基本块。

正确性代价同样存在：SASS 是目标架构相关的，同一份源码在不同 GPU 型号与软件栈版本上生成的指令流不同，agent 学到的“某指令模式导致 stall”的结论不能跨架构迁移。因此 SASS 反馈必须与目标 GPU 型号绑定记录，作为该型号下的局部知识，而不是全局规则。具体例子：一个 matmul kernel 在 profile 中显示高寄存器压力，SASS 摘要揭示存在本地内存溢出，agent 据此缩小 tile 尺寸以降低寄存器需求，溢出消失，occupancy 回升——这个因果链只有在 SASS 层才闭合。

五 · 二进制插桩：低开销的确定性计时

采样类工具的共同弱点是统计性，而 agent 的多轮迭代需要可复现的信号。二进制插桩提供了另一条路径：在编译产物中插入计时或计数指令，在 kernel 内部对特定区段做确定性测量。典型做法是利用 GPU 侧的时钟计数器在基本块边界打点，把每个区段的周期数写入全局缓冲区，kernel 结束后回读。相比 NCU 重放，插桩的运行时开销主要来自打点本身与缓冲区写入，量级远低于全量 replay，但会轻微扰动指令调度，且需要预留缓冲区显存。

代价要明确：插桩改变二进制，测到的是“插桩后的 kernel”，与发布版本不完全一致；打点密度越高，扰动越大，且缓冲区写入本身可能成为新的带宽消耗。因此插桩适用于定位而非验收——用它找出时间花在哪个区段，再用未插桩版本做最终性能判据。另一个代价是显存：每线程或每 warp 的打点记录会累积，需要按采样率稀释，否则缓冲区规模随线程数线性增长。

具体例子：一个 attention 的 fused kernel 在采样 profile 中 stall 分布弥散，难以归因。agent 改用插桩，在 QK 乘法、softmax 归一化、PV 乘法三个区段边界打点，得到三段周期数占比，发现 softmax 段占比远超预期，于是把优化方向锁定在归约与数值稳定性处理上，而不是继续在矩阵乘法 tile 上搜索。这个判断在采样数据里是隐性的，插桩把它变成了显式账本。

六 · 反馈回路的口径：什么信号进奖励，什么只进上下文

硬件反馈进入 agent 回路时有两条通道，混淆这两条通道是常见工程错误。第一条是上下文通道：roofline 判定、stall 分布、SASS 摘要、插桩区段账本作为观察注入，帮助 agent 决定下一步动作，但不直接产生奖励。第二条是奖励通道：只有可复现、与最终验收口径一致的量才进奖励，即正确性 oracle 的通过与否、以及按既定判据（相对基线加速比、SOL 占比、端到端时延）测得的性能。把 NCU 的某个 metric 直接写进奖励，会让 agent 去优化 metric 而非优化 kernel，这是典型的指标劫持。

机制上应做信号分级：一级信号是最终时延与正确性，进奖励；二级信号是 SOL 占比与 roofline 判定，用于可解域筛选与早停；三级信号是 stall、SASS、插桩账本，仅进上下文，用于动作选择。分级的好处是奖励分布稳定，不受采样噪声污染；代价是 agent 在早期只能靠三级信号摸索，收敛慢于直接把 metric 当奖励的做法，但避免了后者带来的口径漂移。另一个代价是上下文长度：三级信号注入会占用推理 token，需要摘要化与按需检索。

具体例子：某轮 agent 通过插桩发现屏障等待是热点，改了归约结构，stall 分布改善但最终时延未变——因为瓶颈已迁移到访存。若把 stall 改善写进奖励，agent 会误以为成功；按分级口径，这轮应记为“无性能收益”，但插桩账本保留在上下文里，指导下轮转向访存优化。这个区分决定了多轮迭代是否在追逐真实收益。

信号层典型内容用途主要代价
一级最终时延、正确性 oracle 结果奖励、验收测量噪声需多次取中位
二级SOL 占比、roofline 判定可解域筛选、早停峰值参数误差导致区间估计
三级stall 分布、SASS 摘要、插桩账本仅上下文、动作选择采样开销、token 占用、架构绑定

落到工程判断上：agent 看见时间去哪了，靠的不是某一个工具，而是三层观测的联合约束——roofline 划定可行域，stall 指出资源类别，SASS 与插桩闭合因果链；而这三层能否进奖励，取决于它们是否与最终验收口径同构。不同构的信号只做上下文，这条边界一旦松动，多轮 RL 的奖励就会偏离真实性能。

硬件反馈的观测边界：agent 能看见什么、看不见什么

roofline、warp stall 采样、SASS 反汇编与二进制插桩共同构成 agent 的“时间去向”观测栈，但它们各自有明确的失效条件。roofline 只回答“理论上还剩多少余量”，对 memory-bound 与 compute-bound 的判定依赖实测带宽与峰值算力口径，一旦 kernel 处于混合受限或受 L2/占用率间接约束，roofline 给出的 SOL 占比会把瓶颈归错类；此时 agent 若据此选择优化方向（例如盲目加大 tile 以提升算术强度），会撞上寄存器溢出或 occupancy 崩塌。warp stall 采样是统计性的：NCU 以固定采样周期收集 stall reason 分布，短 kernel 或低占用 kernel 的样本量不足，stall 占比的置信区间宽到无法区分“等内存”与“等 barrier”，agent 据此改代码等于在噪声上做梯度。

代价体现在观测本身改变被测对象。二进制插桩（如 SASS 级 instruction-level 计时或注入计数器）会引入额外指令与寄存器压力，改变 warp 调度与 cache 行为，测得的时延不能直接作为验收口径；NCU 的 replay 机制对同一 kernel 多次重放以收集不同指标集，重放期间 cache 状态被重置，跨 replay 的指标不可简单相加。SASS 反汇编能揭示编译器是否把循环展开、是否生成冗余的 predicate 或 shared memory bank conflict 模式，但 SASS 与源码之间没有稳定映射，agent 难以把一条低效指令归因到某一行 Triton/CuTe 代码，除非同时保留 PTX 中间层做对齐。工程判断是：把 profile 输出当作“假设生成器”而非“结论”，要求 agent 每次优化前声明预期改善的指标（如 stall_long_scoreboard 占比下降），优化后用同一口径复测，指标未动即回滚。

$$\text{可观测性代价} = \frac{\Delta t_{\text{instrumented}} - \Delta t_{\text{clean}}}{\Delta t_{\text{clean}}} + \frac{C_{\text{replay}} \cdot N_{\text{metric sets}}}{B_{\text{profiling budget}}}$$

具体例子：一个 reduction kernel 在 roofline 上显示 SOL 占比尚有余量，但 NCU 显示 stall 集中在 barrier 与 short scoreboard，说明瓶颈是块内同步粒度而非带宽；agent 若按 roofline 提示去调大 block size，反而拉长 barrier 等待。正确做法是先用 SASS 确认是否存在跨 warp 的冗余 shared memory 往返，再决定是否改用 warp-level reduction。这类判断无法由单一指标给出，必须把 roofline 的“余量”与 stall 的“归因”交叉验证，并把插桩开销计入验收口径的时延预算，否则 agent 会把观测噪声当成优化收益。
