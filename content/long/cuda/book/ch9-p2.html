一 · 基准不是一把尺子，而是一组带约束的坐标系

把“快”翻译成可复核的数字，第一步不是跑分，而是先把坐标系钉死：同一份 kernel 在不同基准下可以得出互相矛盾的结论，原因往往不在 kernel，而在基准的输入分布、基线选择和计时边界。本卷面对的基准至少分三层，每层的语义完全不同，混用就会得出“微基准 1.8x、端到端 4%”这类看似矛盾实则必然的结果。第一层是算子级微基准（KernelBench 系及其派生），它固定 shape、dtype、布局，只测单次 launch 的 device 时间；第二层是模型级基准，把 kernel 嵌进完整前向/解码循环，测的是端到端时延与吞吐；第三层是业务级基准，带真实请求分布、批大小波动、KV cache 压力与并发形态。三层的可比性只在“同一层内部”成立，跨层比较必须显式声明折算假设。

可复核性的核心机制是“口径三元组”：每个数字必须同时携带 (基准层, 基线, 计时方法)。缺任何一项，数字就退化为不可审计的宣传材料。计时方法上，微基准用 CUDA event 包住足够多次迭代取中位数并扣除 launch 开销；模型级用带 warmup 的稳态窗口，明确是否包含 host 侧调度与同步点；业务级则必须声明是否含排队时间。一个具体例子：同一份 fused LayerNorm+残差 kernel，在固定 shape 微基准下相对 PyTorch eager 基线是 1.8x，但嵌进 vLLM 的 decode 路径后，端到端只贡献 4%，因为该路径的时间大头在 attention 与采样，且新 kernel 引入了额外的布局转换。这不是 kernel 变慢了，而是坐标系换了。

$$\text{可复核加速比} = \frac{T_{\text{base}}(\text{层},\ \text{shape},\ \text{dtype})}{T_{\text{cand}}(\text{同层},\ \text{同 shape},\ \text{同 dtype})},\quad \text{附：计时边界、warmup 次数、同步点位置}$$

代价在这里体现为“口径税”：每增加一层基准，就要多维护一套输入生成器、一套基线快照和一套容差配置，编译与回归时间随之上升；业务级基准还需要真实流量回放设施，其存储与调度成本远高于微基准。工程判断是：微基准用于筛选候选与定位 roofline 差距，模型级用于确认集成后不退化，业务级只用于上线前的收益归因，三者不可互相替代。

二 · 基线必须是“可替换的那一个”，而不是“最弱的那个”

基线选择决定了加速比的分母，也决定了这个数字是否对业务有意义。常见错误是拿手写 naive CUDA 或未优化的 Triton 当基线，得出漂亮的倍数，但生产环境里真正会被替换的是框架内已高度优化的实现——PyTorch 的 cuBLAS/cuDNN 路径、TensorRT 的融合引擎、vLLM 的 paged attention kernel。因此基线必须满足“可替换性”约束：它在生产栈中真实存在、真实被调用、且替换后不改变数值语义。基线还应带版本快照，因为框架升级会悄悄改变分母。

机制上，基线分三类并各自绑定用途：框架基线（PyTorch eager / compile、TensorRT、vLLM 默认路径）用于端到端收益归因；硬件基线（同一 GPU 上的 cuBLAS 或厂商库最优实现）用于判断是否已接近 SOL；历史基线（上一版上线 kernel）用于回归测试与灰度对比。三类基线不能混算：对框架基线 1.8x 不代表对硬件基线也 1.8x，后者往往只剩很小的空间，这正是 roofline 分析要回答的问题。

基线类型用途失效模式代价
框架基线端到端收益归因框架版本漂移导致分母不可复现需锁定版本与配置快照
硬件基线判断 SOL 余量库实现随驱动更新变化需固定驱动与库版本
历史基线灰度与回归对比旧 kernel 已不适配新 shape 分布需保留旧二进制与回滚路径

正确性代价与基线绑定：替换基线意味着重新验证数值等价，容差必须按 dtype 与算子语义设定——fp32 归约类可用较紧的相对误差，fp16/bf16 需放宽并配合 ULP 检查，涉及 softmax 或 layernorm 的统计量还要检查极值样本。一个具体例子：把 attention 的基线从 PyTorch SDPA 换成 vLLM paged kernel 后，同一候选 kernel 的“加速比”从 1.8x 掉到 1.1x，因为后者已经做了 KV 分页与连续批处理；这个 1.1x 才是集成路径上真实的替换收益。

三 · 硬件与 dtype 是口径的一部分，不是背景参数

同一个 kernel 在 A100 与 H100 上的 roofline 位置不同，在 fp32 与 bf16 下的瓶颈也不同，因此“硬件 + dtype”必须写进数字本身，而不是放在脚注里。机制上，把硬件抽象为三个可测参数：峰值算力（按 dtype 区分）、HBM 带宽、以及片上缓存/SMEM 容量；把 dtype 抽象为字节宽度与累加精度策略。候选 kernel 的算术强度 I = FLOPs / Bytes 与机器的 Ipeak = 算力 / 带宽 比较，决定它落在计算密集区还是带宽密集区，这直接决定优化方向与可达加速上限。

$$I = \frac{\text{FLOPs}}{\text{Bytes moved}},\qquad \text{可达时间下界} \approx \max\left(\frac{\text{FLOPs}}{\text{Peak}_{\text{dtype}}},\ \frac{\text{Bytes}}{\text{BW}}\right)$$

dtype 的选择同时是性能决策与正确性决策：bf16 把带宽需求减半、把 tensor core 吞吐翻倍，但引入的舍入误差会改变归约顺序敏感的结果；fp8 进一步压缩带宽，却需要 per-tensor 或 per-channel scaling，且对离群值极其敏感。工程上必须把 dtype 与容差成对记录：同一候选在 bf16 下达标、在 fp8 下超差，就是不可上线的组合。代价是显存的权衡：KV cache 用 fp8 可显著降低显存占用、提升可容纳批大小，但需要额外的量化/反量化 kernel，其 launch 开销在 decode 阶段的小 batch 下可能吃掉收益。

具体例子：一个带宽密集的 elementwise 融合 kernel，在 fp32 下受 HBM 带宽限制，实测接近带宽下界；改成 bf16 后理论时间减半，但因为输出需要转回 fp32 供下游消费，额外的转换 kernel 使端到端收益远小于 2x。这说明 dtype 口径必须覆盖“转换成本”，否则数字只在孤立 kernel 内成立。硬件侧同理：为 H100 调的 TMA/异步拷贝流水，迁到 A100 上可能因缺少对应指令而退化，因此硬件口径要绑定具体的 SM 架构代际，而非笼统的“同代 GPU”。

四 · 指标分层：device 时间、端到端时延、吞吐与成本各自回答不同问题

“快”在不同指标下含义不同，可复核的前提是每个指标都有明确的分子分母与采集点。device 时间回答“这个 kernel 本身多快”，由 CUDA event 或 NCU 采集，不含 host 调度；端到端时延回答“用户等多长时间”，包含排队、调度、同步与框架开销；吞吐回答“单位时间处理多少请求”，与批大小和并发强相关；成本回答“每单位产出花多少卡时”。四者之间不存在单调映射：kernel 变快可能因占用 SM 资源更多而降低并发吞吐，也可能因引入同步点而拉高端到端时延。

机制上，收益归因需要把端到端时间拆成可加的分项：kernel 时间占比、框架开销、数据搬运、同步等待。只有当候选 kernel 替换后，其所在分项的下降能被端到端观测到，收益才算成立。一个具体例子正是故事映射里的情形：微基准 1.8x 的 kernel 在端到端只贡献 4%，归因拆解后发现该 kernel 仅占端到端时间的 2.2%，且新 kernel 引入了一次 device-host 同步，抵消了部分收益。这个拆解把“4%”从可疑数字变成了可解释数字。

$$\text{端到端收益} = \frac{\Delta T_{\text{kernel}}}{T_{\text{e2e}}} - \frac{\Delta T_{\text{overhead}}}{T_{\text{e2e}}},\qquad \text{仅当第二项}\ll\text{第一项时收益可复现}$$

代价体现在采集本身：NCU 全量 profile 会带来显著减速与额外显存，不适合在生产流量下常态开启；端到端 A/B 需要双路部署或流量切分，占用额外容量；吞吐指标需要稳定负载才能复现，短时压测的方差会掩盖真实差异。工程判断是：device 时间用于筛选，端到端时延用于准入，吞吐与成本用于容量规划，三者分别对应不同的复核频率与不同的置信要求。

五 · 把数字变成可复核资产：快照、容差与回归门禁

可复核的数字不是一次测量，而是一份可重放的资产。机制上，每个基准结果应绑定四要素快照：输入生成种子与 shape 分布、基线二进制与版本、硬件与驱动、dtype 与容差配置。缺少任一要素，数字在下次回归时就无法判定“变慢是 kernel 退化还是环境漂移”。回归门禁据此设定：微基准允许的退化阈值较紧（因为方差小），端到端允许的阈值较宽（因为受流量与调度影响），但两者都必须有明确的拒绝条件，而不是靠人工目测。

正确性门禁与性能门禁必须同源：同一个候选 kernel 只有在容差内通过数值校验，其性能数字才被接纳；否则加速比再高也不进入对比表。代价是编译与测试时间：为每个候选维护多组 shape 与 dtype 组合会线性放大回归时长，因此实践中按热点 shape 采样并加权，而不是全量枚举。一个具体例子：某融合 kernel 在 4096 序列长度下达标，但在 128 的短序列下因 launch 开销占比过高而退化，回归门禁若只覆盖长序列就会漏掉这个退化，灰度阶段才暴露。

工程判断落在“口径冻结”上：一旦某条基准被用于上线决策，其基线、shape 集合与容差就应冻结并版本化，任何变更都要走显式的口径变更流程，并重跑历史对比。这样，“快”才从一次性的测量变成可审计、可回滚、可跨团队复核的数字。

口径失效的三种边界：微基准 1.8x 只换来端到端 4% 时，数字还剩下什么

本卷把「快」翻译成可复核数字的第一道关口，不是选哪个基准，而是承认基准与生产之间存在一条不可消除的换算损耗。故事里微基准 1.8x、端到端 4% 的落差不是测量错误，而是口径边界本身：KernelBench 系基准测的是单 kernel 在固定 shape、固定 dtype、无并发、无框架开销条件下的稳态时延；生产测的是包含 launch 开销、算子间同步、显存分配、框架调度与请求排队的端到端链路。两者之间隔着 Amdahl 放大器的倒数。设热点 kernel 原耗时占端到端比例为 $$f$$，kernel 自身加速比为 $$s$$，则端到端加速比上界为

$$S_{e2e} \le \frac{1}{(1-f) + f/s}$$

代入 1.8x 与 4% 反推，$$f$$ 必须落在个位数百分比量级——这意味着该 kernel 在真实负载里根本不是热点，微基准的「快」在归因表上被稀释成了噪声。这条公式的工程价值在于它是可复核的：只要在 NCU 或框架 profiler 里取到 $$f$$ 的实测值，就能在候选筛选阶段预先否决掉一批「微基准漂亮、端到端无感」的 kernel，而不必等到灰度上线才发现。代价是 profiler 本身引入的观测开销会扰动 $$f$$ 的测量，尤其在小 batch 高并发场景下，采样粒度与请求到达率的耦合会让 $$f$$ 在多次测量间漂移，因此归因表必须标注测量条件而非给一个裸数字。

第二类边界是精度容差与 dtype 口径的不可通约。微基准通常在 fp32 或 fp16 下验证正确性，生产链路却可能因框架默认 autocast、TensorRT 的层融合重排或 vLLM 的 paged attention 路径而实际运行在 bf16 甚至 fp8 上。此时「1.8x」对应的数值语义与生产不同：bf16 的尾数位宽缩减会让某些归约类 kernel 的相对误差跨过业务容差阈值，而微基准的 correctness oracle 若只比对 fp32 参考实现的绝对误差，就检测不到这种口径漂移。可复核的做法是把容差写成与 dtype 绑定的三元组（参考 dtype、运行 dtype、允许的相对误差与绝对误差上限），并在候选筛选阶段用生产实际 dtype 重跑一遍 oracle，而不是复用微基准的通过结论。系统代价是这轮重跑会把每个候选的验证 token 与编译时间翻倍——Triton 与 CuTe 候选需要针对目标 dtype 重新 autotune，PTX 手写路径则需要重新核对指令选择，这部分开销必须计入筛选预算而非事后补测。

第三类边界是硬件与集群核算口径的错位。单卡微基准的加速比在集群上会被通信、负载不均衡与调度抖动重新定价：一个在单卡上把 kernel 时间压到极限的方案，若改变了 kernel 的显存占用或 occupancy，可能挤占同一 SM 上并发的其他请求，使集群吞吐不升反降。因此归因表必须同时保留单卡时延口径与集群吞吐口径两列，并明确回滚阈值绑定在哪一列上。下表给出本卷要求的最小口径字段，缺任一列的数字都不可复核：

字段微基准口径生产口径失效条件
时延单 kernel 稳态端到端含排队f 低于个位数百分比
dtype固定 fp32/fp16框架实际 autocast容差未随 dtype 重标定
核算单位单卡集群吞吐/成本occupancy 挤占并发请求

把这三类边界写进口径文档，等价于承认「快」是一个带条件的谓词：1.8x 只在「该 kernel 是热点、dtype 未漂移、单卡无并发挤占」三个条件同时成立时才可复核地翻译成收益。工程判断落在候选筛选阶段就该用端到端 $$f$$ 与生产 dtype 做一次预否决，而不是让微基准的漂亮数字直接进入灰度队列——故事里 4% 的落差，本质是筛选阶段少做了一次口径换算。
