一 · 从一个被排队拖死的算子优化任务说起

设想一个团队要把一个 LayerNorm 加残差融合的 kernel 从 Triton 版本换成手写 CUDA，目标是端到端推理延迟下降。算子本身不难，难点在于验证：候选 kernel 要在 7 个 shape 组合、3 种 dtype、2 档 GPU 上跑正确性比对与性能采集，每个组合至少重复 30 次以压住测量噪声，每次重复还要跑一遍 NCU 采集关键指标。粗算下来，一个候选版本的完整评测是数百个 GPU 任务、每个任务几十秒到几分钟量级。当 agent 每天产出几十个候选时，评测集群的排队长度会迅速超过单次评测的执行时间，迭代节奏从“以小时计”退化为“以天计”。这个场景就是本卷的起点：不是 kernel 写不出来，而是**验证一个 kernel 的代价**成了系统瓶颈。

本卷要回答的问题可以收敛成一句话：在给定预算下，如何为“生成—优化—验证—部署”这条链路分配 GPU 容量，并让每一份容量的边际收益可计算。它不讨论怎么写出更快的 kernel，也不讨论奖励函数怎么设计，而是讨论这些环节各自吃掉多少卡时、这些卡时如何换算成端到端收益、以及在峰值与均值之间如何做预留决策。

二 · 上一卷留下的三个缺口

第 3 卷建立了可信评测流水线：正确性 oracle、重复测量、统计置信区间、profile 采集规范。第 7 卷建立了多轮 RL 的奖励与训练循环。第 9/10 卷建立了生产侧的替换与灰度路径。三者各自自洽，但拼在一起时留下三个未被回答的缺口。

  • 缺口一：评测的置信度是有价格的。第 3 卷说“多重复几次更可信”，但没有说多重复一次要花多少 GPU 分钟，也没有说在固定预算下应该把重复次数花在哪些 shape 上。置信区间宽度随重复次数按 1/√n 收缩，而成本按 n 线性增长，这意味着“把噪声压一半”要付四倍成本——这个交换率从未被量化。
  • 缺口二：RL 训练与评测争抢同一批卡。第 7 卷的 rollout 需要大量并行采样，第 3 卷的评测需要低噪声的独占测量，两者的资源画像完全不同：前者吞吐优先、可容忍抖动，后者时延与隔离优先、对同卡邻居敏感。共享集群还是物理隔离，是一个容量问题而非框架问题。
  • 缺口三：生产侧收益无法回溯到训练侧成本。第 9/10 卷能说清某个 kernel 替换让线上 QPS 容量提升多少，但说不清为了得到这个 kernel，前面烧掉了多少卡时的评测与 RL。没有这个回溯，“每 1% 端到端提升值多少卡时”就无法成为投资决策依据。

这三个缺口的共同点是：它们都不是算法问题，而是**计量问题**。缺一个把 GPU 分钟、卡时、采集开销统一到同一坐标系里的成本模型。

三 · 本卷的赌注：成本可分解、收益可归因

本卷押注两件事。第一，单任务评测成本可以被分解为可预测的项，而不是一笔糊涂账。第二，端到端收益可以被归因到具体 kernel，从而让成本与收益在同一单位下比较。若这两条成立，容量规划就从“拍脑袋按峰值留 2 倍”变成可优化的配比问题；若不成立，本卷的方法退化为粗略的经验系数。

成本分解的基本式如下。设一次候选评测包含 S 个 shape 组合、R 次重复、P 次 profile 采集，单次执行耗时 t_exec，单次 profile 采集额外耗时 t_prof，排队与调度开销系数为 α（含镜像拉取、环境初始化、结果回收）：

$$C_{\text{eval}} = S \cdot \big[ R \cdot t_{\text{exec}} + P \cdot t_{\text{prof}} \big] \cdot (1+\alpha)$$

这个式子看起来平凡，但它把“置信度”和“成本”放进了同一个表达式：R 进入线性项，而置信区间半宽按 1/√R 收缩。于是“把误差带压到原来的 1/2”对应 R 变为 4R，成本变为约 4 倍。工程判断由此变得具体：当测量噪声已经小于候选之间的真实差距时，继续加 R 是纯浪费；当噪声大于差距时，加 R 比加 S 更划算，因为 shape 维度的边际信息量在覆盖度足够后迅速衰减。

代价方面，这个模型本身有采集成本。α 不是常数：容器冷启动、驱动初始化、CUDA context 建立在不同集群上差异显著，且会随并发度上升而恶化。经验上，当评测任务并发度接近集群 GPU 数时，α 会因排队与上下文切换明显抬升，模型预测开始偏低。这就是为什么本卷坚持把排队时间单列，而不是塞进 α 里——排队是容量信号，不是效率损失。

具体例子：若某候选的 S=7、R=30、P=1，t_exec 取分钟量级、t_prof 取十秒量级，则单候选评测落在“数十 GPU 分钟”这个量级；agent 每天产出几十个候选时，日需求就是“上千 GPU 分钟”，这已经接近一个小型评测集群的全天可用容量。此时瓶颈不在单任务效率，而在总吞吐。

四 · 容量规划的四个关键决策

本卷把容量问题拆成四个必须显式回答的决策，每一个都有明确的代价面。

决策选项 A选项 B主要代价
评测精度与成本少重复、宽置信区间多重复、窄置信区间误判率 vs GPU 分钟
RL 与评测是否共享集群共享，提高利用率隔离，保证测量隔离性测量噪声 vs 闲置容量
容量预留口径按峰值预留按均值预留 + 排队策略闲置卡时 vs 尾延迟
是否引入 spot 实例引入，降低成本不引入，稳定供给中断重跑 vs 单位卡时价格

第一个决策的机制是统计功效：在固定显著性水平下，要检测的最小可分辨差异 δ 与重复次数满足 δ ∝ σ/√R，σ 为单次测量标准差。若 σ 因同卡邻居干扰而翻倍，则达到同样 δ 需要 4 倍 R——这正是共享集群的隐性成本。第二个决策因此不是“利用率越高越好”，而是“评测任务的隔离性值多少卡时”。

第三个决策的核心是排队论直觉：按峰值预留意味着在均值时段大量卡闲置，按均值预留意味着峰值时段排队。排队对迭代的伤害是非线性的——单次评测从分钟级变成小时级，agent 的多轮循环就被拉长，单位时间内可探索的候选数下降。本卷主张把“排队时长”作为一等指标纳入容量模型，而不是只看 GPU 利用率。

第四个决策的代价是重跑：spot 中断会让长时评测任务作废，重跑成本等于已消耗卡时。对短任务（单次执行分钟级）影响可控，对包含大量重复与 profile 的长任务则可能吞掉价格优势。判断依据是任务时长分布与中断率的乘积，而非单价本身。

五 · 单位收益成本：把生产收益折回卡时

本卷的产出指标之一是“每 1% 端到端提升的卡时成本”。它的构造方式是把生产侧容量变化折算成卡时等价物，再除以训练与评测侧的总消耗。设某 kernel 替换使线上单位请求的 GPU 时间下降 Δt，服务请求量为 Q，则释放出的容量等价卡时为 Δt·Q；设得到该 kernel 所消耗的评测卡时为 C_eval、RL 训练卡时为 C_rl，则：

$$\text{CostPer1\%} = \frac{C_{\text{eval}} + C_{\text{rl}}}{\Delta_{\text{e2e}}\%}$$

这个比值的作用不是给出一个绝对好坏，而是给出**边际判断**：当候选的预期提升递减而评测成本不变时，比值上升，说明继续在同一方向投入的回报在衰减，应转向新的算子族或降低评测精度要求。它同时暴露一个常见误判：把 RL 训练卡时算作沉没成本而不计入，导致“这个 kernel 很值”的结论建立在忽略前期投入之上。

具体例子回到开头的融合算子：若该替换让线上每请求 GPU 时间出现可测的下降，按请求量折算出的容量收益是可观的正数；但若为得到它跑了数十轮 RL、每轮都要对大量候选做完整评测，则分母中的评测卡时可能远大于分子中的容量收益。这时正确的工程动作不是继续调 kernel，而是先降低评测成本——减少低信息量 shape 的重复次数、把 profile 采集从每候选一次改为按需触发。这正是故事映射里“瓶颈在评测吞吐、团队重构资源配比”的含义：成本模型先揭示了瓶颈位置，容量调整才有依据。

六 · 成本模型的可信边界

本卷不承诺成本模型能精确预测每一个任务。它承诺的是：模型的结构正确，即各项成本可分离、可测量、可归因；系数需要按集群实测校准，且校准本身要计入成本。一个必须写进模型的不确定性来源是测量噪声与真实差异的比值——当候选间差异接近噪声底时，任何成本优化都只是在优化一个无法分辨的信号，此时应优先提升测量隔离性而非增加重复次数。

另一个边界是 profile 采集的侵入性：NCU 采集会串行化、复放 kernel、改变缓存状态，其耗时与目标 kernel 的访存模式强相关，不能用一个固定系数乘以执行时间。工程上应把 profile 采集视为独立成本项并按需触发，而不是默认对每个候选全量采集。这条判断直接决定了评测集群的容量需求是“执行主导”还是“采集主导”，两者的配比策略完全不同。

当评测队列成为迭代的隐形税：成本模型的边界与失效条件

以一个具体场景开场：团队把 kernel 替换接进一条在线推理服务，端到端延迟降了，但上线两周后容量告急——不是 GPU 算力不够，而是评测集群的排队把每一轮候选 kernel 的验证周期从小时级拖到天级，工程师在等结果，训练集群却在空转。成本模型要回答的正是这个错配：把“一次 kernel 候选的完整验证”折算成 GPU 分钟数，把“一次 RL 迭代的 rollout+评测”折算成卡时，再把生产侧 kernel 替换带来的容量变化折算成可预留的卡数。三者单位不同，必须先统一到同一资源口径，否则配比决策就是拍脑袋。设单任务评测耗时为 $$T_{\text{eval}} = n_{\text{rep}} \cdot (t_{\text{run}} + t_{\text{prof}}) + t_{\text{queue}}$$，其中 $$n_{\text{rep}}$$ 是重复次数、$$t_{\text{prof}}$$ 是 NCU/SASS 采集开销。这个式子的关键边界在于 $$t_{\text{queue}}$$ 不是常数：它随并发候选数非线性上升，一旦队列深度超过评测集群的吞吐拐点，重复次数带来的置信收益会被排队时延完全吃掉。

失效条件有三类，必须写进成本模型的假设栏而不是藏在附录里。第一，精度-成本权衡失效：少重复换低成本的前提是候选间方差可控；当 RL 采样温度高、候选 kernel 性能分布长尾时，低重复会把“偶发但真实”的加速比误判为噪声，此时节省的 GPU 分钟数以错误接受率为代价，而错误接受在生产侧表现为回滚成本，量级远超评测节省。第二，共享评测集群失效：RL 训练与评测共享集群在均值负载下划算，但训练侧的同步屏障会让负载呈脉冲式，评测任务被挤到低优先级后 $$t_{\text{queue}}$$ 的方差急剧放大，容量按均值预留必然在脉冲点排队。第三，spot 实例失效：spot 降低单位卡时成本，但抢占会打断 profile 采集，NCU 采集中断意味着该次测量作废、需整轮重跑，重跑概率乘以单次采集开销就是隐性成本，在长 profile 任务上尤其显著。

系统代价要按资源维度分开记账，不能合并成一个“总成本”数字。下表给出本卷成本模型的最小字段集，每一行都对应一个可观测的代价来源：

代价维度观测口径失效信号
评测时延单任务 GPU 分钟数（含排队）排队占比超过运行占比
训练卡时RL 迭代卡时 / 有效候选数单位有效候选卡时上升
profile 开销采集时长 / 总评测时长采集中断重跑率上升
生产容量kernel 替换后预留卡数变化峰值排队而非均值排队

回到开场场景：成本模型揭示瓶颈不在单次评测的 $$t_{\text{run}}$$，而在 $$t_{\text{queue}}$$ 与 profile 采集的耦合——团队重构资源配比，把评测集群从“与训练共享、按均值预留”改为“独立配额、按峰值排队策略预留”，并把 NCU 采集从每次候选全量采集改为分层采样。这里的工程判断是：成本模型的产出不是一张总账，而是一组带失效条件的配比约束；任何把 $$t_{\text{queue}}$$ 当常数、把 spot 抢占当零成本的模型，都会在脉冲负载下给出错误的容量结论，而错误的容量结论会以排队时延的形式重新计入下一轮迭代的成本。
