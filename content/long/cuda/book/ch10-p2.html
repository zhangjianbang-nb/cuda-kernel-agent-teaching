一 · 把“快”拆成可复核的四个坐标

“这个 kernel 比 baseline 快 2.3 倍”在工程上不是一个命题，而是一个省略了四个坐标的断言：相对谁（基线）、在什么硬件上、用什么 dtype、按哪个指标计。本卷的基准口径把这四项写成不可省略的元组 $$M = (B, H, D, Q)$$，其中 B 是基线实现，H 是硬件与驱动栈，D 是输入 dtype 与形状分布，Q 是量化指标（时延分位数、吞吐、SOL 占比、加速比）。任何一条 BI 记录若缺任一坐标，就不进入看板，只进草稿区。这不是形式主义：数值精度事故的复盘里，团队最初拿到的“加速比提升”恰恰来自一次 dtype 从 fp32 降到 bf16 的隐性变更，坐标 D 缺失让这条记录看起来是纯性能收益，直到线上告警把数值异常翻出来。口径的第一条工程判断是：**加速比必须与 dtype 绑定登记**，跨 dtype 的比值不进同一张分布图。

指标 Q 本身也要拆。时延用分位数而非均值，因为 kernel 时延分布长尾极重，均值会被少数超长样本拖动，掩盖大多数请求的真实体验；吞吐用单位时间完成的元素数或 token 数，需注明是否含 launch 开销；SOL 占比用 roofline 上界做分母，分子是实测有效带宽或有效算力。三者不可互相替代：一个 kernel 可以在均值时延上赢、在 p99 上输，也可以 SOL 占比高但绝对时延因形状太小而无意义。BI 看板因此对每个 kernel 版本同时保留 p50/p90/p99 时延、吞吐、SOL 占比与加速比五个字段，任何单一数字都不作为“快”的结论。

二 · 基线不是“原来的代码”，而是冻结的可执行契约

基线 B 最容易腐坏。工程上常见做法是拿仓库里当前那份实现当 baseline，但它会随重构漂移，导致历史加速比不可比。本卷要求基线以**冻结产物**形式存在：源码 commit、编译命令、编译产物哈希、运行配置（grid/block、共享内存用量、是否开 TF32）四件套一起入库，且与 kernel 版本表用同一套追踪键关联。基线一旦冻结，只允许在明确的口径变更记录下替换，替换时旧基线的全部历史指标打上“口径断点”标记，看板上以竖线分隔，禁止跨断点求均值。

冻结的代价是编译时间与存储：每个基线要保留一份可复现的编译产物，CI 里对基线做定期重编译校验，单次校验的编译开销按 kernel 规模可达分钟级，且需要与目标硬件架构匹配的 toolchain 镜像。这笔开销换来的是可复核性——任何一条“快 1.8 倍”的记录都能追溯到具体的二进制与运行配置，而不是一句“当时大概是这个版本”。伪代码层面的校验流程是：读取基线记录 → 校验产物哈希 → 在登记硬件上重跑固定形状集 → 比对指标是否落在记录的容差带内 → 不通过则标记该基线为“待复核”，其关联的加速比记录降级为不可引用。容差带本身要按指标分别设定，时延类用相对百分比，SOL 类用绝对百分点，避免用同一阈值粗暴套所有指标。

一个具体例子：某归约 kernel 的基线在开启 TF32 后矩阵乘路径变快，但同一份源码在关闭 TF32 的配置下数值行为不同。若基线记录只存源码不存配置，后续对比会把“配置差异”误读为“实现改进”。冻结契约把配置纳入哈希，这类误读在入库时即被拦截。

三 · 硬件与 dtype：口径里的两个隐形变量

硬件坐标 H 不只是 GPU 型号，还包括架构代号、SM 数量、显存带宽、驱动版本、CUDA/toolchain 版本，以及是否处于 MIG 切分或共享集群状态。同一 kernel 在两种架构上的 SOL 分母不同，加速比不可直接相乘或平均。BI 看板按 H 分组聚合，跨组只做排序不做汇总。共享集群状态下，邻居负载会污染时延测量，因此口径要求测量窗口内记录占用率与干扰标记，被污染的样本进隔离区而非主分布。

dtype 坐标 D 包含输入、累加器与输出三段，三者可以不同。fp16 输入配 fp32 累加是常见配置，但若基线用 fp32 全程而候选用 fp16 输入，加速比里混入了精度让渡，必须单独标注“精度等价性未验证”。本卷的口径把 dtype 变更视为**口径变更**而非优化，任何跨 dtype 对比都要附带数值一致性证据（相对误差上界或逐元素比对通过率），否则该记录只能出现在“探索”标签下，不能进质量 BI 的成功率统计。代价是显存与带宽：降低 dtype 通常减少显存占用与带宽压力，但也可能因累加精度不足引入数值异常，这正是精度事故的典型路径——性能指标好看，数值告警在后。

形状分布同样是 D 的一部分。固定一组代表性形状（小 batch、中等、长序列、极端不规则）作为标准形状集，任何加速比必须声明是在哪个子集上取得的。只在有利形状上赢的 kernel 不进主看板，进“形状敏感”附表。这条规则直接约束了 agent 的优化方向：奖励不能只看单一形状的时延，否则会诱导出对形状过拟合的实现。

四 · 指标的可复核性：从数字到证据链

可复核的数字需要三件东西：测量协议、原始样本、归约规则。测量协议规定预热次数、重复次数、同步方式、是否用 CUDA event 计时、是否剔除首次 launch 的上下文初始化；原始样本保留每次迭代的时延与占用率，不只看聚合值；归约规则明确分位数算法与置信区间。三者一起构成证据链，BI 看板上每个数字都可下钻到样本级。没有证据链的数字在事故复盘时无法自证，团队只能回到“当时跑过”的口头记忆。

归约规则里有一个容易忽略的代价：保留原始样本的存储与采样开销。全量保留会让测量数据量随迭代次数线性增长，因此口径要求按采样率保留，采样率本身是一个关键决策——采样过高拖慢评测流水线，采样过低则长尾分位数估计不稳。工程判断是：p99 类指标需要足够样本量才能稳定，采样率按目标分位数的置信需求反推，而不是拍一个固定百分比。这与监控采样率的决策同源，但评测侧的采样服务于统计有效性，监控侧的服务于开销约束，两者不能共用一套参数。

公式上，加速比定义为 $$S = \frac{T_{\text{base}}}{T_{\text{cand}}}$$，但分子分母必须来自同一形状子集、同一硬件分组、同一 dtype 配置、同一测量协议。SOL 占比定义为 $$\eta = \frac{\text{实测有效吞吐}}{\text{roofline 上界}}$$，上界按该硬件的带宽或算力峰值与该 kernel 的算术强度取小者。两个公式都只是定义，真正的工程含量在于分母的选取与样本的过滤规则——口径文档里写清楚哪些样本被剔除、为什么剔除，比公式本身更重要。

五 · 两套口径：团队看板与管理层看板的翻译层

同一批数据面向不同读者要有不同归约，但**底层证据必须同源**。团队看板按 kernel 版本、形状子集、硬件分组展开，展示 p50/p99 时延、SOL 分布、回退率与失败归因标签；管理层看板只保留成功率、加速比分布的中位数与尾部、回退率趋势，以及按业务线聚合的收益估计。两套口径的差异在聚合粒度与展示字段，不在原始测量。禁止为管理层单独跑一套“好看”的测量，否则两套数字对不上时，团队会失去对看板的信任。

翻译层的具体机制是字段映射表：团队侧的“加速比分布 p50”映射为管理层侧的“典型收益”，“p10”映射为“保守收益”，回退率映射为“稳定性风险”。映射表随口径版本号一起冻结，任何字段增删都要走变更记录。代价是维护成本：每次口径变更要同步更新两套看板的映射与历史断点，且要重跑受影响区间的聚合。工程判断是变更频率要低——口径不是越细越好，字段过多会让映射表本身成为腐坏源。一个具体例子：数值精度事故后新增“数值异常率”字段，团队侧按 kernel 与 dtype 展开，管理层侧只保留按业务线的汇总，两边同源，复盘时能直接对上告警时间线。

回退率的定义也要在口径里写死：是“候选版本指标劣于冻结基线的比例”，还是“线上版本相对上一版本的劣化比例”，两者含义不同，混用会让趋势图出现无法解释的跳变。本卷采用前者作为评测侧口径，后者作为生产侧口径，并在看板上以不同颜色区分，禁止合并成一条曲线。

六 · 口径落地的最小工程闭环

把上述坐标写成机器可校验的 schema，是口径从文档变成约束的关键一步。每条评测记录必须携带 B/H/D/Q 四元组与证据链指针，入库时做 schema 校验：缺坐标拒绝入库，跨 dtype 无一致性证据降级为探索标签，跨硬件分组求均值直接报错。校验器本身要版本化，口径变更时旧记录按旧版本解释，新记录按新版本写入，断点标记自动生成。这样 BI 看板的每个数字都能回答“按哪版口径、在哪个坐标下、由哪些样本归约而来”。

闭环的最后一环是失败归因标签与口径的对接：编译失败、数值失败、性能不达标、集成失败四类标签分别对应不同的坐标缺失模式——编译失败往往缺 toolchain 版本，数值失败缺 dtype 一致性证据，性能不达标缺形状子集声明，集成失败缺运行配置。归因树据此把失败样本分流到对应的口径补全任务，而不是笼统地记为“没跑通”。代价是评测流水线的时延增加：schema 校验与证据链写入会拉长单次评测的周转时间，工程上以异步校验与批量写入摊薄，但校验不可跳过——跳过校验的数字就是不可复核的数字，事故复盘时无法作为证据使用。

最终落在一条工程判断上：口径的价值不在于字段多，而在于**每个字段都能被机器拒绝**。能被拒绝的数字才可信，能被追溯的加速比才是收益。数值精度事故的教训不是“要多测”，而是“测出来的数字必须带着坐标与证据一起流动”，否则性能看板越漂亮，离线上真实行为越远。

口径的失效边界：当“快”被采样率与分位数反噬

本卷把“快”翻译成可复核数字的核心机制是双口径采样：运行时以固定间隔抓取 kernel 版本、配置哈希与耗时，离线按分位数聚合。失效条件首先出在采样率上——采样间隔大于 kernel 实际调用间隔时，短命 kernel 会被系统性漏采，加速比分布向长尾偏移；采样过密则引入可观测性开销，单次采集的时钟读取与环形缓冲写入会挤占 SM 周期，在微秒级 kernel 上直接改变被测对象。代价可写成可观测性税：

$$T_{\text{obs}} = \frac{n_{\text{sample}}}{n_{\text{call}}}\cdot c_{\text{probe}} + \frac{B_{\text{ring}}}{BW_{\text{host}}}$$
其中 $c_{\text{probe}}$ 为单次探针开销，$B_{\text{ring}}$ 为回传缓冲字节数。举例：一个每 3 微秒调用一次的小 kernel，若探针开销 0.4 微秒且每 10 次采一次，则税负约 1.3%，足以让“加速比 1.02”这类结论失去复核意义。

第二个边界是分位数口径本身。告警阈值取 P99 时，回退判定对样本量敏感：同一配置在 200 次调用下 P99 由排序尾部两三个点决定，跨批次抖动可达数十个百分点；取均值则被少数超长尾调用拉偏，掩盖中位数层面的真实回退。工程判断是双指标并列——均值用于容量规划，P50/P90 用于版本对比，且规定最小样本量门槛，低于门槛只记录不告警。代价是告警延迟：门槛抬高后，一次真实数值异常要积累到足够样本才触发，期间错误结果已流入下游。

口径失效场景系统代价
固定间隔采样短命 kernel 漏采探针税、缓冲带宽
P99 阈值小样本尾部抖动误告警、回滚抖动
均值阈值长尾掩盖中位数回退漏告警、事故滞后

第三个边界是硬件与 dtype 口径的不可比性。同一 kernel 在 FP32 与 TF32 下的 SOL 分母不同，跨 dtype 直接比较加速比会把精度降级误读为性能收益；跨代硬件上带宽与缓存层级变化使 roofline 拐点漂移，历史基线必须绑定硬件指纹而非型号名。对应故事中的数值精度事故正是此类失效：告警由 P99 耗时回退触发，而归因树最终定位到 dtype 切换导致的数值异常，说明性能口径与正确性口径必须同源采样、同一配置哈希下对齐，否则 BI 看板的加速比分布只是自洽的幻觉。
