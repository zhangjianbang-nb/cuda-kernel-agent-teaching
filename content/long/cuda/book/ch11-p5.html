一 · 脚手架不是单体：四个角色的接口与失效面

把“agent 生成 kernel”当成一个模型调用是错的。工程上它至少是四个可独立替换、独立计费、独立失效的组件：coder（产出候选源码与编译单元）、judge（正确性 oracle 与容差判定）、profiler（采集 NCU/SASS 与计时）、search（在候选空间上做选择与调度）。四者的接口必须窄到可以序列化：coder 输出 (源码, 编译命令, 输入形状, dtype, 期望语义)；judge 输出 (通过/失败, 最大绝对误差, 失败样本索引)；profiler 输出 (kernel 时延分布, 带宽利用率, 指令计数, stall 原因直方图)；search 只消费前三者的结构化结果，不读源码文本。这个约束的直接收益是：judge 与 profiler 可以被缓存和复用，同一份候选在不同 search 策略下不必重跑 GPU。

失效面各不相同，混在一起会让成本归因失真。coder 的典型失效是编译失败与语义漂移（把 reduce 写成 atomic 累加导致非确定性）；judge 的失效是容差过松放过数值错误、过紧误杀合法实现；profiler 的失效是采样扰动改变被测 kernel 的行为（NCU 的 replay 会重放 kernel，对含原子操作或随机数的 kernel 不可直接重放）；search 的失效是在噪声上做选择，把一次抖动当成真实提升。把四类失效分开统计，才能回答“这一轮迭代的卡时花在了谁身上”。

$$\text{cost}_{\text{iter}} = N_{\text{cand}}\cdot\left(t_{\text{compile}} + t_{\text{judge}} + t_{\text{prof}}\right) + N_{\text{reject}}\cdot t_{\text{compile}}$$

这里 Ncand 是进入评测的候选数，Nreject 是编译即失败的候选数。编译时间在 CPU 侧，看似便宜，但当候选数上千、每个编译单元带模板实例化时，它会成为排队的主因——这是“评测吞吐瓶颈不在 GPU 而在编译队列”的具体机制。一个可操作的例子：把 coder 的产出先过一遍语法与形状推导的静态检查（不启动 nvcc），把明显不合法者挡在编译之前，Nreject 从编译队列里消失，代价是静态检查本身要维护一套形状规则，规则漏判会放过本可被编译器早期发现的错误。

二 · 执行反馈的三种粒度与各自的 token 代价

反馈喂回 coder 的粒度决定多轮修正的效率。最粗的是布尔反馈：编译通过/失败、正确/错误。它几乎不花 token，但信息量最低，模型只能盲改。中等粒度是结构化诊断：编译器的首条错误行、judge 报出的最大误差与首个失配索引、profiler 报出的 top-3 stall 原因。最细的是全量 profile 文本：完整 NCU 报告或 SASS dump，动辄数千行，token 成本高且大部分与当前缺陷无关。

工程判断是：把粒度做成按失效类型自适应。编译失败只回传首条错误加出错行上下文；数值失配回传失配索引、该索引处的输入值与两侧输出值；性能不达标才回传 stall 直方图与占用率。这样每轮反馈的 token 数被压在与缺陷维度相同的量级上，而不是与报告体积成正比。代价是脚手架要维护一套“缺陷分类器”，分类错了就会喂错粒度的反馈——例如把性能问题误判为数值问题，模型会去改算法而不是改访存。

反馈粒度典型 token 量级适用失效代价
布尔个位数编译失败修正轮数多，GPU 空转等待
结构化诊断数十至数百数值失配、明显性能缺陷需维护分类器，误分类会误导
全量 profile数千疑难性能瓶颈token 与上下文窗口双重开销

一个具体例子：某候选 kernel 的时延是参考实现的数倍，布尔反馈只会让模型反复重写；结构化反馈告诉它“shared memory bank conflict 占 stall 的大头、占用率被寄存器数压到低位”，模型就能定向地把寄存器压力降下来或改数据布局。这里省下的不是一次编译，而是若干轮无效候选的 GPU 分钟数。

三 · NCU 与 SASS：把“慢”翻译成可执行的修改指令

profiler 角色的核心不是采集，而是翻译。NCU 给出的是一组计数器：achieved occupancy、DRAM throughput、L2 hit rate、warp stall 分布、指令发射数。这些数字本身不构成修改建议，需要一层映射规则把它们变成候选动作：occupancy 低且寄存器数高 → 减寄存器/调 block size；DRAM throughput 接近峰值而计算单元空闲 → 该 kernel 是带宽受限，优化方向是减少访存字节而非增加 ILP；stall 集中在 long scoreboard → 访存延迟未被掩盖，需要提高并行度或预取。SASS 层面则看指令混合：是否存在大量整数地址计算挤占发射槽、是否有本可向量化的标量访存。

$$\text{bound} = \arg\max\left(\frac{\text{bytes moved}}{\text{peak BW}},\ \frac{\text{FLOPs}}{\text{peak FLOPS}}\right)$$

用这个 roofline 判断先定性再定量：如果实测时延已经贴近 bound，继续调优的边际收益极低，search 应把该候选标记为“已饱和”并停止投入；如果实测时延显著高于 bound，说明存在实现缺陷，值得继续迭代。这一步的代价是 profiler 采集本身的开销：NCU 的 replay 会让被测 kernel 跑多遍，单次采集的 GPU 时间远高于普通计时，且对非确定性 kernel 的结果不可信。因此工程上常见的做法是两段式：先用轻量计时（CUDA event）筛掉明显慢的候选，只对进入决赛圈的少数候选做完整 NCU 采集。这把 profile 开销从“每个候选”压到“每个入围者”，代价是筛选阶段可能漏掉“计时抖动导致被误杀”的候选。

一个具体例子：一个 reduction kernel 的实测带宽只有峰值的较小比例，NCU 显示 L2 hit rate 高但 DRAM throughput 低，SASS 显示每轮循环有冗余的边界判断。翻译层给出的动作是“去掉内层边界分支、改为对齐访存”，而不是笼统的“优化访存”。这种定向性来自 SASS 与计数器的联合读取，单看任何一侧都得不到。

四 · 多轮修正的状态机与停止条件

多轮修正不是“循环直到通过”，而是一个带预算与停止条件的状态机。状态至少包括：待编译、编译失败、数值失败、性能未达标、已接受。转移由 judge 与 profiler 的输出驱动，search 负责决定下一轮把预算投给哪个状态下的哪个候选。关键设计是每状态独立预算：编译失败最多重试少数几次（因为同一类语法错误反复出现说明 coder 的能力边界已到），数值失败允许较多轮（容差与边界条件常需试探），性能未达标则按 roofline 距离决定是否继续。

停止条件必须显式，否则 agent 会在一个不可能通过的候选上烧掉整段预算。三类停止条件：预算耗尽（该候选的累计 GPU 秒数超阈值）、边际收益低于噪声（连续两轮的性能差异落在计时抖动范围内）、饱和（实测贴近 roofline bound）。第三类最容易被忽略：一个已经贴近带宽上限的 kernel，再怎么改也不会更快，继续迭代纯属浪费。代价是噪声估计本身需要重复计时，重复次数越多，判定的置信越高，但每个候选的评测 GPU 分钟数也线性上升——这正是评测精度与成本权衡在脚手架层的具体体现。

一个具体例子：某候选在数值上已通过，性能连续两轮提升幅度落在计时抖动内。若 search 继续投入，它会得到一批统计上不可区分的“改进”，并把其中一个写进最终结果，造成选择偏差。显式停止条件在这里的作用不是省钱，而是防止把噪声固化成结论。

五 · search 的选择偏差与评测吞吐的耦合

search 角色最隐蔽的成本不是它跑了多少候选，而是它如何从噪声里选。当候选池大、每个候选只测一次时，最大值统计量会系统性高估——被选中的往往是“真实性能中等但恰好测出低时延”的那个。这在 kernel 搜索里尤其致命，因为计时抖动来自频率、缓存状态与并发邻居。缓解手段是：对入围候选做重复计时并取分位数而非单次值；或者用两阶段筛选，第一阶段宽进严出，第二阶段对少量候选做高重复测量。

$$\mathbb{E}\left[\max_i \hat{t}_i\right] \ge \max_i \mathbb{E}\left[\hat{t}_i\right]$$

这个不等式说明：候选越多，选出来的“最优”越偏向乐观偏差。代价是纠正偏差需要更多重复测量，也就是更多 GPU 分钟；不纠正则会把虚假提升带进下游，让生产侧替换 kernel 后收益不达预期。这与评测集群的容量直接耦合：如果评测吞吐不足，团队会倾向于“每个候选只测一次”来加快排队，恰好放大了选择偏差。反过来，容量充裕时可以用重复测量换置信度。容量规划因此不只是买卡，而是决定 search 能采用哪种统计策略。

一个具体例子：评测集群排队拖慢迭代时，团队把单候选测量次数砍半以提升吞吐，短期内迭代轮数上升，但被接受的 kernel 在生产端复测时收益缩水——原因正是选择偏差被放大。修复方式不是加卡，而是把“入围候选高重复、落选候选低重复”的分层策略写进 search，用结构而非蛮力换吞吐。

六 · 脚手架的计费口径：把卡时归因到角色

要让成本模型可用，必须能把 GPU 分钟数归因到四个角色上。做法是在脚手架里给每次 GPU 调用打标签：judge 调用、profiler 轻量计时、profiler 完整 NCU、search 的重复测量。归因之后才能回答“这一轮迭代的钱花在正确性验证还是性能采集上”。常见的不均衡是：judge 因为要覆盖边界形状与多种 dtype，调用次数远多于 profiler，占据大部分评测卡时；而 profiler 的 NCU 采集虽然单次贵，但次数少，总量未必高。若不分开计费，团队会误以为“profile 太贵”而砍掉它，实际上砍掉的是信息密度最高的那部分反馈。

归因还暴露一个结构性决策：judge 与 profiler 是否共享同一批 GPU。共享能提高利用率，但会让长队列的 NCU 采集阻塞短小的正确性检查，拖慢整个迭代回路；隔离则要按峰值预留容量，均值利用率下降。这与容量按峰值还是按均值预留的决策直接相连。一个可操作的判断是：把 judge 放在高吞吐、短任务的池子里，把 NCU 采集放在允许长驻、可被抢占的池子里，用队列隔离代替物理隔离，代价是跨池调度逻辑的复杂度与偶尔的跨池排队。

最终落在具体机制上：脚手架的每个角色都应输出可计费的结构化记录（角色标签、GPU 秒数、候选 ID、轮次），成本模型才有输入。没有这层记录，所谓“每 1% 端到端提升的卡时成本”只能靠总量除以总收益，无法定位是 coder 产出质量差、judge 容差不当，还是 search 在选择噪声。归因粒度决定了优化动作能否落到具体组件上，而不是笼统地“少跑点候选”。

脚手架的分工边界：谁该被信任，谁在烧卡时

coder/judge/profiler/search 四角色并非并列流水线，而是代价结构完全不同的四种调用：coder 与 judge 消耗 token 与 GPU 秒，profiler 消耗独占 GPU 分钟并产出高维二进制（NCU 指标、SASS 反汇编），search 消耗检索延迟与上下文窗口。把 profiler 放进每一轮修正的内循环是常见失效点——NCU 采集需要串行化、关闭部分并发、多次 replay 以稳定计数器，单次采集的墙钟时间往往是 kernel 本身执行时间的数十倍，且其输出（数百个 metric、上千行 SASS）若整段回灌 prompt，token 成本随轮数线性膨胀。合理的边界是：profiler 只在 judge 判定“正确但显著慢于 roofline 下界”时触发，且只回灌经筛选的 top-k 指标与热点指令窗口，而非全量 dump。

失效条件可以写成一个触发判据。设第 r 轮修正后实测时延为 Tr，roofline 下界为 Tmin，则相对余量 gr = (Tr − Tmin)/Tmin；当 gr 连续两轮下降幅度小于阈值 δ，说明 coder 已进入“猜测—编译—微调”的平台期，此时继续投喂 profile 的边际收益低于其采集开销，应终止该分支而非加轮数。系统代价体现在三处：采集时延占用评测集群的独占配额，直接压缩同批次其他任务的排队吞吐；SASS 文本进入上下文带来的 token 开销；以及多轮编译（每轮 nvcc/ptxas 的编译时间）在搜索空间大时成为主导项。一个具体例子：某 reduction kernel 在 judge 通过后余量仍高，profiler 显示瓶颈不在算术而在非合并访存，若把整段 SASS 回灌，coder 往往围绕指令调度做无效改写；只给“访存事务数/请求数”与热点行号，修正才落到向量化与对齐上。

角色主要成本项失效信号收敛手段
codertoken、编译时间余量平台期换搜索分支而非加轮
judgeGPU 秒、重复次数正确性 oracle 覆盖不足提高重复换置信
profiler独占 GPU 分钟、上下文指标与余量不相关筛选 top-k 指标
search检索延迟、上下文召回旧解不适用按形状/精度过滤

因此脚手架的成本模型必须按“每次有效修正”而非“每轮”计价：分母是余量的实际下降量，分子是 judge 的 GPU 秒、profiler 的独占分钟与全部 token 之和。当分母趋零时，任何增加轮数的策略都只是在放大分子，这也是评测吞吐成为迭代瓶颈、进而迫使资源配比重构的直接原因。
