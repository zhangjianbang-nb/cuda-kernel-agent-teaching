一 · 口径三件套：任务、基线、硬件

把「快」翻译成可复核的数字，第一步不是测，而是把被测对象钉死。一个 kernel 的时延数字离开三样东西就没有意义：任务边界（输入形状、是否含 host-device 拷贝、是否允许融合前后算子）、基线（对谁快、基线本身用什么实现）、硬件（SM 型号、显存带宽、时钟是否锁定）。本卷把这套约定称为「口径三件套」，任何一条分数记录缺一项即视为不可复核，直接退回重测。工程上最常见的伪加速来自边界漂移：把 epilogue 挪到下一个 kernel、把 dtype 转换算进「准备阶段」、或者基线选了未调优的朴素实现。这三种做法都能让数字好看，但都改变了任务定义。

机制上，口径以结构化记录落地：每条记录包含 task_id、shape_sig（形状签名，含 batch、序列长度、head 数、hidden 维）、baseline_ref（指向基线实现的 commit 与编译选项）、hw_sig（设备名、驱动、时钟策略）、dtype_sig、metric 与 boundary_flags（是否含拷贝、是否含分配）。复核脚本只接受字段齐全的记录，缺字段的记录在聚合时被丢弃而不是补默认值——补默认值是口径污染的第一入口。

代价体现在吞吐上：完整口径意味着每次评测都要跑基线、跑参考实现、跑多次重复取分位，单条任务的评测时延从「一次 kernel 启动」膨胀到「基线 + 候选 + 校验」三段，通常是候选本身耗时的数倍。这是必要开销：没有基线就没有比值，没有比值就没有跨版本可比性。具体例子：同一份 RMSNorm kernel，在「仅 kernel 时间」口径下与「含 residual add 融合」口径下的加速比可以差出一个量级，而两者都自称「相对 PyTorch 快 N 倍」；口径记录的作用就是让这两个数字不可能被混进同一张表。

$$\text{speedup} = \frac{T_{\text{baseline}}(\text{shape\_sig},\ \text{baseline\_ref},\ \text{hw\_sig})}{T_{\text{candidate}}(\text{shape\_sig},\ \text{hw\_sig})}$$

公式里刻意让基线侧多带一个 baseline_ref：基线不是常数，它随 PyTorch/Triton 版本、cuBLAS 版本、编译 flag 变化。把基线当成不动的分母，是历史分数不可比的根源之一。

二 · 指标：时延分位、带宽利用率与「有效 SOL」

单一均值时延是最容易被操纵的指标：一次异常快的迭代就能拉低均值。本卷的默认指标是分位时延（p50 与 p90 并列记录）加一个吞吐口径，并且要求同时记录测量窗口内的方差来源（时钟抖动、其他进程占用、L2 残留状态）。对 memory-bound 算子，另记「有效 SOL」：以实测带宽除以该卡在该 dtype 下的可持续带宽上限，得到 0 到 1 之间的利用率。SOL 的价值在于它把「快」从相对量变成绝对量——相对基线的加速比可以因为基线弱而虚高，SOL 不会。

机制上，SOL 的计算需要两个实测值：kernel 实际搬运字节数与实测耗时。字节数由形状签名与 dtype 直接推出（读多少、写多少、是否重复读），耗时取 p50。对 compute-bound 算子则改用 FLOP 口径，并注明是否计入稀疏化或近似（如 fp16 累加、tf32 降精度）。这里必须写明降精度：一个用 tf32 跑出的 GEMM 时间与 fp32 基线相比的加速比，若不在记录里标注 dtype_sig 的差异，复核者无法判断这是工程优化还是精度换时间。

代价在测量本身：分位时延要求每配置至少数十次重复，且每次重复前要重置 L2 状态或至少固定 warmup 次数，否则缓存命中率漂移会让 p50 在不同批次间跳动。这使单条评测的 GPU 时间上升，也让评测集群的排队时延成为流水线瓶颈——这正是可信评测流水线要解决的问题，此处只指出口径对它的依赖。具体例子：一个 reduction kernel 在小 shape 上 SOL 只有百分之几，加速比却很高，因为基线在该 shape 上根本没做并行规约；只看加速比会把它排进榜首，看 SOL 才知道它离硬件上限还很远。

$$\text{SOL}_{\text{mem}} = \frac{B_{\text{actual}} / T_{p50}}{B_{\text{peak}}}$$

三 · dtype 与数值口径：正确性 oracle 的前置条件

dtype 不只是性能参数，它是正确性判定的前置条件。同一算子在不同 dtype 下的可接受误差界不同：fp32 累加的相对误差界与 fp16 累加差若干数量级，bf16 的尾数更短。若口径不固定 dtype 与累加精度，正确性 oracle 就无法给出稳定的通过/不通过判定——同一个候选在 fp32 下通过、在 fp16 下不通过，而两次评测的记录若都不写 dtype，历史曲线会出现无法解释的跳变。

机制上，本卷要求每条记录携带 dtype_sig 三元组：输入 dtype、累加 dtype、输出 dtype。正确性判定用「参考实现 + 容差」而非逐位相等，容差按 dtype 分档设定，并在记录里写明容差来源（是库函数对照还是高精度参考）。对归约类算子额外记录累加顺序敏感性：并行归约的求和顺序改变会导致末位差异，容差必须覆盖这一项，否则会把正确的并行实现判为错误。

代价是显存与时间：高精度参考实现（如 fp64 累加）在 GPU 上吞吐低、显存占用高，跑一遍参考往往比跑候选贵一个量级；因此参考结果按形状签名缓存，缓存键必须包含 dtype 三元组与容差档位，否则会串档。具体例子：LayerNorm 的均值/方差在 fp16 输入下若用 fp16 累加，长序列上方差会明显偏移，候选「更快」但正确性 oracle 在长序列档位上判失败；口径若只写「fp16」，复核者会误以为是实现 bug 而非累加精度选择。

$$\lVert y_{\text{cand}} - y_{\text{ref}} \rVert_\infty \le \tau(\text{dtype\_sig},\ \text{reduction\_order})$$

四 · 难度分层：按算子还是按优化技巧

基准演化史里一个反复出现的决策是：难度该按算子类型分层，还是按所需优化技巧分层。按算子分层（elementwise、reduction、GEMM、attention、scan）直观、易与公开基准的 L1–L3 对齐，但同一算子内部的难度跨度极大——一个 elementwise 加 bias 和一个需要向量化 + 掩码 + 融合的 elementwise 完全不是一个难度。按技巧分层（访存合并、shared memory 分块、warp 级规约、流水线双缓冲、张量核使用、异步拷贝）能刻画「难在哪」，但一条任务可能同时需要多种技巧，分层边界模糊。

本卷的折中是二维标签：算子族给一维，技巧需求给另一维，难度分数取两维的联合序，而不是简单相加。联合序的构造方式是：先按算子族内已验证的通过率排序（通过率来自历史评测记录，不是主观打分），再在族内按技巧标签细分。这样难度分层是可复核的——任何人拿历史记录都能重算出同一序。代价是分层表需要随基准版本更新重算，每次重算都要保证历史分数在新序下仍可映射回旧序，否则跨版本比较断裂。

具体例子：一个 fused softmax 任务在「算子族 = reduction」下看似中等，但它同时要求 warp 级规约与数值稳定实现（减最大值），技巧维把它推到高难度档；若只按算子分层，它会被排在简单 reduction 旁边，导致难度曲线在训练信号上产生误导。分层规则本身属于本卷产出的一部分，其变更需进入基准变更记录。

维度取值示例可复核依据
算子族elementwise / reduction / GEMM / attention与公开基准 L1–L3 的映射表
技巧标签合并访存、分块、warp 规约、双缓冲、张量核参考实现中实际出现的技巧
难度序族内通过率排序后的联合序历史评测记录的通过率统计

五 · 防污染与可比性：私有 held-out 与时间切分

公开基准的分数会随时间虚高，原因不是模型变强，而是测试集进入了训练语料。本卷对应的转折正是这一点：污染检测揭穿了虚高分数，倒逼基准从公开集迁移到私有 held-out。防污染在本卷不是一条策略而是一组可执行机制：去重（对任务描述与参考实现做近似重复检测，剔除与公开集高度重合的条目）、私有 held-out（不公开、不进入任何训练数据管线、仅通过评测接口暴露分数）、时间切分（按任务首次公开时间划分，晚于模型训练截止的任务才计入「干净」子集）。

机制上，held-out 的访问控制比数据本身更重要：候选生成端只能拿到任务签名与参考输入，拿不到参考输出与参考实现源码；评测端在隔离环境跑参考并比对。这样即使 agent 见过公开集的解法，也无法直接抄到 held-out 的答案。代价是评测吞吐下降：隔离环境意味着不能复用候选端的编译缓存，每次评测都要重新编译参考与候选，编译时间成为固定开销；同时 held-out 规模受限于人工审核成本，覆盖的算子族不可能与公开集等宽。

可比性是另一条约束：基准升级后，历史分数必须能映射到新口径。做法是保留「双跑窗口」——升级后的若干版本内，新旧两套口径并行评测同一批候选，用两套分数的经验映射把历史曲线接上；映射关系写入基准变更记录，并标注映射的适用区间。具体例子：某次升级把「仅 kernel 时间」改为「含输出分配」，历史加速比整体下移，若不双跑，曲线会出现一个无法解释的断崖，读者会误判为模型能力退化。变更记录里必须写清：改了什么口径、影响哪些指标、双跑窗口多长、映射是否单调。

$$\text{score}_{\text{new}} = f(\text{score}_{\text{old}}),\quad f \text{ 由双跑窗口内的配对样本拟合，区间外不外推}$$

六 · 把「快」写成可复核数字的最小充分集

综合以上，一条可复核的分数记录的最小充分集是：任务签名（形状 + 边界标志）、基线引用（实现 + 编译选项）、硬件签名（设备 + 时钟策略）、dtype 三元组、指标（p50/p90 + SOL 或 FLOP 口径）、正确性判定（容差档位 + 参考来源）、基准版本号与变更记录指针。缺任一项，数字就退回「不可复核」。这套最小集不是官僚流程，它是让「快」在不同人、不同时间、不同机器上得到同一个数的唯一办法。

工程判断上，口径的严格程度应与用途匹配：用于训练奖励的信号可以容忍较松的口径（单卡、固定 shape、仅 p50），因为奖励只需要相对排序稳定；用于对外报告或跨版本对比的分数必须走完整最小集，因为一旦口径漂移，历史曲线就失去解释力。两者的记录格式应统一，只在字段完整度上分级，避免出现「训练用一套、报告用另一套」导致两套数字无法对话。

最后一个具体机制：基准变更记录本身要有版本号与不可变性——已发布的记录不修改，只追加。任何口径调整都以新记录追加的方式出现，旧记录保留其原始字段，这样任何历史分数都能追溯到它被产生时的口径，而不是被后来的口径「追认」。这正是本卷产出中「基准版本谱系」的落地形式：谱系不是一条被不断覆盖的曲线，而是一组带口径标签的、可追溯的记录集合。

私有 held-out 的口径边界：分数可比性与系统代价

把公开集换成私有 held-out，最先崩的不是模型而是口径：同一 kernel 在 L1 公开集上跑出的加速比，与在私有集上跑出的加速比，只有在基线、dtype、硬件、计时方式四项全部对齐时才可相减。工程上把这四项固化成一条「口径指纹」——基线实现（cuBLAS / Triton 参考 / 手写 naive）、输入 dtype 与布局、目标 GPU 型号与 SM 配置、计时口径（是否含 warmup、是否用 CUDA event、是否剔除首次 JIT）。指纹不一致的两个分数必须视为不同量纲，禁止直接比较；基准变更记录里要为每次升级写明指纹差异，否则历史分数曲线会被误读成能力涨跌。代价是显性的：每新增一个 held-out 分片，就要重跑全量基线以重建指纹，编译时间与 GPU 机时按分片数线性增长，而 token 侧则要为每个分片维护独立的 prompt 与参考实现。

污染检测本身也有失效条件。去重只能拦住字面近似，拦不住「结构同构」——把同一算子的 tile 大小换一组常量，哈希与编辑距离都判为不同，但优化技巧完全可迁移。因此私有集必须叠加时间切分：以某个 commit 为界，之后进入基准的算子不得出现在训练语料窗口内，否则 held-out 只是名义上的。判定式为 污染率 ≈ 命中同构簇的样本数 / held-out 总数，一旦该比值超过预设阈值，该分片整体作废而非逐条剔除，因为逐条剔除会引入选择偏差，让剩余样本偏向模型已见过的技巧分布。

系统代价落在评测吞吐上：私有 held-out 不可缓存基线结果（缓存即泄漏），每次评测都要现场编译并跑参考实现，单条样本的端到端时延由「编译 + 基线 + 候选 + 校验」四段构成，其中编译段在 Triton/CuTe 路径上往往占大头。工程判断是：把 held-out 切成「快速分片」与「全量分片」两级，快速分片只保留正确性 oracle 与粗粒度 roofline 判定用于多轮 RL 的内循环，全量分片才跑 NCU/SASS 级 profile 与 SOL 对齐，用分片预算换内循环轮次。
