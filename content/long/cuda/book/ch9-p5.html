一 · 脚手架的职责切分：四种角色而非一个万能模型

生产端到端落地里，Agent 脚手架不是“一个会写 CUDA 的大模型”，而是一组职责被显式切开的角色。coder 负责把算子语义翻译成可编译的 kernel 源（CUDA C++ / Triton / CuTe / PTX 内联）；judge 负责在给定输入分布与容差下判定输出是否可接受，它掌握的是正确性 oracle 的调用权，而不是生成权；profiler 负责把一次运行变成结构化证据——NCU 的 stall 原因、achieved occupancy、DRAM/L2 吞吐、SASS 指令组合与寄存器压力；search 负责在候选空间里做预算分配：改 tile、改向量化宽度、改流水深度、换后端，决定下一轮把 token 花在哪里。四者共享一份“工件契约”：kernel 源、编译命令、输入张量规格、容差、profile 摘要、判定结论。契约字段一旦缺失，后续任何一轮修正都不可复现。

切分的工程理由是代价不对称。coder 的一次生成是 token 成本与编译时延；judge 的一次判定是数值比对与潜在的形式审计成本；profiler 的一次采集是 GPU 占用与时间（NCU 逐 kernel 采集会串行化并放大时延，通常只对候选做抽样而非全量）；search 的一次决策错配会浪费整轮预算。若让同一个模型同时“写”和“判”，它会倾向于相信自己写对了，把容差当成可协商项——这是生产事故的常见起点。因此 judge 必须是独立进程、独立容差配置、独立随机种子集合，且对 coder 不可见其内部阈值。

具体例子：某归一化类算子，coder 首轮给出一个按行分块的 Triton 实现，judge 在 fp16 输入下通过，但在含极小方差的行上出现相对误差超限；profiler 显示该 kernel 的寄存器占用导致 occupancy 偏低、且存在大量 predicate 分支。search 据此不追加“再写一版”的预算，而是把预算切给“数值稳定化 + 分块重排”这一具体动作。这个决策链条只有在四角色分离、证据结构化时才成立。

$$\text{budget}_{t+1}=B\cdot\frac{u(\text{stall})+u(\text{err})}{u(\text{stall})+u(\text{err})+u(\text{compile})}$$

其中 $u(\cdot)$ 是归一化后的改进上界估计，$B$ 是单轮 token 预算。该式表达的是：当编译失败或数值错误占据主导时，把预算压向“可编译性/正确性”而非“性能调优”，避免在错误基座上做无效搜索。

二 · 执行反馈的三种粒度：编译、数值、性能

执行反馈不是单一信号，而是三层粒度，每层的失败模式与修复动作完全不同。第一层是编译反馈：nvcc/triton 的报错文本、PTX 汇编失败、CuTe 模板实例化爆炸。它的代价是编译时间与 token（错误信息往往很长，需要截断与摘要），修复动作是语法/类型/布局约束的局部改写。第二层是数值反馈：judge 给出的最大绝对误差、最大相对误差、NaN/Inf 出现位置、以及按输入分桶的失败率。它的代价是正确性风险，修复动作是累加精度、算法重排、边界条件处理。第三层是性能反馈：profiler 给出的时延、带宽利用率、occupancy、stall 分布。它的代价是 GPU 机时，修复动作是 tile/向量化/流水/后端切换。

三层反馈必须被压成可比较的向量，否则 search 无法排序。常见做法是给每层一个硬约束（编译必须通过、数值必须在容差内）加一个软目标（性能），把多目标化为“约束满足下的单目标优化”。这避免了“为了 3% 时延牺牲正确性”的越界行为。表格给出三层反馈的字段与代价对照：

粒度典型信号修复动作主要代价
编译nvcc 报错、模板实例化失败、PTX 版本不匹配类型/布局/语法局部改写编译时间、token 长度
数值max abs/rel err、NaN 位置、分桶失败率累加精度、重排、边界处理正确性风险、审计成本
性能时延、DRAM 吞吐、occupancy、stall 原因tile、向量化、流水、换后端GPU 机时、采集串行化

具体例子：一个 reduce 类 kernel 在编译层反复因共享内存对齐失败，coder 每轮都在改索引表达式；search 若只看性能信号会误判为“已可运行”，实际是编译未过。把编译层设为硬门禁后，预算被正确导向对齐声明与布局重写，而不是继续调 tile。代价是每轮多一次编译等待，但避免了在不可运行代码上采集 profile 的浪费。

三 · NCU/SASS 证据如何进入修正回路

profiler 的价值不在于“跑一次 NCU”，而在于把 NCU 与 SASS 的输出转成 coder 能消费的结构化诊断。NCU 给出的关键量包括：SM 活跃周期占比、achieved occupancy、每个 stall 原因的采样计数（如 long scoreboard、barrier、MIO throttle）、DRAM 与 L2 的字节吞吐、指令发射效率。SASS 层面则看寄存器数量、是否有本地内存溢出、是否有未合并的全局访问、是否有冗余的 predicate 与分支。把这些量映射到具体改写动作，需要一个诊断表，而不是把原始报告整段塞回 prompt——原始报告 token 极长且噪声高。

诊断映射的典型规则：long scoreboard 占主导 → 提高访存并行度或预取，考虑增大每线程的独立加载数；barrier 占主导 → 减少同步点或改用 warp 级原语；MIO throttle → 减少特殊函数与共享内存冲突；寄存器溢出到本地内存 → 降低每线程工作量或缩小 tile；occupancy 受寄存器限制 → 调整 block 大小或强制降低寄存器上限。每条规则对应一个可验证的改写，search 据此生成候选而不是让 coder 自由发挥。

$$\text{occ}_{\text{ach}}=\frac{\text{active warps per SM}}{\text{max warps per SM}},\quad \text{gap}=1-\frac{\text{achieved throughput}}{\text{roofline bound}}$$

这两个量共同决定“该修 occupancy 还是该修访存效率”。若 occupancy 已接近上限而 gap 仍大，说明瓶颈在指令级或访存模式，继续加并行度无益；反之则应先解占用。代价方面，NCU 逐 kernel 采集会引入显著时延放大并占用 GPU，生产环境中通常只对候选集抽样采集，且需与在线流量隔离，否则会污染端到端时延观测。

具体例子：某矩阵乘类 kernel 的 NCU 显示 DRAM 吞吐接近峰值但时延仍高于预期，SASS 显示存在大量未合并的尾块访问。search 判定这不是“再加 tile”的问题，而是尾块处理路径的访存模式问题，于是把预算切给边界分块与对齐填充的改写，而不是继续扩大主 tile。这个判断若只靠时延数字无法做出，必须依赖 NCU 与 SASS 的联合证据。

四 · 多轮修正的状态机与预算控制

多轮修正不是“循环直到变好”，而是一个带终止条件的状态机。状态包括：待编译、编译失败、数值失败、性能未达标、性能达标待集成。转移由 judge 与 profiler 的证据触发，search 决定转移方向与预算。关键设计是“每轮只允许一个语义级别的改动”，否则失败归因不可分离——同时改 tile 与精度，数值变好但时延变差时无法判断是哪个改动起作用。

伪代码思路：维护候选池，每轮取当前最优候选，依据诊断表选一个改写动作生成子候选，编译门禁过滤，judge 判定，profiler 采样，按“约束满足 + 性能改进”排序入池；若连续 $k$ 轮无改进则触发后端切换（如 Triton 转 CUDA C++ 或 CuTe），若数值反复失败则回退到更保守的算法结构。终止条件包括：达到目标加速比、预算耗尽、或连续无改进超过阈值。代价是每轮的编译时间与 GPU 采样时间累加，因此 $k$ 与采样率必须按业务时延预算设定。

具体例子：故事中首个 kernel 上线生产时微基准加速 1.8x 但端到端仅 4%，这个反差正是多轮修正回路必须提前纳入“集成视角”的原因——search 若只以微基准时延为唯一目标，会把预算全部导向 kernel 内部优化，而忽略调用开销、数据布局转换、以及框架侧同步点。修正回路应在性能达标后增加一个“集成预检”状态：估算该 kernel 在真实调用路径中的时间占比，若占比过低则不再追加微基准优化预算。这是本卷收益归因与集成路径要处理的问题，此处只需在脚手架上留出该状态的接口。

$$\text{stop}=\big[\text{speedup}\ge S^\*\big]\lor\big[\text{spend}\ge B\big]\lor\big[\text{no-improve}\ge k\big]$$

该终止式把“目标达成”“预算耗尽”“停滞”三类条件并列，避免无限循环烧 token 与 GPU 机时。

五 · 工件契约与可复现性：让每一轮修正可审计

生产落地的可信度来自可复现，而可复现来自工件契约的完整性。每个候选必须携带：源码哈希、编译命令与工具链版本、输入张量规格与随机种子集合、容差配置、judge 结论、profile 采集配置与摘要、以及 search 的决策理由。缺少任一项，后续灰度发布出现回归时无法定位是“kernel 变了”还是“输入分布变了”还是“工具链变了”。这也是 Oracle 与形式审计所依赖的输入格式，此处不展开其判定逻辑，只强调脚手架的产出必须满足该格式。

代价是存储与 token：完整工件比只存源码大一个量级，且每轮都要写入。工程上通常只对进入候选池的工件做完整留存，对被淘汰的候选保留摘要。另一个代价是 judge 的随机种子集合若过小，会给出过于乐观的通过结论；扩大种子集合会线性增加判定时间。这个权衡必须显式配置，而不是让 judge 自行决定。

具体例子：某 kernel 在灰度阶段出现特定 batch 形状下的数值偏差，若工件契约记录了输入规格与种子，可直接复现并判定是边界分块问题；若只存了源码与“通过”结论，则只能全量回滚。回滚阈值与灰度比例属于灰度发布机制的范畴，此处脚手架的责任是保证“可复现的最小证据集”随候选一起流动。

最后落在工程判断上：Agent 脚手架的设计目标不是让模型“更聪明地写 kernel”，而是让 coder/judge/profiler/search 四者在明确的工件契约下交换可比较的证据，并把编译、数值、性能三层反馈压成带硬约束的搜索问题。判断一个脚手架是否可用于生产，看它能否在预算耗尽时给出“为什么停在这里”的可审计理由，以及能否在微基准加速与端到端收益背离时及时把预算从 kernel 内部优化转向集成路径——这正是 1.8x 与 4% 的反差所要求的能力。

脚手架的分工边界：当 judge 与 profiler 给出互相矛盾的信号

coder/judge/profiler/search 四角色的分工在纸面上清晰，落到生产端到端场景却会暴露一个结构性裂缝：judge 只看数值正确性与容差，profiler 只看时间与带宽，两者的判据不在同一坐标系。judge 通过意味着输出在 atol/rtol 内逐元素一致，而 profiler 报告的是 kernel 级 sm__cycles_active 与 dram__bytes 的占用率。一个被 judge 判为“正确”的 kernel 完全可能在 profiler 视角下是带宽浪费型——例如把本可向量化的访存拆成标量循环，数值分毫不差，但 dram__throughput 远低于 roofline 上限。此时 search 若只按 judge 的通过率排序候选，就会系统性地偏向“正确但慢”的实现。工程上必须让 search 的排序键显式包含 profiler 的归一化指标，而不是把正确性当作硬门槛后再比时间。代价是每轮候选都要跑一次 NCU 采集，单次 profile 的固定开销（多次 replay、指标分组）会把多轮修正的墙钟时间拉长，在候选池大时成为搜索吞吐的瓶颈。

更尖锐的失效条件出现在“微基准加速但端到端无收益”的经典错位。设 kernel 在孤立测试中从 t_base 降到 t_new，微基准加速比为 S_k = t_base / t_new；但端到端时延由 T = T_host + Σ t_k 构成，其中 T_host 含框架调度、launch 开销、同步与数据搬运。端到端收益为：

$$G_{e2e} = \frac{T_{base} - T_{new}}{T_{base}} = \frac{t_{base} - t_{new}}{T_{base}} = \frac{(S_k - 1)\, t_{new}}{T_{base}}$$

该式直接说明：G_e2e 被 t_new / T_base 这个 kernel 时间占比压死。故事中微基准 1.8x、端到端仅 4% 正是这个比值很小的直接后果——kernel 本身只占端到端时延的一小段，优化它的分子再大也被分母稀释。profiler 若只报 kernel 级加速而不报 t_k / T 占比，judge 又无法感知这一层，脚手架就会把“局部最优”误判为“全局收益”。修正路径是让 profiler 在采集时同时输出 kernel 时间占该算子总耗时的比例，并把该比例作为 search 的权重因子，而非事后由人肉归因。

多轮修正的系统代价还体现在反馈信号的噪声上。NCU 的 replay 模式会改变 cache 状态与时钟行为，同一 kernel 两次采集的 dram__throughput 存在抖动；judge 的浮点容差在 reduction 类算子上对累加顺序敏感，不同 block 划分会给出不同的舍入轨迹。若 search 把单次 profile 的微小差异当作改进信号，多轮迭代会陷入在噪声内来回摆动的震荡，浪费大量编译与采集预算。可操作的边界是：只有当 profiler 指标差异超过采集抖动带、且 judge 在固定随机种子下稳定通过时，才允许该候选进入下一轮；否则回退到上一稳定版本。下表给出四角色在端到端场景下的判据与典型失效：

角色主判据典型失效系统代价
coder可编译、语义等价生成依赖未声明头文件编译时间与 token 消耗
judgeatol/rtol 逐元素容差掩盖累加顺序差异参考实现显存占用
profilerNCU 指标与 roofline 距离replay 抖动误判为改进采集墙钟与 GPU 独占
search正确性门槛后比时间忽略 kernel 时间占比候选池吞吐下降

因此脚手架的工程判断应落在“谁有权否决”上：judge 拥有一票否决（正确性不可妥协），profiler 拥有加权否决（指标差异须超过抖动带），search 不得在两者冲突时自行折中，而应把冲突样本回灌给 coder 重写。这一约束把多轮修正从“无限搜索”收敛为“有界迭代”，代价是收敛轮数受限于抖动带宽度与候选池质量，而非算力。
