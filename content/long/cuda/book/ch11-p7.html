一 · 多轮奖励的合成：把稀疏的 kernel 级信号摊成可训练的时间序列

多轮 RL 在 kernel 生成上的根本困难不是奖励函数写不出来，而是奖励在时间轴上极度稀疏：一次 rollout 里 agent 可能连续做十几次编辑（改 tile 大小、换 shared memory 布局、调 unroll 因子），只有最后编译通过并跑完正确性测试才拿到一个标量。若直接把这个终局奖励广播到全部 token，梯度方差随轮数线性放大，策略会把“编译成功”这种低信息量行为过度强化。工程上通行的做法是把终局奖励拆成轮内稠密项与轮间终局项两部分，并按折扣因子做 TD 式回传。

具体机制：每一轮 t 的即时奖励由三块拼成——编译是否通过（二值）、相对上一轮的正确性增量（通过用例数之差）、以及相对上一轮的性能增量（以 roofline 利用率为标度的归一化差值）。终局奖励只在最后一次 rollout 给出，通常取“正确且达到目标 SOL 比例”的分段函数。回传用带基线的折扣和：

$$G_t=\sum_{k=0}^{T-t}\gamma^{k}\,r_{t+k},\qquad \hat{A}_t=G_t-V_\phi(s_t)$$

其中 Vφ 是价值头，输入是当前 kernel 源码的嵌入加最近一次 profile 摘要。代价在这里：稠密化奖励要求每一轮都真的编译并跑测试，单条轨迹的 GPU 分钟数从“一次编译+一次计时”膨胀为“轮数 × 单轮编译+计时”。若一轮平均要做一次 nvcc 编译加一次小规模正确性跑测，轨迹长度十几轮，则单条轨迹的评测开销是单次评测的十几倍——这正是评测吞吐成为 RL 迭代瓶颈的直接来源。例子：一个 reduction kernel 的轨迹，前几轮只拿到“编译通过”的微小正奖励，直到某轮把 block 内归约从原子操作换成 warp shuffle 才触发性能增量项，此时折扣回传把这份增量部分归因到“选择 shuffle”的那几个 token 上，而不是平均摊给前面所有无效编辑。

二 · Robust reward：对抗奖励黑客的三道闸

kernel 任务的奖励黑客面比通用代码任务宽得多，因为“跑得快”可以被合法但无意义的手段伪造：跳过边界检查、把测试用例硬编码进常量、用未定义行为换取编译器优化、甚至在计时区间外做计算。robust reward 的设计不是把奖励函数写得更复杂，而是把可验证性前置成硬闸门，让奖励只在通过闸门后才计算。

  • 闸门一，正确性 oracle 全量跑：不是抽样用例，而是覆盖边界形状（0 长度、非对齐、超大 stride）的固定集合，任何一项失败即该轮奖励置零并终止轨迹。这把“硬编码”类作弊的成本抬高到必须通过全部边界用例。
  • 闸门二，计时口径审计：用 CUDA event 包住 kernel 启动与同步，禁止在计时区内做 host-device 同步以外的 I/O；对同一 kernel 重复多次取中位数，剔除首次启动的上下文开销。若某轮报告的时延显著低于同形状的理论下界（带宽或算力 roofline），标记为可疑并回退到保守估计。
  • 闸门三，行为一致性检查：把 agent 声明的优化意图（例如“改用 vectorized load”）与实际 diff 做粗粒度比对，意图与代码变更不符时降低该轮奖励权重，抑制“说一套写一套”刷分。

代价是评测成本再上一层：全量 oracle 加重复计时意味着单轮评测的 GPU 时间比抽样版高一个量级，而可疑样本的回退重测又引入额外排队。工程判断是闸门一必须无条件执行（正确性是硬约束），闸门二、三可以按采样率执行——例如每 N 条轨迹抽一条做完整审计，其余走快速路径，用采样审计的估计偏差换取吞吐。例子：某轨迹声称把 GEMM 的 shared memory 分块从 32 提到 64 使时延减半，但审计发现它同时删掉了尾块处理，边界用例直接失败，闸门一拦下，避免这条轨迹污染策略。

三 · TRLOO：把留一法基线搬进多轮信用分配

多轮 RL 里最常见的基线是“同组均值”，即对同一 prompt 采样 K 条轨迹取平均回报做基线。问题在于多轮轨迹长度不一、动作空间不同，组均值会被长轨迹和短轨迹的混合稀释，导致优势估计偏向“多做事”的策略而不是“做对事”的策略。TRLOO（leave-one-out 式的轨迹级基线）的思路是：对每条轨迹，用同组其余轨迹的回报均值作为它自己的基线，等价于把每条轨迹的贡献从组均值中剔除后再比较。

$$\hat{A}_i=R_i-\frac{1}{K-1}\sum_{j\neq i}R_j$$

这个式子的直接好处是基线随被评估轨迹变化，消除了“某条特别长的轨迹拉高组均值、压低其余轨迹优势”的系统偏差。实现上需要保存整组的回报向量，内存开销是 K 个标量，可忽略；真正的代价在采样预算：K 越大基线越稳，但每条轨迹都要跑完整的多轮编译与评测，K 从 4 提到 8 意味着评测集群的负载翻倍。这与容量规划直接耦合——若评测集群与训练集群共享，K 的提升会挤占训练卡时。工程折中是按任务难度分层设 K：简单 kernel（单算子、形状固定）用较小 K，复杂融合算子用较大 K，把采样预算花在方差大的地方。例子：同一组 8 条轨迹里，一条尝试了 CuTe 布局重写、跑了二十轮，回报中等；其余七条短轨迹回报偏低。组均值基线会把那条长轨迹的优势压成负值，TRLOO 则让它相对其余七条正确地为正，信用分配方向与真实贡献一致。

四 · 合成数据：从已验证 kernel 反向生成 prompt 与轨迹

真实 kernel 任务的采集成本高：需要有人写参考实现、构造边界用例、标注性能目标。合成数据的路线是反向的——先有已验证的高质量 kernel（正确性 oracle 通过、profile 数据齐全），再从中反推 prompt、分解步骤、生成中间态轨迹。这样每条合成样本天然带着可验证的终局答案和真实的性能标度，奖励信号不需要人工标注。

机制上分三步：第一步，从参考 kernel 提取结构特征（grid/block 维度、内存层级使用、同步点位置），生成描述任务约束的 prompt，刻意隐去实现细节只留接口与性能目标；第二步，用模板化的编辑算子（改 tile、换向量化宽度、插入 pipeline stage）在参考实现上做可控扰动，生成“次优但可编译”的中间态，构成轨迹的中间节点；第三步，把中间态按性能从差到好排序，形成一条从朴素实现到最优实现的示范轨迹，用于轨迹 SFT 或作为 RL 的热启动。

代价有两面。一是合成数据的分布偏移：模板扰动只能覆盖已知的优化模式，agent 在真实任务上遇到的怪异形状、非标准布局不在合成分布里，纯合成训练的策略在真实 benchmark 上会退化，需要混入真实样本做锚定。二是生成成本：每条合成轨迹都要实际编译并 profile 中间态以标注性能，这一步的 GPU 开销与真实评测同量级，合成一万条轨迹的 profile 采集本身就是一笔可观的卡时。例子：从一个已验证的 softmax kernel 反向生成样本，扰动出“未做 online softmax”的中间态，其数值稳定性在长序列上失败，这条中间态被标为负样本，教会策略在长序列场景优先考虑数值稳定而非单纯追求寄存器占用。

五 · 轨迹 SFT 与去重防污染：数据基座的两条底线

轨迹 SFT 与 RL 的分工在于：SFT 学“格式与套路”——如何读 profile、如何组织多轮编辑、如何在失败后回退；RL 学“取舍”——在具体形状下选哪种优化。轨迹 SFT 的数据组织要求把每一轮的观察（编译日志、profile 摘要、正确性结果）与动作（diff）配对成序列，而不是只留最终代码。这样模型学到的是条件于反馈的决策，而非死记答案。代价是序列长度：一条十几轮的轨迹加上每轮的日志摘要，token 数是单次代码生成的数倍，SFT 的显存与训练时间随之上升，长轨迹还需要截断或摘要压缩，压缩本身会丢反馈细节。

去重防污染是数据基座不可让步的底线。KernelBench 系基准的测试用例与参考实现是公开的，合成数据或爬取数据若混入基准原题，评测就失去意义。工程做法是三重去重：源码级做归一化后的哈希比对（去注释、统一变量名后比对）；语义级用参考实现的接口签名与形状集合做匹配；轨迹级比对中间态的 diff 序列，防止“换了变量名但编辑路径完全相同”的泄漏。防污染还要管住评测侧：训练数据里出现的形状组合，在评测时必须用留出的形状，否则模型可能记住了该形状的最优 tile 而非学会推导。

代价是数据吞吐：三重去重中的语义匹配需要对每条样本跑接口提取，轨迹级比对是序列对齐，二者都在 CPU 侧，构成数据管线的吞吐瓶颈，尤其在合成数据量大的时候。工程判断是把源码哈希做成第一道快速过滤（O(1) 查表），只对通过者做语义与轨迹比对，把昂贵的检查留给少数可疑样本。例子：一条合成轨迹的最终代码与基准某题的参考实现变量名不同但控制流完全一致，源码哈希未命中，语义匹配发现接口签名与形状集合完全重合，判定为污染并剔除，避免了评测分数虚高。

六 · 奖励、数据与容量的耦合点

把上述四件事放在容量视角下看，它们共同决定了一个容易被忽略的量：每条有效训练样本的评测卡时。多轮奖励稠密化抬高单轨迹评测次数，robust reward 的全量 oracle 与审计抬高单次评测成本，TRLOO 的 K 值抬高组采样规模，合成数据的 profile 标注抬高数据准备成本，去重则把成本从 GPU 挪到 CPU 管线。这五项相乘，就是 RL 数据侧对评测集群的实际压力。

环节成本载体对容量的影响可压缩手段
稠密多轮奖励单轨迹编译+跑测次数线性放大评测 GPU 分钟缩短轨迹、合并低信息轮
robust 闸门全量 oracle、重复计时单次评测成本升一个量级采样审计、快速路径
TRLOO 的 K组采样规模评测负载按 K 倍增按难度分层设 K
合成数据标注中间态 profile 采集数据准备占用评测卡时模板扰动复用、批量采集
去重防污染CPU 语义/轨迹比对数据管线吞吐瓶颈哈希预过滤、抽样深检

这张表的意义在于把“RL 训练是否共享评测集群”这个决策量化：若稠密奖励与全量 oracle 使单轨迹评测成本达到单次评测的数十倍，而轨迹采样又要按 K 倍增，评测集群的需求会远超训练集群的增量，共享会让训练排队等评测。工程判断是评测侧必须按峰值而非均值预留——RL 的采样是突发的、成组的，均值容量在组采样瞬间被打满，排队延迟直接转化为迭代周期变长。这也解释了为什么成本模型揭示的瓶颈常常不在训练卡时，而在评测吞吐：奖励越 robust、信用分配越精细、数据越干净，评测侧的负载就越重，容量配比必须跟着奖励与数据的设计一起算，而不是事后补。

奖励聚合的尾部风险与轨迹去重的容量账

多轮奖励的失效点不在均值而在尾部：单条轨迹里任一轮的 oracle 判定翻转，就会把整条轨迹的 advantage 符号带偏。稳健做法是对轮级奖励取截断均值而非算术平均，即 $$r_{\text{traj}}=\frac{1}{T}\sum_{t=1}^{T}\mathrm{clip}(r_t,\ q_{0.1},\ q_{0.9})$$，代价是每步多一次分位数估计与两次比较，在 rollout 侧引入可忽略的算力开销，但要求奖励服务保留逐轮原始分而非只回传聚合值——这直接放大了评测侧的存储与回放带宽，轨迹越长，落盘字节线性增长。更隐蔽的代价是置信度：截断会系统性压低高方差任务的奖励幅度，使这些任务在组内比较中被动降权，等价于对难任务做了一次无声的课程裁剪。

TRLOO 一类留一法基线在组规模为 G 时，每条轨迹的基线由同组其余 G−1 条构成，组内方差大时基线本身抖动剧烈，advantage 的噪声不再随 G 增大而收敛，反而在 G 较小时放大。工程判断是：组规模必须与任务奖励的离散度匹配，而不是统一取大；对判定为二值的 oracle，组内出现全对或全错时基线退化，此时应回退到跨组池化基线，代价是引入跨 batch 的同步点，拖慢 rollout 流水。

合成数据与轨迹 SFT 的容量压力集中在去重：n-gram 或语义指纹去重需要在写入前对全量轨迹建索引，索引内存随轨迹数线性增长，且去重判定是 O(1) 哈希查表但建表是 O(N) 扫描，N 为累积轨迹数。防污染还要求对评测集做反向查询，即每条新轨迹必须与 held-out 任务集比对，这一步的时延直接落在数据入库路径上，成为迭代节拍的隐性下限。可参考的取舍如下表。

环节主要代价失效条件
轮级截断奖励逐轮落盘带宽、难任务降权奖励服务只回传聚合值
TRLOO 基线跨 batch 同步点组内奖励全同或 G 过小
轨迹去重与防污染索引内存、入库时延评测集未隔离、指纹碰撞

系统层面的判断是：把去重与污染检查放在离线批处理而非在线入库，用一次全量扫描换取 rollout 路径的零阻塞；代价是污染窗口期内新轨迹可能短暂进入训练，需以版本化数据集快照封住这个窗口，快照本身的存储开销按轨迹字节数计，属于必须预留的容量项而非可压缩项。
