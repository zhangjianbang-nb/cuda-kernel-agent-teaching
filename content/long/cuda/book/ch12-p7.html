一 · 多轮奖励的折扣结构与 TRLOO 的方差账

多轮 kernel 生成里，奖励不是一次性标量，而是沿轨迹分布：第 t 轮编译通过给一分，第 t+1 轮 NCU 显示达到 SOL 的某个比例再给一分，最后一轮正确性 oracle 通过给终局分。若把每轮奖励简单相加，agent 会学会“先骗编译通过”而非“先想清楚 tile 形状”。工程上必须引入折扣因子 γ 与终局权重，把奖励写成

$$R(\tau)=\sum_{t=0}^{T}\gamma^{t}r_{t}+\lambda\,r_{\text{final}},\quad \gamma\in(0,1)$$

γ 太小则中段反馈被淹没，agent 只盯终局；γ 接近 1 则早期错误编译的噪声一直传到末端，梯度方差爆炸。代价是显性的：每一轮都要跑一次编译加一次 profile，单条轨迹的 wall-clock 时延随 T 线性增长，而 GPU 占用时间直接换算成 token 预算之外的算力成本。具体例子：一个 5 轮轨迹，若每轮编译 8 秒、NCU 采集 20 秒，单轨迹近 140 秒，batch 内 64 条轨迹并行也要排队等最慢的那条，吞吐被长尾轨迹拖住。

TRLOO（token-level leave-one-out）针对的正是这个方差问题。其思路是在同一 prompt 的 K 条采样轨迹内，对每条轨迹的优势估计做留一基线：

$$\hat{A}_{i}=\frac{1}{K-1}\sum_{j\neq i}\big(R_{i}-R_{j}\big)$$

相比全局均值基线，留一基线让优势的期望在组内为零，减少 prompt 难度差异带来的偏移。代价是 K 必须足够大才有统计意义，K 增大直接乘以采样成本；K 小则基线噪声反而放大梯度。工程判断是：把 K 与轨迹长度解耦，短轨迹（只到编译层）用大 K，长轨迹（到 profile 层）用小 K，按轮次分层采样，避免“为了统计把最贵的轨迹也复制 K 份”。

二 · robust reward：把 oracle 的脆弱性折进奖励函数

正确性 oracle 不是布尔神谕。浮点比较有容差，随机初始化有分布，边界 shape 有覆盖缺口。若奖励直接用“oracle 通过=1，否则=0”，agent 会收敛到对 oracle 漏洞过拟合的策略：例如只在测试 shape 上正确的 kernel。robust reward 的做法是把 oracle 输出变成带置信度的软标签，奖励写成

$$r_{\text{robust}}=\mathbb{E}_{x\sim\mathcal{D}_{\text{test}}}\big[\mathbb{1}(\text{err}(x)<\tau)\big]-\beta\cdot\text{Var}_{x}\big[\text{err}(x)\big]$$

第一项是跨测试分布的平均通过率，第二项惩罚误差方差——方差大的 kernel 在真实负载上更容易崩。β 是惩罚系数，调大则奖励偏向“稳而慢”的实现，调小则偏向“快而险”。代价体现在评测时延：要估计方差，每个候选 kernel 至少要在多个 shape、多个随机种子上跑，评测成本按测试点数量线性上升，且这些测试点本身要维护版本。具体例子：一个 reduction kernel 在 1024 元素上误差 1e-6、在 1e7 元素上误差 1e-2，布尔 oracle 可能因容差设置而放过它，robust reward 的方差项会把它压下去，代价是该 kernel 需要多跑 6 组 shape 才能被判定。

另一个机制是奖励裁剪与饱和：把单轮奖励截断到 [−1, 1]，防止某轮 profile 异常（如 GPU 被其他任务抢占导致时延虚高）产生巨幅负奖励，把整批梯度带偏。裁剪的代价是信息损失——真正灾难性的错误与普通错误在梯度上被同等对待，需要靠终局 oracle 兜底。

三 · 合成数据的生成-过滤-去重三段流水

合成 kernel 任务的数据不是“让 LLM 随便写题”。可用的流水是：从真实算子库（如 PyTorch 的 aten 算子签名）抽取 shape 与 dtype 组合作为种子，用模板生成参考实现与测试用例，再让强模型生成候选 kernel，最后用 oracle 过滤。过滤环节的关键指标是“可验证率”——候选 kernel 中能通过编译且通过至少一个测试点的比例。这个比例决定合成数据的有效产出，低可验证率意味着大量 token 花在生成不可编译的代码上。

去重是防污染的第一道闸。文本级去重（n-gram 重叠）不够，因为同一 kernel 可以被改写成不同风格。工程上用的是语义指纹：对生成的 kernel 抽取特征——循环结构、tile 尺寸、共享内存用量、同步原语序列——做近似哈希，聚类后每簇只保留一个代表。代价是特征抽取本身要解析 CUDA AST，解析失败的样本只能退回文本去重，形成覆盖缺口。具体例子：两个候选 GEMM kernel 文本差异很大，但都是 128×128 tile、双缓冲、同一 warp 分片策略，语义指纹会把它们归为一簇，避免训练集里同一策略被重复计权。

合成数据的另一个代价是分布偏移：模板生成的 shape 分布与生产负载不一致，agent 在合成集上表现好不代表在真实算子图上好。缓解手段是把生产 trace 中的真实 shape 按频率采样进合成集，代价是需要生产侧的数据脱敏与采样管道，属于平台运维的职责范围。

四 · 轨迹 SFT：把多轮交互压成可训练序列

轨迹 SFT 与单轮 SFT 的区别在于样本是“状态-动作-反馈”的三元组序列，而非一段代码。构造时要把编译错误信息、NCU 摘要、oracle 判定都序列化进上下文，让模型学会“读反馈再改”。序列化格式的选择直接决定训练效率：把 NCU 的完整 metric 表塞进上下文会撑爆长度，工程上只保留与 roofline 判定相关的少数几个指标（如 achieved occupancy、DRAM throughput、SM busy），其余折叠成一句定性描述。

代价有两处。其一是上下文长度：一条 5 轮轨迹若每轮带 2k token 的反馈，总长可达 10k 以上，训练时的显存与注意力计算按长度平方增长，batch size 被迫压小。其二是样本筛选：并非所有轨迹都值得 SFT——失败的轨迹里也有“正确诊断错误”的好行为，需要按“反馈利用率”打标，即模型是否在下一轮针对反馈做了修改。这个打标本身要跑一次差异分析，属于离线数据工程的固定开销。具体例子：一条轨迹第一轮编译报 shared memory 超限，第二轮模型把 tile 从 256 降到 128 并通过，这条轨迹的“读反馈”行为值得保留；另一条轨迹连续三轮报同一错误、模型只是换措辞，则应丢弃。

五 · 防污染：基准与训练集的隔离带

KernelBench 系基准的题目一旦进入训练集，评测数字就失去意义。防污染不是一次性清洗，而是持续的组织流程：训练数据入库时打上来源标签，基准题目入库时打上冻结标签，两者在采样时做集合交集检查。检查粒度要到语义指纹级，因为文本级检查挡不住改写。代价是每次基准版本升级都要重跑全量交集检查，且语义指纹的误报会把合法样本踢出训练集，降低数据利用率。

更隐蔽的污染是“答案泄漏在反馈里”：若某条轨迹的 NCU 输出中包含了参考 kernel 的源码片段（例如 profiler 注释），模型可能在后续轮次直接抄。工程上要在反馈序列化时做源码剥离，只保留指标与错误码。代价是剥离规则要随工具链版本维护，规则漏一条就是一个泄漏通道。具体例子：编译器的 verbose 输出可能带出内联函数的源码行，若原样喂给模型，等于把部分参考实现送进了上下文；剥离后模型只能看到“寄存器压力过高”这类诊断，学习的是诊断到修改的映射而非抄写。

治理上，基准版本冻结与 oracle 变更评审是两条硬规则：冻结期内基准题目与测试用例不得改动，oracle 的任何容差调整都要走评审并重跑历史成绩，否则跨版本数字不可比。这两条规则的成本是发布节奏变慢，收益是路线图上的验收标准可审计。团队路线图里，能力矩阵的“评测”一列若没有这两条规则支撑，季度里程碑就无法用同一把尺子衡量。

六 · 投入配比：RL 与 SFT 的工程判断

RL 与 SFT 的投入配比不是拍脑袋的比例，而是由“可验证奖励的密度”决定的。若任务的可验证率低（大量候选无法编译），RL 的信号稀疏，此时应把预算压在 SFT 上，用轨迹数据先把模型的“可编译率”抬起来；若可验证率高、奖励区分度好，RL 的边际收益才显现。判断指标是每千 token 产生的有效梯度步数，SFT 侧看样本利用率，RL 侧看组内优势的方差。

代价结构不同：SFT 的成本主要是数据工程与训练算力，一次投入可复用；RL 的成本是持续的采样与评测算力，随训练步数线性增长，且评测管道的吞吐是瓶颈。具体例子：若评测平台每小时只能判定 200 个候选 kernel，RL 的 batch 再大也只能等评测回填，此时增加 RL 算力是浪费，应先扩容评测侧或降低每条轨迹的评测点数。路线图按能力排期时，RL 一列的验收标准应写成“单位评测算力下的有效更新次数”，而非“训练步数”，否则会把瓶颈藏在数字背后。

最后落在治理规则上：合成数据的来源标签、轨迹 SFT 的筛选标准、防污染的交集检查，三者共享同一套元数据 schema，才能让季度评审时把“数据”一列的变化追溯到具体流水段。没有这套 schema，路线图上的数据投入就是一笔无法审计的账。

奖励信号失真时，路线图该在哪一层踩刹车

多轮奖励在路线图里不是“RL 工程师一个人的事”，它横跨评测、数据与治理三条线。机制上，奖励由三部分拼成：正确性 oracle 的布尔判定、profile 得到的性能比、以及轨迹级的格式/约束检查。三者权重一旦在季度内被悄悄改动，历史轨迹的 advantage 就不可比，TRLOO 之类的留一法基线会失效——因为它假设同一 prompt 下的采样共享同一奖励尺度。失效条件很具体：当 oracle 从“逐元素容差”切换到“分块容差”，同一批轨迹的通过率分布整体平移，留一均值被系统性污染，策略会把“猜中容差边界”学成一种能力。代价体现在 token 与编译时间上：为压住这种漂移，每轮需重跑基线轨迹做校准，等于把采样预算的一部分固定成“不可用于探索的锚点”。例子：某季度把性能项从“相对 eager 的加速比”改为“相对上一版 kernel 的加速比”，奖励尺度随基线浮动，团队必须在路线图里写明“基线版本冻结”这条治理规则，否则 RL 与评测两个角色的验收标准会对不上。

robust reward 的边界在于它只能吸收噪声，不能吸收偏差。可用的小表把三类失真分开：

失真类型表现路线图对策系统代价
随机噪声同一 kernel 多次 profile 抖动多次采样取中位数，奖励做截断profile 次数上升，单轨迹时延增加

公式上，稳健奖励可写成对原始奖励的截断与去偏组合：

$$r_{\text{robust}}=\mathrm{clip}\left(\frac{r-\mu_{\text{base}}}{\sigma_{\text{base}}},-\tau,\tau\right)-\lambda\cdot\mathbb{1}[\text{constraint violated}]$$

其中基线统计量必须来自冻结的 oracle 版本，否则 μ 与 σ 本身在漂移。代价是双重的：clip 会丢掉真实的大幅改进信号，λ 惩罚项让“高收益但踩线”的轨迹直接归零，等于用样本效率换可信度。工程判断是：把 τ 与 λ 写进治理规则而不是留在代码里，因为它们是验收标准的一部分，改动需走评审。

合成数据与轨迹 SFT 的失效条件不在生成端，而在去重与防污染。合成 kernel 任务若只按“算子名 + 形状”去重，会漏掉同构改写（同一计算的不同 tile 划分），导致 SFT 集里同一模式反复出现，策略过拟合到特定 launch 配置。防污染需要三层：与基准测试集做算子级和形状级交叉比对、对轨迹做语义指纹（如 SASS 指令序列的哈希）去重、以及保留一份“从未进入训练”的留出集供季度验收。代价是数据管线变长：指纹计算与交叉比对让每条轨迹多一次离线处理，合成数据的可用率下降，团队要在路线图里为“数据工程”单列角色工时，而不是把它塞进 RL 工程师的排期。例子：把 KernelBench 系基准的题面直接喂给合成管线，若不剔除，验收时留出集与训练集重叠，季度里程碑的“泛化提升”就是假的——这正是把“去重防污染”固化为组织流程而非一次性脚本的理由。

奖励口径固化之后的失效边界与治理成本

把多轮奖励、robust reward 与 TRLOO 写进路线图，真正要冻结的不是算法名，而是奖励函数的版本与判定口径。TRLOO 的工程含义是：对同一 prompt 采多条轨迹、逐条留一法估计优势，用其余轨迹的均值作基线，形式为 $$A_i = r_i - \frac{1}{K-1}\sum_{j\neq i} r_j$$，K 为组内轨迹数。它把奖励的绝对尺度消掉，只保留组内相对排序，因此对 reward model 的系统性偏移不敏感，但对组内方差极敏感：当 K 小、轨迹正确性高度同质（全对或全错）时，优势趋近于零，梯度信号消失，算力全花在采样上。这是本方案第一个失效条件——它要求任务本身有可分辨的正确性梯度，而不是靠奖励塑形硬造差异。

第二个边界在合成数据与轨迹 SFT 的接缝处。合成 kernel 任务若由模板批量生成，去重必须落在语义层而非文本层：同一算子换形状、换 dtype、换 tile 配置会生成大量文本不同但考察点相同的样本，文本级去重会漏，语义级去重又要付出编译与运行代价。防污染同理，基准题一旦进入训练集，评测分数即失去意义，因此治理规则要求基准版本冻结、训练集与冻结基准做算子级与输入分布级双重比对，任何命中即剔除。这笔开销是 token 与编译时间，不是显存。

环节主要代价失效触发条件
TRLOO 组内采样K 倍 rollout 时延组内正确性同质，优势塌缩
语义去重编译+运行验证时延仅做文本哈希，漏同构样本
基准防污染比对训练前扫描 token 与算子清单基准未冻结、版本漂移

第三个边界是组织性的：robust reward 的鲁棒性来自多信号交叉（正确性 oracle、profile 达标、时延阈值），每加一个信号就多一个需要评审的变更点。因此路线图把 oracle 变更纳入评审门禁，任何奖励权重调整都要重跑一组固定回归轨迹，确认排序未翻转。代价是每次调参的验证周期被拉长到一次完整回归的时延，收益是奖励口径不会在季度中途被悄悄改写，使跨季度的 RL 投入配比决策有可比基线。
