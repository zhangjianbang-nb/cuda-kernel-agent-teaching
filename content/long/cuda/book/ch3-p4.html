一 · 漏检率：把 checker 当成被测对象

在可信评测流水线里，checker 本身是一个需要被审计的组件，而不是天然可信的裁判。工程上最危险的情形是 checker 的假阴性：一个数值错误的 kernel 被判为通过。定义漏检率 FNR 为「错误实现被判通过」的条件概率，则评测流水线的有效严格度不是通过率，而是 1 − FNR 乘以真实错误分布的质量。问题在于，错误分布不是均匀的：LLM 生成的 kernel 的错误集中在边界形状、非对齐 stride、归约尾部、mask 处理、dtype 溢出这几类，而随机生成的测试输入几乎不覆盖它们。

因此 checker 审计的第一步是把输入生成从「随机」改成「分层对抗」。具体机制是：按 kernel 的语义签名（形状、stride、dtype、归约轴、是否含 mask）建立输入族，每个族内至少包含对齐与非对齐、整除与非整除、极值与次正规数、空张量与单元素张量。一个可操作的伪代码思路是：

$$\text{FNR} \approx \frac{1}{|E|}\sum_{e\in E}\mathbf{1}\big[\text{checker}(k_e, x_e)=\text{pass}\big],\quad x_e\sim \text{Family}(e)$$

其中 E 是已知错误实现的集合，ke 是对应错误 kernel。代价是显存的：每个输入族要保留参考输出，参考实现（通常是 PyTorch eager 或高精度 CPU 版本）在大形状上的显存占用与 kernel 本身同量级，若同时跑多族则峰值显存翻倍，直接压缩了可并发评测的卡数。具体例子：一个 softmax kernel 在 N=1024 对齐时正确、在 N=1000 非对齐时尾部越界读到脏数据，若 checker 只采样 2 的幂形状，这个错误实现的漏检率就是 1，而它在 KernelBench 式的通过率统计里会被记成一次干净的成功。

二 · 变异测试：用人工注入的错误给 checker 打分

漏检率无法直接测量，因为真实错误分布未知。变异测试提供了一个可计算的替代：对参考实现注入受控变异，得到一组「必然错误」的 kernel，然后看 checker 能否全部拒绝。变异算子应当与 LLM 的真实失败模式对齐，而不是随便改一个常数。有效的算子集合包括：把归约的累加 dtype 从 fp32 降到 fp16、把 __syncthreads() 删除、把边界判断的 < 改成 <=、把 shared memory tile 的 stride 偏移一位、把 atomicAdd 换成非原子写、把尾块循环的上界减一。

变异测试的产出是变异得分 MS：

$$\text{MS}=\frac{|\{m\in M:\text{checker}(k_m)=\text{fail}\}|}{|M|}$$

工程判断上，MS 低于某个阈值就说明 checker 的容差过松或输入覆盖过窄，此时任何通过率数字都不可信。代价是编译时间：每个变异体都要独立编译并跑一遍，若变异体数量为几十、每个 kernel 编译加执行在秒级，单轮审计的墙钟时间会从分钟级涨到十分钟级，这在多轮 RL 的奖励计算里是不可接受的，因此变异审计应当作为离线门禁而非在线奖励。具体例子：一个 reduction kernel 的变异体把 fp32 累加改成 fp16，输出在 N=4096 时相对误差约在千分之一量级，若 checker 的容差设为 rtol=1e-2，该变异体会被判通过，变异得分暴露了容差口径与任务精度要求不匹配——这正是「噪声压到可判别 3% 差异」之外必须单独审计的正确性维度。

三 · Fuzz：把形状空间当成攻击面

变异测试覆盖的是实现逻辑错误，fuzz 覆盖的是输入空间错误。对 GPU kernel 而言，fuzz 的独特之处在于形状与 stride 的组合爆炸，以及非法配置（超出 shared memory 容量、超出寄存器预算、grid 维度溢出）会以编译错或运行错的形式出现，而不是数值错。一个实用的 fuzz 策略是差分 fuzz：同一输入分别喂给候选 kernel 与参考实现，比较输出；同时对候选 kernel 做「配置扰动」，即在合法边界附近改变 block size、tile 大小，观察是否出现越界或竞态。

竞态的检测不能靠单次比较，因为非确定性错误可能在小概率下才暴露。机制上需要重复执行同一输入并比较多次运行的输出一致性，或用 compute-sanitizer 类的工具做内存检查。代价是时延：重复执行 R 次使单输入成本乘以 R，而竞态窗口往往需要 R 在数十以上才有可观检出概率，这与「warmup/重复次数/中位数」的性能计时口径是两套完全不同的重复语义——性能重复是为了压噪声，正确性重复是为了撞竞态，混用会同时污染两者。具体例子：一个并行归约在 blockDim=256 时正确，在 blockDim=1024 时因 shared memory 尾部未初始化而偶发错误，差分 fuzz 单次通过，重复 50 次才暴露；若流水线只做单次比较，这类错误会稳定漏检。

四 · 形式验证与合约验证：把「正确」变成可判定的命题

数值 oracle 只能采样，形式方法则试图覆盖整个输入域。对 GPU kernel 现实可行的路径不是全自动定理证明，而是合约验证：要求 kernel 携带前置条件（形状、对齐、dtype、值域）与后置条件（输出形状、数值误差界、无越界写），然后用符号执行或 SMT 在受限域上检查。合约的写法直接决定可验证性：把「输出等于参考实现」写成后置条件是不可判定的，必须降解为可检查的局部性质，例如「每个输出元素是输入子集的和」「索引上界不超过 N」「shared memory 访问偏移在 [0, tile) 内」。

形式验证的代价是编译时间与人力：SMT 求解在含浮点运算的路径上极易爆炸，实践中通常只对索引算术与内存安全做形式化，数值误差仍交给采样 oracle。这意味着形式验证的产出是「无越界、无未定义行为」的强保证，而不是「数值正确」的强保证，两者必须分开报告，否则会把内存安全的形式通过误读成数值正确。具体例子：一个 CuTe 布局的 copy kernel，其索引表达式可以在符号域上证明对所有合法形状不越界，但它的 dtype 转换舍入行为仍需数值 oracle 覆盖；合约验证通过而数值 oracle 失败是常见组合，流水线必须能表达这种部分可信。

五 · 怎么证明「正确」：分层证据与不可让渡的门禁

没有任何单一手段能证明正确，工程上可行的做法是分层证据链，每层给出不同强度的保证并标注其覆盖范围。下表给出各层的机制、保证类型与主要代价：

手段保证类型覆盖范围主要代价
采样 oracle数值近似采样输入族参考输出显存
变异测试checker 灵敏度已知错误模式编译时间线性增长
差分 fuzz输入空间鲁棒形状/stride 组合重复执行时延
合约验证内存安全、索引正确受限符号域SMT 求解时间

门禁设计的关键判断是：哪些层是硬门禁，哪些是软信号。内存安全与编译/运行错应当是硬门禁——一个会越界写的 kernel 无论性能多好都不能进入排名，因为它的错误会污染后续所有测量。数值容差与变异得分则应当是软信号，进入可信度评分而非一票否决，原因是容差口径本身依赖任务精度要求，硬编码会误杀合法的低精度实现。这与失败分类（编译错/运行错/超时/数值错/性能不达标）的口径直接咬合：形式验证失败应归入运行错或独立类别，不能与数值错混计，否则失败分布会失真。

具体例子：一条流水线对同一批候选 kernel 报告「通过率 82%」，但变异得分只有 0.4，说明 checker 对 fp16 累加与边界 off-by-one 都不敏感，这个 82% 的有效严格度远低于表面数字；把变异审计设为离线门禁后，同一批候选的有效通过率降到显著更低的水平，agent 排名随之改变。这正是评测结果反复抖动的一个被忽视的来源：抖动不只来自计时噪声，也来自 oracle 的灵敏度漂移。

六 · 审计节奏：离线重审计与在线轻校验的分离

把上述手段全部放进在线奖励计算会拖垮吞吐，因此工程上必须分离节奏。在线侧只跑固定输入族的采样 oracle 加编译/运行错检查，保证单次奖励计算的时延可控；离线侧周期性跑变异测试、差分 fuzz 与合约验证，产出 checker 的灵敏度报告与覆盖缺口，并据此更新在线输入族。这个循环的机制是：离线审计发现的漏检模式被固化为新的输入族或新的变异算子，在线侧随之收紧。

代价体现在 token 与算力预算的分配上：离线审计消耗的是评测集群的墙钟时间而非 agent 的 token，但它决定了在线奖励的可信度上限；若离线审计频率过低，checker 会随任务分布漂移而悄悄退化，而在线通过率数字看不出任何异常。具体例子：当基准任务从 fp32 为主转向 bf16 与 fp8 混合精度时，原有容差口径对新 dtype 的舍入误差不再敏感，变异得分下降而在线通过率反而上升——这种「通过率上升但可信度下降」的组合是审计节奏缺失的典型症状，只有离线重审计能把它识别出来。

工程判断落在最后一点上：可信评测的瓶颈往往不是 GPU 时间，而是 oracle 的灵敏度是否跟得上任务分布的变化；把 checker 当被测对象、把变异得分与形式验证结论作为一等公民写进流水线报告，比再多跑几轮计时重复更能稳定 agent 排名。

当“正确”本身需要被审计：checker 漏检的边界与代价

把 checker 当成 oracle 是一种工程上的自我欺骗：oracle 的可信度不是二值的，而是一条随输入分布漂移的曲线。审计的核心不是再跑一遍 checker，而是构造一个与被测 kernel 输出空间同构、但真值已知的“影子任务集”，用它对 checker 做变异测试。具体机制是：对每个基准任务，按算子语义生成三类变异体——(a) 数值等价但实现路径不同的参考实现（如换累加顺序、换分块形状），checker 必须判过；(b) 语义偏移的“近似错解”（如漏掉边界 mask、把 fp32 累加降为 fp16、把归约维度搞反），checker 必须判错；(c) 只在极端输入下暴露的错解（NaN/Inf 传播、非对齐尾块、零长度张量）。漏检率定义为 checker 在 (b)(c) 上判过的比例，误杀率定义为在 (a) 上判错的比例，二者构成一条 ROC 式的取舍曲线：

$$\text{漏检率}=\frac{|\{x\in \mathcal{M}_{\text{bad}} : \text{checker}(x)=\text{pass}\}|}{|\mathcal{M}_{\text{bad}}|},\qquad \text{误杀率}=\frac{|\{x\in \mathcal{M}_{\text{good}} : \text{checker}(x)=\text{fail}\}|}{|\mathcal{M}_{\text{good}}|}$$

这条曲线的系统代价非常具体：每增加一个变异体就多一次编译加执行，一个含数十个任务的基准若每个任务扩出十余个变异体，沙箱内的编译时间与 GPU 占用会成倍上升，而变异体的构造本身要消耗生成侧的 token——用 LLM 造“近似错解”比造正确解更难，因为它必须错得足够隐蔽又不至于编译失败。工程判断是：变异集应固定成版本化资产，随基准一起冻结，而不是每轮评测临时生成，否则漏检率本身不可复现。一个典型失效条件是容差型 checker：当任务判据用相对误差阈值时，把 fp32 降为 tf32 的错解可能恰好落在阈值内被判过，此时漏检率对阈值极其敏感，审计必须把阈值当作被测参数一并扫描，而不是当作常量。

模糊测试补的是变异测试覆盖不到的输入空间。机制上，fuzz 不是随机撒数，而是按算子的形状约束做结构化采样：维度组合（奇偶、质数长度、跨 warp 边界的 tile 尺寸）、dtype 组合、stride 与 layout（转置、非连续、广播）、以及数值域（极大极小、次正规数、恰好等于容差边界的差值）。判定用差分 oracle：同一输入分别喂给被测 kernel 与一个慢但可信的参考实现（CPU 端或朴素 GPU 实现），逐元素比对并记录最大绝对误差与最大相对误差的分布，而不是只看单点是否超阈。代价在于参考实现的时延：朴素实现往往比优化 kernel 慢一到两个数量级，fuzz 的吞吐因此被参考端卡住，实践中要把 fuzz 预算按“每小时有效用例数”而非“用例总数”来定额。失效条件是差分 oracle 自身有 bug——此时 fuzz 会把参考实现的错误当成被测 kernel 的错误，表现为误杀率异常升高，审计流程必须包含对参考实现的独立单元测试，否则整条链路的可信度锚点就是空的。

形式验证与合约验证走的是另一条路：不枚举输入，而是对 kernel 的前置/后置条件做演绎。合约式做法是在 kernel 入口与出口插入断言——索引不越界、共享内存写入前必先同步、归约结果满足结合律下的等价类、输出张量的每个元素被恰好写一次——再用符号执行或 SMT 在有限位宽上求解违例。它能给出“在给定合约下不存在反例”的强结论，但边界很硬：合约本身写错则一切作废，且浮点语义在 SMT 中只能以近似建模（舍入模式、非结合性），因此形式验证对整数索引与内存安全的结论远强于对数值正确性的结论。系统代价是求解时间随线程块规模与循环展开深度超线性增长，一个中等规模的 tile kernel 的符号执行可能耗时数十分钟到数小时，远超评测流水线单轮的时延预算，所以它只能作为离线门禁、按版本触发，而不是每个候选 kernel 都跑。一个具体例子：对带尾块 mask 的 GEMM kernel，形式验证能证明“当 M 不是 tile 整数倍时不会越界读”，但无法证明“fp16 累加在 K 很大时误差仍在阈值内”——后者只能交给 fuzz 的差分统计。因此可信评测的工程判断是分层：变异测试管语义偏移，fuzz 管输入空间，形式验证管内存与索引安全，三者各自有明确的失效面，任何一层被当成唯一 oracle 都会在对应失效面上静默漏检。
