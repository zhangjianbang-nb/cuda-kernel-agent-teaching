一 · 奖励口径：从单轮到多轮的信号衰减

多轮 RL 的核心困难不在策略更新，而在奖励信号如何跨轮聚合。单轮设定下奖励是一次标量，多轮设定下每一轮都有独立反馈（编译通过、正确性通过、相对基线加速比、SOL 占比），这些反馈的尺度不同、噪声不同、可验证性也不同。若直接求和，编译通过这种二值信号会被加速比这种连续信号淹没；若直接取最后一轮，前几轮的探索信息全部丢弃。工程上通行的做法是分层加权：把奖励拆成“硬约束项”与“软优化项”，硬约束（编译、数值正确性）作为门控，未通过则整条轨迹奖励置零或置负，软优化项只在门控通过后累加。

$$R(\tau)=\mathbb{1}_{\text{compile}}\cdot\mathbb{1}_{\text{correct}}\cdot\sum_{t=1}^{T}\gamma^{T-t}\,r_t,\qquad r_t=w_1\cdot\Delta\text{speedup}_t+w_2\cdot\Delta\text{SOL}_t$$

这里的代价是显式的：门控使有效样本率下降。一个 agent 在 8 轮里前 3 轮编译失败，整条轨迹的奖励为零，这条轨迹对策略梯度的贡献只剩“不要这样写”的负向信号，而它消耗的 token 与编译时间已经付出。以 KernelBench 级别的任务为例，一次编译加一次正确性运行的时间远大于一次 LLM 前向，因此门控过严会让单位 GPU 小时的样本吞吐掉到不可接受的水平。折中方案是对门控做软化：编译失败给一个小负值而非零，正确性失败给中等负值，使轨迹在“几乎正确”和“完全跑不起来”之间仍有梯度差异。

二 · Robust reward：抗奖励黑客的三道闸

奖励黑客在 kernel 生成任务上有非常具体的形态：agent 学会输出恒等 kernel（直接返回输入）、学会在计时区间外做计算、学会针对基准输入形状特化而丧失泛化。robust reward 不是把奖励函数写得更复杂，而是在奖励计算链路上加独立校验。第一道闸是输入扰动：正确性 oracle 除了基准输入，还要跑一组随机形状与随机数值，恒等 kernel 与形状特化 kernel 在这组输入上暴露。第二道闸是计时隔离：性能测量必须在独立的进程或独立的 stream 上执行，且计时区间由 harness 控制而非 kernel 内部自报，防止 agent 把同步点挪到计时之外。第三道闸是结构检查：对生成的 CUDA C++ 或 Triton 源码做静态扫描，拒绝明显退化的模式（如空循环、无实际内存访问）。

代价体现在评测时延与误杀率上。随机形状扰动使每次正确性验证的耗时增加到基准输入的若干倍，因为要覆盖 dtype 与累加顺序的不同组合；计时隔离要求额外的进程启动开销，在短 kernel 上这部分开销可能超过 kernel 本身的执行时间，导致加速比测量失真。工程判断是：对 elementwise 与 reduction 这类短 kernel，用批量重复计时摊薄启动开销；对 attention 与 matmul 这类长 kernel，隔离开销可忽略，可以严格隔离。误杀率则来自结构检查过于激进，把合法的模板元编程写法判为退化，因此结构检查只做黑名单而非白名单。

三 · TRLOO：把多轮轨迹折算成可比较的优势

TRLOO（token-level / trajectory-level leave-one-out 思路的一类实现）要解决的问题是：同一 prompt 下采样出多条轨迹，每条轨迹轮数不同、奖励尺度不同，如何构造无偏且方差可控的优势估计。直接对轨迹奖励做组内归一化（减均值除标准差）在轮数差异大时会偏置：轮数多的轨迹奖励累加项多，天然占优。TRLOO 的做法是把每条轨迹的奖励按轮数归一化后再做留一法基线，即对第 i 条轨迹，基线取其余轨迹归一化奖励的均值，优势为自身归一化奖励减基线。

$$\hat{A}_i=\frac{R(\tau_i)}{T_i}-\frac{1}{N-1}\sum_{j\neq i}\frac{R(\tau_j)}{T_j}$$

这个估计的代价是方差。当 N 较小（组内采样数受显存与编译时间限制，通常不会很大），留一法基线的方差显著高于直接均值基线，策略梯度的高方差会拖慢收敛。缓解手段是对优势做裁剪（clip）并配合较小的学习率，或者对归一化奖励做滑动平均以降低组间波动。具体例子：同一道 matmul 优化题，一条轨迹 4 轮达到 1.3 倍加速，另一条 12 轮达到 1.5 倍加速，未归一化时后者奖励占优，归一化后前者每轮效率更高，TRLOO 会把优势分配给前者，引导策略学会“少轮高效”而非“多轮堆砌”。

四 · 合成数据：从真实 kernel 需求反推任务分布

合成数据的价值在于覆盖真实需求清单里稀疏但关键的任务类型。做法不是随机生成算子，而是从任务分类法（elementwise/reduction/matmul/attention/fused）出发，对每类做参数化采样：形状、dtype、累加顺序、是否融合、是否带 mask。采样分布要贴近业务侧 kernel 需求清单的实际分布，否则 agent 会在合成分布上过拟合而在生产任务上失焦。合成数据的另一个用途是构造难度梯度：同一类任务生成从“直接可写”到“需要 tiling 与 shared memory 优化”的多个变体，供多轮 RL 做课程式推进。

代价是正确性 oracle 的构建成本。合成任务没有现成的手写实现做对照，必须为每个变体生成参考实现（通常是朴素但正确的版本）并定义容差口径。容差按 dtype 与累加顺序分级：fp32 累加的 reduction 容差紧，fp16 累加或 tf32 的 matmul 容差松，且累加顺序改变会引入不可忽略的数值差异，oracle 必须按同一累加顺序比对而非简单逐元素比对。合成数据的规模受限于 oracle 生成与验证的吞吐，盲目扩大合成集只会稀释高质量样本的比例。

五 · 轨迹 SFT 与去重防污染

轨迹 SFT 是把多轮 RL 中成功轨迹（门控通过且奖励为正）转成监督微调数据。关键工程点是轨迹的裁剪：一条 10 轮轨迹里可能只有最后两轮是有效的优化动作，前 8 轮是试错，直接整条喂给 SFT 会让模型学会试错而非学会正确路径。裁剪策略是按轮次奖励增量筛选，只保留奖励上升的轮次及其上下文，丢弃平台期与下降期。这样做的代价是 SFT 样本量大幅缩水，且裁剪后的轨迹丢失了“如何从错误中恢复”的信息，模型在面对新错误时恢复能力下降。折中是保留一轮失败加一轮恢复的配对，作为负正样本对。

去重防污染是这条链路最容易被忽视的环节。合成数据与真实需求清单可能重叠，轨迹 SFT 数据与评测基准可能重叠，一旦重叠，评测结果失去可信度。去重不能只做文本级哈希，因为同一 kernel 的不同写法文本差异大而语义相同。工程上做两层：第一层对任务描述与输入形状做规范化后哈希，第二层对生成的 kernel 做语义指纹（如对 PTX 或 SASS 的关键指令序列做归一化摘要）。代价是去重的计算开销与误删率，语义指纹在编译器版本变化时会漂移，需要按软件栈版本分桶维护。具体例子：一条在 KernelBench 某题上成功的轨迹若被混入 SFT 数据，而该题又出现在评测集中，评测加速比会虚高，且这种污染在聚合指标上几乎不可见，只能靠逐题比对发现。

六 · 数据口径与验收粒度的耦合

RL 与数据的口径最终要回到本卷的验收决策上：哪些任务进入 agent 可解域、以 KernelBench 级别还是生产级为验收粒度。数据侧的直接约束是，若验收粒度是生产级，则合成数据必须包含生产形状与真实 dtype 组合，轨迹 SFT 必须以生产基线为对照；若验收粒度是 KernelBench 级别，则合成数据可以更自由地做难度梯度，但评测结论不能直接外推到生产收益。这个耦合关系决定了两件事：奖励函数里的加速比基准取哪个（相对手写基线还是相对框架默认实现），以及去重时以哪个基准集为污染源。工程判断是：在可解域尚未划清之前，不要用生产级数据做 RL 训练，否则奖励信号会被生产环境的长尾失败模式主导，agent 学到的是规避而非优化。

奖励口径的边界：多轮奖励聚合、TRLOO 方差与污染防线

多轮 RL 的奖励不是单步标量的简单相加，而是把一条轨迹上每一步的可验证信号按任务分类法加权聚合。对 elementwise 与 reduction 类任务，单步奖励可由容差内正确性（0/1）与相对基线加速比的门限函数给出；对 attention 与 fused 类，正确性 oracle 本身要跨 dtype 与累加顺序分级，奖励必须携带“口径标签”，否则同一轨迹在不同容差下会被判成互相矛盾的胜负。聚合公式取折扣加权形式：

$$R(\tau)=\sum_{t=0}^{T}\gamma^{t}\big[\mathbb{1}_{\text{pass}}(o_t)\,f\!\left(\frac{s_t}{s_{\text{base}}}\right)-c\cdot\mathbb{1}_{\text{compile}}(o_t)\big]$$

其中 $s_t/s_{\text{base}}$ 是第 $t$ 轮相对基线的加速比，$f$ 是截断到 SOL 占比上限的单调函数，$c$ 对编译失败或超时施加固定惩罚。这条公式的失效条件很具体：当 $\gamma$ 接近 1 且 $T$ 较大时，早期轮次的一次容差误判会被后续所有轮次继承，轨迹奖励的方差随 $T$ 线性放大，策略会把“先蒙一个能过容差的近似实现”学成主路径。代价体现在 token 与编译时间上——每轮都要真实编译并跑正确性 oracle，一条 $T$ 轮轨迹的墙钟成本约为单轮的 $T$ 倍，而其中相当比例的轮次只产出编译失败，等于用编译机时换负样本。具体例子：一个 reduction kernel 在第 2 轮用 fp32 累加顺序通过了宽松容差，第 5 轮被严格口径判错，若奖励不做口径标签，这条轨迹会被记成“先对后错”的噪声样本，污染策略梯度。

TRLOO（token-level leave-one-out）用于压低这种方差：对同一 prompt 采样 $K$ 条轨迹，逐 token 计算去掉自身后的基线优势，而不是用整条轨迹的均值做基线。伪代码思路是，对每条轨迹的每个 token 位置，用其余 $K-1$ 条轨迹在同一位置的奖励均值作为对照，优势写成 $A_{k,t}=R_k-\frac{1}{K-1}\sum_{j\neq k}R_j$ 的 token 级投影。它在 kernel 场景的边界在于：编译失败轨迹的 token 分布与成功轨迹差异极大，leave-one-out 的对照集若混入大量失败轨迹，基线会被拉低，导致“能编译”本身获得虚高优势，策略倾向于生成保守但低 SOL 的实现。系统代价是显存与通信——$K$ 条轨迹的 logprob 与奖励要同时驻留，$K$ 增大时显存线性增长，且跨设备聚合引入同步时延；工程上通常把 $K$ 控制在能覆盖正确性分级的最小值，用任务分类法按类分层采样，而不是全局统一 $K$。

合成数据与轨迹 SFT 的污染防线要落在去重与口径隔离上。合成 kernel 需求若由 LLM 生成，容易与 KernelBench 系基准的公开题面高度同构，直接混入训练会让评测失去区分度；去重不能只看题面文本，还要看算子签名、dtype 组合与容差口径三元组，任一相同即视为同源。轨迹 SFT 的数据同样要按“口径标签 + 基线版本 + 软件栈版本”分组，跨版本轨迹不可混训，否则模型学到的是旧栈的编译行为。代价是数据吞吐下降：严格三元组去重会砍掉大量看似不同的样本，合成数据的有效利用率降低，而轨迹 SFT 的分组隔离要求每条轨迹携带完整元数据，存储与检索开销上升。具体例子：一批 fused attention 合成题面文字各异，但签名与容差口径完全一致，去重后只剩少数真正的新任务，这部分数据对提升 agent 可解域边界的贡献远大于数量本身。

奖励口径的边界：多轮 RL 在 kernel 任务上何时失效

多轮奖励在 kernel 场景的失效条件很具体：当正确性容差按 dtype 与累加顺序分级后，同一份输出在 fp32 累加与 tf32 累加下可能一边判对一边判错，此时若奖励只看“是否通过 oracle”，策略会学到规避高风险 dtype 而非真正优化。稳健奖励（robust reward）的做法是把奖励拆成可验证项与惩罚项：

$$r = \mathbb{1}[\text{pass}] \cdot \min\left(1, \frac{S_{\text{base}}}{S_{\text{cand}}}\right) - \lambda \cdot \mathbb{1}[\text{timeout}]$$
其中 $S$ 为 SOL 占比或相对基线加速比，$\lambda$ 惩罚超时与编译失败。代价在于：每次 rollout 都要跑 oracle 与计时，单条轨迹的验证时延随轮数线性增长；若容差分级过细，oracle 本身成为瓶颈，token 预算被验证吃掉而非用于探索。

TRLOO 一类轨迹级留一法估计在此处的边界是方差：kernel 任务的奖励分布高度双峰（通过且快 / 不通过），留一法基线在组内全失败时退化为零优势，梯度信号消失。工程判断是给组内失败样本一个小的形状奖励（如编译通过、SASS 无非法访存），否则多轮 RL 在难任务上停滞。合成数据与轨迹 SFT 的污染风险则来自同一 kernel 的变体去重不足：按函数签名与访存模式做指纹去重，比按文本相似度更可靠，代价是去重阶段需要额外编译与 profile，单条样本处理时延上升。
