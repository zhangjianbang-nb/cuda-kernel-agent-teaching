一 · 角色分工：为什么 coder 与 judge 必须拆开

把 kernel 生成塞进一个单体 agent，最直接的后果是“自评自改”闭环：同一个上下文既写代码又判断对错，模型会用语言层面的合理性替代执行层面的证据。工程上可行的拆法是四角色：coder 负责按签名与模板产出候选 kernel；judge 只做正确性裁决，输入是候选、参考实现、测试张量与容差契约，输出是布尔判定加失败定位；profiler 只读 NCU/SASS 与计时数据，输出结构化瓶颈标签；search 负责在历史尝试与已知成功 kernel 之间做检索与重组。四者共享同一份任务描述，但不共享彼此的推理轨迹——这是关键，轨迹共享会让 judge 被 coder 的辩解污染。

分工的代价是上下文与调用次数。一次完整闭环至少四次模型调用（生成、裁决、profile 解读、检索重排），token 消耗约为单体方案的两到三倍；换来的是错误归因的可分离性：编译失败、数值不符、性能不达标三类信号进入不同通道，不会被同一段自然语言含糊掉。具体机制上，judge 的判定函数应写成可执行契约而非提示词，例如对输出张量做 allclose(atol, rtol) 并附加 NaN/Inf 检查与形状断言，任何一项失败即返回带索引的失败记录。

$$\text{accept} = \mathbb{1}\big[\lVert y_{\text{cand}} - y_{\text{ref}}\rVert_\infty \le a + r\lVert y_{\text{ref}}\rVert_\infty\big] \wedge \text{shape\_ok} \wedge \text{finite\_ok}$$

性能代价体现在闭环时延：judge 需要真实执行，单次候选的编译加运行在秒级到十秒级，四角色串行会把每轮修复推到分钟量级；因此工程上常把 judge 与 profiler 合并为一次执行会话，先跑正确性再跑 profile，避免重复启动开销。一个具体例子：Triton 候选在 judge 阶段因归约轴顺序导致末维误差超容差，judge 返回“第 2 个测试用例、轴 1、最大绝对误差超限”，coder 只需改一行 tl.sum(..., axis=1)，而不是重写整个 kernel——定位粒度直接决定修复轮次的收敛速度。

二 · 编译错误解析：把 stderr 变成结构化反馈

编译失败是闭环里信息密度最高也最容易被浪费的信号。nvcc 与 Triton 的报错文本长、嵌套模板展开深，直接回灌给 coder 会挤占上下文且诱导模型做无关重写。可行机制是写一个解析层：用正则与括号匹配从 stderr 抽取文件名、行号、列号、错误类别（未定义符号、类型不匹配、共享内存超限、寄存器溢出、不支持的 PTX 指令），映射为固定枚举，再附上原始片段的前后若干行。反馈粒度选择“行号加错误类别”而非整段日志，是这一层的核心决策。

伪代码思路：parse(stderr) → [(file, line, col, class)]，按 class 分组，同 class 只保留首个实例与计数；对模板展开错误，向上回溯到用户代码的第一帧而非库内部帧。这样一条五十行的报错可以压到三到五行结构化记录，token 成本下降一个量级，同时保留可操作信息。代价是解析层本身要维护：编译器版本升级会改变措辞，正则失配时退化为原始日志回灌，此时上下文预算被迅速吃掉。

具体例子：CuTe 候选因 layout 与 tile 的 stride 不匹配触发静态断言，报错指向库内某模板第数百行；解析层回溯到用户 make_tiled_copy 调用行，标注“tile 形状与 copy 原子不兼容”，coder 据此调整 tile 而非盲目改数据类型。正确性代价在这里体现为误归因风险：解析层把错误类别标错，coder 会沿错误方向修复，浪费整轮预算，因此类别枚举要保守，宁可标“未分类”也不强行猜测。

三 · 执行反馈与 NCU/SASS：从“能跑”到“为什么慢”

正确性通过后，闭环进入性能阶段。profiler 角色的输入不是源码而是执行会话产物：kernel 计时、NCU 的吞吐与占用率指标、SASS 反汇编的关键片段。机制上应把 profile 输出压成有限维特征向量而非原始报告：achieved occupancy、DRAM 吞吐占峰值比例、L2 命中率、每 warp 的 stall 主因（长依赖、屏障、访存）、指令 mix 中访存与算术比例。这些特征与 roofline 位置一起构成瓶颈标签，供 coder 选择优化方向：访存受限则改向量化与合并访问，占用率受限则减共享内存或寄存器，指令受限则看 SASS 里是否有冗余的地址计算。

$$\text{SOL}_{\text{mem}} = \frac{\text{bytes moved}}{\text{peak BW} \times t},\qquad \text{gap} = 1 - \max(\text{SOL}_{\text{mem}}, \text{SOL}_{\text{flop}})$$

代价是 profile 本身的开销：NCU 采集会引入数倍于裸跑的时延，且需要重复执行以稳定指标，单次 profile 会话可能占用数十秒；因此多轮修复预算里必须为 profile 单独留配额，不能每轮都全量采集，通常只在正确性通过后的首轮与性能停滞时触发。SASS 层面的反馈粒度更细但也更贵：反汇编文本长，需截取热点循环并标注访存指令宽度与 bank 冲突迹象，否则上下文被淹没。

具体例子：一个归约 kernel 正确但比参考慢，NCU 显示 DRAM 吞吐接近峰值而占用率低，SASS 显示每线程串行累加多个元素且无向量化加载；profiler 输出“访存受限、加载宽度不足”，coder 改为 float4 加载并调整 block 内归约树，性能缺口收窄。这里的关键判断是：profile 特征必须与 roofline 口径对齐，否则“慢”无法翻译成“改哪里”。

四 · 多轮修复预算与终止条件

闭环不设终止条件就会在失败模式里空转。工程上要同时约束三个量：每任务最大轮数、累计 token 预算、单轮 wall-clock 上限。终止条件应是复合的：正确性通过且性能达到目标阈值即停；连续若干轮错误类别不变（同一编译错误重复出现）即判定陷入局部循环并停；token 预算耗尽即停并落盘当前最优候选。机制上维护一个尝试账本，记录每轮的候选哈希、错误类别、profile 特征与判定结果，供 search 角色检索与去重。

伪代码思路：while rounds < R and tokens < T: cand = coder(ctx); verdict = judge(cand); if verdict.ok and perf_ok(cand): break; if same_class_streak >= K: break; ctx = compress(ctx, ledger)。压缩策略决定上下文成本：历史尝试只保留“候选摘要加失败类别加一行修复动作”，完整代码只在最近一轮保留，早期成功 kernel 若被检索命中则以 diff 形式注入而非全文。代价是压缩会丢失细节，导致模型重复踩同一坑，因此账本里的失败类别必须显式回灌为“已尝试且失败的方向”清单。

具体例子：某任务在 PTX 内联汇编候选上连续三轮报同一“不支持的指令修饰符”，错误类别不变触发终止，账本记录该方向不可行，下一任务若检索到相似签名则直接跳过 PTX 路线。预算的另一面是收益递减：修复轮次带来第一波真实增益，但超过一定轮数后边际正确率提升趋平，工程判断是把轮数上限压在个位数，把省下的预算投给检索与模板多样性。

五 · 上下文管理与失败模式记忆

多轮闭环的上下文是稀缺资源。机制上分三层：任务层（签名、参考实现、容差、目标硬件）、尝试层（账本压缩后的历史）、知识层（检索到的历史成功 kernel 与已知失败模式）。任务层固定注入；尝试层按轮次滚动压缩；知识层按需检索，命中则以结构化片段注入。失败模式记忆应写成可检索的键：(算子类型, 错误类别, 硬件代际)，值为一句归因与一条规避动作，避免把整段失败对话存进上下文。

代价是检索质量直接决定 token 效率：检索到不相关 kernel 会诱导错误类比，检索过窄则重复造轮子。工程上给检索加一道过滤：只接受签名兼容且错误类别不冲突的历史条目，并在注入时标注“仅供参考，需重新验证”，防止 coder 直接复制未验证代码。具体例子：同一 GEMM 变体在两次任务中均因共享内存超限失败，失败模式记忆命中后，coder 首轮即采用分块加载而非整块载入，省去一轮编译失败往返。

上下文压缩还有一个隐性代价：压缩后的历史丢失了“为什么这样改”的推理链，模型可能重新提出已被否决的方案。对策是在账本里保留否决理由的短标签，并在每轮注入时置于历史之前，形成硬约束。这一层的工程判断是：上下文管理的目标不是记住一切，而是让模型在有限 token 内不重复已知错误。

六 · 单 agent 与 planner-executor 的取舍

架构决策落在两点：是否引入 planner 做任务分解与路线选择，以及反馈粒度到行号还是到错误类别。planner-executor 分工的收益在复杂算子：planner 先按 roofline 预估瓶颈并选定实现路线（Triton 快速原型还是 CuTe 精细布局），executor 只负责在该路线内修复，减少路线摇摆带来的轮次浪费。代价是 planner 本身要消耗一次调用且可能选错路线，错误路线下的 executor 修复全部作废。

反馈粒度的取舍更直接：到行号信息量大但要求解析层精确，误标行号会把 coder 引向无关代码；到错误类别稳健但修复动作模糊，可能触发大范围重写。工程上常用混合：编译错误给行号加类别，数值错误给测试用例索引加轴信息，性能问题给瓶颈标签加 SOL 缺口，三者都不给整段日志。具体例子：一个 CuTe 候选数值正确但 SOL 缺口大，planner 判定为布局导致的非合并访存，executor 在 tile 层调整 stride 而非重写 copy 原子，一轮内收敛。

是否允许检索历史成功 kernel 是第三个决策：允许则首轮命中率高、token 省，但带来过拟合基准的风险，且历史 kernel 的硬件假设可能不匹配当前目标；禁止则每任务从零开始，轮次成本上升。可行的折中是检索仅用于生成候选骨架，正确性与性能仍须走完整 judge 与 profiler 通道，历史条目不得跳过验证直接采纳。这一条与可信评测的口径直接咬合：闭环里的任何捷径都必须在 oracle 契约下重新过一遍，否则脚手架会把“看起来对”的候选送进下游。

闭环脚手架的失效边界：反馈回路何时变成空转

编译-执行-修复闭环的增益并非单调。每一轮修复都要付出一次完整编译加一次执行（含 profiler 采集）的代价，而收益取决于新反馈是否携带了上一轮未使用的信息。把第 r 轮反馈记为 Fr，历史尝试记为 Hr，则本轮有效信息量为条件熵 Ir = H(Fr) − H(Fr | Hr)。当 Ir 趋近于零时，继续修复只是把同一错误换个写法重犯：典型如编译错误解析器把 too many resources requested for launch 归到“寄存器压力”类别，coder 于是反复调小 tile，却始终没触碰真正原因——某个 __device__ 函数被内联后撑爆了每线程寄存器上限。此时每轮成本固定（编译时间、执行时延、上下文 token），收益为零，闭环退化为空转。工程上必须给“反馈新颖性”设一个可计算的终止判据，而不是只数轮数。

三类失效条件值得在脚手架里显式编码。其一是反馈粒度错配：把 NCU 的 stall 原因（如 long scoreboard 占比高）直接回灌给 coder，而模型无法把它映射到具体的访存模式改写，反馈就变成噪声；反之只回灌“慢了 1.4 倍”这类标量，又不足以定位。有效做法是让 profiler 角色输出“指标—源码行—候选改写”三元组，把 SASS 里 LDG 与 LDS 的指令计数差异锚定到具体循环，代价是 profiler 侧要多跑一次带行号关联的采集，单轮时延上升。其二是正确性 oracle 的盲区：随机输入通过但边界形状（如 M=1 的 GEMV、非对齐尾块）失败，judge 若只跑固定 shape 集合就会给出假阳性，让修复循环提前收敛到错误 kernel。其三是上下文压缩的失真：历史尝试被摘要成“第 3 轮 tile 调小失败”，丢失了当时的编译日志，后续轮次可能重复同一实验。

失效模式可观测信号系统代价处置
反馈同质化连续两轮错误类别相同且行号不变每轮一次编译+执行强制切换反馈通道（编译→profile）
oracle 盲区固定 shape 全过但尾块未测假阳性，后续返工judge 追加边界 shape 采样
上下文失真摘要后 token 降但重复实验浪费轮数预算保留原始日志的哈希索引

系统代价还体现在角色分工的耦合上。planner-executor 分离能降低单次上下文长度，但 planner 若看不到原始 SASS，就只能依据 executor 的二手摘要做决策，信息在两级传递中被压缩两次。一个可操作的折中是：executor 只回传结构化字段（错误类别、行号、关键指标差值），planner 保留对原始日志的按需检索权，检索本身计入 token 预算。终止条件应写成“轮数上限 ∧ 累计 token 上限 ∧ 新颖性下界”的合取，任一触发即停并交回 judge 做最终判定——把最后一轮预算留给验证而非再生成，是这套脚手架在边界处最划算的工程判断。
