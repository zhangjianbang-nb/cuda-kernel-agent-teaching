一 · 从“能跑”到“跑得好”之间那道看不见的墙

设想一个具体的服务场景：一个在线推理集群里，某层 attention 的 fused kernel 已经由第 5 卷的 agent 产出，编译通过、单测通过、端到端数值与 PyTorch 参考实现对齐到容差内。第 3 卷的计时数据也已经拿到：在目标卡上，这个 kernel 的实测耗时是理论 roofline 下界的数倍，SM 占用率却只有个位数百分比。也就是说，agent 交出的东西在功能上完全合格，在性能上却离硬件能力很远。工程团队此刻面对的不是“能不能算对”，而是“为什么这么慢、慢在哪、下一步改什么”。这三个问题，恰恰是编译器日志和端到端计时都回答不了的。

这一卷要回答的正是这三个问题。它不接受“再采样一次计时、换个 tile size 试试”这种盲试循环，而是要把 GPU 硬件本身变成一个可读的反馈源：NCU 采集到的 occupancy、memory throughput、stall reason、bank conflict 是硬件在用它自己的语言描述瓶颈；SASS 反汇编是编译器最终落地的指令序列，是“源码意图”与“硬件执行”之间的最后一层翻译；roofline/SOL 定位则把一堆百分比换算成“距离物理上限还有多少”的绝对坐标。三者合起来，构成一条从指标到动作的通道。本卷的产出不是又一份 benchmark 报告，而是这条通道本身——采集什么、采多密、哪些指标进 prompt、谁来读、读完怎么变成改写动作。

开场那个 occupancy 个位数、耗时数倍于下界的 kernel，就是本卷的典型病人。它可能因为 shared memory 分块过大导致每个 SM 只能驻留一个 block，也可能因为同步点过密让 warp 长期停在 barrier 上，还可能因为跨步访存把一次本可合并的读拆成几十个独立事务。这三种病因在端到端计时里长得一模一样，在 NCU 报告里却分得很清楚：第一种体现为 occupancy 受限的 theoretical/achieved 差距，第二种体现为 stall reason 里 barrier 占比畸高，第三种体现为 memory throughput 远低于峰值而 L1/L2 事务数异常膨胀。本卷的赌注就押在这里——只要把这些信号以正确的粒度、正确的成本送进 agent 的上下文，agent 就能从“猜”变成“诊断”。

二 · 上一卷留下的缺口：可运行不等于可优化

第 5 卷的 agent 脚手架解决的是“生成并跑通”的问题：它能把自然语言描述或参考实现翻译成 CUDA C++ / Triton / CuTe 代码，能驱动编译、能跑正确性 oracle、能在失败时回读编译错误并修复。这条流水线的终点是一个“可运行且正确”的 kernel，以及第 3 卷那套计时口径下的一组时延数字。缺口在于，这条流水线的反馈信号只有两类：布尔型的正确性判定，和标量型的耗时。两者都是黑箱式的——它们告诉你结果，不告诉你原因。

这个缺口在 agent 的自迭代里会迅速放大。假设 agent 拿到“耗时是下界的数倍”这个标量，它能做的只有搜索：调 block size、调 tile、调 unroll、换 shared memory 用量，每一次改动都要重新编译、重新计时。搜索空间的维度不低，而每个样本的获取成本是一次完整的编译加运行。更糟的是，标量反馈没有方向性：两个截然不同的改动可能给出几乎相同的耗时，agent 无法从数值差异里推断出哪一个更接近瓶颈的真正成因。这就是为什么纯计时驱动的调优在多轮之后往往收敛到一个局部平台，而不是继续逼近 roofline。

缺口还有第二层，关于“可信”。第 3 卷的计时数据本身带有口径问题：warmup 是否充分、是否包含 launch 开销、是否在独占卡上测得、clock 是否稳定。当 agent 依据一个被 launch 开销污染的耗时去判断“这个 kernel 的 compute 部分还有多少空间”时，它的优化方向会系统性偏移。本卷的硬件反馈通道必须与第 3 卷的计时口径对齐，否则 NCU 说“memory throughput 已接近峰值”而计时说“还很慢”，agent 会陷入自相矛盾的证据里。这不是理论担忧，而是把 profile 接进 agent 回路时第一个会撞上的工程问题。

用一个具体例子把缺口钉住：一个 reduction kernel，端到端计时显示它比理论带宽下界慢数倍。agent 按标量反馈去增大每个线程处理的元素数，耗时略降但远未到位。若此时接入 NCU，会看到 dram__throughput 并不低，而 stall reason 里 long_scoreboard 占比很高——真正的问题是访存延迟未被足够多的在飞请求掩盖，而非带宽不足。增大每线程元素数只是碰巧增加了少量 ILP，方向对了一半。没有 stall reason，agent 无法知道“对了一半”这件事，也就无法把改动推向“提高 occupancy 或增加独立访存流”这个正确动作。

三 · 本卷的赌注：硬件反馈可以被结构化、被预算、被消费

本卷押的是一个可以被证伪的判断：硬件反馈不是只能给人看的仪表盘，它可以被结构化成 agent 能消费的证据。这个赌注拆成三个可执行的部分，每一部分都对应一个工程决策，而不是一句愿景。

第一，指标必须被压缩成“诊断向量”而非原始 dump。NCU 一次完整采集能产出数百个指标，直接塞进 prompt 既超预算又稀释信号。本卷的做法是定义一个固定的指标子集与派生量：achieved occupancy 与 theoretical occupancy 的比值、memory throughput 占峰值百分比、按 stall reason 分类的 warp 周期占比（取前若干类）、shared memory bank conflict 次数与访存事务数之比。这些量构成一个低维向量，每个维度都直接对应一类优化动作。压缩的代价是信息损失：某些罕见瓶颈（例如特定指令的吞吐饱和）会被这个子集漏掉，因此规则库需要保留一条“向量各维都正常但 SOL 仍低”的兜底分支，触发更细的二次采集。

第二，采集频率与开销必须被显式预算。NCU 的采集不是免费的：它需要序列化 kernel、可能触发 replay、改变 clock 行为，单次采集的 wall time 可达正常执行的数倍到数十倍。把每一次 agent 迭代都挂上完整 NCU 采集，会让多轮优化的总时延膨胀到不可接受。本卷的决策点是分层采样：正确性阶段不采；性能初筛只在候选 kernel 上采一次轻量指标集；只有当轻量集指向某类瓶颈时，才对症采该瓶颈所需的细粒度指标（例如 bank conflict 需要 shared memory 事务级数据）。这个分层本身就是一条规则，写进规则库而非留给 agent 即兴决定。

$$\text{profile budget} = N_{\text{cand}} \cdot (c_{\text{light}} + p_{\text{hit}} \cdot c_{\text{deep}}) \le B_{\text{wall}}$$

其中 $c_{\text{light}}$ 与 $c_{\text{deep}}$ 分别是轻量与深度采集的单次开销，$p_{\text{hit}}$ 是轻量集触发深度采集的比例。这条不等式是工程判断的量化形式：它迫使你在“采得更全”和“迭代得更快”之间做出显式取舍，而不是默认全采。

第三，SASS 级反馈的 token 成本必须被控制。反汇编一个中等规模的 kernel 动辄数百到上千条指令，整段进 prompt 会挤占本就紧张的上下文。本卷不把 SASS 当作文本读，而是当结构读：只提取与当前诊断向量指向的瓶颈相关的关键片段——例如 stall 指向 memory 时，提取访存指令及其地址计算链附近的窗口；指向 barrier 时，提取同步指令前后的窗口。提取规则由规则库给出，窗口大小是预算参数。这样做的代价是可能错过窗口外的因果链，因此规则库要求每次提取附带一个“指令计数与占比”的摘要，让 agent 知道自己看到的是局部而非全貌。

把这三部分合起来，就是本卷的核心机制：诊断向量定位瓶颈类别，分层采样控制开销，SASS 窗口提供落地证据，规则库把三者映射成具体改写动作（合并访存、shared memory 分块、减少同步、指令级并行）。这个映射不是让 agent 自由发挥，而是给出候选动作集与每个动作的预期指标变化方向，agent 在此基础上做选择与组合。

四 · 故事映射：agent 第一次读懂 stall 报告的那个拐点

本卷的叙事锚点是一个具体的转折：agent 第一次拿到 NCU 的 stall 报告，并在没有人类提示的情况下自主改掉了 shared memory 分块。这个场景值得拆开看，因为它同时验证了上面三条赌注。

场景的起点是开场那个 occupancy 个位数的 kernel。轻量采集给出的诊断向量里，achieved occupancy 远低于 theoretical，memory throughput 中等，stall reason 首位是 barrier。这三条信号合起来指向一个假设：block 内同步点过密，且每个 block 驻留的 warp 数不足以在 barrier 等待期间切换出去做有用功。规则库据此给出候选动作：减少同步点、缩小 shared memory 分块以提升每 SM 的 block 驻留数、或把部分同步改为 warp 内协作。agent 选择缩小分块，因为它同时改善 occupancy 与 barrier 等待的掩盖能力。

改写之后，第二次轻量采集显示 occupancy 上升、barrier stall 占比下降，但 memory throughput 反而略降。这是一个典型的次生效应：分块变小意味着每个 block 从 global memory 读入的数据复用次数减少，访存总量上升。诊断向量此时指向 memory，规则库触发深度采集，提取 shared memory 事务数据与对应 SASS 窗口，发现分块边界处的跨步访存没有合并。agent 于是在新分块下重写地址映射，把跨步读改成连续读。第三次采集，memory throughput 回到高位，SOL 距离明显缩短。

这个三轮过程的信息量在于：每一轮的动作都由上一轮的指标变化驱动，而不是由固定脚本驱动。第一轮的 barrier 信号、第二轮的 memory 次生信号、第三轮的 SASS 窗口证据，构成一条可追溯的因果链。代价同样清晰：三次采集加两次重编译的 wall time 远超纯计时方案的单轮成本，但因为方向明确，总轮数少，整体时延反而可控。这正是分层采样预算存在的理由——不是省采集，而是把采集花在能改变决策的地方。

这个拐点的工程意义不在于“agent 会改分块”这个动作本身，而在于它证明了硬件反馈可以被翻译成 agent 可执行的决策语言。在此之前，agent 的性能优化是搜索；在此之后，它是诊断加验证。本卷后续要展开的 NCU 指标语义、SASS 提取策略、roofline 定位方法与规则库设计，都是把这一次拐点从偶然变成可复现流水线的组件。

五 · 边界与代价：这条通道不承诺什么

把赌注说清楚，也要把边界划清楚，否则读者会误以为接上 NCU 就能自动逼近 roofline。第一条边界是采集本身会扰动被测对象。NCU 的 replay 机制会多次重放同一 kernel 以收集不同指标组，期间 cache 状态与 clock 可能偏离真实负载；对于依赖数据局部性的 kernel，replay 得到的 memory 指标可能比真实执行乐观。因此本卷要求所有 profile 结论在与第 3 卷计时口径一致的独占环境下复核，profile 用于定位，计时用于裁决。

第二条边界是规则库的覆盖度。规则库把“指标模式”映射到“优化动作”，它的有效性受限于编写时见过的瓶颈种类。对于规则库未覆盖的模式，agent 会退化为搜索，此时 profile 的价值只剩“排除已正常维度”这一项。这不是缺陷而是设计取舍：规则库是可扩展的，每遇到一个新瓶颈模式，就新增一条规则并附上验证用例，而不是让 agent 在无约束的动作空间里乱试。

第三条边界是 token 与上下文的硬约束。诊断向量、SASS 窗口、规则库给出的候选动作集，三者叠加会占用可观的上下文预算，挤占 agent 用于代码推理的空间。本卷的控制手段是让规则库输出“动作加预期指标变化”的短结构，而非长篇解释；SASS 只给窗口加摘要。代价是 agent 失去部分背景信息，收益是每轮迭代的上下文成本可预测。这个取舍在多轮 RL 场景下尤其重要——奖励信号来自正确性与性能，而上下文成本直接进入每轮的成本核算。

第四条边界关于正确性。性能改写会引入新的数值路径，shared memory 分块与访存重排都可能改变浮点累加顺序。本卷的硬件反馈通道不替代正确性 oracle，每次改写后仍须过第 5 卷那套判定。profile 告诉你“改哪里会更快”，oracle 告诉你“改完还对不对”，两者缺一不可。把这条写进规则库的执行顺序里，是防止 agent 用性能收益换正确性退化的必要约束。

六 · 本卷的工程判断：反馈的粒度就是优化的上限

回到开场那个服务场景。集群里那个慢数倍的 kernel，最终能不能被推到接近 roofline，取决于反馈通道给出的粒度是否足以区分病因。端到端计时是标量，它把三种病因压成一个数；NCU 的 stall reason 是分类向量，它把病因分开；SASS 窗口是指令级证据，它把病因落到具体代码行。粒度越细，可执行的动作越具体，但采集与上下文的成本越高。本卷的全部设计决策，本质上都是在这条粒度-成本曲线上选点。

选点的原则可以写成一句工程判断：反馈的粒度应当恰好覆盖当前候选动作集所能影响的维度，多一格是浪费，少一格是盲区。当规则库只准备给出“调分块”这一个动作时，采集到 bank conflict 级别就是浪费；当规则库准备给出“重排地址映射”时，没有 SASS 窗口就是盲区。这个原则要求规则库与采集策略同步演进，而不是先建一个大而全的采集器再想怎么用。

具体到实现，这意味着诊断向量的维度、分层采样的触发条件、SASS 窗口的提取规则，三者共享同一套瓶颈分类标签。标签是这套系统的骨架：occupancy 受限、访存带宽受限、访存延迟受限、同步受限、指令吞吐受限。每个标签对应一组指标模式、一组候选动作、一组 SASS 提取规则。agent 在标签空间里做诊断，规则库在标签空间里做映射，采集器在标签空间里做预算分配。标签之外的原始指标不进 prompt，只进日志供人复核。这条设计把硬件反馈从“一大坨数据”变成“一个有结构的证据包”，也正是本卷后续各部件能够被组合成流水线的前提。
