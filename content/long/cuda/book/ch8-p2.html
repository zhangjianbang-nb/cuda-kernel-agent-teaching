一 · 口径三角：硬件、dtype、形状必须同时钉死

“这个 kernel 比 baseline 快 3 倍”在工程上是一句无效陈述，除非它同时携带三个坐标：跑在什么硬件上、用什么 dtype、在什么形状上。三者任一漂移，倍数就不可复核。本卷把这三者称为口径三角，任何进入训练数据资产的性能数字都必须带全三角标签，缺一项即视为脏数据，在清洗阶段直接丢弃而不是“补全猜测”。机制上，口径标签以结构化字段随样本落盘：gpu_arch（如 SM 版本族）、dtype（fp32/fp16/bf16/fp8 及其累加类型）、shape_bucket（M/N/K 的分桶区间与 batch 语义），并与基准版本号绑定。代价是显存与 token：每条样本多出几十个 token 的元数据前缀，在百万级样本上意味着可观的上下文占用；若把标签塞进 SFT 的 prompt，还会挤占真正解释 profile 的篇幅。因此工程判断是标签进数据表头而非进文本，训练时按需拼接。

形式化地，一个可复核的加速比应写成条件化比值：

$$ S(\mathcal{H}, \tau, \sigma) = \frac{T_{\text{ref}}(\mathcal{H}, \tau, \sigma)}{T_{\text{cand}}(\mathcal{H}, \tau, \sigma)} $$

其中 $\mathcal{H}$ 为硬件、$\tau$ 为 dtype、$\sigma$ 为形状。只有当分子分母共享同一组 $(\mathcal{H},\tau,\sigma)$ 时，$S$ 才有意义。具体例子：同一份 reduction kernel 在 fp32 下相对 PyTorch eager 的比值，与在 bf16 下的比值不可互相引用——后者往往因参考实现已走 tensor core 路径而使候选者的相对优势缩水。把两个 dtype 的倍数混进同一个偏好对，会让“快 vs 慢”的标签本身失真。

二 · 基线不是“原版 PyTorch”，而是分层参考系

KernelBench 系基准的通行做法是以框架 eager 实现为基线，但工程上这远远不够：eager 基线自身受算子融合、内存布局、调度开销影响，且随框架版本漂移。本卷要求每条性能样本记录三层参考系：第一层是框架 eager（作为“人类可读的正确性锚”），第二层是同语义的手写 CUDA 参考实现（作为“性能地板”），第三层是 roofline/SOL 推导出的理论上界（作为“天花板”）。三层同时存在，才能把“快”翻译成“离上界还有多少”。机制上，SOL 由算术强度与硬件峰值带宽/算力推出：

$$ \text{SOL}_{\text{time}} = \max\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right) $$

候选 kernel 的实测时间除以 $\text{SOL}_{\text{time}}$ 得到 SOL 利用率，这个无量纲数比加速比更抗硬件漂移，是跨机器汇总时的首选指标。代价在于 SOL 推导本身需要准确的 FLOPs/Bytes 计数，对融合算子或动态形状，计数误差会直接污染利用率；因此本卷规定 SOL 只对形状分桶内的静态图样本计算，动态形状样本仅记录加速比并标注“SOL 不可用”。具体例子：一个 elementwise 加 bias 的 kernel，其算术强度极低，SOL 由带宽项主导，此时任何“算力利用率”表述都是误导，正确口径是带宽利用率。

三 · 指标分层：时延、带宽、显存、编译时间、token

把“快”变成数字，必须区分至少五类指标，它们在不同环节承担不同角色。时延（kernel 级 wall time 与端到端时延）是主指标，但 kernel 级时延需固定测量协议：warmup 次数、重复次数、取中位数还是最小值、是否含 launch 开销。本卷统一取固定 warmup 后的中位数，并单独记录 launch 开销占比，因为小 kernel 的 launch 开销可占总时延的显著份额，把 launch 计入或剔除会改变加速比的符号。带宽指标（有效带宽 = Bytes / time）用于判断是否触顶；显存峰值用于筛掉“用显存换速度”的作弊式优化；编译时间与首次调用时延对 Triton/CuTe 路线尤为关键，JIT 编译可能让“稳态快”的 kernel 在冷启动场景不可用。token 成本则是 agent 侧指标：生成一个候选 kernel 消耗的 token 数、多轮修复消耗的 token 数，直接决定 RL 轨迹的采样预算。

指标测量协议要点失真风险
kernel 时延固定 warmup、取中位数、单列 launch 开销小 kernel 被 launch 主导
有效带宽Bytes 按实际访存计缓存命中使带宽虚高
显存峰值含临时缓冲与 workspace漏计 workspace 低估占用

具体例子：一个 Triton 实现在稳态下比 CUDA 参考快，但首次调用因编译耗时数十倍于对手；若评测只报稳态时延，偏好对会把“冷启动不可用”的样本标成“快”，污染 SFT 基座对部署可行性的判断。

四 · 正确性口径：容差、形状覆盖与随机种子

性能数字只有在正确性通过后才可入账，而“通过”本身需要口径。本卷规定正确性 oracle 至少包含：逐元素容差（按 dtype 设定绝对与相对容差组合）、形状覆盖集（含边界形状与非对齐形状）、随机种子固定以保证可复现。机制上，正确性判定写成布尔与误差范数的组合：

$$ \text{pass} = \left( \lVert y_{\text{cand}} - y_{\text{ref}} \rVert_\infty \le a + r\cdot\lVert y_{\text{ref}} \rVert_\infty \right) \wedge \text{no-NaN} \wedge \text{shape-match} $$

其中 $a$ 为绝对容差、$r$ 为相对容差，二者随 dtype 收紧或放宽。代价是评测时间：形状覆盖集越大，单样本验证越慢，而 agent 多轮采样需要高频反馈，因此工程上采用分层验证——快速子集（少量代表性形状）用于 RL 在线奖励，全量覆盖集用于离线入库审计。具体例子：一个 softmax kernel 在 K 非 2 的幂时数值不稳定，快速子集若只含对齐形状就会放行，全量审计才暴露；这类样本若进入 SFT 正例，会教模型忽略边界形状。

另一条口径是“对 vs 错”偏好对的构造必须与正确性判定同源：错误样本的错误类型（数值偏差、越界、竞态）应被标注，因为不同错误类型对修复策略的提示价值不同。把“编译失败”与“数值错误”混为一类负例，会让模型学不到区分编译期与运行期问题的能力。

五 · 基准版本与数据版本的对齐

基准会演化：题目集合增删、参考实现更新、评测脚本修正。若训练数据里的性能标签来自旧基准版本，而评测跑在新版本上，加速比就不可比。本卷要求数据资产携带基准版本号，并在入库时做对齐检查：同一 task_id 在不同基准版本下的参考实现若发生语义变化，旧标签作废而非沿用。机制上采用“版本指纹”：基准版本 + 评测脚本哈希 + 硬件档案哈希三者合成指纹，样本只在指纹匹配时被允许进入同一训练分片。代价是数据利用率下降——跨版本样本无法直接合并，需要重跑或丢弃；但这是保证“可复核”的必要开销。具体例子：某 reduction 题的参考实现在新版本中改用了不同的累加顺序，数值结果在容差内但性能基线变化，旧加速比若继续使用会系统性高估候选 kernel 的优势。

与去污染联动：评测集必须与训练集在 task_id 层面隔离，且隔离检查要在版本指纹更新后重跑，否则新版本引入的题目可能悄悄泄漏进训练分片。这一步的代价是每次基准升级都要重算隔离矩阵，工程上以增量哈希避免全量重算。

六 · 把口径写进偏好对与 profile 样本

口径最终要落到数据形态上。对“快 vs 慢”偏好对，正负样本必须共享同一口径三角与同一基准版本指纹，否则偏好信号是噪声；对“对 vs 错”偏好对，正确性判定必须来自同一 oracle 配置。对 profile 解释类 SFT 样本，profile 文本需附带采集时的硬件与 dtype 标签，否则模型学到的“瓶颈判断”无法迁移——同一 kernel 在带宽受限与算力受限两种硬件上，profile 的解读方向相反。机制上，样本构造器在拼接 prompt 时按需注入口径字段，并在负例侧保留失败原因的结构化标签，使模型见到的是“条件化的快慢”而非绝对快慢。

工程判断落在配比上：口径完整的样本优先进入 SFT 冷启动集，口径缺失但性能信号强的样本只进 RL 上下文而不进 SFT 正例，因为 SFT 会固化口径缺失下的错误归因。这一决策的代价是冷启动集规模受限，需要用清洗后的高口径样本反复加权来稳住下限——这正是本卷数据资产作为可复用底座的意义所在：底座的可信度不来自样本数量，而来自每条样本都能被独立复核到同一组 $(\mathcal{H},\tau,\sigma)$ 与同一基准指纹。

口径漂移：当「快」的分子分母不再同一套坐标系

本卷把「快」翻译成可复核数字的核心动作，不是测一次加速比，而是把分子（优化后 kernel 时延）与分母（基线时延）钉死在同一套坐标系里：同一 GPU 型号与 SM 配置、同一 dtype 与累加精度、同一输入 shape 分布与 batch 组成、同一 warmup 与迭代次数、同一计时后端（CUDA event 还是 wall clock）、同一是否含 launch 开销与 host-device 拷贝的边界。任何一项漂移都会让加速比失去可比性。工程上把它写成一个显式的口径元组 $$M=(g,d,s,b,t,o)$$，其中 g 为硬件指纹（型号+驱动+CUDA 版本）、d 为 dtype 与累加策略、s 为 shape 采样分布、b 为基线实现与其调优程度、t 为计时协议、o 为开销边界（是否计入 launch、是否计入首次编译）。每条轨迹入库时必须携带完整 M，缺项即判为不可复核，不得进入偏好对的正样本侧。代价是元数据膨胀：一条轨迹的 M 序列化后往往比 kernel 源码本身还长，清洗阶段要为每个字段做一致性校验，这直接拉高数据准备时延与存储带宽占用；更隐蔽的代价是 token——把 M 全文塞进 SFT 样本会挤占上下文预算，实务做法是 M 只保留哈希与关键字段摘要，全文留在旁路索引里供复核时回查。

失效条件集中在三类。其一是基线未调优：拿朴素 PyTorch eager 实现当分母，加速比虚高但对下游无信息量，正确口径要求分母至少是框架内已调优实现或官方库算子，并在 M 的 b 字段标注调优程度。其二是 dtype 与累加不一致：fp16 输入配 fp32 累加与纯 fp16 累加的数值路径不同，前者慢但正确性 oracle 更宽松，后者快却可能在长归约上溢出，二者加速比不可直接相减。其三是 shape 采样偏差：只在大 shape 上测得的加速比在小 shape 上会因 launch 开销占比上升而反转，故 s 必须是分布而非单点，报告需给出分位数而非均值。对应代价是评测集规模膨胀与重复计时开销：为覆盖分布，单条 kernel 的评测次数从个位数升到数十次量级，冷启动数据集的构建时间随之上升，而这正是团队回头用清洗后 SFT 基座稳住下限时要付的账——下限稳不稳，取决于口径是否在训练样本与评测样本之间保持一致。

把口径落到可复核数字上，需要一个判定函数而非单一标量。定义轨迹 t 在口径 M 下可复核当且仅当正确性 oracle 通过、计时方差低于阈值、且 M 与基准版本登记表一致：$$\mathrm{ok}(t,M)=\mathbb{1}[\mathrm{oracle}(t)\land \sigma_{\text{time}}/\mu_{\text{time}}<\epsilon\land \mathrm{hash}(M)\in\mathcal{R}]$$。其中 $$\mathcal{R}$$ 是基准版本登记集合，把硬件、dtype、基线、计时协议四类字段的哈希固定下来，任何字段变更即产生新版本号，旧轨迹不得跨版本比较。这张表是数据版本与基准版本对齐的物理载体：SFT 样本里出现的加速比必须能反查到 $$\mathcal{R}$$ 中的某一条，否则视为口径污染并从偏好对中剔除。代价体现在版本管理上：每次硬件换代或基线升级都会让存量轨迹批量失效，去重与去污染规则要按版本分桶执行，冷启动数据集因此被切成多个互不可比的子集，训练配比不得跨桶混用；同时失败轨迹作负例时也必须携带 M，否则「慢」无法归因于实现而非口径。

口径字段漂移后果复核代价
硬件指纹 gSM 数与带宽差异使加速比不可比换卡即整批轨迹失效，需重测
dtype/累加 d数值路径不同，正确性与时延双漂oracle 阈值需按 d 分档
shape 分布 s小 shape 上加速比反转评测次数上升，构建时延增加
基线 b分母未调优导致虚高需登记调优程度，否则剔除
计时协议 tlaunch 开销与 warmup 影响均值方差校验，低样本轨迹丢弃

具体到 profile 文本进 SFT 还是仅进 RL 上下文这一决策，口径直接决定样本形态：若 profile 文本要进 SFT，则其附带的时延数字必须已通过 $$\mathrm{ok}(t,M)$$ 校验，否则模型会学到「引用一个不可复核的加速比」这种坏习惯，冷启动阶段表现为对下限的估计失真；若仅进 RL 上下文，则口径校验可推迟到奖励计算时执行，SFT 侧只保留正确性 oracle 结论，token 预算更省但 RL 侧需承担重复校验的算力开销。工程判断落在：凡进入 SFT 正样本的加速比，必须绑定 $$\mathcal{R}$$ 中的版本哈希并在清洗规则里做硬校验；失败轨迹作负例时允许口径字段缺失，但必须在标签上标注缺失类型，避免模型把口径漂移误学成实现缺陷。这一条不解决，SFT 基座稳住的下限只是同一套漂移口径下的自洽，而非可复核的工程事实。
