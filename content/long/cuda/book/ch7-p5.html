一 · 脚手架不是单体：四个角色各自的输入输出契约

把 agent 脚手架当成一个“会写 kernel 的模型”是最常见的误解。在本卷的工程口径里，脚手架是一个由四个可替换角色组成的流水线，每个角色只对一种信号负责，并且以显式契约与上下游交接。coder 的输入是问题规格（算子语义、形状约束、dtype、目标硬件）加上历史轮次的失败摘要，输出是候选 kernel 源码与一份自述（它认为自己用了什么策略、哪些假设未验证）。judge 的输入是候选源码与 oracle 用例集，输出是三态判定：编译失败 / 数值不符 / 通过，并附带最小反例输入。profiler 的输入是已通过正确性门控的 kernel，输出是结构化指标（achieved occupancy、DRAM 吞吐、L2 命中、指令 mix、stall 原因分布）以及热点 SASS 片段。search 的输入是前三者产出的全部结构化记录，输出是下一轮的搜索决策：改哪一行、换哪种 tiling、还是放弃该候选重新采样。

契约的关键在于“结构化”三个字。如果 judge 只回一个布尔值，coder 在下一轮拿不到任何可操作的梯度方向；如果 profiler 只回一个加速比数字，search 无法区分“带宽打满所以没救了”与“occupancy 太低所以还有空间”。因此每个角色都必须把结论压缩成定长字段，例如 judge 输出 {status, max_abs_err, failing_index, seed}，profiler 输出 {sol_ratio, bottleneck_tag, top_stall}。这套字段设计直接决定了多轮信用分配能不能做——第 4 卷的 oracle 判定与本卷的奖励管线之间，正是靠这些字段对齐的。

代价出现在 token 与编译时间上。每一轮把完整源码、完整 profile 文本、完整 SASS 反汇编都塞回上下文，会让单条轨迹的 token 消耗随轮数线性甚至超线性增长；而每次编译加运行 oracle 用例的墙钟时间，在候选批量采样时会被放大到与 GPU 队列深度同阶。工程上的做法是分层摘要：源码全量保留（它是被修改的对象），profile 只保留 top-k stall 与瓶颈标签，SASS 只保留热点基本块的 20 到 40 条指令。这样单轮上下文可控，代价是 search 可能看不到某些长尾信号——这是一个明确的取舍，不是可以两全的设计。

$$\text{turn\_cost} = \underbrace{T_{\text{src}}}_{\text{全量}} + \underbrace{k \cdot T_{\text{prof}}}_{\text{top-}k} + \underbrace{m \cdot T_{\text{sass}}}_{\text{热点块}} + T_{\text{judge}}$$

一个具体例子：一个 reduction kernel 首轮编译通过但数值不符，judge 返回 failing_index=1023 与对应 seed。coder 看到索引落在 block 边界，判断是跨 block 归约未同步，第二轮加入 shared memory 两阶段归约。这个修复不需要 profiler 参与，说明角色分工的价值在于“哪类失败走哪条路径”，而不是每轮都把所有工具跑一遍。

二 · 执行反馈的粒度：从布尔到可定位反例

执行反馈是这套脚手架里信息密度最高、也最容易被浪费的信号。最粗的粒度是“跑通了没有”，中等粒度是“最大绝对误差是多少”，最细的粒度是“在哪个输入索引上、以什么方式错”。多轮修正的成功率与反馈粒度强相关，因为 coder 的下一轮编辑本质上是在一个巨大的源码空间里做局部搜索，反馈越定位，搜索半径越小。

设计反馈时有三个必须区分的失败类别。第一类是编译期失败，包括类型不匹配、共享内存超限、不支持的 intrinsic，这类错误信息由编译器直接给出，几乎不需要额外加工，但要注意 nvcc 的报错行号在模板展开后可能指向实例化点而非真实错误点，需要在脚手架里做一次行号回映。第二类是数值失败，包括累加顺序导致的浮点差异、边界条件漏判、race condition 引起的非确定性错误。第三类是性能失败，即正确但远低于 SOL，这类不归 judge 管，交给 profiler。

数值失败的处理要点是“可复现的最小反例”。oracle 用例集往往有几十上百个形状组合，直接告诉 coder“第 37 个用例失败”信息量很低；更好的做法是固定随机种子、缩小到最小触发形状、并给出期望值与实际值的前几个元素。这样 coder 能在不运行的情况下推理出错位置。代价是 judge 需要额外做一次 delta-debugging 式的形状收缩，每次收缩都要重新编译运行，编译时间成为这条路径的主要开销。

  • 编译失败：回映行号 + 提取 nvcc 首条 error，不做形状收缩。
  • 数值失败：固定 seed、收缩到最小形状、给出前若干元素期望/实际对比。
  • 非确定性失败：同一输入跑多次比对，标记为 race 类，提示 coder 检查同步原语。
  • 性能失败：不进入 judge 路径，直接转 profiler，避免污染正确性信号。

一个具体例子：一个 softmax kernel 在长序列上数值不符，judge 收缩后发现只有序列长度不能被 warp 宽度整除时才错，反例是长度 1023。coder 由此定位到尾元素未做 mask，第三轮修复。若只给“用例 12 失败”，这个定位要多花两到三轮。这就是反馈粒度换来的轮数节省，代价是 judge 侧多出的编译次数。

三 · NCU 与 SASS：把“慢”翻译成可执行的编辑动作

profiler 角色的核心任务不是报告数字，而是把“慢”翻译成 coder 能直接执行的编辑动作。NCU 给出的指标本身是描述性的：DRAM throughput 接近峰值说明瓶颈在带宽，achieved occupancy 低说明并行度不足，stall 分布里 long scoreboard 占比高说明访存延迟未被掩盖。这些描述要映射到具体编辑，需要一层规则化的解释器。

映射规则可以写成一张优先级表。若 SOL 比值低且 DRAM 吞吐接近峰值，则编辑方向是减少冗余访存、提高数据复用（例如把多次全局读改为一次读入 shared memory 后复用）；若 occupancy 低且寄存器用量高，则方向是减少寄存器压力或调整 block 尺寸；若 stall 以 barrier 为主，则方向是减少同步点或改用 warp 级原语；若指令 mix 中出现了大量非合并访存，则方向是重排线程与数据的映射关系。SASS 层面的价值在于验证这些假设：反汇编里能看到实际生成的 load 指令宽度、是否有 predicated 分支、循环是否被展开，从而判断源码层的意图有没有被编译器兑现。

$$\text{SOL ratio} = \frac{t_{\text{ideal}}(W, B)}{t_{\text{measured}}}$$

其中理想时间由该算子在此硬件上的最小必要工作量（访存量与浮点量）除以峰值吞吐得到。这个比值是奖励管线里连续奖励的归一化基础，也是 profiler 判断“还有没有空间”的阈值依据：比值已经接近 1 时，继续优化的边际收益极低，search 应当把预算转向其他候选而不是死磕。

代价在这里非常具体。NCU 采集本身会引入测量开销，逐 kernel 全指标采集在批量候选上会把吞吐压低一个量级；SASS 反汇编产出的文本长度与 kernel 规模成正比，直接进上下文会挤占源码的 token 预算。工程做法是采样式采集：只对通过正确性门控的候选做一次中等粒度的 profile，且只采集与当前瓶颈假设相关的指标组，而不是全量指标。这带来一个正确性上的风险——单次采样可能受缓存状态影响而不代表稳态，因此需要在同一候选上做少量重复并取中位数，重复次数本身又是一笔时延成本。

一个具体例子：一个矩阵乘 kernel 的 SOL 比值偏低，NCU 显示 DRAM 吞吐接近峰值而 occupancy 正常，SASS 显示内层循环每次迭代都重新加载同一块 B 矩阵片段。search 据此判定为数据复用不足，指示 coder 引入分块并把 B 片段驻留寄存器，下一轮 SOL 比值上升。这条路径上 profiler 提供的不是“慢”，而是“哪一类慢、对应哪种编辑”。

四 · search 的决策结构：在探索与收敛之间分配轮次预算

search 角色是整条流水线的调度器，它决定的不只是“下一步改什么”，还包括“还要不要继续”。多轮修正的收益曲线通常不是单调的：前几轮修复编译与明显数值错误，收益快；中段修复边界与同步问题，收益中等；后段往往陷入局部最优，继续投入轮次的边际收益趋近于零。search 的职责就是在曲线上找到停止点，把剩余预算分配给新的候选采样。

一个可实现的决策结构是分层策略：第一层判断失败类别，编译失败与数值失败走修复路径，性能失败走优化路径；第二层在修复路径内判断“本轮失败是否与上一轮同类”，若同类连续出现则说明 coder 的假设错了，应当触发重新采样而非继续微调；第三层在优化路径内依据 SOL 比值与瓶颈标签选择编辑族。这个结构可以用一个简单的打分函数表达，把候选的预期增益、已消耗轮次、失败重复次数合成一个优先级。

$$\text{priority} = \frac{\hat{g}(\text{bottleneck})}{1 + \lambda \cdot r_{\text{used}} + \mu \cdot r_{\text{repeat}}}$$

其中分子是依据瓶颈标签估计的剩余增益，分母惩罚已用轮次与同类失败重复。这个打分不需要精确，它的作用是让调度在“继续修这个”与“换一个候选”之间有一致的口径，而不是靠固定轮数硬截断。

代价体现在两个方向。轮次预算给得太宽，单条轨迹的 token 与编译时间膨胀，且后段轮次产生的训练信号质量下降（修复不再带来增益，信用分配难以归因）；给得太窄，则复杂算子永远修不完，课程学习里高难度样本被系统性丢弃，导致训练分布偏斜。这个取舍直接连到本卷的课程学习设计：难度递进不是按题目难度排，而是按“在给定轮次预算内可修复的概率”排。一个具体例子：一个融合算子在前两轮修好了数值问题，第三轮起 SOL 比值停滞，search 依据重复失败计数判定进入平台，停止该轨迹并把预算转给同族另一个候选，避免在同一局部最优上耗掉五轮。

五 · 多轮信用分配：哪一轮的编辑真正带来了增益

多轮修正产生的轨迹天然带有信用分配问题：最终的成功或失败该归功于哪一轮？如果奖励只落在轨迹末端，中间轮次的编辑动作得不到区分，策略学不到“哪类编辑有效”。本卷的口径是把奖励拆到轮次级，用相邻两轮的指标差分作为该轮编辑的贡献估计，再乘以一个折扣因子向后传播。

具体机制是：每轮结束记录一个状态向量（正确性状态、SOL 比值、瓶颈标签），相邻状态之间的差分构成即时增益；若某轮从“数值不符”变为“通过”，这一轮的增益是巨大的离散跳变，应当给予高权重；若某轮只是 SOL 比值小幅上升，权重相应较小。折扣因子控制远端轮次对早期决策的影响，取值偏小会让 agent 只关心最近一轮的编辑，取值偏大则会让早期错误决策获得不应得的信用。

$$R_t = \sum_{i=t}^{T} \gamma^{\,i-t} \, \Delta s_i, \quad \Delta s_i = s_i - s_{i-1}$$

这里的状态差分必须做归一化，否则正确性跳变会淹没性能增益，使策略只学会“先修正确性”而忽略优化。归一化的方式与奖励管线里的 SOL 归一化一致，这也是为什么 profiler 的 SOL 比值要作为标准字段贯穿全程。

代价是记录开销与信号噪声。每轮都做完整 profile 会让差分更精确，但采集成本高；只做轻量记录则差分噪声大，尤其在性能指标上，单次测量的抖动可能大于真实增益，导致信用分配把噪声当成贡献。缓解办法是对性能类差分做重复测量取中位数，对正确性类差分则不需要重复（它是确定性的）。另一个代价是折扣因子的选择本身没有解析最优，只能通过训练曲线是否突破平台期来判断——这正是本卷故事映射里“课程与信用分配调整后多轮修复成功率上升”所指的机制位置。

一个具体例子：某轨迹共五轮，第一轮编译失败，第二轮修复编译但数值不符，第三轮修复数值通过，第四、五轮优化但 SOL 比值几乎不动。按差分计算，第三轮的离散跳变获得最高信用，第四五轮的微小增益被折扣因子压低。策略由此学到“定位数值错误并一次性修复”是高价值动作，而不是在已正确的 kernel 上反复微调。若没有轮次级拆分，这条轨迹只会给出一个末端奖励，第三轮与第五轮的贡献无法区分。

六 · 反馈回路的失效模式与工程判断

这套脚手架有四类典型失效模式，识别它们比调参更重要。第一类是反馈饱和：coder 反复收到同类失败信息，编辑动作开始随机化，轨迹变成噪声。判据是同类失败连续出现且编辑差异度上升，处置是触发重新采样而非继续修复。第二类是 profiler 误导：单次采样受缓存与时钟状态影响，给出的瓶颈标签与实际稳态不符，导致 search 把预算投向错误的编辑族。判据是重复测量的方差过大，处置是提高重复次数或降低该候选的优先级。第三类是 judge 假阴性：oracle 用例集覆盖不足，一个实际错误的 kernel 被判通过，后续所有优化都建立在错误基础上。这类失效最危险，因为它污染的是正确性门控这个硬信号，处置只能靠第 4 卷的 oracle 审计在用例集层面兜底。第四类是 search 过早收敛：打分函数对已用轮次的惩罚过重，导致稍有难度的候选在第一轮失败后就被丢弃，训练分布向简单样本偏斜。

工程判断的核心是：这四个角色的信号不能互相替代。正确性只能由 judge 给，性能只能由 profiler 给，调度只能由 search 做，编辑只能由 coder 做。任何试图让 coder 自己判断“我改得对不对”的设计，都会把可验证信号退化成模型自评，而模型自评在多轮迭代中会系统性漂移。反过来，让 judge 去判断性能、让 profiler 去判断正确性，同样是信号错位。

在成本侧，这套分工的总开销由三部分构成：候选采样的 token 成本、每轮编译与 oracle 运行的墙钟成本、profile 采集的 GPU 时间成本。三者的比例决定了流水线的瓶颈在哪里——若编译时间占主导，应当减少每轮编译次数（例如批量编译、缓存已编译变体）；若 profile 占主导，应当降低采集粒度；若 token 占主导，应当压缩上下文摘要。这个判断不需要精确测量，只需要在批量轨迹上做一次分项计时，就能看出该往哪个方向削减。

最后落到一个具体机制上：把每轮的 {status, sol_ratio, bottleneck_tag, edit_diff} 四元组持久化，既作为信用分配的输入，也作为奖励 hacking 监控面板的数据源。当某一类编辑在大量轨迹上反复出现却不带来 SOL 比值上升时，面板会显示这种“无效勤奋”，提示课程或奖励设计需要调整。这个机制把脚手架的四个角色从一次性流水线变成了可观测的闭环，也是本卷把交互轨迹、评测分数与 oracle 判定三者对齐的落点。
