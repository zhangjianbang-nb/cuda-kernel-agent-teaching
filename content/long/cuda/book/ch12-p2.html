一 · 口径先于路线图：把“快”拆成可复核的字段

路线图的第一行不是排期，是口径表。团队若不能把“这个 kernel 快”翻译成一组字段，后续所有里程碑都会退化成口头承诺。本卷要求每个基准条目至少携带六个字段：基准版本号、基线实现、硬件型号与拓扑、dtype 与累加精度、指标定义（时延/吞吐/带宽利用率/SOL 占比）、以及测量协议（warmup 次数、重复轮数、是否含编译时间）。缺任一字段，该数字不得进入验收标准。

机制上，这六个字段构成一个“可复核断言”的最小单元。评测工程师的职责不是跑分，而是维护这张字段表的 schema 与冻结策略：基准版本一旦冻结，字段只增不改；新增字段走变更评审。代价是显性的——每次基准升级都要重跑全量基线，编译时间与 GPU 机时按条目数线性增长；若条目数百级、每轮含多次重复，单次全量回归的墙钟时间以小时计，这是路线图里必须预留的固定成本，不能摊进“探索性实验”预算。

公式上，把“快”写成相对量而非绝对量，是可复核的前提：

$$\text{speedup}=\frac{T_{\text{baseline}}}{T_{\text{candidate}}},\quad \text{CI}=\left[\frac{T_b}{T_c^{hi}},\ \frac{T_b}{T_c^{lo}}\right]$$

其中 $T_c^{lo},T_c^{hi}$ 是候选实现重复测量的分位区间。只报点估计的 speedup 在路线图评审中一律视为无效证据。具体例子：同一算子在不同 dtype 下基线不同，若候选只在 fp16 上对比而基线取 fp32 版本，speedup 会被系统性放大，这类错误在字段表里表现为“dtype 字段不一致”，评审时可直接拦截，无需重跑。

二 · 基线不是“官方实现”，是团队自己冻结的那一份

基准演化史由别的部分承担，这里只谈路线图视角的选择：基线必须是团队自己冻结、可复现构建的那一份，而不是随上游库版本漂移的“官方实现”。理由是可复核性——上游一次小版本更新可能改变内核调度策略，导致历史 speedup 曲线整体平移，路线图上的季度对比失去意义。

机制上，基线以“实现 + 构建脚本 + 环境锁”三元组入库，与基准版本号绑定。评测流水线在每次回归时先验证基线自身在目标硬件上的时延落在冻结时的置信区间内，偏离超阈值则判定环境漂移，回归结果作废。代价是维护成本：每个基线要占一份镜像与一套构建缓存，显存与磁盘开销随基线数量增长；更贵的是漂移排查的人工时延，一次环境漂移可能吞掉数天的回归窗口。

伪代码思路如下：

  • 读取基准条目 → 校验字段表完整性 → 拉起冻结镜像
  • 先跑基线自检，比对冻结区间；不通过则标记 env-drift 并终止该条目
  • 通过后跑候选，记录重复测量的分位区间与编译时间
  • 输出 (speedup, CI, 编译开销, 正确性 oracle 结果) 四元组入库

具体例子：某团队把基线从“上游最新版”改为“季度冻结版”后，跨季度对比才具备可比性；此前每次上游更新都会让路线图上的达标条目数出现无解释的跳变，评审无法归因。这一改动的代价是团队要自行承担基线镜像的安全更新与构建脚本维护，属于平台运维的固定职责。

三 · 硬件与 dtype：把“同一张卡”写成拓扑约束

“同一张卡”不足以支撑可复核。硬件字段必须写到拓扑层级：卡型号、卡间互联、NUMA 归属、是否共享 MIG 切片。同一型号在不同互联拓扑下的带宽利用率差异会直接改变 roofline 判定，进而改变“是否达标”的结论。路线图若按能力排期，硬件字段就是能力矩阵的列；若按业务场景排期，它就是验收标准的锚点。

dtype 字段同理，必须同时记录输入精度、累加精度与输出精度。混合精度下，累加精度决定数值误差上界，而误差上界决定正确性 oracle 的容差。机制上，把 dtype 三元组与 oracle 容差绑定成一条规则：容差不得宽于该 dtype 组合的理论误差界，否则正确性验证形同虚设。代价是正确性回归的时延——更严的容差意味着更多条目需要逐元素比对而非抽样，单条目的验证墙钟时间上升，全量回归的机时预算随之抬升。

字段缺失后果复核动作
互联拓扑带宽利用率不可比拒绝入库，要求补测
累加精度容差无理论依据触发 oracle 变更评审
MIG 切片时延被资源争用污染标记环境异常，重跑

具体例子：同一算子在独占卡与共享切片上测得的时延差异足以让一个条目在“达标”与“未达标”之间翻转；字段表把切片状态记为必填后，这类翻转在评审阶段即可解释，而不必等到季度复盘时才发现口径不一致。

四 · 指标分层：时延、带宽利用率与 SOL 占比各自回答什么

单一指标无法支撑路线图决策。时延回答“端到端是否变快”，带宽利用率回答“是否接近内存上限”，SOL 占比回答“离 roofline 还有多少空间”。三者对应不同的验收场景：面向生产落地的条目看时延与端到端收益，面向 kernel 优化的条目看 SOL 占比，面向平台容量的条目看带宽利用率。

机制上，指标分层要求每条基准条目声明“主指标”与“辅助指标”，主指标进入验收标准，辅助指标进入诊断视图。这样做的代价是评测流水线要同时采集多路数据，NCU 类 profile 的采集开销会显著拉长单条目测量时间；若对全量条目开启细粒度采集，回归窗口会被 profile 开销主导，因此路线图必须规定“主指标全量采集、辅助指标抽样采集”的分层策略。

$$\text{SOL}=\frac{\text{实测吞吐}}{\min(\text{峰值算力吞吐},\ \text{峰值带宽吞吐})}$$

公式的分母取算力与带宽两条 roofline 的较小者，因此 SOL 占比天然依赖硬件字段与 dtype 字段——换卡或换精度，分母即变，历史 SOL 曲线不可直接续接。具体例子：一个条目在时延上达标但在 SOL 占比上远低于同批条目，说明它靠减少工作量而非提升效率取胜；路线图应把它归入“待优化”而非“已收敛”，否则下一轮基准升级时它会首先失效。

五 · 编译时间与 token 成本：被忽略的两类代价

可复核的数字不止运行时。编译时间直接决定 agent 多轮迭代的吞吐：一次内核编译若耗时以分钟计，多轮 RL 的采样效率就被编译墙钟卡住。路线图必须把编译时间列为基准条目的必填字段，并在验收标准中区分“首次编译”与“缓存命中”两种情形。

机制上，评测流水线记录每条目的编译墙钟与缓存状态，回归报告同时给出运行时指标与编译开销。代价是双向的：编译时间过长会压缩探索预算，而过度依赖缓存会让测量结果偏离真实部署路径——生产端首次加载同样要付编译成本。因此路线图规定“验收测量必须包含冷编译路径的抽样”，抽样比例由平台运维按季度设定。

token 成本是另一类：agent 生成与优化内核时，上下文长度、profile 回灌的文本量、多轮对话的累积 token 都计入单条目成本。可复核的做法是把 token 消耗与条目绑定入库，使“每个达标条目花多少 token”成为可比较的量。代价体现在预算侧——token 消耗高的条目在同等预算下可尝试的轮数更少，路线图据此决定 RL 与 SFT 的投入配比时，必须把 token 单价与条目通过率一起看，而不是只看通过率。

具体例子：两个条目通过率相同，但一个平均消耗的 token 是另一个的数倍，且编译时间更长；在容量固定的季度里，前者应被排到预算宽松的窗口，或先做脚手架侧的上下文压缩，而不是直接扩预算。这是把“快”翻译成数字之后的第二层判断：不仅要知道多快，还要知道达到这个快花了多少可复核的资源。

六 · 冻结、评审与门禁：把口径固化为组织流程

口径表若只存在于文档，路线图就无法执行。治理规则要求三件事落地：基准版本冻结、oracle 变更评审、生产发布门禁。三者共用同一张字段表，形成一条从基准到生产的证据链。

机制上，冻结意味着版本号不可变、字段只增不改；oracle 变更评审意味着任何容差调整都要附理论误差界与回归影响面；发布门禁意味着生产条目必须携带完整字段表与正确性 oracle 通过记录，缺项即阻断。代价是流程时延：一次 oracle 变更评审要走跨角色会签，冻结窗口内的紧急修复只能走例外通道并计入技术债清单。这些时延在路线图上表现为里程碑之间的缓冲，不能压缩为零。

  • 基准版本冻结：季度为粒度，冻结期内新增条目走下一窗口
  • oracle 变更评审：kernel 工程师提理论界，评测工程师核回归影响面，RL 工程师评估奖励漂移
  • 发布门禁：字段表完整性 + 正确性通过 + 端到端收益可归因，三者缺一不放行

具体例子：某条目在门禁处因缺少冷编译抽样记录被阻断，补测后发现冷路径时延显著高于缓存命中路径，端到端收益被高估；若无门禁，该条目会以虚高的收益进入生产验收，随后在真实部署中回退。这类阻断的代价是发布窗口延后，收益是路线图上的数字从此可复核。

技术债清单与下一轮基准升级计划由此获得输入：字段表里长期缺失的字段、被例外通道放行的变更、抽样比例不足的条目，都自动进入债清单。路线图按能力排期时，债清单就是下一季度的输入项；按业务场景排期时，它是验收标准收紧的依据。最终落在一条工程判断上：可复核的数字不是测量出来的，是冻结、评审与门禁共同生产出来的——没有这三道流程，speedup 只是一个无法归因的标量。

冻结口径的代价：基准版本、硬件档位与验收门禁的边界

把「快」翻译成可复核数字，路线图层面真正要固化的是三件事：基准版本号、硬件档位、dtype 与测量口径的组合键。任何一次验收都必须写成「基准@版本 × 硬件档 × dtype × 指标」四元组，缺一项即视为不可复核。冻结基准版本意味着放弃对上游新算子的即时覆盖：当 KernelBench 系基准出现新题型，团队要么等下一轮升级窗口，要么在旁路分支上跑探索性数字但不计入验收。失效条件很明确——一旦有人在验收报告里混用两个版本的 baseline，加速比就失去可比性，因为分母的参考实现本身被换过。系统代价是评测工程师要维护版本矩阵与回归基线，每次升级窗口都要重跑全量参考实现，占用集群机时与 NCU 采集时间；这部分成本必须提前写进季度里程碑，而不是在验收前临时补。

硬件档位与 dtype 的组合直接决定 roofline 上的位置，也就决定「快」的上限。同一 kernel 在 HBM 带宽受限与算力受限两种档位下的 SOL 利用率不可比，因此路线图规定：验收数字必须标注目标硬件的带宽与峰值算力档，并给出实测有效带宽占比。可用如下判据把加速比与 SOL 绑定：

$$\text{SOL}=\frac{\text{实测吞吐}}{\min\!\left(\text{峰值算力},\ \text{峰值带宽}\times \text{算术强度}\right)},\qquad \text{加速比}=\frac{t_{\text{baseline}}}{t_{\text{kernel}}}$$

只有当加速比提升伴随 SOL 同向变化时，才认定为真实优化；若加速比上升而 SOL 下降，多半是 baseline 选弱了或 dtype 不一致（例如 fp32 参考对 fp16 实现），属于口径污染而非工程收益。这类失效在低精度算子密集出现时最典型：一个 fp16 实现在 fp32 baseline 上能报出漂亮倍数，但换成同 dtype 参考后收益归零，路线图若不做 dtype 对齐评审，就会把技术债当成能力写进能力矩阵。

指标侧还要区分端到端时延与 kernel 时延。生产发布门禁应以端到端为准，因为 launch 开销、host-device 同步与框架调度在短 kernel 上占比可观；而优化迭代期用 kernel 时延做快速反馈。两者的换算代价是评测工程师要为每个候选实现跑两条链路，token 与机时开销翻倍，因此路线图规定只有进入候选池的实现才跑端到端，探索期只跑 kernel 级并标注「未过门禁」。表格给出四元组的登记格式，任何缺列的报告退回重跑：

字段取值约束缺失后果
基准版本冻结标签，只读分母漂移，加速比不可比
硬件档带宽/算力档位 + 驱动版本SOL 判据失效
dtype实现与 baseline 对齐虚假加速比
指标kernel 级或端到端，二选一标注门禁误判

这套口径的边界在于它只保证「可复核」，不保证「可外推」。冻结版本与固定档位让历史数字可比，但也意味着路线图无法自动感知上游基准升级带来的能力重估；因此治理规则里必须保留 oracle 变更评审与基准升级窗口两条通道，把口径变更本身当作一次需要评审的工程事件，而不是评测工程师的私活。
