一 · 从“分数”到“时间去向”：反馈通道的层级

在路线图里，硬件反馈不是评测流水线的一个可选插件，而是决定 agent 迭代上限的基础设施。评测工程师需要把反馈分成三层并分别定义 SLA：第一层是标量结果（通过/失败、加速比、相对误差），第二层是聚合计数器（SM 占用、DRAM 吞吐、L2 命中、指令发射率），第三层是逐指令/逐 warp 的时间归因（stall 原因、SASS 热点、访存事务）。三层的信息密度与采集成本呈数量级差异，路线图必须明确“哪一层进入 agent 的上下文窗口、哪一层只进人看的报告”。一个常见工程判断是：标量结果每轮都进 prompt，聚合计数器按需检索，逐指令归因只在候选 kernel 进入 top-k 后触发，否则 token 成本与编译时延会吞掉多轮 RL 的预算。

把三层映射到可验证奖励时，需要区分“可微/可排序的代理信号”和“硬约束”。roofline 给出的理论上界是一个硬约束：任何声称超过 SOL 的候选必须先被判定为测量错误而非优化成果。设某 kernel 的实际吞吐为 T，roofline 上界为 T*，则利用率 u = T / T*；当 u > 1 时触发审计分支，检查计时口径（是否漏掉同步、是否用了错误的字节数）。这个分支本身就是治理规则的一部分：它把“分数异常”转成“口径异常”，避免 agent 通过错误测量获得奖励。

$$u = \frac{T}{T^{*}},\quad T^{*} = \min\left(\frac{\text{FLOPs}}{\text{peak FLOP/s}},\ \frac{\text{Bytes}}{\text{peak B/s}}\right)$$

代价方面：一次完整的 NCU profile 采集会让 kernel 重放数十次，单次采集的墙钟时间通常是裸跑的几十倍；若把它放进每一轮 RL 的 rollout，采样吞吐会塌缩。因此路线图的验收标准应写成“profile 触发率”而非“profile 覆盖率”——例如规定只有进入候选池的 kernel 才允许采集，且采集结果以结构化摘要（而非原始 report）进入检索库。

二 · Roofline 作为先验：让 agent 先算再写

roofline 在 agent 工作流中的正确位置是“写代码之前”，而不是“跑完之后”。脚手架应提供一个可调用的算术强度估算器：给定问题规模、数据类型、算子语义，估算最小访存量与最小浮点量，输出 I = FLOPs / Bytes 与拐点 I_c = peak FLOP/s / peak B/s。若 I < I_c，该 kernel 属于带宽受限，agent 的优化方向应集中在合并访存、减少中间张量、提高 L2 复用；若 I > I_c，则转向指令级并行、减少分支与同步。这个先验把搜索空间从“随便试”压缩到“按瓶颈类型选模板”，直接降低无效编译次数。

具体机制上，估算器不必精确：它只需要给出瓶颈类别与一个宽松上界。工程上更可靠的做法是用“字节下界”而非“实际字节”做分母，因为实际字节依赖实现细节，而 agent 在生成前并不知道。伪代码思路是：bound = max(compute_time_lb, memory_time_lb)，其中 memory_time_lb = min_bytes / peak_bw，min_bytes 由输入输出张量尺寸与是否允许融合决定。这个界用于两件事：一是拒绝明显不可能的候选（例如声称比下界还快），二是为 RL 奖励提供归一化基线，使不同规模的问题的奖励可比。

代价是估算误差会传导为错误的优化方向。对于融合算子，最小访存量取决于融合边界，估算器若假设过度融合会给出过于乐观的下界，导致 agent 追逐不可达目标并在多轮中反复失败。路线图的治理规则应要求：估算器的假设必须与 oracle 的语义检查共享同一份算子描述，任何融合边界的变更走 oracle 变更评审流程。一个具体例子是 layernorm 类算子：若估算器把两次读写合并为一次，带宽下界会减半，agent 会倾向于写单遍 kernel，但若语义要求保留中间统计量用于反向，单遍实现就是错的——这类冲突必须在评审中被显式记录。

三 · Warp stall 与 SASS：把“慢”拆成可行动的类别

聚合计数器只能告诉 agent “哪里慢”，warp stall 分解才能告诉它“为什么慢”。NCU 的 stall 原因分类（长延迟记分牌、屏障、访存依赖、指令取指、执行依赖等）应被映射为一组有限的行动标签，每个标签对应一类改写策略：长延迟记分牌高 → 提高 occupancy 或增加 ILP；屏障 stall 高 → 减少 __syncthreads 或改用 warp 级原语；访存依赖高 → 调整数据布局或预取。这个映射表是脚手架的一部分，而不是 agent 的自由发挥空间，因为自由发挥会产生大量无法验证的猜测。

映射的输入必须是结构化摘要而非自然语言报告。工程做法是让采集工具输出固定 schema：每个 stall 原因的占比、对应源码行号（通过 -lineinfo 关联）、以及该行的 SASS 指令计数。agent 拿到的是“第 42 行，LDG 指令，长延迟记分牌占该 warp 周期的显著比例”，而不是一段散文。这样奖励信号可以绑定到具体改写：若改写后该行 stall 占比下降且总时间下降，则正向奖励；若 stall 下降但总时间不变，说明瓶颈转移，奖励应为零，防止 agent 优化非关键路径。

SASS 层面的检查用于捕捉编译器行为与源码意图的偏差。典型场景是 agent 写了向量化访存但编译器因对齐不确定性退化为标量指令，此时源码看起来正确、计数器看起来正常，只有 SASS 能暴露 LDG.E 与 LDG.E.128 的区别。代价是 SASS 反汇编与行号关联会增加编译流水线的时间，且不同架构的指令编码不同，摘要 schema 需要版本化。路线图应把 SASS 检查列为“候选晋级门禁”而非每轮必跑，并把 schema 版本与基准版本一起冻结。

信号行动标签误判代价
长延迟记分牌占比高提高 occupancy / 预取occupancy 已满时无效改写，浪费编译预算
屏障 stall 高减少同步 / warp 级归约破坏正确性，需 oracle 拦截
SASS 向量化退化显式对齐 / 重排布局布局变更影响下游算子，需回归

四 · 二进制插桩：在无法用 NCU 的场合拿到时间

NCU 并非处处可用：生产环境不允许重放、容器内权限受限、或 kernel 运行时间过短导致采样噪声主导。此时二进制插桩是补充通道。机制上是在编译产物中插入轻量计时点（例如在 kernel 入口与出口写入 clock64() 差值到全局缓冲区），或在 host 侧用 CUDA event 包裹并在流上插入标记。插桩的粒度选择是核心权衡：粗粒度（每 kernel 一个时间戳）开销小但无法定位内部热点；细粒度（每 warp 或每阶段）能定位但会引入全局内存写与同步开销，改变被测对象的行为。

工程判断是：插桩只用于“确认时间归属”，不用于“精确性能排名”。因为插桩本身会扰动测量，排名必须回到无插桩的裸跑。伪代码思路：t0 = clock64(); ...; t1 = clock64(); atomicAdd(buf + block_id, t1 - t0)，聚合时取中位数而非均值以抵抗调度抖动。代价包括：全局内存写增加带宽压力（对带宽受限 kernel 尤其致命）、atomicAdd 引入序列化、以及插桩版本与发布版本必须是两个构建产物，否则生产发布门禁会拒绝带计时代码的二进制。

一个具体例子是多阶段流水线 kernel：agent 不确定时间花在加载、计算还是写回。粗粒度 event 只能给出总时间，插桩在三个阶段边界各打一个点后，发现写回阶段占比异常，进而定位到非合并写。这个信息无法从总时间推出，也无法从 roofline 推出（因为 roofline 只给总量），正是插桩的独有价值。路线图应规定插桩产物的生命周期：仅存在于调试分支，不进入候选池的正式评测，且其结论必须由一次无插桩的对照实验确认后才能写入知识库。

五 · 反馈进入 agent 上下文：检索、压缩与预算

profile 数据的真正瓶颈不是采集而是注入。把一份完整 NCU 报告塞进上下文会挤占代码与语义信息的空间，且长上下文会稀释关键信号。路线图需要定义“反馈压缩比”：原始报告 → 结构化摘要 → 行动标签，每一级都有明确的字段白名单。压缩的机制是规则化的而非模型化的，因为模型化压缩会引入不可复现的偏差，破坏奖励的可信度。字段白名单包括：瓶颈类别、top-3 stall 原因及占比、SASS 关键指令计数、以及与该 kernel 历史最优的差值。

检索侧的做法是把每次 profile 摘要与对应的源码 diff、问题规模一起写入向量库，键为“瓶颈类别 + 算子族”。当新任务进入时，脚手架先检索同族历史摘要，把“上次同类瓶颈的有效改写”作为提示注入，而不是让 agent 从零试错。这直接降低多轮 RL 的轮数需求，也就降低了 token 与编译时间成本。代价是检索可能引入错误先验：不同规模下同一瓶颈类别的有效改写可能相反（小规模下提高 occupancy 有效，大规模下反而因缓存抖动失效），因此检索结果必须附带规模区间标签，超出区间则不注入。

预算分配上，一个可执行的工程规则是：每轮 rollout 的上下文预算中，反馈摘要不超过固定比例，剩余留给源码与语义约束；当摘要超预算时按“瓶颈类别 > stall 占比 > SASS 细节”的顺序截断。这个规则把“看见时间去哪了”变成可审计的流程，而不是依赖 agent 的临场判断。验收标准应写成“摘要字段完整率”与“注入后改写命中率”两个指标，前者由流水线自动检查，后者由人工抽检，二者共同构成路线图中评测工程师的季度里程碑。

六 · 治理：把 profile 口径固化为组织流程

硬件反馈最容易腐化的地方是口径漂移：不同人用不同的计时方式、不同的 warmup 次数、不同的架构，导致历史数据不可比。治理规则必须把 profile 口径写成版本化契约，与基准版本一起冻结。契约内容包括：计时是否含同步、warmup 与重复次数、是否允许插桩、NCU 的采集模式与指标集、以及 SASS 反汇编所用的架构目标。任何变更走评审，评审记录进入技术债清单，因为口径变更会让历史奖励信号失效，进而影响 RL 训练数据的可比性。

角色分工上，评测工程师拥有 profile 契约的定义权与采集流水线的运维权，kernel 工程师负责把行动标签落实为改写并提交对照实验，RL 工程师负责把摘要字段映射为奖励并监控奖励与真实加速比的相关性，平台运维负责采集任务的容量与隔离（避免 profile 任务抢占训练或生产资源）。这个分工的关键接口是“摘要 schema”：它是评测与 RL 之间的唯一契约，schema 变更必须双方签字，否则奖励函数会在无声中错位。

路线图的季度验收应包含一项反向检查：随机抽取若干历史候选，用当前契约重跑 profile，确认瓶颈类别与当时记录一致。不一致则说明契约漂移或环境变化，触发技术债条目并暂停相关奖励信号的使用。这个检查的成本是重跑时间与采集资源，但它是防止“agent 看见的时间”与“团队相信的时间”分叉的唯一手段。最终落在具体机制上：profile 契约、摘要 schema、行动标签映射表三者共同构成硬件反馈的可信边界，路线图的治理规则围绕这三份工件冻结、评审与升级，而不是围绕某一次实验的数字。

当 profile 本身成为路线图上的成本项：硬件反馈链的边界与失效条件

把 NCU/SASS 反馈接进 agent 的闭环，代价不在采集一次指标，而在“每次候选都要采一次”的乘性开销。设单轮生成 N 个候选、每个候选需 k 次 profile 采集（正确性一次、性能一次、必要时 replay 一次），单次采集的墙钟成本为 tp，则一轮反馈时延近似为 N·k·tp 加上编译时间 tc；当 tp 达到秒级而 tc 在数十秒量级时，profile 反而成为瓶颈，agent 的迭代轮数被直接压缩。路线图上必须把“每候选 profile 预算”写成显式配额，而不是让 RL 工程师在无上限的重放里消耗集群时间。

$$\text{反馈吞吐} \approx \frac{N}{N\cdot k\cdot t_p + N\cdot t_c + t_{\text{reward}}}$$

失效条件有三类。其一，指标与目标错位：roofline 判定某 kernel 为 memory-bound，agent 便去压缩访存，但真实瓶颈可能是 launch 配置导致的尾部 warp stall，roofline 的算术强度模型对此不敏感，反馈信号把优化引向错误方向。其二，SASS 级结论不可迁移：在一种架构上通过指令重排消除的 stall，换到寄存器文件更窄或 shared memory bank 不同的目标卡上会重新出现，agent 若把 SASS 模式当作硬约束记忆，就会在跨代部署时产出退化候选。其三，二进制插桩改变被测对象：插桩点引入的额外指令与寄存器压力会扰动占用率，测得的 stall 分布已非原始 kernel 的分布，此时 profile 数据只能作相对比较，不能作为绝对 roofline 输入。

工程判断落在治理规则上：把 profile 反馈分为“筛选级”与“归因级”两档。筛选级只用轻量计时与 occupancy 粗查，覆盖全部候选；归因级才动用 NCU 全指标与 SASS 反汇编，仅对通过正确性 oracle 且进入决赛的少量候选执行，并把采集配置、架构型号、插桩开关一并冻结进基准版本，使跨季度对比不被工具口径漂移污染。这样，硬件反馈既是 agent 的“眼睛”，也是路线图上一项需要预算、需要版本冻结、需要评审变更的技术债。
