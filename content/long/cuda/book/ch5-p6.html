一 · 从“跑通了”到“时间去哪了”：反馈信号的层级

编译通过、结果比对通过，只说明 kernel 落在正确性 oracle 的接受域内，它对“这个 kernel 有多快、慢在哪个单元”一无所知。agent 脚手架要形成有效修复闭环，必须把执行反馈分成三层并分别回灌：第一层是布尔层（编译成功/失败、数值是否在容差内），第二层是标量层（端到端时延、有效带宽、占用率、寄存器数、shared memory 用量、编译耗时），第三层是结构化层（逐行 stall 归因、指令混合、内存事务形态、SASS 片段）。三层的信息密度与获取成本严格反向：布尔层几乎零成本但信息量最小，结构化层需要 NCU 级别的插桩与多次 replay，单次采集的时延可达毫秒到秒级，且会显著扰动被测 kernel 的时序。脚手架的工程判断在于：不要一开始就上最重的一层，而是按“标量层先定位量级、结构化层再定位单元”的顺序逐级下钻，把昂贵的 profile 调用当作预算受限的资源来管理。

一个具体机制是把 roofline 作为标量层的归一化器。给定 kernel 的浮点运算量 $F$（FLOPs）与访存量 $B$（Bytes），以及目标设备的峰值算力 $P_{peak}$ 与峰值带宽 $BW_{peak}$，算术强度 $I=F/B$ 与可达性能上界为：

$$P_{max}=\min\left(P_{peak},\; I\cdot BW_{peak}\right),\qquad \text{SOL}=\frac{P_{measured}}{P_{max}}$$

SOL（speed-of-light）百分比把“快”变成“离物理上界还差多少”，这让 agent 的修复目标从“让时延变小”变成“把 SOL 从某个低值推向更高值”，并且能立刻区分两类失败：算术强度低而带宽已接近峰值，说明瓶颈在访存模式（合并访问、bank conflict、冗余加载）；算术强度高而算力利用率低，说明瓶颈在指令发射与流水线（依赖链、分支、寄存器压力）。这个区分决定了后续该往哪个方向改代码，而不是盲目调 block size。

代价在于归一化本身需要准确的 $F$ 与 $B$，而 agent 往往只能从 kernel 语义推断这两个量；推断错误会让 SOL 失真，进而误导修复方向。工程上的做法是让 agent 同时输出它对 $F$、$B$ 的估算依据（例如“每个输出元素做 2 次乘加、读 3 个输入张量”），把估算与实测带宽/算力并列回灌，让模型自己发现“实测带宽超过峰值”这类矛盾信号，从而修正对访存量的假设。这比直接给一个 SOL 数字更有诊断价值。

二 · Warp stall 归因：把“慢”拆成可命名的原因

NCU 的 warp state 采样把每个 warp 的停滞周期归类到具体原因：long scoreboard（等待全局内存返回）、short scoreboard（等待 shared memory 或 MIO）、wait（等待固定延迟指令结果）、barrier（等待 __syncthreads）、not selected（可发射但调度器选了别的 warp）、math pipe throttle、MIO throttle、LG throttle 等。这些类别构成一张“瓶颈指纹”，agent 需要的是指纹而非原始计数器。伪代码思路如下：

  • 对目标 kernel 采集 warp stall 采样，得到各原因占比 $s_i$，按降序取前 3；
  • 若 long scoreboard 占主导 → 访存延迟未被覆盖，检查是否有足够 ILP、是否该用异步拷贝或预取；
  • 若 barrier 占主导 → 同步点过密或负载不均衡，检查 tile 划分与线程分工；
  • 若 math pipe throttle 占主导 → 计算单元饱和，属于好现象，此时应看 SOL 是否已接近上界；
  • 若 not selected 占主导 → 占用率过高导致调度竞争，可能需要降低 occupancy 换取每 warp 更多寄存器。

把这张指纹与占用率、每线程寄存器数、shared memory 用量一起回灌，agent 才能做出“提高占用率”还是“降低占用率”这种反直觉但正确的判断。代价是采样本身：warp stall 采样需要多次 replay 同一 kernel，NCU 的 replay 机制会序列化执行并保存/恢复内存状态，单次 profile 的墙钟时间可达被测 kernel 的数十倍到数百倍，且 replay 次数随采集的 section 数量增长。在 agent 的多轮修复预算里，这意味着每轮最多只能负担一两次全量 profile；更经济的做法是先用标量层筛掉明显不行的候选，只对“看起来有希望但 SOL 偏低”的候选做 stall 归因。

具体例子：一个 reduction kernel 的 SOL 只有峰值的很小一部分，标量层显示有效带宽远低于峰值。stall 指纹显示 long scoreboard 与 barrier 各占大头，寄存器数偏高导致 occupancy 受限。agent 据此把“每个线程处理多个元素 + 减少同步次数”作为修复动作，而不是去调 block size——后者在这个指纹下几乎不会带来增益。这个例子说明指纹的价值在于排除错误方向，而不只是提示正确方向。

三 · SASS：当源码语义与机器语义分叉时

PTX 到 SASS 之间隔着寄存器分配、指令调度、谓词化、循环展开与软件流水，源码层面的“我写了什么”和机器层面的“实际执行了什么”经常不一致。agent 若只看 CUDA C++ 或 Triton 源码，会错过三类关键信息：编译器插入的冗余指令（例如未优化的地址计算链）、被展开或未展开的循环导致的指令缓存压力、以及 shared memory 访问被编译成 LDS/LDSM 后的 bank 冲突形态。SASS 片段回灌的作用是把这些“编译器做了什么”暴露给模型，让它判断该改源码还是改编译选项（如 maxrregcount、launch bounds）。

代价是 SASS 的可读性与 token 成本：一段完整 kernel 的 SASS 动辄数百到上千条指令，直接塞进上下文会挤占修复预算。工程做法是让脚手架做指令级摘要而非全文回灌：统计指令类别分布（FFMA/FADD/LDG/STG/LDS/BAR/SETP 等各占多少）、最长依赖链长度、每个基本块的指令数、以及被谓词化的指令比例，只在模型明确要求时才附上热点基本块的 SASS 片段。这个摘要本身需要一次 cuobjdump 或 nvdisasm 调用，属于离线可缓存的分析产物，不占用运行时 profile 预算。

一个具体机制是把 SASS 摘要与 stall 指纹交叉验证：若 stall 显示 wait（固定延迟依赖），而 SASS 摘要显示存在长 FFMA 依赖链且缺少交错，则修复方向是手动引入 ILP 或改用多累加器；若 stall 显示 short scoreboard，而 SASS 显示大量 LDS 且同一 warp 内地址步长呈现冲突模式，则修复方向是 padding shared memory 或改变数据布局。交叉验证能显著降低 agent 对单一信号的过拟合——只看 stall 会误判为“内存慢”，只看 SASS 会误判为“指令多”，两者对齐后才指向真实机制。

四 · 二进制插桩：在无法用 NCU 的场合拿到时间线

NCU 依赖特定驱动与权限，且在容器化、多租户或受限 GPU 环境中未必可用；此时二进制插桩提供了另一条路径：在编译产物中注入计时与计数器读取指令（如 clock64()、%globaltimer、或通过 CUDA 的 profiler API 启停），在 kernel 内部按 block/warp 粒度记录时间戳，事后聚合出时间线。典型思路是在 kernel 入口与出口各读一次全局计时器，按 SM id 与 block id 分桶，得到每个 block 的驻留时间分布，从而识别尾部效应（tail effect）与负载不均衡。

插桩的代价直接体现在被测 kernel 的时延上：每次计时器读取都是一条有延迟的指令，且会打断流水线；在访存密集的小 kernel 上，插桩开销可能与被测工作量同量级，测出的时间线已经不代表真实执行。工程判断是只在“需要定位不均衡”时插桩，且插桩版本的时间数据只用于相对比较（哪个 block 慢），不用于绝对性能口径。另一个代价是插桩代码本身要占用寄存器和指令槽，可能改变 occupancy，从而改变被观测对象的行为——这是观测者效应在 GPU 上的具体形态。

具体例子：一个 persistent kernel 的端到端时延波动很大，标量层只能看到方差。插桩后按 SM 分桶发现少数 SM 上的 block 驻留时间明显偏长，结合 SASS 摘要发现这些 block 落在 shared memory 容量受限的配置上，导致 occupancy 不均。修复动作是调整 grid 维度使 block 到 SM 的映射更均匀，而不是改算法。这类问题在纯源码层面几乎不可见，必须依赖运行时时间线。

五 · 反馈回灌的预算与终止条件

把上述信号组织成 agent 可消费的反馈，需要解决三个预算问题：profile 调用次数、上下文 token、以及每任务的修复轮数。一个可操作的机制是分层预算表：

层级单次成本触发条件回灌形态
布尔层编译+执行，最低每轮必做通过/失败 + 错误类别
标量层一次计时 + 一次 roofline 归一正确性通过后时延、带宽、SOL、寄存器/占用率
stall 指纹NCU replay，数十倍时延SOL 低于阈值且标量层无解释前 3 类 stall 占比
SASS 摘要离线反汇编，可缓存指纹指向指令/依赖问题时指令分布、依赖链、热点块片段
插桩时间线改写 kernel，扰动时序怀疑不均衡或尾部效应按 SM/block 的驻留分布

终止条件不能只看“轮数用完”，而要看“信号是否还在变化”。一个可判定的终止规则是：连续两轮的 SOL 提升低于测量噪声水平，且 stall 指纹的前 3 类未发生重排，则判定进入平台期，停止继续投入 profile 预算。这比固定轮数更能节省昂贵的 replay 调用，也避免 agent 在同一个瓶颈上反复做无效修改。代价是噪声估计本身需要重复测量，而重复测量又要占用预算——工程上通常用同一候选的多次计时取中位数来近似噪声下界，只在标量层做，不牵动 NCU。

上下文管理方面，历史尝试压缩应保留“指纹 → 修复动作 → SOL 变化”三元组，而不是保留完整 profile 输出。这样当 agent 在新一轮看到相似指纹时，可以直接检索到此前哪些动作无效，避免重复试错。这个记忆结构与失败模式记忆共用同一份存储，但索引键是 stall 指纹而非错误类别。

六 · 让 agent 自己决定看哪里

更高一层的设计是把 profile 采集本身变成 agent 的动作空间：agent 不只输出代码修改，还输出“下一步要采集什么信号”的请求，脚手架据此调度 NCU 或插桩。这要求脚手架暴露一个受限的采集接口（例如只允许请求 stall 指纹、SASS 摘要、时间线三者之一），并强制 agent 在请求中说明假设——“我认为瓶颈在访存延迟，请采集 long scoreboard 占比以验证”。这种“假设-验证”循环把 profile 从被动回灌变成主动实验，显著提升每轮信息的利用率。

代价是动作空间扩大带来的决策负担与 token 消耗：每次请求都要附带假设文本，且错误的假设会浪费一次昂贵的采集。工程上的约束是给采集请求设配额（例如每任务固定次数），并让脚手架在配额耗尽后强制 agent 基于已有信号做决策。这个约束把“看见时间去哪了”从无限探索变成有限实验设计，也正是 agent 脚手架区别于一次性生成的核心：它不是让模型看得更多，而是让模型在有限观测下做出可验证的归因。

反馈回路的三重衰减：采样偏差、插桩扰动与符号丢失

把 NCU 计数器直接塞进 agent 上下文，第一个失效条件是采样窗口与 kernel 生命周期不匹配。NCU 默认按固定周期采样 SM 的 warp stall 计数器，短 kernel（微秒级）落在采样间隔内只得到个位数样本，stall 分布退化为噪声；而 agent 若据此判定“瓶颈在 long scoreboard”，后续修复方向就是错的。工程上的边界是：只有当 kernel 稳态执行时间显著大于采样周期、且 grid 规模足以让各 SM 都进入稳态时，stall 分类才具备可解释性。对短 kernel 必须改用 replay 模式多次重放取聚合，代价是采集时延成倍上升——这部分开销不进 kernel 时延，却进 agent 的墙钟预算，直接压缩每任务的修复轮数。

第二个失效条件是插桩本身改变被观测对象。二进制插桩（如对 SASS 插入指令级计数器）会破坏编译器原有的指令调度与寄存器分配，测得的时间不再是被优化代码的时间。可用的折中是只对 roofline 的两个端点做粗粒度校验，用下式判断优化空间是否真实存在：

$$\text{SOL}=\max\!\left(\frac{\text{FLOP}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right),\quad \text{headroom}=\frac{T_{\text{meas}}-\text{SOL}}{\text{SOL}}$$

当 headroom 小于插桩引入的扰动幅度时，agent 看到的“优化空间”是测量伪影，任何基于它的修复都是过拟合。此时正确做法是退回不插桩的端到端计时加静态 SASS 审查，牺牲 stall 归因精度换取可信度。

第三个失效条件是SASS 与源码的符号断裂。编译器内联、循环展开、谓词化之后，SASS 行号与 CUDA C++ 行号不再一一对应，agent 拿到的“第 47 条指令 stall 严重”无法映射回源码的哪个循环。反馈粒度必须从行号退到错误类别（如“访存合并失败”“寄存器溢出”），否则 agent 会在错误的源码位置反复改写。系统代价体现在 token 上：带 SASS 片段与 stall 注释的反馈上下文通常是纯编译错误的数倍，多轮修复预算被迅速耗尽。可行的压缩是只回灌 top-k stall 指令的助记符与所属基本块，丢弃完整反汇编。
