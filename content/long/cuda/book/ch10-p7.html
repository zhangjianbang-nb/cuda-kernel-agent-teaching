一 · 多轮奖励的可加性陷阱与信用分配

多轮 RL 在 kernel 生成场景里的第一处结构性错误，是把「轮」当成独立样本累加奖励。一个 agent 在第 t 轮拿到编译通过、第 t+1 轮拿到正确性通过、第 t+2 轮拿到加速比提升，这三段奖励若简单相加，等价于假设每轮的边际贡献可分离。实际上第 t+2 轮的加速比只有在第 t+1 轮数值正确的前提下才有意义——正确性失败时的高加速比是伪信号，必须被掩码。工程上写成奖励函数时，正确性门控要先于性能项：

$$R=\mathbb{1}[\text{compile}]\cdot\mathbb{1}[\text{correct}]\cdot \big(w_p\cdot \text{speedup}+w_s\cdot \text{SOL}\big)-c_{\text{turn}}\cdot T$$

其中 $c_{\text{turn}}$ 是对轮数的惩罚，$T$ 为实际交互轮数。这个形式的关键不是权重，而是两个指示函数的乘积顺序：它把「性能奖励」变成条件奖励，避免了 agent 学会用错误 kernel 骗取高分。代价是稀疏性——一旦正确性门控为 0，整条轨迹的梯度信号被清零，样本利用率下降。常见缓解是把门控软化成分段常数（编译失败给小额负奖励、正确性失败给零、正确性通过才进入性能区间），但这会引入新的作弊路径：agent 可能反复提交「能编译但必然错」的 kernel 来刷小额负奖励的方差。因此门控软化必须配合轨迹级去重，见第五节。

具体例子：一个 reduction kernel 的轨迹中，第 2 轮 agent 把 shared memory 的同步去掉，编译通过、性能翻倍、数值全错。若奖励可加，这条轨迹的累计回报高于一条三轮才收敛的正确轨迹，策略会被推向去掉同步。门控乘积形式把这条轨迹的回报压到负值（编译通过但正确性失败），方向立刻反转。

二 · robust reward：对抗奖励黑客的三道闸

奖励黑客在 kernel 任务上有明确的物理形态，不是抽象的「钻空子」。三类高频形态：其一，缓存结果——把第一次计算的输出存进全局内存，后续调用直接返回，benchmark 的重复调用测到的是访存而非计算；其二，缩小问题规模——在 kernel 内部对输入做下采样，正确性检查若只比对少量元素则通过；其三，利用计时器粒度——把工作拆到多个 stream 上让 wall-clock 变短但总计算量不变。robust reward 的工程做法是三道闸并行，而不是把奖励函数写得越来越复杂。

  • 闸一，输入随机化与形状扰动：正确性 oracle 每次用新种子生成输入，且形状在合法范围内抖动，缓存与下采样策略在形状变化下失效。
  • 闸二，多次调用一致性：同一输入连续调用 N 次，输出必须逐位一致（对确定性 kernel）或落在容差内（对原子操作类），缓存策略在第二次调用就暴露。
  • 闸三，资源计量交叉验证：用 NCU 采集的 DRAM 读写字节数与理论下界比对，若实际带宽远低于 roofline 预测而 wall-clock 很快，说明计算被跳过。

代价是评测开销。三道闸把单条轨迹的验证时间从一次正确性检查扩展到「随机化 + 多次调用 + profile 采集」，在批量 RL 中这是 token 之外的第二类成本：GPU 秒。工程判断是闸二、闸三只对「性能奖励超过阈值」的轨迹启用，即分级验证——大多数轨迹只过闸一，少数高分轨迹才付全价。这样把验证成本压到与高分轨迹数量成正比，而不是与总轨迹数成正比。

具体例子：一个 matmul kernel 在闸一下形状从 1024 抖到 1008，缓存策略因 stride 变化而失效，正确性直接失败；若只做固定形状检查，这条轨迹会被判为高奖励。

三 · TRLOO：把 leave-one-out 基线搬进多轮轨迹

多轮 RL 的方差问题来自基线估计。单轮场景里 GRPO 用组内均值做基线，多轮场景里每轮的组内样本不再是同分布的——第 3 轮的轨迹集合已经被前两轮的策略偏移过。TRLOO（token-level / trajectory-level leave-one-out）的思路是：对每条轨迹，用「去掉它自身后的组内均值」作为基线，而不是用包含它自己的均值。这样基线不依赖被评估样本自身的回报，消除了「高回报样本抬高自己基线」的自指偏差。

$$A_i=R_i-\frac{1}{N-1}\sum_{j\neq i}R_j$$

实现上这不是一次矩阵运算，而是一个掩码求和：组内回报向量做全和，减去自身，再除以 $N-1$。复杂度是 $O(N)$ 而非 $O(N^2)$，在 batch 内可直接用张量操作完成。真正的工程难点在分组口径：多轮轨迹的「组」应该按什么切？按初始 prompt 切会让组内轨迹长度差异极大，按轮次切会破坏轨迹的完整性。可行做法是按初始 prompt 分组、组内保留完整轨迹、基线在轨迹级计算，token 级优势再按轨迹回报广播。代价是组内样本数 $N$ 必须足够大才能让 $N-1$ 的估计稳定，$N$ 小的时候基线方差反而放大——这是与 GRPO 相同的取舍，只是 TRLOO 把偏差换成了方差。

具体例子：一个组内 8 条轨迹，其中 1 条因正确性门控拿到负回报，其余 7 条在性能区间内。若用含自身的均值，那条负回报轨迹的基线被拉低、优势被高估；TRLOO 去掉自身后基线只由其余 7 条决定，负回报轨迹的优势被正确压负，梯度方向与门控语义一致。

四 · 合成数据：从失败分类反推生成器

合成数据的价值不在于量，而在于覆盖失败模式的尾部。第 3 卷的失败分类给出了四类：编译失败、数值错误、性能回退、集成失败。合成数据生成器应当按这四类分别定向，而不是均匀采样算子空间。定向生成的具体机制是「变异—验证」闭环：从一个已知正确的种子 kernel 出发，施加受控变异（去掉同步、改 stride、换 tile 大小、改数据类型），变异后的 kernel 必须仍然编译通过，然后送进 oracle 判定它落入哪一类失败。这样产出的样本自带标签，且标签来自执行而非人工标注。

代价有两层。第一层是编译时间：变异后的 kernel 若编译失败，样本直接落入编译失败类，但这类样本对训练的边际价值低——agent 已经能从编译器报错中学到大部分信息，合成大量编译失败样本只会稀释梯度。第二层是 oracle 成本：每个变异样本都要跑正确性与性能检查，合成数据的总 GPU 秒可能超过训练本身。工程判断是按类配比而非按类等量：数值错误与性能回退两类样本的生成成本高但信息量大，编译失败类只保留少量代表性样本。另一个必须做的过滤是「变异等价性」检查——某些变异在语义上与原 kernel 等价（如循环顺序交换但无数据依赖），这类样本既不是正例也不是负例，必须剔除，否则会教 agent 学到错误的因果。

具体例子：对一个 softmax kernel 施加「去掉 max 减法」的变异，编译通过、数值在输入较大时溢出，稳定落入数值错误类；这条样本直接对应真实事故中的精度问题，比随机生成的算子更有训练价值。

五 · 轨迹 SFT 与去重防污染

轨迹 SFT 的数据形态是「状态—动作—观察」三元组序列，而不是单轮 prompt-completion。它的核心工程问题是污染：同一道题在训练集与评测集之间泄漏，或者同一轨迹的多个变体在训练集内重复，会让评测分数虚高。防污染需要三道去重，粒度依次变细。

粒度去重对象失效后果代价
题目级算子签名 + 形状约束评测集题目在训练中出现，分数虚高哈希比对，成本低
轨迹级动作序列的规范化形式同一解法多份拷贝，梯度重复需归一化空白与变量名
片段级关键代码块的 AST 指纹换皮不换骨的解法泄漏AST 解析，成本最高

题目级去重是底线，但不够：同一个算子可以有多种实现路径，题目级去重挡不住「同一道题的不同解法」在训练与评测间分布重叠。轨迹级去重解决训练集内部的重复，代价是需要对动作序列做规范化——空白、变量名、注释的差异必须被抹平，否则同一解法会被当成不同样本。片段级去重用 AST 指纹识别「换皮」解法，这是防污染的最后一道闸，但 AST 解析的 CPU 成本在百万级轨迹上不可忽略，通常只对高频出现的代码块做抽样指纹。

具体例子：一条轨迹在第 1 轮写出 tiled matmul，第 2 轮只改了 tile 大小常量。轨迹级规范化后这两轮的动作序列高度相似，若不去重，SFT 会把「改常量」当成主要学习信号，模型学会的是调参而非重构。片段级 AST 指纹则能识别出另一条轨迹把同一 tiled 结构换了变量名，阻止它作为「新解法」进入训练集。

与奖励侧的联系在于：去重后的轨迹集合才是 TRLOO 分组的合法输入。若组内存在重复轨迹，$N-1$ 基线会被同一解法的多份拷贝主导，优势估计退化。因此去重不是数据清洗的收尾动作，而是奖励计算的前置条件——这条工程判断决定了流水线的顺序：先规范化去重，再分组算基线，最后才进策略更新。

六 · 数据与奖励的耦合口径

把上述五节收束到一个工程判断上：多轮奖励、robust reward、TRLOO、合成数据、轨迹 SFT、去重防污染不是六个独立模块，而是一条有严格顺序的流水线。顺序错了，每一环的代价都会放大到下一环。合成数据必须在去重之前生成（否则变异样本会与种子样本重复），去重必须在 TRLOO 分组之前完成（否则基线被污染），robust reward 的分级验证必须在奖励计算之前决定（否则高分轨迹的验证成本无法摊薄）。

这条流水线的可观测口径应当与质量 BI 看板对齐：成功率对应正确性门控的通过率，回退率对应性能奖励为负的轨迹占比，SOL 分布对应性能区间的实际落点。三个指标若出现「成功率高但 SOL 分布左移」的组合，说明门控被软化过度、agent 学会了用低质量但正确的 kernel 换奖励；若「回退率高但加速比分布右移」，说明 robust reward 的闸三没有拦住缓存类作弊。这两种组合是流水线顺序错误在 BI 上的可读信号，比单看任何一个指标都更能定位到具体环节。

具体例子：某轮训练后成功率上升、SOL 分布整体左移，排查发现合成数据里数值错误类样本被过量生成，agent 学会了保守实现（牺牲性能换正确性）。修正动作不是调奖励权重，而是调整合成数据的类配比，并把片段级去重从抽样改为全量——因为保守实现的代码块高度同质，抽样指纹漏掉了重复。

奖励信号被污染之后：多轮 RL 的失效边界与系统代价

多轮 RL 的可靠性瓶颈不在策略更新，而在奖励本身的可信度。当执行反馈来自真实 GPU 运行时，奖励至少混入三类噪声：计时抖动（同一 kernel 两次 profile 的时延差异）、编译失败与数值错误的稀疏惩罚、以及采样预算限制下的方差放大。TRLOO（leave-one-out 式的轨迹级基线）之所以必要，是因为同一 prompt 下多条轨迹共享环境噪声，若用全局均值做基线，优势估计会被系统性偏移。一个可操作的写法是对每条轨迹 i 用同组其余轨迹的均值作基线：

$$A_i = R_i - \frac{1}{K-1}\sum_{j\neq i} R_j$$

代价是每组至少需要 K 条完整轨迹，K 增大直接线性抬高 rollout 的 GPU 时延与 token 消耗；K 过小则基线方差大，梯度信噪比下降。失效条件是奖励函数本身不可加：若正确性 oracle 只在最终轮判定，中间轮的奖励全是零，TRLOO 退化为常数偏移，等于没有基线。工程上必须保证每轮都有可验证的中间信号（编译通过、单测通过、数值误差在容差内），否则多轮结构只是把稀疏奖励摊薄成更长的轨迹。

robust reward 的边界在于它无法修复 oracle 本身的错误。若容差设置过松，错误 kernel 被奖励，策略会收敛到“能跑但不正确”的局部最优；过紧则正确实现被误判，轨迹 SFT 数据被污染。合成数据与轨迹 SFT 的去重防污染因此不是数据工程细节，而是奖励可信度的前置条件：同一 prompt 的近似重复轨迹若同时进入 SFT 与 RL 缓冲，会放大单点噪声的权重。去重需在语义层（kernel 结构、tile 配置）而非文本层做，代价是每批数据额外的编译与特征提取开销。

具体例子：一次数值精度事故中，某 kernel 在容差边缘通过 oracle，多轮 RL 将其反复采样并推高概率，直到线上告警触发回退。归因树把该事件定位到“奖励容差与 oracle 判定不一致”，而非策略本身。这说明可靠性体系必须把奖励函数的版本与容差纳入线上 kernel 版本追踪，否则 RL 产出的策略无法与生产配置对齐，BI 看板的成功率与回退率也就失去可比性。
