一 · 四个角色的分工边界与交接契约

Agent 脚手架不是“一个大模型包打天下”，而是把一次 kernel 生成任务拆成四个职责互斥、接口固定的角色：coder 负责把自然语言规格与已有代码上下文翻译成候选实现（CUDA C++ / Triton / CuTe / PTX 片段）；judge 负责在给定输入上判定候选是否满足正确性 oracle；profiler 负责把编译产物送进硬件计数器与反汇编通道，产出 NCU 指标与 SASS 片段；search 负责在多轮之间决定“改什么、保留什么、放弃什么”。这四个角色的分工不是组织图上的装饰，它直接决定执行反馈能否被正确消费。

交接契约的核心是三条不可跨越的边界。第一，coder 不得读取 judge 的判定阈值内部实现，只能拿到布尔结果与失败样例的最小复现；否则 coder 会退化成对测试用例的过拟合器。第二，judge 不得读取 profiler 的性能数据，正确性判定必须先于性能判定完成，否则会出现“为了跑得快而放宽容差”的污染路径。第三，profiler 的输出必须是结构化文本而非自由描述，因为下游的 search 与 SFT 数据清洗都要按字段解析。一个具体机制是：每轮交互产生一条三元组记录 (round_id, role, payload)，payload 带 schema 版本号；search 只消费 schema 校验通过的记录，校验失败即视为该轮无效，不进入轨迹。

代价体现在 token 与时延上。四角色分离意味着每轮至少四次模型调用（coder 生成、judge 判定说明、profiler 解释、search 决策），上下文在角色间反复搬运。若把 judge 与 profiler 合并成一次调用，可省一次往返，但正确性与性能信号会互相污染，后续偏好对构造（快 vs 慢、对 vs 错）就失去可分离的标签来源。工程判断是：宁可多一次调用，也要保住标签的可分离性，因为偏好对的质量直接决定 SFT 基座的上限。

二 · 执行反馈的三种粒度与消费方式

执行反馈不是单一信号，按粒度分三层，每层的消费方不同。最粗一层是编译/运行状态：编译失败、非法内存访问、超时、数值不匹配。这一层由 judge 消费，产出布尔与失败分类码，是过滤失败轨迹的第一道闸。中间一层是数值差异：最大绝对误差、相对误差、逐元素不匹配位置分布。这一层由 judge 与 coder 共同消费，coder 用它定位“哪个 tile、哪个边界条件写错了”。最细一层是硬件反馈：NCU 的吞吐、占用率、访存事务数、bank conflict 计数，以及 SASS 中实际生成的指令序列。这一层由 profiler 消费并转写为解释文本。

三层反馈的消费节奏不同。编译失败是即时反馈，一轮内即可闭环；数值差异需要至少一次完整运行；硬件反馈需要额外一次带计数器采集的运行，且采集本身有开销——NCU 逐 kernel 采集会显著拉长单次执行时间，采集粒度越细（逐指令、逐 sector）开销越大。因此 profiler 角色必须做采样决策：默认只采关键指标集，只有在 search 明确要求“定位瓶颈”时才开启细粒度采集。这个决策本身是一个成本/信息量的权衡，应写进脚手架的策略表而非交给模型即兴判断。

$$\text{gain}(r)=\frac{\text{pass}(r)\cdot \mathbb{1}[\text{speedup}(r)>\theta]}{\text{cost}_{\text{compile}}(r)+\text{cost}_{\text{run}}(r)+\text{cost}_{\text{prof}}(r)}$$

上式是 search 角色给每轮候选打分的一个可用形式：分子只在“通过正确性且加速超过阈值”时非零，分母把编译时间、运行时间与 profile 采集开销都计入。它迫使 search 不能无限追加 profile 轮次——采集越贵，同样的加速收益摊薄后得分越低。一个具体例子：某候选首轮数值不匹配，judge 给出不匹配位置集中在尾块，coder 据此只改尾块边界处理，第二轮通过；此时若 search 仍要求 profiler 做全量逐指令采集，分母膨胀而分子不变，该轮在打分上应被判为低价值，不进入偏好对的正例池。

三 · NCU 与 SASS 的转写：从计数器到可训练文本

NCU 输出的是计数器与派生指标，SASS 输出的是指令序列。两者都不能直接喂给模型——原始计数器是数字表，SASS 是长指令流，直接进上下文既贵又难对齐到源码。profiler 角色的真正工作是转写：把“哪个指标偏离 roofline 预期”映射回“哪段源码结构可能有问题”，并把 SASS 中与源码行对应的指令片段截取出来作为证据。

转写需要一张映射表：指标异常模式 → 可疑源码结构 → 建议动作。例如高 bank conflict 计数对应共享内存访问步长，建议检查 padding；低占用率伴随高寄存器数对应寄存器压力，建议拆分 kernel 或减少活跃变量；访存事务数远高于理论值对应合并访问被破坏，建议检查索引表达式。这张表是脚手架里的静态资产，不依赖模型即兴发挥，保证转写结果稳定可复现。SASS 侧的转写规则是“只截取与可疑结构对应的指令窗口”，窗口长度固定，避免上下文长度随 kernel 规模失控。

代价有两面。转写文本进入 SFT 样本会占用 token 预算：一条完整的 profile 解释样本通常包含指标摘要、映射结论、SASS 窗口三段，长度显著高于纯代码样本，因此 profile 解释类样本在 SFT 配比中必须单独计量，不能与代码样本按条数简单混配。另一面是正确性风险：转写是启发式的，映射表可能给出错误归因，若这类样本未经人工或规则复核就进入 SFT，会把错误归因固化成模型的先验。工程判断是：profile 解释类样本进 SFT 前必须过一道“归因可验证”闸——即该归因能被后续一轮实际修改验证为有效，否则只作为 RL 上下文而不作为 SFT 目标。

四 · 多轮修正的状态机与失败轨迹的保留策略

多轮修正不是“反复重试直到通过”，而是一个带状态的状态机。状态至少包括：待生成、待判定、判定失败（分类码）、判定通过待 profile、profile 完成待决策、已接受、已放弃。状态转移由 search 触发，且每次转移必须记录触发依据（哪条反馈、哪个指标）。没有状态机的多轮循环会产生两类垃圾数据：重复的无效重试（同一错误反复出现）和无依据的接受（通过但无加速，却被记为成功）。

失败轨迹的保留是本部分的关键决策。失败轨迹有两种价值：作为负例进入偏好对（对 vs 错），或作为诊断样本进入 SFT（教模型识别错误模式）。但并非所有失败都值得保留。编译失败且错误信息指向明显语法问题的轨迹，信息量低，保留只会稀释数据；数值不匹配但失败位置稳定、可归因到具体结构的轨迹，信息量高，应保留并标注归因。判据可以写成：保留当且仅当该失败在状态机中产生了新的分类码或新的归因结论。这条判据同时抑制了去重压力——同一分类码的重复失败天然被折叠。

代价是存储与清洗成本。保留失败轨迹意味着数据资产中负例比例上升，SFT 配比必须相应调整，否则模型会学到“先写错再改”的冗长模式而非一次写对。一个具体例子：某轮 coder 生成的 kernel 在边界 tile 上越界，judge 给出非法访存分类码，coder 第二轮加上边界判断后通过但性能下降；这条轨迹应拆成两段——第一段作为“越界负例”，第二段作为“正确但慢”的偏好对负侧，而不是整条作为一个成功样本。拆分动作由状态机在转移时自动完成，这是脚手架而非人工的职责。

五 · 冷启动稳定性：脚手架如何稳住下限

RL 冷启动不稳的根因通常不在奖励函数，而在轨迹质量参差：同一批任务里，有的轨迹经过多轮修正后收敛，有的在无效重试中打转，奖励信号因此方差过大。脚手架的职责是在数据进入 RL 之前把方差压下来——通过状态机过滤无效轮次、通过归因闸过滤错误解释、通过拆分规则把混合轨迹拆成干净的正负片段。

具体机制是“三闸过滤”：第一闸在 judge 层，剔除分类码重复且无新信息的轮次；第二闸在 profiler 层，剔除归因无法被后续修改验证的 profile 解释；第三闸在 search 层，剔除分子为零（未通过或未加速）却消耗了高采集成本的轮次。三闸之后剩下的轨迹才进入清洗与配比环节。代价是数据量下降：过滤越严，可用于冷启动的轨迹越少，需要以更多任务并行来补足绝对量；但方差下降带来的稳定性收益通常大于数量损失，因为冷启动阶段模型需要的是可复现的信号而非海量噪声。

一个具体例子：团队发现同一批 kernel 任务在 RL 初期通过率波动大，回查轨迹发现大量轮次属于“编译失败→改语法→再失败”的循环，这些轮次在三闸中被第一闸折叠，剩余轨迹的通过率分布明显收窄，冷启动随即稳定。这里的关键不是某个阈值调参，而是把“什么算一轮有效修正”的定义从模型手里收回，固化进脚手架的状态机与过滤规则，使数据资产成为可复用底座而非一次性产物。

六 · 版本对齐：脚手架输出与基准版本的绑定

脚手架产出的轨迹、profile 文本与偏好对，必须与基准版本绑定，否则同一份数据在不同基准修订下会给出矛盾的标签。绑定方式是在每条记录上打三元版本号：基准版本、oracle 版本、脚手架 schema 版本。三者任一变更，旧记录不得直接混入新一批训练数据，必须走重放或重标流程。

重放的代价是算力：重放意味着把历史候选重新编译、重新判定、重新采集，编译时间与采集开销按记录数线性增长。因此版本对齐策略应是“增量重放”——只重放受变更影响的记录子集，例如 oracle 容差变更只影响数值判定相关记录，schema 变更只影响解析失败的记录。这个子集划分依赖 schema 版本号在设计时就预留字段级溯源，而不是事后补打标签。工程判断落在具体机制上：脚手架在写每条记录时同时写入其依赖的判定规则标识与指标采集配置标识，使后续版本对齐可以按标识做集合运算而非全量重跑；没有这层标识，数据资产就只是一堆无法审计的文本，冷启动的稳定性也无从复现。

脚手架失效的三种典型形态与可观测代价

coder/judge/profiler/search 的分工在纸面上是流水线，实际运行时是一个带反馈回路的搜索过程：coder 产出候选 kernel，judge 给出正确性判定，profiler 回填 NCU/SASS 证据，search 决定下一轮往哪个方向改。这条回路的边界不在单点能力，而在反馈信号的可分辨性。当 judge 的判定粒度粗于 coder 的修改粒度时，回路退化为随机游走——例如 judge 只输出 pass/fail，而 coder 一轮同时改了 tile 大小、shared memory 布局和 unroll 因子，失败信号无法归因到任一变量，下一轮只能整体回退或盲目重采样。可分辨性可以用一个粗糙的判据表达：若一轮修改涉及 k 个正交决策点，而反馈只有 m 个可区分状态，则有效归因率上界约为 m/k；当 m/k 远小于 1 时，多轮修正的期望收益被稀释成重试成本。这里的代价是 token 与编译时间：每轮重采样都要重新生成完整 kernel 文本并触发 nvcc/ptxas 编译，编译失败还要额外一轮修复，长轨迹的上下文迅速膨胀。

第二类失效来自 profiler 证据的语义鸿沟。NCU 给出的是 stall reason 分布、achieved occupancy、L2 命中率等计数器，SASS 给出的是指令级调度与寄存器压力，但 coder 读到的是自然语言摘要。若摘要丢失了“哪个 warp scheduler 在等哪条依赖”这一层，coder 容易把 memory-bound 误判为 latency-bound，做出加大并行度却恶化寄存器溢出的修改。一个可操作的约束是把 profile 文本的压缩比控制在可回溯范围内：设原始 NCU 报告含 N 个指标，摘要保留 s 个，则误判概率随 s/N 下降但上下文成本随 s 线性上升，工程上应优先保留与 roofline 位置直接相关的少数指标（如 DRAM throughput、SM busy、issue slot 利用率），而非均匀采样。代价体现在显存与上下文长度：完整 NCU 报告动辄数十 KB，直接进 SFT 样本会挤占序列预算，通常需要结构化裁剪后再入模。

第三类失效是 search 的探索预算与验证成本的错配。search 若按“每轮必须提升”的贪心策略推进，会在平台期反复触发 profiler，而 profiler 采集本身有固定开销（需重复执行 kernel、串行化计数器采集），单次采集的墙钟时间往往数倍于 kernel 本身。一个粗略的预算式是：设单轮 coder 生成成本为 Cg、judge 验证成本为 Cv、profile 采集成本为 Cp，则一轮完整反馈的成本为 Cg+Cv+Cp，而只有当预期改进幅度 Δ 满足 Δ·价值 > 成本时，插入 profiler 才划算；在正确性尚未稳定的早期轮次，Cp 应被跳过，先让 judge 把 pass 率抬起来。具体例子：一个 reduction kernel 在首轮因越界写失败，此时立刻跑 NCU 得到的全是无效数据，正确做法是先由 judge 驱动两轮修复把正确性锁死，再让 profiler 介入分析 bank conflict。这也解释了为何失败轨迹在清洗后仍有价值——它们记录了“何时不该调用 profiler”这一决策边界，可作为 profile 解释类 SFT 样本的负例对照。
