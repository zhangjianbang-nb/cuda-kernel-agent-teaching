一 · 漏检率：把 checker 当成被测对象

在 kernel 生成流水线里，checker 通常被当作“地面真值”使用：它说对，样本就进正例池；它说错，样本就进负例池或触发修复轮。这个假设本身就是最大的风险来源。一个只覆盖少数形状、只比对最终张量、容差设得过松的 checker，会把“数值近似正确但边界越界”或“在特定 stride 下静默错位”的 kernel 判为通过。这类错误进入 RL 训练后不会以 loss 的形式暴露，而是以奖励曲线的虚假抬升暴露——策略学会了讨好 checker 而非讨好数学。

因此审计的第一步是把 checker 从裁判席拉到被告席，定义它的漏检率。给定一组已知错误的变异体集合 M（每个变异体都确实违反语义），以及一组已知正确的参考实现集合 R，checker C 的漏检率定义为：

$$\mathrm{FNR}(C)=\frac{|\{m\in M : C(m)=\text{pass}\}|}{|M|},\qquad \mathrm{FPR}(C)=\frac{|\{r\in R : C(r)=\text{fail}\}|}{|R|}$$

这两个量必须同时报告。只压低 FNR 会让容差收紧，进而抬高 FPR，把正确但使用不同累加顺序的 kernel 判错——而不同累加顺序恰恰是合法优化空间的主要来源。工程上可接受的做法是把 FPR 控制在很低水平（正确实现几乎不被误杀），再在此约束下最小化 FNR。代价是明确的：每提高一档检查强度（更多形状、更多 dtype、更细的中间量比对），单样本验证时延上升，进而压缩单位时间内可完成的 RL rollout 数量；如果 checker 需要跑参考实现做逐元素比对，显存占用也随 batch 形状线性增长。

具体机制上，一个可操作的审计口径是“分层漏检率”：按错误类型（索引越界、mask 遗漏、累加精度、同步缺失、边界 tile 处理）分别统计 FNR，而不是只报一个总数。因为总数会被容易检出的错误类型稀释——比如越界访问往往直接触发非法内存访问而被捕获，而累加精度偏差只有在长归约上才显现。若某一类的 FNR 显著高于其他类，说明 checker 的输入分布没有覆盖该类的触发条件，应优先扩充该类形状。

二 · 变异测试：用受控错误反推 checker 的敏感度

漏检率的分母 M 不能凭空构造，需要一套可复现的变异算子。变异测试的核心是把“正确 kernel 的源码”按语义保持与否分成两类变换：语义保持变换（如循环展开、累加顺序调整、共享内存换 bank 布局）应全部通过，用于测 FPR；语义破坏变换（如把 + 改成 -、把边界判断的 < 改成 <=、删掉一个 __syncthreads()、把 tile 索引的取模去掉）应全部失败，用于测 FNR。

伪代码思路如下：对每个参考 kernel，枚举变异算子集合，生成变异体，再用 checker 批量判定，最后按算子类别聚合通过率。

  • 对每个 r ∈ R，对每个变异算子 o ∈ O，生成 m = o(r)；
  • 若 o 属语义保持类，期望 C(m) = pass，否则记为 FPR 事件；
  • 若 o 属语义破坏类，期望 C(m) = fail，否则记为 FNR 事件；
  • 按算子类别与形状维度交叉聚合，输出敏感度矩阵。

敏感度矩阵的价值在于定位“checker 的盲区维度”。例如，若“删除 __syncthreads()”这一类变异体在单 block 小形状上大量漏检，而在大形状上被捕获，说明 checker 的输入分布偏向大形状，小形状下并发竞争尚未显现——这正好对应真实部署中 batch=1 的低时延场景。代价方面，变异测试是离线审计，不进入训练内循环，但它消耗的是编译时间：每个变异体都要单独编译，若算子集合有几十个、参考实现有上百个，编译队列会成为审计吞吐的瓶颈，需要用编译缓存与并行编译摊薄。

一个具体例子：对归约类 kernel 施加“把累加初值从 0 改为 1”的变异，若 checker 只在 float32 上以宽松相对容差比对，该变异体在输出量级远大于 1 时会被判通过——因为 1 的相对误差被淹没。这类漏检直接对应 RL 中“策略学会在数值上偷懒”的奖励 hacking 路径，必须在 checker 侧堵住，而不是靠奖励面板事后监控。

三 · Fuzz：让输入分布成为审计变量

变异测试审计的是 checker 对“错误实现”的敏感度，fuzz 审计的是 checker 对“输入形状与数值分布”的覆盖度。两者互补：前者固定输入、扰动实现；后者固定实现、扰动输入。对 kernel 而言，输入空间至少包含形状（各维长度、是否整除 tile）、stride 与布局（连续、转置、带 padding）、dtype（fp32/fp16/bf16，以及混合精度累加）、数值分布（全零、极大极小、含 NaN/Inf、长尾）。

fuzz 的机制不是随机撒点，而是按等价类生成：把形状空间划分为“整除 tile”“余数小于 tile 一半”“余数大于 tile 一半”等类，每类采样若干代表点，并保证每个代表点都同时喂给参考实现与候选 kernel。判定时除了最终张量比对，还应插入中间量探针——例如在分块归约的每个阶段导出部分和，比对阶段间的一致性。这会把“最终结果碰巧正确但中间路径错误”的情况暴露出来，代价是探针本身引入额外显存写入与同步，单次验证时延上升，因此探针应只在审计模式开启，训练内循环用轻量 checker。

fuzz 的产出应是一张覆盖率账本：哪些等价类被检查过、每类的样本数与最近一次通过率。这张账本直接决定漏检率估计的可信度——如果某个等价类从未被采样，那么该类的 FNR 是未知而非零。工程判断上，宁可报告“该类未覆盖”，也不要用总体通过率掩盖它。另一个代价是 token：若把 fuzz 发现的失败样例回灌进多轮修复流程，会显著拉长轨迹长度，因为形状边界错误往往需要多轮定位，这正是多轮信用分配要处理的问题，此处只需在数据侧标记“该样本的失败来自边界类”，供后续按轮次归因。

具体例子：一个 layernorm kernel 在 hidden size 非 2 的幂时使用了错误的 warp 归约步长，最终结果在 fp16 下因舍入恰好落在容差内。若 fuzz 的等价类只覆盖 2 的幂形状，该 bug 永远不被发现；一旦加入“非 2 的幂 + fp16 累加”类，checker 的 FNR 立刻在该类上暴露，修复轮的成功率也随之从平台期抬升——这正是课程与信用分配调整后曲线突破的一个可归因来源。

四 · 形式验证与合约验证：把“正确”写成可判定的命题

抽样检查永远只能给出概率性信心。要证明“正确”，需要把语义写成命题，再交给可判定的工具。对 kernel 而言，可落地的是合约验证：为每个 kernel 声明前置条件（输入形状、stride 约束、dtype 假设、对齐要求）与后置条件（输出与参考实现的数学关系、无越界写、无数据竞争），然后用符号执行或 SMT 求解在有限范围内检查合约是否被满足。

合约的形式化写法可直接嵌入源码注释，由工具链抽取为验证目标。例如对逐元素算子，后置条件可写成“对所有合法索引 i，输出[i] 与参考表达式在给定容差内相等”；对分块归约，后置条件需拆成两条：块内部分和与全局合并的正确性，以及同步点前后共享内存的可见性。后者是数据竞争检查，通常用 happens-before 关系建模，验证代价随线程数与共享内存规模增长，实践中只对固定 tile 配置做有界验证。

形式验证的代价是编译时间与人力：SMT 求解在含非线性算术（如指数、除法）的 kernel 上容易发散，需要人工切分断言、引入中间不变量。因此工程上采用分层策略——对高风险算子（归约、扫描、注意力掩码）做合约验证，对低风险逐元素算子保留抽样加变异测试。合约验证的另一个产出是“反例”：求解器给出的违例输入可直接作为 fuzz 的种子，形成闭环。

具体例子：一个 softmax kernel 的合约中声明“输出每行和为 1（在容差内）且无 NaN”。求解器可能给出一个全为 -inf 的输入行，此时正确实现应输出均匀分布而非 NaN；若候选 kernel 未处理该分支，合约验证直接给出反例，无需等待随机 fuzz 撞上。这类反例进入修复轮后，往往一轮即可修好，因为错误位置由反例精确定位——这对多轮信用分配意味着“该轮增益可归因于合约反例”，而不是模糊的“又试了一次”。

五 · 审计结论怎么进入奖励：硬门控的可信边界

审计的最终目的是给奖励函数一个可信的正确性门控。若门控本身漏检，RL 会把资源投入到讨好 checker 的方向。因此门控的可信度必须量化并写入训练管线：只有当 checker 在相关等价类上的 FNR 低于阈值、且变异测试敏感度矩阵无空白类别时，该 checker 的输出才可作为硬门控使用；否则应降级为软惩罚，并同时记录“门控不可信”标记，供奖励 hacking 监控面板聚合。

机制上，可把门控写成两级：第一级是快速抽样 checker，用于内循环筛选；第二级是审计级 checker（含变异体回归、fuzz 种子回放、合约反例集），按固定周期对通过第一级的样本做复核。复核发现的不一致样本进入“疑似漏检”队列，既用于更新 FNR 估计，也用于回灌修复流程。代价是复核队列带来的额外验证时延与显存占用，需要按吞吐预算设定复核比例；比例过高会拖慢 rollout，比例过低则 FNR 估计的方差过大。

一个工程判断是：不要追求把 FNR 压到零，而是让 FNR 的估计本身足够紧，使“门控通过”这一事件的置信区间可计算。因为绝对零漏检在含浮点容差与并发语义的场景下不可判定，追求它只会把 checker 推向过紧容差，反噬 FPR 与合法优化空间。真正该做的是把漏检率、变异敏感度、fuzz 覆盖率三张账本与训练曲线并列监控：当奖励上升但三张账本同时恶化时，抬升来自 checker 退化而非策略进步，此时应冻结奖励、先修审计。

具体到本卷的产出，审计结论直接决定“正确性作为硬门控还是软惩罚”这一关键决策的取值：在算子族迁移的课程阶段，新算子族的 checker 尚未积累变异体与 fuzz 覆盖，硬门控会把大量合法实现误杀，拖慢课程推进；此时用软惩罚加人工复核更稳，待该族审计账本补齐后再切回硬门控。这个切换点的选择，本质上是由漏检率估计的置信度而非训练步数决定的。

当“正确”成为奖励门控：审计 oracle 的漏检边界与代价

把正确性当作硬门控，奖励信号就退化为“通过/不通过”的二值函数，此时 check 的漏检率直接决定策略能走多远：漏检一次，一条错误 kernel 就拿到满额加速比奖励，RL 会把这条捷径放大成系统性 hacking。设 checker 对错误实现的漏检率为 ε、单次判定成本为 c_check、每轮 rollout 的候选数为 N，则每轮被错误放行的期望条数为 N·ε，而审计开销为 N·c_check。工程上真正要压的不是 ε 的均值，而是“高加速比且错误”这一子集的漏检率——因为奖励函数对加速比单调，策略会主动搜索 checker 的盲区。具体机制上，差分测试要覆盖的不只是随机输入，而是边界形状（非 2 的幂、单元素、极窄维度）、特殊值（NaN/Inf/denormal、全零、饱和）与别名/步长非连续的张量布局；只做均匀随机采样时，越界写和竞态往往落在采样分布的低概率区，漏检率居高不下。代价是显性的：每增加一组差分用例，判定时延与显存占用线性上升，若把 check 放进 rollout 内循环，吞吐会被判定而非生成主导。

变异测试是给 checker 本身做“反向 oracle”：向参考实现注入语义保持或语义破坏的变异体（换累加顺序、改边界条件、去掉同步、把 fp32 降成 tf32），统计 checker 的杀伤率。杀伤率低说明用例集对这类错误不敏感，需补针对性用例；杀伤率高但误杀率也高，则说明容差过紧，会把合法的浮点重排判成错误，造成假阴性奖励惩罚。fuzz 则把输入空间当作搜索问题，用覆盖率引导生成能触发新分支的形状与数值组合，其系统代价是编译期与运行期的双重膨胀——每个新形状可能触发一次重编译，编译时间进入判定链路。形式验证与合约验证走另一条路：对 tile 级 kernel 给出前置/后置条件（如“输出索引不越界”“共享内存读写无竞争”“累加结果与参考在给定误差界内”），用 SMT 或符号执行证明，或把合约编译成运行时断言。它能把漏检率压到接近零，但状态空间随线程数、共享内存布局与循环边界组合爆炸，可扩展性止步于小 tile、固定形状；对动态 shape 的生产 kernel，合约验证更多是抽样证明加运行时断言，代价是每次 launch 的断言开销与寄存器压力。

手段压制对象主要代价失效条件
差分测试数值与边界错误判定时延、显存采样分布避开盲区
变异测试checker 自身盲区变异体编译与运行变异体不代表真实错误族
fuzz形状/数值组合重编译时间覆盖率引导失真
合约/形式验证越界、竞态、误差界状态空间、断言开销动态 shape 不可证

把四者组合成审计流水线时，关键判断是“在哪一层拦截”：形式验证与合约断言放在候选进入奖励计算之前做硬门控，差分与 fuzz 放在离线回归里持续校准 ε，变异测试则定期给 checker 打分、驱动用例集更新。若把全部审计塞进 rollout 内循环，单条候选的判定成本可能超过其生成成本，训练吞吐被审计吞掉；反之只做轻量差分，则 ε 偏高，多轮修复的成功率会被虚假奖励污染——故事中曲线突破平台期依赖的正是信用分配能区分“真修复”与“蒙对”，而蒙对的样本恰恰来自漏检。可操作的判据是：当某类错误在变异测试中的杀伤率低于阈值，就禁止该类候选进入高奖励区间，用保守门控换取奖励可信度，代价是部分正确候选被误杀、有效样本率下降。
