一 · 漏检率：checker 的第一性指标

讨论“正确”之前，先把 oracle 从布尔量降格为随机变量。一个 checker 对某个 kernel 的判定只有四种结局：真通过、假通过（漏检）、真拒绝、假拒绝（误杀）。工程上真正致命的是假通过，因为它把错误固化进数据集、奖励信号和生产候选池，后续所有环节都在为它背书。因此本片段把漏检率定义为第一性指标，而不是笼统的“准确率”。

设被测 kernel 集合为 K，checker 为 C，对每个 kernel 采样输入分布 D。漏检率可写成条件概率：对“存在错误输出”的 kernel，checker 判通过的比例。更可操作的形式是按输入空间积分：

$$\mathrm{FNR}(C)=\mathbb{E}_{k\in K_{\text{bad}}}\left[\Pr_{x\sim D}\left(C(k,x)=\text{pass}\right)\right]$$

这个式子的关键在于它把漏检率拆成两层：一层是 kernel 层面的坏样本比例，一层是单次输入上的逃逸概率。单次逃逸概率随采样次数 n 指数衰减，若单次逃逸率为 p，重复 n 次的联合漏检率约为 pn（假设输入独立）。这直接给出成本权衡：把漏检率从 p 压到 pn 需要 n 倍 GPU 分钟数，而评测集群的排队时延随负载非线性上升。这就是“少重复 vs 高置信”在 oracle 层面的具体形态——不是拍脑袋定重复次数，而是先测出 p，再反解 n。

具体机制上，单次逃逸率 p 的主要来源是数值容差与形状覆盖。以归约类 kernel 为例，checker 若只比对 float32 绝对误差阈值，则当参考实现与候选实现的累加顺序不同、且输入量级跨三个数量级时，相对误差被绝对阈值吞掉，逃逸概率显著抬升。工程做法是把容差改成相对误差加尺度归一，并对每个输出元素记录最大相对偏差的分布，而不是只报一个通过/失败。代价是 checker 自身要多做一遍归约与统计，单任务评测时延上升，但相比盲目增加重复次数，这个开销通常更划算。

漏检率必须被测量而不是被假设。做法是构造一组“已知有错”的变异 kernel（下一节展开），用 checker 去跑，统计其判通过的比例，得到 p 的经验估计。没有这个估计，任何“我们跑了 5 次都过了”的说法都不构成正确性证据，只构成采样噪声。

二 · 变异测试：给 checker 造一批必错的样本

变异测试的对象不是 kernel，而是 checker 本身。思路是：对一批已知正确的参考 kernel 施加语义保持或语义破坏的变异算子，前者应通过、后者应被拒绝。语义破坏类变异包括：把 += 改成 =（丢失累加）、把边界判断的 < 改成 <=（越界一元素）、把共享内存同步去掉、把 __syncthreads() 移到错误分支、把索引的 stride 写错、把 float 换成 half 而不改累加精度。语义保持类变异包括：改变线程块大小、改变循环展开因子、等价代数重写。

变异测试的产出是一张“杀伤矩阵”：行是变异算子，列是 checker 配置（容差、重复次数、输入分布），单元格是检出率。这张矩阵直接暴露 checker 的结构性盲区。典型盲区是竞态类错误：去掉同步的变异在单次小规模输入下常常仍产生正确结果，因为调度恰好没暴露冲突；只有在大规模输入、多次重复、或开启竞争检测工具时才被捕获。这意味着漏检率对输入规模高度敏感，checker 的输入分布必须包含足够大的规模档位。

代价方面，变异测试本身要跑 M 个变异体 × n 次重复，是纯增量的评测开销，且它跑在评测集群上与正常评测争抢容量。工程判断是把变异测试做成低频的离线任务（例如 checker 配置变更时触发），而不是每次评测都跑；其 GPU 分钟数应计入评测集群的容量预算，而不是被当作“免费的正确性保险”。另一个代价是变异算子的维护：算子集合若长期不更新，杀伤矩阵会饱和，checker 看起来很强，实际只对历史错误类型有效。

具体例子：一个 softmax kernel 的 checker 若只比对最终概率向量，则“减去最大值”这一步被省略的变异在输入数值范围较小时几乎不产生可见误差，逃逸概率高；只有当输入包含较大幅值、指数溢出被触发时才被检出。这提示 checker 的输入分布要专门覆盖数值极端档位，而不是从均匀分布里随机采样。

三 · Fuzz：把输入分布当成一等公民

Fuzz 在这里不是找崩溃，而是找“checker 与 kernel 同时沉默”的输入。对 GPU kernel，fuzz 的维度比 CPU 多得多：形状（含非对齐、零维、极大维）、数据类型与混合精度、stride 与布局（转置、广播、切片）、数值分布（正态、均匀、含 inf/nan、跨数量级）、并发规模（grid 大小、占用率）。这些维度的组合空间巨大，穷举不可行，因此需要结构化采样而非随机撒点。

一个可操作的伪代码思路是分层采样加覆盖反馈：

  • 为每个维度定义边界档位（最小、非对齐、对齐、超大）与典型档位；
  • 按维度组合生成候选输入，优先覆盖尚未被任何测试触及的“档位对”；
  • 对每个候选输入同时跑参考实现与候选 kernel，记录差异向量；
  • 把产生差异的输入收缩（缩小形状、简化数值）后加入回归集。

覆盖反馈的意义在于把有限的 GPU 分钟数投向信息量最大的输入，而不是均匀撒点。收缩步骤降低回归集的存储与重跑成本，因为大形状输入的参考实现本身就很贵。

代价是 fuzz 的吞吐与评测吞吐直接冲突：每个 fuzz 输入都要跑两份实现（参考与候选），且参考实现往往是慢速的朴素版本，单输入成本高。若把 fuzz 塞进每轮评测，评测集群的排队时延会被显著拉长，这与本卷成本模型揭示的瓶颈一致——瓶颈在评测吞吐而非单卡算力。工程判断是把 fuzz 拆成两档：轻量档（固定小回归集，随每次评测跑）与深度档（离线、按周或按 checker 变更触发）。轻量档保证不回归，深度档负责发现新盲区。

具体例子：一个矩阵乘 kernel 的 fuzz 若只采样 2 的幂形状，则非对齐形状下的向量化加载边界处理永远不会被触及；而这类边界错误恰恰是漏检率最高的类别之一，因为它们在多数形状下不触发。把非对齐形状设为必测档位，是用极小的输入数量换取显著漏检率下降的典型手段。

四 · 形式验证与合约验证：把“正确”变成可证命题

采样式 oracle 的天花板是概率性的：无论重复多少次，都存在未被采到的输入。形式验证试图把这个天花板换成确定性命题，但代价是适用范围急剧收窄。对 GPU kernel，可行的形式化路径主要有三条：位精确等价性验证（针对整数/位运算 kernel）、基于 SMT 的边界与索引安全性验证（针对访存越界、竞态）、以及合约验证（把前置条件、后置条件写成断言，在运行时或符号执行下检查）。

合约验证的工程形态最实用：为 kernel 写一份规格，包含前置条件（形状、stride、对齐、数值范围）、后置条件（输出与参考的关系、误差上界）、以及不变量（共享内存使用量、同步点配对）。这份规格有两个用途：一是作为运行时断言插入调试构建，在 fuzz 输入上触发违约即报错；二是作为符号执行的输入，对小规模形状做穷举或约束求解。后者的代价是状态空间爆炸——线程数一多，符号执行基本不可行，因此只对小形状（例如单块、少量线程）做形式化，大形状仍靠采样。

位精确等价性验证在整数 kernel 上价值极高：它把“误差容差”这个模糊参数彻底移除，checker 退化为逐位比对，漏检率在定义上为零（在验证覆盖的输入域内）。代价是它只适用于没有浮点重排、没有未定义行为的 kernel；一旦涉及浮点归约顺序，位精确就不再是合理规格，必须回到误差上界的形式。

形式验证的成本不止算力，还有人力与编译时间：写规格、维护规格、以及符号执行工具的求解时间，都是非 GPU 开销。工程判断是把形式验证集中在“高价值且小规模”的子集上——索引安全性与同步正确性这类错误一旦漏检，后果是静默错误或崩溃，且采样极难覆盖；而数值精度类问题交给统计式 oracle 加误差分布监控更划算。

具体例子：一个带共享内存的转置 kernel，其索引映射的错误在方形形状下恰好对称而不可见，只在非方形、非对齐形状下暴露。对这类 kernel，用合约验证写出“每个输出元素恰好被写入一次”的不变量，并在小形状上符号执行，可以在不依赖大规模采样的前提下证明写入完备性；而大形状仍靠 fuzz 覆盖。

五 · 怎么证明“正确”：证据分层与成本配比

把上述手段组织成一套证据分层，而不是并列罗列。第一层是逐位或严格误差比对，覆盖小规模与整数域，给出确定性结论；第二层是统计式采样 oracle，覆盖大规模与浮点域，给出漏检率上界；第三层是变异测试，度量 checker 自身的杀伤力；第四层是合约与形式验证，覆盖索引安全与同步这类采样难以触及的结构性属性。四层不是替代关系，而是各自回答不同的问题：第一层回答“这个输入上对不对”，第二层回答“还有多少输入可能错”，第三层回答“checker 能不能发现错”，第四层回答“是否存在某类错误在原理上无法被采样发现”。

成本配比要按边际收益分配 GPU 分钟数。设总评测预算为 B，重复次数 n 带来的漏检率下降是 pn 的指数式，但当 p 已被压到很低时，继续加 n 的边际收益迅速衰减；此时把预算转向扩大输入分布的覆盖档位、或转向变异测试更新算子集合，收益更高。这个判断可以写成一个简单的分配准则：当 pn 已低于变异测试测得的 checker 结构性盲区所对应的漏检下限时，加重复次数不再有意义，因为瓶颈已不在采样次数而在输入分布。

具体例子：在一条评测流水线里，若把每个任务的重复次数从 3 提到 10，单任务 GPU 分钟数近似三倍，评测集群排队时延随之上升，而漏检率只从 p3 降到 p10；若此时变异测试显示 checker 对竞态类变异检出率接近零，那么这三倍预算买到的置信度提升远小于把预算投给竞争检测工具或合约断言。这就是“证明正确”的工程判断：不是追求单一指标极致，而是让每一份 GPU 分钟数落在当前最紧的瓶颈上。

最后落到一个可执行机制：把 checker 的漏检率估计、变异杀伤矩阵、fuzz 覆盖档位表三者一起版本化，与 checker 代码同仓管理。任何一次 checker 变更都必须重跑变异测试并更新杀伤矩阵，否则变更被视为未验证。这条规则把“正确”从一次性结论变成持续可审计的属性，也让评测集群的容量规划有了依据——变异测试与深度 fuzz 的 GPU 分钟数是可预算的固定开销，而不是随机膨胀的隐性成本。

审计预算本身要计入容量：漏检率、变异算子与形式化边界的三角权衡

把 checker 当作“免费的正确性 oracle”是容量规划里最贵的一处误判：审计不是零成本旁路，它要么占用评测集群的 GPU 分钟，要么占用编译/求解的 CPU 卡时，两者都在与 RL 训练、生产 profile 抢同一批配额。设 checker 对一批变异体的漏检率为 m、单次审计（含变异生成、差分执行、形式化求解尝试）的 GPU 分钟数为 ca、审计样本量为 n，则每个任务条目摊到的审计容量为 n·ca，而它换来的置信度上界是 mn（独立漏检假设下）。这个式子直接给出容量决策：当 m 已接近 1（checker 只做形状与 dtype 校验、不做数值容差），把 n 翻倍几乎不改变置信度，却线性吃掉评测吞吐——这正是“评测集群排队拖慢迭代”故事里最隐蔽的一股流量，因为它不出现在主评测队列的指标里，只体现在节点利用率与排队时长的残差上。

$$P(\text{漏检全部 } n \text{ 个变异体}) \approx m^{n},\qquad \text{审计容量开销} = n \cdot c_a$$

变异测试的边界在于变异算子与真实失效模式的错配：对 Triton/CUDA kernel 而言，高价值的变异是边界 tile（尾块、非对齐长度）、mask 语义取反、归约初值与累加顺序、`__syncthreads` 位置漂移，而不是把 `+` 改成 `-` 这类会被任何数值比对立刻抓住的语法级变异。若变异算子集合偏向后者，漏检率被系统性低估，checker 在真实尾块越界与竞态上仍然放行——这类错误在单卡小 shape 上不触发，却在生产 batch 与多 stream 并发下暴露，代价是端到端替换后回滚，回滚本身消耗的容量远高于审计预算。fuzz 的边界则是输入分布：随机 shape 若集中在 2 的幂与对齐长度，等于对尾块路径零覆盖；必须把非对齐长度、极小/极大归约维度、空 tensor 作为显式种子，否则 fuzz 的 GPU 分钟买到的只是“对齐路径的重复确认”。

形式验证与合约验证的代价是编译时间与可表达性，而非运行时：把 kernel 的前置/后置条件写成合约（对齐、越界、dtype、确定性归约），可在符号执行或 SMT 求解下证伪部分变异体，但求解时间随分支与循环展开急剧上升，一个带动态 tile 大小的 kernel 往往在超时预算内无法收敛，只能退化为“未证明”而非“已证伪”。工程判断是分层：语法与形状级用差分执行（毫秒级、GPU 分钟可忽略），数值语义用带容差的差分加边界种子 fuzz（秒级），只有被反复回滚的高风险 kernel 才投入合约与形式化（分钟到小时级 CPU 卡时），并把“未证明”显式计入漏检率上界而不是当作通过。
