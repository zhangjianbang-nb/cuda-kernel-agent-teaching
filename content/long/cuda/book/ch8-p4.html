一 · 漏检率：把 checker 当成被测对象

在 kernel 生成流水线里，checker 通常被当作“法官”，但工程上更合理的姿态是把它当作“另一个被测系统”。一个 checker 的失效模式不是二元的对错，而是漏检率（false negative rate）与误杀率（false positive rate）的组合：漏检让错误 kernel 进入训练数据资产，误杀让正确 kernel 被丢弃、污染偏好对。前者是数据污染的上游源头，后者直接压缩可用样本量。

定义上，给定一个 kernel 集合 K 与一组变异体 M（每个变异体植入一个已知缺陷），漏检率可写成：

$$\mathrm{FNR}=\frac{|\{m\in M:\ \mathrm{checker}(m)=\text{pass}\}|}{|M|},\qquad \mathrm{FPR}=\frac{|\{k\in K_{\text{correct}}:\ \mathrm{checker}(k)=\text{fail}\}|}{|K_{\text{correct}}|}$$

关键机制在于：checker 的判定往往依赖有限输入集与容差。以逐元素比较为例，checker 用固定随机种子生成 N 个输入张量，逐元素比较 allclose，容差 rtol/atol。漏检的主要来源是输入覆盖不足——某些缺陷只在特定形状（如非对齐的尾块、极小的 M 或极大的 K）或特定数值区间（如接近溢出、denormal）触发。工程代价是直接的：扩大输入集意味着每个候选 kernel 的执行时间线性增长，而候选 kernel 数量在 RL 采样中可达每步数十个，checker 时延会成为 rollout 吞吐的瓶颈；同时更严格的容差会把合法的浮点重排（如不同累加顺序）判为错误，抬高 FPR。

具体例子：一个 reduction kernel 在 N=1024 的 2 的幂形状上正确，但在 N=1000 时因未处理尾块而越界读写。若 checker 只采样 2 的幂形状，该缺陷漏检；而这类缺陷恰恰是 KernelBench 系基准中区分“能跑”与“正确”的典型分界。审计的第一步因此不是增加测试数量，而是让输入分布显式覆盖边界形状、非对齐 stride、空张量与单元素张量。

二 · 变异测试：用植入缺陷度量 oracle 的杀伤力

漏检率无法在真实缺陷上直接测量，因为真实缺陷的分布未知。变异测试提供了可控的替代：对参考实现施加语义保持或语义破坏的变换，生成一批“已知坏”的 kernel，然后看 checker 能否逐个抓住。语义破坏型变异体（mutant）包括：把 + 改成 -、去掉边界判断、把 __syncthreads() 删除、把 shared memory 的 bank 冲突消解逻辑去掉、把累加精度从 fp32 降到 fp16、把 grid 维度算错一位。

变异测试的核心指标是“杀伤率”（mutation score）：

$$\mathrm{MS}=\frac{|\{m\in M:\ \mathrm{checker}(m)=\text{fail}\}|}{|M|},\qquad \mathrm{FNR}=1-\mathrm{MS}$$

伪代码思路是：对每个变异体，先在 CPU 参考实现上确认它确实产生与参考不同的输出（否则该变异体是等价变异，应从分母剔除），再交给 checker。剔除等价变异体是变异测试最容易被忽略的工程细节——一个删掉 __syncthreads() 的变异体在单 warp、单 block 的输入下可能行为完全一致，把它计入分母会人为压低杀伤率，误导审计结论。

代价方面：变异测试是离线审计，不在 rollout 热路径上，因此其编译时间与执行时间不直接吃 token 预算，但它消耗工程迭代时间。一个 kernel 的变异体集合若有数十个，每个都要编译并跑完整输入集，单轮审计的墙钟时间可达小时级；这也是为什么变异测试适合按 kernel 家族（如 matmul、softmax、layernorm）周期性执行，而不是每个候选都跑。具体例子：对 softmax kernel 施加“去掉减最大值”的变异，checker 若只用小幅值输入则漏检，因为不减去最大值在数值稳定区间内输出几乎一致；只有注入大幅值输入（如 1e4 量级）才能暴露溢出。这条变异体因此成为检验 checker 输入分布是否覆盖数值极端的探针。

三 · Fuzz：把输入空间当成攻击面

变异测试检验的是“缺陷能否被抓”，fuzz 检验的是“输入能否触发缺陷”。两者互补：变异测试固定输入集、变化程序；fuzz 固定程序、变化输入。对 kernel 而言，fuzz 的输入空间是形状、stride、dtype、layout、对齐、别名关系与数值分布的组合，维度高且离散，随机均匀采样效率极低。

可行的机制是结构化 fuzz：以形状为例，从边界值集合中采样（0、1、2、3、7、8、15、16、17、31、32、33、非 2 的幂、接近 shared memory 容量上限的尺寸），并强制覆盖“尾块非空”“stride 非连续”“batch 维为 1”等语义类别，而不是在整数区间上均匀随机。伪代码思路：维护一个覆盖表，记录每个语义类别是否已被某输入命中；每轮 fuzz 优先采样未覆盖类别，命中后标记。这样把有限执行预算花在覆盖增量上。

代价是执行次数与显存：每个 fuzz 输入都要分配张量并跑参考实现与候选实现，大形状输入会推高显存峰值，迫使 fuzz 在较小 batch 下运行，从而牺牲了对大 batch 特有缺陷（如 grid 维度溢出、occupancy 相关竞态）的覆盖。具体例子：一个 matmul kernel 在 M=N=K 对齐时正确，但当 K 不是 tile 大小的整数倍时，边界 tile 的越界读会读到相邻行数据，输出出现微小偏差，被宽松容差放过。结构化 fuzz 若把“K 非 tile 倍数”列为必覆盖类别，就能稳定复现该缺陷；而均匀随机采样命中该组合的概率随维度增加迅速衰减。

需要强调的是，fuzz 发现的失败必须回流到变异体集合或固定回归用例中，否则同一缺陷会在下一轮数据清洗时再次漏过。这一步把 fuzz 从一次性活动变成数据资产的持续防线。

四 · 形式验证与合约验证：从采样到证明

采样型 oracle 的天花板是“未观测到的输入上仍可能错”。形式验证试图消除这一残余风险，但其在 GPU kernel 上的适用面窄且成本高。可行的路径不是对整个 kernel 做端到端证明，而是对可判定的子片段建立合约（contract）：前置条件约束输入域（如 0 < N ≤ 2^31、指针 16 字节对齐、无别名），后置条件约束输出关系（如输出等于参考实现的数学定义、无越界写、无数据竞争）。

机制上，合约验证分两层。第一层是静态断言与类型级约束：在 kernel 入口用 assert 或编译期 static_assert 固化对齐与尺寸假设，让违反前置条件的调用在调试构建中立即失败，而不是产生静默错误。第二层是符号执行或有界模型检验：把线程索引、共享内存偏移符号化，对固定小尺寸（如单 block、tile 级）展开循环，检查越界与竞态。后者的代价是状态空间随线程数与循环次数指数增长，因此只能覆盖 tile 级片段，无法覆盖全 grid 行为；编译与求解时间可达分钟级，远超采样型 checker 的毫秒级。

合约验证的真正价值在于把“隐式假设”变成“可检查的接口”。具体例子：一个 layernorm kernel 隐含假设 N 不超过 shared memory 容量，采样测试在小 N 下全部通过；合约验证把该假设写成前置条件后，checker 在 N 超限时直接判 fail 而非跑出错误结果。这把一类“测试通过但语义越界”的缺陷从漏检转为显式拒绝。工程判断是：形式验证应优先施加在跨 kernel 共享的合约上（对齐、别名、尺寸上界），而不是逐 kernel 做全证明，因为前者的复用率高、维护成本低。

五 · 审计结论如何进入数据资产

审计的产出不是一份报告，而是对数据资产的三个具体动作：标注、过滤、加权。第一步，把 checker 的漏检率与变异杀伤率作为元数据写入每条轨迹：一条“通过”的轨迹若来自低杀伤率的 checker 版本，其标签置信度应下调。第二步，过滤掉由已知漏检模式覆盖的样本——例如所有仅在 2 的幂形状上验证过的 kernel 轨迹，在进入 SFT 前需补跑边界形状，未通过者转为负例而非丢弃。第三步，在偏好对构造中，把“快 vs 慢”与“对 vs 错”分开加权：由形式合约拒绝的样本作为高置信负例，由采样 checker 判错的样本作为低置信负例，避免把 checker 误杀的正确 kernel 当作“错”的对照。

这里的代价是 token 与清洗吞吐：补跑边界形状意味着每条候选轨迹的执行次数增加，清洗流水线的墙钟时间上升；而把失败轨迹保留为负例会扩大数据集规模，推高 SFT 的 token 消耗。关键决策在于是否保留失败轨迹——若 checker 漏检率高，保留失败轨迹会把噪声引入负例集，此时应先提升 checker 杀伤率再扩数据，而不是靠数据量掩盖 oracle 缺陷。

具体例子：团队发现 RL 冷启动不稳，回溯后发现部分“成功”轨迹实际来自未覆盖尾块的 checker 版本，这些轨迹在 SFT 基座中教会模型忽略边界判断。修复动作不是增加样本，而是先用变异测试把 checker 的杀伤率提到可接受水平，再重跑清洗，把此前漏检的轨迹转为负例。这一步把 oracle 审计与数据版本对齐绑定：checker 版本必须与数据版本一同记录，否则同一批轨迹在不同 checker 下的标签不可比。数据资产的可复用性正建立在“标签由哪个 oracle 版本产生”可追溯之上，而不是建立在样本数量上。

Oracle 审计的失效边界：漏检率、变异与合约验证的代价账

把“正确”定义成一个 checker 函数，是这条数据管线里最容易被低估的决策。checker 的漏检率不是抽象指标，它直接决定负例的质量：一个把错误 kernel 判成正确的 checker，会让失败轨迹被清洗进成功集，污染偏好对里的“对 vs 错”标签，进而让 SFT 基座学到错误的收敛方向。工程上可操作的做法是给 checker 本身建立审计闭环——用变异测试度量漏检率。具体机制是：对每个参考实现注入受控变异（索引偏移、边界条件反转、累加顺序改变、dtype 截断、同步缺失），得到一批“必然错误”的 kernel，跑 checker，统计被判为通过的比例，即漏检率 $$ \text{miss} = \frac{|\{m \in M : \text{checker}(m) = \text{pass}\}|}{|M|} $$ 其中 M 是变异体集合。变异体数量与覆盖维度成正比，每增加一个变异维度就多一次编译与执行，代价是编译时间与 GPU 时延的线性增长；在冷启动数据规模上，这意味着审计本身可能比被审计的 kernel 更贵。

漏检率的失效条件很具体：checker 若只做单点数值比对，变异体里的“累加顺序改变”在浮点容差内会被放过；若只做固定 shape 的比对，索引偏移变异在边界外不触发。因此变异测试必须与 fuzz 联合——随机化 shape、stride、dtype、对齐与并发规模，让 checker 在分布边缘暴露。fuzz 的代价是显存与调度：每个随机实例都要分配输入输出缓冲，批量并发时显存峰值随并发数上升，而 shape 随机化会让 kernel 的编译缓存命中率下降，编译时间成为主导开销。一个可用的折中是分层 fuzz：小 shape 高频跑以覆盖逻辑分支，大 shape 低频跑以覆盖带宽与同步路径，把编译时间压在可接受范围内。这里的关键判断是：fuzz 的随机种子与 shape 分布必须版本化，否则同一份数据资产在不同时间重跑会得到不同的漏检率估计，评测集与训练集的隔离也就失去意义。

形式验证与合约验证提供的是另一类保证，但代价结构完全不同。合约验证的思路是把 kernel 的前后条件写成可判定的断言（输入范围、输出不变式、内存不越界、同步点前后的一致性），在编译期或运行时插入检查。它的优势是覆盖所有输入而非采样，劣势是状态空间爆炸：一个带共享内存与多级同步的 kernel，其合约的可判定性依赖对循环不变式的抽象，抽象过粗则漏检，过细则验证时间不可控。工程上常见的做法是把合约验证限定在“结构正确性”层面——越界、竞态、dtype 一致性——而把数值正确性留给变异测试与 fuzz。这样做的代价是验证工具链的编译时间与人工编写不变式的 token 成本，收益是把最危险的一类错误（静默的内存越界导致结果随机）从采样漏检变成确定性排除。

回到数据资产本身：审计结论必须落成可执行的清洗规则，而不是一份报告。具体机制是给每条轨迹打上 checker 版本号与审计状态，只有通过变异测试阈值且 fuzz 未发现反例的 checker 才有资格标注“对/错”；未通过审计的 checker 产出的标签进入隔离区，不参与偏好对构造。这样做的系统代价是数据吞吐下降——每条轨迹多一次审计执行与一次版本比对，清洗管线的时延上升，但换来的是负例可信：失败轨迹作为负例进入 SFT 或 RL 上下文时，其“错”的判定有可追溯的依据。冷启动不稳的根因往往不是数据量不足，而是标签噪声让下限漂移；把 checker 审计做成数据版本的一部分，才让 SFT 基座成为可复用的底座，而不是一次性的补丁。
