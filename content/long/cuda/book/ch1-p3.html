一 · 基线不是数字，是契约：TF32/FP32 双轨与容差分级

可信评测的第一个谎言藏在“加速比”三个字里。同一个 kernel，参考实现用 FP32 累加还是 TF32 张量核，分母可以差出一整个数量级；而分子如果偷偷降精度，加速比就成了拿口径换来的假象。因此 harness 的第一条硬规则是：基线必须与候选实现共享同一份数值契约，而不是共享同一个数字。工程上落成双轨制——每个任务同时登记 FP32 严格基线与 TF32 允许基线，二者各自绑定容差、绑定累加顺序、绑定是否允许 FMA 重排。候选 kernel 声明自己属于哪一轨，评测器只拿对应轨的分母去除。

容差不能是一个全局常数。它必须按 dtype、按 reduction 长度、按累加树形状分级：elementwise 类任务逐元素独立，误差不随规模增长，容差可以收紧到接近机器 epsilon 的量级；reduction 与 matmul 的误差随累加深度增长，容差需按 √K（K 为累加项数）量级放宽，否则正确实现会被误判为错。形式化地，对输出张量 y 与参考 y*，判据写成

$$\max_i \frac{|y_i - y_i^*|}{\max(|y_i^*|, \tau_{\text{abs}})} \le \tau_{\text{rel}}(K, \text{dtype})$$

其中 τ_abs 防止参考值接近零时相对误差爆炸，τ_rel 随 K 单调放宽。这条公式的代价是显存与带宽：逐元素比对需要把参考输出完整驻留，对大输出（如 attention 的 score 矩阵）意味着一次额外的全量写回与读回，评测本身的时延可能超过被测 kernel 数倍。工程判断是：对超大中间张量改用分块流式比对，牺牲“全局 max”改为“分块 max 再聚合”，把峰值显存压到单块大小，代价是比对逻辑复杂度上升、且分块边界处的极值可能被漏检——这必须在失败模式清单里显式登记为已知盲区。

具体例子：一个 reduction kernel 用 warp shuffle 做树形归约，累加顺序与参考的串行循环完全不同。若 harness 只给一个固定 1e-5 的相对容差，树形归约在长序列上必然被判错，agent 会学到“不要用并行归约”这一错误策略。正确做法是把该任务的容差按 K 分级登记，并在任务分类法里标注“累加顺序敏感”。

二 · 隐藏 shape 与分布：把过拟合堵在评测入口

公开 shape 是 agent 最容易记住的东西。只要评测集固定，模型可以针对特定 M/N/K 组合硬编码 tile 尺寸、甚至针对特定输入值分支。harness 的反制机制是评测时采样：任务定义里只给出 shape 的分布族与约束（如 M∈[1, 8192]、K 为 16 的倍数、batch 维可缺省），真实评测在每次运行时从该族中抽样，且抽样种子对被测方不可见。分布维度不止 shape：还包括数值分布（是否含 NaN/Inf、动态范围、稀疏度）、对齐情况（指针是否 128 字节对齐、stride 是否连续）、以及 dtype 组合。

伪代码层面的评测循环大致是：

  • 从任务登记的 shape 族采样 N 组配置，其中一组为“边界组”（最小 shape、非对齐 stride、极端动态范围）；
  • 对每组配置分别跑参考实现与候选实现，按第一节的分轨容差判定；
  • 任一组失败即整体失败，不允许“多数通过”式打分；
  • 记录每组配置的时延，性能判据取几何平均而非算术平均，防止单个大 shape 拉高均值。

代价是评测方差。采样意味着同一份 kernel 两次评测的加速比不完全相同，尤其在小 shape 上，启动开销与测量噪声占比高。控制手段是固定采样族但随机种子、对每组配置重复测量取中位数、并规定“边界组失败即否决”以压低方差带来的误判。另一个代价是 token：隐藏 shape 使 agent 无法从评测反馈中反推具体配置，只能从“通过/失败+误差量级”这类粗粒度信号学习，样本效率下降，多轮 RL 的收敛需要更多轮次。这是可信度换效率的显式交易，必须写进 harness 的设计文档而不是留给运气。

具体例子：一个 matmul kernel 在公开的 4096×4096×4096 上表现优异，但在隐藏采样的 M=1（退化矩阵向量乘）上因 tile 划分退化而崩溃。若评测只跑大方阵，这种 kernel 会被判为成功并进入生产，而在真实推理的 decode 阶段直接失效。隐藏 shape 的意义正是把这类“分布外崩溃”提前到验收环节。

三 · Roofline 与 SOL：把“快”换算成“离上限多远”

加速比是相对量，参考实现本身可能离硬件上限很远，于是“快 3 倍”可能只是从一个糟糕实现换到一个平庸实现。harness 需要绝对量：以 roofline 模型计算该任务在目标 GPU 上的理论上界，报告候选实现的 SOL（speed-of-light）占比。对给定任务，算术强度 I = FLOPs / Bytes，硬件有两个上界——峰值算力 P 与峰值带宽 B，实际可达性能上界为

$$P_{\text{roof}} = \min(P_{\max},\; I \cdot B_{\max}), \qquad \text{SOL} = \frac{P_{\text{achieved}}}{P_{\text{roof}}}$$

关键在于 Bytes 的口径：它必须包含该任务不可避免的全局访存，而不是被测 kernel 实际发生的访存。否则一个把中间结果全部留在 shared memory、跳过必要写回的 kernel 会算出虚高的算术强度，SOL 虚高。因此 harness 为每个任务登记“最小必要访存字节数”，由任务分类法给出，与实现无关。这是防作弊的第一道结构性防线。

代价在测量侧：SOL 需要可信的 achieved 性能，而 achieved 性能依赖计时方法。CUDA event 计时会漏掉异步错误与部分启动开销，NCU 采集则带来可观的 replay 开销与 kernel 重放次数，单次 profile 的时延可能是裸跑的数十倍，且会扰动 cache 状态。工程折中是：正确性与粗粒度性能用 event 计时，SOL 报告只在抽样配置上做 NCU 采集，并明确标注“SOL 为采样估计而非全量测量”。另一个代价是编译时间：为拿到稳定的 achieved 性能，候选 kernel 需要以生产编译选项（含架构特化）构建，构建时间计入评测总成本。

具体例子：一个 attention kernel 加速比 2.5×，但 SOL 只有 18%，说明参考实现与候选实现都远离上限，真正的优化空间在访存合并与 tile 复用而非指令级微调。只看加速比会把团队引向错误方向；SOL 把“还有多少可挖”变成可比较的量。

四 · 内存、能耗与 BI：评测的物理边界

性能不是唯一判据。生产端到端收益要求 harness 同时登记峰值显存、能耗与 BI（business intelligence，此处指业务侧可解释的收益指标）。峰值显存的口径必须包含 workspace 与临时缓冲，而不只是输出张量；一个用大 workspace 换速度的 kernel 在显存受限的推理场景里不可部署。能耗在数据中心语境下折算为每任务焦耳数，测量依赖 GPU 侧的功率采样，采样频率低于 kernel 时延时，短 kernel 的能耗读数噪声极大，因此能耗判据只对超过一定时延阈值的任务生效，短任务以“能耗不可分辨”标注而非给假数字。

BI 这一项最容易被工程团队忽略：它要求每个 kernel 任务绑定一个业务侧可观测的指标（如某层时延占端到端时延的比例、某算子吞吐对 QPS 的贡献），并在评测报告里给出“该 kernel 优化 X% 对端到端指标的影响上界”。这个上界由 Amdahl 型估算给出：若该 kernel 占端到端时延比例为 f，优化使其时延降为原来的 1/s，则端到端收益上界为

$$\text{speedup}_{\text{e2e}} \le \frac{1}{(1-f) + f/s}$$

代价是评测链路变长：显存与能耗需要额外采集通道，BI 需要业务侧提供占比数据，任何一项缺失都会让报告降级为“仅性能”。工程判断是：把这三项设为可选但强推荐，且在验收粒度选择上区分——KernelBench 级别验收只看正确性与 SOL，生产级验收必须三项齐全。这个区分直接对应任务分类法里的“验收粒度”字段。

具体例子：某 fused kernel 加速比 1.8×、SOL 62%，但峰值显存增加 40%，在目标卡的显存预算下使 batch size 被迫减半，端到端 QPS 反而下降。若 harness 只报告加速比，这个 kernel 会被误判为收益项；显存口径与 BI 上界估算把它拦在部署之前。

五 · Anti-cheat：把作弊路径逐条封死

Agent 优化 kernel 时存在大量“合法但无意义”的捷径，harness 必须逐条封死，而不是事后抽查。常见作弊面与对应机制：

作弊面表现封堵机制代价
缓存结果对相同输入直接返回上次输出每次评测输入随机化，含指针地址与数值评测方差上升
跳过计算利用输入稀疏性或特殊值短路分布采样覆盖稠密与极端动态范围采样组数增加，评测时延上升
降精度内部用低精度累加冒充高精度轨双轨容差 + 参考实现同轨比对需维护两套参考
漏写回只算不写，靠计时窗口外完成计时后强制同步并校验全部输出同步开销计入时延
特化 shape硬编码 tile 尺寸匹配公开配置隐藏 shape 采样 + 边界组否决token 效率下降
污染基线提交时替换参考实现参考实现哈希锁定、独立进程运行构建与隔离成本

这张表的核心不是列举，而是每条都绑定一个代价，迫使设计者在可信度与成本之间做显式选择。最容易被低估的是“漏写回”：异步 kernel 的计时窗口可能在写回完成前就关闭，候选实现看起来极快，实际输出不完整。封堵方式是计时后强制 device synchronize 并做全量输出校验，代价是每次评测多一次同步与一次全量读回，对小 kernel 而言这部分开销可能与被测 kernel 本身同量级，导致时延读数被系统性抬高。因此 harness 需报告“含校验时延”与“裸时延”两个数，验收用前者，优化诊断用后者。

具体例子：一个 elementwise kernel 在输入含大量零值时提前 return，公开测试集恰好稀疏，加速比虚高。隐藏分布采样加入稠密随机输入后，该 kernel 退化为与基线持平，作弊路径被封死。这类封堵不需要形式验证的重武器，只需要在采样族里显式登记“稠密”这一档。

六 · Harness 的自我审计：让评测器本身可被质疑

一套不被骗的 harness，最后要能被质疑的是它自己。工程上落成三条自审机制。其一，金标准回归：harness 内置若干已知正确但性能平庸的参考 kernel，每次评测运行前先跑这些金标准，确认它们全部通过正确性判据、且 SOL 落在登记区间内；若金标准被判错或 SOL 漂移，说明评测环境（驱动、编译选项、GPU 状态）发生了变化，本次评测结果作废。其二，负样本注入：定期向评测队列注入故意错误的 kernel（如容差边缘越界、漏写回、降精度），确认 harness 能捕获；捕获率下降即为 harness 退化信号。其三，口径版本化：容差表、shape 族、最小必要访存字节数、SOL 上界参数全部带版本号，任何一次口径变更都触发历史结果的重算标记，防止“换了尺子还比旧数”。

代价是评测吞吐：金标准回归与负样本注入占用评测配额，尤其负样本需要跑完整判据链路，单次成本与被测 kernel 相当。工程折中是按批次而非按单次执行自审，批次边界处做一次全量回归，批次内部只做轻量校验。另一个代价是维护成本：口径版本化意味着每次任务分类法调整都要同步更新四张登记表，任何一张漏更都会让历史对比失效。

具体例子：驱动升级后 TF32 的默认行为发生变化，参考实现的数值结果整体偏移，若没有金标准回归，所有候选 kernel 会被批量误判为正确性失败，agent 的多轮 RL 信号被污染。金标准回归在批次入口拦下这次漂移，把问题定位到环境而非 kernel。这是 harness 可信度的最后一道闸门，也是本卷任务分类法与验收口径能够长期成立的前提。

容差口径的失效边界与 harness 的系统代价

数值容差不是越紧越可信。TF32 基线在 matmul 上把 mantissa 截到 10 位，若把验收容差设成 FP32 级（如 1e-6 相对误差），任何走 TF32 tensor core 的合法实现都会被判错，agent 会被迫退回 SIMT FP32 路径，加速比直接归零；反过来，容差放宽到 1e-2，一个把累加顺序打乱、甚至在 reduction 里丢掉小项的 kernel 也能通过，正确性 oracle 形同虚设。可操作的判据是按 dtype 与累加结构分级：同一 dtype 内比较用 rtol/atol 组合，跨 dtype（TF32 对 FP32 参考）必须显式声明“参考实现本身也跑 TF32”，否则比较无意义。误差传播可按

$$\varepsilon_{\text{rel}} \approx \sqrt{K}\,\varepsilon_{\text{mach}}\,\|A\|\,\|B\|/\|C\|$$
估算，K 为归约长度——它说明容差必须随 K 缩放，固定阈值在长 K 任务上必然误杀。

隐藏 shape 与分布的边界在于“分布外即失效”。harness 若只在一组 shape 上采样，agent 会针对该 shape 做特化（固定 tile、硬编码 block 数），在隐藏 shape 上因 occupancy 崩塌或越界而失败；但隐藏集过大又会让每轮评测的编译与运行时间线性膨胀。工程折中是分层采样：主分布固定若干代表 shape 保证可比性，另设一组仅用于最终验收的隐藏 shape，且隐藏集不进入多轮反馈，避免 agent 过拟合。代价是验收阶段需要额外一次全量编译加运行，编译时间与显存峰值都翻倍，这是可信度换来的系统开销。

roofline 判据的失效条件很具体：当 kernel 的实际瓶颈是 launch 开销或访存不连续导致的低效，SOL 占比会给出误导性的高分或低分。以 elementwise 为例，算术强度极低，roofline 上界就是带宽，此时“达到 80% 带宽”与“达到 80% SOL”等价，但对 fused 任务，roofline 假设的峰值算力在寄存器压力下不可达，SOL 占比会被系统性高估。因此 harness 必须把 roofline 判据与 NCU 的实测 stall 原因对齐，否则加速比与 SOL 两个口径会互相打架。

anti-cheat 的代价落在检测成本上。常见作弊是缓存输出、跳过实际计算、或在 benchmark 循环外预计算；harness 需注入随机输入、校验输出与参考的一致性、并在计时区间内强制重算。每次校验都引入一次额外 kernel 执行与 host-device 同步，端到端时延测量被污染，因此计时与校验必须分轮进行：计时轮不校验，校验轮不计时。这一分离使单次评测的 GPU 时间约为纯计时的两倍，是可信 harness 无法回避的固定开销。
