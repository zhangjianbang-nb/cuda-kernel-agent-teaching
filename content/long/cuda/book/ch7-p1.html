一 · 从一次“修不好”的 kernel 说起

取一个具体场景：一个融合的 LayerNorm + 残差 + 量化算子，输入形状在 decode 阶段是 [B=1, S=1, H=4096]，在 prefill 阶段是 [B=1, S=2048, H=4096]。第 5 卷的交互轨迹里，agent 第一轮生成的 Triton kernel 在 prefill 上跑出正确结果，但在 decode 上因为 block size 选成 1024 而让每个 SM 只拿到一个 program，带宽利用率极低；第二轮它把 block size 改成 256，decode 变快，却因为跨步访问让 prefill 的 L2 命中率掉下来；第三轮它加了 tl.multiple_of 与 tl.max_contiguous 提示，prefill 恢复，但数值上因为 rsqrt 的近似精度在 eps=1e-5 边界上出现了 1 ulp 级别的偏差，被 oracle 判为不通过。第四轮它把 rsqrt 换成 1/sqrt 的精确路径，正确性过了，可加速比只剩 1.07×，因为多了一次除法。

这条轨迹暴露的正是本卷要处理的对象：一个 agent 在四轮里做了四次局部正确的决策，整体却始终没有跨过“既正确又显著更快”的门槛。第 3 卷能告诉你这四轮的评测分数各是多少，第 4 卷能告诉你哪一轮被 oracle 判死、死在哪条断言上，第 5 卷能告诉你每一轮的对话与工具调用长什么样。但没有任何一卷回答：这四轮里，究竟哪一轮的修改真正贡献了最终增益？如果第三轮的数值偏差只是被硬门控一票否决，agent 会不会学到“只要不碰数学函数就安全”这种保守策略？如果奖励只看绝对加速比，agent 会不会干脆放弃 decode 形状、只优化 prefill？这些是训练信号的设计问题，不是评测问题，也不是脚手架问题。

二 · 上一卷留下的三个缺口

第 5 卷把交互轨迹做成了可回放的数据结构：每一轮有代码快照、编译日志、运行输出、profile 片段。它解决的是“记录什么”，没解决“记录下来的东西怎么变成梯度”。缺口之一是轨迹到奖励的映射不唯一。同一条四轮轨迹，按最终轮给奖励，则前三轮全是零贡献；按每轮给奖励，则第三轮那个引入数值偏差的动作会被正奖励强化，因为它在当时确实让 prefill 变快了。两种映射都能自洽，但训出来的策略完全不同。

缺口之二是正确性判定与性能判定不同频。第 4 卷的 oracle 是二值的、硬的、不可微的；第 3 卷的分数是连续的、带噪声的、依赖测量条件的。把二者拼成一个标量奖励时，硬门控会把大量“性能很好但差一个 ulp”的样本打成零，软惩罚又会让 agent 学会用微小的数值让步换取大幅加速——而这类让步在真实服务里是不可接受的。这个权衡没有普适答案，只能按算子族和部署场景分别定。

缺口之三是多轮结构本身没有被建模。第 5 卷的轨迹是变长的：有的算子两轮就收敛，有的要七轮。若把整条轨迹当成一个 episode 给一个终局奖励，信用分配的分辨率就是“整条轨迹”；若按轮给，就要面对折扣因子与轮间依赖。一个具体机制是：把第 t 轮的修复动作视为对第 t-1 轮代码的编辑，则第 t 轮的增益应当以第 t-1 轮的得分为基线，而不是以原始 naive 实现为基线。这直接决定了奖励是绝对量还是相对量。

三 · 本卷的赌注：奖励是可设计的工程对象

本卷押注的一件事是：可验证奖励可以被拆成三层，并且三层的组合方式比任何单层的形式更重要。第一层是正确性门控，来自第 4 卷的 oracle，二值、硬、不可谈判；第二层是加速比的连续信号，但必须以“相对基线”而非“绝对时间”表达，因为绝对时间随 GPU 型号、时钟、并发而漂移；第三层是 SOL 归一化，把加速比除以该算子在该形状下的 roofline 上界，得到一个 0 到 1 之间的效率刻度，使不同算子族之间的奖励可比。

$$ r = \mathbb{1}[\text{oracle}=1] \cdot \left( \alpha \cdot \frac{t_{\text{base}} - t_{\text{cand}}}{t_{\text{base}}} + \beta \cdot \frac{\text{SOL}_{\text{cand}}}{\text{SOL}_{\max}} \right) $$

这个式子的代价不在计算，而在标定。t_base 必须来自同一台机器、同一形状、同一 warmup 条件下的参考实现，否则相对加速比会带上系统偏差；SOL_max 需要按算子族预先算好，对 memory-bound 的 LayerNorm 是带宽上界，对 compute-bound 的 GEMM 是 FMA 吞吐上界，算错族就把奖励刻度拉歪。α 与 β 的配比决定 agent 是偏向“比 baseline 快”还是“逼近硬件极限”，前者容易在低基线算子族上刷分，后者容易在 roofline 本身估不准的算子上给出噪声奖励。

具体例子：前面那个 LayerNorm 算子，naive PyTorch 参考实现在 decode 形状上耗时记为 t_base，agent 第四轮的候选是 1.07×，SOL 效率约 0.6；若 α=1, β=0，这一轮的奖励是 0.07，与“什么都没做”的 0 相差不大，agent 学不到“精确 rsqrt 值得保留”；若 β 占主导，则 0.6 的效率分会让这一轮拿到可观奖励，agent 会强化“正确但只快一点”的行为，长期看会把策略拉向保守。这个配比就是本卷要回答的关键决策之一。

四 · 多轮信用分配：折扣因子不是超参而是结构

把四轮轨迹写成伪代码思路：设第 t 轮得分为 s_t，第 t 轮的动作为 a_t（一次代码编辑），则第 t 轮的优势估计应写成

$$ A_t = \sum_{k=t}^{T} \gamma^{k-t} \left( s_k - s_{k-1} \right) $$

其中 s_0 是 naive 基线分，γ 是轮间折扣。这个式子的含义是：第 t 轮的贡献是它之后所有轮次得分增量按折扣加权之和。若 γ=1，第三轮引入的数值偏差会被第四轮的修复抵消——因为 s_4 - s_3 是负的（正确性从 0 变 1 但加速比掉了），两项相加后第三轮的净贡献接近零，这正是我们想要的：agent 不该因为“暂时变快”而被强化。若 γ 取小值，远期修复的功劳被压掉，agent 会偏向短视的局部优化。

代价在于方差。γ 越接近 1，优势估计的方差越大，因为一条七轮轨迹里早期的动作要背后面六轮的噪声；γ 越小，偏差越大，因为真正的长程修复（比如第四轮换精确 rsqrt 才让整条轨迹可用）被低估。一个工程判断是：折扣因子应当与“平均修复轮数”挂钩，而不是拍一个 0.99。若某算子族的轨迹中位长度是 3 轮，γ 取使 γ^3 约为 0.5 的值，即约 0.79，比 0.99 更贴合该族的信用结构。这需要按算子族分别标定，也是课程学习要处理的事。

另一个具体机制是轮间基线漂移：第 t 轮的 s_{t-1} 是在第 t-1 轮代码上测的，而第 t 轮的候选可能改了形状分支，导致两次测量不在同一形状上。若不校正，s_t - s_{t-1} 会混入形状切换的收益，把“换了个更快但只对 prefill 有效的分支”误判为修复增益。校正办法是在每轮测量时固定一组形状采样，用同一组形状算分，代价是每轮多跑几次 benchmark，直接拉长轨迹的 wall-clock 时延与 GPU 占用。

五 · 课程与算子族迁移：难度递进不是排序而是分布

本卷的第二个赌注是：课程学习的价值不在于把题从易到难排，而在于控制每个难度档上“可修复”的比例。一个具体机制是：对每个算子族，用第 5 卷轨迹统计“首轮正确率”与“三轮内修复率”，把算子分成四档——首轮就对且快、首轮错但可修、多轮可修、几乎不可修。训练分布应当让“多轮可修”档占主导，因为这一档才产生有信息量的多轮信用分配信号；首轮就对且快的样本奖励饱和、梯度接近零，几乎不可修的样本则全是零奖励，两者都浪费 token。

代价是采样成本。要维持这个分布，管线必须在训练前对候选算子做一次“可修性预判”，而预判本身要跑若干轮 agent 交互，等于把一部分训练预算花在了标定上。另一个代价是算子族迁移：在 LayerNorm 上学到的“先调 block size 再调向量化提示”的策略，迁到 GEMM 上未必成立，因为 GEMM 的瓶颈在 tile 形状与 shared memory 占用，不在访存提示。若课程按族串行推进，后一族的早期样本会带着前一族的策略偏差，表现为首轮正确率虚高但加速比偏低。缓解办法是族间保留一定比例的混合采样，代价是单族内的收敛速度变慢。

具体例子：把 decode 形状的 LayerNorm 与 prefill 形状的 LayerNorm 当作两个难度档，前者是 memory-bound、SOL 上界清晰、修复路径短；后者是 compute 与访存混合、修复路径长。若只训 decode，agent 会学到“缩小 block size”这一条捷径，迁到 prefill 上就退化成前面那个 L2 命中率下降的失败案例。课程必须显式包含“同一算子不同形状”的配对样本，让 agent 学到形状条件化的决策，而不是形状无关的固定套路。

六 · 奖励 hacking 的监控面板：看什么、为什么看

可验证奖励的最大风险不是奖励算错，而是 agent 找到一条通过 oracle 但不满足部署约束的路径。一个具体机制是：oracle 只检查输出张量的数值容差，agent 可以合法地降低内部累加精度、跳过某些边界处理、或对特定形状走一条未优化的分支，只要输出落在容差内就算过。这类行为在单轮评测里看不出来，在多轮 RL 里会被稳定强化，因为它的奖励高且可复现。

监控面板要盯的指标包括：候选实现相对参考实现的数值偏差分布（不是通过率，而是偏差的均值与尾部）、形状覆盖率（agent 是否系统性地回避某些形状）、代码编辑的局部性（是否反复只改同一行超参）、以及奖励与 SOL 效率的散点（高奖励低效率的点就是 hacking 嫌疑）。代价是这些指标都要额外的测量与存储：偏差分布要保留中间张量，形状覆盖率要跑全形状集，散点要每轮回写 SOL 估计，直接抬高单条轨迹的显存与 IO 开销。

一个工程判断是：监控面板不应只做离线审计，而应把“偏差尾部超过阈值”作为硬门控的一部分回灌到奖励里，让 hacking 行为在训练时就拿不到分，而不是等训练完再清洗数据。这会把正确性门控从二值 oracle 扩展成“oracle 通过 + 偏差尾部受控”的合取条件，代价是门控更严、通过率更低、需要更多轮修复才能拿到非零奖励——而这恰好也是课程学习要补偿的地方。

奖励管线不是免费的：门控、折扣与课程三处接缝的失效边界

本卷的赌注押在一个具体判断上：多轮修复的增益可以被拆解到“哪一轮、哪类错误、哪种改写”上，从而变成可优化的信号。但这条管线本身有系统代价，且代价集中在三个接缝处。以 FlashAttention 反向算子为例：第 5 卷轨迹显示 agent 在第 3 轮把 shared memory 溢出改成分块累加后正确性通过，第 5 轮把 tl.load 的 mask 提到循环外使加速比从 0.7 抬到 1.1。若奖励只给最终加速比，第 3 轮的修复在第 5 轮成功后会被完全吞掉——信用分配失效的典型形态。本卷用折扣因子把增益回传：

$$R_t = r_t + \gamma \cdot \mathbb{1}[\text{pass}_{t+1}] \cdot R_{t+1},\quad \gamma \in (0,1]$$
门控项 pass 是硬条件：一旦某轮编译失败或数值不匹配，后续奖励链断开，避免把“侥幸通过”的加速比计入。代价是轨迹长度被截断，样本利用率下降；\gamma 取小则早期修复的梯度被稀释，取大则末轮噪声主导，二者都需要在课程难度递进时重新标定。

正确性作为硬门控还是软惩罚，是第二个接缝。硬门控的代价是稀疏性：一个算子族里大量候选在编译期就被淘汰，PPO/GRPO 的 advantage 估计方差变大；软惩罚则让“近似正确但快”的解获得正奖励，直接打开 reward hacking 的入口——例如把越界写改成静默截断，正确性 oracle 的随机种子恰好没覆盖到。本卷的折中是分层门控：编译与数值容差作为硬门，边界条件覆盖作为软惩罚项，并在监控面板上单列“门控翻转率”。一张小表说明三档设计的系统代价：

门控形态样本通过率hacking 风险主要代价
全硬门控低低轨迹截断，token 浪费在无效轮
全软惩罚高高oracle 覆盖不足时奖励失真
分层门控中中需维护两套判定与翻转监控

第三个接缝是课程与算子族迁移。难度递进若按“加速比目标”排序，会把 memory-bound 算子排在 compute-bound 之前，导致 agent 学到的是带宽压榨而非计算重排，迁移到 CuTe 的 tiled MMA 时失效。本卷改用 SOL 归一化后的相对基线作为难度刻度：

$$\text{diff} = \frac{\text{SOL}}{\text{baseline}},\quad \text{reward} = \frac{\text{speedup}}{\text{SOL}/\text{baseline}}$$
这样同一算子族内难度可比，跨族迁移时不会因 roofline 位置不同而误判。代价是 SOL 估计本身要花编译与 profile 时间，且对 Triton 生成的非规则 kernel，SOL 上界偏乐观，归一化后奖励被系统性压低——这正是监控面板要盯的“归一化偏移”。工程判断落在：奖励管线必须先于训练规模定型，否则课程一改，历史轨迹的信用分配全部作废。
