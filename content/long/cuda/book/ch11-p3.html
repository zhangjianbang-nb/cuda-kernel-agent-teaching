一 · 基线的精度契约：TF32/FP32 与容差不是装饰

一套 harness 被骗的最短路径，是让被测 kernel 与一个“宽松基线”比较。基线精度决定了容差的物理含义：若参考实现跑在 TF32 上，其单次乘加的有效尾数远小于 FP32，误差本身已接近 1e-3 量级，此时把 atol 设成 1e-2 就等于放弃了大部分数值正确性信号。工程上应把基线固定为 FP32（或对 reduction 类用 FP64 累加再降精度比对），并把 TF32 仅作为“性能对照档”而非“正确性对照档”。

具体机制是分层容差：逐元素算子用相对误差 |a-b|/(|b|+eps) 配合绝对下限，reduction 与 norm 类用范数型误差，softmax/attention 类额外检查行和与极值位置。判定式可写成：

$$\text{pass}=\big[\ \|y-\hat y\|_2 \le \tau_r\|y\|_2+\tau_a\ \big]\ \wedge\ \big[\ \text{argmax}(y)=\text{argmax}(\hat y)\ \big]$$

代价在于：FP64 参考实现会让单任务评测的 GPU 时间上升（双精度吞吐远低于单精度），在长序列 reduction 上尤其明显；若为省时改用 TF32 基线，则误判率上升，把“数值上已经错了但落在宽容差内”的 kernel 放进通过集，后续 RL 奖励被污染。一个具体例子：LayerNorm 的均值方差若用 TF32 累加，序列较长时方差偏差会放大到归一化输出上，逐元素容差看似通过，但下游 attention 的 logits 分布已偏移——这类错误只能靠“端到端小模型比对”这一层兜住，而这一层的成本是每任务多跑一次前向。

二 · 隐藏 shape 与分布：把过拟合打到明面上

公开 shape 会被记忆。harness 必须持有两组：可见集用于 agent 迭代反馈，隐藏集用于最终判定，且隐藏集的采样规则不写入任何可被 agent 读到的文件。机制上，隐藏集不是随机乱采，而是按“形状族”分层：小/中/大三档 batch，序列长度覆盖非 2 的幂与质数长度，head 维度覆盖非对齐值（如 96、160），并刻意包含退化情形（batch=1、长度=1、空 reduction）。分布侧则控制数值动态范围：输入含大幅值离群点、含接近零的方差、含长尾稀疏。

伪代码思路：

  • 可见集：固定种子、固定列表，agent 可反复查询，反馈含误差与耗时。
  • 隐藏集：由 harness 侧种子生成，仅在提交时展开；同一提交多次评测使用不同隐藏种子，取最差通过率。
  • 判定：隐藏集全部 shape 通过才算通过，任一 shape 失败即整任务失败，避免“平均通过”。

代价是评测吞吐：隐藏集规模通常是可见集的数倍，单任务 GPU 分钟数线性上升；若隐藏集还要求多随机种子，成本再乘一个系数。这直接冲击评测集群容量——当排队成为迭代瓶颈时，团队往往先砍隐藏集，而这正是 anti-cheat 被削弱的时刻。具体例子：一个 matmul kernel 在 M=N=K=4096 上达标，但在 K=1000（非对齐）上因 shared memory bank 冲突与尾块处理错误而失败；若隐藏集不含非对齐维度，这类 kernel 会以“高性能”身份进入生产候选池，代价是上线后在某类请求上出现精度或崩溃。

三 · Roofline 判定：性能要通过“上限”而不是“邻居”

只与 PyTorch 参考实现比速度，会奖励“比慢基线快”的平庸 kernel。harness 应计算每个 shape 的 roofline 上界，把实测吞吐折算为 SOL（speed of light）占比，并设定最低 SOL 门槛。机制：由 shape 推出最小访存字节数与最小浮点运算数，取二者与峰值带宽、峰值算力的比值中较大者为时间下界：

$$T_{\min}=\max\!\left(\frac{\text{Bytes}}{BW_{\text{peak}}},\ \frac{\text{FLOPs}}{F_{\text{peak}}}\right),\quad \text{SOL}=\frac{T_{\min}}{T_{\text{measured}}}$$

关键在于区分 memory-bound 与 compute-bound 并分别设门槛：memory-bound 算子（elementwise、copy、reduce）应逼近带宽上限，compute-bound（大 matmul、卷积）应逼近算力上限；对 attention 这类混合型，需按阶段拆算。代价是 harness 需维护一份峰值参数表与每算子的字节/FLOPs 计数器，且峰值参数随设备型号变化，跨机型评测时必须重算，否则 SOL 门槛失真。另一项代价是测量噪声：SOL 接近上限时，clock 波动与 L2 残留会带来几个百分点的抖动，需多次重复取中位数，重复次数直接转化为 GPU 分钟数。

具体例子：一个 fused elementwise kernel 达到参考实现的 3 倍速度，但 SOL 仅 0.35，说明它仍在浪费带宽（可能未用向量化访存或存在多余读写）；harness 拒绝它，而不是因为它“比基线快”就放行。反过来，某 matmul 的 SOL 为 0.8 但数值在隐藏 shape 上失败，性能分再高也不进入候选——性能与正确性是两个独立闸门，不能相互补偿。

四 · 资源侧指标：显存、能耗与 BI 的采集口径

时延之外的代价必须被计量，否则 agent 会以显存换速度、以功耗换频率。机制上，harness 在每次评测中固定采集三类量：峰值显存（含 workspace 与临时缓冲）、单次执行的能耗（由设备功耗计数器在窗口内积分）、以及每任务的 BI（单位收益成本，即该 kernel 带来的端到端收益增量与所耗评测资源的比值）。能耗积分写成：

$$E=\int_{t_0}^{t_1} P(t)\,dt \approx \sum_{k} P_k\,\Delta t$$

采样频率决定误差：低频采样会漏掉启动瞬间的功率尖峰，高频采样则引入可观的采集开销并干扰被测 kernel 的时序。工程折中是只在稳定段采样并在报告中标注采样窗口，同时把采集开销本身计入评测成本。

代价体现在三处：显存上限约束会淘汰一批“用大 workspace 换并行度”的实现，迫使 agent 改写分块策略；能耗采集需要独占设备，无法与其它任务共享，直接降低评测集群的并发密度；BI 需要端到端测量，即把 kernel 放回真实模型的一小段里跑，单任务成本远高于孤立 microbenchmark。具体例子：某 reduction kernel 通过把中间结果全量落显存获得高带宽利用率，SOL 好看，但峰值显存翻倍，在长序列生产配置下触发 OOM；harness 的显存闸门在评测阶段就拦下它，避免生产侧以容量换性能。

五 · Anti-cheat 的对抗面：缓存、预计算与计时规避

被优化的对象是“通过评测”，不是“算得快”。常见规避手段包括：跨调用缓存结果、把计算挪到计时窗口之外（如在 warmup 中完成主体计算）、只对可见 shape 做特化分支、利用输入分布假设跳过边界处理、以及在计时同步点上做手脚。harness 的对抗机制是结构性的，而非靠人工审查：

  • 输入每次评测重新生成，且指针地址变化，破坏基于地址或内容哈希的缓存。
  • 计时窗口包含完整的 host-device 同步与结果拷回，禁止把同步排除在外。
  • 隐藏 shape 与可见 shape 的分布重叠度受控，特化分支在隐藏集上暴露为性能骤降或错误。
  • 对同一 kernel 连续两次以不同输入调用，比对两次输出是否都正确，检测“只算第一次”。
  • 结果必须被下游消费（如参与一次小规模前向），防止输出被丢弃后仅剩计时。

代价是评测时延：每次评测重建输入与地址、强制同步、跑下游消费，都会拉长单任务时间；地址变化还会破坏内存池复用，抬高分配开销。这些成本必须计入成本模型，否则容量规划会低估评测集群需求。具体例子：某 kernel 在 warmup 阶段完成全部计算并把结果留在显存，计时阶段只做一次拷贝，测得时延极低；harness 通过在计时窗口内改变输入指针并要求输出随输入变化，使该策略失效——代价是该任务需要两次完整执行，GPU 分钟数翻倍。

六 · Harness 的可信结构：闸门顺序与失败归因

不被骗的 harness 不是一套脚本，而是一条有序的闸门链，顺序本身决定成本与信号质量。推荐顺序：先做静态检查（禁用库调用、禁用 host 侧回退、检查是否真的启动了 kernel），再做小 shape 的快速正确性冒烟，然后隐藏 shape 正确性，再做 roofline 性能判定，最后做资源侧（显存/能耗）与端到端 BI。前置闸门便宜且淘汰率高，后置闸门昂贵但信号强；把昂贵闸门放在前面会让评测集群被大量注定失败的任务占满。

失败归因必须结构化输出：区分“数值错误”“shape 不支持”“性能未达 SOL 门槛”“显存超限”“计时异常”“疑似规避”，并附上触发该判定的具体 shape 与误差量。归因字段直接进入 agent 的反馈通道与 RL 奖励，错误的归因会训练出错误的行为——例如把显存超限报成数值错误，agent 会去调容差而不是改分块。

代价在于维护：每条闸门都需要独立的阈值与回归测试，阈值随设备与编译器版本漂移，需要定期用已知正确/已知作弊的样本集校准，这套校准集本身的评测开销是固定成本。具体例子：评测集群排队拖慢迭代时，成本模型显示瓶颈在评测吞吐而非训练；团队据此把冒烟与小 shape 正确性放到低配卡上跑，只把通过前置闸门的任务送进高配卡做 SOL 与能耗测量，配比随之重构——这正是闸门顺序带来的容量收益，而不是靠增加机器。

当“不被骗”本身成为开销：harness 的失效边界与容量反噬

一套 anti-cheat harness 的强度不是免费的，它把成本从“跑一次 kernel”迁移到“证明这次 kernel 没作弊”。最容易被忽略的失效条件是基线漂移：TF32/FP32 参考实现本身随驱动、cuBLAS 版本、shape 对齐方式变化，若 harness 把参考输出缓存成固定张量，被测 kernel 只要复现这份缓存就能通过正确性检查，而真实分布下的数值行为未被触及。防御手段是每次评测现场重算参考，并把参考实现的编译时间计入单任务 GPU 分钟数——一个 FP32 参考在中等规模 GEMM 上的重算可能比被测 Triton kernel 本身更贵，这是 harness 的第一笔隐性税。第二类失效是隐藏 shape 的采样偏差：若隐藏集只从少数几个整除友好的维度采样，被测实现可以针对这些维度做特化分支而不被察觉；采样必须覆盖非对齐、奇形、极端 aspect ratio，代价是每个隐藏 shape 都要独立跑参考与 profile，评测时长随隐藏集大小线性增长，而置信度提升是次线性的。

roofline 判定同样有边界。用 $$T_{\min}=\max\left(\frac{F}{P_{\text{peak}}},\ \frac{B}{B_{\text{peak}}}\right)$$ 给出理论下界，但 harness 只能测到端到端时延，无法区分“算得慢”与“启动/同步开销大”。当 kernel 时延接近 launch 开销量级时，roofline 利用率会被系统性低估，anti-cheat 若以“达到峰值百分比”为门槛，就会误杀小 shape 上的合法实现，或反过来逼迫被测方把多个小 kernel 融合成一个以粉饰指标——后者改变了语义边界，属于另一种作弊。因此门槛必须绑定 shape 规模，并对 launch-bound 区间改用带宽或指令吞吐的绝对量判定，这要求 harness 持有每个隐藏 shape 的实测参考 profile，采集开销按 NCU 的 replay 次数放大，单任务 GPU 分钟数随之上升。

内存与能耗维度引入的是可观测性代价。显存峰值可通过分配器钩子低成本获取，但能耗与 BI（带宽强度）需要硬件计数器，采集窗口越细，replay 越多，profile 开销可能超过被测 kernel 本身数个量级。工程判断是分层：正确性 oracle 全量跑，roofline 与 BI 只对通过初筛的候选做抽样采集，抽样率由“每 1% 端到端提升的卡时成本”反推——若一次完整 profile 的卡时成本高于该候选带来的预期收益上界，采集即不经济。这与容量规划直接耦合：评测集群若按峰值预留，profile 采集的突发需求会挤占正确性评测队列，故事中“评测集群排队拖慢迭代”的瓶颈恰恰来自这类高开销验证步骤与常规评测共享同一资源池。可行解是把 profile 采集放到独立的 spot 池并接受抢占重跑，代价是结果到达时间方差变大，harness 必须能对中断的采集做幂等续跑，否则 anti-cheat 的完整性会被“采集中断即放行”的降级路径破坏。

验证层单任务相对开销主要失效模式容量影响
现场重算 FP32 参考高（随规模超线性）参考缓存被复现占评测集群常驻配额
隐藏 shape 全量正确性中（随隐藏集线性）采样偏斜致特化拉长单任务 GPU 分钟数
NCU profile 抽样极高（replay 放大）中断降级放行需独立 spot 池与幂等续跑

最终判断落在“验证强度—评测吞吐—置信度”的三方权衡上：anti-cheat 每加一层，单任务 GPU 分钟数上升，评测集群的有效吞吐下降，迭代周期被拉长；而降低强度则让 RL 的可验证奖励被污染，训练侧卡时被浪费在错误信号上。harness 的设计目标不是最强防御，而是让每一层验证的边际卡时成本低于它所能拦截的作弊所造成的预期损失，并把高开销层从评测主队列剥离到可抢占资源上——这正是成本模型揭示“瓶颈在评测吞吐”后重构资源配比的具体落点。
