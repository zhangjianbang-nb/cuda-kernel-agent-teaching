一 · 基准矩阵：把“快”拆成可复核的坐标

“快”在 kernel 语境里不是一个标量，而是一个带坐标的量。同一段 CUDA C++ 代码，在 A100 上比 H100 快、在 fp32 下比 tf32 快、在 batch=1 时比 batch=64 快，这些陈述彼此不矛盾，因为它们的坐标不同。本卷面对的基准必须把坐标钉死，否则第 5 卷 agent 产出的 kernel 与第 3 卷计时数据无法对齐，硬件反馈通道拿到的 NCU 指标也就失去参照系。可复核的最小坐标组是五元组：(基准任务, 基线实现, 硬件型号, dtype, 指标)。任何一次“这个 kernel 快了”的判断，都必须能还原到这五个槽位。

基准任务侧，KernelBench 系基准提供的是“算子级任务 + 参考实现 + 正确性检查”的三件套，它的价值在于任务边界清晰、可自动判定；代价是它把真实负载里的融合、动态 shape、边界条件裁掉了，因此算子级加速比不能直接外推到端到端。基线实现侧，必须区分三种基线：框架基线（PyTorch eager）、编译基线（torch.compile / Triton 自动生成）、以及人手调优基线（cuBLAS/CUTLASS 对应算子）。前两者是“agent 至少要打败的”，后者是“agent 应该接近的”。把 cuBLAS 当唯一基线会低估 agent 的改进空间，把 eager 当唯一基线则会高估。

硬件与 dtype 是两个最容易被悄悄换掉的坐标。H100 的 fp8 吞吐与 A100 的 fp16 吞吐不在同一量纲上，跨卡比较加速比是无效陈述。dtype 还牵动正确性口径：tf32 下 1e-2 的相对误差可能可接受，fp32 下同样的误差就是 bug。因此基准表里 dtype 必须与容差绑定出现，不能只写“fp16”。指标侧则要区分延迟（单次 kernel 墙钟）、吞吐（单位时间处理量）、以及 SOL 利用率（相对 roofline 的百分比）。三者对优化的敏感度不同：合并访存主要抬吞吐，减少同步主要降延迟，而 SOL 利用率是唯一能跨硬件归一化的指标。

坐标槽位可取值示例被换掉时的后果
基准任务算子级 / 子图级 / 端到端加速比不可外推
基线eager / compile / 手调库改进空间被高估或低估
硬件同卡内比较才有效跨卡加速比无效
dtype与容差绑定正确性口径漂移
指标延迟 / 吞吐 / SOL优化动作与指标错配

一个具体例子：agent 把一个 layernorm 的 shared memory 分块改小后，单次 kernel 延迟下降，但吞吐持平——因为分块变小抬高了同步次数，延迟收益被 occupancy 下降吃掉。若基准只记延迟，这次改动会被判为“有效”；若同时记 SOL 利用率，会发现它离 roofline 更远了。这就是五元组必须成套出现的原因：单指标会奖励错误的优化动作。

二 · 计时口径：墙钟、事件与采样开销的三角

把“快”翻译成数字的第一步是计时。CUDA 侧有三种口径：host 墙钟（含 launch 开销与同步）、CUDA event（device 侧时间戳，剔除 host 抖动）、以及 NCU 采集下的受控重放。三者数值不同，且差异本身是信息。host 墙钟对短 kernel 严重失真，launch 开销可以占到大头；event 计时把 launch 剥离，但仍有 event 记录本身的开销；NCU 重放会把 kernel 多次执行以采集多组指标，此时测得的时长不是生产时长。

$$T_{\text{wall}} = T_{\text{launch}} + T_{\text{kernel}} + T_{\text{sync}},\qquad \text{SOL} = \frac{T_{\text{ideal}}(W, \text{BW})}{T_{\text{kernel}}}$$

其中 $T_{\text{ideal}}$ 由工作量 $W$ 与该硬件的峰值带宽或峰值算力推出，取两者中较大者作为 roofline 拐点。SOL 的分母必须用 event 口径的 $T_{\text{kernel}}$，否则 launch 开销会污染利用率。这条约束直接决定了本卷的关键决策之一：profile 采样频率与开销预算。NCU 全指标采集一次可能让 kernel 慢一个数量级，若把它当作计时口径，SOL 会被系统性低估。

工程上的做法是双通道：计时通道只跑 event 计时，不挂 NCU；反馈通道单独跑 NCU，采 occupancy、memory throughput、stall reason、bank conflict 四类指标，且只采关键段落。两通道的结果在报告里分开标注，禁止混算。代价是显式的：反馈通道的编译与重放时间计入流水线时延，采样越密，单次迭代的墙钟越长，agent 多轮迭代的预算被压缩。采样频率因此不是“越高越好”，而是与迭代轮数做权衡——每轮多花在 profile 上的时间，等于少跑一轮优化。

具体例子：一个 reduction kernel 的 event 计时为数十微秒量级，而 host 墙钟因 launch 与同步可能翻倍。若 agent 依据墙钟判断“变慢了”而去合并访存，实际瓶颈可能在 launch 侧，优化动作与真实瓶颈错配。把计时口径写进基准表，并在 prompt 里明确告知 agent 所用口径，是避免这类错配的最低成本手段。

三 · 基线校准：加速比的分母必须是同一把尺

加速比 $S = T_{\text{base}} / T_{\text{cand}}$ 的可信度完全取决于分母。分母若来自不同 dtype、不同 shape、不同预热策略，$S$ 就是噪声。校准基线要做三件事：固定输入分布与 shape 集合、固定预热与重复次数、固定计时口径。预热尤其关键——首次 kernel 调用含 JIT 与上下文初始化，若把它算进基线，分母被抬高，加速比虚高；若把它算进候选，则虚低。正确做法是两侧都丢弃前若干次迭代，只统计稳态。

基线校准还有一个隐蔽维度：基线是否经过等价优化。若基线是 eager 实现而候选 kernel 做了算子融合，那么 $S$ 里混入了“融合收益”与“kernel 内优化收益”两项，无法归因。可复核的做法是把基线拆成两级：算子级基线（同算子、同 dtype、同 shape 的库实现）用于衡量 kernel 本体；子图级基线用于衡量融合。两级加速比分别报告，agent 的优化动作才能对应到正确的分母。

  • 固定 shape 集合：覆盖小 batch（launch 主导）与大 batch（带宽主导）两端，避免单一 shape 过拟合。
  • 固定预热：丢弃首次调用，稳态重复取中位数而非均值，抑制长尾。
  • 固定容差：dtype 与容差绑定，正确性 oracle 的判定阈值写进基准表。
  • 固定口径：基线用 event 计时，候选同口径，禁用墙钟混算。

代价方面，多 shape 校准会成倍增加评测时间；每增加一个 shape，就多一次基线测量与一次候选测量，评测流水线的墙钟线性增长。这是可信度的直接成本，不能靠“取平均”省掉——不同 shape 的加速比不可平均，只能分列。具体例子：一个 softmax kernel 在小 shape 上加速比很高（因为 eager 的 launch 开销占比大），在大 shape 上加速比接近 1（因为已接近带宽上限）。若只报小 shape 的数字，agent 会误以为还有巨大优化空间，从而把预算浪费在已经饱和的路径上。

四 · 指标到动作：NCU 四类指标如何映射成可复核的优化

硬件反馈通道的核心不是“采到指标”，而是“指标能落到动作”。本卷规则库把 NCU 指标映射为四类动作：合并访存、shared memory 分块、减少同步、指令级并行。映射关系必须是单向可复核的：给定指标读数，能推出建议动作；给定动作执行后的指标变化，能验证动作是否生效。这条双向链条是“快”变成可复核数字的关键。

NCU 指标读数含义映射动作验证信号
memory throughput接近峰值则带宽受限合并访存 / 向量化吞吐上升且 stall 下降
occupancy低则并行度不足调分块 / 寄存器压力occupancy 上升且延迟下降
stall reason同步或访存等待主导减少同步 / 预取对应 stall 占比下降
bank conflictshared memory 冲突padding / 重排布局冲突计数下降

映射不是一一对应，而是带优先级的判定树：先看 memory throughput 是否接近峰值，若是则带宽受限，动作集中在访存；若不是，再看 stall reason 的主因，若是同步等待则减少同步，若是访存等待则预取或分块。bank conflict 是 shared memory 路径上的局部指标，只在分块方案确定后才有意义。判定树的顺序本身就是工程判断：先判全局瓶颈，再判局部瓶颈，避免在带宽受限的 kernel 上做指令级并行这种无效动作。

代价在这里体现为 token 成本。把 NCU 原始指标全量塞进 prompt 会迅速耗尽上下文预算，而 agent 需要的是“可行动的信号”。本卷的控制策略是：只把判定树命中的前若干项指标、对应的 SASS 关键片段、以及规则库给出的候选动作写进 prompt，其余指标留在本地日志供复核。SASS 反汇编片段尤其昂贵——一段几十条指令的反汇编可能占用大量 token，因此只提取与 stall 相关的关键片段，而非整段 dump。这是“哪些指标进 prompt”这一决策的直接约束。

具体例子：故事中 agent 首次“看懂”NCU stall 报告并自主改 shared memory 分块。其机制正是判定树命中：stall reason 显示同步等待占比高，occupancy 偏低，规则库给出“调分块尺寸”的候选动作，agent 据此改写分块参数，重跑后 stall 占比下降、延迟下降。这条链上每一步都有可复核的数字：stall 占比、occupancy、event 延迟。若缺少任一步的数字，改动就无法归因，也就无法在多轮 RL 中作为可验证奖励。

五 · 可复核数字的封装：报告结构与奖励接口

“快”最终要落成一个结构化记录，供评测流水线、agent 反馈、以及多轮 RL 的奖励函数共同消费。记录的最小字段是：五元组坐标、event 延迟、吞吐、SOL 利用率、正确性判定、NCU 命中指标、以及本次迭代的 profile 开销。字段之间要有派生关系：SOL 由延迟与工作量推出，加速比由候选与基线延迟推出，正确性判定由容差与参考输出推出。派生关系写死在报告结构里，任何手工填写的数字都会被校验拒绝。

$$R = \big(\text{coord},\; T_{\text{cand}},\; S,\; \text{SOL},\; \text{pass},\; \text{stall}_{\text{top}},\; C_{\text{prof}}\big)$$

这个记录同时是奖励接口。多轮 RL 的可验证奖励不能只看 $S$，因为 $S$ 可以被错误基线抬高；也不能只看 SOL，因为 SOL 对 launch 开销不敏感。可行的组合是：正确性 pass 作为硬门槛，$S$ 与 SOL 作为连续奖励，profile 开销 $C_{\text{prof}}$ 作为惩罚项，抑制 agent 用高频采样换取虚假精度。惩罚项的系数是工程判断：采样开销占迭代预算的比例越高，惩罚越重，从而把 agent 推向“少采样、精准采样”的策略。

代价维度上，报告结构的字段越多，写入与校验的时延越长，评测流水线的吞吐下降。字段太少则无法归因。折中是分层：核心字段（坐标、延迟、正确性）必填且强校验，诊断字段（NCU 命中项、SASS 片段）选填且按需拉取。这样常规评测走轻量路径，深挖时才付 token 与时间成本。具体例子：一次迭代若只做正确性与延迟校验，报告写入是毫秒级；若同时拉取 SASS 片段与全量 NCU 指标，写入与 prompt 组装可能达到秒级，且 token 消耗显著上升。分层让 agent 在多数轮次走轻量路径，只在判定树命中且需要深挖时才付重成本。

最后落在工程判断上：基准与口径的本质不是“选一个数字”，而是“选一组互相约束的数字”。五元组钉死坐标，双通道隔离计时与采样，判定树把指标映射成动作，结构化记录把动作结果变成可校验的奖励。任何一环松动，“快”就退化成不可复核的断言。故事里 agent 看懂 stall 报告的那一步之所以成为性能跃迁的拐点，不是因为 NCU 指标本身，而是因为指标被判定树翻译成了具体动作、动作结果又被结构化记录捕获——这条链闭合，硬件反馈才真正成为可迭代的信号。
