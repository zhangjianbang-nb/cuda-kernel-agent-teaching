一 · 脚手架的分工不是角色扮演，而是信息流的切分

把 coder、judge、profiler、search 当成四个“人格”来设计，是这类系统最常见的失败起点。真正决定可靠性的不是它们各自多聪明，而是每个环节向下一环节传递什么、丢弃什么。一个可运营的 kernel agent 脚手架，其本质是一条带类型的信息流水线：coder 产出的是候选源码加自述假设；judge 产出的是布尔正确性判定加最小反例；profiler 产出的是结构化指标向量（时延、带宽利用率、occupancy、指令组合特征）；search 产出的是在候选空间上的采样决策与预算分配。四者之间只允许传递结构化对象，不允许传递自然语言辩解——一旦允许 coder 用文字向 judge “解释为什么这个误差可接受”，judge 的判定就会从可复现的 oracle 退化为语言模型的说服力竞赛。

这条流水线的关键机制是反馈契约：每一环必须声明自己输出的字段与置信度，且下游只能消费声明过的字段。例如 judge 的输出契约规定必须包含 verdict、max_abs_err、max_rel_err、failing_shape、seed；profiler 的输出契约规定必须包含 kernel_time_p50、dram_throughput_pct、sm_occupancy、sass_hot_loop 的指令计数。任何缺失字段都触发降级路径，而不是让下游用猜测填补。

$$\text{accept}(c)=\big[\text{verdict}(c)=\text{pass}\big]\wedge\big[\text{sol}(c)\ge \tau_{\text{sol}}\big]\wedge\big[\text{regress}(c)\le \tau_{\text{reg}}\big]$$

这个接受判据把正确性与性能放在同一个与门上，代价是每次候选评估都要跑满正确性测试集与至少一次 profile，单候选的墙钟成本从“编译+跑一遍”上升到“编译+多 shape 正确性+NCU 采集”。在候选吞吐受限的场景里，这意味着 search 的每轮采样数必须下调，否则队列积压会把多轮修正的时延推到不可接受。一个具体例子：当候选需要覆盖多个输入 shape 时，judge 若只测单一 shape，就会放过在边界 shape 上溢出的实现；而把 shape 集合纳入契约后，单候选评估时间上升，search 必须改为按 shape 分层采样，先在小 shape 上筛掉明显错误，再对大 shape 做完整审计。

二 · 执行反馈的三种粒度与它们的时延账单

执行反馈不是一个东西，而是三个不同粒度的信号，混用会让 agent 学到错误的因果。第一层是编译反馈：nvcc/ptxas 的报错与警告、寄存器溢出、共享内存超限、Triton 的编译期 shape 推导失败。第二层是运行时反馈：启动失败、非法访存、数值不匹配、超时。第三层是微架构反馈：NCU 采集的 stall 原因分布、SASS 层面的指令混合与访存模式。三层的时延差一个到两个数量级，而信息量方向相反——编译反馈最便宜但只覆盖语法与资源约束，NCU 最贵但能指出“这个 kernel 卡在 long scoreboard 上，因为全局访存没有合并”。

合理的调度机制是逐层升级的漏斗：先用编译反馈做零成本过滤，再用运行时反馈做正确性门禁，只有通过前两层且性能未达标的候选才进入 NCU 采集。这样做的代价是漏斗本身有漏检风险——一个编译通过、数值正确但性能极差的候选会消耗一次昂贵的 profile，而一个在运行时反馈层因超时被杀的候选可能只是启动配置选错。因此漏斗需要记录每一层的淘汰率，作为 BI 看板上的一个诊断指标：若编译层淘汰率骤降而 NCU 队列暴涨，说明 coder 在生成大量“语法正确但结构错误”的候选，问题出在生成端而非评估端。

伪代码层面的调度可以写成：

$$\text{route}(c)=\begin{cases}\text{drop} & \text{compile fail}\\\text{revise}(\text{err}) & \text{runtime fail}\\\text{profile}(c) & \text{pass}\wedge\text{sol}<\tau\\\text{accept} & \text{pass}\wedge\text{sol}\ge\tau\end{cases}$$

具体例子：一个 reduction kernel 在编译层通过，运行时在小 shape 上数值正确，但在大 shape 上因共享内存 bank conflict 导致时延翻倍。若没有 NCU 层，agent 只会看到“正确但慢”，无从知道该改访存布局还是改分块策略；NCU 的 stall 分布把“慢”翻译成“bank conflict 占比高”，多轮修正才有方向。代价是这次 NCU 采集本身占用了评估吞吐，且采集时的时钟与缓存状态会扰动测量，因此 profiler 必须声明采集配置（是否锁频、是否重复采样取中位数），否则下游会把测量噪声当成优化信号。

三 · NCU 与 SASS 的分工：指标向量与指令证据

NCU 给出的是聚合指标，SASS 给出的是指令级证据，二者不能互相替代。NCU 的 throughput 百分比告诉你“距离 roofline 还有多少”，但不告诉你为什么；SASS 的热循环指令计数告诉你“这个循环里有几条 LDG、几条 FFMA、是否有冗余的地址计算”，但不直接给出带宽利用率。可靠的脚手架必须让 profiler 同时产出两者，并在契约中规定：任何性能回退的归因，必须至少有一条 SASS 层面的证据支撑，否则归因树只能落到“未归因”分支。

机制上，profiler 对每个候选执行固定次数的采集，取中位数以抵抗抖动，并把 SASS 热循环的指令直方图与 NCU 的 stall 分布做交叉索引。例如当 NCU 显示 dram_throughput_pct 高而 sm_occupancy 低时，SASS 若显示热循环内存在大量标量 LDG 而非向量化 LDG.128，则归因指向“访存未向量化导致带宽被浪费在事务开销上”；反之若 SASS 显示已向量化但仍有大量 long scoreboard stall，则归因指向“延迟隐藏不足，需增加并行度或预取”。这个交叉索引是归因树从“性能”分支细化到具体修复动作的唯一通道。

$$\text{roofline gap}=1-\frac{\text{achieved}}{\min(\text{peak}_{\text{mem}},\text{peak}_{\text{compute}})}$$

代价在于采集开销与可复现性：NCU 采集会使 kernel 运行时间显著拉长，且不同采集配置（是否开启 cache control、是否做 replay）会改变测量结果；SASS 反汇编则依赖编译产物与架构匹配，跨架构的指令计数不可直接比较。一个具体例子：同一份 Triton kernel 在两种 tile 配置下 NCU 显示相近的 DRAM 吞吐，但 SASS 显示一种配置的热循环里多出一组冗余的谓词判断，说明瓶颈不在带宽而在指令发射；若只看 NCU 就会误判为“已接近带宽上限，无需优化”，从而错过一次真实的指令级优化机会。

四 · 多轮修正的状态管理：什么该记住，什么必须丢弃

多轮修正的可靠性瓶颈不在单轮质量，而在状态污染。若把每一轮的完整对话、完整源码、完整 profile 都塞进上下文，agent 会在第若干轮后开始引用已被推翻的假设，把“上一轮我说过这个误差可接受”当成事实。正确的做法是维护一个结构化修订账本：每条记录包含候选 id、父候选 id、修改摘要（结构化字段而非自然语言）、judge 判定、profile 指标向量、以及该修改所针对的归因分支。上下文只注入账本的摘要视图与当前待修分支的相关证据，历史全文留在外部存储。

机制上，账本支持两种检索：按归因分支检索（“历史上所有针对 bank conflict 的修改及其效果”）与按候选谱系检索（“当前候选的祖先链上哪些修改被回滚过”）。前者防止 agent 重复尝试已被证伪的修复，后者防止 agent 在回滚过的方向上反复震荡。代价是账本本身需要维护与去重，且摘要视图的字段选择会直接影响 agent 的修正方向——若摘要里只保留时延不保留 stall 分布，agent 就会倾向于做与 stall 无关的改动。

$$\text{priority}(b)=\frac{\text{gap}(b)\cdot w_b}{\text{cost}(\text{fix}_b)}$$

这个优先级公式用于在多个归因分支间分配修正预算：gap 是该分支对应的性能缺口，w_b 是该分支的历史修复成功率，cost 是预计的评估轮数。具体例子：一次数值精度事故中，judge 报告某 shape 上 max_rel_err 超阈值，账本检索显示祖先链上曾有一次为提升性能而把累加类型从 fp32 改为 fp16 的修改——归因直接指向数值分支而非性能分支，修正动作是回滚该类型变更并重新评估性能代价，而不是盲目再调 tile。若没有谱系检索，agent 很可能在性能分支上继续优化，把精度问题掩盖得更深。

五 · search 的预算分配与 BI 看板的接口

search 不是“多采样几次”，而是在正确性门禁与 profile 成本约束下做预算分配。它需要决定：每轮生成多少候选、多少进入 judge、多少进入 profiler、以及在连续若干轮无提升时是否切换归因分支或回退到更保守的实现。这个决策必须消费 BI 看板上的分布指标，而不是单点数值——成功率、加速比分布、SOL 分布、回退率这四个口径共同定义了“当前搜索是否还在有效区域”。

机制上，search 维护一个按归因分支分层的成功率估计，当某分支的连续失败次数超过阈值时，降低该分支的采样权重；当整体成功率跌破基线时，触发一次“保守重采样”，即从账本中检索历史上通过 judge 且 SOL 达标的候选作为新的起点。代价是分层估计需要足够的样本量，冷启动阶段的分层会引入估计噪声，导致预算被错误地分配给低价值分支；因此冷启动期应退化为均匀采样，待样本积累后再启用分层。

信号来源search 的动作代价
编译淘汰率骤升编译层漏斗降低生成长度，收紧模板约束候选多样性下降
judge 失败集中在单一 shapejudge 契约该 shape 加权采样，优先修边界评估吞吐被单 shape 占用
SOL 分布整体右移但无达标profiler 指标向量切换归因分支，重分配修正预算已投入的 profile 采集沉没
回退率上升账本谱系冻结高风险修改方向，回退到保守起点搜索空间收缩，可能错过更优解

具体例子：当 BI 看板显示加速比分布的长尾变薄而中位数未动，说明 search 正在收敛到局部最优而非发现新结构；此时正确的动作不是增加采样数，而是从账本中取出被回滚过的“高风险高收益”修改，在受控预算下重新评估。这个动作的代价是可能重新引入已被证伪的数值问题，因此必须与 judge 的边界 shape 集合联动，先在小 shape 上验证数值稳定性再放大。

六 · 归因树与告警阈值的接口：从救火到可运营

本卷的可靠性体系要求失败归因树覆盖编译、数值、性能、集成四类分支，而 agent 脚手架的每一层反馈恰好对应其中一类：编译层对应编译分支，judge 对应数值分支，profiler 对应性能分支，端到端集成测试对应集成分支。这意味着脚手架的契约字段必须能直接映射到归因树的节点，否则线上告警触发时，团队无法从 BI 看板下钻到具体的失败原因。映射的机制是给每个契约字段打上归因标签，例如 max_rel_err 标注为数值分支，dram_throughput_pct 标注为性能分支，标签在账本中随候选一起持久化。

告警阈值的选择直接决定这套映射是否有用。按均值设阈值会被长尾掩盖——少数极端慢的 shape 拉高均值但中位数正常，告警不触发，而线上事故恰恰来自这些极端 shape；按分位数设阈值则能捕获长尾，但需要足够的采样量才能稳定估计分位数，采样率与开销之间形成直接权衡。合理的工程判断是：正确性告警用严格阈值（任何边界 shape 的数值异常都触发），性能告警用分位数（如高百分位时延相对基线的回退），并对两类告警分别设定自动回滚策略——数值类默认自动回滚，性能类默认只告警不自动回滚，因为性能回退可能来自测量噪声或负载变化。

$$\text{alert}=\big[\hat{q}_{99}(\text{latency})>\theta_{\text{lat}}\big]\vee\big[\exists s:\text{err}(s)>\theta_{\text{err}}\big]$$

具体例子：一次数值精度事故引发线上告警，归因树把告警定位到数值分支的某个边界 shape，账本谱系显示该候选的祖先链上有一次为提升吞吐而放宽累加精度的修改，而该修改在离线 judge 中因 shape 集合不全而未被捕获。修复动作不是回滚整个候选，而是把该 shape 加入 judge 的常驻边界集合，并在 BI 看板上把“边界 shape 覆盖率”作为一个常驻指标。这里的代价是每次候选评估的 shape 集合扩大，评估时延上升，search 的每轮采样数必须相应下调；而收益是归因树从“事后猜测”变成“事前可查”，团队从救火转向可运营。

最终落在工程判断上：脚手架的可靠性不取决于任何单一环节的智能程度，而取决于契约字段是否足以支撑归因树下钻、账本是否足以阻止状态污染、以及 search 是否把 BI 分布指标当作预算分配的依据而非事后报表。这三者中任何一环缺失，多轮修正都会退化为在噪声上做局部搜索，而线上告警只能给出“失败了”而无法给出“为什么失败、该改哪里”。
