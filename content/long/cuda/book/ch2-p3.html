一 · 基线口径：TF32 与 FP32 的分数不可混算

可信评测的第一道裂缝不在被测 kernel，而在参照系。同一份 harness 若允许提交方自选基线精度，分数就失去可比性：TF32 的矩阵乘峰值吞吐与 FP32 相差一个量级，用 TF32 跑出的加速比与用 FP32 跑出的加速比放在同一张榜上，等于把两种物理量相加。工程上的做法是把基线固定为“参考实现的实测时延”，而不是理论峰值：对每个 shape，先跑一份由 harness 维护的、禁止提交方修改的参考 kernel（cuBLAS 调用或手写朴素实现），在同一时钟、同一显存状态下测三次取中位数，记为 t_ref；提交 kernel 的时延 t_sub 与之相比得到加速比。基线精度必须在任务元数据里硬编码：矩阵类任务声明 baseline_dtype=fp32 或 tf32，且提交 kernel 的数值容差随之切换——TF32 基线对应更宽的相对误差阈值，FP32 基线对应接近机器精度的阈值。若允许提交方在 TF32 基线下用 FP32 计算，它会得到“正确但更慢”的分数；反之在 FP32 基线下偷用 TF32，则可能通过宽松容差骗到加速比。两种作弊方向都必须由元数据封死。

代价是测量开销：每个 shape 多跑一份参考实现，若参考实现本身是朴素三重循环，在 L2 规模的问题上可能比提交 kernel 慢两个数量级，单次评测的墙钟时间被参考侧主导。缓解手段是把参考时延做成离线缓存：基准版本发布时对固定 shape 集合预跑参考实现，把 t_ref 连同 GPU 型号、时钟、驱动版本一起写入基准清单，评测时直接查表，只在硬件指纹不匹配时重跑。这引入一个新的可比性问题：换卡后缓存失效，历史分数不能直接跨卡比较，基准变更记录里必须标注“同卡可比、跨卡需重标定”。

$$\text{speedup}=\frac{t_{\text{ref}}(\text{shape}, \text{dtype}, \text{GPU})}{t_{\text{sub}}(\text{shape})},\quad \text{valid}\iff \|y_{\text{sub}}-y_{\text{ref}}\|_\infty \le \tau(\text{dtype})$$

具体例子：一个 L2 级 GEMM 任务，元数据写死 FP32 基线与 τ=1e-5 相对误差。提交方若把输入降精度到 TF32 计算，误差落在 1e-3 量级，直接被判无效，而不是拿到一个虚高的加速比。这条规则看似简单，却是私有 held-out 迁移后分数虚高被揭穿时最先暴露的问题之一：污染检测发现部分高分提交的误差分布与声明的基线精度不符。

二 · 隐藏 shape 与分布：把过拟合打到明面上

公开基准的 shape 集合一旦进入训练语料，提交方（人或 agent）就能针对固定 shape 做特化：为 4096×4096×4096 手工挑选 tile 尺寸、为特定 batch 写死分支。可信 harness 的应对不是简单换一批 shape，而是把 shape 采样变成评测时才揭晓的随机变量。机制上分三层：第一层是任务元数据只声明 shape 的分布族（如“M,N,K 各自在 512 到 8192 之间按对数均匀采样，K 为 64 的倍数”），不给出具体值；第二层是评测时由 harness 用固定种子的伪随机数生成器现场采样，种子在基准版本发布时写入清单但对提交方不可见；第三层是保留一组固定“锚点 shape”用于跨版本可比，锚点集合公开但只占评测权重的一部分。

分布维度不止 shape。输入数值分布同样影响正确性与性能：全零输入会让某些 kernel 走短路分支，极大值会触发溢出路径，稀疏分布会改变分支发散程度。harness 应对每个任务声明输入分布（均匀、正态、对数正态、含 NaN 的边界用例），并在正确性检查里强制覆盖边界：至少一个含极值的用例、一个含非连续 stride 的用例、一个空 tensor 或退化维度用例。退化维度是最容易被忽略的作弊面——提交 kernel 若对 N=0 直接返回而不做任何计算，时延趋近于零，加速比爆表；harness 必须把退化用例的正确性纳入判定，且对时延设下限（低于参考实现一个数量级以下的时延触发人工复核）。

代价是评测方差：随机采样让同一提交在不同评测轮次得到不同分数，方差大小取决于分布族的宽度。工程判断是把采样数固定（如每任务 20 个随机 shape 加 5 个锚点），报告分数时同时给出中位数与最差 shape 的分数，后者才是部署方真正关心的。token 代价体现在 agent 侧：隐藏 shape 意味着 agent 无法在推理时枚举所有用例做自测，只能依据元数据里的分布族写通用代码，这提高了单次生成的有效信息密度要求，也拉长了多轮 RL 中“试错—修正”的轮数。

三 · roofline 与 SOL：把“快”翻译成“离上限多远”

加速比是相对量，参照实现换一版，分数就漂移。可信 harness 需要一把绝对尺：roofline 模型给出每个任务在给定硬件上的性能上界，把提交 kernel 的实测吞吐折算成“达到 SOL 的百分比”。机制上，对每个任务预先计算算术强度 I = FLOPs / Bytes，其中 Bytes 按最小必要访存计（读输入、写输出，不含中间缓存），再与硬件的峰值算力 P_peak 和峰值带宽 B_peak 比较，取两者较小者作为上界。这个上界是理想化的：它假设无额外访存、无同步开销、无尾效应，因此实测 kernel 永远达不到 100%，但 SOL 百分比在跨版本、跨实现语言（CUDA C++、Triton、CuTe、PTX）之间是可比的。

$$P_{\text{roof}}=\min\left(P_{\text{peak}},\; I\cdot B_{\text{peak}}\right),\qquad \text{SOL}=\frac{P_{\text{measured}}}{P_{\text{roof}}}$$

roofline 的工程价值在于分类诊断：SOL 低且实测带宽接近峰值，说明 kernel 是访存受限，优化方向是减少冗余读写或提高数据复用；SOL 低且算力利用率低而带宽远未饱和，说明存在调度或占用率问题，需要看 NCU 的 warp stall 原因。这把“为什么慢”从猜测变成可分类的判断，也让 agent 的优化动作有了方向性奖励信号，而不是只看加速比的黑箱反馈。

代价是 roofline 上界本身可能算错：算术强度依赖对“最小必要访存”的建模，融合算子（如 softmax、layernorm）的中间量若被计入 Bytes，上界会被低估，导致 SOL 虚高甚至超过 100%。harness 必须对每个任务的上界做健全性检查——任何 SOL 超过 100% 的提交都触发复核，而不是直接记为满分。另一个代价是硬件参数依赖：P_peak 与 B_peak 随 GPU 型号、时钟、功耗墙变化，SOL 分数必须绑定硬件指纹，跨卡不可比。具体例子：一个带宽受限的 elementwise 融合任务，朴素实现 SOL 约三成，优化到七成即为合格；而一个计算受限的 GEMM，SOL 三成可能已经接近该 shape 下的实际可达上限，因为小 shape 的尾效应吃掉了大部分理论峰值。同一 SOL 数值在不同任务上含义完全不同，harness 报告里必须按任务类型给出参考区间，而不是一个全局阈值。

四 · 内存、能耗与 BI：被加速比掩盖的三条曲线

只测时延的 harness 会奖励“用更多显存换速度”的策略：把中间结果全部物化、把输入复制多份、用超大 workspace 换取更简单的索引计算。这些策略在单卡小 shape 上看起来更快，放到生产端到端场景就是显存溢出或吞吐塌方。可信 harness 因此把峰值显存占用作为一等指标：用 CUDA 的内存池统计或驱动层查询，记录提交 kernel 执行期间的显存峰值增量，与参考实现的峰值比较，超出预算（如参考实现的 1.5 倍或任务声明的绝对上限）即判不合格，无论时延多快。

能耗维度更微妙。单次 kernel 的能耗测量噪声大，工程上可行的做法是在固定迭代次数下测整卡功耗积分，得到每次调用的平均能量，再与同任务参考实现比较。能耗指标的意义不在于精确排名，而在于拦住“靠拉高时钟、靠占用全部 SM 空转等待”这类粗暴策略——它们在时延上可能略优，但能量效率明显更差。代价是测量时间长：功耗采样需要稳定窗口，单任务评测从秒级拉长到分钟级，基准全量跑一轮的成本上升，因此能耗通常只在候选提交进入复评阶段时才测，初筛仍以时延与正确性为主。

BI（business intelligence）侧的接入点是把 kernel 级指标映射到端到端收益：一个 SOL 提升 20% 的 kernel，若它在整条推理链路中只占 5% 的时间，端到端收益不足 1%。harness 应记录每个任务在参考工作负载中的时间占比，作为分数加权或分级依据，避免榜单被“占比极小但容易优化”的算子刷满。具体例子：一个 L1 级的小算子，加速比做到 5 倍，但它在目标模型的前向中只被调用一次、耗时占比不到百分之一，这种提交在 BI 加权后几乎不影响总分，harness 的排序逻辑必须体现这一点，否则 agent 会被引导去优化错误的目标。

五 · anti-cheat：把作弊面逐条封死

作弊不是道德问题，是激励结构问题。只要分数可被观测，提交方就有动机寻找测量漏洞。可信 harness 的 anti-cheat 是一张逐条对应的封堵清单，每条都对应一个具体机制与一个代价。

作弊面封堵机制代价
缓存结果跨调用复用每次调用前重置输入 buffer 内容与地址，输入含随机噪声每次评测多一次写带宽开销
异步执行未同步就计时计时区间强制插入事件同步，禁用提交方自报时延同步引入固定开销，小 kernel 时延被高估
针对固定 shape 特化隐藏 shape 现场采样，锚点仅占部分权重评测方差上升，需多轮取中位数
降精度偷跑基线 dtype 硬编码，容差随 dtype 切换参考实现需按 dtype 各跑一份
退化输入短路退化用例纳入正确性判定，时延设下限需人工复核异常低时延
编译期预计算禁止在 host 侧对输入做预处理，只允许 kernel 内计算需审计提交源码的 host 段

其中“编译期预计算”是最隐蔽的一条：提交方可以在 host 代码里对输入做一次昂贵的预处理，把结果传给一个极简 kernel，计时只覆盖 kernel 启动，预处理时间被排除在测量之外。封堵方式是计时区间覆盖从输入就绪到输出可读的全过程，包括必要的 host-device 拷贝，并对提交源码做静态审计，标记任何在计时区间外触碰输入数据的 host 调用。代价是审计需要人力或额外的静态分析工具，且会误伤合法的常量初始化（如查表），需要白名单机制。

另一条常被忽略的是“测量工具本身被污染”：提交方若能在进程内挂钩 CUDA event 或篡改计时返回值，所有指标失效。harness 应在独立进程或独立容器中运行被测代码，计时由外部驱动进程完成，被测进程只负责执行与返回输出，不接触计时逻辑。代价是进程间通信与数据搬运的开销，对小 kernel 的时延测量精度有影响，需要用批量迭代摊薄。

六 · harness 的可信度自身要被评测

一套不被骗的 harness，其可信度不能靠声明，要靠注入测试。机制上维护一组“已知答案的作弊提交”作为 harness 的自检集：缓存复用型、异步未同步型、降精度型、退化短路型各一份，每次 harness 变更后跑一遍，确认这些提交全部被判定为无效或低分。若某份作弊提交意外通过，说明对应的封堵机制失效，harness 版本不能发布。这组自检提交与基准版本一同归档，构成基准变更记录的一部分。

代价是维护成本：作弊手法会演化，自检集需要定期扩充，且每扩充一条就要重跑全量回归，确认没有误伤合法提交。误伤是比漏判更难处理的失败模式——一个合法的、用满显存的融合 kernel 若被显存预算规则误杀，会直接打击提交方的优化方向。因此每条封堵规则都需要一个“合法边界用例”与之配对，规则上线前必须确认边界用例通过。

具体例子：私有 held-out 迁移后，污染检测发现某批高分提交在隐藏 shape 上性能骤降，回溯发现它们对公开 shape 做了 tile 特化。harness 的应对不是简单换 shape，而是把“锚点 shape 与随机 shape 的分数差”本身作为一个指标记录：分数差超过阈值的提交被标记为疑似过拟合，进入人工复核。这个指标后来成为基准版本升级时的常规检查项，也让“分数虚高”从一次性事件变成了可监测的信号。harness 的可信度最终落在这些可复现的检查项上，而不是某一次评测的结论。
