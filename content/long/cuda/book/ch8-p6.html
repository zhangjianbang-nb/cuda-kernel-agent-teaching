一 · 从“跑得对”到“时间去哪了”：硬件反馈的三种可见度

Agent 拿到一个能通过正确性 oracle 的 kernel，只完成了第一层。第二层是它必须能回答“这个 kernel 的时间花在哪、离机器上限多远”。这层反馈有三种可见度，代价依次上升：聚合计数（NCU 的 stall 采样、SM 占用率、DRAM 吞吐）、指令级归因（SASS 与 source 的对应、逐 warp 的 stall reason）、二进制插桩（在编译产物里埋计数器，做精确到指令的时延归因）。三者不是替代关系，而是预算关系：一次完整 NCU 采集在复杂 kernel 上会让被测 kernel 的墙钟时间膨胀到不可用于性能判断的量级，而插桩版本通常还要再慢一个数量级，且改变了寄存器压力与调度。因此 agent 的 profile 策略必须是“先粗后细、按需升级”，把昂贵的可见度留给已经确认的瓶颈假设。

一个具体机制：NCU 的 warp stall 采样以固定周期对每个调度器上的 warp 状态打点，输出的是“采样落在某个 stall reason 上的比例”，不是精确周期数。这意味着小 kernel 或短命 kernel 的采样量不足以稳定区分 stall_long_scoreboard 与 stall_short_scoreboard；agent 若直接读百分比做归因，会把噪声当信号。工程上的做法是要求 profile 文本自带采样充分性判据（采样数、覆盖 warp 数、kernel 持续时间），不满足就拒绝下结论，转而用 roofline 的粗粒度判据先定位是带宽受限还是计算受限。

$$\text{Arithmetic Intensity}=\frac{\text{FLOPs}}{\text{Bytes Moved}},\qquad \text{Attainable}=\min\left(\text{Peak}_{\text{compute}},\ \text{AI}\times\text{BW}_{\text{mem}}\right)$$

roofline 的价值不在画出那条折线，而在给 agent 一个可反驳的假设：若实测吞吐显著低于 Attainable，则问题不在“算术强度不够”而在实现层面（占用率、访存合并、指令混合）；若实测贴着内存斜线，则任何指令级微调都是徒劳，必须改数据复用。代价是 roofline 需要准确的 FLOPs 与字节数口径——这两个数若由 agent 自己估算，误差会直接污染结论，因此本卷要求 profile 样本里必须记录口径来源（是否来自算子语义推导、是否含中间张量回写），否则该样本不进 SFT。

例子：一个归约类 kernel 实测带宽只有峰值的四成，NCU 显示 stall_long_scoreboard 占比最高。agent 的第一反应是“增加 ILP、展开循环”，但 roofline 口径显示该 kernel 的 AI 极低、必然带宽受限，真正的问题是每个线程的访存步长导致 sector 利用率不足。这个反例说明：没有 roofline 约束的 stall 归因会把 agent 引向错误的优化方向，而这类“错误归因—错误修复”的轨迹恰恰是负例数据的富矿。

二 · SASS 是唯一不会撒谎的层：source 与二进制的对齐

CUDA C++ 或 Triton 源码里的循环、分支、向量化意图，在 SASS 里可能完全变形：编译器会重排、谓词化、把循环展开成软件流水、把 shared memory 访问拆成多拍。Agent 若只看源码做优化，等于在猜测编译器。要让 agent“看见”真实指令流，必须提供 source 行与 SASS 指令的对应关系，以及每条指令的发射与停顿归属。这层信息的关键机制是行号映射表：编译器在生成 SASS 时保留源码行归属，NCU 据此把每条指令的采样归到源码行，agent 才能说“这一行的 LDG 造成了长停顿”而不是“这个循环有问题”。

代价有两面。其一，-lineinfo 与优化等级存在张力：高优化等级下指令被重排到与源码行语义不再一一对应的程度，映射表会给出误导性的行归属；其二，SASS 文本本身是 token 密集的，一个中等 kernel 的 SASS 动辄数百到上千行，把整份 SASS 塞进上下文会挤掉正确性信息与任务描述。工程判断是：SASS 只按“热点行窗口”切片进入上下文——以 stall 采样最高的若干源码行为锚，取其前后固定条数的 SASS 指令，附带该窗口的指令混合统计（访存指令占比、双发射机会、谓词寄存器压力）。这样每次注入的 token 量可控，且信息与假设直接挂钩。

一个具体例子：Triton 生成的 kernel 在 SASS 层出现大量 LDS/STS 往返，源码里看不到显式的 shared memory 使用——这是 layout 转换被 lowering 出来的结果。Agent 若只读 Triton IR 会误判为“无 shared 争用”，而 SASS 窗口直接暴露了 bank 冲突的指令模式。这类“源码不可见、SASS 可见”的现象是 profile 解释类 SFT 样本的核心题材：样本的输入是切片后的 SASS 与 stall 统计，输出是对 lowering 行为的解释与可执行的改写建议（例如调整 block 内线程排布以改变 swizzle）。

正确性代价同样存在：任何基于 SASS 的改写建议都必须回到 oracle 验证，因为指令级重排可能改变浮点结合顺序，在容差边缘的算子上翻转结果。因此本卷规定，SASS 驱动的优化轨迹在进入偏好对之前，必须携带“改写后正确性仍通过”的标记，否则只能作为失败负例。

三 · 二进制插桩：把“采样”换成“计数”的代价

当 stall 采样不足以区分两个相邻的假设时，agent 需要精确计数：某条指令被执行了多少次、每次等待了多少周期、某个分支被走过了几成。这需要二进制插桩——在编译产物中插入计数器读写，或使用硬件支持的精确 trap。机制上，插桩点会引入额外的寄存器与指令，改变 occupancy 与指令调度，因此插桩版本的性能数字不可用于绝对性能判断，只能用于相对归因：比较同一 kernel 插桩前后各条指令的计数比例，推断真实执行路径。

代价结构很明确：插桩使 kernel 墙钟时间上升，且寄存器压力上升可能导致 occupancy 掉档，进而让原本隐藏的长延迟暴露出来——也就是说插桩本身会制造它想测量的现象。工程上的缓解是“最小插桩集”：只对候选热点窗口插桩，且插桩后必须重跑一次不插桩版本以确认 occupancy 未变。若 occupancy 变了，该次插桩数据降级为定性参考，不进入训练样本的定量字段。

一个具体例子：agent 怀疑某分支导致 warp 发散，但采样数据显示两种 stall reason 接近。插桩在该分支两侧各埋一个计数器，得到“该分支被 3/4 的 warp 走过、其中一半走的是短路径”的精确分布，从而确认发散假设。代价是该 kernel 的插桩版本执行时间显著拉长，且编译时间因插桩 pass 增加。这条轨迹进入 SFT 时，输入是“采样不可分辨”的困境描述与插桩方案，输出是插桩点的选择理由与对 occupancy 影响的检查步骤——教给模型的是何时值得付插桩的代价，而不是插桩本身。

插桩还有一层与评测可信度的耦合：插桩改变了二进制，因此任何基于插桩版本的性能数字都不能写进基准成绩，只能写进 profile 解释字段。本卷的数据清洗规则据此把“插桩版本性能”与“原始版本性能”分列，禁止混用，防止 agent 学到“插桩后的数字就是成绩”的错误关联。

四 · 让 agent 看见时间：profile 文本的结构化契约

原始 NCU 输出是给人看的表格与告警，直接喂给模型会浪费大量 token 在格式噪声上。本卷要求 profile 文本经过结构化契约转换：固定字段（kernel 标识、网格与块配置、持续时间、采样充分性、occupancy 实际值与理论上限、各 stall reason 占比、DRAM/L2/shared 吞吐与峰值比、roofline 口径与可达上限、热点源码行窗口及其 SASS 切片）。契约的作用是让 agent 的推理有稳定锚点，也让 SFT 样本的字段可对齐、可去重、可版本化。

代价是转换层本身的维护成本与信息损失：结构化会丢掉一些边缘告警（例如非预期的 L2 命中率异常），而这些恰恰可能是新瓶颈的信号。折中方案是保留一个“异常摘要”字段，只写与契约字段偏离阈值的事实，不写解释。这样 agent 拿到的是“事实 + 偏离”，解释留给模型生成——这正是 profile 解释类 SFT 样本要训练的能力。

一个具体机制：契约里必须区分测量值与推导值。occupancy 实际值来自运行时，理论上限来自编译产物的寄存器与 shared 用量，两者不一致时 agent 应优先怀疑 launch 配置而非 kernel 代码。这个区分是防止 agent 把“我算出来的上限”当成“机器告诉我的事实”的关键护栏。公式上，occupancy 受限于三个约束的最小值：

$$\text{Occ}=\min\left(\frac{R_{\text{reg}}}{R_{\text{per-thread}}\cdot T},\ \frac{S_{\text{smem}}}{S_{\text{per-block}}},\ \frac{W_{\text{max}}}{W_{\text{per-block}}}\right)$$

例子：agent 收到一份 profile，实测 occupancy 低于其按寄存器数推导的上限，于是它没有去改代码，而是先检查 launch 的 block 数是否小于 SM 数乘以每 SM 可容纳块数——这是一个“读契约字段就能排除”的错误方向。这类样本训练的是先排除配置层、再动代码层的排查次序，而不是具体的优化技巧。

五 · 反馈的预算与升级策略：agent 何时该花一次昂贵采集

Profile 不是免费的上下文：一次完整采集的时延、一次插桩的编译时间、一份 SASS 切片的 token 占用，都是 agent 回合预算里的硬成本。因此 agent 需要一条升级策略：默认只用 roofline 粗判据与轻量计数；当且仅当粗判据给出“实测显著低于可达上限”且 stall 采样充分时，才升级到 SASS 窗口；当且仅当两个候选假设在采样层面不可分辨时，才升级到插桩。每次升级都必须记录“为什么上一层的证据不足”，这条记录本身就是高价值的 SFT 样本——它教模型的是证据充分性的判断，而非工具调用格式。

代价的量化方式：把 profile 预算折算成回合数与 token 数，与正确性验证预算并列。工程判断是，优化回合里 profile 的 token 占比应有上限，超过则强制 agent 先提交一个可验证的改写再继续采集——防止 agent 陷入“无限采集、从不改写”的惰性循环。这个上限的具体数值属于配置项，本卷不给定数字，但要求数据资产里记录每次轨迹的 profile token 占比，供后续配比决策使用。

一个具体例子：agent 连续三轮采集 NCU 却未提交任何代码改动，轨迹被清洗规则判为“无产出采集”并降权。与之对照，另一条轨迹在首轮 roofline 判定带宽受限后直接改写访存模式、一次通过正确性、二次采集确认吞吐提升——这条轨迹的 profile 文本量小但信息密度高，成为偏好对中的“快”侧。两类轨迹的差异不在工具使用量，而在采集是否服务于一个可证伪的假设。

还有一层与数据配比的耦合：profile 解释类样本若全部来自“采集充分、结论正确”的成功轨迹，模型会学到“profile 总是干净的”这一错误先验。因此本卷要求负例中保留一定比例的“误读 profile”轨迹——例如把采样噪声当瓶颈、把插桩后的 occupancy 变化当真实退化——并在偏好对中与正确解读配对。这类负例的价值高于普通编译失败负例，因为它训练的是归因纪律。

六 · 从 profile 文本到可训练资产：字段、版本与隔离

Profile 文本进入 SFT 还是仅进 RL 上下文，是本卷的关键决策之一。判断依据是该文本是否承载可迁移的归因能力：若一段 profile 的解释依赖具体 kernel 的语义细节（例如某个算子的 tile 形状），它更适合作为 RL 上下文中的即时证据，让模型在交互中学习使用；若解释展示的是跨 kernel 通用的排查次序（先配置层、再访存层、再指令层），则应提炼为 SFT 样本。两者的边界不是文本长度，而是结论的可迁移性。

版本对齐是另一道硬约束：profile 文本必须绑定产生它的代码版本、编译选项与基准版本。同一 kernel 在不同编译选项下的 SASS 与 stall 分布可以完全不同，若版本字段缺失，样本会在去重时被误判为重复，或在训练时教出对编译选项不敏感的错觉。本卷的去重规则因此以“代码哈希 + 编译选项 + 基准版本”为键，profile 字段作为载荷而非键的一部分。

一个具体机制：profile 解释类样本的构造采用“证据—假设—动作—复核”四段式。证据段是结构化契约字段与 SASS 切片；假设段是可证伪的一句话（例如“瓶颈在 shared bank 冲突而非 DRAM 带宽”）；动作段是改写及其代价预估；复核段是改写后的正确性结果与二次采集的关键字段对比。四段式的价值在于它把“解释”变成可审计的推理链，任何一段缺失的样本在清洗时被降级为不完整样本，不进入冷启动数据集。

代价落在数据容量与隔离上：四段式样本的 token 量显著高于普通代码样本，且 profile 文本与评测集必须隔离——若评测 kernel 的 profile 曾出现在 SFT 中，模型在评测时可能复现记忆而非推理。本卷要求 profile 样本的来源 kernel 与评测集 kernel 在哈希层面不重叠，且同一算子的不同实现视为不同样本，防止通过算子族泄漏。这条隔离规则与去污染规则共享同一套哈希机制，但检查的对象是 profile 载荷而非代码文本。

最后落在工程判断上：硬件反馈的可信度不取决于采集工具的精度，而取决于 agent 是否被训练成“先问证据是否充分、再问结论是否可迁移”。Profile 文本作为数据资产，其真正价值不是教会模型读 NCU 表格，而是把“花一次昂贵采集之前先证明上一层不够用”这一纪律固化进推理链——这正是 RL 冷启动不稳时，回头用清洗后的 SFT 基座稳住下限的那条故事线在数据层的具体落点。
