一 · checker 漏检率：把“通过”从布尔值变成分布

在 kernel 生成流水线里，checker 的输出通常被当成一个布尔量：正确或错误。这个抽象在审计上是危险的，因为任何 checker 都只是真实正确性谓词的一个近似实现，它的错误有两个方向——把错判成对（漏检，false accept）和把对判成错（误杀，false reject）。对 agent 生成的 kernel 而言，前者直接污染奖励信号：一个数值上偏离但恰好落在 checker 容差内的 kernel 会被 RL 当成正样本反复强化，最终把整个策略推向“擅长骗过 checker”而不是“擅长算对”。因此审计的第一件事是把 checker 当作被测对象，量化它的漏检率。

具体机制是构造“已知错误”的变异体集合。给定一个参考 kernel K，用一组语义保持或语义破坏的变换生成 {K'_i}，其中每个 K'_i 的正确输出可以由 CPU 参考实现精确给出，于是我们能标注每个变异体“应当被拒绝”。checker C 的漏检率定义为：

$$\mathrm{FAR}(C)=\frac{|\{i: C(K'_i)=\text{accept} \land K'_i \text{ 语义已破坏}\}|}{|\{i: K'_i \text{ 语义已破坏}\}|}$$

与之配对的是误杀率 FRR，用语义保持变异体（如等价重写、循环展开、改变分块但不改变数学）来测。两个数字必须一起报，因为收紧容差会同时压低 FAR、抬高 FRR，只报一个等于隐藏了工作点。代价在这里非常具体：变异体数量 N 直接乘以单次 checker 运行的时延（含 kernel 编译 + 多次重复执行 + 与参考比对），一个含 200 个变异体、每个变异体编译约数秒、执行毫秒级的审计循环，其墙钟时间由编译主导而非执行主导——这正是后面要谈的编译预算问题。举例：一个把 __syncthreads() 从循环体内移到循环外的变异体，在多数输入下数值完全一致，只在跨 warp 依赖的边界 tile 上出错；若 checker 只跑固定随机种子的小规模输入，这个变异体几乎必然被漏检，而它恰恰是 shared memory 分块类 kernel 最典型的错误形态。

二 · 变异测试：让“正确”具备杀伤力

变异测试的价值不在于覆盖率数字，而在于它把 checker 的判别力变成可比较的量。工程上要区分两类变异算子。第一类是语义破坏型：改边界条件（off-by-one）、删同步、把 shared memory 写入的 bank 映射打乱、把归约初值从 0 改成 1、把 float 累加顺序反转以放大舍入误差。第二类是语义保持型：把 a*b+c 改成 fma(a,b,c)、把循环拆分、把 tile 大小从 32 改成 64 但保持总工作量。前者测 FAR，后者测 FRR，且后者还能顺带暴露 checker 对浮点非结合性的过度敏感。

一个可操作的判据是“变异体杀伤率” MS：被 checker 正确拒绝的语义破坏型变异体占全部语义破坏型变异体的比例。审计要求不是 MS 越高越好，而是 MS 必须对每一类变异算子分别达标，因为平均 MS 会被容易检测的算子（如把加法写成减法）拉高，掩盖掉难检测的算子（如竞态、未定义行为、非确定性）。表格给出一个审计矩阵的组织方式：

变异算子语义期望 checker 行为主要代价
删同步破坏拒绝需构造跨 warp 依赖输入，执行次数上升
边界偏移破坏拒绝需覆盖 tile 边界尺寸，输入集合膨胀
FMA 重写保持接受暴露容差过紧导致的误杀
分块重排保持接受编译时间随变体数线性增长

注意“删同步”这一行的代价：它不是靠增加输入规模能解决的，而是要靠输入形状的针对性——必须让数据规模刚好跨越一个 block 的边界，使缺失的同步真正产生可见的数值差异。这意味着变异测试的输入生成器本身要有结构感知，而不是均匀随机。工程判断上，若某类变异算子的杀伤率长期为零，优先怀疑的不是 checker 的容差，而是输入生成器没有触及该类错误的状态空间。

三 · fuzz：把输入空间当作被审计对象

变异测试审计的是“实现错误”，fuzz 审计的是“输入触发的错误”。对 GPU kernel，fuzz 有三个不同于 CPU 的约束。其一，输入形状必须满足 kernel 的 launch 配置约束（对齐、tile 整除、shared memory 容量上限），纯随机形状大量落在非法配置上，浪费编译与执行预算。其二，浮点比较需要相对容差而非绝对容差，且容差应随归约长度增长，否则长归约的合法舍入误差会被误判。其三，非确定性 kernel（原子加、并行归约）需要多次重复执行取统计量，单次比对没有意义。

一个结构感知的 fuzz 循环可以写成：从形状分布中采样 s，按对齐与 tile 约束做投影得到合法形状 s'，用参考实现算期望输出，运行被测 kernel R 次，对每次输出计算与期望的最大相对偏差，若任一超过阈值则判错。伪代码思路：

$$\text{for } s \sim \mathcal{D}:\; s'=\mathrm{proj}(s);\; e=\mathrm{ref}(s');\; \text{for } r \text{ in } 1..R:\; \delta_r=\max_j \frac{|y_{r,j}-e_j|}{\max(|e_j|,\epsilon)};\; \text{reject if } \max_r \delta_r > \tau(s')$$

代价是三重乘积：形状采样数 × 重复次数 R × 单次执行时延，再叠加每个新形状可能触发的重新编译（若 kernel 对形状做了模板特化，形状变化即编译变化）。在审计预算有限时，正确的取舍是把 R 留给非确定性 kernel、把形状预算留给边界形状（tile 边界、非整除尾块、极窄/极宽矩阵），而不是均匀铺开。举例：一个 reduction kernel 在 N 恰为 block 尺寸整数倍时完全正确，在 N 多出 1 个元素时因尾块未初始化而读入脏 shared memory；只有形状投影刻意保留“整除 + 1”这一类，fuzz 才能稳定命中。

四 · 形式验证与合约验证：把正确性写成可判定的命题

fuzz 与变异测试都是采样式的，它们能提高置信度但不能给出证明。形式验证在 kernel 上的现实切入点不是“证明整个 kernel 等于参考实现”，而是分层：对索引算术、边界谓词、同步可达性做可判定的检查；对数值部分保留采样式 oracle。合约验证是这条路径的工程化形态——在 kernel 入口与关键循环处写前置/后置条件（如“所有 shared memory 读之前必有一次覆盖写”“tile 索引恒在界内”），用静态分析或符号执行检查这些条件。

可判定的部分值得投入，因为它们的漏检率为零（在模型正确的前提下）。以 bank conflict 与越界为例，索引表达式是关于线程号与 tile 号的整数函数，可以在有界域上做精确枚举或 SMT 求解：

$$\forall t\in[0,T),\;\forall b\in[0,B):\; 0 \le \mathrm{idx}(t,b) < N \;\land\; \mathrm{bank}(\mathrm{idx}(t,b)) \text{ 在 warp 内互异}$$

这条公式同时覆盖正确性（越界）与性能（bank conflict），是把硬件反馈前置到编译期的一种方式。代价是状态空间：T×B 的全枚举在 tile 较大时不可行，必须依赖 SMT 的剪枝，而 SMT 求解时间对表达式非线性（如含乘除与取模的索引）非常敏感，可能从毫秒级跳到分钟级，成为审计流水线的新瓶颈。工程判断是：把形式检查限制在“索引与同步”这一层，把数值等价留给采样 oracle，不要试图用 SMT 证明浮点归约的位级等价——浮点非结合性会让这类证明要么不可判定，要么需要引入误差界公理，反而削弱结论的可信度。合约验证的具体收益在于它能在没有参考实现的情况下工作：当参考实现本身是 agent 生成的、可信度存疑时，合约是独立于参考的第二信源。

五 · 证明“正确”的工程判据：分层置信与代价核算

把上述手段拼成一个可辩护的结论，需要明确“正确”是一个分层命题而非单一断言。第一层是接口正确：形状、dtype、launch 配置合法，由合约检查覆盖，代价接近零。第二层是索引与同步正确：由形式枚举或 SMT 覆盖，代价是求解时间，收益是零漏检。第三层是数值正确：由 fuzz 与变异测试覆盖，代价是编译与执行预算，收益是统计置信度而非证明。第四层是非确定性正确：由重复执行与统计检验覆盖，代价随 R 线性增长。审计报告应当按层给出结论，而不是给一个总体的“通过”。

代价核算必须显式。设审计总预算为墙钟时间 W，则 W 被分解为编译时间、执行时间、求解时间三部分，其中编译时间在变异体与形状特化场景下通常是主导项。一个常见的失衡是：为了压低 FAR 而把变异体数量翻倍，结果编译时间吃掉了本可用于 fuzz 形状覆盖的预算，总体漏检率反而上升。正确的做法是先测出编译时间在 W 中的占比，若超过一半，优先做编译缓存（相同形状与模板参数的变异体共享编译产物）而不是继续加变异体。

最后落到一个具体的工程判断：checker 的可信度不能被“它通过了我们的测试集”这句话承载，而要被三个可复现的数字承载——分类别的变异体杀伤率、边界形状上的 fuzz 命中率、形式检查覆盖的索引与同步断言比例。当 agent 在 RL 中反复提交“通过 checker”的 kernel 时，审计系统应当能回答：这个通过是在哪一层成立的，哪一层的漏检率是多少，以及为了得到这个通过付出了多少编译与执行预算。只有这三者同时可见，“正确”才是一个可审计的量，而不是奖励信号里的一个比特。

当 checker 本身成为被测对象：审计的边界与代价

把「正确」交给 checker，等于把一个全称命题降级成有限次采样：checker 通过只说明在它枚举的输入集合上无差异，而不说明 kernel 在未枚举处正确。因此审计的第一件事是把 checker 当作被测系统，量化它的漏检率而非它的通过率。具体机制是变异测试：对参考实现注入语义保持或语义破坏的变异体（边界索引 ±1、dtype 提升截断、mask 条件取反、归约初值错误、shared memory 分块边界漏掉尾块），每个变异体必须被 checker 判死；存活变异体即为 checker 的盲区。漏检率可写成

$$\text{escape rate}=\frac{|\{m\in M:\ \text{checker}(K_m)=\text{pass}\}|}{|M|}$$

其中 $M$ 是变异体集合，$K_m$ 是注入变异 $m$ 后的 kernel。代价是双向的：变异体越多，审计越可信，但每个变异体都要编译并跑一遍计时与比对，编译时间与 GPU 时延随 $|M|$ 线性增长；在 agent 多轮 RL 里若把变异测试放进奖励回路，单条 rollout 的 token 与 wall-clock 预算会被审计吃掉，因此工程上通常把变异集裁剪到「历史上真实出现过的错误模式」这一小撮高价值变异体，其余靠离线批量审计。

checker 的典型失效条件有四类，且都与本卷的硬件反馈通道耦合。其一是容差与数值路径不匹配：kernel 走 TF32 或 fp16 累加、参考实现走 fp64，绝对误差阈值设得过松会放过真实的精度退化，过紧则把合法优化判死；正确做法是把容差绑定到 dtype 与累加顺序，而不是一个全局常数。其二是形状覆盖偏差：checker 只测 2 的幂、对齐的 shape，而 kernel 的尾块处理、非对齐访存、bank conflict 恰恰只在非对齐 shape 上暴露，这类漏检不会在 NCU 的 occupancy 或 memory throughput 上留下痕迹，只能靠 fuzz 生成器补。其三是别名与并发：原地操作、跨 stream 复用 buffer、缺少 `__syncthreads()` 的竞态，在单次串行比对下不可见，需要重复运行与不同 launch 配置下的差分。其四是 NaN/Inf 与次正规数被比对逻辑静默跳过。fuzz 的机制是带约束的随机 shape/dtype/stride 生成加差分测试，代价是覆盖率增长边际递减，且每个随机样本都要付出一次参考实现的前向时延——参考实现往往比 kernel 慢一个量级，fuzz 的预算瓶颈通常在参考侧而非被测侧。

形式验证与合约验证补的是采样覆盖不到的部分，但边界很硬。合约验证的思路是在 kernel 入口与出口写断言（索引在界内、shared memory 分块覆盖完整、归约结果满足结合律前提、无数据竞争），把「正确」拆成可局部检查的前置/后置条件；它便宜、可嵌进 CI，但只能证明合约写了的那部分，合约本身写错则一切作废。形式验证（如对索引映射与分块不变式做 SMT 求解）能给出无采样盲区的证明，代价是状态空间随线程数、分块尺寸、循环边界爆炸，实际只能覆盖小参数实例，且对 CuTe/PTX 级手写代码的建模成本极高。于是工程判断落在分层：变异测试定漏检率上限，fuzz 定形状与数值覆盖面，合约断言守住每次 launch 的局部不变式，形式验证只用于索引映射这类小状态空间的核心不变式；四者叠加后的残余风险必须显式记录，而不是用一句「checker 通过」抹平。这也解释了为什么 agent 首次看懂 NCU stall 报告并自主改 shared memory 分块时，正确性 oracle 必须同步升级——分块边界改变正是尾块漏检的高发区，性能跃迁与漏检风险在同一处发生。
