一 · 开场：一次精度事故把“能跑”变成“可运营”

设想一个已经上线的推理服务：某层 attention 的 fused kernel 在灰度环境里跑得好好的，吞吐和延迟都在预算内，于是按版本推进到全量。三天后，监控面板上出现一条不和谐的曲线——该服务的输出分布尾部开始偏移，离线评测集上的 BLEU 类指标没有明显变化，但线上业务侧的重排模型开始报“候选集打分异常”。值班工程师第一反应是回滚模型权重，第二反应是怀疑上游数据管道，第三反应才想到 kernel。等到定位到 kernel，已经过去了数小时；而真正的问题不是“kernel 坏了”，而是“没有人能在十分钟内回答这个 kernel 是哪个版本、用了哪套编译配置、在哪些卡型上跑、和上一版比数值偏差是多少”。

这个场景是本卷的起点。第 9 卷交付的是灰度与生产数据：哪些 kernel 上了线、在什么流量下跑、端到端收益是多少。第 3 卷交付的是失败分类：编译失败、数值错误、性能不达标、集成不兼容，各有各的形态。第 4 卷交付的是审计规则：正确性 oracle 怎么构造、形式化检查覆盖哪些边界。这三样东西放在一起，能回答“这个 kernel 对不对、快不快”，却回答不了“它现在在线上是什么状态、变了没有、变坏了没有、坏了之后谁来修、修完怎么证明修好了”。本卷要补的就是这一段：把一次性的评测结论，变成持续可观测、可归因、可回滚、可复盘的生产资产。

换句话说，前几卷解决的是“生成与验证”，本卷解决的是“运营与信任”。一个 kernel 通过 KernelBench 系基准、通过 NCU/SASS profile 的 roofline 检查、通过多轮 RL 的奖励筛选，只说明它在受控条件下成立；它是否在真实流量、真实卡型组合、真实编译工具链下持续成立，是另一个问题。本卷的赌注是：可靠性不是评测的附属品，而是独立的一层工程，它有自己的数据结构（版本与配置追踪）、自己的信号（数值异常与性能回退告警）、自己的推理结构（失败归因树）和自己的决策口径（采样率、阈值、回滚策略、双口径 BI）。

二 · 上一卷留下的三个缺口

第 9 卷把 kernel 送进了生产，但它留下的是“结果”，不是“过程”。具体说，有三个缺口在本卷必须被填上。

第一个缺口是版本与配置的可追溯性。生产环境里的一个 kernel 不是一个 .cu 文件，而是一个五元组：源码 commit、编译选项（arch、`-O` 级别、是否开 fast math、CuTe/PTX 内联片段）、运行时配置（block/grid、shared memory 用量、是否启用 TMA）、部署卡型、以及它被哪个模型版本调用。第 9 卷的灰度数据记录了“哪个版本上了线”，但没有把上述五元组结构化。结果是，当数值异常出现时，团队无法做差分：不知道是源码变了、编译选项变了、还是卡型组合变了。本卷要求把每一次 kernel 发布登记为一个不可变的配置指纹，任何一次告警都能反查到指纹，任何两个指纹之间都能做逐项 diff。

第二个缺口是失败的可归因性。第 3 卷的失败分类是离线评测语境下的分类：编译不过、数值不对、性能不达标、集成失败。线上失败的表现形态不同——它往往不表现为“报错”，而表现为“指标漂移”。一个数值精度事故可能只让某一类输入的输出偏差扩大，而不触发任何断言；一个性能回退可能只在特定 batch 形状下出现，平均吞吐看不出来。因此本卷需要一棵归因树，把“线上症状”映射回“离线分类”，并且这棵树必须是可执行的判定流程，而不是一张分类表。

第三个缺口是决策口径。第 4 卷的审计规则回答“是否通过”，是一个二值判断；生产运营需要的是连续判断：采样多少、阈值定在哪、超了之后自动回滚还是人工确认、给团队看的指标和给管理层看的指标是否同一套。这些决策没有唯一正确答案，但必须有明确记录，否则每次事故都会重新吵一遍。

这三个缺口共同指向一个事实：评测的可信度是“点”上的，运营的可信度是“线”上的。点上的正确不能自动累加为线上的稳定，因为线上多了三个维度——时间（版本演化）、异构（卡型与形状组合）、流量（分布漂移）。本卷的全部机制都是围绕这三个维度展开的。

三 · 本卷的赌注：把可靠性做成可计算的对象

本卷的核心赌注可以写成一句话：把“这个 kernel 可靠吗”从一个主观判断，变成一个由可观测信号、归因规则和阈值策略共同定义的可计算对象。这个赌注有代价，也有边界。

先看代价。任何线上监控都不是免费的。对 kernel 做数值异常检测，最直接的办法是在关键输出上挂采样比对：以采样率 s 抽取请求，用高精度参考实现（或上一稳定版本的输出）做逐元素比对，计算相对误差并判定是否超过容差。这个机制的代价可以写成：

$$ C_{\text{monitor}} = s \cdot N \cdot \left( t_{\text{ref}} + t_{\text{cmp}} \right) + B_{\text{log}} $$

其中 N 是单位时间请求数，t_ref 是参考路径的单次开销，t_cmp 是比对开销，B_log 是日志与上报带宽。参考路径通常是慢路径（FP64 或未融合实现），t_ref 往往是被监控 kernel 的数倍到数十倍，因此 s 不能大。采样率的选择因此是一个显式的工程决策：s 太高会吃掉服务延迟预算，s 太低会漏掉低频但高危害的精度事故。本卷要求把这个决策写进配置，而不是留在工程师的直觉里。

再看边界。可靠性体系能覆盖的是“可观测的失败”，它不能替代形式验证。第 4 卷的形式审计能证明某些边界条件下无溢出、无越界；本卷的告警只能告诉你“线上出现了偏差”。两者是互补的：形式审计缩小了需要监控的空间，监控覆盖了形式审计没有建模的输入分布。这个分工必须写清楚，否则团队会误以为“有告警就等于有保证”。

赌注的另一半是归因树。归因树不是分类表，而是一组有序判定：给定一个线上症状（例如“某服务 P99 延迟上升且输出偏差扩大”），依次检查编译指纹是否变化、数值比对是否超容差、profile 指标（occupancy、DRAM 吞吐、SOL 利用率）是否偏离基线、集成侧调用形状是否变化。每一步判定都有明确的输入和输出，最终落到第 3 卷的四个失败类别之一。这个结构的价值在于它把“救火”变成了“按图排查”：值班工程师不需要重新发明排查顺序，只需要沿着树走。代价是树本身需要维护——每出现一种新症状，就要决定它挂在哪个节点下，这是一项持续的工程投入。

具体例子：某 fused softmax kernel 在 H 卡上数值正常，在另一类卡上因为 `exp` 实现的差异导致尾部概率出现系统性偏移。归因树的第一层“编译指纹 diff”会发现两张卡的 arch 编译选项不同，第二层“数值比对”确认偏差只在特定卡型上出现，第三层“profile”显示 occupancy 正常、无性能回退。结论直接落到“数值/编译配置”分支，而不是让团队去查数据管道。这个例子的要点不是某张卡，而是：归因树把“卡型差异”这种异构维度变成了一个可判定的分支。

四 · 可靠性体系的四个构件与它们的耦合

本卷的产出由四个构件组成，它们不是并列的模块，而是有数据流耦合的一条链。

第一个构件是版本与配置追踪。它把每次 kernel 发布登记为不可变指纹，指纹包含源码 commit、编译选项、运行时配置、卡型、调用方模型版本。它是整条链的地基：没有指纹，告警无法定位到具体对象，归因树的第一层判定无从做起，回滚也没有明确的回滚目标。代价是存储与查询开销——指纹数量随发布次数线性增长，diff 查询需要索引；工程上通常用“指纹 ID + 结构化字段”的窄表，而不是把整个编译产物入库。

第二个构件是数值异常与性能回退告警。它消费指纹，对每个活跃指纹维护两条基线：数值基线（参考实现的输出分布或上一稳定版本的比对统计）和性能基线（延迟、吞吐、SOL 利用率的分布）。告警的触发条件是偏离基线超过阈值。这里的核心决策是阈值口径：按均值还是按分位数。均值对长尾不敏感，一次只影响少量请求的精度事故可能被平均掉；分位数（如 P99 偏差）能捕捉尾部，但对采样噪声更敏感。本卷的处理是把两类指标分开：性能回退看分位数（因为延迟的长尾直接对应用户体验），数值偏差看超容差请求的比例（因为精度事故的危害与受影响请求比例相关）。

第三个构件是失败归因树。它消费告警，输出归因结论。树的每个节点是一个判定，判定所需的数据来自前两个构件和第 4 卷的审计记录。树的叶子是第 3 卷的四个失败类别加上一个“未知”类别——“未知”不是失败，而是树需要扩展的信号。代价是判定时延：一次完整的树遍历需要拉取指纹 diff、数值比对样本、profile 快照，这些数据的聚合时间决定了从告警到结论的时延。工程上要求关键路径上的判定数据预先物化，避免告警时现算。

第四个构件是质量 BI 看板与事故复盘模板。看板消费前三个构件的输出，呈现成功率、加速比分布、SOL 分布、回退率。复盘模板则把一次事故的归因结论、时间线、决策点固化成文档结构。这两个构件看似“展示层”，实际上承担了决策口径的落地：看板对团队和对管理层用两套口径，复盘模板强制记录阈值与回滚决策的理由。代价是口径分裂带来的沟通成本——两套口径必须能互相映射，否则管理层看到的“稳定”和团队看到的“回退率上升”会互相矛盾。

构件输入输出主要代价
版本与配置追踪发布事件、编译选项、卡型不可变指纹、diff存储与索引开销
异常与回退告警指纹、采样比对、profile告警事件采样开销、误报/漏报
失败归因树告警、审计记录、基线归因结论判定时延、树维护
BI 看板与复盘前三者输出双口径指标、复盘文档口径映射成本

四个构件的耦合点是指纹：告警以指纹为键，归因以指纹 diff 为第一判定，回滚以指纹为目标，BI 以指纹为聚合维度。这个设计选择意味着，如果指纹登记不完整，整条链的可信度都会下降。因此本卷把“指纹完整性”当作一个硬性工程约束，而不是可选的元数据。

五 · 从救火到可运营：归因树如何改变值班行为

回到开场的精度事故。在没有归因树的情况下，值班行为是串行猜测：先怀疑模型，再怀疑数据，最后才怀疑 kernel；每一次怀疑都伴随着一次不必要的回滚或重跑，时间被消耗在排除法上。有了归因树，行为变成并行取证：指纹 diff 立刻回答“变没变”，数值比对回答“偏没偏”，profile 回答“慢没慢”，三者合起来把搜索空间从“整个系统”压缩到“一个分支”。

这个转变的实质是把排查顺序从个人经验变成组织资产。归因树的每个节点都对应一个可复现的判定命令，判定结果被记录进复盘模板。久而久之，树的分支覆盖了历史上出现过的症状类型，新症状要么挂到已有分支下，要么触发树扩展。这就是“可运营”的含义：不是没有事故，而是每次事故都让系统更可判定。

代价同样明确。归因树的判定依赖基线，而基线会随流量分布漂移而过期。一个在灰度流量下建立的数值基线，在全量流量下可能因为输入分布变化而误报。因此基线需要定期重估，重估本身消耗工程时间；如果重估太频繁，告警会失去稳定性，如果太慢，误报会侵蚀团队对告警的信任。本卷把这个权衡写成显式的基线生命周期策略，而不是让它隐式发生。

另一个代价是自动回滚的决策。归因树给出结论后，是否自动回滚是一个独立决策：自动回滚快，但可能因为误报而回滚一个实际上更好的版本；人工确认慢，但保留了判断余地。本卷不预设答案，而是要求把决策条件写进配置——例如“数值偏差超容差且指纹 diff 显示编译选项变化”走自动回滚，“性能回退但数值正常”走人工确认。这个条件表本身就是可靠性体系的一部分。

具体例子：一次性能回退告警，归因树判定为“运行时配置变化导致 occupancy 下降”，而非源码问题。自动回滚策略如果只看“性能回退”就触发，会回滚掉一个同时修复了数值问题的版本；条件表则要求先看数值分支是否干净，再决定回滚目标。这个例子的要点是：归因结论必须参与回滚决策，否则回滚会变成另一种形式的猜测。

六 · 本卷的读者位置与判断标准

对本卷的读者——有工程背景、正在把 kernel 生成推向生产的中文团队——需要明确一件事：本卷不提供“最佳实践清单”，它提供的是一组必须显式做出的决策，以及每个决策的代价结构。采样率、阈值口径、回滚策略、双口径 BI，这四个决策没有普适最优解，但它们有共同的判断标准：每个决策都必须能回答“这个信号从哪里来、它的开销是多少、它错了之后谁来承担”。

这条判断标准可以直接用来检验一个团队的可靠性体系是否成立。如果一个告警无法反查到指纹，它的信号来源就是断的；如果一个阈值没有记录口径（均值还是分位数），它的开销结构就是不清的；如果一次回滚没有归因结论支撑，它的错误成本就是无人承担的。本卷后续部分会逐项展开这四个决策的机制与代价，但它们的共同骨架在这里已经给出：指纹是键，告警是信号，归因树是推理，BI 与复盘是决策的固化。

最后落在一个具体的工程判断上：可靠性体系的建设顺序应该是先指纹、后告警、再归因、最后 BI。原因是数据流的依赖方向——没有指纹，告警无法定位；没有告警，归因树没有输入；没有归因结论，BI 看板上的数字无法解释。反过来做，会得到一个能展示但不能排查的看板，那正是本卷要避免的形态。这个顺序判断不是理论推导，而是由四个构件的耦合结构直接决定的：指纹是唯一的跨构件键，它必须先立起来。
