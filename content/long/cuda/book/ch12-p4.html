一 · 漏检率是 checker 的一等指标

路线图里最容易写坏的一条，是把“正确性”写成一个布尔门禁：checker 通过即发布。工程上真正要固化进治理规则的，是 checker 自身的漏检率——即错误 kernel 被判为正确的条件概率。设被测 kernel 集合中真实错误子集为 F，checker 判错为通过的子集为 P，则漏检率定义为 $$\mathrm{FNR}=\frac{|F\cap P|}{|F|}$$ 与之配对的是误杀率 $$\mathrm{FPR}=\frac{|\bar F\cap \bar P|}{|\bar F|}$$ 两者在路线图上的意义不对称：FNR 决定生产事故面，FPR 决定 agent 的探索成本（被误杀的合法优化会浪费多轮 RL 的 token 与编译时间）。因此验收标准不能写“checker 通过率 100%”，而要写“在冻结的变异体集合上 FNR 低于阈值，且 FPR 不高于基线”。

具体机制上，checker 的漏检来自三个可审计的来源：其一，输入分布覆盖不足，只测了基准自带的形状；其二，数值容差过宽，把累积误差当成合法浮点噪声；其三，比较逻辑本身有洞，例如只比较输出的前若干元素、只检查 dtype 不检查 stride、或在 NaN 参与比较时静默通过。第三类最危险，因为它对任何输入都漏检。工程做法是把 checker 拆成“形状/布局断言 + 逐元素数值比较 + 边界语义检查”三段，每段单独统计触发率，任何一段长期零触发就说明它没在工作。

代价方面，收紧容差直接抬高 FPR，进而抬高 agent 的无效迭代：一个被误杀的 Triton kernel 会触发重写、重编译、重测，单轮成本是编译时间加推理 token，多轮累积可观。反过来放宽容差降低 FPR，却把 FNR 推高，事故被推迟到生产端。路线图的治理规则应当明确：容差是受评审的配置项，随 oracle 变更一起走评审流程，不允许 agent 或单个工程师在提交里静默调整。一个具体例子：某 reduction kernel 在基准形状上误差在容差内，但在非 2 的幂长度上出现尾部元素未累加，逐元素比较若只覆盖基准形状就完全漏检——这正是变异测试要补的洞。

二 · 变异测试：给 checker 造已知错误

变异测试把“证明 checker 有效”从口号变成可执行流程：对参考实现施加语义保持或语义破坏的变异，前者应被 checker 判为通过（检验 FPR），后者应被判为失败（检验 FNR）。语义破坏变异要贴着 GPU 的真实失效模式设计，而不是随机改常数。可固化进路线图的变异算子清单包括：去掉边界判断（越界读写）、把同步点删除或前移（race）、把累加初值改错（off-by-one）、把 shared memory 的填充 stride 写反（bank 冲突之外的语义错误）、把 fp32 中间量提前截断为 fp16（精度退化）、把尾块处理循环上界减一（漏算尾部）。

伪代码思路如下：对每个参考 kernel K，生成变异体集合 M(K)，对每个变异体跑完整 checker，记录判定；再对未变异的 K 跑 checker 记录误杀。指标是变异得分 $$\mathrm{MS}=\frac{|\{m\in M(K): \text{checker 判失败}\}|}{|M(K)|}$$ 变异得分低意味着 checker 对该类错误不敏感，必须补测试或补断言，而不是调容差蒙混。工程上要把变异得分按算子类别分桶统计：elementwise、reduction、matmul、attention 的失效模式不同，全局平均分会掩盖某一类的系统性漏检。

代价是变异测试本身的计算开销：每个变异体都要编译并运行，若一个算子有 20 个变异体、每个编译加执行若干秒，单算子审计就是分钟级；放到全基准上就是小时级。因此路线图应把它定位为“oracle 变更时的强制审计”与“季度回归”，而不是每次提交都跑。具体例子：给一个 softmax kernel 注入“减最大值”步骤被删除的变异，checker 若只在数值稳定的输入上测试就会漏检；补上大幅值输入后该变异被稳定捕获，这一条就应写进该算子的验收清单。

三 · Fuzz：把输入空间当成攻击面

变异测试检验 checker 对“已知错误”的敏感度，fuzz 检验它对“未知输入”的鲁棒性。GPU kernel 的输入空间维度包括：形状（含 0、1、非 2 的幂、极大极小）、dtype 与混合精度组合、stride 与内存布局（非连续、转置、广播）、对齐与偏移、以及数值分布（含 inf/NaN/denormal、极端量级）。fuzz 的机制是生成器按这些维度采样，配合差分测试：同一输入分别喂给参考实现与被测 kernel，比较结果；参考实现本身也要有第二实现或高精度实现做交叉校验，否则 fuzz 只是在测两个错误是否一致。

差分测试的判定要处理浮点非确定性：同一 kernel 多次运行结果可能因原子加顺序不同而不同，因此比较必须用容差而非位相等，且容差要随归约长度缩放，例如按 $$\tau = \epsilon\sqrt{n}\,\|x\|_\infty$$ 量级设定，其中 n 为归约元素数。这个缩放关系本身要作为评审对象：容差随 n 增长是合理的，但若实现里写成固定常数，长归约就会系统性漏检。fuzz 还要记录“覆盖到的输入类别”而非仅记录通过率，否则无法判断漏检是 checker 弱还是采样偏。

代价是 fuzz 的算力与时间：大规模形状采样会触发大量编译（Triton 按形状特化，CUDA 模板按 tile 配置实例化），编译时间往往超过执行时间；显存上，极大形状采样可能 OOM，需要采样器带预算控制。路线图的工程判断是：fuzz 语料要版本化冻结，与基准版本一起冻结，保证不同季度的漏检率可比；新增语料走评审，避免“为了让本轮通过而删掉难例”。具体例子：一个 layernorm kernel 在 stride 非连续的输入上读错偏移，基准形状全是连续布局，fuzz 采样到转置输入后差分测试立即暴露，这类语料应固化为该算子的常驻用例。

四 · 形式验证与合约验证：把“正确”写成可检查的命题

对浮点 kernel 做端到端形式验证不现实，但可以对关键不变量做合约验证：在 kernel 入口与出口写断言，把正确性拆成可局部检查的命题。典型合约包括：索引不越界（$$0\le i<N$$ 对所有访问路径成立）、共享内存读写不冲突于同一线程的语义假设、归约结果的单调性界、以及输出与输入的代数关系（如 softmax 输出和为 1 在容差内）。合约验证的机制是在编译期或运行时插入检查，运行时检查的代价是每线程若干次分支与比较，在访存密集 kernel 上可能带来可测的时延上升；编译期检查（如基于符号执行的边界推导）代价是编译时间与工具链复杂度。

形式化程度要按算子分级写进路线图：elementwise 与简单 reduction 可做到索引边界的静态证明；matmul 的 tile 边界可证明但代价高；attention 的数值语义只能做合约断言加差分测试。分级的意义是避免“所有 kernel 都要形式验证”这种无法验收的口号。合约验证的真正价值在于它把 checker 的隐含假设显式化：一旦某条断言在 fuzz 中被触发，说明参考实现或 checker 的假设本身错了，这比漏检一个 kernel 更有信息量。

代价上，运行时断言在生产 kernel 中通常要编译开关关闭，因此合约验证发生在评测阶段而非部署阶段；这带来一个治理问题：评测阶段带断言、部署阶段不带，两者的行为差异必须被审计，否则断言本身可能改变编译器优化（例如阻止向量化），使评测性能不代表生产性能。具体例子：一个带边界断言的 copy kernel 因断言阻止了向量化，评测时延高于生产，若路线图不区分“带断言评测”与“裸评测”两个口径，性能数据就不可比。

五 · 把审计固化进治理规则

上述四类手段要落成组织流程，关键是三条冻结与一条门禁。基准版本冻结：输入语料、参考实现、容差配置一起打版本号，任何变更走评审。oracle 变更评审：checker 逻辑、容差、变异体集合、fuzz 语料的任何修改都必须附上变更前后的 FNR/FPR 与变异得分对比，没有对比不予合并。生产发布门禁：只有通过冻结版 checker 且在该算子类别变异得分达标的前提下才允许进入生产候选。技术债清单则记录“已知漏检类别”与“尚未覆盖的失效模式”，作为下一轮基准升级的输入。

能力矩阵上，oracle 审计能力应单列一行，标注每个算子类别的变异得分、fuzz 覆盖类别数、合约断言条数，以及最近一次审计的时间戳。角色分工上，评测工程师拥有 checker 与语料的变更权，kernel 工程师提供失效模式输入，RL 工程师反馈误杀导致的无效迭代比例——后者是 FPR 的业务侧度量，能把“容差太紧”从主观抱怨变成可排期的数据。路线图按能力排期还是按业务场景排期，在 oracle 这一项上的判断是：审计能力必须按能力排期，因为它是跨场景的地基；而具体算子的合约与变异体可以按业务场景优先级增量补齐。

成本侧要写清审计的预算：变异测试与 fuzz 是季度级算力支出，合约验证是工具链与人力支出，二者都不产生直接吞吐收益，因此在成本容量规划里应作为固定开销而非弹性开销列支。一个具体例子：季度审计发现某类 attention kernel 的变异得分偏低，补入“mask 边界”变异体与对应 fuzz 语料后，该类算子的漏检被收敛，同时 FPR 因容差按归约长度缩放而下降，agent 的无效重写轮次随之减少——这条因果链应作为验收标准的一部分写入里程碑，而不是只写“完成审计”。

最终落在一条工程判断上：证明“正确”不是找到一个万能 oracle，而是维护一个可度量、可评审、可版本化的漏检预算；路线图的治理规则应把 FNR、变异得分与 fuzz 覆盖作为与性能指标同级的发布条件，任何一次 oracle 变更都必须带着这三个数字走评审，否则“正确”就只是当前 checker 的沉默。

Oracle 审计的失效边界与治理成本

路线图把 oracle 变更评审列为治理规则，但评审本身不产生可信度，只有审计证据才产生。checker 的漏检率必须被显式测量：对同一批 kernel，用参考实现与至少一个独立实现（不同分块策略或不同语言后端）交叉判定，凡是两者结论不一致的样本全部进入人工复核队列。漏检率的估计不能只依赖随机抽样，因为错误分布高度长尾——绝大多数错误集中在边界形状、非对齐 stride、极小或极大 problem size 上，均匀抽样会系统性低估。工程上采用分层抽样：按 shape 类别、dtype、是否对齐分桶，每桶独立估计漏检率，再按桶内样本量加权合成总体指标。代价是审计吞吐下降，一个桶若只有几十个样本，其置信区间宽到无法支撑发布门禁，团队要么扩大采样（评测机时与 token 成本上升），要么把该桶标为“未覆盖”并在门禁中显式降级。

$$\hat{L}=\sum_{b}\frac{n_b}{N}\,\hat{L}_b,\qquad \mathrm{Var}(\hat{L})\approx\sum_{b}\left(\frac{n_b}{N}\right)^2\frac{\hat{L}_b(1-\hat{L}_b)}{n_b}$$

变异测试是补漏检率盲区的低成本手段：对参考实现注入语义保持的变异（等价重写）与语义破坏的变异（如把归约初值改错、把 mask 边界偏移一位），前者用于检测 checker 的误报率，后者用于检测漏检率。关键在于变异体必须落在真实 kernel 的失效模式上——把变异算子限制在索引计算、同步点、累加顺序、边界谓词四类，否则变异测试只证明 checker 能抓语法级错误，对数值与竞态类错误毫无信息。系统代价体现在编译与执行时间：每个变异体都要编译并跑一遍评测，变异体数量乘以单次编译时延直接吃掉 CI 预算，实践中按类别分层保留少量高价值变异体，而不是全量跑。

形式验证与合约验证在路线图中的位置是“窄而深”：对少数核心算子（归约、softmax、attention 的 mask 逻辑）写前置/后置条件与不变量，用符号执行或 SMT 证明其在所有合法输入下满足规格，而不是试图覆盖全部 kernel。失效条件很明确：规格本身写错时，形式验证给出的是“对错误规格的正确性证明”，因此规格必须与参考实现做差分测试对齐；涉及浮点累加顺序的算子，规格只能约束误差界而非精确相等，证明目标退化为区间包含，验证成本随维度指数上升。合约验证的运行时开销则是另一笔账：断言插桩会改变访存模式与寄存器压力，插桩版本与发布版本的性能不可互推，门禁必须区分“验证构建”与“性能构建”。

把三者拼成门禁时，路线图必须回答一个工程判断：审计证据的强度要与发布风险匹配，而不是追求单一“正确”标签。核心算子走形式验证加差分，长尾算子走分层抽样加变异测试，未覆盖桶在门禁中降级为灰度发布并挂技术债；oracle 变更评审的准入条件不是“评审通过”，而是“漏检率估计与变异检出率同时达标，且未覆盖桶清单被显式签字”。这套流程的组织成本落在评测工程师身上——他们要从“跑基准的人”变成“维护审计证据链的人”，能力矩阵里 oracle 一栏的验收标准也应据此定义，而非以基准通过率代替。
