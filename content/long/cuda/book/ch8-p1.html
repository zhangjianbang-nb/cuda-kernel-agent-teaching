一 · 开场：一个“能跑但不可交付”的 kernel

设想一个具体场景。团队要为一个推理服务写 fused RMSNorm + 残差 + 量化的前向 kernel，输入是 [B, S, H] 的 bf16 激活，输出是 int8 量化张量与 scale。第 7 卷的 RL 循环已经跑了几十轮，agent 在 KernelBench 风格的合成任务上能稳定产出通过正确性校验的 Triton 实现，奖励曲线看起来健康。可一旦把这个 kernel 放进真实服务路径，问题立刻分裂成三类：第一类，同一份 prompt 在不同轮次里给出的 kernel 语义不一致——有的把 eps 加在方差里，有的加在均方根外，两者在数值上都“通过”了容差校验，但在下游量化里误差被放大；第二类，agent 学会了针对评测集的形状做特化，B=1, S=2048, H=4096 跑得飞快，换成 S=37 的 decode 阶段就退化到接近 eager 的两倍时延；第三类，profile 文本里明明写着 “uncoalesced global load, 32-byte sectors per request”，agent 却在下一轮把 shared memory 加大了一倍，因为它从没被训练过如何读这段文本。这三类问题都不是 RL 能自己修好的：奖励信号只覆盖“对/错”和“快/慢”的标量，而缺口在语义口径、分布覆盖与反馈解释上。

这一卷要回答的就是这件事：如何把第 7 卷的 RL 轨迹、第 5 卷的修复记录、第 6 卷的 profile 文本，加工成一份可复用、可版本化、可审计的训练数据资产，让 agent 的下限不再依赖采样运气。开场这个算子的三类失败，恰好对应本卷的三个产出面向：清洗规则决定哪些轨迹配进训练集，偏好对构造决定“快 vs 慢”如何变成可学习的信号，profile 解释类 SFT 样本决定 agent 能否把硬件反馈翻译成动作。这不是数据工程的泛泛之谈，而是 kernel agent 特有的问题：数据本身就是一段程序加一段测量，清洗它等于清洗程序语义与测量语义的联合分布。

二 · 上一卷留下的三个缺口

第 7 卷把 RL 循环搭起来了，但它的产出是策略，不是资产。缺口之一是可复现性：一条轨迹的奖励值依赖于当时的基准版本、GPU 型号、编译 flag 与容差阈值，四者任一变动，同一条轨迹的“正确”与“快”就可能翻转。RL 只消费即时奖励，不记录这些上下文，于是轨迹一旦离开当轮环境就失去意义。缺口之二是负例的浪费：修复记录里最有信息量的部分恰恰是失败轨迹——编译失败、数值越界、bank conflict 导致的 8 倍减速——但 RL 的奖励塑形把它们压成了一个低标量，失败的模式信息被丢掉了。缺口之三是反馈的解释断层：profile 文本是非结构化自然语言加计数器表格，RL 把它当作上下文的一段字符串塞进 prompt，从不检验 agent 是否真的据此改了代码；没有监督信号，读 profile 这项能力就不会被习得。

用一句话把三个缺口统一起来：第 7 卷优化的是“在当前环境里采样出好 kernel 的概率”，本卷要优化的是“在环境漂移后仍然能采样出好 kernel 的概率”。前者是策略问题，后者是数据分布问题。形式化地，设轨迹 τ 带有环境签名 e = (bench_ver, gpu, flags, tol)，第 7 卷最大化 E_{τ~π}[R(τ)]，而本卷要构造数据集 D = {(x, y, e, m)}，其中 m 是测量元数据，使得在 e 漂移后训练出的策略仍满足 P(correct | e') ≥ 1 - δ。这个不等式是本卷所有清洗与配比决策的判据：任何一条数据，若其 e 不可追溯，就不能进入 D；任何一类失败，若不能在 e' 下复现其失败原因，就只能作为弱负例。

代价在这里第一次出现。给每条轨迹打环境签名意味着存储与校验开销：一条轨迹含源码、编译日志、NCU 摘要与容差判定，签名要覆盖四元组并做哈希对齐，冷启动数据集规模上升时，版本对齐的校验时间会线性增长。更贵的是去污染：合成基准的题面与真实服务 kernel 的形状分布重叠，若不剔除，评测集隔离就形同虚设，而剔除需要按形状签名与源码指纹双重比对，这一步的编译时间成本无法摊薄到训练里，只能前置到数据生产流水线。

三 · 本卷的赌注：数据资产是可复用底座

本卷押的是一个工程判断：在 kernel agent 这个任务上，SFT 基座的作用不是“教会模型写 CUDA”，而是“稳住下限”。故事映射里团队发现 RL 冷启动不稳，回头用清洗后的 SFT 基座稳住下限，这个回头动作就是赌注的具体形态。冷启动不稳的机制很直接：RL 的初始策略在稀疏奖励下会塌缩到少数几种模板（比如无脑上 tl.load + tl.store 的朴素实现），一旦评测形状偏离模板覆盖，奖励方差骤增，策略在“探索”与“保守”之间震荡。SFT 基座提供的是分布上的锚：一批经过清洗的、语义口径统一的、覆盖多形状与多失败模式的样本，把策略的初始分布钉在一个不会崩的位置，RL 再从这个位置往上推。

赌注的代价必须写清楚。SFT 与 RL 的数据配比是一个显式的资源分配问题：SFT token 消耗的是监督信号预算，RL token 消耗的是采样与验证预算，两者共享同一批 GPU 时。设 SFT 样本数为 N_s、RL 每轮采样数为 N_r、验证一次 kernel 的正确性与计时成本为 c_v，则单位墙钟时间内可用于提升下限的“有效信号”大致是 N_s · u_s / (N_s · c_s + N_r · c_v)，其中 u_s 是单条 SFT 样本的信息增益、c_s 是其训练成本。这个式子说明配比不是拍脑袋的比例，而是由 c_v（验证贵）与 u_s（清洗后的样本信息密度高）共同决定的。保留失败轨迹做负例会抬高 u_s，但会拉低正确性 oracle 的通过率统计口径，需要单独的标签体系；profile 文本进 SFT 还是仅进 RL 上下文，则取决于 c_s：把 profile 解释做成 SFT 样本意味着每条样本要附带一段可判定的“解释是否正确”的标注，标注成本高于纯代码样本。

具体例子：开场那个 RMSNorm 算子，若把“eps 位置”这一语义口径写进清洗规则，则所有通过容差但口径错误的轨迹被标为“语义漂移负例”，进入偏好对的 rejected 侧；若把 decode 形状 S=37 纳入冷启动数据集的形状覆盖，则特化模板在 SFT 阶段就被打破。两件事都不需要新算法，只需要在数据生产时把口径与覆盖写成可执行的规则。

四 · 数据资产的四个加工面向

本卷的产出可以拆成四个加工面向，每个面向都有明确的输入、规则与代价。第一个是成功/失败轨迹清洗：输入是第 7 卷轨迹与第 5 卷修复记录，规则要覆盖编译成功但数值越界、数值通过但语义口径不符、计时异常（如未做 warmup 导致的首次调用抖动）三类脏数据。清洗的判据不能只看奖励标量，要回放编译日志与容差判定。代价是回放本身需要 GPU 时间，且对失败轨迹的回放要区分“环境导致的失败”与“代码导致的失败”，前者应剔除而非标负例。第二个是去污染与去重：合成基准题面与服务 kernel 的形状签名要做交集检测，源码指纹要做归一化后比对（去掉变量名与注释），否则同一实现换个名字就会重复进入训练集，抬高 N_s 却不抬高 u_s。

第三个是偏好对构造，这是本卷最需要机制设计的一环。快 vs 慢的偏好对不能只按实测时延排序，因为时延受形状与 GPU 状态影响；正确 vs 错误的偏好对不能只按容差通过与否，因为口径错误会通过容差。可行的机制是三元组标注：(prompt, chosen, rejected, reason)，其中 reason 取自 profile 文本的关键计数器差异（如 sector 数、occupancy 限制因子），使偏好信号携带可解释的因果线索而非纯标量。代价是标注吞吐：每条偏好对需要一次对照 profile 的人工或规则化归因，规则化归因可以用计数器阈值自动生成，但阈值本身要在验证集上校准，校准成本随形状覆盖线性上升。第四个是 profile 解释类 SFT 样本：把 NCU 摘要翻译成“哪一行代码导致哪个计数器异常、应改什么”的监督对，样本的可判定性来自“改后计数器是否改善”这一可回放指标，而不是解释文本本身是否流畅。

用一个表格把四个面向的代价对齐，便于工程判断：

面向核心机制主要代价失败形态举例
轨迹清洗回放编译日志与容差判定，按环境签名分类GPU 回放时间，失败归因的标注成本eps 口径错误通过容差被误标为成功

这张表的意义在于：四个面向的代价性质不同，清洗与去重是前置的一次性成本，偏好对与 profile 解释是随覆盖增长的边际成本。配比决策必须区分这两类成本，否则会把一次性投入误算进每轮 RL 的预算里。

五 · 版本对齐：数据与基准必须同签名

本卷的一个关键决策是数据版本与基准版本如何对齐。机制上，给数据集打上基准版本、容差阈值、GPU 型号与编译 flag 的四元组签名，训练时按签名分组采样，评测时只允许同签名或签名兼容的数据参与下限评估。兼容性判据可以写成偏序：若 e1 与 e2 的容差相同、GPU 架构相同、flag 差异仅在不影响数值语义的优化级别内，则视为兼容；否则视为漂移，漂移组的数据只能用于训练、不能用于下限声明。这个偏序的代价是采样复杂度：分组采样降低了 batch 内的形状多样性，需要按签名分层后再做形状均衡，均衡本身引入额外的采样逻辑与显存占用（分层缓冲）。

具体到一个可执行的伪代码思路：对每条样本计算 sig = H(bench_ver, tol, gpu_arch, flags_norm)，按 sig 分桶；训练采样时以 p(sig) ∝ n_sig^α 做温度采样，α < 1 用于防止大桶主导；下限评估时只在 sig 与当前评测签名兼容的桶内统计通过率。这个设计的工程判断是：下限不是一个全局数字，而是签名条件下的条件概率，报一个不带签名的通过率在环境漂移后没有意义。代价是评估口径变复杂，需要向使用方解释“同签名通过率”与“跨签名泛化率”的区别，后者只能定性表述为“在未见签名上是否保持语义口径”，不能编造具体数字。

回到开场的算子：若服务端的容差是量化后误差阈值、评测端的容差是 bf16 相对误差，两者签名不兼容，则任何在评测端“通过”的 kernel 都不能直接声明为服务端下限。数据版本对齐要做的，就是把这条不兼容性写进清洗规则，让口径错误的轨迹在训练阶段就被标为负例，而不是等到服务端才暴露。

六 · 落到工程判断：先修口径，再谈配比

本卷的赌注能否成立，取决于一个顺序判断：先修语义口径与形状覆盖，再谈 SFT 与 RL 的配比。理由是配比优化的是信号分配，而口径错误会让信号本身失真——把口径错误的轨迹当正例，配比再精细也是在放大噪声。可执行的机制是三层闸门：第一层，编译与容差闸门剔除硬失败；第二层，语义口径闸门（如 eps 位置、累加精度、边界处理）用小型参考实现做差分比对，不通过者进负例池；第三层，形状覆盖闸门检查冷启动数据集是否覆盖 decode、prefill、变长三类形状签名，缺覆盖则回补采样而不是调配比。三层闸门的代价是数据生产流水线变长，单条样本从采集到入集的时间上升，但换来的是一次性成本替代了 RL 每轮的重复验证成本。

$$\text{有效下限} \;=\; \min_{e \in \mathcal{E}_{\text{compat}}} P(\text{correct} \mid e),\quad \text{s.t.}\; \forall e:\ \text{sig}(e)\ \text{可追溯}$$

这个式子是本卷的口径：下限是对兼容签名集合取最小值，而不是对全体取平均；约束是每条参与评估的数据都必须签名可追溯。工程判断落在最后一句上——若一条轨迹的签名不可追溯，它对下限没有贡献，只能作为训练素材，且必须与评估集物理隔离。隔离的代价是存储与索引的重复，但这是可信评测流水线（另一片段主题）能够成立的前提，此处只指路，不展开。

最后落在一个具体机制上：把“口径差分比对”做成数据生产流水线的常驻闸门，而不是一次性脚本。常驻意味着每次基准版本或容差阈值变动时，闸门自动重跑受影响签名的样本并重标标签，数据版本随之递增。这个机制把本卷的赌注从“清洗一批数据”变成“维护一个随环境漂移而自更新的数据底座”，代价是持续的流水线维护与重标算力，收益是 RL 冷启动不再依赖单轮采样运气。开场那个 RMSNorm 算子的三类失败，在这个机制下分别被闸门二、闸门三与 profile 解释样本接住，而配比问题退居为闸门通过后的二阶优化。
