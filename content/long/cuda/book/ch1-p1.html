一 · 从一张待优化清单说起

假设你所在的团队刚接手一个推理服务，手里有一份由业务侧提交的 kernel 需求清单：七个算子，覆盖 elementwise 的激活与归一化、两个 reduction、一个 matmul 变体、一个 attention 变体，还有一个融合了残差与 layernorm 的复合算子。清单上附着目标 GPU 型号、CUDA 与 Triton 的软件栈版本、现有手写实现的源码，以及一份性能基线——基线不是理论峰值，而是“当前线上跑着的那个版本”的实测时延。这份材料看起来齐备，但它不足以支撑任何一次 agent 尝试，因为它缺少三样东西：每个算子属于哪一类、正确性用什么口径判定、性能达到什么程度才算通过。这三样东西不是文档格式问题，而是本卷要回答的全部问题。

把这份清单直接丢给一个 kernel 生成 agent，最常见的失败不是它写不出能编译的代码，而是它写出的代码在某个口径下“对了”、在另一个口径下“错了”，而团队没有事先声明用哪个口径。一个 reduction 算子用不同累加顺序实现，float32 下结果可以差出若干个 ulp；如果验收脚本用 torch.allclose 的默认容差去比对，这个实现会通过，但它在一个要求逐位复现的数值审计里会被判失败。反过来，如果容差收得过紧，一个在数学上完全正确、只是分块策略不同的实现会被误杀。验收口径的每一次摇摆，都会让后续的基准分数、profile 结论和 RL 奖励信号同时失焦。

所以这一卷的起点不是“怎么让 agent 写出更快的 kernel”，而是“在让 agent 动手之前，先把问题的边界画出来”。画边界这件事本身就是一项工程产出，它的交付物是一份任务分类法、一套容差与数值口径、一组性能判据，以及一份不可接受失败模式清单。这四件东西合起来，决定了后面所有环节的可信度上限。

二 · 上一卷留下的缺口：可解域没有被划出来

前序各条目已经把评测流水线、oracle 与形式审计、agent 脚手架、硬件反馈与 profile、多轮 RL 与奖励、数据基座这些部件分别讲清楚了。这些部件各自成立，但它们共同预设了一个前提：待评测的任务集合是已知的、稳定的、口径统一的。这个前提在实际工程里几乎从不自动成立。基准演化史告诉我们 KernelBench 系基准的任务分布有其自身的偏置，可信评测流水线告诉我们一次评测要固定哪些变量，但没有任何一个部件回答“你手上这批业务 kernel，哪些应该进这个流水线，哪些不该进”。

这就是缺口所在。一个团队如果把业务清单里的七个算子不加区分地全部塞进 agent 可解域，会遭遇两类错误。第一类是假阴性：某个算子其实在 agent 能力范围内，但因为验收粒度定成了生产级（要求端到端时延改善且数值逐位一致），agent 的合理实现被拒。第二类是假阳性：某个算子被 KernelBench 级别的宽松容差放行，agent 交出一个在孤立 microbenchmark 上加速明显、但一放进真实服务就因显存布局冲突而变慢的实现，团队误以为问题解决。两类错误的代价不对称：假阳性会污染后续所有 RL 奖励信号，让策略朝着“在宽松口径下刷分”的方向漂移；假阴性则让团队低估 agent 的可用范围，把本可自动化的任务继续留在人手写。

缺口的具体形态可以写成一个判断式。设任务集合为 T，每个任务 t 带有类别 c(t)、数值敏感度 s(t)、基线余量 m(t)（现有实现距 SOL 的距离），则进入 agent 可解域的判据不是单一阈值，而是三元组的分层：

$$ \text{solvable}(t) = \big[\, c(t) \in C_{\text{agent}} \,\big] \wedge \big[\, s(t) \le s_{\max}(c(t)) \,\big] \wedge \big[\, m(t) \ge m_{\min} \,\big] $$

三个条件分别对应“这一类 agent 会不会写”“这一类允许多大的数值漂移”“这个任务值不值得优化”。任何一个条件不满足，任务就不该进这一轮的验收，而应退回人工或进入另一条轨道。上一卷留下的缺口正是这三个条件的取值从未被系统化地定过。

三 · 本卷的赌注：口径先于生成

本卷押的是一个顺序判断：在 agent 生成 kernel 之前，先把口径定死，收益大于先把生成能力做强。这个赌注有明确的代价结构。定口径需要人力：要把七个算子逐个归类、要为每种 dtype 与累加顺序组合确定容差分级、要跑现有实现拿到可信基线、要枚举失败模式。这些工作不产生任何一行 kernel 代码，在进度表上看起来是纯开销。而它的回报是延迟兑现的——只有当 agent 开始批量产出候选实现、评测开始高频运行时，口径的价值才显现为“少返工”。

赌注的另一面是：口径一旦定错，后续所有优化都会被系统性地带偏。举个具体机制。假设团队把 attention 变体的容差按 float16 的默认口径设为相对误差 1e-2，而该算子在服务里实际以 float16 输入、float32 累加、再转回 float16 输出。一个 agent 若采用 fp16 累加的实现，在短序列上误差可能落在容差内，在长序列上因累加项增多而越界。如果验收只跑短序列，这个实现会被放行；上线后在长序列请求上出现数值异常。这里的代价不是一次评测的时延，而是整条流水线的可信度：一旦团队发现“通过验收的实现仍会在生产出错”，他们就会开始怀疑所有基准分数，agent 的迭代循环随之失去反馈价值。

因此本卷把“口径”当作一等工程对象，而不是评测脚本里的几个常数。容差要按 dtype 与累加顺序分级，性能判据要区分相对基线加速比、SOL 占比与端到端时延三种不同量纲，失败模式要显式列出“不可接受”的类别而不是笼统地说“要正确”。这三件事的共同点是：它们都必须先于生成发生，且必须写成机器可执行的判据，否则 agent 无法在闭环里获得稳定奖励。

四 · 任务分类法：四类算子的可解域边界

分类法的作用不是给算子贴标签，而是把“agent 需要掌握什么”与“验收需要检查什么”绑定在一起。elementwise、reduction、matmul、attention、fused 这五类在本卷里各自对应不同的可解域边界与不同的验收重心。下表给出的是分类维度与判据的对应关系，而不是性能数字。

类别agent 主要难点验收重心典型失败模式
elementwise向量化宽度与访存合并带宽利用率、逐元素容差边界处理遗漏、非对齐访存
reduction分块与累加顺序累加精度、确定性跨块归约顺序导致的 ulp 漂移
matmultiling 与 shared memory 布局SOL 占比、数值稳定性bank conflict、K 维累加溢出
attentionsoftmax 数值稳定与分块长序列容差、显存占用fp16 累加在长序列越界
fused算子间数据流与寄存器压力端到端时延、中间结果精度融合后中间量精度被隐式降低

以 reduction 为例说明分类法如何改变验收。一个 sum-reduction 在数学上是结合律成立的，但在浮点下不成立。agent 若把输入切成 B 个块、每块内部顺序累加、块间再顺序累加，其结果与参考实现的差异取决于 B 与每块长度。设单次浮点加法的相对误差上界为 u，则最坏情况下 n 项顺序累加的误差上界约为 n·u，而树形归约约为 log₂n·u。这个公式直接决定了容差分级：如果验收要求与参考实现逐位一致，那么任何改变累加顺序的实现都不可接受，agent 可解域被压缩到“必须复刻参考的归约树”；如果验收允许 k·u·log₂n 量级的相对误差，agent 才获得选择分块策略的自由。这就是“容差按 dtype 与累加顺序分级”的具体含义——分级不是拍一个数，而是从误差上界公式反推可接受的分块自由度。

代价在这里体现为编译时间与 token 消耗。若容差收紧到要求确定性归约，agent 的搜索空间变小，但它需要更多轮尝试才能命中参考的归约结构，每轮都要编译、运行、比对，单任务的编译时间与 token 消耗上升。若容差放宽，搜索空间变大、收敛更快，但假阳性风险上升，后续要用更多生产验证来兜底。分类法的价值就是让这个权衡在任务级别被显式做出，而不是在流水线里隐式漂移。

五 · 性能判据的三种量纲不能混用

性能判据有三个来源：相对基线加速比、SOL 占比、端到端时延。它们量纲不同，回答的问题也不同，混用会让验收结论互相矛盾。相对基线加速比回答“比现有手写实现快多少”，它的分母是团队自己的基线，因此对基线质量高度敏感——如果基线本身距 SOL 很远，一个平庸的 agent 实现也能拿到好看的加速比。SOL 占比回答“距硬件理论上限还有多远”，它不依赖基线，但依赖 roofline 模型中对访存与算力瓶颈的判定，判定错了 SOL 分母就错了。端到端时延回答“服务整体是否变快”，它把 kernel 之外的调度、数据传输、框架开销都算进来，因此单个 kernel 的加速可能被端到端噪声淹没。

一个具体的混用错误：某 matmul 变体在 microbenchmark 上相对基线加速比达到可观数值，团队据此判定通过；但该 kernel 在服务里被调用时，输入张量的布局要求一次额外的转置，端到端时延反而上升。这不是 agent 的错，是验收判据选错了量纲。正确的做法是在分类法里为 matmul 类同时声明两个判据：microbenchmark 上用 SOL 占比判断 kernel 本身的质量，端到端链路上用端到端时延判断集成后的收益，两者都通过才算通过。两个判据的代价不同：SOL 占比需要 roofline 分析与 profiler 数据，端到端时延需要真实服务流量或高保真回放，后者更贵，因此只对进入生产验收粒度的任务执行。

这也直接连到本卷的关键决策之一：以 KernelBench 级别还是生产级为验收粒度。KernelBench 级别的验收便宜、可批量、适合 RL 高频迭代，但它的容差与性能判据都是孤立口径；生产级验收贵、慢、需要真实链路，但它的结论可直接用于上线决策。分级的工程判断是：agent 可解域内的任务先在 KernelBench 级别跑通，只有那些类别属于 fused 或 attention、且数值敏感度高的任务，才升级到生产级验收。升级的门槛写在失败模式清单里，而不是凭感觉决定。

六 · 不可接受失败模式清单是口径的最后一环

容差与性能判据定义了什么算“对”和“快”，失败模式清单定义了什么算“不可接受”，即使它在数值与性能上都通过了。这类失败模式的特征是：它们在孤立评测里不显现，只在特定输入分布、特定并发或特定硬件状态下暴露。清单的作用是把这些条件写进验收脚本，让 agent 在闭环里就能被这些条件惩罚，而不是等到上线后由用户发现。

以 fused 类算子为例。一个把残差加法与 layernorm 融合的实现，若在融合时把中间残差和以 fp16 保存而非 fp32，数值上在短输入下可能落在容差内，但当输入存在大幅值元素时，fp16 的表示范围会导致溢出或精度骤降。这个失败模式在随机小输入上测不出来。清单里应显式写出“融合中间量不得低于输入精度的累加精度”这一条，并配一个针对大幅值输入的测试用例。这条规则的代价是显存：保持 fp32 中间量会增加寄存器与 shared memory 压力，可能压低占用率，进而影响 SOL 占比。于是口径内部出现张力——数值安全与性能判据互相拉扯，而这个拉扯必须在验收前被显式定价，而不是让 agent 在搜索中自行发现一个“既通过容差又通过 SOL”的巧合实现。

清单的另一个作用是约束 agent 的搜索方向。多轮 RL 的奖励若只由“通过/不通过”二值构成，agent 会倾向于寻找判据的漏洞；若奖励里包含失败模式清单的逐条检查结果，agent 就被引导去满足那些在孤立评测中不可见的条件。这就是口径先于生成的最终落点：口径不只是验收标准，它同时是奖励函数的定义域。一个没有被写进清单的失败模式，等于在奖励函数里不存在，agent 不会为它付出任何搜索代价。因此本卷把清单列为产出之一，与分类法、容差、性能判据并列，四者共同构成 agent 可解域的完整边界。

回到开篇那份七个算子的清单：在动手之前，团队要先把每个算子归入五类之一，为每类确定 dtype 与累加顺序对应的容差分级，为每类选定性能判据的量纲组合，并把已知的不可接受失败模式逐条写成可执行检查。这四步做完，agent 的第一次生成才有意义；这四步没做完，后面所有的基准分数、profile 结论与奖励信号都建立在流沙上。
