一 · 口径先于数字：本卷评测对象的边界

本卷讨论的“快”，必须先被钉死在一个可复核的对象上。评测对象不是某个 kernel 的孤立时延，而是 agent 在给定基准、给定硬件、给定 dtype、给定基线的前提下，产出的 kernel 相对基线的可复现比值。这个比值要能被第三方用同一份输入、同一份编译命令、同一份测量脚本重新跑出来，才算数字。凡是不能重跑的，只能叫观察，不能进表。

具体机制上，本卷把每个评测条目拆成五元组：基准条目 ID、硬件标识、dtype 组合、基线实现、指标定义。五元组缺一项，条目即判为不可复核。基线实现必须显式声明是 PyTorch eager、torch.compile、cuBLAS/cuDNN 调用，还是手写参考 kernel；不同基线给出的加速比不可横向比较，因为分母不同。指标定义要写清是 wall-clock 端到端、纯 kernel 时间、还是含 launch 开销的流内时间。

$$\text{Speedup} = \frac{T_{\text{baseline}}(\text{同一输入、同一 dtype、同一硬件})}{T_{\text{agent kernel}}(\text{同一测量口径})}$$

代价在于口径收紧会显著缩小可入表条目数：要求同一测量脚本，意味着跨机器结果不可直接合并；要求显式基线，意味着历史条目里基线未记录的必须重跑。一个具体例子：某条目基线写“PyTorch”，但未注明是否 torch.compile，则其 1.8× 加速比在复核时可能落到 1.1×，因为分母从 eager 换成了编译后的实现。这类返工是本卷口径设计的直接成本。

二 · 基准分层：从 KernelBench 系到自建条目

本卷面对的基准分三层。第一层是 KernelBench 系公开条目，提供算子语义与参考实现，适合做跨 agent 的可比对照；第二层是自建的形状与 dtype 扫描条目，用来暴露 agent 在非方形、非对齐、混合精度下的退化；第三层是端到端片段，把若干 kernel 串成一个小图，测的是拼接后的真实时延而非单点峰值。三层不可混算总分，因为它们的失败模式不同：第一层考语义正确性，第二层考边界处理，第三层考 kernel 间同步与显存复用。

分层带来的机制是“条目配额”：每个 agent 版本在每层上跑固定条目数，层内取几何平均而非算术平均，避免个别超大加速比拉偏整体。几何平均对加速比的压缩效应明显，一个 8× 的离群条目在十个条目里只能把几何均值抬高约 1.23×，而算术平均会抬高近 1.7×。代价是几何平均对“某个条目彻底失败（加速比小于 1 或不可运行）”极其敏感，一个失败条目会把整层均值拉到 1 以下，因此必须把不可运行条目单独计数，不能静默按 0 计入。

层考察点失败代价入表条件
公开基准条目语义正确性、基本加速语义错则整条作废参考实现可跑通
形状/dtype 扫描边界、对齐、混合精度退化到基线以下扫描表完整
端到端片段拼接时延、显存复用同步开销吞掉单点收益图级输入固定

具体例子：一个 agent 在公开条目上把某个 reduction 算子做到 3×，但在非 2 的幂形状扫描上退化为 0.7×，若只报第一层，结论就是失真的。分层配额强制把这类退化暴露在表内。

三 · 硬件与 dtype：把“快”锚定在可复现的机器状态上

硬件标识必须细到能决定测量结果的程度：GPU 型号、SM 数量、显存容量与带宽档位、是否开启 ECC、时钟是否锁定。时钟不锁定是时延抖动的主要来源，同一 kernel 在 boost 与 base 时钟下的比值可以差出可观幅度，因此本卷要求评测机在测量窗口内固定时钟策略，并在条目里记录该策略。多卡条目还要记录互联拓扑，因为跨卡 kernel 的时延由链路决定而非算力决定。

dtype 组合是第二个锚点。条目要声明输入、累加、输出的 dtype 三元组，例如输入 fp16、累加 fp32、输出 fp16，或输入 bf16、累加 fp32。同一算子在不同三元组下的 roofline 位置完全不同：fp16 输入把计算强度压到带宽侧，fp32 累加又把寄存器压力抬上去。只写“fp16”而不写累加精度，等于没写口径。混合精度条目还必须声明是否允许 TF32，因为 TF32 在矩阵乘上会改变基线的分母。

$$\text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes Moved}},\quad \text{roofline 上限} = \min(\text{峰值算力},\ \text{带宽} \times \text{AI})$$

代价在测量侧：锁定时钟会降低机器吞吐，评测机的有效利用率下降；逐条记录 dtype 三元组会让条目元数据膨胀，检索与聚合的 token 成本上升。具体例子：一个 agent 在 fp16 输入、fp32 累加的配置下拿到 2.2×，换到 bf16 输入、fp32 累加后掉到 1.4×，原因不是 kernel 变差，而是 bf16 的尾数位少，参考实现走了不同的累加路径，分母变了。口径不记录三元组，这个差异就无法归因。

四 · 指标族：时延、带宽、显存与编译时间各自回答不同问题

单一加速比不足以描述 agent 产出的质量，本卷用指标族。时延回答“跑得多快”，带宽利用率回答“离 roofline 多远”，显存峰值回答“能不能装进目标卡”，编译时间回答“agent 的多轮修复预算是否被编译吃掉”。四个指标各自有独立的失败模式：时延好但显存峰值超限的 kernel 在目标硬件上不可部署；带宽利用率高但编译时间长的 kernel 会拖垮多轮修复的 token 预算。

机制上，每个指标都要绑定测量方法。时延用固定次数的重复测量取中位数而非均值，因为首次 launch 的冷启动与上下文切换会污染均值；带宽利用率由实测字节数除以实测时延得到，字节数必须按实际访问模式估算而非按张量大小；显存峰值用分配器钩子记录，不能用理论估算；编译时间从编译命令发起到产物可加载为止，包含模板实例化与 PTX 汇编。指标之间不可互相替代，也不可加权成一个总分，因为权重选择本身就是口径决策。

  • 时延：中位数，固定重复次数，剔除首次冷启动。
  • 带宽：实测访问字节除以时延，与 roofline 上限对比。
  • 显存：分配器峰值，含临时缓冲与 workspace。
  • 编译：从命令到可加载产物的墙钟时间，计入模板实例化。

代价是测量开销本身：固定重复次数意味着每个条目的测量时间随重复数线性增长；分配器钩子会引入轻微扰动；编译时间测量要求每次从干净产物开始，禁止增量缓存，否则数字不可比。具体例子：一个 Triton kernel 时延优于基线 1.6×，但编译耗时是 CUDA C++ 版本的数倍，在多轮修复预算固定的前提下，agent 实际可用于尝试的轮数被压缩，端到端收益反而下降。只报时延就会掩盖这个代价。

五 · 把“快”翻译成可复核数字：从单次观察到入表记录

翻译过程是一条流水线：原始测量 → 口径校验 → 聚合 → 入表。口径校验检查五元组完整性与测量脚本一致性；聚合按层取几何平均并单独统计不可运行条目；入表记录必须携带可重跑的脚本标识与硬件状态快照。任何一步缺失，数字降级为“观察”，不参与跨 agent 比较。

伪代码思路如下：对每个条目，先跑基线得到分母，再跑 agent kernel 得到分子，两者在同一进程、同一流、同一测量循环内交替执行，以抵消时钟漂移；然后对每个条目的加速比取对数，层内求对数均值再取指数，得到几何平均；最后把不可运行条目数与总条目数一起写入记录，作为该层结论的置信边界。

$$\text{LayerScore} = \exp\left(\frac{1}{N}\sum_{i=1}^{N}\ln \frac{T_{\text{base},i}}{T_{\text{agent},i}}\right),\quad \text{附：不可运行条目数 } M$$

代价在于交替执行会让单条目测量时间翻倍，且基线必须与 agent kernel 共享同一输入缓冲，否则显存状态不一致会引入偏差。具体例子：某 agent 版本在十个条目上几何均值为 1.9×，但其中两个条目不可运行；若把不可运行按 0 计入，均值跌到 1 以下，若单独列出，结论是“八个条目有效、两个失败”，这两种表述对应完全不同的工程判断。入表记录必须同时给出均值与失败计数，缺一不可。

六 · 基线选择的工程判断：分母决定结论

基线不是越强越好，也不是越弱越安全，而是要与评测目的对齐。若目的是判断 agent 是否具备替代手写 kernel 的能力，基线应是经过调优的库调用或手写参考；若目的是判断 agent 是否能在多轮修复中逼近编译器的自动优化，基线应是 torch.compile 产物。混用两种基线会让加速比失去可比性，因为前者分母是人工调优的峰值，后者分母是编译器生成的次优实现。

机制上，本卷要求每个条目在元数据里写明基线类别，并在聚合时按基线类别分组报告，禁止跨组求总均值。分组报告的代价是表体变宽、结论变碎，读者需要自己判断哪一组更接近自己的部署场景；但不分组的代价更大，一个用弱基线撑起来的 4× 会污染整卷的可信度。具体例子：同一 agent 在库调用基线下为 1.3×，在 torch.compile 基线下为 2.1×，两个数字都真实，但只有标注了基线类别才可解释——前者说明 agent 尚未超过人工调优，后者说明 agent 已超过编译器自动路径。工程判断落在基线类别上，而不是落在单个加速比上。

最终入表的每个数字都应能回答三个问题：分母是谁、测量口径是什么、失败条目怎么计。回答不了这三个问题的数字，在本卷的语境里不具备复核价值，只能作为下一轮修复的线索。

闭环脚手架的失效边界：反馈带宽、修复预算与口径漂移

把“编译-执行-修复”闭环当作默认架构，第一个要问的不是它能涨多少，而是它在什么条件下必然失效。失效条件有三类。其一是反馈带宽不足：结构化反馈若只回灌“编译失败/运行失败”布尔量，agent 无法区分语法错误、类型不匹配、共享内存超限与非法访存，修复轮次退化为随机扰动，此时闭环的期望增益趋近于零，却仍按轮计费 token。其二是修复预算与任务难度错配：每任务最大轮数 R 与单轮 token 预算 B 构成硬约束，当首个 kernel 的正确性缺口需要跨多个抽象层重构（例如从线程级规约改为 warp shuffle 再改为 CuTe tiled copy）时，R 轮内的局部修补无法到达可行域，闭环只是在错误吸引域内打转。其三是口径漂移：修复过程中若允许改变 dtype、允许换 baseline 实现、允许放宽 tolerance，则“变快”可能只是把计算搬到了更低精度或更弱基线上，数字可复核但语义不可比。

把闭环写成可分析的代价模型：设单轮编译时延为 c、执行与 profile 时延为 e、反馈解析与上下文注入的 token 开销为 t，则单任务墙钟约为 R·(c+e) 加上串行的模型解码时间，token 消耗约为 R·(t + 生成长度)。关键判断是边际收益递减点：第 k 轮修复带来的正确率增量 Δp_k 与第 k 轮成本 c+e+t 之比，在反馈粒度粗（只到错误类别）时通常在第 2–3 轮后跌破阈值；粒度细到行号与 SASS 指令级 stall 原因时，递减点后移，但每轮上下文注入的 token 显著上升，压缩历史尝试的摘要策略成为主要成本项。因此“每任务最大轮数”不是拍脑袋的超参，而是由反馈粒度与压缩率共同决定的预算边界。

口径层面，把“快”翻译成可复核数字需要固定四元组：硬件（SM 架构与显存带宽档位）、dtype（输入/累加/输出的精度链路）、基线（同语义的参考实现及其编译选项）、指标（端到端时延、kernel 时延、有效带宽占 SOL 比例，三者不可混用）。一个具体例子：同一 reduction kernel 在允许把累加器从 fp32 降为 fp16 后，报告时延下降，但有效带宽占 roofline 上界的比例并未提升，说明收益来自精度让渡而非访存效率；若评测口径未锁定 dtype 链路，这个数字会被误读为 kernel 优化成果。表格化的口径登记比文字描述更能防止跨轮漂移：

口径项锁定内容漂移后果
dtype 链路输入/累加/输出精度时延下降但语义不可比
基线参考实现与编译选项加速比虚高
指标端到端 vs kernel-only启动开销被隐藏
tolerance正确性判定阈值错误 kernel 被判通过

由此得到的工程判断是：闭环脚手架的可信度上限由反馈粒度与口径锁定的严格程度共同决定，而非由轮数堆叠决定。当反馈只能到错误类别、且口径允许 dtype 与基线漂移时，增加修复轮数只会放大 token 成本而不改善可复核性；反之，把反馈细到行号与 stall 原因、把口径四元组写进每轮评测的固定前置，才能让“第 k 轮变快”成为可归因的数字。允许检索历史成功 kernel 的策略同样受此约束：检索命中会缩短达到可行域的路程，但若检索结果跨 dtype 或跨基线复用，口径漂移会以“复用成功”的形式被掩盖，因此检索必须带口径标签过滤。
