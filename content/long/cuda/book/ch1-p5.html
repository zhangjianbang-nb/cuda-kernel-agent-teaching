一 · 脚手架的分工不是角色扮演，是信息通道设计

把 coder / judge / profiler / search 四个角色当成四个 prompt 模板是常见误读。真正决定这套脚手架成败的，是每个角色能读到什么、能写回什么、以及写回的内容以什么形态进入下一轮上下文。coder 的输出是候选 kernel 源码加一份自述（用了什么 tile、假设了什么对齐、对哪个维度做了特化）；judge 的输出不是“对/错”布尔值，而是带定位信息的失败证据——哪个 shape 下第几个元素超差、最大相对误差、是否 NaN、是否在某个 dtype 上才崩。profiler 的输出是结构化指标而非自然语言总结：kernel 时长、achieved occupancy、DRAM 吞吐占峰值比、L2 命中、指令数、以及从 SASS 抽出的关键计数（例如 LDG 数量、shared bank conflict 次数、是否出现 local memory spill）。search 的职责不是“再想想”，而是维护一个候选池与淘汰记录，把“哪类改写在这类任务上反复失败”沉淀成下一轮的先验约束。

这四者的接口必须窄。窄接口的代价是表达能力受限：judge 若只回传标量误差，coder 就无法知道是尾部处理错了还是累加顺序错了；profiler 若只回传时长，就无法区分是带宽打满还是延迟受限。但宽接口的代价更直接——token。一份完整 NCU 报告动辄数千行，直接塞进上下文会挤掉源码与任务描述，且模型对长表格的利用效率极低。工程上的折中是分层摘要：profiler 先产出一份固定字段的短记录（十余个字段），再按需挂载一到两个原始 section 的裁剪片段。这个裁剪策略本身要有判据，例如仅当 SOL 占比低于阈值且 DRAM 吞吐接近峰值时才挂载内存相关 section，否则挂载 warp stall 相关 section。

一个具体例子：任务是把一个 reduction 从两段式改成单 kernel。coder 第一版用了 256 线程、每线程 4 元素向量化，judge 报某非 2 的幂 shape 下误差超标，profiler 显示 occupancy 只有三成且出现 spill。若 profiler 只回传“慢”，coder 大概率会去调 tile 大小；而回传 spill 计数与寄存器用量后，正确的修正方向是缩小每线程累加数组或改用 warp shuffle 归约。这就是接口字段决定搜索方向的直接体现。

二 · 执行反馈的三种粒度与各自的时延账

执行反馈不是单一信号，至少分三层，代价差一个量级以上。第一层是编译+正确性：编译一个 CUDA 翻译单元、跑若干 shape 的数值比对。第二层是计时：在固定输入上多次迭代取中位数，需要处理 warmup、L2 冷热、clock 波动。第三层是 profile：NCU 采集需要 replay kernel 多次以收集不同 counter 组，单次采集的墙钟时间远高于普通计时，且会改变执行时序。

把这三层混在一轮里做，会让每轮迭代的时延被 profile 主导，而 profile 的信息在早期迭代里价值最低——一个连正确性都没过的 kernel，其 occupancy 数字毫无意义。合理的门控是：正确性不过则不进计时；计时未达基线则不进 profile；profile 只在候选已经“能跑且不慢”时才付费。这个门控把每轮平均时延压下来的同时，也让 profiler 的反馈质量上升，因为它面对的是一批已经过滤过的候选。

$$T_{\text{iter}} = T_{\text{gen}} + n_{\text{cand}}\cdot(T_{\text{compile}} + T_{\text{correct}}) + n_{\text{pass}}\cdot T_{\text{bench}} + n_{\text{prof}}\cdot T_{\text{ncu}}$$

其中 n 的下标逐级递减。工程判断在于：T_ncu 往往是 T_bench 的数倍到数十倍，因此 n_prof 必须被严格限制，通常每轮只对最优的一到两个候选做 profile。另一笔账是 token：每轮把 judge 的失败证据与 profiler 的短记录拼进上下文，长度随轮数线性增长，若不做摘要压缩，到第十轮左右上下文就会被历史反馈占满，反而丢失了当前任务的源码细节。压缩策略应是“保留最近两轮的完整证据 + 更早轮次的结论性约束”，而不是等长保留。

具体例子：一个 attention 变体任务，前几轮 coder 反复在 shared memory 布局上试错。若每轮都跑 NCU，单轮时延被拉长数倍，而真正有用的信号（bank conflict 计数）只在布局改动的那几轮才有区分度。把 profile 限制在“计时进入基线附近”的候选上，既省了采集时间，也让 bank conflict 这个字段真正对应到一次具体的布局决策。

三 · NCU 与 SASS 的分工：一个回答“瓶颈在哪”，一个回答“为什么”

NCU 给的是聚合视角：吞吐占峰值比例、stall 原因分布、occupancy 上限由什么限制（寄存器、shared memory、block 数）。它能告诉你这个 kernel 是 memory bound 还是 latency bound，但很难告诉你具体是哪条指令导致的。SASS 给的是指令级视角：实际生成的指令序列、谓词化、向量化宽度、是否有冗余地址计算、shared memory 访问的 stride 形态。两者的正确用法是 NCU 定位、SASS 归因。

一个典型链路：NCU 显示 DRAM 吞吐接近峰值但 SOL 占比仍不高，说明有额外的内存流量。此时去看 SASS，若发现本该向量化的加载被拆成多条标量 LDG，或地址计算里出现了重复的 64 位乘加，就能定位到源码里某个索引表达式的写法问题。反过来，若 NCU 显示 stall 主要集中在 barrier，SASS 里能看到同步点前后的指令分布，判断是负载不均还是同步过密。

代价必须说清楚。SASS 的 token 成本极高：一个中等 kernel 的 SASS 数百行，逐行喂给模型既贵又噪声大。可行做法是让 profiler 侧做指令级聚合——按指令类型统计条数、标出访问 global/shared 的指令及其地址表达式模式，只把聚合结果与少量可疑片段送入上下文。另一笔代价是正确性风险：基于 SASS 的改写建议若脱离了源码语义（例如模型误读谓词逻辑），会引入难以察觉的边界错误，因此任何由 SASS 归因驱动的改写仍须过 judge 的数值比对，且要比对边界 shape。

具体例子：一个 elementwise 融合 kernel 在某个 dtype 上比基线慢。NCU 显示吞吐不低但指令数偏多，SASS 聚合显示存在大量标量访存与重复的类型转换。修正方向是把向量化宽度与对齐假设写进源码，而不是去调 block 大小。这里 NCU 的“指令数偏多”是入口，SASS 的“标量访存”是归因，两者缺一，搜索就会在错误的参数空间里打转。

四 · 多轮修正的状态管理：什么该进上下文，什么该进约束

多轮修正的核心问题不是“改几次”，而是“每一轮改什么”以及“历史如何影响当前”。若把全部历史对话原样保留，模型倾向于重复已经失败的思路，因为失败证据在长上下文里被稀释；若只保留当前候选，模型会丢掉已经排除的方向，反复踩同一个坑。可行结构是双轨：一条是短期轨，保留最近一到两个候选的源码与完整证据；一条是长期轨，维护一份结构化的“已排除假设”清单，每条包含假设内容、失败表现、失败时的任务特征。

长期轨的条目要能被检索而不是被通读。检索键可以是任务分类（elementwise/reduction/matmul/attention/fused）加失败模式（数值超差、spill、bank conflict、同步过密）。当新一轮任务落入同一分类且 profiler 报出同一失败模式时，才把对应条目注入上下文作为硬约束，例如“该分类下每线程累加数组超过某长度会 spill，不要从这条路走”。这把上下文从“叙事”变成“约束”，token 成本低且对搜索方向的塑形更强。

代价在于长期轨的维护本身：条目过粗则约束无效，过细则条目膨胀、检索命中率下降，且错误的约束会过早剪掉可行解空间。工程判断是让长期轨只记录“有 profiler 证据支撑的失败”，不接受仅凭 judge 单次超差就写入的结论——单次超差可能是容差口径问题而非思路问题。具体例子：某 matmul 任务连续三轮在尾块处理上超差，若直接写入“尾块特化不可行”，可能剪掉了正确解；而若 profiler 同时显示该思路下寄存器用量逼近上限，则这条约束就有了物理依据，值得写入。

五 · search 的职责边界：它不该生成代码

search 若被允许直接产出候选源码，就会与 coder 的职责重叠，导致两个角色互相污染：search 基于历史统计做出的改写往往缺乏对当前源码结构的理解，产生看似合理但语义偏移的补丁；coder 则因为 search 也在产出而降低了自身修正的深度。更稳的分工是 search 只做三件事：排序候选、分配预算、决定下一轮的方向标签。

排序的依据应是多目标而非单一加速比：正确性裕度（离容差边界多远）、性能相对基线的位置、以及改写风险（改动行数、是否触及索引逻辑）。一个正确但贴着容差边界的候选，其后续被采纳的概率低于一个略慢但裕度充足的候选，因为前者在生产口径下极易在别的 shape 上翻车。预算分配则体现在：对高潜力候选给多次修正机会，对已多次失败的方向直接关闭，把轮次留给新方向。

代价是搜索空间被人为收窄带来的机会成本，以及排序函数本身可能固化偏见——若排序过度偏好“改动小”，就会系统性压制需要重构才能拿到大幅加速的解。具体例子：一个 fused kernel 的初版正确但慢，一个激进重构版快但某 shape 超差。若排序只看加速比，资源会全部流向重构版；若把正确性裕度纳入排序，则会给初版一次针对性优化（例如只改向量化宽度）的机会，这条路径的期望收益更稳。这里的工程判断是：在验收粒度尚未确定（KernelBench 级还是生产级）时，排序应偏向裕度；一旦口径锁定为生产级，才允许为加速比承担更多正确性风险。

六 · 反馈闭环的失效模式与可观测性

这套脚手架最危险的失效不是“改不对”，而是“看起来在改”。三种典型形态：其一，judge 的容差口径与任务定义不一致，导致模型在追一个错误的数值目标，所有轮次都在优化一个不该优化的量；其二，profiler 的指标与真实瓶颈脱钩，例如在小 shape 上采集的 occupancy 被当作大 shape 的判据，搜索被引向错误方向；其三，coder 反复做等价改写，源码 diff 不为零但语义与性能均无变化，轮次被空耗。

对抗这三种形态需要可观测性，而不是更多的 prompt。对第一种，把容差口径作为任务元数据显式注入每一轮，并让 judge 回传“当前误差 / 容差上限”的比值而非仅布尔结果；对第二种，profiler 记录采集时的 shape 与 dtype，并在跨 shape 引用指标时标注不匹配警告；对第三种，对候选做语义等价与性能等价的粗筛，diff 非空但计时落在噪声区间内的候选直接标记为无效轮次，不计入预算。

代价是这套可观测性本身要写代码、要维护，且会拖慢单轮时延（等价性粗筛需要额外一次编译或哈希比对）。但相比空耗轮次带来的 token 与墙钟浪费，这笔开销是值得的。具体例子：某团队在 reduction 任务上连续多轮无进展，事后发现 judge 用的是绝对误差而任务定义要求相对误差，模型一直在压一个与验收无关的量；加上误差比值回传后，第一轮就暴露了口径错配。这类问题的根因不在模型能力，而在脚手架的信息通道设计——这也是为什么本卷把“哪些任务进入 agent 可解域、以何种粒度验收”作为前置决策，而不是留给脚手架在运行中自行摸索。

脚手架的分工边界与失效条件

coder/judge/profiler/search 四角色的分工不是并行流水线，而是带反馈环的串行依赖：coder 产出候选，judge 判定正确性，profiler 采集 NCU/SASS 证据，search 依据证据决定下一轮候选的变异方向。边界在于 judge 的判定口径必须与任务分类法绑定的容差分级一致——若 judge 用固定绝对误差，reduction 类因累加顺序变化产生的漂移会被误判为失败，导致 search 在正确候选上反复回退。失效条件是 profiler 的证据粒度不足：当 kernel 时延低于单次 NCU 采集的固定开销时，profile 数据被测量噪声淹没，search 拿到的“加速比”实际是噪声，多轮修正退化为随机游走。

系统代价集中在反馈环的往返时延上。设单轮成本为编译时间 $T_c$、正确性验证 $T_j$、profile 采集 $T_p$、模型推理 $T_m$，则一轮总时延为 $T_{round}=T_c+T_j+T_p+T_m$，而有效修正轮数受 token 预算约束：$N_{eff}=\min(N_{max},\ \lfloor B_{token}/B_{round}\rfloor)$。NCU 采集本身引入的时延放大在高 occupancy kernel 上尤为明显，SASS 反汇编的存储开销也会挤占上下文窗口。工程判断是：对 elementwise 类任务，profile 环节可降级为计时器采样以压缩 $T_p$；对 attention/fused 类，NCU 的 stall 原因分布不可替代，此时应接受更长的 $T_{round}$ 并相应收紧 $N_{max}$，否则 token 预算会在低信息量的轮次中被耗尽。
