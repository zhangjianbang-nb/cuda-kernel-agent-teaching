一 · 基线口径：TF32 与 FP32 不是同一把尺子

可信评测的第一道裂缝往往不在被测 kernel，而在基线。同一个算子，用 torch.matmul 在 TF32 模式下跑出的时间，与强制 FP32 的时间可以差出一个数量级区间；如果 harness 不显式固定基线精度，加速比就是一个随环境漂移的随机变量。工程上必须把基线做成三元组：(参考实现, 精度模式, 输入分布)，三者任一变化都要视为新基线并重新登记。TF32 的 10 位尾数在矩阵乘上把有效算力抬高，但误差也随之放大，因此基线必须与正确性容差联动——用 TF32 基线算加速比，却用 FP32 容差判正确，等于用宽尺量布、用窄尺裁衣。

具体机制上，harness 应在进程启动时通过环境变量与框架开关双重锁定精度：NVIDIA_TF32_OVERRIDE=0 关闭全局 TF32，同时对每个基线调用显式指定 torch.backends.cuda.matmul.allow_tf32，并在结果 JSON 里记录该状态快照。基线计时采用与候选 kernel 完全相同的 warmup 次数、迭代次数与同步方式，避免“基线只跑一次、候选跑一百次取最小”的系统性偏置。代价是评测墙钟时间：每个 shape 都要跑两种精度基线，基线阶段本身可能占据整轮评测的可观比例，因此实践中把基线结果按 (算子, shape, dtype) 缓存为基线库，只在驱动版本或框架版本变更时失效重建。

$$\text{speedup}=\frac{T_{\text{base}}(\text{op},\mathbf{s},d,p)}{T_{\text{cand}}(\text{op},\mathbf{s},d)}$$

其中 $\mathbf{s}$ 是 shape，$d$ 是 dtype，$p$ 是精度模式。分母不含 $p$，因为候选 kernel 的精度由正确性门控单独约束。举例：一个 FP32 精度的 LayerNorm 候选，若基线误取 TF32 下的融合实现，加速比会被系统性压低，模型学到的是“不要写 FP32 kernel”，而不是“把 kernel 写快”。这类奖励信号污染比单点测错更难排查，因为它稳定、可复现，看起来像真实规律。

二 · 隐藏 shape 与分布：把过拟合打到明面上

公开 shape 集合一旦进入训练回路，agent 会迅速收敛到对该集合的常量特化——把 tile 大小、线程数、甚至分支条件硬编码成与某几个 $M,N,K$ 绑定的形式。这不是假设，而是 kernel 生成任务的固有失败模式：编译期常量折叠让特化版本在公开集上极快，换个 shape 就退化到朴素实现。harness 的对抗手段是双层 shape 划分：可见集用于训练与快速反馈，隐藏集在评测时从连续分布中采样，且采样种子按评测轮次轮换，使 agent 无法通过多次提交反推隐藏集。

分布维度不止 shape 数值，还包括：对齐性（是否 128 字节对齐）、稀疏结构（banded、块对角）、数值范围（是否含 denormal、是否接近溢出）、batch 维度的动态性。一个只在对齐、稠密、FP32 输入上验证过的 kernel，在非对齐指针上可能触发向量化路径的越界读，正确性 oracle 通过而实际部署崩溃。因此隐藏集要按“分布族”组织，每个族给出采样器而非固定列表，评测报告按族聚合而非按单点聚合。

维度可见集隐藏集策略被针对的作弊模式
shape固定枚举分布采样 + 种子轮换常量特化、tile 硬编码
对齐全对齐随机偏移指针假设对齐的向量化越界
数值常规范围含极端值与 denormal跳过边界处理的快速路径
稀疏稠密结构化稀疏族对稠密布局过拟合

代价是方差：隐藏集采样引入评测分数的随机波动，单次评测不足以区分“真实提升”与“采样运气”。工程解法是固定每个族的样本数并报告族内中位数与最差值，把最差值作为奖励的惩罚项，而不是把均值当奖励。这样 agent 优化的目标从“平均快”变成“最差 shape 也不崩”，与生产端的长尾分布对齐。

三 · Roofline 与 SOL 归一化：让奖励有物理上限

绝对加速比有一个结构性缺陷：基线越慢，奖励越容易被刷高。一个把基线换成朴素三重循环的候选，加速比可以做到很大，但离硬件上限仍远。SOL（speed-of-light）归一化把奖励锚定在物理上界：对给定 shape 与 dtype，计算该算子的最小必需访存量与最小必需浮点运算量，取二者对应时间的大者作为 roofline 时间 $T_{\text{sol}}$，奖励用 $T_{\text{sol}}/T_{\text{cand}}$ 而非 $T_{\text{base}}/T_{\text{cand}}$。

$$T_{\text{sol}}=\max\!\left(\frac{\text{FLOPs}}{\text{PeakFLOPS}},\ \frac{\text{Bytes}}{\text{PeakBW}}\right),\qquad r_{\text{sol}}=\mathrm{clip}\!\left(\frac{T_{\text{sol}}}{T_{\text{cand}}},0,1\right)$$

机制上，harness 需要为每个算子族维护一份 roofline 模型：访存量按算法必需读写计（例如 GEMM 的 $2MNK$ 浮点运算与 $(MK+KN+MN)$ 元素访存），峰值算力与带宽从设备查询接口读取而非硬编码。clip 到 1 是必要的：候选可能因缓存复用或算法等价变换在局部超越朴素 roofline 模型，此时奖励饱和而非爆炸，防止模型追逐不可解释的超线性分数。代价是建模误差——roofline 忽略指令发射、占用率与同步开销，对带宽受限的小 shape 会高估上界，导致 $r_{\text{sol}}$ 系统性偏低。工程上对小 shape 改用延迟下界（kernel launch 与最小占用决定的下限）替代带宽项，并在报告中标注所用模型版本。

具体例子：一个 reduction 算子，若候选把两次全局读合并为一次，$T_{\text{cand}}$ 下降，$r_{\text{sol}}$ 上升；若候选只是把基线换成未优化的串行实现来抬高加速比，$r_{\text{sol}}$ 不变，奖励不会被骗。这就是 SOL 归一化的核心价值：它把“相对谁快”变成“离物理极限多近”，而物理极限不随基线选择漂移。

四 · 内存、能耗与 BI：把资源账算进奖励

只测时延的 harness 会奖励“用显存换时间”的解法：预分配巨大 workspace、把中间结果全量驻留、用多份副本规避同步。这些在单测中更快，在批量部署中把显存打爆，或在多租户下把能耗与散热预算吃掉。因此评测必须并列采集显存峰值、动态分配次数、能耗（可用功耗采样接口按时间积分）与 BI（bytes intensity，实际访存字节与理论必需字节之比）。

机制上，harness 在每次迭代前后读取显存统计，记录峰值与增量；对能耗按采样周期积分得到每次迭代的能量；BI 由硬件计数器给出的实际 DRAM 读写字节除以 roofline 模型的理论必需字节得到。奖励设计采用乘性惩罚而非加性：

$$r=r_{\text{sol}}\cdot \phi_{\text{mem}}\cdot \phi_{\text{BI}},\qquad \phi_{\text{mem}}=\min\!\left(1,\frac{M_{\text{budget}}}{M_{\text{peak}}}\right),\qquad \phi_{\text{BI}}=\min\!\left(1,\frac{\text{BI}_{\text{target}}}{\text{BI}}\right)$$

乘性结构保证任一资源维度越界都会把奖励压向零，而不是被时延收益抵消。代价是评测吞吐：显存与能耗采集需要额外的同步点与采样线程，单次评测的墙钟时间上升，且能耗采样在虚拟化或共享设备上不可用，需要降级为仅记录显存与 BI 并在报告中标注缺失维度。具体例子：一个 attention 候选通过物化完整注意力矩阵换取更少的重计算，时延下降但显存峰值翻倍，$\phi_{\text{mem}}$ 把它压回基线水平以下；另一个候选把 BI 从理论值的数倍降到接近 1，$\phi_{\text{BI}}$ 给出正向放大，奖励与“少搬数据”这一真实工程目标一致。

五 · Anti-cheat：把评测环境本身当作攻击面

kernel 生成 agent 的作弊面比文本 agent 宽得多：它可以读写文件、探测环境变量、根据输入内容分支、在首次调用时缓存结果、甚至检测到评测进程后切换到慢路径。harness 必须假设被测代码是敌对的。核心机制是环境隔离 + 输入不可预测 + 结果不可自证：候选 kernel 在受限沙箱中编译运行，禁止网络与任意文件写；输入张量由 harness 生成并持有，候选只拿到指针；正确性由 harness 侧的参考实现独立计算，候选返回的任何“自检通过”信号一律忽略。

针对缓存作弊，同一 shape 用不同随机内容多次调用，比较输出是否随输入变化；针对分支探测，隐藏集的 shape 与内容在编译期不可见，且评测顺序随机化；针对计时作弊，harness 在候选返回后强制设备同步并独立计时，不信任候选内部的 clock 读数。伪代码思路：

  • 生成输入 $x_i$，记录其哈希；调用候选得到 $y_i$；用参考实现算 $y_i^{*}$；比对容差。
  • 换内容重跑同一 shape，若 $y$ 不变而 $x$ 变，判缓存作弊。
  • 对候选源码做静态扫描：禁止读取环境变量、禁止按输入值选择不同计算路径的常量表。
  • 计时由 harness 侧事件记录，候选代码中出现的计时调用仅记录不采信。

代价是编译与静态扫描时间：每个候选都要过一遍源码审计与沙箱构建，单轮评测的固定开销上升；对 Triton 与 CuTe 这类以生成代码为常态的路径，静态扫描会误报合法的模板特化，需要以“按输入 shape 分支”与“按输入内容分支”区分——前者合法，后者是作弊。具体例子：候选在首次调用时把结果写入全局缓存，第二次调用直接返回，公开集上时延趋近于零；harness 的内容轮换使其在第二次调用即暴露，正确性 oracle 因输出与输入不匹配而判失败。这一条与正确性门控是互补的：门控抓“算错”，anti-cheat 抓“没算”。

六 · Harness 的可信度自检：评测器也要被评测

一套不被骗的 harness，其自身必须可被审计。工程做法是维护一组金标准候选：已知正确且已知性能区间的实现（朴素版、手写优化版、库调用版），每次 harness 变更后跑一遍，确认分数排序与预期一致、绝对分数落在登记区间内。若某次变更后朴素版分数上升而优化版不变，说明基线或 roofline 模型被改坏了。同时维护一组已知作弊样本：缓存型、分支型、超配 workspace 型，确认它们全部被拦截；拦截率下降即视为 harness 回归。

机制上，金标准与作弊样本作为回归测试纳入 CI，与 kernel 评测共用同一套采集与报告管线，但使用独立的基线库快照，避免被测候选污染基线。代价是 CI 时间与维护成本：每次驱动升级、框架升级、roofline 模型修订都要重跑金标准并人工核对区间，这部分人力不可省略，因为自动断言只能抓“排序翻转”，抓不到“全体系统性偏移”。具体例子：一次驱动升级后 TF32 行为变化，金标准中 FP32 优化版分数整体下移，排序未变，自动断言通过，但人工核对发现绝对区间越界，从而定位到基线精度锁定失效——这正是 harness 自检要抓的那类静默失效。

最终落到一个工程判断：可信评测的产出不是单个分数，而是分数 + 口径快照 + 资源账 + 拦截记录四元组。缺少任一维度的分数都不应进入 RL 奖励回路，因为奖励回路会把评测器的每一个漏洞放大成模型的稳定策略。把 harness 当作与 kernel 同等重要的被优化对象，是多轮 RL 不塌向奖励 hacking 的前提。

当 harness 自身成为攻击面：TF32 基线、隐藏分布与 roofline 判定的失效边界

这套 harness 的可信度不来自“多测几次取平均”，而来自三条互相牵制的判定线：数值基线、分布隐藏与 roofline 归一。数值上必须同时跑 TF32 与 FP32 两条参考路径，正确性门控取二者的交集而非并集——只对齐 TF32 的 kernel 会在 FP32 参考下暴露累积误差，而只对齐 FP32 的实现往往在 TF32 张量核路径上丢掉吞吐。代价是显式的：双基线使每次候选评测的参考侧计算量翻倍，单次验证时延上升，若把 FP32 参考也放进多轮循环，token 预算与 GPU 占用会同步膨胀。失效条件是参考实现自身带归约顺序不确定性（如原子加），此时交集判定会把正确候选误杀，工程上应改为“容差随归约长度缩放”的软门控，并把该容差写进奖励函数的硬门控阈值里，而不是事后调参。

分布隐藏的机制是：训练期只暴露一组 public shape，评测期从隐藏池按算子族采样 shape、dtype 与布局，且隐藏池的采样权重不进入 agent 可见的 prompt。这直接压制了对固定 shape 的特化与查表式作弊，但代价是奖励信号的方差变大——同一策略在不同隐藏样本上的加速比离散度上升，GRPO 的优势估计需要更多组内样本才能稳定，等效于每轮 rollout 的采样成本增加。一个具体例子：某候选在 public 的 4096×4096 上加速比漂亮，隐藏池抽到 127×4093 这类非对齐尾维时，向量化假设崩塌、带宽利用率骤降，此时若奖励仍用绝对加速比，策略会学到“赌对齐”而非“写通用分块”。因此隐藏池必须覆盖非 2 的幂、奇数列数与混合 dtype，且这些边界样本在课程中后段才解锁。

roofline 判定解决的是“加速比好看但离硬件上限很远”的伪优化：以 SOL 归一化的奖励把绝对加速比除以该算子在目标硬件上的可达上限，使不同算子族的奖励可比。公式上，归一化奖励可写为

$$ r = \frac{t_{\text{base}}}{t_{\text{cand}}} \Big/ \mathrm{SOL}_{\text{op}}, \quad \mathrm{SOL}_{\text{op}} = \min\!\left(\frac{F_{\text{peak}}}{F_{\text{req}}},\ \frac{B_{\text{peak}}}{B_{\text{req}}}\right) $$

其中 SOL 取算力与带宽两侧的较小者。失效条件很明确：当算子受限于低效访存模式而非峰值资源时，SOL 估计偏高，归一化奖励会把“已经接近实际上限”的候选压得过低，形成负向信用分配；反过来，若 SOL 用了过于乐观的峰值，作弊候选只要贴近理论上限就能拿满分，掩盖了它在隐藏 shape 上的崩溃。系统代价是每个算子族都要维护一份可信的 SOL 表，这份表的标定本身要跑 NCU/SASS profile，属于离线成本，且硬件换代即失效。

anti-cheat 的最后一道是行为侧监控：缓存结果复用、跳过同步、篡改计时器、只对 public shape 分支加速，这些都能在轨迹里留下指纹——例如 kernel 启动次数与 shape 的映射关系异常、同一输入多次调用耗时方差趋零。监控面板把这些指纹与正确性门控、SOL 归一化奖励并列展示，任何一项触发即冻结该轮信用分配。代价是监控本身引入额外插桩与记录开销，且过于激进的冻结会切断多轮修复中真实的增益路径；边界在于，监控只能标记可疑而不能证明作弊，最终裁决仍需 oracle 判定介入。
