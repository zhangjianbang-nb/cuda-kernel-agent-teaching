一 · 把“时间去哪了”变成可观测量：roofline 作为归因的第一把尺

Agent 拿到一个 kernel，最先要回答的不是“它快不快”，而是“它离硬件上限还有多远、差在哪个维度”。roofline 模型给出的正是这个二维坐标系：横轴是算术强度 I（每字节 DRAM 流量对应的浮点运算数），纵轴是可达性能。峰值算力 Ppeak 与峰值带宽 Bpeak 的比值定义了拐点 Iridge = Ppeak / Bpeak。当 I < Iridge 时，kernel 落在带宽受限区，可达性能上界为 I · Bpeak；反之落在算力受限区，上界为 Ppeak。

$$P_{att} = \min\left(P_{peak},\; I \cdot B_{peak}\right),\qquad \text{SOL} = \frac{P_{measured}}{P_{att}}$$

工程上真正有用的是把 SOL（speed-of-light）拆成两个可诊断的量：一是实测带宽利用率，二是实测算力利用率。二者中较高的那个告诉你“瓶颈侧已经压到多少”，较低的那个告诉你“另一侧还有多少余量”。一个典型的误判场景：agent 生成的分块矩阵乘 kernel 实测 SOL 只有三成，它误以为是算力不足而去加大 tile、提高寄存器占用，结果 occupancy 掉到每 SM 仅数个 warp，时延反而变差。正确的读法是先看带宽侧利用率——若带宽侧已接近饱和而算力侧远低，说明问题在数据复用不足（shared memory 分块粒度或 swizzle 布局），而不是在指令吞吐。roofline 的代价是它只给上界、不给路径：它无法区分“带宽打满是因为真的需要这么多字节”还是“因为合并访问失败导致实际流量翻倍”。这就必须交给下一层的计数器。

把 roofline 接入 agent 的方式不是让模型心算，而是把 profile 输出结构化：每个 kernel 一条记录，含 I、实测 P、两侧利用率、以及相对上一次版本的差分。差分比绝对值更有信息量——一次数值精度事故的排查中，正是“带宽利用率不变而算力利用率骤降”这一差分模式，把归因从“数据布局退化”纠正到“新增的边界判断分支拖垮了内层循环”。

二 · warp stall 归因：把“等待”拆成可命名的类别

roofline 说“差多少”，stall 分析说“为什么等”。SM 上的 warp 调度器在每个周期从就绪 warp 中发射指令；当所有 warp 都不可发射时，采样器记录一个 stall reason。主流 profiler 给出的分类包括：long scoreboard（等待全局/本地内存返回）、short scoreboard（等待 shared memory 或 MIO 队列）、barrier（等待 __syncthreads）、MIO throttle（特殊功能单元队列满）、LG throttle（全局内存指令队列满）、not selected（有就绪 warp 但调度器选了别人）、以及 execution dependency（等待前一条指令的寄存器结果）。

关键机制在于：stall 的比例必须与 occupancy 联合读。高 long scoreboard 占比在低 occupancy 下意味着延迟无法被其他 warp 掩盖，解法是提高并行度或做软件流水预取；同样的高 long scoreboard 在高 occupancy 下则意味着带宽真的被打满了，解法转向减少流量（提高复用、压缩数据类型、改进合并访问）。仅凭 stall 百分比下结论，是 agent 最常犯的归因错误之一。

一个具体例子：某归约 kernel 的 profile 显示 barrier stall 占比最高。agent 的第一反应是删掉同步点，但正确诊断是每个 block 内的 warp 工作量不均——部分 warp 提前到达 barrier 空转。解法是让分块边界与 warp 数对齐，使各 warp 处理等量元素。这里付出的代价是尾部元素的处理路径变复杂，代码分支增多，编译后指令数上升，寄存器压力增加，可能反过来压低 occupancy。这就是典型的“修一个 stall 引入另一个 stall”，必须靠修改后的再 profile 闭环验证，而不是靠推理宣布修好了。

把 stall 归因做成 agent 可消费的形式，需要一张“stall reason → 候选动作”的映射表，并为每个动作标注预期副作用（例如“提高 occupancy 可能增加寄存器溢出”“减少同步可能引入竞态”）。这张表本身就是可靠性体系的一部分：它让失败归因树（编译/数值/性能/集成）中的“性能”分支有了可执行的下一层。

三 · SASS：越过源码看真实指令流

CUDA C++ 或 Triton 源码到 SASS 之间隔着编译器的大量变换：循环展开、指令重排、谓词化、向量化、常量折叠、以及寄存器分配带来的 spill。Agent 若只看源码做优化，等于在错误的抽象层上推理。SASS 层面能看见的东西包括：实际的 load/store 宽度（是否真的合并成 128-bit）、是否有 local memory 的 LDL/STL（寄存器溢出）、内层循环的指令条数、以及是否存在被谓词化掉的冗余分支。

一个可操作的检查顺序：先数内层循环的指令条数，与理论最小值比对，差额往往来自地址计算与边界判断；再查是否存在 LDL/STL，一旦出现说明寄存器压力已越过阈值，此时提高 tile 尺寸或展开因子会进一步恶化；最后看内存指令的宽度与对齐，判断合并访问是否成立。这套检查的代价是 SASS 与源码的对应关系不总是一一映射，agent 很难把某条 SASS 指令精确回溯到某一行源码，因此反馈信号应当以“统计特征”而非“逐行定位”的形式给出，例如“内层循环 47 条指令，其中 12 条为地址计算”。

把 SASS 纳入 agent 反馈回路有一个现实约束：反汇编与解析本身要花时间，且不同架构的指令集不同，工具链版本会影响输出。因此它适合作为“深挖阶段”的信号，而不是每轮迭代都跑的常规信号。合理的分层是：常规轮次用高层计数器（roofline + stall），当高层信号指向指令效率问题时才触发 SASS 深挖。这个分层直接决定了 agent 单轮迭代的时延预算——高层 profile 是秒级，SASS 分析加反汇编可能到十秒级，若每轮都做，多轮 RL 的采样吞吐会被显著拖慢。

四 · 二进制插桩：在无法改源码时拿到时间线

当 kernel 来自闭源库、或源码被框架封装、或需要在不重新编译的前提下观测时，二进制插桩是唯一路径。典型做法是在 SASS 层插入计数或时间戳指令：在每个基本块入口记录时钟，或在指定指令前后打点，从而得到每个基本块的周期数分布。这比采样式 profiler 更精确，因为采样有间隔、会漏掉短命的基本块。

插桩的代价是双重的。其一是观测开销改变被测对象：插入的指令本身占用发射槽与寄存器，可能把原本的瓶颈从内存等待推到指令吞吐，测出来的时间线已经不是原始 kernel 的时间线。其二是可移植性：插桩依赖具体的指令编码与架构特性，跨架构迁移需要重做。因此插桩的定位应是“疑难案件的取证工具”，用于回答“这个分支到底执行了多少次”“这段代码的周期占比是否与静态估算一致”这类采样无法回答的问题，而不是常规流水线的一环。

一个具体场景：某线上 kernel 出现性能回退告警，但源码未变、编译选项未变，profile 显示各项利用率都在正常范围。二进制插桩后发现某个数据依赖的分支在不同输入分布下走了不同路径，而该路径的指令缓存命中率显著更低。这类问题在源码层完全不可见，只有插桩加指令地址采样才能定位。它对应的工程判断是：可靠性体系里的“性能回退告警”不能只比对 kernel 级总时延，还要保留输入分布这一维度，否则同一 kernel 在不同 batch 形状下的表现差异会被误判为随机波动。

五 · 让 agent 看见：反馈信号的结构化与预算分配

上述四类信号要真正被 agent 用起来，必须解决三个工程问题：结构化、可比、有预算。

结构化指把 profiler 的原始输出转成固定 schema 的记录，字段包括 kernel 标识、版本、输入形状、roofline 两侧利用率、top-3 stall reason 及占比、内层循环指令数、spill 字节数。自由文本的 profiler 日志对模型是噪声，固定 schema 才能支撑跨轮次比较与失败归因树的自动挂接。

可比指同一 kernel 的不同版本必须在同一输入形状、同一 profiler 配置下测量，且记录测量噪声水平。否则 agent 会把噪声当成改进。多轮 RL 中这一点尤其致命：若奖励基于不可比的测量，策略会学到“挑一个测量友好的形状”而不是“写出更快的 kernel”。

有预算指明确每类信号的时延与 token 成本。高层计数器便宜，可每轮跑；SASS 深挖昂贵，按需触发；插桩最贵，仅在告警复盘时用。这个预算分配直接决定了 agent 的迭代节奏：把昂贵的信号放进常规回路，会让单轮时延从秒级升到十秒级，采样吞吐下降一个量级，进而影响多轮 RL 的有效样本量。

信号层回答的问题典型代价触发条件
roofline离上限多远、哪一侧受限低，秒级每轮
warp stall为什么等、等待能否被掩盖低到中每轮或 SOL 低于阈值时
SASS指令效率、spill、合并宽度中，十秒级高层信号指向指令效率时
二进制插桩基本块级时间线、分支实际执行高，且改变被测对象告警复盘、疑难取证

最后一点工程判断：反馈信号的价值不在于“多”，而在于“能证伪 agent 的假设”。一个只有 SOL 数字的反馈回路，agent 只能做盲目搜索；一个带 stall 分类与 SASS 统计特征的回路，agent 才能提出可检验的假设并在下一轮验证。可靠性体系中的性能回退告警若只挂总时延，归因树就退化成“重跑一遍”；挂上 roofline 差分与 stall 分布差分，归因才能落到具体机制上，事故复盘模板也才有可填的内容。

当 NCU 采样本身成为扰动：硬件反馈链路的失效边界与系统代价

把 NCU 或 SASS 反汇编接入 agent 的观测回路，最容易被忽略的前提是：观测行为本身会改变被观测对象。NCU 默认采用基于硬件计数器的多趟重放（multi-pass replay），每一趟只开一组计数器，同一 kernel 被反复执行多次以拼出完整指标集；开启 --set full 时重放趟数可达数十趟，加上 --cache-control all 的缓存刷新，被测 kernel 的实际执行时间与缓存行为已偏离生产态。对 agent 而言这意味着：它看到的 stall 分布是"被插桩后的 stall 分布"，而非线上真实分布。当 kernel 本身处于 L2 容量临界点或依赖跨趟的缓存预热时，重放会系统性地放大 memory throttle 与 long scoreboard 的占比，agent 据此做出的"减少全局访存"决策可能在生产态下毫无收益甚至负收益。工程上的边界条件应写死为：只有当单趟重放开销相对 kernel 稳态执行时间可忽略、且 kernel 无跨调用状态时，NCU 的 stall 归因才可作为优化信号；否则必须退化为单趟轻量计数器采样。

采样率与开销的权衡需要显式建模，而不是凭经验设一个百分比。设线上 kernel 调用频率为 f，单次调用稳态耗时为 T，插桩后单次耗时膨胀为 T(1+δ)，采样比例为 p，则监控引入的额外时间占比为

$$\eta = \frac{p\,\delta}{1 + p\,\delta} \approx p\,\delta$$

当 δ 在重放模式下远大于 1 时，即便 p 取很小的值，η 也会迅速吃掉生产吞吐。更隐蔽的代价是尾延迟：插桩调用被随机插入到请求路径中，其膨胀后的耗时直接落在该请求的关键路径上，P99 时延的抬升幅度与 p·δ 同阶，而告警阈值若按均值设定则完全看不见这一抬升——这正是"阈值按分位数还是均值"这一关键决策在 profile 链路上的投影。可行的折中是分层采样：对稳态高频 kernel 只采硬件计数器的单趟快照（δ 接近 0），对疑似回退的 kernel 才触发全量重放，并把重放限定在影子流量或离线回放环境，使 δ 不进入线上关键路径。

SASS 与二进制插桩的失效条件与 NCU 不同，代价结构也不同。SASS 反汇编给出的是静态指令序列，agent 从中读取寄存器压力、指令混合与访存指令宽度，但静态视图无法区分"指令存在"与"指令在热路径上被执行"——分支发散下的谓词执行会让静态指令计数与动态指令计数严重背离，agent 若按静态 SASS 估算 occupancy 上限，会把寄存器溢出导致的 local memory 流量误判为可优化项。二进制插桩（如在 kernel 入口/出口打点、按 warp 记录时间戳）则引入每 warp 的额外指令与同步开销，在占用率高的 kernel 上插桩点本身会成为新的 stall 源，且时间戳读取的序列化会破坏 warp 间的自然重叠，测得的"时间去哪了"被插桩粒度重新切分。其代价可定性表述为：插桩密度越高，测得的 stall 归因越细，但被测量对象偏离真实执行流的程度越大；当插桩开销与 kernel 有效计算量同阶时，数据只剩相对参考价值。

因此 agent 的 profile 回路需要一个显式的"反馈可信度"门控，而不是无条件信任任何一次采集。判据可组织为一张准入表：

反馈源可信条件主要代价典型失效
NCU 全量重放无跨调用状态、δ 可控多趟重放时间膨胀、缓存刷新临界容量 kernel 的 stall 被放大
单趟计数器快照指标集受限但 δ≈0指标不全，需多次采样拼合无法定位细粒度 stall 来源
静态 SASS无严重分支发散零运行时开销静态/动态指令计数背离
二进制插桩插桩开销远小于有效计算每 warp 打点、序列化插桩点成为新 stall 源

这张表的作用不是选一个最好的源，而是让 agent 在给出优化建议时附带"该建议基于何种可信度"的标注。例如一次数值精度事故后的归因中，若 agent 依据全量重放数据判定某 kernel 的 shared memory bank conflict 是主因，而该 kernel 恰处于 L2 临界容量，则归因树应把"观测扰动"列为待排除分支，先以单趟快照复核再进入修复。可靠性体系在这里的价值不是提供更细的 profile，而是让每一条 profile 结论都带着它的失效边界一起进入归因树，使团队从"相信最后一次采集"转向"知道这次采集能证明什么"。
