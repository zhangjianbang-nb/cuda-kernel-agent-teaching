一 · 多轮奖励的信用分配：从轨迹到 token 的折扣结构

生产端到端落地的 RL 数据链路，与离线评测最大的差别在于奖励的到达方式：一次 kernel 生成任务往往包含“读题—写初版—编译—跑正确性—看 profile—改写—再编译”多轮交互，最终只有一个端到端信号（是否通过 oracle、端到端时延是否达标）。把单点奖励摊回多轮动作，是本部分第一个要处理的机制问题。工程上常用的是带折扣的轨迹回报：设第 t 轮动作后环境给出即时奖励 r_t（编译失败为负、正确性通过为正、profile 改善为小幅正），则第 k 轮动作的优势估计写成

$$A_k=\sum_{t=k}^{T}\gamma^{\,t-k}r_t-\hat V(s_k)$$

其中 γ 取接近 1 的值以让早期决策（例如是否选择融合策略、是否换用 Triton 而非 CUDA C++）分享到最终收益，\hat V 是同一 prompt 下多次采样的基线。代价在于方差：折扣越接近 1，轨迹越长，基线估计越不稳，需要更多采样才能压住噪声；而每多一轮编译加一次 NCU profile，单条轨迹的墙钟成本就上升一个量级。具体例子：一个 reduction kernel 的任务，模型在第 2 轮选择了 shared memory 分块，第 5 轮才通过正确性，若 γ 取 0.99，则第 2 轮分到的回报约为最终奖励的 0.97 倍，选择被正确强化；若取 0.9，则只剩 0.66 倍，早期正确决策被稀释，策略会退化成“先随便写、靠后期修补”。工程判断是：编译/正确性类信号放在早期轮次并给稀疏正奖励，性能类信号只在通过 oracle 后发放，避免模型学会用错误 kernel 骗取 profile 数字。

二 · robust reward：把可验证信号做成抗噪的判据

多轮 RL 的第二个陷阱是奖励被“钻空子”。kernel 任务的奖励天然包含三类噪声源：计时抖动（同一 kernel 多次运行方差可达数个百分点）、编译器版本差异导致的性能漂移、以及模型通过特判输入形状或硬编码常量“骗过”正确性检查。robust reward 的做法是把奖励从单次标量改成带置信区间的判据：对同一 kernel 做 n 次重复计时，取中位数并计算相对离散度，只有当离散度低于阈值时才把加速比计入奖励；正确性侧则用多组随机输入加边界形状（如 N=1、非 2 的幂、超大 stride）做 oracle，任一失败即整条轨迹奖励截断。一个可操作的伪代码思路是：

  • 奖励 = 通过 oracle 的组数占比 × min(实测加速比, 上限) × 稳定性系数；
  • 稳定性系数 = 1 若计时离散度低于阈值，否则线性衰减到 0；
  • 对硬编码嫌疑做静态检查：源码中出现与测试形状相同的字面量则扣分。

代价是采样成本：把每条轨迹的计时从 1 次提到 n 次，单条轨迹的 GPU 占用时间线性上升，在共享集群上直接压缩了并行轨迹数，进而拉长 RL 的墙钟周期。具体例子：某元素级 kernel 在 N=1024 上加速 3 倍，但在 N=4097 上因未处理尾块而回退到标量路径，单形状评测会给高分，多形状 oracle 则直接判负——这正是生产端最怕的“微基准好看、真实负载翻车”，与故事中 1.8x 微基准只换来 4% 端到端收益的教训同源。

三 · TRLOO：把留一法基线搬进多轮轨迹

多轮场景下，同一 prompt 的 G 条轨迹共享前缀，朴素地拿全体均值做基线会把“题目难度”和“策略好坏”混在一起。TRLOO（leave-one-out 形式的轨迹基线）的核心是：对第 i 条轨迹的优势，用其余 G-1 条轨迹的回报均值做基线，即

$$A_i=\frac{G}{G-1}\left(R_i-\frac{1}{G}\sum_{j=1}^{G}R_j\right)$$

这个系数 G/(G-1) 保证在无偏前提下不引入组内均值带来的收缩偏差，等价于对组内回报做中心化后再放大。它在多轮里的价值在于：同一 prompt 下不同轨迹可能走完全不同的路径（一条走 CuTe 模板、一条走手写 PTX），留一法让每条路径只与“同题的其他路径”比较，而不是与全局平均比较，从而避免高难度题目整体被压低优势。代价是组大小 G 直接决定显存与吞吐：每条轨迹都要保留完整的多轮上下文与工具输出（编译日志、profile 摘要），G 翻倍意味着 KV cache 与轨迹缓存的显存占用翻倍，在长上下文下这是硬约束。具体例子：一个 softmax kernel 的 8 条轨迹中 3 条因编译错误提前终止，留一法会把它们的负优势按剩余 5 条的正常回报校准，而不是让 3 条失败轨迹把整组均值拉到负值、误伤那 5 条正确路径。

四 · 合成数据：从真实仓库与形状分布反推任务

生产端到端落地需要的不是 KernelBench 式的孤立算子，而是“真实模型里的热点 + 真实形状 + 真实精度约束”。合成数据的机制是三步反推：从目标框架的模型图里抽取热点算子及其输入形状分布（含动态维度的分位点），从真实 trace 里抽取调用频次与前后依赖，再把这些约束写成任务描述与 oracle 的测试用例集。这样合成的任务天然带端到端口径：一个 kernel 只有在真实形状分布上通过正确性、且在端到端链路上不被框架的 fallback 路径绕过，才算有效样本。代价是数据构建的工程投入与污染风险：从开源仓库抽取的代码片段可能已经包含目标 kernel 的实现，若不去重，模型是在背答案而不是学方法。具体例子：为 vLLM 的 attention 后端合成任务时，把 batch 与序列长度的联合分布按真实 serving trace 的分位点采样，而不是均匀采样，能让模型学到“短序列低 batch 走小 kernel、长序列走分块”的分支判断，这类判断在均匀形状上根本不会出现。

五 · 轨迹 SFT 与去重防污染：让监督信号对齐推理时的动作序列

轨迹 SFT 与普通指令 SFT 的差别在于监督的是动作序列而非最终答案：一条合格样本应包含“读 profile 摘要 → 定位瓶颈（带宽还是计算）→ 选择改写方向 → 编译 → 用 oracle 自检 → 提交”的完整链路，且每一步的工具输出都是真实执行结果而非模型自述。构造时通常只对关键决策步计算损失，把冗长的编译日志与重复的试错轮次做掩码，否则 token 预算会被日志吞掉。代价体现在 token 与训练时长上：一条含 5 轮工具调用的轨迹，其 token 数往往是最终代码的十几倍，若不做掩码与截断，单条样本的有效监督密度极低。去重防污染则是同一批数据的另一半工作：对合成任务与公开基准做代码级近似去重（归一化后比对函数体与常量表），对评测集做 prompt 级哈希隔离，确保 SFT 数据里不出现评测题的原题或其改写。具体例子：某批轨迹 SFT 数据中，模型在“看到编译错误后回退到朴素实现”这一步上被大量监督，导致上线后遇到编译失败就放弃优化；把这类轨迹按结果过滤（只保留最终通过 oracle 的轨迹）后，模型学会了在编译失败后换策略重试，而不是回退。工程判断落在数据配比上：合成任务提供形状与框架约束的覆盖，真实仓库轨迹提供工程风格与调试习惯，两者按任务难度分层混合，比单纯扩大合成规模更能提升端到端通过率。

六 · 奖励与数据的闭环：把端到端收益写进训练信号

上述机制要真正服务于生产落地，最后一步是把端到端收益归因接进奖励与数据筛选。微基准加速比只能作为中间信号，最终奖励应以“该 kernel 在目标框架链路中的时间占比 × 端到端时延改善”为口径，否则模型会持续优化那些占比极低、对端到端无感的算子。可操作的判据是：只有当 kernel 时间占比超过阈值、且端到端 A/B 的改善在统计上稳定时，该轨迹才进入高权重样本池；占比低但微基准提升大的轨迹降权保留，用于维持模型的优化能力但不主导策略。代价是归因本身需要真实负载的回放环境，A/B 回放的机器成本与灰度窗口的等待时间会拖慢数据回流周期，使 RL 迭代从“小时级”变成“天级”。具体例子：故事中那个微基准 1.8x、端到端仅 4% 的 kernel，若按端到端口径计算奖励，其优势值会被压缩到与普通样本相当，模型不会把它当作成功范式反复复制；而真正把端到端时延压下来的融合算子轨迹会被显著加权。这一判断也决定了灰度与回滚阈值的设计：奖励口径与灰度观测口径必须一致，否则训练端认为的“好 kernel”在灰度里会被回滚，数据闭环就断在部署这一步。

奖励信号在端到端账本上的失真与鲁棒化

多轮 RL 的奖励若直接取微基准加速比，训练目标与生产收益之间会系统性错位：agent 学会的是把单个 kernel 的 SOL 利用率推到极限，而端到端只关心该 kernel 在真实负载时间占比下的加权收益。故事里微基准 1.8x、端到端仅 4% 的落差，本质是奖励函数缺少“占比”这一乘子。设第 i 个候选 kernel 的微基准加速为 $$s_i$$、其在目标负载中的时间占比为 $$f_i$$，则按 Amdahl 口径的端到端收益近似为 $$\Delta T/T \approx f_i\left(1-\frac{1}{s_i}\right)$$。当 $$f_i=0.05$$、$$s_i=1.8$$ 时该式给出约 2.2% 量级，与观测到的 4% 同阶——这说明奖励必须写成 $$r=\hat f_i\cdot(1-1/\hat s_i)-\lambda\cdot c_{\text{integ}}$$，其中 $$\hat f_i$$ 来自 profile 采样的时间占比估计，$$c_{\text{integ}}$$ 是集成代价（框架适配、精度校验、回归用例）。代价是每轮 rollout 都要跑一次带 NCU 采样的端到端 trace，单条轨迹的 wall-clock 从纯微基准的秒级涨到分钟级，采样吞吐下降一个量级；若用离线 profile 缓存替代在线采样，则 $$\hat f_i$$ 在负载漂移后失效，奖励重新失真。鲁棒奖励的工程做法是对 $$\hat f_i$$ 取分位而非均值，并对 $$s_i$$ 做多 shape 的最差-case 聚合，避免 agent 针对单一 shape 过拟合。

TRLOO（token-level leave-one-out）类信用分配解决的是另一类失效：一条轨迹里既有正确的 kernel 改写也有错误的边界处理，序列级奖励无法区分贡献，导致正确片段被错误片段拖累而遭惩罚。TRLOO 的思路是对每个 token 位置做留一基线估计，用同一 prompt 下其余采样的平均奖励作为该位置的对照，从而把优势写成 $$A_t = r - \frac{1}{K-1}\sum_{j\neq k} r_j$$ 的 token 级形式。它的边界在于：当组内采样数 $$K$$ 很小（受显存与编译时间约束，kernel 任务的 rollout 往往只能开少量并行），留一估计的方差极大，优势信号被噪声淹没；且 kernel 代码的正确性奖励是稀疏的（编译失败、数值不符、超时），大量 token 共享同一稀疏奖励，TRLOO 退化为常数偏移。系统代价体现在显存：每个 prompt 需保留 $$K$$ 条完整轨迹的 logprob 与激活，长 kernel 代码（数百行 CUDA）使 KV 与激活占用线性上升，直接压缩 batch size，反过来又加剧 $$K$$ 小的困境。

合成数据与轨迹 SFT 的边界是污染与分布漂移。用强模型生成 kernel 轨迹做 SFT，若不去重，同一道 KernelBench 题目的近似重复样本会主导梯度，模型学到的是题目记忆而非改写策略；更隐蔽的是评测集泄漏——合成时若以基准题面为种子，生成的轨迹可能携带基准的参考实现片段，使离线指标虚高而在生产负载上失效。去重需在语义层做：对 kernel 源码做规范化（去除注释、统一变量名）后按 AST 结构哈希，再对轨迹做指令级 n-gram 近似去重，代价是每批数据要跑一次解析与哈希流水线，吞吐受 Python AST 解析限制。防污染则要求合成种子与评测题目做显式隔离，并在训练日志里记录每条轨迹的来源标签，便于事后审计。轨迹 SFT 的另一代价是 token 预算：一条含多轮编译反馈与修正的完整轨迹动辄数千 token，其中大量是重复的报错信息，需按“保留首次失败与最终修复”裁剪，否则 SFT 的有效信息密度被稀释。

把这些机制放进生产账本，判断标准不是离线奖励涨了多少，而是灰度阶段端到端指标能否复现。一个可操作的护栏是：任何进入候选池的 kernel 必须同时通过微基准 SOL 阈值、多 shape 最差-case 正确性 oracle、以及集成后的端到端 A/B（含框架开销与精度容差）。鲁棒奖励的作用是让 RL 不奖励那些“微基准漂亮但集成代价高”的解——例如为追求 1.8x 而引入额外的一次全局同步或格式转换，其 $$c_{\text{integ}}$$ 在端到端 trace 里表现为 kernel 时间占比不降反升。工程判断落在采样预算的分配上：把有限的 rollout 预算优先给时间占比高的热点 kernel，对占比低于阈值的候选直接跳过 RL 精调，只做规则化筛选，这比在低收益 kernel 上堆多轮奖励更能守住端到端收益。
