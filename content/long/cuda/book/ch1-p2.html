一 · 把「快」拆成三层可复核的量

业务侧说「这个 kernel 要快三倍」，这句话在工程上不可执行，因为它没有指定比较对象、测量边界和数值前提。本卷的口径工作第一步是把「快」拆成三个互相不可替代的量：相对基线的加速比、相对硬件上限的 SOL 占比、以及端到端时延。三者回答的是不同问题，混用会直接导致验收争议。加速比回答「比现有手写实现好多少」，它的分母是团队已有的实现与其测量条件；SOL 占比回答「离这台机器的物理上限还有多远」，它的分母是 roofline 模型给出的理论下界；端到端时延回答「这次优化在真实调用链里值多少钱」，它的分母是整个算子在图或服务中的实际耗时。一个 kernel 可以加速比很高而 SOL 占比很低（基线本身很差），也可以 SOL 占比很高而端到端收益为零（该 kernel 在总时延中占比极小）。因此验收口径必须显式声明用哪一个量作为主判据，其余两个作为辅助证据。

机制上，这三层量对应三种不同的测量装置。加速比需要固定基线二进制与固定输入分布，在同一软件栈版本下重跑；SOL 占比需要构造 roofline 模型，即按 dtype 与累加精度算出必须搬运的字节数与必须完成的浮点运算数，再分别除以实测带宽与实测峰值算力，取两者较大者作为时间下界：

$$T_{\text{SOL}} = \max\left(\frac{\text{Bytes}_{\text{req}}}{BW_{\text{eff}}},\ \frac{\text{FLOPs}_{\text{req}}}{F_{\text{eff}}}\right),\quad \text{SOL ratio} = \frac{T_{\text{SOL}}}{T_{\text{measured}}}$$

这里 BW 与 F 的下标 eff 是关键：必须用同一张卡上实测的有效带宽与有效算力，而不是厂商标称峰值，否则 SOL 占比会被系统性高估。代价在于，roofline 建模本身要花人力：每个任务类别（elementwise、reduction、matmul、attention、fused）的必需字节数与必需 FLOPs 算法不同，fused 类还要处理中间结果是否落回显存的问题。一个具体例子：elementwise 加法的必需字节数是读两个输入写一个输出共 3N·sizeof(dtype)，其 SOL 时间几乎完全由带宽项决定，算力项可以忽略；而 matmul 的必需 FLOPs 是 2M N K，在较大形状下由算力项主导。若把这两类任务用同一套判据验收，elementwise 会因为「算力利用率低」被误判为不合格。

二 · 基线不是「旧代码」，是一份可复现的测量契约

基线在本卷中不是随手拿来对比的那份旧实现，而是一份契约：它固定了输入形状集合、输入数据分布、dtype 与累加顺序、编译选项、驱动与库版本、以及测量协议（是否含 warmup、是否含 host-device 拷贝、计时用哪种事件）。任何一项变动都会让加速比失去可比性。工程上最常见的失焦来源是基线在测量时用了与候选实现不同的编译优化等级，或者候选实现把输出拷贝排除在计时之外而基线没有。这类差异足以让加速比出现数量级的虚假变化，而它和 kernel 本身的质量毫无关系。

因此口径文档必须为每个任务条目记录一份基线指纹，伪代码思路如下：

  • 记录 shape_set：主形状、边界形状（极小、极大、非对齐）、以及业务真实分布下的形状直方图；验收以主形状为主判据，边界形状作为正确性与不崩溃的附加判据。
  • 记录 dtype_profile：输入 dtype、累加 dtype、输出 dtype 三元组，例如 fp16 输入、fp32 累加、fp16 输出，或 bf16 输入、fp32 累加。
  • 记录 stack：CUDA 版本、编译器版本、cuBLAS/cuDNN 版本、驱动版本，以及是否启用了特定的架构特性。
  • 记录 timing_protocol：warmup 次数、重复次数、取中位数还是最小值、是否使用 CUDA event、是否同步。

代价是显而易见的：为每个任务维护基线指纹意味着基线要随软件栈升级而重测，否则加速比会在栈升级后失真。这笔重测成本必须计入评测预算，否则团队会在半年后发现所有历史加速比都不可比。具体例子：某 reduction kernel 的基线在 fp32 累加下测得的时间，与候选实现在 fp16 累加下测得的时间直接相除，得到的「加速比」混合了精度差异，不能作为性能判据；正确做法是要求候选实现至少在 fp32 累加下给出同口径数字，再单独报告低精度路径的收益。

三 · 容差按 dtype 与累加顺序分级，而不是一个全局阈值

正确性口径与性能口径必须同时定义，否则会出现「快但错」的候选被误收。本卷的做法是按 dtype 与累加顺序分级设定容差，而不是给一个全局的 1e-5。原因在于浮点误差的量级由累加链长度、累加精度和归约顺序共同决定：fp32 累加下的长 reduction 与 fp16 累加下的同一 reduction，误差量级相差数个数量级；matmul 的 K 维长度直接决定误差累积；attention 的 softmax 归一化会放大或抑制某些误差路径。

分级机制可以写成一张按 (dtype 组合, 任务类别, 累加顺序是否确定) 索引的表。对每个条目定义两个阈值：绝对容差与相对容差，并规定比较方式（逐元素、范数相对误差、或统计量如最大值与均值偏差）。伪代码思路是：

  • 若累加 dtype 为 fp32 且归约顺序确定，采用逐元素相对容差加小绝对容差兜底，重点检查接近零的元素。
  • 若累加 dtype 为 fp16 或 bf16，容差按累加链长度的平方根量级放宽，并要求报告误差分布而非单点最大误差，避免被个别离群元素主导判定。
  • 若归约顺序不确定（如并行树形归约、原子加），要求候选实现与参考实现都在同一不确定性下比较，或改用高精度参考（fp64 累加）作为 oracle，再对候选实现单独设定容差。

代价体现在两处：一是高精度 oracle 的计算时间与显存开销，fp64 参考实现在大形状上可能比被测 kernel 慢一个数量级以上，评测流水线必须为此预留时间；二是容差放宽会削弱对真实数值缺陷的检出能力，因此每个放宽都必须附上理由与对应的失败模式清单。具体例子：一个 attention kernel 在 bf16 输入、fp32 累加下，若候选实现改为 fp16 累加以换取吞吐，其相对误差会明显上升；口径必须规定这类改动只能在明确标注的低精度路径下验收，并且该路径的输出要经过下游任务的端到端正确性检查，而不能仅凭单算子容差通过。

四 · 任务分类法决定判据，而不是反过来

本卷把任务分为 elementwise、reduction、matmul、attention、fused 五类，这个分类不是为了归档，而是因为每一类的性能判据与正确性判据结构不同。elementwise 的判据几乎纯带宽，正确性以逐元素比较为主；reduction 的判据是带宽与归约树效率的混合，正确性对累加顺序敏感；matmul 的判据由算力项主导，正确性对 K 维累加与分块顺序敏感；attention 的判据同时受带宽与算力影响，且 softmax 的数值稳定性是独立失败模式；fused 类的判据必须区分「融合后中间结果不落显存」带来的带宽节省是否真实发生，正确性则要覆盖融合边界上的语义等价。

因此口径文档的结构是按类别给出判据模板，而不是给一个统一模板再打补丁。每个模板包含：主性能判据（加速比 / SOL 占比 / 端到端时延三选一或加权）、必测形状集合、容差分级、以及不可接受失败模式清单。后者是本卷特别强调的部分：失败模式清单不是「可能出错的地方」，而是明确列为验收否决项的行为，例如越界写、非确定性输出在要求确定性的场景下出现、在特定形状下退化为串行、以及数值溢出未被检测。代价是模板数量增加带来的维护成本：五类模板乘以 dtype 组合，条目数会迅速膨胀，必须用生成式配置而非手写文档来管理，否则口径本身会成为瓶颈。

具体例子：一个 fused 的 layernorm 加残差 kernel，若候选实现把中间结果写回显存再读入，其带宽项会翻倍，SOL 占比会明显下降；口径模板要求候选实现报告实际显存流量（可通过 profiler 的字节计数核对），而不是仅凭源码结构声称已融合。这一条把「融合」从源码层面的声明变成了可复核的数字。

五 · 可解域与验收粒度是两个独立开关

本卷的关键决策之一是：哪些任务进入 agent 可解域，以及以 KernelBench 级别还是生产级作为验收粒度。这两个开关必须独立设定，因为一个任务可以「agent 能写出正确实现」但「不值得按生产级验收」，也可以「必须生产级验收」但「当前 agent 尚不可解」。把两者绑在一起会导致两种错误：为了迁就 agent 能力而降低生产验收标准，或者为了生产标准而把大量可解任务挡在门外。

机制上，可解域由三个条件联合判定：任务是否有明确的参考实现或可构造的 oracle、性能上限是否可由 roofline 估算、以及失败模式是否可在单算子层面检出。验收粒度则由业务影响决定：KernelBench 级别意味着以基准形状与基准容差为准，产出可比较的数字但不承诺端到端收益；生产级意味着必须覆盖真实形状分布、真实 dtype 路径、以及与下游算子的组合正确性。两个开关的组合形成四象限，口径文档必须为每个任务标注其所在象限，否则后续评测会在「这个数字能不能用于上线决策」上反复扯皮。

代价是生产级验收的成本远高于基准级：真实形状分布意味着更多测量点，组合正确性意味着跨算子测试，端到端时延意味着要搭建可复现的服务或图执行环境。这笔成本必须显式计入，不能隐含在「反正都要做」里。具体例子：一个 matmul 任务在 KernelBench 级别下可以用固定形状与固定容差快速给出加速比，但若业务侧的真实形状包含大量非对齐的 K 维，基准级的数字不能直接用于容量规划；口径必须标注该任务的验收象限，并说明基准级数字的适用边界。

六 · 指标之间的换算关系必须写进口径

最后一层口径工作是把指标之间的换算关系固定下来，使得不同团队报出的数字可以互相校验。加速比与 SOL 占比之间的换算依赖于基线的 SOL 占比：若基线本身的 SOL 占比为 s_0，候选实现的 SOL 占比为 s_1，则加速比近似为 s_1 / s_0（在测量协议一致的前提下）。这个关系式看起来简单，但它给出了一个强约束：任何声称的加速比都必须与 SOL 占比的改善方向一致，若两者矛盾，说明测量协议或 roofline 模型有误。同理，端到端时延的收益上限由该 kernel 在总时延中的占比决定，一个占比很小的 kernel 即使加速十倍，端到端收益也有限，口径必须要求报告这个占比，否则端到端数字无法解释。

这些换算关系写入配置而非文档正文，使得评测流水线可以在报告生成时自动做一致性检查：加速比与 SOL 占比矛盾时标红，端到端收益超出占比上限时标红。代价是配置本身需要随任务类别与硬件更新，且一致性检查只能发现矛盾、不能发现共同错误（例如基线与候选实现用了同一个错误的 roofline 模型）。具体例子：一个 reduction kernel 报告了高于其带宽上限的 SOL 占比，一致性检查会立即暴露该数字不可信，因为 reduction 的必需字节数下界是确定的，任何超过该下界的吞吐都意味着测量边界包含了不该包含的东西，或者字节数被少算。

工程判断上，口径的价值不在于它写得多完整，而在于它能否让两个不同的人独立复现同一个数字。因此本卷要求每个验收条目都附带一条可执行的复核路径：用哪份基线指纹、哪组形状、哪个容差表、哪条一致性检查。缺少复核路径的数字，无论多漂亮，都不进入验收。

口径的边界：当“快”无法被单一数字承载时

把加速比写成 baseline_latency / candidate_latency 看似可复核，但它隐含了一个强假设：基线实现与候选实现在同一输入形状、同一 dtype、同一累加顺序下完成同一语义。一旦任务进入 fused 类别（如 attention 中 softmax 与 matmul 融合），基线往往由多个 kernel 串行拼成，端到端时延包含 launch 开销与中间张量往返 HBM 的带宽代价；此时加速比会系统性高估融合收益，因为分母里混入了本可被消除的显存流量。更稳的口径是把判据拆成三层：单 kernel 的 SOL 占比（以 roofline 的带宽或算力上界为分母）、消除中间张量带来的带宽节省量、以及端到端时延。三层同时记录，任何一层不达标都视为口径失效而非实现失败。

$$\text{SOL}=\frac{\text{achieved FLOPs/s}}{\min(\text{peak FLOPs/s},\ \text{peak BW}\times \text{arithmetic intensity})}$$

失效条件集中在容差分级上。reduction 类任务若基线用 fp32 累加、候选改用 tf32 或分块树形归约，数值路径不同，逐元素比对会因累加顺序产生超出 1 ulp 的偏差；此时正确性 oracle 必须按 dtype 与归约树深度给出分级容差，而不是一个全局 atol。代价是评测吞吐：更严的容差要求参考实现以高精度重算，单任务验证时延上升，且形式验证工具在含数据依赖分支的 kernel 上难以给出闭式证明，只能退化为区间算术加采样。工程判断是：容差分级表必须与任务分类法同表维护，否则 agent 会在“通过正确性”与“通过性能”之间做不可复核的取舍。

系统代价还体现在验收粒度选择上。KernelBench 级别的验收以单 kernel、固定 shape、隔离环境为准，编译时间与 token 消耗可控，但无法暴露生产栈中 stream 并发、显存碎片与多 dtype 混跑的问题；生产级验收要求把候选 kernel 嵌入真实调用链，单次评测的时延与显存占用显著上升，且失败模式从“数值不对”扩展到“抢占 SM 导致邻居 kernel 退化”。因此可解域的划定必须显式标注每个任务落在哪一级粒度，并把不可接受失败模式（如静默溢出、非确定性归约、越界写）写成清单而非阈值，让 agent 的搜索空间在口径层面就被约束住。
