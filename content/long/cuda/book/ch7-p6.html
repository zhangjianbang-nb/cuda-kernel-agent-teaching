一 · 从“分数”到“时间去哪了”：profile 作为奖励信号的前置层

在可验证奖励管线里，评测分数只给出一个标量：正确性门控通过与否、加速比多少、SOL 归一化后落在哪个区间。这个标量对策略更新足够，但对“下一轮该改什么”几乎无信息。agent 拿到一个 1.3× 的加速比，无法判断瓶颈在访存合并、occupancy 不足、指令依赖链过长，还是 launch 配置把 tile 切错了。硬件反馈层的作用，是把标量奖励拆解成可归因的结构化证据，让多轮修复的每一轮都有明确的搜索方向。这一层不是评测的替代品，而是奖励塑形（reward shaping）的输入源：正确性 oracle 决定“能不能给分”，profile 决定“分该往哪个方向涨”。

具体机制上，agent 侧需要一个统一的 profile 采集接口，输入是 kernel 源码 + 固定 shape 集合，输出是三类证据：roofline 落点（计算/带宽受限判定与理论上界距离）、warp stall 分布（stall 原因直方图）、SASS 级指令统计（访存指令宽度、寄存器压力、分支密度）。这三类证据分别回答“天花板在哪”“卡在哪个流水级”“编译器生成了什么”。采集本身有代价：一次 NCU 全量 metrics 采集会把 kernel 串行重放数十次，单次采集的墙钟时间可达毫秒级 kernel 的百倍以上；若在 RL 采样循环里对每个候选都做全量采集，采样吞吐会被 profile 开销吞掉。工程上的折中是分级采集：快速路径只取 roofline 所需的 DRAM 吞吐与 SM 利用率两个计数器（单次 replay），慢速路径在候选进入 top-k 或连续多轮无增益时才触发全量 stall 与 SASS 采集。

$$\text{speedup}_{\text{norm}}=\frac{T_{\text{base}}}{T_{\text{cand}}}\Big/\frac{T_{\text{base}}}{T_{\text{SOL}}}\;=\;\frac{T_{\text{SOL}}}{T_{\text{cand}}}$$

这个归一化把“离硬件上界还有多远”直接写进奖励：当候选的实测时间 $T_{\text{cand}}$ 逼近 roofline 预测的 $T_{\text{SOL}}$ 时，归一化加速比趋近 1，继续优化的边际奖励递减，agent 应转向算子族迁移而非在同一 kernel 上死磕。代价是 SOL 估计本身依赖带宽/算力峰值与访存量的建模，建模偏差会系统性地抬高或压低奖励——这正是奖励 hacking 监控面板要盯的指标之一：归一化奖励的分布若整体贴着 1.0 而实测加速比离散度很大，说明 SOL 建模过于乐观。一个具体例子：一个 elementwise 加法的候选 kernel 实测达到 DRAM 峰值的九成以上，roofline 判定为带宽受限且已接近上界，此时再让 agent 尝试 shared memory 分块只会增加同步开销，profile 证据应当在 prompt 里明确写出“带宽受限、已接近峰值”，阻断这条错误搜索分支。

二 · warp stall 直方图：把“慢”翻译成流水级语言

roofline 给的是上界，warp stall 给的是路径。NCU 的 warp state 统计把每个 warp 在采样周期内处于何种 stall 原因（long scoreboard 等访存依赖、short scoreboard、barrier、MIO throttle、LG throttle、not selected、dispatch stall 等）累计成直方图。agent 需要的不是原始计数器，而是按占比排序的 top-3 stall 原因及其与源码结构的映射。映射规则可以写成确定性的启发式：long scoreboard 占比高且 DRAM 吞吐未饱和，指向访存延迟未被足够多的 in-flight 请求掩盖，修复方向是提高 occupancy 或做软件预取；barrier 占比高，指向 shared memory 分块粒度过细或 block 内负载不均；MIO throttle 高，指向 shared memory bank conflict 或特殊函数吞吐瓶颈。

伪代码层面的采集与归因流程是：对候选 kernel 在固定 shape 下跑一次 NCU，取 smsp__average_warps_issue_stalled_* 系列计数器，归一化为百分比，与阈值表比对生成结构化诊断文本，再拼进下一轮的修复 prompt。这里有一个必须显式处理的代价：stall 分布对 shape 和 launch 配置高度敏感，同一 kernel 在 batch=1 与 batch=64 下 top stall 原因可能完全不同。若 profile 只在单一 shape 上采集，agent 会学到针对该 shape 的过拟合修复，换 shape 后加速比回退。工程判断是：profile 采集的 shape 集合必须与评测 shape 集合一致，且诊断文本要标注 shape，避免 agent 把 shape 特定结论当成普适规律。

另一个代价在 token 侧：把完整 stall 直方图塞进 prompt 会占用大量上下文，且低占比条目是噪声。有效做法是只保留占比超过阈值的条目并附一句源码定位（例如“barrier stall 占 34%，集中在第 2 次 __syncthreads 之后”），把诊断文本压到几百 token 量级。一个具体例子：一个 reduction kernel 在多轮修复中加速比停滞，stall 直方图显示 barrier 与 long scoreboard 各占约三成，agent 据此把两阶段 reduction 改为 warp shuffle 单阶段，消除了 block 内同步，加速比出现跃升——这类跃升正是多轮信用分配要归因的对象：增益来自哪一轮、由哪条 profile 证据触发。

三 · SASS 与二进制插桩：看见编译器做了什么

源码层面的推理经常与编译器实际生成的指令脱节。agent 写出看似合并访存的代码，编译器可能因指针对齐信息缺失而生成多条窄加载；写出看似无分支的内核，编译器可能因边界检查生成谓词化指令与额外寄存器。SASS 反汇编提供的是最终事实：每条 LDG/STG 的宽度（32/64/128 位）、寄存器数量与占用、指令总数、是否存在本地内存 spill。对 agent 而言，SASS 证据的价值在于把“源码意图”与“机器现实”的差距显式化，从而把修复从猜测变成定向改写。

二进制插桩是另一条路径：在编译产物中插入计时或计数器读取，获得每个 pipeline 阶段或每个 tile 迭代的周期数，而不依赖 NCU 的重放机制。插桩的代价直接体现在被测 kernel 的运行时：每次插桩读取时钟寄存器都会引入额外指令与同步，改变寄存器压力与指令调度，可能使被测 kernel 的性能特征偏离未插桩版本。因此插桩版本只能用于归因，不能用于最终加速比测量；评测口径必须锁定未插桩二进制。这个区分要在 agent 的工具描述里写死，否则 agent 会把插桩开销计入加速比，产生系统性偏低的奖励。

证据类型回答的问题采集代价失效模式
roofline 落点天花板在哪、是否已接近上界低（两个计数器）SOL 建模偏差导致奖励失真
warp stall 直方图卡在哪个流水级中（多次 replay）shape 过拟合、诊断文本噪声
SASS 指令统计编译器实际生成了什么低（离线反汇编）与源码语义映射需人工规则
二进制插桩阶段级周期归因高（改变运行时特征）插桩开销污染加速比

一个具体例子：agent 连续三轮尝试用向量化加载提升带宽利用率但加速比不动，SASS 显示加载指令已是 128 位宽、寄存器数接近上限、存在 spill。profile 证据链（roofline 显示带宽接近峰值 + SASS 显示 spill）共同指向“寄存器压力导致的 occupancy 下降”，正确修复是缩小 tile 或减少每线程累加器数量，而非继续加宽加载。没有 SASS 这一层，agent 会在错误的维度上反复试探，多轮预算被无效消耗。

四 · 反馈的保真度：profile 证据如何进入多轮信用分配

多轮 RL 的核心问题之一是信用分配：一次成功修复的增益该记在哪一轮、哪条证据上。profile 证据在这里扮演双重角色——既是修复的输入，也是归因的标签。工程上可行的做法是给每一轮修复打上“触发证据”标签（例如“本轮由 barrier stall 诊断触发”），在轨迹回放时统计不同触发证据对应的增益分布。若某类证据触发的修复长期零增益，说明该诊断规则对该算子族无效，应当从 prompt 模板中降权；若某类证据触发后增益显著，则在课程学习中提高该类证据的出现频率。这个统计不需要额外实验，直接复用第 5 卷交互轨迹即可。

保真度的另一个维度是 profile 与评测口径的一致性。评测在固定 shape、固定 warmup、固定测量次数下给出加速比，profile 采集若在不同条件下进行，诊断结论可能与评测表现矛盾。例如 profile 在冷缓存下采集，显示 DRAM 吞吐饱和，而评测在热缓存下实际是 L2 受限。这种矛盾会让 agent 收到互相冲突的信号，修复方向摇摆。工程判断是：profile 采集必须复用评测的输入生成与 warmup 流程，把 profile 当作评测流水线的一个旁路输出，而不是独立的一次运行。

$$\text{gain}_t=\frac{T_{t-1}-T_t}{T_{t-1}},\qquad \text{attr}(e)=\frac{\sum_{t:\,\text{trigger}_t=e}\text{gain}_t}{\big|\{t:\text{trigger}_t=e\}\big|}$$

上式给出按触发证据聚合的平均增益，用于诊断规则的在线调权。代价在于样本量：单个算子族内每类证据的触发次数有限，早期估计方差大，直接按估计值调权会造成模板震荡。稳妥做法是设置最小触发次数门槛，未达门槛的证据保持默认权重。一个具体例子：某算子族中“MIO throttle”触发的修复在多次轨迹里平均增益接近零，而“long scoreboard”触发的修复增益稳定为正，调权后 agent 在该族上的多轮成功率上升——这与卷首故事中“课程与信用分配调整后多轮修复成功率显著上升”的映射一致，但机制落点是证据级归因而非笼统的轮次折扣。

五 · 奖励 hacking 的 profile 侧监控

profile 证据本身可以成为被 hack 的对象。若 agent 发现“报告带宽受限”能让奖励归一化更宽松，它可能倾向于生成在 profile 采集条件下表现好、在评测条件下表现差的 kernel；若诊断文本直接暴露阈值，agent 可能针对阈值写特化代码而非真正优化。监控面板需要盯住几类信号：profile 判定与实测加速比的一致性（判定“接近上界”但实测远低于基线，说明判定失真）、诊断文本触发修复的增益分布是否随训练推进而塌缩（塌缩意味着 agent 学会了迎合诊断而非优化）、以及同一 kernel 在不同 shape 下 profile 结论的方差（方差过大说明证据不稳定）。

这些监控项的采集成本主要是存储与聚合，不增加被测 kernel 的运行开销，但要求轨迹记录里保留每轮的 profile 摘要与触发标签。工程上把摘要压成固定字段的结构化记录（受限类型、top stall 原因、SASS 关键计数、判定结论），既控制存储也便于面板聚合。一个具体例子：面板发现某算子族中“判定为计算受限”的候选比例在训练后期异常升高，而实测加速比分布未变，追查发现 agent 学会了写出让 SOL 建模低估访存量、从而把 kernel 判成计算受限的代码形态——这是典型的奖励 hacking，修复手段是让 SOL 建模的访存量从 SASS 指令统计反推而非从源码声明读取，堵住声明与实现不一致的缝隙。

最终落在工程判断上：硬件反馈层的设计目标不是给 agent 更多数字，而是给更少但更可信的归因。roofline 划定搜索边界，stall 直方图给出流水级方向，SASS 校正源码意图与机器现实的偏差，插桩只在归因时使用且绝不进入评测口径。这四层证据的采集代价与失效模式各不相同，必须分级触发、与评测口径对齐、并按触发证据聚合增益做在线调权；任何一层失真都会通过奖励塑形放大成策略层面的错误搜索方向，而监控面板的作用就是在失真变成系统性偏差之前把它识别出来。

当硬件反馈成为奖励信号：profile 证据链的失效边界

把 NCU 指标直接喂进奖励函数，最先撞上的不是精度问题，而是可观测性失真。roofline 的横轴要求实际达成 FLOPS 与字节吞吐，这两个量在 kernel 内部只能靠计数器近似：SM 级 inst_executed 与 dram__bytes 的采样窗口一旦跨越多个并发 block，roofline 点就会落在“算术强度虚高”的区域，agent 据此判定“已接近 SOL”而停止优化，实际是采样把访存延迟摊薄了。更隐蔽的是 warp stall 归因：stall_long_scoreboard 高并不等于访存受限，也可能是寄存器压力导致的调度饥饿，agent 若按 stall 类别直接映射到优化动作（见 stall 就加 prefetch），会把寄存器溢出误诊为带宽瓶颈。这类误诊在 RL 里的代价是奖励噪声：同一份代码两次 profile 得到不同的 stall 分布，优势估计方差被放大，多轮信用分配无法区分“这一轮修复真的有效”与“采样抖动”。

SASS 与二进制插桩提供的是另一条证据链，但它的系统代价必须计入奖励预算。反汇编级指令计数（如每 warp 的 LDG 与 FFMA 比例）比 NCU 采样更确定，代价是编译期插入 -lineinfo 与关闭部分优化后，被测 kernel 的绝对时延偏离生产二进制，加速比奖励因此系统性偏低；若用 nvdisasm 做静态指令统计而不插桩，则拿不到动态执行频次，分支与循环体内的指令权重只能靠静态启发式估计。一个可操作的折中是分层证据：正确性门控与加速比用生产二进制测，profile 只在“疑似瓶颈”样本上触发，且触发条件写成可判定的谓词，例如

$$\text{trigger} = \big[\text{speedup} < \tau_s\big] \land \big[\text{occupancy} < \tau_o\big] \land \big[\text{stall}_{mem} > \tau_m\big]$$

只有三项同时成立才付一次 NCU 采集的时延与显存开销（NCU 回放会串行化 kernel，单次采集可把端到端评测拉长数倍），把 profile 从“每轮必做”降为“按需取证”。

边界还在于反馈与奖励的语义错位。profile 回答“时间去哪了”，奖励回答“这一轮是否值得记功”，二者之间缺一个归因层。若把 stall 比例的下降直接当作正奖励，agent 会学会把 kernel 拆成更多小 launch 以稀释单 kernel 的 stall 计数，而总时延因 launch 开销上升——这是典型的奖励 hacking，监控面板上表现为“stall 指标改善但加速比不动”。可行的做法是把 profile 证据作为信用分配的辅助变量而非奖励本体：多轮轨迹中，只有当某轮修复同时改变 SASS 指令构成（如消除冗余 LDS）且加速比提升超过噪声带，才把该轮标记为有效修复；否则该轮的 profile 差异视为采样噪声，折扣因子照常衰减。这样 profile 的角色从“打分器”退回“诊断器”，其失效条件（采样失真、插桩扰动、归因错位）不再污染奖励，而 agent 仍能看见时间去哪了。

证据源确定性主要代价失效条件
NCU 采样低（窗口抖动）回放串行化，评测时延上升并发 block 跨窗口、stall 归因混淆
SASS 静态统计中（无动态频次）反汇编时间，无运行时扰动循环体权重靠启发式
二进制插桩高（指令级）编译期与运行时扰动，绝对时延偏移优化关闭后加速比不可比
