一 · 四个角色的边界：谁看数、谁下判断、谁动手

把“硬件反馈”塞进 agent 回路，第一件事不是接 NCU，而是把职责切开。一个能跑通的脚手架至少需要四个角色：coder 负责把优化意图落成可编译的 kernel 变体；judge 负责正确性与口径裁决，决定这个变体是否“算通过”；profiler 负责采集与提炼硬件证据，把原始 NCU 输出压成可消费的信号；search 负责在变体空间里决定下一步试什么、什么时候回退。四者混在一起最典型的失败是：coder 自己读 NCU 又自己改代码，于是它会把“occupancy 低”直接翻译成“加大 block”，而不知道这条改动可能同时破坏合并访存，最后 judge 只能看到一个变慢且仍然正确的 kernel，search 无法判断这是探索还是退化。

切分的判据是信息不对称的方向。profiler 掌握的是“机器说了什么”，judge 掌握的是“我们允许什么算对”，coder 掌握的是“源码怎么变”，search 掌握的是“预算怎么花”。任何跨界的判断都必须以结构化消息传递，而不是让一个模型在长上下文里同时扮演四个角色。工程上这体现为一条消息契约：profiler 输出的是带单位的指标向量与定位结论，judge 输出的是布尔裁决加失败归因标签，coder 输出的是 diff 加自述的优化假设，search 输出的是下一个动作与预算扣减。消息契约一旦固定，多轮修正才有可能被审计——你可以回放任意一轮，看清是证据错了、裁决错了还是改动错了。

代价在这里是轮次时延。四角色串行一轮意味着至少一次编译、一次正确性跑、一次 profile 采集、一次模型推理，端到端时延被拉长到分钟级；如果 search 每轮只允许一个变体，探索效率会被这个串行结构锁死。因此实践中的折中是让 profiler 与 judge 并行（正确性跑与 profile 跑可以是同一次执行的不同采集面），而 coder 与 search 保持串行。这个并行化不改变语义，只压缩墙钟时间，是脚手架层面最划算的一刀。

一个具体例子：coder 提交了把 shared memory 分块从 32×32 改成 64×64 的变体，judge 判定数值通过，profiler 报告 shared memory 用量翻倍导致 occupancy 从若干档位掉到更低档位、同时 bank conflict 计数下降。这条消息如果直接喂给 coder，它很可能只看到“conflict 下降”就继续加大分块；正确做法是 search 拿到这对矛盾指标后，把“分块尺寸”与“occupancy 下限”作为联合约束下发，让 coder 在保持 occupancy 不低于阈值的条件下继续调分块。角色的价值就在于把互相冲突的证据保留到决策层，而不是在单点被压平。

二 · 执行反馈的三层：能不能跑、跑得对不对、跑得多快

执行反馈不是一条信号，而是三层，且三层的失败模式完全不同。第一层是可执行性：编译是否通过、launch 是否成功、是否触发非法访存或超时。第二层是正确性：与 oracle 比对是否在容差内一致。第三层是性能：计时与硬件指标是否达到目标。三层必须按序短路——性能层永远不该在正确性未定的 kernel 上被讨论，否则 agent 会学会用“更快但算错”的变体骗过奖励。

短路顺序带来一个具体的工程机制：judge 在正确性层返回的不只是布尔值，而是失败归因标签，例如“边界越界”“归约顺序导致的浮点漂移”“同步缺失导致的竞态”。这些标签决定 coder 的修正方向：浮点漂移应当放宽比对口径或改归约树，而不是去调 tile 尺寸。若 judge 只回一个 false，coder 会在错误的维度上反复试探，把预算烧在不可能收敛的方向上。

代价体现在正确性判定的成本。逐元素比对需要把输出搬回主机，这是一次额外的设备到主机传输；对大规模输出，这次传输的字节数可能超过 kernel 本身的访存规模，使“验证”成为流水线里最贵的一环。工程折中是分层抽样加统计判据：先做小规模全量比对筛掉明显错误，再对大形状做抽样与范数比对。抽样会带来漏检概率，这个概率必须写进 judge 的口径里，而不是隐式假设为零。

$$\text{accept} = \big[\lVert y_{\text{ker}} - y_{\text{ref}} \rVert_\infty \le \tau \big] \wedge \big[\text{shape}, \text{dtype}, \text{stride} \text{ 一致}\big]$$

其中容差 τ 必须与 dtype 和归约长度挂钩，而不是一个全局常数；对 fp32 长归约，τ 随累加长度增长，固定 τ 会把正确实现判成错误。一个具体例子：coder 把串行归约改成树形归约以提升指令级并行，数值结果与参考实现出现末位差异，judge 若用固定 τ 会拒绝这个变体，从而把一条真实的性能优化路径堵死。这正是“口径即能力”的体现——judge 的容差策略直接决定 search 能看见多大的优化空间。

三 · NCU 指标到 prompt：哪些进、怎么压、压掉什么

NCU 的输出是几十到上百个计数器，全量塞进 prompt 既超预算又稀释注意力。profiler 的核心工作不是采集，而是选择与压缩。选择的原则是：只保留能直接映射到优化动作的指标族。给定事实里明确了四类——occupancy、memory throughput、stall reason、bank conflict——它们恰好覆盖了“并行度不足”“带宽未饱和”“等待而非计算”“访存模式低效”四种诊断，且每一类都能对应到具体动作（调 block 尺寸、改向量化宽度、减少同步、重排 shared memory 布局）。

压缩的机制是派生比值优先于原始计数。原始计数器（如某类 stall 的周期数）绝对值不可比，跨 kernel、跨形状都不可比；而派生量如“stall 周期占总周期比例”“实际带宽占峰值带宽比例”是可比的，也是 roofline/SOL 定位的输入。profiler 应当输出派生量加少量原始量作为佐证，而不是反过来。这样 prompt 的长度由指标族的数量决定，而不是由硬件计数器数量决定。

$$\text{SOL}_{\text{mem}} = \frac{B_{\text{achieved}}}{B_{\text{peak}}}, \qquad \text{SOL}_{\text{comp}} = \frac{F_{\text{achieved}}}{F_{\text{peak}}}$$

把这两个比值与 stall reason 的分布并列，就能做 roofline 定位：若内存 SOL 高而计算 SOL 低且 stall 集中在访存等待，说明已接近带宽上限，继续调计算无益；若两者都低且 stall 集中在同步或屏障，说明问题在并行结构而非算术强度。这个判断必须由 profiler 给出结论标签，而不是把原始表格丢给 coder 让它自己推——后者在长上下文里极易把相关性读成因果性。

代价是采样开销与 token 成本的双重预算。NCU 的精细采集会引入重放与串行化，使被测 kernel 的墙钟时间显著偏离真实执行时间，因此 profile 采集必须与计时采集分离：计时用干净执行，profile 用带采集执行，两者不可混用同一组数字。token 侧，指标族加结论标签加关键 SASS 片段，单轮反馈的 token 量级需要被显式设上限，超出时按“结论标签优先、原始指标次之、SASS 最后”的顺序截断。一个具体例子：某轮 profiler 发现 memory throughput 已接近峰值而 occupancy 处于中档，结论标签是“带宽受限，勿增并行度”，这条十几个 token 的结论比一整页计数器更能约束 coder 的动作空间。

四 · SASS 级反馈：什么时候值得付这个 token

SASS 反汇编提供的是源码层看不到的信息：编译器是否把循环展开、是否生成了向量化访存、shared memory 访问是否被拆成多次、是否有意外的本地内存溢出。这些信息对“源码意图与机器实际行为不一致”的诊断不可替代。但 SASS 的 token 成本极高——一段关键循环反汇编动辄数百行，全量塞入会挤占指标与结论的空间。

控制成本的机制是关键片段提取，而不是全量反汇编。提取规则可以按三类锚点定位：kernel 主循环体、shared memory 读写指令簇、以及出现本地内存（local）访存的指令。profiler 只截取这些锚点前后有限条指令，并附带指令计数摘要（如向量化访存指令数、屏障指令数）。这样 SASS 反馈的 token 量由锚点数量决定，而非 kernel 规模决定。

触发条件必须显式：只有当指标层给出“源码意图与硬件行为矛盾”的结论时才拉 SASS。典型触发是 occupancy 正常、stall 不在访存等待、但实际带宽远低于按访存指令数估算的期望值——这暗示访存被拆散或未向量化，此时 SASS 能直接确认。反之，若指标已明确指向带宽饱和，拉 SASS 只是浪费预算。

代价是编译时间与反馈时延。生成可读的 SASS 需要一次额外的编译与反汇编步骤，在迭代循环里这是一次固定开销；若每轮都做，轮次时延被进一步拉长。因此 SASS 应当是“按需触发”的低频通道，而不是每轮的标配。一个具体例子：coder 写了 `#pragma unroll` 期望展开，但 SASS 显示循环仍带分支且访存是标量而非向量，profiler 据此给出“展开未生效、访存未向量化”的结论，coder 改为显式向量化加载后带宽指标改善——这条路径若只靠源码审查无法发现，因为源码看起来完全合理。

五 · 多轮修正：规则引擎给建议，还是 agent 自主读 profile

这是本卷列出的关键决策之一：由 agent 自主读 profile，还是由规则引擎给建议。两者不是互斥，而是分层。规则引擎负责把指标模式映射到动作候选：occupancy 偏低且寄存器压力高 → 降寄存器或调 block；bank conflict 计数高 → 改 shared memory 填充或重排；stall 集中在屏障 → 减少同步点或改分块粒度。规则引擎的优点是稳定、可审计、token 便宜，缺点是覆盖不到规则库之外的新模式。

agent 自主读 profile 的价值在于处理规则未覆盖的组合。给定事实里的故事映射正是这个拐点：agent 首次“看懂”NCU stall 报告并自主改 shared memory 分块，硬件反馈成为性能跃迁的关键。这里的“看懂”不是读表格，而是把 stall 分布与访存模式联系起来，推断出分块尺寸与 bank 布局的联合调整——这类推断难以写成有限条规则。

工程上的折中是规则引擎兜底、agent 在规则失效时接管。search 每轮先跑规则匹配：命中则直接下发动作候选，省掉一次大模型推理；未命中或规则给出的动作连续若干轮无改善，则升级为 agent 自主读压缩后的 profile。这个升级阈值本身就是预算控制：它把昂贵的自主推理留给真正需要探索的轮次。

代价是错误规则的放大效应。规则引擎一旦把“occupancy 低”无条件映射为“加大 block”，在寄存器受限的 kernel 上会反复触发同一错误动作，且因为规则稳定，search 会误以为这是收敛方向。因此规则库必须带前置条件（如寄存器用量上限、shared memory 余量），并且每条规则要有“失效计数”，连续失效即降权。一个具体例子：某 kernel 的 stall 集中在 shared memory 访问，规则库给出“重排填充以消除 bank conflict”，coder 执行后 conflict 下降但总时延未改善，因为瓶颈已转移到同步；此时规则失效计数触发，agent 接管并读到屏障 stall 占比上升，转而减少同步点。这条链路说明规则与 agent 的分工不是能力高低，而是成本与覆盖面的权衡。

六 · 反馈通道的可信性：采样频率、开销预算与回放

硬件反馈通道本身必须被审计，否则 agent 会在噪声上做决策。第一个机制是采样频率与开销预算的显式化：profile 采集的粒度（是否逐 kernel 重放、是否采集 source-level 计数器）直接决定开销倍数，这个倍数必须记录在每轮反馈的元数据里，供 search 判断“这次观测是否可信”。若某轮采集开销过高导致被测执行被严重拖慢，该轮的计时数据必须作废，只保留指标结论。

第二个机制是回放。每一轮的输入（压缩后的指标、结论标签、SASS 片段）、judge 裁决、coder 改动、search 动作都应可回放。回放的价值不在于复现性能数字（硬件状态不可完全复现），而在于复现决策链：当最终 kernel 表现不佳时，能定位是哪一轮的证据被误读、哪条规则被错误触发。没有回放，多轮修正就是一个不可调试的黑箱。

第三个机制是指标与动作的因果留痕。coder 每次改动都应附带它声称要影响的指标，profiler 下一轮只需回报该指标是否按预期变化。这个“假设—验证”对是反馈通道的最小可信单元：若假设与观测长期不符，说明 coder 对硬件的理解模型有偏差，search 应当降低对该类改动的信任权重。代价是每轮多一次结构化记录，但它把“性能提升”从偶然变成可归因。

一个具体例子：coder 声称“减少同步点会降低屏障 stall 并提升吞吐”，profiler 回报屏障 stall 占比下降但总时延持平，因为瓶颈转移到访存。这条留痕让 search 知道该假设部分成立、部分失效，下一轮应把访存作为主攻方向，而不是继续削减同步。若没有这条留痕，search 只能看到“时延没变”，从而错误地把整条优化方向判死。反馈通道的可信性最终落在这种细粒度的因果对上，而不是落在任何单次测量的精度上。
