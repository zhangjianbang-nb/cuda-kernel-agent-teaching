一 · 题干的四段式结构：从自然语言到可评测产物

KernelBench 的题干不是一段散文，而是一条被固定下来的流水线契约。拆题的第一步是把这条契约还原成四个可检查的交接面：生成（自然语言规格 → 源码文本）、编译（源码文本 → 可加载的二进制/模块）、运行（模块 + 输入张量 → 输出张量与计时）、评测（输出与参考实现比对 + 性能与基线比对）。每一段都有明确的输入类型、输出类型和独立的失败模式，任何一段失败都会让后面的段失去意义。读题时若把四段混成一团，就会写出“看起来对但不可评测”的答案。

这条流水线的关键工程性质是失败可归因：编译失败与运行失败必须被区分开，因为前者是语法/类型/架构匹配问题，后者是越界、非法访存、同步错误、资源超限等问题。把两者混为一谈的评测器会把“模型写出了不合法的 CUDA”误判为“模型写错了算法”，从而污染后续的优化信号。题干要求按“生成—编译—运行—评测”的顺序回答，本质上是在考这条归因链是否完整。

一个具体例子：题目给出“对形状为 (B, N) 的输入做逐元素 ReLU 并写回”。生成段的输出是一段 CUDA C++ 源码文本；编译段要把它变成一个可调用的 kernel 符号；运行段要分配设备缓冲、拷贝输入、以给定 grid/block 启动、拷回输出；评测段要拿参考实现的输出做逐元素比对，同时把实测时延与一个基线（例如框架自带算子或一个朴素实现）比较。四段中任意一段的接口约定（例如张量布局、dtype、是否允许原地写）没对齐，后面全部作废。

这里已经能提炼出第一个公式化的判据：设生成段产出源码 S，编译算子 C 把 S 映射为模块 M 或错误 e_c，运行算子 R 把 (M, x) 映射为 (y, t) 或错误 e_r，评测算子 E 把 (y, y_ref, t, t_ref) 映射为通过/不通过。整条链的通过条件是 C、R、E 三级全部成功且 E 的判定为真。读题时要能一眼指出：题干给的规格里，哪些字段喂给 C（架构、编译选项），哪些喂给 R（形状、dtype、随机种子），哪些喂给 E（容差、基线、计时方法）。漏掉任何一个字段，就是漏掉一个考点。

二 · 生成段的考点：规格到源码的语义保真

生成段最容易被低估。它不只是“让模型写个 kernel”，而是要保证源码在语义上等价于规格、在接口上匹配评测器的调用约定。考点集中在三处：接口签名（参数顺序、指针 const 性、是否接受 stride）、边界语义（越界元素是否被 mask、尾块如何处理）、数值语义（累加精度、是否允许融合、是否允许改变结合律）。这三处任何一处偏差，都会在评测段表现为“数值不对”或“形状不对”，但根因在生成段。

以带 stride 的二维输入为例，规格可能只写了“对最后一维做归约”，但评测器传入的张量可能是非连续的。生成段若默认连续布局并直接用线性索引，就会在运行段读到错误位置——这类错误不会触发非法访存，只会静默产生错误结果，属于最危险的失败模式。因此生成段的一个硬性考点是：源码是否显式处理了 stride，或是否在入口处做了连续性断言。

生成段的代价主要是 token 与时延：源码越长、注释与模板越多，解码开销越大；而一次生成失败就要重试，重试次数直接乘在端到端时延上。设单次生成的平均 token 数为 L，解码吞吐为 v token/s，重试概率为 p，则生成段期望时延约为 L/v · 1/(1-p)。这个式子说明：降低 p（例如在提示里固定接口模板）比压缩 L 更能省时间，因为 1/(1-p) 在 p 接近 1 时发散。这是读题时应识别出的第一个工程判断：接口约束写进提示，比让模型自由发挥更划算。

具体例子：规格要求“输入 (B, N)，输出 (B,)，沿 N 归约求和”。若生成段写出 __global__ void reduce(const float* x, float* y, int B, int N) 并假设 x 连续，则在 x 为转置视图时结果错误；正确做法是传入 stride 或在 host 侧做 contiguous()。这个差异在编译段完全看不出来，只在评测段暴露，因此题干要求按顺序回答，正是在逼读者把“生成段的接口约定”当成独立考点。

三 · 编译段与运行段：两类失败的分界

编译段的输入是源码文本加编译配置（架构代号、优化级别、是否开启快速数学），输出是一个可被 host 侧加载的模块，或一条编译错误。考点是配置与源码的匹配：源码里用了某个架构才有的指令（例如特定宽度的张量核心指令或共享内存特性），而编译配置指向更低架构，就会在编译期报错；反之，源码用了过时的写法而配置指向新架构，可能编译通过但运行期行为改变。编译段的代价是编译时间，模板实例化越多、头文件越重，编译越慢；在批量评测里，编译时间会与生成重试次数相乘，成为吞吐瓶颈。

运行段的输入是模块、设备缓冲、形状与 dtype、启动配置（grid/block/共享内存大小），输出是结果张量与实测时延，或一条运行错误。考点是资源与合法性：共享内存超出上限、寄存器压力导致占用率过低、grid 维度超过设备限制、越界访存、缺少同步导致的竞态。运行段的代价是显存与时延：中间缓冲的分配、host-device 拷贝、多次重复计时带来的额外开销，都会计入端到端成本。一个常见陷阱是把首次调用的初始化开销（上下文建立、模块加载）算进计时，导致时延被高估；正确做法是预热若干次再取统计量。

两类失败的分界必须用可判定的信号区分。设编译算子返回 e_c 当且仅当编译器退出码非零或产物无法加载；运行算子返回 e_r 当且仅当启动返回错误码或结果缓冲区出现非法值（NaN/Inf 在规格未允许时）。判据可以写成：若 e_c 存在，则跳过运行与评测，记为编译失败；若 e_c 不存在而 e_r 存在，记为运行失败；两者都不存在才进入评测。这个三分法是评测器可信度的基础，也是读题时必须点明的结构。

具体例子：一个使用动态共享内存的归约 kernel，在 block 大小设为超过设备上限时，编译可以通过（共享内存大小是运行期参数），但启动返回错误——这是典型的运行段失败而非编译段失败。若评测器把这类情况记成“编译失败”，就会误导后续优化方向（模型会去改语法而不是改 block 大小）。

四 · 评测段：正确性 oracle 与性能基线的双重判定

评测段是整条流水线的收敛点，它同时做两件事：正确性比对与性能比对。正确性比对的输入是实测输出 y 与参考输出 y_ref，输出是布尔判定；考点是容差设计与比对范围。浮点归约的顺序不同会带来舍入差异，因此逐元素严格相等几乎必然失败，必须用相对/绝对容差。设容差为 ε，判据为 |y_i - y_ref,i| ≤ ε · max(1, |y_ref,i|) 对所有 i 成立；ε 太小会误杀正确实现，太大会放过错误实现。这个权衡是评测段的核心考点，题干要求回答“评测步的失败模式”，答案必须包含“容差不当导致的假阴性/假阳性”。

性能比对的输入是实测时延 t 与基线时延 t_ref，输出是加速比 t_ref / t 或是否超过阈值。考点是计时方法与基线选择：计时是否包含数据传输、是否使用设备端事件、重复次数是否足够以压过噪声；基线是框架算子还是朴素实现，直接决定“加速”的含义。若基线是高度优化的库算子，则加速比接近 1 已属不易；若基线是朴素实现，则加速比容易虚高。读题时要能指出：题干里的“efficient”必须被操作化为一个具体的比值与一个具体的基线，否则不可评测。

评测段的代价是显存与时间：参考实现本身要占显存，比对要遍历全部元素，重复计时要把运行段执行多次。设重复次数为 k，单次运行时间为 t，则评测段时间开销约为 k·t 加上比对遍历的带宽开销；在显存紧张时，参考输出与实测输出同时驻留会抬高峰值占用。一个具体例子：对 (4096, 4096) 的浮点矩阵做逐元素运算，输出缓冲各占数十 MB 量级，若评测器同时保留输入、参考输出、实测输出与中间缓冲，峰值显存会显著高于单次运行所需——这是评测段而非运行段的成本，容易被漏算。

把两重判定合成一个通过条件：设正确性判定为 A(y, y_ref, ε)，性能判定为 P(t, t_ref, θ)（θ 为加速比阈值），则总判定为 A ∧ P。读题时要能说出：A 为假时 P 无意义（快但错不算通过），P 为假时 A 为真只说明“正确但不够快”。这两个失败模式对应两种完全不同的优化路径，不能合并。

五 · 解题路径：把题干映射成可执行的检查清单

基于上述四段，解题路径可以写成一条自顶向下的检查链，而不是直接写 kernel。第一步，从规格中抽出接口契约：输入输出的形状、dtype、布局（连续/带 stride）、是否原地、是否允许融合。第二步，抽出数值契约：归约维度、累加精度、容差、是否允许重排。第三步，抽出资源契约：目标架构、可用共享内存与寄存器预算、启动配置约束。第四步，抽出评测契约：基线是谁、计时是否含拷贝、重复次数与预热策略。四份契约齐了，才进入源码设计。

这条路径的伪代码思路可以写成：

$$\text{spec} \rightarrow (\text{iface}, \text{num}, \text{res}, \text{eval}) \rightarrow S \xrightarrow{C} M \xrightarrow{R} (y,t) \xrightarrow{E} \{\text{pass}, \text{fail}_A, \text{fail}_P\}$$

其中 fail_A 与 fail_P 必须分开记录，因为前者指向语义或容差问题，后者指向性能或基线问题。路径的每一步都要问“这一步的失败模式是什么、由谁捕获”。生成段失败由编译段捕获（语法/类型），编译段失败由加载器捕获，运行段失败由启动返回码捕获，评测段失败由比对与比值捕获。任何一步没有捕获机制，就是题干里的隐藏考点。

代价维度也要在路径上标注：生成段的 token 与重试、编译段的编译时间、运行段的显存与启动开销、评测段的重复计时与比对带宽。一个具体例子：若规格要求“尽量快”，解题路径应先确认基线是库算子还是朴素实现；若是库算子，则优化空间主要在访存合并与占用率，而非算法复杂度；若是朴素实现，则先做分块与向量化即可获得明显加速。这个判断不需要写一行代码，却决定了后续所有工作的方向。

六 · 读题时最易漏掉的三处接口细节

第一处是布局与 stride。规格常只写逻辑形状，而评测器传入的张量可能非连续。生成段若不处理 stride，运行段不会报错，评测段会给出错误结果，归因却落在“数值不对”上。第二处是原地与别名。若规格允许原地写，而生成段假设输入输出不重叠，则在别名情况下产生竞态；这类错误在单次运行中可能偶然通过，在重复计时中暴露为不稳定结果。第三处是dtype 与累加宽度。半精度输入做归约时，累加若用半精度会损失精度，评测段的容差判定会失败；若用单精度累加，则要通过类型转换，增加指令数与寄存器压力。

这三处细节共同说明一个工程判断：题干的“正确性”不是抽象等价，而是在给定接口与给定容差下的等价。读题时应把这三处写成显式检查项，而不是留给生成段自由发挥。每漏一处，就多一类无法归因的失败；而归因能力正是这条流水线可信度的来源。最后落在具体机制上：评测器应为每次失败记录四段中哪一段返回了错误、错误码是什么、输入契约的哪个字段不匹配——没有这份记录，多轮优化就失去了可验证的奖励信号，RL 与执行反馈也就无从谈起。
