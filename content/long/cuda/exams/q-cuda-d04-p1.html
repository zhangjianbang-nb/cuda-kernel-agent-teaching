一 · 把题干拆成四个可判定的子问题

题干里真正有约束力的词只有三个：“一张 GPU”“两周”“正确性 oracle 与形式验证”。其余都是修饰。把这三个词展开，题目实际在问四件事，且每一件都必须给出可判定的答案，否则两周结束时无法验收。

第一，资源约束下的方向裁剪：一张 GPU 意味着不能靠“多卡并行跑大规模随机测试”来换取置信度，采样预算被硬性限制在单卡吞吐内；两周意味着不能先搭一套通用验证框架再往里填算子，必须从已有算子反推最小验证闭环。第二，oracle 的构造方式：正确性 oracle 不是“跑一遍看对不对”，而是要回答“参照物从哪来、误差容限怎么定、哪些输入空间必须覆盖”。第三，形式验证的适用边界：形式方法在 GPU kernel 上能证明什么、不能证明什么，哪些性质值得形式化，哪些只能靠差分测试兜底。第四，验收口径：两周后拿什么证明这套 oracle 可信——是覆盖率、是发现的真实缺陷数、还是对已知错误注入的检出率。

拆题的关键在于识别出这四问之间存在依赖顺序：oracle 的构造方式决定了形式验证能形式化什么，而验收口径又反过来约束前两者不能做得太泛。若把顺序倒过来——先选形式化工具再找性质——两周内必然卡在工具适配上。因此解题路径应当是“先定验收口径，再定 oracle 形态，最后定形式化的切入点”，而不是按题面词序推进。

一个具体的拆法：把“正确性 oracle 与形式验证”看成一个缺陷检出系统，其输入是待测 kernel 与输入分布，输出是“通过/拒绝 + 反例”。于是题干变成：在单卡、两周内，如何让这个系统的检出率与误报率同时达到可交付水平。这个视角把“形式验证”降格为系统中的一个检出器，而非独立目标，避免了把两周耗在证明器的完备性上。

二 · 考点：三个必须显式回答的技术判断

考点不在“会不会用某个验证工具”，而在三个判断上，每个判断都有明确的代价面。

判断一：oracle 的参照物是解析解、高精度实现，还是另一个 kernel。三者代价不同。解析解（如用 CPU 双精度逐元素算参考值）精度最高但吞吐极低，单卡上对大规模输入不可行，只能用于小规模边界样本；高精度 GPU 实现（如用 float64 或 Kahan 求和重写一遍）能覆盖较大输入但开发时间翻倍；拿另一个已有 kernel 做差分则开发最快，却把“参照物本身是否正确”变成新的未验证假设。考点是能否说清：参照物的可信度必须高于被测物，否则差分测试只是把错误搬了个家。代价面是采样预算——解析解 oracle 每验证一个样本的时延可能是 kernel 本身的数十倍，直接压缩了可覆盖的输入数量。

判断二：误差容限按什么范数、什么尺度定。这不是拍一个 1e-5 就完事。对归约类算子，误差随累加长度增长，容限必须与问题规模挂钩；对逐元素算子，容限可以固定。考点是能否给出一个与规模相关的容限模型，例如相对误差上界写成

$$\varepsilon_{\text{rel}} \le \kappa \cdot \sqrt{n} \cdot u,\qquad u = 2^{-24}\ (\text{fp32 单位舍入})$$

其中 $n$ 是累加长度、$\kappa$ 是与求和树形状有关的常数。这个式子本身不重要，重要的是它把“容限”从魔法数字变成了可推导量，从而使误报（把正确实现判为错）可解释。代价面是：容限放宽会降低检出率，收紧会引入误报，二者在单卡采样预算下不可兼得，必须显式取舍。

判断三：形式验证证明的是哪一类性质。GPU kernel 的性质大致分三层：内存安全（越界、竞态、未初始化读）、数值语义（与规格的数学等价）、性能上界（访存模式、占用率）。形式方法在内存安全层最成熟，因为可以编码为有界模型检查或符号执行下的断言；数值语义层极难，浮点舍入与并行归约顺序使“等价”本身需要重新定义；性能层基本不属于形式验证范畴。考点是能否明确：两周内形式验证只应攻内存安全与索引正确性，数值正确性交给差分 oracle。代价面是编译/求解时间——符号执行对有界循环展开的规模敏感，展开深度每加一层，求解时间非线性上升，单卡机器上跑求解器还会与 kernel 测试争抢资源。

一个具体例子：转置或 stride 类 kernel 的索引错误（把 blockIdx.x 与 threadIdx.y 写反）在随机输入下常常“碰巧”通过，因为对称矩阵或方阵使错误索引仍落在合法范围。这类缺陷正是形式化索引断言的靶子，而差分测试对它几乎无检出率。反过来，归约求和的浮点偏差用形式方法几乎无法证明，只能靠容限模型加差分。两个考点在此交汇：缺陷类型决定验证手段，而不是工具决定缺陷类型。

三 · 解题路径：从验收口径倒推的两周排布

路径设计的第一原则是先写验收脚本，再写验证器。验收口径若不先定，两周内会不断扩张范围。可交付的验收口径应包含三项可测指标：对一组已知错误注入的检出率、对一组正确实现的误报率、以及单位时间内的样本吞吐。这三项都不需要编造数字，只需在团队自己的算子集上测出基线。

据此倒推排布，可分成四个阶段，每阶段有明确的退出条件而非时间点。

  • 阶段 A：算子与缺陷清单。从团队实际在写的 kernel 中挑出三到五个，按缺陷类型分类（索引类、同步类、数值类、边界类）。退出条件：每个算子有一份“最可能错在哪”的假设列表。代价：这一步不消耗 GPU，消耗的是人对代码的阅读时间。
  • 阶段 B：差分 oracle 骨架。为每个算子配一个可信度更高的参照实现，并接入容限模型。退出条件：正确实现全部通过、注入的索引类错误全部被拒。代价：参照实现的开发时间往往超过被测 kernel 本身，这是单卡团队最容易低估的一项。
  • 阶段 C：形式化切入点。只对索引与内存安全性质写断言，用有界展开覆盖典型 tile 形状。退出条件：至少一个注入的越界或竞态缺陷被形式工具在求解时间内报出。代价：求解时间与展开深度挂钩，必须限制在单卡可承受的范围内，否则会挤占差分测试的 GPU 时间。
  • 阶段 D：验收跑通。把 A/B/C 串成一条命令，输出检出率、误报率、吞吐三项。退出条件：三项指标可复现。

路径中的关键取舍是明确不做什么：不做全算子覆盖、不做浮点语义的形式化证明、不做跨架构（多 GPU 型号）验证、不做自动化缺陷定位。这四项每一项都能吃掉两周。判断依据是边际检出率——在单卡采样预算下，扩大算子覆盖带来的新增检出远低于把已有算子的缺陷类型挖深。

需要调用的公式除容限模型外，还有一个覆盖率与采样预算的关系式，用于说明“为什么不能靠多跑随机样本提置信度”：

$$P(\text{漏检}) \approx (1-p)^{N},\qquad N \le \frac{T_{\text{wall}} \cdot \text{throughput}}{1 + c_{\text{oracle}}}$$

其中 $p$ 是单样本触发缺陷的概率，$N$ 是可跑样本数，$c_{\text{oracle}}$ 是 oracle 相对 kernel 的时延倍率。这个式子说明：当 $p$ 很小（如仅在特定 tile 边界触发），随机采样需要天文数字的 $N$ 才能压低漏检率，而单卡吞吐与 oracle 开销把 $N$ 锁死。结论直接指向形式化——对低 $p$ 的索引类缺陷，定向断言比增加采样有效得多。这是路径设计的数学依据，也是“先做什么”的答案来源。

四 · 单卡约束如何改变验证策略的形状

一张 GPU 不只是“算得慢一点”，它改变了验证策略的形状。多卡团队可以让验证与开发并行、可以让大规模随机测试与形式求解分摊到不同设备；单卡团队则必须让所有验证活动串行共享同一块设备时间，于是GPU 时间成为与人力并列的稀缺资源。

具体机制上，这意味着三件事。其一，oracle 若用 GPU 高精度实现，会与 kernel 测试争抢设备，必须把 oracle 计算与 kernel 执行错峰或合并到同一进程内以减少启动开销。其二，形式工具的求解器若跑在 CPU 上，看似不占 GPU，但其反例回放需要在 GPU 上执行以确认缺陷真实，这条回放路径必须提前打通，否则形式工具报出的反例无法闭环。其三，随机测试的批量大小受显存限制，而显存同时被参照实现占用，批量被迫缩小，进一步压低 $N$。

代价面很直接：显存。差分测试需要同时驻留被测输出与参照输出，若参照用 float64，显存占用翻倍，直接限制了可测的最大问题规模。工程判断是：对大规模输入只做抽样比对（如按 tile 抽样），对小规模输入做全量比对，用规模换精度。这一取舍必须写进验收口径，否则“通过”二字没有意义。

另一个被单卡放大的代价是编译时间。形式化验证常需要对 kernel 做插桩（加断言、加边界检查），插桩版本与被测版本是两个不同的编译产物，每次修改断言都要重编译。单卡机器上编译与测试串行，编译时间直接吃掉 wall clock。缓解机制是把断言集中到一份可配置的头文件，用模板参数开关，避免为每种断言组合单独编译。这个机制不新鲜，但在两周约束下它是能否跑完阶段 C 的前提。

具体例子：一个团队若把形式化目标定为“证明整个 kernel 的数值等价”，会在第一周就卡在浮点模型的形式化上，因为需要把 GPU 的 FMA 收缩、并行归约顺序都编码进语义，工作量远超两周。而若把目标收窄为“证明所有全局内存访问的索引落在分配范围内”，则可以用有界展开在数小时内得到结论，且反例可直接回放。同一个团队、同一张卡，目标选择决定了可行性。单卡约束的真正含义是：它惩罚宽而浅的目标，奖励窄而深的目标。

五 · 验收口径的构造：把“可信”变成可测的量

“可信的 oracle”若不能量化，就无法在两周后交付。构造验收口径的核心是引入错误注入作为标尺：人为在 kernel 中植入已知缺陷，看验证系统能否检出。这把“可信度”从主观判断转成检出率。

注入的缺陷应按考点分类设计，每类至少两个样本：索引置换（写反 block/thread 维度）、边界偏移（off-by-one 的 tile 边界）、同步缺失（去掉 __syncthreads()）、精度降级（把 float64 累加改成 float32）。对每类缺陷记录：差分 oracle 是否检出、形式断言是否检出、检出所需时间。这张表就是验收报告的主体。

缺陷类型差分 oracle 期望形式断言期望主要代价
索引置换低检出（对称输入下常漏）高检出求解展开深度
边界偏移中检出（依赖输入规模）高检出断言编写时间
同步缺失不稳定（依赖调度）中检出（需编码竞态）反例回放
精度降级高检出（容限模型敏感）几乎不可检容限标定

表格的读法是：没有单一手段能覆盖全部缺陷类型，验收口径必须按类型分别报告。把四类混成一个“总检出率”会掩盖结构性盲区。工程判断是：验收报告应明确写出“本系统对精度类缺陷的检出依赖容限模型，对索引类缺陷的检出依赖形式断言”，并给出每类的样本数与检出数。

误报率的构造对称：用一组已知正确的实现（包括官方库实现与团队已上线的 kernel）跑同一套验证，统计被误判为错的次数。误报主要来自容限过紧与形式断言的过度约束（如断言了实际不成立的 tile 形状假设）。代价面是：压低误报会迫使放宽容限或收窄断言，两者都降低检出率，这个张力必须在验收口径里显式记录，而不是事后解释。

吞吐指标用于约束前两项不能被无限精化：单位 GPU 时间内完成的“算子×缺陷类型”组合数。它把“可信”锚定在资源现实上——一个检出率极高但两周只能跑两个组合的系统，交付价值有限。三项指标合起来，才构成题干所要求的“取舍依据与验收口径”。

六 · 从题干到可执行判断的最后一步

把上述拆解收敛成一个可执行判断：先做什么是差分 oracle 骨架加容限模型，因为它对精度类与边界类缺陷有直接检出率，且不依赖求解器；明确不做什么是全算子覆盖、浮点语义形式化、多架构验证、自动缺陷定位，因为它们要么超出两周，要么在单卡采样预算下边际检出率过低。

形式验证的切入点应精确落在索引与内存安全上，用有界展开覆盖团队实际使用的 tile 形状集合，而不是追求任意形状的普适证明。这个选择的依据是第三节的漏检概率式：低 $p$ 缺陷靠采样无法压低漏检，而索引类缺陷恰恰是低 $p$ 且可被定向断言捕获的。于是形式化不是“更高级的验证”，而是“针对特定缺陷类型的采样替代品”。

最后一个机制性判断关于顺序：验收脚本必须先于验证器存在。具体做法是先写一个只输出“通过/拒绝”的桩，把错误注入表跑通，确认桩能把已知错误判错、把已知正确判对，再往里填真正的 oracle 与断言。这样做的代价是前期多花半天写桩，收益是后续每一次 oracle 修改都能立即被同一张表度量，避免两周结束时才发现验证器度量的是错误的东西。这个顺序本身就是题干“先做什么”的一部分答案——先做度量，再做验证。
