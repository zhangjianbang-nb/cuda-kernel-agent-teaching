一 · 把题干拆成四个可判定的子问题

「一张 GPU、两周、方向是 Agent 脚手架与执行反馈」这句话里藏着四个必须分开回答的子问题，混在一起谈就会得到“什么都做一点”的方案。第一，资源约束是什么形态：单卡意味着并发评测吞吐、profile 采集、编译缓存全部串行化，任何需要多卡比对的实验设计直接出局。第二，时间约束是两周，它约束的不是“能写多少代码”，而是“能跑多少轮假设—验证循环”，因为脚手架本身的调试周期会吃掉大半时间。第三，方向被限定在“脚手架与执行反馈”，意味着模型侧的训练、数据配比、reward 设计不属于本方向的可交付物，本方向交付的是“让 agent 拿到可信反馈”的那层基础设施。第四，题干问的是“先做什么、明确不做什么”，这是一个排序问题而非清单问题，答案必须给出取舍依据与验收口径。

把四个子问题写成可判定形式：资源上，单卡下单位时间能完成的 kernel 编译—运行—profile 次数是多少；时间上，两周内能闭合几轮“生成→执行→反馈→再生成”；范围上，哪些反馈信号在单卡上可得且与正确性/性能强相关；排序上，哪一个组件缺失会让其余组件全部失效。这四个问题的答案共同决定优先级，而不是靠“哪个听起来更酷”。

拆题的直接产物是一张依赖图：正确性 oracle 是根节点，执行反馈通道是它的第一层子节点，多轮循环是第二层，性能反馈（NCU/SASS）是第三层。根节点不稳，上面三层全是噪声。这个依赖关系本身就是取舍依据——两周内必须先把根节点做扎实，否则后面所有“agent 变强了”的观测都无法归因。

二 · 考点在哪：可验证奖励的噪声底

这个方向真正的考点不是“搭一个能跑的 agent loop”，而是“反馈信号的信噪比”。LLM 生成的 kernel 有大量“编译通过但结果错”“结果对但慢得离谱”“结果对且快但只在某个 shape 上对”的情形。如果 oracle 只做“跑通不报错”，agent 会把大量错误解当成成功解强化，多轮迭代后策略退化。因此考点的核心是：在单卡、两周的预算下，如何构造一个足够严、足够快、覆盖足够广的正确性判定，并让它成为奖励的可信来源。

形式化地，设一次 rollout 产生候选 kernel k，判定函数 O(k) 返回三元组（编译状态、数值误差、资源占用）。可验证奖励 r 应当是 O 的确定性函数，且满足：对任意错误解，r 低于正确解的下界；对任意正确解，r 不因 shape 抖动而剧烈波动。写成条件就是

$$r(k)=\mathbb{1}[\text{compile}]\cdot\mathbb{1}[\max_i \|y_i-\hat y_i\|_\infty \le \tau]\cdot f(\text{latency})$$

其中 τ 是数值容差，f 是性能项。考点在于 τ 的选取：太松则错误解通过，太紧则合法优化（如用 tf32、改变累加顺序）被误杀。单卡上无法用大规模统计确定 τ，只能用“参考实现 + 多组随机输入 + 逐元素相对误差”这种低成本手段逼近。

代价在这里非常具体：每增加一组随机输入，正确性验证的时延线性增长；每增加一个 dtype 或 shape，编译时间翻倍（模板实例化）。两周内如果 oracle 覆盖了 20 组输入、3 种 dtype，单次 rollout 的验证开销可能已经和 kernel 本身运行时间同量级，agent 的迭代轮数被直接压缩。这就是为什么考点不是“做得全”，而是“在轮数与覆盖率之间取一个可解释的平衡点”。

一个具体例子：矩阵乘 kernel 的候选解在 M=N=K=1024 上误差 1e-5 通过，但在 K=4097（非 2 的幂）上因边界处理缺失而越界。若 oracle 只测一个 shape，这个解会被判为正确并进入下一轮，agent 学到的是“不用管边界”。加入一组非对齐 shape 后，该解被拦下，但验证时延增加一次编译加一次运行。这个 trade-off 就是本方向最核心的工程判断。

三 · 解题路径：先立 oracle，再建通道，后接循环

路径的第一步是把正确性 oracle 做成独立、可单测的模块，而不是嵌在 agent loop 里的一个函数调用。独立模块的好处是可以用固定的一组“已知正确解/已知错误解”做回归测试，确认 oracle 本身不误判。这一步的验收口径是：给定若干人工构造的边界案例（越界、非对齐、混合精度、空 tensor），oracle 的判定与人工预期一致。代价是前期投入约一到两天，换来的是后续所有实验的可归因性。

第二步是执行反馈通道。单卡上通道的关键设计是“一次编译、多次运行”：把候选 kernel 编译成独立可执行体或动态库，缓存编译产物，按 shape 批量跑。伪代码思路是

$$\text{for } s \in \text{shapes}: \quad \text{out}[s]=\text{run}(\text{bin},\ s),\quad \text{err}[s]=\text{compare}(\text{out}[s],\ \text{ref}[s])$$

通道的代价是编译缓存的管理复杂度：缓存键必须包含源码哈希、编译选项、架构，否则会命中错误的二进制。单卡上缓存命中率直接决定迭代速度，一次未命中就是数十秒的编译等待。

第三步才是多轮循环。循环的骨架是“生成→编译→验证→打分→回填上下文”，但本方向要强调的是：循环里每一轮必须携带结构化的失败原因（编译错误行、误差最大的元素位置、超时的 shape），而不是一句“失败了”。结构化反馈让 agent 的下一轮修改有方向，这是脚手架与裸 prompt 的区别所在。代价是上下文 token 增长：每轮携带完整错误摘要会挤占生成长度预算，需要截断策略。

三步的顺序不可颠倒。若先搭循环再补 oracle，会得到“循环跑得很顺但奖励全是噪声”的假象，两周结束时无法回答“agent 是否真的变强”。若先做性能反馈（NCU/SASS）再补正确性，则大量错误解被性能数据掩盖。这个排序依据是依赖图，不是偏好。

四 · 需要调用的公式与判据

本方向要用的公式不多，但每一个都直接对应一个工程决策。第一个是数值误差判据：逐元素相对误差与无穷范数组合，

$$\text{err}=\max_i \frac{|y_i-\hat y_i|}{\max(|y_i|,\ \epsilon)}$$

它决定 τ 的取值。对 fp32 累加，τ 取 1e-5 量级；对 tf32 或 fp16 混合，τ 必须放宽到 1e-3 量级，否则合法优化被误杀。这个判据的代价是：放宽 τ 会放过“精度换速度”的偷懒解，收紧 τ 会拒绝真实的硬件加速路径。两周内必须明确写下 τ 的选择理由，作为验收口径的一部分。

第二个是单卡吞吐判据：单位时间有效 rollout 数

$$N_{\text{eff}}=\frac{T_{\text{budget}}}{t_{\text{gen}}+t_{\text{compile}}+t_{\text{run}}\cdot n_{\text{shape}}+t_{\text{profile}}}$$

它决定 shape 组数 n 的上限。t_compile 在模板重的 CUDA C++ 上往往是最大项，因此减少模板实例化、复用编译产物比增加 shape 更划算。这个公式的工程含义是：优化 t_compile 的收益是全局的，优化 t_run 的收益是局部的。

第三个是性能反馈的可用性判据：roofline 距离。对 memory-bound kernel，用实际带宽与峰值带宽之比；对 compute-bound，用实际 FLOPs 与峰值之比。单卡上 NCU 可采，但采集本身有开销（replay、序列化），因此只在“正确性已通过”的候选上采，且限制采样次数。代价是 profile 时延可能数倍于运行时延，必须纳入 N_eff 的分母。

具体例子：一个 reduction kernel 正确性通过，但 NCU 显示 achieved occupancy 低、访存不合并。若脚手架只回传“慢”，agent 无从下手；若回传“带宽利用率 30%、stride 访问”，下一轮修改就有明确目标。这要求反馈通道把 profile 的关键指标结构化，而不是丢一张原始报告。

五 · 明确不做什么，以及验收口径

两周单卡下，明确不做的事情需要写进方案首页，否则会被“顺手做一下”侵蚀。第一，不做多卡扩展与分布式评测：单卡上的正确性结论不依赖多卡，多卡只会引入不可复现的通信噪声。第二，不做端到端生产收益测量：那需要真实模型与真实负载，两周内无法闭合，且与本方向的反馈可信度问题是两件事。第三，不做 PTX 级手写优化与 SASS 级调优：这些属于 kernel 优化方向，本方向只需把 profile 指标作为反馈信号接入，不需要自己成为优化器。第四，不做大规模 RL 训练：本方向交付的是可验证奖励的接口与噪声评估，训练配方不在范围内。

验收口径要能被第三方复核。建议三条：其一，oracle 回归集全部通过，且对人工构造的错误解零漏判；其二，在固定预算内完成的可归因迭代轮数达到预设下限，且每轮失败原因结构化落盘；其三，正确性通过的解中，性能反馈与 NCU 实测方向一致（例如反馈说“访存瓶颈”，NCU 确实显示高访存压力）。三条都不依赖“agent 变强了”这种主观判断，而是可复现的工程事实。

取舍依据可以浓缩成一句工程判断：在单卡两周的约束下，反馈信号的正确性优先级高于反馈信号的丰富性，因为错误的正反馈会以指数方式污染多轮循环，而缺失的性能反馈只让优化变慢、不会让方向变错。这个判断决定了先做 oracle、后做 profile，先做结构化失败原因、后做性能打分。

最后落到具体机制上：把 oracle 做成带版本号的独立服务，每次 agent 生成都记录（源码哈希、编译选项、shape 组、判定结果、时延）五元组，两周结束时这份日志就是唯一的可信证据链。没有这份日志，任何“脚手架有效”的结论都无法在单卡预算内被复核。

单卡两周窗口下，读题拆解要先划出“不做什么”的边界

在只有一张 GPU、两周时间的约束下，读题与考点拆解的第一产出不是解题路径，而是一张“考点—证据—代价”的三列表。题干里的每个名词都要被翻译成可观测的执行反馈信号：算子语义对应正确性 oracle，形状与 dtype 对应编译期与运行期分支，性能目标对应 roofline 上界与实测时延的比值。拆题时先问三个问题：这个考点能否被单卡在分钟级复现？它的失败是否能在不读源码的情况下从 NCU/SASS 或 Triton 编译日志中定位？修复它所需的 token 预算是否落在两周内可回滚的范围内。任一答案为否，就应写入“明确不做”清单，而不是留作待探索项。这里的关键机制是**考点分层**：把题干拆成语义正确性、数值稳定性、访存模式、并行粒度、编译可行性五层，每层绑定一种反馈通道（单元测试、误差界、带宽利用率、occupancy、编译退出码），避免把“跑不通”和“跑得慢”混为同一类失败。

拆解过程本身有系统代价。以单卡上的 Triton 路径为例，一次“改 kernel—编译—跑正确性—采 profile”的闭环，编译时间与 profile 采集时间往往超过实际执行时间；若每题平均消耗的 token 预算记作 $$T_{\text{ep}} = T_{\text{read}} + T_{\text{gen}} + T_{\text{fb}}$$，其中反馈项 $$T_{\text{fb}}$$ 随 profile 粒度线性增长，那么两周内可覆盖的题目数近似为 $$N \approx \frac{B_{\text{total}}}{T_{\text{ep}} \cdot (1 + r_{\text{retry}})}$$，$$r_{\text{retry}}$$ 是多轮 RL 式重试率。这个式子给出的工程判断是：读题阶段就必须决定 profile 的采样密度，全量 NCU 采集会让 $$T_{\text{fb}}$$ 吃掉大部分预算，而只采关键 metric（如 dram throughput、smsp__inst_executed）能把闭环压到可接受范围。失效条件也很明确：当题干涉及的算子依赖跨卡通信或超大显存驻留时，单卡无法构造合法输入，此时任何“先做”的排序都失去意义，应直接标记为环境不满足而非能力不足。

具体例子：面对一个“融合 softmax 与 dropout 的反向算子”题干，拆题时应先判定考点落在数值稳定性（分母累加的溢出界）与访存模式（两次读还是寄存器复用）两层，而不是先写 kernel。解题路径是先构造一个只含前向的 oracle 与误差阈值，再用最小 shape 触发编译，最后才引入带宽公式 $$\text{SOL} = \frac{\text{bytes moved}}{\text{peak BW} \cdot t}$$ 判断是否值得继续优化。若最小 shape 下编译即失败，说明考点在编译可行性层，继续调性能是无效投入；若编译通过但误差超界，说明 oracle 设计本身需要先修。表格可用于记录每层的通过/失败与耗时，把“不做”的决策依据固化为可复查的记录，而不是依赖口头共识。
