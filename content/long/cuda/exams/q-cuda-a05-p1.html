一 · 题干拆成三段：生成、优化、验证的流动

「变异测试审计 checker」这个题目名字里塞了三个动作：变异（mutation）、测试（test）、审计（audit），而宾语是 checker。真正的考点不在「写一个 checker」，而在「让 checker 在 kernel 生成/优化/验证的流动里被反复注入缺陷后仍然判得准」。读题第一步是把题干还原成一条流水线：一次 kernel 生成产生候选实现，一次优化产生变体，一次验证产生判定；checker 是这条流水线上唯一的判决器，而变异测试是给判决器做体检的手段。三段流动的输入输出必须先在纸上钉死，否则后面所有讨论都会漂。

拆题干时要把「被测对象」和「检测工具」分清：被测对象是 kernel 的正确性与性能断言，检测工具是 checker 自身。变异测试审计的意思是——往被测对象里注入已知缺陷（变异体），看 checker 是否报错；报错即「杀死」变异体，不报错即「存活」。存活率高的 checker 是漏检的 checker。这里有一个容易读漏的考点：变异体不是随便乱改，而是按算子语义改，例如把归约的初值从 0 改成 1、把 mask 边界从 < 改成 <=、把共享内存的同步点删掉。每一种变异对应一类真实 bug，checker 的覆盖面由变异算子集合决定。

流动的第一段是生成：输入是算子规格（shape、dtype、语义约束）与参考实现，输出是候选 kernel 源码加一份声称的正确性/性能契约。第二段是优化：输入是候选 kernel 与 profile 反馈，输出是变体（换 tile、换流水、换向量化宽度）。第三段是验证：输入是变体与参考输出，输出是 pass/fail 以及失败定位。checker 在三段里都要被调用，但调用形态不同：生成段判「语义是否等价」，优化段判「优化是否保持语义」，验证段判「数值是否在容差内」。同一份 checker 要扛住三种调用形态，这就是流动的难点。

代价在这一步就要标出来，因为后面每一节都要引用。生成段的代价是 token 与时延：候选越多，checker 被调用的次数线性增长。优化段的代价是编译时间与显存：每个变体都要编译、要跑、要占一块 workspace。验证段的代价是带宽与数值误差预算：参考输出与候选输出的比对要读回全局内存，容差设太紧会误杀正确变体，设太松会放过变异体。这三类代价互相拉扯，checker 的设计就是在拉扯中找平衡点。

二 · 考点清单：checker 要判什么、不能判什么

把考点拆成四类，每类都对应一个具体的判定机制。第一类是语义等价判定：checker 要能区分「数值不同但语义等价」（例如浮点结合律导致的末位差异）与「语义真错」（例如漏掉一个元素）。机制是分层比对——先比形状与 dtype，再比统计量（和、均值、极值），最后比逐元素误差分布。公式上，逐元素相对误差用

$$\varepsilon_i = \frac{|y_i - \hat{y}_i|}{\max(|y_i|, \tau)},\quad \text{pass} \iff \max_i \varepsilon_i \le \epsilon_{\text{rel}} \ \wedge\ \|y-\hat{y}\|_2 \le \epsilon_{\text{abs}}\|y\|_2$$

其中 τ 是防止除零的下限，两个判据必须同时满足，否则大范数元素会掩盖小范数元素的错误。代价是：逐元素比对要把两份输出都读回主机，带宽开销与输出规模成正比；分层比对先用统计量筛掉明显错的变体，能把读回次数压下来，但统计量本身要在设备端算，多一次 kernel 启动的时延。

第二类是性能断言判定：checker 不能只看「跑得快」，要看「快得合理」。机制是把实测时延与 roofline 上界比对，若实测低于带宽/算力上界对应的理论下界，说明测量本身有问题（例如没同步、没算 warmup）。公式是

$$T_{\text{lower}} = \max\!\left(\frac{\text{Bytes}}{\text{BW}_{\text{peak}}},\ \frac{\text{FLOPs}}{\text{FLOPS}_{\text{peak}}}\right),\quad \text{suspect} \iff T_{\text{meas}} < \kappa\, T_{\text{lower}}$$

κ 取略小于 1 的系数，用来抓「测出来比物理下界还快」的假阳性。代价是：roofline 需要知道每个变体的实际访存量与 FLOPs，这要求 checker 能读 profile 或从源码静态推导，静态推导对 Triton/CuTe 的抽象层容易失真，于是要么多跑一次 NCU，要么接受定性判断。

第三类是变异体杀伤判定：checker 对每个变异体必须给出「杀死/存活」二值结论，且这个结论要可复现。机制是固定随机种子与输入分布，变异体与原始实现跑同一批输入。代价是：变异体数量乘以输入批次数就是 checker 的总调用次数，若变异算子有 M 个、每算子 K 个变体、输入 B 组，则调用量为 M·K·B，token 与编译时间都按这个量放大。工程上要按「杀伤率增益/调用成本」排序变异算子，优先保留高增益低成本的。

第四类是审计可追溯判定：checker 报 fail 时必须能指出「哪一类变异被漏掉」，而不是只给一个布尔值。机制是给每个变异体打标签（变异算子 ID、注入位置），checker 的输出是标签到判定结果的映射表。代价是：标签体系本身要维护，标签粒度越细，checker 的日志与存储开销越大；粗粒度标签省成本但定位能力弱。这四类考点合起来，就是 checker 的「判什么」清单；「不能判什么」同样重要——checker 不应判优化策略优劣，也不应判硬件选型，那是 profile 与 roofline 分析的职责。

三 · 解题路径：从规格到判定表的五步

路径第一步是把算子规格翻译成可执行的 oracle。输入是题干给的语义描述，输出是一份参考实现加一组边界输入。机制是「三组输入」：随机稠密输入、边界输入（全零、全最大、含 NaN/Inf）、形状退化输入（单元素、非对齐长度）。代价是：边界输入会触发参考实现自身的慢路径，oracle 的准备时间可能超过被测 kernel 的运行时间，因此 oracle 结果要缓存复用，缓存命中率决定整条流动的摊销成本。

第二步是定义变异算子集合。每个变异算子是一段对源码或对参数的可控改写，改写后必须仍能编译。机制上把变异分成三类：语义变异（改运算、改边界条件）、结构变异（删同步、换内存层级）、数值变异（改 dtype 精度、改累加顺序）。代价是：结构变异容易编译失败，编译失败率高的变异算子要单独统计，否则杀伤率会被「编译不过」污染。工程判断是：编译失败的变异体不计入分母，但要记录失败原因，因为「编译不过」本身也是一种 checker 该捕获的缺陷形态。

第三步是搭判定流水线。伪代码思路如下：

  • 对每个变异体 v：编译 → 跑 B 组输入 → 收集输出与耗时 → 与 oracle 比对 → 记录 (v, 输入组, 判定, 误差, 耗时)。
  • 对每个变异算子 o：统计杀伤率 kill(o) = 被杀变异体数 / 该算子变异体总数。
  • 对 checker 整体：输出杀伤率矩阵，行是变异算子，列是输入组，矩阵稀疏处即覆盖盲区。

代价是：矩阵的每一格都是一次完整运行，B 组输入乘以变异体总数就是总运行次数；若每组输入都要重新编译，编译时间会成为主项，因此要按「同变异体只编译一次、多输入复用二进制」组织，把编译次数从 M·K·B 压到 M·K。

第四步是校准容差。容差不是拍脑袋，而是从 oracle 自身的数值稳定性推。机制是：对参考实现跑两遍不同累加顺序，测出它自身的误差分布，把 ε_rel 设在分布的高分位之上。代价是：容差越紧，误杀正确变体越多，checker 的假阳性上升；容差越松，数值变异类变异体存活越多，假阴性上升。校准的代价是一次性的额外运行，但换来的是后续所有判定的可解释性。

第五步是产出判定表与审计报告。判定表要能回答「哪个变异算子没被杀死、在哪种输入下存活」。具体例子：若「删同步」类变异体在单元素输入下全部存活，说明 checker 的输入集缺少能暴露竞态的规模，补一组多 block 竞争输入即可；若「改边界条件」类变异体在随机稠密输入下存活，说明随机输入没覆盖到边界，补边界输入。这一步的代价是报告生成与人工复核的时间，但它是把 checker 从「能跑」推到「可信」的关键一步。

四 · 需要调用的公式：误差、杀伤率与成本

第一组公式是误差判据，已在第二节给出逐元素形式。这里补一个聚合形式，用于判定表里的「误差列」：

$$E = \frac{\|y-\hat{y}\|_2}{\|y\|_2},\quad \text{rel\_err}_{\text{max}} = \max_i \frac{|y_i-\hat{y}_i|}{|y_i|+\tau}$$

两个量一起报，是因为 L2 相对误差对离群值不敏感，而 max 相对误差对单点错误敏感；只报一个都会漏。代价是两次归约，若在设备端做，要多一个 reduction kernel 的启动时延；若在主机端做，要多一次全量读回。

第二组公式是杀伤率与覆盖率：

$$\text{kill}(o) = \frac{|\{v \in V_o : \text{checker}(v)=\text{fail}\}|}{|V_o|},\quad \text{cover} = \frac{|\{o : \text{kill}(o) \ge \theta\}|}{|O|}$$

θ 是判定某变异算子「已被覆盖」的杀伤率阈值。cover 是审计报告的头号指标，它回答「checker 对多少类缺陷有把握」。代价是：θ 设高则 cover 低但可信，设低则 cover 虚高；工程上按缺陷危害分级设不同 θ，高危算子用高阈值。

第三组公式是成本模型，用来决定变异测试跑多深：

$$C_{\text{total}} = N_{\text{mut}} \cdot \left( t_{\text{compile}} + B \cdot (t_{\text{run}} + t_{\text{readback}}) \right)$$

其中 N_mut 是变异体总数，t_compile 是单次编译时间，t_run 是单组输入运行时间，t_readback 是输出读回时间。这个式子直接告诉你优化方向：编译时间占比高就复用二进制，读回占比高就分层比对先筛后读，运行占比高就减少输入组数但保留边界组。具体例子：若某类变异体只需判「是否编译通过」，则 B 可取 0，成本退化为 N_mut·t_compile，这类变异适合放在流水线最前做快速筛。

第四组是 token 成本，针对 LLM 生成 checker 的场景：checker 的 prompt 里要带算子规格、参考实现、变异算子说明，token 量与这三者长度成正比；多轮修复时每轮都要重带上下文，token 量按轮数线性增长。工程判断是：把变异算子说明做成结构化短标签而非自然语言长描述，能显著压 prompt 长度，代价是标签体系的设计成本前置。

五 · 具体例子：一个归约算子的读题拆解

以「按行归约求和」为例走一遍读题。题干给的规格是二维输入、按行求和、输出一维。考点拆解：语义等价判定要覆盖「行内元素顺序」「初值」「mask 边界」三类变异；性能断言要覆盖「是否用了向量化加载」「是否合并了访存」；变异算子集合至少包含改初值、改循环边界、删同步、改累加精度四类。解题路径按第三节五步走，第一步的边界输入要包含行长非 2 的幂、行长小于 warp 宽度、含 Inf 的行。

判定流水线的具体形态：对「改初值」变异体，随机稠密输入下误差 E 会明显偏离，checker 应杀死；对「删同步」变异体，单 block 输入下可能存活，因为单 block 内竞争窗口小，必须补多 block 输入才能暴露。这里体现的是输入集与变异算子的匹配关系——杀伤率矩阵的稀疏格直接指向输入集的缺口。代价上，多 block 输入会让运行时间上升，但只对「删同步」这一类变异体跑多 block 输入即可，按变异算子分派输入集能把成本控制在可接受范围。

公式调用上，这个例子里 ε_rel 的校准要特别小心：归约的累加顺序变化会带来末位差异，若 ε_rel 设得比参考实现自身误差还紧，会把正确的重排变体误杀。做法是先测参考实现在不同累加顺序下的 rel_err_max 分布，取其高分位作为 ε_rel。代价是这次校准要多跑几组输入，但换来的是「改累加顺序」类变异体不会被误判为「语义错误」——这类变异体本就不该被杀死，因为它语义等价，只是数值路径不同。这正说明 checker 的判定边界要按「语义是否等价」划，而不是按「数值是否逐位相同」划。

审计报告的具体产出：一张表，行是四个变异算子，列是三组输入（随机、边界、多 block），格子里是杀死/存活。若「改循环边界」在边界输入下存活，说明边界输入没覆盖到「行长恰好等于 tile 宽度」的情形，补这一组即可。这张表就是 checker 可信度的直接证据，也是下一轮变异算子扩充的依据。

六 · 工程判断：读题阶段就要定的三个取舍

第一个取舍是变异算子集合的广度与成本。算子越多，cover 的分母越大，但 N_mut 线性推高 C_total。读题阶段要按「真实 bug 分布」排序：语义变异优先，结构变异次之，数值变异最后，因为数值变异多数语义等价，杀它反而暴露 checker 容差过紧。代价是排序本身需要领域知识，但比盲目铺满算子集合省得多。

第二个取舍是输入集的规模与代表性。B 组输入直接乘进成本公式，但输入集不足会让杀伤率矩阵出现整列存活，误判 checker 漏检。工程判断是：每个变异算子配最小充分输入集——能杀死该类变异体的最少输入组合，而不是全量输入。具体机制是按变异算子分派输入，而非所有变异体跑所有输入，这把 B 从全局常数变成按算子变化的向量，成本按算子加权而非按最大值。

第三个取舍是 checker 输出的粒度。布尔值最省成本但无法审计；标签映射表可审计但存储与日志开销大。读题阶段要定的是「审计需要多细」：若目标是定位漏检类别，标签到变异算子 ID 即可；若目标是定位漏检的具体代码位置，标签要到行号，成本上一个量级。工程上先用算子级标签跑通流动，再按需细化，避免一开始就为粒度付全额成本。

这三个取舍的共同点是：它们都在读题阶段决定，而不是在实现阶段补救。读题阶段把流动的三段、考点的四类、路径的五步、公式的四组钉死，后面写 checker 才是填空题而不是开放题。最后落在一个具体机制上：杀伤率矩阵的行列结构——行是变异算子、列是输入组——就是读题阶段要预判的产出形态，矩阵的稀疏格就是后续所有优化的靶点。
