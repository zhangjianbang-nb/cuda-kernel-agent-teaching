一 · 题干的三层结构：问的是什么、答的是什么、判的是什么

这道题表面上是一个公式题，实质上是一道“口径题”。题干由三句话构成，每一句都在指定答题的边界。第一句“《Dr. Kernel: Reinforcement Learning Done Right for Triton Kernel Generations》报告的加速比如何计算”锁定的是论文自身的报告口径，不是 PyTorch 官方 benchmark 口径，也不是 KernelBench 原始脚本的口径；第二句“若基线时延为 T0、候选为 T1，写出 speedup 公式”要求把口径落成一个可计算的表达式，并显式声明 T0、T1 各自测的是什么；第三句“结合论文中的口径说明这个数字在什么条件下不可比”是真正的考点——它要求答题者指出该比值在哪些测量条件下失去意义。三句话对应三个得分点：口径识别、公式落地、可比性边界。漏掉第三句，答案就退化成初中算术；只答第三句而不写公式，则无法证明你真的读懂了 T0 与 T1 的取法。

需要特别注意的是，题干用的是“报告的加速比”而非“真实的加速比”。这个措辞差异是命题人埋的钩子：论文报告的 speedup 是一个由特定测量协议产生的统计量，它的分子分母都带有协议烙印。答题时若直接写 \(T_0/T_1\) 而不交代 T0 是 baseline 的什么时延（端到端 wall-clock？单 kernel device time？含编译？含首次 autotune？），就等于默认了一个未声明的协议，这在工程评审里是硬伤。

二 · 公式本身与它的三个必须声明项

加速比的定义式是：

$$\text{speedup} = \frac{T_0}{T_1}$$

其中 T0 为基线时延，T1 为候选（生成的 Triton kernel）时延。公式一行写完，但要让这个式子成立且可复核，必须同时声明三件事，缺一不可：

  • 测的是什么区间：是包含 host 侧 launch 与同步的端到端时延，还是仅 device 侧 kernel 执行时间。前者含 Python/框架开销与 launch latency，后者只含 SM 上的执行。两者在短 kernel 上可以差出一个数量级，因为小 kernel 的 launch 开销会主导 wall-clock。
  • 测的是什么输入：shape、dtype、batch、是否含边界 case。Triton kernel 的 tile 配置与 shape 强耦合，同一份代码在不同 shape 下的时延可能反向排序。
  • 测的是什么状态：是否包含首次编译与 autotune 的摊销。Triton 的 JIT 编译与 autotune 在首次调用时发生，若 T1 只测稳态热路径，则编译成本被排除在比值之外；若 T0 是预编译的 cuBLAS/cuDNN 路径，则比较本身就不对等。

代价在这里体现得很直接：把编译时间计入 T1，会让一个稳态快 2 倍的 kernel 在单次调用场景下变成慢的；把 launch 开销计入 T0 而不计入 T1（或反之），会让比值系统性偏移。因此公式的正确写法应带下标注释，例如 \(\text{speedup} = T_0^{\text{(proto)}} / T_1^{\text{(proto)}}\)，proto 显式写出测量协议。答题时给出这个上标，比多写三行解释更能说明你懂口径。

三 · 论文口径下的“不可比”条件清单

第三问的实质是：在什么条件下 \(T_0/T_1\) 这个数不再承载“候选更快”这一语义。按测量协议拆，至少有以下几类不可比情形，答题时应逐条点名并各给一句机制解释。

  • 基线不同源：T0 取自 PyTorch eager 参考实现、torch.compile 产物、cuBLAS 手写调用，三者的绝对时延差异巨大。若论文的 T0 是某一固定参考（例如 eager），而读者拿自己的 T0（例如已用 torch.compile 优化过的版本）去套同一候选的 T1，得到的比值不可比——分母换了，比值失去意义。
  • 计时区间不一致：一端含 launch 与同步，另一端只含 device time。短 kernel 上这会直接翻转结论。
  • 编译/autotune 摊销策略不一致：T1 取稳态热路径而 T0 取冷启动，或反之。Triton 的 autotune 会在候选配置空间上做搜索，其成本与配置数成正比，若被排除则高估候选。
  • 输入分布不一致：shape、dtype、stride、是否 contiguous 不同。Triton kernel 的 block size 与 num_warps 是针对特定 shape 调的，换 shape 后同一 kernel 的时延可能劣于基线。
  • 硬件与软件栈不一致：不同 GPU 架构的 SM 数、L2 容量、HBM 带宽不同，同一 kernel 的 roofline 位置不同；CUDA 版本、Triton 版本、驱动版本亦影响生成代码的 lowering 质量。
  • 正确性未对齐：若候选在数值容差外或未覆盖边界 case，其 T1 是在“少算了活”的前提下测得的，此时 speedup 再大也不可比——这是 oracle 问题，不是性能问题。

这六条里，前三条属于协议层不可比，后三条属于环境层不可比。答题时若能做这个二分，说明你不是在背清单，而是在按“测量协议 vs 测量环境”组织判据。代价维度上，每一条都对应一个具体的失真方向：基线不同源导致分母漂移，计时区间不一致导致短 kernel 结论翻转，摊销策略不一致导致候选被高估，输入不一致导致 tile 配置失配，栈不一致导致 lowering 质量差异，正确性未对齐导致分子被虚高。

四 · 解题路径：从题干到可复核答案的四步

给出路径而非答案，是本部分的写作约束，也是这道题真正想训练的能力。可复核的答题路径应为四步：

  • 第一步，定位口径：在论文中找到报告 speedup 的那张表或那段文字，确认 T0 的取法（哪个 baseline、哪个精度、哪个 shape 集合）与 T1 的取法（是否含编译、是否取中位数/均值、warmup 次数）。这一步的产出是一句“T0 = X 协议下的基线时延，T1 = Y 协议下的候选时延”。
  • 第二步，写公式并带上标：\(\text{speedup} = T_0^{\text{proto}_0} / T_1^{\text{proto}_1}\)，并声明 proto 相同是可比的前提。
  • 第三步，列不可比条件：按协议层与环境层二分，逐条给出机制与失真方向，每条配一个具体例子（例如“短 kernel 上 launch 开销占 wall-clock 主导，含/不含 launch 的两种计时会给出相反的排序”）。
  • 第四步，给出复核建议：说明若要跨论文比较，需要把 T0、T1 重测到同一协议下，或至少报告协议元数据（warmup、同步方式、计时工具、shape 集合）。

这四步的 token 成本很低，但第三步的例子质量决定得分上限。命题人期待的例子应当具体到机制层面，而不是“不同设置下结果不同”这种空话。例如：一个 elementwise kernel 在小 shape 上 device time 只有几微秒，而 launch + 同步的 wall-clock 可能是它的数倍，此时“含 launch 的 T1 / 不含 launch 的 T0”会系统性压低 speedup；反过来若 T1 排除了 autotune 而 T0 是冷启动，则系统性抬高 speedup。两个方向的失真都要能说清。

五 · 与 roofline/SOL 口径的接口：为什么 speedup 不是 SOL

这道题还有一个隐藏考点：speedup 是相对量，SOL（speed of light）是绝对量。前者回答“比基线快多少”，后者回答“离硬件上限还有多远”。二者不可互相替代。一个 kernel 可以在 speedup 上很好看（基线本身很慢），同时在 SOL 上只有很小的占比（离 HBM 带宽上限很远）；反之，一个已经接近 SOL 的基线，其候选的 speedup 天然被压缩在 1 附近，此时“加速比小”不代表候选差，而是分母已经接近物理上限。

$$\text{SOL}_{\text{mem}} = \frac{\text{bytes moved}}{\text{peak BW}},\quad \text{SOL}_{\text{comp}} = \frac{\text{FLOPs}}{\text{peak FLOPS}}$$

把这两个式子与 speedup 并置，可以得出一个工程判断：报告 speedup 时必须同时报告基线相对 SOL 的位置，否则读者无法判断这个比值是“基线太慢”还是“候选太快”。代价维度上，SOL 口径需要额外的硬件峰值参数与 bytes/FLOPs 计数，这些计数在 Triton 生成代码里并不总是显式可得（需要从 tile 配置与循环结构反推），因此报告 SOL 的工程成本高于报告 speedup；但缺少 SOL 的 speedup 在跨硬件比较时几乎无意义，因为峰值带宽与 FLOPS 随架构变化，同一比值的物理含义随之漂移。

具体例子：一个 memory-bound 的归一化 kernel，若基线是未融合的多趟实现（读多次、写多次），其 bytes moved 远高于单趟融合版本，speedup 会显著大于 1；但若把候选放到 SOL 口径下，它可能只是从“远低于带宽上限”走到“接近带宽上限”，此时 speedup 的大小主要反映基线的低效，而非候选的卓越。答题时点出这一层，说明你理解 speedup 的分母承载了基线的实现质量。

六 · 一个可操作的判据：什么时候这个数字可以写进结论

把上面的分析收束成一个判据：只有当 T0 与 T1 满足“同源基线、同计时区间、同摊销策略、同输入分布、同软硬件栈、同正确性 oracle”这六同，\(T_0/T_1\) 才可以作为“候选更快”的结论写进报告；缺任意一项，该数字只能作为该协议下的观测值，不能跨协议引用。这个判据本身就是答题第三问的骨架。

工程上更实用的做法是把协议元数据与 speedup 一起落盘：记录 warmup 次数、同步方式（是否 cudaDeviceSynchronize / torch.cuda.synchronize）、计时工具（CUDA events 还是 wall-clock）、shape 集合、是否含首次编译、Triton 版本与 autotune 配置数。这些字段的存储成本可以忽略，但它们决定了这个数字在半年后还能不能被复核。反过来，若论文只报告一个标量 speedup 而不报告协议，读者应当把它当作定性信号而非定量结论——这不是对论文的苛责，而是测量学的基本要求。落在具体机制上：Triton 的 autotune 在首次调用时对配置空间做搜索，其搜索成本与配置数成正比，若论文把这段成本排除在 T1 之外，则报告的 speedup 描述的是“稳态热路径”而非“用户首次调用体验”，这两个语义在部署决策里指向不同的结论。

加速比口径的边界：T0/T1 何时不可比

《Dr. Kernel》给出的加速比定义本身只有一行：若基线时延为 T0、候选时延为 T1，则 $$\text{speedup}=\frac{T_0}{T_1}$$ 论文口径下这个比值是“同一算子、同一输入形状、同一精度、同一测量协议下，候选实现相对基线实现的时延倒数比”。真正决定这个数字能否被引用的不是公式，而是 T0 与 T1 是否落在同一坐标系里。读题时若只抄公式不看口径，就会把不同测量边界下的两个数直接相除，得到一个既非上界也非下界的伪加速比。工程上必须先把“计时区间”钉死：T 是端到端墙钟（含 launch、含 host 侧同步、含内存分配），还是仅 kernel 主体（device 侧事件计时、剔除首次调用与编译）；是单次冷启动，还是预热后的稳态中位数。这三种口径在同一份代码上可以差出数倍，而公式对此毫无感知。

失效条件可以归成四类，每一类都让 T0/T1 失去可比性。其一，基线不唯一：T0 取 PyTorch eager、torch.compile、cuBLAS 还是手写 CUDA，量级完全不同；论文口径要求基线固定为某一参考实现，换基线等于换考卷。其二，输入域漂移：形状、batch、dtype、stride、是否含 mask 与边界，都会改变最优 tiling 与 occupancy，候选在某一形状上快、在另一形状上慢，单点比值不能外推。其三，测量污染：Triton 首次调用触发 JIT 编译与 autotune，若把这段算进 T1，加速比会被编译时间吞掉；反之若把 autotune 的候选搜索时间排除在 T1 之外，又等于让候选免费获得一份离线调优预算，与基线的不对等。其四，正确性未闭环：T1 只有在输出通过 oracle（数值容差、边界用例、非连续布局）后才有资格进入分子，否则“更快”可能只是少算了工作量的错误实现。

系统代价要按“谁付”来拆。JIT 编译与 autotune 的代价付在首调用时延上，属于一次性但可观测的尖峰；稳态收益付在吞吐上，二者不能混入同一个比值。一个具体的判断例子：某候选在固定形状下 T1 明显低于 T0，但若 T0 用的是未融合的多 kernel 链路而 T1 是单融合 kernel，则比值里混入了“减少 launch 次数”的收益，此时应把它标注为端到端口径而非单 kernel 口径，并在表里并列两个数而不是取其一。

口径维度可比条件不可比时的表现
基线实现固定同一参考实现换基线后比值漂移
计时区间同为 kernel-only 或同为端到端一方含 launch/编译
输入域形状/dtype/stride 一致单点外推
正确性oracle 通过后计入错误实现虚高

因此读题阶段的动作不是算比值，而是先写出一张“口径声明”：T0 与 T1 各自的计时边界、基线身份、输入集合、是否含编译、正确性判定阈值。只有这五项对齐，T0/T1 才是一个可被复现的数；任一项缺失，加速比就退化为一个只能内部比较、不能跨方案引用的相对量。

加速比口径的边界：T0 从哪来、何时不可比

读题时最容易滑过去的一步，是把 speedup 当成一个纯算术量。论文口径下 $$\text{speedup}=\frac{T_0}{T_1}$$，其中 T0 是参考实现（baseline）的时延、T1 是候选 kernel 的时延，两者必须在同一输入形状、同一 dtype、同一设备、同一计时方法下测得，且 T1 只计 kernel 本体、不含编译与 autotune 预热。一旦 T0 取自框架算子库的默认路径而 T1 取自候选在最优 tile 下的稳态时延，分子分母就不同源，这个比值不再可比——它不是加速，而是两条不同测量流水线的商。

失效条件集中在三处：其一，T0 若包含框架调度、内存分配或 layout 转换，而 T1 是裸 kernel 计时，则分母被系统性压低，speedup 虚高；其二，若候选仅在某一固定 shape 上调优而 baseline 走通用启发式，则比较退化为“特化 vs 通用”，换 shape 即翻盘；其三，若 T1 低于计时分辨率或受 launch 开销主导，比值被固定开销污染。工程上应把口径写成三元组（T0 来源、计时边界、shape 集合），任一缺失即标记不可比。

口径要素可比不可比
T0 来源同库同版本参考实现跨版本/跨框架默认路径
计时边界两侧同为 kernel-only 稳态一侧含调度与分配
shape同一离散集合逐点报告单点最优对通用启发式

代价落在评测可信度上：把不可比口径混入训练奖励，等于给策略注入一个与真实收益无关的偏置信号，多轮 RL 会朝“压低分母”而非“真正提速”的方向漂移；同时逐 shape 重测使评测时延与 token 消耗随 shape 集合线性增长。因此读题时应先判定该题属于“同源可比”还是“需重测 T0”，再决定是否调用 speedup 公式，而不是见到两个时延就直接相除。
