一 · 题干的三层结构：从论文标题拆出可判定的问题

题干只有一句话，但它同时压了三件事：一是对 Astra 方法机制的准确复述，二是对“迁移”这一失效场景的定位，三是给出可执行的验证方案与回退条件。三者缺一，答案就不成立。拆题时先做一次语法分析：主语是“Astra 的方法”，不是 Astra 这个系统整体；谓语是“最可能在哪里失效”，要求的是排序后的单点判断而非罗列；状语是“跨硬件、跨 shape 或跨 dtype 迁移时”，三个维度并列，意味着必须分别给出机制层面的失效路径，再收敛到一个“最可能”的结论。

这里有一个容易读漏的约束：“不要只复述摘要”。这句话在评分上等价于一条硬性判据——凡是能在摘要里直接找到的句子，都不构成得分点。摘要通常只交代多 agent 分工（如 planner、coder、profiler、critic 之类的角色划分）与迭代优化循环的存在，而失效分析必须落到这些角色之间的信息传递契约上：谁把什么信息写进了下一轮的上下文，谁读取了硬件相关的反馈，谁对 shape 做了假设。换句话说，题干问的不是“Astra 有哪些模块”，而是“这些模块之间的哪一条接口在分布偏移下会传错信息”。

因此解题路径应当是：先建立 Astra 的信息流图（agent 角色 → 中间产物 → 反馈信号 → 决策），再在图上标注三个迁移维度各自会污染哪条边，最后用“污染是否可被系统自身的验证环节捕获”作为排序依据。可捕获的失效是性能退化，不可捕获的失效才是正确性风险，后者优先级更高。这条判据贯穿全文，也是后面验证方案设计的骨架。

二 · 考点定位：多 agent 优化系统里真正承压的三个接口

把 Astra 拆成接口后，考点集中在三处。第一处是性能反馈接口：profiler agent 采集到的指标（时延、带宽利用率、occupancy、访存事务数）如何被序列化成文本或结构化信号进入下一轮 prompt。第二处是代码生成接口：coder agent 产出的 kernel 变体所隐含的硬件假设（warp 数、shared memory 容量、tensor core 代际、向量化宽度）是否被显式记录。第三处是评判接口：critic 或验证环节用什么 oracle 判定“这一版更好”，是相对加速比、绝对时延，还是正确性比对。

三个迁移维度分别打击不同接口。跨硬件迁移打击的是第一与第二接口的耦合：profiler 给出的反馈是源硬件上的因果解释，而 coder 会把它当成目标硬件上的因果规律来用。例如源卡上 shared memory 容量宽裕，profiler 反馈“bank conflict 是瓶颈”，coder 于是加大 padding；换到 shared memory 更紧张的目标卡，同一改动可能把 occupancy 压下去，而反馈信号里并不包含这条副作用。跨 shape 迁移打击的是评判接口：小 shape 下 launch 开销与尾效应主导，大 shape 下带宽与并行度主导，同一套“加速比更好”的判据在两个区间指向不同的最优变体。跨 dtype 迁移则同时打击第二与第三接口：低精度路径涉及累加器精度、舍入模式与溢出边界，而多数评判 oracle 只做容差比对，容差阈值本身是随 dtype 变化的超参。

用一张表把考点与代价对齐，便于在答题时逐项落笔：

接口迁移维度失效形态主要代价
性能反馈 → 代码生成跨硬件把源硬件的瓶颈归因当作目标硬件的规律时延回退、occupancy 下降、编译时间浪费在无效变体上
评判 oracle跨 shape加速比判据在小/大 shape 区间指向不同最优解选中变体在目标 shape 上劣于基线，token 消耗在错误方向上迭代
代码生成 → 评判跨 dtype容差阈值与累加精度不匹配，正确性判定失真显存带宽收益被精度修复抵消，或错误通过验证

这张表的作用不是给结论，而是给答题者一个自检清单：每写一条失效路径，必须能指出它落在哪一行，并给出对应的代价量纲。缺代价量纲的判断在工程语境里不可信。

三 · 失效排序的形式化：用可捕获性而非严重性排序

“最可能在哪里失效”需要一个排序准则。直觉上按严重性排序（正确性 > 性能）是合理的，但题干要的是“最可能”，即概率意义上的高发点，而不是最坏点。更稳的做法是把两个维度合成一个判据：失效发生的概率 × 该失效逃过系统自检的概率。后者可称为不可捕获度。Astra 这类系统的自检主要来自两处：正确性比对（对拍参考实现）与性能回归（与基线比较）。凡是能被对拍捕获的错误，会在迭代中被淘汰，不构成最终失效；凡是能表现为“通过验证但性能不达标”的退化，会被误判为收敛。

$$\text{risk}(f)=\Pr[f]\cdot\bigl(1-\Pr[\text{detect}(f)\mid f]\bigr)$$

这个式子的工程含义是：一个高发但必被捕获的失效，风险接近零；一个低频但静默的失效，风险可能最高。把它套到三个维度上，跨 dtype 的精度问题通常能被对拍捕获（只要 oracle 设计得当），因此不可捕获度低；跨 shape 的性能退化会被性能回归部分捕获，但若回归只在单一 shape 上跑，则捕获概率骤降；跨硬件的归因错配几乎无法被系统自身捕获，因为系统没有目标硬件的真实 profile 作为对照，它只能看到“这一版在目标机上跑出来的数”，而无法判断这个数是否已接近该硬件的 roofline 上限。

由此得到一个可辩护的排序假设：跨硬件迁移中“反馈归因错配”是最可能失效点，其风险由不可捕获度主导；跨 shape 次之，取决于回归覆盖的 shape 集合；跨 dtype 再次，前提是 oracle 的容差设计没有系统性偏差。这个排序不是结论，而是需要在答题中显式论证的中间命题——评分者要看的正是这条论证链，而非排序结果本身。

具体例子可以这样构造：假设源硬件上某 kernel 的瓶颈被 profiler 判定为全局访存未合并，coder 引入 shared memory 中转并做向量化加载；该变体在源硬件上时延下降。迁移到访存带宽更高、shared memory 更小的目标硬件后，中转带来的额外拷贝与容量压力使 occupancy 受限，时延反而上升。系统看到的只是“这一版比上一版慢”，于是回退或继续变异，但它不会去质疑“未合并访存”这个归因在目标硬件上是否仍是主瓶颈——因为归因文本已经写进了上下文，成为后续所有变体的先验。这就是静默失效的典型形态：不是算错，而是优化方向的先验被污染。

四 · 解题路径：从信息流图到可证伪的假设

答题时应避免直接跳到“我认为跨硬件最危险”，而要先给出可复现的分析路径，让判断显得可检验。建议的四步路径如下。

  • 第一步，画信息流图。把 Astra 的每一轮迭代抽象为四元组：上下文 C、候选代码 K、目标机测量 M、决策 D。标注哪些字段是硬件相关的（occupancy、SM 数、cache 容量）、哪些是 shape 相关的（grid 维度、tile 大小）、哪些是 dtype 相关的（累加器类型、容差）。这一步的产出是一张“字段—维度”关联表。
  • 第二步，定位跨维度的字段泄漏。检查是否存在这样的字段：它在源分布上被测量、被写入上下文，却在目标分布上被当作常量使用。跨硬件场景中，最典型的是把源硬件的 occupancy 上限或 shared memory 预算硬编码进生成模板。
  • 第三步，构造可证伪假设。针对每条泄漏路径写出“若假设成立，则应观察到 X”的预测。例如：若归因错配是主因，则在目标硬件上固定其他变量、仅替换 profiler 反馈文本为中性描述，性能应显著改善；若假设不成立，则改善不出现。
  • 第四步，给出验证方案与回退条件。验证方案要能区分“失效来自归因”与“失效来自代码本身不适配”，回退条件要写成可执行的判定式而非模糊描述。

第三步的关键在于“固定其他变量”。多 agent 系统的输出是高维的，直接比较两个完整 pipeline 的端到端时延无法归因。可行的做法是做消融：保留 coder 与 critic，仅把 profiler 的输出替换为与硬件无关的中性指标（如仅给时延数值，不给瓶颈解释），观察目标硬件上的收敛速度与最终时延。这个消融的代价是 token 与编译时间——每一轮都要重新生成并编译 kernel，编译时间在变体数量大时会成为主要开销，因此消融应限制在少量代表性 shape 上。

第四步的回退条件应当写成阈值形式。一个可用的判据是：当目标硬件上连续若干轮迭代的相对基线加速比不再提升，且 profiler 反馈的瓶颈归因与目标硬件的理论 roofline 预测不一致时，触发回退——回退动作是清空上下文中的归因文本，仅保留数值指标，重新开始搜索。这里的“不一致”需要一个可计算的判据，例如实测达到的带宽占该硬件理论峰值的比例与 profiler 声称的瓶颈类型矛盾。公式上可写成：

$$\text{rollback}\iff \Bigl(\Delta s_t\le 0\ \text{for}\ t\in[t_0,t_0+k]\Bigr)\ \wedge\ \Bigl(\bigl|\,\hat{b}-b_{\text{roof}}\,|>\epsilon\Bigr)$$

其中 ŝ 是相对基线的加速比，̂b 是实测带宽利用率，broof 是该硬件 roofline 给出的可达上限估计，ε 是容忍带宽。这个式子的价值在于它把“归因是否可信”转成了可测量的量，而不是留给 critic agent 的主观判断——后者恰恰是被污染的那一环。

五 · 需要调用的公式与量纲：把定性判断锚在可测量上

本部分要求给出解题路径与需要调用的公式，公式的作用是让“失效”具备量纲，从而可被实验区分。除上面的风险式与回退式外，至少还要调用三类。

其一是 roofline 判据，用于判断目标硬件上的实测性能是否已接近该硬件的上限，从而判断 profiler 的归因是否还有意义：

$$P_{\text{roof}}=\min\bigl(P_{\text{peak}},\ I\cdot B_{\text{mem}}\bigr),\qquad I=\frac{\text{FLOPs}}{\text{Bytes}}$$

当实测性能已贴近 Proof 时，继续按“访存未合并”之类的归因去优化是无效的，因为瓶颈已转移到算术强度或 occupancy。跨硬件迁移恰恰会改变 I 的临界点：同一 kernel 在带宽更高的硬件上可能从 memory-bound 翻转为 compute-bound，而归因文本不会自动翻转。这是跨硬件失效在公式层面的直接体现。

其二是跨 shape 的尾效应判据。小 shape 下 grid 规模不足以填满 SM，launch 开销与尾部波次主导，加速比判据会系统性偏向减少 kernel 数量而非减少单 kernel 工作量：

$$T_{\text{tail}}\approx \frac{N_{\text{blk}}\bmod N_{\text{SM}}}{N_{\text{SM}}}\cdot T_{\text{wave}}$$

答题时应指出：若评判 oracle 只在单一 shape 上做回归，则它在小 shape 区间选出的变体在大 shape 上可能劣于基线。验证方案因此必须包含 shape 扫描，且扫描点的选择要覆盖 Nblk 相对 NSM 的整数倍边界，因为尾效应在边界处最显著。

其三是 dtype 的精度预算。低精度路径中，累加器位宽与容差阈值必须匹配，否则正确性判定会失真：

$$\epsilon_{\text{tol}}\ \gtrsim\ \sqrt{K}\cdot \epsilon_{\text{mach}}\cdot \lVert x\rVert$$

其中 K 是归约长度，εmach 是该 dtype 的机器精度。跨 dtype 迁移时，若 oracle 沿用高精度的容差阈值，低精度实现会被误判为错误而遭淘汰，系统于是收敛到“保守但慢”的实现；反之若容差过宽，真实溢出会被放过。这条公式的工程价值在于它把“容差该设多少”从拍脑袋变成可计算的量，代价则是需要在验证阶段额外跑一次高精度参考以标定 εtol，这增加了显存与时间开销。

三类公式共同支撑一个判断：跨硬件失效最难被系统自身捕获，因为它改变的是 roofline 的拐点而非数值本身；跨 shape 与跨 dtype 的失效则分别有尾效应与精度预算可作为外部锚点，因而更容易被设计良好的验证方案捕获。

六 · 验证方案的设计要点与不可回避的代价

验证方案必须能区分三种失效来源，否则“最可能在哪里失效”的判断无法落地。建议采用三层验证，每层对应一个迁移维度，且每层都要明确其代价。

第一层是归因消融，针对跨硬件。做法是双轨运行：一轨保留 profiler 的瓶颈归因文本，另一轨仅保留数值指标，两轨在目标硬件上从相同初始代码出发，比较收敛曲线与最终时延。若两轨最终时延差异显著且归因轨更差，则归因错配被证实。代价是双倍编译与双倍测量，编译时间在多 agent 迭代中本就是瓶颈，因此该层应只在少量代表 shape 上执行。

第二层是shape 扫描回归，针对跨 shape。选取覆盖尾效应边界的若干 shape，对每个候选变体记录相对基线的加速比，并要求加速比在扫描集合上的最小值不低于阈值。代价是测量时间随 shape 数线性增长，且大 shape 的显存占用会限制并发测量数。

第三层是精度标定，针对跨 dtype。用高精度参考实现标定容差阈值，再以该阈值判定低精度候选。代价是参考实现本身的显存与时间开销，以及标定过程需要额外一轮对拍。

三层验证的排序也应是代价感知的：先跑最便宜的第二层筛掉明显不适配的变体，再对幸存者跑第一层与第三层。这个顺序的理由是编译时间与显存是稀缺资源，而 shape 扫描只需重跑已有二进制，边际成本最低。

回退条件应绑定到具体层：若第一层证实归因错配，回退动作是清空上下文中的归因字段并重启搜索；若第二层发现加速比在扫描集合上出现负值，回退到基线变体并冻结该 shape 区间的搜索；若第三层标定显示容差与 dtype 不匹配，回退到高精度路径并重新设定阈值。每个回退动作都要写明触发它的可测量条件，避免“表现不佳就回退”这种不可执行的表述。

最后落到一个工程判断上：Astra 这类多 agent 优化系统的核心脆弱性不在单个 agent 的能力，而在 agent 之间传递的解释性文本。数值指标是分布无关的，解释是分布相关的。跨硬件迁移之所以最可能失效，正是因为解释性文本被当作了跨分布的常量。因此任何针对该类系统的验证方案，都应以“能否在不依赖解释文本的情况下复现性能收益”作为核心判据——这也正是归因消融这一层不可省略的原因。
