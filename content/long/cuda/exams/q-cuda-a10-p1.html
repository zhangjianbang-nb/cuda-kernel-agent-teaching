一 · 题干里的三个层次：从「读懂一段 SASS」到「给出上线判断」

这类题目的题干通常只给两样东西：一段（或一段摘要形式的）SASS 反汇编，以及一个性能现象描述——例如某个 kernel 在 NCU 里 smsp__average_warps_issue_stalled_* 的分布异常，或者实测吞吐只有 roofline 预测的某个比例。题干不会直接问「这个 stall 是什么」，而是问「瓶颈在哪、该改什么、值不值得上线」。因此读题的第一步是把题干拆成三个层次，每一层对应不同的考点与不同的公式族。

第一层是指令级事实层：SASS 里出现了哪些指令、哪些是长延迟指令（LDG、LDS、HMMA、MUFU、BAR）、哪些是控制流指令、寄存器复用距离有多远。这一层考的是「你能不能把 SASS 行翻译成资源占用与依赖关系」，调用的是指令发射与依赖距离的记账公式。第二层是warp 调度层：给定 SM 上的 warp 数、每 warp 的指令流、以及各条指令的延迟，算出每个 cycle 有多少 warp 处于可发射状态（eligible），从而算出 stall 的构成。这一层考的是 Little 定律式的占用-延迟匹配，以及 stall 分类的分解公式。第三层是决策层：把 stall 归因换算成「改这一处的收益上限」，再与改动成本（编译时间、寄存器压力、正确性风险、搜索预算）比较，给出上线与否的判断。这一层考的是 Amdahl 型收益上界与代价核算。

三层之间的连接是单向的：事实层决定调度层的输入参数，调度层给出 stall 分解，决策层只接受分解结果中「可被单点改动影响」的那部分。读题时若跳过第一层直接谈「memory bound」，就会在算例里把 L1 命中率与 DRAM 带宽混为一谈；若跳过第二层直接谈优化，就会把「warp 数不足导致的延迟暴露」误判为「带宽不够」，从而给出错误的搜索方向。

二 · 考点拆解：题干中每个词对应哪一族公式

把题干的关键词逐个映射到公式族，是这一部分的核心工作。下面这张表给出映射关系，后续算例的解题路径完全依赖它。

题干措辞考点调用的公式族常见误判
「stall 占比最高的是 long_scoreboard」延迟暴露 vs 带宽饱和的区分占用-延迟匹配式、stall 分解式直接判定为 DRAM 带宽瓶颈
「occupancy 只有 N 个 warp/SM」可发射 warp 数是否足以覆盖延迟Little 定律变体、eligible warp 期望把 occupancy 当作吞吐的直接度量
「寄存器数 R、共享内存 S 字节」占用上界的资源约束寄存器/共享内存占用上界式忽略寄存器分配粒度
「实测达到 roofline 的 x%」SOL 归因与收益上界roofline 比值、Amdahl 上界把 roofline 当硬上限而非上界
「改这一处需要重新编译/重搜索」代价核算与搜索预算收益-代价比、编译时间与 token 预算只算收益不算代价

表中第一行与第二行是同一枚硬币的两面：long_scoreboard stall 高，既可能是「有足够 warp 但每条 warp 都在等长延迟内存返回」，也可能是「warp 太少，一条 warp 等待时没有别的 warp 可发射」。区分这两者的唯一手段是把占用数代入占用-延迟匹配式，看「理论可隐藏延迟」是否已经覆盖实测延迟。若已覆盖而 stall 仍高，则问题在依赖链本身（例如单 warp 内的串行 LDG→FFMA 链）；若未覆盖，则问题在占用。

第三行的资源约束常被低估。寄存器占用上界不是简单的「65536 / (R × 32)」，因为分配以固定粒度为步长，且架构对每线程寄存器数有上限；共享内存上界也不是「总量 / S」，因为存在每 block 的分配粒度与 carveout 配置。这两条约束共同决定 occupancy 的上界，而 occupancy 又是第二层公式的输入，所以读题时必须先把题干给的 R 与 S 换算成「warp/SM 上界」，再与题干声称的实测 occupancy 对照——若两者不符，说明题干还隐含了别的限制（例如 block 数上限或 barrier 同步），这本身就是考点。

第四行的 roofline 比值是决策层的入口。题干说「达到 roofline 的 x%」时，考的是你能否把 x% 拆成「延迟暴露损失」与「带宽/算力饱和损失」两部分，而不是笼统地说「还有优化空间」。拆解的依据正是第二层的 stall 分解：可隐藏但未隐藏的延迟对应前者，已饱和的资源对应后者。只有前者能通过增加并行度或缩短依赖链回收，后者只能通过减少访存量或换算法回收——这两类改动的代价完全不同，直接决定搜索预算的分配。

三 · 解题路径：从 SASS 行到判断句的六步

给出可复用的解题路径，比给出某道题的答案更有价值。下面六步是这类题目的标准骨架，每一步都标注了它调用的公式与它产出的中间量。

  • 第一步，标注长延迟指令与依赖边。把 SASS 中每条 LDG/LDS/HMMA/MUFU/BAR 标出，并记录其目的寄存器被后续哪条指令首次读取——这个距离就是依赖距离 d。产出的中间量是「每条长延迟指令的暴露窗口」。代价提示：手工标注一段 200 行的 SASS 需要可观的注意力，工程上通常用脚本抽取，但脚本抽取的依赖边会漏掉跨基本块的寄存器复用，需要人工复核。
  • 第二步，算占用上界。由题干给的每线程寄存器数 R 与每 block 共享内存 S，结合架构的分配粒度，算出 warp/SM 上界 W。这一步调用占用上界式，产出 W。若题干另给了实测 occupancy，则取二者较小者作为后续输入。
  • 第三步，算理论可隐藏延迟。把 W 与每 warp 的平均指令发射间隔相乘，得到「在一条 warp 等待期间，其他 warp 能发射多少条指令」的期望值，再与长延迟指令的延迟周期数比较。这一步调用占用-延迟匹配式，产出「延迟是否已被覆盖」的布尔判断。
  • 第四步，做 stall 分解。把实测 stall 周期按「可隐藏未隐藏」「资源饱和」「同步与屏障」「控制流」四类归并，得到各类占比。这一步调用 stall 分解式，产出归因向量。
  • 第五步，算收益上界。对归因向量中「可隐藏未隐藏」那一项，用 Amdahl 型上界算出「若完全消除该类 stall，总时延最多下降多少」。这一步产出收益上界百分比，是决策层的第一输入。
  • 第六步，核算代价并给判断。把改动所需的编译时间、寄存器压力变化、正确性验证成本、以及在自动搜索中占用的 token/采样预算，与第五步的收益上界比较。这一步调用收益-代价比，产出「改 / 不改 / 先做更便宜的改动」的判断句。

六步中最容易出错的是第三步与第四步的衔接。第三步给出的是「理论上应该被隐藏」的延迟量，第四步给出的是「实测未被隐藏」的量；两者之差才是真正可回收的部分。若直接把第四步的 long_scoreboard 占比当作可回收量，就会高估收益——因为其中一部分延迟本来就被其他 warp 覆盖了，只是 NCU 的 stall 采样把它记在了某条 warp 头上。这个差值的计算需要把第三步的期望值与第四步的实测值放在同一时间基准上，否则量纲不一致。

四 · 需要调用的公式：逐项写出并标注每个符号的来源

本类题目需要调用四组公式。下面逐项写出，并标注每个符号在题干中的对应位置——这是「读题」与「套公式」之间的桥。

$$W_{\max} = \min\left(\left\lfloor \frac{R_{\text{file}}}{R \cdot 32 \cdot g_r}\right\rfloor \cdot g_r,\ \left\lfloor \frac{S_{\text{sm}}}{S \cdot g_s}\right\rfloor \cdot g_s,\ W_{\text{arch}}\right)$$

其中 R_file 是每 SM 寄存器文件容量，R 是题干给出的每线程寄存器数，g_r 是寄存器分配粒度（以 warp 为单位），S_sm 是每 SM 可用共享内存，S 是每 block 共享内存，g_s 是共享内存分配粒度，W_arch 是架构允许的每 SM 最大 warp 数。这个式子的考点在于两个「向下取整再乘粒度」的结构：很多人会写成连续除法，从而高估占用。代价面：W 每提高一档，寄存器压力就下降一档，但可能引入 spill，spill 的 LDG/STL 又会反过来增加 long_scoreboard——这是一个必须在本步就预见到的反馈环。

$$T_{\text{hide}} \approx W \cdot \bar{I}_{\text{issue}} \cdot \bar{L}_{\text{lat}}$$

这是占用-延迟匹配式的工程化写法：W 是第三步算出的 warp 数，I_issue 是每 warp 在无 stall 时的平均发射间隔（由指令混合决定），L_lat 是长延迟指令的平均延迟。乘积的物理含义是「一条 warp 等待期间，整个 SM 能发射的指令槽位数」。判断条件是：若 T_hide 大于等于暴露窗口，则延迟已被覆盖。这个式子是近似的，因为它假设各 warp 的 stall 不相关；在存在 barrier 同步的 kernel 里，warp 会同时进入等待，T_hide 会被高估——这正是第四步要把「同步与屏障」单列一类的理由。

$$f_{\text{stall}} = \frac{C_{\text{stall}}}{C_{\text{total}}},\quad C_{\text{stall}} = C_{\text{mem}} + C_{\text{dep}} + C_{\text{sync}} + C_{\text{ctrl}}$$

stall 分解式把总 stall 周期拆成内存、依赖、同步、控制流四类。题干给的 NCU stall 采样通常已经按硬件计数器分好类，考的是你能否把硬件分类映射到这四类，并识别出「同一物理原因被记在两个计数器上」的重叠。代价面：NCU 采样本身有开销，逐 warp 采样会显著拉长 kernel 时延，因此题干给的往往是采样后的比例而非绝对周期数；把比例换算成绝对周期需要总周期数，这个数题干通常不给，需要用「实测时延 × 时钟频率」自行推算，这一步的误差会直接传播到第五步的收益上界。

$$G_{\text{upper}} = f_{\text{recoverable}} \cdot \left(1 - \frac{T_{\text{ideal}}}{T_{\text{measured}}}\right)$$

收益上界式：f_recoverable 是第四步归因向量中「可隐藏未隐藏」那一项占总 stall 的比例，括号内是实测时延与理想时延的差距。这个式子的考点是它给出的是上界而非预测值——它假设该类 stall 能被完全消除，而实际改动只能部分消除。因此决策层必须把 G_upper 乘以一个实现折损系数再与代价比较。折损系数的取值依赖具体改动：增加 warp 数通常折损较大（受资源上界限制），缩短依赖距离折损较小（改动局部）。

四组公式的调用顺序与第三节的六步一一对应：第一、二步用占用上界式，第三步用占用-延迟匹配式，第四步用 stall 分解式，第五、六步用收益上界式。读题时若题干缺少某个符号（例如没给共享内存大小），则说明该约束不是本题考点，应在解题路径中显式标注「该上界不活跃」，而不是自行假设一个数值。

五 · 算例的题面结构：给定什么、要求什么、陷阱在哪

本类题目的算例通常这样构造：给一段含 3 到 5 条长延迟指令的 SASS 片段，给每线程寄存器数与每 block 共享内存大小，给实测 occupancy 与 NCU stall 分布，给一个 roofline 达成比例，最后问「瓶颈归因 + 一个改动建议 + 是否上线」。题面不给你总周期数、不给时钟频率、不给具体架构代号——这些缺失本身就是考点：你需要判断哪些量可以从给定量推出，哪些量缺失会导致结论只能定性。

陷阱有三处。第一处是 occupancy 与 W_max 不一致：题干给的实测 occupancy 往往低于资源上界算出的 W_max，此时若直接把 W_max 代入第三步，就会高估可隐藏延迟，从而低估 long_scoreboard 的可回收比例。正确做法是以实测 occupancy 为准，并把「为什么低于上界」作为一个待解释项——它可能来自 block 数不足（grid 太小）、来自 barrier 同步、或来自题干未给的 carveout 配置。第二处是 stall 分布中 long_scoreboard 与 short_scoreboard 并存：前者对应全局内存，后者对应共享内存与常量内存，两者的可回收手段不同（前者靠提高占用或预取，后者靠消除 bank conflict 或改用寄存器），若合并成一类就会给出错误的改动建议。第三处是 roofline 达成比例的分母：题干说的「达到 roofline 的 x%」可能以 DRAM 带宽为 roofline，也可能以算力为 roofline，两者对应的饱和资源不同，收益上界式的括号项含义也不同。

算例的「要求」部分通常包含一个隐含约束：改动建议必须是单点改动，即只改一处（例如只调 tile 大小、只改寄存器分配策略、只加 prefetch），而不是重写 kernel。这个约束把决策层的搜索空间限制在一维，使得收益-代价比可以逐点计算。工程含义是：这类题目模拟的是自动搜索中的「局部邻域评估」，而不是全局重设计。代价面：单点改动意味着搜索预算只需覆盖一个维度的若干取值，token 消耗与编译次数都可控；若题目允许组合改动，则搜索空间呈组合爆炸，收益上界的可加性假设也不再成立。

具体到一个典型算例的题面：SASS 片段含两条 LDG 与一条 HMMA，寄存器数 R 较大导致 W_max 偏低，实测 occupancy 等于 W_max，NCU 显示 long_scoreboard 占比最高，roofline 达成比例为中等水平。这个题面的解题路径是：先由 R 算出 W_max 并确认 occupancy 已顶到上界（说明不能靠加 warp 回收），再由依赖距离判断两条 LDG 是否串行（若是，则缩短依赖距离是唯一可回收手段），最后由收益上界式算出该手段的上界，并与「改 tile 大小导致重编译」的代价比较。陷阱在于：题干可能故意让 HMMA 的延迟与 LDG 的延迟相近，诱使你把 long_scoreboard 归因于 HMMA 而非 LDG——区分依据是 stall 计数器的名字与指令类型，而不是延迟长短。

六 · 公式与题面的对齐检查：读题时先做量纲与活跃性核对

在动笔套公式之前，有一道必须做的核对：把题干给出的每个量与公式中的每个符号对齐，标出「已给」「可推」「缺失」三种状态，并对缺失量判断其对应约束是否活跃。这道核对决定了后续解题路径是定量还是定性。

量纲核对的重点是周期与时间的混用。占用-延迟匹配式里的 L_lat 是周期数，而题干给的实测时延通常是毫秒或微秒；把两者直接相乘会得到无意义的数。正确做法是先把实测时延换算成周期（需要时钟频率，题干常不给，此时只能定性），或把 L_lat 换算成时间（需要同一频率）。工程上更稳妥的做法是全程用周期作为统一量纲，因为 stall 分解式与收益上界式都以周期为基准，只有 roofline 比值涉及时间。代价面：换算引入的频率误差会以线性方式传播到收益上界，若频率误差为若干个百分点，收益上界的绝对误差同量级——这也是为什么决策层要求把收益上界与代价比较时留出余量，而不是卡在临界点上做判断。

活跃性核对的重点是资源约束是否真的绑定。若寄存器上界算出的 W_max 远大于实测 occupancy，则寄存器约束不活跃，第三步应改用实测 occupancy；若共享内存上界算出的 W_max 恰好等于实测 occupancy，则共享内存约束活跃，任何增加 S 的改动都会直接压低 occupancy，收益上界式中的可回收项要相应打折。这个核对还能揭示题干的一个常见设计：给出一个看似宽裕的 S，但实际上 block 数上限才是绑定约束——此时占用上界式中的第三项 W_arch 或 block 数上限才是有效项，前两项只是陪衬。

最后一道核对是 stall 分类与改动手段的对应关系。long_scoreboard 对应「提高占用或预取」，short_scoreboard 对应「消除 bank conflict 或提升复用」，dep 类对应「缩短依赖距离或重排指令」，sync 类对应「减少 barrier 或改流水线」，ctrl 类对应「减少分支或展开」。读题时若题干的 stall 分布跨越三类以上，则单点改动只能回收其中一类，收益上界式必须按类分别计算再取最大者，而不是把各类占比相加。这一步的工程判断是：当最大一类占比不足总 stall 的多数时，单点改动的收益上界有限，此时更合理的判断是「先不改，把预算投向能同时影响多类的结构性改动」——这正是搜索预算分配在题面上的落点。

把上述核对做完，题面就从一段 SASS 与几个数字变成了一个带约束的优化问题：目标函数是收益上界式，约束是资源上界与单点改动限制，代价是编译时间与搜索预算。后续的逐项代入与数值计算，建立在这个已经对齐好的符号表之上。
