一 · 题干的三层结构：算法、奖励塑形、按流动拆步

这道题的问法本身就是一个陷阱。它问的不是「抗噪鲁棒奖励塑形是什么」，也不是「kernel 生成流程有哪几步」，而是把两件事叠在一起：一个算法概念（抗噪鲁棒奖励塑形）必须被按一次 kernel 生成/优化/验证的流动切开。也就是说，答题者要做的第一件事不是解释算法，而是识别出题干里存在三个可分离的层次，并判断哪一层是主语、哪一层是修饰、哪一层是切分维度。

第一层是「算法」——抗噪鲁棒奖励塑形。它是一个训练侧的奖励设计方法，作用对象是 RL 的 reward signal，而不是 GPU 上的某个算子。第二层是「按一次 kernel 生成/优化/验证的流动」——这是一个执行侧的时间轴，描述的是 agent 从拿到一个 kernel 任务到产出可部署实现所经历的阶段序列。第三层是「拆成哪几步」——这是切分动作，要求把前两层对齐：算法在流动的每个阶段分别以什么形态出现、消耗什么、产出什么。

考点的核心在于：算法不是流动的一个步骤，而是贯穿流动的一条约束。抗噪鲁棒奖励塑形不会单独占据「第三步」，它在读题阶段决定任务如何被形式化，在生成阶段决定候选如何被筛选，在验证阶段决定正确性 oracle 的容差如何设定，在优化阶段决定 reward 的噪声模型如何进入多轮迭代。把算法当成一个孤立步骤来答，是把约束误当成节点，这是本题最主要的失分模式。

解题路径因此是：先拆题干得到「算法约束 × 流动阶段」的二维表，再对每个格子问三个问题——输入是什么、输出是什么、代价落在哪个资源上（时延、带宽、显存、编译时间、token）。公式不是装饰，而是用来把「代价」从定性说法变成可比较的量。下面几节分别处理拆题干、识别考点、给出路径、以及路径上必须调用的公式。

二 · 拆题干：把「抗噪鲁棒」拆成可操作的约束项

「抗噪鲁棒奖励塑形」这个短语里，真正能落到 kernel 流动上的信息只有三个词根：「奖励」「塑形」「抗噪鲁棒」。逐个拆开看它们各自约束什么。

「奖励」约束的是流动的评价函数。在 kernel 生成场景里，reward 不是标量准确率，而是由多个可验证信号合成的：编译是否通过、正确性 oracle 是否通过、NCU/SASS profile 得到的带宽或时延是否达标、以及相对 roofline/SOL 的差距。奖励的存在意味着流动的每一步都必须产出可被 reward 消费的信号，而不是只产出代码文本。一个只输出 CUDA C++ 源码、不附带编译日志和 profile 的步骤，在奖励视角下是半成品。

「塑形」约束的是流动的信号密度。塑形（shaping）的本质是把稀疏的终局奖励拆成中间奖励，让多轮迭代有梯度可循。对应到 kernel 流动上，就是每个阶段都要有局部可判定的进展指标：读题阶段的形式化是否完整、生成阶段的候选是否可编译、验证阶段的 oracle 覆盖是否充分、优化阶段的 profile 是否相对上一轮有改善。塑形不是把终局奖励改小，而是增加中间节点，这直接决定了流动必须被切成多于两段。

「抗噪鲁棒」约束的是流动的信号可信度。噪声来源在 kernel 场景里是具体的：编译时间的抖动、GPU 频率与占用导致的时延方差、NCU 采样本身的统计误差、以及正确性 oracle 在浮点容差边界上的误判。抗噪意味着 reward 不能直接取单次测量值，而要对同一候选做重复测量并做聚合，或者对测量值设置信区间。鲁棒意味着当某个信号缺失（例如 profile 失败）时，reward 不能崩掉，而要有降级路径。

把三个词根合起来，题干要求的其实是一张约束映射表：算法的每个性质对应流动中某一阶段的某一项检查。这张表就是解题路径的骨架。填表时要注意，抗噪鲁棒不是加在最后一步的过滤器，它必须出现在测量发生的地方——也就是验证与优化阶段，而不是生成阶段。生成阶段能做的是让候选易于被抗噪地测量，例如保证候选带有可复现的编译配置和固定的输入形状。

三 · 识别考点：四个容易被误答的边界

这道题的考点不在「知道流程」，而在「知道流程的边界在哪里」。以下四个边界是判分时区分深浅的分水岭。

边界一：算法侧与执行侧不可混算。抗噪鲁棒奖励塑形是训练侧方法，它改变的是 agent 在多轮 RL 中的更新信号；kernel 生成/优化/验证是执行侧流程，它改变的是单个任务的产物。两者通过 reward 接口耦合，但代价记账必须分开：算法侧的代价是 token 与训练轮次，执行侧的代价是编译时间、显存、时延与带宽。把「多轮 RL 的 token 消耗」记到「验证阶段」头上，是记账错误。

边界二：验证不等于优化。验证阶段的输出是判定（通过/不通过、误差界、profile 数值），优化阶段的输出是新候选。抗噪鲁棒在验证阶段表现为 oracle 的容差设计与重复测量，在优化阶段表现为「上一轮 profile 噪声是否足以支撑一次接受/拒绝决策」。两者共用测量数据，但决策对象不同。

边界三：正确性 oracle 与性能 profile 是两类信号，噪声性质不同。正确性 oracle 的噪声主要是浮点容差与边界用例覆盖，属于离散判定噪声；性能 profile 的噪声是测量方差，属于连续数值噪声。抗噪处理对前者是扩大容差或增加用例，对后者是重复采样取统计量。用同一套抗噪手段处理两类信号，是把两种噪声混为一谈。

边界四：拆步的粒度由「可独立判定」决定，不由「代码模块」决定。一个阶段能否成为独立一步，判据是它能否产出可被 reward 单独消费的信号。读题阶段产出形式化规格，生成阶段产出可编译候选，验证阶段产出判定与 profile，优化阶段产出改进候选。如果两个动作共享同一个不可分的测量，它们就不该被拆成两步——例如「编译」与「首次正确性检查」在多数流动里共享同一次构建，硬拆会引入重复编译的时延代价。

这四个边界共同指向一个答题判断：拆步的依据是信号的可判定性，而不是工程上的模块划分。凡是能被 reward 单独打分、且打分不依赖下游阶段的动作，才配得上一个独立步骤。

四 · 解题路径：从二维表到逐步的输入/输出/代价

路径的第一步是建表。行是流动阶段，列是算法的三个性质（奖励、塑形、抗噪鲁棒），格子里填「该阶段为满足该性质必须做的事」。这张表不要求填满——有些格子是空的，空格本身就是答案的一部分，说明该性质在该阶段不施加约束。

路径的第二步是对每个非空格问三件事：输入、输出、代价。输入必须是上游阶段已产出的、可被本阶段直接消费的东西；输出必须是下游阶段或 reward 能直接消费的东西；代价必须落到具体资源上。三者缺一，该步的拆法就不成立。

路径的第三步是检查耦合。相邻两步之间如果存在「本步输出必须等下游测量才能确定」的循环依赖，说明拆步位置错了，需要把两步合并或把测量前移。抗噪鲁棒奖励塑形最容易制造这种循环：优化阶段想用 profile 决定是否接受候选，但 profile 本身有噪声，于是需要验证阶段先给出置信区间——这就把验证的测量前移到了优化的决策之前。

以「读题」这一步为例走一遍。输入是自然语言的 kernel 任务描述与参考实现（若有）；输出是形式化规格，包括算子语义、输入形状与 dtype、容差要求、目标硬件与 roofline 参照；代价主要是 token（把描述解析成规格的推理开销）以及一次人工或自动的规格核对。抗噪鲁棒在这一步的约束是：规格里必须显式写出容差与测量重复次数，否则下游无法做抗噪判定。塑形在这一步的约束是：规格必须足够具体，使「形式化是否完整」本身成为一个可判定的中间奖励。

再以「验证」这一步为例。输入是候选 kernel 与形式化规格；输出是正确性判定、误差分布、以及 NCU/SASS profile 的统计量（均值与方差）；代价是编译时间、GPU 占用时长、显存峰值，以及为降噪而做的重复测量所放大的时延。抗噪鲁棒在这一步是主战场：正确性侧要给出容差边界上的用例，性能侧要给出重复采样的置信区间。塑形在这一步的约束是：判定必须分级（编译失败、数值不符、性能不达标），每一级都是独立可消费的信号。

路径的第四步是把逐步结果拼成流动，并标注每步的失败降级路径。抗噪鲁棒要求任何一步的信号缺失都不能让整条流动崩掉：profile 失败时应降级为「仅正确性判定」，编译超时应降级为「候选标记为不可用但保留诊断」。降级路径的存在与否，是判断答题者是否真的理解「鲁棒」而非只理解「抗噪」的标志。

五 · 必须调用的公式：把代价从定性变成可比

路径上至少要调用三类公式，分别对应测量噪声、性能上界与信号聚合。

第一类是测量均值的标准误，用来判断重复测量多少次才足以支撑一次接受/拒绝决策。设单次测量的标准差为 σ，重复 n 次取均值，则均值的标准误为：

$$\mathrm{SE}(\bar{x}) = \frac{\sigma}{\sqrt{n}}$$

这个公式的工程含义是：要把噪声压到原来的 1/k，需要 k² 倍的测量次数。在 kernel profile 场景里，σ 来自 GPU 频率抖动与 NCU 采样误差，n 的每一次增加都直接放大 GPU 占用时长——这就是抗噪鲁棒在验证阶段的时延代价。答题时若只写「多测几次」，而不写 n 与 σ 的关系，就没有把代价量化。

第二类是roofline 上界，用来给性能信号设一个与硬件无关的参照，使不同候选的 profile 可比。设算术强度为 I（FLOP/Byte），峰值算力为 P，峰值带宽为 B，则可达性能上界为：

$$P_{\text{roof}} = \min(P,\; I \cdot B)$$

这个公式在流动里的位置是「验证阶段的性能判定基准」：候选的实测性能与 P_roof 的比值就是 SOL 利用率，它比绝对时延更抗噪，因为绝对时延随 GPU 状态漂移，而比值在同一硬件状态下相对稳定。塑形在这里的作用是把「SOL 利用率是否提升」作为优化阶段的中间奖励，而不是等到终局才看绝对时延。

第三类是多信号聚合的加权形式，用来把编译、正确性、性能三类信号合成一个 reward。设三类信号分别为 c（编译通过）、v（正确性通过）、s（SOL 利用率），权重为 w，则：

$$R = w_c \cdot c + w_v \cdot v + w_s \cdot s$$

抗噪鲁棒对这个公式的约束是：c 与 v 是离散判定，噪声小但一旦误判代价高，因此权重应使「误判为通过」的惩罚显著大于「误判为不通过」；s 是连续量，噪声大，因此应使用上一节的 SE 来决定 s 是否参与本轮聚合。塑形对这个公式的约束是：三个分量必须分别可观测，否则无法做中间奖励——如果只输出 R 而不输出 c、v、s 的分量，多轮迭代就失去了梯度来源。

三类公式的分工是清楚的：SE 管「测多少次」，roofline 管「跟什么比」，加权聚合管「怎么合成」。答题路径上每到一个阶段，都要指明该阶段调用哪一个，以及调用它带来的具体代价——SE 带来时延，roofline 带来一次参照计算，加权聚合带来 token 与判定逻辑的复杂度。

六 · 读题阶段的工程判断：规格即契约

把上面几节收束到一个具体机制上：读题阶段的输出不是一段描述，而是一份契约。这份契约规定了后续每个阶段能被 reward 消费的信号形态，也规定了抗噪鲁棒的落点。契约里必须出现的字段包括：算子语义的精确形式、输入形状与 dtype、正确性容差及其边界用例、目标硬件的 roofline 参照、profile 的重复次数与聚合方式、以及每一步的降级路径。

这份契约的代价是 token 与一次核对，但它换来的是下游阶段的可判定性：没有容差字段，验证阶段就无法区分「数值不符」与「浮点边界噪声」；没有重复次数字段，优化阶段就无法判断一次 profile 改善是否显著；没有降级路径字段，鲁棒性就无从谈起。反过来说，如果读题阶段把这些字段留空，后续阶段就会被迫在测量发生的地方临时补规格，而那时补规格的代价是重跑测量——这正是抗噪鲁棒奖励塑形在流动中最容易失控的地方。

工程判断因此是：拆步的正确性取决于读题阶段契约的完整度。契约完整，则「生成—验证—优化」三段边界清晰，每段的输入输出可独立判定，抗噪手段各归其位；契约残缺，则阶段之间出现循环依赖，拆步退化为「先跑一遍再说」，塑形失去中间节点，鲁棒退化为对单次测量的盲目信任。这也是为什么本题的第一问必须是「拆题干」而不是「列步骤」——步骤是契约的下游产物，契约不清，步骤怎么列都是错的。
