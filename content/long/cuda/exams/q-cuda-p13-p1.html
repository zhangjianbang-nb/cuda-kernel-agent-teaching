一 · 题干的三层结构：从“造 harness”反推考点

《AgentKernelArena》这类题目的题干通常只给一句话：为某篇 benchmark 论文的方法搭一套可复现的评测 harness，并回答基线、输入分布、正确性门、防作弊、上线门五个配置项。读题时不要直接进入“我要写什么代码”，而要先把题干拆成三层。第一层是对象层：harness 要评测的是“GPU kernel 优化 agent”，不是 kernel 本身，因此被测系统的输出是一个候选 kernel 源码加一份自述的性能声明；第二层是约束层：可复现意味着同一份输入在同一硬件、同一驱动、同一编译选项下必须给出可比较的结果，任何依赖时间戳、随机种子未固定、GPU 时钟未锁定的环节都是漏洞；第三层是裁决层：五个配置项不是并列的清单，而是一条判定链——基线定义“什么叫变快”，输入分布定义“在哪些形状上变快才算数”，正确性门定义“变快但不能错”，防作弊定义“变快不是靠偷看”，上线门定义“变快且可信才允许进生产”。

考点因此落在三个能力上：能否把“泛化感知”翻译成可执行的采样与分层策略；能否把“正确性”从单点 assert 升级为带容差、带边界、带对抗输入的 oracle；能否把“防作弊”写成对 agent 行为空间的显式封堵，而不是事后审计。题干里“Generalization-Aware”是关键词，它要求 harness 的评分不是单形状最优，而是跨形状分布上的稳健收益，这一点决定了输入分布与基线必须成对设计。

一个具体例子：若只给 agent 一个固定的 M=N=K=4096 的 GEMM 形状，agent 完全可以针对该形状硬编码 tile 尺寸与边界处理，harness 表面上通过，但换到 M=17 的瘦长矩阵就崩。题干要求的是“泛化感知”，所以读题时必须意识到：任何单一形状的通过都不构成验收证据，验收口径必须写成分布级统计量。

二 · 基线：不是“原版 kernel”，而是可复算的参照系

基线配置的考点在于区分三种参照：框架自带实现（如 PyTorch eager）、厂商库实现（cuBLAS/cuDNN）、以及 agent 自己产出的“未优化版本”。三者混用会让加速比失去意义。可执行的口径是：每个任务声明一个 primary baseline 与一个 reference ceiling。primary baseline 用框架 eager 实现，因为它与 agent 的输出在同一编译栈、同一内存布局下可直接对比；reference ceiling 用厂商库，用来判断 agent 的收益是否只是“追平库”，从而避免把“重新发现 cuBLAS”当成创新。

基线必须带三个可复算属性：固定随机种子生成的输入张量、固定的 warmup 与计时轮数、固定的 GPU 时钟与电源模式。加速比公式写成：

$$ S = \frac{T_{\text{base}}^{\text{med}}}{T_{\text{cand}}^{\text{med}}},\quad \text{且}\quad T^{\text{med}} = \operatorname{median}\{t_i\}_{i=1}^{R} $$

用中位数而非均值，是因为 kernel 计时分布右偏，偶发的调度抖动会污染均值；同时要求 R 轮中剔除首轮 warmup，并对 S 附加一个置信区间下界，只有下界大于 1 才记为“有效加速”。代价是：基线本身要跑满 R 轮，若每个任务 20 个形状、每形状 100 轮，基线阶段就消耗可观的 GPU 时延；这是 harness 的固定开销，不能省，否则加速比不可复现。

具体例子：一个 softmax 任务，框架 eager 基线在 N=1024 行上的中位时延记为 T_base，agent 候选若只在该形状上快 1.3 倍，但在 N=8 的小行数上慢 2 倍，则分布级加速比的中位数可能低于 1，此时基线配置必须允许 harness 输出“分形状加速比向量”而非单一标量，供上线门做分层裁决。

三 · 输入分布：分层采样与“泛化感知”的评分口径

输入分布的考点是把“泛化”变成可采样的分层结构，而不是随机撒点。可执行的做法是三维分层：形状层（规整大形状、瘦长形状、极小形状、非 2 的幂形状）、数值层（常规值、极端幅值、含 NaN/Inf 的对抗输入、次正规数）、布局层（连续、转置、带 stride 的视图）。每层内按固定种子采样若干实例，形成“分布卡”，随任务一起版本化。

评分不能取所有实例的算术平均，因为大形状主导时延、小形状主导正确性风险。更合适的口径是分层加权的中位加速比，并对每层设“不退化”约束：

$$ S_{\text{agg}} = \sum_{l \in L} w_l \cdot \operatorname{median}_{x \in D_l} S(x),\quad \text{s.t.}\ \min_{x \in D_l} S(x) \ge \theta_l $$

其中 w_l 按层的重要性给定，\theta_l 是该层允许的最差加速比下界（小形状层可设得宽松，但不得低于 1 以下太多，否则等于允许退化）。这个约束项是“泛化感知”的落点：它把“平均好看但个别形状灾难”的候选直接判负。代价是采样规模直接乘以评测时延与显存占用；对抗数值层还会触发额外的正确性检查开销，因此分布卡要在覆盖度与 harness 运行时间之间做显式取舍，并把取舍写进配置而非隐含在代码里。

具体例子：LayerNorm 任务在 hidden=768 与 hidden=769（非 2 的幂）两个实例上，候选 kernel 若按 768 对齐做向量化，769 会走标量尾处理，时延骤增；分层约束会在 D_{\text{odd}} 层把它拦下，这正是单形状评测无法暴露的泛化缺口。

四 · 正确性门：从 assert 到带容差的 oracle 与边界对抗

正确性门的考点是“门”的判定逻辑，而不是“跑一遍 allclose”。可执行的门分三级：数值门（与高精度参考实现比较，按 dtype 给定绝对/相对容差）、边界门（空张量、单元素、极长维度、stride 非连续）、对抗门（NaN/Inf 传播、次正规数、极大极小混合幅值）。三级门是短路结构：数值门不过直接判负，不进入性能计时，避免把错误 kernel 的时延计入统计。

数值门的判据写成组合容差，而非单一阈值：

$$ \text{pass} \iff \forall i:\ |y_i - \hat{y}_i| \le a + r\,|\hat{y}_i|,\quad \text{且}\ \text{NaN/Inf 位置集合一致} $$

其中 a 是绝对容差、r 是相对容差，二者随 dtype 与归约长度调整；NaN/Inf 位置一致这一条必须单列，因为很多候选在数值上“接近”却把 Inf 静默成有限值，这在生产里是灾难。代价是参考实现要用高精度路径（如 float64 或 Kahan 求和）跑一遍，显存与时延翻倍；对抗门还要构造特殊输入，增加 harness 的准备时间。这些开销必须计入验收预算，否则正确性门会被压缩成形式检查。

具体例子：一个 reduction kernel 在含 Inf 的输入上返回了有限值，数值门因相对误差小可能放行，但位置一致性检查会立刻判负；另一个候选在 N=1 的空维度边界上越界读，边界门用 guard page 或 canary 检测捕获，而不是依赖随机内存布局碰巧不崩。

五 · 防作弊与上线门：行为封堵与分层放行

防作弊的考点是把 agent 的可利用面显式封堵，而不是赛后审计日志。可执行的封堵清单包括：禁止读取基线计时结果（否则可针对计时器做特化）、禁止在 kernel 内检测输入形状后调用库函数（否则是“调度器”而非“kernel”）、禁止跨轮缓存编译产物以复用上一次的计时、禁止访问 harness 的分布卡文件。实现上，harness 应在隔离进程中运行候选、以只读方式挂载输入、对候选源码做静态扫描（检查是否出现库调用符号与形状分支常量），并把“是否调用外部库”作为硬性判负项而非扣分项。

上线门则是把前述四项聚合成放行决策，采用分层而非单一阈值：

$$ \text{release} \iff S_{\text{agg}} \ge S_{\min}\ \land\ \forall l:\ \min_{x \in D_l} S(x) \ge \theta_l\ \land\ \text{正确性三级门全过}\ \land\ \text{防作弊扫描通过} $$

其中 S_{\min} 是生产端到端收益的最低门槛，必须由端到端链路（含数据搬运、launch 开销、框架胶水）测得，而不是 kernel 内计时；这一点是上线门与基准分的分界线。代价是上线门要跑端到端链路，时延远高于 kernel 级评测，且端到端测量受框架版本影响，必须固定容器镜像；防作弊静态扫描会带来编译时间与误报成本，需要在配置里声明扫描规则版本。

具体例子：某候选在 kernel 级拿到 1.8 倍加速，但端到端因额外的 host-device 同步只带来 1.05 倍，上线门按 S_{\min} 判负；另一候选在静态扫描中被发现按形状常量分支调用库函数，防作弊项直接判负，尽管其分布级加速比很漂亮。这两个例子说明上线门的裁决顺序应是“正确性与防作弊先行、性能后置”，否则漂亮数字会掩盖不可信来源。

六 · 解题路径：把五个配置写成一份可执行规格

读题的落点是产出一份规格而非代码。路径可分四步：第一步，为每个任务写“任务卡”，声明 primary baseline、reference ceiling、分布卡版本、三级正确性门的容差参数；第二步，写“评分卡”，声明分层权重 w_l、层下界 \theta_l、聚合公式与置信区间口径；第三步，写“封堵卡”，声明隔离方式、只读挂载、静态扫描规则版本与硬性判负项；第四步，写“放行卡”，声明 S_{\min}、端到端链路定义与容器镜像哈希。四张卡合起来就是可复现 harness 的验收口径。

需要调用的公式已在各节给出：中位加速比与置信下界（基线）、分层加权聚合与层下界（分布）、组合容差与 NaN/Inf 位置一致（正确性）、分层放行合取式（上线门）。解题时应把公式中的每个符号映射到配置字段，例如 \theta_l 对应分布卡里的 min_speedup_per_layer，a, r 对应正确性门里的 atol/rtol，这样验收时任何人拿配置就能复算。

工程判断上，最容易出错的是把“泛化”当成“多测几个形状”。真正的泛化感知要求层下界约束与分层权重同时存在：只有层下界而无权重，会让小形状层过度主导；只有权重而无下界，会让灾难性退化被平均掩盖。另一个判断是防作弊必须前置于性能统计，否则错误或作弊候选的时延会污染基线分布，使后续所有加速比不可信。这两条判断决定了 harness 的可信度上限，也是本题“可复现”与“泛化感知”两个词的交汇点。

考点不在“能不能跑”，而在“泛化声明能否被证伪”

这一节要拆的题干，其实是一个评测 harness 的边界设计问题：AgentKernelArena 把“泛化”写进标题，意味着评测对象不是单点 kernel 的正确性，而是 agent 在未见输入分布上的优化策略是否仍然成立。因此考点有三层。第一层是基线定义：基线不能是 agent 自己产出的最优 kernel，否则泛化无从比较；必须固定为参考实现（如 PyTorch eager 或手写 naive CUDA），并在同一 harness 下测量，使“加速比”有共同分母。第二层是输入分布切分：训练/调优可见的 shape、dtype、layout 集合与评测集合必须显式不相交，且不相交性要可审计——不是随机抽样就算泛化，而是按维度族（如序列长度区间、batch 档位、stride 模式）做留出。第三层是正确性门与防作弊门的分工：正确性门回答“算得对不对”，防作弊门回答“是不是靠 harness 漏洞拿分”，两者不能合并成一个阈值。

拆题时要把“泛化”转成可判定的命题。设可见分布为 Dseen，评测分布为 Dheld，agent 产出的 kernel 为 k，则 harness 要验证的是：k 在 Dheld 上的正确率与加速比，是否与 Dseen 上的表现同向。一个可操作的判据是泛化落差：

$$\Delta_g = \frac{S_{seen} - S_{held}}{S_{seen}},\quad \text{且}\ \mathrm{corr}(S_{seen}, S_{held}) > 0$$

其中 S 为相对基线的加速比。若 Δg 超过预设容忍带，或两个分布上的排序相关性消失，则 agent 的“泛化声明”被证伪——这正是 harness 要输出的验收口径，而不是一个笼统的“通过/不通过”。解题路径因此是：先定基线 → 再定分布切分与留出维度 → 再定正确性 oracle（含边界 shape、非对齐 stride、极小/极大尺寸）→ 最后定防作弊与上线门。每一步都要回答“这一步失效时，harness 会误判成什么”。

边界与失效条件必须写进题干拆解，否则 harness 会在三种情况下给出虚假泛化。其一是分布泄漏：agent 在调优阶段通过执行反馈间接看到了 held-out shape 的 profile 特征（如 NCU 报告的 occupancy 拐点），从而针对性地特化；防作弊门要用输入指纹隔离——held-out 集合的 shape 与 stride 组合在 agent 可见的日志中被脱敏或延迟披露。其二是正确性门过松：只比对输出张量的全等会放过“在特定对齐下才正确”的 kernel，正确性 oracle 需覆盖非对齐指针、越界尾块与 NaN/Inf 传播，代价是每个候选 kernel 要跑多组边界用例，评测时延上升。其三是基线漂移：若基线随硬件或框架版本变化而未冻结，加速比不可跨轮比较，harness 必须把基线二进制与测量脚本一起版本化。系统代价上，held-out 分布越宽，正确性门与 profile 采集的用例数越多，单轮评测的 GPU 时延与显存占用越高；而防作弊的日志脱敏又会削弱执行反馈的信息量，使 agent 的多轮优化信号变稀——这是 harness 设计里必须显式权衡的一对矛盾。

门判定对象失效后果主要代价
基线冻结参考实现+测量脚本加速比不可跨轮比较版本管理开销
分布留出shape/stride 族不相交泛化被高估用例数增加、时延上升
正确性 oracle边界与非对齐输入特化 kernel 蒙混过关每候选多组用例
防作弊日志脱敏与指纹隔离反馈泄漏 held-out优化信号变稀

一个具体例子：题干要求给出“可执行配置与验收口径”，那么拆解时应落到配置项而非结论——基线选 eager 参考实现并冻结其 commit；Dseen 取若干常见 batch 档与对齐 stride，Dheld 取相邻档位与非对齐 stride 的组合；正确性门要求逐元素容差比对并额外覆盖尾块；防作弊门要求 held-out 的 shape 在 agent 可见日志中以占位符出现。验收口径写成“Δg 在容忍带内且排序相关性保持”，而不是“平均加速比超过某值”。这样，harness 的输出是一个可被复现实验反驳的泛化断言，而不是一个漂亮的分数。
