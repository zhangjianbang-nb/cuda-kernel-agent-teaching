一 · 把题干拆成「一次 kernel 生命周期」的五个交接面

「多 agent 策略 IR 协同」这个题干里藏着三个容易被读漏的限定词：多 agent（不是单模型多轮，而是有角色分工、有共享产物的并发实体）、策略 IR（agent 之间传递的不是自然语言建议，而是可被下游消费的中间表示）、按一次 kernel（协同的粒度是单个 kernel 的生成—优化—验证闭环，而不是整个模型或整个仓库）。读题第一步是把这三者对齐到一条流水线上，并明确每个交接面上「谁写、谁读、写什么格式、失败时谁负责」。

按一次 kernel 的生命周期，交接面可以拆成五段：规格化（把算子语义、形状约束、dtype、容差、目标硬件压成一份可判定的任务描述）、策略选择（决定用 CUDA C++、Triton、CuTe 还是手写 PTX，以及分块/流水/归约的基本骨架）、实现生成（产出可编译源码与其调度参数）、执行反馈（编译日志、运行时错误、NCU/SASS profile、roofline 位置）、验证裁决（正确性 oracle 与性能门槛共同决定接受、回退还是重写）。五个交接面的输入输出必须显式成文，否则多 agent 之间会退化成「互相复述自然语言」——这正是协同失败的主要形态。

考点的第一层就在这里：题干问的是「流动拆成哪几步」，实质是问状态在哪里落地。若策略 IR 只存在于某个 agent 的上下文窗口里，那么并行的另一个 agent 无法读到它，回退时也无法复现上一版决策。因此每一步的产物必须是可序列化、可 diff、可被下游程序解析的对象，而不是散文。

代价在这一层已经出现：规格化越严格，任务描述 token 越长，且容差与形状约束的枚举会随维度组合膨胀；反之规格化过松，则验证阶段要反复澄清，把时延从「一次生成」推高到「多轮往返」。工程判断是：把形状与 dtype 压成参数化模板（而非逐例枚举），把容差写成相对误差加绝对下限的两段式，用固定字段承载，避免自然语言描述。

二 · 策略 IR 的最小字段集与「可判定性」考点

策略 IR 不是代码，也不是注释，它是决策的可执行摘要。最小字段集应覆盖：算子族与语义不变量（如归约的结合律假设、是否允许重排）、问题形状的参数化表达、dtype 与累加精度、目标架构的约束（共享内存上限、warp 数、是否允许 TMA）、所选后端与骨架（分块尺寸、线程映射、流水级数）、以及该决策的依据引用（指向哪一次 profile 或哪一条 roofline 结论）。最后一项是考点：没有依据引用的策略 IR 无法在回退时被审计，多 agent 会陷入「谁都说自己对」的僵局。

可判定性体现在两个方向。向上，规格化 agent 必须能仅凭 IR 判断「这个策略是否满足语义不变量」；向下，生成 agent 必须能仅凭 IR 还原出源码骨架而不需要额外追问。若做不到，说明 IR 字段缺失或语义含糊，这本身就是一道考点题：给出一个 IR，问它是否足以驱动生成。

$$\text{IR}_{\text{ok}} = \big[\text{Sem}(k) \land \text{Shape}(k) \land \text{Dtype}(k) \land \text{Arch}(k) \land \text{Skeleton}(k) \land \text{Evidence}(k)\big]$$

其中每一项都是可机械检查的谓词，而非「描述得清楚」这种主观判断。工程上把它实现为一组 schema 校验加语义断言，任一失败即拒绝进入生成阶段。

代价：字段越多，序列化与校验的编译期开销越大，且 agent 之间传递 IR 的 token 成本随字段线性增长；字段越少，生成阶段的试错轮次上升，每次试错都要付一次编译加一次运行的时延。典型例子是归约类 kernel：若 IR 未声明「是否允许非确定性累加顺序」，生成 agent 可能选择原子加，验证 agent 又用逐位比对做 oracle，两者冲突导致无谓回退——补一个布尔字段即可消除整轮往返。

三 · 协同拓扑：谁在什么时机读同一份 IR

多 agent 的协同不是「开会」，而是对同一份 IR 的并发读写与版本裁决。常见拓扑有三种：串行接力（规格→策略→生成→验证，单写者）、并行候选（多个生成 agent 基于同一策略 IR 产出不同实现，由裁决 agent 择优）、以及回退环（验证失败后把 profile 与错误注入策略 IR 的新版本，触发重选）。考点在于识别题干描述的是哪一种，以及每种拓扑下 IR 的写权限归属。

并行候选拓扑的关键机制是「策略 IR 冻结 + 实现 IR 分叉」：策略层一旦冻结，多个生成 agent 不得修改骨架字段，只能在实现层引入差异（如不同的分块尺寸、不同的流水深度）。这样裁决才有可比性——否则各候选连语义假设都不同，profile 数字无法横向比较。回退环拓扑的关键机制是「差异最小化」：失败信息必须定位到具体字段（哪个骨架参数导致共享内存溢出、哪个 dtype 假设导致精度不达标），而不是整份 IR 重写。

  • 串行接力：写者唯一，IR 版本线性递增，代价低但吞吐受最慢环节限制。
  • 并行候选：读多写一，需冻结策略层；代价是候选数乘以单次编译运行时延，收益是命中更优实现的概率上升。
  • 回退环：写者交替，需版本号与差异记录；代价是每轮回退都付一次完整验证，若差异定位不准则轮次爆炸。

具体例子：一个 GEMM 类 kernel 在并行候选下，三个生成 agent 分别给出不同的 tile 形状，但若策略 IR 未冻结「累加精度必须为 fp32」，其中一个候选可能用 fp16 累加而跑出更漂亮的时延，裁决 agent 若只看性能就会误接受——正确性 oracle 必须先于性能门槛执行，这是拓扑设计里的硬约束。

四 · 每一步的输入、输出与代价账本

把五段交接面写成表，是本部分要求的「解题路径」骨架。表中每一行的代价列必须落到具体资源：时延、带宽、显存、编译时间或 token，不能写「开销较大」。

读表时要抓两个考点。其一是反馈的粒度：编译日志是文本，NCU 指标是结构化数字，SASS 是汇编——三者进入策略 IR 时必须被压缩成可比较的量（如「共享内存占用超限」「达到带宽上限的百分比」「存在未合并访存」），否则回退环无法做差异定位。其二是验证的顺序：正确性 oracle 必须先跑，性能门槛后跑；若颠倒，则会用宝贵的 profile 时延去评估一个语义错误的实现。

$$T_{\text{cycle}} = T_{\text{spec}} + T_{\text{policy}} + T_{\text{gen}} + T_{\text{compile}} + T_{\text{run}} + T_{\text{prof}} + T_{\text{verify}}$$

回退时该式按轮次累加，因此「减少无效轮次」比「缩短单轮」更有效：一次差异定位准确的回退，胜过三次盲目重写。具体例子是共享内存溢出——若反馈只写「运行失败」，策略 agent 只能猜；若反馈写成「骨架参数 tile_k 使共享内存需求超过架构上限」，则下一轮只需调一个字段。

五 · 需要调用的公式：把「够不够快」变成可判定的不等式

解题路径里必须出现的公式有三类。第一类是roofline 判据，用来判断实现是受带宽还是受算力约束，从而决定优化方向是减少访存还是提高占用率：

$$P_{\max} = \min\left(\frac{\text{FLOPs}}{\text{Bytes}} \cdot B_{\text{mem}},\; F_{\text{peak}}\right)$$

其中算术强度由 kernel 的访存模式决定，Bmem 与 Fpeak 由目标架构给定。策略 IR 里的「依据引用」应指向该 kernel 在 roofline 图上的坐标，而不是一句「需要优化」。

第二类是正确性判据，把容差写成可判定的不等式，避免「看起来差不多」：

$$\big|y_{\text{impl}} - y_{\text{ref}}\big| \le \varepsilon_{\text{rel}}\cdot\big|y_{\text{ref}}\big| + \varepsilon_{\text{abs}}$$

逐元素成立，且需声明对 NaN/Inf 的处理与归约顺序的敏感性。第三类是资源约束判据，把骨架参数与架构上限对齐：

$$\text{SMem}(t) = t_m \cdot t_n \cdot t_k \cdot \text{sizeof}(\text{dtype}) \le \text{SMem}_{\max}$$

这三类公式分别对应策略选择、验证裁决、实现生成三个交接面，缺一则某一步无法机械化判定。代价在于：roofline 判据需要一次 profile 才能定位坐标，而 profile 采集本身要复跑 kernel 并占用显存；容差判据的逐元素比对要读回整块输出，带宽开销与输出规模成正比；资源约束判据是编译期可算的，几乎零运行时代价，因此应尽量前移到策略阶段做静态筛查。

具体例子：一个逐元素激活 kernel 的算术强度极低，roofline 判据直接判定其受带宽约束，于是策略 IR 应禁止生成 agent 引入复杂的流水骨架——那只会增加寄存器压力而不提升带宽利用率。若策略 agent 忽略该判据，生成 agent 可能产出过度工程化的实现，编译时间与寄存器溢出同时上升。

六 · 解题路径的写法：从题干到可执行检查单

落到答题层面，路径应是「先定交接面，再定 IR 字段，再定拓扑，最后定判据」四步，而不是直接描述某个 agent 该做什么。第一步从题干抽出「一次 kernel」的边界：哪些属于本次闭环（生成、优化、验证），哪些属于闭环之外（如端到端集成收益，那是另一条条目的主题，此处一句指路即可）。第二步列出策略 IR 的最小字段集并标注每个字段的可判定谓词。第三步判定协同拓扑与写权限，明确冻结层与分叉层。第四步把三类公式挂到对应交接面上，并写明每类判据所需的反馈数据从哪来。

检查单的价值在于暴露「缺项」：若题干未提容差，则验证裁决无法机械化，必须补；若题干未提目标架构，则资源约束判据失效，策略选择退化为猜测；若题干未提依据引用，则回退环无法差异定位。每一处缺项都对应一个具体的代价——补容差要付比对带宽，补架构约束要付一次静态筛查的编译期开销，补依据引用要付 profile 采集时延。

一个可操作的具体例子：给定「为某归约算子生成并验证一个 kernel」的题干，路径写法应是——规格化阶段把归约维度与是否允许重排写成布尔与整数参数；策略阶段依据 roofline 判据判定其受带宽约束并冻结「不使用原子加」的语义字段；生成阶段在冻结骨架下分叉出不同的线程映射；反馈阶段把 NCU 的访存效率与共享内存占用压成结构化字段；裁决阶段先跑容差不等式再跑性能门槛，失败则把差异定位回具体字段。整条路径不含任何「大概更快」的表述，每个决策都挂在一个可检查的谓词上。

最后落在工程判断上：多 agent 协同的瓶颈通常不在单个 agent 的生成质量，而在交接面的信息损失——自然语言摘要丢掉了可判定性，导致下游只能重试而不能定位。把策略 IR 做成带谓词与依据引用的结构化对象，把反馈压成可 diff 的字段，把判据写成不等式，这三件事决定了回退轮次是收敛还是发散。

读题即编译：把题干拆成可调度的 IR 契约

「多 agent 策略 IR 协同」的读题环节不是自然语言理解，而是把题干编译成一份可被各 agent 共享的中间表示：算子语义、形状/步长约束、精度契约、目标硬件与验收口径五类字段必须齐备，缺一项就意味着后续某个 agent 只能靠猜补齐，而猜出来的字段在验证阶段会以静默数值偏差的形式暴露。拆题的具体机制是「约束抽取 + 缺口标注」：从题干中抽出 dtype、layout、归约轴、边界条件，把未给出的部分显式标为待定槽位而非默认值，再由调度 agent 决定由谁填补。代价是 token：一份完整 IR 契约通常比原始题干长数倍，且每个下游 agent 都要重读，上下文预算随 agent 数线性增长，这是协同方案最先撞上的墙。

考点拆解要区分「可验证考点」与「不可验证考点」。前者如数值等价、越界访存、同步正确性，能落到正确性 oracle 上；后者如「是否最优」，只能靠 roofline 与 NCU 指标做区间判断。解题路径因此分叉：正确性路径先冻结语义再谈性能，性能路径先定 SOL 上界再谈实现。用公式表达这一分叉的判据：

$$\text{可接受}=\big[\text{err}\le \tau_{\text{num}}\big]\land\big[\text{lat}\le \alpha\cdot \text{SOL}^{-1}\big]$$

其中 τ 由精度契约给出，α 是工程容忍系数；两者任一未定，验证 agent 就无法给出二值结论，只能输出「不确定」，而「不确定」在多轮 RL 里等价于零奖励，直接浪费一次生成预算。

失效条件集中在三处：题干含隐式广播或非连续步长时，IR 契约的 layout 字段会与真实张量不符，导致生成的 kernel 在正确性 oracle 上通过却在端到端集成时崩溃；目标硬件未指明时，SOL 上界无从计算，性能考点退化为不可判定；验收口径写成「更快」而无基线时，多 agent 会各自朝不同方向优化，协同退化为互相覆盖。系统代价上，读题阶段本身不产生 GPU 时延，但它的错误会以编译时间和重试次数放大——一次 layout 误判通常要付出整轮重新生成加一次 NCU profile 的开销，且该开销随 agent 数量增加而重复支付。
