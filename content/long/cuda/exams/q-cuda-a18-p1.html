一 · 题干拆解：把「仅目标驱动基线生成」拆成可计算的四个量

「仅目标驱动基线生成」这个说法里藏着三个约束和一个动作，读题时必须逐字拆开。约束一「仅」：不提供参考实现、不提供历史 kernel 片段、不提供人工写的模板，agent 只拿到目标语义（算子定义、输入输出形状、dtype、边界条件）与验收口径。约束二「目标驱动」：搜索的停止条件由目标侧指标定义，而不是由与参考实现的相似度定义——正确性 oracle 与性能目标共同构成停止面。约束三「基线」：产出物是后续优化轮次的起点，不是最终交付物，因此它必须可编译、可运行、可被 profile，但不要求在首轮就逼近 SOL。动作是「生成」：一次从语义到 CUDA C++/Triton 源码的映射，其代价以 token 与编译时间计。

把这四个字面约束翻译成可计算的量，得到本条目要逐项解释的核心公式所需的四个自变量：候选数 $N$（一次搜索预算内实际编译并运行的 kernel 变体数）、单候选正确率 $p$（在无参考实现条件下，一个候选通过正确性 oracle 的概率）、单候选达标率 $q$（在通过正确性的候选中，性能达到目标阈值的条件概率）、单候选全链路成本 $c$（生成 token + 编译 + 运行 + profile 的时延折算）。这四个量不是题干给的，而是题干要求解题者自己估计的——这正是考点所在：题目考的不是「会不会写 kernel」，而是「能不能把一次无参考的生成式搜索折算成预算与上线判断」。

解题路径因此分三步，且顺序不可颠倒。第一步，从题干抽取验收口径，明确正确性 oracle 的严格度（是否逐元素、容差多少、是否覆盖边界形状），因为这直接决定 $p$；第二步，从目标侧抽取性能阈值与测量方法（用什么计时、是否含 launch 开销、是否要求 NCU 指标达标），这决定 $q$；第三步，把 $N$、$p$、$q$、$c$ 代入预算与收益公式，回答「给定预算下期望拿到几个可用基线」以及「首轮基线是否足以支撑上线判断」。三步中任何一步跳过去直接写代码，都会在后续多轮 RL 里以错误奖励信号的形式反噬。

二 · 考点定位：三个易错点与它们对应的公式入口

考点一：把「仅目标驱动」误读成「无约束生成」。实际上约束在验收侧而非生成侧——agent 可以自由选择分块策略、向量化宽度、共享内存布局，但每一个选择都要在 oracle 下被检验。这里的机制是正确性 oracle 的分层构造：第一层是形状/dtype 合法性检查（编译期与 launch 期即可判定，成本极低），第二层是小形状逐元素比对（用高精度 CPU 参考或解析解，成本中等），第三层是边界与极端值覆盖（NaN/Inf、非对齐长度、空张量，成本最高但最能暴露越界写）。三层串联后单候选正确率不是简单的 $p$，而是 $p = p_1 p_2 p_3$，其中 $p_1$ 接近 1，$p_2$ 与 $p_3$ 才是真正的方差来源。代价在于：第三层若对每个候选都跑，单候选成本 $c$ 会显著抬升，因为边界用例往往触发最慢路径与最多的同步点。

考点二：把性能目标当成单一标量。目标驱动意味着阈值可能是多维的——时延上限、带宽利用率下限、显存占用上限三者同时成立才算达标。于是 $q$ 不是「跑得快」的概率，而是「同时满足 $k$ 个约束」的概率。若各维近似独立，$q \approx \prod_{j=1}^{k} q_j$，维度越多，$q$ 衰减越快，这是搜索预算被吃掉的隐性原因。具体例子：一个 reduction kernel 的目标写成「时延不超过阈值、且不引入额外全局显存」，则一个用两趟全局内存交换掉寄存器的候选虽然快，却在显存维度被判不达标，$q$ 直接归零。

考点三：混淆「基线可用」与「可上线」。基线只要求通过 oracle 且进入性能候选池，上线判断还要求跨形状的稳定性与端到端收益。二者的判据不同，公式入口也不同：前者用 $N p q$ 的期望计数，后者要用收益的置信下界。解题时必须明确指出这两个判断发生在不同轮次，不能用一个公式回答两个问题。

三 · 核心公式逐项展开：期望可用基线数与预算闭合

本条目要求解释的核心公式是期望可用基线数：

$$E[\text{usable}] = N \cdot p \cdot q,\qquad B = N \cdot c,\qquad N^{*} = \left\lfloor \frac{B}{c} \right\rfloor$$

逐项解释。$N$ 是搜索预算内实际走完「生成—编译—运行—oracle」全链路的候选数，注意它不等于生成的候选数：编译失败的候选不进入 $N$ 的分子，却照样消耗 $c$ 中的生成与编译时间，因此工程上应把 $c$ 拆成 $c_{\text{gen}} + c_{\text{compile}} + c_{\text{run}} + c_{\text{prof}}$，并承认编译失败率会稀释有效 $N$。$p$ 是无参考条件下单候选通过分层 oracle 的概率，它的上界受限于 agent 对语义边界的推断能力，而不是编码能力——一个语法完美但把归约顺序搞反的候选，$p_2$ 直接为 0。$q$ 是条件达标率，其条件性必须被尊重：只有在 $p$ 成立的候选上统计 $q$ 才有意义，否则会把「快但错」的候选计入收益，这是多轮 RL 中最常见的奖励污染。

预算闭合式 $B = N c$ 的作用是把「搜索多久」翻译成「搜多少个」。给定 $B$ 与 $c$，$N^{*}$ 是硬上限；若 $E[\text{usable}] = N^{*} p q < 1$，说明在当前预算下连一个可用基线都拿不到，此时正确的工程动作不是加大 $N$，而是先降 $c$（例如把第三层 oracle 从每个候选都跑改为只对通过前两层的候选跑）或先升 $p$（例如在生成侧注入形状约束的静态检查）。这个判断顺序有代价含义：降 $c$ 牺牲的是错误检出的覆盖率，升 $p$ 牺牲的是候选多样性，两者都会改变后续优化轮次的起点分布。

算例。设某算子目标为逐元素复合运算，验收口径为三形状逐元素比对（容差给定）、性能阈值为时延上限且要求不额外分配全局显存。取 $N = 40$，$p = 0.35$（三层串联后，主要损失在边界形状），$q = 0.5$（一半候选因额外全局缓冲被判不达标）。则 $E[\text{usable}] = 40 \times 0.35 \times 0.5 = 7$。若单候选全链路成本折算为 $c$，则 $B = 40c$；若把预算翻倍到 $80c$，$E[\text{usable}]$ 线性升到 14，但这是线性外推，前提是 $p$、$q$ 不随 $N$ 增大而漂移——实际上候选越多，agent 越容易重复采样同一失败模式，$p$ 会边际下降，因此预算翻倍的收益应打折看待，这一折扣正是多轮 RL 中需要显式建模的部分。

四 · 算例如何影响搜索预算：从 $E[\text{usable}]$ 反推 $N$ 与分层策略

把上节算例继续推演，看它如何改变预算分配而非仅仅给出一个数字。已知 $E[\text{usable}] = 7$ 在 $N=40$ 下成立，若上线判断要求「至少 3 个可用基线以覆盖不同形状区间」，则当前预算刚好够用但无冗余；一旦 $p$ 因 oracle 加严降到 0.2，$E[\text{usable}]$ 跌到 4，冗余消失，此时任何一次编译失败都会让计划落空。工程判断因此落在「预算的方差」而非「预算的均值」上：可用基线数的分布近似二项分布，其标准差约为 $\sqrt{N p q (1-pq)}$，在 $N=40$、$pq=0.175$ 时标准差与均值同量级，意味着单次搜索的结果波动很大，不能按均值做排期。

机制上，降低这种波动的办法是分层预算：把 $N$ 拆成 $N_1$（只跑第一、二层 oracle 的廉价筛选）与 $N_2$（跑完整三层 oracle 与 profile 的昂贵确认），且 $N_1 \gg N_2$。伪代码思路是：对每个生成候选先做编译与形状合法性检查，失败即丢弃并计入 $c_{\text{compile}}$；通过的候选跑小形状比对，仅当通过才进入第三层与计时。这样有效 $c$ 被摊薄，$N^{*}$ 上升，而 $p$ 的估计仍以完整三层为准，只是统计样本变少。代价是 $p$ 的估计方差变大，若 $N_2$ 太小，$q$ 的条件统计会失真，进而误导后续 RL 的奖励尺度。

另一个影响搜索预算的具体机制是候选去重。仅目标驱动时，agent 容易在不同轮次生成结构等价但参数不同的候选（同一分块策略、仅 tile 大小不同），这些候选在 oracle 下高度相关，对 $E[\text{usable}]$ 的边际贡献远低于独立候选。若不做去重，$N$ 的名义值上升而有效独立样本数不升，预算被重复消耗。工程上可用编译产物的静态特征（寄存器数、共享内存用量、循环结构哈希）做粗筛，把明显同构的候选折叠，代价是可能误杀参数敏感性强的变体——这正是需要 profile 而非仅靠静态特征来兜底的原因。

五 · 算例如何影响上线判断：从基线可用到端到端收益

上线判断与基线可用是两个判据，算例在此处的作用是把二者分开。基线可用的判据是 $E[\text{usable}] \ge$ 所需基线数，上线判断的判据是端到端收益的置信下界为正。设某候选在目标形状上时延优于现有实现，但其收益来自把计算挪到更宽的向量化路径，代价是对非对齐长度退化严重；此时单形状的 $q$ 很高，跨形状的收益却可能为负。上线判断要求把收益写成按形状分布加权的形式，并对每个形状区间取收益的下界，只有当最差区间的下界仍为正才可上线。

机制上，这要求基线生成阶段就产出可复现的 profile 记录，而不是只产出源码。具体做法是对每个可用基线在至少两类形状（对齐与非对齐、大与小）上各跑一次计时，记录时延与显存峰值，形成二维收益表；上线判断读取该表并按流量权重聚合。代价是 profile 次数随形状数线性增长，直接抬高 $c_{\text{prof}}$，因此工程上常把 profile 限制在通过完整 oracle 的 $N_2$ 个候选上，用少量样本估计收益分布，并接受估计误差。

把算例代入：$E[\text{usable}]=7$ 中有 3 个候选在目标形状达标，但只有 1 个在非对齐形状上不退化的候选，则上线判断的结论取决于非对齐形状的流量占比。若该占比不可忽略，则可用基线数虽满足要求，上线判断仍应保守——这不是数字游戏，而是判据维度不同导致的必然分歧。解题时若把 $E[\text{usable}] \ge 3$ 直接当作上线依据，就是把「基线可用」误当「可上线」，属于本条目要指出的典型错误路径。

六 · 解题路径收束：需要调用的公式与不应越过的边界

本部分给出的解题路径要求解题者在动笔写 kernel 前先完成三张表：验收口径表（oracle 分层与容差）、目标阈值表（时延/带宽/显存多维约束及其测量方法）、预算表（$B$、$c$ 拆分、$N$ 上限）。三张表齐备后，调用公式的顺序是：先由 $B$ 与 $c$ 得 $N^{*}$，再由分层 oracle 估 $p$，由多维阈值估 $q$，最后算 $E[\text{usable}] = N^{*} p q$ 并与所需基线数比较；若不足，回到预算表调 $c$ 的分层结构，而不是直接加预算。上线判断则另起一行，用跨形状收益下界，不复用 $E[\text{usable}]$。

不应越过的边界有三条。其一，不得在无参考实现时把 $p$ 估成接近 1——分层 oracle 的第三层几乎必然暴露边界错误，$p$ 的主要折损在此。其二，不得把 $q$ 当作与 $p$ 独立的量来相乘而不加条件说明，$q$ 是在通过 oracle 的候选上统计的，样本量小则其估计不可靠。其三，不得用单形状的达标率代替跨形状收益下界做上线判断，这是算例已经展示过的分歧点。三条边界的共同代价都落在时延与 token 上：加严 oracle 抬 $c$，加宽形状覆盖抬 $c_{\text{prof}}$，而两者都会压缩 $N^{*}$，进而压缩 $E[\text{usable}]$——预算、正确性与上线判断三者通过 $c$ 耦合在一起，这正是「仅目标驱动基线生成」在工程上真正的难点所在。

目标驱动基线在题面歧义与预算耦合处的失效边界

「仅目标驱动基线生成」把题面里可观测的目标量（输出形状、归约轴、dtype、容差）直接映射成一份参考实现骨架，跳过对输入分布与算子语义的显式建模。它的边界条件很窄：只有当目标量足以唯一确定计算图时，映射才是单值的。一旦题面同时约束「沿哪个轴归约」和「是否保持广播语义」，目标量之间出现耦合，基线生成器会退化成在候选骨架集合上做无约束枚举，公式退化为 $$B_{\text{eff}} = \frac{B_{\text{total}}}{1 + \alpha \cdot |\mathcal{C}_{\text{amb}}|}$$ 其中 $$\mathcal{C}_{\text{amb}}$$ 是歧义候选数，$$\alpha$$ 是每次候选验证所需的编译加运行开销折算成的预算份额。歧义每多一个候选，可用于后续搜索的有效预算就被摊薄一次，且摊薄不是线性的——候选之间共享的编译缓存命中率下降会放大 $$\alpha$$。

失效的典型触发点是容差与数值稳定性目标同时出现：题面要求 fp16 输入、fp32 累加、相对误差阈值，基线生成器若把容差当成硬约束直接写进骨架，会生成带显式升精度的参考实现，正确性 oracle 通过，但它在搜索阶段作为「基线」被反复调用做差分比对，每次比对都要跑一遍高精度路径。代价落在时延上：单次基线调用从一次 kernel launch 变成 launch 加同步加逐元素比对，端到端搜索轮次被拉长；更隐蔽的代价是显存，高精度中间张量在 batch 较大时挤占可用于并行候选评估的显存池，导致并发度下降，反过来又拉长墙钟时间。

工程判断上，这类题面应先做考点拆解再决定是否启用目标驱动基线：把「归约轴」「广播语义」「容差」三项分别标注为确定项与歧义项，只对确定项生成骨架，歧义项留给搜索阶段用执行反馈裁决。若歧义项超过两项，直接放弃基线生成、改用带正确性 oracle 的多候选并行评估更划算——此时基线的边际收益已被摊薄公式吃掉，继续生成只是把编译时间换成无效候选。
