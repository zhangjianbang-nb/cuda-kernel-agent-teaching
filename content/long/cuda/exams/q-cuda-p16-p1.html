一 · 题干的三层结构：pipeline、逐段 I/O、失败模式

这道题表面上是一个“流程题”，实质是一个“可观测性题”。《The Correctness Illusion in LLM-Generated GPU Kernels》这个标题已经把考点写在脸上：correctness 是可以被“illusion”的，也就是说，一个 kernel 在评测里显示“通过”，并不等于它真的正确。题干要求按“生成—编译—运行—评测”的顺序回答 pipeline 的步骤、每步的输入输出、每步的失败模式，这意味着答题者必须把一条看似线性的流水线拆成若干个可独立观测的边界，并在每个边界上指出“什么信号能证明这一步真的成功了”。

拆题干时先抓三个关键词。“pipeline”要求的是阶段划分，而不是罗列工具；“输入、输出”要求的是每段的契约（contract），即上一段的产物以什么形式交给下一段；“失败模式”要求的是每段特有的、不能被下游掩盖的错误形态。三者合起来构成一个判据：如果答题者只写了“LLM 生成代码→nvcc 编译→跑一下→对比结果”，那他只答了“动作序列”，没有答“契约与失败模式”，属于典型的低分答法。

题干还有一层隐含约束：“按一次 kernel 生成—编译—运行—评测的顺序”。这个“一次”很关键，它把问题锁定在单轮（single rollout）而非多轮 RL 循环上。也就是说，本部分不讨论 reward 设计、不讨论多轮修正，只讨论一次尝试从自然语言/参考实现到评测结论之间经过的每一个环节。多轮与可验证奖励属于其他片段的主题，此处只用一句话指路：多轮循环本质上是对这条单轮 pipeline 的重复调用与反馈注入。

由此，解题路径可以定为四步：第一步，把 pipeline 切成四段并写出每段的 I/O 契约；第二步，为每段列出至少两类失败模式（一类是“硬失败”，即报错；一类是“软失败”，即静默错误）；第三步，指出哪些失败模式会被下游阶段“吞掉”，从而制造 correctness illusion；第四步，给出每段应当采集的证据（编译日志、launch 配置、数值比对、profiling 计数），并说明采集这些证据的代价。这四步就是本部分的骨架。

二 · 生成段：输入是规格，输出是“可编译候选”，失败模式是规格漂移

生成段的输入不是“一句话需求”，而是一组规格：参考实现（通常是 PyTorch 或 NumPy 的算子）、张量形状与 dtype、边界条件（如非连续 stride、空张量、极值）、目标后端（CUDA C++ / Triton / CuTe / PTX）以及性能约束。输出是一段候选源码加上它的 launch 配置（grid/block、shared memory 用量、stream）。这里的契约是：候选源码必须在语义上等价于参考实现，并且在语法上可被目标工具链接受。注意“等价”不是“看起来像”，而是对所有合法输入给出相同的可观测结果（在浮点容差内）。

生成段最典型的失败模式是规格漂移（spec drift）：模型在生成时悄悄改变了问题。常见形态有三类。其一是形状假设固化，把动态 shape 写成编译期常量，导致换一个 batch size 就越界或算错；其二是 dtype 降级，把 fp32 累加写成 fp16 累加，单看代码“合理”，但在长归约上误差累积；其三是边界裁剪，把 tail 元素直接丢掉，理由是“大多数情况下整除”。这三类都不是编译错误，而是语义错误，它们会顺利通过编译段，把问题推迟到运行段甚至评测段才暴露——或者根本不暴露。

可以用一个简单的伪代码思路来描述生成段应当产出的“契约检查清单”：

$$\text{Gen}(s) \rightarrow (C,\ \text{cfg}),\quad \text{require}:\ \forall x \in D,\ \text{eval}(C,\text{cfg},x) \approx \text{ref}(x)$$

其中 $D$ 是输入域，$s$ 是规格。这个式子的工程含义是：生成段的正确性命题是一个全称命题，而 pipeline 后续所有阶段都只是在有限样本上逼近它。任何一次评测都只是对 $D$ 的一个采样，这就是 correctness illusion 的数学根源。生成段的代价主要体现在 token 与时延上：候选越长、越接近 PTX 层，生成耗时与 token 消耗越高，而编译期常量化的写法虽然能减少运行期分支，却把灵活性换成了规格漂移的风险。

具体例子：参考实现是一个带 mask 的 softmax，输入形状为 $(B, S)$ 且 $S$ 可变。模型生成的 CUDA kernel 把 $S$ 写成模板参数并在 host 端按 128 对齐向上取整，越界部分用 0 填充后参与归约。这个写法在 $S$ 恰为 128 倍数时结果正确，在其余情况下分母被污染，输出整体偏小。编译段完全通过，运行段不报错，评测段若只测整除形状就会给出“通过”——这就是一次完整的 illusion 生成过程。

三 · 编译段：输入是候选源码，输出是二进制与元数据，失败模式是“编译通过但语义已变”

编译段的输入是候选源码、编译选项（arch、优化级别、是否开启 fast math）、以及依赖的头文件与库。输出是可加载的二进制（cubin/fatbin 或 Triton 的编译产物）、符号表、以及寄存器占用、shared memory 用量、是否发生 spill 等元数据。契约是：产物的语义必须与源码语义一致，且资源占用满足 launch 配置的可行性约束（例如 shared memory 不超过硬件上限，否则 launch 直接失败）。

编译段有两类失败模式。硬失败是语法错误、未定义符号、不支持的 intrinsic、arch 不匹配，这类失败会立刻中断 pipeline，代价是编译时间与一次重试的 token。软失败则危险得多：编译器在合法范围内改变了语义。典型来源是 fast math（把除法换成倒数近似、允许重排浮点加法）、以及未定义行为被优化器“利用”（越界写被当作不存在，循环被向量化后 tail 处理被删）。这类失败在编译日志里通常只有一行 warning，甚至没有 warning。

因此编译段必须采集的证据不只是“成功/失败”，而是资源与告警的量化指标。一个可操作的判据是：把寄存器数、spill 字节数、shared memory 用量与 launch 配置做交叉校验，若 shared memory 需求超过配置上限，则 launch 阶段必然失败，这属于可以在编译段提前拦截的失败。另一个判据是把 fast math 开关作为实验变量固定下来，因为它是“编译通过但数值已变”的最常见开关。

代价方面，编译段时间随模板实例化数量、PTX 到 SASS 的优化级别上升而增长；对 Triton 而言，autotune 会触发多次编译，编译时间成为端到端时延的显著组成部分。具体例子：一个归约 kernel 在开启 fast math 后，编译器把跨线程的加法重排并结合成部分和，单看每个线程的结果都在容差内，但整体归约顺序改变导致与参考实现的差异超出阈值；若评测只做单元素抽查而非全量比对，这个差异不会被发现。

四 · 运行段：输入是二进制与实参，输出是设备端结果与运行时状态，失败模式是“静默错误与异步吞错”

运行段的输入是二进制、launch 配置、设备内存上的实参（含 stride、offset、dtype 描述）、以及 stream/event 的同步策略。输出是输出张量的内容、kernel 的返回状态、以及可选的运行时计数（如实际占用、耗时）。契约是：在给定的 launch 配置下，kernel 对给定输入产生正确结果，且不破坏其他内存。这里的关键工程事实是 CUDA 的错误报告是异步的：kernel 内部的越界访问、非法指令往往不会在 launch 调用处返回，而是在后续的同步点或下一次 API 调用时才被报告，甚至被后续的合法操作掩盖。

运行段的失败模式可以分为三类。第一类是静默数值错误：没有越界、没有非法指令，只是算错了，例如前面 softmax 例子里分母被污染。第二类是内存破坏：越界写踩到相邻张量或元数据，症状出现在别处，定位困难。第三类是同步缺失：漏掉 __syncthreads() 或 stream 间缺少依赖，导致读到未完成的数据，结果依赖调度时序，表现为“有时对有时错”。第三类最阴险，因为它让评测结果具有随机性，而单次评测无法区分“偶发错误”与“确定性正确”。

运行段应采集的证据包括：launch 是否成功、同步点返回的错误码、以及用 compute-sanitizer 一类工具做的越界与竞态检查。代价是显存的额外占用（sanitizer 需要影子内存）与运行时间的成倍增加；在长 kernel 或大 batch 上，这种检查可能让单次运行从毫秒级升到秒级，因此通常只在抽样上开启。具体例子：一个矩阵乘 kernel 的边界 tile 写越界了一个元素，踩到了紧随其后的 bias 张量首元素，导致 bias 被改写；主输出比对通过，但下游算子结果异常，评测若只看主输出就会判为正确。

五 · 评测段：输入是设备端结果与参考，输出是判定，失败模式是“采样偏差与判据过松”

评测段的输入是运行段产出的输出张量、参考实现的输出、以及判据参数（dtype、相对/绝对容差、是否做全量比对、随机种子集合）。输出是一个二值或分级的判定，以及可能的差异统计。契约是：判定必须对“该 kernel 在目标输入分布上是否正确”给出可信的回答。问题在于，评测段只能看到有限样本，而正确性命题是全称命题，因此评测段的本质是统计推断，而不是证明。

评测段的失败模式主要有两种。其一是采样偏差：测试集集中在“好走”的形状上，例如整除的、对齐的、连续的、数值温和的输入，而真实负载恰恰落在非整除、非连续、含 NaN/Inf、含极值的区域。其二是判据过松：容差设得比参考实现的数值误差还宽，或者只比对部分元素（如只查首元素、只查均值），使得系统性偏差被平均掉。两者叠加，就构成 correctness illusion 的最后一环：一个在真实分布上错误的 kernel，在评测分布上被判为正确。

可以把判据写成如下形式，用来暴露“过松”在哪里：

$$\text{pass} = \bigwedge_{x \in S} \left( \lVert y(x) - y_{\text{ref}}(x) \rVert \le \tau(x) \right),\quad S \subseteq D$$

这里 $S$ 是采样集，$\tau(x)$ 是逐元素的容差。工程判断在于：$\tau$ 应当由参考实现的数值特性推导（例如归约长度与 dtype 决定的误差上界），而不是拍一个常数；$S$ 应当显式覆盖边界形状与极端值，而不是随机采样了事。代价方面，全量比对意味着把整个输出张量搬回 host 并逐元素比较，带宽与显存占用成为瓶颈；对大规模输出，通常采用分块比对或设备端归约差异，但这又引入了“差异本身被近似”的风险。

具体例子：一个 LayerNorm kernel 在 fp16 输入上做了 fp16 累加，评测集只包含均值接近 0、方差接近 1 的输入，容差设为 1e-2，全部通过；换到方差极小的输入上，fp16 累加的舍入误差相对放大，输出偏差超过真实负载可接受范围。评测段没有覆盖这类输入，于是 illusion 成立。要打破它，评测段必须把“输入分布”当作一等公民来设计，而不是把评测简化成一次 torch.allclose。

六 · 四段之间的耦合：哪些失败会被吞掉，以及证据该挂在哪

把四段串起来看，真正的考点是失败模式在段间的传播与掩盖。生成段的规格漂移不会被编译段发现，因为语法合法；编译段的语义改变不会被运行段发现，因为不报错；运行段的静默数值错误不会被评测段发现，如果采样集恰好避开；评测段的判据过松则会把前三段的所有软失败一并合法化。这条链条上每一环都在“过滤”信号，而过滤的方向是一致的：把错误变成“通过”。

因此解题路径的第三步应当是给每段挂一个不可被下游替代的证据。生成段挂“规格对照表”：把参考实现的输入域显式列出，并要求候选代码对每个维度假设作出声明；编译段挂“资源与告警清单”：寄存器、spill、shared memory、fast math 开关状态；运行段挂“同步点错误码与 sanitizer 抽样结果”；评测段挂“采样集覆盖报告与容差推导”。这四类证据的共同点是：它们都在各自的段内可观测，且不依赖下游的判定结果。

代价的分配也需要在答题中体现。生成段用 token 换灵活性；编译段用编译时间换资源可见性；运行段用运行时间与显存换内存安全；评测段用带宽与 host 内存换统计可信度。四者不可能同时最优，工程判断在于根据目标负载选择在哪一段加码。例如面向生产端到端收益时，评测段的采样集设计成本最高但收益最大，因为它直接决定“通过”二字是否可信；而面向快速迭代时，编译段的告警清单成本最低，能最早拦截一批硬失败。

最后一个具体机制值得点出：把四段的证据做成一条带时间戳的记录链，每段写入自己的输入摘要、输出摘要与判定，下游段只能读取上游的摘要而不能改写。这样当评测给出“通过”时，可以回溯到生成段声明的形状假设、编译段的 fast math 状态、运行段的同步点错误码，从而判断这个“通过”是在什么条件下成立的。这正是把 correctness illusion 转化为可审计结论的最小工程手段，也是本部分读题后应当落到实处的解题路径终点。
