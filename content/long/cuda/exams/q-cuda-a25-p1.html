一 · 题干里真正被问的是什么：一次「生成—优化—验证」流动的分解

「合成算子数据扩增」这个说法容易被误读成数据工程问题：仿佛先造一批算子样本，再去训练。放到 kernel agent 的语境里，它问的是另一件事——当我们要让 agent 生成一个 GPU kernel 时，如何用「合成出来的算子」把一次生成/优化/验证的流动撑开，使这条流动的每一步都有明确的输入、输出与代价，并且这些代价可以被计量、被比较、被回放。因此题干的核心不是「扩增多少条数据」，而是「一次 kernel 生成/优化/验证的流动拆成哪几步」。拆分的粒度决定了后面所有评测与 RL 奖励的可信度：步拆得太粗，执行反馈无法归因到具体决策；拆得太细，每步的 token 与编译开销会把预算吃光。

读题时要抓住三个隐含约束。第一，合成算子必须是可执行的：它有确定的输入张量形状、数据类型、语义参考实现，否则正确性 oracle 无从建立。第二，合成算子必须是可评分的：它要能落到 KernelBench 系的基准形态上，即给定参考实现与性能基线，产出正确性与加速比两类信号。第三，合成算子必须是可扩增的：同一语义可以由不同写法（CUDA C++、Triton、CuTe、PTX 内联）表达，扩增的意义在于让 agent 在同语义的不同表达面上被检验，而不是把同一条样本复制多份。这三条约束直接决定了流动的切分方式：切分点必须落在「语义已固定、表达未固定」的位置上。

由此，题干的考点可以归纳为四类：其一，流动的阶段划分与阶段间契约——每一步输出什么、下一步凭什么接受它；其二，合成算子作为输入时的构造规范——形状、dtype、边界条件、参考实现的等价性判据；其三，代价的归属——时延、带宽、显存、编译时间、token 各自记在哪一步；其四，反馈回路的闭合条件——哪一步的失败可以回退，哪一步的失败必须终止。这四类考点不给出答案，只给出解题路径：先把流动切成段，再为每段定义契约，最后为每段挂上代价与回退规则。

二 · 切分原则：以「语义冻结」为界，而不是以工具为界

常见的错误切法是按工具切：生成阶段用 LLM、优化阶段用编译器、验证阶段用测试框架。这种切法把流动绑死在具体工具上，一旦换表达面（例如从 Triton 换到 CuTe）整条流动就要重画。正确的切分原则是以语义冻结为界：在语义冻结之前，一切决策都还可能改变算子「算什么」；在语义冻结之后，一切决策只改变算子「怎么算」。合成算子数据扩增恰好提供了这个边界——扩增产生的是同一语义的多个表达候选，语义本身在扩增那一刻就被冻结了。

按此原则，一次流动至少切成四段：读题与规格化（把合成算子转成可执行的规格）、生成（产出候选 kernel 源码）、优化（在保持语义的前提下改写）、验证（用 oracle 与 profile 判定正确性与性能）。四段之间有三份契约：规格→生成是「签名契约」（函数签名、形状约束、dtype、对齐要求）；生成→优化是「语义契约」（优化不得改变可观察输出）；优化→验证是「证据契约」（验证方拿到的不只是源码，还有优化方声称的变换理由与预期收益）。契约的存在使得每一步的失败可以被定位到具体一段，而不是笼统地说「这个 kernel 不行」。

代价上，这个切分原则的直接后果是：语义冻结点越早，扩增的候选越多，但每个候选可做的优化空间越小；语义冻结点越晚，优化空间越大，但验证方需要承担的等价性证明负担越重。用公式表达这种张力，设候选数为 N、单候选优化搜索空间为 S、验证单候选代价为 V，则总代价近似为

$$ C_{\text{total}} \approx N \cdot (C_{\text{gen}} + C_{\text{opt}}(S) + V) $$

其中 C_{\text{opt}}(S) 随 S 增长而增长，而 V 在语义冻结晚时会因等价性判据变复杂而上升。切分点就是在 N 与 S 之间做取舍的工程判断，而不是理论最优。具体例子：一个归约类合成算子，若在规格化阶段就冻结「沿最后一维求和、输出形状去掉该维」，则扩增出的候选只是在 reduction 策略上不同（线程内串行、warp shuffle、共享内存树形），验证只需比对输出张量；若把冻结推迟到优化之后，候选可能连输出布局都改了，验证就必须额外比对布局契约，代价上升。

三 · 第一段：读题与规格化——把合成算子变成可执行契约

这一段是整条流动中唯一不产生 kernel 源码的阶段，但它决定了后面所有阶段的输入质量。输入是合成算子描述（语义、形状族、dtype 族、边界条件），输出是一份规格对象，至少包含：函数签名、输入输出张量的形状与步长约束、dtype 与对齐、数值容差、参考实现的调用方式、以及该算子所属的基准类别。规格对象是生成阶段的唯一输入，生成阶段不得越过规格自行发明语义。

规格化的关键机制是形状族的参数化。合成算子不应只给一个固定形状，而应给一族由参数生成的形状，使得同一语义在不同规模下被检验。参数化的形状族同时承担了扩增的职责：不同参数取值就是不同的样本，但它们共享同一份语义契约，因此验证 oracle 只需写一次。这里要付出的代价是编译时间与显存：形状族中每个取值都要单独编译一次 kernel（模板实例化或 JIT），显存峰值由族中最大形状决定。若族中最大形状远超实际部署规模，编译与显存代价会挤占优化阶段的预算。

规格化阶段还要显式写出容差判据。浮点算子的正确性不能靠逐位相等，必须给出绝对/相对容差与归约顺序敏感性说明。容差写得太松，错误 kernel 会通过验证；写得太紧，合法的重排（例如改变累加顺序）会被误判为错误。这个判据是验证阶段 oracle 的直接输入，也是优化阶段允许的变换范围的边界。伪代码上，规格对象的构造可以写成：

  • 读入算子语义描述，抽取输出与输入的形状映射关系；
  • 为每个张量维度标注是否可变、可变范围、是否要求连续；
  • 绑定 dtype 与对齐，标注是否允许混合精度累加；
  • 生成参考实现的调用封装，固定随机种子以保证可复现；
  • 写出容差与归约敏感性说明，作为后续等价性判据。

具体例子：一个「按行 softmax」的合成算子，规格化时要写明行内元素数可变、行数可变、dtype 为半精度输入单精度累加、容差按相对误差给出、参考实现固定用某一归约顺序。若省略「单精度累加」这一条，生成阶段可能产出半精度累加的 kernel，数值上在长行时偏差放大，验证阶段就会在容差边界上反复摇摆，浪费多轮预算。

四 · 第二段：生成——在签名契约下产出候选源码

生成阶段的输入是规格对象，输出是一组候选 kernel 源码，每个候选附带其自述的「实现要点」（用了哪种并行分解、哪种内存层次、哪种向量化宽度）。自述要点不是装饰，它是优化阶段的输入之一：优化方需要知道当前候选的瓶颈假设，才能决定往哪个方向改写。生成阶段的代价主要是 token 与时延：候选数越多，token 消耗线性增长；而每个候选都要经过一次编译才能进入验证，编译时间随候选数与形状族规模相乘。

生成阶段的核心机制是表达面的选择。同一语义可以用 CUDA C++ 写、用 Triton 写、用 CuTe 写布局、用 PTX 内联写关键循环。不同表达面的可优化空间不同：CUDA C++ 给出手动管理共享内存与寄存器的自由，Triton 把分块与流水交给编译器，CuTe 把布局与线程映射显式化，PTX 则把指令级选择暴露出来。扩增的意义正在于此——让同一语义在多个表达面上被生成，从而检验 agent 是否理解「语义不变、表达可变」。代价是：表达面越多，验证方需要支持的编译与运行环境越多，环境维护成本上升；同时不同表达面的性能基线不可直接比较，必须各自绑定基线。

生成阶段必须遵守的一条纪律是不越过签名契约。候选可以改变内部循环结构，但不能改变函数签名、不能改变输出形状、不能改变 dtype 约定。违反签名契约的候选在验证阶段会被直接判为无效，浪费一次编译。为降低这种浪费，生成阶段应做一次轻量的静态检查：签名匹配、形状映射一致、dtype 一致。静态检查的代价很低（不编译），但能挡掉相当一部分无效候选。用公式刻画生成阶段的预算分配，设 token 预算为 B、单候选平均 token 为 t、编译单候选时间为 c，则候选数 N 受两侧约束：

$$ N \le \min\left(\frac{B}{t},\ \frac{T_{\text{build}}}{c}\right) $$

其中 T_{\text{build}} 是本轮允许的编译总时间。这个式子说明生成阶段不是「越多越好」：当编译时间成为瓶颈时，增加候选只会拉长流动而不增加有效信息。具体例子：一个矩阵乘类合成算子，若形状族含三个规模、每个候选编译需数十秒量级，则候选数应控制在个位数到十余个，把预算留给优化阶段的迭代改写，而不是一次性铺开几十个候选。

五 · 第三段：优化——在语义契约下改写并自证变换理由

优化阶段的输入是候选源码及其自述要点，输出是改写后的源码、变换理由、以及预期收益的定性说明。它与生成阶段的区别在于：生成是从规格出发构造，优化是从已有候选出发改写，且改写必须保持语义契约。语义契约的具体内容是「可观察输出不变」——在规格给定的容差内，输出张量与参考实现一致。优化方不得以「性能更好」为由放宽容差，也不得改变输出布局而不声明。

优化的核心机制是基于 profile 的定向改写。优化不是盲目重写，而是先用 NCU/SASS profile 定位瓶颈：是访存受限、是计算受限、是占用率不足、还是指令级并行不够。profile 给出的是每一条改写方向的证据，改写后再用 profile 验证收益是否兑现。这个「profile—改写—再 profile」的循环是优化阶段的骨架，其代价是每轮循环都要一次编译加一次运行，编译时间与运行时间共同构成循环成本。若 profile 采集本身开销大（例如需要多次重放以稳定计数），循环成本会显著上升，此时应降低 profile 采集频率，只在关键改写前后采集。

优化阶段还必须产出变换理由，这是它与验证阶段之间的证据契约。理由不需要形式证明，但必须能让验证方判断「这个改写是否在语义契约允许的范围内」。例如「把逐元素循环改为向量化加载，因为输入对齐且长度为向量宽度的整数倍」是一条可检验的理由；「调整了线程块大小」则需要说明为何不影响输出。理由的质量直接决定验证阶段能否快速定位失败原因：没有理由的改写一旦失败，验证方只能从头比对，代价高。伪代码上，一轮优化循环可以写成：

  • 采集 profile，标注瓶颈类别与关键计数；
  • 依据瓶颈选择一条改写方向，写出变换理由与预期收益；
  • 改写源码，保持签名与语义契约；
  • 编译并运行，比对输出是否在容差内；
  • 若输出不符，回退并记录该改写方向的失败；若相符，再采集 profile 验证收益。

具体例子：一个带宽受限的逐元素算子，profile 显示全局加载未合并，优化方改写为按线程连续映射的合并访问，理由写明「原映射导致相邻线程访问跨步，合并后每 warp 访问连续段」。改写后输出不变、带宽利用上升；若改写同时改变了边界处理而未声明，验证阶段会在非对齐形状上抓到输出偏差。这里要付出的代价是：每轮改写都要一次编译，且改写方向若选错，回退成本是一次完整编译加运行。

六 · 第四段：验证——oracle、profile 与回退规则的闭合

验证阶段的输入是优化后的源码、变换理由、以及规格对象中的容差判据，输出是三元判定：正确性是否通过、性能是否达到预期、失败是否可归因。验证不是简单跑一遍测试，而是要把「正确性 oracle」与「性能证据」分开记录，使得一个候选可以「正确但慢」或「快但错」，两种失败对应不同的回退路径。

正确性 oracle 的机制是参考实现比对加边界形状覆盖。规格中的形状族必须包含至少一个非对齐形状、一个极小形状、一个极大形状，用以检验边界处理与数值稳定性。比对时按规格给定的容差判据逐元素比较，并对归约类算子额外检查归约顺序敏感性。代价是运行时间与显存：极大形状的比对需要同时驻留参考输出与候选输出，显存峰值翻倍；若显存不足，验证只能退化为分块比对，代价是比对逻辑复杂化。性能证据的机制是 profile 计数与基线对比：把候选的关键计数（带宽、占用率、指令吞吐）与基线对照，判断收益是否来自预期的改写方向，而非来自形状偶然性。

回退规则是验证阶段闭合反馈回路的关键。可回退的失败包括：改写方向选错但语义未破、性能未达预期、profile 显示瓶颈转移。必须终止的失败包括：签名契约被破坏、语义契约被破坏且无法定位到单条改写、参考实现本身不可复现。回退的代价是重入优化阶段的一轮循环；终止的代价是丢弃该候选并消耗已投入的 token 与编译时间。用公式表达一次流动的期望代价，设通过率为 p、单候选验证代价为 V、回退一轮代价为 R、回退概率为 q，则

$$ E[C] \approx N \cdot \left(V + q \cdot R\right) / p $$

这个式子说明：提高通过率 p 或降低回退概率 q 比单纯增加候选数 N 更能压低期望代价。具体例子：一个归约算子候选在极大形状上因累加溢出导致输出偏差，验证阶段判定为语义契约破坏但可定位到「累加 dtype 选择」这一条改写，于是回退到优化阶段只改这一条，重入代价仅一轮循环；若偏差无法定位到任何单条改写，则只能终止该候选，已投入的生成与优化预算全部沉没。验证阶段因此不是流动的终点，而是把失败翻译成下一轮输入的翻译器——它输出的归因标签，就是下一轮生成或优化的起点。
