一 · 把题干拆成可判定的三层

题干只有一句：“方向「基准与可信评测」要解决的三个具体问题是什么？给出评测侧与部署侧各两条可执行做法，并说明它与相邻方向的分工。”这句话在阅卷上被切成三层可判定要求，任何一层缺失都直接扣分，而不是“答得不够全面”。第一层是枚举：必须给出恰好三个“具体问题”，且每个问题要落到可观测的失败模式上——不是“评测不可信”这种同义反复，而是“同一 kernel 在两次评测中通过率不一致”“优化后的 kernel 在真实负载下收益为负”这类能被实验证伪的陈述。第二层是可执行性：评测侧两条、部署侧两条，共四条做法，每条必须包含触发条件、执行动作、判定阈值三要素，缺阈值即视为不可执行。第三层是边界：说明本方向与相邻方向（生成、优化、训练）的分工，分工的判据是“谁对最终数字负责”，而不是“谁做哪一步”。

拆题时最容易犯的错是把三层混成一段散文。工程上更稳的做法是先写一个判定表，把每层要求映射到可检查的产出物：枚举层对应三个“问题—失败模式—度量”三元组；可执行层对应四条“条件—动作—阈值”记录；分工层对应一张责任矩阵，行是方向，列是“产出物/负责的数字/不负责的数字”。这张表本身就是答题骨架，后续所有论述都是往格子里填内容。代价在于时间：把三层显式化大约要多花几分钟构思，但换来的是不会在某一层上漏项——漏一条可执行做法通常比论证不严谨扣得更狠。

一个具体例子：若考生把“三个问题”写成“正确性、性能、可复现性”，这在枚举层是失败的，因为三者不是同一抽象层级——“可复现性”是正确性与性能度量能否成立的前提条件，把它与另两者并列会造成集合重叠，阅卷时无法判定三个问题是否互斥。正确做法是让三个问题各自对应一种独立的失效来源，例如：正确性 oracle 本身不完备导致的假阴性、性能度量口径不一致导致的排序翻转、评测分布与部署分布偏移导致的收益消失。三者互不蕴含，且各自能挂上不同的度量。

二 · 三个具体问题的考点定位

考点不在“知道有三个问题”，而在“能说清每个问题为什么不能靠相邻方向顺手解决”。第一个问题围绕正确性 oracle 的完备性：LLM 生成的 kernel 常在边界形状、非对齐 stride、极值输入上出错，而基准自带的参考实现与容差设置决定了这些错误是否会被捕获。这里的机制是“容差—覆盖—判定”三者耦合：容差放宽会掩盖数值误差，覆盖不足会漏掉形状分支，判定规则（全等/近似/相对误差）选择不当会让同一 kernel 在不同测试间翻转结论。公式上要写出相对误差判据：

$$\ \text{pass} = \bigwedge_{i}\ \frac{|y_i - \hat{y}_i|}{\max(|y_i|,\ \epsilon)} \le \tau \ \wedge\ \text{shape}(y)=\text{shape}(\hat{y})$$

代价是显存与时间：覆盖更多形状分支意味着要保留多组输入输出缓冲，测试集规模上升会线性抬高评测时延与显存占用；而容差 τ 收紧会提高假阴性率，让本可用的 kernel 被判失败，进而污染后续优化的奖励信号。具体例子：一个 reduction kernel 在 N 为 2 的幂时通过、在 N 为质数时越界写，若基准只采样幂次形状，这个错误在评测侧完全不可见，直到部署侧出现非法内存访问。

第二个问题围绕性能度量的口径：同一 kernel 在不同测量方式下排序会翻转，原因包括是否计入启动开销、是否固定时钟、是否使用 warmup、是否统计尾延迟。考点是要求考生指出“度量口径必须与部署场景对齐”，而不是追求某个绝对准确的数字。机制上要区分吞吐口径与延迟口径：吞吐用总工作量除以墙钟时间，延迟用单次调用的分位数。公式上给出加速比的两种定义差异：

$$S_{\text{throughput}}=\frac{T_{\text{base}}^{\text{total}}}{T_{\text{opt}}^{\text{total}}},\qquad S_{\text{latency}}=\frac{\text{p50}(T_{\text{base}})}{\text{p50}(T_{\text{opt}})}$$

两者在批量小、启动开销占比高时会给出相反结论。代价是测量成本：要得到稳定的分位数需要足够多的重复采样，采样数增加会拉长评测时间；固定时钟与隔离干扰需要独占设备，降低评测吞吐。具体例子：一个小规模 elementwise kernel 优化后单次延迟下降，但若基准按大批量吞吐统计，启动开销被摊薄，加速比反而看不出差异——这不是 kernel 变差，而是口径与场景错配。

第三个问题围绕评测分布与部署分布的偏移：基准里的形状、dtype、并发度是人为选定的，部署侧的真实负载分布不同，导致“基准上加速、部署上无收益甚至退化”。考点是要求考生把这个问题与“泛化”区分开：它不是模型泛化，而是度量对象（工作负载）的分布偏移。机制上需要定义负载指纹（形状直方图、dtype 比例、batch 分布），并在评测侧采样时显式记录。代价是评测代表性：要让基准覆盖真实分布，需要采集生产 trace，这带来数据隐私与存储成本，且 trace 回放会引入额外调度开销。具体例子：基准里全是 fp16、对齐形状的 GEMM，部署侧却以 fp32、非对齐 batch 为主，优化后的 kernel 在后者上因额外类型转换而变慢。

三 · 评测侧两条做法的构造路径

题干要求“评测侧两条可执行”，考的是能否把上面的问题转成带阈值的动作。第一条应针对正确性 oracle：做法是分层覆盖 + 容差分级。触发条件是“新 kernel 进入候选池”；动作是按形状类别（对齐/非对齐、幂次/质数、极小/极大）分层采样，并对每层设定独立容差；判定阈值是“任一层出现失败即整体拒绝，且失败样本必须可复现”。伪代码思路是：

  • 对每个形状层 L：生成 k 个输入，跑参考实现与候选 kernel；
  • 若该层相对误差超过 τ_L 或形状不匹配，记录 (L, 输入指纹, 误差)；
  • 仅当所有层通过且失败集为空时，标记 pass。

代价是评测时延与显存：分层意味着测试用例数随层数线性增长，保留输入指纹与中间结果会抬高显存；容差分级需要为每层校准 τ_L，校准本身要跑参考实现的数值分布，增加一次性编译与运行时间。具体例子：对 softmax kernel，对“全等值输入”层设更严的相对误差阈值，因为该层分母接近常数、数值误差会被放大，放宽阈值会让错误实现蒙混过关。

第二条应针对性能口径：做法是双口径报告 + 口径锁定。触发条件是“候选 kernel 进入排序阶段”；动作是同时报告吞吐加速比与分位数延迟加速比，并锁定 warmup 次数、采样数、时钟策略；判定阈值是“两种口径下排序一致才进入下一轮，不一致则标记为口径敏感并人工复核”。机制上要把测量配置写成不可变记录，随结果一起存档，否则同一 kernel 在不同时间跑出不同数字无法归因。代价是评测吞吐下降：双口径意味着两套采样，采样数增加会拉长单次评测时间；锁定时钟与独占设备会降低并行评测的吞吐。具体例子：一个 fused kernel 在吞吐口径下因减少中间写回而占优，在 p99 延迟口径下因尾部抖动而落后，双口径报告让这个矛盾显式暴露，而不是被单一数字掩盖。

四 · 部署侧两条做法的构造路径

部署侧的两条做法必须回答“评测通过之后，凭什么相信它在生产里成立”。第一条针对分布偏移：做法是负载指纹比对 + 影子回放。触发条件是“候选 kernel 通过评测并准备上线”；动作是采集生产侧的形状/dtype/batch 指纹，与评测采样分布做比对，并在影子流量上回放候选 kernel；判定阈值是“指纹覆盖率达到设定比例且影子回放的收益方向与评测一致，才允许灰度”。机制上要把指纹比对做成集合覆盖问题：评测分布必须覆盖生产分布的高频桶，未覆盖桶单独标记。代价是部署时延与资源：影子回放要复制一份流量，占用额外显存与算力；指纹采集需要埋点，增加运行时开销。具体例子：生产侧 90% 的请求集中在某几个非对齐形状，而评测集只覆盖对齐形状，影子回放会直接暴露候选 kernel 在这些形状上的退化。

第二条针对上线后的可信性：做法是灰度期双跑 + 自动回滚判据。触发条件是“候选 kernel 进入灰度”；动作是同一请求同时走旧 kernel 与新 kernel（或按比例分流），比对输出一致性与延迟分布；判定阈值是“输出不一致率超过容差或 p99 延迟退化超过设定比例即自动回滚”。机制上要区分“数值不一致”与“合法差异”：浮点结合律导致的末位差异应在容差内，而形状或越界错误必须零容忍。代价是灰度期资源翻倍：双跑意味着同一请求算两遍，显存与算力开销上升，且比对逻辑本身引入延迟。具体例子：一个新写的 layernorm kernel 在灰度期被发现有极少数非对齐行触发越界读，双跑比对捕获了输出不一致，自动回滚避免了污染下游。

五 · 与相邻方向的分工判据

分工层的考点是“用责任边界而不是流程步骤来切分”。判据可以写成一句话：谁对最终被采信的数字负责，谁就拥有该环节的否决权。生成方向对“候选 kernel 是否存在”负责，优化方向对“候选 kernel 是否更快”负责，训练方向对“策略是否学到可复用的搜索行为”负责，而基准与可信评测方向对“这个更快/更正确的结论是否可信”负责。责任矩阵的列应包含“产出物”“负责的数字”“不负责的数字”：评测侧负责通过率、加速比的口径与置信度，不负责 kernel 的内部实现；部署侧负责线上收益与回滚判据，不负责训练奖励的设计。

这个判据的工程价值在于避免越权：评测侧不能因为某 kernel 在基准上失败就断言它“不可优化”，那是优化方向要回答的；优化方向也不能自行放宽容差来让候选通过，容差是评测侧的否决权。代价是协作开销：责任边界清晰意味着跨方向的接口需要显式契约（例如评测侧向优化侧输出“失败样本指纹”，优化侧向评测侧输出“候选池版本号”），契约维护本身消耗工程时间。具体例子：优化方向报告某 kernel 加速 1.3 倍，评测侧按双口径复核发现吞吐口径成立、延迟口径不成立，此时评测侧有权标记“口径敏感”，而不是直接采信优化方向的单一数字——这正是分工判据在起作用。

落到答题上，分工段不需要长篇，但必须给出可判定的边界陈述：三个问题分别由谁度量、四条做法分别由谁执行、哪些数字不由本方向负责。缺少“不负责的数字”这一列，分工就会被判为模糊，因为无法区分“本方向没做”与“本方向不该做”。

题干拆解：把“三个问题”还原成可判定的命题

题干表面问“三个具体问题”，实际考点是三层可判定性：其一，能否把“可信评测”从“跑分”里剥离出来，识别出正确性、性能归因、分布外泛化这三个彼此不可替代的命题；其二，能否为每个命题给出可执行的评测侧动作（正确性 oracle、profile 归因）与部署侧动作（回归门禁、收益核算），并说明二者的接口；其三，能否划清与相邻方向的分工——生成侧管搜索与采样，训练侧管 RL 与奖励建模，本方向只管“判据与证据链”。解题路径是先列命题表，再为每条命题标注判据来源、证据形态与失效条件，最后用分工矩阵收口。

边界在于：本方向不产出 kernel，也不定义奖励函数的具体形状，只定义“什么算通过”。失效条件是判据本身可被优化器利用——若正确性 oracle 只覆盖有限形状，agent 会收敛到对该形状过拟合的 kernel；若性能归因只取端到端时延，则会把编译时间、预热开销误记为 kernel 收益。系统代价体现在评测吞吐：每增加一条 oracle 分支就多一次编译与启动，token 与 GPU 时延随之上升。

$$\text{可判定性} = \frac{\text{覆盖的输入族}}{\text{判据分支数}} \times \frac{1}{\text{单次评测时延}}$$
命题判据来源失效条件
正确性多形状 oracle 对比形状覆盖不足
性能归因NCU/SASS 计数端到端时延混入编译开销
分布外泛化未见形状族基准族泄漏进训练

具体例子：题干要求“评测侧与部署侧各两条”，若只答“加测试、加监控”即失分，因为未给出判据与证据形态的对应；正确拆解应指出评测侧的正确性 oracle 需与部署侧的回归门禁共享同一输入族定义，否则两侧判据漂移，收益核算失去可比性。
