一 · 题干的三层结构：从论文标题反推可评测对象

《LLM4LLM: Bridging Kernel Benchmarks and Real Deployment via Closed-Loop Agentic Optimization》这个标题本身就是一个三层断言，读题时必须把它拆成三个可分别验证的命题，而不是当成一个整体口号。第一层是“Kernel Benchmarks”——存在一类以 KernelBench 系为代表的基准，它们用算子级任务（如 matmul、softmax、layernorm、attention 变体）配合参考实现与正确性比对来度量生成能力；第二层是“Real Deployment”——基准分数与真实部署收益之间存在鸿沟，鸿沟的来源是输入分布、端到端上下文、框架约束与硬件状态；第三层是“Closed-Loop Agentic Optimization”——用 agent 在多轮中读取执行反馈（编译错误、正确性失败、NCU/SASS profile 指标），据此修改 kernel，形成闭环。考点的关键不在于复述这三层，而在于识别出：论文要主张的是“闭环能把第一层的分数转化为第二层的收益”，因此任何评测 harness 都必须同时钉住“基准侧可复现”与“部署侧可归因”两个锚点，否则闭环的增益无法被证伪。

把标题拆成命题后，题干中的“可复现评测 harness”就对应四个必须显式定义的构件：基线（baseline）、输入分布（input distribution）、正确性门（correctness gate）、防作弊与上线门（anti-cheat & deployment gate）。这四者不是并列的清单，而是有依赖顺序的：输入分布决定正确性门的判定域，正确性门决定防作弊的搜索空间，基线决定上线门的比较基准。读题时若把四者当独立项分别配置，就会得到一套自洽但无法归因的 harness——例如基线用了 PyTorch eager 而输入分布用了基准默认 shape，那么“上线收益”里混入了 shape 选择带来的收益，闭环的贡献被稀释。

一个具体机制上的考点：论文的闭环依赖执行反馈，而执行反馈的粒度直接决定 agent 能修正什么。编译错误是二值信号，正确性失败可给出最大误差位置，NCU profile 给出带宽/占用率/指令混合。三者对应不同的修正动作：编译错误只能改语法与类型，正确性失败可改索引与归约顺序，profile 才能引导 tiling 与流水。harness 若不记录反馈的粒度与来源，就无法区分“agent 靠正确性信号修好了 bug”与“agent 靠 profile 调优了性能”，而这正是闭环论文最需要区分的两类增益。

$$\text{Gain}_{\text{loop}} = \frac{T_{\text{deploy}}(K_{\text{agent}})}{T_{\text{deploy}}(K_{\text{base}})} \quad\text{s.t.}\quad \text{Correct}(K_{\text{agent}})=\text{True},\ \text{Dist}_{\text{eval}}\subseteq\text{Dist}_{\text{deploy}}$$

这个式子的代价在于：约束项要求评测分布是部署分布的子集，实践中这意味着一部分基准任务必须被排除或重加权，从而降低基准分数的可比性；同时正确性门为 True 是硬约束，任何为了性能放宽容差的动作都会使 Gain 失去意义。token 代价上，闭环每轮都要把反馈序列化进上下文，profile 文本远长于编译错误，因此“允许 agent 看 profile”这一配置会显著抬高每任务的 token 消耗，harness 必须把这一项计入成本而非只计 wall-clock。

二 · 输入分布：基准默认 shape 与部署 shape 的错位是主要考点

KernelBench 系基准的任务定义通常固定一组 shape 与 dtype，而真实部署的 shape 来自模型配置与批调度，二者错位是“基准分数不转化为部署收益”的第一大来源。读题时要问：论文的闭环是否在输入分布上做了显式对齐？如果没有，harness 必须自己定义三套分布并分别报告——基准默认分布、部署采样分布、以及二者的交集。只报告单一分布会让上线门的比较基准漂移。

具体机制上，输入分布要参数化为一个可复现的采样器：固定随机种子、固定 shape 集合、固定 dtype 与 layout（row-major 还是转置）、固定数值范围（是否含 NaN/Inf、是否含极端小值以触发下溢）。对 reduction 类算子，还要固定归约维的长度是否对齐 warp/CTA 边界，因为这直接决定生成 kernel 的 tiling 策略是否在部署 shape 上退化。一个具体例子：layernorm 在基准里常用 hidden=1024、batch 较小，而部署中 hidden 可能是 4096 且 batch 动态；若 harness 只用基准 shape，agent 优化出的向量化宽度在部署 shape 上可能因寄存器压力而降低占用率，profile 上的带宽利用率反而下降。

代价方面，扩大输入分布会线性抬高评测时延与显存占用：每个 shape 都要跑参考实现与候选实现，参考实现通常是 PyTorch，显存峰值由最大 shape 决定。若 harness 为覆盖部署分布而加入大 batch，单次评测的显存需求可能超过基准任务的数倍，导致并行评测的并发度下降，整体 wall-clock 上升。token 代价上，输入分布若以列表形式进入 agent 上下文，shape 数量越多上下文越长，且 agent 容易对特定 shape 过拟合而非学到通用策略——这正是防作弊门要处理的。

分布维度基准默认部署采样harness 处理
shape固定集合动态、含边界值两套分别跑，报告交集
dtype/layoutfp32/fp16 固定混合精度、转置输入layout 作为独立因子
数值范围常规随机含极端值单独正确性子集

工程判断：输入分布的定义必须写进 harness 的配置文件并与 kernel 源码一起版本化，否则“同一 agent 在同一基准上分数不同”无法归因于是分布变了还是 agent 变了。这是可复现性的最低要求，也是读题时最容易被忽略的考点。

三 · 正确性门：容差、参考实现与判定域三者必须同时钉死

正确性门是 harness 的核心，也是最容易被 agent 钻空子的地方。读题时要区分三个独立决策：容差（tolerance）怎么定、参考实现（oracle）用谁、判定域（哪些输入参与判定）覆盖多大。三者任一松动都会让“正确”变成可协商的形容词。

具体机制上，容差应按 dtype 与算子数值特性分层：fp32 的 matmul 可用相对误差加绝对误差的混合判据，fp16/bf16 需要按累加长度放大容差，reduction 类算子要单独处理归约顺序带来的非确定性。判定域要区分“全量比对”与“抽样比对”：全量比对代价是每个输出元素都要读回 host，带宽与同步开销大；抽样比对快但可能漏掉局部错误。一个具体例子：softmax 的候选实现若在某一行的最大值上做了近似，全量比对能抓到该行的分布偏移，而只比对行和（sum≈1）则会放过——因为行和仍为 1。因此判定域必须包含逐元素比对，而不能只保留统计量。

参考实现的选取同样是考点：用 PyTorch eager 作 oracle 会引入框架自身的数值行为（如不同的归约树），导致候选 kernel 在数学上正确却被判错；用高精度 CPU 实现作 oracle 更严格但评测时延显著上升。harness 应记录 oracle 的类型与版本，并把“候选与 oracle 的差异”与“oracle 与数学定义的差异”分开报告，否则无法判断失败是候选的错还是 oracle 的噪声。

$$\text{pass} = \bigwedge_{i\in\mathcal{D}} \left( |y_i-\hat{y}_i| \le a + r\,|\hat{y}_i| \right),\quad \mathcal{D}=\mathcal{D}_{\text{full}}\cup\mathcal{D}_{\text{edge}}$$

代价：全量判定域使每次评测都要 device-to-host 拷贝全部输出，对大规模输出（如 attention 的完整分数矩阵）带宽开销不可忽略，且强制同步会破坏评测流水线；容差收紧会提高假阴性率，把数值上可接受的 kernel 判错，进而让 agent 在闭环中反复“修复”不存在的错误，浪费轮次与 token。工程上常见的折中是分层判定：先用抽样快速筛掉明显错误，再对通过者做全量比对，但这一折中本身要写进 harness 文档，否则复现者会误以为全量是默认。

四 · 防作弊门：agent 可触及的搜索空间必须被显式封闭

闭环 agent 的作弊面比单轮生成大得多，因为它能读反馈、能多轮修改、能看见评测代码。读题时要枚举 agent 可能利用的通道：读取参考实现、缓存上一次的输出、针对评测 shape 特化、修改评测脚本、在 kernel 里检测输入特征后走不同分支。防作弊门的目标不是“禁止一切优化”，而是把“合法优化”与“绕过判定”分开。

具体机制上，harness 应做到：参考实现与评测脚本对 agent 不可读（沙箱隔离），候选 kernel 在独立进程中编译与运行，输入在运行时生成且种子对 agent 不可见，输出比对在 agent 进程之外完成。对“针对 shape 特化”，可接受但需标记——因为特化本身是合法优化手段，问题在于它是否在部署分布上仍然正确；因此防作弊门应与输入分布联动，用未公开的 held-out shape 做二次判定。一个具体例子：候选 kernel 若在检测到某一 shape 时直接返回预计算的常量张量，held-out shape 会使其失败；但若它只是为常见 shape 选了更优的 tiling，held-out shape 仍能通过，二者由此区分。

代价：沙箱隔离与独立进程会引入进程启动与 IPC 开销，每任务的评测时延上升；held-out shape 使评测覆盖翻倍，显存与时延同比例增加。token 代价上，防作弊要求 agent 看不到评测代码，意味着反馈信息必须由 harness 摘要后注入，摘要本身可能丢失定位错误所需的信息，降低闭环的修正效率——这是安全性与样本效率之间的直接 trade-off，harness 必须显式记录摘要策略。

  • 封闭通道：参考实现不可读、评测脚本不可写、种子不可见。
  • 二次判定：held-out shape 与 held-out dtype 各一组。
  • 行为审计：记录候选是否读取输入统计量并分支。
  • 版本锁定：kernel 源码、harness 配置、oracle 版本三者绑定哈希。

五 · 上线门：端到端收益必须可归因，而非基准分数的线性外推

上线门回答的是“这个 kernel 值不值得进部署”。读题时要拒绝把基准加速比直接当上线收益，因为端到端时延里包含框架调度、内存分配、kernel launch、数据搬运与同步，算子级加速在这些项面前会被稀释。上线门必须定义端到端测量口径：测什么模型、什么 batch、什么精度、是否含前后处理、是否含首次编译/autotune 的冷启动。

具体机制上，上线门应做消融式归因：固定其他算子，只替换目标算子，测端到端时延差；同时记录该算子占总时延的比例，若占比过小，即使算子级加速显著，端到端收益也在测量噪声内。一个具体例子：一个 attention 变体在基准上相对 eager 有明显加速，但部署中该层只占端到端时延的小部分，替换后总时延变化落在噪声区间，此时上线门应判“不显著”而非“有收益”。这要求 harness 具备重复测量与方差报告，而非单次计时。

$$\text{DeployGain} = \frac{T_{\text{e2e}}(K_{\text{base}})-T_{\text{e2e}}(K_{\text{agent}})}{T_{\text{e2e}}(K_{\text{base}})},\quad \text{report}\ \text{CI}_{95\%}\ \text{and}\ \text{share}=\frac{T_{\text{op}}}{T_{\text{e2e}}}$$

代价：端到端测量需要完整模型与真实输入，显存占用远高于算子级评测，且冷启动（编译、autotune、cuDNN 算法选择）会污染首次测量，harness 必须区分冷/热启动并分别报告。时延上，端到端重复测量次数受限于单次运行成本，方差估计的置信区间可能偏宽，导致上线门在小收益上无法给出确定判断——这时工程判断应是“不显著即不上线”，而不是用基准分数补位。token 代价在此处体现为报告长度：归因需要把算子占比、方差、冷热启动分开写，报告越长，人工复核成本越高。

六 · 解题路径：把四个构件串成一条可执行的验收链

读题的落点是给出一条可执行的路径，而不是四个孤立配置。路径的顺序应是：先定输入分布（因为它定义判定域），再定正确性门（因为它定义合法解空间），再定防作弊门（因为它封闭搜索空间），最后定基线与上线门（因为它们定义收益的比较基准）。这个顺序不可颠倒：若先定基线再定分布，基线会在错误的分布上测，后续所有比较都失效。

具体机制上，harness 的配置应是一个结构化文件，字段包括：分布采样器（种子、shape 列表、dtype、layout、数值范围）、oracle（类型、版本、容差分层）、判定域（全量/抽样、edge 子集）、沙箱策略（可读/可写资源）、held-out 集合、基线（框架、版本、是否 eager/编译）、端到端测量（模型、batch、冷热启动、重复次数）。每个字段都要有默认值与覆盖规则，且默认值本身要被文档化为“可复现的最小集”。一个具体例子：若某任务在基准默认 shape 上通过但在 held-out shape 上失败，harness 应输出“分布外失败”而非“正确性失败”，因为二者的修正动作不同——前者要求 agent 泛化，后者要求 agent 修 bug。

公式层面，验收口径可写成一个合取式：基准侧要求正确性门通过且相对基线有加速，部署侧要求端到端收益的置信区间下界为正且算子占比足够大，防作弊侧要求 held-out 集合全部通过。三者同时满足才判“可上线”，任一不满足则输出对应的失败类别，供闭环下一轮定向修正。代价是这套合取式使通过率显著低于单看基准分数，且失败类别的细分会增加报告与人工复核的时延；但正是这种严格性使闭环的增益可归因，否则“分数涨了”无法回答“涨在哪里”。

最后落在工程判断上：这套 harness 的价值不在于给出一个分数，而在于把“基准通过”与“部署有效”之间的每一步都变成可观测的中间量——分布是否对齐、正确性是否在判定域内成立、agent 是否越界、收益是否超出噪声。闭环 agent 的优化能力越强，harness 越要把这些中间量显式化，否则 agent 会优化 harness 没有钉住的那部分，而论文主张的“桥接”就退化为基准分数的另一种表述。
