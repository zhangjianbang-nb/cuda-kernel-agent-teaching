一 · 题干的三层结构：从“加速比”这个词拆出三个待答子问题

“Kevin 报告的加速比如何计算”这句话看似一问，实则是三问叠在一起，拆不开就会答偏。第一层是定义层：speedup 这个标量在论文里由哪两个量相除得到，分子分母各自对应什么被测对象。第二层是口径层：这两个量在什么测量条件下取得——是单次 kernel 调用还是端到端模型前向，是否含编译、是否含数据搬运、是否含 warmup、计时用的是 CUDA event 还是 wall clock。第三层是可比性层：即便公式写对，什么样的跨论文、跨硬件、跨输入规模的数字放在一起就是不可比的。答题时若只写 $$S = T_0 / T_1$$ 就交卷，等于只回答了第一层，而这道题的考点恰恰压在第二、三层上。读题第一步应把“如何计算”显式改写为“在何种测量协议下、对哪一对被测对象、用何种计时手段得到两个时延，再相除”，这样后续每一句论述都能落到具体机制上，而不是停在公式表面。

具体到本题给定的事实，题干只锚定了两个符号：基线时延 T0、候选时延 T1，以及“论文给出的口径”这一约束。这意味着解题路径必须包含一次口径核对：把论文自己声明的测量边界复述清楚，再据此判断哪些外部数字能与它对齐。考点因此可以归为三类：公式书写是否正确（定义层）、口径描述是否完整（口径层）、不可比条件的列举是否有机制支撑（可比性层）。三者权重不同，第三层最容易失分，因为它要求考生理解“同一个 speedup 数值在不同测量边界下指向不同的物理量”。

二 · 公式本身：T0 与 T1 各自是什么，分母里藏了什么

最简形式是 $$S=\frac{T_0}{T_1},\qquad T_1<T_0 \Rightarrow S>1$$，其中 T0 为基线实现的时延，T1 为候选 kernel 的时延。公式一行写完，但两个符号的指称才是考点。T0 必须明确是“哪个基线”：是 PyTorch eager 的算子组合、是 torch.compile 产物、还是某个手写 CUDA 参考实现——不同基线给出的 T0 相差可达数量级，而论文若未声明基线版本与后端，读者无法复现该比值。T1 同理，要区分“单次 kernel launch 的 device 时间”与“含 host 侧调度、含 Python 开销的端到端时间”。

分母里还常藏一个不易察觉的项：计时是否包含编译与 autotune。若 T1 取的是 steady-state 下多次迭代的均值，则首次 JIT 编译、Triton autotune 的候选搜索、CuTe 模板实例化都被摊掉；若 T1 取的是首次调用时延，则这些一次性成本全额计入，S 会被显著压低。这不是细枝末节：对 Triton 与 CuTe 路线，编译/实例化开销在冷启动场景下足以让“加速”变成“减速”，因此口径描述里必须写明 warmup 次数与是否剔除首次调用。工程判断上，把 $$T_1 = \frac{1}{N}\sum_{i=1}^{N} t_i^{(\text{steady})}$$ 与 $$T_1^{\text{cold}} = t_{\text{compile}} + t_{\text{first}}$$ 分开报告，比只给一个 S 更能说明候选 kernel 的真实可用性。

代价维度也要在公式旁标注：T1 的测量本身消耗 GPU 时间与显存，若候选 kernel 依赖较大 workspace，则计时期间的显存驻留会影响同卡其他任务；若用 CUDA event 计时，event 插入带来的同步会截断异步流水，测得的 T1 可能略高于真实吞吐对应值。这些都属于“公式对但数字含义偏移”的情形，答题时应作为口径的一部分写出，而不是当作实现细节略过。

三 · 口径核对：论文声明的测量边界决定了 S 的物理含义

题干要求“结合论文中的口径说明这个数字在什么条件下不可比”，这里的动作是先复述、再划线。复述部分应准确交代：T0 与 T1 是否在同一 GPU 型号、同一驱动与 CUDA 版本、同一输入 shape 与 dtype、同一 batch 配置下测得；计时是否隔离了数据搬运（H2D/D2H）；是否固定了 clock、是否开启了持久化 L2；是否报告了多次运行的方差而非单次最优值。划线部分则指出：一旦上述任一条件在对比对象之间不一致，S 就不再是同一物理量的比值。

举个具体例子说明不可比的机制。设某候选 kernel 在 shape A 下相对 PyTorch 基线取得 S>1，而另一份报告在 shape B 下相对同一基线取得更大的 S。若两份报告的 shape 不同，则两者的 T1 分别对应不同的 occupancy 与不同的 memory-bound/compute-bound 区段，S 的差异主要来自 roofline 上工作点的移动，而非 kernel 质量差异；此时把两个 S 并列比较，等于把“工作点选择”误读为“实现优劣”。同理，若一方 T0 取 eager、另一方 T0 取 torch.compile，则分母基线强度不同，S 的高低更多反映基线选择而非候选改进。答题时把这类“变量未锁定”逐条列出，比笼统说“条件不同不可比”更有分量。

还需注意口径中的聚合方式：论文若报告的是多组 shape 上的几何平均或算术平均 S，则单组数据的极端值会被平滑，读者无法从均值反推任一具体配置下的表现；若报告的是最优组，则 S 带有选择偏差。这两种聚合在口径描述里必须点明，否则“论文报告的加速比”本身就是一个未定义统计量的点估计。代价层面，聚合与逐组报告之间的取舍是 token 与篇幅：逐组报告信息量大但占版面，均值报告紧凑却丢失分布，工程读者应据此后验地判断该数字能否迁移到自己的负载。

四 · 可比性判据：把“不可比”写成可检验的条件清单

把不可比条件写成清单，是这道题拿分的关键形态。可检验的判据至少包括：硬件同一性（GPU 型号、SM 数、显存带宽、clock 策略）、软件栈同一性（CUDA/driver、框架版本、编译选项如 -O3 与 arch 指定）、被测对象同一性（基线实现与候选实现的边界是否都止于 kernel，还是都含框架调度）、输入同一性（shape、dtype、layout、是否含 mask/变长）、计时协议同一性（warmup、迭代数、event vs wall clock、是否剔除首次编译）。每一条都能用“是/否一致”回答，从而把定性讨论转成可核对的表。

判据一致时 S 可比不一致时的失真机制
GPU 型号与 clock是带宽与 SM 数变化直接改变 memory-bound kernel 的 T1
基线实现是eager 与 compile 的 T0 差距使 S 反映基线而非候选
输入 shape/dtype是工作点在 roofline 上移动，S 变成工作点函数
计时是否含编译是冷启动 T1 含 JIT/autotune，S 被一次性成本稀释
聚合方式是均值/最优掩盖分布，S 不可反推单配置

这张表的作用是把“不可比”从形容词变成判据集合。答题时若能在每条判据后补一句该判据影响的是 T0 还是 T1，论述就具备了机制支撑。例如“计时含编译”影响的是 T1 的分子项构成，使 S 的分母被一次性开销抬高，从而系统性低估稳态加速；而“基线实现不同”影响的是 T0，使 S 的分子被弱基线放大，系统性高估候选收益。两种失真的方向相反，混在一起谈会掩盖问题。

五 · 解题路径：从符号到判据的四步走，以及每步的验证动作

给出路径而不给答案，意味着要写清“先做什么、用什么证据、在哪一步停下核对”。第一步锁定符号指称：为 T0、T1 各写一句定义，明确被测对象边界与计时手段；验证动作是检查论文是否在同一段里声明了这两点，若分散在不同章节则需交叉引用。第二步写出公式并标注假设：在 S=T0/T1 旁注明 steady-state、warmup 已剔除、单 kernel 边界；验证动作是确认 T1 的统计量是均值还是最优。第三步复述论文口径：把硬件、软件栈、输入、聚合四项逐条摘出；验证动作是对照表格判据打勾。第四步给出不可比条件：对每个未锁定变量写出失真方向（高估或低估）与影响的是分子还是分母。

这四步的代价在于时间与信息可得性：口径核对要求读者真的去翻实验设置小节，而不是只读摘要里的 S；若论文未报告方差或未声明 warmup，则第三步只能标注“口径不完整”，此时应把不确定性显式写出而非用“大概”填补。工程判断上，一个只给单点 S、不给测量协议的 kernel 报告，其可信度低于给出逐组时延与方差、并声明基线的报告——这不是苛求，而是因为 S 作为比值对分母极其敏感。答题时把“口径完整性”本身作为一个评价维度提出，比单纯复述公式更贴近这道题的考点。

需要调用的公式除 S=T0/T1 外，还应备好两个辅助式以便在口径讨论中引用：其一是算术/几何平均聚合 $$S_{\text{arith}}=\frac{1}{K}\sum_{k=1}^{K}\frac{T_{0,k}}{T_{1,k}},\qquad S_{\text{geo}}=\Big(\prod_{k=1}^{K}\frac{T_{0,k}}{T_{1,k}}\Big)^{1/K}$$，用于说明论文报告的“平均加速比”是哪个统计量；其二是冷启动修正 $$S_{\text{cold}}=\frac{T_0}{t_{\text{compile}}+t_{\text{first}}}$$，用于说明含编译口径下 S 的构成。两式都不需要具体数值即可写出，符合“只给路径不给答案”的要求。

六 · 一个具体例子的走查：同一 S 值在两种口径下的不同所指

设某候选 kernel 相对基线在稳态下测得 S=2，且论文声明该值来自单 kernel 边界、warmup 后多次迭代均值、同一 GPU 与同一 shape。此时 S=2 的物理含义是：在该 shape 对应的工作点上，候选 kernel 的 device 时间约为基线的一半。若另一份报告在相同硬件上对同一候选测得 S=1.2，差异可能来自三处：其 T0 取了更强的基线（如 torch.compile），使其分子变小；其 T1 含首次编译，使分母变大；或其 shape 落在 memory-bound 区段而前者落在 compute-bound 区段。三者都能让同一个候选 kernel 给出不同的 S，而候选本身未变。这个走查说明：S 不是 kernel 的固有属性，而是“候选、基线、工作点、计时协议”四元组的函数。

因此答题时对“不可比”的表述应落到四元组上：只要两份报告的基线、工作点、计时协议中任一不同，其 S 就不能直接比较；硬件不同则连 T0 与 T1 的绝对量都不可迁移。工程上可操作的做法是要求报告同时给出 T0、T1 的绝对值与测量协议，使读者能自行重算 S 并判断是否与自身负载对齐；只给比值不给绝对时延的报告，读者无法做这项核对。这一判断落在具体机制上——比值丢失了分母信息，而分母恰是口径差异最敏感的地方。

加速比口径的边界：T0/T1 何时才可比

Kevin 一类多轮 RL 工作里，加速比几乎总是被写成 $$\text{speedup}=\frac{T_0}{T_1}$$，其中 T0 是基线（通常是 PyTorch eager 或某个参考实现）的时延，T1 是候选 kernel 的时延。这个式子在数学上平凡，工程上却极易被误读：它把“同一输入、同一语义、同一测量口径”三个前提全部隐式吞掉了。读题时必须先把这三个前提拆出来，否则 T0/T1 只是两个来源不明的浮点数之比。论文给出的口径本身是有条件的——它绑定在固定的输入形状、固定的数据类型与固定的计时方式（含或不含 warmup、是否同步、是否计入 launch 开销）之上，一旦候选 kernel 换了 tile 尺寸或走了不同的融合路径，T1 的测量边界就与 T0 不再对齐。

失效条件可以列成一张小表，逐条对应“不可比”的来源：

条件对 T0/T1 的影响代价形态
输入形状偏离基准T1 的最优 tile 失效，比值虚高或虚低时延
基线未做同等融合T0 被高估，speedup 系统性偏大时延、可信度
计时含/不含 launch 与同步小 kernel 上 T1 被低估时延、token（重测成本）
数值精度路径不同语义不等价，比值无意义正确性

具体例子：一个 reduction kernel 在基准形状上把 T1 压到 T0 的若干分之一，但候选实现把中间累加从 fp32 换成 fp16，此时 T0/T1 虽然好看，正确性 oracle 的容差检查会直接判负——加速比在语义不等价时没有定义，必须先过正确性再谈比值。另一个例子是候选 kernel 把多次小 launch 合并成一次，T1 的下降里有相当部分来自 launch 开销的摊薄，而 T0 的基线若按逐 op 计时，则两者测量的根本不是同一段工作。

因此解题路径应当是：先锁定基准的输入域与计时协议，再判断候选是否在同一协议下测量，最后才允许把 T0/T1 写进结论。系统代价在于，严格对齐口径意味着每一轮候选都要重跑基线计时并做正确性校验，这会拉长多轮 RL 的反馈回路、增加 token 与编译时间开销；而放松口径换来的“更高加速比”只是评测噪声。工程判断是：把 speedup 当作受约束的观测量而非自由标量，口径不一致时宁可报“不可比”，也不要把两个不同测量边界的数相除。
