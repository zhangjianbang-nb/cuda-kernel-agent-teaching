一 · 题干的三层结构：从“写一个 kernel”到“证明它值得被采纳”

《KernelBenchX》这类基准的题干不是一句“实现算子 X”，而是一个三层嵌套的命题。第一层是功能层：给定输入形状、dtype、layout、边界条件（是否含 padding、是否含 mask、是否允许原地写），候选 kernel 必须产生与参考实现逐元素一致的输出。第二层是性能层：候选要在同一硬件、同一输入分布下，相对某个基线实现取得加速。第三层是可比性层：这个加速比必须在明确的口径下成立——基线是谁、计时包含什么、是否允许跨轮缓存、是否计入编译与 autotune 开销。读题时若只拆第一层，就会写出“正确但无意义”的 kernel；若跳过第三层，就会得到一个无法与他人的数字并列的 speedup。

因此解题路径的第一步不是写代码，而是把题干重写成一张契约表：输入域（shape 集合与 dtype）、参考语义（允许的误差界，浮点是否按 bit 对齐）、基线定义（T0 取自哪里）、计时协议（warmup 次数、是否同步、是否用 CUDA event 还是 wall clock）、资源约束（显存上限、是否允许多 kernel 融合）。这张表决定了后面所有优化方向的合法性。一个具体例子：题干要求对形如 (B, S, H) 的张量做 masked softmax，若契约表里没写“mask 为加性 -inf 还是布尔掩码”，候选就可能用错分支，正确性 oracle 直接判负，性能再高也无意义。

代价在这里已经出现：契约表越严，搜索空间越小。把误差界从 1e-2 收紧到 bit-exact，会排除掉所有依赖重排求和顺序的 reduction 变体，等于放弃了 shared memory 树形归约这条主要路径；把计时协议要求“含首次编译”写进题干，则 Triton 的 JIT 开销会直接吃掉小 shape 上的全部收益。这是读题阶段必须付出的判断成本。

二 · 加速比公式与它的四个隐藏参数

基准报告的加速比定义为基线时延与候选时延之比：

$$\text{speedup}=\frac{T_0}{T_1},\qquad T_0=\text{baseline latency},\; T_1=\text{candidate latency}$$

这个式子只有两个符号，却隐含四个未写出的参数：测量对象（哪个 shape、哪个 batch）、测量环境（GPU 型号、时钟是否锁定、是否与其他进程共享）、测量边界（是否含 kernel launch、是否含 host-device 拷贝、是否含 Python 调度）、测量统计量（中位数、均值还是最小值）。任何一篇报告给出的单个 speedup 数字，都是这四个参数的一次取值。把它们省略，数字就退化为不可复现的口号。

论文中出现的 9.4、3.3、72、52.3、68.8、46.6 这组数字，正是“同一公式、不同取值”的典型样本。它们的量级跨度从个位数到七十量级，说明这些数字并非在同一条件下取得：9.4 与 3.3 属于温和加速，通常对应候选与基线在同一抽象层级上的竞争（例如都是手写 CUDA，差距来自 tiling 与 occupancy）；而 72、68.8、52.3、46.6 这种量级，只有在基线本身处于极不利位置时才成立——例如基线是未经融合的 PyTorch 多算子组合、是朴素逐元素实现、或是在小 shape 上被 launch 开销与框架调度支配的实现。此时分子里的 T1 已经接近硬件下限，分母里的 T0 却包含大量非 kernel 时间，比值放大的是“框架税”而非“kernel 质量”。

所以判断一个 speedup 是否可比，要问三个问题：T0 是不是同一个基线实现？T1 的计时是否排除了编译与 autotune？两者的输入 shape 与 dtype 是否一致？三者任一不同，9.4 和 72 就不能放进同一张表里排序。工程上的处理办法是把 speedup 拆成两个可分别核对的量：kernel 自身的 SOL 利用率（相对 roofline 上限）与端到端时延比（相对基线）。前者跨实现可比，后者只在固定基线时可比。

三 · 考点拆解：基准真正在测什么

把题干拆到考点层，会发现 KernelBenchX 类基准的评分维度不止“快”。可归纳为四类考点，每类都对应一种可被 agent 利用或误用的机制。

  • 语义正确性：以参考实现为 oracle，覆盖边界 shape、非连续 stride、极端值（inf/nan 传播）、dtype 混合。考点在于候选是否处理了 reduction 的结合律误差与 mask 语义。
  • 性能相对基线：即上面的 speedup，考点在于候选是否识别出基线的瓶颈位置（是访存受限还是 launch 受限），并选择了匹配的优化手段。
  • 资源与可部署性：显存占用、是否引入额外 kernel、是否依赖特定架构特性（如 TMA、warp specialization）。考点在于候选在受限显存或旧架构上是否仍然成立。
  • 可验证性：候选是否自带可复现的计时脚本与正确性检查，使第三方能在不读代码的情况下复核数字。

这四类考点的权重不是均等的：正确性是门槛项，一项不过则整题归零；性能是排序项；资源与可验证性是区分“能跑”与“能部署”的分界。一个具体的反例：候选在 (4096, 4096) 的方阵上把 GEMM 加速到基线的数倍，但在 (1, 4096) 的瘦长 shape 上因 tile 划分退化而慢于基线——若题干未声明 shape 分布，这个候选的“平均加速比”就是采样偏差的产物。这正是基准设计里 shape 集合必须显式写出的原因。

代价方面，考点越细，评测成本越高：每增加一个 dtype 组合与一个边界 shape，正确性 oracle 的调用次数线性增长，而每次调用都要跑参考实现，参考实现本身可能是慢的 PyTorch 路径，于是验证阶段的时延可能超过候选 kernel 的运行时延几个数量级。这是“可信评测”的固有开销，不能靠抽样绕开，只能靠缓存参考输出与按 shape 分层抽样来控制。

四 · 解题路径：从 roofline 反推到实现选择

读题之后的第一条技术路径是判定算子属于哪一类受限，公式为：

$$\text{arithmetic intensity}=\frac{\text{FLOPs}}{\text{Bytes moved}},\qquad \text{attainable}=\min\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right)$$

若算子的 arithmetic intensity 低于硬件的 ops:byte 拐点，它是访存受限，优化路径应落在合并访存、向量化宽度、减少冗余读写、把中间结果留在寄存器或 shared memory；若高于拐点，它是计算受限，路径落在提高 ILP、使用 tensor core、减少分支与同步。这个判定必须在写第一行代码前完成，否则会出现在访存受限的算子上堆砌 FMA、或在计算受限的算子上反复调 tile 大小的徒劳循环。

第二条路径是基线解剖：把 T0 拆成 kernel 时间、launch 时间、框架调度时间三部分。若 launch 占比高（小 shape 常见），正确解法是融合或使用 CUDA Graph 批量提交，而不是优化 kernel 内部；若 kernel 时间占主导且已接近 roofline，则加速空间只剩算法级重写（例如把两遍 reduction 改为单遍在线算法）。一个具体例子：LayerNorm 在 S 较小、H 较大时是访存受限，基线若由 mean、var、normalize 三个独立 kernel 组成，则 T0 里包含三次全量读写；候选若用单 kernel 在线计算均值方差并原地归一化，访存次数从三倍降到一倍，speedup 上限直接由带宽比给出，而不是靠指令级调优。

第三条路径是误差预算：浮点归约的树形结构改变求和顺序，误差随 log 深度增长；若题干要求 bit-exact，则只能复刻参考实现的归约顺序，性能上限被锁死。这里的代价是可量化的：放弃重排意味着放弃 shared memory 并行归约带来的带宽利用，候选的 attainable 时延可能比自由重排版本高出一个可测的比例。解题时必须先确认误差界，再决定是否值得走这条路。

五 · 需要调用的公式与它们的适用边界

解题路径上真正需要动笔的公式不多，但每个都有明确的适用边界，误用即错。

公式用途适用边界与代价
speedup = T0 / T1性能排序仅当基线、shape、计时边界一致时可比；否则只反映框架税
attainable = min(FLOPs/P, Bytes/B)判定受限类型与性能上限需真实统计 Bytes moved，含被 cache 命中的部分要按层级折算
occupancy = active warps / max warps判断延迟隐藏能力高 occupancy 不等于高吞吐；寄存器压力与 shared memory 会反向限制
error ~ O(u · log n)归约误差预算仅适用于树形归约；串行累加误差为 O(u · n)，两者不可混用

以 occupancy 为例，它的代价是双向的：提高 occupancy 需要压低寄存器用量，而压低寄存器往往意味着把本可留在寄存器里的中间量溢出到 local memory，反而增加访存。一个具体场景是 GEMM 的 register tiling：把每线程累加器从 8×8 降到 4×4 可以提高 occupancy，但每个输出元素的 global load 次数上升，在访存受限的小矩阵上净收益为负。这类权衡无法靠单一公式判定，必须结合 attainable 与实测带宽共同判断。

误差公式的边界同样关键：O(u · log n) 只在平衡树归约下成立；若候选为了并行度采用了分块部分和再二次归约的结构，误差常数会随分块数变化，此时应把分块数作为误差预算的一个显式变量写进契约表，而不是笼统引用对数界。

六 · 不可比条件的识别：把 9.4 与 72 分开看

回到题干的核心问题：给定 T0 与 T1，speedup 公式本身没有歧义，歧义全部来自 T0 与 T1 的取法。识别不可比条件，本质是识别“分母被注水”或“分子被优待”的情形。

  • 基线层级不同：T0 取自 eager 模式的多算子组合，T1 是融合后的单 kernel。此时 speedup 度量的是融合收益，而非 kernel 实现质量；同一候选若与已融合的基线比较，数字会大幅缩水。
  • 计时边界不同：T1 排除了 JIT 编译与 autotune，T0 却包含框架首次调度。在小 shape 上，这一项可以主导整个比值，使 72 这类数字失去意义。
  • shape 与 dtype 不同：候选在宽 shape 上取胜、在窄 shape 上退化，若报告只取前者，speedup 是采样选择的结果。
  • 硬件与时钟状态不同：未锁频、共享 GPU、热降频都会让 T0 偏大，从而抬高比值。

工程判断的落点是：任何单个 speedup 数字都必须附带它的四元组（基线实现、shape 集合、计时边界、统计量），否则只能作为定性证据。9.4 与 3.3 这类温和数字，通常意味着比较发生在同一层级、计时边界对齐，因而更接近“kernel 质量”的真实度量；72 与 68.8 这类数字则应优先怀疑分母注水，直到四元组被完整披露。把这两组数字并列排序，是把不同口径的测量混为一谈——这正是 KernelBenchX 强调报告口径而非只报告比值的原因。

因此读题阶段的最后一个动作，是把候选的评测脚本反向写成契约：明确 T0 取自哪个 commit 的哪个实现、T1 的计时是否用 CUDA event 包裹且前后同步、warmup 与重复次数是否固定、shape 集合是否覆盖退化情形。只有当这些字段与题干一致，T0/T1 才是一个可比较的量；否则再大的数字也只是分母的注水高度。

加速比读数的可比性边界：从 T0/T1 到论文里的 9.4、3.3、72

题干给的是「报告的加速比如何计算」，考点却落在「这个数字在什么条件下不可比」。先把公式钉死：

$$\mathrm{speedup}=\frac{T_0}{T_1}$$
其中 T0 是基线时延、T1 是候选时延。工程上真正要拆的是 T0 与 T1 各自测的是什么：T0 是 PyTorch eager 参考实现、torch.compile 版本，还是某个手写库函数；T1 是否含 kernel launch 开销、是否含 host-device 同步、是否只计 GPU 事件区间。分子分母口径不一致，比值就失去意义。解题路径是先对齐计时区间（同一 warmup、同一 stream、同一 dtype/shape 分布），再判断候选是否落在同一语义契约内。

论文中出现的 9.4、3.3 与 72、52.3、68.8、46.6 属于不同量级的读数，不能放进同一张排行榜。9.4 与 3.3 这类个位数加速比通常对应计算密度高、基线已接近硬件上限的算子，候选只能在指令级或访存模式上抠收益；72、52.3、68.8、46.6 这类数十倍读数则往往出现在基线本身存在明显低效路径的场景——例如基线走了未被融合的多算子串行、或参考实现受 Python 侧调度与多次 launch 拖累。此时 T0 的分母被放大，speedup 反映的是「基线有多差」而非「候选有多好」。判据是看候选的 SOL 占比：若候选仍未接近 roofline，则高 speedup 只是基线欠优化的镜像。

失效条件集中在三类。其一，语义漂移：候选为提速裁剪了边界处理、改变了归约顺序或数值精度，正确性 oracle 未覆盖该路径，speedup 是「错得更快」。其二，形状绑定：加速比在基准给定 shape 上成立，换到 batch 更小、维度非对齐的场景，T1 的 occupancy 与向量化收益塌陷，比值不可迁移。其三，计时污染：T1 若省去了基线必须做的同步或内存分配，比较的是两段不同工作量。系统代价上，追求高 speedup 的候选常以编译时间与显存换取收益——更激进的 unroll、更大的 tile、更多寄存器占用会拉长编译并压低 occupancy，单看比值会掩盖这些成本。

具体例子：同一 reduction 算子，基线若因多次 launch 与中间张量落地导致 T0 偏大，候选融合后拿到数十倍读数；但把基线换成已融合的库实现，同一候选的比值会回落到个位数。因此读题时应把 speedup 与「基线是谁、计时含什么、正确性覆盖到哪」三件事绑定成三元组，缺一项即判不可比。
