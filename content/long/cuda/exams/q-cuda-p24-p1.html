一 · 题干的三层结构：目标、基线、失效面

这道题的问法不是“复述 JustGoal 做了什么”，而是“它在迁移时最可能在哪里失效”。题干里藏着三层可拆解的信息，读题时若不逐层剥离，很容易写成摘要式回答。第一层是方法承诺：“With Only a Goal”——系统只拿到一个目标（比如“实现一个 attention kernel，达到某延迟上限”），不提供参考实现、不提供 shape 列表、不提供目标硬件规格。第二层是基线定位：“the AI Baseline Is Above the Expert Kernels”——AI 生成的基线在作者设定的评测条件下超过了人类专家手写 kernel。第三层才是真正的考点：“跨硬件、跨 shape、跨 dtype 迁移时最可能在哪里失效”。这三层不是并列关系，而是递进关系：第一层定义了方法的输入约束，第二层定义了它在原分布上的表现，第三层要求你把前两层的前提条件逐一放松，找出承诺崩塌的那个点。

考点因此可以精确化为三个子问题：(a) “Only a Goal”这个约束在什么意义上成立——目标里隐含了多少未言明的先验；(b) “Above the Expert”是在哪个度量、哪个分布、哪个硬件上成立的，这个比较的边界在哪里；(c) 迁移失效的机制是什么，是搜索空间塌缩、反馈信号失真，还是验证 oracle 本身不可迁移。回答必须给出判断、验证方案与回退条件，三者缺一不可：判断是立场，验证方案是可执行的证伪路径，回退条件是工程上的止损阈值。

解题路径建议按“约束→信号→分布”三段走：先拆“Only a Goal”里被省略的隐式规格，再拆 AI 基线超越专家所依赖的反馈回路，最后拆迁移时这三个环节中哪一个最先断裂。需要调用的公式主要是 roofline 判据与 Amdahl 型收益上界，前者用于判断某硬件上某 kernel 是否还有优化余量，后者用于判断端到端收益是否值得继续投入。下面逐节展开。

二 · “Only a Goal”的隐式规格：目标文本里已经写死了什么

“只给一个目标”在工程上从来不是真的只给一句话。一个可执行的目标至少隐含四类规格：数值语义（dtype、累加精度、是否允许 TF32）、形状域（哪些 shape 必须正确、哪些只需不崩）、性能口径（测的是 kernel 时延还是端到端时延、是否含 launch 开销、warmup 与重复次数）、以及正确性容差（绝对误差、相对误差、NaN/Inf 处理）。JustGoal 类方法的“目标”若只写了“快”，那么 dtype 与容差就是由生成器自行补全的——这正是迁移失效的第一候选点。生成器在训练分布内见过大量同构任务，它补全的隐式规格与评测方的真实规格对齐；一旦换 dtype（fp16→bf16→fp8）或换容差口径，补全的规格就可能系统性偏移。

机制上，这对应“规格补全”而非“规格遵循”：模型从目标文本与历史上下文中推断未写明的约束，推断依据是训练分布的条件概率。可以用一个简单的形式化来描述这种风险：设真实规格为 s*，模型补全的规格为 ŝ，则迁移后的有效正确率近似为 P(correct) ≈ P(ŝ = s*) · P(code correct | ŝ = s*)。第一项在分布内接近 1，跨 dtype 时迅速下降；第二项即使规格对齐也可能因硬件差异下降。这个分解的价值在于它把“失效”定位到了具体环节，而不是笼统地说“泛化不好”。

代价体现在验证成本上：规格补全错误不会在编译期暴露，只会在正确性 oracle 上以零星 mismatch 出现，排查一个 dtype 相关的累加精度问题通常要跑多组 shape 与多组容差才能定位，这消耗的是验证机时与人工 token，而不是 GPU 算力。具体例子：目标写“实现 fp16 矩阵乘，越快越好”，生成器可能默认 fp32 累加；换到 bf16 输入、要求 fp32 累加且容差为 1e-2 相对误差时，同一个 kernel 的数值行为需要重新验证，而“越快越好”这个目标文本没有提供任何区分信息。

三 · “Above the Expert”的度量边界：比较在哪个分布上成立

“AI 基线超过专家 kernel”是一个条件命题，其真值依赖于四个坐标：硬件型号、shape 集合、dtype、以及度量口径（kernel-only 还是 end-to-end）。题干要求判断迁移失效点，就必须先把这四个坐标显式化，否则“超过”无法被证伪。工程上可用的判据是 roofline：对某 kernel 在某硬件上的算术强度 I（FLOP/Byte），可达性能上界为

$$P_{\text{roof}} = \min(P_{\text{peak}},\ I \cdot B_{\text{mem}})$$

其中 P_peak 是峰值算力，B_mem 是有效带宽。专家 kernel 通常已贴近该上界的某一侧；AI 基线若“超过”，要么是专家实现留有明显余量（例如未做 swizzle、未用 TMA、未做 pipeline），要么是比较落在了专家未针对优化的 shape 上。这两种情形的迁移行为完全不同：前者说明 AI 找到的是实现级优化，跨硬件时只要新硬件的瓶颈侧不变就可能保持优势；后者说明优势来自分布选择，换 shape 即消失。

区分二者的验证方案是“瓶颈侧标注”：对每个被测 shape 计算 I 并判断其落在 memory-bound 还是 compute-bound 区间，再看 AI 基线的优势是否只集中在某一侧。若优势全部集中在 memory-bound 区间，而专家 kernel 在该区间未做向量化访存或未用异步拷贝，那么“超过专家”更可能是专家实现的时代局限，而非方法的普适能力。代价是：做这个标注需要对每个 shape 采样 NCU 的 dram throughput 与 sm throughput，profile 本身有开销，且 profiler 会扰动时序，通常需要单独一轮无 profile 的计时来交叉验证。

具体例子：一个 elementwise 归一化 kernel 在 memory-bound 区间，AI 基线用向量化加载加单遍归约超过专家手写的两遍实现；换到 compute-bound 的 reduction 变体后，AI 基线的优势消失甚至反转，因为它的优势来源（访存模式）不再是瓶颈。这个例子说明“Above the Expert”必须绑定到瓶颈侧才有意义。

四 · 迁移失效的三个候选机制与优先级判断

跨硬件、跨 shape、跨 dtype 三类迁移，失效机制并不相同，需要分别给出候选并排序。

  • 跨硬件：反馈信号失真。AI 基线的优化循环依赖执行反馈（时延、profile 计数）。换到新硬件后，同一份代码的相对优劣可能反转：旧硬件上 L2 容量大、bank 冲突不显著，新硬件上同一访问模式成为瓶颈。此时搜索过程仍在“优化”，但优化的是旧硬件的代理指标。失效点是反馈回路与目标硬件脱钩，而非生成能力不足。
  • 跨 shape：搜索空间塌缩。方法在少量 shape 上迭代到高性能后，倾向于复用同一套 tiling 与 launch 配置。当 shape 进入极端区间（极小 batch、超大 K、非 2 的幂维度），模板化配置失效，而方法缺少从头推导 tiling 的机制。失效点是配置空间覆盖不足。
  • 跨 dtype：正确性 oracle 漂移。低精度 dtype 改变的不只是吞吐，还有累加顺序敏感性与容差口径。生成器若沿用高精度的容差假设，产出的 kernel 在数值上“看起来对”但在严格 oracle 下失败。失效点是验证环节，而非生成环节。

优先级判断应基于“失效是否可被现有反馈捕获”。跨硬件的反馈失真会在计时上表现为“优化停滞”，可被察觉但难以归因；跨 shape 的塌缩会在正确性上暴露为崩溃或明显变慢，容易被察觉；跨 dtype 的 oracle 漂移最危险，因为它在宽松容差下完全不暴露，直到下游任务出现数值问题。因此工程判断是：跨 dtype 是三者中最可能被低估的失效点，应优先建立 dtype 感知的验证矩阵。

代价维度上，三者消耗的资源不同：跨硬件迁移消耗的是 profile 机时与多次编译（每个硬件后端要重新编译，编译时间随模板实例化数量增长）；跨 shape 消耗的是搜索轮次与 token（每个新 shape 需要重新迭代）；跨 dtype 消耗的是验证机时与人工排查。三者的回退条件也不同，见下节。

五 · 验证方案的设计：可证伪的三组实验

验证方案必须能证伪“方法可迁移”这一命题，而不是重复原论文的设定。建议三组实验，每组对应一个迁移轴，且每组都要有明确的通过/失败判据。

第一组，硬件轴：在同一 shape 与 dtype 下，把 AI 基线移植到第二块硬件，记录其相对专家 kernel 的比值，并用 roofline 标注瓶颈侧是否改变。判据是“优势是否在瓶颈侧不变时保持”。若瓶颈侧改变而优势消失，则失效机制是反馈失真而非生成能力。这里需要调用 Amdahl 型上界来判断端到端收益：设 kernel 占端到端时延比例为 f，kernel 加速比为 s，则端到端加速比为

$$S_{\text{e2e}} = \frac{1}{(1-f) + f/s}$$

当 f 很小（例如 kernel 只占 10%），即使 s 很大，端到端收益也被封顶在约 1/(1-f)。这意味着“超过专家 kernel”在 kernel 层面成立，不代表生产端到端有收益——这是迁移判断中必须区分的一层。

第二组，shape 轴：构造三个分布外 shape（极小、极大、非对齐），只给目标不给参考实现，观察方法是否能自主推导 tiling。判据是“是否在无提示下产出正确且不劣于朴素实现的 kernel”。失败则说明配置空间覆盖不足，回退条件是把 shape 域显式写入目标文本，放弃“Only a Goal”的强承诺。

第三组，dtype 轴：对同一 kernel 在 fp32、bf16、fp8 三档下用分级容差 oracle 验证，记录每档的 mismatch 率与最大相对误差。判据是“低精度档在严格容差下是否仍通过”。失败则说明 oracle 漂移，回退条件是为每个 dtype 绑定独立的容差与累加精度规格，并在生成阶段就把 dtype 写入目标。

三组实验的共同代价是编译与验证机时：每个硬件后端、每个 dtype 组合都要重新编译与重新计时，模板实例化数量随组合数相乘增长，编译时间成为实际瓶颈之一。因此验证方案应做正交裁剪，优先跑“瓶颈侧改变”与“低精度严格容差”这两个最可能失败的组合。

六 · 回退条件与工程判断的落点

回退条件不是“效果不好就放弃”，而是预先定义的止损阈值，且阈值要绑定到可观测指标。对跨硬件轴，回退条件是：新硬件上 AI 基线的 kernel 时延超过专家 kernel 的同一量级，且 NCU 显示瓶颈侧已改变——此时应回退到“以专家 kernel 为种子、只做局部调优”的模式，放弃端到端自主生成。对跨 shape 轴，回退条件是：分布外 shape 上出现正确性失败或性能低于朴素实现，此时应把 shape 域写入目标规格，把“Only a Goal”降级为“Goal + 域约束”。对跨 dtype 轴，回退条件是：严格容差下 mismatch 率不可接受，此时应把 dtype 与累加精度作为硬约束前置，并在验证环节引入分级 oracle。

工程判断的落点在于：JustGoal 类方法的真实边界不是“能不能生成 kernel”，而是“目标文本能否承载足够的规格信息”。当目标只写“快”，方法用训练分布补全规格，在分布内表现优异；一旦迁移轴改变了规格的隐式假设，补全就会系统性偏移，而反馈回路无法自行发现这种偏移，因为计时指标对数值正确性不敏感。因此最可能失效的点是跨 dtype 的验证环节，其次是跨硬件的反馈失真，最后是跨 shape 的配置塌缩。可执行的动作是把 dtype 与容差写进目标、把瓶颈侧标注写进验证、把 Amdahl 上界写进收益判断——这三件事都不依赖新方法，只依赖把题干里被省略的规格显式化。

跨迁移失效面：先钉住“目标—基线”的耦合点

JustGoal 的题眼不在“AI 基线超过专家 kernel”这个结论，而在“仅给目标”这一约束如何把搜索空间压到可验证的窄带。跨硬件、跨 shape、跨 dtype 迁移时，最先失效的是目标函数与硬件执行模型之间的隐式耦合：目标里隐含的 tile 形状、共享内存预算、寄存器压力上限，都是针对某一代 SM 的占用率曲线标定的。换到 SM 数更少、L2 更小或 bank 宽度不同的器件上，同一目标会把 agent 推向一个在源器件上最优、在目标器件上却触发 occupancy 悬崖的配置。用占用率近似表达这一耦合：

$$\text{occ}=\min\!\left(\frac{R_{\text{sm}}}{R_{\text{blk}}},\ \frac{S_{\text{sm}}}{S_{\text{blk}}},\ \frac{W_{\text{sm}}}{W_{\text{blk}}}\right)$$

其中寄存器、共享内存、warp 槽三项任一成为瓶颈，目标函数在源器件上“看不见”的约束就会在迁移后显形。代价是双重的：编译期搜索要多花 token 去试探被隐式约束排除的配置，运行期则表现为实际带宽利用率低于 roofline 预测，而正确性 oracle 不会报错——它只保证数值对，不保证性能目标仍可达。

跨 shape 的失效更隐蔽。JustGoal 的目标通常绑定在一个参考 shape 的访存比上，当 M、N、K 中任一维跨过 tile 边界，合并访存模式与 bank conflict 分布会整体翻转，agent 学到的“目标—实现”映射不再是插值而是外推。验证方案应把 shape 扫描做成阶梯：先在参考 shape 的整除邻域内取样，再取非整除尾块，记录每次编译时间与 NCU 的 dram__throughput 与 l1tex 冲突计数，用“目标达成但 SOL 下降”作为失效判据。回退条件是：当尾块场景下实测吞吐低于参考 shape 的同一实现且冲突计数上升，就退回按 shape 分档的目标重标定，而不是继续让 agent 外推。

跨 dtype 的边界在于精度换带宽的假设。把 fp32 目标平移到 fp16/bf16 时，向量化宽度与寄存器打包方式改变，目标里“每字节有效计算”的权重需要重算；若沿用旧目标，agent 会优先满足吞吐而牺牲累加精度，正确性 oracle 的容差若不随 dtype 收紧，就会放过误差累积。工程判断是：迁移前先做一次目标敏感性检查——固定实现、只换 dtype，看目标值漂移是否超过阈值；超过则判定目标不可迁移，回退到按 dtype 重建目标并用小规模 shape 做校准编译，把编译时间成本前置到离线阶段，避免在线搜索被无效目标拖长。
