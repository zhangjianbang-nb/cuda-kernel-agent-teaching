一 · 题干的三层结构：论文主张、harness 契约、验收口径

这道题的题干只有一句话，但它压着三层不同的东西，拆不开就会答成“综述”。第一层是论文主张：CUDA Agent 用大规模 agentic RL 把 kernel 生成做成一个可训练的任务，其方法有效性必须由“生成—验证—反馈”闭环来支撑。第二层是 harness 契约：要让这套方法可复现，必须固定基线、输入分布、正确性门、防作弊与上线门这五个可配置对象，它们之间是耦合的，不是并列清单。第三层是验收口径：什么叫“这套 harness 通过了”，必须给出可判定的判据，而不是“效果良好”。

考点因此不在“复述论文”，而在能否把一句主张翻译成一组可执行配置。判卷时最容易被扣分的是把五件事写成五个孤立段落：基线只谈选哪个参考实现，正确性门只谈 allclose，防作弊只谈“禁止调用 cuBLAS”，上线门只谈 speedup 阈值。真正的得分点是指出它们共享同一套输入分布与同一套计时协议——基线若换了输入分布，正确性门的容差前提就失效；防作弊若只做静态扫描，动态链接的库调用仍可绕过；上线门若用不同 warmup 次数，speedup 与基线不可比。

解题路径建议按“主张→可观测量→配置项→判据”四步走：先把论文主张拆成可观测的成功信号（正确性通过率、相对基线的加速比分布、编译与运行失败率），再把每个信号映射到 harness 的一个配置项，最后为每个配置项写出可判定的验收表达式。这条路径的代价是配置空间变大：五个对象两两耦合，最坏情况下需要枚举的组合数随输入分布的分档数线性增长，而每档都要跑一遍基线，编译时间与 GPU 时延随之上升。一个具体例子：若输入分布按 shape 分 4 档、每档 3 个 dtype，则基线需 12 次独立测量，每次测量的 warmup 与重复次数直接决定 harness 的总墙钟时间。

二 · 基线的定义：不是“选一个库”，而是“固定一条可比链”

基线在 harness 里承担两个职责：提供正确性参照，提供性能分母。两者对基线的要求不同——正确性参照要求数值稳定、覆盖全部输入档；性能分母要求计时协议与待测 kernel 完全一致。因此基线的配置项应写成三元组：实现来源、编译/加载方式、计时协议。实现来源可以是框架自带算子、手写参考 kernel 或论文给出的对照实现；编译/加载方式决定是否计入 JIT 开销；计时协议决定 warmup、重复次数与同步点。

可比链的形式化约束可以写成：对同一输入档 $i$，待测 kernel 的时间 $T_i$ 与基线时间 $B_i$ 必须满足同一测量函数 $M(\cdot)$，即

$$\text{speedup}_i=\frac{M(B_i,\ \text{warmup}=w,\ \text{rep}=r,\ \text{sync}=s)}{M(T_i,\ \text{warmup}=w,\ \text{rep}=r,\ \text{sync}=s)}$$

其中 $w,r,s$ 三个参数在待测与基线两侧必须逐字相同。工程上最常见的错误是待测侧用 CUDA event 计时、基线侧用 wall clock，导致 speedup 系统性偏高；另一个错误是基线侧把首次调用的 cuBLAS handle 初始化计入，而待测侧已 warmup 过。代价体现在时延上：若 $r$ 取到统计稳定所需的下限，每档测量时间约为 $r\cdot(T_i+B_i)$，档数增加时 harness 墙钟线性增长；若为省时间把 $r$ 压到很小，speedup 的方差会吞掉真实差异，上线门的判定就失去意义。

具体例子：同一 GEMM 形状下，基线若选框架算子，其内部可能走 heuristic 选 kernel，换一个 shape 就换一条实现路径，导致 $B_i$ 在不同档之间不可比；此时应把基线固定为“同一实现路径 + 显式指定算法”，或在 harness 中记录基线实际命中的 kernel 标识，作为该档的可比性凭证。这一步的代价是额外的 profile 采集时间，但换来的是 speedup 分母的可解释性。

三 · 输入分布：分档、边界与“不可比区”的显式声明

输入分布不是“随机生成一批 tensor”，而是 harness 的一等配置。它要回答三个问题：覆盖哪些 shape/dtype/布局、每档的采样规则、哪些区域被声明为不可比。分档的依据应是 kernel 的性能相变点——例如 tile 能否整除、是否触发边界分支、是否走 split-K 路径——而不是均匀撒点。均匀撒点会让大量样本落在同一性能区间，浪费测量预算，却漏掉相变附近的样本。

采样规则应写成可复现的伪代码思路：固定随机种子，按档位权重抽样，每档至少 $n_{\min}$ 个样本，且对每个样本记录其“档位标签”。判据是覆盖率而非样本数：每个声明的档位至少被命中一次，边界样本（如 $M$ 或 $N$ 恰为 tile 尺寸整数倍减一）必须显式构造，不能靠随机撞上。代价是显存：边界样本往往需要额外 padding 或非对齐分配，单样本显存占用上升；若档位数多，批量构造输入会推高峰值显存，需要分阶段释放。

“不可比区”的声明是这道题容易被忽略的考点。某些输入（极端小 shape、非对齐 stride、超出 shared memory 容量的 tile）下，基线本身走的是 fallback 路径，此时 speedup 不具工程意义。harness 应把这些区域标记为 excluded，并在验收口径中要求 excluded 比例有上限，否则被测方可以通过扩大 excluded 区来美化整体 speedup。具体例子：当 $M<16$ 时，cuBLAS 类基线可能退化为逐元素路径，而待测 kernel 仍按 tile 逻辑执行，两者计时都受 launch 开销主导，speedup 趋近 1 且方差极大；这类档应单列为“launch-bound 区”，只校验正确性、不参与 speedup 聚合。

四 · 正确性门：容差不是常数，而是随输入档变化的判据

正确性门的核心是把“数值等价”翻译成可判定的表达式，并明确参照物。参照物应与基线解耦：基线用于性能分母，正确性参照应是一个数值稳定的高精度实现（如 float64 累加或分段归约），否则基线的启发式选择会污染正确性判定。判据形式建议写成逐元素的相对误差与绝对误差的混合门：

$$\text{pass}=\bigwedge_{j}\ \Big(|y_j-\hat y_j|\le \tau_a+\tau_r\cdot|\hat y_j|\Big)$$

其中 $\tau_a,\tau_r$ 随 dtype 与归约长度变化：归约长度 $K$ 增大时浮点累加误差随 $\sqrt{K}$ 或 $K$ 增长（取决于累加顺序），固定容差会在长归约档上系统性误判。因此 harness 应把容差写成 $(\text{dtype},K)$ 的函数，并在配置中显式列出每个档的 $(\tau_a,\tau_r)$。代价是正确性检查本身的时延：逐元素比较需要把输出搬回 host 或做 device-side 归约，前者引入 D2H 带宽开销，后者需要额外的归约 kernel 与临时显存；对超大输出，D2H 可能成为 harness 的瓶颈。

另一个考点是“正确性门的粒度”。只做整体 allclose 会放过局部错误：一个 kernel 可能在大部分元素上正确、在边界 tile 上越界写入，整体误差被平均掉。判据应包含结构检查——输出 tensor 的越界写检测（可用哨兵值填充 padding 区）、NaN/Inf 计数、以及分块最大误差的分布。具体例子：对边界样本，在输出 buffer 尾部填充哨兵值，kernel 执行后检查哨兵是否被改写；这一步的代价是额外分配与一次 D2H 读回，但能捕获 allclose 无法发现的越界写。正确性门还应记录失败样本的档位标签，供后续 RL 反馈使用——这是与 agentic RL 闭环的接口，失败样本不是丢弃，而是进入下一轮生成的负例池。

五 · 防作弊与上线门：静态扫描不够，要绑定动态行为与统计判据

防作弊的考点是识别“绕过计算”的路径，而不是罗列禁止清单。常见绕过有三类：调用高度优化的库函数冒充自研 kernel、缓存结果跳过重复计算、针对 harness 的输入分布做特化（把答案硬编码）。对应的机制应分层：静态层扫描源码中的库调用符号与可疑常量；动态层在运行时拦截库加载与函数指针替换，并检查 kernel 的实际指令数/访存模式是否与声称的计算量匹配；统计层用输入扰动检测结果是否随输入变化。

动态层的判据可以写成：对同一档位的两个不同输入，若输出完全相同而输入不同，则判定为缓存或硬编码嫌疑。代价是测量预算翻倍——每个档位至少跑两次不同输入，harness 墙钟增加约一倍；若用 NCU 采集指令数，profile 本身的开销会让计时失真，因此 profile 应在独立进程、独立计时轮次中进行，不与 speedup 测量混跑。具体例子：某 kernel 在固定 shape 下 speedup 异常高，NCU 显示其 global load 指令数远低于理论访存量，结合输入扰动后输出不变，即可判定为缓存结果；此时上线门应直接拒绝，而不是调低 speedup 阈值。

上线门是把正确性、防作弊、性能三者合成一个可判定决策。建议写成三段式：先过正确性门（硬门，任一档失败即拒），再过防作弊门（硬门），最后看性能门的统计判据。性能门不应是单点 speedup 阈值，而应是“在覆盖率满足、excluded 比例受限的前提下，聚合 speedup 的下置信界超过阈值”。用下置信界而非均值，是为了防止少数极端样本拉高均值。代价是样本数需求上升：置信界越紧，每档所需重复次数越多，测量时延与 GPU 占用随之增加。工程判断上，若 harness 的墙钟预算固定，应优先增加档位覆盖率而非单档重复次数，因为相变点的漏测比均值估计的方差更致命。

三段式门的配置应落成一张可执行的验收表：每个门的判据、阈值来源（由基线测量导出而非拍脑袋）、失败后的处置（拒绝/进入负例池/标记 excluded）。这张表本身就是 harness 的契约文本，复现者按表执行即可得到可比的结论。最后一段落在具体机制上：上线门的聚合函数必须与输入分布的档位权重一致，权重变更即视为 harness 版本变更，旧结论不可直接沿用——这是可复现性的最小工程约束。

读题即建模：把题干拆成可判定的考点与失效边界

读题的第一步不是想 kernel 怎么写，而是把题干拆成三层可判定命题：语义层（输入输出契约、dtype、layout、广播与边界语义）、性能层（相对谁、在什么 shape 分布上、以什么口径计）、约束层（允许的 API、是否可多 kernel、是否可调库）。每层都要落成可执行的判据，否则 agent 的“解题路径”会退化成猜。以 GEMM 类题为例，语义层要判定的是 M/N/K 三元组与 batch 维的映射、是否要求 epilogue 融合 bias/激活、是否允许 split-K 归约；性能层要判定基线是 cuBLAS 还是 PyTorch eager，以及计时是否含 launch 开销；约束层要判定是否禁用 cublasLt、是否允许 inline PTX。这三层决定了后续 harness 的输入分布与正确性门，而不是反过来。

考点拆解要显式给出“解题路径 + 需调用公式”，但不给答案。路径是：先由题干推出 roofline 上界，再决定 tiling 与数据复用策略，最后决定是否需要 persistent kernel 或 stream-K。公式层面必须调用算术强度与 roofline 判定：

$$I=\frac{2MNK}{4(MK+KN+MN)}\ \text{FLOP/Byte},\qquad P_{\text{sol}}=\min(P_{\text{peak}},\ I\cdot B_{\text{HBM}})$$

由 $I$ 与 $P_{\text{sol}}$ 可判定该题是带宽受限还是算力受限，从而决定考点是“减少 HBM 往返”还是“提高 MMA 占用率”。这一步的代价是 token：把题干转成结构化 schema（shape 集合、dtype、容差、基线名、禁用 API 列表）通常要一次长上下文解析加一次自检，若 schema 字段缺失，后续多轮 RL 的奖励会落在错误的目标上，等于用整条 rollout 的算力换一个错题解。

边界与失效条件必须前置写进题面解析器，而不是留给 reward 事后补救。典型失效有三类：其一，题干给的 shape 分布若只覆盖单一 N（如 N=4096 固定），agent 会过拟合到某一 tile 配置，换 N 后 shared memory 占用与 occupancy 骤降，此时正确性门仍通过但性能门失效，harness 必须把 shape 分布写成显式列表而非“随机”。其二，容差判定若只用全等比较，融合 epilogue 的浮点结合律差异会被误判为错误，需按 dtype 给出 atol/rtol 二元组并把 NaN/Inf 语义单列。其三，禁用 API 的检查若只做源码字符串匹配，宏展开与模板别名可绕过，需在编译产物层面做符号级检查。系统代价上，符号级防作弊检查会增加编译时间与 harness 复杂度，但相比放行一个调库作弊解、让 RL 在错误奖励上收敛，这个代价是必要开销。
