一 · 题干的三层结构：pipeline 问题被伪装成流程题

题干表面是“按一次 kernel 生成—编译—运行—评测的顺序回答”，但它真正问的是 KernelAudit 这篇工作对“验证器（validator）”的审计视角：不是问一个 kernel 怎么跑起来，而是问在一条从 LLM 输出到最终判定的流水线上，哪些环节是契约（contract）、哪些环节是可被验证器自身缺陷污染的。拆题第一步是把题干里的四个动词还原成四类对象：生成阶段的输入是自然语言/参考实现/签名约束，输出是源码文本；编译阶段的输入是源码与编译选项，输出是二进制或编译错误；运行阶段的输入是二进制与测试输入/形状配置，输出是数值结果与计时；评测阶段的输入是结果与参考 oracle，输出是正确性判定与性能分数。每一段都有独立的失败模式，而 KernelAudit 的核心主张是：评测阶段的失败往往不是 kernel 的错，而是 validator 的契约没被显式声明。因此答题路径不能写成“先这样再那样”的流水账，而要写成“每步的契约—违反契约的表现—审计手段”三段式。

考点因此落在三个层次：第一层是流程完整性（能否不漏环节，尤其是编译选项、形状配置、计时口径这些容易被忽略的隐式输入）；第二层是失败模式归因（把错误归给 kernel、归给 harness、还是归给 validator 的判定逻辑）；第三层是审计方法（如何用可复现的探针区分这三类归因）。题干没有要求给出 KernelAudit 的具体实现细节，但要求“每一步的输入、输出和失败模式”，这实际上是在考你是否理解 validator 本身也是一个需要被验证的程序。一个合格的回答应当在每一步都点出“这一步的契约是什么、谁负责保证、违反时症状是什么”，而不是罗列 API 调用。

二 · 生成阶段：契约是签名与语义约束，失败模式是“可编译但语义漂移”

生成阶段的输入不是单一文本，而是三元组：参考实现（reference）、函数签名与形状约束（shape/dtype/layout contract）、以及可选的性能目标。输出是候选 kernel 源码（CUDA C++ / Triton / CuTe / PTX 之一）。这一阶段的契约是语义等价：候选 kernel 在契约声明的输入域上应当与参考实现数值一致（在给定容差内），并且满足签名所隐含的布局假设（例如 stride、对齐、是否允许原地写）。失败模式有三类：语法/编译失败（下一阶段才暴露）、可编译但数值错误、以及最隐蔽的一类——只在契约未覆盖的输入上出错，例如参考实现未声明的边界形状、非连续布局、或 dtype 提升规则。KernelAudit 的审计视角在这里的切入点是：validator 若只按固定形状测试，就把“契约覆盖不足”伪装成了“kernel 正确”。

这一阶段的代价主要是 token 与时延：生成候选需要采样，候选越多，后续编译与运行的摊销成本越高；而如果契约声明不完整，节省下来的声明成本会在评测阶段以“假阳性通过”的形式放大。一个具体例子：参考实现是一个 row-wise softmax，签名只写了 (M, N) 与 float32，但候选 kernel 内部假设 N 是 2 的幂以使用 warp shuffle 归约。固定形状测试全过，validator 判正确；一旦审计探针加入 N=1000，数值偏差立刻出现。这说明生成阶段的契约必须把“输入域”写清楚，否则后续所有判定都建立在流沙上。

$$\text{Contract}_{gen} = (\text{signature},\ \text{shape domain},\ \text{dtype/layout},\ \text{tolerance})$$

解题路径上，这一问要答出“输入是三元组而非一段文本”，并把失败模式按“编译前可判 / 编译后可判 / 仅契约外可判”分层。公式的作用是把契约显式化：审计的第一步就是把隐式假设提升为可检查的谓词。

三 · 编译阶段：契约是编译选项与环境，失败模式是“环境差异伪装成 kernel 缺陷”

编译阶段的输入是源码加上一组编译契约：目标架构（sm 版本）、优化级别、是否开启 fast math、宏定义、以及 Triton/CuTe 场景下的编译器版本与后端选项。输出是二进制（cubin/ptx）或结构化的编译诊断。这一阶段最容易被流程题忽略，因为题干只说了“编译”，但 KernelAudit 的审计要点恰恰在这里：validator 若固定一套编译选项，就无法区分“kernel 写错了”与“kernel 在该选项下不合法”。典型失败模式包括：架构不匹配导致的指令不可用（例如某些 warp-level 原语在低 sm 上不存在）、fast math 改变了数值语义从而让正确性判定漂移、以及编译超时被误判为失败。

代价维度是编译时间与缓存：候选数量乘以编译选项组合会线性放大编译开销，而编译缓存若以源码哈希为键、忽略选项，就会让不同契约下的产物互相污染。一个具体例子：同一份使用 __fmaf_rn 的 kernel，在开启 -use_fast_math 时数值结果与参考实现的差异可能超出容差，validator 若把该选项写死为开启，就会把一批本可通过的候选判错；反之若写死关闭，又会放过在目标部署环境下不安全的候选。审计探针应当把编译选项作为显式维度记录进结果元数据，使失败可归因。

$$\text{Compile}(s, o) \rightarrow (b,\ \text{diag}),\quad \text{audit} = \{(s_i, o_j, b_{ij})\} \text{ 需可复现}$$

解题路径：答出“编译的输入不止源码”，并把失败模式分为“诊断可读的硬失败”与“选项相关的语义漂移”。这一阶段不需要展开 PTX 细节（那是别的片段主题），只需指出契约维度与归因要求。

四 · 运行阶段：契约是输入域与计时口径，失败模式是“测量本身成为变量”

运行阶段的输入是二进制、测试输入（形状、dtype、布局、随机种子）、以及计时契约：warmup 次数、重复次数、是否同步、是否包含数据传输、是否使用 CUDA graph。输出是数值结果张量与计时样本。这一阶段的契约是“在声明的输入域上执行，并按声明的口径测量”。失败模式分两类：正确性侧——越界访问、未初始化读、竞态导致的非确定性结果；性能侧——计时口径不一致导致候选间不可比，例如一个候选把 kernel launch 开销算进去、另一个没有，或者一个在未同步的情况下计时得到虚假的低时延。KernelAudit 的审计角度是：validator 若不做确定性检查（同输入多次运行结果是否一致）与口径检查，就会把测量噪声当成 kernel 属性。

代价维度是显存与同步开销：大批形状组合会放大显存占用与运行时间；每次计时若强制同步，会引入主机端等待，使时延数字偏大。一个具体例子：两个候选都正确，A 在 kernel 内做了边界检查，B 没有；在固定形状下 B 更快，但审计探针加入非对齐形状后 B 越界写坏了相邻缓冲区，数值结果在后续用例中才暴露。若运行阶段没有“结果确定性 + 越界检测（如 compute-sanitizer 类探针）”的契约，这个错误会被归因到“评测阶段的容差问题”，从而误导优化方向。

$$\text{Run}(b, x, \text{cfg}) \rightarrow (y, \{t_k\}),\quad \text{valid} \iff y \approx y_{\text{ref}} \ \wedge\ \operatorname{var}(y \mid x) = 0$$

解题路径：把运行阶段的输入写成“二进制 + 输入域 + 计时契约”，并把失败模式按正确性/确定性/口径三分。公式给出的是判定谓词：数值一致且同输入结果方差为零，二者缺一不可。

五 · 评测阶段：契约是 oracle 与判定规则，失败模式是“validator 自身的假阳/假阴”

评测阶段的输入是运行结果、参考 oracle、容差规则、以及性能基线（roofline/SOL 参照）。输出是正确性判定与性能分数。这一阶段的契约是判定规则本身的可审计性：容差如何随 dtype 与归约规模缩放、性能分数是否按声明的基线归一、失败是否被分类（编译失败/数值失败/超时/越界）。失败模式正是 KernelAudit 命名的对象：validator 的假阳性（错误 kernel 被判通过，通常因为测试覆盖不足或容差过松）与假阴性（正确 kernel 被判失败，通常因为容差过紧、基线选择不当、或计时口径不一致）。审计手段是把判定过程拆成可复现的探针集合：对每个候选记录“哪些输入被测试、容差是多少、基线是什么”，并注入已知错误/已知正确的对照 kernel 来校准 validator 本身。

代价维度是评测吞吐与 token：对照探针会增加评测次数，但换来的是归因可信度；若省去对照，错误归因会导致后续多轮优化在错误方向上消耗生成 token。一个具体例子：某候选在 M=1 的退化形状上因归约实现返回了未定义值，但 validator 的测试集恰好不含 M=1，于是判通过；审计探针加入退化形状后暴露。反过来，一个正确候选因容差按绝对误差设定、在数值量级较大的用例上被判失败，这是假阴性。两者都说明：评测阶段的契约必须显式声明输入域与容差规则，否则判定不可归因。

$$\text{FP} = \{\text{bad kernel} \mid \text{pass}\},\quad \text{FN} = \{\text{good kernel} \mid \text{fail}\},\quad \text{audit} = \text{FP} \cup \text{FN} \text{ 的可复现探针集}$$

解题路径：答出评测阶段的输入包含 oracle 与判定规则，输出是判定与分数，失败模式是 validator 自身的假阳/假阴，并给出用对照 kernel 校准的思路。这一问的得分点在于把“评测”从“跑个分”提升为“被审计的对象”。

六 · 解题路径的组织方式：按契约维度而非时间顺序作答

把四步串成答案时，最稳的结构是“每步三问”：输入中的契约是什么、输出是什么、违反契约的症状是什么。这样既覆盖题干要求的顺序，又避免写成无归因的流水账。需要调用的公式集中在两处：生成阶段的契约四元组（签名、形状域、dtype/layout、容差），以及运行/评测阶段的判定谓词（数值一致 + 确定性 + 口径一致）。表格可以用来压缩四步的对照关系，但不要用它替代归因分析。

阶段输入中的契约输出典型失败模式
生成签名、形状域、dtype/layout、容差候选源码契约外输入语义漂移
编译架构、优化级别、fast math、编译器版本二进制/诊断选项相关语义漂移、架构不匹配
运行输入域、随机种子、计时口径结果张量、计时样本越界、竞态、口径不一致
评测oracle、容差规则、性能基线判定、分数validator 假阳/假阴

最后落在工程判断上：这道题的分水岭不在于你是否知道 CUDA 的编译运行链路，而在于你是否把 validator 当作被测系统的一部分。KernelAudit 的审计思路要求每一步都留下可复现的契约记录与对照探针，否则“kernel 错了”与“validator 错了”无法区分，后续的优化反馈与可验证奖励都会建立在错误归因上。答题时只要在每一步都点出“谁保证契约、违反时症状是什么、用什么探针归因”，就已经覆盖了题干的核心考点。

契约审计流水线的边界：哪一步开始失真

把“生成—编译—运行—评测”四段拆开看，真正决定审计结论可信度的不是最贵的评测段，而是最容易被忽略的编译段：编译器可以合法地把一个语义错误的 kernel 优化成看起来正确的结果，也可以把正确 kernel 的浮点顺序改掉，使 oracle 判定翻转。契约审计的边界就在这里——它审计的是“被观测到的行为”，而不是“源码的意图”。设审计判定为布尔函数 A(x)，其中 x 是 (源码 s、编译产物 b、输入分布 D、容差 τ) 四元组，则失效条件可写成：存在 s 使 A(s,b₁,D,τ)=真 而 A(s,b₂,D,τ)=假，b₁、b₂ 为同一源码在不同优化级别下的产物。这条式子说明审计结论对编译配置的敏感性必须被显式记录，否则同一 kernel 在不同机器上得到相反判定，评测就退化成环境指纹。

运行段的失效条件更隐蔽：输入分布 D 若只覆盖对齐、无边界、单批次形状，则越界写与竞态会被静默吞掉——错误结果落在未被检查的显存区域，oracle 只比较输出张量，看不到被踩坏的其他缓冲区。代价是显存：为捕获这类错误需要影子缓冲与哨兵填充，按输出规模线性放大占用；另一种做法是启用越界检查工具，代价是时延上升一个量级，且改变 kernel 的调度行为，使原本能复现的竞态不再复现。因此审计流水线必须区分“功能正确性运行”与“契约违反探测运行”，两者不能共用同一次执行。

评测段的系统代价集中在 oracle 本身。逐元素容差比较的复杂度是 O(N·d)，N 为元素数、d 为每元素比较开销；若 oracle 用高精度参考实现，参考实现本身的时延往往超过被测 kernel，使端到端吞吐测量失去意义。工程判断是：把正确性 oracle 与性能测量拆成两条独立执行路径，性能路径只做轻量校验和，正确性路径允许慢。下表给出四段各自的输入、输出与首要失效模式。

段输入输出首要失效模式
生成题干、形状约束、dtype源码与调用契约契约漏写导致后续判定无依据
编译源码、优化级别、arch二进制与寄存器/共享内存用量优化改变浮点顺序或消除检查
运行二进制、输入分布、哨兵缓冲输出张量、越界/竞态信号分布覆盖不足使错误不可见
评测输出、参考实现、容差 τ判定与性能计数oracle 时延污染吞吐测量

具体例子：一个归约 kernel 在契约里只写了“输出等于输入和”，没写累加顺序与容差。生成段因此不约束树形归约的划分方式；编译段在高优化级别下重排浮点加法；运行段用随机正态输入，误差恰好落在默认容差内；评测段判定通过。但换一组量级差异极大的输入，同一二进制误差超出容差，判定翻转。审计要拦住的正是这种“契约未闭合”的情形——题干拆解时必须把累加顺序、容差、输入分布三者写进契约，否则后面三段的所有观测都缺少可比基准。
