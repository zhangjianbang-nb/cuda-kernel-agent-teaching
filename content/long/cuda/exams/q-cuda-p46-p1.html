一 · 题干的三层结构：任务、约束、判据

《D2K-Bench》这个标题本身就是一个可拆解的命题。把它当成一道工程题来读，题干包含三层：第一层是任务（Turn Expert Designs into Efficient GPU Kernels），即把专家给出的设计意图翻译成可运行的 kernel 实现；第二层是执行者（LLM Agents），意味着输入不是单轮 prompt 而是一个 agent 在工具反馈下迭代的过程；第三层是判据（Efficient），效率不是“能跑”而是相对某个基线或理论上界的比值。读题时若只抓住“生成 kernel”这一层，就会漏掉 agent 的多轮性与效率判据的可度量性，而这两点恰恰决定了后面 pipeline 每一步的失败模式分类方式。

把这三层映射成可操作的输入输出，可以写出一个粗略的接口签名：输入是专家设计描述 D（可能包含算法伪代码、张量形状、数据布局、精度要求、目标硬件），输出是一个 kernel 产物 K 以及一组评测记录 E。agent 的中间状态是对话历史与工具调用轨迹 T。于是整条 pipeline 可以抽象为复合函数：

$$K, E = \mathcal{A}(D;\ \text{tools}=\{\text{compile},\text{run},\text{profile}\})$$

其中 \mathcal{A} 是 agent 策略，工具集决定了反馈信号的种类。这个式子的价值在于：它把“哪一步失败”变成“复合函数的哪一段返回值异常”——编译工具返回非零退出码是语法/类型层失败，运行工具返回错误码是语义/边界层失败，profile 工具返回的指标偏离 roofline 是性能层失败。三类失败对应三种不同的修复动作，读题时先把它们分开，才不会在后续分析中把“编译不过”和“跑得慢”混为一谈。

一个具体例子：专家设计若写明“对 M×N 矩阵做分块 GEMM，块大小 128×128，使用共享内存双缓冲”，那么 agent 首先要判断这是 CUDA C++ 还是 Triton 表达更自然，再决定是否引入 CuTe 的 layout 抽象。这个判断本身不是代码生成，而是表达介质选择，属于题干第一层与第二层交界处的考点。

二 · 编译步：输入是源码与构建描述，失败模式分四类

编译步的输入不只是 kernel 源码，还包括构建描述：目标架构（如 sm_80 与 sm_90 的指令集差异）、编译选项（优化级别、是否开启 fast math）、依赖头文件与链接库。输出是二进制或 PTX/SASS 中间产物，以及编译器诊断信息。失败模式可以按诊断信息的来源分四类：语法错误（parser 层）、类型/模板实例化错误（语义层）、架构不匹配（如使用了目标架构不支持的指令）、资源超限（寄存器数或共享内存超出硬件上限导致 launch 配置非法）。

其中资源超限这一类最容易被误判为“运行时错误”，因为它在编译期往往只表现为一个 warning 或 occupancy 提示，真正报错发生在 launch 时。工程上应把“编译通过但 occupancy 过低”单独列为一种失败模式，因为它不阻断执行却直接摧毁效率判据。可以用一个简单的占用率估算式来量化：

$$\text{occupancy} = \frac{\text{active warps per SM}}{\text{max warps per SM}},\quad \text{active warps} = \left\lfloor \frac{\text{regs per SM}}{\text{regs per thread}\times 32} \right\rfloor$$

这个式子说明寄存器压力如何通过整数除法截断直接压低占用率，是 agent 在编译步就该读取的信号，而不是等到 profile 步才发现。代价方面：编译步本身消耗的是编译时间与 token——agent 每轮修改源码后都要重新编译，若构建系统不做增量缓存，多轮迭代的编译时间会线性累积；而编译器诊断信息作为反馈文本进入上下文，又消耗 token 预算。一个具体例子：Triton kernel 的编译是 JIT 的，首次调用触发编译，若 agent 在循环里反复改变 block size，每次都会触发重新编译，编译时间成为迭代速度的瓶颈，这一点与 CUDA C++ 的离线 nvcc 编译在反馈时延上完全不同。

三 · 运行步：输入是 launch 配置与数据，失败模式分正确性与资源两类

运行步的输入是编译产物、launch 配置（grid/block 维度、共享内存大小、流）以及输入数据。输出是输出张量与运行状态。失败模式首先分正确性与资源两类。正确性失败包括：越界访存（表现为非法地址或静默错误结果）、竞态（缺少同步导致结果不确定）、数值偏差（浮点累加顺序不同导致与参考实现超出容差）。资源失败包括：launch 配置超出硬件限制、显存不足、超时。

这里的关键考点是“正确性 oracle 的构造”。运行步不能只判断“没崩”，还要判断“结果对不对”。一个最小 oracle 是参考实现比对，容差按数据类型设定：fp32 用相对误差，fp16/bf16 用更宽的绝对误差带。伪代码思路如下：

$$\text{pass} = \forall i:\ |y_i - \hat{y}_i| \le \tau_{\text{abs}} + \tau_{\text{rel}}\cdot|y_i|$$

这个判据的代价是它需要一份可信的参考实现，而参考实现本身的性能无关紧要、正确性必须无争议——通常用框架算子或 CPU 版本充当。若 agent 生成的 kernel 与参考实现都错，oracle 就失效，因此工程上要求参考实现独立于 agent 的生成路径。另一个代价是运行步的时延：正确性测试通常用小规模输入快速筛错，性能测试才用大规模输入，两者分开跑意味着两倍的 launch 开销与数据准备开销。一个具体例子：一个 reduction kernel 在 N 不是 block 大小整数倍时，若尾部处理缺失，小规模测试可能恰好整除而通过，大规模测试才暴露越界——这说明测试输入的形状选择本身就是考点，agent 需要主动构造非整除、非对齐的边界用例。

四 · 评测步：输入是计时与 profile 数据，判据是相对效率而非绝对时延

评测步的输入是运行步产生的计时数据与硬件计数器数据（如 NCU 采集的访存吞吐、SM 利用率、指令发射率），输出是效率判据的取值。这里必须区分两种计时口径：wall-clock 时延包含 launch 开销与同步开销，适合端到端收益评估；kernel-only 时延剔除这些开销，适合判断 kernel 本身的质量。两者混用会让“效率”失去可比性。

效率判据的构造是本题的核心考点之一。绝对时延没有意义，必须相对于某个上界。roofline 模型给出两个上界：访存受限时的带宽上界与计算受限时的算力上界，实际可达性能取两者较小值：

$$P_{\text{roof}} = \min\left(\frac{\text{BW}}{\text{bytes per FLOP}},\ \text{peak FLOPs}\right)$$

把实测性能除以 P_{\text{roof}} 得到 SOL（speed-of-light）比例，这就是“efficient”的可度量定义。代价在于：roofline 上界依赖对算法的算术强度估计，若 agent 对数据复用程度的判断错误（例如漏算了中间结果的写回带宽），分母就错，效率判据随之失真。另一个代价是 profile 采集本身的开销——NCU 逐 kernel 采集会引入可观的运行时膨胀，不能与计时跑在同一轮里，否则计时被污染。一个具体例子：一个融合了 bias-add 的 GEMM，若 agent 只按纯 GEMM 的 FLOPs 计算算术强度，会高估算力需求、低估带宽需求，从而误判自己已接近计算上界而停止优化，实际上瓶颈在写回带宽。

五 · 解题路径：从设计描述到可评测产物的四段映射

把上述四步串成解题路径，可以得到一张输入输出对照表，用来定位任一失败发生在哪一段：

阶段输入输出典型失败模式
读题/设计解析专家设计描述、形状、精度、目标架构算法骨架、表达介质选择、分块策略草案算术强度估计错误、布局假设与硬件不符
生成/编译源码、构建描述、编译选项二进制或 PTX/SASS、诊断信息语法/模板错误、架构不匹配、寄存器超限
运行launch 配置、输入数据、参考实现输出张量、状态码、正确性判定越界、竞态、容差超标、显存不足
评测计时数据、NCU 计数器、roofline 参数SOL 比例、瓶颈归类计时口径混用、算术强度错算、profile 污染计时

这张表的价值在于它把“agent 该看哪个反馈”变成查表动作：编译诊断信息只应触发源码修改，不应触发算法重构；SOL 比例偏低才应触发分块策略或数据布局的重新设计。若 agent 在编译失败时就去改算法，或在 SOL 偏低时只做语法微调，都是反馈信号与修复动作的错配，这是多轮迭代中最常见的 token 浪费来源。

解题路径还需要明确“表达介质”的选择判据。CUDA C++ 适合需要精细控制共享内存布局与同步的场景；Triton 适合以 tile 为单位、由编译器自动管理共享内存的场景，其代价是丧失对底层调度的直接控制；CuTe 适合需要显式 layout 代数推导的复杂数据重排；PTX 只在需要手写特定指令或规避编译器生成的低效序列时使用，代价是可移植性归零。这个选择本身消耗的是设计阶段的判断力，选错介质会导致后续所有迭代都在与工具的抽象阻抗作斗争。

六 · 需要调用的公式清单与调用时机

本题在解题路径上需要调用的公式不多，但每个都有明确的调用时机，误用时机比误用公式更常见。第一是占用率式，调用时机在编译步之后、运行步之前，用于判断 launch 配置是否可行；第二是正确性容差式，调用时机在运行步，用于判定输出是否可信；第三是 roofline 上界式，调用时机在评测步，用于把绝对时延转换为相对效率；第四是算术强度式，即 \text{FLOPs}/\text{bytes}，调用时机在读题阶段，用于预判瓶颈在算力还是带宽，从而决定分块策略的方向。

这四个公式构成一条判断链：读题阶段用算术强度定方向，编译阶段用占用率定可行性，运行阶段用容差定正确性，评测阶段用 roofline 定效率。任何一环缺失，agent 的迭代就会失去收敛依据——例如缺少算术强度预判，agent 可能在带宽受限的 kernel 上反复增大 tile 以提升计算密度，而实际瓶颈在写回，迭代方向从一开始就错了。这里的工程判断是：公式不是用来算数的，是用来决定“下一步该改什么”的。一个具体例子：当 SOL 比例显示访存吞吐已接近峰值而算力利用率很低时，正确的动作是减少数据搬运（融合算子、改变布局），而不是调整指令级并行；这个判断只能由 roofline 的两个上界对比得出，单看时延无法区分。

最后落在失败模式与反馈信号的映射上：编译诊断、运行状态码、正确性判定、SOL 比例这四种反馈各自对应不同的修复动作集合，agent 的策略设计应把这四种信号视为四个互不替代的通道，而不是压缩成一个“成功/失败”布尔值。压缩成布尔值会丢失定位信息，导致多轮迭代退化为随机搜索，token 消耗与编译时间随之失控。

读题即建模：把题干拆成可执行的约束集

D2K-Bench 的题干不是自然语言需求，而是一份隐式的规格书：专家设计里同时编码了数据布局、并行分解、数值语义与性能目标。读题的第一步是把这些维度显式化，形成一张“约束—产物”对照表，否则后续生成阶段会把专家设计中的某个不变量当成可选优化。以一次典型的 kernel 生成任务为例，题干通常给出算子语义（如归约、转置、卷积的某种变体）、输入张量的形状与 dtype、允许的误差界，以及一个隐含的 roofline 参照。拆解时应把语义部分与性能部分分开：语义部分决定正确性 oracle 的构造方式，性能部分决定 SOL 的判定口径。二者混在一起，就会出现“数值对了但带宽利用率不达标”或“跑得快但边界情形漏算”的双重失效。

题干成分对应考点失败模式
张量形状与 stride访存合并与 tile 切分非连续维度被当作连续，合并访存退化
dtype 与累加精度数值语义、归约顺序fp16 累加溢出或与 oracle 容差冲突
误差界正确性判定口径把 bitwise 相等当作唯一标准
性能参照roofline 定位、SOL 计算用峰值算力而非带宽上限估界

解题路径的给出必须停在“路径”层面：先确定并行分解的粒度（线程块映射到哪一维、共享内存承载哪一块），再确定同步点与流水线阶段数，最后才落到具体 API 选择（CUDA C++ 的 `__syncthreads`、Triton 的 block pointer、CuTe 的 layout 代数）。这里的关键公式是 roofline 的时间下界：

$$T_{\min} = \max\left(\frac{F}{P_{\text{peak}}},\ \frac{B}{BW_{\text{peak}}}\right)$$

其中 F 为浮点运算量、B 为必须搬运的字节数。读题阶段就要判断哪一项主导：若 B 主导，考点是访存模式与数据复用；若 F 主导，考点是指令级并行与寄存器压力。误判主导项会让整条生成路径偏离，例如在带宽受限的归约上堆砌 tensor core 指令，编译能过、运行也快，但 SOL 判定仍不达标。

这一节的边界在于：拆题只产出约束与路径，不产出 kernel 代码，也不替代后续的编译—运行—评测环节。它的失效条件是题干信息缺失——当专家设计未显式给出 stride 或容差时，agent 必须把缺失项标记为待验证假设，而不是自行填补；否则正确性 oracle 会继承一个未经确认的语义。系统代价体现在 token 与编译时间上：约束表越细，prompt 越长，单轮生成消耗的上下文预算越高；而过早锁定 tile 尺寸等参数，会把后续多轮 RL 的搜索空间压窄，使编译失败后的回退代价变大。工程判断是：拆题粒度应恰好覆盖“能被 oracle 判定”的维度，超出部分留给执行反馈去修正。
