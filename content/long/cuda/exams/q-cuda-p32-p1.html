一 · 题干的三层结构：从“加速比”这个词开始拆

这道题表面在问一个除法，实质在问三件事：加速比的定义域、论文给出的六个数字各自处在什么测量条件下、以及跨条件比较时哪些量必须被固定。读题时先把题干切成三层。第一层是符号层：基线时延 T0、候选时延 T1，要求写出 speedup 表达式。第二层是语义层：论文中 43.7、77.0、14.8、21.8、97.4、72.9 这组数字不是同一实验的重复测量，而是分布在不同 kernel、不同基线选取、不同输入规模上的结果，因此“这个数字”指代不明。第三层是工程层：什么条件下两个加速比可以相除、相减或排序，什么条件下只能并列陈述。

考点因此不在算术，而在“可比性”的判定链条：测量对象是否同一、基线是否同一实现、输入形状与数据类型是否同一、计时口径是否含启动开销与同步、是否经过同一编译器与同一 GPU 配置。任何一环不同，speedup 就退化为一个只对本实验有效的局部量。解题路径应当是先给出公式与口径，再建立一张可比性检查表，最后用论文的六个数字做反例演示——而不是直接宣布某个数字“更高所以更好”。

$$\text{speedup} = \frac{T_0}{T_1},\qquad \text{slowdown} = \frac{T_1}{T_0} = \frac{1}{\text{speedup}}$$

这个式子的代价藏在 T 的定义里。若 T 取端到端墙钟时间，则包含 host 侧 launch、参数打包、同步与内存分配；若取 device 侧 kernel 时间，则排除上述开销。两者在小 kernel 上可差出一个数量级，因为 launch 开销是常数项而 kernel 本体随时延缩小。用 T = T_launch + T_kernel 展开，加速比变为

$$\text{speedup} = \frac{L + K_0}{L + K_1}$$

当 K_1 → 0 时该比值上界为 (L + K_0)/L，即 launch 开销本身构成了加速比的天花板。这解释了为什么同一份候选代码在墙钟口径下与 device 口径下会给出两个不同的数字，也解释了为什么论文里那些大数值必须连同计时口径一起读。

二 · 六个数字的定位：它们不是同一个量的六个样本

43.7、77.0、14.8、21.8、97.4、72.9 这六个数值，在题干给定的事实中只被描述为“论文报告的加速比”，并未给出各自的基线、kernel 与输入。这恰恰是考点：在没有这些元信息时，六个数字构成的是一个集合而非一个序列，不能求均值、不能取最大者作为“代表性能”、不能两两相除得出“改进倍数”。工程上正确的处理是把每个数字写成带下标的四元组：

$$\text{speedup}_i = \frac{T_0^{(i)}}{T_1^{(i)}}\Big|_{\,\text{kernel}_i,\ \text{shape}_i,\ \text{baseline}_i,\ \text{timer}_i}$$

只有当四个下标全部一致时，两个 speedup 才可比较。举例说明不可比的典型情形：若 97.4 对应的基线是一个未做向量化的朴素实现，而 14.8 对应的基线是厂商库中已高度调优的实现，那么 97.4 更大并不表示那份候选代码更快——它只表示它面对的基线更弱。同理，若 77.0 的输入规模远大于 21.8 的输入规模，前者可能受益于更充分的并行度填充，后者可能被固定开销主导，两者的比值差异反映的是 roofline 上工作点的位置差异，而非代码质量差异。

可比性维度一致时不一致时的后果代价形态
基线实现可直接排序加速比混入基线强弱结论失真，非时延代价
输入形状/数据类型可直接排序工作点漂移，roofline 区间不同带宽/占用率主导项改变
计时口径可直接排序常数开销被计入或排除小 kernel 上可达数量级差
编译与 GPU 配置可直接排序寄存器压力、occupancy 不同编译时间与显存占用改变

这张表本身就是解题路径的骨架：先逐项核对，再决定能否比较。注意表中“代价形态”一列——不可比并不总是表现为时延数字错误，有时表现为编译时间膨胀（例如为追求更高加速比而展开大量模板导致编译时间上升）、显存占用上升（更大的 tile 或更多驻留块）、或 token 消耗上升（多轮生成中为搜索更优实现而反复采样）。这些代价在只报一个 speedup 数字时全部被隐藏。

三 · 解题路径：从公式到判定，再到反例

建议的作答顺序是四步。第一步写出 speedup 与 slowdown 的互逆关系，并声明 T 的口径（墙钟或 device），因为口径决定了后续所有讨论的边界。第二步给出可比性四元组，把六个数字各自视为独立实验的结果。第三步构造反例：任取两个数字，假设它们来自不同基线或不同形状，演示为何不能相除。第四步给出“若要比较应当怎么做”的操作性建议，例如固定基线、固定 shape、固定计时方式后重跑，或改用相对 roofline 的 SOL 比例作为归一化指标。

第三步的反例可以写得很具体。设 43.7 来自某 kernel 在基线为朴素实现时的结果，72.9 来自另一 kernel 在基线为较优实现时的结果。若直接把 72.9 与 43.7 相减得出“后者更优 29.2”，这个差值没有任何物理意义，因为两个分母不同。正确的表述是：在各自实验条件下，候选相对各自基线分别取得 43.7 倍与 72.9 倍加速；跨实验的优劣判断需要重新建立共同基线。这一步的代价是重跑实验所需的 GPU 机时与编译时间，以及为对齐 shape 而可能引入的显存压力。

第四步涉及一个替代指标。当基线难以统一时，用候选达到的 SOL（speed of light）比例替代裸加速比：

$$\text{SOL} = \frac{\text{achieved}}{\text{roofline bound}} = \min\!\left(\frac{\text{FLOPs}/T}{\text{peak FLOPs}},\ \frac{\text{Bytes}/T}{\text{peak BW}}\right)^{-1}\ \text{的倒数形式}$$

更常见的写法是直接取达成率 achieved / bound，其中 bound 由算术强度与峰值算力/带宽共同决定。SOL 的好处是分母由硬件参数决定而非由某个实现决定，因此跨 kernel、跨 shape 具备可比性；代价是需要准确的 FLOPs 与字节计数，且对 roofline 模型的假设（缓存命中、峰值可达性）敏感。这一步把“加速比不可比”的问题转化为“归一化基准是否可靠”的问题，是本题从算术走向工程判断的关键转折。

四 · 需要调用的公式清单与各自的失效边界

本题可调用的公式不多，但每个都有失效边界，写出边界比写出公式更能体现工程背景。除 speedup 定义与 launch 开销展开外，还应准备算术强度与 roofline 交点：

$$I = \frac{\text{FLOPs}}{\text{Bytes}},\qquad P_{\text{attainable}} = \min(P_{\text{peak}},\ I \cdot BW_{\text{peak}})$$

该式用于判断某 kernel 处于计算受限还是带宽受限区间，从而解释为何同一候选在不同 shape 下加速比差异巨大。失效边界是：当 kernel 受延迟而非吞吐限制（例如小 batch、低并行度、串行依赖链），roofline 上界不再紧致，此时加速比更多由 launch 开销与占用率决定，而非由 I 决定。

另一个需要准备的是有效带宽与占用率的粗算，用于解释候选实现是否真的吃满了硬件：

$$BW_{\text{eff}} = \frac{\text{Bytes moved}}{T},\qquad \text{occupancy} = \frac{\text{active warps}}{\text{max warps per SM}}$$

这两个量本身不是加速比，但它们是把一个孤立 speedup 数字还原为物理图像的工具。代价在于：Bytes moved 需要区分全局访存与缓存复用，粗算容易高估；occupancy 高不等于性能高，寄存器压力导致的 spill 会让高占用率反而变慢，此时显存流量上升、有效带宽下降。

举例：若某候选把 tile 从 32 扩大到 128，寄存器压力上升导致 occupancy 下降，但全局访存次数减少，净效果可能是加速比上升而 occupancy 下降。若只报加速比，读者会误以为占用率也改善了。这就是为什么解题时必须把“加速比 + 计时口径 + 关键资源指标”三者并列，而不是只给一个数。

五 · 把六个数字放回生成—验证回路里看

这六个数字的另一层考点是它们在生产流程中的位置。LLM/agent 生成 kernel 的回路通常是：采样候选 → 编译 → 正确性 oracle 比对 → 计时 → 反馈进下一轮。加速比是计时环节的产物，但它只有在正确性通过后才有意义。若候选在某个 shape 上数值正确、在另一 shape 上越界或精度不符，那么对应的 speedup 数字描述的是一个不可部署的实现。因此读这六个数字时应当追问：每个数字背后是否附带了正确性验证的范围（哪些 dtype、哪些边界 shape、容差多少）。题干未给出这些信息，这本身就是不可比的一个来源。

回路中的另一个代价是 token 与编译时间。为得到更高的加速比，agent 往往需要多轮采样与多次编译尝试；每轮尝试消耗生成 token，每次编译消耗墙钟时间。若某数字是在大量采样中挑出的最优者，那么它带有选择偏差（best-of-n），与单次生成得到的数字不可比。这一点在比较多轮 RL 训练前后的模型时尤其关键：训练后的模型可能单次通过率更高，但报告的最大加速比未必上升，因为最大值受采样预算影响。工程判断应当是同时报告分布（中位数、通过率）与极值，而不是只报极值。

具体例子：假设某候选在 21.8 倍的条件下来自一次通过，而在 97.4 倍的条件下来自数十次采样后的择优。两者若并列，会让读者误判模型的稳定生成能力。正确的读法是：97.4 描述的是搜索上限，21.8 描述的是更接近单次生成的典型值；二者之间的差距反映的是采样预算，而非代码质量。这一判断不需要任何新数字，只需要把“选择偏差”这一机制讲清楚。

六 · 落到判定规则：什么条件下这个数字才可用

最后把解题路径收敛为一条可执行的判定规则，供作答时直接引用。一个 speedup 数字可用于跨实验比较，当且仅当：基线实现相同或基线强弱已被量化；输入 shape 与 dtype 相同或已归一化到同一 roofline 工作点；计时口径相同且常数开销的处理方式一致；正确性验证范围覆盖被比较的所有 shape；采样预算相同或已声明为极值/典型值。五条中任一条不满足，该数字只能作为本实验的局部结论陈述，不得参与排序或求均值。

这条规则的工程价值在于它把“43.7 与 77.0 谁更好”这种伪问题转化为一张检查表。作答时先写公式，再写四元组下标，再写检查表，最后用六个数字中的任意两个演示违反某一条后的后果——例如基线不同导致加速比混入基线强弱，或计时口径不同导致小 kernel 上常数开销主导。整条路径不依赖任何未给定的实验数字，只依赖题干给出的符号与那六个数值的存在性，因此是自洽的。

需要强调的是，判定规则本身也有代价：严格执行它意味着每次比较都要重跑基线、对齐 shape、统一计时，这会消耗 GPU 机时与编译时间，并可能因显存限制而无法覆盖最大 shape。工程上的折中是分层报告：在同一实验内给出可比数字，跨实验只给 SOL 达成率与定性描述。这一折中不是回避问题，而是承认加速比是一个条件量，其意义由测量条件定义。

加速比口径的边界：分母是谁、在什么机器上、测的是哪一段

题干里“报告的加速比如何计算”看似一行公式，真正的考点在分母的定义与测量边界。论文口径是 $$\mathrm{speedup}=\frac{T_0}{T_1}$$，其中 T0 为基线时延、T1 为候选时延；但 T0 究竟是 PyTorch eager、编译后的 torch.compile、还是厂商库调用，T1 是否含 kernel launch 与同步开销、是否剔除首次 JIT/autotune 的预热轮，都会让同一个候选读出不同的比值。工程上必须把计时区间钉死为“稳态多次迭代的墙钟时间除以迭代数”，并把预热、编译、autotune 单列，否则 43.7 与 77.0 这类数字之间的差距无法归因于 kernel 本身。

失效条件集中在三类不可比情形。其一是分母被替换：若基线是未融合的多算子序列，而候选是单个融合 kernel，则加速比里混入了“算子融合收益”而非“生成质量收益”，此时 97.4 这类高值反映的是融合空间而非模型能力。其二是硬件与形状绑定：同一候选在 H100 与 A100 上的 T0/T1 比值不同，且 batch size、序列长度、dtype 一变，roofline 上的工作点就从带宽受限滑向算力受限，21.8 与 72.9 之间的落差往往来自工作点迁移而非实现退化。其三是测量口径不一致：若 T0 取自论文引用的公开基线、T1 取自本地实测，两者的同步策略、时钟频率、显存状态都不同，比值不具备统计意义。

系统代价必须与加速比同时报告，否则该数字不可复现。候选侧要付出编译时间（Triton autotune 的候选配置搜索、CuTe 模板实例化、PTX 到 SASS 的 ptxas 阶段）与显存代价（融合 kernel 的寄存器压力上升会压低 occupancy，进而反噬 T1）；评测侧要付出正确性 oracle 的运行开销与多轮采样的 token 成本。一个可操作的判据是：只有当 T0 与 T1 在同一设备、同一输入分布、同一预热策略下测得，且编译与预热开销被显式扣除时，14.8 与 43.7 才可放在同一张表里比较；否则应把加速比降级为“同口径相对值”，并附上 T0 的来源标注。
