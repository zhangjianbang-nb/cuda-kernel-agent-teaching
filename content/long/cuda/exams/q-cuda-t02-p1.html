一 · 把题干拆成三个可独立证伪的子命题

题干只有一句话，但它内部至少压了三个命题，混在一起答就会失焦。第一个命题是「存在一个被称作 SOL 归一化评分口径的东西」，即评分函数 score = f(实测性能, 理论上界) 的具体形式；第二个命题是「它成立依赖于一组假设」，即该口径在什么条件下是有效度量；第三个命题是「线上出现相反现象时，归因可以二选一」，即公式错还是负载变。读题的第一动作是把这三层剥开：口径是什么、假设是什么、归因判据是什么。三者不是并列关系，而是链式依赖——不知道口径的构造，就说不清它依赖哪些假设；说不清假设，就无法判断「相反现象」究竟证伪了哪一条。

注意题干用的是「相反现象」而不是「分数偏低」。这是一个刻意的措辞：SOL 归一化评分通常把实测吞吐或时延与一个理论上界做比值，分数越高表示越接近上界。所谓相反，指的是分数给出的排序或结论与线上真实收益方向不一致——比如离线评分里 A kernel 优于 B，线上端到端却是 B 带来更大收益；或者评分显示某 kernel 已接近饱和，线上却仍有可观优化空间。因此解题路径的第一步不是算分，而是明确「相反」的判定维度：是绝对分数反向，还是相对排序反向，还是分数与端到端收益的相关性反向。这三种「相反」对应的归因逻辑完全不同，混答会直接丢分。

考点由此可以列举。其一是口径构造能力：能否写出归一化评分的分子分母，并说明分母那个「理论上界」是怎么来的（roofline 的算术强度分段、SOL 的时间下界、还是某个 memory-bound/compute-bound 判据）。其二是假设审计能力：能否列出该上界成立所依赖的物理与工程假设，并指出每条假设被违反时分数会朝哪个方向偏。其三是归因方法论：能否给出一个可操作的判别流程，把「公式错」与「负载变」区分开，而不是靠直觉。其四是代价意识：任何判别手段本身都有成本——重跑 profile 的时延、NCU 采集的显存与带宽开销、多轮采样的 token 消耗、编译期重算上界的时间。

二 · 归一化评分口径的形式与被它隐藏的分母

典型形式可以写成实测时间与理论最短时间之比，再取倒数或补数映射到 [0,1]：

$$ \text{score} = \frac{T_{\text{SOL}}}{T_{\text{measured}}},\qquad T_{\text{SOL}} = \max\!\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right) $$

这个式子的关键不在分子，而在 T_SOL 的构造：它取计算下界与访存下界的较大者，等价于假设 kernel 要么被算力卡住、要么被带宽卡住，二者不会同时成为瓶颈，且不存在第三类瓶颈。分母里藏了至少四个隐含参数：峰值算力 P_peak 取的是哪一档（FP32 还是 TF32/BF16 张量核）、峰值带宽 B_peak 是 HBM 理论值还是可持续值、FLOPs 是否计入了被算法省掉的冗余计算、Bytes 是否只算必需流量而忽略中间张量的往返。任何一个参数取错，T_SOL 就不再是「下界」而变成「某个参考实现的时间」，归一化随之失去意义。

代价在这里第一次出现：把 Bytes 算准需要知道数据复用模式，而这依赖 tile 尺寸与片上存储层级；把 P_peak 取成理论峰值会让分数系统性偏低（因为真实 kernel 达不到理论峰值），取成实测微基准峰值又会让分数虚高且随机器漂移。工程上常见的折中是固定一套「口径常量」并随硬件代际更新，代价是跨代比较失真。举一个具体例子：一个 elementwise 加法 kernel，Bytes 为两读一写共 3N 个元素，算术强度极低，T_SOL 完全由带宽项决定；此时若评分口径误把 FLOPs 项当作主导，分数会给出一个与带宽无关的虚高值，而线上该 kernel 的收益几乎只随有效带宽变化。这就是「分母构造错误」这一类失效的最小实例。

三 · 假设清单：每一条都对应一个可观测的违反信号

把假设写成可审计的条目，而不是笼统说「理想条件」。第一条是稳态假设：kernel 运行时间远大于启动与同步开销，评分不把 launch latency、stream 同步、host-device 拷贝计入分母。违反信号是 kernel 时长与总时延同量级，此时分数再高也不代表端到端收益。第二条是单瓶颈假设：roofline 的 max 形式默认只有一类资源饱和。违反信号是 NCU 显示 SM 利用率与 DRAM 利用率同时处于中高水平，说明存在混合瓶颈或流水线气泡，T_SOL 被低估、分数被高估。第三条是流量封闭假设：Bytes 只计必需流量，假设没有额外中间张量落盘或重复读。违反信号是实测 DRAM 流量显著高于按张量尺寸估算的值。

第四条是峰值可达假设：P_peak 与 B_peak 是 kernel 在该数据布局与指令组合下可逼近的上限。违反信号是同一 kernel 换一种指令（如从 FP32 FMA 换到张量核 MMA）后分数跳变，说明原口径的峰值取错了档位。第五条是负载不变假设：评分所依据的问题规模、batch、序列长度、数据分布与实际线上一致。这条最容易被忽略，也恰恰是「负载变了」这一归因的落点。第六条是可复现假设：同一 kernel 多次测量的方差远小于评分差距，否则排序结论本身不可信。

假设违反时的分数偏向可观测信号判别代价
稳态（忽略启动开销）偏高kernel 时长 ≈ 端到端时延低，计时即可
单瓶颈（max 形式成立）偏高SM 与 DRAM 利用率同时中等中，需 NCU 采集
流量封闭偏高实测 DRAM 流量 > 估算流量中，需计数器
峰值可达（档位正确）双向换指令后分数跳变高，需重写变体
负载不变双向规模/shape 与线上不一致低，比对配置
可复现（低方差）排序不可信重复测量离散度大低，多次采样

这张表的用法不是逐条打勾，而是把它当作归因的候选集：当线上出现相反现象时，先问「哪条假设最可能被线上负载破坏」，再问「破坏后分数应该朝哪个方向偏」，最后看观测到的偏移方向是否吻合。方向吻合则倾向「负载变了」，方向不吻合则倾向「公式错了」。这就是解题路径里归因判据的骨架。

四 · 解题路径：从口径复算到反事实对照

给出路径而不给结论。第一步是口径复算：拿到评分实现，把 T_SOL 的每个输入参数显式列出，用线上实际 shape 重算一遍 T_SOL，看分数是否变化。若重算后排序翻转，则「负载变了」已被证实到相当程度，因为公式没动、只有输入动了。第二步是反事实对照：固定线上负载，人为构造一个已知应被算力卡住的 kernel 和一个已知应被带宽卡住的 kernel，分别打分，检查分数是否落在预期区间。若两个本应差异明显的 kernel 得到接近的分数，说明 max 分段或峰值档位取错，倾向公式错。

第三步是剖面交叉验证：用 NCU 采集实际瓶颈资源，与 T_SOL 所假设的瓶颈资源比对。若 NCU 指认的瓶颈与公式假设的瓶颈不一致，且该不一致在多个 kernel 上稳定复现，则公式的分段判据有系统性缺陷；若不一致只在特定 shape 上出现，则是负载域偏移。第四步是端到端回归：把评分与线上端到端收益做秩相关，观察相关性是否随负载漂移而下降。相关性在旧负载上高、在新负载上低，指向负载变；在两个负载上都低，指向口径本身与收益脱钩。

$$ \rho = 1 - \frac{6\sum d_i^2}{n(n^2-1)} $$

这里 d_i 是同一 kernel 在评分排序与端到端收益排序中的名次差，n 是参与比较的 kernel 数。用秩相关而非线性相关，是因为评分与收益的量纲不可比，且工程上真正关心的是排序是否一致。代价是样本量 n 小时 rho 的置信度低，需要更多 kernel 变体或多次采样，而每多一个变体就多一次编译与 profile 的时延开销；若用 agent 自动生成变体，还额外消耗生成 token 与验证轮次。这是判别流程绕不开的成本，也是为什么工程上倾向先用低成本的「口径复算」筛一遍，再决定是否动用 NCU 与端到端回归。

五 · 需要调用的公式与判据，以及它们的适用边界

解题时需要能随手写出三组公式。第一组是 roofline 分段与算术强度：

$$ I = \frac{\text{FLOPs}}{\text{Bytes}},\qquad T_{\text{SOL}} = \max\!\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right) $$

它的适用边界是单瓶颈；一旦 I 落在拐点附近，两条下界接近，实测往往同时受两类资源制约，max 会高估可达性能。第二组是有效带宽与有效算力的折算，用来判断峰值假设是否被违反：把实测流量除以实测时长得到有效带宽，与 B_peak 比较；若有效带宽超过口径里的 B_peak，说明口径常量取低了，分数被系统性压低，这本身就是公式错的直接证据。第三组是方差判据，用重复测量的相对离散度决定排序结论是否可信：离散度与评分差距同量级时，任何「相反」都可能是噪声而非信号。

具体例子：一个 reduction kernel 在小 batch 下 Bytes 很小、启动开销占比高，稳态假设被违反，评分给出的高分与线上收益背离；把 batch 放大后 Bytes 主导，分数回落但线上收益上升。此时若只看分数会误判为「公式错」，而按路径第一步用线上 shape 重算 T_SOL，会发现分母随 batch 变化而分子（实测时间）变化更剧烈，归因应落在负载域而非公式。这个例子的价值在于它同时踩中稳态假设与负载不变假设，正好演示「方向吻合」判据如何把两个候选分开：稳态违反使分数偏高，负载变化使分数与收益脱钩，两者叠加时观测到的偏移方向仍可由重算区分。

还要提醒一个易错点：不要用「分数是否接近 1」当作公式正确性的证据。分数接近 1 只说明实测逼近了该口径下的上界，而上界本身可能取错；反过来分数远低于 1 也可能是口径常量过于乐观。正确性的判据只能是「口径假设与线上负载是否匹配」以及「排序是否与端到端收益一致」，这两条都需要外部观测，不能从分数自身读出。

六 · 读题时就要标记的陷阱与作答边界

第一个陷阱是把「SOL」当成一个唯一确定的量。实际上 SOL 依赖峰值档位、流量口径、瓶颈分段三组选择，不同选择给出不同的 T_SOL，因此题干问「在什么假设下失效」时必须先声明自己用的是哪一套口径，否则答案无法被检验。第二个陷阱是把「线上相反现象」直接等同于「公式错」。线上收益受端到端流水、调度、内存压力、并发争用影响，评分只覆盖单 kernel 的局部上界，二者的差异可能来自评分口径之外的系统层，归因时必须把「口径覆盖范围」作为第三个候选，而不是在公式错与负载变之间二选一硬凑。

第三个陷阱是忽略判别手段自身的代价。NCU 采集会改变 kernel 的运行时序（采集开销、时钟锁定），用采集数据反推稳态性能本身就有偏差；多轮 agent 生成变体做反事实对照会消耗可观的编译时间与 token，且变体质量参差会污染秩相关。作答时应把「先低成本复算、后高成本剖面」写成有次序的流程，并说明每一步的判据与停止条件，而不是罗列所有手段。第四个陷阱是把假设清单写成泛泛的「理想条件」，没有对应的可观测信号——那样的清单无法支撑归因，考场上也拿不到分。

作答边界要清楚：本部分只拆题、列考点、给路径与公式，不给出「哪条假设最常失效」的结论，也不给出「相反现象时该判为公式错还是负载变」的最终答案。真正需要落地的是那条判据链——重算 T_SOL 看排序是否翻转、反事实对照看分段是否合理、NCU 看瓶颈是否与假设一致、秩相关看评分与收益是否脱钩——四步各自对应一个可观测信号和一个代价，缺任何一步，归因都只是猜测。
