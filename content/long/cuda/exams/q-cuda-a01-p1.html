一 · 题干里的四个锚点：TF32、编译基线、一次流动、拆步

这道题的题干只有十几个字，但它同时压了四层约束，任何一层读漏都会把答案写成泛泛的“生成—优化—验证”三段式。第一层是数值格式锚点：TF32 不是“低精度”的同义词，它是 19 位尾数（10 位显式尾数加隐含位）、8 位指数、与 FP32 同宽的存储占位，在 Ampere 及以后的 Tensor Core 上以 mma.sync.aligned.m16n8k8.f32.tf32.tf32.f32 一类指令形态出现。这意味着题干要求你讨论的不是“把 FP32 换成 FP16 省带宽”，而是“在保持 FP32 累加器与 FP32 显存布局的前提下，把乘法输入截断到 10 位尾数”。第二层是编译基线锚点：所谓 baseline 不是手写 CUDA 参考实现，而是“同一份源在给定编译选项下由 nvcc/ptxas 产出的 SASS”，它把优化目标从“跑得快”钉死为“相对这条 SASS 的 roofline 差距”。第三层是流动锚点：一次 kernel 的生成、优化、验证必须构成一条有向流水线，每一步的输出是下一步的输入，不允许回跳成无状态的重试。第四层是拆步锚点：题目问的是“拆成哪几步”，答案必须是可命名的阶段，而不是“先这样再那样”的散文。

考点因此可以精确列举：其一，你是否知道 TF32 的误差结构是“输入截断误差”而非“累加误差”，从而把正确性 oracle 的容差设计放在输入侧；其二，你是否能把编译基线写成可复现的产物（SASS 文本 + 资源占用 + 指令计数），而不是一句“用 -O3”；其三，你是否理解流动的每一步都要付出 token、编译时间或显存代价，并且这些代价在阶段之间是耦合的；其四，你是否能把“验证”拆成正确性与性能两条互不替代的判据。解题路径由此确定：先做题干到考点的映射表，再为每个考点指定一个可调用的公式，最后把公式串成阶段间的接口契约。

二 · 拆题干：把自然语言问句翻译成阶段接口

把题干逐词拆开，能得到四个必须回答的子问句，每个子问句对应一个接口。(a)“按一次 kernel”——主语是单次 launch，因此流动的粒度是“一个 kernel 实例”，不是“一个模型”或“一个算子族”；接口上要求每一步的输入输出都以该 kernel 的签名（grid/block、共享内存字节数、寄存器上限）为边界。(b)“生成”——输入是自然语言或参考实现加形状约束，输出是候选源文本（CUDA C++ / Triton / CuTe DSL / 内联 PTX 之一），代价是采样 token 数与首次编译时间。(c)“优化”——输入是候选源加基线 SASS 加 profile 数据，输出是改写后的源或编译选项组合，代价是每轮编译时间与 NCU 采集的 replay 开销。(d)“验证”——输入是改写后的源与其运行结果，输出是布尔判据（正确性）与标量判据（相对基线的加速比或 SOL 占比），代价是参考实现的运行时间与容差比较的显存。

这里的关键工程判断是：不要把“生成”和“优化”合并成“让模型一次写出好代码”。合并会消灭接口，导致优化阶段无法引用基线 SASS 作为输入，也就无法回答“相对谁优化”。同理，不要把“验证”放在优化之前作为门禁，因为 TF32 候选在未优化时往往已经数值正确，先验证会浪费一次完整编译；正确做法是验证作为流动的末端闸门，但把轻量正确性冒烟测试（小形状、单 block）前置到生成阶段末尾，用极小代价拦截语法与越界错误。

一个具体例子：题干若给出“矩阵乘 C=A·B，A/B 为 FP32，允许 TF32”。拆解后生成阶段的输入必须显式携带 M/N/K 与 leading dimension，因为 TF32 的 tile 形状（m16n8k8）决定了 K 必须是 8 的倍数才能无尾块；若题干未给形状，生成阶段就必须输出一个形状断言而非默认值。这个断言就是接口契约的一部分，缺了它，后续优化阶段无法判断“尾块处理”该不该计入代价。

三 · 考点对应的可调用公式：误差、roofline 与编译代价

TF32 的正确性考点需要一个可计算的误差上界，而不是“精度够用”的定性话。设输入 a 被截断为 a'，截断误差满足 |a − a'| ≤ 2−11·|a|（10 位显式尾数对应相对精度 2−11）。单次乘加的误差由输入误差主导，累加在 FP32 中进行，其舍入误差为 2−24 量级，远小于输入截断项。因此 K 项点积的误差上界可写成：

$$|\hat{c}-c| \le \sum_{k=1}^{K} 2^{-11}\,|a_k|\,|b_k| + K\cdot 2^{-24}\max_k|a_k b_k|$$

这条公式直接决定验证阶段的容差：容差必须随 K 与输入幅值缩放，写成固定绝对阈值（如 1e-3）在 K 较大时必然误判。代价方面，容差越松，假阳性（把错误 kernel 判为正确）概率越高；容差越紧，假阴性（把正确 kernel 判为错误）概率越高，两者都消耗一次完整重编译的 token 与时间。工程上把容差写成相对形式并乘以 K 的平方根量级，是这条公式给出的唯一可辩护选择。

性能考点对应 roofline。设 kernel 的算术强度为 I = FLOP / Byte，机器峰值算力 P、峰值带宽 B，则可达性能上界为 min(P, I·B)。TF32 的考点在于：Tensor Core 的 TF32 峰值通常是 FP32 FMA 峰值的数倍，但输入仍是 FP32 存储，因此 I 的分母没有变小，roofline 拐点向高算术强度一侧移动。用公式表达相对基线的加速上限：

$$\text{speedup}_{\max}=\frac{\min(P_{\text{tf32}},\,I\cdot B)}{\min(P_{\text{fp32}},\,I\cdot B)}$$

当 I·B < P_fp32 时该比值恒为 1，即带宽受限的 kernel 换 TF32 不会加速——这正是考点：题干要求“优化”，但优化阶段必须先判定该 kernel 是否落在带宽受限区，否则所有 TF32 改写都是零收益并白付编译时间。编译代价的公式化表达是每轮优化的总开销 T = n_compile·t_compile + n_profile·t_replay + n_token·t_token，其中 t_replay 是 NCU 为采集指标对 kernel 的重复执行时间，通常与 kernel 本身时长同阶甚至更高，因此 profile 次数必须被预算约束，不能每轮全量采集。

四 · 解题路径：把公式串成五步流动与接口契约

基于上述公式，流动可拆为五步，每步给出输入、输出与代价，并标注它调用哪条公式。第一步“读题与形状固化”：输入是题干与参考实现，输出是带形状断言与数值格式声明的 kernel 规格（含是否允许 TF32、累加器精度、tile 形状约束），代价是一次人工或模型侧的规格生成 token，不触发编译。第二步“基线锚定”：输入是同一规格下的参考源，输出是固定编译选项下的 SASS 文本、寄存器数、共享内存字节数与指令计数，代价是一次编译时间加一次静态反汇编；此步不调用误差公式，只建立性能分母。第三步“候选生成”：输入是规格加基线资源画像，输出是候选源，代价是采样 token 与首次编译；此步末尾插入小形状冒烟测试，调用误差公式的 K=小值特例做快速拦截。第四步“优化”：输入是候选源、基线 SASS、以及按预算采集的 profile 片段，输出是改写源或编译选项，代价是每轮编译与受限次数的 replay；此步调用 roofline 公式判定是否值得继续，若 I·B < P_fp32 则直接终止优化并记录“带宽受限，TF32 无收益”作为结论。第五步“验证”：输入是优化后源，输出是正确性布尔值与相对基线的加速比，代价是参考实现运行时间与容差比较显存；此步同时调用误差上界公式与 roofline 比值公式，前者定容差，后者定性能判据。

接口契约的关键在于相邻两步之间的数据格式必须可机读。基线锚定输出的 SASS 不能是自然语言描述，必须是可被优化阶段引用的结构化计数（例如每类指令条数、寄存器峰值），否则优化阶段无法回答“我的改写减少了多少条 FFMA、增加了多少条 LDS”。同理，优化阶段的输出必须携带“本轮改了什么”的差异描述，验证阶段才能把性能变化归因到具体改写而非编译噪声。一个具体例子：若候选把内层循环的 FP32 FMA 换成 TF32 mma，指令计数会从大量 FFMA 变为少量 mma 加额外的数据重排（ldmatrix/shfl），优化阶段必须输出这两类计数的前后对比，验证阶段才能判断加速比是否来自计算密度提升而非重排开销下降。

五 · 需要调用的公式清单与调用时机

把公式按调用时机列成表，可以避免在错误阶段用错判据。误差上界公式只在验证阶段做容差设计与冒烟测试时调用，绝不能在生成阶段用来“预估正确性”，因为生成阶段尚无实际数值。roofline 比值公式在优化阶段入口调用一次做可行性判定，在验证阶段再调用一次做性能归因，两次调用的输入不同（前者用理论峰值，后者用实测时长反推的有效算力）。编译代价公式贯穿优化阶段，用于决定 profile 采集次数上限。

误差上界生成末尾冒烟、验证K、输入幅值、容差布尔正确性参考运行时间、比较显存

这张表暴露了一个常见错误：把 roofline 比值当成验证阶段的唯一判据。加速比高但正确性容差被突破的候选必须被拒绝，反之正确但零加速的候选在“优化”语境下也不合格。两个判据是合取关系，缺一不可，这正是题干把“优化”与“验证”分成两步而非一步的原因。另一个具体例子：某候选在 K 较小时误差上界远低于容差，冒烟测试通过，但 K 放大后上界线性增长越过容差，验证阶段必须用实际 K 重算上界而不是复用冒烟阶段的结论——这就是公式必须随形状参数重新调用的工程含义。

六 · 拆步的边界判据：什么算一步，什么必须拆开

拆步不是越细越好，判据是“该阶段是否产生一个可被下游机读的新产物，且该产物无法由上游产物平凡导出”。按此判据，基线锚定必须独立成步，因为 SASS 与资源画像无法从源文本平凡导出（同一源在不同 ptxas 版本下寄存器分配不同）。候选生成与优化必须拆开，因为前者的产物是“能编译的源”，后者的产物是“相对基线有差异的源”，差异描述无法由候选源自身导出。验证必须独立成步，因为它的产物是布尔与标量判据，无法由优化阶段的差异描述导出。反之，“读题”与“形状固化”可以合并为一步，因为形状断言是规格的一部分，不构成独立产物。

边界判据还要求每步的失败模式可区分。生成阶段失败表现为编译错误或冒烟越界，代价是一次编译；优化阶段失败表现为差异描述为空或 roofline 判定为带宽受限，代价是零额外编译（直接终止）；验证阶段失败表现为容差突破或加速比低于阈值，代价是一次完整参考运行。三种失败若混在一步里，就无法判断该重试生成还是该放弃优化，token 预算会被无差别消耗。一个具体工程判断：当优化阶段连续若干轮差异描述只涉及编译选项（如 -maxrregcount）而不涉及源改写时，应判定该 kernel 已进入寄存器压力受限区，此时继续调选项的边际收益低于重新生成候选，流动应回到生成阶段而非在优化阶段内打转——这条判断的依据是编译代价公式中 n_compile·t_compile 已占主导而 n_profile 未带来新信息。

锚定失效的三种边界与流动代价核算

TF32/编译基线锚定这条路径的失效条件集中在三处。第一处是精度边界：当算子被判定为对 TF32 尾数截断敏感（例如累加链长、归约顺序改变导致误差放大），锚定值必须回落到 FP32 编译基线，此时“TF32 加速”这一考点实际不成立，解题路径要改写为“先证明 FP32 基线不可再压缩，再讨论是否值得引入分块累加补偿”。第二处是编译基线自身的可复现性边界：同一份源码在不同 nvcc 版本、不同 -arch 与 --use_fast_math 组合下生成的 SASS 不同，锚定值若取自不可复现的编译产物，后续所有优化收益的比较都失去参照。第三处是测量边界：基线锚定要求同一测量口径（同一 NCU section、同一 warmup 次数），口径漂移会让“优化后更快”变成伪信号。

流动拆解上，读题阶段要显式给出代价核算式。设单次生成-优化-验证循环的墙钟代价为 $$T_{loop}=T_{gen}+T_{compile}+T_{correct}+T_{profile}$$，其中编译项随模板实例化数量线性增长，profile 项随采集的 metric 组数增长。工程判断是：若 $$T_{compile}$$ 占比过高，应把编译基线锚定提前到生成阶段之前一次性完成并缓存，而不是每轮重编；若 $$T_{profile}$$ 占比过高，则只对通过正确性 oracle 的候选做全量 NCU 采集，其余仅做计时筛选。

具体例子：一个 reduction 类 kernel 的题干同时含“TF32 输入”“确定性归约”“带宽受限”三个考点，解题路径应先锚定 FP32 编译基线的 SOL 利用率，再判断 TF32 是否改变瓶颈类型（从带宽受限转为精度受限），最后才决定是否进入分块与向量化优化。此处的系统代价是显存占用（TF32 中间缓冲与 FP32 校验副本并存）与验证时延（双精度参考实现拖慢正确性判定）。
