一 · 题干的三层结构：策略、IR、约束

这道题的问法看起来像“解释公式”，实际考的是把一个模糊的生成问题拆成可计算的搜索问题。题干里“策略IR”与“DSL约束生成”是两个不同层次的东西，必须分开读：策略是搜索空间上的决策规则（在什么状态下选哪个变换、何时停止、预算怎么分配），IR 是策略作用于程序后留下的中间表示（变换序列、调度参数、tile 形状、内存层级选择），约束是 DSL 对合法 IR 的静态限制（形状整除、共享内存上限、线程数上限、对齐要求）。三者的关系是：策略在 IR 空间上产生候选，DSL 约束把候选裁成可行集，公式则描述“可行集大小 × 单次验证代价”如何决定搜索预算。

读题时第一个要抓的考点是：题干给的公式里，哪些量是策略可控的，哪些是约束决定的，哪些是硬件/编译器给定的常数。把这三类量分开，才能判断公式是在算“搜索空间规模”还是在算“单次尝试的期望代价”。很多读者一上来就逐项代数化简，结果把约束项当成可调参数，得出“加大预算就能覆盖”的错误结论——而约束项恰恰是让可行集从乘积变成稀疏子集的元凶。

第二个考点是量纲。策略 IR 的公式里通常同时出现“候选数”（无量纲计数）、“每次编译/验证的时延”（秒）、“显存占用”（字节）、“token 数”（生成侧成本）。这些量不能直接相加，必须通过预算约束（总时延上限、总显存上限、总 token 上限）分别写成不等式，再取交集。题干若只给一个等式，往往是在暗示某一维已经饱和，其余维才是瓶颈。

二 · 逐项拆解：每个符号对应一个工程对象

以典型的策略 IR 公式为例，形如：策略在深度 d 的搜索中，候选集大小由分支因子 b、可行率 ρ、剪枝阈值 τ 共同决定，写作

$$N(d)=\sum_{i=0}^{d} b^{i}\cdot\rho(i)\cdot\mathbb{1}\{\tau(i)\ge \tau_{\min}\}$$

逐项读：b 是每个 IR 节点上策略允许的变换分支数（例如 tile 大小候选、流水级数候选、向量化宽度候选的笛卡尔积），它是策略设计者直接写的超参；ρ(i) 是第 i 层候选通过 DSL 约束检查的比例，由约束的紧度决定，策略只能通过“提前把约束编码进生成”来抬高它，而不能任意设定；τ(i) 是剪枝打分（例如 roofline 预测的 SOL 下界或静态资源占用估计），τ_min 是进入下一层验证的门槛。指示函数把“打分不够”的候选直接排除，这一步的代价是假阴性：被剪掉的真优解不会再回来。

公式的第二层含义是它把“搜索预算”写成了对深度的求和而非对宽度的乘积。这意味着预算的主要消耗不在单层宽度，而在深度累积——每多一层，前面所有层的候选都要再乘一次分支。工程判断由此而来：当 ρ(i) 随深度快速下降时，加深搜索的边际收益低于加宽当前层；反之若 ρ(i) 稳定，深度优先更划算。题干要求“逐项解释”，实质是要求考生指出哪一项主导了 N(d) 的增长阶，而不是把符号念一遍。

第三层是约束项的位置。ρ(i) 若写成乘积形式 ρ(i)=∏_k ρ_k(i)，则每个约束因子 ρ_k 对应一条 DSL 规则，且各因子之间不独立——形状整除约束和共享内存约束会联合把可行率压到远低于各自单独作用的乘积。这是本题最容易被忽略的考点：约束的相关性使可行集不是乘积空间，因此不能用“每条约束的通过率相乘”来估预算，必须用联合采样或静态枚举来测 ρ。

三 · 算例的读法：先定可行集，再定预算

给定算例通常是一个具体 kernel（例如某个归约或矩阵乘变体）加上一组 DSL 约束和一次搜索记录。正确的读法不是直接代数，而是三步：第一步，把算例中的约束逐条翻译成对 IR 参数的取值范围，得到每个参数的合法区间；第二步，检查这些区间是否互相耦合（例如 tile 的 M 维必须被问题规模整除，同时 tile 的 M×N 又要落进共享内存上限），耦合处就是可行率 ρ 的塌陷点；第三步，用算例给出的单次验证代价（编译时间、NCU 采集时延、正确性 oracle 的运行时间）乘上可行集规模，得到预算下界，再与题干给的预算上限比较，判断是“预算不够”还是“约束太紧”。

这一步要调用两个公式。其一是可行集规模的估计：若参数向量 θ 有 m 个分量，每个分量合法取值数为 n_k，联合可行率为 ρ，则

$$|\Theta_{\text{feasible}}|=\rho\cdot\prod_{k=1}^{m}n_k,\qquad \rho=\frac{|\{\theta:\ \text{DSL}(\theta)=\text{true}\}|}{\prod_k n_k}$$

其二是预算等式：总预算 B 必须覆盖“生成 token 成本 + 编译时延 + 验证时延”三项，写作 B ≥ c_gen·|Θ| + t_compile·|Θ_compiled| + t_verify·|Θ_verified|，其中三个集合是逐级过滤后的子集。算例里若给出编译时延远大于验证时延，则预算瓶颈在编译，策略应优先提高 ρ 以减少进入编译的候选数，而不是加大分支因子。

具体到算例的一个典型形态：某 kernel 的 tile 参数在三个维度上各有若干候选，DSL 要求总共享内存不超过上限、线程数不超过上限、问题规模被 tile 整除。前两条约束各自砍掉一部分候选，第三条整除约束与 tile 形状强相关，三者叠加后 ρ 显著低于任一单条约束的通过率。考生若只按单条约束估 ρ，会高估可行集、低估预算，从而误判“预算充足”。算例给出的搜索记录里，被剪枝的候选数与实际进入编译的候选数之比，正是 ρ 的实测代理——这是题干埋的验证点。

四 · 解题路径：从公式到可执行判断

推荐路径是四步，每步产出一个可检验的中间结论，而不是直接跳到最终答案。第一步，标注公式中每个符号的“可控性等级”：策略超参、约束导出量、硬件常数，并写出各自的量纲。第二步，用算例数据估计 ρ 的两个版本——独立乘积版与联合实测版——并指出二者差异的来源，这一步直接对应考点“约束相关性”。第三步，把预算等式按瓶颈项排序，判断当前算例的瓶颈是生成侧 token、编译时延还是验证时延；若瓶颈是编译，则策略的优化方向是“更准的剪枝”而非“更多的候选”。第四步，给出一个敏感性判断：当分支因子 b 增加一档时，N(d) 的增长是否超过预算余量；当 τ_min 放松一档时，假阴性风险如何变化。四步走完，答案自然浮现，但本部分只到路径为止。

需要调用的公式清单应明确列出：可行集规模公式（含 ρ 的联合定义）、预算不等式（三项成本）、剪枝假阴性的期望损失（用 τ 分布与真实最优分布的重叠面积表示）、以及深度-宽度边际收益比较（N(d+1)−N(d) 与单层加宽的增量之比）。这四个公式分别对应题干中“规模”“预算”“正确性代价”“搜索策略”四个考点，缺一不可。特别提醒：假阴性损失这一项在算例中往往以“被剪掉但事后发现更优”的候选数体现，考生必须把它计入正确性代价，而不能只算时延。

性能代价的表述要落到具体量：ρ 每下降一档，进入编译的候选数按比例上升，编译时延线性增加；τ_min 每放松一档，假阴性期望损失上升，但编译候选数下降——这是一对反向权衡，算例的作用就是让考生在给定预算下找到这对权衡的可行点，而不是求一个“最优”。题干问“如何影响搜索预算或上线判断”，落点正在这里：预算判断看的是瓶颈项是否被 ρ 的塌陷击穿，上线判断看的是假阴性损失是否落在可接受区间。

五 · 易错点与工程判断的落点

第一个易错点是把 ρ 当成常数。实际上 ρ 随深度变化，且约束越往下越紧（深层 IR 参数更多、耦合更强），因此 N(d) 的求和不能把 ρ 提到求和号外。第二个易错点是把预算等式写成等式而非不等式：预算约束是“不超过”，瓶颈项饱和时其余项仍有压缩空间，写成等式会丢掉策略调整的自由度。第三个易错点是把剪枝阈值 τ_min 当成纯性能参数：它同时是正确性参数，放松它换来的是预算节省，付出的是漏掉更优解的风险，算例中若出现“被剪枝候选的预测分与实测分偏离”，就是这一风险的直接证据。

工程判断的落点是：在给定算例下，先判断可行集是否已经小到“枚举即可”，若 ρ·∏n_k 落在单次批量验证可覆盖的范围内，则策略应退化为静态枚举加剪枝，而非多轮搜索；反之若可行集远大于预算，则必须提高 ρ（把约束前移到生成侧）或提高剪枝精度（降低假阴性），二者选其一取决于瓶颈是编译时延还是正确性风险。这个判断不需要算出最终数字，只需要比较可行集规模与预算覆盖能力两个量级——这正是本题“逐项解释 + 算例影响”的合流处。

最后落在具体机制上：策略 IR 的公式之所以值得逐项读，是因为每一项都对应一个可以单独调节的工程旋钮，而 DSL 约束的联合作用决定了这些旋钮不是正交的。算例的价值不在于给出一个数，而在于暴露哪两个旋钮在给定约束下被绑死——绑死的那一对，就是搜索预算的真正边界，也是上线判断中“能否在预算内达到目标 SOL”的唯一决定因素。

约束生成的三类边界：语法可满足、语义可验证、预算可承受

把「策略IR与DSL约束生成」当成一个纯语法问题会立刻失效。它的核心公式通常写成搜索空间收缩的形式：给定候选 kernel 集合 K、DSL 约束谓词集合 C、以及每条约束的静态检查代价 c_i 与动态验证代价 v_i，有效搜索预算 B_eff = |K| · Π_i p_i − Σ_i (c_i + v_i)，其中 p_i 是约束 i 在候选集上的通过率。这个式子的每一项都不是装饰：p_i 由题干中给出的 tile 形状、dtype、对齐要求决定，c_i 是编译期可判定的部分（形状整除、共享内存上限、线程数上限），v_i 必须落到 GPU 上跑正确性 oracle 才能判定（越界、竞态、数值容差）。考点拆解的第一步就是判断某条约束落在哪一侧——落在语法侧的错误只会浪费编译时间，落在语义侧的错误会污染奖励信号。

边界条件有三类，必须逐项在题干里找证据。其一是可满足性边界：当 Π_i p_i 趋近于零时，约束集本身互斥，例如同时要求向量化 128-bit 访存与任意非对齐 stride，此时公式退化为空集，搜索预算归零，正确工程判断是放弃该 DSL 片段而不是加大采样。其二是可验证性边界：若某条约束只能靠 NCU/SASS profile 事后确认（如 bank conflict 上限），则 v_i 的量级是毫秒级每候选，乘以 |K| 后可能超过整轮搜索的时间预算，此时应把它降级为软约束进入打分而非硬过滤。其三是收益边界：约束收紧带来的 p_i 下降若快于无效候选的剔除速度，B_eff 反而缩小，这就是「约束越多越慢」的具体机制。

具体算例：题干给出一个 Triton 归约 kernel，要求 BLOCK 为 2 的幂、输入长度非 2 的幂、且禁止使用原子操作。拆解时先定位考点——BLOCK 的幂次约束是语法侧（c_i 极小），长度非整除是语义侧（需要 mask，正确性 oracle 必须覆盖尾块），禁原子则把跨 block 归约逼成两阶段或单 block 方案，直接改变搜索空间的拓扑。解题路径应写成：先用语法约束把候选压到可编译子集，再用一次小规模 oracle 筛掉尾块越界，最后才把带宽利用率作为软打分。需要调用的公式就是上面的 B_eff 与 p_i 估计，而不是直接给出某个 BLOCK 值——那属于下一部分算例展开的内容。这里的工程判断是：当 profile 级约束的 v_i 乘以候选数超过总预算的三成，就应改写 DSL，把该约束表达为编译期可判定的上界近似。
