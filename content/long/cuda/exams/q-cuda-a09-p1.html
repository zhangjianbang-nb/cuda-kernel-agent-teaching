一 · 把题干拆成可执行的四个槽位

“NCU 指标回灌”这个说法本身不是一条流水线，而是一个闭环的名字。读题的第一步不是去想 NCU 有哪些 section，而是把题干里的名词逐个落到槽位上：谁产生指标、指标以什么形态离开 profiler、谁消费它、消费之后改变了什么。四个槽位分别是被测对象（一次 kernel 的 launch 配置与源码版本）、测量装置（NCU 的采集模式与 section 集合）、回灌通道（指标从 profiler 输出到 agent 上下文的序列化形式）、动作空间（agent 拿到指标后允许改的那几个自由度）。题干里“按一次 kernel 生成/优化/验证的流动拆成哪几步”这句话，真正的考点是把“一次 kernel”当成不可再分的最小实验单元——一次 launch、一个源码版本、一份指标快照，三者必须一一对应，否则回灌的因果链就断了。

拆题时最容易漏掉的是“一次”这个词的约束力。它意味着不能在同一个 profiling 会话里混入多个 kernel 变体，否则 NCU 的 replay 机制会把不同变体的计数器混在一起，agent 看到的 stall 归因就不再属于任何一个具体版本。因此第一步的输入是一个确定的源码哈希 + 一个确定的 launch 参数元组，输出是一份带版本标签的指标记录，代价是每次采集都要重新 replay kernel 若干遍（NCU 按 section 分组做多 pass 采集，pass 数随 section 数量线性增长），这段时延不进 kernel 本身但进 agent 的墙钟预算。

具体例子：题干若给出“把 shared memory 占用从 48KB 降到 32KB 后回灌指标”，读题时就应立刻识别出这是动作空间槽位的一个取值，而不是测量装置的变化；测量装置必须保持不变，否则 occupancy 的提升无法归因到 shared memory 这一项。考点在这里：区分“改了被测对象”和“改了测量方式”，前者是回灌要解释的因，后者是必须冻结的实验条件。

二 · 考点的三层结构：正确性、归因、可复现

这类题目的考点不是单层的。第一层是正确性 oracle：回灌指标之前，必须先有一次与参考实现逐元素比对的通过记录，否则优化后的 kernel 可能只是“更快地算错”。第二层是归因有效性：NCU 给出的 stall 分解（如 long scoreboard、MIO throttle、barrier）必须能映射回源码里的具体构造，映射不成立时指标就是噪声。第三层是可复现性：同一源码哈希、同一 launch 配置、同一 NCU section 集合，两次采集的指标应当在计数器分辨率内一致；不一致则说明存在未受控变量（时钟频率、L2 残留状态、同卡其他进程）。

三层考点对应三种代价。正确性层付出的是参考实现的显存与比对时延——逐元素比对要求两侧张量同时驻留，显存占用翻倍。归因层付出的是采集 pass 数与 replay 开销，section 越多，单次 kernel 的观测成本越高，且 replay 会反复写回显存以恢复 kernel 前的状态。可复现层付出的是token 预算：agent 若要把两次采集的差异写进上下文做比较，指标文本的体量直接吃掉上下文窗口。

$$\text{归因可信度} \propto \frac{\text{可映射到源码构造的计数器数}}{\text{采集到的计数器总数}}$$

这个比值不是装饰：它提示读题时要数一数题干给出的指标里有多少条能落到具体代码行。例如题干只给“achieved occupancy 偏低”，这几乎无法归因，因为 occupancy 受寄存器压力、shared memory、block 尺寸三者共同影响；而给出“每 warp 的 long scoreboard stall 周期数”就能直接指向全局内存访问的延迟隐藏不足。考点拆解到这一层，解题路径才不是“多采几个 section”，而是“先确定哪几个计数器具备单义映射”。

三 · 解题路径：从题干到公式的映射表

读题产出物应当是一张路径表，而不是一段散文。表的每一行是题干里的一个约束，列是它触发的计算。下面这张表给出本类题目常见的映射关系，读题时按行勾选，缺行即缺考点。

题干约束触发的量公式或判据代价所在
“一次 kernel”实验单元边界源码哈希 × launch 元组唯一确定一次采集replay pass 时延
“回灌”指标序列化体量上下文占用 ≈ 计数器条数 × 每条 token 数token 预算
“优化”动作空间基数可改自由度：tile 尺寸、线程映射、访存宽度、流水深度搜索轮次 × 每轮采集成本
“验证”正确性 oracle 强度逐元素容差比对 + 边界形状覆盖参考侧显存翻倍
roofline 判据理论上界见下方公式带宽/算力实测偏差

roofline 这一行是路径表里唯一带连续量的判据，读题时必须把它写成可代入的形式，否则“优化到什么程度算够”没有终点。

$$P_{\text{bound}} = \min\left(\frac{\text{FLOPs}}{\text{字节搬运量}} \cdot B_{\text{mem}},\; F_{\text{peak}}\right)$$

其中比值项是算术强度，$B_{\text{mem}}$ 是可持续内存带宽，$F_{\text{peak}}$ 是目标精度下的峰值算力。读题时若题干给出 kernel 的输入输出形状与数据类型，就能算出字节搬运量的下界；若给出 tile 尺寸，就能判断该 tile 是否把算术强度推到了拐点右侧。这一步的输出不是答案，而是优化目标的量化锚点：agent 后续每一轮回灌，都要拿实测吞吐与这个锚点比，差距缩小才算有效动作。

具体例子：题干描述一个矩阵乘 kernel，tile 为 128×128、数据类型 fp16。读题时应立刻算出该 tile 下每字节搬运对应的乘加次数，判断它落在内存墙还是算力墙一侧；若落在内存墙一侧，则动作空间应优先指向提高数据复用（更大的 tile 或更好的 swizzle），而不是提高 ILP。这个判断不需要跑任何 profile，纯靠题干参数与 roofline 公式完成，是读题阶段就能给出的解题路径分叉。

四 · 需要调用的公式：把 stall 折算成时间

NCU 回灌的核心不是“看到 stall 百分比”，而是把 stall 折算成可比较的时间量，否则不同 kernel 之间无法排序。折算的基本式是每个 warp 的 stall 周期数除以该 SM 上的活跃 warp 数，再乘以时钟周期。

$$T_{\text{stall}} = \frac{C_{\text{stall}}}{\,W_{\text{active}}\,} \cdot \frac{1}{f_{\text{clk}}}$$

读题时要检查题干是否给了 $W_{\text{active}}$ 与 $f_{\text{clk}}$ 的可代入值；若只给了 stall 占比而没有活跃 warp 数，则该指标不可折算，只能做同版本内的相对比较，不能跨版本做绝对归因。这是考点：指标的可比性取决于分母是否被固定。回灌通道若把不同分母下的 stall 百分比并列呈现给 agent，agent 会做出错误的优先级排序。

代价方面，折算本身不花 GPU 时间，但要求采集时同时抓取 occupancy 相关 section 与 stall 相关 section，section 数量上升直接抬高 replay pass 数。一个具体例子：若题干要求“定位延迟隐藏不足的根因”，则需要同时具备 long scoreboard stall 与 achieved occupancy 两项，缺一不可；只抓前者会把“访存延迟高”误判为“并行度不够”，而实际根因可能是寄存器压力压低了 occupancy，此时正确动作是减寄存器而非改访存模式。

另一条必调公式是有效带宽，用于判断实测是否已贴近可持续带宽：

$$B_{\text{eff}} = \frac{\text{实际搬运字节数}}{T_{\text{kernel}}}$$

读题时要注意“实际搬运字节数”不等于“逻辑字节数”：cache 命中会放大有效带宽的表观值，因此该式只能用于判断是否触顶，不能用于反推 DRAM 流量。题干若给出 L2 命中率相关指标，应把它作为解释 $B_{\text{eff}}$ 超出可持续带宽的原因，而不是把它当作独立考点。

五 · 读题产出物：一份可执行的采集清单

读题的终点不是理解题意，而是产出一份采集清单：哪几个 section、哪几个计数器、按什么顺序采、采完之后用什么判据筛选。清单的每一项都要能回答“这个计数器支撑哪一条归因”。支撑不了的计数器不进清单，因为每多一个 section 就多一轮 replay，而 replay 的代价是显存写回与 kernel 重放，直接吃掉 agent 的迭代轮次预算。

  • 必采项：与题干动作空间直接对应的计数器。若动作空间含 tile 尺寸，则采 occupancy 与 shared memory 相关项；若含访存宽度，则采 sector 数与 long scoreboard。
  • 冻结项：测量装置参数在一次实验内不得变动，包括 section 集合、replay 模式、时钟锁定状态。变动即破坏归因链。
  • 舍弃项：与动作空间无映射关系的计数器，即便数值异常也不进回灌通道，避免 token 预算被噪声挤占。

这份清单的代价体现在两个方向：采集侧是 replay pass 数乘以单 pass 的 kernel 重放时间；消费侧是序列化后的指标文本占用的上下文 token。两者共同构成一次回灌的固定开销，读题时应把它与 agent 允许的迭代轮数相乘，判断题干给出的预算是否够走完“生成—优化—验证”至少一个完整闭环。若不够，解题路径就必须收窄动作空间，把有限轮次押在 roofline 判据指出的那一侧。

具体例子：题干若只允许三轮回灌，而动作空间同时包含 tile 尺寸与流水深度两个维度，则读题阶段就应判定这两个维度不能并行搜索，必须先由 roofline 公式定出哪一维是瓶颈，再在瓶颈维上做两轮二分。这个判断完全来自题干约束与公式，不依赖任何实测数字，属于读题阶段应当给出的解题路径。

六 · 正确性 oracle 在读题阶段的定位

验证不是回灌之后的收尾动作，而是读题阶段就要定下的前置条件。理由很直接：若优化后的 kernel 与参考实现的比对未通过，则所有性能指标都失去意义，回灌通道会把“更快地算错”当成有效改进喂给 agent。因此读题时要明确 oracle 的强度：容差取多少、覆盖哪些边界形状、是否包含非对齐尺寸与极端 batch。

oracle 的代价是显存与时间。逐元素比对要求参考输出与候选输出同时驻留，显存占用约为单侧的两倍；若题干给出的形状接近显存上限，则比对必须分块进行，分块又引入额外的 kernel launch 与同步开销。读题时应把这一项计入总预算，而不是默认验证是免费的。考点在于：验证的强度与回灌的轮次是竞争关系，两者共享同一份墙钟与显存预算，题干若同时要求“多轮优化”与“严格验证”，解题路径就必须把验证做成抽样式而非全量式，并明确抽样覆盖的边界集合。

一个具体机制：把正确性判据写成“参考实现与候选实现在给定容差下的最大绝对误差”，并在每一轮回灌前先跑该判据，未通过则不进入指标采集。这样做的代价是每轮多一次比对 launch，收益是回灌通道里不会出现无法归因的性能提升。读题阶段确定这一顺序，比在优化中途才发现数值漂移要省下整轮预算。

读题先划边界：NCU 回灌在什么条件下才成立

把「NCU 指标回灌」拆成读题、生成、优化、验证四步之前，先要承认这套流动有一条硬边界：它假定被观测的 kernel 是可重复、可隔离、且瓶颈可归因的。一旦 kernel 的运行时间被 host 侧调度、其他 stream 的并发、或 L2 残留状态主导，NCU 采到的 stall 分布就不再是 kernel 自身的属性，回灌给 agent 的信号就是噪声。工程上要先用一个判据筛掉这类样本：设同一 kernel 在相同输入下重复采样的主指标（如 sm__throughput 或 dram__throughput）的相对离散度为

$$ \delta = \frac{\max_i m_i - \min_i m_i}{\frac{1}{n}\sum_i m_i} $$

当 δ 超过该指标在目标架构上的固有抖动带时，这一轮 profile 不应进入优化回路，而应退回生成步重做 launch 配置或加隔离。这一步的代价是采样轮次乘以单次 NCU 采集的固定开销——NCU 默认会串行化 kernel 并多次 replay，单次采集常把原本微秒级的 kernel 拉长到毫秒量级，若每轮优化都全量采集，wall-clock 会被 profile 本身吞掉。

失效条件还有一类更隐蔽：指标名对但语义错位。例如用 dram__bytes_read 判断是否访存受限，却在 L2 命中率很高的 kernel 上得出「带宽充裕」的结论，实际瓶颈是 L2 到 SM 的路径。回灌前必须把题干里的性能目标翻译成一组互相约束的指标，而不是单个数字。下表给出读题阶段应固定的三元组，缺一项就说明考点没拆干净：

题干信号对应考点回灌时要盯的指标
「比 baseline 慢」occupancy 与指令级并行achieved occupancy、stall 分布
「显存涨了」中间缓冲与生命周期显存峰值、alloc/free 次数
「数值不对」归约顺序与精度不适用 NCU，走正确性 oracle

系统代价体现在流动的耦合上：读题阶段若把考点定得过窄（只盯一个 stall 原因），优化步会在局部最优里打转，验证步则因缺少对照指标而无法判定回灌是否真的改善了端到端时延；反之定得过宽，每轮都要采全量 section，编译与采集时间线性膨胀，token 预算被 profile 文本挤占。因此读题的产出不是答案，而是一份带优先级的指标清单和一条明确的「不可回灌」判据——它决定了后面三步是否值得启动。
