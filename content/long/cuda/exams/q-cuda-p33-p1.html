一 · 题干的三层结构：论文声称、可复现主张、可验收主张

《CUDA-LLM: LLMs Can Write Efficient CUDA Kernels》这个标题本身就是一个待拆解的断言，而深读的第一步不是接受它，而是把它切成三层可分别检验的主张。第一层是能力主张：LLM 能写出“efficient”的 CUDA kernel——这里的 efficient 是相对量，必须绑定一个基线才有意义，孤立地说“高效”不可证伪。第二层是方法主张：论文给出的生成/优化回路（通常是“生成—编译—运行—profile—再生成”的闭环）是产生效率优势的因果机制，而不是模型规模或采样预算的副产品。第三层是可复现主张：这套回路在换机器、换驱动、换输入分布后仍能复现出同样的效率排序。三层主张对应三种不同的证据：能力主张要 baseline 与 speedup 分布，方法主张要消融与执行反馈的归因，可复现主张要 harness 的配置冻结与验收口径。

读题时最容易犯的错是把三层压成一层，看到某 kernel 比 PyTorch eager 快就认为三层的证据都齐了。实际上，一个 speedup 数字只能支撑第一层的一个点估计，它对第二层毫无信息——你无法从“快”反推“是因为模型读了 NCU 的 stall 原因才快”。因此本部分的解题路径是：先把题干拆成“基线怎么定 / 输入分布怎么定 / 正确性门怎么定 / 防作弊怎么定 / 上线门怎么定”这五个可执行决策，再逐一指认它们各自考的是哪一层主张、需要调用哪个公式、以及每个决策要付什么代价。

一个具体例子：题干若写“在 KernelBench 上平均加速 X 倍”，你需要立刻追问分母是什么。若分母是 PyTorch eager 且输入是论文自选的 shape，那这个数字只覆盖第一层的一个受控切片；若分母是 torch.compile 且输入分布跨了多个 batch size，它才开始触及第二层。拆题不是抠字眼，而是确定“这个数字能被我用来做哪个决策”。

二 · 基线：三种分母与它们各自的考点

基线选择是 harness 的第一个岔路口，考的是“你是否知道 speedup 是一个比值而非属性”。三种常见分母各有考点。eager 基线（PyTorch 默认算子）考的是“相对框架默认路径的收益”，它最容易做出好看的数字，但对生产端到端收益的指示性最弱，因为生产里往往已经用了融合算子或编译后端。编译基线（torch.compile / Triton 手写参考实现）考的是“相对已有优化路径的增量”，这是方法主张真正该打的擂台——如果 LLM 生成的 kernel 打不过 torch.compile，那“efficient”就只是相对未优化路径的 efficient。硬件理论基线（roofline 上界）考的是“离 SOL 还有多远”，它不产生 speedup，而产生一个归一化的效率坐标。

需要调用的公式是 roofline 的双约束形式：给定算子的算术强度 I（FLOP/Byte），可达性能上界为

$$P_{\text{roof}} = \min\left(P_{\text{peak}},\; I \cdot B_{\text{mem}}\right)$$

其中 P_peak 是峰值算力、B_mem 是可达显存带宽。用它可以把“比 eager 快 3 倍”翻译成“达到 roofline 的百分之几”，从而判断这个 speedup 是“框架太慢”还是“kernel 真好”。代价在于：roofline 需要为每个算子单独估 I，对融合算子（如 softmax、layernorm）I 随 shape 变化，估错会让效率坐标失真；此外 roofline 是上界而非可达值，把上界当验收线会系统性高估差距。

具体例子：一个 elementwise 加法的 I 极低，roofline 完全由带宽项支配，此时“比 eager 快”几乎必然发生，因为 eager 的 launch 开销和多余读写才是瓶颈；而一个 GEMM 的 I 高，roofline 由算力项支配，此时 speedup 才真正反映 tile/流水线质量。同一份 harness 若不分算子类型统一用 eager 作分母，就会把“带宽受限算子的 launch 优化”和“算力受限算子的指令级优化”混成一个平均数字，掩盖方法主张的真实适用范围。

三 · 输入分布：shape 网格、dtype 与边界条件

输入分布决定正确性门与性能数字是否可迁移，考的是“你是否把 shape 当作分布而非单点”。可执行的做法是定义一个 shape 网格：至少包含一个“小 shape”（launch 开销主导）、一个“中 shape”（带宽/算力混合）、一个“大 shape”（接近 roofline）、以及一个“非对齐 shape”（维度不是 2 的幂、不是 128 的倍数）。dtype 至少要覆盖 fp32 与 fp16/bf16 两档，因为 kernel 的向量化宽度与寄存器压力随 dtype 变化，只测一档会把“针对 fp16 调优”误读为通用效率。

这里要调用的是有效带宽的核算式，用来判断一个 shape 是否落在带宽受限区：

$$B_{\text{eff}} = \frac{\text{Bytes moved}}{\text{kernel time}}$$

把 B_eff 与设备可达带宽对比，若接近则说明该 shape 下 kernel 已贴近内存墙，进一步的指令优化收益有限；若远低于，则说明还有计算或访存模式的改进空间。代价是：shape 网格每增加一档，编译与运行次数线性增长，若 harness 还带 NCU profile，单次 profile 的采集开销会让总评测时间显著膨胀；同时非对齐 shape 会触发额外的边界分支，可能让正确性门暴露论文未覆盖的越界写。

具体例子：一个 reduction kernel 在 N=4096 时可能被单 block 处理完，测出的是“无跨 block 同步”的理想路径；在 N=10^7 时才会暴露多阶段归约与原子操作的竞争。若 harness 只取前者，正确性门通过、性能数字漂亮，但上线到真实张量形状时会出现数值顺序差异甚至非确定性。因此输入分布的设计必须显式声明“哪些 shape 是验收范围、哪些只是诊断”，否则验收口径就是空的。

四 · 正确性门：从 allclose 到 oracle 的分级

正确性门考的是“你能否区分数值等价、语义等价与容差等价”。最低一级是 torch.allclose 式逐元素比较，需要同时指定 rtol 与 atol；对 fp16/bf16 输出，固定 atol 会在大幅值元素上过松、在小幅值元素上过紧，因此更稳的做法是按 dtype 设定相对容差并辅以一个绝对下限。第二级是参考实现 oracle：用高精度（fp64 或 fp32 累积）实现同一算子，把 LLM kernel 的输出与它比，而不是与可能有实现差异的框架算子比。第三级是性质 oracle：对 reduction 类算子检查结合律无关的量（如总和、均值），对归一化类检查输出统计量（均值≈0、方差≈1），这类检查不依赖逐元素对齐，能捕捉“数值上接近但语义错位”的实现。

伪代码思路是三级门串联而非并联：

  • 第一关：shape/dtype 合法性检查，越界写用 guard page 或 canary 值捕获；
  • 第二关：与高精度 oracle 的 rtol/atol 比较，失败即拒；
  • 第三关：性质检查（统计量、单调性、边界值），失败标记为“语义可疑”而非直接拒。

代价在于：高精度 oracle 本身要写、要验证，且 fp64 参考实现在 GPU 上可能比被测 kernel 慢一个量级，使正确性门的时延超过性能测量本身；性质 oracle 则可能对合法实现误报（例如不同归约顺序导致的末位差异被统计量放大）。具体例子：一个 softmax kernel 若漏掉减最大值的数值稳定步骤，在输入幅值较大时 allclose 可能仍通过（因为输出都在 0–1 之间），但性质 oracle 检查“输入加常数后输出不变”会立刻暴露它——这正是逐元素比较抓不到、而语义检查能抓到的错误类型。

五 · 防作弊与上线门：把“快”约束在“对”的流形上

防作弊考的是“你是否意识到 speedup 可以被非法的计算量削减伪造”。常见作弊面包括：跳过部分输入元素、用低精度近似替代规定精度、缓存跨调用结果、把计算挪到计时区间之外、针对固定 shape 硬编码。对应的机制是计时区间与计算区间的一致性校验：在计时前后各做一次输出校验，若计时区间内的输出与区间外不一致，说明存在缓存或状态泄漏；对每个 shape 单独计时并要求同一 kernel 在未见过的 shape 上也通过正确性门，可以排除硬编码。

上线门则是把“通过评测”翻译成“可以部署”的判据，它至少包含三条：正确性门全过、在目标 shape 网格上的中位 speedup 超过阈值、以及端到端收益为正。端到端收益的核算要调用 Amdahl 形式的加权：

$$S_{\text{e2e}} = \frac{1}{(1-f) + f / s}$$

其中 f 是该 kernel 在端到端时延中的占比、s 是该 kernel 的局部 speedup。这个式子说明：局部加速 10 倍但 f=0.05 时端到端只有约 1.3 倍，若 harness 只报局部 speedup 就会系统性高估上线价值。代价是：端到端测量需要把 kernel 嵌回真实调用链，引入框架开销与调度抖动，测量方差远大于孤立 kernel 计时；同时 f 的估计依赖 profiler 归因，归因误差会直接传进 S_e2e。

具体例子：一个 attention kernel 在孤立计时下比基线快数倍，但它在端到端中占比很小，且替换后触发了额外的 layout 转换（transpose/copy），端到端反而变慢。上线门若只看局部 speedup 就会放行这种“局部赢、全局输”的改动；把 S_e2e 作为门限、把 layout 转换计入计时区间，才能拦住它。防作弊与上线门在机制上是同构的：都要求“计时区间内的计算必须完整且与验收语义一致”，区别只在于前者防的是评测内的伪造，后者防的是评测与部署之间的语义漂移。

六 · 解题路径：五个决策的依赖顺序与公式清单

把上述拆解收敛成一条可执行的解题路径，顺序不能颠倒，因为后一个决策依赖前一个的输出。第一步定基线：先声明分母是 eager、编译后端还是 roofline，并据此确定 speedup 的语义；第二步定输入分布：用 shape 网格覆盖小/中/大/非对齐四档，用 B_eff 判断每档落在带宽区还是算力区；第三步定正确性门：三级串联，容差按 dtype 分级，oracle 用高精度参考实现加性质检查；第四步定防作弊：计时区间内外输出一致性、未见 shape 泛化、计算量完整性；第五步定上线门：正确性全过 + 目标网格中位 speedup 阈值 + S_e2e 为正。

需要随身携带的公式清单只有四个：roofline 的 min(P_peak, I·B_mem) 用来定位效率坐标；B_eff 用来判断 shape 的受限类型；rtol/atol 分级用来定义数值等价；Amdahl 的 1/((1-f)+f/s) 用来把局部加速折算成端到端收益。四个公式分别对应四个决策点，缺一个就会在对应环节失去量化依据。代价是：这套路径要求 harness 同时具备编译、运行、profile、高精度参考四条能力链，任一条缺失都会让某个决策退化为定性判断；而定性判断在验收口径里是不可审计的。

具体例子：若团队只有 eager 基线而没有 roofline 估算，第一步就只能报“比 eager 快”，无法回答“是否已接近硬件上界”，于是第三步的正确性门通过后，第四步的防作弊也无法判断“跳过部分元素”是否只是“在带宽受限区做了合法的访存裁剪”。这说明五个决策不是并列清单，而是有依赖的链条：上游的量化缺失会向下游传播成不可判定的验收问题。因此读这篇论文时，应当把它的实验配置逐项映射到这五个决策上，标出哪些决策有显式配置、哪些被默认值隐式决定——后者正是复现风险所在。

读题边界：当“题干可拆”本身不成立时

拆题干这套动作有一个隐含前提：题面已经把语义契约写清楚了——输入形状、dtype、边界条件、允许的数值误差、是否要求 in-place。CUDA-LLM 这类工作里，题面往往来自 KernelBench 式的“PyTorch 参考实现 + 一句自然语言描述”，此时拆题不是把文字读细，而是先把参考实现反推成契约：哪些维度是动态的、哪些分支在测试分布里根本不触发、参考实现自身的数值路径（是否用 fp32 累加、是否走 fused 路径）是否构成隐式规范。若参考实现里存在对 batch=1 的特化分支，而题面只字未提，那么“考点”其实是分布外行为，拆题阶段必须把它标成待验证项而非默认约束。

失效条件集中在三类。其一是题面欠定：同一句“实现 softmax”在是否要求数值稳定、是否允许近似 exp 上有完全不同的正确性门，此时拆题只能产出候选契约集合，把裁决权交给正确性 oracle 与分布采样，而不是在拆题阶段拍板。其二是参考实现不可执行或依赖库算子，导致无法用它做逐元素比对，只能退化为性质检验（单调性、归一化和、极值位置）。其三是性能考点与正确性考点冲突：题面要求“高效”，但高效实现常改变累加顺序，浮点结果与参考不再 bitwise 相等，拆题时必须显式区分 bitwise 门与容差门。

$$\text{可拆性} = \mathbb{1}[\text{契约完备}] \cdot \mathbb{1}[\text{参考可执行}] \cdot \mathbb{1}[\text{数值路径可判定}]$$

系统代价落在评测吞吐上：每增加一个待验证的分布外分支，正确性门就要多跑一组输入，而每组输入都要过参考实现与候选实现两遍。以动态 shape 为例，若拆题阶段把 3 个候选维度组合全部保留为必测项，单题的正确性验证时延大致按组合数线性增长，token 侧则体现为 agent 每轮都要重读更长的契约说明，挤占生成本身的预算。工程判断是：拆题产出应是“契约 + 待验证清单 + 每项的裁决方式”，而不是一份更长的题面复述；清单里每一项都要标注它由哪条门（bitwise、容差、性质）裁决，否则后续多轮 RL 会把不可判定的项当成可优化目标，把奖励浪费在无意义的数值抖动上。
