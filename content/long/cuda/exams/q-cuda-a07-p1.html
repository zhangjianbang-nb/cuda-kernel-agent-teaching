一 · 把题干拆成「合约三件套」：前置条件、后置条件、循环不变式

拿到一道 kernel 生成题，第一件事不是写 CUDA，而是把自然语言题干翻译成一份可被机器检查的合约。合约的骨架只有三样东西：前置条件（precondition，描述输入张量的形状、dtype、对齐、stride、值域与别名关系）、后置条件（postcondition，描述输出与输入之间的数学关系，以及数值误差容限）、循环不变式（loop invariant，描述每个 tile/每个 warp 迭代时局部缓冲区与全局内存之间应当保持的等式）。这三样东西不是文档，而是后续正确性 oracle、形式验证与奖励函数的共同输入——它们决定了「验证」这一步到底能不能自动化。

拆题的具体机制是「逐句标注量词」。题干里每一句形如「对每个 batch b、每个通道 c」的表述都是一个全称量词，必须落到前置条件的维度约束上；每一句「结果等于 softmax 的某一行」都是一个存在量词加函数等式，必须落到后置条件的表达式上。把量词标完，题干里剩下的形容词（「高效的」「融合的」）才是优化考点，而它们不进入合约，只进入代价模型。

$$\forall\, i \in [0, N),\quad \big|\,\text{out}[i] - f(\text{in})[i]\,\big| \le \tau \cdot \big|f(\text{in})[i]\big| + \epsilon$$

这条式子就是后置条件的标准形：相对误差 τ 与绝对误差 ε 双约束。它直接决定了后面 oracle 的写法——如果题干只给「近似相等」，τ 就必须由考点反推（例如归约类算子要按累加顺序估计浮点误差增长），而不是随手取一个数。代价在这里第一次出现：τ 取得越松，验证通过率越高但语义越弱；取得越紧，形式验证的求解时间与反例搜索空间都会上升，等价于把编译/验证时延换成可信度。

具体例子：题干要求「实现一个按行 softmax，支持任意列数，输出与 PyTorch 在 fp32 下一致」。拆解结果是前置条件 0 < cols 且行内 stride 连续、输入无 NaN；后置条件为每行和等于 1 且逐元素满足上式；循环不变式是「已处理的列的最大值与指数和，等于当前前缀的最大值与指数和」。注意这里没有出现任何 tile 大小——tile 是优化变量，不是合约变量，把它写进前置条件会让验证器把实现细节误当成语义。

二 · 考点识别：把题干映射到四类可验证命题

题干拆完之后，考点要分成四类，因为它们的验证手段与代价完全不同。第一类是语义等价（输出等于参考实现），可用差分测试与 SMT 求解；第二类是内存安全（越界、别名、未初始化读），可用符号执行或带断言的编译；第三类是数值稳定（溢出、下溢、累加顺序导致的误差界），需要区间算术或高精度参考；第四类是性能合约（达到 roofline 的某个比例、不引入额外全局同步），只能靠 profile 与解析模型，不能靠形式化证明。

识别考点的机制是「反例驱动」：对每一类命题，先问「什么样的输入会让它失败」，再把这类输入写成前置条件的否定。例如语义等价类的反例是边界形状（cols=1、cols 非 2 的幂、行数极小），内存安全类的反例是非对齐指针与原地操作，数值稳定类的反例是极大/极小值混合的行。把这些反例整理成一张表，就是解题路径的检查清单。

代价判断要具体：数值稳定类考点若用 fp64 参考，显存占用翻倍、带宽需求翻倍，在小规模测试上可接受，在全尺寸上会让验证本身成为瓶颈，因此通常只在采样子集上做。性能合约类考点不能写进形式化验证，因为「达到 SOL 的 70%」不是输入输出的谓词，而是实现与硬件交互的性质；把它塞进 SMT 只会得到不可判定的目标。这一点是解题路径分叉的关键：语义与安全走证明，性能走测量，两者共享同一份前置条件。

三 · 解题路径：从合约到「可执行判据」的四段流水

路径的第一段是合约固化：把第一节拆出的三件套写成机器可读形式（断言、类型约束、参考函数签名），并冻结。冻结的意义在于后续所有优化都不得修改合约——一旦允许改合约，优化就会退化为「改题目」。第二段是判据生成：由后置条件生成差分测试用例集，由前置条件生成边界用例，由循环不变式生成中间断言插入点。第三段是实现搜索：在合约约束下枚举 tile 大小、向量化宽度、归约策略，每个候选实现都要先过判据再进 profile。第四段是代价核算：把每个候选的验证时延、编译时间、显存占用与实测性能一起记账，形成帕累托前沿。

伪代码思路如下（不是可运行代码，只表达控制流）：对候选集合 C 中的每个实现 k，先跑 assert_pre(in)，再跑边界用例，再跑随机差分用例，全部通过后才允许进入 profile(k)；任何一步失败就把失败输入回填为新的边界用例，扩充判据集。这个回填机制是路径的核心：验证不是一次性闸门，而是不断把反例变成新考点的过程。

$$\text{cost}(k) = \alpha \cdot T_{\text{verify}}(k) + \beta \cdot T_{\text{compile}}(k) + \gamma \cdot M_{\text{peak}}(k) + \delta \cdot \big(T_{\text{ref}} - T_{k}\big)^{-1}$$

这条代价式把四类开销放在同一个标量里，权重由部署场景决定。注意最后一项是性能收益的倒数，它使得「更快但更难验证」的实现不会自动胜出。具体例子：一个用 warp shuffle 做行内归约的 softmax 实现，性能优于共享内存版本，但它的循环不变式涉及跨 lane 的部分和，断言插入点更多、符号执行的路径数更大，T_verify 上升；若 β、γ 较小而 α 较大（验证预算紧张），代价式会把它排在共享内存版本之后。这就是「解题路径」与「直接给答案」的区别：路径产出的是带代价标签的候选集，而不是单一实现。

四 · 需要调用的公式：误差界、roofline 与验证复杂度

解题路径上要调用的公式有三组，分别对应正确性、性能与验证成本。第一组是浮点误差界：对长度为 n 的归约，最坏情况相对误差随 n 线性增长，而 pairwise/树形归约可压到对数级。这直接决定后置条件里 τ 的取值，也决定循环不变式该写成「顺序累加」还是「树形累加」——两者语义不同，不能混用同一个 τ。

$$\big|\hat{s} - s\big| \;\lesssim\; (n-1)\,\varepsilon \sum_i |x_i| \quad\text{（顺序累加）},\qquad \big|\hat{s} - s\big| \;\lesssim\; \lceil \log_2 n\rceil\,\varepsilon \sum_i |x_i|\quad\text{（树形）}$$

第二组是 roofline：给定算子的算术强度 I（FLOP/Byte）与机器峰值算力 P、带宽 B，可达性能上界为 min(P, I·B)。性能合约应当写成「实测吞吐 ≥ ρ · min(P, I·B)」，ρ 由题干或部署目标给出，而不是由实现者自定。第三组是验证复杂度：差分测试的用例数 m 与覆盖率的经验关系、符号执行的路径数随分支数指数增长。这三组公式共同约束了「τ、ρ、m」三个可调参数，它们不是独立的——收紧 τ 会增加 m，提高 ρ 会增加 profile 次数，两者都推高 T_verify。

具体例子：一个矩阵乘加融合算子，I 约为每字节若干 FLOP，落在 roofline 的带宽斜面上，因此性能合约应写成带宽比例而非算力比例；若误写成算力比例，实现者会被诱导去做无意义的指令级优化。同时，该算子的累加长度 K 很大，顺序累加的误差界随 K 线性增长，若 τ 按 K 估计，差分测试在 fp32 下几乎必然失败，于是必须把循环不变式改为分块树形累加，并把 τ 按 log K 估计。这一步是「调用公式」的真正含义：公式不是装饰，而是决定合约参数与实现结构的依据。

五 · 拆题产出物：一张可交接的「考点-判据-代价」表

读题的终点不是心里有数，而是产出一张可交接的表，让后续的实现搜索与验证环节无需重新读题干。这张表至少四列：考点、对应合约片段、判据（具体输入与断言）、代价标签（验证时延、显存、编译时间、token 预算）。表里每一行都必须能追溯到题干的一句话，不能有「防御性」条目——凡是题干没要求的，不进入合约，否则会无谓地扩大验证空间。

机制上，这张表就是一次 kernel 生成流动中「读题」步骤的输出。它的下游是判据生成器与实现搜索器；它的上游是题干与参考实现。代价标签的用处在于排序：当验证预算有限时，按「考点失败概率 × 失败后果」排序，先验证高风险条目。例如原地操作类题干，别名检查的失败后果是静默错误，优先级高于性能合约。

具体例子：题干「实现一个支持任意 head 数的 attention 前向，输出与参考一致，且不得物化完整的注意力矩阵」。拆出的表包含：前置条件（head 数任意、序列长度可变、dtype 一致）、后置条件（逐元素误差 ≤ τ）、循环不变式（在线 softmax 的 running max 与 running sum 在每个 key block 后保持一致）、考点（语义等价、数值稳定、显存上界）、判据（极长序列、单 head、非 2 的幂序列长度、极大极小 logit 混合）、代价（fp64 参考的显存、在线 softmax 断言的插入开销）。其中「不得物化完整矩阵」是显存合约，它不能写成输出谓词，只能写成对中间缓冲区的上界约束，验证手段是显存峰值测量而非 SMT——这一条正是四类考点分类的实际应用。

这张表还承担一个工程判断：哪些考点可以交给形式化验证，哪些只能交给测量。判据列里凡是写成「对所有输入成立」的，走证明；写成「在采样输入上观测」的，走测试与 profile。混用会导致两种失败：把测量当证明，得到虚假可信度；把证明当测量，得到不可判定的目标与超时。读题阶段就要把这条界线画清楚，因为它是后续所有代价核算的前提。

六 · 读题阶段的代价前置：token、编译与验证时延的预算分配

读题本身有成本，而且这个成本会沿流动放大。把题干拆成合约、生成判据、枚举候选，每一步都消耗 token 与工具调用；若在读题阶段就把合约写得过宽（例如把「任意 stride」写进前置条件），后续判据生成会爆炸，验证时延随之上升。因此读题阶段必须做预算分配：给定总 token 预算与验证时延上限，决定合约的精细度与判据的规模。

机制上，预算分配是一个约束满足问题：合约精细度越高，判据越少但每条判据越难构造；合约越粗，判据越多但单条越便宜。工程上的折中是「按考点分层」：语义等价类用少量高价值判据（边界形状 + 随机差分），内存安全类用符号执行覆盖全部下标表达式，数值稳定类只在采样子集上用 fp64 参考，性能合约类只做一次 profile。这样每一层的代价都可控，且不会互相挤占预算。

具体代价要落到可观测的量：fp64 参考使显存与带宽翻倍，等价于验证阶段的时延翻倍；符号执行的路径数随分支数指数增长，一个带三重条件判断的边界处理就可能让求解时间从秒级跳到分钟级；profile 采集需要独占 GPU，等价于把验证吞吐减半。这些都不是定性描述，而是读题阶段就要写进代价标签的具体项。工程判断是：当验证时延上限紧张时，优先砍掉性能合约的 profile 次数，保留语义与安全的判据，因为后者的失败是静默的，前者至少能被基准测试暴露。

最后落在具体机制上：读题产出的「考点-判据-代价」表应当带一个版本号与冻结标记，后续实现搜索只能读不能改。冻结之后，任何优化若想放宽 τ 或降低 ρ，都必须走合约变更流程，重新生成判据并重算代价——这条流程本身就是防止「用优化偷换语义」的工程闸门。读题阶段的价值不在于给出答案，而在于把答案空间约束成一个可验证、可记账、可交接的集合。
