一 · 题干的三层结构：论文主张、harness 需求、验收口径

《CUDA-L1: Improving CUDA Optimization via Contrastive Reinforcement Learning》这个题干不是一句“读论文写摘要”，而是三层嵌套的工程任务。第一层是论文主张层：CUDA-L1 用对比式强化学习改进 CUDA 优化，读者要判断它的方法在什么条件下成立、改进来自哪里。第二层是 harness 需求层：题干明确要求“搭一套可复现的评测 harness”，并把配置对象点名为基线、输入分布、正确性门、防作弊、上线门五项。第三层是验收口径层：要求“给出可执行的配置与验收口径”，即每一项都要落到可写进配置文件、可被 CI 判定的字段，而不是原则性描述。

拆题干的第一步是把动词圈出来。“搭”意味着产出物是代码与配置，不是评论；“可复现”意味着随机种子、输入生成器版本、编译选项、驱动与工具链版本都要被固定并被记录；“评测”意味着要有度量对象与度量方式；“验收”意味着存在通过/不通过的二元判定。任何一段只谈“RL 能提升 kernel 性能”而不落到这五个配置项的写作，都偏离了题干。

考点的分布可以从题干的名词密度看出：五个配置项里，“正确性门”和“防作弊”是正确性侧，“基线”和“上线门”是收益侧，“输入分布”是统计侧。也就是说，这道题真正考的是“如何让一个 LLM 生成的 kernel 在可信的前提下被判定为有收益”。对比式 RL 只是被评测的方法，不是被讲解的主题；方法细节留给方法部分，本部分只关心它给 harness 提出了什么额外要求——例如对比学习需要成对样本，因此 harness 必须能对同一问题的多个候选 kernel 给出可比较的、稳定的评分，否则对比信号本身就是噪声。

一个具体例子：若 harness 只报告“候选 kernel 比基线快”，而不记录输入分布与正确性门，那么一个把所有输出写成常量的 kernel 在特定小形状上会“更快”，这种候选一旦进入对比池，就会污染 RL 的奖励信号。题干把“防作弊”单列为一项，正是要求 harness 在设计阶段就堵住这类通道。代价是明确的：每增加一道门，候选 kernel 的评测时延与编译时间都会上升，吞吐下降，因此门的粒度必须与上线门的收益阈值匹配。

二 · 基线怎么定：不是“原始 kernel”，而是可归因的参照系

基线是 harness 的第一个配置项，也是最容易被草率处理的一项。把“PyTorch 参考实现”直接当基线，会把框架调度开销、内存分配策略、算子融合差异全部混进对比结果，导致无法归因“改进来自 kernel 本身”。可执行的基线配置应至少包含三层参照：参考实现层（用于正确性 oracle）、朴素 CUDA 层（用于性能下限）、以及调优后的库实现层（cuBLAS/CUTLASS 等，用于性能上限）。三层各自独立记录，任何一层缺失都会让上线门的判定失去锚点。

基线的度量必须与 roofline 口径对齐，否则“快”没有物理含义。对每个问题实例，harness 应计算其算术强度与可达上界：

$$I=\frac{\text{FLOPs}}{\text{Bytes}},\qquad T_{\min}=\max\!\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right)$$

其中 $I$ 为算术强度，$T_{\min}$ 为该实例在给定硬件上的时间下界。候选 kernel 的实测时间与 $T_{\min}$ 的比值即 SOL 利用率，它与“相对基线的加速比”是两个不同维度的指标。只报加速比会让一个在低算术强度实例上“赢了朴素实现但远未接近带宽上限”的候选显得很好；同时报 SOL 利用率才能暴露这类虚高。

基线的稳定性代价必须计入。朴素 CUDA 基线若未做 autotune，其性能会随形状剧烈波动，导致同一候选在不同输入上得到互相矛盾的加速比。工程判断是：基线本身也要跑固定次数的预热与重复测量，取中位数而非均值，因为 kernel 启动时延的尾部会拉偏均值。这会增加每次评测的时延，但换来的是对比信号的可比性——对对比式 RL 而言，这个代价是必须付的，否则成对样本的差值里混入了基线抖动。

具体例子：一个 reduction 问题，朴素实现用单 block 串行归约，库实现用多级树形归约。若 harness 只把前者当基线，候选只要做两级展开就能拿到漂亮加速比；但把库实现也纳入基线后，同一候选的 SOL 利用率可能仍低于带宽上界，上线门应据此拒绝。基线配置因此要写成“每个问题实例绑定一组参照实现 + 各自的测量协议”，而不是全局一个基线。

三 · 输入分布：形状、dtype、稀疏度与边界值的联合采样

输入分布决定了评测结论的外推范围，也是防作弊的第一道物理约束。可执行的配置应把输入空间拆成四个正交维度：形状（含极端小形状与大形状）、dtype（fp32/fp16/bf16/int8 等）、数据分布（均匀、正态、含 NaN/Inf 的边界值）、以及布局（连续、带 stride、转置）。每个维度都要有明确的采样权重与固定种子，且采样器版本要随 harness 一起版本化。

形状采样不能只取“好看”的维度。LLM 生成的 kernel 常在 2 的幂形状上表现良好，而在非对齐形状上因 bank conflict 或尾块处理退化。harness 应显式构造三类形状：对齐形状、非对齐形状（如质数维度）、以及退化形状（维度为 1 或极小）。退化形状是防作弊的关键——一个只对特定形状硬编码的 kernel 会在退化形状上暴露。

数据分布的代价体现在正确性门的误报率上。若输入只含有限值，一个未处理 NaN 的 kernel 会通过正确性门；一旦上线遇到真实数据中的 NaN，行为未定义。因此输入分布必须包含边界值注入，且注入比例要可配置。代价是：边界值样本会触发更多慢路径，拉高评测时延，并可能让某些候选在正确性门上失败率上升，从而降低 harness 的吞吐。工程判断是把边界值样本作为独立子集报告，而不是混入主分布的平均值。

具体例子：一个 softmax kernel，在维度为 1024 的对齐形状上，向量化读写能跑满带宽；在维度为 1000 的非对齐形状上，尾块处理若用标量循环，带宽利用率骤降。若输入分布只采样 1024，候选的“优化”其实是对齐假设的产物。harness 应把这两类形状分别记录 SOL 利用率，并在上线门中要求非对齐形状也达到阈值，否则拒绝。

采样器本身要有伪代码级的确定性：

  • 种子由 (问题 ID, 形状索引, dtype, 分布类型) 四元组哈希得到，保证跨机器可复现；
  • 每个子集固定样本数，不允许“跑到通过为止”的自适应采样；
  • 采样结果落盘为张量文件，评测时直接加载，避免生成器版本漂移。

这三条把输入分布的随机性关进了笼子，代价是存储与加载时延，但换来了跨轮次对比的可比性——对比式 RL 需要的正是这种可比性。

四 · 正确性门：oracle 的分层与容差的可执行定义

正确性门是 harness 的判定核心，考点的关键在于“oracle 不是单一函数”。可执行配置应把 oracle 分成三层：参考实现层（高精度、慢，作为真值）、性质层（不依赖真值的守恒量或不变量检查）、以及边界层（NaN/Inf/极值的行为约定）。三层各自有独立的通过条件，任一失败即整候选失败。

容差不能写成“近似相等”。对浮点 kernel，应给出与 dtype 和累加顺序相关的误差界。一个可执行的思路是按相对误差与 ULP 双阈值判定：

$$\bigl|y-\hat y\bigr|\le \max\!\left(\varepsilon_{\text{rel}}\cdot|y|,\ \varepsilon_{\text{ulp}}\cdot\text{ulp}(y)\right)$$

其中 $\varepsilon_{\text{rel}}$ 随 dtype 设定，$\varepsilon_{\text{ulp}}$ 控制接近零时的绝对误差。对归约类 kernel，误差随累加长度增长，容差应随问题规模缩放，否则长归约会系统性失败。代价是：容差放宽会降低正确性门的判别力，让“数值上略有偏差但语义错误”的候选蒙混过关；容差收紧则会让合法的重排累加被判失败。工程判断是按 dtype 与算子类别分别设定容差表，而不是全局一个数。

性质层是防作弊的主力。对 softmax，可检查输出和为 1、非负；对 layernorm，可检查均值与方差；对矩阵乘，可检查结合律不变量或与参考实现的部分和一致性。性质检查不依赖真值，因此可以在大形状上低成本运行，代价是它只能捕获特定类别的错误，不能替代参考实现层。两层并用，才能在时延与判别力之间取得平衡。

具体例子：一个候选 kernel 在 fp16 下用快速近似倒数实现归一化，参考实现层在宽松容差下通过，但性质层的“输出和等于 1”在尾数舍入下失败。若 harness 只有参考层，这个候选会被误判为正确。正确性门的配置因此要写明每层的启用条件、样本子集与失败后的处理（直接拒绝，不进入性能测量），避免“先测性能再补正确性”的顺序倒置——后者会让错误候选占用大量评测时延。

五 · 防作弊与上线门：从奖励信号污染到收益判定的闭环

防作弊不是一条规则，而是一组必须同时生效的约束。可执行配置至少覆盖四类通道：硬编码输出（用输入分布中的退化形状与随机种子变化检测）、缓存复用（用同一形状不同数据的多次调用检测）、绕过计算（用性质层与参考层交叉验证）、以及测量作弊（用固定预热、事件计时、禁用动态频率缩放来约束）。每一类都要有对应的检测样本与判定逻辑。

对比式 RL 对防作弊有额外要求：奖励来自成对比较，因此任何能让候选“在比较中占便宜”的通道都会被放大。例如候选若在首次调用时做昂贵初始化、后续调用走缓存，则成对比较中它总在第二次测量里显得更快。harness 必须对每个候选独立进程、独立上下文、独立预热，且测量顺序随机化，避免顺序效应。代价是评测时延成倍上升，吞吐下降；工程判断是把防作弊检测放在候选筛选的前段，只对通过者做完整性能测量，用两级流水控制总时延。

上线门是收益侧的最终判定，它必须同时满足三个条件才放行：正确性门全通过、防作弊检测无命中、以及在目标输入分布上的 SOL 利用率或相对基线加速比超过阈值。阈值不能是单一数字，应按问题类别给出，并与基线的稳定性挂钩——若基线抖动大，阈值要相应抬高以覆盖噪声。可执行的判定写成：

$$\text{pass}=\bigl(\text{correct}\bigr)\wedge\bigl(\text{no-cheat}\bigr)\wedge\bigl(\text{speedup}\ge \theta_{\text{class}}+\delta_{\text{noise}}\bigr)$$

其中 $\theta_{\text{class}}$ 为类别阈值，$\delta_{\text{noise}}$ 为基线抖动带来的安全裕度。这个式子的工程含义是：上线门不是“最快者胜”，而是“在可信前提下有可归因收益者胜”。代价是放行率下降，部分真实有收益但幅度小的候选被拒；这是可信评测必须接受的取舍。

具体例子：一个候选在主要形状上比基线快，但在退化形状上因未处理边界而输出错误。若上线门只看主形状加速比，它会放行；加入防作弊的退化形状检测后，它在正确性门前即被拒，节省了后续性能测量的时延。这个顺序本身就是配置的一部分：正确性门与防作弊在前，性能测量在后，上线门最后做阈值判定。整条流水线的验收口径应写成“每个候选的判定轨迹可追溯”：记录它经过了哪些门、在哪一门失败、测量了哪些形状、SOL 利用率是多少。可追溯性是“可复现”的最终落点，也是对比式 RL 奖励信号可信的前提。

读题与考点拆解：这道题真正要你交的不是 harness 代码，而是口径

题干里“可复现的评测 harness”是外壳，考点落在四个可判定的口径上：基线怎么冻结、输入分布怎么参数化、正确性门怎么分层、防作弊与上线门怎么联动。拆题时先把“复现”翻译成可执行约束——同一 commit、同一 GPU 型号与驱动、同一编译选项（-O3、--use_fast_math 是否开启必须写死）、同一随机种子与输入张量生成器版本；任何一项漂移，对比 RL 前后收益的差值就不再是方法带来的。解题路径建议按“先定门、再定分布、最后定基线”的顺序倒推：上线门决定你要多严的正确性 oracle，正确性 oracle 决定输入分布要覆盖哪些边界形状，边界形状又决定基线必须在这批形状上先跑出可信参照。需要调用的公式是收益口径本身，例如相对基线的加速比与门限的联合判定：

$$\text{accept} = \big[\text{speedup} \ge \tau_s\big] \wedge \big[\text{err}_{\max} \le \tau_e\big] \wedge \big[\text{cheat score} = 0\big]$$

其中 $\tau_s$ 与 $\tau_e$ 必须由基线自身的方差标定，而不是拍脑袋。边界与失效条件要提前写进题面：当 kernel 对输入形状极度敏感时，单一 shape 的加速比会掩盖退化，必须用形状分桶后的最差桶判定；当基线本身未被冻结（例如换了 cuBLAS 版本），加速比可正可负，此时 harness 只能报“不可比”而非“提升”。系统代价同样要计入：每个候选 kernel 都要跑正确性 + 计时 + 防作弊扫描，若每轮 RL 采样数十个候选，编译与 profile 的墙钟时间会成为吞吐瓶颈；防作弊扫描（检测硬编码输出、跳过计算、缓存复用）本身要额外跑一组扰动输入，token 与算力开销按候选数线性增长。具体例子：某候选在 $M=N=4096$ 上加速明显，但在 $M=1$ 的 decode 形状上因 launch 开销反而变慢，若只按均值判定就会放行一个生产端有害的 kernel——这正是分桶最差判定要拦下的情形。
