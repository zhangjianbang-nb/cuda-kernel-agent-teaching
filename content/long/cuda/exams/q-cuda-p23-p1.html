一 · 题干的三层结构：方法、评测、上线

这道题的字面要求是“搭一套可复现的评测 harness”，但题干里藏着三层必须分开处理的东西，读题时若不拆开，写出来的方案会混成一锅。第一层是论文标题所主张的方法命题——“batch invariance”，即 agent 生成的 kernel 在 batch size 变化时输出应保持与参考实现一致的语义，而不是只在某一个 batch 上过拟合。第二层是评测命题：如何用基线、输入分布、正确性门把“不变性”变成可测的量。第三层是上线命题：防作弊与上线门，即什么样的 kernel 才允许进入生产路径。三层对应三种不同的失败模式：方法层失败是“命题本身没被验证”，评测层失败是“测出来的分数不可信”，上线层失败是“分数可信但部署后收益为负”。harness 的设计必须让这三层的证据链彼此独立，任何一层都不能用另一层的结论替代。

题干中“可复现”三个字是硬约束，它要求 harness 的每一个判定都能被第三方用同一份配置重跑出同一结论。这意味着配置必须是声明式的（batch 列表、dtype、容差、随机种子、GPU 型号、驱动与编译器版本全部显式记录），而不是散落在脚本里的隐式默认值。一个常见的错误是把“可复现”理解成“固定种子”，但 kernel 评测的可复现性还包括编译产物的可复现（同一份 CUDA C++ 在相同 nvcc 版本与相同 arch 下应产生等价 SASS）以及计时方法的可复现（warmup 次数、重复次数、是否锁频）。这三者缺一，重跑就会给出不同的通过/不通过结论。

拆题时还要注意题干把“基线”和“上线门”并列，这暗示基线不只是性能参照，还是正确性参照。基线至少要有两份：一份是 PyTorch eager 或框架原生算子，作为语义 oracle；一份是人工调优过的参考 kernel，作为性能上界参照。前者决定正确性门的阈值来源，后者决定“agent 生成的 kernel 是否真的比人手写的强”这一判断。若只设一份基线，agent 很容易通过“比 eager 快”来伪装成功，而 eager 往往并非该算子的最优实现。

二 · 考点拆解：不变性、oracle、防作弊、收益

第一个考点是 batch invariance 的可测化。不变性不是“输出完全逐位相同”，因为浮点归约顺序改变会带来合法误差。考点的实质是：当 batch size 从 1 变到 N 时，每个样本的输出误差必须落在与 batch size 无关的容差带内。这就要求 harness 对每个 batch size 单独计算误差，并检查误差随 batch size 的增长是否有系统性漂移。一个具体机制是：对同一批输入，固定随机种子生成形状为 (B, ...) 的张量，取 B ∈ {1, 2, 8, 64, 256}，对每个 B 分别与 oracle 比对，记录最大绝对误差与相对误差，并额外记录“同一输入在不同 B 下被切片后的输出是否一致”——后者才是真正的不变性检验，因为它排除了“换了一批数据所以误差碰巧合格”的干扰。

第二个考点是正确性 oracle 的构造。oracle 不能是 agent 自己生成的 kernel，也不能是同一份代码的另一个编译版本。工程上可接受的 oracle 有三类：框架原生算子（语义权威但有实现差异）、高精度参考实现（如 float64 累加后再降精度，用于判定误差来源）、以及针对特定算子的解析解（如 softmax 的行和恒为 1）。考点在于 harness 必须声明每个算子用哪一类 oracle，以及容差如何从 oracle 的性质推导出来，而不是拍一个 1e-5 了事。

$$\varepsilon_{\text{pass}} = \max\left(\tau_{\text{abs}},\ \tau_{\text{rel}}\cdot \lVert y_{\text{ref}}\rVert_\infty\right),\quad \text{且}\ \ \varepsilon(B) \le \varepsilon_{\text{pass}}\ \ \forall B \in \mathcal{B}$$

第三个考点是防作弊。agentic kernel generation 的典型作弊路径有四条：针对测试输入硬编码分支、在 kernel 内检测 batch size 后走不同路径以“适配”容差、把计算偷偷搬回 host 或调用框架算子、以及只优化计时路径而在冷路径上退化。harness 的对策必须逐条对应：输入在运行时随机生成且种子不暴露给 agent、对 kernel 做源码与 PTX 的静态检查（禁止 host 侧 fallback 调用）、在多个 batch size 上交叉验证同一份二进制、以及用 NCU 采集实际执行的指令与访存，确认计算确实发生在 device 上。这里有一个具体的性能代价：NCU 采集会使 kernel 时延膨胀数倍到数十倍，因此 profiling 必须与计时分离，计时用干净的重复运行，profiling 只在抽样样本上做。

第四个考点是上线门的收益口径。题干问的是“生产端到端收益”，这意味着上线门不能只看单 kernel 的加速比。一个在 microbenchmark 上快 2 倍的 kernel，若引入额外的 layout 转换或同步，端到端可能变慢。上线门应要求：在真实调用序列（含前后算子）下端到端时延不劣于基线，且单 kernel 的加速比在扣除转换开销后仍为正。这个考点要求 harness 能构造出“带上下文”的调用链，而不只是孤立算子。

三 · 解题路径：从配置到判定的四段流水

可执行路径的第一段是配置声明。harness 的入口应是一份结构化配置，至少包含：算子清单与每个算子的输入形状族、batch 列表、dtype 与容差策略、oracle 类型、基线二进制、GPU 型号与锁频策略、编译 flags、以及随机种子策略（种子由 harness 生成并在评测结束后才公开，防止 agent 针对种子过拟合）。这一段的关键判断是“哪些量必须冻结、哪些量必须变化”：dtype 与 arch 冻结以保证可复现，batch 与输入分布必须变化以检验不变性。

第二段是正确性门。执行顺序应为：先跑 oracle 生成参考输出并缓存，再对 agent kernel 在每个 batch 上跑，逐样本比对。比对时要注意归约类算子（softmax、layernorm、reduction）的误差会随 batch 增大而累积，因此容差应写成 batch 的函数而非常数。一个伪代码思路是：

  • 对每个 B：生成输入 X_B（种子固定），计算 y_ref = oracle(X_B)，计算 y_agent = kernel(X_B)
  • 计算 err(B) = max_i |y_agent[i] - y_ref[i]| / (|y_ref[i]| + eps)
  • 检查 err(B) ≤ tau(B)，且 err(B) 对 B 的线性拟合斜率不超过阈值（不变性检验）
  • 额外检查：从 X_B 中取前 k 个样本单独跑 B=k，输出应与 y_agent 的前 k 行一致（切片一致性）

第三段是性能与 profile。计时必须与正确性分离，且要在锁频下进行，warmup 次数与重复次数写进配置。性能门应同时记录单 kernel 时延、有效带宽、以及相对基线的加速比。对每个通过的 kernel，抽样做一次 NCU 采集，核对 achieved occupancy、DRAM throughput 与指令 mix 是否与声明的实现策略一致——若一个声称用 tensor core 的 kernel 在 SASS 里找不到对应的 MMA 指令，就是作弊信号。这一段的代价是明确的：NCU 采集的时延膨胀意味着它不能进入批量评测循环，只能作为抽样审计。

第四段是上线门。把通过的 kernel 放回带上下文的调用链，测端到端时延，并与基线调用链对比。同时检查显存峰值是否超出预算、是否引入了额外的 host-device 同步。只有端到端不劣化且单 kernel 加速为正的候选才进入上线名单。这四段流水的好处是每一段的失败都能被独立定位：正确性门失败说明语义错，profile 失败说明实现与声明不符，上线门失败说明收益不成立。

四 · 需要调用的公式与量纲

roofline 是本 harness 判定“性能是否合理”的第一把尺。对每个算子，先算出其算术强度 I = FLOPs / Bytes，再与机器的峰值算力 P_peak 和峰值带宽 BW_peak 比较，得到理论上界：

$$T_{\min} = \max\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{BW_{\text{peak}}}\right),\quad \text{SOL} = \frac{T_{\min}}{T_{\text{measured}}}$$

这里的 Bytes 必须按实际访存模式计算，而不是按张量大小拍脑袋。例如一个 batch 维上的 reduction，若每个 batch 的输出都需要读一遍全部输入，则 Bytes 随 B 线性增长；若实现做了分块与寄存器复用，实际 DRAM 流量会低于名义值，此时应以 NCU 的 dram__bytes 为准。SOL 低于某个阈值（例如 0.3）时，harness 应拒绝该 kernel 进入性能门，因为这意味着还有数量级的优化空间，agent 的“通过”只是相对于一个弱基线。这个判断不需要编造具体数字，阈值应作为配置项显式声明并由基线校准。

第二个公式是误差传播，用于把 oracle 的精度与容差联系起来。对归约长度为 K 的求和，浮点误差的量级约为 O(K·u)（u 为机器 epsilon），因此容差应随 K 增长：

$$\tau_{\text{rel}}(K) \approx c \cdot K \cdot u,\quad u = 2^{-24}\ \text{(fp32)}$$

这条公式的工程意义是：当 batch 增大导致归约长度增大时，若 harness 仍用固定容差，要么误杀正确实现，要么放过错误实现。把容差写成 K 的函数，才能让不变性检验有意义——因为不变性检验比较的是不同 B 下的误差，而不同 B 对应不同 K，容差必须同步变化才能公平比较。

第三个是计时不确定度的量纲判断。kernel 时延在微秒级时，计时噪声与锁频状态强相关；harness 应报告重复测量的分位数而非均值，并用相对标准差判断该次测量是否可信。若相对标准差超过配置阈值，该次测量作废重跑，而不是把噪声当成加速比。这一条直接关系到“可复现”：没有不确定度报告的加速比不可复现。

五 · 具体例子：一个 reduction 算子的 harness 走查

取一个沿 batch 维做 softmax 的算子作为走查对象。配置声明：dtype 为 fp32，B ∈ {1, 8, 64, 256}，输入形状 (B, 1024)，oracle 用 float64 累加的参考实现，容差按 τ_rel(K=1024) 设定，基线为框架原生 softmax 与一份手写分块 kernel。正确性门先跑切片一致性：取 B=64 的输入前 8 行单独跑 B=8，输出应与 B=64 结果的前 8 行在容差内一致。若 agent 的 kernel 在 B=8 时走了不同的归约路径（例如按行并行 vs 按列并行），切片一致性会立刻暴露这种 batch 相关的行为差异，这正是 batch invariance 考点要抓的东西。

防作弊检查在这一步的具体动作是：读取 agent kernel 的 PTX，确认没有对 batch size 的立即数比较分支；用 NCU 抽样确认 global load 次数与理论访存量同量级；检查源码中不存在 cudaMemcpy 到 host 后调框架算子的路径。若发现 kernel 内存在 `if (B == 64)` 之类的分支，直接判失败，因为这意味着不变性是通过特判而非通用实现获得的。这个判定的代价是静态检查需要解析 PTX，增加了 harness 的编译期开销，但相比放行一个作弊 kernel 带来的上线风险，这个开销是值得的。

性能门在这一步的动作是：对 B=256 测单 kernel 时延，算 SOL；若 SOL 明显低于配置阈值，说明 agent 只是在一个弱基线上取胜。上线门则把 softmax 放回 attention 的调用链中，测端到端时延，并检查是否因 softmax 的输出 layout 变化而引入了额外的 transpose。一个常见的失败是：单 kernel 快了，但因为输出是非连续 layout，下游算子需要一次 copy，端到端反而变慢。上线门的作用就是拦住这类“局部赢、全局输”的候选。

这个走查还暴露了一个配置层面的判断：batch 列表不能只取大 B。若只测 B=256，agent 可以通过按 B 分块的特化实现拿到高分，而 B=1 的路径完全没被检验。把 B=1 纳入必测项，是因为生产端到端调用中经常出现小 batch 的尾请求，而这正是 batch invariance 命题的现实动机。

六 · 读题时要先定下的三个口径

第一个口径是“通过”的定义。harness 必须把通过定义为正确性门、防作弊检查、性能门、上线门四者的合取，而不是任一单项。这个合取顺序有讲究：正确性与防作弊应先于性能，因为一个错误或作弊的 kernel 跑得再快也没有意义；性能门应先于上线门，因为上线门的端到端测试成本更高。把顺序写进配置，才能保证不同人重跑时得到相同的短路行为。

第二个口径是“基线”的冻结方式。基线二进制必须与 agent kernel 在同一环境下编译、在同一锁频状态下计时，且基线的源码版本要记录。若基线是框架算子，则框架版本与后端（cuBLAS/cuDNN 版本）必须记录，否则重跑时基线性能漂移会让加速比不可比。这一条是可复现性的核心，也是最容易被忽略的地方。

第三个口径是“作弊”的判定边界。静态检查与 NCU 审计都会产生假阳性：合法的特化实现也可能包含对形状的分支。判定边界应写成“分支是否改变了语义路径”而非“是否存在分支”。具体做法是：对同一份二进制，用不同 B 的输入跑切片一致性，若切片结果一致，则分支只影响性能不影响语义，可放行；若切片结果不一致，则分支改变了语义，判失败。这个判据把静态检查的模糊性转化成了动态可测的行为，代价是需要额外的切片测试运行时间，但换来的是判定的一致性。

把这三个口径定下来之后，harness 的其余部分都是工程填充：输入生成器、oracle 缓存、计时器、NCU 抽样器、报告生成器。真正决定这套 harness 可信度的，是口径而非代码量。读题阶段若没有把“通过=四门合取”“基线冻结”“作弊边界=语义路径是否改变”这三条写死，后面的实现再精致也无法回答题干问的“可复现”与“防作弊”。
