一 · 题干的三层结构：核心问题、基准、口径

这道题问的不是“这篇论文做了什么”，而是“它把哪一类 GPU kernel 工程问题作为核心”。题干本身是三段式：第一段要求界定核心问题域，第二段要求给出基准、基线与指标口径的定义，第三段要求说明与相邻工作的分工。三段之间存在依赖关系——核心问题的界定决定了基准的选取边界，基准的选取又决定了基线必须覆盖哪些对照，指标口径则必须能区分基线与方法之间的差异来源。答题时若把三段并列作答，会丢掉这条推理链，评卷人看到的只是三个孤立定义。

拆题干时要先锁定“哪一类”这个限定词。它要求的是一个问题类的刻画，而不是论文标题的复述。标题中的 “Feedback-to-Plan Decisions” 指向的是 agent 在收到执行反馈之后如何改变其计划（plan），而 “Self-Evolving” 指向跨轮次的策略累积。两者叠加，核心问题域应当被刻画为：在 CUDA kernel 生成任务上，agent 如何把来自编译、运行、profiling 的反馈转化为对后续生成计划的决策，并使该决策能力在多轮交互中自我演化。这里的关键是把“反馈”与“计划”之间的映射当作研究对象，而不是把“生成一个更快的 kernel”当作研究对象——后者是 KernelBench 系基准的常规目标，前者才是本文的切入点。

“给出定义”这一要求意味着答案中必须出现可判定的边界。定义核心问题时要写明输入、输出与判定条件：输入是任务规格（算子语义、形状、dtype）加上上一轮的执行反馈；输出是下一轮的计划表示（例如分解策略、优化方向、是否放弃当前路线）；判定条件是计划变更后该轮 kernel 在正确性 oracle 下通过且在指标口径上取得可归因的改进。缺少判定条件的定义无法与“随机重试”区分开，这是本题的第一个失分点。

二 · 基准的定位：它测的是什么，不测什么

基准部分要回答的不是“用了哪个数据集”，而是“该基准把哪一层能力暴露为可测量量”。CUDA kernel 生成类基准的常见构造是：给定 PyTorch 参考实现与输入形状，要求产出语义等价的 CUDA/Triton 实现，并以加速比或达标率计分。此类基准天然测量的是单轮生成质量——一次前向、一次编译、一次计时。而本文的核心问题落在反馈到计划的跨轮决策上，因此基准必须提供多轮交互的记录结构：每一轮的反馈内容、agent 的计划表述、该轮产物的正确性与性能。若基准只保留最终产物，反馈到计划的映射就不可观测，核心问题便无法被测量。

这里存在一个必须点明的口径问题：多轮基准的计分单位是“任务”还是“轮次”。以任务为单位计分时，指标是最终达标率或最终加速比，多轮只是达成手段，轮次间的决策质量被折叠进结果；以轮次为单位计分时，指标是每轮改进的幅度与方向正确率，能直接反映反馈到计划的转化效率，但会奖励“多轮刷分”而非“高效收敛”。两种口径对基线的要求不同：前者只需一个强单轮基线，后者还需要一个“无计划更新”的消融基线来隔离计划决策的贡献。答题时应明确指出本文采用哪一种，并说明该选择如何影响基线集合的构成。

基准的另一个定位维度是任务难度分布。KernelBench 系基准按算子复杂度分层，从逐元素算子到融合算子再到含规约与矩阵乘的复合算子。难度分层直接决定反馈的信息量：逐元素算子的失败多为语法或边界错误，反馈到计划的映射近乎确定；复合算子的失败可能源于分块策略、共享内存容量、occupancy 与寄存器压力的耦合，反馈到计划的映射才是真正的决策问题。因此核心问题域的刻画必须与难度分层绑定，否则“反馈到计划”在简单任务上退化为“修 bug”，在困难任务上才成为“做取舍”。这一点是区分本文与普通 agentic 代码生成工作的关键，也是第三段“与相邻工作的分工”的伏笔。

三 · 指标口径的拆解：正确性、性能、决策质量三线并行

指标口径要拆成三条线，缺一条都会让“反馈到计划”的贡献不可归因。第一条是正确性线，其判定依赖正确性 oracle：与参考实现逐元素比对，需规定容差、是否覆盖边界形状、是否要求多次随机输入下稳定通过。正确性线的代价是时延——每个候选 kernel 都要编译、加载、跑参考对比，多轮交互下这部分开销随轮次线性增长，且编译失败与运行崩溃必须被计为失败而非跳过，否则达标率被高估。

第二条是性能线，其口径必须写明计时方式与比较基准。以参考 PyTorch 实现为分母的加速比是最常见口径，但它对基线不公平：PyTorch 实现本身可能已调用高度优化的库函数，也可能在小形状上受启动开销支配。更严格的口径是同时报告相对基线的加速比与相对硬件 SOL（speed-of-light）的达成率，后者用 roofline 模型给出该算子在该形状下的理论上界，把“比 PyTorch 快”与“接近硬件极限”区分开。roofline 的判定式为：

$$P_{\text{bound}} = \min\left(\frac{\text{FLOPs}}{\text{峰值算力}},\ \frac{\text{Bytes}}{\text{峰值带宽}}\right),\quad \text{SOL} = \frac{P_{\text{measured}}}{1/P_{\text{bound}}}$$

该式的工程含义是：先判断算子落在计算受限还是带宽受限区间，再判断实测时延距离该区间上界多远。若不做这步，一个在带宽受限算子上通过增大分块提升算术强度的改动，会被误记为“性能提升”，而实际上它只是把瓶颈从带宽挪到了计算，SOL 达成率未必改善。性能线的代价是测量噪声：GPU 计时需多次迭代取中位数并固定时钟状态，否则轮次间的微小改进会被噪声淹没，导致计划决策的归因失效。

第三条是决策质量线，这是本文相对常规基准的增量口径。它要求把每一轮的“反馈—计划—产物”三元组记录下来，并定义可判定的决策正确性：计划所声明的优化方向是否与该轮反馈所指示的瓶颈一致。例如反馈显示该 kernel 的 occupancy 受寄存器数限制，而计划选择增大 tile 尺寸，则方向不一致，即便该轮时延偶然下降也应记为决策错误。这条线的代价是标注成本与 token 开销——判定方向一致性需要解析反馈文本（编译日志、profiler 指标）与计划文本，在多轮长交互中这部分文本量会迅速膨胀，成为上下文窗口的主要占用者。工程上常见的处理是对反馈做结构化摘要后再送入计划模块，但摘要本身会丢失信息，这是口径设计中必须承认的折衷。

四 · 基线的构成：单轮强基线、无计划消融、以及相邻工作的对照

基线不是“随便找个模型跑一下”，而是要与核心问题域一一对应。第一类基线是单轮强基线：给定同样的任务规格，只做一次生成、一次修复，不跨轮累积计划。它回答的问题是“多轮反馈到计划的机制是否带来了单轮做不到的东西”。若单轮基线在达标率上已接近方法，则多轮机制的价值只能体现在困难分层或收敛轮次上，答题时必须指出这一分层结论，而不能笼统称“方法更优”。

第二类基线是无计划更新的消融：保留多轮交互与执行反馈，但 agent 每轮从头生成，不携带上一轮的计划表示。它与方法的唯一差异是计划是否跨轮传递，因此能把“多轮本身带来的收益”与“计划决策带来的收益”分开。这类消融的代价是实验次数翻倍，且需要控制轮次预算一致，否则计划模块因多消耗 token 而获得不公平的额外尝试机会。工程判断上，轮次预算与 token 预算必须同时固定，二者任一放开都会污染归因。

第三类对照来自相邻工作，分工要在此处说清。与纯执行反馈驱动的修复型 agent 相比，本文的分工在于把反馈的用途从“定位错误”扩展到“选择优化路线”，前者关心编译错误与数值不符，后者关心 profiler 指示的瓶颈与计划声明的方向是否匹配。与基于可验证奖励的多轮 RL 工作相比，本文不训练策略参数，而是把反馈到计划的映射作为 agent 的显式决策结构来研究，因此其对照不是“训练后的策略”，而是“同一策略下有无计划模块”。与形式验证导向的正确性工作相比，本文的正确性 oracle 是经验性的逐元素比对，不追求语义等价证明，其分工是把正确性作为筛选门槛而非研究对象。这三条分工线各自对应一种被排除的问题域，答题时逐条点明即可，不必展开各相邻工作的内部细节。

五 · 解题路径：从题干到可评分答案的推进顺序

给出解题路径时，要写成可执行的步骤序列而非要点罗列。第一步是界定核心问题域并写出判定条件，同时标注该问题域与“单轮 kernel 生成”“纯 bug 修复”“策略训练”三者的边界。第二步是锁定基准的构造与计分单位，说明多轮记录结构如何使反馈到计划的映射可观测，并指出难度分层对该问题域刻画的影响。第三步是并列三条指标线，对每条线写出判定式或伪代码思路、代价来源与一个具体例子。第四步是列出三类基线并说明每类基线隔离的是哪个变量。第五步是给出相邻工作的分工对照，每条对照只写“本文研究什么、对方研究什么、边界在哪”。

以性能线为例，伪代码思路可写成：对每个候选 kernel，先过正确性 oracle（容差比对、边界形状、多次随机输入），通过后固定时钟、多次迭代取中位数计时，再按 roofline 判定受限类型并计算 SOL 达成率，最后把该轮的反馈指标（occupancy、寄存器数、共享内存用量、带宽利用率）与计划声明的优化方向做一致性比对。这条链上每一环都有代价：正确性比对增加时延，固定时钟降低吞吐测量的方差但拉长实验周期，SOL 计算需要额外的硬件峰值参数查询，方向一致性比对消耗 token。把这些代价写在路径里，答案才具备工程可信度。

具体例子应选一个能同时暴露三条线的算子。以含规约的复合算子为例：某轮 kernel 数值不符，正确性线判失败，反馈为越界或同步缺失；修复后通过正确性，但计时显示其带宽利用率远低于峰值，roofline 判定为带宽受限，SOL 达成率低；此时若计划选择继续增大 tile 以提升算术强度，则方向与带宽受限的判定不一致，决策质量线记为错误，正确路线应是改善访存合并或减少冗余读写。这个例子同时覆盖了正确性门槛、性能口径的受限类型判定、以及决策方向一致性，且不需要编造任何数值即可定性说明。

六 · 需要调用的公式与它们各自回答的问题

本题要求“给出需要调用的公式”，因此公式必须与考点一一对应，而不是堆砌。第一个是 roofline 判定式，回答“该算子在该形状下理论上界在哪、实测距离多远”，用于性能线的口径定义与受限类型判定。第二个是加速比定义式，回答“相对基线改进了多少”，其分母必须明确是参考实现还是基线产物，否则跨轮比较无意义：

$$S = \frac{T_{\text{ref}}}{T_{\text{cand}}},\quad \text{并同时报告}\ \frac{T_{\text{ref}}}{T_{\text{base}}}$$

该式并列两个比值的作用是把“候选相对参考实现的收益”与“基线相对参考实现的收益”放在同一尺度上，避免把基线本身已获得的收益记到方法头上。第三个是决策一致性的判定思路，它不是数值公式而是布尔判定：设反馈指示的瓶颈类型为 b，计划声明的优化目标类型为 p，则一致性为 b 与 p 是否落在同一受限区间（计算受限、带宽受限、延迟受限）。该判定需要把 profiler 指标映射到受限类型，映射规则本身应在答案中写明，否则判定不可复现。第四个是轮次预算与 token 预算的约束式，用于基线公平性：方法在轮次 n 内消耗的 token 不得超过基线在同一轮次预算下的上限，否则计划模块的额外尝试机会无法与决策能力分离。

这四个公式/判定各自对应一个失分点：缺 roofline 则性能口径无法区分“变快”与“接近极限”；缺双比值则基线收益被误记；缺一致性判定则决策质量线退化为结果论；缺预算约束则消融不公平。答题时按此顺序排列，评卷人可逐项核对。需要强调的是，公式的作用是让定义可判定，而非追求数值精确——在没有给定硬件峰值参数与实测数据的前提下，答案应给出公式结构与应用方式，不填入任何未经给定的数字。

最后落在工程判断上：本题的真正难点不在复述论文结构，而在把“反馈到计划”这一看似软性的能力转成可测量、可归因、可对照的三线口径。若答案只给出核心问题的文字描述而三条线中任一条缺失判定条件，则核心问题域无法与相邻工作划清边界，第三段的分工也失去依据。反过来，若三条线各自给出判定式与代价来源，即便不引用任何实验数字，答案也已具备可评分性——因为考点被拆成了可逐项检验的定义与路径。
