一 · 把题干拆成三个可判定的子问题

题干问的是“跨硬件、跨 shape、跨 dtype 迁移时最可能在哪里失效”，并要求给出判断、验证方案与回退条件。这不是一道复述论文的题，而是一道定位失效面并设计可执行实验的题。拆解时先把它切成三个可独立回答的子问题：其一，KernelMosaic 的数据集与 agent 框架在什么意义上把“kernel 生成”变成了可检索、可复用的模式匹配；其二，这种模式匹配在三种迁移维度上分别依赖什么不变量；其三，当不变量被破坏时，系统会以什么可观测的形式失效（错误结果、编译失败、性能崩塌、还是静默降级）。三个子问题各自对应一个考点：数据集的组织粒度、agent 的反馈闭环、以及迁移时的正确性与性能 oracle。

题干里“最可能”三个字是考点核心。它要求排序而非罗列。排序的依据只能是机制层面的脆弱性：哪个环节对迁移最敏感，哪个环节的假设最容易被打破。回答时必须把“数据集覆盖了哪些 kernel 家族、agent 如何检索与改写、评测如何判定正确性”这条链条上的每一环都过一遍，找出假设最硬的那一环。题干还要求“不要只复述摘要”，意味着答案的骨架必须是自己的失效假设加验证设计，论文的贡献只作为定位失效面的坐标。

解题路径可以写成四步：第一步，从数据集的组织方式反推它隐含的不变量（shape 族、dtype 集合、硬件代际）；第二步，从 agent 的生成流程找出这些不变量被显式编码的位置（模板、检索键、反馈信号）；第三步，对每个迁移维度构造一个“不变量被破坏”的最小反例；第四步，为每个反例配一个可观测指标和一个回退动作。这四步对应四个公式或伪代码片段，下面逐节展开。

二 · 数据集粒度决定了迁移的“最近邻”是否可信

KernelMosaic 作为开放数据集，其价值在于把大量 CUDA kernel 连同问题描述、参考实现和评测配置一起组织起来，供 agent 检索与复用。考点在于：数据集的索引键是什么。如果索引键以算子语义（如 softmax、layernorm、GEMM 变体）为主，那么跨 shape 迁移时 agent 找到的“最近邻”在语义上正确，但在 tile 划分、寄存器压力、共享内存占用上可能完全不匹配；如果索引键包含 shape 与 dtype 的粗粒度分桶，那么跨硬件迁移时最近邻的语义仍然成立，但分桶边界之外的配置会落到错误的桶里。数据集粒度越粗，检索命中率越高，但命中后的改写成本越大；粒度越细，检索越精准，但长尾配置的覆盖率下降，agent 更容易退化成从零生成。

这里可以写出一个检索可信度的判据。设查询配置为 q=(shape, dtype, arch)，数据集中候选为 c，定义不变量距离

$$d(q,c)=\alpha\cdot\frac{|\log S_q-\log S_c|}{\log S_{\max}}+\beta\cdot\mathbb{1}[\text{dtype}_q\neq\text{dtype}_c]+\gamma\cdot\mathbb{1}[\text{arch}_q\neq\text{arch}_c]$$

其中 S 代表主导维度规模，α、β、γ 是权重。这个式子的用途不是算出精确数值，而是迫使解题者说明：哪些维度是连续的（shape 可用对数距离），哪些是离散的（dtype、arch 只能 0/1 判定）。离散维度的惩罚必须足够大，否则 agent 会把一个 fp16 的 kernel 直接套到 bf16 上，而 bf16 的尾数位更少，累加顺序与舍入行为不同，正确性 oracle 在容差边缘会抖动。代价体现在 token 上：检索键越细，agent 需要读入的候选描述越长，上下文预算被挤占，多轮改写轮次上升。

具体例子：一个以“行归约”为语义键检索到的 softmax kernel，在 shape 从每行 1024 元素迁移到每行 8191 元素时，原 kernel 的 block 内归约假设行宽是 2 的幂，越界处理分支被省略；迁移后要么编译期常量折叠失效导致性能崩塌，要么尾元素被静默丢弃导致正确性失败。这个例子说明数据集粒度不足时，失效首先表现为“语义对、配置错”，而 agent 的反馈信号如果只做数值比对，就会在容差内放过错误。

三 · agent 的反馈闭环在哪一环对迁移最敏感

Agentic framework 的核心是把“生成—编译—运行—比对—改写”做成闭环。考点是闭环中每一环的信号强度。编译失败是最强信号，因为它给出确定的布尔值；运行崩溃次之；数值比对依赖容差，是弱信号；性能信号最弱，因为噪声大且与正确性正交。跨硬件迁移时，最敏感的环节是编译与运行之间的那段：同一份 CUDA C++ 源码在不同架构上可能都编译通过，但其中一个架构的共享内存上限更低或 warp 调度粒度不同，导致运行期资源不足或 occupancy 骤降。此时闭环拿到的是“能跑但慢”，弱信号无法驱动 agent 做出正确的改写方向。

可以把闭环写成一个带优先级的选择伪代码思路：

  • 若编译失败，提取错误码与出错行，优先修正类型与内建函数可用性；
  • 若运行失败（非法访存、资源超限），回退到上一个通过编译的版本并降低 tile 规模；
  • 若数值比对超容差，定位首个不匹配元素的下标，判断是归约顺序还是边界处理；
  • 若以上皆过但性能低于阈值，才进入 profile 驱动的改写，且必须与基线对比而非与绝对阈值对比。

这个优先级顺序本身就是解题路径：它说明 agent 在迁移时最可能失效的地方不是“不会写 kernel”，而是“在弱信号区间做了错误的归因”。跨 dtype 迁移尤其如此：fp32 到 fp16 的累加精度变化不会让编译失败，也不会让大多数元素超容差，但会在长归约上累积出可观测偏差；agent 若只看最大绝对误差，就会误判为通过。代价是验证时延：为了捕获这种偏差，需要在比对时引入相对误差与分位数统计，单次验证的 GPU 时间上升，多轮 RL 的采样吞吐下降。

具体例子：一个在 A 架构上通过闭环的 reduction kernel，迁移到共享内存更小的 B 架构时，agent 收到“运行失败”信号后按伪代码回退 tile 规模，但回退动作只改了 block 维度，没有同步改 grid 维度的映射，导致部分输出未被写入；下一轮数值比对发现未初始化区域，agent 却把它归因为“随机初始化噪声”。这就是反馈闭环在迁移场景下的典型失效：信号存在，但归因错误。

四 · 三个迁移维度各自的不变量与破坏方式

跨硬件迁移依赖的不变量是“资源约束下的并行分解仍然合法”。具体机制包括共享内存容量、寄存器文件大小、warp 数与调度策略、以及内存层级带宽比。破坏方式很直接：原 kernel 的 tile 尺寸是按源架构的共享内存上限选的，迁移到上限更低的架构后，静态共享内存分配直接超出限制，编译期或加载期报错；或者 tile 恰好不超限但 occupancy 从多块每 SM 降到一块每 SM，延迟隐藏能力丧失，性能崩塌。这里的公式是 occupancy 的约束

$$\text{blocks per SM}=\left\lfloor\frac{\text{SM resources}}{\text{per-block resources}}\right\rfloor,\quad \text{occupancy}=\frac{\text{blocks per SM}\times\text{warps per block}}{\text{max warps per SM}}$$

解题时要指出：agent 若把 tile 尺寸当作超参数在源架构上搜到最优，迁移后这个最优点的邻域可能整体不可行，搜索空间发生拓扑变化，局部搜索会卡在边界。代价是编译时间与搜索轮次：每次 tile 变更都要重新编译并跑一遍正确性，跨架构的搜索预算成倍增长。

跨 shape 迁移依赖的不变量是“边界处理与归约顺序在规模变化下保持等价”。破坏方式是尾块比例上升：当主导维度不再是 tile 尺寸的整数倍时，越界分支从冷路径变成热路径，分支发散与谓词执行的开销占比上升；更隐蔽的是归约树的形状随规模变化，浮点加法的结合顺序改变，数值结果在容差边缘漂移。跨 dtype 迁移依赖的不变量是“算术强度与精度需求匹配”。破坏方式是低精度下的累加溢出与舍入误差累积，以及某些内建函数在低精度下没有对应指令而被迫走软件路径，性能与正确性同时受影响。

三个维度可以放进一张对照表，把不变量、破坏方式、可观测信号和回退动作并列：

迁移维度依赖的不变量破坏方式可观测信号回退动作
跨硬件资源约束下并行分解合法共享内存/寄存器超限、occupancy 骤降加载期报错、profile 中 stall 占比上升按新架构资源上限重算 tile，禁用原搜索缓存
跨 shape边界处理与归约顺序等价尾块变热路径、归约树形状改变尾块分支耗时占比、分位数误差漂移切换到按规模分档的模板，重跑分位数比对
跨 dtype算术强度与精度需求匹配累加溢出、内建函数降级为软件路径相对误差分位数、指令混合中软件路径占比提升累加精度或改用分块累加，重设容差判据

这张表本身就是解题路径的骨架：每一行给出一个可验证的假设，验证方案就是构造该行的最小反例并采集对应信号。具体例子：跨 dtype 时把 fp32 累加的 layernorm 迁到 fp16 输入，若仍用 fp16 累加，长行上的方差估计会出现系统性偏低，表现为归一化后输出的均值偏移；验证方案是对同一输入分别用高精度参考实现和候选实现比对分位数误差，而不是只看最大误差。

五 · 验证方案的设计：从最小反例到回退条件

验证方案必须能区分“失效”与“噪声”。设计要点有三：其一，每个迁移维度构造一个只破坏该维度不变量的最小反例，其余维度保持与源配置一致，避免多因素混淆；其二，正确性 oracle 采用分层判据——布尔级（编译、运行）、元素级（最大误差与相对误差）、统计级（分位数与均值偏移），三层各自设阈值；其三，性能判据必须与同架构基线对比，而不是与源架构的绝对数值对比，因为跨硬件的绝对性能不可比。

回退条件要写成可执行的判定，而不是模糊的“效果不好就回退”。可以给出一个回退触发的合取式：当且仅当候选在最小反例上通过布尔级与元素级判据、但在统计级判据上超出阈值，且 profile 显示新增开销集中在边界分支或软件路径时，触发回退到按规模或按 dtype 分档的模板版本。这个合取式的意义在于排除“性能略低但正确”和“正确性略差但性能更好”两种不该回退的情形。代价是验证流水线的复杂度：每个迁移维度都要维护一套反例与阈值，回归测试的 GPU 时延随维度数线性增长。

具体例子：跨硬件迁移的验证可以固定 shape 与 dtype，只改目标架构，采集加载期是否报错、occupancy 是否低于源架构的一半、以及相同输入下的输出是否逐位一致（同 dtype 同归约顺序时应逐位一致）。若加载期报错，回退动作是重算 tile 并清空 agent 的检索缓存；若 occupancy 骤降但结果正确，回退动作是切换到按架构分档的 tile 模板，而不是放弃该 kernel 家族。这个例子说明回退条件必须绑定具体信号，否则 agent 会在“重试”与“放弃”之间随机游走，浪费采样预算。

还需要指出验证方案的一个盲区：跨 shape 的统计级判据依赖输入分布。若反例只用了均匀随机输入，归约顺序改变带来的误差可能被低估；需要加入长尾分布或极端值输入，才能让分位数误差暴露出来。这增加了单次验证的 token 与 GPU 时间，但它是把“最可能失效”从猜测变成可判定结论的必要成本。

六 · 工程判断落在哪一环

综合三节的不变量分析，最可能的失效点排序是：跨硬件迁移中的资源约束破坏排第一，因为它是硬失败且 agent 的局部搜索无法跨越可行域拓扑变化；跨 dtype 迁移中的精度判据盲区排第二，因为它是静默失败且弱信号难以归因；跨 shape 迁移中的边界与归约顺序问题排第三，因为它通常表现为性能退化而非正确性失败，闭环尚能捕获。这个排序的依据是信号强度与可行域变化的组合：硬失败加拓扑变化最难恢复，静默失败加弱信号最难发现，性能退化加强信号最易处理。

工程判断的落点因此不在“让 agent 更会写 kernel”，而在“让 agent 在迁移前先重算可行域”。具体机制是：把目标架构的资源上限、目标 shape 的分档边界、目标 dtype 的累加精度要求作为生成前的硬约束注入 prompt 与检索键，而不是留给生成后的反馈去纠正。这样做的代价是 prompt 长度与检索复杂度上升，但换来了失效面的前移——把跨硬件与跨 dtype 的硬失败挡在生成之前，把闭环的采样预算留给真正需要搜索的性能调优。回退条件也随之简化：生成前约束不满足时直接拒绝该候选，而不是进入多轮改写。

最后落到一个可操作的判据：对任一迁移请求，先计算目标配置与数据集中最近邻的不变量距离 d(q,c)，若离散维度（dtype、arch）任一不匹配，则禁止直接复用最近邻的 tile 与内建函数选择，必须走“重算可行域—生成—分层验证”的路径；若仅连续维度（shape）不匹配，则允许复用但强制加入尾块反例与分位数比对。这个判据把题干要求的“判断、验证方案、回退条件”压缩成一条可执行的分支逻辑，也是本部分拆解题干的最终产物。
