一 · 题干的三层结构：从标题到可判定问题

《KernelFoundry: Hardware-aware evolutionary GPU kernel optimization》这个标题里藏着三层可拆解的信息，读题的第一步是把它们分开，而不是急着去找“加速比是多少”。第一层是对象：KernelFoundry 是一套面向 GPU kernel 的进化式优化框架，它的输入是算子规格（op spec）与硬件描述，输出是候选 kernel 实现；第二层是方法限定词 hardware-aware，意味着搜索循环里嵌入了硬件侧的可观测信号，而不是仅靠输出正确性做黑箱打分；第三层是 evolutionary，意味着候选池按代际演化，存在变异、交叉、选择三类算子与一个适应度函数。题干真正要问的是：在这个闭环里，“加速比”这个数字是在哪一步被计算出来的、它的分子分母各自取自什么测量口径、以及什么条件下这个比值失去可比性。

把标题拆成“对象—方法—度量”三元组之后，考题的判定点就明确了：考生需要能画出从基线测量到候选测量再到比值输出的数据通路，并指出通路上每一个可能引入不可比性的接缝。这些接缝包括：基线是否与候选跑在同一硬件同一驱动同一编译选项下；计时是否包含 kernel launch 开销与主机侧同步；候选是否经过 autotune 选点而基线是固定配置；以及最容易被忽略的一条——候选的正确性是否由与基线相同的 oracle 判定。任何一条接缝错位，比值就不再是同一坐标系下的两个点之比。

一个具体例子可以说明拆题的价值：若题干只写“报告加速比”，考生容易直接写出 T0/T1 就收笔；但若把“hardware-aware”这一层纳入，就必须回答硬件信号（如 occupancy、访存吞吐、SM 利用率）在搜索中扮演的是适应度项还是仅作日志，因为这决定了最终被选中的候选是不是“为这块卡调过参”的版本，而基线往往不是。这个差别直接落在可比性讨论上。

二 · 考点定位：四个必须命中的判分点

这类题目的判分点通常落在四处，缺一处即视为未完成拆解。第一处是公式本身：设基线时延为 T0、候选时延为 T1，加速比定义为

$$\text{speedup} = \frac{T_0}{T_1}$$

考生必须写清 T0 与 T1 是同一统计量（例如同为中位数、同为多次迭代的均值、同为剔除首轮预热后的稳态值），且单位一致。第二处是口径来源：论文给出的口径必须被复述为“基线取自何处、候选取自何处”，而不是笼统说“论文报告的加速比”。第三处是不可比条件的枚举，这需要按接缝逐条列出，而不是泛泛说“环境不同”。第四处是解题路径：从题干到公式到不可比条件之间要有可执行的推理链，例如“先确认基线是否为官方参考实现 → 再确认候选是否经过搜索选点 → 再确认计时边界是否含 launch → 最后判定比值是否落在同一坐标系”。

这四点的权重并不相同。公式是入场券，口径复述是区分“读过论文”与“只记结论”的分水岭，不可比条件是真正拉开差距的部分，解题路径则检验考生能否把上述三点组织成可复核的流程。工程上，这对应一个很实际的问题：当有人拿 KernelFoundry 的加速比数字去和另一套框架的数字并列比较时，能不能当场指出两者分母不同源。

代价维度在这里首次出现：把口径核对做扎实，需要额外的测量轮次。若基线要跑预热加稳态两段、候选要在 autotune 选点后重跑，单次对比的墙钟时间会成倍上升；在搜索循环内部，每一代候选都做全口径测量会拖慢演化收敛，因此实践中常采用“搜索期用廉价代理指标、报告期用全口径复测”的两段式，这个折衷本身就是考点之一。具体例子：若一代有数十个候选，搜索期每个候选只测一次短迭代，报告期只对最终胜出者做完整预热与多轮统计，则报告数字的统计功效依赖于这一次复测，而复测若与搜索期环境不一致，比值就带上了选择偏差。

三 · 解题路径：从题干到可复核的判定链

建议的路径是五步，每步产出一个可写进答案的判定句。第一步，锁定比较对象：确认 T0 对应的是官方基线实现还是框架自带的参考 kernel，二者在指令选择与并行分解上可能完全不同，混用会让比值失去意义。第二步，锁定测量边界：确认计时是否包含 kernel launch、是否在流上同步、是否计入首次编译或 JIT 开销。第三步，锁定选点状态：确认 T1 是搜索空间中的最优选点还是某一代的平均候选，前者带选择偏差，后者低估框架能力。第四步，锁定硬件与软件栈：确认两次测量是否同卡同驱动同编译器版本，hardware-aware 的搜索若针对特定 SM 数量与缓存层级调参，换卡即失效。第五步，写出结论句：在以上四项全部对齐时比值可比，任一项错位则只能作为“该框架在该配置下的自报数字”，不可跨框架横比。

这条路径可以用伪代码思路固化为一个核对函数：输入是两份测量记录，输出是可比性标签。伪代码层面，核对函数依次检查 baseline_id == candidate_id_source、timer_boundary_equal、selection_stage_equal、device_fingerprint_equal，任一为假即返回不可比并附上失配字段。这个函数的工程价值在于它可被写进评测流水线，作为报告生成前的门禁；代价是每次报告都要保存完整的测量元数据，元数据的存储与校验会带来额外的流水线时延，但对可信评测而言这是必要开销。

具体例子：假设某次报告中 T0 取自未调优的朴素实现、T1 取自经过多代演化并在本卡上 autotune 过的候选，则即便公式计算无误，比值也混合了“算法改进”与“调参收益”两种来源，无法归因。解题时应明确指出这种混合，而不是给出一个笼统的倍数。

四 · 需要调用的公式与量纲检查

除主公式外，答题时通常还要调用两个辅助关系。其一是加速比与吞吐的倒数关系：若以每秒处理元素数计，则吞吐比等于时延比的倒数，二者在数值上一致但量纲不同，写答案时不可混用单位。其二是相对误差传播：若 T0 与 T1 各自带有测量抖动 σ0 与 σ1，则比值的相对不确定度近似为

$$\frac{\sigma_{r}}{r} \approx \sqrt{\left(\frac{\sigma_0}{T_0}\right)^2 + \left(\frac{\sigma_1}{T_1}\right)^2}$$

这条式子用来判断“报告出的加速比”是否落在噪声之内。当 T1 远小于 T0 时，第二项主导，候选侧的单次测量抖动会被放大进比值；因此报告口径若只做单次测量，比值的可信区间会宽到足以吞掉框架间的差异。工程含义是：报告期必须给出重复测量的离散度，否则加速比只是一个点估计。

量纲检查还包括一个常被忽略的点：T0 与 T1 是否针对同一问题规模。若基线在大规模输入上测、候选在小规模输入上测，比值同时混入了规模效应；hardware-aware 搜索常在小规模上快速筛选、在大规模上复测，这个两段式若在报告中不声明，读者会把规模差异误读为框架差异。代价方面，统一规模意味着搜索期不能用小规模廉价筛选，收敛所需的候选评估次数上升，编译与测量总时间随之增加。

具体例子：若某候选在小规模下因 launch 开销占比高而显得慢，在大规模下因计算占比高而显得快，则同一候选在两个规模上给出两个方向相反的比值；解题时应把规模作为可比性条件之一显式列出，而不是默认读者知道。

五 · 不可比条件的分类与判据

不可比条件应按来源分类，每类给出可操作的判据。第一类是同源性问题：T0 与 T1 是否来自同一实现谱系。判据是检查基线是否为该算子的官方参考实现，若是，则候选相对它的比值衡量的是“从参考到优化”的总收益；若基线本身已是某框架的调优版本，则比值只衡量增量。第二类是对齐性问题：计时边界、同步方式、预热策略是否一致。判据是核对两份测量记录中的计时器起止点字段。第三类是选择偏差问题：T1 是否经过搜索选点。判据是看候选是否带“best-of-N”标记，带此标记的比值不能与单次实现的比值并列。第四类是硬件绑定问题：hardware-aware 的调参是否针对特定设备指纹。判据是比对两次测量的设备与驱动指纹，不同则搜索所得参数可能已不在最优区间。

这四类之外还有一类常被漏掉：正确性 oracle 的一致性。若候选的正确性由与基线不同的容差或不同的参考输出判定，则“通过验证的候选”集合本身不同，比值所对应的候选群体也就不同。判据是核对两侧的容差设置与参考实现。这一类在可信评测里权重很高，因为一个放宽容差后通过的候选可能在实际数值范围内不可用，其加速比再高也不构成有效收益。

表格可以把上述分类压缩成一张核对清单：

类别判据字段失配后果
同源性基线实现标识比值含义从“总收益”变为“增量”
对齐性计时起止点、预热轮次比值混入 launch 与冷启动开销

具体例子：若报告只写“相对基线加速若干倍”而未声明基线谱系，读者无法判断这个倍数里有多少来自算法重构、多少来自硬件调参；解题时应把“基线谱系声明”作为报告的最低要求写出，而不是替论文补全。

六 · 从拆题到答题的落点

把上述内容组织成答案时，落点应放在“可比性是一个需要逐字段核对的谓词，而不是一句定性描述”。具体写法是：先给出 speedup 公式并声明 T0、T1 的统计量一致性；再复述论文口径中基线取自何处、候选取自何处；然后按五类接缝逐条给出判据与失配后果；最后给出核对函数的伪代码思路，说明它在评测流水线中的位置。这样组织的好处是每一条结论都可被复核，而不是依赖读者对论文的信任。

工程判断上还有一层：hardware-aware 这一限定词使得 KernelFoundry 的加速比天然带有设备绑定性，因此它的数字更适合作为“在该设备上、相对该基线、经该搜索流程”的联合声明，而不适合作为框架能力的横向标尺。答题时若能把这一层写进不可比条件，就命中了本题最核心的考点。代价方面，坚持逐字段核对意味着报告生成前多一道门禁、测量元数据多一份存储、复测多一轮墙钟时间；这三项开销换来的是比值可归因，对于需要把 kernel 优化收益折算进端到端生产收益的场景，这是必须支付的成本。

最后一个具体机制值得点出：核对函数返回不可比时，不应简单丢弃数字，而应输出失配字段清单，使后续复测能定向补齐。这个设计把“不可比”从否定判断转化为可执行的修复指令，也是本题从读题走向工程落地的接口。

加速比口径的边界：T0 与 T1 在什么条件下才可比

KernelFoundry 这类硬件感知进化流程里，speedup 的定义本身很短：若基线时延为 T0、候选 kernel 时延为 T1，则 $$\text{speedup}=\frac{T_0}{T_1}$$ 但真正决定这个数字能不能横向比较的，是 T0 与 T1 是否在同一测量口径下取得。论文给出的口径要求基线与被测候选共享同一输入形状、同一 dtype、同一 warmup/重复次数、同一计时后端（CUDA event 或 wall clock），并且基线必须是“未改写的参考实现”而非另一个已调优版本。任一条不满足，比值就退化为两个不同实验的拼合，只能内部自比，不能跨条目、跨硬件排名。

失效条件集中在三处。其一是基线漂移：若 T0 取自框架默认 kernel（如 cuBLAS 启发式选择），而 T1 是在固定 tile 配置下测得，则 T0 随驱动版本、GPU 型号、甚至张量对齐变化，speedup 的分母不稳定。其二是计时边界：把 host 侧 launch 开销、内存分配、layout 转换计入 T1 却不计入 T0，会系统性高估；反之把 T0 的首次编译/autotune 时间摊入则系统性低估。其三是数值路径差异：候选若降低了精度（TF32、fp16 累加）而基线为 fp32，speedup 里混入了精度让渡，必须与正确性 oracle 的容差一起报告，否则该数字不可比。

工程代价随之而来。为守住可比性，评测端要对每个候选重跑基线并做配对采样，单条目的计时开销随时延线性增长；若候选触发重编译，编译时间不进 speedup 却进 wall-clock 预算，长尾候选会把整轮进化的吞吐拖低。一个具体例子：同一 GEMM 形状下，候选通过更大 shared memory tile 把 T1 压低，但 occupancy 下降导致尾块形状（M 不被 tile 整除）时延反弹，此时全形状平均 speedup 好看，单点 speedup 却小于 1——报告必须按形状分桶，而不是只给一个标量。
