一 · 题干的三层结构：问的是“问题”而非“方案清单”

题干“方向「生产端到端部署」要解决的三个具体问题是什么？给出评测侧与部署侧各两条可执行做法，并说明它与相邻方向的分工”包含三个可独立判分的成分，读题时必须先把它们拆开，否则容易写成一份泛泛的部署清单。第一层是“三个具体问题”——要求的是问题陈述，不是技术栈罗列；第二层是“评测侧与部署侧各两条可执行做法”——要求做法具备可执行性，即能被写成脚本、检查项或流水线阶段，而不是“加强监控”这类口号；第三层是“与相邻方向的分工”——要求给出边界判据，说明哪些事属于本方向、哪些事应交给相邻方向处理。

这三层的判分权重并不相同。第一层决定答案是否切题：如果三个问题彼此重叠（例如把“性能不达标”和“kernel 太慢”写成两条），则实际只回答了一个问题。第二层决定答案是否落地：可执行做法的判据是“能否被一个工程师在一天内写成可运行的检查”，而不是“是否听起来合理”。第三层决定答案是否具备工程判断力：分工说明必须能回答“同一个失败现象，应该由哪个方向负责定位”。

一个常见的失分模式是把“端到端”理解成“把 kernel 跑通”。端到端部署的真正难点在于：单 kernel 在 KernelBench 式微基准上通过正确性与加速比门槛，并不蕴含它在真实模型中、在真实输入分布下、在真实调度序列里仍然正确且仍然有收益。三个具体问题应当围绕这一落差展开，而不是围绕“如何写一个更快的 kernel”展开——后者是优化方向的事。

$$\text{端到端收益} = \frac{T_{\text{baseline}} - T_{\text{deployed}}}{T_{\text{baseline}}},\quad \text{约束：} \Delta_{\text{correct}} = 0$$

上式给出本方向的第一个形式化抓手：收益是相对基线的时延差，而正确性偏差必须为零。注意分子是端到端时延差，不是单 kernel 时延差——这直接引出第一个具体问题：微基准加速比与端到端时延之间的映射关系并不平凡，Amdahl 式稀释、kernel 启动开销、数据布局转换、框架调度间隙都会吞掉微基准上的收益。

二 · 考点拆解：三个问题各自对应哪类证据

把“三个具体问题”落到可判分的考点上，应当各自绑定一类证据，否则答案会退化成观点陈述。

  • 问题一：微基准到端到端的收益保真。考点是“加速比是否可迁移”。需要的证据是同一 kernel 在微基准 harness 与真实模型中的时延对比，以及端到端时间线上该 kernel 占比。代价维度是时延与测量噪声：端到端测量受调度抖动影响，单次测量不足以判定，需要重复采样并区分冷/热路径。
  • 问题二：真实输入分布下的正确性保持。考点是“微基准的输入采样是否覆盖部署分布”。需要的证据是正确性 oracle 在部署输入上的通过率，以及数值容差随规模/形状变化的敏感度。代价维度是显存与 token：构造覆盖性输入需要额外显存，若用 LLM 生成测试输入则消耗 token 预算。
  • 问题三：部署形态的约束满足。考点是“kernel 是否能在目标运行时、目标精度、目标并发下被实际调用”。需要的证据是编译产物在目标架构上的可加载性、动态形状下的重编译次数、以及与框架算子注册的兼容性。代价维度是编译时间与首次调用时延：Triton/CuTe 路径的 JIT 编译在动态形状下会触发多次特化编译，首次调用时延可能远超稳态。

这三个问题之所以是“具体问题”而非“泛泛风险”，在于每一个都能被写成一条可失败的检查：收益保真可以被“端到端收益低于阈值”判失败；正确性保持可以被“部署分布上 oracle 不通过”判失败；约束满足可以被“目标运行时加载失败或重编译次数超限”判失败。判分时看的是这三条检查是否互不重叠、是否各自有明确的失败判据。

问题失败判据主要代价维度应交给相邻方向的情形
收益保真端到端收益低于门槛时延、测量噪声单 kernel 内部仍慢 → 优化方向
正确性保持部署分布上 oracle 不通过显存、token需要形式化证明而非采样 → 验证方向
约束满足加载失败或重编译超限编译时间、首次调用时延需要改 DSL 表达 → Triton/CuTe 方向

三 · 解题路径：从题干到可执行做法的推导链

解题路径应当是“先定问题，再由问题反推做法”，而不是“先列做法，再凑问题”。具体推导链如下。

第一步，确定端到端收益的定义与基线。基线必须是部署前的真实路径，而不是微基准里的参考实现。这里需要调用一个分解式：把端到端时延拆成 kernel 计算时间、数据搬运时间、启动与调度开销、以及框架侧间隙。只有拆开之后，才能判断微基准收益在端到端中能保留多少。这一步的产物是一条时间线分解，而不是一个数字。

$$T_{\text{e2e}} = \sum_i \left( T^{\text{compute}}_i + T^{\text{mem}}_i + T^{\text{launch}}_i \right) + T_{\text{gap}}$$

第二步，确定正确性 oracle 的覆盖策略。微基准通常用随机输入加固定容差，而部署分布可能包含极端形状、稀疏输入、长尾数值。可执行做法是把 oracle 拆成“逐元素容差检查”与“分布覆盖检查”两层：前者判定数值是否在容差内，后者判定输入采样是否触达部署分布的关键区域。代价是显存与采样成本，因此需要给出采样预算的上界。

第三步，确定部署形态的约束清单。约束至少包括：目标架构的可加载性、动态形状下的特化次数、精度模式（如是否允许 TF32/FP16 累加）、以及与框架算子注册的接口一致性。这一步的产物是一张约束检查表，每一项都能被脚本化。

第四步，做分工判据。分工的本质是“失败现象的归属”。若端到端收益不足但单 kernel 在微基准上已接近 roofline/SOL，则问题在本方向（收益保真），应检查数据布局与调度间隙；若单 kernel 本身离 roofline 很远，则问题在优化方向；若正确性失败源于浮点结合律或规约顺序，且采样无法覆盖，则应转交形式验证方向；若约束不满足源于 DSL 表达力不足，则应转交 Triton/CuTe 方向。判据必须写成“若现象 X 且证据 Y，则归属 Z”，而不是“大致上属于”。

第五步，把两条评测侧做法与两条部署侧做法分别绑定到上述检查上。评测侧做法的判据是“能否在 CI 中自动判失败”，部署侧做法的判据是“能否在发布前拦截”。两侧不重复：评测侧回答“是否可信”，部署侧回答“是否可上线”。

四 · 需要调用的公式与伪代码思路

本方向至少需要三类公式。第一类是收益分解式（见第二节），用于判断微基准收益的保留率。第二类是正确性判据式，用于把 oracle 写成可执行检查：

$$\text{pass} = \bigwedge_{x \in \mathcal{D}_{\text{deploy}}} \left( \lVert f_{\text{kernel}}(x) - f_{\text{ref}}(x) \rVert \le \tau(\text{shape}, \text{dtype}) \right)$$

其中容差 τ 随形状与数据类型变化，而不是一个全局常数——这正是微基准与部署分布落差的来源之一。第三类是特化次数与编译代价的关系式，用于约束满足问题：动态形状下，特化次数随形状桶数量增长，首次调用时延等于各桶编译时间之和的期望。工程上常用“形状桶”策略把连续形状离散化，以编译时间换稳态时延。

伪代码思路（不写成代码块，只描述结构）：评测侧第一条做法是“端到端收益回归”——在固定模型与固定输入序列上，交替运行基线路径与部署路径，采集多次重复的时延分布，取分位数而非均值作为判据，并在时间线分解中标注该 kernel 占比；若占比低于某阈值，则收益保真检查直接判为“不可判定”而非“通过”，避免用噪声得出结论。评测侧第二条做法是“部署分布正确性采样”——从真实流量中抽取输入，按形状与数值区间分层，逐层跑 oracle，并记录每层的通过率与最大偏差；代价是显存与采样 token，因此需要设定分层数与每层样本数的预算上界。

部署侧第一条做法是“约束检查表脚本化”——在发布流水线中对编译产物做可加载性检查、对动态形状做特化次数上限检查、对精度模式做一致性检查；任一项失败即阻断发布。代价是编译时间：每次发布都要触发一次目标架构编译，若形状桶较多则编译时间线性增长，因此需要缓存编译产物并按桶复用。部署侧第二条做法是“灰度期收益与正确性双监控”——在小流量上同时采集端到端时延与 oracle 通过率，设定回滚判据；代价是灰度期资源占用与监控开销，且灰度流量若与部署分布不一致，则监控结论不可迁移。

一个具体例子：某归约类 kernel 在微基准上相对参考实现有明显加速，但在端到端中收益被数据布局转换吞掉——此时收益保真检查应判失败，并把证据指向布局转换的时延占比，而不是回头去优化 kernel 内部；这正是分工判据的用处。另一个例子：动态形状下形状桶设为若干档，特化编译在首次调用时集中发生，部署侧约束检查若只看稳态时延就会漏掉首次调用时延，因此检查表必须包含“冷启动路径”一项。

五 · 评测侧与部署侧的分工边界如何写进答案

分工说明不是一句“本方向负责端到端”，而是要给出可操作的归属规则。写法上应当把相邻方向各自的主题用一句话指路，然后把篇幅留给边界判据。例如：单 kernel 的 roofline/SOL 分析与内部优化属于优化方向；形式化正确性证明属于验证方向；DSL 层的表达与代码生成属于 Triton/CuTe 方向；多轮 RL 与可验证奖励属于训练侧方向。本方向只处理“已经有一个在微基准上可用的 kernel 之后，它能否在真实部署中保真地产生收益并保持正确”。

边界判据可以写成三条：其一，若失败现象在单 kernel 隔离测试中不复现，则归本方向；其二，若失败现象在隔离测试中复现且与硬件利用率相关，则归优化方向；其三，若失败现象是数值偏差且采样无法判定，则归验证方向。这三条判据的价值在于它们能被写成检查顺序：先隔离复现，再判断利用率，再判断数值可判定性。评测侧的两条做法对应前两条判据的证据采集，部署侧的两条做法对应第三条判据与发布拦截。

需要强调的是，评测侧与部署侧的可执行做法不能互相替代。评测侧的收益回归回答“这个 kernel 是否值得部署”，部署侧的约束检查回答“这个 kernel 是否能被部署”。前者失败时应回到优化或验证方向，后者失败时应回到 DSL 或编译配置。把两者混为一谈，会导致答案在判分时被认定为“只给了一条做法换了两个名字”。

最后落在具体机制上：本方向的工程判断力体现在“收益保真检查的判据是分位数时延加时间线占比，而不是均值加速比；约束检查的判据是冷启动路径的特化次数，而不是稳态吞吐”。这两条判据一旦写成脚本，三个具体问题就各自有了可失败的检查，评测侧与部署侧的分工也就有了可执行的归属规则，而不是停留在文字层面的方向声明。

题干的三层切口与不可回避的边界

拆这道题，先要意识到“三个具体问题”不是并列清单，而是有依赖顺序的三层切口：第一层是可测性——kernel 在评测环境里能否被稳定地判定正确与快慢；第二层是可迁移性——评测得到的收益能否在真实推理栈（含动态 shape、并发流、显存压力）里复现；第三层是可归因性——端到端收益究竟来自 kernel 本身还是来自调度、融合或数据布局的连带改动。三层中任一层断裂，后一层的结论都失效。因此答题时必须显式声明边界：本题只讨论“给定一个已通过单 kernel 正确性 oracle 的实现，如何把它送进生产并证明收益”，不讨论 kernel 的生成本身，也不讨论训练侧吞吐。

考点集中在两处容易被含糊带过的失效条件。其一是评测侧的代理指标偏差：microbenchmark 常用固定 shape 与独占 GPU，而生产端是变长序列、多流并发、L2 被邻接算子污染。若把评测加速比记为 $$S_{\text{eval}} = \frac{t_{\text{ref}}^{\text{iso}}}{t_{\text{cand}}^{\text{iso}}}$$，生产加速比记为 $$S_{\text{prod}} = \frac{t_{\text{ref}}^{\text{stack}}}{t_{\text{cand}}^{\text{stack}}}$$，则二者之差主要来自隔离假设被打破，答题时应指出需用后者而非前者做部署判据。其二是部署侧的回退成本：任何 kernel 替换都必须附带一条可执行的 fallback 路径，否则一次数值偏差就会把整条链路拖入不可用。

解题路径可拆为四步并各自绑定一条可执行做法：拆题干定位三层切口；对每层给出评测侧与部署侧各一条动作；用一张小表把“动作—验证信号—系统代价”对齐；最后说明与相邻方向（kernel 生成、单算子优化）的分工——本方向只对“已生成实现”做端到端裁决。下表给出该对齐的骨架，其中代价列必须写实：评测侧多轮复测带来的是 GPU 机时与排队时延，部署侧影子流量带来的是显存与带宽的额外占用。
