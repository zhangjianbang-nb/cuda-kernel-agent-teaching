一 · 题干的三层结构：方法主张、评测对象、验收口径

这道题表面是一个“怎么搭 harness”的工程问题，实质是一次对方法论文的可复现性审计。题干里“Agentic Kernel Optimization”是方法主张，“State-of-the-Art GPU Kernels”是效果主张，“Without Hand-Written CUDA”是约束主张——三者必须分别被 harness 的某一部分钉住，否则任何一项都可以被含糊过去。读题时先把题干拆成三列：左列是被测对象（agent 生成的 kernel 及其生成过程），中列是参照系（基线），右列是判定规则（正确性门、防作弊、上线门）。这三列不是并列关系，而是依赖关系：没有输入分布，基线无从谈起；没有正确性门，性能数字没有意义；没有防作弊，正确性门和性能门都可以被绕过。

考点因此落在四个具体位置。第一，“Without Hand-Written CUDA”是可证伪的约束：harness 必须能区分“agent 从零生成”与“agent 检索/复制了人类写的 kernel”，这要求记录生成轨迹而非只看产物。第二，“State-of-the-Art”是相对量：SOTA 只在给定基线、给定输入形状、给定硬件与软件栈下成立，harness 必须把这三者冻结成可版本化的配置。第三，正确性不是布尔值：浮点 kernel 的正确性门要定义容差、覆盖的输入域、以及是否包含边界与退化形状。第四，上线门与评测门不是同一个门：评测门关心的是“在受控分布上是否优于基线”，上线门关心的是“在真实流量分布与真实尾延迟约束下是否可接受”，两者的统计口径与样本量不同。

解题路径可以写成一条流水线：冻结环境 → 定义输入分布族 → 选定基线与基线实现方式 → 设计正确性 oracle → 设计防作弊信号 → 设计性能度量与统计口径 → 合成上线门。每一步都要回答“这一步拒绝了什么错误结论”。例如冻结环境拒绝的是“换了驱动版本所以变快了”；输入分布族拒绝的是“只在方阵上测所以看起来很好”。下面各节按这条流水线拆考点，不给最终配置，只给需要调用的公式与判断依据。

二 · 基线的三种形态与“SOTA”的可比性条件

基线不是一个数字，而是一个实现 + 调用约定 + 环境快照的三元组。工程上至少要准备三种基线，各自回答不同问题：库基线（cuBLAS/cuDNN/Triton 官方实现）回答“是否打得过成熟工程实现”；手写基线（人类专家针对同一形状调优的 kernel）回答“是否打得过人类专家”；朴素基线（naive 实现，如逐元素循环或未分块的 GEMM）回答“是否至少没有退化”。只报库基线会掩盖“agent 只是调用了库”的作弊路径，只报朴素基线则会把“略优于 naive”包装成 SOTA。

可比性有三个必须冻结的维度。其一是调用约定：是否允许融合、是否允许改变数值精度（如 TF32/FP16 累加）、是否允许改变输出布局。若 agent 把 FP32 GEMM 换成 TF32 而基线是 FP32，性能提升里混入了精度降级，必须单独标注。其二是环境快照：驱动、CUDA 版本、编译器版本、编译 flag（-O3、--use_fast_math）、GPU 型号与时钟策略。其三是测量协议：warmup 次数、重复次数、是否锁频、是否用 CUDA Graph 消除 launch 开销。任何一项未冻结，“快了多少”都不可复现。

这里需要调用加速比的规范定义，并明确分母：

$$\text{Speedup} = \frac{T_{\text{baseline}}}{T_{\text{agent}}},\quad T \text{ 为同一输入分布下的中位时延（含 launch）}$$

分母若取均值而非中位数，尾延迟会被少数离群样本主导；若排除 launch 开销，则小形状上的收益被系统性高估。代价在于：含 launch 的测量会让小 kernel 的加速比被固定开销压平，从而低估 agent 在大形状上的收益；不含 launch 则高估小形状收益。工程判断是两套都报，并在配置里声明哪一套用于上线门。具体例子：一个 fused elementwise kernel 在 1K 元素上，launch 开销可能与时延同量级，此时“加速 3 倍”只在排除 launch 的口径下成立，上线门必须用含 launch 的口径复核。

另一个常被忽略的考点是基线自身的调优程度。若库基线用的是默认启发式而非 autotune 后的最优配置，agent 只要触发一次 autotune 就能“赢”，这不构成方法贡献。harness 应记录基线是否经过与 agent 同等预算的调优，并在报告中把“基线调优预算”作为一个显式字段。

三 · 输入分布族：形状、稀疏性、数值域与到达模式

输入分布决定了性能结论的适用范围，也决定了正确性门的覆盖面。一个可复现的 harness 不应使用单一形状，而应定义分布族并从中采样，同时保留一组固定的“钉子形状”用于跨版本对比。分布族至少要在四个轴上展开：形状（方阵/长宽比极端的矩阵、batch 维为 1 或很大的情形、非 2 的幂的维度）、数值域（正态、均匀、含大量零、含极大/极小值、含 NaN/Inf 的鲁棒性样本）、稀疏性（结构化稀疏与非结构化稀疏对 kernel 路径的影响）、到达模式（离线大批量 vs 在线小批量、连续调用 vs 间隔调用对缓存与时钟的影响）。

采样策略需要公式化，否则“随机测了几个形状”无法复现。一个可执行的思路是分层采样并固定种子：

$$\mathcal{D} = \{(M_i, N_i, K_i, \text{dtype}_i, \text{layout}_i)\}_{i=1}^{n},\quad \text{seed}=s_0,\ \text{分层键}=\text{规模桶}\times\text{长宽比桶}$$

分层键保证小、中、大形状各有代表，避免随机采样全部落在中等方阵上。代价是样本量 n 直接乘以测量时间：每个形状都要 warmup 与多次重复，n 增大线性推高 harness 总时延。工程上常见的折中是固定一组钉子形状（覆盖典型与极端）用于回归，另用分层随机采样用于统计报告，两者分开记账。

数值域这一轴的考点最容易被跳过。正确性门若只用正态分布输入，kernel 在累加顺序改变后产生的误差可能被低估；若输入含大量零，某些分支可能未被覆盖。具体例子：一个 reduction kernel 在输入全为正态随机数时误差可控，但当输入含 +1e30 与 -1e30 相邻元素时，不同累加顺序会给出符号相反的结果，此时“正确性门通过”只在受限数值域上成立。harness 必须把数值域写进配置，并在报告中声明正确性结论的适用范围。

到达模式影响的是时钟与缓存状态。连续背靠背调用会让 GPU 保持高频，间隔调用则可能触发降频；前者测得的是稳态性能，后者测得的是冷启动性能。上线门若面向在线服务，应以间隔调用或真实请求间隔重放为准，否则会系统性高估吞吐。

四 · 正确性 oracle：容差、覆盖与“通过”的含义

正确性门不是“输出相等”，而是在声明容差与声明输入域下的等价判定。对浮点 kernel，至少要区分三种误差来源：算法等价性（同一数学表达的不同实现）、累加顺序导致的舍入差异、以及精度降级（TF32/FP16）。容差必须与这三种来源匹配，否则要么误杀合法优化，要么放过精度降级。

常用的判定式是相对误差与绝对误差的混合，并对分母做保护：

$$\text{pass} \iff |y_{\text{agent}} - y_{\text{ref}}| \le \text{atol} + \text{rtol}\cdot|y_{\text{ref}}|,\quad \text{对全部元素成立}$$

考点在于 atol 与 rtol 的取值依据：它们应由参考实现的数值分析与输入量级共同决定，而不是拍一个 1e-5。当 |y_ref| 接近零时，相对项失效，必须靠 atol 兜底；当输出量级很大时，atol 又形同虚设。更稳的做法是同时报告最大绝对误差、最大相对误差、以及误差分布的尾部分位数，让“通过”附带误差画像，而不是一个布尔值。

覆盖维度上，正确性门必须包含退化形状（M=1、K=1、空张量、非对齐维度）与边界数值（NaN/Inf 的传播行为、denormal）。代价是测试用例数量上升带来的验证时延；一个 GEMM kernel 若对每个形状都跑全量参考实现，参考实现本身可能比被测 kernel 慢一个数量级，验证时间会成为 harness 的瓶颈。工程折中是：参考实现用高精度（如 FP64 或 Kahan 求和）但只在抽样形状上跑，其余形状用库实现做交叉校验。

还有一个结构性考点：正确性 oracle 与被测 kernel 不能共享同一实现路径。若参考实现也调用了 agent 生成的同一份代码，正确性门就退化为自洽检查。具体例子：agent 生成一个融合了 bias 的 GEMM，若参考实现同样融合 bias 且用相同累加顺序，则累加顺序误差被完全掩盖，此时“通过”只证明了确定性，没有证明正确性。

五 · 防作弊信号：从产物审计到轨迹审计

“Without Hand-Written CUDA”这一约束的可信度，取决于 harness 能否观测到生成过程而非仅观测产物。仅审计产物时，agent 复制一段人类写的 kernel 与从零生成一段 kernel 在文本上不可区分。因此防作弊要分三层：产物层（代码相似度、是否包含对库的直接调用、是否包含从训练语料复现的注释）、轨迹层（工具调用序列、检索行为、编辑历史、是否出现整段粘贴）、行为层（在禁用检索的条件下是否仍能产出同等质量的 kernel）。

产物层最直接的信号是库调用检测：若 agent 生成的“kernel”内部直接调用 cuBLAS 或 Triton 的 dot，则性能优势来自库而非生成能力，必须单独归类。轨迹层的信号是检索—粘贴模式：一次工具调用返回大段代码后紧接着一次整文件写入，且写入内容与检索结果高度重合，这是需要标记的模式。行为层的对照实验是消融检索：在关闭检索工具的条件下重跑同一任务，比较成功率与性能分布，差异即为检索贡献。

这里有一个必须付出的代价：轨迹审计要求 harness 记录完整的工具调用日志与文件快照，存储与回放成本随任务时长线性增长；消融检索则直接把可用预算减半（同一任务跑两遍）。工程判断是：把消融检索限制在抽样子集上，而把产物层与轨迹层的自动信号做成全量、低成本的过滤器，只对过滤器命中的样本做人工复核。

另一个考点是测试集污染。若 agent 的训练或检索语料中包含 KernelBench 系的题目与参考实现，那么“生成”可能退化为“回忆”。harness 应保留一组未公开的形状与算子组合作为留出集，并在报告中区分公开集与留出集的成绩。具体例子：某 agent 在公开 GEMM 形状上表现优异，但在留出的非方阵、非 2 的幂形状上性能回落，这一落差本身就是防作弊信号的一部分。

六 · 上线门：把评测结论翻译成部署判据

上线门与评测门的差别在于约束的方向：评测门问“是否优于基线”，上线门问“在真实约束下是否不劣化”。上线门至少要加三条评测门没有的判据。第一，尾延迟约束：以 P99 而非中位数为判据，因为服务端的 SLO 通常定义在尾部。第二，数值稳定性约束：在真实流量分布上重跑正确性门，特别是长尾输入（极大 batch、异常值）不得触发 NaN 或显著误差。第三，回退成本：agent 生成的 kernel 若在部分形状上退化，是否有形状分派的回退路径，回退路径本身的时延是否被计入。

上线门的统计口径需要显式公式，否则“通过”无法复现：

$$\text{accept} \iff \Delta T_{P99} \le 0 \ \wedge\ \text{pass}_{\text{correctness}}(\mathcal{D}_{\text{prod}}) \ \wedge\ \text{fallback\_cost} \le \tau$$

其中 ΔT_P99 是相对基线的 P99 时延变化，D_prod 是生产流量分布，τ 是允许的回退开销上限。代价在于：P99 需要足够大的样本量才能稳定估计，样本量不足时 P99 的置信区间会宽到无法做出接受/拒绝判断；而增大样本量又推高上线前的验证时延。工程折中是先用中位数与 P95 做快速筛选，只对通过筛选的候选跑足量 P99 验证。

还有一个容易被忽略的判据是编译与加载时间。agent 生成的 kernel 若依赖运行期 JIT（如 Triton 的编译缓存未命中），首次调用的时延可能远超稳态时延，这在冷启动或弹性扩缩容场景下直接体现为超时。上线门应把“冷启动首次调用时延”作为一个独立指标，而不是把它平均进稳态测量里。具体例子：一个 Triton kernel 稳态比基线快，但首次调用触发编译，冷启动时延是基线的数倍；若上线门只看稳态，这个 kernel 会在扩容瞬间造成请求堆积。

最后，上线门必须绑定可回滚的配置：kernel 选择、形状分派阈值、精度模式都应作为可版本化的配置项，使得一次上线失败可以定位到具体配置差异而非“整体变慢”。这与第二节的环境快照是同一套思路，只是从评测侧延伸到了部署侧。
