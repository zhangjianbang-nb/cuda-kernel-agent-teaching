一 · 拆题干：四个问句对应四个可独立验收的子系统

题干是一句带问号的标题，但工程上它必须被拆成四个可以分别写测试、分别出报告的子问题，否则整篇论文的结论无法被复现。第一问是“基线是什么”：PyTorch 的哪个版本、哪种调用路径（eager 还是 torch.compile）、是否允许 cuBLAS/cuDNN 的启发式选择、是否计入首次调用的 autotune 开销。第二问是“输入分布是什么”：shape、dtype、layout、stride、是否含广播、是否含 mask、数值范围与稀疏度。第三问是“正确性门怎么定”：逐元素容差、归约类算子的相对误差、NaN/Inf 传播语义、非确定性算子的可接受抖动。第四问是“上线门怎么定”：在什么硬件、什么 batch 下、以什么统计量（中位数还是 p99）、相对基线要快多少才算“actually beat”。

这四个问句不是并列的，它们有依赖顺序：基线定义决定了输入分布的可比性，输入分布决定了正确性门的严格程度，正确性门决定了哪些候选 kernel 能进入性能比较，性能比较的统计口径决定了上线门。任何一环松动，后面三环的结论都会被污染。因此读这篇论文时，第一个动作不是看它的加速比表格，而是找它把这四问写在哪一节、用了什么措辞、有没有给出可执行的配置片段。

一个具体的拆解例子：若论文声称某 fused softmax kernel 比 PyTorch 快，必须能回答“PyTorch 侧是 torch.softmax 还是手写三段式”“输入是否沿最后一维连续”“是否包含 causal mask 分支”“计时是否包含 kernel launch 之外的 host 侧同步”。这四个细节中任意一个缺失，读者就无法在自己的 harness 里重建同一条基线，论文的“beat”就退化为不可验证的断言。

二 · 考点一：基线的可复现性——把“PyTorch”钉死成一个可执行对象

“Beat PyTorch”这句话在评测学上是病句，因为 PyTorch 不是一个固定的性能点，而是一个随版本、后端、启发式策略、甚至环境变量漂移的分布。可复现 harness 的第一条要求是把基线钉成一个带版本号与调用签名的可执行对象，并在报告里显式记录它的“配置指纹”。

机制上，基线应当由三部分组成：算子级参考实现（reference op）、其调用路径（dispatch path）、以及计时边界（timing boundary）。参考实现要固定 dtype 提升规则与广播语义；调用路径要固定是否走 torch.compile、是否允许 TF32、是否开启 cudnn.benchmark；计时边界要固定是否 warmup、是否在同一个 stream 上、是否用 CUDA event 而非 host 时钟。三者任一漂移，基线的时延就会变，而候选 kernel 的时延不变，于是“加速比”变成一个受基线漂移支配的量。

$$\text{speedup}=\frac{T_{\text{base}}(\text{cfg}_{\text{base}})}{T_{\text{cand}}(\text{cfg}_{\text{cand}})},\quad \text{valid only if } \text{cfg}_{\text{base}}\equiv\text{cfg}_{\text{cand}}\text{ on dtype/layout/shape}$$

代价在这里体现为“基线构建的工程量”：为了让基线可信，harness 需要为每个算子维护一份参考实现与一份调用配置，并在每次评测时校验配置指纹是否与记录一致。这不是免费的——它增加了 harness 的维护成本与每次评测的启动时延（要跑 warmup、要读环境变量、要校验版本），但它换来的是结论的可迁移性。若省掉这一步，省下的是几行配置代码，付出的是整篇论文的加速比无法被任何人复算。

具体例子：同一台机器上，torch.matmul 在开启 TF32 与关闭 TF32 两种配置下的时延差异足以让一个手写 GEMM kernel 的“加速比”从正变负。因此基线配置必须把 TF32 开关写进指纹，并在候选 kernel 侧做同样的数值精度对齐，否则正确性门与性能门会互相打架。

三 · 考点二：输入分布——shape 与 layout 是隐藏的自变量

kernel 的性能对 shape 极其敏感：一个在 (4096, 4096) 上跑出高利用率的 tiling 策略，在 (17, 4093) 上可能因为尾块处理而塌陷。因此输入分布不是“随便给几个 tensor”，而是一组被显式声明、可枚举、可复现的用例集合。harness 需要把用例集合写成数据文件，而不是散落在脚本里的字面量。

机制上，输入分布应包含四个维度：规模维度（覆盖小、中、大与不规则尾块）、dtype 维度（fp32/fp16/bf16，必要时 fp8）、layout 维度（连续、转置、带 stride 的视图、非对齐起始地址）、语义维度（是否含 mask、是否含边界条件、是否含退化输入如空 tensor）。每个维度都要有“为什么选它”的理由，因为评测的覆盖面直接决定了结论的外推范围。

代价体现在显存与评测时长：覆盖大 shape 会推高显存占用，覆盖多 dtype 会把评测时间乘以用例数。一个务实的口径是分层采样——用小 shape 做正确性门（便宜、快、覆盖边界），用大 shape 做性能门（贵、慢、覆盖吞吐），两层用不同的用例集合，并在报告里分别标注。若把两层混在一起，要么正确性门被大 shape 拖慢，要么性能门被小 shape 稀释。

具体例子：一个 reduction kernel 在 N=1024 时可能被 launch 开销支配，在 N=2^24 时才进入带宽受限区。若输入分布只取前者，测出来的是 launch 开销而非 kernel 质量；若只取后者，边界条件（如 N 不是 block 整数倍）永远测不到。因此用例集合必须同时包含“支配项不同的两端”，并在报告里说明每一端各自在考什么。

四 · 考点三：正确性门——容差不是拍脑袋，而是由数值路径决定

正确性门是 harness 里最容易被糊弄过去的一环：很多评测只写“allclose with rtol=1e-2”，却不说明这个容差从哪来。可复现的正确性门应当由数值路径推导：算子内部是否改变了求和顺序（归约）、是否使用了低精度中间量（如 bf16 累加）、是否引入了 fused 的近似（如 fast math 的 rsqrt）。每一种路径改变都对应一个误差量级，容差应当与这个量级同阶，而不是与“看起来能过”同阶。

机制上，正确性门分三层：第一层是形状与 dtype 契约（输出 shape、stride、dtype 必须与参考一致，这一层是硬门，不容差）；第二层是数值等价（逐元素或按范数比较，容差由数值路径给出）；第三层是语义等价（NaN/Inf 传播、mask 位置的行为、空输入的行为）。三层中任何一层失败，候选 kernel 都不进入性能比较——这一点必须在 harness 里写成短路逻辑，而不是靠人工判断。

$$\text{pass}\iff \|\hat{y}-y\|_2 \le \tau\cdot\|y\|_2+\epsilon,\quad \tau=\tau(\text{accum dtype},\ \text{reduction order},\ \text{fused approx})$$

代价是“正确性门会杀掉一部分本来能跑得更快的候选”：一个用 bf16 累加换取吞吐的 kernel，可能在 fp32 参考下过不了严格容差，但它在其目标精度下是合法的。harness 的处理方式不是放宽全局容差，而是为每个用例声明其“参考精度”，让候选 kernel 在与自身精度匹配的参考下比较。这样做的代价是 harness 需要维护精度矩阵，收益是正确性门不再成为“谁更保守谁通过”的竞赛。

具体例子：softmax 的参考实现若在 fp32 下逐元素比较，一个用 online softmax 且以 fp32 累加的 kernel 通常能过；但若参考实现本身用了不同的 max 减法顺序，误差会集中在极小概率元素上，此时逐元素容差会误杀。正确做法是按行做范数比较并单独检查最大值位置，而不是对每个元素用同一个阈值。

五 · 考点四：防作弊与上线门——把“快”定义成可统计、可归因的量

防作弊要防的不是恶意，而是“无意的度量污染”：缓存命中被当成 kernel 快、把计算挪到计时区间外、用更低的精度换时延却不声明、只报最好一次而隐去方差。harness 的应对是把计时协议写成不可协商的契约：固定 warmup 次数、固定重复次数、固定取哪个统计量（中位数与 p99 同时报）、固定是否清 L2、固定输入是否复用同一块显存。

机制上，防作弊的核心是“归因”：每一次计时必须能回答“这段时间花在哪”。这要求 harness 在候选 kernel 侧也采集与基线同口径的指标——至少是 kernel 级时延与有效带宽，必要时用 NCU 采集 DRAM 吞吐、occupancy、stall 原因。只有当候选与基线在同一套归因口径下比较，“beat”才有意义；否则一个把预处理挪出计时区间的 kernel 会显得更快，而它的端到端收益为零。

上线门则是把“快”转成工程判断：相对基线的加速比要达到多少、在哪个 batch 下、端到端（含数据搬运与 launch）是否仍为正收益、方差是否小到可以被部署决策依赖。这里必须区分 kernel 级加速与端到端加速——前者是微基准，后者才是上线依据。一个 kernel 级 2 倍加速若被 host 侧同步与数据布局转换吃掉，端到端可能为负，此时上线门应当拒绝它。

门判据失败代价
形状/dtype 契约输出元数据与参考逐项相等直接淘汰，不进入计时
数值等价范数误差 ≤ 由数值路径导出的 τ淘汰或降级到低精度赛道
语义等价NaN/Inf/mask/空输入行为一致淘汰，防止边界条件下静默错误
计时协议warmup、重复数、统计量、L2 状态固定报告作废，需重跑
端到端上线门含搬运与 launch 的收益为正且方差可接受拒绝上线，保留为微基准结论

代价是评测吞吐：完整跑一遍五道门，每个用例要经历参考实现、候选实现、多次计时、必要时 NCU 采集，单用例耗时远高于“跑一次 allclose 再跑一次计时”的草率做法。但这个代价换来的是结论的可审计性——任何读者都能按同一份配置复算，而不是只能相信表格。

具体例子：一个 fused layernorm 候选在 kernel 级比基线快，但 harness 若把输入布局转换算进端到端，收益可能被吃掉；此时正确的工程判断不是宣布“beat”，而是把结论限定为“在已就绪的连续布局下、batch 达到某阈值时端到端为正”，并把布局转换的成本单独列为上线门的一项。这正是这篇论文的 harness 必须回答、而标题问句本身无法回答的部分。

六 · 解题路径：从题干到可执行配置的推导链

把上述考点串成一条推导链，就是读这篇论文时应逐段核对的路径：先定位基线配置指纹，再定位输入用例集合的声明方式，再定位正确性门的容差来源，再定位计时协议与归因口径，最后定位上线门的统计判据。每一段都要问同一个问题——“这一段的配置能否被我原样抄进自己的 harness”。能抄，则结论可复现；不能抄，则这一段只是叙述而非方法。

这条路径也给出了写 harness 的顺序：先写基线封装与指纹校验，再写用例集合的数据化描述，再写三层正确性门与短路逻辑，再写计时协议与归因采集，最后写上线门的统计汇总。顺序不能颠倒，因为后一层的输入依赖前一层的输出契约。若先写计时再写正确性门，就会出现“跑得快的候选其实算错了”的返工。

需要调用的公式在此收敛为三组：加速比的定义式（必须带配置等价前提）、正确性门的范数判据（必须带由数值路径导出的 τ）、以及端到端收益的分解式——把 kernel 时延、launch 开销、布局转换与同步开销分别列出，只有当总和相对基线为负时才判上线。三组公式的共同点是都带“前提条件”，这正是评测 harness 与单纯跑分脚本的区别。

读题不是读题面：把题干拆成可执行的约束集合

读题阶段真正要产出的是四张清单：算子语义、数据形状与 dtype 组合、数值容差与边界行为、以及基线口径。以“LLM 生成的 kernel 是否真的快过 PyTorch”为例，题干里“beat”这个词必须被拆成可判定的谓词：在给定输入分布下，生成 kernel 的端到端时延低于基线，且正确性门全部通过，且不触发防作弊规则。三者是合取关系，任一失败即整条样本判负。读题时要把“正确性门”与“性能门”写成两个独立函数，而不是一个混合打分，否则一个 0.1% 的数值偏差会被时延优势掩盖。代价在这里已经出现：每增加一个 dtype 组合或一个边界形状，正确性校验的调用次数线性上升，评测 harness 的 wall-clock 时间随之膨胀，而 token 预算不变——读题阶段多列一组 shape，后面就要多跑一轮参考实现。

考点拆解要落到可调用的公式上。性能侧的核心判据是 roofline 上的可达上界：

$$T_{\min}=\max\left(\frac{\text{FLOPs}}{\text{PeakFLOPS}},\ \frac{\text{Bytes}}{\text{PeakBW}}\right),\quad \text{SOL}=\frac{T_{\min}}{T_{\text{measured}}}$$

读题时必须先估出 $T_{\min}$，否则无法判断“快过 PyTorch”是真实优化还是基线选弱了。若基线用的是未融合的 eager 实现，SOL 天然偏高，生成 kernel 的“胜利”是伪胜利。失效条件很具体：当算子处于 memory-bound 区间且 PyTorch 已走融合路径（如 `torch.compile` 后的 inductor kernel），生成 kernel 的剩余空间只剩 launch 开销与尾部规约，此时任何“大幅领先”的读数都应先怀疑基线口径而非庆祝。系统代价是编译时间——为确认基线是否已融合，需要跑一次带缓存的编译，冷启动编译时间会直接计入 harness 的准备阶段，且这部分时间不应算进 kernel 时延。

解题路径应写成有序的判定链而非单一答案：先定语义等价（含 NaN/Inf 传播、空 tensor、非连续 stride），再定容差（按 dtype 给绝对/相对阈值），再定输入分布（是否含极端幅值、是否覆盖尾部 shape），最后才谈时延。防作弊的边界条件要在读题时就写死：禁止生成代码读取基线输出、禁止按 shape 硬编码分支、禁止在计时区间外做预计算。一个具体例子是归约类算子——若生成 kernel 在 warmup 阶段把结果缓存进全局内存、正式计时时直接读回，正确性门会通过而时延异常低，这类样本必须在读题阶段就标记为“需检查计时区间内的内存写入量”。
