一 · 把题干拆成可判定的子问题

题干问的是“a real workload”能被 LLM 生成的 GPU kernel 覆盖到多少。这句话里有三个必须分开处理的词：real workload、LLM-generated kernel、actually reach。它们分别对应三类不同的判定对象，混在一起答就会变成泛泛而谈。拆题的第一步是把“覆盖多少”翻译成一个可测量的比值：在真实负载的计算图中，有多少比例的计算量（或时延）被替换成了 LLM 产出的 kernel，并且这些替换在正确性 oracle 下通过、在 roofline/SOL 意义下达到可接受的效率。这个比值不是单一标量，而是一个三元组：覆盖率、正确率、效率达标率。题干中的“reach”正是指第三个维度——kernel 不只是能跑对，还要跑到接近硬件上限。

第二个拆解点在于“real workload”的边界。真实负载不是 KernelBench 里那种单算子、固定 shape 的题目，而是由多个算子串成的图，带有动态 shape、混合精度、原地操作、非连续 stride、跨流依赖。因此题干隐含了一个 pipeline 视角：从负载图切分出候选 kernel 边界，到生成、编译、运行、评测，每一步都可能截断“可达比例”。读题时必须意识到，最终数字是这条链上各步通过率的乘积，而不是某一步的孤立指标。

第三个拆解点是“LLM-generated”的粒度。生成的是 CUDA C++、Triton、CuTe 还是 PTX，决定了后续编译与 profile 的失败模式完全不同：Triton 走的是编译器自动调度，失败多发生在 layout 与 block size 选择；CUDA C++ 失败多发生在同步与共享内存；PTX 则把寄存器分配与指令选择的代价全部暴露给生成器。题干没有限定语言，因此答题路径应当按语言分层给出判据，而不是假定单一技术栈。

二 · 考点定位：四个必须显式回答的判据

这道题的考点不在“能不能生成一个能跑的 kernel”，而在评测可信度。可以把考点归为四条判据，答题时每一条都要给出机制与代价。

  • 正确性 oracle 的强度：是逐元素 allclose、还是带容差的相对误差、还是对 reduction 类算子用统计量比对。oracle 太松会把错误 kernel 判为通过，直接虚高覆盖率；太严会把合法的浮点重排判为失败。这里要指出 oracle 本身有成本：参考实现的运行时间、额外显存占用、以及为动态 shape 生成参考输出的编译开销。
  • 执行反馈的可归因性：编译失败、运行时报错、结果错误、性能不达标是四类不同信号，必须分别统计。把它们合并成一个“成功率”会掩盖 pipeline 的真实瓶颈。考点在于能否说清每一类失败模式对应哪一步、由什么信息触发。
  • 性能判据的基准选择：是跟 PyTorch eager 比、跟 cuBLAS/cuDNN 比、还是跟手写最优 kernel 比。基准不同，“reach”的分母就不同。roofline/SOL 分析要求先算出该算子的算术强度与内存流量下界，再判断实测时延离下界多远。
  • 多轮优化的收敛性：单轮生成的成功率与多轮 RL/执行反馈后的成功率不是同一个量。考点是能否说明反馈信号如何进入下一轮、以及多轮带来的 token 与时延代价。

这四条判据共同决定了题干中“how much”的分母与分子。只回答其中一条，就等于没有回答题干。

三 · 解题路径：按 pipeline 顺序展开的五步

题干明确要求按“生成—编译—运行—评测”的顺序回答，因此解题路径应当是一条链，每一步写清输入、输出、失败模式，并在步与步之间标出通过率如何累积。

第一步，负载切分与候选提取。输入是真实负载的计算图（算子序列、shape、dtype、依赖边），输出是一组候选 kernel 边界及其调用契约（输入输出 tensor 的 layout、stride、别名关系）。失败模式是切分错误：把有跨算子融合机会的区域切碎，或把带副作用的原地操作当成纯函数。这一步的代价是分析时间与图重写风险，且切分粒度直接决定后续生成题目的难度分布。

第二步，生成。输入是候选边界加上参考实现（或规格描述），输出是源码。失败模式包括语法错误、API 误用、缺少边界检查、对动态 shape 硬编码。代价是 token 消耗与生成时延；若采用多候选采样，代价按候选数线性增长。

第三步，编译。输入是源码与目标架构，输出是可加载模块或编译诊断。失败模式按语言分化：Triton 常见的是 block size 与 layout 约束冲突、不支持的数据类型；CUDA C++ 常见的是共享内存超限、寄存器溢出、缺少架构特性守卫。代价是编译时间，尤其在多候选、多架构交叉编译时会被放大。

第四步，运行。输入是可加载模块与构造好的输入 tensor，输出是结果 tensor 与运行时统计。失败模式包括非法内存访问、同步缺失导致的竞态、动态 shape 下的越界、以及数值溢出。代价是显存占用与运行时时延；竞态类错误还可能表现为间歇性错误结果，使 oracle 判定不稳定。

第五步，评测。输入是结果与参考、以及 profile 数据，输出是正确性判定与效率判定。失败模式是判据本身失真：容差设置不当、基准选择不当、profile 采样开销扰动时延。代价是参考实现与 profile 工具的额外时间与显存。

把五步串起来，最终“可达比例”是各步通过率的连乘。答题时应显式写出这个连乘结构，并指出哪一步是当前瓶颈——这比给出一个孤立百分比更能体现工程判断。

四 · 需要调用的公式与判据

题干要求给出公式，但不是要数值答案。核心公式有三组。

第一组是覆盖率与可达比例的连乘定义。设候选 kernel 总数为 N，第 i 步的通过率为 p_i，则端到端可达比例可写成：

$$\text{Reach} = \prod_{i \in \{\text{gen},\text{compile},\text{run},\text{correct}\}} p_i \cdot \frac{1}{N}\sum_{j=1}^{N} \mathbb{1}[\text{efficiency}_j \ge \tau]$$

这里 efficiency 是相对 roofline 的达标程度，τ 是工程上可接受的阈值。公式的作用是把“多少”拆成通过率与效率达标率两部分，避免把“能跑对”和“跑得快”混为一谈。

第二组是 roofline 判据。对某算子，先算算术强度 I = FLOPs / Bytes，再与机器的拐点 I* 比较，得到时延下界：

$$T_{\min} = \max\left(\frac{\text{FLOPs}}{\text{PeakFLOPS}},\ \frac{\text{Bytes}}{\text{PeakBW}}\right)$$

实测时延 T 与 T_min 的比值就是 SOL 利用率。答题时要指出，Bytes 的估算依赖对 layout 与缓存行为的假设，估算偏差会直接改变“达标”判定，因此效率判据本身带有建模误差。

第三组是正确性判据的容差形式。对浮点输出，常用相对误差与绝对误差的混合判据：

$$|y - \hat{y}| \le \text{atol} + \text{rtol}\cdot|y|$$

对 reduction 类算子，逐元素判据不适用，应改为对总和或均值的统计比对。答题时要说明容差选择与 dtype、累加顺序的关系：fp16 累加与 fp32 累加的误差量级不同，容差过紧会误杀合法实现。

此外还应给出一个伪代码思路，说明多轮反馈如何闭合：

  • 对每个候选，记录 (编译结果, 运行结果, 正确性判定, SOL 利用率) 四元组；
  • 仅当正确性通过时才把 profile 数据回灌到下一轮提示；
  • 把失败模式按类别聚合，作为下一轮生成的负样本约束；
  • 每轮结束后重算连乘通过率，判断是否已收敛。

这个闭环的关键在于：错误 kernel 的 profile 数据没有意义，不能用来指导优化；只有正确性先过，性能反馈才可信。

五 · 具体例子：一个融合算子的五步走查

取一个真实负载中常见的模式：LayerNorm 后接残差加与 GELU。它是一个多算子串，存在融合机会，shape 随 batch 动态变化，dtype 为 fp16 输入、fp32 累加。按上面的路径走一遍。

切分阶段，候选边界有两种：整体融合成一个 kernel，或拆成 LayerNorm 与逐元素两段。前者减少一次全局内存往返，但要求生成器同时处理 reduction 与逐元素逻辑；后者更容易生成正确，但带宽代价更高。这一步的失败模式是把残差加的别名关系漏掉，导致原地写入破坏输入。

生成阶段，若用 Triton，生成器需要给出 block size 与 num_warps；若用 CUDA C++，需要给出共享内存归约与 warp shuffle 的选择。失败模式分别是 layout 约束冲突与共享内存超限。编译阶段的代价体现在多候选交叉编译上：每个候选都要单独编译，编译时间随候选数增长。

运行阶段，动态 shape 会触发对硬编码 tile 大小的越界；fp16 输入若在归约时未提升到 fp32，会引入可见误差，触发正确性判据失败。评测阶段，逐元素容差判据对 GELU 的近似实现可能过严，应改用组合判据；roofline 估算要把两次全局读写与一次写出的字节数算清，才能判断融合版本是否真的接近带宽下界。

这个例子的价值在于：它同时暴露了切分、生成、编译、运行、评测五步各自的失败模式，并且说明“可达比例”不是单点指标——融合版本可能正确率更低但效率更高，拆分版本相反。答题时应把这种权衡写出来，而不是只报一个通过率。

六 · 答题时需要显式标注的代价项

题干要求每个部分都给出性能或正确性代价。读题阶段就应把代价项列成清单，避免答题时遗漏。代价项包括：生成阶段的 token 与时延、编译阶段的编译时间、运行阶段的显存与时延、评测阶段的参考实现开销与 profile 采样扰动、以及多轮反馈带来的总时延放大。

其中两个代价最容易被忽略。其一是 profile 工具的采样开销：NCU 逐 kernel 采集会串行化执行，改变原本的并发重叠，使测得的时延偏离真实负载下的表现。其二是参考实现的显存占用：在动态 shape 下为每个 shape 生成参考输出，会额外占用显存，可能反过来限制候选 kernel 的可测规模。答题时指出这两点，能体现对评测可信度的理解，而不只是罗列 pipeline 步骤。

最后落到工程判断上：这道题的正确答法不是给出一个百分比，而是给出连乘结构、指出瓶颈步、说明判据的建模误差来源，并用一个具体融合算子把五步走查一遍。题干问“how much”，真正考的是能否把“多少”拆成可归因、可复现的量。

拆解“生成—编译—运行—评测”链路的边界：每一步的失效面与系统代价

题干问的是“pipeline 从输入到评测要经过哪几步、每步的输入输出与失败模式”，考点不在列举步骤名称，而在识别这条链路是串联的可靠性链而非并列的四个模块：任何一步的失败都会截断后续信号，因此“LLM 生成的 kernel 能走多远”本质上是各步存活概率的乘积，而不是单点能力的上限。解题路径应先把题干拆成四个可判定的状态转移——生成（自然语言/参考实现 → 源码文本）、编译（源码 → 可加载的 cubin/PTX）、运行（可加载模块 → 正确输出 + 计时）、评测（正确性与性能数据 → 相对基线或 SOL 的比值），再对每个转移问三件事：输入是什么形态、输出用什么契约判定、失败时留下什么可观测痕迹。公式上可写成 $$P_{\text{reach}} = \prod_{i=1}^{4} p_i,\quad \text{且}\ \text{cost}=\sum_i c_i^{\text{tok}}+\sum_i c_i^{\text{compile}}+\sum_i c_i^{\text{run}}$$ 其中每个 $$p_i$$ 不是常数而是条件概率，取决于前一步输出的质量（例如编译期报错信息是否足以让下一轮生成修正）。

边界首先出现在“生成”这一步：题干的输入若是自然语言描述，则失败模式是语义漂移——模型给出语法合法但语义错位的 kernel（例如把归约维度写反），此时编译与运行都可能通过，错误只在评测的正确性 oracle 处暴露；若输入是参考实现（PyTorch 或 numpy），失败模式转为 API 覆盖不足与数值约定不一致（dtype 提升、边界 padding、非连续 stride）。这一阶段的代价主要是 token：多轮修复会把单次生成的 token 预算成倍放大，而每次重试都要重新走编译，因此 token 成本与编译时延是耦合的，不能分开估算。一个具体例子：参考实现里含一个动态 shape 的 softmax，生成侧若把 shape 硬编码进 launch 配置，编译能过、小 shape 能跑，但在评测的变 shape 用例上直接触发越界或静默错误结果——这正是“编译通过≠语义正确”的典型失效面。

“编译”这一步的考点是工具链契约：输入是源码加编译选项（arch、优化级别、是否启用 fast math），输出是可加载模块；失败模式包括语法/类型错误、不支持的 intrinsic、寄存器或共享内存超限、以及 arch 不匹配导致的加载期失败。这里的系统代价是编译时间与缓存命中率——批量评测时若每个候选都触发完整 nvcc 编译，编译时间会压过运行时间成为瓶颈，因此工程上必须以编译缓存与最小可复现编译单元来控制。需要指出的是，编译失败留下的诊断信息质量直接决定 $$p_1$$ 的回溯效率：报错若只给行号不给约束冲突原因，多轮 RL 的奖励信号就会退化为“能否编译”的二值信号，丢掉性能维度。

“运行”与“评测”两步的边界在于正确性 oracle 的严格度与计时口径。运行步的输入是可加载模块加测试张量，输出是数值结果与耗时；失败模式有越界写、未初始化读、竞态（缺 sync）、以及非确定性归约顺序导致的容差漂移。评测步则把结果折算成相对基线的加速比或相对 SOL 的占比，其失效条件是基线本身未被公平测量（例如基线未做 warmup、未固定 clock），此时加速比失去意义。代价上，运行步的显存占用决定能否在单卡上并发多候选，评测步的重复次数决定时延估计的方差；一个具体判断是：若正确性检查用固定容差而 kernel 采用不同累加顺序，则“正确”的判定会随输入规模漂移，必须在评测契约里显式写明容差与 shape 覆盖集，否则整条链路的结论不可信。
