一 · 把题干拆成可判定的子问题

「预算感知由粗到细搜索」这个名字里藏着三个必须分别落地的约束：预算（一个显式的资源上限，通常是候选 kernel 的编译+评测次数、wall-clock 或 token 数）、由粗到细（搜索空间在每一层被重新参数化，粒度递减）、搜索（存在一个可被调用的评分函数，且评分本身有代价）。读题的第一步不是想算法，而是把这三者写成一份可判定的规格：预算记作 B，第 l 层的候选数记作 n_l，单次评估代价记作 c_l，则可行性约束是

$$\sum_{l=1}^{L} n_l \, c_l \;\le\; B,\qquad n_1 \gg n_2 \gg \cdots \gg n_L .$$

这个不等式就是考点的骨架。它同时约束了两件事：粗层必须便宜（c_1 小）才能容纳大 n_1；细层必须少（n_L 小）才能承受昂贵的 c_L。任何一份答案如果只写了「先粗后细」而没有把 c_l 与 n_l 的乘积摆出来，就没有回答题干。

拆题干的动作可以固定为四问：被搜索的对象是什么（是 Triton 的 BLOCK_SIZE/num_warps 这类离散旋钮，还是 CUDA C++ 的 tile 形状与流水深度，还是 CuTe 的 layout 组合）、粗层用什么代理信号（编译是否通过、静态资源占用、单次小规模正确性）、细层用什么真信号（端到端时延、NCU 采集的带宽/占用率、SASS 指令计数）、预算耗尽时如何截断（返回当前最优还是报未收敛）。这四问的答案决定了后面所有步骤的输入输出类型。

代价必须先算清：以一次 Triton kernel 的候选评估为例，编译一次要付出秒级的编译时间（JIT 缓存未命中时尤其明显），跑一次正确性要付出毫秒级，跑一次 NCU profile 则要付出数量级更高的时延并产生可观的 trace 体积。粗层若用「编译通过 + 小规模数值比对」作代理，c_1 主要被编译时间支配；细层若用 NCU，c_L 被 profile 的采样开销支配。这个量级差正是「由粗到细」的经济学依据，也是考点之一：考生要能说出为什么不能在所有候选上直接跑 NCU。

二 · 考点识别：四个必答项与两个陷阱

这类题目的评分点通常落在四处。第一，分层定义：每一层的搜索空间如何从上一层收缩出来，是枚举、剪枝还是局部扰动。第二，代理信号的可信度：粗层信号与细层信号的相关性，若相关性弱，粗层会把好候选误杀，此时需要保留一个「幸存者池」而不是只留 top-1。第三，预算记账：每一步消耗多少预算、剩余预算如何驱动下一层的 n_l。第四，终止条件：预算耗尽、连续若干层无改进、或达到目标 SOL 比例。

两个陷阱值得单独指出。陷阱一，把「由粗到细」误解为「先跑一遍全部候选再挑最好的精调」，这退化成单层搜索，预算不等式右端会被 n_1 c_L 撑爆。陷阱二，把粗层做成纯静态分析（只看寄存器数和 shared memory 用量），而忽略静态指标与真实时延之间的非单调关系——占用率高不等于快，寄存器压力小可能换来更多溢出到 local memory 的访存。正确做法是让粗层至少包含一次真实执行，哪怕规模缩小。

与考点对应的公式除了上面的预算不等式，还有一条分层收缩的配额公式。设第 l 层结束时剩余预算为 B_l，下一层候选数为 n_{l+1}，则

$$n_{l+1} \;=\; \left\lfloor \frac{\alpha \, B_l}{c_{l+1}} \right\rfloor,\qquad 0<\alpha<1,$$

其中 \alpha 是留给后续层与最终验证的预算保留比例。这个式子的工程含义是：n_{l+1} 不是拍脑袋定的，而是由「还剩多少钱」和「下一层一次评估多贵」共同决定。答题时给出 \alpha 的取值理由（例如必须留出至少一次完整正确性验证与一次端到端基准的预算），比给出一个具体数字更重要。

具体例子：一个融合的 elementwise+reduction kernel，粗层枚举 BLOCK_SIZE ∈ {128,256,512,1024} 与 num_warps ∈ {2,4,8} 共 12 个候选，每个只做编译与小规模数值比对；细层对粗层幸存的前 3 个做 NCU profile 与端到端计时。若粗层单次代价约 1 秒、细层单次约 30 秒，则粗层 12 秒、细层 90 秒，总量级差近一个数量级，这就是分层带来的节省。

三 · 解题路径：五步流动与每步的输入输出

把一次 kernel 的生成/优化/验证流动拆成五步，是本题要求的主干。第一步规格化：输入是自然语言或参考实现（PyTorch 版本、形状、dtype、容差），输出是一份机器可读的约束集——形状、dtype、允许的误差界、目标硬件、预算 B。代价主要是 token 与人工校对，错误在这里会放大到后面所有层。

第二步粗层生成与筛选：输入是约束集与一个参数化模板（Triton 的 autotune 空间或 CUDA 的 tile 参数网格），输出是幸存候选列表及其代理分数。这一步的机制是「模板 + 枚举 + 廉价评估」，评估器只做编译、资源占用检查和小规模正确性。代价是编译时间乘以候选数，显存开销可忽略。

第三步细层优化：输入是幸存列表，输出是每个候选的真实性能画像（时延、带宽利用率、占用率、SASS 关键指令）。机制是对每个候选做一次 NCU 采集并据此做局部扰动（例如发现 shared memory bank conflict 就改 padding，发现 occupancy 受限就调 num_warps）。代价是 profile 的时延与 trace 体积，这是全流程最贵的一步，因此 n_3 必须小。

第四步正确性裁决：输入是细层选出的最优候选，输出是通过/不通过以及误差分布。机制是用一个独立于搜索过程的 oracle——参考实现逐元素比对、边界形状（非对齐、极小、极大）覆盖、以及必要的确定性检查（例如 atomic 累加的顺序不确定性是否在容差内）。代价是一次完整规模的执行与比对，显存要容纳参考输出。

第五步预算结算与回退：输入是剩余预算与当前最优，输出是最终交付物或「未达预算内的最优」标记。机制是检查是否还有预算做一次端到端基准，若没有则明确标注结果的可信度等级。代价接近于零，但它决定了交付物是否可被下游信任。

五步的输入输出类型必须自洽：第二步的输出若是「候选源码 + 代理分数」，第三步就必须能直接消费源码而不重新生成，否则生成成本会被重复计入预算。这一点在答题时容易被忽略，却是工程上最常见的预算泄漏来源。

四 · 需要调用的公式：代理相关性、加速比与 roofline 判据

粗层能不能信，取决于代理分数与真实时延的相关性。设粗层分数为 s、细层真实时延为 t，用 Spearman 秩相关 \rho 度量排序一致性。若 \rho 低，则粗层应保留 k 个幸存者而非 1 个，k 由预算反推：

$$k \;=\; \min\!\left(n_l,\ \left\lfloor \frac{B_l}{c_{l+1}} \right\rfloor\right).$$

这条式子把「相关性不足」翻译成「多留几个」，是考点从定性走向定量的接口。答题时若能指出 \rho 需要在历史任务上离线标定、且不同 kernel 类别（访存密集型 vs 计算密集型）的 \rho 不同，就体现了对代理信号局限性的理解。

细层的判据应落在 roofline 上，而不是绝对时延。对给定 kernel，算其算术强度 I（FLOP/Byte），与目标硬件的峰值算力 P 和峰值带宽 W 比较，得到可达性能上界

$$\text{SOL} \;=\; \min\!\left(P,\ I \cdot W\right).$$

细层报告的是实测时延对应的性能占 SOL 的比例，而不是「比 PyTorch 快多少倍」。原因是加速比会被参考实现的低效放大，而 SOL 比例直接指向还剩多少优化空间。代价是 SOL 需要准确的 I 计算与硬件峰值参数，算错会把优化方向带偏。

还有一个必须调用的量是端到端收益。单 kernel 的加速比 t_{\text{base}}/t_{\text{opt}} 不等于生产收益，因为 kernel 在总时延中的占比 f 决定了 Amdahl 上界：

$$\text{speedup}_{\text{e2e}} \;=\; \frac{1}{(1-f) + f/\text{speedup}_{\text{kernel}}}.$$

这一步的工程判断是：若 f 很小，即使 kernel 快数倍，端到端收益也有限，此时预算应优先给别的 kernel 而不是在这个 kernel 的细层上继续加码。这条公式是「预算感知」在跨 kernel 层面的延伸，也是答题时区分「会调 kernel」与「会做系统」的分水岭。

具体例子：一个 reduction kernel 的算术强度很低，SOL 由带宽项 I \cdot W 支配，那么细层的优化方向应是减少访存次数与提高合并访问，而不是增加 ILP 或展开循环；反之若 I 高到算力项 P 成为瓶颈，才值得投入寄存器与指令级优化。这个判断在粗层就可以用静态的 I 估算做出，从而把细层预算集中到真正有空间的候选上。

五 · 正确性代价与预算记账的耦合

正确性不是免费的最后一道闸。它的代价包括：参考实现的显存占用（要同时驻留输入、参考输出、候选输出）、比对本身的时延、以及为覆盖边界形状而增加的多次执行。若把正确性验证放在细层之后只做一次，风险是细层基于一个数值错误的候选做了大量 profile，预算被浪费在错误分支上。因此更稳的流动是在粗层就做小规模正确性，在细层前做中等规模正确性，最后做全规模正确性，形成三道闸，每道的代价递增而候选数递减。

记账表应显式列出每一步的预算消耗。以候选数乘以单次代价的形式记录，并在每步结束时更新剩余预算。工程上常见的错误是把生成阶段的 token 成本漏记，导致「预算感知」只感知了评测成本而没感知生成成本；对于 LLM 生成 kernel 的场景，生成本身就是预算的大头，必须在第一步就把生成预算与评测预算分开列账。

一个具体的耦合例子：某候选在中等规模正确性上因非对齐形状出现越界读，若这道闸被跳过，细层的 NCU 会显示漂亮的带宽数字，最终全规模验证才暴露错误，此时预算已耗尽且没有时间回退。三道闸的设计正是用递增的正确性代价换取「不把预算花在错误分支上」的保险。

需要强调的是，正确性 oracle 的可信度本身也要被预算约束：形式验证或差分测试的代价可能高于性能评测，因此它通常只作用于最终候选而非全部候选。答题时应说明哪一道闸用轻量 oracle（逐元素比对）、哪一道用重量 oracle（形式化或大规模随机差分），以及这个选择如何由 B 与 c_l 决定。

六 · 解题路径的落点：把五步写成可执行规格

把上面的分析收束成一份可执行规格，是本题的交付形态。规格应包含：分层参数表（每层的 n_l、c_l、代理信号、真信号）、预算不等式与配额公式的实例化、三道正确性闸的位置与 oracle 类型、以及终止条件的判定逻辑。这份规格的价值在于它可被直接翻译成调度代码：一个外层循环按层推进，内层按 n_l 枚举，每次评估前检查剩余预算是否足够，不足则截断并标记。

伪代码层面的关键判断是「预算检查放在评估前还是评估后」。放在评估前可以保证不超支，但会浪费最后一次评估的机会；放在评估后则可能超支一次昂贵评估。工程上通常采用「预估代价 + 硬上限」的双重检查：若剩余预算小于预估代价的某个比例就停止，避免用尽预算做一次无法消化的 profile。

最后落到一个具体机制上：细层的局部扰动应以上一层留下的参数为中心做邻域搜索，而不是重新全局枚举。邻域大小由剩余预算与单次扰动代价决定，这使「由粗到细」在参数空间上也是真的收缩，而不只是候选数量的减少。若邻域搜索连续若干次无改进，则提前退出并把预算让给下一层或下一个 kernel——这正是预算感知与普通网格搜索的分界点。

读题即预算分配：题干拆解的三类考点与失效边界

「预算感知由粗到细搜索」的题干本身就是一个约束满足问题：给定总预算 B（以 token、编译-执行轮次或 wall-clock 计），要在生成、优化、验证三段流动上分配 b_gen、b_opt、b_val，使端到端收益最大。读题时要拆出三类考点：其一是预算的度量口径——预算记在 token 上还是记在 GPU 秒上，直接决定粗搜阶段能否用大 batch 并行采样；其二是粗细粒度的切换判据——何时从「宽而浅」的候选筛选转入「窄而深」的单点优化；其三是验证的召回率——粗搜阶段用廉价 oracle（形状检查、小规模随机输入）过滤，漏掉的真解无法在后续阶段被找回。解题路径应写成：先定预算口径与分段比例，再定切换判据，最后定每段的验证强度，而不是先想算法。

切换判据可用一个边际收益比较式表达：只有当深挖单个候选的期望增量 ΔU_deep 超过继续拓宽候选集的期望增量 ΔU_wide 时才切换，即

$$\frac{\Delta U_{\text{deep}}}{b_{\text{opt}}} > \frac{\Delta U_{\text{wide}}}{b_{\text{gen}}},\quad \text{且}\quad b_{\text{gen}}+b_{\text{opt}}+b_{\text{val}}\le B$$

这里的代价是实打实的：粗搜阶段每个候选都要付一次编译时延（Triton 的 JIT 与 CuTe 的模板实例化在候选数线性增长时会把编译时间推到分钟级），而深挖阶段的 NCU profile 采集本身占用 GPU 时间、与训练/推理负载争抢 SM。失效条件很明确：当验证 oracle 的假阴性率高到粗搜筛掉的候选里含有最优解时，整个由粗到细的链条退化为随机深挖；当 B 小到不足以覆盖一次编译加一次 profile 时，任何分段都无意义，应直接退化为单候选贪心。
