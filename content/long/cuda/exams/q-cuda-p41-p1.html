一 · 把题干还原成一条可执行流水线

《KernelArc》这类多 agent 框架的题干，表面问的是“pipeline 有哪几步”，真正的考点是能否把一句自然语言需求还原成一条带输入契约、输出契约与失败模式的流水线。题干里“从输入到评测”这五个字已经限定了边界：起点是任务描述（算子语义、形状、dtype、目标硬件），终点是评测结论（正确性判定 + 性能判定），中间不允许插入“训练”“调参”这类与单次生成无关的环节。答题时若把 agent 的角色分工当成流水线步骤来写，就已经偏题——角色是横切的，步骤是纵切的。

正确的拆法是按状态转移切分：每一步的产物必须是下一步的合法输入，且每一步都必须能独立失败。据此可切出五段：读题与规格化、kernel 生成、编译、运行与正确性校验、评测与反馈。这五段构成一次闭环；多轮优化只是把这个闭环重复，不改变单轮内的段数。判卷时看的是你有没有为每一段写出“输入是什么形态、输出是什么形态、失败时下游看到什么”。

$$\text{Pipeline} = S_0 \xrightarrow{f_1} S_1 \xrightarrow{f_2} S_2 \xrightarrow{f_3} S_3 \xrightarrow{f_4} S_4 \xrightarrow{f_5} S_5$$

其中 $S_0$ 是原始题面，$S_5$ 是评测报告。关键约束是每个 $f_i$ 都可能不产生 $S_i$ 而转入失败分支，因此流水线不是链而是带旁路的图。这一点决定了答题时必须写失败模式，只写“生成→编译→运行”的线性叙述拿不到分。

二 · 读题与规格化：把自然语言压成可判定的契约

第一段的输入是题面文本，输出是一份规格对象：算子语义（逐元素、归约、矩阵乘、卷积等）、张量形状与 dtype、内存布局假设、目标 GPU 架构、精度容差、以及是否允许使用特定指令（如 tensor core、异步拷贝）。这一段的核心机制是歧义消解：题面里“实现一个 softmax”并不指定沿哪一维、是否数值稳定、是否融合，agent 必须把这些补成显式约束，否则后续正确性 oracle 无法构造。

失败模式有三类：语义缺失（题面没给形状，规格对象里形状字段为空）、约束冲突（要求 fp16 输入但容差按 fp32 给）、以及不可判定（题面描述的算子没有公认参考实现，oracle 无从建立）。第三类最致命，因为它会让后面的正确性校验退化成“跑通即正确”，这是评测可信度的直接漏洞。

代价体现在 token 与时延上：规格化阶段若让 agent 反复追问澄清，每轮都是一次完整的前向，token 消耗随澄清轮数线性增长；若改为一次性抽取，则漏抽字段的概率上升，下游编译阶段会以“shape mismatch”的形式把代价推迟暴露。工程判断是：把形状与 dtype 做成结构化字段而非自由文本，让下游用断言而非自然语言理解来消费。

  • 输入：题面文本 + 目标硬件描述。
  • 输出：规格对象（语义、shape、dtype、容差、允许指令集）。
  • 失败：字段缺失、约束冲突、无参考实现。

三 · kernel 生成：从规格到源码，考点在“可编译性”而非“性能”

第二段输入是规格对象，输出是一段 CUDA C++ / Triton / CuTe 源码（含 launch 配置）。这一段最容易被误答成“让 agent 写一个快的 kernel”——但单轮 pipeline 里生成阶段的目标函数是可编译且语义等价，性能是评测阶段才引入的信号。把性能目标提前到生成阶段，会让 agent 在还没有执行反馈时就做启发式猜测，反而抬高编译失败率。

机制上，生成需要三样东西同时到位：kernel 函数体、host 侧 launch 参数（grid/block、共享内存大小）、以及绑定到规格对象的参数校验。伪代码思路可写成：

$$\text{gen}: (spec) \mapsto (src,\; launch,\; asserts),\quad \text{s.t. } \text{asserts} \subseteq \text{spec}$$

失败模式按发生位置分：语法/类型错误（编译期暴露）、launch 配置越界（如 block 超过架构上限，运行期暴露）、以及语义漂移——源码能编译能跑，但归约维度或边界处理与规格不符，这类只有正确性校验能抓。第三类是评测可信度的主要威胁，因为它在“跑通”这一层是隐形的。

具体例子：规格要求对 shape 为 (B, N) 的张量沿 N 维做数值稳定 softmax，生成阶段若只写了减去行最大值的版本却漏了 N 非 2 的幂时的尾块处理，编译与运行都成功，但边界行的结果偏离参考实现——这正是需要 oracle 而非“能跑”来判定的情形。代价上，生成阶段的编译时间与源码长度正相关，长源码（模板展开、多分支）会显著拉长编译，而编译失败会直接吞掉本轮的全部 token 投入。

四 · 编译与运行：两类失败必须分开记账

第三段输入是源码与 launch 配置，输出是可加载的二进制（cubin/fatbin）或 Triton 的编译产物；第四段输入是二进制与输入张量，输出是输出张量与运行状态。把这两段合并叙述是常见失分点，因为它们的失败模式性质完全不同：编译失败是静态可判的，运行失败是动态依赖输入的。

编译段的失败模式包括：nvcc/ptxas 报错、寄存器溢出导致 occupancy 崩塌（编译成功但性能劣化）、以及编译超时——模板重度展开时编译时间可能远超运行时间，这在多轮优化里是实打实的预算消耗。运行段的失败模式包括：非法内存访问、launch 失败（grid 维度为 0 或超限）、以及静默数值错误（NaN/Inf 传播、竞态导致的不确定结果）。

这里必须给出一个可判定的判据，而不是“看是否报错”。对确定性要求，可用两次相同输入运行的结果比对：

$$\text{det-ok} \iff \forall i,\; y^{(1)}_i = y^{(2)}_i \;\text{bitwise}$$

不满足则说明存在竞态或未初始化读取，此时即便数值“看起来对”，正确性判定也应降级。代价上，运行段的时间由输入规模决定，而正确性校验若要覆盖边界形状（非对齐、非 2 的幂、极小 batch），就要多次 launch，时延随用例数线性增长；这是评测可信度与预算之间的直接权衡。

五 · 评测：正确性 oracle 与性能信号必须解耦

第五段输入是输出张量、参考实现结果与运行期 profile 数据，输出是评测报告：正确性通过/失败、性能指标（时延、带宽利用率、SOL 占比）、以及可供下一轮使用的反馈。考点的核心是把正确性与性能分成两个独立判据，而不是合成一个分数。合成分数会让“快但错”的 kernel 获得正反馈，这是可验证奖励设计里最危险的漏洞。

正确性侧需要一个 oracle：可以是框架自带参考实现（PyTorch eager）、也可以是高精度 CPU 实现。判据写成容差形式：

$$\text{pass} \iff \max_i \frac{|y_i - \hat{y}_i|}{\max(\epsilon, |\hat{y}_i|)} \le \tau_{\text{dtype}}$$

其中 $\tau$ 随 dtype 变化（fp32 与 fp16 不同），这个细节是考点：用统一容差会让低精度 kernel 被误判为错，或让高精度 kernel 的细微错误被放过。性能侧则依赖 profile（NCU/SASS）给出带宽、occupancy、指令吞吐，并与 roofline 上界比较得出 SOL。失败模式是测量污染：未做 warmup、未固定时钟、未排除首次 launch 的初始化开销，都会让性能信号失真，进而误导下一轮优化方向。

段输入输出典型失败代价维度
规格化题面文本规格对象字段缺失/无 oracletoken、澄清轮数
生成规格对象源码+launch语义漂移编译时间、源码长度
编译源码二进制报错/寄存器溢出编译时延
运行二进制+输入输出张量越界/竞态/NaNlaunch 次数、显存
评测输出+profile报告+反馈测量污染/容差误设用例数、profile 开销

六 · 解题路径：先画失败图，再填公式

落到答题动作上，路径应是：第一步写出五段的状态名与转移条件；第二步为每段标注“下游能看到什么”——这是失败模式的具体化，例如编译失败时下游拿到的是编译器 stderr 而非二进制，运行越界时下游拿到的是 CUDA error code 而非张量；第三步才填公式，且公式必须绑定到具体判据（容差、确定性、SOL），而不是泛泛写“计算误差”。

需要调用的公式清单在此收束：规格化的字段完备性可写成断言集合包含关系；生成段的目标函数是“可编译 ∧ 语义等价”；编译段关注寄存器压力与 occupancy 的关系；运行段的确定性判据是逐位相等；评测段是相对容差判据与 roofline 上界比。每条公式都对应一个可观测的量，缺了可观测量，公式就只是装饰。

工程判断上，最需要强调的是失败模式的可归因性：多 agent 框架的价值不在于把五段串起来，而在于每一段失败时能把责任定位到具体段，从而让下一轮的修改有方向。若评测段把编译失败与数值错误混成一个“未通过”，反馈信号就退化成二值，多轮优化的信息增益随之消失。这也是为什么本部分只拆题不给答案——答案的价值取决于你是否先把这条带旁路的流水线和它的代价账本画对。

拆题之后：KernelArc 读题阶段的边界、失效条件与系统代价

KernelArc 的读题不是把题干转成一段自然语言摘要，而是把题目拆成三张互相约束的清单：算子语义清单（输入输出张量形状、dtype、layout、是否 in-place、边界条件）、考点清单（访存模式、归约维度、并行粒度、数值精度要求、是否要求确定性）、可执行路径清单（用 CUDA C++ 直接写、用 Triton 写 block 级程序、用 CuTe 拼 layout 与 tiled copy、还是手写 PTX 片段）。这三张清单必须同时产出，因为考点决定路径，路径反过来约束考点能否被验证。读题模块的输出是一份结构化 spec：字段化的语义约束、按优先级排序的考点、以及每条路径对应的预期失败模式。它的下游是生成模块，生成模块只消费 spec，不消费原始题干，这样题干里的歧义在读题阶段被一次性消解，而不是在编译失败后反复回溯。代价在这里已经出现：读题阶段每多拆一个考点，生成阶段就要多产出一份候选，编译与运行次数线性增长；如果读题阶段把考点拆得过细（例如把一次归约拆成访存对齐、warp 内 shuffle、跨 warp 共享内存三段），候选数量会膨胀到评测预算无法承受，因此读题必须给出考点优先级，让生成模块只对高优先级考点做多路径尝试。

失效条件集中在三类。第一类是语义歧义未被识别：题干给出“沿最后一维归约”但没有说明是否允许改变输出 dtype，读题若默认沿用输入 dtype，生成出的 kernel 在正确性 oracle 上会因精度截断而失败，而失败信号会被误判为 kernel 逻辑错误，导致多轮 RL 把错误的负奖励分配给正确的实现。第二类是考点误判：把一道以访存带宽为瓶颈的 elementwise 题判成计算密集型，于是生成模块去优化指令级并行而忽略合并访存，profile 显示 SM 利用率高但 DRAM 吞吐低，读题阶段的错误直接传导为优化方向的错误。第三类是路径越界：题干要求的数值行为（例如严格 IEEE 舍入）在 Triton 的默认语义下不可控，读题若仍把 Triton 列为首选路径，后续所有候选都会在正确性 oracle 上系统性失败。这三类失效的共同代价是 token 与编译时间：一次误判会让生成模块产出若干份注定失败的候选，每份候选都要经过编译、运行、profile 三轮反馈，而读题阶段本身只消耗一次前向。用比值刻画这个代价，设读题阶段产出 k 个考点、生成阶段每个考点产出 m 份候选、单份候选的编译加运行加 profile 成本为 c，则读题误判带来的额外系统成本近似为

$$C_{\text{miss}} \approx k_{\text{wrong}} \cdot m \cdot c + T_{\text{retry}}$$

其中 Tretry 是多轮重试额外消耗的 token。这个式子的工程含义是：读题阶段的错误不是加性的，而是乘性的，它把下游每一份候选的成本都放大一遍。因此 KernelArc 在读题阶段设置了硬边界：任何无法被正确性 oracle 形式化表达的语义约束，必须在 spec 里标记为“不可验证”，而不是让生成模块去猜。标记为不可验证的考点不进入候选生成，直接降低 k，用覆盖率换预算。

系统代价还体现在读题与评测之间的耦合上。读题阶段给出的考点清单同时是评测阶段的检查项来源：每个考点对应一个正确性断言或一个性能阈值。如果读题把某个考点写成“尽量合并访存”这种不可判定的表述，评测阶段就无法为它生成断言，只能退化为整体正确性检查加整体 roofline 对比，于是该考点的失败无法被定位到具体候选，多轮 RL 的奖励信号变成粗粒度的通过或不通过。具体例子：一道“转置加 softmax”的题，读题若只写“实现转置与 softmax”，评测只能检查最终输出是否接近参考；若读题拆成“转置后的 stride 是否导致 bank conflict”“softmax 的 max 归约是否跨 block”“exp 是否在 fp32 下计算”，评测就能为每条分别给出断言，失败候选的反馈里带上具体是哪一条不满足，下一轮生成可以直接针对该条修改。前者的代价是每轮反馈只告诉模型“错了”，后者的代价是读题阶段多花一次结构化输出，但把多轮重试的 Tretry 压下来。KernelArc 选择后者，因为编译与 profile 的机器时间远比读题阶段的一次前向昂贵，而错误的负奖励对 RL 的污染是不可逆的。

读题产物下游消费者缺失时的失效代价形态
语义约束字段正确性 oracle断言无法生成，只能整体比对反馈粒度粗，重试 token 上升
考点优先级候选生成候选数量膨胀或方向错误编译与运行次数乘性增长
路径可行性标记生成模块系统性不可满足的候选整批候选在 oracle 上失败
