一 · 题干拆解：把“SOL-ExecBench”拆成四个可判定的子问题

《SOL-ExecBench: Speed-of-Light Benchmarking for Real-World GPU Kernels Against Hardware Limits》这个标题本身就是一道题的题干。拆开看，它同时约束了四件事：SOL（Speed-of-Light，即硬件上限）是评测的参照系而非绝对分数；ExecBench 说明评测对象是“可执行”的 kernel，不是静态代码片段；Real-World GPU Kernels 把任务域限定在真实负载形态（非玩具 shape、非单一算子）；Against Hardware Limits 则要求把实测性能与硬件可达上限做比值，而不是与某个基线实现做比值。题干问的是“pipeline 从输入到评测要经过哪几步，每一步的输入、输出和失败模式”，因此答题时必须按“生成—编译—运行—评测”这条链逐段给出三元组（输入、输出、失败模式），任何一段缺失三元组都算漏答。

考点因此可以枚举为四类：其一，阶段划分的正确性——能否识别出“编译”是一个独立阶段而非运行阶段的子步骤，因为编译失败与运行失败在工程上对应完全不同的修复动作（改源码 vs 改 launch 配置/改 shape）；其二，失败模式的归属——每个失败模式必须落到唯一阶段，例如数值不匹配属于运行后的正确性判定，而寄存器溢出导致的 occupancy 塌陷属于编译产物的静态属性；其三，SOL 参照系的计算——必须给出 roofline 形式的界，而不是笼统说“接近峰值”；其四，评测口径——实测时间与 SOL 时间的比值如何定义、以谁为分子。解题路径是：先画阶段状态机，再为每条边标注失败模式，最后把 SOL 公式代入评测阶段。

代价维度必须显式写出：生成阶段的代价是 token 与采样次数；编译阶段的代价是编译时间（含模板实例化与 PTX→SASS 的 cubin 生成）；运行阶段的代价是显存占用与 launch 时延；评测阶段的代价是重复测量带来的墙钟时间与 profiling 开销。一个具体例子：若题干给出“某 kernel 实测 0.42 ms、SOL 时间 0.30 ms”，则比值 1.4，考点在于判断这 0.12 ms 的差是落在带宽受限段还是延迟受限段——这决定了后续优化该动 memory access 还是动 occupancy，而不是笼统地“再调调 tile”。

二 · 生成阶段：输入是任务规约，输出是候选源码，失败模式是“可编译但语义错”

生成阶段的输入不是一句自然语言，而是任务规约：算子语义描述、输入/输出张量的 dtype 与 shape 约束、允许使用的语言层（CUDA C++ / Triton / CuTe / PTX）、以及参考实现的接口签名。输出是候选 kernel 源码，通常附带 launch 配置（grid/block、shared memory 大小）与 host 侧胶水代码。这一阶段的关键机制是约束采样：把 shape 约束与接口签名作为硬约束注入解码过程，避免生成出签名不匹配的代码——签名不匹配会在编译阶段以链接错误暴露，属于可廉价过滤的失败，不值得消耗运行阶段的 GPU 时间。

失败模式有三类，且必须区分：语法/接口失败（编译期即可捕获，代价最低）；可编译但语义错（例如漏掉边界谓词、归约初值错误、stride 方向写反），这类失败只能靠运行阶段的正确性 oracle 捕获，代价是一次完整的编译加运行；可编译、语义对但性能塌陷（例如把本可向量化的访存写成标量循环），这类失败不触发任何正确性告警，只能靠评测阶段的 SOL 比值暴露。第二类和第三类的区分是本题的核心考点之一：很多答题者会把“性能差”误归为生成阶段的失败，实际上生成阶段只对“是否满足规约”负责，性能归属评测阶段。

伪代码思路如下：对每个任务规约 spec，采样 k 个候选，先做静态过滤（签名匹配、禁用 API 检查），通过的进入编译队列。代价上，生成阶段消耗的是 token 与采样次数；k 越大，进入编译队列的候选越多，编译时间线性上升，而编译是整个 pipeline 中最容易被低估的墙钟开销——模板重的 CUDA C++ 候选单次编译可达数十秒量级，Triton 候选则显著更短，这个差异直接影响“每 token 的有效产出率”。具体例子：同一归约任务，生成 8 个候选，其中 3 个签名不匹配被静态过滤，5 个进入编译，最终只有 2 个通过正确性 oracle——这条漏斗的比例就是生成阶段的质量指标，而不是用“生成成功率”这种含糊说法。

三 · 编译阶段：输入是源码加 launch 配置，输出是 cubin 与静态资源画像

编译阶段的输入是候选源码、编译选项（arch、优化级别、是否开启 fast math）与 launch 配置。输出有两部分：可加载的 cubin/PTX，以及静态资源画像——每线程寄存器数、shared memory 静态占用、是否发生 spill、以及由这些量推出的理论 occupancy。这个画像之所以是编译阶段的输出而非运行阶段的输出，是因为它由编译器在生成 SASS 时确定，运行阶段只能观测到它的后果（实际 occupancy、实际带宽），不能直接读出寄存器分配决策。

失败模式按严重度排列：编译错误（语法、类型、未定义符号、模板实例化失败），直接丢弃候选；资源超限（shared memory 超过每 SM 上限、寄存器需求导致 occupancy 降到不可接受水平），这类候选能编译通过但注定跑不出好成绩，属于“编译成功、评测必败”的预判失败；架构不匹配（使用了目标 arch 不支持的指令，例如某些 warp-level 原语或特定精度的 MMA），在加载或首次 launch 时暴露。第三类失败的归属容易答错：它发生在编译产物与硬件之间，工程上应归入编译阶段的产物校验，而不是运行阶段的数值错误。

代价维度是编译时间与编译产物的确定性。编译时间随模板深度与候选数量增长；更隐蔽的代价是编译结果的不确定性——同一源码在不同编译选项下寄存器分配不同，进而 occupancy 不同，最终 SOL 比值不同。因此评测阶段必须固定编译选项，否则跨候选的比较不成立。公式上，occupancy 的上界可由资源约束给出：

$$\text{occupancy} \le \min\left(\frac{R_{\text{reg/file}}}{R_{\text{reg/thread}}\cdot T_{\text{thread}}},\ \frac{S_{\text{smem}}}{S_{\text{smem/block}}\cdot B_{\text{block}}},\ \frac{W_{\text{max}}}{T_{\text{thread}}}\right)$$

其中三项分别对应寄存器文件、shared memory 与 warp 槽位约束，取最小值即为该 kernel 在该 arch 上的理论 occupancy 上限。具体例子：某候选每线程用 64 个寄存器、block 为 256 线程，则单 block 占用 16384 个寄存器；若寄存器文件容量对应 65536 个寄存器，则寄存器维度允许 4 个 block 并发——这个数就是编译阶段应当输出的画像，评测阶段拿它解释实测带宽为何达不到 SOL。

四 · 运行阶段：输入是 cubin 加实参，输出是数值结果与计时样本，失败模式是“错”与“崩”

运行阶段的输入是编译产物、实参（张量指针、shape、stride）、launch 配置与正确性 oracle 的参照输出。输出是两份互不替代的东西：数值结果（供 oracle 比对）与计时样本（供评测阶段折算）。机制上，计时必须与正确性校验分离：先跑一次正确性比对，通过后再进入计时循环，否则错误候选会污染计时统计。计时循环需要 warmup 以排除首次 launch 的上下文建立与 cache 冷启动，并对多次采样取稳健统计量（中位数或截尾均值），因为 GPU 计时分布存在长尾。

失败模式分四类：launch 失败（grid/block 超限、shared memory 动态申请超限、参数数量不匹配），发生在 kernel 真正执行之前；执行崩溃（非法访存、越界写、未对齐访问），表现为 CUDA error 而非数值错误，必须与数值不匹配严格区分，因为前者是内存安全问题、后者是逻辑问题；数值不匹配（超出容差的元素级差异），由 oracle 判定，容差需按 dtype 与归约规模设定，浮点归约的顺序差异会放大误差；超时/挂起（死锁、无界循环），需要外部 watchdog 而非依赖 kernel 自行退出。

代价维度是显存占用与 launch 时延。显存占用由输入输出张量加 workspace 决定，workspace 大小常被生成阶段忽略而在运行阶段暴露为 OOM；launch 时延在极小 shape 上会主导总时间，此时 SOL 比值天然偏离 1，评测阶段必须识别这一区段而非误判为 kernel 质量差。具体例子：一个 shape 极小的逐元素 kernel，实测 8 微秒，其中 launch 开销占 5 微秒，此时即便 kernel 本体已达 SOL，比值仍显著大于 1——正确做法是在评测阶段标注“launch-bound 区段”，而不是把这个候选判为低质。

五 · 评测阶段：输入是计时样本加静态画像，输出是 SOL 比值与归因，失败模式是“口径错”

评测阶段的输入是运行阶段产出的计时样本、编译阶段的静态资源画像、以及该任务在目标硬件上的 SOL 参照值。输出是SOL 比值及其归因：比值偏离 1 时，必须指出偏离来自带宽受限、延迟受限、occupancy 受限还是 launch 开销受限。机制上，SOL 参照值由 roofline 给出，取两个界中的较小者：

$$T_{\text{SOL}} = \max\left(\frac{\text{FLOPs}}{P_{\text{peak}}},\ \frac{\text{Bytes}}{B_{\text{peak}}}\right),\qquad \text{ratio} = \frac{T_{\text{measured}}}{T_{\text{SOL}}}$$

其中 Bytes 按该任务的最小必要访存量计（而非实际访存量），P_peak 与 B_peak 是目标硬件的峰值算力与峰值带宽。比值的分子是实测时间，因此比值越接近 1 越好，小于 1 意味着实测优于朴素 roofline 界，通常提示访存被 cache 复用或计算被特殊指令加速，需要复核 Bytes 的计法是否漏算了复用。

失败模式集中在口径：SOL 界取错（该任务实为带宽受限却用了算力界，导致比值虚高）；Bytes 计法错（把中间结果写回计入必要访存，或漏算归约的多趟读写）；计时口径错（未排除 launch 开销、未做 warmup、用均值而非稳健统计量）；跨候选不可比（编译选项或测量环境不一致）。这些失败不会让任何一次运行报错，却会让整份评测结论失效，因此是评测阶段最需要防守的部分。

代价维度是评测本身的墙钟时间与 profiling 开销：逐候选做多轮采样加 NCU 采集，时间随候选数线性增长；NCU 采集会串行化执行、放大单次测量时间，因此通常只在归因阶段对少量候选开启，而非对全量候选开启。具体例子：某候选比值 1.6，静态画像显示 occupancy 已达上限、实测带宽接近峰值，则归因应为“带宽受限且已接近 SOL，剩余差距来自必要访存之外的额外流量”，修复方向是减少冗余读写而非提高并行度——这就是评测阶段应当输出的工程判断，而不是一个孤立的分数。

六 · 把四段串成状态机：每条边的失败模式决定下一步动作

把四个阶段写成状态机后，题干要求的“每一步的输入、输出和失败模式”就变成一张可核对的表。关键在于每条边上的失败模式对应不同的修复动作，而不是笼统地“重试”。

阶段输入输出主要失败模式对应动作
生成任务规约、语言层约束候选源码 + launch 配置签名不匹配；语义错；性能塌陷静态过滤；进入运行校验；留给评测归因
编译源码、编译选项、launch 配置cubin/PTX + 静态资源画像编译错误；资源超限；架构不匹配丢弃；预判淘汰；产物校验
运行cubin、实参、oracle 参照数值结果 + 计时样本launch 失败；崩溃；数值不匹配；挂起改配置；查内存安全；查逻辑；watchdog
评测计时样本、静态画像、SOL 参照SOL 比值 + 归因界取错；Bytes 计错；计时口径错；不可比复核 roofline；复核访存计法；固定测量协议

这张表的信息量在于“失败模式 → 动作”的映射是单向的：编译错误不应触发重新生成以外的动作，数值不匹配不应触发改 launch 配置，性能塌陷不应触发正确性排查。把映射搞反，就是 pipeline 设计中最常见的浪费——用昂贵的 GPU 运行时间去诊断本可在编译期廉价捕获的问题。一个具体例子：某候选在编译阶段寄存器需求导致 occupancy 上限仅为 2 个 block/SM，此时不应进入运行阶段做多轮采样，而应直接依据静态画像判为“预判淘汰”，把 GPU 时间留给 occupancy 达标的候选；这一决策把评测阶段的墙钟开销从“全量候选 × 多轮采样”压到“存活候选 × 多轮采样”，是 pipeline 吞吐的关键杠杆。

最后落在工程判断上：SOL-ExecBench 的评测可信度不取决于单次测量多精确，而取决于四段之间的失败模式归属是否互斥且完备。归属互斥保证一个失败只触发一种修复动作，归属完备保证没有失败会静默穿过 pipeline 进入最终分数。生成阶段用静态过滤压低进入编译的候选数，编译阶段用静态画像压低进入运行的候选数，运行阶段用 oracle 压低进入计时的候选数，评测阶段用固定口径保证跨候选可比——四级漏斗的每一级都在用更廉价的手段淘汰更昂贵的失败，而 SOL 比值只是这条漏斗末端的输出，不是 pipeline 的起点。
