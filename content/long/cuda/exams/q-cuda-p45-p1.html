一 · 题干到底在问什么：三个子问题的边界

这道题表面上是“介绍一篇论文”，实质上是要求答题者把 KernelZero 的问题定位从相邻工作中切出来。题干可拆成四个可判分的成分：(1) 核心工程问题属于哪一类 GPU kernel 工程问题；(2) 基准是什么、口径如何定义；(3) 基线是谁、比较在什么条件下成立；(4) 与相邻工作的分工边界在哪里。四者缺一，答案就会退化成“又一篇 kernel 生成论文”的泛泛描述。

关键考点在于：KernelZero 的标题里出现的是 proposer 与 coder 两个角色，且限定词是 continuously improved。这意味着它处理的不是“单次生成一个正确 kernel”的问题，而是“生成器自身如何随迭代持续变强”的问题——即把 kernel 生成从一次性采样任务，改写成带自举结构的协同演化任务。答题时必须先声明这一层，否则后面谈基准和指标会失去指向。

解题路径建议按“定义问题类→定义基准与口径→定义基线与对照条件→划分工边界”四步推进。每一步都要落到可检验的对象上：问题类要能说出输入输出与失败模式；基准要能说出任务来源、正确性判定与性能度量；基线要能说出它代表的能力上限或下限；分工要能说出相邻工作各自解决了哪一段、留下了哪一段。

需要调用的第一个形式化工具是“任务-评估”二元组。设任务集为 T，评估算子为 E，则一个 kernel 生成系统的可比较性依赖于 (T, E) 的同时固定：

$$\text{Comparability} \iff (T_{\text{fixed}},\ E_{\text{fixed}})\ \text{held invariant across systems}$$

代价在于：固定 T 会牺牲覆盖面，固定 E 会牺牲对新型失败模式的敏感度；若为覆盖更多 kernel 形态而扩大 T，则基线数量与评测时延同步上升，单次全量评测的 GPU 机时成为瓶颈。具体例子：若把 T 从单一算子扩展到含规约、扫描、矩阵乘等多形态，则每个基线都需在同一 T 上重跑，评测成本按 |T| × |Baselines| 增长，这正是答题时必须交代的口径成本。

二 · 基准与指标口径：正确性先于性能

KernelZero 使用的基准属于 KernelBench 系的任务式 kernel 生成评测：给定一个以高层框架写成的参考算子（含其语义），要求系统产出一个可编译、可运行、数值等价的 GPU kernel。口径上必须区分三层：编译通过、正确性通过、性能达标。三层是串联门控，不是并列打分——一个数值错误的快 kernel 不得计入性能统计，否则指标会被“快但错”的样本污染。

正确性 oracle 的定义应写成对参考实现的数值等价判定，通常以相对/绝对误差阈值与特殊值（NaN、Inf、边界形状）覆盖共同构成：

$$\text{pass}(k) = \big[\text{compiles}(k)\big] \wedge \Big[\max_{i}\ \frac{|k(x_i)-r(x_i)|}{\max(|r(x_i)|,\epsilon)} \le \tau\Big] \wedge \big[\text{shape/edge cases OK}\big]$$

性能口径则必须声明基线参照物与计时方式：是相对参考框架实现的加速比，还是相对手写最优 kernel 的 SOL 占比；计时是否含 launch 开销、是否取多次中位数、是否固定输入形状。这些选择直接改变排名。代价体现在：阈值 τ 收紧会提高正确性门槛但压低通过率，使性能样本变少、方差变大；计时含 launch 开销则对小 kernel 不利，会系统性低估细粒度算子的收益。

具体例子：一个融合了 bias 与激活的逐元素 kernel，其算术强度极低，性能上限由显存带宽决定；此时若计时包含 kernel launch 与框架调度开销，则加速比会被摊薄，答题者若不声明这一点，就无法解释为何同一 kernel 在不同口径下排名不同。这里应指路 roofline/SOL 的判定方法（该部分另有专述），本处只强调：指标口径必须先于数字。

三 · 基线与对照条件：谁代表“不演化”

基线的作用是给“协同演化”提供一个反事实：如果不让 proposer 与 coder 互相提供信号，系统能到什么水平。因此基线至少应覆盖三类：(a) 单次提示下的直接生成（无迭代、无反馈）；(b) 带执行反馈但角色不分离的单 agent 迭代；(c) 有迭代但 proposer 不随 coder 能力变化而调整任务分布的变体。三者分别剥离了“迭代”“角色分工”“任务分布自适应”三个因素。

对照条件必须写清：同一基座模型、同一 token 预算、同一采样温度与同一评测轮数。否则“演化带来提升”会被预算差异混淆。这里可用的伪代码思路是把预算显式约束为等式：

$$\text{Budget}_{\text{proposer}}+\text{Budget}_{\text{coder}}=\text{Budget}_{\text{baseline}},\quad \text{Rounds}_{\text{equal}}$$

代价在于：角色分离会把有限 token 切成两份，单侧预算下降；若 proposer 生成的题目质量不高，则 coder 侧的有效训练信号被稀释，出现“预算花在错题上”的浪费。具体例子：当 proposer 持续产出已被 coder 稳定解决的简单算子时，coder 侧获得的梯度信息趋近于零，此时协同演化的收益反而低于单 agent 直接迭代——这正是需要 (c) 类基线来暴露的失败模式。

另一个必须交代的口径是“持续改进”的度量方式：是以固定任务集上的通过率随轮次上升，还是以 proposer 新生成任务上的通过率上升。前者衡量拟合，后者衡量泛化。两者混用会让“改进”看起来比实际更强。答题时应明确：KernelZero 的“continuously improved”主张，其可信度取决于是否在未参与演化的留出任务上报告，而非仅在自生成任务上报告。

四 · 与相邻工作的分工：三段流水线各管一段

把 kernel 生成的技术栈切成三段：任务供给（题目从哪来、难度如何分布）、生成与优化（如何写出并改进 kernel）、验证与评测（如何可信地判定正确与快）。相邻工作大多占据其中一段：KernelBench 系基准占据第三段的任务与口径定义；执行反馈与 NCU/SASS profile 类工作占据第二段的优化信号来源；多轮 RL 与可验证奖励类工作占据第二段的训练机制。

KernelZero 的位置在第一段与第二段的接缝处：它不只消费固定任务集，而是让 proposer 生产任务、coder 消费任务，并把 coder 的成败回灌给 proposer。因此它与基准类工作的分工是——基准提供外部锚点（留出任务与统一口径），KernelZero 提供内部课程（自生成任务分布）。它与 RL 类工作的分工是——RL 类工作关注奖励如何从可验证信号构造，KernelZero 关注奖励信号如何在两个角色间分配与回流。

环节相邻工作职责KernelZero 的增量接口风险
任务供给固定任务集与难度分层proposer 按 coder 能力生成任务自生成任务与留出任务分布漂移
生成优化执行反馈驱动的单 agent 迭代coder 侧接收课程化任务预算切分导致单侧信号不足
验证评测正确性 oracle 与性能口径沿用外部口径做锚定口径不一致使跨系统比较失效

代价在于接口处：proposer 与 coder 共享同一基座时，任务分布会向 coder 的当前能力塌缩，导致课程“过拟合当前弱点”；若两者用不同基座，则信号传递需要额外的格式对齐，token 开销上升。具体例子：proposer 生成的题目若只覆盖 coder 已掌握的算子族，则留出任务上的通过率不升反降，这一现象只能通过外部基准锚点观测到，而不能在内部课程里自证。

五 · 解题路径的落地检查清单

把上面的拆解收束成可执行的答题顺序：先给出一句话的问题类定义（输入是高层算子语义，输出是可编译且数值等价的 GPU kernel，失败模式是编译失败、数值错误、性能不达标三类），再给出 (T, E) 的口径声明，再列出三类基线与预算等式，最后用三段流水线表划出分工。每一步都要附一个代价陈述，否则会被判为“只描述不分析”。

检查点包括：是否正确区分了“通过率”与“加速比”两个不同量纲的指标，是否声明了计时口径，是否说明了留出任务与自生成任务的差别，是否指出了角色分离带来的预算切分代价。任何一项缺失，都会使“协同演化带来持续改进”这一主张失去可检验性。

最后落在工程判断上：KernelZero 的核心贡献不在单个 kernel 的绝对速度，而在把任务分布变成可优化的对象；因此评价它时必须同时报告内部课程指标与外部锚点指标，二者缺一，协同演化的收益就无法与“题目变简单了”区分开。这一判断决定了后续读论文时该盯哪张表、该质疑哪个口径。

读题即定界：KernelZero 把问题切在“可共演化的 kernel 生成”这一刀上

KernelZero 的核心问题不是“让模型写出一个能跑的 kernel”，而是把 kernel 生成组织成一个**可持续自我改进的闭环**：一个 proposer 负责把任务读成“考点 + 可执行规格 + 验收口径”，一个 coder 负责在给定规格下产出 CUDA C++/Triton 实现，二者在同一个可验证奖励信号上共同演化。读题时必须先拆出三层：任务层（KernelBench 系基准中的算子语义与形状约束）、实现层（目标语言与硬件约束，如 shared memory 容量、warp 级原语可用性）、验收层（正确性 oracle + 性能口径）。这三层任何一层定义含糊，共演化就会退化成“proposer 猜题、coder 背题”。因此考点拆解的第一动作是把题干里的自然语言描述转成一份**可判定的契约**：输入张量的 dtype/layout、边界条件（非对齐长度、空张量）、数值容差、是否允许原子操作改变结合律、以及性能测量是端到端 wall time 还是 kernel-only 时间。契约不写死，后续所有 reward 都是噪声。

边界与失效条件集中在“奖励可验证性”上。KernelZero 依赖的奖励本质是一个分段函数：正确性不通过则奖励为零或负，通过后按相对基线的加速比给分。可写成 $$ r = \mathbb{1}[\text{pass}] \cdot \min\left(\frac{t_{\text{base}}}{t_{\text{cand}}},\, c\right) - \lambda \cdot \mathbb{1}[\text{timeout}] $$ 其中 $$c$$ 是加速比截断上限，防止 proposer 把任务改写成“几乎无计算”的退化形态来刷分；$$\lambda$$ 惩罚编译或运行超时。这个式子的失效条件很具体：若正确性 oracle 只覆盖基准自带的小形状，coder 可以针对固定形状硬编码 tile 尺寸而牺牲通用性；若基线选择不当（例如拿未优化的 naive 实现做分母），加速比会系统性虚高，proposer 学到的是“找弱基线”而非“找好算法”。因此读题时要追问：基线是 PyTorch eager、torch.compile 还是手写 CUDA 参考？指标是几何平均加速比还是逐任务通过率？两者混用会让共演化信号不可比。

系统代价必须在这一步就算清楚，否则后面多轮 RL 的预算会被悄悄吃掉。proposer 每轮要产出规格文本，coder 每轮要产出代码并触发编译 + 正确性测试 + 计时，单条样本的代价大致是：编译时间（NVCC 对模板重的 kernel 可达数十秒量级，Triton JIT 首次编译同样不可忽略）、显存（正确性测试需同时驻留参考输出与候选输出，大 batch 下会顶到容量上限）、以及 token（proposer 的规格越细，上下文越长，多轮共演化中历史规格的累积会线性推高 token 成本）。一个具体例子：对 reduction 类算子，若契约要求覆盖非 2 的幂长度，正确性测试就要枚举多种尾块形状，测试矩阵从个位数膨胀到几十个 case，单样本时延随之上升；反之若只测对齐形状，proposer 会稳定收敛到“只处理整除情形”的局部最优。读题阶段的工程判断是：**先确定测试矩阵的规模上限，再决定 proposer 规格的细度**，二者是同一预算的两端。

读题产出必须写死的字段缺失后的典型失效
任务契约dtype/layout、边界形状、容差、禁用原语coder 硬编码形状，跨形状通过率崩塌
验收口径基线实现、计时范围、加速比截断奖励被弱基线或退化任务污染
预算约束编译超时、测试 case 数、上下文长度共演化轮次被单样本时延吞没

与相邻工作的分工也由这次读题划定：纯 KernelBench 式评测只回答“某模型在某基准上的通过率与加速比”，不涉及 proposer 与 coder 的角色分离；纯 RL 训练工作关心策略更新，但不定义 kernel 级验收契约；形式验证方向关心单条实现的语义等价，不处理多轮共演化的信号设计。KernelZero 的位置是把“读题—出规格—写实现—验收”拆成可分别优化的两个角色，并用同一奖励耦合。因此本节的读题不是给答案，而是给出解题路径的骨架：先把契约写成可判定谓词，再把奖励写成带截断与超时惩罚的分段函数，最后用测试矩阵规模反推 proposer 规格的粒度——这三步任何一步跳过，共演化都会在边界条件上失守。
