一 · 题干拆解：把“pipeline”还原成可判定的阶段边界

这道题问的是《CUDA-L2: Surpassing cuBLAS Performance for Matrix Multiplication through Reinforcement Learning》里一条从输入到评测的流水线，但题面本身已经给了强约束：必须按“一次 kernel 生成—编译—运行—评测”的顺序回答，并且每一步都要交代输入、输出与失败模式。这意味着它不是让你复述论文的贡献点，而是考你能不能把一条 RL 驱动的 kernel 合成链路切成若干个状态可判定、失败可归因的阶段。读题时第一个动作是把“pipeline”这个词降维成状态机：每个阶段接收一个确定形态的产物，产出一个确定形态的产物，并且存在一组明确的拒绝条件。凡是不满足这三条的描述，都是叙事而非工程。

题干里“一次”这个限定词是考点密度的来源。它排除了“多轮迭代后收敛”的笼统说法，要求你描述单次采样（rollout）内部的生命周期：模型吐出一段源码文本，这段文本被落到文件系统，被编译器消费，被加载器加载，被 benchmark harness 计时，最后被一个评分函数折算成标量。每一步的输入输出类型都不同——文本、目标文件、可执行行为、数值向量——因此失败模式也分属不同层：语法/语义层、工具链层、运行时层、度量层。答题时若把编译失败和数值错误混为一谈，就等于没有拆开考点。

第二个考点是“评测”与“运行”的分离。运行只回答“它跑起来了吗、跑出了什么”，评测回答“它跑得对不对、跑得快不快、快得是否可信”。这两件事在实现上往往由不同组件承担：前者是 driver 与计时循环，后者是正确性 oracle 加性能基线比较。题干把它们并列成两步，就是在提示你：正确性判定与性能判定必须是两个独立可失败的关口，否则一个数值全错的 kernel 只要够快就会被奖励函数误判为优秀。

第三个考点是矩阵乘这个具体负载带来的额外约束。MatMul 的输入形态是固定的几个张量（A、B，可能还有 bias 与输出 C），形状、数据类型、布局（行主序/列主序、是否转置）都是 harness 给定的常量而非模型可选。于是“生成”阶段的输入不只是自然语言提示，还包括一组形状与 dtype 契约；模型生成的 kernel 必须在这个契约下自洽，否则编译能过、运行能过，却在边界 tile 上越界或错位。这一点是本题区别于一般“代码生成 pipeline”题的地方。

二 · 生成阶段：输入是契约，输出是候选源码，失败在语义而非语法

生成阶段的输入应当被精确描述为三元组：任务描述（要做 C = α·A·B + β·C 这类语义）、形状/dtype/布局契约（M、N、K 与元素类型、leading dimension）、以及可选的性能上下文（目标基线是 cuBLAS，硬件档位）。输出是一段完整的、可独立编译的 CUDA C++（或 Triton/CuTe）源码文本，通常还带一个固定的 host 侧入口签名，供 harness 以统一方式调用。注意输出不是“一个 kernel 函数”，而是“一个满足调用约定的翻译单元”，因为 harness 需要在不改代码的前提下完成加载与计时。

这一阶段的核心机制是受约束的解码：模型在 token 空间里逐位生成，而合法性由事后的编译与运行来裁决，因此生成端本身不保证任何语义正确性。工程上常见的做法是把源码包在一个模板里（固定 include、固定 launch 配置解析、固定错误检查宏），让模型只填核心计算部分，从而把“接口不匹配”这类失败从生成阶段挤出去，留给编译阶段处理。这个模板化动作的代价是表达力受限：模型无法自行改变 launch 策略的元信息结构，只能改 kernel 内部。

失败模式在这一层最典型的不是语法错误，而是语义漂移：生成的代码能编译，但 tile 尺寸与共享内存容量不匹配、边界谓词写反、同步点缺失导致 race、或者把 K 维循环的累加器初值搞错。这些都不会在生成时暴露，只会推迟到运行或评测阶段才炸。另一个失败模式是“看似合理但不可编译”的伪代码：调用了不存在的 intrinsic、把 PTX 内联汇编的约束符写错、或用了当前架构不支持的指令。生成阶段的 token 成本直接决定这条链路的吞吐：候选越长，采样越贵，而大多数候选最终会死在编译或正确性关口，所以单位有效样本的 token 开销是这一阶段真正的经济指标。

具体例子：契约给定 M=N=K 为 4096、fp16 输入 fp32 累加。模型生成一个 128×128 tile、每线程 8×8 累加的 kernel，共享内存按 fp16 双缓冲计算应为 2×(128×16)×2 字节量级；若模型按 fp32 估算共享内存，编译期静态共享内存超限直接报错，这就是一个可归因于生成阶段的失败，而不是运行阶段。

三 · 编译阶段：工具链是第二道 oracle，失败要分类而非二分

编译阶段的输入是上一阶段落盘的源码文件加一组编译选项（架构号、优化级别、是否开 fast math、链接哪些库）。输出是一个可加载的二进制（cubin/so）或一个明确的诊断。这一阶段的关键机制是把自然语言模型的输出翻译成机器可验证的中间表示：nvcc 或 triton 编译器完成语法分析、类型检查、PTX 生成、寄存器分配与指令调度。它是整条链路上第一个真正意义上的确定性 oracle——同一份源码在同一工具链下给出同一结果，因此失败可以被稳定复现与归类。

失败模式必须细分，因为不同子类对 RL 信号的含义完全不同。第一类是语法/类型错误，属于模型没学会语言规则，信号应当直接给零。第二类是资源超限：寄存器溢出到本地内存、静态共享内存超过上限、launch 配置的 block 数超过硬件限制，这类失败说明模型对硬件约束无感知，是本题的高频考点。第三类是架构不匹配：用了目标 SM 版本不支持的指令或 intrinsic，编译能过但加载失败，或编译期直接拒绝。第四类是警告淹没：编译成功但伴随大量未初始化变量、隐式类型转换警告，这类候选往往在运行期表现为数值错误。

代价在这里体现为编译时间与缓存命中率。RL 采样一轮可能产生成百上千个候选，每个都要走一次完整编译；编译时间从数百毫秒到数秒不等，若不做并发与缓存（相同源码哈希复用产物），编译就会成为整条 pipeline 的吞吐瓶颈，而不是 GPU。工程判断是：编译阶段的预算应当按“每有效候选的编译秒数”计量，并且必须把编译失败率作为独立指标记录，否则你无法区分“模型不会写代码”与“模型写的代码硬件跑不了”。

具体例子：候选 kernel 声明了 __launch_bounds__(1024) 却按每线程 256 个寄存器使用，编译器被迫 spill，产生大量 local memory 访问；编译成功，但生成的 SASS 里 LDG/STL 比例异常，这属于“编译通过但性能注定崩坏”的类别，评测阶段才会显现，因此编译阶段应当把寄存器用量与 spill 统计作为附加输出留存。

四 · 运行阶段：加载、launch、计时，失败在动态行为

运行阶段的输入是可加载二进制加一组运行参数（A、B、C 的设备指针、形状、stream）。输出是两样东西：一是数值结果（C 的内容或校验和），二是时间度量（多次迭代的耗时分布）。机制上它由三部分组成：模块加载与符号解析、launch 配置的合法性检查、以及带 warmup 的计时循环。计时必须包含 warmup 以排除首次加载与 JIT 的开销，并且要用同一 stream 上的事件计时而非 host 墙钟，否则测到的是 launch 开销而非 kernel 执行。

这一层的失败模式是动态的，且往往不可从源码静态推断。非法内存访问是最常见的一类：边界 tile 未加谓词，越界读写触发 device-side assert 或静默污染相邻内存；后者更危险，因为它不报错却让正确性判定随机通过。同步缺失导致的 race 表现为结果随运行次数漂移，单次运行看不出问题，需要重复运行比对。launch 配置错误（grid/block 维度算错、共享内存动态申请量超过声明）会在 launch 时立刻返回错误码，属于最容易归因的一类。死锁与超时则来自错误的 barrier 放置，表现为 kernel 不返回，harness 必须以超时机制兜底，否则整条 pipeline 挂起。

代价在这里是显存与时间。显存方面，harness 需要为每个候选分配输入输出缓冲区，若候选自行申请额外 workspace 而未释放，多次采样会累积泄漏；时间方面，计时循环的迭代次数与输入规模共同决定单候选的评测墙钟，规模越大、迭代越多，单位候选成本越高。工程上通常固定一个较小的迭代数用于筛选，再对通过正确性关口的候选做更精细的重复计时。

具体例子：一个把 C 的写回放在 K 循环内部的候选，在 K 较大时对同一输出元素反复读写，单次运行结果“看起来对”，但重复运行出现末位差异，这就是 race 类失败；它无法靠一次运行捕获，必须靠多次运行的一致性检查。

五 · 评测阶段：正确性 oracle 与性能基线的双关口

评测阶段的输入是运行阶段留下的数值结果与时间分布，加上参考实现（cuBLAS 或朴素 kernel）的结果与基线时间。输出是一个标量奖励或一组分层判定：正确 / 错误 / 超时 / 编译失败，以及在正确前提下的加速比。机制上它由两个独立关口构成。正确性关口用逐元素比较，容差按 dtype 设定：fp32 累加下常用相对误差与绝对误差的混合判据，fp16 输出则需更宽的容差。性能关口把候选的中位耗时与基线中位耗时相除得到加速比，并要求候选在多次重复计时下方差可控，否则加速比不可信。

$$\text{rel\_err}=\frac{\lVert C_{\text{cand}}-C_{\text{ref}}\rVert_2}{\lVert C_{\text{ref}}\rVert_2+\epsilon},\qquad \text{speedup}=\frac{t_{\text{base}}^{\text{med}}}{t_{\text{cand}}^{\text{med}}}$$

考点在于两个关口的顺序与耦合。必须先正确后性能：一个数值错误的候选即使快十倍也不能给正奖励，否则 RL 会迅速学会“跳过计算”。同时，正确性容差本身是一个可调参数，容差过松会让近似算法（例如降低累加精度）蒙混过关，容差过紧会把合法的重排累加判错——浮点加法不满足结合律，改变累加顺序必然带来末位差异，这是 MatMul 评测里必须显式承认的物理事实。

失败模式在这一层是度量失真：基线时间测在冷缓存或不同 clock 状态下，导致加速比虚高；候选的计时包含了未同步的异步错误，导致时间被低估；或者正确性检查只覆盖了部分输出元素（例如只查对角线），让越界写回的错误漏网。代价体现为评测本身的算力开销：参考实现要跑、候选要跑多轮、还要做全量逐元素比较，这些都比较耗时，尤其在大形状下，比较操作的带宽开销不可忽略。

具体例子：候选使用 split-K 策略，把 K 维切成多段并行累加再归约，速度显著优于单 kernel 串行累加，但由于归约顺序与 cuBLAS 不同，末位出现差异；若容差按严格逐位相等设定，这个合法优化会被判错，因此评测阶段必须把“累加顺序可变”写进 oracle 的设计里。

六 · 解题路径：先画状态机，再逐格填输入输出与失败

给出这条题目的作答路径应当是：第一步，明确写出四个阶段的名字与边界，并声明每个阶段的产物类型（文本 → 二进制 → 数值+时间 → 标量判定），这一步决定了答案的骨架是否可判定。第二步，对每个阶段填三格：输入是什么形态、输出是什么形态、失败如何归类。第三步，指出阶段之间的信息丢失点：生成到编译之间丢失了模型的意图，编译到运行之间丢失了源码结构（只剩 SASS），运行到评测之间丢失了单次运行的偶然性（只剩统计量）。这些丢失点正是失败模式滋生的位置，也是评分者想看你是否理解 pipeline 的地方。

需要调用的公式与判据在答题时应显式列出：正确性用上面的相对误差式并说明容差与 dtype 的关系；性能用中位耗时之比并说明 warmup 与重复计时的必要性；若涉及 roofline 判断，则用算术强度与峰值算力/带宽的比值来界定候选是否已接近 SOL，从而判断“比 cuBLAS 快”是否还有物理空间。这三个公式分别对应评测阶段的正确性、性能与可信度三个维度，缺一个答案就不完整。

工程判断上，这条 pipeline 的真正难点不在生成，而在失败归因的粒度。把“编译失败”当成一个桶，你就无法给 RL 提供有区分度的奖励；把“运行失败”与“数值错误”混在一起，模型就学不到边界谓词的重要性。可操作的判据是：每个阶段至少输出一个结构化状态码加一个可复现的最小证据（编译诊断文本、launch 错误码、最大误差位置、计时方差），使得任一失败都能被回溯到具体阶段。这也是本题作为“读题与考点拆解”而非“给答案”的意义所在：先把判定框架立起来，后续的优化与验证才有落点。
