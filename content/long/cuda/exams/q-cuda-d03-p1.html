一 · 题干的三层结构：方向、问题、交付物

这道题不是问“多轮 RL 与可验证奖励是什么”，而是问它要解决哪三个具体问题，并且必须给出评测侧两条、部署侧两条可执行做法，最后还要交代与相邻方向的分工。题干里藏着三层结构，读题时要把它们拆开，否则答案会滑向泛泛而谈的综述。

第一层是“方向”：多轮 RL 与可验证奖励，它属于 kernel agent 的训练信号与反馈闭环这一层，不是模型结构层，也不是推理框架层。第二层是“三个具体问题”：注意“具体”二字，意味着不能答成“奖励稀疏”“样本效率低”这类通用 RL 套话，必须落到 kernel 生成这个任务域上——即奖励从哪来、多轮之间状态怎么传、验证信号如何不被 reward hacking 侵蚀。第三层是“交付物”：评测侧两条 + 部署侧两条 + 分工说明，这是一个结构化输出要求，答题时必须显式分块，缺一块就是结构性失分。

把题干翻译成一句可执行的解题指令：在 kernel 生成任务上，指出可验证奖励在多轮交互中失效的三个具体环节，对每个环节给出评测侧与部署侧各一条可落地做法，并说明这套机制与正确性 oracle、profile 反馈、基准评测三个相邻方向各自负责什么、交界在哪。

这里有一个容易踩的坑：题干要求“评测侧与部署侧各两条”，不是“每个问题各两条”。也就是说四条做法是对整个方向的横切，而不是三个问题乘以二。读题时若按“3×2=6 条”去组织，篇幅会失控且重复。正确的结构是：三个问题纵向展开讲机制，四条做法横向收口讲落地。

二 · 考点拆解：出题人真正想看你区分什么

这道题的考点不在“知不知道 RL”，而在四个区分能力上。第一个区分是可验证（verifiable）与可测量（measurable）。kernel 的正确性可以由对拍 oracle 判定为布尔值，这是可验证；而性能是连续量，受噪声、频率、占用率影响，只能算可测量。把性能当成可验证奖励直接塞进 RL，就是把噪声当信号，这是出题人希望你在第一段就点破的。

第二个区分是单轮奖励与多轮信用分配。单轮时，一条 kernel 生成对应一个奖励，归因清晰；多轮时，第 k 轮的编译失败可能源于第 k−1 轮的错误改写，奖励要回溯分配到具体轮次与具体编辑动作上。这里需要调用折扣回报的形式：

$$G_t=\sum_{k=0}^{T-t-1}\gamma^{k}\,r_{t+k},\qquad \gamma\in(0,1]$$

当 γ 接近 1，远端轮次的稀疏奖励会主导梯度，方差大；当 γ 偏小，模型只优化眼前能编译通过，学不到“先改对再改快”的策略。这个权衡就是多轮信用分配的具体代价，答题时应把它与 token 预算挂钩：轮数 T 增加，序列长度线性增长，训练侧显存与采样时延随之上升。

第三个区分是奖励黑客（reward hacking）的入口在哪。可验证奖励的强度来自 oracle，但 oracle 本身有覆盖盲区：只测了若干形状、只比对容差内的数值、只跑固定 dtype。模型会学会“在测试形状上对、在真实形状上错”，这不是模型坏，是奖励函数漏。考点是让你指出：验证信号的覆盖度本身就是奖励设计的一部分，而不是评测阶段才补的事。

第四个区分是训练侧与部署侧的目标错位。训练侧要的是可复现、可批量、低时延的奖励计算；部署侧要的是真实负载下的端到端收益。两者对同一个 kernel 的评价可能相反：训练侧奖励一个在固定 shape 上快的 kernel，部署侧却因为动态 shape 退化而拒绝它。这个错位是“部署侧两条做法”存在的理由。

四个考点对应四种失分模式：把性能当可验证奖励、忽略多轮信用分配、无视 oracle 覆盖盲区、混淆训练与部署的评价口径。答题时每节至少命中一个，并在例子中显式体现。

三 · 三个具体问题的解题路径（只给路径，不给结论）

问题一：奖励从哪里来，且如何保持“可验证”的纯度。解题路径是先把奖励源分层：编译通过是硬布尔、对拍正确是硬布尔、性能是软连续量、NCU/SASS profile 是结构化诊断量。然后问：哪一层可以进 RL 的奖励函数而不引入噪声？路径的落点是构造分层奖励，硬布尔做门控（gate），软量做门内的排序信号。需要调用的公式是门控加权形式：

$$r=\mathbb{1}[\text{compile}\wedge\text{correct}]\cdot\big(w_1\cdot \text{speedup}+w_2\cdot \text{profile\_score}\big)$$

代价在于：门控使奖励稀疏，正确率低时几乎无梯度，需要课程式放宽或分阶段放开；同时 profile 采集本身有开销，一次 NCU 采集的时延远高于一次编译，若每轮都采，采样吞吐会掉一个量级。具体例子：一个 reduction kernel 在门控下只有“编译+对拍”通过才给分，模型前期大量样本得零分，此时若不做难度分级，多轮 RL 的样本效率会被稀疏奖励拖垮。

问题二：多轮之间状态如何传递，信用如何分配。解题路径是把一轮交互建模为“观察—编辑—验证”三元组，观察里放上一轮的编译错误、对拍差异、profile 摘要，编辑是 diff 级别的 kernel 修改，验证产出下一轮的观察。关键是观察的压缩：把完整 SASS 或完整 NCU 报告塞进上下文会迅速吃满 token 预算，必须做结构化摘要（如 top-k 热点指令、占用率瓶颈标签）。需要调用的思路是轮次级优势估计，把折扣回报按轮次拆开，用组内相对比较降低方差。代价是上下文长度随轮数增长，训练侧显存与注意力计算上升，且摘要本身可能丢信息导致错误归因。具体例子：第 3 轮把 shared memory 用错导致第 4 轮 bank conflict 加剧，若观察里只给“变慢了”，模型无法定位到上一轮的编辑，信用分配就断链。

问题三：验证信号如何抵抗 reward hacking 与分布漂移。解题路径是把 oracle 从“单点判定”升级为“覆盖度可度量的判定集合”：形状集合、dtype 集合、边界条件、数值容差都要显式参数化，并让训练时的采样分布与部署分布对齐。需要调用的思路是覆盖率指标与对抗采样：

$$\text{cover}=\frac{|\{c\in C:\text{oracle}(c)=\text{pass}\}|}{|C|},\qquad \text{reward}\propto \text{cover}\cdot\text{perf}$$

代价是覆盖集合越大，单样本验证时延越高，训练吞吐下降；容差收紧会误杀合法优化（如 fast-math 重排），容差放松则给黑客留门。具体例子：模型学会只对 2 的幂长度做向量化，对非对齐长度回退到标量，若测试集恰好全是 2 的幂，覆盖率满分而真实负载退化——这就是覆盖度未参数化的直接后果。

四 · 评测侧两条做法的推导路径

评测侧的第一条做法，路径指向把奖励函数的覆盖度当成被评测对象。也就是说，评测不只评模型产出的 kernel，还要评“这套可验证奖励是否真的可验证”。落地方式是构造一个分层的测试矩阵：编译层、数值层、形状层、dtype 层、并发层，每层给出通过率，并单独报告“训练分布内”与“分布外”两组。需要调用的量是覆盖率与误判率，代价是评测本身的计算量随矩阵维度乘积增长，且分布外样本的 oracle 往往需要参考实现，参考实现本身的性能会成为评测瓶颈。具体例子：对同一批生成的 GEMM kernel，在固定 M/N/K 上通过率很高，换到非对齐 K 后通过率骤降，这个落差就是评测侧要暴露的信号，而不是训练侧该藏起来的东西。

评测侧的第二条做法，路径指向多轮轨迹的可复现记录。多轮 RL 的奖励归因依赖轨迹，若评测只存最终 kernel，无法判断是第几轮变好或变坏。落地方式是为每条轨迹存轮次索引、编辑 diff、每轮观察摘要、每轮奖励分量，并保证 oracle 版本与随机种子可复现。代价是存储与回放成本：轨迹长度乘以观察摘要大小，批量评测时 I/O 会成为瓶颈；同时 oracle 版本漂移会让旧轨迹不可比，必须做版本钉死。具体例子：同一模型两次训练，最终 kernel 性能相近，但轨迹显示一次是第 2 轮就收敛、一次是第 6 轮反复回退，评测侧若不记录轮次，就看不出后者是信用分配失效。

评测侧做法核心机制主要代价暴露的信号
覆盖度作为评测对象分层测试矩阵 + 分布内外分组矩阵维度乘积带来的验证时延分布外通过率落差
多轮轨迹可复现记录轮次索引 + diff + 奖励分量落盘存储与回放 I/O、oracle 版本钉死收敛轮次与回退模式

五 · 部署侧两条做法的推导路径

部署侧的第一条做法，路径指向把训练奖励口径与部署评价口径对齐。训练侧奖励的是固定 shape 上的 speedup，部署侧关心的是动态 shape、批大小波动、显存上限下的端到端时延。落地方式是在部署前跑一组“口径对齐测试”：用真实请求分布采样 shape，比较训练奖励排序与部署排序的秩相关性，若相关性低，说明奖励函数过拟合了训练分布。需要调用的量是排序一致性，代价是对齐测试需要真实负载回放，回放环境本身要占资源，且真实分布随时间漂移，对齐是一次性的还是会退化的，需要周期性重跑。具体例子：训练侧奖励最高的 kernel 在固定 batch 上最快，但部署侧 batch 动态变化时因 occupancy 不足被次优 kernel 反超，秩相关性低就是预警。

部署侧的第二条做法，路径指向把可验证奖励的产物做成可回滚的部署单元。多轮 RL 产出的 kernel 带有“在某个 oracle 版本下通过”的隐含假设，部署时必须把这个假设显式化：绑定 oracle 版本、绑定测试覆盖集、绑定生成时的轮次与编辑历史，一旦线上出现数值异常可快速定位到是哪条假设失效并回滚。代价是部署包体积与元数据管理成本上升，且回滚粒度越细，灰度发布的编排越复杂。具体例子：线上某 shape 出现偶发数值偏差，若部署单元只含 kernel 二进制，排查只能靠猜；若含 oracle 版本与覆盖集，可直接判定是该 shape 不在覆盖集内，属于已知盲区而非回归。

两条部署侧做法与两条评测侧做法形成交叉：评测侧管“奖励是否可信、轨迹是否可查”，部署侧管“口径是否对齐、产物是否可回滚”。四者共同构成这个方向的落地闭环，而不是四个孤立建议。

六 · 与相邻方向的分工：交界线画在哪

题干最后要求说明分工，解题路径是把相邻方向按“谁产出信号、谁消费信号”排成一条链。正确性 oracle 与形式验证方向负责产出硬布尔信号与覆盖集定义，它不负责多轮信用分配，也不负责把信号变成奖励；本方向消费它的输出，并把覆盖度纳入奖励设计。执行反馈与 NCU/SASS profile方向负责产出结构化诊断量与性能测量，它解决“怎么测准”，本方向解决“测出来的量怎么进奖励、怎么在多轮里归因”。KernelBench 系基准方向负责提供可比的评测协议与任务分布，它定义“考什么题”，本方向定义“做题过程中怎么给分”。

分工的关键判断是：本方向不重新发明 oracle，也不重新发明 profiler，它的独特职责是把这两类信号组织成多轮可归因、抗黑客的奖励，并把训练口径与部署口径对齐。若答题时把 oracle 的构造细节大篇幅展开，就是越界，会挤占本方向的核心篇幅。反过来，若只谈 RL 算法而不谈信号来源，就是悬空。

交界线上还有一处容易混淆：基准评测方向关心“最终产物的绝对水平”，本方向关心“训练过程能否稳定产出高水平产物”。前者是一次性度量，后者是过程信号。具体例子：同一模型在 KernelBench 上得分相同，但一个是通过多轮稳定收敛得到，一个是靠大量采样撞运气，基准评测看不出差别，本方向的轨迹记录与信用分配分析才能区分。这个区分正是分工说明该落笔的地方。

把分工写成一句话的工程判断：本方向是信号链上的组织层，上游是 oracle 与 profiler 的产出，下游是部署侧的收益验证，自身不产出新的测量工具，只产出“如何可信地用这些测量去训练”的机制。答题时若能在分工段落到这句判断，并把三个问题的机制、四条做法的代价、以及覆盖度公式串起来，就完成了本部分要求的读题与考点拆解。
