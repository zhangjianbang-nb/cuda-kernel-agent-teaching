一 · 题干里的三层结构：度量对象、度量口径、度量边界

《MetaKernelBench: Measuring GPU Kernel Knowledge Transfer Beyond Code》这个标题本身就是一道压缩过的题干。拆开来看，它包含三个必须分别作答的子问题：第一，“Knowledge Transfer”指的是什么被传递——是代码片段、是优化策略、还是对某一类算子瓶颈的判断力；第二，“Beyond Code”排除了什么——排除了逐字复制实现、排除了只比对源码相似度，也就意味着评测必须落在行为层面；第三，“Measuring”要求给出可复现的量化口径，而不是定性描述。三者叠加，才构成“GPU Kernel Knowledge”这个被测量的构念（construct）。

读题时最容易犯的错误是把“加速比”当成唯一考点。加速比只是度量口径的一个实例，它回答的是“候选相对基线快多少”，却完全不回答“这个快是否来自可迁移的知识”。因此本条目要求的第一件事，是把题干拆成可判定的命题：度量对象是跨任务/跨实现的能力迁移；度量口径是相对基线的时延比值；度量边界是“在什么条件下该比值失去可比性”。

具体机制上，这类基准通常构造“源任务—目标任务”配对：源任务给出参考实现与优化后的 kernel，目标任务只给问题描述与基线，要求被测系统产出 kernel。考点因此落在配对设计上——若目标任务与源任务共享同一算子族但形状不同，测的是形状泛化；若共享形状但算子族不同，测的是策略迁移。这两种配对下同一个 speedup 数值的含义完全不同，这正是后文“不可比”讨论的根源。

代价方面，配对设计直接决定评测成本：每一对源—目标组合都需要一次基线测量与一次候选测量，若配对数为 N，则至少 2N 次计时；若再叠加多轮采样（同一 prompt 多次生成取最优或取均值），计时次数按采样数线性放大，GPU 机时与编译时间同步放大。这是设计配对矩阵时必须先算清的账。

二 · speedup 的形式化：从 T0、T1 到可比较的比值

论文报告的加速比，其定义是候选 kernel 相对基线 kernel 的时延改善倍数。设基线时延为 T0、候选时延为 T1，则

$$\text{speedup} = \frac{T_0}{T_1}$$

等价的倒数形式是 slowdown = T1/T0，两者互为倒数，工程上常用 speedup > 1 表示正收益、< 1 表示退化。这里必须强调 T0 与 T1 的测量口径必须一致：同一输入形状、同一 dtype、同一 batch、同一 warmup 与重复次数、同一计时方式（CUDA event 还是 wall clock）、同一是否包含 launch 开销与 host-device 同步。任何一项不一致，比值就不再是同一个量。

伪代码层面的计时骨架可以写成：对每个配置先做若干次 warmup 丢弃，再连续记录 K 次 event 时间取中位数或最小值；基线用框架自带实现（如 PyTorch eager 或 cuBLAS/cuDNN 路径），候选用被测系统产出的 kernel。中位数抗离群，最小值贴近理论上限，二者给出的 speedup 会有系统性差异，因此论文必须声明取哪一种。这一点在跨条目比较时尤其致命：取最小值的实现天然比取中位数的实现“更快”。

性能代价在这里体现为测量噪声与统计功效的权衡：K 太小则方差大，单次 speedup 的置信区间宽；K 太大则单配置机时上升，且长跑可能触发时钟降频，反而污染 T1。工程判断是：先用小 K 做筛选，再对进入报告的配置用大 K 复测，并把 K 与统计量写进评测协议，否则 speedup 不可复现。

具体例子：若某候选在基线 T0 上取得 speedup 2.0，读者不能直接推断“该 kernel 快一倍”，因为 T0 若取自未融合的 eager 实现，则 2.0 里有一部分来自融合本身而非被测系统的知识；若 T0 取自高度调优的库实现，则 2.0 才更接近真实增益。同一个公式，两种基线，两个故事。

三 · 19、29、16、45、71、54：这些数字在什么条件下不可比

题目给出的 19、29、16、45、71、54 是一组加速比数值。在不引入论文未给出的实验条件的前提下，只能从度量口径的角度说明它们为何不能直接横向比较。第一层不可比来自基线选择：若不同数值对应的 T0 分别取自 eager、TorchInductor、厂商库或手写参考，则分母不同，比值不可通约。第二层来自任务集合：若 19 与 71 分别对应不同算子族（如 elementwise 与 reduction、GEMM 与 attention），则它们的 roofline 位置不同，可达加速上限本就不同，把两个比值并列排序没有意义。

第三层来自输入形状与 dtype：小形状下 launch 开销占比高，speedup 对 kernel 质量不敏感而对融合与 launch 次数敏感；大形状下带宽或算力成为瓶颈，speedup 才反映实现效率。第四层来自计时口径：是否包含 host 侧调度、是否同步、是否摊销编译与 autotune 时间。第五层来自聚合方式：是逐配置取几何平均、算术平均，还是取最优配置的单点值；几何平均对退化更敏感，算术平均会被个别超高值拉高，单点最优则完全不可比。

不可比来源对 speedup 的影响方向工程后果
基线实现不同（eager vs 库 vs 手写）分母变大则比值变小跨论文数值无法排序
任务族不同（带宽型 vs 算力型）可达上限不同并列比较失去意义
形状/dtype 不同小形状被 launch 开销主导结论不可外推
计时是否含编译/autotune含则比值下降部署收益被高估
聚合方式（几何/算术/最优）最优值系统性偏高报告数字偏乐观

因此正确读法是：把每个数字绑定到它的（基线、任务集、形状、计时口径、聚合方式）五元组上，只在五元组相同的子集内比较。19 与 29 若同属一个任务族且同基线，可以谈趋势；71 与 54 若跨族，只能各自陈述，不能相减。代价是评测报告的信息量上升——每个数字都要携带上下文，token 与表格体积增加，但这正是“可信评测”的必要开销。

四 · 解题路径：从题干到可执行验证计划

面对这类题，推荐四步路径。第一步，锁定度量对象：明确要证明的是“迁移”而非“记忆”，因此必须存在目标任务上未见过的实现或形状，且源任务信息以自然语言或参考代码形式给出。第二步，锁定口径：写出 speedup 公式并逐项固定 T0、T1 的测量协议，包括 warmup 次数、重复次数、统计量、是否含编译。第三步，锁定边界：列出使比值失效的条件清单，并在报告中为每个数字标注五元组。第四步，给出验证手段：正确性 oracle（与参考实现逐元素比对，容差按 dtype 设定）、性能 oracle（NCU 采集的带宽/占用率与 roofline 上界对照），二者缺一不可，因为一个错误但快的 kernel 会让 speedup 虚高。

伪代码思路可写成判定流程：若候选输出未通过容差比对，则 speedup 记为无效而非 0；若通过，则计算 T0/T1 并同时记录候选的 SOL（speed of light）占比，用于判断剩余空间来自实现还是来自任务本身的上限。这样每个数字都带有“是否可信”的标签，而不是一个孤立比值。

代价在于验证环节的机时：正确性比对需要额外的前向与数据搬运，NCU 采集会引入 profiling 开销并可能改变时序，通常需要单独一轮不采样的计时。工程判断是：正确性与性能分两轮跑，性能轮不挂 profiler，profiler 轮只用于解释瓶颈，不用于报告 speedup。

具体例子：若某候选在目标任务上 speedup 为 45，但 NCU 显示其 DRAM 吞吐已接近峰值带宽的绝大部分，则该 45 的进一步提升空间受限于带宽而非实现，此时把它与一个算力受限任务上的 71 并列，会误导读者以为后者“更值得优化”。

五 · 需要调用的公式与量纲检查

除 speedup 外，本条目要求调用的公式还包括 roofline 上界与相对效率。设任务的计算量为 F（FLOPs）、访存量为 B（bytes），机器峰值算力为 P、峰值带宽为 W，则可达时延下界为

$$T_{\min} = \max\left(\frac{F}{P},\ \frac{B}{W}\right)$$

对应的 SOL 占比为 T_min / T1，它把 speedup 从“相对基线”翻译成“相对物理上限”，两者结合才能判断一个 19 或 71 是接近天花板还是仍有空间。量纲检查同样重要：T0 与 T1 必须同为时间单位，若一方是每迭代时间、另一方是总时间，比值无量纲但语义错误；若 batch 不同，则需先归一化为每样本时延再取比值。

另一个必须调用的量是编译与 autotune 开销 T_c。部署端到端收益应写成 (T0 − T1 − T_c/N_reuse)，其中 N_reuse 是该 kernel 在真实负载中的复用次数。当 N_reuse 很小，T_c 会吞掉 speedup 的收益；当 N_reuse 很大，T_c 可摊销至可忽略。这一项在只报告 T0/T1 的表格里完全不可见，是读题时必须补上的维度。

代价层面，SOL 计算依赖对 F 与 B 的准确计数，计数错误会让上界失真；对融合 kernel，B 应按实际 DRAM 流量而非逻辑张量大小计，否则会高估带宽压力。工程判断是：先用解析计数得到粗略上界，再用 NCU 的实测吞吐校正，两者偏差大时优先怀疑计数而非硬件。

具体例子：一个 elementwise 候选取得 speedup 16，若其 T_min 由 B/W 决定且实测已贴近该下界，则 16 的绝对值取决于基线离上界有多远，而非候选有多好；此时换一个更强的基线，同一个候选的 speedup 会显著下降，这正是“不可比”的又一种表现。

六 · 读题时的工程判断：把数字还原成条件

本条目要求的最终能力，是在看到任何一个 speedup 时立刻追问它的五元组，并判断该数字能否进入横向比较。19、29、16、45、71、54 这组数值的正确用法不是排序，而是分组：先按任务族与基线分组，再在组内看趋势，组间只做定性陈述。若论文未给出分组所需的条件，则该数字只能作为存在性证据（“该系统能在某类任务上取得正收益”），不能作为强度证据（“该系统比另一系统强多少”）。

与之配套的机制是评测协议的最小充分集：基线声明、形状与 dtype 清单、warmup 与重复次数、统计量、是否含编译、聚合方式、正确性容差。缺任一项，speedup 就不可复现；缺三项以上，数字应被视为不可用。这一判断标准比任何单个数值都更重要，因为它决定了整套基准的可信度。

代价是报告体积与读者负担：每个数字携带七项上下文，表格从一列变成多列，token 消耗上升。但这是“Beyond Code”的必然代价——既然测量的不是代码相似度而是行为迁移，行为条件就必须显式写出，否则度量退化为不可解释的排行榜。工程上可接受的做法是把五元组编码为配置 ID，正文只引 ID，附录给全表，从而在可读性与可复现性之间取得平衡。

具体到本题，解题路径的落点是：写出 speedup = T0/T1，固定测量协议，列出使 19/29/16/45/71/54 不可比的五类条件，并给出用 SOL 与 T_c 校正读数的公式。做到这三点，题干就被拆解为可验证的命题，而不是一组待记忆的数字。

加速比读题：分母是谁、在哪个时钟域、跨不跨设备

这道题表面是套公式，真正的考点在“T0 到底取哪一次测量”。题干给出的 T0 是基线时延、T1 是候选时延，于是 $$\text{speedup}=\frac{T_0}{T_1}$$ 只是起点；判分时要追问三件事：T0 是否与 T1 在同一输入形状、同一 dtype、同一 warmup 与重复次数下测得；两者是否在同一 GPU、同一时钟/功耗状态下采集；计时是否都覆盖了端到端（含 launch、同步、必要的 host-device 拷贝）而非只截 kernel 体。任一条不满足，比值就退化为两个不同实验的商，只能称“相对提升”而不能称加速比。

论文给出的 19、29、16、45、71、54 这组数字正是失效条件的集中体现：它们量级跨度大，说明分母侧基线实现的起点差异极大——有的基线是未融合的逐算子 PyTorch 组合，有的是已高度调优的库实现，有的候选则换了算法族（如把多次归约折叠成一次）。因此这些倍数之间不可横向比较，也不可与 KernelBench 系其他条目的倍数直接对齐；只有当基线选择规则、输入规模与计时协议被固定成同一口径时，倍数才具备可比性。工程上应把 speedup 视为“在声明口径下的条件量”，读题时必须先还原口径再谈数值。

代价落在验证侧：为拿到可比数字，需要在同一进程内交替跑 T0/T1 并做多次采样取稳健统计，这会拉长评测 wall-clock 并占用显存驻留两套实现；若为省时改为分别跑，则时钟漂移与热漂移会直接污染比值。一个具体例子：同一候选在冷启动首次调用时含 JIT/autotune 开销，若 T1 取首次、T0 取稳态，倍数会被系统性压低；反之若 T1 取 autotune 后的最优配置而 T0 未做等价调优，倍数被系统性抬高。故解题路径是先固定“同形状、同设备、同 warmup、同同步点、同基线选择规则”，再代入公式，并把 19/29/16/45/71/54 标注为“各自口径下的条件倍数”，拒绝跨条目排序。
