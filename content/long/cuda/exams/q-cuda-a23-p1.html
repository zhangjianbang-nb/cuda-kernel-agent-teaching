一 · 把题干拆成可执行的三层结构

题干只有一句话，但它同时约束了三件事：算法对象（成对排序偏好奖励）、工程对象（一次 kernel 生成/优化/验证的流动）、以及回答形式（拆成几步，每步给出输入、输出与代价）。读题时先把这句话还原成三层：第一层是奖励语义层，问的是「成对偏好」在 kernel 语境下到底对什么做比较；第二层是流水线层，问的是一次 kernel 生命周期里哪些阶段是必须显式建模的；第三层是代价层，要求每一步都落到可度量的资源上，而不是停在流程名词。

拆题的关键判断是：这里的「成对排序偏好奖励」不是训练配方里的 RLHF 奖励模型，而是把「两个候选 kernel 实现之间谁更优」编码成一个可计算的标量信号。也就是说，奖励的输入是一对候选（例如同一算子的 Triton 版与 CUDA C++ 版，或同一版本的两份优化产物），输出是一个偏好方向与强度。题干要求把这个奖励嵌进「生成—优化—验证」的流动里，因此每一步都必须回答：这一步产出什么候选、奖励在这一步读到什么、以及奖励计算本身付出什么代价。

考点因此可以归为四类：其一是候选对的构造——偏好奖励要求成对输入，而 kernel 流水线天然是单候选推进的，二者之间存在结构错位，这是第一个考点；其二是奖励的可验证性——偏好信号必须能追溯到正确性 oracle 与性能度量，否则奖励就是噪声；其三是奖励计算的摊销——成对比较意味着候选数按对增长，代价如何不爆炸；其四是流动的闭合性——优化步产生的候选要能回流到生成步的偏好分布里。解题路径就是沿这四类考点逐层给出机制、公式与代价，而不是直接给一张步骤表。

二 · 奖励语义层：偏好到底比较什么

成对排序偏好奖励的标准形式是 Bradley-Terry 型的成对似然：给定候选 a 与 b，奖励模型输出 r(a)、r(b)，偏好概率为

$$P(a \succ b)=\sigma\big(r(a)-r(b)\big),\qquad \sigma(x)=\frac{1}{1+e^{-x}}$$

在 kernel 语境下，r 不能是自由学习的标量，而必须由可观测信号构造，否则偏好无法被验证。工程上通常把 r 写成正确性与性能的合成：正确性作为硬门（不通过则 r 置为负无穷或直接剔除该对），性能作为软序（时延、带宽利用率、SOL 比例等）。这一步的输入是一对候选及其各自的执行反馈（编译产物、运行结果、profile 摘要），输出是一个偏好标签与一个置信度，代价是每对候选至少两次完整执行——这是偏好奖励相对单点奖励最直接的开销来源。

具体例子：同一 GEMM 算子的两个候选，一个用 Triton 写、一个用 CuTe 写，二者都通过正确性 oracle，但 Triton 版在目标形状上时延更低。偏好标签为「Triton 版更优」，强度由时延差经单调映射得到。这里的机制要点是把性能差归一化到与形状无关的尺度，否则不同算子的偏好强度不可比，回流到生成步时会污染偏好分布。

代价要显式记账：每对比较需要两次编译（编译时间）、两次执行（时延）、两次 profile（NCU 采集带来的额外时延与显存占用），若正确性 oracle 采用形式验证则还要加上求解器时间。偏好标签的置信度若来自多次重复执行，则代价按重复次数线性增长。这一步不产出新候选，只产出标签，因此它的输出是下一步的监督信号而非工件。

三 · 流水线层：生成、优化、验证三段的边界与接口

把一次 kernel 生命周期拆成三段，每段都要定义「输入候选集、输出候选集、奖励读取点」。生成段的输入是算子规格（形状、dtype、语义约束）与历史偏好分布，输出是一批初始候选；优化段的输入是上一段的候选与它们的 profile，输出是改写后的候选；验证段的输入是候选，输出是正确性判定与性能度量。偏好奖励在三段中的读取点不同：生成段读的是历史对的偏好统计（用于条件化采样），优化段读的是同源候选对的局部偏好（用于决定改写方向），验证段读的是跨源候选对的全局偏好（用于决定是否接纳）。

这里的关键机制是候选对的构造规则：生成段内部的对来自同一 prompt 下的多次采样（同源对），优化段的对来自改写前后（前后对），验证段的对来自不同实现路线（跨源对）。三类对的语义不同，奖励模型若共用同一套 r，必须保证 r 对「同源」「前后」「跨源」三种差异都单调，否则会出现偏好不可传递。工程上常用的做法是给每类对加一个偏置项，使 r 分解为「绝对质量分 + 对类型修正」。

伪代码思路如下（不展开实现）：对每个候选 c，先跑正确性 oracle 得到布尔门 g(c)，再跑 profile 得到性能向量 p(c)；对每一对 (a,b)，若 g(a)∧g(b) 为假则丢弃该对，否则计算 r(a)-r(b) 并写入偏好缓冲。偏好缓冲按对类型分桶，供三段分别读取。代价上，验证段的跨源对数量是候选数的平方量级，若不加剪枝，偏好计算会成为流水线瓶颈；剪枝策略（只对同形状、同语义的候选配对）是这一步必须给出的工程判断。

具体例子：一个 softmax 算子，生成段产出 8 个 Triton 候选，优化段对其中 3 个做循环展开改写得到 3 个新候选，验证段把 11 个候选按「同形状」配对。若全配对则有数十对，剪枝后只保留同源对与前后对，跨源对仅取每类代表各一，对数降到个位数。这一步的代价是配对与剪枝的逻辑本身，以及偏好缓冲的显存占用（每对一个标签与置信度，量级很小但需持久化以支持回流）。

四 · 代价层：偏好奖励的摊销与回流代价

偏好奖励的代价有两个方向：前向摊销与回流代价。前向摊销指每产生一个偏好标签所消耗的执行与 profile 资源；回流代价指把偏好统计写回生成段的条件分布时，采样器需要维护的额外状态。前者可以用「每标签代价 = 2×执行代价 + 2×profile 代价 + oracle 代价」记账；后者体现为生成段采样时的额外 token 或额外显存——若偏好分布以向量形式条件化，采样器每步要多读一个偏好嵌入。

公式上，若候选数为 N、配对数为 M，则偏好标签的总代价为

$$\text{Cost}_{\text{pref}}=M\cdot\big(2C_{\text{exec}}+2C_{\text{prof}}+C_{\text{oracle}}\big)+C_{\text{writeback}}$$

其中 M 受剪枝规则约束，Cwriteback 是偏好缓冲写入与采样器读取的固定开销。这个式子给出的工程判断是：剪枝比加速单次执行更能降低偏好代价，因为 M 是平方量级的杠杆。具体例子：把跨源对从全配对改为代表对，M 从平方级降到线性级，偏好计算从流水线瓶颈退为次要开销，代价是跨源偏好的统计置信度下降，需要在验证段用更多重复执行补偿。

正确性代价同样要记账：偏好标签只在双方都通过 oracle 时才有意义，因此 oracle 的假阳性会直接污染偏好。若 oracle 采用形式验证，其求解时间随候选复杂度增长，可能超过执行本身；若采用数值比对，则需固定随机种子与容差，否则同一对候选在不同轮次得到相反偏好，破坏可传递性。这一步的输出是偏好缓冲与代价账本，二者共同构成回流到生成段的输入。

五 · 解题路径：从考点到可回答的结构

综合以上三层，解题路径可以写成四步的推导链，而不是直接列步骤表。第一步，定义偏好对象：明确一对候选是什么、r 由哪些可观测信号构成、硬门与软序如何分离。第二步，划定三段边界：生成、优化、验证各自读哪类对，接口是候选集与偏好缓冲。第三步，给出配对与剪枝规则：同源对、前后对、跨源对的构造条件与数量控制。第四步，记账代价：用上面的公式逐项填 M、Cexec、Cprof、Coracle、Cwriteback，并指出瓶颈所在。

这条路径对应四个考点：偏好对象的可验证性、三段接口的闭合性、配对数量的可控性、代价账本的完整性。每个考点都要求给出机制而非名词：例如「可验证性」要求说明 oracle 的假阳性如何被偏好缓冲的置信度字段吸收；「闭合性」要求说明优化段的前后对如何回流为生成段的同源对统计。具体例子：若优化段发现某类改写（如 shared memory 分块）在前后对中持续胜出，则该改写类型作为先验写入生成段的条件分布，下一轮生成段对该类型的采样概率上调——这就是回流的具体机制，代价是采样器多维护一个类型先验表。

需要调用的公式在本部分只有两个：Bradley-Terry 偏好概率与偏好代价公式。前者用于定义标签语义，后者用于回答「每一步的代价是什么」。解题时不直接给答案，而是把这两个公式作为骨架，让读者自己填三段的具体输入输出。这样做的工程理由是：kernel 流水线的具体形态随算子与工具链变化，唯一稳定的部分是偏好语义与代价结构，抓住这两者，步骤拆分就是可复现的推导而非记忆。

成对偏好奖励流：边界条件、失效模式与系统代价的拆解

把「成对排序偏好奖励」嵌进一次 kernel 生成—优化—验证的流动里，第一步不是写代码，而是判定这条流动在什么条件下才成立。题干里「成对」二字决定了输入必须是同一 prompt 下的两个候选 kernel（记为 k_a、k_b）及其各自的执行反馈，而不是两个独立任务；「排序偏好」决定了奖励只在两者可比时才有意义。可比性的硬边界有三条：其一，两候选必须针对同一算子语义与同一输入形状，否则正确性 oracle 的判定基准不同，偏好信号退化为噪声；其二，两者的编译状态必须同层，一个编译通过、一个编译失败时，奖励应走「可行性优先」的字典序而非连续打分；其三，profiling 采集口径必须一致（同一 NCU section、同一采样次数），否则时延差里混入了测量噪声。考点正在这里：多数方案把奖励写成 $$r = \sigma\big(\beta\,(s_a - s_b)\big),\quad s = w_c\cdot \mathbb{1}[\text{correct}] + w_p\cdot \text{SOL}$$ 却不在题干里声明 $w_c$ 与可行性过滤的先后关系，导致正确性未通过的候选仍能靠 SOL 分拿到正偏好。解题路径因此是先拆出「可行性门 → 正确性门 → 性能序」三级，再谈连续奖励。

失效条件需要逐条落到流动的每一步上。读题阶段若把「一次 kernel」误解为「一次编译」，就会漏掉 autotune 配置空间这一层——同一 kernel 源在多个 tile/block 配置下产生多个候选，成对比较的对象究竟是源级还是配置级，直接决定奖励的方差。生成阶段若两候选共享同一模板只改常量，偏好对的信息量趋近于零，RL 梯度被稀释；此时应改用同一模板的不同变体做「难负例」构造。优化阶段最典型的失效是奖励黑客：候选通过裁剪边界检查换取 SOL 提升，正确性 oracle 若只测单一形状便放行，偏好就被系统性带偏。验证阶段的失效是 oracle 覆盖不足导致的假阳性——成对比较把两个都错的候选排出高低，等于在错误子空间里做排序。系统代价上，成对流动把单候选的验证成本翻倍：两次编译、两次 NCU profile、两次正确性比对，且 profile 本身是串行瓶颈，单对样本的墙钟时延由 profile 采集主导而非编译主导。

下表把三级门与代价对齐，作为解题路径的骨架而非答案：

阶段输入判据主要代价
可行性门两候选源 + 编译日志编译/链接成功、无非法指令编译时间 ×2，失败即短路
正确性门两候选输出 + 参考实现多形状逐元素容差比对显存峰值 ×2，参考实现常驻
性能序两候选 NCU 指标SOL 或时延比，同口径profile 串行，采样次数决定方差

需要调用的公式除上面的 sigmoid 偏好外，还有偏好对的置信度修正：当两候选 SOL 差小于测量噪声 $\epsilon$ 时应置零而非强行排序，即 $$\tilde{r}=r\cdot\mathbb{1}[|s_a-s_b|>\epsilon]$$，否则 RL 在噪声上做梯度上升。工程判断落在流动的入口：先问「这对候选是否同语义、同形状、同编译层」，任一不满足就退回单候选绝对评分，而不是硬凑成对。这一步的 token 代价体现在读题与考点标注上——把边界条件写进 prompt 模板比让模型自行推断更省 token，也更少出现把可行性失败误判为性能劣势的偏好翻转。
