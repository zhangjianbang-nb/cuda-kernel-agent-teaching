一 · 先把题干拆成四层可执行对象

这道题的问法看起来是一句“搭一套评测 harness”，但它实际上把论文标题里的每个词都变成了一个必须落到配置文件的决策点。拆题的第一步不是去想“怎么评”，而是先把题干里的名词逐个翻译成 harness 中的实体：Multi-turn 对应的是 rollout 的轮数与每轮的观测接口；Structural rewards 对应的是不依赖运行结果的静态奖励项；Performance aware rewards 对应的是依赖 profile 或计时的动态奖励项；CUDA Kernel Generation 对应的是被测对象——一段从自然语言规格到可编译 kernel 的生成过程。四层对象之间是耦合的：轮数决定了奖励在哪些时刻被计算，奖励的结构又决定了正确性门必须放在哪一轮之前。

因此解题路径的第一段应当是画一张“对象—接口—验收”的三列表。左列写 harness 的六个部件：基线集合、输入分布、正确性门、防作弊层、上线门、报告口径。中列写每个部件与论文方法的接触面：基线集合要能区分“多轮带来的增益”与“单轮采样更多带来的增益”，所以基线至少包含单轮 best-of-n 与单轮自反思两条；输入分布要覆盖结构奖励能起作用的情形（例如需要拆分 tile、需要重排访存）与性能奖励能起作用的情形（例如带宽受限与计算受限两类）；正确性门要区分“编译通过”“数值对齐”“边界条件”三级；防作弊层要拦住对测试用例的硬编码、对计时器的篡改、对 profiler 的探测；上线门要把离线奖励与端到端时延挂钩；报告口径要固定随机种子、固定驱动与编译器版本、固定 GPU 型号。

这里必须给出一个代价判断：每增加一个基线，rollout 的 token 消耗与编译时间都线性上升。设单条轨迹平均消耗 T 个 token、编译与运行合计 C 秒，则 B 条基线、N 个任务的评测总成本约为 B·N·(T·p_token + C)，其中 p_token 是单位 token 的计价。这个式子不是装饰，它决定了你能否在 CI 里跑全量：如果 B·N·C 超过单次 CI 的时间预算，就必须把基线拆成“每夜全量”和“每次提交抽样”两档，而抽样档只保留能区分方法差异的那几条基线。

二 · 结构奖励的考点：它奖励的是什么，以及它为什么可能被绕过

结构奖励的考点不在于“有没有结构”，而在于“结构信号是否与最终性能单调相关”。题干要求你搭 harness，本质上是在问：你如何证明一个不运行 kernel 的静态打分器没有把模型引向错误方向。具体机制上，结构奖励通常由若干可静态检查的性质组成，例如循环嵌套是否与 tile 形状匹配、共享内存声明是否与 block 维度一致、是否存在明显的 bank conflict 模式、是否使用了向量化加载。把这些性质记为一个布尔向量 s = (s_1, …, s_k)，结构奖励就是 R_struct = Σ w_i·s_i 或 R_struct = Π s_i 的加权形式。harness 必须能对每一项单独开关，否则你无法定位“奖励涨了但性能没涨”的归因。

$$R_{\text{struct}}(y)=\sum_{i=1}^{k} w_i\,\mathbb{1}\!\left[\phi_i(y)=1\right],\qquad \sum_i w_i = 1$$

代价在于：静态检查器本身要写规则，规则越多，误报与漏报的组合爆炸越严重；更关键的是，静态检查器只看代码文本，模型可以写出“形式上满足 φ_i 但语义上无意义”的代码，例如声明了共享内存却从不读写、写了向量化加载却把结果丢弃。这就是防作弊层必须与结构奖励同轮次介入的原因：harness 要在每一轮生成后立即跑一次“结构—语义一致性”检查，把 φ_i 为真但对应变量在数据流上死掉的样本标记为无效，并从奖励中扣除。一个具体例子：某轮生成中模型为了让 φ(共享内存复用) 为真，声明了 __shared__ float buf[256] 却只写不读，静态检查通过、运行结果也正确（因为没用它），但性能奖励为零；如果 harness 不拦，这类样本会污染多轮训练的信用分配。

另一个代价是编译时间。结构检查若需要 AST 级分析（例如判断循环边界是否为编译期常量），就要调用编译器前端，单条样本的分析时间从毫秒级升到数百毫秒级；在 N 个任务、每任务 M 轮的设定下，这部分开销是 N·M·t_ast，必须与 rollout 的 token 成本分开计量，否则你会误以为瓶颈在模型侧。

三 · 性能奖励的考点：测什么、在哪一轮测、噪声怎么压

性能奖励的考点是“测量口径”而非“测量本身”。题干要求可复现，意味着你必须固定：计时方式（CUDA event 还是 wall clock）、预热次数、重复次数、是否锁频、是否独占 GPU、是否包含 kernel launch 开销。这些选择直接改变奖励的排序。具体机制上，性能奖励通常写成相对基线的加速比或相对 roofline 的达成率：

$$R_{\text{perf}}(y)=\mathrm{clamp}\!\left(\frac{t_{\text{ref}}}{t_y},\;0,\;\rho\right)\quad\text{或}\quad R_{\text{perf}}(y)=\frac{\mathrm{FLOPs}/t_y}{\min(\mathrm{peak}_{\text{mem}},\,\mathrm{peak}_{\text{comp}})}$$

前者的问题是 t_ref 的选择：用 PyTorch 参考实现、用同任务的历史最佳、还是用 roofline 下界？三者给出的奖励尺度完全不同，harness 必须把 t_ref 作为配置项显式记录，并在报告中同时给出三种口径，否则跨任务比较无意义。后者的代价是 roofline 参数本身需要标定，而标定又依赖 GPU 型号与时钟，这使“可复现”从代码层面延伸到硬件层面。

噪声是这一节最实的工程问题。单次计时在共享 GPU 上的方差可以轻易吞掉 5% 以内的加速差异，而多轮 RL 恰恰要在小差异上做信用分配。harness 的对策应当是：每轮至少 k 次重复取中位数，且把“计时方差超过阈值”的样本标记为 unstable 并从奖励中剔除，而不是把噪声当成信号喂给训练。代价是评测时延：k 次重复意味着 k 倍的 kernel 执行时间，若 k=20 且单次执行 2 ms，单样本就是 40 ms，乘以 N·M 后可能超过 rollout 本身。一个具体例子：带宽受限的 copy-like kernel，其计时对 L2 残留状态极度敏感，若不固定预热与 flush 策略，同一份代码两次测量可以差出可观比例，harness 必须在配置里写明 flush 行为。

四 · 多轮与信用分配：harness 要记录什么才能事后归因

多轮的考点是“奖励在时间上的归属”。题干的方法把结构奖励与性能奖励放进多轮循环，那么一次成功或失败该记到哪一轮？harness 的最小记录单元必须包含：轮次索引、该轮的完整生成文本、编译产物哈希、静态检查逐项结果、计时原始样本、以及该轮是否触发了早停。没有这些，你只能得到轨迹级的总奖励，无法回答“是第几轮的结构修正带来了性能提升”。

伪代码层面的思路是：每轮结束后计算一个增量奖励 Δ_r = R_r − R_{r−1}，并把 Δ_r 与当轮的动作类型（改 tile、改访存、改同步）对齐；若 Δ_r 为负且下一轮未恢复，则标记该轮为“有害探索”。这套记账的代价是存储：每条轨迹要保留 M 份生成文本与编译产物，若 M=8、每份产物含 cubin 与日志，单轨迹可达数十 MB 量级，全量 N 条轨迹的存储需求必须提前估算，否则 harness 会在磁盘上先崩掉。另一个代价是 token：多轮意味着上下文累积，第 r 轮的输入 token 数约为前 r−1 轮生成之和加上规格文本，总 token 消耗随 M 呈二次增长趋势，这是多轮方法相对单轮最直接的成本。

具体例子：某任务第 3 轮模型把 block 从 128 改到 256，静态检查全过，计时却变慢；第 4 轮模型回退到 128 并加了向量化加载，计时改善。若 harness 只记总奖励，这次“先错后对”的探索会被记为正贡献；若记了 Δ_r，则第 3 轮是负贡献、第 4 轮是正贡献，信用分配才正确。

五 · 正确性门与防作弊：三级门与四条拦截线

正确性门的考点是“门放在哪一级”。harness 应设三级：第一级是编译门，任何编译失败直接终止该轮且奖励为零；第二级是数值门，用固定随机种子生成输入，与参考实现比对，容差按数据类型给定（fp32 与 fp16 的容差不同，累加顺序不同也会引入差异）；第三级是边界门，覆盖零尺寸、非对齐尺寸、极端值。三级门的代价是评测时延与显存：数值门要为每个任务准备参考输出，若任务输出是大张量，参考输出的显存占用可能与被测 kernel 同量级，harness 必须支持分块比对而非全量驻留。

防作弊的四条拦截线应写成可执行的检查，而不是原则：其一，输入随机化——测试输入在评测时现场生成且种子不进入模型上下文，防止对固定用例硬编码；其二，计时器完整性——kernel 内部若出现对 clock64 的读取或对 profiler 计数器的写操作，标记为可疑；其三，产物一致性——编译产物的哈希必须与生成文本对应的源码一致，防止模型在文本里写一套、在文件里留另一套；其四，跨任务泄漏检查——若某任务的 kernel 源码与另一任务的参考实现高度相似，标记为可能抄袭。每条拦截线都有误报代价：随机化输入会让“针对特定形状优化”的合法策略被误判为不稳定，因此 harness 应把随机化输入与固定形状输入分成两组分别报告，而不是混在一起。

六 · 上线门与报告口径：把离线奖励接到端到端时延上

上线门的考点是“离线奖励与真实收益之间是否存在断点”。harness 不能只用 kernel 级加速比作为上线依据，因为端到端时延还包含 launch 开销、数据搬运、框架调度。具体机制是：对每个任务记录 kernel 级时间 t_k 与端到端时间 t_e，并计算覆盖率 c = t_k / t_e；只有当 c 足够高时，kernel 级加速才能传导到端到端。上线门应写成“t_e 的相对改善超过阈值且 c 不低于基线”的合取条件，而不是单看 t_k。

$$\text{gate}_{\text{online}}=\mathbb{1}\!\left[\frac{t_e^{\text{base}}-t_e^{\text{new}}}{t_e^{\text{base}}}>\delta\right]\cdot\mathbb{1}\!\left[c_{\text{new}}\ge c_{\text{base}}\right]$$

代价在于端到端测量本身：它要求把生成的 kernel 真正嵌入一个可运行的最小宿主程序，这引入了宿主代码的正确性风险——如果宿主写错，端到端数字全废。harness 的对策是把宿主程序也纳入版本控制与冒烟测试，并在报告中把“kernel 级”与“端到端级”两列并排给出，任何一列异常都能被立刻看到。报告口径上，必须固定随机种子、驱动版本、编译器版本、GPU 型号与时钟策略，并把它们写进结果文件的头部；跨版本比较时，头部不一致的结果不得合并统计。一个具体例子：同一份 kernel 在锁频与不锁频两种设置下，端到端改善可能一个为正一个为负，若不记录时钟策略，上线门会给出互相矛盾的结论。

最后落在工程判断上：这套 harness 的验收口径不是“跑通”，而是“任意一条轨迹都能被追溯到轮次级、任意一个奖励项都能被单独关闭、任意一次上线决策都能被复现”。做到这三点，题干里的“可复现”才从口号变成配置项；做不到，多轮 RL 的奖励曲线再好看也无法归因到结构项或性能项中的任何一项。

评测 harness 的边界：何时这套多轮 RL 奖励结构会失效

该方案的评测 harness 有三个硬边界，越界即失效。第一，正确性门必须独立于奖励函数：多轮 RL 的结构奖励与性能奖励都由同一套静态分析加 profile 管线产生，若正确性 oracle 也复用该管线，则策略可以学到“让分析器满意”而非“让 kernel 正确”，此时 harness 的通过率不再具备判别力。第二，输入分布必须与训练分布解耦采样，否则多轮交互中的反馈会退化为对固定 shape 的记忆，性能奖励的方差被压缩到接近零，梯度信号消失。第三，防作弊门要覆盖编译期与运行期两侧：仅检查输出张量相等无法拦截“缓存上一次结果”“按 shape 查表返回预编译 kernel”这类策略，必须叠加源码哈希、PTX/SASS 指纹与首次调用时延的联合校验。

失效条件的量化判据可写成门控不等式：设正确性通过率为 $$P_c$$、性能奖励相对基线的加速比为 $$S$$、防作弊命中率为 $$P_f$$，则上线门要求 $$P_c \ge \tau_c,\ \mathbb{E}[S] \ge \tau_s,\ P_f \le \tau_f$$ 同时成立；任一条件单独达标而其余不达标，说明奖励被单维度劫持，harness 应判定为不可信而非部分可信。典型失效例子：策略在固定 batch 下把 shared memory 占用压到极低从而通过结构奖励，但换到长序列输入时因 occupancy 不足导致时延翻倍，此时 $$S$$ 的分布出现双峰，均值达标而尾部崩溃，必须用分位数门替代均值门。

系统代价集中在三处：正确性 oracle 的形式验证（如 SMT 求解等价性）随 kernel 规模增长呈超线性，单次验证的编译时间可能超过多轮 RL 单步采样时间，使 harness 吞吐受限于验证端而非生成端；NCU/SASS profile 采集引入的时延抖动会污染性能奖励，需固定采集窗口并对多次采样取中位数；输入分布解耦采样要求每个评测点重新生成数据，显存占用随分布宽度线性上升，在长上下文 kernel 上会成为 OOM 主因。工程判断是：把形式验证限制在候选集的前若干名而非全量，用分层抽样替代全分布覆盖，以可控的验证召回损失换取 harness 的可运行吞吐。
