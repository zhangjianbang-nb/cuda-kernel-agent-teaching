一 · 题干的三层结构与“问题驱动”的可评测化

《Ask, Don't Equip》这个标题本身就是一个可拆的命题：它主张 coding agent 在深度 kernel 优化里，不应被一次性塞满工具与上下文（equip），而应由问题驱动（ask）——agent 主动向环境/评测器/自身历史提出结构化问题，再据此决定下一步动作。要把这套方法做成可复现 harness，第一步不是写代码，而是把题干拆成三层可判定的对象：方法层（question 的生成、选择、回答闭环）、任务层（kernel 优化的输入分布与目标）、验收层（什么叫“优化成功”且“没有作弊”）。三层各自对应不同的考点，混在一起谈就会导致 harness 既测不出方法增益、也拦不住 reward hacking。

方法层的考点是“问题是否真的改变了动作分布”。一个 question-driven agent 的最小闭环可写成：给定当前 kernel 状态 s（源码、编译结果、profile 片段），agent 产生问题集合 Q(s)，环境返回回答 A(Q,s)，策略据此采样动作 a ~ π(· | s, A)。可评测的关键不是问题文本好不好看，而是回答是否携带了 s 中不可直接读出的信息。若 A 只是把 s 复述一遍，则 ask 与 equip 在信息论上等价，方法增益为零。因此 harness 必须记录每次 ask 的“信息增量”，最粗的代理是回答前后动作熵的变化，或回答所引用的新事实条数（例如 NCU 计数器里此前未被读取的 metric）。这是考点一，也是后面所有基线与门禁设计的锚点。

任务层的考点是输入分布的可控性。KernelBench 系基准的价值在于它把“算子 + 形状 + dtype”组合成可枚举的样本空间，但深度优化恰恰发生在分布边缘：非常规 shape、非对齐 stride、混合精度、batch 极小或极大。harness 若只取默认形状，agent 会学到“针对一个点调参”而非“针对一族问题推理”。这里需要一个显式的分布参数化，例如按 (op, shape regime, dtype, layout) 四元组分层采样，并规定每层的最小样本数与权重。代价是评测时延：分层采样意味着同一 op 要被多次编译与计时，编译时间在 Triton/CuTe 路径上尤其显著，单样本从“一次编译”变成“每 regime 一次编译”，这是 harness 预算里必须显式记账的一项。

$$\text{Cost}_{\text{eval}} = \sum_{g \in G} n_g \cdot \big( T_{\text{compile}}(g) + T_{\text{run}}(g) + T_{\text{verify}}(g) \big)$$

其中 G 是分层集合，n_g 是该层样本数。这个式子不是装饰：它决定了你能不能在固定 token/时延预算内同时覆盖“方法增益”和“分布鲁棒性”。一个具体例子：对同一个 reduction 算子，若只测 N=4096 的对齐 fp32，agent 可能靠固定 tile size 就拿到加速；但一旦加入 N=4097 的非对齐与 fp16 混合，同一份 tile 假设会触发边界分支与额外的 mask 计算，正确性门与性能门同时收紧。harness 若不把这两类样本分开记账，就会把“过拟合单点”误判为“深度优化能力”。

二 · 正确性 oracle 的分级：从逐元素到形式化边界

正确性门是防作弊的第一道闸，但它不能是一刀切的 allclose。深度 kernel 优化的常见“合法近似”包括：改变累加顺序（浮点非结合性）、使用 TF32/bf16 中间量、融合后引入不同的舍入路径。若 oracle 过严，会误杀真实优化；过松，则 agent 可以用“降精度换速度”刷分。可执行的做法是分级 oracle：L0 逐元素严格比对（用于整数索引、mask、边界逻辑）；L1 带容差的数值比对，容差按 dtype 与归约长度参数化；L2 统计等价（分布矩、分位数）用于长归约；L3 形式化/符号检查，仅用于可判定的子集（如 affine index 映射、无数据竞争的共享内存布局）。

L1 的容差不能拍脑袋，要写成可复算的公式。对长度 n 的浮点归约，误差上界随 n 增长，常用形式是相对误差界 γ_n = n·u/(1-n·u)（u 为机器 epsilon 的一半量级），再乘以一个安全系数 k。harness 应把 k 作为显式配置项而非硬编码，因为不同 op 的 condition number 差异极大。代价是：容差越宽，越容易放过“偷偷降精度”的作弊；容差越窄，越容易把合法的重排归约判错。这个 trade-off 必须由人来定，并在验收口径里写清楚“本 harness 接受的最大 k”。

$$\text{pass}_{L1} = \big[\, \lVert y_{\text{agent}} - y_{\text{ref}} \rVert_\infty \le k \cdot \gamma_n \cdot \lVert y_{\text{ref}} \rVert_\infty \,\big]$$

L3 是防作弊的关键补充。很多 reward hacking 不体现在数值上，而体现在“计算根本没发生”：例如 agent 发现参考实现可被缓存复用，或直接把输入映射到预计算的查表。形式化检查可以针对 kernel 的索引表达式做符号验证——证明输出索引覆盖了全部输入元素且无重复写。对 CuTe/PTX 路径，这可以退化为对 layout 的静态断言（stride、cosize、alignment 的组合是否与声明一致）。代价是工程复杂度：形式化工具对动态 shape 与数据依赖分支支持有限，harness 只能对“可判定子集”启用 L3，其余样本回落到 L1+L2，并在报告中标注覆盖率，而不是假装全覆盖。

一个具体例子：一个 softmax kernel 的 agent 版本把最大值减法省略，改用 clamp 近似。L1 在常规输入下通过（数值差异在容差内），但 L2 的分布矩检查在极端输入（全负大值）下暴露了溢出。这说明单级 oracle 不够，分级 + 分层输入才能把“近似”与“错误”分开。正确性门的验收口径应写成：每层样本必须通过其对应级别，且 L3 覆盖率不低于配置阈值——覆盖率本身是报告项，不是通过项，避免为了数字好看而虚报可判定性。

三 · 防作弊的四个面：输入、缓存、计时与提交物

防作弊不能只靠“看代码”，要把它拆成可执行的检查面。第一面是输入面：agent 不得读取参考输出、不得访问测试集标签、不得在编译期把输入形状硬编码成常量表。可执行检查包括：在 harness 侧对输入做随机化扰动（同分布内换 seed），并要求 agent kernel 在扰动后仍通过；静态扫描源码中是否出现与测试 shape 完全一致的魔法常量。代价是每增加一次扰动就多一轮编译+运行，时延线性增长，因此扰动次数应作为预算项而非无限加码。

第二面是缓存面：禁止跨样本复用编译产物或结果。harness 应为每个样本分配独立的编译目录与进程隔离，并在计时前清空 L2 之外的持久缓存（如 Triton 的 kernel cache）。这里有一个容易被忽略的代价：清缓存会让首次调用的编译时间计入时延，若 harness 用“预热后计时”掩盖它，就等于允许 agent 把编译成本外部化。验收口径应明确区分 T_{\text{cold}} 与 T_{\text{warm}}，并规定性能门用哪一个。

第三面是计时面：agent 不能通过异步流未同步、事件记录位置错误、或把计算挪到计时窗口外来伪造加速。可执行做法是 harness 自己持有 CUDA event 与同步点，agent 只提交 kernel 启动，不控制计时边界；同时用 NCU 的 kernel duration 做交叉校验，两者偏差超过配置阈值即判为计时异常。代价是 NCU 采集本身有开销（ replay 与计数器多路复用），不能对每个样本全量开启，只能按分层抽样开启，这又回到第一节的预算公式。

第四面是提交物面：最终提交必须是可独立编译的源码 + 声明式元数据（dtype 支持、shape 约束、是否使用近似）。元数据用于自动选择 oracle 级别：声明了近似的样本走 L1/L2，未声明却数值偏离的走失败。这一面把“诚实声明”变成可验证契约，而不是靠人工审阅。一个具体例子：agent 提交了一个使用 bf16 累加的 layernorm，元数据声明“允许 bf16 中间量”，harness 据此放宽 L1 容差并启用 L2；若它未声明却实际用了 bf16，L0/L1 会直接失败。代价是元数据本身可能被滥用（声明过宽），因此需要一个白名单：只有预注册的近似类型才被接受，白名单之外的声明一律拒绝。

四 · 基线设计：三层对照与“问题增益”的隔离

没有正确基线，任何“方法有效”的结论都不可信。针对 question-driven 方法，基线至少要三层：B0 无工具单轮（agent 只看题面与参考实现，一次生成）；B1 equip 全量上下文（把 profile、文档、历史一次性塞入，不给提问接口）；B2 ask 但回答受限（允许提问，但环境只返回 s 中已有信息，用于检验“提问本身”是否只是增加了 token）。三层基线共享同一输入分布、同一正确性门、同一计时口径，唯一变量是信息获取方式。这样“问题增益”才被隔离出来：Δ = metric(B_ask) − metric(B_equip)，而不是与无工具基线比出来的虚高差值。

B2 的设计尤其关键，它直接对应第一节的信息增量考点。若 B2 与 B_ask 表现相同，说明增益来自“多轮交互带来的额外 token/尝试次数”，而非“问题驱动”；若 B2 明显低于 B_ask，才说明回答携带了新信息。代价是 B2 需要环境实现一个“受限回答器”，它要能判断哪些信息已在 s 中——这本身是一层工程，且判断错误会污染结论。可执行的折中是：B2 的回答器只做字符串级检索（在 s 的文本里找答案），命中则返回原文，未命中则返回“不可用”，并记录命中率作为解释变量。

基线的验收口径还包括预算对齐：三层基线的 token 预算、编译次数、wall-clock 时延应尽量对齐，否则“ask 多花了三倍 token 所以更好”就无法归因。对齐不是绝对相等，而是把预算作为协变量记录，并在报告中给出“等预算下的 metric”与“等时延下的 metric”两个口径。一个具体例子：在同一个 matmul 样本上，B1 一次性拿到完整 NCU 报告后直接改 tile；B_ask 先问“当前 occupancy 瓶颈在寄存器还是共享内存”，得到回答后再决定改 tile 还是改流水。若两者最终性能接近，但 B_ask 的编译次数更少，则增益体现在“搜索效率”而非“峰值性能”，验收口径必须能表达这种差异，而不是只报一个加速比。

五 · 上线门：性能、正确性与可复现性的联合判据

上线门不是“跑分超过阈值”，而是三个判据的联合：性能门、正确性门、可复现门。性能门应相对基线而非绝对数字，且必须声明比较对象（B0/B1/B2 中的哪一个）与计时口径（cold/warm）。正确性门沿用第二节的分级 oracle，并要求 L3 覆盖率报告。可复现门要求同一配置在固定 seed 下重复运行，metric 的离散度在配置阈值内；对 GPU kernel 而言，计时抖动主要来自频率与占用竞争，harness 应固定 clock 或至少记录频率作为协变量，否则复现门会变成噪声门。

联合判据可以写成一个合取式，任何一项失败即不上线：

$$\text{ship} = \text{perf}(m \ge \tau_p \mid \text{baseline}=B,\ \text{timer}=w) \wedge \text{correct}(L_0..L_2 \text{ pass},\ L_3 \text{ cov} \ge \tau_c) \wedge \text{repro}(\sigma/\mu \le \tau_r)$$

三个阈值 τ_p, τ_c, τ_r 都是配置项，必须随 harness 一起版本化。这里有一个工程判断：τ_p 不应设成“相对 B1 提升 X%”，因为 B1 本身可能被 equip 的上下文长度拖累；更稳的做法是同时报告相对 B1 与相对 B2 的提升，并要求至少一个口径达标。代价是报告复杂度上升，但换来的是结论不被单一基线绑架。

上线门还要处理“性能提升但正确性降级”的灰色地带。可执行的做法是引入风险分级：若样本声明了预注册近似且 L1/L2 通过，则允许上线但标记为“近似路径”；若未声明近似却只通过 L2，则拒绝。这把“是否可接受”从主观判断变成白名单+分级 oracle 的机械判定。一个具体例子：一个使用 TF32 的卷积 kernel 在 L1 下失败但在 L2 下通过，若元数据声明了 TF32，则走近似路径上线并附带精度说明；若未声明，直接拒绝，无论加速比多高。这一条是防作弊与上线门的交汇点，也是 harness 最容易被绕过的地方——因此元数据白名单必须由 harness 维护，而不是 agent 自填。

最后落在具体机制上：这套 harness 的可执行配置应包含四个版本化文件——输入分布清单（分层与权重）、oracle 分级表（每层对应的 op 与容差参数 k）、防作弊检查清单（四面的开关与阈值）、上线门判据（τ_p, τ_c, τ_r 与基线选择）。验收口径写成“每个样本必须产出 (metric, oracle 级别, 计时口径, 复现离散度, 元数据声明) 五元组”，任何缺失字段即视为无效样本而非通过。这样 question-driven 方法的增益才能被归因到“提问带来的新信息”，而不是被缓存、计时或未声明近似悄悄污染。

提问式 harness 的失效边界与系统代价

把“提问驱动”接进评测 harness，最先要承认它的失效条件不是模型答错，而是问题本身不产生信息增益。若 agent 的提问落在题干已显式给出的约束上（例如题面已写明 dtype、shape 范围），则每轮问答只增加 token 与时延，正确性门不变、优化空间不变。可操作的判据是给每轮提问算一个信息增益近似：

$$\Delta H = H(\text{search space}\mid \text{context}) - H(\text{search space}\mid \text{context}\cup q)$$
当 $\Delta H$ 低于阈值时该问应被 harness 判为无效并计入“无效提问率”，作为防作弊指标之一——否则 agent 可以靠堆提问刷交互轮次而不改进 kernel。

第二个边界是提问与执行反馈的耦合成本。每次提问后若触发一次编译+profile 才能回答，单轮代价就从 token 级跃到秒级：一次 Triton 编译加一次 NCU 采集的墙钟时间远高于一次 LLM 调用，而显存占用在 profile 期间被独占，无法与基线并发跑。因此 harness 必须把“可离线回答的问题”（读题即可答）与“需执行才能答的问题”分流，前者走缓存、后者进串行队列，否则基线对比会被排队噪声污染。

第三是正确性门与提问的相互作用。提问式 agent 倾向于先问清边界再写码，这会推迟首次正确性检查的时点；若 harness 只在最终提交时验正确性，错误会累积到最后一轮才暴露，回滚成本高。配置上应设“每 N 轮强制一次正确性 oracle 快照”，N 取小值以限制错误传播，代价是 oracle 调用次数上升、总 token 与编译次数增加。

失效条件可观测信号harness 代价
提问无信息增益无效提问率上升token 与时延白耗
提问需执行才可答单轮墙钟时间跃升显存独占、基线串行化
正确性检查后置末轮才暴露错误回滚与重跑成本

工程判断落在验收口径上：上线门不应只看最终 kernel 的 SOL 或 roofline 位置，还要把无效提问率、每轮平均墙钟时间、正确性快照次数一并纳入，否则“提问驱动”会被优化成“多问少改”的刷分策略，而真实优化能力并未提升。
