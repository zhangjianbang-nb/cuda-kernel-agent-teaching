一 · 题干到底在问什么：把“pipeline”拆成可判定的四段

这道题的题干只有一句话，但它同时埋了三个约束。第一，“从输入到评测”限定了回答的边界——不要从模型预训练讲起，也不要延伸到部署后的 A/B 实验，起点是待优化 kernel 的规格输入，终点是评测结论。第二，“按一次 kernel 生成—编译—运行—评测的顺序”给出了强制的叙述骨架，四个阶段必须一一对应，不能合并成“生成并验证”这种模糊段落。第三，“每一步的输入、输出和失败模式”是三问结构，意味着每个阶段都要给出三元组，缺一不可。真正的考点不在“知道 KernelClaw 有哪些 agent”，而在于能否把多 agent 框架的抽象还原成一条**数据流**：什么对象在阶段之间传递、传递时携带哪些字段、哪个字段缺失会导致下游无法判定。

拆题时最容易犯的错是把“失败模式”写成“可能出错”。失败模式必须是**可观测的判据**：编译阶段失败模式的判据是编译器返回非零退出码并附带诊断信息；运行阶段的判据是进程异常终止或输出与参考实现超出容差。判据不明确，评测阶段就无法把失败归因到具体阶段，多轮迭代就会退化成盲目重试。因此本题的隐含考点是：**失败模式必须与阶段边界对齐**，即每个失败模式都能唯一地归属到某一个阶段的输出上。这也是 dual-memory 机制存在的理由——历史失败若不能按阶段归档，就无法在下一轮生成时被检索和规避。

解题路径建议按“先定对象、再定判据、后定回路”三步走。先定对象：列出四个阶段各自的输入输出对象及其关键字段（源码文本、编译产物、运行轨迹、评分向量）。再定判据：为每个阶段写出通过/失败的最小判定条件，并标注该判据依赖哪些字段。后定回路：说明失败信息如何回流到生成阶段，回流时携带的是原始诊断还是结构化摘要。这条路径的价值在于，它把“多 agent 协作”从角色叙事转成了接口叙事——agent 之间的契约就是阶段之间的数据契约。

一个具体例子可以校准粒度：假设输入是一个逐元素加法 kernel 的规格（张量形状、dtype、参考语义）。生成阶段的输出不是“一段 CUDA 代码”，而是“代码文本 + 声明的 launch 配置 + 假定的输入约束”三元组；若只输出代码文本，编译阶段就无法判断 grid 维度是否越界，运行阶段也无法构造合法输入。这个例子说明：题干问的“输出”不是单数对象，而是**带元数据的产物**。代价方面，元数据越丰富，生成阶段的 token 开销越高——每增加一个必须显式声明的字段，解码长度就增加，而解码长度直接线性推高单轮时延；这是本题在工程判断上必须点明的取舍。

二 · 生成阶段的考点：规格到源码的映射与可编译性前置约束

生成阶段的输入是 kernel 规格，通常包含算子语义、张量形状与 dtype、目标硬件架构、以及性能目标（例如相对基线实现的加速比诉求）。输出应是可被编译器接受的源码及其附属声明。这里的核心考点是**可编译性前置约束**：生成 agent 在写出第一行代码前，必须已经把架构相关的约束（共享内存上限、warp 数量、寄存器压力）纳入决策，而不是留给编译器报错后再修。KernelClaw 的多 agent 分工在此处的意义是把“写代码”和“审约束”拆开：一个 agent 产出候选实现，另一个 agent 依据规格检查 launch 配置与资源占用是否自洽。这种拆分的代价是通信开销——每轮生成需要至少两次模型调用，token 消耗翻倍，端到端时延随之上升；收益是把编译失败从“事后修补”前移为“事前过滤”。

形式上，生成阶段可以写成一个带约束的采样问题：给定规格 s 与历史记忆 M，采样源码 c 使其满足一组静态约束集合 C(s)。

$$c \sim p(\cdot \mid s, M), \quad \text{s.t. } \forall\, \kappa \in C(s):\ \kappa(c) = \text{true}$$

这里的 C(s) 不是编译器，而是可在解码期或解码后立即检查的轻量判据，例如“block 维度不超过架构上限”“共享内存声明量不超过规格给定上限”。把约束放在采样侧而非编译侧，换来的是更少的无效编译轮次；代价是每次候选生成都要跑一遍静态检查，检查本身消耗 CPU 时间，且约束写得过紧会压低候选多样性，导致搜索空间塌缩。这是一个明确的工程权衡点，答题时应指出而非回避。

失败模式在这一阶段有三类可判定形态。其一是**语义漂移**：生成的代码语法合法但实现的算子与规格不符，判据是后续运行阶段与参考实现的数值比对超差——注意这个失败在生成阶段无法被直接观测，只能被标记为“待验证”。其二是**约束违反**：静态检查不通过，可直接在生成阶段拒绝并回流。其三是**元数据缺失**：源码存在但 launch 配置或输入假定未声明，导致编译阶段无法构造编译单元、运行阶段无法构造输入。第三类最隐蔽，因为它在文本层面看起来“像是对的”。

具体例子：规格要求处理非连续布局的输入。生成 agent 若只写逐元素索引而忽略 stride 参数，代码可编译、可运行，但结果错误——这属于语义漂移，只能由运行阶段的 oracle 捕获。反过来，若 agent 声明了过大的共享内存 tile，静态检查即可拦截，省去一次完整编译。两类失败的处置路径不同，正说明失败模式必须按“能否在本阶段判定”分类，而不是笼统列一张错误清单。dual-memory 在此处的作用是把“曾因 stride 遗漏而失败”这类案例以结构化形式存入长期记忆，使下一轮生成在相似规格下主动带上 stride 处理，减少重复踩坑；其代价是记忆检索增加上下文长度，推高每轮 token 成本。

三 · 编译阶段的考点：诊断信息如何变成可回流的信号

编译阶段的输入是生成阶段的产物（源码 + 声明），输出是编译产物与诊断记录。考点集中在**诊断的结构化**：原始编译器输出是非结构化文本，直接塞回生成 agent 的上下文既浪费 token 又噪声大；必须抽取错误码、出错行号、涉及的符号与约束类型，形成一条可检索的记录。KernelClaw 的 dual-memory 在此处的分工是：短期记忆保存本轮诊断供立即修复，长期记忆沉淀“某类约束反复触发”的模式供跨任务复用。这个设计的性能代价是编译时间本身——每次候选都要真实调用编译器，编译时延与源码复杂度正相关，多候选并行编译会争抢 CPU 与显存以外的宿主机资源，成为流水线的吞吐瓶颈。

可以把编译阶段判定写成布尔函数：编译成功当且仅当退出码为零且产物可加载。

$$\text{ok}_{\text{compile}} = [\,\text{exit}(c) = 0\,] \wedge [\,\text{loadable}(\text{artifact})\,]$$

两个合取项对应两类不同的失败：前者是语法/语义/资源约束错误，后者是链接或 ABI 层面的问题（例如目标架构不匹配）。分开判定很重要，因为二者的回流内容不同——前者回流源码修复指令，后者回流构建配置修复指令。若合并成一个“编译失败”标签，生成 agent 会误以为要改代码，实际要改的是编译选项，多轮迭代就会在错误的方向上消耗预算。

失败模式的具体形态包括：语法错误（判据明确，行号可定位）、资源超限（寄存器或共享内存超出架构约束，诊断中通常带具体数值）、架构不匹配（编译目标与运行设备不一致）、以及模板实例化失败（在 CuTe 或模板化 kernel 中常见，诊断冗长且难以定位）。最后一类的处理代价最高：诊断文本可能长达数千 token，直接回流会挤占生成阶段的上下文预算，因此需要摘要策略——只保留首个致命错误的符号名与约束条件。摘要会丢失部分信息，可能导致修复不彻底，这是编译阶段必须承认的正确性代价。

具体例子：一个使用 CuTe 布局抽象的 kernel 在编译时因 tile 形状与线程布局不匹配而实例化失败。原始诊断包含完整的模板展开栈，若整段回流，单轮上下文即被占满；若只回流“布局 L 与线程数 T 不满足整除关系”这一条结构化摘要，生成 agent 就能定向修改 tile 尺寸。这个例子同时展示了机制（诊断抽取）、代价（摘要丢失细节带来的修复不彻底风险）与收益（token 预算可控）。答题时若只写“编译失败则重试”，就没有触及本题真正要考的接口设计问题。

四 · 运行阶段的考点：正确性 oracle 与性能测量的分离

运行阶段的输入是编译产物与构造好的输入数据，输出是运行结果、正确性判定与性能测量值。这里的核心考点是**把正确性与性能拆成两条独立的判定链**：正确性由 oracle 判定（与参考实现的数值比对，含容差），性能由计时或 profiler 判定（时延、带宽利用率、SOL 占比）。二者不能混在一个“通过”标签里，因为一个数值错误的 kernel 可能跑得很快，若只看性能就会把错误实现选为最优候选。KernelClaw 的评测环节必须先在正确性上过滤，再在通过的候选里排序性能，这个顺序不可颠倒。

正确性判定的形式化表达需要容差与覆盖度两个维度：

$$\text{pass} = \bigwedge_{i \in \mathcal{I}} \left| y_i - y_i^{\text{ref}} \right| \le \tau(\text{dtype}), \quad \mathcal{I} \text{ 覆盖边界与随机输入}$$

容差 τ 随 dtype 变化（浮点与整型的判据不同），覆盖集 I 必须包含边界情形（零长度、极端值、非对齐形状），否则 oracle 会给出假通过。假通过是运行阶段最严重的失败模式：它让错误实现进入性能排序，最终产出“快但错”的结论。其代价是评测可信度整体崩塌，且这种错误无法通过增加轮次修复，只能通过扩充覆盖集预防。覆盖集越大，运行阶段的总时延越高——每个输入都要跑一次参考实现与候选实现，参考实现的成本往往被忽略，但它是评测预算的固定开销。

性能测量的失败模式与正确性不同：测量噪声、缓存状态未控制、以及测量本身改变被测对象（profiler 插桩带来的开销）。判据是重复测量的离散度是否在可接受范围内，若离散度过大则测量无效而非 kernel 无效。这一区分直接影响回流内容：测量无效应回流“重测”指令，而不是“优化”指令。具体例子：一个小规模 kernel 的单次计时被启动开销主导，测得的时间主要反映 launch 时延而非计算时延；此时应改用批量调用或 profiler 的 kernel 级计时，否则性能排序会把“启动快”误判为“算得快”。这个例子说明运行阶段的输出必须携带测量方法元数据，否则评测阶段无法判断数值的可比性。

运行阶段还需处理异常终止：越界访存导致的进程崩溃是明确的失败判据，但它不产生任何数值输出，因此无法走数值比对路径。此类失败的回流信号应是“内存访问模式可疑”，并附带触发崩溃的输入形状，供生成 agent 定位索引计算。代价是崩溃复现需要重跑，且某些越界在特定硬件上不崩溃只返回脏数据——后者会伪装成正确性失败，增加归因难度。

五 · 评测阶段的考点：从单次结果到可比较的评分向量

评测阶段的输入是运行阶段产出的正确性判定与性能测量，输出是候选之间的排序与归因结论。考点是**可比性**：不同候选的性能数字只有在相同测量方法、相同输入集、相同硬件状态下才能比较。KernelClaw 的评测不能只输出一个加速比数字，而要输出一个带条件的评分向量——正确性通过率、时延、带宽利用率、以及测量置信度。缺少置信度字段，排序就无法区分“真实领先”与“噪声波动”。

排序规则可以写成带硬约束的字典序：先按正确性过滤，再按性能排序。

$$\text{rank}(c) = \begin{cases} \text{valid}, & \text{pass}(c) \\ \text{by perf}(c), & \text{otherwise} \end{cases}$$

这个规则看似平凡，但它的工程含义是：任何性能优化都不得以牺牲正确性为代价，评测阶段必须拒绝“用容差放宽换取速度”的候选。失败模式在此阶段表现为归因错误——把编译失败计入生成质量、把测量噪声计入 kernel 质量。归因错误的代价是 dual-memory 被污染：错误的因果关联被写入长期记忆，后续任务会继承错误的先验，导致系统性偏差。因此评测阶段的输出必须携带阶段标签，使每条记忆都能追溯到具体阶段。

具体例子：两个候选在同一输入集上时延相近，但其中一个仅在部分形状上通过正确性。若评测只报告平均时延，二者会被视为等价；若报告评分向量（通过率 + 时延 + 覆盖集），前者因通过率不足被排除。这个例子说明评测阶段的输出粒度直接决定选择质量。代价方面，评分向量字段越多，存储与检索成本越高；长期记忆若保存完整向量，检索时的相似度计算开销上升，而若只保存标量摘要，又会丢失归因所需的阶段信息。这是一个必须显式取舍的设计点。

评测阶段还要处理跨轮次的预算问题：多轮迭代中，每轮都产生编译、运行、评测开销，总预算随时延线性增长。若评测阶段不能快速淘汰明显失败的候选，预算就会消耗在无望的修复上。因此淘汰判据应尽量前置——能在编译阶段判定的不要留到运行阶段，能在运行阶段正确性过滤中判定的不要留到性能排序。这条“判据前置”原则是本题在工程判断上的落点：pipeline 的分段不是为了叙述清晰，而是为了把失败尽早拦截，把昂贵的测量留给真正有希望的候选。

六 · 解题路径的收束：公式清单与答题时应避免的三种写法

把上述四段串起来，解题所需的公式清单是四项：生成阶段的约束采样式（规格与记忆条件下的带约束采样）、编译阶段的合取判定式（退出码与可加载性）、运行阶段的容差与覆盖合取式（数值比对与输入覆盖）、评测阶段的字典序排序式（正确性优先于性能）。这四个式子分别对应四个阶段的“通过”定义，答题时按阶段逐一给出输入、输出、失败模式，并用对应式子说明判据来源，就能覆盖题干的全部要求。公式的作用不是装饰，而是把“失败模式”从形容词变成可判定的谓词——这是本题评分的关键区分点。

需要避免的第一种写法是把 agent 角色当作阶段。题干问的是数据流阶段，不是组织架构；写“规划 agent 输出计划、编码 agent 输出代码”只是把 pipeline 换成了角色表，没有回答输入输出对象是什么。第二种写法是把失败模式写成原因列表，例如“生成失败可能因为模型能力不足”。这不是判据，无法在流水线中被检测。第三种写法是跳过评测阶段的归因问题，直接把评测等同于“算个加速比”。归因错误会污染 dual-memory，这一点是本题的深层考点，遗漏它会让答案停留在流程描述层面。

从工程判断上收束：这条 pipeline 的设计张力在于**判据前置与信息完整性之间的取舍**。判据越前置，失败拦截越早、预算越省，但前置判据只能看到局部信息（例如静态检查看不到数值语义），因此会漏放一些错误到下游；判据越靠后，信息越完整，但每次判定的成本（编译时间、运行时间、参考实现开销）越高。KernelClaw 的 dual-memory 机制本质上是在这个张力上做补偿：把前置阶段漏放的失败以结构化记忆的形式保留，使后续轮次能在生成侧提前规避，而不是靠增加下游判定次数来兜底。答题时若能指出这条张力并给出具体的字段设计（诊断摘要、测量方法元数据、阶段标签），就已经越过了“复述流程”的层次，落到接口与代价的层面。
