一 · 题干的三层结构：把一句话拆成可执行的校验任务

「防作弊合约校验」这个题面在字面上只给了一个动作，但它实际上压了三层可分离的工程任务，读题的第一步是把这三层拆开，否则后面所有公式都会失去落点。第一层是合约语义层：被校验的对象不是一段孤立的 kernel 代码，而是一份「合约」——即提交方对自身 kernel 行为作出的可观测承诺，例如「在给定输入域上输出与参考实现逐元素一致」「不读取越界地址」「不引入未声明的全局同步」。第二层是作弊面层：校验算法要防的不是随机 bug，而是针对评测口径的定向规避，典型形态包括对 benchmark 输入做特判、缓存上一次结果、把计算挪到 host 端、用低精度近似冒充精确、在计时区间外做预热。第三层是预算层：校验本身要花时间、花显存、花编译次数，而搜索（多轮生成—评测循环）的总预算有限，校验强度与搜索广度是直接竞争关系。

读题时必须意识到：题目问的不是「如何写一个 assert」，而是「给定一份合约，如何用一个可计算的校验强度去约束搜索过程」。这意味着答案里必须出现一个把「校验覆盖度」映射到「搜索预算」的量，而不是罗列检查项。考点因此落在三处：合约的形式化表达是否足以排除特判类作弊；校验算法的采样策略是否能在有限预算下逼近全覆盖；以及校验失败时对搜索树的剪枝是否可逆、是否会把正确候选误杀。

二 · 核心公式的逐项定位：校验强度是一个可分解的乘积

这类题的标准骨架是一个「通过概率」公式，把单次校验的漏检率沿搜索轮次累乘，再与预算约束联立。写成可讨论的形式：

$$P_{\text{escape}}(N, k, \varepsilon) = \bigl(1 - (1-\varepsilon)^{k}\bigr)^{N}$$

逐项解释必须落到工程含义上，而不是符号游戏。ε 是单次校验对「一个作弊候选」的漏检率，它由采样输入域与合约断言的联合覆盖决定：若合约只声明了形状约束而没声明数值域，ε 就退化为接近 1，因为特判型作弊只要识别出「这不是 benchmark 的那批张量」就能全身而退。k 是单次校验内独立采样的输入个数，注意它乘的是 (1−ε) 的指数，而不是 ε 本身——这决定了提高 k 的边际收益是递减的，从 k 到 2k 带来的漏检下降远小于线性。N 是搜索轮次中被校验放行的候选总数，外层指数意味着只要 N 足够大，任何非零漏检率都会被放大成「至少放行一个作弊者」的高概率。这个公式的考点在于：它把「校验算法设计」和「搜索预算分配」放进同一个不等式，读者必须能指出三个变量中哪个是算法可控的、哪个是预算可控的。

与之配套的预算约束通常写成校验开销与搜索开销的加和不超过总预算：

$$C_{\text{total}} \ge N \cdot \bigl(c_{\text{gen}} + k \cdot c_{\text{check}}\bigr) + c_{\text{compile}}$$

其中 c_check 是单次输入校验的时延（含 kernel 启动、参考实现比对、必要时 NCU 采样），c_compile 是候选编译的一次性成本。这里的性能代价非常具体：k 增大直接线性拉高单轮校验时延，而 N 增大则线性拉高编译次数——编译是搜索循环里最贵的一项，因为每个候选都要走一遍 nvcc 或 Triton 编译，且编译时间与模板实例化深度正相关。工程判断因此不是「把 k 拉满」，而是在固定 C_total 下解一个 k 与 N 的权衡：由于 P_escape 对 N 是指数敏感、对 k 是多项式敏感，通常应优先压 N（即提高单候选的淘汰率）而非盲目堆 k。

三 · 具体算例：一个特判型作弊候选如何吃掉搜索预算

设某轮搜索产生一个候选 kernel，它在合约声明的「输入形状为 (M, K) × (K, N)、dtype 为 fp16」范围内行为正确，但内部含有一个分支：当检测到 K 等于 benchmark 固定值 4096 时走快速路径，否则回退到一段朴素实现。合约若只校验形状与 dtype，ε 接近 1；若合约追加了「对 K 在声明区间内随机取值」的断言，则该候选在 K≠4096 时暴露回退路径——回退路径虽然数值正确，但性能远低于声明，于是「性能合约」被违反。这个例子的价值在于它同时触发两类考点：正确性 oracle 无法仅靠逐元素比对抓住它（因为回退路径也是对的），必须引入性能合约，即把实测时延与 roofline 上界或 SOL 比例作为断言的一部分。

把它代入预算：假设单候选生成与编译合计占用一轮预算的主要部分，k 次校验每次需要一次参考比对加一次计时。若把 k 从较小值提升，单轮校验时延线性上升，可用于生成新候选的轮次 N 相应下降。这里出现一个反直觉的结论：对于特判型作弊，提高 k 的收益远大于提高 N，因为作弊者对固定输入的识别是确定性的，随机化 k 个输入能直接击穿其分支；而对于随机性 bug（如竞态、越界读），提高 N 更有效，因为需要更多候选样本才能撞上触发条件。因此算例的真正考点是按作弊面类型分配 k 与 N，而不是套一个统一参数。

代价还体现在显存上：k 个独立输入若同时驻留以保证比对吞吐，显存占用随 k 线性增长；若改为流式逐个校验，则时延受限于每次 kernel 启动与同步的固定开销，在 k 较大时启动开销占比上升，校验的有效算力利用率下降。这是一个典型的带宽/时延权衡，读题时应能指出「k 的提升不是免费的，它要么吃显存要么吃启动开销」。

四 · 解题路径：从合约形式化到剪枝决策的调用链

题目要求的路径不是直接写校验代码，而是给出「调用哪些公式、按什么顺序调用」。第一步是把合约写成三元组：输入域 D、输出断言 A、性能断言 R。输入域必须显式给出随机化维度（形状、dtype、数值分布、边界值），这是压低 ε 的唯一杠杆。第二步是选定 oracle：正确性用参考实现逐元素比对（注意浮点容差要与 dtype 匹配，fp16 的容差不能沿用 fp32 的阈值），性能用实测时延对照 roofline 预测，形式验证只在断言可归约为有界整数或线性约束时启用，否则编译时间成本会吞掉预算。第三步才是代入上面的 P_escape 与 C_total 两式，解出在当前预算下可接受的 (k, N) 组合，并据此设定剪枝规则。

剪枝规则本身要可逆：一次校验失败不应永久剔除候选，因为失败可能来自校验器自身的采样偏差（例如随机输入恰好落在参考实现的数值不稳定区）。工程上常见的做法是给每个候选维护一个失败计数，只有连续多次失败且失败模式一致时才剪枝，这样把误杀率控制在可接受范围，代价是每个候选多消耗若干次校验预算。这一步的考点是：剪枝的激进程度直接改变有效 N，而有效 N 又回到 P_escape 公式里，形成一个需要联立求解的闭环，不能把剪枝当作事后补丁。

需要调用的公式清单因此是：漏检率累乘式（决定 k 的下界）、预算加和式（决定 N 的上界）、以及 roofline 或 SOL 比例式（把性能断言变成可计算的阈值，而不是主观判断）。三者缺一，答案就会退化成「多测几次」的空话。

五 · 上线判断的接口：校验结论如何变成发布决策

题干后半问「如何影响上线判断」，其接口是把 P_escape 与一个业务可接受的风险阈值对齐。上线判断不是「校验通过就发布」，而是「在给定 N 与 k 下，残余作弊概率低于阈值才发布」。这要求把 P_escape 的计算结果显式写进发布门槛，并且记录本次搜索实际消耗的编译次数与校验时延，作为下次预算分配的依据。一个具体机制是：对每个通过校验的候选，额外跑一次与 benchmark 分布不同的「留出输入」校验，若留出集上性能断言不成立则拒绝上线——这一步的代价是一次额外编译与计时，但它把 ε 中「对 benchmark 过拟合」的那一部分单独压下去，属于性价比最高的单项投入。

上线判断还需要区分两类失败：正确性失败是不可协商的一票否决，性能失败则允许在 SOL 比例阈值内带条件上线（例如仅在特定形状下启用）。这个区分直接影响剪枝策略与预算：正确性校验必须覆盖全部随机化维度，性能校验可以按形状分层抽样以节省 k。把这条分层规则写进解题路径，才能体现「校验强度按风险分层」而非一刀切。

最终落在工程判断上：防作弊合约校验的核心不是把 ε 压到零（那需要穷举输入域，编译与校验预算都不允许），而是让 P_escape 在预算约束下可计算、可审计，并把 k 与 N 的分配依据作弊面类型显式化。一个候选能否上线，取决于它的残余漏检概率是否落在阈值内，以及它的性能断言是否在留出输入上复现——这两条都是可写成公式、可代入算例的量，而不是评审者的主观印象。

校验合约的边界：公式在哪一步开始失真

把「防作弊合约校验」拆成可执行的三段：题干给出的是被校验对象（合约代码或算子实现）与约束集合；考点落在三处——第一，核心公式的每一项是否都能在编译期或运行期被独立观测；第二，给定算例下公式输出的量纲是否与搜索预算同量纲；第三，公式的失效条件是否被显式写进合约，而不是留给调用方默认成立。解题路径因此不是「代入算例求值」，而是先做量纲对齐，再做单调性检查，最后做边界反例构造。需要调用的公式是校验残差与预算映射的复合式：

$$R = \sum_{i} w_i \cdot \big| f_i(\theta) - \hat{f}_i \big|, \qquad B = B_0 \cdot \exp(-\lambda R)$$

其中 $f_i$ 是第 $i$ 项可观测指标（如共享内存占用、分支发散度、访存合并率），$\hat{f}_i$ 是合约声明的阈值，$w_i$ 是该项在合约中的权重，$R$ 是加权残差，$B$ 是由残差折算出的剩余搜索预算。考点在于：$w_i$ 的选取若与 $f_i$ 的观测噪声同阶，则 $R$ 的符号会在多次 profile 之间翻转，此时 $B$ 的指数衰减把微小残差差放大成预算的成倍跳变——这是公式的第一处失真边界，即权重未做噪声归一化时，校验结论不可复现。

第二处失效条件在 $\lambda$ 的标定。$\lambda$ 必须由合约自身的容差反推：若合约允许 $R \le R_{\max}$ 即判通过，则 $\lambda$ 应满足 $\exp(-\lambda R_{\max})$ 落在预算下限之上，否则一个刚好达标的算例会被折算成近乎零预算，搜索被迫终止。给定算例：某实现的三项残差分别为共享内存超限、合并率不足、分支发散超标，权重按合约声明取定后 $R$ 落在 $R_{\max}$ 附近；此时若 $\lambda$ 偏大，$B$ 跌破单轮编译加一次 NCU profile 的成本线，系统表现为「校验通过但无法继续搜索」。代价是显性的：一次 NCU profile 的时延与显存快照占用构成预算的下界，$\lambda$ 标定错误会让这部分开销被重复支付而得不到新信息。

第三处边界是公式对离散指标的失效。合并率、发散度这类指标在 tile 尺寸跨越边界时呈阶跃变化，$f_i$ 对 $\theta$ 不连续，残差的绝对值在阶跃点两侧不可微，基于梯度的预算调整会在此处震荡。工程判断是：把离散项从 $R$ 中剥离，改为硬约束（布尔门），只让连续项进入指数映射；下表给出三类项的处理归属。

项类型观测方式进入 $R$失效表现
连续（占用、带宽）编译期静态 + profile是，需噪声归一权重失配致符号翻转
离散（tile 阶跃）编译期枚举否，作硬门梯度震荡
语义（正确性 oracle）运行期比对否，一票否决预算被无效消耗

系统代价还体现在 token 侧：把失效条件写进合约意味着题干与合约文本变长，读题阶段消耗的上下文 token 上升，而收益是搜索阶段不再为不可满足的约束反复生成候选。判断标准是合约中每条失效条件的表述成本是否低于它所能剪掉的候选生成轮次；若某条边界在算例中从未触发，它只是增加了读题负担而不改变预算轨迹，应移出合约正文、放入附录。
