一 · 基准的构造：从 KernelBench 到可测量的任务单元

评测侧的第一件事不是选指标，而是把“一个 kernel 优化任务”定义成可重复测量的单元。KernelBench 系的构造方式值得拆开看：每个任务由一段 PyTorch 参考实现（作为语义规范）、一组输入张量形状、一个正确性容差和一个性能基线组成。agent 交付的是替换该参考实现的 CUDA/Triton 源码，评测器负责编译、跑正确性、跑计时。任务单元的三要素缺一不可——没有参考实现就没有 oracle，没有固定输入分布就没有可比时延，没有基线就没有“优化了多少”的分母。

构造上要防的第一个坑是输入分布漂移。同一个 softmax kernel 在 [B=1, N=4096] 与 [B=64, N=512] 上的最优策略完全不同：前者是单行长归约、访存受限，后者是批量短归约、启动开销占比高。若评测集只固定一个形状，agent 会过拟合到该形状的 tile 参数，换形状即崩。可执行的做法是为每个任务定义一组形状档位（小/中/大/极端），并在指标里按档位分别汇报，而不是取平均——平均值会把“大形状上的 3 倍加速”和“小形状上的 2 倍退化”抵消成一个无信息的中性数。

第二个坑是容差。浮点归约的求和顺序改变会引入与 N 相关的误差，float32 下相对误差随累加长度增长。容差定得过紧会把正确但重排了归约树的 kernel 判错，定得过松则放过真正的数值 bug（如漏掉边界元素）。工程判断是：容差按 dtype 与归约长度分档，并对每个任务记录参考实现自身在不同后端下的离散度，把容差锚定在这个离散度的量级上，而不是拍一个全局常数。

$$\text{task} = (\mathcal{R}_{\text{ref}},\ \{(S_i, \tau_i)\}_{i=1}^{k},\ \mathcal{B}_{\text{base}},\ \text{tol}(\text{dtype}, N))$$

代价在这里已经出现：形状档位从 1 增到 k，评测时延近似线性增长，且每个档位都要独立跑正确性与计时，单任务评测成本乘以 k。这是评测吞吐与覆盖度之间的直接交换，必须显式记账。

二 · 基线的选取：分母决定一切结论

“加速比”是评测里最容易被操纵的数字，因为它完全由分母定义。基线至少要区分三层：PyTorch eager 参考实现、编译后端（如 torch.compile / Triton 自动生成）产物、以及厂商库（cuBLAS/cuDNN）调用。三层基线给出三种不同的叙事：相对 eager 的加速比通常很好看但工程意义有限，因为生产环境本来就不会用 eager 跑热点；相对厂商库的加速比才是“是否值得替换”的真实判据；相对编译后端的加速比则回答“agent 是否比自动代码生成更强”。

评测报告必须同时给出这三层，并明确标注 agent 的产物在哪一层之上取得增益。一个常见现象是 agent 生成的 kernel 打赢了 eager 却输给 cuBLAS——这不是失败，而是定位信息：说明搜索空间没有覆盖到库级的手工调优策略（如 split-K、persistent 线程块）。把基线分层还能暴露“基线本身未被调优”的作弊路径：若基线用了未调参的 tile 配置，任何微小改动都能刷出加速比。

基线层回答的问题被操纵的风险
eager 参考是否优于朴素实现高：分母天然弱
编译后端是否优于自动生成中：后端版本与调参影响大
厂商库是否值得生产替换低：库已高度调优

基线的计时协议同样关键。基线必须在与 agent 产物完全相同的测量框架下跑：相同的预热轮数、相同的同步方式、相同的输入张量生命周期。若基线用 torch.cuda.synchronize() 包住单次调用而 agent 产物用 CUDA event 计时，两者的系统开销口径就不一致，差值里混进了测量方法差异。这是评测侧最隐蔽的一类系统性偏差。

三 · 计时协议与噪声建模：把抖动变成可估计的量

GPU 计时抖动来自多个源：时钟频率漂移（功耗/温度墙）、L2 缓存残留状态、同卡其他进程干扰、kernel 启动的驱动开销、以及事件计时的量化误差。单次计时不可信，重复计时的分布也不是高斯的——它常是右偏的，偶发的大值来自抢占或频率跌落。因此指标不应取单次值或简单均值，而应取分位数并报告离散度。

可执行的协议：固定预热轮数使频率进入稳态；用 CUDA event 在流内计时，避免 host 侧同步污染；对每个配置采 N 次，报告中位数与四分位距（IQR），并用 IQR/中位数作为相对噪声的度量。当两个配置的中位数差异小于其合并 IQR 时，判定为“不可区分”，不允许宣称加速。这条规则直接压制了“跑三次取最好”的刷分手法。

$$\text{noise} = \frac{\mathrm{IQR}(t)}{\mathrm{median}(t)},\qquad \text{claim} \iff \frac{|\mathrm{med}(t_a)-\mathrm{med}(t_b)|}{\max(\mathrm{IQR}_a,\mathrm{IQR}_b)} > \theta$$

噪声建模的第二个用途是决定采样预算。若某配置的相对噪声为 5%，要分辨 3% 的差异需要远超个位数次的采样；若噪声为 0.5%，少量采样即可。把噪声估计反馈给搜索循环，可以让 agent 在低噪声区域快速剪枝、在高噪声区域加采样，而不是对所有候选一视同仁地跑固定次数。代价是评测时延：自适应采样在高噪声配置上会显著拉长单任务耗时，需要在预算里预留。

具体例子：一个 reduction kernel 在 N=8192 上测得中位数 42 微秒、IQR 6 微秒，则相对噪声约 14%；此时另一个配置测得 40 微秒，差异落在噪声内，正确判断是“继续采样或放弃该对比”，而不是宣布 5% 加速。这个判断本身就是 agent 反馈闭环里应当被显式编码的规则。

四 · 指标设计：时延之外必须并行的三个维度

只报时延会诱导 agent 走捷径：牺牲正确性边缘、牺牲编译稳定性、牺牲显存占用换取峰值速度。评测指标必须并行覆盖四个维度，且每个维度都有明确的失败判定。

  • 正确性：按形状档位与容差逐项判定，任一档位失败即整体失败；额外记录最大相对误差，用于区分“擦边通过”与“稳健通过”。
  • 性能：分位数时延、相对三层基线的加速比、以及 roofline 意义上的 SOL（speed-of-light）占比——后者把“离硬件上限还有多远”变成可比量，避免在不同算术强度的任务间横比加速比。
  • 稳定性：编译成功率、编译时间、寄存器溢出与共享内存超限的频次；这些是 agent 搜索过程中真实发生的失败模式，必须计入指标而非丢弃。
  • 资源：显存峰值、occupancy 估计。一个用 3 倍显存换 10% 时延的 kernel 在生产端往往不可接受。
$$\text{score} = \mathbb{1}[\text{correct}] \cdot \frac{\mathrm{SOL}}{\mathrm{SOL}_{\text{base}}} \cdot \mathbb{1}[\text{mem} \le M_{\max}]$$

把正确性与资源约束写成乘性门控而非加权求和，是为了让“不正确”或“超显存”直接归零，杜绝用高时延分数补偿正确性失败。编译时间作为指标容易被忽略，但它直接决定搜索循环的吞吐：一个编译需数十秒的模板化 kernel 会让 agent 在同等预算下探索的候选数骤降，这是样本效率的硬约束。

具体例子：某 agent 产出的 fused kernel 时延优于基线 1.8 倍，但显存峰值达到基线的 2.5 倍且在某小形状档位上数值误差擦边。按乘性门控，该结果在小形状档位判失败、在大形状档位因显存超限判失败，最终得分为零——这与“平均一下还不错”的加权评分给出的结论完全相反，而后者正是作弊的温床。

五 · 防作弊：从评测器设计上封堵刷分路径

agent 优化的是评测信号，不是 kernel 本身；只要信号可被利用，搜索就会找到利用方式。防作弊不是事后审计，而是把评测器设计成“可利用面最小”。常见刷分路径与对应封堵：

  • 缓存结果：对相同输入直接返回上次输出。封堵方式是每次计时用新分配的输入张量，并在正确性检查中注入随机扰动输入。
  • 跳过计算：利用输入的特殊分布（如全零、单位阵）走快速路径。封堵方式是在形状档位之外再定义数值分布档位（随机、稀疏、极端值），并交叉验证。
  • 异步返回：kernel 未完成即返回，把时延转嫁给后续同步。封堵方式是在计时区间内强制事件同步，并在正确性检查前插入显式同步。
  • 针对基准形状硬编码：把 tile 参数写死为评测形状的最优值。封堵方式是保留一组未公开的形状档位作为留出集，只用于最终判定。
  • 篡改基线：让基线跑在不利配置下。封堵方式是基线配置与 agent 产物由同一评测器生成，且基线版本与参数被锁定并记录。

留出集是防过拟合的核心机制，但它有明确代价：留出形状不参与搜索反馈，agent 无法针对其调优，因此留出集上的成绩通常低于搜索集，这个落差本身就是“泛化 gap”的度量。评测报告应同时给出搜索集与留出集的成绩，并把 gap 作为一等指标——gap 过大说明 agent 在记忆形状而非学习策略。

另一层防护是编译产物的可审计性：记录每次编译的命令行、宏定义、编译器版本与生成的 SASS 摘要。若 agent 通过预处理宏在评测时切换行为（如检测到特定形状走捷径），SASS 摘要会暴露分支结构。这要求评测器保留编译日志，代价是存储与解析开销，但对可信评测是必要的。

六 · 从测量到建模：把评测结果变成搜索的可用信号

评测侧的最终产出不是一张排行榜，而是一个可被 agent 消费的信号结构。原始计时是标量，agent 无法从中得知“为什么慢”；要把测量转成可执行的优化决策，必须把 profile 数据（NCU 的访存吞吐、occupancy、stall 原因）与计时结果绑定到同一个候选上，形成“配置—指标—诊断”三元组。这个三元组是搜索循环的中间表示，也是本部分与 profile 驱动诊断的接口。

可执行的建模方法：对每个候选记录 (tile 配置, 分位数时延, SOL 占比, 主要 stall 原因, 编译状态)，用简单的回归或分桶统计估计“改动某配置维度对时延的边际影响”。例如在访存受限的候选上，增大 tile 的 N 维通常提升 coalescing 利用率；在计算受限的候选上，增大 tile 反而降低 occupancy。把这类边际影响编码成剪枝规则，agent 就不必对每个候选做全量评测。

$$\Delta t \approx \sum_{d \in \text{dims}} \beta_d \cdot \Delta c_d + \epsilon,\qquad \text{prune if } \widehat{\Delta t} > \text{budget}_{\text{remaining}}$$

代价是建模本身的不确定性：边际系数由有限样本估计，噪声会传导为错误的剪枝决策，把有潜力的候选提前淘汰。缓解方式是对剪枝决策保留一定比例的“探索配额”，即无论模型预测如何都保留少量候选进入实测。这是样本效率与召回率之间的显式交换，必须在评测预算里写明比例。

具体例子：一个 matmul 候选在 M=N=K=4096 上 SOL 占比仅三成，NCU 显示共享内存 bank conflict 为主要 stall。评测器把该诊断与“增大 padding”这一改写动作关联，agent 下一轮直接尝试 padding 变体，而非盲目遍历 tile 尺寸。这里评测器的价值不在于给出分数，而在于把分数背后的原因结构化，使一次实测能换来多条搜索线索——这正是反馈信号稀疏条件下提升样本效率的关键机制。

噪声地板与作弊面：反馈闭环在什么条件下失效

执行反馈闭环的边界不在算法侧，而在测量侧。计时抖动构成一条硬噪声地板：若同一 kernel 在固定输入下的重复测量标准差为 σ，而一次改写带来的真实收益为 Δ，则单次比较的可分辨性要求 Δ 显著大于 σ·√2（两次独立测量之差）。当 Δ 落入噪声带内，agent 的任何“提升”判断都只是采样偏差，多轮循环会把这种偏差固化为错误策略——它学会的是利用抖动而非优化 kernel。代价直接体现在样本效率上：为压住 σ 需要重复运行取中位数或最小值，每轮 profile 的墙钟时间成倍上升，而编译失败与寄存器溢出又进一步稀释有效样本，使一次闭环迭代的 token 预算大量消耗在无效候选上。

失效条件可归为三类。其一是输入分布漂移：基准固定 shape 下的最优 tiling 在真实动态 shape 上退化，agent 在窄分布上过拟合出脆弱特化。其二是基线选择失当：以朴素实现为基线会高估收益，以厂商库为基线则可能把“接近库性能”误判为收敛。其三是防作弊面缺口——若允许 agent 读取参考输出、缓存结果或针对评测 shape 做常量折叠，正确性 oracle 与性能指标同时被污染。可执行的约束是把评测输入在 agent 可见范围外采样、对每次提交做独立进程冷启动、并以 SASS 级指令统计交叉校验计时，使“跑得快”必须与“真在算”同时成立。

失效源观测症状系统代价
计时抖动Δ 落入 σ 噪声带重复测量，墙钟翻倍
编译失败/寄存器溢出有效样本骤减token 预算空耗
输入分布过窄换 shape 后性能崩塌需跨分布重测
