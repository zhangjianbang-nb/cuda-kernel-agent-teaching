一 · 三条路线的机制分界：谁在承担“改写决策”

同一个 kernel 优化问题，agent 脚手架可以走三条机制上截然不同的路线。第一条是源码级自由改写：agent 直接编辑 CUDA C++ 源文件，编译器是唯一的语义仲裁者，反馈来自编译结果、运行计时与 profile。第二条是DSL 约束改写：agent 在 Triton/CuTe 这类领域特定 DSL 的合法构造空间内改写，DSL 的语义边界与编译器后端替它挡掉了一整类非法变换。第三条是profile 驱动的定向改写：agent 不直接读源码，而是先把 NCU/SASS 数据压成一份诊断摘要，再由摘要映射到有限的动作集合（调 tile、换 layout、改流水深度、动 shared memory 分配）。

三者的机制差异不在“是否用 LLM”，而在改写决策的搜索空间由谁定义、由谁裁剪。源码级路线把搜索空间交给 LLM 的语言先验，空间最大、语义风险最高；DSL 路线把空间交给 DSL 的类型系统与编译器约束，空间被结构化裁剪；profile 驱动路线把空间交给诊断到动作的映射表，空间最小但每一步的指向性最强。脚手架的核心设计问题因此是：把有限的 token 预算和编译-运行轮次，投在多大的搜索空间上、由谁来裁剪它。

代价的分野同样清晰。源码级路线的单轮代价是编译时间不可控（模板展开、寄存器压力导致的编译爆炸）与高失败率；DSL 路线的代价是表达力损失——某些手写 CUDA 能做的 warp 级技巧在 DSL 里没有对应构造，agent 被迫在更窄的空间里找次优解；profile 驱动路线的代价是诊断摘要的信息损失与映射表的覆盖不全，摘要丢掉的细节恰恰可能是关键线索。三条路线不是优劣排序，而是搜索空间大小与单步信息量之间的权衡曲线上的三个点。

$$\text{总代价} \approx N_{\text{round}} \cdot \left( T_{\text{compile}} + T_{\text{run}} + T_{\text{profile}} \right) + N_{\text{fail}} \cdot T_{\text{recover}} + C_{\text{token}}$$

这个式子说明路线选择如何改变代价结构：源码级路线抬高 $N_{\text{fail}}$ 与 $T_{\text{compile}}$，DSL 路线压低 $N_{\text{fail}}$ 但可能抬高 $N_{\text{round}}$（空间窄、需要更多轮试探），profile 驱动路线压低 $N_{\text{round}}$ 但每轮的 $T_{\text{profile}}$ 与摘要生成成本更高。一个具体例子：对一个 reduction kernel，源码级 agent 可能花三轮才把 shared memory bank conflict 改对，其中一轮编译因寄存器溢出失败；DSL agent 第一轮就写出合法的 Triton reduction，但发现 DSL 不暴露某个 swizzle 控制，只能接受次优 layout；profile 驱动 agent 从 NCU 的 bank conflict 计数直接跳到“改 padding”这一个动作，一轮命中，但若摘要没保留该计数，它就无从下手。

二 · 源码级自由改写：语义仲裁在编译器，风险在不可编译

源码级路线的机制是“编辑—编译—运行—profile”四段闭环，agent 的输出直接是 diff 或整文件重写。它的关键机制特征是编译器作为唯一 oracle：正确性由运行结果与参考实现比对，性能由计时与 profile 给出，任何语义错误都在编译或运行阶段暴露。这带来一个结构性优势——搜索空间不受 DSL 表达力限制，agent 可以尝试 DSL 里不存在的构造；也带来一个结构性劣势——非法变换与编译失败的比例高，而失败本身不产生任何性能信号，只消耗轮次。

伪代码层面的闭环大致是：读取当前源码与上一轮 profile 摘要 → LLM 生成候选改写 → 编译 → 若失败则把编译器错误回灌 → 若成功则运行正确性检查 → 通过后计时并采集 profile → 把计时与 profile 压成下一轮上下文。这里的核心工程判断是失败回灌的粒度：把完整编译日志塞回上下文会迅速耗尽 token 预算，而只回灌错误行号又可能丢失模板实例化链条上的关键信息。

  • 机制代价一：编译时间。模板重度使用的 kernel，单次编译可达数十秒量级，多轮闭环下编译时间可能超过运行时间本身，成为 $T_{\text{compile}}$ 主导的瓶颈。
  • 机制代价二：寄存器溢出与占用率。agent 改写引入的局部数组或展开循环可能把寄存器压力推过阈值，触发 spill，此时计时变差但 profile 显示的瓶颈会从计算转向 local memory 流量，诊断信号被污染。
  • 机制代价三：正确性检查的成本。逐元素比对需要额外的 kernel 启动与显存读写，在大 tensor 上这部分开销与计时本身同量级，必须与计时分离测量，否则计时抖动被正确性检查放大。

具体例子：agent 试图把一个 GEMM 的 inner loop 手动展开以提升 ILP，源码级路线允许它这么做，但展开后寄存器需求翻倍，编译器报告 spill，运行计时反而退化。此时反馈信号是“变慢了”，但 agent 从计时数字无法区分是展开本身有害还是 spill 导致——它需要 SASS 里的 spill 计数才能定位。这正是源码级路线对 profile 深度的依赖：没有 SASS 级证据，源码级 agent 容易把“寄存器压力”误读为“展开策略错误”而反复试错。

三 · DSL 约束改写：搜索空间被类型系统裁剪

DSL 路线的机制差异在于合法性由构造空间前置保证。Triton 的 block 级编程模型、CuTe 的 layout 代数，都把“哪些变换在语义上成立”编码进了类型与 API。agent 不再需要担心写出越界访存或非法的 warp 同步，因为 DSL 不提供这些构造，或者提供了也由编译器后端保证语义。这把 $N_{\text{fail}}$ 显著压低，代价是表达力被裁剪。

机制上，DSL 路线的闭环是“在合法构造空间内采样—编译—运行—profile”。关键在于构造空间的结构化程度决定了 agent 的有效搜索维度：Triton 的 tile size、num_warps、num_stages 是少数几个连续/离散旋钮，agent 的改写动作因此可以被参数化为一个低维向量；CuTe 的 layout 组合空间更大，但每一步组合都受 layout 代数约束，非法组合在编译期被拒绝而非运行期崩溃。

$$\text{有效搜索维度} \;=\; \dim(\text{DSL 暴露的旋钮}) \;<\; \dim(\text{源码级可改写自由度})$$

这个不等式是 DSL 路线的核心代价来源。维度低意味着单位轮次的信息密度高、收敛快，但也意味着最优解可能落在 DSL 表达力之外。一个具体例子：在 Triton 里写 flash attention 风格的 kernel，agent 可以调 block size 与 pipeline stage，但无法直接控制 shared memory 的 swizzle 模式；当 profile 显示 shared memory bank conflict 是瓶颈时，DSL agent 的动作空间里没有“改 swizzle”这个动作，它只能通过改 block size 间接缓解，收敛到的是约束下的局部最优。

  • 机制代价一：表达力损失导致的性能上限。DSL 编译器的调度策略是固定的，agent 无法像手写 CUDA 那样插入 inline PTX 或手工编排流水，性能天花板因此低于源码级路线的最优解。
  • 机制代价二：编译时间的可预测性换来了编译器的黑盒性。DSL 编译通常更快，但编译器内部做的优化决策对 agent 不可见，profile 显示的瓶颈可能源于编译器调度而非源码，agent 的改写动作与瓶颈之间的因果链被编译器切断。
  • 机制代价三：错误信息的可读性。DSL 编译失败往往报的是类型或 layout 不匹配，而非具体的性能问题，agent 需要额外的语义理解才能把类型错误翻译成改写方向。

工程判断上，DSL 路线适合搜索预算紧张、正确性风险不可接受的场景：当每轮编译-运行的成本高、且 agent 的改写能力尚不可靠时，用 DSL 裁剪空间换取失败率的下降是划算的。反之，当目标是把性能推到硬件极限、且 profile 已经明确指出 DSL 无法表达的瓶颈时，DSL 路线会成为天花板。

四 · profile 驱动定向改写：诊断摘要作为中间表示

第三条路线的机制核心是引入一个可压缩、可映射的中间表示：把 NCU/SASS 的原始计数器压成一份诊断摘要，再由摘要映射到有限动作集。这直接回应了“profile 数据到改写动作的映射缺乏可学习中间表示”这一挑战——中间表示就是这份摘要，它的设计质量决定了整条路线的样本效率。

机制上分两段。第一段是摘要生成：从 NCU 的 metrics 里挑出与瓶颈分类相关的少数几个（如 DRAM 吞吐占比、shared memory conflict 计数、warp stall 原因分布、指令发射率），归一化成“瓶颈类型 + 置信度”的标签。第二段是动作映射：每个瓶颈标签对应一组候选改写动作，agent 在候选集内选择并执行。伪代码思路是：瓶颈标签 → 动作候选表 → LLM 在候选表内排序并生成具体参数 → 编译运行 → 用新 profile 更新标签。

$$\text{动作} = \pi\left(\text{摘要}(M_{\text{NCU}}),\, \text{候选表}\right),\quad \text{摘要}: M_{\text{NCU}} \rightarrow \text{瓶颈标签}$$

这条路线最大的机制优势是把稀疏的 profile 信号转成离散的、可枚举的动作空间，从而让 LLM 的每次改写都有明确的因果指向，而非在源码空间里盲试。代价则集中在摘要的信息损失与映射表的覆盖度上。

  • 机制代价一：摘要丢弃的细节可能是关键。把 stall 原因压成“memory-bound”标签后，agent 看不到具体是 L1 miss 还是 DRAM 带宽饱和，两者的改写动作完全不同；摘要粒度太粗会导致动作映射错位。
  • 机制代价二：映射表的覆盖不全。候选表是人设计的，遇到表外瓶颈（如指令缓存压力、特殊功能单元饱和）时 agent 无动作可选，只能退回源码级自由改写，路线发生退化。
  • 机制代价三：profile 采集本身的时延与显存开销。NCU 采集需要多次 replay kernel，单次 profile 的墙钟时间可达运行时间的数倍，显存上还要为 replay 保留输入输出，这在预算感知的搜索里是必须计入 $T_{\text{profile}}$ 的固定成本。

具体例子：一个 memory-bound 的 elementwise kernel，NCU 显示 DRAM 吞吐接近峰值但计时仍不理想。摘要若只标“memory-bound”，agent 会去调 vectorization 宽度；但若摘要保留了“L2 hit rate 低”这一项，动作映射会指向“改数据布局以提升 L2 复用”，两者性能差距显著。这说明摘要的字段选择本身就是一种工程决策，它决定了 agent 能看到哪些因果线索。

五 · 三条路线的代价对照与混合机制

把三条路线放在同一张代价表上，可以看到它们的差异不是单点的，而是沿“搜索空间大小—单步信息量—失败率”三个轴的系统性偏移。下表只做定性对照，不引入未给定的数字。

维度源码级自由改写DSL 约束改写profile 驱动定向改写
搜索空间定义者LLM 语言先验DSL 类型系统与编译器诊断摘要 + 动作候选表
单轮失败率高（非法变换、编译失败）低（合法性前置保证）中（动作合法但可能无效）
单步信息量低（计时数字语义模糊）中（瓶颈与源码因果被编译器切断）高（瓶颈标签直指动作）
性能上限最高（可表达任意构造）受 DSL 表达力限制受候选表覆盖度限制
主要时延来源编译时间 + 失败恢复轮次数（空间窄需多试）profile replay 时间
主要 token 开销编译日志回灌类型错误语义翻译摘要生成与候选排序

混合机制是工程上更常见的形态：用 profile 驱动路线做粗定位，用 DSL 路线做中段收敛，用源码级路线做末端精修。机制上这要求脚手架维护一个“路线切换判据”——当 profile 摘要的瓶颈标签落在候选表覆盖范围内时走定向改写；当标签落在表外或 DSL 表达力之外时，切换到源码级自由改写并接受更高的失败率。切换判据本身是一个工程决策点，它的阈值设定直接决定样本效率。

代价上，混合路线引入了切换开销：每次切换都要重新建立上下文（源码级需要完整源码，DSL 需要当前 DSL 表达，profile 驱动需要最新摘要），这部分上下文重建的 token 成本在纯单一路线里不存在。一个具体例子：agent 先用 profile 驱动把 tile size 调到接近最优，profile 显示剩余瓶颈是 warp 调度，候选表里没有对应动作，于是切换到源码级改写手工插入 warp 级同步——切换本身消耗一轮上下文重建，但避免了在 DSL 空间里继续无效试探。

$$\text{切换收益} \;=\; \Delta\text{perf}_{\text{新路线}} \;-\; \left( C_{\text{context重建}} + N_{\text{失败}}\cdot T_{\text{recover}} \right)$$

这个式子给出的工程判断是：切换只在“新路线能触达的瓶颈确实存在、且重建成本低于继续原地试探的成本”时才划算。若 profile 摘要已经足够精确地指出瓶颈在候选表之外，切换是必要的；若摘要本身模糊，切换只是把不确定性从一个空间搬到另一个空间。

六 · 路线选择的可操作判据：从瓶颈标签到脚手架配置

把路线差异落到可操作层面，脚手架需要一个由瓶颈标签驱动的路线配置，而不是全局固定的路线。机制上，这表现为一个查表：输入是摘要给出的瓶颈类型与置信度，输出是路线选择、动作空间大小、每轮预算上限。置信度高且瓶颈在表内 → profile 驱动 + 小动作空间 + 低轮次预算；置信度低或瓶颈在表外 → 源码级 + 大动作空间 + 高失败恢复预算；瓶颈涉及 layout 代数且 DSL 有对应构造 → DSL 路线。

  • 判据一：失败率容忍度。若正确性检查成本高（大 tensor、多次比对），优先 DSL 路线压低失败率；若正确性检查便宜，源码级路线的高失败率可以被快速吸收。
  • 判据二：编译时间占比。若 $T_{\text{compile}}$ 已经主导单轮成本，源码级路线的多轮试错不划算，应优先 profile 驱动路线压缩轮次。
  • 判据三：profile 采集成本。若 NCU replay 的时延不可接受，profile 驱动路线的每轮固定成本过高，应降低 profile 频率，改用计时作为主信号并接受更低的单步信息量。

具体例子：一个计算密集的卷积 kernel，首轮 NCU 显示计算单元吞吐接近饱和、stall 主要来自指令依赖。摘要置信度高，瓶颈标签落在“指令级并行不足”，候选表里有“增加 ILP 展开”与“调整流水深度”两个动作，脚手架选择 profile 驱动路线、动作空间限定为这两个、轮次预算设为两轮。若两轮后计时无改善，说明瓶颈不在候选表覆盖的因果链上，此时切换到源码级路线手工重排指令顺序，并接受编译失败与寄存器溢出的风险。

这条判据链的关键在于把“路线”从脚手架的静态属性变成由反馈信号动态选择的运行时决策。三条路线的机制差异因此不是三选一的设计题，而是同一个闭环在不同瓶颈、不同预算下的三种工作模式；脚手架的可信度取决于它能否在正确的时机切换，以及切换时上下文重建的成本是否被计入预算。最终落在具体机制上：摘要字段的选择、候选表的覆盖度、切换判据的阈值，这三者共同决定了 agent 把硬件执行反馈转化为优化决策的效率上限。
