一 · 基准构造：从 KernelBench 任务到可归因的测量单元

评测侧的第一件事不是选指标，而是把“一个 kernel 生成任务”切成可独立归因的测量单元。KernelBench 系基准的原始形态是“给定 PyTorch 参考实现与算子语义，要求生成等价的高性能实现”，但直接拿整网或整算子做单点计时，会把启动开销、数据搬运、编译等待混进同一个数里，导致 profile 证据无法回指到某一行源码。可执行的做法是把每个任务拆成三层：语义层（输入张量形状、dtype、布局、边界条件）、执行层（grid/block 配置、stream 与同步点、是否含 host-device 拷贝）、测量层（warmup 次数、计时区间、是否锁频）。三层各自记录，评测报告里任何一次性能差异都必须能落到某一层的某个字段上。

具体机制上，用“固定形状 + 形状族”双轨制。固定形状用于跨实现横向对比，形状族（同一算子的一组代表性 shape，覆盖对齐与非对齐、单波与多波、小 batch 与大 batch）用于暴露 DSL 生成代码对尾块、mask、padding 的敏感度。伪代码思路如下：

$$\text{score}(k)=\frac{1}{|S|}\sum_{s\in S}\mathbb{1}\big[\text{correct}(k,s)\big]\cdot\frac{T_{\text{ref}}(s)}{T_k(s)}$$

其中 S 是形状族，正确性指示函数先于性能比值，任何形状上不正确即该形状记零，避免“快但错”的实现靠平均分蒙混。代价是测量时间随 |S| 线性增长：一个含 8 个形状的任务，若每形状 warmup 20 次、计时 100 次，单卡上单实现的测量开销在秒级到十秒级，整批任务评测会放大到小时级；这是评测吞吐与归因精度之间的直接权衡。例子：一个 Triton 生成的 reduction kernel 在 4096 的整齐长度上接近参考实现，但在 4097 这种非对齐长度上因 mask 分支退化为两倍时间——固定形状基准完全看不到这一点，形状族才把它暴露出来。

二 · 基线选择：参考实现、SOL 与“同抽象层基线”三线并行

基线不是一条，而是三条，各自回答不同问题。第一条是语义基线（PyTorch/cuBLAS 参考实现），回答“生成代码是否至少不劣于库”；第二条是 SOL 基线（roofline 上界），回答“距离硬件极限还有多少”；第三条是同抽象层基线（同 DSL、同版本编译器、同手写风格的对照实现），回答“性能差异究竟来自 DSL 抽象还是来自生成质量”。只报第一条会让高分实现显得毫无改进空间，只报第二条会让所有实现都显得很差，只报第三条则无法判断绝对值是否有工程意义。

SOL 基线的构造必须绑定具体访存与计算模式，而不是套一个峰值 FLOPs 数字。对 memory-bound kernel，用 字节数 / 有效带宽 作为时间下界；对 compute-bound kernel，用 有效 FLOPs / 峰值算力，其中有效 FLOPs 要按实际数据通路（是否走 tensor core、是否有 padding 浪费）折算。代价在于 SOL 建模本身需要人工判断瓶颈归属，一旦归错类，整条基线的参考价值归零；因此评测流程里应把“瓶颈归类”作为显式字段记录，并允许后续用 NCU 指标（如 DRAM 吞吐占比、SM 吞吐占比、issue slot 利用率）反证归类是否正确。例子：一个 CuTe 生成的 GEMM，若按峰值算力算 SOL 得到 30% 利用率，但 NCU 显示 DRAM 吞吐已接近饱和，则真实瓶颈是访存而非算力，SOL 基线应改用带宽口径重算，否则会误导优化方向。

基线回答的问题失效场景测量代价
语义基线是否不劣于库实现库实现本身非最优低，直接调用
SOL 基线距硬件极限多远瓶颈归类错误中，需建模与 NCU 反证
同抽象层基线差异来自抽象还是生成对照实现选取偏差中，需维护对照集

三 · 输入分布：让正确性与性能在同一分布上被检验

输入分布同时决定正确性 oracle 的覆盖面和性能测量的代表性，二者必须共用同一套分布定义，否则会出现“在随机正态上正确、在极端值上溢出”或“在小 shape 上快、在真实 shape 上慢”的错配。可执行的做法是把分布写成显式规格：数值范围（是否含 inf/nan/denormal）、稀疏度、对齐性（首地址与 stride 是否满足向量化要求）、以及 shape 的分布族。每个规格对应一组固定种子，保证跨实现、跨轮次可复现。

机制上，正确性检验用“分层抽样 + 边界穷举”组合：对连续值域用固定种子随机抽样比对，对离散边界（0、±1、最大最小值、mask 边界索引）做穷举。性能测量则只使用分布族中的代表性子集，避免把测量时间耗在无信息量的形状上。代价是分布规格越细，评测准备与维护成本越高：每增加一个 dtype 或一种布局，正确性比对与性能测量都要重跑，且固定种子的输入张量本身占用显存，大 shape 下输入构造可能成为评测本身的瓶颈。例子：一个 PTX 手写 kernel 在 fp16 随机输入上数值正确，但在含 denormal 的输入上因未处理次正规数而输出偏差；若分布规格里没有 denormal 这一项，这个缺陷在评测中不可见。

另一个必须显式化的维度是“输入是否在测量区间内被复用”。同一块输入反复读取会命中 L2，测得的带宽高于真实冷数据场景；每次测量前重置输入则引入额外拷贝开销。工程判断是：对 memory-bound kernel 明确区分“热缓存”与“冷缓存”两个指标分别报告，而不是取平均。

四 · 指标：从单点时延到可归因的剖面向量

单一 wall-clock 时延不足以支撑优化决策，评测侧应输出一个剖面向量：时延中位数与分位数（反映抖动）、有效带宽与有效算力（对照 SOL）、occupancy 与 issue slot 利用率（反映调度质量）、以及编译时间与生成 token 数（反映生成侧成本）。分位数而非均值是必须的，因为 kernel 启动与调度抖动会让均值被长尾拉偏；中位数配合 P90 能同时表达典型值与最坏情况。

把 NCU 指标纳入评测向量时，关键约束是“profile 本身改变被测量对象”。NCU 采集会引入序列化与重放，测得的时间不能直接当作性能指标，只能当作瓶颈归因证据。可执行的做法是：性能数字来自无 profile 的干净运行，归因证据来自单独的 profile 运行，两者用同一输入规格与同一编译产物，报告中分列。代价是评测总时间约翻倍，且 profile 运行需要额外显存与权限配置。例子：一个 Triton kernel 干净运行显示时延稳定，但 NCU 显示其 stall 主要来自长延迟的全局访存且 L1 命中率低，据此可判断优化方向是提高数据复用而非调整 block 大小——这个判断无法从时延数字本身得出。

$$\text{util}=\frac{\text{achieved}}{\text{SOL}},\qquad \text{gap}=1-\text{util}$$

把 util 与 gap 作为一等指标后，评测报告的结构应是“gap 分解”：多少 gap 来自带宽未饱和、多少来自 occupancy 不足、多少来自指令混合不佳。分解本身依赖 NCU 指标与 SOL 口径的一致性，口径不一致时分解结果无意义，因此瓶颈归类字段必须与 SOL 口径绑定记录。

五 · 防作弊：让“快”必须同时是“对”和“可复现”

生成式评测的作弊面比传统 benchmark 宽得多：缓存结果、跳过计算、针对固定输入硬编码、利用计时区间外的异步执行、以及只对基准形状特化。防作弊不能靠单条规则，而要靠一组互相牵制的约束。第一，正确性检验使用与性能测量不同的固定种子与不同形状，使针对测量输入的特化无法通过正确性；第二，计时区间强制包含同步点，禁止把异步 launch 的开销推到区间外；第三，对同一实现做“输入扰动重测”，若结果随输入变化而性能异常稳定，提示存在缓存或跳过计算的嫌疑；第四，保留编译产物哈希，防止同一任务在不同轮次间复用旧二进制。

机制上，最有效的一条是“隐藏形状集”：评测方保留一组不公开的形状与数值规格，只在最终评分时使用。生成侧只能看到公开集，针对公开集的特化在隐藏集上会暴露为正确性或性能断崖。代价是隐藏集使生成侧无法针对真实分布调优，可能低估其泛化能力，因此隐藏集应只用于防作弊判定，不参与主分数构成。例子：一个生成的 kernel 对固定 shape 做了编译期常量折叠，公开集上极快，隐藏集上因需要运行时分支而退化——这种退化在隐藏集上表现为性能骤降，是特化的直接证据。

另一条代价明确的约束是“禁止跨轮次缓存编译产物”。DSL 编译（尤其 CuTe 模板实例化与 PTX 汇编）耗时可达秒级到分钟级，允许缓存会显著提升评测吞吐，但也会让“生成质量”与“编译缓存命中”混为一谈。工程判断是：编译时间单独作为指标报告，缓存策略在评测配置中显式声明，跨实现对比时统一关闭缓存。

六 · 测量与建模的可执行流程

把上述要素串成一条可执行流水线：任务规格（语义层 + 形状族 + 分布规格）→ 生成与编译（记录编译时间与产物哈希）→ 正确性检验（分层抽样 + 边界穷举，独立种子）→ 干净性能测量（warmup、分位数、冷热缓存分列）→ 单独 profile 运行（NCU 指标采集）→ gap 分解与瓶颈归类 → 防作弊判定（隐藏集、扰动重测、缓存检查）。每一步的输入输出都以结构化字段落盘，任何一次评分都能回溯到具体字段。

建模侧的关键是把 SASS 级证据映射回源码级改写点。可执行的做法是：在生成阶段保留 DSL 源码到编译产物的映射（如 Triton 的 IR 层级、CuTe 的模板实例名），profile 阶段按指令类型与 stall 原因聚合到函数或循环层级，形成“源码位置—指令混合—stall 原因”的三元组。映射困难在于编译器会重排与内联，源码行与 SASS 指令不是一一对应；代价是需要维护映射表并在每次编译器版本变化时重建，否则归因会指向错误的改写点。例子：NCU 显示某段循环的 stall 集中在长延迟 scoreboard 依赖，若映射表能把该段指令回指到 CuTe 中某个 tile 的加载方式，优化就直接落在数据布局上，而不是盲目调 block 大小。

最后一条工程判断是评测的“版本锚定”：DSL 与 profile 知识随架构迭代快速过时，因此每次评测必须记录工具链版本、目标架构、驱动与 NCU 版本，并把 SOL 口径与瓶颈归类规则一并版本化。没有版本锚定的评测结果在跨架构比较时不可解释，gap 分解也会失去意义。

评测侧的三重边界：基线漂移、分布错配与作弊面

硬件感知 DSL 的评测不能只报一个加速比。可执行的测量骨架是：固定 baseline 三元组（同一算子、同一 dtype、同一输入形状族）下测 t_dsl 与 t_ref，同时记录编译时间 t_compile 与 NCU 采集的 dram_bytes、sm__pipe_tensor_cycles_active。加速比必须与 roofline 位置一起报，否则无法区分“DSL 真的逼近 SOL”与“基线本身写得很差”。判据写成

$$S=\frac{t_{\text{ref}}}{t_{\text{dsl}}+t_{\text{compile}}/N_{\text{iter}}},\quad \eta=\frac{\text{实测 FLOPs/s}}{\text{SOL}_{\text{roofline}}}$$
其中 N_iter 是摊销迭代数。代价很直接：把 t_compile 计入分母后，Triton 的 autotune 与 CuTe 模板实例化会显著压低小形状下的 S；而 NCU 逐 kernel 采集会让端到端时延膨胀数倍，因此 profile 只能抽样跑，不能进主计时循环。

输入分布错配是第二个失效面。DSL 生成的 kernel 常在规整形状（2 的幂、连续 stride）上被 autotune 选中，一旦遇到非对齐尾块、广播 stride 或动态 shape，Triton 的 mask 分支与 CuTe 的 tile 划分会退化。评测集必须显式分层：对齐主形状、尾块形状、退化 stride 三类分别计时，并对每类给出 dram_bytes 与理论下界的比值。若某类只报一个合并数字，优化器会学到“在易测分布上过拟合”的策略，这正是可验证奖励被污染的地方。

防作弊面在于计时口径与缓存状态。必须固定 GPU 时钟、清空 L2（或用固定 warmup 次数后取稳态）、禁止在计时区内做 host-device 同步之外的隐式同步，并要求提交方附带 NCU 的 dram_bytes 与 SASS 中 tensor core 指令计数作为交叉证据。表格给出三类典型失效的判据：

失效模式可观测信号系统代价
基线漂移t_ref 跨轮次方差大加速比不可比，需重跑基线
分布过拟合尾块形状 η 骤降需分层评测，token 与机时翻倍
缓存作弊dram_bytes 远低于理论值需清 L2，单次测量时延上升

最后一个边界是 SASS 证据到源码改写的映射成本：NCU 指出瓶颈在 sm__pipe_tensor_cycles_active 偏低时，agent 未必能定位到 Triton 中哪一层 tile 或 CuTe 中哪个 layout 造成，诊断结论与可改写动作之间存在语义鸿沟。工程判断是：把 profile 指标作为否决信号而非奖励信号——只有当 η 与 dram_bytes 同时满足下界时才接受该 kernel，避免优化器追逐无法映射回源码的 SASS 局部指标。
