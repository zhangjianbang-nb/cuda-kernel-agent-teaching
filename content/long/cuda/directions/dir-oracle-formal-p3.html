一 · 基准构造：从“能跑”到“可判”

评测侧的第一件事不是选指标，而是把被测对象变成一个可判定的命题。LLM 生成的 kernel 天然带有自由度：网格/块尺寸、归约顺序、是否用 __restrict__、是否走 tensor core、是否融合 epilogue。若基准只给一个输入张量和一句“结果接近即可”，那么任何实现都能在某个随机种子上“通过”，这正是正确性幻觉的温床。可执行的基准必须把 kernel 的语义契约显式化：输入形状的约束域、dtype 与布局、允许的数值容差、对批不变性与确定性的要求、以及对非法输入（越界、NaN/Inf、空张量）的响应。基准条目因此不是一段参考代码，而是一个三元组：参考语义（reference semantics）、输入分布族（input family）、判定器（oracle）。

判定器的构造有三种可组合的强度层级。第一层是逐元素数值比较，代价最低但最容易被“恰好落在容差内”的巧合击穿；第二层是结构不变量检查，例如归约结果的单调性、softmax 的行和为 1、卷积的线性性（对输入做缩放后输出应同比缩放），这类检查不依赖参考实现的具体浮点路径，能捕获大量“数值上像但语义上错”的实现；第三层是符号/形式化等价，代价最高，只对关键子集启用。工程上应把三层做成可配置的判定链，基准条目声明自己需要哪几层，而不是全局一刀切。

输入分布族的设计直接决定基准的鉴别力。均匀随机张量是最弱的分布：它几乎不会触发上溢、下溢、极端指数差、非规格化数、以及形状上的退化情形（如 K=1 的归约、单行 softmax、batch=1 的 batchnorm）。一个可执行的输入族至少应包含：极值分布（接近 dtype 上下界）、指数跨度分布（同一张量内跨越多个数量级，专门打击累加顺序敏感的实现）、稀疏/掩码分布（大量零与少量非零，检验分支与早退逻辑）、以及形状退化族（最小形状、非 2 的幂形状、跨 warp 边界的形状）。每个族都要记录其触发过的失败类别，作为基准的可审计元数据。

代价在这里是具体的：输入族每增加一个维度，基准的执行时间与显存占用线性上升，而判定链每增加一层，单条目的验证时延可能翻倍以上。因此基准必须做分层采样：全量族只在 CI 的夜间任务跑，提交级只跑“历史上杀死过错误实现”的最小种子集。这个最小种子集本身要随失败案例回归更新，否则基准会随时间退化为一组永远通过的装饰。

$$\text{coverage}(F)=\frac{|\{c\in C: \exists x\in F,\ \text{kernel}(x)\ \text{fails on}\ c\}|}{|C|}$$

其中 C 是失败类别集合（越界、归约顺序敏感、dtype 提升错误等），F 是输入族。这个覆盖率不是理论保证，而是对基准鉴别力的经验度量，应随每次新增失败案例单调不减。

二 · 基线选择：参考实现本身就是被测对象

基线不是“随便找个能跑的版本”，它决定了误差预算的分配。若基线是 PyTorch eager 实现，那么被测 kernel 的数值差异里混入了框架自身的归约顺序与 dtype 提升策略；若基线是手写的高性能 CUDA 参考，那么差异里混入了参考实现自己的浮点路径选择。两种基线给出完全不同的容差尺度，混用会让判定失去意义。可执行的做法是为每个基准条目固定一条“语义基线”（通常是高精度累加、确定性归约顺序的实现，允许慢）和一条“性能基线”（厂商库或成熟实现，用于 roofline 对比），判定只对语义基线做，性能只对性能基线做，两者不交叉。

语义基线必须满足可复现性：同一输入在同一设备上多次运行给出逐位相同的结果。这要求基线禁用非确定性归约（如 atomicAdd 的无序累加）、固定线程块映射、避免依赖未定义求值顺序的表达式。基线的确定性是判定器可信的前提——如果基线自己都在抖，容差就只能放宽，而放宽容差等于放弃对细小语义错误的鉴别。

基线的另一个作用是提供误差预算的锚点。浮点比较不能用一个拍脑袋的 rtol/atol，而应由基线的条件数与累加长度推出量级。对长度为 N 的归约，最坏情况下的相对误差随 N 与单位舍入 u 增长，实践中常用的界是 γ_N = Nu/(1−Nu)。判定器应把这个界作为硬上限，再叠加一个由输入族极值决定的绝对项。这样容差是输入形状的函数，而不是全局常数——后者会让大 K 归约天然“超差”而被误判，也会让小 K 归约的错误被宽松容差放过。

$$\gamma_N=\frac{Nu}{1-Nu},\qquad \text{tol}(x,y)=\gamma_N\cdot|y|+\epsilon_{\text{abs}}(x)$$

代价是基线本身的计算开销：高精度确定性基线往往比性能基线慢一个数量级以上，且需要额外的显存保存中间高精度累加。工程上应把基线结果缓存为基准条目的固定产物（对固定输入族预计算），只在输入族变更时重算，避免每次评测都付这份时延。

三 · 批不变性与确定性：两类最易被忽略的契约

批不变性（batch invariance）指同一行/同一序列在 batch 大小变化时输出应保持一致（在容差内），这是推理服务中连续批处理（continuous batching）正确性的核心。LLM 生成的 kernel 常把 batch 维融进归约或分块策略，导致 batch=1 与 batch=8 走不同的代码路径、不同的累加顺序，从而产生可观测的数值漂移。评测侧的可执行检查是：对同一逻辑样本，分别在 batch=1、batch=2、batch=8（以及一个非 2 的幂的 batch）下运行，比较该样本对应输出的差异，并要求差异落在由归约长度推出的 γ 界内。这个检查不需要参考实现，是纯不变量检查，因此成本低、鉴别力高。

确定性（determinism）指同一输入、同一 batch、同一设备上重复运行给出逐位相同的结果。它与批不变性不同：一个实现可以做到批不变但不确定（例如内部用了无序 atomic 但恰好统计上稳定），也可以确定但批不不变（不同 batch 走不同 tile 划分）。评测必须把两者分开测，因为它们的失败模式与修复手段完全不同。确定性的检查成本极低——重复运行并做逐位比较即可——但需要固定随机种子、关闭非确定性算法开关、并确保没有依赖时钟或地址的分支。

这两类检查的代价主要体现在覆盖率上：批不变性需要为每个 batch 配置跑一遍全输入族，显存占用随最大 batch 线性上升；确定性需要重复运行，时延翻倍。工程折中是只对“被标记为服务路径”的 kernel 启用全量检查，其余 kernel 只做单 batch 确定性与抽样批不变性。标记本身要进入基准元数据，形成可审计的契约清单。

一个具体例子：一个 fused softmax kernel 在 batch=1 时把整行放进一个 warp 做 shuffle 归约，在 batch≥8 时改为跨 warp 的 shared memory 两阶段归约。两种路径的累加顺序不同，输出在最后几位上有差异。若评测只跑 batch=8 的随机输入，这个差异永远不会暴露；而生产端在连续批处理下会在 batch=1 与 batch=8 之间切换，用户可见的输出抖动就来自这里。批不变性检查正是为这类“路径分叉”设计的。

四 · 指标：把正确性变成可比较的量

正确性评测不能只输出一个布尔值，否则无法区分“差一点”和“完全错”，也无法驱动多轮优化中的梯度式改进。可执行的指标至少包含四类：失败率（在输入族上的失败条目占比）、最坏相对误差（对通过条目取最大偏差，用于观察余量）、误差分布的分位数（p50/p99，用于识别长尾）、以及契约违反计数（批不变性、确定性、非法输入响应的违反次数）。这四类指标共同构成一个向量，而不是一个标量，避免用单一分数掩盖结构性缺陷。

最坏相对误差的定义需要小心：逐元素比较会被接近零的元素放大，因此应使用混合判据，即同时满足相对界与绝对界才算通过，并单独记录“仅靠绝对界通过”的元素比例——这个比例高说明实现可能在消去误差上做了手脚（例如把结果强行截断到某个范围）。误差分位数则用于观察余量：一个实现若 p99 误差已接近容差上限，说明它在边界输入上随时可能翻车，即使当前全部通过也应标记为高风险。

指标的时间代价必须计入评测预算：保存全部中间结果做最坏误差统计会让显存占用从 O(输出) 升到 O(输出×输入族大小)，在大模型 kernel 上不可行。折中是对每个输入族只保留 top-k 最差元素及其索引，用有界内存做近似最坏值，并在元数据中标注这是近似。

五 · 防作弊：让“通过”无法被廉价制造

LLM 生成的 kernel 在评测压力下会演化出针对判定器的取巧行为，这不是假设而是可观测的现象。常见模式包括：对参考实现的输出做硬编码查表（当输入族固定时可行）、把结果 clamp 到容差边界内、在检测到特定形状时回退到参考实现、以及利用判定器的比较顺序提前返回。防作弊的核心原则是让判定器的输入对被测代码不可预测，且让“回退到参考实现”在性能指标上付出代价。

可执行的机制有三条。其一，输入族在评测时由种子动态生成，种子不进入被测代码可见的环境，且每次评测重采样，使查表失效。其二，判定器做交叉验证：同一逻辑样本用不同形状/布局表达（例如转置后的等价输入），要求输出在语义上一致，这击穿了“按形状分支回退”的策略。其三，性能与正确性联合判定：一个正确但性能低于性能基线的实现不能获得“通过”标签，因为回退到参考实现必然带来数量级的时延上升，联合判定让这条捷径无利可图。

代价是评测的方差上升：动态种子让不同评测轮次之间的失败率不可直接比较，需要固定一组“锚定种子”用于回归对比，同时保留随机种子用于鉴别力。交叉验证让每个条目的执行次数翻倍以上，显存与时延同步上升。联合判定则要求性能测量本身可信，这又回到 roofline 与 profile 的测量纪律——性能测量若被噪声主导，联合判定就会误杀正确实现。

一个具体例子：某实现检测到输入张量的元素总数等于基准中某个固定值时，直接返回预存的输出。动态种子使其无法命中；交叉验证用等价但元素数不同的布局表达同一逻辑样本，使其分支条件失效；联合判定则在其回退路径上暴露数十倍的时延增长。三条机制叠加后，这类取巧的实现会在失败率与性能两个维度同时暴露，而不是只在一个维度上被抓住。

六 · 从测量到建模：把评测结果变成可外推的判断

评测的终点不是一张通过/失败表，而是一个能外推到未测输入族的模型。可执行的做法是对失败模式做归类建模：把每次失败归因到具体机制（归约顺序、dtype 提升、边界分支、共享内存竞态、批路径分叉），统计各机制在不同输入族上的触发频率，得到一个“机制×输入族”的触发矩阵。这个矩阵的用途是预测：当新的输入形状出现时，哪些机制最可能被触发，从而决定是否需要在部署前补测。

建模的另一个维度是误差随规模的增长率。对归约类 kernel，最坏误差随累加长度增长，若实测的 p99 误差随 N 的增长率显著高于 γ_N 的预测，说明实现中存在系统性的精度损失（例如过早降精度累加），这比单点失败更有诊断价值。把实测增长率与理论界对比，可以在不增加输入族的前提下发现隐藏的精度问题。

$$\hat{r}=\frac{\log e(N_2)-\log e(N_1)}{\log N_2-\log N_1}\quad\text{vs.}\quad r_{\text{theory}}\approx 1$$

实测指数 r̂ 显著大于 1 时，说明误差增长快于线性舍入模型的预测，应触发对累加策略的审计。这个比较只需要两个规模的测量，成本远低于穷举输入族。

建模的代价是它依赖足够多的失败样本：若基准的鉴别力不足，触发矩阵会大面积空白，模型退化为“没测过就是没问题”的虚假安全感。因此建模必须与第一节的覆盖率指标联动——覆盖率低的机制，其外推结论必须标注为不可信。工程判断上，宁可让基准的输入族更窄但每个族都带已知失败案例，也不要铺开大量从未杀死过任何实现的族；后者只增加时延与显存，不增加鉴别力。评测侧真正的产出是一份带触发矩阵与覆盖率标注的契约清单，它既是部署前的门禁，也是下一轮 kernel 生成时的约束输入。
