一 · 基准的可复现性从输入分布开始

KernelBench 系基准最容易被忽视的污染源不是 kernel 本身，而是测试输入。同一个算子，在 torch.randn 生成的输入上跑出的时延，与在含大量零、极端指数、非连续 stride 的输入上跑出的时延，可以差出一个数量级——前者触发的是稠密路径，后者触发的是分支与掩码路径。若基准只声明"随机输入"，跨论文数字就失去了可比性。可执行的做法是把输入分布写成契约：每个任务附带一个生成器，显式声明 dtype、shape 采样范围、值域、稀疏度、对齐约束与 stride 模式，并在基准仓库中以版本号冻结。评测时按固定种子重放，任何一次跑分都能被第三方逐位复现。

分布契约的代价是显存与生成时间。以注意力类任务为例，若要在 batch、序列长度、head 数三维上做分层采样，单次评测的输入集合可能占用数 GB 显存，生成耗时进入秒级；若用 CPU 端生成再拷入，PCIe 带宽会成为评测本身的瓶颈。工程折中是分层抽样加预算上限：主分布覆盖典型 shape，边界分布只保留少量固定用例，极端分布按类别各取一例。这样既保证覆盖，又把评测自身的时延控制在可接受范围。

具体机制上，输入生成器应输出一个可哈希的描述符（dtype、shape、seed、分布参数），与 kernel 输出一并存档。当两次评测结果不一致时，先比对描述符，再比对数值——这一步能把"kernel 写错了"与"输入根本不是同一个"区分开。没有这一步，任何跨论文的加速比都只是定性表述。

$$\text{reproducible} = \mathbb{1}[\text{desc}_A = \text{desc}_B] \cdot \mathbb{1}[\text{tol}(\text{out}_A, \text{out}_B) \le \epsilon]$$

二 · 基线选择决定加速比的分母

加速比是比值，分母的选择比分子更能操纵结论。KernelBench 系基准的常见问题是对照基线随意：有的用 PyTorch eager，有的用 torch.compile，有的用厂商库（cuBLAS、cuDNN、CUTLASS），还有的干脆与一个明显未优化的朴素实现比较。这四种分母对应的加速比不可互相引用。可执行的规范是分层基线：每个任务声明一个"参考实现"（通常是 eager 或厂商库）作为正确性与性能的双重锚点，再声明一个"强基线"（编译后的版本或手工调优版本）作为竞争力门槛。报告加速比时必须注明分母身份，且分母实现本身要通过同一套正确性 oracle。

基线自身的测速口径同样要统一。若参考实现是 eager，其 Python 调度开销会被计入分母，从而系统性放大加速比；若参考实现是编译后的融合版本，分母更紧，加速比更诚实但更难刷高。工程判断是：面向 agent 训练的奖励信号应以强基线为分母，因为弱基线会让 agent 学会"打败一个本就不该存在的对手"；面向部署决策的收益评估则以参考实现为分母，因为那才是替换前的真实成本。

代价体现在评测吞吐上。每增加一个基线，就要多跑一遍完整输入集合，评测总时延近似线性增长；若基线包含编译步骤，首次评测还要额外付出编译时间。因此基线集合应控制在两到三个，且编译产物缓存复用。一个具体例子：同一 GEMM 任务，以 eager 为分母得到的高加速比，在换成 cuBLAS 为分母后往往大幅缩水——这不是 kernel 变差了，而是分母变诚实了。

三 · 多级 oracle 与变异测试校准误判率

正确性 oracle 过松是基准可信度的头号杀手。单一 allclose 在浮点累加顺序变化、归约维度不同、低精度累加时会产生假阴（把正确 kernel 判错），而在输出被截断、掩码写反、边界未处理时又会产生假阳（把错误 kernel 判对）。可执行的做法是分级 oracle：第一级做形状与 dtype 校验；第二级做随机输入下的相对误差与绝对误差双阈值；第三级做边界与极端输入（全零、全最大、含 NaN/Inf 的受控用例、长度为 1 或非对齐长度）；第四级对归约类算子做高精度参考（float64 累加）比对。级别越高，假阳越低，假阴风险越高，因此每级都要单独报告通过率而非只报最终布尔值。

阈值本身不能拍脑袋。对 float32 归约，误差随累加长度增长，阈值应写成与 sqrt(n) 或 n 相关的形式，而非固定常数。变异测试是校准 checker 的手段：向参考实现注入受控缺陷（去掉边界判断、交换两个操作数、把累加精度降一级、把掩码偏移一位），观察 oracle 是否逐一如期报错。若某个变异体未被捕获，说明 oracle 在该缺陷类型上存在假阳盲区；若正确实现被误报，说明阈值过紧。变异测试的成本是每轮要跑数十个变异体乘以完整输入集合，评测时延成倍上升，因此适合作为基准发布前的离线校准，而非每次评测的在线步骤。

$$\text{FPR} = \frac{|\text{变异体被误判为通过}|}{|\text{变异体总数}|},\quad \text{FNR} = \frac{|\text{正确实现被误判为失败}|}{|\text{正确实现总数}|}$$

这两个比率应当作为基准自身的元指标公开。一个 oracle 若假阳率高，agent 会学到"写错也能拿奖励"；若假阴率高，agent 会学到"保守到不敢优化"。两者都会污染后续的 RL 奖励与执行反馈。

四 · 测速口径与 SOL 归一化

测速口径不统一是跨论文数字不可比的直接原因。是否包含 kernel launch 开销、是否做 warmup、是否用 CUDA event 还是 wall clock、是否在测速前同步、是否取中位数还是最小值——每一项都会改变结果。可执行规范是：固定 warmup 轮数并丢弃，用 CUDA event 在设备端计时以排除主机调度抖动，每配置重复若干次取中位数并同时报告分位数，测速期间锁定时钟或至少记录时钟状态。对短 kernel，launch 开销占比高，应单独报告纯设备时间与端到端时间两个口径。

绝对时延不可跨架构比较，因此需要归一化。SOL（speed of light）与 roofline 提供了分母：对计算密集算子，用峰值算力与实测 FLOPs 得到计算利用率；对访存密集算子，用峰值带宽与实测字节数得到带宽利用率。归一化后的指标是"达到硬件的百分比"，它与架构无关，因而可跨 GPU 比较。代价是 SOL 分母本身依赖厂商峰值参数与实测可达峰值的差距，若用理论峰值作分母，利用率会被系统性低估；若用微基准实测峰值，则需额外付出一次标定成本。

口径包含内容适用场景主要偏差来源
纯设备时间仅 kernel 执行算子级对比忽略 launch 与调度
端到端时间launch + 执行 + 同步部署收益评估主机抖动、框架开销
SOL 利用率实测吞吐 / 硬件峰值跨架构比较峰值参数选取

一个具体例子：某逐元素算子的端到端时间被 Python 调度主导，纯设备时间只占小部分；若只报端到端加速比，会把框架开销的削减误记为 kernel 优化收益。分开报告两个口径，才能把收益归因到正确的层次。

五 · 泛化与知识迁移的评测协议

"能跑、真快"之外还要"真可迁移"。单任务过拟合的 agent 可以在见过的最优解上刷分，但在未见 shape、未见 dtype、未见算子组合上崩溃。评测协议应包含三部分：分布内任务、分布外任务（同算子不同 shape 或 dtype）、跨算子迁移任务（结构相似但语义不同）。分布外任务不参与训练奖励，只作为泛化门槛；跨算子任务检验 agent 是否学到了可复用的优化模式而非记忆。

协议的可执行细节是冻结划分：训练可见的任务集合与评测任务集合在基准发布时固定，且评测集合的输入描述符不公开具体种子，只公开分布类别。这样 agent 无法针对评测输入做特化。代价是评测集合的覆盖面受限——隐藏种子意味着无法逐位复现单次结果，只能复现统计结论，因此需要报告多次采样的方差而非单点数字。

迁移评测还要防止"抄基线"：若 agent 在跨算子任务上直接调用厂商库，加速比会虚高但不体现生成能力。协议应要求提交的 kernel 为自生成实现，并对调用外部库的行为做静态检查。这一检查的成本是解析与符号分析的时间，属于离线环节。工程判断是：泛化门槛应作为奖励的乘性因子而非加性项，否则 agent 会用分布内的极高加速比抵消分布外的失败。

六 · 防作弊与评测器自身的度量

防作弊不是道德问题而是测量问题。常见作弊路径包括：缓存输出绕过计算、针对固定输入做常量折叠、在测速循环外预计算、用低精度近似骗过阈值、检测到评测环境后切换实现。对应的检测手段是：输入每次评测重新生成且不可预测、测速与正确性用不同输入、对输出做逐位比对而非仅统计误差、在 kernel 内注入不可优化的依赖以阻止常量折叠、记录编译产物的 SASS 指令数并与计算量做一致性检查。

更根本的是度量评测器自身。一个基准应公开三项元指标：oracle 的假阳率与假阴率（由变异测试估计）、测速的重复性（同一实现多次评测的方差）、以及基线实现的稳定性。若某基准的重复性方差大到与任务间差异同量级，它的排名就没有意义。这三项指标的测量成本是离线的一次性投入，但它们是后续所有 RL 奖励可信度的前提。

具体机制上，可对每个提交做"影子评测"：用一组未公开的输入与一个独立的 oracle 实现交叉验证，只有两者一致才计入分数。影子评测的代价是评测时延翻倍与显存占用增加，但它把"针对公开 checker 调参"的作弊路径堵死。工程判断是：当评测预算有限时，优先保证 oracle 的假阳率低而非假阴率低——假阳会让错误实现获得奖励并污染训练信号，假阴只是让正确实现少拿分，前者不可逆，后者可容忍。

评测器自身的失效边界：从 oracle 假阳到基线漂移

多级正确性 oracle 的边界不在输入数量，而在输入分布的覆盖结构。随机输入只能命中“典型路径”，边界与极端输入才触发分支发散、归约尾部、越界掩码这些真正区分“能跑”与“真对”的位置；若把随机采样当成主判据，假阳率会被系统性低估——kernel 在 99% 的随机点上与参考一致，却在一个 stride 非对齐的尾部块上写越界。可执行的校准手段是变异测试：对参考实现注入受控缺陷（少一次同步、错一个索引偏移、漏掉边界判断），看 checker 能否逐类捕获。设注入变异体集合为 M，被 checker 判错的子集为 D，则检出率 det = |D|/|M|，未检出即 checker 的假阴上界。代价是编译与运行时间：每个变异体都要重新编译并跑完整输入套件，变异体数量与输入套件规模相乘，直接推高评测墙钟时间与 token 消耗（若由 agent 生成变异体）。工程判断是分层：廉价随机套件做门禁，边界/极端套件只在候选通过门禁后触发，把变异测试限制在 checker 变更时回归。

基线选择与测速口径是另一类失效源。随意基线（如 PyTorch eager 而非融合后的参考 kernel）会让加速比虚高，且不同测速工具（CUDA event、NCU 周期计数、wall clock）对同一 kernel 给出不可比的数字。归一化口径应锚定 roofline：以该 kernel 的算术强度与目标 GPU 的峰值带宽/算力算出 SOL 时间 t_SOL，报告 SOL 利用率 = t_SOL / t_measured，而不是裸加速比。这样跨架构比较退化为“离各自 roofline 多远”，消除了峰值参数差异带来的不可比。代价是建模成本：算术强度依赖访存模式假设，非规则访存（gather/scatter、稀疏）下 roofline 上界偏乐观，利用率会被高估，需要在报告中标注该假设并给出实测带宽反推的修正项。

泛化与迁移评测的失效条件是分布漂移未被显式建模。同一 kernel 在固定 shape 上快，换到 batch 变小、序列变长、dtype 变化时可能退化到 memory-bound 或触发不同的 tile 配置。协议上应把 shape 空间划分为训练可见区与留出区，留出区按维度外推（更大 batch、非 2 的幂长度）采样，并单独报告留出区通过率与 SOL 利用率下降幅度。变异测试与留出区评测的共同系统代价是评测器吞吐：每个候选要跑多套输入、多套基线、多套 shape，单次评测的 GPU 占用时间随套件层数线性增长，在 RL 多轮采样中会挤压 rollout 预算。可行的折中是缓存参考输出与 SOL 上界（按 shape 与 dtype 建索引），把重复计算从评测热路径移出，仅对 checker 变更做全量重校准。
