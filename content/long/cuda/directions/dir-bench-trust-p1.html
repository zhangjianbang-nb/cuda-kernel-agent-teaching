一 · 评测器本身是待测系统，不是裁判席

这个方向要解决的问题可以压成一句话：在 GPU kernel 生成这件事上，构建一套能区分「能跑」与「真快、真对、真可迁移」的评测基准，并同时量化评测器自身的误判率。注意后半句——量化评测器自身的误判率——才是这个方向区别于「造一个 benchmark 数据集」的根本。KernelBench 系基准的通行做法是：给定一个 PyTorch 参考实现，让 agent 生成 kernel，跑一遍正确性检查，再跑一遍计时，输出一个 speedup 数字。这个流水线里，正确性检查器、基线选择、测速口径三者都是人为选定的，它们不是自然常数。于是「某 agent 在 KernelBench 上达到 X 倍加速」这句话的语义，取决于 checker 有多松、baseline 有多弱、计时有多随意。评测器不是裁判席，它是整条流水线里最容易被优化掉的一环，因此必须被当作待测系统来测。

具体机制上，把评测器拆成三个可独立校准的部件：正确性 oracle、基线/测速口径、泛化协议。每个部件都有自己的误判模式。正确性 oracle 的假阳（把错的说成对的）会让 agent 学会写「数值上碰巧过」的 kernel；假阴（把对的说成错的）会砍掉合法但数值路径不同的实现，比如用不同累加顺序的 reduction。基线选择随意则直接改变 speedup 的分母：拿一个未调优的 eager 实现当 baseline，任何手写 kernel 都显得快；拿 cuBLAS/cuDNN 当 baseline，多数生成 kernel 立刻现形。测速口径不统一则让跨论文数字不可比——是否 warmup、是否含 launch 开销、是否用 CUDA event 还是 wall clock、是否固定 clock、是否在同一 MIG 切片上跑，每一项都能把数字移动一个量级。这三者的组合误差不是相加而是相乘：一个松 oracle 加一个弱 baseline，能稳定产出「又快又对」的假象。

$$\text{报告可信度} \;=\; \frac{1}{1 + \alpha_{\text{oracle}} + \beta_{\text{baseline}} + \gamma_{\text{timing}}}$$

这个式子是定性表达：三项误判率任意一项不可忽略，报告可信度就掉到不可用区间。工程代价在于，校准这三项本身要花算力与时间——变异测试要跑大量变异体，多级 oracle 要在随机/边界/极端输入上重复执行，SOL 归一化要为每个 shape 算 roofline 上界。这些开销不进 agent 的 token 预算，却进评测集群的 GPU 小时。一个具体例子：对同一个 softmax kernel，用「全 1 输入 + 固定 seed」做 oracle，任何把分母写成常数的实现都能过；换成含极大值、含 -inf mask、含全负数的输入集，同一份代码立刻暴露。前者省下的 oracle 成本，最终以「领域结论不可复现」的形式被整个社区支付。

二 · 边界：能测什么，不能测什么

这个方向的边界由「可观测的执行痕迹」划定。能测的是：给定输入分布下的数值正确性、给定 shape 与 dtype 下的时延与带宽、给定架构上的 SOL 占比、以及在受控变体上的行为一致性。不能测的是：kernel 在未见 shape 上的性能、在未见 GPU 架构上的可移植性、以及「这个 kernel 是否体现了某种可迁移的优化知识」——后者只能通过迁移协议间接推断，不能直接测量。把不可测的东西写成可测的指标，是这一方向最常见的越界。

多级正确性 oracle 是边界内的核心机制。它把「对」定义成一个输入集上的全称命题，而不是单点抽样。三级结构通常是：随机输入（覆盖一般数值路径）、边界输入（零、极小、极大、次正规数、NaN/Inf 传播）、极端输入（长序列、退化 shape、mask 全真/全假）。每一级都有明确的通过判据与容差。容差本身是设计决策：fp16 累加与 fp32 累加的差异、TF32 与 fp32 的差异，都必须写进容差而不是靠「差不多」放行。代价是执行时间线性增长——三级 oracle 意味着三倍于单点检查的 kernel 执行次数，若再叠加变异测试，成本按变异体数量再乘一次。

变异测试校准 checker 是量化 oracle 误判率的唯一手段。做法是：对参考实现注入语义保持的变异（重排累加顺序、换用等价但不同的归约树）与语义破坏的变异（漏掉 mask、错写 stride、把 softmax 分母换成常数），然后看 checker 是否分别放行与拒绝。语义保持变异被拒 = 假阴；语义破坏变异被放行 = 假阳。两个率必须同时报告，只报一个等于没报。这里的工程判断是：变异体的构造质量决定校准的有效性，构造一批「看起来像错但实际等价」的变异体，比构造一百个显然错误的变异体更有价值，也更贵。一个具体例子：把 layernorm 的均值计算从两遍循环改成 Welford 单遍，数值上等价但累加顺序不同，一个用严格 bitwise 比较的 checker 会判错——这正是假阴的来源，也是必须用容差而非 bitwise 的原因。

三 · 为什么其他方向替代不了

Agent 脚手架与执行反馈方向解决的是「怎么让 agent 拿到有用的反馈并迭代」，它默认反馈信号是可信的；多轮 RL 与可验证奖励方向解决的是「怎么把信号变成梯度」，它默认奖励是可验证的。这两个方向都在评测器下游。如果 oracle 有假阳，脚手架会把「碰巧过」的 kernel 当作成功样本继续 refine，RL 会把假阳奖励当成正样本强化——污染沿着流水线向后传播，且在下游无法被检测出来，因为下游只看到「奖励为 1」。这就是为什么校准必须先于反馈与奖励：不是流程顺序问题，是信号完整性问题的因果方向。

正确性 oracle 与形式验证方向处理的是「如何证明对」，它给出的是更强的正确性保证，但它不解决「测速口径」与「基线选择」。一个被形式验证证明正确的 kernel 仍然可能在一个弱 baseline 下报告出虚高的 speedup。形式验证替代不了评测口径的归一化，因为前者管的是语义，后者管的是比较基准。生产端到端部署方向处理的是「真实负载下的收益」，它天然带有真实 baseline 与真实计时，但它的代价是不可复现——生产流量、硬件状态、并发模式都不可控，无法用来做跨论文比较。硬件感知 DSL 与 profile 方向提供的是 SOL/roofline 与 NCU/SASS 级别的洞察，它是归一化测速口径的技术基础，但它本身不定义「什么算通过」。

于是这个方向的不可替代性落在两件事上：一是它定义了「对」与「快」的判据，二是它量化了判据自身的错误率。任何下游方向——脚手架、RL、部署——都消费这两个输出，却都不生产它们。代价是这一层的工作不产生「agent 变强」的直接证据，它产生的是「agent 变强的证据是否可信」的元证据。工程上这意味着它的产出形式是校准报告与协议文档，而不是更高的 pass@k 数字，因此在以数字论英雄的评价体系里天然吃亏。一个具体例子：两个 agent 在同一基准上报告 3 倍与 2 倍加速，若评测器未校准，无法判断差异来自 agent 还是来自两次运行用了不同的 baseline 与不同的 warmup 策略；校准之后，差异才能归因。

四 · 跨架构不可比：数字的物理边界

不同 GPU 架构与测速工具导致跨论文数字不可比，这不是工程疏忽，是物理边界。同一个 kernel 在两种架构上的 SOL 占比可以完全不同，因为 roofline 的拐点由带宽与峰值算力共同决定，而这两者随架构变化。因此「speedup 相对于 PyTorch」这个数字在跨架构比较时同时混入了两件事：kernel 相对 PyTorch 的改进，以及 PyTorch 在该架构上的实现质量。后者不是常数。用 SOL/roofline 归一化测速口径，是把「快」重新定义为「离物理上界有多近」，从而剥离 baseline 质量的影响。归一化后的指标是 SOL 占比，它跨架构可比的前提是每个架构的 roofline 上界被正确计算——而这又依赖对峰值带宽与峰值算力的准确取值，取值本身有误差。

归一化的代价是它需要为每个 shape 计算上界，而 shape 空间是组合爆炸的。实践中只能对基准中出现的 shape 逐个计算，这意味着归一化指标只在该 shape 集上有效，不能外推到未见 shape。另一个代价是 SOL 占比对 memory-bound 与 compute-bound 的判定敏感：一个 kernel 若实际是 memory-bound 却被按 compute-bound 的上界归一化，占比会被系统性低估。因此归一化必须附带 bound 类型标注，否则跨论文比较仍然是错的。一个具体例子：同一个 reduction kernel 在带宽受限架构上 SOL 占比高，在算力受限架构上占比低，若两篇论文各自报告 raw speedup 而不报 SOL 与 bound 类型，读者无法判断差异来自 kernel 还是来自架构。

五 · 泛化与迁移：评测协议的第二轴

「真可迁移」是三个判据里最难测的。泛化与知识迁移评测协议的做法是：在训练/生成时可见的 shape 与 dtype 集上评测之后，再在一组受控的未见变体上评测——未见 shape、未见 dtype、未见布局。变体的构造必须是系统性的，否则「泛化」退化成「碰巧覆盖了几个 shape」。协议要报告的是两个数字：分布内通过率与分布外通过率，以及两者的落差。落差本身就是信号：一个只在分布内通过的 kernel，说明 agent 学到的是对特定 shape 的拟合而非可迁移的优化知识。

代价在于分布外评测的 oracle 成本更高——未见 shape 上参考实现的正确性本身需要验证，且极端 shape 更容易触发数值问题，需要更严的容差设计。另一个代价是分布外变体可能触发未定义行为（越界、对齐违规），这类失败与「性能不迁移」是两类不同的失败，必须分开报告，否则通过率被混为一谈。工程判断是：迁移协议的变体集应当小而有代表性，而不是大而随机；每增加一个变体，就增加一份 oracle 与计时成本，而边际信息量递减。一个具体例子：一个在 1024×1024 上调优的 matmul kernel，换到 1×4096 的 skinny shape 上，tiling 策略完全失效，分布内通过率满分而分布外通过率归零——这个落差正是迁移协议要捕捉的东西，而单点基准完全看不到它。

把这三条轴——正确性 oracle 的误判率、测速口径的归一化、迁移协议的落差——放在一起，就得到这个方向的完整问题全景：它不是造一个更大的 benchmark，而是造一个能被审计的测量仪器。仪器的读数误差必须与读数一起报告，否则读数只是噪声的另一种写法。

评测器自身失效的边界条件与系统代价

把评测器当成被测对象，是本方向区别于其他方向的根本姿态：其他方向优化 kernel，这里优化的是「判断 kernel 好坏的那段代码」。它的边界由此划定——评测器只能在其 oracle 覆盖的输入分布内给出可信判决，一旦被测 kernel 的数值行为落在分布之外（例如只在极端指数、非规格化数或特定 stride 下出错），评测器就退化为一个高概率放行的过滤器。设 oracle 的假阴率为 α（错误 kernel 被判通过）、假阳率为 β（正确 kernel 被判失败），则单次判决的信息量受限于这两条错误率之和；多级 oracle 串联时，若各级独立，总假阴率近似为各级 α 之积，但代价是假阳率随级数累加，且每级都要付出一次完整执行的时延与显存占用。这就是为什么「多加几组随机输入」不是免费的：正确性验证的时延会挤占测速预算，而测速本身需要重复运行取稳定分位数。

变异测试是校准 α 的唯一可操作手段：向参考实现注入已知语义等价的变异（重排归约顺序、改变分块大小、替换精度路径），若 checker 将这些变异判为失败，说明它过严；注入已知语义破坏的变异（漏掉边界 mask、错位 shared memory 同步），若被判通过，则直接暴露 α。其系统代价是组合爆炸——变异体数量随 kernel 参数空间增长，每个变异体都要编译并跑完整 oracle 套件，编译时间与 GPU 占用成为校准成本的主项，且这套成本必须随参考实现更新而重复支付。一个具体例子：对归约类 kernel 注入「去掉最后一次 warp 内同步」的变异，若 checker 只比对最终标量而输入规模恰好是 warp 大小的整数倍，该变异会被静默放过，这正是 α 在真实基准中的典型来源。

跨架构不可比性构成第二重边界。SOL/roofline 归一化试图把「快」从绝对时延转成占理论上限的比例，但归一化的分母依赖显存带宽与峰值算力的实测口径，不同测速工具（事件计时、CUPTI、NCU 采集）对同一 kernel 给出的有效带宽本身就存在系统性偏差，于是归一化后的分数在跨论文比较时仍携带工具误差。工程判断是：把评测器误差显式建模为区间而非点值，报告中给出「判决置信区间 + 校准成本」，让下游 RL 奖励在误差带内做保守裁剪，而不是把单次通过当作真值使用。

$$\alpha_{\text{total}} \approx 1-\prod_{i=1}^{k}(1-\alpha_i),\quad \beta_{\text{total}} \approx 1-\prod_{i=1}^{k}(1-\beta_i)$$
