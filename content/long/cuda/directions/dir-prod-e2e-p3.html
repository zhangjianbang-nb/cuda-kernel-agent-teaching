一 · 基准分层：从微基准到 trace 回放的三级阶梯

评测侧第一件事不是选指标，而是把“基准”分层，让每一层回答一个不同的问题。第一层是算子级微基准：固定 shape、固定 dtype、固定 layout，测单 kernel 的时延与带宽，回答“这个 kernel 本身快不快”。第二层是子图级基准：把相邻若干算子按真实调用序列串起来，包含必要的中间张量分配与同步，回答“这段融合是否被调度开销吃掉”。第三层是 trace 驱动的端到端回放：从真实推理服务采集算子调用序列（op、shape、stride、dtype、stream、依赖边），在受控环境中按原顺序重放，回答“换掉这个 kernel 后整条链路是否真的变快”。三层缺一不可，因为微基准的加速比与端到端收益之间不是单调关系：一个在微基准上快 2 倍的 kernel，若引入了额外的 layout 转换或破坏了原有的流水重叠，端到端可能为零甚至为负。

分层的关键机制是“同一份 workload 描述贯穿三层”。工程上把 trace 解析成一张有向无环的调用图，节点携带 shape/stride/dtype 元组，边携带 stream 与事件依赖。微基准从图中抽取单节点，子图基准抽取连通子图，端到端回放执行整图。这样三层的差异只来自“被替换的节点范围”，而不是来自输入分布或测量方法的漂移。代价是 trace 采集与解析的工程成本：一次完整回放需要固定 GPU 型号、驱动版本、clock 策略，且 trace 文件本身可能达到数百 MB 量级，存储与重放时延都不可忽略；若 trace 中含隐私数据（用户输入长度分布、序列内容），还需脱敏并保证脱敏后 shape 分布不失真。

具体例子：一个 attention 的 fused kernel 在微基准上把单次调用从 T0 降到 0.6·T0，但子图基准显示它迫使上游做一次 contiguous 拷贝，端到端只降到 0.85·T0；trace 回放进一步显示该拷贝与下游 all-reduce 无法重叠，最终收益收敛到 0.9·T0 附近。这个阶梯的作用就是让“0.6”这个数字在到达部署决策前被逐层修正。

二 · 基线选择：同语义、同精度、同调度约束

基线不是“框架自带的那个 kernel”，而是“在相同语义、相同数值精度、相同调度约束下，当前生产实际使用的实现”。三者任一不同，加速比就失去意义。语义上要区分是否允许融合、是否允许改变归约顺序；精度上要区分 fp32 累加与 fp16 累加、是否启用 TF32；调度约束上要区分单 stream 串行与多 stream 重叠、是否允许占用额外 SM。基线选择错误是评测中最常见的系统性偏差来源：拿一个未融合的朴素实现当基线，会把“融合带来的收益”误记为“kernel 生成带来的收益”。

可执行的判定方法是构造基线矩阵：对每个待测算子，列出 (a) 框架默认实现、(b) 框架在最优 layout 下的实现、(c) 手写参考实现（若存在）、(d) 生成 kernel 的等价变体。加速比只在同一列内比较，跨列比较必须标注语义差异。公式上，定义有效加速比

$$S_{\text{eff}} = \frac{T_{\text{base}}^{\text{same-sem}}}{T_{\text{gen}} + T_{\text{glue}}}$$

其中 T_glue 是生成 kernel 为接入生产而引入的额外开销（layout 转换、额外同步、临时缓冲分配）。分母含 glue 是这条公式与微基准加速比的唯一实质差别。代价在于 glue 的测量本身需要插桩：在 kernel 前后打事件、统计额外拷贝字节数与同步次数，插桩会引入微小扰动，需用空插桩对照扣除。

具体例子：某归一化算子，框架默认实现在非连续输入上退化为逐元素路径，基线时延偏高；若直接与之比较，生成 kernel 显得收益巨大。正确做法是把基线换成“框架在连续输入上的最优路径”，此时生成 kernel 的收益从数倍收缩到十几个百分点，且 glue 中的一次转置拷贝解释了大部分差额。

三 · 输入分布：shape 采样与尾部分离

端到端收益对输入分布高度敏感。生产负载的 shape 分布通常是长尾的：多数请求落在少数几个常见序列长度上，少量长请求贡献了不成比例的时延。评测若只用均值 shape，会系统性高估生成 kernel 的收益，因为长尾 shape 往往触发不同的 tiling 策略、寄存器压力与 occupancy 退化。可执行的做法是从 trace 中提取 shape 直方图，按频次分层采样：头部（高频）全量覆盖，中部按分位抽样，尾部（低频但高代价）单独成组并强制纳入。

机制上，为每个 shape 组记录三个量：调用次数占比、单次时延、以及该组对总时延的贡献占比。伪代码思路是

$$\text{score} = \sum_{g \in \text{groups}} w_g \cdot \frac{T_{\text{base},g}}{T_{\text{gen},g} + T_{\text{glue},g}}, \quad w_g = \frac{n_g \cdot T_{\text{base},g}}{\sum_h n_h \cdot T_{\text{base},h}}$$

即按基线时延贡献加权，而非按调用次数加权。这样尾部高代价 shape 的权重被正确放大。代价是评测时延本身：尾部组单次运行时间长、方差大，需要更多重复次数才能得到稳定区间，整体评测 wall-clock 可能显著上升；同时尾部 shape 可能触发显存峰值，需单独监控峰值显存而非只看均值。

具体例子：一个 GEMM 类 kernel 在头部 shape（较小 M）上收益明显，但在尾部大 M 上因 tile 划分不当导致 occupancy 下降，单次时延反而劣于基线；按调用次数加权会得出“整体加速”的错误结论，按基线时延贡献加权则显示该 kernel 对总时延的净贡献为负，从而阻止部署。

四 · 指标：端到端时延、吞吐与尾分位

指标选择决定结论的方向。微基准常用“单次调用时延中位数”，但生产决策需要的是端到端时延分布、吞吐与尾分位。至少要报告：p50 与 p99 端到端时延、单位时间吞吐、以及峰值显存。p99 尤其重要，因为生成 kernel 的 tiling 或 occupancy 退化往往只在少数 shape 或少数并发水平下暴露，中位数会把它掩盖。吞吐与 p99 需要同时报告，因为二者可能反向：一个降低单次时延但增加显存占用的 kernel 会压低并发度，从而在吞吐上表现为负收益。

测量机制上，端到端时延必须在请求边界打点，而非在 kernel 边界打点；kernel 边界打点会漏掉框架调度、内存分配与同步等待。对回放系统，需固定请求到达模式（匀速或按 trace 的到达间隔），否则排队时延会污染 kernel 收益的归因。代价是测量噪声：端到端时延的方差来自调度器、显存分配器与 clock 波动，需用多次重复的置信区间而非单次读数；若 clock 策略未锁定，同一配置的重复测量可能给出不一致的 p99。

具体例子：某生成 kernel 把单次调用时延降低，但因临时缓冲使峰值显存上升，导致服务端并发 batch 数下降一档，吞吐不升反降；只报告单次时延的评测会给出“值得部署”的结论，而同时报告吞吐与峰值显存则给出相反判断。这就是为什么指标必须成组报告，且每组都对应一个部署约束。

五 · 防作弊：让加速比无法被构造

生成 kernel 的评测存在三类可被“构造”的加速：偷精度（用更低精度累加换取速度）、偷语义（跳过边界处理或假设输入已对齐）、偷测量（预热不充分、缓存命中被计入、只测有利 shape）。防作弊不是靠信任，而是靠可执行的检查项。精度检查：对同一输入比对生成 kernel 与高精度参考输出的误差分布，并规定误差上界；语义检查：注入非对齐、非连续、含 NaN/Inf 的边界输入，验证不崩溃且结果在容差内；测量检查：强制冷缓存与热缓存分别报告，强制报告预热轮次与被丢弃的首次调用。

机制上，把每个待测 kernel 视为一个黑盒，用一组“对抗输入”探测其假设。伪代码思路：

$$\text{pass} = \big[\forall x \in \mathcal{X}_{\text{adv}}: \|f_{\text{gen}}(x) - f_{\text{ref}}(x)\| \le \epsilon\big] \wedge \big[T_{\text{cold}} \text{ 与 } T_{\text{warm}} \text{ 均报告}\big]$$

其中对抗输入集包含非连续 stride、奇数长度、极端值。代价是评测吞吐：对抗输入通常走慢路径，单次运行时间长；同时参考实现本身可能很慢，误差比对的计算成本不可忽略。另一个代价是误杀：过于严格的误差上界会把合法的重排累加实现判为不合格，因此容差需按算子类型分别设定，而非全局一个常数。

具体例子：一个归约 kernel 在常规输入上误差合格，但在含 Inf 的输入上因未处理传播规则而输出错误；若评测只覆盖常规输入，该缺陷会进入生产。对抗输入集的作用就是在部署前把这类假设暴露出来，代价是评测集规模与运行时间上升。

六 · 建模：把评测结果折算成部署判断

评测的终点不是一张加速比表，而是一个可复核的部署判断。做法是把端到端回放结果折算成“单位请求成本”与“峰值资源占用”两个量，再与部署约束比对。折算公式为

$$\Delta C = \sum_g n_g \cdot \big(T_{\text{gen},g} + T_{\text{glue},g} - T_{\text{base},g}\big), \quad \text{约束：} \max_g M_{\text{gen},g} \le M_{\text{budget}}$$

ΔC 为负才意味着总时延下降；若 ΔC 为正但头部 shape 变快，说明收益被尾部抵消，部署判断应为“不换”或“按 shape 分发”。分发感知的调度正是从这里进入：评测侧需输出每个 shape 组上“生成 kernel 是否优于基线”的布尔表，供运行时按 shape 选择路径。代价是评测输出从单一数字变成一张表，且该表需随驱动、shape 分布漂移而重测；表的维护成本是持续评测的主要开销。

具体例子：回放显示生成 kernel 在头部 shape 上 ΔC 为负、尾部为正，折算后整体 ΔC 接近零；此时正确判断不是“整体无收益”，而是“按 shape 分发可在头部拿到收益且不伤尾部”，并把分发阈值作为部署产物之一交付。评测侧的可执行产出因此包含三样：分层基准结果、对抗输入通过情况、以及按 shape 的收益布尔表——三者共同构成“是否值得部署”的可复核证据链。

回放保真度的边界：当 trace 驱动评测自身成为误差源

trace 驱动回放的可信度取决于一个常被忽略的前提：回放负载与生产负载的到达过程同分布。采集到的 trace 本质是一次观测样本，它固定了请求序列、batch 组成与张量形状，却丢掉了生产环境中的到达随机性。回放时若按 trace 的原始时间戳串行重放，GPU 侧看到的是被“压平”的负载——真实系统里突发流量造成的排队、batch 拼装的抖动、KV cache 命中率随并发变化的漂移全部消失。此时测得的端到端收益是条件收益而非期望收益。可执行的修正是在回放器中引入到达过程重采样：以 trace 的经验分布拟合请求到达强度 λ(t) 与形状分布，按可配置的随机种子重新生成请求流，同一 kernel 变体跑 N 次取收益的均值与分位数。代价是评测时延：单次回放从确定性的一次性执行变为 N 倍采样，且每次采样都要重建 batch 拼装状态，显存侧需保留多份中间激活以支持并发形状。工程判断是 N 取到收益置信区间收敛即可，而非盲目加大。

第二个失效条件是基线选择的锚定效应。微基准里“相对 PyTorch eager 的加速比”几乎必然为正，因为 eager 路径包含大量逐算子 launch 与中间张量物化；但生产部署的真实基线往往是框架已融合的算子（如 cuBLAS 调优后的 GEMM、框架自带的 fused attention）或图编译器产出的融合 kernel。若基线仍取 eager，评测就把“消除框架开销”误记为“kernel 本身更优”，收益被系统性高估。正确做法是建立分级基线：L0 为 eager 逐算子，L1 为框架融合算子，L2 为图编译后的等价子图，报告必须同时给出相对三级的收益，并以 L2 作为部署决策依据。代价是基线构建本身的工程量与编译时间——L2 基线需要把目标子图从模型中切出并独立编译，切图边界处的 layout 转换会引入额外拷贝，这部分开销必须计入基线而非被隐去。

$$\text{端到端收益} = \frac{T_{\text{base}}(L2) - T_{\text{cand}}}{T_{\text{base}}(L2)},\quad \text{且}\ \text{收益}_{\text{净}} = \text{收益} - \frac{T_{\text{glue}} + T_{\text{launch}}}{T_{\text{base}}(L2)}$$

第三个边界是防作弊与测量口径的耦合。生成 kernel 常见的“作弊”不是算错，而是把代价挪到测量口径之外：异步流未同步导致计时偏小、把 layout 转换推给调用方、在 warmup 阶段完成一次性预处理却在计时阶段复用。可执行的防线是三项强制口径：计时区间必须包含输入 layout 变换与输出写回，且在每个测量点插入设备同步；warmup 次数与正式迭代次数固定并公开；正确性 oracle 除数值比对（含 NaN/Inf 与边界形状）外，追加对输出 stride 与 dtype 的断言，防止“数值对但布局错”蒙混。代价直接体现在评测吞吐上：逐点同步摧毁了流水线重叠，单次测量时延上升，且固定迭代次数使长尾 kernel 的评测墙钟时间显著拉长。一个具体例子是 attention 类 kernel：若允许候选在计时外完成 causal mask 的预计算，其测得的时延会低于把 mask 构造计入区间的诚实实现，而后者才是生产路径的真实成本。因此回放器与计时器必须共享同一份“计入区间”的声明，任何区间外的准备工作都要在报告中单列。
