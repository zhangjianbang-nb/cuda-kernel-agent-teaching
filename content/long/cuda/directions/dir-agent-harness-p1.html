一 · 问题的真实形状：从“生成一个 kernel”到“让一个 kernel 变快”

在 LLM 生成 GPU kernel 的整条链路里，生成只是起点。一个能编译、能跑对、在 KernelBench 这类基准上通过正确性检查的 kernel，距离“在目标硬件上接近 roofline”往往还差着数轮乃至数十轮改写。这中间的落差不是靠换一个更强的模型就能填平的：模型权重固定之后，剩下的全部杠杆都在脚手架——也就是 agent 如何组织“编译—运行—profile—改写”这个循环，如何从硬件执行反馈中提取信号，如何把信号变成下一步具体的代码动作。这个方向要解决的问题可以精确表述为：给定一个初始 kernel 与一个可执行的评测环境，agent 如何在有限预算内，把稀疏、带噪的执行反馈转化为一系列有明确因果指向的改写决策，而不是在代码空间里盲目游走。

把它称为“搜索问题”是准确的，但需要说清楚搜索的是什么。搜索空间不是自然语言描述的算法，而是具体的实现选择：tile 尺寸、线程块形状、共享内存布局、是否用向量化加载、循环展开因子、是否把某个归约拆成两段、是否切换到 warp-level primitive。这些选择彼此耦合，且每一个的收益都依赖硬件与输入形状。搜索的评估函数是“编译 + 运行 + 计时 + 正确性校验”这一整套昂贵操作，单次评估的代价以秒到分钟计，并且返回的信号既稀疏（大多数改写不改变性能或直接编译失败）又带噪（计时抖动、寄存器溢出导致的 occupancy 变化、编译器的启发式决策）。脚手架的设计决定了在这个昂贵且嘈杂的评估面上，每一次采样能换回多少信息量。

这里必须划出一条边界：本方向不负责“如何判定正确性”的完整体系，那是正确性 oracle 与形式验证条目的主题；也不负责“如何构造可信的基准与统计口径”，那是基准与可信评测条目的主题；更不负责“如何把 kernel 收益折算成端到端产品收益”，那是生产部署条目的主题。本方向只处理中间那段：从一次执行到下一次改写的映射。这个映射之所以独立成问题，是因为它既不属于模型能力（模型可以生成任意代码），也不属于评测基础设施（评测只给出数字），它是把两者接起来的决策层。

一个具体的例子能说明这条边界的位置。假设 agent 拿到一个朴素实现的 softmax kernel，第一次运行通过正确性检查，但 NCU 显示它的 achieved occupancy 偏低、global load 的 sector 利用率不足、且存在明显的 shared memory bank conflict。这三条 profile 事实指向三种不同的改写：提高 occupancy 可能需要减小寄存器压力或调整 block size；load 效率问题可能需要改变数据布局或引入向量化；bank conflict 需要重排 shared memory 的索引方式。脚手架的任务不是“知道这些知识”，而是决定先动哪一个、动多大、动完之后如何判断这次改动是否真的产生了预期效果、以及如果计时抖动掩盖了真实变化该怎么办。这就是本方向的核心工作量所在。

二 · 为什么反馈闭环不可省略：稀疏信号下的样本效率

把 kernel 优化交给一次性生成，等价于在一个高维离散空间里做零样本猜测。即便模型见过大量 CUDA 代码，它对“这段代码在这块卡上、对这个 shape 会跑多快”的先验也是弱的，因为性能是编译产物与硬件微架构交互的结果，而不是源码文本的属性。执行反馈的价值在于它把这个隐式的、不可靠的先验替换成显式的、可复现的观测。一次运行给出的不只是“快或慢”，而是可以分解的诊断量：每个 kernel 的 duration、SM 占用、memory throughput 相对峰值的比例、指令发射的 stall 原因分布。这些量把“慢”这个标量拆成若干可归因的维度，从而让下一步改写有方向。

用信息论的视角看，脚手架的目标是最小化达到目标性能所需的评估次数。设第 t 轮评估得到的反馈为 ft，改写动作为 at，则一个理想的决策策略应当最大化互信息 I(at; 性能增益 | ft)，即在给定当前诊断的前提下，选择那个最能减少性能不确定性的动作。工程上无法直接计算这个量，但可以用它作为设计准则：好的脚手架应当让每一轮反馈都缩小候选改写集合，而不是让 agent 在“再试一个 tile size”和“换一种算法”之间随机跳。

$$ \text{eval cost} = N_{\text{compile}} \cdot c_{\text{compile}} + N_{\text{run}} \cdot (c_{\text{launch}} + c_{\text{exec}}) + N_{\text{profile}} \cdot c_{\text{profile}} $$

这个代价分解说明了为什么“多试几次”不是免费的策略。编译本身在模板密集的 CuTe 或大规模展开的 CUDA 代码上可能耗时数十秒；profile（尤其是 NCU 的全量 metric 采集）会把单次执行放大若干倍；而计时抖动意味着同一个配置往往需要重复运行取中位数才能得到可用信号，这直接把 Nrun 乘以一个不小的系数。于是预算感知就不是优化项而是必需项：脚手架必须在“采集更贵的诊断”与“承担更盲目的改写”之间做取舍。一个常见的设计是分层采集——先用便宜的 wall-clock 计时筛掉明显退化的候选，只对性能进入前列的候选开启 NCU 细粒度采集。这个分层策略的代价是可能错过“计时看起来没变但 stall 结构已经改善、只差一步就能突破”的候选，这是用样本效率换诊断深度的典型折衷。

具体到工程判断：当一次改写后计时从某个基线下降到接近噪声底限时，脚手架若继续在同一维度上微调（例如把 tile 从 128 改到 120），其期望信息增益已经极低，因为计时抖动幅度可能大于真实差异。此时正确的动作是切换到另一个诊断维度，或者引入更精确的测量手段（固定 clock、增加重复次数、用指令级计数替代 wall-clock）。这个判断不是模型能凭代码文本做出的，它依赖脚手架对“当前信号是否已经饱和”的显式建模。

三 · profile 到改写动作的映射：缺失的中间表示

这是本方向最硬的挑战，也是它无法被其他方向替代的根本原因。NCU 给出的是一组硬件计数器：stall 原因分布、L1/L2 命中率、DRAM 吞吐、warp 发射效率、寄存器与 shared memory 用量。SASS 给出的是实际生成的指令序列。这些是“症状”，而改写动作是“处方”。从症状到处方之间，缺少一个可学习、可组合的中间表示。当前的实践大多靠规则或靠模型在 prompt 里“读懂”profile 文本后自行推理，前者脆弱（规则覆盖不到新 kernel 形态），后者不可靠（模型可能把 stall 归因错，或给出与诊断无关的改写）。

一个可行的中间表示应当把 profile 事实映射到“受约束的改写算子”上。例如把“long scoreboard stall 占比高”映射到“存在未被隐藏的 global memory 延迟”这一中间命题，再映射到候选算子集合 {提高 occupancy、软件预取、把加载提到循环外、改用异步拷贝}。每个算子带有前置条件（例如异步拷贝要求目标架构支持且数据布局允许）与预期收益方向。这样，改写就不再是从自然语言直接跳到代码，而是在一个有限的、语义明确的动作空间里选择。这个动作空间的大小直接决定搜索的可处理性：若动作空间有 K 个算子、每个算子有若干参数档位，则一轮的候选数是 K 乘以档位数，脚手架可以用剪枝把明显违反前置条件的候选剔除。

代价在于构建与维护这个中间表示本身。它需要把硬件计数器语义、编译器行为、代码变换三者对齐，任何一环的版本变化（新架构的 stall 分类、编译器换了调度策略）都可能让映射失效。另一个代价是表达力损失：把改写限制在预定义算子里，会排除掉那些“不在算子表里但确实有效”的创造性改写。这是用搜索空间的可控性换覆盖度的折衷，也是本方向与“硬件感知 DSL”条目交界的地方——DSL 提供的是受约束的代码空间，而这里提供的是受约束的动作空间，两者互补但不同层。

具体例子：一个 reduction kernel 的 NCU 显示 DRAM throughput 已接近峰值而 SM 利用率不高，中间表示应把它归为“memory-bound 且已饱和”，此时继续优化计算指令是无意义的，候选动作应集中在减少数据搬运（例如改变分块使每个元素只被读一次）或改变算法结构（两阶段归约减少原子操作）。若脚手架缺少这层归因，agent 很可能去调 unroll 因子，得到零收益，浪费一整轮预算。

四 · 噪声与失败：反馈信号的信噪比问题

执行反馈不是干净的标签。三类污染源必须被脚手架显式处理。第一是计时抖动：GPU 上的 wall-clock 受时钟频率波动、其他进程干扰、cache 状态影响，同一配置重复运行的方差可能吞掉真实的性能差异。第二是编译失败：模板实例化错误、寄存器溢出、非法内存访问在编译期或运行期终止循环，这类失败不提供性能信号，但消耗预算，且其错误信息往往指向语法而非性能。第三是寄存器溢出与 occupancy 的隐性退化：一次看似无害的改写可能让寄存器用量跨过阈值，occupancy 骤降，性能反而变差，而计时只告诉你“变慢了”，不告诉你为什么。

脚手架对这三类污染的处理方式决定了循环能否收敛。对计时抖动，标准做法是重复采样取稳健统计量（中位数或截尾均值），并设定一个“最小可辨差异”阈值，低于该阈值的改动视为无效果而不进入下一轮。对编译失败，脚手架需要把失败当作一种反馈而不是终止：失败信息应当被解析成“哪个约束被违反”，并作为负样本约束后续候选，避免在同一约束上反复失败。对 occupancy 退化，需要在改写后主动检查寄存器与 shared memory 用量，把它作为改写的守门条件而非事后诊断。

$$ \text{SNR} = \frac{\lvert \mu_{\text{after}} - \mu_{\text{before}} \rvert}{\sqrt{(\sigma_{\text{after}}^2 + \sigma_{\text{before}}^2)/n}} $$

这个比值给出了一个可操作的判据：当 SNR 低于某个门槛时，继续在同一维度上采样只是在消耗预算买噪声。脚手架应当据此触发“换维度”或“加测量精度”的动作，而不是机械地再跑一次。这里的具体代价是测量开销：提高 n 能提升 SNR，但每次运行都要花时间，预算感知的剪枝必须把测量开销计入总预算，否则会出现“为了确认一个微小收益而耗尽全部预算”的退化。

具体例子：某次改写把 shared memory 用量从接近上限推到超出，编译器把原本的静态分配改为动态或直接报错；若脚手架只看到“编译失败”就回退，它学不到“这个方向的改动已触及资源上限”这一有价值的信息。更好的处理是把失败归因到资源约束，并在后续候选中主动降低该方向的激进程度。这类归因不需要形式化验证，但需要脚手架维护一个跨轮次的约束记忆，这正是它区别于单次生成的地方。

五 · 为什么其他方向替代不了这一层

把这个问题拆给相邻方向看，会发现每一层都只覆盖一段。基准与可信评测解决的是“如何公平地测量与比较”，它给出可信的数字，但不决定下一步改什么；一个完美的基准不能替 agent 做改写决策。正确性 oracle 与形式验证解决的是“这次改写是否仍然正确”，它是守门员而非导航员；通过正确性检查的 kernel 仍可能离 roofline 很远。多轮 RL 与可验证奖励解决的是“如何用奖励信号训练策略”，它需要脚手架先产出结构化的轨迹与可验证的中间信号，否则奖励稀疏到无法学习。生产端到端部署解决的是“收益是否值得上线”，它关心的是端到端时延与回归风险，而不是单 kernel 的微架构效率。硬件感知 DSL 与 profile 提供的是表达空间与观测手段，但它们本身不做决策。

换句话说，这一层是唯一同时接触“代码动作空间”与“硬件观测空间”并负责在两者间建立因果链的地方。它的输出不是数字、不是通过/失败、不是训练样本，而是一个具体的下一步代码改动及其理由。这个输出是其他所有层的前提：没有它，RL 没有可学习的中间步骤，评测没有可比较的候选序列，部署没有可归因的收益来源。它的不可替代性来自这个位置，而不是来自某种算法上的独特性。

代价也随之而来：这一层的正确性无法被单点验证。一个改写决策的好坏只有在执行之后才知道，而执行结果又被噪声污染，于是脚手架的决策质量只能通过多轮累积的样本效率来间接衡量。这意味着它的工程评估指标不是“单步准确率”，而是“达到目标性能所需的评估次数”与“预算耗尽时的最好性能”。这两个指标都依赖基准与评测层的口径，但它们的优化对象是脚手架本身。

具体机制上，一个可落地的设计是把每一轮循环记录为结构化的一条：观测（profile 摘要）、归因（中间表示上的命题）、动作（改写算子及参数）、结果（编译状态、正确性、计时统计、资源用量）。这条记录既是脚手架做剪枝的依据，也是下游 RL 的可验证中间信号来源。它的存储与解析开销相对于编译与 profile 是小的，但它把原本散落在 prompt 里的隐式推理变成了可审计、可复用的状态。没有这层记录，多轮循环退化为无记忆的重复试错，样本效率无从谈起。
