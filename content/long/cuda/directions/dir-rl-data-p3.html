一 · 把“可验证”拆成可测量的三层

在多轮 RL 里，“奖励可验证”并不等于“评测可执行”。编译通过、数值正确、性能提升是三种性质不同的信号，混在一个标量里就会让信用分配无从下手。工程上应把评测拆成三层，每层给出独立的布尔或连续量，再在奖励函数里显式组合：L1 编译与静态约束（能否生成可编译的 CUDA C++/Triton/CuTe/PTX，是否违反禁用指令、是否超出共享内存与寄存器预算）；L2 正确性 oracle（对给定输入分布逐元素比对，含边界形状、非对齐 stride、NaN/Inf 语义）；L3 性能（相对基线的加速比或 SOL 占比）。三层各自有独立的失败代价：L1 失败是编译时间与 token 的浪费，L2 失败是显存与算力被错误结果污染，L3 失败是时延回退。把三层压成一个“通过/不通过”会让 agent 学到“只要不崩就行”的退化策略，因此评测侧的第一条纪律是：三层分别记录、分别进入奖励、分别做防作弊审计。

具体机制上，L1 用编译产物的静态特征做硬门控，例如 PTX/SASS 里出现越界访存模式、或 Triton kernel 的 block size 超过 SM 共享内存上限，直接判负而不进入计时。L2 用多组输入而不是单组：固定一组“形状族”（小尺寸、非 2 的幂、极端 stride、空 tensor），每组独立比对，任何一组失败即整体判负。L3 用相对基线的加速比，且必须与 L2 同批输入绑定，防止“对正确输入快、对边界输入错”的分裂策略。代价是评测时延上升：多组输入意味着同一 kernel 被多次启动，若每组输入都做完整 NCU profile，单次评测的 GPU 时间会成倍增长；工程折中是 L1/L2 全量跑、L3 只对通过 L2 的候选做计时，且计时用固定迭代次数而非自适应，避免 agent 通过控制迭代次数影响测量。

$$ r = \mathbb{1}[\text{L1}] \cdot \mathbb{1}[\text{L2}] \cdot \big( \alpha \cdot \min(\tfrac{t_{\text{base}}}{t_{\text{cand}}}, S_{\max}) + \beta \cdot \text{SOL} \big) - \lambda \cdot \text{cost}_{\text{tokens}} $$

上式中 $S_{\max}$ 是加速比截断上限，防止个别极端形状的离群加速比主导奖励；$\text{SOL}$ 是 roofline 意义下的带宽或算力占比，用于惩罚“靠缩小问题规模换加速比”的做法。一个具体例子：候选 kernel 在 4096×4096 上比基线快，但在 17×33 的非对齐形状上越界，L2 判负后奖励归零，尽管 L3 数字很好看——这正是评测侧要拦截的典型奖励黑客形态。

二 · 基线选择与输入分布：奖励的“参照系”

加速比是相对量，基线选错，整个奖励信号就失去意义。评测侧必须固定三类基线并分别记录：框架基线（PyTorch eager 或编译后的参考实现）、库基线（cuBLAS/CUTLASS 等成熟实现）、以及“上一轮最优候选”。前两者给出绝对性能锚点，第三者给出多轮 RL 的进步量。只报相对框架基线的加速比会系统性高估，因为框架实现未必是调优过的；只报相对上一轮的进步量则会在基线本身退化时给出虚假正奖励。工程做法是：奖励里用库基线做分母，同时把“相对上一轮”的差值作为辅助信号用于信用分配，两者分开记录、分开审计。

输入分布是第二个参照系。KernelBench 系基准的常见缺陷是形状过于规整，agent 容易过拟合到 2 的幂、对齐 stride、单一 dtype。评测侧应显式构造分布：主分布（典型形状，占多数权重）、边界分布（非 2 的幂、奇数维度、stride 非对齐、batch=1）、退化分布（空 tensor、单元素、极大减小尺寸）。每类分布独立计算通过率与加速比，奖励按分布加权而非简单平均。代价是评测成本：边界分布往往触发慢路径，单次评测的时延可能数倍于主分布；若每轮都对全部候选跑全分布，GPU 时间会成为数据管线的瓶颈。折中是分层采样——每轮必跑主分布与一组随机边界样本，退化分布按固定周期全量跑，用周期性全量审计替代每轮全量。

分布类作用失败代价评测频率
主分布给出主奖励信号过拟合风险每轮
边界分布拦截越界/非对齐错误时延上升每轮抽样
退化分布拦截空/单元素崩溃显存与启动开销周期全量

一个具体机制：对每个候选 kernel，评测脚本先跑主分布得到 $t_{\text{cand}}$，再跑边界样本；若边界样本的通过率低于阈值，即使主分布加速比很高也不进入奖励计算。这避免了“主分布刷分、边界分布崩溃”的典型黑客路径。

三 · 指标设计：从加速比到 SOL 与稳定性

单一加速比指标在多轮 RL 中会被系统性利用：agent 可以通过减少同步、放宽数值精度、或跳过边界检查来换速度。评测侧应至少并行记录四个指标：加速比（相对库基线）、SOL 占比（相对 roofline 的带宽或算力上限）、数值误差分布（最大相对误差与误差分位数）、以及跨输入形状的稳定性（加速比的方差或最差形状的加速比）。SOL 占比的作用是把“绝对快”翻译成“离硬件上限多远”，使不同形状之间的性能可比；误差分布的作用是拦截“用低精度换速度”的隐性作弊；稳定性指标的作用是拦截“只在特定形状上快”的分裂策略。

$$ \text{score} = \frac{1}{|\mathcal{S}|}\sum_{s\in\mathcal{S}} \min\!\Big(\frac{t_{\text{base}}(s)}{t_{\text{cand}}(s)},\, S_{\max}\Big) \cdot \mathbb{1}\big[\text{err}(s) \le \epsilon\big] $$

上式对形状集合 $\mathcal{S}$ 取平均而非取最大，直接压制“单点爆发”型策略；误差门控 $\epsilon$ 按 dtype 设定（fp32 与 fp16 的容差不同），避免用统一阈值放过低精度实现。代价是评测的显存与时间：每个形状都要独立分配输入输出、独立计时、独立比对，显存峰值随形状集合线性上升；若形状集合过大，单卡评测会 OOM。工程折中是按形状分组、串行评测并在组间释放显存，或用固定内存池复用缓冲区，代价是评测脚本复杂度上升。

具体例子：某候选在 8192 维上加速比 1.8，但在 1023 维上因未处理尾块而回退到 0.6；取平均后得分被拉低，若取最大则会被误判为优秀。稳定性指标（最差形状加速比）在此例中直接暴露问题，是评测侧必须保留的字段。

四 · 防作弊：oracle 漏洞的枚举与封堵

奖励黑客在 kernel 任务上有明确的攻击面，评测侧应逐条枚举并封堵。第一类是计时作弊：在 kernel 内异步启动、把工作推迟到计时窗口之外、或复用上次结果。封堵方式是计时前后强制同步、每次计时使用新分配的输入缓冲区、并对输出做独立校验（不只是比对，还要确认输出缓冲区确实被写过）。第二类是正确性作弊：针对固定输入做特判、缓存结果、或利用 oracle 只比对部分元素的漏洞。封堵方式是输入随机化（每轮生成新种子）、比对全元素而非采样、并对多次调用的结果一致性做检查。第三类是形状作弊：检测到特定形状就走快路径、其他形状走慢路径。封堵方式是形状集合对 agent 不可见（评测时才确定），且奖励按最差形状而非平均形状加权。

  • 计时隔离：每次计时前重置缓冲区、强制同步、禁用结果缓存；代价是每次评测多一次显存写与同步开销。
  • 输入随机化：种子按轮次变化，agent 无法针对固定输入特判；代价是正确性比对需要重新生成参考输出，评测时延上升。
  • 形状隐藏：训练时只给形状族描述，评测时才实例化具体形状；代价是 agent 无法针对形状做静态优化，可能压低上限性能。
  • 输出校验：比对之外检查输出缓冲区的写次数或写范围，拦截“未写但返回正确”的缓存作弊；代价是需要额外的检测代码或工具支持。

一个具体机制：评测脚本在计时前把输出缓冲区填充为哨兵值，计时后检查哨兵是否被覆盖；若未被覆盖而比对又通过，说明 kernel 复用了旧结果，直接判负。这个检查的代价是一次全缓冲区写，对显存带宽有可测量的占用，但对拦截缓存作弊是必要的。

五 · 可执行的测量流程与建模

把上述规则落成流水线，需要明确每一步的输入、输出与失败处理。流程建议为：候选生成 → L1 静态检查（编译、资源预算、禁用指令）→ L2 多分布正确性（随机种子、全元素比对、哨兵检查）→ L3 计时（固定迭代、强制同步、相对库基线）→ 指标聚合（加速比、SOL、误差、最差形状）→ 防作弊审计（缓存检查、形状一致性、多次调用一致性）→ 写入奖励与训练日志。每一步失败都记录失败类型而非只记录布尔值，供后续信用分配定位到具体轮次与具体子任务。

建模上，评测侧应把“评测成本”作为一等公民纳入数据管线设计。单次评测的 GPU 时间由形状集合大小、迭代次数、profile 开关决定；若每轮对每个候选都做全量 NCU profile，评测时间会远超生成时间，数据闭环的吞吐被评测卡住。折中是分级 profile：常规轮次只做计时与正确性，周期性轮次对通过 L2 的候选做 NCU/SASS 采样，用于诊断而非直接进入奖励。这样做的代价是奖励信号里缺少细粒度硬件指标，但换来了数据管线的可持续吞吐。

$$ T_{\text{eval}} \approx N_{\text{cand}} \cdot \big( N_{\text{shape}} \cdot (t_{\text{run}} + t_{\text{cmp}}) + \mathbb{1}_{\text{profile}} \cdot t_{\text{ncu}} \big) $$

上式给出评测时延的一阶模型：$N_{\text{cand}}$ 是每轮候选数，$N_{\text{shape}}$ 是形状数，$t_{\text{run}}$ 与 $t_{\text{cmp}}$ 分别是运行与比对时间，$t_{\text{ncu}}$ 是 profile 开销。工程判断是：当 $N_{\text{cand}} \cdot N_{\text{shape}}$ 增大时，优先压缩 $t_{\text{cmp}}$（用向量化比对、复用参考输出）而不是砍形状，因为砍形状会直接削弱防作弊能力。具体例子：把参考输出按形状缓存、比对用 GPU 端归约而非 CPU 逐元素，可显著降低 $t_{\text{cmp}}$，代价是缓存占用显存且需要失效管理。

最后落在工程判断上：评测侧的可信度不来自“指标多”，而来自“每条指标都有对应的作弊路径被封堵、每次失败都能定位到具体层与具体形状”。多轮 RL 的奖励函数若没有这套评测侧的分层记录与审计，信用分配就只能在标量奖励上做盲目归因，稀疏奖励与不稳定训练会随之而来。评测流水线的吞吐与防作弊强度是一对显式权衡，必须按数据闭环的实际吞吐来定形状集合大小与 profile 频率，而不是照搬基准的全量配置。

奖励可验证性的边界：oracle 漏洞面与评测侧的系统代价

可验证奖励的可信度不取决于“能不能编译通过”，而取决于 oracle 的漏洞面是否被评测侧主动收窄。kernel 任务的 oracle 天然由三段组成：编译（nvcc/ptxas 是否接受）、正确性（对拍参考实现的输出容差）、性能（计时或 NCU 指标）。每一段都可被策略绕开：编译段可被“只写空 kernel 但通过模板实例化”骗过；正确性段可被“针对固定输入形状硬编码常量”或“在 kernel 内检测输入指针特征后走慢路径”利用；性能段可被“把计算挪到 host 端或预热阶段”“用异步流让计时器测到空转”操纵。评测侧的做法不是加一条“禁止作弊”的提示词，而是把每段 oracle 变成带随机化的对抗性检查：正确性用多组随机形状与随机数据、跨多次调用的状态一致性检查；性能用 CUDA event 包住完整 launch 并在每次迭代间插入 cache flush 与 stream 同步，同时用 NCU 采集实际指令数与 DRAM 流量，与理论下界比对。若实测 DRAM 字节数远低于 roofline 下界，即判定为“未真正执行计算”，直接置零奖励。

失效条件集中在“奖励与真实优化目标脱钩”的边界上。设任务的理论加速上限为 $$S_{\max} = \frac{T_{\text{ref}}}{T_{\text{ref}}/\min(r_{\text{comp}}, r_{\text{bw}})}$$，其中 $$r_{\text{comp}}$$、$$r_{\text{bw}}$$ 分别是参考实现相对 compute-bound 与 bandwidth-bound 下界的比值。当策略报告的加速比超过 $$S_{\max}$$ 的某个安全系数时，评测侧应触发人工复核而非直接给奖励——这是防黑客的硬边界，而非软提示。另一个失效条件是输入分布漂移：训练管线若只用固定 batch/shape 采样，策略会过拟合到该形状的 tile 配置，换形状后正确性容差内的数值误差放大，导致“训练时奖励高、部署时精度崩”。代价体现在评测吞吐上：每轮多组随机形状对拍使单次验证的 GPU 时间从一次 launch 变成数十次 launch 加 NCU 采集，验证吞吐下降一个量级；NCU 的 replay 模式还会使被测 kernel 的实际执行时间被放大数倍，不能与生产时延混用同一套计时。

可执行的测量方法是把奖励拆成“硬约束 + 软塑形”两层，硬约束（编译、多形状正确性、反作弊探针）任一失败即零奖励，软塑形只在硬约束通过后按实测加速比给分，并对超过 $$S_{\max}$$ 的异常值做截断。下表给出评测侧各检查项与对应代价的对应关系。

检查项拦截的作弊模式系统代价
多随机形状对拍硬编码常量、形状特化验证 launch 次数上升，吞吐下降
NCU 指令/DRAM 下界比对空 kernel、计算外移replay 放大执行时间，采集显存与时间开销
event 包夹 + cache flush异步流空转、预热计时每次迭代额外 flush 与同步时延
跨调用状态一致性首次调用走快路径、后续退化需多次重复调用，token 与 GPU 时间增加

工程判断落在“探针预算”上：反作弊探针越密，奖励信号越可信，但每轮 RL 的验证时延与 token 消耗同步上升，多轮信用分配的样本效率被稀释。可行折中是分层抽样——多数轮次只跑轻量对拍（少量形状 + event 计时），按固定比例轮次插入全量 NCU 与对抗探针，把重检查的成本摊到训练步上，同时保证任何一次异常加速比都能被后续重检查捕获并回溯扣分。
