一 · 被随机测试掩盖的失效面

LLM 生成的 kernel 在评测流水线里最常见的通过信号是“跑一批随机输入，与 PyTorch 参考实现比对 allclose”。这个信号的问题不在于它弱，而在于它的失效模式是静默的：一个 kernel 在 N=1024, C=64 的随机张量上误差 1e-6，在 N=1 或 N=1023（非整除尾块）上却写越界或漏算最后一个 tile；一个归约 kernel 在 batch=1 时正确，在 batch=7 时因为 grid 维度映射错位而把不同样本的 partial sum 混在一起。随机测试的采样分布几乎必然落在“对齐、整除、单批次”这些良性区域，而边界条件恰恰是分布的尾部。这就是“正确性幻觉”的工程含义：通过率是采样密度的函数，不是正确性的函数。

把这个失效面形式化一下。设 kernel 的输入空间为 $\mathcal{X}$，参考实现为 $f$，生成 kernel 为 $g$，随机测试等价于从某个提议分布 $q(x)$ 中抽 $m$ 个样本并检验 $\|g(x)-f(x)\|\le \tau$。测试通过只给出

$$\Pr_{x\sim q}\big[\|g(x)-f(x)\|\le\tau\big]\approx 1$$

而部署需要的是 $\sup_{x\in\mathcal{X}}\|g(x)-f(x)\|\le\tau$，或至少在一个显式声明的契约域上成立。两者之间的差距由 $q$ 对 $\mathcal{X}$ 的覆盖度决定，而 $q$ 通常由测试框架的默认 shape 采样器给出，与真实负载的 shape 分布无关。代价是双向的：把 $m$ 从几十提到几千只能把尾部漏检概率压低一个量级，却让每次 agent rollout 的验证时延线性增长——在 RL 场景里，验证时延直接吃掉 rollout 吞吐，token 预算被浪费在重复的良性样本上；而真正的边界样本（N 非 2 的幂、stride 非连续、空张量、极小的 M）在均匀采样下出现的概率接近零。

具体例子：一个 layernorm 的 Triton 实现，行长度 N 作为 constexpr 传入，agent 为常见尺寸 1024/2048 生成了带向量化的版本，随机测试全过；当 N=1000 时，尾块 mask 写错一位，越界写入相邻行，随机测试因采样不到该尺寸而放行，直到生产端出现跨行污染。这个例子里没有任何“难”的数值问题，纯粹是契约域没被枚举。所以本方向的第一性问题不是“怎么测得更准”，而是“怎么把测试从采样变成对契约域的覆盖证明”。

二 · 契约的三层结构与可审计性

生产部署要求的不是“我觉得它对”，而是一份可审计的正确性契约：一组显式声明的前提、一组被检查的后置条件、以及检查过程本身可复现。把契约拆成三层，每层的验证手段和代价都不同。

  • 形状/索引契约：输入 shape、stride、对齐、dtype、空张量与退化维度。这一层是离散的、可枚举的，验证代价主要是编译时间与用例数，不涉及浮点。
  • 语义契约：批不变性（batch invariance，同一元素在不同 batch 组合下的输出逐位一致或落在声明误差内）、确定性（同一输入多次运行结果一致，排除 atomicAdd 的非确定归约）、mask 与 padding 的语义。
  • 数值契约：误差界 $\tau$ 的定义方式——是绝对误差、相对误差、还是 ULP 距离；在什么范数下；对归约顺序变化的敏感度上界。

三层里最容易被跳过的是第二层。批不变性检查的机制很直接：固定某个样本 $x_i$，把它分别放进 batch size 为 1、3、8、17 的输入中，比较 $g$ 在对应位置的输出。若 kernel 内部用了跨 batch 的归约（例如把整个 batch 展平后做一次 reduction），或用了依赖 grid 配置的 tile 划分，输出会随 batch 组合漂移。检查的代价是 $O(\text{batch 候选数})$ 次前向，显存占用随最大 batch 增长，但相比形式验证几乎为零。确定性检查则要重复运行同一输入并逐位比对，代价是时延翻倍，且会暴露 atomicAdd 类归约的非确定性——这在浮点上是合法实现，但在要求可复现的生产契约里是不可接受的。

可审计性的关键不是“跑过”，而是“跑过什么、以什么前提跑过”。一份契约应当记录：被枚举的 shape 集合（含边界）、误差度量与阈值、批不变性检查的 batch 组合、以及每条检查对应的参考实现版本。没有这些，性能收益无法被信任——一个快 3 倍的 kernel 如果只在良性 shape 上被验证过，它的加速比在真实负载上不可外推。

三 · 浮点非结合性：等价性定义的硬边界

形式验证在这个方向上的根本困难不是工具不够强，而是“等价”本身在浮点上没有唯一含义。IEEE-754 的加法不满足结合律：$(a+b)+c \ne a+(b+c)$ 在舍入下普遍成立。并行归约天然改变求和顺序——tree reduction、split-K、warp shuffle 的顺序都与串行参考不同。因此一个数值上完全正确的并行 kernel，其输出与串行参考逐位不等是正常的，不是 bug。形式等价若定义为逐位相等，会把所有合法并行实现判为失败；若定义为误差有界，则要先给出界。

可行的定义方式是：对给定输入，声明一个误差上界 $\tau$，并要求 $\|g(x)-f(x)\|\le\tau$ 对所有契约域内的 $x$ 成立，其中 $\tau$ 由浮点误差分析给出而非拍脑袋。一个粗糙但可用的界来自归约深度：若求和涉及 $n$ 项、每步相对误差上界为 $u$（单位舍入），则顺序求和的误差界约为 $nu$，而平衡树归约约为 $\lceil\log_2 n\rceil u$。这解释了为什么并行归约的误差通常小于串行累加，也解释了为什么用串行参考做逐位比对是错误的方法论。代价在于：误差界是保守的，实际误差远小于界，用界做阈值会放过一些真实 bug；用更紧的经验阈值又失去可证明性。这个张力是本方向无法回避的。

具体例子：一个 split-K 的 GEMM，K 维被切成 8 段并行累加再合并。与 cuBLAS 参考比对时相对误差 1e-5，随机测试通过；但若契约要求与某个特定串行实现逐位一致，它必然失败。正确的契约应声明“在 fp32 下相对误差 ≤ 某界，且对 K 切分数不敏感”——后者本身就是一个需要检查的性质，而不是可以从误差界推出的。

四 · 形式工具对 CUDA/Triton 语义的覆盖缺口

符号执行与形式验证在 CPU 侧有成熟工具链，但搬到 GPU kernel 上会遇到语义覆盖问题。CUDA 的执行模型包含线程束（warp）级的隐式同步、共享内存的 bank 冲突语义、__syncthreads() 的屏障语义、以及未定义行为（越界、数据竞争）在硬件上的实际表现。符号执行器若把每个线程当作独立顺序程序处理，就丢失了 warp 内 shuffle 与屏障的耦合；若试图建模整个 block 的交错执行，状态空间随线程数指数爆炸。Triton 的抽象层次更高（block 级编程、编译器负责线程映射），符号执行需要建模的是 Triton IR 的语义而非 PTX，但 Triton 的语义文档与形式化定义并不完整，mask 语义、tl.load 的边界行为、归约的确定性都没有权威的形式规约。

代价是双重的。其一是覆盖代价：能进形式验证的 kernel 规模受限于状态空间，通常只能验证小 shape（例如 $N\le 64$）上的索引正确性，而真实 kernel 的 tile 尺寸是 128/256，验证时的抽象需要证明“小 shape 正确蕴含大 shape 正确”，这一步本身需要归纳不变式，往往比验证本身更难。其二是工程代价：把 CUDA kernel 翻译成验证器可接受的中间表示需要人工或半自动的建模，编译时间从秒级升到分钟级，在 agent 多轮迭代的场景里这个时延不可忽略。因此形式验证在当前工程实践中的定位不是“替代随机测试”，而是“对高风险 kernel 的索引与同步逻辑做局部证明”，其余部分仍靠契约感知的测试覆盖。

具体例子：一个带共享内存 tiling 的卷积 kernel，索引逻辑包含 blockIdx、threadIdx 与边界 mask 的三重组合。符号执行可以证明在 $N=16$ 时无越界，但要推广到 $N=1024$ 需要证明 tile 划分的归纳性质；实际工程里更常见的是用契约测试枚举 tile 边界（N mod tile == 0 与 == tile-1）来近似这个证明，代价是枚举数随维度组合增长。

五 · 为什么其他方向替代不了这一层

把本方向与其他方向的分工说清楚，才能界定它的边界。基准与可信评测回答的是“在固定任务集上谁更强”，它的度量是聚合通过率与加速比，本质上仍是采样——任务集是有限的，通过率不构成对任意输入的保证。Agent 脚手架与执行反馈提供的是编译错误、运行时错误、以及测试失败的信号，它能高效排除崩溃类错误，但对“通过测试的静默错误”无能为力，因为反馈信号本身来自同一批随机测试。多轮 RL 与可验证奖励把正确性当作奖励项，可验证奖励的“可验证”程度取决于验证器，若验证器是随机测试，RL 会把策略优化到“通过随机测试”而非“正确”，这正是正确性幻觉被强化的路径。生产端到端部署关心的是真实负载下的收益，它需要契约作为前提，而不是自己生产契约。硬件感知 DSL 与 profile 关心的是性能上限与瓶颈定位，roofline 分析假设 kernel 已经正确。

换句话说，其他方向都在“正确性已给定”的前提下工作，而本方向生产的就是这个前提。它的边界也很明确：它不负责性能，不负责搜索，不负责部署；它负责把一个 kernel 的适用域、误差界、确定性性质写成可检查、可复现的契约，并在这个契约上给出尽可能强的证据——从枚举边界到局部形式证明。这个定位决定了它的成本结构：验证时延、编译时间、以及为形式化建模付出的人力，都是它必须计入的代价，而不是可以忽略的开销。

工程判断上，一个可操作的划分是：索引与同步逻辑用契约枚举加局部符号执行覆盖，数值部分用误差界加批不变性检查覆盖，确定性用重复运行逐位比对覆盖。三者的组合不构成完整的形式证明，但它把“随机测试通过”升级为“在声明域上被检查过”，这正是可审计性的最低要求。任何声称“kernel 正确”而不附带契约域与检查记录的说法，在这个框架下都不成立。

契约边界：oracle 能承诺什么、在哪儿失效

把「正确性 oracle」当成一个判定函数看，它的输出不是布尔值而是三态：通过、拒绝、不可判定。形式验证侧真正能给出的强保证，只覆盖被显式建模的那部分语义——索引算术、共享内存同步、归约顺序、边界谓词。一旦 kernel 里出现未建模的浮点行为（编译器重排、FMA 收缩、`--use_fast_math` 下的近似指令），验证器只能退回「假设」模式，此时它证明的是模型而非二进制。这就是边界的第一层：被证明的对象与真正部署的 cubin 之间存在语义缺口，缺口大小取决于编译选项与目标架构，而不是验证器本身的强度。工程上必须把这个缺口显式记录进契约，否则「已验证」标签会变成新的正确性幻觉来源。

第二层边界是浮点等价性本身的可定义性。并行归约的非结合性使得「同一数学函数」在浮点下对应一族结果，形式等价只能定义为误差界内的包含关系：对输出张量 $y$ 与参考 $y^\*$，契约要求 $\lVert y-y^\* \rVert_\infty \le \tau_{\text{abs}} + \tau_{\text{rel}}\lVert y^\* \rVert_\infty$，且该界需对任意批大小 $B$ 与任意分块配置成立。批不变性检查因此不能只跑单批，必须在 $B \in \{1, \text{非对齐尾块}, \text{满载}\}$ 上验证同一元素的结果落在同一误差球内——这条约束把测试从「一次前向」变成「一组前向」，直接放大了验证时延与显存占用：每个批配置都要保留参考输出与中间归约缓冲，显存代价随配置数线性增长，而形式化路径的代价更陡，符号执行对含循环的归约核往往在路径爆炸处不可判定。

第三层是系统代价的不可替代性论证。随机测试的代价是 $O(\text{采样数})$ 次前向，覆盖的是输入分布的典型区域；契约感知验证的代价是「契约维度」的笛卡尔积——边界谓词、批组合、数值容差、确定性开关。下表对比三类手段在失效条件上的分工，说明为什么其他方向替代不了这一层：

手段能覆盖典型失效条件主要代价
随机测试典型输入下的数值偏差尾块、非对齐批、极端指数采样时延，覆盖不可审计
NCU/SASS profile性能与访存行为不判定数值正确性profile 开销，无正确性契约
契约感知验证边界、批不变性、误差界未建模浮点语义、路径爆炸多配置前向 + 符号执行编译时间

具体例子：一个 layernorm 融合核在 $B=1024$（对齐）时随机测试全通过，但当 $B=1023$ 触发尾块、线程束内归约顺序改变，末元素因累加顺序不同超出 $\tau_{\text{rel}}$ 而被生产监控捕获——这正是随机测试的盲区，也是契约验证必须把「批大小 × 分块 × 容差」写进 oracle 输入的原因。反过来，若把全部希望寄托于形式化工具，则要面对 CUDA/Triton 语义覆盖不足的现实：工具不理解 `__shfl_down_sync` 的掩码语义或 Triton 的 block-level 抽象时，验证器只能对降级后的标量模型下结论，代价是编译时间与人工建模，收益却止步于模型层。因此这一方向的工程定位不是「替代测试」，而是把不可审计的通过变成可审计的契约：明确哪些性质被证明、哪些被采样、哪些被声明为不可判定，并让下游部署决策读取这份三态记录而非单一绿灯。
