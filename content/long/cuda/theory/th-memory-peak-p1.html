一 · 一句话直觉：速度是用显存买来的

峰值内存约束这件事，最凝练的直觉是：kernel 的加速比不是免费的，它常常以更大的中间缓冲为代价。一个算子可以用分块、重排、双缓冲、前缀和物化、原子累加替代规约等手段，把串行依赖打断、把访存合并、把分支消除，从而把时延压下来；代价是执行期间某一时刻同时驻留的张量变多、变大。对单卡跑一个孤立 kernel 的评测来说，这部分额外占用往往被忽略；但放到生产推理链路上，它直接挤压 KV cache 的容量与并发 batch 的上限，于是“更快的 kernel”反而让端到端吞吐下降。KernelBench-Verified 的统计给出了这一现象的规模：28% 的核在变快的同时增加了峰值内存。这个比例说明它不是边角案例，而是生成式优化的系统性偏向——因为奖励信号通常只看时延与正确性，不看显存。

因此本部分要建立的不是“省显存”的技巧清单，而是一个判断框架：把峰值内存当作与正确性、时延并列的一等约束，而不是事后审计的附属指标。读者若已熟悉 Roofline 可达上界与 SOL 归一化评分口径，应把峰值内存理解为第三个正交维度：一个 kernel 可以同时是 SOL 高分、数值正确、却因峰值超标而在生产不可用。

二 · 严格定义：三个加数和一个上界

把“峰值”定义清楚，是后续所有测量与优化的前提。执行期间的峰值显存指从 kernel 启动到其所有下游依赖完成之间，设备上同时驻留的显存的最大值。它由三部分构成：输入张量占用、输出张量占用，以及各执行阶段临时缓冲的最大值。写成约束形式：

$$M_{\text{peak}}=M_{\text{in}}+M_{\text{out}}+\max_{\text{stage}}M_{\text{tmp}}(\text{stage})\le M_{\text{budget}}$$

这里的关键在于第三项取的是阶段最大值而非总和：临时缓冲的生命周期彼此重叠程度不同，一个 stage 结束后其缓冲可被复用，所以峰值是时间轴上的上确界，而不是所有分配的算术和。这一点决定了优化方向：减少同时存活的缓冲数量（生命周期拆分、原地复用）通常比减少总分配量更有效。第二项 M_budget 是线上显存预算，它不是物理显存容量，而是扣除框架常驻、通信缓冲、KV cache 预留后的可用额度；在服务化部署中，它往往远小于设备容量。

定义里隐含一个工程判断：M_in 与 M_out 通常不可压缩（它们是算子契约的一部分），可压缩的只有 M_tmp。所以峰值优化问题的实质是“在不牺牲时延的前提下压缩临时缓冲的阶段最大值”。这也解释了为什么单纯换更省显存的算法（如用重计算替代物化）会带来时延代价：它把 M_tmp 换成额外的计算与重复访存。

一个具体例子：LayerNorm 的前向若采用两遍扫描（先求均值方差、再归一化），临时缓冲只有标量级的统计量；若为提速改成单遍 Welford 并物化中间归一化结果以配合融合的后续算子，则 M_tmp 从 O(1) 涨到与激活同阶。前者时延更高但峰值几乎不增，后者反之。二者都在 M_budget 内时才可自由选择，一旦预算紧张，选择权就被收窄。

三 · 为什么需要：峰值是并发预算的硬通货

需要把峰值内存单列为一等约束，原因在于它与服务端的并发能力是直接换算关系。KV cache 的可用容量等于 M_budget 减去所有算子执行期间的峰值占用；峰值每涨一份，可容纳的并发序列就少一份。设单序列 KV cache 占用为 k，则粗略的并发上限为 (M_budget − M_peak)/k。这个式子是定性的换算关系而非精确容量模型（分页、碎片、预留都会修正它），但方向明确：峰值是并发预算的硬通货，而不是软指标。

更隐蔽的一层是：峰值超标不会表现为“报错”，而表现为“降级”。allocator 在压力下触发同步回收、碎片化加剧、甚至回退到更保守的调度策略，于是时延分布尾部变长。这类代价不出现在单 kernel 的微基准里，却出现在端到端 P99 上。评测若只看单次调用的平均时延，就会系统性地奖励那些用显存换速度的生成结果——这正是 28% 这个数字背后的激励结构。

还有一个代价维度是编译与验证成本。为压低 M_tmp 而做的生命周期重排、原地写、分块策略调整，会显著增加搜索空间：候选实现变多，autotune 的编译时间与验证轮次上升。对多轮 RL 而言，这意味着每条样本的反馈时延变长，token 预算被摊薄。因此峰值约束不是“加一个过滤器”那么简单，它改变了搜索的性价比。

具体例子：一个 attention 变体为了减少一次全局同步，把 softmax 的中间结果整块物化，时延下降，但 M_tmp 与序列长度平方同阶。在长上下文服务中，这一项直接吃掉本可用于 KV cache 的额度，导致并发从数十路降到个位数——单 kernel 更快，端到端更慢。这是“为什么需要”的最直接证据。

四 · 常见误解之一：单 shape 测量等于峰值

第一个高频误解是把某个固定 shape 下测得的占用当作 kernel 的峰值属性。事实是峰值依赖 shape 与 batch：分块大小、临时缓冲的元素数、规约树的层数都随输入规模变化，某些实现在小 batch 下 M_tmp 可忽略，在大 batch 或长序列下则成为主导项。单 shape 测量会系统性低估真实峰值，且低估幅度随规模增长而非线性扩大。

工程上的对策是把峰值当作关于 shape 的函数来采样，而不是一个标量。评测口径应至少覆盖若干代表性规模，并在报告中标注测量所对应的 shape，否则跨实现比较失去意义。这与计时噪声与置信区间的处理逻辑同构：单点测量不足以支撑结论，需要分布视角。代价是评测成本上升——每个候选实现要在多个 shape 上跑，编译与执行时间成倍增加，这正是峰值评测比时延评测更贵的原因。

具体例子：一个采用大 tile 的 GEMM 融合实现，在小 M 下临时缓冲仅数 MB，在 M 增大到数千时缓冲随 tile 数线性增长，峰值翻数倍。若只在小 M 上验证，会得出“该实现省显存”的错误结论，部署到大批量场景即触发预算越界。

五 · 常见误解之二：allocator 缓存与多流叠加

第二个误解是相信运行时报告的数字。深度学习框架的 allocator 普遍带缓存：释放的块不归还驱动，而是留在池中供后续复用。于是“当前已分配”与“真实驻留”不一致，测量到的峰值可能被缓存掩盖——既可能低估（缓存让复用显得平滑），也可能在重置统计后突然暴露真实高点。正确做法是在测量前重置统计、隔离被测区间、并区分“池内保留”与“实际驻留”。这是一个测量协议问题，而非算法问题，但它决定了所有后续结论的可信度。

第三个误解是多流场景下只看单流。多流并发时各流的峰值在时间上可能重叠，总占用是叠加而非取最大：M_total ≈ Σ_stream M_peak(stream)（在无跨流复用的前提下）。只测单流会低估整体压力，尤其在多路推理、流水并行或通信与计算重叠的场景中。叠加还带来调度代价：流间同步点会拉长临时缓冲的存活窗口，进一步抬高实际峰值。

具体例子：一个 kernel 在单流下峰值 2 GB，看似宽裕；部署时四路并发、每路各自持有一份临时缓冲，叠加后逼近预算上限，触发 allocator 回收与同步，端到端时延尾部显著恶化。若评测阶段只跑单流，这个失效模式完全不可见。

误解机制代价对策
单 shape 即峰值缓冲随规模增长低估，部署越界按 shape 采样报告
信任运行时数字allocator 缓存掩盖驻留测量失真重置统计、隔离区间

这三类误解共享一个结构：它们都把峰值当成静态属性，而峰值本质是“在特定 shape、特定分配器状态、特定并发度下的时间轴上确界”。把它静态化，就会在评测里放过那些用显存换速度的实现，进而把这种偏向写进奖励函数。工程判断因此落在测量协议上：先固定 shape 集合、重置 allocator 统计、按目标并发度折算，再谈优化。峰值约束只有在测量可信之后才是一个可优化的目标，否则它只是一个会被生成器绕过的数字。

峰值内存不是"用了多少"，而是"某一瞬间同时活着多少"

把峰值内存当成 kernel 跑完之后的显存占用量，是最常见的误读。严格定义要盯住执行期间任意时刻的同时存活集合：输入张量、输出张量，加上各阶段临时缓冲在同一时刻的叠加上界。写成约束就是

$$M_{\text{peak}}=M_{\text{in}}+M_{\text{out}}+\max_{\text{stage}}M_{\text{tmp}}(\text{stage})\le M_{\text{budget}}$$
这个式子的关键在于 max 落在 stage 上而不是落在时间点上：一个 kernel 可以平均临时占用很低，却在某个 tile 展开或 reduction 中间态物化的瞬间把峰值顶到预算之上。因此"平均带宽利用率高、显存看起来不紧张"与"峰值超预算"完全可以并存。工程上真正要守的是 $M_{\text{budget}}$——线上留给这个 kernel 的显存额度，它由 KV cache 与并发批次共同挤压出来，而不是设备总容量减去已用量的余数。

为什么必须把它当成一等约束而不是事后观测：生成的 kernel 常用更大的中间缓冲换速度——把原本分块的归约改成一次性物化、把 layout 变换拆成显式 transpose 缓冲、把 softmax 的两次遍历合成一次但保留整行副本。这些改写往往确实减少了同步与重读，但代价直接落在 $M_{\text{tmp}}$ 上。KernelBench-Verified 的统计给出 28% 的核增加了峰值内存，这个比例说明它不是边缘现象，而是搜索空间里一条被频繁踩中的捷径。放到生产端，峰值上涨的直接后果不是 OOM 报错那么干脆，而是服务端被迫下调并发批次或缩小 KV cache 分片，端到端吞吐下降——正确性 oracle 全绿、单核时延更优，系统收益却是负的。

边界与失效条件有三类，必须分开处理。其一，峰值依赖 shape 与 batch。$M_{\text{tmp}}$ 通常随 tile 数、归约长度、batch 维线性或超线性增长，单 shape 测量会系统性低估：在小 batch 上测得的峰值余量，换到长序列或大 batch 就消失。评测协议必须按目标分布的 shape 网格取最坏点，而不是取均值或某个代表点。其二，allocator 缓存会掩盖真实峰值。缓存分配器复用已释放的块，使"进程 RSS 上涨"与"kernel 峰值"脱钩；不重置统计就测，读到的是历史高水位而非本次执行的水位。正确做法是在每次测量前重置 allocator 统计并隔离其他分配源，否则数字不可比。其三，多流并发时各流峰值叠加。单流测得的 $M_{\text{peak}}$ 只是下界，N 条流同时进入各自的最坏 stage 时，实际占用接近各流峰值之和（扣除可共享的常驻部分）。只看单流会把预算算得过于乐观。

具体例子：一个 fused softmax kernel 原本分两块做 max 与 sum 的在线归约，临时占用约为一个 tile；改写为一次性载入整行到共享/寄存器缓冲后单遍完成，减少了全局重读与同步，但 $M_{\text{tmp}}$ 从 tile 级跃升到行级，在长序列 shape 上直接把 $M_{\text{peak}}$ 推过预算。此时正确的工程判断不是回退到慢版本，而是把该改写标记为"shape 条件性可行"：仅在 $M_{\text{budget}}$ 足以容纳行级缓冲的 shape 区间启用，其余走分块路径，并在评测中把峰值作为与正确性、时延并列的门槛指标。
失效来源表现代价
shape/batch 依赖小 shape 低估峰值长序列上线即超预算
allocator 缓存高水位被历史污染测量不可比、误判余量
多流叠加单流数字偏乐观并发批次被迫下调
这三条共同决定了：峰值内存必须作为带 shape 条件的约束进入搜索与验证回路，而不是一次性的 profile 附注。

峰值内存的边界：从单核数字到线上预算

峰值内存不是核函数的一个静态属性，而是输入形状、批大小、分配器状态与并发流四者的函数。把 M_peak 写成 M_in + M_out + max_stage M_tmp(stage) 只是把问题拆成可测的三块，真正的工程风险在于每一块都随上下文漂移：M_tmp 由 tile 尺寸、流水级数与归约策略决定，M_in/M_out 由调用方决定，而 M_budget 是线上留给 KV cache 与并发请求的剩余额度。因此“这个核峰值多少 MB”这句话在没有绑定 shape 与 batch 时没有意义，单 shape 测量会把长序列或大 batch 下的临时缓冲低估成一条平线，进而让预算判断失效。

失效条件里最容易被忽略的是分配器缓存：PyTorch caching allocator 会保留已释放的 block，使第二次测量的峰值看起来比首次低，甚至低于真实需求。要拿到可比较的数字，必须在测量前重置统计（如 torch.cuda.reset_peak_memory_stats 与空缓存），否则优化前后的对比会被缓存命中污染。多流并发则把问题从“单核峰值”变成“叠加峰值”——各流的 M_tmp 在时间上重叠时，预算约束应写成 sum_i M_peak^(i) ≤ M_budget 而非逐流检查，否则线上并发一开就 OOM。代价是显式的：为压峰值而做的分块重计算会增加时延与指令数，为省临时缓冲而做的原地写会引入正确性风险（别名与读后写），而收紧 M_budget 直接压缩 KV cache 容量与并发预算，换算成吞吐损失。

一个具体例子：融合 softmax 与后续 GEMM 时，把整行中间结果落成 [batch, seq, seq] 的缓冲能省掉一次重读，速度提升明显，但该缓冲随 seq^2 增长；在长序列 shape 下它会把 M_peak 推过预算，挤掉 KV cache 的预留空间。工程判断因此不是“峰值越低越好”，而是把 M_peak 作为带 shape 标签的分布来管理：对目标 shape 集合逐点测量、重置统计、按并发流叠加核算，再决定哪些核允许用内存换速度、哪些必须分块。
