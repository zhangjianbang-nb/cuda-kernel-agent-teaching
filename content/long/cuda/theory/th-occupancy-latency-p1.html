一 · 一句话直觉：用并发填满延迟的空洞

把一次全局访存想成一条必须走完的固定长度的管道：发出请求之后，数据要经过若干级缓存与显存，回来时已经是几十乃至上百个周期之后。如果 SM 上只有一个 warp 在跑，它在发出请求后唯一能做的事就是等，等待期间发射口空转，流水线出现气泡。占用率要回答的问题只有一个：手头到底有多少个独立的 warp，可以在别人等待的时候继续发射指令。直觉版本可以压缩成一句话——每个 SM 上驻留的 warp 数乘以每 warp 可重叠的访存延迟，必须覆盖一次全局访存的延迟，否则流水线出现气泡。这句话里藏着两个必须分开看的量：一个是“有多少并发”（warp 数），一个是“每个并发能遮住多久”（每 warp 可重叠的延迟）。二者相乘才是被隐藏掉的时间总量，单看任何一个都会得出错误结论。

这个直觉之所以容易被误读，是因为它把“占用率”从一个百分比变成了一个乘积因子。工程上真正起作用的不是 50% 还是 75% 这个数字本身，而是这个数字换算出来的驻留 warp 数是否足以让 SM 的发射单元在任意时刻都有可发射的指令。一个 32 warp 上限的 SM 上，25% 占用率意味着 8 个 warp；如果每个 warp 在等一次 400 周期的访存，那么 8 个 warp 最多只能覆盖 8 条独立请求的往返，剩下的时间仍然是气泡。反过来，如果每个 warp 内部已经通过指令级并行把多条访存请求提前发出，那么即使 warp 数不多，也能凑够覆盖量。这就是为什么“占用率”必须和“每 warp 可重叠延迟”一起读，而不能当成一个孤立的健康指标。

二 · 严格定义：三个上界的取最小

严格地说，占用率是实际驻留 warp 数与硬件上限的比值，而实际驻留数由三个互相独立的资源约束共同决定，取三者最小值：

$$N_{\text{warp}}^{\text{res}}=\min\left(\left\lfloor\frac{R_{\text{SM}}}{R_{\text{thread}}\cdot 32}\right\rfloor,\;\left\lfloor\frac{M_{\text{SM}}}{M_{\text{blk}}}\right\rfloor N_{\text{warp}}^{\text{blk}},\;N_{\text{warp}}^{\max}\right),\qquad \text{hide}:\;N_{\text{warp}}^{\text{res}}\cdot L_{\text{mem}}\ge L_{\text{lat}}$$

第一项是寄存器约束：每 SM 的寄存器文件容量 R_SM 除以每线程寄存器用量 R_thread 乘以 32（一个 warp 的线程数），向下取整得到能容纳的 warp 数。第二项是共享内存约束：每 SM 可用共享内存 M_SM 除以每 block 申请的共享内存 M_blk，得到能同时驻留的 block 数，再乘以每 block 的 warp 数 N_warp^blk。第三项是硬件架构的硬上限 N_warp^max，任何情况下都不能突破。注意第二项的结构：共享内存是按 block 分配的，所以它的粒度是 block 而不是 warp，这导致一个 block 只要共享内存超了，整个 block 的所有 warp 一起被挡在门外，哪怕只差几个字节。

隐藏条件 N_warp^res · L_mem ≥ L_lat 是这套定义的目的所在：驻留 warp 数乘以每 warp 可重叠的访存延迟 L_mem，要覆盖目标访存延迟 L_lat。这里的 L_mem 不是标称延迟，而是“每个 warp 在等一次访存期间能真正并行推进的其他访存量”，它由访问模式决定。合并访问、L2 命中率高时，单次访存的实际代价低、可重叠的有效延迟大；反之，分散的、未合并的访问会让 L_mem 急剧缩水。用标称延迟代入这个不等式，是工程上最常见的误判来源之一：算出来“够了”，跑起来仍然满屏 stall。

举一个具体例子。设某 SM 的寄存器文件为 65536 个 32-bit 寄存器，每线程用 64 个寄存器，则第一项给出 ⌊65536 / (64·32)⌋ = 32 个 warp。若每 block 有 8 个 warp、每 block 申请 32 KB 共享内存，而 SM 可用共享内存为 100 KB，则第二项给出 ⌊100/32⌋ · 8 = 24 个 warp。若架构上限是 48，则实际驻留 24 个 warp，占用率为 50%。此时若 L_lat 为 400 周期、每 warp 可重叠延迟为 16 周期，则 24 · 16 = 384 < 400，隐藏条件不满足——即便占用率数字看起来“还行”，流水线仍有气泡。把每线程寄存器压到 48 个，第一项升到 42，但第二项仍是 24，瓶颈在共享内存，压寄存器毫无收益。这个例子说明：占用率优化不是“把所有资源都省着用”，而是先定位三个上界里最小的那一个，再决定动哪个旋钮。

三 · 为什么需要它：延迟受限 kernel 的吞吐由并发决定

需要占用率这个概念，根本原因是 GPU 的执行模型把“等待”变成了必须被显式填满的资源。CPU 靠乱序执行和深缓存层次把延迟藏在硬件里，而 GPU 的 SM 是顺序发射的：一个 warp 一旦因为操作数未就绪而 stall，发射口就转向其他 warp。于是吞吐不取决于单个 warp 跑得多快，而取决于在任意时刻有多少 warp 处于“可发射”状态。占用率就是对这个“可发射池”大小的静态估计。它之所以值得单独定义、单独度量，是因为它可以在不运行 kernel 的情况下从编译产物（寄存器数、共享内存申请量）算出来，从而在写代码阶段就预判一个 kernel 是否具备隐藏延迟的结构性条件。

但必须强调它的适用边界：这套推理仅适用于延迟受限（latency-bound）kernel。当 kernel 是带宽受限时，增加占用率不提升吞吐——此时瓶颈是 DRAM 的字节吞吐，SM 上有多少 warp 在等并不改变内存控制器能吐出多少数据。判断自己处在哪一侧，需要看实际吞吐与可达上界的关系（可达上界的口径见 Roofline 相关条目，此处不展开）。一个常见的工程错误是在带宽受限的 kernel 上反复调 block size 追求更高占用率，测出来毫无变化，却误以为“占用率没用”。真正的原因是优化方向错了：带宽受限时该做的是减少访存字节数、提高合并度，而不是增加并发。

代价方面，占用率本身不消耗时延，但追求它会消耗真实资源。压低每线程寄存器用量（例如加 launch bound 限制）会迫使编译器把变量溢出到本地内存，本地内存走的是全局访存路径，等于把寄存器压力转化成了额外的访存流量与带宽开销；缩小 block 的共享内存申请会限制分块（tiling）的尺寸，进而降低数据复用率，同样抬高了带宽需求。也就是说，占用率的提升往往以寄存器溢出、共享内存复用下降为代价，二者都会实打实地增加显存带宽占用与执行时间。工程判断是：只有当 kernel 确实延迟受限、且瓶颈项确实是三个上界中最小的那个时，为占用率付出的这些代价才划算。

四 · 常见误解之一：占用率越高越好

“占用率越高越好”是流传最广的误解，它把占用率当成了目标而不是约束。事实是占用率不是越高越好，受寄存器与共享内存约束——这句话有两层意思。第一层是物理上的：你无法任意提高它，三个上界里最小的那个封死了上限，硬压只会带来溢出代价。第二层是收益上的：一旦隐藏条件已经满足（N_warp^res · L_mem ≥ L_lat），继续增加驻留 warp 数对延迟隐藏没有边际收益，因为气泡已经被填满了；此时多出来的 warp 只是增加了调度器的轮转压力与缓存竞争，甚至可能因为更多 warp 争抢同一份 L1/L2 而降低命中率，反过来削弱 L_mem。也就是说，占用率对性能的曲线是先升后平的，而不是单调上升。

一个具体的反例结构：某 kernel 每线程用 128 个寄存器，第一项给出很低的 warp 上限，占用率只有 12.5%，但它每个 warp 内部通过展开循环把 8 条独立访存请求同时发出，L_mem 很大，12.5% 的占用率已经足够覆盖 L_lat。此时若强行把寄存器压到 64 以翻倍占用率，编译器插入溢出存储，每条溢出都变成一次额外的全局访存，带宽占用上升，端到端时间反而变长。这里的教训不是“低占用率好”，而是“占用率必须和 L_mem 一起评估”：低占用率配合高指令级并行可以达标，高占用率配合低 L_mem（例如大量未合并访问）同样可能不达标。把占用率当成独立 KPI 去追，等于把一个乘积因子当成了乘积本身。

五 · 常见误解之二：用标称延迟代入隐藏条件

第二个高频误解是把 L_lat 当成一个固定的硬件常数，用标称的全局访存延迟去算隐藏条件，得出“我的占用率够了”的结论，然后在实测中看到大量 long scoreboard stall。问题出在 L_mem 这一侧：它依赖访问模式（合并度、L2 命中率），用标称延迟会误判。合并访问且 L2 命中率高时，一次访存的等效延迟远低于标称值，L_mem 的有效覆盖能力强；而跨步访问、随机访问、或者工作集刚好超过 L2 容量导致命中率崩塌时，等效延迟接近甚至超过标称值，同样的 warp 数就遮不住了。换句话说，隐藏条件里的两个量都不是常数：L_lat 随数据布局与缓存状态漂移，L_mem 随每个 warp 能并行发出的独立请求数漂移。

工程上的正确做法是把隐藏条件当成一个需要实测校准的不等式，而不是纸面推导。先用编译产物算出 N_warp^res，再用 profiler 观察实际 stall 构成（stall 归因的方法见 Warp Stall 归因分解条目），确认主导 stall 是否确实是访存等待；如果是，再检查访问模式是否合并、L2 命中率是否如预期。一个典型场景：某 kernel 理论占用率 50%、按标称延迟算隐藏条件刚好满足，但实测 L2 命中率因工作集划分不当而偏低，等效 L_lat 上升，隐藏条件实际不成立，表现为吞吐随 block 数增加而饱和甚至下降。此时正确的动作是改数据布局提高合并度或调整分块提高 L2 复用，而不是继续加 warp。这也解释了为什么占用率分析必须与访存模式分析绑定：单独看占用率数字，无法区分“并发足够但访存太散”和“并发不足但访存很整齐”这两种截然不同的病。

还有一个容易被忽略的代价维度：编译时间与 token。占用率相关的约束（launch bound、共享内存尺寸、分块参数）会改变编译器的寄存器分配与展开策略，进而改变编译产物的大小与编译耗时；在 agent 自动生成 kernel 的流水线里，这意味着每一轮“调占用率”的尝试都要付出一次重新编译与重新 profile 的成本。若把占用率当成盲目搜索的维度，搜索空间会迅速膨胀，而收益在隐藏条件满足后即归零。因此自动化流程更合理的做法是：先用静态资源算出三个上界、定位瓶颈项，再只针对瓶颈项做有限次尝试，把编译预算花在真正可能改变隐藏条件是否成立的那些参数上。

六 · 定义落地：把占用率当成约束而非目标

把上述内容收束成一个可操作的判断链：第一步，从编译产物读出 R_thread 与 M_blk，代入三个上界算出 N_warp^res，确认瓶颈是寄存器、共享内存还是架构上限；第二步，判断 kernel 是否延迟受限（若带宽受限，占用率不是杠杆，直接转向访存字节与合并度优化）；第三步，若延迟受限，用实测 stall 构成与 L2 命中率校准 L_mem 与有效 L_lat，检验隐藏条件是否成立；第四步，只在条件不成立且瓶颈项明确时才动对应旋钮，并同时计量寄存器溢出、共享内存复用下降带来的带宽与时延代价。这条链条的核心是把占用率当作一个约束——它告诉你并发池有多大、上限在哪里——而不是当作一个目标去最大化。

最后落到一个具体的工程判断上：当一个 kernel 的实测吞吐已经贴近其可达上界、而 stall 构成里访存等待不占主导时，继续调占用率是纯粹的浪费，因为隐藏条件早已满足，瓶颈在别处；反之，当 stall 构成里 long scoreboard 占主导、且静态算出的 N_warp^res 明显受限于共享内存而非寄存器时，正确的第一动作是重划分块以降低 M_blk 或提高每 block 的 warp 密度，而不是去压寄存器——压寄存器根本不会移动那个真正封死上限的项。占用率的全部工程价值，就在于它能让你在写第一行代码之前就知道该动哪个旋钮，以及动完之后要付什么代价。

占用率的适用边界：它只在延迟受限时才是杠杆

把占用率当成“越高越好”的调优旋钮，是本领域最常见的误判。严格地说，占用率只是延迟隐藏的一个必要资源项：它给出每 SM 能同时挂起的 warp 数上限，而真正决定流水线是否出现气泡的，是这个上限乘以每 warp 可重叠的访存延迟能否覆盖目标延迟。公式里三项取最小值，意味着寄存器与共享内存任何一项先撞墙，占用率就被钉死——此时继续调大 block 尺寸或缩小线程数只会让编译器溢出寄存器到 local memory，反而拉长单次访存的有效延迟。工程上更该问的是“这个 kernel 是不是延迟受限”，而不是“占用率能不能再高 5%”。

$$N_{\text{warp}}^{\text{res}}=\min\left(\left\lfloor\frac{R_{\text{SM}}}{R_{\text{thread}}\cdot 32}\right\rfloor,\;\left\lfloor\frac{M_{\text{SM}}}{M_{\text{blk}}}\right\rfloor N_{\text{warp}}^{\text{blk}},\;N_{\text{warp}}^{\max}\right),\qquad \text{hide}:\;N_{\text{warp}}^{\text{res}}\cdot L_{\text{mem}}\ge L_{\text{lat}}$$

失效条件有三类，代价各不相同。其一，带宽受限 kernel：一旦 DRAM 或 L2 带宽饱和，增加驻留 warp 只会加剧争用，吞吐不升，反而因更多并发请求抬高队列时延与功耗；此时应转向减少访存字节或提高合并度，而非堆占用率。其二，L_mem 并非常数：它依赖合并度与 L2 命中率，用标称延迟代入不等式会系统性误判——一个合并度差、L2 命中低的访问模式，其有效延迟远高于标称值，按标称算出的“足够”占用率实际仍会露出气泡。其三，寄存器压力：R_thread 每增加几个，N_warp^res 就整档下滑，编译器为保占用率而 spill 的代价是额外的 local memory 流量与指令数，这部分时延直接吃掉延迟隐藏的收益。

场景占用率作用主要代价
延迟受限、合并良好线性提升隐藏能力寄存器/共享内存挤压
带宽受限基本无效，甚至负收益队列时延、功耗上升
访问模式差（低合并、低 L2 命中）标称公式误判有效延迟被低估

具体例子：一个逐元素访存 kernel 在合并访问下带宽已接近饱和，把每线程寄存器从 32 压到 24 换取更高占用率，测得吞吐不变而编译时间与指令缓存压力上升；反之，一个带跨步索引的归约 kernel 合并度差、L2 命中低，即便占用率算出来“够”，仍需靠预取或改变数据布局把有效 L_mem 拉回不等式右侧，而不是继续加 warp。判断顺序应是先定性分类（延迟受限还是带宽受限），再用实测的有效延迟而非标称延迟校验不等式。
