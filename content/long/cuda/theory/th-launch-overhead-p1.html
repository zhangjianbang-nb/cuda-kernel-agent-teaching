一 · 一句话直觉：吞吐被“提交频率”而非“算术”锁死

把 GPU 想象成一台需要凭票入场的机器：每张票由 CPU 侧填写、驱动侧核验、硬件侧放行，票本身不产出任何浮点结果。当 kernel 在 GPU 上只跑几微秒时，填票与验票的时间反而比机器真正干活的时间更长，于是整个 step 的节奏由“多久能递进一张票”决定，而不是由“机器算得多快”决定。这就是 launch 开销问题的全部直觉：它不是某个 kernel 慢，而是相邻两次 kernel 之间的空隙太宽。工程上表现为 GPU 利用率曲线呈锯齿状——短促的忙碌尖峰被长长的空闲平台隔开，nvidia-smi 上的 SM 占用率在个位数与满值之间反复跳变，而算术强度、访存带宽这些指标看上去都还很健康。

这个直觉有一个直接推论：优化对象不是 kernel 内部，而是 kernel 之间的边界。把 100 个各跑 3 微秒的 kernel 合并成 1 个跑 300 微秒的 kernel，算术工作量分毫未变，但边界从 100 个降到 1 个，吞吐可以成倍抬升。反过来，把一个已经跑满的大 kernel 拆成细粒度流水，如果没有并发流或图机制兜住提交开销，收益会被边界成本吞掉。判断一个负载是否落入这个陷阱，只需比较两个量级：单次 kernel 的 GPU 执行时间，与单次提交的固定开销。

二 · 严格定义：T_launch 到底包含什么

把一次“逻辑上的 kernel 调用”拆成端到端时间，可以写成下面的串行模型。它不是性能模型的上界，而是单流串行提交路径下的记账方式：

$$T_{\text{step}}=T_{\text{launch}}+\max\left(T_{\text{kernel}},\;T_{\text{queue}}\right),\qquad \eta_{\text{launch}}=\frac{T_{\text{kernel}}}{T_{\text{launch}}+T_{\text{kernel}}}$$

其中 T_launch 是单次 launch 的端到端固定开销，由三段构成：CPU 侧构造调用参数与 grid/block 配置、运行时库把请求打包成命令、驱动把命令写入提交队列并触发硬件取指；T_kernel 是 kernel 在 GPU 上真正占用 SM 执行的时间；T_queue 是前序工作造成的排队等待，它只在队列非空时才有意义，因此与外层取 max 而非相加；eta_launch 是在“无排队”假设下，GPU 真正用于计算的时间占端到端时间的比例。注意 eta_launch 的定义刻意把 T_queue 排除在外：排队是调度策略问题，launch 开销是提交路径问题，两者混在一起会让归因失效。

严格定义的关键在于“固定”二字。T_launch 与 kernel 的 grid 规模、线程数、寄存器用量基本无关（参数拷贝量极大时例外），它更像一个常数项而非比例项。这意味着 eta_launch 随 T_kernel 缩小而急剧恶化：T_kernel 等于 T_launch 时 eta_launch 只有一半；T_kernel 降到 T_launch 的十分之一，eta_launch 跌到约 9%。这条双曲线是判断“是否值得批量化”的第一把尺子——它不告诉你绝对数字，但告诉你形状：小 kernel 的利用率损失是结构性的，靠调优 kernel 内部无法挽回。

定义还隐含一个边界：公式只对单流串行提交成立。一旦引入多流并发或图级重放，T_launch 不再串行叠加到每个 kernel 前面，而是被重叠或整体消除，此时公式退化为纯计算界。这一点在后续部分展开，此处只需记住：本公式是“最坏串行情形”的记账，不是普适定律。

三 · 为什么需要这个定义：三类工程决策都靠它

第一类决策是是否批量化。设一个推理 step 由 N 个同构小 kernel 组成，每个 T_kernel 为 t。串行提交的端到端时间为 N·(T_launch + t)，而把 N 个请求合并成一个 batch kernel 后，时间约为 T_launch + N·t（假设合并后单 kernel 仍受同一资源约束）。两者的比值给出摊销收益：只要 t 显著小于 T_launch，合并就是净赚；反之当 t 已经远大于 T_launch，合并带来的收益趋近于零，还要额外付出显存与调度代价。这个判据不需要跑 benchmark，只需要一次 NCU 采集拿到 T_kernel，再对照提交路径的固定开销量级即可分流。

第二类决策是是否引入 CUDA Graph 或 persistent kernel。图机制把 N 次提交折叠为一次图实例化加一次重放，重放侧的固定成本被压到微秒级以下；persistent kernel 则把“提交”这件事彻底移出热路径，由 GPU 上的常驻循环自行取任务。两者都以“牺牲灵活性换边界成本”为代价：图要求拓扑与参数地址在实例化时固定，动态控制流与变长输入需要额外的节点或回退路径；persistent kernel 要求任务队列与同步协议自建，调试与正确性验证成本上升。定义中的 eta_launch 正是评估这笔交换的度量：若 eta_launch 已接近 1，引入图机制的边际收益很小，工程复杂度却是实打实的。

第三类决策是评测口径。在 KernelBench 系基准里，若被测实现由多个小 kernel 串成，而参考实现是单 kernel，那么测得的时延差异里混入了 launch 开销，不能直接归因于“生成的 kernel 算术效率差”。正确做法是把 T_launch 从端到端时间里剥离，或者统一用图模式计时，否则奖励信号会把“kernel 数量多”误判为“kernel 写得差”，进而训练出偏好大融合核的策略——这在正确性上未必安全。定义在这里的作用是提供一个可分解的记账框架，让时延差异能被拆成提交项与计算项。

具体例子：一个逐元素的归一化算子被切成三段——统计均值方差、归一化、缩放偏置——每段各是一个小 kernel，单段 T_kernel 与提交开销同量级。此时 eta_launch 约为二分之一，端到端时间里有近一半花在边界上。把三段融合为一个 kernel 后，算术量不变，但边界从两个降为零，端到端时间显著下降；而如果三段本来就各自跑得很久，融合的收益就只剩显存往返的节省，与 launch 无关。同一个融合动作，收益来源完全不同，定义决定了你该期待哪一种。

四 · 常见误解之一：把 T_launch 当成“CPU 时间”

最常见的误读是把 T_launch 等同于 CPU 侧函数调用耗时，于是用 CPU profiler 去量，得出“CPU 只花了很少时间，所以 launch 开销可忽略”的结论。这是错的。T_launch 是端到端固定开销，包含 CPU 提交、驱动打包与硬件启动三段，其中驱动与硬件段并不出现在 CPU 时间线上。更关键的是，在异步提交模型下，CPU 可以连续提交多个 kernel 而不等待，于是 CPU 侧看起来“很快”，但 GPU 侧仍在逐个消费命令、逐个启动，边界成本并未消失，只是从 CPU 时间转移到了 GPU 的空闲间隙里。用 CPU 时间评估 launch 开销，等于用提交端的吞吐去推断消费端的间隙，两者不是一回事。

正确的观测位置是 GPU 侧的时间线：相邻两个 kernel 之间的空隙、kernel 实际占用 SM 的区间、以及队列深度随时间的变化。工程上常犯的第二个错误是把“CPU 提交快”当成“可以无限拆分 kernel”的理由——拆分增加的是 GPU 侧的启动次数，CPU 再快也改变不了硬件逐个放行的事实。这条误解的代价是真实的：一个被拆成几十段的热路径，CPU 侧 profiler 显示开销微小，端到端吞吐却上不去，团队会把时间浪费在调优每段 kernel 的内部效率上，而真正的瓶颈在段与段之间。

五 · 常见误解之二：以为“大 kernel 一定更好”

反向的误解同样有害：既然边界成本高，那就把所有东西融成一个大 kernel。这个判断忽略了公式里的另一项——T_queue 与资源约束。融合后的单 kernel 若受寄存器、共享内存或占用率限制，其 T_kernel 可能因资源压力而拉长，甚至因占用率过低而无法隐藏访存延迟；融合还会消灭 kernel 之间的自然并发机会，原本可以多流重叠的独立工作被串成一条链。更隐蔽的代价在正确性侧：融合要求所有子任务的线程映射与同步协议统一，一旦某段逻辑需要全局同步或动态并行，融合就得引入额外的栅栏与中间缓冲，显存占用上升，验证难度也随之上升。

因此“大 kernel 更好”只在特定条件下成立：子任务同构、无跨段全局同步、融合后资源占用不越界、且原本确实受 launch 边界支配。判断依据仍是 eta_launch：若 eta_launch 已高，融合的收益主要来自显存往返而非边界，此时应优先考虑分块与流水而不是无脑合并。把 launch 开销问题误读为“融合越多越好”，会让生成侧的策略偏向巨型 kernel，在正确性 oracle 上通过率下降，而评测端若只看时延不看正确性，就会奖励这种退化。

还有一个常被忽略的代价：编译时间与调试成本。巨型融合 kernel 的模板实例化与寄存器分配搜索会显著拉长编译时间，在多轮 RL 的采样循环里，编译时间直接吃掉 token 预算与墙钟预算；一个需要几十秒编译的候选实现，即使时延更优，也可能因为采样吞吐下降而在训练中被淘汰。这是 launch 开销讨论里少见的“非性能代价”，但在 agent 生成场景中它是真实约束。

六 · 常见误解之三：把排队时间算进 launch 开销

公式里 T_queue 与外层取 max 而非相加，这个细节常被忽略。当队列里积压了前序工作时，新 kernel 的端到端时间会被拉长，但这段拉长不是提交路径的成本，而是调度与资源竞争的结果。把两者混为一谈，会导致错误的优化方向：看到端到端时间变长就去优化提交路径（换运行时、上图），而真正的瓶颈可能是前序 kernel 占满了 SM 导致排队。区分方法很直接：若空隙出现在 kernel 启动之前且队列深度大于零，归因于排队；若空隙出现在命令已出队但硬件尚未开始执行，归因于启动开销。前者靠调度与并发解决，后者靠摊销与图机制解决。

这条误解在评测里尤其危险。基准计时若包含队列效应，不同实现的时延差异会随同批次的其他负载漂移，导致评分不可复现；而把队列效应误记为 launch 开销，又会诱导生成侧去追求“更少 kernel”而不是“更好的并发”。定义中把 T_queue 单列，正是为了让归因可分解：先看队列深度，再看启动间隙，最后才谈 kernel 内部效率。三者对应三种不同的修复手段，混在一起就只能靠猜。

具体到工程判断：一个 step 的端到端时间若远大于各 kernel 的 T_kernel 之和，先量队列深度。深度持续为正说明提交速率超过了消费速率，此时增加并发流或调整批次比优化单个 kernel 更有效；深度为零而仍有空隙，才轮到 launch 开销登场。这条分流规则不依赖任何绝对数字，只依赖两个可观测量——队列深度与 kernel 占用区间——因此在没有精确计时数据时依然可用。

launch 开销模型的适用边界：何时它解释吞吐，何时它彻底失效

把 T_launch 当作一个可加常数，是这套书里最常被误用的简化。严格地说，T_launch 是单次 launch 的端到端固定开销，涵盖 CPU 侧参数打包与 API 提交、驱动校验与命令写入、GPU 前端取指启动三段，其中只有最后一段真正落在设备上，前两段发生在主机线程里。因此它不是一个硬件常数，而是「主机提交路径 + 驱动版本 + 上下文状态」的函数：同一 kernel 在热上下文与冷上下文、在单流与多流下，测得的 T_launch 并不相同。公式 T_step = T_launch + max(T_kernel, T_queue) 之所以写成 max 而非简单相加，是因为当 T_queue（前序工作造成的排队等待）已经覆盖了 kernel 执行窗口时，launch 的提交动作与排队重叠，不再额外计入关键路径；η_launch = T_kernel / (T_launch + T_kernel) 只在单流串行、队列为空的前提下才是有效利用率，一旦队列非空，分母就该换成 T_launch + max(T_kernel, T_queue)，否则会系统性低估真实占用。

这套模型的失效条件必须写进使用者的判断清单，而不是当作脚注。第一，CUDA Graph 或 persistent kernel 把 T_launch 压到微秒级以下，公式退化为纯计算界，此时再谈「launch 占比」已无意义，优化目标应转向 kernel 内部的 roofline 位置与占用率。第二，多流并发下 T_launch 可被其他流的计算隐藏，单流串行模型失效——此时测得的「吞吐提升」可能来自重叠而非摊销，把两者混为一谈会导致错误的批量决策。第三，T_queue 主导时（例如长训练步中前序 collective 未完成），launch 开销根本不是瓶颈，加大 batch 只会拉长 T_kernel 而无收益。工程代价上，摊销手段本身要付费：CUDA Graph 捕获需要固定 shape 与地址，动态 shape 场景下需重捕获，捕获期编译/构建时间与显存驻留（图持有的中间缓冲）都是隐性成本；persistent kernel 则以占用常驻 SM、牺牲其他 kernel 的并发空间为代价。

一个具体例子足以说明边界感：某 elementwise kernel 在 T_kernel 约数微秒量级时，η_launch 落在很低的区间，此时把 64 次小 launch 合成一次大 launch，收益几乎全部来自 T_launch 的消除；但若同一 kernel 已被 Graph 捕获，单次提交开销降到微秒以下，同样的合并动作只剩带宽与 L2 局部性上的微弱差别，甚至因工作集变大而变差。判断准则因此不是「launch 贵不贵」，而是「T_launch 是否仍在关键路径上、且是否已被 Graph/多流消解」。
