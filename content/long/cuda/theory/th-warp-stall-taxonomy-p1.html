一 · 一句话直觉与它为什么反直觉

把 GPU 上每个 warp 看成一条被反复打断的流水线：调度器每个周期都想从就绪的 warp 里挑一个发射指令，但只要某个 warp 因为操作数没到、屏障没齐、指令没取到而无法发射，这个周期就白白流走。Warp Stall 归因分解的全部内容，就是把这些“白白流走的周期”按原因记账：把 warp 未发射的周期按原因（访存依赖、执行依赖、屏障、指令取指、not-selected）分类，各类占比之和近似总 stall 周期，用于定位瓶颈而非猜测。这句话的直觉部分很短，但它反直觉的地方在于“未发射”这个视角——它统计的不是“做了什么”，而是“没做成什么”，而恰恰是后者决定了 kernel 离硬件上限有多远。

严格定义需要三个量。设 C_stall 为 warp 未发射的总周期数，C_k 为第 k 类 stall 原因的周期数，f_k 为该类 stall 的占比，则：

$$C_{\text{stall}}=\sum_{k\in\mathcal{K}}C_k,\qquad \mathcal{K}=\{\text{long\_scoreboard},\text{short\_scoreboard},\text{wait},\text{barrier},\text{imc},\text{not\_selected},\dots\},\qquad f_k=\frac{C_k}{C_{\text{stall}}}$$

这里 K 是一个开放集合，末尾的省略号不是修辞：不同架构、不同 profiler 版本会给出不同的 stall 类别名，例如 long_scoreboard 对应长延迟操作数（典型是全局访存返回）未就绪，short_scoreboard 对应短延迟操作数（共享内存、部分特殊功能单元）未就绪，wait 对应固定延迟指令的依赖等待，barrier 对应 __syncthreads 之类的同步点，imc 对应指令取指缺失，not_selected 对应 warp 已就绪但调度器选了别人。这个求和式是近似而非恒等式：采样型 profiler 在每个采样点只记录当时处于 stall 的 warp 及其原因，多个 warp 同时 stall 时计数如何摊派、采样间隔内状态如何变化，都会让 ΣC_k 与真实未发射周期产生偏差。工程上把它当作“归因账本”而不是“精确守恒量”来用，才是正确姿势。

为什么需要它？因为“kernel 慢”是一个没有信息量的结论。一个 kernel 达到峰值算力的 30%，可能是访存带宽打满、可能是依赖链太长、可能是 block 太小导致占用率不足、也可能是指令缓存抖动。这四种情况的优化动作完全不同：前者要改数据布局与合并访问，次者要重排计算顺序或做指令级并行，第三者要调 block/grid 尺寸，末者要压缩代码体积或调整循环结构。没有归因，工程师只能靠猜和试；有了 f_k，至少能把“猜”变成“按占比排序的假设队列”。这就是本片段要强调的第一层工程判断：stall 归因的价值不在于给出一个分数，而在于把优化搜索的维度从“改什么”收缩到“先改哪一类”。

举个具体例子。一个做逐元素归一化的 kernel，每个线程读一个 float4、做几次乘加、写回。若 profile 显示 long_scoreboard 占比最高，说明瓶颈在全局访存延迟未被隐藏，优化方向是提高每线程的在途请求数（unroll、增加独立访存）或提高占用率；若显示 barrier 占比高，说明 block 内同步点把 warp 卡住了，方向是减少同步次数或改成分块更细的算法；若显示 not_selected 占比高，则说明 warp 供给充足、调度器在排队，此时再提高占用率是无效动作。三种占比对应三条完全不同的修改路径，而它们的总 stall 周期可能相近——这正是“只看总 stall 不看分解”会误导人的地方。

二 · 严格定义里的三个坑：近似、摊派与采样

把上面的公式落到工程上，需要明确三件事，否则归因结果会被误读。

第一，求和是近似。采样型 profiler 的工作方式是周期性中断、记录当前各 warp 的 stall 原因，再按采样数外推。若一个 warp 在一个采样间隔内先因 long_scoreboard stall 了若干周期、随后操作数到达继续执行，采样点恰好落在 stall 段内才会被记为该原因。这意味着 C_k 是“被采样到的 stall 周期数按比例放大”的估计量，而不是逐周期的精确计数。它的统计误差在小 kernel 上尤其显著：kernel 总时长只有几微秒时，采样点总数很少，单次运行的 f_k 抖动可以很大。工程对策是多次采样取中位数，并同时看 C_stall 的绝对量级——如果 C_stall 本身很小，占比再漂亮也没有优化价值。

第二，多 warp 同时 stall 时的摊派问题。一个 SM 上可能同时有多个 warp 因不同原因无法发射，profiler 在每个采样点只能记录有限信息。若把每个被采样到的 stall warp 都计入 C_stall，则 C_stall 的量级会随占用率上升而膨胀，此时 f_k 的解读必须结合占用率：高占用率下的高 C_stall 未必是坏事，它可能只是“有很多 warp 在排队等发射”。这正是 not_selected 这个类别存在的意义——它把“就绪但没轮到”从“真的卡住”里剥离出来。

第三，类别的语义边界。以 long_scoreboard 与 short_scoreboard 为例，二者的区分依据是操作数来源的延迟量级，而不是指令类型本身；同一个共享内存访问在不同架构上可能被归入不同类别。跨架构比较 f_k 时，必须先确认类别定义一致，否则会把“分类口径差异”误读为“瓶颈迁移”。这是一个纯工程纪律问题，与算法无关，但它是归因可信度的前提。

代价层面，归因本身不是免费的。开启逐 warp stall 采样的 profile 会引入额外开销：采样中断会扰动 warp 调度，kernel 的有效执行时间被拉长，且这种扰动对短 kernel 的相对影响更大。因此归因通常在“定位阶段”做，而不是在“最终计时阶段”做——后者需要干净的计时环境，归因数据与计时数据不应混在同一轮里解读。另一个代价是 token 与人力：把 f_k 向量喂给 LLM agent 做优化决策时，每个候选 kernel 都要跑一次 profile，profile 的 wall-clock 时间与结果解析成本会直接进入多轮优化的预算。一个 20 轮、每轮 8 个候选的搜索，就是 160 次 profile，这个量级决定了归因必须做粗粒度筛选而不是全量精读。

三 · 常见误解之一：not_selected 高就是瓶颈

最常见的误读是把 not_selected 当成和访存 stall 同等的“坏消息”。事实相反：not_selected 高说明占用率充足而非真瓶颈，不能与访存 stall 同等归因。它的语义是“这个 warp 已经就绪、可以发射，但调度器在这个周期选了另一个 warp”。这恰恰是延迟隐藏生效的证据——SM 上有足够多的就绪 warp 在竞争发射端口，说明供给端不缺 warp。此时若继续提高占用率，只会让 not_selected 更高，而 kernel 的实际吞吐不变，因为瓶颈在别处（发射带宽、某个功能单元、或访存带宽本身）。

把这一点写成可操作的判据：设 f_not_selected 显著高于其他类别，且 C_stall 随占用率上升而上升、吞吐不升，则归因结论应为“占用率已饱和，瓶颈不在延迟隐藏”。反之，若 long_scoreboard 占比高而 not_selected 低，说明就绪 warp 不足、延迟未被隐藏，提高占用率或增加指令级并行才是正解。这两条判据的分叉点就在 not_selected 的占比上，而很多自动化优化流程恰恰忽略了这个分叉，导致它在占用率已经足够时还在盲目调 block 尺寸。

具体例子：一个 reduction kernel 在较大 block 尺寸下，profile 显示 barrier 与 not_selected 都高。若只看总 stall 就断定“同步太多”，可能去改算法减少同步；但若看分解，not_selected 高说明 warp 供给充足，真正的代价是 barrier 处所有 warp 一起等——优化方向应是让各 warp 在 barrier 前有更多独立工作可做（例如把部分归约放到寄存器内完成），而不是简单删同步。这个例子的教训是：归因分解的读法是“看占比结构”，不是“看最大项”。最大项告诉你哪里周期最多，占比结构告诉你这些周期是否可被优化动作消除。

四 · 常见误解之二：stall 总和可以直接当性能分数

第二个误解是把 C_stall 当作跨 kernel 可比的性能指标。它不可比，原因有三：其一，C_stall 的量级随 warp 总数与占用率变化，一个占用率高的 kernel 天然有更多 warp 在 stall 账本上；其二，不同 kernel 的指令总数不同，同样的 C_stall 在长 kernel 里占比更小；其三，采样误差在小 kernel 上放大 C_stall 的方差。因此 C_stall 只适合在同一 kernel 的多个候选实现之间做相对比较，且必须同时报告 f_k 结构与绝对量级。

与之配套的是一个归一化思路：把 C_stall 除以该 kernel 的总发射周期数或总指令数，得到“每指令 stall 周期”这类强度量，再在候选间比较。这一步的代价是引入了一个新的分母估计，分母本身也有采样误差；但它把“warp 多所以 stall 多”这个混淆因素消掉了。工程上更稳妥的做法是：先看 f_k 结构判断瓶颈类型，再用干净的计时数据判断优化是否真的带来吞吐提升，归因只做“方向指示”，不做“收益承诺”。

具体例子：两个候选实现 A 与 B，A 的 C_stall 更高但 long_scoreboard 占比更低、not_selected 占比更高；B 的 C_stall 更低但 long_scoreboard 占比高。若只看总和会选 B，但结构上 A 的瓶颈更可能是发射带宽而非访存延迟，B 则明确指向访存优化空间。正确的决策不是二选一，而是：若目标是降低访存延迟暴露，选 B 继续优化；若目标是确认 A 已接近发射上限，则 A 不应再在访存侧投入。归因在这里的作用是排除错误方向，而不是直接选出赢家。

五 · 常见误解之三：类别名即因果，占比即处方

第三个误解是把 stall 类别名当成因果解释，把占比当成优化处方。long_scoreboard 高不等于“访存带宽不足”，它只说明“有 warp 在等长延迟操作数返回”。这两者的区别在于：带宽不足时，访存请求排队导致返回延迟变长，表现为 long_scoreboard 上升；但延迟未被隐藏时（例如每线程只有一次在途访存、占用率低），同样表现为 long_scoreboard 上升，而带宽可能远未饱和。区分二者需要另一个维度的数据——访存吞吐或带宽利用率——单看 stall 占比无法分辨。这正是归因分解必须与 roofline 类上界分析配合使用的原因：stall 占比告诉你“周期花在哪”，上界分析告诉你“理论上还能快多少”，两者缺一不可。

同理，imc（指令取指缺失）高不等于“代码太大”，它也可能是循环体跨缓存行、分支密集导致取指不连续。把 imc 直接映射为“压缩代码体积”这个处方，可能改错地方。正确的做法是把类别名当作假设生成器：imc 高 → 假设“取指路径有问题” → 用指令地址分布或代码布局信息验证 → 再决定改循环结构还是改代码体积。

代价上，这种“假设—验证”循环每轮都要消耗一次 profile 与一次候选生成，在多轮 RL 场景里意味着奖励信号必须能区分“归因正确但优化无效”与“归因错误但碰巧变快”。若奖励只看最终时延，agent 会学到“绕过归因直接试错”的策略，归因数据沦为装饰。要让归因真正进入决策回路，奖励需要包含对 f_k 结构变化的可验证约束——例如“优化后目标类别的占比必须下降”，这是一个可自动检验的代理信号，代价是它可能被 reward hacking（例如通过人为增加其他类别周期来稀释目标占比），因此需要与真实计时共同校验。

具体例子：一个矩阵乘 kernel 的 wait 占比异常高。若直接按“减少固定延迟依赖”去改，可能去重排指令；但若结合寄存器压力与占用率数据，发现是寄存器溢出导致局部内存访问增加、进而拉长了依赖链，则处方应是降低寄存器压力而非重排指令。类别名给的是方向，不是答案；占比给的是优先级，不是处方。这是本片段要落下的工程判断：归因分解的输出是一组待验证的假设及其优先级，而不是一份可直接执行的修改清单。

六 · 失效条件与最小可信用法

归因分解有两个明确的失效条件，工程上必须写进使用规范。其一，not_selected 高说明占用率充足而非真瓶颈，不能与访存 stall 同等归因——这条已在第三节展开，此处只强调它在自动化流程里的后果：任何以“总 stall 最小化”为目标的搜索，都会倾向于压低 not_selected，而压低它的唯一方式是减少就绪 warp，也就是降低占用率，这与性能目标背道而驰。其二，采样型 profiler 的 stall 计数存在统计误差，小 kernel 上需多次采样取中位数。小 kernel 的判定标准是 kernel 时长与采样间隔同量级，此时单次 profile 的 f_k 不可作为决策依据；取中位数是最低成本的可信化手段，代价是 profile 次数乘以采样轮数，直接进入优化预算。

最小可信用法可以写成三步伪代码思路：第一步，对同一候选跑 N 次 profile，取每个 f_k 的中位数，同时记录 C_stall 的中位数与离散度；第二步，若离散度超过阈值则判定该候选的归因不可信，退回干净计时；第三步，只在离散度可接受的候选上做 f_k 结构比较，并把结构差异翻译成假设队列交给下一轮优化。这个流程的代价是 N 倍 profile 时间，收益是把“归因噪声”从优化决策里剔除。对于 LLM agent 驱动的多轮优化，这意味着每轮可用于结构比较的候选数被压缩，搜索广度下降，但错误方向的排除率上升——这是一个明确的工程取舍，而不是免费的改进。

最后落到一个具体机制上：归因分解的真正接口不是一张占比表，而是“类别 → 可验证假设 → 优化动作 → 复测”的闭环。占比表只是这个闭环的入口。一个负责任的 kernel agent 在拿到 f_k 后，应当先检查 not_selected 是否已高到让其他类别失去解释力，再检查采样离散度是否允许结构比较，最后才把最大类别翻译成假设。跳过前两步直接按最大项开处方，是把归因降级成了猜测的另一种形式。
