一 · 无穷范数为何是批不变性的正确度量

批不变性偏差的定义把两个 batch 配置下的输出差取无穷范数再取最大：

$$\Delta_{\text{BI}}=\max_{b_1,b_2}\;\left\|f(x;b_1)-f(x;b_2)\right\|_{\infty}$$
这里 f(x;b) 是同一输入 x 在 batch size 为 b 时的输出张量，b_1,b_2 遍历所有被声明为合法的 batch 配置。选择无穷范数而非 L2 或均值，是因为服务端的失效模式是“某一个元素漂了”：动态 batching 下同一请求可能被塞进不同 batch，下游若对单个 logit 做阈值判断、argmax 或采样，任何一个坐标的偏移都足以改变结果。L2 范数会把这种单点漂移摊薄到整个张量上，均值更是直接掩盖它。无穷范数取的是最坏坐标，恰好对应“最坏情况下这个请求的输出会不会变”。

逐项看：max 外层遍历的是配置对，内层范数遍历输出坐标。两个 max 的复合意味着这是一个“最坏配置下的最坏坐标”度量，代价是它需要对每个配置对做一次完整的前向并逐元素比较，评测成本随合法 batch 配置数呈平方增长——若声明 k 个合法 batch size，需要 k(k-1)/2 次成对比较，每次比较要跑两遍 kernel 并做一次全张量归约。对一个大输出张量（例如词表维度的 logits），单次比较的显存带宽开销是 2·|output|·sizeof(dtype) 的读写量级，配置数一多，评测本身就成了瓶颈。工程上的折中是固定一个参考配置 b_ref，只比较 f(x;b_ref) 与其余配置，把平方降到线性，代价是失去了“两个非参考配置之间也一致”的传递性保证——若偏差不满足三角不等式意义上的可控，这个折中会漏检。

具体例子：一个 RMSNorm 加 matmul 的融合 kernel，输出是 [batch, hidden]。若 b_1=1、b_2=64，无穷范数会直接指出“第几行第几列的那个元素漂了多少”，而 L2 只会给出一个被 64 行摊薄的小数。对 agent 生成的 kernel 做回归时，前者能定位到具体 tile 边界，后者只能告诉你“整体还行”。

二 · 通过判据的两条分支与容差语义

判据写成 pass ⟺ Δ_BI ≤ τ_bit 或 Δ_BI ≤ τ_num。两条分支不是二选一的风格偏好，而是对应两类任务契约。τ_bit 是逐位一致容差，通常取 0，意味着要求 f(x;b_1) 与 f(x;b_2) 的每个 bit 完全相同；τ_num 是数值容差阈值，需按任务声明，例如“相对误差不超过某个量级”或“绝对误差不超过某个量级”，具体数值由任务方给出而非评测方臆定。

推导的关键一步在于：Δ_BI ≤ τ_bit 是一个比 Δ_BI ≤ τ_num 强得多的条件，前者蕴含后者（当 τ_num ≥ 0 时），但反之不成立。因此判据的布尔结构实际上是“优先争取逐位一致，退而求其次接受声明容差”。这在工程上意味着 agent 的优化目标是有序的：先尝试不改变归约顺序、不改变 tile 划分的优化（向量化、访存合并、指令选择），这些通常能保住逐位一致；一旦引入 split-K 或改变 tile 数，就必然落到第二条分支，此时必须由任务声明 τ_num，否则判据无定义。

代价在这里体现为两种：追求 τ_bit=0 会限制可选优化空间，agent 被迫放弃那些能显著提升吞吐但改变归约树的变换，性能收益被正确性契约吃掉；接受 τ_num 则把风险转移给下游，容差定得太松会让服务端出现不可复现的采样结果，定得太紧则大量合法优化被判失败。具体例子：一个 softmax 前的 logits kernel，若 τ_num 按绝对误差声明为某个小量，而 logits 的动态范围很大，绝对误差判据在数值大的坐标上过松、在数值小的坐标上过严，此时应改用相对误差或按坐标归一化的判据，这属于任务声明层面的设计而非公式本身的改动。

三 · 失效条件的推导：归约顺序为何必然引入非零 Delta

失效条件的核心命题是：归约顺序随 batch 改变必然引入非零 Δ_BI，逐位一致要求在存在此类变换时往往不可达。推导的关键步是把浮点加法的不结合性写成显式误差项。设某个输出坐标是 n 个浮点数的和 S = Σ_{i=1}^{n} a_i，两种归约顺序分别产生 S_1 与 S_2。浮点加法满足 fl(a+b) = (a+b)(1+δ)，|δ| ≤ u（u 为机器精度）。对长度为 n 的归约树，误差界随树深累积，不同树形给出不同的累积路径，因此 S_1 ≠ S_2 在一般情况下成立，除非所有部分和恰好可精确表示。

把这一步落到 batch 上：split-K 把 K 维归约切成 s 段并行累加再合并，s 的取值往往随 batch 变化——batch 大时并行度需求高、切得多，batch 小时切得少甚至不切。于是同一输入在不同 batch 下走的是不同的归约树，Δ_BI 非零是结构性的，不是实现 bug。同理，tile 数随 batch 改变会改变每个 tile 内的累加长度，也改变归约树形。这就是为什么“逐位一致”在允许 split-K 的 kernel 上通常不可达：不是 agent 不够努力，而是数学上不成立。

代价的具体形态：要保住 τ_bit=0，必须禁止归约树随 batch 变化，即固定切分策略、让并行度与 batch 解耦，这通常意味着在小 batch 下并行度不足、大 batch 下切分不够，吞吐落在 roofline 之下（可达上界与 SOL 口径见对应条目，此处不展开）。具体例子：一个 [batch, K] 的 reduction，K 很大，agent 为大 batch 选了 s=8 的 split-K，为小 batch 选了 s=1，两个配置的 Δ_BI 必然非零；若任务声明 τ_num，则需验证该偏差是否落在容差内，而这取决于 K 的长度与数据动态范围，不能靠定性判断。

四 · 离散化与近似发生在哪三个位置

公式本身是精确的实数表达式，但工程实现里有三处离散化/近似，必须逐一说清它们各自引入什么。

  • 配置集合的离散化。max_{b_1,b_2} 遍历的是被声明的合法 batch 配置集合，而非连续区间。服务端的动态 batching 实际会遇到的 batch size 是离散的（受显存、请求队列、调度策略约束），声明集合若漏掉某个实际会出现的配置，公式就测不到那个失效点。这是“测什么”的近似，代价是评测覆盖不全。
  • 输出比较的离散化。无穷范数在浮点域上比较，τ_bit 分支比较的是 bit 模式，τ_num 分支比较的是数值差。当输出是 logits 时，微小差异经 softmax 后可放大——softmax 的雅可比含 p_i(1-p_i) 因子，在概率接近 0 或 1 的区域梯度小、在中间区域梯度大，因此同样的 logit 偏差在不同坐标上对最终概率的影响不同。这是“比较对象”的近似：Δ_BI 在 logits 上小，不代表在概率上小。
  • 容差阈值的离散化。τ_num 是一个标量阈值，把连续的误差分布压成通过/失败二元判断。阈值的选择把“多大误差可接受”这一连续权衡离散化，代价是阈值附近的样本判定对噪声敏感（计时噪声与置信区间见对应条目）。

具体例子：一个输出 logits 的 kernel，Δ_BI 在 logits 上落在 τ_num 内，但某个坐标的 logit 恰好处于两个候选 token 概率接近的位置，softmax 放大后 argmax 翻转。这说明判据必须声明在哪个域上比较：在 logits 域通过，不等于在概率域或 argmax 域通过。任务声明 τ_num 时应同时声明比较域，否则公式的通过判据与下游实际行为脱节。

五 · 从公式到可执行判据的推导链

把公式变成 agent 可执行的判据，需要一条明确的推导链，每一步都对应一个可检查的工程动作。第一步：枚举合法 batch 配置集合 B，这来自服务端调度策略而非评测方猜测；集合大小决定评测成本。第二步：对每个 b ∈ B 跑同一输入 x 的前向，得到输出张量；此处要求输入 x 在所有配置下逐位相同，否则测的是输入差异而非 kernel 差异。第三步：成对（或对参考配置）计算无穷范数差，得到 Δ_BI 的候选最大值。第四步：按任务声明的域与阈值判定 Δ_BI ≤ τ_bit 或 Δ_BI ≤ τ_num。

这条链上每一步都有代价。第一步的集合枚举若过大，评测时间线性增长；第二步每个配置一次前向，显存占用按最大 batch 配置计（峰值内存约束见对应条目）；第三步的全张量归约是带宽受限操作，输出越大越慢；第四步的判定本身廉价，但阈值设计错误会让整条链失去意义。工程判断在于：把评测预算优先花在“最可能失效的配置对”上——通常是 batch 最小与最大的一对，因为归约树差异最大；中间配置的成对比较可以抽样。

伪代码思路：for b in B: y[b] = f(x; b)；for (b1,b2) in pairs(B): d = max_abs_diff(y[b1], y[b2]); Delta = max(Delta, d)；pass = (Delta <= tau_bit) or (Delta <= tau_num)。注意 max_abs_diff 必须在声明域上做（logits 或概率），且比较前不得对输出做任何会掩盖单点漂移的聚合。具体例子：若 B = {1, 8, 64}，三对比较中 (1,64) 最可能给出最大 Δ_BI，可先测这一对，若已超阈值则无需测其余两对，这是评测成本与覆盖的务实折中。

六 · 容差声明与判据的工程边界

τ_num 需按任务声明，这句话的工程含义是：容差不是评测方可以单方面收紧或放松的超参数，而是任务契约的一部分。若 agent 在优化时自行放宽 τ_num 以让更多 kernel 通过，判据就退化为奖励黑客的入口（激励不相容见对应条目）；若评测方擅自收紧，则合法优化被误判失败，agent 学到的是“不要做任何改变归约顺序的优化”，这与性能目标冲突。正确的边界是：容差由任务方给出，agent 只能在其约束下搜索，判据的通过/失败是硬约束而非软奖励。

另一个边界是 τ_bit=0 分支的适用性判断。当 kernel 结构上允许归约树随 batch 变化（split-K、动态 tile 数）时，τ_bit=0 分支在数学上不可达，继续要求它只会让 agent 陷入无解搜索。此时应显式声明任务属于 τ_num 分支，并把比较域、误差度量（绝对/相对/归一化）一并写进契约。这不是放松要求，而是把“不可达的逐位一致”替换为“可验证的数值容差”，让判据与 kernel 的实际数学结构对齐。

代价的最终落点是：判据越严，可选优化空间越小、吞吐收益越少；判据越松，服务端结果漂移风险越大。具体例子：一个 attention 类 kernel，batch 变化会改变 head 的并行切分，归约树必然变化，此时声明 τ_num 并按概率域比较是唯一自洽的选择；若强行要求 τ_bit=0，agent 只能退化为不切分的串行实现，性能落在 roofline 远下方。工程判断因此落在“先判定 kernel 的归约结构是否 batch 相关，再选择判据分支”，而不是先定期望再倒推实现。

边界条件：Δ_BI 在哪些 kernel 上必然非零

公式里的 Δ_BI 取两个 batch 配置下同一输入 x 的输出无穷范数差，这个定义本身是干净的，但它把“批不变性”压成了一个标量判据，代价是丢掉了差异的来源信息。真正决定一个 kernel 能否通过 τ_bit 的，不是 Δ_BI 的大小，而是归约树的形状是否随 b 改变。以 split-K 为例：当 b 较小时，grid 只够铺一层 tile，K 维归约在单个 block 内串行完成；当 b 增大到某个阈值，调度器把 K 切成 S 段并行累加，再用原子加或二次归约合并。浮点加法不满足结合律，(a+b)+c 与 a+(b+c) 的舍入结果不同，于是 Δ_BI 从 0 跳到末位量级。这不是实现缺陷，而是并行度与 batch 绑定的结构性后果。同理，tile 数随 b 变化的 tiling 策略、按 b 选择不同 vectorization 宽度的加载路径，都会让累加顺序漂移。结论很硬：只要 kernel 的并行分解依赖 b，逐位一致就不可达，τ_bit=0 的判据在这些 kernel 上恒为 fail，agent 再怎么调优也过不了。

推导的关键步在离散化这一层。连续域上 f(x;b) 与 b 无关是平凡命题；落到 GPU 上，b 只通过三个离散量影响结果：grid 维度、每 block 的归约长度、以及累加器的合并次序。把这三者写成映射 g(b)→(G,L,π)，π 是合并排列，则 Δ_BI 的上界可由舍入误差累积估计：单次浮点加法的相对误差不超过 u（单位舍入），长度为 L 的归约链最坏误差约 (L−1)u·Σ|a_i|，两条不同长度的链相减，Δ_BI 的量级落在 u·Σ|a_i| 上。这个式子说明两件事：误差随归约规模线性增长，且与输入幅值成正比。对 fp16 累加、K 很大的 GEMM 类 kernel，u 本身较大，Δ_BI 轻易越过 τ_num；对 fp32 且 K 小的 elementwise 归约，Δ_BI 可能恰好落在 τ_bit 内，但这是运气而非保证。工程上应把 τ_num 按任务声明成与 u·Σ|a_i| 同量级的阈值，而不是拍一个固定小数。

失效条件的另一半在输出端。logits 类输出经过 softmax 后，微小差异被指数放大：两个 logit 相差 δ，概率比变为 e^δ，当 δ 接近 τ_num 而 top-1 与 top-2 的 logit 间隔很窄时，argmax 翻转，下游采样结果完全分叉。这意味着 Δ_BI 判据必须在 softmax 之前施加，或者把 τ_num 收紧到能保证 argmax 稳定的水平——后者往往要求 τ_num 远小于 logit 间隔，而 logit 间隔由模型决定，不由 kernel 决定，于是容差声明变成了一件需要跨层协商的事。系统代价随之而来：为压住 Δ_BI，常见做法是固定归约顺序（禁用 split-K 或固定 S）、强制 fp32 累加、或在 b 变化时回退到标量路径。固定 S 直接砍掉大 b 下的并行度，fp32 累加让带宽需求翻倍，回退路径引入分支与额外 kernel launch。这些代价都体现在时延与显存上，而收益只是让 Δ_BI 落进容差。判断是否值得，取决于服务端动态 batching 的 b 分布：若 b 长期落在同一 tile 档位内，归约形状不变，Δ_BI 天然为 0，无需任何牺牲；只有当 b 跨档位抖动时，批不变性才成为必须付费的约束。
