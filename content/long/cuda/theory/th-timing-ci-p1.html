一 · 一句话直觉：单次计时是一个随机变量，不是一个数

把 kernel 的一次计时想象成从某个分布里抽出的一个样本，而不是这个 kernel 的“真实耗时”。这个分布的形状由至少三类来源叠加而成：时钟与计时器本身的抖动（读表精度、事件同步开销）、DVFS 与功耗/温度状态导致的频率漂移（同一段指令在不同 SM 频率下执行时间不同）、以及缓存与内存子系统状态的路径依赖（L2 是否已被前一次迭代预热、TLB 是否命中、HBM 行缓冲是否打开）。因此“跑一次得到 0.42 ms”这句话在工程上不构成一个可比较的量，它只是一个观测值。可比较的量是“在声明了测量协议的前提下，重复测量的中位数及其置信区间”。这句话的严格版本是：报告一个 kernel 的性能，等价于报告一个三元组（中心估计、区间半宽、测量协议），缺任何一项都无法判断两次报告之间的差异是真实改进还是计时噪声。

这个直觉的直接推论是：优化前后的差值必须与区间半宽比较，而不是与中心估计比较。若优化带来的中位数下降小于 rel_err 的量级，则该下降在统计上不可区分于噪声，不能作为“优化有效”的证据。这不是保守主义，而是可验证奖励（verifiable reward）设计的前提——如果奖励信号把噪声当成信号，RL 会稳定地学到“如何让计时器读数偏小”而不是“如何让 kernel 更快”，这正是奖励黑客在计时维度上的具体形态。

二 · 严格定义：中位数、区间与相对误差

设第 i 次有效重复测量的 kernel 时间为 t_i，n 为剔除预热轮次后的有效重复次数。中心估计取中位数而非均值：

$$\bar{t}=\operatorname{median}\{t_1,\dots,t_n\},\qquad CI_{1-\alpha}=\left[t_{(k_1)},t_{(k_2)}\right],\qquad \text{rel\_err}=\frac{\text{half\_width}}{\bar{t}}$$

其中 t_(k) 表示升序排列后的第 k 个次序统计量，区间端点由自助法（bootstrap）重采样分布的分位数确定：对原始样本做 B 次有放回重采样，每次计算中位数，得到中位数的经验分布，取该分布的 α/2 与 1−α/2 分位数作为 CI 上下界。半宽即 (上界−下界)/2，rel_err 是半宽相对中位数的比例，是一个无量纲量，因此可以跨 kernel、跨规模比较测量质量。

选择中位数而非均值的理由是稳健性：计时分布通常右偏（偶发的调度抢占、频率跌落、ECC 或页迁移造成长尾），均值会被少数极端样本拉高，且拉高的幅度随 n 增长不稳定。中位数对长尾不敏感，代价是它丢弃了分布形状信息——两个中位数相同但尾部截然不同的 kernel，其 p99 延迟可能相差数倍，而中位数对此完全沉默。因此严格定义里必须同时保留原始样本或至少分位数摘要，否则区间只描述中心，不描述尾部。

定义中“有效重复次数”的措辞是关键：n 不是循环次数，而是剔除预热后的次数。预热轮次的剔除必须在测量协议中显式声明（剔除几轮、依据是什么），因为首轮冷启动同时包含缓存未预热、频率尚未爬升、驱动/上下文首次路径开销，把它计入会系统性高估耗时；把它悄悄剔除而不声明，则使不同来源的报告不可复现。声明本身是定义的一部分，不是附注。

三 · 为什么需要：三个不可回避的工程场景

第一个场景是优化前后对比。假设某次改动把中位数从 A 降到 B，若 |A−B| 与 rel_err·A 同量级，则这次改动在测量分辨率之下。工程判断应是“先提高测量精度再判断”，而不是“相信中心估计”。提高精度的手段包括增大 n、固定频率（关闭 DVFS 或锁定 clocks）、控制缓存状态（每次迭代前做统一的 flush 或 warm），三者分别对应抖动、漂移、路径依赖三类噪声源。

第二个场景是自动调优与搜索。triton autotune 或手写搜索在候选配置间比较时，若每个候选只测一次，选择结果等价于在噪声上取 argmin，选出的配置在重复测量下往往不再最优。把每个候选的测量替换为“中位数 + 区间”，并把比较规则改为“区间不重叠才判定优劣”，可以把搜索的样本效率转化为判定可靠性；代价是每个候选的测量次数上升，编译与测量总时间线性增长，这是搜索预算里必须显式计入的一项开销。

第三个场景是 RL 的可验证奖励。若奖励函数直接取单次计时（或取最小值），策略会倾向于产生“计时器友好”的行为：更短的 launch 序列、更少的同步点、甚至跳过必要的收尾工作。用中位数加区间构造奖励，可以把奖励定义为“在给定置信水平下可区分于基线的改进步长”，使奖励对噪声不敏感；代价是每次 rollout 需要多次重复测量，token 与 wall-clock 预算成倍增加，这是多轮 RL 中计时类奖励的主要成本项。

三个场景共享同一个代价结构：可靠性来自重复，重复消耗时间与算力。因此“需要置信区间”不是统计洁癖，而是在“测量预算有限”这一约束下的最优报告形式——它把不确定性显式化，让下游决策者知道哪些差异可以行动、哪些应当忽略。

四 · 常见误解：区间覆盖什么、不覆盖什么

误解一：置信区间覆盖真实耗时。不成立。自助法区间刻画的是“中位数估计量的抽样波动”，它假设样本近似独立同分布。DVFS 漂移造成的系统性偏移是分布本身的平移，不是抽样波动，区间不会覆盖它——测量期间频率整体下降 10%，所有 t_i 同步变大，中位数与区间一起平移，区间依旧“窄而自信”，却指向一个不代表稳态性能的值。这是本定义最重要的失效条件：区间宽度度量的是随机误差，不度量系统误差。

误解二：n 越大越好，区间自然可信。n 过小（<10）时中位数本身不稳定，自助法重采样在极少样本上生成的分位数几乎没有信息量，区间会给出虚假的窄度。此时正确做法不是报告区间，而是报告原始样本（全部 t_i 的列表或至少五分位数），让读者自行判断。n 的增长也有收益递减：抖动类噪声随 √n 收缩，但漂移类系统误差不随 n 收缩，因此把 n 从 10 加到 1000 只能压缩随机项，无法修正频率漂移。

误解三：剔除首轮冷启动是“作弊”。相反，不剔除且不声明才是问题。冷启动轮次包含与稳态无关的一次性开销，把它混入样本会污染中心估计；但剔除规则必须公开，因为“剔除几轮”直接影响 n 与区间宽度，不同剔除策略下的报告不可直接比较。可复现的协议应写明：预热轮数、是否 flush 缓存、是否锁定频率、n 的取值、自助法重采样次数 B、α 取值。

误解四：rel_err 小就说明测量好。rel_err 是相对量，短 kernel 的绝对抖动可能很小但相对占比大；长 kernel 的 rel_err 小也可能因为漂移被平均掉而掩盖了分段性能退化。判断测量质量应同时看 rel_err、n、以及原始样本的离散度（如四分位距），三者缺一不可。一个具体的工程例子：某 elementwise kernel 在 n=10 时 rel_err 报出很小的值，但原始样本显示前两轮明显偏慢、后八轮聚集——这说明预热剔除不足，区间虽窄却建立在被污染的中心上，此时应增大预热轮数而非增大 n。

五 · 定义落地时的两个接口约定

第一个约定是计时边界。区间定义在“被测量的那段区间”上，因此必须声明计时起点与终点：是否包含 kernel launch 的 host 侧开销、是否包含尾部同步（cudaDeviceSynchronize 或 event 同步）、是否使用 CUDA event 而非 host 墙钟。使用 event 计时会把异步队列的排队时间排除在外，得到的是设备侧执行时间；使用墙钟则包含排队与同步开销。两者不可混用，混用会使不同报告的中位数不可比，区间也随之失去意义。此处的取舍与 launch 开销摊销是同一问题的两面，本片段只强调：计时边界是定义的一部分，必须与区间一起报告。

第二个约定是“同一分布”假设的检验。自助法区间的前提是样本来自同一分布，而 GPU 上的计时样本常常不满足：热稳定过程需要时间，频率在测量窗口内单调爬升，样本呈现时间相关性。一个低成本的检验是把样本按时间顺序分成前后两半，分别计算中位数；若两半中位数之差显著大于各自区间半宽，则说明存在漂移，此时应延长预热或缩短测量窗口，而不是直接报告全样本区间。这个检验不引入新公式，只复用已有的中位数与半宽，因此可以在不增加测量成本的前提下暴露最危险的系统误差。

把这两个约定与前述定义合起来，一个可复现的计时报告应包含：计时边界、预热与剔除规则、频率与缓存控制策略、n、中心估计、区间、rel_err、以及原始样本摘要。缺少任一项，区间就退化为一个装饰性的数字——它看起来定量，实际上不可比较。工程判断应落在“区间是否与协议一起出现”上，而不是落在区间宽度本身。

计时区间的边界：它覆盖什么、不覆盖什么

把中位数与自助法区间当成“kernel 的真实耗时”是一种系统性误读。区间刻画的是在当前这台机器、当前这次进程、当前这段代码路径下，重复采样所呈现的随机波动范围，它的统计对象是采样分布，而不是硬件或编译产物本身。因此它的有效性完全依赖于一个前提：样本近似独立同分布。这个前提在 GPU 计时里恰恰最容易被破坏——DVFS 的频率档位切换、L2 与共享内存的残留状态、同一 MIG 切片上邻居负载的抢占、驱动侧的上下文切换，都会让第 i 次与第 i+1 次测量之间存在相关性。此时自助法重采样只是在重复同一段系统性偏移，重采样得到的分布宽度反映的是抖动，而不是偏差。

形式化地，设真实耗时为 t*，采样得到 t_i = t* + b + ε_i，其中 b 是系统性偏移（例如降频导致的固定拉长），ε_i 是零均值抖动。自助法区间只能覆盖 ε 的分布，对 b 无能为力：无论 n 多大，区间中心都会稳定地偏离 t* 一个 b。这就是“精度很高但准确度很差”的典型形态——$$\bar{t}=\operatorname{median}\{t_1,\dots,t_n\},\qquad CI_{1-\alpha}=\left[t_{(k_1)},t_{(k_2)}\right],\qquad \text{rel\_err}=\frac{\text{half\_width}}{\bar{t}}$$ 里 rel_err 很小，只说明抖动被压住了，不说明中位数接近真实值。工程上必须把这两件事分开报告：一个是区间的相对半宽，另一个是跨进程、跨时段重测时中位数的漂移量。后者才是偏差的量度。

样本量是第二个硬边界。n 小于 10 时，中位数本身对单个异常值敏感，自助法重采样的经验分布只有寥寥几个支撑点，区间的端点实际上由极少数样本决定，重复跑两次得到的区间可以相差很大。此时正确做法不是硬报一个区间，而是把原始样本全部列出，让读者自己看到离散程度；同时明确声明剔除了几轮预热、剔除依据是什么（例如首轮包含模块加载与 JIT 编译，或首轮缓存全冷）。剔除预热会减少有效 n，这本身就是一个需要声明的代价：预热轮数越多，稳态样本越少，区间越宽。

系统代价还体现在测量预算上。要把 rel_err 压到某个阈值，所需重复次数随抖动方差与目标半宽呈平方关系增长，而每次重复都要付出 kernel 启动、同步、以及可能的缓存刷新开销。对于毫秒级以下的小 kernel，同步与事件记录本身的固定开销会显著侵蚀信噪比，此时增加 n 带来的边际收益迅速衰减。一个具体例子：对同一份 Triton 归约 kernel 连续做 50 次测量，前 5 次因缓存冷启动明显偏长，剔除后剩 45 个样本；若期间 GPU 因功耗墙降频，后 20 次整体抬高，则中位数被拉向高值，区间变窄却整体偏移——报告里若不附上“测量期间是否观察到频率变化”的说明，这个区间就是误导性的。
