一 · 三个上界：min 里每一项在约束什么

驻留 warp 数公式的第一层是三个上界的取小，理解它的关键不是记住形式，而是分清每一项对应哪一类硬件资源的耗尽方式。第一项 ⌊R_SM / (R_thread·32)⌋ 是寄存器上界：每 SM 的寄存器文件被划分为 32-bit 寄存器，一个 warp 的 32 个线程各自持有 R_thread 个寄存器，因此一个 warp 的寄存器开销是 R_thread·32，向下取整是因为寄存器分配以 warp 为粒度、不能跨 warp 拼凑。第二项 ⌊M_SM / M_blk⌋·N_warp^blk 是共享内存上界：它以 block 为分配单位，先算能同时驻留多少个 block，再乘以每 block 的 warp 数——注意这里乘的是 block 内的 warp 数而不是线程数，因为驻留决策发生在 block 粒度上。第三项 N_warp^max 是架构硬上限，即每 SM 的 warp slot 数，它通常由 warp scheduler 数量与每 scheduler 可管理 warp 数决定，是寄存器与共享内存都极度节省时才会触碰的天花板。

三项取 min 的工程含义是：占用率的天花板由“最先耗尽的那类资源”决定，而不是由平均值决定。一个 R_thread=64 的 kernel 在寄存器文件充裕的 SM 上可能先撞到共享内存上界；反过来，一个共享内存几乎为零的 elementwise kernel 往往先撞寄存器上界或 warp slot 上界。推导的关键一步是把“每线程资源”换算成“每 warp 资源”再换算成“每 SM 可容纳 warp 数”，这个换算链条中任何一步用了错误的粒度（例如用线程数代替 warp 数去除共享内存）都会让上界偏离真实值。代价方面：寄存器上界是编译期决定的，R_thread 一旦因编译器展开、向量化或临时变量增多而上升，驻留 warp 数会以 32 个寄存器为台阶跳变，这种跳变是离散的、非线性的，意味着“稍微多用一个寄存器”可能让占用率从 48 个 warp 掉到 40 个 warp，而不是平滑下降。

具体例子：一个 block 有 256 线程即 8 个 warp，若 R_thread=40，则每 warp 耗 1280 个寄存器，寄存器文件若按常见的 64K 个 32-bit 寄存器计，可容纳 51 个 warp，向下取整到 48 或受 warp slot 上限截断；若编译器把 R_thread 抬到 48，每 warp 耗 1536，可容纳 42 个 warp，实际驻留按 block 粒度只能取 40（5 个 block×8 warp），占用率出现台阶式下跌。这就是为什么调 __launch_bounds__ 或 maxrregcount 时，收益不是连续的，而是在台阶边界上跳变。

二 · 隐藏条件：L_mem 与 L_lat 的量纲对齐

第二个不等式 N_warp^res · L_mem ≥ L_lat 常被误读为“warp 数乘以延迟”，实际上它是一个吞吐-延迟平衡式：左边是“在途访存请求可覆盖的时间窗口”，右边是“一次访存从发射到数据可用的完整延迟”。L_mem 的量纲是每 warp 在延迟窗口内能重叠的访存周期数，它不是一个硬件常数，而是由访问模式决定的等效值——合并访问、L2 命中率高时，单次访存的实际服务时间短，等效 L_mem 大；反之，非合并访问或 L2 miss 率高时，等效 L_mem 小。因此这个不等式成立的前提是 L_mem 用实测或按访问模式修正后的值，而不是标称的 DRAM 延迟。

推导的关键步在于：把“延迟隐藏”转化为“在途请求数 × 每请求服务时间 ≥ 总延迟”。若每个 warp 在等待期间能发出 k 个独立访存，则 L_mem 正比于 k 与访存吞吐的乘积；当 k 因寄存器压力或指令依赖链而下降时，即使 N_warp^res 很高，乘积仍可能不足。这解释了为什么“占用率高但延迟没被隐藏”是常见现象：warp 数量够了，但每个 warp 内部的指令级并行不足，L_mem 被压低。

$$\text{hide}:\;N_{\text{warp}}^{\text{res}}\cdot L_{\text{mem}}\ge L_{\text{lat}},\qquad L_{\text{mem}}\approx \frac{k\cdot \text{throughput}_{\text{mem}}}{\text{latency}_{\text{nominal}}}\cdot \text{hit\_factor}$$

代价维度：这个不等式只对延迟受限 kernel 有约束力。带宽受限时，增加 N_warp^res 不会提升吞吐，因为瓶颈已经从“等待数据到达”变成“数据通路饱和”，此时继续堆占用率只会增加调度开销与 L2 争用，甚至因缓存抖动降低有效带宽。具体例子：一个 stride 访问的 reduction kernel，标称延迟按 DRAM 计会算出需要极高占用率才能隐藏，但实测 L_mem 因非合并访问被压低，实际需要的 warp 数反而更高；若按标称值配置，会误判为“占用率已足够”而错过真正的瓶颈——访问模式本身。

三 · 离散化：为什么占用率是台阶而非斜坡

公式中所有取整都来自硬件分配的离散性：寄存器以 warp 为粒度分配、共享内存以 block 为粒度分配、warp slot 以整数计。这意味着 N_warp^res 是三个整数上界的 min，其结果只能取离散值，且相邻可行值之间的间隔由 block 内 warp 数决定。若 block 有 8 个 warp，则驻留 warp 数的可行集是 8 的倍数（受 warp slot 上限截断时除外）；若 block 只有 1 个 warp，可行集是连续整数，但 block 调度开销上升。这是一个被低估的设计权衡：小 block 提高占用率的粒度分辨率，却增加 block 调度与共享内存碎片；大 block 降低调度开销，却让占用率只能大步跳变。

推导中还有一个常被忽略的近似：N_warp^max 通常按每 scheduler 的 warp 上限乘以 scheduler 数计算，但实际可驻留数还受“每 scheduler 同时可发射的 warp 数”与指令发射端口限制，公式把它折叠进一个常数上界，这在多数架构上够用，但在指令混合极度偏向某一执行单元时会失效——此时真正的瓶颈是执行单元吞吐而非 warp slot。代价是：按公式算出的占用率是“资源可行”的上界，不是“性能最优”的点；把可行上界当作目标去追，可能在一个执行单元已经饱和的 kernel 上白白牺牲寄存器换取更多 warp，反而因寄存器溢出到本地内存增加访存流量。

具体例子：一个 block 内 warp 数为 4 的 kernel，寄存器上界算出可驻留 13 个 warp，但按 block 粒度只能取 12（3 个 block），共享内存上界若只允许 2 个 block 则取 8。三次取整叠加后，真实占用率与“资源总量除以单 warp 开销”的连续估算可能相差一个 block 的量级。工程判断上，调优时应把 block 大小作为与 R_thread 并列的自由度一起搜索，而不是先固定 block 再调寄存器。

四 · 失效条件的定量刻画：延迟受限与带宽受限的分界

公式的适用域是延迟受限 kernel，其判据可以用 roofline 的语言表述：当算术强度低于机器平衡点时，kernel 受带宽约束，此时 N_warp^res 的增加不改变吞吐上界；当算术强度高于平衡点但实测吞吐仍低于计算峰值时，才可能是延迟受限，公式才有指导意义。推导的关键在于把“延迟受限”操作化为“实测吞吐随 N_warp^res 单调上升且未饱和”——若增加 warp 数吞吐不变，说明已进入带宽或执行单元受限区，公式的隐藏条件不再提供新信息。

另一个失效来源是 L_mem 对访问模式的依赖。合并度差、L2 命中率低的访问会让等效 L_mem 显著低于标称值，此时用标称延迟代入不等式会系统性低估所需 warp 数。定量上，若 L_mem 被高估 α 倍，则所需 N_warp^res 被低估 α 倍，而占用率上界是硬的，低估会导致“以为够了其实不够”的误判。代价是：修正 L_mem 需要 profile 数据（L2 命中率、sector 利用率），这引入了测量开销与噪声，且 profile 本身会扰动时序。

具体例子：一个 L2 命中率高的 stencil kernel，标称 DRAM 延迟代入会算出需要 60 个以上 warp 才能隐藏，但实测因命中率高、等效 L_mem 大，20 个 warp 已足够；反过来一个 pointer-chasing 式的不规则访存 kernel，标称值算出 20 个 warp 够用，实测却因每次访存都 miss 且依赖链长，需要远高于公式给出的占用率，而寄存器与共享内存上界又不允许——此时正确做法不是继续堆占用率，而是重构访问模式或引入软件预取，把 L_mem 拉回公式可用的区间。

五 · 从公式到可执行判断：把不等式变成调优顺序

把两个式子组合起来，可以得到一个调优的优先顺序：先判断 kernel 是否延迟受限（看吞吐随占用率是否单调），若不是则公式不适用、转向带宽或执行单元优化；若是，则先检查 N_warp^res 由哪一项 min 决定——寄存器上界主导时，降低 R_thread 或调整 block 大小；共享内存上界主导时，压缩 M_blk 或改用动态共享内存的分块策略；warp slot 上界主导时，说明资源已不是瓶颈，应转向提高 L_mem（增加每 warp 的独立访存数、改善合并度）。这个顺序的价值在于它把“占用率不够”这个模糊诊断拆成三个可分别验证的子命题。

推导上的一个近似值得单独指出：公式把 L_mem 当作与 N_warp^res 无关的常数，但实际上更多 warp 驻留会增加 L2 与 DRAM 的并发请求数，可能改变有效延迟与带宽分配，使 L_mem 随占用率漂移。这意味着不等式两边不是独立的，公式给出的是局部线性化的近似，在占用率大幅变化时预测会偏。代价是：以公式为目标做全局搜索时，需要在几个离散占用率点上实测吞吐来校准，而不是信任单点外推。

具体例子：一个寄存器上界主导的 kernel，把 R_thread 从 40 压到 32 可让驻留 warp 数从 40 跳到 48，但编译器可能因寄存器不足插入 spill，把原本的寄存器压力转化为本地内存流量，L_mem 反而下降，净效果可能是吞吐不升反降。工程判断因此是：寄存器压缩必须与 spill 计数一起看，公式给出的占用率提升只有在 spill 不增加时才兑现为延迟隐藏收益；否则应优先改 block 大小或共享内存分块，而不是硬压寄存器。

六 · 量纲与边界：公式没说的两件事

公式没有显式包含指令级并行与依赖链长度，但这两者通过 L_mem 隐式进入。一个 warp 内若存在长依赖链，其可发出的独立访存数 k 下降，等效 L_mem 随之下降，此时即使 N_warp^res 达到上界，乘积仍可能小于 L_lat。这解释了“占用率拉满仍有气泡”的现象，也说明公式的隐藏条件是一个必要条件而非充分条件：满足它不保证无气泡，但不满足它一定有气泡。代价维度上，提升 k 往往需要更多寄存器来保存中间结果，与寄存器上界直接冲突，这是占用率调优中最本质的张力。

第二件没说的是 L_lat 本身的取值：它应是“目标访存延迟”，即从发射到数据可用的完整周期数，包含地址计算、TLB 查找、L2 与 DRAM 访问；把它简化为单一常数忽略了 TLB miss 与页表遍历带来的长尾延迟。长尾延迟对平均值影响小，但对“最慢那次访存是否被隐藏”影响大，因此按平均延迟配置的占用率在存在长尾时仍会出现周期性气泡。工程上判断是否被长尾支配，看的是 stall 分布的长尾而非均值，这与 warp stall 归因的口径一致，此处不展开。

具体例子：一个跨页边界的大数组遍历 kernel，多数访问命中 TLB、延迟短，少数访问触发页表遍历、延迟长；按平均 L_lat 算出的所需 warp 数在多数时间段够用，但在长尾访问集中的时刻出现气泡，表现为吞吐的周期性抖动而非稳定低位。此时提高占用率的边际收益递减，正确做法是改善访问局部性以减少长尾比例，或增大 block 内独立访存数以摊薄单次长尾的影响——这仍然是公式的语言，只是把 L_mem 从平均值换成对长尾更敏感的等效值。

隐藏不等式在什么条件下会骗你：边界、失效与系统代价

把 hide 不等式当成设计目标之前，先看清它三项各自的“软肋”。N_warp^res 取三个上界的最小值，其中寄存器项 ⌊R_SM/(R_thread·32)⌋ 是硬约束——编译期 ptxas 报告的寄存器数一旦跨过某个 32 的倍数，驻留 warp 数会整档跌落，占用率呈阶梯而非线性；共享内存项 ⌊M_SM/M_blk⌋·N_warp^blk 则取决于块粒度，块越大，向上取整浪费的 SMEM 越多，实际驻留块数可能比除法结果少一档。真正危险的是右边 L_mem：它不是一个常数，而是访问模式的函数。合并度差、L2 命中率低的访问，其有效延迟远高于标称值；用标称延迟代入不等式，会得到“已充分隐藏”的假结论。工程上应把 L_mem 视为实测分布的中位数而非定值，并在合并度可疑时直接以 NCU 的 stall 采样反推，而不是信任公式。

失效条件必须写进设计文档：该不等式只在延迟受限（latency-bound）区间成立。一旦 kernel 进入带宽受限，增加 N_warp^res 不会提升吞吐，反而抬高 L2 与 DRAM 的争用、加剧分区 camping，并让指令缓存与调度器压力上升。判别方法很直接——把占用率从低档扫到高档，若吞吐曲线在某一档后走平而 stall 中 long_scoreboard 占比已低，说明瓶颈已迁移到带宽侧，此时继续压寄存器或缩 SMEM 换占用率是纯亏损：寄存器溢出到 local memory 会额外产生访存流量，SMEM 缩小可能迫使算法改用更多全局读写。

$$\text{有效隐藏}:\;N_{\text{warp}}^{\text{res}}\cdot L_{\text{mem}}^{\text{eff}}\ge L_{\text{lat}},\qquad L_{\text{mem}}^{\text{eff}}=f(\text{合并度},\;\text{L2 命中率})$$

系统代价体现在三处：编译期，为压低 R_thread 而加 __launch_bounds__ 会触发更多溢出与重算，延长 ptxas 时间并可能恶化单线程指令数；运行期，高占用率压缩每 warp 可用的寄存器窗口，迫使编译器插入 spill/fill，把“隐藏延迟”变成“制造延迟”；显存侧，块粒度与 SMEM 取整造成的驻留块数损失，直接表现为 SM 利用率不足而非报错，极难在日志中发现。一个具体例子：某归约 kernel 将 R_thread 从 40 压到 32 以图多驻留一档 warp，结果 ptxas 报告 spill stores 增加，实测 stall 从 long_scoreboard 转向 lg_throttle，吞吐不升反降——这正是不等式右侧被“有效延迟”悄悄改写的典型现场。
