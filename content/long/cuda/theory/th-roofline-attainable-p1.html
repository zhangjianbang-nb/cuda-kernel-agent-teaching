一 · 一句话直觉：两条斜线夹出的天花板

把一个 kernel 的实测吞吐画在一张以算术强度 I 为横轴、以性能 P 为纵轴的双对数图上，你会看到两条直线：一条是水平的 P_peak，代表这台机器在该指令组合下能持续吐出的浮点运算；另一条是斜率为 1 的 I·B_eff，代表每从 HBM 搬进一个字节所能支撑的运算量被带宽折算成的性能。两条线相交处是一个拐点，拐点左侧是带宽墙，右侧是算力墙。任何 kernel 的实测点都落在这两条线围成的折线之下——这就是 roofline 的全部直觉。它的价值不在于画图，而在于把“这个 kernel 离硬件极限还有多远”从一句模糊的感叹变成一个可计算的比值：实测吞吐除以该 kernel 自身算术强度对应的上界。

需要立刻澄清的是，这条折线不是硬件的物理天花板，而是“给定这段代码的数据搬运模式与指令组合”下的天花板。同一块 GPU，换一种指令组合，水平的 P_peak 就换一个高度；换一种数据布局，斜线的斜率就换一个值。因此 roofline 上界是一个随 kernel 实现方式漂移的曲面，而不是一张固定的规格表。这一点决定了后面所有讨论的基调：我们衡量的不是“kernel 离 GPU 多远”，而是“kernel 离它自己在最优实现下的可达性能多远”。

二 · 严格定义：三个量、一个比值、两个约束

把直觉写成式子，只需要三个量。给定算术强度 I（每字节 DRAM 流量对应的浮点运算数），可达性能上界为：

$$P_{\text{att}}(I)=\min\left(P_{\text{peak}},\; I\cdot B_{\text{eff}}\right),\qquad I=\frac{\text{FLOP}}{\text{Byte}},\; \text{attain}=\frac{P_{\text{meas}}}{P_{\text{att}}(I_{\text{meas}})}\in[0,1]$$

三个变量的含义必须钉死。P_att 是给定算术强度下的可达性能上界，单位随场景取 FLOP/s 或 Byte/s；I 是算术强度；B_eff 是实测可持续 HBM 带宽，注意是实测、可持续，不是规格书上的理论峰值带宽；P_peak 是该指令组合的实测峰值算力。比值 attain 落在 [0,1] 区间内，1 表示实测吞吐恰好触到折线，0 表示完全没跑起来。

这个定义有两处容易被忽略的严格性。第一，I 的分母是“Byte”，但这个 Byte 必须是实际发生的 DRAM 流量，不是算法逻辑上的字节数。一次逻辑上只读 4 字节的访问，如果因为 stride 不对齐导致每个线程各拉一个 128 字节的 sector，实际流量就是 32 倍；写回、padding、因 tile 切分导致的重复读，全部要计入分母。第二，P_peak 是“该指令组合”的实测峰值，不是标称 FLOPS。一个 FP32 FMA 与 INT 地址计算混合的内核，其可持续算力低于纯 FMA 微基准，因为 INT 流水与 FP 流水共享发射端口与寄存器带宽。用标称值做分母，attain 会被系统性压低，且压低的幅度随指令混合比例变化，导致不同 kernel 之间的比值不可比。

于是严格定义可以浓缩成一句话：attain 是一个在“实际 DRAM 流量”与“实际指令组合峰值”两个约束下归一化的效率指标。这两个约束不是修饰语，而是定义的一部分；丢掉任何一个，比值就失去意义。

三 · 为什么需要它：把“优化了多少”变成可归因的量

没有 roofline 上界时，工程上判断一个 kernel 好不好只有两种粗糙手段：与上一个版本比（相对加速比），或与厂商库比（绝对时延）。前者无法回答“还剩多少空间”，因为一个从 5% 优化到 10% 的 kernel 和从 80% 优化到 85% 的 kernel 报出同样的 2x 与 6% 加速，但前者意味着巨大的剩余空间，后者意味着已经贴近极限、继续投入的边际收益极低。后者则被库实现的指令组合与数据布局绑架，比较的是两个不同上界下的点。

roofline 上界提供的正是“剩余空间”的度量。它把实测吞吐除以该 kernel 自身算术强度对应的上界，得到一个无量纲的 attain，从而让不同形状、不同算术强度的 kernel 落在同一把尺子上。更关键的是，它把优化方向变成可归因的：如果 I 落在拐点左侧而 attain 远低于 1，问题几乎必然在访存侧（合并访问、sector 利用率、重复读），因为此时上界由 I·B_eff 决定，提升 I 或提升有效带宽都能抬高上界；如果 I 落在拐点右侧而 attain 低，问题在算力侧（指令混合、流水停顿、寄存器压力），因为上界已被 P_peak 钳住，唯一出路是让实际发射率逼近该指令组合的可持续峰值。

代价在这里第一次显现：计算 attain 需要两次额外的测量开销。一次是实测 B_eff（一个纯拷贝或 stream 型微基准，占用整卡数十毫秒量级），一次是实测 P_peak（针对该指令组合的算力微基准）。在自动调优或 RL 循环里，如果每一轮候选 kernel 都重新测这两个量，评测时延会被显著放大；工程上的折中是按指令组合族缓存 P_peak、按卡型缓存 B_eff，只在指令混合发生实质变化时才重测。另一个代价是 I 的精确统计本身需要 profile 工具给出 DRAM 流量计数，而不是从源码静态推算——静态推算会漏掉编译器插入的 spill 与冗余加载。

一个具体例子：两个 kernel 都做逐元素缩放，逻辑上每元素读 4 字节写 4 字节、做 1 次乘法，逻辑算术强度 1/8 FLOP/Byte，远在拐点左侧。若其中一个因线程映射不当使每个 4 字节访问独占一个 32 字节 sector，实际 DRAM 流量变成 8 倍，真实 I 降到 1/64，其上界随之降到原来的八分之一；此时它的实测吞吐若与另一个 kernel 相同，前者的 attain 反而更高——因为它离自己被压低的上界更近。这正是“按实际流量计算 I”的必要性：否则你会把 sector 浪费误判为算力不足。

四 · 常见误解之一：把逻辑字节当成分母

最常见的错误是用算法层面的字节数计算 I。矩阵乘的逻辑强度是 2·M·N·K 次浮点运算除以 (M·K + K·N + M·N) 个元素字节，看起来是一个只由问题形状决定的漂亮数字。但真实 kernel 在分块时，A 与 B 的 tile 会被多个 block 重复读取，重复次数取决于 tile 尺寸与 L2 命中；写回 C 时若采用原子累加或分段归约，写流量也会膨胀。把这些全部忽略，得到的 I 是上界的一个上界——用它算出的 P_att 偏高，attain 被系统性低估，于是你会误以为一个已经很好的 kernel 还有巨大空间，把优化预算投进一个不存在的缺口。

反过来，padding 与对齐也会让实际流量偏离逻辑值。为了满足向量化加载的 16 字节对齐，tile 的行宽常被补齐到 2 的幂，补齐部分不承载有效数据却真实占用 DRAM 带宽。这部分流量必须计入分母，否则 I 偏高。工程上的做法是让 profile 工具直接给出 DRAM read/write bytes 计数，用这个计数做分母，而不是用源码里的数组维度推算。代价是每次候选 kernel 都要跑一次带计数采集的 profile，比纯计时贵；在批量评测里这构成可观的开销，因此常见折中是只对进入决赛圈的候选做流量采集，初筛阶段用计时与静态估算粗排。

五 · 常见误解之二：把标称峰值当作 P_peak

第二个高频错误是拿规格书的 FLOPS 当分母。规格书的峰值通常对应纯 FMA、无地址计算、无分支、寄存器压力极低的理想微基准，而真实 kernel 的指令流里混着大量 INT 地址运算、谓词判断、循环控制与数据搬移。这些指令与 FP 指令争抢发射槽，使得可持续算力低于标称值。用标称值做分母，attain 会被压到一个偏低的区间，而且压低幅度随指令混合比例变化：一个地址计算密集的 kernel 被压得更狠，一个纯 FMA 的 kernel 几乎不被压。结果是不同 kernel 的 attain 之间失去了可比性，你无法判断 0.4 与 0.6 的差距是真实差距还是指令混合差异造成的假象。

正确做法是针对该 kernel 的指令组合测一个可持续峰值。工程上可以用一个与被测 kernel 指令混合比例相近的微基准，或者直接从 SASS 统计里取出 FP 与 INT 指令比例，按流水吞吐折算。代价是这套折算本身需要 SASS 级分析，比读规格书贵得多；而且在指令混合随数据分布变化时（例如分支走向随输入改变），P_peak 本身不是一个常数，而是一个随输入漂移的量。此时 attain 的分母带有不确定性，比值应当被理解为区间而非点值——这与计时噪声的处理是两回事，后者扰动的是分子。

六 · 常见误解之三：把 attain=1 当作可达目标

第三个误解是把 attain 逼近 1 当成优化目标本身。折线是“给定当前数据搬运模式与指令组合”的上界，而改变数据搬运模式（更好的分块、更高的 L2 复用、更少的重复读）会同时改变 I 与上界本身。一个 kernel 可以把 attain 从 0.5 提到 0.9，同时因为减少了重复读而使 I 上升、上界抬高，最终绝对吞吐提升远超 0.5→0.9 所暗示的幅度；反过来，也可能出现 attain 上升而绝对吞吐下降的情形——上界被压低了。因此 attain 是诊断量，不是目标函数；优化目标是绝对吞吐，attain 只用来告诉你剩余空间在哪一侧。

还有一个更微妙的陷阱：当 I 恰好落在拐点附近时，attain 对 I 的测量误差极其敏感，因为两条线在此处相交，分母对 I 的偏导在两侧符号相反。此时一个小的流量统计误差会让 attain 跳动，进而误导优化方向判断。工程判断是：拐点附近的 kernel 不要只看 attain，要同时看实测 DRAM 流量与实测指令发射率两个原始量，用它们分别对照 B_eff 与 P_peak，判断到底哪一侧先饱和。这一步的代价是需要两份 profile 数据而非一个比值，但它把“拐点附近不可靠”这个定义层面的弱点变成了可操作的检查清单。

可达上界不是性能承诺，而是失效诊断的坐标系

把 Roofline 的 min 结构当成“预测器”是最常见的误用：它给的是给定算术强度下的可达性能上界 P_att，不是这个 kernel 应该跑到的性能。二者的差别在分母上——$$P_{\text{att}}(I)=\min\left(P_{\text{peak}},\; I\cdot B_{\text{eff}}\right),\qquad I=\frac{\text{FLOP}}{\text{Byte}},\; \text{attain}=\frac{P_{\text{meas}}}{P_{\text{att}}(I_{\text{meas}})}\in[0,1]$$ attain 落在 [0,1] 内是定义上的必然，因为 P_att 是上界；真正有信息量的是 attain 偏离 1 的方向与幅度。若实测点贴在带宽斜线下方很远，问题在访存路径（合并度、L2 命中、写回策略）；若贴在算力水平线下方很远，问题在指令组合与占用率（发射密度、寄存器压力、依赖链）。同一个 attain 数值，两种失效原因的修复代价完全不同：前者往往靠改数据布局与分块，后者往往要改指令选择甚至换精度路径。因此 Roofline 在工程流水线里的角色是“把优化方向二分类”，而不是“给出目标数字”。

边界条件比公式本身更值得写进检查清单。第一，I 必须按实际 DRAM 流量计算，含写回、padding、重复读——用逻辑字节数（比如“读一个 N×N 矩阵”）会系统性高估上界，因为 padding 到对齐边界、转置时的非合并访问、以及因分块不足导致的重复读都会把真实字节数抬高，I 被压低，P_att 随之被高估，attain 被虚假地压低。第二，P_peak 必须取该指令组合的实测峰值：FP32 FMA 与 INT 混合、或含特殊函数单元的 kernel，其可持续算力低于规格书标称的峰值 FLOPS，用标称值会把水平线画高，让一个其实已接近指令级上限的 kernel 看起来“还有很大空间”。这两条失效条件共同决定了 Roofline 的可信区间：它只在“字节数按 DRAM 实际流量统计、峰值按实测指令组合标定”时才是一个可用的上界。

系统代价体现在标定环节本身。B_eff 需要一次独立的带宽压测（大粒度流式读写），P_peak 需要一次针对目标指令组合的算力压测；这两次标定各自消耗编译时间与 GPU 机时，且必须与待测 kernel 在同一卡、同一时钟策略下完成，否则斜线与水平线的位置漂移会让 attain 失去可比性。在多轮 agent 优化循环里，这个代价会被放大：每一轮候选 kernel 若改变精度或指令组合，P_peak 的标定口径就得跟着变，否则跨轮次的 attain 不可比。工程上的折中是固定一组“标定 kernel”（纯带宽、纯 FMA、混合 INT）作为参照系，只在硬件或编译选项变化时重标，把标定成本摊到整条流水线而非单个候选。

误用后果诊断信号
I 用逻辑字节数上界被高估，attain 虚假偏低实测 DRAM 流量显著大于逻辑量
P_peak 用规格标称值水平线画高，掩盖指令级瓶颈混合指令 kernel 的 attain 长期停在低位
跨轮次不重标 B_eff斜线漂移，候选间不可比同一 kernel 在不同轮次 attain 抖动

具体例子：一个做逐元素缩放加归约的 kernel，逻辑上每元素读 4 字节写 4 字节，算术强度极低，落在带宽斜线上；但若归约阶段因分块不当对输入做了两遍读，实际 DRAM 字节数接近逻辑量的两倍，真实 I 减半，P_att 也随之减半——此时 agent 若按逻辑字节数算出“还有一倍余量”，就会把优化预算错误地投到指令调度上，而真正的修复点是消除重复读。反过来，一个 FP32 与 INT 地址计算混合的 kernel，按标称 FP32 峰值算出的水平线远高于其可持续算力，attain 看起来只有零点几，实际已接近该指令组合的上限；此时继续压指令密度的收益趋近于零，正确判断是换数据通路而非继续调优。这两类判断都依赖把失效条件写进度量口径，而不是依赖 min 公式本身。
