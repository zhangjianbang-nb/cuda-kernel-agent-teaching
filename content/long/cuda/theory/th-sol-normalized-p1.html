一 · 一句话直觉：分数是“离物理下界还有多远”

SOL 归一化评分要回答的问题只有一个：给定一个 kernel 和一组形状，它在硬件上跑出的时间，距离这块硬件在物理上“最快可能做到”的时间有多远。把这两个时间相除，就得到一个无量纲的比值。比值接近 1，说明实现已经贴住物理下界，继续优化空间被硬件本身封死；比值远小于 1，说明还有大量时间花在了下界之外的东西上——多余的访存、多余的指令、没有被隐藏的延迟、没有摊销的固定开销。这个直觉的关键在于：分母不是“别人的实现”，不是“上一次的基线”，而是一个由算法必需工作量与硬件峰值能力共同决定的量。因此它天然跨 kernel、跨形状可比，这也是它被用作可验证奖励与跨论文对照口径的根本原因。

但直觉里藏着一个必须立刻说清的转折：分子并不是“上帝给定的常数”，它依赖一个“最优实现”的假设。你假设算法只需要读这么多字节、只需要做这么多次浮点运算，并且这些工作量能以硬件峰值速率被消化——这三条假设任何一条不成立，分子就变了，分数随之改变，而分母（实测时间）丝毫未动。所以 SOL 分数的可比性不是无条件的，它可比的前提是“最优实现假设”被同一套规则钉死。这一点是本部分要展开的核心，也是后续所有口径争议的源头。

二 · 严格定义：分子、分母与各自的计数规则

形式化地，对某个 kernel 在给定形状下：

$$\text{SOL}=\frac{T_{\text{SOL}}}{T_{\text{meas}}},\qquad T_{\text{SOL}}=\max\left(\frac{\text{Byte}_{\text{min}}}{B_{\text{eff}}},\;\frac{\text{FLOP}_{\text{min}}}{P_{\text{peak}}}\right)$$

四个变量各有明确语义。T_SOL 是硬件 Speed-of-Light 下的下界时间，单位是秒；T_meas 是实测 kernel 时间，且“含不含 launch 摊销”这一口径必须在报告里声明，否则同一份测量可以给出两个不同的分数；Byte_min 是算法必需的最小 DRAM 字节数；FLOP_min 是算法必需的最小浮点运算数。取 max 而非求和，是因为在理想实现中访存与计算可以重叠，瓶颈由更慢的那一侧决定——这正是 roofline 的思路，此处不再展开其可达上界的讨论。

真正决定分数含义的是 Byte_min 与 FLOP_min 的计数规则。三个必须固定的判定点：其一，是否计入中间张量。一个两阶段的归约若把中间结果落到 DRAM 再读回，Byte_min 会显著变大；若允许在片上完成融合，Byte_min 只算输入与最终输出。其二，是否允许融合。融合把多次 kernel 启动的访存合并成一次，直接压低 Byte_min。其三，FLOP_min 是否计入为数值稳定而做的额外运算（例如在线 softmax 的重缩放）。这三条规则不写清，两个团队对同一个 kernel 可以算出差异明显的 SOL 分数，且双方都没有算错——他们只是用了不同的“最优实现”假设。

工程上可行的做法是把计数规则写成一份显式的口径契约，随分数一起发布：输入输出张量的枚举、中间张量是否允许驻留 DRAM、融合的允许范围、FLOP 计数的算子白名单。契约一旦固定，Byte_min 与 FLOP_min 就成为形状的确定函数，T_SOL 也随之确定，分数才具备跨论文比较的资格。没有契约的 SOL 数字只能在同一份代码、同一套假设内部做纵向对比。

三 · 为什么需要：把“快”从相对量变成绝对量

没有 SOL 归一化时，衡量一个 kernel 快不快只能靠相对基线：比 PyTorch 快几倍、比上一版快几个百分点。相对量的问题在于它会随基线漂移——基线本身可能离物理下界很远，于是“快三倍”可能只是从一个糟糕实现走到一个仍然糟糕的实现。更严重的是，在自动生成与多轮优化的场景里，相对基线会诱导奖励黑客：agent 学会针对特定基线做局部修补，而不是逼近物理极限。SOL 把评价锚在硬件常数上，使“快”变成绝对量：分数只取决于实现离下界的距离，与基线是谁无关。

第二个需求是跨形状与跨 kernel 的聚合。一个 agent 在一批形状上生成的 kernel，若用原始时延求平均，大形状会淹没小形状，且不同 kernel 的时延量纲不可加。SOL 是无量纲比值，可以直接做算术平均或几何平均，把“这一批生成结果整体离物理下界多远”压缩成一个数，作为可验证奖励的标量输出。这也是它适合做 RL 奖励的原因：奖励的尺度不随形状量级漂移，梯度信号不会被某个超大形状独占。

代价同样明确。计算 T_SOL 需要为每个形状推导 Byte_min 与 FLOP_min，这本身是一份人工或半自动的算子建模工作，对融合边界模糊的 kernel（例如带动态分支的注意力变体）建模成本很高；建模错误会系统性地偏移分数，且偏移方向不易察觉。此外，T_SOL 依赖 B_eff 与 P_peak 两个硬件常数，这两个常数的取值口径（是否用理论峰值、是否扣除 ECC 与刷新开销）也必须写进契约，否则跨硬件比较同样失效。一个具体例子：同一份融合归约 kernel，在“允许片上融合”契约下 Byte_min 只计一读一写，分数贴近 1；在“禁止融合、中间张量落 DRAM”契约下 Byte_min 翻倍，同一份实测时间算出的分数直接减半。两次测量一模一样，结论却相反——这正是为什么必须先把契约摆在分数前面。

四 · 常见误解之一：SOL 超过 1 就是测错了

最普遍的误解是认为 SOL 分数天然落在 (0,1] 区间，一旦看到大于 1 就判定测量有误。事实是 T_SOL 的构造里没有计入不可消除的 launch 与同步开销。T_SOL 描述的是“纯工作量在峰值速率下所需的时间”，而 T_meas 至少包含一次 kernel 启动的固定成本与必要的同步。对于小 kernel——工作量极小、启动开销占比极高——T_meas 可以小于按朴素模型算出的 T_SOL，于是分数超过 1。这不是测量错误，而是口径的必然产物：分子描述的是一个不含固定开销的理想世界，分母是含开销的现实世界。

正确的处理不是去“修正”这个大于 1 的分数，而是在契约里声明小 kernel 的适用边界，或者把 launch 摊销口径显式写入 T_meas 的定义。若 T_meas 采用“批量摊销后的单次时间”，启动开销被摊薄，分数会回落；若采用“单次冷启动时间”，分数就可能越界。两种口径都合法，但不能混用后再做跨论文比较。工程判断是：当 kernel 工作量低于某个阈值时，SOL 分数失去区分度，应改用其他口径评价，而不是强行把分数裁剪到 1。裁剪会掩盖真实信息——它把“这个 kernel 太小、固定开销主导”这一事实抹掉了。

五 · 常见误解之二：分数高就等于实现好

第二个误解把 SOL 分数当成实现质量的充分证据。分数高只说明实测时间接近按当前契约算出的下界，它不说明这个下界本身是否紧。如果 Byte_min 被高估——例如契约允许把本可融合的中间张量计入 DRAM 流量——那么一个平庸实现也能拿到接近 1 的分数，因为分母被抬高了。反过来，如果 FLOP_min 漏计了数值稳定所需的额外运算，一个诚实实现会因为做了“契约外”的工作而被判低分。分数的意义完全寄生在契约的紧致性上。

因此读到一个 SOL 分数时，正确的追问顺序是：契约是什么、Byte_min 与 FLOP_min 如何计数、T_meas 是否含 launch 摊销、B_eff 与 P_peak 取值口径为何。四个问题答不上来，分数就只是一个内部纵向对比的序号，不能作为“实现已达物理极限”的证据。在自动优化流水线里这一点尤其致命：如果奖励直接取 SOL 分数而不校验契约，agent 会发现放宽契约比优化代码更省力——把中间张量算进 Byte_min，分数立刻上升，而真实性能毫无变化。这是奖励黑客在 SOL 口径下的一种具体形态，防御手段只能是把契约冻结在评分侧，不让被评对象触碰。

一个具体机制上的例子：带在线 softmax 的注意力 kernel，若契约把重缩放所需的额外乘加排除在 FLOP_min 之外，实现为了数值稳定必须做这些运算，实测时间无法压缩到 T_SOL，分数被系统性压低；若把这些运算计入 FLOP_min，T_SOL 上升，分数回到合理区间。同一份代码，两种契约，两种结论。这说明 SOL 分数的可比性完全建立在计数规则的统一之上，而不是建立在公式本身之上。

六 · 常见误解之三：跨论文的 SOL 数字可以直接比大小

第三个误解最常见也最危险：看到两篇工作报告了 SOL 分数，就直接比较数值高低。公式本身是通用的，但 Byte_min 与 FLOP_min 的计数规则必须固定，否则分数不可跨论文比较——这不是保守说法，而是定义层面的结论。两篇论文若对“是否计中间张量”“是否允许融合”采取不同立场，它们的分子属于不同的数学对象，比值之间没有可比性，哪怕公式长得一模一样。

可操作的工程判断是：跨来源比较 SOL 之前，先做契约对齐。对齐的最小集包括中间张量计数、融合允许范围、FLOP 算子白名单、T_meas 的 launch 摊销口径、B_eff 与 P_peak 的取值来源。任何一项不一致，比较就退化为定性参考。若无法对齐，正确做法是只比较同一契约下的分数，或改用对契约不敏感的指标。这不是苛求，而是因为 SOL 的设计初衷就是“在固定最优实现假设下度量距离”，抽掉假设，度量就失去意义。把这一点写进评分口径文档，比在论文里多报一位小数更有价值。

SOL 分数的边界：它测的是“离最优实现有多远”，不是“离物理极限有多远”

把 SOL 当成“硬件利用率”来读，是最常见的口径错位。T_SOL 里的 Byte_min 与 FLOP_min 并非物理定律给出的常数，而是在某一套实现假设下算法“必需”的最小搬运量与最小运算量：是否允许把中间张量留在片上、是否允许跨算子融合、是否把 softmax 的两次归约合并成一次、是否把 bias 与激活折进 GEMM 的 epilogue，每一项都会改写 Byte_min。因此 SOL 分数的语义应严格表述为“实测时间相对该假设下最优实现的比值”，它衡量的是实现差距，而非“硅片还剩多少余量”。同一 kernel 在“允许融合”口径下 Byte_min 减半，T_SOL 随之减半，分数凭空掉一半——硬件没变、代码没变，变的只是分母的定义。这就是为什么跨论文比较 SOL 之前，必须先对齐计数规则；口径不同的两个 SOL 数字放在一张表里，等于拿两把不同刻度的尺子量同一根轴。

第二个边界来自 T_SOL 的构成。公式 $$\text{SOL}=\frac{T_{\text{SOL}}}{T_{\text{meas}}},\qquad T_{\text{SOL}}=\max\left(\frac{\text{Byte}_{\text{min}}}{B_{\text{eff}}},\;\frac{\text{FLOP}_{\text{min}}}{P_{\text{peak}}}\right)$$ 只取带宽项与算力项的较大者，隐含“计算与搬运完全重叠”的理想流水；它没有为 kernel launch、grid 同步、尾部归约的跨 block 通信留出任何时间。于是当 kernel 本体只有几微秒时，固定的 launch 与同步开销在 T_meas 中占比可观，而 T_SOL 仍按纯数据量估算，分数会被系统性压低；反过来，若 T_meas 采用去掉 launch 的纯 device 计时口径，小 kernel 的 SOL 甚至可能越过 1。越过 1 不是“超越光速”，而是分母漏项的直接证据，应当触发口径复核而不是当作性能亮点上报。

第三个边界是 max 取值的单侧性。当 Byte_min/B_eff 与 FLOP_min/P_peak 接近时，真实 kernel 往往既受带宽牵制又受流水依赖牵制，两者无法完美重叠，实测时间会高于 max 而低于两者之和；此时 SOL 分数对“算术强度落在转折点附近”的实现格外苛刻，任何一处寄存器压力导致的 occupancy 下降都会同时拖慢搬运与计算。以融合后的 LayerNorm 加残差为例：按“读一次输入、写一次输出”计 Byte_min 时 T_SOL 很小，但真实实现需要至少两遍归约或一次片上缓存，warp 内 shuffle 与跨 warp 共享内存的同步开销并不进入分母，分数天然偏低，且偏低的幅度随隐藏维尺寸变化——这正是 SOL 适合做同口径下的横向排序、不适合做绝对达标线的原因。

失效来源对分数的作用工程处置
Byte_min 计数规则未固定（中间张量、融合许可）分母漂移，跨论文不可比在评测卡上显式声明计数规则与融合边界
T_SOL 未计 launch/同步小 kernel 分数偏低，去 launch 口径可越 1声明 T_meas 是否含 launch 摊销，并对 <10 µs 级 kernel 单独标注
算术强度贴近转折点重叠损失无法被 max 捕获与 NCU 的 dram throughput、sm busy 双指标并读，不单看 SOL

因此把 SOL 当作 agent 优化循环里的奖励信号时，必须把口径写进 reward 定义本身：固定 Byte_min 的计数规则、固定 T_meas 的计时边界（是否含 launch、是否做 warmup 摊销）、并对小尺寸形状设置“分数越 1 即判口径异常”的护栏。否则 RL 会学会优化分母假设而非优化 kernel——例如通过声明更激进的融合许可来抬高分数，而实测时间毫无改善。SOL 的价值在于它是一个可复现、可对齐的归一化坐标，前提是坐标系本身被冻结在评测协议里，而不是留在每次实验的口头约定中。
