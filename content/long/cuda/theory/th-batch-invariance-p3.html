一 · 归约顺序：批不变性失效的第一性来源

批不变性公式的成立前提是：对同一个输入 x，函数 f 在不同 batch 配置下走的是同一条数值计算路径。这个前提在 GPU kernel 里几乎从不自动成立。归约（reduction）是第一个被击穿的点。以 GEMM 的 K 维归约为例，kernel 通常把 K 切成若干 tile，每个 block 负责一段，再通过 split-K 或原子加合并。当 batch size 变化时，调度器给出的 block 数、每个 block 覆盖的 K 区间、以及合并顺序都会变。浮点加法不满足结合律，(a+b)+c 与 a+(b+c) 在舍入后可能差一个 ulp。于是即使算法在数学上等价，不同 batch 配置下的输出也会出现非零的 Δ_BI。

把这一点写成可检验的形式：设 K 维被切成 n(b) 段，段内顺序归约、段间树形合并，则输出是 n(b) 个部分和的函数。只要 n(b_1) ≠ n(b_2)，两个配置就在做不同的浮点运算序列，Δ_BI 的下界由该序列的舍入误差差决定，而不是由输入决定。这就是为什么逐位一致（τ_bit = 0）在 split-K kernel 上往往不可达：不是实现不够小心，而是归约树本身随 batch 改变。工程上能做的只有两件事——固定归约树（放弃 split-K 的自适应切分），或把 τ_bit 放宽到 τ_num 并声明。

代价是具体的。固定归约树意味着每个 block 必须覆盖固定的 K 区间，不能按 batch 动态调整并行度。在小 batch 下这会浪费 SM：原本可以切 8 段并行归约的 K，现在只能切 4 段，归约阶段的有效占用率下降，kernel 时延上升。反过来，若坚持自适应 split-K 以压低时延，就必须接受 Δ_BI > 0，把逐位一致降级为数值容差。这是一个显式的时延-可复现性权衡，agent 在优化时必须知道自己在选哪一边。

具体例子：一个 layernorm 的 backward kernel，对行内元素做归约。batch=1 时每行一个 block，行内 1024 元素顺序累加；batch=64 时为了填满 SM，把每行拆成两个半行并行归约再合并。两次的加法顺序不同，输出在最后几位上分叉。若下游是 logits 类输出，这个分叉会被 softmax 放大（见下文），Δ_BI 在概率空间里可能远超 ulp 量级。

二 · 容差声明：τ_num 不是常数，是任务契约

公式里 τ_num 看似一个阈值，实则是一个必须由任务方声明的契约。批不变性检验 pass ⟺ Δ_BI ≤ τ_bit 或 Δ_BI ≤ τ_num 的语义完全依赖 τ_num 的取值：取 0 就是逐位一致，取 10^{-6} 是宽松数值一致，取 10^{-2} 则几乎放过任何实现。agent 若自行挑选 τ_num，就等于自行定义了什么算“不变”，这是奖励黑客的温床——把阈值调大，pass 率立刻上升，但服务端的漂移并未消失。

因此 τ_num 必须与任务语义绑定，而不是与 kernel 实现绑定。对分类 logits，容差应定义在 softmax 后的概率上，因为下游消费的是概率而非 logits。设 logits 差为 δ，softmax 的 Jacobian 给出概率差的上界约 δ · p_max 量级；当某个类别的概率接近 1 时，logits 的微小差异被压缩；当概率分布平坦时，差异被放大到与 δ 同阶。这意味着同一个 τ_num 在 logits 空间通过检验，未必在概率空间通过。检验口径必须与部署端消费口径一致，否则批不变性检验给出的是虚假的安全感。

代价落在 token 与编译时间上。若任务要求逐位一致，agent 的搜索空间被大幅压缩：所有依赖动态切分、原子加、非确定性调度的优化都被排除，可探索的 kernel 变体数量下降，多轮 RL 中有效样本的多样性随之下降，达到同等 pass 率需要更多轮次与更多 token。若任务允许数值容差，搜索空间打开，但验证端必须额外跑一遍参考实现的概率空间比对，验证时延增加。这是一个验证成本与优化自由度的直接交换。

具体例子：同一份 softmax kernel，在 logits 空间 Δ_BI 落在 τ_num = 10^{-6} 内，但其中一个样本的 top-1 概率为 0.999，另一个为 0.5。前者概率差被压到 10^{-9} 量级，后者被放大到 10^{-6} 量级仍可接受；但若 τ_num 声明在概率空间为 10^{-8}，平坦分布样本就会失败。阈值口径选错，检验结论直接反转。

三 · 规模上限：batch 增大时失效条件如何累积

批不变性的失效不是二值的，它随 batch 规模单调恶化。原因有三层。第一层是归约段数 n(b) 随 batch 增大而增大（为填满 SM 而切得更细），归约树差异随之增大。第二层是累加链变长：batch 维若参与归约（如 batch 维的均值、方差统计），累加元素数从 b_1 变到 b_2，舍入误差的累积上界随元素数增长。第三层是调度非确定性：大 batch 下 block 数量多，原子加的到达顺序在硬件层面不可复现，同一 batch 配置跑两次都可能不同，更不用说跨配置。

把累积写成界：若每个浮点加法的相对误差不超过 u（单位舍入），长度为 m 的顺序累加，其误差上界正比于 m·u；树形归约把上界压到 log(m)·u。当 b_1 与 b_2 分别走顺序与树形两条路径时，Δ_BI 的上界由两条路径的误差界之差给出，随 m 增大而拉开。这就是规模上限的数学来源：不是某个固定 batch 值之后突然失效，而是 Δ_BI 随规模增长，直到越过 τ_num。

代价体现在显存与带宽上。要在大规模 batch 下维持批不变性，最直接的手段是固定归约路径并禁用原子加，改用确定性两阶段归约（先写部分和到显存，再统一合并）。这引入一次额外的显存往返：部分和缓冲区的读写增加带宽占用，且缓冲区大小随 batch 与切分数增长，峰值显存上升。对显存受限的部署，这个代价可能直接否决确定性方案，逼得工程方接受数值容差。

具体例子：一个 batch 维归约的 kernel，b=8 时切 4 段、树形合并，b=256 时切 32 段。段数从 4 到 32，归约树深度从 2 到 5，两条路径的误差界差随段数增长。若 τ_num 声明在 10^{-6}，小 batch 配置对通过，大 batch 配置对失败——失效不是均匀的，而是集中在规模高端。检验必须覆盖 batch 区间的两端，只测中间值会漏掉高端失效。

四 · 假设清单：公式成立需要哪些前提

批不变性公式 Δ_BI = max_{b_1,b_2} ‖f(x;b_1) − f(x;b_2)‖_∞ 的成立依赖一组未被写出的假设，工程上必须逐条核对。第一条：f 对同一 x 是纯函数，不依赖 batch 内的其他样本。若 kernel 做了跨样本归约（batch norm 的训练态统计、跨样本 softmax 归一化），则 f(x;b) 本身随 b 改变，批不变性在定义上就不成立——这不是数值误差，是语义依赖。第二条：batch 配置只影响调度，不影响数学。若 kernel 在 b 变化时切换算法（小 batch 走 GEMV、大 batch 走 GEMM），两条路径的数值行为不同，Δ_BI 由算法切换而非舍入主导。第三条：输入 x 的表示在两种配置下相同，不被 padding 或布局变换改变。

这三条假设中，第二条最容易被 agent 忽略。kernel 生成器常按 batch 阈值分派不同实现，理由是性能：小 batch 下 GEMM 的 tile 利用率低，GEMV 更快。但分派阈值两侧的数值路径不同，跨阈值比较 Δ_BI 时得到的是算法差异而非实现差异。检验若只在一个阈值内取样，会得出“批不变”的错误结论。正确做法是把阈值点作为必测的 (b_1, b_2) 对，显式覆盖算法切换边界。

代价是编译时间与验证覆盖。覆盖算法切换边界意味着每个分派阈值都要构造一对配置并跑参考比对，验证用例数随阈值数线性增长。若 kernel 有多级分派（如 b<8、8≤b<64、b≥64 三档），验证成本三倍于单档实现。多轮 RL 中，这意味着每轮验证的时延上升，单位 token 的有效反馈密度下降。

具体例子：一个 attention kernel 在 b≤4 时走 decode 路径（逐 token），b>4 时走 prefill 路径（批量矩阵乘）。两条路径的 softmax 归一化顺序不同，跨阈值 Δ_BI 由归一化顺序差异主导，量级远超同路径内的舍入差。若检验只在 b=2 与 b=3 之间比较，结论是 pass；在 b=4 与 b=5 之间比较，结论是 fail。批不变性的适用边界恰好落在分派阈值上。

五 · 失效条件的工程判定：何时放弃逐位一致

工程判断的核心不是“能否做到逐位一致”，而是“逐位一致的代价是否值得”。判定可以写成一条决策链：先看 f 是否跨样本耦合（假设一），耦合则批不变性在语义层不成立，直接放弃逐位一致并声明任务不支持动态 batching；再看归约是否随 b 改变切分（假设二），改变则逐位一致需要固定归约树，评估固定树的时延代价；最后看规模上限，若 Δ_BI 在大 batch 端越过 τ_num，则逐位一致不可达，降级为数值容差并声明 τ_num 的口径（logits 还是概率）。

这条链的每一环都有明确的观测手段。跨样本耦合可以通过构造两个仅在其他样本上不同的输入、比较 f(x;b) 是否变化来检测。归约切分可以通过 NCU 的 block 数与 split-K 配置观测。规模上限可以通过在 batch 区间两端取样、测量 Δ_BI 随 b 的增长趋势来外推。三者都不需要形式验证，只需要受控实验，代价是每个 kernel 变体的验证时延。

放弃逐位一致的代价必须被量化后写进任务契约，而不是隐式接受。若声明 τ_num 在概率空间为某值，服务端的动态 batching 就必须保证任意两个 batch 配置下的输出差不超过该值，否则契约被违反。这意味着部署端要么限制 batch 配置的跨度（不让 b_1 与 b_2 相差过大），要么在路由层做 batch 归一化（把请求填充到固定 batch 再计算，牺牲吞吐换可复现性）。两者都是真实的工程代价：前者限制调度自由度，后者增加 padding 计算量。

具体例子：一个推理服务在 batch 从 1 到 128 动态变化。若 kernel 声明逐位一致，则必须固定归约树并禁用 split-K，大 batch 下时延上升；若声明概率空间 τ_num，则必须验证 b=1 与 b=128 这一对的 Δ_BI 在阈值内，且部署端不得让 batch 跨度超过验证覆盖的范围。后者给出更大的优化空间，但把可复现性的责任从 kernel 转移到了调度层——这是一个必须显式记录的架构决策，而不是 kernel agent 单方面能决定的。

最终落在一条可执行的判定上：批不变性公式的适用边界由三个可测条件划定——跨样本耦合、归约切分随 b 变化、Δ_BI 随规模越过 τ_num。任一条件成立，逐位一致即不可达或代价过高，检验必须切换到声明了口径的数值容差，并把容差口径、验证覆盖的 batch 区间、以及部署端的 batch 跨度约束一并写进契约。公式本身不失效，失效的是“逐位一致”这个默认假设。

边界条件：归约拓扑、容差声明与规模天花板

批不变性公式的成立前提，是把 kernel 视为一个从输入张量到输出张量的确定性映射，且该映射的数值路径不随 b 改变。这个前提在两类实现上直接失效。其一是归约拓扑随 batch 分裂：split-K 的 K 维切分数、tile 覆盖的行数、warp 内 shuffle 的树形深度，都会随 batch 规模变化而重新编排，浮点加法不满足结合律，重排即产生非零 Δ_BI。其二是动态 batching 下的 padding 与掩码：为对齐 tile 而补的零参与归约，若归约实现未做掩码剔除，补零位置会改变累加次序与累加项数。因此逐位一致（τ_bit=0）在 split-K 与变 tile 场景下往往不可达，工程上必须退到 τ_num 通道，而 τ_num 的取值不能由 kernel 作者自定，须由任务侧按输出语义声明——这正是公式中 pass 判据写成析取而非单一阈值的原因。

$$\Delta_{\text{BI}}=\max_{b_1,b_2}\;\left\|f(x;b_1)-f(x;b_2)\right\|_{\infty},\qquad \text{pass}\iff \Delta_{\text{BI}}\le \tau_{\text{bit}}\;\text{or}\;\Delta_{\text{BI}}\le\tau_{\text{num}}$$

容差声明本身有代价。逐位通道要求 agent 放弃一切依赖 batch 形状的并行划分，等价于把 kernel 钉死在单一归约序上，编译期无法为不同 b 生成特化变体，吞吐收益被削掉；数值通道则把验证成本从“比较位模式”转为“构造覆盖 b_1,b_2 组合的扫描”，扫描的组合数是 batch 档位数的平方，每对组合都要跑一次前向并取无穷范数，验证时延随档位线性增长而实际比较次数平方增长。对 logits 类输出，微小差异经 softmax 后会被指数放大：Δ_BI 在 logits 上处于 τ_num 量级，落到概率分布上可能跨越采样边界，使贪心解码选出不同 token。这意味着 τ_num 不能只按 logits 的绝对误差设定，须按下游 softmax/采样环节的敏感度反推，否则公式在数值上 pass、在服务语义上 fail。

规模上限来自验证成本与显存占用的双重约束。b_1,b_2 的扫描需要同时驻留两份激活以计算差值，显存开销约为单次前向的两倍；当 b 接近单卡可容纳上限时，扫描本身会触发 OOM，公式的可行域被显存而非数学定义截断。更隐蔽的是编译时间：为覆盖 batch 档位而生成的模板实例化数量随档位数增长，每个实例都要独立编译与注册，编译时间成为 agent 迭代循环中的固定税。具体例子：一个 split-K 归约的 softmax kernel，在 b=1 与 b=64 两档下 K 维切分数不同，Δ_BI 非零且落在 τ_num 内，但若任务声明的 τ_num 按 logits 设定而未考虑 softmax 放大，该 kernel 会在服务端动态 batching 下产生不可复现的采样漂移——这正是边界条件必须与容差声明绑定、而非与 kernel 实现绑定的工程判断。
