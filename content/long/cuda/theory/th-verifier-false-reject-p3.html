一 · 参考实现作为标签源：FRR 的分母本身不可信

FRR 的定义把「correct」当作已知量，但工程上这个集合从来不是白给的：它由参考实现（reference）与容差判据共同构造。于是公式的适用边界第一条就是——参考实现必须被独立验证过。一旦参考实现本身有错，分子与分母同时被污染：某些真正正确的 kernel 被参考的偏差推向 reject 侧，而参考的偏差又可能让某些错误 kernel 恰好落在容差带内。此时 FRR 不再是「验证器的误拒率」，而是「验证器与参考实现联合体的不一致率」，两个误差源无法从单一统计量中分离。

机制上，这等价于把标签函数写成 $$y=\mathbb{1}\big[\lVert K(x)-R(x)\rVert\le\tau\big]$$，其中 R 是参考、τ 是容差。FRR 度量的是 $$\Pr(y=0\mid K \text{ 真正确})$$，可这个条件概率里的「真正确」若也用 R 定义，就退化成自指。要打破自指，必须引入第二个独立 oracle：高精度 CPU 实现、区间算术、或形式化规约（后者在别的条目展开）。没有第二 oracle 时，任何 FRR 数字都只能解释为「相对于该参考的一致性」，不能跨参考实现横向比较。

代价是显式的：独立 oracle 通常比 GPU 参考慢一到几个数量级，若对每个候选 kernel 都跑一遍，验证吞吐会被 oracle 的时延钉死；折中做法是分层抽样——只对 reject 集合与 accept 集合各抽一小批做 oracle 复核，用复核结果估计参考自身的错误率，再据此给 FRR 加上修正项。这个修正项本身有方差，抽样比例越低方差越大，token 预算与置信区间宽度直接对冲。具体例子：某 validator 对一批正确 kernel 报出高 FRR，复核发现其中多数是参考实现在边界输入（如极小 batch、含零元素）上数值退化所致，真实 FRR 远低于表面值——若不复核，agent 会朝错误方向重写 kernel。

二 · 容差 τ 是双刃变量：FRR 与 FAR 沿同一条曲线滑动

公式里 τ 没有出现，但它是隐藏自变量。放宽 τ 会降低 FRR（更多正确实现落入带内），同时抬高 FAR（更多错误实现也被放过）；收紧 τ 反之。因此 FRR 不能单独作为验证器质量的标尺，必须与 FAR 成对报告，且必须声明 τ 的取值口径——是绝对误差、相对误差、ULP 距离还是混合范数。不同口径下同一条曲线形状完全不同，跨论文比较 FRR 而无 τ 口径等于比较两个不同的函数。

把两者写成一条权衡曲线：以 τ 为参数，点集 $$\big(\mathrm{FRR}(\tau),\ \mathrm{FAR}(\tau)\big)$$ 构成验证器的工作特征曲线。工程判断落在曲线的拐点附近：拐点左侧 τ 过紧，FRR 主导，搜索预算被大量浪费在重写本来正确的 kernel 上；拐点右侧 τ 过松，FAR 主导，错误 kernel 进入下游，正确性债务被推迟到端到端测试才暴露，修复成本高一个量级。拐点位置依赖任务分布——归约类 kernel 的误差累积路径长，拐点偏右；逐元素 kernel 路径短，拐点偏左。

具体机制上，τ 的选择应与误差累积界联动（该界在浮点误差条目中给出），把 τ 设为「该界在目标规模下的上界」而非拍脑袋常数。代价是：误差界本身是保守的，用它当 τ 会把一批数值上完全可接受的实现判为 reject，FRR 被人为抬高；反之若 τ 低于界，FAR 上升且随规模增长而恶化。规模是这里的关键变量——误差界通常随归约长度对数或线性增长，固定 τ 在中小规模上合适，在长归约上必然失效。因此 τ 必须是规模的函数，验证器若用常数 τ 跑全规模评测，其 FRR/FAR 报告只在被校准的那个规模点上成立。

三 · 对抗样本：两种错误率可以同时被推高

通常的权衡曲线假设 FRR 与 FAR 沿一条单调曲线此消彼长。这个假设在存在对抗输入时不成立：精心构造的输入可以让正确实现落在容差带外、同时让错误实现落在带内，于是两个错误率同时上升，曲线被整体推离原点。触发条件是验证器的判据对输入的某类结构敏感——例如只在特定数值范围、特定内存对齐、特定 stride 下才暴露的偏差。

机制上，对抗样本利用的是判据的「盲区」与「过敏感区」并存：盲区让错误实现逃逸（FAR 升），过敏感区让正确实现的微小无害差异被放大（FRR 升）。对 LLM 生成的 kernel 而言，这不是理论威胁——agent 在 RL 循环中会主动搜索能通过验证器的写法，若验证器判据可被输入结构操纵，搜索压力会自然把候选推向这些结构，形成奖励黑客的一种具体形态（激励不相容在别处展开，此处只指出它对 FRR 估计的污染）。

工程代价：要检测这种同时抬升，必须做输入分布的分层评测，而不是在单一随机分布上取平均。分层意味着评测用例数成倍增加，每个用例都要跑参考与候选，时延与显存占用线性上涨；若用固定种子的小样本，对抗结构极易被漏掉，报告的 FRR 系统性偏低。具体例子：某 validator 在随机输入上 FRR 很低，但把输入换成含大量次正规数或极端指数的分布后，正确 kernel 因不同的舍入顺序被判错，错误 kernel 因恰好复现参考的舍入路径被判对——两个错误率同向恶化，单分布平均值完全掩盖了这一现象。

四 · 规模上限：FRR 随问题规模漂移，公式在超界后失效

FRR 不是常数，它是规模的函数。原因在于验证器内部的判据（容差、采样点、归约检查）几乎都带有规模假设：固定 τ 在大规模上过紧，固定采样点数在大规模上覆盖率骤降，固定超时阈值在大规模上把慢但正确的实现判为失败。三者叠加，FRR 随规模单调漂移，方向取决于哪个因素主导。

把规模效应写成可检验的形式：设判据为 $$\text{reject}=\mathbb{1}\big[\lVert K-R\rVert>\tau(n)\big]\ \lor\ \mathbb{1}\big[t(K)>\theta(n)\big]$$，其中 n 是问题规模，τ 与超时 θ 若为常数，则第一项随 n 增大而更易触发（误差界增长），第二项随 n 增大而更易触发（执行时间增长）。两个「更易」不是线性的，误差界可能对数增长而时间线性增长，交叉点决定了 FRR 曲线的主斜率切换位置。验证器若未在多个规模点上校准 τ 与 θ，其 FRR 报告只在单一规模点有效，外推即失效。

规模上限还有一层：验证器自身的资源上限。参考实现与候选 kernel 同时驻留显存，规模增大到某一阈值后验证器无法同时容纳两者，只能串行或分块，分块改变数值路径又引入新的判据偏差。此时 FRR 的上升不是候选 kernel 的问题，而是验证基础设施的问题——把它记在 agent 头上会误导搜索方向。工程判断是：在评测协议里显式声明验证器的规模适用范围，超出范围的 FRR 数字标注为「不可比」，而不是与其他规模点混在一起求平均。代价是评测矩阵变大，每个规模点都要独立校准，token 与算力预算按规模点数线性分摊。

联合判定规则：只要参考独立性缺失，FRR 数字就降级为「相对一致性指标」，不得用于跨验证器排序；只要 τ 为常数且评测跨多个规模，FRR 只在被校准点有效；只要输入未分层，FRR 是下界而非估计值。三条同时满足时，FRR 才可作为公式意义上的误拒率使用。这个判定本身要花评测预算——每条检查都需要额外用例或复核，成本与可信度直接对冲。

具体例子：一个 agent 流水线报告某轮 FRR 显著下降，检查表显示 τ 在该轮被悄悄放宽且评测规模缩小，两个变量同向压低 FRR，而 FAR 未被报告。按联合判定规则，这个下降不可信，不能作为验证器改进的证据；正确的做法是固定 τ 口径与规模点重跑，或在报告中同时给出 FAR 与规模标签。工程上把这张检查表嵌入评测脚本的元数据，比事后人工审查更可靠——元数据缺失时脚本直接拒绝输出 FRR 汇总，强制每个数字携带其适用域。

最终落在机制上：FRR 的适用边界不是一条静态的数学条件，而是由参考独立性、τ 的规模依赖、输入分层覆盖率三者共同张成的区域；区域之外，公式仍然能算出数，但那个数不再度量验证器的误拒倾向，而度量的是评测配置本身的偏差。判断一个 FRR 数字能否进入决策，等价于判断它是否携带了这三项元数据——没有元数据的 FRR 在工程上应被视为未定义，而不是一个偏保守或偏乐观的估计。

当“正确”本身不可靠：参考实现、容差与对抗输入如何让 FRR 失去意义

FRR 的分子是“被判错的正确实现”，这个定义把正确性标签完全外包给参考实现。一旦参考实现自身有数值缺陷——比如归约顺序导致的浮点误差、未处理边界条件、或在某些形状上退化为串行路径——那么“正确→reject”的计数就不再是验证器的过错，而是标签噪声。此时 FRR 与 FAR 同时失真：一个真正正确的 kernel 可能因为与错误参考不一致而被记为 false reject，而一个同样偏离参考但恰好落在容差内的错误 kernel 被记为 accept。工程上判断 FRR 是否可信，第一步不是看验证器，而是看参考实现是否经过独立 oracle 交叉验证；否则 FRR 只是“与参考的一致率”的补集，而非正确性度量。代价是显性的：为参考实现建立第二套独立实现（例如 CPU 高精度版本或 MPFR 路径）会引入额外的编译与运行时间，且在 GPU 上逐元素比对需要把中间张量回传到主机，带宽开销随张量规模线性增长。

容差是第二个边界变量。设逐元素判定为 $$|a_i-b_i| \le \tau + \rho|b_i|$$，则 τ 与 ρ 的每一次收紧都会把一批数值上合法的实现推入 reject 集合，FRR 上升；每一次放宽则把近似错误的实现拉入 accept 集合，FAR 上升。两者不是独立可调的：在 KernelAudit 发现的 6 个存在不可忽视 false-reject 的 validator 中，问题恰恰出在容差与参考实现的联合设定上——收紧容差以压制 FAR，代价是 FRR 抬升，搜索预算被大量消耗在重新生成本已正确的 kernel 上。对 agent 而言这不是中性代价：一次 false reject 会触发多轮重写，每轮都消耗 token 与编译时间，而编译一个中等规模 CUDA kernel 的时延远高于一次前向推理，重试次数直接转化为 wall-clock 预算。

规模上限来自比对本身的结构。逐元素容差判定的成本是 O(N) 的访存与比较，但当 N 增大到需要分块归约时，判定逻辑必须处理跨块累积误差；若验证器采用全局范数相对误差（如 ‖a−b‖/‖b‖），则单个大幅值元素的偏差会被整体范数稀释，FAR 在长尾分布上系统性偏高，而 FRR 在小幅值元素上偏高。更隐蔽的失效来自对抗输入：构造使参考与候选在容差边界两侧摆动的输入，可以同时推高两种错误率，使 FRR/FAR 的测量值不再反映验证器在自然分布上的行为。因此这套公式的适用边界应明确写死：参考实现经独立 oracle 验证、容差在目标分布上标定、输入分布非对抗且规模在比对策略可承受的分块范围内；越出任一条，FRR 数值只能作为相对比较的序参量，不能作为绝对可信度声明。
