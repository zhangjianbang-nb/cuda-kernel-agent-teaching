一 · 计数规则固定之前，SOL 不是度量而是约定

公式里 Byte_min 与 FLOP_min 的语义看似自明，实则是一份未签字的合同。同一段 attention 计算，若把 softmax 的中间张量计入 DRAM 字节，Byte_min 会显著抬高；若认定融合实现可以完全驻留片上，Byte_min 则被压到只剩输入输出。两种口径下 T_SOL 相差可达数倍，而 T_meas 是同一个数，SOL 分数随之分裂。跨论文比较之所以危险，不在于测量噪声，而在于双方对“算法必需”的定义不同：一方按未融合的算子图逐节点累加，另一方按理论最小数据流下界计算。

工程上可行的做法是把计数规则写成可执行的判定函数，而不是散文描述。伪代码思路如下：对计算图做一次数据流分析，标记每个张量的生命周期——若某张量在融合后能被寄存器或共享内存完全吸收且不被外部观察，则不计入 Byte_min；否则计入一次写与一次读。FLOP_min 同理，需声明是否允许代数重写（如把两个同底 matmul 合并）来削减运算数。规则一旦固定，SOL 就退化为“在该规则下的最优实现假设”，可比性被限定在同一规则族内。

代价体现在评测吞吐上：严格的融合可行性判定需要对每个候选实现做一次编译期资源核算（寄存器压力、共享内存容量），单 kernel 的判定开销在毫秒级，但对 KernelBench 规模的批量评测会累积成可观的编译时间预算；更宽松的规则省掉这一步，却把不可比性引入分数。具体例子：两个团队各自报告同一 LayerNorm 融合 kernel 的 SOL，一方把中间均值方差张量计入 Byte_min，另一方不计，前者分数系统性偏低，评审若不做规则对齐就会误判后者实现更优。

二 · 小 kernel 上 SOL 越过 1 的结构性原因

T_SOL 只由带宽项与算力项取大构成，不含 launch 与同步的不可消除开销。当 kernel 的实际工作量小到执行时间与 launch 延迟同量级时，实测时间里有一块是固定成本，而 SOL 下界时间里没有对应项，于是 T_SOL / T_meas 可以大于 1。这不是测量错误，是口径缺陷：分母漏掉了必须支付的固定项。

$$\text{SOL}_{\text{corr}}=\frac{T_{\text{SOL}}}{T_{\text{meas}}-T_{\text{fixed}}},\qquad T_{\text{fixed}}=T_{\text{launch}}+T_{\text{sync}}$$

修正口径要求显式扣除固定项，但扣除本身引入新的不确定性：T_fixed 随驱动版本、流优先级、是否使用 graph capture 而变，且难以从单次测量中分离。可行的折中是声明“含 launch 摊销口径”——把 T_meas 定义为一批 N 次调用的平均时间，让固定项摊薄到可忽略，同时声明 N 的取值。N 太小则分数虚高，N 太大则掩盖了单次调用的真实时延特征，二者都是口径选择而非物理事实。

具体例子：一个逐元素缩放 kernel 在极小形状下，实测时间几乎全由 launch 构成，SOL 分数轻松超过 1；同一 kernel 在批量摊销口径下分数回落到 1 以下并趋于稳定。评审若只看单次口径的数字，会把“固定开销占比高”误读为“实现超越硬件极限”。性能代价在此处转化为评测可信度代价：为了拿到稳定的摊销口径，需要把批量规模调到固定项占比低于阈值，这直接拉长了单点评测的墙钟时间。

三 · 规模上限：当 Byte_min 假设被缓存层级推翻

Byte_min 的定义隐含“所有必需数据都从 DRAM 搬运”的前提。当问题规模小到工作集能整体驻留 L2，或分块策略使重复访问命中片上缓存时，真实 DRAM 流量低于 Byte_min，带宽项下界变得保守，SOL 分数被系统性压低——实现明明更快，分数却上不去，因为分母假设了不存在的 DRAM 压力。反向的失效发生在规模过大时：分块后的中间结果无法驻留，必须回写 DRAM，实际字节数超过按理想融合估算的 Byte_min，此时 SOL 分数虚高，实现看似接近极限实则被额外流量拖累。

判定边界需要一个容量判据：设工作集为 W，片上可用容量为 C（共享内存加寄存器文件扣除占用率约束后的有效值），当 W ≤ C 时 Byte_min 的 DRAM 假设失效，应改用片上带宽项重写 T_SOL；当分块产生的中间张量总量超过 C 时，需在 Byte_min 中补入回写字节。这两个判据都可以在编译期由资源核算得到，代价是每个形状都要重算一次口径，跨形状可比性因此被削弱——同一 kernel 在小形状与超大形状下适用的 SOL 公式不同，分数不能直接并列。

具体例子：一个归约 kernel 在中等形状下按 DRAM 带宽口径得分接近上限，形状缩小到工作集落入 L2 后，实测时间由片上延迟主导，DRAM 带宽项不再是瓶颈，原公式给出的 T_SOL 偏大，分数被压到失真；此时正确做法是切换到片上口径并单独标注，而不是把两个形状的分数放进同一张对比表。

四 · 峰值算力项的可达性假设与精度绑定

算力项 FLOP_min / P_peak 中的 P_peak 是硬件标称峰值，其可达性依赖指令 mix 与数据精度。若算法必需的是 FP32 运算而峰值按 Tensor Core 的低精度吞吐标定，算力项下界被低估，SOL 分数虚高；反之若 kernel 实际以低精度张量指令执行却被按 FP32 峰值计价，分数被压低。精度与峰值必须成对声明，否则算力项不构成下界。

更深一层的失效是：P_peak 假设了无依赖停顿的满发射。真实 kernel 中指令级依赖、流水线气泡与寄存器 bank 冲突使可达吞吐低于峰值，这一差距已被占用率与延迟隐藏机制吸收（见该条目），但 SOL 公式把它当作零。于是当 kernel 受限于依赖链而非吞吐时，SOL 分数天然偏低，且偏低幅度与实现的调度质量无关，只与算法结构有关。此时 SOL 不再衡量“离硬件极限多远”，而混入了“算法本身能否喂满流水线”的信息。

代价是评测解释成本：同一分数在不同精度口径下含义不同，报告必须携带精度标签与峰值来源。具体例子：一个以 FP32 累加、低精度输入的混合精度 kernel，若按低精度峰值计价则算力项极小、带宽项主导，SOL 反映的是访存效率；若按 FP32 峰值计价则算力项抬升，分数结构完全改变。两种计价都“正确”，但不可混用。

五 · 跨 kernel 可比性的三重前提与破裂点

SOL 声称跨 kernel、跨形状可比，这一声称成立需同时满足三个前提：计数规则一致、固定开销口径一致、峰值与精度绑定一致。任一前提破裂，分数就退化为同一规则族内的相对量。工程上应把这三个前提编码为评测元数据，与分数一同落库，缺项即标记为不可比。这不是形式主义：多轮 RL 的可验证奖励若直接吃 SOL 分数而不检查元数据，奖励信号会在口径漂移时给出错误梯度，把策略推向“迎合口径”而非“逼近硬件”。

破裂点的具体机制在于口径的隐式继承：一个 kernel 的 Byte_min 规则往往从参考实现抄来，参考实现若已融合则规则偏紧，若未融合则偏松，下游实现无论多优都无法跳出继承来的口径。跨形状时，同一规则在不同规模下的适用性还会翻转（见第三节），使“跨形状可比”在极端规模区间失效。性能代价体现在评测流水线：为保证可比，每个候选实现都要在同一规则下重算 T_SOL，规则重算的编译期开销与批量规模线性相关。

具体例子：把两个来源不同、计数规则不同的 GEMM kernel 分数并列，其中一个把 epilogue 融合计入 Byte_min 节省，另一个按未融合计，前者分数系统性偏高；若奖励函数以此排序，会奖励“口径选择”而非“实现质量”，这正是奖励黑客的一种形态（见该条目），其根因不在激励设计而在度量口径未闭合。

六 · 失效条件的工程判据：何时不该用 SOL

把上述边界收拢成可操作的判据：当固定开销占实测时间比例超过阈值、当工作集落入片上容量、当算法受依赖链而非吞吐限制、当精度与峰值计价不匹配、当计数规则无法与对比对象对齐时，SOL 分数不应作为主排序键。此时应降级为带标签的辅助指标，主排序改用端到端时延或经摊销的吞吐，并把 SOL 仅用于同规则族内的相对比较。

判据的落地方式是评测前的口径审计：对每个候选实现，先算出固定项占比、工作集与容量比、依赖链深度估计、精度标签，四项中任一触发失效条件就在分数旁打标，并在聚合时按标签分层。分层聚合的代价是样本被切碎，统计功效下降，置信区间变宽（见计时噪声与置信区间条目），但换来的是排序不被口径漂移污染。具体例子：一个小形状逐元素 kernel 在四项审计中触发固定项占比与工作集两项，其 SOL 分数虽高却被标记为不可用于跨形状排序，评审据此改看摊销吞吐，避免了把 launch 开销误读为算力优势。

最终落在一条工程判断上：SOL 的价值不在于给出一个绝对数字，而在于把“离硬件极限多远”这个问题压缩成一个可计算的比值；一旦比值的前提被打破，继续使用它就等于用一个失效的下界去评价实现，误差方向不可预测且不可校正。口径审计的成本是评测流水线的一次性工程投入，收益是奖励信号与评审结论在规模、精度、融合策略变化时保持方向正确。

当“最优实现”假设崩塌：SOL 口径的失效面

SOL 分数的分母是 T_SOL，而 T_SOL 并非硬件实测值，它是一个“存在某个最优实现”的构造性下界。这个假设在三种情形下会直接失效。第一种是计数规则不闭合：Byte_min 是否计入中间张量、是否允许把多个算子融合成单次读写，FLOP_min 是否把 softmax 的归约与 exp 计入、是否允许用代数等价变换削减运算量，这些选择会让同一个 kernel 的 T_SOL 相差数倍。口径一旦不同，两个 SOL 分数之间不存在任何偏序关系——0.6 与 0.8 谁更优无法判断，因为它们的分母不是同一个下界。工程上唯一可接受的做法是把计数规则写成可执行的“字节账本”：逐张量列出读、写、是否驻留片上，把融合边界钉死，再让评分脚本从同一份账本生成 Byte_min，而不是靠人工口算。

第二种失效来自 T_SOL 对固定开销的系统性忽略。公式只取带宽项与算力项的较大者，隐含假设 kernel 一旦启动就能把硬件喂满。但真实执行里存在不可消除的 launch 延迟、grid 尾部不满一个 wave 的量化损失、以及跨 kernel 的同步与依赖等待。把这些记为 T_fix 后，更贴近实际的下界应是 T_SOL' = max(Byte_min/B_eff, FLOP_min/P_peak) + T_fix。当 T_meas 逼近前者时，T_SOL/T_meas 会被 T_fix 的相对占比推高，小 kernel 上 SOL 分数超过 1 不是实现超越了硬件，而是分母漏掉了必须付出的那部分时间。判定阈值可以写得很具体：若 T_fix/T_SOL > 5%，该 kernel 的 SOL 分数就应标注为“含固定开销偏差”，不参与跨形状排名。

第三种是规模上限。带宽项随 Byte_min 线性增长，而 T_fix 近似常数，因此大形状下固定开销被摊薄、SOL 口径自洽；反过来，当形状小到工作集可以整体驻留 L2 或共享内存时，Byte_min 的 DRAM 口径本身就不再是瓶颈的真实刻画，此时应改用片上带宽与占用率建模，而不是硬套 DRAM 下界。同一份评分体系里混用两种口径，等于把不同物理 regime 的分数放进同一张表。

失效来源表现系统代价
计数规则不一致分数不可跨论文比较需重跑账本与评分脚本，编译与复测时间翻倍
忽略 T_fix小 kernel SOL > 1排名被 launch 开销主导，误导选型

一个具体例子：逐元素缩放 kernel 在极小张量上实测时间几乎全由 launch 与尾部 wave 构成，按原公式算出的 SOL 会明显偏高；把 T_fix 显式并入分母后分数回落到合理区间，代价是每次评测要多采集一次空 kernel 基线以标定 T_fix，profile 轮次与 token 消耗随之增加。这类标定成本必须计入评测预算，否则“可比”只是纸面承诺。
