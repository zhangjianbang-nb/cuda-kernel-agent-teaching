一 · 公式隐含的三个前提

前两部分给出的 $$T_{\text{step}}=T_{\text{launch}}+\max\left(T_{\text{kernel}},\;T_{\text{queue}}\right)$$ 与 $$\eta_{\text{launch}}=\frac{T_{\text{kernel}}}{T_{\text{launch}}+T_{\text{kernel}}}$$ 之所以能写成加法形式，依赖三个未被写出的前提，而适用边界正是由这三个前提的破裂位置划定的。

第一个前提是串行提交：CPU 侧在发起第 i 次 launch 之前，必须已经完成第 i−1 次 launch 的提交动作，且两者之间没有重叠窗口。第二个前提是单流：所有工作进入同一条 stream，因而 $$T_{\text{queue}}$$ 是单调累积的排队量，不存在另一条流上的 kernel 与本 kernel 并行填充 GPU。第三个前提是开销恒定：$$T_{\text{launch}}$$ 被当作与 kernel 形态、参数数量、上下文状态无关的常数，从而 $$\eta_{\text{launch}}$$ 只随 $$T_{\text{kernel}}$$ 变化。

这三个前提在朴素 PyTorch 逐算子调用场景下基本成立，因此公式在该场景下是可信的工程近似。但一旦进入 agent 生成的 kernel 评测流水线——尤其是带 CUDA Graph 捕获、persistent kernel 驻留、多流 overlap 的评测框架——前提会逐个破裂。破裂不是“公式稍微不准”，而是公式的函数形式本身失效：加法项消失、max 项被并行项替代、常数项变成随机变量。下面三节分别处理这三种破裂，最后一节给出规模上限的判据。

二 · 失效条件一：图捕获与常驻 kernel 抹掉加法项

CUDA Graph 的机制是把一串 launch 的提交动作在捕获阶段录制为一张有向图，重放时由驱动一次性提交整张图，CPU 侧只付出一次图重放开销，而非 N 次独立 launch 开销。persistent kernel 则更进一步：kernel 常驻 SM，通过设备侧队列或原子标志轮询取任务，CPU 完全不参与每次“逻辑 launch”的提交。两种机制都把 $$T_{\text{launch}}$$ 压到微秒级以下，此时 $$T_{\text{launch}}\ll T_{\text{kernel}}$$，公式退化为纯计算界：

$$T_{\text{step}}\approx\max\left(T_{\text{kernel}},\;T_{\text{queue}}\right),\qquad \eta_{\text{launch}}\to 1$$

这里的关键工程判断是：一旦评测框架启用了图捕获，用 $$\eta_{\text{launch}}$$ 做的任何“launch 占比”归因都失去意义，因为分母里的固定项已经不存在，剩余的时间差全部来自 $$T_{\text{kernel}}$$ 本身或排队。此时若仍按旧公式解释 profile 中 kernel 之间的空隙，会把图重放开销、图节点间的依赖同步误判为 launch 开销，进而给出错误的优化方向（例如去合并算子，而真正瓶颈是图内节点粒度过细导致的依赖串行）。

代价体现在另一侧：图捕获要求 kernel 参数在重放时保持地址稳定，agent 生成的 kernel 若使用动态分配的临时缓冲区，捕获会失败或需要额外的地址固定层；persistent kernel 则要求 kernel 内部实现任务分发逻辑，这本身引入轮询开销与尾任务不均衡——当任务粒度细到与轮询周期同量级时，persistent kernel 的收益被自身调度开销吃掉。一个具体例子：一个由 8 个逐元素算子组成的融合链，逐算子提交时 $$T_{\text{launch}}$$ 主导、$$\eta_{\text{launch}}$$ 很低；改用图捕获后 $$T_{\text{launch}}$$ 消失，但若这 8 个节点在图中仍是串行依赖，总时间仍等于 8 个 $$T_{\text{kernel}}$$ 之和，图只摊销了提交开销、没有摊销依赖链——这正是公式退化后必须转向依赖图分析的原因。

三 · 失效条件二：多流并发使单流串行模型失效

单流模型把 $$T_{\text{queue}}$$ 当作串行累加量，但在多流场景下，第 i 条流上的 kernel 可以在第 j 条流的 kernel 执行期间完成自己的提交，即 $$T_{\text{launch}}$$ 被隐藏在另一条流的 $$T_{\text{kernel}}$$ 之下。此时端到端时间不再由单条流的加法式给出，而由所有流的关键路径决定：

$$T_{\text{step}}=\max_{s\in\text{streams}}\left(\sum_{k\in s}T_{\text{kernel},k}\right)+\text{关键路径上的残余提交开销}$$

公式的失效方式是结构性的：单流公式中 $$T_{\text{launch}}$$ 是每条流都要付的税，多流下它变成可被并行填充的空隙。因此“launch 开销占比”在多流下不再是单条流的属性，而是整个提交-执行流水线的填充率。工程上这意味着：在多流评测中观察到 GPU 利用率不满，不能直接归因于 launch 开销，必须先判断是提交侧供给不足（CPU 打不满）还是依赖侧阻塞（流间同步点过多）。

代价是同步与竞争：多流并发要求流间事件同步正确，否则正确性 oracle 会在竞态下给出不稳定结果；同时多条流共享 L2 与显存带宽，$$T_{\text{kernel}}$$ 本身会因带宽竞争而膨胀，公式中原本视为常数的 $$T_{\text{kernel}}$$ 变成与并发度相关的量。一个具体例子：agent 生成的 kernel A 与框架自带的拷贝 kernel B 分属两条流，若 B 的拷贝占满 HBM 带宽，A 的 $$T_{\text{kernel}}$$ 被拉长，此时即便 $$T_{\text{launch}}$$ 完全被隐藏，端到端时间仍可能劣于单流串行——多流不是免费的，它把 launch 开销换成了带宽竞争开销。

四 · 失效条件三：开销非恒定与参数规模效应

第三个前提——$$T_{\text{launch}}$$ 与 kernel 形态无关——在参数规模变大时开始松动。launch 开销中包含参数拷贝到常量/参数区的部分，参数越多、结构体越大，CPU 侧打包与驱动侧校验的成本越高；此外，kernel 的 grid/block 配置若触及占用率边界，驱动侧的资源检查与启动配置也会带来额外成本。因此更准确的写法是把 $$T_{\text{launch}}$$ 视为参数的函数：

$$T_{\text{launch}}=T_{\text{fixed}}+c\cdot n_{\text{param}}+T_{\text{config}}(grid,block)$$

当 $$c\cdot n_{\text{param}}$$ 与 $$T_{\text{fixed}}$$ 同量级时，把 $$T_{\text{launch}}$$ 当常数会系统性低估开销，尤其在 agent 生成的 kernel 常带大量模板参数、张量描述符、stride 数组的场景。代价直接体现在 token 与编译时间上：为压低参数规模而做的模板特化会增加编译时间，而 agent 若在搜索中反复重编译不同参数布局的变体，编译时间会挤占本可用于 kernel 执行的评测预算。

一个具体例子：同一算子，参数为 3 个指针时 launch 开销可忽略；参数扩展为 3 个指针加 8 个 stride、4 个 shape、2 个标量标志时，参数区打包成本上升，在 $$T_{\text{kernel}}$$ 很短的逐元素 kernel 上，这部分增量足以让 $$\eta_{\text{launch}}$$ 明显下降。此时正确的优化不是“减少 launch 次数”，而是压缩参数布局（把 stride/shape 打包进单个描述符结构体、用设备端常量内存承载只读元数据），这与批量化是两条不同的摊销路径。

五 · 规模上限：公式在哪个 $$T_{\text{kernel}}$$ 区间还有解释力

把 $$\eta_{\text{launch}}$$ 对 $$T_{\text{kernel}}$$ 求导可得其灵敏度：

$$\frac{\partial\eta_{\text{launch}}}{\partial T_{\text{kernel}}}=\frac{T_{\text{launch}}}{(T_{\text{launch}}+T_{\text{kernel}})^2}$$

该导数在 $$T_{\text{kernel}}=T_{\text{launch}}$$ 处取最大值，即公式的解释力最强区间恰在 kernel 时间与 launch 开销同量级处；当 $$T_{\text{kernel}}\gg T_{\text{launch}}$$ 时导数趋零，$$\eta_{\text{launch}}$$ 饱和于 1，公式不再提供任何区分度——此时继续用 launch 占比解释性能差异是无效归因。反过来，当 $$T_{\text{kernel}}\ll T_{\text{launch}}$$ 时 $$\eta_{\text{launch}}\to 0$$，公式退化为 $$T_{\text{step}}\approx T_{\text{launch}}\cdot N$$，吞吐完全由提交频率决定，与 kernel 质量无关。

由此得到规模上限的判据：当单 kernel 时间低于 launch 开销一个数量级以上时，对该 kernel 做指令级优化（减少 warp stall、提高占用率）在端到端吞吐上不可观测，评测应转向批量化或图捕获；当单 kernel 时间高于 launch 开销一个数量级以上时，launch 项可忽略，评测应转向 roofline/SOL 口径。公式的有效窗口就是这两条边界之间的中间带，宽度由 $$T_{\text{launch}}$$ 的绝对量级决定——图捕获把窗口整体左移，使更多小 kernel 落入“纯计算界”一侧。

代价是评测分辨率：在中间带内，$$T_{\text{launch}}$$ 的抖动与 $$T_{\text{kernel}}$$ 的抖动同量级，单次计时无法区分二者，必须依赖重复采样与置信区间（该口径见计时噪声条目，此处不展开）。一个具体例子：一个 $$T_{\text{kernel}}$$ 与 $$T_{\text{launch}}$$ 相当的 reduction kernel，agent 把 block 数翻倍以提升并行度，$$T_{\text{kernel}}$$ 略降，但 grid 配置变化带来的启动配置成本使 $$T_{\text{launch}}$$ 略升，端到端 $$\eta_{\text{launch}}$$ 几乎不变——这正是公式在饱和区失去区分度的具体表现，也是 agent 在该区间做搜索时容易陷入的无效优化循环。

六 · 边界之外的工程判断

把三条失效条件合起来看，公式的适用边界可以表述为一个二维判据：横轴是 $$T_{\text{kernel}}/T_{\text{launch}}$$ 的比值，纵轴是提交-执行流水线的并行度（单流串行 → 多流 → 图/persistent）。比值在 0.1 到 10 之间且并行度为单流串行时，公式是可信的一阶模型；比值越界则公式退化为纯提交界或纯计算界；并行度升高则加法项被隐藏、max 项被关键路径替代。agent 在生成 kernel 时若不做这一判据检查，就会把优化预算花在公式已失效的区间——例如对已被图捕获的微 kernel 做 SASS 级调优，或对已饱和的大 kernel 反复削减 launch 次数。

更细的工程判断落在评测框架自身的配置上：同一个 agent 生成的 kernel，在逐算子提交、图捕获、persistent 三种评测模式下会得到三组不同的 $$\eta_{\text{launch}}$$，而 kernel 代码本身未变。因此任何跨条目、跨实验的 launch 占比比较，必须先声明评测模式的并行度与是否启用图捕获，否则比较的是框架配置而非 kernel 质量。这一条对可验证奖励的设计有直接影响：若奖励函数以端到端时间为信号，而评测模式在图捕获与逐算子之间切换，奖励信号会随模式漂移，agent 学到的可能是“适配评测框架的提交模式”而非“更快的 kernel”——这正是公式适用边界与奖励黑客风险的交汇点。

公式失效的三种现场：谁在替 T_launch 买单

前文给出的 $$T_{\text{step}}=T_{\text{launch}}+\max\left(T_{\text{kernel}},\;T_{\text{queue}}\right),\qquad \eta_{\text{launch}}=\frac{T_{\text{kernel}}}{T_{\text{launch}}+T_{\text{kernel}}}$$ 成立的前提比它看上去要窄：它默认每一步只有一次 launch、单流串行、且 T_launch 是必须由该步独立承担的固定成本。这三条假设中任何一条被打破，η_launch 就不再是描述系统的量，而只是描述“某一种提交方式”的量。工程上判断是否该套用这个模型，第一步不是测 T_kernel，而是先确认 T_launch 到底有没有被别的东西吸收——如果被吸收了，公式里的加号就该换成 max，甚至整项消失。

第一种失效来自提交机制的替换。CUDA Graph 把一串 launch 的 CPU 提交与驱动校验一次性固化成图，重放时 T_launch 被压到微秒级以下；persistent kernel 则更进一步，把多次迭代收进同一个常驻 kernel 的循环里，launch 次数从 N 降到 1。此时公式退化为纯计算界 T_step ≈ T_kernel，η_launch 趋近于 1，继续用 η_launch 做容量规划会系统性高估所需批量。代价转移到了别处：Graph 要求捕获期内的参数地址、grid/block 形状固定，动态 shape 或数据依赖的控制流必须回退到非图路径，捕获本身也有一次性编译与显存驻留成本；persistent kernel 则要自行实现跨迭代的任务队列与同步，一旦 occupancy 被常驻块占满，其他 kernel 的并发空间被压缩。具体例子：一个逐 token 解码的采样 kernel，单次 T_kernel 只有几微秒，串行模型下 η_launch 极低，但把它放进 Graph 后瓶颈立刻变成采样内部的访存与归约，此时优化方向应从“合并 launch”转向“减少 kernel 内的同步点”。

第二种失效来自并发流。多流并发下，一条流的 T_launch 可以被另一条流的 T_kernel 覆盖，单流串行模型里那个显式的加号不再对应真实的墙钟时间；此时实际下界是 max(T_kernel, T_queue) 的资源竞争版本，而非简单相加。判断是否落入这一区间，要看 SM 占用与拷贝引擎是否已饱和：若两条流的 kernel 各自只占用部分 SM，launch 隐藏成立；若它们争抢同一组 SM 与 L2，隐藏就变成排队，T_queue 反而上升。代价是正确性上的：多流并发要求对共享缓冲区做显式事件同步，漏掉一个 event 就会产生数据竞争，而这种错误在单流模型下根本不会出现。工程判断上，只有当单 kernel 的 SM 占用显著低于满载、且流间无数据依赖时，才应把 T_launch 视为可隐藏项。

第三种失效是规模上限本身。批量摊销的收益随批量增大而递减，因为 T_kernel 随批量近似线性增长，而 T_launch 是常数，η_launch 的改善在 T_kernel ≫ T_launch 之后趋于饱和；继续加大批量只会抬高 T_queue 与显存占用，并把尾延迟拉长。下表给出定性判断而非实测值：

区间主导项公式是否适用主要代价
T_kernel ≪ T_launch提交开销适用，η_launch 低CPU 占用、驱动排队
T_kernel ≈ T_launch两者叠加适用，最敏感区批量或 Graph 收益最大
T_kernel ≫ T_launch，单流计算退化，加号可忽略显存与 T_queue 上升
Graph / persistent计算不适用，T_launch≈0捕获约束、常驻占用
多流并发资源竞争不适用，需 max 形式同步正确性、L2 争用

因此这套模型的有效域应写成一条可检验的判据：先测出单次 launch 的端到端固定开销与目标 kernel 的执行时间，若二者同量级且系统为单流串行，则 η_launch 是可信的优化指标；若已引入 Graph、persistent kernel 或多流，则必须改用 max 形式并重新定位瓶颈，否则批量策略会在错误的区间里继续加码，把本已饱和的计算项和排队项进一步推高。

摊销模型的适用边界：从单流串行假设到多流隐藏

前述利用率公式的成立依赖一个未被明说的前提：工作负载在单流上严格串行提交，且每次提交的端到端固定开销 T_launch 都完整暴露在关键路径上。一旦这个前提被打破，公式给出的 η_launch 就不再是可优化的目标，而只是一个被高估的代价项。具体地，当 CUDA Graph 把整段 kernel 序列一次性实例化后，T_launch 从每次提交的 CPU 提交加驱动加启动开销，退化为图实例的单次重放开销，量级落到微秒级以下；此时分母中 T_launch 相对 T_kernel 可忽略，公式退化为纯计算界 η→1，继续按“批量化摊薄 launch”的思路调参只会把注意力从真正的瓶颈（T_kernel 内的访存与占用率）上移开。同理，persistent kernel 把循环留在 GPU 内部，主机侧只提交一次，T_launch 被彻底移出稳态路径。

更常见的失效来自多流并发。当多个 stream 同时有可提交工作、且驱动侧提交队列未饱和时，一个流的 T_launch 可以与另一个流的 T_kernel 重叠，单流串行模型下逐次累加的固定开销被隐藏进别的流的计算窗口。此时真实吞吐由最慢流的 T_kernel 与队列深度共同决定，而非各流 T_launch 之和；用单流公式估算多流配置会系统性低估吞吐，进而误导是否值得引入 Graph 的工程判断。判定是否已进入该区间的可操作信号是：把流数从 1 增到 2 后，端到端时延未按预期翻倍下降，说明 T_launch 已被隐藏而非被摊薄。

$$\eta_{\text{launch}}=\frac{T_{\text{kernel}}}{T_{\text{launch}}+T_{\text{kernel}}}\ \text{仅在}\ T_{\text{queue}}\ll T_{\text{kernel}}\ \text{且单流串行时成立}$$

规模上限则体现在另一侧：当 T_kernel 本身已经远大于 T_launch（例如大 tile 的 GEMM 或长序列 attention），η_launch 接近 1，此时再增大 batch 只增加显存占用与排队时间 T_queue，摊薄收益趋零，而 T_queue 一旦超过 T_kernel，公式中的 max 项接管，端到端时延由排队而非计算决定。工程上应把优化预算从“继续合并 launch”转向降低 T_kernel 或拆分队列；反过来，当 T_kernel 与 T_launch 同量级时，Graph 或 persistent kernel 的引入才有明确收益，且需付出图实例化的一次性编译与显存代价，以及捕获期间对动态 shape 与主机回读的约束。

条件公式状态应关注的代价

Graph / persistent kernel退化为纯计算界捕获约束、显存驻留
