一 · 一句话直觉：把 batch 当“并行度旋钮”，而不是“语义参数”

批不变性（batch invariance）的直觉可以压缩成一句工程判据：batch size 是调度层的并行度旋钮，不是计算语义的参数。同一个请求 x，无论它在服务端被塞进 b₁=1 的独占批次，还是被拼进 b₂=64 的动态批次，kernel 对这条请求应当给出同一个答案——逐位相同，或至少落在事先声明的数值容差内。换句话说，b 只允许影响“算得多快、占用多少 SM、切几个 tile”，不允许影响“算出什么”。

这句话之所以值得单独拎出来，是因为在 GPU 上它并不自动成立。一个 reduction kernel 在 b=1 时可能走单 block 串行归约，在 b=64 时被切成 split-K、多 tile 并行归约再二次合并；浮点加法不满足结合律，归约树的形状一变，舍入误差的累积路径就变，末位结果随之漂移。批不变性要求的正是：把这种由并行度引入的漂移，压到零或压进声明容差。

代价首先体现在性能侧。为了守住逐位一致，kernel 往往被迫放弃随 batch 自适应调整的归约切分，例如固定 tile 数与累加顺序、禁用 split-K 的动态选择，于是大 batch 下拿不到最优的并行度。这类约束的直接代价是 SM 占用率与有效带宽利用率的下降，表现为大 batch 吞吐不及“自由切分”版本；而收益是可复现性——同一请求在任意批次组合下结果稳定。工程判断的分水岭在于：这份吞吐损失是否小于服务端因结果漂移导致的排障与回滚成本。

二 · 严格定义：无穷范数下的最大偏差与双阈值判据

把直觉形式化，需要一个能覆盖“逐位一致”与“数值近似一致”两种诉求的判据。定义批不变性偏差为：对同一输入 x，在所有 batch 配置对上的输出最大绝对差，取无穷范数：

$$\Delta_{\text{BI}}=\max_{b_1,b_2}\;\left\|f(x;b_1)-f(x;b_2)\right\|_{\infty},\qquad \text{pass}\iff \Delta_{\text{BI}}\le \tau_{\text{bit}}\;\text{or}\;\Delta_{\text{BI}}\le\tau_{\text{num}}$$

变量含义如下：b₁、b₂ 是两个不同的 batch size 配置（可以是 1 与 64，也可以是 32 与 33 这类非整除关系，后者更容易暴露 tile 边界效应）；Δ_BI 是批不变性偏差，用无穷范数是因为我们关心“最坏的那个输出元素”，而不是平均漂移——服务端一个 token 的 logit 错了就足以改变采样结果；τ_bit 是逐位一致容差，通常取 0，即要求两次运行的输出位模式完全相同；τ_num 是数值容差阈值，必须由任务显式声明，不能由 kernel 作者临时拍脑袋。

判据是“或”关系而非“与”：要么严格逐位一致（τ_bit=0 时 Δ_BI 必须恰为 0），要么落进声明的数值容差。这个结构承认了一个事实——逐位一致在很多 kernel 上不可达，强行要求它等于要求放弃所有自适应并行策略。因此工程上真正可执行的是第二条路径，但它的前提是 τ_num 被写进契约、被测试覆盖、被下游消费方知晓。

代价体现在验证成本上。Δ_BI 是对所有 (b₁,b₂) 对取 max，配置对数量随支持的 batch 范围呈平方增长；若服务端支持 1 到 256 的任意 batch，朴素枚举就是数万对比较，每对都要跑一次前向并做逐元素比对。实践中靠采样关键边界（1、tile 整数倍、tile 整数倍±1、最大 batch）来压缩，但采样本身引入漏检风险，这是一笔必须计入验证预算的时延与显存开销。

具体例子：一个 layernorm 类 kernel 在 b=1 时用单 warp 做 32 元素归约，在 b=64 时每个 block 处理一行、用 4 个 warp 做树形归约。两种归约树的加法顺序不同，Δ_BI 在 fp32 下通常落在 1e-7 量级（相对量级），若任务声明 τ_num=1e-5 则通过；若下游是要求逐位复现的回归测试，则必须改写成固定归约顺序，代价是大 batch 下并行度受限。

三 · 为什么需要：动态 batching 把“离线正确”变成“在线漂移”

需要批不变性的根本原因不在单机测试，而在服务端的运行形态。推理服务普遍采用动态 batching：请求到达时间不确定，调度器把当前排队请求拼成一批送进 GPU，batch size 随负载实时波动。于是同一个用户请求，在低峰期可能独占 b=1，在高峰期被拼进 b=64。如果 kernel 的输出依赖 b，那么“同一请求两次调用结果不同”就不是偶发 bug，而是系统性的、与负载相关的不可复现漂移。

这种漂移的破坏力在于它破坏了可复现性这条工程底线。离线评测里 agent 优化出的 kernel 在固定 batch 下跑出漂亮数字，Δ_BI 却从未被测过；上线后用户报告“同样的问题两次回答不一样”，排障时却无法在实验室复现，因为实验室的 batch 配置和服务端的动态拼批永远对不上。批不变性测试的作用就是把这类问题从“线上玄学”拉回“离线可判定”。

代价维度是 token 与时延。对 logits 类输出，微小差异经 softmax 后可放大：两个 logit 相差 1e-6，在温度参数较小或 top-k 边界附近时，足以让 argmax 翻转，进而改变采样出的 token，整条生成轨迹分叉。这不是危言耸听的数量级推演，而是 softmax 的指数放大特性决定的定性事实——Δ_BI 在 logits 空间可以很小，在概率空间与 token 空间却可能被放大到不可忽略。因此 τ_num 不能只在 logits 上声明，还要评估其对下游采样环节的传导。

具体例子：一个 fused softmax kernel 在 b=1 时用单 block 完成整行归约，在 b=32 时按行并行、每行一个 block，两者的 max 与 sum 归约顺序不同，导致分母有末位差异。若该差异恰好落在两个候选 token 的概率差之内，采样结果翻转。工程上的应对不是把 τ_num 调大蒙混过关，而是要么固定归约顺序，要么在契约中声明“本 kernel 不保证 token 级可复现”，让下游调度层知情。

四 · 常见误解之一：逐位一致是默认可达的

最常见的误解是认为“同一个 kernel、同一份输入，结果当然一样”。这在 GPU 上不成立，因为归约顺序随 batch 改变是必然的：split-K 把 K 维切成多段并行累加再合并，不同 batch 下切分段数不同；tile 数随 batch 变化，每个 tile 内部的累加次序也随之变化。只要归约树形状变了，浮点加法的舍入路径就变了，Δ_BI 就非零。

更精确地说，失效条件是结构性的而非偶发的：归约顺序随 batch 改变（split-K、不同 tile 数）必然引入非零 Δ_BI，逐位一致要求往往不可达。这不是实现质量问题，而是并行归约的数学本质——浮点加法不满足结合律，(a+b)+c 与 a+(b+c) 在末位上可以不同。因此把 τ_bit=0 当作默认验收标准，等于要求 kernel 放弃所有随 batch 自适应的并行策略，这在性能上通常不可接受。

代价是双重的。若坚持逐位一致，就要固定归约切分，大 batch 下 SM 利用率下降、吞吐受损；若放弃逐位一致转向 τ_num，就要承担容差声明与传导评估的验证成本，并且必须接受“某些边界输入下 token 可能翻转”的残余风险。工程判断在于：对确定性要求极高的场景（回归测试基线、审计复现）守 τ_bit=0；对吞吐优先的在线服务用 τ_num 并在契约中写清。

具体例子：一个矩阵乘 kernel 在 b=1 时 K 维不切分，在 b=64 时切 4 段 split-K 再合并。两次运行的累加顺序完全不同，fp32 下 Δ_BI 非零。若测试脚本用 torch.allclose 的默认容差去比，可能恰好通过；但若用位比较，必然失败。误解的根源就在于把“allclose 通过”误读为“逐位一致”。

五 · 常见误解之二：容差可以事后补、可以拍脑袋定

第二个误解是把 τ_num 当成可以事后填的橡皮图章。事实是：τ_num 需按任务声明，它是一份契约的一部分，而不是测试失败后的补救措施。若容差在 kernel 写完之后才由作者凭经验设定，那么它衡量的就不再是“这个 kernel 是否满足任务要求”，而是“这个 kernel 恰好漂移了多少”——判据被结果反向污染，验证失去意义。

正确的顺序是：任务先声明输出语义与可接受偏差（例如“logits 相对误差不超过某阈值，且采样 token 在固定种子下一致”），kernel 再去满足它。Δ_BI 的测量是对照这份声明做判定，而不是反过来用测量值去定义声明。这也解释了为什么判据写成“或”结构：τ_bit 与 τ_num 是两条不同严格度的契约路径，选哪条由任务决定，不由实现便利决定。

代价在于契约维护成本。τ_num 一旦声明，就要覆盖所有支持的 batch 配置对，且要评估其对下游（softmax、采样、beam search）的传导；任务变更时容差可能需重新标定，这是一笔持续的验证开销。相比之下，“拍脑袋定一个 1e-5”看似省事，实则把风险推给了线上——漂移在容差内通过测试，却在服务端因负载相关的 batch 组合触发翻转。

具体例子：某 kernel 作者在测试失败后把 τ_num 从 1e-6 放宽到 1e-4 使测试变绿。表面上 Δ_BI 判据通过了，但该容差从未评估过对 softmax 的放大效应，也未写进下游契约。上线后动态 batching 下出现 token 级不一致，排障时才发现容差是事后补的、没有传导分析。这就是把判据当装饰品的代价。

六 · 常见误解之三：批不变性等于“固定 batch 下可复现”

第三个误解是把批不变性混同于“同一 batch 下多次运行结果一致”。后者只是确定性（determinism），前者要求跨 batch 配置的一致性，严格得多。一个 kernel 完全可以在 b=64 下每次运行都逐位相同（因为归约顺序固定），却在 b=1 与 b=64 之间产生非零 Δ_BI——这正是动态 batching 场景下最危险的情形：单 batch 测试全绿，跨 batch 漂移潜伏。

机制上，这两类一致性受不同因素支配。固定 batch 下的可复现性取决于是否使用了非确定性原子操作、是否受调度抖动影响；跨 batch 的一致性取决于归约树形状是否随 b 变化。前者可以通过禁用 atomicAdd 的浮点版本、固定线程映射来解决；后者必须通过固定切分策略或声明容差来解决。把两者混为一谈，会导致测试设计漏掉最关键的一维——batch 配置对。

代价体现在测试矩阵的规模上。只测固定 batch 的确定性，测试量是线性的（每个 batch 跑几遍）；测跨 batch 的 Δ_BI，测试量是配置对的组合，且要覆盖 tile 边界。这笔时延与显存开销是批不变性验证的主要成本，也是它容易被省略的原因。但省略它的后果是把风险转移到服务端，而服务端的动态 batching 恰恰是最难复现的环境。

具体例子：一个 kernel 在 b=64 下连跑十次结果完全一致，测试报告写“确定性通过”。但服务端把同一请求分别以 b=1 和 b=64 调度时输出不同，Δ_BI 非零。根因是 b=1 走了不同的归约分支。这说明“固定 batch 可复现”这个测试项对批不变性毫无覆盖力，二者必须作为独立判据分别测量。

批不变性的边界：何时它不可达，以及代价落在哪

把批不变性当成一个“开关”是常见误解。它本质是一个声明式契约：agent 优化出的 kernel 必须对同一输入 x 在任意两个 batch 配置 b₁、b₂ 下给出可接受的一致结果。判据写成无穷范数形式，是因为服务端最关心单个元素的最坏漂移，而非平均误差：

$$\Delta_{\text{BI}}=\max_{b_1,b_2}\;\left\|f(x;b_1)-f(x;b_2)\right\|_{\infty},\qquad \text{pass}\iff \Delta_{\text{BI}}\le \tau_{\text{bit}}\;\text{or}\;\Delta_{\text{BI}}\le\tau_{\text{num}}$$

这里 τ_bit 通常取 0，代表逐位一致；τ_num 则必须由任务显式声明，不能由 agent 自行放宽。边界的第一条硬约束来自归约结构：只要 kernel 的归约顺序随 batch 改变——split-K 的分段数随 b 变化、tile 数随 occupancy 调整、跨 block 的原子累加顺序不确定——浮点加法的非结合性就必然产生非零 Δ_BI。此时逐位一致在数学上不可达，不是“优化不够努力”，而是方案本身越界。工程判断是：对含跨 batch 归约的算子，直接声明 τ_num 并按任务敏感性定值，比追求 τ_bit=0 更诚实。

第二条失效条件更隐蔽：τ_num 的合格线不等于下游合格线。对 logits 类输出，softmax 的指数放大效应会把微小差异转成概率分布上的可见偏移，Δ_BI 在 logits 上达标却在采样结果上翻车。因此容差必须按最终消费该张量的算子来定，而不是按产生它的 kernel 来定。表中给出三类典型边界：

场景Δ_BI 可达性主要代价
逐元素算子（无跨 batch 归约）τ_bit=0 可达几乎为零，仅需固定计算图
split-K 归约（GEMM 类）τ_bit 不可达，须 τ_num固定分段数换取确定性，牺牲部分 occupancy
logits→softmax 链路τ_num 需按概率误差反推容差收紧导致可选 kernel 变少

系统代价体现在三个方向。其一是性能：为压住 Δ_BI，agent 往往被迫放弃 batch 自适应启发式（如按 b 选 tile、按 b 调 split-K 段数），把最优配置钉死成对最坏 b 也安全的保守版本，时延在中等 batch 区间明显劣化。其二是验证成本：Δ_BI 要对 b₁、b₂ 的组合做扫描，每个组合都要跑正确性 oracle，评测 token 与 GPU 时间随配置对数增长；若再叠加 NCU profile 定位漂移来源，单条样本的验证开销可达普通正确性检查的数倍。其三是搜索空间收缩：τ_num 一旦收紧，大量依赖动态归约划分的候选 kernel 直接被判失败，RL 的可行解集变小，收敛所需的采样轮次上升。一个具体例子：某 reduction kernel 在 b=1 时走单 block 全归约、b≥8 时走 split-K 四段，两路径的累加顺序不同，Δ_BI 稳定非零；agent 若坚持 τ_bit=0，只能退化为全 batch 统一单 block 路径，吞吐随 b 增长迅速饱和——这正是“正确性契约反向绑架性能”的典型形态。
