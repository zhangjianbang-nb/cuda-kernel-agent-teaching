一 · 逐项拆解：T_launch 到底由什么构成

公式里的 T_launch 被定义为“单次 launch 的端到端固定开销（CPU 提交+驱动+启动）”，这个括注本身就是推导的第一块砖：它把三个物理上分离的阶段压成一个标量。拆开看，CPU 提交阶段是 host 侧构造参数、写命令缓冲区、进入运行时 API 的路径；驱动阶段是运行时到内核态驱动、再到 GPU 前端（pushbuffer 解析、通道调度）的转换；启动阶段是 GPU 侧网格配置、CTA 分配、常量/参数上传到片上存储的固定流水。这三段在时间上串行，但它们的成本结构完全不同：CPU 提交随参数规模与 API 选择（runtime vs driver）变化，驱动段近似常数，启动段则与网格维度、每块共享内存、寄存器占用有关，而与 kernel 实际做了多少计算无关。

推导的关键一步是承认这三段无法在单流串行模型里被计算重叠掉。设一次迭代的计算量为 W，硬件的有效吞吐为 R，则 T_kernel = W / R。若把 T_launch 视为与 W 无关的常数，则有效利用率

$$\eta_{\text{launch}}=\frac{T_{\text{kernel}}}{T_{\text{launch}}+T_{\text{kernel}}}=\frac{1}{1+T_{\text{launch}}\,R/W}$$

这个改写把“开销占比”翻译成了“计算量与开销的比值”的函数：分母里出现的是 T_launch·R，即“在开销时间内硬件本可完成的计算量”。它给出一条硬判据——当 W 与 T_launch·R 同量级时，η 掉到 50% 附近，吞吐由 launch 频率而非计算决定。举例：一个逐元素缩放 kernel，若单次只处理一个小张量，其 W 远小于 T_launch·R，即便 kernel 内部做到访存饱和，端到端时间仍由提交路径主导；把同样的工作合并成一次大网格调用，T_launch 只付一次，η 随 W 线性回升。代价在于批量化的显存占用与尾延迟：合并意味着中间结果必须同时驻留，峰值内存上升，且单次调用的完成时间变长，对小批量请求的响应变差。

二 · max 项的来源：排队等待为何不能并入 T_kernel

公式写成 T_step = T_launch + max(T_kernel, T_queue) 而不是简单相加，是因为 T_queue 与 T_kernel 在时间轴上部分重叠：一旦命令进入 GPU 通道，前序工作的执行与本次 kernel 的执行是同一硬件资源上的串行占用，而排队等待发生在“命令已提交但尚未开始执行”的窗口。若队列为空，T_queue 趋近于零，max 退化为 T_kernel；若队列拥塞，T_queue 主导，此时再优化 kernel 内部毫无收益——这正是多轮 agent 反复调优 kernel 却看不到端到端提升的典型场景。

推导中容易被忽略的近似在于：T_queue 被当作与 T_kernel 独立的标量，但真实队列的等待时间取决于前序工作的剩余时长分布，是一个随机变量而非定值。工程上取 max 是一种保守的确定性上界近似，它假设排队与执行不重叠，从而高估了拥塞时的总时延。这个近似在单流串行、队列深度为一的理想条件下是精确的；一旦引入异步提交或多流，误差方向反转——实际时延低于公式预测，因为提交与执行可以并行。代价是：用该公式做容量规划会偏保守，导致为并不存在的拥塞预留资源；反过来，若忽略 T_queue 只测空载 T_launch，则会系统性低估生产环境的步时。

具体机制上，T_queue 的测量必须与 T_launch 分离：在提交后插入事件记录、在 kernel 开始执行时再记录一次，两次之差即排队窗口。若只测 API 返回时间，得到的是提交成本而非排队成本，两者在拥塞时相差一个数量级。正确性代价在于事件插入本身引入额外同步点，会改变被测量的流水行为，因此测量代码与生产代码必须分开评估。

三 · 摊销的离散化：批量 B 如何进入公式

把单次调用扩展为批量 B 次独立工作，有两种截然不同的摊销方式，公式对二者的处理不同。第一种是“一次 launch 处理 B 份工作”，此时

$$\eta_{\text{batch}}=\frac{B\,T_{\text{kernel}}^{(1)}}{T_{\text{launch}}+B\,T_{\text{kernel}}^{(1)}}\;\xrightarrow{B\to\infty}\;1$$

其中 T_kernel^{(1)} 是单份工作的执行时间。摊销的斜率是 T_launch / (B·T_kernel^{(1)})，即开销被稀释的速度与 B 成反比。第二种是“B 次 launch 各自处理一份工作”，则总时间为 B(T_launch + T_kernel^{(1)})，η 与 B 无关——批量化本身不摊销任何东西，摊销来自“合并提交”而非“增加工作量”。这是推导中最容易出错的一步：许多实现把循环里的逐次调用改成循环外的单次大调用，误以为 B 增大自动带来收益，实际上收益全部来自 T_launch 从 B 次降为 1 次。

离散化近似出现在两处。其一，T_kernel^{(1)} 被假设为常数，但批量增大后单份工作的执行时间会因占用率下降、缓存竞争、尾块不均而漂移，公式的线性外推在 B 较大时高估收益。其二，网格维度必须按 B 取整，若 B 不能被每块工作数整除，会引入空转 CTA，这部分计算量计入 T_kernel 却不产生有效输出，等价于在分子里掺入无效项。具体例子：一个按行处理的归一化 kernel，若每块固定处理 8 行而 B 不是 8 的倍数，最后一块的利用率不足，端到端时间高于公式预测；把每块行数改为运行期参数可消除该偏差，但代价是启动段需要读取更多参数、常量上传变大，T_launch 略微上升。

四 · 失效条件的推导：Graph 与 persistent kernel 如何改写公式

给定事实指出，CUDA Graph 或 persistent kernel 可把 T_launch 降到微秒级以下，此时公式退化为纯计算界。推导路径是：Graph 把多次提交的 CPU 与驱动段一次性录制、后续重放只付一次解析成本，因此 T_launch 从“每次调用一份”变为“每张图一份”，摊销分母从 B 次调用变成 1 次录制加 B 次重放。代入 η 表达式，T_launch 项相对 T_kernel 可忽略，η→1，公式退化为 T_step ≈ max(T_kernel, T_queue)。persistent kernel 走的是另一条路：内核常驻、由设备侧循环取任务，host 侧提交被彻底移除，T_launch 不再出现在每次迭代的时延里，取而代之的是任务分发与栅栏同步的成本，这部分成本必须重新建模，不能沿用原公式。

代价是正确性与灵活性。Graph 要求捕获期间的内存地址与网格配置固定，动态形状或运行期决定的参数需要在图外处理，捕获失败会退回到逐次提交，此时公式重新适用而实现者往往没有察觉。persistent kernel 占用 SM 不释放，与同卡其他工作争抢资源，且设备侧循环的终止条件若写错会导致挂起而非报错，调试成本远高于普通 kernel。具体例子：一个由多阶段小 kernel 组成的流水线，逐次提交时 T_launch 主导；录制为单张 Graph 后步时降至计算界，但一旦某一阶段的张量形状随输入变化，整张图失效，必须维护多张按形状分档的图，编译时间与显存（图持有的中间缓冲）随之上升。

五 · 多流并发：单流串行模型的边界

公式的第二个失效条件是多流并发下 T_launch 可被隐藏。机制是：host 侧提交流 A 的 kernel 时，流 B 的 kernel 正在 GPU 上执行，提交段的 CPU 时间与执行段的 GPU 时间落在不同资源上，因而可以重叠。此时端到端时间不再是 T_launch + T_kernel 的串行和，而是各流时间轴上的最大完工时刻。设 n 条流、每条流上 k 次调用，理想重叠下

$$T_{\text{step}}^{\text{multi}}=\max_{i}\Big(k\,T_{\text{kernel}}^{(i)}\Big)+\text{首次提交的}\,T_{\text{launch}}$$

即 T_launch 只在流水线填充阶段付一次，稳态下被完全隐藏。这个改写的前提是 host 提交速度不低于 GPU 消费速度；若提交本身成为瓶颈（例如参数构造昂贵、驱动调用阻塞），则 T_launch 重新浮出水面，多流退化为串行。推导中的近似在于忽略了流间同步：若两条流在某个点需要事件等待，重叠被切断，公式高估收益。

代价是显存与可预测性。多流并发要求各流的中间缓冲同时驻留，峰值内存随流数上升；且流间无全局顺序，错误传播与复现难度增加，同一输入在不同流调度下可能得到不同的浮点累加顺序。具体例子：把一批独立的小规模归约分派到多条流，稳态吞吐接近计算界，但若某条流的输入依赖前一条流的输出，必须插入事件同步，重叠窗口缩短，实测步时向串行公式回归。工程判断上，多流适合无依赖的批量任务，不适合有阶段依赖的流水线——后者应优先考虑 Graph 或设备侧编排。

六 · 公式的适用域与工程判据

综合以上推导，该公式的适用域可以写成三条判据的交集：单流串行提交、T_launch 未被 Graph/persistent 消除、队列深度不超过一。三条同时成立时，公式是精确的；缺一条，误差方向与量级取决于缺失的是哪一条。把判据转成工程动作：先测空载 T_launch（单次极小 kernel 的端到端时间），再测目标 kernel 的 T_kernel，两者之比给出是否需要摊销的信号；若比值接近或超过 1，优先做合并提交或 Graph，而不是继续优化 kernel 内部——后者在 η 很低时对端到端的边际贡献被 T_launch 稀释。

公式还提供了一个反向用途：用实测 η 反推 T_launch，与空载测量交叉验证。若反推值显著大于空载值，说明 T_queue 被误计入 T_launch，此时应分离测量而非调整模型。这个交叉验证的成本是一次额外的计时实验与事件插入，收益是避免把拥塞误诊为提交开销，从而把优化力气花错地方。在 agent 生成 kernel 的评测流程里，这一步尤其关键：执行反馈若只报 kernel 内部时间，会系统性地奖励那些在空载下好看、在真实批量下被 launch 开销吞掉的实现。

公式的适用边界：什么时候 T_launch 可以当作常数，什么时候必须当作变量

把 \(T_{\text{launch}}\) 写成一个固定常数，是这套摊销推导最脆弱的假设。它成立的隐含前提是：提交路径单一、队列空闲、驱动侧无批处理合并。一旦这三个条件中任一被打破，公式里的加法结构就不再成立——因为 \(T_{\text{launch}}\) 不再是串行前置项，而会与 \(T_{\text{kernel}}\) 发生重叠。最典型的失效点是 CUDA Graph：把一串 kernel 捕获成图后，单次重放的 CPU 提交成本被压到微秒级以下，此时 \(T_{\text{launch}}\) 相对 \(T_{\text{kernel}}\) 可忽略，\(\eta_{\text{launch}}\) 趋近 1，公式退化为纯计算界 \(T_{\text{step}}\approx T_{\text{kernel}}\)。这意味着基于该公式做的“批量越大越好”的外推在 Graph 场景下完全失效：继续增大 batch 只会增加 \(T_{\text{kernel}}\)，不再有任何摊销收益，反而抬高显存占用与单步时延。同理，persistent kernel 把 launch 成本一次性支付后常驻 SM，公式中的固定项被移到循环之外，逐迭代的 \(T_{\text{launch}}\) 应视为 0 而非小常数。

第二个失效条件是多流并发。单流串行模型假设 \(T_{\text{launch}}\) 与 \(T_{\text{kernel}}\) 严格串行相加，但在多流场景下，流 A 的 kernel 执行期间，流 B 的 launch 提交可以在 CPU 侧并行完成，\(T_{\text{launch}}\) 被隐藏进 \(T_{\text{kernel}}\) 的窗口内。此时真实的 step 时间不再是两项之和，而更接近 \(\max(T_{\text{kernel}}^{(A)}+T_{\text{kernel}}^{(B)},\,T_{\text{launch}}^{\text{eff}})\)，其中 \(T_{\text{launch}}^{\text{eff}}\) 是 CPU 侧提交全部流所需的总时间。公式给出的 \(\eta_{\text{launch}}\) 会系统性低估有效利用率——它把一个已经被隐藏的成本仍当作显式扣减项。工程判断上，这意味着：用该公式评估多流方案时，得到的“launch 占比”是上界而非实测值，据此做的批量化决策会偏向过度合并，牺牲并行度换取并不存在的摊销。

第三个边界来自 \(T_{\text{queue}}\) 这一项的语义漂移。在单 kernel 串行模型里，\(T_{\text{queue}}\) 表示前序工作造成的排队等待，公式用 \(\max(T_{\text{kernel}}, T_{\text{queue}})\) 取较大者，隐含假设排队与执行不重叠。但在真实流水线中，当前 kernel 的排队时间往往与前一个 kernel 的执行时间部分重叠——GPU 在执行 kernel N 时，kernel N+1 已在硬件队列中就位。此时 \(\max\) 的取值会高估 step 时间，因为 \(T_{\text{queue}}\) 的很大一部分已被前序 \(T_{\text{kernel}}\) 吸收。离散化误差就出在这里：公式把连续重叠的流水线离散成“先排队、再执行”的两段式，重叠部分被重复计入。对短 kernel 密集的负载，这种重复计误会累积成可观的时延高估，进而让 \(\eta_{\text{launch}}\) 显得比实际更差，误导优化方向。

把三个失效条件并排看，可以给出一张判定表，用于决定公式是否还能作为决策依据：

场景T_launch 的角色公式是否适用主要代价
单流、无 Graph、队列空闲串行前置常数适用短 kernel 下吞吐受 launch 频率限制
CUDA Graph / persistent kernel趋近 0，移出循环退化，仅剩计算界Graph 捕获占显存与编译时间；persistent 占满 SM 阻塞其他工作
多流并发被 T_kernel 窗口隐藏不适用，需改用 max 形式流间同步与显存竞争抬高尾延迟
深流水线、短 kernel 密集与 T_queue 重叠高估 step 时间离散化重复计误导致过度合并

落到具体机制上，一个常被忽略的代价是 Graph 捕获本身的显存与编译开销：捕获阶段需要为图中每个节点保留参数缓冲与依赖元数据，图越大，实例化时的显存峰值越高，且捕获后图结构固定，无法在运行时动态改变 batch 形状——这直接把“按负载动态调 batch 以摊销 launch”的策略堵死。因此工程判断应落在：先用公式做粗筛，确认 \(T_{\text{kernel}}\) 与 \(T_{\text{launch}}\) 是否同量级；一旦进入 Graph 或多流路径，就必须放弃该公式的加法结构，改用实测的 step 时间与重叠窗口来评估，否则摊销推导会把优化引向错误的方向。
