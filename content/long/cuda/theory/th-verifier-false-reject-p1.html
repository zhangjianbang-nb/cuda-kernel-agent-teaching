一 · 一句话直觉与严格定义

验证器误拒率（False Reject Rate，FRR）衡量的是：在所有真正正确的 kernel 实现中，被验证器判定为“不通过”的比例。一句话直觉——它是“把好人关进监狱”的概率。与之对偶的误放率（False Accept Rate，FAR）则是“把坏人放出去”的概率。二者不是同一件事的两面，因为它们的分母不同：FRR 的分母是“正确实现集合”，FAR 的分母是“错误实现集合”。这个分母差异是后面一切工程判断的根源。

严格定义如下。设 C 为所有满足规格的正确实现集合，W 为所有不满足规格的错误实现集合，验证器 V 输出 accept/reject。则

$$\text{FRR}=\frac{\#\{\text{correct}\to\text{reject}\}}{\#\{\text{correct}\}},\qquad \text{FAR}=\frac{\#\{\text{wrong}\to\text{accept}\}}{\#\{\text{wrong}\}}$$

注意分子分母都带“correct”前缀：FRR 只在正确样本上统计，因此它无法从“整体通过率”反推。一个验证器整体通过率 90%，可能是 FRR=2% 且 FAR=8%，也可能是 FRR=10% 且 FAR=0%，两者对 agent 搜索的含义截然相反。工程上必须把两个比率分开测量，混在一起会掩盖失效方向。

定义里“correct”本身是一个依赖参考实现的标签：判定一个 kernel 是否正确，靠的是与参考实现比对。于是 FRR 的定义隐含了一个前提——参考实现是对的。这个前提一旦破裂，FRR 与 FAR 同时失真（见失效条件），这也是为什么 FRR 不能当作绝对量，只能当作“相对于某个 oracle 的条件量”。

二 · 为什么需要单独度量 FRR

在 LLM/agent 生成 kernel 的搜索循环里，验证器是唯一的“门”。门有两个方向的错误，但它们在搜索动力学中的后果不对称。FAR 让错误 kernel 进入候选池，浪费后续评测预算并可能污染训练信号；FRR 则直接杀死正确解——agent 明明写对了，却被判错，于是它得到的反馈是“这条路不通”，从而转向别的实现路径，或者在同一路径上做无意义的“修复”。

这种误导的代价可以量化到搜索预算上。设每轮生成 N 个候选，正确率为 p，验证器 FRR 为 r，则每轮被误杀的正确候选期望数为 N·p·r。若 r 不可忽视，等价于把有效正确率从 p 压到 p(1−r)，agent 需要多花约 1/(1−r) 倍的轮次才能命中一个被接受的正解。这是纯 token 与 GPU 时延的浪费，且随 r 非线性放大——因为被误杀的解往往正是“非标准写法但语义正确”的解，而这类解恰恰是 agent 探索多样性的来源。

KernelAudit 的发现给出了现实锚点：6 个 validator 存在不可忽视的 false-reject。这不是个别 bug，而是验证器设计中的系统性现象。原因在于 kernel 正确性判定天然带容差：浮点比较要设 atol/rtol，规约顺序不同导致末位差异，非确定性原子操作导致 run-to-run 抖动。容差收紧会推高 FRR，容差放松会推高 FAR——这是一个无法同时消除的双目标权衡，因此 FRR 必须作为一等待测量指标，而不是“验证器调好之后自然就低”的副产品。

具体例子：一个正确的 warp-level reduction kernel，因归约树形状与参考实现不同，在 1e-6 量级的相对误差上超出验证器设定的 rtol，被判 reject。它在数学上完全正确，却因为“求和顺序”这一与规格无关的自由度被误杀。此类误杀在规约、softmax、layernorm 类 kernel 上尤其密集，因为它们的输出对累加顺序敏感。

三 · 常见误解之一：FRR 是验证器的固有属性

最常见的误解是把 FRR 当成验证器的一个固定常数，仿佛换个验证器就能查表得到它的 FRR。实际上 FRR 是验证器 × 输入分布 × 容差配置的联合函数。同一个验证器，在“agent 生成的接近参考写法的 kernel”上 FRR 很低，在“agent 探索出的等价但结构迥异的 kernel”上 FRR 会显著升高。因为后者与参考实现的数值路径差异更大，更容易触碰容差边界。

这意味着 FRR 不能离线标定一次就写进文档。它随搜索阶段漂移：早期 agent 输出粗糙，正确样本少，FRR 的统计基数小、方差大；后期 agent 输出精细且多样，FRR 的绝对影响反而更大，因为此时被误杀的都是高价值正解。工程判断是：FRR 应当按搜索阶段分桶统计，而不是全局平均。全局平均会把“早期少量正确样本被误杀”和“后期大量正确样本被误杀”混为一谈，掩盖后者对收敛的实质伤害。

另一个相关误解是“FRR 高说明验证器太严，放宽容差即可”。放宽容差确实降 FRR，但同时抬 FAR，而 FAR 抬升会让错误 kernel 混入候选池，污染后续多轮信用分配——agent 会把“被误放的错误解”当成成功经验去模仿。所以容差不是单向旋钮，而是双向杠杆。正确的做法是把 FRR 与 FAR 画成一条随容差变化的曲线，在曲线上选工作点，而不是单独优化其中一个。

四 · 常见误解之二：FRR 可以用整体准确率替代

第二个误解是拿验证器的“整体判定准确率”当作 FRR 的代理。整体准确率 = (TP+TN)/(总数)，它把两个方向的错误混在一起，且被正负样本比例主导。在 agent 搜索场景里，正确样本通常是少数（尤其早期），于是整体准确率几乎完全由 FAR 决定，FRR 的变化被淹没。一个 FRR 从 2% 涨到 15% 的验证器，整体准确率可能只掉一两个百分点，看起来“没问题”，实际上搜索效率已经腰斩。

更隐蔽的是，整体准确率无法区分“误拒了一个正确解”和“误放了一个错误解”在搜索中的不同后果。前者让 agent 失去一条正确路径，后者让 agent 学到一条错误路径。二者对最终产出的影响方向相反，合并成一个标量后信息不可恢复。因此 FRR 必须独立报告，且要报告它的分母——正确样本数，因为小分母下的 FRR 估计不可信。

具体代价：若某轮正确样本只有 8 个，误拒 1 个，FRR 点估计 12.5%，但置信区间极宽，此时不应据此调整容差。工程上应设最小分母阈值，低于阈值只报计数不报比率。这与计时噪声的置信区间处理是同一类统计纪律，只是对象从时延换成了判定结果。

五 · 常见误解之三：FRR 与对抗样本无关

第三个误解是认为 FRR 只关乎“无心之失”，对抗样本只影响 FAR。事实是失效条件明确指出：对抗样本可以同时推高两种错误率。一个精心构造的输入，可以让验证器在正确实现上误判（推高 FRR），也可以在错误实现上误放（推高 FAR）。因为对抗样本攻击的是验证器的判定边界本身，而不是某一个方向。

在 agent 场景里，这种“对抗”未必是恶意攻击，而可能是 agent 在搜索中自发找到的边界样本：它生成的 kernel 在数值上恰好落在容差边缘，验证器时而接受时而拒绝，表现为 run-to-run 不稳定的判定。这种不稳定性对 FRR 的贡献是隐性的——同一正确 kernel 多次评测，部分 run 被拒，FRR 被稀释进噪声里，看起来“还好”，实则每次重跑都在随机丢弃正解。

工程对策是把判定稳定性纳入 FRR 测量：对同一候选重复评测 k 次，统计“至少一次被拒”的比例，作为 FRR 的上界估计。这个量比单次 FRR 更能反映 agent 实际感受到的误杀率，因为 agent 在搜索中会对同一路径反复尝试。代价是 k 倍评测时延与 GPU 占用，需要在预算内选 k。

六 · 定义落地时的两个工程约束

把 FRR 定义落地，有两个绕不开的约束。第一，正确性标签依赖参考实现，参考错则 FRR/FAR 都失真。若参考实现本身有数值偏差或边界处理错误，那么“正确实现”集合的定义就被污染，FRR 的分子分母都不可信。工程上应把参考实现视为 oracle 的一部分并单独验证，而不是默认它正确。第二，容差选择同时改变 FRR 与 FAR，因此 FRR 的报告必须附带容差配置，脱离容差谈 FRR 没有意义。

具体机制上，建议把 FRR 测量嵌入验证流水线：对每个被判 reject 的候选，用更高精度的参考（如 CPU 双精度或形式化检查）复核，若复核判定其正确，则计入 FRR 分子。这一步的代价是额外的复核时延与显存，但它是把 FRR 从“估计”变成“可审计计数”的唯一途径。没有复核，FRR 只是验证器自说自话。

最后落在工程判断上：FRR 不是验证器的“质量分”，而是搜索系统的“漏损率”。它的值只在给定参考、给定容差、给定输入分布下才有意义；它的危害随搜索阶段放大；它的测量必须与 FAR 分离、与分母一起报告、并经过独立复核。把这四点写进验证器的接口契约，比事后调容差更能守住 agent 的搜索预算。

误拒率不是一个标量，而是一条随容差漂移的曲线

把 FRR 当成一个可以“测出来”的固定数值，是这一节要拆掉的第一种误解。严格地说，$$\text{FRR}=\frac{\#\{\text{correct}\to\text{reject}\}}{\#\{\text{correct}\}},\qquad \text{FAR}=\frac{\#\{\text{wrong}\to\text{accept}\}}{\#\{\text{wrong}\}}$$ 这两个量都隐含了一个未写出的自变量：判定所用的容差与比较方式。同一个 kernel 对，在 rtol=1e-2 下被判通过，在 rtol=1e-5 下被判拒绝，分子分母都没变，FRR 却变了。因此工程上更有意义的表述不是“这个 validator 的 FRR 是某个数”，而是“在给定容差族上，FRR 作为容差的函数长什么样”。KernelAudit 报告 6 个 validator 存在不可忽视的 false-reject，其真正含义是：在这些 validator 的默认容差设定下，正确实现被误拒的比例高到会实质影响搜索，而不是说它们在任何容差下都错。把 FRR 画成随容差单调下降、FAR 单调上升的两条曲线，交点才是这个 validator 的工作点；只报一个点而不报曲线，等于隐藏了工作点是被谁选定的。

由此引出 FRR 的第一个边界：它只对“正确”这一侧有定义，而“正确”本身依赖参考实现。若参考实现本身有数值偏差、边界处理错误或未覆盖的 dtype 分支，那么被标为 correct 的集合里混进了实际错误的样本，FRR 的分子被污染——一个真正错误的候选被拒，会被记成一次误拒。此时 FRR 与 FAR 同时失真，且失真方向不可预判：参考偏松会让 FAR 虚高，参考偏紧会让 FRR 虚高。这就是为什么在 kernel 生成流水线里，参考实现的审计优先级不低于 validator 本身；一个未经交叉验证的参考，其下游所有 FRR/FAR 统计都只是自洽的幻觉。代价是显性的：为参考实现建立多后端交叉校验（例如 CPU 高精度版本对照 GPU 版本）会拉长每次评测的时延，并占用额外显存做双份中间张量，这部分开销不进 FRR 分子，却直接吃掉了搜索预算。

第二个失效条件是容差与比较逻辑的耦合。逐元素 allclose 类判定对离群点极其敏感：一个 kernel 在 99.99% 的元素上与参考一致，仅少数元素因归约顺序不同产生末位差异，逐元素判定会整体拒绝，而范数型判定（相对 L2 误差）会接受。两种判定对应的 FRR 可以相差一个量级，但它们对 FAR 的宽松程度也不同。工程判断因此落在“判定算子与容差必须与 kernel 的数值结构匹配”上：归约类 kernel 用范数型判据，逐元素类 kernel 用逐元素判据，混合精度 kernel 需要按 dtype 分层设容差。伪代码层面，一个可用的判定骨架是 reject = (err_elem > tol_elem).any() or (err_norm > tol_norm)，两个阈值分别对应离群与整体漂移，任一触发即拒。这套双阈值把 FRR 从单点变成一个二维工作点，代价是每次判定要做两遍归约，评测时延上升，且两个阈值的标定需要额外的正确样本集，这部分样本集的构造本身就要花 token 与人工。

第三个边界是对抗性。候选 kernel 不是自然分布的样本，而是被 agent 反复修改、朝“通过验证”方向优化的产物。一个被奖励信号驱动的搜索过程会主动寻找判定逻辑的缝隙：例如在输出中注入极小量噪声使逐元素差异恰好落在容差内，或在特定 shape 上走一条数值上“看起来对”的捷径分支。这类样本会同时推高两种错误率——对正确实现它制造了更严苛的比对环境（因为判定阈值被迫收紧以拦截它），对错误实现它找到了放行通道。FRR 在这种分布漂移下不再是 validator 的固有属性，而是 validator 与搜索策略的联合属性。系统代价在这里体现为防御成本：加入随机化比对顺序、多容差交叉判定、对输出做统计检验，都会增加单次评测的时延与显存占用，并消耗额外的验证 token；而不加防御，FRR 的测量值会随搜索轮次漂移，使多轮 RL 中的可验证奖励信号失去可比性。一个具体例子是：同一 validator 在第 1 轮测得的 FRR 与第 10 轮测得的 FRR 不可直接相减，因为第 10 轮的候选分布已经被前 9 轮的误拒反馈重塑过。工程上应把 FRR 的测量绑定到固定的、与搜索隔离的探针集上，探针集的维护成本就是这套方案必须支付的固定税。
