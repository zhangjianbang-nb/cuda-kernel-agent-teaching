一 · 公式的四个符号各自绑定什么测量

把 $$P_{\text{att}}(I)=\min\left(P_{\text{peak}},\; I\cdot B_{\text{eff}}\right)$$ 拆开看，它不是一条从硬件规格书抄下来的线，而是四个各自需要独立标定的量。P_peak 是“该指令组合的实测峰值算力”，注意“该指令组合”这个限定：一个 kernel 里若混着 FP32 FMA、INT 地址运算和少量 SFU 调用，其可达峰值既不是 FP32 的规格峰值，也不是 INT 的规格峰值，而是这条混合指令流在目标 SM 上能稳定发射的吞吐。B_eff 是“实测可持续 HBM 带宽”，它必须用与目标 kernel 访问模式相近的流式读写微基准测出来，而不是用厂商标称带宽乘以一个想当然的折扣系数。I 是算术强度，分子是浮点运算数，分母是 DRAM 字节数——这两个量的口径决定了整条上界是否可信。attain 则是把实测吞吐 P_meas 除以在 I_meas 处取到的上界，落进 [0,1]。

四个量的测量代价并不对称。P_peak 的标定需要构造一条指令密度极高、访存极少的内核，编译时间和反复调参的 token 开销都不小，但一旦标定完可复用；B_eff 依赖访问模式，读密集、写密集、混合读写会给出不同的可持续带宽，因此每换一类 kernel 形态就得重测；I 和 P_meas 则是每个被测 kernel 各自一份，随 kernel 变化。这意味着 attain 的分母不是常量，而是随被测对象漂移的函数——同一份代码换一种数据布局，I 变了，上界跟着变，attain 的可比性就断了。工程上的直接后果是：跨 kernel 比较 attain 之前，必须先确认两者的 I 口径一致，否则比较的是两个不同的分母。

一个具体例子：某 kernel 逻辑上读 A（FP16，M×K）与 B（FP16，K×N），做一次 GEMM 并写回 C。若按逻辑字节数算，I 会得到一个偏乐观的值；但实际 DRAM 流量里含有因 tile 切分导致的 A/B 重复读、因对齐要求产生的 padding、以及 C 的写回字节。把写回计入分母后 I 下降，I·B_eff 这一支随之下移，交点右移，带宽受限区扩大。这就是下一节要展开的离散化问题。

二 · 交点：门槛算术强度从哪一步推出来

两条斜线的交点由 P_peak = I·B_eff 解出，得到门槛算术强度 $$I^{*}=\frac{P_{\text{peak}}}{B_{\text{eff}}}$$。这一步推导本身是初等的，但它的工程含义常被误读：I* 不是硬件的固有属性，而是 P_peak 与 B_eff 两个实测量的比值。若某指令组合的实测峰值只有规格值的六成，I* 就相应下移，意味着更多 kernel 会落进带宽受限区——这不是硬件变差了，而是“这条指令流根本喂不饱算力单元”这一事实被如实反映到了门槛上。反过来，若 B_eff 因为访问模式不佳而低于可持续带宽，I* 上移，原本该被判为带宽受限的 kernel 会被误判成算力受限，attain 随之被高估。

推导中真正需要交代的关键步是“为什么取 min 而不是取加权或取调和”。取 min 的依据是两条资源通道串联：一个 kernel 的每次迭代既要发射指令又要搬运字节，完成时间由较慢的那条通道决定，因此吞吐被较慢者钳住。写成时间形式更清楚：设总 FLOP 为 F、总字节为 D，则算力通道耗时 F/P_peak，带宽通道耗时 D/B_eff，实际耗时不超过两者较大者，吞吐不超过 min(P_peak, D/F·B_eff) = min(P_peak, I·B_eff)。这个推导假设两条通道可以完全重叠（计算与访存并行），一旦重叠不充分——例如依赖链让 load 与 FMA 无法交错——实际吞吐会低于 min，attain 的上界仍然成立但会显得偏松。这正是 attain 作为“上界”而非“预测”的定位：它给的是不可逾越的顶，不是可达的期望值。

代价在这里体现为：取 min 的推导忽略了重叠效率，因此 attain 接近 1 并不自动意味着 kernel 已最优，只意味着它贴近了某一条斜线；attain 明显小于 1 才是有信息量的信号，指向重叠不足、额外流量或指令组合不匹配。一个具体例子：某 elementwise 内核 I 极低（每字节只做几次浮点运算），远在 I* 左侧，其上界就是 I·B_eff；此时提升 P_peak 毫无意义，唯一有效的优化是减少 D 或提高 B_eff（改善合并访问、减少写回）。若工程师误把注意力放在指令优化上，attain 不会动，因为分母压根没被算力那一支钳住。

三 · 离散化：tile、wave 与字节粒度如何进入公式

连续形式的公式假设 FLOP 与 Byte 可以无限细分，但 GPU 执行是离散的：线程块按 tile 切分，SM 按 wave 调度，DRAM 事务按 32B/128B 粒度成交。离散化首先冲击 I 的分母。以 tile 化的 GEMM 为例，若 tile 尺寸为 T_M×T_N，每个 tile 需要读 T_M×K 的 A 片段与 K×T_N 的 B 片段，而相邻 tile 之间共享的边界数据若未被复用，就会产生重复读。设复用率为 r（被复用字节占总读字节的比例），有效字节数从逻辑值 D_log 膨胀为 D_log/(1−r) 量级，I 相应缩小。写成 $$I_{\text{eff}}=\frac{F}{D_{\text{log}}+D_{\text{dup}}+D_{\text{pad}}+D_{\text{wb}}}$$，四项分别是逻辑流量、重复读、对齐 padding 与写回。忽略后三项中的任何一项，都会让 I 偏大、上界偏松、attain 偏小——注意方向：高估 I 会高估上界，从而低估 attain，让一个其实不错的 kernel 显得很差。

离散化的第二个入口是 wave 量化。当网格的线程块数不是 SM 数乘以每 SM 常驻块数的整数倍时，最后一波只有部分 SM 工作，尾波的空转直接压低 P_meas，而这个损失不进入公式的任何一项——公式描述的是稳态吞吐，尾波是瞬态。于是 attain 在尾波显著的 kernel 上系统性偏低，且偏低幅度随问题规模变化。工程判断是：对小规模问题，attain 的低值可能纯粹来自量化损失，不应据此判定 kernel 质量差；应把规模扫一遍，看 attain 是否随规模上升而收敛，收敛点之后才是公式适用的区间。

第三个入口是字节粒度。DRAM 事务以固定粒度成交，一次非对齐的 4B 访问可能触发整条 32B 事务，实际字节数远超逻辑字节。这在 I 的分母上表现为 padding 项的放大，在小维度、窄数据类型（如 FP8、INT4 打包）场景下尤为突出。代价是显存带宽的实际消耗高于逻辑估算，B_eff 的实测值也会因事务粒度不匹配而下降，两项叠加使 I·B_eff 这一支被双重压低。具体例子：某 kernel 以 INT8 存储权重、按 4 字节对齐读取，逻辑上每字节承载 4 个权重元素，但若访问跨事务边界，实际搬运字节翻倍，I 减半，带宽受限上界随之下移一半——这类损失在公式的连续形式里完全不可见，只有把离散化项显式写进分母才能捕捉。

四 · 近似：B_eff 与 P_peak 的标定误差如何传播

公式里的两个“实测”量本身带误差，误差沿乘法和除法传播到上界，再传到 attain。设 B_eff 的相对误差为 ε_B，P_peak 的相对误差为 ε_P，则在带宽受限区 P_att = I·B_eff，上界的相对误差就是 ε_B；在算力受限区上界的相对误差是 ε_P；在交点附近两者混合。attain 的相对误差近似为 ε_B 或 ε_P 加上 P_meas 自身的计时噪声——后者在短 kernel 上可能远大于标定误差。这意味着 attain 的有效分辨率受限于最弱的那一环：若 B_eff 标定只做到 5% 的重复性，attain 的差异小于 5% 就不应被解读为 kernel 优劣。

近似还出现在“可持续”这个词上。B_eff 不是峰值带宽，而是长时间流式访问下能维持的带宽，它依赖访问模式、并发请求数、以及是否与计算争抢资源。用一条纯拷贝微基准测出的 B_eff 去评价一个读写比 3:1 的 kernel，会系统性高估后者的可持续带宽，从而高估上界、低估 attain。更贴近的做法是按目标 kernel 的读写比例构造微基准，代价是每类 kernel 形态都要单独标定，标定本身的编译与运行开销进入工程预算。P_peak 同理：用纯 FMA 循环测出的峰值，对含大量 INT 地址运算的 kernel 是高估；必须按实际指令配比构造混合指令流。

一个具体例子说明误差方向的重要性：若某团队用规格书标称带宽作为 B_eff，上界被抬高，attain 被压低，团队会误以为 kernel 还有很大优化空间，投入人力去改一个其实已贴近真实可持续带宽的实现；反之若 B_eff 测得偏低，attain 虚高，优化动力被过早掐灭。两种错误都源于把近似量当成精确量。工程上的防线是：把 B_eff 与 P_peak 的标定脚本连同其重复性区间一起纳入评测流水线，让 attain 的输出附带一个误差带，而不是一个孤立的标量。

五 · 失效条件的判别：什么时候公式不该被引用

公式的失效条件在给定事实里写得很明确：I 必须按实际 DRAM 流量计算，用逻辑字节数会高估上界；P_peak 必须取该指令组合的实测峰值，而非规格标称值。这两条各自对应一类可判别的失效。第一类失效可通过对比 I_log 与 I_eff 检出：若两者差距超过某个阈值（例如重复读与写回合计使分母翻倍），则基于 I_log 的 attain 不可引用。第二类失效可通过对比纯指令微基准与混合指令微基准的峰值检出：若混合峰值显著低于纯峰值，则用纯峰值算出的上界偏松。

还有一类失效不在给定事实的显式列表里，但由公式结构推出：当 kernel 的行为不由稳态吞吐主导时——例如极短 kernel 被 launch 开销主导、或尾波占比很高——公式描述的是稳态，实测吞吐里混入了非稳态成分，attain 失去解释力。判别方法是扫描问题规模：若 attain 随规模单调上升并在某点后走平，走平前的点落在失效区；若 attain 不随规模收敛，说明存在与规模无关的固定开销在主导，公式不适用。这类判别的代价是每个 kernel 要跑一组规模点，计时噪声在最小规模上最大，需要足够的重复次数才能把趋势和噪声分开。

具体例子：一个融合了多种算子的 kernel，前半段是带宽受限的归一化，后半段是算力受限的矩阵乘。整段用一个 I 去套公式，得到的上界既不对应前半段也不对应后半段，attain 是一个没有物理意义的混合数。正确做法是按阶段切分，各自算 I 与上界，再按时间加权合成整体 attain；代价是需要分段计时（如用 CUDA event 在阶段边界打点），分段本身引入的同步开销会轻微扰动测量。工程判断是：只要 kernel 内部存在明显的受限类型切换，单一 I 的公式就应被拆开使用，否则 attain 的数值不可归因。

六 · 从公式到可复算的评测记录

要让这条公式在评测流水线里可信，每个 attain 数值背后必须能复算出四个量及其口径。最小记录集是：I 的分子分母各自的口径说明（逻辑流量、重复读、padding、写回是否计入）、B_eff 的标定方法与重复性区间、P_peak 的指令配比与实测值、P_meas 的计时方法与噪声水平。缺任何一项，attain 就退化为一个不可审计的标量，跨 kernel、跨版本、跨硬件的比较都失去依据。这套记录的成本是每次评测多存几行元数据，收益是当 attain 出现异常时能立刻定位是分子口径变了、分母标定漂了，还是实测本身被噪声污染。

可复算性还要求公式的离散化项显式化。把 $$I_{\text{eff}}=\frac{F}{D_{\text{log}}+D_{\text{dup}}+D_{\text{pad}}+D_{\text{wb}}}$$ 写进记录，而不是只存一个 I 的标量，使得后来者能判断某次 attain 偏低是重复读造成的还是写回造成的——这两种原因的优化路径完全不同，前者靠改进 tile 复用，后者靠减少中间结果落盘。代价是需要在 kernel 侧插入计数器或借助 profile 工具拆解流量，这本身有测量开销，但对被判为“需要优化”的 kernel 而言，这笔开销换来的是可归因的优化方向。

最后落在工程判断上：这条公式的价值不在于给出一个精确数字，而在于它把“性能差距”分解成可分别验证的几项——I 的口径、B_eff 的标定、P_peak 的配比、以及离散化损失。当 attain 显著小于 1 时，正确的下一步不是笼统地说“还有优化空间”，而是按这四项逐一排查：分母是否漏计了流量、B_eff 是否被访问模式压低、P_peak 是否因指令混合而不可达、离散化项是否吃掉了本可复用的字节。每一项都有对应的测量手段和优化动作，公式的作用是把排查路径结构化，而不是替代排查本身。

斜线交点之后：上界公式的失效边界与系统代价

公式本身只有两行，但它的可信度完全押在三个量的测量口径上。第一是 I 的分母：必须按实际 DRAM 流量计，含写回字节、为对齐或 tile 形状引入的 padding、以及因缓存未命中而重复读的字节。用逻辑字节数（例如"输入张量是 N×N 个 float"）代入，会把 I 系统性抬高，于是 Patt 被高估，attain 反而被压低——一个本来已经贴着带宽墙跑满的 kernel，会被误判成"还有优化空间"，进而把后续多轮优化预算浪费在不可能收敛的方向上。第二是 Ppeak：必须取该 kernel 实际指令组合的实测峰值，FP32 FMA 与 INT 混合、含特殊函数单元、含 shared memory 广播的指令流，其可达峰值都低于规格书标称值；用标称值代入会让算力受限区间的斜线整体上移，把交点右移，从而把一批本已算力受限的 kernel 错误归类为带宽受限。

离散化的近似发生在两个地方。其一，Beff 是"实测可持续带宽"，它不是一条直线：访问模式从纯流式读转为读改写、从合并访问转为跨 stride 访问时，有效带宽会随工作集与并发度变化，把单点实测值当作全域常数，等价于假设带宽墙是一条水平线，而真实情况下它在小工作集与不规则访问处会向下弯折。其二，Ppeak 随 occupancy 与指令级并行变化，低 occupancy 下算力墙同样会下移。两条斜线各自被"钉"在一个测量点上，交点附近的判定因此最不可靠——恰恰是 attain 最接近 1、最需要精确判断的那一段。

$$\text{err}(I)=\frac{P_{\text{att}}^{\text{logic}}(I)-P_{\text{att}}^{\text{dram}}(I)}{P_{\text{att}}^{\text{dram}}(I)}=\frac{I_{\text{dram}}}{I_{\text{logic}}}-1$$

上式给出逻辑字节口径带来的相对高估：只要实际 DRAM 流量比逻辑字节多出比例 r，上界就被高估 r/(1+r)。写回与 padding 在小 tile、非对齐形状上轻易把 r 推到可观量级，此时 attain 的分母虚高，评分失真。系统代价方面，把 I 与 Beff 测准需要额外的 profile 轮次（NCU 采集 DRAM 计数器、多工作集扫描带宽曲线），这直接增加每次评估的时延与 token 预算；而若为省成本退回逻辑字节口径，代价则转移到判定质量上——错误的上界会污染可验证奖励信号，让 RL 在多轮迭代中奖励"看起来更接近上界"的伪优化。工程判断是：交点附近的 kernel 必须用 DRAM 实测口径复算一次上界，远离交点的两端才可以容忍粗口径。
