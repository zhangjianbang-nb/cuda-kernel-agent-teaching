一 · 适用边界的第一道闸门：I 必须按实际 DRAM 流量计

Roofline 的可达上界 P_att 是 I 的函数，而 I 的分母是“每字节 DRAM 流量”。这里的“DRAM 流量”不是逻辑张量字节数，而是经 L2 过滤后真正落到 HBM 上的字节数。两者之间的差额，就是公式失效的第一类来源。一个典型例子是 GEMM 的 tile 化：逻辑上读 A、B 两个矩阵各一次，但若 tile 尺寸选得让同一块 B 被多个 block 重复从 HBM 拉取，实际流量可以是逻辑量的数倍，I 被高估同样倍数，P_att 随之虚高，attain 被系统性压低——这不是 kernel 差，是分母错了。写回同理：一个 in-place 归约若把中间结果写回 DRAM 再读回，逻辑字节数完全看不到这笔往返。padding 与对齐填充（如把 N 补到 128 的倍数）也计入实际流量却不计入逻辑形状。工程上唯一可信的做法是从 NCU 的 dram__bytes_read/write 计数器取值，而不是从 PyTorch 张量 shape 反推。代价是测量链路变长：一次 profile 采集本身要引入 replay 开销，且在长 kernel 上采样窗口可能截断，需要多次采集取稳定段。判断规则很直接：当 $$I_{\text{actual}}=\frac{\text{FLOP}}{B_{\text{dram}}^{\text{read}}+B_{\text{dram}}^{\text{write}}}$$ 与逻辑口径的 I 相差超过一个可接受阈值时，任何基于逻辑 I 的“离上界还差多少”结论都应作废，改用实测口径重算。

二 · 第二道闸门：P_peak 是指令组合的函数，不是规格书数字

规格书上的峰值 FLOPS 通常对应“纯 FP32 FMA 流”或“纯 Tensor Core 路径”这类理想指令组合。真实 kernel 是混合的：地址计算用 INT、边界判断用谓词、归约用 shuffle、激活用 SFU。这些指令与 FMA 争用同一套 issue 端口与寄存器带宽，导致可持续峰值低于标称值。失效条件因此写得很明确：P_peak 必须取该指令组合下的实测峰值。一个具体例子是带 mask 的 softmax：exp 走 SFU、比较走 FP32、地址走 INT，其可持续 FLOP/s 明显低于纯 FMA 微基准；若拿规格书峰值当 P_peak，attain 会被算成“远未达标”，从而误导优化方向去堆并行度，而真实瓶颈是 SFU 吞吐与指令混合比。测量方法是构造一个与目标 kernel 指令配比近似、但数据全部驻留寄存器/共享内存的微基准，测其稳态吞吐，作为该配比下的 P_peak。代价是这类微基准的编译与调参时间不小，且配比近似本身有误差；对快速迭代场景，可以用“同一 kernel 把数据规模缩到 L2 可容纳”的变体近似，但要注意此时瓶颈已从 HBM 转向 L2，不能直接外推。工程判断：当 kernel 的指令混合显著偏离纯 FMA（例如 SFU 或 INT 占比可观），用标称峰值算出的 attain 只能当“乐观上界下的下界”，不能当验收口径。

三 · 规模上限：当工作集落进 cache，roofline 的斜线失去意义

Roofline 的两条斜线以 HBM 为内存层级假设。一旦工作集小于 L2（甚至小于共享内存可容纳规模），带宽项 B_eff 不再是 HBM 带宽，而是 L2 或 SMEM 带宽，量级差异可达一个数量级以上。此时公式仍能算出一个数，但它描述的不再是目标场景。这是规模上限的失效：小规模 benchmark 上 attain 接近 1，不代表大规模生产负载上也能接近 1；反过来，小规模上 attain 低，可能只是 launch 与尾部效应占比过大。一个具体例子是 reduction：N 从几千扩到上亿，前者的数据几乎全在 L2，实测吞吐远超按 HBM 带宽算的 P_att，attain 大于 1 的荒谬结果会直接暴露口径错误（公式定义 attain∈[0,1]，越界即说明 P_att 用错了层级）。另一端的规模上限是并行度耗尽：当 grid 规模小到无法填满 SM，或大到尾部 wave 占比显著，P_meas 被 occupancy 与尾效应主导，roofline 的“稳态吞吐”假设不成立。代价体现在评测设计上：必须显式声明 benchmark 的规模区间，并把规模外推当作独立风险项；跨规模比较 attain 时，要么固定规模，要么同时报告两端的绝对吞吐。工程判断：把“工作集是否超出 L2”作为是否启用 roofline 评分的前置检查，超出才计分，否则改用绝对时延或带宽利用率口径。

四 · 稳态假设的破裂：短 kernel、动态形状与不规则访存

公式隐含“稳态”语义：足够长的执行窗口内，带宽与算力都达到可持续水平。短 kernel 打破这一点——启动、warp 填充、尾部 drain 占比高，P_meas 是瞬态平均而非稳态值。动态形状打破得更彻底：I 随 shape 变化，单点 attain 无法代表一个 shape 分布；若用分布上的平均 I 去算单个 P_att，等于把非线性函数套在均值上，误差方向不可控。不规则访存（gather/scatter、稀疏）则让“每字节对应固定 FLOP”这一线性关系失效：实际带宽由访存模式决定，B_eff 本身随数据分布漂移，公式退化为“用一组实测常数近似一个非平稳过程”。一个具体例子是 embedding lookup 类 kernel：逻辑 FLOP 极低、I 接近 0，roofline 判定为纯带宽受限，但随机行访问使有效带宽远低于顺序流带宽，P_att 用顺序 B_eff 会高估，attain 被低估。代价是评测方差：这类 kernel 的重复测量离散度显著高于规则 kernel，单次 attain 不可信，需要分布级报告（这与计时噪声的处理是两件事，此处只强调口径随 shape 漂移）。工程判断：对 shape 敏感或不规则访存的 kernel，roofline 只作为“量级筛查”，不作为细粒度评分；评分应绑定具体 shape 与访存模式。

五 · 失效条件的组合与判定流程

上述四类失效很少单独出现。一个真实 kernel 可能同时：用逻辑字节算 I、用标称峰值算 P_peak、工作集部分落进 L2、shape 动态。此时 attain 的偏差是乘性的，无法靠单点校正挽回。可操作的判定流程是串行闸门：先查工作集是否超出 L2（否则换口径）；再查 NCU 实测 DRAM 字节与逻辑字节的比值（偏离则重算 I）；再查指令混合是否偏离纯 FMA（偏离则换实测 P_peak）；最后查执行窗口是否足够长、shape 是否固定（否则只做量级筛查）。每一步的代价不同：L2 检查几乎零成本（看 shape 与 dtype 即可估算），DRAM 字节比对需要一次 profile，指令混合微基准成本最高。因此流程应按成本从低到高排序，尽早短路。一个具体例子：某 fused kernel 在小 batch 上 attain 报 0.95，按流程先查工作集——落进 L2，直接判定该评分不适用于大 batch 场景，无需再做后续测量，省下一次完整 profile 的时延开销。工程判断落在最后一段：roofline 的可达上界是一个“条件成立时才可引用”的量，工程上应把适用条件作为评分元数据与数值一起输出，让下游消费者知道这个 attain 在什么前提下有效；缺了条件的 attain 数字，比没有数字更危险。

公式成立的前提：I 与 P_peak 都必须“按实测算”

roofline 上界本身只是一次取小，真正决定它能否当“可达上界”用的是两个输入量的口径。第一个是算术强度 I。公式里 I=FLOP/Byte 的分母必须是实际 DRAM 流量，而不是 kernel 逻辑上“应该读多少”。一个 tiled GEMM 在逻辑上读 A、B 各一遍，但分块后 B 被重复读、边界 tile 有 padding、写回 C 又是一次完整流量，实际字节数往往是逻辑字节数的若干倍。用逻辑字节数算 I，会把点画到交点右侧，得出一个偏高的 P_att，attain 随之被系统性低估——你以为是 kernel 不够好，其实是分母错了。工程上必须用 NCU 的 dram__bytes_read/write 实测值反算 I，而不是从张量形状推。第二个是 P_peak。规格书的标称 FLOPS 对应的是理想指令流（纯 FP32 FMA、无依赖停顿、满 occupancy），而真实 kernel 里 FP32 FMA 与 INT 地址计算、分支、类型转换混编，SM 的 issue 能力被分摊，实测峰值可能明显低于标称。用标称值当 P_peak，算力受限段的斜线被抬高，attain 被压低，优化方向会被误导到“继续堆 FMA”而不是“减少非浮点指令”。

这两个口径错误叠加时，roofline 的“上界”性质就破了：它不再是一个可达上界，而变成一个既可能高估（I 偏大）又可能低估（P_peak 偏大）的混合估计，attain 落在 [0,1] 之外也不奇怪。判断公式是否仍然成立，第一步不是看 kernel，而是看这两个量是不是实测反算出来的。一个可操作的检查是：把同一 kernel 的 NCU 实测 dram 字节与逻辑字节对比，比值明显大于 1 就说明 I 必须修正；把 microbenchmark 的纯 FMA 峰值与混编指令流的实测峰值对比，差距明显就说明 P_peak 要按指令组合取。这两步不做，后面所有 attain 数字都不可信。

规模上限：当工作集落进 cache，roofline 的“DRAM 受限”前提消失

roofline 的带宽斜线假设性能被 HBM 字节数卡住，这个假设只在工作集大于末级 cache、且数据确实每次都要从 DRAM 取时成立。当问题规模缩小到 L2 能容纳，重复读命中 cache，实际 DRAM 流量骤降，I 按实测 dram 字节算会变得极大，点被推到算力受限段甚至交点右侧很远，此时 P_att 退化为 P_peak，roofline 不再提供任何有区分度的信息——它只说“你别超过峰值算力”，这对优化没有指导意义。反过来，小规模下 launch 开销、尾部 wave 不满、occupancy 不足成为主导，实测吞吐远低于任何斜线，attain 低但原因不在 roofline 覆盖的维度内。规模上限因此是双向的：太大时公式仍成立但优化空间被带宽锁死；太小时公式的假设（DRAM 受限或算力受限二选一）不再成立，测量的是另一套开销。

判断规模是否越界，可以看实测 dram 字节与理论工作集大小的比值：接近 1 说明数据确实走 DRAM，公式适用；明显小于 1 说明 cache 吃掉了流量，此时应改用 cache 带宽或直接放弃 roofline 改用延迟/占用率分析。另一个信号是 attain 随规模的非单调变化：如果缩小规模后 attain 反而下降，多半是 launch 与尾部开销盖过了 roofline 描述的瓶颈，公式的解释力已经让位。工程上把 roofline 用在“工作集远大于 cache、且单次 launch 的 wave 数足够多”的区间，越界区间换用别的模型，不要硬套。

指令组合与访存模式改变时，斜线本身要重画

P_peak 是“该指令组合的实测峰值”，这意味着换一种指令组合，roofline 的两条斜线都要重画，而不是沿用上一版。FP32 FMA 密集的 kernel 与 INT 重、含大量 shared memory 搬运或 Tensor Core 指令的 kernel，其可达峰值不同，B_eff 也随访问模式变化：连续合并访问能接近 HBM 峰值，而跨步、非对齐、bank 冲突的访问会把 B_eff 拉低，带宽斜线的斜率随之变小。此时若仍用“通用”的 B_eff 与 P_peak 画线，attain 的分子分母口径不一致，结论失真。一个具体例子是带 padding 的卷积：padding 区域的读入是真实 DRAM 流量但不产生有效 FLOP，I 被拉低，点左移，看起来“带宽受限”，实际是无效流量在吃带宽——这不是 roofline 失效，而是提醒你 I 的分母已经把无效流量算进去了，优化方向应是消除 padding 流量而非提高算力。

更隐蔽的失效是写回与重复读被漏算。一个 in-place 或带中间缓冲的 kernel，写回字节与读入同量级，若只按读入算 I，点会偏右；一个 reduction 类 kernel 多次读同一块数据，重复读若未命中 cache 就是真实 DRAM 流量。这些都会让 I 偏离实测口径。代价体现在误判上：把带宽受限误判为算力受限，会去优化指令而实际瓶颈在流量，白花编译与调优时间；反之亦然。判断方法是拿 NCU 的 dram 读写字节分别代入，看 I 是否随优化动作（如合并访问、去 padding）同步变化——若 I 变了而 attain 没变，说明你动的不是 roofline 描述的那个瓶颈。

斜线在什么条件下会变成一条谎

Roofline 的两条斜线不是物理定律，而是三个假设的推论：流量只走 DRAM、带宽与算力可同时饱和、指令组合的峰值是常数。任一假设破裂，P_att 就从“上界”退化为“乐观估计”，attain 会被系统性抬高，优化方向随之失真。最隐蔽的一种破裂来自 I 的分子分母口径不一致：分母若取逻辑字节数（张量形状乘 dtype 宽度），就漏掉了写回、padding 到对齐边界、因 bank 冲突或 tile 切分导致的重复读、以及 reduction 的中间落盘。一个 128×128 的 tile 若按 132 列对齐填充，DRAM 流量立刻多出约 3%；注意力类 kernel 若把 K/V 按 block 重复搬运，重复读的倍数可达个位数。此时真实 I 远低于账面值，公式给出的上界被高估，attain 却显得“还有余量”，诱导工程师继续在算力侧加码。

第二种破裂在 P_peak。规格书的 FLOPS 是单一指令、满占用、无依赖链的理想值；实际 kernel 里 FP32 FMA 与 INT 地址运算、谓词、分支混合发射，SM 的 issue 槽位被切碎，实测峰值往往显著低于标称。用标称值代入，P_att 偏大，attain 偏小，看起来“离上界还远”，实际已贴着真实天花板。B_eff 同理：它必须是该访问模式（stride、粒度、并发度）下的可持续带宽，而非 STREAM 峰值；小规模、低占用或非合并访问会把 B_eff 压到峰值的几分之一，此时斜线斜率本身是错的。

$$\text{attain}_{\text{true}}=\frac{P_{\text{meas}}}{\min\left(P_{\text{peak}}^{\text{real}},\; I_{\text{real}}\cdot B_{\text{eff}}^{\text{real}}\right)}$$

规模上限是第三种边界。当工作集小于 L2、问题规模小到启动与尾部延迟占主导、或 grid 不足以填满 SM 时，kernel 既不受 DRAM 带宽约束也不受峰值算力约束，而受限于延迟与占用率——roofline 的横轴 I 失去意义。以一个 batch=1、序列极短的 decode kernel 为例，其时间几乎全花在 launch 与同步上，实测吞吐远低于两条斜线中的任一条，attain 的数值没有诊断价值。工程判断是：先确认工作集确实溢出 L2、占用率足以隐藏延迟、流量口径按 DRAM 计数器（而非逻辑字节）核算，再谈 attain；否则应改用延迟模型或直接看 NCU 的 stall 归因。
