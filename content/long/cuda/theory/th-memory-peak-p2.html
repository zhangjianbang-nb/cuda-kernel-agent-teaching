一 · 公式的逐项语义：为什么 max 只作用在 tmp 上

先把公式摆正：

$$M_{\text{peak}}=M_{\text{in}}+M_{\text{out}}+\max_{\text{stage}}M_{\text{tmp}}(\text{stage})\le M_{\text{budget}}$$
这个式子的结构不是随手写的，它编码了一条关于 kernel 生命周期的断言：输入与输出张量的生命周期覆盖整个执行区间，因此它们的占用在任何时刻都必须计入；而临时缓冲是分阶段申请、分阶段释放的，同一时刻通常只有一个阶段的 tmp 活着，所以取 max 而不是求和。这一步推导的关键前提是「阶段间串行且前一阶段 tmp 在下一阶段开始前已释放」。一旦这个前提被打破——比如双缓冲流水、跨阶段复用的 workspace、或者为了隐藏时延而预取的下一阶段缓冲——max 就退化为 sum，公式必须改写为 M_in+M_out+Σ_stage M_tmp(stage) 的悲观上界。工程上判断该用哪个版本，不看代码注释，看 allocator 的实际驻留曲线：如果两个阶段的 tmp 指针地址区间重叠且生命周期有交集，就是 sum 语义。

逐项含义上还有一处容易读错的地方：M_in 并不等于「用户传入的张量大小」。kernel 内部常见的 layout 转换（如 NCHW→NHWC 的 transpose、padding 到对齐边界、dtype 提升到 fp32 做归约）会派生出一份输入副本，这份副本在语义上属于 M_in 的放大项而非 M_tmp，因为它与原始输入同时存活。把它错记到 M_tmp 里，会让 max 项低估，进而让整个上界失真。代价是具体的：一个 batch 内 transpose 副本若按 fp32 存放，相对 fp16 原始输入就是 2 倍占用，在 KV cache 挤压场景下直接换算成可并发序列数的下降。

二 · 推导关键步：从「时刻快照」到「阶段上界」

严格推导应从连续时间的驻留函数出发：设 A(t) 为 t 时刻 allocator 已分配且未释放的字节数，则 M_peak = max_t A(t)。要把它变成可计算的离散形式，需要做三步近似。第一步是时间离散化：把执行切成以 kernel launch 或 stage 边界为粒度的采样点，只在边界处取 A(t)。这一步会漏掉阶段内部的瞬时峰值——典型例子是归约树在中间层需要一份与输入等大的 partial buffer，而这份 buffer 在阶段开始和结束时都不存在。漏采的代价是上界偏低，且偏低量随归约深度增长。第二步是空间聚合：把同一 stage 内所有并发存活的缓冲合并为一个标量 M_tmp(stage)，这要求我们知道 stage 内的最大并发集合，而不是简单相加。第三步才是取 max。三步之中，第一步的误差最难控，因为它依赖采样粒度而非代码结构。

离散化误差有一个可操作的收紧手段：在 stage 内部插入显式的 allocator 统计重置点，读取 cudaMemGetInfo 或框架 allocator 的 reserved/allocated 双计数，取二者之差作为该点的真实占用。伪代码思路是：在每个 stage 入口记录 baseline，在 stage 内每次大块申请后记录 delta，取 stage 内 delta 的最大值作为 M_tmp(stage)，而不是用 stage 结束时的残留值。这里必须强调「重置统计」不是可选步骤：allocator 的缓存池会把已释放的块保留在 reserved 里，若不重置，测得的 reserved 会把历史峰值带进当前 stage，造成高估；反之若只看 allocated，又会漏掉碎片导致的额外 reserved 扩张。两种偏差方向相反，工程上应同时记录并分别报告。

三 · 失效条件的量化形态：shape、batch 与多流

公式右侧的 M_budget 是线上预算，左侧是测量值，比较本身简单，失效却发生在测量口径上。第一类失效是 shape 依赖：M_tmp 对 shape 的敏感度远高于 M_in/M_out，因为临时缓冲的尺寸常由 tile 数、归约维度、对齐 padding 共同决定，其中任何一项随 shape 变化都可能让 max 项跳变。单 shape 测量低估的机制是：小 shape 下 tmp 可能小于输入，大 shape 下 tmp 可能反超，若只测小 shape，max 项被系统性压到输入量级以下。第二类失效是 batch 依赖：batch 增大时 M_in/M_out 线性增长，而 M_tmp 可能因分块策略改变而呈阶梯式增长，二者不同步，导致「按单样本内存乘以 batch」的外推失效。第三类失效是多流并发：公式默认单流，多流时各流的 M_peak 在时间上可能重叠，总占用是各流驻留曲线的逐点和，而不是各自峰值的 max。把单流峰值当作并发预算，等于假设流间完全错峰，这在生产调度里几乎不成立。

代价可以落到具体机制上：以 KernelBench-Verified 的观察为锚，28% 的核增加了峰值内存，这个比例说明「用更大中间缓冲换速度」是一种普遍存在的优化方向，而非边缘现象。对生产端，峰值内存的增量直接换算为 KV cache 可用容量的减少与并发预算的压缩——这不是抽象的百分比，而是可并发请求数的下降。因此公式的用途不是事后审计，而是作为生成阶段的硬约束：在候选 kernel 进入正确性验证之前，先用离散采样估计 M_peak，超预算的直接淘汰，避免把编译与 profiling 的 token 花在注定不可部署的候选上。

四 · 一个具体例子：归约核的 tmp 项如何被低估

考虑一个沿长轴归约的 kernel：输入 fp16、输出 fp16，中间需要 fp32 累加缓冲与一份分块 partial sum。按公式逐项拆：M_in 是输入张量本身加上 layout 对齐 padding；M_out 是输出；M_tmp 在 stage 1（分块累加）是 fp32 累加器，尺寸与输入块数成正比，在 stage 2（跨块合并）是 partial sum 数组。若实现采用两阶段串行，max 项取两者较大者；若实现为了隐藏时延把 stage 2 的 partial buffer 预取到 stage 1 末尾，两者生命周期重叠，max 必须换成 sum，峰值上升量等于较小的那一份。低估的典型来源是把 fp32 累加器记成「与输出同尺寸」——实际它按块数分配，块数由 tile size 决定，tile 越小块数越多、tmp 越大。这就把 shape 依赖引了进来：同一份代码在小 shape 下 tmp 可忽略，在大 shape 下 tmp 成为主导项。验证这一点的最小实验是在两个相差一个数量级的 shape 上分别做重置统计后的采样，比较 M_tmp/M_in 的比值是否稳定；比值不稳定即说明公式的 max 项不可用单点测量外推。

五 · 近似边界与工程判断

公式的三处近似各有明确的适用边界。时间离散化的边界是「stage 内无瞬时峰值」，一旦归约树深度或流水线级数增加，就必须加密采样点或改用解析上界。空间聚合的边界是「stage 内并发集合已知」，对于依赖运行时分派（如 autotune 选出的不同 tile 配置）的 kernel，并发集合随配置变化，聚合前必须先固定配置再测。max 语义的边界是「阶段串行且及时释放」，任何跨阶段复用或预取都会把它推向 sum。工程判断上，应把公式当作两级筛子：第一级用解析上界（sum 语义）做保守淘汰，保证不漏；第二级用重置统计后的实测 max 做精确判定，保证不误杀。两级之间的差距本身就是优化空间——缩小这个差距意味着减少不必要的预取或提前释放，而这正是峰值内存约束下最值得做的改动。

峰值公式的失效边界：从逐项含义到测量口径

把峰值拆成三项不是记账习惯，而是三种不同的失效来源。$$M_{\text{peak}}=M_{\text{in}}+M_{\text{out}}+\max_{\text{stage}}M_{\text{tmp}}(\text{stage})\le M_{\text{budget}}$$ 其中 M_in 与 M_out 由调用方给定、kernel 无法单方面压缩，真正可优化的是 M_tmp；但 max 算子意味着峰值由最坏那一个 stage 决定，而不是由平均临时占用决定。于是“把临时缓冲做大以换取更少同步或更高 occupancy”这类生成策略，代价会全部落在 max 上：只要有一个 stage 的缓冲翻倍，整条链路的上限就被它钉死。反过来，若某个 stage 的临时量虽大却与其他 stage 串行、可复用同一块 workspace，则 max 不会叠加——这正是推导里最关键的一步：临时缓冲的峰值是**按生命周期区间求并集后的最大值**，而不是各次分配的算术和。allocator 的复用行为因此直接进入公式，而不是公式之外的实现细节。

离散化与近似发生在两处。其一是 stage 的划分：编译器看到的是一串指令，工程上按 kernel launch 边界或 tile 循环边界切 stage，切得粗会把不重叠的生命周期误判为重叠，切得细则引入分析开销与保守估计。其二是 shape 依赖：M_tmp 通常是 (tile 数 × tile 大小 × dtype) 的函数，而 tile 数随 batch、序列长度、问题规模变化，因此单 shape 测量得到的 max 只是该 shape 下的一个采样点，对更大 batch 会系统性低估。生成侧若以单 shape 的 profile 作为奖励信号，模型会学到“在这个 shape 下不超预算”的局部策略，而不是“在预算内随 shape 缩放”的策略。代价是可量化的：低估导致线上 OOM 或被迫降低并发；高估则浪费 KV cache 空间。前者是正确性事故，后者是吞吐损失，两者都不体现在 kernel 自身的时延数字里。

测量口径是第三个失效点，且最容易被误认为已经解决。allocator 的缓存池会保留已释放的块，使 nvidia-smi 或框架级统计显示的是“高水位”而非“当前真实需求”；若在多次迭代之间不重置统计，峰值会被历史最大占用污染，无法反映本次 kernel 的真实 M_tmp。正确做法是在目标 kernel 前后插入统计重置点，并以分配器自身的峰值计数器为准，而不是外部采样。多流并发时公式还要再改一次：各流的 M_tmp 不能取 max，而要在时间轴上求叠加，即 $$\max_t \sum_{s} M^{(s)}_{\text{tmp}}(t)$$ 单流测量得到的预算余量在多流下会成倍收紧。工程判断因此落在两点：一是把 M_tmp 的 shape 依赖显式写进生成与验证的约束里，让奖励函数对超预算的 shape 也给出惩罚；二是把峰值测量做成带重置、带多流叠加的口径，否则公式左侧只是一个在特定条件下成立的近似，而 28% 的核增加峰值内存这一事实说明，这个近似在生成分布上并不罕见。

峰值公式的失效边界：谁在悄悄改写 M_tmp

把 $$M_{\text{peak}}=M_{\text{in}}+M_{\text{out}}+\max_{\text{stage}}M_{\text{tmp}}(\text{stage})\le M_{\text{budget}}$$ 当作验收判据时，真正危险的不是等式本身，而是 max 这个算子被误读成“与输入无关的常数”。M_tmp 的每一项都由 kernel 的 tiling 与流水深度决定：以 shared memory 双缓冲为例，单块占用为 $$M_{\text{smem}}=2\cdot B_t\cdot B_k\cdot d\cdot s$$，其中 B_t 为 tile 行数、B_k 为归约维块宽、d 为数据类型字节数、s 为每元素暂存份数（累加器、规约树中间值等）。当 B_k 随归约维长度增长而抬升，或流水级数从 2 提到 3，M_tmp 呈线性上升，而 M_in/M_out 不变——于是“同一个 kernel、同一个 shape 家族、只改归约维”就能把峰值顶穿预算。工程上必须把 M_tmp 表达为 (shape, tile 参数, 流水深度) 的函数再取 max，而不是测一次就写死。

离散化与近似发生在两处，代价性质完全不同。其一是对齐与填充：为满足 128B 事务与 bank 冲突规避，tile 宽常被向上取整到 2 的幂，实际占用 $$M_{\text{smem}}^{\text{real}}=2\cdot \lceil B_t\rceil_{32}\cdot \lceil B_k\rceil_{32}\cdot d\cdot s$$，取整浪费在窄 shape 上可达数倍，这是纯容量代价、不影响正确性。其二是统计口径的近似：allocator 的缓存池会把已释放块留在池中，使 nvidia-smi 或框架计数器读到的是“池占用”而非“活跃峰值”，真实峰值被系统性低估；必须在测量前重置统计并禁用缓存复用，否则 M_peak 的读数只是历史高水位。此外多流并发时各流峰值叠加，单流测得的 max 不能直接代入预算不等式，需按并发流数做保守放大。

正确性侧的代价同样来自这条公式的松弛。用更大的中间缓冲换速度，典型手法是把整段归约结果物化到全局显存再二次规约，以避免跨 block 同步；这消除了原子竞争与重排误差，却把 M_tmp 从片上搬到 HBM，同时引入一次额外的写回与读回带宽开销，端到端时延随中间张量尺寸线性增长。反过来，为压峰值而做的分块累加会改变浮点求和顺序，在长归约上放大舍入误差，必须以更高精度的累加器或补偿求和换取正确性裕度，这又抬高了寄存器与片上占用。判断准则很直接：当 M_budget 的余量小于单次 tile 的 M_tmp 时，任何“换速度”的缓冲扩张都不成立，应退回分块方案并接受带宽代价。
